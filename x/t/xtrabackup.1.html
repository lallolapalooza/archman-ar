النسخ الاحتياطي التدريجي

تحضير النسخ الاحتياطي التدريجي

بعد إجراء النسخ الاحتياطي الأساسي، يمكنك التقدم من خلال النسخ الاحتياطي التدريجي. يتم تطبيق دلتا النسخة الاحتياطي التدريجي على النسخة الاحتياطي الأساسية، مما يؤدي إلى التدحرج بالبيانات إلى النقطة الزمنية للنسخة الاحتياطي التدريجي:

xtrabackup --prepare --target-dir=/data/backups/base \
--incremental-dir=/data/backups/inc1

في هذا المثال، ستكون نتيجة مجلد النسخة الاحتياطي الأساسية مطابقة للنسخة الاحتياطي الأساسية.

إعداد النسخة الاحتياطي التدريجي الثاني هو عملية مماثلة: قم بتطبيق دلتا النسخ الاحتياطي الأساسية (المعدلة)، وستقوم بتدوير بياناتها إلى الأمام في الوقت المناسب للنسخة الاحتياطي التدريجي الثاني:

xtrabackup --prepare --target-dir=/data/backups/base \
--incremental-dir=/data/backups/inc2

ملاحظة:

يجب استخدام --apply-log-only عند دمج جميع النسخ الاحتياطي التدريجي باستثناء الأخير. لهذا السبب لا يحتوي السطر السابق على الخيار --apply-log-only. حتى لو تم استخدام --apply-log-only في الخطوة الأخيرة، فسيظل النسخ الاحتياطي متسقًا ولكن في هذه الحالة سيقوم الخادم بتنفيذ مرحلة التراجع.

إذا كنت ترغب في تجنب الإشعار بأن InnoDB لم يتم إيقافه بشكل طبيعي، عندما تقوم بتطبيق دلتا المطلوبة على النسخة الاحتياطي الأساسية، يمكنك تشغيل --prepare مرة أخرى دون تعطيل مرحلة التراجع.

استعادة النسخ الاحتياطي التدريجي

بعد تحضير النسخ الاحتياطي التدريجي، يحتوي المجلد الأساسي على نفس البيانات مثل النسخة الاحتياطي الكامل. لاستعادة هذه النسخة الاحتياطي، يمكنك استخدام هذا الأمر: xtrabackup --copy-back --target-dir=BASE-DIR

قد تحتاج إلى تغيير الملكية كما هو مفصل في restoring_a_backup.

النسخ الاحتياطي التدريجي المتدفق باستخدام xbstream

يمكن إجراء النسخ الاحتياطي التدريجي المتدفق باستخدام خيار البث xbstream. حاليًا، يتم تجميع النسخ الاحتياطي بتنسيق xbstream مخصص. مع هذه الميزة، تحتاج إلى إجراء نسخة احتياطي أساسية أيضًا. إجراء نسخة احتياطي أساسية.INDENT 0.0

$ xtrabackup --backup --target-dir=/data/backups


إجراء نسخة احتياطي محلية.INDENT 0.0 
$ xtrabackup --backup --incremental-lsn=LSN-number --stream=xbstream --target-dir=./ > incremental.xbstream


فك النسخة الاحتياطي.INDENT 0.0 
$ xbstream -x < incremental.xbstream


إجراء نسخة احتياطي محلية وتدفقها إلى الخادم البعيد وفكها.INDENT 0.0 
$ xtrabackup --backup --incremental-lsn=LSN-number --stream=xbstream --target-dir=./
$ ssh user@hostname " cat - | xbstream -x -C > /backup-dir/"


النسخ الاحتياطي الجزئي

يدعم xtrabackup إجراء نسخ احتياطي جزئي عندما يكون الخيار innodb_file_per_table ممكّنًا. هناك ثلاث طرق لإنشاء نسخ احتياطي جزئي:

1.
مطابقة أسماء الجداول بتعبير نمطي
2.
توفير قائمة بأسماء الجداول في ملف
3.
توفير قائمة بقواعد البيانات

تحذير:

لا تقم بنسخ النسخة الاحتياطي المعدة مرة أخرى.

يجب استعادة النسخ الاحتياطي الجزئي عن طريق استيراد الجداول، وليس باستخدام الخيار --copy-back. لا يُنصح بتشغيل النسخ الاحتياطي التدريجي بعد تشغيل نسخة احتياطي جزئي.

على الرغم من وجود بعض السيناريوهات التي يمكن فيها إجراء الاستعادة عن طريق نسخ الملفات مرة أخرى، فقد يؤدي ذلك إلى عدم تناسق قاعدة البيانات في العديد من الحالات وليس طريقة موصى بها للقيام بذلك.

لأغراض صفحة الدليل هذه، سنفترض أن هناك قاعدة بيانات تسمى test تحتوي على جداول تسمى t1 و t2.

تحذير:

إذا تم حذف أي من الجداول المطابقة أو المدرجة أثناء النسخ الاحتياطي، فسيفشل xtrabackup.

إنشاء النسخ الاحتياطي الجزئي

هناك طرق متعددة لتحديد الجزء الذي يتم نسخه احتياطيًا من إجمالي البيانات:

  • استخدم الخيار --tables لسرد أسماء الجداول
  • استخدم الخيار --tables-file لسرد الجداول في ملف
  • استخدم الخيار --databases لسرد قواعد البيانات
  • استخدم الخيار --databases-file لسرد قواعد البيانات

خيار --tables

تتضمن الطريقة الأولى خيار --tables الخاص بـ xtrabackup. قيمة الخيار هي تعبير نمطي تتم مطابقته مقابل اسم قاعدة البيانات الكامل واسم الجدول باستخدام تنسيق databasename.tablename.

لنسخ الجداول الموجودة في قاعدة البيانات test فقط، استخدم الأمر التالي:

$ xtrabackup --backup --datadir=/var/lib/mysql --target-dir=/data/backups/ \
--tables="^test[.].*"

لنسخ الجدول test.t1 فقط، استخدم الأمر التالي:

$ xtrabackup --backup --datadir=/var/lib/mysql --target-dir=/data/backups/ \
--tables="^test[.]t1"

خيار --tables-file

يحدد الخيار --tables-file ملفًا يمكن أن يحتوي على أسماء جداول متعددة، اسم جدول واحد في كل سطر في الملف. سيتم عمل نسخة احتياطي للجداول المسماة في الملف فقط. تتم مطابقة الأسماء بشكل دقيق، حساسة لحالة الأحرف، بدون أي مطابقة نمط أو تعبير نمطي. يجب أن تكون أسماء الجداول كاملة التحديد بتنسيق databasename.tablename.

$ echo "mydatabase.mytable" > /tmp/tables.txt
$ xtrabackup --backup --tables-file=/tmp/tables.txt

خيارا --databases و --databases-file

يقبل الخيار ` --databases` قائمة مفصولة بمسافات من قواعد البيانات والجداول التي سيتم عمل نسخة احتياطي لها بتنسيق databasename[.tablename]. بالإضافة إلى هذه القائمة، تأكد من تحديد قواعد البيانات mysql و sys و

performance_schema. هذه القواعد البيانات مطلوبة عند استعادة قواعد البيانات باستخدام xtrabackup --copy-back.

ملاحظة:

قد تتم أيضًا إضافة الجداول التي تمت معالجتها أثناء خطوة --prepare إلى النسخة الاحتياطي حتى لو لم يتم إدراجها صراحةً بواسطة المعلمة إذا تم إنشاؤها بعد بدء النسخة الاحتياطي.
$ xtrabackup --databases='mysql sys performance_schema test ...'

خيار --databases-file

يحدد الخيار --databases-file ملفًا يمكن أن يحتوي على قواعد بيانات وجداول متعددة بتنسيق databasename[.tablename]، اسم عنصر واحد في كل سطر في الملف. تتم مطابقة الأسماء بشكل دقيق، حساسة لحالة الأحرف، بدون أي مطابقة نمط أو تعبير نمطي.

ملاحظة:

قد تتم أيضًا إضافة الجداول التي تمت معالجتها أثناء خطوة --prepare إلى النسخة الاحتياطي حتى لو لم يتم إدراجها صراحةً بواسطة المعلمة إذا تم إنشاؤها بعد بدء النسخة الاحتياطي.

تحضير النسخ الاحتياطي الجزئي

الإجراء مشابه لاستعادة الجداول الفردية: قم بتطبيق السجلات واستخدم الخيار --export:

$ xtrabackup --prepare --export --target-dir=/path/to/partial/backup

عند استخدام الخيار --prepare على نسخة احتياطي جزئي، سترى تحذيرات حول الجداول التي لا توجد. هذا لأن هذه الجداول موجودة في قاموس البيانات داخل InnoDB، ولكن ملفات .ibd المقابلة لها غير موجودة. لم يتم نسخها إلى مجلد النسخة الاحتياطي. سيتم إزالة هذه الجداول من قاموس البيانات، وعندما تقوم باستعادة النسخة الاحتياطي وتشغيل InnoDB، لن تكون موجودة ولن تسبب أي أخطاء أو تحذيرات ليتم طباعتها في ملف السجل.

تعذر العثور على أي ملف مرتبط بمعرف مساحة الجدول: 5

استخدم --innodb-directories للعثور على ملفات مساحة الجدول. إذا فشل ذلك، فاستخدم --innodb-force-recovery=1 لتجاهل هذا ولخسارة جميع التغييرات بشكل دائم على مساحة (مساحات) الجدول المفقودة.

استعادة النسخ الاحتياطي الجزئي

يجب أن يتم الاستعادة عن طريق استعادة الجداول الفردية في النسخة الاحتياطي الجزئي إلى الخادم.

يمكن أيضًا القيام بذلك عن طريق نسخ النسخة الاحتياطي المعدة مرة أخرى إلى datadir "نظيف" (في هذه الحالة، تأكد من تضمين قاعدة البيانات mysql) إلى datadir الذي تنقل النسخة الاحتياطي إليه. يمكن إنشاء قاعدة بيانات نظام باستخدام ما يلي:

$ sudo mysql --initialize --user=mysql

بمجرد تشغيل الخادم، قد ترى mysql يشكو من مساحات جداول مفقودة:

2021-07-19T12:42:11.077200Z 1 [Warning] [MY-012351] [InnoDB] Tablespace 4, name 'test1/t1', file './d2/test1.ibd' is missing!
2021-07-19T12:42:11.077300Z 1 [Warning] [MY-012351] [InnoDB] Tablespace 4, name 'test1/t1', file './d2/test1.ibd' is missing!

لتنظيف قاعدة البيانات اليتيمة من قاموس البيانات، يجب عليك إنشاء مجلد قاعدة البيانات المفقود يدويًا ثم DROP (حذف) قاعدة البيانات هذه من الخادم.

مثال على إنشاء قاعدة البيانات المفقودة:

$ mkdir /var/lib/mysql/test1/d2

مثال على حذف قاعدة البيانات من الخادم:

mysql> DROP DATABASE d2;
Query OK, 2 rows affected (0.5 sec)

الميزات المتقدمة

تحليل إحصائيات الجداول

يمكن لبرنامج xtrabackup تحليل ملفات بيانات InnoDB في وضع القراءة فقط لتقديم إحصائيات عنها. للقيام بذلك، يجب عليك استخدام الخيار --stats. يمكنك دمجه مع الخيار --tables للحد من الملفات التي سيتم فحصها. كما أنه يستخدم الخيار --use-memory.

يمكنك إجراء التحليل على خادم قيد التشغيل، مع احتمال وجود أخطاء بسبب تغيير البيانات أثناء التحليل. أو، يمكنك تحليل نسخة احتياطي من قاعدة البيانات. في كلتا الحالتين، لاستخدام ميزة الإحصائيات، تحتاج إلى نسخة نظيفة من قاعدة البيانات بما في ذلك ملفات السجل ذات الحجم الصحيح.

نعم، لذلك تحتاج إلى التنفيذ باستخدام --prepare مرتين لاستخدام هذه الوظيفة على نسخة احتياطية.

قد تبدو نتيجة التشغيل على نسخة احتياطية كما يلي:

<INDEX STATISTICS>
  table: test/table1, index: PRIMARY, space id: 12, root page 3
  estimated statistics in dictionary:
    key vals: 25265338, leaf pages 497839, size pages 498304
  real statistics:
     level 2 pages: pages=1, data=5395 bytes, data/pages=32%
     level 1 pages: pages=415, data=6471907 bytes, data/pages=95%
        leaf pages: recs=25958413, pages=497839, data=7492026403 bytes, data/pages=91%

يمكن تفسير ذلك على النحو التالي:

  • يُظهر السطر الأول ببساطة اسم الجدول والفهرس ومعرفاته الداخلية. إذا رأيت فهرسًا باسم GEN_CLUST_INDEX، فهذا هو الفهرس المجمع للجدول، والذي تم إنشاؤه تلقائيًا لأنك لم تقم بإنشاء PRIMARY KEY صراحةً.
  • المعلومات الإحصائية المقدرة في القاموس تشبه البيانات التي يتم جمعها عبر ANALYZE TABLE داخل InnoDB ليتم تخزينها كإحصائيات تقديرية للكاردينالية وتمريرها إلى مُحسن الاستعلام.
  • معلومات الإحصاءات الحقيقية هي نتيجة مسح صفحات البيانات وحساب معلومات دقيقة حول الفهرس.
  • The level <X> pages: يعني الإخراج أن السطر يعرض معلومات حول الصفحات في هذا المستوى في شجرة الفهرس. كلما زادت قيمة <X>، كلما ابتعدت عن صفحات الأوراق، وهي المستوى 0. السطر الأول هو صفحة الجذر.
  • يُظهر إخراج leaf pages صفحات الأوراق، بالطبع. هذا هو المكان الذي يتم فيه تخزين بيانات الجدول.
  • يُظهر إخراج external pages (غير معروض) الصفحات الخارجية الكبيرة التي تحتوي على قيم طويلة جدًا بحيث لا تتناسب مع الصف نفسه، مثل قيم BLOB و TEXT الطويلة.
  • recs هو العدد الفعلي للسجلات (الصفوف) في صفحات الأوراق.
  • pages هو عدد الصفحات.
  • data هو الحجم الإجمالي للبيانات في الصفحات، بالبايت.
  • data/pages يتم حسابه كـ (data / (pages * PAGE_SIZE)) * 100%. لن يصل أبدًا إلى 100% بسبب المساحة المحجوزة لرؤوس وتذييلات الصفحات.

تم نشر مثال أكثر تفصيلاً في منشور مدونة أداء MySQL.

برنامج نصي لتنسيق الإخراج

يمكن استخدام البرنامج النصي التالي لتلخيص وترتيب إخراج معلومات الإحصاءات:

tabulate-xtrabackup-stats.pl
#!/usr/bin/env perl
use strict;
use warnings FATAL => 'all';
my $script_version = "0.1";
my $PG_SIZE = 16_384; # InnoDB defaults to 16k pages, change if needed.
my ($cur_idx, $cur_tbl);
my (%idx_stats, %tbl_stats);
my ($max_tbl_len, $max_idx_len) = (0, 0);
while ( my $line = <> ) {
   if ( my ($t, $i) = $line =~ m/table: (.*), index: (.*), space id:/ ) {
      $t =~ s!/!.!;
      $cur_tbl = $t;
      $cur_idx = $i;
      if ( length($i) > $max_idx_len ) {
         $max_idx_len = length($i);
      }
      if ( length($t) > $max_tbl_len ) {
         $max_tbl_len = length($t);
      }
   }
   elsif ( my ($kv, $lp, $sp) = $line =~ m/key vals: (\d+), \D*(\d+), \D*(\d+)/ ) {
      @{$idx_stats{$cur_tbl}->{$cur_idx}}{qw(est_kv est_lp est_sp)} = ($kv, $lp, $sp);
      $tbl_stats{$cur_tbl}->{est_kv} += $kv;
      $tbl_stats{$cur_tbl}->{est_lp} += $lp;
      $tbl_stats{$cur_tbl}->{est_sp} += $sp;
   }
   elsif ( my ($l, $pages, $bytes) = $line =~ m/(?:level (\d+)|leaf) pages:.*pages=(\d+), data=(\d+) bytes/ ) {
      $l ||= 0;
      $idx_stats{$cur_tbl}->{$cur_idx}->{real_pages} += $pages;
      $idx_stats{$cur_tbl}->{$cur_idx}->{real_bytes} += $bytes;
      $tbl_stats{$cur_tbl}->{real_pages} += $pages;
      $tbl_stats{$cur_tbl}->{real_bytes} += $bytes;
   }
}
my $hdr_fmt = "%${max_tbl_len}s %${max_idx_len}s %9s %10s %10s\n";
my @headers = qw(TABLE INDEX TOT_PAGES FREE_PAGES PCT_FULL);
printf $hdr_fmt, @headers;
my $row_fmt = "%${max_tbl_len}s %${max_idx_len}s %9d %10d %9.1f%%\n";
foreach my $t ( sort keys %tbl_stats ) {
   my $tbl = $tbl_stats{$t};
   printf $row_fmt, $t, "", $tbl->{est_sp}, $tbl->{est_sp} - $tbl->{real_pages},
      $tbl->{real_bytes} / ($tbl->{real_pages} * $PG_SIZE) * 100;
   foreach my $i ( sort keys %{$idx_stats{$t}} ) {
      my $idx = $idx_stats{$t}->{$i};
      printf $row_fmt, $t, $i, $idx->{est_sp}, $idx->{est_sp} - $idx->{real_pages},
         $idx->{real_bytes} / ($idx->{real_pages} * $PG_SIZE) * 100;
   }
}

العمل مع سجلات التغيير

يتكامل ثنائي xtrabackup مع log_status table. يمكّن هذا التكامل xtrabackup من طباعة موضع سجل التغيير المقابل للنسخة الاحتياطية، حتى تتمكن من استخدام موضع سجل التغيير هذا لتوفير نسخة طبق الأصل جديدة أو إجراء استعادة في نقطة زمنية.

العثور على موضع سجل التغيير

يمكنك العثور على موضع سجل التغيير المقابل لنسخة احتياطية بعد أخذ النسخة الاحتياطية. إذا كانت نسختك الاحتياطية من خادم تم تمكين تسجيل التغيير فيه، فإن xtrabackup ينشئ ملفًا باسم xtrabackup_binlog_info في الدليل المستهدف. يحتوي هذا الملف على اسم ملف سجل التغيير وموضعه في النقطة الدقيقة التي تم فيها أخذ النسخة الاحتياطية.

IMPLEMENTATION

Implementation Details

This page contains notes on various internal aspects of the xtrabackup tool's operation.

File Permissions

xtrabackup opens the source data files in read-write mode, although it does not modify the files. This means that you must run xtrabackup as a user who has permission to write the data files. The reason for opening the files in read-write mode is that xtrabackup uses the embedded InnoDB libraries to open and read the files, and InnoDB opens them in read-write mode because it normally assumes it is going to write to them.

Tuning the OS Buffers

Because xtrabackup reads large amounts of data from the filesystem, it uses posix_fadvise() where possible, to instruct the operating system not to try to cache the blocks it reads from disk. Without this hint, the operating system would prefer to cache the blocks, assuming that xtrabackup is likely to need them again, which is not the case. Caching such large files can place pressure on the operating system's virtual memory and cause other processes, such as the database server, to be swapped out. The xtrabackup tool avoids this with the following hint on both the source and destination files:

posix_fadvise(file, 0, 0, POSIX_FADV_DONTNEED)

In addition, xtrabackup asks the operating system to perform more aggressive read-ahead optimizations on the source files:

posix_fadvise(file, 0, 0, POSIX_FADV_SEQUENTIAL)

Copying Data Files

When copying the data files to the target directory, xtrabackup reads and writes 1 MB of data at a time. This is not configurable. When copying the log file, xtrabackup reads and writes 512 bytes at a time. This is also not possible to configure, and matches InnoDB's behavior (workaround exists in Percona Server for MySQL because it has an option to tune innodb_log_block_size for XtraDB, and in that case Percona XtraBackup will match the tuning).

After reading from the files, xtrabackup iterates over the 1MB buffer a page at a time, and checks for page corruption on each page with InnoDB's buf_page_is_corrupted() function. If the page is corrupt, it re-reads and retries up to 10 times for each page. It skips this check on the doublewrite buffer.

xtrabackup Exit Codes

The xtrabackup binary exits with the traditional success value of 0 after a backup when no error occurs. If an error occurs during the backup, the exit value is 1.

In certain cases, the exit value can be something other than 0 or 1, due to the command-line option code included from the MySQL libraries. An unknown command-line option, for example, will cause an exit code of 255.

Modes of operation

You invoke xtrabackup in one of the following modes:

  • --backup mode to make a backup in a target directory
  • --prepare mode to restore data from a backup (created in --backup mode)
  • --copy-back to copy data from a backup to the location that contained the original data; to move data instead of copying use the alternate --move-back mode.
  • --stats mode to scan the specified data files and print out index statistics.

When you intend to run xtrabackup in any of these modes, use the following syntax:

$ xtrabackup [--defaults-file=#] --backup|--prepare|--copy-back|--stats [OPTIONS]

For example, the --prepare mode is applied as follows:

$ xtrabackup --prepare --target-dir=/data/backup/mysql/

~/.my.cnf.

--safe-slave-backup
عند تحديده، سيقوم xtrabackup بإيقاف خيط SQL للنسخ المتماثل (replica SQL thread) قبل تشغيل FLUSH TABLES WITH READ LOCK والانتظار لبدء النسخ الاحتياطي حتى يصبح Slave_open_temp_tables في SHOW STATUS صفرًا. إذا لم تكن هناك جداول مؤقتة مفتوحة، سيتم إجراء النسخ الاحتياطي، وإلا سيتم تشغيل وإيقاف خيط SQL حتى لا تكون هناك جداول مؤقتة مفتوحة. سيفشل النسخ الاحتياطي إذا لم يصبح Slave_open_temp_tables صفرًا بعد --safe-slave-backup-timeout ثانية. سيتم إعادة تشغيل خيط SQL للنسخ المتماثل عند الانتهاء من النسخ الاحتياطي. تم تنفيذ هذا الخيار للتعامل مع جداول النسخ المتماثل المؤقتة (replicating temporary tables) وليس ضروريًا مع النسخ المتماثل القائم على الصفوف (Row-Based-Replication).
--safe-slave-backup-timeout=SECONDS
كم عدد الثواني التي يجب أن ينتظرها --safe-slave-backup حتى يصبح Slave_open_temp_tables صفرًا. الافتراضي هو 300 ثانية.
