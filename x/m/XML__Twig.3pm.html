الحزمة: perl-xml-twig

التراخيص: GPL، PerlArtistic

XML::Twig(3) وثائق بيرل المساهمة من المستخدمين XML::Twig(3)

الاسم

XML::Twig - وحدة بيرل لمعالجة مستندات XML الضخمة في وضع الشجرة.

الملخص

لاحظ أن هذه الوثائق مخصصة كمرجع للوحدة.

الوثائق الكاملة، بما في ذلك برنامج تعليمي وأمثلة ونسخة HTML أسهل في الاستخدام وبطاقة مرجعية سريعة والأسئلة الشائعة متاحة على http://www.xmltwig.org/xmltwig.

المستندات الصغيرة (تُحمَّل في الذاكرة كشجرة):

my $twig=XML::Twig->new();    # إنشاء الـ twig
$twig->parsefile( 'doc.xml'); # بناءه
my_process( $twig);           # استخدام طرق twig لمعالجته
$twig->print;                 # إخراج الـ twig

المستندات الضخمة (تُعالَج في وضع الدفق/الشجرة المدمج):

# سيتم تحميل عنصر div واحد على الأكثر في الذاكرة
my $twig=XML::Twig->new(
  twig_handlers =>
    { title   => sub { $_->set_tag( 'h2') }, # تغيير وسوم title إلى h2
                                             # $_ هو العنصر الحالي
      para    => sub { $_->set_tag( 'p')  }, # تغيير para إلى p
      hidden  => sub { $_->delete;       },  # إزالة العناصر المخفية
      list    => \&my_list_process,          # معالجة عناصر list
      div     => sub { $_[0]->flush;     },  # إخراج وتحرير الذاكرة
    },
  pretty_print => 'indented',                # سيكون الإخراج منسقًا بشكل جميل
  empty_tags   => 'html',                    # يُخرج <empty_tag />
                       );
$twig->parsefile( 'my_big.xml');
sub my_list_process
  { my( $twig, $list)= @_;
    # ...
  }

راجع XML::Twig 101 لطرق أخرى لاستخدام الوحدة، كمرشح على سبيل المثال.

الوصف

توفر هذه الوحدة طريقة لمعالجة مستندات XML. وهي مبنية على "XML::Parser".

تقدم الوحدة واجهة شجرة للمستند، مع السماح لك بإخراج الأجزاء التي تمت معالجتها بالكامل.

تسمح باستخدام أدنى قدر من الموارد (المعالج والذاكرة) من خلال بناء الشجرة فقط للأجزاء من المستندات التي تحتاج إلى معالجة فعلية، عبر استخدام خيارات "twig_roots " و "twig_print_outside_roots ". كما تساعد الطرق "finish " و "finish_print " على زيادة الأداء.

يحاول XML::Twig جعل الأمور البسيطة سهلة، لذا يبذل قصارى جهده للعناية بالكثير من الميزات (عادةً) المزعجة (لكنها ضرورية أحيانًا) التي تأتي مع XML وXML::Parser.

الأدوات

يأتي XML::Twig مع بعض الأدوات المساعدة لسطر الأوامر:

xml_pp - منسق XML الجميل

تنسيق XML الجميل باستخدام XML::Twig.

xml_grep - البحث في ملفات XML عن عناصر محددة

يقوم "xml_grep" بالبحث في ملفات XML. فبدلاً من استخدام التعبيرات النمطية، يستخدم تعبيرات XPath (في الواقع المجموعة الفرعية من XPath التي يدعمها XML::Twig).

xml_split - تقسيم ملف XML كبير إلى أجزاء أصغر

يأخذ "xml_split" ملف XML (يُفترض أنه كبير) ويقسمه إلى عدة ملفات أصغر، بناءً على معايير متنوعة (المستوى في الشجرة، أو الحجم، أو تعبير XPath).

xml_merge - دمج ملفات XML المقسمة بـ xml_split مرة أخرى

يأخذ "xml_merge" عدة ملفات XML تم تقسيمها باستخدام "xml_split" ويعيد إنشاء ملف واحد.

xml_spellcheck - التدقيق الإملائي لملفات XML

يتيح لك "xml_spellcheck" التدقيق الإملائي لمحتويات ملف XML. يستخرج النص (محتوى العناصر واختياريًا السمات)، ويستدعي مدققًا إملائيًا عليه، ثم يعيد إنشاء مستند XML.

XML::Twig 101

يمكن استخدام XML::Twig إما على مستندات XML "الصغيرة" (التي تتسع في الذاكرة)، أو على المستندات الضخمة من خلال معالجة أجزاء من المستند وإخراجها أو التخلص منها بمجرد معالجتها.

تحميل مستند XML ومعالجته

my $t= XML::Twig->new();
$t->parse( '<d><title>title</title><para>p 1</para><para>p 2</para></d>');
my $root= $t->root;
$root->set_tag( 'html');              # تغيير المستند إلى html
$title= $root->first_child( 'title'); # الحصول على العنوان
$title->set_tag( 'h1');               # تحويله إلى h1
my @para= $root->children( 'para');   # الحصول على العناصر الفرعية para
foreach my $para (@para)
  { $para->set_tag( 'p'); }           # تحويلها إلى p
$t->print;                            # إخراج المستند

تشمل الطرق المفيدة الأخرى:

att: "$elt->att( 'foo')" يعيد سمة "foo" لعنصر ما،

set_att : "$elt->set_att( foo => "bar")" يضبط السمة "foo" على القيمة "bar"،

next_sibling: "$elt->next_sibling" يعيد الشقيق التالي في المستند (في المثال "$title->next_sibling" هو أول "para"، يمكنك أيضًا (وفي الواقع يجب) استخدام "$elt->next_sibling( 'para')" للحصول عليه.

يمكن أيضًا تحويل المستند من خلال استخدام طرق القص والنسخ واللصق والنقل: "$title->cut; $title->paste( after => $p);" على سبيل المثال.

والمزيد والمزيد، راجع XML::Twig::Elt.

معالجة مستند XML قطعة قطعة

إحدى نقاط قوة XML::Twig هي أنه يتيح لك العمل مع ملفات لا تتسع في الذاكرة. تخزين مستند XML في الذاكرة كشجرة يستهلك الكثير من الذاكرة؛ إذ يبلغ عامل التوسع غالبًا حوالي 10 أضعاف.

للقيام بذلك، يمكنك تعريف معالجات سيتم استدعاؤها بمجرد تحليل عنصر معين بالكامل (إغلاقه). في هذه المعالجات، يمكنك الوصول إلى العنصر ومعالجته كما تراه مناسبًا، باستخدام طرق التنقل والقص/النسخ/اللصق، بالإضافة إلى الكثير من الطرق الملائمة مثل "prefix ". بمجرد معالجة العنصر بالكامل، يمكنك حينها "flush " له، مما يُخرج العنصر ويحرر ذاكرته. يمكنك أيضًا "purge " له إذا لم تكن بحاجة إلى إخراجه (إذا كنت تستخرج بعض البيانات من المستند على سبيل المثال). سيتم استدعاء المعالج مرة أخرى بمجرد تحليل العنصر التالي ذي الصلة.

my $t= XML::Twig->new( twig_handlers =>
                        { section => \&section,
                          para   => sub { $_->set_tag( 'p'); }
                        },
                     );
$t->parsefile( 'doc.xml');
# يتم استدعاء المعالج بمجرد تحليل قسم بالكامل، أي عندما
# يتم العثور على وسم الإغلاق للقسم، ويستقبل الـ twig نفسه
# والعنصر (بما في ذلك جميع عناصره الفرعية) كوسائط
sub section
  { my( $t, $section)= @_;      # وسائط لجميع twig_handlers
    $section->set_tag( 'div');  # تغيير اسم الوسم
    # لنستخدم السمة nb كبادئة للعنوان
    my $title= $section->first_child( 'title'); # العثور على العنوان
    my $nb= $title->att( 'nb'); # الحصول على السمة
    $title->prefix( "$nb - ");  # سهل أليس كذلك؟
    $section->flush;            # يُخرج القسم ويحرر الذاكرة
  }

عند استدعاء معالج، يحتوي $_ على العنصر الذي طابقه المعالج.

يمكنك تفعيل hمعالجات على شروط أكثر تعقيدًا. هذه المعالجة تطابق فقط عناصر "title" الموجودة داخل عناصر "section":

my $t= XML::Twig->new( twig_handlers =>
                         { 'section/title' => sub { $_->print } }
                     )
                ->parsefile( 'doc.xml');

هنا "sub { $_->print }" ببساطة يطبع العنصر الحالي.

يمكن للمعالجات أيضًا اختبار وجود السمات أو محتواها:

my $t= XML::Twig->new( twig_handlers =>
                    { 'section[@level="1" or @force]' => sub { $_->print } }
                     );
                ->parsefile( 'doc.xml');

يمكنك أيضًا استخدام "start_tag_handlers " لمعالجة عنصر بمجرد العثور على وسم البداية.

معالجة أجزاء فقط من مستند XML

يبني وضع twig_roots فقط الأشجار الفرعية المطلوبة من المستند. يتم تجاهل أي شيء خارج جذور twig:

my $t= XML::Twig->new(
     # the twig will include just the root and selected titles
         twig_roots   => { 'section/title' => \&print_n_purge,
                           'annex/title'   => \&print_n_purge
         }
                    );
$t->parsefile( 'doc.xml');
sub print_n_purge
  { my( $t, $elt)= @_;
    print $elt->text;    # print the text (including sub-element texts)
    $t->purge;           # frees the memory
  }

يمكنك استخدام هذا الوضع عندما تريد معالجة أجزاء من المستندات ولكنك غير مهتم بالباقي ولا تريد دفع الثمن، سواء في الوقت أو الذاكرة، لبناء الشجرة من أجله.

بناء مرشح XML

يمكنك الجمع بين خيارات "twig_roots" و "twig_print_outside_roots" لبناء مرشحات، والتي تتيح لك تعديل عناصر محددة وإخراج بقية المستند كما هو.

هذا من شأنه تحويل الأسعار بالدولار إلى أسعار باليورو في مستند:

my $t= XML::Twig->new(
         twig_roots   => { 'price' => \&convert, },   # process prices
         twig_print_outside_roots => 1,               # print the rest
                    );
$t->parsefile( 'doc.xml');
sub convert
  { my( $t, $price)= @_;
    my $currency=  $price->att( 'currency');          # get the currency
    if( $currency eq 'USD')
      { $usd_price= $price->text;                     # get the price
        # %rate is just a conversion table
        my $euro_price= $usd_price * $rate{usd2euro};
        $price->set_text( $euro_price);               # set the new price
        $price->set_att( currency => 'EUR');          # don't forget this!
      }
    $price->print;                                    # output the price
  }

تبسيط معالجة XML

المسافات البيضاء
يتم التخلص من المسافات البيضاء التي تبدو غير مهمة. يمكن التحكم في هذا السلوك باستخدام خيارات "keep_spaces " و "keep_spaces_in " و "discard_spaces_in ".
الترميز
يمكنك تحديد أنك تريد الإخراج بنفس ترميز الإدخال (بشرط أن يكون لديك XML صالح، مما يعني أنه يجب عليك تحديد الترميز إما في المستند أو عند إنشاء كائن Twig) باستخدام خيار "keep_encoding ".

يمكنك أيضًا استخدام "output_encoding " لتحويل تنسيق UTF-8 الداخلي إلى الترميز المطلوب.

التعليقات و تعليمات المعالجة (PI)
يمكن إخفاء التعليقات و PIs من المعالجة، ولكنها لا تزال تظهر في الإخراج (يتم حملها بواسطة العنصر "الحقيقي" الأقرب إليها). أو، يمكن جعلها متاحة للمعالجة كعناصر "#COMMENT" و "#PI".
الطباعة الجميلة
يمكن لـ XML::Twig إخراج المستند مطبوعًا بشكل جميل بحيث يكون أسهل في القراءة بالنسبة لنا نحن البشر.
النجاة من موت مفاجئ
من المفترض أن تتفاعل محللات XML بعنف عندما تُغذى بـ XML غير صالح. XML::Parser يموت فقط.

يوفر XML::Twig طرق "safe_parse " و "safe_parsefile " التي تغلف التحليل في "eval" وتعيد إما twig المحلل أو 0 في حالة الفشل.

السمات الخاصة
السمات التي يبدأ اسمها بـ # (غير قانونية في XML!) لن يتم إخراجها، لذلك يمكنك استخدامها بأمان لتخزين قيم مؤقتة أثناء المعالجة. لاحظ أنه يمكنك تخزين أي شيء في سمة خاصة، وليس النص فقط، إنها مجرد متغير Perl عادي، لذا فإن مرجعًا إلى كائن أو بنية بيانات ضخمة أمر جيد تمامًا.

الفئات

يستخدم XML::Twig عددًا محدودًا جدًا من الفئات. تلك التي من المرجح أن تستخدمها هي "XML::Twig "، والتي تمثل مستند XML كاملًا، بما في ذلك المستند نفسه (جذر المستند نفسه هو "root ")، ومعالجاتها، ومرشحات الإدخال أو الإخراج الخاصة بها... الفئة الرئيسية الأخرى هي "XML::Twig::Elt "، والتي تمثل عنصر XML. "العنصر" هنا له تعريف واسع جدًا: يمكن أن يكون عنصرًا عاديًا، أو نصًا مخزنًا في وسم "#PCDATA" (أو "#CDATA")، أو كيانًا (الوسم هو "#ENT")، أو تعليمة معالجة ("#PI")، أو تعليقًا ("#COMMENT").

XML::Twig و XML::Twig::Elt هما الفئتان الشائعتان الاستخدام.

قد ترغب في إلقاء نظرة على خيار "elt_class " إذا كنت تريد إنشاء فئة فرعية من "XML::Twig::Elt".

السمات مرتبطة فقط بالعنصر الأصلي الخاص بها، فهي ليست كائنات بحد ذاتها. (يرجى استخدام الطرق المتوفرة "att " و "set_att " للوصول إليها، إذا وصلت إليها كتجزئة، فإن الكود الخاص بك يصبح معتمدًا على التنفيذ وقد ينكسر في المستقبل.)

الفئات الأخرى التي نادرًا ما تُستخدم هي "XML::Twig::Entity_list " و "XML::Twig::Entity ".

إذا كنت تستخدم "XML::Twig::XPath " بدلاً من "XML::Twig"، فسيتم إنشاء العناصر بعد ذلك كـ "XML::Twig::XPath::Elt ".

الطرق

XML::Twig

twig هي فئة فرعية من XML::Parser، لذلك يمكن استدعاء جميع طرق XML::Parser على كائن twig، بما في ذلك parse و parsefile. من ناحية أخرى، لا يمكن استخدام "setHandlers"، انظر "BUGS ".

new
هذه طريقة فئة، وهي المُنشئ لـ XML::Twig. يتم تمرير الخيارات كأزواج كلمة مفتاحية-قيمة. الخيارات المعترف بها هي نفسها كما في XML::Parser، بالإضافة إلى بعض (في الواقع الكثير!) من خصائص XML::Twig.

خيارات جديدة:

twig_handlers
تتكون هذه الوسيطة من تجزئة "{ expression =" \&handler}> حيث expression هو تعبير شبيه بـ XPath (+ بعض التعبيرات الأخرى).

تقتصر تعبيرات XPath على استخدام محور الطفل والسليل (في الواقع لا يمكنك تحديد محور)، ولا يمكن تداخل المسندات. يمكنك استخدام دالة "string"، أو string(<tag>) (باستثناء محفزات "twig_roots").

بالإضافة إلى ذلك يمكنك استخدام التعبيرات النمطية (المحددة بـ /) لمطابقة قيم السمات والنصوص.

أمثلة:

foo
foo/bar
foo//bar
/foo/bar
/foo//bar
/foo/bar[@att1 = "val1" and @att2 = "val2"]/baz[@a >= 1]
foo[string()=~ /^duh!+/]
/foo[string(bar)=~ /\d+/]/baz[@att != 3]

يمكن استخدام #CDATA لاستدعاء معالج لوسم CDATA. يمكن استخدام #COMMENT لاستدعاء معالج للتعليقات.

بعض الإضافات (يتم أيضًا توفير تعبيرات (غير XPath) للراحة:

تعليمات المعالجة
'?' أو '#PI' تُفعّل المعالج لأي تعليمة معالجة، و'?<target>' أو '#PI <target>' تُفعّل معالجًا لتعليمة المعالجة ذات الهدف المحدد (مثال: '#PI xml-stylesheet').
level(<level>)
تُفعّل المعالج على أي عنصر عند ذلك المستوى في الشجرة (الجذر هو المستوى 1).
_all_
تُفعّل المعالج لـجميع العناصر في الشجرة.
_default_
تُفعّل المعالج لكل عنصر لا يملك أي معالج آخر.

يتم تقييم المعالجات وإدراجها في قائمة الانتظار مقابل المستند المُدخل، ثم تنفيذها. التغييرات التي يُجريها معالج واحد (مثل تغيير أسماء الوسوم، أو نقل العنصر أو تغليفه - حتى في معالجات وسم البداية) <لا> تؤثر على المعالجات المُدرجة لاحقًا حتى لو تسببت التعديلات في عدم تطابق تعبير التفعيل الخاص بها. هناك استثناء لهذا: السمات "الخاصة" (التي تبدأ أسماؤها بـ '#' ولا يمكن إنشاؤها إلا أثناء المعالجة، لأنها ليست XML صالحة) يتم التحقق منها مقابل الغصن الحالي.

يتم تفعيل المعالجات بترتيب ثابت، مُرتّبة حسب نوعها (تعبيرات xpath أولًا، ثم التعبيرات النمطية، ثم المستوى)، ثم حسب ما إذا كانت تحدد مسارًا كاملًا (يبدأ من عنصر الجذر) أم لا، ثم حسب عدد الخطوات في التعبير، ثم عدد المسندات، ثم عدد الاختبارات في المسندات. المعالجات التي لا تحدد خطوتها الأخيرة خطوة ("foo/bar/*") يتم تفعيلها بعد معالجات XPath الأخرى. أخيرًا، معالجات "_all_" يتم تفعيلها في النهاية.

مهم: بمجرد تفعيل معالج، إذا أعاد 0 فلن يتم استدعاء أي معالج آخر، باستثناء معالج "_all_" الذي يُستدعى دائمًا.

إذا أعاد معالج قيمة صحيحة وكانت هناك معالجات أخرى تنطبق، فسيتم استدعاء المعالج التالي المنطبق. كرر، اشطف، أعد..؛ الاستثناء من هذه القاعدة هو عندما يتم تعيين خيار "do_not_chain_handlers "، وفي هذه الحالة سيتم استدعاء المعالج الأول فقط.

من الجيد إرجاع قيمة صحيحة قصيرة (مثل 1) صراحةً من المعالجات؛ هذا يضمن استدعاء المعالجات الأخرى المنطبقة حتى لو صادف أن العبارة الأخيرة للمعالج تُقيّم إلى خطأ. يمكن أن يؤدي هذا أيضًا إلى تسريع الكود بتجنب نسخ نتيجة العبارة الأخيرة من الكود وتمريرها إلى الكود الذي يدير المعالجات. يمكن أن يكون مجديًا حقًا إرجاع 1 بدلًا من سلسلة طويلة.

عندما يتم تحليل وسم الإغلاق لعنصر، يُستدعى المعالج المقابل بوسيطين: الغصن و"Element ". يتضمن الغصن شجرة المستند التي تم بناؤها حتى الآن، والعنصر هو الشجرة الفرعية الكاملة للعنصر.

لأن المعالجات تُستدعى فقط عند العثور على وسم الإغلاق للعنصر، فهذا يعني أن معالجات العناصر الداخلية تُستدعى قبل معالجات العناصر الخارجية.

يتم أيضًا تعيين $_ إلى العنصر، لذا من السهل كتابة معالجات مضمّنة مثل:

para => sub { $_->set_tag( 'p'); }

يُخزَّن النص في عناصر اسم وسمها "#PCDATA" (بسبب المحتوى المختلط، النص والعنصر الفرعي في عنصر، لا توجد طريقة لتخزين النص كمجرد سمة للعنصر المحيط).

تحذير: إذا استخدمت "purge" أو "flush" على الغصن، فقد لا يكون العنصر مكتملًا: ربما تم تفريغ أو تطهير بعض أبنائه بالكامل، وربما تمت طباعة وسم البداية (بواسطة "flush") بالفعل، لذا قد لا يعطي تغيير وسطه النتيجة المتوقعة.

twig_roots
يتيح لك هذا الوسيط بناء الشجرة فقط لتلك العناصر التي تهتم بها. 
مثال: my $t= XML::Twig->new( twig_roots => { title => 1, subtitle => 1});
         $t->parsefile( file);
         my $t= XML::Twig->new( twig_roots => { 'section/title' => 1});
         $t->parsefile( file);

يُرجع غصنًا يحتوي على مستند يتضمن فقط عناصر "title" و"subtitle"، كأبناء لعنصر الجذر.

يمكنك استخدام generic_attribute_condition وattribute_condition وfull_path وpartial_path وtag وtag_regexp و_default_ و_all_ لتفعيل بناء الغصن. لا يمكن استخدام string_condition وregexp_condition كمحتوى للعنصر، والسلسلة لم يتم تحليلها بعد عند التحقق من الشرط.

تحذير: يتم التحقق من المسارات مقابل المستند. حتى لو تم استخدام خيار "twig_roots"، فسيتم التحقق منها مقابل شجرة المستند الكاملة، وليس الشجرة الافتراضية التي أنشأها XML::Twig.

تحذير: يجب ألا تكون عناصر twig_roots متداخلة، فذلك سيربك XML::Twig بشكل ميؤوس منه.

ملاحظة: يمكنك تعيين معالجات (twig_handlers) باستخدام twig_roots
مثال: my $t= XML::Twig->new( twig_roots =>
{ title => sub { $_[1]->print;},
subtitle => \&process_subtitle
}
);
$t->parsefile( file);

twig_print_outside_roots
يُستخدم بالاقتران مع وسيط "twig_roots". عند تعيينه إلى قيمة صحيحة، فإنه يطبع المستند خارج عناصر "twig_roots". 
مثال: my $t= XML::Twig->new( twig_roots => { title => \&number_title },
                               twig_print_outside_roots => 1,
                              );
          $t->parsefile( file);
          { my $nb;
          sub number_title
            { my( $twig, $title);
              $nb++;
              $title->prefix( "$nb ");
              $title->print;
            }
          }

يطبع هذا المثال المستند خارج عنصر title، ويستدعي "number_title" لكل عنصر "title"، ويطبعه، ثم يستأنف طباعة المستند. يُبنى الغصن فقط لعناصر "title".

إذا كانت القيمة مرجعًا إلى مقبض ملف، فسيتم إخراج المستند خارج عناصر "twig_roots" إلى مقبض الملف هذا:

open( my $out, '>', 'out_file.xml') or die "cannot open out file.xml out_file:$!";
my $t= XML::Twig->new( twig_roots => { title => \&number_title },
                       # default output to $out
                       twig_print_outside_roots => $out,
                     );
       { my $nb;
         sub number_title
           { my( $twig, $title);
             $nb++;
             $title->prefix( "$nb ");
             $title->print( $out);    # you have to print to \*OUT here
           }
         }
start_tag_handlers
تجزئة "<{ expression =" \&handler}>>. تعيّن معالجات العناصر التي تُستدعى عند فتح العنصر (في نهاية معالج "Start" الخاص بـ XML::Parser). تُستدعى المعالجات بمعاملين: الغصن والعنصر. يكون العنصر فارغًا في تلك المرحلة، لكن سماته تكون منشأة.

يمكنك استخدام generic_attribute_condition وattribute_condition وfull_path وpartial_path وtag وtag_regexp و_default_ و_all_ لتفعيل المعالج.

لا يمكن استخدام string_condition وregexp_condition كمحتوى للعنصر، لأن السلسلة لم يتم تحليلها بعد عند التحقق من الشرط.

الاستخدامات الرئيسية لمعالجات وسم البداية هي تغيير اسم الوسم (قد تحتاج إلى فعل ذلك بمجرد العثور على الوسم المفتوح إذا كنت تخطط لـ"flush" الغصن في مرحلة ما داخل العنصر)، وإنشاء سمات مؤقتة تُستخدم عند معالجة العنصر الفرعي باستخدام "twig_handlers" العادية.

يجب عليك أيضًا استخدامه لتغيير الوسوم إذا استخدمت "flush". إذا غيّرت الوسم في "twig_handler" عادي فقد يكون وسم البداية قد تم تفريغه بالفعل.

ملاحظة: يمكن استدعاء معالجات "start_tag" خارج "twig_roots" إذا تم استخدام هذا الوسيط، وفي هذه الحالة تُستدعى المعالجات بالمعاملات التالية: $t (الغصن)، $tag (وسم العنصر) و%att (تجزئة سمات العنصر).

إذا تم استخدام وسيط "twig_print_outside_roots" أيضًا، فإذا أعاد آخر معالج مُستدعى قيمة "true"، فسيتم إخراج وسم البداية كما ظهر في المستند الأصلي؛ وإذا أعاد المعالج قيمة "false"، فلن تتم طباعة وسم البداية (حتى تتمكن من طباعة سلسلة معدّلة بنفسك على سبيل المثال).

لاحظ أنه يمكنك استخدام طريقة ignore في "start_tag_handlers" (وهناك فقط).

end_tag_handlers
تجزئة "<{ expression =" \&handler}>>. تعيّن معالجات العناصر التي تُستدعى عند إغلاق العنصر (في نهاية معالج "End" الخاص بـ XML::Parser). تُستدعى المعالجات بمعاملين: الغصن ووسم العنصر.

تُستدعى twig_handlers عندما يتم تحليل العنصر بالكامل، فلماذا يوجد هذا الخيار الزائد؟ هناك استخدام واحد فقط لـ"end_tag_handlers": عند استخدام خيار "twig_roots"، لتفعيلمعالج لعنصر خارج الجذور. وهو، على سبيل المثال، مفيد جدًا لترقيم العناوين في مستند باستخدام أقسام متداخلة:

my @no= (0);
my $no;
my $t= XML::Twig->new(
        start_tag_handlers =>
         { section => sub { $no[$#no]++; $no= join '.', @no; push @no, 0; } },
        twig_roots         =>
         { title   => sub { $_[1]->prefix( $no); $_[1]->print; } },
        end_tag_handlers   => { section => sub { pop @no;  } },
        twig_print_outside_roots => 1
                    );
 $t->parsefile( $file);

استخدام الوسيط "end_tag_handlers" بدون "twig_roots" سيؤدي إلى خطأ.

do_not_chain_handlers
إذا تم تعيين هذا الخيار إلى قيمة صحيحة، فسيتم استدعاء معالج واحد فقط لكل عنصر، حتى لو استوفى عدة معالجات الشرط.

لاحظ أن المعالج "_all_" لا يزال يُستدعى بغض النظر عن ذلك.

ignore_elts
يتيح لك هذا الخيار تجاهل العناصر عند بناء الشجرة (twig). وهذا مفيد في الحالات التي لا يمكنك فيها استخدام "twig_roots" لتجاهل العناصر، على سبيل المثال إذا كان العنصر المراد تجاهله شقيقًا لعناصر تهتم بها.

مثال:

my $twig= XML::Twig->new( ignore_elts => { elt => 'discard' });
$twig->parsefile( 'doc.xml');

سيؤدي هذا إلى بناء الشجرة الكاملة للمستند، باستثناء أن جميع عناصر "elt" (وأبنائها) ستُترك خارجًا.

المفاتيح في التجزئة (hash) هي محفزات (triggers)، محدودة بنفس المجموعة الفرعية مثل "start_tag_handlers ". يمكن أن تكون القيم "discard" لتجاهل العنصر، أو "print" لإخراج العنصر كما هو، أو "string" لتخزين نص العناصر المتجاهلة، بما في ذلك الترميز (markup)، في حقل من الشجرة: "$t->{twig_buffered_string}" أو مرجع إلى متغير عددي (scalar)، وفي هذه الحالة سيتم تخزين نص العناصر المتجاهلة، بما في ذلك الترميز، في المتغير العددي. أي قيمة أخرى ستُعامل على أنها "discard".

char_handler
مرجع إلى روتين فرعي سيتم استدعاؤه في كل مرة يتم فيها العثور على "#PCDATA".

يستقبل الروتين الفرعي السلسلة كوسيط، ويعيد السلسلة المعدلة:

# we want all strings in upper case
sub my_char_handler
  { my( $text)= @_;
    $text= uc( $text);
    return $text;
  }
css_sel
عند تعيينه إلى قيمة صحيحة، يسمح بالمحددات "tag.class" في المعالجات.

النقطة هي حرف صالح في أسماء العناصر، على سبيل المثال "div.header" هو اسم XML صالح تمامًا.

ولكن نظرًا لأن XML::Twig يُستخدم كثيرًا لمعالجة XHTML واللهجات المبنية على HTML، فمن الملائم جدًا أن تكون قادرًا على استخدام "div.header" للتحفيز على عنصر "div" بفئة "header"، بدلاً من الصيغة الأكثر تعقيدًا "div[@class=~/\bheader\b/]".

لاحظ أن صيغة "tag.class" مدعومة في تعبيرات التنقل، ما لم يتم تعيين "css_sel" صراحةً إلى 0.

elt_class
اسم فئة تُستخدم لتخزين العناصر. يجب أن ترث هذه الفئة من "XML::Twig::Elt" (وافتراضيًا هي "XML::Twig::Elt"). يُستخدم هذا الخيار لإنشاء فئة فرعية من فئة العنصر وتوسيعها بطرق جديدة.

هذا الخيار ضروري لأنه أثناء تحليل XML، يتم إنشاء العناصر بواسطة "XML::Twig" دون أي تحكم من كود المستخدم.

keep_atts_order
تعيين هذا الخيار إلى قيمة صحيحة يجعل تجزئة السمات (attribute hash) مرتبطة بكائن "Tie::IxHash". وهذا يعني أن "Tie::IxHash" يحتاج إلى التثبيت ليكون هذا الخيار متاحًا. كما يعني أن التجزئة تحافظ على ترتيبها، لذا ستحصل على السمات بالترتيب. وهذا يسمح بإخراج السمات بنفس الترتيب الذي كانت عليه في المستند الأصلي.
keep_encoding
هذا خيار (شرير قليلاً؟): إذا لم يكن مستند XML مشفرًا بـ UTF-8 وأردت إبقاءه على ذلك، فإن تعيين keep_encoding سيستخدم طريقة original_string الخاصة بـ "Expat" للأحرف، وبالتالي الحفاظ على الترميز الأصلي، بالإضافة إلى الكيانات الأصلية في السلاسل.

راجع ملف الاختبار "t/test6.t" لمعرفة النتائج التي يمكنك توقعها من خيارات الترميز المختلفة.

تحذير: هذا الخيار غير مستخدم عند التحليل باستخدام المحلل غير الحاجب (طرق "parse_start"، "parse_more"، parse_done) والتي ربما لا يجب عليك استخدامها مع XML::Twig على أي حال لأنها غير مختبرة تمامًا!

output_encoding
يُنشئ هذا الخيار output_filter باستخدام "Encode"، أو "Text::Iconv"، أو "Unicode::Map8" و "Unicode::Strings"، ويعيّن الترميز في تعريف XML. هذه هي أسهل طريقة للتعامل مع الترميزات. إذا كنت بحاجة إلى ميزات أكثر تطورًا، فراجع "output_filter" أدناه.
output_filter
يُستخدم هذا الخيار لتحويل ترميز الأحرف لمستند الإخراج. يُمرر إليه إما سلسلة تقابل مرشحًا محددًا مسبقًا أو مرجع روتين فرعي. سيتم استدعاء المرشح في كل مرة تتم فيها معالجة مستند أو عنصر بواسطة دوال "print" ("print"، "sprint"، "flush").

المرشحات المحددة مسبقًا:

latin1
يستخدم إما "Encode"، أو "Text::Iconv" أو "Unicode::Map8" و "Unicode::String" أو تعبيرًا نمطيًا (يعمل فقط مع XML::Parser 2.27)، بهذا الترتيب، لتحويل جميع الأحرف إلى ISO-8859-15 (عادةً ما يكون latin1 مرادفًا لـ ISO-8859-1، ولكن عمليًا يبدو أن ISO-8859-15، الذي يتضمن علامة اليورو، أكثر فائدة وربما هو ما يريده معظم الناس).
html
يقوم بنفس التحويل مثل "latin1"، بالإضافة إلى ترميز الكيانات باستخدام "HTML::Entities" (ومن الغريب أنك ستحتاج إلى تثبيت HTML::Entities ليكون متاحًا). يجب استخدام هذا فقط إذا كانت الوسوم وأسماء السمات نفسها بـ US-ASCII، وإلا فسيتم تحويلها ولن يكون الإخراج XML صالحًا بعد الآن.
safe
يحوّل الإخراج إلى ASCII (US) فقط بالإضافة إلى كيانات الأحرف ("&#nnn;") يجب استخدام هذا فقط إذا كانت الوسوم وأسماء السمات نفسها بـ US-ASCII، وإلا فسيتم تحويلها ولن يكون الإخراج XML صالحًا بعد الآن.
safe_hex
مثل "safe" باستثناء أن كيانات الأحرف بصيغة سداسية عشرية ("&#xnnn;").
encode_convert ($encoding)
يعيد مرجعًا فرعيًا يمكن استخدامه لتحويل سلاسل utf8 إلى $encoding). يستخدم "Encode". 
my $conv = XML::Twig::encode_convert( 'latin1');
my $t = XML::Twig->new(output_filter => $conv);
iconv_convert ($encoding)
تُستخدم هذه الدالة لإنشاء روتين فرعي للمرشح سيُستخدم لتحويل الأحرف إلى الترميز الهدف باستخدام "Text::Iconv" (الذي يحتاج إلى التثبيت، راجع وثائق الوحدة ومكتبة "iconv" لمعرفة الترميزات المتاحة على نظامك). 
my $conv = XML::Twig::iconv_convert( 'latin1');
my $t = XML::Twig->new(output_filter => $conv);
unicode_convert ($encoding)
تُستخدم هذه الدالة لإنشاء روتين فرعي للمرشح سيُستخدم لتحويل الأحرف إلى الترميز الهدف باستخدام "Unicode::Strings" و "Unicode::Map8" (الذين يحتاجان إلى التثبيت، راجع وثائق الوحدات لمعرفة الترميزات المتاحة على نظامك). 
my $conv = XML::Twig::unicode_convert( 'latin1');
my $t = XML::Twig->new(output_filter => $conv);

لا تستخدم الطرق "text" و "att" المرشح، لذا فإن نتائجها دائمًا باليونيكود.

تستند هذه المرشحات المعلنة مسبقًا إلى روتينات فرعية يمكن استخدامها بذاتها (مثل "XML::Twig::foo").

html_encode ($string)
يستخدم "HTML::Entities" لترميز سلسلة utf8.
safe_encode ($string)
يستخدم "Encode" لترميز الأحرف غير الأسكية في السلسلة بصيغة "&#<nnnn>;".
safe_encode_hex ($string)
يستخدم "Encode" لترميز الأحرف غير الأسكية في السلسلة بصيغة سداسية عشرية "&#x<nnnn>;".
regexp2latin1 ($string)
استخدم تعبيرًا نمطيًا لتشفير سلسلة utf8 إلى latin 1 (ISO-8859-1).
output_text_filter
مثل output_filter، إلا أنه لا يُطبَّق على الأقواس وعلامات الاقتباس المحيطة بقيم السمات. هذا مفيد لجميع المرشحات التي قد تغيّر الوسم، أي كل ما لا يغيّر فقط ترميز المخرجات. "html"، "safe" و "safe_hex" يُستخدمون بشكل أفضل مع هذا الخيار.
input_filter
هذا الخيار مشابه لـ "output_filter" إلا أن المرشح يُطبَّق على الأحرف قبل تخزينها في twig، في وقت التحليل.
remove_cdata
تعيين هذا الخيار إلى قيمة صحيحة سيجبر twig على إخراج أقسام "#CDATA" كـ "#PCDATA" عادية (مهرَّبة).
parse_start_tag
إذا استخدمت خيار "keep_encoding"، فيمكن استخدام هذا الخيار لاستبدال دالة التحليل الافتراضية. يجب أن توفّر coderef (مرجعًا إلى روتين فرعي) كوسيط. يأخذ هذا الروتين الفرعي الوسم الأصلي (المعطى بواسطة طريقة original_string() في XML::Parser::Expat) ويعيد وسمًا والسمات في hash (أو في قائمة attribute_name/attribute value).
no_xxe
يمنع تحليل الكيانات الخارجية.

هذه ميزة أمان، في حال كان إدخال XML غير موثوق. مع تعيين هذا الخيار إلى قيمة صحيحة، فإن تعريف الكيانات الخارجية في المستند سيتسبب في فشل التحليل.

هذا يمنع كيانًا مثل "<!ENTITY xxe PUBLIC "bar" "/etc/passwd">" من جعل حقل كلمة المرور متاحًا في المستند.

expand_external_ents
عند استخدام هذا الخيار، يتم توسيع الكيانات الخارجية (المعرَّفة) عند إخراج المستند باستخدام دوال "print" مثل "print "، "sprint "، "flush " و "xml_string ". لاحظ أنه في twig سيُخزَّن الكيان كعنصر بوسم '"#ENT"'، ولن يُوسَّع الكيان هناك، لذا قد ترغب في معالجة الكيانات قبل إخراجها.

إذا لم يكن الكيان الخارجي متاحًا، فسيفشل التحليل.

هناك حالة خاصة عندما تكون قيمة هذا الخيار -1. في تلك الحالة لن يتسبب كيان مفقود في موت المحلل، بل سيُخزَّن "name"، "sysid" و "pubid" الخاص به في twig كـ "$twig->{twig_missing_system_entities}" (مرجع إلى مصفوفة من hashes { name => <name>, sysid => <sysid>, pubid => <pubid> }). نعم، هذا نوع من الحلول الملتفة، لكنه مفيد في بعض الحالات.

load_DTD
إذا عُيِّن هذا الوسيط إلى قيمة صحيحة، فإن "parse" أو "parsefile" على twig سيحمّل معلومات DTD. يمكن بعد ذلك الوصول إلى هذه المعلومات عبر twig، في "DTD_handler" على سبيل المثال. هذا سيحمّل حتى DTD خارجيًا.

سيتم أيضًا ملء القيم الافتراضية والثابتة للسمات، بناءً على DTD.

لاحظ أنه للقيام بذلك ستولّد الوحدة ملفًا مؤقتًا في الدليل الحالي. إذا كان هذا مشكلة، أخبرني وسأضيف خيارًا لتحديد دليل بديل.

انظر "DTD Handling" لمزيد من المعلومات.

DTD_handler
يعيّن معالجًا سيُستدعى بمجرد تحميل doctype (و DTD)، بوسيطين: twig و DTD.
no_prolog
لا يُخرج prolog (إعلان XML و DTD).
id
يعطي هذا الوسيط الاختياري اسم سمة يمكن استخدامها كمعرّف في المستند. يمكن الوصول إلى العناصر التي يُعرف معرّفها عبر طريقة elt_id. القيمة الافتراضية لـ id هي 'id'. انظر "BUGS ".
discard_spaces
إذا عُيِّن هذا الوسيط الاختياري إلى قيمة صحيحة، فسيتم تجاهل المسافات عندما تبدو غير ذات دلالة: السلاسل التي تحتوي فقط على مسافات وعلى الأقل سطر جديد واحد يتم تجاهلها. يُعيَّن هذا الوسيط إلى true افتراضيًا.

الخوارزمية الدقيقة لإسقاط المسافات هي: السلاسل التي تتضمن فقط مسافات (perl \s) وعلى الأقل \n واحد مباشرة قبل وسم فتح أو إغلاق يتم إسقاطها.

discard_all_spaces
إذا عُيِّن هذا الوسيط إلى قيمة صحيحة، فسيتم تجاهل المسافات بشكل أكثر عدوانية من "discard_spaces": السلاسل التي لا تتضمن \n يتم إسقاطها أيضًا. هذا الخيار مناسب لـ XML الموجّه نحو البيانات.
keep_spaces
إذا عُيِّن هذا الوسيط الاختياري إلى قيمة صحيحة، فسيتم الاحتفاظ بجميع المسافات في المستند، وتُخزَّن كـ "#PCDATA".

تحذير: إضافة هذا الخيار يمكن أن تؤدي إلى تغييرات في twig المولَّد: المسافة التي كانت تُسقَط سابقًا قد تنتهي في عنصر نصي جديد. انظر الفرق باستدعاء الكود التالي مع 0 و 1 كوسيطين:

perl -MXML::Twig -e'print XML::Twig->new( keep_spaces => shift)->parse( "<d> \n<e/></d>")->_dump'

لا يمكن تعيين "keep_spaces" و "discard_spaces" معًا.

discard_spaces_in
يعيّن هذا الوسيط "keep_spaces" إلى true، لكنه يجعل باني twig يُسقط المسافات في العناصر المدرجة.

صيغة استخدام هذا الوسيط هي:

XML::Twig->new( discard_spaces_in => [ 'elt1', 'elt2']);
keep_spaces_in
يعيّن هذا الوسيط "discard_spaces" إلى true، لكنه يجعل باني twig يحتفظ بالمسافات في العناصر المدرجة.

صيغة استخدام هذا الوسيط هي:

XML::Twig->new( keep_spaces_in => [ 'elt1', 'elt2']);

تحذير: إضافة هذا الخيار يمكن أن تؤدي إلى تغييرات في twig المولَّد: المسافة التي كانت تُسقَط سابقًا قد تنتهي في عنصر نصي جديد.

pretty_print
يعيّن طريقة الطباعة الجميلة. القيم هي '"none"' (افتراضي)، '"nsgmls"'، '"nice"'، '"indented"'، '"indented_c"'، '"indented_a"'، '"indented_close_tag"'، '"cvs"'، '"wrapped"'، '"record"' و '"record_c"'.

تنسيقات pretty_print:

none
يُخرَج المستند كسلسلة واحدة طويلة، دون فواصل أسطر باستثناء تلك الموجودة داخل عناصر النص.
nsgmls
تُدرَج فواصل الأسطر في أماكن آمنة: أي داخل الوسوم، بين وسم وسمة، بين السمات وقبل > في نهاية الوسم.

هذا قبيح نوعًا ما لكنه أفضل من "none"، وهو آمن جدًا، وسيظل المستند صالحًا (متوافقًا مع DTD الخاص به).

هكذا يقسّم محلل SGML "sgmls" المستندات، ومن هنا الاسم.

nice
يُدرج هذا الخيار فواصل أسطر قبل أي وسم لا يحتوي على نص (لذا لا تُكسَر العناصر ذات المحتوى النصي لأن \n ذو دلالة).

تحذير: يترك هذا الخيار المستند سليم البنية لكنه قد يجعله غير صالح (غير متوافق مع DTD الخاص به). إذا كانت لديك عناصر معلنة كـ:

<!ELEMENT foo (#PCDATA|bar)>

فسيُطبَع عنصر "foo" الذي يتضمن عنصر "bar" كـ:

<foo>
<bar>bar is just pcdata</bar>
</foo>

هذا غير صالح، لأن المحلل سيعتبر فاصل السطر بعد وسم "foo" علامة على أن العنصر يحتوي على PCDATA، ثم سيموت عندما يجد وسم "bar". قد يكون هذا أو لا يكون مهمًا بالنسبة لك، لكن كن على علم بذلك!

indented
مثل "nice" (ومع نفس التحذير) لكنه يزحزح العناصر وفقًا لمستواها.
indented_c
مثل "indented"، لكنه أكثر إحكامًا قليلًا: وسوم الإغلاق تكون على نفس سطر النص السابق.
indented_close_tag
مثل "indented"، إلا أن وسم الإغلاق يكون مزاحًا أيضًا، ليصطف مع الوسوم داخل العنصر.
indented_a
يُنسّق هذا ملفات XML بطريقة صديقة لأنظمة التحكم بالإصدارات الموجّهة نحو الأسطر. التنسيق موصوف في http://tinyurl.com/2kwscq (هذا مستند Oracle يحتوي علىعنوان URL طويل بشكل جنوني).

لاحظ أنه لكي تكون متوافقًا تمامًا مع "المواصفات"، يجب ألا يتم تغيير ترتيب السمات، لذا إذا لم تكن بالفعل بترتيب أبجدي فستحتاج إلى استخدام خيار "keep_atts_order ".

cvs
مثل "indented_a ".
wrapped
مثل "indented_c"، لكن يتم لف الأسطر باستخدام Text::Wrap::wrap. الطول الافتراضي للأسطر هو الافتراضي لـ $Text::Wrap::columns، ويمكن تغييره بتغيير ذلك المتغير.
record
هذا طباعة جميلة موجهة نحو السجلات تعرض البيانات في سجلات، حقل واحد لكل سطر (وهو يشبه كثيرًا "indented").
record_c
يرمز إلى سجل مضغوط، سجل واحد لكل سطر.
empty_tags
يضبط نمط عرض الوسم الفارغ ('"normal"'، '"html"' أو '"expand"').

"normal" يُخرج وسمًا فارغًا '"<tag/>"'، "html" يضيف مسافة '"<tag />"' للعناصر التي يمكن أن تكون فارغة في XHTML و "expand" يُخرج '"<tag></tag>"'.

quote
يضبط حرف الاقتباس للسمات ('"single"' أو '"double"').
escape_gt
بشكل افتراضي لا يقوم XML::Twig بتهريب حرف > في مخرجاته، لأنه غير مفروض بواسطة مواصفات XML. عند تفعيل هذا الخيار، يتم استبدال > بـ "&gt;".
comments
يضبط طريقة معالجة التعليقات: '"drop"' (الافتراضي)، '"keep"' أو '"process"'.

خيارات معالجة التعليقات:

drop
يُسقط التعليقات؛ لا يتم قراءتها، ولا طباعتها إلى المخرجات.
keep
يتم تحميل التعليقات وستظهر في المخرجات؛ لكنها غير قابلة للوصول داخل twig ولن تتداخل مع المعالجة.

ملاحظة: التعليقات في منتصف عنصر نصي مثل:

<p>text <!-- comment --> more text --></p>

يتم الاحتفاظ بها في موضعها الأصلي في النص. استخدام طرق "print" مثل "print" أو "sprint" سيعيد التعليقات في النص. استخدام "text" أو "field" من ناحية أخرى لن يفعل ذلك.

أي استخدام لـ "set_pcdata" على عنصر "#PCDATA" (مباشرة أو من خلال طرق أخرى مثل "set_content") سيحذف التعليق/التعليقات.

process
يتم تحميل التعليقات في twig وتُعامل كعناصر عادية بقيمة "tag" تساوي "#COMMENT". هذا يمكن أن يتداخل مع المعالجة إذا كنت تتوقع أن يكون "$elt->{first_child}" عنصرًا لكنك تجد تعليقًا هناك. لن يحميك التحقق من صحة المخطط من هذا لأن التعليقات يمكن أن تحدث في أي مكان. يمكنك استخدام "$elt->first_child( 'tag')" (وهي عادة جيدة على أي حال) للحصول على ما تريد.

فكر في استخدام "process" إذا كنت تُخرج أحداث SAX من XML::Twig.

pi
يضبط طريقة معالجة تعليمات المعالجة: '"drop"'، '"keep"' (الافتراضي)، أو '"process"'.

لاحظ أنه يمكنك أيضًا تعيين معالجات PI في خيار "twig_handlers":

'?'       => \&handler
'?target' => \&handler2

سيتم استدعاء المعالجات بمعاملين، الـ twig و عنصر PI إذا تم تعيين "pi" إلى "process"، وثلاثة، الـ twig، والهدف والبيانات إذا تم تعيين "pi" إلى "keep". بالطبع لن يتم استدعاؤها إذا تم تعيين "pi" إلى "drop".

إذا تم تعيين "pi" إلى "keep"، يجب أن تُعيد المعالجة سلسلة تُستخدم كما هي كنص PI (يجب أن تبدو مثل "" <?target data?" >" أو '' إذا كنت تريد إزالة PI)،

سيتم استدعاء معالج واحد فقط، "?target" أو "?" إذا لم يكن هناك معالج محدد لذلك الهدف متاح.

map_xmlns
يُمرر لهذا الخيار مرجع تجزئة يربط عناوين URI بالبادئات. سيتم استبدال البادئات في المستند بالبادئات الموجودة في الخريطة. يمكن استخدام البادئات المعينة (في الواقع يجب) لتحفيز المعالجات، أو التنقل أو الاستعلام عن المستند.

مثال:

my $t= XML::Twig->new( map_xmlns => {'http://www.w3.org/2000/svg' => "svg"},
                       twig_handlers =>
                         { 'svg:circle' => sub { $_->set_att( r => 20) } },
                       pretty_print => 'indented',
                     )
                ->parse( '<doc xmlns:gr="http://www.w3.org/2000/svg">
                            <gr:circle cx="10" cy="90" r="10"/>
                         </doc>'
                       )
                ->print;

سيُخرج هذا:

<doc xmlns:svg="http://www.w3.org/2000/svg">
   <svg:circle cx="10" cy="90" r="20"/>
</doc>
keep_original_prefix

my $t= XML::Twig->new( map_xmlns => {'http://www.w3.org/2000/svg' => "svg"},
                       twig_handlers =>
                         { 'svg:circle' => sub { $_->set_att( r => 20) } },
                       keep_original_prefix => 1,
                       pretty_print => 'indented',

                ->parse( '<doc xmlns:gr="http://www.w3.org/2000/svg">

<doc xmlns:gr="http://www.w3.org/2000/svg">

original_uri ($prefix)
عند استدعائها داخل معالج، تُعيد عنوان URI المرتبط ببادئة مساحة الأسماء في المستند الأصلي.
index ($arrayref أو $hashref)
ينشئ هذا الخيار قوائم بعناصر محددة أثناء تحليل XML. يأخذ مرجعًا إما إلى قائمة تعبيرات محفزة أو إلى تجزئة اسم => تعبير، ولكل واحد منها يُنشئ قائمة العناصر التي تطابق التعبير. يمكن الوصول إلى القائمة من خلال طريقة "index ".

مثال:

# using an array ref
my $t= XML::Twig->new( index => [ 'div', 'table' ])
                ->parsefile( "foo.xml");
my $divs= $t->index( 'div');
my $first_div= $divs->[0];
my $last_table= $t->index( table => -1);
# using a hashref to name the indexes
my $t= XML::Twig->new( index => { email => 'a[@href=~/^ \s*mailto:/]'})
                ->parsefile( "foo.xml");
my $last_emails= $t->index( email => -1);

لاحظ أن الفهرس لا يُصان بعد التحليل. إذا تم حذف العناصر، أو إعادة تسميتها، أو إتلافها بطريقة أخرى أثناء المعالجة، فإن الفهرس لا يتم تحديثه. (تغيير عنصر المعرف، من ناحية أخرى، سيُحدّث الفهرس).

att_accessors <قائمة أسماء السمات>
ينشئ طرقًا تمنح وصولًا مباشرًا إلى السمة: 
my $t= XML::Twig->new( att_accessors => [ 'href', 'src'])
                ->parsefile( $file);
my $first_href= $t->first_elt( 'img')->src; # same as ->att( 'src')
$t->first_elt( 'img')->src( 'new_logo.png') # changes the attribute value
elt_accessors
ينشئ طرقًا تمنح وصولًا مباشرًا إلى أول عنصر فرعي (في سياق عددي) أو قائمة العناصر (في سياق قائمة):

يمكن إعطاء قائمة الوصولات المراد إنشاؤها بطريقتين مختلفتين: في مصفوفة، أو في تجزئة اسم مستعار => تعبير.

my $t=  XML::Twig->new( elt_accessors => [ 'head'])
                ->parsefile( $file);
my $title_text= $t->root->head->field( 'title');
# same as $title_text= $t->root->first_child( 'head')->field( 'title');
my $t=  XML::Twig->new( elt_accessors => { warnings => 'p[@class="warning"]', d2 => 'div[2]'}, )
                ->parsefile( $file);
my $body= $t->first_elt( 'body');
my @warnings= $body->warnings; # same as $body->children( 'p[@class="warning"]');
my $s2= $body->d2;             # same as $body->first_child( 'div[2]')
field_accessors

my $t=  XML::Twig->new( field_accessors => [ 'h1'])

my $div_title_text= $t->first_elt( 'div')->title;

use_tidy
اضبط هذا الخيار لاستخدام HTML::Tidy بدلاً من HTML::TreeBuilder لتحويل HTML إلى XML. بالنسبة لـ HTML، وخاصة HTML الحقيقي (الحقيقي "الرديء") الموجود في البرية، تقوم إحدى الوحدات أو الأخرى بعمل أفضل في التحويل. أيضًا، قد يكون تثبيت HTML::Tidy صعبًا بعض الشيء، لذا يقدم XML::Twig كلا الخيارين. TIMTOWTDI.
output_html_doctype
عند استخدام HTML::TreeBuilder لتحويل HTML، يتسبب هذا الخيار في إخراج تعريف DOCTYPE، والذي قد يكون مهمًا لبعض المتصفحات القديمة. بدون هذا الخيار لا يتم إخراج تعريف DOCTYPE. أيضًا إذا كان التعريف خاطئًا تمامًا (أي غير قابل للتحليل بسهولة)، فلا يتم إخراجه أيضًا.

parse ( $source)
يجب أن تكون المعلمة $source إما سلسلة تحتوي على مستند XML كامل، أو يجب أن تكون "IO::Handle" مفتوحًا (أي مقبض ملف).

يتم طرح استدعاء "die" إذا حدث خطأ في التحليل. وإلا، فإنه يعيد الغصن الذي بناه التحليل. استخدم "safe_parse" إذا كنت تريد أن يعود التحليل حتى عند حدوث خطأ.

إذا تم استدعاء هذه الطريقة كطريقة صنف ("XML::Twig->parse( $some_xml_or_html)") فسيتم إنشاء كائن XML::Twig، باستخدام المعلمات باستثناء الأخيرة (مثل "XML::Twig->parse( pretty_print => 'indented', $some_xml_or_html)") ويتم استدعاء "xparse " عليه.

لاحظ أنه عند تحليل مقبض ملف، يجب ألا يكون المقبض مفتوحًا بترميز (أي افتح بـ "open( my $in, '<', $filename)". سيتم تحليل الملف بواسطة "expat"، لذا فإن تحديد الترميز يسبب في الواقع مشاكل للمحلل (بمعنى: يمكن أن يتعطل، انظر https://rt.cpan.org/Ticket/Display.html?id=78877). لتحليل ملف يُوصى في الواقع باستخدام "parsefile" على اسم الملف، بدلاً من <parse> على الملف المفتوح.

parsestring
مثل "parse" (للتوافق العكسي).
parsefile (FILE [, OPT => OPT_VALUE [...]])
يفتح "FILE" للقراءة، ثم يستدعي "parse" بالمقبض المفتوح. يتم إغلاق الملف بغض النظر عن كيفية عودة "parse".

يتم طرح استدعاء "die" إذا حدث خطأ في التحليل. وإلا فإنه يعيد الغصن الذي بناه التحليل. استخدم "safe_parsefile" إذا كنت تريد أن يعود التحليل حتى عند حدوث خطأ.

flush ($optional_filehandle, %options)
يفرغ twig حتى (وبما في ذلك) العنصر الحالي، ثم يحذف جميع العناصر غير الضرورية من الشجرة الموجودة في الذاكرة. يتتبع "flush" العناصر التي تحتاج إلى فتح/إغلاق، لذا إذا قمت بالتفريغ من المعالجات فلن تضطر إلى القلق بشأن أي شيء. فقط استمر في تفريغ twig في كل مرة تنتهي فيها
مع شجرة فرعية وسيخرج بتنسيق جيد. بعد اكتمال التحليل، لا تنسَ "flush" مرة أخرى لطباعة نهاية المستند. يتم أيضًا طباعة إعلانات doctype والكيانات.

"flush" يأخذ مقبض ملف اختياري كوسيط.

إذا استخدمت "flush" في أي نقطة أثناء التحليل، سيتم تفريغ المستند مرة أخيرة في نهاية التحليل، إلى مقبض الملف المناسب.

خيار "pretty_print" يضبط الطباعة الجميلة للمستند.

مثال: $t->flush( Update_DTD => 1);
         $t->flush( $filehandle, pretty_print => 'indented');
         $t->flush( \*FILE);

XML::Twig::Elt

new ($optional_tag, $optional_atts, @optional_content)
يُرجع العنصر المُنشأ حديثًا.

يكون "tag" اختياريًا (لكن حينها لا يمكنك الحصول على محتوى!)، وسيط $optional_atts هو مرجع إلى تجزئة من السمات، ويمكن أن يكون المحتوى مجرد سلسلة أو قائمة من السلاسل والعناصر. المحتوى '"#EMPTY"' يُنشئ عنصرًا فارغًا.

Examples: my $elt= XML::Twig::Elt->new();
          my $elt= XML::Twig::Elt->new( para => { align => 'center' });
          my $elt= XML::Twig::Elt->new( para => { align => 'center' }, 'foo');
          my $elt= XML::Twig::Elt->new( br   => '#EMPTY');
          my $elt= XML::Twig::Elt->new( 'para');
          my $elt= XML::Twig::Elt->new( para => 'this is a para');
          my $elt= XML::Twig::Elt->new( para => $elt3, 'another para');

لا يتم تحليل السلاسل، ولا يتم إرفاق العنصر بأي twig.

تحذير: إذا كنت تعتمد على المعرّفات فسيتعين عليك تعيين المعرّف بنفسك. في هذه المرحلة لا ينتمي العنصر إلى twig بعد، لذا سمة المعرّف غير معروفة ولن تُخزَّن في قائمة المعرّفات.

لاحظ أن "#COMMENT" و "#PCDATA" و "#CDATA" هي أسماء وسوم صالحة ستُنشئ تلك الأنواع من العناصر.

لإنشاء عنصر "foo" يحتوي على قسم "#CDATA":

my $foo= XML::Twig::Elt->new( '#CDATA' => "content of the CDATA section")
                       ->wrap_in( 'foo');

سمة

من '#CDATA'، عند تعيينه، يُنشئ محتوى العنصر كـ CDATA:

my $elt= XML::Twig::Elt->new( 'p' => { '#CDATA' => 1}, 'foo < bar');

يُنشئ عنصرًا.

<p><![CDATA[foo < bar]]></>

أمثلة

يمكن العثور على أمثلة إضافية (ودرس تعليمي كامل) على صفحة XML::Twighttp://www.xmltwig.org/xmltwig/.

لمعرفة ما تفعله flush، استدعِ السكربت التالي مع ملف XML واسم عنصر كوسائط:

use XML::Twig;
my ($file, $elt)= @ARGV;
my $t= XML::Twig->new( twig_handlers =>
    { $elt => sub {$_[0]->flush; print "\n[flushed here]\n";} });
$t->parsefile( $file, ErrorContext => 2);
$t->flush;
print "\n";

ملاحظات

إنشاء فئة فرعية من XML::Twig

طرق مفيدة:

elt_class
لإنشاء فئة فرعية من "XML::Twig"، ستحتاج على الأرجح إلى إنشاء فئة فرعية أيضًا من "XML::Twig::Elt ". استخدم خيار "elt_class" عند إنشاء كائن "XML::Twig" للحصول على العناصر المنشأة في فئة مختلفة (والتي يجب أن تكون فئة فرعية من "XML::Twig::Elt".
add_options
إذا ورثت طريقة new الخاصة بـ "XML::Twig" لكنك تريد إضافة المزيد من الخيارات إليها، يمكنك استخدام هذه الطريقة لمنع XML::Twig من إصدار تحذيرات بشأن تلك الخيارات الإضافية.

معالجة DTD

هناك 3 احتمالات هنا. وهي:

لا DTD
لا doctype، ولا معلومات DTD، ولا معلومات كيانات، والعالم بسيط...
DTD داخلي
يتضمن مستند XML تعريف نوع مستند (DTD) داخلي، وربما إعلانات كيانات.

إذا استخدمت خيار load_DTD عند إنشاء twig، فيمكن الوصول إلى معلومات DTD وإعلانات الكيانات.

سيتم "flush" (أو "print") لـ DTD وإعلانات الكيانات إما كما هي (إذا لم يتم تعديلها) أو كما أعيد بناؤها (بشكل رديء، تُفقد التعليقات، ولا يُحافظ على الترتيب، ونظرًا لمحتواها فلا ينبغي لأي شخص عرض هذا DTD) إذا تم تعديلها. يمكنك أيضًا تعديلها مباشرةً بتغيير الحقل "$twig->{twig_doctype}->{internal}" (مباشرةً من XML::Parser، انظر وثائق معالج "Doctype").

DTD خارجي
يتضمن مستند XML إشارة إلى DTD خارجي، وربما إعلانات كيانات.

إذا استخدمت "load_DTD" عند إنشاء twig، فيمكن الوصول إلى معلومات DTD وإعلانات الكيانات. سيتم "flush" (أو "print") لإعلانات الكيانات إما كما هي (إذا لم يتم تعديلها) أو كما أعيد بناؤها (بشكل سيئ، تُفقد التعليقات، ولا يُحافظ على الترتيب).

يمكنك تغيير doctype عبر طريقة "$twig->set_doctype" وطباعة dtd عبر "$twig->dtd_text" أو "$twig->dtd_print"
.

إذا كنت بحاجة إلى تعديل قائمة الكيانات، فمن المحتمل أن تكون هذه أسهل طريقة للقيام بذلك.

Flush

تذكّر أن معالجات العناصر تُستدعى عند إغلاق العنصر (CLOSED)، لذا إذا كانت لديك معالجات لعناصر متداخلة فسيتم استدعاء المعالجات الداخلية أولًا. وهذا يجعل، على سبيل المثال، ترقيم الأقسام المتداخلة (أو البنود، أو divs) أصعب مما قد يبدو، لأن عناوين الأقسام الداخلية تُعالج قبل الأقسام الخارجية.

الأخطاء

segfault أثناء التحليل
يحدث هذا عند تحليل مستندات ضخمة، أو الكثير من المستندات الصغيرة، باستخدام إصدار من Perl أقدم من 5.16.

وهذا راجع إلى خطأ في طريقة معالجة المراجع الضعيفة في Perl نفسه.

الإصلاح هو إما الترقية إلى Perl 5.16 أو أحدث ("perlbrew" أداة رائعة لإدارة عدة تثبيتات من perl على الجهاز نفسه).

وهناك طريقة أخرى، غير موصى بها، لإصلاح المشكلة، وهي إيقاف المراجع الضعيفة بكتابة "XML::Twig::_set_weakrefs( 0);" في أعلى الشيفرة. هذا غير مدعوم إطلاقًا، وقد يؤدي إلى مشكلات أخرى رغم ذلك.

معالجة الكيانات
بسبب سلوك XML::Parser، تختفي الكيانات غير الأساسية في قيم السمات إذا لم تكن معلنة في المستند: "att="val&ent;"" ستتحول إلى "att => val"، ما لم تستخدم وسيط "keep_encoding" مع "XML::Twig->new".
معالجة DTD
طرق معالجة DTD مليئة بالأخطاء إلى حد كبير. لا أحد يستخدمها ويبدو أنه من الصعب جدًا جعلها تعمل في جميع الحالات، بما في ذلك مع عدة إصدارات غير متوافقة قليلًا من XML::Parser ومن libexpat.

في الأساس يمكنك قراءة DTD، وإخراجه مرة أخرى بشكل صحيح، وتحديث الكيانات، لكن ليس أكثر من ذلك بكثير.

لذا استخدم XML::Twig مع مستندات مستقلة، أو مع مستندات تشير إلى DTD خارجي، لكن لا تتوقع منه أن يحلل DTD بشكل صحيح أو حتى أن يعيد إخراجه.

قائمة ID
لا يتم تحديث قائمة ID عند قطع العناصر أو حذفها.
change_gi
لن تعمل هذه الطريقة بشكل صحيح إذا قمت بما يلي: 
$twig->change_gi( $old1, $new);
$twig->change_gi( $old2, $new);
$twig->change_gi( $new, $even_newer);
فحص سلامة استدعاءات طرق XML::Parser
ينبغي لـ XML::Twig فعليًا منع الاستدعاءات إلى بعض طرق XML::Parser، وخاصة طريقة "setHandlers".
الطباعة الجميلة
الطباعة الجميلة (على الأقل باستخدام نمط '"indented"') يصعب ضبطها بشكل صحيح! فقط العناصر التي تنتمي إلى المستند سيتم إزاحتها بشكل صحيح. طباعة عناصر لا تنتمي إلى twig تجعل من المستحيل على XML::Twig معرفة عمقها، وبالتالي مستوى إزاحتها.

هناك أيضًا خطأ لا مفر منه عند استخدام "flush" والطباعة الجميلة للعناصر ذات المحتوى المختلط التي تبدأ بعنصر مضمّن:

<elt><b>b</b>toto<b>bold</b></elt>
سيُخرَج كـ
<elt>
  <b>b</b>toto<b>bold</b></elt>

إذا قمت بعمل flush للـ twig عند العثور على عنصر "<b>".

المتغيرات العامة

هذه هي الأشياء التي يمكن أن تعبث بشيفرة الاستدعاء، خاصةً إذا كانت متعددة الخيوط. وقد تسبب أيضًا مشكلات تحت mod_perl.

الثوابت المصدَّرة
سواء أردتها أم لا فستحصل عليها! هذه إجراءات فرعية تُستخدم كثوابت عند إنشاء العناصر أو اختبارها: 
PCDATA  return '#PCDATA'
CDATA   return '#CDATA'
PI      return '#PI', I had the choice between PROC and PI :--(
قيم على نطاق الوحدة: الثوابت
هذه لا ينبغي أن تسبب أي مشكلة: 
%base_ent= ( '>' => '&gt;',
             '<' => '&lt;',
             '&' => '&amp;',
             "'" => '&apos;',
             '"' => '&quot;',
           );
CDATA_START   = "<![CDATA[";
CDATA_END     = "]]>";
PI_START      = "<?";
PI_END        = "?>";
COMMENT_START = "<!--";
COMMENT_END   = "-->";

أنماط الطباعة الجميلة:

( $NSGMLS, $NICE, $INDENTED, $INDENTED_C, $WRAPPED, $RECORD1, $RECORD2)= (1..7);

نمط إخراج الوسم الفارغ:

( $HTML, $EXPAND)= (1..2);
قيم على نطاق الوحدة: قد تتغير
معظم هذه تتعامل مع الطباعة الجميلة، لذا أسوأ ما يمكن أن يحدث هو على الأرجح ألا يبدو إخراج XML صحيحًا، لكنه يظل صالحًا ويُعالج بشكل مماثل بواسطة معالجات XML.

يمكن أن يعبث $empty_tag_style بمتصفحات HTML رغم ذلك، وتغيير $ID من المرجح أن يخلق مشكلات.

$pretty=0;           # pretty print style
$quote='"';          # quote for attributes
$INDENT= '  ';       # indent for indented pretty print
$empty_tag_style= 0; # how to display empty tags
$ID                  # attribute used as an id ('id' by default)
قيم على نطاق الوحدة: تتغير بالتأكيد
يُستخدم هذان المتغيران لاستبدال الوسوم بفهرس، مما يوفر بعض المساحة عند إنشاء twig. إذا كانت تسبب لك مشكلات كبيرة حقًا، فأخبرني، فمن المحتمل أنه يمكن إنشاء إما مفتاح تبديل أو على الأقل إصدار من XML::Twig لا ينفذ هذا التحسين. 
%gi2index;     # tag => index
@index2gi;     # list of tags

إذا كنت بحاجة إلى التعامل مع كل تلك القيم، يمكنك استخدام الطرق التالية على كائن XML::Twig:

global_state
يعيد مرجع hash يحتوي على جميع المتغيرات العامة التي يستخدمها XML::Twig.

يحتوي الـ hash على الحقول التالية: "pretty", "quote", "indent", "empty_tag_style", "keep_encoding", "expand_external_entities", "output_filter", "output_text_filter", "keep_atts_order".

set_global_state ($state)
يضبط الحالة العامة، $state هو مرجع hash.
save_global_state
يحفظ الحالة العامة الحالية.
restore_global_state
يستعيد الحالة المحفوظة سابقًا (باستخدام "Lsave_global_state">.

وحدات بديلة

XML::Twig ليس الوحدة الوحيدة لمعالجة XML المتاحة على CPAN (بل هو بعيد عن ذلك!).

البديل الرئيسي الذي أوصي به هو XML::LibXML.

فيما يلي مقارنة سريعة بين الوحدتين:

XML::LibXML، في الواقع "libxml2" الذي يعتمد عليه، يلتزم بالمعايير، وينفذ عدداً جيداً منها بطريقة صارمة إلى حد ما: XML، XPath، DOM، RelaxNG، ولا بد أنني أنسى اثنين (XInclude؟). إنه سريع واقتصادي إلى حد ما في استهلاك الذاكرة.

XML::Twig أقدم: عندما بدأت كتابته كان XML::Parser/expat هو الخيار الوحيد المتاح. إنه ينفذ XML وهذا كل شيء تقريباً (بالإضافة إلى مجموعة فرعية من XPath، ويمكنك استخدام XML::Twig::XPath إذا كان لديك XML::XPathEngine مثبتاً للحصول على دعم كامل). إنه أبطأ ويتطلب ذاكرة أكبر لشجرة كاملة مقارنة بـ XML::LibXML. من الجانب الإيجابي (نعم، هناك جانب إيجابي!) فهو يتيح لك معالجة مستند كبير على شكل أجزاء، وبالتالي يتيح لك التعامل مع مستندات لا يمكن تحميلها في الذاكرة بواسطة XML::LibXML، كما أنه يوفر الكثير (وأعني الكثير!) من الطرق عالية المستوى، لكل شيء، من إضافة البنية إلى XML "منخفض المستوى"، إلى اختصارات لتحويلات XHTML والمزيد. كما أنه يطبق مبدأ DWIM إلى حد ما، فيزيل التعليقات والمسافات البيضاء غير الدلالية من الطريق مع الحفاظ عليها في المخرجات على سبيل المثال. ولأنه لا يلتزم بـ DOM، فإنه عادةً ما يؤدي أيضاً إلى كود أقصر مما هو عليه في XML::LibXML.

بالإضافة إلى الميزات البحتة للوحدتين، يبدو أن XML::LibXML مفضل لدى "متزمتي XML"، بينما يبدو أن XML::Twig أكثر استخداماً من قبل قراصنة Perl الذين يتعين عليهم التعامل مع XML. وكما لاحظت، يأتي XML::Twig أيضاً مع الكثير من الوثائق، لكنني متأكد من أنك إذا طلبت المساعدة بشأن XML::LibXML هنا أو على Perlmonks فستحصل على إجابات.

لاحظ أنه في الواقع من الصعب جداً عليّ مقارنة الوحدتين: فمن ناحية أعرف XML::Twig من الداخل والخارج ويمكنني جعله يفعل أي شيء أحتاجه تقريباً (أو أحسّنه ؛--)، بينما لدي معرفة أساسية جداً بـ XML::LibXML. لذا من حيث الميزات، أفضل استخدام XML::Twig ؛--). من ناحية أخرى، أنا مدرك بشكل مؤلم لبعض أوجه القصور، والأخطاء المحتملة، والكود القبيح ببساطة التي تكمن في XML::Twig، حتى لو كان من غير المرجح أن تتأثر بها (إلا إذا كنت مثلاً بحاجة إلى تغيير DTD لمستند برمجياً)، بينما لم أتعمق كثيراً في XML::LibXML لذا لا يزال يبدو لامعاً ونظيفاً بالنسبة لي.

ومع ذلك، إذا كنت بحاجة إلى معالجة مستند كبير جداً بحيث لا يتسع له الذاكرة وكان XML::Twig بطيئاً جداً بالنسبة لك، فإن نصيحتي المترددة هي استخدام XML::Parser "المجرد". لن يكون سهل الاستخدام مثل XML::Twig: في الأساس مع XML::Twig أنت تقايض بعض السرعة (اعتماداً على ما تفعله بمعامل من 3 إلى... لا شيء) مقابل سهولة الاستخدام، لكنه سيكون أسهل في رأيي المتواضع من استخدام SAX (وإن لم يكن قياسياً)، وعند هذه النقطة أسرع بكثير (انظر الاختبار الأخير في http://www.xmltwig.org/article/simple_benchmark/).
