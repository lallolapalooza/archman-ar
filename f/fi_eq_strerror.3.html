الوصف

تُستخدم قوائم الانتظار للأحداث للإبلاغ عن الأحداث المرتبطة بعمليات التحكم. وهي مرتبطة بتسجيل الذاكرة، ومتجهات العناوين، وإدارة الاتصالات، والأحداث على مستوى النسيج والنطاق. الأحداث المُبلَّغ عنها إما أن تكون مرتبطة بعملية مطلوبة أو مرتبطة بنداء يسجّل لأنواع محددة من الأحداث، مثل الاستماع لطلبات الاتصال.

fi_eq_open

يخصص fi_eq_open قائمة انتظار جديدة للأحداث.

تُعرَّف خصائص وسلوك قائمة انتظار للأحداث بواسطة struct fi_eq_attr.

struct fi_eq_attr {
    size_t               size;      /* # entries for EQ */
    uint64_t             flags;     /* operation flags */
    enum fi_wait_obj     wait_obj;  /* requested wait object */
    int                  signaling_vector; /* interrupt affinity */
    struct fid_wait     *wait_set;  /* optional wait set, deprecated */
};
size
يحدد الحد الأدنى لحجم قائمة انتظار للأحداث.
flags
أعلام تتحكم في تكوين EQ.
- FI_WRITE
يشير إلى أن التطبيق يتطلب دعمًا لإدراج أحداث المستخدم في EQ. إذا تم تعيين هذا العلم، فيجب أن يدعم المزوّد عملية fi_eq_write. إذا لم يتم تعيين علم FI_WRITE، فلا يجوز للتطبيق استدعاء fi_eq_write.
- FI_AFFINITY
يشير إلى أن حقل signaling_vector (انظر أدناه) صالح.
wait_obj
قد ترتبط قوائم EQ بكائن انتظار محدد. تسمح كائنات الانتظار للتطبيقات بالحجب حتى يتم إشارة كائن الانتظار، مما يشير إلى توفر حدث جاهز للقراءة. يمكن للمستخدمين استخدام fi_control لاسترداد كائن الانتظار الأساسي المرتبط بـ EQ، لاستخدامه في نداءات نظام أخرى. يمكن استخدام القيم التالية لتحديد نوع كائن الانتظار المرتبط بـ EQ:
- FI_WAIT_NONE
يُستخدم للإشارة إلى أن المستخدم لن يحجب (ينتظر) الأحداث على EQ. عند تحديد FI_WAIT_NONE، لا يجوز للتطبيق استدعاء fi_eq_sread. هذا هو الافتراضي إذا لم يتم تحديد كائن انتظار.
- FI_WAIT_UNSPEC
يحدد أن المستخدم سينتظر فقط على EQ باستخدام نداءات واجهة النسيج، مثل fi_eq_sread. في هذه الحالة، قد يختار المزوّد الأساسي كائن الانتظار الأنسب أو الأعلى أداءً المتاح، بما في ذلك آليات الانتظار المخصصة. لا يُضمن للتطبيقات التي تختار FI_WAIT_UNSPEC استرداد كائن الانتظار الأساسي.
- FI_WAIT_SET (مهمل)
يشير إلى أن قائمة انتظار للأحداث يجب أن تستخدم كائن مجموعة انتظار لانتظار الأحداث. إذا تم تحديده، فيجب أن يشير حقل wait_set إلى كائن مجموعة انتظار موجود.
- FI_WAIT_FD
يشير إلى أن EQ يجب أن يستخدم واصف ملف كآلية انتظار له. يجب أن يكون كائن انتظار واصف الملف قابلاً للاستخدام في إجراءات select وpoll وepoll. ومع ذلك، قد يشير المزوّد إلى كائن انتظار FD عن طريق تعليمه كقابل للقراءة أو بخطأ.
- FI_WAIT_MUTEX_COND (مهمل)
يحدد أن EQ يجب أن يستخدم mutex وcond variable من pthread ككائن انتظار.
- FI_WAIT_YIELD
يشير إلى أن EQ سينتظر بدون كائن انتظار ولكن بدلاً من ذلك سيتنازل في كل انتظار. يسمح باستخدام fi_eq_sread عبر دوران.
signaling_vector
إذا تم تعيين علم FI_AFFINITY، فهذا يشير إلى رقم المعالج المنطقي (0..max cpu - 1) الذي يجب أن تستهدفه المقاطعات المرتبطة بـ EQ. يجب التعامل مع هذا الحقل كتلميح للمزوّد وقد يتم تجاهله إذا كان المزوّد لا يدعم تقارب المقاطعات.
wait_set (مهمل)
إذا كان wait_obj هو FI_WAIT_SET، فإن هذا الحقل يشير إلى كائن انتظار يجب أن ترتبط به قائمة انتظار للأحداث. عند إدراج حدث في قائمة انتظار للأحداث، ستتم الإشارة إلى مجموعة الانتظار المقابلة إذا تم استيفاء جميع الشروط اللازمة. يتيح استخدام wait_set طريقة محسّنة لانتظار الأحداث عبر قوائم انتظار متعددة للأحداث. يتم تجاهل هذا الحقل إذا لم يكن wait_obj هو FI_WAIT_SET.

fi_close

يحرر نداء fi_close جميع الموارد المرتبطة بقائمة انتظار للأحداث. أي أحداث تبقى على EQ عند إغلاقه تُفقد.

يجب ألا يكون EQ مرتبطًا بأي كائنات أخرى قبل إغلاقه، وإلا سيعيد النداء -FI_EBUSY.

fi_control

يُستخدم نداء fi_control للوصول إلى تفاصيل قائمة انتظار للأحداث الخاصة بالمزوّد أو التنفيذ. يجب تسلسل الوصول إلى EQ عبر جميع النداءات عندما fi_contrيتم استدعاء ol، حيث قد يعيد توجيه تنفيذ عمليات EQ. الأوامر التحكمية التالية قابلة للاستخدام مع EQ.

FI_GETWAIT (void **)
يسمح هذا الأمر للمستخدم باسترداد كائن الانتظار منخفض المستوى المرتبط بـ EQ. يتم تحديد تنسيق كائن الانتظار أثناء إنشاء EQ، من خلال سمات EQ. يجب أن تكون معلمة fi_control arg عنوانًا حيث سيتم كتابة مؤشر إلى كائن الانتظار المُعاد. يجب أن يكون هذا ’int *’ لـ FI_WAIT_FD، أو `struct fi_mutex_cond' لـ FI_WAIT_MUTEX_COND (مهجور).
struct fi_mutex_cond {
    pthread_mutex_t     *mutex;
    pthread_cond_t      *cond;
};

fi_eq_read

تُجري عمليات fi_eq_read قراءة غير حاجزة لبيانات الحدث من EQ. يعتمد تنسيق بيانات الحدث على نوع الحدث المسترد من EQ، حيث تبدأ جميع الأحداث بترويسة struct fi_eq_entry. سيتم إرجاع حدث واحد على الأكثر لكل عملية قراءة من EQ. يتم إرجاع عدد البايتات المقروءة بنجاح من EQ من عملية القراءة. يمكن استخدام علامة FI_PEEK للإشارة إلى أنه يجب قراءة بيانات الحدث من EQ دون استهلاكها. ستؤدي القراءة اللاحقة بدون علامة FI_PEEK بعد ذلك إلى إزالة الحدث من EQ.

قد يتم الإبلاغ عن الأنواع التالية من الأحداث إلى EQ، إلى جانب المعلومات المتعلقة بالتنسيق المرتبط بكل حدث.

عمليات التحكم غير المتزامنة
عمليات التحكم غير المتزامنة هي طلبات أساسية تحتاج ببساطة إلى توليد حدث للإشارة إلى أنها قد اكتملت. تشمل هذه الأنواع التالية من الأحداث: تسجيل الذاكرة، وحل متجه العنوان، والانضمام إلى البث المتعدد.

تُبلغ طلبات التحكم عن اكتمالها عن طريق إدراج struct fi_eq_entry في EQ. تنسيق هذا الهيكل هو:

struct fi_eq_entry {
    fid_t            fid;        /* fid associated with request */
    void            *context;    /* operation context */
    uint64_t         data;       /* completion-specific data */
};

لاكتمال عمليات التحكم غير المتزامنة الأساسية، سيشير الحدث المُعاد إلى العملية التي اكتملت، وسيشير fid إلى واصف النسيج المرتبط بالحدث. لتسجيل الذاكرة، سيكون هذا حدث FI_MR_COMPLETE و fid_mr. سيُشير حل العنوان إلى حدث FI_AV_COMPLETE و fid_av. ستُبلغ عمليات الانضمام إلى البث المتعدد عن FI_JOIN_COMPLETE و fid_mc. سيتم تعيين حقل context إلى السياق المحدد كجزء من العملية، إن كان متاحًا، وإلا فسيتم ربط السياق بواصف النسيج. سيتم تعيين حقل data كما هو موضح في صفحة الدليل لنوع الكائن المقابل (على سبيل المثال، راجع fi_av(3) لوصف كيفية اكتمال إدراجات متجه العنوان غير المتزامنة).

إشعار الاتصال
إشعارات الاتصال هي إشعارات إدارة الاتصال المستخدمة لإعداد أو تفكيك الاتصالات بين نقاط النهاية. هناك ثلاثة أحداث إشعار اتصال: FI_CONNREQ و FI_CONNECTED و FI_SHUTDOWN. يتم الإبلاغ عن إشعارات الاتصال باستخدام struct fi_eq_cm_entry:
struct fi_eq_cm_entry {
    fid_t            fid;        /* fid associated with request */
    struct fi_info  *info;       /* endpoint information */
    uint8_t         data[];     /* app connection data */
};

يشير حدث طلب الاتصال (FI_CONNREQ) إلى أن نقطة نهاية بعيدة ترغب في إنشاء اتصال جديد بنقطة نهاية مستمعة، أو سلبية. fid هو نقطة النهاية السلبية. المعلومات المتعلقة بقدرات وسمات نقطة النهاية النشطة المطلوبة متاحة من حقل info. التطبيق مسؤول عن تحرير هذا الهيكل عن طريق استدعاء fi_freeinfo عندما لا يكون هناك حاجة إليه بعد الآن. سيُشير حقل fi_info connreq إلى طلب الاتصال المرتبط بهذا الحدث. لقبول اتصال، يجب أولاً إنشاء نقطة نهاية عن طريق تمرير هيكل fi_info يشير إلى حقل connreq هذا إلى fi_endpoint(). ثم يتم تمرير نقطة النهاية هذه إلى fi_accept() لإكمال قبول محاولة الاتصال. يتم إنشاء نقطة النهاية بأسهل طريقة عن طريق تمرير fi_info المُعاد كجزء من حدث CM إلى fi_endpoint(). إذا كان الاتصال سيُرفض، يتم تمرير connreq إلى fi_reject().

أي بيانات تطبيق يتم تبادلها كجزء من طلب الاتصال تُوضع بعد هيكل fi_eq_cm_entry. تعتمد كمية البيانات المتاحة على التطبيق وتقتصر على مساحة المخزن المؤقت التي يوفرها التطبيق عند استدعاء fi_eq_read. يمكن حساب كمية البيانات المُعادة باستخدام القيمة المُعادة لـ fi_eq_read. لاحظ أن كمية البيانات المُعادة محدودة ببروتوكول الاتصال الأساسي، وقد يتضمن طول أي بيانات مُعادة حشوًا بروتوكوليًا. نتيجة لذلك، قد يكون الطول المُعاد أكبر من ذلك المحدد بواسطة النظير المتصل.

إذا تم قبول طلب اتصال، فسيتم توليد حدث FI_CONNECTED على جانبي الاتصال. الجانب النشط – الذي استدعى fi_connect() – قد يتلقى بيانات المستخدم كجزء من حدث FI_CONNECTED. يتم تمرير بيانات المستخدم إلى مدير الاتصال على الجانب السلبي من خلال استدعاء fi_accept. لا يتم توفير بيانات المستخدم مع حدث FI_CONNECTED على جانب الاستماع من الاتصال.

يتم الإشعار بأن نظيرًا بعيدًا قد قطع الاتصال من نقطة نهاية نشطة من خلال حدث FI_SHUTDOWN. يستخدم إشعار الإيقاف struct fi_eq_cm_entry كما هو معلن أعلاه. يشير حقل fid لإشعار الإيقاف إلى fid_ep الخاص بنقطة النهاية النشطة.

إشعار الخطأ غير المتزامن
تُستخدم الأخطاء غير المتزامنة للإبلاغ عن مشكلات في موارد النسيج. قد تكون الأخطاء المُبلغ عنها قاتلة أو عابرة، بناءً على الخطأ، وتؤدي إلى تعطيل المورد. ستفشل الموارد المعطلة في العمليات المقدمة إليها حتى يتم إعادة تمكينها صراحةً بواسطة التطبيق.

قد يتم الإبلاغ عن الأخطاء غير المتزامنة لقوائم الإكمال و نقاط النهاية من جميع الأنواع. يمكن أن تنتج أخطاء CQ عندما تكون إدارة الموارد قد تم تعطيلها، واكتشف المزود تجاوزًا في قائمة الانتظار. قد تكون أخطاء نقطة النهاية نتيجة لعدة إجراءات، ولكنها غالبًا ما ترتبط بـ عملية فاشلة. قد تفشل العمليات بسبب تجاوزات المخزن المؤقت، أو أذونات غير صالحة، أو مفاتيح وصول ذاكرة غير صحيحة، أو فشل توجيه الشبكة، أو مشكلات إمكانية الوصول إلى الشبكة، إلخ.

يتم الإبلاغ عن الأخطاء غير المتزامنة باستخدام struct fi_eq_err_entry، كما هو محدد أدناه. يتم توفير واصف النسيج (fid) المرتبط بالخطأ كجزء من بيانات الخطأ. يتوفر أيضًا رمز خطأ لتحديد سبب الخطأ.

fi_eq_sread

استدعاء fi_eq_sread هو المكافئ الحاجز (أو المتزامن) لـ fi_eq_read. يتصرف بشكل مشابه للاستدعاء غير الحاجز، باستثناء أن الاستدعاءات لن تعود حتى يتم إما قراءة حدث من EQ أو حدوث خطأ أو مهلة. تحديد مهلة سالبة يعني مهلة لا نهائية.

ستعود الخيوط المحجوبة في هذه الدالة إلى المستدعي إذا تمت الإشارة إليها من مصدر خارجي. هذا صحيح حتى لو لم تحدث المهلة أو تم تحديدها على أنها لا نهائية.

من غير الصالح للتطبيقات استدعاء هذه الدالة إذا تم تكوين EQ بكائن انتظار FI_WAIT_NONE أو FI_WAIT_SET.

fi_eq_readerr

تسترد دالة قراءة الخطأ، fi_eq_readerr، المعلومات المتعلقة بأي عملية غير متزامنة اكتملت بخطأ غير متوقع. fi_eq_readerr هو استدعاء غير حاجز، يعود فورًا سواء تم العثور على إكمال خطأ أم لا.

تم تحسين EQs للإبلاغ عن العمليات التي اكتملت بنجاح. يتم الإبلاغ عن العمليات التي تفشل `خارج النطاق'. يتم استرداد هذه العمليات باستخدام دالة fi_eq_readerr. عندما يتم إدراج عملية تكتمل بخطأ غير متوقع في EQ، يتم وضعها في قائمة انتظار أخطاء مؤقتة. تؤدي محاولة القراءة من EQ أثناء وجود عنصر في قائمة انتظار الأخطاء إلى فشل FI_EAVAIL. يمكن للتطبيقات استخدام رمز الإرجاع هذا لتحديد متى يتم استدعاء fi_eq_readerr.

يتم الإبلاغ عن معلومات الخطأ للمستخدم من خلال struct fi_eq_err_entry. يتم تعريف تنسيق هذا الهيكل أدناه.

struct fi_eq_err_entry {
    fid_t            fid;        /* fid associated with error */
    void            *context;    /* operation context */
    uint64_t         data;       /* completion-specific data */
    int              err;        /* positive error code */
    int              prov_errno; /* provider error code */
    void            *err_data;   /* additional error data */
    size_t           err_data_size; /* size of err_data */
};

سيشير fid إلى واصف النسيج المرتبط بـ الحدث. لتسجيل الذاكرة، سيكون هذا هو fid_mr، وسيشير حل العنوان إلى fid_av، وستشير أحداث CM إلى fid_ep. سيتم تعيين حقل context إلى السياق المحدد كجزء من العملية.

سيتم تعيين حقل data كما هو موضح في صفحة الدليل لنوع الكائن المقابل (على سبيل المثال، راجع fi_av(3) لوصف كيفية اكتمال إدراجات متجه العنوان غير المتزامنة).

يتم توفير السبب العام للخطأ من خلال حقل err. قد تكون معلومات الخطأ الخاصة بالمزود أو التشغيل متاحة أيضًا من خلال حقلي prov_errno و err_data. يمكن للمستخدمين استدعاء fi_eq_strerror لتحويل معلومات الخطأ الخاصة بالمزود إلى سلسلة قابلة للطباعة لأغراض التصحيح.

عند الإدخال، يشير err_data_size إلى حجم مخزن err_data المؤقت بالبايت. عند الإخراج، سيتم تعيين err_data_size إلى عدد البايتات المنسوخة إلى مخزن err_data المؤقت. تُستخدم معلومات err_data عادةً مع fi_eq_strerror لتوفير تفاصيل حول نوع الخطأ الذي حدث.

لأغراض التوافق، إذا كان err_data_size يساوي 0 عند الإدخال، أو تم فتح النسيج بإصدار < 1.5، فسيتم تعيين err_data إلى مخزن بيانات مؤقت مملوك للمزود. سيبقى محتوى المخزن المؤقت صالحًا حتى استدعاء قراءة لاحق ضد EQ. يجب على التطبيقات تسلسل الوصول إلى EQ عند معالجة الأخطاء لضمان عدم تغير المخزن المؤقت المشار إليه بواسطة err_data.
