gitattributes(5)

الحزمة: git

التراخيص: GPL-2.0-only

اختياريًا، لتحويلها إلى CRLF عند سحب الملفات.

إذا كنت ترغب ببساطة في الحصول على نهايات أسطر CRLF في دليل العمل الخاص بك بغض النظر عن المستودع الذي تعمل معه، يمكنك تعيين متغير التكوين "core.autocrlf" دون استخدام أي سمات.

[core]
        autocrlf = true

هذا لا يجبر تطبيع الملفات النصية، ولكنه يضمن تطبيع نهايات أسطر الملفات النصية التي تقدمها إلى المستودع إلى LF عند إضافتها، وأن الملفات التي تم تطبيعها بالفعل في المستودع تظل مطبعة.

إذا كنت ترغب في التأكد من تطبيع نهايات أسطر الملفات النصية التي يقدمها أي مساهم إلى المستودع، يمكنك تعيين السمة text إلى "auto" لجميع الملفات .

*       text=auto

تسمح السمات بالتحكم الدقيق في كيفية تحويل نهايات الأسطر. إليك مثال سيؤدي إلى قيام Git بتطبيع ملفات .txt و .vcproj و .sh، وضمان أن ملفات .vcproj تحتوي على CRLF وملفات .sh تحتوي على LF في دليل العمل، ومنع ملفات .jpg من التطبيع بغض النظر عن محتواها.

*               text=auto
*.txt           text
*.vcproj        text eol=crlf
*.sh            text eol=lf
*.jpg           -text

ملاحظة

عند تمكين تحويل text=auto في مشروع متعدد المنصات باستخدام push و pull إلى مستودع مركزي، يجب تطبيع الملفات النصية التي تحتوي على CRLFs.

من دليل عمل نظيف:

$ echo "* text=auto" >.gitattributes
$ git add --renormalize .
$ git status        # إظهار الملفات التي سيتم تطبيعها
$ git commit -m "Introduce end-of-line normalization"

إذا ظهرت أي ملفات لا يجب تطبيعها في git status، قم بإلغاء تعيين السمة text الخاصة بها قبل تشغيل git add -u.

manual.pdf      -text

على العكس من ذلك، يمكن تمكين التطبيع يدويًا للملفات النصية التي لا يكتشفها Git.

weirdchars.txt  text

إذا تم تعيين core.safecrlf إلى "true" أو "warn"، فإن Git يتحقق مما إذا كان التحويل قابلاً للعكس بالنسبة للإعداد الحالي لـ core.autocrlf. بالنسبة لـ "true"، يرفض Git التحويلات غير القابلة للعكس؛ بالنسبة لـ "warn"، يطبع Git تحذيرًا ولكنه يقبل التحويل غير القابل للعكس. تمنع عوامل السلامة مثل هذا التحويل من الملفات في شجرة العمل، ولكن هناك بعض الاستثناءات. حتى لو...

•git add نفسه لا يلمس الملفات في شجرة العمل، فإن سحبها لاحقًا سيلمسها، لذلك تعمل عوامل السلامة؛
•git apply لتحديث ملف نصي برقعة يلمس الملفات في شجرة العمل، ولكن العملية تتعلق بالملفات النصية وتحويل CRLF يتعلق بإصلاح تناقضات نهاية الأسطر، لذلك لا تعمل السلامة؛
•git diff نفسه لا يلمس الملفات في شجرة العمل، غالبًا ما يتم تشغيله لفحص التغييرات التي تنوي git add لاحقًا. لالتقاط المشاكل المحتملة مبكرًا، تعمل عوامل السلامة.

working-tree-encoding

يتعرف Git على الملفات المشفرة بـ ASCII أو أحد مجموعاتها الفائقة (مثل UTF-8، ISO-8859-1، ...). يتم تفسير الملفات المشفرة بتشفيرات أخرى معينة (مثل UTF-16) على أنها ثنائية، وبالتالي فإن أدوات معالجة النصوص المضمنة في Git (مثل git diff) وكذلك معظم واجهات الويب الأمامية لـ Git لا تعرض محتويات هذه الملفات افتراضيًا.

في هذه الحالات، يمكنك إخبار Git بتشفير ملف في دليل العمل باستخدام السمة working-tree-encoding. إذا تمت إضافة ملف بهذه السمة إلى Git، يقوم Git بإعادة تشفير المحتوى من التشفير المحدد إلى UTF-8. أخيرًا، يقوم Git بتخزين المحتوى المشفر بـ UTF-8 في هيكل البيانات الداخلي الخاص به (المسمى "الفهرس"). عند سحب الملف، يتم إعادة تشفير المحتوى مرة أخرى إلى التشفير المحدد.

يرجى ملاحظة أن استخدام السمة working-tree-encoding قد يكون له عدد من المشاكل:

•تطبيقات Git البديلة (مثل JGit أو libgit2) وإصدارات Git الأقدم (حتى مارس 2018) لا تدعم السمة working-tree-encoding. إذا قررت استخدام السمة working-tree-encoding في المستودع الخاص بك، فمن المستحسن بشدة التأكد من أن جميع العملاء الذين يتعاملون مع المستودع يدعمونها.

على سبيل المثال، ملفات موارد Microsoft Visual Studio (*.rc) أو ملفات نصوص PowerShell (*.ps1) يتم تشفيرها أحيانًا بـ UTF-16. إذا قمت بتعريف *.ps1 كملفات بتشفير UTF-16 وقمت بإضافة foo.ps1 بعميل Git تم تمكين working-tree-encoding له، فسيتم تخزين foo.ps1 بتشفير UTF-8 داخليًا. سيقوم عميل بدون دعم working-tree-encoding بسحب foo.ps1 كملف مشفر بـ UTF-8. سيؤدي هذا عادةً إلى مشاكل للمستخدمين لهذا الملف.

إذا قام عميل Git لا يدعم السمة working-tree-encoding بإضافة ملف جديد bar.ps1، فسيتم تخزين bar.ps1 "كما هو" داخليًا (في هذا المثال ربما بتشفير UTF-16). سيقوم عميل يدعم working-tree-encoding بتفسير المحتويات الداخلية على أنها UTF-8 ومحاولة تحويلها إلى UTF-16 عند السحب. ستفشل هذه العملية وتسبب خطأ.

•قد يتسبب إعادة تشفير المحتوى إلى تشفيرات غير UTF في حدوث أخطاء لأن التحويل قد لا يكون آمنًا ذهابًا وإيابًا مع UTF-8. إذا كنت تشك في أن تشفيرك ليس آمنًا ذهابًا وإيابًا، فأضفه إلى core.checkRoundtripEncoding لجعل Git يتحقق من تشفير الرحلة ذهابًا وإيابًا (انظر git-config(1)). معروف أن SHIFT-JIS (مجموعة الأحرف اليابانية) لديها مشاكل في الرحلة ذهابًا وإيابًا مع UTF-8 ويتم التحقق منها افتراضيًا.
•تتطلب إعادة تشفير المحتوى موارد قد تبطئ بعض عمليات Git (مثل git checkout أو git add).

استخدم السمة working-tree-encoding فقط إذا كنت غير قادر على تخزين ملف بتشفير UTF-8 وتريد أن يتمكن Git من معالجة المحتوى كنص.

على سبيل المثال، استخدم السمات التالية إذا كانت ملفات *.ps1 الخاصة بك مشفرة بـ UTF-16 مع علامة ترتيب البايت (BOM) وتريد أن يقوم Git بتحويل تلقائي لنهاية الأسطر بناءً على نظامك.

*.ps1           text working-tree-encoding=UTF-16

استخدم السمات التالية إذا كانت ملفات *.ps1 الخاصة بك مشفرة بـ UTF-16 little endian بدون BOM وتريد أن يستخدم Git نهايات أسطر Windows في دليل العمل (استخدم UTF-16LE-BOM بدلاً من UTF-16LE إذا كنت تريد UTF-16 little endian مع BOM). يرجى ملاحظة أنه يوصى بشدة بتحديد نهايات الأسطر بشكل صريح باستخدام eol إذا تم استخدام السمة working-tree-encoding لتجنب الغموض.

*.ps1           text working-tree-encoding=UTF-16LE eol=crlf

يمكنك الحصول على قائمة بجميع التشفيرات المتاحة على نظامك باستخدام الأمر التالي:

iconv --list

إذا كنت لا تعرف تشفير الملف، فيمكنك استخدام الأمر file للتخمين بشأن التشفير:

file foo.ps1

ident

عندما يتم تعيين السمة ident لمسار، يقوم Git باستبدال $Id$ في كائن blob بـ $Id:، متبوعًا باسم كائن blob السداسي عشري المكون من 40 حرفًا، متبوعًا بعلامة الدولار $ عند السحب. أي تسلسل بايت يبدأ بـ $Id: وينتهي بـ $ في ملف شجرة العمل يتم استبداله بـ $Id$ عند تسجيل الدخول.

filter

يمكن تعيين سمة filter إلى قيمة سلسلة نصية تحدد برنامج تصفية في التكوين.

يتكون برنامج التصفية من أمر clean وأمر smudge، يمكن ترك أي منهما غير محدد. عند السحب، عندما يتم تحديد أمر smudge، يتم إدخال كائن blob إلى مدخلاته القياسية، ويتم استخدام مخرجاته القياسية لتحديث ملف شجرة العمل. وبالمثل، يتم استخدام أمر clean لتحويل محتويات ملف شجرة العمل عند تسجيل الدخول. افتراضيًا، تعالج هذه الأوامر blob واحدًا فقط وتنتهي. إذا تم استخدام تصفية process طويلة الأمد بدلاً من عوامل تصفية clean و/أو smudge، فيمكن لـ Git معالجة جميع الكائنات الثنائية باستخدام استدعاء واحد لأمر التصفية طوال مدة أمر Git واحد، على سبيل المثال git add --all. إذا تم تكوين تصفية process طويلة الأمد، فإنها تتفوق دائمًا على تصفية blob واحدة تم تكوينها. انظر القسم أدناه لوصف البروتوكول المستخدم للتواصل مع عامل process.

أحد استخدامات تصفية المحتوى هو معالجة المحتوى إلى شكل أكثر ملاءمة للنظام الأساسي ونظام الملفات والمستخدم. لهذا الوضع من التشغيل، العبارة الرئيسية هنا هي "أكثر ملاءمة" وليس "تحويل شيء غير قابل للاستخدام إلى قابل للاستخدام". بمعنى آخر، القصد هو أنه إذا قام شخص ما بإلغاء تعيين تعريف برنامج التصفية، أو لم يكن لديه برنامج التصفية المناسب، فيجب أن يظل المشروع قابلاً للاستخدام.

استخدام آخر لتصفية المحتوى هو تخزين المحتوى الذي لا يمكن استخدامه مباشرة في المستودع (على سبيل المثال، UUID يشير إلى المحتوى الحقيقي المخزن خارج Git، أو محتوى مشفر) وتحويله إلى شكل قابل للاستخدام عند السحب (على سبيل المثال، تنزيل المحتوى الخارجي، أو فك تشفير المحتوى المشفر).

هذان المرشحان يتصرفان بشكل مختلف، وافتراضيًا، يعتبر المرشح هو الأول، وهو معالجة المحتوى إلى شكل أكثر ملاءمة. عدم وجود تعريف لبرنامج التصفية في التكوين، أو برنامج تصفية يخرج بحالة غير صفرية، ليس خطأ ولكنه يجعل المرشح لا يقوم بأي شيء.

يمكنك الإعلان عن أن مرشحًا يحول المحتوى الذي هو غير قابل للاستخدام بحد ذاته إلى محتوى قابل للاستخدام عن طريق تعيين متغير التكوين filter.<driver>.required إلى true.

ملاحظة: كلما تم تغيير المرشح النظيف، يجب إعادة تطبيع المستودع: $ git add --renormalize .

على سبيل المثال، في .gitattributes، ستقوم بتعيين سمة filter للمسارات.

*.c     filter=indent

ثم ستقوم بتعريف تكوين "filter.indent.clean" و "filter.indent.smudge" في ملف .git/config الخاص بك لتحديد زوج من الأوامر لتعديل محتويات برامج C عند تسجيل ملفات المصدر ("clean" يتم تشغيله) وسحبها (لا يتم إجراء تغيير لأن الأمر هو "cat").

[filter "indent"]
        clean = indent
        smudge = cat

للحصول على أفضل النتائج، لا ينبغي لـ clean تعديل مخرجاته أكثر من اللازم إذا تم تشغيله مرتين ("clean→clean" يجب أن

'clean' تساوي "clean"), والعديد من أوامر smudge لا ينبغي أن تغير مخرجات clean ("smudge→smudge→clean" يجب أن تكون مكافئة لـ "clean"). انظر القسم حول الدمج أدناه.

الفلتر "indent" يتصرف بشكل جيد في هذا الصدد: إنه لن يعدل المدخلات التي تم تنسيقها بالفعل بشكل صحيح. في هذه الحالة، يعني عدم وجود فلتر smudge أن فلتر clean *يجب* أن يقبل مخرجاته الخاصة دون تعديلها.

إذا كان يجب أن ينجح فلتر ما لجعل المحتويات المخزنة قابلة للاستخدام، يمكنك الإعلان عن أن الفلتر *مطلوب*، في الإعدادات:

[filter "crypt"]
        clean = openssl enc ...
        smudge = openssl enc -d ...
        required

يتم استبدال التسلسل "%f" في سطر أوامر الفلتر باسم الملف الذي يعمل عليه الفلتر. قد يستخدم الفلتر هذا في استبدال الكلمات المفتاحية. على سبيل المثال:

[filter "p4"]
        clean = git-p4-filter --clean %f
        smudge = git-p4-filter --smudge %f

لاحظ أن "%f" هو اسم المسار الذي يتم العمل عليه. اعتمادًا على الإصدار الذي يتم تصفيته، قد لا يكون الملف المقابل على القرص موجودًا، أو قد يحتوي على محتويات مختلفة. لذلك، يجب ألا تحاول أوامر smudge و clean الوصول إلى الملف على القرص، بل يجب أن تعمل كمرشحات للمحتوى المقدم لها عبر الإدخال القياسي.

عملية فلتر طويلة الأمد

إذا تم تعريف أمر الفلتر (قيمة سلسلة نصية) عبر filter.<driver>.process، فيمكن لـ Git معالجة جميع الكائنات الثنائية (blobs) باستدعاء فلتر واحد طوال عمر أمر Git واحد. يتم تحقيق ذلك باستخدام بروتوكول العملية طويلة الأمد (الموصوف في Documentation/technical/long-running-process-protocol.adoc).

عندما يصادف Git الملف الأول الذي يحتاج إلى تنظيف أو تشويش، يبدأ الفلتر ويجري المصافحة. في المصافحة، تكون رسالة الترحيب التي يرسلها Git هي "git-filter-client"، ويتم دعم الإصدار 2 فقط، والقدرات المدعومة هي "clean" و "smudge" و "delay".

بعد ذلك، يرسل Git قائمة بأزواج "key=value" تنتهي بحزمة flush. ستحتوي القائمة على أمر الفلتر على الأقل (بناءً على القدرات المدعومة) ومسار الملف المراد تصفيته نسبة إلى جذر المستودع. مباشرة بعد حزمة flush، يرسل Git المحتوى مقسمًا إلى صفر أو أكثر من حزم pkt-line وحزمة flush لإنهاء المحتوى. يرجى ملاحظة أن الفلتر يجب ألا يرسل أي رد قبل استلامه للمحتوى وحزمة flush النهائية. لاحظ أيضًا أن "value" لزوج "key=value" يمكن أن يحتوي على الحرف "=" بينما لن يحتوي المفتاح أبدًا على هذا الحرف.

packet:          git> command=smudge
packet:          git> pathname=path/testfile.dat
packet:          git> 0000
packet:          git> CONTENT
packet:          git> 0000

من المتوقع أن يستجيب الفلتر بقائمة من أزواج "key=value" تنتهي بحزمة flush. إذا لم يواجه الفلتر مشاكل، فيجب أن تحتوي القائمة على حالة "success". مباشرة بعد هذه الحزم، من المتوقع أن يرسل الفلتر المحتوى في صفر أو أكثر من حزم pkt-line وحزمة flush في النهاية. أخيرًا، من المتوقع قائمة ثانية من أزواج "key=value" تنتهي بحزمة flush. يمكن للفلتر تغيير الحالة في القائمة الثانية أو الاحتفاظ بالحالة كما هي بقائمة فارغة. يرجى ملاحظة أنه يجب إنهاء القائمة الفارغة بحزمة flush بغض النظر.

packet:          git< status=success
packet:          git< 0000
packet:          git< SMUDGED_CONTENT
packet:          git< 0000
packet:          git< 0000  # empty list, keep "status=success" unchanged!

إذا كان محتوى النتيجة فارغًا، فمن المتوقع أن يستجيب الفلتر بحالة "success" وحزمة flush للإشارة إلى المحتوى الفارغ.

packet:          git< status=success
packet:          git< 0000
packet:          git< 0000  # empty content!
packet:          git< 0000  # empty list, keep "status=success" unchanged!

في حالة عدم تمكن الفلتر من معالجة المحتوى أو عدم رغبته في ذلك، فمن المتوقع أن يستجيب بحالة "error".

packet:          git< status=error
packet:          git< 0000

إذا واجه الفلتر خطأ أثناء المعالجة، فيمكنه إرسال حالة "error" بعد إرسال المحتوى (جزئيًا أو كليًا).

packet:          git< status=success
packet:          git< 0000
packet:          git< HALF_WRITTEN_ERRONEOUS_CONTENT
packet:          git< 0000
packet:          git< status=error
packet:          git< 0000

في حالة عدم تمكن الفلتر من معالجة المحتوى أو عدم رغبته في ذلك، وكذلك أي محتوى مستقبلي طوال عمر عملية Git، فمن المتوقع أن يستجيب بحالة "abort" في أي نقطة في البروتوكول.

packet:          git< status=abort
packet:          git< 0000

لا يوقف Git عملية الفلتر أو يعيد تشغيلها في حالة تعيين حالة "error"/"abort". ومع ذلك، يقوم Git بتعيين رمز الخروج الخاص به وفقًا لعلامة filter.<driver>.required، محاكيًا سلوك آلية filter.<driver>.clean / filter.<driver>.smudge.

إذا مات الفلتر أثناء الاتصال أو لم يلتزم بالبروتوكول، فسيقوم Git بإيقاف عملية الفلتر وإعادة تشغيلها مع الملف التالي الذي يحتاج إلى معالجة. اعتمادًا على علامة filter.<driver>.required، سيفسر Git ذلك على أنه خطأ.

تأخير

إذا كان الفلتر يدعم إمكانية "delay"، فيمكن لـ Git إرسال العلامة "can-delay" بعد أمر الفلتر والمسار. تشير هذه العلامة إلى أن الفلتر يمكنه تأجيل تصفية الكائن الثنائي الحالي (على سبيل المثال، للتعويض عن تأخيرات الشبكة) بالاستجابة بدون محتوى ولكن بحالة "delayed" وحزمة flush.

packet:          git> command=smudge
packet:          git> pathname=path/testfile.dat
packet:          git> can-delay=1
packet:          git> 0000
packet:          git> CONTENT
packet:          git> 0000
packet:          git< status=delayed
packet:          git< 0000

إذا كان الفلتر يدعم إمكانية "delay"، فيجب أن يدعم أمر "list_available_blobs". إذا أرسل Git هذا الأمر، فمن المتوقع أن يعيد الفلتر قائمة بالمسارات التي تمثل الكائنات الثنائية التي تم تأخيرها سابقًا وهي متاحة الآن. يجب أن تنتهي القائمة بحزمة flush متبوعة بحالة "success" تنتهي أيضًا بحزمة flush. إذا لم تكن هناك كائنات ثنائية للمسارات المؤجلة متاحة بعد، فمن المتوقع أن يحظر الفلتر الاستجابة حتى تصبح كتلة واحدة متاحة على الأقل. يمكن للفلتر إخبار Git بأنه لم يعد لديه كائنات ثنائية مؤجلة عن طريق إرسال قائمة فارغة. بمجرد أن يستجيب الفلتر بقائمة فارغة، سيتوقف Git عن السؤال. تعتبر جميع الكائنات الثنائية التي لم يستلمها Git حتى هذه النقطة مفقودة وستؤدي إلى خطأ.

packet:          git> command=list_available_blobs
packet:          git> 0000
packet:          git< pathname=path/testfile.dat
packet:          git< pathname=path/otherfile.dat
packet:          git< 0000
packet:          git< status=success
packet:          git< 0000

بعد أن استلم Git المسارات، سيطلب الكائنات الثنائية المقابلة مرة أخرى. تحتوي هذه الطلبات على مسار وقسم محتوى فارغ. من المتوقع أن يستجيب الفلتر بالمحتوى المشوّش بالطريقة المعتادة كما هو موضح أعلاه.

packet:          git> command=smudge
packet:          git> pathname=path/testfile.dat
packet:          git> 0000
packet:          git> 0000  # empty content!
packet:          git< status=success
packet:          git< 0000
packet:          git< SMUDGED_CONTENT
packet:          git< 0000
packet:          git< 0000  # empty list, keep "status=success" unchanged!

مثال

يمكن العثور على تنفيذ توضيحي لعملية فلتر طويلة الأمد في contrib/long-running-filter/example.pl الموجود في مستودع Git الأساسي. إذا قمت بتطوير عملية فلتر طويلة الأمد خاصة بك، فإن متغير البيئة GIT_TRACE_PACKET يمكن أن يكون مفيدًا جدًا لتصحيح الأخطاء (انظر git(1)).

يرجى ملاحظة أنه لا يمكنك استخدام أمر filter.<driver>.clean أو filter.<driver>.smudge موجود مع filter.<driver>.process لأن الأمرين السابقين يستخدمان بروتوكول اتصال بين العمليات مختلفًا عن البروتوكول الأخير.

التفاعل بين سمات الرفع/التنزيل

في مسار عمل الرفع (check-in)، يتم تحويل ملف مساحة العمل أولاً باستخدام مشغل filter (إذا تم تحديده وتم تعريف المشغل المقابل)، ثم تتم معالجة النتيجة باستخدام ident (إذا تم تحديده)، ثم أخيرًا باستخدام text (مرة أخرى، إذا تم تحديده وكان منطبقًا).

في مسار عمل التنزيل (check-out)، يتم تحويل محتوى الكائن الثنائي أولاً باستخدام text، ثم ident، ثم يتم تغذيته إلى filter.

دمج فروع بسمات رفع/تنزيل مختلفة

إذا قمت بإضافة سمات إلى ملف تتسبب في تغيير تنسيق المستودع القانوني لهذا الملف، مثل إضافة فلتر clean/smudge أو سمات text/eol/ident، فإن دمج أي شيء حيث السمة غير موجودة سيؤدي عادةً إلى تعارضات في الدمج.

لمنع تعارضات الدمج غير الضرورية هذه، يمكن إخبار Git بتشغيل عملية تنزيل وتحميل افتراضية لجميع المراحل الثلاث لكل ملف يحتاج إلى دمج محتوى ثلاثي الاتجاهات، عن طريق تعيين متغير الإعدادات merge.renormalize. هذا يمنع التغييرات الناتجة عن تحويل الرفع من التسبب في تعارضات دمج زائفة عندما يتم دمج ملف محول مع ملف غير محول.

طالما أن "smudge→clean" ينتج نفس المخرجات مثل "clean" حتى على الملفات التي تم تشويشها بالفعل، فإن هذه الاستراتيجية ستقوم تلقائيًا بحل جميع التعارضات المتعلقة بالفلتر. قد تتسبب المرشحات التي لا تتصرف بهذه الطريقة في تعارضات دمج إضافية يجب حلها يدويًا.
