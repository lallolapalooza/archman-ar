git-log(1)

الحزمة: git

التراخيص: GPL-2.0-only

لاحظ أنه نظرًا لأن M يمكن الوصول إليه من R، تم تبسيط الحافة من N إلى M. ومع ذلك، لا يزال N يظهر في السجل باعتباره التزامًا مهمًا لأنه "سحب" التغيير R إلى الفرع الرئيسي.

يتيح الخيار --simplify-by-decoration عرض الصورة الكبيرة للتوبولوجيا فقط للسجل، عن طريق حذف الالتزامات التي لا تشير إليها العلامات. يتم تمييز الالتزامات على أنها !TREESAME (بمعنى آخر، يتم الاحتفاظ بها بعد قواعد تبسيط السجل الموضحة أعلاه) إذا (1) كانت تشير إليها العلامات، أو (2) تغيرت محتويات المسارات المعطاة في سطر الأوامر. يتم تمييز جميع الالتزامات الأخرى على أنها TREESAME (قابلة للتبسيط).

ترتيب الالتزام

بشكل افتراضي، يتم عرض الالتزامات بترتيب زمني عكسي.

--date-order

لا تعرض الأصول قبل عرض جميع فروعها، ولكن بخلاف ذلك، اعرض الالتزامات بترتيب طابع وقت الالتزام.

--author-date-order

لا تعرض الأصول قبل عرض جميع فروعها، ولكن بخلاف ذلك، اعرض الالتزامات بترتيب طابع وقت المؤلف.

--topo-order

لا تعرض الأصول قبل عرض جميع فروعها، وتجنب عرض الالتزامات على خطوط سجل متعددة مختلطة.

على سبيل المثال، في سجل التزام مثل هذا:

    ---1----2----4----7
        \              \
         3----5----6----8---

حيث تمثل الأرقام ترتيب أوقات الالتزام، يعرض git rev-list وما شابه مع --date-order الالتزامات بترتيب طابع الوقت: 8 7 6 5 4 3 2 1.

مع --topo-order، سيعرضون 8 6 5 3 7 4 2 1 (أو 8 7 4 2 6 5 3 1)؛ يتم عرض بعض الالتزامات القديمة قبل الالتزامات الأحدث لتجنب عرض الالتزامات من مساري تطوير متوازيين مختلطين.

--reverse

اعرض الالتزامات المختارة للعرض (انظر قسم تحديد الالتزامات أعلاه) بترتيب عكسي. لا يمكن دمجه مع --walk-reflogs.

اجتياز الكائنات

تستهدف هذه الخيارات في الغالب تجميع مستودعات Git.

--no-walk[=(sorted|unsorted)]

اعرض الالتزامات المعطاة فقط، ولكن لا تجتز أصولها. ليس لهذا أي تأثير إذا تم تحديد نطاق. إذا تم إعطاء الوسيط unsorted، يتم عرض الالتزامات بالترتيب الذي تم تقديمه به في سطر الأوامر. بخلاف ذلك (إذا تم إعطاء sorted أو لم يتم إعطاء أي وسيط)، يتم عرض الالتزامات بترتيب زمني عكسي حسب وقت الالتزام. لا يمكن دمجه مع --graph.

--do-walk

تجاوز --no-walk سابقًا.

تنسيق الالتزام

--pretty[=<format>], --format=<format>

قم بطباعة محتويات سجلات الالتزام بشكل جميل بتنسيق معين، حيث يمكن أن يكون <format> أحد الخيارات التالية: oneline، short، medium، full، fuller، reference، email، raw، format:<string> و tformat:<string>. عندما لا يكون <format> أحد الخيارات المذكورة أعلاه، ويحتوي على %<placeholder> فيه، فإنه يتصرف كما لو تم إعطاء --pretty=tformat:<format>.

راجع قسم "تنسيقات جميلة" لمزيد من التفاصيل حول كل تنسيق. عند حذف جزء =<format>، فإنه يستخدم الافتراضي medium.


ملاحظة
يمكنك تحديد التنسيق الجميل الافتراضي في إعدادات المستودع (راجع git-config(1)).

--abbrev-commit

بدلاً من عرض اسم كائن الالتزام السداسي العشري الكامل المكون من 40 بايت، اعرض بادئة تسمي الكائن بشكل فريد. يمكن استخدام الخيار --abbrev=<n> (الذي يعدل أيضًا إخراج الفرق، إذا تم عرضه) لتحديد الحد الأدنى لطول البادئة.

يجب أن يجعل هذا --pretty=oneline أكثر قابلية للقراءة بكثير للأشخاص الذين يستخدمون أطراف 80 عمودًا.

--no-abbrev-commit

اعرض اسم كائن الالتزام السداسي العشري الكامل المكون من 40 بايت. هذا يلغي --abbrev-commit، سواء كان صريحًا أو ضمنيًا بواسطة خيارات أخرى مثل --oneline. كما أنه يتجاوز المتغير log.abbrevCommit.

--oneline

هذه اختصار لـ --pretty=oneline --abbrev-commit مستخدمين معًا.

--encoding=<encoding>

تسجل كائنات الالتزام ترميز الأحرف المستخدم لرسالة السجل في رأس الترميز الخاص بها؛ يمكن استخدام هذا الخيار لإخبار الأمر بإعادة ترميز رسالة سجل الالتزام بالترميز المفضل للمستخدم. بالنسبة للأوامر غير الأساسية، يكون الافتراضي هو UTF-8. لاحظ أنه إذا ادعى كائن ما أنه مرمّز بـ X وكنا نخرج بتنسيق X، فسنقوم بإخراج الكائن كما هو؛ هذا يعني أنه قد يتم نسخ التسلسلات غير الصالحة في الالتزام الأصلي إلى الإخراج. وبالمثل، إذا فشل iconv(3) في تحويل الالتزام، فسنقوم بإخراج الكائن الأصلي بهدوء كما هو.

--expand-tabs=<n>, --expand-tabs, --no-expand-tabs

قم بتوسيع علامات الجدولة (استبدل كل علامة جدولة بعدد كافٍ من المسافات لملء العمود التالي للعرض الذي يكون مضاعفًا لـ <n>) في رسالة السجل قبل عرضها في الإخراج. --expand-tabs هو اختصار لـ --expand-tabs=8، و --no-expand-tabs هو اختصار لـ --expand-tabs=0، والذي يعطل توسيع علامات الجدولة.

بشكل افتراضي، يتم توسيع علامات الجدولة في التنسيقات الجميلة التي تعمل على تحديد مسافة بادئة لرسالة السجل بمقدار 4 مسافات (أي medium، وهو الافتراضي، full، و fuller).

--notes[=<ref>]

اعرض الملاحظات (راجع git-notes(1)) التي تشرح الالتزام، عند عرض رسالة سجل الالتزام. هذا هو الافتراضي لأوامر git log، git show، و git whatchanged عندما لا يكون هناك خيار --pretty، --format، أو --oneline معطى في سطر الأوامر.

بشكل افتراضي، الملاحظات المعروضة تكون من مراجع الملاحظات المدرجة في متغيري core.notesRef و notes.displayRef (أو ما يقابلها من تجاوزات البيئة). راجع git-config(1) لمزيد من التفاصيل.

مع وسيط اختياري <ref>، استخدم المرجع للعثور على الملاحظات المراد عرضها. يمكن للمرجع تحديد اسم المرجع الكامل عندما يبدأ بـ refs/notes/؛ عندما يبدأ بـ notes/، refs/، وإلا يتم إضافة refs/notes/ لتكوين الاسم الكامل للمرجع.

يمكن دمج خيارات --notes متعددة للتحكم في الملاحظات التي يتم عرضها. أمثلة: "--notes=foo" سيعرض فقط الملاحظات من refs/notes/foo؛ "--notes=foo --notes" سيعرض كلاً من الملاحظات من "refs/notes/foo" والملاحظات الافتراضية.

--no-notes

لا تعرض الملاحظات. هذا يلغي خيار --notes أعلاه، عن طريق إعادة تعيين قائمة مراجع الملاحظات التي يتم عرض الملاحظات منها. يتم تحليل الخيارات بالترتيب المعطى في سطر الأوامر، لذلك على سبيل المثال، "--notes --notes=foo --no-notes --notes=bar" سيعرض فقط الملاحظات من refs/notes/bar.

--show-notes-by-default

اعرض الملاحظات الافتراضية ما لم يتم إعطاء خيارات لعرض ملاحظات معينة.

--show-notes[=<ref>], --standard-notes, --no-standard-notes

تم إيقاف هذه الخيارات. استخدم خيارات --notes/--no-notes أعلاه بدلاً من ذلك.

--show-signature

تحقق من صحة كائن الالتزام الموقّع عن طريق تمرير التوقيع إلى gpg --verify وعرض المخرجات.

--relative-date

مرادف لـ --date=relative.

--date=<format>

يتم تطبيقه فقط على التواريخ المعروضة بتنسيق يمكن قراءته بواسطة الإنسان، مثل عند استخدام --pretty. يقوم متغير إعداد log.date بتعيين قيمة افتراضية لخيار --date الخاص بأمر log. بشكل افتراضي، يتم عرض التواريخ في المنطقة الزمنية الأصلية (إما للملتزم أو المؤلف). إذا تم إلحاق -local بالتنسيق (على سبيل المثال، iso-local)، فسيتم استخدام المنطقة الزمنية المحلية للمستخدم بدلاً من ذلك.

يعرض --date=relative التواريخ بالنسبة للوقت الحالي، على سبيل المثال "منذ ساعتين". الخيار -local ليس له تأثير على --date=relative.

--date=local هو اسم مستعار لـ --date=default-local.

يعرض --date=iso (أو --date=iso8601) الطوابع الزمنية بتنسيق يشبه ISO 8601. الاختلافات عن تنسيق ISO 8601 الصارم هي:

• مسافة بدلاً من الفاصل T بين التاريخ/الوقت
• مسافة بين الوقت والمنطقة الزمنية
• لا يوجد نقطتان رأسيتان بين ساعات ودقائق المنطقة الزمنية

يعرض --date=iso-strict (أو --date=iso8601-strict) الطوابع الزمنية بتنسيق ISO 8601 صارم.

يعرض --date=rfc (أو --date=rfc2822) الطوابع الزمنية بتنسيق RFC 2822، الموجود غالبًا في رسائل البريد الإلكتروني.

--date=short يعرض التاريخ فقط، ولكن ليس الوقت، بتنسيق YYYY-MM-DD.

يعرض --date=raw التاريخ كثوانٍ منذ بداية الحقبة (1970-01-01 00:00:00 UTC)، متبوعًا بمسافة، ثم المنطقة الزمنية كإزاحة من UTC (علامة + أو - بأربعة أرقام؛ الأولان هما الساعات، والثانيان هما الدقائق). أي، كما لو تم تنسيق الطابع الزمني باستخدام strftime("%s %z"). لاحظ أن الخيار -local لا يؤثر على قيمة الثواني منذ بداية الحقبة (التي يتم قياسها دائمًا بالتوقيت العالمي المنسق)، ولكنه يغير قيمة المنطقة الزمنية المصاحبة.

يعرض --date=human المنطقة الزمنية إذا لم تتطابق المنطقة الزمنية مع المنطقة الزمنية الحالية، ولا يطبع التاريخ بأكمله إذا تطابق (أي، تخطي طباعة السنة للتواريخ التي هي "هذا العام"، ولكن أيضًا تخطي التاريخ بأكمله إذا كان في الأيام القليلة الماضية ويمكننا فقط قول يوم الأسبوع الذي كان). بالنسبة للتواريخ القديمة، يتم أيضًا حذف الساعة والدقيقة.

يعرض --date=unix التاريخ كطابع زمني لبداية الحقبة اليونانية (ثوانٍ منذ 1970). كما هو الحال مع --raw، يكون هذا دائمًا بتوقيت UTC وبالتالي لا يؤثر -local.

--date=format:<format> يمرر <format> إلى نظام strftime الخاص بك، باستثناء %s، %z، و b> mode <mode> copy from <path> copy to <path> rename from <path> rename to <path> similarity index <number> dissimilarity index <number> index <hash>..<hash> <mode>

File modes <mode> are printed as 6-digit octal numbers including the file type and file permission bits.

Path names in extended headers do not include the a/ and b/ prefixes.

The similarity index is the percentage of unchanged lines, and the dissimilarity index is the percentage of changed lines. It is a rounded down integer, followed by a percent sign. The similarity index value of 100% is thus reserved for two equal files, while 100% dissimilarity means that no line from the old file made it into the new one.

The index line includes the blob object names before and after the change. The <mode> is included if the file mode does not change; otherwise, separate lines indicate the old and the new mode.

COMBINED DIFF FORMAT

Any diff-generating command can take the -c or --cc option to produce a combined diff when showing a merge. This is the default format when showing merges with git-diff(1) or git-show(1). Note also that you can give suitable --diff-merges option to any of these commands to force generation of diffs in a specific format.

A "combined diff" format looks like this:

diff --combined describe.c
index fabadb8,cc95eb0..4866510
--- a/describe.c
+++ b/describe.c
@@@ -98,20 -98,12 +98,20 @@@
        return (a_date > b_date) ? -1 : (a_date == b_date) ? 0 : 1;
  }
- static void describe(char *arg)
 -static void describe(struct commit *cmit, int last_one)
 ++static void describe(char *arg, int last_one)
  {
 +      unsigned char sha1[20];
 +      struct commit *cmit;
        struct commit_list *list;
        static int initialized = 0;
        struct commit_name *n;
 +      if (get_sha1(arg, sha1) < 0)
 +              usage(describe_usage);
 +      cmit = lookup_commit_reference(sha1);
 +      if (!cmit)
 +              usage(describe_usage);
 +
        if (!initialized) {
                initialized = 1;
                for_each_ref(get_name);
1.It is preceded by a "git diff" header, that looks like this (when the -c option is used): 
diff --combined file

or like this (when the --cc option is used):

diff --cc file
2.It is followed by one or more extended header lines (this example shows a merge with two parents): 
index <hash>,<hash>..<hash>
mode <mode>,<mode>..<mode>
new file mode <mode>
deleted file mode <mode>,<mode>

The mode <mode>,<mode>..<mode> line appears only if at least one of the <mode> is different from the rest. Extended headers with information about detected content movement (renames and copying detection) are designed to work with the diff of two <tree-ish> and are not used by combined diff format.

3.It is followed by a two-line from-file/to-file header: 
--- a/file
+++ b/file

Similar to the two-line header for the traditional unified diff format, /dev/null is used to signal created or deleted files.

However, if the --combined-all-paths option is provided, instead of a two-line from-file/to-file, you get an N+1 line from-file/to-file header, where N is the number of parents in the merge commit:

--- a/file
--- a/file
--- a/file
+++ b/file

This extended format can be useful if rename or copy detection is active, to allow you to see the original name of the file in different parents.

4.Chunk header format is modified to prevent people from accidentally feeding it to patch -p1. Combined diff format was created for review of merge commit changes, and was not meant to be applied. The change is similar to the change in the extended index header: 
@@@ <from-file-range> <from-file-range> <to-file-range> @@@

There are (number of parents + 1) @ characters in the chunk header for combined diff format.

Unlike the traditional unified diff format, which shows two files A and B with a single column that has - (minus — appears in A but removed in B), + (plus — missing in A but added to B), or " " (space — unchanged) prefix, this format compares two or more files file1, file2,... with one file X, and shows how X differs from each of fileN. One column for each of fileN is prepended to the output line to note how X’s line is different from it.

A - character in the column N means that the line appears in fileN but it does not appear in the result. A + character in the column N means that the line appears in the result, and fileN does not have that line (in other words, the line was added, from the point of view of that parent).

In the above example output, the function signature was changed from both files (hence two - removals from both file1 and file2, plus ++ to mean one line that was added does not appear in either file1 or file2). Also, eight other lines are the same from file1 but do not appear in file2 (hence prefixed with +).

When shown by git diff-tree -c, it compares the parents of a merge commit with the merge result (i.e. file1..fileN are the parents). When shown by git diff-files -c, it compares the two unresolved merge parents with the working tree file (i.e. file1 is stage 2 aka "our version", file2 is stage 3 aka "their version").

EXAMPLES

git log --no-merges

Show the whole commit history, but skip any merges

git log v2.6.12.. include/scsi drivers/scsi

Show all commits since version v2.6.12 that changed any file in the include/scsi or drivers/scsi subdirectories

git log --since="2 weeks ago" -- gitk

Show the changes during the last two weeks to the file gitk. The -- is necessary to avoid confusion with the branch named gitk

git log --name-status release..test

Show the commits that are in the "test" branch but not yet in the "release" branch, along with the list of paths each commit modifies.

git log --follow builtin/rev-list.c

Shows the commits that changed builtin/rev-list.c, including those commits that occurred before the file was given its present name.

git log --branches --not --remotes=origin

Shows all commits that are in any of local branches but not in any of remote-tracking branches for origin (what you have that origin doesn’t).

git log master --not --remotes=*/master

Shows all commits that are in local master but not in any remote repository master branches.

git log -p -m --first-parent

Shows the history including change diffs, but only from the “main branch” perspective, skipping commits that come from merged branches, and showing full diffs of changes introduced by the merges. This makes sense only when following a strict policy of merging all topic branches when staying on a single integration branch.

git log -L '/int main/',/^}/:main.c

Shows how the function main() in the file main.c evolved over time.

git log -3

Limits the number of commits to show to 3.

DISCUSSION

Git is to some extent character encoding agnostic.

•The contents of the blob objects are uninterpreted sequences of bytes. There is no encoding translation at the core level.
•Path names are encoded in UTF-8 normalization form C. This applies to tree objects, the index file, ref names, as well as path names in command line arguments, environment variables and config files (.git/config (see git-config(1)), gitignore(5), gitattributes(5) and gitmodules(5)).

Note that Git at the core level treats path names simply as sequences of non-NUL bytes, there are no path name encoding conversions (except on Mac and Windows). Therefore, using non-ASCII path names will mostly work even on platforms and file systems that use legacy extended ASCII encodings. However, repositories created on such systems will not work properly on UTF-8-based systems (e.g. Linux, Mac, Windows) and vice versa. Additionally, many Git-based tools simply assume path names to be UTF-8 and will fail to display other encodings correctly.<
