git-rerere(1)

الحزمة: git

التراخيص: GPL-2.0-only

GIT-RERERE(1) دليل Git GIT-RERERE(1)

الاسم

git-rerere - إعادة استخدام الحلول المسجلة للدمجات المتعارضة

الملخص

git rerere [clear | forget <pathspec>... | diff | status | remaining | gc]

الوصف

في سير عمل يستخدم فروع موضوعات طويلة العمر نسبيًا، يحتاج المطور أحيانًا إلى حل نفس التعارضات مرارًا وتكرارًا حتى تنتهي فروع الموضوعات (إما بدمجها في فرع "الإصدار"، أو بإرسالها وقبولها في المنبع).

يساعد هذا الأمر المطور في هذه العملية عن طريق تسجيل نتائج الدمج التلقائي المتعارضة ونتائج الحل اليدوي المقابلة لها عند الدمج اليدوي الأولي، وتطبيق الحلول اليدوية المسجلة سابقًا على نتائج الدمج التلقائي المقابلة لها.


ملاحظة

تحتاج إلى تعيين متغير الإعدادات rerere.enabled لتمكين هذا الأمر.

الأوامر

عادةً، يتم تشغيل git rerere بدون وسائط أو تدخل من المستخدم. ومع ذلك، فإنه يحتوي على عدة أوامر تسمح له بالتفاعل مع حالته العاملة.

clear

إعادة تعيين البيانات الوصفية التي يستخدمها rerere إذا كان سيتم إلغاء حل دمج. استدعاء git am [--skip|--abort] أو git rebase [--skip|--abort] سيستدعي هذا الأمر تلقائيًا.

forget <pathspec>

إعادة تعيين حلول التعارضات التي سجلها rerere للتعارض الحالي في <pathspec>.

diff

عرض الفروقات للحالة الحالية للحل. إنه مفيد لتتبع ما تغير أثناء قيام المستخدم بحل التعارضات. يتم تمرير الوسائط الإضافية مباشرة إلى أمر diff النظامي المثبت في PATH.

status

طباعة المسارات التي بها تعارضات سيسجل rerere حل دمجها.

remaining

طباعة المسارات التي بها تعارضات لم يتم حلها تلقائيًا بواسطة rerere. يشمل ذلك المسارات التي لا يمكن لـ rerere تتبع حلولها، مثل الوحدات الفرعية المتعارضة.

gc

تقليم سجلات الدمجات المتعارضة التي حدثت منذ وقت طويل. افتراضيًا، يتم تقليم التعارضات غير المحلولة الأقدم من 15 يومًا والتعارضات المحلولة الأقدم من 60 يومًا. يتم التحكم في هذه الإعدادات الافتراضية عبر متغيري الإعدادات gc.rerereUnresolved و gc.rerereResolved على التوالي.

المناقشة

عندما يعدّل فرع موضوعك منطقة متداخلة لمسها فرع master (أو المنبع) منذ أن تفرّع فرع موضوعك منه، قد ترغب في اختباره مع أحدث master، حتى قبل أن يكون فرع موضوعك جاهزًا للدفع إلى المنبع:

              o---*---o topic
             /
    o---o---o---*---o---o master

لمثل هذا الاختبار، تحتاج إلى دمج master و topic بطريقة ما. إحدى الطرق للقيام بذلك هي سحب master إلى فرع الموضوع:

        $ git switch topic
        $ git merge master
              o---*---o---+ topic
             /           /
    o---o---o---*---o---o master

الالتزامات المميزة بـ * تلمس نفس المنطقة في نفس الملف؛ تحتاج إلى حل التعارضات عند إنشاء الالتزام المميز بـ +. ثم يمكنك اختبار النتيجة للتأكد من أن عملك قيد التقدم لا يزال يعمل مع ما هو موجود في أحدث master.

بعد دمج الاختبار هذا، هناك طريقتان لمواصلة عملك على الموضوع. الأسهل هو البناء فوق التزام دمج الاختبار +، وعندما يصبح عملك في فرع الموضوع جاهزًا أخيرًا، اسحب فرع الموضوع إلى master، و/أو اطلب من المنبع السحب منك. بحلول ذلك الوقت، ومع ذلك، قد يكون master أو المنبع قد تقدم منذ دمج الاختبار +، وفي هذه الحالة سيبدو رسم الالتزام النهائي هكذا:

        $ git switch topic
        $ git merge master
        $ ... work on both topic and master branches
        $ git switch master
        $ git merge topic
              o---*---o---+---o---o topic
             /           /         \
    o---o---o---*---o---o---o---o---+ master

عندما يكون فرع موضوعك طويل العمر، ومع ذلك، سينتهي به الأمر بوجود العديد من التزامات "الدمج من master" عليه، مما سيزحم تاريخ التطوير دون داعٍ. قد يتذكر قراء قائمة بريد نواة لينكس أن لينوس اشتكى من عمليات دمج الاختبار المتكررة جدًا هذه عندما طلب أحد مشرفي النظام الفرعي السحب من فرع مليء بـ "الدمجات عديمة الفائدة".

كبديل، للحفاظ على فرع الموضوع نظيفًا من دمجات الاختبار، يمكنك إزالة دمج الاختبار، والاستمرار في البناء فوق الطرف قبل دمج الاختبار:

        $ git switch topic
        $ git merge master
        $ git reset --hard HEAD^ ;# rewind the test merge
        $ ... work on both topic and master branches
        $ git switch master
        $ git merge topic
              o---*---o-------o---o topic
             /                     \
    o---o---o---*---o---o---o---o---+ master

سيؤدي هذا إلى ترك التزام دمج واحد فقط عندما يصبح فرع موضوعك جاهزًا أخيرًا ويُدمج في فرع master. سيتطلب هذا الدمج منك حل التعارض الذي أدخلته الالتزامات المميزة بـ *. ومع ذلك، غالبًا ما يكون هذا التعارض هو نفس التعارض الذي حللته عند إنشاء دمج الاختبار الذي أزلته. يساعدك git rerere في حل هذا الدمج المتعارض النهائي باستخدام المعلومات من حلك اليدوي السابق.

تشغيل أمر git rerere مباشرة بعد دمج تلقائي متعارض يسجل ملفات شجرة العمل المتعارضة، مع علامات التعارض المعتادة <<<<<<<، =======، و >>>>>>> فيها. لاحقًا، بعد الانتهاء من حل التعارضات، تشغيل git rerere مرة أخرى سيسجل الحالة المحلولة لهذه الملفات. افترض أنك فعلت ذلك عندما أنشأت دمج الاختبار لـ master في فرع الموضوع.

في المرة التالية، بعد رؤية نفس الدمج التلقائي المتعارض، سيقوم تشغيل git rerere بإجراء دمج ثلاثي بين الدمج التلقائي المتعارض السابق، والحل اليدوي السابق، والدمج التلقائي المتعارض الحالي. إذا حل هذا الدمج الثلاثي بشكل نظيف، تُكتب النتيجة في ملف شجرة العمل الخاص بك، لذلك لا تضطر إلى حلها يدويًا. لاحظ أن git rerere يترك ملف الفهرس كما هو، لذلك لا تزال بحاجة إلى إجراء فحوصات السلامة النهائية باستخدام git diff (أو git diff -c) و git add عندما تكون راضيًا.

كإجراء ملائم، يستدعي git merge تلقائيًا git rerere عند الخروج بدمج تلقائي فاشل ويسجل git rerere الحل اليدوي عندما يكون تعارضًا جديدًا، أو يعيد استخدام الحل اليدوي السابق عندما لا يكون كذلك. يستدعي git commit أيضًا git rerere عند إيداع نتيجة دمج. ما يعنيه هذا هو أنه لا يتعين عليك القيام بأي شيء خاص بنفسك (إلى جانب تمكين متغير الإعدادات rerere.enabled).

في مثالنا، عندما تقوم بدمج الاختبار، يتم تسجيل الحل اليدوي، وسيُعاد استخدامه عندما تقوم بالدمج الفعلي لاحقًا مع master وفرع الموضوع المحدثين، طالما أن الحل المسجل لا يزال قابلًا للتطبيق.

تُستخدم المعلومات التي يسجلها git rerere أيضًا عند تشغيل git rebase. بعد إزالة دمج الاختبار ومواصلة التطوير على فرع الموضوع:

              o---*---o-------o---o topic
             /
    o---o---o---*---o---o---o---o   master
        $ git rebase master topic
                                  o---*---o-------o---o topic
                                 /
    o---o---o---*---o---o---o---o   master

يمكنك تشغيل git rebase master topic، لتحديث نفسك قبل أن يكون موضوعك جاهزًا للإرسال إلى المنبع. سيؤدي هذا إلى الرجوع إلى دمج ثلاثي، وسيتعارض بنفس الطريقة التي تعارض بها دمج الاختبار الذي حللته سابقًا. سيتم تشغيل git rerere بواسطة git rebase لمساعدتك في حل هذا التعارض.

[ملاحظة] يعتمد git rerere على علامات التعارض في الملف لاكتشاف التعارض. إذا كان الملف يحتوي بالفعل على أسطر تبدو مثل الأسطر التي بها علامات تعارض، فقد يفشل git rerere في تسجيل حل تعارض. للالتفاف حول هذا، يمكن استخدام إعداد conflict-marker-size في gitattributes(5).
