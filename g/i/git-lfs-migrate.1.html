اسم

git-lfs-migrate - ترحيل السجل إلى Git LFS أو منه

ملخص

git lfs migrate <mode> [options] [--] [branch ...]

وصف

تحويل الملفات في مستودع Git إلى أو من مؤشرات Git LFS، أو تلخيص أحجام ملفات Git حسب نوع الملف. الوضع import يحول ملفات Git (أي، الكائنات الكروية) إلى Git LFS، بينما الوضع export يفعل العكس، والوضع info يوفر ملخصًا معلوماتيًا قد يكون مفيدًا في تحديد الملفات التي سيتم استيرادها أو تصديرها.

في جميع الأوضاع، بشكل افتراضي، يعمل git lfs migrate فقط على الفرع الذي تم فحصه حاليًا، وفقط على الملفات (بأي حجم ونوع) المضافة في الالتزامات التي لا توجد على أي جهاز عن بعد. تتوفر خيارات متعددة لتجاوز هذه الإعدادات الافتراضية.

عند تحويل الملفات إلى أو من Git LFS، لن يقوم الأمر git lfs migrate بإجراء أي تغييرات على مستودعك المحلي ونسختك العاملة، ولا على أي أجهزة عن بعد. هذا متعمد لأن أوضاع import و export هي عمومًا "مدمرة" بمعنى أنها تعيد كتابة سجل Git الخاص بك، وتغير الالتزامات وتولد معرفات التزام جديدة. (الاستثناء هو وضع import "بدون إعادة كتابة"؛؛ انظر الاستيراد بدون إعادة كتابة السجل لمزيد من التفاصيل).

لذلك، يجب عليك دائمًا أولاً الالتزام أو تخزين أي عمل غير ملتزم قبل استخدام أوضاع import أو export، ثم التحقق من صحة نتيجة الترحيل قبل دفع التغييرات إلى أجهزتك عن بعد، على سبيل المثال عن طريق تشغيل الوضع info وفحص سجل الترحيل الخاص بك.

بمجرد رضاك عن التغييرات، ستحتاج إلى فرض دفع سجل Git الجديد لأي فروع أعيدت كتابتها إلى جميع أجهزتك عن بعد. هذه خطوة يجب اتخاذها بحذر، حيث أنك ستقوم بتعديل سجل Git على أجهزتك عن بعد.

لفحص أو تعديل الملفات في فروع غير تلك التي تم فحصها حاليًا، يمكن تحديد مراجع الفروع مباشرة، أو توفيرها في خيار أو أكثر من خيارات --include-ref. يمكن أيضًا استبعادها عن طريق بادئتها بـ ^ أو توفيرها في خيارات --exclude-ref. استخدم الخيار --everything لتحديد أنه يجب فحص جميع المراجع، بما في ذلك جميع المراجع عن بعد. انظر تضمين واستبعاد المراجع لمزيد من التفاصيل.

بالنسبة لوضعي info و import، يتم النظر في جميع أنواع الملفات افتراضيًا؛ بينما يكون مفيدًا في وضع info، إلا أنه غالبًا ما لا يكون مرغوبًا فيه عند الاستيراد، لذلك يجب عادةً تحديد أنماط أسماء الملفات (مسارات) أو خيار --fixup في هذه الحالة. (يلزم وجود مسار تضمين واحد على الأقل لوضع export). يمكن تعريف مسارات المسارات باستخدام خيارات --include و --exclude ( -I و -X للاختصار)، كما هو موضح في تضمين واستبعاد.

نظرًا لأن الاستخدام القياسي لـ Git LFS يعتمد على تتبع أنواع ملفات محددة باستخدام أنماط أسماء الملفات المحددة في ملفات .gitattributes، فإن الأمر git lfs migrate سيقوم بفحص وإنشاء وتعديل ملفات .gitattributes حسب الضرورة. سيتم دائمًا تعيين ملفات .gitattributes على وضع الأذونات الافتراضي للقراءة/الكتابة (أي، بدون أذونات تنفيذ). أي روابط رمزية بهذا الاسم ستتسبب في توقف الترحيل مبكرًا.

سيقوم وضع import (انظر الاستيراد) بتحويل كائنات Git لأنواع الملفات المحددة (على سبيل المثال، باستخدام --include) إلى مؤشرات Git LFS، وسيضيف إدخالات لتلك الأنواع من الملفات إلى ملفات .gitattributes، وسيُنشئ تلك الملفات إذا لم تكن موجودة. يجب أن تكون النتيجة كما لو تم تشغيل أوامر git lfs track في النقاط في سجل Git الخاص بك المقابلة لمكان ظهور كل نوع من أنواع الملفات المحولة. الاستثناء هو إذا تم تقديم الخيار --fixup، وفي هذه الحالة سيقوم وضع import بفحص أي ملفات .gitattributes موجودة فقط ثم تحويل كائنات Git التي يجب تتبعها بواسطة Git LFS ولكنها ليست كذلك بعد.

يعمل وضع export (انظر التصدير) كعملية عكسية لوضع import، ويحول أي مؤشرات Git LFS تتطابق مع أنواع الملفات المحددة باستخدام --include، والتي يجب تقديمها مرة واحدة على الأقل. لاحظ أنه لن يتم إزالة إدخالات .gitattributes، ولا الملفات؛ بدلاً من ذلك، يقوم وضع export بإدراج إدخالات "لا تتتبع" مشابهة لتلك التي تم إنشاؤها بواسطة الأمر git lfs untrack. الخيار --remote متاح في وضع export لتحديد الجهاز البعيد الذي يجب جلب كائنات Git LFS منه إذا لم تكن موجودة في ذاكرة التخزين المؤقت المحلية لكائنات Git LFS؛ إذا لم يتم توفيره، يتم استخدام origin افتراضيًا.

يقوم الوضع info (انظر المعلومات) بتلخيص حسب نوع الملف (أي، حسب امتداد اسم الملف) العدد الإجمالي وحجم الملفات في المستودع. لاحظ أنه مثل الوضعين الآخرين، بشكل افتراضي، يعمل الوضع info فقط على الفرع الذي تم فحصه حاليًا وفقط على الالتزامات التي لا توجد على أي جهاز عن بعد، لذلك للحصول على ملخص للمستودع بأكمله عبر جميع الفروع، استخدم الخيار --everything. إذا تم بالفعل تحويل الكائنات إلى مؤشرات Git LFS، فسيتم افتراضيًا جمع حجم الكائنات المشار إليها والإبلاغ عنها بشكل منفصل. يمكنك أيضًا اختيار تجاهلها باستخدام --pointers=ignore أو معاملة المؤشرات كملفات باستخدام --pointers=no-follow. (هذا الخيار الأخير يشبه كيف تم التعامل مع مؤشرات Git LFS الموجودة بواسطة الوضع info في الإصدارات السابقة من Git LFS).

عند استخدام الخيار --everything، لاحظ أنه يعني أنه سيتم النظر في جميع الالتزامات التي يمكن الوصول إليها من جميع المراجع (المحلية وعن بعد)، ولكن ليس بالضرورة جميع أنواع الملفات. يأخذ وضعا import و info جميع أنواع الملفات في الاعتبار افتراضيًا، على الرغم من أن خيارات --include و --exclude تقيد هذا السلوك.

بينما يعني الخيار --everything أنه سيتم النظر في جميع الالتزامات التي يمكن الوصول إليها من أي مرجع للترحيل، بعد الترحيل، سيتم تحديث المراجع المحلية فقط حتى عند تحديد --everything. هذا يضمن بقاء المراجع عن بعد متزامنة مع أجهزتها عن بعد. بعبارة أخرى، سيتم تحديث refs/heads/foo باستخدام الخيار --everything، ولكن refs/remotes/origin/foo لن يتم تحديثه، لذلك يظل متزامنًا مع الجهاز البعيد حتى يتم تنفيذ git push origin foo. بعد التحقق من أن نتائج الترحيل باستخدام --everything مرضية، قد يكون من المناسب دفع جميع الفروع المحلية إلى أجهزتك عن بعد باستخدام الخيار --all لـ git push.

ما لم يتم تقديم الخيار --skip-fetch، يبدأ git lfs migrate دائمًا بجلب قوائم محدثة بالمراجع من جميع الأجهزة عن بعد التي يتم إرجاعها بواسطة git remote، ولكن كما ذكرنا أعلاه، بعد إجراء تغييرات على سجل Git المحلي الخاص بك أثناء تحويل الكائنات، فإنه لن يدفع أبدًا تلك التغييرات تلقائيًا إلى أجهزتك عن بعد.

الأوضاع

info

عرض معلومات حول حجم المستودع. انظر المعلومات.

import

تحويل كائنات Git إلى مؤشرات Git LFS. انظر الاستيراد والاستيراد بدون إعادة كتابة السجل.

export

تحويل مؤشرات Git LFS إلى كائنات Git. انظر التصدير.

خيارات

-I <paths>, --include=<paths>

انظر تضمين واستبعاد.

-X <paths>, --exclude=<paths>

انظر تضمين واستبعاد.

--include-ref=<refname>

انظر تضمين واستبعاد المراجع.
