git-revise(1)

الحزمة: git-revise

التراخيص: MIT

GIT-REVISE(1) git-revise GIT-REVISE(1)

الاسم

git-revise - تحديث وتقسيم وإعادة ترتيب الـ commits بكفاءة

الملخص

git revise [<خيارات>] [<هدف>]

الوصف

git revise هو أمر فرعي لـ git(1) لتحديث وتقسيم وإعادة ترتيب الـ commits بكفاءة. إنه مستوحى بشكل كبير من git-rebase(1)، ولكنه يحاول أن يكون أكثر كفاءة وسهولة في الاستخدام لسير العمل الموجه نحو stack الرقع.

افتراضيًا، سيقوم git revise بتطبيق التغييرات المرحلية على <target>، وتحديث HEAD ليشير إلى الـ history المعدلة. كما أنه يدعم تقسيم الـ commits وتغيير رسائل الـ commit.

على عكس git-rebase(1)، يتجنب git revise تعديل حالة دليل العمل والفهرس، حيث يقوم بجميع عمليات الدمج في الذاكرة، ويكتبها فقط عند الضرورة. وهذا يسمح له بأن يكون أسرع بشكل كبير في قواعد الكود الكبيرة، وتجنب إبطال عمليات البناء.

إذا تم تحديد --autosquash أو --interactive، فقد يتم حذف الوسيطة <target> أو إعطاؤها كقيمة خاصة :option:--root. إذا تم حذفها، فسيأخذ git revise في الاعتبار نطاقًا من الـ commits غير المنشورة على الفرع الحالي. إذا تم إعطاؤها كـ :option:--root، فسيتم أخذ جميع الـ commits بما في ذلك الـ commit الجذري في الاعتبار.

الخيارات

خيارات عامة

-a, --all
مرحلة التغييرات للملفات المتعقبة قبل المراجعة.
-p, --patch
مرحلة الأجزاء (hunks) بشكل تفاعلي من دليل العمل قبل المراجعة.
--no-index
تجاهل التغييرات المرحلية في الفهرس.
--reauthor
إعادة تعيين مؤلف الـ commit الهدف إلى المستخدم الحالي.
--ref <gitref>
الفرع العامل للتحديث؛ افتراضيًا هو HEAD.
-S, --gpg-sign, --no-gpg-sign
توقيع الـ commits باستخدام GPG. يتجاوز إعدادات التكوين commit.gpgSign و revise.gpgSign.

أوضاع التشغيل الرئيسية

-i, --interactive
بدلاً من تطبيق التغييرات المرحلية على <target>، قم بتحرير قائمة مهام للإجراءات التي يجب تنفيذها على الـ commits بعد <target>. انظر وضع تفاعلي.
--autosquash, --no-autosquash
بدلاً من تطبيق التغييرات المرحلية مباشرة على <target>، قم بتنفيذ إجراءات fixup أو squash تلقائيًا المميزة بـ fixup! أو squash! بين <target> و HEAD الحالي. لمزيد من المعلومات حول ما تقوم به هذه الإجراءات، انظر وضع تفاعلي.

عادةً ما يتم إنشاء هذه الـ commits باستخدام git commit --fixup=<commit> أو git commit --squash=<commit>، وتحديد الـ target بسطرها الأول في رسالة الـ commit.

يمكن دمج هذا الخيار مع --interactive لتعديل مهام todo التي تم إنشاؤها قبل تنفيذها.

إذا تم تمكين الخيار --autosquash افتراضيًا باستخدام متغير تكوين، فيمكن استخدام الخيار --no-autosquash لتجاوز وتعطيل هذا الإعداد. انظر التكوين.

-c, --cut
اختر الأجزاء (hunks) بشكل تفاعلي من <target>. يتم تقسيم الأجزاء المختارة إلى commit ثانٍ مباشرة بعد الـ target.

بعد اكتمال التقسيم، يتم تحرير رسائل كلا الـ commits.

راجع قسم "الوضع التفاعلي" في git-add(1) لمعرفة كيفية تشغيل هذا الوضع.

-e, --edit
بعد تطبيق التغييرات المرحلية، قم بتحرير رسالة الـ commit الخاصة بـ <target>.

يمكن دمج هذا الخيار مع --interactive للسماح بتحرير رسائل الـ commit داخل قائمة المهام. لمزيد من المعلومات، انظر وضع تفاعلي.

-m <msg>, --message <msg>
استخدم <msg> المعطاة كرسالة الـ commit الجديدة لـ <target>. إذا تم إعطاء خيارات -m متعددة، يتم تجميع قيمها كفقرات منفصلة.
--version
اطبع معلومات الإصدار واخرج.

التكوين

تتم إدارة التكوين بواسطة git-config(1).

revise.autoSquash
إذا تم تعيينه على true، فإنه يعني ضمنيًا --autosquash كلما تم استخدام --interactive. يتم تجاوزه بواسطة --no-autosquash. الافتراضي هو false. إذا لم يتم تعيينه، يتم استخدام قيمة rebase.autoSquash بدلاً من ذلك.
revise.gpgSign
إذا تم تعيينه على true، فقم بتوقيع الـ commits الجديدة باستخدام GPG؛ الافتراضي هو false. هذا الإعداد يتجاوز تكوين git الأصلي commit.gpgSign وقد يتم تجاوزه بواسطة خيارات سطر الأوامر --gpg-sign و --no-gpg-sign.

حل التعارضات

عند مواجهة تعارض، سيحاول git revise حله تلقائيًا باستخدام آليات git القياسية. إذا فشل الحل التلقائي، سيتم مطالبة المستخدم بحلها يدويًا.

لا يوجد حاليًا دعم لاستخدام git-mergetool(1) لحل التعارضات.

لا يتم بذل أي محاولة لاكتشاف إعادة تسمية الملفات أو المجلدات. قد ينتج عن git revise نتائج دون المستوى الأمثل عبر عمليات إعادة التسمية. استخدم الوضع التفاعلي لـ git-rebase(1) عندما يكون تتبع إعادة التسمية مهمًا.

ملاحظات

سيؤدي نجاح git revise إلى إضافة إدخال واحد إلى reflog، مما يسمح بالتراجع عنه باستخدام git reset @{1}. ستترك أوامر git revise الفاشلة المستودع الخاص بك دون تغيير إلى حد كبير.

لا يُسمح بوجود commits دمج بين الـ commit الهدف و HEAD، حيث لا يتم دعم إعادة كتابتها.

انظر git-rebase(1) لمزيد من المعلومات حول آثار تعديل الـ history على مستودع تشاركه.

وضع تفاعلي

يدعم git revise وضعًا تفاعليًا مستوحى من الوضع التفاعلي لـ git-rebase(1).

يبدأ هذا الوضع بآخر commit تريد الاحتفاظ بها "كما هي":

git revise -i <after-this-commit>

الهدف الخاص --root متاح لمراجعة كل شيء حتى الـ commit الجذري:

git revise -i --root

سيتم فتح محرر بـ commits في فرعك الحالي بعد الـ commit المحدد. إذا كان الفهرس يحتوي على أي تغييرات مرحلية ولكن غير ملتزم بها، فسيظهر أيضًا إدخال <git index>.

pick 8338dfa88912 Oneline summary of first commit
pick 735609912343 Summar

هذا الموقع غير مرتبط بـ Arch Linux ولا تابع له بأي شكل من الأشكال. المحتوى هو ترجمة فقط لصفحات دليل Arch المنشورة على man.archlinux.org.
