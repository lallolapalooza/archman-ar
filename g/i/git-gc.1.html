git-gc(1)

الحزمة: git

التراخيص: GPL-2.0-only

NAME

git-gc — collection of utilities and repository cleanup

SYNOPSIS

git gc [--auto] [--aggressive] [--prune=<date>] [--quiet] [--verbose] [--force] [--keep-pack=...] [--small-objects-check=<mode>] [--big-objects-check=<mode>] [--write-commit-graph] [--no-write-commit-graph] [--log-expiration-info] [--sd-ref=...] [--cruft] [--no-cruft] [--max-cruft-size=<size>] [--expire=<time>] [--worktree-expire=<time>] [--reflog-expire=<time>] [--reflog-expire-unreachable=<time>] [--rerere-gc]

DESCRIPTION

This command is a collection of utilities that Git uses for cleanup. It is run automatically by git-fetch, git pull and git-daemon if you have it enabled.

Running git gc manually is useful for cleaning up unnecessary files and performing aggressive maintenance on the local repository.

The command can be run with the --auto option. This option is used by Git to run the garbage collection at appropriate times, e.g. when a fetch has completed. It is not intended to be run manually.

The command can be run with the --aggressive option. This option is used by Git to run the garbage collection at appropriate times, e.g. when a fetch has completed. It is not intended to be run manually.

OPTIONS

--auto:: When this option is specified, git gc will not run unless at least one of the conditions described in the AGGRESSIVE section is met. This is the default when git gc is run by other Git commands. This option implies --prune=2.weeks.ago if gc.pruneExpire is not set.

--aggressive:: This option tells git gc to optimize the repository by packing more aggressively. This can take longer than the default garbage collection.

--prune=<date>:: Remove any loose objects older than the specified date. Defaults to 2 weeks ago. See git-gc(1) for more info on date formats.

--quiet:: Suppress informative output. Only errors and the final summary are shown.

--verbose:: Print more detailed output.

--force:: Force git gc to run even if it thinks it's not needed.

--keep-pack=...:: Do not remove the specified packfiles. This option can be specified multiple times.

--small-objects-check=<mode>:: This option determines how to handle small objects. Possible values are auto, unpack, keep, none. Defaults to auto.

--big-objects-check=<mode>:: This option determines how to handle big objects. Possible values are auto, unpack, keep, none. Defaults to auto.

--write-commit-graph, --no-write-commit-graph:: These options control whether git gc will write the commit-graph file. See git-commit-graph(1) for details.

--log-expiration-info:: When removing reflog entries, print information about which entries were expired.

--sd-ref=...:: When repacking, do not prune loose objects that are reachable from the specified ref(s). This option can be specified multiple times.

--cruft, --no-cruft:: These options control whether to use cruft packs. See git-repack(1) for details.

--max-cruft-size=<size>:: Limit the size of new cruft packs when repacking. See the --max-cruft-size option of git-repack(1).

--expire=<time>:: Override the value of gc.pruneExpire. See below.

--worktree-expire=<time>:: Override the value of gc.worktreePruneExpire. See below.

--reflog-expire=<time>:: Override the value of gc.reflogExpire. See below.

--reflog-expire-unreachable=<time>:: Override the value of gc.reflogExpireUnreachable. See below.

--rerere-gc:: Run git rerere gc to prune the rerere database. See git-rerere(1).

AGGRESSIVE

When git gc --auto is run, it checks for a few conditions to decide whether to run. These conditions are meant to prevent git gc from running too often and slowing down normal operations.

The conditions are:

1. The repository has loose objects that are older than gc.pruneExpire (default: 2.weeks.ago).

2. The repository has more than gc.packThreshold (default: 0) loose objects.

3. The repository has more than gc.bigPackThreshold (default: 50 MiB) worth of loose objects.

4. The total size of all loose objects is more than gc.looseObjectThreshold (default: 100 MiB).

5. The repository has more than gc.fullPackReasonThreshold (default: 1000) packs that could be consolidated.

If any of these conditions are met, git gc --auto will run.

If the repository is pushed to, then the default gc.pruneExpire setting is 2.weeks.ago. This ensures that objects pushed to the repository are not immediately pruned. When --aggressive is used, the gc.pruneExpire is set to 1.day.ago.

The gc.bigPackThreshold setting is used to control the size of packs that are consolidated. If the largest pack is larger than gc.bigPackThreshold and the repository is not being run with --auto, then the largest pack will also be excluded (this is the equivalent of running git gc with --keep-largest-pack).

CONFIGURATION

The git gc command respects the following configuration variables:

gc.auto

A threshold for the number of loose objects. If the repository has more loose objects than this, git gc --auto will run. Default is 0, meaning git gc --auto will run unconditionally unless a grace period is active.

gc.packThreshold

A threshold for the number of loose objects. If the repository has more loose objects than this, git gc --auto will run. Default is 0, meaning git gc --auto will run unconditionally unless a grace period is active.

gc.bigPackThreshold

A threshold for the size of loose objects. If the total size of loose objects exceeds this, git gc --auto will run. Default is 50 MiB. If gc.bigPackThreshold is not set and --auto is not used, the largest pack will also be excluded (this is the equivalent of running git gc with --keep-largest-pack).

gc.looseObjectThreshold

A threshold for the total size of loose objects. If the total size of loose objects exceeds this, git gc --auto will run. Default is 100 MiB.

gc.fullPackReasonThreshold

A threshold for the number of packs that could be consolidated. If the number of packs exceeds this, git gc --auto will run. Default is 1000.

gc.pruneExpire

When git gc is run, it will call git prune --expire with this value. Default is "2.weeks.ago".

gc.incrementalPruneExpire

When git gc --auto is run, it will call git prune --expire with this value. Default is "1.day.ago". This is only used when --auto is specified and gc.pruneExpire is not explicitly set.

gc.packEverything

A boolean value. If true, then git gc will pack all loose objects into a single packfile. Default is false. This option is only useful when run manually, not with --auto.

gc.autopackLargeFiles

A boolean value. If true, then git gc will pack large files into a separate packfile. Default is false. This option is only useful when run manually, not with --auto.

gc.bigPackThreshold

If gc.bigPackThreshold is not set and --auto is not used, the largest pack will also be excluded (this is the equivalent of running git gc with --keep-largest-pack).

gc.writeCommitGraph

If true, then gc will rewrite the commit-graph file when git gc is run. When using git gc --auto the commit-graph will be updated if housekeeping is required. Default is true. See git-commit-graph(1) for details.

gc.logExpiry

If the file gc.log exists, then git gc --auto will print its content and exit with status zero instead of running unless that file is more than gc.logExpiry old. Default is "1.day". See gc.pruneExpire for more ways to specify its value.

gc.packRefs

Running git pack-refs in a repository renders it unclonable by Git versions prior to 1.5.1.2 over dumb transports such as HTTP. This variable determines whether git gc runs git pack-refs. This can be set to notbare to enable it within all non-bare repos or it can be set to a boolean value. The default is true.

gc.cruftPacks

Store unreachable objects in a cruft pack (see git-repack(1)) instead of as loose objects. The default is true.

gc.maxCruftSize

Limit the size of new cruft packs when repacking. When specified in addition to --max-cruft-size, the command line option takes priority. See the --max-cruft-size option of git-repack(1).

gc.pruneExpire

When git gc is run, it will call prune --expire 2.weeks.ago (and repack --cruft --cruft-expiration 2.weeks.ago if using cruft packs via gc.cruftPacks or --cruft). Override the grace period with this config variable. The value "now" may be used to disable this grace period and always prune unreachable objects immediately, or "never" may be used to suppress pruning. This feature helps prevent corruption when git gc runs concurrently with another process writing to the repository; see the "NOTES" section of git-gc(1).

gc.worktreePruneExpire

When git gc is run, it calls git worktree prune --expire 3.months.ago. This config variable can be used to set a different grace period. The value "now" may be used to disable the grace period and prune $GIT_DIR/worktrees immediately, or "never" may be used to suppress pruning.

gc.reflogExpire, gc.<pattern>.reflogExpire

git reflog expire removes reflog entries older than this time; defaults to 90 days. The value "now" expires all entries immediately, and "never" suppresses expiration altogether. With "<pattern>" (e.g. "refs/stash") in the middle the setting applies only to the refs that match the <pattern>.

gc.reflogExpireUnreachable, gc.<pattern>.reflogExpireUnreachable

git reflog expire removes reflog entries older than this time and are not reachable from the current tip; defaults to 30 days. The value "now" expires all entries immediately, and "never" suppresses expiration altogether. With "<pattern>" (e.g. "refs/stash") in the middle, the setting applies only to the refs that match the <pattern>.

These types of entries are generally created as a result of using git commit --amend or git rebase and are the commits prior to the amend or rebase occurring. Since these changes are not part of the current project most users will want to expire them sooner, which is why the default is more aggressive than gc.reflogExpire.

gc.recentObjectsHook

When considering whether or not to remove an object (either when generating a cruft pack or storing unreachable objects as loose), use the shell to execute the specified command(s). Interpret their output as object IDs which Git will consider as "recent", regardless of their age. By treating their mtimes as "now", any objects (and their descendants) mentioned in the output will be kept regardless of their true age.

Output must contain exactly one hex object ID per line, and nothing else. Objects which cannot be found in the repository are ignored. Multiple hooks are supported, but all must exit successfully, else the operation (either generating a cruft pack or unpacking unreachable objects) will be halted.

gc.repackFilter

When repacking, use the specified filter to move certain objects into a separate packfile. See the --filter=<filter-spec> option of git-repack(1).

gc.repackFilterTo

When repacking and using a filter, see gc.repackFilter, the specified location will be used to create the packfile containing the filtered out objects. WARNING: The specified location should be accessible, using for example the Git alternates mechanism, otherwise the repo could be considered corrupt by Git as it might not be able to access the objects in that packfile. See the --filter-to=<dir> option of git-repack(1) and the objects/info/alternates section of gitrepository-layout(5).

gc.rerereResolved

Records of conflicted merge you resolved earlier are kept for this many days when git rerere gc is run. You can also use more human-readable "1.month.ago", etc. The default is 60 days. See git-rerere(1).

gc.rerereUnresolved

Records of conflicted merge you have not resolved are kept for this many days when git rerere gc is run. You can also use more human-readable "1.month.ago", etc. The default is 15 days. See git-rerere(1).

NOTES

git gc tries very hard not to delete objects that are referenced anywhere in your repository. In particular, it will keep not only objects referenced by your current set of branches and tags, but also objects referenced by the index, remote-tracking branches, reflogs (which may reference commits in branches that were later amended or rewound), and anything else in the refs/* namespace. Note that a note (of the kind created by git notes) attached to an object does not contribute in keeping the object alive. If you are expecting some objects to be deleted and they aren’t, check all of those locations and decide whether it makes sense in your case to remove those references.

On the other hand, when git gc runs concurrently with another process, there is a risk of it deleting an object that the other process is using but hasn’t created a reference to. This may just cause the other process to fail or may corrupt the repository if the other process later adds a reference to the deleted object. Git has two features that significantly mitigate this problem:

1. Any object with modification time newer than the --prune date is kept, along with everything reachable from it.

2. Most operations that add an object to the database update the modification time of the object if it is already present so that #1 applies.

However, these features fall short of a complete solution, so users who run commands concurrently have to live with some risk of corruption (which seems to be low in practice).

HOOKS

The git gc --auto command will run the pre-auto-gc hook. See githooks(5) for more information.
