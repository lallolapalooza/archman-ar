git-cherry(1)

الحزمة: git

التراخيص: GPL-2.0-only

GIT-CHERRY(1) دليل Git GIT-CHERRY(1)

الاسم

git-cherry - البحث عن الالتزامات التي لم يتم تطبيقها بعد على المنبع

ملخص

git cherry [-v] [<upstream> [<head> [<limit>]]]

الوصف

تحديد ما إذا كانت هناك التزامات في <head>..<upstream> مكافئة لتلك الموجودة في النطاق <limit>..<head>.

يعتمد اختبار التكافؤ على الفرق، بعد إزالة المسافات البيضاء وأرقام الأسطر. لذلك، يكتشف git-cherry متى تم "نسخ" الالتزامات عن طريق git-cherry-pick(1)، git-am(1) أو git-rebase(1).

يخرج SHA1 لكل التزام في <limit>..<head>، مسبوقًا بـ - للالتزامات التي لها ما يعادلها في <upstream>، و + للالتزامات التي لا تملك.

خيارات

-v

إظهار مواضيع الالتزام بجوار SHA1s.

<upstream>

فرع المنبع للبحث عن التزامات مكافئة. الافتراضي هو فرع المنبع لـ HEAD.

<head>

فرع العمل؛ الافتراضي هو HEAD.

<limit>

لا تقم بالإبلاغ عن الالتزامات حتى (بما في ذلك) الحد.

أمثلة

سير عمل الرقع

يُستخدم git-cherry بشكل متكرر في سير عمل يعتمد على الرقع (انظر gitworkflows(7)) لتحديد ما إذا كان المراجع العلوي قد طبق سلسلة من الرقع. في سير العمل هذا، قد تقوم بإنشاء وإرسال فرع موضوع مثل هذا:

$ git checkout -b topic origin/master
# العمل وإنشاء بعض الالتزامات
$ git format-patch origin/master
$ git send-email ... 00*

لاحقًا، يمكنك معرفة ما إذا تم تطبيق تغييراتك بقول (لا تزال على topic):

$ git fetch  # تحديث فكرتك عن origin/master
$ git cherry -v

مثال ملموس

في حالة تضمنت الموضوع ثلاثة التزامات، وطبق المراجع اثنين منها، فقد يبدو الوضع كالتالي:

$ git log --graph --oneline --decorate --boundary origin/master...topic
* 7654321 (origin/master) آخر التزام للمنبع
[... اقتطع بعض الالتزامات الأخرى ...]
* cccc111 cherry-pick لـ C
* aaaa111 cherry-pick لـ A
[... اقتطع الكثير مما حدث ...]
| * cccc000 (topic) الالتزام C
| * bbbb000 الالتزام B
| * aaaa000 الالتزام A
|/
o 1234567 نقطة الفرع

في هذه الحالات، يعرض git-cherry ملخصًا موجزًا لما لا يزال يتعين تطبيقه:

$ git cherry origin/master topic
- cccc000... الالتزام C
+ bbbb000... الالتزام B
- aaaa000... الالتزام A

هنا، نرى أن الالتزامين A و C (مميزين بـ -) يمكن إسقاطهما من فرع topic الخاص بك عند إعادة تأسيسه فوق origin/master، بينما الالتزام B (مميز بـ +) لا يزال بحاجة إلى الاحتفاظ به حتى يتم إرساله ليتم تطبيقه على origin/master.

استخدام حد

الـ <limit> الاختياري مفيد في الحالات التي يعتمد فيها موضوعك على عمل آخر غير موجود في المنبع. بالتوسع في المثال السابق، قد يبدو الأمر كالتالي:

$ git log --graph --oneline --decorate --boundary origin/master...topic
* 7654321 (origin/master) آخر التزام للمنبع
[... اقتطع بعض الالتزامات الأخرى ...]
* cccc111 cherry-pick لـ C
* aaaa111 cherry-pick لـ A
[... اقتطع الكثير مما حدث ...]
| * cccc000 (topic) الالتزام C
| * bbbb000 الالتزام B
| * aaaa000 الالتزام A
| * 0000fff (base) أشياء غير منشورة F
[... اقتطع ...]
| * 0000aaa أشياء غير منشورة A
|/
o 1234567 نقطة التقاطع بين المنبع والموضوع

بتحديد base كحد، يمكنك تجنب سرد الالتزامات بين base و topic:

$ git cherry origin/master topic base
- cccc000... الالتزام C
+ bbbb000... الالتزام B
- aaaa000... الالتزام A
