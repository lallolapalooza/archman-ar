git-credential(1)

الحزمة: git

التراخيص: GPL-2.0-only

GIT-CREDENTIAL(1) دليل Git GIT-CREDENTIAL(1)

الاسم

git-credential - استرجاع وتخزين بيانات اعتماد المستخدم

المختصر

'git credential' (fill|approve|reject|capability)

الوصف

يحتوي Git على واجهة داخلية لتخزين واسترجاع بيانات اعتماد المستخدم من أدوات مساعدة خاصة بالنظام، بالإضافة إلى طلب أسماء المستخدمين وكلمات المرور من المستخدم. يعرض أمر git-credential هذه الواجهة للبرامج النصية التي قد ترغب في استرجاع أو تخزين أو طلب بيانات اعتماد بنفس الطريقة التي يستخدمها Git. تصميم واجهة البرمجة النصية هذه يحاكي واجهة برمجة التطبيقات C الداخلية؛ انظر credential.h لمزيد من الخلفية حول المفاهيم.

يأخذ git-credential خيار "action" على سطر الأوامر (واحد من fill، approve، أو reject) ويقرأ وصف بيانات الاعتماد على stdin (انظر تنسيق الإدخال/الإخراج).

إذا كان الإجراء هو fill، فسيحاول git-credential إضافة سمات "username" و "password" إلى الوصف عن طريق قراءة ملفات التكوين، أو عن طريق الاتصال بأي أدوات مساعدة لبيانات الاعتماد المكونة، أو عن طريق مطالبة المستخدم. ثم يتم طباعة سمات اسم المستخدم وكلمة المرور لوصف بيانات الاعتماد إلى stdout مع السمات المقدمة بالفعل.

إذا كان الإجراء هو approve، فسيقوم git-credential بإرسال الوصف إلى أي أدوات مساعدة لبيانات الاعتماد المكونة، والتي قد تقوم بتخزين بيانات الاعتماد للاستخدام لاحقًا.

إذا كان الإجراء هو reject، فسيقوم git-credential بإرسال الوصف إلى أي أدوات مساعدة لبيانات الاعتماد المكونة، والتي قد تقوم بمسح أي بيانات اعتماد مخزنة تطابق الوصف.

إذا كان الإجراء هو capability، فسيقوم git-credential بالإعلان عن أي قدرات يدعمها إلى الإخراج القياسي.

إذا كان الإجراء هو approve أو reject، فلا ينبغي إصدار أي مخرجات.

الاستخدام المعتاد لـ GIT CREDENTIAL

سيستخدم التطبيق الذي يستخدم git-credential عادةً git credential باتباع الخطوات التالية:

1.إنشاء وصف لبيانات الاعتماد بناءً على السياق.

على سبيل المثال، إذا كنا نريد كلمة مرور لـ https://example.com/foo.git، فقد ننشئ وصف بيانات الاعتماد التالي (لا تنسَ السطر الفارغ في النهاية؛ فهو يخبر git credential أن التطبيق قد انتهى من تغذية جميع المعلومات التي يملكها):

protocol=https
host=example.com
path=foo.git
2.طلب من git-credential تزويدنا باسم مستخدم وكلمة مرور لهذا الوصف. يتم ذلك عن طريق تشغيل git credential fill، وتغذية الوصف من الخطوة (1) إلى مدخله القياسي. سيتم إنتاج وصف بيانات الاعتماد الكامل (بما في ذلك بيانات الاعتماد نفسها، أي اسم المستخدم وكلمة المرور) على الإخراج القياسي، مثل:

protocol=https
host=example.com
username=bob
password=secr3t

في معظم الحالات، يعني هذا أن السمات المعطاة في المدخلات ستتكرر في المخرجات، ولكن قد يقوم Git أيضًا بتعديل وصف بيانات الاعتماد، على سبيل المثال عن طريق إزالة سمة path عندما يكون البروتوكول HTTP(s) و credential.useHttpPath هو false.

إذا كان git credential يعرف كلمة المرور، فقد لا تتضمن هذه الخطوة قيام المستخدم بكتابة كلمة المرور فعليًا (قد يكون المستخدم قد كتب كلمة مرور لفتح مفتاح الوصول بدلاً من ذلك، أو لم يتم إجراء أي تفاعل مع المستخدم إذا كان مفتاح الوصول مفتوحًا بالفعل) قبل أن يقوم بإرجاع password=secr3t.

3.استخدام بيانات الاعتماد (على سبيل المثال، الوصول إلى عنوان URL باسم المستخدم وكلمة المرور من الخطوة (2))، ومعرفة ما إذا كان قد تم قبوله.
4.الإبلاغ عن نجاح أو فشل كلمة المرور. إذا سمحت بيانات الاعتماد بإكمال العملية بنجاح، فيمكن تمييزها بإجراء "approve" لإخبار git credential بإعادة استخدامها في استدعائه التالي. إذا تم رفض بيانات الاعتماد أثناء العملية، استخدم إجراء "reject" حتى يطلب git credential كلمة مرور جديدة في استدعائه التالي. في كلتا الحالتين، يجب تغذية git credential بوصف بيانات الاعتماد الذي تم الحصول عليه من الخطوة (2) (الذي يحتوي أيضًا على الحقول المقدمة في الخطوة (1)).

تنسيق الإدخال/الإخراج

يقرأ git credential و/أو يكتب (اعتمادًا على الإجراء المستخدم) معلومات بيانات الاعتماد في مدخله/مخرجه القياسي. يمكن أن تتوافق هذه المعلومات إما مع المفاتيح التي سيحصل git credential على معلومات تسجيل الدخول لها (على سبيل المثال، المضيف، البروتوكول، المسار)، أو مع بيانات الاعتماد الفعلية المراد الحصول عليها (اسم المستخدم/كلمة المرور).

تنقسم بيانات الاعتماد إلى مجموعة من السمات المسماة، مع سمة واحدة لكل سطر. يتم تحديد كل سمة بزوج مفتاح-قيمة، مفصول بـ = (علامة يساوي)، متبوعًا بسطر جديد.

يمكن أن يحتوي المفتاح على أي بايتات باستثناء =، سطر جديد، أو NUL. يمكن أن تحتوي القيمة على أي بايتات باستثناء سطر جديد أو NUL. قد لا يتجاوز طول السطر، بما في ذلك سطر النهاية الجديد، 65535 بايت للسماح للتطبيقات بالتفسير بكفاءة.

السمات ذات المفاتيح التي تنتهي بأقواس مصفوفة بأسلوب C [] يمكن أن تحتوي على قيم متعددة. يشكل كل مثيل لسمة متعددة القيم قائمة مرتبة من القيم - يحدد ترتيب السمات المتكررة ترتيب القيم. تعمل السمة متعددة القيم الفارغة (key[]=\n) على مسح أي إدخالات سابقة وإعادة تعيين القائمة.

في جميع الحالات، يتم التعامل مع جميع البايتات كما هي (أي، لا يوجد اقتباس، ولا يمكن نقل قيمة تحتوي على سطر جديد أو NUL). يتم إنهاء قائمة السمات بسطر فارغ أو نهاية الملف.

يفهم Git السمات التالية:

protocol

البروتوكول الذي سيتم استخدامه لبيانات الاعتماد (على سبيل المثال، https).

host

اسم المضيف البعيد لبيانات اعتماد الشبكة. يشمل هذا رقم المنفذ إذا تم تحديده (على سبيل المثال، "example.com:8088").

path

المسار الذي سيتم استخدامه مع بيانات الاعتماد. على سبيل المثال، للوصول إلى مستودع https بعيد، سيكون هذا مسار المستودع على الخادم.

username

اسم مستخدم بيانات الاعتماد، إذا كان لدينا واحد بالفعل (على سبيل المثال، من عنوان URL، أو التكوين، أو المستخدم، أو من مساعد تم تشغيله سابقًا).

password

كلمة مرور بيانات الاعتماد، إذا كنا نطلب تخزينها.

password_expiry_utc

قد تحتوي كلمات المرور التي تم إنشاؤها مثل رمز وصول OAuth على تاريخ انتهاء. عند قراءة بيانات الاعتماد من أدوات المساعدة، يتجاهل git credential fill كلمات المرور منتهية الصلاحية. ممثلة كـ Unix time UTC، بالثواني منذ عام 1970.

oauth_refresh_token

قد يرافق رمز تحديث OAuth كلمة مرور هي رمز وصول OAuth. يجب على الأدوات المساعدة التعامل مع هذه السمة كمعلومة سرية مثل سمة كلمة المرور. لا يمتلك Git نفسه سلوكًا خاصًا لهذه السمة.

url

عند قراءة هذه السمة الخاصة بواسطة git credential، يتم تحليل القيمة كعنوان URL ويتم التعامل معها كما لو تم قراءة أجزائها المكونة (على سبيل المثال، url=https://example.com سيتصرف كما لو تم تقديم protocol=https و host=example.com). يمكن أن يساعد هذا المتصلين على تجنب تحليل عناوين URL بأنفسهم.

لاحظ أن تحديد بروتوكول إلزامي، وإذا لم يحدد عنوان URL اسم مضيف (على سبيل المثال، "cert:///path/to/file")، فستحتوي بيانات الاعتماد على سمة مضيف بقيمة سلسلة فارغة.

المكونات المفقودة من عنوان URL (على سبيل المثال، لا يوجد اسم مستخدم في المثال أعلاه) ستظل غير محددة.

authtype

يشير هذا إلى أنه يجب استخدام مخطط المصادقة المعني. تشمل القيم الشائعة لـ HTTP و HTTPS basic و bearer و digest، على الرغم من أن الأخير غير آمن ويجب عدم استخدامه. إذا تم استخدام credential، فقد يتم تعيين هذا إلى سلسلة عشوائية مناسبة للبروتوكول المعني (عادةً HTTP).

لا ينبغي إرسال هذه القيمة إلا إذا تم توفير القدرة المناسبة (انظر أدناه) في المدخلات.

credential

بيانات الاعتماد المشفرة مسبقًا، مناسبة للبروتوكول المعني (عادةً HTTP). إذا تم إرسال هذا المفتاح، فإن authtype إلزامي، ولا يتم استخدام username و password. بالنسبة لـ HTTP، يقوم Git بدمج قيمة authtype وهذه القيمة بمسافة واحدة لتحديد رأس Authorization
