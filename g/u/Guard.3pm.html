Guard(3pm)

الحزمة: perl-guard

التراخيص: GPL, PerlArtistic

Guard(3) وثائق Perl المساهمة من المستخدم Guard(3)

الاسم

Guard - عمليات تنظيف آمنة

الملخص

use Guard;

# قم بتغيير الدليل مؤقتًا إلى الدليل "/etc"، ولكن تأكد من
# العودة إلى "/" بغض النظر عن كيفية انتهاء myfun:
sub myfun {
   scope_guard { chdir "/" };
   chdir "/etc";

   code_that_might_die_or_does_other_fun_stuff;
}
# أنشئ كائنًا، عند اختفاء آخر مرجع إليه،
# يستدعي كتلة الكود المعطاة:
my $guard = guard { print "destroyed!\n" };
undef $guard; # ربما تم تدميره هنا

الوصف

تطبق هذه الوحدة ما يسمى بـ "الحراس" (guards). الحارس هو شيء (عادة كائن) "يحرس" موردًا، مما يضمن تنظيفه عند المتوقع.

على وجه التحديد، تدعم هذه الوحدة نوعين مختلفين من الحراس: كائنات الحراسة، التي تنفذ كتلة كود معينة عند تدميرها، وحراس النطاق، التي ترتبط بانتهاء النطاق.

الوظائف

تُصدّر هذه الوحدة حاليًا الوظيفتين "scope_guard" و "guard" افتراضيًا.

scope_guard BLOCK
scope_guard ($coderef)
تسجل كتلة يتم تنفيذها عند انتهاء النطاق الحالي (كتلة، دالة، طريقة، تقييم، إلخ).

انظر قسم الاستثناءات لشرح كيفية التعامل مع الاستثناءات (أي "die") داخل كتل الحراسة.

الوصف أدناه يبدو معقدًا بعض الشيء، ولكن هذا فقط لأن "scope_guard" يحاول الحصول على حتى الحالات القصوى "بشكل صحيح": الهدف هو تزويدك بأداة تنظيف قوية.

السلوك مشابه لمقتطف الكود هذا:

eval ... code following scope_guard ...
{
   local $@;
   eval BLOCK;
   eval { $Guard::DIED->() } if $@;
}
die if $@;

باستثناء أنها أسرع بكثير، ويتم تنفيذ كل شيء حتى عندما تستدعي الكتلة "exit" أو "goto" أو "last" أو تهرب بطرق أخرى.

إذا تم تسجيل كتل متعددة لنفس النطاق، فسيتم تنفيذها بترتيب عكسي. يتم إدارة أشياء أخرى متعلقة بالنطاق مثل "local" عبر نفس الآلية، لذلك سيتم استعادة المتغيرات التي تم جعلها "local" *بعد* استدعاء "scope_guard" عند تشغيل الحارس.

مثال: تغيير المنطقة الزمنية مؤقتًا للعملية الحالية، مع ضمان إعادة تعيينها عند انتهاء نطاق "if":

use Guard;
use POSIX ();
if ($need_to_switch_tz) {
   # تأكد من استدعاء tzset بعد استعادة $ENV{TZ}
   scope_guard { POSIX::tzset };
   # اجعل محليًا بعد scope_guard، لذلك سيتم إلغاؤه في الوقت المناسب
   local $ENV{TZ} = "Europe/London";
   POSIX::tzset;
   # افعل شيئًا بالمنطقة الزمنية الجديدة
}
my $guard = guard BLOCK
my $guard = guard ($coderef)
يتصرف بنفس طريقة "scope_guard"، باستثناء أنه بدلاً من تنفيذ الكتلة عند انتهاء النطاق، فإنه يعيد كائنًا يحدد عمره وقت تنفيذ الكتلة: عند تدمير آخر مرجع للكائن، يتم تنفيذ الكتلة كما هو الحال مع "scope_guard".

انظر قسم الاستثناءات لشرح كيفية التعامل مع الاستثناءات (أي "die") داخل كتل الحراسة.

مثال: اكتساب Coro::Semaphore لمدة ثانية عن طريق تسجيل مؤقت. دالة رد استدعاء المؤقت تشير إلى الحارس المستخدم لإلغاء قفله مرة أخرى. (يرجى تجاهل حقيقة أن "Coro::Semaphore" لديه طريقة "guard" تقوم بذلك بالفعل):

use Guard;
use Coro::AnyEvent;
use Coro::Semaphore;
my $sem = new Coro::Semaphore;
sub lock_for_a_second {
   $sem->down;
   my $guard = guard { $sem->up };
   Coro::AnyEvent::sleep 1;
   # سيتم تنفيذ $sem->up عند العودة
}

الميزة في القيام بذلك مع حارس بدلاً من مجرد استدعاء "$sem->down" في دالة رد الاستدعاء هي أنه يمكنك اختيار عدم إنشاء المؤقت، أو يمكن للكود الخاص بك إلقاء استثناء قبل أن يتمكن من إنشاء المؤقت (أو تم إلغاء الخيط)، أو يمكنك إنشاء مؤقتات متعددة أو مشاهدات أحداث أخرى وفقط عندما يتم تنفيذ آخرها سيتم فتح القفل. باستخدام "guard"، لا داعي للقلق بشأن التقاط جميع الأماكن التي يجب عليك فيها فتح قفل السيمفور.

$guard->cancel
سيؤدي استدعاء هذه الوظيفة إلى "تعطيل" كائن الحارس الذي أعادته وظيفة "guard"، أي أنه سيحرر الكتلة التي تم تمريرها أصلاً إلى "guard" وسيرتب بحيث لا يتم تنفيذ الكتلة.

يمكن أن يكون هذا مفيدًا عندما تستخدم "guard" لإنشاء معالج تنظيف ليتم استدعاؤه في ظروف كارثية وتقرر لاحقًا أنه لم يعد ضروريًا.

الاستثناءات

لا ينبغي لكتل الحراسة أن تلقي استثناءات بشكل طبيعي (أي "die"). في النهاية، يتم استخدامها عادة للتنظيف بعد مثل هذه الاستثناءات. ومع ذلك، إذا كان هناك شيء استثنائي حقًا يحدث، فيجب بالطبع السماح لكتلة الحراسة بالموت. أيضًا، أخطاء البرمجة هي مصدر كبير للاستثناءات، والمبرمج بالتأكيد يريد معرفة تلك الأخطاء.

نظرًا لأنه في معظم الحالات، الكتلة التي يتم تنفيذها عندما يتم تنفيذ الحارس لا تعرف أو لا تهتم بكتل الحراسة، فإنه لا معنى له تقريبًا للسماح للكود الحاوي بمعالجة الاستثناء.

لذلك، كلما ألقت كتلة حراسة استثناءً، سيتم التقاطها بواسطة Guard، يليه استدعاء مرجع الكود المخزن في $Guard::DIED (مع تعيين $@ إلى الاستثناء الفعلي)، وهو مشابه لكيفية تعامل معظم حلقات الأحداث مع هذه الحالة.

القيمة الافتراضية لـ $Guard::DIED هي استدعاء "warn "$@""، أي يتم طباعة الخطأ كتحذير ويستمر البرنامج.

سيتم استعادة المتغير $@ إلى قيمته قبل استدعاء الحارس في جميع الحالات، لذلك لن تزعج الحراس $@ بأي شكل من الأشكال.

مرجع الكود المخزن في $Guard::DIED لا ينبغي أن يموت (السلوك غير مضمون، ولكن في الوقت الحالي، سيتم تجاهل الاستثناء ببساطة).

شكر

شكرًا لـ Marco Maisenhelder، الذي ذكّرني بحل $Guard::DIED لمشكلة الاستثناءات.

انظر أيضًا

Scope::Guard و Sub::ScopeFinalizer، التي تنفذ بالفعل حراس النطاق الديناميكي فقط، وليس حراس النطاق المعجمي التي تعد بها وثائقها، ولديها نفقات أعلى بكثير لوحدة المعالجة المركزية والذاكرة والكتابة.

Hook::Scope، الذي لم يكتمل على ما يبدو ويمكن أن يفسد الذاكرة عند استخدامه.

يبدو أن Scope::Guard يحتوي على قسم كبير من "انظر أيضًا" لمزيد من الوحدات المشابهة له.
