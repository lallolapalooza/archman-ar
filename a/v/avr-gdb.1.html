NAME

avr-gdb — The GNU Project Debugger

SYNOPSIS

gdb [ -b baudrate ] [ -d directory ] [ -s symfile ] [ -se symfile ] [ -c corefile ] [ --core=corefile ] [ -ex binh ] [ -ex command ] [ -i subcommand ] [ -m ] [ -n ] [ -q ] [ --quiet ] [ -batch ] [ --batch-silent ] [ --args prog [ arglist ... ] ] [ --pid=pid ] [ --tui ] [ --readnow ] [ --readnever ] [ --return-child-result ] [ --configuration ] [ --version ] [ --cd=directory ] [ --data-directory=directory ] [ -D ] [ --fullname ] [ -f ] [ -l timeout ] [ --tty=device ] [ --help ] [ program [ args ... ] ] [ corefile ]

DESCRIPTION

GDB is a source-level debugger. You can use it to see what is going on inside another program while it executes or what the other program was doing at the time it crashed. The activity might be happening on another machine, or your own, or inside a stripped binary that seems to have no information about its run-time activities.

GDB can be used to debug programs written in C, C++, Ada, Pascal, Fortran, Objective-C, Assembly, and many other languages.

GDB allows you to:

  • Start your program, specifying anything that might affect its behavior
  • Make your program take a specific conditional action when some condition occurs
  • Examine what has happened when the program has stopped
  • Change things in your program so you can continue to experiment with correcting the effects of one bug and go on to learn about another.

As well as these things, GDB also provides commands for more complex debugging tasks, such as debugging heavily-used library code, or even debugging GDB itself.

GDB has a customizable user interface. It can be operated in two modes: the command-line interface (CLI) and the terminal user interface (TUI). The TUI mode is a more graphical interface, consisting of two sections: one for source code display and another for command input and command output.

OPTIONS

-s symfile
Read symbol table from symfile.
-se symfile
Read symbol table from symfile and also use symfile as the program to execute.
-c corefile
Use corefile as the core dump to examine.
--core=corefile
Use corefile as the core dump to examine.
-ex command
Execute command using GDB's command reader. This is useful for running a script of GDB commands. You can use multiple -ex options to specify multiple commands.
-i subcommand
Run the specified GDB subcommand.
-m
Set the memory map of the core file. GDB will ask you for the memory map.
-n
Do not read the user init file (~/.gdbinit).
-q
Quiet mode. Do not print the usual GDB version and copyright notice.
--batch
Run in batch mode. GDB will exit after processing all script commands. This is useful for analyzing core dumps or for running GDB in a shell script. The default behavior in batch mode is to read commands from standard input and write output to standard error. The output includes all GDB output, including the prompt and messages such as 
Program exited normally.
(which is ordinarily issued whenever a program running under GDB control terminates) is not issued when running in batch mode.

This option is useful for automating tasks, like downloading and running a program on another computer; in order to make this more useful, the message

Program exited normally.

(which is ordinarily issued whenever a program running under GDB control terminates) is not issued when running in batch mode.

--batch-silent
Run in batch mode, just like --batch, but totally silent. All GDB output is suppressed (stderr is unaffected). This is much quieter than --silent and would be useless for an interactive session.

This is particularly useful when using targets that give Loading section messages, for example.

Note that targets that give their output via GDB, as opposed to writing directly to "stdout", will also be made silent.

--args prog [arglist]
Change interpretation of command line so that arguments following this option are passed as arguments to the inferior. As an example, take the following command: 
gdb ./a.out -q

It would start GDB with -q, not printing the introductory message. On the other hand, using:

gdb --args ./a.out -q

starts GDB with the introductory message, and passes the option to the inferior.

--pid=pid
Attach GDB to an already running program, with the PID pid.
--tui
Open the terminal user interface.
--readnow
Read all symbols from the given symfile on the first access.
--readnever
Do not read symbol files.
--return-child-result
GDB's exit code will be the same as the child's exit code.
--configuration
Print details about GDB configuration and then exit.
--version
Print version information and then exit.
--cd=directory
Run GDB using directory as its working directory, instead of the current directory.
--data-directory=directory
-D
Run GDB using directory as its data directory. The data directory is where GDB searches for its auxiliary files.
--fullname
-f
Emacs sets this option when it runs GDB as a subprocess. It tells GDB to output the full file name and line number in a standard, recognizable fashion each time a stack frame is displayed (which includes each time the program stops). This recognizable format looks like two \032 characters, followed by the file name, line number and character position separated by colons, and a newline. The Emacs-to-GDB interface program uses the two \032 characters as a signal to display the source code for the frame.
-b baudrate
Set the line speed (baud rate or bits per second) of any serial interface used by GDB for remote debugging.
-l timeout
Set timeout, in seconds, for remote debugging.
--tty=device
Run using device for your program's standard input and output.

SEE ALSO

The full documentation for GDB is maintained as a Texinfo manual. If the "info" and "gdb" programs and GDB's Texinfo documentation are properly installed at your site, the command

info gdb

should give you access to the complete manual.
