الاسم

tup - أداة التحديث

الملخص

tup [--debug-sql] [--debug-fuse] [أمر_ثانوي] [وسائط]

الوصف

Tup هو نظام بناء يعتمد على الملفات. يجب عليك استخدام tup إذا كنت تقوم بتطوير برامج تحتاج إلى الترجمة من ملفات الإدخال (التي تكتبها) إلى تنسيق إخراج مختلف. على سبيل المثال، إذا كنت تكتب برنامجًا بلغة C، يمكنك استخدام tup لتحديد الملفات التي تحتاج إلى إعادة تجميعها أو أرشفتها أو ربطها بناءً على رسم بياني للاعتمادية.

لا يمتلك Tup معرفة خاصة بالمجال. يجب عليك إخبار tup بكيفية بناء برنامجك، مثل القول بأن جميع ملفات .c يتم تحويلها إلى ملفات .o باستخدام gcc. يتم ذلك عن طريق كتابة ملف Tupfile واحد أو أكثر.

الأمر الأساسي: tup

يمكنك القيام بكل التطوير الخاص بك باستخدام 'tup' فقط، بالإضافة إلى كتابة Tupfiles. انظر أيضًا أقسام ملف INI و ملفات الخيارات و TUPFILES أدناه.

tup [<output_1> ... <output_n>]
يقوم بتحديث مجموعة المخرجات بناءً على رسم بياني للاعتمادية والحالة الحالية لنظام الملفات. إذا لم يتم تحديد أي مخرجات، فسيتم تحديث المشروع بالكامل. هذا هو ما تشغله في كل مرة تقوم فيها بتغييرات على برنامجك لتحديثه. يمكنك تشغيل هذا في أي مكان في التسلسل الهرمي لـ tup، وسيقوم دائمًا بتحديث الإخراج المطلوب. افتراضيًا، يتم تحديد قائمة الملفات التي تم تغييرها عن طريق مسح نظام الملفات والتحقق من أوقات التعديل. بالنسبة للمشاريع الكبيرة جدًا، قد يكون هذا بطيئًا، ولكن يمكنك تخطي وقت المسح عن طريق تشغيل مراقب الملفات (انظر أوامر ثانوية لوصف المراقب).
-jN
تجاوز مؤقتًا خيار updater.num_jobs إلى 'N'. سيؤدي هذا إلى تشغيل ما يصل إلى N مهمة بالتوازي، مع مراعاة قيود DAG. مثال: 'tup -j2' سيشغل ما يصل إلى مهمتين بالتوازي، بينما 'tup' سيشغل ما يصل إلى updater.num_jobs بالتوازي. انظر أمر الخيار الثانوي أدناه.
--verbose
يجعل tup يعرض سلسلة الأوامر الكاملة بدلاً من السلسلة المنسقة فقط للأوامر التي تستخدم البادئة ^ TEXT^.
--quiet
تجاوز مؤقتًا خيار display.quiet إلى '1'. انظر أمر الخيار الثانوي أدناه.
-k
--keep-going
تجاوز مؤقتًا خيار updater.keep_going إلى '1'. انظر أمر الخيار الثانوي أدناه.
--no-keep-going
تجاوز مؤقتًا خيار updater.keep_going إلى '0'. انظر أمر الخيار الثانوي أدناه.
--no-scan
لا تقم بمسح المشروع بحثًا عن الملفات التي تم تغييرها. هذا للاختبار الداخلي لـ tup فقط، ولا ينبغي استخدامه أثناء التطوير العادي.
--no-environ-check
لا تقم بالتحقق من تحديثات متغيرات البيئة المصدرة للعمليات الفرعية. بدلاً من ذلك، سيتم استخدام متغيرات البيئة من قاعدة البيانات. يستخدم هذا بواسطة المراقب في وضع autoupdate/autoparse بحيث يتم استخدام أحدث متغيرات البيئة، بدلاً من الإعدادات عند تهيئة المراقب.
-d
إخراج سجل التصحيح إلى الشاشة.
--debug-run
إخراج القواعد :- التي تم إنشاؤها بواسطة نص برمجي تشغيل. انظر ميزة 'run ./script args' في قسم TUPFILES. --debug-logging حفظ بعض سجلات التصحيح ورسم بياني للبناء في .tup/log. يتم تدوير الرسوم البيانية عند كل استدعاء مع --debug-logging.

أوامر ثانوية

تستخدم هذه الأوامر لتعديل سلوك tup أو النظر في داخلياته. ربما لن تحتاج هذه الأوامر كثيرًا. يتم استدعاء الأوامر الثانوية كالتالي:

tup [--debug-sql] [--debug-fuse] أمر_ثانوي [وسائط_الأمر_الثانوي]

init [دليل]
ينشئ دليل '.tup' في الدليل المحدد ويقوم بتهيئة قاعدة بيانات tup. إذا لم يتم تحديد اسم دليل، فسيتم افتراضي إنشاء '.tup' في الدليل الحالي. هذا يحدد قمة مشروعك، كما يراها tup. كل شيء في الدليل الحالي ودلائله الفرعية يُعرف بـ "التسلسل الهرمي لتوب".

إذا كنت ترغب في تجنب الاضطرار إلى تشغيل 'tup init' في كل مرة تقوم فيها بنسخ مستودعك إلى موقع جديد، يمكنك بدلاً من ذلك إنشاء ملف فارغ يسمى 'Tupfile.ini' في جذر المشروع. إذا تم تشغيل 'tup' بدون وجود الدليل '.tup'، فسيقوم تلقائيًا بإنشاء واحد كشريك للملف Tupfile.ini، كما لو كنت قد قمت بتشغيل 'tup init' في هذا الدليل. إذا كانت هناك ملفات Tupfile.ini متعددة في المسارات الأصل، فسيتم اختيار الملف الأعلى في الشجرة.

--no-sync
يضبط خيار 'db.sync' للمشروع على '0'. افتراضيًا، سيتم ضبط خيار 'db.sync' على '1'. يستخدم هذا العلم في الغالب لحالات الاختبار، ولكن يمكنك أيضًا استخدامه في أي بيئة تريد فيها كتابة نصوص tup البرمجية ولا تستخدم المزامنة افتراضيًا.
refactor
ref
يمكن استخدام أمر refactor للمساعدة في إعادة هيكلة Tupfiles. سيؤدي هذا إلى تشغيل tup خلال مرحلة التحليل، ولكن لن يتم تنفيذ أي أوامر. إذا كانت أي ملفات Tupfiles تم تحليلها تؤدي إلى تغييرات في قاعدة البيانات، فستتم الإبلاغ عن هذه كأخطاء. على سبيل المثال، قد يكون لدينا Tupfile البسيط التالي: 
: foreach *.c |> gcc -c %f -o %o -Wall |> %B.o

بعد تشغيل 'tup' الأولي، نقرر أننا نريد نقل -Wall إلى متغير يسمى CFLAGS. الآن يبدو Tupfile كالتالي:

CFLAGS = -Wall
: foreach *.c |> gcc -c %f -o %o $(CFLAGS) |> %B.o

سيؤدي تشغيل 'tup refactor' إلى تحليل tup للملف Tupfile، وإذا ارتكبنا أي أخطاء، فسيتم عرض رسالة خطأ. يمكن بعد ذلك تعديل ملفات Tupfiles لإصلاح هذه الأخطاء، والاستمرار في تشغيل 'tup refactor' حتى يتم تحليل جميع ملفات Tupfiles بنجاح.

يتم الإبلاغ عن الأخطاء عند إضافة أو إزالة أي مما يلي: الأوامر، الإدخالات التي تم إنشاؤها، المخرجات، التوجيه .gitignore، <مجموعات> الإدخال أو الإخراج، واعتماديات مستوى الدليل. بخلاف ذلك، يمكنك نقل أي سلاسل إلى متغيرات $-، وماكرو !-، وما شابه، طالما أن النتيجة النهائية لمجموعة قواعد :- هي نفسها.

monitor
*Linux فقط* يبدأ مراقب الملفات القائم على inotify. يجب أن يقوم المراقب بمسح نظام الملفات مرة واحدة وتهيئة المشاهدات على كل دليل. ثم عندما تقوم بتغييرات على الملفات، سيرى المراقب هذه التغييرات ويكتبها مباشرة في قاعدة البيانات. مع تشغيل المراقب، لا يحتاج 'tup' إلى إجراء المسح الأولي، ويمكنه البدء في بناء رسم بياني للبناء على الفور. وقت "مسح نظام الملفات..." من 'tup' يساوي تقريبًا الوقت الذي ستوفره عن طريق تشغيل المراقب. عند تشغيل المراقب، يجب أن يستغرق 'tup' بدون تغييرات في الملفات بضع مللي ثوانٍ (على أجهزتي أحصل على حوالي 2 أو 3 مللي ثانية عندما تكون كل شيء في ذاكرة التخزين المؤقت للقرص). إذا أعدت تشغيل جهاز الكمبيوتر الخاص بك، فستحتاج إلى إعادة تشغيل المراقب. يمكن إعطاء الوسائط التالية في سطر الأوامر. سيتم تمرير أي وسائط إضافية لا يتعامل معها المراقب إلى أداة التحديث إذا تم تمكين monitor.autoupdate أو monitor.autoparse. على سبيل المثال، يمكنك تشغيل المراقب كـ 'tup monitor -f -a -j2' لتشغيل المراقب في المقدمة، وتحديث تلقائي بمهمتين عند اكتشاف التغييرات. انظر أيضًا أمر الخيار الثانوي أدناه.
-d
تمكين تصحيح عملية المراقب.
-f
--foreground
تجاوز مؤقتًا monitor.foreground
--foreground
Temporarily override the monitor.foreground option to 1. The monitor will run in the foreground (don't daemonize).
-b
--background
Temporarily override the monitor.foreground option to 0. The monitor will run in the background (daemonize).
-a
--autoupdate
Temporarily override the monitor.autoupdate option to 1. This will automatically run an update when file changes are detected.
-n
--no-autoupdate
Temporarily override the monitor.autoupdate option to 0. This will prevent the monitor from automatically running an update when file changes are detected.
--autoparse
Temporarily override the monitor.autoparse option to 1. This will automatically run the parser when file changes are detected.
--no-autoparse
Temporarily override the monitor.autoparse option to 0. This will prevent the monitor from automatically running the parser when file changes are detected.
stop
يقوم بإيقاف المراقب إذا كان يعمل. هذا يوفر عليك عناء البحث عن معرف العملية (PID) وإيقافها بهذه الطريقة.
variant foo.config [bar.config] [...]
لكل وسيط، يقوم هذا الأمر بإنشاء دليل متغير مع ربط tup.config بملف التكوين المحدد. على سبيل المثال، إذا احتوى دليل على عدة تكوينات متغيرة، يمكن للمرء بسهولة إنشاء متغير لكل ملف تكوين: 
$ ls configs/
bar.config
foo.config
$ tup variant configs/*.config
tup: Added variant 'build-bar' using config file 'configs/bar.config'
tup: Added variant 'build-foo' using config file 'configs/foo.config'

هذا يعادل ما يلي:

$ mkdir build-bar
$ ln -s ../configs/bar.config build-bar/tup.config
$ mkdir build-foo
$ ln -s ../configs/foo.config build-foo/tup.config

بالنسبة للمشاريع التي تستخدم عدة متغيرات بشكل شائع، يمكن حفظ الملفات الموجودة في الدليل configs/ في نظام التحكم بالمصادر. سيقوم كل مطور بتشغيل 'tup variant' بعد 'tup init' أثناء الاستنساخ الأولي للبرنامج. يمكن أيضًا إنشاء المتغيرات يدويًا عن طريق إنشاء دليل بناء وإنشاء ملف tup.config فيه (انظر قسم VARIANTS). هذا الأمر يوفر بعض الخطوات فقط، بحيث لا تضطر إلى إنشاء كل دليل بناء ورابط tup.config يدويًا.

dbconfig
يعرض تكوين قاعدة بيانات tup الحالية. هذه هي القيم الداخلية التي يستخدمها tup.
options
يعرض جميع خيارات tup الحالية، وكذلك مصدرها.

للحصول على تفاصيل حول جميع الخيارات المتاحة وكيفية تعيينها، راجع قسم OPTIONS FILES أدناه.

graph [--dirs] [--ghosts] [--env] [--combine] [--stickies] [<output_1> ... <output_n>]
يطبع رسم بياني بتنسيق graphviz .dot لقاعدة بيانات tup إلى المخرج القياسي. بشكل افتراضي، يعرض فقط أجزاء الرسم البياني التي تحتوي على تغييرات. إذا قمت بتوفير وسائط إضافية، فيفترض أنها ملفات تريد رسمها. يعمل هذا مباشرة على قاعدة بيانات tup، لذلك ما لم تكن تشغل مراقب الملفات، قد ترغب في تشغيل 'tup scan' أولاً. يستخدم هذا بشكل عام لتصحيح أخطاء tup - قد تجده مفيدًا أو لا لمحاولة النظر في بنية برنامجك.
--dirs
يتجاوز مؤقتًا خيار graph.dirs إلى '1'. سيؤدي ذلك إلى إظهار عقد الدلائل وملفات Tupfiles.
--ghosts
يتجاوز مؤقتًا خيار graph.ghosts إلى '1'. سيؤدي ذلك إلى إظهار العقد الوهمية (الملفات التي حاول أمر الوصول إليها، ولكنها غير موجودة بالفعل).
--env
يتجاوز مؤقتًا خيار graph.environment إلى '1'. سيؤدي ذلك إلى إظهار متغيرات البيئة، مثل PATH.
todo [<output_1> ... <output_n>]
يطبع الخطوات التالية في عملية tup التي سيتم تنفيذها عند تحديث المخرجات المحددة. إذا لم يتم تحديد مخرجات، فإنه يطبع الخطوات اللازمة لتحديث المشروع بأكمله. على غرار أمر 'upd'، سيقوم 'todo' بفحص المشروع تلقائيًا بحثًا عن تغييرات الملفات إذا لم يكن مراقب الملفات قيد التشغيل.
--no-scan
لا تقم بفحص المشروع بحثًا عن الملفات المتغيرة. هذا مخصص فقط لاختبارات tup الداخلية، ولا ينبغي استخدامه أثناء التطوير العادي.
--verbose
يتسبب في قيام tup بعرض سلسلة الأوامر الكاملة بدلاً من مجرد سلسلة الأحرف المنسقة للأوامر التي تستخدم البادئة ^ TEXT^.
generate [--config config-file] [--builddir directory] script.sh (or script.bat on Windows) [<output_1> ... <output_n>]
يقوم أمر generate بتحليل جميع ملفات Tupfiles وإنشاء نص برمجي يمكنه بناء البرنامج دون التشغيل في بيئة tup. الاستخدام المتوقع هو في بيئات التكامل المستمر التي لا تتوافق مع التحقق من التبعيات الخاصة بـ tup (مثل: إذا لم يكن FUSE مدعومًا). على نظام Windows، إذا كان اسم ملف البرنامج النصي له امتداد ".bat"، فسيكون الإخراج نصًا برمجيًا للدُفعات بدلاً من نص برمجي للشل. على سبيل المثال: 
git clone ... myproj
cd myproj
tup generate build.sh
./build.sh
# Copy out build artifacts / logs here
git clean -f -x -d
النص البرمجي للشل لا يعمل بشكل تزايدي، لذا فهو للاستخدام مرة واحدة بشكل فعال. ستحتاج إلى تنظيف الشجرة قبل 'tup generate' التالي واستدعاء البرنامج النصي. بشكل افتراضي، يستخدم ملف tup.config العلوي لتحديد متغيرات التكوين. اختياريًا، يمكن تمرير ملف تكوين منفصل باستخدام الوسيط --config.

إذا تم تحديد وسيط --builddir، يتم إنشاء النص البرمجي للشل كما لو كان بناءً متغيرًا. يتم وضع جميع مخرجات البناء في الدليل المحدد. بخلاف ذلك، يكون السلوك الافتراضي هو وضع جميع مخرجات البناء داخل الشجرة. يجب ألا يكون دليل البناء موجودًا بالفعل في الشجرة.

بعد اسم البرنامج النصي، يمكن سرد ملفات المخرجات الفردية للحد من نطاق البرنامج النصي للشل لبناء تلك المخرجات فقط. إذا لم يتم سرد أي مخرجات، فسيقوم البرنامج النصي للشل ببناء جميع المخرجات.


compiledb
ينشئ أمر compiledb ملف compile_commands.json للاستخدام مع أدوات الطرف الثالث التي تستخدم هذا الملف كمرجع لتحديد كيفية تجميع الملفات. يتم إنشاء الملف في الجزء العلوي من تسلسل هرمي لـ tup، أو إذا كنت تستخدم متغيرات، فكل متغير يحصل على ملف compile_commands.json الخاص به في جذر المتغير. يجب عليك وضع علامة على الملفات التي تريد تصديرها باستخدام العلامة ^j. على سبيل المثال، يمكنك إضافة العلامة ^j إلى استدعاءات المترجم الخاصة بك: 
: foreach *.c |> ^j^ gcc -c %f -o %o |> %B.o

يقوم tup بتحليل أي ملفات Tupfiles قديمة تلقائيًا (مكافئ لـ 'tup parse') قبل إنشاء قاعدة البيانات.

نظرًا للتكلفة الباهظة لتحديث compile_commands.json مع المشاريع الكبيرة، لا يتم تحديث الملف تلقائيًا عندما تتغير ملفات Tupfiles. يجب عليك إعادة تشغيل 'tup compiledb' يدويًا عندما تريد إصدارًا محدثًا.

لسحب أحدث سطر أوامر مباشرة من قاعدة البيانات بدلاً من استخدام compile_commands.json كوسيط، راجع أمر 'commandline'.

انظر أيضًا: https://clang.llvm.org/docs/JSONCompilationDatabase.html


commandline <file_1> [<file_2> ... <file_n>]
سيقوم أمر commandline بطباعة المعلومات اللازمة لتجميع اسم الملف المقدم كوسيط. يتم طباعة المعلومات إلى المخرج القياسي بنفس تنسيق JSON مثل ملف compile_commands.json من 'tup compiledb'. لاحظ أنه مقارنة بأمر compiledb، فإن 'tup commandline' لا يقوم بتحليل ملفات Tupfiles تلقائيًا قبل محاولة العثور على الأمر. هذا يستعلم مباشرة عن قاعدة البيانات.

كمثال على كيفية استخدام هذا، راجع ملف .ycm_extra_conf.py الموجود في جذر مستودع tup git: https://github.com/gittup/tup/


varsed
يستخدم أمر varsed كبرنامج فرعي في Tupfile؛ لن تقوم بتشغيله يدويًا من سطر الأوامر. يستخدم لقراءة ملف واحد، واستبدال أي مراجع متغير وكتابة الإخراج إلى ملف ثانٍ. مراجع المتغيرات هي من النموذج @VARIABLE@، ويتم استبدالها بالقيمة المقابلة للمتغير @. على سبيل المثال، إذا احتوى foo.txt على: 
The architecture is set to @ARCH@
وكان لديك قاعدة :-rule في Tupfile على النحو التالي: 
: foo.txt |> tup varsed %f %o |> foo-out.txt
فعند التحديث، سيكون ملف الإخراج مطابقًا للملف الإدخال، باستثناء أن السلسلة @ARCH@ سيتم استبدالها بما هو معين لـ CONFIG_ARCH في tup.config. يضيف أمر varsed تلقائيًا تبعية من CONFIG_ARCH إلى عقدة الأمر المحددة التي استخدمتها (لذا إذا تغير CONFIG_ARCH، فسيتم تحديث ملف الإخراج بالقيمة الجديدة).
scan
لا ينبغي عليك تشغيل هذا أبدًا، إلا إذا كنت ترغب في جعل قاعدة البيانات تعكس نظام الملفات قبل تشغيل 'tup graph'. يتم استدعاء Scan تلقائيًا بواسطة 'upd' إذا لم يكن المراقب قيد التشغيل.
upd
أمر ثانوي قديم. استدعاء 'tup upd' يعادل استدعاء 'tup' ببساطة.

ملف INI

يمكن تشغيل أمر tup من أي مكان في شجرة المصدر. يستخدم المعلومات من جميع ملفات Tupfiles (انظر قسم TUPFILES) بالإضافة إلى المعلومات الديناميكية الخاصة به

قاعدة البيانات، والتي تتم صيانتها في الدليل .tup الموجود في جذر المشروع. يمكن إنشاء الدليل .tup يدويًا باستخدام الأمر 'tup init'، أو يمكنك جعله يعمل تلقائيًا عن طريق إضافة ملف Tupfile.ini فارغ في جذر مستودع التحكم بالإصدار للمشروع.

يتم تجاهل محتويات ملف Tupfile.ini.

ملفات الخيارات

يسمح Tup بمجموعة متنوعة من ملفات التكوين. تؤثر هذه الملفات على سلوك tup كبرنامج، ولكن ليس على tup كنظام بناء. بمعنى آخر، لا ينبغي أن يؤثر تغيير أي من هذه الخيارات على النتيجة النهائية للبناء الناجح، ولكنه قد يؤثر على كيفية وصول tup إلى هناك (على سبيل المثال، عدد وظائف الترجمة التي سيتم تشغيلها بالتوازي).

تتم قراءة الخيارات بالترتيب التالي للأسبقية:

  تجاوزات سطر الأوامر (مثال: العلم -j الممرر إلى 'tup')
  ملف .tup/options
  ملف ~ / .tupoptions
  ملف /etc/tup/options
  افتراضيات tup المضمنة في الكود

بالنسبة لنظام Windows، تتم قراءة ملفات الخيارات على النحو التالي:

  تجاوزات سطر الأوامر
  ملف .tup/options
  tup.ini في مسار بيانات التطبيق (عادةً C:\ProgramData\tup\tup.ini)
  افتراضيات tup المضمنة في الكود

للحصول على قائمة دقيقة بالمسارات على نظامك، اكتب 'tup options'.

تستخدم جميع الملفات نفس بناء جملة نمط .ini. يتم تغليف عنوان القسم بين قوسين مربعين، كالتالي:

[updater]

يتبع عنوان القسم تعريف واحد أو أكثر للمتغيرات، بالشكل 'variable = value'. تبدأ التعليقات بفاصلة منقوطة وتستمر حتى نهاية السطر. يمكن تعيين جميع تعريفات المتغيرات إلى أعداد صحيحة. بالنسبة للأعلام المنطقية، تعتبر "true" / "yes" و "false" / "no" مرادفات لـ 1 و 0 على التوالي. على سبيل المثال، إذا كان لديك ملف .tup/options يحتوي على:

[updater]
	num_jobs = 2
	keep_going = true

إذًا، سيعتمد 'tup' افتراضيًا على وظيفتين، وسيتم تعيين علم updater.keep_going. الخيارات المدرجة أدناه هي بالشكل 'section.variable'، لذا لتعيين 'db.sync'، ستحتاج إلى قسم '[db]' متبوعًا بـ 'sync = 0'، على سبيل المثال. الافتراضيات المدرجة هنا هي الافتراضيات المضمنة في الكود.

db.sync (الافتراضي '1')
يتم تعيينه إلى '1' إذا تم تمكين ميزة SQLite المتزامنة. عند تمكينها، تتم مزامنة قاعدة البيانات بشكل صحيح مع القرص بطريقة تضمن اتساقها دائمًا. عند تعطيلها، ستعمل بشكل أسرع حيث تُترك عمليات الكتابة في ذاكرة التخزين المؤقت للقرص لفترة قبل كتابتها. ومع ذلك، إذا تعطل جهاز الكمبيوتر الخاص بك قبل كتابة كل شيء، فقد تتلف قاعدة بيانات tup. انظر http://www.sqlite.org/pragma.html لمزيد من المعلومات.
updater.num_jobs (افتراضيًا هو عدد المعالجات في النظام)
يتم تعيينه إلى الحد الأقصى لعدد الأوامر التي سيتم تشغيلها بالتوازي بواسطة tup. الافتراضي هو تحديد ديناميكي لعدد المعالجات في النظام. إذا كان updater.num_jobs أكبر من 1، فسيتم تشغيل الأوامر بالتوازي فقط إذا كانت مستقلة. انظر أيضًا الخيار -j.
updater.keep_going (الافتراضي '0')
يتم تعيينه إلى '1' للاستمرار في البناء قدر الإمكان حتى عند مواجهة أخطاء. لن يتم تنفيذ أي شيء يعتمد على أمر فاشل، ولكن سيتم تنفيذ الأوامر المستقلة الأخرى. الافتراضي هو '0'، مما يؤدي إلى توقف tup بعد أول أمر فاشل. انظر أيضًا الخيار -k.
updater.full_deps (افتراضيًا '0')
يتم تعيينه إلى '1' لتتبع التبعيات على الملفات خارج تسلسل tup الهرمي. الافتراضي هو '0'، والذي يتتبع فقط التبعيات داخل تسلسل tup الهرمي. على سبيل المثال، إذا كنت تريد إعادة تجميع جميع ملفات C عند تحديث gcc على نظامك، فيجب عليك تعيين هذا إلى '1'. في Linux و OSX، يتطلب استخدام التبعيات الكاملة أن يكون ثنائي tup ذو صلاحيات root (suid) حتى يتمكن من تشغيل العمليات الفرعية في بيئة chroot. بدلاً من ذلك، في Linux، إذا كانت النواة تدعم مساحات أسماء المستخدم، فلن تحتاج إلى جعل الثنائي suid. لاحظ أنه إذا تم تعيين هذه القيمة إلى '1' من '0'، فسيعيد tup بناء المشروع بالكامل. تعطيل هذا الخيار عندما تم تمكينه سابقًا لا يتطلب إعادة بناء كاملة، ولكنه يستغرق بعض الوقت حيث يتم مسح العقد التي تمثل الملفات الخارجية. ملاحظة: لا يعمل هذا حاليًا مع ccache أو البرامج الأخرى التي قد تكتب إلى ملفات خارجية بسبب مشكلات في التأمين. قد يتم إصلاح هذا في المستقبل.
updater.warnings (افتراضيًا '1')
يتم تعيينه إلى '0' لتعطيل التحذيرات حول الكتابة إلى الملفات المخفية. لا يتتبع Tup الملفات المخفية. إذا كتبت عملية فرعية إلى ملف مخفي، فسيقوم tup افتراضيًا بعرض تحذير بأن هذا الملف قد تم إنشاؤه. عن طريق تعطيل هذا الخيار، لا يتم عرض هذه التحذيرات. تشمل أسماء الملفات (أو الدلائل) المخفية: ., .., .tup, .git, .hg, .bzr, .svn.
display.color (افتراضي 'auto')
يتم تعيينه إلى 'never' لتعطيل رموز ANSI للتنسيق الملون، أو 'always' لاستخدام رموز ANSI دائمًا للتنسيق الملون. الافتراضي هو 'auto'، والذي يعرض تنسيقًا ملونًا إذا كان الإخراج القياسي متصلاً بـ tty، ولا يستخدم ألوانًا بخلاف ذلك (أي: إذا تم إعادة توجيه الإخراج القياسي إلى ملف).
display.width (افتراضيًا عرض المحطة الطرفية)
يتم تعيينه إلى أي رقم 10 أو أكبر لفرض عرض ثابت لشريط التقدم. يُفترض أن هذا هو العرض الإجمالي، والذي يستخدم جزء منه للمسافات والأقواس ونسبة الإكمال. إذا كانت هذه القيمة أقل من 10، يتم تعطيل شريط التقدم.
display.progress (افتراضيًا '1' إذا كان الإخراج القياسي TTY)
يتم تعيينه إلى '1' لتمكين شريط التقدم، أو '0' لإيقاف تشغيله. افتراضيًا، يتم تمكينه إذا كان الإخراج القياسي TTY، ويتم تعطيله إذا لم يكن الإخراج القياسي TTY.
display.job_numbers (الافتراضي '1')
يتم تعيينه إلى '0' لتجنب عرض السلسلة "N) " قبل نتائج المهمة. الافتراضي هو عرض هذا الرقم.
display.job_time (الافتراضي '1')
يتم تعيينه إلى '0' لتجنب عرض وقت تشغيل المهمة مع النتائج. الافتراضي هو عرض وقت التشغيل. لاحظ أن وقت التشغيل المعروض يشمل الوقت الذي يستغرقه tup لحفظ التبعيات. لذلك، من المحتمل أن يكون وقت التشغيل هذا أكبر من وقت التشغيل عند تنفيذ نفس المهمة يدويًا في الصدفة.
display.quiet (الافتراضي '0')
يتم تعيينه إلى '1' لمنع tup من عرض معظم المخرجات. لا يزال tup يعرض شعارًا والمخرجات من أي مهمة تكتب إلى الإخراج القياسي / الإخراج القياسي للأخطاء، أو أي مهمة ترجع رمز خروج غير صفري. لا يزال شريط التقدم معروضًا؛ انظر أيضًا display.progress للحصول على إخراج هادئ جدًا.
monitor.autoupdate (الافتراضي '0')
يتم تعيينه إلى '1' لإعادة البناء تلقائيًا إذا تم اكتشاف تغيير في الملف. هذا له تأثير فقط إذا كان المراقب قيد التشغيل. الافتراضي هو '0'، مما يعني أنه يتعين عليك كتابة 'tup' عندما تكون مستعدًا للتحديث.
monitor.autoparse (الافتراضي '0')
يتم تعيينه إلى '1' لتشغيل المحلل تلقائيًا إذا تم اكتشاف تغيير في الملف. هذا مشابه لـ monitor.autoupdate، باستثناء أن التحديث يتوقف بعد مرحلة المحلل - لا يتم تشغيل أي أوامر حتى تكتب يدويًا 'tup'. هذا له تأثير فقط إذا كان المراقب قيد التشغيل. لاحظ أنه إذا تم تعيين كل من autoupdate و autoparse، فإن autoupdate له الأسبقية.
monitor.foreground (الافتراضي '0')
يتم تعيينه إلى '1' لتشغيل المراقب في المقدمة، لذلك لن يتم إرجاع التحكم إلى المحطة الطرفية حتى يتم إيقاف المراقب (إما عن طريق Ctrl-C في المحطة الطرفية المتحكمة، أو تشغيل 'tup stop' في محطة طرفية أخرى). الافتراضي هو '0'، مما يعني أن المراقب سيعمل في الخلفية.
graph.dirs (الافتراضي '0')
عند تعيينه إلى '1'، سيظهر الأمر 'tup graph' عقد الدليل وروابط الملكية الخاصة بها. يتم أيضًا عرض Tupfiles، حيث تشير إلى عقد الدليل. افتراضيًا، لا يتم عرض الدلائل و Tupfiles لأنها قد تزحم الرسم البياني في بعض الحالات، وليست مفيدة دائمًا.
graph.ghosts (الافتراضي '0')
يتم تعيينه إلى '1' لعرض العقد الشبحية. قد تحاول بعض الأوامر القراءة من العديد من الملفات غير الموجودة، مما يؤدي إلى إنشاء عقد شبحية. افتراضيًا، لا يتم عرض الأشباح لجعل الرسم البياني أسهل في الفهم.
graph.environment (الافتراضي '0')
يتم تعيينه إلى '1' لعرض عقد البيئة (مثل PATH) وتبعياتها. افتراضيًا، لا يتم عرض متغيرات البيئة لأن كل شيء تقريبًا سيعتمد على PATH.
graph.combine (الافتراضي '0')
يتم تعيينه إلى '1' لمحاولة دمج العقد المتشابهة في الرسم البياني. على سبيل المثال، بدلاً من عرض 10 أوامر ترجمة منفصلة لها جميعًا ملف .c كمدخل وملف .o كمخرج، سيقوم هذا بدمجها في أمر واحد لتسهيل رؤية الهيكل الكامل للرسم البياني. افتراضيًا، يتم عرض جميع العقد بشكل منفصل.

ملفات TUPFILES

يجب عليك إنشاء ملف يسمى "Tupfile" في أي مكان في تسلسل tup الهرمي تريد فيه إنشاء ملف إخراج بناءً على ملفات الإدخال. يمكن أن تكون ملفات الإدخال في أي مكان آخر في تسلسل tup الهرمي، ولكن يجب كتابة ملف (ملفات) الإخراج في نفس الدليل مثل Tupfile.

: [foreach] [inputs] [ | order-only inputs] |> command |> [outputs] [ | extra outputs] [<group>] [{bin}]
قواعد :- هي الوسيلة الأساسية لإنشاء الأوامر، ويتم تمييزها بحقيقة أن الحرف ':' يظهر في العمود الأول من Tupfile. يُفترض أن يبدو بناء الجملة مشابهًا إلى حد ما لخط الأنابيب، حيث تنتقل ملفات الإدخال على اليسار إلى الأمر في المنتصف، وتخرج ملفات الإخراج على اليمين.
foreach
هذه إما السلسلة الفعلية "foreach"، أو أنها فارغة. الفرق يكمن في عدد الأوامر التي تم إنشاؤها عندما يكون هناك م
ملفات متعددة. إذا تم تحديد "foreach"، يتم إنشاء أمر واحد لكل ملف في قسم المدخلات. إذا لم يتم تحديده، يتم إنشاء أمر واحد يحتوي على جميع الملفات في قسم المدخلات. على سبيل المثال، ملفات Tup التالية مكافئة: 
# Tupfile 1
: foo.c |> gcc -c foo.c -o foo.o |> foo.o
: bar.c |> gcc -c bar.c -o bar.o |> bar.o
# Tupfile 2
: foreach foo.c bar.c |> gcc -c %f -o %o |> %B.o
بالإضافة إلى ذلك، يتيح استخدام "foreach" استخدام علامة "%e" (انظر أدناه).
inputs
ملفات الإدخال للأمر. يمكن أن يكون ملف الإدخال في أي مكان في تسلسل هرمي لتوب، ويتم تحديده بالنسبة للدليل الحالي. تؤثر ملفات الإدخال على علامات النسبة المئوية (انظر أدناه). يتم دعم الأحرف البديلة داخل دليل باستخدام وظيفة SQLite glob. الأحرف الخاصة لـ glob هي "*"، و"؟"، و"[]". على سبيل المثال، "*.c" سيطابق أي ملف .c، و"fo?.c" سيطابق أي ملف .c مكون من 3 أحرف يبدأ بحرفي "f" و"o"، و"fo[xyz].c" سيطابق fox.c، وfoy.c، وfoz.c. لا تطابق glob المجلدات، لذا "src/*.c" ستعمل، ولكن "*/*.c" لن تعمل.

أي مدخلات تبدأ بـ "^" هي تعبيرات نمطية متوافقة مع Perl تستخدم لاستبعاد الملفات التي تمت مطابقتها في glob سابق. على سبيل المثال، يمكنك تجميع جميع ملفات *.c باستثناء main.c باستخدام الجزء التالي:

: foreach *.c ^main.c |> ... |>

يتم التعامل مع هذه الاستثناءات المدخلة في وقت التحليل، وهي متميزة عن استثناءات الاعتمادية في قسم المخرجات.

order-only inputs
تُستخدم هذه أيضًا كمدخلات للأمر، ولكنها لن تظهر في أي من علامات النسبة المئوية باستثناء "%i". يتم فصلها عن المدخلات العادية باستخدام الحرف "|". في الواقع، يمكن استخدامها لتحديد مدخلات إضافية للأمر لا ينبغي أن تظهر في سطر الأوامر. يتم دعم glob كما في قسم المدخلات. على سبيل المثال، أحد استخداماتها هو تحديد الاعتماديات الرأسية التي تم إنشاؤها تلقائيًا: 
: |> echo "#define FOO 3" > %o |> foo.h
: foreach foo.c bar.c | foo.h |> gcc -c %f -o %o |> %B.o
سيؤدي هذا إلى إضافة اعتمادية foo.h إلى أوامر gcc لـ foo.c و bar.c، حتى يعرف tup أنه يجب إنشاء الملف الرأسي قبل محاولة التجميع. سيتكرر أمر foreach فوق المدخلات العادية (هنا، foo.c و bar.c)، وليس المدخلات الترتيبية (foo.h). إذا نسيت إضافة مثل هذه الاعتمادية، فسيبلغ tup عن خطأ عند تنفيذ الأمر. لاحظ أن اعتمادية foo.h مدرجة هنا فقط لأنها تم إنشاؤها بواسطة أمر آخر - لا تحتاج الرؤوس العادية إلى تحديدها.
command
سلسلة الأوامر التي سيتم تمريرها إلى استدعاء system(3) بواسطة tup. يُسمح لهذا الأمر بالقراءة من أي ملف محدد كمدخل أو مدخل ترتيبي، بالإضافة إلى أي ملف آخر في التسلسل الهرمي لتوب ليس مخرجًا لأمر آخر. بمعنى آخر، لا يمكن لأمر القراءة من مخرج أمر آخر ما لم يتم تحديده كمدخل. هذا القيد هو ما يسمح لـ tup بأن يكون آمنًا بالتوازي. بالإضافة إلى ذلك، يجب أن يكتب الأمر إلى جميع ملفات المخرجات المحددة في قسم "outputs"، إن وجدت.
عند التنفيذ، يتم مراقبة وصول الملفات للأمر بواسطة tup لضمان توافقها مع هذه القواعد. يتم الإبلاغ عن أي ملفات تم فتحها للقراءة تم إنشاؤها من أمر آخر ولكن لم يتم تحديدها كمدخلات على أنها أخطاء. وبالمثل، يتم الإبلاغ عن أي ملفات تم فتحها للكتابة ولم يتم تحديدها كمخرجات على أنها أخطاء. يتم تسجيل جميع الملفات المفتوحة للقراءة كاعتماديات للأمر. إذا تغير أي من هذه الملفات، سيعيد tup تنفيذ الأمر أثناء التحديث التالي. لاحظ أنه إذا تغير مدخل مدرج في Tupfile، فلن يتسبب ذلك بالضرورة في إعادة تنفيذ الأمر، إلا إذا قام الأمر فعليًا بالقراءة من هذا المدخل أثناء التنفيذ السابق. المدخلات المدرجة في Tupfile تفرض فقط الترتيب بين الأوامر، بينما تحدد عمليات الوصول إلى الملفات أثناء التنفيذ متى يتم إعادة تنفيذ الأوامر.
يمكن أن تبدأ سلسلة الأوامر بالتسلسل الخاص ^ TEXT ^ ، والذي سيخبر tup بطباعة "TEXT" بدلاً من سلسلة الأوامر بأكملها عند تنفيذ الأمر. هذا يوفر الجهد لاستخدام echo لطباعة أمر طويل بشكل جميل. يمكن تجاوز سلوك العرض القصير عن طريق تمرير العلامة --verbose إلى tup، والتي ستتسبب في عرض tup لسلسلة الأوامر الفعلية بدلاً من "TEXT". المسافة بعد أول "^" ذات دلالة. سيتم التعامل مع أي أحرف مباشرة بعد أول "^" كعلامات. انظر قسم علامات ^ أدناه للحصول على التفاصيل. على سبيل المثال، سيقوم هذا الأمر بطباعة "CC foo.c" عند تنفيذ system(gcc -c foo.c -o foo.o) : 
: foo.c |> ^ CC %f^ gcc -c %f -o %o |> foo.o
يمكن أن تبدأ سلسلة الأوامر أيضًا بالحرف الخاص "!"، وفي هذه الحالة سيتم استبدال ماكرو ! المحدد بالأمر الفعلي. انظر تعريف ماكرو ! لاحقًا. يمكن أن تكون الأوامر فارغة أيضًا، وهو أمر مفيد لوضع جميع ملفات الإدخال في {bin} لقاعدة لاحقة.
outputs
يحدد قسم المخرجات الملفات التي ستتم كتابتها بواسطة الأمر. يمكن لأمر واحد فقط الكتابة إلى ملف معين، ولكن يمكن لأمر واحد إخراج ملفات متعددة (مثل أمر bison الذي سيخرج ملف .c وملف .h). يمكن للمخرجات استخدام أي علامات نسبة مئوية باستثناء %o. بمجرد تحديد ملف في قسم مخرجات، يتم وضعه في قاعدة بيانات tup. يمكن لأي قواعد تالية استخدام هذا الملف كمدخل، حتى لو لم يكن موجودًا في نظام الملفات بعد.

تبدأ المخرجات التي تبدأ بـ "^" وتستخدم لتجاهل الاعتماديات على الملفات. هذه الاستثناءات هي تعبيرات نمطية متوافقة مع Perl يتم تخزينها في قاعدة البيانات. سيتم تجاهل أي ملفات تتم قراءتها أو الكتابة إليها عند تنفيذ العملية الفرعية التي تطابق هذه الأنماط بواسطة tup. على سبيل المثال، إذا كان المترجم الخاص بك يكتب إلى "license_file.txt"، يمكنك توجيه tup لتجاهل أخطاء الاعتمادية على هذا الملف كالتالي:

: foreach *.c |> ... |> %B.o ^license_file.txt

لاحظ أن هذا يوجه tup أيضًا لتجاهل اعتماديات الإدخال على الملف. إذا كنت ترغب ببساطة في تخطي الملفات في glob، انظر بناء الجملة المشابه لـ '^' في قسم المدخلات.

لا يمكن استخدام استثناء لمطابقة ملف تم إنشاؤه بواسطة نفس القاعدة (أي، مدرج كمخرج في الأمر). سيؤدي القيام بذلك إلى خطأ "Unable to exclude a generated file".

يجب عليك تجاهل الاعتماديات فقط بحذر شديد. من السهل جدًا جعل tup يفشل في التحديث عندما كان يجب أن يحدث لأن tup قد تم توجيهه لتجاهل الاعتماديات.

extra-outputs
قسم المخرجات الإضافية مشابه لقسم المدخلات الترتيبية. يتم فصله عن المخرجات العادية بالحرف "|". تتصرف المخرجات الإضافية تمامًا مثل المخرجات العادية، باستثناء أنها لا تظهر في علامة %o. يمكن استخدام هذه إذا كان الأمر ينشئ ملفات لا تظهر أسماؤها فعليًا في سطر الأوامر. إذا كان هناك مخرج واحد فقط محدد بواسطة القاعدة، يمكن لقسم المخرجات الإضافية استخدام علامة %O لتمثيل الاسم الأساسي للمخرج. يمكن أن يكون هذا مفيدًا في المخرجات الإضافية لماكرو !.
<group>
يمكن تجميع ملفات المخرجات في مجموعات عامة عن طريق تحديد <group> بعد المخرجات ولكن قبل bin. تسمح المجموعات باعتماديات ترتيبية بين المجلدات. لاحظ أن المجموعات خاصة بالدليل، لذلك عند الإشارة إلى مجموعة، يجب تحديد المسار إلى حيث تم تعيينها. على سبيل المثال، إذا كان مشروع رئيسي يعتمد على مخرجات من وحدات فرعية متعددة، يمكنك هيكلة Tup على النحو التالي للتأكد من بناء الوحدات الفرعية قبل المشروع الرئيسي: 
#./submodules/sm1/Tupfile
: foo.c |> gcc -c %f -o %o |> %B.o ../<submodgroup>
#./submodules/sm2/Tupfile
: bar.c |> gcc -c %f -o %o |> %B.o ../<submodgroup>
#./project/Tupfile
: baz.c | ../submodules/<submodgroup> |> gcc -c %f -o %o |> %B.o
لاحظ كيف أن المجموعات خاصة بالدليل ويتم تحديد المسار خارج <>. عن طريق تحديد <submodgroup> كمدخل ترتيبي، سيقوم Tup ببناء الوحدات الفرعية قبل محاولة بناء المشروع بأكمله.
{bin}
يمكن تجميع المخرجات في bin باستخدام بناء الجملة "{bin}". يمكن لقاعدة لاحقة استخدام "{bin}" كمدخل لاستخدام جميع الملفات في هذا bin. على سبيل المثال، ستقوم قاعدة foreach بوضع كل ملف .o في bin الـ objs، والذي يتم استخدامه كمدخل في قاعدة الرابط: 
: foreach *.c |> gcc -c %f -o %o |> %B.o {objs}
: {objs} |> gcc %f -o %o |> program
في هذه الحالة، يمكن استخدام *.o كمدخل بدلاً من ذلك، ولكن في بعض الأحيان يكون من المفيد فصل المخرجات إلى مجموعات حتى لو كان لها نفس الامتداد (مثل إذا أنشأ دليل واحد ملفات ثنائية متعددة، فإن استخدام *.o لن يكون صحيحًا). إذا تم تحديد {bin} في قسم المخرجات لقواعد متعددة، فسيكون bin هو اتحاد جميع المخرجات. لا يمكنك إزالة أشياء من bin، ويختفي bin بعد تحليل Tupfile الحالي.
^-flags
في سلسلة أوامر تستخدم تسلسل ^ TEXT ^ ، يمكن وضع أحرف العلامة مباشرة بعد ^ حتى أول حرف مسافة أو علامة اقتباس مغلقة. على سبيل المثال: 
: foo.c |> ^c CC %f^ gcc --coverage %f -o %o |> foo | foo.gcno
: bar.c |> ^c^ gcc --coverage %f -o %o |> bar | bar.gcno
في حالة foo.c، يتطلب الأمر مساحات أسماء (أو suid) وسيعرض "CC foo.c". في حالة bar.c، يتطلب الأمر مساحات أسماء (أو suid) ويتم عرض سلسلة "gcc --coverage bar.c -o bar". هذه هي أحرف العلامات المدعومة:
b
تتسبب علامة "b" في تشغيل الأمر عبر "/usr/bin/env bash -e -o pipefail -c <command>" بدلاً من "/bin/sh -e -c <command>" الافتراضي. بالإضافة إلى السماح بامتدادات bash في قاعدة :-، يحدد "-o pipefail" أن "القيمة المرتجعة لخط الأنابيب هي قيمة آخر (أقصى) أمر يخرج بحالة غير صفرية، أو صفر إذا خرجت جميع الأوامر في خط الأنابيب بنجاح."
c
تتسبب علامة "c" في فشل الأمر إذا لم يدعم tup مساحات الأسماء للمستخدمين (على Linux) أو لم يكن suid root. في هذه الحالات، يعمل tup في وضع متدهور حيث تكون الدلائل الوهمية مرئية في العمليات الفرعية، وقد يتم تفويت بعض الاعتماديات. إذا كانت هذه السلوكيات المتدهورة ستكسر جزءًا
c
لإضافة الأمر suid في عملية البناء الخاصة بك، أضف علامة 'c' حتى يعرف المستخدمون أنهم بحاجة إلى إضافة بت suid أو ترقية نواة النظام الخاصة بهم. يتم تجاهل هذه العلامة على نظام التشغيل Windows.
j
علامة 'j' تحدد الأمر للتصدير في الأمر tup compiledb. إذا كنت مهتمًا باستخدام compile_commands.json، قم بتعليق الأوامر التي تريد تصديرها باستخدام ^j ثم قم بتشغيل tup compiledb. راجع أمر compiledb لمزيد من التفاصيل.
o
تتسبب علامة 'o' في مقارنة الأمر للمخرجات الجديدة بالمخرجات من التشغيل السابق. لن تؤدي أي مخرجات متطابقة إلى تنفيذ الأوامر التابعة في DAG. على سبيل المثال، إضافة هذه العلامة إلى أمر تجميع ستتجاوز خطوة الربط إذا كان ملف الكائن هو نفسه من المرة الأخيرة التي تم تشغيله فيها. علامة 'o' غير متوافقة مع علامة 't'.
s
تعطّل علامة 's' تخزين الإخراج القياسي/الخطأ القياسي للعمليات الفرعية وتمكّن "وضع التدفق". عند التدفق، يتم وراثة الإخراج القياسي/الخطأ القياسي من عملية tup، لذا عادةً ما يتم عرض الرسائل على الجهاز الطرفي أثناء تشغيل العملية الفرعية بأي ترتيب تم إنشاؤها به. لاحظ أن العمليات التي تم تمكين 's' فيها قد تعرض رسائل متداخلة مع بعضها البعض، بالإضافة إلى شريط تقدم tup أو رسائل tup الأخرى. قد تكون هذه العلامة مفيدة للعمليات طويلة الأمد التي ترغب في رؤية المخرجات فور حدوثها، على الرغم من أنها قد تجعل السجلات مربكة إذا تم استخدامها للعديد من الأوامر الصاخبة التي قد تعمل بالتوازي.

بشكل افتراضي، يقوم tup بتخزين رسائل الأمر مؤقتًا (على سبيل المثال، رسائل تحذير المترجم) ويعرضها تحت رأس الأمر بعد اكتماله. لذلك، تكون الرسائل من أوامر منفصلة دائمًا مميزة ومرتبطة بالأمر الذي أنشأها.

t
تتسبب علامة 't' في أن تكون مخرجات الأمر مؤقتة. يمكن استخدام المخرجات كمدخلات لأوامر أخرى، ولكن بعد تنفيذ جميع الأوامر التابعة، سيتم حذف المخرجات المؤقتة من نظام الملفات. يمكن استخدام هذا لتوفير المساحة إذا كانت هناك مراحل معالجة متعددة تنتج كل منها مخرجات كبيرة، ولكن يجب الاحتفاظ بالمخرجات النهائية فقط. علامة 't' غير متوافقة مع علامة 'o'.

مثال حيث يمكن أن تكون علامة 't' منطقية في خط أنابيب البناء هو إذا كانت هناك أصول كبيرة تمر عبر مراحل معالجة متعددة. على سبيل المثال، ملف صوتي أو فيديو كبير تطبق عليه مراحل مؤثرات، كل منها كخطوة منفصلة في Tupfile.

على النقيض من ذلك، علامة 't' لا معنى لها لملفات الكائنات في برنامج C، حتى لو كان يمكن نظريًا حذف هذه الملفات بعد ربط الملف التنفيذي النهائي. إذا تم تمييز ملفات الكائنات على أنها مؤقتة في هذه الحالة، فإن التغيير في أي من ملفات C المدخلة سيتطلب إعادة بناء جميع ملفات الكائنات لإنتاج الملف التنفيذي، بدلاً من الملف الفردي الذي تم تغييره فقط.

%-flags
داخل سلسلة الأوامر أو سلسلة المخرجات، يمكن أيضًا استخدام علامات النسبة المئوية التالية لاستبدال القيم من المدخلات أو المخرجات. بشكل عام، تتوسع علامات النسبة المئوية لتشمل جميع أسماء الملفات في قائمة. على سبيل المثال، يتوسع %o ليشمل جميع ملفات المخرجات. للإشارة إلى ملف واحد، يمكنك استخدام %1o، %2o، إلخ، للإشارة إلى الملف الأول أو الثاني (وهكذا) في القائمة.
%%
يتوسع إلى حرف "%" واحد في سلسلة الأوامر. يجب استخدام هذا عندما تريد أن يتم تفسير حرف النسبة المئوية بواسطة الأمر نفسه بدلاً من محلل tup.
%f
أسماء الملفات من قسم "inputs". يتضمن هذا المسار والامتداد. هذا مفيد جدًا في أمر، لأنه يسرد اسم كل ملف مدخل مع المسار النسبي للمجلد الحالي. على سبيل المثال، سيتم نسخ "src/foo.c" بالضبط على هيئة "src/foo.c". يمكن الرجوع إلى الملفات الفردية باستخدام %1f، %2f، إلخ.
%i
أسماء الملفات من قسم "order-only inputs". يتضمن هذا المسار والامتداد. عادةً ما تُستخدم المدخلات ذات الترتيب فقط لأسماء الملفات التي لا تريد ظهورها في سطر الأوامر، ولكن إذا كنت بحاجة إلى الإشارة إليها، يمكنك استخدام %i. يمكن الرجوع إلى الملفات الفردية باستخدام %1i، %2i، إلخ.
%b
مثل %f، ولكنه اسم الملف الأساسي فقط. يتم تجريد جزء المسار. على سبيل المثال، "src/foo.c" سيصبح "foo.c". يمكن الرجوع إلى الملفات الفردية باستخدام %1b، %2b، إلخ.
%B
مثل %b، ولكنه يزيل الامتداد. هذا مفيد جدًا في تحويل ملف مدخل إلى ملف مخرج بنفس الاسم ولكن بامتداد مختلف، لأن ملف المخرجات يحتاج إلى أن يكون في نفس المجلد. على سبيل المثال، "src/foo.c" سيصبح "foo". يمكن الرجوع إلى الملفات الفردية باستخدام %1B، %2B، إلخ.
%e
امتداد ملف الملف الحالي عند استخدامه في قاعدة foreach. يمكن استخدامه للمتغيرات التي يمكن أن يكون لها قيم مختلفة بناءً على لاحقة الملف. على سبيل المثال، يمكنك تعيين علامات معينة لملفات التجميع (.S) التي تختلف عن ملفات .c، ثم استخدام بناء جملة مثل $(CFLAGS_%e) للإشارة إلى المتغير CFLAGS_S أو CFLAGS_c اعتمادًا على نوع الملف الذي يتم تجميعه. على سبيل المثال، "src/foo.c" سيصبح "c"، بينما "src/foo.S" سيصبح "S".
%o
اسم ملف المخرجات. إنه مفيد في أمر بحيث يتطابق اسم الملف الذي يتم تمريره إلى أمر دائمًا مع ما يعتقده tup أنه المخرجات. هذا يعمل فقط في قسم "command"، وليس في قسم "outputs". يمكن الرجوع إلى الملفات الفردية باستخدام %1o، %2o، إلخ.
%O
اسم ملف المخرجات بدون الامتداد. هذا يعمل فقط في قسم المخرجات الإضافية إذا تم تحديد ملف مخرجات واحد بالضبط. حالة استخدام لهذا هي إذا كان لديك ماكرو !- يقوم بإنشاء ملفات غير محددة في سطر الأوامر، ولكنها تستند إلى المخرجات المسماة. على سبيل المثال، إذا قام رابط بإنشاء ملف خريطة عن طريق أخذ المخرجات المحددة "foo.so"، وإزالة ".so" وإضافة ".map"، فقد ترغب في ماكرو !- على النحو التالي: 
!ldmap = |> ld ... -o %o |> | %O.map
: foo1.o foo2.o |> !ldmap |> foo.so
%d
اسم أدنى مستوى للمجلد. على سبيل المثال، في foo/bar/Tupfile، ستكون هذه السلسلة "bar". إحدى الحالات التي يمكن أن يكون فيها هذا مفيدًا هي في تسمية المكتبات بناءً على المجلد الذي توجد فيه، كما هو الحال مع الماكرو !- التالي: 
!ar = |> ar crs %o %f |> lib%d.a
سيؤدي استخدام هذا الماكرو في foo/bar/Tupfile إلى إنشاء foo/bar/libbar.a.
%g
السلسلة التي تطابقت مع عامل التجميع. على سبيل المثال مع الملفات a_text.txt و b_text.txt، القاعدة: 
: foreach *_text.txt |> foo %f |> %g_binary.bin
ستنتج أسماء الملفات a_binary.bin و b_binary.bin. سيتم فقط استبدال أول توسيع للتجميع بـ %g. %g صالح فقط عندما يكون هناك ملف إدخال واحد أو عند استخدام foreach.
%<group>
جميع الملفات في "group". على سبيل المثال: 
#./submodules/sm1/Tupfile
: foo.c |> gcc -c %f -o %o |> %B.o ../<submodgroup>
#./submodules/sm2/Tupfile
: bar.c |> gcc -c %f -o %o |> %B.o ../<submodgroup>
#./project/Tupfile
: ../submodules/<submodgroup> |> echo '%f' > %o |> submodules_f.txt
: ../submodules/<submodgroup> |> echo '%<submodgroup>' > %o |> submodules_group.txt

TUPFILE NOTES

\n

Variable expansion in tup is immediate in every case except for\n !-macros. That is, if you see a :-rule or variable declaration, you can\n substitute the current values for the variables. The !-macros are only\n parsed when they used in a :-rule. In that case, the actual :-rule is a\n sort\n of a union between the :-rule as written and the current value of the\n !-macro.

When tup parses a Tupfile, it makes a single pass through the\n file, parsing a line at a time. At the end of the Tupfile, all variable,\n !-macro, and {bin} definitions are discarded. The only lingering effects of\n parsing a Tupfile are the command nodes and dependencies that now exist in\n the tup database. Additionally, a .gitignore file may have been created if\n requested by the Tupfile.

@-VARIABLES

\n

@-variables are special variables in tup. They are used as\n configuration variables, and can be read by Tupfiles or used by the varsed\n command. Commands are able to read them too, but the program executed by the\n command has to have direct knowledge of the variables. @-variables are\n specified in the tup.config file at the top of the tup hierarchy or in a\n variant directory. For example, tup.config may contain:

\n
CONFIG_FOO=y
\n

A Tupfile may then read the @-variable like so:

\n
srcs-@(FOO) += foo.c\nsrcs-y += bar.c\n: foreach $(srcs-y) |> gcc -c %f -o %o |> %B.o
\n

In this example, if CONFIG_FOO is set to 'y', then the foo.c file\n will be included in the input list and therefore compiled. If CONFIG_FOO is\n unspecified or set to some other value, foo.c will not be included.

\n

The @-variables can be used similar to $-variables, with the\n following distinctions: 1) @-variables are read-only in Tupfiles, and 2)\n @-variables are in the DAG, which means reading from them creates a\n dependency from the @-variable to the Tupfile. Therefore any Tupfile that\n reads @(FOO) like the above example will be reparsed if the value of\n CONFIG_FOO in tup.config changes.

\n

The reason for prefixing with "CONFIG_" in the\n tup.config file is to maintain compatibility with kconfig, which can be used\n to generate this file.

\n

Note that the syntax for tup.config is fairly strict. For a\n statement like "CONFIG_FOO=y", tup will create an @-variable using\n the string starting after "CONFIG_", and up to the '=' sign. The\n value is everything immediately after the '=' sign until the newline, but if\n there is a surrounding pair of quotes, they are stripped. In this example,\n it would set "FOO" to "y". Note that if instead the line\n were "CONFIG_FOO = y", then the variable "FOO " would be\n set to " y".

VARIANTS

\n

Tup supports variants, which allow you to build your project\n multiple times with different configurations. Perhaps the most common case\n is to build a release and a debug configuration with different compiler\n flags, though any number of variants can be used to support whatever\n configurations you like. Each variant is built in its own directory distinct\n from each other and from the source tree. When building with variants, the\n in-tree build is disabled. To create a variant, make a new directory at the\n top of the tup hierarchy and create a "tup.config" file there. For\n example:

\n
$ mkdir build-default\n$ touch build-default/tup.config\n$ tup
\n

Here we created a directory called "build-default" and\n made an empty tup.config inside. Note that the build directory must be at\n the same level as the ".tup" directory. Upon updating, tup will\n parse all of the Tupfiles using the configuration file we created, and place\n all build products within subdirectories of build-default that mirror the\n source tree. We could then create another variant like so:

\n
$ mkdir build-debug\n$ echo "CONFIG_MYPROJ_DEBUG=y" > build-debug/tup.config\n$ tup
\n

This time all Tupfiles will be parsed with @(MYPROJ_DEBUG) set to\n "y", and all build products will be placed in the build-debug\n directory. Note that setting @(MYPROJ_DEBUG) only has any effect if the\n variable is actually used in a Tupfile (perhaps by adding debug flags to the\n compiler command-line).

\n

Running "tup" will update all variants. For example,\n updating after modifying a C file that is used in all configurations will\n cause it to be re-compiled for each variant. As with any command that is\n executed, this is done in parallel subject to the constraints of the DAG and\n the number of jobs specified. To build a single variant (or subset of\n variants), specify the build directory as the target to "tup",\n just like with any partial update. For example:

\n
$ tup build-default
\n

To delete a variant, just wipe out the build directory:

\n
$ rm -rf build-debug
\n

If you build with variants, it is recommended that you always have\n a default variant that contains an empty tup.config file. This helps check\n that your software is always able to be built by simply checking it out and\n doing 'tup init; tup' without relying on a specific configuration.
