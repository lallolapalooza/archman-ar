الاسم

SELECT, TABLE, WITH - استرداد الصفوف من جدول أو عرض

الملخص

[ WITH [ RECURSIVE ] with_query [, ...] ]
SELECT [ ALL | DISTINCT [ ON ( expression [, ...] ) ] ]
    [ { * | expression [ [ AS ] output_name ] } [, ...] ]
    [ FROM from_item [, ...] ]
    [ WHERE condition ]
    [ GROUP BY [ ALL | DISTINCT ] grouping_element [, ...] ]
    [ HAVING condition ]
    [ WINDOW window_name AS ( window_definition ) [, ...] ]
    [ { UNION | INTERSECT | EXCEPT } [ ALL | DISTINCT ] select ]
    [ ORDER BY expression [ ASC | DESC | USING operator ] [ NULLS { FIRST | LAST } ] [, ...] ]
    [ LIMIT { count | ALL } ]
    [ OFFSET start [ ROW | ROWS ] ]
    [ FETCH { FIRST | NEXT } [ count ] { ROW | ROWS } { ONLY | WITH TIES } ]
    [ FOR { UPDATE | NO KEY UPDATE | SHARE | KEY SHARE } [ OF from_reference [, ...] ] [ NOWAIT | SKIP LOCKED ] [...] ]
where from_item can be one of:
    [ ONLY ] table_name [ * ] [ [ AS ] alias [ ( column_alias [, ...] ) ] ]
                [ TABLESAMPLE sampling_method ( argument [, ...] ) [ REPEATABLE ( seed ) ] ]
    [ LATERAL ] ( select ) [ [ AS ] alias [ ( column_alias [, ...] ) ] ]
    with_query_name [ [ AS ] alias [ ( column_alias [, ...] ) ] ]
    [ LATERAL ] function_name ( [ argument [, ...] ] )
                [ WITH ORDINALITY ] [ [ AS ] alias [ ( column_alias [, ...] ) ] ]
    [ LATERAL ] function_name ( [ argument [, ...] ] ) [ AS ] alias ( column_definition [, ...] )
    [ LATERAL ] function_name ( [ argument [, ...] ] ) AS ( column_definition [, ...] )
    [ LATERAL ] ROWS FROM( function_name ( [ argument [, ...] ] ) [ AS ( column_definition [, ...] ) ] [, ...] )
                [ WITH ORDINALITY ] [ [ AS ] alias [ ( column_alias [, ...] ) ] ]
    from_item join_type from_item { ON join_condition | USING ( join_column [, ...] ) [ AS join_using_alias ] }
    from_item NATURAL join_type from_item
    from_item CROSS JOIN from_item
and grouping_element can be one of:
    ( )
    expression
    ( expression [, ...] )
    ROLLUP ( { expression | ( expression [, ...] ) } [, ...] )
    CUBE ( { expression | ( expression [, ...] ) } [, ...] )
    GROUPING SETS ( grouping_element [, ...] )
and with_query is:
    with_query_name [ ( column_name [, ...] ) ] AS [ [ NOT ] MATERIALIZED ] ( select | values | insert | update | delete | merge )
        [ SEARCH { BREADTH | DEPTH } FIRST BY column_name [, ...] SET search_seq_col_name ]
        [ CYCLE column_name [, ...] SET cycle_mark_col_name [ TO cycle_mark_value DEFAULT cycle_mark_default ] USING cycle_path_col_name ]
TABLE [ ONLY ] table_name [ * ]

الوصف

SELECT يسترد الصفوف من صفر أو أكثر من الجداول. المعالجة العامة لـ SELECT هي كما يلي:

1.يتم حساب جميع الاستعلامات في قائمة WITH. هذه تعمل فعليًا كجداول مؤقتة يمكن الإشارة إليها في قائمة FROM. يتم حساب استعلام WITH الذي تتم الإشارة إليه أكثر من مرة في FROM مرة واحدة فقط، ما لم يتم تحديد خلاف ذلك مع NOT MATERIALIZED. (انظر قسم WITH أدناه.)
2.يتم حساب جميع العناصر في قائمة FROM. (كل عنصر في قائمة FROM هو جدول حقيقي أو افتراضي.) إذا تم تحديد أكثر من عنصر في قائمة FROM، فسيتم دمجها معًا. (انظر قسم FROM أدناه.)
3.إذا تم تحديد جملة WHERE، فسيتم حذف جميع الصفوف التي لا تلبي الشرط من الإخراج. (انظر قسم WHERE أدناه.)
4.إذا تم تحديد جملة GROUP BY، أو إذا كانت هناك استدعاءات لوظائف التجميع، فسيتم دمج الإخراج في مجموعات من الصفوف التي تتطابق مع قيمة واحدة أو أكثر، وسيتم حساب نتائج وظائف التجميع. إذا كانت جملة HAVING موجودة، فستحذف المجموعات التي لا تلبي الشرط المحدد. (انظر قسم GROUP BY Clause و HAVING Clause أدناه.) على الرغم من أن أعمدة إخراج الاستعلام يتم حسابها اسميًا في الخطوة التالية، إلا أنه يمكن أيضًا الإشارة إليها (بالاسم أو الرقم الترتيبي) في جملة GROUP BY.
5.يتم حساب صفوف الإخراج الفعلية باستخدام تعبيرات إخراج SELECT لكل صف أو مجموعة صفوف محددة. (انظر قائمة SELECT أدناه.)
6.SELECT DISTINCT يحذف الصفوف المكررة من النتيجة. SELECT DISTINCT ON يحذف الصفوف التي تتطابق في جميع التعبيرات المحددة. SELECT ALL (الافتراضي) سيعيد جميع الصفوف المرشحة، بما في ذلك التكرارات. (انظر قسم DISTINCT Clause أدناه.)
7.باستخدام العوامل UNION و INTERSECT و EXCEPT، يمكن دمج إخراج أكثر من عبارة SELECT واحدة لتشكيل مجموعة نتائج واحدة. يعيد عامل UNION جميع الصفوف الموجودة في مجموعة نتائج واحدة أو كليهما. يعيد عامل INTERSECT جميع الصفوف الموجودة بشكل صارم في كلتا المجموعتين. يعيد عامل EXCEPT الصفوف الموجودة في مجموعة النتائج الأولى ولكن ليس في الثانية. في جميع الحالات الثلاث، يتم حذف الصفوف المكررة ما لم يتم تحديد ALL. يمكن إضافة الكلمة الدلالية DISTINCT لتحديد حذف الصفوف المكررة بشكل صريح. لاحظ أن DISTINCT هو السلوك الافتراضي هنا، على الرغم من أن ALL هو الافتراضي لـ SELECT نفسه. (انظر قسم UNION Clause و INTERSECT Clause و EXCEPT Clause أدناه.)
8.إذا تم تحديد جملة ORDER BY، فسيتم فرز الصفوف المعاد إرجاعها بالترتيب المحدد. إذا لم يتم إعطاء ORDER BY، فسيتم إرجاع الصفوف بأي ترتيب يجده النظام أسرع في إنتاجه. (انظر قسم ORDER BY Clause أدناه.)
9.إذا تم تحديد جملة LIMIT (أو FETCH FIRST) أو OFFSET، فإن عبارة SELECT تعيد مجموعة فرعية فقط من صفوف النتائج. (انظر قسم LIMIT Clause أدناه.)
10.إذا تم تحديد FOR UPDATE أو FOR NO KEY UPDATE أو FOR SHARE أو FOR KEY SHARE، فإن عبارة SELECT تقفل الصفوف المحددة ضد التحديثات المتزامنة. (انظر قسم The Locking Clause أدناه.)

يجب أن يكون لديك امتياز SELECT على كل عمود مستخدم في أمر SELECT. يتطلب استخدام FOR NO KEY UPDATE أو FOR UPDATE أو FOR SHARE أو FOR KEY SHARE امتياز UPDATE أيضًا (لعمود واحد على الأقل من كل جدول تم تحديده).

المعلمات

قسم WITH

يسمح لك قسم WITH بتحديد استعلامات فرعية واحدة أو أكثر يمكن الإشارة إليها بالاسم في الاستعلام الأساسي. تعمل الاستعلامات الفرعية فعليًا كجداول مؤقتة أو عروض لمدة الاستعلام الأساسي. يمكن أن يكون كل استعلام فرعي عبارة SELECT أو TABLE أو VALUES أو INSERT أو UPDATE أو DELETE أو MERGE. عند كتابة عبارة تعديل البيانات (INSERT أو UPDATE أو DELETE أو MERGE) في WITH، من المعتاد تضمين عبارة RETURNING. إنه إخراج RETURNING، وليس الجدول الأساسي الذي تعدله العبارة، الذي يشكل الجدول المؤقت الذي تقرأه الاستعلام الأساسي. إذا تم حذف RETURNING، فسيتم تنفيذ العبارة، ولكنها لن تنتج أي إخراج لذلك لا يمكن الإشارة إليها كجدول بواسطة الاستعلام الأساسي.

يجب تحديد اسم (بدون تأهيل مخطط) لكل استعلام WITH. اختياريًا، يمكن تحديد قائمة بأسماء الأعمدة؛ إذا تم حذف هذه القائمة، فسيتم استنتاج أسماء الأعمدة من الاستعلام الفرعي.

إذا تم تحديد RECURSIVE، فإنه يسمح للاستعلام الفرعي SELECT بالإشارة إلى نفسه بالاسم. يجب أن يأخذ هذا الاستعلام الفرعي الشكل

non_recursive_term UNION [ ALL | DISTINCT ] recursive_term

حيث يجب أن يظهر الإشارة الذاتية المتكررة على الجانب الأيمن من UNION. لا يُسمح إلا بمرجع ذاتي متكرر واحد لكل استعلام. لا يتم دعم عبارات تعديل البيانات المتكررة، ولكن يمكنك استخدام نتائج استعلام SELECT المتكرر في عبارة تعديل البيانات. انظر القسم 7.8 للحصول على مثال.

تأثير آخر لـ RECURSIVE هو أن استعلامات WITH لا تحتاج إلى ترتيب: يمكن للاستعلام الإشارة إلى استعلام آخر يكون لاحقًا في القائمة. (ومع ذلك، لا يتم تنفيذ المراجع الدائرية، أو التكرار المتبادل.) بدون RECURSIVE، يمكن لاستعلامات WITH فقط الإشارة إلى استعلامات WITH الشقيقة التي تكون أقدم في قائمة WITH.

عندما تكون هناك استعلامات متعددة في قائمة WITH، يجب كتابة RECURSIVE مرة واحدة فقط، مباشرة بعد WITH. تنطبق على جميع الاستعلامات في قائمة WITH، على الرغم من أنها لا تؤثر على الاستعلامات التي لا تستخدم التكرار أو المراجع الأمامية.

تحسب جملة SEARCH الاختيارية عمود تسلسل بحث يمكن استخدامه لترتيب نتائج الاستعلام المتكرر بترتيب البحث الشامل أو العميق. تحدد قائمة أسماء الأعمدة المقدمة

EXCLUDE GROUP يستثني الصف الحالي والمتطابقين في الترتيب من الإطار. EXCLUDE TIES يستثني أي متطابقين للصف الحالي من الإطار، ولكن ليس الصف الحالي نفسه. EXCLUDE NO OTHERS يحدد ببساطة السلوك الافتراضي لعدم استثناء الصف الحالي أو متطابقيه.

احذر من أن وضع ROWS يمكن أن ينتج نتائج غير متوقعة إذا كان ترتيب ORDER BY لا يرتب الصفوف بشكل فريد. تم تصميم وضعي RANGE و GROUPS لضمان معاملة الصفوف المتطابقة في ترتيب ORDER BY بشكل متشابه: جميع صفوف مجموعة متطابقين معينة ستكون في الإطار أو مستبعدة منه.

الغرض من عبارة WINDOW هو تحديد سلوك دوال النوافذ التي تظهر في قائمة SELECT أو عبارة ORDER BY للاستعلام. يمكن لهذه الدوال الإشارة إلى إدخالات عبارة WINDOW بالاسم في عبارات OVER الخاصة بها. لا يلزم أن يكون إدخال عبارة WINDOW مرجعًا في أي مكان، ومع ذلك؛ إذا لم يتم استخدامه في الاستعلام، فسيتم تجاهله ببساطة. من الممكن استخدام دوال النوافذ دون أي عبارة WINDOW على الإطلاق، حيث يمكن لمكالمة دالة النافذة تحديد تعريف النافذة الخاصة بها مباشرة في عبارة OVER الخاصة بها. ومع ذلك، فإن عبارة WINDOW توفر الكتابة عند الحاجة إلى نفس تعريف النافذة لأكثر من دالة نافذة واحدة.

حاليًا، لا يمكن تحديد FOR NO KEY UPDATE أو FOR UPDATE أو FOR SHARE أو FOR KEY SHARE مع WINDOW.

قائمة SELECT

تحدد قائمة SELECT (بين الكلمتين المفتاحيتين SELECT و FROM) تعبيرات تشكل صفوف الإخراج لبيان SELECT. يمكن للتعبيرات (وعادة ما تفعل ذلك) الإشارة إلى الأعمدة المحسوبة في عبارة FROM.

تمامًا كما في الجدول، كل عمود إخراج من SELECT له اسم. في SELECT بسيط، يُستخدم هذا الاسم فقط لتسمية العمود للعرض، ولكن عندما يكون SELECT استعلامًا فرعيًا لاستعلام أكبر، فإن الاسم يُرى بواسطة الاستعلام الأكبر باسم العمود للجدول الافتراضي الذي ينتجه الاستعلام الفرعي. لتحديد الاسم المراد استخدامه لعمود الإخراج، اكتب AS output_name بعد تعبير العمود. (يمكنك حذف AS، ولكن فقط إذا كان اسم الإخراج المطلوب لا يتطابق مع أي كلمة مفتاحية في PostgreSQL (راجع الملحق C). للحماية ضد الإضافات المستقبلية المحتملة للكلمات المفتاحية، يوصى بكتابة AS دائمًا أو وضع اسم الإخراج بين علامتي اقتباس مزدوجتين.) إذا لم تحدد اسم عمود، فسيتم اختيار اسم تلقائيًا بواسطة PostgreSQL. إذا كان تعبير العمود عبارة عن مرجع عمود بسيط، فسيكون الاسم المختار هو نفس اسم هذا العمود. في الحالات الأكثر تعقيدًا، يمكن استخدام اسم دالة أو نوع، أو قد يعود النظام إلى اسم تم إنشاؤه مثل ?column؟.

يمكن استخدام اسم عمود الإخراج للإشارة إلى قيمة العمود في عبارات ORDER BY و GROUP BY، ولكن ليس في عبارتي WHERE أو HAVING؛ هناك يجب كتابة التعبير بالكامل بدلاً من ذلك.

بدلاً من تعبير، يمكن كتابة * في قائمة الإخراج كاختصار لجميع الأعمدة للصفوف المحددة. أيضًا، يمكنك كتابة table_name.* كاختصار للأعمدة القادمة من هذا الجدول فقط. في هذه الحالات، لا يمكن تحديد أسماء جديدة باستخدام AS؛ ستكون أسماء أعمدة الإخراج هي نفسها أسماء أعمدة الجدول.

وفقًا لمعيار SQL، يجب حساب التعبيرات في قائمة الإخراج قبل تطبيق DISTINCT أو ORDER BY أو LIMIT. هذا ضروري بشكل واضح عند استخدام DISTINCT، لأنه بخلاف ذلك، ليس من الواضح ما هي القيم التي يتم جعلها مميزة. ومع ذلك، في العديد من الحالات، من الملائم أن يتم حساب تعبيرات الإخراج بعد ORDER BY و LIMIT؛ خاصة إذا كانت قائمة الإخراج تحتوي على أي دوال متقلبة أو باهظة الثمن. مع هذا السلوك، يكون ترتيب تقييم الدوال أكثر بداهة ولن تكون هناك تقييمات مقابلة للصفوف التي لا تظهر أبدًا في الإخراج. ستقوم PostgreSQL بتقييم تعبيرات الإخراج فعليًا بعد الفرز والتحديد، طالما أن هذه التعبيرات لا يتم الإشارة إليها في DISTINCT أو ORDER BY أو GROUP BY. (كمثال مضاد، SELECT f(x) FROM tab ORDER BY 1 يجب بوضوح تقييم f(x) قبل الفرز.) يتم تقييم تعبيرات الإخراج التي تحتوي على دوال تُرجع مجموعات فعليًا بعد الفرز وقبل التحديد، بحيث يعمل LIMIT على قطع الإخراج من دالة تُرجع مجموعات.


ملاحظة

إصدارات PostgreSQL قبل 9.6 لم تقدم أي ضمانات حول توقيت تقييم تعبيرات الإخراج مقابل الفرز والتحديد؛ كان يعتمد على شكل خطة الاستعلام المختارة.

عبارة DISTINCT

إذا تم تحديد SELECT DISTINCT، يتم إزالة جميع الصفوف المكررة من مجموعة النتائج (يتم الاحتفاظ بصف واحد من كل مجموعة من الصفوف المكررة). يحدد SELECT ALL العكس: يتم الاحتفاظ بجميع الصفوف؛ هذا هو الافتراضي.

يحتفظ SELECT DISTINCT ON ( expression [, ...] ) بالصف الأول فقط من كل مجموعة من الصفوف حيث يتم تقييم التعبيرات المحددة على أنها متساوية. يتم تفسير تعبيرات DISTINCT ON باستخدام نفس القواعد كما هو الحال بالنسبة لـ ORDER BY (انظر أعلاه). لاحظ أن "الصف الأول" من كل مجموعة يكون غير قابل للتنبؤ ما لم يتم استخدام ORDER BY لضمان ظهور الصف المطلوب أولاً. على سبيل المثال:

SELECT DISTINCT ON (location) location, time, report
    FROM weather_reports
    ORDER BY location, time DESC;

يسترد أحدث تقرير طقس لكل موقع. ولكن إذا لم نستخدم ORDER BY لفرض الترتيب التنازلي لقيم الوقت لكل موقع، فسنحصل على تقرير من وقت غير قابل للتنبؤ لكل موقع.

يجب أن تتطابق تعبيرات DISTINCT ON (s) مع تعبيرات ORDER BY الأكثر يسارًا. عادةً ما تحتوي عبارة ORDER BY على تعبيرات إضافية تحدد الأولوية المرغوبة للصفوف داخل كل مجموعة DISTINCT ON.

حاليًا، لا يمكن تحديد FOR NO KEY UPDATE أو FOR UPDATE أو FOR SHARE أو FOR KEY SHARE مع DISTINCT.

عبارة UNION

تحتوي عبارة UNION على هذا الشكل العام:

select_statement UNION [ ALL | DISTINCT ] select_statement

select_statement هو أي بيان SELECT بدون عبارة ORDER BY أو LIMIT أو FOR NO KEY UPDATE أو FOR UPDATE أو FOR SHARE أو FOR KEY SHARE. (يمكن إرفاق ORDER BY و LIMIT بتعبير فرعي إذا كان محاطًا بأقواس. بدون أقواس، سيتم اعتبار هذه العبارات مطبقة على نتيجة UNION، وليس على تعبير الإدخال الأيمن.)

تقوم عامل UNION بحساب اتحاد المجموعات للصفوف التي تعيدها بيانات SELECT المعنية. يكون الصف في اتحاد مجموعتين من النتائج إذا ظهر في واحدة على الأقل من مجموعتي النتائج. يجب أن تنتج عبارتي SELECT اللتان تمثلان المعاملات المباشرة لـ UNION نفس عدد الأعمدة، ويجب أن تكون الأعمدة المقابلة من أنواع بيانات متوافقة.

نتيجة UNION لا تحتوي على صفوف مكررة ما لم يتم تحديد خيار ALL. يمنع ALL إزالة التكرارات. (وبالتالي، فإن UNION ALL أسرع بكثير من UNION؛ استخدم ALL عندما يمكنك ذلك.) يمكن كتابة DISTINCT لتحديد السلوك الافتراضي لإزالة الصفوف المكررة بشكل صريح.

يتم تقييم عوامل UNION المتعددة في نفس بيان SELECT من اليسار إلى اليمين، ما لم يُشر إلى خلاف ذلك بواسطة الأقواس.

حاليًا، لا يمكن تحديد FOR NO KEY UPDATE أو FOR UPDATE أو FOR SHARE أو FOR KEY SHARE إما لنتيجة UNION أو لأي مدخل لـ UNION.

عبارة INTERSECT

تحتوي عبارة INTERSECT على هذا الشكل العام:

select_statement INTERSECT [ ALL | DISTINCT ] select_statement

select_statement هو أي بيان SELECT

عبارة EXCEPT

عبارة EXCEPT لها الشكل العام التالي:

select_statement EXCEPT [ ALL | DISTINCT ] select_statement

select_statement هو أي SELECT بدون عبارة ORDER BY، LIMIT، FOR NO KEY UPDATE، FOR UPDATE، FOR SHARE، أو FOR KEY SHARE.

يقوم العامل EXCEPT بحساب مجموعة الصفوف الموجودة في نتيجة SELECT اليسرى ولكن ليست في اليمنى.

لا تحتوي نتيجة EXCEPT على أي صفوف مكررة، إلا إذا تم تحديد الخيار ALL. مع ALL، سيظهر صف يحتوي على m تكرار في الجدول الأيسر و n في الجدول الأيمن min(m, n) مرة في النتيجة. يمكن كتابة DISTINCT لتحديد السلوك الافتراضي لإزالة الصفوف المكررة بشكل صريح.

يتم تقييم عوامل EXCEPT في نفس SELECT من اليسار إلى اليمين، ما لم تشير الأقواس إلى خلاف ذلك. يتم تقييم EXCEPT بالقرب من UNION. أي، A UNION B EXCEPT C تُقرأ على أنها A UNION (B EXCEPT C).

في الوقت الحالي، لا يمكن تحديد عبارات FOR NO KEY UPDATE، FOR UPDATE، FOR SHARE، و FOR KEY SHARE لكل من نتيجة EXCEPT ولكل مدخل من مدخلات EXCEPT.

عبارة ORDER BY

عبارة ORDER BY اختيارية ولها الشكل العام التالي:

ORDER BY expression [ ASC | DESC | USING operator ] [ NULLS { FIRST | LAST } ] [, ...]

تتسبب عبارة ORDER BY في ترتيب صفوف النتيجة وفقًا للتعبيرات المحددة. إذا كان صَفان متساويين وفقًا للتعبير الأيسر، فسيتم مقارنتهما وفقًا للتعبير التالي وهكذا. إذا كانا متساويين وفقًا لجميع التعبيرات المحددة، فسيتم إرجاعهما بترتيب يعتمد على التنفيذ.

يمكن أن يكون كل expression اسمًا أو رقمًا لعمود إخراج (عنصر قائمة SELECT)، أو تعبيرًا عشوائيًا مكونًا من قيم أعمدة الإدخال.

يشير الرقم الترتيبي إلى موضع (من اليسار إلى اليمين) لعمود الإخراج. تسمح هذه الميزة بتحديد ترتيب يعتمد على عمود ليس له اسم فريد. هذا ليس ضروريًا على الإطلاق، حيث يمكن دائمًا تسمية عمود إخراج باستخدام عبارة AS.

من الممكن أيضًا استخدام تعبيرات عشوائية في عبارة ORDER BY، بما في ذلك الأعمدة التي لا تظهر في قائمة إخراج SELECT. لذلك، العبارة التالية صالحة:

SELECT name FROM distributors ORDER BY code;

أحد قيود هذه الميزة هو أن عبارة ORDER BY المطبقة على نتيجة UNION، INTERSECT، أو EXCEPT يمكنها فقط تحديد اسم أو رقم عمود إخراج، وليس تعبيرًا.

إذا كان تعبير ORDER BY اسمًا بسيطًا يتطابق مع اسم عمود إخراج واسم عمود إدخال، فستفسره ORDER BY على أنه اسم عمود إخراج. هذا هو عكس ما ستفعله GROUP BY في نفس الموقف. هذا التناقض مصمم ليكون متوافقًا مع معيار SQL.

اختياريًا، يمكن إضافة الكلمة المفتاحية ASC (تصاعدي) أو DESC (تنازلي) بعد أي تعبير في عبارة ORDER BY. إذا لم يتم تحديد أي منهما، فإن ASC هو الافتراضي. بدلاً من ذلك، يمكن تحديد اسم عامل ترتيب في عبارة USING. يجب أن يكون عامل الترتيب عضوًا في عائلة عوامل B-tree. ASC عادة ما يعادل USING <؛ و DESC عادة ما يعادل USING >؛. (ولكن يمكن لمنشئ نوع بيانات مخصص تحديد الترتيب الافتراضي بالضبط، وقد يتوافق مع عوامل تحمل أسماء أخرى.)

إذا تم تحديد NULLS LAST، فسيتم ترتيب القيم الفارغة بعد جميع القيم غير الفارغة؛ إذا تم تحديد NULLS FIRST، فسيتم ترتيب القيم الفارغة قبل جميع القيم غير الفارغة. إذا لم يتم تحديد أي منهما، فإن السلوك الافتراضي هو NULLS LAST عند استخدام ASC، أو NULLS FIRST عند استخدام DESC (وبالتالي، فإن السلوك الافتراضي هو أن القيم الفارغة أكبر من القيم غير الفارغة). عند تحديد USING، يعتمد السلوك الافتراضي للقيم الفارغة على ما إذا كان العامل هو عامل "أقل من" أو "أكبر من".

ملاحظة: تنطبق خيارات الترتيب فقط على التعبير الذي يتبعها؛ على سبيل المثال، ORDER BY x, y DESC لا يعني نفس معنى ORDER BY x DESC, y DESC.

يتم ترتيب بيانات النص وفقًا للترتيب المطبق على العمود الذي يتم ترتيبه. يمكن تجاوز هذا عن طريق تضمين عبارة COLLATE في expression، على سبيل المثال، ORDER BY mycolumn COLLATE "en_US". لمزيد من المعلومات، انظر القسم 4.2.10 والقسم 23.2.

عبارة LIMIT

تتكون عبارة LIMIT من عبارتين فرعيتين مستقلتين:

LIMIT { count | ALL }
OFFSET start

يحدد المعامل count الحد الأقصى لعدد الصفوف المراد إرجاعها، بينما يحدد start عدد الصفوف التي سيتم تخطيها قبل البدء في إرجاع الصفوف. عند تحديد كليهما، يتم تخطي start صفوف قبل البدء في عد count صفوف لإرجاعها.

إذا قام التعبير count بتقييم إلى NULL، فإنه يعامل على أنه LIMIT ALL، أي لا يوجد حد. إذا قام start بتقييم إلى NULL، فإنه يعامل على أنه OFFSET 0.

قدم SQL:2008 بناء جملة مختلف لتحقيق نفس النتيجة، والذي يدعمه PostgreSQL أيضًا. وهو:

OFFSET start { ROW | ROWS }
FETCH { FIRST | NEXT } [ count ] { ROW | ROWS } { ONLY | WITH TIES }

في هذا البناء، يُطلب من القيمة start أو count وفقًا للمعيار أن تكون قيمة ثابتة، أو معامل، أو اسم متغير؛ كملحق لـ PostgreSQL، يُسمح بتعبيرات أخرى، ولكنها يجب عمومًا أن تكون داخل أقواس لتجنب الغموض. إذا لم يتم تحديد count في عبارة FETCH، فإنها تُعيّن افتراضيًا إلى 1. يُستخدم الخيار WITH TIES لإرجاع أي صفوف إضافية تحتل المركز الثاني في النتيجة وفقًا لعبارة ORDER BY؛ ORDER BY إلزامي في هذه الحالة، وSKIP LOCKED غير مسموح به. المصطلحان ROW و ROWS وكذلك FIRST و NEXT هما كلمتان رئيسيتان لا تؤثران على آثار هاتين العبارتين. وفقًا للمعيار، يجب أن تظهر عبارة OFFSET قبل عبارة FETCH إذا كان كلاهما موجودًا؛ ولكن PostgreSQL أكثر مرونة ويسمح بالترتيب أيهما.

عند استخدام LIMIT، من الجيد استخدام عبارة ORDER BY تقيد صفوف النتيجة بترتيب واحد. وإلا، ستحصل على مجموعة فرعية غير متوقعة من صفوف الاستعلام، بأي ترتيب؟ لن تعرف حتى تحدد ORDER BY.

يأخذ مخطط الاستعلام في الاعتبار LIMIT عند إنشاء مخطط استعلام، لذلك من المحتمل أن تحصل على مخططات مختلفة (تعطيك ترتيبات صفوف مختلفة) اعتمادًا على ما تستخدمه لـ LIMIT و OFFSET. لذلك، فإن استخدام قيم مختلفة لـ LIMIT/OFFSET لتحديد مجموعات فرعية مختلفة من نتائج الاستعلام سيؤدي إلى نتائج غير متسقة، ما لم تكن قد حددت ترتيبًا يمكن التنبؤ به باستخدام ORDER BY. هذا ليس خطأ؛ إنه نتيجة متأصلة لعدم وعود SQL بتسليم نتائج الاستعلام بأي ترتيب معين، ما لم يتم استخدام ORDER BY لتقييد الترتيب.

من الممكن حتى أن تؤدي عمليات التنفيذ المتكررة لاستعلام مع LIMIT إلى إرجاع مجموعات فرعية مختلفة من الصفوف من جدول، إذا لم يكن هناك عبارة ORDER BY لضمان تحديد مجموعة فرعية حتمية. مرة أخرى، هذا ليس خطأ؛ تحديد النتائج غير مضمون ببساطة في مثل هذه الحالات.

عبارة القفل

FOR UPDATE، FOR NO KEY UPDATE، FOR SHARE، و FOR KEY SHARE هي عبارات قفل؛ تؤثر على كيفية الحصول على أقفال صفوف SELECT من الجدول.

عبارة القفل لها الشكل العام:

FOR lock_strength [ OF from_reference [, ...] ] [ NOWAIT | SKIP LOCKED ]

حيث lock_strength يمكن أن يكون أحد:

UPDATE
NO KEY UPDATE
SHARE
KEY SHARE

يجب أن يكون from_reference اسم مستعار للجدول أو اسم جدول غير مخفي مشار إليه في عبارة FROM. لمزيد من المعلومات حول كل نوع من أنواع الأقفال على مستوى الصف، انظر القسم 13.3.2.

لتجنب انتظار العملية حتى تقوم المعاملات الأخرى بالالتزام، استخدم إما الخيار NOWAIT أو SKIP LOCKED. مع NOWAIT، تقوم العبارة بالإبلاغ عن خطأ، بدلاً من الانتظار، إذا لم يكن من الممكن قفل صف محدد على الفور. مع SKIP LOCKED، يتم تخطي أي صف محدد لا يمكن قفله على الفور. يوفر تخطي الصفوف المقفلة عرضًا غير مستقر للبيانات، لذا فهو غير مناسب للأعمال العامة، ولكنه يمكن استخدامه لتجنب تضارب الأقفال مع مستهلكين متعددين يصلون إلى جدول مشابه لقائمة انتظار. ملاحظة: ينطبق NOWAIT و SKIP LOCKED فقط على الأقفال على مستوى الصف — لا يزال قفل ROW SHARE على مستوى الجدول يتم الحصول عليه بشكل مشترك (انظر الفصل 13). يمكنك استخدام LOCK مع الخيار NOWAIT أولاً، إذا كنت بحاجة إلى الحصول على قفل على مستوى الجدول دون انتظار.

إذا تم تحديد جداول محددة في عبارة قفل، فسيتم قفل الصفوف القادمة من تلك الجداول فقط؛ أي جداول أخرى مستخدمة في SELECT تتم قراءتها بشكل طبيعي. عبارة قفل بدون قائمة جداول تؤثر على جميع الجداول المستخدمة في العبارة. إذا تم تطبيق عبارة قفل على عرض أو استعلام فرعي، فإنها تؤثر على جميع الجداول المستخدمة في العرض أو الاستعلام الفرعي. ومع ذلك، لا تنطبق هذه العبارات على استعلامات WITH المشار إليها بواسطة الاستعلام الرئيسي. إذا كنت تريد تفعيل قفل الصف داخل استعلام WITH، فحدد عبارة قفل داخل استعلام WITH.

يمكن كتابة عبارات قفل متعددة:

حافظ على بنية الملف بأكملها. إذا لزم الأمر، يتم تحديد سلوك قفل مختلف لجداول مختلفة. إذا تم ذكر نفس الجدول (أو الجدول المتأثر ضمنيًا) في أكثر من عبارة قفل واحدة، فسيتم معالجته كما لو تم تحديده بواسطة العبارة الأقوى فقط. وبالمثل، تتم معالجة الجدول كـ NOWAIT إذا تم تحديد تلك العبارة في أي من العبارات التي تؤثر عليه. خلاف ذلك، يتم معالجته كـ SKIP LOCKED إذا تم تحديد تلك العبارة في أي من العبارات التي تؤثر عليه. لا يمكن استخدام عبارات القفل في سياقات لا يمكن فيها تحديد الصفوف التي تم إرجاعها بوضوح مع صفوف فردية من الجدول؛ على سبيل المثال، لا يمكن استخدامها مع التجميع. عندما تظهر عبارة قفل في المستوى الأعلى من استعلام SELECT، فإن الصفوف المقفلة هي بالضبط تلك التي يرجعها الاستعلام؛ في حالة استعلامات الربط، تكون الصفوف المقفلة هي تلك التي تساهم في الصفوف التي تم إرجاعها في الربط. بالإضافة إلى ذلك، سيتم قفل الصفوف التي تلبي شروط الاستعلام في لقطة الاستعلام، حتى لو لم يتم إرجاعها إذا تم تحديثها بعد اللقطة ولم تعد تلبي شروط الاستعلام. إذا تم استخدام LIMIT، يتوقف القفل بمجرد إرجاع عدد كافٍ من الصفوف لتلبية الحد (على الرغم من أن الصفوف التي تم تخطيها بواسطة OFFSET سيتم قفلها). وبالمثل، إذا تم استخدام عبارة قفل في استعلام مع مؤشر، فسيتم قفل الصفوف التي تم تحميلها أو المرور عليها فعليًا بواسطة المؤشر فقط. عندما تظهر عبارة قفل في استعلام فرعي، فإن الصفوف المقفلة هي تلك التي يرجعها الاستعلام الفرعي في الاستعلام الرئيسي. قد يتضمن هذا عددًا أقل من الصفوف مما قد توحي به معاينة الاستعلام الفرعي، حيث يمكن استخدام شروط الاستعلام الرئيسي لتحسين تنفيذ الاستعلام الفرعي. على سبيل المثال: ```sql SELECT * FROM (SELECT * FROM mytable FOR UPDATE) ss WHERE col1 = 5; ``` سيقوم بقفل الصفوف التي بها col1 = 5 فقط، على الرغم من أن الشرط ليس داخل الاستعلام الفرعي نصيًا. فشلت الإصدارات السابقة من النظام في الحفاظ على قفل تم تحديثه بواسطة نقطة حفظ لاحقة. على سبيل المثال، هذا الكود: ```sql BEGIN; SELECT * FROM mytable WHERE key = 1 FOR UPDATE; SAVEPOINT s; UPDATE mytable SET ... WHERE key = 1; ROLLBACK TO s; ``` لم يحافظ على قفل FOR UPDATE بعد ROLLBACK TO. تم إصلاح هذا في الإصدار 9.3. **انتباه** من الممكن أن يقوم استعلام SELECT الذي يتم تنفيذه في مستوى العزل READ COMMITTED ويستخدم ORDER BY وعبارة قفل بإرجاع صفوف بترتيب غير متسلسل. يحدث هذا لأن ORDER BY يتم تطبيقه أولاً. يقوم الاستعلام بترتيب النتائج، ولكنه قد يمنع بعد ذلك الحصول على قفل على أي من الصفوف. بمجرد تحرير الاستعلام، قد تكون بعض قيم عمود الترتيب قد تم تعديلها، مما يتسبب في ظهور الصفوف بترتيب غير متسلسل (على الرغم من أنها مرتبة وفقًا للقيم الأصلية). يمكن التحايل على هذا عن طريق وضع عبارة FOR UPDATE/SHARE في استعلام فرعي، على سبيل المثال: ```sql SELECT * FROM (SELECT * FROM mytable FOR UPDATE) ss ORDER BY column1; ``` ملاحظة: هذا الشكل سيقفل جميع صفوف mytable، على الرغم من أن قفل FOR UPDATE في المستوى الأعلى سيقفل الصفوف التي تم إرجاعها فعليًا فقط. قد يتسبب هذا في فرق كبير في الأداء، خاصة إذا كان الترتيب مقترنًا بـ LIMIT أو قيود. لذلك، يوصى بهذه التقنية فقط إذا كان من المتوقع حدوث تحديث متزامن لأعمدة الترتيب وكان مطلوبًا نتيجة مرتبة بالكامل. في مستوى العزل REPEATABLE READ أو SERIALIZABLE، سيؤدي هذا إلى فشل التسلسل (مع حالة SQLSTATE '40001')، لذلك لا يمكن تلقي أي صفوف بترتيب غير متسلسل تحت هذه المستويات من العزل. --- **التوافق** بطبيعة الحال، فإن عبارة SELECT متوافقة مع معيار SQL. ومع ذلك، هناك بعض الامتدادات والميزات المفقودة. ### عبارات FROM المحذوفة يسمح PostgreSQL بحذف عبارة FROM. لها استخدام بسيط لحساب نتائج تعبيرات بسيطة: ```sql SELECT 2+2; ?column? ---------- 4 ``` لا يمكن لبعض قواعد بيانات SQL الأخرى القيام بذلك إلا عن طريق إدخال جدول وهمي من صف واحد يتم منه تشغيل SELECT. ### قوائم تحديد فارغة يمكن أن تكون قائمة التعبيرات الناتجة بعد SELECT فارغة، مما ينتج عنه جدول نتائج من صفر أعمدة. هذا غير صالح وفقًا لمعيار SQL. يسمح PostgreSQL بذلك بما يتوافق مع تحمل الجداول ذات الأعمدة الصفرية. ومع ذلك، لا يُسمح بقائمة فارغة عند استخدام DISTINCT. ### حذف الكلمة الرئيسية AS في معيار SQL، يمكن حذف الكلمة الرئيسية الاختيارية AS. postgresql(7) — PostgreSQL 18.1 manual

COMPATIBILITY

This section describes PostgreSQL compatibility with the SQL standard.

AS Keyword

In standard SQL, the keyword AS can be omitted before an output column name whenever the new column name is a valid column name (that is, not the same as any reserved keyword). PostgreSQL is slightly more restrictive: AS is required if the new column name matches any keyword at all, reserved or not. Recommended practice is to use AS or double-quote output column names, to prevent any possible conflict against future keyword additions.

In FROM items, both the standard and PostgreSQL allow AS to be omitted before an alias that is an unreserved keyword. But this is impractical for output column names, because of syntactic ambiguities.

Omitting Sub-SELECT Aliases in FROM

According to the SQL standard, a sub-SELECT in the FROM list must have an alias. In PostgreSQL, this alias may be omitted.

ONLY and Inheritance

The SQL standard requires parentheses around the table name when writing ONLY, for example SELECT * FROM ONLY (tab1), ONLY (tab2) WHERE .... PostgreSQL considers these parentheses to be optional.

PostgreSQL allows a trailing * to be written to explicitly specify the non-ONLY behavior of including child tables. The standard does not allow this.

(These points apply equally to all SQL commands supporting the ONLY option.)

TABLESAMPLE Clause Restrictions

The TABLESAMPLE clause is currently accepted only on regular tables and materialized views. According to the SQL standard it should be possible to apply it to any FROM item.

Function Calls in FROM

PostgreSQL allows a function call to be written directly as a member of the FROM list. In the SQL standard it would be necessary to wrap such a function call in a sub-SELECT; that is, the syntax FROM func(...) alias is approximately equivalent to FROM LATERAL (SELECT func(...)) alias. Note that LATERAL is considered to be implicit; this is because the standard requires LATERAL semantics for an UNNEST() item in FROM. PostgreSQL treats UNNEST() the same as other set-returning functions.

Namespace Available to GROUP BY and ORDER BY

In the SQL-92 standard, an ORDER BY clause can only use output column names or numbers, while a GROUP BY clause can only use expressions based on input column names. PostgreSQL extends each of these clauses to allow the other choice as well (but it uses the standard's interpretation if there is ambiguity). PostgreSQL also allows both clauses to specify arbitrary expressions. Note that names appearing in an expression will always be taken as input-column names, not as output-column names.

SQL:1999 and later use a slightly different definition which is not entirely upward compatible with SQL-92. In most cases, however, PostgreSQL will interpret an ORDER BY or GROUP BY expression the same way SQL:1999 does.

Functional Dependencies

PostgreSQL recognizes functional dependency (allowing columns to be omitted from GROUP BY) only when a table's primary key is included in the GROUP BY list. The SQL standard specifies additional conditions that should be recognized.

LIMIT and OFFSET

The clauses LIMIT and OFFSET are PostgreSQL-specific syntax, also used by MySQL. The SQL:2008 standard has introduced the clauses OFFSET ... FETCH {FIRST|NEXT} ... for the same functionality, as shown above in LIMIT Clause. This syntax is also used by IBM DB2. (Applications written for Oracle frequently use a workaround involving the automatically generated rownum column, which is not available in PostgreSQL, to implement the effects of these clauses.)

FOR NO KEY UPDATE, FOR UPDATE, FOR SHARE, FOR KEY SHARE

Although FOR UPDATE appears in the SQL standard, the standard allows it only as an option of DECLARE CURSOR. PostgreSQL allows it in any SELECT query as well as in sub-SELECTs, but this is an extension. The FOR NO KEY UPDATE, FOR SHARE and FOR KEY SHARE variants, as well as the NOWAIT and SKIP LOCKED options, do not appear in the standard.

Data-Modifying Statements in WITH

PostgreSQL allows INSERT, UPDATE, DELETE, and MERGE to be used as WITH queries. This is not found in the SQL standard.

Nonstandard Clauses

DISTINCT ON ( ... ) is an extension of the SQL standard.

ROWS FROM( ... ) is an extension of the SQL standard.

The MATERIALIZED and NOT MATERIALIZED options of WITH are extensions of the SQL standard.
