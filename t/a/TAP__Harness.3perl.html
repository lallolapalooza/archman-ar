TAP__Harness.3perl

الحزمة: perl

التراخيص: Artistic-1.0-Perl OR GPL-1.0-or-later

. للحصول على التفاصيل الكاملة لهيكل البيانات ومطابقة النمط بأسلوب glob ذي الصلة، راجع "هيكل بيانات القواعد" في TAP::Parser::Scheduler.

# تشغيل جميع الاختبارات بالتسلسل، باستثناء تلك التي تبدأ بـ "p"
$harness->rules({
    par => 't/p*.t'
});
# ملف YAML مكافئ
---
par: t/p*.t
# تشغيل جميع الاختبارات بالتوازي، باستثناء تلك التي تبدأ بـ "p"
$harness->rules({
    seq => [
              { seq => 't/p*.t' },
              { par => '**'     },
           ],
});
# ملف YAML مكافئ
---
seq:
    - seq: t/p*.t
    - par: **
# تشغيل بعض اختبارات بدء التشغيل بالتسلسل، ثم بعض الاختبارات المتوازية ثم بعض
# اختبارات إنهاء التشغيل بالتسلسل.
$harness->rules({
    seq => [
        { seq => 't/startup/*.t' },
        { par => ['t/a/*.t','t/b/*.t','t/c/*.t'], }
        { seq => 't/shutdown/*.t' },
    ],
});
# ملف YAML مكافئ
---
seq:
    - seq: t/startup/*.t
    - par:
        - t/a/*.t
        - t/b/*.t
        - t/c/*.t
    - seq: t/shutdown/*.t

هذه ميزة تجريبية وقد يتغير الواجهة.

  • "rulesfiles"

    يحدد هذا المكان الذي سيتم فيه العثور على ملف YAML لقواعد جدولة الاختبارات. إذا لم يتم توفيره، فإنه يبحث عن ملف افتراضي لاستخدامه. يتحقق أولاً من وجود ملف معين في متغير البيئة "HARNESS_RULESFILE"، ثم يتحقق من testrules.yml ثم t/testrules.yml.

  • "stdout"

    مقبض ملف لالتقاط الإخراج القياسي.

  • "trap"

    محاولة طباعة معلومات الملخص إذا تمت مقاطعة التشغيل بواسطة SIGINT (Ctrl-C).

    • سيتم تجاهل أي مفاتيح تكون قيمتها "undef".

    طرق المثيل

    "runtests"

    $harness->runtests(@tests);

    يقبل مصفوفة من @tests ليتم تشغيلها. يجب أن تكون هذه بشكل عام أسماء ملفات الاختبار، ولكن هذا ليس مطلوبًا. سيتم تمرير كل عنصر في @tests إلى TAP::Parser::new() كـ "source". راجع TAP::Parser لمزيد من المعلومات.

    من الممكن توفير أسماء مستعارة سيتم عرضها بدلاً من اسم الاختبار عن طريق توفير الاختبار كمرجع لمصفوفة تحتوي على "[ $test, $alias ]":

    $harness->runtests( [ 't/foo.t', 'Foo Once' ] ,
                    [ 't/foo.t', 'Foo Twice' ] );

    عادةً ما يكون خطأ محاولة تشغيل نفس الاختبار مرتين. تتيح لك الأسماء المستعارة تجاوز هذا القيد عن طريق إعطاء كل تشغيل للاختبار اسمًا فريدًا.

    سيتم تشغيل الاختبارات بالترتيب الذي تم العثور عليها به.

    إذا كان متغير البيئة "PERL_TEST_HARNESS_DUMP_TAP" معرفًا، فيجب أن يحدد دليلاً سيتم فيه كتابة نسخة من TAP الخام لكل اختبار. تتم كتابة TAP في ملفات مسماة لكل اختبار. سيتم إنشاء أدلة فرعية حسب الحاجة.

    يعيد TAP::Parser::Aggregator يحتوي على نتائج الاختبار.

    "summary"

    $harness->summary( $aggregator );

    طباعة الملخص لـ TAP::Parser::Aggregator.

    "aggregate_tests"

    $harness->aggregate_tests( $aggregate, @tests );

    قم بتشغيل الاختبارات المسماة وعرض ملخص للنتائج. سيتم تشغيل الاختبارات بالترتيب الذي تم العثور عليها به.

    ستتم إضافة نتائج الاختبار إلى TAP::Parser::Aggregator المقدم. يمكن استدعاء "aggregate_tests" عدة مرات لتشغيل مجموعات متعددة من الاختبارات. يمكن استخدام مثيلات "Test::Harness" متعددة لتمرير النتائج إلى مجمع واحد بحيث يمكن تشغيل أجزاء مختلفة من مجموعة اختبارات معقدة باستخدام إعدادات "TAP::Harness" مختلفة. هذا مفيد، على سبيل المثال، في الحالة التي يجب فيها تشغيل بعض الاختبارات بالتوازي ولكن البعض الآخر غير مناسب للتنفيذ المتوازي.

    my $formatter   = TAP::Formatter::Console->new;
my $ser_harness = TAP::Harness->new( { formatter => $formatter } );
my $par_harness = TAP::Harness->new(
    {   formatter => $formatter,
        jobs      => 9
    }
);
my $aggregator = TAP::Parser::Aggregator->new;
$aggregator->start();
$ser_harness->aggregate_tests( $aggregator, @ser_tests );
$par_harness->aggregate_tests( $aggregator, @par_tests );
$aggregator->stop();
$formatter->summary($aggregator);

    لاحظ أنه بالنسبة لمتطلبات الاختبار الأبسط، غالبًا ما يكون من الممكن استبدال الكود أعلاه باستدعاء واحد لـ "runtests".

    كل عنصر في مصفوفة @tests هو:

    • اسم المصدر للاختبار المراد تشغيله
    • مرجع لمصفوفة [ اسم المصدر، اسم العرض ]

    في حالة مجموعة اختبارات perl، عادةً ما تكون أسماء المصادر مجرد أسماء ملفات نصوص الاختبار المراد تشغيلها.

    عندما توفر اسم عرض منفصل، يصبح من الممكن تشغيل اختبار أكثر من مرة؛ اسم العرض هو فعليًا الاسم المستعار الذي يُعرف به الاختبار داخل الـ harness. لا يهتم الـ harness بما إذا كان يشغل نفس الاختبار أكثر من مرة عندما يستخدم كل استدعاء اسمًا مختلفًا.

    "make_scheduler"

    يتم استدعاؤه بواسطة الـ harness عندما يحتاج إلى إنشاء TAP::Parser::Scheduler. تجاوز في فئة فرعية لتوفير مجدول بديل. يتم تمرير قائمة الاختبارات التي تم تمريرها إلى "aggregate_tests" إلى "make_scheduler".

    "jobs"

    يحصل على عدد عمليات تشغيل الاختبار المتزامنة التي يتعامل معها الـ harness أو يضبطه. بشكل افتراضي، هذه القيمة هي 1 - للاختبار المتوازي، يجب ضبطها على قيمة أعلى.

    "make_parser"

    إنشاء محلل جديد وجلسة تنسيق عرض. يستخدم عادةً ويتجاوز في الفئات الفرعية.

    my ( $parser, $session ) = $harness->make_parser;

    "finish_parser"

    إنهاء استخدام المحلل. يستخدم عادةً ويتجاوز في الفئات الفرعية. لا يتم تدمير المحلل نتيجة لذلك.

    الإعداد

    "TAP::Harness" مصمم ليكون سهل الإعداد.

    الإضافات

    تتيح لك إضافات "TAP::Parser" تغيير طريقة إدخال TAP إلى المحلل أو إخراجه منه.

    تتعامل TAP::Parser::SourceHandlers مع إدخال TAP. يمكنك تكوينها وتحميل معالجات مخصصة باستخدام المعلمة "sources" لـ "new".

    تتعامل TAP::Formatters مع إخراج TAP. يمكنك تحميل منسقات مخصصة عن طريق استخدام المعلمة "formatter_class" لـ "new". لتكوين منسق، تحتاج حاليًا إلى إنشاء مثيل له خارج TAP::Harness وتمريره باستخدام المعلمة "formatter" لـ "new". قد يتم معالجة هذا عن طريق إضافة معلمة formatters إلى "new" في المستقبل.

    "Module::Build"

    يدعم Module::Build الإصدار 0.30 "TAP::Harness".

    لتحميل إضافات "TAP::Harness"، ستحتاج إلى استخدام المعلمة "tap_harness_args" لـ "new"، عادةً من "Build.PL" الخاص بك. على سبيل المثال:

    Module::Build->new(
    module_name        => 'MyApp',
    test_file_exts     => [qw(.t .tap .txt)],
    use_tap_harness    => 1,
    tap_harness_args   => {
        sources => {
            MyCustom => {},
            File => {
                extensions => ['.tap', '.txt'],
            },
        },
        formatter_class => 'TAP::Formatter::HTML',
    },
    build_requires     => {
        'Module::Build' => '0.30',
        'TAP::Harness'  => '3.18',
    },
)->create_build_script;

    راجع "new"

    "ExtUtils::MakeMaker"

    لا يدعم ExtUtils::MakeMaker TAP::Harness بشكل افتراضي.

    "prove"

    يدعم prove إضافات "TAP::Harness"، ولديه نظام إضافات خاص به. راجع "FORMATTERS" في prove، و "SOURCE HANDLERS" في prove و App::Prove لمزيد من التفاصيل.

    كتابة الإضافات

    إذا لم تتمكن من تكوين "TAP::Harness" للقيام بما تريده، ولم تجد إضافة موجودة، ففكر في كتابة واحدة.

    حالات الاستخدام الرئيسية التي تدعمها TAP::Harness للإضافات هي الإدخال و الإخراج:

    تخصيص كيفية دخول TAP إلى المحلل
    للقيام بذلك، يمكنك إما توسيع TAP::Parser::SourceHandler موجود، أو كتابة الخاص بك. إنها واجهة برمجة تطبيقات بسيطة جدًا، ويمكن تحميلها وتكوينها باستخدام المعلمة "sources" لـ "new".
    تخصيص كيفية إخراج نتائج TAP من المحلل
    للقيام بذلك، يمكنك إما توسيع TAP::Formatter موجود، أو كتابة الخاص بك. كتابة المنسقات أكثر تعقيدًا قليلاً من كتابة SourceHandler، حيث ستحتاج إلى فهم واجهة برمجة تطبيقات TAP::Parser. مكان جيد للبدء هو فهم كيفية عمل "aggregate_tests".

    يمكن تحميل المنسقات المخصصة وتكوينها باستخدام المعلمة "formatter_class" لـ "new".
