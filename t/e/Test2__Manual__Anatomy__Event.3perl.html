FACETAS PERSONALIZADAS

Puedes escribir tipos de facetas personalizadas, simplemente añade un nuevo key a la hash y poblalo. La regla general es que cualquier código que vea las facetas debe ignorar las que no entiende.

Opcionalmente puedes crear una paquete para documentar tus facetas personalizadas. El paquete debe ser un objeto correcto y puede tener métodos adicionales para ayudar a trabajar con tu faceta.

package Test2::EventFacet::MyFacet;
use parent 'Test2::EventFacet';
sub facet_key { 'myfacet' }
sub is_list { 0 }
1;

Tu paquete de faceta debe estar siempre bajo el espacio de nombre Test2::EventFacet:: si quieres que los herramientas lo encuentren automáticamente. El último parte del nombre del espacio debe ser el nombre no plural de tu faceta, con solo la primera palabra mayúscula.

$string = $facet_class->facet_key
El key de tu faceta debería ser el mismo que el último apartado del espacio de nombre, pero en minúsculas. Puedes append 's' al key si tu faceta es de tipo lista.
$bool = $facet_class->is_list
True si un evento debe poner estas facetas en una lista: 
{ myfacet => [{}, {}] }

False si un evento solo puede tener una de esta tipo de faceta a la vez:

{ myfacet => {} }

EJEMPLOS

El faceta assert no es de tipo lista, por lo que su implementación sería así:

package Test2::EventFacet::Assert;
sub facet_key { 'assert' }
sub is_list { 0 }

El faceta amnesty es de tipo lista, pero no necesita 's' appendido para ser plural:

package Test2::EventFacet::Amnesty;
sub facet_key { 'amnesty' }
sub is_list { 1 }

El faceta error es de tipo lista, y append 's' hace plural de error. Esto significa que el nombre del paquete es '::Error', pero el key es 'errors'.

package Test2::EventFacet::Error;
sub facet_key { 'errors' }
sub is_list { 1 }

Nota2: En la práctica, los más herramientas ignoran los paquetes de faceta, y trabajan con los datos de la faceta directamente en su estructura. Esto es por diseño y recomendado. Los datos de la faceta están diseñados para ser serializados frecuentemente y pasados alrededor. Cuando se trate de facetas, los datos son importantes, clases y métodos no lo son.

LA API ANTIGUA

La API antigua simplemente era un conjunto de métodos que debías implementar:

$bool = $e->causes_fail
Devuelve true si este evento debe resultar en una falla de prueba. En general, debería ser false.
$bool = $e->increments_count
Debes devolver true si este evento debe provocar un incremento en el contador de pruebas.
$e->callback($hub)
Si tu evento necesita tener efectos adicionales sobre el Test2::Hub, puedes sobrescribir este método.

Este método se llama ANTES de que el evento sea pasado al formateador.

$num = $e->nested
Si este evento está dentro de otros eventos, debe ser el nivel de nesting. (Esto es principalmente para subpruebas)
$bool = $e->global
Establece este a true si tu evento es global, es decir, todos los hilos y procesos deben verlo, sea cuando o donde se genere. Esto no es algo común, pero se usa para salir de pruebas con bail-out y skip_all.
$code = $e->terminate
Este se llama DESPUÉS de que el evento haya sido pasado al formateador. Debería normalmente devolver undef, pero solo cambia si el evento debe hacer que la prueba se termine inmediatamente.

Si quieres que el evento cause que la prueba se termine, deberías devolver el código de salida aquí. El código de salida de 0 significa exito, cualquier otro número significa falla.

Este se usa por Test2::Event::Plan para salir con 0 cuando el plan es 'skip_all'. También se usa por Test2::Event:Bail para forzar la prueba a terminar con una falla.

Este se llama después de que el evento haya sido enviado al formateador para asegurar que el evento sea visto y entendido.

$msg = $e->summary
Esto se utiliza como una resumen humano de evento. Deberías tener un resumen idealmente una línea, pero puedes usar múltiples si es necesario. Esto se utiliza para consumo humano. No necesitas hacerlo fácil para máquinas.

El por defecto es simplemente devolver el nombre del paquete del evento.

($count, $directive, $reason) = $e->sets_plan()
Verifica si este evento establece el plan de prueba. Devolverá una lista vacía si no lo hace. Si lo hace, devolverá una lista de 1 a 3 elementos en orden: Cuenta de pruebas esperada, Directiva, razón de la directiva.
$bool = $e->diagnostics
True si el evento contiene información de diagnóstico. Esto es útil porque un harness no verbose puede elegir ocultar eventos no en este categoría. Algunos formateadores pueden elegir enviar estos a STDERR en lugar de STDOUT para asegurar que se vean.
$bool = $e->no_display
False por defecto. Este devolverá true en eventos que no deben mostrarse por formateadores.
