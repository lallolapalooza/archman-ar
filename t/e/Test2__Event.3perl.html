Test2::Event(3perl) دليل مبرمج Perl Test2::Event(3perl)

الاسم

Test2::Event - فئة أساسية للأحداث

الوصف

فئة أساسية لجميع كائنات الأحداث التي يتم تمريرها بواسطة Test2.

الملخص

package Test2::Event::MyEvent;
use strict;
use warnings;
# سيؤدي هذا إلى جعل فئتنا فئة فرعية للحدث (مطلوب)
use base 'Test2::Event';
# إضافة بعض المستقبليين (اختياري)
# لست ملزمًا باستخدام HashBase، يمكنك استخدام أي أداة كائن تريدها، أو يمكنك إنشاء المستقبليين الخاصين بك.
use Test2::Util::HashBase qw/foo bar baz/;
# استخدم هذا إذا كنت تريد أن يتم كتابة واجهة برمجة التطبيقات القديمة لك، لكي يعمل هذا، ستحتاج إلى تنفيذ طريقة facet_data().
use Test2::Util::Facets2Legacy;
# فرصة لتهيئة بعض القيم الافتراضية
sub init {
    my $self = shift;
    # لا توجد وسائط أخرى في @_ 
    $self->set_foo('xxx') unless defined $self->foo;
    ...
}
# هذا هو الوضع الجديد لنقل البيانات إلى Test2
sub facet_data {
    my $self = shift;
    # الحصول على أوجه التشابه الشائعة مثل 'about'، 'trace'، 'amnesty'، و 'meta'
    my $facet_data = $self->common_facet_data();
    # هل تجري تأكيدًا؟
    $facet_data->{assert} = {pass => 1, details => 'تأكيدي'};
    ...
    return $facet_data;
}
1;

عام

$trace = $e->trace
يحصل على لقطة من Test2::EventFacet::Trace الخاص بـ Test2::Event كما كان عند إنشاء هذا الحدث.
$bool_or_undef = $e->related($e2)
يتحقق مما إذا كان حدثان مرتبطان. في هذه الحالة، يعني الارتباط أن تتبعهما مشتركة، مما يشير إلى أنهما تم إنشاؤهما بنفس السياق (أو على الأقل بواسطة سياقات تشترك في معرف، وهو نفس الشيء، ما لم يكن شخص ما يفعل شيئًا سيئًا للغاية).

يمكن استخدام هذا لربط أحداث متعددة تم إنشاؤها بواسطة نفس البرنامج. على سبيل المثال، اختبار فاشل مثل "ok(0, "fail"" سيؤدي إلى إنشاء حدثين، أحدهما Test2::Event::Ok، والآخر Test2::Event::Diag، وكلاهما مرتبطان، حيث تم إنشاؤهما تحت نفس السياق ومن نفس البرنامج الأولي (على الرغم من أنه قد تكون هناك برامج متعددة داخل البرنامج الأولي).

سيعيد هذا "undef" إذا لم يكن من الممكن التحقق من الارتباط، والذي يحدث إذا كان لأي من الحدثين تتبع غير مكتمل أو غير محدد. سيعيد 0 إذا كانت التتبعات كاملة ولكنها لا تتطابق. سيتم إرجاع 1 إذا كان هناك تطابق.

$e->add_amnesty({tag => $TAG, details => $DETAILS});
يمكن استخدام هذا لإضافة عفو إلى هذا الحدث. يؤثر العفو فقط على التأكيدات الفاشلة، ولكن قد تعرضها بعض الأدوات لتأكيدات ناجحة أو حتى لغير التأكيدات.

يمنع العفو التأكيد الفاشل من التسبب في فشل الاختبار بأكمله. بمعنى آخر، فإنه يضع علامة على فشل متوقع ومسموح به.

ملاحظة: هذه هي الطريقة التي يتم بها تنفيذ "TODO"، أي "عفو" مع الوسم "TODO". التفاصيل هي سبب TODO.

$uuid = $e->uuid
إذا كان وسم UUID ممكّنًا (انظر Test::API)، فسيتم وسم أي حدث مر عبر محور بمعرف UUID. لن يتم وسم حدث جديد في معظم الحالات.
$class = $e->load_facet($name)
تُستخدم هذه الطريقة لتحميل جانب بالاسم (أو المفتاح). ستحاول تحميل فئة الجانب، وإذا نجحت، فستعيد الفئة التي تم تحميلها. إذا فشلت، فستعيد "undef". تقوم بتخزين النتيجة مؤقتًا على مستوى الفئة بحيث تكون الاستدعاءات اللاحقة أسرع.

يجب أن يكون المعامل $name هو المفتاح المستخدم للوصول إلى الجانب في تجزئة البيانات. على سبيل المثال، جانب التأكيد لديه المفتاح 'assert'، وجانب المعلومات لديه 'info'، وجانب الخطأ لديه 'errors'. يمكنك تضمين أو حذف 's' في نهاية الاسم، والطريقة ذكية لمحاولة كلا الشكلين، والتحقق أولاً مما قدمته، وإذا لم تجده، فستضيفه أو تزيل 's' وتحاول مرة أخرى.

@classes = $e->FACET_TYPES()
@classes = Test2::Event->FACET_TYPES()
يعيد هذا قائمة بجميع الجوانب التي تم تحميلها باستخدام الطريقة load_facet(). لا يعيد أي فئات لم يتم تحميلها، أو التي تم تحميلها مباشرة دون استدعاء load_facet().

ملاحظة: يتم تحميل أنواع الجوانب الأساسية تلقائيًا وملؤها في هذه القائمة.

واجهة برمجة التطبيقات الجديدة

$hashref = $e->common_facet_data();
يمكن استخدام هذا بواسطة الفئات الفرعية لإنشاء تجزئة بيانات أولية. سيقوم بملء التجزئة بالمسار (trace) والبيانات الوصفية (meta) والعفو (amnesty) والمعلومات (about). يتم إنتاج هذه الجوانب دائمًا بنفس الطريقة لجميع الأحداث.
$hashref = $e->facet_data()
إذا لم تتجاوز هذه الطريقة، فإن التنفيذ الافتراضي سيحاول إنشاء بيانات الجانب من واجهة برمجة التطبيقات القديمة. هذا الإنشاء مقيد فقط بما يمكن لواجهة برمجة التطبيقات القديمة توفيره. يوصى بتجاوز هذه الطريقة وكتابة بيانات الجانب بشكل صريح.
$hashref = $e->facets()
تأخذ هذه الطريقة تجزئة البيانات من facet_data() وتُعَيّن كل جانب في الفئة المقابلة "Test2::EventFacet::*". إذا تعذر العثور على الفئة لأي جانب، فسيتم تمريرها دون تغيير.
@errors = $e->validate_facet_data();
@errors = $e->validate_facet_data(%params);
@errors = $e->validate_facet_data(\%facets, %params);
@errors = Test2::Event->validate_facet_data(%params);
@errors = Test2::Event->validate_facet_data(\%facets, %params);
ستقوم هذه الطريقة بالتحقق من صحة بيانات الجانب وإرجاع قائمة بالأخطاء. إذا لم تكن هناك أخطاء، فسوف تعيد قائمة فارغة.

يمكن استدعاؤها كطريقة للكائن بدون وسائط، وفي هذه الحالة سيتم استدعاء الطريقة facet_data() للحصول على بيانات الجانب للتحقق من صحتها.

عند استدعائها كطريقة للكائن، يمكن حذف الوسيط "\%facet_data".

عند استدعائها كطريقة للفئة، يكون الوسيط "\%facet_data" مطلوبًا.

سيتم استهلاك الوسائط المتبقية في تجزئة %params.

حاليا، يتم تعريف معامل واحد فقط:

require_facet_class => $BOOL
إذا تم تعيينه على صحيح (الافتراضي هو خطأ)، فسيؤدي ذلك إلى رفض أي جانب لا يمكن العثور على فئته. افتراضيًا، تعتبر الجوانب التي لا تحتوي على فئات مخصصة ويتم تجاهلها.

ما هي الجوانب؟

الجوانب هي كيف تنقل الأحداث غرضها إلى الأجزاء الداخلية لـ Test2 والأدوات. لن يكون للحدث بدون جوانب أي تأثير مقصود على الحالة العامة للاختبار، ولن يتم عرضه في جميع الأدوات تقريبًا، باستثناء ربما القول بأنه تم رؤية حدث من نوع غير معروف.

يتم إنتاج الجوانب بواسطة الإجراء الفرعي facet_data()، والذي يجب عليك تجاوزه في جميع الحالات تقريبًا. يُتوقع من facet_data() أن تعيد تجزئة بيانات حيث يكون كل مفتاح هو نوع الجانب والقيمة هي بيانات لذلك الجانب، أو مصفوفة من تجزئات البيانات. يجب تعريف بعض الجوانب كتجزئات بيانات فقط، والبعض الآخر كمصفوفات من تجزئات البيانات، ولا تسمح بكليهما.

facet_data() يجب ألا تعيّن البيانات التي تعيدها، يجب أن تكون تجزئة البيانات الرئيسية وتجزئات البيانات المتداخلة غير معينة. ومع ذلك، يمكن تعيين العناصر داخل كل جانب. يجب أيضًا أن تكون البيانات التي تعيدها هذه الطريقة نسخًا من البيانات الداخلية لتجنب التعديلات العرضية للحالة.

facets() تأخذ البيانات من facet_data() وتعينها في فئات "Test2::EventFacet::*". نادرًا ما يتم استخدام هذا، ولكن حزم EventFacet هي بشكل أساسي للراحة والتوثيق. لا يتم استخدام فئات EventFacet داخليًا، بل يتم استخدام البيانات المباشرة.

فيما يلي قائمة بأنواع الجوانب حسب الحزمة. لا يتم استخدام الحزم داخليًا، ولكن يتم استخدامها كـ...

هذا الموقع غير مرتبط بـ Arch Linux ولا تابع له بأي شكل من الأشكال. المحتوى هو ترجمة فقط لصفحات دليل Arch المنشورة على man.archlinux.org.

NAME

Test2::Event::Hub - The central hub for all Test2 events.

DESCRIPTION

This is the central hub for Test2 events. It is responsible for passing events to formatters, and for managing the state of testing. Most users will never need to interact with this directly. It is usually created by the test harness.

SYNOPSIS

  use Test2::API;

  my $hub = Test2::API::create_hub();

  # ... run tests ...

  # The hub is automatically destroyed when the process exits.

METHODS

The Test2::Event::Hub object is a composite object. It has a list of facets. Each facet has a specific purpose, and is documented below.

about => {...}
Test2::EventFacet::About

This contains information about the event itself such as the event package name. The "details" field for this facet is an overall summary of the event.

assert => {...}
Test2::EventFacet::Assert

This facet is used if an assertion was made. The "details" field of this facet is the description of the assertion.

control => {...}
Test2::EventFacet::Control

This facet is used to tell the Test2::Event::Hub about special actions the event causes. Things like halting all testing, terminating the current test, etc. In this facet the "details" field explains why any special action was taken.

Note: This is how bail-out is implemented.

meta => {...}
Test2::EventFacet::Meta

The meta facet contains all the meta-data attached to the event. In this case the "details" field has no special meaning, but may be present if something sets the 'details' meta-key on the event.

parent => {...}
Test2::EventFacet::Parent

This facet contains nested events and similar details for subtests. In this facet the "details" field will typically be the name of the subtest.

plan => {...}
Test2::EventFacet::Plan

This facet tells the system that a plan has been set. The "details" field of this is usually left empty, but when present explains why the plan is what it is, this is most useful if the plan is to skip-all.

trace => {...}
Test2::EventFacet::Trace

This facet contains information related to when and where the event was generated. This is how the test file and line number of a failure is known. This facet can also help you to tell if tests are related.

In this facet the "details" field overrides the "failed at test_file.t line 42." message provided on assertion failure.

amnesty => [{...}, ...]
Test2::EventFacet::Amnesty

The amnesty facet is a list instead of a single item, this is important as amnesty can come from multiple places at once.

For each instance of amnesty the "details" field explains why amnesty was granted.

Note: Outside of formatters amnesty only acts to forgive a failing assertion.

errors => [{...}, ...]
Test2::EventFacet::Error

The errors facet is a list instead of a single item, any number of errors can be listed. In this facet "details" describes the error, or may contain the raw error message itself (such as an exception). In perl exception may be blessed objects, as such the raw data for this facet may contain nested items which are blessed.

Not all errors are considered fatal, there is a "fail" field that must be set for an error to cause the test to fail.

Note: This facet is unique in that the field name is 'errors' while the package is 'Error'. This is because this is the only facet type that is both a list, and has a name where the plural is not the same as the singular. This may cause some confusion, but I feel it will be less confusing than the alternative.

info => [{...}, ...]
Test2::EventFacet::Info

The 'info' facet is a list instead of a single item, any quantity of extra information can be attached to an event. Some information may be critical diagnostics, others may be simply commentary in nature, this is determined by the "debug" flag.

For this facet the "details" flag is the info itself. This info may be a string, or it may be a data structure to display. This is one of the few facet types that may contain blessed items.

where the documentation for each type is kept.

Note: Every single facet type has the 'details' field. This field is always intended for human consumption, and when provided, should explain the 'why' for the facet. All other fields are facet specific.

LEGACY API

$bool = $e->causes_fail
Returns true if this event should result in a test failure. In general this should be false.
$bool = $e->increments_count
Should be true if this event should result in a test count increment.
$e->callback($hub)
If your event needs to have extra effects on the Test2::Hub you can override this method.

This is called BEFORE your event is passed to the formatter.

$num = $e->nested
If this event is nested inside of other events, this should be the depth of nesting. (This is mainly for subtests)
$bool = $e->global
Set this to true if your event is global, that is ALL threads and processes should see it no matter when or where it is generated. This is not a common thing to want, it is used by bail-out and skip_all to end testing.
$code = $e->terminate
This is called AFTER your event has been passed to the formatter. This should normally return undef, only change this if your event should cause the test to exit immediately.

If you want this event to cause the test to exit you should return the exit code here. Exit code of 0 means exit success, any other integer means exit with failure.

This is used by Test2::Event::Plan to exit 0 when the plan is 'skip_all'. This is also used by Test2::Event:Bail to force the test to exit with a failure.

This is called after the event has been sent to the formatter in order to ensure the event is seen and understood.

$msg = $e->summary
This is intended to be a human readable summary of the event. This should ideally only be one line long, but you can use multiple lines if necessary. This is intended for human consumption. You do not need to make it easy for machines to understand.

The default is to simply return the event package name.

($count, $directive, $reason) = $e->sets_plan()
Check if this event sets the testing plan. It will return an empty list if it does not. If it does set the plan it will return a list of 1 to 3 items in order: Expected Test Count, Test Directive, Reason for directive.
$bool = $e->diagnostics
True if the event contains diagnostics info. This is useful because a non-verbose harness may choose to hide events that are not in this category. Some formatters may choose to send these to STDERR instead of STDOUT to ensure they are seen.
$bool = $e->no_display
False by default. This will return true on events that should not be displayed by formatters.
$id = $e->in_subtest
If the event is inside a subtest this should have the subtest ID.
$id = $e->subtest_id
If the event is a final subtest event, this should contain the subtest ID.

THIRD PARTY META-DATA

This object consumes Test2::Util::ExternalMeta which provides a consistent way for you to attach meta-data to instances of this class. This is useful for tools, plugins, and other extensions.
