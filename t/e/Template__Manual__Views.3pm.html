Template::Manual::Views - عروض Template Toolkit (تجريبي)

نظرة عامة

العرض هو في الواقع مجموعة من القوالب و/أو تعريفات المتغيرات التي يمكن تمريرها كوحدة قائمة بذاتها. يمثل هذا بعد ذلك واجهة معينة أو أسلوب عرض للأشياء أو البيانات الأخرى.

يمكنك استخدام العروض لتطبيق "جلود" مخصصة لتطبيق أو مجموعة محتوى. يمكنك استخدامها للمساعدة في تبسيط عرض الكائنات أو أنواع البيانات الشائعة. يمكنك حتى استخدامها لأتمتة عرض هياكل البيانات المعقدة مثل تلك الناتجة في شجرة "XML::DOM" أو ما شابه ذلك. أنت تدع المكرر يقوم بالمشي، والعرض يقوم بالحديث (أو في هذه الحالة، العرض). فوالا - لديك عبور مستقل عن العرض، وغير حساس للبنية باستخدام القوالب.

بشكل عام، يمكن استخدام العروض بعدة طرق مختلفة لتحقيق عدة أشياء مختلفة. إنها تحل ببراعة بعض المشاكل التي كانت صعبة أو معقدة في الأصل، وتجعل الأمور سهلة.

في الوقت الحالي، لا تزال تجريبية للغاية. من المحتمل أن تتغير صيغة التوجيهات وواجهة برمجة التطبيقات الأساسية بشكل كبير خلال الإصدار القادم أو الاثنين. يرجى توخي الحذر الشديد عند بناء حلول التجارة الإلكترونية التي تدر عليك ملايين الدولارات بناءً على هذه الميزة.

العروض كمجمعات/مزودات قوالب

يبدأ التوجيه "VIEW" تعريف العرض ويتضمن اسمًا يمكن الإشارة إلى العرض به. يستمر تعريف العرض حتى يصل إلى التوجيه "END" المطابق.

[% VIEW myview %]
   ...
[% END %]

الدور الأول للعرض هو العمل كمجمع ومزود للقوالب. يمكن استدعاء الطريقة include() على عرض للقيام فعليًا بنفس الشيء مثل التوجيه "INCLUDE". يتم تمرير اسم القالب كوسيط أول، متبوعًا بأي تعريفات متغيرات محلية للقالب.

[% myview.include('header', title='The Title') %]
# equivalent to
[% INCLUDE header  title='The Title' %]

تقبل العروض عددًا من خيارات التكوين التي يمكن استخدامها للتحكم في جوانب مختلفة من سلوكها. يمكن تحديد خيارات '"prefix"' و '"suffix"' لإضافة بادئة و/أو لاحقة ثابتة لكل اسم قالب.

[% VIEW myview
     prefix = 'my/'
     suffix = '.tt2' ;
   END
%]

الآن المكالمة

[% myview.include('header', title='The Title') %]

يعادل

[% INCLUDE my/header.tt2  title='The Title' %]

توفر العروض طريقة "AUTOLOAD" التي تربط أسماء الطرق بالطريقة include(). وبالتالي، فإن ما يلي متكافئ جميعًا:

[% myview.include('header', title='Hello World') %]
[% myview.include_header(title='Hello World') %]
[% myview.header(title='Hello World') %]

تعريفات BLOCK المحلية

يمكن أن يتضمن تعريف "VIEW" تعريفات "BLOCK" التي تظل محلية للعرض. طلب قالب معين سيعيد "BLOCK"، إذا تم تعريفه، تفضيلًا لأي قالب آخر بنفس الاسم.

[% BLOCK foo %]
   public foo block
[% END %]
[% VIEW plain %]
   [% BLOCK foo %]
   plain foo block
   [% END %]
[% END %]
[% VIEW fancy %]
   [% BLOCK foo %]
   fancy foo block
   [% END %]
[% END %]
[% INCLUDE foo %]       # public foo block
[% plain.foo %]         # plain foo block
[% fancy.foo %]         # fancy foo block

بالإضافة إلى تعريفات "BLOCK"، يمكن أن يحتوي "VIEW" على أي توجيهات قوالب أخرى. يتم معالجة كتلة تعريف "VIEW" بأكملها لتهيئة العرض ولكن لا يتم إنشاء أي إخراج (قد يتغير هذا قريبًا - ويتم تخزينه كعنصر '"output"'، يمكن الوصول إليه لاحقًا كـ '"[% view.output %]"'). ومع ذلك، فإن التوجيهات التي لها آثار جانبية، مثل تلك التي تحدث متغيرًا، ستكون لها عواقب ملحوظة.

الحفاظ على حالة المتغيرات داخل العروض

يمكن أيضًا استخدام العروض لحفظ قيم أي متغيرات موجودة، أو لإنشاء متغيرات جديدة عند تعريف العرض. على عكس بيانات التعريف البسيطة للقوالب ("META") التي لا يمكن أن تحتوي إلا على قيم نصية ثابتة، يمكن أن تحتوي كتلة تهيئة العرض على أي توجيهات قوالب وإنشاء أي نوع من الإخراج الديناميكي و/أو عناصر البيانات.

[% VIEW my_web_site %]
   [% view.title   = title or 'My Cool Web Site' %]
   [% view.author  = "$abw.name, $abw.email" %]
   [% view.sidebar = INCLUDE my/sidebar.tt2 %]
[% END %]

لاحظ أنه يمكن تحديد عناصر بيانات إضافية كوسائط للتوجيه "VIEW". يُفترض أن أي شيء لا يبدو كمعامل تكوين هو عنصر بيانات. قد يكون هذا خطيرًا بعض الشيء، بالطبع، لأنك لا تعرف أبدًا متى قد تتم إضافة عنصر تكوين جديد يتعارض مع بياناتك.

[% VIEW my_web_site
        # config options
        prefix = 'my/'
        # misc data
        title   = title or 'My Cool Web Site'
        author  = "$abw.name, $abw.email"
        sidebar = INCLUDE my/sidebar.tt2
%]
   ...
[% END %]

خارج تعريف العرض، يمكنك الوصول إلى متغيرات العرض على سبيل المثال:

[% my_web_site.title %]

أحد الميزات الهامة هو تكافؤ المتغيرات البسيطة والقوالب. يمكنك تنفيذ عنصر العرض '"title"' كمتغير بسيط، أو قالب معرف في ملف خارجي، ربما مع إضافة بادئة/لاحقة تلقائيًا، أو كتعريف "BLOCK" محلي داخل تعريف "[% VIEW %] ... [% END %]". إذا استخدمت الصيغة أعلاه، فسيتولى العرض الأمر "القيام بالصواب" لإعادة الإخراج المناسب.

عند نهاية كتلة تعريف "VIEW"، يتم "ختم" العرض لمنعك من تحديث أي قيم للمتغيرات عن طريق الخطأ. إذا حاولت تغيير قيمة متغير بعد نهاية كتلة تعريف "VIEW"، فسيتم طرح خطأ "view".

[% TRY;
     my_web_site.title = 'New Title';
   CATCH;
     error;
   END
%]

سيتم الإبلاغ عن الخطأ أعلاه كالتالي:

view error - cannot update item in sealed view: title

وينطبق الشيء نفسه إذا قمت بتمرير وسيط إلى متغير عرض. يتم تفسير هذا كمحاولة لتحديث المتغير وسيرفع نفس التحذير.

[% my_web_site.title('New Title') %]    # view error!

يمكنك تعيين المعلمة "silent" لجعل العرض يتجاهل هذه الوسائط ويعيد ببساطة قيمة المتغير.

[% VIEW my_web_site
        silent = 1
        title  = title or 'My Cool Web Site'
        # ... ;
   END
%]
[% my_web_site.title('Blah Blah') %]   # My Cool Web Site

بدلاً من ذلك، يمكنك تحديد أن العرض غير مختوم، مما يسمح بتحديث المتغيرات الموجودة وتعريف متغيرات جديدة.

[% VIEW my_web_site
        sealed = 0
        title  = title or 'My Cool Web Site'
        # ... ;
   END
%]
[% my_web_site.title('Blah Blah') %]   # Blah Blah
[% my_web_site.title %]                # Blah Blah

الوراثة، التفويض وإعادة الاستخدام

يمكن وراثة العروض من عروض معرفة سابقًا باستخدام المعلمة "base". يوضح هذا المثال كيفية تعريف عرض فئة أساسية يطبق بادئة "view/default/" على جميع أسماء القوالب.

[% VIEW my.view.default
        prefix = 'view/default/';
   END
%]

وبالتالي، فإن التوجيه:

[% my.view.default.header(title='Hello World') %]

يعادل الآن:

[% INCLUDE view/default/header title='Hello World' %]

عرض ثانٍ يمكن

This is a basic example of how you can use inheritance to build up a hierarchy of views. You can also use it for delegation. For example, you might have a view which delegates the rendering of specific objects to another view.

A view can be specified to act as a delegate for a particular object type, or any object matching a given regular expression.

[% VIEW default_handler
        # ... definition ...
   END
%]
[% VIEW xml_handler
        # ... definition ...
        delegate = default_handler
   END
%]
[% VIEW json_handler
        # ... definition ...
        delegate = default_handler
   END
%]
[% VIEW main
        # ... definition ...
   END
%]
[% WRAPPER my.wrapper %]
   [% PROCESS main %]
[% END %]

If the object being processed by the "main" view has a type of "xml" then the "xml_handler" view will be used to process it. If the type is "json" then the "json_handler" view will be used. Otherwise, the "default_handler" view will be used.

The delegate view is instantiated with the same arguments as the original object, and the result of the delegate's processing is returned.

You can create a recursive view definition by specifying the view itself as the delegate.

[% VIEW my_recursive_view
        delegate = self
   END
%]
[% my_recursive_view.process(data) %]

The view will be instantiated recursively as each item in the data structure is processed. The recursion stops when the processed item is not a list or hash, or when the item is an empty list or hash.

واجهة برمجة تطبيقات العرض

A view object has the following methods:

include($template, %args)

Includes the specified template, passing any additional arguments as local variables.

clear()

Clears all cached templates and definitions within the view.

define($name, $code, [%cached=1%])

Dynamically defines a template, block, or variable named $name with the value $code. If $cached is true (the default), the definition is cached for subsequent use.

addpath($path, [%cached=1%])

Adds a directory path to the search path for templates used by the view. If $cached is true (the default), template search paths are cached for subsequent use.

process($item, %args)

Processes a data item using the view's defined templates and/or variables. The behavior of this method depends on the type of $item and the configurations defined within the view.

The view object also acts as a proxy for the underlying template search path, so you can use it to directly include templates:

[% myview.include('footer') %]

This is equivalent to the directive:

[% INCLUDE footer %]

Any arguments passed to the view (other than configuration parameters) are stored as items within the view. These can be accessed using standard object notation:

[% VIEW my.web.site
        title = 'My Web Site'
        author = 'ABW'
%]
[% my.web.site.title %]  # Output: My Web Site
[% my.web.site.author %] # Output: ABW

This is equivalent to defining the items within the view definition block:

[% VIEW my.web.site
   [% view.title = 'My Web Site' %]
   [% view.author = 'ABW' %]
%]
[% my.web.site.title %]  # Output: My Web Site
[% my.web.site.author %] # Output: ABW

خيارات التكوين

Views accept the following configuration options:

prefix

A string that is prepended to template names requested via the include() method or object access.

suffix

A string that is appended to template names.

path

A list of directories to search for templates. This is effectively equivalent to calling addpath() for each directory in the list.

extension

A list of template file extensions to try when searching for a template. For example, ['.tt', '.tmpl', '.tpl'].

extension

A list of template file extensions to try when searching for a template. For example, ['.tt', '.tmpl', '.tpl'].

implicit

If true, then a missing template will be automatically loaded from the associated template directory using the configured extension. Defaults to false.

cache

If true (the default), template definitions are cached internally by the view object. Setting this to false can be useful for debugging, but may impact performance.

sealed

If true (the default), the view is sealed upon definition, preventing modifications to its items after the "END" directive. Setting to false allows items to be updated.

silent

If true, attempts to update items in a sealed view are silently ignored rather than raising an error. Defaults to false.

base

Specifies a base view from which to inherit configuration options and definitions. Can be a view name or a view object.

delegate

Specifies a delegate view to which processing requests may be delegated, based on object type or other criteria.

مثال: تنفيذ عرض بسيط

Here's a simple example demonstrating how to define and use a view:

# Define a view named 'product_view'
[% VIEW product_view
   prefix = 'products/'
   suffix = '.tt2'
%]
   [% BLOCK title %]
      Product: [% product.name %]
   [% END %]

   [% BLOCK body %]
      
[% product.name %]

      
Price: $% product.price %

      
[% product.description %]

   [% END %]
[% END %]

# Assume $product is a hash/object with name, price, and description attributes

# Use the view to render the product details
[% product_view.include(body, product=product) %]

# Access the title template via the view

[% product_view.include(title) %]

In this example:

  • A view named product_view is defined.
  • It's configured to prepend 'products/' and append '.tt2' to template names.
  • It defines two local blocks: title and body.
  • The body block is included, passing the $product data. This will effectively render products/body.tt2 with the product variable available.
  • The title block (which resolves to products/title.tt2) is also included to generate the page title.

This demonstrates how views can encapsulate presentation logic, making templates more reusable and manageable.

See also template(3), template_directive_include(3), template_directive_block(3).

VIEW DIRECTIVE

A VIEW directive is used to define and manage a named view. A view is essentially a named set of template blocks and associated variables. Views can be used to implement template inheritance, delegation, and other forms of template reuse.

Inheritance and Delegation

You can specify a parent view for a view using the "base" parameter. This allows the current view to inherit templates and variables from its parent. When a template or variable is not found in the current view, it will be looked up in the parent view, and so on, up the inheritance chain.

Here's an example where my.view.fancy is defined with my.view.default as its base.

[% VIEW my.view.fancy
        base   = my.view.default
        prefix = 'view/fancy/';
   END
%]

Now the directive:

[% my.view.fancy.header(title='Hello World') %]

will resolve to:

[% INCLUDE view/fancy/header title='Hello World' %]

or if that doesn't exist, it will be handled by the base view as:

[% INCLUDE view/default/header title='Hello World' %]

When a parent view is specified via the "base" parameter, the delegation of a view to its parent for fetching templates and accessing user defined variables is automatic. You can also implement your own inheritance, delegation or other reuse patterns by explicitly delegating to other views.

[% BLOCK foo %]
   public foo block
[% END %]
[% VIEW plain %]
   [% BLOCK foo %]
   <plain>[% PROCESS foo %]</plain>
   [% END %]
[% END %]
[% VIEW fancy %]
   [% BLOCK foo %]
   [% plain.foo | replace('plain', 'fancy') %]
   [% END %]
[% END %]
[% plain.foo %]     # <plain>public foo block</plain>
[% fancy.foo %]     # <fancy>public foo block</fancy>

Note that the regular "INCLUDE/PROCESS/WRAPPER" directives work entirely independently of views and will always get the original, unaltered template name rather than any local per-view definition.

Self-Reference

A reference to the view object under definition is available with the "VIEW ... END" block by its specified name and also by the special name '"view"' (similar to the "my $self = shift;" in a Perl method or the '"this"' pointer in C++, etc). The view is initially unsealed allowing any data items to be defined and updated within the "VIEW ... END" block. The view is automatically sealed at the end of the definition block, preventing any view data from being subsequently changed.

(NOTE: sealing should be optional. As well as sealing a view to prevent updates ("SEALED"), it should be possible to set an option in the view to allow external contexts to update existing variables ("UPDATE") or even create totally new view variables ("CREATE")).

[% VIEW fancy %]
   [% fancy.title  = 'My Fancy Title' %]
   [% fancy.author = 'Frank Open' %]
   [% fancy.col    = { bg => '#ffffff', bar => '#a0a0ff' } %]
[% END %]

or

[% VIEW fancy %]
   [% view.title  = 'My Fancy Title' %]
   [% view.author = 'Frank Open' %]
   [% view.col    = { bg => '#ffffff', bar => '#a0a0ff' } %]
[% END %]

It makes no real difference in this case if you refer to the view by its name, '"fancy"', or by the general name, '"view"'. Outside of the view block, however, you should always use the given name, '"fancy"':

[% fancy.title  %]
[% fancy.author %]
[% fancy.col.bg %]

The choice of given name or '"view"' is much more important when it comes to "BLOCK" definitions within a "VIEW". It is generally recommended that you use '"view"' inside a "VIEW" definition because this is guaranteed to be correctly defined at any point in the future when the block gets called. The original name of the view might have long since been changed or reused but the self-reference via '"view"' should always be intact and valid.

Take the following VIEW as an example:

[% VIEW foo %]
   [% view.title = 'Hello World' %]
   [% BLOCK header %]
   Title: [% view.title %]
   [% END %]
[% END %]

Even if we rename the view, or create a new "foo" variable, the header block still correctly accesses the "title" attribute of the view to which it belongs. Whenever a view "BLOCK" is processed, the "view" variable is always updated to contain the correct reference to the view object to which it belongs.

[% bar = foo %]
[% foo = { title => "New Foo" } %]  # no problem
[% bar.header %]                    # => Title: Hello World

Saving References to External Views

When it comes to view inheritance, it's always a good idea to take a local copy of a parent or delegate view and store it as an attribute within the view for later use. This ensures that the correct view reference is always available, even if the external name of a view has been changed.

[% VIEW plain %]
   ...
[% END %]
[% VIEW fancy %]
   [% view.plain = plain %]
   [% BLOCK foo %]
   [% view.plain.foo | replace('plain', 'fancy') %]
   [% END %]
[% END %]
[% plain.foo %]         # => <plain>public foo block</plain>
[% plain = 'blah' %]    # no problem
[% fancy.foo %]         # => <fancy>public foo block</fancy>

Views as Data Presenters

Another key role of a view is to act as a dispatcher to automatically apply the correct template to present a particular object or data item. This is handled via the print() method.

Here's an example:

[% VIEW foo %]
   [% BLOCK text %]
      Some text: [% item %]
   [% END %]
   [% BLOCK hash %]
      a hash:
      [% FOREACH key = item.keys.sort -%]
         [% key %] => [% item.$key %]
      [% END -%]
   [% END %]
   [% BLOCK list %]
      a list: [% item.sort.join(', ') %]
   [% END %]
[% END %]

We can now use the view to print text, hashes or lists. The print() method includes the right template depending on the typing of the argument (or arguments) passed.

[% some_text = 'I read the news today, oh boy.' %]
[% a_hash    = { house => 'Lords', hall => 'Albert' } %]
[% a_list    = [ 'sure', 'Nobody', 'really' ] %]
[% view.print(some_text) %]
                    # Some text: I read the news today, oh boy.
[% view.print(a_hash) %]
                    # a hash:
                         hall => Albert
                         house => Lords
[% view.print(a_list) %]
                    # a list: Nobody, really, sure

You can also provide templates to print objects of any other class. The class name is mapped to a template name with all non-word character sequences such as '"::"' converted to a single '"_"'.

[% VIEW foo %]
   [% BLOCK Foo_Bar %]
      a Foo::Bar object:
          thingies: [% view.print(item.thingies) %]
           doodahs: [% view.print(item.doodahs)  %]
   [% END %]
[% END %]
[% USE fubar = Foo::Bar(...) %]
[% foo.print(fubar) %]

Note how we use the view object to display various items within the objects ('"thingies"' and '"doodahs"'). We don't need to worry what kind of data these represent (text, list, hash, etc) because we can let the view worry about it, automatically mapping the data type to the correct template.

Views may define their own type => template map.

[% VIEW foo
     map = { TEXT  => 'plain_text',
             ARRAY => 'show_list',
             HASH  => 'show_hash',
             My::Module => 'template_name'
             default    => 'any_old_data'
           }
%]
    [% BLOCK plain_text %]
       ...
    [% END %]
    ...
[% END %]

They can also provide a "default" map entry, specified as part of the "map" hash or as a parameter by itself.

[% VIEW foo
     map     = { ... },
     default = 'whatever'
%]
   ...
[% END %]

or

[% VIEW foo %]
   [% view.map     = { ... }
      view.default = 'whatever'
   %]
   ...
[% END %]

The print() method provides one more piece of magic. If you pass it a reference to an object which provides a present() method, then the method will be called passing the view as an argument. This then gives any object a chance to determine how it should be presented via the view.

package Foo::Bar;
...
sub present {
    my ($self, $view) = @_;
    return "a Foo::Bar object:\n"
         . "thingies: " . $view->print($self->{ _THINGIES }) . "\n"
         . "doodahs: " . $view->print($self->{ _DOODAHS }) . "\n";
}

The object is free to delve deeply into its innards and mess around with its own private data, before presenting the relevant data via the view. In a more complex example, a present() method might walk part of a tree making calls back against the view to present different nodes within the tree. We may not want to expose the internal structure of the tree (because that would break encapsulation and make our presentation code dependant on it) but we want to have some way of walking the tree and presenting items found in a particular manner.

This is known as Structure Shy Traversal. Our view object doesn't require prior knowledge about the internal structure of any data set to be able to traverse it and present the data contained therein. The data items themselves, via the present() method, can implement the internal iterators to guide the view along the right path to presentation happiness.

The upshot is that you can use views to greatly simplify the display of data structures like "XML::DOM" trees. The documentation for the "Template::Plugin::XML::DOM" module contains an example of this. In essence, it looks something like this:

XML source:

<user name="Andy Wardley">
    <project id="iCan" title="iCan, but theyCan't"/>
