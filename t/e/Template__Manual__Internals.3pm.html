NAME

Template::Manual::Internals - Internals of the Template Toolkit

Introduction

This document describes the internal workings of the Template Toolkit, version 2. It is intended for those who wish to understand how the toolkit operates, or who wish to extend or modify its behaviour.

The Template Toolkit is a highly configurable and extensible template processing system. It is written in Perl and provides a powerful and flexible way to generate text-based output, such as HTML, XML, email, or configuration files.

Outside Looking In

From the perspective of a user writing templates, the Template Toolkit presents a relatively simple interface. A template is a text file containing a mixture of static text and template directives. Directives are embedded within the text and are typically delimited by `[% ... %]` or `` markers.

The main directives are:

  • [% INCLUDE ... %]: Include another template.
  • [% PROCESS ... %]: Process another template, potentially with arguments.
  • [% WRAP ... %]: Wrap a block of text with another template.
  • [% IF ... %] ... [% END %]: Conditional processing.
  • [% UNLESS ... %] ... [% END %]: Conditional processing.
  • [% ELSE %]: Alternate for IF/UNLESS.
  • [% ELSIF ... %]: Alternate for IF.
  • [% FOR ... %] ... [% END %]: Loop through a list.
  • [% WHILE ... %] ... [% END %]: Loop based on a condition.
  • [% BLOCK ... %] ... [% END %]: Define a named block.
  • [% MACRO ... %] ... [% END %]: Define a reusable macro.
  • [% FILTER ... %] ... [% END %]: Filter a block of text.
  • [% USE ... %]: Load and instantiate a plugin.
  • [% PERL ... %] ... [% END %]: Execute arbitrary Perl code (use with caution).
  • [% TAG ... %]: Define a custom directive.

Variables are accessed using dot notation (e.g., [% user.name %]) or array indexing (e.g., [% users.0.name %]).

The Template Toolkit engine (Template::Toolkit) takes a template file (or string) and a context object (containing variables and configuration) and returns the processed output.

Inside Looking Out

Internally, the Template Toolkit operates in several distinct phases:

  1. Parsing: The template is parsed into an internal representation, typically a tree of opcodes (operations). This phase is handled by the Template::Parser class.
  2. Compilation: The opcode tree is compiled into a more efficient form, ready for execution. This phase is handled by the Template::Compiler class.
  3. Execution: The compiled code is executed by the Template::Engine class, which traverses the opcode tree and performs the required operations.
  4. Output: The generated output is sent to the designated output stream or stored in a variable.

Key internal components include:

  • Template::Toolkit: The main driver class. It orchestrates the parsing, compilation, and execution phases.
  • Template::Context: Holds the configuration, variables, and other runtime information.
  • Template::Parser: Responsible for parsing template text into an abstract syntax tree (AST).
  • Template::Compiler: Converts the AST into executable bytecode or opcodes.
  • Template::Service::Stream: Manages input and output streams.
  • Template::Provider: Handles loading of templates, filters, plugins, etc.
  • Template::Stash: Manages the variable namespace.
  • Template::Plugin::*: Base class for plugins.
  • Template::Filter::*: Base class for filters.

Hacking on the Template Toolkit

To hack on the Template Toolkit, you'll need a good understanding of Perl and object-oriented programming. Here's a general approach:

  1. Understand the architecture: Familiarize yourself with the classes and their responsibilities as outlined above.
  2. Identify the area to modify: Are you adding a new directive, improving performance, fixing a bug, or implementing a new feature?
  3. Locate the relevant code: The source code is organized into modules corresponding to the internal components.
  4. Make your changes: Implement your modifications carefully.
  5. Write tests: The Template Toolkit has a comprehensive test suite. Add new tests to cover your changes and ensure existing tests still pass. You can run the tests using make test in the distribution directory.
  6. Document your changes: Update the relevant documentation files (e.g., this manual, specific module PODs) to reflect your modifications.
  7. Submit your changes: If you're contributing back to the project, follow the contribution guidelines (typically found in the CONTRIBUTING.md file or similar).

Common areas for extension include:

  • Plugins: Add new functionality through the [% USE ... %] directive. Create a new class inheriting from Template::Plugin.
  • Filters: Implement custom text transformations using the [% FILTER ... %] directive. Create a new class inheriting from Template::Filter.
  • Directives: Add new template commands by subclassing Template::Parser and Template::Compiler, or by implementing custom tags.
  • Output methods: Change how output is handled by interacting with Template::Service::Stream or custom output handlers.

Debugging can be aided by enabling verbose output and error reporting within the Template::Context object.
