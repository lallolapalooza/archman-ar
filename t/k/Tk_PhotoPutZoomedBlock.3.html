الوصف

Tk_FindPhoto يعيد مقبضًا غير شفاف يُستخدم لتحديد صورة فوتوغرافية معينة للإجراءات الأخرى. المعامل هو اسم الصورة، أي الاسم المحدد لأمر image create photo، أو المعين بواسطة هذا الأمر إذا لم يتم تحديد اسم. إذا لم يكن imageName موجودًا أو لم يكن صورة فوتوغرافية، فإن Tk_FindPhoto يعيد NULL.

Tk_PhotoPutBlock يُستخدم لتوفير كتل من بيانات الصورة للعرض. يؤثر الاستدعاء على منطقة من الصورة بحجم width x height بكسل، مع وجود زاويتها العلوية اليسرى عند الإحداثيات (x,y). يجب أن تكون جميع قيم width و height و x و y غير سالبة. إذا كان جزء من هذه المنطقة يقع خارج الحدود الحالية للصورة، فسيتم توسيع الصورة لتشمل المنطقة، ما لم يحدد المستخدم حجم صورة صريحًا باستخدام خيارات تكوين الأدوات -width و/أو -height (انظر photo(n)؛ في هذه الحالة، سيتم اقتصاص المنطقة بصمت إلى حدود الصورة.

المعامل block هو مؤشر إلى بنية Tk_PhotoImageBlock، المعرفة على النحو التالي:

typedef struct {
    unsigned char *pixelPtr;
    int width;
    int height;
    int pitch;
    int pixelSize;
    int offset[4];
} Tk_PhotoImageBlock;
يشير الحقل pixelPtr إلى البكسل الأول، أي البكسل العلوي الأيسر في الكتلة. يحدد الحقلان width و height أبعاد كتلة البكسلات. يحدد الحقل pixelSize فرق العنوان بين بكسلين أفقيين متجاورين. يجب أن يكون 4 لبيانات RGB و 2 لبيانات الصور ذات التدرج الرمادي. قد تكون هناك قيم أخرى ممكنة، إذا تم تعديل الإزاحات في مصفوفة offset وفقًا لذلك (على سبيل المثال، للبيانات الحمراء والخضراء والزرقاء المخزنة في مستويات مختلفة). ومع ذلك، فإن استخدام هذا التخطيط غير مستحسن بشدة. بسبب خطأ، قد لا يعمل بشكل صحيح إذا تم توفير قناة ألفا. (انظر قسم BUGS أدناه). يحدد الحقل pitch فرق العنوان بين بكسلين رأسيين متجاورين. تحتوي مصفوفة offset على الإزاحات من عنوان البكسل إلى عناوين البايتات التي تحتوي على المكونات الحمراء والخضراء والزرقاء والشفافية (الألفا). إذا كانت الإزاحات للأحمر والأخضر والأزرق متساوية، فسيتم تفسير الصورة على أنها ذات تدرج رمادي. إذا اختلفت، فسيتم افتراض بيانات RGB. عادةً ما تكون الإزاحات 0، 1، 2، 3 لبيانات RGB و 0، 0، 0، 1 للبيانات ذات التدرج الرمادي. من الممكن توفير بيانات صور بدون قناة ألفا عن طريق تعيين الإزاحة للألفا إلى قيمة سالبة وتعديل الحقل pixelSize وفقًا لذلك. ومع ذلك، فإن هذا الاستخدام غير مستحسن (انظر قسم BUGS أدناه).

المعامل compRule لـ Tk_PhotoPutBlock يحدد قاعدة تركيب تقول ماذا تفعل بالبكسلات الشفافة. القيمة TK_PHOTO_COMPOSITE_OVERLAY تعني أن المحتويات السابقة للصورة الفوتوغرافية يجب أن تظهر من خلالها، والقيمة TK_PHOTO_COMPOSITE_SET تعني أنه يجب تجاهل محتويات الصورة الفوتوغرافية السابقة تمامًا، ونسخ القيم من الكتلة مباشرة. كان السلوك في Tk8.3 وما قبله يعادل وجود TK_PHOTO_COMPOSITE_OVERLAY كقاعدة تركيب.

لا يلزم أن تتوافق القيمة المعطاة للمعاملين width و height لـ Tk_PhotoPutBlock مع القيم المحددة في block. إذا كانت أصغر، فإن Tk_PhotoPutBlock يستخرج كتلة فرعية من بيانات الصورة المقدمة. إذا كانت أكبر، يتم تكرار البيانات المعطاة (بطريقة متجانبة) لملء المنطقة المحددة. تعمل هذه القواعد بشكل مستقل في الاتجاهين الأفقي والرأسي.

يعيد Tk_PhotoPutBlock عادةً TCL_OK، على الرغم من أنه إذا لم يتمكن من تخصيص ذاكرة كافية للاحتفاظ بالصورة الناتجة، يتم إرجاع TCL_ERROR بدلاً من ذلك، وإذا كان المعامل interp غير NULL، فستتم إضافة رسالة خطأ إلى نتيجة المفسر.

Tk_PhotoPutZoomedBlock يعمل مثل Tk_PhotoPutBlock باستثناء أنه يمكن تقليل أو تكبير الصورة للعرض. تسمح المعاملات subsampleX و subsampleY بتقليل حجم الصورة عن طريق الفرعي. سيستخدم Tk_PhotoPutZoomedBlock فقط البكسلات من الصورة المدخلة التي تكون إحداثياتها X مضاعفات لـ subsampleX، وتكون إحداثياتها Y مضاعفات لـ subsampleY. على سبيل المثال، يمكن تقليل صورة بحجم 512x512 بكسل إلى 256x256 عن طريق تعيين subsampleX و subsampleY إلى 2.

تسمح المعاملات zoomX و zoomY بتكبير الصورة عن طريق تكرار البكسل. سيتم كتابة كل بكسل من الصورة المدخلة (التي تم فرعيها ربما) إلى كتلة بعرض zoomX بكسل وارتفاع zoomY بكسل من الصورة المعروضة. يمكن استخدام الفرعي والتكبير معًا لتأثيرات خاصة.

يمكن استخدام Tk_PhotoGetImage لاسترداد بيانات الصورة من صورة فوتوغرافية. يقوم Tk_PhotoGetImage بملء البنية التي يشير إليها المعامل blockPtr بقيم تصف عنوان وتخطيط بيانات الصورة التي خزنتها الصورة الفوتوغرافية داخليًا. تكون القيم صالحة حتى يتم تدمير الصورة أو تغيير حجمها.

من الممكن تعديل صورة عن طريق الكتابة مباشرة إلى البيانات التي يشير إليها الحقل pixelPtr. ومع ذلك، لا يمكن تغيير حجم الصورة بهذه الطريقة. أيضًا، لن تكون التغييرات التي تم إجراؤها عن طريق الكتابة مباشرة إلى pixelPtr مرئية على الفور، ولكن فقط بعد استدعاء Tk_ImageChanged أو بعد حدث يتسبب في إعادة رسم الأدوات المهتمة لنفساها. لهذه الأسباب، من الأفضل عادةً إجراء

ARGUMENTS

See the descriptions of the individual procedures below for details on their arguments.

DESCRIPTION

These procedures provide a C-level interface for manipulating Tk photo images. A photo image is a general-purpose image type that can be created and manipulated using the image create photo command in Tcl.

Tk_PhotoPutBlock writes a block of pixel data from blockPtr into the photo image referred to by photo. The data in blockPtr is described by the Tk_PhotoImageBlock structure, which contains a pointer to the pixel data, and information about the offset of the red, green, blue, and alpha channels, and the size of each pixel. See the tk.h header file for the definition of Tk_PhotoImageBlock. The interp argument is for error reporting.

Tk_PhotoPutZoomedBlock is similar to Tk_PhotoPutBlock, except that it scales the block of pixel data to fit into the destination rectangle specified by x, y, width, and height. The zoom argument is a scaling factor; if zoom is 1, the block is not scaled. If zoom is greater than 1, the block is enlarged by that factor. If zoom is less than 1, the block is reduced. The arguments are analogous to those for the zoom command in the photo widget. This allows Tk to handle zooming and panning efficiently.

After modifying the photo image data, you may need to tell Tk that the image has changed. This is done by calling Tk_PhotoGetImage. This procedure causes the image to be redrawn if it is currently displayed in any windows. It returns 1 if the image was redrawn, and 0 if it was not (e.g., if the image was not displayed).

Tk_PhotoBlank blanks the entire area of the photo image. Blank areas of a photo image are transparent.

Tk_PhotoExpand requests that the widget's image be expanded to be at least width x height pixels in size. The width and/or height are unchanged if the user has specified an explicit image width or height with the -width and/or -height configuration options, respectively. If the image data are being supplied in many small blocks, it is more efficient to use Tk_PhotoExpand or Tk_PhotoSetSize at the beginning rather than allowing the image to expand in many small increments as image blocks are supplied.

Tk_PhotoExpand normally returns TCL_OK, though if it cannot allocate sufficient memory to hold the resulting image, TCL_ERROR is returned instead and, if the interp argument is non-NULL, an error message is placed in the interpreter's result.

Tk_PhotoSetSize specifies the size of the image, as if the user had specified the given width and height values to the -width and -height configuration options. A value of zero for width or height does not change the image's width or height, but allows the width or height to be changed by subsequent calls to Tk_PhotoPutBlock, Tk_PhotoPutZoomedBlock or Tk_PhotoExpand.

Tk_PhotoSetSize normally returns TCL_OK, though if it cannot allocate sufficient memory to hold the resulting image, TCL_ERROR is returned instead and, if the interp argument is non-NULL, an error message is placed in the interpreter's result.

Tk_PhotoGetSize returns the dimensions of the image in *widthPtr and *heightPtr.

PORTABILITY

In Tk 8.3 and earlier, Tk_PhotoPutBlock and Tk_PhotoPutZoomedBlock had different signatures. If you want to compile code that uses the old interface against 8.4 without updating your code, compile it with the flag -DUSE_COMPOSITELESS_PHOTO_PUT_BLOCK. Code linked using Stubs against older versions of Tk will continue to work.

In Tk 8.4, Tk_PhotoPutBlock, Tk_PhotoPutZoomedBlock, Tk_PhotoExpand and Tk_PhotoSetSize did not take an interp argument or return any result code. If insufficient memory was available for an image, Tk would panic. This behaviour is still supported if you compile your extension with the additional flag -DUSE_PANIC_ON_PHOTO_ALLOC_FAILURE. Code linked using Stubs against older versions of Tk will continue to work.

BUGS

The Tk_PhotoImageBlock structure used to provide image data to Tk_PhotoPutBlock promises great flexibility in the layout of the data (e.g. separate planes for the red, green, blue and alpha channels). Unfortunately, the implementation fails to hold this promise. The problem is that the pixelSize field is (incorrectly) used to determine whether the image has an alpha channel. Currently, if the offset for the alpha channel is greater than or equal to pixelSize, tk_PhotoPutblock assumes no alpha data is present and makes the image fully opaque. This means that for layouts where the channels are separate (or any other exotic layout where pixelSize has to be smaller than the alpha offset), the alpha channel will not be read correctly. In order to be on the safe side if this issue will be corrected in a future release, it is strongly recommended you always provide alpha data - even if the image has no transparency - and only use the "standard" layout with a pixelSize of 2 for grayscale and 4 for RGB data with offsets of 0, 0, 0, 1 or 0, 1, 2, 3 respectively.
