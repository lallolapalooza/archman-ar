الوصف

Tk_FindPhoto يعيد معرّفًا غير شفاف يُستخدم لتحديد صورة فوتوغرافية معينة للإجراءات الأخرى. المعامل هو اسم الصورة، أي الاسم المحدد في أمر image create photo أو المعين بواسطة هذا الأمر إذا لم يتم تحديد اسم. إذا لم يكن imageName موجودًا أو لم يكن صورة فوتوغرافية، فإن Tk_FindPhoto يعيد NULL.

Tk_PhotoPutBlock يُستخدم لتوفير كتل بيانات الصورة للعرض. يؤثر الاستدعاء على منطقة حجمها width × height بكسل، مع زاويتها العلوية اليسرى عند الإحداثيات (x, y). يجب أن تكون جميع قيم width، height، x، و y غير سالبة. إذا كان جزء من هذه المنطقة خارج الحدود الحالية للصورة، فسيتم توسيع الصورة لتشملها، ما لم يكن المستخدم قد حدد حجم صورة صريحًا باستخدام خيارات التكوين للأداة -width و/أو -height (انظر photo(n)); في هذه الحالة، سيتم قص المنطقة بصمت إلى حدود الصورة.

المعامل block هو مؤشر إلى هيكل Tk_PhotoImageBlock، المعرف على النحو التالي:

typedef struct {
    unsigned char *pixelPtr;
    int width;
    int height;
    int pitch;
    int pixelSize;
    int offset[4];
} Tk_PhotoImageBlock;
يشير الحقل pixelPtr إلى البكسل الأول، أي البكسل العلوي الأيسر للكتلة. تحدد الحقوق width و height أبعاد كتلة البكسلات. يحدد الحقل pixelSize فرق العنوان بين بكسلين متتاليين أفقيًا. يجب أن يكون 4 للصور RGB و 2 لبيانات الرمادي. قد تكون هناك قيم أخرى ممكنة، طالما تم تعديل الفهارس في الحقل offset بشكل مناسب (على سبيل المثال، لمكونات الأحمر والأخضر والأزرق المخزنة في مستويات مختلفة). يُمنع بشدة استخدام هذا التخطيط. بسبب خطأ، قد لا يعمل بشكل صحيح إذا تم توفير قناة شفافة. (انظر قسم BUGS أدناه). يحدد الحقل pitch فرق العنوان بين بكسلين متتاليين عموديًا. يحتوي الحقل offset على فهارس اتجاهات البايتات التي تحتوي على مكونات الأحمر والأخضر والأزرق والشفافية (شفاف) للبكسل. إذا كانت فهارس الأحمر والأخضر والأزرق متساوية، فسيتم تفسير الصورة على أنها رمادية. إذا اختلفت، فسيتم افتراض بيانات RGB. عادةً، ستكون الفهارس 0، 1، 2، 3 لبيانات RGB و 0، 0، 0، 1 لبيانات الرمادي. من الممكن توفير بيانات صورة بدون قناة شفافية عن طريق تعيين الحقل offset لقناة الشفافية إلى قيمة سالبة وتعديل الحقل pixelSize بشكل مناسب. يُمنع بشدة استخدام هذا (انظر قسم BUGS أدناه).

المعامل compRule لـ Tk_PhotoPutBlock يحدد قاعدة تركيب تشير إلى ما يجب فعله مع البكسلات الشفافة. القيمة TK_PHOTO_COMPOSITE_OVERLAY تعني أنه يجب عرض المحتويات السابقة للصورة الفوتوغرافية من خلال البتات الشفافة، والقيمة TK_PHOTO_COMPOSITE_SET تعني أنه يجب تجاهل المحتويات السابقة للصورة الفوتوغرافية تمامًا ونسخ قيم الكتلة مباشرة. كان السلوك في Tk8.3 والإصدارات السابقة مكافئًا لوجود TK_PHOTO_COMPOSITE_OVERLAY كقاعدة تركيب.

لا يلزم أن تتطابق القيم المعطاة للمعاملين width و height في Tk_PhotoPutBlock مع القيم المحددة في block. إذا كانت أصغر، فسيقوم Tk_PhotoPutBlock باستخراج كتلة فرعية من بيانات الصورة المقدمة. إذا كانت أكبر، فسيتم تكرار البيانات المعطاة (في وضع التكرار) لملء المنطقة المحددة. تعمل هذه القواعد بشكل مستقل في الاتجاهين الأفقي والعمودي.

Tk_PhotoPutBlock يعيد عادةً TCL_OK، على الرغم من أنه إذا لم يكن بالإمكان تخصيص ذاكرة كافية لتخزين الصورة الناتجة، فإنه يعيد TCL_ERROR، وإذا كان المعامل interp ليس NULL، فسيتم وضع رسالة خطأ في نتيجة المفسر.

Tk_PhotoPutZoomedBlock يعمل مثل Tk_PhotoPutBlock باستثناء أنه يمكن تصغير أو تكبير الصورة للعرض. تتيح المعاملات subsampleX و subsampleY تصغير الصورة عن طريق أخذ عينات فرعية. سيستخدم Tk_PhotoPutZoomedBlock فقط وحدات البكسل من الصورة المدخلة التي تكون إحداثيات X فيها مضاعفات لـ subsampleX وإحداثيات Y فيها مضاعفات لـ subsampleY. على سبيل المثال، يمكن تصغير صورة 512 × 512 بكسل إلى 256 × 256 عن طريق تعيين subsampleX و subsampleY إلى 2.

تسمح المعاملات zoomX و zoomY بتكبير الصورة عن طريق تكرار وحدات البكسل. سيتم كتابة كل بكسل من الصورة المدخلة (التي تم أخذ عينات فرعية منها ربما) في كتلة بعرض zoomX بكسل وارتفاع zoomY بكسل في الصورة المعروضة. يمكن استخدام أخذ العينات الفرعية والتكبير معًا لتأثيرات خاصة.

يمكن استخدام Tk_PhotoGetImage لاستعادة بيانات الصورة من صورة فوتوغرافية. يملأ Tk_PhotoGetImage القيم التي تصف العنوان والتخطيط لبيانات الصورة التي خزنتها الصورة الفوتوغرافية داخليًا. تكون القيم صالحة حتى يتم تدمير الصورة أو تغيير حجمها.

من الممكن تعديل صورة بالكتابة مباشرة إلى البيانات التي يشير إليها الحقل pixelPtr. ومع ذلك، لا يمكن تغيير حجم الصورة بهذه الطريقة. أيضًا، التغييرات التي تم إجراؤها بالكتابة مباشرة إلى pixelPtr ليست مرئية على الفور، ولكن فقط بعد استدعاء Tk_ImageChanged أو بعد حدث يتسبب في إعادة رسم الأدوات المهتمة. لهذا السبب، يكون عادةً من الأفضل إجراء التغييرات بمساعدة Tk_ImageChanged أو الأحداث.

DESCRIPTION

These procedures provide the interface for manipulating the pixel data of Tk photo images. Photo images are used to store and display arbitrary raster image data, typically loaded from image files or generated dynamically. The data is stored in a Tk_PhotoImage structure, which is managed internally by Tk. The procedures described here are used by the implementation of the photo command, but they can also be used by extensions to create and manipulate photo images.

Tk_PhotoPutBlock writes a block of pixel data into the photo image. The data in blockPtr is copied into the photo image, overwriting any existing pixels in the specified region. The layout of the pixel data in blockPtr is described by the fields of the Tk_PhotoImageBlock structure:

    typedef struct {
        unsigned char *pixelPtr;
        int width;
        int height;
        int pitch;
        int *red;
        int *green;
        int *blue;
        int *alpha;
    } Tk_PhotoImageBlock;

pixelPtr points to the first pixel of the data. width and height specify the dimensions of the block. pitch is the number of bytes between the start of one scanline and the next. The red, green, blue, and alpha fields point to arrays of integers that map channel values to red, green, blue, or alpha components, respectively. If a component is not present, its corresponding pointer can be NULL. If red, green, or blue is NULL, the channel values are assumed to be in the standard order (RGB). If alpha is NULL, the image is assumed to be opaque.

Tk_PhotoPutZoomedBlock is similar to Tk_PhotoPutBlock, but it also supports zooming. The data in blockPtr is copied into the photo image within the rectangle specified by x, y, width, and height. The source pixel data is scaled (zoomed) from the dimensions zoomWidth and zoomHeight to the dimensions width and height. This allows for efficient scaling of image data when it is being loaded.

Tk_PhotoGetImage retrieves the image data in the Tk_PhotoImageBlock structure. This is generally not useful unless you plan to make extensive changes to a copy of the image data and write it back with Tk_PhotoPutBlock or Tk_PhotoPutZoomedBlock.

Tk_PhotoGetImage returns 1 for compatibility with the corresponding procedure in the old photo widget.

Tk_PhotoBlank blanks the entire area of the photo image. Blank areas of a photo image are transparent.

Tk_PhotoExpand requests that the widget's image be expanded to be at least width x height pixels in size. The width and/or height are unchanged if the user has specified an explicit image width or height with the -width and/or -height configuration options, respectively. If the image data are being supplied in many small blocks, it is more efficient to use Tk_PhotoExpand or Tk_PhotoSetSize at the beginning rather than allowing the image to expand in many small increments as image blocks are supplied.

Tk_PhotoExpand normally returns TCL_OK, though if it cannot allocate sufficient memory to hold the resulting image, TCL_ERROR is returned instead and, if the interp argument is non-NULL, an error message is placed in the interpreter's result.

Tk_PhotoSetSize specifies the size of the image, as if the user had specified the given width and height values to the -width and -height configuration options. A value of zero for width or height does not change the image's width or height, but allows the width or height to be changed by subsequent calls to Tk_PhotoPutBlock, Tk_PhotoPutZoomedBlock or Tk_PhotoExpand.

Tk_PhotoSetSize normally returns TCL_OK, though if it cannot allocate sufficient memory to hold the resulting image, TCL_ERROR is returned instead and, if the interp argument is non-NULL, an error message is placed in the interpreter's result.

Tk_PhotoGetSize returns the dimensions of the image in *widthPtr and *heightPtr.

PORTABILITY

In Tk 8.3 and earlier, Tk_PhotoPutBlock and Tk_PhotoPutZoomedBlock had different signatures. If you want to compile code that uses the old interface against 8.4 without updating your code, compile it with the flag -DUSE_COMPOSITELESS_PHOTO_PUT_BLOCK. Code linked using Stubs against older versions of Tk will continue to work.

In Tk 8.4, Tk_PhotoPutBlock, Tk_PhotoPutZoomedBlock, Tk_PhotoExpand and Tk_PhotoSetSize did not take an interp argument or return any result code. If insufficient memory was available for an image, Tk would panic. This behaviour is still supported if you compile your extension with the additional flag -DUSE_PANIC_ON_PHOTO_ALLOC_FAILURE. Code linked using Stubs against older versions of Tk will continue to work.

BUGS

The Tk_PhotoImageBlock structure used to provide image data to Tk_PhotoPutBlock promises great flexibility in the layout of the data (e.g. separate planes for the red, green, blue and alpha channels). Unfortunately, the implementation fails to hold this promise. The problem is that the pixelSize field is (incorrectly) used to determine whether the image has an alpha channel. Currently, if the offset for the alpha channel is greater than or equal to pixelSize, tk_PhotoPutblock assumes no alpha data is present and makes the image fully opaque. This means that for layouts where the channels are separate (or any other exotic layout where pixelSize has to be smaller than the alpha offset), the alpha channel will not be read correctly. In order to be on the safe side if this issue will be corrected in a future release, it is strongly recommended you always provide alpha data - even if the image has no transparency - and only use the "standard" layout with a pixelSize of 2 for grayscale and 4 for RGB data with offsets of 0, 0, 0, 1 or 0, 1, 2, 3 respectively.
