Tk__ConfigSpecs(3pm)

ConfigSpecs(3) وثائق Perl مساهم بها من قبل المستخدم ConfigSpecs(3)

اسم

Tk::ConfigSpecs - تحديد سلوك 'configure' للأدوات المركبة.

الموجز

sub Populate
{
 my ($composite,$args) = @_;
 ...
 $composite->ConfigSpecs('-attribute' => [ where,dbName,dbClass,default ]);
 $composite->ConfigSpecs('-alias' => '-otherattribute');
 $composite->ConfigSpecs('DEFAULT' => [ where ]);
 $composite->ConfigSpecs($subwidget->ConfigSpecs);
 ...
}
$composite->configure(-attribute => value);

الوصف

الهدف هو جعل طريقة تهيئة الأداة المركبة تبدو مشابهة قدر الإمكان لطريقة تهيئة الأداة العادية. (انظر Tk::options لوصف هذا السلوك.) لتمكين ذلك، يجب تعريف السمات التي تقبلها الأداة المركبة ككل.

تحديد ConfigSpecs للفئة.

عادةً ما تحتوي الأداة على استدعاء واحد أو أكثر مثل الاستدعاء التالي:

$composite->ConfigSpecs(-attribute => [where,dbName,dbClass,default]);

في طريقة Populate الخاصة بها. عندما يتم استدعاء ConfigSpecs بهذه الطريقة (مع وسيطات) يتم استخدام الوسيطات لإنشاء أو زيادة/استبدال جدول هاش للأداة. (يمكن تحديد أكثر من زوج -option=>value لاستدعاء واحد.)

dbName و dbClass و default تُستخدم فقط بواسطة ConfigDefault الموضحة أدناه، أو للاستجابة لأوامر التهيئة 'الاستقصائية'.

يمكن أن تكون أيًا من القيم أدناه، أو قائمة من هذه القيم محاطة بـ [].

القيم المسموح بها حاليًا لـ where هي:

'ADVERTISED'
تطبيق configure على الأدوات الفرعية المعلنة.
'DESCENDANTS'
تطبيق configure بشكل متكرر على جميع الأحفاد.
'CALLBACK'
يؤدي تعيين السمة إلى "Tk::Callback->new($value)" قبل التخزين في "$composite->{Configure}{-attribute}". هذا مناسب للسمات "-command => ..." التي تتعامل معها الأداة المركبة ولا يتم إعادة توجيهها إلى أداة فرعية. (على سبيل المثال، لدى Tk::Tiler "-yscrollcommand" للسماح بربط شريط تمرير.)

قد تكون هذه الأولى من بين عدة كلمات مفتاحية 'للتحقق' (مثل font، cursor، anchor إلخ) التي تتعامل معها Tk الأساسية بشكل خاص مع كود C.

'CHILDREN'
تطبيق configure على جميع الأطفال. (الأطفال هم الأحفاد المباشرون للأداة.)
'METHOD'
استدعاء "$cw->attribute(value)"

هذه هي الحالة الأكثر عمومية. فقط ضع طريقة للفئة المركبة بنفس اسم السمة. يمكن للطريقة إجراء أي تحقق ولها أي آثار جانبية ترغب فيها. (ربما يستحق الأمر 'وضعها في قائمة انتظار' باستخدام afterIdle للآثار الجانبية الأكثر تعقيدًا.)

'PASSIVE'
فقط قم بتخزين القيمة في "$composite->{Configure}{-attribute}".

هذا الشكل هو أيضًا مكان مناسب للسمات التي تتعامل معها حاليًا في وقت الإنشاء فقط.

'SELF'
تطبيق configure على الأداة الأساسية (مثل Frame) التي تشكل أساس الأداة المركبة. (هذا هو السلوك الافتراضي لمعظم السمات الذي يجعل Frame البسيط يعمل كما تتوقع.) لاحظ أنه بمجرد تحديد ConfigSpecs لسمة ما، يجب عليك تضمين 'SELF' صراحةً في القائمة إذا كنت تريد أن تنطبق السمة على الأداة المركبة نفسها (هذا يتجنب مشاكل التكرار اللانهائي المزعجة).
$reference (مبروك)
استدعاء $reference->configure(-attribute => value)

الحالة الشائعة هي عندما يكون $reference أداة فرعية.

$reference يمكن أن يكون أيضًا نتيجة لـ

Tk::Config->new(setmethod,getmethod,args,...);

تُستخدم الفئة Tk::Config لتنفيذ جميع أنواع المفاتيح المذكورة أعلاه. الفئة لديها طرق "configure" و "cget" لذا تسمح للكود عالي المستوى بالاتصال بـ فقط إحدى هذه الطرق على كائن من نوع ما.

مرجع هاش
التحديد: 
$cw->ConfigSpecs(
        ...
        -option => [ { -optionX=>$w1, -optionY=>[$w2, $w3] },
                        dbname dbclass default ],
        ...
        );

لذلك "$cw->configure(-option => value)" تفعل فعليًا

$w1->configure(-optionX => value);
$w2->configure(-optionY => value);
$w3->configure(-optionY => value);
'otherstring'
استدعاء 
$composite->Subwidget('otherstring')->configure( -attribute => value );

بينما هذا موجود للتوافق مع الإصدارات السابقة مع Tk-b5، فمن الأفضل ربما استخدام مرجع الأداة الفرعية مباشرة. الحالة الوحيدة للاحتفاظ بهذا الشكل هي السماح بطبقة إضافية من التجريد - ربما وجود أداة فرعية 'حالية' - هذا لم يتم إثباته بعد.

الأسماء المستعارة
"ConfigSpecs( -alias => '-otherattribute' )" تُستخدم لجعل "-alias" مكافئًا لـ "-otherattribute". على سبيل المثال، الأسماء المستعارة 
-fg => '-foreground',
-bg => '-background'

يتم توفيرها تلقائيًا (إذا لم يتم تحديدها بالفعل).

تفويض جميع خيارات فئة الأداة إلى أداة فرعية

$composite->ConfigSpecs($subwidget->ConfigSpecs);

ينشئ هذا قائمة من وسيطات ConfigSpecs المركبة، واحدة لكل خيار صالح في فئة $subwidget، ويفوض الخيار المذكور إلى $subwidget. انظر Tk::Widget وطريقة ConfigSpecs الخاصة بالأداة. تكرار مفاتيح composite ConfigSpecs و widget ConfigSpecs سيؤدي إلى نتائج غير محددة.

القيم الافتراضية

عندما تعود طريقة Populate، يتم استدعاء ConfigDefault.

$composite->ConfigSpecs;

(بدون وسيطات) لإرجاع مرجع إلى هاش. تأخذ الإدخالات في الهاش الشكل:

'-attribute' => [ where, dbName, dbClass, default ]

يتجاهل ConfigDefault 'where' تمامًا (وكذلك إدخال DEFAULT) ويتحقق من قاعدة بيانات 'options' نيابة عن الأداة، وإذا كان هناك إدخال مطابق لـ dbName/dbClass

-attribute => value

يتم إضافته إلى قائمة الخيارات التي ستطبقها new في النهاية على الأداة. وبالمثل، إذا لم يكن هناك تطابق وتم تعريف default، فسيتم إضافة هذه القيمة الافتراضية.

تُستخدم إدخالات الأسماء المستعارة في الهاش لتحويل القيم المحددة من قبل المستخدم للأسماء المستعارة إلى قيم للسمة الحقيقية.

التهيئة وقت New()

بمجرد عودة التحكم إلى new، يتم تطبيق قائمة الخيارات المقدمة من المستخدم، مع زيادة تلك من ConfigDefault، على الأداة باستخدام طريقة configure أدناه.

تكون الأدوات أكثر مرونة وتشبه Tk بشكل أكبر إذا كانت تتعامل مع غالبية سماتها بهذه الطريقة.

تهيئة الأدوات المركبة

بمجرد حدوث ما سبق، يجب أن تتصرف الاستدعاءات بالشكل:

$composite->configure( -attribute => value );

مثل أي أداة أخرى من منظور كود المستخدم النهائي. سيتم التعامل مع configure بواسطة Tk::Derived::configure على النحو التالي:

$composite->ConfigSpecs;

يتم استدعاؤها (بدون وسيطات) لإرجاع مرجع إلى هاش، يتم البحث عن -attribute في هذا الهاش، إذا لم يكن -attribute موجودًا في الهاش، فسيتم البحث عن 'DEFAULT' بدلاً من ذلك. (يتم أيضًا تجربة الأسماء المستعارة وتسبب إعادة توجيه إلى السمة المستعارة). يجب أن تكون النتيجة مرجعًا إلى قائمة مثل:

[ where, dbName, dbClass, defa

NAME

Tk::ConfigSpecs - A mechanism for configuring composite widgets

SYNOPSIS

package Tk::Composite;

@ISA = qw(Tk::Widget);

sub Populate {
    my ($self, $args) = @_;

    my @ConfigSpecs = (
        [ -attribute => 'value', 'Tk::Style', 'attribute' ],
        [ -other     => 'foo',   'Tk::Widget', 'foo', 'bar' ],
        [ -foobar    => 'bar',   'Tk::Widget', 'foobar', 'baz' ],
        [ -composite => 'comp',  'Tk::Composite', 'composite', 'subwidget' ],
    );

    $self->ConfigSpecs(\@ConfigSpecs);

    # ... create subwidgets ...
    $self->Frame($args); # Or whatever base widget you're using
    my $self->{some_widget} = $self->SomeWidget( ... );
    my $self->{another_widget} = $self->AnotherWidget( ... );
}

sub DESTROY {
    # ...
    $self->SUPER::DESTROY(@_);
}

DESCRIPTION

This module provides a general mechanism for configuring composite widgets. A composite widget is a widget that is composed of other widgets. For example, a labelled entry widget might be composed of a label and an entry widget.

The basic idea is to provide a list of configuration specifications (often called ConfigSpecs) which map options specified for the composite widget to options or methods of its subwidgets.

The configuration specifications are stored in the composite widget's hash table in the key ConfigSpecs. They are passed to the Populate method via the ConfigSpecs class method.

Each configuration specification is a reference to an array of four elements:

-option
The name of the option for the composite widget. This should start with a dash, like -background.
-attribute
The name of the attribute in the composite widget's hash table where the value for this option will be stored. Usually, this is the same as the option name, but without the leading dash.
-class
The name of the Tk class of the subwidget that this option applies to. This can be a built-in Tk class like Tk::Widget or Tk::Frame, or a custom class you have defined.
-subwidget
The name of the subwidget. This is the key in the composite widget's hash table that refers to the subwidget instance. For example, if you created a subwidget like this:
$self->{entry} = $self->Entry(-textvariable => \$self->{foo});

then the -subwidget would be 'entry'.

The configuration mechanism works as follows:

  • When the composite widget is created, or when its configure method is called, Tk iterates through the ConfigSpecs.
  • For each specification, it checks if the composite widget has been passed an option with the corresponding name.
  • If an option is found, its value is stored in the composite widget's hash table under the specified -attribute key.
  • The mechanism then attempts to configure the named subwidget using the value. The exact way this is done depends on the type of the subwidget and the option.

Configuring Subwidgets

For most standard Tk widgets, the ConfigSpecs mechanism works by calling the subwidget's configure method. For example, if you have a specification like:

    [ -textColour => 'textColour', 'Tk::Label', 'textColour', 'label' ]

and you call the composite widget like this:

$composite->configure(-textColour => 'red');

then the mechanism will effectively execute:

$self->{label}->configure(-textColour => 'red');

The -attribute part of the specification is used to store the value within the composite widget itself, which can be useful for retrieving the value later using cget.

In the case where the -class is specified as 'Tk::Derived', the configuration is handled by Tk::Derived::configure. This method uses the -subwidget part of the specification to determine which subwidget's configure method to call.

At this stage only where is of interest, it maps to a list of object references (maybe only one) foreach one

$object->configure( -attribute => value );

is evaled.

Inquiring attributes of composites

$composite->cget( '-attribute' );

This is handled by Tk::Derived::cget in a similar manner to configure. At present if where is a list of more than one object it is ignored completely and the "cached" value in

$composite->{Configure}{-attribute}.

is returned.

CAVEATS

The "-background" and "-foreground" option values are automatically propagated down to all composite widget's children. This may be sometimes not desirable, especially if some subwidgets should use own color schemes, either by using explicit options or by option database definitions. If this is the case, then just add

-foreground => 'SELF',
-background => 'SELF',

to "ConfigSpecs".

It is the author's intention to port as many of the "Tix" composite widgets as make sense. The mechanism described above may have to evolve in order to make this possible, although now aliases are handled I think the above is sufficient.
