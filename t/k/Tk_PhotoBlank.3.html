الاسم

Tk_FindPhoto، Tk_PhotoPutBlock، Tk_PhotoPutZoomedBlock، Tk_PhotoGetImage، Tk_PhotoBlank، Tk_PhotoExpand، Tk_PhotoGetSize، Tk_PhotoSetSize - معالجة بيانات الصورة المخزنة في صورة فوتوغرافية.

الوصف

Tk_FindPhoto تُرجع مقبضًا غير شفاف يُستخدم لتحديد صورة فوتوغرافية معينة للإجراءات الأخرى. الوسيط هو اسم الصورة، أي الاسم المحدد لأمر image create photo، أو المعين بواسطة هذا الأمر إذا لم يتم تحديد اسم. إذا كان imageName غير موجود أو ليس صورة فوتوغرافية، فإن Tk_FindPhoto تُرجع NULL.

Tk_PhotoPutBlock تُستخدم لتوفير كتل من بيانات الصورة للعرض. يؤثر الاستدعاء على منطقة من الصورة بحجم width x height بكسل، مع وجود زاويتها العلوية اليسرى عند الإحداثيات (x,y). يجب أن تكون جميع قيم width و height و x و y غير سالبة. إذا كان جزء من هذه المنطقة يقع خارج الحدود الحالية للصورة، فسيتم توسيع الصورة لتشمل المنطقة، ما لم يحدد المستخدم حجم صورة صريحًا باستخدام خيارات تكوين الأداة -width و/أو -height (انظر photo(n)؛ في هذه الحالة، سيتم اقتطاع المنطقة بصمت إلى حدود الصورة.

المعلمة block هي مؤشر إلى بنية Tk_PhotoImageBlock، المعرفة على النحو التالي:

typedef struct {
    unsigned char *pixelPtr;
    int width;
    int height;
    int pitch;
    int pixelSize;
    int offset[4];
} Tk_PhotoImageBlock;
يشير الحقل pixelPtr إلى أول بكسل، أي البكسل العلوي الأيسر في الكتلة. تحدد حقلا width و height أبعاد كتلة البكسلات. يحدد الحقل pixelSize الفرق في العنوان بين بكسلين متجاورين أفقيًا. يجب أن يكون 4 لبيانات RGB و 2 لبيانات التدرج الرمادي. قد تكون القيم الأخرى ممكنة، إذا تم تعديل الإزاحات في مصفوفة offset وفقًا لذلك (على سبيل المثال، لبيانات الأحمر والأخضر والأزرق المخزنة في مستويات مختلفة). ومع ذلك، يُثبط بشدة استخدام هذا التخطيط. بسبب خطأ، قد لا يعمل بشكل صحيح إذا تم توفير قناة ألفا. (انظر قسم BUGS أدناه). يحدد الحقل pitch الفرق في العنوان بين بكسلين متجاورين رأسيًا. تحتوي مصفوفة offset على الإزاحات من عنوان بكسل إلى عناوين البايتات التي تحتوي على مكونات الأحمر والأخضر والأزرق والشفافية (ألفا). إذا كانت الإزاحات للأحمر والأخضر والأزرق متساوية، يتم تفسير الصورة على أنها تدرج رمادي. إذا اختلفت، يُفترض أن البيانات هي RGB. عادةً ما تكون الإزاحات 0، 1، 2، 3 لبيانات RGB و 0، 0، 0، 1 لبيانات التدرج الرمادي. من الممكن توفير بيانات الصورة بدون قناة ألفا عن طريق تعيين إزاحة ألفا إلى قيمة سالبة وتعديل الحقل pixelSize وفقًا لذلك. ومع ذلك، يُثبط هذا الاستخدام (انظر قسم BUGS أدناه).

المعلمة compRule إلى Tk_PhotoPutBlock تحدد قاعدة تركيب تقول ما يجب فعله مع البكسلات الشفافة. القيمة TK_PHOTO_COMPOSITE_OVERLAY تقول إنه يجب أن تظهر المحتويات السابقة للصورة الفوتوغرافية، والقيمة TK_PHOTO_COMPOSITE_SET تقول إنه يجب تجاهل محتويات الصورة الفوتوغرافية السابقة تمامًا، ونسخ القيم من الكتلة مباشرة. كان السلوك في Tk8.3 والإصدارات الأقدم مكافئًا لوجود TK_PHOTO_COMPOSITE_OVERLAY كقاعدة تركيب.

لا يلزم أن تتوافق القيمة المعطاة للمعلمات width و height إلى Tk_PhotoPutBlock مع القيم المحددة في block. إذا كانت أصغر، تستخرج Tk_PhotoPutBlock كتلة فرعية من بيانات الصورة المقدمة. إذا كانت أكبر، يتم تكرار البيانات المعطاة (بطريقة متجانبة) لملء المنطقة المحددة. تعمل هذه القواعد بشكل مستقل في الاتجاهين الأفقي والرأسي.

عادةً ما تُرجع Tk_PhotoPutBlock القيمة TCL_OK، على الرغم من أنه إذا لم تتمكن من تخصيص ذاكرة كافية لاستيعاب الصورة الناتجة، يتم إرجاع TCL_ERROR بدلاً من ذلك، وإذا كانت الوسيط interp غير NULL، يتم وضع رسالة خطأ في نتيجة المترجم.

Tk_PhotoPutZoomedBlock تعمل مثل Tk_PhotoPutBlock باستثناء أنه يمكن تقليل الصورة أو تكبيرها للعرض. تسمح معلمات subsampleX و subsampleY بتقليل حجم الصورة عن طريق التقليل الفرعي. ستستخدم Tk_PhotoPutZoomedBlock فقط بكسلات من الصورة المدخلة التي تكون إحداثياتها السينية (X) مضاعفات لـ subsampleX، والتي تكون إحداثياتها الصادية (Y) مضاعفات لـ subsampleY. على سبيل المثال، يمكن تقليل صورة بحجم 512x512 بكسل إلى 256x256 عن طريق تعيين subsampleX و subsampleY إلى 2.

تسمح معلمات zoomX و zoomY بتكبير الصورة عن طريق تكرار البكسلات. سيتم كتابة كل بكسل من الصورة المدخلة (التي تم تقليلها فرعيًا ربما) إلى كتلة بعرض zoomX بكسل وارتفاع zoomY بكسل من الصورة المعروضة. يمكن استخدام التقليل الفرعي والتكبير معًا لتأثيرات خاصة.

يمكن استخدام Tk_PhotoGetImage لاسترداد بيانات الصورة من صورة فوتوغرافية. تقوم Tk_PhotoGetImage بملء البنية المشار إليها بواسطة المعلمة blockPtr بقيم تصف عنوان وتخطيط بيانات الصورة التي تخزنها الصورة الفوتوغرافية داخليًا. القيم صالحة حتى يتم تدمير الصورة أو تغيير حجمها.

من الممكن تعديل صورة عن طريق الكتابة مباشرة إلى البيانات التي يشير إليها الحقل pixelPtr. ومع ذلك، لا يمكن تغيير حجم الصورة بهذه الطريقة. أيضًا، التغييرات التي تم إجراؤها عن طريق الكتابة مباشرة إلى pixelPtr لن تكون مرئية على الفور، ولكن فقط بعد استدعاء Tk_ImageChanged أو بعد حدث يتسبب في إعادة رسم الأدوات المهتمة نفسها. لهذه الأسباب، من الأفضل عادةً إجراء تعديلات

NAME

Tk_PhotoBlank, Tk_PhotoExpand, Tk_PhotoGetImage, Tk_PhotoGetSize, Tk_PhotoPutBlock, Tk_PhotoPutZoomedBlock, Tk_PhotoSetSize — manipulate Tk photo image objects

SYNOPSIS

#include <tk.h>

void
Tk_PhotoExpand(photoPtr, width, height)
int

Tk_PhotoGetSize(photoPtr, widthPtr, heightPtr)

void

ARGUMENTS

The following arguments are used by the procedures above:

photoPtr (Input)
A pointer to a Tk_PhotoHandle structure for the photo image object. This is obtained from a call to Tk_FindPhoto.
blockPtr (Input)
A pointer to a Tk_PhotoImageBlock structure containing the image data to be written to the photo image. See the BUGS section below for details on the limitations of this structure.
width (Input)
Desired width in pixels.
height (Input)
Desired height in pixels.
offsetx (Input)
The X coordinate within the photo image where the data in the block should be placed. The coordinate system starts at 0,0 in the top-left corner.
offsety (Input)
The Y coordinate within the photo image where the data in the block should be placed. The coordinate system starts at 0,0 in the top-left corner.
zoomCyclesX (Input)
The number of times the block should be horizontally tiled. For example, a value of 2 means that the block should be stretched horizontally to twice its original width.
zoomCyclesY (Input)
The number of times the block should be vertically tiled. For example, a value of 2 means that the block should be stretched vertically to twice its original height.
interp (Input)
The Tcl interpreter in which to look up the image name. This is needed in case the image name does not yet exist.
imageName (Input)
The name of the photo image to retrieve. This must be a name that has been previously registered with Tk_CreatePhotoImage.
widthPtr (Output)
Pointer to location where the width of the photo image will be stored.
heightPtr (Output)
Pointer to location where the height of the photo image will be stored.

DESCRIPTION

These procedures provide an interface for manipulating Tk photo image objects from C code. Photo images are created by calling Tk_CreatePhotoImage, which returns a Tk_PhotoHandle. This handle can then be used in subsequent calls to the procedures described below.

The core of the photo image interface is the ability to write blocks of pixel data into the image. This is done using Tk_PhotoPutBlock and Tk_PhotoPutZoomedBlock. The Tk_PhotoImageBlock structure passed to these functions contains pointers to the image data, along with information about its layout (width, height, pixel size, and offsets of the red, green, blue, and alpha channels).

The Tk_PhotoPutBlock procedure writes the pixel data from the blockPtr structure into the photo image object identified by photoPtr, starting at coordinates (offsetx, offsety).

The Tk_PhotoPutZoomedBlock procedure is similar to Tk_PhotoPutBlock, but it also allows the block of data to be tiled and scaled. The zoomCyclesX and zoomCyclesY arguments specify how many times the block should be tiled horizontally and vertically, respectively. For example, if zoomCyclesX is 2, the block will be stretched horizontally to twice its original width. A value of 1 means no tiling or scaling.

After modifying the image data, you may need to update the widget displaying the image. This is typically done by calling Tk_PhotoExpand or Tk_PhotoSetSize to adjust the image's dimensions and then by invalidating the widget's display area.

The Tk_PhotoExpand procedure requests that the image be expanded to at least the given width and height. If the image is smaller than the requested dimensions, it will be enlarged. If it is already larger, it will remain unchanged. This is useful when you are adding data to an image and want to ensure it is large enough to accommodate the new data.

The Tk_PhotoSetSize procedure explicitly sets the width and height of the photo image. This is equivalent to setting the -width and -height options of the image widget. If a width or height of 0 is given, that dimension is not changed, but it allows it to be changed by subsequent calls to Tk_PhotoPutBlock, Tk_PhotoPutZoomedBlock or Tk_PhotoExpand.

The Tk_PhotoGetImage procedure is used to retrieve a photo image handle given its name. This is useful when you need to perform operations on an existing photo image.

The Tk_PhotoBlank procedure clears the entire photo image, making it completely transparent. This is useful for resetting the image or preparing it for new data.

The procedures Tk_PhotoExpand and Tk_PhotoSetSize return TCL_OK on success, or TCL_ERROR if memory allocation fails. In the latter case, if the interp argument is not NULL, an error message is placed in the interpreter's result.

The Tk_PhotoGetSize procedure returns the current dimensions of the photo image in the variables pointed to by widthPtr and heightPtr.

The Tk_PhotoGetImage function returns 1 for compatibility with the corresponding procedure in the old photo widget.

PORTABILITY

In Tk 8.3 and earlier, Tk_PhotoPutBlock and Tk_PhotoPutZoomedBlock had different signatures. If you want to compile code that uses the old interface against 8.4 without updating your code, compile it with the flag -DUSE_COMPOSITELESS_PHOTO_PUT_BLOCK. Code linked using Stubs against older versions of Tk will continue to work.

In Tk 8.4, Tk_PhotoPutBlock, Tk_PhotoPutZoomedBlock, Tk_PhotoExpand and Tk_PhotoSetSize did not take an interp argument or return any result code. If insufficient memory was available for an image, Tk would panic. This behaviour is still supported if you compile your extension with the additional flag -DUSE_PANIC_ON_PHOTO_ALLOC_FAILURE. Code linked using Stubs against older versions of Tk will continue to work.

BUGS

The Tk_PhotoImageBlock structure used to provide image data to Tk_PhotoPutBlock promises great flexibility in the layout of the data (e.g. separate planes for the red, green, blue and alpha channels). Unfortunately, the implementation fails to hold this promise. The problem is that the pixelSize field is (incorrectly) used to determine whether the image has an alpha channel. Currently, if the offset for the alpha channel is greater than or equal to pixelSize, tk_PhotoPutblock assumes no alpha data is present and makes the image fully opaque. This means that for layouts where the channels are separate (or any other exotic layout where pixelSize has to be smaller than the alpha offset), the alpha channel will not be read correctly. In order to be on the safe side if this issue will be corrected in a future release, it is strongly recommended you always provide alpha data - even if the image has no transparency - and only use the "standard" layout with a pixelSize of 2 for grayscale and 4 for RGB data with offsets of 0, 0, 0, 1 or 0, 1, 2, 3 respectively.
