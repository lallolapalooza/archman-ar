Type__Tiny__Manual__Params(3pm)

الحزمة: perl-type-tiny

التراخيص: PerlArtistic, GPL

Type::Tiny::Manual::Params(3) وثائق مساهمة المستخدم في Perl Type::Tiny::Manual::Params(3)

الاسم

Type::Tiny::Manual::Params - معلومات متقدمة حول Type::Params

الدليل

للبدء باستخدام Type::Params، يرجى قراءة Type::Tiny::Manual::UsingWithMoo الذي سيغطي الكثير من الأساسيات، حتى لو لم تكن تستخدم Moo.

"multiple"

يتيح لك الخيار "multiple" تحديد طرق متعددة لاستدعاء دالة.

signature_for repeat_string => (
  multiple => [
    { positional => [ Str, Int ] },
    { named => [ string => Str, count => Int ], named_to_list => true },
  ],
);

sub repeat_string ( $string, $count ) {
  return $string x $count;
}

repeat_string(            "Hello",          42  );    # يعمل
repeat_string(  string => "Hello", count => 42  );    # يعمل
repeat_string({ string => "Hello", count => 42 });    # يعمل
repeat_string( qr/hiya/ );                            # يموت

إنه يجمع بين فحوصات متعددة ويحاول كل منها حتى يعمل أحدها.

"list_to_named"

في العديد من الحالات، يمكن تنفيذ اتفاقيات الاستدعاء المتعددة التي تقدمها "multiple" بسهولة أكبر باستخدام "list_to_named".

signature_for repeat_string => (
  list_to_named => true,
  named         => [ string => Str, count => Int ],
  named_to_list => true,
);

sub repeat_string ( $string, $count ) {
  return $string x $count;
}

# الطرق القياسية لاستدعاء الدالة:
repeat_string(  string => "Hello", count => 42  );
repeat_string({ string => "Hello", count => 42 });

# يجب أن تعمل هذه أيضًا:
repeat_string( "Hello", count => 42 );
repeat_string( "Hello", { count => 42 } );
repeat_string( 42, string => "Hello" );
repeat_string( 42, { string => "Hello" } );
repeat_string( "Hello", 42 );

# هذا لن يعمل حاليًا، لأن "42" يظهر أولاً لذا يُعتبر هو السلسلة النصية، ولكن "Hello" ليس عددًا صحيحًا صالحًا!
repeat_string( 42, "Hello" );

يعمل الخيار "list_to_named" على ثلاث مراحل. عند البحث عن الهاش أو الهاش ريف (hashref) للمعلمات المسماة، إذا كانت هناك معلمات أخرى أولاً، يتم الاحتفاظ بهذه المعلمات جانباً في قائمة معلمات موضعية "متسللة".

لاحقًا عند التحقق من صحة المعلمات المسماة، إذا بدا أن أيًا منها مفقود، يتم فحص قائمة المعلمات الموضعية المتسللة وإذا أمكن، يتم أخذ المعلمة منها.

أخيرًا بعد معالجة جميع المعلمات المسماة، إذا كانت لا تزال هناك أي معلمات موضعية لم تكن مطلوبة، يتم طرح خطأ.

"signature"

"signature" يسمح بتعريف التوقيع داخل الدالة نفسها، وربما عند الطلب، وهو أمر مفيد في بعض الأحيان.

بدلاً من هذا:

signature_for foobar => (
  positional => [ Int, Str ],
);

sub foobar ( $foo, $bar ) {
  ...;
}

تقوم بهذا:

sub foobar {
  my $check = signature( positional => [ Int, Str ] );
  my ( $foo, $bar ) = $check->( @_ );
  ...;
}

أو استخدم "state $check" إذا كنت تعلم أن الفحص سيكون هو نفسه في كل مرة.

الدوال مقابل التوابع

للدوال التي يُقصد استدعاؤها كدوال:

signature_for my_sub => ( method => false, ... );

signature_for my_sub => ( ... ); # هذا هو الافتراضي على أي حال

للتوابع التي يُقصد استدعاؤها كتوابع على كائن مُبارَك (blessed object):

signature_for my_method => ( method => Object, ... );

للتوابع التي يُقصد استدعاؤها كتوابع على فئة:

signature_for my_method => ( method => ClassName, ... );

signature_for my_method => ( method => Str, ... );  # أسرع، أقل قابلية للقراءة

يُسمح أيضًا بما يلي، مما يشير إلى أن الدالة المقصودة للاستدعاء كتابع، ولكنك لا ترغب في إجراء فحوصات النوع على المستدعي:

signature_for my_method => ( method => builtin::true, ... );

signature_for my_method => ( method => 1, ... );

تتوفر اختصارات:

use Type::Params qw( signature_for_func signature_for_method );

signature_for_func my_function => ( ... );

signature_for_method my_method => ( ... );

المعلمات المسماة والموضعية المختلطة

يسمح الخياران "head" و "tail" بمعلمات موضعية مطلوبة في بداية أو نهاية قائمة المعلمات المسماة:

signature_for my_func => (
  head  => [ Int ],
  named => [
    foo => Int,
    bar => Optional[Int],
    baz => Optional[Int],
  ],
);

my_func( 42, foo => 21 );                 # مقبول
my_func( 42, foo => 21, bar  => 84 );     # مقبول
my_func( 42, foo => 21, bar  => 10.5 );   # غير مقبول
my_func( 42, foo => 21, quux => 84 );     # غير مقبول

بدلاً من ذلك، قد يكون "list_to_named" (انظر أعلاه) مفيدًا.

التواقيع المناسبة

ألا تتمنى لو أن دوالك يمكن أن تبدو هكذا؟

sub set_name ( Object $self, Str $name ) {
  $self->{name} = $name;
}

حسنًا؛ إليك بعض الحلول لتواقيع الدوال التي تعمل مع Type::Tiny...

Zydeco

Zydeco هي مجموعة أدوات بناء جملة Perl للكائنات (OO) مع دعم Type::Tiny مدمج في كل مكان.

package MyApp {
  use Zydeco;

  class Person {
    has name ( type => Str );

    method rename ( Str $new_name ) {
      printf( "%s سيُطلق عليه الآن %s\n", $self->name, $new_name );
      $self->name( $new_name );
    }

    coerce from Str via {
      $class->new( name => $_ )
    }
  }

  class Company {
    has owner ( type => 'Person' );
  }
}

my $acme = MyApp->new_company( owner => "Robert" );
$acme->owner->rename( "Bob" );

Kavorka

Kavorka هو تطبيق لتواقيع الدوال مكتوب لاستخدام "dwim_type" من Type::Utils لقيود النوع، والاستفادة من ميزات Type::Tiny مثل تضمين (inlining) والتحويل (coercions).

method set_name ( Str $name ) {
  $self->{name} = $name;
}

توفر تواقيع Kavorka مرونة أكبر، وسرعة أعلى قليلاً من Type::Params. (تأتي السرعة من تضمين جميع فحوصات النوع تقريبًا في جسم الدالة التي يتم الإعلان عنها.)

يتضمن Kavorka أيضًا دعمًا للتحقق من نوع القيمة المُرجعة.

يمكن أيضًا استخدام Kavorka كجزء من Moops، وهو إطار عمل أكبر للبرمجة الشيئية في Perl.

Function::Parameters

يوفر Function::Parameters دعمًا لـ Type::Tiny و MooseX::Types.

use Types::Standard qw( Str );
use Function::Parameters;

method set_name ( Str $name ) {
    $self->{name} = $name;
}

Attribute::Contract

يتطلب كل من Kavorka و Function::Parameters إصدارًا حديثًا نسبيًا من Perl. يدعم Attribute::Contract الإصدارات الأقدم باستخدام سحر أقل بكثير.

تحتاج إلى Attribute::Contract 0.03 أو أعلى.

use Attribute::Contract -types => [qw/Object Str/];

sub set_name :ContractRequires(Object, Str) {
    my ($self, $name) = @_;
    $self->{name} = $name;
}

يتضمن Attribute::Contract أيضًا دعمًا للتحقق من نوع القيمة المُرجعة.

Params::Validate

Type::Params ليس بديلاً مباشرًا لـ Params::Validate؛ واجهة برمجة التطبيقات مختلفة جدًا لدرجة الادعاء بذلك. ومع ذلك، فإنه يؤدي مهمة مماثلة، لذلك من المنطقي مقارنتهما.

  • يميل Type::Params إلى أن يكون أسرع إذا كان لديك دالة يتم استدعاؤها بشكل متكرر، ولكن قد يكون أبطأ قليلاً من Params::Validate للدوال التي يتم استدعاؤها بضع مرات فقط. هذا لأنه يقوم بالكثير من العمل في المرة الأولى التي يتم فيها استدعاء دالتك لجعل الاستدعاءات اللاحقة

MANUAL

This manual covers parameter validation, and specifically: the differences between Type::Params and Params::ValidationCompiler.

Type::Params

Type::Params is a module that lets you validate parameters using Type::Tiny type constraints.

  • It's faster than Params::Validate.
  • Params::Validate doesn't appear to have a particularly natural way of validating a mix of positional and named parameters.
  • Type::Utils allows you to coerce parameters. For example, if you expect a Path::Tiny object, you could coerce it from a string.
  • If you are primarily writing object-oriented code, using Moose or similar, and you are using Type::Tiny type constraints for your attributes, then using Type::Params allows you to use the same constraints for method calls.
  • Type::Params comes bundled with Types::Standard, which provides a much richer vocabulary of types than the type validation constants that come with Params::Validate. For example, Types::Standard provides constraints like "ArrayRef[Int]" (an arrayref of integers), while the closest from Params::Validate is "ARRAYREF", which you'd need to supplement with additional callbacks if you wanted to check that the arrayref contained integers.

    Whatsmore, Type::Params doesn't just work with Types::Standard, but also any other Type::Tiny type constraints.

Params::ValidationCompiler

Params::ValidationCompiler does basically the same thing as Type::Params.

  • Params::ValidationCompiler and Type::Params are likely to perform fairly similarly. In most cases, recent versions of Type::Params seem to be slightly faster, but except in very trivial cases, you're unlikely to notice the speed difference. Speed probably shouldn't be a factor when choosing between them.
  • Type::Params's syntax is more compact: 
    state $check = signature(
  pos => [
    Object,
    Optional[Int],
    Slurpy[ArrayRef],
  ],
);

    Versus:

    state $check = validation_for(
  params => [
    { type => Object },
    { type => Int,      optional => 1 },
    { type => ArrayRef, slurpy => 1 },
  ],
);
  • Params::ValidationCompiler probably has slightly better exceptions.
