Tcl_FSNewNativePath performs something similar to the reverse of the usual obj->path->native_rep conversions. If some code obtains a path in native form (e.g., via readlink or a native dialog), and that path is to be used at the Tcl level, then calling this function is an efficient way to create the corresponding path-type value.

The resulting value is a pure "path" value, which will receive a UTF-8 representation only if required by some Tcl code.

Tcl_FSGetNativePath is used for the Win/Unix native filesystem, allowing them to easily obtain the native representation (char* or TCHAR*) of a path. This function is a convenient wrapper to Tcl_FSGetInternalRep. It might be desirable in the future to have non-string based native representations (e.g., on macOS, a representation using an FSRef structure would likely be more efficient). On Windows a full Unicode representation would allow for unlimited length paths. Currently the representation is simply a character string which may contain the relative path or a full, normalized path in the native encoding (complex conditions determine which of these is supplied, so neither can be relied upon, unless the path is known to be absolute). If you need a native path that must be absolute, you should ask for the native version of a normalized path. If for some reason a non-absolute, non-normalized version of the path is needed, that must be constructed separately (e.g., using Tcl_FSGetTranslatedPath).

The native representation is cached so that repeated calls to this function require no additional conversions. The returned value is owned by Tcl and has a lifetime equivalent to that of the passed pathPtr (unless that is a relative path, in which case the native representation may be freed any time the cwd changes).

Tcl_FSFileSystemInfo returns a two-element list. The first element is the name of the filesystem (e.g., "native", "vfs", "zip", "prowrap", etc.), and the second is the path type within that filesystem (depends on the filesystem). The second element may be empty if the filesystem does not provide further categorization of files.

A valid value is returned, unless the path value is unrecognized, in which case NULL is returned.

Tcl_FSGetFileSystemForPath returns a pointer to the Tcl_Filesystem that accepts this path as valid.

If no filesystem accepts this path, NULL is returned.

Tcl_FSGetPathType determines whether a given path is relative to the current directory, relative to the current volume, or absolute.

It returns one of TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE, or TCL_PATH_VOLUME_RELATIVE.

PORTABLE STAT RESULT API

THE VIRTUAL FILESYSTEM API

A filesystem provides a Tcl_Filesystem structure containing pointers to functions that implement the various operations on a filesystem; these operations are invoked as needed by the generic layer, which generally happens through the functions mentioned above.

The Tcl_Filesystem structures are manipulated via the following methods.

Tcl_FSRegister takes a pointer to a filesystem structure and an optional clientData associated with that structure. Upon calling this function, Tcl will bind the filesystem to the list of known filesystems, and it will become immediately functional. Tcl does not check if the same filesystem is registered multiple times (and it's generally not a good idea). It returns TCL_OK.

Tcl_FSUnregister removes the given filesystem from the list of known filesystems, if it is known, and returns TCL_OK. If the filesystem is not currently registered, it returns TCL_ERROR.

Tcl_FSData returns the clientData associated with the given filesystem, if that filesystem is registered. Otherwise it returns NULL.

Tcl_FSMountsChanged is used to inform the Tcl core that the set of mount points for the given (already registered) filesystem has changed, and that cached file representations may thus no longer be accurate.

With the exception of the first three fields in this structure which contain simple data elements, all other fields contain pointers to functions called by the generic filesystem layer to perform a full range of filesystem-related actions.

The functions in this structure fall into three categories: infrastructure functions (the bulk of which must be implemented), operational functions (which must be implemented if a full filesystem is provided), and performance functions (which must be implemented only if they can be performed efficiently, or if they have side effects required by the filesystem; Tcl has less efficient emulations it can fall back to). It is important to note that, in the current version of Tcl, most of these fallbacks are used only to handle commands initiated in Tcl, not C. This means that, if a file rename instruction is issued in Tcl, and the relevant filesystems do not implement their Tcl_FSRenameFileProc, Tcl's core will fall back to a combination of other filesystem functions (it will use Tcl_FSCopyFileProc followed by Tcl_FSDeleteFileProc, and if Tcl_FSCopyFileProc is not implemented, there is a further fallback). However, if a Tcl_FSRenameFileProc instruction is issued at the C level, no such fallback occurs. This is true except for the last four entries in the filesystem table (lstat, load, getcwd and chdir), where fallbacks occur at the C level.

Any function that takes file names in Tcl_Obj form must take those names in UTF-8 form. The API infrastructure for conversions of these UTF-8 paths to efficient, cached native representations is designed for this.

بنية نظام الملفات

تحتوي هذه الحقول على معلومات أساسية حول بنية نظام الملفات وعناوين الوظائف المستخدمة لربط نظام ملفات معين بمسار ملف والتعامل مع التمثيل الداخلي لمسارات الملفات، على سبيل المثال، نسخ وتحرير هذه التمثيلات.

اسم النوع

طول الهيكل

الإصدار

يجب تعيين حقل version إلى TCL_FILESYSTEM_VERSION_1.

وظيفة المسار في نظام الملفات

يحتوي حقل pathInFilesystemProc على عنوان وظيفة يتم استدعاؤها لتحديد ما إذا كان المسار المحدد ينتمي إلى نظام الملفات هذا أم لا. ستستدعي Tcl فقط وظائف نظام الملفات الأخرى للمسارات التي أعادت وظيفة هذا النوع الخاص بها TCL_OK. إذا لم ينتم المسار، فيجب إرجاع -1 (سلوك Tcl للقيم المرتجعة الأخرى غير محدد). إذا تم إرجاع TCL_OK، فيمكن استخدام معلمة الإخراج الاختيارية clientDataPtr لإرجاع تمثيل داخلي (خاص بنظام الملفات) للمسار، والذي سيتم تخزينه داخل قيمة المسار ويمكن استرداده بكفاءة بواسطة وظائف نظام الملفات الأخرى في Tcl. ستقوم Tcl بتخزين معلومات تفيد بأن هذا المسار ينتمي إلى نظام الملفات هذا في نفس الوقت. يتم إلغاء صلاحية هذه ذاكرة التخزين المؤقت عند إضافتها أو إزالتها من القائمة الداخلية لأنظمة الملفات المعروفة في Tcl.

وظيفة تسوية المسار

وظيفة لتسوية المسار. يجب تنفيذها لجميع أنظمة الملفات التي قد تحتوي على تمثيلات سلسلة نصية متعددة لنفس المسار. في Tcl، يجب أن يكون لكل مسار تمثيل فريد واحد "عادي". اعتمادًا على نظام الملفات، قد يكون هناك أكثر من تمثيل سلسلة نصية غير عادي يشير إلى نفس المسار (على سبيل المثال، مسار نسبي، مسار بحالة مختلفة إذا كان نظام الملفات غير حساس للحالة، مسار يحتوي على إشارة إلى دليل المستخدم مثل ~، مسار يحتوي على روابط رمزية، وما إلى ذلك). إذا كان المكون الأخير للمسار رابطًا رمزيًا، فلا يجب تحويله إلى القيمة التي يشير إليها (ولكن يجب أن تكون حالته أو جوانبه الأخرى فريدة). يجب تحويل جميع المكونات الأخرى للمسار من الروابط الرمزية. هذا الاستثناء ضروري للتوافق مع معاني Tcl لأمر file، delete، rename، copy مع الروابط الرمزية. يمكن استدعاء هذه الوظيفة مع nextCheckpoint في بداية المسار (أي صفر)، أو في نهاية المسار، أو في أي فاصل ملف وسيط. لن يتم استدعاؤها في أي نقطة عشوائية أخرى في المسار. في الحالة الأخيرة من الحالات الثلاث الصالحة، يمكن للتنفيذ افتراض أن المسار حتى بما في ذلك فاصل الملف معروف ومنظم.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

عمليات نظام الملفات

تحتوي حقول هذا القسم من الهيكل على عناوين الوظائف التي يتم استدعاؤها لتنفيذ عمليات نظام الملفات الأساسية. يجب على نظام الملفات الذي يتوقع استخدامه مع المجموعة الكاملة من أوامر Tcl القياسية تنفيذ كل هذه العمليات. إذا لم يتم تنفيذ بعضها، فقد تفشل بعض أوامر Tcl عند التشغيل على المسارات داخل نظام الملفات هذا. ومع ذلك، في بعض الحالات قد يكون هذا مرغوبًا (على سبيل المثال، يجب ألا ينفذ نظام الملفات للقراءة فقط الوظائف الأربع الأخيرة، ويجب ألا ينفذ نظام الملفات الذي لا يدعم الروابط الرمزية وظيفة readlink، وما إلى ذلك. يتوقع نواة Tcl أن تتصرف أنظمة الملفات بهذه الطريقة).

وظيفة نوع مسار نظام الملفات

وظيفة لتحديد نوع المسار في نظام الملفات هذا. يمكن أن تكون NULL، وفي هذه الحالة لن يتمكن المستخدم من الحصول على معلومات النوع من نظام الملفات. يتم استخدام type فقط لأغراض إعلامية ويجب إرجاعه كسلسلة نصية لكائن Tcl المرتجع. قد يكون القيمة المرتجعة النموذجية هي networked أو zip أو ftp. Tcl مملوكة للنتيجة، وبالتالي ستزيد Tcl عداد المراجع للقيمة إذا كانت ترغب في الاحتفاظ بها.

typedef Tcl_Obj *Tcl_FSFilesystemSeparatorProc(

وظيفة stat

وظيفة لمعالجة استدعاء Tcl_FSStat. يجب تنفيذها لأي نظام ملفات معقول، حيث تعتمد العديد من أوامر مستوى Tcl عليه بشكل حاسم (على سبيل المثال، file atime، file isdirectory، file size، glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

تقوم الوظيفة Tcl_FSStatProc بملء الهيكل statPtr بمعلومات حول الملف المحدد. لا يلزم الوصول إلى حقوق القراءة أو الكتابة أو الاختبار للملف (أو كائن نظام ملفات آخر) الذي يحمل اسمه في pathPtr. ومع ذلك، يلزم حقوق البحث في جميع الدلائل المذكورة في المسار الذي يشير إلى الملف. يتضمن هيكل stat معلومات حول الجهاز، ورقم i-node (دائمًا 0 في Windows)، ووضع الامتيازات، وعدد الروابط (دائمًا 1 في Windows)، ومعرف المستخدم (دائمًا 0 في Windows)، ومعرف المجموعة (دائمًا 0 في Windows)، و rdev (نفس الجهاز في Windows)، والحجم، وآخر مرة تم الوصول إليها، وآخر مرة تم تعديلها، وآخر مرة تم تغيير بيانات التعريف.

إذا كان الملف الذي تمثله pathPtr موجودًا، فإن Tcl_FSStatProc تُرجع 0 ويتم ملء الهيكل stat بالبيانات. وإلا، فإنها تُرجع -1 ولا يتم تقديم أي معلومات stat.

وظيفة الوصول

وظيفة لمعالجة استدعاء Tcl_FSAccess. يجب تنفيذها لأي نظام ملفات معقول، حيث تعتمد العديد من أوامر مستوى Tcl عليه بشكل حاسم (على سبيل المثال، file exists، file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

تتحقق الوظيفة Tcl_FSAccessProc مما إذا كان سيُسمح للعملية بالقراءة أو الكتابة أو اختبار وجود الملف (أو كائن نظام ملفات آخر) الذي يحمل اسمه في pathPtr. إذا كان اسم المسار يشير إلى رابط رمزي، فيجب اختبار أذونات الملف الذي يشير إليه هذا الرابط الرمزي.

في حالة النجاح (جميع الأذونات المطلوبة ممنوحة)، يتم إرجاع 0. في حالة حدوث خطأ (يطلب بت واحد على الأقل في mode رفض إذن، أو يحدث خطأ آخر)، يتم إرجاع -1.

وظيفة لمعالجة استدعاء لـ Tcl_FSOpenFileChannel. يجب تنفيذ هذه الوظيفة لأي نظام ملفات معقول، حيث أن أي عملية تتطلب فتح أو الوصول إلى محتويات ملف ستستخدم هذه الوظيفة (على سبيل المثال، open، encoding والعديد من أوامر Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

تقوم Tcl_FSOpenFileChannelProc بفتح ملف محدد بواسطة pathPtr وإرجاع مقبض قناة يمكن استخدامه لإجراء إدخال وإخراج على الملف. تم تصميم واجهة برمجة التطبيقات هذه على غرار وظيفة fopen من مكتبة الإدخال/الإخراج القياسية في Unix. بناء الجملة ومعنى جميع الوسائط مشابهان لتلك المحددة في أمر Tcl open عند فتح ملف، حيث الوسيط mode هو مزيج من علامات POSIX O_RDONLY، O_WRONLY، إلخ. إذا حدث خطأ أثناء فتح القناة، فإن Tcl_FSOpenFileChannelProc ترجع NULL وتسجل رمز خطأ POSIX يمكن الحصول عليه باستخدام Tcl_GetErrno. علاوة على ذلك، إذا كان interp غير فارغ، فإن Tcl_FSOpenFileChannelProc تترك رسالة خطأ في نتيجة interp بعد أي خطأ.

        const char *pattern,
        Tcl_GlobTypeData *types);

يجب أن ترجع الوظيفة جميع الملفات أو الدلائل (أو كائنات نظام الملفات الأخرى) التي تطابق النمط المحدد وتتوافق مع مواصفات types. يمكن استدعاء هذه الوظيفة بطريقتين. إذا كان pattern هو NULL، فإن pathPtr هو مواصفات كاملة لملف أو دليل يجب التحقق منه لوجوده ونوعه الصحيح. بخلاف ذلك، فإن pathPtr هو دليل ويجب على الوظيفة البحث عن ملفات أو دلائل لها النوع الصحيح. في كلتا الحالتين، يمكن افتراض أن pathPtr غير فارغ وغير فارغ. لا يتم توثيق ما إذا كان pathPtr سيحتوي على فاصل ملف في النهاية حاليًا، لذلك يجب أن يكون الكود مرنًا لكلا الاحتمالين.

قيمة الإرجاع هي نتيجة Tcl قياسية تشير إلى ما إذا كان قد حدث خطأ أثناء عملية المطابقة. توضع رسائل الخطأ في interp، ما لم يكن interp فارغًا، وفي هذه الحالة لا يتم إنشاء رسالة خطأ؛ في نتيجة TCL_OK، يجب إضافة النتائج إلى القيمة المقدمة في resultPtr (والتي يُفترض أنها قائمة Tcl صالحة وغير مشتركة). يجب أن تتضمن المطابقات المضافة إلى resultPtr أي بادئة مسار معطاة في pathPtr (مما يعني عادةً أنها ستكون مواصفات مسار مطلقة). لاحظ أنه إذا لم يتم العثور على مطابقات، فسيتم الحصول على نتيجة فارغة؛ يتم الإبلاغ عن الأخطاء فقط للمشاكل الفعلية في الملف أو نظام الملفات أثناء عملية المطابقة.

تحتوي البنية Tcl_GlobTypeData التي يتم تمريرها في المعامل types على الحقول التالية:

typedef struct Tcl_GlobTypeData {
    /* يتوافق مع bcdpfls كما في 'find -t' */
    int type;
    /* يتوافق مع أذونات الملف */
    int perm;
    /* نوع الماك مقبول */
    Tcl_Obj *macType;
    /* منشئ الماك مقبول */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

هناك حالتان محددتان من المهم التعامل معهما بشكل صحيح، كلاهما عندما يكون types غير NULL. الحالتان هما عندما يكون types->types هو TCL_GLOB_TYPE_DIR أو TCL_GLOB_TYPE_MOUNT (وخاصة عندما تكون العلامات الأخرى خاطئة). في الحالة الأولى، يجب على الوظيفة سرد الدلائل المحتوتة. تستخدم Tcl هذا لتنفيذ globing متكرر، لذلك من الأهمية بمكان أن تنفذ أنظمة الملفات مطابقة الدلائل بشكل صحيح. في الحالة الثانية، مع TCL_GLOB_TYPE_MOUNT، يجب على نظام الملفات سرد نقاط التحميل الموجودة داخل الدليل المحدد بواسطة pathPtr (وفي هذه الحالة، لا يلزم أن يكون pathPtr في نفس نظام الملفات - بخلاف جميع الحالات الأخرى التي يتم فيها استدعاء هذه الوظيفة). دعم هذا أمر بالغ الأهمية إذا كانت Tcl تريد أن تكون هناك انتقالات سلسة بين أنظمة الملفات.

CHDIRPROC

دالة لمعالجة استدعاء Tcl_FSChdir. إذا لم تقم أنظمة الملفات بتنفيذ هذا، فسيتم محاكاته بسلسلة من فحوصات الوصول إلى الدليل. بخلاف ذلك، تحتاج أنظمة الملفات الافتراضية التي تنفذها فقط إلى الاستجابة بنتيجة إرجاع إيجابية إذا كان pathPtr دليلاً صالحًا ويمكن الوصول إليه في نظام ملفاتها. لا يلزمها تذكر النتيجة، حيث سيتم تذكرها تلقائيًا لاستخدامها بواسطة Tcl_FSGetCwd. يجب على أنظمة الملفات الحقيقية تنفيذ الإجراء الصحيح (أي استدعاء واجهة برمجة تطبيقات chdir للنظام الصحيح).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

تقوم Tcl_FSChdirProc بتغيير الدليل الحالي للتطبيق إلى القيمة المحددة في pathPtr. تُرجع الدالة -1 عند الخطأ أو 0 عند النجاح.
