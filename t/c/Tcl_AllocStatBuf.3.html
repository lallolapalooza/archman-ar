DESCRIPTION

There are several reasons for calling the Tcl_FS API functions (e.g. Tcl_FSAccess and Tcl_FSStat) rather than calling system level functions like access and stat directly. First, they will work cross-platform, so an extension which calls them should work unmodified on Unix and Windows. Second, the Windows implementation of some of these functions fixes some bugs in the system level calls. Third, these function calls deal with any “Utf to platform-native” path conversions which may be required (and may cache the results of such conversions for greater efficiency on subsequent calls). Fourth, and perhaps most importantly, all of these functions are “virtual filesystem aware”. Any virtual filesystem (VFS for short) which has been registered (through Tcl_FSRegister) may reroute file access to alternative media or access methods. This means that all of these functions (and therefore the corresponding file, glob, pwd, cd, open, etc. Tcl commands) may be operate on “files” which are not native files in the native filesystem. This also means that any Tcl extension which accesses the filesystem (FS for short) through this API is automatically “virtual filesystem aware”. Of course, if an extension accesses the native filesystem directly (through platform-specific APIs, for example), then Tcl cannot intercept such calls.

If appropriate VFSes have been registered, the “files” may, to give two examples, be remote (e.g. situated on a remote ftp server) or archived (e.g. lying inside a .zip archive). Such registered filesystems provide a lookup table of functions to implement all or some of the functionality listed here. Finally, the Tcl_FSStat and Tcl_FSLstat calls abstract away from what the “struct stat” buffer is actually declared to be, allowing the same code to be used both on systems with and systems without support for files larger than 2GB in size.

The Tcl_FS API is Tcl_Obj-ified and may cache internal representations and other path-related strings (e.g. the current working directory). One side-effect of this is that one must not pass in values with a reference count of zero to any of these functions. If such calls were handled, they might result in memory leaks (under some circumstances, the filesystem code may wish to retain a reference to the passed in value, and so one must not assume that after any of these calls return, the value still has a reference count of zero - it may have been incremented) or in a direct segmentation fault (or other memory access error) due to the value being freed part way through the complex value manipulation required to ensure that the path is fully normalized and absolute for filesystem determination. The practical lesson to learn from this is that

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

is wrong, and may cause memory errors. The path must have its reference count incremented before passing it in, or decrementing it. For this reason, values with a reference count of zero are considered not to be valid filesystem paths and calling any Tcl_FS API function with such a value will result in no action being taken.

FS API FUNCTIONS

Tcl_FSCopyFile attempts to copy the file given by srcPathPtr to the path name given by destPathPtr. If the two paths given lie in the same filesystem (according to Tcl_FSGetFileSystemForPath) then that filesystem's “copy file” function is called (if it is non-NULL). Otherwise the function returns -1 and sets the errno global C variable to the “EXDEV” POSIX error code (which signifies a “cross-domain link”).

Tcl_FSCopyDirectory attempts to copy the directory given by srcPathPtr to the path name given by destPathPtr. If the two paths given lie in the same filesystem (according to Tcl_FSGetFileSystemForPath) then that filesystem's “copy file” function is called (if it is non-NULL). Otherwise the function returns -1 and sets the errno global C variable to the “EXDEV” POSIX error code (which signifies a “cross-domain link”).

Tcl_FSCreateDirectory attempts to create the directory given by pathPtr by calling the owning filesystem's “create directory” function.

Tcl_FSDeleteFile attempts to delete the file given by pathPtr by calling the owning filesystem's “delete file” function.

Tcl_FSRemoveDirectory attempts to remove the directory given by pathPtr by calling the owning filesystem's “remove directory” function.

Tcl_FSRenameFile attempts to rename the file or directory given by srcPathPtr to the path name given by destPathPtr. If the two paths given lie in the same filesystem (according to Tcl_FSGetFileSystemForPath) then that filesystem's “rename file” function is called (if it is non-NULL). Otherwise the function returns -1 and sets the errno global C variable to the “EXDEV” POSIX error code (which signifies a “cross-domain link”).

Tcl_FSListVolumes calls each filesystem which has a non-NULL “list volumes” function and asks them to return their list of root volumes. It accumulates the return values in a list which is returned to the caller (with a reference count of 0).

Tcl_FSEvalFileEx reads the file given by pathPtr using the encoding identified by encodingName and evaluates its contents as a Tcl script. It returns the same information as Tcl_EvalObjEx. If encodingName is NULL, the system encoding is used for reading the file contents. If the file could not be read then a Tcl error is returned to describe why the file could not be read. The eofchar for files is “\x1A” (^Z) for all platforms. If you require a “^Z” in code for string comparison, you can use “\x1A”, which will be safely substituted by the Tcl interpreter into “^Z”. Tcl_FSEvalFile is a simpler version of Tcl_FSEvalFileEx that always uses the system encoding when reading the file.

Tcl_FSLoadFile dynamically loads a binary code file into memory and returns the addresses of two procedures within that file, if they are defined. The appropriate function for the filesystem to which pathPtr belongs will be called. If that filesystem does not implement this function (most virtual filesystems will not, because of OS limitations in dynamically loading binary code), Tcl will attempt to copy the file to a temporary directory and load that temporary file. Tcl_FSUnloadFile reverses the operation, asking for the library indicated by the loadHandle to be removed from the process. Note that, unlike with the unload command, this does not give the library any opportunity to clean up.

Both the above functions return a standard Tcl completion code. If an error occurs, an error message is left in the interp's result.

The token provided via the variable indicated by loadHandlePtr may be used with Tcl_FindSymbol.

Tcl_FSMatchInDirectory is used by the globbing code to search a directory for all files which match a given pattern. The appropriate function for the filesystem to which pathPtr belongs will be called.

The return value is a standard Tcl result indicating whether an error occurred in globbing. Error messages are placed in interp (unless interp is NULL, which is allowed), but good results are placed in the resultPtr given.

Note that the glob code implements recursive patterns internally, so this function will only ever be passed simple patterns, which can be matched using the logic of string match. To handle recursion, Tcl will call this function frequently asking only for directories to be returned. A special case of being called with a NULL pattern indicates that the path needs to be checked only for the correct type.

Tcl_FSLink replaces the library version of readlink, and extends it to support the creation of links. The appropriate function for the filesystem to which linkNamePtr belongs will be called.

If the toPtr is NULL, a “read link” action is performed. The result is a Tcl_Obj specifying the contents of the symbolic link given by linkNamePtr, or NULL if the link could not be read. The result is owned by the caller, which should call Tcl_DecrRefCount when the result is no longer needed. If the toPtr is not NULL, Tcl should create a link of one of the types passed in in the linkAction flag. This flag is an OR'ed combination of TCL_CREATE_SYMBOLIC_LINK and TCL_CREATE_HARD_LINK. Where a choice exists (i.e. more than one flag is passed in), the Tcl convention is to prefer symbolic links. When a link is successfully created, the return value should be toPtr (which is therefore already owned by the caller). If unsuccessful, NULL is returned.

The value of lenPtr is the number of elements in the split path. If non-NULL, it is filled with the number of elements in the split path. The value of basePtr is the base path on to which to join the given elements. May be NULL. The value of objc is the number of elements in objv. The value of objv are the elements to join to the given base path. The value of linkNamePtr is the name of the link to be created or read. The value of toPtr is what the link called linkNamePtr should be linked to, or NULL if the symbolic link specified by linkNamePtr is to be read. The value of linkAction is an OR-ed combination of flags indicating what kind of link should be created (will be ignored if toPtr is NULL). Tcl_FSNewNativePath يقوم بشيء مثل عكس التحويلات المعتادة obj->path->nativerep. إذا استرد بعض التعليمات البرمجية مسارًا في شكل أصلي (من، على سبيل المثال، readlink أو مربع حوار أصلي)، وكان هذا المسار سيتم استخدامه على مستوى Tcl، فإن استدعاء هذه الوظيفة يعد طريقة فعالة لإنشاء نوع قيمة المسار المناسب.

القيمة الناتجة هي قيمة "مسار" نقية، والتي ستحصل فقط على تمثيل سلسلة UTF-8 إذا كان ذلك مطلوبًا بواسطة بعض تعليمات Tcl البرمجية.

Tcl_FSGetNativePath مخصص للاستخدام من قبل أنظمة الملفات الأصلية Win/Unix، بحيث يمكنهم بسهولة استرداد التمثيل الأصلي (char* أو TCHAR*) للمسار. هذه الوظيفة هي غلاف مريح حول Tcl_FSGetInternalRep. قد يكون من المرغوب فيه في المستقبل وجود تمثيلات أصلية غير قائمة على السلاسل (على سبيل المثال، على macOS، قد يكون التمثيل الذي يستخدم هيكل fileSpec أو FSRef أكثر كفاءة). على Windows، سيسمح تمثيل Unicode كامل بمسارات ذات طول غير محدود. حاليًا، التمثيل هو ببساطة سلسلة أحرف قد تحتوي إما على المسار النسبي أو مسار كامل ومطلق ومنظم بالترميز الأصلي (تحدد الظروف المعقدة أي من هذه سيتم توفيره، لذلك لا يمكن الاعتماد على أي منهما، إلا إذا كان المسار معروفًا بأنه مطلق). إذا كنت بحاجة إلى مسار أصلي يجب أن يكون مطلقًا، فيجب عليك طلب الإصدار الأصلي لمسار منظم. إذا، لسبب ما، كان هناك حاجة إلى إصدار غير مطلق وغير منظم للمسار، فيجب إنشاؤه بشكل منفصل (على سبيل المثال، باستخدام Tcl_FSGetTranslatedPath).

يتم تخزين التمثيل الأصلي مؤقتًا بحيث لا تتطلب الاستدعاءات المتكررة لهذه الوظيفة تحويلات إضافية. القيمة المرجعة مملوكة لـ Tcl ولها عمر مكافئ لعمر pathPtr الذي تم تمريره (ما لم يكن مسارًا نسبيًا، وفي هذه الحالة قد يتم تحرير التمثيل الأصلي في أي وقت يتغير فيه cwd).

Tcl_FSFileSystemInfo ترجع قائمة من عنصرين. العنصر الأول هو اسم نظام الملفات (على سبيل المثال، "native"، "vfs"، "zip"، أو "prowrap"، ربما)، والثاني هو النوع المحدد للمسار المعطى داخل نظام الملفات هذا (وهو يعتمد على نظام الملفات). قد يكون العنصر الثاني فارغًا إذا لم يوفر نظام الملفات تصنيفًا إضافيًا للملفات.

يتم إرجاع قائمة صالحة، ما لم يتم التعرف على قيمة المسار، عندما يتم إرجاع NULL.

Tcl_FSGetFileSystemForPath ترجع مؤشرًا إلى Tcl_Filesystem الذي يقبل هذا المسار على أنه صالح.

إذا لم يقبل أي نظام ملفات المسار، يتم إرجاع NULL.

Tcl_FSGetPathType تحدد ما إذا كان المسار المعطى نسبيًا للدليل الحالي، أو نسبيًا للمجلد الحالي، أو مطلقًا.

ترجع أحد القيم التالية: TCL_PATH_ABSOLUTE، TCL_PATH_RELATIVE، أو TCL_PATH_VOLUME_RELATIVE

واجهة برمجة تطبيقات نتائج stat قابلة للنقل

Tcl_AllocStatBuf تخصص Tcl_StatBuf في كومة النظام (والتي يمكن إلغاء تخصيصها عن طريق تمريرها إلى ckfree). هذا يسمح للامتدادات باستدعاء Tcl_FSStat و Tcl_FSLstat دون الاعتماد على حجم المخزن المؤقت. وهذا بدوره يعتمد على الأعلام المستخدمة لبناء Tcl.

واجهة برمجة تطبيقات نظام الملفات الافتراضي

يقدم نظام الملفات هيكل Tcl_Filesystem الذي يحتوي على مؤشرات إلى وظائف تنفذ العمليات المختلفة على نظام الملفات؛ يتم استدعاء هذه العمليات حسب الحاجة بواسطة الطبقة العامة، والتي تحدث بشكل عام من خلال الوظائف المدرجة أعلاه.

يتم التعامل مع هياكل Tcl_Filesystem باستخدام الطرق التالية.

Tcl_FSRegister يأخذ مؤشرًا إلى هيكل نظام الملفات وقطعة اختيارية من البيانات لربطها بنظام الملفات هذا. عند استدعاء هذه الوظيفة، يقوم Tcl بإرفاق نظام الملفات بقائمة أنظمة الملفات المعروفة، ويصبح فعالًا بالكامل على الفور. لا يتحقق Tcl مما إذا كان نفس نظام الملفات مسجلًا عدة مرات (وبشكل عام هذا ليس شيئًا جيدًا للقيام به). سيتم إرجاع TCL_OK.

Tcl_FSUnregister يزيل هيكل نظام الملفات المحدد من قائمة أنظمة الملفات المعروفة، إذا كان معروفًا، ويرجع TCL_OK. إذا لم يكن نظام الملفات مسجلًا حاليًا، يتم إرجاع TCL_ERROR.

Tcl_FSData سترجع clientData المرتبط بنظام الملفات المحدد، إذا كان نظام الملفات هذا مسجلًا. وإلا فإنه سيرجع NULL.

Tcl_FSMountsChanged تستخدم لإعلام جوهر Tcl بأن مجموعة نقاط التحميل لنظام الملفات المحدد (المسجل بالفعل) قد تغيرت، وأن التمثيلات المخزنة مؤقتًا للملفات قد لا تكون صحيحة بعد ذلك.

باستثناء الحقول الثلاثة الأولى في هذا الهيكل التي تحتوي على عناصر بيانات بسيطة، تحتوي جميع الإدخالات على عناوين وظائف يتم استدعاؤها بواسطة طبقة نظام الملفات العامة لتنفيذ النطاق الكامل للإجراءات المتعلقة بنظام الملفات.

تنقسم العديد من الوظائف في هذا الهيكل إلى ثلاث فئات: وظائف البنية التحتية (التي يجب تنفيذ معظمها)، ووظائف التشغيل (التي يجب تنفيذها إذا تم توفير نظام ملفات كامل)، ووظائف الكفاءة (التي تحتاج فقط إلى تنفيذها إذا كان يمكن القيام بها بكفاءة، أو إذا كان لها آثار جانبية مطلوبة من قبل نظام الملفات؛ لدى Tcl محاكيات أقل كفاءة يمكنها الرجوع إليها). من المهم ملاحظة أنه في الإصدار الحالي من Tcl، يتم استخدام معظم هذه الرجوعيات فقط لمعالجة الأوامر التي تبدأ في Tcl، وليس في C. ما يعنيه هذا هو، أنه إذا تم إصدار أمر file rename في Tcl، ولم تقم أنظمة الملفات ذات الصلة بتنفيذ Tcl_FSRenameFileProc الخاصة بها، فإن نواة Tcl ستعود بدلاً من ذلك إلى مزيج من وظائف أنظمة الملفات الأخرى (ستستخدم Tcl_FSCopyFileProc متبوعة بـ Tcl_FSDeleteFileProc، وإذا لم يتم تنفيذ Tcl_FSCopyFileProc فهناك رجوع إضافي). ومع ذلك، إذا تم إصدار أمر Tcl_FSRenameFileProc على مستوى C، فلن تحدث أي رجوعات من هذا القبيل. هذا صحيح باستثناء آخر أربعة إدخالات في جدول نظام الملفات (lstat، load، getcwd و chdir) والتي تحدث في الواقع رجوعيات على مستوى C.

أي وظائف تأخذ أسماء مسارات في شكل Tcl_Obj تأخذ هذه الأسماء في شكل UTF-8. تم تصميم واجهة برمجة تطبيقات البنية التحتية لنظام الملفات لدعم التحويل الفعال والمخزن مؤقتًا لهذه المسارات UTF-8 إلى تمثيلات أصلية أخرى.

بنية نظام الملفات

تحتوي هذه الحقول على معلومات أساسية حول بنية نظام الملفات وعناوين الوظائف المستخدمة لربط نظام ملفات معين بمسار ملف، وإدارة التمثيل الداخلي لمسارات الملفات، على سبيل المثال، نسخ هذه التمثيلات وتحريرها.

اسم النوع

يحتوي الحقل typeName على سلسلة نصية تنتهي ب NULL تحدد نوع نظام الملفات المنفذ، على سبيل المثال، "native" أو "zip" أو "vfs".

طول البنية

عادةً ما يتم تنفيذ الحقل structureLength كـ sizeof(Tcl_Filesystem)، وهو موجود للسماح بتوافق ثنائي أسهل إذا تغير حجم البنية في إصدار مستقبلي من Tcl.

الإصدار

يجب تعيين الحقل version إلى TCL_FILESYSTEM_VERSION_1.

وظيفة مسار نظام الملفات

يحتوي الحقل pathInFilesystemProc على عنوان دالة يتم استدعاؤها لتحديد ما إذا كانت قيمة المسار المعطاة تنتمي إلى نظام الملفات هذا أم لا. ستستدعي Tcl فقط الوظائف الأخرى لنظام الملفات بمسار تُرجع هذه الدالة له TCL_OK. إذا لم يكن المسار ينتمي، يجب إرجاع -1 (سلوك Tcl للقيم المرتجعة الأخرى غير محدد). إذا تم إرجاع TCL_OK، يمكن استخدام معلمة الإخراج clientDataPtr لإرجاع تمثيل داخلي (خاص بنظام الملفات) للمسار، والذي سيتم تخزينه مؤقتًا داخل قيمة المسار ويمكن استعادته بكفاءة بواسطة وظائف أنظمة الملفات الأخرى في Tcl. ستقوم Tcl أيضًا بتخزين حقيقة أن هذا المسار ينتمي إلى نظام الملفات هذا. يتم إبطال هذه التخزينات المؤقتة عند إضافة أو إزالة هياكل نظام الملفات من القائمة الداخلية لأنظمة الملفات المعروفة في Tcl.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

وظيفة تكرار التمثيل الداخلي

تقوم هذه الدالة بعمل نسخة من التمثيل الداخلي للمسار ويتم استدعاؤها عندما تحتاج Tcl إلى تكرار قيمة المسار. إذا كانت NULL، فلن تقوم Tcl ببساطة بنسخ التمثيل الداخلي، والذي قد يلزم إنشاؤه لاحقًا.

typedef ClientData Tcl_FSDupInternalRepProc(
        ClientData clientData);

وظيفة تحرير التمثيل الداخلي

تحرر التمثيل الداخلي. يجب تنفيذها إذا كان يلزم تحرير التمثيل الداخلي (أي إذا تم تخصيص ذاكرة عند إنشاء تمثيل داخلي)، ولكن يمكن أن تكون NULL بخلاف ذلك.

typedef void Tcl_FSFreeInternalRepProc(
        ClientData clientData);

وظيفة التحويل من داخلي إلى طبيعي

دالة لتحويل التمثيل الداخلي إلى مسار طبيعي. هذه مطلوبة فقط إذا كان نظام الملفات ينشئ قيمًا نقية بتمثيل string/path. القيمة المرتجعة هي قيمة Tcl التي يكون تمثيلها string هو المسار الطبيعي.

typedef Tcl_Obj *Tcl_FSInternalToNormalizedProc(
        ClientData clientData);

وظيفة إنشاء تمثيل داخلي

دالة لأخذ قيمة مسار وحساب تمثيل داخلي لها، وتخزين هذا التمثيل الأصلي في القيمة. قد تكون NULL إذا لم تكن للمسارات تمثيل داخلي، أو إذا كانت Tcl_FSPathInFilesystemProc لنظام الملفات هذا تنشئ دائمًا تمثيلًا داخليًا على الفور للمسارات التي تقبلها.

typedef ClientData Tcl_FSCreateInternalRepProc(
        Tcl_Obj *pathPtr);

وظيفة تطبيع المسار

دالة لتطبيع المسار. يجب تنفيذها لجميع أنظمة الملفات التي قد يكون لها تمثيلات string متعددة لنفس قيمة المسار. في Tcl، يجب أن يكون لكل "مسار" تمثيل string "طبيعي" فريد. اعتمادًا على نظام الملفات، قد يكون هناك أكثر من تمثيل string واحد غير طبيعي يشير إلى قيمة المسار تلك (على سبيل المثال، مسار نسبي، مسار بحالة مختلفة إذا كان نظام الملفات غير حساس للحالة، مسار مع مرجع لدليل المنزل مثل ~، مسار مع روابط رمزية، إلخ). إذا كان المكون الأخير للمسار رابطًا رمزيًا، فلا يجب تحويله إلى القيمة التي يشير إليها، ولكن يجب أن تكون حالته أو جوانبه الأخرى فريدة. يجب تحويل جميع مكونات المسار الأخرى من الروابط الرمزية. هذا الاستثناء ضروري لمطابقة دلالات Tcl مع file delete، file rename، file copy عند التعامل مع الروابط الرمزية. قد يتم استدعاء هذه الدالة مع nextCheckpoint في بداية المسار (أي صفر)، أو في نهاية المسار، أو في أي فاصل ملف وسيط في المسار. لن تشير أبدًا إلى أي موضع عشوائي في المسار. في الحالة الأخيرة من الحالات الثلاث الصالحة، يمكن للمنفذ أن يفترض أن المسار حتى الفاصل ويتضمنه معروف وطبيعي.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

عمليات نظام الملفات

تحتوي حقول هذا القسم من البنية على عناوين وظائف يتم استدعاؤها لتنفيذ عمليات نظام الملفات الأساسية. يجب على نظام الملفات الذي يتوقع استخدامه مع المجموعة الكاملة من أوامر Tcl تنفيذ جميع هذه الوظائف. إذا لم يتم تنفيذ بعضها، فقد تفشل بعض أوامر Tcl عند العمل بمسارات داخل نظام الملفات هذا. ومع ذلك، قد يكون هذا مرغوبًا فيه في بعض الحالات (على سبيل المثال، لا ينبغي لنظام ملفات للقراءة فقط تنفيذ الوظائف الأربع الأخيرة، ونظام ملفات لا يدعم الروابط الرمزية لا ينبغي له تنفيذ وظيفة readlink، إلخ. يتوقع نواة Tcl أن تتصرف أنظمة الملفات بهذه الطريقة).

وظيفة نوع مسار نظام الملفات

دالة لتحديد نوع المسار في نظام الملفات هذا. قد تكون NULL، وفي هذه الحالة لن يتم توفير معلومات النوع لمستخدمي نظام الملفات. يستخدم type لأغراض إعلامية فقط ويجب إرجاعه كتمثيل string لقيمة Tcl_Obj المرتجعة. قد تكون القيمة النموذجية "networked" أو "zip" أو "ftp". قيمة Tcl_Obj المرتجعة مملوكة لنظام الملفات، وبالتالي ستزيد Tcl عداد المراجع لتلك القيمة إذا رغبت في ذلك.

typedef Tcl_Obj *Tcl_FSFilesystemPathTypeProc(
        Tcl_Obj *pathPtr);

وظيفة فاصل نظام الملفات

دالة لإرجاع حرف الفاصل لنظام الملفات هذا. يجب تنفيذ هذا فقط إذا كان نظام الملفات يريد استخدام فاصل مختلف عن الفاصل القياسي "/*". من بين استخدامات أخرى، يتم إرجاعها بواسطة أمر file separator. يجب أن يكون للقيمة المرتجعة عداد مراجع صفر.

typedef Tcl_Obj *Tcl_FSFilesystemSeparatorProc(
        Tcl_Obj *pathPtr);

وظيفة stat

دالة لمعالجة استدعاء Tcl_FSStat. يجب تنفيذها لأي نظام ملفات معقول، لأن العديد من أوامر المستوى Tcl تعتمد عليها بشكل حاسم (على سبيل المثال، file atime، file isdirectory، file size، glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

ستقوم دالة Tcl_FSStatProc بملء البنية statPtr بمعلومات حول الملف المحدد. لا يلزم وجود حقوق وصول للملف للحصول على هذه المعلومات، ولكن يلزم وجود حقوق بحث في جميع الدلائل المذكورة في المسار المؤدي إلى الملف. تتضمن بنية stat معلومات حول الجهاز، والجذع (دائمًا 0 على Windows)، ووضع الامتياز، وعدد الروابط (دائمًا 1 على Windows)، و UID (دائمًا 0 على Windows)، و GID (دائمًا 0 على Windows)، و rdev (نفس الجهاز على Windows)، والحجم، ووقت آخر وصول، ووقت آخر تعديل، ووقت آخر تغيير بيانات وصفية.

إذا كان الملف الذي تمثله pathPtr موجودًا، فإن Tcl_FSStatProc ترجع 0 ويتم ملء بنية stat بالبيانات. بخلاف ذلك، يتم إرجاع -1 ولا يتم تقديم أي معلومات stat.

وظيفة الوصول

دالة لمعالجة استدعاء Tcl_FSAccess. يجب تنفيذها لأي نظام ملفات معقول، لأن العديد من أوامر المستوى Tcl تعتمد عليها بشكل حاسم (على سبيل المثال، file exists، file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

تتحقق دالة Tcl_FSAccessProc مما إذا كان سيُسمح للعملية بالقراءة أو الكتابة أو اختبار وجود الملف (أو كائن نظام ملفات آخر) الذي اسمه موجود في pathPtr. إذا كان المسار يشير إلى رابط رمزي، فيجب اختبار أذونات الملف الذي يشير إليه هذا الرابط الرمزي.

في حالة النجاح (تم منح جميع الأذونات المطلوبة)، يتم إرجاع 0. في حالة حدوث خطأ (طلب بت واحد على الأقل في mode إذنًا مرفوضًا، أو حدث خطأ آخر)، يتم إرجاع -1.

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(

        int mode,
        int permissions);

تقوم Tcl_FSOpenFileChannelProc بفتح ملف محدد بواسطة pathPtr وإرجاع مقبض قناة يمكن استخدامه لإجراء عمليات الإدخال والإخراج على الملف. تم تصميم واجهة برمجة التطبيقات هذه على غرار وظيفة fopen في مكتبة الإدخال/الإخراج القياسية في Unix. بناء الجملة ومعنى جميع الوسائط مشابه لتلك المقدمة في أمر Tcl open عند فتح ملف، حيث الوسيط mode هو مزيج من علامات POSIX O_RDONLY و O_WRONLY وما إلى ذلك. إذا حدث خطأ عند فتح القناة، تقوم Tcl_FSOpenFileChannelProc بإرجاع NULL وتسجيل رمز خطأ POSIX يمكن استرداده باستخدام Tcl_GetErrno. بالإضافة إلى ذلك، إذا كان interp غير NULL، تقوم Tcl_FSOpenFileChannelProc بوضع رسالة خطأ في نتيجة interp بعد أي خطأ.

لا ينبغي تسجيل القناة التي تم إنشاؤها حديثًا في المفسر الذي توفره Tcl_FSOpenFileChannelProc؛ هذه المهمة هي لـ Tcl_FSOpenFileChannel (إذا لزم الأمر). إذا تم إغلاق إحدى القنوات القياسية، stdin أو stdout أو stderr، مسبقًا، فإن إجراء إنشاء القناة الجديدة يعينها أيضًا كقناة قياسية.

MATCHINDIRECTORYPROC

وظيفة لمعالجة استدعاء لـ Tcl_FSMatchInDirectory. إذا لم يتم تنفيذها، فلن تكون وظائف glob والنسخ المتكرر متاحة في نظام الملفات (وقد يؤثر ذلك على أوامر مثل encoding names التي تستخدم وظائف glob).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

يجب أن ترجع الوظيفة جميع الملفات أو الدلائل (أو كائنات نظام الملفات الأخرى) التي تطابق النمط المحدد وتفي بمواصفات types. يمكن استدعاء هذه الوظيفة بطريقتين. إذا كان pattern هو NULL، فإن pathPtr هو مواصفات كاملة لملف أو دليل يجب التحقق من وجوده ونوعه. بخلاف ذلك، فإن pathPtr هو دليل، ويجب على الوظيفة البحث عن ملفات أو دلائل ذات النوع الصحيح. في كلتا الحالتين، سيُفترض أن pathPtr غير NULL وغير فارغ. لا توجد حاليًا وثائق حول ما إذا كان pathPtr سيحتوي على فاصل ملف في النهاية، لذلك يجب أن يكون الكود مرنًا لكلا الحالتين.

قيمة الإرجاع هي نتيجة Tcl قياسية تشير إلى ما إذا كان هناك خطأ أثناء عملية المطابقة. توضع رسائل الخطأ في interp، إلا إذا كان interp هو NULL، وفي هذه الحالة لا يتم إنشاء رسالة خطأ. في نتيجة TCL_OK، يجب إضافة النتائج إلى القيمة المقدمة في resultPtr (والتي يمكن افتراض أنها قائمة Tcl غير مشتركة). يجب أن تتضمن التطابقات المضافة إلى resultPtr أي بادئة مسار مقدمة في pathPtr (مما يعني عادةً أنها ستكون مواصفات مسار مطلق). ملاحظة: إذا لم تكن هناك تطابقات، تحصل ببساطة على نتيجة فارغة؛ يتم الإشارة إلى الأخطاء فقط للمشاكل الفعلية في الملفات أو أنظمة الملفات التي قد تحدث أثناء عملية المطابقة.

يحتوي Tcl_GlobTypeData المقدم في المعلمة types على الحقول التالية:

typedef struct Tcl_GlobTypeData {
    /* يقابل bcdpfls كما في 'find -t' */
    int type;
    /* يقابل أذونات الملف */
    int perm;
    /* نوع mac مقبول */
    Tcl_Obj *macType;
    /* منشئ mac مقبول */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

هناك حالتان خاصتان مهمتان للتعامل معهما بشكل صحيح، وكلاهما عندما يكون types غير NULL. الحالتان هما عندما يكون types->types هو TCL_GLOB_TYPE_DIR أو TCL_GLOB_TYPE_MOUNT (وخاصة عندما تكون العلامات الأخرى خاطئة). في الحالة الأولى، يجب على الوظيفة سرد الدلائل الموجودة. تستخدم Tcl هذا لتنفيذ globbing المتكرر، لذا من المهم أن تنفذ أنظمة الملفات مطابقة الدلائل بشكل صحيح. في الحالة الثانية، مع TCL_GLOB_TYPE_MOUNT، يجب على نظام الملفات سرد نقاط التحميل الموجودة داخل pathPtr المعطى (وفي هذه الحالة، لا يلزم أن يكون pathPtr ضمن نفس نظام الملفات - على عكس جميع الحالات الأخرى التي يتم فيها استدعاء هذه الوظيفة). يعد الدعم لهذا الأمر بالغ الأهمية إذا كانت Tcl ترغب في الحصول على انتقالات سلسة بين أنظمة الملفات.

UTIMEPROC

وظيفة لمعالجة استدعاء لـ Tcl_FSUtime. إلزامي للسماح بتعيين (وليس قراءة) الأوقات باستخدام file mtime و file atime وتنفيذ file copy (open-r/open-w/fcopy).

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

يجب تغيير أوقات الوصول والتعديل للملف المحدد بواسطة pathPtr إلى القيم المعطاة في الهيكل tval.

يجب أن تكون قيمة الإرجاع 0 في حالة النجاح و -1 في حالة الخطأ، كما هو الحال مع نظام utime.

LINKPROC

وظيفة لمعالجة استدعاء لـ Tcl_FSLink. يجب تنفيذها فقط إذا كان نظام الملفات يدعم الارتباطات، ويمكن أن تكون NULL في حالات أخرى.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

إذا كان toPtr هو NULL، يُطلب من الوظيفة قراءة محتويات الارتباط. النتيجة هي Tcl_Obj يحدد محتويات الارتباط المحدد بواسطة linkNamePtr، أو NULL إذا تعذر قراءة الارتباط. النتيجة مملوكة للاتصال (ويجب زيادة عداد مرجعها قبل إرجاعها). يجب على أي متصل استدعاء Tcl_DecrRefCount على هذه النتيجة عند عدم استخدامه بعد الآن. إذا لم يكن toPtr هو NULL، يجب على الوظيفة محاولة إنشاء ارتباط. يجب أن تكون النتيجة في هذه الحالة هي toPtr إذا نجح الارتباط و NULL في حالات أخرى. في هذه الحالة، لا تكون النتيجة مملوكة للاتصال (أي لا توجد معالجة لعداد المراجع على كلا الجانبين). انظر وثائق Tcl_FSLink للتفسير الصحيح لعلامات linkAction.

LISTVOLUMESPROC

وظيفة لسرد أي مجلدات أنظمة ملفات تمت إضافتها بواسطة نظام الملفات هذا. يجب تنفيذها فقط إذا كان نظام الملفات يضيف مجلدات في بداية نظام الملفات، بحيث يمكن إرجاعها بواسطة file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

يجب أن تكون النتيجة قائمة بمجلدات تمت إضافتها بواسطة نظام الملفات هذا، أو NULL (أو قائمة فارغة) إذا لم يتم توفير أي مجلدات. تعتبر قيمة الإرجاع ملكًا لنظام الملفات (وليس نواة Tcl)، ولكن يجب أن يكون لها عداد مرجع لـ Tcl. ستستخدم Tcl محتويات القائمة ثم تقلل عداد المرجع هذا. هذا يسمح لأنظمة الملفات بالاختيار ما إذا كانت تريد حقًا الاحتفاظ "بقائمة عالمية" للمجلدات أم لا (إذا لم يكن الأمر كذلك، فإنها تنشئ القائمة في وقت الاستدعاء وتمررها إلى Tcl بعداد مرجع 1، ثم تنسى القائمة؛ إذا كان الأمر كذلك، فإنها تزيد عداد مرجع قائمتها العالمية وتمررها إلى Tcl التي ستنسخ المحتويات ثم تقلل عداد المرجع إلى حيث كان).

لذلك، تعتبر Tcl قيم الإرجاع لهذه الوظيفة غير قابلة للتغيير.

FILEATTRSTRINGSPROC

وظيفة لسرد جميع سلاسل السمات الصالحة لنظام الملفات هذا. إذا لم يتم تنفيذها، فلن يدعم نظام الملفات الأمر file attributes. يسمح هذا بمعلومات إضافية تعسفية يمكن إرفاقها بالملفات في نظام الملفات. إذا لم يتم تنفيذها، فلا يلزم تنفيذ طريقتي get و set.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

يمكن للوظيفة إرجاع مصفوفة من السلاسل أو، بدلاً من ذلك، وضع قائمة Tcl في objPtrRef. ستأخذ Tcl هذه القائمة وستقوم أولاً بزيادة عداد مرجعها قبل استخدامه. عند الانتهاء من استخدامها، ستقوم Tcl بتقليل عداد المرجع الخاص بها. لذلك، إذا كان يجب تحرير القائمة بواسطة Tcl عند اكتمالها، فيجب أن يكون لها عداد مرجع صفر، وإذا كان يجب عدم تحريرها، فيجب على نظام الملفات التأكد من أنه يرجع قيمة بعداد مرجع لا يقل عن واحد.

FILEATTRSGETPROC

وظيفة لمعالجة استدعاء لـ Tcl_FSFileAttrsGet، المستخدمة بواسطة file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

ترجع رمز إرجاع Tcl قياسي. يتم وضع قيمة السمة المستردة، والتي تتوافق مع العنصر ذي المؤشر index في القائمة التي تم إرجاعها بواسطة Tcl_FSFileAttrStringsProc، في objPtrRef (إذا تم إرجاع TCL_OK)، ومن المحتمل أن يكون لها عداد مرجع صفر. في كلتا الحالتين، يجب علينا تخزين هذه القيمة في مكان ما (على سبيل المثال، في نتيجة Tcl)، أو زيادة/تقليل عداد مرجعها لضمان تحريرها بشكل صحيح.

FILEATTRSSETPROC

وظيفة لمعالجة استدعاء لـ Tcl_FSFileAttrsSet، المستخدمة بواسطة file attributes. إذا كان نظام الملفات للقراءة فقط، فلا يلزم تنفيذ هذه الوظيفة.

typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);

يجب تعيين سمة القيمة للعنصر ذي المؤشر index في القائمة التي تم إرجاعها بواسطة Tcl_FSFileAttrStringsProc إلى objPtr المعطى.
