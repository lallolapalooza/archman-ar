الأحداث؛ يُستخدم عادةً للإشارة إلى معلومات خاصة تديرها مصادر الأحداث. يشير evPtr إلى الحدث التالي في قائمة الانتظار.

Tcl_DeleteEventSource يزيل مصدر أحداث. يجب أن تتطابق الوسائط setupProc و checkProc و clientData تمامًا مع تلك التي قدمتها Tcl_CreateEventSource لإزالة مصدر الأحداث. إذا لم يكن هناك مصدر مطابق، فإن Tcl_DeleteEventSource ليس لها تأثير.

إنشاء مُرسِل جديد

يتكون المرسل من جميع الإجراءات الموضحة في هذا الدليل، بالإضافة إلى Tcl_DoOneEvent و Tcl_Sleep، المتوفرة على جميع المنصات، و Tcl_CreateFileHandler و Tcl_DeleteFileHandler، وهي خاصة بـ Unix. معظم هذه الإجراءات عامة، حيث أنها متماثلة لجميع المرسلين. ومع ذلك، لا يوجد أي من الإجراءات التي تعتمد على المرسل: Tcl_InitNotifier، Tcl_AlertNotifier، Tcl_FinalizeNotifier، Tcl_SetTimer، Tcl_Sleep، Tcl_WaitForEvent، Tcl_CreateFileHandler، Tcl_DeleteFileHandler، و Tcl_ServiceModeHook. لدعم نظام تشغيل جديد أو دمج Tcl مع حلقة أحداث خاصة بتطبيق، يجب عليك كتابة إصدارات جديدة لهذه الإجراءات.

Tcl_InitNotifier تهيئ حالة المرسل وتعيد مؤشرًا لحالة المرسل. تستدعي Tcl هذه الوظيفة عند تهيئة بيئة Tcl. وبالمثل، Tcl_FinalizeNotifier تنهي المرسل، ويتم استدعاؤها بواسطة Tcl_Finalize عند إغلاق بيئة Tcl.

Tcl_WaitForEvent هو الإجراء الأدنى للمرسل؛ وهو مسؤول عن انتظار "حدث مثير للاهتمام" أو مرور وقت معين. قبل استدعاء Tcl_WaitForEvent، سيتم استدعاء كل إجراء مصدر أحداث أولاً. تعطي الوسيطة timePtr لـ Tcl_WaitForEvent الحد الأقصى لوقت الحظر لحدث، بناءً على استدعاءات Tcl_SetMaxBlockTime التي تمت بواسطة إجراءات الإعداد والمعلومات الأخرى (مثل، البت TCL_DONT_WAIT في flags).

من الناحية المثالية، يجب أن تنتظر Tcl_WaitForEvent حدثًا واحدًا فقط؛ يجب ألا تعالج الحدث بأي شكل من الأشكال. بعد ذلك، ستقوم إجراءات مصدر الأحداث بمعالجة الأحداث الخام وإنشاء Tcl_Events في قائمة انتظار الأحداث من خلال إجراءات checkProc الخاصة بها. ومع ذلك، في بعض الأنظمة (مثل Windows)، لا يمكن تحقيق ذلك؛ يمكن معالجة الأحداث في Tcl_WaitForEvent، بما في ذلك قائمة انتظار Tcl_Events والمزيد (على سبيل المثال، الاستدعاءات الخلفية للويدجت الأصلية). يجب أن تكون القيمة المرجعة لـ Tcl_WaitForEvent هي 0 أو 1 أو -1. على المنصات مثل Windows، حيث يتم معالجة الأحداث في Tcl_WaitForEvent، يشير الارتجاع 1 إلى أنه قد تكون هناك أحداث معلقة إضافية لم تتم معالجتها. هذه إشارة للمتصل بأنه يجب استدعاء Tcl_WaitForEvent مرة أخرى لمعالجة جميع الأحداث المعلقة. يشير الارتجاع 0 إلى أن استدعاء Tcl_WaitForEvent مرة أخرى لن يكون له تأثير: قد يكون نظامًا ينتظر فيه Tcl_WaitForEvent فقط دون معالجة أي أحداث، أو قد يكون Tcl_WaitForEvent متأكدًا من عدم وجود أحداث معلقة أخرى (على سبيل المثال، انتهى الوقت بالفعل). أخيرًا، يشير الارتجاع -1 إلى أن حلقة الأحداث لم تعد عاملة، ويجب على التطبيق التخلص من نفسه وإنهاء. في Windows، يحدث هذا عند تلقي رسالة WM_QUIT؛ في Unix، يحدث عندما ينتظر Tcl_WaitForEvent إلى الأبد نظرًا لعدم وجود مصادر أحداث نشطة ووقت الانتظار لا نهائي.

Tcl_AlertNotifier يُستخدم في التطبيقات متعددة الخيوط للسماح لأي خيط "بإيقاظ" المرسل لإخطاره بأحداث جديدة في قائمة الانتظار الخاصة به. يتطلب Tcl_AlertNotifier كمُدخل مقبض المرسل الذي أعاده Tcl_InitNotifier.

إذا كان المرسل سيُستخدم مع حلقة أحداث خارجية، فيجب عليه أيضًا دعم واجهة Tcl_SetTimer. يتم استدعاء Tcl_SetTimer بواسطة Tcl_SetMaxBlockTime عندما تم تقليل الحد الأقصى لوقت الحظر. يجب على Tcl_SetTimer ترتيب حلقة الأحداث الخارجية لاستدعاء Tcl_ServiceAll بعد الفترة المحددة، حتى لو لم يحدث أي حدث. هذه الواجهة ضرورية لأن Tcl_WaitForEvent لا يتم استدعاؤه عند وجود حلقة أحداث خارجية. إذا كان المرسل سيُستخدم فقط من Tcl_DoOneEvent، فلا يجب أن يقوم Tcl_SetTimer بأي شيء.

Tcl_ServiceModeHook يتم استدعاؤه بواسطة الجزء المستقل عن المرسل عندما يستدعي كود العميل Tcl_SetServiceMode. يتم توفير هذا الخطاف لدعم أنظمة التشغيل التي تتطلب معالجة خاصة للأحداث عندما يكون التطبيق في حلقة أحداث نمطية (على سبيل المثال، يستخدم مرسل Windows هذا الخطاف لإنشاء نافذة اتصال).

في أنظمة Unix، يحتاج مصدر أحداث الملفات أيضًا إلى دعم من المرسل. يتكون مصدر أحداث الملفات من الإجراءات Tcl_CreateFileHandler و Tcl_DeleteFileHandler، والتي تم وصفها في صفحة الدليل لـ Tcl_CreateFileHandler.

تم وصف واجهات Tcl_Sleep و Tcl_DoOneEvent في صفحات الدليل الخاصة بها.

أسهل طريقة لإنشاء مرسل جديد هي دراسة كود مرسل موجود، كما هو الحال في ملفات unix/tclUnixNotfy.c أو win/tclWinNotify.c من توزيع كود Tcl.

استبدال المرسل

يمكن أيضًا تثبيت مرسل مكتوب وفقًا للاتفاقيات المذكورة أعلاه في عملية قيد التشغيل بدلاً من المرسل القياسي. تُستخدم هذه الآلية للسماح باستخدام قابل تنفيذي واحد (مع المرسل القياسي) كبرنامج مستقل وإعادة استخدامه (كملحق لبرنامج آخر، مثل مكون إضافي لمتصفح الويب).

للقيام بذلك، يقوم الملحق بإجراء استدعاء إلى Tcl_SetNotifier، ويمرر مؤشرًا إلى هيكل Tcl_NotifierProcs. يحتوي الهيكل على التخطيط التالي:

typedef struct Tcl_NotifierProcs {
    Tcl_SetTimerProc *setTimerProc;
    Tcl_WaitForEventProc *waitForEventProc;
    Tcl_CreateFileHandlerProc *createFileHandlerProc;
    Tcl_DeleteFileHandlerProc *deleteFileHandlerProc;
    Tcl_InitNotifierProc *initNotifierProc;
    Tcl_FinalizeNotifierProc *finalizeNotifierProc;
    Tcl_AlertNotifierProc *alertNotifierProc;
    Tcl_ServiceModeHookProc *serviceModeHookProc;
} Tcl_NotifierProcs;

بعد استدعاء Tcl_SetNotifier، تحل المؤشرات المقدمة في هيكل Tcl_NotifierProcs محل أي مرسل تم تثبيته في العملية.

من غير العملي عادةً استبدال مرسل قيد التشغيل. عادةً، يجب استدعاء Tcl_SetNotifier قبل استدعاء Tcl_InitNotifier الأول.

حلقات الأحداث الخارجية

تم تصميم واجهات المرسل لدمج Tcl في التطبيقات التي تحتوي على حلقات أحداث خاصة بها. في هذه الحالة، لا تستدعي التطبيق Tcl_DoOneEvent إلا في حالات حلقات الأحداث المتكررة، مثل استدعاء أوامر Tcl مثل update أو vwait. يقضي معظم الوقت في حلقة الأحداث الخارجية للتطبيق. في هذه الحالة، يجب على المرسل ترتيب حلقة الأحداث الخارجية لاستدعاء Tcl مرة أخرى عند حدوث حدث في مصادر أحداث Tcl المختلفة. يجب أن ترتب هذه الاستدعاءات الخلفية وضع الأحداث المناسبة في قائمة انتظار أحداث Tcl.

نظرًا لأن حلقة الأحداث الخارجية لا تستدعي Tcl_DoOneEvent بانتظام، فإن المرسل هو الذي يجب أن يرتب استدعاء Tcl_ServiceEvent عند وجود أحداث معلقة في قائمة انتظار أحداث Tcl. أسهل طريقة للقيام بذلك هي استدعاء Tcl_ServiceAll في نهاية كل استدعاء خلفي لحلقة الأحداث الخارجية. هذا يضمن فحص جميع مصادر الأحداث، ومعالجة الأحداث المعلقة، ومعالجة معالجات الانتظار المعلقة قبل إعادة التحكم إلى التطبيق. بالإضافة إلى ذلك، يمكن لمصادر الأحداث التي تحتاج إلى فحص استدعاء Tcl_SetMaxBlockTime لإجبار حلقة الأحداث الخارجية على استدعاء Tcl_ServiceAll حتى لو لم تكن هناك أحداث متاحة في قائمة انتظار أحداث النظام.

كأثر جانبي لمعالجة الأحداث المكتشفة في حلقة الأحداث الخارجية الرئيسية، قد تستدعي Tcl Tcl_DoOneEvent لبدء حلقة أحداث متكررة في أوامر مثل vwait. ستستدعي Tcl_DoOneEvent حلقة الأحداث الخارجية، مما يؤدي إلى استدعاءات خلفية كما هو موضح في الفقرة السابقة، والتي ستؤدي إلى استدعاءات لـ Tcl_ServiceAll. ومع ذلك، في هذه الحالات، لا يُفضل معالجة الأحداث في Tcl_ServiceAll. معالجة الأحداث هناك غير ضرورية لأن التحكم سيعود فورًا إلى حلقة الأحداث الخارجية وبالتالي إلى Tcl_DoOneEvent، التي يمكنها معالجة الأحداث بنفسها. علاوة على ذلك، تم تصميم Tcl_DoOneEvent لمعالجة حدث واحد فقط، بينما تعالج Tcl_ServiceAll عادةً جميع الأحداث المعلقة. لمعالجة هذا الموقف، تقوم Tcl_DoOneEvent بتعيين علامة لـ Tcl_ServiceAll تجعلها تعود دون معالجة أي أحداث. تسمى هذه العلامة وضع الخدمة؛ تستعيدها Tcl_DoOneEvent إلى قيمتها السابقة قبل العودة. Tcl_DoOneEvent تعيد تعيين وضع الخدمة إلى قيمته السابقة قبل العودة.

في بعض الحالات، ومع ذلك، قد يكون من الضروري معالجة الأحداث حتى لو تم استدعاء Tcl_ServiceAll من Tcl_DoOneEvent. يحدث هذا عندما يتم استدعاء حلقة أحداث متكررة أخرى بواسطة معالج أحداث تم استدعاؤه بواسطة Tcl_DoOneEvent (مثل جزء من ويدجت أصلي). في هذه الحالة، قد لا تحصل Tcl_DoOneEvent على فرصة لمعالجة الأحداث، وبالتالي، يجب على Tcl_ServiceAll معالجة جميع الأحداث. يجب على أي حلقة أحداث متكررة تستدعي حلقة أحداث خارجية بدلاً من Tcl_DoOneEvent إعادة تعيين وضع الخدمة بحيث تتم معالجة جميع الأحداث في Tcl_ServiceAll. يتم تحقيق ذلك عن طريق استدعاء الإجراء Tcl_SetServiceMode. إذا تم تمرير TCL_SERVICE_NONE إلى Tcl_SetServiceMode، فستعود استدعاءات Tcl_ServiceAll فورًا دون معالجة أي أحداث. إذا تم تمرير TCL_SERVICE_ALL إلى Tcl_SetServiceMode، فستعمل استدعاءات Tcl_ServiceAll بشكل طبيعي. تقوم Tcl_SetServiceMode بإعادة القيمة السابقة لوضع الخدمة، والتي يجب استعادتها عند انتهاء حلقة الأحداث المتكررة. تقوم Tcl_GetServiceMode بإعادة القيمة الحالية لوضع الخدمة.

NAME

Tcl_GetCurrentThread - retrieve the current thread's identifier

SYNOPSIS

#include <tcl.h>

Tcl_ThreadId
Tcl_GetCurrentThread(void);

ARGUMENTS

None.

DESCRIPTION

The Tcl_GetCurrentThread function returns the identifier for the current thread. The identifier is of type Tcl_ThreadId. If the current thread is not managed by Tcl (e.g. it is the main thread which is not explicitly created with Tcl_CreateThread), then this function will return NULL.

NOTIFIER BASICS

The Tcl notifier mechanism is used to integrate external events into the Tcl event loop. The notifier is a set of functions that the Tcl core calls to process events. The notifier is responsible for monitoring various event sources and dispatching events to the Tcl interpreter when they occur.

CREATING A NEW EVENT SOURCE

To create a new event source, you need to define a structure that contains the event source's information, such as its type, file descriptor (if applicable), and a callback function to be called when the event occurs. You then register this event source with the Tcl notifier using Tcl_CreateEventSource.

CREATING A NEW NOTIFIER

A new notifier can be created by implementing the notifier functions and registering them with the Tcl core using Tcl_SetNotifier. The notifier functions include:

  • Tcl_WaitEvent: Waits for an event to occur.
  • Tcl_AwakeEvent: Wakes up the notifier thread.
  • Tcl_HandleEvent: Handles a dispatched event.

REPLACING THE NOTIFIER

You can replace the default Tcl notifier with a custom notifier by calling Tcl_SetNotifier with a pointer to your notifier structure. This allows you to customize how Tcl handles events.

EXTERNAL EVENT LOOPS

Tcl can be integrated into external event loops. You can use Tcl_InitTclThread to initialize Tcl for multithreading and Tcl_CreateThread to create new Tcl threads. The Tcl event loop can then be driven by the external event loop.
