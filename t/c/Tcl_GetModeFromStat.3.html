There are several reasons for calling the Tcl_FS API functions (e.g. Tcl_FSAccess and Tcl_FSStat) rather than calling system level functions like access and stat directly. First, they will work cross-platform, so an extension which calls them should work unmodified on Unix and Windows. Second, the Windows implementation of some of these functions fixes some bugs in the system level calls. Third, these function calls deal with any “Utf to platform-native” path conversions which may be required (and may cache the results of such conversions for greater efficiency on subsequent calls). Fourth, and perhaps most importantly, all of these functions are “virtual filesystem aware”. Any virtual filesystem (VFS for short) which has been registered (through Tcl_FSRegister) may reroute file access to alternative media or access methods. This means that all of these functions (and therefore the corresponding file, glob, pwd, cd, open, etc. Tcl commands) may be operate on “files” which are not native files in the native filesystem. This also means that any Tcl extension which accesses the filesystem (FS for short) through this API is automatically “virtual filesystem aware”. Of course, if an extension accesses the native filesystem directly (through platform-specific APIs, for example), then Tcl cannot intercept such calls.

\n

If appropriate VFSes have been registered, the “files” may, to give two examples, be remote (e.g. situated on a remote ftp server) or archived (e.g. lying inside a .zip archive). Such registered filesystems provide a lookup table of functions to implement all or some of the functionality listed here. Finally, the Tcl_FSStat and Tcl_FSLstat calls abstract away from what the “struct stat” buffer is actually declared to be, allowing the same code to be used both on systems with and systems without support for files larger than 2GB in size.

\n

The Tcl_FS API is Tcl_Obj-ified and may cache internal representations and other path-related strings (e.g. the current working directory). One side-effect of this is that one must not pass in values with a reference count of zero to any of these functions. If such calls were handled, they might result in memory leaks (under some circumstances, the filesystem code may wish to retain a reference to the passed in value, and so one must not assume that after any of these calls return, the value still has a reference count of zero - it may have been incremented) or in a direct segmentation fault (or other memory access error) due to the value being freed part way through the complex value manipulation required to ensure that the path is fully normalized and absolute for filesystem determination. The practical lesson to learn from this is that

\n
Tcl_Obj *path = Tcl_NewStringObj(...);\nTcl_FSWhatever(path);\nTcl_DecrRefCount(path);
\nis wrong, and may cause memory errors. The path must have its reference count incremented before passing it in, or decrementing it. For this reason, values with a reference count of zero are considered not to be valid filesystem paths and calling any Tcl_FS API function with such a value will result in no action being taken.

\n

FS API FUNCTIONS

\n

Tcl_FSCopyFile attempts to copy the file given by srcPathPtr to the path name given by destPathPtr. If the two paths given lie in the same filesystem (according to Tcl_FSGetFileSystemForPath) then that filesystem's “copy file” function is called (if it is non-NULL). Otherwise the function returns -1 and sets the errno global C variable to the “EXDEV” POSIX error code (which signifies a “cross-domain link”).

\n

Tcl_FSCopyDirectory attempts to copy the directory given by srcPathPtr to the path name given by destPathPtr. If the two paths given lie in the same filesystem (according to Tcl_FSGetFileSystemForPath) then that filesystem's “copy file” function is called (if it is non-NULL). Otherwise the function returns -1 and sets the errno global C variable to the “EXDEV” POSIX error code (which signifies a “cross-domain link”).

\n

Tcl_FSCreateDirectory attempts to create the directory given by pathPtr by calling the owning filesystem's “create directory” function.

\n

Tcl_FSDeleteFile attempts to delete the file given by pathPtr by calling the owning filesystem's “delete file” function.

\n

Tcl_FSRemoveDirectory attempts to remove the directory given by pathPtr by calling the owning filesystem's “remove directory” function.

\n

Tcl_FSRenameFile attempts to rename the file or directory given by srcPathPtr to the path name given by destPathPtr. If the two paths given lie in the same filesystem (according to Tcl_FSGetFileSystemForPath) then that filesystem's “rename file” function is called (if it is non-NULL). Otherwise the function returns -1 and sets the errno global C variable to the “EXDEV” POSIX error code (which signifies a “cross-domain link”).

\n

Tcl_FSListVolumes calls each filesystem which has a non-NULL “list volumes” function and asks them to return their list of root volumes. It accumulates the return values in a list which is returned to the caller (with a reference count of 0).

\n

Tcl_FSEvalFileEx reads the file given by pathPtr using the encoding identified by encodingName and evaluates its contents as a Tcl script. It returns the same information as Tcl_EvalObjEx. If encodingName is NULL, the system encoding is used for reading the file contents. If the file could not be read then a Tcl error is returned to describe why the file could not be read. The eofchar for files is “\\x1A” (^Z) for all platforms. If you require a “^Z” in code for string comparison, you can use “\\x1A”, which will be safely substituted by the Tcl interpreter into “^Z”. واجهة برمجة تطبيقات Tcl_FSForPath

Tcl_FSGetFileSystemForPath هي الواجهة الرئيسية لتحويل كائن مسار Tcl (Tcl_Obj) إلى مسار النظام الأصلي. يجب على المطورين استخدام هذه الوظيفة عند الحاجة إلى التعامل مع مسارات الملفات في شكلها الأصلي. يتم إرجاع مؤشر إلى بنية Tcl_Filesystem التي تتعرف على المسار. إذا لم يتم التعرف على المسار من قبل أي نظام ملفات، فسيتم إرجاع NULL.

Tcl_FSGetNormalizedPath تحول المسار المعطى إلى شكل طبيعي وموحد. هذا يعني إزالة أي عناصر غير ضرورية مثل "." أو "..". يجب على المستخدمين استدعاء ckfree لتحرير الذاكرة التي تم تخصيصها للمسار المُرجع. يفضل استخدام هذه الوظيفة في معظم الحالات.

Tcl_FSGetNativePath تحول المسار إلى تمثيل النظام الأصلي. مثل Tcl_FSGetNormalizedPath، يجب على المستخدمين تحرير الذاكرة باستخدام ckfree. تعتبر Tcl_FSGetNormalizedPath و Tcl_FSGetNativePath بشكل عام وظائف أفضل للاستخدام في معظم الأغراض.

Tcl_FSNewNativePath تؤدي عملية عكسية للتحويلات المعتادة من كائن إلى مسار إلى تمثيل أصلي. إذا قام رمز ما باسترداد مسار بالشكل الأصلي (من، على سبيل المثال، readlink أو مربع حوار أصلي)، وتم استخدام هذا المسار على مستوى Tcl، فإن استدعاء هذه الوظيفة هو طريقة فعالة لإنشاء نوع قيمة المسار المناسب.

القيمة الناتجة هي قيمة "مسار" خالصة، والتي ستحصل فقط على تمثيل سلسلة UTF-8 إذا كان ذلك مطلوبًا من قبل بعض رموز Tcl.

Tcl_FSGetNativePath مخصصة للاستخدام من قبل أنظمة الملفات الأصلية لـ Win/Unix، حتى يتمكنوا من استرداد التمثيل الأصلي (char* أو TCHAR*) للمسار بسهولة. هذه الوظيفة هي غلاف اختصاري حول Tcl_FSGetInternalRep. قد يكون من المرغوب فيه في المستقبل وجود تمثيلات أصلية غير قائمة على السلاسل (على سبيل المثال، في macOS، قد يكون التمثيل الذي يستخدم بنية FSRef لـ fileSpec أكثر كفاءة). في Windows، ستسمح التمثيل الكامل لـ Unicode بمسارات بطول غير محدود. حاليًا، التمثيل هو ببساطة سلسلة حرفية قد تحتوي إما على المسار النسبي أو مسار كامل ومطلق وموحد في الترميز الأصلي (تحدد الظروف المعقدة أيًا من هذين سيتم توفيره، لذلك لا يمكن الاعتماد على أي منهما، إلا إذا كان المسار معروفًا بأنه مطلق). إذا كنت بحاجة إلى مسار أصلي يجب أن يكون مطلقًا، فيجب عليك طلب النسخة الأصلية من مسار موحد. إذا كان هناك سبب يتطلب إصدارًا غير مطلق وغير موحد من المسار، فيجب إنشاؤه بشكل منفصل (على سبيل المثال، باستخدام Tcl_FSGetTranslatedPath).

يتم تخزين التمثيل الأصلي في ذاكرة التخزين المؤقت بحيث لا تتطلب الاستدعاءات المتكررة لهذه الوظيفة تحويلات إضافية. قيمة الإرجاع مملوكة من قبل Tcl ولها عمر مكافئ لعمر pathPtr المُمرر (ما لم يكن مسارًا نسبيًا، وفي هذه الحالة يمكن تحرير التمثيل الأصلي في أي وقت يتغير فيه المجلد الحالي).

Tcl_FSFileSystemInfo تُرجع قائمة من عنصرين. العنصر الأول هو اسم نظام الملفات (مثل "native" أو "vfs" أو "zip" أو "prowrap"، ربما)، والثاني هو النوع المحدد للمسار المعطى داخل نظام الملفات هذا (وهو يعتمد على نظام الملفات). قد يكون العنصر الثاني فارغًا إذا لم يوفر نظام الملفات تصنيفًا إضافيًا للملفات.

يتم إرجاع قيمة قائمة صالحة، ما لم يكن قيمة المسار غير معروفة، عندها سيتم إرجاع NULL.

إذا لم يقبل أي نظام ملفات المسار، فسيتم إرجاع NULL.

واجهة برمجة تطبيقات نظام الملفات الافتراضي

يوفر نظام الملفات بنية Tcl_Filesystem التي تحتوي على مؤشرات إلى وظائف تنفذ العمليات المختلفة على نظام الملفات؛ يتم استدعاء هذه العمليات حسب الحاجة من قبل الطبقة العامة، والتي تحدث بشكل عام من خلال الوظائف المذكورة أعلاه.

يتم التعامل مع هياكل Tcl_Filesystem باستخدام الطرق التالية.

Tcl_FSRegister تأخذ مؤشرًا إلى بنية نظام الملفات وقطعة اختيارية من البيانات لربطها بنظام الملفات هذا. عند استدعاء هذه الوظيفة، سيقوم Tcl بربط نظام الملفات بقائمة أنظمة الملفات المعروفة، وسيصبح فعالًا بالكامل على الفور. لا يتحقق Tcl مما إذا كان نفس نظام الملفات مسجلاً عدة مرات (وهو ليس شيئًا جيدًا للقيام به بشكل عام). سيتم إرجاع TCL_OK.

Tcl_FSUnregister يزيل بنية نظام الملفات المعطاة من قائمة أنظمة الملفات المعروفة، إذا كانت معروفة، ويُرجع TCL_OK. إذا لم يكن نظام الملفات مسجلاً حاليًا، فسيتم إرجاع TCL_ERROR.

Tcl_FSData ستُرجع بيانات العميل (clientData) المرتبطة بنظام الملفات المعطى، إذا كان نظام الملفات هذا مسجلاً. وإلا، فسوف تُرجع NULL.

Tcl_FSMountsChanged تُستخدم لإعلام نواة Tcl بأن مجموعة نقاط التحميل لنظام الملفات المعطى (المسجل بالفعل) قد تغيرت، وأن تمثيلات الملفات المخزنة في الذاكرة المؤقتة قد لا تكون صحيحة بعد الآن.
