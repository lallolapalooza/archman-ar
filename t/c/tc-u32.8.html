tc-u32(8)

الحزمة: iproute2

التراخيص: GPL-2.0-or-later

أرقام صغيرة أو قيمة واحدة بحجم 32 بت تجمع بين كليهما.
divisor u32_value
حدد قيمة باقي القسمة (modulo). تُستخدم عند إنشاء جداول التجزئة لتحديد حجمها أو عند الإعلان عن sample لحساب مفاتيح جدول التجزئة منها. يجب أن يكون قوة للعدد 2 مع ألا يتجاوز الأس ثمانية.
order u32_value
قيمة لترتيب المرشحات تصاعديًا. يتعارض مع handle الذي يقوم بنفس الغرض.
sample SELECTOR
تُستخدم مع ht لتحديد المستودع (bucket) الذي سيتم إضافة هذا المرشح إليه. هذا يسمح بتجنب معرفة كيفية حساب النواة (kernel) للتجزئات بالضبط. القيمة الافتراضية لـ divisor الإضافي هي 256، لذا يجب تقديمها لجداول التجزئة ذات الأحجام المختلفة.
link HANDLE
تفويض حزم المطابقة للمرشحات في جدول تجزئة. يُستخدم HANDLE لتحديد جدول التجزئة فقط، لذا يمكن تقديم htid فقط، ويجب حذف hash و nodeid. افتراضيًا، سيتم استخدام المستودع رقم 0 ويمكن تجاوز ذلك باستخدام الخيار hashkey.
indev ifname
الترشيح بناءً على الواجهة الواردة للحزمة. يعمل بشكل طبيعي فقط للحركة المرورية المعاد توجيهها.
skip_sw
عدم معالجة المرشح بواسطة البرمجيات. إذا لم يكن للأجهزة دعم تفريغ (offload) لهذا المرشح، أو لم يتم تمكين تفريغ TC للواجهة، فسيفشل العمل.
skip_hw
عدم معالجة المرشح بواسطة الأجهزة.
help
طباعة نص مساعدة موجز حول الخيارات الممكنة.

المحددات (SELECTORS)

في الأساس، المحدد الوحيد الحقيقي هو u32 . كل المحددات الأخرى توفر ببساطة بناء جملة عالي المستوى ويتم ترجمتها داخليًا إلى u32 .

u32 VAL_MASK_32
u16 VAL_MASK_16
u8 VAL_MASK_8
مطابقة بيانات الحزمة بقيمة معينة. يحدد اسم المحدد طول العينة المراد استخراجها (32 بت لـ u32، 16 بت لـ u16، و 8 بت لـ u8). قبل المقارنة، يتم إجراء عملية AND منطقية ثنائية للعينة مع القناع المحدد. بهذه الطريقة، يمكن مسح البتات غير المهمة قبل المقارنة. يتم تحديد موضع العينة بواسطة الإزاحة (offset) المحددة في AT.
ip IP
ip6 IP6
افترض أن الحزمة تبدأ برأس IPv4 (ip) أو IPv6 (ip6). يسمح IP/IP6 بعد ذلك بمطابقة حقول رأس مختلفة:
src ADDR
dst ADDR
مقارنة حقول المصدر أو الوجهة مقابل قيمة ADDR. الكلمات المحجوزة default و any و all تطابق فعليًا أي عنوان. بخلاف ذلك، يُتوقع عنوان IP للبروتوكول المحدد، مع لاحقة اختيارية لطول بادئة لمطابقة شبكات فرعية كاملة. في حالة IPv4، يمكن أيضًا تقديم قناع شبكة.
dsfield VAL_MASK_8
IPv4 فقط. مطابقة حقل DSCP/ECN لرأس الحزمة. المرادفات لذلك هي tos و precedence.
ihl VAL_MASK_8
IPv4 فقط. مطابقة حقل طول رأس الإنترنت (Internet Header Length). لاحظ أن وحدة القيمة هي 32 بت، لذلك لمطابقة حزمة بطول رأس 24 بايت، يجب أن تكون u8_value 6.
protocol VAL_MASK_8
مطابقة قيمة حقل البروتوكول (IPv4) أو الرأس التالي (IPv6)، على سبيل المثال 6 لـ TCP.
icmp_type VAL_MASK_8
icmp_code VAL_MASK_8
افترض أن بروتوكول الرأس التالي هو icmp أو ipv6-icmp وقم بمطابقة قيم حقول النوع (Type) أو الرمز (Code). هذا خطير، لأن الرمز يفترض الحد الأدنى لحجم الرأس لـ IPv4 وعدم وجود رؤوس إضافية لـ IPv6.
sport VAL_MASK_16
dport VAL_MASK_16
مطابقة منافذ المصدر أو الوجهة في الطبقة الرابعة. هذا خطير أيضًا، لأنه يفترض وجود بروتوكول طبقة رابعة مناسب (يحتوي على حقول منفذ المصدر والوجهة مباشرة في بداية الرأس وحجمها 16 بت). كما يُفترض الحد الأدنى لحجم الرأس لـ IPv4 وعدم وجود رؤوس إضافية لـ IPv6.
nofrag
firstfrag
df
mf
IPv4 فقط، تحقق من علامات معينة وقيم إزاحة الأجزاء (fragment offset). مطابقة إذا لم تكن الحزمة جزءًا (nofrag)، أو كانت الجزء الأول من حزمة مجزأة (firstfrag)، أو إذا كانت علامات عدم التجزيء (df) أو المزيد من الأجزاء (mf) مضبوطة.
priority VAL_MASK_8
IPv6 فقط. مطابقة حقل فئة حركة المرور (Traffic Class) في الرأس، والذي له نفس الغرض والدلالات لحقل ToS في IPv4 منذ RFC 3168: الست بتات العليا هي DSCP، والبتات الدنيا هي ECN.
flowlabel VAL_MASK_32
IPv6 فقط. مطابقة قيمة حقل تسمية التدفق (Flow Label). لاحظ أن تسمية التدفق نفسها هي 20 بايت فقط، وهي البتات الأقل أهمية هنا. البايتات الـ 12 العليا المتبقية تطابق حقلي الإصدار وفئة حركة المرور.
tcp TCPUDP
udp TCPUDP
مطابقة حقول الرأس التالي للبروتوكول TCP أو UDP. القيم الممكنة لـ TCPDUP هي:
src VAL_MASK_16
المطابقة على قيمة حقل منفذ المصدر.
dst VALMASK_16
المطابقة على قيمة حقل منفذ الوجهة.
icmp ICMP
مطابقة حقول الرأس التالي للبروتوكول ICMP. القيم الممكنة لـ ICMP هي:
type VAL_MASK_8
المطابقة على حقل نوع ICMP (ICMP Type).
code VAL_MASK_8
المطابقة على حقل رمز ICMP (ICMP Code).
mark VAL_MASK_32
المطابقة على قيمة علامة تصفية الشبكة (netfilter fwmark).
ether ETHER
المطابقة على حقول رأس الإيثرنت. القيم الممكنة لـ ETHER هي:
src ether_address AT
dst ether_address AT
المطابقة على عنوان الإيثرنت للمصدر أو الوجهة. هذا خطير: يفترض وجود رأس إيثرنت في بداية الحزمة. هذا قد يؤدي إلى نتائج غير متوقعة إذا تم استخدامه مع واجهات الطبقة الثالثة مثل tun أو ppp.

أمثلة (EXAMPLES)

tc filter add dev eth0 parent 999:0 prio 99 protocol ip u32 \
        match ip src 192.168.8.0/24 classid 1:1

هذا يضيف مرشحًا إلى قائمة انتظار (qdisc) معرفة بـ 999:0. أولويته هي 99، مما يؤثر على الترتيب الذي يتم به استشارة المرشحات المتعددة المرفقة بنفس parent (الأقل هو الأسبق). يتعامل المرشح مع حزم من نوع protocol هو ip، و match إذا كان عنوان المصدر لرأس IP ضمن الشبكة الفرعية 192.168.8.0/24. الحزم المطابقة تصنف إلى الفئة 1.1. قد تكون نتيجة هذا الأمر مفاجئة للوهلة الأولى:

filter parent 1: protocol ip pref 99 u32
filter parent 1: protocol ip pref 99 u32 \
        fh 800: ht divisor 1
filter parent 1: protocol ip pref 99 u32 \
        fh 800::800 order 2048 key ht 800 bkt 0 flowid 1:1 \
        match c0a80800/ffffff00 at 12

لذلك، يتم تعيين parent 1: لمرشح u32 جديد، والذي يحتوي على جدول تجزئة بحجم 1 (كما يشير divisor). معرف الجدول هو 800. يوضح السطر الثالث المرشح الفعلي الذي تم إضافته أعلاه: إنه موجود في الجدول 800 والمستودع 0، ويصنف الحزم إلى معرف الفئة 1:1، ويطابق البايتات الثلاثة العليا للقيمة المكونة من أربعة بايتات عند الإزاحة 12 لتكون 0xc0a808، وهي 192، 168 و 8.

الآن لشيء أكثر تعقيدًا، وهو إنشاء جدول تجزئة مخصص:

tc filter add dev eth0 prio 99 handle 1: u32 divisor 256

ينشئ هذا جدولًا بحجم 256 بمعرف 1: في الأولوية 99. التأثير كما يلي:

filter parent 1: protocol all pref 99 u32
filter parent 1: protocol all pref 99 u32 fh 1: ht divisor 256
filter parent 1: protocol all pref 99 u32 fh 800: ht divisor 1

لذلك، جنبًا إلى جنب مع جدول التجزئة المطلوب (المعرف 1:)، قامت النواة بإنشاء جدولها الخاص بحجم 1 لاحتواء المرشحات الأخرى بنفس الأولوية.

الخطوة التالية هي إنشاء مرشح يرتبط بجدول التجزئة الذي تم إنشاؤه:

tc filter add dev eth0 parent 1: prio 1 u32 \
        link 1: hashkey mask 0x0000ff00 at 12 \
        match ip src 192.168.0.0/16

يُعطى المرشح أولوية أقل من جدول التجزئة نفسه، لذا فإن u32 يستشيره قبل اجتياز جدول التجزئة يدويًا. تحدد الخيارات link و hashkey الجدول والمستودع المراد إعادة التوجيه إليهما. في هذه الحالة، يجب بناء مفتاح التجزئة من البايت الثاني عند الإزاحة 12، والذي يتوافق

الوصف

يستجيب للبايت الثالث لحزمة IP في حقل عنوان المصدر. جنبًا إلى جنب مع البيان match، يقوم هذا بشكل فعال بتعيين جميع شبكات الفئة C تحت 192.168.0.0/16 إلى مجموعات مختلفة من جدول التجزئة.

يمكن إنشاء مرشحات لشبكات فرعية معينة على النحو التالي:

tc filter add dev eth0 parent 1: prio 99 u32 \
        ht 1: sample u32 0x00000800 0x0000ff00 at 12 \
        match ip src 192.168.8.0/24 classid 1:1

يتم تعريف المجموعة باستخدام الخيار sample: في هذه الحالة، يجب أن يكون البايت الثاني في الإزاحة 12 هو 0x08 بالضبط. في هذه الحالة، يكون معرف المجموعة الناتج هو 8 بشكل واضح، ولكن بمجرد أن يختار sample كمية من البيانات قد تتجاوز divisor، سيكون على المرء أن يعرف خوارزمية النواة الداخلية لاستنتاج المجموعة الوجهة. البيان match لهذا المرشح غير ضروري في هذه الحالة، حيث أن الانتروبيا لمفتاح التجزئة لا تتجاوز حجم الجدول وبالتالي لا يمكن أن تحدث تصادمات. بخلاف ذلك، من الضروري منع مطابقة الحزم غير المرغوب فيها.

تعد مطابقة حقول الطبقة العليا مشكلة نظرًا لأن طول رأس IPv4 متغير وتدعم IPv6 رؤوس الامتداد التي تؤثر على إزاحة رأس الطبقة العليا. للتغلب على هذا، هناك إمكانية لتحديد nexthdr+ عند إعطاء إزاحة، ولتسهيل الأمور، هناك مطابقات tcp و udp التي تستخدم nexthdr+ ضمنياً. يجب حساب هذه الإزاحة مسبقًا، والطريقة الوحيدة لتحقيق ذلك هي القيام بها في مرشح منفصل يقوم بعد ذلك بالربط بالمرشح الذي يريد استخدامه. إليك مثال على القيام بذلك:

tc filter add dev eth0 parent 1:0 protocol ip handle 1: \
        u32 divisor 1
tc filter add dev eth0 parent 1:0 protocol ip \
        u32 ht 1: \
        match tcp src 22 FFFF \
        classid 1:2
tc filter add dev eth0 parent 1:0 protocol ip \
        u32 ht 800: \
        match ip protocol 6 FF \
        match u16 0 1fff at 6 \
        offset at 0 mask 0f00 shift 6 \
        link 1:

هذا ما يتم فعله: في الاستدعاء الأول، يتم إنشاء جدول تجزئة بحجم عنصر واحد بحيث يكون هناك مكان للاحتفاظ بالمرشح المرتبط ومعرف معروف (1:) للإشارة إليه. يقوم الاستدعاء الثاني بعد ذلك بإضافة المرشح الفعلي، والذي يدفع الحزم ذات منفذ مصدر TCP 22 إلى الفئة 1:2. باستخدام ht، يتم نقله إلى جدول التجزئة الذي تم إنشاؤه بواسطة الاستدعاء الأول. يقوم الاستدعاء الثالث بعد ذلك بالسحر الفعلي: يطابق حزم IPv4 ببروتوكول الطبقة التالية 6 (TCP)، فقط إذا كانت هي الجزء الأول (عادةً ما يقوم TCP بتعيين بت DF، ولكن إذا لم يفعل ذلك وتم تقسيم الحزمة، فإن الجزء الأول فقط يحتوي على رأس TCP)، ثم يقوم بتعيين الإزاحة بناءً على حقل IHL لرأس IP (إزاحة اليمين بمقدار 6 تلغي إزاحة الحقل وفي نفس الوقت تحول القيمة إلى وحدة البايت). أخيرًا، باستخدام link، يتم الإشارة إلى جدول التجزئة من الاستدعاء الأول الذي يحتوي على المرشح من الاستدعاء الثاني.
