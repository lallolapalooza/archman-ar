Si es exitosa, actualiza los valores atime y mtime del archivo dado. Tcl_FSFileAttrsGet implementa el acceso lectura para el subcomando file attributes de la subcomando file. La función adecuada para el sistema de archivos al que pertenece pathPtr será llamada. Tcl tomará ese list y primero incrementará su cuenta de referencia antes de usarlo. Al finalizar su uso, Tcl decrementará su cuenta de referencia. Por lo tanto, si el list debe ser destruido por Tcl cuando se complete, debe tener un cuenta de referencia de cero, y si no debe ser destruido, el sistema de archivos debe asegurar que mantenga una cuenta de referencia al valor. Tcl_FSAccess verifica si el proceso sería permitido a leer, escribir o probar la existencia del archivo (o objeto de sistema de archivos) cuyo nombre es pathname. Si pathname es un enlace simbólico en Unix, se testan los permisos del archivo al que se refiere este enlace simbólico. En caso de éxito (todas las permisos solicitadas), se devuelve 0. En caso de error (al menos un bit en el modo solicitado es denegado, o se produjo otro error), se devuelve -1. Tcl_FSStat completa la estructura Tcl_StatBuf con información sobre el archivo especificado. No se necesitan derechos de acceso al archivo para obtener esta información, pero se necesitan derechos de búsqueda en todos los directorios mencionados en el camino hacia el archivo. La estructura Tcl_StatBuf incluye información sobre el dispositivo, el inodo (siempre 0 en Windows), el modo de privilegio, el número de enlaces (siempre 1 en Windows), el ID del usuario (siempre 0 en Windows), el ID del grupo (siempre 0 en Windows), rdev (igual que el dispositivo en Windows), el tamaño, el tiempo de acceso último, el tiempo de modificación y el tiempo de cambio de metadatos. Consulta PORTABLE STAT RESULT API para una descripción de cómo escribir código portable para allocar y acceder a la estructura Tcl_StatBuf. Si path existe, Tcl_FSStat devuelve 0 y la estructura statPtr está llena de datos. De lo contrario, devuelve -1 y no se proporcionan datos de estadísticas. Tcl_FSOpenFileChannel abre un archivo especificado por pathPtr y devuelve un handle de canal que puede usarse para realizar entrada y salida en el archivo. Esta API es modelada después de la función fopen de la librería de entrada/salida estándar de Unix. El sintaxis y significado de los argumentos son similares a los de la comanda open de Tcl cuando se abre un archivo. Si ocurre un error al abrir el canal, Tcl_FSOpenFileChannel devuelve NULL y registra un código de error POSIX que puede ser recuperado con Tcl_GetErrno. Además, si interp no es NULL, Tcl_FSOpenFileChannel deja un mensaje de error en interp's result después de cualquier error. El canal creado se encuentra registrado en el interpretador proporcionado; para registrarlo, use Tcl_RegisterChannel. Si uno de los canales estándar, stdin, stdout o stderr estaba previamente cerrado, la acción de crear el nuevo canal también lo asigna como sustituto del canal estándar. Tcl_FSGetCwd reemplaza la versión del biblioteca de getcwd. Devuelve el directorio de trabajo actual del biblioteca Tcl. Esto puede ser diferente al directorio de trabajo nativo, que se cambia cuando el directorio de trabajo actual no está en el sistema de archivos nativo. El resultado es un puntero a un Tcl_Obj especificando el directorio actual, o NULL si no se puede determinar el directorio. Si se devuelve NULL, se deja un mensaje de error en el resultado de interp. El resultado ya tiene su cuenta de referencia incrementada para el llamante. Cuando no se necesita más, se debe decrementar la cuenta de referencia. Esto es necesario para la seguridad multithread, para permitir múltiples hilos acceder a esta y funciones relacionadas, mientras garantizan que los resultados siempre sean válidos. Tcl_FSChdir reemplaza la versión del biblioteca de chdir. El camino es normalizado y luego pasa a la unidad de sistema de archivos que lo claime. Si esa unidad no implementa esta función, Tcl se retrae a una combinación de stat y access para verificar si la carpeta existe y tiene permisos adecuados. Para los resultados, consulta la documentación de chdir. Si es exitosa, se mantiene un registro de la ruta exitosa en cwdPathPtr para llamadas futuras a Tcl_FSGetCwd. Tcl_FSPathSeparator devuelve el carácter de separador para el elemento más específico de la ruta especificada por pathPtr (es decir, el último parte de la ruta). El separador se devuelve como un Tcl_Obj conteniendo una cadena de longitud 1. Si la ruta es inválida, se devuelve NULL. Tcl_FSJoinPath toma el objeto Tcl especificado, que debe ser un lista válida (que permite tener un conteo de referencia nulo), y devuelve el valor de ruta considerando los primeros elements elementos como segmentos válidos de ruta (cada segmento puede ser un ruta completa, una ruta parcial o simplemente un nombre de directorio o archivo). Si algún segmento de ruta es realmente una ruta absoluta, todos los segmentos anteriores son ignorados. Si elements es menor que 0, se utiliza el entero completo. Puede ocurrir que el valor devuelto sea realmente un elemento del lista dada, por lo que el llamante debe ser cuidadoso al incrementar la cuenta de referencia del valor antes de liberar el lista. El valor devuelto, típicamente con una cuenta de referencia de 0 (pero podría compartirse en ciertas condiciones), contiene la ruta unida. El llamante debe agregar una cuenta de referencia al valor antes de usarlo. En particular, el valor devuelto podría ser un elemento de la lista dada, por lo que liberar el lista podría liberar el valor prematuramente si no se ha tomado una cuenta de referencia. Si el número de elementos es cero, el valor devuelto será un objeto Tcl con valor vacío (""). Tcl_FSSplitPath toma el objeto Tcl especificado, que debe ser una ruta válida, y devuelve un valor de lista conteniendo cada segmento de esa ruta como elemento. Devuelve un valor de lista con una cuenta de referencia de 0. Si el lenPtr es no NULL, el variable que apunta a él será actualizado para contener el número de elementos en el valor devuelto. Tcl_FSEqualPaths prueba si las dos rutas dadas representan el mismo objeto de sistema de archivos. Devuelve 1 si las rutas son iguales, 0 si son diferentes. Si alguna de las rutas es NULL, se devuelve 0 siempre. Tcl_FSGetNormalizedPath intenta extraer una representación normalizada única de la ruta dada, que puede usarse como identificador único para el archivo. Devuelve la ruta normalizada, propiedad de Tcl, o NULL si la ruta era inválida o no pudo ser convertida correctamente. La extracción de rutas absolutas y normales es muy eficiente (porque el sistema de archivos opera internamente en estas representaciones), aunque el resultado cuando el sistema de archivos contiene múltiples enlaces simbólicos no será la versión más amigable de una ruta. El valor devuelto está propiedad de Tcl y tiene una vida útil equivalente a la del pathPtr pasado (a menos que sea un camino relativo, en cuyo caso el valor normalizado puede ser liberado cualquier vez que cambie el cwd) - el llamante puede incrementar la cuenta de referencia si lo desea para mantener una copia más tiempo. Tcl_FSJoinToPath toma el valor dado, que suele ser una ruta válida o NULL, y une el array de segmentos de rutas dados. Devuelve un valor, típicamente con una cuenta de referencia de 0 (pero podría compartirse en ciertas condiciones), conteniendo la ruta unida. El llamante debe agregar una cuenta de referencia al valor antes de usarlo. Si alguna de los valores pasados a esta función (pathPtr o path elementos) tiene una cuenta de referencia de 0, se liberará cuando esta función devuelva el valor. Tcl_FSConvertToPathType intenta convertir el objeto Tcl dado a un tipo de ruta válido, considerando que el cwd puede haber cambiado incluso si este valor ya se supone de tipo correcto. El nombre de archivo puede comenzar con “~” (para indicar el directorio de usuario actual) o “~” (para indicar cualquier directorio de usuario). Si la conversión es exitosa (es decir, el valor es una ruta válida en uno de los sistemas de archivos actuales), se devuelve TCL_OK. De lo contrario, se devuelve TCL_ERROR, y un mensaje de error puede ser almacenado en el interpretador. Tcl_FSGetInternalRep extrae la representación interna de un valor de ruta dado en el sistema de archivos especificado. Si el valor de ruta pertenece a un sistema de archivos diferente, se devuelve NULL. Si la representación interna es actualmente NULL, intenta generarla llamando a la función Tcl_FSCreateInternalRepProc del sistema de archivos. Devuelve NULL o una representación válida de la ruta interna. Esta representación interna es cachada, por lo que las llamadas repetidas a esta función no requieren conversiones adicionales. Tcl_FSGetTranslatedPath intenta extraer la ruta traducida a partir del objeto Tcl dado. Si la traducción es exitosa (es decir, el valor es una ruta válida), se devuelve el valor. De lo contrario, se devuelve NULL, y un mensaje de error puede ser almacenado en el interpretador. Una ruta traducida es una que contiene ni ~ ni ~user (estos han sido expandidos a su representación actual en el sistema de archivos). El valor devuelto está propiedad del llamante, que debe almacenarlo o llamar Tcl_DecrRefCount para asegurar que se libere la memoria. Esta función es de poca utilidad práctica y Tcl_FSGetNormalizedPath o Tcl_FSGetNativePath suelen ser funciones más adecuadas para muchos propósitos. Tcl_FSGetTranslatedStringPath hace lo mismo que Tcl_FSGetTranslatedPath, pero devuelve una cadena o NULL. El string devuelto es dinámicamente alineado. located and owned by the caller, which must store it or call ckfree to ensure it is freed. Again, Tcl_FSGetNormalizedPath or Tcl_FSGetNativePath are usually better functions to use for most purposes.

Tcl_FSNewNativePath performs something like the reverse of the usual obj->path->nativerep conversions. If some code retrieves a path in native form (from, e.g. readlink or a native dialog), and that path is to be used at the Tcl level, then calling this function is an efficient way of creating the appropriate path value type.

The resulting value is a pure “path” value, which will only receive a UTF-8 string representation if that is required by some Tcl code.

Tcl_FSGetNativePath is for use by the Win/Unix native filesystems, so that they can easily retrieve the native (char* or TCHAR*) representation of a path. This function is a convenience wrapper around Tcl_FSGetInternalRep. It may be desirable in the future to have non-string-based native representations (for example, on macOS, a representation using a fileSpec of FSRef structure would probably be more efficient). On Windows a full Unicode representation would allow for paths of unlimited length. Currently the representation is simply a character string which may contain either the relative path or a complete, absolute normalized path in the native encoding (complex conditions dictate which of these will be provided, so neither can be relied upon, unless the path is known to be absolute). If you need a native path which must be absolute, then you should ask for the native version of a normalized path. If for some reason a non-absolute, non-normalized version of the path is needed, that must be constructed separately (e.g. using Tcl_FSGetTranslatedPath).

The native representation is cached so that repeated calls to this function will not require additional conversions. The return value is owned by Tcl and has a lifetime equivalent to that of the pathPtr passed in (unless that is a relative path, in which case the native representation may be freed any time the cwd changes).

Tcl_FSFileSystemInfo returns a list of two elements. The first element is the name of the filesystem (e.g. “native”, “vfs”, “zip”, or “prowrap”, perhaps), and the second is the particular type of the given path within that filesystem (which is filesystem dependent). The second element may be empty if the filesystem does not provide a further categorization of files.

A valid list value is returned, unless the path value is not recognized, when NULL will be returned.

Tcl_FSGetFileSystemForPath returns a pointer to the Tcl_Filesystem which accepts this path as valid.

If no filesystem will accept the path, NULL is returned.

Tcl_FSGetPathType determines whether the given path is relative to the current directory, relative to the current volume, or absolute.

It returns one of TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE, or TCL_PATH_VOLUME_RELATIVE

THE VIRTUAL FILESYSTEM API

A filesystem provides a Tcl_Filesystem structure that contains pointers to functions that implement the various operations on a filesystem; these operations are invoked as needed by the generic layer, which generally occurs through the functions listed above.

The Tcl_Filesystem structures are manipulated using the following methods.

Tcl_FSRegister takes a pointer to a filesystem structure and an optional piece of data to associated with that filesystem. On calling this function, Tcl will attach the filesystem to the list of known filesystems, and it will become fully functional immediately. Tcl does not check if the same filesystem is registered multiple times (and in general that is not a good thing to do). TCL_OK will be returned.

Tcl_FSUnregister removes the given filesystem structure from the list of known filesystems, if it is known, and returns TCL_OK. If the filesystem is not currently registered, TCL_ERROR is returned.

Tcl_FSData will return the clientData associated with the given filesystem, if that filesystem is registered. Otherwise it will return NULL.

Tcl_FSMountsChanged is used to inform the Tcl's core that the set of mount points for the given (already registered) filesystem have changed, and that cached file representations may therefore no longer be correct.

Except for the first three fields in this structure which contain simple data elements, all entries contain addresses of functions called by the generic filesystem layer to perform the complete range of filesystem related actions.

The many functions in this structure are broken down into three categories: infrastructure functions (almost all of which must be implemented), operational functions (which must be implemented if a complete filesystem is provided), and efficiency functions (which need only be implemented if they can be done so efficiently, or if they have side-effects which are required by the filesystem; Tcl has less efficient emulations it can fall back on). It is important to note that, in the current version of Tcl, most of these fallbacks are only used to handle commands initiated in Tcl, not in C. What this means is, that if a file rename command is issued in Tcl, and the relevant filesystem(s) do not implement their Tcl_FSRenameFileProc, Tcl's core will instead fallback on a combination of other filesystem functions (it will use Tcl_FSCopyFileProc followed by Tcl_FSDeleteFileProc, and if Tcl_FSCopyFileProc is not implemented there is a further fallback). However, if a Tcl_FSRenameFileProc command is issued at the C level, no such fallbacks occur. This is true except for the last four entries in the filesystem table (lstat, load, getcwd and chdir) for which fallbacks do in fact occur at the C level.

Any functions which take path names in Tcl_Obj form take those names in UTF-8 form. The filesystem infrastructure API is designed to support efficient, cached conversion of these UTF-8 paths to other native representations.

وظيفة لمعالجة استدعاء Tcl_FSCopyFile. إذا لم يتم تنفيذها، تلجأ Tcl إلى استخدام open-r، open-w و fcopy كآلية نسخ. لذلك، يجب تنفيذها فقط إذا كان نظام الملفات يمكنه تنفيذ هذا الإجراء بكفاءة أكبر.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

القيمة المرجعة هي نتيجة Tcl قياسية تشير إلى ما إذا كانت هناك مشكلة في عملية النسخ. لاحظ أن destPathPtr هو اسم الملف الذي يجب أن يصبح نسخة من srcPathPtr. إنه ليس اسم مجلد يمكن نسخ srcPathPtr إليه (أي أن الوظيفة أبسط بكثير من الأمر الفرعي file copy على مستوى Tcl). لاحظ أنه إذا كان نظام الملفات يدعم الروابط الرمزية، فسوف تستدعي Tcl دائمًا هذه الوظيفة وليس copyDirectoryProc عند الضرورة لنسخها (حتى لو كانت روابط رمزية للمجلدات). أخيرًا، إذا قرر نظام الملفات أنه لا يمكنه دعم إجراء file copy، فإن استدعاء Tcl_SetErrno(EXDEV) وإرجاع نتيجة غير TCL_OK سيجعل Tcl تستخدم آلياتها القياسية البديلة.

        Tcl_LoadHandle *handlePtr,

وظيفة لمعالجة استدعاء Tcl_FSGetCwd. لا تحتاج معظم أنظمة الملفات إلى تنفيذ هذا. يمكن استدعاؤه مرة واحدة، إذا تم استدعاء getcwd قبل chdir. يمكن أن يكون NULL.

        Tcl_Interp *interp);

وظيفة لمعالجة استدعاء Tcl_FSChdir. إذا لم تقم أنظمة الملفات بتنفيذ هذا، فسيتم محاكاته عن طريق سلسلة من عمليات التحقق من الوصول إلى المجلدات. بخلاف ذلك، يجب أن تستجيب أنظمة الملفات الافتراضية التي تنفذ هذا بنتيجة إيجابية إذا كان pathPtr مجلدًا صالحًا ويمكن الوصول إليه في نظام الملفات الخاص بها. لا ينبغي لهم تذكر النتيجة، حيث سيتم تذكرها تلقائيًا بواسطة Tcl_FSGetCwd. يجب أن تقوم أنظمة الملفات الفعلية بإجراء الإجراء الصحيح (أي استدعاء واجهة برمجة تطبيقات chdir المناسبة للنظام).

        Tcl_Obj *pathPtr);
