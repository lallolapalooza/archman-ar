vent queue to see if it contains any events that can be serviced. If so, service the first possible event, remove it from the queue, and return.
[6]
See if there are idle callbacks pending. If so, invoke all of them and return.
[7]
Either return 0 to indicate that no events were ready, or go back to step [2] if blocking was requested by the caller.

إنشاء مصدر حدث جديد

يتكون مصدر الحدث من ثلاث إجراءات يتم استدعاؤها بواسطة المُعلم، بالإضافة إلى إجراءات C إضافية يتم استدعاؤها بواسطة التعليمات البرمجية ذات المستوى الأعلى لترتيب استدعاءات الأحداث. تتكون الإجراءات الثلاثة التي يستدعيها المُعلم من إجراءات الإعداد والفحص الموضحة أعلاه، بالإضافة إلى إجراء إضافي يتم استدعاؤه عند إزالة حدث من قائمة الأحداث للخدمة.

يقوم الإجراء Tcl_CreateEventSource بإنشاء مصدر حدث جديد. تحدد وسيطاته إجراء الإعداد وإجراء الفحص لمصدر الحدث. يجب أن يتطابق SetupProc مع النموذج الأولي التالي:

typedef void Tcl_EventSetupProc(
        ClientData clientData,
        int flags);

ستكون الوسيطة clientData هي نفسها الوسيطة clientData لـ Tcl_CreateEventSource؛ وهي تُستخدم عادةً للإشارة إلى معلومات خاصة يديرها مصدر الحدث. ستكون الوسيطة flags هي نفسها الوسيطة flags التي تم تمريرها إلى Tcl_DoOneEvent باستثناء أنها لن تكون 0 أبدًا (يستبدل Tcl_DoOneEvent القيمة 0 بـ TCL_ALL_EVENTS). تشير Flags إلى أنواع الأحداث التي يجب أخذها في الاعتبار؛ إذا لم يتم تعيين البت المقابل لمصدر الحدث هذا، فيجب أن يعود مصدر الحدث فورًا دون القيام بأي شيء. على سبيل المثال، يتحقق مصدر حدث الملف من البت TCL_FILE_EVENTS.

مهمة SetupProc هي التأكد من أن التطبيق يستيقظ عندما تحدث أحداث من النوع المطلوب. يتم ذلك عادةً بطريقة تعتمد على النظام الأساسي. على سبيل المثال، تحت Unix قد يستدعي مصدر حدث Tcl_CreateFileHandler؛ تحت Windows قد يطلب إشعارًا بحدث Windows. بالنسبة لمصادر الأحداث التي تعتمد على المؤقت مثل أحداث المؤقت أو أي حدث يتم فحصه، يمكن لمصدر الحدث استدعاء Tcl_SetMaxBlockTime لإجبار التطبيق على الاستيقاظ بعد وقت محدد حتى لو لم تحدث أحداث. إذا لم يستدعي أي مصدر حدث Tcl_SetMaxBlockTime، فسوف ينتظر Tcl_WaitForEvent لأطول فترة ضرورية لحدوث حدث؛ وإلا، فسوف ينتظر فقط طالما أن أقصر فترة تم تمريرها إلى Tcl_SetMaxBlockTime بواسطة أحد مصادر الأحداث. إذا عرف مصدر حدث أنه لديه بالفعل أحداث جاهزة للإبلاغ، فيمكنه طلب وقت حظر أقصى صفري. على سبيل المثال، ينظر إجراء الإعداد لمصدر حدث X لمعرفة ما إذا كانت هناك أحداث تم وضعها بالفعل في قائمة الانتظار. إذا كانت موجودة، فإنه يستدعي Tcl_SetMaxBlockTime بوقت حظر 0 حتى لا يحظر Tcl_WaitForEvent إذا لم تكن هناك بيانات جديدة في اتصال X. تشير الوسيطة timePtr إلى Tcl_WaitForEvent إلى بنية تصف فترة زمنية بالثواني وأجزاء من الثانية:

typedef struct Tcl_Time {
    long sec;
    long usec;
} Tcl_Time;

يجب أن يكون الحقل usec أقل من 1000000.

تُستخدم المعلومات المقدمة إلى Tcl_SetMaxBlockTime فقط للمكالمة التالية لـ Tcl_WaitForEvent؛ يتم تجاهلها بعد عودة Tcl_WaitForEvent. في المرة التالية التي يتم فيها انتظار حدث، سيتم استدعاء إجراءات الإعداد لكل مصدر حدث مرة أخرى، ويمكنهم تحديد معلومات جديدة لانتظار الحدث هذا.

إذا استخدم التطبيق حلقة أحداث خارجية بدلاً من Tcl_DoOneEvent، فقد تحتاج مصادر الأحداث إلى استدعاء Tcl_SetMaxBlockTime في أوقات أخرى. على سبيل المثال، إذا تم تسجيل معالج حدث جديد يحتاج إلى فحص الأحداث، فقد يستدعي مصدر الحدث Tcl_SetMaxBlockTime لتعيين وقت الحظر إلى الصفر لإجبار حلقة الأحداث الخارجية على استدعاء Tcl. في هذه الحالة، يستدعي Tcl_SetMaxBlockTime Tcl_SetTimer بأقصر فترة تم رؤيتها منذ آخر استدعاء لـ Tcl_DoOneEvent أو Tcl_ServiceAll.

بالإضافة إلى الإجراء العام Tcl_SetMaxBlockTime، قد تتوفر أيضًا إجراءات أخرى خاصة بالنظام الأساسي لـ setupProc، إذا كانت هناك معلومات إضافية مطلوبة بواسطة Tcl_WaitForEvent على هذا النظام الأساسي. على سبيل المثال، في أنظمة Unix يمكن استخدام واجهة Tcl_CreateFileHandler للانتظار لأحداث الملف.

الإجراء الثاني الذي يوفره كل مصدر حدث هو إجراء الفحص الخاص به، المشار إليه بواسطة الوسيطة checkProc لـ Tcl_CreateEventSource. يجب أن يتطابق CheckProc مع النموذج الأولي التالي:

typedef void Tcl_EventCheckProc(
        ClientData clientData,
        int flags);

الوسيطات لهذا الإجراء هي نفسها كما هو الحال بالنسبة لـ setupProc. يتم استدعاء CheckProc بواسطة Tcl_DoOneEvent بعد انتظار الأحداث. من المفترض أن يكون مصدر حدث واحد على الأقل مستعدًا الآن لوضع حدث في قائمة الانتظار. يستدعي Tcl_DoOneEvent كل مصدر حدث بدوره، لذلك لديهم جميعًا فرصة لوضع أي أحداث جاهزة في قائمة الانتظار. يقوم إجراء الفحص بأمرين. أولاً، يجب أن يرى ما إذا كانت أي أحداث قد تم تشغيلها. تقوم مصادر الأحداث المختلفة بذلك بطرق مختلفة.

إذا اكتشف إجراء فحص مصدر الحدث حدثًا مثيرًا للاهتمام، فيجب عليه إضافة الحدث إلى قائمة أحداث Tcl. للقيام بذلك، يستدعي مصدر الحدث Tcl_QueueEvent. الوسيطة evPtr هي مؤشر إلى بنية تم تخصيصها ديناميكيًا تحتوي على الحدث (انظر أدناه لمزيد من المعلومات حول قضايا إدارة الذاكرة). يمكن لكل مصدر حدث تعريف بنية الحدث الخاصة به بأي معلومات ذات صلة بمصدر الحدث هذا. ومع ذلك، يجب أن يكون العنصر الأول في البنية بنية من النوع Tcl_Event، ويتم استخدام عنوان هذه البنية عند التواصل بين مصدر الحدث وبقية المُعلم. يحتوي Tcl_Event على التعريف التالي:

typedef struct {
    Tcl_EventProc *proc;
    struct Tcl_Event *nextPtr;
} Tcl_Event;

يجب على مصدر الحدث ملء حقل proc للحدث قبل استدعاء Tcl_QueueEvent. يتم استخدام nextPtr لربط الأحداث معًا في قائمة الانتظار ولا ينبغي تعديلها بواسطة مصدر الحدث.

يمكن إضافة حدث إلى قائمة الانتظار في أي من ثلاثة مواضع، اعتمادًا على الوسيطة position لـ Tcl_QueueEvent:

TCL_QUEUE_TAIL
أضف الحدث إلى نهاية قائمة الانتظار، بحيث تتم خدمة جميع الأحداث المعلقة الأخرى أولاً. هذا هو المكان الصحيح تقريبًا دائمًا للأحداث الجديدة.
TCL_QUEUE_HEAD
أضف الحدث إلى مقدمة قائمة الانتظار، بحيث تتم خدمته قبل جميع الأحداث الأخرى في قائمة الانتظار.
TCL_QUEUE_MARK
أضف الحدث إلى مقدمة قائمة الانتظار، ما لم تكن هناك أحداث أخرى في المقدمة يكون موضعها TCL_QUEUE_MARK؛ إذا كان الأمر كذلك، فأضف الحدث الجديد مباشرة بعد جميع أحداث TCL_QUEUE_MARK الأخرى. تُستخدم قيمة position هذه لإدراج تسلسل مرتب من الأحداث في مقدمة قائمة الانتظار، مثل سلسلة من أحداث الدخول والخروج التي تم إنشاؤها أثناء عملية الإمساك أو التحرير في Tk.

عندما يحين وقت معالجة حدث من قائمة الانتظار (الخطوات 1 و 4 أعلاه) سيقوم Tcl_ServiceEvent باستدعاء proc المحدد في بنية Tcl_Event الأولى في قائمة الانتظار. يجب أن يتطابق Proc مع النموذج الأولي التالي:

typedef int Tcl_EventProc(
        Tcl_Event *evPtr,
        int flags);

الوسيطة الأولى لـ proc هي مؤشر إلى الحدث، والتي ستكون هي نفسها الوسيطة الأولى لمكالمة Tcl_QueueEvent التي أضافت الحدث إلى قائمة الانتظار. الوسيطة الثانية لـ proc هي الوسيطة flags للمكالمة الحالية لـ Tcl_ServiceEvent؛ يستخدمها مصدر الحدث للعودة فورًا إذا لم تكن أحداثه ذات صلة.

يعود الأمر إلى proc لمعالجة الحدث، عادةً عن طريق استدعاء أمر Tcl واحد أو أكثر أو استدعاءات C. بمجرد انتهاء مصدر الحدث من معالجة الحدث، فإنه يعيد 1 للإشارة إلى أنه يمكن إزالة الحدث من قائمة الانتظار. إذا قرر مصدر الحدث، لسبب ما، أنه لا يمكن معالجة الحدث في هذا الوقت، فقد يعيد 0 للإشارة إلى أنه يجب تأجيل الحدث للمعالجة لاحقًا؛ في هذه الحالة، سيستمر Tcl_ServiceEvent إلى الحدث التالي في قائمة الانتظار ويحاول خدمته. هناك عدة أسباب قد تؤدي إلى تأجيل مصدر حدث لحدث. أحد الاحتمالات هو استبعاد الأحداث من هذا النوع بواسطة الوسيطة flags. على سبيل المثال، سيعيد مصدر حدث الملف دائمًا 0 إذا لم يتم تعيين البت TCL_FILE_EVENTS في flags. مثال آخر لتأجيل الأحداث يحدث في Tk إذا تم استدعاء Tk_RestrictEvents لتأجيل أنواع معينة من أحداث النافذة.

عندما يعيد proc القيمة 1، ستقوم Tcl_ServiceEvent بإزالة الحدث من قائمة الأحداث وتحرير تخزينه. لاحظ أن تخزين الحدث يجب أن يتم تخصيصه بواسطة مصدر الحدث (باستخدام Tcl_Alloc أو ماكرو Tcl ckalloc) قبل استدعاء Tcl_QueueEvent، ولكنه سيتم تحريره بواسطة Tcl_ServiceEvent، وليس بواسطة مصدر الحدث.

تعمل التطبيقات متعددة الخيوط بطريقة مماثلة، باستثناء أن هناك قائمة انتظار أحداث منفصلة لكل خيط يحتوي على مترجم Tcl. استدعاء Tcl_QueueEvent في تطبيق متعدد الخيوط يضيف حدثًا إلى قائمة الانتظار للخيط الحالي. لإضافة حدث إلى قائمة انتظار خيط آخر، استخدم Tcl_ThreadQueueEvent. يقبل Tcl_ThreadQueueEvent كوسيطة وسيطة Tcl_ThreadId، والتي تحدد بشكل فريد خيطًا في تطبيق Tcl. للحصول على Tcl_ThreadId للخيط الحالي، استخدم الإجراء Tcl_GetCurrentThread. (سيحتاج الخيط بعد ذلك إلى تمرير هذا المعرف إلى خيوط أخرى لتتمكن تلك الخيوط من إضافة أحداث إلى قائمته). بعد إضافة حدث إلى قائمة انتظار خيط آخر، عادةً ما تحتاج إلى استدعاء Tcl_ThreadAlert لـ "إيقاظ" مُعلم ذلك الخيط لتنبيهه إلى الحدث الجديد.

يمكن استخدام Tcl_DeleteEvents لإزالة حدث أو أكثر بشكل صريح من قائمة الأحداث. يقوم Tcl_DeleteEvents باستدعاء proc لكل حدث في قائمة الانتظار، وحذف تلك التي يعيد الإجراء لها 1. الأحداث التي يعيد الإجراء لها 0 تظل في قائمة الانتظار. يجب أن يتطابق Proc مع النموذج الأولي التالي:

typedef int Tcl_EventDeleteProc(
        Tcl_Event *evPtr,
        ClientData clientData);

ستكون الوسيطة clientData هي نفسها الوسيطة clientData لـ Tcl_DeleteEvent

s؛ يستخدم عادةً للإشارة إلى معلومات خاصة تديرها مصدر الحدث. ال evPtr ستشير إلى الحدث التالي في قائمة الانتظار.

Tcl_DeleteEventSource تحذف مصدر حدث. ال setupProc، checkProc، و clientData يجب أن تتطابق تمامًا مع تلك المقدمة إلى Tcl_CreateEventSource لمصدر الحدث المراد حذفه. إذا لم يكن هناك مصدر كهذا، فإن Tcl_DeleteEventSource ليس لها أي تأثير.

إنشاء موجه أحداث جديد

يتكون الموجه من جميع الإجراءات الموصوفة في دليل الاستخدام هذا، بالإضافة إلى Tcl_DoOneEvent و Tcl_Sleep، المتوفرة على جميع المنصات، و Tcl_CreateFileHandler و Tcl_DeleteFileHandler، وهي خاصة بنظام Unix. معظم هذه الإجراءات عامة، بمعنى أنها هي نفسها لجميع الموجهات. ومع ذلك، لا يوجد أي من الإجراءات يعتمد على الموجه: Tcl_InitNotifier، Tcl_AlertNotifier، Tcl_FinalizeNotifier، Tcl_SetTimer، Tcl_Sleep، Tcl_WaitForEvent، Tcl_CreateFileHandler، Tcl_DeleteFileHandler و Tcl_ServiceModeHook. لدعم منصة جديدة أو لدمج Tcl مع حلقة أحداث خاصة بتطبيق، يجب عليك كتابة إصدارات جديدة من هذه الإجراءات.

Tcl_InitNotifier تهيئ حالة الموجه وتعيد مقبضًا لحالة الموجه. تقوم Tcl باستدعاء هذا الإجراء عند تهيئة مترجم Tcl. وبالمثل، يقوم Tcl_FinalizeNotifier بإيقاف تشغيل الموجه، ويتم استدعاؤه بواسطة Tcl_Finalize عند إيقاف مترجم Tcl.

Tcl_WaitForEvent هو الإجراء الأقل مستوى في الموجه؛ وهو مسؤول عن الانتظار لوقوع حدث "مثير للاهتمام" أو لانقضاء وقت معين. قبل استدعاء Tcl_WaitForEvent، تم استدعاء إجراء الإعداد لكل مصدر حدث. الوسيط timePtr إلى Tcl_WaitForEvent يعطي الحد الأقصى للوقت الذي سيتم فيه حظر الانتظار لحدث، بناءً على استدعاءات Tcl_SetMaxBlockTime التي تمت بواسطة إجراءات الإعداد والمعلومات الأخرى (مثل بت TCL_DONT_WAIT في flags).

من الناحية المثالية، يجب على Tcl_WaitForEvent الانتظار فقط لوقوع حدث؛ يجب ألا يقوم بمعالجة الحدث بأي شكل من الأشكال. لاحقًا، ستقوم مصادر الأحداث بمعالجة الأحداث الخام وإنشاء Tcl_Events على قائمة انتظار الأحداث في إجراءات checkProc الخاصة بها. ومع ذلك، في بعض المنصات (مثل Windows) هذا غير ممكن؛ قد تتم معالجة الأحداث في Tcl_WaitForEvent، بما في ذلك وضع Tcl_Events في قائمة الانتظار والمزيد (على سبيل المثال، قد يتم استدعاء ردود الاتصال للودجات الأصلية). يجب أن تكون القيمة المرجعة من Tcl_WaitForEvent إما 0 أو 1 أو -1. على المنصات مثل Windows حيث تتم معالجة الأحداث في Tcl_WaitForEvent، تعني القيمة المرجعة 1 أنه قد تكون هناك أحداث أخرى لا تزال معلقة لم تتم معالجتها. هذه علامة للمستدعي بأنه يجب عليه استدعاء Tcl_WaitForEvent مرة أخرى إذا كان يريد معالجة جميع الأحداث المعلقة. تعني القيمة المرجعة 0 أن استدعاء Tcl_WaitForEvent مرة أخرى لن يكون له أي تأثير: إما أن هذه منصة حيث Tcl_WaitForEvent تنتظر فقط دون القيام بأي معالجة للأحداث، أو أن Tcl_WaitForEvent تعرف بالتأكيد أنه لا توجد أحداث إضافية لمعالجتها (مثل أنها عادت لأن الوقت انقضى). أخيرًا، تعني القيمة المرجعة -1 أن حلقة الأحداث لم تعد عاملة وأن التطبيق يجب أن يفك التكديس وينتهي. تحت Windows يحدث هذا عندما يتم استلام رسالة WM_QUIT؛ تحت Unix يحدث هذا عندما كان Tcl_WaitForEvent سينتظر إلى الأبد لأنه لم تكن هناك مصادر أحداث نشطة وكان المهلة لا نهائية.

Tcl_AlertNotifier يستخدم في التطبيقات متعددة الخيوط للسماح لأي خيط "بإيقاظ" الموجه لتنبيهه إلى أحداث جديدة في قائمة الانتظار الخاصة به. يتطلب Tcl_AlertNotifier كمُدخل مقبض الموجه الذي أعادته Tcl_InitNotifier.

إذا كان سيتم استخدام الموجه مع حلقة أحداث خارجية، فيجب عليه أيضًا دعم واجهة Tcl_SetTimer. يتم استدعاء Tcl_SetTimer بواسطة Tcl_SetMaxBlockTime كلما تم تقليل الحد الأقصى لوقت الحظر. يجب على Tcl_SetTimer ترتيب حلقة الأحداث الخارجية لاستدعاء Tcl_ServiceAll بعد الفترة الزمنية المحددة حتى لو لم تحدث أي أحداث. هذه الواجهة مطلوبة لأن Tcl_WaitForEvent لا يتم استدعاؤه عند وجود حلقة أحداث خارجية. إذا كان سيتم استخدام الموجه فقط من Tcl_DoOneEvent، فلن يحتاج Tcl_SetTimer إلى القيام بأي شيء.

يتم استدعاء Tcl_ServiceModeHook بواسطة الجزء المستقل عن المنصة من الموجه عندما يقوم رمز العميل باستدعاء Tcl_SetServiceMode. يتم توفير هذا الخطاف لدعم أنظمة التشغيل التي تتطلب معالجة أحداث خاصة عندما يكون التطبيق في حلقة نمطية (الموجه Windows، على سبيل المثال، يستخدم هذا الخطاف لإنشاء نافذة اتصال).

على أنظمة Unix، يحتاج مصدر حدث الملف أيضًا إلى دعم من الموجه. يتكون مصدر حدث الملف من إجراءات Tcl_CreateFileHandler و Tcl_DeleteFileHandler، التي يتم وصفها في صفحة دليل Tcl_CreateFileHandler.

يتم وصف واجهتي Tcl_Sleep و Tcl_DoOneEvent في صفحات أدلة الخاصة بهما.

أسهل طريقة لإنشاء موجه جديد هي النظر إلى الكود الخاص بموجه موجود، مثل ملفات unix/tclUnixNotfy.c أو win/tclWinNotify.c في توزيع مصدر Tcl.

استبدال الموجه

يمكن أيضًا تثبيت موجه تم كتابته وفقًا للاصطلاحات المذكورة أعلاه في عملية قيد التشغيل محل الموجه القياسي. تستخدم هذه الآلية بحيث يمكن استخدام ملف تنفيذي واحد (مع الموجه القياسي) كبرنامج مستقل وإعادة استخدامه (مع موجه بديل في امتداد قابل للتحميل) كامتداد لبرنامج آخر، مثل مكون إضافي لمتصفح الويب.

للقيام بذلك، يقوم الامتداد بإجراء استدعاء إلى Tcl_SetNotifier يمرر مؤشرًا إلى بنية بيانات Tcl_NotifierProcs. يكون للبنية التخطيط التالي:

typedef struct Tcl_NotifierProcs {
    Tcl_SetTimerProc *setTimerProc;
    Tcl_WaitForEventProc *waitForEventProc;
    Tcl_CreateFileHandlerProc *createFileHandlerProc;
    Tcl_DeleteFileHandlerProc *deleteFileHandlerProc;
    Tcl_InitNotifierProc *initNotifierProc;
    Tcl_FinalizeNotifierProc *finalizeNotifierProc;
    Tcl_AlertNotifierProc *alertNotifierProc;
    Tcl_ServiceModeHookProc *serviceModeHookProc;
} Tcl_NotifierProcs;

بعد استدعاء Tcl_SetNotifier، تستبدل المؤشرات المقدمة في بنية Tcl_NotifierProcs أي موجه تم تثبيته في العملية.

من الحكمة للغاية استبدال موجه قيد التشغيل. عادةً، يجب استدعاء Tcl_SetNotifier عند تهيئة العملية قبل أول استدعاء لـ Tcl_InitNotifier.

حلقات الأحداث الخارجية

تم تصميم واجهات الموجه بحيث يمكن تضمين Tcl في التطبيقات التي لديها حلقات أحداث خاصة بها. في هذه الحالة، لا يستدعي التطبيق Tcl_DoOneEvent إلا في حالة حلقات الأحداث المتكررة مثل استدعاء أوامر Tcl update أو vwait. يتم قضاء معظم الوقت في حلقة الأحداث الخارجية للتطبيق. في هذه الحالة، يجب على الموجه ترتيب حلقة الأحداث الخارجية للعودة إلى Tcl عند حدوث شيء ما على مصادر أحداث Tcl المختلفة. يجب أن ترتب ردود الاتصال هذه لوضع أحداث Tcl المناسبة في قائمة انتظار أحداث Tcl.

نظرًا لأن حلقة الأحداث الخارجية لا تستدعي Tcl_DoOneEvent بشكل منتظم، فإنه يعود للموجه لترتيب استدعاء Tcl_ServiceEvent كلما كانت هناك أحداث معلقة في قائمة انتظار أحداث Tcl. أسهل طريقة للقيام بذلك هي استدعاء Tcl_ServiceAll في نهاية كل رد اتصال من حلقة الأحداث الخارجية. هذا سيضمن مسح جميع مصادر الأحداث، وخدمة أي أحداث معلقة، ومعالجة أي معالجات خاملة معلقة قبل إعادة التحكم إلى التطبيق. بالإضافة إلى ذلك، يمكن لمصادر الأحداث التي تحتاج إلى فحص الأحداث استدعاء Tcl_SetMaxBlockTime لإجبار حلقة الأحداث الخارجية على استدعاء Tcl حتى لو لم تكن هناك أحداث متاحة في قائمة انتظار أحداث النظام.

كنتيجة جانبية لمعالجة الأحداث المكتشفة في حلقة الأحداث الخارجية الرئيسية، قد تستدعي Tcl Tcl_DoOneEvent لبدء حلقة أحداث متكررة في أوامر مثل vwait. سيستدعي Tcl_DoOneEvent حلقة الأحداث الخارجية، مما يؤدي إلى ردود اتصال كما هو موضح في الفقرة السابقة، مما يؤدي إلى استدعاءات لـ Tcl_ServiceAll. ومع ذلك، في هذه الحالات، من غير المرغوب فيه خدمة الأحداث في Tcl_ServiceAll. خدمة الأحداث هناك غير ضرورية لأن التحكم سيعود فورًا إلى حلقة الأحداث الخارجية وبالتالي إلى Tcl_DoOneEvent، الذي يمكنه خدمة الأحداث بنفسه. علاوة على ذلك، من المفترض أن يقوم Tcl_DoOneEvent بخدمة حدث واحد فقط، بينما يقوم Tcl_ServiceAll عادةً بخدمة جميع الأحداث المعلقة. لمعالجة هذا الموقف، يقوم Tcl_DoOneEvent بتعيين علامة لـ Tcl_ServiceAll تجعلها تعود دون خدمة أي أحداث. تسمى هذه العلامة وضع الخدمة؛ يستعيدها Tcl_DoOneEvent إلى قيمتها السابقة قبل أن يعود. Tcl_SetServiceMode يعيد القيمة السابقة لوضع الخدمة، والتي يجب استعادتها عند خروج الحلقة المتكررة. Tcl_GetServiceMode يعيد القيمة الحالية لوضع الخدمة.

في بعض الحالات، قد يكون من الضروري أن يقوم Tcl_ServiceAll بخدمة الأحداث حتى عند استدعائه من Tcl_DoOneEvent. يحدث هذا عندما يكون هناك حلقة أحداث متكررة أخرى تم استدعاؤها عبر معالج أحداث بواسطة Tcl_DoOneEvent (مثل تلك التي هي جزء من ودجت أصلي). في هذه الحالة، قد لا تتاح لـ Tcl_DoOneEvent فرصة لخدمة الأحداث، لذلك يجب على Tcl_ServiceAll خدمتها جميعًا. يجب على أي حلقة أحداث متكررة تستدعي حلقة أحداث خارجية بدلاً من Tcl_DoOneEvent إعادة تعيين وضع الخدمة بحيث تتم معالجة جميع الأحداث في Tcl_ServiceAll. يتم ذلك عن طريق استدعاء إجراء Tcl_SetServiceMode. إذا تم تمرير TCL_SERVICE_NONE إلى Tcl_SetServiceMode، فإن استدعاءات Tcl_ServiceAll ستعود على الفور دون معالجة أي أحداث. إذا تم تمرير TCL_SERVICE_ALL إلى Tcl_SetServiceMode، فإن استدعاءات Tcl_ServiceAll ستتصرف بشكل طبيعي. Tcl_SetServiceMode يعيد القيمة السابقة لوضع الخدمة، والتي يجب استعادتها عند انتهاء الحلقة المتكررة. Tcl_GetServiceMode يعيد القيمة الحالية لوضع الخدمة.

INTRODUCTION

The Tcl event loop is responsible for dispatching events to the appropriate handlers. In a single-threaded Tcl application, the event loop is relatively simple. However, in a multithreaded Tcl application, the event loop becomes more complex. This manual page describes the Tcl threading model and the functions that allow you to manage threads and their associated event loops.

NOTIFIER BASICS

Each Tcl thread has an associated notifier. The notifier is responsible for handling thread-specific events. When an event occurs in a thread, the notifier is called to process the event. The notifier can then queue the event for processing by the thread's event loop, or it can handle the event directly.

CREATING A NEW EVENT SOURCE

You can create a new event source by calling the Tcl_CreateEventSource function. This function takes a filter procedure, a check procedure, and client data as arguments. The filter procedure is called when an event occurs, and it is responsible for determining whether the event should be processed by the event source. The check procedure is called when the event loop is idle, and it is responsible for checking if there are any events that should be processed by the event source. The client data is a pointer to the data that will be passed to the filter procedure and the check procedure.

CREATING A NEW NOTIFIER

You can create a new notifier by calling the Tcl_NewNotifier function. This function takes a notifier procedure, an exit procedure, and client data as arguments. The notifier procedure is called when an event occurs, and it is responsible for handling the event. The exit procedure is called when the thread exits, and it is responsible for cleaning up any resources that were allocated by the notifier. The client data is a pointer to the data that will be passed to the notifier procedure and the exit procedure.

REPLACING THE NOTIFIER

You can replace the notifier for a thread by calling the Tcl_DeleteNotifier function to delete the existing notifier, and then calling the Tcl_NewNotifier function to create a new notifier.

EXTERNAL EVENT LOOPS

Tcl provides functions that allow you to integrate Tcl's event loop with an external event loop. This is useful if you are embedding Tcl in an application that already has its own event loop, such as a GUI toolkit. The Tcl_WaitForEvent function can be used to wait for events to occur, and the Tcl_ServiceEvent function can be used to process events. The Tcl_MainLoop function starts the Tcl event loop, and the Tcl_Main function initializes Tcl and starts the event loop.
