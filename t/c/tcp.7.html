اسم

tcp - بروتوكول TCP

ملخص

#include <sys/socket.h>
#include <netinet/in.h>

الوصف

هذا تنفيذ لبروتوكول TCP المحدد في RFC 793 و RFC 1122 و RFC 2001 مع امتدادات NewReno و SACK. يوفر اتصالاً موثوقًا، موجهاً كسلسلة، مزدوج الاتجاه بين مقبسين فوق ip(7)، لكل من الإصدارين v4 و v6. يضمن TCP وصول البيانات بالترتيب ويعيد إرسال الحزم المفقودة. يقوم بإنشاء وفحص المجموع الاختباري لكل حزمة لاكتشاف أخطاء الإرسال. TCP لا يحافظ على حدود السجلات.

المقبس TCP الذي تم إنشاؤه حديثًا ليس له عنوان بعيد أو محلي وليس محددًا بالكامل. لإنشاء اتصال TCP صادر، استخدم connect(2) لإنشاء اتصال بمقبس TCP آخر. لاستقبال الاتصالات الواردة الجديدة، قم أولاً باستدعاء bind(2) للمقبس بعنوان ومنفذ محلي ثم استدعاء listen(2) لوضع المقبس في حالة الاستماع. بعد ذلك، يمكن قبول مقبس جديد لكل اتصال وارد باستخدام accept(2). المقبس الذي تم استدعاء accept(2) أو connect(2) عليه بنجاح يكون محددًا بالكامل ويمكنه نقل البيانات. لا يمكن إرسال البيانات على المقابس التي تستمع أو غير المتصلة بعد.

يدعم Linux امتدادات TCP عالية الأداء RFC 1323. وتشمل هذه الحماية ضد أرقام التسلسل الملفوفة (PAWS)، وتوسيع النافذة، والطوابع الزمنية. يسمح توسيع النافذة باستخدام نوافذ TCP كبيرة (> 64 كيلوبايت) لدعم الارتباطات ذات زمن الاستجابة أو النطاق الترددي العالي. للاستفادة منها، يجب زيادة أحجام مخزن الإرسال والاستقبال. يمكن تعيينها بشكل عام باستخدام الملفات /proc/sys/net/ipv4/tcp_wmem و /proc/sys/net/ipv4/tcp_rmem، أو على مقابس فردية باستخدام خيارات المقبس SO_SNDBUF و SO_RCVBUF مع استدعاء setsockopt(2).

يتم تحديد الأحجام القصوى لمخازن المقبس المعلنة عبر آليات SO_SNDBUF و SO_RCVBUF بواسطة القيم في الملفات /proc/sys/net/core/rmem_max و /proc/sys/net/core/wmem_max. لاحظ أن TCP يخصص فعليًا ضعف حجم المخزن المطلوب في استدعاء setsockopt(2)، وبالتالي فإن استدعاء getsockopt(2) اللاحق لن يعيد نفس حجم المخزن المطلوب في استدعاء setsockopt(2). يستخدم TCP المساحة الإضافية للأغراض الإدارية وهياكل النواة الداخلية، وتعكس قيم /proc الأحجام الأكبر مقارنة بنوافذ TCP الفعلية. على الاتصالات الفردية، يجب تعيين حجم مخزن المقبس قبل استدعاءات listen(2) أو connect(2) حتى يسري مفعولها. انظر socket(7) لمزيد من المعلومات.

يدعم TCP البيانات العاجلة. تُستخدم البيانات العاجلة لإبلاغ المستلم بأن رسالة مهمة جزء من تدفق البيانات وأنه يجب معالجتها في أقرب وقت ممكن. لإرسال بيانات عاجلة، حدد الخيار MSG_OOB لـ send(2). عند استقبال بيانات عاجلة، يرسل النواة إشارة SIGURG إلى العملية أو مجموعة العمليات التي تم تعيينها كـ "مالك" للمقبس باستخدام عمليات ioctls SIOCSPGRP أو FIOSETOWN (أو عملية POSIX.1 المحددة fcntl(2) F_SETOWN). عند تمكين خيار المقبس SO_OOBINLINE، يتم وضع البيانات العاجلة في تدفق البيانات العادي (يمكن للبرنامج الاختبار لموقعه باستخدام ioctl SIOCATMARK الموضحة أدناه)، وإلا فلا يمكن استقبالها إلا عند تعيين علامة MSG_OOB لـ recv(2) أو recvmsg(2).

عند وجود بيانات خارج النطاق، يشير select(2) إلى واصف الملف كشرط استثنائي ويشير poll(2) إلى حدث POLLPRI.

قدم Linux 2.4 عددًا من التغييرات لتحسين الإنتاجية والتوسع، بالإضافة إلى وظائف محسنة. تتضمن بعض هذه الميزات دعم sendfile(2) بدون نسخ، والإبلاغ عن الازدحام الصريح (Explicit Congestion Notification)، والإدارة الجديدة لمقابس TIME_WAIT، وخيارات مقبس keep-alive، ودعم امتدادات Duplicate SACK.

تنسيقات العناوين

يعتمد TCP على IP (انظر ip(7)). تنطبق تنسيقات العناوين المعرفة بواسطة ip(7) على TCP. يدعم TCP الاتصال من نقطة إلى نقطة فقط؛ لا يتم دعم البث المتعدد أو البث.

واجهات /proc

يمكن الوصول إلى إعدادات معلمات TCP على مستوى النظام عن طريق الملفات الموجودة في الدليل /proc/sys/net/ipv4/. بالإضافة إلى ذلك، تنطبق معظم واجهات IP /proc على TCP؛ انظر ip(7). تأخذ المتغيرات الموصوفة كـ Boolean قيمة عددية، مع قيمة غير صفرية ("صحيح") تعني تمكين الخيار المقابل، وقيمة صفرية ("خطأ") تعني تعطيل الخيار.

tcp_abc (عدد صحيح؛ افتراضي: 0؛ Linux 2.6.15 إلى Linux 3.8)
التحكم في عد البايت المناسب (ABC)، المحدد في RFC 3465. ABC هي طريقة لزيادة نافذة الازدحام (cwnd) بشكل أبطأ استجابة للإقرارات الجزئية. القيم الممكنة هي:
0
زيادة cwnd مرة واحدة لكل إقرار (لا يوجد ABC)
1
زيادة cwnd مرة واحدة لكل إقرار بحزمة كاملة الحجم
2
السماح بزيادة cwnd مرتين إذا كان الإقرار لحزمتين للتعويض عن الإقرارات المتأخرة.
tcp_abort_on_overflow (Boolean؛ افتراضي: معطل؛ منذ Linux 2.4)
تمكين إعادة تعيين الاتصالات إذا كانت الخدمة المستمعة بطيئة جدًا وغير قادرة على مواكبة الاستقبال وقبولها. هذا يعني أنه إذا حدث تجاوز بسبب انفجار، فسيتم استعادة الاتصال. قم بتمكين هذا الخيار فقط إذا كنت متأكدًا حقًا من أنه لا يمكن ضبط خادم الاستماع لقبول الاتصالات بشكل أسرع. قد يؤدي تمكين هذا الخيار إلى الإضرار بعملاء خادمك.
tcp_adv_win_scale (عدد صحيح؛ افتراضي: 2؛ منذ Linux 2.4)
حساب تكلفة التخزين المؤقت كـ bytes/2^tcp_adv_win_scale، إذا كان tcp_adv_win_scale أكبر من 0؛ أو bytes-bytes/2^(-tcp_adv_win_scale)، إذا كان tcp_adv_win_scale أقل من أو يساوي صفر.
تتم مشاركة مساحة مخزن الاستقبال للمقبس بين التطبيق والنواة. يحتفظ TCP بجزء من المخزن كنافذة TCP، وهذا هو حجم نافذة الاستقبال المعلنة للطرف الآخر. يُستخدم الجزء المتبقي من المساحة كمخزن "التطبيق"، ويُستخدم لعزل الشبكة عن زمن الاستجابة المجدولة وزمن استجابة التطبيق. القيمة الافتراضية لـ tcp_adv_win_scale وهي 2 تعني أن المساحة المستخدمة لمخزن التطبيق هي ربع الإجمالي.
tcp_allowed_congestion_control (سلسلة؛ افتراضي: انظر النص؛ منذ Linux 2.4.20)
عرض/تعيين خيارات خوارزمية التحكم في الازدحام المتاحة للعمليات غير المميزة (انظر وصف خيار المقبس TCP_CONGESTION). يتم فصل العناصر في القائمة بمسافات بيضاء وتنتهي بحرف سطر جديد. القائمة هي مجموعة فرعية لتلك المدرجة في tcp_available_congestion_control. القيمة الافتراضية لهذه القائمة هي "reno" بالإضافة إلى الإعداد الافتراضي لـ tcp_congestion_control.
tcp_autocorking (Boolean؛ افتراضي: ممكّن؛ منذ Linux 3.14)
إذا تم تمكين هذا الخيار، تحاول النواة دمج حزم صغيرة

NAME

tcp — Transmission Control Protocol

SYNOPSIS

#include <sys/types.h>
#include <sys/socket.h>
#include <netinet/in.h>
#include <netinet/tcp.h>

socket(AF_INET, SOCK_STREAM, IPPROTO_TCP);

DESCRIPTION

The Virtual Circuit Service, commonly known as Transmission Control Protocol (TCP), is an internet protocol that provides reliable, ordered, and error-checked delivery of a stream of bytes between applications running on hosts communicating via an Internet Protocol (IP) network. TCP is designed to be used for applications that require high reliability. The IP protocol provides basic datagram transfer, and TCP adds reliability, flow control, and multiplexing capabilities.

TCP is a connection-oriented protocol. A connection must be established between the sender and receiver before any data can be transferred. This connection establishment is performed using a three-way handshake.

TCP segments outgoing data into packets and reassembles incoming packets into a byte stream. TCP manages the sequence numbers and acknowledgments to ensure that data is delivered reliably and in the correct order. Flow control is performed using a sliding window mechanism, which prevents a fast sender from overwhelming a slow receiver.

TCP uses a congestion control algorithm to prevent the network from becoming overloaded. This algorithm adjusts the sending rate based on network conditions such as packet loss and round-trip time.

TCP supports options that can be negotiated during connection establishment. Common options include:

Maximum Segment Size (MSS)
The largest amount of data, specified in bytes, that TCP is willing to receive in a single segment.
Window scaling
Allows TCP to use larger receive windows than the default 65,535 bytes, improving throughput over high-bandwidth, high-latency networks.
Timestamps
Used for more accurate round-trip time estimation and protection against wrapped sequence numbers.
Selective acknowledgments (SACK)
Allows the receiver to inform the sender about specific segments that have been received, enabling the sender to retransmit only the missing segments.
Explicit Congestion Notification (ECN)
Allows network routers to signal congestion to endpoints without dropping packets.

The Linux kernel implements several TCP congestion control algorithms, including:

TCP Reno
The standard algorithm, which uses slow start, congestion avoidance, fast retransmit, and fast recovery.
TCP Cubic
The default on many Linux systems. It uses a cubic function to adjust the congestion window, providing better performance in high-bandwidth, long-delay networks.
TCP BBR
Bottleneck Bandwidth and Round-trip propagation time. A newer algorithm that aims to maximize throughput and minimize latency by modeling the network path.

The default congestion control algorithm can be queried and set using the net.ipv4.tcp_congestion_control sysctl parameter.

Socket options

The following socket options are specific to TCP:

TCP_CORK
If set, tells the kernel to delay sending any outgoing data until the cork is popped. This is useful for sending data more efficiently by allowing multiple small chunks to be bundled into a single packet. When the cork is set, the kernel will not send any partial segments. The option is cleared by setting it to 0. This option is defined in <linux/tcp.h>.
TCP_NODELAY
If set, disables the Nagle algorithm. The Nagle algorithm is a heuristic intended to improve network performance by minimizing the number of small packets sent. However, it can also introduce latency, especially in interactive applications. Disabling it can reduce latency but may increase network overhead. This option is defined in <linux/tcp.h>.
TCP_QUICKACK
If set, enables quick acknowledgments. When quick acknowledgments are enabled, TCP sends acknowledgments immediately in response to received data, rather than delaying them to potentially piggyback them on outgoing data segments. This can help speed up the detection of packet loss and improve performance in certain network conditions. This option is defined in <linux/tcp.h>.
TCP_DEFER_ACCEPT
This option enables and sets a timeout for the TCP deferred accept mechanism. If set to a positive value, it enables the deferred accept feature. The socket must be in the LISTEN state. When a SYN arrives, the kernel accepts the connection but does not generate the SYN-ACK until data arrives from the client, or the specified timeout expires. This can help mitigate certain types of denial-of-service attacks. The timeout value is specified in seconds. This option is defined in <linux/tcp.h>.
TCP_FASTOPEN
This option enables TCP Fast Open. Fast Open allows data to be sent in the initial SYN packet, reducing the round-trip time for establishing a connection. The option value determines the maximum number of Fast Open connections that can be pending. This option is defined in <linux/tcp.h>.

In addition to TCP-specific options, the following generic socket options can also be applied to TCP sockets:

SO_KEEPALIVE
Enables the sending of keep-alive messages on the connection. When enabled, the kernel periodically sends a probe packet to the peer. If the peer does not respond after a certain number of probes, the connection is considered broken, and an error is reported to the application.
SO_LINGER
Controls the behavior of close(2) on a connection-oriented socket. If linger is disabled (l_onoff is 0), close(2) returns immediately, and the system attempts to send any unsent data in the background. If linger is enabled (l_onoff is 1) and the linger timeout (l_linger) is zero, pending data is discarded and the connection is reset. If linger is enabled and the timeout is non-zero, close(2) blocks until all data is sent or the timeout expires.
SO_RCVBUF
Sets or gets the size of the socket's receive buffer. A larger buffer can improve throughput by allowing the application to consume data faster than it arrives, reducing the likelihood of packet loss due to buffer overflows.
SO_SNDBUF
Sets or gets the size of the socket's send buffer. A larger buffer allows the application to send data more quickly without being blocked by the network congestion or the receiver's ability to process data.

Urgent data

TCP supports the concept of "urgent" data. When urgent data is sent, the sender notifies the receiver that the data is important and should be processed quickly. This is typically used for transmitting control commands or out-of-band signals.

Applications can send urgent data using the MSG_OOB flag with send(2) or sendmsg(2). Receiving urgent data requires the MSG_OOB flag with recv(2).

When urgent data is present, the application can be notified via a select(2) call (using the exceptfds argument) or through delivery of a SIGURG signal. The urgent data is located at the end of the regular data buffer. A read never reads across the urgent mark.

If an application is informed of the presence of urgent data, it can advance up to the mark using a loop which repeatedly tests SIOCATMARK and performs a read (requesting any number of bytes) as long as SIOCATMARK returns false.

SIOCATMARK
This ioctl(2) command checks if the read pointer is currently at the urgent mark. Returns true if the current read position is at the urgent mark, false otherwise. This is used to determine when all urgent data has been read.
SIOCOUTQ
Returns the amount of unsent data in the socket send queue. The socket must not be in LISTEN state, otherwise an error (EINVAL) is returned. SIOCOUTQ is defined in <linux/sockios.h>. Alternatively, you can use the synonymous TIOCOUTQ, defined in <sys/ioctl.h>.

Error handling

When a network error occurs, TCP tries to resend the packet. If it doesn't succeed after some time, either ETIMEDOUT or the last received error on this connection is reported.

Some applications require a quicker error notification. This can be enabled with the IPPROTO_IP level IP_RECVERR socket option. When this option is enabled, all incoming errors are immediately passed to the user program. Use this option with care — it makes TCP less tolerant to routing changes and other normal network conditions.

ERRORS

EAFNOTSUPPORT
Passed socket address type in sin_family was not AF_INET.
EPIPE
The other end closed the socket unexpectedly or a read is executed on a shut down socket.
ETIMEDOUT
The other end didn't acknowledge retransmitted data after some time.

Any errors defined for ip(7) or the generic socket layer may also be returned for TCP.
