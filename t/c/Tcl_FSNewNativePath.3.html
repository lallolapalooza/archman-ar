الوصف

هناك عدة أسباب لاستدعاء دوال واجهة برمجة تطبيقات Tcl_FS (على سبيل المثال، Tcl_FSAccess و Tcl_FSStat) بدلاً من استدعاء دوال النظام مثل access و stat مباشرة. أولاً، ستعمل هذه الدوال عبر المنصات، لذا يجب أن يعمل الامتداد الذي يستدعيها دون تعديل على Unix و Windows. ثانياً، يقوم تطبيق Windows لبعض هذه الدوال بإصلاح بعض الأخطاء في استدعاءات مستوى النظام. ثالثاً، تتعامل استدعاءات الدوال هذه مع أي تحويلات مسار من “Utf إلى متخفي النظام” قد تكون مطلوبة (وقد تقوم بتخزين نتائج هذه التحويلات مؤقتًا لزيادة الكفاءة في الاستدعاءات اللاحقة). رابعاً، ولعل الأهم من ذلك، أن جميع هذه الدوال “تدرك نظام الملفات الافتراضي”. أي نظام ملفات افتراضي (VFS للاختصار) تم تسجيله (من خلال Tcl_FSRegister) قد يعيد توجيه الوصول إلى الملفات إلى وسائط بديلة أو طرق وصول بديلة. هذا يعني أن جميع هذه الدوال (وبالتالي أوامر Tcl المقابلة مثل file و glob و pwd و cd و open، إلخ) يمكن أن تعمل على “ملفات” ليست ملفات أصلية في نظام الملفات الأصلي. هذا يعني أيضًا أن أي امتداد Tcl يصل إلى نظام الملفات (FS للاختصار) من خلال واجهة برمجة التطبيقات هذه يكون تلقائيًا “مدركًا لنظام الملفات الافتراضي”. بالطبع، إذا قام امتداد بالوصول إلى نظام الملفات الأصلي مباشرة (من خلال واجهات برمجة التطبيقات الخاصة بالمنصة، على سبيل المثال)، فلا يمكن لـ Tcl اعتراض هذه الاستدعاءات.

إذا تم تسجيل أنظمة ملفات افتراضية مناسبة، فقد تكون “الملفات”، لتقديم مثالين، بعيدة (على سبيل المثال، موجودة على خادم ftp بعيد) أو مؤرشفة (على سبيل المثال، داخل أرشيف .zip). توفر أنظمة الملفات المسجلة هذه جدول بحث للدوال لتنفيذ كل أو بعض الوظائف المدرجة هنا. أخيرًا، تقوم استدعاءات Tcl_FSStat و Tcl_FSLstat بتجريد مخزن مؤقت “struct stat” مما هو عليه فعليًا، مما يسمح باستخدام نفس الكود على الأنظمة التي تدعم الملفات الأكبر من 2 جيجابايت والأنظمة التي لا تدعمها.

تم تحويل واجهة برمجة تطبيقات Tcl_FS إلى Tcl_Obj وقد تقوم بتخزين التمثيلات الداخلية والسلاسل النصية المتعلقة بالمسار مؤقتًا (على سبيل المثال، دليل العمل الحالي). أحد الآثار الجانبية لذلك هو أنه لا يجوز تمرير قيم ذات عدد مراجع صفر إلى أي من هذه الدوال. إذا تم التعامل مع هذه الاستدعاءات، فقد تؤدي إلى تسرب في الذاكرة (في ظل بعض الظروف، قد يرغب رمز نظام الملفات في الاحتفاظ بمرجع للقيمة التي تم تمريرها، وبالتالي لا يجب افتراض أنه بعد عودة أي من هذه الاستدعاءات، لا تزال القيمة تمتلك عدد مراجع صفر - قد تكون قد تم زيادتها) أو خطأ تجزئة مباشر (أو خطأ وصول آخر إلى الذاكرة) بسبب تحرير القيمة في منتصف معالجة القيمة المعقدة اللازمة لضمان أن المسار طبيعي وكامل ونسبي لتحديد نظام الملفات. الدرس العملي المستفاد من هذا هو أن

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

هو خطأ، وقد يتسبب في أخطاء في الذاكرة. يجب زيادة عدد مراجع path قبل تمريرها، أو تقليلها. لهذا السبب، تعتبر القيم ذات عدد مراجع صفر غير صالحة كمسارات لنظام الملفات، وسيؤدي استدعاء أي دالة واجهة برمجة تطبيقات Tcl_FS بقيمة كهذه إلى عدم اتخاذ أي إجراء.

دوال واجهة برمجة تطبيقات FS

Tcl_FSCopyFile تحاول نسخ الملف المعطى بواسطة srcPathPtr إلى اسم المسار المعطى بواسطة destPathPtr. إذا كان المساران المعطيان يقعان في نفس نظام الملفات (وفقًا لـ Tcl_FSGetFileSystemForPath) فسيتم استدعاء دالة “نسخ ملف” لنظام الملفات هذا (إذا لم تكن NULL). وإلا، فإن الدالة ترجع -1 وتعين المتغير العام C errno إلى رمز خطأ POSIX “EXDEV” (الذي يشير إلى “رابط عبر النطاقات”).

Tcl_FSCopyDirectory تحاول نسخ الدليل المعطى بواسطة srcPathPtr إلى اسم المسار المعطى بواسطة destPathPtr. إذا كان المساران المعطيان يقعان في نفس نظام الملفات (وفقًا لـ Tcl_FSGetFileSystemForPath) فسيتم استدعاء دالة “نسخ ملف” لنظام الملفات هذا (إذا لم تكن NULL). وإلا، فإن الدالة ترجع -1 وتعين المتغير العام C errno إلى رمز خطأ POSIX “EXDEV” (الذي يشير إلى “رابط عبر النطاقات”).

Tcl_FSCreateDirectory تحاول إنشاء الدليل المعطى بواسطة pathPtr عن طريق استدعاء دالة “إنشاء دليل” لنظام الملفات المالك.

Tcl_FSDeleteFile تحاول حذف الملف المعطى بواسطة pathPtr عن طريق استدعاء دالة “حذف ملف” لنظام الملفات المالك.

Tcl_FSRemoveDirectory تحاول إزالة الدليل المعطى بواسطة pathPtr عن طريق استدعاء دالة “إزالة دليل” لنظام الملفات المالك.

Tcl_FSRenameFile تحاول إعادة تسمية الملف أو الدليل المعطى بواسطة srcPathPtr إلى اسم المسار المعطى بواسطة destPathPtr. إذا كان المساران المعطيان يقعان في نفس نظام الملفات (وفقًا لـ Tcl_FSGetFileSystemForPath) فسيتم استدعاء دالة “إعادة تسمية ملف” لنظام الملفات هذا (إذا لم تكن NULL). وإلا، فإن الدالة ترجع -1 وتعين المتغير العام C errno إلى رمز خطأ POSIX “EXDEV” (الذي يشير إلى “رابط عبر النطاقات”).

Tcl_FSListVolumes يستدعي كل نظام ملفات لديه دالة “قائمة وحدات التخزين” غير NULL ويطلب منها إرجاع قائمة وحدات التخزين الجذرية الخاصة بها. يقوم بتجميع القيم المرتجعة في قائمة يتم إرجاعها إلى المتصل (بعدد مراجع 0).

Tcl_FSEvalFileEx يقرأ الملف المعطى بواسطة pathPtr باستخدام الترميز المحدد بواسطة encodingName ويقيّم محتوياته كبرنامج نصي Tcl. يقوم بإرجاع نفس المعلومات مثل Tcl_EvalObjEx. إذا كان encodingName هو NULL، يتم استخدام الترميز النظامي لقراءة محتويات الملف. إذا لم يكن من الممكن قراءة الملف، يتم إرجاع خطأ Tcl لوصف سبب عدم إمكانية قراءة الملف. حرف نهاية الملف للملفات هو “\x1A” (^Z) لجميع الأنظمة الأساسية. إذا كنت تتطلب “^Z” في الكود للمقارنة النصية، يمكنك استخدام “\x1A”، والذي سيتم استبداله بأمان بواسطة مترجم Tcl إلى “^Z”. FILESYSTEM INTERFACE

The filesystem interface is designed to be extensible, and Tcl provides support for several distinct filesystems. This is accomplished by allowing filesystems to be registered with Tcl's core, and for those filesystems to be accessed by the standard Tcl file I/O commands, and by the Tcl C API file functions.

The following functions are exported by the Tcl library for use in implementing Tcl extensions that manipulate files.

PATH MANIPULATION

Tcl_FSGetNormalizedPath returns a pointer to a Tcl object containing the normalized path for the given path. Normalization involves resolving symbolic links, eliminating redundant components like “.” and “..”, and ensuring that the path is represented in a canonical form. This function may allocate memory, and the caller is responsible for freeing it using ckfree.

Tcl_FSGetTranslatedPath is similar to Tcl_FSGetNormalizedPath, but it additionally translates the path through intermediate virtual filesystems. This is useful when a path might be represented in multiple ways or pass through different filesystem layers.

Tcl_FSGetNativePath returns a pointer to a Tcl object containing the native path representation. This is the form typically used by the underlying operating system. The returned object is owned by Tcl and must not be freed by the caller. Its lifetime is tied to the lifetime of the input path object.

Tcl_FSNewNativePath creates a Tcl object representing a path in its native form. This is useful when you have a path string in the native encoding of the operating system and want to represent it as a Tcl path object. The caller is responsible for the returned Tcl object, which must be stored or freed using ckfree. Again, Tcl_FSGetNormalizedPath or Tcl_FSGetNativePath are usually better functions to use for most purposes.

Tcl_FSNewNativePath performs something like the reverse of the usual obj->path->nativerep conversions. If some code retrieves a path in native form (from, e.g. readlink or a native dialog), and that path is to be used at the Tcl level, then calling this function is an efficient way of creating the appropriate path value type.

The resulting value is a pure “path” value, which will only receive a UTF-8 string representation if that is required by some Tcl code.

Tcl_FSGetNativePath is for use by the Win/Unix native filesystems, so that they can easily retrieve the native (char* or TCHAR*) representation of a path. This function is a convenience wrapper around Tcl_FSGetInternalRep. It may be desirable in the future to have non-string-based native representations (for example, on macOS, a representation using a fileSpec of FSRef structure would probably be more efficient). On Windows a full Unicode representation would allow for paths of unlimited length. Currently the representation is simply a character string which may contain either the relative path or a complete, absolute normalized path in the native encoding (complex conditions dictate which of these will be provided, so neither can be relied upon, unless the path is known to be absolute). If you need a native path which must be absolute, then you should ask for the native version of a normalized path. If for some reason a non-absolute, non-normalized version of the path is needed, that must be constructed separately (e.g. using Tcl_FSGetTranslatedPath).

The native representation is cached so that repeated calls to this function will not require additional conversions. The return value is owned by Tcl and has a lifetime equivalent to that of the pathPtr passed in (unless that is a relative path, in which case the native representation may be freed any time the cwd changes).

Tcl_FSFileSystemInfo returns a list of two elements. The first element is the name of the filesystem (e.g. “native”, “vfs”, “zip”, or “prowrap”, perhaps), and the second is the particular type of the given path within that filesystem (which is filesystem dependent). The second element may be empty if the filesystem does not provide a further categorization of files.

A valid list value is returned, unless the path value is not recognized, when NULL will be returned.

Tcl_FSGetFileSystemForPath returns a pointer to the Tcl_Filesystem which accepts this path as valid.

If no filesystem will accept the path, NULL is returned.

Tcl_FSGetPathType determines whether the given path is relative to the current directory, relative to the current volume, or absolute.

It returns one of TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE, or TCL_PATH_VOLUME_RELATIVE

THE VIRTUAL FILESYSTEM API

A filesystem provides a Tcl_Filesystem structure that contains pointers to functions that implement the various operations on a filesystem; these operations are invoked as needed by the generic layer, which generally occurs through the functions listed above.

The Tcl_Filesystem structures are manipulated using the following methods.

Tcl_FSRegister takes a pointer to a filesystem structure and an optional piece of data to associated with that filesystem. On calling this function, Tcl will attach the filesystem to the list of known filesystems, and it will become fully functional immediately. Tcl does not check if the same filesystem is registered multiple times (and in general that is not a good thing to do). TCL_OK will be returned.

Tcl_FSUnregister removes the given filesystem structure from the list of known filesystems, if it is known, and returns TCL_OK. If the filesystem is not currently registered, TCL_ERROR is returned.

Tcl_FSData will return the clientData associated with the given filesystem, if that filesystem is registered. Otherwise it will return NULL.

Tcl_FSMountsChanged is used to inform the Tcl's core that the set of mount points for the given (already registered) filesystem have changed, and that cached file representations may therefore no longer be correct.

Except for the first three fields in this structure which contain simple data elements, all entries contain addresses of functions called by the generic filesystem layer to perform the complete range of filesystem related actions.

The many functions in this structure are broken down into three categories: infrastructure functions (almost all of which must be implemented), operational functions (which must be implemented if a complete filesystem is provided), and efficiency functions (which need only be implemented if they can be done so efficiently, or if they have side-effects which are required by the filesystem; Tcl has less efficient emulations it can fall back on). It is important to note that, in the current version of Tcl, most of these fallbacks are only used to handle commands initiated in Tcl, not in C. What this means is, that if a file rename command is issued in Tcl, and the relevant filesystem(s) do not implement their Tcl_FSRenameFileProc, Tcl's core will instead fallback on a combination of other filesystem functions (it will use Tcl_FSCopyFileProc followed by Tcl_FSDeleteFileProc, and if Tcl_FSCopyFileProc is not implemented there is a further fallback). However, if a Tcl_FSRenameFileProc command is issued at the C level, no such fallbacks occur. This is true except for the last four entries in the filesystem table (lstat, load, getcwd and chdir) for which fallbacks do in fact occur at the C level.

Any functions which take path names in Tcl_Obj form take those names in UTF-8 form. The filesystem infrastructure API is designed to support efficient, cached conversion of these UTF-8 paths to other native representations.

Tcl_FSOpenFileChannelProc

وظيفة لمعالجة استدعاء Tcl_FSOpenFileChannel. يجب تنفيذها لأي نظام ملفات معقول، حيث أن أي عمليات تتطلب فتح أو الوصول إلى محتويات ملف ستستخدمها (مثل open، encoding، والعديد من أوامر Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

تقوم Tcl_FSOpenFileChannelProc بفتح ملف محدد بواسطة pathPtr وتعيد مقبض قناة يمكن استخدامه لإجراء الإدخال والإخراج على الملف. هذه الواجهة البرمجية مستوحاة من الإجراء fopen لمكتبة الإدخال / الإخراج القياسية في Unix. بناء الجملة ومعنى جميع الوسائط مشابهة لتلك المقدمة في أمر Tcl open عند فتح ملف، حيث أن الوسيط mode هو مزيج من علامات POSIX O_RDONLY، O_WRONLY، إلخ. إذا حدث خطأ أثناء فتح القناة، فإن Tcl_FSOpenFileChannelProc يعيد NULL ويسجل رمز خطأ POSIX يمكن استرداده باستخدام Tcl_GetErrno. بالإضافة إلى ذلك، إذا كان interp غير NULL، فإن Tcl_FSOpenFileChannelProc يترك رسالة خطأ في نتيجة interp بعد أي خطأ.

يجب ألا يتم تسجيل القناة التي تم إنشاؤها حديثًا في المترجم المقدم بواسطة Tcl_FSOpenFileChannelProc؛ هذه المهمة تقع على عاتق المستدعي لـ Tcl_FSOpenFileChannel (إذا لزم الأمر). إذا تم إغلاق إحدى القنوات القياسية، stdin، stdout أو stderr، مسبقًا، فإن فعل إنشاء القناة الجديدة يعينها أيضًا كبديل للقناة القياسية.

        Tcl_GlobTypeData *types);

يجب أن تعيد الوظيفة جميع الملفات أو الأدلة (أو كائنات نظام الملفات الأخرى) التي تطابق النمط المحدد وتتوافق مع مواصفات types المقدمة. هناك طريقتان يمكن استدعاء هذه الوظيفة بهما. إذا كان pattern هو NULL، فإن pathPtr هو مواصفات مسار كامل لملف واحد أو دليل يجب التحقق من وجوده ونوعه الصحيح. بخلاف ذلك، pathPtr هو دليل، ويجب على الوظيفة البحث في محتوياته عن ملفات أو أدلة ذات نوع صحيح. في كلتا الحالتين، يمكن افتراض أن pathPtr ليس NULL ولا فارغًا. لم يتم توثيق ما إذا كان pathPtr سيحتوي على فاصل ملف في نهايته أم لا، لذا يجب أن يكون الكود مرنًا لكلا الاحتمالين.

القيمة المرجعة هي نتيجة Tcl قياسية تشير إلى ما إذا كان قد حدث خطأ في عملية المطابقة. يتم وضع رسائل الخطأ في interp، ما لم يكن interp هو NULL في هذه الحالة لا يلزم إنشاء رسالة خطأ؛ عند نتيجة TCL_OK، يجب إضافة النتائج إلى قيمة resultPtr المقدمة (والتي يمكن افتراض أنها قائمة Tcl صالحة وغير مشتركة). يجب أن تتضمن التطابقات المضافة إلى resultPtr أي بادئة مسار مقدمة في pathPtr (هذا يعني عادةً أنها ستكون مواصفات مسار مطلقة). لاحظ أنه إذا لم يتم العثور على تطابقات، فهذا يؤدي ببساطة إلى نتيجة فارغة؛ يتم الإشارة إلى الأخطاء فقط للمشاكل الفعلية في الملف أو نظام الملفات التي قد تحدث أثناء عملية المطابقة.

        Tcl_Obj *toPtr,
        int linkAction);

إذا كان toPtr هو NULL، يُطلب من الوظيفة قراءة محتويات رابط. النتيجة هي Tcl_Obj يحدد محتويات الرابط المعطى بواسطة linkNamePtr، أو NULL إذا تعذر قراءة الرابط. النتيجة مملوكة للمستدعي (وبالتالي يجب زيادة عداد المراجع الخاص بها قبل إعادتها). يجب على أي مستدعين استدعاء Tcl_DecrRefCount لهذه النتيجة عندما لم تعد هناك حاجة إليها. إذا كان toPtr غير NULL، يجب على الوظيفة محاولة إنشاء رابط. يجب أن تكون النتيجة في هذه الحالة هي toPtr إذا كان الرابط ناجحًا، وNULL بخلاف ذلك. في هذه الحالة، النتيجة غير مملوكة للمستدعي (أي لا حاجة إلى معالجة عدادات المراجع من أي طرف). انظر توثيق Tcl_FSLink للتفسير الصحيح لعلامات linkAction.

LISTVOLUMESPROC

وظيفة لإدراج أي وحدات نظام ملفات تمت إضافتها بواسطة نظام الملفات هذا. يجب تنفيذها فقط إذا كان نظام الملفات يضيف وحدات في بداية نظام الملفات، بحيث يمكن إرجاعها بواسطة file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

يجب أن تكون النتيجة قائمة بوحدات النظام التي أضافها نظام الملفات هذا، أو NULL (أو قائمة فارغة) إذا لم يتم توفير وحدات. تعتبر قيمة النتيجة مملوكة لنظام الملفات (وليس لنواة Tcl)، ولكن يجب منحها عداد مراجع لـ Tcl. ستستخدم Tcl محتويات القائمة ثم تقلل عداد المراجع هذا. هذا يسمح لأنظمة الملفات باختيار ما إذا كانت تريد بالفعل الاحتفاظ بـ "قائمة عالمية" للوحدات أم لا (إذا لم يكن الأمر كذلك، فإنها تنشئ القائمة ديناميكيًا وتمررها إلى Tcl مع عداد مراجع 1 ثم تنسى الأمر بشأن القائمة، وإذا كان الأمر كذلك، فإنها ببساطة تزيد عداد مراجع قائمتها العالمية وتمررها إلى Tcl التي ستنسخ المحتويات ثم تقلل العداد مرة أخرى إلى حيث كان).

لذلك، تعتبر Tcl القيم المرجعة من هذه الوظيفة للقراءة فقط.

FILEATTRSTRINGSPROC

وظيفة لإدراج جميع سلاسل السمات الصالحة لنظام الملفات هذا. إذا لم يتم تنفيذها، فلن يدعم نظام الملفات أمر file attributes. هذا يسمح بإرفاق معلومات إضافية عشوائية بالملفات في نظام الملفات. إذا لم يتم تنفيذها، فلا حاجة لتنفيذ طرق get و set.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

قد تعيد الوظيفة المستدعاة مصفوفة من السلاسل، أو قد تعيد NULL وتضع قائمة Tcl في objPtrRef المقدم. ستأخذ Tcl هذه القائمة وتزيد عداد المراجع الخاص بها أولاً قبل استخدامها. عند اكتمال هذا الاستخدام، ستقوم Tcl بتقليل عداد المراجع الخاص بها. لذلك، إذا كان يجب التخلص من القائمة بواسطة Tcl عند الانتهاء، فيجب أن يكون عداد المراجع الخاص بها صفرًا، وإذا كان يجب عدم التخلص من القائمة، فيجب على نظام الملفات التأكد من إرجاع قيمة مع عداد مراجع لا يقل عن واحد.

FILEATTRSGETPROC

وظيفة لمعالجة استدعاء Tcl_FSFileAttrsGet، والتي يستخدمها file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

تعيد رمز استجابة Tcl قياسي. قيمة السمة التي تم استردادها، والتي تتوافق مع العنصر ذي index في القائمة التي تم إرجاعها بواسطة Tcl_FSFileAttrStringsProc، هي Tcl_Obj تم وضعه في objPtrRef (إذا تم إرجاع TCL_OK) ومن المحتمل أن يكون عداد المراجع الخاص بها صفرًا. في كلتا الحالتين، يجب علينا إما تخزينها في مكان ما (مثل نتيجة Tcl)، أو زيادة/تقليل عداد المراجع الخاص بها لضمان تحريرها بشكل صحيح.

FILEATTRSSETPROC

وظيفة لمعالجة استدعاء Tcl_FSFileAttrsSet، والتي يستخدمها file attributes. إذا كان نظام الملفات للقراءة فقط، فلا داعي لتنفيذ هذا.

typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);

يجب تعيين قيمة السمة للعنصر ذي index في القائمة التي تم إرجاعها بواسطة Tcl_FSFileAttrStringsProc إلى objPtr المقدم.
