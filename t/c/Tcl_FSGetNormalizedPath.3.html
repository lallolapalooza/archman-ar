DESCRIPTION

Il existe plusieurs raisons d'appeler les fonctions de l'API Tcl_FS (par exemple, Tcl_FSAccess et Tcl_FSStat) plutôt que d'appeler directement des fonctions de niveau système comme access et stat. Premièrement, ces fonctions fonctionneront de manière multiplateforme, de sorte que toute extension qui les appelle doit fonctionner sans modification sur Unix et Windows. Deuxièmement, l'implémentation de certaines de ces fonctions sous Windows corrige certains bogues dans les appels de niveau système. Troisièmement, ces appels gèrent toute conversion de chemin d'accès "UTF vers plateforme native" qui peut être nécessaire (et peuvent mettre en cache les résultats de ces conversions pour une meilleure efficacité lors d'appels ultérieurs). Quatrièmement, et peut-être le plus important, toutes ces fonctions sont "virtually file system aware" (conscientes du système de fichiers virtuel). Tout système de fichiers virtuel (VFS en abrégé) enregistré (via Tcl_FSRegister) peut réorienter l'accès aux fichiers vers des supports ou des méthodes d'accès alternatifs. Cela signifie que toutes ces fonctions (et par conséquent, les commandes Tcl correspondantes file, glob, pwd, cd, open, etc.) peuvent fonctionner avec des fichiers qui ne sont pas des fichiers natifs sur le système de fichiers natif. Cela signifie également que toute extension Tcl qui accède au système de fichiers (FS en abrégé) via cette API devient automatiquement "virtually file system aware". Bien sûr, si une extension accède directement au système de fichiers natif (via des API spécifiques au système, par exemple), Tcl ne peut pas intercepter de tels appels.

Si des VFS ont été enregistrés correctement, les "fichiers" peuvent être, par exemple, distants (comme s'ils se trouvaient sur un serveur ftp distant) ou archivés (comme s'ils se trouvaient dans un fichier .zip). Ces VFS enregistrés fournissent une carte de fonctions pour implémenter tout ou partie de la fonctionnalité mentionnée ici. Enfin, les appels à Tcl_FSStat et Tcl_FSLstat abstraient le contenu du tampon struct stat, permettant d'utiliser le même code sur les systèmes qui prennent en charge les fichiers de plus de 2 Go et ceux qui ne le font pas.

L'API Tcl_FS est "typiquement" une Tcl_Obj et peut mettre en cache des représentations internes et d'autres chaînes liées aux chemins d'accès (par exemple, le répertoire courant). Un effet secondaire de ceci est que vous ne devez passer à aucune fonction des valeurs avec un compteur de références nul. Si vous le faisiez, cela pourrait entraîner des fuites de mémoire (dans certains cas, le code du système de fichiers pourrait supprimer une référence à la valeur passée, et vous ne devriez donc pas supposer qu'après tout appel à ces fonctions, la valeur a toujours un compteur de références nul - il pourrait avoir été incrémenté). Ou, cela pourrait provoquer une défaillance de segmentation (ou une autre erreur d'accès mémoire) car la valeur pourrait avoir été libérée pendant la manipulation complexe des valeurs pour normaliser et rendre le chemin absolu. La leçon pratique à retenir est que

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

est incorrect et peut entraîner des erreurs de mémoire. Le path doit voir son compteur de références incrémenté avant d'être passé, ou décrémenté. Pour cette raison, les valeurs avec un compteur de références nul sont considérées comme invalides en tant que chemins de système de fichiers et tout appel à une fonction de l'API Tcl_FS avec de telles valeurs n'entraînera aucune action.

FS API FUNCTIONS

Tcl_FSCopyFile tente de copier le fichier donné par srcPathPtr vers le chemin donné par destPathPtr. Si les deux chemins donnés sont sur le même système de fichiers (tel que déterminé par Tcl_FSGetFileSystemForPath), la fonction de copie de fichier du système de fichiers est appelée. Sinon, la fonction renvoie -1 et définit la valeur globale C errno à EXDEV (code POSIX indiquant un "cross-device link").

Tcl_FSCopyDirectory tente de copier le répertoire donné par srcPathPtr vers le chemin donné par destPathPtr. Si les deux chemins donnés sont sur le même système de fichiers (tel que déterminé par Tcl_FSGetFileSystemForPath), la fonction de copie de répertoire du système de fichiers est appelée. Sinon, la fonction renvoie -1 et définit la valeur globale C errno à EXDEV (code POSIX indiquant un "cross-device link").

Tcl_FSCreateDirectory tente de créer le répertoire donné par pathPtr en appelant la fonction de création de répertoire du système de fichiers qui le possède.

Tcl_FSDeleteFile tente de supprimer le fichier donné par pathPtr en appelant la fonction de suppression de fichier du système de fichiers qui le possède.

Tcl_FSRemoveDirectory tente de supprimer le répertoire donné par pathPtr en appelant la fonction de suppression de répertoire du système de fichiers qui le possède.

Tcl_FSRenameFile tente de renommer le fichier ou le répertoire donné par srcPathPtr vers le chemin donné par destPathPtr. Si les deux chemins donnés sont sur le même système de fichiers (tel que déterminé par Tcl_FSGetFileSystemForPath), la fonction de renommage de fichier du système de fichiers est appelée. Sinon, la fonction renvoie -1 et définit la valeur globale C errno à EXDEV (code POSIX indiquant un "cross-device link").

Tcl_FSListVolumes appelle chaque système de fichiers qui a une fonction de "liste de volumes" non nulle et leur demande de renvoyer leur liste de volumes racine. Elle accumule les valeurs renvoyées dans une liste qui est renvoyée à l'appelant (avec un compteur de références 0).

Tcl_FSEvalFileEx lit le contenu du fichier donné par pathPtr en utilisant le nom de codage identifié par encodingName et évalue son contenu comme un script Tcl. Elle renvoie les mêmes informations que Tcl_EvalObjEx. Si encodingName est NULL, la page de code du système est utilisée pour lire le contenu du fichier. Si le fichier ne peut pas être lu, une erreur Tcl est renvoyée pour décrire pourquoi il ne peut pas être lu. Le caractère EOF pour les fichiers est \x1A (^Z) pour tous les systèmes. Si vous souhaitez avoir ^Z dans le code de comparaison de chaînes, vous pouvez utiliser \x1A, qui sera probablement remplacé par l'interpréteur Tcl par ^Z. Tcl_FSEvalFile est une version plus simple de Tcl_FSEvalFileEx qui utilise toujours la page de code du système lors de la lecture du fichier.

Tcl_FSLoadFile charge dynamiquement un fichier binaire en mémoire et renvoie les adresses de deux procédures dans ce fichier, si elles sont définies. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée. Si ce système de fichiers n'implémente pas cette fonction (la plupart des systèmes de fichiers virtuels ne le feront pas en raison des limitations du système sur le chargement de code binaire), Tcl tentera de copier le fichier dans un répertoire temporaire et de charger ce fichier temporaire. Tcl_FSUnloadFile annule cette opération, demandant que le livre indiqué par loadHandle soit déchargé du processus. Notez que, contrairement à la commande unload, cela ne donne aucune chance au livre de se nettoyer.

Les deux fonctions mentionnées ci-dessus renvoient un code d'achèvement Tcl standard. Si une erreur se produit, un message d'erreur est laissé dans le résultat de l' interp.

Le jeton fourni par la variable indiquée par loadHandlePtr peut être utilisé avec Tcl_FindSymbol.

Tcl_FSMatchInDirectory est utilisé par le code de globbing pour rechercher tous les fichiers correspondant à un motif donné dans un répertoire. La fonction appropriée pour le système de fichiers auquel appartient pathPtr sera appelée.

La valeur renvoyée est un résultat Tcl standard indiquant s'il y a eu une erreur dans le globbing. Les messages d'erreur sont placés dans interp (sauf si interp est NULL, ce qui est autorisé), mais les bons résultats sont placés dans resultPtr donné.

Notez que le code glob implémente les motifs récursifs en interne, de sorte que cette fonction ne recevra que des motifs simples, qui peuvent être mis en correspondance avec la logique de string match. Pour gérer la récursion, Tcl appellera cette fonction fréquemment en demandant uniquement aux répertoires d'être renvoyés. Une exception spéciale d'appel avec un motif nul indique que le chemin doit simplement être vérifié pour le bon type.

Tcl_FSLink remplace la version de bibliothèque de readlink et l'étend pour prendre en charge la création de liens. La fonction appropriée pour le système de fichiers auquel appartient linkNamePtr sera appelée.

Si toPtr est NULL, une action de "lecture de lien" sera effectuée. Le résultat est un objet Tcl spécifiant le contenu du lien donné par linkNamePtr, ou NULL si le lien ne peut pas être lu. Le résultat est tout ce dont l'appelant doit se soucier, qui doit appeler Tcl_DecrRefCount lorsque le résultat n'est plus nécessaire. Si toPtr n'est pas NULL, Tcl doit créer un lien d'un des types de liens passés dans le linkAction du drapeau. Ce drapeau est une combinaison OR de TCL_CREATE_SYMBOLIC_LINK et TCL_CREATE_HARD_LINK. S'il y a un choix (c'est-à-dire que plus d'un drapeau est passé), la convention Tcl est de préférer les liens symboliques. Lorsqu'un lien est créé avec succès, la valeur renvoyée doit être toPtr (qui est donc déjà à la charge de l'appelant). S'il ne peut pas être créé, NULL est renvoyé.

Tcl_FSLstat remplit la structure Tcl_StatBuf statPtr avec des informations sur le fichier spécifié. Aucun droit d'accès au fichier n'est nécessaire pour obtenir ces informations, mais des droits de recherche sur les répertoires qui composent le chemin d'accès au fichier sont nécessaires. La structure Tcl_StatBuf contient des informations sur le périphérique, l'i-node (toujours 0 sous Windows), le mode de privilège, le nlink (toujours 1 sous Windows), l'utilisateur id (toujours 0 sous Windows), le groupe id (toujours 0 sous Windows), rdev (identique au périphérique sous Windows), la taille, la date

بنية نظام الملفات

تحتوي هذه الحقول على معلومات أساسية حول بنية نظام الملفات وعناوين الدوال التي تستخدم لربط نظام ملفات معين بمسار ملف، ولإدارة التمثيل الداخلي لمسارات الملفات، على سبيل المثال، نسخ هذه التمثيلات وتحريرها.

اسم النوع

يحتوي الحقل typeName على سلسلة منتهية بفارغ تعرف نوع نظام الملفات الذي تم تنفيذه، على سبيل المثال، native، zip أو vfs.

طول البنية

عادةً ما يتم تنفيذ الحقل structureLength على أنه sizeof(Tcl_Filesystem)، وهو موجود للسماح بالتوافق الثنائي مع التوافق الرجعي في الإصدارات المستقبلية من Tcl إذا تغير حجم البنية.

الإصدار

يحتوي الحقل pathInFilesystemProc على عنوان دالة يتم استدعاؤها لتحديد ما إذا كانت قيمة مسار معينة تنتمي إلى نظام الملفات هذا أم لا. ستستدعي Tcl فقط باقي دوال نظام الملفات بمسار أعادت له هذه الدالة TCL_OK. إذا كان المسار لا ينتمي، فسيتم إرجاع -1 (سلوك Tcl للقيم الأخرى المعادة غير محدد). إذا تم إرجاع TCL_OK، يمكن استخدام المعلمة الاختيارية clientDataPtr لإرجاع تمثيل داخلي (خاص بنظام الملفات) للمسار، والذي سيتم تخزينه داخل قيمة المسار، ويمكن استعادته بكفاءة بواسطة دوال أنظمة الملفات الأخرى من نوع مختلف. ستقوم Tcl في نفس الوقت بتخزين حقيقة أن هذا المسار ينتمي إلى نظام الملفات هذا. سيتم إبطال مثل هذه المخازن المؤقتة عند إضافة أو إزالة أنظمة الملفات من القائمة الداخلية لأنظمة الملفات المعروفة لدى Tcl.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

typedef ClientData Tcl_FSDupInternalRepProc(

دالة تسوية المسار

دالة لتسوية المسار. يجب تنفيذها لجميع أنظمة الملفات التي قد يكون لديها تمثيلات نصية متعددة لنفس قيمة المسار. في Tcl، يجب أن يكون لكل مسار تمثيل طبيعي فريد. اعتمادًا على نظام الملفات، قد يكون هناك أكثر من تمثيل غير طبيعي يشير إلى نفس المسار (على سبيل المثال، مسار نسبي، مسار بحالة أحرف مختلفة إذا كان نظام الملفات غير حساس لحالة الأحرف، مسار يحتوي على دليل مشار إليه مثل ~، مسار يحتوي على روابط رمزية، إلخ). إذا كان المكون الأخير للمسار هو رابط رمزي، فلا يجب تحويله إلى القيمة التي يشير إليها (ولكن يجب جعل حالة أحرفه أو جوانب أخرى فريدة). يجب تحويل جميع المكونات الأخرى للمسار من الروابط الرمزية. هذا الاستثناء مطلوب للمواءمة مع سلوك Tcl لأوامر file delete، file rename، file copy عند العمل مع الروابط الرمزية. يمكن استدعاء هذه الدالة مع nextCheckpoint في بداية المسار (أي صفر)، أو في نهاية المسار، أو في أي نقطة فاصلة ملف في المسار. لن تشير أبدًا إلى أي موضع عشوائي في المسار. في الحالة الأخيرة من الحالات الثلاث الصالحة، يمكن للمنفذ افتراض أن المسار حتى الفاصلة الملف بما في ذلك معروف وطبيعي.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

عمليات نظام الملفات

تحتوي حقول هذا القسم من البنية على عناوين الدوال التي يتم استدعاؤها لتنفيذ عمليات نظام الملفات الأساسية. يجب على نظام الملفات الذي يتوقع استخدامه مع مجموعة الأوامر القياسية الكاملة لـ Tcl تنفيذ كل هذه الأوامر. إذا لم يتم تنفيذ بعضها، فقد تفشل أوامر Tcl معينة عند تشغيلها على مسارات داخل نظام الملفات هذا. ومع ذلك، في بعض الحالات قد يكون هذا مرغوبًا (على سبيل المثال، يجب ألا ينفذ نظام الملفات للقراءة فقط الأربع دوال الأخيرة، ونظام الملفات الذي لا يدعم الروابط الرمزية يجب ألا ينفذ دالة readlink، إلخ). تتوقع نواة Tcl أن تتصرف أنظمة الملفات بهذه الطريقة.

دالة stat

دالة تعالج استدعاء Tcl_FSStat. يجب تنفيذها لأي نظام ملفات معقول، لأن العديد من أوامر Tcl تعتمد عليها بشكل حاسم (على سبيل المثال، file atime، file isdirectory، file size، glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

تقوم الدالة Tcl_FSStatProc بملء بنية المعلومات statPtr بمعلومات حول الملف المحدد. لا يلزم وجود حقوق وصول للملف للحصول على هذه المعلومات، ولكن يلزم وجود حقوق بحث في جميع الدلائل المسماة في المسار الذي يؤدي إلى هذا الملف. تتضمن بنية المعلومات بيانات حول الجهاز، والـ inode (دائمًا 0 في Windows)، ووضع الأذونات، وعدد الروابط (دائمًا 1 في Windows)، ومعرف المستخدم (دائمًا 0 في Windows)، ومعرف المجموعة (دائمًا 0 في Windows)، و rdev (نفس الجهاز في Windows)، والحجم، ووقت آخر وصول، ووقت آخر تعديل، ووقت آخر تغيير للبيانات الوصفية.

إذا كان الملف الذي يمثله pathPtr موجودًا، فإن Tcl_FSStatProc ترجع 0 ويتم ملء بنية المعلومات بالبيانات. بخلاف ذلك، يتم إرجاع -1 ولا يتم تقديم بيانات المعلومات.
