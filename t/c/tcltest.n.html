DESCRIPTION

The tcltest package provides several utility commands useful in the construction of test suites for code instrumented to be run by evaluation of Tcl commands. Notably the built-in commands of the Tcl library itself are tested by a test suite using the tcltest package.

All the commands provided by the tcltest package are defined in and exported from the ::tcltest namespace, as indicated in the SYNOPSIS above. In the following sections, all commands will be described by their simple names, in the interest of brevity.

The central command of tcltest is test that defines and runs a test. Testing with test involves evaluation of a Tcl script and comparing the result to an expected result, as configured and controlled by a number of options. Several other commands provided by tcltest govern the configuration of test and the collection of many test commands into test suites.

See CREATING TEST SUITES WITH TCLTEST below for an extended example of how to use the commands of tcltest to produce test suites for your Tcl-enabled code.

COMMANDS

test name description ?-option value ...?
Defines and possibly runs a test with the name name and description description. The name and description of a test are used in messages reported by test during the test, as configured by the options of tcltest. The remaining option value arguments to test define the test, including the scripts to run, the conditions under which to run them, the expected result, and the means by which the expected and actual results should be compared. See TESTS below for a complete description of the valid options and how they define a test. The test command returns an empty string.
test name description ?constraints? body result
This form of test is provided to support test suites written for version 1 of the tcltest package, and also a simpler interface for a common usage. It is the same as “test name description -constraints constraints -body body -result result”. All other options to test take their default values. When constraints is omitted, this form of test can be distinguished from the first because all options begin with “-”.
loadTestedCommands
Evaluates in the caller's context the script specified by configure -load or configure -loadfile. Returns the result of that script evaluation, including any error raised by the script. Use this command and the related configuration options to provide the commands to be tested to the interpreter running the test suite.
makeFile contents name ?directory?
Creates a file named name relative to directory directory and write contents to that file using the encoding encoding system. If contents does not end with a newline, a newline will be appended so that the file named name does end with a newline. Because the system encoding is used, this command is only suitable for making text files. The file will be removed by the next evaluation of cleanupTests, unless it is removed by removeFile first. The default value of directory is the directory configure -tmpdir. Returns the full path of the file created. Use this command to create any text file required by a test with contents as needed.
removeFile name ?directory?
Forces the file referenced by name to be removed. This file name should be relative to directory. The default value of directory is the directory configure -tmpdir. Returns an empty string. Use this command to delete files created by makeFile.
makeDirectory name ?directory?
Creates a directory named name relative to directory directory. The directory will be removed by the next evaluation of cleanupTests, unless it is removed by removeDirectory first. The default value of directory is the directory configure -tmpdir. Returns the full path of the directory created. Use this command to create any directories that are required to exist by a test.
removeDirectory name ?directory?
Forces the directory referenced by name to be removed. This directory should be relative to directory. The default value of directory is the directory configure -tmpdir. Returns an empty string. Use this command to delete any directories created by makeDirectory.
viewFile file ?directory?
Returns the contents of file, except for any final newline, just as read -nonewline would return. This file name should be relative to directory. The default value of directory is the directory configure -tmpdir. Use this command as a convenient way to turn the contents of a file generated by a test into the result of that test for matching against an expected result. The contents of the file are read using the system encoding, so its usefulness is limited to text files.
cleanupTests
Intended to clean up and summarize after several tests have been run. Typically called once per test file, at the end of the file after all tests have been completed. For best effectiveness, be sure that the cleanupTests is evaluated even if an error occurs earlier in the test file evaluation.

Prints statistics about the tests run and removes files that were created by makeDirectory and makeFile since the last cleanupTests. Names of files and directories in the directory configure -tmpdir created since the last cleanupTests, but not created by makeFile or makeDirectory are printed to outputChannel. This command also restores the original shell environment, as described by the global envإلى تقييم برنامج نصي Tcl ومقارنة النتيجة مع نتيجة متوقعة. خيارات test تحدد البرنامج النصي للاختبار، والبيئة التي سيتم تقييمها فيها، والنتيجة المتوقعة، وكيفية مقارنة النتيجة الفعلية بالنتيجة المتوقعة. بعض خيارات التكوين الخاصة بـ tcltest تؤثر أيضًا على كيفية عمل test.

تم تلخيص الخيارات الصحيحة لـ test:

test name description
        ?-constraints keywordList|expression?
        ?-setup setupScript?
        ?-body testScript?
        ?-cleanup cleanupScript?
        ?-result expectedAnswer?
        ?-output expectedOutput?
        ?-errorOutput expectedError?
        ?-returnCodes codeList?
        ?-errorCode expectedErrorCode?

يمكن أن يكون name أي سلسلة نصية. من المعتاد اختيار name وفقًا للنمط:

target-majorNum.minorNum

بالنسبة للاختبارات من النوع white-box (الانحدار)، يجب أن يكون target هو اسم وظيفة C أو إجراء Tcl الذي يتم اختباره. بالنسبة للاختبارات من النوع black-box، يجب أن يكون target هو اسم الميزة التي يتم اختبارها. تتطلب بعض الاتفاقيات أن يكون لأسماء اختبارات black-box اللاحقة _bb. يجب أن تشترك الاختبارات ذات الصلة في رقم رئيسي. مع تطور مجموعة الاختبارات، من الأفضل أن يستمر اسم الاختبار نفسه في المطابقة لنفس الاختبار، بحيث يظل من المنطقي قول أشياء مثل "اجتاز الاختبار foo-1.3 في جميع الإصدارات حتى 3.4، لكنه بدأ بالفشل في الإصدار 3.5."

أثناء تقييم test، تتم مقارنة name بقوائم أنماط مطابقة السلاسل النصية التي تم إرجاعها بواسطة configure -match و configure -skip. سيتم تشغيل الاختبار فقط إذا كان name يطابق أيًا من الأنماط من configure -match ولا يطابق أيًا من الأنماط من configure -skip.

يجب أن يكون description وصفًا نصيًا قصيرًا للاختبار. يتم تضمين description في المخرجات التي ينتجها الاختبار، وعادةً ما تكون رسائل فشل الاختبار. يجب أن تشرح قيم description الجيدة بإيجاز الغرض من الاختبار لمستخدمي مجموعة الاختبارات. يجب تضمين اسم وظيفة Tcl أو C التي يتم اختبارها في الوصف الخاص باختبارات الانحدار. إذا كان هناك حالة اختبار موجودة لإعادة إنتاج خطأ، فقم بتضمين معرف الخطأ في الوصف.

السمات الصالحة والقيم المرتبطة بها هي:

-constraints keywordList|expression
يمكن أن تكون السمة الاختيارية -constraints قائمة بكلمة مفتاحية واحدة أو أكثر أو تعبيرًا. إذا كانت قيمة -constraints قائمة بكلمات مفتاحية، فيجب أن تكون كل كلمة مفتاحية من هذه الكلمات اسم قيد تم تعريفه بواسطة استدعاء testConstraint. إذا كان أي من القيود المدرجة خاطئًا أو غير موجود، فسيتم تخطي الاختبار. إذا كانت قيمة -constraints تعبيرًا، فسيتم تقييم هذا التعبير. إذا كان التعبير يقيّم إلى صحيح، فسيتم تشغيل الاختبار. لاحظ أن شكل التعبير الخاص بـ -constraints قد يتداخل مع عملية configure -constraints و configure -limitconstraints، ولا يوصى به. يجب إضافة القيود المناسبة إلى أي اختبارات لا ينبغي تشغيلها دائمًا. أي، يجب أن يتم إجراء التقييم الشرطي للاختبار بواسطة الخيار -constraints، وليس بواسطة التقييم الشرطي لـ test. بهذه الطريقة، يتم دائمًا الإبلاغ عن نفس عدد الاختبارات بواسطة مجموعة الاختبارات، على الرغم من أن عدد الاختبارات التي تم تخطيها قد يتغير بناءً على بيئة الاختبار. القيمة الافتراضية هي قائمة فارغة. انظر TEST CONSTRAINTS أدناه للحصول على قائمة بالقيود المضمنة ومعلومات حول كيفية إضافة قيودك الخاصة.
-setup script
تشير السمة الاختيارية -setup إلى script سيتم تشغيله قبل النص البرمجي المشار إليه بالسمة -body. إذا أثار تقييم script خطأ، فسيفشل الاختبار. القيمة الافتراضية هي نص برمجي فارغ.
-body script
تشير السمة -body إلى script الذي سيتم تشغيله لتنفيذ الاختبار، والذي يجب أن يعيد نتيجة يمكن التحقق من صحتها. إذا أثار تقييم script خطأ، فسيفشل الاختبار (ما لم يتم استخدام الخيار -returnCodes لذكر أن خطأ متوقع). القيمة الافتراضية هي نص برمجي فارغ.
-cleanup script
تشير السمة الاختيارية -cleanup إلى script سيتم تشغيله بعد النص البرمجي المشار إليه بالسمة -body. إذا أثار تقييم script خطأ، فسيفشل الاختبار. القيمة الافتراضية هي نص برمجي فارغ.
-match mode
تحدد السمة -match كيفية مقارنة الإجابات المتوقعة المقدمة بواسطة -result و -output و -errorOutput. القيم الصالحة لـ mode هي regexp و glob و exact، وأي قيمة مسجلة باستدعاء سابق لـ customMatch. القيمة الافتراضية هي exact.
-result expectedValue
توفر السمة -result الـ expectedValue التي سيتم مقارنة القيمة المرتجعة من النص البرمجي بها. القيمة الافتراضية هي سلسلة نصية فارغة.
-output expectedValue
توفر السمة -output الـ expectedValue التي سيتم مقارنة أي مخرجات مرسلة إلى stdout أو outputChannel أثناء تقييم النص (النصوص) البرمجي بها. لاحظ أن المخرجات التي تتم طباعتها باستخدام الأمر العام puts فقط هي المستخدمة للمقارنة. إذا لم يتم تحديد -output، فلن تتم معالجة المخرجات المرسلة إلى stdout و outputChannel للمقارنة.
-errorOutput expectedValue
توفر السمة -errorOutput الـ expectedValue التي سيتم مقارنة أي مخرجات مرسلة إلى stderr أو errorChannel أثناء تقييم النص (النصوص) البرمجي بها. لاحظ أن المخرجات التي تتم طباعتها باستخدام الأمر العام puts فقط هي المستخدمة للمقارنة. إذا لم يتم تحديد -errorOutput، فلن تتم معالجة المخرجات المرسلة إلى stderr و errorChannel للمقارنة.
-returnCodes expectedCodeList
توفر السمة الاختيارية -returnCodes الـ expectedCodeList، وهي قائمة برموز الإرجاع التي يمكن قبولها من تقييم النص البرمجي -body. إذا أعادت تقييم النص البرمجي -body رمزًا غير موجود في expectedCodeList، فسيفشل الاختبار. جميع رموز الإرجاع المعروفة لـ return، في كل من الشكل الرقمي والرمزي، بما في ذلك رموز الإرجاع الموسعة، هي عناصر مقبولة في expectedCodeList. القيمة الافتراضية هي "ok return".
-errorCode expectedErrorCode
توفر السمة الاختيارية -errorCode الـ expectedErrorCode، وهو نمط glob يجب أن يتطابق مع رمز الخطأ المبلغ عنه من تقييم النص البرمجي -body. إذا أعادت تقييم النص البرمجي -body رمزًا لا يتطابق مع expectedErrorCode، فسيفشل الاختبار. القيمة الافتراضية هي "*" . إذا لم تتضمن -returnCodes "error"، فسيتم تعيينها إلى "error".

لكي ينجح الاختبار، يجب عليه تقييم النصوص البرمجية -setup و -body و -cleanup بنجاح. يجب أن تتطابق القيمة المرجعة للنص البرمجي -body ونتيجته مع القيم المتوقعة، وإذا تم تحديد ذلك، فيجب أن تتطابق المخرجات وبيانات الخطأ من الاختبار مع قيم -output و -errorOutput المتوقعة. إذا لم يتم استيفاء أي من هذه الشروط، فسيفشل الاختبار. لاحظ أنه يتم تقييم جميع النصوص البرمجية في سياق مستدعي test.

طالما تم استدعاء test بتنسيق صحيح وقيم قانونية لجميع السمات، فلن يثير خطأ. بدلاً من ذلك، يتم الإبلاغ عن فشل الاختبارات كمخرجات مكتوبة إلى outputChannel. في التشغيل الافتراضي، لا ينتج عن الاختبار الناجح أي مخرجات. يتم التحكم في رسائل المخرجات التي ينتجها test بواسطة الخيار configure -verbose كما هو موضح في CONFIGURABLE OPTIONS أدناه. يجب إنتاج أي مخرجات تنتجها نصوص الاختبار نفسها باستخدام puts إلى outputChannel أو errorChannel، حتى يتمكن المستخدمون من مجموعة الاختبارات من التقاط المخرجات بسهولة باستخدام خيارات configure -outfile و configure -errfile، ولضمان عمل سمات -output و -errorOutput بشكل صحيح.

قيود الاختبار

تُستخدم القيود لتحديد ما إذا كان يجب تخطي الاختبار أم لا. كل قيد له اسم، والذي يمكن أن يكون أي سلسلة نصية، وقيمة منطقية. كل test لديه قيمة -constraints وهي قائمة بأسماء القيود. هناك وضعان للتحكم في القيود. في أغلب الأحيان، يتم استخدام الوضع الافتراضي، والمشار إليه بضبط configure -limitconstraints على false. سيتم تشغيل الاختبار فقط إذا كانت جميع القيود في القائمة ذات قيمة صحيحة. وبالتالي، فإن خيار -constraints الخاص بـ test هو طريقة رمزية ومريحة لتحديد أي شروط مطلوبة ليكون الاختبار ممكنًا أو ذا معنى. على سبيل المثال، سيتم تشغيل test مع -constraints unix فقط إذا كان القيد unix صحيحًا، مما يشير إلى أن مجموعة الاختبارات يتم تشغيلها على منصة Unix.

يجب أن يتضمن كل test أي -constraints مطلوبة لتقييدها لتشغيلها فقط عند الاقتضاء. يتم تعريف عدة قيود في حزمة tcltest، مدرجة أدناه. يتم تسجيل القيود المعرفة من قبل المستخدم بواسطة الأمر testConstraint. قد تظهر القيود المعرفة من قبل المستخدم داخل ملف اختبار، أو داخل النص البرمجي المحدد بواسطة الخيار configure -load أو configure -loadfile.

القائمة التالية هي قائمة بالقيود المعرفة مسبقًا بواسطة حزمة tcltest نفسها:

singleTestInterp
يمكن تشغيل هذا الاختبار فقط إذا تم استدعاء جميع ملفات الاختبار في مترجم واحد.
unix
يمكن تشغيل هذا الاختبار فقط على أي منصة Unix.
win
يمكن تشغيل هذا الاختبار فقط على أي منصة Windows.
nt
يمكن تشغيل هذا الاختبار فقط على أي منصة Windows NT.
mac
يمكن تشغيل هذا الاختبار فقط على أي منصة Mac.
unixOrWin
يمكن تشغيل هذا الاختبار فقط على نظام Unix أو Windows.
macOrWin
يمكن تشغيل هذا الاختبار فقط على نظام Mac أو Windows.
macOrUnix
يمكن تشغيل هذا الاختبار فقط على نظام Mac أو Unix.
tempNotWin
لا يمكن تشغيل هذا الاختبار على نظام Windows. يتم استخدام هذا العلم لتعطيل اختبار مؤقتًا.
tempNotMac
لا يمكن تشغيل هذا الاختبار على نظام Mac. يتم استخدام هذا العلم لتعطيل اختبار مؤقتًا.
unixCrash
يتعطل هذا الاختبار إذا تم تشغيله على نظام Unix. يتم استخدام هذا العلم لتعطيل اختبار مؤقتًا.
winCrash
يتعطل هذا الاختبار إذا تم تشغيله على نظام Windows. يتم استخدام هذا العلم لتعطيل اختبار مؤقتًا.
macCrash
يتعطل هذا الاختبار إذا تم تشغيله على نظام Mac. يتم استخدام هذا العلم لتعطيل اختبار مؤقتًا.
emptyTest
هذا الاختبار فارغ، وبالتالي لا يستحق التشغيل، ولكنه يظل بمثابة عنصر نائب لاختبار سيتم كتابته في المستقبل. هذه القيود لها قيمة خاطئة للتسبب في تخطي الاختبارات ما لم يحدد المستخدم خلاف ذلك.
knownBug
من المعروف أن هذا الاختبار يفشل والخطأ لم يتم إصلاحه بعد. هذه القيود لها قيمة خاطئة للتسبب في تخطي الاختبارات ما لم يحدد المستخدم خلاف ذلك.
nonPortable
يمكن تشغيل هذا الاختبار فقط في بيئة تطوير معروفة. بعض الاختبارات غير قابلة للنقل بطبيعتها لأنها تعتمد على أشياء مثل طول الكلمة، تكوين نظام الملفات، مدير النوافذ، إلخ. هذه القيود لها قيمة خاطئة للتسبب في تخطي الاختبارات ما لم يحدد المستخدم خلاف ذلك.
userInteraction
يتطلب هذا الاختبار تفاعلاً من المستخدم. هذه القيود لها قيمة خاطئة للتسبب في تخطي الاختبارات ما لم يحدد المستخدم خلاف ذلك.
interactive
لا يمكن تشغيل هذا الاختبار إلا إذا كان المفسر في وضع تفاعلي (عندما يكون المتغير العام tcl_interactive مضبوطًا على 1).
nonBlockFiles
لا يمكن تشغيل هذا الاختبار إلا إذا كانت المنصة تدعم ضبط الملفات في وضع غير مانع.
asyncPipeClose
لا يمكن تشغيل هذا الاختبار إلا إذا كانت المنصة تدعم التدفق غير المتزامن والإغلاق غير المتزامن على الأنابيب.
unixExecs
لا يمكن تشغيل هذا الاختبار إلا إذا كانت هذه الآلة تحتوي على أوامر بأسلوب Unix cat، echo، sh، wc، rm، sleep، fgrep، ps، chmod، و mkdir متاحة.
hasIsoLocale
لا يمكن تشغيل هذا الاختبار إلا إذا كان بإمكانه التبديل إلى إعدادات محلية ISO.
root
لا يمكن تشغيل هذا الاختبار إلا إذا كان مستخدم Unix هو root.
notRoot
لا يمكن تشغيل هذا الاختبار إلا إذا كان مستخدم Unix ليس root.
eformat
لا يمكن تشغيل هذا الاختبار إلا إذا كان التطبيق يحتوي على إصدار عامل من sprintf فيما يتعلق بتنسيق "e" للأرقام العشرية.
stdio
لا يمكن تشغيل هذا الاختبار إلا إذا كان يمكن فتح interpreter كـ أنبوب.

يتم تمكين وضع بديل للتحكم في القيود عن طريق ضبط configure -limitconstraints على true. مع هذا الإعداد للتكوين، يتم تعيين جميع القيود الموجودة بخلاف تلك الموجودة في قائمة القيود التي تم إرجاعها بواسطة configure -constraints إلى false. عندما يتم تعيين قيمة configure -constraints، يتم تعيين جميع هذه القيود إلى true. التأثير هو أنه عندما يتم استخدام كل من الخيارين configure -constraints و configure -limitconstraints، يتم تشغيل الاختبارات التي تتضمن فقط القيود من قائمة configure -constraints؛ يتم تخطي جميع الاختبارات الأخرى. على سبيل المثال، قد يقوم المرء بإعداد تكوين مع

configure -constraints knownBug \
          -limitconstraints true \
          -verbose pass

لتشغيل الاختبارات التي تمارس الأخطاء المعروفة بالضبط، واكتشاف ما إذا كان أي منها يمر، مما يشير إلى أن الخطأ قد تم إصلاحه.

تشغيل جميع الاختبارات

يتم تقييم الأمر الوحيد runAllTests لتشغيل مجموعة اختبار كاملة، تمتد عبر العديد من الملفات والمجلدات. تتحكم خيارات تكوين tcltest في العمليات الدقيقة. يبدأ الأمر runAllTests بطباعة ملخص لتكوينه إلى outputChannel.

يتم البحث عن ملفات الاختبار المراد تقييمها في الدليل configure -testdir. يتم إنشاء قائمة بالملفات في هذا الدليل التي تتطابق مع أي من الأنماط في configure -file ولا تتطابق مع أي من الأنماط في configure -notfile ويتم فرزها. ثم يتم تقييم كل ملف بدوره. إذا كان configure -singleproc صحيحًا، فسيتم source كل ملف في سياق المستدعي. إذا كان خطأ، فسيتم exec نسخة من interpreter لتقييم كل ملف. عملية تعدد العمليات مفيدة عند اختبار يمكن أن تسبب أخطاء خطيرة لدرجة أن عملية تنتهي. على الرغم من أن مثل هذا الخطأ قد ينهي عملية فرعية تقوم بتقييم ملف واحد، إلا أن العملية الرئيسية يمكن أن تستمر مع بقية مجموعة الاختبار. في عملية تعدد العمليات، يتم تمرير تكوين tcltest في العملية الرئيسية إلى العمليات الفرعية كوسائط سطر أوامر، باستثناء configure -outfile. يجمع الأمر runAllTests في العملية الرئيسية كل المخرجات من العمليات الفرعية ويجمع نتائجها في تقرير رئيسي واحد. أي تقارير عن فشل اختبار فردي، أو رسائل مطلوبة بواسطة إعداد configure -verbose يتم تمريرها مباشرة إلى outputChannel بواسطة العملية الرئيسية.

بعد تقييم جميع ملفات الاختبار المحددة، يتم طباعة ملخص للنتائج إلى outputChannel. يتضمن الملخص العدد الإجمالي لـ tests التي تم تقييمها، مقسمة إلى تلك التي تم تخطيها، وتلك التي نجحت، وتلك التي فشلت. يلاحظ الملخص أيضًا عدد الملفات التي تم تقييمها، وأسماء أي ملفات تحتوي على اختبارات فاشلة أو أخطاء. يتم أيضًا طباعة قائمة بالقيود التي تسببت في تخطي الاختبارات، وعدد الاختبارات التي تم تخطيها لكل منها. أيضًا، يتم طباعة رسائل إذا بدا أن تقييم ملف اختبار قد تسبب في ترك أي ملفات مؤقتة في configure -tmpdir.

بعد الانتهاء من تلخيص جميع ملفات الاختبار المحددة، يتصرف runAllTests بشكل تكراري على الدلائل الفرعية لـ configure -testdir. يتم فحص جميع الدلائل الفرعية التي تتطابق مع أي من الأنماط في configure -relateddir ولا تتطابق مع أي من الأنماط في configure -asidefromdir. إذا تم العثور على ملف يسمى all.tcl في مثل هذا الدليل، فسيتم source في سياق المستدعي. سواء كان الدليل الذي تم فحصه يحتوي على ملف all.tcl أم لا، يتم فحص دلائله الفرعية أيضًا مقابل الأنماط configure -relateddir و configure -asidefromdir. بهذه الطريقة، يمكن تقييم العديد من الدلائل في شجرة دليل بواسطة أمر runAllTests واحد.

خيارات قابلة للتكوين

يتم استخدام الأمر configure لتعيين الاستعلام عن الخيارات القابلة للتكوين لـ tcltest. الخيارات الصالحة هي:

-singleproc boolean
يتحكم فيما إذا كان runAllTests يقوم بإنشاء عملية فرعية لكل ملف اختبار. لا يتم إنشاء عملية عندما يكون boolean صحيحًا. القيمة الافتراضية هي false.
-debug level
يضبط مستوى التصحيح على level، وهو قيمة عددية تشير إلى مقدار معلومات التصحيح التي يجب طباعتها إلى stdout. لاحظ أن رسائل التصحيح تذهب دائمًا إلى stdout، بشكل مستقل عن قيمة configure -outfile. القيمة الافتراضية هي 0. المستويات معرفة كما يلي:
0
لا تعرض أي معلومات تصحيح.
1
عرض المعلومات المتعلقة بما إذا كان اختبار ما قد تم تخطيه لأنه لا يتطابق مع أي من الاختبارات التي تم تحديدها بواسطة configure -match (userSpecifiedNonMatch) أو يتطابق مع أي من الاختبارات المحددة بواسطة configure -skip (userSpecifiedSkip). طباعة تحذيرات حول احتمال عدم التنظيف أو التوازن في ملفات الاختبار. طباعة تحذيرات حول أي إعادة استخدام لأسماء الاختبارات.
2
عرض مصفوفة العلم التي تم تحليلها بواسطة معالج سطر الأوامر، ومحتويات مصفوفة env العامة، وجميع المتغيرات المعرفة من قبل المستخدم الموجودة في الفضاء الحالي كما يتم استخدامها.
3
عرض المعلومات المتعلقة بما تفعله الإجراءات الفردية في ساحة الاختبار.
-verbose level
يضبط نوع تفصيل الإخراج المطلوب على level، وهي قائمة بصفر أو أكثر من العناصر body، pass، skip، start، error، line، msec و usec. القيمة الافتراضية هي "body error". المستويات معرفة كما يلي:
body (b)
عرض نص الاختبارات الفاشلة
pass (p)
طباعة الإخراج عند نجاح اختبار
skip (s)
طباعة الإخراج عند تخطي اختبار
start (t)
طباعة الإخراج كلما بدأ اختبار
error (e)
طباعة errorInfo و errorCode، إذا كانت موجودة، عندما لا يتطابق رمز إرجاع الاختبار مع رمز الإرجاع المتوقع
line (l)
طباعة معلومات سطر الملف المصدر للاختبارات الفاشلة

التوافق

لم يتم توثيق عدد من الأوامر والمتغيرات في مساحة الاسم ::tcltest المقدمة من الإصدارات السابقة لـ tcltest هنا. لم تعد هذه جزءًا من الواجهة العامة المدعومة لـ tcltest ولا ينبغي استخدامها في مجموعات الاختبار الجديدة. ومع ذلك، لمواصلة دعم مجموعات الاختبار الموجودة المكتوبة وفقًا لمواصفات الواجهة القديمة، لا تزال العديد من هذه الأوامر والمتغيرات المهملة تعمل كما كانت من قبل. على سبيل المثال، في العديد من الظروف، سيتم استدعاء configure تلقائيًا بعد فترة وجيزة من نجاح package require tcltest 2.1 مع وسائط من المتغير ::argv. هذا لدعم مجموعات الاختبار التي تعتمد على السلوك القديم الذي تم تكوينه تلقائيًا لـ tcltest من وسائط سطر الأوامر. لا ينبغي لملفات الاختبار الجديدة الاعتماد على هذا، ولكن يجب أن تتضمن صراحةً

eval ::tcltest::configure $::argv

أو

::tcltest::configure {*}$::argv

لإنشاء تكوين من وسائط سطر الأوامر.

مشاكل معروفة

هناك مشكلتان تتعلقان بالتقييمات المتداخلة لـ test. تتعلق المشكلة الأولى بمستوى المكدس الذي يتم فيه تنفيذ نصوص الاختبار. قد يتم تنفيذ الاختبارات المتداخلة ضمن اختبارات أخرى بنفس مستوى المكدس مثل الاختبار الخارجي. على سبيل المثال، في الشفرة التالية:

test level-1.1 {level 1} {
    -body {
        test level-2.1 {level 2} {
        }
    }
}

قد يتم تنفيذ أي نص يتم تنفيذه في level-2.1 بنفس مستوى المكدس مثل النص المحدد لـ level-1.1.

بالإضافة إلى ذلك، بينما تم تشغيل اختبارين test، لن يتم الإبلاغ عن النتائج إلا بواسطة cleanupTests للاختبارات في نفس مستوى الاختبار level-1.1. ومع ذلك، ستكون نتائج الاختبارات لجميع الاختبارات التي تم تشغيلها قبل level-1.1 متاحة عند تشغيل الاختبار level-2.1. ما يعنيه هذا هو أنه إذا حاولت الوصول إلى نتائج الاختبار للاختبار level-2.1، فقد يقول أن "m" اختبارًا قد تم تشغيله، و "n" اختبارًا قد تم تخطيه، و "o" اختبارًا قد نجح، و "p" اختبارًا قد فشل، حيث تشير "m" و "n" و "o" و "p" إلى الاختبارات التي تم تشغيلها في نفس مستوى الاختبار مثل الاختبار level-1.1.

يعتمد تنفيذ مقارنة الإخراج والخطأ في أمر الاختبار test على استخدام puts في شفرة التطبيق الخاصة بك. يتم اعتراض الإخراج عن طريق إعادة تعريف الأمر العام puts أثناء تشغيل نص الاختبار المحدد. لن يتم التقاط الأخطاء التي تثيرها إجراءات C أو تتم طباعتها مباشرة من تطبيقات C بواسطة أمر الاختبار test. لذلك، فإن استخدام خيارات -output و -errorOutput للأمر test مفيد فقط لتطبيقات Tcl النقية التي تستخدم puts لإنتاج الإخراج.
