Tcl_FSNewNativePath performs something like the reverse of the usual obj->path->nativerep conversions. If some code retrieves a path in native form (from, e.g. readlink or a native dialog), and that path is to be used at the Tcl level, then calling this function is an efficient way of creating the appropriate path value type.

The resulting value is a pure “path” value, which will only receive a UTF-8 string representation if that is required by some Tcl code.

Tcl_FSGetNativePath is for use by the Win/Unix native filesystems, so that they can easily retrieve the native (char* or TCHAR*) representation of a path. This function is a convenience wrapper around Tcl_FSGetInternalRep. It may be desirable in the future to have non-string-based native representations (for example, on macOS, a representation using a fileSpec of FSRef structure would probably be more efficient). On Windows a full Unicode representation would allow for paths of unlimited length. Currently the representation is simply a character string which may contain either the relative path or a complete, absolute normalized path in the native encoding (complex conditions dictate which of these will be provided, so neither can be relied upon, unless the path is known to be absolute). If you need a native path which must be absolute, then you should ask for the native version of a normalized path. If for some reason a non-absolute, non-normalized version of the path is needed, that must be constructed separately (e.g. using Tcl_FSGetTranslatedPath).

The native representation is cached so that repeated calls to this function will not require additional conversions. The return value is owned by Tcl and has a lifetime equivalent to that of the pathPtr passed in (unless that is a relative path, in which case the native representation may be freed any time the cwd changes).

Tcl_FSFileSystemInfo returns a list of two elements. The first element is the name of the filesystem (e.g. “native”, “vfs”, “zip”, or “prowrap”, perhaps), and the second is the particular type of the given path within that filesystem (which is filesystem dependent). The second element may be empty if the filesystem does not provide a further categorization of files.

A valid list value is returned, unless the path value is not recognized, when NULL will be returned.

Tcl_FSGetFileSystemForPath returns a pointer to the Tcl_Filesystem which accepts this path as valid.

If no filesystem will accept the path, NULL is returned.

Tcl_FSGetPathType determines whether the given path is relative to the current directory, relative to the current volume, or absolute.

It returns one of TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE, or TCL_PATH_VOLUME_RELATIVE

THE VIRTUAL FILESYSTEM API

A filesystem provides a Tcl_Filesystem structure that contains pointers to functions that implement the various operations on a filesystem; these operations are invoked as needed by the generic layer, which generally occurs through the functions listed above.

The Tcl_Filesystem structures are manipulated using the following methods.

Tcl_FSRegister takes a pointer to a filesystem structure and an optional piece of data to associated with that filesystem. On calling this function, Tcl will attach the filesystem to the list of known filesystems, and it will become fully functional immediately. Tcl does not check if the same filesystem is registered multiple times (and in general that is not a good thing to do). TCL_OK will be returned.

Tcl_FSUnregister removes the given filesystem structure from the list of known filesystems, if it is known, and returns TCL_OK. If the filesystem is not currently registered, TCL_ERROR is returned.

Tcl_FSData will return the clientData associated with the given filesystem, if that filesystem is registered. Otherwise it will return NULL.

Tcl_FSMountsChanged is used to inform the Tcl's core that the set of mount points for the given (already registered) filesystem have changed, and that cached file representations may therefore no longer be correct.

THE TCL_FILESYSTEM STRUCTURE

The Tcl_Filesystem structure contains the following fields:

typedef struct Tcl_Filesystem {
    const char *typeName;
    int structureLength;
    Tcl_FSVersion version;
    Tcl_FSPathInFilesystemProc *pathInFilesystemProc;
    Tcl_FSDupInternalRepProc *dupInternalRepProc;
    Tcl_FSFreeInternalRepProc *freeInternalRepProc;
    Tcl_FSInternalToNormalizedProc *internalToNormalizedProc;
    Tcl_FSCreateInternalRepProc *createInternalRepProc;
    Tcl_FSNormalizePathProc *normalizePathProc;
    Tcl_FSFilesystemPathTypeProc *filesystemPathTypeProc;
    Tcl_FSFilesystemSeparatorProc *filesystemSeparatorProc;
    Tcl_FSStatProc *statProc;
    Tcl_FSAccessProc *accessProc;
    Tcl_FSOpenFileChannelProc *openFileChannelProc;
    Tcl_FSMatchInDirectoryProc *matchInDirectoryProc;
    Tcl_FSUtimeProc *utimeProc;
    Tcl_FSLinkProc *linkProc;
    Tcl_FSListVolumesProc *listVolumesProc;
    Tcl_FSFileAttrStringsProc *fileAttrStringsProc;
    Tcl_FSFileAttrsGetProc *fileAttrsGetProc;
    Tcl_FSFileAttrsSetProc *fileAttrsSetProc;
    Tcl_FSCreateDirectoryProc *createDirectoryProc;
    Tcl_FSRemoveDirectoryProc *removeDirectoryProc;
    Tcl_FSDeleteFileProc *deleteFileProc;
    Tcl_FSCopyFileProc *copyFileProc;
    Tcl_FSRenameFileProc *renameFileProc;
    Tcl_FSCopyDirectoryProc *copyDirectoryProc;
    Tcl_FSLstatProc *lstatProc;
    Tcl_FSLoadFileProc *loadFileProc;
    Tcl_FSGetCwdProc *getCwdProc;
    Tcl_FSChdirProc *chdirProc;
} Tcl_Filesystem;

Except for the first three fields in this structure which contain simple data elements, all entries contain addresses of functions called by the generic filesystem layer to perform the complete range of filesystem related actions.

The many functions in this structure are broken down into three categories: infrastructure functions (almost all of which must be implemented), operational functions (which must be implemented if a complete filesystem is provided), and efficiency functions (which need only be implemented if they can be done so efficiently, or if they have side-effects which are required by the filesystem; Tcl has less efficient emulations it can fall back on). It is important to note that, in the current version of Tcl, most of these fallbacks are only used to handle commands initiated in Tcl, not in C. What this means is, that if a file rename command is issued in Tcl, and the relevant filesystem(s) do not implement their Tcl_FSRenameFileProc, Tcl's core will instead fallback on a combination of other filesystem functions (it will use Tcl_FSCopyFileProc followed by Tcl_FSDeleteFileProc, and if Tcl_FSCopyFileProc is not implemented there is a further fallback). However, if a Tcl_FSRenameFileProc command is issued at the C level, no such fallbacks occur. This is true except for the last four entries in the filesystem table (lstat, load, getcwd and chdir) for which fallbacks do in fact occur at the C level.

Any functions which take path names in Tcl_Obj form take those names in UTF-8 form. The filesystem infrastructure API is designed to support efficient, cached conversion of these UTF-8 paths to other native representations.

البنية التحتية لنظام الملفات

تحتوي هذه الحقول على معلومات أساسية حول بنية نظام الملفات وعناوين الوظائف التي تُستخدم لربط مسار ملف معين بنظام ملفات معين، والتعامل مع المعالجة الداخلية لتمثيلات المسارات، مثل نسخ هذه التمثيلات وتحريرها.

اسم النوع

يحتوي حقل typeName على سلسلة نصية منتهية بصفر تعرّف نوع نظام الملفات المُنفّذ، على سبيل المثال، “native” أو “zip” أو “vfs”.

طول الهيكل

يتم تنفيذ حقل structureLength بشكل عام على أنه sizeof(Tcl_Filesystem)، وهو موجود للسماح بتوافق أفضل للخلفية الثنائية إذا تغير حجم الهيكل في إصدار Tcl مستقبلي.

الإصدار

يجب تعيين حقل version إلى TCL_FILESYSTEM_VERSION_1.

وظيفة المسار في نظام الملفات

يحتوي حقل pathInFilesystemProc على عنوان وظيفة يتم استدعاؤها لتحديد ما إذا كانت قيمة مسار معينة تنتمي إلى نظام الملفات هذا أم لا. ستقوم Tcl باستدعاء وظائف نظام الملفات الأخرى فقط مع مسار أعادت هذه الوظيفة له القيمة TCL_OK. إذا كان المسار لا ينتمي، فيجب إرجاع -1 (سلوك Tcl لأي قيمة إرجاع أخرى غير محدد). إذا تم إرجاع TCL_OK، فيمكن استخدام معلمة الإخراج الاختيارية clientDataPtr لإرجاع تمثيل داخلي (خاص بنظام الملفات) للمسار، والذي سيتم تخزينه مؤقتًا داخل قيمة المسار، وقد يتم استرجاعه بكفاءة بواسطة وظائف نظام الملفات الأخرى. ستقوم Tcl في نفس الوقت بتخزين حقيقة أن هذا المسار ينتمي إلى نظام الملفات هذا. يتم إبطال صلاحية هذه المخازن المؤقتة عند إضافة أو إزالة هياكل نظام الملفات من قائمة Tcl الداخلية لأنظمة الملفات المعروفة.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

وظيفة نسخ التمثيل الداخلي

تقوم هذه الوظيفة بعمل نسخة من التمثيل الداخلي للمسار، ويتم استدعاؤها عندما تحتاج Tcl إلى تكرار قيمة مسار. إذا كانت NULL، فلن تقوم Tcl بنسخ التمثيل الداخلي، والذي قد يحتاج بعد ذلك إلى إعادة إنشائه لاحقًا.

typedef ClientData Tcl_FSDupInternalRepProc(
        ClientData clientData);

وظيفة تحرير التمثيل الداخلي

تحرير التمثيل الداخلي. يجب تنفيذ هذا إذا كانت التمثيلات الداخلية تحتاج إلى تحرير (أي، إذا تم تخصيص ذاكرة عند إنشاء تمثيل داخلي)، ولكن يمكن أن تكون NULL بخلاف ذلك.

typedef void Tcl_FSFreeInternalRepProc(
        ClientData clientData);

وظيفة تحويل الداخلي إلى قياسي

وظيفة لتحويل التمثيل الداخلي إلى مسار قياسي. مطلوبة فقط إذا كان نظام الملفات ينشئ قيم مسار خالصة بدون تمثيل سلسلة نصية/مسار. القيمة المرجعة هي قيمة Tcl التي يكون تمثيلها النصي هو المسار القياسي.

typedef Tcl_Obj *Tcl_FSInternalToNormalizedProc(
        ClientData clientData);

وظيفة قياس المسار

وظيفة لقياس المسار. يجب تنفيذها لجميع أنظمة الملفات التي يمكن أن يكون لها تمثيلات نصية متعددة لنفس قيمة المسار. في Tcl، يجب أن يكون لكل "مسار" تمثيل نصي "قياسي" فريد واحد. اعتمادًا على نظام الملفات، قد يكون هناك أكثر من تمثيل نصي غير قياسي يشير إلى هذا المسار (على سبيل المثال، مسار نسبي، مسار بحالة أحرف مختلفة إذا كان نظام الملفات غير حساس لحالة الأحرف، مسار يحتوي على إشارة إلى دليل المنزل مثل "~"، مسار يحتوي على روابط رمزية، إلخ). إذا كان المكون الأخير في المسار رابطًا رمزيًا، فلا يجب تحويله إلى القيمة التي يشير إليها (ولكن يجب جعل حالته أو جوانبه الأخرى فريدة). يجب تحويل جميع مكونات المسار الأخرى من الروابط الرمزية. هذا الاستثناء الوحيد مطلوب ليتوافق مع دلالات Tcl مع file delete و file rename و file copy التي تعمل على الروابط الرمزية. قد يتم استدعاء هذه الوظيفة مع nextCheckpoint إما في بداية المسار (أي صفر)، أو في نهاية المسار، أو في أي فاصل ملف وسيط في المسار. لن يشير أبدًا إلى أي موضع تعسفي آخر في المسار. في الحالة الأخيرة من الحالات الثلاث الصالحة، يمكن للتنفيذ افتراض أن المسار حتى فاصل الملف بما في ذلك تم قياسه.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

عمليات نظام الملفات

تحتوي الحقول في هذا القسم من الهيكل على عناوين الوظائف التي يتم استدعاؤها لتنفيذ عمليات نظام الملفات الأساسية. يجب على نظام الملفات الذي يتوقع استخدامه مع مجموعة أوامر Tcl القياسية الكاملة تنفيذ جميع هذه العمليات. إذا لم يتم تنفيذ بعضها، فقد تفشل أوامر Tcl معينة عند العمل على المسارات داخل نظام الملفات هذا. ومع ذلك، قد يكون هذا مرغوبًا فيه في بعض الحالات (على سبيل المثال، يجب ألا ينفذ نظام الملفات للقراءة فقط الوظائف الأربع الأخيرة، ولا يلزم نظام الملفات الذي لا يدعم الروابط الرمزية تنفيذ وظيفة readlink، وما إلى ذلك. تتوقع نواة Tcl أن تتصرف أنظمة الملفات بهذه الطريقة).

وظيفة نوع مسار نظام الملفات

وظيفة لتحديد نوع مسار في نظام الملفات هذا. يمكن أن تكون NULL، وفي هذه الحالة لن تكون هناك معلومات عن النوع متاحة لمستخدمي نظام الملفات. يُستخدم "النوع" لأغراض إعلامية فقط، ويجب إرجاعه كتمثيل نصي لقيمة TclObj التي يتم إرجاعها. قد تكون القيمة المرجعة النموذجية هي "networked" أو "zip" أو "ftp". قيمة TclObj المرجعة مملوكة لنظام الملفات، لذا ستقوم Tcl بزيادة عدد المراجع لتلك القيمة إذا كانت ترغب في الاحتفاظ بمرجع لها.

typedef Tcl_Obj *Tcl_FSFilesystemPathTypeProc(

وظيفة فاصل نظام الملفات

typedef Tcl_Obj *Tcl_FSFilesystemSeparatorProc(

وظيفة stat

وظيفة لمعالجة استدعاء Tcl_FSStat. يجب تنفيذها لأي نظام ملفات معقول، حيث تعتمد العديد من أوامر مستوى Tcl بشكل حاسم عليها (على سبيل المثال، file atime، file isdirectory، file size، glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

تقوم Tcl_FSStatProc بملء بنية stat statPtr بمعلومات حول الملف المحدد. لا تحتاج إلى أي حقوق وصول إلى الملف للحصول على هذه المعلومات ولكنك تحتاج إلى حقوق بحث لجميع الدلائل المسماة في المسار المؤدي إلى الملف. تتضمن بنية stat معلومات تتعلق بالجهاز، inode (0 دائمًا على Windows)، وضع الامتيازات، nlink (1 دائمًا على Windows)، معرف المستخدم (0 دائمًا على Windows)، معرف المجموعة (0 دائمًا على Windows)، rdev (نفس الجهاز على Windows)، الحجم، وقت آخر وصول، وقت آخر تعديل، ووقت آخر تغيير للبيانات الوصفية.

إذا كان الملف الذي تمثله pathPtr موجودًا، فإن Tcl_FSStatProc تُرجع 0 ويتم ملء بنية stat بالبيانات. بخلاف ذلك، يتم إرجاع -1، ولا يتم تقديم أي معلومات stat.

وظيفة الوصول

وظيفة لمعالجة استدعاء Tcl_FSAccess. يجب تنفيذها لأي نظام ملفات معقول، حيث تعتمد العديد من أوامر مستوى Tcl بشكل حاسم عليها (على سبيل المثال، file exists، file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

تتحقق Tcl_FSAccessProc مما إذا كان سيُسمح للعملية بالقراءة أو الكتابة أو اختبار وجود الملف (أو كائن نظام الملفات الآخر) الذي يحمل اسمه pathPtr. إذا كان اسم المسار يشير إلى رابط رمزي، فيجب اختبار أذونات الملف الذي يشير إليه هذا الرابط الرمزي.

عند النجاح (تم منح جميع الأذونات المطلوبة)، يتم إرجاع صفر. عند حدوث خطأ (تم طلب إذن واحد على الأقل في الوضع وهو مرفوض، أو حدث خطأ آخر)، يتم إرجاع -1.

MATCHINDIRECTORYPROC

وظيفة لمعالجة استدعاء Tcl_FSMatchInDirectory. إذا لم يتم تنفيذها، فإن وظيفة glob والنسخ المتكرر في نظام الملفات ستكون مفقودة (وقد يؤثر ذلك على الأوامر مثل encoding names التي تستخدم وظيفة glob).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

يجب أن تعيد الدالة جميع الملفات أو الدلائل (أو كائنات نظام الملفات الأخرى) التي تطابق النمط المعطى وتحترم المواصفات types. يمكن استدعاء هذه الدالة بطريقتين. إذا كان pattern هو NULL، فيجب أن يكون pathPtr مواصفات كاملة لملف أو دليل يجب التحقق من وجوده ونوعه. خلاف ذلك، يكون pathPtr دليلاً ويجب أن تبحث الدالة عن ملفات أو دلائل ذات أنواع صحيحة. في كلتا الحالتين، يُفترض أن pathPtr غير فارغ وغير صفري. لا توثق حاليًا ما إذا كان pathPtr سيحتوي على فاصل ملف في النهاية، لذا يجب أن يكون الكود مرنًا في كلتا الحالتين.

القيمة المرجعة هي نتيجة Tcl قياسية تشير إلى ما إذا كانت هناك خطأ أثناء عملية المطابقة. توضع رسائل الخطأ في interp، إلا إذا كان interp هو NULL، وفي هذه الحالة لا يتم إنشاء أي رسالة خطأ. إذا كانت النتيجة TCL_OK، فيجب إضافة النتائج إلى القيمة المعطاة في resultPtr (والتي يفترض أنها قائمة Tcl غير مشتركة). يجب أن تتضمن النتائج المضافة إلى resultPtr أي بادئة مسار معطاة في pathPtr (مما يعني عادةً أنها ستكون مواصفات مسار مطلقة). ملاحظة: إذا لم تكن هناك مطابقات، يتم الحصول على نتيجة فارغة؛ فقط يتم الإبلاغ عن الأخطاء للمشاكل الفعلية في الملفات أو أنظمة الملفات التي قد تحدث أثناء عملية المطابقة.

يحتوي هيكل Tcl_GlobTypeData الذي يتم تمريره في المعلمة types على الحقول التالية:

typedef struct Tcl_GlobTypeData {
    /* يتوافق مع bcdpfls كما في 'find -t' */
    int type;
    /* يتوافق مع أذونات الملف */
    int perm;
    /* نوع mac مقبول */
    Tcl_Obj *macType;
    /* منشئ mac مقبول */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

هناك حالتان خاصتان مهمتان يجب التعامل معهما بشكل صحيح، وكلاهما عندما يكون types ليس NULL. الحالتان هما عندما يكون types->types هو TCL_GLOB_TYPE_DIR أو TCL_GLOB_TYPE_MOUNT (وخاصة عندما تكون العلامات الأخرى خاطئة). في الحالة الأولى، يجب على الدالة سرد الدلائل المحتوي. تستخدم Tcl هذا لتنفيذ globbing المتكرر، لذلك من الضروري أن تنفذ أنظمة الملفات مطابقة الدلائل بشكل صحيح. في الحالة الثانية، مع TCL_GLOB_TYPE_MOUNT، يجب على نظام الملفات سرد نقاط التحميل الموجودة داخل الدليل المعطى بواسطة pathPtr (وفي هذه الحالة، لا يلزم أن يكون pathPtr داخل نفس نظام الملفات - على عكس جميع الحالات الأخرى التي يتم فيها استدعاء هذه الدالة). دعم هذه الحالة أمر بالغ الأهمية إذا كانت Tcl تريد أن يكون لديها انتقالات سلسة بين أنظمة الملفات.

LINKPROC

وظيفة لمعالجة استدعاء Tcl_FSLink. يجب تنفيذها فقط إذا كان نظام الملفات يدعم الروابط، وإلا يمكن أن تكون NULL.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

إذا كان toPtr هو NULL، فسيتم الاستعلام عن محتويات رابط. النتيجة هي كائن Tcl يحدد محتوى الرابط المعطى بواسطة linkNamePtr، أو NULL إذا تعذر قراءة الرابط. الكائن الناتج مملوك للمستدعي (وبالتالي يجب زيادة عداد المراجع الخاص به قبل إعادته). يجب على أي مستدعي استدعاء Tcl_DecrRefCount على هذه النتيجة عندما لم يعد بحاجة إليها. إذا كان toPtr ليس NULL، فيجب على الدالة محاولة إنشاء رابط. في هذه الحالة، يجب أن تكون النتيجة toPtr إذا تم إنشاء الرابط بنجاح، و NULL بخلاف ذلك. في هذه الحالة، الكائن الناتج ليس مملوكًا للمستدعي (أي، لا حاجة لمعالجة عداد المراجع على كلا الجانبين). انظر وثائق Tcl_FSLink للتفسير الصحيح لعلامات linkAction).

LISTVOLUMESPROC

وظيفة لسرد أي وحدات نظام ملفات إضافية أضيفت بواسطة نظام الملفات هذا. يجب تنفيذها فقط إذا كان نظام الملفات يضيف وحدات إلى مقدمة نظام الملفات، بحيث يمكن إعادتها بواسطة file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

يجب أن تكون النتيجة قائمة بالوحدات المضافة بواسطة نظام الملفات هذا، أو NULL (أو قائمة فارغة) إذا لم يتم توفير أي وحدات. يعتبر الكائن المرجع مملوكًا لنظام الملفات (وليس لنواة Tcl)، ولكن يجب توفير عداد مراجع لـ Tcl. ستستخدم Tcl محتويات القائمة ثم تقلل عداد المراجع. هذا يسمح لأنظمة الملفات باختيار ما إذا كانت تريد حقًا الاحتفاظ بـ "قائمة عامة" للوحدات أم لا (إذا لم يكن الأمر كذلك، فإنها تنشئ القائمة في الوقت الفعلي وتمررها إلى Tcl مع عداد مراجع واحد، ثم تنسى القائمة، وإذا كان الأمر كذلك، فإنها تزيد عداد المراجع لقائمتها العامة وتمررها إلى Tcl التي تنسخ المحتويات ثم تقلل عداد المراجع من حيث كانت).

لذلك، تعتبر Tcl القيم المرجعة لهذه الدالة للقراءة فقط.

typedef const char *const *Tcl_FSFileAttrStringsProc(

        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

سلوك هذه الدالة مشابه جدًا لسلوك Tcl_FSStatProc المحدد أعلاه، باستثناء أنها إذا تم تطبيقها على رابط رمزي، فإنها ترجع معلومات حول الرابط، وليس عن الملف الهدف.

COPYFILEPROC

دالة لمعالجة استدعاء Tcl_FSCopyFile. إذا لم يتم تنفيذها، فسوف تعتمد Tcl على open-r و open-w و fcopy كآلية نسخ. لذلك، يجب تنفيذها فقط إذا كان نظام الملفات يمكنه إجراء هذا الإجراء بكفاءة أكبر.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

القيمة المرتجعة هي نتيجة Tcl قياسية تشير إلى ما إذا كان قد حدث خطأ أثناء عملية النسخ. يجب ملاحظة أن destPathPtr هو اسم الملف الذي يجب أن يصبح نسخة من srcPathPtr. إنه ليس أبدًا اسم دليل يمكن نسخ srcPathPtr إليه (أي أن الدالة أبسط بكثير من الأمر الفرعي file copy على مستوى Tcl). يجب ملاحظة أنه إذا كان نظام الملفات يدعم الروابط الرمزية، فستستدعي Tcl دائمًا هذه الدالة وليس copyDirectoryProc عند الضرورة لنسخها (حتى لو كانت روابط رمزية لأدلة). أخيرًا، إذا قرر نظام الملفات أنه لا يمكنه دعم إجراء file copy، فإن استدعاء Tcl_SetErrno(EXDEV) وإرجاع نتيجة غير TCL_OK سيجعل Tcl تستخدم آلياتها الاحتياطية القياسية.

RENAMEFILEPROC

دالة لمعالجة استدعاء Tcl_FSRenameFile. إذا لم يتم تنفيذها، فسوف تعتمد Tcl على آلية نسخ وحذف. لذلك، يجب تنفيذها فقط إذا كان نظام الملفات يمكنه إجراء هذا الإجراء بكفاءة أكبر.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

القيمة المرتجعة هي نتيجة Tcl قياسية تشير إلى ما إذا كان قد حدث خطأ أثناء عملية إعادة التسمية. إذا قرر نظام الملفات أنه لا يمكنه دعم إجراء file rename، فإن استدعاء Tcl_SetErrno(EXDEV) وإرجاع نتيجة غير TCL_OK سيجعل Tcl تستخدم آلياتها الاحتياطية القياسية.

COPYDIRECTORYPROC

دالة لمعالجة استدعاء Tcl_FSCopyDirectory. إذا لم يتم تنفيذها، فسوف تعتمد Tcl على آلية file mkdir تكرارية و file copy كآلية نسخ. لذلك، يجب تنفيذها فقط إذا كان نظام الملفات يمكنه إجراء هذا الإجراء بكفاءة أكبر.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

القيمة المرتجعة هي نتيجة Tcl قياسية تشير إلى ما إذا كان قد حدث خطأ أثناء عملية النسخ. إذا حدث خطأ، يجب أن يكون اسم الملف أو الدليل الذي تسبب في الخطأ في errorPtr. يجب ملاحظة أن destPathPtr هو اسم الدليل الذي يجب أن يصبح نسخة طبق الأصل من srcPathPtr. إنه ليس أبدًا اسم دليل يجب نسخ srcPathPtr إليه (أي أن الدالة أبسط بكثير من الأمر الفرعي file copy على مستوى Tcl). أخيرًا، إذا قرر نظام الملفات أنه لا يمكنه دعم إجراء نسخ الدلائل، فإن استدعاء Tcl_SetErrno(EXDEV) وإرجاع نتيجة غير TCL_OK سيجعل Tcl تستخدم آلياتها الاحتياطية القياسية.

LOADFILEPROC

دالة لمعالجة استدعاء Tcl_FSLoadFile. إذا لم يتم تنفيذها، فسوف تعتمد Tcl على نسخ الملف إلى ملف مؤقت ثم استدعاء Tcl_FSLoadFile على هذا الملف المؤقت. لذلك، يجب تنفيذها فقط إذا كان نظام الملفات يمكنه تحميل الكود مباشرة، أو يمكن تنفيذه ببساطة عن طريق إرجاع TCL_ERROR لتعطيل وظيفة التحميل في نظام الملفات هذا.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

ترجع رمز اكتمال قياسي من Tcl. إذا حدث خطأ، يتم ترك رسالة خطأ في نتيجة interp. تقوم الدالة بتحميل ملف ثنائي ديناميكيًا في الذاكرة. في حالة النجاح، يجب ملء handlePtr برمز لملف تم تحميله ديناميكيًا، ويجب ملء unloadProcPtr بعنوان إجراء. يتم استدعاء إجراء إلغاء التحميل بالـ Tcl_LoadHandle المحدد كمعامل وحيد عندما تحتاج Tcl إلى إلغاء تحميل الملف. على سبيل المثال، لنظام الملفات الأصلي، فإن Tcl_LoadHandle المرتجع هو حاليًا رمز يمكن استخدامه في TclpFindSymbol الخاص للوصول إلى وظائف في الكود الجديد. يمكن لكل نظام ملفات تعريف Tcl_LoadHandle حسب الحاجة. أخيرًا، إذا قرر نظام الملفات أنه لا يمكنه دعم إجراء تحميل الملف، فإن استدعاء Tcl_SetErrno(EXDEV) وإرجاع نتيجة غير TCL_OK سيجعل Tcl تستخدم آلياتها الاحتياطية القياسية.

UNLOADFILEPROC

دالة لإلغاء تحميل ملف تم تحميله سابقًا. إذا تم تنفيذ التحميل، فيجب أيضًا تنفيذ هذه الدالة إذا كان هناك أي إجراء تنظيف ضروري.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

دالة لمعالجة استدعاء Tcl_FSGetCwd. لا تحتاج العديد من أنظمة الملفات إلى تنفيذ هذه الدالة. غالبًا ما يتم استدعاؤها مرة واحدة، إذا تم استدعاء getcwd قبل chdir. يمكن أن تكون NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

إذا كان نظام الملفات يدعم مفهومًا أصليًا للدليل الحالي (الذي قد يتغير بشكل مستقل عن Tcl)، فيجب أن ترجع هذه الدالة هذا الدليل الحالي كنتيجة، أو NULL إذا لم يكن من الممكن تحديد الدليل الحالي (على سبيل المثال، ليس لدى المستخدم الأذونات المناسبة في دليل الدليل الحالي). إذا تم إرجاع NULL، يتم ترك رسالة خطأ في نتيجة interp.

CHDIRPROC

دالة لمعالجة استدعاء Tcl_FSChdir. إذا لم تقم أنظمة الملفات بتنفيذ هذه الدالة، فسيتم محاكاتها من خلال سلسلة من فحوصات الوصول إلى الدليل. بخلاف ذلك، يجب أن تستجيب أنظمة الملفات التي تنفذ هذه الدالة بنتيجة إيجابية إذا كان pathPtr دليلًا صالحًا ويمكن الوصول إليه في نظام الملفات الخاص بها. لا يجب عليها تذكر النتيجة، حيث سيتم تذكرها تلقائيًا بواسطة Tcl_FSGetCwd. يجب أن تنفذ التطبيقات الفعلية الإجراء الصحيح (أي استدعاء واجهة برمجة تطبيقات chdir المناسبة للنظام).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

تقوم الدالة Tcl_FSChdirProc بتغيير الدليل الحالي للتطبيق إلى القيمة المحددة في pathPtr. ترجع الدالة -1 عند حدوث خطأ أو 0 عند النجاح.
