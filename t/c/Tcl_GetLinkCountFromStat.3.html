الوصف

هناك عدة أسباب لاستدعاء دوال واجهة برمجة تطبيقات Tcl_FS (مثل Tcl_FSAccess و Tcl_FSStat) بدلاً من استدعاء دوال نظام المستوى مثل access و stat مباشرة. أولاً، ستعمل عبر الأنظمة الأساسية، لذا يجب أن يعمل الامتداد الذي يستدعيها دون تعديل على Unix و Windows. ثانياً، يقوم تنفيذ Windows لبعض هذه الدوال بإصلاح بعض الأخطاء في استدعاءات مستوى النظام. ثالثاً، تتعامل استدعاءات هذه الدوال مع أي تحويلات للمسار من “Utf إلى أصلي النظام” قد تكون مطلوبة (وقد تخزن نتائج هذه التحويلات مؤقتًا لتحقيق كفاءة أكبر في الاستدعاءات اللاحقة). رابعاً، وربما الأهم من ذلك، كل هذه الدوال “تدرك نظام الملفات الافتراضي”. أي نظام ملفات افتراضي (VFS للاختصار) تم تسجيله (من خلال Tcl_FSRegister) قد يعيد توجيه الوصول إلى الملفات إلى وسائط بديلة أو طرق وصول بديلة. هذا يعني أن كل هذه الدوال (وبالتالي أوامر Tcl المقابلة file و glob و pwd و cd و open وما إلى ذلك) قد تعمل على “ملفات” ليست ملفات أصلية في نظام الملفات الأصلي. هذا يعني أيضًا أن أي امتداد Tcl يصل إلى نظام الملفات (FS للاختصار) من خلال واجهة برمجة التطبيقات هذه يكون تلقائيًا “يدرك نظام الملفات الافتراضي”. بالطبع، إذا وصل امتداد ما إلى نظام الملفات الأصلي مباشرة (من خلال واجهات برمجة التطبيقات الخاصة بالمنصة، على سبيل المثال)، فلا يمكن لـ Tcl اعتراض مثل هذه الاستدعاءات.

إذا تم تسجيل أنظمة ملفات افتراضية مناسبة، فقد تكون “الملفات”، لإعطاء مثالين، عن بعد (على سبيل المثال، موجودة على خادم ftp عن بعد) أو مؤرشفة (على سبيل المثال، داخل أرشيف .zip). توفر أنظمة الملفات المسجلة هذه جدول بحث للدوال لتنفيذ كل أو جزء من الوظائف المدرجة هنا. أخيرًا، تقوم استدعاءات Tcl_FSStat و Tcl_FSLstat بتجريد بنية المخزن المؤقت “struct stat” عما هو معلن عنه بالفعل، مما يسمح باستخدام نفس الكود لكل من الأنظمة التي تدعم الملفات الأكبر من 2 جيجابايت والأنظمة التي لا تدعمها.

واجهة برمجة تطبيقات Tcl_FS هي “Tcl_Obj-ified” وقد تخزن تمثيلات داخلية وسلاسل نصية أخرى متعلقة بالمسار (مثل الدليل الحالي). أحد الآثار الجانبية لذلك هو أنه يجب عدم تمرير قيم ذات عدد مراجع صفر إلى أي من هذه الدوال. إذا تم التعامل مع هذه الاستدعاءات، فقد يؤدي ذلك إلى تسرب في الذاكرة (في ظل بعض الظروف، قد يرغب كود نظام الملفات في الاحتفاظ بمرجع للقيمة الممررة، لذا لا يجب افتراض أنه بعد عودة أي من هذه الاستدعاءات، لا تزال القيمة لديها عدد مراجع صفر - قد تكون قد زادت) أو خطأ تجزئة مباشر (أو خطأ وصول آخر في الذاكرة) بسبب تحرير القيمة في منتصف معالجة القيمة المعقدة المطلوبة لضمان تطبيع المسار وإطلاقه بالكامل لتحديد نظام الملفات. الدرس العملي المستفاد من هذا هو أن

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

هذا خطأ، وقد يسبب أخطاء في الذاكرة. يجب زيادة عدد مراجع path قبل تمريرها، أو تقليلها. لهذا السبب، تعتبر القيم ذات عدد مراجعات صفر مسارات ملفات غير صالحة، وسيؤدي استدعاء أي دالة واجهة برمجة تطبيقات Tcl_FS بقيمة كهذه إلى عدم اتخاذ أي إجراء.

دوال واجهة برمجة تطبيقات FS

Tcl_FSCopyFile تحاول نسخ الملف المعطى بواسطة srcPathPtr إلى اسم المسار المعطى بواسطة destPathPtr. إذا كان المساران المعطيان يقعان في نفس نظام الملفات (وفقًا لـ Tcl_FSGetFileSystemForPath) فيتم استدعاء دالة “نسخ ملف” لنظام الملفات هذا (إذا لم تكن NULL). وإلا، ترجع الدالة -1 وتعين متغير C العام errno إلى رمز خطأ POSIX “EXDEV” (الذي يشير إلى “رابط عبور المجال”).

Tcl_FSCopyDirectory تحاول نسخ الدليل المعطى بواسطة srcPathPtr إلى اسم المسار المعطى بواسطة destPathPtr. إذا كان المساران المعطيان يقعان في نفس نظام الملفات (وفقًا لـ Tcl_FSGetFileSystemForPath) فيتم استدعاء دالة “نسخ ملف” لنظام الملفات هذا (إذا لم تكن NULL). وإلا، ترجع الدالة -1 وتعين متغير C العام errno إلى رمز خطأ POSIX “EXDEV” (الذي يشير إلى “رابط عبور المجال”).

Tcl_FSCreateDirectory تحاول إنشاء الدليل المعطى بواسطة pathPtr عن طريق استدعاء دالة “إنشاء دليل” لنظام الملفات المالك.

Tcl_FSDeleteFile تحاول حذف الملف المعطى بواسطة pathPtr عن طريق استدعاء دالة “حذف ملف” لنظام الملفات المالك.

Tcl_FSRemoveDirectory تحاول إزالة الدليل المعطى بواسطة pathPtr عن طريق استدعاء دالة “إزالة دليل” لنظام الملفات المالك.

Tcl_FSRenameFile تحاول إعادة تسمية الملف أو الدليل المعطى بواسطة srcPathPtr إلى اسم المسار المعطى بواسطة destPathPtr. إذا كان المساران المعطيان يقعان في نفس نظام الملفات (وفقًا لـ Tcl_FSGetFileSystemForPath) فيتم استدعاء دالة “إعادة تسمية ملف” لنظام الملفات هذا (إذا لم تكن NULL). وإلا، ترجع الدالة -1 وتعين متغير C العام errno إلى رمز خطأ POSIX “EXDEV” (الذي يشير إلى “رابط عبور المجال”).

Tcl_FSListVolumes تستدعي كل نظام ملفات لديه دالة “قائمة وحدات التخزين” غير NULL وتطلب منهم إرجاع قائمة وحدات التخزين الجذرية الخاصة بهم. تجمع القيم المرجعة في قائمة يتم إرجاعها إلى المستدعي (بعدد مراجع 0).

Tcl_FSEvalFileEx تقرأ الملف المعطى بواسطة pathPtr باستخدام الترميز المحدد بواسطة encodingName وتقيّم محتوياته كبرنامج Tcl نصي. ترجع نفس المعلومات مثل Tcl_EvalObjEx. إذا كان encodingName NULL، يتم استخدام الترميز النظامي لقراءة محتويات الملف. إذا لم يكن بالإمكان قراءة الملف، فسيتم إرجاع خطأ Tcl لوصف سبب عدم إمكانية قراءة الملف. حرف نهاية الملف للملفات هو “\x1A” (^Z) لجميع الأنظمة الأساسية. إذا كنت بحاجة إلى “^Z” في السلسلة النصية للمقارنة، يمكنك استخدام “\x1A”، والذي سيتم استبداله بأمان بواسطة مترجم Tcl إلى “^Z”. Tcl_FSEvalFile هو نسخة أبسط من Tcl_FSEvalFileEx الذي يستخدم دائمًا الترميز النظامي عند قراءة الملف.

FILESYSTEM INFRASTRUCTURE

These fields contain basic information about the filesystem structure and addresses of functions which are used to associate a particular filesystem with a file path, and deal with the internal handling of path representations, for example copying and freeing such representations.

TYPENAME

The typeName field contains a null-terminated string that identifies the type of the filesystem implemented, e.g. “native”, “zip” or “vfs”.

STRUCTURE LENGTH

The structureLength field is generally implemented as sizeof(Tcl_Filesystem), and is there to allow easier binary backwards compatibility if the size of the structure changes in a future Tcl release.

VERSION

The version field should be set to TCL_FILESYSTEM_VERSION_1.

PATHINFILESYSTEMPROC

The pathInFilesystemProc field contains the address of a function which is called to determine whether a given path value belongs to this filesystem or not. Tcl will only call the rest of the filesystem functions with a path for which this function has returned TCL_OK. If the path does not belong, -1 should be returned (the behavior of Tcl for any other return value is not defined). If TCL_OK is returned, then the optional clientDataPtr output parameter can be used to return an internal (filesystem specific) representation of the path, which will be cached inside the path value, and may be retrieved efficiently by the other filesystem functions. Tcl will simultaneously cache the fact that this path belongs to this filesystem. Such caches are invalidated when filesystem structures are added or removed from Tcl's internal list of known filesystems.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

DUPINTERNALREPPROC

This function makes a copy of a path's internal representation, and is called when Tcl needs to duplicate a path value. If NULL, Tcl will simply not copy the internal representation, which may then need to be regenerated later.

typedef ClientData Tcl_FSDupInternalRepProc(
        ClientData clientData);

FREEINTERNALREPPROC

Free the internal representation. This must be implemented if internal representations need freeing (i.e. if some memory is allocated when an internal representation is generated), but may otherwise be NULL.

typedef void Tcl_FSFreeInternalRepProc(
        ClientData clientData);

INTERNALTONORMALIZEDPROC

Function to convert internal representation to a normalized path. Only required if the filesystem creates pure path values with no string/path representation. The return value is a Tcl value whose string representation is the normalized path.

typedef Tcl_Obj *Tcl_FSInternalToNormalizedProc(
        ClientData clientData);

CREATEINTERNALREPPROC

Function to take a path value, and calculate an internal representation for it, and store that native representation in the value. May be NULL if paths have no internal representation, or if the Tcl_FSPathInFilesystemProc for this filesystem always immediately creates an internal representation for paths it accepts.

typedef ClientData Tcl_FSCreateInternalRepProc(
        Tcl_Obj *pathPtr);

NORMALIZEPATHPROC

Function to normalize a path. Should be implemented for all filesystems which can have multiple string representations for the same path value. In Tcl, every “path” must have a single unique “normalized” string representation. Depending on the filesystem, there may be more than one unnormalized string representation which refers to that path (e.g. a relative path, a path with different character case if the filesystem is case insensitive, a path contain a reference to a home directory such as “~”, a path containing symbolic links, etc). If the very last component in the path is a symbolic link, it should not be converted into the value it points to (but its case or other aspects should be made unique). All other path components should be converted from symbolic links. This one exception is required to agree with Tcl's semantics with file delete, file rename, file copy operating on symbolic links. This function may be called with nextCheckpoint either at the beginning of the path (i.e. zero), at the end of the path, or at any intermediate file separator in the path. It will never point to any other arbitrary position in the path. In the last of the three valid cases, the implementation can assume that the path up to and including the file separator is known and normalized.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

FILESYSTEM OPERATIONS

The fields in this section of the structure contain addresses of functions which are called to carry out the basic filesystem operations. A filesystem which expects to be used with the complete standard Tcl command set must implement all of these. If some of them are not implemented, then certain Tcl commands may fail when operating on paths within that filesystem. However, in some instances this may be desirable (for example, a read-only filesystem should not implement the last four functions, and a filesystem which does not support symbolic links need not implement the readlink function, etc. The Tcl core expects filesystems to behave in this way).

FILESYSTEMPATHTYPEPROC

Function to determine the type of a path in this filesystem. May be NULL, in which case no type information will be available to users of the filesystem. The “type” is used only for informational purposes, and should be returned as the string representation of the Tcl_Obj which is returned. A typical return value might be “networked”, “zip” or “ftp”. The Tcl_Obj result is owned by the filesystem and so Tcl will increment the reference count of that value if it wishes to retain a reference to it.

typedef Tcl_Obj *Tcl_FSFilesystemPathTypeProc(
        Tcl_Obj *pathPtr);

FILESYSTEMSEPARATORPROC

Function to return the separator character(s) for this filesystem. This need only be implemented if the filesystem wishes to use a different separator than the standard string “/”. Amongst other uses, it is returned by the file separator command. The return value should be a value with reference count of zero.

typedef Tcl_Obj *Tcl_FSFilesystemSeparatorProc(
        Tcl_Obj *pathPtr);

STATPROC

Function to process a Tcl_FSStat call. Must be implemented for any reasonable filesystem, since many Tcl level commands depend crucially upon it (e.g. file atime, file isdirectory, file size, glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

The Tcl_FSStatProc fills the stat structure statPtr with information about the specified file. You do not need any access rights to the file to get this information but you need search rights to all directories named in the path leading to the file. The stat structure includes info regarding device, inode (always 0 on Windows), privilege mode, nlink (always 1 on Windows), user id (always 0 on Windows), group id (always 0 on Windows), rdev (same as device on Windows), size, last access time, last modification time, and last metadata change time.

If the file represented by pathPtr exists, the Tcl_FSStatProc returns 0 and the stat structure is filled with data. Otherwise, -1 is returned, and no stat info is given.

ACCESSPROC

Function to process a Tcl_FSAccess call. Must be implemented for any reasonable filesystem, since many Tcl level commands depend crucially upon it (e.g. file exists, file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

The Tcl_FSAccessProc checks whether the process would be allowed to read, write or test for existence of the file (or other filesystem object) whose name is in pathPtr. If the pathname refers to a symbolic link, then the permissions of the file referred by this symbolic link should be tested.

On success (all requested permissions granted), zero is returned. On error (at least one bit in mode asked for a permission that is denied, or some other error occurred), -1 is returned.

PATHINFILESYSTEMPROC

يحتوي الحقل pathInFilesystemProc على عنوان دالة يتم استدعاؤها لتحديد ما إذا كانت قيمة مسار معينة تنتمي إلى نظام الملفات هذا أم لا. ستستدعي Tcl فقط باقي وظائف نظام الملفات لمسار أعادت هذه الدالة من أجله TCL_OK. إذا كان المسار لا ينتمي، فيجب إرجاع -1 (سلوك Tcl لأي قيمة إرجاع أخرى غير محدد). إذا تم إرجاع TCL_OK، فيمكن استخدام المعلمة الاختيارية clientDataPtr لإرجاع تمثيل داخلي (خاص بنظام الملفات) للمسار، والذي سيتم تخزينه مؤقتًا داخل قيمة المسار، ويمكن استرداده بكفاءة بواسطة وظائف نظام الملفات الأخرى. ستقوم Tcl بتخزين حقيقة أن هذا المسار ينتمي إلى نظام الملفات هذا بشكل متزامن. يتم إبطال صلاحية هذه المخازن المؤقتة عند إضافة أو إزالة هياكل أنظمة الملفات من القائمة الداخلية لأنظمة الملفات المعروفة لدى Tcl.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

تقوم هذه الدالة بنسخ تمثيل داخلي للمسار، ويتم استدعاؤها عندما تحتاج Tcl إلى تكرار قيمة المسار. إذا كانت NULL، فلن تقوم Tcl بنسخ التمثيل الداخلي ببساطة، والذي قد يحتاج بعد ذلك إلى إعادة إنشائه لاحقًا.

typedef ClientData Tcl_FSDupInternalRepProc(
        ClientData clientData);

typedef void Tcl_FSFreeInternalRepProc(
        ClientData clientData);

typedef Tcl_Obj *Tcl_FSInternalToNormalizedProc(

typedef ClientData Tcl_FSCreateInternalRepProc(

NORMALIZEPATHPROC

دالة لتسوية المسار. يجب تنفيذها لجميع أنظمة الملفات التي يمكن أن يكون لها تمثيلات نصية متعددة لنفس قيمة المسار. في Tcl، يجب أن يكون لكل "مسار" تمثيل نصي "قياسي" فريد واحد. اعتمادًا على نظام الملفات، قد يكون هناك أكثر من تمثيل نصي غير قياسي يشير إلى هذا المسار (على سبيل المثال، مسار نسبي، مسار بحالة أحرف مختلفة إذا كان نظام الملفات غير حساس لحالة الأحرف، مسار يحتوي على مرجع لدليل المنزل مثل "~"، مسار يحتوي على روابط رمزية، إلخ). إذا كان المكون الأخير في المسار رابطًا رمزيًا، فلا يجب تحويله إلى القيمة التي يشير إليها (ولكن يجب جعل حالته أو جوانبه الأخرى فريدة). يجب تحويل جميع مكونات المسار الأخرى من الروابط الرمزية. هذا الاستثناء الواحد مطلوب للتوافق مع دلالات Tcl مع file delete و file rename و file copy التي تعمل على الروابط الرمزية. قد يتم استدعاء هذه الدالة مع nextCheckpoint إما في بداية المسار (أي صفر)، أو في نهاية المسار، أو عند أي فاصل ملف وسيط في المسار. لن يشير أبدًا إلى أي موضع عشوائي آخر في المسار. في الحالة الأخيرة من الحالات الثلاث الصالحة، يمكن للتنفيذ افتراض أن المسار حتى بما في ذلك فاصل الملف معروف وموحد.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

عمليات نظام الملفات

تحتوي الحقول في هذا القسم من الهيكل على عناوين الوظائف التي يتم استدعاؤها لتنفيذ عمليات نظام الملفات الأساسية. يجب على نظام الملفات الذي يتوقع استخدامه مع مجموعة الأوامر القياسية الكاملة لـ Tcl تنفيذ كل هذه الوظائف. إذا لم يتم تنفيذ بعضها، فقد تفشل أوامر Tcl معينة عند العمل على مسارات داخل نظام الملفات هذا. ومع ذلك، قد يكون هذا مرغوبًا فيه في بعض الحالات (على سبيل المثال، يجب ألا ينفذ نظام ملفات للقراءة فقط الوظائف الأربع الأخيرة، ونظام الملفات الذي لا يدعم الروابط الرمزية لا يحتاج إلى تنفيذ وظيفة readlink، وما إلى ذلك. تتوقع نواة Tcl أن تتصرف أنظمة الملفات بهذه الطريقة).

FILESYSTEMPATHTYPEPROC

دالة لتحديد نوع المسار في نظام الملفات هذا. يمكن أن تكون NULL، وفي هذه الحالة لن تتوفر أي معلومات نوع للمستخدمين لنظام الملفات. يتم استخدام "النوع" فقط لأغراض إعلامية، ويجب إرجاعه كتمثيل نصي لكائن Tcl الذي يتم إرجاعه. قد تكون القيمة المرتجعة النموذجية "networked" أو "zip" أو "ftp". الكائن المرجع مملوك لنظام الملفات، لذا ستقوم Tcl بزيادة عدد المراجع لهذا الكائن إذا رغبت في الاحتفاظ بمرجع له.

typedef Tcl_Obj *Tcl_FSFilesystemPathTypeProc(
        Tcl_Obj *pathPtr);

FILESYSTEMSEPARATORPROC

دالة لإرجاع حرف (أو أحرف) الفاصل لنظام الملفات هذا. لا تحتاج هذه الدالة إلا إلى التنفيذ إذا كان نظام الملفات يرغب في استخدام فاصل مختلف عن السلسلة القياسية "/" . من بين الاستخدامات الأخرى، يتم إرجاعها بواسطة الأمر file separator. يجب أن تكون القيمة المرتجعة كائنًا ذا عدد مراجع صفر.

typedef Tcl_Obj *Tcl_FSFilesystemSeparatorProc(
        Tcl_Obj *pathPtr);

STATPROC

دالة لمعالجة استدعاء Tcl_FSStat. يجب تنفيذها لأي نظام ملفات معقول، حيث تعتمد العديد من أوامر مستوى Tcl عليها بشكل حاسم (على سبيل المثال، file atime، file isdirectory، file size، glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

تقوم Tcl_FSStatProc بملء بنية stat statPtr بمعلومات حول الملف المحدد. لا تحتاج إلى أي حقوق وصول للملف للحصول على هذه المعلومات، ولكنك تحتاج إلى حقوق بحث لجميع الأدلة المسماة في المسار المؤدي إلى الملف. تتضمن بنية stat معلومات تتعلق بالجهاز، inode (دائمًا 0 على Windows)، وضع الامتيازات، nlink (دائمًا 1 على Windows)، معرف المستخدم (دائمًا 0 على Windows)، معرف المجموعة (دائمًا 0 على Windows)، rdev (نفس الجهاز على Windows)، الحجم، وقت آخر وصول، وقت آخر تعديل، ووقت آخر تغيير للبيانات الوصفية.

إذا كان الملف الذي يمثله pathPtr موجودًا، فإن Tcl_FSStatProc ترجع 0 ويتم ملء بنية stat بالبيانات. بخلاف ذلك، يتم إرجاع -1، ولا يتم تقديم أي معلومات stat.

ACCESSPROC

دالة لمعالجة استدعاء Tcl_FSAccess. يجب تنفيذها لأي نظام ملفات معقول، حيث تعتمد العديد من أوامر مستوى Tcl عليها بشكل حاسم (على سبيل المثال، file exists، file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

تتحقق Tcl_FSAccessProc مما إذا كانت العملية مسموح لها بالقراءة أو الكتابة أو التحقق من وجود الملف (أو كائن نظام الملفات الآخر) الذي يحمل اسمه pathPtr. إذا كان اسم المسار يشير إلى رابط رمزي، فيجب اختبار أذونات الملف الذي يشير إليه هذا الرابط الرمزي.

عند النجاح (تم منح جميع الأذونات المطلوبة)، يتم إرجاع صفر. عند الخطأ (طلب أحد البتات في mode إذنًا مرفوضًا، أو حدث خطأ آخر)، يتم إرجاع -1.

OPENFILECHANNELPROC

دالة لمعالجة استدعاء Tcl_FSOpenFileChannel. يجب تنفيذها لأي نظام ملفات يرغب في دعم عمليات الإدخال/الإخراج على الملفات. يجب على هذه الدالة فتح الملف المحدد بواسطة pathPtr في الوضع المحدد بواسطة سلسلة mode وبالأذونات permissions المعطاة. تُستخدم وسيطة الأذونات فقط على أنظمة Unix، لتعيين وضع الملفات المنشأة حديثًا.

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        const char *mode,
        int permissions);

يجب أن ترجع هذه الدالة مقبض قناة في حالة النجاح، أو NULL في حالة حدوث خطأ. إذا تم إرجاع NULL، فيجب كتابة رسالة خطأ إلى نتيجة المفسر.

FILESYSTEM CORE FUNCTIONS

Estas son las funciones que deben implementarse para cualquier sistema de archivos que Tcl pueda utilizar para manipulación de archivos. Si un sistema de archivos no implementa una de estas funciones, Tcl puede caer a un mecanismo de respaldo de alguna manera, aunque esto puede ser menos eficiente o incluso imposible.

OPENFILEPROC

Función para procesar una llamada a Tcl_FSOpenFile. Esta función es la más importante, ya que Tcl la usará para abrir archivos para lectura y escritura. Si esta función no está implementada, el sistema de archivos se considera de solo lectura (o no utilizable en absoluto).

typedef Tcl_Channel Tcl_FSOpenFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode);

El valor de retorno es un Tcl_Channel si la operación fue exitosa, o NULL si ocurrió un error. Si ocurre un error, se deja un mensaje de error en el resultado del interp. El argumento mode es una combinación de banderas estándar de C, como O_RDONLY, O_WRONLY, O_RDWR, O_CREAT, O_TRUNC, etc., que especifican cómo se debe abrir el archivo.

STATPROC

Función para procesar una llamada a Tcl_FSStat. Debe implementarse a menos que el sistema de archivos sea de solo lectura.

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

El valor de retorno es un resultado estándar de Tcl indicando si se produjo un error durante el proceso. Si es exitoso, statPtr será poblado con información sobre el archivo o directorio especificado por pathPtr. La información incluye tamaño, permisos, tiempo de modificación, etc.

CREATEDIRECTORYPROC

Función para procesar una llamada a Tcl_FSCreateDirectory. Debe implementarse a menos que el FS sea solo-lectura.

typedef int Tcl_FSCreateDirectoryProc(
        Tcl_Obj *pathPtr);

El valor de retorno es un resultado estándar de Tcl indicando si se produjo un error durante el proceso. Si es exitoso, se debería haber añadido una nueva carpeta al sistema de archivos en la ubicación especificada por pathPtr.

REMOVEDIRECTORYPROC

Función para procesar una llamada a Tcl_FSRemoveDirectory. Debe implementarse a menos que el FS sea solo-lectura.

typedef int Tcl_FSRemoveDirectoryProc(
        Tcl_Obj *pathPtr,
        int recursive,
        Tcl_Obj **errorPtr);

El valor de retorno es un resultado estándar de Tcl indicando si se produjo un error durante el proceso. Si es exitoso, la carpeta especificada por pathPtr debería haber sido eliminada del sistema de archivos. Si el flag recursive está dado, una carpeta no vacía debería haber sido eliminada sin error. Si el flag no está dado, y la carpeta es no vacía, se debería lanzar un error POSIX "EEXIST". Si hay un error, el nombre del archivo o carpeta que causó el error debería estar en errorPtr.

DELETEFILEPROC

Función para procesar una llamada a Tcl_FSDeleteFile. Debe implementarse a menos que el FS sea solo-lectura.

typedef int Tcl_FSDeleteFileProc(
        Tcl_Obj *pathPtr);

El valor de retorno es un resultado estándar de Tcl indicando si se produjo un error durante el proceso. Si es exitoso, el archivo especificado por pathPtr debería haber sido eliminado del sistema de archivos. Debe tener en cuenta que, si el sistema de archivos soporta enlaces simbólicos, Tcl llamará esta función y no Tcl_FSRemoveDirectoryProc cuando sea necesario para eliminarlos (incluso si son enlaces simbólicos a directorios).

FILESYSTEM EFFICIENCY

Estas funciones no deben implementarse para un determinado sistema de archivos, ya que el núcleo tiene una implementación de fallback disponible. Véase cada descripción individual para las consecuencias de dejar el campo NULL.

LSTATPROC

Función para procesar una llamada a Tcl_FSLstat. Si no está implementada, Tcl intentará usar statProc definido anteriormente. Por lo tanto, solo debe implementarse si el sistema de archivos puede diferenciar entre llamadas stat y lstat.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

El comportamiento de esta función es muy similar al de Tcl_FSStatProc definido anteriormente, a menos que se aplique a un enlace simbólico, en cuyo caso devuelve información sobre el enlace, no sobre el archivo objetivo.

COPYFILEPROC

Función para procesar una llamada a Tcl_FSCopyFile. Si no está implementada, Tcl recurrirá al mecanismo de open-r, open-w y fcopy para realizar una copia. Por lo tanto, solo debe implementarse si el sistema de archivos puede realizar esa acción de forma más eficiente.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

El valor de retorno es un resultado estándar de Tcl indicando si se produjo un error durante el proceso de copia. Tenga en cuenta que destPathPtr es el nombre del archivo que debe convertirse en la copia de srcPathPtr. No es el nombre de un directorio en el cual srcPathPtr podría ser copiado (es decir, la función es mucho más simple que el subcomando file copy en el nivel Tcl). Tenga en cuenta que, si el sistema de archivos soporta enlaces simbólicos, Tcl llamará esta función y no copyDirectoryProc cuando sea necesario para copiarlos (incluso si son enlaces simbólicos a directorios). Finalmente, si el sistema de archivos determina que no puede soportar la acción de copiar archivos, se llamará Tcl_SetErrno(EXDEV) y se devolverá un resultado no TCL_OK para que Tcl use sus mecanismos de reemplazo estándar.

RENAMEFILEPROC

Función para procesar una llamada a Tcl_FSRenameFile. Si no está implementada, Tcl recurrirá a un mecanismo de copia y eliminación. Por lo tanto, solo debe implementarse si el sistema de archivos puede realizar esa acción de forma más eficiente.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

El valor de retorno es un resultado estándar de Tcl indicando si se produjo un error durante el proceso de renombrado. Si el sistema de archivos determina que no puede soportar la acción de renombrado, se llamará Tcl_SetErrno(EXDEV) y se devolverá un resultado no TCL_OK para que Tcl use sus mecanismos de reemplazo estándar.

COPYDIRECTORYPROC

Función para procesar una llamada a Tcl_FSCopyDirectory. Si no está implementada, Tcl recurrirá a un mecanismo recursivo de file mkdir, file copy. Por lo tanto, solo debe implementarse si el sistema de archivos puede realizar esa acción de forma más eficiente.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

El valor de retorno es un resultado estándar de Tcl indicando si se produjo un error durante el proceso de copia. Si hay un error, el nombre del archivo o carpeta que causó el error debería estar en errorPtr. Tenga en cuenta que destPathPtr es el nombre de la carpeta que debe convertirse en el espejo de srcPathPtr. No es el nombre de un directorio en el cual srcPathPtr debería ser copiado (es decir, la función es mucho más simple que el subcomando file copy en el nivel Tcl). Finalmente, si el sistema de archivos determina que no puede soportar la acción de copiar directorios, se llamará Tcl_SetErrno(EXDEV) y se devolverá un resultado no TCL_OK para que Tcl use sus mecanismos de reemplazo estándar.

LOADFILEPROC

Función para procesar una llamada a Tcl_FSLoadFile. Si no está implementada, Tcl recurrirá a una copia a un archivo temporal, seguido de una llamada a Tcl_FSLoadFile en ese archivo temporal. Por lo tanto, solo debe implementarse si el sistema de archivos puede cargar el código directamente, o puede implementarse simplemente para devolver TCL_ERROR para desactivar la funcionalidad de carga en este sistema de archivos.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

Devuelve un código de finalización estándar de Tcl. Si hay un error, un mensaje de error se queda en el resultado del interp. La función carga dinámicamente un archivo de código binario en la memoria. En caso de éxito, handlePtr debe estar poblado con un token para el archivo cargado dinámicamente, y unloadProcPtr debe estar poblado con la dirección de un procedimiento. El procedimiento de descarga se llamará con el Tcl_LoadHandle dado como único parámetro cuando Tcl necesite descargar el archivo. Por ejemplo, para el sistema de archivos nativo, el Tcl_LoadHandle devuelto es actualmente un token que puede usarse en el TclpFindSymbol privado para acceder a funciones en el nuevo código. Cada sistema de archivos puede definir el Tcl_LoadHandle como lo requiera. Finalmente, si el sistema de archivos determina que no puede soportar la acción de carga de archivos, se llamará Tcl_SetErrno(EXDEV) y se devolverá un resultado no TCL_OK para que Tcl use sus mecanismos de reemplazo estándar.

UNLOADFILEPROC

Función para descargar un archivo que fue previamente cargado con éxito. Si se implementó la carga, esta también debe ser implementada si hay alguna acción de limpieza requerida.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

Función para procesar una llamada a Tcl_FSGetCwd. La mayoría de los sistemas de archivos no necesitan implementar esto. A veces se llama una vez, si getcwd es llamado antes de chdir. Puede ser NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

Si el sistema de archivos soporta una noción nativa de directorio de trabajo (que podría cambiar independientemente de Tcl), esta función debería devolver ese cwd como resultado, o NULL si el directorio de trabajo no puede ser determinado (por ejemplo, el usuario no tiene permisos adecuados en el directorio cwd). Si se devuelve NULL, se deja un mensaje de error en el resultado del interp.

CHDIRPROC

Función para procesar una llamada a Tcl_FSChdir. Si los sistemas de archivos no implementan esto, se emulará mediante una serie de comprobaciones de acceso a directorios. De lo contrario, los sistemas de archivos que implementan esto deben responder con un resultado positivo si pathPtr es un directorio válido y accesible en su sistema de archivos. No deben recordar el resultado, ya que ese será recordado automáticamente por Tcl_FSGetCwd. Las implementaciones reales deberían realizar la acción correcta (es decir, llamar a la API de sistema chdir correspondiente).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

La función Tcl_FSChdirProc cambia el directorio de trabajo de la aplicación al valor especificado en pathPtr. La función devuelve -1 en caso de error o 0 en caso de éxito.
