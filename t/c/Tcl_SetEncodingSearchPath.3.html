مقدمة

تقوم هذه الروتينات بالتحويل بين تمثيل الأحرف الداخلي لـ Tcl، UTF-8، وتمثيلات الأحرف التي تستخدمها أنظمة التشغيل أو أنظمة الملفات المختلفة، مثل Unicode أو ASCII أو Shift-JIS. عند العمل على السلاسل، مثل الحصول على أسماء الملفات أو عرض الأحرف باستخدام خطوط دولية، يجب ترجمة السلاسل إلى تنسيق واحد أو ربما تنسيقات متعددة يمكن لاستدعاءات النظام المختلفة استخدامها. على سبيل المثال، في محطة Unix يابانية، قد يحصل المستخدم على اسم ملف ممثل في ترميز الملف EUC-JP ثم يترجم الأحرف إلى ترميز الخط jisx0208 لعرض اسم الملف في عنصر واجهة Tk. الغرض من حزمة الترميز هو المساعدة في سد فجوة الترجمة. يوفر UTF-8 أرضية وسيطة لجميع الترميزات المختلفة. في المثال أعلاه، سيتم ترجمة النص إلى UTF-8 من أي ترميز ملف يستخدمه نظام التشغيل. ثم سيتم ترجمته من UTF-8 إلى أي ترميز خط تتطلبه روتينات العرض.

بعض الترميزات الأساسية مدمجة في Tcl. يمكن تعريف أخرى بواسطة المستخدم أو تحميلها ديناميكيًا من ملفات الترميز بطريقة مستقلة عن المنصة.

الوصف

Tcl_GetEncoding يبحث عن ترميز بالنظر إلى name الخاص به. قد يشير الاسم إلى ترميز Tcl مدمج، ترميز معرف من قبل المستخدم مسجل عن طريق استدعاء Tcl_CreateEncoding، أو ملف ترميز قابل للتحميل ديناميكيًا. القيمة المرجعة هي رمز يمثل الترميز ويمكن استخدامه في استدعاءات لاحقة للإجراءات مثل Tcl_GetEncodingName، Tcl_FreeEncoding، و Tcl_UtfToExternal. إذا كان الاسم لا يشير إلى أي ترميز معروف أو قابل للتحميل، يتم إرجاع NULL ويتم إرجاع رسالة خطأ في interp.

تحتفظ حزمة الترميز بقاعدة بيانات لجميع الترميزات قيد الاستخدام حاليًا. في المرة الأولى التي يتم فيها رؤية name، تقوم Tcl_GetEncoding بإرجاع ترميز بعدد مرجعي يبلغ 1. إذا تم طلب نفس name عدة مرات أخرى، يتم زيادة عدد المراجع لهذا الترميز دون عبء تخصيص ترميز جديد وجميع هياكل البيانات المرتبطة به.

عندما لا يعود encoding مطلوبًا، يجب استدعاء Tcl_FreeEncoding لتحريره. عندما لا يعود encoding قيد الاستخدام في أي مكان (أي، تم تحريره بالقدر نفسه الذي تم الحصول عليه به) ستقوم Tcl_FreeEncoding بتحرير جميع المساحات التي كان يستخدمها الترميز وحذفه من قاعدة البيانات.

Tcl_GetEncodingFromObj يعامل التمثيل السلسلي لـ objPtr كاسم ترميز، ويبحث عن ترميز بهذا الاسم، تمامًا كما تفعل Tcl_GetEncoding. عند العثور على ترميز، يتم تخزينه مؤقتًا داخل قيمة objPtr للإشارة المستقبلية، ويتم كتابة رمز Tcl_Encoding إلى مساحة Mantén toda la estructura del archivo. El puntero que se indica por encodingPtr y el valor TCL_OK se devuelve. Si no existe tal codificación, se devuelve el valor TCL_ERROR y no se realiza ninguna escritura en *encodingPtr. De manera similar a Tcl_GetEncoding, el llamante debe llamar a Tcl_FreeEncoding sobre el token de codificación resultante cuando ese token no será más usado.

Tcl_ExternalToUtfDString convierte un buffer de fuente src de la codificación especificada encoding en UTF-8. Los bytes convertidos se almacenan en dstPtr, que se termina con el cero de la codificación específica. El llamante debe llamar eventualmente a Tcl_DStringFree para liberar cualquier información almacenada en dstPtr. Cuando se convierte, si alguna de las caractéres en el buffer de fuente no puede representarse en la codificación de destino, se usará una caracter por defecto. El valor devuelto es un puntero al valor almacenado en el DString.

Tcl_ExternalToUtf convierte un buffer de fuente src de la codificación especificada encoding en UTF-8. Se convierten hasta srcLen bytes del buffer de fuente, y hasta dstLen bytes se almacenan en dst. En todos los casos, *srcReadPtr se llena con el número de bytes convertidos de src, y *dstWrotePtr se llena con el número de bytes almacenados en dst. El valor devuelto es uno de los siguientes:

TCL_OK
Todos los bytes de src fueron convertidos.
TCL_CONVERT_NOSPACE
El buffer de destino no era suficiente para todos los datos convertidos; se convertieron tantos caracteres como podían.
TCL_CONVERT_MULTIBYTE
Los últimos pocos bytes del buffer de fuente eran el inicio de una secuencia de múltiples bytes, pero más bytes eran necesarios para completar esta secuencia. Una llamada posterior al procedimiento de conversión debe pasar un buffer que contenga los bytes no convertidos que aún estén en src más algunos bytes adicionales del flujo de entrada para convertir adecuadamente la secuencia de múltiples bytes que se ha dividido.
TCL_CONVERT_SYNTAX
El buffer de fuente contuvo una secuencia de caracteres inválida. Esto puede ocurrir si el flujo de entrada ha sido dañado o si el método de codificación fue mal identificado.
TCL_CONVERT_UNKNOWN
El buffer de fuente contuvo un carácter que no podía representarse en la codificación de destino y TCL_ENCODING_STOPONERROR fue especificado.

Tcl_UtfToExternalDString convierte un buffer de fuente src de UTF-8 en la codificación especificada encoding. Los bytes convertidos se almacenan en dstPtr, que se termina con el cero de la codificación específica. El llamante debe llamar eventualmente a Tcl_DStringFree para liberar cualquier información almacenada en dstPtr. Cuando se convierte, si alguna de las caractéres en el buffer de fuente no puede representarse en la codificación de destino, se usará una caracter por defecto. El valor devuelto es un puntero al valor almacenado en el DString.

Tcl_UtfToExternal convierte un buffer de fuente src de UTF-8 en la codificación especificada encoding. Se convierten hasta srcLen bytes del buffer de fuente, y hasta dstLen bytes se almacenan en dst. En todos los casos, *srcReadPtr se llena con el número de bytes convertidos de src, y *dstWrotePtr se llena con el número de bytes almacenados en dst. Los valores devueltos son los mismos que para Tcl_ExternalToUtf.

Tcl_WinUtfToTChar y Tcl_WinTCharToUtf son funciones de conveniencia solo para Windows que convierten entre UTF-8 y cadenas de Windows basadas en el tipo TCHAR, que por conveniencia es una carácter Unicode en Windows NT.

Tcl_GetEncodingName es aproximadamente el inverso de Tcl_GetEncoding. Dada una codificación encoding, el valor devuelto es el argumento name que fue usado para crear la codificación. El string devuelto por Tcl_GetEncodingName solo es garantizado para persistir hasta que la codificación encoding sea eliminada. El llamante debe no modificar este string.

Tcl_SetSystemEncoding establece la codificación predeterminada que se debe usar cuando el usuario pasa un valor nulo para el argumento encoding a cualquier función de codificación. Si name es nulo, la codificación del sistema se resetea a la codificación predeterminada, binary. Si el nombre no refiere a ninguna codificación conocida o cargaable, se devuelve TCL_ERROR y se deja un mensaje de error en interp. De otra forma, este procedimiento incrementa el contador de referencia de la nueva codificación del sistema, decremente el contador de referencia de la codificación antigua, y devuelve TCL_OK.

Tcl_GetEncodingNameFromEnvironment proporciona un medio para que la biblioteca Tcl reporte el nombre de la codificación que creye ser el correcto para usar como codificación del sistema, basado en llamadas de sistema y examen del entorno adecuado para la plataforma. Recibe bufPtr, un puntero a un Tcl_DString inicializado o liberado, y escribe el nombre de la codificación en él. El valor devuelto es el valor de Tcl_DStringValue.

Tcl_GetEncodingNames establece el resultado interp a una lista consistente en los nombres de todas las codificaciones definidas o dinámicamente cargables, buscando en la ruta de codificación especificada por Tcl_SetDefaultEncodingDir. Este procedimiento no asegura que los archivos dinámicamente cargables contengan datos válidos, pero solo asegura que existan.

Tcl_CreateEncoding define una nueva codificación y registra los procedimientos C que se llaman para convertir entre la codificación y UTF-8. Las codificaciones creadas por Tcl_CreateEncoding son thereafter visibles en la base de datos usada por Tcl_GetEncoding. De manera similar a Tcl_GetEncoding, el valor devuelto es un token que representa la codificación y puede usarse en llamadas posteriores a otras funciones de codificación. Tcl_CreateEncoding devuelve una codificación con un contador de referencia de 1. Si ya existe una codificación con el nombre especificado name, su entrada en la base de datos se reemplaza con la nueva codificación; el token de la antigua codificación permanece válido y continúa comportándose como antes, pero los usuarios del nuevo token ahora llaman a los procedimientos de codificación nuevos.

El argumento typePtr de Tcl_CreateEncoding contiene información sobre el nombre de la codificación y los procedimientos que se llamarán para convertir entre esta codificación y UTF-8. Se define como:

typedef struct Tcl_EncodingType {
    const char *encodingName;
    Tcl_EncodingConvertProc *toUtfProc;
    Tcl_EncodingConvertProc *fromUtfProc;
    Tcl_EncodingFreeProc *freeProc;
    ClientData clientData;
    int nullSize;
} Tcl_EncodingType;

El encodingName proporciona un nombre para la codificación, por el cual se puede referir en otros procedimientos como Tcl_GetEncoding. El toUtfProc refiere a un procedimiento de callback para invocar para convertir texto de esta codificación a UTF-8. El fromUtfProc refiere a un procedimiento de callback para invocar para convertir texto de UTF-8 a esta codificación. El freeProc refiere a un procedimiento de callback para invocar cuando esta codificación se elimina. El campo freeProc puede ser nulo. El clientData contiene un valor de una palabra arbitrario pasado a toUtfProc, fromUtfProc y freeProc cuando se llamen. Generalmente, este es un puntero a un conjunto de datos que contiene información específica de la codificación, que puede usarse por los procedimientos de callback. Por ejemplo, dos codificaciones muy similares como ascii y macRoman pueden usar el mismo procedimiento de callback, pero usan diferentes valores de clientData para controlar su comportamiento. El nullSize especifica el número de bytes cero que signifiquen el final de cadena en esta codificación. Debe ser 1 (para codificaciones de un byte o múltiples bytes como ASCII o Shift-JIS) o 2 (para codificaciones de dos bytes como Unicode). Las codificaciones de tamaño constante con 3 o más bytes por carácter (como CNS11643) no son aceptadas.

Los procedimientos de callback toUtfProc y fromUtfProc deben coincidir con el tipo Tcl_EncodingConvertProc:

typedef int Tcl_EncodingConvertProc(
        ClientData clientData,
        const char *src,
        int srcLen,
        int flags,
        Tcl_EncodingState *statePtr,
        char *dst,
        int dstLen,
        int *srcReadPtr,
        int *dstWrotePtr,
        int *dstCharsPtr);

Los procedimientos toUtfProc y fromUtfProc se llaman por Tcl_ExternalToUtf o Tcl_UtfToExternal para realizar la conversión real. El parámetro clientData de estos procedimientos es el mismo que el campo clientData especificado en Tcl_CreateEncoding cuando la codificación fue creada. Los argumentos restantes a los procedimientos de callback son los mismos que los argumentos, documentados en la parte superior, para Tcl_ExternalToUtf o Tcl_UtfToExternal, con las siguientes excepciones. Si el argumento srcLen de una de estas funciones de nivel alto es negativo, el valor pasado al procedimiento de callback será el largo adecuado de la codificación de fuente src. Si algún de los argumentos srcReadPtr, dstWrotePtr, o dstCharsPtr de una de estas funciones de nivel alto es nulo, el valor correspondiente pasado al procedimiento de callback será un lugar no nulo.

El procedimiento de callback freeProc, si no es nulo, debe coincidir con el tipo Tcl_EncodingFreeProc:

typedef void Tcl_EncodingFreeProc(
        ClientData clientData);

Este freeProc función se llama cuando se elimina la codificación. El parámetro clientData es el mismo que el campo clientData especificado en Tcl_CreateEncoding cuando la codificación fue creada.

Tcl_GetEncodingSearchPath y Tcl_SetEncodingSearchPath se llaman para acceder y configurar la lista de directorios de sistema que se buscan para archivos de datos de codificación. El valor devuelto por Tcl_GetEncodingSearchPath es el valor almacenado por la última llamada exitosa a Tcl_SetEncodingSearchPath. Si no se han realizado llamadas a Tcl_SetEncodingSearchPath, Tcl calculará un valor inicial basado en el entorno. Hay una ruta de búsqueda de codificación para el proceso completo, compartida por todas las hilos en el proceso.

Tcl_SetEncodingSearchPath almacena searchPath y devuelve TCL_OK, excepto si searchPath no es una lista válida de Tcl, en cuyo caso se devuelve TCL_ERROR. Los elementos de searchPath son los mismos que los argumentos, documentados en la parte superior, para Tcl_ExternalToUtf o Tcl_UtfToExternal, con la excepción de que el argumento srcLen puede ser negativo.

INTRODUCTION

Tcl supports a wide variety of character encodings. Some of these encodings are built into the Tcl library, but many are dynamically loaded from external files. This manual page describes the mechanisms Tcl uses to find and load these external encoding files.

DESCRIPTION

When Tcl needs to load an encoding that is not built-in, it searches a list of directories for a file named encodingName.enc. This list of directories is called the searchPath. The default searchPath is initialized to contain a single directory, defaultEncodingDir, which is typically derived from the Tcl library installation location.

The Tcl_GetEncodingSearchPath procedure returns the current search path as a null-terminated array of strings. The caller is responsible for freeing the memory for this array using Tcl_Free. This array will never be empty, and its elements are guaranteed to be existing readable filesystem directories. However, they may be removed by other threads between the call to Tcl_GetEncodingSearchPath and their use.

The Tcl_SetEncodingSearchPath procedure sets the search path for encoding data files to searchPath. searchPath must be a null-terminated array of strings. Tcl makes a copy of the strings in searchPath and the caller is responsible for managing the memory of the original array. Any directories in searchPath that are not verified as existing readable filesystem directories are silently ignored. When searching for encoding data files takes place, and non-existent or non-readable filesystem directories on the searchPath are silently ignored.

Tcl_GetDefaultEncodingDir and Tcl_SetDefaultEncodingDir are obsolete interfaces best replaced with calls to Tcl_GetEncodingSearchPath and Tcl_SetEncodingSearchPath. They are called to access and set the first element of the searchPath list. Since Tcl searches searchPath for encoding data files in list order, these routines establish the “default” directory in which to find encoding data files.

ENCODING FILES

Space would prohibit precompiling into Tcl every possible encoding algorithm, so many encodings are stored on disk as dynamically-loadable encoding files. This behavior also allows the user to create additional encoding files that can be loaded using the same mechanism. These encoding files contain information about the tables and/or escape sequences used to map between an external encoding and Unicode. The external encoding may consist of single-byte, multi-byte, or double-byte characters.

Each dynamically-loadable encoding is represented as a text file. The initial line of the file, beginning with a “#” symbol, is a comment that provides a human-readable description of the file. The next line identifies the type of encoding file. It can be one of the following letters:

[1] S
A single-byte encoding, where one character is always one byte long in the encoding. An example is iso8859-1, used by many European languages.
[2] D
A double-byte encoding, where one character is always two bytes long in the encoding. An example is big5, used for Chinese text.
[3] M
A multi-byte encoding, where one character may be either one or two bytes long. Certain bytes are lead bytes, indicating that another byte must follow and that together the two bytes represent one character. Other bytes are not lead bytes and represent themselves. An example is shiftjis, used by many Japanese computers.
[4] E
An escape-sequence encoding, specifying that certain sequences of bytes do not represent characters, but commands that describe how following bytes should be interpreted.

The rest of the lines in the file depend on the type.

The third line of the file is three numbers. The first number is the fallback character (in base 16) to use when converting from UTF-8 to this encoding. The second number is a 1 if this file represents the encoding for a symbol font, or 0 otherwise. The last number (in base 10) is how many pages of data follow.

Subsequent lines in the example above are pages that describe how to map from the encoding into 2-byte Unicode. The first line in a page identifies the page number. Following it are 256 double-byte numbers, arranged as 16 rows of 16 numbers. Given a character in the encoding, the high byte of that character is used to select which page, and the low byte of that character is used as an index to select one of the double-byte numbers in that page - the value obtained being the corresponding Unicode character. By examination of the example above, one can see that the characters 0x7E and 0x8163 in shiftjis map to 203E and 2026 in Unicode, respectively.

Following the first page will be all the other pages, each in the same format as the first: one number identifying the page followed by 256 double-byte Unicode characters. If a character in the encoding maps to the Unicode character 0000, it means that the character does not actually exist. If all characters on a page would map to 0000, that page can be omitted.

Case [4] is the escape-sequence encoding file. The lines in an this type of file are in the same format as this example taken from the iso2022-jp encoding:

# Encoding file: iso2022-jp, escape-driven
E
init		{}
final		{}
iso8859-1	\x1b(B
jis0201		\x1b(J
jis0208		\x1b$@
jis0208		\x1b$B
jis0212		\x1b$(D
gb2312		\x1b$A
ksc5601		\x1b$(C

In the file, the first column represents an option and the second column is the associated value. init is a string to emit or expect before the first character is converted, while final is a string to emit or expect after the last character. All other options are names of table-based encodings; the associated value is the escape-sequence that marks that encoding. Tcl syntax is used for the values; in the above example, for instance, “{}” represents the empty string and “\x1b” represents character 27.

When Tcl_GetEncoding encounters an encoding name that has not been loaded, it attempts to load an encoding file called name.enc from the encoding subdirectory of each directory that Tcl searches for its script library. If the encoding file exists, but is malformed, an error message will be left in interp.
