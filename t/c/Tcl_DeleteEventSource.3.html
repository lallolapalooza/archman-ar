إنشاء مصدر حدث جديد

يتكون مصدر الحدث من ثلاثة إجراءات يتم استدعاؤها بواسطة المُخطِر، بالإضافة إلى إجراءات C إضافية يتم استدعاؤها بواسطة كود عالي المستوى لتنظيم استدعاءات الأحداث غير المتزامنة. الإجراءات الثلاثة التي يستدعيها المُخطِر تتكون من إجراءات الإعداد والتحقق الموضحة أعلاه، بالإضافة إلى إجراء إضافي يتم استدعاؤه عند إزالة حدث من طابور الأحداث لتتم معالجته.

يقوم الإجراء Tcl_CreateEventSource بإنشاء مصدر حدث جديد. تحدد وسيطاته إجراء الإعداد والتحقق لمصدر الحدث. يجب أن يتوافق SetupProc مع النموذج الأولي التالي:

typedef void Tcl_EventSetupProc(
        ClientData clientData,
        int flags);

سيتم استخدام الوسيطة clientData للإجراء بنفس clientData للإجراء Tcl_CreateEventSource؛ وعادة ما تستخدم للإشارة إلى معلومات خاصة يديرها مصدر الحدث. سيتم استخدام الوسيطة flags بنفس flags التي تم تمريرها إلى Tcl_DoOneEvent، ما لم تكن 0 (في هذه الحالة، تستبدل Tcl_DoOneEvent القيمة 0 بـ TCL_ALL_EVENTS). تشير Flags إلى أنواع الأحداث التي يجب مراعاتها؛ إذا لم يكن البت المقابل لمصدر الحدث هذا نشطًا، فيجب أن يعود مصدر الحدث فورًا دون القيام بأي شيء. على سبيل المثال، يتحقق مصدر حدث الملف من البت TCL_FILE_EVENTS.

يجب أن يضمن SetupProc إيقاظ التطبيق عند وقوع أحداث من النوع المطلوب. يتم تنفيذ ذلك بشكل يعتمد على المنصة. على سبيل المثال، تحت Unix، قد يستدعي مصدر حدث Tcl_CreateFileHandler؛ تحت Windows، قد يطلب إشعارًا باستخدام حدث Windows. بالنسبة لأحداث النوع المؤقت، مثل أحداث المؤقت أو أي حدث يتم فحصه، يمكن لمصدر الحدث استدعاء Tcl_SetMaxBlockTime لإجبار التطبيق على الاستيقاظ حتى لو لم يقع أي حدث. إذا لم يستدعي أي مصدر حدث Tcl_SetMaxBlockTime، فستنتظر Tcl_WaitForEvent بالقدر اللازم لحدوث حدث؛ بخلاف ذلك، فإنها تنتظر فقط بالقدر المحدد من قبل أقصر فترة زمنية حددها أحد مصادر الحدث في Tcl_SetMaxBlockTime. إذا عرف مصدر حدث أن لديه بالفعل أحداثًا جاهزة للإبلاغ عنها، فيمكنه طلب وقت حظر أقصى يساوي صفرًا. على سبيل المثال، يبحث إعداد مصدر حدث X عن ما إذا كانت هناك أحداث مدرجة بالفعل. إذا كان الأمر كذلك، فإنه يستدعي Tcl_SetMaxBlockTime بوقت أقصى قدره 0 بحيث لا تقوم Tcl_WaitForEvent بحظر إذا لم تكن هناك بيانات جديدة في اتصال X. تشير الوسيطة timePtr لـ Tcl_WaitForEvent إلى هيكل يصف فترة زمنية بالثواني وأجزاء الثانية:

typedef struct Tcl_Time {
    long sec;
    long usec;
} Tcl_Time;

يجب أن يكون الحقل usec أقل من 1000000.

تُستخدم المعلومات المقدمة إلى Tcl_SetMaxBlockTime فقط للاستدعاء التالي لـ Tcl_WaitForEvent؛ ويتم تجاهلها بعد عودة Tcl_WaitForEvent. في المرة التالية التي يتم فيها إجراء انتظار حدث، سيتم استدعاء كل إجراء إعداد لمصدر الحدث مرة أخرى، ويمكنهم تحديد معلومات جديدة لذلك انتظار الحدث.

إذا كان التطبيق يستخدم حلقة أحداث خارجية بدلاً من Tcl_DoOneEvent، فقد تحتاج مصادر الأحداث إلى استدعاء Tcl_SetMaxBlockTime في أوقات أخرى. على سبيل المثال، إذا تم تسجيل معالج حدث جديد يحتاج إلى مراقبة الأحداث، فقد يستدعي مصدر الحدث Tcl_SetMaxBlockTime لتعيين وقت حظر أقصى يساوي صفرًا، مما يجبر حلقة الأحداث الخارجية على استدعاء Tcl. في هذه الحالة، تستدعي Tcl_SetMaxBlockTime Tcl_SetTimer بأقصر فترة زمنية شوهدت منذ آخر استدعاء لـ Tcl_DoOneEvent أو Tcl_ServiceAll.

بالإضافة إلى الإجراء العام Tcl_SetMaxBlockTime، قد تكون هناك إجراءات أخرى خاصة بالمنصة متاحة لـ setupProc، إذا كانت هناك معلومات إضافية مطلوبة بواسطة Tcl_WaitForEvent على تلك المنصة. على سبيل المثال، في أنظمة Unix، يمكن استخدام الواجهة Tcl_CreateFileHandler للانتظار أحداث الملفات.

الإجراء الثاني الذي يوفره كل مصدر حدث هو إجراء التحقق الخاص به، والمشار إليه بالوسيطة checkProc إلى Tcl_CreateEventSource. يجب أن يتوافق CheckProc مع النموذج الأولي التالي:

typedef void Tcl_EventCheckProc(
        ClientData clientData,
        int flags);

الوسيطات لهذا الإجراء هي نفس وسيطات setupProc. يتم استدعاء CheckProc بواسطة Tcl_DoOneEvent بعد انتظاره للأحداث. من المفترض أن يكون مصدر حدث واحد على الأقل مستعدًا لإدراج حدث. تستدعي Tcl_DoOneEvent كل مصدر حدث بالترتيب، لذلك كل لديه فرصة لإدراج أي أحداث جاهزة. يقوم إجراء التحقق بشيئين. أولاً، يجب أن يرى ما إذا كانت هناك أحداث قد تم تنشيطها. تقوم مصادر الأحداث المختلفة بذلك بطرق مختلفة.

إذا اكتشف مصدر حدث حدثًا مثيرًا للاهتمام، فيجب عليه إضافة الحدث إلى طابور أحداث Tcl. للقيام بذلك، يستدعي مصدر الحدث Tcl_QueueEvent. الوسيطة evPtr هي مؤشر إلى هيكل تم تخصيصه ديناميكيًا يحتوي على الحدث (انظر معلومات أكثر تفصيلاً حول قضايا إدارة الذاكرة). يمكن لكل مصدر حدث تحديد هيكل الحدث الخاص به بمعلومات ذات صلة بمصدر الحدث هذا. ومع ذلك، يجب أن يكون العنصر الأول في الهيكل هو هيكل من النوع Tcl_Event، ويتم استخدام المؤشر إلى هذا الهيكل عند الاتصال بين مصدر الحدث وبقية المُخطِر. يحتوي Tcl_Event على التعريف التالي:

typedef struct {
    Tcl_EventProc *proc;
    struct Tcl_Event *nextPtr;
} Tcl_Event;

يجب ملء الحقل proc للحدث قبل استدعاء Tcl_QueueEvent. يستخدم nextPtr لربط الأحداث في الطابور ولا يجب تعديله بواسطة مصدر الحدث.

يمكن إضافة حدث إلى الطابور في أحد المواضع الثلاثة، اعتمادًا على الوسيطة position لـ Tcl_QueueEvent:

TCL_QUEUE_TAIL
إضافة الحدث إلى نهاية الطابور، بحيث تتم معالجة الأحداث المعلقة أولاً. هذا هو دائمًا أفضل موضع للأحداث الجديدة.
TCL_QUEUE_HEAD
إضافة الحدث إلى بداية الطابور، بحيث تتم معالجته قبل الأحداث الأخرى في الطابور.
TCL_QUEUE_MARK
إضافة الحدث إلى بداية الطابور، إلا إذا كانت هناك أحداث أخرى في رأس الطابور بالموضع TCL_QUEUE_MARK. في حالة وجودها، أضف الحدث الجديد مباشرة بعد جميع TCL_QUEUE_MARK الموجودة. تُستخدم قيمة position هذه لإدراج تسلسل مرتب من الأحداث في رأس الطابور، مثل سلسلة من أحداث Enter و Leave التي تم إنشاؤها أثناء عملية تسجيل أو إلغاء تسجيل في Tk.

عندما يحين وقت معالجة حدث من الطابور (الخطوتان 1 و 4 أعلاه)، سيقوم Tcl_ServiceEvent باستدعاء proc المحدد في أول Tcl_Event في الطابور. يجب أن يتوافق Proc مع النموذج الأولي التالي:

typedef int Tcl_EventProc(
        Tcl_Event *evPtr,
        int flags);

الوسيطة الأولى لـ proc هي مؤشر إلى الحدث، والذي سيتم استخدامه كالوسيطة الأولى لاستدعاء Tcl_QueueEvent الذي أضاف الحدث إلى الطابور. الوسيطة الثانية لـ proc هي flags للاستدعاء الحالي لـ Tcl_ServiceEvent؛ يستخدمها مصدر الحدث للعودة فورًا إذا لم تكن أحداثه ذات صلة.

تقع على عاتق proc مسؤولية معالجة الحدث، وعادة ما يستدعي أمر Tcl واحدًا أو أكثر أو استدعاءات C. بمجرد الانتهاء من معالجة الحدث بواسطة مصدر الحدث، فإنه يعيد 1 للإشارة إلى أنه يمكن إزالة الحدث من الطابور. إذا قرر مصدر الحدث، لأي سبب، أنه لا يمكن معالجة الحدث في الوقت الحالي، فيمكنه إعادة 0 للإشارة إلى أنه يجب تأجيل الحدث للمعالجة لاحقًا؛ في هذه الحالة، سيواصل Tcl_ServiceEvent إلى الحدث التالي في الطابور ويحاول معالجته. هناك عدة أسباب قد تجعل مصدر حدث يؤجل حدثًا. أحد الاحتمالات هو أن أحداث هذا النوع مستبعدة بواسطة الوسيطة flags. على سبيل المثال، يعيد مصدر حدث الملف 0 إذا لم يكن البت TCL_FILE_EVENTS نشطًا في flags. مثال آخر على تأجيل الأحداث يحدث في Tk إذا تم استدعاء Tk_RestrictEvents لتأجيل أحداث نوافذ معينة.

عندما يعيد proc القيمة 1، ستقوم Tcl_ServiceEvent بإزالة الحدث من الطابور وتحرير مساحته. لاحظ أنه يجب تخصيص مساحة الحدث بواسطة مصدر الحدث (باستخدام Tcl_Alloc أو الماكرو ckalloc) قبل استدعاء Tcl_QueueEvent، ولكن سيتم تحريرها بواسطة Tcl_ServiceEvent، وليس بواسطة مصدر الحدث.

تعمل التطبيقات متعددة الخيوط بشكل مشابه، إلا أن هناك طابور أحداث منفصل لكل خيط يحتوي على مترجم Tcl. يؤدي استدعاء Tcl_QueueEvent في تطبيق متعدد الخيوط إلى إضافة حدث إلى طابور الخيط الحالي. لإضافة حدث إلى طابور خيط آخر، استخدم Tcl_ThreadQueueEvent. تقبل Tcl_ThreadQueueEvent وسيطة Tcl_ThreadId، التي تحدد خيطًا فريدًا في تطبيق Tcl. للحصول على Tcl_ThreadId للخيط الحالي، استخدم الإجراء Tcl_GetCurrentThread. (سيحتاج الخيط بعد ذلك إلى تمرير هذا المعرف إلى خيوط أخرى حتى يتمكنوا من إضافة أحداث إلى طابوره.) بعد إضافة حدث إلى طابور خيط آخر، يلزم عادةً استدعاء Tcl_ThreadAlert "لإيقاظ" مُخطِر هذا الخيط لإعلامه بالحدث الجديد.

يمكن استخدام Tcl_DeleteEvents صراحة لإزالة حدث واحد أو أكثر من طابور الأحداث. يستدعي Tcl_DeleteEvents proc لكل حدث في الطابور، وإزالة تلك التي يعيد الإجراء لها القيمة 1. تظل الأحداث التي يعيد الإجراء لها القيمة 0 في الطابور. يجب أن يتوافق Proc مع النموذج الأولي التالي:

typedef int Tcl_EventDeleteProc(
        Tcl_Event *evPtr,
        ClientData clientData);

سيتم استخدام الوسيطة clientData بنفس clientData الوسيطة لـ Tcl_DeleteEvent؛ وهي تستخدم عادة للإشارة إلى معلومات خاصة يديرها مصدر الحدث.

INTRODUCTION

The Tcl event loop is the heart of any Tcl application. It is responsible for monitoring various sources of events and dispatching them to the appropriate handlers. This document describes the core primitives of the Tcl event loop and how to interact with them.

NOTIFIER BASICS

The Tcl event loop is managed by a notifier. The notifier is responsible for waiting for events and dispatching them. Tcl provides a default notifier, but it can be replaced with a custom one if needed.

Events in Tcl are represented by the Tcl_Event structure. Events can be generated by various sources, including file descriptors, timers, and idle handlers. Events are queued in an event queue before being processed by the notifier.

The following are the key components of the Tcl event loop:

  • Event Sources: These are the sources from which events can originate. Examples include file descriptors (for I/O events), timers, and idle time.
  • Event Queue: A queue where incoming events are stored before being processed.
  • Notifier: The component responsible for waiting for events and dispatching them to the appropriate handlers.
  • Event Handlers: Procedures that are called when a specific type of event occurs.

The main Tcl event loop function is Tcl_DoOneEvent, which processes a single event from the queue. Applications typically call this function repeatedly in a loop to handle events.

CREATING A NEW EVENT SOURCE

You can create new event sources by using Tcl_CreateEventSource. This function takes a procedure to be called when the source becomes ready, a procedure to be called when the source is lost, and client data. The event source is typically associated with a file descriptor.

When the event source becomes ready (e.g., a file descriptor has data to read), Tcl will queue an event. You then need to provide a handler for this event.

CREATING A NEW NOTIFIER

A notifier is responsible for waiting for events from various sources and dispatching them. You can create a custom notifier by implementing the Tcl_NotifierProcs structure and registering it with Tcl_SetNotifier. The default notifier handles file events, timer events, and idle events.

REPLACING THE NOTIFIER

You can replace the default Tcl notifier with your own implementation by calling Tcl_SetNotifier. This allows you to customize how Tcl waits for and dispatches events. Your custom notifier must implement the `Tcl_NotifierProcs` structure, which includes functions for waiting for events, checking for pending events, and performing other notifier-specific operations.

EXTERNAL EVENT LOOPS

In some cases, you might want to integrate the Tcl event loop with an external event loop, such as the event loop of a GUI toolkit (e.g., Tk, GTK+, Qt). Tcl provides mechanisms to allow this integration. You can use functions like Tcl_SetMaxBlockTime to control how long Tcl's event loop will block, allowing the external loop to process events.

You can also use Tcl_ServiceModeHook to be notified when Tcl enters or exits its event loop servicing mode. This can be useful for performing application-specific tasks during event loop processing.
