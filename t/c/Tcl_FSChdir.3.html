DESCRIPTION

There are several reasons for calling the Tcl_FS API functions (e.g. Tcl_FSAccess and Tcl_FSStat) rather than calling system level functions like access and stat directly. First, they will work cross-platform, so an extension which calls them should work unmodified on Unix and Windows. Second, the Windows implementation of some of these functions fixes some bugs in the system level calls. Third, these function calls deal with any “Utf to platform-native” path conversions which may be required (and may cache the results of such conversions for greater efficiency on subsequent calls). Fourth, and perhaps most importantly, all of these functions are “virtual filesystem aware”. Any virtual filesystem (VFS for short) which has been registered (through Tcl_FSRegister) may reroute file access to alternative media or access methods. This means that all of these functions (and therefore the corresponding file, glob, pwd, cd, open, etc. Tcl commands) may be operate on “files” which are not native files in the native filesystem. This also means that any Tcl extension which accesses the filesystem (FS for short) through this API is automatically “virtual filesystem aware”. Of course, if an extension accesses the native filesystem directly (through platform-specific APIs, for example), then Tcl cannot intercept such calls.

If appropriate VFSes have been registered, the “files” may, to give two examples, be remote (e.g. situated on a remote ftp server) or archived (e.g. lying inside a .zip archive). Such registered filesystems provide a lookup table of functions to implement all or some of the functionality listed here. Finally, the Tcl_FSStat and Tcl_FSLstat calls abstract away from what the “struct stat” buffer is actually declared to be, allowing the same code to be used both on systems with and systems without support for files larger than 2GB in size.

The Tcl_FS API is Tcl_Obj-ified and may cache internal representations and other path-related strings (e.g. the current working directory). One side-effect of this is that one must not pass in values with a reference count of zero to any of these functions. If such calls were handled, they might result in memory leaks (under some circumstances, the filesystem code may wish to retain a reference to the passed in value, and so one must not assume that after any of these calls return, the value still has a reference count of zero - it may have been incremented) or in a direct segmentation fault (or other memory access error) due to the value being freed part way through the complex value manipulation required to ensure that the path is fully normalized and absolute for filesystem determination. The practical lesson to learn from this is that

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

is wrong, and may cause memory errors. The path must have its reference count incremented before passing it in, or decrementing it. For this reason, values with a reference count of zero are considered not to be valid filesystem paths and calling any Tcl_FS API function with such a value will result in no action being taken.

FS API FUNCTIONS

Tcl_FSCopyFile attempts to copy the file given by srcPathPtr to the path name given by destPathPtr. If the two paths given lie in the same filesystem (according to Tcl_FSGetFileSystemForPath) then that filesystem's “copy file” function is called (if it is non-NULL). Otherwise the function returns -1 and sets the errno global C variable to the “EXDEV” POSIX error code (which signifies a “cross-domain link”).

Tcl_FSCopyDirectory attempts to copy the directory given by srcPathPtr to the path name given by destPathPtr. If the two paths given lie in the same filesystem (according to Tcl_FSGetFileSystemForPath) then that filesystem's “copy file” function is called (if it is non-NULL). Otherwise the function returns -1 and sets the errno global C variable to the “EXDEV” POSIX error code (which signifies a “cross-domain link”).

Tcl_FSCreateDirectory attempts to create the directory given by pathPtr by calling the owning filesystem's “create directory” function.

Tcl_FSDeleteFile attempts to delete the file given by pathPtr by calling the owning filesystem's “delete file” function.

Tcl_FSRemoveDirectory attempts to remove the directory given by pathPtr by calling the owning filesystem's “remove directory” function.

Tcl_FSRenameFile attempts to rename the file or directory given by srcPathPtr to the path name given by destPathPtr. If the two paths given lie in the same filesystem (according to Tcl_FSGetFileSystemForPath) then that filesystem's “rename file” function is called (if it is non-NULL). Otherwise the function returns -1 and sets the errno global C variable to the “EXDEV” POSIX error code (which signifies a “cross-domain link”).

Tcl_FSListVolumes calls each filesystem which has a non-NULL “list volumes” function and asks them to return their list of root volumes. It accumulates the return values in a list which is returned to the caller (with a reference count of 0).

Tcl_FSEvalFileEx reads the file given by pathPtr using the encoding identified by encodingName and evaluates its contents as a Tcl script. It returns the same information as Tcl_EvalObjEx. If encodingName is NULL, the system encoding is used for reading the file contents. If the file could not be read then a Tcl error is returned to describe why the file could not be read. The eofchar for files is “\x1A” (^Z) for all platforms. If you require a “^Z” in code for string comparison, you can use “\x1A”, which will be safely substituted by the Tcl interpreter into “^Z”. Tcl_FSEvalFile is a simpler version of Tcl_FSEvalFileEx that always uses the system encoding when reading the file.

Tcl_FSLoadFile dynamically loads a binary code file into memory and returns the addresses of two procedures within that file, if they are defined. The appropriate function for the filesystem to which pathPtr belongs will be called. If that filesystem does not implement this function (most virtual filesystems will not, because of OS limitations in dynamically loading binary code), Tcl will attempt to copy the file to a temporary directory and load that temporary file. Tcl_FSUnloadFile reverses the operation, asking for the library indicated by the loadHandle to be removed from the process. Note that, unlike with the unload command, this does not give the library any opportunity to clean up.

Both the above functions return a standard Tcl completion code. If an error occurs, an error message is left in the interp's result.

The token provided via the variable indicated by loadHandlePtr may be used with Tcl_FindSymbol.

Tcl_FSMatchInDirectory is used by the globbing code to search a directory for all files which match a given pattern. The appropriate function for the filesystem to which pathPtr belongs will be called.

The return value is a standard Tcl result indicating whether an error occurred in globbing. Error messages are placed in interp (unless interp is NULL, which is allowed), but good results are placed in the resultPtr given.

Note that the glob code implements recursive patterns internally, so this function will only ever be passed simple patterns, which can be matched using the logic of string match. To handle recursion, Tcl will call this function frequently asking only for directories to be returned. A special case of being called with a NULL pattern indicates that the path needs to be checked only for the correct type.

Tcl_FSLink replaces the library version of readlink, and extends it to support the creation of links. The appropriate function for the filesystem to which linkNamePtr belongs will be called.

If the toPtr is NULL, a “read link” action is performed. The result is a Tcl_Obj specifying the contents of the symbolic link given by linkNamePtr, or NULL if the link could not be read. The result is owned by the caller, which should call Tcl_DecrRefCount when the result is no longer needed. If the toPtr is not NULL, Tcl should create a link of one of the types passed in in the linkAction flag. This flag is an OR'ed combination of TCL_CREATE_SYMBOLIC_LINK and TCL_CREATE_HARD_LINK. Where a choice exists (i.e. more than one flag is passed in), the Tcl convention is to prefer symbolic links. When a link is successfully created, the return value should be toPtr (which is therefore already owned by the caller). If unsuccessful, NULL is returned.

Tcl_FSLstat fills the Tcl_StatBuf structure statPtr with information about the specified file. You do not need any access rights to the file to get this information but you need search rights to all directories named in the path leading to the file. The Tcl_StatBuf structure includes info regarding device, inode (always 0 on Windows), privilege mode, nlink (always 1 on Windows), user id (always 0 on Windows), group id (always 0 on Windows), rdev (same as device on Windows), size, last access ti

me, tiempo de modificación, y tiempo de cambio de metadatos. Vea **PORTABLE STAT RESULT API** para una descripción de cómo escribir código portable para allocar y acceder a la estructura _Tcl_StatBuf_. Si _path_ existe, **Tcl_FSLstat** devuelve 0 y la estructura _statPtr_ se llena con datos. De lo contrario, -1 se devuelve y no se dan información de estadísticas. **Tcl_FSUtime** reemplaza la versión del biblioteca de _utime_. Este devuelve 0 en éxito y -1 en error (como según la documentación de **utime**). Si es exitoso, la función actualizará los valores de _atime_ y _mtime_ de un archivo dado. **Tcl_FSFileAttrsGet** implementa el acceso leído para el subcomando **file attributes** de la hookable **file**. La función adecuada para el sistema de archivos al que pertenece _pathPtr_ será llamada. Si el resultado es **TCL_OK**, un valor se colocó en _objPtrRef_, que será válido solo temporalmente (hasta que se llame **Tcl_IncrRefCount**). **Tcl_FSFileAttrsSet** implementa el acceso de escritura para el subcomando **file attributes** de la hookable **file**. La función adecuada para el sistema de archivos al que pertenece _pathPtr_ será llamada. **Tcl_FSFileAttrStrings** implementa parte del subcomando **file attributes** de la hookable **file**. La función adecuada para el sistema de archivos al que pertenece _pathPtr_ será llamada. La llamada a la procedimiento puede devolver un array de strings o, en su lugar, devolver NULL y colocar una lista de Tcl en _objPtrRef_. Tcl tomará esa lista y primero incrementará su contador de referencias antes de usarla. Al terminar el uso, Tcl decrementará su contador de referencias. Por lo tanto, si la lista debe ser destruida por Tcl al terminar, debe tener un contador de referencias igual a cero, y si no debe ser destruida, el sistema de archivos debe asegurarse de mantener un contador de referencias al valor. **Tcl_FSAccess** verifica si el proceso sería permitido para leer, escribir o testear la existencia de un archivo (o otro objeto del sistema de archivos) cuyo nombre es _pathname_. Si _pathname_ es un enlace simbólico en Unix, se prueba el permiso del archivo referido por este enlace simbólico. En éxito (todas las permisos solicitadas), se devuelve 0. En error (al menos un bit en el modo solicitado es denegado o ocurre otro error), se devuelve -1. **Tcl_FSStat** rellena la estructura _Tcl_StatBuf_ con información sobre el archivo especificado. No se necesitan derechos de acceso al archivo para obtener esta información, pero sí se requieren derechos de búsqueda en todos los directorios mencionados en el camino hacia el archivo. La estructura _Tcl_StatBuf_ incluye información sobre el dispositivo, el inodo (0 en Windows), el modo de privilegio, el nlink (1 en Windows), el UID (0 en Windows), el GID (0 en Windows), rdev (igual que dispositivo en Windows), el tamaño, el tiempo de última accesión, el tiempo de última modificación, y el tiempo de último cambio de metadatos. Vea **PORTABLE STAT RESULT API** para una descripción de cómo escribir código portable para allocar y acceder a la estructura _Tcl_StatBuf_. Si _path_ existe, **Tcl_FSStat** devuelve 0 y la estructura _statPtr_ se llena con datos. De lo contrario, -1 se devuelve y no se dan información de estadísticas. **Tcl_FSOpenFileChannel** abre un archivo especificado por _pathPtr_ y devuelve un handle de canal que se puede usar para realizar entrada y salida en el archivo. Esta API se modela después del procedimiento **fopen** de la biblioteca de I/O estándar Unix. El sintaxis y significado de todos los argumentos son similares a los dados en la comanda Tcl **open** cuando se abre un archivo. Si ocurre un error al abrir el canal, **Tcl_FSOpenFileChannel** devuelve NULL y registra un código de error POSIX que se puede recuperar con **Tcl_GetErrno**. Además, si _interp_ no es NULL, **Tcl_FSOpenFileChannel** deja un mensaje de error en _interp_'s result después de cualquier error. El canal creado no se registra en el interprete proporcionado; para registrarlo, use **Tcl_RegisterChannel**. Si uno de los canales estándar, **stdin**, **stdout** o **stderr** fue anteriormente cerrado, la acción de crear el nuevo canal también lo asigna como reemplazo del canal estándar. **Tcl_FSGetCwd** reemplaza la versión del biblioteca de **getcwd**. Devuelve el directorio de trabajo de la biblioteca Tcl. Este puede ser diferente al directorio de trabajo nativo, que ocurre cuando el directorio de trabajo actual no está en el sistema de archivos nativo. El resultado es un puntero a un objeto Tcl _Tcl_Obj_ especificando el directorio actual, o NULL si no se pudo determinar el directorio. Si se devuelve NULL, un mensaje de error se deja en el resultado de _interp_. El resultado ya tiene su contador de referencias incrementado para el llamador. Cuando no se necesite más, ese contador debe ser decrementado. Esto es necesario para la seguridad en multithreading, para permitir múltiples hilos acceder a esta y funciones relacionadas, mientras garantizando que los resultados siempre sean válidos. **Tcl_FSChdir** reemplaza la versión del biblioteca de **chdir**. El camino se normaliza y luego se pasa al sistema de archivos que lo reclama. Si ese sistema de archivos no implementa esta función, Tcl se retrasa a combinar **stat** y **access** para verificar si el directorio existe y tiene permisos adecuados. Para los resultados, vea la documentación de **chdir**. Si es exitoso, se mantiene un registro de la ruta exitosa en _cwdPathPtr_ para llamadas posteriores a **Tcl_FSGetCwd**. **Tcl_FSPathSeparator** devuelve el carácter de separación para el elemento más específico de la ruta especificada por _pathPtr_ (es decir, el último parte de la ruta). El separador se devuelve como un objeto Tcl con una cadena de longitud 1. Si la ruta es inválida, se devuelve NULL. **Tcl_FSJoinPath** toma el objeto Tcl dado, que debe ser un lista válida (que permite tener un contador de referencias igual a cero), y devuelve el valor de ruta considerando los primeros _elements_ como segmentos válidos de ruta (cada segmento puede ser un camino completo, una parte de camino o solo un nombre de directorio o archivo). Si algún segmento es realmente un camino absoluto, se descarta todos los segmentos anteriores. Si _elements_ es menor que 0, usamos el entero completo. Es posible que el valor devuelto sea realmente un elemento del listado dado, por lo que el llamador debe ser cuidadoso de incrementar el contador de referencias del valor antes de liberar la lista. El valor devuelto, típicamente con un contador de referencias igual a cero (pero podría ser compartido en ciertos casos), contiene el camino unido. El llamador debe agregar un contador de referencias al valor antes de usarlo. En particular, el valor devuelto podría ser un elemento del listado dado, por lo que liberar la lista podría liberar el valor prematuramente si no se ha tomado un contador de referencias. Si el número de elementos es cero, el valor devuelto será una cadena vacía _Tcl_Obj_. **Tcl_FSSplitPath** toma el objeto Tcl dado, que debe ser un camino válido, y devuelve un valor de lista con cada segmento de ese camino como elemento. Devuelve un valor de lista con un contador de referencias igual a cero. Si el _lenPtr_ pasado es no NULL, el variable que señala el número de elementos en el valor devuelto será actualizado. **Tcl_FSEqualPaths** prueba si dos rutas dadas representan el mismo objeto del sistema de archivos. Devuelve 1 si las rutas son iguales y 0 si son diferentes. Si cualquiera de las rutas es NULL, siempre devuelve 0. **Tcl_FSGetNormalizedPath** intenta extraer una representación normalizada única de un camino dado, cuyo valor de cadena puede usarse como identificador único para el archivo. Devuelve la representación normalizada del camino, propiedad de Tcl, o NULL si el camino no es válido o no puede ser convertido correctamente. La extracción de caminos absolutos y normalizados es muy eficiente (ya que el sistema de archivos opera internamente con estas representaciones), aunque el resultado cuando el sistema de archivos contiene múltiples enlaces simbólicos no será la versión más amigable de una ruta. El valor de retorno es propiedad de Tcl y tiene una vida útil equivalente a la del _pathPtr_ pasado (a menos que ese sea un camino relativo, en cuyo caso el valor normalizado puede ser liberado cualquier tiempo que cambie el cwd) - el llamador puede incrementar el contador de referencias si lo desea para mantener una copia más larga. **Tcl_FSJoinToPath** toma el valor dado, que usualmente será un camino válido o NULL, y lo une a un array de segmentos de caminos. Devuelve un valor, típicamente con un contador de referencias igual a cero (pero podría ser compartido en ciertos casos), conteniendo el camino unido. El llamador debe incrementar el contador de referencias al valor antes de usarlo. Si cualquier valor pasado a esta función (_pathPtr_ o _path_ elementos) tiene un contador de referencias igual a cero, se liberará cuando esta función devuelva. **Tcl_FSConvertToPathType** intenta convertir el objeto Tcl dado a un tipo válido de ruta Tcl, considerando que el cwd podría haber cambiado incluso si este valor ya es de tipo correcto. El nombre de archivo puede comenzar con “~“ (para indicar el directorio de usuario actual) o “~<user>“ (para indicar el directorio de cualquier usuario). Si la conversión es exitosa (es decir, el valor es un camino válido en uno de los sistemas de archivos actuales), se devuelve **TCL_OK**. De lo contrario, se devuelve **TCL_ERROR**, y un mensaje de error puede ser dejado en el interprete. **Tcl_FSGetInternalRep** extrae la representación interna de un valor de camino dado, en el sistema de archivos dado. Si el valor de camino pertenece a un sistema de archivos diferente, se devuelve NULL. Si la representación interna es actualmente NULL, se intenta generarla llamando a **Tcl_FSCreateInternalRepProc** del sistema de archivos. Devuelve NULL o una representación válida de la ruta interna. Esta representación interna es cachada, por lo que llamadas repetidas a esta función no requieren conversiones adicionales. **Tcl_FSGetTranslatedPath** intenta extraer la ruta traducida del objeto Tcl dado. Si la traducción es exitosa (es decir, el valor es un camino válido), se devuelve el valor. De lo contrario, se devuelve NULL, y un mensaje de error puede ser dejado en el interprete. Una ruta traducida es una que contiene ninguna secuencia de “~“ o “~user“ (estas se han expandido a su representación actual en el sistema de archivos). El valor devuelto es propiedad del llamador, que debe almacenar el valor o llamar a **Tcl_DecrRefCount** para asegurar la liberación de memoria. Esta función es de poca utilidad práctica, y **Tcl_FSGetNormalizedPath** o **Tcl_FSGetNativePath** son generalmente funciones más útiles para la mayoría de los casos. **Tcl_FSGetTranslatedStringPath** hace lo mismo que **Tcl_FSGetTranslatedPath**, pero devuelve una cadena de caracteres o NULL. El string devuelto es dinamicamente asignado y se debe almacenar o llamar a **Tcl_DecrRefCount** para asegurar la liberación de memoria. Esta función es de poca utilidad práctica, y **Tcl_FSGetNormalizedPath** o **Tcl_FSGetNativePath** son generalmente funciones más útiles para la mayoría de los casos. بواسطة المتصل، والتي يجب تخزينها أو استدعاء ckfree لضمان تحريرها. مرة أخرى، Tcl_FSGetNormalizedPath أو Tcl_FSGetNativePath هي عادةً دوال أفضل للاستخدام لمعظم الأغراض.

Tcl_FSNewNativePath تقوم بشيء يشبه عكس التحويلات المعتادة obj->path->nativerep. إذا استردت بعض التعليمات البرمجية مسارًا بالشكل الأصلي (من، على سبيل المثال، readlink أو مربع حوار أصلي)، وكان هذا المسار سيتم استخدامه على مستوى Tcl، فإن استدعاء هذه الدالة هو طريقة فعالة لإنشاء نوع قيمة المسار المناسب.

القيمة الناتجة هي قيمة "مسار" خالصة، والتي ستتلقى تمثيلًا سلسلة UTF-8 فقط إذا كان ذلك مطلوبًا بواسطة بعض تعليمات Tcl البرمجية.

Tcl_FSGetNativePath مخصص للاستخدام بواسطة أنظمة الملفات الأصلية Win/Unix، بحيث يمكنهم بسهولة استرداد التمثيل الأصلي (char* أو TCHAR*) للمسار. هذه الدالة هي غلاف مريح حول Tcl_FSGetInternalRep. قد يكون من المرغوب فيه في المستقبل أن تكون هناك تمثيلات أصلية غير قائمة على السلاسل (على سبيل المثال، على macOS، تمثيل يستخدم بنية FSRef لـ fileSpec سيكون على الأرجح أكثر كفاءة). في Windows، س يسمح تمثيل Unicode الكامل بمسارات بطول غير محدود. حاليًا، التمثيل هو ببساطة سلسلة أحرف قد تحتوي على المسار النسبي أو مسار كامل ومطلق ومنظم بالترميز الأصلي (تحدد الشروط المعقدة أي من هذه سيتم توفيره، لذلك لا يمكن الاعتماد على أي منهما، ما لم يكن المسار معروفًا بأنه مطلق). إذا كنت بحاجة إلى مسار أصلي يجب أن يكون مطلقًا، فيجب عليك طلب النسخة الأصلية من مسار منظم. إذا لسبب ما، تمسكت الحاجة إلى نسخة غير مطلقة وغير منظمة من المسار، فيجب بناؤها بشكل منفصل (على سبيل المثال، باستخدام Tcl_FSGetTranslatedPath).

يتم تخزين التمثيل الأصلي مؤقتًا بحيث لا تتطلب الاستدعاءات المتكررة لهذه الدالة تحويلات إضافية. القيمة المرجعة مملوكة لـ Tcl ولها عمر مكافئ لعمر pathPtr الذي تم تمريره (ما لم يكن مسارًا نسبيًا، وفي هذه الحالة قد يتم تحرير التمثيل الأصلي في أي وقت يتغير فيه cwd).

Tcl_FSFileSystemInfo تعيد قائمة من عنصرين. العنصر الأول هو اسم نظام الملفات (على سبيل المثال، "native"، "vfs"، "zip"، أو "prowrap"، ربما)، والعنصر الثاني هو النوع المحدد للمسار المعطى ضمن نظام الملفات هذا (وهو يعتمد على نظام الملفات). قد يكون العنصر الثاني فارغًا إذا لم يقدم نظام الملفات تصنيفًا إضافيًا للملفات.

يتم إرجاع قيمة قائمة صالحة، ما لم تكن قيمة المسار غير معروفة، عند إرجاع NULL.

Tcl_FSGetFileSystemForPath تعيد مؤشرًا إلى Tcl_Filesystem الذي يقبل هذا المسار على أنه صالح.

إذا لم يقبل أي نظام ملفات المسار، يتم إرجاع NULL.

Tcl_FSGetPathType تحدد ما إذا كان المسار المعطى نسبيًا للدليل الحالي، نسبيًا لمجلد التشغيل الحالي، أو مطلقًا.

يعيد واحدًا من TCL_PATH_ABSOLUTE، TCL_PATH_RELATIVE، أو TCL_PATH_VOLUME_RELATIVE

THE VIRTUAL FILESYSTEM API

يوفر نظام الملفات بنية Tcl_Filesystem تحتوي على مؤشرات للدوال التي تنفذ العمليات المختلفة على نظام الملفات؛ يتم استدعاء هذه العمليات عند الحاجة بواسطة الطبقة العامة، والتي تحدث بشكل عام من خلال الدوال المدرجة أعلاه.

يتم معالجة هياكل Tcl_Filesystem باستخدام الطرق التالية.

Tcl_FSRegister تأخذ مؤشرًا إلى بنية نظام ملفات وقطعة اختيارية من البيانات لربطها بنظام الملفات هذا. عند استدعاء هذه الدالة، سيقوم Tcl بإرفاق نظام الملفات بقائمة أنظمة الملفات المعروفة، وسيكون جاهزًا تمامًا للعمل على الفور. لا يتحقق Tcl مما إذا كان نفس نظام الملفات مسجلاً عدة مرات (وبشكل عام هذا ليس شيئًا جيدًا للقيام به). سيتم إرجاع TCL_OK.

Tcl_FSUnregister تزيل بنية نظام الملفات المعطاة من قائمة أنظمة الملفات المعروفة، إذا كانت معروفة، وتعيد TCL_OK. إذا لم يكن نظام الملفات مسجلاً حاليًا، يتم إرجاع TCL_ERROR.

Tcl_FSData تعيد clientData المرتبط بنظام الملفات المعطى، إذا كان نظام الملفات هذا مسجلاً. خلاف ذلك، ستعيد NULL.

Tcl_FSMountsChanged تستخدم لإعلام نواة Tcl بأن مجموعة نقاط التحميل لنظام الملفات المعطى (المسجل بالفعل) قد تغيرت، وأن التمثيلات المخزنة مؤقتًا للملفات قد لا تكون صحيحة بعد ذلك.

أي دوال تأخذ أسماء مسارات في شكل Tcl_Obj تأخذ تلك الأسماء بتنسيق UTF-8. تم تصميم واجهة برمجة تطبيقات البنية التحتية لنظام الملفات لدعم التحويل الفعال والمخزن مؤقتًا لهذه المسارات UTF-8 إلى تمثيلات أصلية أخرى.

بنية نظام الملفات

تحتوي هذه الحقول على معلومات أساسية حول بنية نظام الملفات وعناوين الوظائف التي تُستخدم لربط نظام ملفات معين بمسار ملف، والتعامل مع المعالجة الداخلية لتمثيلات المسارات، على سبيل المثال نسخ هذه التمثيلات وتحريرها.

اسم النوع

يحتوي حقل typeName على سلسلة نصية تنتهي بحرف NULL تحدد نوع نظام الملفات المنفذ، على سبيل المثال "أصلي" (native)، "zip"، أو "vfs".

طول البنية

يتم تنفيذ الحقل structureLength بشكل عام على أنه sizeof(Tcl_Filesystem)، وهو موجود للسماح بتوافق أسهل مع الإصدارات الثنائية السابقة إذا تغير حجم البنية في إصدار Tcl مستقبلي.

الإصدار

يجب تعيين الحقل version إلى TCL_FILESYSTEM_VERSION_1.

وظيفة مسار نظام الملفات

يحتوي حقل pathInFilesystemProc على عنوان وظيفة يتم استدعاؤها لتحديد ما إذا كان مسار معين ينتمي إلى نظام الملفات هذا أم لا. لن تستدعي Tcl وظائف نظام الملفات الأخرى إلا بمسار أعادت هذه الوظيفة TCL_OK له. إذا لم يكن المسار ينتمي، فيجب إرجاع -1 (لم يتم تعريف سلوك Tcl لأي قيمة إرجاع أخرى). إذا تم إرجاع TCL_OK، فيمكن استخدام المعلمة الاختيارية للمخرجات clientDataPtr لإرجاع تمثيل داخلي (خاص بنظام الملفات) للمسار، والذي سيتم تخزينه مؤقتًا داخل قيمة المسار، ويمكن استرجاعه بكفاءة بواسطة وظائف نظام الملفات الأخرى. ستقوم Tcl في نفس الوقت بتخزين حقيقة أن هذا المسار ينتمي إلى نظام الملفات هذا مؤقتًا. يتم إلغاء صلاحية هذه المخازن المؤقتة عند إضافة أو إزالة هياكل أنظمة الملفات من القائمة الداخلية لأنظمة الملفات المعروفة لدى Tcl.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

وظيفة Stat

وظيفة لمعالجة استدعاء Tcl_FSStat. يجب تنفيذها لأي نظام ملفات معقول، حيث تعتمد العديد من أوامر مستوى Tcl بشكل حاسم عليها (على سبيل المثال، file atime، file isdirectory، file size، glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

تقوم Tcl_FSStatProc بملء بنية stat statPtr بمعلومات حول الملف المحدد. لا تحتاج إلى أي حقوق وصول إلى الملف للحصول على هذه المعلومات ولكنك تحتاج إلى حقوق البحث لجميع الدلائل المسماة في المسار المؤدي إلى الملف. تتضمن بنية stat معلومات بخصوص الجهاز، inode (دائمًا 0 على Windows)، وضع الامتياز، nlink (دائمًا 1 على Windows)، معرف المستخدم (دائمًا 0 على Windows)، معرف المجموعة (دائمًا 0 على Windows)، rdev (نفس الجهاز على Windows)، الحجم، وقت آخر وصول، وقت آخر تعديل، ووقت آخر تغيير في البيانات الوصفية.

إذا كان الملف الذي تمثله pathPtr موجودًا، فإن Tcl_FSStatProc تُرجع 0 ويتم ملء بنية stat بالبيانات. بخلاف ذلك، يتم إرجاع -1، ولا يتم تقديم أي معلومات stat.

وظيفة الوصول

عند النجاح (تم منح جميع الأذونات المطلوبة)، يتم إرجاع صفر. عند الخطأ (طلب بت واحد على الأقل في mode إذنًا مرفوضًا، أو حدث خطأ آخر)، يتم إرجاع -1.

ILECHANNELPROC

وظيفة لمعالجة استدعاء إلى Tcl_FSOpenFileChannel. يجب تنفيذها لأي نظام ملفات معقول، حيث أن أي عملية تتطلب فتح أو الوصول إلى محتويات ملف ستستخدم هذه الوظيفة (على سبيل المثال، open، encoding، والعديد من أوامر Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

تقوم Tcl_FSOpenFileChannelProc بفتح ملف محدد بواسطة pathPtr وتعيد مقبض قناة يمكن استخدامه لإجراء الإدخال والإخراج على الملف. تم تصميم واجهة برمجة التطبيقات هذه على غرار الإجراء fopen الخاص بمكتبة الإدخال/الإخراج القياسية في Unix. يتشابه تركيب ومعنى جميع الوسائط مع تلك المقدمة في أمر Tcl open عند فتح ملف، حيث يمثل mode مزيجًا من علامات POSIX O_RDONLY، O_WRONLY، إلخ. إذا حدث خطأ أثناء فتح القناة، فإن Tcl_FSOpenFileChannelProc تعيد NULL وتسجل رمز خطأ POSIX يمكن الحصول عليه باستخدام Tcl_GetErrno. بالإضافة إلى ذلك، إذا كان interp ليس NULL، فإن Tcl_FSOpenFileChannelProc تترك رسالة خطأ في نتيجة interp بعد أي خطأ.

يجب ألا تسجل القناة المنشأة حديثًا في المفسر الذي توفره Tcl_FSOpenFileChannelProc؛ مهمة تسجيلها هي مهمة استدعاء Tcl_FSOpenFileChannel (إذا لزم الأمر). إذا تم إغلاق إحدى القنوات القياسية، stdin، stdout، أو stderr سابقًا، فإن فعل إنشاء القناة الجديدة يعينها أيضًا كبديل للقناة القياسية.

MATCHINDIRECTORYPROC

وظيفة لمعالجة استدعاء إلى Tcl_FSMatchInDirectory. إذا لم يتم تنفيذها، فسوف تفقد وظائف الاستدلال والنسخ المتكرر في نظام الملفات (وقد يؤثر ذلك على أوامر مثل encoding names التي تستخدم وظائف الاستدلال).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

يجب أن تعيد الوظيفة جميع الملفات أو الدلائل (أو كائنات نظام الملفات الأخرى) التي تطابق النمط المحدد وتتوافق مع مخطط types المحدد. يمكن استدعاء الوظيفة بطريقتين. إذا كان pattern هو NULL، فإن pathPtr هو مواصفات كاملة لملف أو دليل يجب التحقق من وجوده ونوعه. بخلاف ذلك، فإن pathPtr هو دليل ويجب أن تبحث الوظيفة عن ملفات أو دلائل ذات أنواع صحيحة. في كلتا الحالتين، يمكن افتراض أن pathPtr ليس NULL وليس فارغًا. لا توثق حاليًا ما إذا كان pathPtr سيحتوي على فاصل ملف في النهاية، لذا يجب أن يكون الكود مرنًا لكلا الاحتمالين.

قيمة الإرجاع هي نتيجة Tcl قياسية تشير إلى ما إذا كان قد حدث خطأ أثناء عملية المطابقة. يتم وضع رسائل الخطأ في interp، ما لم يكن interp NULL، وفي هذه الحالة لا يتم إنشاء رسالة خطأ. في حالة نتيجة TCL_OK، يجب إضافة النتائج إلى القيمة المعطاة في resultPtr (والتي يمكن افتراضها كقائمة Tcl غير مشتركة). يجب أن تتضمن المطابقات المضافة إلى resultPtr أي بادئة مسار معطاة في pathPtr (مما يعني عادةً أنها ستكون مواصفات مسار مطلق). ملاحظة: إذا لم تكن هناك مطابقات، فهذا يؤدي فقط إلى نتيجة فارغة؛ يتم الإشارة إلى الأخطاء فقط عندما تكون هناك مشاكل حقيقية مع الملفات أو أنظمة الملفات أثناء عملية المطابقة.

يحتوي الهيكل Tcl_GlobTypeData الذي يتم تمريره في المعامل types على الحقول التالية:

typedef struct Tcl_GlobTypeData {
    /* يتوافق مع bcdpfls كما في 'find -t' */
    int type;
    /* يتوافق مع أذونات الملف */
    int perm;
    /* نوع mac مقبول */
    Tcl_Obj *macType;
    /* منشئ mac مقبول */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

هناك حالتان خاصتان من المهم معالجتهما بشكل صحيح، وكلاهما عندما يكون types ليس NULL. الحالتان هما عندما يكون types->types & TCL_GLOB_TYPE_DIR صحيحًا أو types->types & TCL_GLOB_TYPE_MOUNT صحيحًا (وبشكل خاص عندما تكون الأعلام الأخرى خاطئة). في الحالة الأولى، يجب على الوظيفة سرد الدلائل الموجودة. يستخدم Tcl هذا لتنفيذ الاستدلال المتكرر، لذا من المهم أن تقوم أنظمة الملفات بتنفيذ مطابقة الدلائل بشكل صحيح. في الحالة الثانية، مع TCL_GLOB_TYPE_MOUNT، يجب على نظام الملفات سرد نقاط التحميل الموجودة داخل الدليل المقدم بواسطة pathPtr (وفي هذه الحالة، لا يحتاج pathPtr إلى أن يكون داخل نفس نظام الملفات - بخلاف جميع الحالات الأخرى التي يتم فيها استدعاء هذه الوظيفة). يعد دعم هذه الحالة أمرًا بالغ الأهمية إذا كان Tcl لديه انتقالات سلسة بين أنظمة الملفات.

تعيد رمز إرجاع Tcl قياسي. القيمة التي تم الحصول عليها تتوافق مع العنصر ذي المؤشر index في القائمة المعادة بواسطة Tcl_FSFileAttrStringsProc، ويتم وضعها في objPtrRef (إذا تم إرجاع TCL_OK). من المحتمل أن تكون لهذه القيمة عداد مرجع صفر. لذلك، يجب علينا تخزينها في مكان ما (على سبيل المثال، في نتيجة Tcl)، أو زيادة/تقليل عداد المرجع الخاص بها لضمان تحريرها بشكل صحيح.

FILEATTRSSETPROC

وظيفة لمعالجة استدعاء إلى Tcl_FSFileAttrsSet، والتي يستخدمها الأمر file attributes. إذا كان نظام الملفات للقراءة فقط، فلا يلزم تنفيذ هذا.

typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);

يجب تعيين قيمة خاصية العنصر ذي المؤشر index في القائمة المعادة بواسطة Tcl_FSFileAttrStringsProc إلى objPtr المعطى.

CREA

TEDIRECTORYPROC

دالة لمعالجة استدعاء Tcl_FSCreateDirectory. يجب تنفيذها ما لم يكن نظام الملفات للقراءة فقط.

typedef int Tcl_FSCreateDirectoryProc(
        Tcl_Obj *pathPtr);

القيمة المرجعة هي نتيجة Tcl قياسية تشير إلى ما إذا كان هناك خطأ قد حدث في العملية. في حالة النجاح، يجب أن يكون قد تمت إضافة دليل جديد إلى نظام الملفات في الموقع المحدد بواسطة pathPtr.

REMOVEDIRECTORYPROC

دالة لمعالجة استدعاء Tcl_FSRemoveDirectory. يجب تنفيذها ما لم يكن نظام الملفات للقراءة فقط.

typedef int Tcl_FSRemoveDirectoryProc(
        Tcl_Obj *pathPtr,
        int recursive,
        Tcl_Obj **errorPtr);

القيمة المرجعة هي نتيجة Tcl قياسية تشير إلى ما إذا كان هناك خطأ قد حدث في العملية. في حالة النجاح، يجب أن يكون قد تمت إزالة الدليل المحدد بواسطة pathPtr من نظام الملفات. إذا تم إعطاء العلامة recursive، فيجب حذف دليل غير فارغ دون خطأ. إذا لم يتم إعطاء هذه العلامة، وكان الدليل غير فارغ، فيجب الإشارة إلى خطأ POSIX "EEXIST". إذا حدث خطأ، فيجب وضع اسم الملف أو الدليل الذي تسبب في الخطأ في errorPtr.

DELETEFILEPROC

دالة لمعالجة استدعاء Tcl_FSDeleteFile. يجب تنفيذها ما لم يكن نظام الملفات للقراءة فقط.

typedef int Tcl_FSDeleteFileProc(
        Tcl_Obj *pathPtr);

القيمة المرجعة هي نتيجة Tcl قياسية تشير إلى ما إذا كان هناك خطأ قد حدث في العملية. في حالة النجاح، يجب أن يكون قد تمت إزالة الملف المحدد بواسطة pathPtr من نظام الملفات. لاحظ أنه إذا كان نظام الملفات يدعم الروابط الرمزية، فسوف تقوم Tcl دائمًا باستدعاء هذه الدالة وليس Tcl_FSRemoveDirectoryProc عند الحاجة إلى حذفها (حتى لو كانت روابط رمزية لأدلة).

كفاءة نظام الملفات

لا يلزم تنفيذ هذه الدوال لنظام ملفات معين لأن النواة لديها تنفيذ احتياطي متاح. انظر الوصف الفردي لكل دالة لمعرفة عواقب ترك الحقل NULL.

LSTATPROC

دالة لمعالجة استدعاء Tcl_FSLstat. إذا لم يتم تنفيذها، ستحاول Tcl استخدام statProc المعرفة أعلاه بدلاً من ذلك. لذلك، لا يلزم تنفيذها إلا إذا كان نظام الملفات يمكنه التمييز بين استدعاءات stat و lstat.

typedef int Tcl_FSLstatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

سلوك هذه الدالة مشابه جدًا لسلوك Tcl_FSStatProc المعرفة أعلاه، باستثناء أنه إذا تم تطبيقها على رابط رمزي، فإنها تُرجع معلومات حول الرابط، وليس حول الملف المستهدف.

COPYFILEPROC

دالة لمعالجة استدعاء Tcl_FSCopyFile. إذا لم يتم تنفيذها، فسوف تعتمد Tcl على آلية نسخ تعتمد على open-r و open-w و fcopy. لذلك، لا يلزم تنفيذها إلا إذا كان نظام الملفات يمكنه أداء هذا الإجراء بشكل أكثر كفاءة.

typedef int Tcl_FSCopyFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

القيمة المرجعة هي نتيجة Tcl قياسية تشير إلى ما إذا كان هناك خطأ قد حدث أثناء عملية النسخ. لاحظ أن destPathPtr هو اسم الملف الذي سيصبح نسخة من srcPathPtr. إنه ليس اسم دليل يمكن نسخ srcPathPtr إليه (أي أن الدالة أبسط بكثير من الأمر الفرعي file copy على مستوى Tcl). لاحظ أنه إذا كان نظام الملفات يدعم الروابط الرمزية، فسوف تقوم Tcl دائمًا باستدعاء هذه الدالة وليس copyDirectoryProc عند الحاجة إلى نسخها (حتى لو كانت روابط رمزية لأدلة). أخيرًا، إذا قرر نظام الملفات أنه لا يمكنه دعم إجراء file copy، فإن استدعاء Tcl_SetErrno(EXDEV) وإرجاع نتيجة غير TCL_OK سيخبر Tcl باستخدام آلياتها الاحتياطية القياسية.

RENAMEFILEPROC

دالة لمعالجة استدعاء Tcl_FSRenameFile. إذا لم يتم تنفيذها، فسوف تعتمد Tcl على آلية النسخ والحذف. لذلك، لا يلزم تنفيذها إلا إذا كان نظام الملفات يمكنه أداء هذا الإجراء بشكل أكثر كفاءة.

typedef int Tcl_FSRenameFileProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr);

القيمة المرجعة هي نتيجة Tcl قياسية تشير إلى ما إذا كان هناك خطأ قد حدث أثناء عملية إعادة التسمية. إذا قرر نظام الملفات أنه لا يمكنه دعم إجراء file rename، فإن استدعاء Tcl_SetErrno(EXDEV) وإرجاع نتيجة غير TCL_OK سيخبر Tcl باستخدام آلياتها الاحتياطية القياسية.

COPYDIRECTORYPROC

دالة لمعالجة استدعاء Tcl_FSCopyDirectory. إذا لم يتم تنفيذها، فسوف تعتمد Tcl على آلية تعتمد على file mkdir متكرر و file copy. لذلك، لا يلزم تنفيذها إلا إذا كان نظام الملفات يمكنه أداء هذا الإجراء بشكل أكثر كفاءة.

typedef int Tcl_FSCopyDirectoryProc(
        Tcl_Obj *srcPathPtr,
        Tcl_Obj *destPathPtr,
        Tcl_Obj **errorPtr);

القيمة المرجعة هي نتيجة Tcl قياسية تشير إلى ما إذا كان هناك خطأ قد حدث أثناء عملية النسخ. إذا حدث خطأ، فيجب وضع اسم الملف أو الدليل الذي تسبب في الخطأ في errorPtr. لاحظ أن destPathPtr هو اسم الدليل الذي سيصبح النسخة المتطابقة من srcPathPtr. إنه ليس اسم دليل يمكن نسخ srcPathPtr إليه (أي أن الدالة أبسط بكثير من الأمر الفرعي file copy على مستوى Tcl). أخيرًا، إذا قرر نظام الملفات أنه لا يمكنه دعم إجراء نسخ الدليل، فإن استدعاء Tcl_SetErrno(EXDEV) وإرجاع نتيجة غير TCL_OK سيخبر Tcl باستخدام آلياتها الاحتياطية القياسية.

LOADFILEPROC

دالة لمعالجة استدعاء Tcl_FSLoadFile. إذا لم يتم تنفيذها، فسوف تعتمد Tcl على نسخ إلى ملف مؤقت أصلي متبوعًا باستدعاء Tcl_FSLoadFile على هذا النسخة المؤقتة. لذلك، لا يلزم تنفيذها إلا إذا كان نظام الملفات يمكنه تحميل التعليمات البرمجية مباشرة، أو يمكن تنفيذها ببساطة لإرجاع TCL_ERROR لتعطيل وظيفة التحميل في نظام الملفات هذا تمامًا.

typedef int Tcl_FSLoadFileProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        Tcl_LoadHandle *handlePtr,
        Tcl_FSUnloadFileProc *unloadProcPtr);

تُرجع رمز إكمال Tcl قياسيًا. في حالة حدوث خطأ، يتم ترك رسالة خطأ في نتيجة interp. تقوم الدالة بتحميل ملف رمز ثنائي ديناميكيًا في الذاكرة. عند التحميل الناجح، يجب ملء handlePtr برمز للملف الذي تم تحميله ديناميكيًا، ويجب ملء unloadProcPtr بعنوان إجراء. سيتم استدعاء إجراء إلغاء التحميل باستخدام Tcl_LoadHandle المحدد كمعلمة وحيدة عندما تحتاج Tcl إلى إلغاء تحميل الملف. على سبيل المثال، بالنسبة لنظام الملفات الأصلي، فإن Tcl_LoadHandle المرجعة هي حاليًا رمز يمكن استخدامه في TclpFindSymbol الخاص للوصول إلى الدوال في التعليمات البرمجية الجديدة. لكل نظام ملفات حرية تعريف Tcl_LoadHandle كما يقتضي الأمر. أخيرًا، إذا قرر نظام الملفات أنه لا يمكنه دعم إجراء تحميل الملف، فإن استدعاء Tcl_SetErrno(EXDEV) وإرجاع نتيجة غير TCL_OK سيخبر Tcl باستخدام آلياتها الاحتياطية القياسية.

UNLOADFILEPROC

دالة لإلغاء تحميل ملف تم تحميله بنجاح سابقًا. إذا تم تنفيذ التحميل، فيجب أيضًا تنفيذ هذا، إذا كان هناك أي إجراء تنظيف مطلوب.

typedef void Tcl_FSUnloadFileProc(
        Tcl_LoadHandle loadHandle);

GETCWDPROC

دالة لمعالجة استدعاء Tcl_FSGetCwd. لا تحتاج معظم أنظمة الملفات إلى تنفيذها. عادةً ما يتم استدعاؤها مرة واحدة فقط، إذا تم استدعاء getcwd قبل chdir. قد تكون NULL.

typedef Tcl_Obj *Tcl_FSGetCwdProc(
        Tcl_Interp *interp);

إذا كان نظام الملفات يدعم مفهومًا أصليًا للدليل الحالي (والذي قد يتغير بشكل مستقل عن Tcl)، فيجب أن تُرجع هذه الدالة هذا الدليل الحالي كنتيجة، أو NULL إذا تعذر تحديد الدليل الحالي (على سبيل المثال، المستخدم ليس لديه الأذونات المناسبة على دليل الدليل الحالي). إذا تم إرجاع NULL، يتم ترك رسالة خطأ في نتيجة interp.

CHDIRPROC

دالة لمعالجة استدعاء Tcl_FSChdir. إذا لم تقم أنظمة الملفات بتنفيذها، فسيتم محاكاتها عن طريق سلسلة من عمليات التحقق من الوصول إلى الدليل. بخلاف ذلك، تحتاج أنظمة الملفات الافتراضية التي تنفذها إلى الاستجابة فقط بنتيجة إرجاع إيجابية إذا كان pathPtr دليلًا صالحًا ومتاحًا في نظام ملفاتها. لا يحتاجون إلى تذكر النتيجة، حيث سيتم تذكرها تلقائيًا للاستخدام بواسطة Tcl_FSGetCwd. يجب على أنظمة الملفات الحقيقية تنفيذ الإجراء الصحيح (أي استدعاء واجهة برمجة تطبيقات chdir الصحيحة للنظام).

typedef int Tcl_FSChdirProc(
        Tcl_Obj *pathPtr);

تغير Tcl_FSChdirProc الدليل الحالي للتطبيق إلى القيمة المحددة في pathPtr. تُرجع الدالة -1 عند حدوث خطأ أو 0 عند النجاح.
