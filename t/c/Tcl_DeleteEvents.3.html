Tcl_EventSetupProc *setupProc (in)
الإجراء المطلوب استدعاؤه للإعداد لانتظار الحدث في Tcl_DoOneEvent.
Tcl_EventCheckProc *checkProc (in)
الإجراء المطلوب من Tcl_DoOneEvent استدعاؤه بعد انتظار الأحداث. يتحقق مما إذا كانت أي أحداث قد وقعت، وإذا كان الأمر كذلك، يضيفها إلى الطابور.
ClientData clientData (in)
قيمة كلمة واحدة عشوائية تمرر إلى setupProc أو checkProc أو deleteProc.
const Tcl_Time *timePtr (in)
يشير إلى الحد الأقصى للوقت المراد الانتظار فيه لحدوث حدث. يتم تحديد هذا على أنه فاصل زمني (مدة الانتظار)، وليس وقتًا مطلقًا (متى سيتم الاستيقاظ). إذا كان المؤشر الممرر إلى Tcl_WaitForEvent هو NULL، فهذا يعني عدم وجود حد أقصى لوقت الانتظار: انتظر إلى الأبد إذا لزم الأمر.

حدث لإضافته إلى طابور الأحداث. يجب أن تكون مساحة الحدث قد تم تخصيصها بواسطة المتصل باستخدام Tcl_Alloc أو ckalloc.
Tcl_QueuePosition position (in)
مكان إضافة الحدث الجديد في الطابور: TCL_QUEUE_TAIL، TCL_QUEUE_HEAD، أو TCL_QUEUE_MARK.
Tcl_ThreadId threadId (in)

int mode (in)
يشير إلى ما إذا كان يجب معالجة الأحداث بواسطة Tcl_ServiceAll. يجب أن يكون أحد الخيارات التالية: TCL_SERVICE_NONE أو TCL_SERVICE_ALL.

مقدمة

تُستخدم الواجهات الموصوفة هنا لتخصيص حلقة أحداث Tcl. يتم وصف التخصيصات الأكثر شيوعًا، وهي إضافة مصادر أحداث جديدة ودمج حلقة أحداث Tcl مع حلقة أحداث أخرى، مثل تلك التي توفرها تطبيق يتم تضمين Tcl فيه. يتم وصف كل من هذه المهام في قسم منفصل أدناه.

الإجراءات الموجودة في إدخال الدليل هذا هي اللبنات الأساسية التي يتم بناء مُشعر Tcl منها. مُشعر الأحداث هو أدنى طبقة في آلية أحداث Tcl. وهو يتكون من ثلاثة أشياء:

[1]
مصادر الأحداث: تمثل هذه المصادر الطرق التي يمكن بها إنشاء الأحداث. على سبيل المثال، هناك مصدر أحداث مؤقت ينفذ إجراء Tcl_CreateTimerHandler والأمر after، وهناك مصدر أحداث ملف ينفذ إجراء Tcl_CreateFileHandler على أنظمة Unix. يجب أن يعمل مصدر الأحداث مع المُشعر للكشف عن الأحداث في الأوقات المناسبة، وتسجيلها في طابور الأحداث، وإبلاغ البرامج ذات المستوى الأعلى في النهاية بحدوثها. تُستخدم الإجراءات Tcl_CreateEventSource، Tcl_DeleteEventSource، و Tcl_SetMaxBlockTime، Tcl_QueueEvent، و Tcl_DeleteEvents بشكل أساسي بواسطة مصادر الأحداث.
[2]
طابور الأحداث: بالنسبة للتطبيقات غير المترابطة، يوجد طابور واحد للتطبيق بأكمله، يحتوي على الأحداث التي تم اكتشافها ولكن لم يتم التعامل معها بعد. تضع مصادر الأحداث الأحداث في الطابور حتى يمكن معالجتها بترتيب في أوقات مناسبة أثناء حلقة الأحداث. يضمن طابور الأحداث نظامًا عادلاً لمعالجة الأحداث، بحيث لا يمكن لأي مصدر أحداث استنزاف الآخرين. كما يسمح بتخزين الأحداث للمعالجة في وقت لاحق. تعمل التطبيقات المترابطة بطريقة مماثلة، باستثناء وجود طابور أحداث منفصل لكل خيط يحتوي على مترجم Tcl. يُستخدم Tcl_QueueEvent (بشكل أساسي بواسطة مصادر الأحداث) لإضافة الأحداث إلى طابور الأحداث، ويُستخدم Tcl_DeleteEvents لإزالة الأحداث من الطابور دون معالجتها. في تطبيق مترابط، تضيف Tcl_QueueEvent حدثًا إلى طابور الخيط الحالي، وتضيف Tcl_ThreadQueueEvent حدثًا إلى طابور في خيط معين.
[3]
حلقة الأحداث: للكشف عن الأحداث ومعالجتها، يدخل التطبيق في حلقة تنتظر حدوث الأحداث، ويضعها في طابور الأحداث، ثم يعالجها. ستقوم معظم تطبيقات Tcl بذلك عن طريق استدعاء الإجراء Tcl_DoOneEvent، الموصوف في دليل منفصل.

لا تحتاج معظم تطبيقات Tcl إلى القلق بشأن أي من التفاصيل الداخلية لمُشعر Tcl. ومع ذلك، فإن المُشعر يتمتع الآن بالمرونة الكافية لإعادة توجيهه إما لمنصة جديدة أو لاستخدام حلقة أحداث خارجية (مثل حلقة أحداث Motif، عند تضمين Tcl في تطبيق Motif). يتم تنفيذ الإجراءات Tcl_WaitForEvent و Tcl_SetTimer عادةً بواسطة Tcl، ولكن يمكن استبدالها بإصدارات جديدة لإعادة توجيه المُشعر (يجب أيضًا استبدال Tcl_InitNotifier، Tcl_AlertNotifier، Tcl_FinalizeNotifier، Tcl_Sleep، Tcl_CreateFileHandler، و Tcl_DeleteFileHandler؛ انظر إنشاء مُشعر جديد أدناه للحصول على التفاصيل). تم توفير الإجراءات Tcl_ServiceAll، Tcl_ServiceEvent، Tcl_GetServiceMode، و Tcl_SetServiceMode للمساعدة في ربط حلقة أحداث Tcl بحلقة أحداث خارجية مثل حلقة Motif.

أساسيات المُشعر

أسهل طريقة لفهم كيفية عمل المُشعر هي النظر إلى ما يحدث عند استدعاء Tcl_DoOneEvent. يتم تمرير وسيطة flags إلى Tcl_DoOneEvent تشير إلى نوع الأحداث التي لا بأس بمعالجتها وما إذا كان يجب الحظر إذا لم تكن هناك أحداث جاهزة. يقوم Tcl_DoOneEvent بالمهام التالية:

[1]
التحقق من طابور الأحداث لمعرفة ما إذا كان يحتوي على أي أحداث يمكن التعامل معها. إذا كان الأمر كذلك، قم بمعالجة أول حدث ممكن، وإزالته من الطابور، والعودة. يتم ذلك عن طريق استدعاء Tcl_ServiceEvent وتمرير وسيطة flags.
[2]
الاستعداد للحظر لحدث ما. للقيام بذلك، يستدعي Tcl_DoOneEvent إجراء إعداد في كل مصدر حدث. سيقوم مصدر الحدث بإجراء تهيئة خاصة بمصدر الحدث وقد يستدعي Tcl_SetMaxBlockTime لتحديد المدة التي سيحظرها Tcl_WaitForEvent إذا لم تحدث أحداث جديدة.
[3]
استدعاء Tcl_WaitForEvent. يتم تنفيذ هذا الإجراء بشكل مختلف على منصات مختلفة؛ ينتظر حدوث حدث، بناءً على المعلومات المقدمة من مصادر الأحداث. قد يتسبب في حظر التطبيق إذا كانت timePtr تحدد فاصلًا زمنيًا بخلاف 0. تُرجع Tcl_WaitForEvent عندما يحدث شيء ما، مثل أن يصبح الملف قابلاً للقراءة أو انتهاء المهلة المحددة بواسطة timePtr. إذا لم تكن هناك أحداث لـ Tcl_WaitForEvent للانتظار، بحيث يحظر إلى الأبد، فإنه يُرجع على الفور وتُرجع Tcl_DoOneEvent القيمة 0.
[4]
استدعاء إجراء تحقق في كل مصدر حدث. يحدد إجراء التحقق ما إذا كانت الأحداث التي تهم هذا المصدر قد وقعت. إذا كان الأمر كذلك، تتم إضافة الأحداث إلى طابور الأحداث.
[5]

إنشاء مصدر حدث جديد

يتكون مصدر الحدث من ثلاثة إجراءات تستدعيها أداة الإشعار، بالإضافة إلى إجراءات C إضافية يتم استدعاؤها بواسطة كود المستوى الأعلى لتنظيم استدعاءات ردود الفعل المستندة إلى الأحداث. تتكون الإجراءات الثلاثة التي تستدعيها أداة الإشعار من إجراءات الإعداد والتحقق الموضحة أعلاه، بالإضافة إلى إجراء إضافي يتم استدعاؤه عند إزالة حدث من قائمة انتظار الأحداث للمعالجة.

ينشئ الإجراء Tcl_CreateEventSource مصدر حدث جديد. تحدد وسيطاته إجراء الإعداد والتحقق لمصدر الحدث. يجب أن يتوافق SetupProc مع النموذج الأولي التالي:

typedef void Tcl_EventSetupProc(
        ClientData clientData,
        int flags);

ستكون الوسيطة clientData هي نفسها الوسيطة clientData لـ Tcl_CreateEventSource؛ تُستخدم عادةً للإشارة إلى معلومات خاصة تديرها مصدر الحدث. ستكون الوسيطة flags هي نفسها الوسيطة flags التي تم تمريرها إلى Tcl_DoOneEvent، إلا إذا كانت 0 (في هذه الحالة، يستبدل Tcl_DoOneEvent القيمة 0 بـ TCL_ALL_EVENTS). تشير flags إلى أنواع الأحداث التي يجب أخذها في الاعتبار؛ إذا لم يتم تعيين البت المقابل لمصدر الحدث هذا، يجب أن يعود مصدر الحدث فورًا دون فعل أي شيء. على سبيل المثال، يتحقق مصدر حدث الملف من البت TCL_FILE_EVENTS.

يجب أن يضمن SetupProc أن التطبيق يستيقظ عند حدوث أحداث من النوع المطلوب. يتم ذلك عادةً بطريقة تعتمد على النظام الأساسي. على سبيل المثال، في نظام Unix، قد يستدعي مصدر حدث Tcl_CreateFileHandler؛ في نظام Windows، قد يطلب إشعارًا باستخدام حدث Windows. بالنسبة لمصادر الأحداث المستندة إلى مؤقت مثل الأحداث المؤقتة أو أي أحداث يتم استقصاؤها، يمكن لمصدر الحدث استدعاء Tcl_SetMaxBlockTime لإجبار التطبيق على الاستيقاظ بعد فترة زمنية محددة، حتى لو لم تكن هناك أحداث. إذا لم يستدعِ أي مصدر حدث Tcl_SetMaxBlockTime، فسيتم انتظار Tcl_WaitForEvent طالما لزم الأمر لحدوث حدث؛ وإلا، فلن ينتظر إلا أقصر فترة بين استدعاءات Tcl_SetMaxBlockTime التي يجريها أحد مصادر الأحداث. إذا كان مصدر الحدث يعلم أنه لديه بالفعل أحداث جاهزة للإبلاغ عنها، فيمكنه طلب وقت حظر أقصى يبلغ صفرًا. على سبيل المثال، يقوم إجراء إعداد حدث X بفحص ما إذا كانت هناك أحداث موجودة بالفعل في قائمة الانتظار. إذا كان الأمر كذلك، فإنه يستدعي Tcl_SetMaxBlockTime بوقت حظر أقصى يبلغ صفرًا حتى لا يتم حظر Tcl_WaitForEvent إذا لم تكن هناك بيانات جديدة في اتصال X. تشير الوسيطة timePtr لـ Tcl_WaitForEvent إلى بنية تصف فترة زمنية بالثواني والميكروثواني:

typedef struct Tcl_Time {
    long sec;
    long usec;
} Tcl_Time;

يجب أن يكون الحقل usec أقل من 1,000,000.

تُستخدم المعلومات المقدمة إلى Tcl_SetMaxBlockTime فقط لاستدعاء Tcl_WaitForEvent التالي؛ يتم تجاهلها بعد عودة Tcl_WaitForEvent. في المرة التالية التي يتم فيها إجراء انتظار حدث، سيتم استدعاء كل إجراء إعداد لمصادر الأحداث مرة أخرى، ويمكنها تحديد بيانات جديدة لهذا الانتظار الحدث.

إذا كان التطبيق يستخدم حلقة أحداث خارجية بدلاً من Tcl_DoOneEvent، فقد تحتاج مصادر الأحداث إلى استدعاء Tcl_SetMaxBlockTime في أوقات أخرى. على سبيل المثال، إذا تم تسجيل معالج حدث جديد يحتاج إلى مراقبة الأحداث، فقد يستدعي مصدر الحدث Tcl_SetMaxBlockTime لتعيين وقت حظر أقصى يبلغ صفرًا، مما يجبر حلقة الأحداث الخارجية على استدعاء Tcl. في هذه الحالة، يستدعي Tcl_SetMaxBlockTime Tcl_SetTimer بأقصر فترة منذ آخر استدعاء لـ Tcl_DoOneEvent أو Tcl_ServiceAll.

بالإضافة إلى الإجراء العام Tcl_SetMaxBlockTime، قد تكون هناك إجراءات أخرى خاصة بالمنصة متاحة لـ setupProc، إذا كانت هناك حاجة لمعلومات إضافية من قبل Tcl_WaitForEvent على تلك المنصة. على سبيل المثال، في أنظمة Unix، يمكن استخدام الواجهة Tcl_CreateFileHandler لانتظار أحداث الملف.

الإجراء الثاني الذي يوفره كل مصدر حدث هو إجراء التحقق الخاص به، والمشار إليه بالوسيطة checkProc لـ Tcl_CreateEventSource. يجب أن يتوافق CheckProc مع النموذج الأولي التالي:

typedef void Tcl_EventCheckProc(
        ClientData clientData,
        int flags);

الوسيطات لهذا الإجراء هي نفس الوسيطات الخاصة بـ setupProc. يتم استدعاء CheckProc بواسطة Tcl_DoOneEvent بعد الانتظار للأحداث. من المفترض أن يكون مصدر حدث واحد على الأقل جاهزًا لوضع حدث في قائمة الانتظار. يستدعي Tcl_DoOneEvent كل مصدر حدث بالترتيب، بحيث تتاح للجميع فرصة وضع أي أحداث جاهزة. يقوم إجراء التحقق بأمرين. أولاً، يجب عليه التحقق مما إذا كانت هناك أحداث قد حدثت. تقوم مصادر الأحداث المختلفة بذلك بطرق مختلفة.

إذا اكتشف مصدر حدث حدثًا مثيرًا للاهتمام، فيجب عليه إضافة الحدث إلى قائمة انتظار Tcl. للقيام بذلك، يستدعي مصدر الحدث Tcl_QueueEvent. الوسيطة evPtr هي مؤشر إلى بنية تم تخصيصها ديناميكيًا تحتوي على الحدث (انظر المزيد حول مشاكل إدارة الذاكرة). يمكن لكل مصدر حدث تعريف بنية الحدث الخاصة به مع معلومات ذات صلة بمصدر الحدث هذا. ومع ذلك، يجب أن يكون العنصر الأول من البنية بنية من نوع Tcl_Event، ويستخدم المؤشر إلى هذه البنية عند الاتصال بين مصدر الحدث وبقية أداة الإشعار. تحتوي Tcl_Event على التعريف التالي:

typedef struct {
    Tcl_EventProc *proc;
    struct Tcl_Event *nextPtr;
} Tcl_Event;

يجب على مصدر الحدث ملء الحقل proc لبنية الحدث قبل استدعاء Tcl_QueueEvent. يُستخدم nextPtr لربط الأحداث في قائمة الانتظار ويجب ألا يتم تعديله بواسطة مصدر الحدث.

يمكن إضافة حدث إلى قائمة الانتظار في أحد المواقع الثلاثة، اعتمادًا على الوسيطة position لـ Tcl_QueueEvent:

TCL_QUEUE_TAIL
إضافة الحدث إلى نهاية قائمة الانتظار، بحيث يتم معالجة جميع الأحداث المعلقة أولاً. هذا هو المكان المناسب دائمًا للأحداث الجديدة.
TCL_QUEUE_HEAD
إضافة الحدث إلى بداية قائمة الانتظار، بحيث يتم معالجته قبل جميع الأحداث الأخرى في قائمة الانتظار.
TCL_QUEUE_MARK
إضافة الحدث إلى بداية قائمة الانتظار، إلا إذا كانت هناك أحداث أخرى في بداية قائمة الانتظار لها الموضع TCL_QUEUE_MARK؛ إذا كان الأمر كذلك، أضف الحدث الجديد مباشرة بعد جميع أحداث TCL_QUEUE_MARK الأخرى. تُستخدم قيمة position هذه لإدراج تسلسل مرتب من الأحداث في مقدمة قائمة الانتظار، مثل سلسلة من أحداث Enter و Leave الاصطناعية أثناء عملية التقاط أو إلغاء التقاط في Tk.

عندما يحين وقت معالجة حدث من قائمة الانتظار (الخطوتان 1 و 4 أعلاه)، سيستدعي Tcl_ServiceEvent proc المحدد في البنية الأولى لـ Tcl_Event الموجودة في قائمة الانتظار. يجب أن يتوافق Proc مع النموذج الأولي التالي:

typedef int Tcl_EventProc(
        Tcl_Event *evPtr,
        int flags);

الوسيطة الأولى لـ proc هي مؤشر إلى الحدث، والذي سيكون هو نفسه الوسيطة الأولى لاستدعاء Tcl_QueueEvent الذي أضاف الحدث إلى قائمة الانتظار. الوسيطة الثانية لـ proc هي الوسيطة flags لاستدعاء Tcl_ServiceEvent الحالي؛ تُستخدم هذه من قبل مصدر الحدث للعودة فورًا إذا لم تكن أحداثه ذات صلة.

تقع على عاتق proc مسؤولية التعامل مع الحدث، وذلك عادةً عن طريق استدعاء أمر Tcl واحد أو أكثر أو استدعاءات ردود الفعل على مستوى C. بمجرد الانتهاء من مصدر الحدث من التعامل مع الحدث، فإنه يعيد 1 للإشارة إلى أنه يمكن إزالة الحدث من قائمة الانتظار. إذا قرر مصدر الحدث، لأي سبب من الأسباب، أنه لا يمكن معالجة الحدث في الوقت الحالي، فيمكنه إعادة 0 للإشارة إلى أنه يجب تأجيل الحدث للمعالجة لاحقًا؛ في هذه الحالة، ينتقل Tcl_ServiceEvent إلى الإدخال التالي في قائمة الانتظار ويحاول معالجته. هناك عدة أسباب قد تجعل مصدر الحدث يؤجل حدثًا. أحد الاحتمالات هو أن الأحداث من هذا النوع مستبعدة بواسطة الوسيطة flags. على سبيل المثال، يعيد مصدر حدث الملف دائمًا 0 إذا لم يتم تعيين البت TCL_FILE_EVENTS في flags. مثال آخر لتأجيل الأحداث يحدث في Tk إذا تم استدعاء Tk_RestrictEvents لتأجيل أنواع معينة من أحداث النافذة.

عندما يعيد proc القيمة 1، ستقوم Tcl_ServiceEvent بإزالة الحدث من قائمة انتظار الأحداث وتحرير مساحته التخزينية. يجب أن تلاحظ أن مساحة تخزين الحدث يجب أن يتم تخصيصها بواسطة مصدر الحدث (باستخدام Tcl_Alloc أو ماكرو Tcl ckalloc) قبل استدعاء Tcl_QueueEvent، ولكن سيتم تحريرها بواسطة Tcl_ServiceEvent، وليس بواسطة مصدر الحدث.

تعمل التطبيقات متعددة الخيوط بشكل مشابه، باستثناء وجود قائمة انتظار أحداث منفصلة لكل خيط يحتوي على مترجم Tcl. يؤدي استدعاء Tcl_QueueEvent في التطبيقات متعددة الخيوط إلى إضافة حدث إلى قائمة انتظار الخيط الحالي. لإضافة حدث إلى قائمة انتظار خيط آخر، استخدم Tcl_ThreadQueueEvent. يقبل Tcl_ThreadQueueEvent كوسيطة وسيطة Tcl_ThreadId، والتي تحدد فريدًا خيطًا في تطبيق Tcl. للحصول على Tcl_ThreadId للخيط الحالي، استخدم الإجراء Tcl_GetCurrentThread. (بعد ذلك، سيحتاج الخيط إلى تمرير هذا المعرف إلى خيوط أخرى حتى يتمكنوا من إضافة أحداث إلى قائمته.) بعد إضافة حدث إلى قائمة انتظار خيط آخر، يجب عادةً استدعاء Tcl_ThreadAlert "لإيقاظ" أداة إشعار هذا الخيط لتنبيهه بالحدث الجديد.

يمكن استخدام Tcl_DeleteEvents بشكل صريح لإزالة حدث واحد أو أكثر من قائمة انتظار الأحداث. يستدعي Tcl_DeleteEvents proc لكل حدث في قائمة الانتظار، وإزالة تلك التي تعيد 1. تظل الأحداث التي تعيد 0 في قائمة الانتظار. يجب أن يتوافق Proc مع النموذج الأولي التالي:

typedef int Tcl_EventDeleteProc(
        Tcl_Event *evPtr,
        ClientData clientData);

ستكون الوسيطة clientData هي نفسها الوسيطة clientData لـ Tcl_DeleteEvent؛ تُستخدم عادةً للإشارة إلى معلومات خاصة تديرها مصدر الحدث.

NAME

Tcl_NotifierCmd - create a new notifier, event queue, event sources, file events, timer, idle, service mode, threads

SYNOPSIS


notifier cmd ?arg ...?

ARGUMENTS

notifier create ?"name"? ?"mode"?
Creates a new notifier with the given name and mode. If the name is not given, it will be generated automatically. If the mode is not given, it defaults to "auto". Valid modes are "auto", "poll", "select", "threads".
notifier delete notifierName
Deletes the notifier with the given name.
notifier find ?name?
Finds a notifier by name. If no name is given, it returns a list of all notifiers.
notifier info notifierName
Returns information about the given notifier.
notifier install notifierName ?source?
Installs the notifier with the given name. If a source is given, it will be used as the event source for the notifier.
notifier uninstall notifierName
Uninstalls the notifier with the given name.
notifier service notifierName ?mode?
Sets the service mode for the notifier. Valid modes are "start", "stop", "suspend", "resume".
notifier mode notifierName ?newMode?
Gets or sets the mode for the notifier.
notifier queue notifierName ?newQueue?
Gets or sets the event queue for the notifier.
notifier source notifierName ?newSource?
Gets or sets the event source for the notifier.
notifier flush notifierName
Flushes the event queue for the notifier.
notifier poll notifierName ?timeout?
Polls the event source for events. If a timeout is given, it will block for that long.
notifier process notifierName
Processes events in the queue for the notifier.

INTRODUCTION

The notifier command is used to create and manage notifiers. A notifier is an object that monitors event sources and dispatches events to the Tcl event queue. Notifiers are used to implement event-driven programming in Tcl.

NOTIFIER BASICS

A notifier consists of the following components:

  • Event Sources: These are objects that generate events. Examples include file descriptors, timers, and idle sources.
  • Event Queue: This is a queue that stores events that have been generated by the event sources.
  • Notifier: This object monitors the event sources and dispatches events to the event queue. It also processes events from the queue and dispatches them to the appropriate Tcl commands.

The notifier command provides a way to create, delete, find, and manage notifiers. It also allows you to install and uninstall event sources, and to control the service mode of a notifier.

CREATING A NEW EVENT SOURCE

Tcl provides several built-in event sources, such as file events, timer events, and idle events. You can also create custom event sources by implementing the Tcl notifier interface.

CREATING A NEW NOTIFIER

To create a new notifier, use the notifier create command:


notifier create ?"name"? ?"mode"?

The name argument is optional and specifies the name of the notifier. If not given, a name will be generated automatically. The mode argument specifies the polling mode of the notifier. Valid modes are "auto", "poll", "select", and "threads".

REPLACING THE NOTIFIER

You can replace the current notifier with a new one using the notifier install command. This is useful for changing the event handling mechanism or for integrating with external event loops.

EXTERNAL EVENT LOOPS

The notifier command can be used to integrate Tcl with external event loops. By replacing the default notifier with a custom one, you can use Tcl's event handling capabilities within other frameworks or applications.
