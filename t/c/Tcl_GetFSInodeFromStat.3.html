الوصف

هناك عدة أسباب لتسمية دوال Tcl_FS (مثل Tcl_FSAccess و Tcl_FSStat) بدلاً من استدعاء دوال النظام مباشرة مثل access و stat. أولاً، ستعمل هذه الدوال عبر المنصات، لذا فإن أي امتداد يستدعيها يجب أن يعمل دون تعديل على أنظمة Unix و Windows. ثانيًا، يقوم تطبيق بعض هذه الدوال على Windows بتصحيح بعض الأخطاء في استدعاءات مستوى النظام. ثالثًا، تتعامل استدعاءات الدوال هذه مع أي تحويلات مطلوبة من مسارات "UTF إلى المنصة الأصلية" (وقد تقوم بتخزين نتائج هذه التحويلات مؤقتًا لتحسين الأداء في الاستدعاءات اللاحقة). رابعًا، وربما الأهم، كل هذه الدوال "واعية بالملفات الافتراضية" (VFS). أي VFS (اختصار للملفات الافتراضية) مسجل (عبر Tcl_FSRegister) يمكنه إعادة توجيه الوصول إلى الملفات إلى وسائط أو طرق بديلة. هذا يعني أن كل هذه الدوال (وبالتالي أوامر Tcl المقابلة file و glob و pwd و cd و open وما إلى ذلك) يمكنها العمل على "ملفات" ليست ملفات أصلية في نظام الملفات. هذا يعني أيضًا أن أي امتداد Tcl يصل إلى نظام الملفات (FS باختصار) عبر واجهة برمجة التطبيقات هذه سيكون "واعيًا بالملفات الافتراضية" تلقائيًا. من الواضح أنه إذا وصل امتداد مباشرة إلى نظام الملفات الأصلي (عبر واجهات برمجة التطبيقات الخاصة بالمنصة)، فلا يمكن لـ Tcl اعتراض مثل هذه الاستدعاءات.

إذا تم تسجيل VFS بشكل صحيح، يمكن أن تكون "الملفات"، على سبيل المثال، بعيدة (مثل الموجودة على خادم ftp بعيد) أو مؤرشفة (مثل الموجودة داخل ملف .zip). توفر أنظمة الملفات المسجلة جدول دوال لتنفيذ جزء أو كل الدوال المذكورة هنا. أخيرًا، تقوم استدعاءات Tcl_FSStat و Tcl_FSLstat بتجريد محتويات المخزن المؤقت struct stat، مما يسمح باستخدام نفس الكود على كل من الأنظمة التي تدعم الملفات التي تزيد عن 2 جيجابايت وتلك التي لا تدعم ذلك.

واجهة برمجة تطبيقات Tcl_FS مصممة باستخدام Tcl_Obj ويمكنها تخزين التمثيل الداخلي مؤقتًا وغيرها من السلاسل النصية المتعلقة بالمسارات (مثل الدليل الحالي). أحد الآثار الجانبية لهذا هو أنه لا يجب عليك تمرير قيم ذات عداد مرجعي صفر إلى أي من هذه الدوال. إذا تم التعامل مع مثل هذه الاستدعاءات، فقد تتسبب في تسرب الذاكرة (في بعض الحالات، قد يتخلص كود النظام من مرجع إلى القيمة الممررة، وبالتالي لا يفترض أنه بعد أي استدعاء لهذه الدوال، لم تعد القيمة تحتوي على عداد مرجعي صفر - ربما تم زيادته). أو، قد يؤدي ذلك إلى خطأ في القسم (أو خطأ آخر في الوصول إلى الذاكرة) نظرًا لأنه قد يتم تحرير القيمة أثناء معالجة معقدة للقيمة لضمان أن المسار طبيعي ومطلق لنظام الملفات. الدرس العملي الذي يجب تعلمه من هذا هو:

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

غير صحيح وقد يسبب أخطاء في الذاكرة. يجب زيادة عداد المراجع لـ path قبل تمريره، أو إنقاصه. لهذا السبب تعتبر القيم ذات عداد مرجعي صفر غير صالحة كمسارات لنظام الملفات، واستدعاء أي دالة لواجهة برمجة التطبيقات Tcl_FS بقيمة كهذه لا يؤدي إلى أي إجراء.

دوال واجهة برمجة التطبيقات لنظام الملفات

تحاول Tcl_FSCopyFile نسخ الملف المحدد بواسطة srcPathPtr إلى المسار المحدد بواسطة destPathPtr. إذا كان المساران المحددان يقعان في نفس نظام الملفات (حسب Tcl_FSGetFileSystemForPath)، يتم استدعاء دالة نسخ الملف الخاصة بنظام الملفات. بخلاف ذلك، ترجع الدالة -1 وتعين المتغير العام errno إلى EXDEV (رمز POSIX يشير إلى رابط عبر النطاقات).

تحاول Tcl_FSCopyDirectory نسخ الدليل المحدد بواسطة srcPathPtr إلى المسار المحدد بواسطة destPathPtr. إذا كان المساران المحددان يقعان في نفس نظام الملفات (حسب Tcl_FSGetFileSystemForPath)، يتم استدعاء دالة نسخ الدليل الخاصة بنظام الملفات. بخلاف ذلك، ترجع الدالة -1 وتعين المتغير العام errno إلى EXDEV (رمز POSIX يشير إلى رابط عبر النطاقات).

تحاول Tcl_FSCreateDirectory إنشاء الدليل المحدد بواسطة pathPtr عن طريق استدعاء دالة إنشاء الدليل الخاصة بنظام الملفات الذي يمتلكه.

تحاول Tcl_FSDeleteFile حذف الملف المحدد بواسطة pathPtr عن طريق استدعاء دالة حذف الملف الخاصة بنظام الملفات الذي يمتلكه.

تحاول Tcl_FSRemoveDirectory حذف الدليل المحدد بواسطة pathPtr عن طريق استدعاء دالة حذف الدليل الخاصة بنظام الملفات الذي يمتلكه.

تحاول Tcl_FSRenameFile إعادة تسمية الملف أو الدليل المحدد بواسطة srcPathPtr إلى المسار المحدد بواسطة destPathPtr. إذا كان المساران المحددان يقعان في نفس نظام الملفات (حسب Tcl_FSGetFileSystemForPath)، يتم استدعاء دالة إعادة تسمية الملف الخاصة بنظام الملفات. بخلاف ذلك، ترجع الدالة -1 وتعين المتغير العام errno إلى EXDEV (رمز POSIX يشير إلى رابط عبر النطاقات).

تستدعي Tcl_FSListVolumes كل نظام ملفات لديه قيمة list volumes غير فارغة وتطلب منه إرجاع قائمة وحدات التخزين الجذرية الخاصة به. تقوم بتجميع القيم المرجعة في قائمة يتم إرجاعها إلى المتصل (بعداد مراجع صفر).

تقوم Tcl_FSEvalFileEx بقراءة الملف المحدد بواسطة pathPtr باستخدام ترميز التشفير المحدد بواسطة encodingName وتقييم محتواه كبرنامج نصي Tcl. ترجع نفس المعلومات التي ترجعها Tcl_EvalObjEx. إذا كان encodingName هو NULL، يتم استخدام ترميز التشفير الخاص بالنظام لقراءة محتويات الملف. إذا لم يكن من الممكن قراءة الملف، يتم إرجاع خطأ Tcl لوصف سبب عدم إمكانية قراءة الملف. حرف نهاية الملف للملفات هو \x1A (^Z) لجميع الأنظمة. إذا كنت ترغب في استخدام \x1A في الكود لمقارنات السلاسل النصية، يمكنك استخدامه، وسيتم استبداله بشكل صحيح بواسطة مترجم Tcl بـ \x1A. Tcl_FSEvalFile هي نسخة أبسط من Tcl_FSEvalFileEx، والتي تستخدم دائمًا ترميز التشفير الخاص بالنظام عند قراءة الملف.

تقوم Tcl_FSLoadFile بتحميل ملف كود ثنائي ديناميكيًا في الذاكرة وترجع عناوين إجرائين داخل هذا الملف، إذا تم تحديدهما. سيتم استدعاء الدالة المناسبة لنظام الملفات الذي ينتمي إليه pathPtr. إذا لم يقم نظام الملفات هذا بتنفيذ هذه الدالة (لن تقوم معظم الأنظمة الافتراضية بتنفيذها بسبب قيود نظام التشغيل على تحميل الكود الثنائي ديناميكيًا)، فستحاول Tcl نسخ الملف إلى دليل مؤقت وتحميل هذا الملف المؤقت. تقوم Tcl_FSUnloadFile بعكس هذه العملية، وتطلب من العملية إزالة المكتبة المحددة بواسطة loadHandle من التنفيذ. لاحظ أنه على عكس الأمر unload، فإن هذا لا يمنح المكتبة فرصة للتنظيف.

كلتا الدالتين المذكورتين أعلاه ترجعان رمز نتيجة قياسي من Tcl. إذا حدث خطأ، يتم ترك رسالة خطأ في نتيجة interp.

يمكن استخدام الرمز المميز الذي توفره المتغير المحدد بواسطة loadHandlePtr مع Tcl_FindSymbol.

تستخدم Tcl_FSMatchInDirectory بواسطة كود globbing للعثور على جميع الملفات التي تتطابق مع نمط معين في دليل. سيتم استدعاء الدالة المناسبة لنظام الملفات الذي ينتمي إليه pathPtr.

القيمة المرجعة هي نتيجة Tcl قياسية تشير إلى ما إذا كان هناك خطأ أثناء عملية globbing. يتم وضع رسائل الخطأ في interp (ما لم يكن interp هو NULL، وهو ما يُسمح به)، ولكن يتم وضع نتائج جيدة في resultPtr المحدد.

ملاحظة: يقوم كود glob بتنفيذ الأنماط المتكررة داخليًا، لذلك سيتم تمرير أنماط بسيطة فقط إلى هذه الدالة، والتي يمكن مطابقتها باستخدام منطق string match. للتعامل مع التكرار، ستستدعي Tcl هذه الدالة بشكل متكرر مطالبةً بإرجاع الأدلة فقط. حالة خاصة من الاستدعاء بنمط NULL تعني أنه يجب التحقق من المسار فقط لمعرفة نوعه الصحيح.

تستبدل Tcl_FSLink إصدار المكتبة من readlink وتوسعه لدعم إنشاء الروابط. سيتم استدعاء الدالة المناسبة لنظام الملفات الذي ينتمي إليه linkNamePtr.

Tcl_FSNewNativePath performs something like the reverse of the usual obj->path->nativerep conversions. If some code retrieves a path in native form (from, e.g. readlink or a native dialog), and that path is to be used at the Tcl level, then calling this function is an efficient way of creating the appropriate path value type.

The resulting value is a pure “path” value, which will only receive a UTF-8 string representation if that is required by some Tcl code.

Tcl_FSGetNativePath is for use by the Win/Unix native filesystems, so that they can easily retrieve the native (char* or TCHAR*) representation of a path. This function is a convenience wrapper around Tcl_FSGetInternalRep. It may be desirable in the future to have non-string-based native representations (for example, on macOS, a representation using a fileSpec of FSRef structure would probably be more efficient). On Windows a full Unicode representation would allow for paths of unlimited length. Currently the representation is simply a character string which may contain either the relative path or a complete, absolute normalized path in the native encoding (complex conditions dictate which of these will be provided, so neither can be relied upon, unless the path is known to be absolute). If you need a native path which must be absolute, then you should ask for the native version of a normalized path. If for some reason a non-absolute, non-normalized version of the path is needed, that must be constructed separately (e.g. using Tcl_FSGetTranslatedPath).

THE VIRTUAL FILESYSTEM API

A filesystem provides a Tcl_Filesystem structure that contains pointers to functions that implement the various operations on a filesystem; these operations are invoked as needed by the generic layer, which generally occurs through the functions listed above.

The Tcl_Filesystem structures are manipulated using the following methods.

Tcl_FSRegister takes a pointer to a filesystem structure and an optional piece of data to associated with that filesystem. On calling this function, Tcl will attach the filesystem to the list of known filesystems, and it will become fully functional immediately. Tcl does not check if the same filesystem is registered multiple times (and in general that is not a good thing to do). TCL_OK will be returned.

Tcl_FSUnregister removes the given filesystem structure from the list of known filesystems, if it is known, and returns TCL_OK. If the filesystem is not currently registered, TCL_ERROR is returned.

Tcl_FSData will return the clientData associated with the given filesystem, if that filesystem is registered. Otherwise it will return NULL.

Tcl_FSMountsChanged is used to inform the Tcl's core that the set of mount points for the given (already registered) filesystem have changed, and that cached file representations may therefore no longer be correct.

Except for the first three fields in this structure which contain simple data elements, all entries contain addresses of functions called by the generic filesystem layer to perform the complete range of filesystem related actions.

The many functions in this structure are broken down into three categories: infrastructure functions (almost all of which must be implemented), operational functions (which must be implemented if a complete filesystem is provided), and efficiency functions (which need only be implemented if they can be done so efficiently, or if they have side-effects which are required by the filesystem; Tcl has less efficient emulations it can fall back on). It is important to note that, in the current version of Tcl, most of these fallbacks are only used to handle commands initiated in Tcl, not in C. What this means is, that if a file rename command is issued in Tcl, and the relevant filesystem(s) do not implement their Tcl_FSRenameFileProc, Tcl's core will instead fallback on a combination of other filesystem functions (it will use Tcl_FSCopyFileProc followed by Tcl_FSDeleteFileProc, and if Tcl_FSCopyFileProc is not implemented there is a further fallback). However, if a Tcl_FSRenameFileProc command is issued at the C level, no such fallbacks occur. This is true except for the last four entries in the filesystem table (lstat, load, getcwd and chdir) for which fallbacks do in fact occur at the C level.

Any functions which take path names in Tcl_Obj form take those names in UTF-8 form. The filesystem infrastructure API is designed to support efficient, cached conversion of these UTF-8 paths to other native representations.
