مقدمة

تقوم هذه الروتينات بالتحويل بين تمثيل أحرف Tcl الداخلي، UTF-8، وتمثيلات الأحرف التي تستخدمها أنظمة التشغيل أو أنظمة الملفات المختلفة، مثل Unicode أو ASCII أو Shift-JIS. عند العمل على السلاسل النصية، مثل الحصول على أسماء الملفات أو عرض الأحرف باستخدام الخطوط الدولية، يجب ترجمة السلاسل إلى تنسيق واحد أو ربما تنسيقات متعددة يمكن لنداءات النظام المختلفة استخدامها. على سبيل المثال، على محطة عمل Unix يابانية، قد يحصل المستخدم على اسم ملف ممثل بترميز الملف EUC-JP ثم يترجم الأحرف إلى ترميز الخط jisx0208 لعرض اسم الملف في عنصر واجهة Tk. الغرض من حزمة الترميز هو المساعدة في سد فجوة الترجمة. يوفر UTF-8 ساحة وقوف وسيطة لجميع الترميزات المختلفة. في المثال أعلاه، سيتم ترجمة النص إلى UTF-8 من أي ترميز ملف يستخدمه نظام التشغيل. ثم سيتم ترجمته من UTF-8 إلى أي ترميز خط تتطلبه روتينيات العرض.

بعض الترميزات الأساسية مدمجة في Tcl. يمكن تعريف ترميزات أخرى بواسطة المستخدم أو تحميلها ديناميكيًا من ملفات الترميز بطريقة مستقلة عن المنصة.

Tcl_ExternalToUtfDString convierte un buffer fuente `src` de la codificación especificada `encoding` en UTF-8. Los bytes convertidos se almacenan en `dstPtr`, que se termina con el carácter nulo especifico para la codificación. El llamador debe llamar a `Tcl_DStringFree` para liberar cualquier información almacenada en `dstPtr`. Cuando se convierte, si algún carácter en el buffer fuente no puede representarse en la codificación objetivo, se usa un carácter de reemplazo por defecto. El valor devuelto es un puntero al valor almacenado en el DString.

Tcl_ExternalToUtf convierte un buffer fuente `src` de la codificación especificada `encoding` en UTF-8. Se convierten hasta `srcLen` bytes del buffer fuente y se almacenan hasta `dstLen` bytes en `dst`. En todos los casos, `*srcReadPtr` se llena con el número de bytes que se convirtieron con éxito desde `src`, y `*dstWrotePtr` se llena con el número de bytes que se almacenaron en `dst`. El valor devuelto es uno de los siguientes:

TCL_OK
Todos los bytes de `src` se convirtieron.
TCL_CONVERT_NOSPACE
El buffer de destino no es suficiente para almacenar todos los datos convertidos; se convirtieron tantos caracteres como pudieron, aunque el espacio fuera insuficiente.
TCL_CONVERT_MULTIBYTE
Los últimos bytes del buffer fuente eran el inicio de una secuencia de múltiples bytes, pero se necesitaban más bytes para completar esta secuencia. Una llamada posterior a la rutina de conversión debe pasar un buffer que contenga los bytes no convertidos que quedan en `src` más algunos bytes adicionales de la fuente para convertir correctamente la secuencia que había sido dividida previamente.
TCL_CONVERT_SYNTAX
El buffer fuente contuvo una secuencia de caracteres inválida. Esto puede ocurrir si el flujo de entrada ha sido dañado o si el método de codificación de entrada fue mal identificado.
TCL_CONVERT_UNKNOWN
El buffer fuente contuvo un carácter que no se puede representar en la codificación objetivo y `TCL_ENCODING_STOPONERROR` fue especificado.

Tcl_CreateEncoding define una nueva codificación y registra los procedimientos C que se llaman cuando se convierte entre esta codificación y UTF-8. Las codificaciones creadas por `Tcl_CreateEncoding` son visibles en la base de datos usada por `Tcl_GetEncoding`. De manera similar a `Tcl_GetEncoding`, el valor devuelto es un token que representa la codificación y puede usarse en llamadas posteriores a otras funciones de codificación. `Tcl_CreateEncoding` devuelve una codificación con un contador de referencia de 1. Si una codificación con el nombre especificado ya existe, su registro en la base de datos se reemplaza con la nueva codificación; el token de la codificación antigua permanece válido y continúa a comportarse como antes, pero los usuarios del nuevo token ahora llamarán las procedimientos de codificación nuevas.

El argumento `typePtr` de `Tcl_CreateEncoding` contiene información sobre el nombre de la codificación y los procedimientos que se llaman cuando se convierte entre esta codificación y UTF-8. Se define como: 

typedef struct Tcl_EncodingType {
const char *encodingName;
Tcl_EncodingConvertProc *toUtfProc;
Tcl_EncodingConvertProc *fromUtfProc;
Tcl_EncodingFreeProc *freeProc;
ClientData clientData;
int nullSize;
} Tcl_EncodingType;

El `encodingName` proporciona un nombre para la codificación, mediante el cual se puede referir en otras procedimientos como `Tcl_GetEncoding`. El `toUtfProc` se refiere a un procedimiento de callback para convertir texto de esta codificación a UTF-8. El `fromUtfProc` se refiere a un procedimiento de callback para convertir texto de UTF-8 a esta codificación. El `freeProc` se refiere a un procedimiento de callback para invocar cuando se elimina esta codificación. El campo `freeProc` puede ser `NULL`. El `clientData` contiene un valor de una palabra arbitraria pasado a `toUtfProc`, `fromUtfProc` y `freeProc` cuando se les llama. Por lo general, este es un puntero a un estructura de datos que contiene información específica de codificación que puede usarse por los procedimientos de callback. Por ejemplo, dos codificaciones muy similares como `ascii` y `macRoman` pueden usar el mismo procedimiento de callback, pero usan valores diferentes de `clientData` para controlar su comportamiento. El `nullSize` especifica el número de bytes nulos que indican el fin de cadena en esta codificación. Debe ser `1` (para codificaciones de solo un byte o multi-byte como ASCII o Shift-JIS) o `2` (para codificaciones de dos bytes como Unicode). Las codificaciones constantes con 3 o más bytes por carácter (como CNS11643) no son aceptadas.

Los procedimientos de callback `toUtfProc` y `fromUtfProc` deben corresponder al tipo `Tcl_EncodingConvertProc:`

Los procedimientos de callback `toUtfProc` y `fromUtfProc` se llaman por `Tcl_ExternalToUtf` o `Tcl_UtfToExternal` para realizar la conversión real. El parámetro `clientData` de estos procedimientos es el mismo que el campo `clientData` especificado en `Tcl_CreateEncoding` cuando se creó la codificación. Los argumentos restantes de los procedimientos de callback son los mismos que los argumentos, documentados en el inicio, de `Tcl_ExternalToUtf` o `Tcl_UtfToExternal`, con las siguientes excepciones. Si el argumento `srcLen` de una de estas funciones de nivel alto es negativo, el valor pasado al procedimiento de callback será el largo adecuado de `src` para la codificación. Si algún de los argumentos `srcReadPtr`, `dstWrotePtr` o `dstCharsPtr` de una de estas funciones de nivel alto es `NULL`, el valor correspondiente pasado al procedimiento de callback será una ubicación no nula.

El procedimiento de callback `freeProc`, si no es `NULL`, debe corresponder al tipo `Tcl_EncodingFreeProc:` 

typedef void Tcl_EncodingFreeProc(
ClientData clientData);

Este `freeProc` se llama cuando se elimina la codificación. El parámetro `clientData` es el mismo que el campo `clientData` especificado en `Tcl_CreateEncoding` cuando se creó la codificación.

INTRODUCTION

Tcl supports a wide variety of character encodings. The primary goal of these routines is to provide a mechanism for Tcl to convert between Tcl's internal representation of strings (UTF-8) and external encodings. In addition, these routines provide a mechanism for managing the search path for dynamically loadable encoding files.

DESCRIPTION

The function Tcl_GetEncodingSearchPath returns a string containing the current encoding search path. This path is a list of filesystem directories that Tcl will search, in order, for dynamically loadable encoding files. The path is returned in Tcl's list format, with directory names separated by spaces or quotes. The caller is responsible for freeing the returned string using Tcl_Free. If the encoding search path has not been explicitly set, it defaults to a system-defined path.

The function Tcl_SetEncodingSearchPath sets the encoding search path to path. The path argument is a string containing a Tcl list of directory names. Tcl may perform some internal validation on the path, but it does not verify that the directories exist or are readable. The encoding search path is used by Tcl_GetEncoding when searching for dynamically loadable encoding files.

The directories in the search path are searched in order. As soon as an encoding file is found that matches the requested encoding name, it is loaded and used. No further directories in the search path are examined for that request.

Note that Tcl does not automatically canonicalize or normalize the directory names in the search path. It is the responsibility of the caller to ensure that the directory names are valid and correctly formatted. Any filesystem directories specified in path that are not verified as existing readable filesystem directories. When searching for encoding data files takes place, and non-existent or non-readable filesystem directories on the searchPath are silently ignored.

Tcl_GetDefaultEncodingDir and Tcl_SetDefaultEncodingDir are obsolete interfaces best replaced with calls to Tcl_GetEncodingSearchPath and Tcl_SetEncodingSearchPath. They are called to access and set the first element of the searchPath list. Since Tcl searches searchPath for encoding data files in list order, these routines establish the “default” directory in which to find encoding data files.

ENCODING FILES

Space would prohibit precompiling into Tcl every possible encoding algorithm, so many encodings are stored on disk as dynamically-loadable encoding files. This behavior also allows the user to create additional encoding files that can be loaded using the same mechanism. These encoding files contain information about the tables and/or escape sequences used to map between an external encoding and Unicode. The external encoding may consist of single-byte, multi-byte, or double-byte characters.

Each dynamically-loadable encoding is represented as a text file. The initial line of the file, beginning with a “#” symbol, is a comment that provides a human-readable description of the file. The next line identifies the type of encoding file. It can be one of the following letters:

[1] S
A single-byte encoding, where one character is always one byte long in the encoding. An example is iso8859-1, used by many European languages.
[2] D
A double-byte encoding, where one character is always two bytes long in the encoding. An example is big5, used for Chinese text.
[3] M
A multi-byte encoding, where one character may be either one or two bytes long. Certain bytes are lead bytes, indicating that another byte must follow and that together the two bytes represent one character. Other bytes are not lead bytes and represent themselves. An example is shiftjis, used by many Japanese computers.
[4] E
An escape-sequence encoding, specifying that certain sequences of bytes do not represent characters, but commands that describe how following bytes should be interpreted.

The rest of the lines in the file depend on the type.

The third line of the file is three numbers. The first number is the fallback character (in base 16) to use when converting from UTF-8 to this encoding. The second number is a 1 if this file represents the encoding for a symbol font, or 0 otherwise. The last number (in base 10) is how many pages of data follow.

Subsequent lines in the example above are pages that describe how to map from the encoding into 2-byte Unicode. The first line in a page identifies the page number. Following it are 256 double-byte numbers, arranged as 16 rows of 16 numbers. Given a character in the encoding, the high byte of that character is used to select which page, and the low byte of that character is used as an index to select one of the double-byte numbers in that page - the value obtained being the corresponding Unicode character. By examination of the example above, one can see that the characters 0x7E and 0x8163 in shiftjis map to 203E and 2026 in Unicode, respectively.

Following the first page will be all the other pages, each in the same format as the first: one number identifying the page followed by 256 double-byte Unicode characters. If a character in the encoding maps to the Unicode character 0000, it means that the character does not actually exist. If all characters on a page would map to 0000, that page can be omitted.

Case [4] is the escape-sequence encoding file. The lines in an this type of file are in the same format as this example taken from the iso2022-jp encoding:

# Encoding file: iso2022-jp, escape-driven
E
init		{}
final		{}
iso8859-1	\x1b(B
jis0201		\x1b(J
jis0208		\x1b$@
jis0208		\x1b$B
jis0212		\x1b$(D
gb2312		\x1b$A
ksc5601		\x1b$(C

In the file, the first column represents an option and the second column is the associated value. init is a string to emit or expect before the first character is converted, while final is a string to emit or expect after the last character. All other options are names of table-based encodings; the associated value is the escape-sequence that marks that encoding. Tcl syntax is used for the values; in the above example, for instance, “{}” represents the empty string and “\x1b” represents character 27.

When Tcl_GetEncoding encounters an encoding name that has not been loaded, it attempts to load an encoding file called name.enc from the encoding subdirectory of each directory that Tcl searches for its script library. If the encoding file exists, but is malformed, an error message will be left in interp.
