Tcl_FSNewNativePath performs something like the reverse of the usual obj->path->nativerep conversions. If some code retrieves a path in native form (from, e.g. readlink or a native dialog), and that path is to be used at the Tcl level, then calling this function is an efficient way of creating the appropriate path value type.

The resulting value is a pure “path” value, which will only receive a UTF-8 string representation if that is required by some Tcl code.

Tcl_FSGetNativePath is for use by the Win/Unix native filesystems, so that they can easily retrieve the native (char* or TCHAR*) representation of a path. This function is a convenience wrapper around Tcl_FSGetInternalRep. It may be desirable in the future to have non-string-based native representations (for example, on macOS, a representation using a fileSpec of FSRef structure would probably be more efficient). On Windows a full Unicode representation would allow for paths of unlimited length. Currently the representation is simply a character string which may contain either the relative path or a complete, absolute normalized path in the native encoding (complex conditions dictate which of these will be provided, so neither can be relied upon, unless the path is known to be absolute). If you need a native path which must be absolute, then you should ask for the native version of a normalized path. If for some reason a non-absolute, non-normalized version of the path is needed, that must be constructed separately (e.g. using Tcl_FSGetTranslatedPath).

The native representation is cached so that repeated calls to this function will not require additional conversions. The return value is owned by Tcl and has a lifetime equivalent to that of the pathPtr passed in (unless that is a relative path, in which case the native representation may be freed any time the cwd changes).

Tcl_FSFileSystemInfo returns a list of two elements. The first element is the name of the filesystem (e.g. “native”, “vfs”, “zip”, or “prowrap”, perhaps), and the second is the particular type of the given path within that filesystem (which is filesystem dependent). The second element may be empty if the filesystem does not provide a further categorization of files.

A valid list value is returned, unless the path value is not recognized, when NULL will be returned.

Tcl_FSGetFileSystemForPath returns a pointer to the Tcl_Filesystem which accepts this path as valid.

If no filesystem will accept the path, NULL is returned.

Tcl_FSGetPathType determines whether the given path is relative to the current directory, relative to the current volume, or absolute.

It returns one of TCL_PATH_ABSOLUTE, TCL_PATH_RELATIVE, or TCL_PATH_VOLUME_RELATIVE

THE VIRTUAL FILESYSTEM API

A filesystem provides a Tcl_Filesystem structure that contains pointers to functions that implement the various operations on a filesystem; these operations are invoked as needed by the generic layer, which generally occurs through the functions listed above.

The Tcl_Filesystem structures are manipulated using the following methods.

Tcl_FSRegister takes a pointer to a filesystem structure and an optional piece of data to associated with that filesystem. On calling this function, Tcl will attach the filesystem to the list of known filesystems, and it will become fully functional immediately. Tcl does not check if the same filesystem is registered multiple times (and in general that is not a good thing to do). TCL_OK will be returned.

Tcl_FSUnregister removes the given filesystem structure from the list of known filesystems, if it is known, and returns TCL_OK. If the filesystem is not currently registered, TCL_ERROR is returned.

Tcl_FSData will return the clientData associated with the given filesystem, if that filesystem is registered. Otherwise it will return NULL.

Tcl_FSMountsChanged is used to inform the Tcl's core that the set of mount points for the given (already registered) filesystem have changed, and that cached file representations may therefore no longer be correct.

    Tcl_FSDeleteFileProc *deleteFileProc;
    Tcl_FSCopyFileProc *copyFileProc;
    Tcl_FSRenameFileProc *renameFileProc;
    Tcl_FSCopyDirectoryProc *copyDirectoryProc;
    Tcl_FSLstatProc *lstatProc;
    Tcl_FSLoadFileProc *loadFileProc;
    Tcl_FSGetCwdProc *getCwdProc;
    Tcl_FSChdirProc *chdirProc;
} Tcl_Filesystem;

Except for the first three fields in this structure which contain simple data elements, all entries contain addresses of functions called by the generic filesystem layer to perform the complete range of filesystem related actions.

The many functions in this structure are broken down into three categories: infrastructure functions (almost all of which must be implemented), operational functions (which must be implemented if a complete filesystem is provided), and efficiency functions (which need only be implemented if they can be done so efficiently, or if they have side-effects which are required by the filesystem; Tcl has less efficient emulations it can fall back on). It is important to note that, in the current version of Tcl, most of these fallbacks are only used to handle commands initiated in Tcl, not in C. What this means is, that if a file rename command is issued in Tcl, and the relevant filesystem(s) do not implement their Tcl_FSRenameFileProc, Tcl's core will instead fallback on a combination of other filesystem functions (it will use Tcl_FSCopyFileProc followed by Tcl_FSDeleteFileProc, and if Tcl_FSCopyFileProc is not implemented there is a further fallback). However, if a Tcl_FSRenameFileProc command is issued at the C level, no such fallbacks occur. This is true except for the last four entries in the filesystem table (lstat, load, getcwd and chdir) for which fallbacks do in fact occur at the C level.

Any functions which take path names in Tcl_Obj form take those names in UTF-8 form. The filesystem infrastructure API is designed to support efficient, cached conversion of these UTF-8 paths to other native representations.

ENFILECHANNELPROC

وظيفة لمعالجة استدعاء Tcl_FSOpenFileChannel. يجب تنفيذها لأي نظام ملفات معقول، حيث أن أي عمليات تتطلب فتح أو الوصول إلى محتويات ملف ستستخدمها (مثل open، encoding، والعديد من أوامر Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

يفتح Tcl_FSOpenFileChannelProc ملفًا تم تحديده بواسطة pathPtr ويعيد مقبض قناة يمكن استخدامه لإجراء الإدخال والإخراج على الملف. تم تصميم واجهة برمجة التطبيقات هذه على غرار إجراء fopen لمكتبة الإدخال والإخراج القياسية في Unix. يشبه بناء ومعنى جميع الوسائط تلك المعطاة في أمر Tcl open عند فتح ملف، حيث يكون الوسيط mode مزيجًا من علامات POSIX O_RDONLY، O_WRONLY، إلخ. إذا حدث خطأ أثناء فتح القناة، يعيد Tcl_FSOpenFileChannelProc القيمة NULL ويسجل رمز خطأ POSIX يمكن استرداده باستخدام Tcl_GetErrno. بالإضافة إلى ذلك، إذا كان interp غير NULL، فإن Tcl_FSOpenFileChannelProc يترك رسالة خطأ في نتيجة interp بعد أي خطأ.

يجب ألا يتم تسجيل القناة التي تم إنشاؤها حديثًا في المفسر المقدم بواسطة Tcl_FSOpenFileChannelProc؛ هذه المهمة تقع على عاتق المتصل بـ Tcl_FSOpenFileChannel (إذا لزم الأمر). إذا تم إغلاق إحدى القنوات القياسية، stdin، stdout، أو stderr، سابقًا، فإن فعل إنشاء القناة الجديدة يعينها أيضًا كبديل للقناة القياسية.

MATCHINDIRECTORYPROC

وظيفة لمعالجة استدعاء Tcl_FSMatchInDirectory. إذا لم يتم تنفيذها، فستكون وظائف glob والنسخ المتكرر مفقودة في نظام الملفات (وقد يؤثر ذلك على أوامر مثل encoding names التي تستخدم وظائف glob داخليًا).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

يجب أن تعيد الوظيفة جميع الملفات أو الدلائل (أو كائنات نظام الملفات الأخرى) التي تتطابق مع النمط المحدد وتتوافق مع مواصفات types المقدمة. هناك طريقتان يمكن استدعاء هذه الوظيفة بهما. إذا كان pattern يساوي NULL، فإن pathPtr هو تحديد مسار كامل لملف أو دليل واحد يجب التحقق من وجوده ونوعه الصحيح. خلاف ذلك، pathPtr هو دليل، يجب أن تبحث الوظيفة في محتوياته عن ملفات أو دلائل ذات نوع صحيح. في كلتا الحالتين، يمكن افتراض أن pathPtr ليس NULL وغير فارغ. لم يتم توثيق ما إذا كان pathPtr سيحتوي على فاصل ملف في نهايته أم لا، لذلك يجب أن يكون الكود مرنًا لكلا الاحتمالين.

القيمة المرجعة هي نتيجة Tcl قياسية تشير إلى ما إذا كان قد حدث خطأ في عملية المطابقة. يتم وضع رسائل الخطأ في interp، ما لم يكن interp NULL، وفي هذه الحالة لا يلزم إنشاء رسالة خطأ؛ عند نتيجة TCL_OK، يجب إضافة النتائج إلى قيمة resultPtr المعطاة (والتي يمكن افتراض أنها قائمة Tcl صالحة غير مشتركة). يجب أن تتضمن المطابقات التي تمت إضافتها إلى resultPtr أي بادئة مسار معطاة في pathPtr (وهذا يعني عادةً أنها ستكون تحديدات مسارات مطلقة). لاحظ أنه إذا لم يتم العثور على أي مطابقات، فهذا يؤدي ببساطة إلى نتيجة فارغة؛ لا يتم الإبلاغ عن الأخطاء إلا للمشاكل الفعلية في الملف أو نظام الملفات التي قد تحدث أثناء عملية المطابقة.

تحتوي بنية Tcl_GlobTypeData التي يتم تمريرها في المعامل types على الحقول التالية:

typedef struct Tcl_GlobTypeData {
    /* يتوافق مع bcdpfls كما في 'find -t' */
    int type;
    /* يتوافق مع أذونات الملف */
    int perm;
    /* نوع Mac مقبول */
    Tcl_Obj *macType;
    /* منشئ Mac مقبول */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

هناك حالتان محددتان من المهم التعامل معهما بشكل صحيح، وكلاهما عندما يكون types غير NULL. الحالتان هما عندما يكون types->types & TCL_GLOB_TYPE_DIR أو types->types & TCL_GLOB_TYPE_MOUNT صحيحان (وخاصة عندما تكون الأعلام الأخرى خاطئة). في الحالة الأولى، يجب على الوظيفة سرد الدلائل المحتوية. يستخدم Tcl هذا لتنفيذ globing متكرر، لذلك من المهم أن تنفذ أنظمة الملفات مطابقة الدلائل بشكل صحيح. في الحالة الثانية، مع TCL_GLOB_TYPE_MOUNT، يجب على نظام الملفات سرد نقاط التحميل التي تقع ضمن pathPtr المعطى (وفي هذه الحالة، قد لا يقع pathPtr ضمن نفس نظام الملفات - يختلف عن جميع الحالات الأخرى التي يتم فيها استدعاء هذه الوظيفة). يعد دعم هذا الأمر حاسمًا إذا كان Tcl سيحتوي على انتقالات سلسة بين نظام ملفات وآخر.

UTIMEPROC

وظيفة لمعالجة استدعاء Tcl_FSUtime. مطلوبة للسماح بضبط (وليس قراءة) الأوقات باستخدام file mtime، file atime وتنفيذ open-r/open-w/fcopy لـ file copy.

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

يجب تغيير أوقات الوصول والتعديل للملف المحدد بواسطة pathPtr إلى القيم المعطاة في بنية tval.

يجب أن تكون القيمة المرجعة 0 عند النجاح و -1 عند حدوث خطأ، كما هو الحال مع utime في النظام.

LINKPROC

وظيفة لمعالجة استدعاء Tcl_FSLink. يجب تنفيذها فقط إذا كان نظام الملفات يدعم الروابط، وقد تكون NULL خلاف ذلك.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

إذا كان toPtr يساوي NULL، يتم سؤال الوظيفة عن قراءة محتويات رابط. النتيجة هي Tcl_Obj يحدد محتويات الرابط المعطى بواسطة linkNamePtr، أو NULL إذا تعذر قراءة الرابط. تكون النتيجة مملوكة للمتصل (وبالتالي يجب زيادة عداد المراجع الخاص بها قبل إعادتها). يجب على أي متصلين استدعاء Tcl_DecrRefCount لهذه النتيجة عند عدم الحاجة إليها. إذا كان toPtr غير NULL، يجب على الوظيفة محاولة إنشاء رابط. يجب أن تكون النتيجة في هذه الحالة هي toPtr إذا كان الرابط ناجحًا و NULL خلاف ذلك. في هذه الحالة، لا تكون النتيجة مملوكة للمتصل (أي لا يلزم إجراء أي تعديلات على عداد المراجع من أي من الطرفين). راجع وثائق Tcl_FSLink للتفسير الصحيح لعلامات linkAction.

LISTVOLUMESPROC

وظيفة لسرد أي وحدات تخزين لنظام الملفات تمت إضافتها بواسطة نظام الملفات هذا. يجب تنفيذها فقط إذا كان نظام الملفات يضيف وحدات تخزين في بداية نظام الملفات، بحيث يمكن إرجاعها بواسطة file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

يجب أن تكون النتيجة قائمة بوحدات التخزين التي أضافها نظام الملفات هذا، أو NULL (أو قائمة فارغة) إذا لم يتم توفير أي وحدات تخزين. تعتبر قيمة النتيجة مملوكة لنظام الملفات (وليس لنواة Tcl)، ولكن يجب إعطاؤها عداد مراجع لـ Tcl. سيستخدم Tcl محتويات القائمة ثم يقلل من عداد المراجع هذا. هذا يسمح لأنظمة الملفات بالاختيار ما إذا كانت تريد بالفعل الاحتفاظ بـ "قائمة عامة" لوحدات التخزين أم لا (إذا لم يكن الأمر كذلك، فإنها تنشئ القائمة أثناء التنقل وتمررها إلى Tcl مع عداد مراجع قدره 1 ثم تنسى القائمة، وإذا كان الأمر كذلك، فإنها ببساطة تزيد عداد المراجع لقائمتها العامة وتمررها إلى Tcl الذي سينسخ المحتويات ثم يقلل العداد مرة أخرى إلى ما كان عليه).

لذلك، يعتبر Tcl القيم المرجعة من هذه الوظيفة للقراءة فقط.

FILEATTRSTRINGSPROC

وظيفة لسرد جميع سلاسل السمات الصالحة لنظام الملفات هذا. إذا لم يتم تنفيذها، فلن يدعم نظام الملفات أمر file attributes. هذا يسمح بإرفاق معلومات إضافية تعسفية بالملفات في نظام الملفات. إذا لم يتم تنفيذها، فلا داعي لتنفيذ طرق get و set.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

يجوز للوظيفة المستدعاة إما إرجاع مصفوفة من السلاسل، أو قد تعيد بدلاً من ذلك NULL وتضع قائمة Tcl في objPtrRef المعطاة. سيأخذ Tcl هذه القائمة ويزيد عداد المراجع الخاص بها أولاً قبل استخدامها. عند الانتهاء من هذا الاستخدام، سيقوم Tcl بتقليل عداد المراجع. لذلك، إذا كان يجب على Tcl التخلص من القائمة عند الانتهاء، فيجب أن يكون عداد المراجع الخاص بها صفرًا، وإذا كان يجب عدم التخلص من القائمة، فيجب على نظام الملفات التأكد من أنه يعيد قيمة مع عداد مراجع لا يقل عن واحد.

FILEATTRSGETPROC

وظيفة لمعالجة استدعاء Tcl_FSFileAttrsGet، تستخدم بواسطة file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

تعيد رمز نتيجة Tcl قياسي. قيمة السمة المستردة، والتي تتوافق مع العنصر index في القائمة التي تم إرجاعها بواسطة Tcl_FSFileAttrStringsProc، هي Tcl_Obj يتم وضعه في objPtrRef (إذا تم إرجاع TCL_OK) ومن المحتمل أن يكون عداد المراجع الخاص بها صفرًا. في كلتا الحالتين، يجب علينا إما تخزينها في مكان ما (على سبيل المثال، نتيجة Tcl)، أو زيادة/تقليل عداد المراجع الخاص بها لضمان تحريرها بشكل صحيح.

FILEATTRSSETPROC

وظيفة لمعالجة استدعاء Tcl_FSFileAttrsSet، تستخدم بواسطة file attributes. إذا كان نظام الملفات للقراءة فقط، فلا حاجة لتنفيذ ذلك.

typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);

يجب تعيين قيمة السمة للعنصر index في القائمة التي تم إرجاعها بواسطة Tcl_FSFileAttrStringsProc إلى objPtr المعطى.
