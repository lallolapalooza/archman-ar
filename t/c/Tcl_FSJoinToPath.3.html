DESCRIPTION

There are several reasons for calling the Tcl_FS API functions (e.g. Tcl_FSAccess and Tcl_FSStat) rather than calling system level functions like access and stat directly. First, they will work cross-platform, so an extension which calls them should work unmodified on Unix and Windows. Second, the Windows implementation of some of these functions fixes some bugs in the system level calls. Third, these function calls deal with any “Utf to platform-native” path conversions which may be required (and may cache the results of such conversions for greater efficiency on subsequent calls). Fourth, and perhaps most importantly, all of these functions are “virtual filesystem aware”. Any virtual filesystem (VFS for short) which has been registered (through Tcl_FSRegister) may reroute file access to alternative media or access methods. This means that all of these functions (and therefore the corresponding file, glob, pwd, cd, open, etc. Tcl commands) may be operate on “files” which are not native files in the native filesystem. This also means that any Tcl extension which accesses the filesystem (FS for short) through this API is automatically “virtual filesystem aware”. Of course, if an extension accesses the native filesystem directly (through platform-specific APIs, for example), then Tcl cannot intercept such calls.

If appropriate VFSes have been registered, the “files” may, to give two examples, be remote (e.g. situated on a remote ftp server) or archived (e.g. lying inside a .zip archive). Such registered filesystems provide a lookup table of functions to implement all or some of the functionality listed here. Finally, the Tcl_FSStat and Tcl_FSLstat calls abstract away from what the “struct stat” buffer is actually declared to be, allowing the same code to be used both on systems with and systems without support for files larger than 2GB in size.

The Tcl_FS API is Tcl_Obj-ified and may cache internal representations and other path-related strings (e.g. the current working directory). One side-effect of this is that one must not pass in values with a reference count of zero to any of these functions. If such calls were handled, they might result in memory leaks (under some circumstances, the filesystem code may wish to retain a reference to the passed in value, and so one must not assume that after any of these calls return, the value still has a reference count of zero - it may have been incremented) or in a direct segmentation fault (or other memory access error) due to the value being freed part way through the complex value manipulation required to ensure that the path is fully normalized and absolute for filesystem determination. The practical lesson to learn from this is that

Tcl_Obj *path = Tcl_NewStringObj(...);
Tcl_FSWhatever(path);
Tcl_DecrRefCount(path);

is wrong, and may cause memory errors. The path must have its reference count incremented before passing it in, or decrementing it. For this reason, values with a reference count of zero are considered not to be valid filesystem paths and calling any Tcl_FS API function with such a value will result in no action being taken.

FS API FUNCTIONS

Tcl_FSCopyFile attempts to copy the file given by srcPathPtr to the path name given by destPathPtr. If the two paths given lie in the same filesystem (according to Tcl_FSGetFileSystemForPath) then that filesystem's “copy file” function is called (if it is non-NULL). Otherwise the function returns -1 and sets the errno global C variable to the “EXDEV” POSIX error code (which signifies a “cross-domain link”).

Tcl_FSCopyDirectory attempts to copy the directory given by srcPathPtr to the path name given by destPathPtr. If the two paths given lie in the same filesystem (according to Tcl_FSGetFileSystemForPath) then that filesystem's “copy file” function is called (if it is non-NULL). Otherwise the function returns -1 and sets the errno global C variable to the “EXDEV” POSIX error code (which signifies a “cross-domain link”).

Tcl_FSCreateDirectory attempts to create the directory given by pathPtr by calling the owning filesystem's “create directory” function.

Tcl_FSDeleteFile attempts to delete the file given by pathPtr by calling the owning filesystem's “delete file” function.

Tcl_FSRemoveDirectory attempts to remove the directory given by pathPtr by calling the owning filesystem's “remove directory” function.

Tcl_FSRenameFile attempts to rename the file or directory given by srcPathPtr to the path name given by destPathPtr. If the two paths given lie in the same filesystem (according to Tcl_FSGetFileSystemForPath) then that filesystem's “rename file” function is called (if it is non-NULL). Otherwise the function returns -1 and sets the errno global C variable to the “EXDEV” POSIX error code (which signifies a “cross-domain link”).

Tcl_FSListVolumes calls each filesystem which has a non-NULL “list volumes” function and asks them to return their list of root volumes. It accumulates the return values in a list which is returned to the caller (with a reference count of 0).

Tcl_FSEvalFileEx reads the file given by pathPtr using the encoding identified by encodingName and evaluates its contents as a Tcl script. It returns the same information as Tcl_EvalObjEx. If encodingName is NULL, the system encoding is used for reading the file contents. If the file could not be read then a Tcl error is returned to describe why the file could not be read. The eofchar for files is “\x1A” (^Z) for all platforms. If you require a “^Z” in code for string comparison, you can use “\x1A”, which will be safely substituted by the Tcl interpreter into “^Z”. Tcl_FSEvalFile is a simpler version of Tcl_FSEvalFileEx that always uses the system encoding when reading the file.

Tcl_FSLoadFile dynamically loads a binary code file into memory and returns the addresses of two procedures within that file, if they are defined. The appropriate function for the filesystem to which pathPtr belongs will be called. If that filesystem does not implement this function (most virtual filesystems will not, because of OS limitations in dynamically loading binary code), Tcl will attempt to copy the file to a temporary directory and load that temporary file. Tcl_FSUnloadFile reverses the operation, asking for the library indicated by the loadHandle to be removed from the process. Note that, unlike with the unload command, this does not give the library any opportunity to clean up.

Both the above functions return a standard Tcl completion code. If an error occurs, an error message is left in the interp's result.

The token provided via the variable indicated by loadHandlePtr may be used with Tcl_FindSymbol.

Tcl_FSMatchInDirectory is used by the globbing code to search a directory for all files which match a given pattern. The appropriate function for the filesystem to which pathPtr belongs will be called.

The return value is a standard Tcl result indicating whether an error occurred in globbing. Error messages are placed in interp (unless interp is NULL, which is allowed), but good results are placed in the resultPtr given.

Note that the glob code implements recursive patterns internally, so this function will only ever be passed simple patterns, which can be matched using the logic of string match. To handle recursion, Tcl will call this function frequently asking only for directories to be returned. A special case of being called with a NULL pattern indicates that the path needs to be checked only for the correct type.

Tcl_FSLink replaces the library version of readlink, and extends it to support the creation of links. The appropriate function for the filesystem to which linkNamePtr belongs will be called.

If the toPtr is NULL, a “read link” action is performed. The result is a Tcl_Obj specifying the contents of the symbolic link given by linkNamePtr, or NULL if the link could not be read. The result is owned by the caller, which should call Tcl_DecrRefCount when the result is no longer needed. If the toPtr is not NULL, Tcl should create a link of one of the types passed in in the linkAction flag. This flag is an OR'ed combination of TCL_CREATE_SYMBOLIC_LINK and TCL_CREATE_HARD_LINK. Where a choice exists (i.e. more than one flag is passed in), the Tcl convention is to prefer symbolic links. When a link is successfully created, the return value should be toPtr (which is therefore already owned by the caller). If unsuccessful, NULL is returned.

Tcl_FSLstat fills the Tcl_StatBuf structure statPtr with information about the specified file. You do not need any access rights to the file to get this information but you need search rights to all directories named in the path leading to the file. The Tcl_StatBuf structure includes info regarding device, inode (always 0 on Windows), privilege mode, nlink (always 1 on Windows), user id (always 0 on Windows), group id (always 0 on Windows), rdev (same as device on Windows), size, last access time, last modification time, and last status change time. On Unix systems, Tcl_StatBuf is a struct stat, possibly redefined to handle files larger than 2GB. On Windows, it is a WIN32_FILE_ATTRIBUTE_DATA structure, converted to a common format. Tcl_FSStat is identical to Tcl_FSLstat except that if the file is a symbolic link, Tcl_FSStat operates on the file the link points to, while Tcl_FSLstat operates on the link itself.

\nTcl_FSGetPathType determines whether the given path is\nrelative to the current directory, relative to the current volume, or\nabsolute.

\n

\nIt returns one of TCL_PATH_ABSOLUTE,\nTCL_PATH_RELATIVE, or TCL_PATH_VOLUME_RELATIVE

THE VIRTUAL FILESYSTEM API

\n

\nA filesystem provides a Tcl_Filesystem structure that\ncontains pointers to functions that implement the various operations on a\nfilesystem; these operations are invoked as needed by the generic layer, which\ngenerally occurs through the functions listed above.

\n

\nThe Tcl_Filesystem structures are manipulated using the\nfollowing methods.

\n

\nTcl_FSRegister takes a pointer to a filesystem structure\nand an optional piece of data to associated with that filesystem. On calling\nthis function, Tcl will attach the filesystem to the list of known\nfilesystems, and it will become fully functional immediately. Tcl does not\ncheck if the same filesystem is registered multiple times (and in general\nthat is not a good thing to do). TCL_OK will be returned.

\n

\nTcl_FSUnregister removes the given filesystem structure\nfrom the list of known filesystems, if it is known, and returns\nTCL_OK. If the filesystem is not currently registered,\nTCL_ERROR is returned.

\n

\nTcl_FSData will return the clientData associated with the\ngiven filesystem, if that filesystem is registered. Otherwise it will return\nNULL.

\n

\nTcl_FSMountsChanged is used to inform the Tcl's core that\nthe set of mount points for the given (already registered) filesystem have\nchanged, and that cached file representations may therefore no longer be\ncorrect.

\n
\n

THE TCL_FILESYSTEM STRUCTURE

\n

\nThe Tcl_Filesystem structure contains the following\nfields:

\n
\n
typedef struct Tcl_Filesystem {\n    const char *typeName;\n    int structureLength;\n    Tcl_FSVersion version;\n    Tcl_FSPathInFilesystemProc *pathInFilesystemProc;\n    Tcl_FSDupInternalRepProc *dupInternalRepProc;\n    Tcl_FSFreeInternalRepProc *freeInternalRepProc;\n    Tcl_FSInternalToNormalizedProc *internalToNormalizedProc;\n    Tcl_FSCreateInternalRepProc *createInternalRepProc;\n    Tcl_FSNormalizePathProc *normalizePathProc;\n    Tcl_FSFilesystemPathTypeProc *filesystemPathTypeProc;\n    Tcl_FSFilesystemSeparatorProc *filesystemSeparatorProc;\n    Tcl_FSStatProc *statProc;\n    Tcl_FSAccessProc *accessProc;\n    Tcl_FSOpenFileChannelProc *openFileChannelProc;\n    Tcl_FSMatchInDirectoryProc *matchInDirectoryProc;\n    Tcl_FSUtimeProc *utimeProc;\n    Tcl_FSLinkProc *linkProc;\n    Tcl_FSListVolumesProc *listVolumesProc;\n    Tcl_FSFileAttrStringsProc *fileAttrStringsProc;\n    Tcl_FSFileAttrsGetProc *fileAttrsGetProc;\n    Tcl_FSFileAttrsSetProc *fileAttrsSetProc;\n    Tcl_FSCreateDirectoryProc *createDirectoryProc;\n    Tcl_FSRemoveDirectoryProc *removeDirectoryProc;\n    Tcl_FSDeleteFileProc *deleteFileProc;\n    Tcl_FSCopyFileProc *copyFileProc;\n    Tcl_FSRenameFileProc *renameFileProc;\n    Tcl_FSCopyDirectoryProc *copyDirectoryProc;\n    Tcl_FSLstatProc *lstatProc;\n    Tcl_FSLoadFileProc *loadFileProc;\n    Tcl_FSGetCwdProc *getCwdProc;\n    Tcl_FSChdirProc *chdirProc;\n} Tcl_Filesystem;
\n
\n

\nExcept for the first three fields in this structure which contain\nsimple data elements, all entries contain addresses of functions called by\nthe generic filesystem layer to perform the complete range of filesystem\nrelated actions.

\n

\nThe many functions in this structure are broken down into three\ncategories: infrastructure functions (almost all of which must be\nimplemented), operational functions (which must be implemented if a complete\nfilesystem is provided), and efficiency functions (which need only be\nimplemented if they can be done so efficiently, or if they have side-effects\nwhich are required by the filesystem; Tcl has less efficient emulations it\ncan fall back on). It is important to note that, in the current version of\nTcl, most of these fallbacks are only used to handle commands initiated in\nTcl, not in C. What this means is, that if a file rename command is\nissued in Tcl, and the relevant filesystem(s) do not implement their\nTcl_FSRenameFileProc, Tcl's core will instead fallback on a\ncombination of other filesystem functions (it will use\nTcl_FSCopyFileProc followed by Tcl_FSDeleteFileProc, and if\nTcl_FSCopyFileProc is not implemented there is a further fallback).\nHowever, if a Tcl_FSRenameFileProc command is issued at the C level,\nno such fallbacks occur. This is true except for the last four entries in\nthe filesystem table (lstat, load, getcwd and\nchdir) for which fallbacks do in fact occur at the C level.

\n

\nAny functions which take path names in Tcl_Obj form take those\nnames in UTF-8 form. The filesystem infrastructure API is designed to\nsupport efficient, cached conversion of these UTF-8 paths to other native\nrepresentations.

\n
\n
\n

\n

بنية نظام الملفات

تحتوي هذه الحقول على معلومات أساسية حول بنية نظام الملفات وعناوين الوظائف المستخدمة لربط نظام ملفات معين بمسار ملف، وإدارة التمثيل الداخلي لمسارات الملفات، على سبيل المثال، نسخ هذه التمثيلات وتحريرها.

اسم النوع

يحتوي حقل typeName على سلسلة منتهية بـ NULL تحدد نوع نظام الملفات الذي تم تنفيذه، على سبيل المثال، native، zip أو vfs.

طول البنية

عادةً ما يتم تطبيق حقل structureLength كـ sizeof(Tcl_Filesystem)، وهو موجود للسماح بتوافق ثنائي أسهل إذا تغير حجم البنية في إصدار مستقبلي من Tcl.

الإصدار

يجب تعيين حقل version إلى TCL_FILESYSTEM_VERSION_1.

وظيفة المسار في نظام الملفات

يحتوي حقل pathInFilesystemProc على عنوان وظيفة يتم استدعاؤها لتحديد ما إذا كانت قيمة مسار معينة تنتمي إلى نظام الملفات هذا أم لا. ستستدعي Tcl فقط الوظائف المتبقية لنظام الملفات باستخدام مسار قد أعادت هذه الوظيفة له TCL_OK. إذا كان المسار لا ينتمي، فيجب إرجاع -1 (لم يتم تحديد سلوك Tcl لأي قيمة إرجاع أخرى). إذا تم إرجاع TCL_OK، فيمكن استخدام معلمة الإخراج الاختيارية clientDataPtr لإرجاع تمثيل داخلي (خاص بنظام الملفات) للمسار، والذي سيتم تخزينه مؤقتًا داخل قيمة المسار ويمكن استرداده بكفاءة بواسطة وظائف نظام الملفات الأخرى. ستقوم Tcl بتخزين ذاكرة مؤقتة بشكل متزامن بأن هذا المسار ينتمي إلى نظام الملفات الحالي. يتم إبطال هذه التخزينات المؤقتة عند إضافة هياكل نظام الملفات أو إزالتها من القائمة الداخلية لأنظمة الملفات المعروفة لـ Tcl.

typedef int Tcl_FSPathInFilesystemProc(
        Tcl_Obj *pathPtr,
        ClientData *clientDataPtr);

وظيفة نسخ التمثيل الداخلي

تقوم هذه الوظيفة بنسخ تمثيل داخلي للمسار ويتم استدعاؤها عندما تحتاج Tcl إلى تكرار قيمة مسار. إذا كانت NULL، فلن تقوم Tcl ببساطة بنسخ التمثيل الداخلي، والذي قد يلزم بعد ذلك إعادة إنشائه لاحقًا.

typedef ClientData Tcl_FSDupInternalRepProc(
        ClientData clientData);

وظيفة تحرير التمثيل الداخلي

تحرر التمثيل الداخلي. يجب تنفيذها إذا كان التمثيل الداخلي يحتاج إلى تحرير (أي إذا تم تخصيص ذاكرة عند إنشاء تمثيل داخلي)، ولكن يمكن أن تكون NULL بخلاف ذلك.

typedef void Tcl_FSFreeInternalRepProc(
        ClientData clientData);

وظيفة التمثيل الداخلي إلى الطبيعي

وظيفة لتحويل تمثيل داخلي إلى مسار طبيعي. مطلوبة فقط إذا كان نظام الملفات يقوم بإنشاء قيم مسار نقية بدون تمثيل سلسلة / بوابة ملف. القيمة المرجعة هي كائن Tcl يكون تمثيلها كسلسلة هو المسار الطبيعي.

typedef Tcl_Obj *Tcl_FSInternalToNormalizedProc(
        ClientData clientData);

وظيفة إنشاء التمثيل الداخلي

وظيفة تأخذ قيمة مسار وتحسب تمثيلًا داخليًا لها وتخزنه في القيمة. يمكن أن تكون NULL إذا لم يكن للمسارات تمثيل داخلي، أو إذا كانت Tcl_FSPathInFilesystemProc لنظام الملفات تنشئ دائمًا تمثيلًا داخليًا فورًا للمسارات التي تقبلها.

typedef ClientData Tcl_FSCreateInternalRepProc(
        Tcl_Obj *pathPtr);

وظيفة تطبيع المسار

وظيفة لتطبيع المسار. يجب تنفيذها لجميع أنظمة الملفات التي قد يكون لديها تمثيلات سلسلة متعددة لنفس قيمة المسار. في Tcl، يجب أن يكون لكل "مسار" تمثيل "طبيعي" فريد. اعتمادًا على نظام الملفات، قد يكون هناك أكثر من تمثيل سلسلة غير طبيعي يشير إلى نفس المسار (على سبيل المثال، مسار نسبي، مسار بأحرف كبيرة / صغيرة مختلفة إذا كان نظام الملفات غير حساس لحالة الأحرف، مسار يحتوي على إشارة إلى مجلد المنزل مثل ~، مسار يحتوي على روابط رمزية، وما إلى ذلك). إذا كان المكون الأخير من المسار رابطًا رمزيًا، فيجب عدم تحويله إلى القيمة التي يشير إليها (ولكن يجب أن تكون حالته أو جوانبه الأخرى فريدة). يجب تحويل جميع المكونات الأخرى للمسار من الروابط الرمزية. هذا الاستثناء ضروري لمطابقة رموز Tcl لسلوك file delete، file rename، file copy مع الروابط الرمزية. قد يتم استدعاء هذه الوظيفة مع nextCheckpoint في بداية المسار (أي صفر)، في نهاية المسار، أو في أي فاصل ملف وسيط في المسار. لن تشير أبدًا إلى أي موضع عشوائي آخر في المسار. في الحالة الأخيرة من الحالات الثلاث الصالحة، يمكن للتنفيذ افتراض أن المسار حتى بما في ذلك فاصل الملف معروف وطبيعي.

typedef int Tcl_FSNormalizePathProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int nextCheckpoint);

عمليات نظام الملفات

تحتوي حقول هذا القسم من البنية على عناوين الوظائف التي يتم استدعاؤها لتنفيذ عمليات نظام الملفات الأساسية. يجب على نظام الملفات الذي يتوقع استخدامه مع المجموعة الكاملة من الأوامر القياسية لـ Tcl تنفيذ جميع هذه الوظائف. إذا لم يتم تنفيذ بعضها، فقد تفشل بعض أوامر Tcl في العمل على المسارات داخل نظام الملفات هذا. ومع ذلك، قد يكون هذا مرغوبًا فيه في بعض الحالات (على سبيل المثال، لا ينبغي لنظام ملفات للقراءة فقط تنفيذ الوظائف الأربع الأخيرة، ولا ينبغي لنظام ملفات لا يدعم الروابط الرمزية تنفيذ وظيفة readlink، وما إلى ذلك). تتوقع Tcl core من أنظمة الملفات التصرف بهذه الطريقة.

وظيفة نوع مسار نظام الملفات

وظيفة لتحديد نوع المسار في نظام الملفات هذا. يمكن أن تكون NULL، وفي هذه الحالة لن يتم عرض معلومات النوع لمستخدمي نظام الملفات. يتم استخدام type فقط للمعلومات، ويجب إرجاعه كتمثيل سلسلة لكائن Tcl الذي تم إرجاعه. قد يكون القيمة النموذجية networked، zip أو ftp. كائن Tcl الناتج مملوك لنظام الملفات وبالتالي ستزيد Tcl عداد المراجع لهذه القيمة إذا أرادت الاحتفاظ بمرجع لها.

typedef Tcl_Obj *Tcl_FSFilesystemPathTypeProc(
        Tcl_Obj *pathPtr);

وظيفة فاصل نظام الملفات

وظيفة لإرجاع حرف الفاصل لنظام الملفات هذا. هذا التنفيذ مطلوب فقط إذا كان نظام الملفات يريد استخدام فاصل مختلف عن الفاصل القياسي /. من بين استخدامات أخرى، يتم إرجاعه بواسطة أمر file separator. يجب أن يكون للقيمة المرجعة عداد مراجع يساوي صفرًا.

typedef Tcl_Obj *Tcl_FSFilesystemSeparatorProc(
        Tcl_Obj *pathPtr);

وظيفة STAT

وظيفة لمعالجة استدعاء Tcl_FSStat. يجب تنفيذها لأي نظام ملفات معقول، حيث تعتمد العديد من الأوامر على مستوى Tcl عليها بشكل حاسم (على سبيل المثال، file atime، file isdirectory، file size، glob).

typedef int Tcl_FSStatProc(
        Tcl_Obj *pathPtr,
        Tcl_StatBuf *statPtr);

تقوم وظيفة Tcl_FSStatProc بملء بنية الإحصائيات statPtr بمعلومات حول الملف المحدد. لا تحتاج إلى حقوق وصول إلى الملف للحصول على هذه المعلومات، ولكنك تحتاج إلى حقوق بحث لجميع الدلائل المسماة في المسار الذي يؤدي إلى الملف. تتضمن بنية الإحصائيات معلومات حول الجهاز، والـ inode (0 في Windows)، ووضع الامتيازات، وعدد الروابط (1 في Windows)، و UID (0 في Windows)، و GID (0 في Windows)، و rdev (نفس الجهاز في Windows)، والحجم، وتاريخ آخر وصول، وتاريخ آخر تعديل، وتاريخ آخر تغيير في البيانات الوصفية.

إذا كان الملف الذي تمثله pathPtr موجودًا، فإن Tcl_FSStatProc تعيد 0 ويتم ملء بنية الإحصائيات بالبيانات. خلاف ذلك، يتم إرجاع -1 ولا يتم تقديم أي بيانات إحصائية.

وظيفة الوصول

وظيفة لمعالجة استدعاء Tcl_FSAccess. يجب تنفيذها لأي نظام ملفات معقول، حيث تعتمد العديد من الأوامر على مستوى Tcl عليها بشكل حاسم (على سبيل المثال، file exists، file readable).

typedef int Tcl_FSAccessProc(
        Tcl_Obj *pathPtr,
        int mode);

تتحقق وظيفة Tcl_FSAccessProc مما إذا كان سيُسمح للعملية بالقراءة أو الكتابة أو اختبار وجود الملف (أو كائن نظام ملفات آخر) الذي اسمه موجود في pathPtr. إذا كان المسار يشير إلى رابط رمزي، فيجب اختبار أذونات الملف الذي يشير إليه هذا الرابط الرمزي.

في حالة النجاح (تم منح جميع الأذونات المطلوبة)، يتم إرجاع 0. في حالة حدوث خطأ (يشير بت واحد على الأقل في الوضع المطلوب إلى رفض الإذن، أو حدث خطأ آخر)، يتم إرجاع -1.

وظيفة فتح قناة ملف

OPENFILECHANNELPROC

دالة لمعالجة استدعاء Tcl_FSOpenFileChannel. يجب تنفيذها لأي نظام ملفات منطقي، حيث أن أي عملية تتطلب فتح أو الوصول إلى محتوى ملف ستستخدم هذه الدالة (مثل open و encoding والعديد من أوامر Tk).

typedef Tcl_Channel Tcl_FSOpenFileChannelProc(
        Tcl_Interp *interp,
        Tcl_Obj *pathPtr,
        int mode,
        int permissions);

تقوم Tcl_FSOpenFileChannelProc بفتح ملف محدد بواسطة pathPtr وإرجاع مقبض قناة يمكن استخدامه لإجراء إدخال وإخراج على الملف. تم تصميم واجهة برمجة التطبيقات هذه على غرار دالة fopen القياسية لمكتبة الإدخال/الإخراج في Unix. بناء الجملة ومعنى جميع الوسائط مشابهان لتلك المقدمة في أمر Tcl open عند فتح ملف، حيث يكون الوسيط mode مزيجًا من علامات POSIX O_RDONLY و O_WRONLY وما إلى ذلك. إذا حدث خطأ أثناء فتح القناة، فإن Tcl_FSOpenFileChannelProc ترجع NULL وتسجل رمز خطأ POSIX يمكن استعادته باستخدام Tcl_GetErrno. بالإضافة إلى ذلك، إذا لم يكن interp NULL، فإن Tcl_FSOpenFileChannelProc تترك رسالة خطأ في نتيجة interp بعد أي خطأ.

يجب تسجيل القناة الجديدة في المفسر الذي قدمته Tcl_FSOpenFileChannelProc؛ وهذا العمل يقع على عاتق المتصل بـ Tcl_FSOpenFileChannel (إذا لزم الأمر). إذا تم إغلاق إحدى القنوات القياسية، stdin أو stdout أو stderr، في السابق، فإن إجراء إنشاء القناة الجديدة يعينها أيضًا كبديل للقناة القياسية.

MATCHINDIRECTORYPROC

دالة لمعالجة استدعاء Tcl_FSMatchInDirectory. إذا لم يتم تنفيذها، فستكون وظائف النسخ المتكرر والنشر (globbing) مفقودة في نظام الملفات (وقد يؤثر هذا على أوامر مثل encoding names التي تستخدم وظائف النشر).

typedef int Tcl_FSMatchInDirectoryProc(
        Tcl_Interp *interp,
        Tcl_Obj *resultPtr,
        Tcl_Obj *pathPtr,
        const char *pattern,
        Tcl_GlobTypeData *types);

يجب أن ترجع الدالة جميع الملفات أو الدلائل (أو كائنات نظام الملفات الأخرى) التي تتطابق مع النمط المحدد وتفي بمواصفات types. هناك طريقتان يمكن استدعاء هذه الدالة بهما. إذا كان pattern NULL، فإن pathPtr هو مواصفات كاملة لملف واحد أو دليل واحد يجب التحقق من وجوده ونوعه. بخلاف ذلك، فإن pathPtr هو دليل، ويجب على الدالة البحث عن ملفات أو دلائل من النوع الصحيح. في أي حال، يمكن افتراض أن pathPtr ليس NULL وليس فارغًا. لا تزال الوثائق غير واضحة حول ما إذا كان pathPtr سيحتوي على فاصل ملف في نهاية اسمه، لذلك يجب أن يكون الكود مرنًا لكلا الحالتين المحتملتين.

القيمة المرجعة هي نتيجة Tcl قياسية تشير إلى ما إذا كان قد حدث خطأ أثناء عملية المطابقة. يتم وضع رسائل الخطأ في interp، ما لم يكن interp NULL، وفي هذه الحالة لا يجب إنشاء رسالة خطأ؛ في حالة نتيجة TCL_OK، يجب إضافة النتائج إلى قيمة resultPtr المقدمة (والتي يمكن افتراض أنها قائمة Tcl صالحة وغير مشتركة). يجب أن تتضمن التطابقات المضافة إلى resultPtr أي بادئة مسار معطاة في pathPtr (مما يعني عادةً أنها ستكون مواصفات مسار مطلقة). ملاحظة: إذا لم يتم العثور على أي تطابقات، فستحصل على نتيجة فارغة فقط؛ تم الإشارة إلى خطأ فقط للمشاكل الفعلية في الملفات أو نظام الملفات التي قد تحدث أثناء عملية المطابقة.

يحتوي الهيكل Tcl_GlobTypeData المقدم في الوسيط types على الحقول التالية:

typedef struct Tcl_GlobTypeData {
    /* يتوافق مع bcdpfls كما في 'find -t' */
    int type;
    /* يتوافق مع أذونات الملف */
    int perm;
    /* نوع Mac مقبول */
    Tcl_Obj *macType;
    /* منشئ Mac مقبول */
    Tcl_Obj *macCreator;
} Tcl_GlobTypeData;

هناك حالتان خاصتان مهمتان يجب معالجتهما بشكل صحيح، كلاهما عندما يكون types ليس NULL. الحالتان هما عندما يكون types->types هو & TCL_GLOB_TYPE_DIR أو types->types & TCL_GLOB_TYPE_MOUNT صحيحًا (وبشكل خاص عندما تكون العلامات الأخرى خاطئة). في الحالة الأولى، يجب على الدالة سرد الدلائل الداخلية. تستخدم Tcl هذا لتنفيذ النشر المتكرر، لذلك من الأهمية بمكان أن تنفذ أنظمة الملفات مطابقة الدلائل بشكل صحيح. في الحالة الثانية، مع TCL_GLOB_TYPE_MOUNT، يجب على نظام الملفات سرد نقاط التحميل الموجودة داخل pathPtr المحدد (وفي هذه الحالة، لا يلزم بالضرورة أن يكون pathPtr داخل نفس نظام الملفات - على عكس جميع الحالات الأخرى التي يتم فيها استدعاء هذه الدالة). دعم هذا أمر بالغ الأهمية إذا كانت Tcl ترغب في الانتقالات السلسة بين أنظمة الملفات.

UTIMEPROC

دالة لمعالجة استدعاء Tcl_FSUtime. مطلوب للسماح بتحديث (وليس قراءة) الأوقات باستخدام file mtime و file atime وتنفيذ file copy من open-r/open-w/fcopy.

typedef int Tcl_FSUtimeProc(
        Tcl_Obj *pathPtr,
        struct utimbuf *tval);

يجب تغيير أوقات الوصول والتعديل للملف المحدد بواسطة pathPtr إلى القيم المعطاة في الهيكل tval.

يجب أن تكون القيمة المرجعة 0 في حالة النجاح و -1 في حالة الخطأ، كما هو الحال مع نظام utime.

LINKPROC

دالة لمعالجة استدعاء Tcl_FSLink. يجب تنفيذها فقط إذا كان نظام الملفات يدعم الروابط، ويمكن أن تكون NULL في حالات أخرى.

typedef Tcl_Obj *Tcl_FSLinkProc(
        Tcl_Obj *linkNamePtr,
        Tcl_Obj *toPtr,
        int linkAction);

إذا كان toPtr NULL، فسيتم طلب الدالة لقراءة محتوى رابط. النتيجة هي Tcl_Obj يحدد محتوى الرابط المقدم بواسطة linkNamePtr، أو NULL إذا لم يكن بالإمكان قراءة الرابط. المتصل هو المسؤول عن النتيجة (وبالتالي، يجب زيادة عداد مرجعه قبل إرجاعها). يجب على أي متصل استدعاء Tcl_DecrRefCount على هذه النتيجة عندما لم يعد بحاجة إليها. إذا كان toPtr ليس NULL، فيجب على الدالة محاولة إنشاء رابط. في هذه الحالة، يجب أن تكون النتيجة toPtr إذا نجح الرابط و NULL إذا فشل. في هذه الحالة، المتصل ليس مسؤولاً عن النتيجة (أي، لا توجد معالجات لعداد المرجع على كلا الجانبين). راجع وثائق Tcl_FSLink لتفسير علامات linkAction بشكل صحيح.

LISTVOLUMESPROC

دالة لسرد أي وحدات نظام الملفات تم إضافتها بواسطة نظام الملفات هذا. يجب تنفيذها فقط إذا كان نظام الملفات يضيف وحدات في بداية نظام الملفات، مما يسمح بإرجاعها بواسطة file volumes.

typedef Tcl_Obj *Tcl_FSListVolumesProc(void);

FILEATTRSTRINGSPROC

دالة لسرد جميع سلاسل السمات الصالحة لنظام الملفات هذا. إذا لم يتم تنفيذها، فلن يدعم نظام الملفات الأمر file attributes. يسمح هذا بمعلومات إضافية عشوائية للملفات في نظام الملفات. إذا لم يتم تنفيذها، فلا حاجة لتنفيذ طرق get و set.

typedef const char *const *Tcl_FSFileAttrStringsProc(
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

يمكن للدالة المسماة إرجاع مصفوفة من السلاسل، أو يمكنها إرجاع NULL ووضع قائمة Tcl في objPtrRef المعطى. ستأخذ Tcl هذه القائمة وتزيد عداد مرجعها أولاً قبل استخدامها. عند الانتهاء من استخدامها، ستقلل Tcl عداد المرجع. لذلك، إذا كان يجب تدمير القائمة بواسطة Tcl عند الانتهاء، فيجب أن يكون لها عداد مرجع صفر، وإذا كان لا يجب تدميرها، فيجب على نظام الملفات ضمان إرجاع قيمة بعداد مرجع لا يقل عن واحد.

FILEATTRSGETPROC

دالة لمعالجة استدعاء Tcl_FSFileAttrsGet، المستخدمة بواسطة file attributes.

typedef int Tcl_FSFileAttrsGetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj **objPtrRef);

ترجع رمز إرجاع Tcl قياسي. يتم وضع قيمة السمة التي تم الحصول عليها، والتي تتوافق مع العنصر ذي الفهرس index في القائمة التي تم إرجاعها بواسطة Tcl_FSFileAttrStringsProc، في objPtrRef (إذا تم إرجاع TCL_OK)، ومن المحتمل أن يكون لها عداد مرجع صفر. على الرغم من ذلك، يجب علينا تخزينها في مكان ما (على سبيل المثال، في نتيجة Tcl)، أو زيادة/إنقاص عداد مرجعها لضمان تحريرها بشكل صحيح.

FILEATTRSSETPROC

دالة لمعالجة استدعاء Tcl_FSFileAttrsSet، المستخدمة بواسطة file attributes. إذا كان نظام الملفات للقراءة فقط، فلا حاجة لتنفيذ هذا.

typedef int Tcl_FSFileAttrsSetProc(
        Tcl_Interp *interp,
        int index,
        Tcl_Obj *pathPtr,
        Tcl_Obj *objPtr);

يجب تعيين قيمة السمة للعنصر ذي الفهرس index في القائمة التي تم إرجاعها بواسطة Tcl_FSFileAttrStringsProc إلى objPtr المقدم.
