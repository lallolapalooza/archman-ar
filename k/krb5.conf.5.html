KRB5.CONF(5) MIT Kerberos KRB5.CONF(5)

NAME

krb5.conf - Kerberos configuration file

The krb5.conf file contains Kerberos configuration information, including the locations of KDCs and admin servers for the Kerberos realms of interest, defaults for the current realm and for Kerberos applications, and mappings of hostnames onto Kerberos realms. Normally, you should install your krb5.conf file in the directory /etc. You can override the default location by setting the environment variable KRB5_CONFIG. Multiple colon-separated filenames may be specified in KRB5_CONFIG; all files which are present will be read. Starting in release 1.14, directory names can also be specified in KRB5_CONFIG; all files within the directory whose names consist solely of alphanumeric characters, dashes, or underscores will be read.

STRUCTURE

The krb5.conf file is set up in the style of a Windows INI file. Lines beginning with '#' or ';' (possibly after initial whitespace) are ignored as comments. Sections are headed by the section name, in square brackets. Each section may contain zero or more relations, of the form:

foo = bar

or:

fubar = {
    foo = bar
    baz = quux
}

Placing a '*' after the closing bracket of a section name indicates that the section is final, meaning that if the same section appears within a later file specified in KRB5_CONFIG, it will be ignored. A subsection can be marked as final by placing a '*' after either the tag name or the closing brace.

The krb5.conf file can include other files using either of the following directives at the beginning of a line:

include FILENAME
includedir DIRNAME

FILENAME or DIRNAME should be an absolute path. The named file or directory must exist and be readable. Including a directory includes all files within the directory whose names consist solely of alphanumeric characters, dashes, or underscores. Starting in release 1.15, files with names ending in ".conf" are also included, unless the name begins with ".". Included profile files are syntactically independent of their parents, so each included file must begin with a section header. Starting in release 1.17, files are read in alphanumeric order; in previous releases, they may be read in any order.

The krb5.conf file can specify that configuration should be obtained from a loadable module, rather than the file itself, using the following directive at the beginning of a line before any section headers:

module MODULEPATH:RESIDUAL

MODULEPATH may be relative to the library path of the krb5 installation, or it may be an absolute path. RESIDUAL is provided to the module at initialization time. If krb5.conf uses a module directive, kdc.conf(5) should also use one if it exists.

SECTIONS

The krb5.conf file may contain the following sections:

[libdefaults] Settings used by the Kerberos V5 library
[realms] Realm-specific contact information and settings
[domain_realm] Maps server hostnames to Kerberos realms
[capaths] Authentication paths for non-hierarchical cross-realm
[appdefaults] Settings used by some Kerberos V5 applications
[plugins] Controls plugin module registration

Additionally, krb5.conf may include any of the relations described in kdc.conf(5), but it is not a recommended practice.

[libdefaults]

The libdefaults section may contain any of the following relations:

allow_des3
Permit the KDC to issue tickets with des3-cbc-sha1 session keys. In future releases, this flag will allow des3-cbc-sha1 to be used at all. The default value for this tag is false. (Added in release 1.21.)
allow_rc4
Permit the KDC to issue tickets with arcfour-hmac session keys. In future releases, this flag will allow arcfour-hmac to be used at all. The default value for this tag is false. (Added in release 1.21.)
allow_weak_crypto
If this flag is set to false, then weak encryption types (as noted in Encryption_types in kdc.conf(5)) will be filtered out of the lists default_tgs_enctypes, default_tkt_enctypes, and permitted_enctypes. The default value for this tag is false.
canonicalize
If this flag is set to true, initial ticket requests to the KDC will request canonicalization of the client principal name, and answers with different client principals than the requested principal will be accepted. The default value is false.
ccache_type
This parameter determines the format of credential cache types created by kinit(1) or other programs. The default value is 4, which represents the most current format. Smaller values can be used for compatibility with very old implementations of Kerberos which interact with credential caches on the same host.
clockskew
Sets the maximum allowable amount of clockskew in seconds that the library will tolerate before assuming that a Kerberos message is invalid. The default value is 300 seconds, or five minutes.

The clockskew setting is also used when evaluating ticket start and expiration times. For example, tickets that have reached their expiration time can still be used (and renewed if they are renewable tickets) if they have been expired for a shorter duration than the clockskew setting.

default_ccache_name
This relation specifies the name of the default credential cache. The default is FILE:/tmp/krb5cc_%{uid}. This relation is subject to parameter expansion (see below). New in release 1.11.
default_client_keytab_name
This relation specifies the name of the default keytab for obtaining client credentials. The default is FILE:/var/lib/krb5/user/%{euid}/client.keytab. This relation is subject to parameter expansion (see below). New in release 1.11.
default_keytab_name
This relation specifies the default keytab name to be used by application servers such as sshd. The default is FILE:/etc/krb5.keytab. This relation is subject to parameter expansion (see below).
default_rcache_name
This relation specifies the name of the default replay cache. The default is dfl:. This relation is subject to parameter expansion (see below). New in release 1.18.
default_realm
Identifies the default Kerberos realm for the client. Set its value to your Kerberos realm. If this value is not set, then a realm must be specified with every Kerberos principal when invoking programs such as kinit(1).

واجهة hostrealm

يتحكم قسم hostrealm (المقدم في الإصدار 1.12) في الوحدات النمطية لواجهة المضيف إلى النطاق، والتي تؤثر على التعيين المحلي لأسماء المضيفين إلى أسماء النطاقات واختيار النطاق الافتراضي. الوحدات النمطية المضمنة التالية موجودة لهذه الواجهة:

profile
تستشير هذه الوحدة قسم [domain_realm] في الملف الشخصي لتعيينات المضيف إلى النطاق الموثوق بها، ومتغير default_realm للنطاق الافتراضي.
dns
تبحث هذه الوحدة عن سجلات DNS لتعيينات المضيف إلى النطاق الاحتياطية والنطاق الافتراضي. تعمل فقط إذا تم تعيين المتغير dns_lookup_realm إلى true.
domain
تطبق هذه الوحدة أساليب استدلال لتعيينات المضيف إلى النطاق الاحتياطية. وهي تنفذ المتغير realm_try_domains، وتستخدم النطاق الأصلي بالحروف الكبيرة لاسم المضيف إذا لم يؤد ذلك إلى نتيجة.

واجهة localauth

يتحكم قسم localauth (المقدم في الإصدار 1.12) في الوحدات النمطية لواجهة التفويض المحلي، والتي تؤثر على العلاقة بين أصول Kerberos وحسابات النظام المحلية. الوحدات النمطية المضمنة التالية موجودة لهذه الواجهة:

default
تنفذ هذه الوحدة نوع DEFAULT لقيم auth_to_local.
rule
تنفذ هذه الوحدة نوع RULE لقيم auth_to_local.
names
تبحث هذه الوحدة عن تعيين auth_to_local_names لاسم الأصل.
auth_to_local
تعالج هذه الوحدة قيم auth_to_local في قسم النطاق الافتراضي، وتطبق الطريقة الافتراضية إذا لم توجد قيم auth_to_local.
k5login
تفوض هذه الوحدة أصلًا إلى حساب محلي وفقًا للملف .k5login(5) الخاص بالحساب.
an2ln
تفوض هذه الوحدة أصلًا إلى حساب محلي إذا كان اسم الأصل يتطابق مع اسم الحساب المحلي.

واجهة certauth

يتحكم قسم certauth (المقدم في الإصدار 1.16) في الوحدات النمطية لواجهة التفويض بالشهادة، والتي تحدد ما إذا كان مسموحًا للشهادة بالتحقق المسبق من المستخدم عبر PKINIT. الوحدات النمطية المضمنة التالية موجودة لهذه الواجهة:

pkinit_san
تفوض هذه الوحدة الشهادة إذا كانت تحتوي على اسم بديل للموضوع (Subject Alternative Name) PKINIT للأصل العميل المطلوب، أو اسم UPN SAN مطابق للأصل إذا تم تعيين pkinit_allow_upn إلى true للنطاق.
pkinit_eku
ترفض هذه الوحدة الشهادة إذا كانت لا تحتوي على سمة استخدام مفتاح ممتد (Extended Key Usage) متوافقة مع قيمة pkinit_eku_checking للنطاق.
dbmatch
تفوض هذه الوحدة أو ترفض الشهادة وفقًا لما إذا كانت تتطابق مع سمة النص pkinit_cert_match على الأصل العميل، إذا كانت هذه السمة موجودة.

خيارات PKINIT

ملاحظة:

الخيارات التالية خاصة بـ PKINIT. يمكن تحديد هذه القيم في [libdefaults] كقيم افتراضية عامة، أو ضمن قسم خاص بالنطاق في [libdefaults]، أو يمكن تحديدها كقيم خاصة بالنطاق في قسم [realms]. القيمة الخاصة بالنطاق تلغي، ولا تضيف إلى، مواصفات [libdefaults] العامة. ترتيب البحث هو:
1.
قسم خاص بالنطاق في [libdefaults]:
[libdefaults]
    EXAMPLE.COM = {
        pkinit_anchors = FILE:/usr/local/example.com.crt
    }
2.
قيمة خاصة بالنطاق في قسم [realms]:
[realms]
    OTHERREALM.ORG = {
        pkinit_anchors = FILE:/usr/local/otherrealm.org.crt
    }
3.
قيمة عامة في قسم [libdefaults]:
[libdefaults]
    pkinit_anchors = DIR:/usr/local/generic_trusted_cas/

تحديد معلومات هوية PKINIT

تركيب تحديد معلومات هوية المفتاح العام والثقة وإبطال الشهادات لـ PKINIT هو كالتالي:

FILE:filename[,keyfilename]
لهذا الخيار سلوك يعتمد على السياق.

في pkinit_identity أو pkinit_identities، يحدد filename اسم ملف بتنسيق PEM يحتوي على شهادة المستخدم. إذا لم يتم تحديد keyfilename، فمن المتوقع أن تكون المفتاح الخاص للمستخدم في filename أيضًا. بخلاف ذلك، keyfilename هو اسم الملف الذي يحتوي على المفتاح الخاص.

في pkinit_anchors أو pkinit_pool، يُفترض أن يكون filename اسم ملف حزمة CA بأسلوب OpenSSL.

DIR:dirname
لهذا الخيار سلوك يعتمد على السياق.

في pkinit_identity أو pkinit_identities، يحدد dirname دليلًا يحتوي على ملفات باسم *.crt و *.key حيث يكون الجزء الأول من اسم الملف متطابقًا لأزواج متطابقة من ملفات الشهادات والمفتاح الخاص. عند العثور على ملف باسم ينتهي بـ .crt، يُفترض أن ملفًا مطابقًا ينتهي بـ .key يحتوي على المفتاح الخاص. إذا لم يتم العثور على مثل هذا الملف، فلن يتم استخدام الشهادة الموجودة في .crt.

في pkinit_anchors أو pkinit_pool، يُفترض أن يكون dirname دليل CA مُجزأ بأسلوب OpenSSL حيث يتم تخزين كل شهادة CA في ملف باسم hash-of-ca-cert.#. يتم تشجيع هذه البنية التحتية، ولكن سيتم فحص جميع الملفات في الدليل وإذا كانت تحتوي على شهادات (بتنسيق PEM)، فسيتم استخدامها.

في pkinit_revoke، يُفترض أن يكون dirname دليل CA مُجزأ بأسلوب OpenSSL حيث يتم تخزين كل قائمة إبطال في ملف باسم hash-of-ca-cert.r#. يتم تشجيع هذه البنية التحتية، ولكن سيتم فحص جميع الملفات في الدليل وإذا كانت تحتوي على قائمة إبطال (بتنسيق PEM)، فسيتم استخدامها.

PKCS12:filename
filename هو اسم ملف بتنسيق PKCS #12، يحتوي على شهادة المستخدم والمفتاح الخاص.
PKCS11:[module_name=]modname[:slotid=slot-id][:token=token-label][:certid=cert-id][:certlabel=cert-label]
جميع الكلمات المفتاحية/القيم اختيارية. يحدد modname موقع مكتبة تنفذ PKCS #11. إذا تم العثور على قيمة بدون كلمة مفتاحية، فيُفترض أنها modname. إذا لم يتم تحديد اسم الوحدة، فالقيمة الافتراضية هي opensc-pkcs11.so. يمكن تحديد slotid= و/أو token= لفرض استخدام قارئ بطاقة ذكية معين أو رمز مميز إذا كان هناك أكثر من واحد متاح. يمكن تحديد certid= و/أو certlabel= لفرض تحديد شهادة معينة على الجهاز. انظر خيار التكوين pkinit_cert_match لمزيد من الطرق لتحديد شهادة معينة لاستخدامها لـ PKINIT.
ENV:envvar
envvar يحدد اسم متغير بيئة تم تعيينه إلى قيمة تتوافق مع إحدى القيم السابقة. على سبيل المثال، ENV:X509_PROXY، حيث تم تعيين متغير البيئة X509_PROXY إلى FILE:/tmp/my_proxy.pem.

خيارات PKINIT krb5.conf

pkinit_anchors
يحدد موقع شهادات المرساة (الجذر) الموثوق بها التي يثق بها العميل لتوقيع شهادات KDC. يمكن تحديد هذا الخيار عدة مرات. لا يتم استخدام هذه القيم من ملف التكوين إذا قام المستخدم بتحديد X509_anchors على سطر الأوامر.
pkinit_cert_match
يحدد قواعد المطابقة التي يجب أن تتطابق معها شهادة العميل قبل استخدامها لمحاولة مصادقة PKINIT. إذا كان لدى المستخدم شهادات متعددة متاحة (على بطاقة ذكية، أو عبر وسائط أخرى)، فيجب اختيار شهادة واحدة فقط قبل محاولة مصادقة PKINIT. يمكن تحديد هذا الخيار عدة مرات. يتم التحقق من جميع الشهادات المتاحة مقابل كل قاعدة بالترتيب حتى تتم مطابقة شهادة واحدة بالضبط.

سلاسل مقارنة الموضوع والمصدر هي تمثيلات سلسلة RFC 2253 من قيم DN الموضوع و DN المصدر للشهادة.

تركيب قواعد المطابقة هو:

>
[relation-operator]component-rule ...

حيث:

relation-operator
يمكن أن يكون إما &&، مما يعني أن جميع قواعد المكون يجب أن تتطابق، أو ||، مما يعني أن قاعدة مكون واحدة فقط يجب أن تتطابق. الافتراضي هو &&.
component-rule
يمكن أن يكون أحد الخيارات التالية. لاحظ أنه لا توجد علامات ترقيم أو مسافات بيضاء بين قواعد المكون.
<SUBJECT>regular-expression
<ISSUER>regular-expression
<SAN>regular-expression
<EKU>extended-key-usage-list
<KU>key-usage-list

extended-key-usage-list هي قائمة مفصولة بفواصل لقيم استخدام المفتاح الممتد المطلوبة. يجب أن تكون جميع القيم في القائمة موجودة في الشهادة. يمكن أن تكون قيم استخدام المفتاح الممتد:

  • pkinit
  • msScLogin
  • clientAuth
  • emailProtection

key-usage-list هي قائمة مفصولة بفواصل لقيم استخدام المفتاح المطلوبة. يجب أن تكون جميع القيم في القائمة موجودة في الشهادة. يمكن أن تكون قيم استخدام المفتاح:

  • digitalSignature
  • keyEncipherment

أمثلة:

pkinit_cert_match = ||<SUBJECT>.*DoE.*<SAN>.*@EXAMPLE.COM
pkinit_cert_match = &&<EKU>msScLogin,clientAuth<ISSUER>.*DoE.*
pkinit_cert_match = <EKU>msScLogin,clientAuth<KU>digitalSignature
pkinit_eku_checking
يحدد هذا الخيار قيمة استخدام المفتاح الممتد التي يجب أن تحتوي عليها شهادة KDC المقدمة للعميل. (لاحظ أنه إذا كانت شهادة KDC تحتوي على اسم بديل للموضوع (SubjectAlternativeName) مشفر كاسم Kerberos TGS، فلن يكون فحص EKU ضروريًا لأن CA المصدر قد صدقت على ذلك كشهادة KDC.) القيم المعترف بها في ملف krb5.conf هي:
kpKDC
هذه هي القيمة الافتراضية وتحدد أن KDC يجب أن تحتوي على EKU id-pkinit-KPKdc كما هو معرف في RFC 4556.
kpServerAuth
إذا تم تحديد kpServerAuth، فسيتم قبول شهادة KDC مع EKU id-kp-serverAuth. يتم استخدام قيمة استخدام المفتاح هذه في معظم شهادات الخادم الصادرة تجاريًا.
none
إذا تم تحديد none، فلن يتم التحقق من شهادة KDC للتأكد من أنها تحتوي على EKU مقبول. لا يوصى باستخدام هذا الخيار.
pkinit_dh_min_bits
يحدد حجم مفتاح Diffie-Hellman الذي سيحاول العميل استخدامه. القيم المقبولة هي 1024، 2048، و 4096. الافتراضي هو 2048.
pkinit_identities
يحدد المواقع التي سيتم استخدامها للعثور على معلومات هوية X.509 للمستخدم. إذا تم تحديد هذا الخيار عدة مرات، يتم محاولة كل قيمة بترتيبها حتى يتم العثور على الشهادات. لاحظ أن هذه القيم لا تستخدم إذا حدد المستخدم X509_user_identity في سطر الأوامر.
pkinit_kdc_hostname
يشير وجود هذا الخيار إلى أن العميل على استعداد لقبول شهادة KDC مع اسم dNSName SAN (اسم بديل للموضوع) بدلاً من طلب id-pkinit-san كما هو معرف في RFC 4556. يمكن تحديد هذا الخيار عدة مرات. يجب أن تحتوي قيمته على اسم المضيف المقبول لـ KDC (كما هو موجود في شهادته).
pkinit_pool
يحدد موقع الشهادات الوسيطة التي قد يستخدمها العميل لإكمال سلسلة الثقة بين شهادة KDC ومرساة موثوقة. يمكن تحديد هذا الخيار عدة مرات.
pkinit_require_crl_checking
ستتحقق عملية التحقق من الشهادة الافتراضية دائمًا من معلومات الإلغاء المتاحة لمعرفة ما إذا تم إلغاء شهادة ما. إذا تم العثور على تطابق للشهادة في CRL، يفشل التحقق. إذا لم يتم إدراج الشهادة التي يتم التحقق منها في CRL، أو لا توجد CRL موجودة لـ CA المصدر، وكان pkinit_require_crl_checking خطأ، فسينجح التحقق.

ومع ذلك، إذا كان pkinit_require_crl_checking صحيحًا ولا توجد معلومات CRL متاحة لـ CA المصدر، فسيفشل التحقق.

يجب تعيين pkinit_require_crl_checking على صحيح إذا كانت السياسة تتطلب وجود CRLs محدثة لكل CA.

pkinit_revoke
يحدد موقع معلومات قائمة إلغاء الشهادات (CRL) التي سيستخدمها العميل عند التحقق من صحة شهادة KDC المقدمة. يمكن تحديد هذا الخيار عدة مرات.

توسيع المعلمات

بدءًا من الإصدار 1.11، تسمح العديد من المتغيرات، مثل default_keytab_name، بتوسيع المعلمات. المعلمات الصالحة هي:

%{TEMP} الدليل المؤقت
%{uid} معرف المستخدم الحقيقي لنظام Unix أو معرف الأمان لنظام Windows
%{euid} معرف المستخدم الفعال لنظام Unix أو معرف الأمان لنظام Windows
%{USERID} نفس %{uid}
%{null} سلسلة فارغة
%{LIBDIR} دليل مكتبة التثبيت
%{BINDIR} دليل الثنائيات للتثبيت
%{SBINDIR} دليل الثنائيات الإدارية
%{username} (Unix) اسم المستخدم لمعرف المستخدم الفعال
%{APPDATA} (Windows) بيانات التطبيق المتجولة للمستخدم الحالي
%{COMMON_APPDATA} (Windows) بيانات التطبيق لجميع المستخدمين
%{LOCAL_APPDATA} (Windows) بيانات التطبيق المحلية للمستخدم الحالي
%{SYSTEM} (Windows) مجلد نظام Windows
%{WINDOWS} (Windows) مجلد Windows
%{USERCONFIG} (Windows) دليل ملف تكوين MIT krb5 لكل مستخدم
%{COMMONCONFIG} (Windows) دليل ملف تكوين MIT krb5 المشترك

ملفSAMPLE KRB5.CONF

هذا مثال لملف krb5.conf عام:

[libdefaults]
    default_realm = ATHENA.MIT.EDU
    dns_lookup_kdc = true
