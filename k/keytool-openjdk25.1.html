KEYTOOL KEYSTORE MANAGEMENT

The keytool utility is a key and certificate management tool that is included with the JDK. It is used for:

  • Managing a keystore (security database) containing keys and certificates.
  • Generating public/private key pairs.
  • Importing and exporting digital certificates.

The primary function of keytool is to manage a keystore, which is a secure repository for cryptographic keys and certificates. It can also be used to manage trusted certificates, which are certificates issued by trusted Certificate Authorities (CAs).

The keytool utility provides a comprehensive set of commands for managing keystores and certificates. Some of the most commonly used commands include:

•
-genkeypair: Generates a public/private key pair and stores it in a keystore.
•
-certreq: Generates a certificate signing request (CSR) based on a public/private key pair.
•
-importcert: Imports a certificate (or a certificate chain) into a keystore.
•
-exportcert: Exports a certificate from a keystore.
•
-list: Lists the contents of a keystore.
•
-printcert: Prints the details of a certificate.
•
-delete: Deletes an entry (key pair or certificate) from a keystore.

When using keytool, it's important to understand the following concepts:

Keystore:
A file that contains a collection of cryptographic keys and certificates. Keystores are used to securely store private keys and their corresponding public key certificates, as well as trusted CA certificates.
Alias:
A unique name used to identify an entry (key pair or certificate) within a keystore. Each entry in a keystore is associated with an alias.
Distinguished Name (DN):
A string that uniquely identifies an entity, such as a person, organization, or server. DNs are used in certificates to identify the subject and issuer of the certificate.
Certificate Signing Request (CSR):
A request sent to a Certificate Authority (CA) to obtain a digital certificate. A CSR typically contains the public key of the entity requesting the certificate, along with identifying information such as the distinguished name.
Certificate Chain:
A sequence of certificates, starting with the end-entity certificate and ending with a root CA certificate. Each certificate in the chain (except the root) is signed by the issuer of the next certificate in the chain. This chain is used to establish trust in the end-entity certificate.
Trusted Certificate:
A certificate that has been imported into a keystore and is trusted by the system. Trusted certificates are typically issued by trusted Certificate Authorities (CAs) and are used to verify the authenticity of other certificates.

CAUTION:

Users should be aware that some combinations of extensions (and other certificate fields) may not conform to the Internet standard. See Certificate Conformance Warning.

GENERATING THE KEY PAIR

Create a keystore and then generate the key pair.

You can enter the command as a single line such as the following:

keytool -genkeypair -dname "cn=myname, ou=mygroup, o=mycompany, c=mycountry" -alias business -keyalg rsa -keypass password -keystore /working/mykeystore -storepass password -validity 180

The command creates the keystore named mykeystore in the working directory (provided it doesn't already exist), and assigns it the password specified by -keypass. It generates a public/private key pair for the entity whose distinguished name is myname, mygroup, mycompany, and a two-letter country code of mycountry. It uses the RSA key generation algorithm to create the keys; both are 3072 bits.

The command uses the default SHA384withRSA signature algorithm to create a self-signed certificate that includes the public key and the distinguished name information. The certificate is valid for 180 days, and is associated with the private key in a keystore entry referred to by -alias business. The private key is assigned the password specified by -keypass.

The command is significantly shorter when the option defaults are accepted. In this case, only -keyalg is required, and the defaults are used for unspecified options that have default values. You are prompted for any required values. You could have the following:

keytool -genkeypair -keyalg rsa

In this case, a keystore entry with the alias mykey is created, with a newly generated key pair and a certificate that is valid for 90 days. This entry is placed in your home directory in a keystore named .keystore . .keystore is created if it doesn't already exist. You are prompted for the distinguished name information, the keystore password, and the private key password.

Note:

The rest of the examples assume that you responded to the prompts with values equal to those specified in the first -genkeypair command. For example, a distinguished name of cn=myname, ou=mygroup, o=mycompany, c=mycountry.

REQUESTING A SIGNED CERTIFICATE FROM A CA

Note:

Generating the key pair created a self-signed certificate; however, a certificate is more likely to be trusted by others when it is signed by a CA.

To get a CA signature, complete the following process:

1.
Generate a CSR:

keytool -certreq -file myname.csr

This creates a CSR for the entity identified by the default alias mykey and puts the request in the file named myname.csr.

2.
Submit myname.csr to a CA, such as DigiCert.

The CA authenticates you, the requestor (usually offline), and returns a certificate, signed by them, authenticating your public key. In some cases, the CA returns a chain of certificates, each one authenticating the public key of the signer of the previous certificate in the chain.

IMPORTING A CERTIFICATE FOR THE CA

To import a certificate for the CA, complete the following process:

1.
Before you import the certificate reply from a CA, you need one or more trusted certificates either in your keystore or in the cacerts keystore file. See -importcert in Commands.
•
If the certificate reply is a certificate chain, then you need the top certificate of the chain. The root CA certificate that authenticates the public key of the CA.
•
If the certificate reply is a single certificate, then you need a certificate for the issuing CA (the one that signed it). If that certificate isn't self-signed, then you need a certificate for its signer, and so on, up to a self-signed root CA certificate.

The cacerts keystore ships with a set of root certificates issued by the CAs of the Oracle Java Root Certificate program [https://www.oracle.com/java/technologies/javase/carootcertsprogram.html]. If you request a signed certificate from a CA, and a certificate authenticating that CA's public key hasn't been added to cacerts, then you must import a certificate from that CA as a trusted certificate.

A certificate from a CA is usually self-signed or signed by another CA. If it is signed by another CA, you need a certificate that authenticates that CA's public key.

For example, you have obtained a X.cer file from a company that is a CA and the file is supposed to be a self-signed certificate that authenticates that CA's public key. Before you import it as a trusted certificate, you should ensure that the certificate is valid by:

1.
Viewing it with the keytool -printcert command or the keytool -importcert command without using the -noprompt option. Make sure that the displayed certificate fingerprints match the expected fingerprints.
2.
Calling the person who sent the certificate, and comparing the fingerprints that you see with the ones that they show or that a secure public key repository shows.

Only when the fingerprints are equal is it assured that the certificate wasn't replaced in transit with somebody else's certificate (such as an attacker's certificate). If such an attack takes place, and you didn't check the certificate before you imported it, then you would be trusting anything that the attacker signed.

2.
Replace the self-signed certificate with a certificate chain, where each certificate in the chain authenticates the public key of the signer of the previous certificate in the chain, up to a root CA.

If you trust that the certificate is valid, then you can add it to your keystore by entering the following command:

keytool -importcert -alias alias -file *X*.cer`

This command creates a trusted certificate entry in the keystore from the data in the CA certificate file and assigns the values of the alias to the entry.

IMPORTING THE CERTIFICATE REPLY FROM THE CA

After you import a certificate that authenticates the public key of the CA that you submitted your certificate signing request to (or there is already such a certificate in the cacerts file), you can import the certificate reply and replace your self-signed certificate with a certificate chain.

The certificate chain is one of the following:

•
Returned by the CA when the CA reply is a chain.
•
Constructed when the CA reply is a single certificate. This certificate chain is constructed by using the certificate reply and trusted certificates available either in the keystore where you import the reply or in the cacerts keystore file.

For example, if you sent your certificate signing request to DigiCert, then you can import their reply by entering the following command:

Note:

In this example, the returned certificate is named DCmyname.cer.

keytool -importcert -trustcacerts -file DCmyname.cer

EXPORTING A CERTIFICATE THAT AUTHENTICATES THE PUBLIC KEY

Note:

If you used the jarsigner command to sign a Java Archive (JAR) file, then clients that use the file will want to authenticate your signature.

One way that clients can authenticate you is by importing your public key certificate into their keystore as a trusted entry. You can then export the certificate and supply it to your clients.

For example:

1.
Copy your certificate to a file named myname.cer by entering the following command:

Note:

In this example, the entry has an alias of mykey.

keytool -exportcert -alias mykey -file myname.cer

keystore.type=jks

شهادة
الشهادة (أو شهادة المفتاح العام) هي بيان موقع رقميًا من كيان واحد (المُصدر)، يقول إن المفتاح العام وبعض المعلومات الأخرى لكيان آخر (الموضوع) لها قيمة محددة. المصطلحات التالية مرتبطة بالشهادات:
•
المفاتيح العامة: هذه هي أرقام مرتبطة بكيان معين، ومقصود أن يعرفها كل من يحتاج إلى تفاعلات موثوقة مع هذا الكيان. تستخدم المفاتيح العامة للتحقق من التوقيعات.
•
موقع رقميًا: إذا تم توقيع بعض البيانات رقميًا، فإنها تُخزن مع هوية كيان وتوقيع يثبت أن هذا الكيان يعرف هذه البيانات. يتم جعل البيانات غير قابلة للتزوير عن طريق التوقيع بمفتاح الكيان الخاص.
•
الهوية: طريقة معروفة لمعالجة كيان. في بعض الأنظمة، الهوية هي المفتاح العام، وفي أنظمة أخرى يمكن أن تكون أي شيء من معرف مستخدم Oracle Solaris إلى عنوان بريد إلكتروني إلى اسم مميز X.509.
•
التوقيع: يتم حساب التوقيع على بعض البيانات باستخدام المفتاح الخاص للكيان. المُوقِّع، والذي في حالة الشهادة يُعرف أيضًا باسم المُصدر.
•
المفاتيح الخاصة: هذه هي أرقام، يُفترض أن يعرفها فقط الكيان الخاص الذي ينتمي إليه مفتاحه الخاص (أي، يُفترض أن يبقى سريًا). توجد المفاتيح الخاصة والعامة في أزواج في جميع أنظمة تشفير المفتاح العام (يشار إليها أيضًا بأنظمة تشفير المفتاح العام). في نظام تشفير مفتاح عام نموذجي، مثل DSA، يتوافق المفتاح الخاص مع مفتاح عام واحد فقط. تستخدم المفاتيح الخاصة لحساب التوقيعات.
•
الكيان: الكيان هو شخص، منظمة، برنامج، كمبيوتر، عمل تجاري، بنك، أو أي شيء آخر تثق به بدرجة معينة.

يتطلب تشفير المفتاح العام الوصول إلى المفاتيح العامة للمستخدمين. في بيئة شبكة واسعة النطاق، من المستحيل ضمان إنشاء علاقات سابقة بين الكيانات المتواصلة أو وجود مستودع موثوق به يحتوي على جميع المفاتيح العامة المستخدمة. تم اختراع الشهادات كحل لمشكلة توزيع المفاتيح العامة هذه. الآن يمكن لسلطة التصديق (CA) أن تعمل كطرف ثالث موثوق به. سلطات التصديق هي كيانات مثل الشركات التي يثق بها للتوقيع (إصدار) شهادات لكيانات أخرى. يُفترض أن سلطات التصديق تنشئ فقط شهادات صالحة وموثوقة لأنها ملزمة باتفاقيات قانونية. هناك العديد من سلطات التصديق العامة، مثل DigiCert وComodo وEntrust، وما إلى ذلك.

يمكنك أيضًا تشغيل سلطة تصديق خاصة بك باستخدام منتجات مثل Microsoft Certificate Server أو منتج Entrust CA لمؤسستك. باستخدام أمر `keytool`، من الممكن عرض الشهادات واستيرادها وتصديرها. من الممكن أيضًا إنشاء شهادات موقعة ذاتيًا.

يتعامل أمر `keytool` حاليًا مع شهادات X.509.

شهادات X.509
يحدد معيار X.509 المعلومات التي يمكن أن تدخل في الشهادة ويصف كيفية كتابتها (تنسيق البيانات). يتم ترميز جميع البيانات في الشهادة باستخدام معيارين مرتبطين يسمى ASN.1/DER. يصف Abstract Syntax Notation 1 البيانات. تصف قواعد الترميز المحددة طريقة واحدة لتخزين تلك البيانات ونقلها.

تحتوي جميع شهادات X.509 على البيانات التالية، بالإضافة إلى التوقيع:

•
الإصدار: يحدد هذا أي إصدار من معيار X.509 ينطبق على هذه الشهادة، مما يؤثر على المعلومات التي يمكن تحديدها فيها. حتى الآن، تم تعريف ثلاثة إصدارات. يمكن لأمر `keytool` استيراد وتصدير شهادات v1 و v2 و v3. يقوم بإنشاء شهادات v3.
•
كان إصدار X.509 v1 متاحًا منذ عام 1988، وهو منتشر على نطاق واسع، وهو الأكثر عمومية.
•
قدم إصدار X.509 v2 مفهوم معرفات فريدة للموضوع والمُصدر للتعامل مع إمكانية إعادة استخدام أسماء الموضوع أو المُصدر بمرور الوقت. توصي معظم وثائق ملف تعريف الشهادة بشدة بعدم إعادة استخدام الأسماء وألا تستخدم الشهادات المعرفات الفريدة. شهادات الإصدار v2 ليست مستخدمة على نطاق واسع.
•
إصدار X.509 v3 هو الأحدث (1996) ويدعم مفهوم الامتدادات حيث يمكن لأي شخص تعريف امتداد وتضمينه في الشهادة. بعض الامتدادات الشائعة هي: KeyUsage (يحد من استخدام المفاتيح لأغراض معينة مثل `signing-only`) وAlternativeNames (يسمح بربط هويات أخرى بهذا المفتاح العام، على سبيل المثال، أسماء DNS، وعناوين البريد الإلكتروني، وعناوين IP). يمكن تمييز الامتدادات على أنها حرجة للإشارة إلى أنه يجب التحقق من الامتداد وإنفاذه أو استخدامه. على سبيل المثال، إذا كانت الشهادة تحتوي على امتداد KeyUsage معلم كـ "حرج" وتم تعيينه إلى `keyCertSign`، فعند تقديم هذه الشهادة أثناء اتصال SSL، يجب رفضها لأن امتداد الشهادة يشير إلى أنه يجب استخدام المفتاح الخاص المرتبط فقط لتوقيع الشهادات وليس للاستخدام في SSL.
•
الرقم التسلسلي: الكيان الذي أنشأ الشهادة مسؤول عن تعيين رقم تسلسلي لها لتمييزها عن الشهادات الأخرى التي يصدرها. تستخدم هذه المعلومات بطرق عديدة. على سبيل المثال، عند إلغاء شهادة، يتم وضع رقمها التسلسلي في قائمة مراجعة الشهادات (CRL).
•
معرف خوارزمية التوقيع: يحدد هذا الخوارزمية التي استخدمتها سلطة التصديق للتوقيع على الشهادة.
•
اسم المُصدر: الاسم المميز X.500 للكيان الذي وقع الشهادة. عادة ما يكون هذا سلطة تصديق (CA). استخدام هذه الشهادة يعني الثقة في الكيان الذي وقع هذه الشهادة. في بعض الحالات، مثل شهادات سلطة التصديق الجذرية أو العليا، توقع سلطة التصديق شهادتها الخاصة.
•
فترة الصلاحية: كل شهادة صالحة لفترة زمنية محدودة فقط. تصف هذه الفترة تاريخ ووقت البدء وتاريخ ووقت الانتهاء، ويمكن أن تكون قصيرة مثل بضع ثوانٍ أو تقارب قرنًا. تعتمد فترة الصلاحية المختارة على عدد من العوامل، مثل قوة المفتاح الخاص المستخدم لتوقيع الشهادة، أو المبلغ الذي يرغب المرء في دفعه مقابل شهادة. هذه هي الفترة المتوقعة التي يمكن للكيانات الاعتماد فيها على القيمة العامة، عندما لم يتم اختراق المفتاح الخاص المرتبط.
•
اسم الموضوع: اسم الكيان الذي تحدد شهادته المفتاح العام له. يستخدم هذا الاسم معيار X.500، لذا فهو مصمم ليكون فريدًا عبر الإنترنت. هذا هو الاسم المميز X.500 (DN) للكيان. على سبيل المثال،

CN=Java Duke, OU=Java Software Division, O=Oracle Corporation, C=US

تشير هذه إلى الاسم الشائع للموضوع (CN)، الوحدة التنظيمية (OU)، المنظمة (O)، والبلد (C).

•
معلومات المفتاح العام للموضوع: هذا هو المفتاح العام للكيان المسمى مع معرف خوارزمية يحدد نظام تشفير المفتاح العام الذي ينتمي إليه هذا المفتاح وأي معلمات مفتاح مرتبطة.
سلاسل الشهادات
يمكن لأمر `keytool` إنشاء وإدارة إدخالات مفاتيح في مخزن المفاتيح التي تحتوي كل منها على مفتاح خاص وسلسلة شهادات مرتبطة. تحتوي الشهادة الأولى في السلسلة على المفتاح العام الذي يتوافق مع المفتاح الخاص.

عند إنشاء المفاتيح لأول مرة، تبدأ السلسلة عادةً بعنصر واحد، وهو شهادة موقعة ذاتيًا. انظر -genkeypair في الأوامر. الشهادة الموقعة ذاتيًا هي شهادة يكون فيها المُصدر (المُوقِّع) هو نفسه الموضوع. الموضوع هو الكيان الذي يتم المصادقة على مفتاحه العام بواسطة الشهادة. عند استدعاء أمر `-genkeypair` لإنشاء زوج مفاتيح عام/خاص جديد، فإنه يغلف المفتاح العام في شهادة موقعة ذاتيًا (ما لم يتم تحديد الخيار `-signer`).

لاحقًا، بعد إنشاء طلب توقيع شهادة (CSR) باستخدام أمر `-certreq` وإرساله إلى سلطة التصديق (CA)، يتم استيراد الرد من سلطة التصديق باستخدام `-importcert`، ويتم استبدال الشهادة الموقعة ذاتيًا بسلسلة من الشهادات. في أسفل السلسلة توجد الشهادة (الرد) الصادرة عن سلطة التصديق والتي تصادق على المفتاح العام للموضوع. الشهادة التالية في السلسلة هي شهادة تصادق على المفتاح العام لسلطة التصديق.

في كثير من الحالات، تكون هذه شهادة موقعة ذاتيًا، وهي شهادة من سلطة التصديق تصادق على مفتاحها العام، وهي الشهادة الأخيرة في السلسلة. في حالات أخرى، قد تعيد سلطة التصديق سلسلة من الشهادات. في هذه الحالة، تكون الشهادة السفلية في السلسلة هي نفسها (شهادة موقعة بواسطة سلطة التصديق، تصادق على المفتاح العام لإدخال المفتاح)، ولكن الشهادة الثانية في السلسلة هي شهادة موقعة بواسطة سلطة تصديق مختلفة تصادق على المفتاح العام لسلطة التصديق التي أرسلت إليها طلب توقيع الشهادة. ال

التالية في السلسلة هي شهادة تصادق على مفتاح CA الثاني، وهكذا، حتى يتم الوصول إلى شهادة جذر موقعة ذاتيًا. كل شهادة في السلسلة (بعد الأولى) تصادق على المفتاح العام لموقّع الشهادة السابقة في السلسلة.

العديد من CAs لا ترجع سوى الشهادة الصادرة، دون أي سلسلة داعمة، خاصة عندما تكون هناك بنية هرمية مسطحة (لا توجد CAs وسيطة). في هذه الحالة، يجب إنشاء سلسلة الشهادات من معلومات الشهادات الموثوقة المخزنة بالفعل في مخزن المفاتيح.

تنسيق رد مختلف (محدد بواسطة معيار PKCS #7) يتضمن سلسلة الشهادات الداعمة بالإضافة إلى الشهادة الصادرة. يمكن معالجة كلا تنسيقي الرد بواسطة الأمر keytool.

شهادة CA الجذرية (الطبقة العليا) موقعة ذاتيًا. ومع ذلك، فإن الثقة في المفتاح العام للجذر لا تأتي من شهادة الجذر نفسها، بل من مصادر أخرى مثل الصحف. هذا لأنه يمكن لأي شخص إنشاء شهادة موقعة ذاتيًا بالاسم المميز، على سبيل المثال، لـ DigiCert root CA. المفتاح العام لـ root CA معروف على نطاق واسع. السبب الوحيد لتخزينه في شهادة هو أن هذا هو التنسيق الذي تفهمه معظم الأدوات، لذا فإن الشهادة في هذه الحالة تُستخدم فقط كوسيلة لنقل المفتاح العام لـ root CA. قبل إضافة شهادة root CA إلى مخزن المفاتيح الخاص بك، يجب عليك عرضها باستخدام الخيار -printcert ومقارنة البصمة المعروضة بالبصمة المعروفة التي تم الحصول عليها من الصحف، وصفحة الويب الخاصة بـ root CA، وما إلى ذلك.

ملف شهادات cacerts
يوجد ملف شهادات يسمى cacerts في دليل خصائص الأمان:
•
Linux و macOS: JAVA_HOME/lib/security
•
Windows: JAVA_HOME\lib\security

يمثل ملف cacerts مخزن مفاتيح على مستوى النظام بشهادات CA. يمكن لمسؤولي النظام تكوين وإدارة هذا الملف باستخدام الأمر keytool عن طريق تحديد jks كنوع لمخزن المفاتيح. يتم شحن ملف مخزن المفاتيح cacerts بمجموعة افتراضية من شهادات CA الجذرية. بالنسبة لأنظمة Linux و macOS و Windows، يمكنك سرد الشهادات الافتراضية باستخدام الأمر التالي:

keytool -list -cacerts

كلمة المرور الأولية لملف مخزن المفاتيح cacerts هي changeit. يجب على مسؤولي النظام تغيير كلمة المرور هذه وإذن الوصول الافتراضي لهذا الملف عند تثبيت SDK.

ملاحظة:

من المهم التحقق من ملف cacerts الخاص بك. نظرًا لأنك تثق في CAs الموجودة في ملف cacerts ككيانات لتوقيع وإصدار الشهادات لكيانات أخرى، يجب عليك إدارة ملف cacerts بعناية. يجب أن يحتوي ملف cacerts على شهادات CAs التي تثق بها فقط. تقع على عاتقك مسؤولية التحقق من شهادات CA الجذرية الموثوقة المضمنة في ملف cacerts واتخاذ قرارات الثقة الخاصة بك.

لإزالة شهادة CA غير موثوق بها من ملف cacerts، استخدم الخيار -delete من الأمر keytool. يمكنك العثور على ملف cacerts في دليل JDK $JAVA_HOME/lib/security. اتصل بمسؤول النظام الخاص بك إذا لم يكن لديك إذن لتعديل هذا الملف.

معيار ترميز الشهادات RFC 1421 للإنترنت
غالبًا ما يتم تخزين الشهادات باستخدام تنسيق الترميز القابل للطباعة المحدد بواسطة معيار RFC 1421 للإنترنت، بدلاً من ترميزها الثنائي. تنسيق الشهادة هذا، المعروف أيضًا باسم ترميز Base64، يجعل من السهل تصدير الشهادات إلى تطبيقات أخرى عبر البريد الإلكتروني أو من خلال آلية أخرى.

يمكن قراءة الشهادات بواسطة الأوامر -importcert و -printcert إما بهذا التنسيق أو بالترميز الثنائي. يقوم الأمر -exportcert افتراضيًا بإخراج شهادة بتنسيق الترميز الثنائي، ولكنه سيقوم بدلاً من ذلك بإخراج شهادة بتنسيق الترميز القابل للطباعة، عندما يتم تحديد الخيار -rfc.

يطبع الأمر -list افتراضيًا بصمة SHA-256 للشهادة. إذا تم تحديد الخيار -v، فسيتم طباعة الشهادة بتنسيق قابل للقراءة البشرية. إذا تم تحديد الخيار -rfc، فسيتم إخراج الشهادة بتنسيق الترميز القابل للطباعة.

في تنسيق الترميز القابل للطباعة، يتم تحديد الشهادة المشفرة في البداية والنهاية بالنص التالي:

-----BEGIN CERTIFICATE-----
encoded certificate goes here.
-----END CERTIFICATE-----
أسماء X.500 المميزة
تُستخدم أسماء X.500 المميزة لتحديد الكيانات، مثل تلك التي تحمل اسم حقلي subject و issuer (الموقّع) لشهادات X.509. يدعم الأمر keytool الأجزاء الفرعية التالية:
•
commonName: الاسم الشائع للشخص مثل Susan Jones.
•
organizationUnit: اسم المنظمة الصغيرة (مثل القسم أو الفرع). على سبيل المثال، Purchasing.
•
localityName: اسم المنطقة (المدينة)، على سبيل المثال، Palo Alto.
•
stateName: اسم الولاية أو المقاطعة، على سبيل المثال، California.
•
country: رمز البلد المكون من حرفين، على سبيل المثال، CH.

عند توفير سلسلة اسم مميز كقيمة للخيار -dname، كما هو الحال في الأمر -genkeypair، يجب أن تكون السلسلة بالتنسيق التالي:

CN=cName, OU=orgUnit, O=org, L=city, S=state, C=countryCode

تمثل جميع العناصر التالية قيمًا فعلية، والكلمات الرئيسية السابقة هي اختصارات لما يلي:

CN=commonName
OU=organizationUnit
O=organizationName
L=localityName
S=stateName
C=country

سلسلة اسم مميز نموذجية هي:

CN=Mark Smith, OU=Java, O=Oracle, L=Cupertino, S=California, C=US

أمر نموذجي يستخدم مثل هذه السلسلة هو:

keytool -genkeypair -dname "CN=Mark Smith, OU=Java, O=Oracle, L=Cupertino, S=California, C=US" -alias mark -keyalg rsa

لا يهم حالة الأحرف للاختصارات الرئيسية. على سبيل المثال، CN و cn و Cn تُعامل جميعها بنفس الطريقة.

الترتيب مهم؛ يجب أن يظهر كل مكون فرعي بالترتيب المحدد. ومع ذلك، ليس من الضروري وجود جميع المكونات الفرعية. يمكنك استخدام مجموعة فرعية، على سبيل المثال:

CN=Smith, OU=Java, O=Oracle, C=US

إذا كانت سلسلة اسم مميز تحتوي على فاصلة، فيجب الهروب من الفاصلة بحرف الشرطة المائلة العكسية (\) عند تحديد السلسلة في سطر الأوامر، كما في:

cn=Jack, ou=Java\, Product Development, o=Oracle, c=US

لا يلزم أبدًا تحديد سلسلة اسم مميز في سطر الأوامر. عندما يكون الاسم المميز مطلوبًا لأمر ما، ولكن لم يتم توفيره في سطر الأوامر، يتم مطالبة المستخدم بكل مكون فرعي. في هذه الحالة، لا تحتاج الفاصلة إلى الهروب بحرف الشرطة المائلة العكسية (\).

تحذيرات

تحذير بشأن استيراد الشهادات الموثوقة

هام: تأكد من التحقق من الشهادة بعناية فائقة قبل استيرادها كشهادة موثوق بها.

مثال على Windows:

اعرض الشهادة أولاً باستخدام الأمر -printcert أو الأمر -importcert بدون الخيار -noprompt. تأكد من تطابق بصمات الشهادات المعروضة مع البصمات المتوقعة. على سبيل المثال، افترض أن شخصًا ما يرسل لك شهادة عبر البريد الإلكتروني وأنك تضعها في ملف يسمى \tmp\cert. قبل أن تفكر في إضافة الشهادة إلى قائمة الشهادات الموثوق بها، يمكنك تنفيذ أمر -printcert لعرض بصماتها، كما يلي:

  keytool -printcert -file \tmp\cert
    Owner: CN=ll, OU=ll, O=ll, L=ll, S=ll, C=ll
    Issuer: CN=ll, OU=ll, O=ll, L=ll, S=ll, C=ll
    Serial Number: 59092b34
    Valid from: Thu Jun 24 18:01:13 PDT 2016 until: Wed Jun 23 17:01:13 PST 2016
    Certificate Fingerprints:
                   SHA-1: 20:B6:17:FA:EF:E5:55:8A:D0:71:1F:E8:D6:9D:C0:37:13:0E:5E:FE
