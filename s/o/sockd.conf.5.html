مع المفتاح nodnsmismatch، لن يقبل الخادم الاتصالات من عناوين بها عدم تطابق بين عنوان IP لنظام أسماء النطاقات واسم المضيف. الافتراضي هو قبولها.

مع المفتاح checkreplyauth، سيتحقق الخادم من أن المصادقة على ردود الربط وردود UDP تتطابق مع ما تم تعيينه في القاعدة وطريقة socks العامة. عادةً، لا تكون المصادقة مرغوبة على الردود، حيث إنها ردود مرسلة إلى عملاء socks من عملاء غير socks، وبالتالي تكون مجموعة محدودة فقط من طرق المصادقة ممكنة.

الطرق الممكنة لـ TCP هي الطرق التي لا تتضمن بروتوكول socks بأي شكل من الأشكال، وهي مدرجة في قسم clientmethod المذكور سابقًا. بالنسبة لردود UDP، لا يمكن استخدام أي طرق.

الافتراضي هو عدم التحقق من المصادقة على الردود.

عدد الثواني التي سينتظرها الخادم حتى يكتمل الاتصال الذي بدأ نيابة عن عميل socks. الافتراضي هو 30. تعيينه إلى 0 سيستخدم افتراضي النظام.
timeout.io
عدد الثواني التي يمكن أن يظل فيها الاتصال القائم خاملاً. الافتراضي هو 0، مما يعني إلى الأبد. انظر أيضًا الخيار "-n" في صفحة الدليل sockd(8).

يمكن تعيين مهلات فردية لـ TCP و UDP عن طريق إضافة ".<protocolname>" إلى io، أي timeout.io.tcp أو timeout.io.udp.

يمكن أيضًا تعيين مهلات فردية ضمن القواعد، باستخدام نفس بناء الجملة. ستقوم المهلة المعينة في القاعدة بعد ذلك بتجاوز المهلات الافتراضية للعملاء الذين تتطابق معهم القاعدة.

timeout.negotiate
عدد الثواني التي يمكن أن يقضيها العميل في التفاوض مع خادم Dante لجلسة socks قبل أن يقوم Dante بإغلاق الاتصال بالعميل. الافتراضي هو 30. قم بتعيينه إلى 0 إلى الأبد، على الرغم من أن هذا غير مستحسن بشدة.
timeout.tcp_fin_wait
المهلة المكافئة لحالة FIN-WAIT-2 في TCP. الافتراضي هو 0، مما يعني استخدام افتراضي النظام (عادةً، لا توجد مهلة).
udp.connectdst
تمكين أو تعطيل ما إذا كان يجب على الخادم محاولة توصيل مقابس UDP بالوجهة. القيم الصالحة هي yes و no.

الافتراضي هو yes، مما يحسن أداء UDP، ولكنه قد لا يكون متوافقًا مع بعض بروتوكولات تطبيقات UDP لأنه يعني أن الخادم يمكنه فقط تلقي حزم من عنوان الوجهة.

سيبقى المقبس متصلاً فقط طالما أن العميل يرسل حزم UDP إلى عنوان وجهة واحد فقط. إذا تم إرسال حزم إلى وجهات متعددة، فلن يظل المقبس متصلاً ويمكن استلام الردود من أي وجهة.

SOCKET OPTIONS

The socket options are set with the directive directive socket. The syntax is as follows:

socket
<direction>.<level>.<option>: <value>
socket
<direction>.<level>.<option>.<subfield>: <value>
socket
<direction>.<level>.<option>: <value>
socket
<direction>.<level>.<option>.<subfield>: <value>

The syntax for setting socket options is as follows:

<direction>.<level>.<option>: <value>

The value field corresponds to the value that the socket option should be set to. For many socket options this is an integer value. The level and option values correspond to the socket names and protocol levels listed above. Both should be in lower-case.

The direction keywords is used to specify whether the socket option should be set for traffic on the internal or the external interface and can have the values internal and external. For example, to set the IP_TOS socket option on outgoing traffic, the following syntax can be used:

external.ip.ip_tos: 0x10

In this example, the argument value (0x10) is specified as a hex value. For some of the socket options the value can also be set symbolically. Currently this is possible for the following options, with the listed values:

ip_portrange
ip_portrange_default, ip_portrange_low, ip_portrange_high

The IP_TOS socket option also supports this, but handling this option is somewhat complicated by the same bits having different meanings in different RFCs. Handling this is done with a subfield that indicates the type of argument that should be used. The following subfields are defined and should be added to the name of the socket option as specified below:

ip_tos.dscp
af11 af12 af13 af21 af22 af23 af31 af32 af33 af41 af42 af43 cs0 cs1 cs2 cs3 cs4 cs5 cs6 cs7 ef
ip_tos.prec
netcontrol internetcontrol critic_ecp flashoverride flash immediate priority routine
ip_tos.tos
lowdelay throughput reliability

When numerical arguments are given to subfields, the values are shifted to apply only to the subfield bit range. The following example shows the different ways of setting IP_TOS to lowdelay on external traffic:

external.ip.ip_tos:     0x10       #base value, numerically
external.ip.ip_tos.tos: 0x08       #subfield, numerically
external.ip.ip_tos.tos: lowdelay   #subfield, symbolically

The first value sets the value directly, the second sets only the TOS bits, which are shifted relative to the base value. The final line sets the TOS value symbolically.

This functionality gives a large amount of control over socket options, but it should not be used without some understanding of how the kernel allows the socket option to be set, and the limitations that apply when the socket options are set as either defaults or in rules.

Setting a socket option in a client pass or socks-rules will cause any defaults to be overridden. Global options are set before bind() is called on internal sockets, or before connect() is called on external sockets. Options set in client rules are also applied before bind() is called on the internal socket, but cannot be set for the external socket. For socks-rules, both external and internal options can be set, but because the socks-request must be interpreted before the rules can be evaluated, socket options can only be set on internal sockets after the connection has been received.

Some socket options must be set before a connection has been established, while others can only be set after a connection has been established. Others can be set at any time.

Socket options that are not listed above can also be set by specifying the socket option name numerically, for example:

external.ip.10: 0x12

In this example the socket option corresponding to the value 10 will be set. These numbers are platform dependent but can typically be determined by looking at the appropriate system header files. Specifying options numerically might result in some warnings, but allows any socket option to be specified, as long as it takes a numerical argument. This is not the recommended approach for setting socket options, but represents a simple way of setting socket options that are not directly supported by the server, such as local kernel extensions.

طرق المصادقة

يدعم خادم Dante طرق المصادقة التالية. قد تدعم بعض تثبيتات Dante مجموعة فرعية فقط من هذه، اعتمادًا على دعم النظام الأساسي.

none
تتطلب هذه الطريقة لا شكل من أشكال المصادقة.
username
تتطلب هذه الطريقة من العميل تقديم اسم مستخدم وكلمة مرور. يجب أن تتطابق هذه المعلومات مع اسم المستخدم وكلمة المرور المقدمة في ملف كلمة المرور للنظام.
gssapi
تتطلب هذه الطريقة إعداد بيئة Kerberos ويمكنها توفير تشفير ومصادقة قوية، اعتمادًا على إعدادات gssapi التي تختارها.
rfc931
تتطلب هذه الطريقة من المضيف الذي يعمل عليه عميل socks توفير اسم مستخدم rfc931 ("ident") للعميل. يجب أن يتطابق اسم المستخدم هذا مع اسم مستخدم مقدم في ملف كلمة المرور للنظام.
pam.address
مصادقة PAM المستندة إلى IP (rhosts).
pam.any
سيحاول المطابقة مع أي نوع من مصادقة PAM، اعتمادًا على المعلومات المتاحة حاليًا. عادة ما يكون ذا فائدة محدودة، ويجب عليك بدلاً من ذلك تعيين طريقة (طرق) PAM التي تريدها بالفعل.
pam.username
مصادقة PAM المستندة إلى اسم المستخدم / كلمة المرور. مشابهة للطريقة username، ولكن يتم تمرير المعلومات إلى نظام PAM للمصادقة، بدلاً من استخدام Dante لملف كلمة المرور للنظام مباشرة. عند استخدام PAM، كن حذرًا من تسرب الذاكرة والأخطاء الأخرى في مكتبة PAM الخارجية التي سيضطر Dante إلى استخدامها على نظامك.

العناوين

يمكن أن يتكون كل حقل عنوان من عنوان IP (وعند الاقتضاء، قناع شبكة، مفصول عن عنوان IP بعلامة '/')، أو اسم مضيف، أو اسم نطاق (يُشار إليه بحرف '.' البادئ)، أو اسم واجهة.

يمكن إعطاء عنوان IP بصيغة IPv4، أو صيغة IPv6، أو بالقيمة الخاصة 0/0، والتي تتطابق مع جميع عناوين IP، سواء كانت IPv4 أو IPv6. يُقصد بالأخير استخدامها في rules التي يجب أن تتطابق مع عملاء أو أهداف IPv4 و IPv6.

يمكن لكل عنوان، باستثناء عنوان external، أن يتضمن محدد port اختياري.

قواعد

هناك مجموعتان من القواعد وتعملان على مستويات مختلفة. يتم التحقق من القواعد التي تبدأ بـ client أولاً وتُستخدم لمعرفة ما إذا كان مسموحًا للعميل بالاتصال بخادم Dante. نسميها "قواعد العميل" (client-rules). تبدأ هذه القواعد بـ client pass لقاعدة تسمح للعميل، أو client block لقاعدة تحظر العميل.

يوصى بأن لا تستخدم قواعد العميل أسماء المضيفين بل عناوين IP فقط، لأسباب أمنية وأسباب الأداء. تعمل هذه القواعد على مستوى TCP.

القواعد الأخرى، التي نسميها "socks-rules"، تبدأ بـ socks وتعمل على مستوى بروتوكول socks.

تبدأ هذه القواعد بـ socks pass لقاعدة تسمح للعميل، أو socks block لقاعدة تحظر العميل.

يتم التحقق من هذه القواعد فقط إذا سمحت قواعد العميل بالاتصال. تُستخدم قواعد socks لتقييم طلب socks الذي يرسله العميل.

بينما أهمية استخدام هذه القواعد لعناوين IP فقط أقل، بشرط أن تكون قواعد العميل قد تم تكوينها للسماح بالوصول فقط من نطاق محدد مسبقًا لعناوين IP للعملاء، إلا أنه لا يزال يوصى بذلك.

تتضمن كلتا المجموعتين من القواعد كلمة مفتاحية pass أو deny. تحدد كلمة المفتاح pass/deny ما إذا كان سيتم تمرير الاتصالات المطابقة للقاعدة أو حظرها.

تحدد كل من قواعد العميل وقواعد socks أيضًا زوج عنوان from/to الذي يعطي العناوين التي ستتطابق معها القاعدة.

في كلا السياقين، تشير from إلى عنوان العميل، أي العنوان الذي يتصل به العميل بخادم Dante منه. أما عنوان to فيشير إلى أشياء مختلفة اعتمادًا على ما إذا كان يُستخدم في قاعدة عميل أو في قاعدة socks.

في سياق قاعدة العميل، تعني to العنوان الذي يتم قبول الطلب عليه، أي عنوان يستمع إليه خادم Dante.

في سياق قاعدة socks، تعني to عنوان الوجهة للعميل، كما هو معبر عنه في طلب socks الخاص بالعميل. أي، العنوان الذي يجب على خادم Dante الاتصال به (لجلسات TCP) أو إرسال الحزم إليه (لجلسات UDP) نيابة عن العميل.

يتم تقييم كلتا المجموعتين من القواعد على أساس "أفضل تطابق هو الأول". هذا يعني أن القاعدة الأولى المطابقة لعميل معين أو طلب socks هي القاعدة التي سيتم استخدامها.

بالإضافة إلى العناوين، توجد مجموعة من الكلمات المفتاحية الاختيارية التي يمكن تقديمها. هناك شكلان من الكلمات المفتاحية: الشروط والإجراءات. لكل قاعدة، يتم التحقق من جميع الشروط وإذا تطابقت مع الطلب، يتم تنفيذ جميع الإجراءات.

قائمة كلمات المفتاح الشرطية هي: clientcompatibility، clientmethod، command، from، group، socksmethod، protocol، proxyprotocol، to، user.

قائمة كلمات المفتاح الإجرائية هي: bandwidth، libwrap، log، session، redirect، timeout.connect، timeout.negotiate، timeout.io، timeout.tcp_fin_wait، و udp.portrange.

تنسيق ومحتوى الكلمة المفتاحية كما هي مستخدمة في قواعد العميل أو قواعد socks متطابق، ولكن قواعد العميل يمكن أن تحتوي فقط على مجموعة فرعية من الكلمات المفتاحية التي قد تحتوي عليها قواعد socks.

ROUTES

يتم تحديد المسارات باستخدام الكلمة المفتاحية route. داخل زوج من الأقواس المعقوفة ({})، تتحكم مجموعة من الكلمات المفتاحية في سلوك المسار. راجع socks.conf(5) للحصول على وصف. يُستخدم هذا لتنفيذ ما يسمى بـ "سلسلة الخوادم" (server-chaining)، حيث يتصل خادم socks بخادم socks آخر أعلى منه في التسلسل.

تركيب هذه المسارات هو نفس تركيب المسارات المستخدمة بواسطة العميل. يرجى مراجعة socks.conf(5) للحصول على معلومات حول تركيب المسارات.

ومع ذلك، هناك بعض الأمور الخاصة التي يجب الانتباه إليها فيما يتعلق بسلسلة الخوادم والمسارات المحددة للخادم:

في الوقت الحالي، لا تدعم سلسلة الخوادم إلا أمر tcp connect.
إذا حدد المسار أنه يجب تقديم طريقة اسم المستخدم/كلمة المرور إلى الخادم الوكيل الأعلى، فسوف يقوم Dante بتمرير اسم المستخدم/كلمة المرور المستلمة من العميل الخاص به إلى الخادم الوكيل الأجنبي الأعلى، مما يعني أن الخادم الوكيل الأعلى سيتلقى اسم المستخدم وكلمة المرور الخاصين بالمستخدم كنص عادي من Dante.
في الوقت الحالي، لا تتوسع سلسلة الخوادم بشكل جيد في Dante ولا ينبغي استخدامها لأي شيء بخلاف الأحمال الدنيا للعملاء.
