SOAP::Lite(3) وثائق مساهمة من المستخدم في Perl SOAP::Lite(3)

الاسم

SOAP::Lite - حزمة أدوات خدمات الويب في Perl

الوصف

SOAP::Lite هي مجموعة من وحدات Perl توفر واجهة بسيطة وخفيفة الوزن لبروتوكول الوصول إلى الكائنات البسيط (SOAP) على جانب العميل والخادم.

تحذير إصدار Perl

اعتبارًا من الإصدار SOAP::Lite version 1.05، لن يتم دعم أي إصدارات Perl قبل 5.8.

SOAP::Lite 0.71 سيكون آخر إصدار من SOAP::Lite يعمل على Perl 5.005

ستتطلب الإصدارات المستقبلية من SOAP::Lite على الأقل Perl 5.6.0

إذا لم يكن لديك الوقت لترقية Perl الخاص بك، يجب أن تفكر في ذلك الآن.

الأساليب

جميع أساليب الوصول تعيد القيمة الحالية عند استدعائها بدون وسائط، بينما تعيد مرجع الكائن نفسه عند استدعائها بقيمة جديدة. هذا يسمح بتسلسل استدعاءات سمة الضبط.

new(أزواج مفتاح/قيمة اختيارية)
$client = SOAP::Lite->new(proxy => $endpoint)

الباني. يمكن تهيئة العديد من أساليب الوصول المحددة هنا عند الإنشاء عن طريق توفير اسمها كمفتاح، متبوعًا بالقيمة المطلوبة. المثال يوفر القيمة لعنصر الوكيل للعميل.

transport(كائن نقل اختياري)
$transp = $client->transport( );

يحصل على أو يضبط كائن النقل المستخدم لإرسال/استقبال رسائل SOAP.

انظر SOAP::Transport للتفاصيل.

serializer(كائن محول اختياري)
$serial = $client->serializer( )

يحصل على أو يضبط كائن المحول المستخدم لإنشاء رسائل XML.

انظر SOAP::Serializer للتفاصيل.

packager(كائن تعبئة اختياري)
$packager = $client->packager( )

يوفر الوصول إلى كائن "SOAP::Packager" الذي يستخدمه العميل لإدارة استخدام المرفقات. عامل التعبئة الافتراضي هو عامل تعبئة MIME، ولكن ما لم تحدد أجزاء لإرسالها، فلن يتم إجراء تنسيق MIME.

انظر أيضًا: SOAP::Packager.

proxy(نقطة نهاية، وسائط إضافية اختيارية)
$client->proxy('http://soap.xml.info/ endPoint');

الوكيل هو الخادم أو نقطة النهاية التي سيتصل بها العميل. تسمح هذه الطريقة بضبط نقطة النهاية، بالإضافة إلى أي معلومات إضافية قد تحتاجها كائن النقل عند الاتصال بالطلب.

هذه الطريقة هي في الواقع اسم مستعار لطريقة الوكيل الخاصة بـ SOAP::Transport. إنها نفس كتابة:

$client->transport( )->proxy(...arguments);

يمكن تمرير معلمات إضافية إلى proxy() - انظر أدناه.

compress_threshold
انظر COMPRESSION في HTTP::Transport.

خيارات HTTP(S) هي نفس خيارات طريقة new() الخاصة بـ LWP::UserAgent.

الخيار الشائع هو إنشاء مثيل لـ HTTP::Cookies وتمريره كخيار cookie_jar:

my $cookie_jar = HTTP::Cookies->new()
$client->proxy('http://www.example.org/webservice',
   cookie_jar => $cookie_jar,
);

endpoint(عنوان نقطة نهاية جديد اختياري)
$client->endpoint('http://soap.xml.info/ newPoint')

قد يكون من الأفضل تعيين نقطة نهاية جديدة دون العمل الإضافي لفحص العنوان الجديد لمعلومات البروتوكول والتحقق من تحميل رمز الدعم وتوفره. تسمح هذه الطريقة للمستدعي بتغيير نقطة النهاية التي تم تعيين العميل حاليًا للاتصال بها، دون إعادة تحميل رمز النقل ذي الصلة. لاحظ أنه يجب استدعاء طريقة الوكيل قبل استخدام هذه الطريقة.

default_ns($uri)
يضبط النطاق الافتراضي للطلب على URI المحدد. هذا يتجاوز أي إعلان نطاق اسم سابق قد تم تعيينه باستخدام استدعاء سابق لـ ns() أو default_ns(). يتسبب تعيين النطاق الافتراضي في تسلسل العناصر بدون بادئة نطاق اسم، مثل هذا: 
<soap:Envelope>
  <soap:Body>
    <myMethod xmlns="http://www.someuri.com">
      <foo />
    </myMethod>
  </soap:Body>
</soap:Envelope>

تم الإبلاغ عن أن بعض خدمات الويب .NET تتطلب هذه الأيقونة لاسم نطاق XML.

ns($uri,$prefix=undef)
يضبط URI واسم النطاق، وبشكل اختياري بادئة اسم النطاق، للطلب إلى القيم المحددة. هذا يتجاوز أي إعلان نطاق اسم سابق قد تم تعيينه باستخدام استدعاء سابق لـ ns() أو default_ns().

إذا لم يتم تحديد بادئة، فسيتم إنشاء واحدة لك تلقائيًا. يتسبب تعيين اسم النطاق في تسلسل العناصر مع بادئة نطاق اسم معلنة، مثل هذا:

<soap:Envelope>
  <soap:Body>
    <my:myMethod xmlns:my="http://www.someuri.com">
      <my:foo />
    </my:myMethod>
  </soap:Body>
</soap:Envelope>
use_prefix(boolean)
مهمل. استخدم الدوال ns() و "default_ns" الموصوفة أعلاه.

اختصار لـ "serializer->use_prefix()". هذا يتيح لك تشغيل/إيقاف استخدام بادئة نطاق اسم للعناصر الفرعية لـ العنصر /Envelope/Body. الافتراضي هو 'true'.

عند تعيين use_prefix إلى 'true'، سيبدو XML المسلسل كالتالي:

<SOAP-ENV:Envelope ...attributes skipped>
  <SOAP-ENV:Body>
    <namesp1:mymethod xmlns:namesp1="urn:MyURI" />
  </SOAP-ENV:Body>
</SOAP-ENV:Envelope>

عند تعيين use_prefix إلى 'false'، سيبدو XML المسلسل كالتالي:

<SOAP-ENV:Envelope ...attributes skipped>
  <SOAP-ENV:Body>
    <mymethod xmlns="urn:MyURI" />
  </SOAP-ENV:Body>
</SOAP-ENV:Envelope>

تم الإبلاغ عن أن بعض خدمات الويب .NET تتطلب هذه الأيقونة لاسم نطاق XML.

soapversion(optional قيمة)

يجب أن تكون القيمة إما 1.1 أو 1.2.

هذه الطريقة هي اختصار لـ:

يحصل على أو يضبط بادئة نطاق الاسم لنطاق SOAP. الافتراضي هو SOAP.

البادئة نفسها ليس لها معنى، ولكن قد يرغب التطبيقات في اختيار واحدة بشكل صريح لتمييز إصدارات مختلفة من SOAP أو ما شابه ذلك.

هذه الطريقة هي اختصار لـ:

يحصل على أو يضبط بادئة نطاق الاسم لنطاق قواعد التشفير. القيمة الافتراضية هي SOAP-ENC.

على الرغم من أنه قد يبدو عملية غير ضرورية لتعيين قيمة غير ذات صلة بالرسالة، مثل تسميات نطاق الاسم لـ URNs الخاصة بالغلاف والتشفير، فإن القدرة على تعيين هذه التسميات بشكل صريح يمكن أن تكون مساعدة كبيرة في تمييز الرسائل وتصحيحها على جانب الخادم من العمليات.

typelookup

uri(service محدد)
مهمل - تم إهمال الدالة "uri" لتوفير مخطط تسمية أكثر بديهية للدوال التي تعين نطاقات الأسماء. في المستقبل، سيُطلب منك استخدام إما الدوال ns() أو default_ns() بدلاً من uri(). 
$client->uri($service_uri);

هذه الطريقة هي اختصار لـ:

$client->serializer->uri(service);

URI المرتبط بهذا الواجهة على كائن العميل هو محدد الخدمة للطلب، وغالبًا ما يتم تشفيره للطلبات المستندة إلى HTTP كرأس SOAPAction. بينما قد تبدو الأسماء مربكة، فإن هذه الطريقة لا تحدد نقطة النهاية نفسها. في معظم الظروف، يشير "uri" إلى نطاق الاسم المستخدم للطلب.

في كثير من الأحيان، قد تبدو القيمة مثل عنوان URL صالح. على الرغم من ذلك، لا يجب أن تشير إلى مورد موجود (وغالبًا لا تفعل ذلك). تقوم هذه الطريقة بتعيين واسترداد هذه القيمة من الكائن. لاحظ أنه لا يتم تشغيل أي كود نقل بواسطة هذا لأنه ليس له تأثير مباشر على نقل الكائن.

multirefinplace(boolean)
$client->multirefinplace(1);

هذه الطريقة هي اختصار لـ:

$client->serializer->multirefinplace(boolean);

يتحكم في كيفية معالجة المُسلسل للقيم التي لها مراجع متعددة لها. تذكر من فصول SOAP السابقة أن القيمة قد يتم تمييزها بمعرف، ثم الإشارة إليها في أماكن متعددة. عندما يكون هذا هو الحال بالنسبة لقيمة، فإن الافتراضي للمُسلسل هو وضع عنصر البيانات في الجزء العلوي من الرسالة، مباشرة بعد علامة الفتح للمواصفات الخاصة بالطريقة. يتم تسلسله ككيان مستقل بمعرف تتم الإشارة إليه في الأماكن ذات الصلة لاحقًا. إذا تم استخدام هذه الطريقة لتعيين قيمة صحيحة، فإن السلوك مختلف. عندما تكون سمة multirefinplace صحيحة، يتم تسلسل البيانات في المكان الأول الذي يشير إليها، بدلاً من عنصر منفصل أعلى في الجسم. هذا أكثر إيجازًا ولكنه قد يكون أصعب في القراءة أو التتبع في بيئة تصحيح.

f method ولكنها لا تتناسب مع المجموعة التي تليها مباشرة:

call(arguments)
$client->call($method => @arguments);

كما تم توضيحه في الفصول السابقة، يمكن لكائنات عميل "SOAP::Lite" إدارة الاستدعاءات البعيدة باستخدام الإرسال التلقائي مع بعض الميزات الأكثر تطوراً في Perl. يتم استخدام `call` عندما يرغب التطبيق في درجة أكبر من التحكم في تفاصيل الاستدعاء نفسه. قد يتم بناء الدالة من كائن SOAP::Data، للسماح بالتحكم الكامل في مساحة الاسم المرتبطة بالوسم، بالإضافة إلى سمات أخرى مثل الترميز. هذا مهم أيضاً لاستدعاء الدوال التي تحتوي على أحرف غير مسموح بها في أسماء دوال Perl، مثل A.B.C.

الأربع دوال التالية المستخدمة في فئة "SOAP::Lite" موجهة للتعامل مع أنواع الأحداث التي يمكن أن تحدث أثناء دورة حياة الرسالة. كل منها يقوم بإعداد رد اتصال للحدث المطلوب:

on_action(callback)
$client->on_action(sub { qq("$_[0]") });

يتم تشغيلها عندما يقوم كائن النقل بإعداد رأس SOAPAction لاستدعاء قائم على HTTP. الافتراضي هو تعيين الرأس إلى السلسلة، `uri#method`، حيث URI هي القيمة التي تم تعيينها بواسطة الدالة `uri` الموصوفة سابقاً، و `method` هو اسم الدالة التي يتم استدعاؤها. عند استدعاء الروتين المشار إليه (أو الإغلاق، إذا تم تحديده كما في المثال) يتم تمرير وسيطتين له، `uri` و `method`، بهذا الترتيب.

تتوقع خدمات الويب .NET عادةً "/" كفاصل بين "uri" و "method". لتغيير سلوك SOAP::Lite لاستخدام `uri/method` كرأس SOAPAction، استخدم الكود التالي:

$client->on_action( sub { join '/', @_ } );
on_fault(callback)
$client->on_fault(sub { popup_dialog($_[1]) });

يتم تشغيلها عندما يؤدي استدعاء دالة إلى استجابة خطأ من الخادم. عند استدعائها، تكون قائمة الوسائط أولاً هي كائن العميل نفسه، يليها الكائن الذي يغلف الخطأ. في المثال، يتم تمرير كائن الخطأ (بدون كائن العميل) إلى دالة واجهة رسومية افتراضية تعرض مربع حوار خطأ مع نص الخطأ المستخرج من الكائن (والذي سنغطيه قريبًا ضمن دوال SOAP::SOM).

on_nonserialized(callback)
$client->on_nonserialized(sub { die "$_[0]?!?" });

في بعض الأحيان، قد يتم تقديم بيانات إلى المسؤول عن الترميز لا يمكنه تحويلها إلى XML مناسب لـ SOAP؛ على سبيل المثال، إذا نتج عن خطأ في البرنامج تمرير مرجع كود أو شيء مشابه كوسيط لدالة. عندما يحدث ذلك، يتم تنشيط رد الاتصال هذا، مع وسيط واحد. هذه الوسيطة هي عنصر البيانات الذي لم يتم فهمه. سيكون هو الوسيط الوحيد. إذا عاد الروتين، يتم لصق القيمة المُرجعة في الرسالة كترميز. بشكل عام، يكون الخطأ هو المطلوب، وهذا الرد يسمح بالتحكم في الإشارة إلى ذلك الخطأ.

on_debug(callback)
$client->on_debug(sub { print @_ });

مهمل. استخدم المرافق العالمية +debug و +trace الموصوفة في SOAP::Trace

لاحظ أن هذه الدالة لن تعمل كما هو متوقع: بدلاً من التأثير على سلوك التصحيح للكائن الذي تم استدعاؤه عليه، فإنها ستؤثر عالمياً على سلوك التصحيح لجميع كائنات هذا الصف.

كتابة عميل SOAP

يرشدك هذا الفصل إلى كتابة عميل SOAP من خلال الأمثلة.

الخدمة التي سيتم الوصول إليها هي نسخة مبسطة من برنامج "Hello World" المعروف. تقبل وسيطين، الاسم الأول واسم العائلة، وتعيد "Hello $given_name $name".

سنستخدم "Martin Kutter" كاسم للاستدعاء، لذا فإن جميع المتغيرات ستطبع الرسالة التالية عند النجاح:

Hello Martin Kutter!

أنماط رسائل SOAP

هناك ثلاثة أنواع شائعة (ونوع واحد أقل شيوعًا) من رسائل SOAP.

تتعلق هذه بالنمط (معلمات موضعية مقابل مستندات رسائل محددة) والترميز (كما هو مقابل مُعرّف بنوع).

أنماط الرسائل المختلفة هي:

  • rpc/encoded

    معلمات مُعرّفة بنوع، موضعية. تستخدم على نطاق واسع في لغات البرمجة النصية. يتم تضمين نوع الوسائط في الرسالة. قد يتم ترميز المصفوفات وما شابه ذلك باستخدام قواعد ترميز SOAP (أو غيرها).

  • rpc/literal

    كما هو، معلمات موضعية. يتم تحديد نوع الوسائط بواسطة تعريف واجهة تم تبادله مسبقًا.

  • document/encoded

    مستند رسالة مع عناصر مُعرّفة بنوع. نادر الاستخدام.

  • document/literal

    مستند رسالة مع عناصر كما هي. يتم تحديد مواصفات الرسالة وأنواع العناصر بواسطة تعريف واجهة تم تبادله مسبقًا.

اعتبارًا من عام 2008، أصبح document/literal هو النمط السائد لرسائل SOAP. لا يزال rpc/literal و rpc/encoded قيد الاستخدام، خاصة مع لغات البرمجة النصية، بينما لا يتم استخدام document/encoded تقريبًا على الإطلاق.

سترى عملاء لأنماط رسائل SOAP rpc/encoded و document/literal في هذا القسم.

تنفيذات أمثلة

RPC/ENCODED

rpc/encoded هو الأكثر شيوعًا مع لغات البرمجة النصية مثل perl، php، و python بدون استخدام WSDL. عادةً ما تبدو أوصاف الدالة كما يلي:

Method: sayHello(string, string)
Parameters:
   name: string
   givenName: string

عادةً ما يعني وصف كهذا أنه يمكنك استدعاء دالة باسم "sayHello" مع وسيطتين موضعيتين، "name" و "givenName"، وكلاهما عبارة عن سلاسل نصية.

الرسالة المقابلة لهذا الوصف تبدو شيئًا كهذا:

<sayHello xmlns="urn:HelloWorld">
  <s-gensym01 xsi:type="xsd:string">Kutter</s-gensym01>
  <s-gensym02 xsi:type="xsd:string">Martin</s-gensym02>
</sayHello>

يمكن استخدام أي أسماء وسوم XML بدلاً من "s-gensym01" - الوسائط موضعية، وليس لأسماء الوسوم أي معنى.

يتم تنفيذ عميل ينتج مثل هذا الاستدعاء كما يلي:

use SOAP::Lite;
my $soap = SOAP::Lite->new( proxy => 'http://localhost:81/soap-wsdl-test/helloworld.pl');
$soap->default_ns('urn:HelloWorld');
my $som = $soap->call('sayHello', 'Kutter', 'Martin');
die $som->faultstring if ($som->fault);
print $som->result, "\n";

يمكنك بالطبع استخدام سطر واحد أيضًا...

في بعض الأحيان، يتم وصف واجهات rpc/encoded بتعريفات WSDL. يبدو WSDL الذي يقبل وسيطات "مسماة" مع rpc/encoded كما يلي:

<definitions xmlns:soap="http://schemas.xmlsoap.org/wsdl/soap/"
  xmlns:s="http://www.w3.org/2001/XMLSchema"
  xmlns:s0="urn:HelloWorld"
  targetNamespace="urn:HelloWorld"
  xmlns="http://schemas.xmlsoap.org/wsdl/">
  <types>
    <s:schema targetNamespace="urn:HelloWorld">
    </s:schema>
  </types>
  <message name="sayHello">
    <part name="name" type="s:string" />
    <part name="givenName" type="s:string" />
  </message>
  <message name="sayHelloResponse">
    <part name="sayHelloResult" type="s:string" />
  </message>
  <portType name="Service1Soap">
    <operation name="sayHello">
      <input message="s0:sayHello" />
      <output message="s0:sayHelloResponse" />
    </operation>
  </portType>
  <binding name="Service1Soap" type="s0:Service1Soap">
    <soap:binding transport="http://schemas.xmlsoap.org/soap/http"
        style="rpc" />
    <operation name="sayHello">
      <soap:operation soapAction="urn:HelloWorld#sayHello"/>
      <input>
        <soap:body use="encoded"
          encodingStyle="http://schemas.xmlsoap.org/soap/encoding/"/>
      </input>
      <output>
        <soap:body use="encoded"
          encodingStyle="http://schemas.xmlsoap.org/soap/encoding/"/>
      </output>
    </operation>
  </binding>
  <service name="HelloWorld">
    <port name="HelloWorldSoap" binding="s0:Service1Soap">
      <soap:address location="http://localhost:81/soap-wsdl-test/helloworld.pl" />
    </port>
  </service>
</definitions>

الرسالة المقابلة لهذا المخطط تبدو كما يلي:

<sayHello xmlns="urn:HelloWorld">
  <name xsi:type="xsd:string">Kutter</name>
  <givenName xsi:type="xsd:string">Martin</givenName>
</sayHello>

يبدو عميل خدمة الويب الذي يستخدم هذا المخطط كما يلي:

use SOAP::Lite;
my $soap = SOAP::Lite->service("file:say_hello_rpcenc.wsdl");
eval { my $result = $soap->sayHello('Kutter', 'Martin'); };
if ($@) {
    die $@;
}
print $som->result();

يمكنك بالطبع أيضًا استخدام سطر واحد التالي:

perl -MSOAP::Lite -e 'print SOAP::Lite->service("file:say_hello_rpcenc.wsdl")\
  ->sayHello('Kutter', 'Martin'), "\n";'

يبدو عميل خدمة الويب (بدون وصف خدمة) كما يلي.

use SOAP::Lite;
my $soap = SOAP::Lite->new( proxy => 'http://localhost:81/soap-wsdl-test/helloworld.pl');
$soap->default_ns('urn:HelloWorld');
my $som = $soap->call('sayHello',
   SOAP::Data->name('name')->value('Kutter'),
   SOAP::Data->name('givenName')->value('Martin')
);
die $som->faultstring if ($som->fault);
print $som->result, "\n";

DOCUMENT/LITERAL

SOAP web services using the document/literal message encoding are usually described by some Web Service Definition. Our web service has the following WSDL description:

<definitions xmlns:soap="http://schemas.xmlsoap.org/wsdl/soap/"
   xmlns:s="http://www.w3.org/2001/XMLSchema"
   xmlns:s0="urn:HelloWorld"
   targetNamespace="urn:HelloWorld"
   xmlns="http://schemas.xmlsoap.org/wsdl/">
  <types>
    <s:schema targetNamespace="urn:HelloWorld">
      <s:element name="sayHello">
        <s:complexType>
          <s:sequence>
             <s:element minOccurs="0" maxOccurs="1" name="name" type="s:string" />
              <s:element minOccurs="0" maxOccurs="1" name="givenName" type="s:string" nillable="1" />
          </s:sequence>
         </s:complexType>
       </s:element>
       <s:element name="sayHelloResponse">
         <s:complexType>
           <s:sequence>
             <s:element minOccurs="0" maxOccurs="1" name="sayHelloResult" type="s:string" />
           </s:sequence>
       </s:complexType>
     </s:element>
   </types>
   <message name="sayHelloSoapIn">
     <part name="parameters" element="s0:sayHello" />
   </message>
   <message name="sayHelloSoapOut">
     <part name="parameters" element="s0:sayHelloResponse" />
   </message>
   <portType name="Service1Soap">
     <operation name="sayHello">
       <input message="s0:sayHelloSoapIn" />
       <output message="s0:sayHelloSoapOut" />
     </operation>
   </portType>
   <binding name="Service1Soap" type="s0:Service1Soap">
     <soap:binding transport="http://schemas.xmlsoap.org/soap/http"
         style="document" />
     <operation name="sayHello">
       <soap:operation soapAction="urn:HelloWorld#sayHello"/>
       <input>
         <soap:body use="literal" />
       </input>
       <output>
         <soap:body use="literal" />
       </output>
     </operation>
   </binding>
   <service name="HelloWorld">
     <port name="HelloWorldSoap" binding="s0:Service1Soap">
       <soap:address location="http://localhost:80//helloworld.pl" />
     </port>
   </service>
</definitions>

The XML message (inside the SOAP Envelope) look like this:

<sayHello xmlns="urn:HelloWorld">
  <name>Kutter</name>
  <givenName>Martin</givenName>
</sayHello>
<sayHelloResponse>
  <sayHelloResult>Hello Martin Kutter!</sayHelloResult>
</sayHelloResponse>

You can call this web service with the following client code:

 use SOAP::Lite;
 my $soap = SOAP::Lite->new( proxy => 'http://localhost:80/helloworld.pl');
 $soap->on_action( sub { "urn:HelloWorld#sayHello" });
 $soap->autotype(0);
 $soap->default_ns('urn:HelloWorld');
 my $som = $soap->call("sayHello",
    SOAP::Data->name('name')->value( 'Kutter' ),
    SOAP::Data->name('givenName')->value('Martin'),
);
 die $som->fault->{ faultstring } if ($som->fault);
 print $som->result, "\n";

الاختلافات بين التطبيقات

You may have noticed that there's little difference between the rpc/encoded, rpc/literal and the document/literal example's implementation. In fact, from SOAP::Lite's point of view, the only differences between rpc/literal and document/literal that parameters are always named.

In our example, the rpc/encoded variant already used named parameters (by using two messages), so there's no difference at all.

You may have noticed the somewhat strange idiom for passing a list of named parameters in the rpc/literal example:

my $som = $soap->call('sayHello', SOAP::Data->name('parameters')->value(
   \SOAP::Data->value([
       SOAP::Data->name('name')->value( 'Kutter' ),
       SOAP::Data->name('givenName')->value('Martin'),
   ]))
);

While SOAP::Data provides full control over the XML generated, passing hash-like structures require additional coding.

المرفقات

"SOAP::Lite" features support for the SOAP with Attachments specification. Currently, SOAP::Lite only supports MIME based attachments. DIME based attachments are yet to be fully functional.

EXAMPLES

Client sending an attachment

"SOAP::Lite" clients can specify attachments to be sent along with a request by using the SOAP::Lite::parts() method, which takes as an argument an ARRAY of "MIME::Entity"'s.

use SOAP::Lite;
use MIME::Entity;
my $ent = build MIME::Entity
  Type        => "image/gif",
  Encoding    => "base64",
  Path        => "somefile.gif",
  Filename    => "saveme.gif",
  Disposition => "attachment";
my $som = SOAP::Lite
  ->uri($SOME_NAMESPACE)
  ->parts([ $ent ])
  ->proxy($SOME_HOST)
  ->some_method(SOAP::Data->name("foo" => "bar"));

Client retrieving an attachment

A client accessing attachments that were returned in a response by using the SOAP::SOM::parts() accessor.

use SOAP::Lite;
use MIME::Entity;
my $soap = SOAP::Lite
  ->uri($NS)
  ->proxy($HOST);
my $som = $soap->foo();
foreach my $part (${$som->parts}) {
  print $part->stringify;
}

Server receiving an attachment

Servers, like clients, use the SOAP::SOM module to access attachments transmitted to it.

package Attachment;
use SOAP::Lite;
use MIME::Entity;
use strict;
use vars qw(@ISA);
@ISA = qw(SOAP::Server::Parameters);
sub someMethod {
  my $self = shift;
  my $envelope = pop;
  foreach my $part (@{$envelope->parts}) {
    print "AttachmentService: attachment found! (".ref($part).")\n";
  }
  # do something
}

Server responding with an attachment

Servers wishing to return an attachment to the calling client need only return "MIME::Entity" objects along with SOAP::Data elements, or any other data intended for the response.

package Attachment;
use SOAP::Lite;
use MIME::Entity;
use strict;
use vars qw(@ISA);
@ISA = qw(SOAP::Server::Parameters);
sub someMethod {
  my $self = shift;
  my $envelope = pop;
  my $ent = build MIME::Entity
  'Id'          => "<1234>",
  'Type'        => "text/xml",
  'Path'        => "some.xml",
  'Filename    => "some.xml",
  'Disposition' => "attachment";
  return SOAP::Data->name("foo" => "blah blah blah"),$ent;
}
