NAME

SoRotation — transformation node representing an arbitrary rotation

SYNOPSIS

      #include <Coin/SoRotation.h>

Inheritance diagram:

    SoNode
      ∟ SoTransform
        ∟ SoRotation

Detailed Description

This node represents an arbitrary rotation. The rotation is specified using an SbRotation value, which can be set using any of the standard methods (e.g., using an axis and an angle, or using Euler angles).

The rotation is applied in local object space. It is applied after any scaling and before any translation.

The default rotation is the identity rotation (no rotation).

To be useful, this node must be placed within a traversal path.

The following example demonstrates how to create and use an SoRotation node:

    // Create a rotation node
    SoRotation *myRotation = new SoRotation;
    // Set it to rotate 90 degrees around the Z axis
    myRotation->rotation.setValue(SbVec3f(0, 0, 1), M_PI/2.0f);
    // Add it to the scene graph
    root->addChild(myRotation);

Member Data Documentation

SoSFRotation SoRotation::rotation

Rotation specification. Defaults to no rotation at all. See the SbRotation documentation for instructions on how to set the value of this field.

Note that there is one very common mistake that is easy to make when setting the value of an SoSFRotation field, and that is to inadvertently use the wrong SbRotation constructor. This example should clarify the problem:

    mytransformnode->rotation.setValue(0, 0, 1, 1.5707963f);

The programmer clearly tries to set a PI/2 rotation around the Z-axis, but this will fail, as the SbRotation constructor invoked above is the one that takes as arguments the 4 floats of a quaternion. What the programmer almost certainly wanted to do was to use the SbRotation constructor that takes a rotation vector and a rotation angle, which is invoked like this:

    mytransformnode->rotation.setValue(SbVec3f(0, 0, 1), 1.5707963f);

Another common problem is to set the rotation value to exactly 0.0, while wanting to store just a rotation angle in the field: rotations are internally handled as quaternions, and when converting from an angle and a rotation value to a quaternion representation, the information about the angle "gets lost" if there is no actual rotation.
