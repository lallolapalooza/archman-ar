بيئة الأوامر

نظرًا لأن متغيرات البيئة يمكن أن تؤثر على سلوك البرنامج، فإن sudoers يوفر وسيلة لتقييد المتغيرات التي يتم وراثتها من بيئة المستخدم بواسطة الأمر المراد تشغيله. هناك طريقتان مميزتان يمكن لـ sudoers التعامل بهما مع متغيرات البيئة.

بشكل افتراضي، تكون علامة env_reset ممكّنة. هذا يتسبب في تنفيذ الأوامر ببيئة جديدة وصغيرة. في أنظمة AIX (وأنظمة Linux بدون PAM)، تتم تهيئة البيئة بمحتويات ملف /etc/environment. تتم تهيئة متغيرات البيئة HOME و MAIL و SHELL و LOGNAME و USER بناءً على المستخدم المستهدف، ويتم تعيين متغيرات SUDO_* بناءً على المستخدم المستدعي. يتم الاحتفاظ بمتغيرات إضافية، مثل DISPLAY و PATH و TERM، من بيئة المستخدم المستدعي إذا سمحت بذلك خيارات env_check أو env_keep. يتم التعامل مع عدد قليل من متغيرات البيئة بشكل خاص. إذا لم يتم الاحتفاظ بمتغيرات PATH و TERM من بيئة المستخدم، فسيتم تعيينها إلى قيم افتراضية. يتم التعامل مع LOGNAME و USER كوحدة واحدة. إذا تم الاحتفاظ بأحدهما (أو إزالته) من بيئة المستخدم، فسيتم فعل الشيء نفسه مع الآخر. هذا يتجنب بيئة غير متسقة حيث يتم تعيين أحد المتغيرات التي تصف اسم المستخدم إلى المستخدم المستدعي والآخر إلى المستخدم الهدف. يتم إزالة متغيرات البيئة التي تبدأ قيمتها بـ ‘()’ ما لم يتم مطابقة كل من الاسم والقيمة بواسطة env_keep أو env_check، حيث قد يتم تفسيرها كدوال بواسطة شل bash. قبل الإصدار 1.8.11، تم دائمًا إزالة مثل هذه المتغيرات.

إذا تم تعطيل علامة env_reset، فسيتم السماح بأي متغيرات لم يتم حظرها صراحةً بواسطة خيارات env_check و env_delete، وسيتم وراثة قيمها من العملية المستدعية. قبل الإصدار 1.8.21، تم دائمًا إزالة متغيرات البيئة التي تبدأ قيمتها بـ ‘()’. بدءًا من الإصدار 1.8.21، يتم استخدام نمط في env_delete لمطابقة دوال شل bash بدلاً من ذلك. نظرًا لأنه لا يمكن حظر جميع متغيرات البيئة التي قد تكون خطرة، يتم تشجيع استخدام سلوك env_reset الافتراضي.

قد تتضمن متغيرات البيئة المحددة بواسطة env_check أو env_delete أو env_keep حرفًا واحدًا أو أكثر من ‘*’ الذي يطابق صفرًا أو أكثر من الأحرف. لا يتم دعم أي أحرف بدل أخرى.

بشكل افتراضي، تتم مطابقة متغيرات البيئة حسب الاسم. ومع ذلك، إذا كان النمط يتضمن علامة يساوي (‘=’)، فيجب مطابقة كل من اسم المتغير وقيمته. على سبيل المثال، يمكن مطابقة دالة شل bash على النحو التالي:

env_keep += "BASH_FUNC_my_func%%=()*"

بدون اللاحقة ‘=()*’، لن يتم المطابقة، حيث لا يتم الاحتفاظ بدوال شل bash افتراضيًا.

يتم عرض القائمة الكاملة لمتغيرات البيئة التي يتم الاحتفاظ بها أو إزالتها، كما تم تعديلها بواسطة معلمات الافتراضيات العامة في sudoers، عند تشغيل sudo بواسطة root مع الخيار -V. تختلف قائمة متغيرات البيئة المراد إزالتها بناءً على نظام التشغيل الذي يعمل عليه sudo.

قد تؤثر الإعدادات الأخرى على بيئة الأوامر:

  • خيارات sudoers مثل always_set_home و secure_path و set_logname و set_home و setenv.
  • علامات الأوامر، مثل SETENV و NOSETENV. لاحظ أن SETENV ضمني إذا كان الأمر المطابق هو ALL.
  • خيارات sudo، مثل -E و -i.

على الأنظمة التي تدعم PAM حيث تكون وحدة pam_env ممكّنة لـ sudo، قد يتم دمج متغيرات بيئة PAM في البيئة. إذا كان المتغير في بيئة PAM موجودًا بالفعل في بيئة المستخدم، فسيتم استبدال القيمة فقط إذا لم يتم الاحتفاظ بالمتغير بواسطة sudoers. عند تمكين env_reset، تتفوق المتغيرات المحفوظة من بيئة المستخدم المستدعي بواسطة قائمة env_keep على تلك الموجودة في بيئة PAM. عند تعطيل env_reset، تتفوق المتغيرات الموجودة في بيئة المستخدم المستدعي على تلك الموجودة في بيئة PAM ما لم تتطابق مع نمط في قائمة env_delete.

يقوم الرابط الديناميكي في معظم أنظمة التشغيل بإزالة المتغيرات التي يمكنها التحكم في الربط الديناميكي من بيئة الملفات التنفيذية ذات معرف المستخدم المعين (set-user-ID)، بما في ذلك sudo. اعتمادًا على نظام التشغيل، قد يشمل ذلك _RLD* و DYLD_* و LD_* و LDR_* و LIBPATH و SHLIB_PATH وغيرها. يتم إزالة هذه الأنواع من المتغيرات من البيئة قبل أن يبدأ sudo التنفيذ حتى، وبسبب ذلك، لا يمكن لـ sudo الاحتفاظ بها.

كحالة خاصة، إذا تم تحديد الخيار -i (تسجيل الدخول الأولي)، فسوف يقوم sudoers بتهيئة البيئة بغض النظر عن قيمة env_reset. تظل متغيرات DISPLAY و PATH و TERM دون تغيير؛ يتم تعيين HOME و MAIL و SHELL و USER و LOGNAME بناءً على المستخدم الهدف. في أنظمة AIX (وأنظمة Linux بدون PAM)، يتم تضمين محتويات /etc/environment أيضًا. تتم إزالة جميع متغيرات البيئة الأخرى ما لم يسمح بذلك env_keep أو env_check، الموضحة أعلاه.

أخيرًا، يتم تطبيق ملفات restricted_env_file و env_file، إذا كانت موجودة. يتم تطبيق المتغيرات في restricted_env_file أولاً وهي تخضع لنفس القيود مثل بيئة المستخدم المستدعي، كما هو مفصل أعلاه. يتم تطبيق المتغيرات في env_file أخيرًا وهي غير خاضعة لهذه القيود. في كلتا الحالتين، سيتم تعيين المتغيرات الموجودة في الملفات إلى قيمها المحددة فقط إذا لم تتعارض مع متغير بيئة موجود.

صيغة ملف SUDOERS

يتكون ملف sudoers من نوعين من الإدخالات: الأسماء المستعارة (بشكل أساسي متغيرات) ومواصفات المستخدم (التي تحدد من يمكنه تشغيل ماذا).

عندما تتطابق إدخالات متعددة لمستخدم، يتم تطبيقها بالترتيب. حيث توجد مطابقات متعددة، يتم استخدام المطابقة الأخيرة (والتي ليست بالضرورة المطابقة الأكثر تحديدًا).

سيتم وصف قواعد ملف sudoers أدناه بصيغة EBNF الموسعة (Extended Backus-Naur Form). لا تيأس إذا كنت غير مألوف مع EBNF؛ فهي بسيطة جدًا، والتعريفات أدناه مشروحة.

حدود الموارد

بشكل افتراضي، يستخدم sudoers طريقة نظام التشغيل الأصلية لتعيين حدود الموارد للمستخدم الهدف. في أنظمة Linux، يتم عادةً تعيين حدود الموارد بواسطة وحدة PAM pam_limits.so. في بعض أنظمة BSD، يحدد ملف /etc/login.conf حدود الموارد للمستخدم. في أنظمة AIX، يتم تكوين حدود الموارد في ملف /etc/security/limits. إذا لم تكن هناك آلية نظام لتعيين حدود موارد لكل مستخدم، فسيتم تشغيل الأمر بنفس الحدود التي يمتلكها المستخدم المستدعي. الاستثناء الوحيد لهذا هو حجم ملف تفريغ النواة، والذي يتم تعيينه بواسطة sudoers إلى 0 افتراضيًا. يجعل تعطيل تفريغ النواة افتراضيًا من الممكن تجنب مشاكل الأمان المحتملة حيث يتم التعامل مع ملف النواة كمدخل موثوق به.

يحدد مواصفات المستخدم الأوامر التي قد يقوم المستخدم بتشغيلها (وكمستخدم) على مضيفين محددين. بشكل افتراضي، يتم تشغيل الأوامر بصفتك root (ما لم يتم تعيين runas_default إلى قيمة مختلفة) ولكن يمكن أيضًا تغيير ذلك على أساس كل أمر.

يتكون الهيكل الأساسي لمواصفات المستخدم من "من أين = (بصفتك) ماذا". دعنا نقسم ذلك إلى أجزائه المكونة:

مواصفات التشغيل (Runas_Spec)

يحدد Runas_Spec المستخدم و/أو المجموعة التي يمكن تشغيل الأمر بصفتها. تتكون Runas_Spec محددة بالكامل من قائمتين Runas_List (كما هو موضح أعلاه) مفصولتين بنقطتين رأسيتين (":") ومغلقتين بين قوسين. تشير قائمة Runas_List الأولى إلى المستخدمين الذين يمكن تشغيل الأمر بصفتهم عبر الخيار -u. تحدد الثانية قائمة بالمجموعات التي يمكن تحديدها عبر الخيار -g (بالإضافة إلى أي من مجموعات المستخدم الهدف). إذا تم تحديد كلتا قائمتي Runas_List، يمكن تشغيل الأمر بأي مجموعة من المستخدمين والمجموعات المدرجة في قوائم Runas_List الخاصة بها. إذا تم تحديد الأولى فقط، يمكن تشغيل الأمر بصفتك أي مستخدم في القائمة، وبشكل اختياري، مع أي مجموعة ينتمي إليها المستخدم الهدف. إذا كانت قائمة Runas_List الأولى فارغة ولكن الثانية محددة، يمكن تشغيل الأمر بصفتك المستخدم المستدعي مع تعيين المجموعة إلى أي منها مدرج في قائمة Runas_List. إذا كانت كلتا قائمتي Runas_List فارغتين، يمكن تشغيل الأمر فقط بصفتك المستخدم المستدعي ويجب أن تكون المجموعة، إذا تم تحديدها، عضوًا فيها المستخدم المستدعي. إذا لم يتم تحديد Runas_Spec، يمكن تشغيل الأمر فقط بصفتك المستخدم runas_default (افتراضيًا root) ويجب أن تكون المجموعة، إذا تم تحديدها، عضوًا فيها المستخدم runas_default.

تحدد Runas_Spec الإعداد الافتراضي للأوامر التي تليها. هذا يعني أنه بالنسبة للإدخال:

dgb	boulder = (operator) /bin/ls, /bin/kill, /usr/bin/lprm

يمكن للمستخدم dgb تشغيل /bin/ls و /bin/kill و /usr/bin/lprm على المضيف boulder - ولكن فقط بصفتك operator. على سبيل المثال:

$ sudo -u operator /bin/ls

من الممكن أيضًا تجاوز Runas_Spec لاحقًا في الإدخال. إذا قمنا بتعديل الإدخال على هذا النحو:

dgb	boulder = (operator) /bin/ls, (root) /bin/kill, /usr/bin/lprm

الآن يُسمح للمستخدم dgb بتشغيل /bin/ls بصفتك operator، ولكن /bin/kill و /usr/bin/lprm بصفتك root.

يمكننا توسيع ذلك للسماح لـ dgb بتشغيل /bin/ls إما مع تعيين المستخدم أو المجموعة إلى operator:

dgb	boulder = (operator : operator) /bin/ls, (root) /bin/kill,\
	/usr/bin/lprm

بينما يسمح الجزء الخاص بالمجموعة من Runas_Spec للمستخدم بتشغيل الأمر بهذه المجموعة، إلا أنه لا يجبر المستخدم على القيام بذلك. إذا لم يتم تحديد مجموعة على سطر الأوامر، فسيتم تشغيل الأمر بالمجموعة المدرجة في إدخال قاعدة بيانات كلمة مرور المستخدم الهدف. ستكون الأمثلة التالية مسموحًا بها بموجب إدخال sudoers أعلاه:

$ sudo -u operator /bin/ls
$ sudo -u operator -g operator /bin/ls
$ sudo -g operator /bin/ls

في المثال التالي، قد يقوم المستخدم tcm بتشغيل الأوامر التي تصل إلى ملف جهاز المودم مع مجموعة الاتصال.

tcm	boulder = (:dialer) /usr/bin/tip, /usr/bin/cu,\
	/usr/local/bin/minicom

في هذا المثال، سيتم تعيين المجموعة فقط، وسيظل الأمر يعمل بصفتك المستخدم tcm. على سبيل المثال:

$ sudo -g dialer /usr/bin/cu

قد يكون هناك العديد من المستخدمين والمجموعات في Runas_Spec، وفي هذه الحالة قد يختار المستخدم أي مجموعة من المستخدمين والمجموعات عبر الخيارات -u و -g. في هذا المثال:

alan	ALL = (root, bin : operator, system) ALL

المستخدم alan يمكنه تشغيل أي أمر بصفتك المستخدم root أو bin، مع تعيين المجموعة بشكل اختياري إلى operator أو system.

مواصفات الخيار (Option_Spec)

قد يحتوي Cmnd على صفر أو أكثر من الخيارات المرتبطة به. قد تتكون الخيارات من تواريخ بدء و/أو انتهاء وفترات زمنية للأوامر. بمجرد تعيين خيار لـ Cmnd، ترث Cmnds اللاحقة في Cmnd_Spec_List هذا الخيار ما لم يتم تجاوزه بواسطة خيار آخر. أسماء الخيارات هي كلمات محجوزة في sudoers. هذا يعني أنه لا يمكن استخدام أي من أسماء الخيارات الصالحة (انظر أدناه) عند الإعلان عن اسم مستعار.

مواصفات التاريخ (Date_Spec)

يمكن تحديد قواعد sudoers بتاريخ بدء وانتهاء عبر إعدادات NOTBEFORE و NOTAFTER. يجب تحديد الطابع الزمني بتنسيق "زمن معمَّم" (Generalized Time) كما هو محدد في RFC 4517. التنسيق هو فعليًا 'yyyymmddHHMMSSZ' حيث تكون الدقائق والثواني اختيارية. اللاحقة 'Z' تشير إلى أن الطابع الزمني في التوقيت العالمي المنسق (UTC). من الممكن أيضًا تحديد إزاحة منطقة زمنية من UTC بالساعات والدقائق بدلاً من 'Z'. على سبيل المثال، '-0500' تتوافق مع التوقيت القياسي الشرقي في الولايات المتحدة. كتوسيع، إذا لم يتم تحديد 'Z' أو إزاحة المنطقة الزمنية، فسيتم استخدام التوقيت المحلي.

2017021408Z

مواصفات المهلة (Timeout_Spec)

يمكن أن يكون للأمر مهلة مرتبطة به. إذا انتهت المهلة قبل أن يخرج الأمر، فسيتم إنهاؤه. يمكن تحديد المهلة بتوليفات من الأيام والساعات والدقائق والثواني مع لاحقة حرف واحد غير حساسة لحالة الأحرف تشير إلى وحدة الوقت. على سبيل المثال، مهلة مدتها 7 أيام و 8 ساعات و 30 دقيقة و 10 ثوانٍ ستُكتب على النحو التالي '7d8h30m10s'. إذا تم تحديد رقم بدون وحدة، فسيتم افتراض الثواني. يمكن حذف أي من الأيام أو الدقائق أو الساعات أو الثواني. يجب أن يكون الترتيب من أكبر وحدة إلى أصغر وحدة، ولا يمكن تحديد وحدة أكثر من مرة.

القيم التالية كلها قيم مهلة صالحة: '7d8h30m10s'، '14d'، '8h30m'، '600s'، '3600'. القيم التالية غير صالحة: '12m2w1d'، '30s10m4h'، '1d2d3h'.

هذا الإعداد مدعوم فقط بالإصدار 1.8.20 أو أعلى.

مواصفات تغيير الدليل (Chdir_Spec)

يمكن تحديد دليل العمل الذي سيتم تشغيل الأمر فيه باستخدام إعداد CWD. يجب أن يكون directory اسم مسار مؤهل بالكامل يبدأ بالحرف '/' أو '~'، أو القيمة الخاصة "*". تشير القيمة "*" إلى أنه يجوز للمستخدم تحديد دليل العمل عن طريق تشغيل sudo باستخدام الخيار -D. بشكل افتراضي، يتم تشغيل الأوامر من دليل العمل الحالي للمستخدم المستدعي، ما لم يتم إعطاء الخيار -i. يتم تفسير أسماء المسارات بالشكل ~user/path/name على أنها نسبية إلى الدليل الرئيسي للمستخدم المسمى. إذا تم حذف اسم المستخدم، فسيكون المسار نسبيًا إلى الدليل الرئيسي لمستخدم التشغيل.

هذا الإعداد مدعوم فقط بالإصدار 1.9.3 أو أعلى.

مواصفات Chroot (Chroot_Spec)

EVENT LOGGING sudoers can log events in either JSON or sudo format, this section describes the sudo log format. Depending on sudoers configuration, sudoers can log events via syslog(3), to a local log file, or both. The log format is almost identical in both cases. Any control characters present in the log data are formatted in octal with a leading '#' character. For example, a horizontal tab is stored as '#011' and an embedded carriage return is stored as '#015'. In addition, space characters in the command path are stored as '#040'. Command line arguments that contain spaces are enclosed in single quotes (''). This makes it possible to distinguish multiple command line arguments from a single argument that contains spaces. Literal single quotes and backslash characters ('') in command line arguments are escaped with a backslash. Accepted command log entries Commands that sudo runs are logged using the following format (split into multiple lines for readability): date hostname progname: username : TTY=ttyname ; CHROOT=chroot ; \ PWD=cwd ; USER=runasuser ; GROUP=runasgroup ; TSID=logid ; \ ENV=env_vars COMMAND=command Where the fields are as follows: date The date the command was run. Typically, this is in the format "MMM, DD, HH:MM:SS". If logging via syslog(3), the actual date format is controlled by the syslog daemon. If logging to a file and the log_year option is enabled, the date will also include the year. hostname The name of the host sudo was run on. This field is only present when logging via syslog(3). progname The name of the program, usually sudo or sudoedit. This field is only present when logging via syslog(3). username The login name of the user who ran sudo. ttyname The short name of the terminal (e.g., "console", "tty01", or "pts/0") sudo was run on, or "unknown" if there was no terminal present. chroot The root directory that the command was run in, if one was specified. cwd The current working directory that sudo was run in. runasuser The user the command was run as. runasgroup The group the command was run as if one was specified on the command line. logid An I/O log identifier that can be used to replay the command's output. This is only present when the log_input or log_output option is enabled. env_vars A list of environment variables specified on the command line, if specified. command The actual command that was executed, including any command line arguments. Messages are logged using the locale specified by sudoers_locale, which defaults to the 'C' locale. Denied command log entries If the user is not allowed to run the command, the reason for the denial will follow the user name. Possible reasons include: user NOT in sudoers The user is not listed in the sudoers file. user NOT authorized on host The user is listed in the sudoers file but is not allowed to run commands on the host. command not allowed The user is listed in the sudoers file for the host but they are not allowed to run the specified command. 3 incorrect password attempts The user failed to enter their password after 3 tries. The actual number of tries will vary based on the number of failed attempts and the value of the passwd_tries option. a password is required The -n option was specified but a password was required. sorry, you are not allowed to set the following environment variables

CAVEATS

The sudoers file should always be edited by the visudo utility which locks the file and checks for syntax errors. If sudoers contains syntax errors, sudo may refuse to run, which is a serious problem if sudo is your only method of obtaining superuser privileges. Recent versions of sudoers will attempt to recover after a syntax error by ignoring the rest of the line after encountering an error. Older versions of sudo will not run if sudoers contains a syntax error.

When using netgroups of machines (as opposed to users), if you store fully qualified host name in the netgroup (as is usually the case), you either need to have the machine's host name be fully qualified as returned by the hostname command or use the fqdn option in sudoers.
