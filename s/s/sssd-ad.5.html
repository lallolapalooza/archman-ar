ad_gpo_access_control (string)

\n
This option specifies the operation mode for GPO-based\n access control functionality: whether it operates in disabled mode, enforcing\n mode, or permissive mode. Please note that the “access_provider”\n option must be explicitly set to “ad” in order for this option\n to have an effect.\n

GPO-based access control functionality uses GPO policy settings to\n determine whether or not a particular user is allowed to logon to the host.\n For more information on the supported policy settings please refer to the\n “ad_gpo_map” options.

\n

Please note that current version of SSSD does not support Active\n Directory's built-in groups. Built-in groups (such as Administrators with\n SID S-1-5-32-544) in GPO access control rules will be ignored by SSSD. See\n upstream issue tracker https://github.com/SSSD/sssd/issues/5063 .\n

\n

Before performing access control SSSD applies group policy\n security filtering on the GPOs. For every single user login, the\n applicability of the GPOs that are linked to the host is checked. In order\n for a GPO to apply to a user, the user or at least one of the groups to\n which it belongs must have following permissions on the GPO:

\n
•Read: The user or one of its groups must have\n read access to the properties of the GPO (RIGHT_DS_READ_PROPERTY)
\n
•Apply Group Policy: The user or at least one of\n its groups must be allowed to apply the GPO (RIGHT_DS_CONTROL_ACCESS).
\n

By default, the Authenticated Users group is present on a GPO and\n this group has both Read and Apply Group Policy access rights. Since\n authentication of a user must have been completed successfully before GPO\n security filtering and access control are started, the Authenticated Users\n group permissions on the GPO always apply also to the user.

\n

NOTE: If the operation mode is set to enforcing, it is possible\n that users that were previously allowed logon access will now be denied\n logon access (as dictated by the GPO policy settings). In order to\n facilitate a smooth transition for administrators, a permissive mode is\n available that will not enforce the access control rules, but will evaluate\n them and will output a syslog message if access would have been denied. By\n examining the logs, administrators can then make the necessary changes\n before setting the mode to enforcing. For logging GPO-based access control\n debug level 'trace functions' is required (see sssctl(8) manual\n page).

\n

There are three supported values for this option:

\n
•disabled: GPO-based access control rules are\n neither evaluated nor enforced.
\n
•enforcing: GPO-based access control rules are\n evaluated and enforced.
\n
•permissive: GPO-based access control rules are\n evaluated, but not enforced. Instead, a syslog message will be emitted\n indicating that the user would have been denied access if this option's value\n were set to enforcing.
\n

Default: enforcing

dyndns_server (string)

The DNS server to use when performing a DNS update. In most setups, it's recommended to leave this option unset.

Setting this option makes sense for environments where the DNS server is different from the identity server or when we use encrypted DNS.

The parameter can be a simple string containing DNS name or IP address. It can also be an URI. The URI can look like dns://servername/ or dns+tls://1.2.3.4:853#servername/.

The second example enables DNS-over-TLS protocol for DNS updates. The nsupdate utility must support DoT - check the man nsupdate before enabling it in SSSD.

Please note that this option will be only used in fallback attempt when previous attempt using autodetected settings failed or when DNS-over-TLS is enabled.

Default: None (let nsupdate choose the server)

NSS configuration

•fallback_homedir = /home/%d/%u

If your AD Domain is properly populated with Posix attributes, and you want to avoid this fallback behavior, you can explicitly set "fallback_homedir = %o".

Note that the system typically expects a home directory in /home/%u folder. If you decide to use a different directory structure, some other parts of your system may need adjustments.

For example automated creation of home directories in combination with selinux requires selinux adjustment, otherwise the home directory will be created with wrong selinux context.

FAILOVER

The failover feature allows back ends to automatically switch to a different server if the current server fails.

Failover Syntax

The list of servers is given as a comma-separated list; any number of spaces is allowed around the comma. The servers are listed in order of preference. The list can contain any number of servers.

For each failover-enabled config option, two variants exist: primary and backup. The idea is that servers in the primary list are preferred and backup servers are only searched if no primary servers can be reached. If a backup server is selected, a timeout of 31 seconds is set. After this timeout SSSD will periodically try to reconnect to one of the primary servers. If it succeeds, it will replace the current active (backup) server.

The Failover Mechanism

The failover mechanism distinguishes between a machine and a service. The back end first tries to resolve the hostname of a given machine; if this resolution attempt fails, the machine is considered offline. معرفات الأمان المعروفة (Well-Known SIDs)

يدعم SSSD البحث عن أسماء معرفات الأمان المعروفة (Well-Known SIDs)، أي معرفات الأمان ذات المعنى الخاص والمبرمج مسبقًا. نظرًا لأن المستخدمين والمجموعات العامة المرتبطة بمعرفات الأمان المعروفة هذه ليس لها مقابل في بيئة Linux/UNIX، فلا تتوفر معرفات POSIX لهذه الكائنات.

تنظم مساحة أسماء SID في سلطات (authorities) يمكن اعتبارها نطاقات مختلفة. السلطات لمعرفات الأمان المعروفة هي:

• سلطة فارغة (Null Authority)
• سلطة العالم (World Authority)
• السلطة المحلية (Local Authority)
• سلطة المنشئ (Creator Authority)
• سلطة التسمية الإلزامية (Mandatory Label Authority)
• سلطة المصادقة (Authentication Authority)
• سلطة NT (NT Authority)
• مدمج (Built-in)

تُستخدم النسخة المكتوبة بأحرف كبيرة من هذه الأسماء كأسماء نطاقات عند إرجاع الاسم المؤهل بالكامل لمعرف أمان معروف. نتيجة لذلك، لا يجب استخدام أسماء النطاقات "NULL AUTHORITY"، "WORLD AUTHORITY"، "LOCAL AUTHORITY"، "CREATOR AUTHORITY"، "MANDATORY LABEL AUTHORITY"، "AUTHENTICATION AUTHORITY"، "NT AUTHORITY"، و"BUILTIN" كأسماء نطاقات في ملف sssd.conf.

نظرًا لأن بعض الأدوات تسمح بتعديل معلومات التحكم في الوصول المستندة إلى SID بمساعدة اسم بدلاً من استخدام SID مباشرة، يدعم SSSD البحث عن SID بالاسم أيضًا. لتجنب التعارضات، يمكن فقط استخدام الأسماء المؤهلة بالكامل للبحث عن معرفات الأمان المعروفة. ونتيجة لذلك، يجب ألا تُستخدم أسماء النطاقات "NULL AUTHORITY"، "WORLD AUTHORITY"، "LOCAL AUTHORITY"، "CREATOR AUTHORITY"، "MANDATORY LABEL AUTHORITY"، "AUTHENTICATION AUTHORITY"، "NT AUTHORITY"، و"BUILTIN" كأسماء نطاقات في sssd.conf.

مثال

يفترض المثال التالي أن SSSD تم تكوينه بشكل صحيح وأن example.com هو أحد النطاقات في قسم [sssd]. يوضح هذا المثال الخيارات الخاصة بموفر AD فقط.

[domain/EXAMPLE]
id_provider = ad
auth_provider = ad
access_provider = ad
chpass_provider = ad
ad_server = dc1.example.com
ad_hostname = client.example.com
ad_domain = example.com

ملاحظات

يقوم موفر التحكم في الوصول AD بالتحقق مما إذا كان الحساب منتهي الصلاحية. وله نفس تأثير التكوين التالي لموفر LDAP:

access_provider = ldap
ldap_access_order = expire
ldap_account_expire_policy = ad

ومع ذلك، ما لم يتم تكوين موفر الوصول "ad" بشكل صريح، فإن موفر الوصول الافتراضي هو "permit". يرجى ملاحظة أنه إذا قمت بتكوين موفر وصول بخلاف "ad"، فأنت بحاجة إلى تعيين جميع معلمات الاتصال (مثل عناوين LDAP وتفاصيل التشفير) يدويًا.

عندما يتم تعيين موفر autofs إلى "ad"، يتم استخدام تعيين سمات مخطط RFC2307 (nisMap، nisObject، ...) لأن هذه السمات مدرجة في مخطط Active Directory الافتراضي.
