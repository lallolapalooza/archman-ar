SSL_CTX_set_verify(3ssl)

الحزمة: openssl

التراخيص: Apache-2.0

الوصف

SSL_CTX_set_verify() تحدد أعلام التحقق لـ ctx لتكون mode وتحدد دالة verify_callback المراد استخدامها. إذا لم يتم تحديد دالة رد اتصال، يمكن استخدام المؤشر NULL لـ verify_callback. يجب ألا يكون ctx NULL.

SSL_set_verify() تحدد أعلام التحقق لـ ssl لتكون mode وتحدد دالة verify_callback المراد استخدامها. إذا لم يتم تحديد دالة رد اتصال، يمكن استخدام المؤشر NULL لـ verify_callback. في هذه الحالة، يبقى آخر verify_callback تم تعيينه خصيصًا لهذا ssl. إذا لم يتم تعيين رد اتصال خاص من قبل، يتم استخدام رد الاتصال الافتراضي لـ ctx الأساسي، الذي كان صالحًا في وقت إنشاء ssl باستخدام SSL_new(3). ضمن دالة رد الاتصال، يمكن استدعاء SSL_get_ex_data_X509_STORE_CTX_idx للحصول على فهرس بيانات كائن SSL الحالي الذي يقوم بالتحقق.

في وضع العميل، قد يقوم verify_callback أيضًا باستدعاء دالة SSL_set_retry_verify(3) على كائن SSL المحدد في بيانات ex لـ x509_store_ctx (انظر SSL_get_ex_data_X509_STORE_CTX_idx(3)) وإرجاع 1. سيتم القيام بذلك عادةً في حالة عدم تمكن التحقق من الشهادة من النجاح بعد. هذا يجعل المصافحة معلقة وتعيد التحكم إلى التطبيق المستدعي مع SSL_ERROR_WANT_RETRY_VERIFY. يمكن للتطبيق، على سبيل المثال، جلب شهادات إضافية أو معلومات حالة الشهادة المطلوبة للتحقق. استدعاء SSL_connect(3) مرة أخرى يستأنف محاولة الاتصال عن طريق إعادة محاولة خطوة التحقق من شهادة الخادم. قد يتم تكرار هذه العملية حتى لو لزم الأمر. لاحظ أن المصافحة قد لا تزال يتم إنهاؤها إذا أعادت استدعاءات رد الاتصال اللاحقة (على سبيل المثال، في عمق أقل، أو لحالة خطأ منفصلة) القيمة 0.

SSL_CTX_set_verify_depth() تحدد الحد الأقصى depth للتحقق من سلسلة الشهادات التي يجب السماح بها لـ ctx.

SSL_set_verify_depth() تحدد الحد الأقصى depth للتحقق من سلسلة الشهادات التي يجب السماح بها لـ ssl.

SSL_CTX_set_post_handshake_auth() و SSL_set_post_handshake_auth() تمكنان امتداد مصادقة ما بعد المصافحة من إضافته إلى ClientHello بحيث يمكن للخادم طلب مصادقة ما بعد المصافحة. إذا كانت val تساوي 0، فلن يتم إرسال الامتداد، وإلا فسيتم إرساله. افتراضيًا، لا يتم إرسال الامتداد. ستحتاج دالة رد اتصال الشهادة إلى تعيينها عبر SSL_CTX_set_client_cert_cb() إذا لم يتم توفير شهادة عند التهيئة.

SSL_verify_client_post_handshake() تتسبب في إرسال رسالة CertificateRequest بواسطة خادم على اتصال ssl المحدد. يجب تعيين العلامة SSL_VERIFY_PEER؛ العلامة SSL_VERIFY_POST_HANDSHAKE اختيارية.

ملاحظات

يمكن التحكم في التحقق من الشهادات بواسطة مجموعة من الأعلام mode المدمجة منطقيًا:

SSL_VERIFY_NONE
وضع الخادم: لن يرسل الخادم طلب شهادة عميل إلى العميل، لذلك لن يرسل العميل شهادة.

وضع العميل: إذا لم يتم استخدام تشفير مجهول (معطل افتراضيًا)، سيرسل الخادم شهادة سيتم التحقق منها. يمكن التحقق من نتيجة عملية التحقق من الشهادة بعد مصافحة TLS/SSL باستخدام دالة SSL_get_verify_result(3). ستستمر المصافحة بغض النظر عن نتيجة التحقق.

SSL_VERIFY_PEER
وضع الخادم: يرسل الخادم طلب شهادة عميل إلى العميل. يتم التحقق من الشهادة المرتجعة (إن وجدت). إذا فشلت عملية التحقق، يتم إنهاء مصافحة TLS/SSL فورًا برسالة تنبيه تحتوي على سبب فشل التحقق. يمكن التحكم في السلوك بواسطة الأعلام الإضافية SSL_VERIFY_FAIL_IF_NO_PEER_CERT و SSL_VERIFY_CLIENT_ONCE و SSL_VERIFY_POST_HANDSHAKE.

وضع العميل: يتم التحقق من شهادة الخادم. إذا فشلت عملية التحقق، يتم إنهاء مصافحة TLS/SSL فورًا برسالة تنبيه تحتوي على سبب فشل التحقق. إذا لم يتم إرسال شهادة خادم، لأنه تم استخدام تشفير مجهول، يتم تجاهل SSL_VERIFY_PEER.

SSL_VERIFY_FAIL_IF_NO_PEER_CERT
وضع الخادم: إذا لم يرجع العميل شهادة، يتم إنهاء مصافحة TLS/SSL فورًا بتنبيه "فشل المصافحة". يجب استخدام هذا العلم مع SSL_VERIFY_PEER.

وضع العميل: تم تجاهله (انظر BUGS)

SSL_VERIFY_CLIENT_ONCE
وضع الخادم: طلب شهادة عميل مرة واحدة فقط أثناء الاتصال. لا تطلب شهادة عميل مرة أخرى أثناء إعادة التفاوض أو المصادقة اللاحقة إذا تم طلب شهادة أثناء المصافحة الأولية. يجب استخدام هذا العلم مع SSL_VERIFY_PEER.

وضع العميل: تم تجاهله (انظر BUGS)

SSL_VERIFY_POST_HANDSHAKE
وضع الخادم: لن يرسل الخادم طلب شهادة عميل أثناء المصافحة الأولية، ولكنه سيرسل الطلب عبر SSL_verify_client_post_handshake(). هذا يسمح بتهيئة SSL_CTX أو SSL للتحقق من الطرف المقابل بعد المصافحة قبل حدوث المصافحة. يجب استخدام هذا العلم مع SSL_VERIFY_PEER. TLSv1.3 فقط؛ لا يؤثر على الاتصالات قبل TLSv1.3.

وضع العميل: تم تجاهله (انظر BUGS)

إذا كان mode هو SSL_VERIFY_NONE، فلا يجوز تعيين أي من الأعلام الأخرى.

إذا لم يتم تعديل أعلام التحقق بشكل صريح بواسطة SSL_CTX_set_verify() أو SSL_set_verify()، فإن القيمة الافتراضية ستكون SSL_VERIFY_NONE.

يتم إجراء إجراء التحقق الفعلي إما باستخدام إجراء التحقق المدمج أو باستخدام دالة تحقق أخرى يقدمها التطبيق تم تعيينها باستخدام SSL_CTX_set_cert_verify_callback(3). تنطبق الأوصاف التالية في حالة الإجراء المدمج. لدى إجراء يقدمه التطبيق وصول أيضًا إلى معلومات عمق التحقق ودالة verify_callback()، ولكن الطريقة التي يتم بها استخدام هذه المعلومات قد تكون مختلفة.

SSL_CTX_set_verify_depth() و SSL_set_verify_depth() تحددان حدًا لعدد الشهادات بين شهادات الكيان النهائي وشهادات موثوق المصدر. لا تُحسب شهادات الكيان النهائي ولا شهادات موثوق المصدر مقابل depth. إذا كانت سلسلة الشهادات المطلوبة للوصول إلى جهة إصدار موثوقة أطول من depth+2، فسيتم إصدار X509_V_ERR_CERT_CHAIN_TOO_LONG. عدد العمق هو "المستوى 0: شهادة الطرف المقابل"، "المستوى 1: شهادة CA"، "المستوى 2: شهادة CA ذات مستوى أعلى"، وهكذا. يتيح تعيين الحد الأقصى للعمق إلى 2 المستويات 0، 1، 2، و 3 (حيث 0 هو الكيان النهائي و 3 هو موثوق المصدر). الحد الافتراضي للعمق هو 100، مما يسمح بشهادة الطرف المقابل، وما يصل إلى 100 شهادة CA وسيطة، وشهادة موثوق المصدر نهائية.

تُستخدم دالة verify_callback للتحكم في السلوك عندما يتم تعيين علامة SSL_VERIFY_PEER. يجب أن يتم توفيرها بواسطة التطبيق وتتلقى وسيطين: preverify_ok و x509_ctx.

الأخطاء

في وضع العميل، يتم تجاهل علامة SSL_VERIFY_PEER إذا لم يتم إرسال شهادة، لأنه تم استخدام تشفير مجهول. هذه مشكلة معروفة وصفحة أخطاء Arch Linux تسرد رقم الخطأ ووصفه.

يشير، إذا كانت عملية التحقق من الشهادة المعنية ناجحة (preverify_ok=1) أو لا (preverify_ok=0). x509_ctx هو مؤشر إلى السياق الكامل المستخدم للتحقق من سلسلة الشهادات.

يتم التحقق من سلسلة الشهادات بدءًا من أعمق مستوى تداخل (شهادة الجذر) والتحرك للأعلى نحو الشهادة الموجودة على الجانب المقابل. عند كل مستوى، يتم التحقق من توقيعات وبيانات المُصدر. عندما يتم العثور على خطأ في التحقق، يتم تخزين رقم الخطأ في x509_ctx ويتم استدعاء verify_callback مع preverify_ok=0. عند تطبيق وظائف X509_CTX_store_*، يمكن لـ verify_callback تحديد موقع الشهادة المعنية واتخاذ خطوات إضافية (انظر الأمثلة). إذا لم يتم العثور على خطأ لشهادة، يتم استدعاء verify_callback مع preverify_ok=1 قبل الانتقال إلى المستوى التالي.

قيمة الإرجاع من verify_callback تتحكم في استراتيجية التحقق اللاحقة. إذا أعادت verify_callback القيمة 0، يتوقف التحقق فورًا بحالة "فشل التحقق". إذا تم تعيين SSL_VERIFY_PEER، يتم إرسال رسالة تنبيه إلى الجانب المقابل ويتم إنهاء تبادل TLS/SSL. إذا أعادت verify_callback القيمة 1، يستمر التحقق. إذا أعادت verify_callback دائمًا القيمة 1، فلن يتوقف تبادل TLS/SSL فيما يتعلق بأخطاء التحقق وسيتم إنشاء الاتصال. يمكن لعملية الاستدعاء استرداد رمز الخطأ لآخر تحقق فاشل باستخدام SSL_get_verify_result(3) أو عن طريق الاحتفاظ بقائمة الأخطاء الخاصة بها التي يديرها verify_callback.

إذا لم يتم تحديد verify_callback، فسيتم استخدام الاستدعاء الافتراضي. قيمة إرجاعه متطابقة مع preverify_ok، لذلك يؤدي أي فشل في التحقق إلى اكتشاف تبادل TLS/SSL برسالة تنبيه، إذا كان SSL_VERIFY_PEER نشطًا.

بعد استدعاء SSL_set_post_handshake_auth()، يحتاج العميل إلى إضافة شهادة أو استدعاء شهادة قبل أن يتمكن من المصادقة بنجاح. يجب استدعاء هذه العملية قبل SSL_connect().

يتطلب SSL_verify_client_post_handshake() تعيين علامات التحقق مسبقًا وأن يكون العميل قد أرسل امتداد المصادقة بعد المصافحة. عندما يعيد العميل شهادة، يتم استدعاء استدعاء التحقق. يجب إجراء عملية كتابة لإرسال طلب الشهادة عبر العميل، والتي يمكن القيام بها باستخدام SSL_do_handshake() أو SSL_write_ex(). يمكن أن يكون هناك طلب شهادة واحد فقط قيد التقدم في المرة الواحدة.

عند إجراء المصادقة بعد المصافحة، يتم إرسال تذكرة جلسة محدثة جديدة إلى العميل.

لا يمكن استخدام المصادقة بعد المصافحة مع QUIC. SSL_set_post_handshake_auth() ليس له تأثير إذا تم استدعاؤه على كائن SSL QUIC.

أخطاء

في وضع العميل، لا يتم التحقق مما إذا كانت علامة SSL_VERIFY_PEER نشطة، ولكن يتم التحقق مما إذا كانت هناك علامات أخرى بخلاف SSL_VERIFY_NONE نشطة. قد يؤدي هذا إلى سلوك غير متوقع إذا لم يتم استخدام علامات SSL_VERIFY_PEER وغيرها بشكل صحيح.

قيم الإرجاع

لا توفر وظائف SSL*_set_verify*() أي معلومات تشخيصية.

تُرجع الوظيفة SSL_verify_client_post_handshake() القيمة 1 إذا كان الطلب ناجحًا، و 0 إذا فشل. يمكن فحص مكدس الأخطاء لتحديد سبب الفشل.

أمثلة

تنفذ سلسلة التعليمات البرمجية التالية مثالاً لوظيفة verify_callback تستمر دائمًا في تبادل TLS/SSL، بغض النظر عن فشل التحقق، إذا كنت ترغب في ذلك. تقوم الوظيفة بحد عمق التحقق مع إخراج معلوماتي إضافي.

يتم طباعة جميع أخطاء التحقق؛ يتم طباعة معلومات حول سلسلة الشهادات في حالة الطلب. تم تنفيذ المثال لخادم يسمح بشهادات العملاء ولكن لا يتطلبها.

يستخدم المثال طريقة CRYPTO_get_ex_new_index(3)، SSL_get_ex_data_X509_STORE_CTX_idx(3) لتخزين واسترداد البيانات المطبقة في بنية SSL.

...
typedef struct {
  int verbose_mode;
  int verify_depth;
  int always_continue;
} mydata_t;
int mydata_index;
...
static int verify_callback(int preverify_ok, X509_STORE_CTX *ctx)
{
    char    buf[256];
    X509   *err_cert;
    int     err, depth;
    SSL    *ssl;
    mydata_t *mydata;
    err_cert = X509_STORE_CTX_get_current_cert(ctx);
    err = X509_STORE_CTX_get_error(ctx);
    depth = X509_STORE_CTX_get_error_depth(ctx);
    /*
     * Retrieve the pointer to the SSL of the connection currently treated
     * and the application specific data stored into the SSL object.
     */
    ssl = X509_STORE_CTX_get_ex_data(ctx, SSL_get_ex_data_X509_STORE_CTX_idx());
    mydata = SSL_get_ex_data(ssl, mydata_index);
    X509_NAME_oneline(X509_get_subject_name(err_cert), buf, 256);
    /*
     * Catch a too long certificate chain. The depth limit set using
     * SSL_CTX_set_verify_depth() is by purpose set to "limit+1" so
     * that whenever the "depth>verify_depth" condition is met, we
     * have violated the limit and want to log this error condition.
     * We must do it here, because the CHAIN_TOO_LONG error would not
     * be found explicitly; only errors introduced by cutting off the
     * additional certificates would be logged.
     */
    if (depth > mydata->verify_depth) {
        preverify_ok = 0;
        err = X509_V_ERR_CERT_CHAIN_TOO_LONG;
        X509_STORE_CTX_set_error(ctx, err);
    }
    if (!preverify_ok) {
        printf("verify error:num=%d:%s:depth=%d:%s\n", err,
               X509_verify_cert_error_string(err), depth, buf);
    } else if (mydata->verbose_mode) {
        printf("depth=%d:%s\n", depth, buf);
    }
    /*
     * At this point, err contains the last verification error. We can use
     * it for something special
     */
    if (!preverify_ok && (err == X509_V_ERR_UNABLE_TO_GET_ISSUER_CERT)) {
        X509_NAME_oneline(X509_get_issuer_name(err_cert), buf, 256);
        printf("issuer= %s\n", buf);
    }
    if (mydata->always_continue)
        return 1;
    else
        return preverify_ok;
}

mydata_index = SSL_get_ex_new_index(0, "mydata index", NULL, NULL, NULL);
