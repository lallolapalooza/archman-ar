الوصف

sd_bus_add_object_vtable() تُستخدم لتعريف سمات لمسار الكائن path المتصل باتصال الناقل bus تحت الواجهة interface. قد يحتوي الجدول vtable على تعريفات خصائص باستخدام SD_BUS_PROPERTY() أو SD_BUS_WRITABLE_PROPERTY()، وتعريفات طرق باستخدام SD_BUS_METHOD()، أو SD_BUS_METHOD_WITH_NAMES()، أو SD_BUS_METHOD_WITH_OFFSET()، أو SD_BUS_METHOD_WITH_NAMES_OFFSET()، وتعريفات إشارات باستخدام SD_BUS_SIGNAL_WITH_NAMES() أو SD_BUS_SIGNAL()، انظر أدناه. يحتوي المعامل userdata على مؤشر سيتم تمريره إلى دوال استدعاء مختلفة. قد يتم تحديده كـ NULL إذا لم تكن هناك قيمة ضرورية. يمكن أن تحتوي الواجهة على أي عدد من vtables مرفقة بها.

sd_bus_add_fallback_vtable() مشابه لـ sd_bus_add_object_vtable()، ولكنه يُستخدم لتسجيل سمات "احتياطية". عند البحث عن تعريف سمة، يتم التحقق من مسارات كائنات الناقل المسجلة باستخدام sd_bus_add_object_vtable() أولاً. إذا لم يتم العثور على تطابق، يتم التحقق من vtables الاحتياطية لكل بادئة من مسار كائن الناقل، أي مع إزالة المكونات المفصولة بشرطة مائلة الأخيرة بشكل متتابع. هذا يسمح باستخدام vtable لعدد عشوائي من الكائنات التي تم إنشاؤها ديناميكيًا.

المعامل find هي دالة تُستخدم لتحديد موقع الكائن الهدف بناءً على مسار كائن الناقل path. يجب أن ترجع 1 وتضبط المعامل الناتج ret_found إذا تم العثور على الكائن، وترجع 0 إذا لم يتم العثور على الكائن، وترجع رمز خطأ سالب بنمط errno أو تهيئة هيكل الخطأ ret_error عند حدوث خطأ. سيتم استخدام المؤشر الممرر في ret_found كمعامل userdata لدوال الاستدعاء (بإزاحة من إزاحات offset كما هو محدد في إدخالات vtable).

sd_bus_add_object() تربط دالة استدعاء مباشرة بمسار الكائن path. يمكن أن تحتوي مسارات الكائنات على أي عدد من دوال الاستدعاء المربوطة بها. يتم إضافة كل دالة استدعاء إلى بداية قائمة دوال الاستدعاء التي يتم استدعاؤها دائمًا بالتسلسل. sd_bus_add_fallback() مشابه لـ sd_bus_add_object() ولكنه ينطبق على مسارات احتياطية بدلاً من ذلك.

sd_bus_add_filter() تثبت دالة استدعاء يتم استدعاؤها لكل رسالة D-Bus واردة. يمكن استخدام المرشحات لمعالجة المنطق المشترك لجميع الرسائل التي تتلقاها خدمة (مثل المصادقة أو التفويض).

عندما يتم تلقي طلب، يتم استدعاء أي دوال استدعاء مرتبطة به بالتتابع حتى ترجع دالة استدعاء عدداً صحيحاً غير صفري. ارجع صفراً من دالة استدعاء لإعطاء دوال استدعاء أخرى فرصة لمعالجة الطلب. يتم استدعاء دوال الاستدعاء بالترتيب التالي: أولاً، يتم استدعاء دوال الاستدعاء الشاملة المثبتة باستخدام sd_bus_add_filter(). ثانياً، يتم استدعاء دوال الاستدعاء المربوطة مباشرة بمسار الكائن المطلوب، تليها أي دوال استدعاء طرق D-Bus مرتبطة بمسار الكائن، الواجهة، والعضو. أخيراً، يتم استدعاء دوال استدعاء الخصائص المرتبطة بمسار الكائن، الواجهة، والعضو. إذا قامت دالة الاستدعاء النهائية بإرجاع صفر، فإن خطأ

يتم إرجاع الرد إلى المتصل للإشارة إلى عدم العثور على كائن مطابق للطلب.

لاحظ أنه يمكنك إرجاع عدد صحيح موجب من استدعاء method دون إرسال رد على الفور. هذا يبلغ sd-bus بأن هذا الاستدعاء سيتولى مسؤولية الرد على الطلب دون إجبار الاستدعاء على إنتاج رد فورًا. هذا يسمح للاستدعاء بأداء أي عدد مطلوب من العمليات غير المتزامنة لإنشاء رد. ومع ذلك ، إذا استغرق إنشاء رد وقتًا طويلاً جدًا ، فسينتهي وقت استدعاء الطريقة لدى المتصل. هذا متاح للطرق فقط وليس للخصائص.

إذا تم استدعاء استدعاء لمعالجة طلب يتوقع ردًا وكان الاستدعاء يرجع قيمة سالبة ، فيتم تفسير القيمة كرمز خطأ سالب بأسلوب errno ويتم إرجاعها إلى المتصل كخطأ D-Bus كما لو تم استدعاء sd_bus_reply_method_errno(3). بالإضافة إلى ذلك ، تأخذ جميع الاستدعاءات معلمة إخراج sd_bus_error التي يمكن استخدامها لتوفير معلومات خطأ أكثر تفصيلاً. إذا تم تعيين ret_error عند انتهاء الاستدعاء ، يتم إرجاع خطأ D-Bus المقابل إلى المتصل كما لو تم استدعاء sd_bus_reply_method_error(3). أي خطأ مخزن في ret_error له الأولوية على أي قيم سالبة تم إرجاعها بواسطة نفس الاستدعاء عند تحديد الخطأ الذي يجب إرجاعه إلى المتصل. استخدم sd_bus_error_set(3) أو أحد متغيراته لتعيين ret_error وإرجاع عدد صحيح سالب من استدعاء برمجتها مع استدعاء دالة واحدة. لإرسال رد خطأ بعد انتهاء الاستدعاء بالفعل ، استخدم sd_bus_reply_method_errno(3) أو أحد متغيراته.

لجميع الوظائف ، يتم إنشاء فتحة مطابقة داخليًا. إذا كانت معلمة الإخراج slot هي NULL ، يتم إنشاء كائن فتحة "عائم" ، انظر sd_bus_slot_set_floating(3). بخلاف ذلك ، يتم إرجاع مؤشر إلى كائن الفتحة. في هذه الحالة ، يجب إسقاط المرجع إلى كائن الفتحة عندما لم تعد هناك حاجة إلى vtable ، انظر sd_bus_slot_unref(3).

مصفوفة sd_bus_vtable

تتكون المصفوفة من هياكل من نوع sd_bus_vtable ، ولكن لا ينبغي ملؤها يدويًا أبدًا ، ولكن من خلال إحدى وحدات الماكرو التالية:

SD_BUS_VTABLE_START(flags), SD_BUS_VTABLE_END

يجب أن تكون هذه دائمًا العنصر الأول والأخير. يمكن استخدام معلمة flags لتعيين سمات تنطبق على المصفوفة بأكملها ؛ انظر قسم "Flags" أدناه.

SD_BUS_METHOD_WITH_ARGS_OFFSET(), SD_BUS_METHOD_WITH_ARGS()

يعلن عن طريقة D-Bus بالاسم member، والوسائط args والنتيجة result. تتوقع args تسلسلاً من أزواج نوع/اسم الوسيط مغلفة في ماكرو SD_BUS_ARGS(). تصف العناصر في المؤشرات الزوجية في هذه القائمة أنواع وسائط الطريقة. توقيع معلمة الطريقة هو التسلسل لجميع السلاسل الحرفية في المؤشرات الزوجية في args. إذا كانت الطريقة لا تحتوي على وسائط ، قم بتمرير SD_BUS_NO_ARGS إلى args. تصف العناصر في المؤشرات الفردية أسماء وسائط الطريقة. تتوقع result تسلسلاً من أزواج نوع/اسم مغلفة في ماكرو SD_BUS_RESULT() بنفس تنسيق SD_BUS_ARGS(). توقيع نتيجة الطريقة هو التسلسل لجميع السلاسل الحرفية في المؤشرات الزوجية في result. إذا كانت الطريقة لا تحتوي على نتيجة ، قم بتمرير SD_BUS_NO_RESULT إلى result. لاحظ أن أنواع الوسائط متوقعة أن تكون سلاسل حرفية مقتبسة وأن أسماء الوسائط متوقعة أن تكون سلاسل حرفية غير مقتبسة. انظر أدناه مثالاً كاملاً.

يجب أن تكون دالة المعالج handler من النوع sd_bus_message_handler_t. سيتم استدعاؤها لمعالجة الرسائل الواردة التي تستدعي هذه الطريقة. تتلقى مؤشرًا هو معلمة userdata التي تم تمريرها إلى دالة التسجيل مزاحة بعدد offset من البايتات. يمكن استخدام هذا لتمرير مؤشرات إلى حقول مختلفة في نفس بنية البيانات لطرق مختلفة في نفس vtable. لإرسال رد من handler ، قم باستدعاء sd_bus_reply_method_return(3) مع الرسالة التي تم استدعاء الاستدعاء بها. معلمة flags هي مزيج من الأعلام ، انظر أدناه.

SD_BUS_METHOD_WITH_ARGS() هو اختصار لاستدعاء SD_BUS_METHOD_WITH_ARGS_OFFSET() بإزاحة صفر.

SD_BUS_METHOD_WITH_NAMES_OFFSET(), SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET(), SD_BUS_METHOD()

يعلن عن طريقة D-Bus بالاسم member، وتوقيع الوسائط signature، وتوقيع النتيجة result. تحدد المعلمتان in_names و out_names أسماء وسائط وسائط الإدخال والإخراج في توقيع الدالة. يجب إنشاء in_names و out_names باستخدام ماكرو SD_BUS_PARAM() ، انظر أدناه. في جميع النواحي الأخرى ، يتصرف هذا الماكرو تمامًا مثل SD_BUS_METHOD_WITH_ARGS_OFFSET().

SD_BUS_METHOD_WITH_NAMES() ، SD_BUS_METHOD_WITH_OFFSET() ، و SD_BUS_METHOD() هي متغيرات تحدد إزاحة صفر (يتم تمرير معلمة userdata بدون تغيير) ، وتترك الأسماء غير محددة (أي لا توجد أسماء وسائط) ، أو كليهما.

يفضل استخدام SD_BUS_METHOD_WITH_ARGS_OFFSET() و SD_BUS_METHOD_WITH_ARGS() على هذه وحدات الماكرو لأنها تسمح بتحديد أنواع الوسائط وأسمائها جنبًا إلى جنب مما يقلل من الأخطاء مقارنة بتحديد جميع أنواع الوسائط أولاً ثم تحديد جميع أسماء الوسائط.

SD_BUS_SIGNAL_WITH_ARGS()

يعلن عن إشارة D-Bus بالاسم member والوسائط args. تتوقع args تسلسلاً من أزواج نوع/اسم وسيط مغلفة في ماكرو SD_BUS_ARGS(). تصف العناصر في المؤشرات الزوجية في هذه القائمة أنواع وسائط الإشارة. توقيع وسائط الإشارة هو التسلسل لجميع السلاسل الحرفية في المؤشرات الزوجية في args. إذا كانت الإشارة لا تحتوي على وسائط ، قم بتمرير SD_BUS_NO_ARGS إلى args. تصف العناصر في المؤشرات الفردية أسماء وسائط الإشارة. معلمة flags هي مزيج من الأعلام. انظر أدناه مثالاً كاملاً.

SD_BUS_SIGNAL_WITH_NAMES(), SD_BUS_SIGNAL()

يعلن عن إشارة D-Bus بالاسم member، وتوقيع الوسائط signature، وأسماء الوسائط names. يجب إنشاء names باستخدام ماكرو SD_BUS_PARAM() ، انظر أدناه. معلمة flags هي مزيج من الأعلام ، انظر أدناه.

SD_BUS_SIGNAL() يعادل SD_BUS_SIGNAL_WITH_NAMES() مع معلمة names غير محددة (أي لا توجد أسماء وسائط).

يفضل استخدام SD_BUS_SIGNAL_WITH_ARGS() على هذه وحدات الماكرو لأنها تسمح بتحديد أنواع الوسائط وأسمائها جنبًا إلى جنب مما يقلل من الأخطاء مقارنة بتحديد جميع أنواع الوسائط أولاً ثم تحديد جميع أسماء الوسائط.

SD_BUS_WRITABLE_PROPERTY(), SD_BUS_PROPERTY()

يعلن عن خاصية D-Bus بالاسم member وتوقيع القيمة signature. المعلمتان get و set هما طريقتي الحصول والتعيين. يتم استدعاؤهما بمؤشر هو معلمة userdata التي تم تمريرها إلى دالة التسجيل مزاحة بعدد offset من البايتات. يمكن استخدام هذا لتمرير مؤشرات إلى حقول مختلفة في نفس بنية البيانات إلى طرق تعيين واستلام مختلفة في نفس vtable. معلمة flags هي مزيج من الأعلام ، انظر أدناه.

يمكن حذف طريقتي التعيين والحصول (تحديدها كـ NULL) ، إذا كانت الخاصية من الأنواع الأساسية أو "as" في حالة الخصائص للقراءة فقط. في هذه الحالات ، يجب أن يشير معلما userdata و offset معًا إلى متغير صالح من النوع المقابل. سيتم توفير طريقة تعيين وحصول افتراضية ، والتي تقوم ببساطة بنسخ الوسيط بين هذا المتغير والرسالة.

يستخدم SD_BUS_PROPERTY() لتعريف خاصية للقراءة فقط.

SD_BUS_PARAM()

يجب تغليف أسماء الوسائط في هذا الماكرو ، انظر المثال أدناه.

الأعلام

تستخدم معلمة flags لتحديد مزيج من تعليقات D-Bus[1].

SD_BUS_VTABLE_DEPRECATED

ضع علامة على إدخال vtable هذا على أنه مهمل باستخدام تعليق org.freedesktop.DBus.Deprecated في بيانات الفحص. إذا تم تحديده لـ SD_BUS_VTABLE_START() ، يتم تطبيق التعليق على الواجهة المغلفة.

SD_BUS_VTABLE_HIDDEN

اجعل إدخال vtable هذا مخفيًا. لن يتم عرضه في بيانات الفحص. إذا تم تحديده لـ SD_BUS_VTABLE_START() ، فسيتم إخفاء جميع الإدخالات في المصفوفة.

SD_BUS_VTABLE_METHOD_NO_REPLY

ضع علامة على إدخال vtable هذا على أنه طريقة لن تعيد ردًا باستخدام تعليق org.freedesktop.DBus.Method.NoReply في بيانات الفحص.

SD_BUS_VTABLE_PROPERTY_CONST, SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE, SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION

تتوافق هذه الأعلام الثلاثة مع قيم مختلفة من تعليق org.freedesktop.DBus.Property.EmitsChangedSignal ، والذي يحدد ما إذا كانت إشارة org.freedesktop.DBus.Properties.PropertiesChanged تُرسل كلما تغيرت الخاصية. SD_BUS_VTABLE_PROPERTY_CONST يتوافق مع const ويعني أن الخاصية لا تتغير أبدًا أثناء فترة حياة الكائن الذي تنتمي إليه ، لذلك لا يلزم إرسال إشارة. SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE يتوافق مع true ويعني أن الإشارة تُرسل. SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION يتوافق مع invalidates ويعني أن الإشارة تُرسل ، ولكن القيمة غير مدرجة في الإشارة.

SD_BUS_VTABLE_PROPERTY_EXPLICIT

ضع علامة على إدخال خاصية vtable هذا على أنه يتطلب طلبًا صريحًا لعرض القيمة (بشكل عام لأن القيمة كبيرة أو بطيئة في الحساب). لا يمكن دمج هذا الإدخال مع SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE ، ولن يتم عرضه في قوائم الخصائص افتراضيًا (مثل busctl introspect). هذا يتوافق مع التعليق org.freedesktop.systemd1.Explicit في بيانات الفحص.

SD_BUS_VTABLE_SENSITIVE

ضع علامة على إدخال طريقة vtable هذا على أنه يعالج بيانات حساسة. عند التعيين ، يتم تمييز رسائل استدعاء الطريقة الواردة ورسائل الرد الصادرة على أنها حساسة باستخدام sd_bus_message_sensitive(3) ، بحيث يتم مسحها من الذاكرة عند تحريرها.

SD_BUS_VTABLE_ABSOLUTE_OFFSET

ضع علامة على إدخال طريقة أو خاصية vtable بحيث تكون بيانات المستخدم

DESCRIPTION

These functions are used to register objects on the D-Bus connection bus. Objects are identified by their path.

sd_bus_add_object_vtable() registers an object at path that implements the D-Bus interface described by vtable. The vtable parameter should point to a null-terminated array of sd_bus_method_entry structures.

sd_bus_add_fallback_vtable() is similar, but registers a "fallback" object. Fallback objects are only used if no other object (regular or fallback) is registered for the same path and interface. This is useful for implementing generic interfaces that can be served by multiple objects.

sd_bus_add_object() and sd_bus_add_fallback() are convenience functions that register an object implementing the D-Bus interface named interface. The object will implement the methods listed in methods. The methods parameter should point to a null-terminated array of sd_bus_method_handler structures.

sd_bus_object_find_t(), sd_bus_property_get_t(), and sd_bus_property_set_t() are used to query the registered vtables, property getters, and property setters for a given object path and interface.

The userdata parameter can be used to pass arbitrary data to the method handlers. It is returned by sd_bus_object_find_t(), sd_bus_property_get_t(), and sd_bus_property_set_t().

See D-Bus specifications for details on D-Bus paths and interfaces.

See sd-bus(3).

RETURN VALUE

On success, these functions return a non-negative integer. On failure, they return a negative error number.

NOTES

These functions are available as a shared library, which can be compiled against and linked to with the libsystemd pkg-config(1) file.

The code described here uses getenv(3), which is declared to be not multi-thread-safe. This means that the code calling the functions described here must not call setenv(3) from a parallel thread. It is recommended to only do calls to setenv() from an early phase of the program when no other threads have been started.
