الوصف

sd_id128_get_machine() يعيد معرف الجهاز الخاص بالمضيف الذي يتم تنفيذه. يقوم هذا بقراءة وتحليل ملف machine-id(5). تقوم هذه الدالة بتخزين معرف الجهاز مؤقتًا داخليًا لجعل استرداد معرف الجهاز عملية سهلة. يمكن استخدام هذا المعرف كلما احتجت إلى معرف فريد للنظام المحلي. ومع ذلك، يوصى باستخدام هذا المعرف كما هو فقط في البيئات الموثوقة. في البيئات غير الموثوقة، يوصى باشتقاق معرف خاص بالتطبيق من معرف الجهاز هذا، بطريقة لا رجعة فيها (آمنة تشفيرياً). لجعل هذا الأمر سهلاً، يتم توفير sd_id128_get_machine_app_specific()، انظر أدناه.

sd_id128_get_app_specific() يعيد معرف جهاز هو مزيج من المعاملين base و app_id. داخليًا، تقوم هذه الدالة بحساب HMAC-SHA256 للمعامل app_id باستخدام المعامل base كمفتاح، وتقوم بتقليص هذه النتيجة لتناسب sd_id128_t وتحويلها إلى UUID صالح من النوع Variant 1 Version 4، وفقًا لـ RFC 4122[1]. لا يمكن حساب أي من المعاملين المدخلين من المعامل المخرج ret.

sd_id128_get_machine_app_specific() مشابه لـ sd_id128_get_machine()، ولكنه يسترد معرف جهاز خاص بالتطبيق الذي تم تحديده بواسطة معرف التطبيق المشار إليه. يوصى باستخدام هذه الدالة بدلاً من sd_id128_get_machine() عند تمرير معرف إلى بيئات غير موثوقة، لضمان عدم إمكانية تحديد معرف الجهاز الأصلي خارجيًا. بهذه الطريقة، يظل المعرف المستخدم بواسطة التطبيق ثابتًا على جهاز معين، ولكن لا يمكن ربطه بسهولة بالمعرفات المستخدمة في تطبيقات أخرى على نفس الجهاز. يجب إنشاء المعرف الخاص بالتطبيق عبر أداة مثل systemd-id128 new، ويمكن تجميعه في التطبيق. ستعيد هذه الدالة نفس المعرف الخاص بالتطبيق لكل تركيبة من معرف الجهاز ومعرف التطبيق. داخليًا، تقوم هذه الدالة باستدعاء sd_id128_get_app_specific() مع النتيجة من sd_id128_get_machine() والمعامل app_id.

sd_id128_get_boot() يعيد معرف الإقلاع للنواة التي يتم تنفيذها. يقوم هذا بقراءة وتحليل ملف /proc/sys/kernel/random/boot_id الذي تعرضه النواة. يتم إنشاؤه عشوائيًا في بداية الإقلاع وهو فريد لكل نسخة نواة قيد التشغيل. انظر random(4) لمزيد من المعلومات. تقوم هذه الدالة أيضًا بتخزين المعرف المعاد داخليًا مؤقتًا لجعل هذه المكالمة عملية سهلة. يوصى باستخدام هذا المعرف كما هو فقط في البيئات الموثوقة. في البيئات غير الموثوقة، يوصى باشتقاق معرف خاص بالتطبيق باستخدام sd_id128_get_boot_app_specific()، انظر أدناه.

sd_id128_get_boot_app_specific() مماثل لـ sd_id128_get_machine_app_specific()، ولكنه يعيد معرفًا يتغير بين عمليات الإقلاع. قد يتم استخدام بعض الأجهزة لفترة طويلة دون إعادة التشغيل، وبالتالي قد يظل معرف الإقلاع ثابتًا لفترة طويلة، وله خصائص مشابهة لمعرف الجهاز خلال تلك الفترة.

sd_id128_get_invocation() يعيد معرف الاستدعاء للخدمة التي يتم تنفيذها حاليًا. في تنفيذه الحالي، يحاول قراءة وتحليل ما يلي:

• متغير البيئة $INVOCATION_ID الذي يقوم مدير الخدمة بتعيينه عند تنشيط خدمة.
• إدخال في مفتاح سلسلة مفاتيح النواة الذي يقوم مدير خدمة النظام بتعيينه عند تنشيط خدمة.

انظر systemd.exec(5) للحصول على التفاصيل. يتم تخزين المعرف داخليًا مؤقتًا. في المستقبل، قد يتم إضافة آلية مختلفة لتحديد معرف الاستدعاء.

sd_id128_get_invocation_app_specific() يشتق معرفًا خاصًا بالتطبيق من معرف الاستدعاء.

لاحظ أن sd_id128_get_machine_app_specific()، sd_id128_get_boot()، sd_id128_get_boot_app_specific()، sd_id128_get_invocation() و sd_id128_get_invocation_app_specific يعيد دائمًا معرفات متوافقة مع UUID Variant 1 Version 4. sd_id128_get_machine() سيعيد أيضًا معرفًا متوافقًا مع UUID Variant 1 Version 4 في التثبيتات الجديدة ولكن قد لا يفعل ذلك في الإصدارات القديمة. من الممكن تحويل معرف الجهاز بشكل لا رجعة فيه إلى معرف متوافق مع UUID Variant 1 Version 4. لمزيد من المعلومات، انظر machine-id(5). لذلك، من المضمون أن هذه الدوال لن تعيد أبدًا المعرف المكون من جميع البتات الصفرية أو جميع البتات الواحدة (SD_ID128_NULL، SD_ID128_ALLF) - مع احتمال استثناء sd_id128_get_machine()، كما ذكر.

لمزيد من المعلومات حول النوع "sd_id128_t" انظر sd-id128(3).

قيمة الإرجاع

تعيد هذه المكالمات 0 عند النجاح (في هذه الحالة يتم ملء ret)، أو رمز خطأ سلبي بأسلوب errno.

الأخطاء

قد تشير الأخطاء المعادة إلى المشاكل التالية:

-ENOENT

تُعاد بواسطة sd_id128_get_machine() و sd_id128_get_machine_app_specific() عندما يكون /etc/machine-id مفقودًا.

تمت الإضافة في الإصدار 242.

-ENOMEDIUM

تُعاد بواسطة sd_id128_get_machine() و sd_id128_get_machine_app_specific() عندما يكون /etc/machine-id فارغًا أو كله أصفار. تُعاد أيضًا بواسطة sd_id128_get_invocation() عندما يكون معرف الاستدعاء كله أصفار.

تمت الإضافة في الإصدار 242.

-ENOPKG

تُعاد بواسطة sd_id128_get_machine() و sd_id128_get_machine_app_specific() عندما يكون محتوى /etc/machine-id "غير مهيأ".

تمت الإضافة في الإصدار 253.

-ENOSYS

تُعاد بواسطة sd_id128_get_boot() و sd_id128_get_boot_app_specific() عندما لا يكون /proc/ مثبتًا.

تمت الإضافة في الإصدار 253.

-ENXIO

تُعاد بواسطة sd_id128_get_invocation() إذا لم يتم تعيين معرف استدعاء. تُعاد أيضًا بواسطة sd_id128_get_app_specific()، sd_id128_get_machine_app_specific()، و sd_id128_get_boot_app_specific() عندما يكون المعامل app_id كله أصفار.

تمت الإضافة في الإصدار 242.

-EUCLEAN

تُعاد بواسطة أي من الدوال الموصوفة هنا عندما يكون القيمة المهيأة ذات تنسيق غير صالح.

تمت الإضافة في الإصدار 253.

-EPERM

لم يتمكن من استرداد المعلومات المطلوبة بسبب عدم كفاية الأذونات.

تمت الإضافة في الإصدار 242.

ملاحظات

الدوال الموصوفة هنا متاحة كمكتبة مشتركة، والتي يمكن تجميعها وربطها باستخدام ملف libsystemd pkg-config(1).

يستخدم الكود الموصوف هنا getenv(3)، والتي تم الإعلان عنها بأنها ليست آمنة للاستخدام المتعدد الخيوط. هذا يعني أن الكود الذي يستدعي الدوال الموصوفة هنا يجب ألا يستدعي setenv(3) من خيط موازٍ. يوصى بالقيام بمكالمات لـ setenv() فقط من مرحلة مبكرة من البرنامج عندما لم تبدأ أي خيوط أخرى.

NAME

sd_id128_get_machine, sd_id128_get_boot, sd_id128_get_invocation, sd_id128_get_machine_app_specific, sd_id128_get_boot_app_specific, sd_id128_get_invocation_app_specific, sd_id128_get_app_specific - get unique identifiers

SYNOPSIS

#include <systemd/sd-id128.h>
sd_id128_t sd_id128_get_machine(void);
sd_id128_t sd_id128_get_boot(void);
sd_id128_t sd_id128_get_invocation(void);
sd_bool_t sd_id128_get_machine_app_specific(sd_id128_t app_id, sd_id128_t *ret);
sd_bool_t sd_id128_get_boot_app_specific(sd_id128_t app_id, sd_id128_t *ret);
sd_bool_t sd_id128_get_invocation_app_specific(sd_id128_t app_id, sd_id128_t *ret);
sd_bool_t sd_id128_get_app_specific(sd_id128_t app_id, sd_id128_t *ret);

DESCRIPTION

These functions retrieve various unique identifiers. The identifiers returned by sd_id128_get_machine(), sd_id128_get_boot(), and sd_id128_get_invocation() are 128-bit values stored in sd_id128_t objects.

sd_id128_get_machine() returns the unique identifier of the local machine. This identifier is stored in the machine ID file, typically found at /etc/machine-id or /var/lib/dbus/machine-id. It must be constant across reboots and system reconstructions, but it may change if the machine ID is reset.

sd_id128_get_boot() returns the identifier of the current boot. This identifier is unique per boot and changes every time the system is restarted.

sd_id128_get_invocation() returns the identifier of the current service invocation. This identifier is unique per service invocation and changes every time a service is started.

The functions ending in _app_specific() take an application-specific identifier and combine it with a system-provided unique identifier. The argument app_id is a 128-bit value that should be derived from a fixed, known value for the application. If this value is not available, use SD_ID128_NULL. The result is stored in the location pointed to by ret.

The app_id argument for sd_id128_get_machine_app_specific() is combined with the machine ID. The resulting identifier is unique per machine and per application.

The app_id argument for sd_id128_get_boot_app_specific() is combined with the boot ID. The resulting identifier is unique per boot and per application.

The app_id argument for sd_id128_get_invocation_app_specific() is combined with the invocation ID. The resulting identifier is unique per service invocation and per application.

sd_id128_get_app_specific() is a generic version of the above functions. It takes an identifier which is unique per invocation and combines it with the application-specific identifier app_id. This function is useful for generating unique identifiers for custom daemons that do not necessarily use systemd for service management.

RETURN VALUE

The functions sd_id128_get_machine(), sd_id128_get_boot(), and sd_id128_get_invocation() return the respective 128-bit identifiers.

The functions ending in _app_specific() return a non-zero value on success, or zero on failure. Failure might occur if the underlying unique identifier cannot be determined.

NOTES

All functions listed here are thread-safe.

The identifiers generated by these functions are based on UUIDs (Universally Unique Identifiers). They follow the RFC 4122 standard.

The machine ID is guaranteed to be constant across reboots only if the machine ID file is not modified. If the machine ID file is missing or corrupted, these functions may return an invalid identifier.

For debugging purposes, you can use the systemd-id128 command-line tool to display these identifiers.

Example Usage

To generate a new application-specific identifier, you can use systemd-id128 new:

$ systemd-id128 -p new
As string:
c273277323db454ea63bb96e79b53e97
As UUID:
c2732773-23db-454e-a63b-b96e79b53e97
As man:sd-id128(3) macro:
#define MESSAGE_XYZ SD_ID128_MAKE(c2,73,27,73,23,db,45,4e,a6,3b,b9,6e,79,b5,3e,97)
...

Then use the new identifier in an example application:

/* SPDX-License-Identifier: MIT-0 */
#include <stdio.h>
#include <systemd/sd-id128.h>
#define OUR_APPLICATION_ID SD_ID128_MAKE(c2,73,27,73,23,db,45,4e,a6,3b,b9,6e,79,b5,3e,97)
int main(int argc, char *argv[]) {
  sd_id128_t id;
  sd_id128_get_machine_app_specific(OUR_APPLICATION_ID, &id);
  printf("Our application ID: " SD_ID128_FORMAT_STR "\n", SD_ID128_FORMAT_VAL(id));
  return 0;
}
