DESCRIPTION

The sd-login library provides interfaces to query and monitor login sessions and seats.

It is primarily used by systemd itself, but is also available for general use by other applications.

See systemd-logind(8) for more details on the systemd login manager.

The following functions query information about existing sessions and users:

  • sd_pid_get_session(), sd_uid_get_session(), and sd_session_get_uid() retrieve the session ID associated with a process ID or a user ID, or the user ID associated with a session ID, respectively. The returned string must be freed with free().

  • sd_pid_get_user() and sd_session_get_user() retrieve the user ID and group ID associated with a process ID or session ID.

  • sd_uid_get_state() retrieves the login state of a user. The state is one of "active", "sleeping", or "idle".

  • sd_uid_get_seat() and sd_session_get_seat() retrieve the seat ID associated with a user ID or session ID.

  • sd_seat_get_active() retrieves the session ID of the active session on a given seat.

  • sd_session_is_active() checks if a session is currently active.

  • sd_session_get_state(), sd_session_get_tty(), sd_session_get_display(), sd_session_get_remote_host(), sd_session_get_remote_address(), sd_session_get_remote_credential(), sd_session_get_service(), and sd_session_get_type() retrieve various properties of a login session. The returned strings must be freed with free().

  • sd_get_seats() and sd_get_sessions() retrieve lists of all known seat and session IDs, respectively. The returned arrays of strings must be freed with sd_free_arrays().

The following functions allow monitoring login events via sd_event(3) .

  • sd_login_monitor_new() creates a new login monitor object. It should be associated with an event loop using sd_event_add_io().

  • sd_login_monitor_connect() connects to the systemd login manager.

  • sd_login_monitor_get_fd() returns the file descriptor that can be polled for new events.

  • sd_login_monitor_read() reads all pending events from the file descriptor.

  • sd_login_monitor_enumerate() sends a request to the login manager to enumerate all current sessions and users. The results are delivered as events.

  • sd_login_monitor_subscribe() and sd_login_monitor_unsubscribe() allow subscribing to or unsubscribing from specific event types. The events parameter is a bitmask of SD_LOGIN_MONITOR_EVENT_* flags. sd_login_monitor_get_events() retrieves the currently subscribed events.

  • sd_login_monitor_unref() decreases the reference count of a monitor object.

  • The event structure passed to the callback contains information about the event. The specific fields available depend on the event type. sd_login_monitor_event_get_type() returns the type of the event (e.g., "login", "logout", "change"). sd_login_monitor_event_get_state() returns the new state of the session or user (e.g., "active", "idle", "sleeping"). sd_login_monitor_event_get_path(), sd_login_monitor_event_get_username(), sd_login_monitor_event_get_uid(), sd_login_monitor_event_get_gid(), sd_login_monitor_event_get_tty(), sd_login_monitor_event_get_display(), sd_login_monitor_event_get_remote_host(), sd_login_monitor_event_get_remote_address(), sd_login_monitor_event_get_remote_credential(), sd_login_monitor_event_get_session_id(), sd_login_monitor_event_get_seat_id(), sd_login_monitor_event_get_service(), and sd_login_monitor_event_get_pid() retrieve specific details about the event, such as the affected user, session, or seat. sd_login_monitor_event_is_active() indicates whether the session or user involved in the event is currently active.

The sd_setcred() function should be called by services that need to act as the logged-in user (e.g., on behalf of a graphical session). It performs the necessary operations to set up credentials for the calling process to act as the logged-in user, possibly switching the user ID of the process. This is particularly useful for services that are started before the user logs in, but need to access user resources once the user logs in.

Note that calling setenv(3) from a parallel thread is not recommended. It is recommended to only do calls to setenv() from an early phase of the program when no other threads have been started.
