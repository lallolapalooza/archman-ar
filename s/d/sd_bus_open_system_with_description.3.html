sd_bus_open_system_with_description(3)

الحزمة: systemd-libs

التراخيص: LGPL-2.1-or-later, CC0-1.0, GPL-2.0-or-later WITH Linux-syscall-note

NAME

sd_bus_open_system_with_description, sd_bus_open_user_with_description, sd_bus_open_system_machine_with_description, sd_bus_open_system_with_description_user_unsafe - Connect to the system or user message bus

SYNOPSIS

#include <systemd/sd-bus.h>
int sd_bus_open_system_with_description(sd_bus **bus, const char *description);
int sd_bus_open_user_with_description(sd_bus **bus, const char *description);
int sd_bus_open_system_machine_with_description(sd_bus **bus, const char *machine, const char *description);
int sd_bus_open_system_with_description_user_unsafe(sd_bus **bus, const char *description);

DESCRIPTION

Use sd_bus_open_system_with_description() to connect to the system message bus. Use sd_bus_open_user_with_description() to connect to the per-user message bus.

sd_bus_open_system_machine_with_description() connects to the system message bus of a specified foreign machine (see machinectl(1)). This is intended for use when connecting from within a systemd-powered container or virtual machine.

sd_bus_open_system_with_description_user_unsafe() is similar to sd_bus_open_system_with_description() but connects to the user bus that belongs to the specified user ID (see id parameter of sd_bus_open_user(3)). This function is unsafe if used concurrently with sd_bus_default_user() or sd_bus_open_user() in the same process, as it relies on the global user ID environment variable. It should only be used in single-threaded processes or when the user ID is set early in the process lifetime.

The description parameter may be used to pass a string that describes the connection. This is useful for debugging and logging. It is not used if the bus cannot be opened.

These functions are wrappers around sd_bus_new(3), sd_bus_add_filter(3), sd_bus_request_name(3), sd_bus_call_method(3), sd_bus_process(3), and sd_bus_close(3). They create a new bus object, set up a default event loop, register a default event loop handler, and connect to the bus.

The bus connection object created is associated with the default event loop. See sd_event_new(3) for details.

The connection is established using the appropriate bus address. For the system bus, this is typically defined by the $SYSTEMD_SYSTEM_BUS_ADDRESS environment variable, or defaults to unix:path=/run/dbus/system_bus_socket. For the user bus, this is typically defined by the $XDG_RUNTIME_DIR environment variable, or defaults to unix:path=/run/user/$UID/bus.

The returned bus object is a reference-counted object. You must call sd_bus_unref(3) on it when you are done with it. Use sd_bus_ref(3) to increment the reference count.

These functions are intended to be used as a simple way to acquire a bus connection. For more advanced usage, consider using sd_bus_new(3) directly.

The functions sd_bus_default_system(), sd_bus_default_user(), and sd_bus_default_container() are deprecated and replaced by sd_bus_open_system_with_description(), sd_bus_open_user_with_description(), and sd_bus_open_system_machine_with_description() respectively.

REFERENCE OWNERSHIP

The returned bus object is owned by the caller. The caller must call sd_bus_unref(3) to release it. In order to flush any pending replies and disconnect gracefully, the caller should call sd_bus_close() on the bus object before calling sd_bus_unref().

To flush the unread incoming messages, use sd_bus_close(), which will also close the bus connection. When using the default bus logic, it is a good idea to first invoke sd_bus_flush() followed by sd_bus_close() when a thread or process terminates, and thus its bus connection object should be freed.

Normally, slot objects (as created by sd_bus_add_match(3) and similar calls) keep a reference to their bus connection object, too. Thus, as long as a bus slot object remains referenced its bus object will remain allocated too. Optionally, bus slot objects may be placed in "floating" mode. When in floating mode the life cycle of the bus slot object is bound to the bus object, i.e. when the bus object is freed the bus slot object is automatically unreferenced too. The floating state of a slot object may be controlled explicitly with sd_bus_slot_set_floating(3), though usually floating bus slot objects are created by passing NULL as the slot parameter of sd_bus_add_match() and related calls, thus indicating that the caller is not directly interested in referencing and managing the bus slot object.

The life cycle of the default bus connection should be the responsibility of the code that creates/owns the thread the default bus connection object is associated with. Library code should neither call sd_bus_flush() nor sd_bus_close() on default bus objects unless it does so in its own private, self-allocated thread. Library code should not use the default bus object in other threads unless it is clear that the program using it will life cycle the bus connection object and flush and close it before exiting from the thread. In libraries where it is not clear that the calling program will life cycle the bus connection object, it is hence recommended to use sd_bus_open_system(3) instead of sd_bus_default_system() and related calls.

RETURN VALUE

On success, these calls return 0 or a positive integer. On failure, these calls return a negative errno-style error code.

Errors

Returned errors may indicate the following problems:

-EINVAL

The specified parameters are invalid.

-ENOMEDIUM

The requested bus type is not available because of invalid environment (for example the user session bus is not available because $XDG_RUNTIME_DIR is not set).

-ENOMEM

Memory allocation failed.

-ESOCKTNOSUPPORT

The protocol version required to connect to the selected bus is not supported.

In addition, other connection-related errors may be returned. See sd_bus_send(3).

NOTES

Functions described here are available as a shared library, which can be compiled against and linked to with the libsystemd pkg-config(1) file.

The code described here uses getenv(3), which is declared to be not multi-thread-safe. This means that the code calling the functions described here must not call setenv(3) from a parallel thread. It is recommended to only do calls to setenv() from an early phase of the program when no other threads have been started.
