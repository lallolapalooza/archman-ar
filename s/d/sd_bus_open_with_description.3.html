sd_bus_open_with_description(3)

الحزمة: systemd-libs

التراخيص: LGPL-2.1-or-later, CC0-1.0, GPL-2.0-or-later WITH Linux-syscall-note

NAME

sd_bus_open_with_description, sd_bus_open_user_with_description, sd_bus_open_system_with_description - connect to the system or user bus, or a private bus

SYNOPSIS

#include <systemd/sd-bus.h>

int sd_bus_open_with_description(sd_bus **bus, const char *description);

int sd_bus_open_user_with_description(sd_bus **bus, const char *description);

int sd_bus_open_system_with_description(sd_bus **bus, const char *description);

DESCRIPTION

sd_bus_open_with_description(), sd_bus_open_user_with_description(), and sd_bus_open_system_with_description() may be used to open a connection to the D-Bus system bus, user bus, or a private bus. These functions are similar to sd_bus_open(3), sd_bus_open_user(3) and sd_bus_open_system(3) respectively, but take an additional description parameter.

The description string is used to identify the client in logs and for implementing bus policies. If this string is empty or NULL, a default description is generated.

sd_bus_open_system_with_description() connects to the system bus. This bus is typically used for low-level system services.

sd_bus_open_user_with_description() connects to the user session bus. This bus is typically used for desktop services and applications.

sd_bus_open_with_description() is an alias for sd_bus_open_system_with_description(). This is a historical artifact; use sd_bus_open_system(3) or sd_bus_open_system_with_description() for clarity.

The default bus logic is available via sd_bus_default(), sd_bus_default_user(), and sd_bus_default_system(). These functions return a singleton bus object for the respective bus types. The default bus objects are automatically created on first use, and automatically flushed and closed when the program exits. Library code should not use these functions, but rather explicitly open and manage bus connections using sd_bus_open(3) or related functions, unless it is known that the library runs in its own thread, or that the calling program guarantees proper lifecycle management of the default bus object.

When a bus object is no longer needed, it should be unreferenced using sd_bus_unref(3). When the last reference is dropped, the bus connection is automatically flushed and closed. Alternatively, you may explicitly flush and close the bus connection object by calling sd_bus_flush() and then sd_bus_close().

The default bus connection object is implicitly created when first accessed and automatically flushed and closed when the program exits. Library code should not use the default bus object unless it is known that the program calling the library guarantees proper lifecycle management of the bus connection.

It is generally recommended to use sd_bus_open_system() or sd_bus_open_user() instead of the default bus functions. This allows for explicit control over the bus connection's lifecycle.

When using the default bus logic, it is a good idea to first invoke sd_bus_flush() followed by sd_bus_close() when a thread or process terminates, and thus its bus connection object should be freed.

Normally, slot objects (as created by sd_bus_add_match(3) and similar calls) keep a reference to their bus connection object, too. Thus, as long as a bus slot object remains referenced its bus object will remain allocated too. Optionally, bus slot objects may be placed in "floating" mode. When in floating mode the life cycle of the bus slot object is bound to the bus object, i.e. when the bus object is freed the bus slot object is automatically unreferenced too. The floating state of a bus slot object may be controlled explicitly with sd_bus_slot_set_floating(3), though usually floating bus slot objects are created by passing NULL as the slot parameter of sd_bus_add_match() and related calls, thus indicating that the caller is not directly interested in referencing and managing the bus slot object.

The life cycle of the default bus connection should be the responsibility of the code that creates/owns the thread the default bus connection object is associated with. Library code should neither call sd_bus_flush() nor sd_bus_close() on default bus objects unless it does so in its own private, self-allocated thread. Library code should not use the default bus object in other threads unless it is clear that the program using it will life cycle the bus connection object and flush and close it before exiting from the thread. In libraries where it is not clear that the calling program will life cycle the bus connection object, it is hence recommended to use sd_bus_open_system() instead of sd_bus_default_system() and related calls.

RETURN VALUE

On success, these calls return 0 or a positive integer. On failure, these calls return a negative errno-style error code.

Errors

Returned errors may indicate the following problems:

-EINVAL

The specified parameters are invalid.

-ENOMEDIUM

The requested bus type is not available because of invalid environment (for example the user session bus is not available because $XDG_RUNTIME_DIR is not set).

-ENOMEM

Memory allocation failed.

-ESOCKTNOSUPPORT

The protocol version required to connect to the selected bus is not supported.

In addition, other connection-related errors may be returned. See sd_bus_send(3).

NOTES

Functions described here are available as a shared library, which can be compiled against and linked to with the libsystemd pkg-config(1) file.

The code described here uses getenv(3), which is declared to be not multi-thread-safe. This means that the code calling the functions described here must not call setenv(3) from a parallel thread. It is recommended to only do calls to setenv() from an early phase of the program when no other threads have been started.
