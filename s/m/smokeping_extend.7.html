الاسم

smokeping_extend - ملاحظات حول توسيع Smokeping

نظرة عامة

يهدف هذا المستند إلى توجيه المؤلفين المحتملين لكتابة وحدات استقصاء جديدة لـ Smokeping. يصف بشكل أساسي الواجهة بين Smokeping ووحدات الاستقصاء الخاصة به. إذا بدا الأمر معقدًا جدًا للفهم، فانظر إلى الوحدات الموجودة للحصول على أمثلة.

التعليقات والتغييرات أو الإضافات المقترحة مرحب بها. يرجى إرسالها إلى القائمة البريدية لمستخدمي smokeping. البقع (patches) مقابل مصدر POD لهذا المستند هي الأكثر تقديرًا.

اختيار فئة أساسية

أول شيء يجب أن تقرره هو أي فئة أساسية يجب استخدامها للاستقصاء الخاص بك. بالنسبة لمعظم (إن لم يكن جميع) الاستخدامات، فهو خيار بين Smokeping::probes::base و Smokeping::probes::basefork. الأول مخصص للاستقصاءات التي يمكنها قياس أهدافها دفعة واحدة، بينما الآخر هو للاستقصاءات واحدًا تلو الآخر، ربما في عدة عمليات فرعية متزامنة.

في الوقت الحالي، الاستقصاءات الوحيدة التي تستخدم "Smokeping::probes::base" هي المشتقات من FPing. كل الآخرين يستخدمون "Smokeping::probes::basefork"، ومن المحتمل أن تفعل ذلك أيضًا. سيركز هذا المستند بالتالي على الحالة الأخيرة.

ملف الهيكل العظمي

وحدة Smokeping::probes::skel هي استقصاء غير وظيفي مخصص ليكون أساسًا جيدًا لوحدة استقصاء جديدة. انسخ الملف، "lib/probes/skel.pm"، إلى اسم جديد واملأ الفراغات فقط :) لاحظ أن أسماء وحدات الاستقصاء الحقيقية يجب أن تبدأ بحرف كبير.

توثيق الاستقصاء

يتم إنشاء توثيق الاستقصاء من الشيفرة المصدرية باستخدام وسيطات smokeping "--man" أو "--makepod". يجب أن يشير توثيق POD المضمن إلى هذا التوثيق الفعلي، حتى يرى المستخدمون الفضوليون لأمر "perldoc" ما يحدث. كل الاستقصاءات الحالية تفعل ذلك.

يجب عليك توفير الدالة "pod_hash" التي تُرجع مرجعًا إلى جدول (hash) بأسماء مفاتيح تتوافق مع أسماء الأقسام التي تريدها في صفحة الدليل. أسماء الأقسام المدعومة هي "name"، "overview"، "description"، "authors"، "notes"، "bugs"، و "see_also". إذا كنت لا تحتاج إلى قسم معين، فما عليك سوى تركه.

يتم إنشاء الأقسام الخاصة "synopsis" و "variables" تلقائيًا من وصف المتغيرات الخاصة بك. انظر أدناه.

لاحظ أنه إذا كنت تستخدم 'here documents' ('<<') التي تحتوي على علامات POD بداخلها، يجب عليك تهريب العلامات (escape) حتى لا تظهر في توثيق POD المضمن. معظم الاستقصاءات تفعل ذلك هكذا:

my $e = "=";
my $doc = <<DOC;
${e}head1 SECTION TITLE

وصف الاستقصاء

يجب أن توفر الاستقصاء الدالة "ProbeDesc" التي تُرجع وصفًا موجزًا لما تفعله. سيتم استخدام هذا في الرسوم البيانية التي تنتجها الواجهة الأمامية للويب.

المتغيرات

يجب على جميع استقصاءات Smokeping تعريف متغيراتها عن طريق تنفيذ دالة "probevars" للمتغيرات الخاصة بالاستقصاء ودالة "targetvars" للمتغيرات الخاصة بالهدف. إذا لم تكن تعرف الفرق بينهما بعد، انظر smokeping_examples.

(الاستقصاءات المشتقة من "Smokeping::probes::base" لا تدعم المتغيرات الخاصة بالهدف، لذلك تستخدم فقط الدالة "probevars".)

توفر الفئات الأساسية هذه الدوال أيضًا لتوفير المتغيرات المشتركة لجميع الاستقصاءات (مثل متغير "step" الخاص بالاستقصاء ومتغير "pings" الخاص بالهدف. إذا كنت لا ترغب في إضافة أي شيء إلى متغيرات الفئة الأساسية (ربما لأن جميع متغيراتك خاصة بالهدف، لذلك لا تحتاج إلى متغيرات خاصة بالاستقصاء على الإطلاق)، يمكنك ترك الدالة المقابلة وحيث سيتم وراثتها من الفئة الأساسية.

عندما تقدم دالة "probevars" أو "targetvars" الخاصة بك، يجب عليك دمج متغيراتك مع تلك القادمة من الفئة الأعلى. هناك دالة مساعدة تسمى "_makevars" تقوم بذلك، والنمط الشائع هو

sub probevars {
       my $class = shift;
       return $class->_makevars($class->SUPER::probevars, {
               # ضع متغيراتك هنا
       }
}

يتم تعريف المتغيرات في صيغة تأتي من الوحدة المستخدمة لتحليل ملف التكوين، "Config::Grammar". يجب أن يكون كل متغير جدولاً يستخدم "مفاتيح المتغيرات الخاصة" الموثقة في Config::Grammar. انظر "Smokeping::probes::skel" والاستقصاءات الأخرى للحصول على أمثلة.

للرجوع، إليك المفاتيح التي يجب أن يحتوي عليها الجدول:

المفاتيح التي يجب تقديمها
_doc
وصف المتغير.
_example
قيمة مثال. سيتم استخدام هذا في قسم SYNOPSIS في دليل الاستقصاء.
المفاتيح الاختيارية
_default
قيمة افتراضية سيتم تعيينها للمتغير إذا لم يتم تحديد أي قيمة أو وراثتها.
_re
تعبير عادي سيتم التحقق من القيمة بناءً عليه.
_re_error
سلسلة تحتوي على الخطأ المُعاد في حالة عدم تطابق التعبير العادي (إذا لم يتم تحديده، سيتم إرجاع رسالة خطأ عامة 'syntax error').
_sub
مؤشر دالة. يتم استدعاؤه لكل قيمة، مع تمرير القيمة كوسيطتها الأولى. إذا أعادت الدالة قيمة معرفة، فمن المفترض أن الاختبار لم ينجح وسيتم إنشاء خطأ بسلسلة الإرجاع كمحتوى.

يجب أن تُرجع دوال "probevars" و "targetvars" مراجع جداول تحتوي على أسماء المتغيرات كمفاتيح والجداول الموضحة أعلاه كقيم. بالإضافة إلى ذلك، يتم دعم مفتاح القسم الخاص "Config::Grammar" "_mandatory" ويجب أن يحتوي على مرجع لقائمة المتغيرات الإلزامية. تدرك الدالة "_makevars" هذا المفتاح الخاص وتدمج القوائم الإلزامية في وسيطاتها. لاحظ أنه لا يتم دعم أي مفاتيح قسم خاصة أخرى لـ "Config::Grammar".

التهيئة

smokeping_extend(7) — Smokeping 2.9.0

NAME

smokeping_extend — Extending Smokeping with new probes

OVERVIEW

Smokeping is a \"notice and alert\" service that knows how to keep an eye on a network. It can trace the latency of packet loss of your network connections.

Smokeping is written in Perl and is highly extensible. This document explains how to write new probes for Smokeping.

CHOOSING A BASE CLASS

Most probes can be implemented by subclassing "Smokeping::probes::base" or "Smokeping::probes::basefork".

"basefork" is the base for probes that need to fork a child process to do the actual probing. This is the case for probes that rely on external programs like ping, fping, traceroute, or dig. It handles process management and communication between the parent and child processes.

"base" is a simpler base class for probes that can perform their task within the main Smokeping process, e.g. by using Perl modules like LWP or Net::DNS.

SKELETON FILE

A minimal probe is just a Perl module that exports a probe() subroutine.

package Smokeping::probes::MyProbe;

use strict;
use base qw(Smokeping::probes::basefork); # Or Smokeping::probes::base

sub probe {
    my ($self, $target) = @_;

    # ... probe logic ...
    # return an array of measured latencies
}

1;

The probe file should be named according to the probe type, e.g. "MyProbe.pm" and placed in the "probes" directory within the Smokeping installation. For example, if you want to create a new probe type named "MyProbe", the file would be "lib/Smokeping/probes/MyProbe.pm".

PROBE DOCUMENTATION

Each probe module should contain POD (Plain Old Documentation) explaining how to use it, its configuration parameters, and any special notes.

The documentation should start with a NAME section, followed by OVERVIEW, DESCRIPTION, SYNOPSIS, AUTHOR, and COPYRIGHT sections.

Example:

=head1 NAME

Smokeping::probes::MyProbe - A simple probe for testing purposes

=head1 OVERVIEW

This probe measures the latency to a target host using the external 'ping'
command.

=head1 DESCRIPTION

This probe sends a specified number of ICMP ECHO_REQUEST packets to the target
host and measures the round-trip time.

=head1 SYNOPSIS

  # Example configuration
  + host
  # ... other targets ...
  host.myprobe
    # probe settings go here
    port = 80
    count = 5

=head1 VARIABLES

=over

=item B<port>

The port to connect to. Defaults to 80.

=item B<count>

The number of pings to send. Defaults to 5.

=back

=head1 AUTHOR

Your Name <youremail@example.com>

=head1 COPYRIGHT

Copyright 2023, Your Name

=cut

PROBE DESCRIPTION

The probe description is the text that appears in the Smokeping web interface for the probe type. It is typically set in the "description" subroutine.

sub description {
    return "My custom probe";
}

VARIABLES

Probes can define their own configuration variables. These variables can be accessed within the probe code and can be configured per target in the smokeping_config file.

Variables are defined using the "probevars" subroutine:

sub probevars {
    my $class = shift;
    return $class->_makevars({
        # probe-specific variables
        'myvar' => {
            _default => 'default_value',
            title    => 'My Custom Variable',
        },
    }, {
        # target-specific variables (optional)
        'my_target_var' => {
            _default => 'target_default',
            title    => 'Target Specific Variable',
        },
    });
}

The first hash defines probe-specific variables, and the second defines target-specific variables. The keys of the hashes are the variable names. The values are themselves hashes containing:

  • _default: The default value for the variable.
  • title: A human-readable title for the variable, used in the web interface.

These variables can be accessed within the probe() subroutine via the "$self->{properties}" hash.

INITIALIZATION

If your probe needs to perform any initialization tasks, you can override the "initialize" subroutine:

sub initialize {
    my ($self) = @_;
    # Initialization code here
}

PINGING

The core of a probe is its probe() subroutine. This subroutine takes the target as an argument and should return an array of measured latency times.

The target is represented by a hash reference containing information about the target, including its address and any target-specific variables. You can access the probe-specific variables here via the "$self->{properties}" hash and the target-specific ones via the "$target->{vars}" hash. You get the number of pings needed for the target via the "pings" method: "my $count = $self->pings($target)".

You should return a sorted array of the latency times measured. If a ping fails, don't put anything in the array.

That's it, you're done!

EXAMPLE CONFIGURATIONS

If you would like to provide a documented example configuration for your probe (in addition to the automatically generated SYNOPSIS section in the probe manual), you can do so by adding it to the Smokeping::Examples module. Look for the 'examples' subroutine and add your example there.

Future versions of Smokeping might provide a way to embed examples in the probe modules too. The author's motivation for implementing this would be greatly increased by even a single demand for it, so please speak up if you think you'd use it.

TIMEOUT HANDLING

If you deal with timeouts (for example because your program offers a parameter for specifying the timeout for the pings), you should know a few things.

First, there's timeout logic in "Smokeping::probes::basefork" that kills the probe when the timeout is reached. By default the timeout is (# of pings * 5 seconds) + 1 second. If you expect that your pings can take longer, you should modify the default value of the probe-specific variable "timeout". This would be done like this:

sub probevars {
       my $class = shift;
       my $h = $class->SUPER::probevars;
       $h->{timeout}{_default} = 10; # override the superclass default
       return $class->_makevars($h, {
               # your variables go here
       }
}

If you want to provide a target-specific "timeout" setting, you should delete the probe-specific variable and be sure to provide a default for your target-specific one. See eg. "Smokeping::probes::AnotherDNS" for an example of how this is done.

Providing a target-specific "timeout" will make the timeout in "Smokeping::probes::basefork" be (# of pings * the maximum timeout of all targets) + 1 second. The 1 second is added so that the own timeout logic of the probe has time to kick in even in the worst case (ie. all pings are lost) before "Smokeping::probes::basefork" starts killing the processes.
