الاسم

systemd-soft-reboot.service - عملية إعادة تشغيل مساحة المستخدم

الملخص

systemd-soft-reboot.service

الوصف

systemd-soft-reboot.service هي خدمة نظام يتم سحبها بواسطة soft-reboot.target وهي مسؤولة عن تنفيذ عملية إعادة تشغيل لمساحة المستخدم فقط. عند استدعائها، سترسل إشارة SIGTERM إلى أي عمليات متبقية قيد التشغيل (لكنها لا تنتظر حتى تنتهي العمليات)، وتتبعها بإشارة SIGKILL. إذا كان الدليل /run/nextroot/ موجودًا (والذي قد يكون دليلًا عاديًا، أو نقطة تحميل دليل، أو رابطًا رمزيًا لكليهما) فسيتم تبديل نظام الملفات الجذري إليه. ثم تعيد تنفيذ مدير الخدمة من نظام الملفات الجذري (الذي قد يكون جديدًا الآن)، والذي سيضع معاملة إقلاع جديدة في قائمة الانتظار كما في إعادة التشغيل العادية.

تسمح عملية إعادة تشغيل مساحة المستخدم هذه بتحديث أو إعادة تعيين كامل مساحة المستخدم مع الحد الأدنى من وقت التعطل، حيث أن عملية إعادة التشغيل لا تمر عبر:

•المرحلة الثانية من الإغلاق العادي، كما تم تنفيذها بواسطة systemd-shutdown(8).
•المرحلة الثالثة من الإغلاق العادي، أي العودة إلى سياق initrd.
•عملية إعادة تشغيل الجهاز.
•تهيئة البرنامج الثابت.
•تهيئة محمل الإقلاع.
•تهيئة النواة.
•تهيئة initrd.

ومع ذلك، فإن هذا الشكل من إعادة التشغيل يأتي مع عيوب أيضًا:

•يبقى تحديث نظام التشغيل غير مكتمل، حيث لا تتم إعادة تشغيل النواة وتستمر في العمل.
•لا تتم إعادة تعيين إعدادات النواة (مثل إعدادات /proc/sys/، المعروفة باسم "sysctl"، أو إعدادات /sys/).

يمكن معالجة هذه القيود بوسائل مختلفة، وهي خارج نطاق هذه الوثائق، مثل التصحيح المباشر للنواة وملفات /etc/sysctl.d/ الشاملة بما يكفي.

مرور الموارد

يمكن تمرير موارد نظام التشغيل المختلفة قيد التشغيل من تشغيل نظام إلى التالي، من خلال عملية إعادة تشغيل مساحة المستخدم. على وجه الخصوص:

•يتم تمرير واصفات الملفات الموضوعة في مخزن واصفات الملفات للخدمات التي تظل نشطة حتى النهاية إلى الإقلاع التالي، حيث يتم وضعها في مخزن واصفات الملفات لنفس الوحدة. لكي يعمل هذا، يجب أن تعلن الوحدات عن DefaultDependencies=no (وتتجنب Conflicts=shutdown.target يدويًا أو ما شابه) لضمان عدم إنهاءها كالمعتاد أثناء عملية إغلاق النظام. بدلاً من ذلك، استخدم FileDescriptorStorePreserve= للسماح بتثبيت مخزن واصفات الملفات حتى عندما تكون الوحدة متوقفة. راجع systemd.service(5) للحصول على تفاصيل حول مخزن واصفات الملفات.
•بالمثل، تبقى واصفات الملفات المرتبطة بوحدات .socket مفتوحة (وقابلة للاتصال) إذا لم يتم إيقاف الوحدات أثناء الانتقال. (يتم تحقيق ذلك عبر DefaultDependencies=no.)
•يبقى نظام الملفات /run/ مثبتًا ومليئًا ويمكن استخدامه لتمرير معلومات الحالة بين دورات إعادة تشغيل مساحة المستخدم هذه.
•قد تستمر عمليات الخدمة في العمل خلال الانتقال، متجاوزة إعادة التشغيل الناعمة وتدخل الجلسة التالية، إذا تم وضعها في خدمات تظل نشطة حتى نهاية الإغلاق (والذي يتم تحقيقه مرة أخرى عبر DefaultDependencies=no). يجب أيضًا إعدادها لتجنب أن يتم قتلها بواسطة SIGTERM و SIGKILL المذكورة أعلاه عبر SurviveFinalKillSignal=yes، ويجب أيضًا تكوينها لتجنب التوقف عند العزل عبر IgnoreOnIsolate=yes. يجب أيضًا تكوينها للتوقف عند الإغلاق العادي، وإعادة التشغيل، ووضع الصيانة. أخيرًا، يجب تقديمها بعد basic.target لضمان الترتيب الصحيح عند الإقلاع. لاحظ أنه في حالة استخدام أي وحدات جديدة أو مخصصة للعزل، أو تلك التي تنفذ وظيفة إغلاق معادلة، فسيتعين أيضًا تكوينها يدويًا للترتيب والتضارب الصحيحين. على سبيل المثال: 
[Unit]
Description=My Surviving Service
SurviveFinalKillSignal=yes
IgnoreOnIsolate=yes
DefaultDependencies=no
After=basic.target
Conflicts=reboot.target kexec.target poweroff.target halt.target rescue.target emergency.target
Before=shutdown.target rescue.target emergency.target
[Service]
Type=oneshot
ExecStart=sleep infinity
•بالإضافة إلى ما سبق، تحتاج الوحدات المُقوالبة أيضًا إلى ملف تكوين لشريحتها، لأنها بشكل افتراضي تستخدم شريحة مسماة باسم الجزء غير المُقوالب للوحدة. على سبيل المثال، لمثيل foo@test.service، يمكن إضافة وحدة system-foo.slice بالمحتوى التالي: 
[Unit]
SurviveFinalKillSignal=yes
IgnoreOnIsolate=yes
DefaultDependencies=no
•قد تبقى عمليات تحميل نظام الملفات مثبتة خلال الانتقال، ويمكن إرفاق تخزين معقد، إذا تم تكوينها لتبقى حتى نهاية عملية الإغلاق. (يتم تحقيق ذلك أيضًا عبر DefaultDependencies=no، وتجنب Conflicts=umount.target)
•إذا نشرت الوحدة خدمة عبر D-Bus، فيجب إعادة إنشاء الاتصال بعد إعادة التشغيل الناعمة لأن وسيط D-Bus سيتم إيقافه ثم تشغيله مرة أخرى. عند استخدام مكتبة sd-bus(3) يمكن تحقيق ذلك عن طريق تكييف المثال التالي.

typedef struct object {
  const char *example;
  sd_bus **bus;
  sd_event **event;
} object;
static int property_get(
                sd_bus *bus,
                const char *path,
                const char *interface,
                const char *property,
                sd_bus_message *reply,
                void *userdata,
                sd_bus_error *error) {
  object *o = userdata;
  if (strcmp(property, "Example") == 0)
    return sd_bus_message_append(reply, "s", o->example);
  return sd_bus_error_setf(error,
                           SD_BUS_ERROR_UNKNOWN_PROPERTY,
                           "Unknown property '%s'",
                           property);

static int setup(object *o);
static int on_disconnect(sd_bus_message *message, void *userdata, sd_bus_error *ret_error) {
  int r;
  r = setup((object *)userdata);
  if (r < 0) {
    object *o = userdata;
    r = sd_event_exit(*o->event, r);
    if (r < 0)
      return log_error(r, "sd_event_exit()");
  }
  return 1;
}
