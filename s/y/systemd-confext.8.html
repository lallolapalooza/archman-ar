systemd-sysext, systemd-sysext.service, systemd-sysext-initrd.service, systemd-confext, systemd-confext.service, systemd-confext-initrd.service - تفعيل صور امتداد النظام

الوصف

يقوم systemd-sysext بتفعيل/إلغاء تفعيل صور امتداد النظام. يمكن لصور امتداد النظام – ديناميكيًا في وقت التشغيل – توسيع التسلسلات الهرمية للمجلدين /usr/ و /opt/ بملفات إضافية. هذا مفيد بشكل خاص في صور النظام غير القابلة للتعديل حيث يلزم توسيع التسلسل الهرمي /usr/ و/أو /opt/ الموجود على نظام ملفات للقراءة فقط مؤقتًا في وقت التشغيل دون إجراء أي تعديلات دائمة.

يجب أن تحتوي صور امتداد النظام على ملفات ومجلدات تشبه شجرة نظام التشغيل العادية. عند تفعيل صورة امتداد نظام واحدة أو أكثر، يتم دمج التسلسلات الهرمية /usr/ و /opt/ الخاصة بها عبر "overlayfs" مع نفس التسلسلات الهرمية لنظام التشغيل المضيف، ويتم تحميل التسلسلات الهرمية /usr/ و /opt/ للمضيف فوقها ("الدمج"). عند إلغاء تفعيلها، يتم تفكيك نقطة التحميل – مما يكشف مرة أخرى عن النسخة الأصلية غير المعدلة للتسلسل الهرمي للمضيف ("إلغاء الدمج"). وبالتالي، يجعل الدمج موارد الامتداد تظهر فجأة أسفل التسلسلات الهرمية /usr/ و /opt/ كما لو كانت مضمنة في صورة نظام التشغيل نفسها. إلغاء الدمج يجعلها تختفي مرة أخرى، تاركًا فقط الملفات التي تم شحنها مع صورة نظام التشغيل نفسها.

الملفات والمجلدات الموجودة في صور الامتداد خارج التسلسلات الهرمية /usr/ و /opt/ لا يتم دمجها، وبالتالي ليس لها أي تأثير عند تضمينها في صورة امتداد نظام. على وجه الخصوص، الملفات الموجودة في /etc/ و /var/ المضمنة في صورة امتداد نظام لن تظهر في التسلسلات الهرمية المقابلة بعد التفعيل.

صور امتداد النظام للقراءة فقط بشكل افتراضي. على أنظمة الملفات المضيفة القابلة للتعديل، تصبح التسلسلات الهرمية /usr/ و /opt/ للقراءة فقط أثناء دمج الامتدادات، ما لم يتم تمكين القابلية للتعديل. يمكن تمكين القابلية للتعديل عبر الخيار --mutable=؛ انظر "القابلية للتعديل" أدناه لمزيد من المعلومات.

يُفترض أن تكون امتدادات النظام إضافية بحتة، أي أنها يفترض أن تتضمن فقط ملفات غير موجودة في صورة النظام الأساسي الأساسية. ومع ذلك، تسمح الآلية الأساسية (overlayfs) بتراكب الملفات أو إزالتها، ولكن يوصى بعدم استخدام هذا.

يمكن توفير صور امتداد النظام بالتنسيقات التالية:

1. مجلدات عادية أو وحدات فرعية btrfs تحتوي على شجرة نظام التشغيل
2. صور أقراص بعلامة قرص GPT، تتبع مواصفات الأقسام القابلة للاكتشاف[1]
3. صور أقراص تفتقر إلى جدول أقسام، مع نظام ملفات Linux عاري (مثل erofs، squashfs أو ext4)

هذه التنسيقات للصور هي نفسها التي تدعمها systemd-nspawn(1) عبر مفاتيح --directory=/--image= وتلك التي يدعمها مدير الخدمة عبر RootDirectory=/RootImage=. على غرارها، يمكنها اختياريًا حمل معلومات مصادقة Verity.

يتم البحث عن امتدادات النظام في الدلائل /etc/extensions/, /run/extensions/ و /var/lib/extensions/. الدليلان الأولان المذكوران ليسا مناسبين لحمل الصور الثنائية الكبيرة، ولكنهما لا يزالان مفيدين لحمل روابط رمزية إليها. المكان الأساسي لتثبيت امتدادات النظام هو /var/lib/extensions/. أي مجلدات يتم العثور عليها في هذه الدلائل البحثية تعتبر صور امتداد قائمة على المجلدات؛ أي ملفات باللاحقة .raw تعتبر صور امتداد قائمة على صور الأقراص. عند استدعائه في initrd، يتم تضمين الدليل الإضافي /.extra/sysext/ في الدلائل التي يتم البحث فيها عن صور الامتداد. لاحظ مع ذلك، أنه افتراضيًا ينطبق سياسة صورة أضيق على الصور الموجودة هناك، رغم ذلك، انظر أدناه. يتم ملء هذا الدليل بواسطة systemd-stub(7) مع صور الامتداد الموجودة في قسم EFI النظام الخاص بالنظام.

أثناء التمهيد، يتم تفعيل صور امتداد النظام تلقائيًا، إذا تم تمكين service systemd-sysext.service. لاحظ أن هذه الخدمة تعمل فقط بعد تحميل أنظمة الملفات الأساسية حيث قد توجد امتدادات النظام. هذا يعني أنها غير مناسبة لشحن الموارد التي تعالجها الأنظمة الفرعية التي تعمل في أقرب وقت من التمهيد. على وجه التحديد، صور امتداد النظام غير مناسبة لشحن خدمات النظام أو تعريفات systemd-sysusers(8). انظر صفحة الخدمات المحمولة[2] للحصول على آلية بسيطة لشحن خدمات النظام في صور الأقراص، بطريقة مشابهة لامتدادات النظام. لاحظ العزل المختلف لهاتين الآليتين: بينما توسع امتدادات النظام مباشرة صورة نظام التشغيل الأساسية بملفات إضافية تظهر بطريقة مشابهة جدًا كما لو كانت مشحونة في صورة النظام نفسها وبالتالي لا تتضمن أي عزل أمني، فإن الخدمات المحمولة تتضمن تأمين مستوى الخدمة بطريقة أو بأخرى. تم ضمان انتهاء خدمة systemd-sysext.service من بدء التشغيل قبل الوصول إلى basic.target؛ أي، في الوقت الذي تبدأ فيه الخدمات العادية (تلك التي لا تستخدم DefaultDependencies=no)، تتوفر الملفات والمجلدات التي توفرها امتدادات النظام في /usr/ و /opt/ ويمكن الوصول إليها.

لاحظ أنه لا يوجد مفهوم لتمكين/تعطيل امتدادات النظام المثبتة: يتم تفعيل جميع امتدادات النظام المثبتة تلقائيًا عند التمهيد. ومع ذلك، يمكنك وضع دليل فارغ باسم يشبه اسم الامتداد (بدون .raw) في /etc/extensions/ لـ "إخفاء" امتداد بنفس الاسم في مجلد نظام ذي أسبقية أقل.

يتم فرض آلية بسيطة للتوافق مع الإصدارات: يجب أن تحمل صورة امتداد النظام ملف /usr/lib/extension-release.d/extension-release.NAME، والذي يجب أن يطابق اسم صورتها، والذي تتم مقارنته بملف os-release الخاص بالمضيف: يجب أن تتطابق حقول ID= الموجودة ما لم يتم تعيين "_any" للامتداد. إذا لم يكن ID= للامتداد "_any"، فيجب أن يتطابق حقل SYSEXT_LEVEL= (إذا تم تعريفه). إذا لم يتم تعريف الأخير، فيجب أن يتطابق حقل VERSION_ID= بدلاً من ذلك. إذا قام الامتداد بتعريف حقل ARCHITECTURE= وكانت القيمة ليست "_any"، فيجب أن تتطابق مع معمارية النواة التي يتم الإبلاغ عنها بواسطة uname(2) ولكن معرفات المعمارية المستخدمة هي نفسها لـ ConditionArchitecture= الموصوفة في systemd.unit(5). يمكن تعيين EXTENSION_RELOAD_MANAGER= إلى 1 إذا كان الامتداد يتطلب إعادة تحميل مدير الخدمة بعد تطبيق الامتداد. لاحظ أنه للأسباب المذكورة سابقًا، تظل الخدمات المحمولة[2] هي الطريقة الموصى بها لشحن خدمات النظام. يجب ألا تقوم امتدادات النظام بشحن ملف /usr/lib/os-release (لأن ذلك سيتم دمجه في شجرة /usr/ للمضيف، متجاوزًا بيانات إصدار نظام التشغيل المضيف، وهو أمر غير مرغوب فيه). يتبع ملف extension-release نفس التنسيق والدلالات، ويحمل نفس المحتوى، مثل ملف os-release الخاص بنظام التشغيل، ولكنه يصف الموارد الموجودة في صورة الامتداد.

يتبع مفهوم systemd-confext نفس مبدأ وظيفة systemd-sysext(8) ولكن بدلاً من العمل على /usr و /opt، يقوم confext بتوسيع /etc فقط. الملفات والمجلدات الموجودة في صور confext خارج التسلسل الهرمي /etc/ لا يتم دمجها، وبالتالي ليس لها أي تأثير عند تضمينها في الصورة. تنسيقات هذه الصور هي نفسها صور sysext. سيتم تحميل التسلسل الهرمي المدمج بـ "nosuid" و (إذا لم يتم تعطيله عبر --noexec=false) "noexec".

تمامًا مثل sysexts، صور confext للقراءة فقط بشكل افتراضي. سيؤدي دمج confexts على أنظمة الملفات المضيفة القابلة للتعديل إلى جعل /etc/ للقراءة فقط. كما هو الحال مع sysexts، يمكن تمكين القابلية للتعديل عبر الخيار --mutable=. ارجع إلى "القابلية للتعديل" أدناه لمزيد من المعلومات.

يتم البحث عن confexts في الدلائل /run/confexts/, /var/lib/confexts/, /usr/lib/confexts/ و /usr/local/lib/confexts/. الدليل الأول المذكور ليس مناسبًا لحمل الصور الثنائية الكبيرة، ولكنه لا يزال مفيدًا لحمل روابط رمزية إليها. المكان الأساسي لتثبيت امتدادات التكوين هو /var/lib/confexts/. أي مجلدات يتم العثور عليها في هذه الدلائل البحثية تعتبر صور confext قائمة على المجلدات؛ أي ملفات باللاحقة .raw تعتبر صور امتداد قائمة على صور الأقراص.

مرة أخرى، تمامًا مثل صور sysext، ستحتوي صور confext على ملف /etc/extension-release.d/extension-release.NAME، والذي يجب أن يتطابق مع اسم الصورة

هذا الموقع غير مرتبط بـ Arch Linux ولا تابع له بأي شكل من الأشكال. المحتوى هو ترجمة فقط لصفحات دليل Arch المنشورة على man.archlinux.org.

systemd-confext(8) — systemd manual

NAME

systemd-confext.service, systemd-confext - Manage systemd configuration extensions

SYNOPSIS

systemd-confext [OPTIONS...] {COMMAND}

DESCRIPTION

systemd-confext manages systemd configuration extensions. Configuration extensions are a mechanism to add or override configuration files in systemd units and related configuration directories. This is useful for adding custom units, drop-in files, or modifying existing configurations without directly altering the original files.

The tool operates on directories containing configuration files, referred to as extensions. These extensions are typically located in directories like /etc/systemd/system-extensions/. systemd-confext can merge these extensions into the main configuration directories (e.g., /etc/systemd/system/), refresh existing configurations, or unmerge them.

USES

Configuration extensions are discovered automatically by systemd services and generators if placed in the correct locations. They allow for modular configuration management, separating customizations from base system configurations.

MUTABILITY

Configuration extensions can be merged, unmerged, or refreshed. Merging applies the extensions to the main configuration directories, while unmerging reverts these changes. Refreshing ensures that systemd is aware of any changes made to the extensions.

COMMANDS

merge
Merges configuration extensions into the main systemd configuration directories. This command processes extensions found in designated extension directories and applies them to their corresponding main configuration locations.
unmerge
Reverts the changes made by merging configuration extensions. This command removes any files or directories that were added or modified by a previous merge operation.
refresh
Refreshes the systemd configuration by reprocessing existing extensions. This is useful after making changes to the extension files themselves to ensure systemd picks up the updates.

OPTIONS

The following options are understood:

--root=ROOT

Specifies the root directory for operating on an alternative system image. This is useful for system maintenance or when operating on a read-only system.

--all

When used with merge, merges all configuration extensions found. By default, only extensions that are not already managed or overridden are merged.

--noexec=BOOL

When merging configuration extensions into /etc/ the "MS_NOEXEC" mount flag is used by default. This option can be used to disable it.

Added in version 254.

--no-reload

When used with merge, unmerge or refresh, do not reload daemon after executing the changes even if an extension that is applied requires a reload via the EXTENSION_RELOAD_MANAGER= set to 1.

Added in version 255.

--no-pager

Do not pipe output into a pager.

--no-legend

Do not print the legend, i.e. column headers and the footer with hints.

--json=MODE

Shows output formatted as JSON. Expects one of "short" (for the shortest possible output without any redundant whitespace or line breaks), "pretty" (for a pretty version of the same, with indentation and line breaks) or "off" (to turn off JSON output, the default).

EXIT STATUS

On success, 0 is returned.
