SYSUPDATE.D(5) sysupdate.d SYSUPDATE.D(5)

NAME

sysupdate.d - Transfer Definition Files for Automatic Updates

SYNOPSIS

/etc/sysupdate.d/*.transfer
/run/sysupdate.d/*.transfer
/usr/local/lib/sysupdate.d/*.transfer
/usr/lib/sysupdate.d/*.transfer

DESCRIPTION

These files describe how specific resources on the local system shall be updated from a remote source. Each such file defines one such transfer: typically a remote HTTP/HTTPS resource as source; and a local file, directory or partition as target. This may be used as a simple, automatic, atomic update mechanism for the OS itself, for containers, portable services or system extension images — but in fact may be used to update any kind of file from a remote source.

The systemd-sysupdate(8) command reads these files and uses them to determine which local resources should be updated, and then executes the update.

Both the remote HTTP/HTTPS source and the local target typically exist in multiple, concurrent versions, in order to implement flexible update schemes, e.g. A/B updating (or a superset thereof, e.g. A/B/C, A/B/C/D, ...).

Each *.transfer file defines one transfer, i.e. describes one resource to update. Typically, multiple of these files (i.e. multiple of such transfers) are defined together, and are bound together by a common version identifier in order to update multiple resources at once on each update operation, for example to update a kernel, a root file system and a Verity partition in a single, combined, synchronized operation, so that only a combined update of all three together constitutes a complete update. We'll call such a collection of transfers a target. systemd-sysupdate(8) always operates on a single target.

Transfers may be grouped together into sets that can be individually enabled or disabled by the system administrator, called "Optional Features": sysupdate.features(5).

Each *.transfer file contains three sections: [Transfer], [Source] and [Target].

BASIC MODE OF OPERATION

Disk-image based OS updates typically consist of multiple different resources that need to be updated together, for example a secure OS update might consist of a root file system image to drop into a partition, a matching Verity integrity data partition image, and a kernel image prepared to boot into the combination of the two partitions. The first two resources are files that are downloaded and placed in a disk partition, the latter is a file that is downloaded and placed in a regular file in the boot file system (e.g. EFI system partition). Hence, during an update of a hypothetical operating system "foobarOS" to a hypothetical version 47 the following operations should take place:

1.A file "https://download.example.com/foobarOS_47.root.xz" should be downloaded, decompressed and written to a previously unused partition with GPT partition type UUID 4f68bce3-e8cd-4db1-96e7-fbcaf984b709 for x86-64, as per Discoverable Partitions Specification[1].
2.Similarly, a file "https://download.example.com/foobarOS_47.verity.xz" should be downloaded, decompressed and written to a previously empty partition with GPT partition type UUID of 2c7357ed-ebd2-46d9-aec1-23d437ec2bf5 (i.e. the partition type for Verity integrity information for x86-64 root file systems).
3.Finally, a file "https://download.example.com/foobarOS_47.efi" (a unified kernel, as per Boot Loader Specification[2] Type #2) should be downloaded, decompressed and written to the $BOOT file system, i.e. to EFI/Linux/foobarOS_47.efi in the ESP or XBOOTLDR partition.

The version-independent generalization of this would be (using the special marker "@v" as wildcard for the version identifier):

1.A transfer of a file "https://download.example.com/foobarOS_@v.root.xz" → a local, previously empty GPT partition of type 4f68bce3-e8cd-4db1-96e7-fbcaf984b709, with the label to be set to "foobarOS_@v".
2.A transfer of a file "https://download.example.com/foobarOS_@v.verity.xz" → a local, previously empty GPT partition of type 2c7357ed-ebd2-46d9-aec1-23d437ec2bf5, with the label to be set to "foobarOS_@v_verity".
3.A transfer of a file "https://download.example.com/foobarOS_@v.efi" → a local file $BOOT/EFI/Linux/foobarOS_@v.efi.

An update can only complete if the relevant URLs provide their resources for the same version, i.e. for the same value of "@v".

The above may be translated into three *.transfer files in sysupdate.d/, one for each resource to transfer. The *.transfer files configure the type of download, and what place to write the download to (i.e. whether to a partition or a file in the file system). Most importantly these files contain the URL, partition name and filename patterns shown above that describe how these resources are called on the source and how they shall be called on the target.

In order to enumerate available versions and figuring out candidates to update to, a mechanism is necessary to list suitable files:

•For partitions: the surrounding GPT partition table contains a list of defined partitions, including a partition type UUID and a partition label (in this scheme the partition label plays a role for the partition similar to the filename for a regular file).
•For regular files: the directory listing of the directory the files are contained in provides a list of existing files in a straightforward way.
•For HTTP/HTTPS sources a simple scheme is used: a manifest file SHA256SUMS, following the format defined by sha256sum(1), lists file names and their SHA256 hashes.

Transfers are done in the alphabetical order of the .transfer file names they are defined in. First, the resource data is downloaded directly into a target file/directory/partition. Once this is completed for all defined transfers, in a second step the files/directories/partitions are renamed to their final names as defined by the target MatchPattern=, again in the order the .transfer transfer file names dictate. This step is not atomic, however it is guaranteed to be executed strictly in order with suitable disk synchronization in place. Typically, when updating an OS one of the transfers defines the entry point when booting. Thus it is generally a good idea to order the resources via the transfer configuration file names so that the entry point is written last, ensuring that any abnormal termination does not leave an entry point around whose backing is not established yet. In the example above it would hence make sense to establish the EFI kernel image last and thus give its transfer configuration file the alphabetically last name.

See below for an extended, more specific example based on the above.

RESOURCE TYPES

Each transfer file defines one source resource to transfer to one target resource. The following resource types are supported:

1.Resources of type "url-file" encapsulate a file on a web server, referenced via a HTTP or HTTPS URL. When an update takes place, the file is downloaded and decompressed and then written to the target file or partition. This resource type is only available for sources, not for targets. The list of available versions of resources of this type is encoded in SHA256SUMS manifest files, accompanied by SHA256SUMS.gpg detached signatures.
2.The "url-tar" resource type is similar, but the file must be a .tar archive. When an update takes place, the file is decompressed and unpacked into a directory or btrfs subvolume. This resource type is only available for sources, not for targets. Just like "url-file", "url-tar" version enumeration makes use of SHA256SUMS files, authenticated via SHA256SUMS.gpg.

3. نوع المورد "regular-file" يغلف ملفًا عاديًا محليًا على القرص. أثناء التحديثات، يتم فك ضغط الملف وكتابته إلى الملف أو القسم الهدف. هذا النوع من الموارد متاح كمصدر وكهدف. عند التحديث، لا يتم إجراء أي تحقق من التكامل أو المصادقة للموارد من هذا النوع.
4. نوع المورد "partition" مشابه لـ "regular-file"، ويغلف قسم GPT على القرص. عند التحديث، يجب أن يكون القسم موجودًا بالفعل، وأن يكون له نوع قسم GPT الصحيح. يعتبر القسم الذي تم تعيين تسميته إلى "_empty" فارغًا، وهو مرشح لوضع مورد تم تنزيله حديثًا فيه. تُستخدم تسمية قسم GPT لتخزين معلومات الإصدار، بمجرد تحديث القسم. هذا النوع من الموارد متاح فقط للموارد الهدف.
5. نوع المورد "tar" يغلف ملفات أرشيف .tar محلية. عند حدوث تحديث، يتم فك ضغط الملفات وفك حزمها في دليل هدف أو subvolume btrfs. السلوك الخاص بـ "tar" و "url-tar" متشابه بشكل عام، ولكن الأخير يقوم بالتنزيل من مصادر بعيدة، ويجري فحوصات التكامل والمصادقة بينما الأول لا يفعل ذلك. نوع المورد "tar" متاح فقط للموارد المصدر.
6. نوع المورد "directory" يغلف أشجار الدلائل المحلية. هذا النوع متاح لكل من موارد المصدر والهدف. إذا تم إجراء تحديث على مورد مصدر من هذا النوع، يتم إجراء نسخ متكرر للدليل.
7. نوع المورد "subvolume" مطابق لـ "directory"، باستثناء عند استخدامه كهدف، حيث يتم وضع شجرة الملفات في subvolume btrfs بدلاً من دليل عادي، إذا كان نظام الملفات الأساسي يدعم ذلك (أي أنه btrfs).

أنماط المطابقة

عادةً ما توجد موارد المصدر والهدف في إصدارات متعددة بشكل متزامن. تتم عملية التحديث عندما يكون أحدث إصدارات المصدر أحدث من أحدث إصدارات الهدف. لتحديد أحدث إصدار للموارد، يتم استخدام قائمة الدلائل، أو قائمة الأقسام، أو قائمة البيانات الوصفية، ويتم تحديد مجموعة فرعية من الإدخالات المؤهلة من ذلك، ويتم استخراج معرف الإصدار من أسماء الملفات أو تسميات الأقسام لهذه الإدخالات المحددة. يتم تحديد المجموعة الفرعية واستخراج معرف الإصدار (بالإضافة إلى بيانات وصفية أخرى محتملة) عبر أنماط المطابقة، التي تم تكوينها في
MatchPattern= في أقسام [Source] و [Target]. هذه الأنماط عبارة عن سلاسل تصف كيفية تسمية الملفات أو الأقسام، مع أحرف بدل مسماة لمجالات محددة مثل معرف الإصدار. أحرف البدل التالية معرفة:

الجدول 2. أحرف البدل لأنماط المطابقة

حرف بدل الوصف التنسيق ملاحظات
"@v" معرف الإصدار سلسلة إصدار صالحة إلزامي
"@u" معرف UUID لقسم GPT سلسلة UUID صالحة 128 بت ذات صلة فقط إذا تم اختيار نوع المورد الهدف كـ partition
"@f" أعلام قسم GPT عدد صحيح سداسي عشري منسق ذات صلة فقط إذا تم اختيار نوع المورد الهدف كـ partition
"@a" علم قسم GPT NoAuto إما "0" أو "1" يتحكم في بت NoAuto لأعلام قسم GPT، وفقًا لـ Discoverable Partitions Specification[1]؛ ذو صلة فقط إذا تم اختيار نوع المورد الهدف كـ partition
"@g" علم قسم GPT GrowFileSystem إما "0" أو "1" يتحكم في بت GrowFileSystem لأعلام قسم GPT، وفقًا لـ Discoverable Partitions Specification[1]؛ ذو صلة فقط إذا تم اختيار نوع المورد الهدف كـ partition
"@r" علم القراءة فقط إما "0" أو "1" يتحكم في بت ReadOnly لأعلام قسم GPT، وفقًا لـ Discoverable Partitions Specification[1] وأعلام القراءة فقط الأخرى في الإخراج، انظر ReadOnly= أدناه
"@t" وقت تعديل الملف عدد صحيح عشري منسق، ميكرو ثانية منذ حقبة يونكس 1 يناير 1970 ذات صلة فقط إذا تم اختيار نوع المورد الهدف كـ regular-file
"@m" وضع وصول الملف عدد صحيح ثماني منسق، بأسلوب يونكس ذات صلة فقط إذا تم اختيار نوع المورد الهدف كـ regular-file
"@s" حجم الملف بعد فك الضغط عدد صحيح عشري منسق مفيد لقياس التقدم ولتحسين منطق تخصيص القسم
"@d" المحاولات التي تم إجراؤها عدد صحيح عشري منسق مفيد عند العمل مع ملفات صور النواة، وفقًا لـ Automatic Boot Assessment[3]
"@l" المحاولات المتبقية عدد صحيح عشري منسق مفيد عند العمل مع ملفات صور النواة، وفقًا لـ Automatic Boot Assessment[3]
"@h" تجزئة SHA256 للملف المضغوط 64 حرفًا سداسي عشري تجزئة SHA256 للملف المضغوط؛ غير مفيدة لـ url-file أو url-tar حيث يتم تضمين تجزئة SHA256 بالفعل في ملف البيانات الوصفية على أي حال

من بين أحرف البدل هذه، فقط
"@v" يجب أن يكون موجودًا في نمط صالح، وجميع أحرف البدل الأخرى اختيارية. يمكن استخدام كل حرف بدل مرة واحدة على الأكثر في كل نمط. نمط بدل نموذجي يطابق صورة مصدر نظام الملفات يمكن أن يكون "MatchPattern=foobar_@v.raw.xz"، أي ملف يبدأ اسمه بـ "foobar_"، يتبعه معرف إصدار وينتهي بـ ".raw.xz".

لا تخلط بين بادئة حرف البدل "@" لمطابقة الأنماط وبين بادئة توسيع المحدد "%". الأولى تغلف جزءًا متغيرًا من سلسلة نمط المطابقة، والأخيرة عبارة عن اختصارات بسيطة يتم توسيعها أثناء تحليل الملفات المُسقطة. للحصول على تفاصيل حول المحددات، انظر أدناه.

خيارات قسم [TRANSFER]

يحدد هذا القسم خصائص عامة لهذا النقل.

MinVersion=

يحدد الحد الأدنى للإصدار المطلوب لهذا النقل ليحدث. إذا كانت أنماط المصدر أو الهدف في تعريف النقل هذا تطابق ملفات أقدم من هذا الإصدار، فسيتم اعتبارها قديمة، ولن يتم النظر فيها أبدًا لعملية التحديث.

تمت الإضافة في الإصدار 251.

ProtectVersion=

يأخذ سلسلة إصدار واحد أو أكثر لتمييزها على أنها "محمية". لا يتم إزالة الإصدارات المحمية أبدًا أثناء توفير مساحة للإصدارات الجديدة والمحدثة. هذا مفيد لضمان عدم استبدال/الكتابة فوق إصدار نظام التشغيل الذي يتم تشغيله حاليًا (أو الموارد الإضافية المرتبطة به) أثناء التحديثات، لتجنب تلف نظام الملفات أثناء التشغيل.

مثل العديد من الإعدادات في ملفات التكوين هذه، يدعم هذا الإعداد توسيع المحددات. من المفيد بشكل خاص تعيين هذا الإعداد إلى أحد محددات "%A" أو "%B" أو "%w" للإشارة تلقائيًا إلى إصدار نظام التشغيل الحالي للنظام قيد التشغيل. انظر أدناه للحصول على تفاصيل حول المحددات المدعومة.

تمت الإضافة في الإصدار 251.

Verify=

يأخذ قيمة منطقية، والقيمة الافتراضية هي نعم. يتحكم في ما إذا كان سيتم التحقق تشفيريًا من الموارد التي تم تنزيلها (على وجه التحديد: التحقق من صحة توقيعات GPG لملفات SHA256SUMS التي تم تنزيلها، عبر ملفات التوقيع المنفصلة SHA256SUMS.gpg بالاقتران مع مفتاح النظام /usr/lib/systemd/import-pubring.pgp أو /etc/systemd/import-pubring.pgp).

هذا الخيار ضروري لتوفير ضمانات التكامل للموارد التي تم تنزيلها، وبالتالي يجب تركه ممكّنًا، خارج بيئات الاختبار.

لاحظ أن ملفات الحمولة التي تم تنزيلها يتم التحقق منها بشكل غير مشروط مقابل تجزئات SHA256 المدرجة في البيانات الوصفية. يتحكم هذا الخيار فقط في ما إذا كانت توقيعات هذه البيانات الوصفية يتم التحقق منها.

هذا الخيار له تأثير فقط إذا تم تحديد نوع المورد المصدر كـ url-file أو url-tar، حيث أن فحص التكامل والمصادقة متاح فقط للنقل من المصادر البعيدة.

تمت الإضافة في الإصدار 251.

ChangeLog=

يأخذ اختياريًا عنوان URL يمكن تقديمه بشريًا لموقع ويب يحتوي على سجل تغييرات للمورد الذي يتم تحديثه.

systemd.directives(7)

NAME

sysupdate.d, systemd-sysupdate — Configuration directory for systemd-sysupdate

SYNOPSIS

/etc/systemd/sysupdate.d/*.conf
/usr/lib/systemd/sysupdate.d/*.conf
/run/systemd/sysupdate.d/*.conf

DESCRIPTION

systemd-sysupdate is a service that may be used to download and install system updates. The behaviour of the service is configured via these configuration files.

The configuration files are named similarly to systemd.directives(7) files, and are parsed in the same order. They contain settings that control the download and installation process.

The primary purpose of these files is to define update resources, their locations, and how they should be deployed. This includes defining how to obtain the updates (e.g., via URL or local path) and where to install them on the system.

BASIC MODE OF OPERATION

The service operates by reading a set of configuration files that define various update resources. Each resource is typically described by a set of directives within a section, specifying its source, target, and matching patterns.

The service can be configured to handle different types of updates, such as kernel images, OS components, or container images. The configuration allows for specifying versioning and updating mechanisms, ensuring that the system remains up-to-date with the desired software components.

RESOURCE TYPES

The configuration files define various resource types that can be updated. These include, but are not limited to:

url-tar
Downloads a compressed tar archive from a URL.
directory
Uses a local directory as the source.
subvolume
Installs the resource as a subvolume (common in Btrfs filesystems).
file
Installs the resource as a regular file.

MATCH PATTERNS

Match patterns are used to associate specific files or directories with particular configurations. These patterns can include version specifiers that allow for dynamic matching of the latest available update.

For example, a pattern like myContainer_@v could match files like myContainer_1.0, myContainer_1.1, etc., where @v is a placeholder for the version number.

[TRANSFER] SECTION OPTIONS

Type=
Specifies the type of the resource to be transferred (e.g., url-tar, directory).
Path=
Specifies the path to the resource. This can be a URL or a local file system path.
MatchPattern=
A pattern used to identify the specific resource version to download or use.
CurrentSymlink=
(Optional) Specifies a symbolic link that should always point to the currently active version of the resource.

[SOURCE] SECTION OPTIONS

Type=
The type of the source, for example url-tar.
Path=
The URL from which to download the resource.
MatchPattern=
A glob pattern used to match the desired file(s) at the specified path. Version specifiers like @v can be used here.

[TARGET] SECTION OPTIONS

Type=
The type of the target location, for example subvolume or directory.
Path=
The destination path on the local file system where the resource should be installed.
MatchPattern=
A pattern that identifies the target directory or file, often used in conjunction with version specifiers.
CurrentSymlink=
The name of a symbolic link that will be created or updated to point to the latest installed version.

SPECIFIERS

Version specifiers, such as @v, are used in the MatchPattern directives to dynamically select the correct version of a resource. systemd-sysupdate resolves these specifiers to determine which version to download and install.

•foobarOS_7.efi – The unified kernel image for version 7

For each new OS release a new set of the latter three files would be added, each time with an updated version. The SHA256SUMS manifest should then be updated accordingly, listing all files for all versions that shall be offered for download.

EXAMPLES

Example 1. Unified Kernel Image

[Transfer]
Type=directory
Path=/boot/efi/EFI/Linux/
MatchPattern=foobarOS_@v.efi
CurrentSymlink=foobarOS.efi

This configuration specifies that kernel images are stored in /boot/efi/EFI/Linux/. The MatchPattern foobarOS_@v.efi indicates that files follow the naming convention foobarOS_<version>.efi. The CurrentSymlink=foobarOS.efi directive ensures that a symbolic link named foobarOS.efi always points to the most recently installed kernel image file.

Example 2. Updates for Plain Directory Container Image

[Source]
Type=url-tar
Path=https://download.example.com/
MatchPattern=myContainer_@v.tar.gz
[Target]
Type=subvolume
Path=/var/lib/machines
MatchPattern=myContainer_@v
CurrentSymlink=myContainer

On updates this downloads "https://download.example.com/myContainer_@v.tar.gz" and decompresses/unpacks it to /var/lib/machines/myContainer_@v. After each update a symlink /var/lib/machines/myContainer is created/updated always pointing to the most recent update.
