NAME

\n

syncthing - decentralized synchronization tool

\n
\n
\n

INTRODUCTION AND DEFINITIONS

\n

Syncthing is a continuous file synchronization program. It synchronizes files between two or more computers in real time, safely encrypted and with no central server. It is free and open source, easy to use, and powerful. It is a direct replacement for Dropbox, Google Drive, OneDrive, etc. etc. while being fully decentralized.

\n

This document describes the protocol used by Syncthing for communication between its nodes.

\n
\n
Block
\n
A contiguous chunk of bytes within a file. For the purpose of this protocol, blocks are 1,048,576 bytes (1 MiB) in size.
\n
Index
\n
A list of all files and directories on a filesystem. It is used to determine what files are present, their metadata, and their integrity.
\n
IndexItem
\n
A single item within an Index, representing either a file, directory or symlink.
\n
SequenceNumber
\n
A monotonically increasing integer associated with an IndexItem. It represents the time at which the IndexItem was last modified.
\n
Hash
\n
A cryptographic hash of a file's contents. Used to verify file integrity.
\n
LocalDiscovery
\n
The process of discovering other Syncthing nodes on the local network.
\n
GlobalDiscovery
\n
The process of discovering Syncthing nodes on the internet via public discovery servers.
\n
RelayServer
\n
A server that relays traffic between Syncthing nodes that cannot connect directly.
\n
Node
\n
A single instance of Syncthing running on a computer.
\n
Device
\n
A remote Syncthing node that a local node is configured to synchronize with.
\n
Folder
\n
A directory that is being synchronized between nodes.
\n
\n
\n
\n

TRANSPORT AND AUTHENTICATION

\n

Syncthing uses TLS for transport encryption and authentication. Each node is identified by a cryptographic key pair. Nodes authenticate each other by exchanging their public keys.

\n

The protocol is designed to be run over a TCP connection. Each message is prefixed with its length, allowing the receiver to read the entire message.

\n
\n
\n

PRE-AUTHENTICATION MESSAGES

\n

Before authentication, the following messages are exchanged:

\n
\n
Hello
\n
Sent by the client to initiate a connection. Contains the client's node ID and supported protocol versions.
\n
Hello-Ack
\n
Sent by the server in response to a Hello message. Contains the server's node ID and selected protocol version.
\n
Connect
\n
Sent by the client after receiving Hello-Ack. Contains the client's TLS certificate.
\n
Connect-Ack
\n
Sent by the server in response to a Connect message. Contains the server's TLS certificate.
\n
\n
\n
\n

\n

After successful authentication, the following messages are exchanged:

\n
\n
ClusterConfig
\n
Contains the cluster configuration, including the list of known nodes and their addresses.
\n
Index
\n
Contains a list of files and directories in a folder. Used for initial synchronization and to establish the current state of a folder.
\n
IndexUpdate
\n
Contains a list of changes to the index. Used to notify other nodes of modifications to files and directories.
\n
Request
\n
Used to request specific blocks of a file. Sent by a node that is missing data.
\n
Response
\n

\n
Ping
\n
A keep-alive message to check if the connection is still active.
\n
Pong
\n
A response to a Ping message.
\n
Disconnect
\n
Sent by a node to gracefully close the connection.

SHARING MODES

\n

Syncthing supports two sharing modes:

\n
\n
ReceiveOnly
\n
The node will only receive files, not send them.
\n
SendOnly
\n
The node will only send files, not receive them.
\n

By default, nodes operate in read-write mode, allowing both sending and receiving.

\n

DELTA INDEX EXCHANGE

\n

Delta index exchange is a mechanism that allows nodes to synchronize only the changes that have occurred since the last synchronization. This significantly reduces the amount of data that needs to be transferred.

\n
\n
Sequence:
\n
Each index item (i.e., file, directory or symlink) has a sequence number\n field. It contains the value of a counter at the time the index item was\n updated. The counter increments by one for each change. That is, as files\n are scanned and added to the index they get assigned sequence numbers 1, 2,\n 3 and so on. The next file to be changed or detected gets sequence\n number 4, and future updates continue in the same fashion.
\n
Index ID:
\n
Each folder has an Index ID. This is a 64 bit random identifier set at\n index creation time.
\n\n
\n

Given the above, we know that the tuple {index ID, maximum\n sequence number} uniquely identifies a point in time of a given index. Any\n further changes will increase the sequence number of some item, and thus the\n maximum sequence number for the index itself. Should the index be reset or\n removed (i.e., the sequence number reset to zero), a new index ID must be\n generated.

\n

By letting a device know the {index ID, maximum sequence number}\n we have for their index data, that device can arrange to only transmit\n Index Update messages for items with a higher sequence number. This\n is the delta index mechanism.

\n

The index ID and maximum sequence number known for each device is\n transmitted in the Cluster Config message at connection start.

\n

For this mechanism to be reliable it is essential that outgoing\n index information is ordered by increasing sequence number. Devices\n announcing a non-zero index ID in the Cluster Config message MUST\n send all index data ordered by increasing sequence number. Devices not\n intending to participate in delta index exchange MUST send a zero index ID\n or, equivalently, not send the index_id attribute at all.

\n
\n
\n

MESSAGE\n LIMITS

\n

An implementation MAY impose reasonable limits on the length of\n messages and message fields to aid robustness in the face of corruption or\n broken implementations. An implementation should strive to keep messages\n short and to the point, favouring more and smaller messages over fewer and\n larger. For example, favour a smaller Index message followed by one or more\n Index Update messages rather than sending a very large Index message.

\n

The Syncthing implementation imposes a hard limit of 500,000,000\n bytes on all messages. Attempting to send or receive a larger message will\n result in a connection close. This size was chosen to accommodate Index\n messages containing a large block list. It’s intended that the limit\n may be further reduced in a future protocol update supporting variable block\n sizes (and thus shorter block lists for large files).

\n
\n
\n
