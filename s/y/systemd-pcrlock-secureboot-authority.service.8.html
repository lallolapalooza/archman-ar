NAME

systemd-pcrlock, systemd-pcrlock-file-system.service, systemd-pcrlock-firmware-code.service, systemd-pcrlock-firmware-config.service, systemd-pcrlock-machine-id.service, systemd-pcrlock-make-policy.service, systemd-pcrlock-secureboot-authority.service, systemd-pcrlock-secureboot-policy.service - Analyze and predict TPM2 PCR states and generate an access policy from the prediction

SYNOPSIS

/usr/lib/systemd/systemd-pcrlock [OPTIONS...]

DESCRIPTION

Note: this command is experimental for now. While it is likely to become a regular component of systemd, it might still change in behaviour and interface.

systemd-pcrlock is a tool that may be used to analyze and predict TPM2 PCR measurements, and generate TPM2 access policies from the prediction which it stores in a TPM2 NV index (i.e. in the TPM2 non-volatile memory). This may then be used to restrict access to TPM2 objects (such as disk encryption keys) to system boot-ups in which only specific, trusted components are used.

systemd-pcrlock uses as input for its analysis and prediction:

•The UEFI firmware TPM2 event log (i.e. /sys/kernel/security/tpm0/binary_bios_measurements) of the current boot.
•The userspace TPM2 event log (i.e. /run/log/systemd/tpm2-measure.log) of the current boot.
•The current PCR state of the TPM2 chip.
•Boot component definition files (*.pcrlock and *.pcrlock.d/*.pcrlock, see systemd.pcrlock(5)) that each define expected measurements for one component of the boot process, permitting alternative variants for each. (Variants may be used to bless multiple kernel versions or boot loader versions at the same time.)

It uses these inputs to generate a combined event log, validating it against the PCR states. It then attempts to recognize event log records and matches them against the defined components. For each PCR where this can be done comprehensively (i.e. where all listed records and all defined components have been matched) this may then be used to predict future PCR measurements, taking the alternative variants defined for each component into account. This prediction may then be converted into a TPM2 access policy (consisting of TPM2 PolicyPCR and PolicyOR items), which is then stored in an NV index in the TPM2. This may be used to then lock secrets (such as disk encryption keys) to these policies (via a TPM2 PolicyAuthorizeNV policy).

Use tools such as systemd-cryptenroll(1) or systemd-repart(8) to bind disk encryption to such a systemd-pcrlock TPM2 policy. Specifically, see the --tpm2-pcrlock= switches of these tools.

The access policy logic requires a TPM2 device that implements the "PolicyAuthorizeNV" command, i.e. implements TPM 2.0 version 1.38 or newer.

COMMANDS

The following commands are understood:

log

This reads the combined TPM2 event log, validates it, matches it against the current PCR values, and outputs both in tabular form. Combine with --json= to generate output in JSON format.

Added in version 255.

cel

This reads the combined TPM2 event log and writes it to STDOUT in TCG Canonical Event Log Format (CEL-JSON)[1].

Added in version 255.

list-components

Shows a list of component definitions and their variants, i.e. the *.pcrlock files discovered in /var/lib/pcrlock.d/, /usr/lib/pcrlock.d/, and the other supported directories. See systemd.pcrlock(5) for details on these files and the full list of directories searched.

Added in version 255.

predict

Predicts the PCR state on future boots. This will analyze the TPM2 event log as described above, recognize components, and then generate all possible resulting PCR values for all combinations of component variants. Note that no prediction is made for PCRs whose value does not match the event log records, for which unrecognized measurements are discovered or for which components are defined that cannot be found in the event log. This is a safety measure to ensure that any generated access policy can be fulfilled correctly on current and future boots.

Added in version 255.

make-policy

This predicts the PCR state for future boots, much like the predict command above. It then uses this data to generate a TPM2 access policy which it stores in a TPM2 NV index. The prediction and information about the used TPM2 and its NV index are written to /var/lib/systemd/pcrlock.json.

The NV index is allocated on first invocation, and updated on subsequent invocations.

The NV index contents may be changed (and thus the policy stored in it updated) by providing an access PIN. This PIN is normally generated automatically and stored in encrypted form (with an access policy binding it to the NV index itself) in the aforementioned JSON policy file. This PIN may be chosen by the user, via the --recovery-pin= switch. If specified it may be used as alternative path of access to update the policy.

If the new prediction matches the old this command terminates quickly and executes no further operation. (Unless --force is specified, see below.)

Starting with v256, a copy of the /var/lib/systemd/pcrlock.json policy file is encoded in a credential (see systemd-creds(1) for details) and written to the EFI System Partition or XBOOTLDR partition, in the /loader/credentials/ subdirectory. There it is picked up at boot by systemd-stub(7) and passed to the invoked initrd, where it can be used to unlock the root file system (which typically contains /var/, which is where the primary copy of the policy is located, which hence cannot be used to unlock the root file system). The credential file is named after the boot entry token of the installation (see bootctl(1)), which is configurable via the --entry-token= switch, see below.

Added in version 255.

remove-policy

Removes a previously generated policy. Deletes the /var/lib/systemd/pcrlock.json file, and deallocates the NV index.

Added in version 255.

is-supported

Checks if the local TPM2 supports all functionality for systemd-pcrlock to work correctly. This does similar tests as systemd-analyze has-tpm2, but also checks for supported of the TPM2 operations requires by systemd-pcrlock. Outputs one of "no", "partial" (in case some parts of TPM2 support are available in hardware, firmware, OS, but not complete), "obsolete" (if TPM2 support is available in hardware, firmware and OS, but the operations required for systemd-pcrlock are missing), "yes". Returns an exit status of zero if full support is available, otherwise non-zero.

If combined with --quiet, suppresses the output of the string.

Currently, this checks for support for the PolicAuthorizeNV TPM2 command, as well as for support of the SHA-256 hash algorithm.

Added in version 258.

lock-firmware-code, unlock-firmware-code

Generates/removes .pcrlock files based on the TPM2 event log of the current boot covering all records for PCRs 0 ("platform-code") and 2 ("external-code").

This operation allows locking the boot process to the current version of the firmware of the system and its extension cards. This operation should only be used if the system vendor does not provide suitable pcrlock data ahead of time.

Note that this data only matches the current version of the firmware. If a firmware update is applied this data will be out-of-date and any access policy generated from it will no longer pass. It is thus recommended to invoke unlock-firmware-code before doing a firmware update, followed by make-policy to refresh the policy.

systemd-pcrlock lock-firmware-code is invoked automatically at boot via the systemd-pcrlock-firmware-code.service unit, if enabled. This ensures that an access policy managed by systemd-pcrlock is automatically locked to the new firmware version whenever the

systemd-pcrlock-firmware-config.service.service unit is run. This unit is usually run by the system firmware update process, or by the user manually.

Added in version 255.

OPTIONS

The following options are understood:

--force
Forces generation of a new policy even if the prediction matches the old one. This is useful for updating the policy to a newer version of the same components, or for generating a new recovery PIN.
--recovery-pin=PIN
Specifies a recovery PIN to be used when generating or updating a policy. This PIN is used as an alternative means of accessing the policy, and should be stored securely. If not specified, a new PIN is generated automatically.
--entry-token=TOKEN
Specifies the token to be used when writing the policy credential to the EFI System Partition or XBOOTLDR partition. Defaults to the current boot entry token.
--json
Output in JSON format.
--quiet
Suppress output.

EXIT STATUS

Returns 0 on success, non-zero on failure.

EXAMPLES

Generate a TPM2 policy based on the current boot components:

# systemd-pcrlock make-policy

Generate a new policy and set a recovery PIN:

# systemd-pcrlock --recovery-pin=mysecretpin make-policy

Remove the current TPM2 policy:

# systemd-pcrlock remove-policy

List all known boot components and their variants:

# systemd-pcrlock list-components

Lock the firmware code to the current version:

# systemd-pcrlock lock-firmware-code

Generate a policy for Secure Boot authority:

# systemd-pcrlock lock-secureboot-authority
# systemd-pcrlock make-policy

الوصف

ملاحظة: هذه الأداة تجريبية في الوقت الحالي. بينما من المرجح أن تصبح جزءًا منتظمًا من systemd، فقد تظل تتغير في سلوكها وواجهتها.

systemd-pcrlock هي أداة يمكن استخدامها لتحليل وتوقع قياسات TPM2 PCR، وإنشاء سياسات وصول TPM2 من التنبؤ الذي تخزنه في مؤشر NV من TPM2 (أي في ذاكرة TPM2 غير المتطايرة). يمكن بعد ذلك استخدام هذا لتقييد الوصول إلى كائنات TPM2 (مثل مفاتيح تشفير القرص) إلى عمليات تمهيد النظام التي تستخدم فقط مكونات محددة وموثوقة.

يستخدم systemd-pcrlock كمدخلات لتحليله وتنبؤاته:

•سجل أحداث TPM2 الثابتة لـ UEFI (أي /sys/kernel/security/tpm0/binary_bios_measurements) لعملية التمهيد الحالية.
•سجل أحداث TPM2 للمستخدم (أي /run/log/systemd/tpm2-measure.log) لعملية التمهيد الحالية.
•حالة PCR الحالية لشريحة TPM2.
•ملفات تعريف مكونات التمهيد (*.pcrlock و *.pcrlock.d/*.pcrlock، راجع systemd.pcrlock(5)) التي تحدد كل منها قياسات متوقعة لمكون واحد من عملية التمهيد، مما يسمح بمتغيرات بديلة لكل منها. (يمكن استخدام المتغيرات لمباركة إصدارات متعددة من النواة أو إصدارات محمل التمهيد في نفس الوقت.)

يستخدم هذه المدخلات لإنشاء سجل أحداث مدمج، والتحقق منه مقابل قيم PCR. ثم يحاول التعرف على سجلات الأحداث ومطابقتها مع المكونات المحددة. لكل PCR يمكن القيام بذلك بشكل شامل (أي حيث تم مطابقة جميع السجلات المدرجة وجميع المكونات المحددة) يمكن بعد ذلك استخدامه للتنبؤ بقياسات PCR المستقبلية، مع مراعاة المتغيرات البديلة المحددة لكل مكون. يمكن بعد ذلك تحويل هذا التنبؤ إلى سياسة وصول TPM2 (تتكون من عناصر TPM2 PolicyPCR و PolicyOR)، والتي يتم تخزينها بعد ذلك في مؤشر NV في TPM2. يمكن استخدام هذا لقفل الأسرار (مثل مفاتيح تشفير القرص) لهذه السياسات (عبر سياسة TPM2 PolicyAuthorizeNV).

استخدم أدوات مثل systemd-cryptenroll(1) أو systemd-repart(8) لربط تشفير القرص بسياسة TPM2 systemd-pcrlock كهذه. على وجه التحديد، راجع مفاتيح --tpm2-pcrlock= لهذه الأدوات.

يتطلب منطق سياسة الوصول جهاز TPM2 الذي ينفذ الأمر "PolicyAuthorizeNV"، أي أنه ينفذ TPM 2.0 الإصدار 1.38 أو أحدث.

الأوامر التالية مفهومة:

log

يقرأ هذا سجل أحداث TPM2 المدمج، ويتحقق منه، ويطابقه مع قيم PCR الحالية، ويخرج كلاهما في شكل جدول. ادمجه مع --json= لإنشاء مخرجات بتنسيق JSON.

cel

يقرأ هذا سجل أحداث TPM2 المدمج ويكتبه إلى STDOUT بتنسيق TCG Canonical Event Log Format (CEL-JSON)[1].

أضيف في الإصدار 255.

list-components

يعرض قائمة بتعريفات المكونات ومتغيراتها، أي ملفات *.pcrlock التي تم اكتشافها في /var/lib/pcrlock.d/، /usr/lib/pcrlock.d/، والدلائل الأخرى المدعومة. راجع systemd.pcrlock(5) للحصول على تفاصيل حول هذه الملفات والقائمة الكاملة للدلائل التي تم البحث فيها.

أضيف في الإصدار 255.

predict

يتنبأ بحالة PCR في عمليات التمهيد المستقبلية. سيقوم هذا بتحليل سجل أحداث TPM2 كما هو موضح أعلاه، والتعرف على المكونات، ثم إنشاء جميع قيم PCR الناتجة الممكنة لجميع مجموعات متغيرات المكونات. لاحظ أنه لا يتم إجراء أي تنبؤ لـ PCRs التي لا تتطابق قيمتها مع سجلات الأحداث، أو التي يتم اكتشاف قياسات غير معروفة لها، أو التي توجد لها مكونات محددة لا يمكن العثور عليها في سجل الأحداث. هذا إجراء أمان لضمان إمكانية تلبية سياسة الوصول التي تم إنشاؤها بشكل صحيح في عمليات التمهيد الحالية والمستقبلية.

أضيف في الإصدار 255.

make-policy

يقوم هذا بالتنبؤ بحالة PCR لعمليات التمهيد المستقبلية، مثل أمر predict أعلاه. ثم يستخدم هذه البيانات لإنشاء سياسة وصول TPM2 التي يخزنها في مؤشر NV لـ TPM2. يتم كتابة التنبؤ والمعلومات حول TPM2 المستخدم ومؤشر NV الخاص به إلى /var/lib/systemd/pcrlock.json.

يتم تخصيص مؤشر NV عند الاستدعاء الأول، ويتم تحديثه عند الاستدعاءات اللاحقة.

يمكن تغيير محتويات مؤشر NV (وبالتالي تحديث السياسة المخزنة فيه) عن طريق توفير رقم تعريف شخصي للوصول (PIN). يتم إنشاء هذا الرقم الشخصي عادةً تلقائيًا وتخزينه بتنسيق مشفر (مع سياسة وصول تربطه بمؤشر NV نفسه) في ملف السياسة JSON المذكور أعلاه. يمكن للمستخدم اختيار هذا الرقم الشخصي، عبر مفتاح --recovery-pin=. إذا تم تحديده، يمكن استخدامه كمسار وصول بديل لتحديث السياسة.

إذا تطابق التنبؤ الجديد مع القديم، ينهي هذا الأمر بسرعة ولا ينفذ أي عملية أخرى. (ما لم يتم تحديد --force، انظر أدناه.)

بدءًا من الإصدار v256، يتم ترميز نسخة من ملف السياسة /var/lib/systemd/pcrlock.json في بيانات اعتماد (راجع systemd-creds(1) للحصول على التفاصيل) وتكتب إلى قسم EFI System Partition أو قسم XBOOTLDR، في الدليل الفرعي /loader/credentials/. هناك يتم التقاطها عند التمهيد بواسطة systemd-stub(7) وتمريرها إلى initrd الذي يتم استدعاؤه، حيث يمكن استخدامها لفتح نظام ملفات الجذر (الذي يحتوي عادةً على /var/، وهو المكان الذي يوجد فيه النسخة الأساسية من السياسة، والتي لا يمكن استخدامها لفتح نظام ملفات الجذر). يتم تسمية ملف بيانات الاعتماد باسم رمز إدخال التمهيد الخاص بالتثبيت (راجع bootctl(1))، والذي يمكن تكوينه عبر مفتاح --entry-token=، انظر أدناه.

is-supported

يتحقق مما إذا كان TPM2 المحلي يدعم جميع وظائف systemd-pcrlock للعمل بشكل صحيح. يقوم هذا بإجراء اختبارات مشابهة لاختبارات systemd-analyze has-tpm2، ولكنه يتحقق أيضًا من دعم عمليات TPM2 المطلوبة لـ systemd-pcrlock. يخرج أحد القيم التالية: "no"، "partial" (في حالة توفر بعض أجزاء دعم TPM2 في الأجهزة، الثابتة، نظام التشغيل، ولكن ليس بشكل كامل)، "obsolete" (إذا كان دعم TPM2 متوفرًا في الأجهزة، الثابتة، ونظام التشغيل، ولكن العمليات المطلوبة لـ systemd-pcrlock مفقودة)، "yes". يعيد حالة خروج صفر إذا كان الدعم الكامل متاحًا، وإلا فيعيد قيمة غير صفرية.

إذا تم دمجه مع --quiet، فإنه يكتم إخراج السلسلة النصية.

حاليًا، يتحقق هذا من دعم أمر TPM2 PolicAuthorizeNV، بالإضافة إلى دعم خوارزمية التجزئة SHA-256.

lock-firmware-code, unlock-firmware-code

ينشئ/يزيل ملفات .pcrlock بناءً على سجل أحداث TPM2 لعملية التمهيد الحالية التي تغطي جميع السجلات الخاصة بـ PCRs 0 ("platform-code") و 2 ("external-code").

تسمح هذه العملية بتقييد عملية التمهيد للإصدار الحالي من ثابت النظام وبطاقاته الإضافية. يجب استخدام هذه العملية فقط إذا كان بائع النظام لا يوفر بيانات pcrlock مناسبة مسبقًا.

لاحظ أن هذه البيانات تطابق فقط الإصدار الحالي للثابت. إذا تم تطبيق تحديث للثابت، فستكون هذه البيانات قديمة ولن تمر أي سياسة وصول تم إنشاؤها منها. لذلك، يوصى باستدعاء unlock-firmware-code قبل إجراء تحديث للثابت، متبوعًا بـ make-policy لتحديث السياسة.

يتم استدعاء systemd-pcrlock lock-firmware-code تلقائيًا عند التمهيد عبر وحدة systemd-pcrlock-firmware-code.service، إذا تم تمكينها. هذا يضمن أن سياسة الوصول التي يديرها systemd-pcrlock مقيدة تلقائيًا بإصدار الثابت الجديد كلما تم تشغيل وحدة

systemd-pcrlock-firmware-config.service. عادةً ما يتم تشغيل هذه الوحدة بواسطة عملية تحديث الثابت للنظام، أو بواسطة المستخدم يدويًا.

خيارات

الخيارات التالية مفهومة:

--force
يجبر إنشاء سياسة جديدة حتى لو تطابق التنبؤ مع السياسة القديمة. هذا مفيد لتحديث السياسة إلى إصدار أحدث من نفس المكونات، أو لإنشاء رقم تعريف شخصي جديد للاسترداد.
--recovery-pin=PIN
يحدد رقم تعريف شخصي للاسترداد لاستخدامه عند إنشاء أو تحديث سياسة. يتم استخدام هذا الرقم الشخصي كوسيلة وصول بديلة للسياسة، ويجب تخزينه بأمان. إذا لم يتم تحديده، يتم إنشاء رقم شخصي جديد تلقائيًا.
--entry-token=TOKEN
يحدد الرمز المميز الذي سيتم استخدامه عند كتابة بيانات اعتماد السياسة إلى قسم EFI System Partition أو قسم XBOOTLDR. الافتراضي هو رمز إدخال التمهيد الحالي.
--json
إخراج بتنسيق JSON.
--quiet
كتم الإخراج.

حالة الخروج

يعيد 0 عند النجاح، وقيمة غير صفرية عند الفشل.

أمثلة

إنشاء سياسة TPM2 بناءً على مكونات التمهيد الحالية:

# systemd-pcrlock make-policy

إنشاء سياسة جديدة وتعيين رقم تعريف شخصي للاسترداد:

# systemd-pcrlock --recovery-pin=mysecretpin make-policy

إزالة سياسة TPM2 الحالية:

# systemd-pcrlock remove-policy

عرض جميع مكونات التمهيد المعروفة ومتغيراتها:

# systemd-pcrlock list-components

تقييد ثابت النظام إلى إصداره الحالي:

# systemd-pcrlock lock-firmware-code

إنشاء سياسة لسلطة Secure Boot:

# systemd-pcrlock lock-secureboot-authority
# systemd-pcrlock make-policy

If used with list-components the selected location range\n will be highlighted in the component list.

\n
Takes either a string or a colon-separated pair of\n strings. Configures up to which point in the sorted list of defined components\n to analyze/predict PCRs to. Typically, the systemd-pcrlock tool is\n invoked from a fully booted system after boot-up and before shutdown. This\n means various components that are defined for shutdown have not been measured\n yet, and should not be searched for. This option allows one to restrict which\n components are considered for analysis (taking only components before some\n point into account, ignoring components after them). The expected string is\n ordered against the filenames of the components defined. Any components with a\n lexicographically later name are ignored. This logic applies to the\n log, predict, and make-policy verbs. If a colon-separated\n pair of strings are specified then they select which phases of the boot to\n include in the prediction/policy. The first string defines where the first\n prediction shall be made, and the second string defines where the last\n prediction shall be made. All such predictions are then combined into one set.\n

If used with list-components the selected location range\n will be highlighted in the component list.

\n

Defaults to "760-:940-", which means the policies\n generated by default will basically cover the whole runtime of the OS\n userspace, from the initrd (as "760-" closely follows\n 750-enter-initrd.pcrlock) until (and including) the main runtime of the\n system (as "940-" is closely followed by 950-shutdown.pcrlock). \n
Takes either a string or a colon-separated pair of\n strings. Configures up to which point in the sorted list of defined components\n to analyze/predict PCRs to. Typically, the systemd-pcrlock tool is\n invoked from a fully booted system after boot-up and before shutdown. This\n means various components that are defined for shutdown have not been measured\n yet, and should not be searched for. This option allows one to restrict which\n components are considered for analysis (taking only components before some\n point into account, ignoring components after them). If used with list-components the selected location range\n will be highlighted in the component list.

NAME

systemd-pcrlock-secureboot-authority.service, systemd-pcrlock-machine-info.service, systemd-pcrlock-policy.service, systemd-pcrlock-tpm2-policy.service, systemd-pcrlock-tpm2-owner.service, systemd-pcrlock-tpm2-nv.service — TPM2 PCR-based disk encryption lock authority

\n
\n

SYNOPSIS

\n

systemd-pcrlock-secureboot-authority.service, systemd-pcrlock-machine-info.service, systemd-pcrlock-policy.service, systemd-pcrlock-tpm2-policy.service, systemd-pcrlock-tpm2-owner.service, systemd-pcrlock-tpm2-nv.service

\n
\n
\n

DESCRIPTION

\n

These are service units for systemd-pcrlock(1). They are intended to be used in conjunction with Trusted Platform Module (TPM) devices and disk encryption. The service units manage the locking and unlocking of TPM 2.0 NV Indexes, and the loading and verification of TPM 2.0 policies.

\n

The different service units cater to specific aspects of TPM 2.0 integration:

\n
\n
systemd-pcrlock-secureboot-authority.service
\n
Manages the secure boot authority, ensuring that only trusted bootloaders can unlock the system.
\n
systemd-pcrlock-machine-info.service
\n
Handles machine information, potentially including hardware-specific PCR values.
\n
systemd-pcrlock-policy.service
\n
Manages the general PCrlock policy, allowing customization of PCR values used for locking.
\n
systemd-pcrlock-tpm2-policy.service
\n
Specifically manages TPM 2.0 policies, loading and verifying them.
\n
systemd-pcrlock-tpm2-owner.service
\n
Manages the TPM 2.0 owner authorization, which is required for certain TPM operations.
\n
systemd-pcrlock-tpm2-nv.service
\n
Manages TPM 2.0 NV Indexes, which are used to store persistent data like encryption keys or policies.
\n
\n

These services work by utilizing the systemd-pcrlock(1) command-line tool to interact with the TPM and manage the necessary cryptographic materials.

\n

The primary goal is to provide a mechanism for unlocking encrypted storage devices based on the state of the TPM's Platform Configuration Registers (PCRs) and associated policies. This allows for disk encryption to be automatically unlocked when the system boots in a trusted state, and to remain locked otherwise.

\n
\n
\n

COMMANDS

\n

This section describes the command-line options for the systemd-pcrlock(1) tool, which is used by the service units.

\n

--tpm2-policy=

\n
Takes a file system path as argument. Specifies the file containing the TPM 2 policy digest. The policy digest is a cryptographic hash that represents a set of conditions (e.g., specific PCR values) that must be met for the policy to be considered valid. This option is used by the systemd-pcrlock-tpm2-policy.service unit.
\n

--tpm2-nv-index=

\n
Takes a numeric argument, the NV Index identifier. Specifies the TPM 2 NV Index to use for storing or retrieving data. NV Indexes are persistent memory locations within the TPM. This option is used by the systemd-pcrlock-tpm2-nv.service unit.
\n

--tpm2-nv-owner=

\n
Takes a file system path as argument. Specifies the file containing the TPM 2 owner authorization secret. This is required to access certain NV Indexes or perform owner-related operations. This option is used by the systemd-pcrlock-tpm2-owner.service unit.
\n

--tpm2-pin=

\n
Takes a file system path as argument. Specifies the file containing the PIN to unlock the TPM 2 NV index. This PIN is used to protect the NV index, either when creating it or when unlocking write access to it. If no policy was created before, this PIN is used to protect the newly allocated NV index. If a policy has been created before, the PIN is used to unlock write access to the NV index. If either "hide" or "show" is used, a PIN is automatically generated, and — only in case of "show" — displayed on screen. Regardless if user supplied or automatically generated, it is stored in encrypted form in the policy metadata file. The recovery PIN may be used to regain write access to an NV index in case the access policy became out of date.

Added in version 255.

\n

--pcrlock=

\n
Takes a file system path as argument. If specified, configures where to write the generated pcrlock data to. Honoured by the various lock-* commands. If not specified, a default path is generally used, as documented above.

Added in version 255.

\n

--policy=

\n
Takes a file system path as argument. If specified, configures where to write pcrlock policy metadata to. If not specified, defaults to /var/lib/systemd/pcrlock.json.

Added in version 255.

\n

--force

\n
If specified with make-policy, the predicted policy will be written to the NV index even if it is detected to be the same as the previously stored one.

Added in version 255.

\n

--entry-token=

\n
Sets the boot entry token to use for the file name for the pcrlock policy credential in the EFI System Partition or XBOOTLDR partition. See the bootctl(1) option of the same regarding expected values. This switch has an effect on the make-policy command only.

Added in version 256.

\n

--quiet

\n
If specified suppresses output when invoked for is-supported.

Added in version 258.

\n

--json=MODE

\n
Shows output formatted as JSON. Expects one of "short" (for the shortest possible output without any redundant whitespace or line breaks), "pretty" (for a pretty version of the same, with indentation and line breaks) or "off" (to turn off JSON output, the default).
\n

--no-pager

\n
Do not pipe output into a pager.
\n

-h, --help

\n
Print a short help text and exit.
\n

--version

\n
Print a short version string and exit.
\n
\n
\n

EXIT STATUS

\n

On success, 0 is returned, a non-zero failure code otherwise.

systemd-pcrlock-tpm2-policy.service
\n
تدير سياسات TPM 2.0 بشكل خاص، وتقوم بتحميلها والتحقق منها.
\n
systemd-pcrlock-tpm2-owner.service
