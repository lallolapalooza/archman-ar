الوصف

برنامج stap هو الواجهة الأمامية لأداة Systemtap. يقبل تعليمات الفحص المكتوبة بلغة بسيطة خاصة بالمجال، ويترجم هذه التعليمات إلى كود C، ويقوم بتجميع هذا الكود C، ويقوم بتحميل الوحدة النمطية الناتجة في نواة لينكس قيد التشغيل أو في عدّال مساحة المستخدم Dyninst، لأداء وظائف الفحص/الاستقصاء المطلوبة للنظام. يمكنك توفير النص البرمجي في ملف مسمى (اسم_الملف)، من المدخل القياسي (استخدم - بدلاً من اسم_الملف)، أو من سطر الأوامر (باستخدام -e نص_برمجي). يعمل البرنامج حتى يتم مقاطعته بواسطة المستخدم، أو إذا استدعت البرمجة النصية طوعًا الدالة exit()، أو بواسطة عدد كافٍ من الأخطاء الناعمة.

اللغة، الموصوفة في قسم لغة النصوص البرمجية أدناه، هي ذات أنواع صارمة، ومعبرة، وخالية من التعريفات، وإجرائية، وصديقة للنماذج الأولية، ومستوحاة من awk و C. تسمح بربط نقاط الكود المصدري أو الأحداث في النظام بالمعالجات، وهي روتينات فرعية يتم تنفيذها بشكل متزامن. وهي مشابهة مفاهيمياً إلى حد ما لـ "قوائم أوامر نقطة التوقف" في مصحح الأخطاء gdb.

نظرة عامة على التوثيق

يأتي systemtap مع مجموعة متنوعة من الموارد التعليمية، والتوثيقية، والمرجعية. تأتي عبر الإنترنت و/أو معبأة للاستخدام دون اتصال. تشير بعض رسائل التحذير/الخطأ التشخيصية لنظام systemtap بشكل خاص إلى قراءة صفحة دليل بإدراج سلسلة مثل [man error::pass5]. للحصول على توثيق عبر الإنترنت، راجع موقع المشروع على الويب، https://sourceware.org/systemtap/

الخيارات

يدعم مترجم systemtap الخيارات التالية. أي خيار آخر يطبع قائمة بالخيارات المدعومة. يمكن إعطاء الخيارات في سطر الأوامر، كما هو معتاد. إذا كان الملف $SYSTEMTAP_DIR/rc موجودًا، يتم تحميل الخيارات منه أيضًا وتفسيرها أولاً. ($SYSTEMTAP_DIR افتراضيًا هو $HOME/.systemtap إذا لم يتم تعيينه.)

في بعض الحالات، تعتمد القيمة الافتراضية للخيارة على تكوين النظام المعين وبالتالي لا يمكن ذكرها هنا مباشرة. في بعض هذه الحالات، قد يعرض تشغيل "stap --help" القيمة الافتراضية.

-
استخدم المدخل القياسي بدلاً من اسم_الملف المحدد كمدخل للغة الفحص، ما لم يتم إعطاء -e نص_برمجي.
-h --help
عرض رسالة المساعدة.
-V --version
عرض رسالة الإصدار.
-p NUM
توقف بعد المرور NUM. يتم ترقيم المراحل من 1 إلى 5: تحليل، تفصيل، ترجمة، تجميع، تشغيل. انظر قسم المعالجة للتفاصيل.
-v
زيادة الإسهاب لجميع المراحل. أنتج حجمًا أكبر من المخرجات المعلوماتية (?) في كل مرة تتكرر فيها الخيارات.
--vp ABCDE
زيادة الإسهاب على أساس كل مرحلة. على سبيل المثال، "--vp 002" تضيف وحدتين من الإسهاب للمرحلة 3 فقط. الجمع "-v --vp 00004" يضيف وحدة واحدة من الإسهاب لجميع المراحل، و 4 وحدات أخرى للمرحلة 5.
-k
احتفظ بالدليل المؤقت بعد جميع عمليات المعالجة. قد يكون هذا مفيدًا لفحص كود C الذي تم إنشاؤه، أو لإعادة استخدام كائن النواة المجمّع.
-g
وضع الخبير. تمكين تحليل البناءات غير الآمنة على مستوى الخبراء مثل كود C المضمن.
-P
وضع البحث عن المقدمة. هذا يعادل --prologue-searching=always. قم بتنشيط الاستدلالات للتحايل على معلومات التصحيح غير الصحيحة لمتغيرات $context الخاصة بمعلمات الدالة.
-u
وضع غير محسّن. تعطيل إزالة الكود غير المستخدم والعديد من التحسينات الأخرى أثناء التفصيل / الترجمة.
-w
وضع إخفاء التحذيرات. تعطيل جميع رسائل التحذير.
-W
معاملة جميع التحذيرات كأخطاء.
-b
استخدم وضع الدُفعات (ملفات لكل وحدة معالجة) لنقل البيانات من النواة إلى المستخدم. استخدم برنامج stap-merge لتجميعها معًا لاحقًا.
-i --interactive
وضع تفاعلي. تمكين واجهة لبناء نص systemtap بشكل تدريجي وتفاعلي.
-t
جمع معلومات التوقيت حول عدد مرات تنفيذ الفحص ومتوسط الوقت المستغرق في كل نقطة فحص. يعرض أيضًا الاشتقاق لكل نقطة فحص.
-s NUM
استخدم مخازن مؤقتة بحجم NUM ميجابايت لنقل البيانات من النواة إلى المستخدم لكل معالج. القيمة الافتراضية هي 16 ميجابايت، أو أقل في الأجهزة ذات الذاكرة الأصغر.
-I DIR
أضف الدليل المحدد إلى دليل البحث عن tapset. انظر وصف المرحلة 2 للتفاصيل.
-D NAME=VALUE
أضف توجيه المعالج المسبق C المحدد إلى Makefile الخاص بالوحدة. يمكن استخدام هذه لتجاوز معلمات الحد الموضحة أدناه.
-B NAME=VALUE
في وضع التشغيل في النواة، أضف توجيه make المحدد إلى استدعاء make لتجميع وحدة النواة. يمكن استخدام هذه لإضافة أو تجاوز خيارات kconfig. على سبيل المثال، استخدم 
-B CONFIG_DEBUG_INFO=y

لإضافة معلومات التصحيح.

-B FLAG
في وضع التشغيل dyninst
mode, add the given parameter to the compiler CFLAGS used for building the dyninst shared library. For example, use 
-B -g

to add debugging information.

-a ARCH
Use a cross-compilation mode for the given target architecture. This requires access to the cross-compiler and the kernel build tree, and goes along with the 
-B CROSS_COMPILE=arch-tool-prefix-
and
-r /build/tree

options.

--modinfo NAME=VALUE
Add the name/value pair as a MODULE_INFO macro call to the generated module. This may be useful to inform or override various module-related checks in the kernel.
-G NAME=VALUE
Sets the value of global variable NAME to VALUE when staprun is invoked. This applies to scalar variables declared global in the script/tapset.
-R DIR
Look for the systemtap runtime sources in the given directory. Your DIR default can be seen using "stap --help".
-r /DIR
Build for kernel in given build tree. Can also be set with the SYSTEMTAP_RELEASE environment variable.
-r RELEASE
Build for kernel in build tree /lib/modules/RELEASE/build. Can also be set with the SYSTEMTAP_RELEASE environment variable.
-m MODULE
Use the given name for the generated kernel object module, instead of a unique randomized name. The generated kernel object module is copied to the current directory.
-d MODULE
Add symbol/unwind information for the given module into the kernel object module. This may enable symbolic tracebacks from those modules/programs, even if they do not have an explicit probe placed into them.
--ldd
Add symbol/unwind information for all user-space shared libraries suspected by ldd to be necessary for user-space binaries being probed or listed with the -d option. Caution: this can make the probe modules considerably larger. Note that this option does not deal with kernel-space modules: see instead --all-modules below.
--all-modules
Equivalent to specifying "-dkernel" and a "-d" for each kernel module that is currently loaded. Caution: this can make the probe modules considerably larger.
-o FILE
Send standard output to named file. In bulk mode, percpu files will start with FILE_ (FILE_cpu with -F) followed by the cpu number. This supports strftime(3) formats for FILE.
-c CMD
Start the probes, run CMD, and exit when CMD finishes. This also has the effect of setting target() to the pid of that process. Note that many probe types trigger independently of this setting. Consider including something like this to focus your script. 
   probe FOO { if (pid() != target()) next; .... }
-x PID
Sets target() to PID. The script runs independently of the PID's lifespan.
-e SCRIPT
Run the given SCRIPT specified on the command line.
-E SCRIPT
Run the given SCRIPT specified. This SCRIPT is run in addition to the main script specified, through -e, or as a script file. This option can be repeated to run multiple scripts, and can be used in listing mode (-l/-L).
-l PROBE
Instead of running a probe script, just list all available probe points matching the given single probe point. The pattern may include wildcards and aliases, but not comma-separated multiple probe points. The process result code will indicate failure if there are no matches. 
% stap -e 'probe syscall.* { }'
[...]
% stap -l 'syscall.*'
syscall.accept
[...]
syscall.writev
-L PROBE
Similar to "-l", but list matching probe points plus their available context variables. When -v is set with -L, the output includes duplicate probe points which are distinguished by their PC address. 
% stap -L 'process("/lib64/libpython*.so.*").mark("*")'
process("/usr/lib64/libpython2.7.so.1.0").mark("function__entry") $arg1:long $arg2:long $arg3:long
process("/usr/lib64/libpython2.7.so.1.0").mark("function__return") $arg1:long $arg2:long $arg3:long
process("/usr/lib64/libpython3.6m.so.1.0").mark("function__entry") $arg1:long $arg2:long $arg3:long
process("/usr/lib64/libpython3.6m.so.1.0").mark("function__return") $arg1:long $arg2:long $arg3:long
process("/usr/lib64/libpython3.6m.so.1.0").mark("gc__done") $arg1:long
process("/usr/lib64/libpython3.6m.so.1.0").mark("gc__start") $arg1:long
process("/usr/lib64/libpython3.6m.so.1.0").mark("line") $arg1:long $arg2:long $arg3:long
-F
Without -o option, load module and start probes, then detach from the module leaving the probes running. With -o option, run staprun in background as a daemon and show its pid.
-S size[,N]
Sets the maximum size of output file and the maximum number of output files. If the size of output file will exceed size megabytes, systemtap switches output file to the next file. And if the number of output files exceed N , systemtap removes the oldest output file. You can omit the second argument.
-T TIMEOUT
Exit the script after TIMEOUT seconds.
--skip-badvars
Ignore unresolvable or run-time-inaccessible context variables and substitute with 0, without errors.
--prologue-searching[=WHEN]
Prologue-searching mode. Activate heuristics to work around incorrect debugging information for function parameter $context variables. WHEN can be either "never", "always", or "auto" (i.e. enabled by heuristic). If WHEN is missing, then "always" is assumed. If the option is missing, then "auto" is assumed.
--suppress-handler-errors
Wrap all probe handlers into something like this 
try { ... } catch { next }

block, which causes any runtime errors to be quietly suppressed. Suppressed errors do not count against MAXERRORS limits. In this mode, the MAXSKIPPED limits are also suppressed, so that many errors and skipped probes may be accumulated during a script's runtime. Any overall counts will still be reported at shutdown.

--compatible VERSION
Suppress recent script language or tapset changes which are incompatible with given older version of systemtap. This may be useful if a much older systemtap script fails to run. See the DEPRECATION section for more details.
--check-version
This option is used to check if the active script has any constructs that may be systemtap version specific. See the DEPRECATION section for more details.
--clean-cache
This option prunes stale entries from the cache directory. This is normally done automatically after successful runs, but this option will trigger the cleanup manually and then exit. See the CACHING section for more details about cache limits.
--color[=WHEN], --colour[=WHEN]
This option controls coloring of error messages. WHEN can be either "never", "always", or "auto" (i.e. enable only if at a terminal). If WHEN is missing, then "always" is assumed. If the option is missing, then "auto" is assumed.

Colors can be modified using the SYSTEMTAP_COLORS environment variable. The format must be of the form key1=val1:key2=val2:key3=val3 ...etc. Valid keys are "error", "warning", "source", "caret", and "token". Values constitute Select Graphic Rendition (SGR) parameter(s). Consult the documentation of your terminal for the SGRs it supports. As an example, the default colors would be expressed as error=01;31:warning=00;33:source=00;34:caret=01:token=01. If SYSTEMTAP_COLORS is absent, the default colors will be used. If it is empty or invalid, coloring is turned off.

--disable-cache
This option disables all use of the cache directory. No files will be either read from or written to the cache.
--poison-cache
This option treats files in the cache directory as invalid. No files will be read from the cache, but resulting files from this run will still be written to the cache. This is meant as a troubleshooting aid when stap's cached behavior seems to be misbehaving. If it helped, there is a probably a bug in systemtap that the developers would like you to report.
--privilege[=stapusr | =stapsys | =stapdev]
This option instructs stap to examine the script looking for constructs which are not allowed for the specified privilege level (see UNPRIVILEGED USERS). Compilation fails if any such constructs are used. If stapusr or stapsys are specified when using a compile server (see --use-server), the server will examine the script and, if compilation succeeds, the server will cryptographically sign the resulting kernel module, certifying that is it safe for use by users at the specified privilege level.

--suppress-time-limits

--runtime=MODE
تعيين وضع تشغيل المرور 5. الخيارات الصالحة هي kernel (افتراضي)، dyninst و bpf. انظر ORUNTIMES أدناه لمزيد من المعلومات.
--dyninst

--bpf
اختصار لـ --runtime=bpf.
--save-uprobes
على الأجهزة التي تتطلب من SystemTap بناء وحدة uprobes الخاصة به (النواة قبل الإصدار 3.5)، يوجه هذا الخيار SystemTap إلى حفظ نسخة من الوحدة في الدليل الحالي (إنشاء دليل "uprobes" جديد أولاً).
--target-namespaces=PID
السماح بتعيين مجموعة من مساحات أسماء الهدف بناءً على مساحات الأسماء التي يوجد بها PID معين. هذا مخصص لوظائف tapset المدركة لمساحات الأسماء. إذا لم يتم تعيين مساحات أسماء الهدف، فإن الهدف افتراضيًا لمساحات أسماء عملية stap.
--monitor=INTERVAL
يمكّن واجهة لعرض معلومات الحالة حول الوحدة (وقت التشغيل، اسم الوحدة، معرف مستخدم المستدعي، أحجام الذاكرة، المتغيرات العامة، قائمة المسابر مع إحصائياتها). يمكن توفير وسيط اختياري INTERVAL لتعيين معدل التحديث بالثواني لنافذة الحالة. يمكن أيضًا التحكم في الوحدة عن طريق قائمة أوامر باستخدام المفاتيح التالية:
c

s
تدوير السمة المستخدمة لفرز قائمة المسابر.
t
عرض موجه للسماح بالتبديل (تشغيل/إيقاف) للمسابر حسب الفهرس. نقاط المسابر لا تزال تتأثر بشروطها.
r
استئناف البرنامج النصي عن طريق تبديل تشغيل جميع المسابر.
p
إيقاف البرنامج النصي مؤقتًا عن طريق تبديل إيقاف تشغيل جميع المسابر.
x
إخفاء/إظهار نافذة الحالة. يسمح هذا برؤية المزيد من المخرجات.
navigation-keys
يمكن استخدام مفاتيح التنقل للتمرير لأعلى ولأسفل في النوافذ.
Tab

SCRIPT LANGUAGE

تشبه لغة برمجة SystemTap لغة awk و C. هناك بنائين رئيسيين خارجيين: المسابر (probes) والدوال (functions). ضمنها، تستخدم العبارات والتعبيرات نحو عوامل النحو والنطاق المشابهة لـ C.

GENERAL SYNTAX

يتم تجاهل المسافات البيضاء. يتم دعم ثلاثة أشكال للتعليقات:


# ... نمط shell، حتى نهاية السطر، باستثناء $# و @#
// ... نمط C++، حتى نهاية السطر
/* ... نمط C ... */
الحروف هي إما سلاسل محاطة بعلامات اقتباس مزدوجة (تمر عبر رموز الهروب C العادية مع الشرطات المائلة العكسية، ومع سلاسل الحروف المتجاورة الملصقة معًا، كما في C)، أو أعداد صحيحة (بالعشرة، سداسي عشري، أو ثماني، باستخدام نفس الترميز كما في C). جميع السلاسل محدودة في الطول بقيمة معقولة (بضع مئات من البايتات). الأعداد الصحيحة هي قيم موقّعة بحجم 64 بت، على الرغم من أن المحلل يقبل (ويلف حول) القيم التي تزيد عن 2**63 موجب.

بالإضافة إلى ذلك، قد يتم إدراج حجج البرنامج النصي المقدمة في نهاية سطر الأوامر. استخدم $1 ... $<NN> للإدراج بدون اقتباس، @1 ... @<NN> للإدراج كسلسلة حرفية. يمكن الوصول إلى عدد الحجج من خلال $# (كرقم بدون اقتباس) أو من خلال @# (كرقم مقتبس). يمكن استخدامها في أي مكان يمكن أن يبدأ فيه رمز، بما في ذلك خلال مرحلة المعالجة المسبقة. يشكل الإشارة إلى رقم وسيط يتجاوز ما تم تقديمه بالفعل خطأ.

PREPROCESSING

يتم تشغيل مرحلة معالجة مسبقة بسيطة شرطية كجزء من التحليل. الشكل العام مشابه للمشغل الثلاثي cond ? exp1 : exp2:

%( CONDITION %? TRUE-TOKENS %)
%( CONDITION %? TRUE-TOKENS %: FALSE-TOKENS %)

تكون CONDITION إما تعبيرًا يعتمد شكله على الكلمة الرئيسية الأولى، أو مقارنة سلاسل حرفية أو مقارنة أحرف عددية. يمكن أيضًا تكوينها من العديد من البدائل والتقاطعات لـ CONDITIONs (كما هو مقصود في الجملة السابقة) باستخدام || و && على التوالي. ومع ذلك، لا تدعم الأقواس حاليًا، لذا فإن تذكر أن التقاطع له الأسبقية على البديل أمر مهم.

إذا كان الجزء الأول هو المعرف kernel_vr أو kernel_v للإشارة إلى رقم إصدار النواة، مع ("2.6.13-1.322FC3smp") أو بدونه ("2.6.13") لاحقة رمز الإصدار، فإن الجزء الثاني هو أحد عوامل مقارنة الأرقام الستة القياسية <، <=، ==، !=، >، و >=، والجزء الثالث هو سلسلة حرفية تحتوي على قيمة إصدار RPM. يعتبر الشرط مستوفى إذا كان إصدار النواة المستهدف (كما تم تجاوزه اختياريًا بواسطة الخيار -r) يقارن بسلسلة الإصدار المعطاة. تتم المقارنة بواسطة وظيفة glibc strverscmp. كحالة خاصة، إذا كان العامل هو مقارنة بسيطة (==)، أو عدم مساواة (!=)، وكانت السلسلة الثالثة تحتوي على أي أحرف بدل (* أو ? أو [)، فيتم التعامل مع التعبير على أنه تطابق بدل (غير صحيح) كما يتم تقييمه بواسطة fnmatch.

إذا، من ناحية أخرى، كان الجزء الأول هو المعرف arch للإشارة إلى بنية المعالج (كما يسميها نظام بناء النواة ARCH/SUBARCH)، فإن الجزء الثاني هو أحد عاملي مقارنة السلاسل == أو !=، والجزء الثالث هو سلسلة حرفية لمطابقتها. هذه المقارنة هي تطابق بدل (غير صحيح).

بالمثل، إذا كان الجزء الأول معرفًا مثل CONFIG_something للإشارة إلى خيار تكوين النواة، فإن الجزء الثاني هو == أو !=، والجزء الثالث هو سلسلة حرفية لمطابقة القيمة (عادة "y" أو "m"). خيارات تكوين النواة غير الموجودة أو غير المعينة يتم تمثيلها بسلسلة فارغة. هذه المقارنة هي أيضًا تطابق بدل (غير صحيح).

إذا كان الجزء الأول هو المعرف systemtap_v، فإن الاختبار يشير إلى إصدار توافق systemtap، والذي قد يتم تجاوزه للبرامج النصية القديمة باستخدام العلامة --compatible. عامل المقارنة هو كما هو الحال بالنسبة لـ kernel_v والجزء الأيمن.

foreach (VAR in ARRAY [ limit EXP ]) STMT
This is the basic foreach loop. On each iteration, VAR is set to the next available key from the array ARRAY, and STMT is executed. The loop terminates when there are no more keys. Keys are iterated in sorted order. The optional [ limit EXP ] clause limits the number of iterations to EXP. Sorting suffixes may be applied to ARRAY to change the order of iteration.
foreach (VAR in ARRAY [INDEX1, INDEX2, ...] [ limit EXP ]) STMT
Same as above, where iterations are limited to elements in the array where the keys match the index values specified. The symbol * can be used to specify an index and will be treated as a wildcard.
foreach (VAR0 = VAR in ARRAY [ limit EXP ]) STMT
This variant of foreach saves current value into VAR0 on each iteration, so it is the same as ARRAY[VAR]. This also works with a tuple of keys. Sorting suffixes on VAR0 have the same effect as on ARRAY.
foreach (VAR0 = VAR in ARRAY [INDEX1, INDEX2, ...] [ limit EXP ]) STMT
Same as above, where iterations are limited to elements in the array where the keys match the index values specified. The symbol * can be used to specify an index and will be treated as a wildcard.
break, continue
Exit or iterate the innermost nesting loop (while or for or foreach) statement.
return EXP
Return EXP value from enclosing function. If the function's value is not taken anywhere, then a return statement is not needed, and the function will have a special "unknown" type with no return value.
next
Return now from enclosing probe handler. This is especially useful in probe aliases that apply event filtering predicates. When used in functions, the execution will be immediately transferred to the next overloaded function.
try { STMT1 } catch { STMT2 }
Run the statements in the first block. Upon any run-time errors, abort STMT1 and start executing STMT2. Any errors in STMT2 will propagate to outer try/catch blocks, if any.
try { STMT1 } catch(VAR) { STMT2 }
Same as above, plus assign the error message to the string scalar variable VAR.
delete ARRAY[INDEX1, INDEX2, ...]
Remove from ARRAY the element specified by the index tuple. If the index tuple contains a * in place of an index, the * is treated as a wildcard and all elements with keys that match the index tuple will be removed from ARRAY. The value will no longer be available, and subsequent iterations will not report the element. It is not an error to delete an element that does not exist.
delete ARRAY
Remove all elements from ARRAY.
delete SCALAR
Removes the value of SCALAR. Integers and strings are cleared to 0 and "" respectively, while statistics are reset to the initial empty state.

تعبيرات

يدعم Systemtap عددًا من المعاملات التي لها نفس بناء الجملة العام والمعنى والأسبقية كما في C و awk. يتم إجراء العمليات الحسابية وفقًا لقواعد C النموذجية للأعداد الصحيحة الموقعة. يتم اكتشاف القسمة على صفر أو تجاوز السعة وتؤدي إلى خطأ.

معاملات الأرقام الثنائية
* / % + - >> << & ^ | && ||
معاملات السلاسل النصية الثنائية
. (ربط السلاسل النصية)
معاملات تعيين الأرقام
= *= /= %= += -= >>= <<= &= ^= |=
معاملات تعيين السلاسل النصية
= .=
معاملات الأرقام الأحادية
+ - ! ~ ++ --
معاملات الأرقام الثنائية أو السلاسل النصية أو المقارنة أو مطابقة التعبيرات المنتظمة
< > <= >= == != =~ !~
معامل ثلاثي
cond ? exp1 : exp2
معامل التجميع
( exp )
استدعاء دالة
fn ([ arg1, arg2, ... ])
فحص عضوية المصفوفة
exp in array
[exp1, exp2, ... ] in array
[*, *, ... ] in array

مطابقة التعبيرات المنتظمة

تدعم لغة البرمجة النصية مطابقة التعبيرات المنتظمة. بناء الجملة الأساسي هو كما يلي:

exp =~ regex
exp !~ regex

(يجب أن يكون المعامل الأول تعبيرًا يقيم إلى سلسلة نصية ؛ يجب أن يكون المعامل الثاني حرفًا نصيًا يحتوي على تعبير منتظم صالح نحويًا.)

يدعم بناء الجملة للتعبيرات المنتظمة ميزات التعبيرات المنتظمة القياسية POSIX كما هو موثق في grep(1) باستثناء وظائف إعادة استخدام التعبير الفرعي ("\1").

بعد المطابقة الناجحة، يمكن استخراج محتويات السلسلة النصية المطابقة والتعبيرات الفرعية باستخدام دوال tapset matched() و ngroups() كما يلي:

if ("an example string" =~ "str(ing)") {
  matched(0) // -> returns "string", the matched substring
  matched(1) // -> returns "ing", the 1st matched subexpression
  ngroups()  // -> returns 2, the number of matched groups
}

المجسات

البناء الرئيسي في لغة البرمجة النصية يحدد المجسات. تربط المجسات الأحداث المجردة بكتلة عبارة ("معالج المجس") ليتم تنفيذها عند حدوث أي من هذه الأحداث. بناء الجملة العام هو كما يلي:

probe PROBEPOINT [, PROBEPOINT] { [STMT ...] }
probe PROBEPOINT [, PROBEPOINT] if (CONDITION) { [STMT ...] }

يتم تحديد الأحداث في بناء جملة خاص يسمى "نقاط المجسات". هناك عدة أنواع من نقاط المجسات التي يحددها المترجم، ويمكن لبرامج tapset تعريف المزيد باستخدام الأسماء المستعارة. يمكن أن تكون نقاط المجسات عامة (wildcarded)، مجمعة، أو مدرجة في تسلسلات تفضيل، أو معلنة اختيارية. مزيد من التفاصيل حول بناء الجملة ودلالات نقاط المجسات مدرجة في صفحة الدليل stapprobes(3stap).

يتم تفسير معالج المجس بالنسبة لسياق كل حدث. بالنسبة للأحداث المرتبطة بشفرة النواة، قد يشمل هذا السياق المتغيرات المعرفة في الشفرة المصدرية في ذلك المكان. يتم تقديم هذه "المتغيرات السياقية" إلى البرنامج النصي كمتغيرات تحمل أسماء مسبوقة بـ "$". لا يمكن الوصول إليها إلا إذا حافظت مترجم النواة عليها على الرغم من التحسين. بالإضافة إلى ذلك، يجب أن تكون الكائنات موجودة في الذاكرة المدخلة (paged-in) في لحظة تنفيذ معالج المجس الخاص بنظام systemtap، لأن systemtap يجب ألا يسبب أي عمليات إدخال إضافية (يقمعها). تحتوي بعض أنواع المجسات على سياق قليل جدًا. انظر صفحات الدليل stapprobes(3stap) لمعرفة أنواع المتغيرات السياقية المتاحة في كل نوع من نقاط المجسات. اعتبارًا من الإصدار 4.3 من systemtap، قد تشير الدوال المستدعاة من معالجات أنواع معينة من نقاط المجسات أيضًا إلى متغيرات سياقية. يتم التعامل مع هذه على أنها استنساخ لتلك الدالة تم تضمينه في معالج المجس المستدعي وتم تقييم $variables في سياقها.

يمكن تزيين المجسات بـ شرط تسليح، يتكون من تعبير منطقي بسيط على متغيرات البرنامج النصي العامة للقراءة فقط. أثناء نزع السلاح (غير نشط، التعبير يقيم إلى خطأ)، تقلل بعض أنواع المجسات أو تلغي نفقات وقت التشغيل الخاصة بها. عندما يقيم شرط التسليح إلى صحيح، سيتم إعادة تسليح المجسات قريبًا، وسيبدأ استدعاء معالجات المجسات الخاصة بها عند إطلاق الأحداث. (قد تُفقد بعض الأحداث خلال فترة التسليح. إذا كان هذا غير مقبول، فلا تستخدم شروط التسليح لتلك المجسات.) مثال على بناء الجملة:

probe timer.us(TIMER) if (enabled) {
}

يمكن تعريف نقاط مجسات جديدة باستخدام "الأسماء المستعارة". تبدو الأسماء المستعارة لنقاط المجسات مشابهة لتعريفات المجسات، ولكن بدلاً من تنشيط مجس في النقطة المحددة، فإنها تحدد فقط اسم نقطة مجس جديدة كاسم مستعار لنقطة موجودة. هناك نوعان من الأسماء المستعارة، أي نمط المقدمة (prologue style) ونمط الخاتمة (epilogue style) اللذين يتم تحديدهما بـ "=" و "+=" على التوالي.

بالنسبة لاسم المستعار بنمط المقدمة، يتم إضافة كتلة العبارات التي تتبع تعريف الاسم المستعار ضمنيًا كمقدمة لأي مجس يشير إلى الاسم المستعار. بينما بالنسبة لاسم المستعار بنمط الخاتمة، يتم إضافة كتلة العبارات التي تتبع تعريف الاسم المستعار ضمنيًا كخاتمة لأي مجس يشير إلى الاسم المستعار. على سبيل المثال:

probe syscall.read = kernel.function("sys_read") {
  fildes = $fd
  if (execname() == "init") next  # skip rest of probe
}

يعرّف نقطة مجس جديدة syscall.read، والتي تتوسع إلى kernel.function("sys_read")، مع العبارة المحددة كمقدمة، وهي مفيدة لتعريف بعض المتغيرات مسبقًا لمستخدم الاسم المستعار و/أو تخطي معالجة المجس بالكامل بناءً على بعض الشروط. و

probe syscall.read += kernel.function("sys_read") {
  if (tracethis) println ($fd)
}

يعرّف نقطة مجس جديدة مع العبارة المحددة كخاتمة، وهي مفيدة لاتخاذ إجراءات بناءً على متغيرات تم تعيينها أو تركها من قبل مستخدم الاسم المستعار. يرجى ملاحظة أنه في كل حالة، يتم التعامل مع العبارات الموجودة في كتلة معالج الاسم المستعار بشكل عادي، بحيث تشكل المتغيرات المعينة هناك تهيئة فقط، وليس استبدالًا بالماكرو.

يمكن أيضًا تعريف الأسماء المستعارة لتشمل مقدمة وخاتمة.

probe syscall.read = kernel.function("sys_read") {
  fildes = $fd
  if (execname() == "init") next
},{
  if (tracethis) println ($fd)
}

يتم استخدام الاسم المستعار تمامًا مثل نوع مجس مدمج.

probe syscall.read {
  printf("reading fd=%d\n", fildes)
  if (fildes > 10) tracethis = 1
}

يمكن للمجسات ذات الاسم المستعار الاستفادة من شرط @probewrite. يتم استخدام هذا التحقق للكشف عما إذا كان متغير البرنامج النصي أو متغير الهدف قد تم كتابته في كتلة معالج المجس.
