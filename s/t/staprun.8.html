NAME

staprun

run a systemtap script

SYNOPSIS

staprun [OPTION]...

DESCRIPTION

The staprun program is the runtime component of the SystemTap SystemTap infrastructure. It runs SystemTap scripts. Scripts are typically written in the SystemTap Scripting Language and translated by the stap(1) utility into loadable kernel modules. These modules are then loaded by staprun using the loadable module interface of the Linux kernel.

The script translator stap(1) generates a compiled module, which is then typically found in the current directory. staprun may be invoked directly by the user or invoked by the stap(1) utility itself.

When staprun is invoked, it looks for a loadable module in the current directory, or in a directory specified by the user.

The module will be loaded into the running kernel. Probes defined in the script will be activated. When probes are triggered, the associated actions in the script will be executed. The output of the script will be printed to standard output.

When the script is finished, or when staprun is interrupted (e.g. by Ctrl+C), the module will be unloaded from the kernel, and the probes will be deactivated.

OPTIONS

--wait
Wait for the script to finish.
--privilege=$LEVEL
Set the privilege level for the script. This option is passed to staprun by stap(1), and is enforced by staprun. See section SAFETY AND SECURITY.
--debug
Enable debug messages from staprun itself.
--help
Print a help message and exit.
--version
Print version information and exit.

ARGUMENTS

MODULE
The name of the SystemTap script module to load. If not specified, staprun will look for a module named script.ko in the current directory.

EXAMPLES

staprun my_script.ko
staprun --wait my_script.ko
staprun --privilege=stapusr my_script.ko

MODULE DETACHING AND ATTACHING

A running SystemTap script module can be detached and reattached using signals. Sending a SIGUSR1 signal to the staprun process will detach the module. Sending a SIGUSR2 signal will reattach the module.

Detaching a module can be useful for temporarily disabling a script without unloading it. Reattaching will resume the script's execution from where it left off.

FILE SWITCHING BY SIGNAL

A running SystemTap script module can be made to switch its output file by sending it a SIGHUP signal. If the script was invoked with the --output= option, staprun will close the current output file and open a new one with a timestamp appended to the filename. For example, if the output file was output.txt, it will be renamed to output.txt.1, and a new file output.txt will be created. This can be repeated indefinitely, creating files like output.txt.2, output.txt.3, and so on.

SAFETY AND SECURITY

SystemTap scripts run in the context of the kernel, and thus have the potential to crash the system or compromise security. To mitigate this, SystemTap implements a set of safety and security features. The primary mechanism is the use of security groups and privilege levels.

A user may select a particular privilege level with the stap --privilege= option, which staprun will later enforce.

stapdev
Members of the stapdev group can write and load script modules with root-equivalent privileges, without particular security constraints. (Many safety constraints remain.)
stapsys
Members of the stapsys group have almost all the privileges of stapdev, except for guru mode constructs.
stapusr
Members only of the stapusr group may any-privileged modules placed into the /lib/modules/VERSION/systemtap by the system administrator.
stapusr
Members only of the stapusr group may also write and load low-privilege script modules, which are normally limited to manipulating their own processes (and not the kernel nor other users' processes).

Part of the privilege enforcement mechanism may require using a stap-server and administrative trust in its cryptographic signer; see the stap-server(8) manual page for a for more information.

On a kernel with FIPS mode enabled, staprun normally refuses to attempt to load systemtap-generated kernel modules. This is because on some kernels, this results in a panic. If your kernel includes corrections such as linux commit #002c77a48b47, then you can force staprun to attempt module loads anyway, by setting the STAP_FIPS_OVERRIDE environment variable to any value.

FILES

/lib/modules/VERSION/systemtap
If MODULE is a module name, the module will be looked for in this directory. Users who are only in the 'stapusr' group can install modules located in this directory. This directory must be owned by the root user and not be world writable.
