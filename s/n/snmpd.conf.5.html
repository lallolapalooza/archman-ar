snmpd.conf(5)

وحدة (module) ucd-snmp/disk (والتي يتم تضمينها كجزء من تهيئة البناء الافتراضية).

disk PATH [ MINSPACE | MINPERCENT% ]
يراقب المساحة المتاحة على القرص المثبت في المسار PATH. الأقراص المثبتة بعد بدء تشغيل الوكيل (agent) لن تتم مراقبتها، ما لم يتم تحديد خيار includeAllDisks.
يمكن تحديد الحد الأدنى إما بالكيلوبايت (MINSPACE) أو كنسبة مئوية من إجمالي القرص (MINPERCENT% مع حرف '%')، الافتراضي هو 100 كيلوبايت إذا لم يتم تحديد أي منهما. إذا انخفضت مساحة القرص الحرة عن هذا الحد، فسيتم تعيين مثيل dskErrorFlag المقابل إلى 1، وسيتم الإبلاغ عن رسالة وصفية مناسبة عبر مثيل dskErrorMsg.
ملاحظة:
هذا الوضع **لن** يؤدي تلقائيًا إلى إرسال فخ (trap) للإبلاغ عن المشكلة - انظر قسم MIB لأحداث DisMan لاحقًا.
includeAllDisks MINPERCENT%
يقوم بتهيئة مراقبة جميع الأقراص الموجودة على النظام، باستخدام الحد المحدد (بالنسبة المئوية). يتم تحديث جدول dskTable ديناميكيًا، تختفي الأقراص غير المثبتة من الجدول وتتم إضافة الأقراص المثبتة حديثًا إلى الجدول. يمكن تعديل الحد للأقراص الفردية باستخدام توجيهات disk المناسبة (التي يمكن أن تأتي إما قبل أو بعد توجيه includeAllDisks).
ملاحظة:
ما إذا كانت توجيهات disk تظهر قبل أو بعد includeAllDisks قد يؤثر على فهرسة جدول dskTable.
يجب تحديد توجيه includeAllDisks واحد فقط - سيتم تجاهل أي نسخ لاحقة.
سيتم تحديد قائمة الأقراص المثبتة من HOST-RESOURCES-MIB::hrFSTable.

إذا لم يتم تحديد أي توجيهات disk أو includeAllDisks، فإن اجتياز جدول dskTable سيفشل (noSuchObject).

مراقبة دخل/خرج القرص

يتطلب هذا أن يكون الوكيل قد تم بناؤه بدعم لوحدة (module) ucd-snmp/diskio (والتي لا يتم تضمينها كجزء من تهيئة البناء الافتراضية).

بشكل افتراضي، يتم تضمين جميع الأجهزة الكتلية المعروفة لنظام التشغيل في جدول diskIOTable. على الأنظمة بخلاف Linux، لا تحتوي هذه الوحدة على توجيهات تهيئة.

على أنظمة Linux، من الممكن استبعاد عدة فئات من أجهزة الكتل من diskIOTable لتجنب تضخيم الجدول بإحصائيات صفرية غير مفيدة للأجهزة الوهمية التي غالبًا ما تكون غير مستخدمة ولكنها مهيأة افتراضيًا لتكون موجودة في معظم توزيعات Linux الحديثة.

diskio_exclude_fd yes
يستبعد جميع أجهزة الكتل لمحركات الأقراص المرنة في Linux، والتي تبدأ أسماؤها بالحرف "fd"، على سبيل المثال "fd0".
diskio_exclude_loop yes
يستبعد جميع أجهزة الكتل لحلقات الاتصال في Linux، والتي تبدأ أسماؤها بالحرف "loop"، على سبيل المثال "loop0".
diskio_exclude_ram yes
يستبعد جميع أجهزة الكتل للذاكرة العشوائية في Linux، والتي تبدأ أسماؤها بالحرف "ram"، على سبيل المثال "ram0".

على أنظمة Linux، من الممكن أيضًا الإبلاغ عن الأجهزة المقبولة صراحةً فقط. قد يستغرق معالجة بيانات diskIOTable وقتًا طويلاً على الأنظمة التي تحتوي على عشرات الآلاف من أجهزة الكتل، ويؤدي قبول الأجهزة الهامة فقط إلى تجنب استهلاك كبير لوحدة المعالجة المركزية.

diskio <device>
يمكّن قائمة قبول الأجهزة ويضيف الجهاز إلى قائمة القبول. سيتم الإبلاغ عن الأجهزة المقبولة صراحةً فقط. يمكن استخدام هذا الخيار عدة مرات.

مراقبة حمل النظام

يتطلب هذا أن يكون الوكيل قد تم بناؤه بدعم لوحدة (module) ucd-snmp/loadave أو وحدة ucd-snmp/memory (وكلاهما يتم تضمينهما كجزء من تهيئة البناء الافتراضية).

load MAX1 [MAX5 [MAX15]]
يراقب متوسط الحمل للنظام المحلي، ويحدد الحدود للمتوسطات لمدة دقيقة واحدة، و 5 دقائق، و 15 دقيقة. إذا تجاوز أي من هذه الأحمال القيمة القصوى المرتبطة بها، فسيتم تعيين مثيل laErrorFlag المقابل إلى 1، وسيتم الإبلاغ عن رسالة وصفية مناسبة عبر مثيل laErrMessage.
ملاحظة:
هذا الوضع **لن** يؤدي تلقائيًا إلى إرسال فخ (trap) للإبلاغ عن المشكلة - انظر قسم MIB لأحداث DisMan لاحقًا.
إذا تم حذف حد MAX15، فسيتم افتراضه إلى قيمة MAX5. إذا تم حذف كل من MAX5 و MAX15، فسيتم افتراضهما إلى قيمة MAX1. إذا لم يتم تحديد هذا التوجيه، فستكون الحدود الثلاثة الافتراضية هي DEFMAXLOADAVE.
إذا تم إعطاء قيمة حد قدرها 0، فلن يقوم الوكيل بالإبلاغ عن الأخطاء عبر مثيلات laErrorFlag أو laErrMessage ذات الصلة، بغض النظر عن الحمل الحالي.

على عكس توجيهات proc و disk، فإن اجتياز جدول laTable سينجح (بافتراض أن وحدة ucd-snmp/loadave تم تكوينها في الوكيل)، حتى لو لم يكن توجيه load موجودًا.

swap MIN
يراقب كمية مساحة المبادلة (swap) المتاحة على النظام المحلي. إذا انخفضت هذه الكمية عن الحد المحدد (MIN كيلوبايت)، فسيتم تعيين الكائن memErrorSwap إلى 1، وسيتم الإبلاغ عن رسالة وصفية مناسبة عبر memSwapErrorMsg.
ملاحظة:
هذا الوضع **لن** يؤدي تلقائيًا إلى إرسال فخ (trap) للإبلاغ عن المشكلة - انظر قسم MIB لأحداث DisMan لاحقًا.
إذا لم يتم تحديد هذا التوجيه، فإن الحد الافتراضي هو 16 ميجابايت.

مراقبة ملف السجل

يتطلب هذا أن يكون الوكيل قد تم بناؤه بدعم لوحدة (module) ucd-snmp/file أو ucd-snmp/logmatch (وكلاهما يتم تضمينهما كجزء من تهيئة البناء الافتراضية).

file FILE [MAXSIZE]
يراقب حجم الملف المحدد (بالكيلوبايت). إذا تم تحديد MAXSIZE، وحجم الملف تجاوز هذا الحد، فسيتم تعيين مثيل fileErrorFlag المقابل إلى 1، وسيتم الإبلاغ عن رسالة وصفية مناسبة عبر مثيل fileErrorMsg.
ملاحظة:
هذا الوضع **لن** يؤدي تلقائيًا إلى إرسال فخ (trap) للإبلاغ عن المشكلة - انظر قسم MIB لأحداث DisMan لاحقًا.
ملاحظة: يمكن مراقبة ما يصل إلى 20 ملفًا.
ملاحظة: إذا لم يتم تحديد أي توجيهات file، فإن اجتياز جدول fileTable سيفشل (noSuchObject).
logmatch NAME FILE CYCLETIME REGEX
يراقب الملف المحدد بحثًا عن تكرارات النمط المحدد REGEX. يتم تخزين موضع الملف داخليًا، لذلك يتم قراءة الملف بالكامل مرة واحدة فقط، وكل تمريرة لاحقة ستقرأ فقط الأسطر الجديدة التي تمت إضافتها إلى الملف منذ القراءة الأخيرة.
NAME
اسم مثيل logmatch (سيظهر باسم logMatchName في شجرة MIB الخاصة بـ ucd-snmp ضمن logMatch/logMatchTable/logMatchEntry/logMatchName).
FILE
المسار المطلق لملف السجل المراد مراقبته. لاحظ أن هذا المسار يمكن أن يحتوي على توجيهات التاريخ/الوقت (كما في أمر 'date' الخاص بـ UNIX). انظر صفحة الدليل لـ 'strftime' للحصول على التوجيهات المختلفة المقبولة.
CYCLETIME
الفترة الزمنية لكل قراءة لملف السجل وتحديث متغير داخلي بالثواني. ملاحظة: ستؤدي عملية SNMPGET* أيضًا إلى قراءة فورية لملف السجل وتحديث المتغير.
REGEX
التعبير النمطي (regular expression) المراد استخدامه. ملاحظة: لا تقم بتضمين التعبير النمطي بين علامتي اقتباس حتى لو كانت هناك مسافات في التعبير، حيث أن علامات الاقتباس ستصبح جزءًا من النمط المطلوب مطابقته!
مثال:
logmatch apache-GETs /usr/local/apache/logs/access.log-%Y-%m-%d 60 GET.*HTTP.*
تم تسمية مثيل logmatch هذا باسم 'apache-GETs'، ويستخدم 'GET.*HTTP.*' كتعبير نمطي له، وسيقوم بمراقبة الملف المسمى (بافتراض أن اليوم هو 6 مايو 2009): '/usr/local/apache/logs/access.log-2009-05-06'، وغدًا سيبحث عن 'access.log-2009-05-07'. يتم قراءة ملف السجل كل 60 ثانية.
ملاحظة: يمكن تحديد ما يصل إلى 250 توجيه logmatch.
ملاحظة: إذا لم يتم تحديد أي توجيهات logmatch، فإن اجتياز جدول logMatchTable سيفشل (noSuchObject).

المراقبة النشطة

السلوك المعتاد لوكيل SNMP هو الانتظار لطلبات SNMP الواردة والاستجابة لها - إذا لم يتم استلام أي طلبات، فعادةً ما لا يتخذ الوكيل أي إجراءات. يصف هذا القسم توجيهات مختلفة يمكنها تهيئة snmpd لاتخاذ دور أكثر نشاطًا.

معالجة الإشعارات

trapcommunity STRING
يحدد سلسلة المجتمع الافتراضية التي سيتم استخدامها عند إرسال الفخاخ (traps). لاحظ أنه يجب استخدام هذا التوجيه قبل أي توجيهات وجهة فخ تعتمد على المجتمع تحتاج إلى استخدامها.
trapsink [-profile p] [-name n] [-tag t] [-s src] HOST [COMMUNITY [PORT]]
trap2sink [-profile p] [-name n] [-tag t] [-s src] HOST [COMMUNITY [PORT]]
/a>
-o OID
تحديد متغيرات إضافية لإضافتها إلى حمولة الإشعار عند تشغيل هذا المراقب. بالنسبة للتعبير الواسع النطاق، سيتم إضافة لاحقة المثيل المطابق إلى أي OIDs محددة باستخدام -o، بينما ستُعامل OIDs المحددة باستخدام -i كمثيلات دقيقة. إذا تم تحديد العلم -I، فلن يكون هناك فرق بين هذين الخيارين.
راجع strictDisman للحصول على تفاصيل ترتيب حمولات الإشعارات.
-r FREQUENCY
يراقب التعبير المعطى كل FREQUENCY، حيث FREQUENCY بالثواني أو اختياريًا متبوعًا بـ s (للثواني) أو m (للدقائق) أو h (للساعات) أو d (للأيام) أو w (للأسابيع). افتراضيًا، سيتم تقييم التعبير كل 600 ثانية (10 دقائق).
-S
يشير إلى أن تعبير المراقب لا ينبغي تقييمه عند بدء تشغيل الوكيل لأول مرة. سيتم إجراء التقييم الأول بمجرد انتهاء فترة التكرار الأولى.
-s
يشير إلى أن تعبير المراقب ينبغي تقييمه عند بدء تشغيل الوكيل لأول مرة. هذا هو السلوك الافتراضي.
ملاحظة:
سيتم إرسال الإشعارات التي يتم تشغيلها بواسطة هذا التقييم الأولي قبل إشارة coldStart.
-u SECNAME
يحدد اسم أمان لاستخدامه في مسح المضيف المحلي، بدلاً من iquerySecName الافتراضي. مرة أخرى، يجب إنشاء هذا المستخدم صراحةً ومنحه حقوق وصول مناسبة.
notificationEvent ENAME NOTIFICATION [-m] [-i OID | -o OID ]*
يحدد حدث إشعار يسمى ENAME. يمكن تشغيل هذا من إدخال monitor معين عن طريق تحديد الخيار -e ENAME (انظر أعلاه). يجب أن يكون NOTIFICATION هو OID لتعريف NOTIFICATION-TYPE للإشعار الذي سيتم إنشاؤه.
إذا تم تقديم الخيار -m، فستتضمن حمولة الإشعار المتغيرات القياسية كما هو محدد في بند OBJECT من تعريف MIB للإشعار. يجب أن يأتي هذا الخيار بعد OID الإشعار (ويجب أن يكون ملف MIB ذي الصلة متاحًا ومحملًا بواسطة الوكيل). خلاف ذلك، يجب سرد هذه المتغيرات بشكل صريح (إما هنا أو في توجيه monitor المقابل).
تحدد الخيارات -i OID و -o OID متغيرات إضافية ليتم إلحاقها بحمولة الإشعار، بعد القائمة القياسية. إذا تضمن إدخال المراقب الذي قام بتشغيل هذا الحدث تعبيرًا واسع النطاق، فسيتم إضافة لاحقة المثيل المطابق إلى أي OIDs محددة باستخدام -o، بينما ستُعامل OIDs المحددة باستخدام -i كمثيلات دقيقة. إذا تم تحديد العلم -I لتوجيه monitor، فلن يكون هناك فرق بين هذين الخيارين.
setEvent ENAME [-I] OID = VALUE
يحدد حدث تعيين يسمى ENAME، ويخصص القيمة (عدد صحيح) VALUE للمعرف OID المحدد. يمكن تشغيل هذا من إدخال monitor معين عن طريق تحديد الخيار -e ENAME (انظر أعلاه).
إذا تضمن إدخال المراقب الذي قام بتشغيل هذا الحدث تعبيرًا واسع النطاق، فسيتم عادةً إضافة لاحقة المثيل المطابق إلى OID. إذا تم تحديد العلم -I لأي من توجيهات monitor أو setEvent، فسيتم اعتبار OID المحدد مثيلًا واحدًا دقيقًا.
strictDisman yes
ينص تعريف إشعارات SNMP على أن المتغيرات المحددة في بند OBJECT يجب أن تأتي أولاً (بالترتيب المحدد)، تليها أي متغيرات "إضافية" قد يشعر مولد الإشعارات بأنها مفيدة. النهج الأكثر طبيعية سيكون ربط هذه المتغيرات الإلزامية بإدخال notificationEvent، وإلحاق أي متغيرات مرتبطة بإدخال المراقب الذي قام بتشغيل الإشعار بنهاية هذه القائمة. هذا هو السلوك الافتراضي لتنفيذ Net-SNMP Event MIB.
للأسف، تحدد مواصفات DisMan Event MIB في الواقع أن المتغيرات المتعلقة بالمشغل يجب أن تأتي أولاً، تليها تلك المتعلقة بالحدث. يمكن استخدام هذا التوجيه لاستعادة هذا السلوك الصحيح تمامًا (ولكن غير المناسب).
ملاحظة:
قد يؤدي ترتيب DisMan الصارم إلى إنشاء قوائم حمولات إشعارات غير صالحة إذا تم استخدام علامة notificationEvent -n مع خيارات متغيرات monitor -o (أو -i).
إذا لم تحدد إدخالات monitor متغيرات حمولة، فإن تعيين هذا التوجيه لا يكون ذا صلة.
linkUpDownNotifications yes
سيقوم بتكوين جداول Event MIB لمراقبة ifTable لشبكة الواجهات التي يتم تشغيلها أو إيقافها، وتشغيل إشعار linkUp أو linkDown حسب الاقتضاء.
هذا يعادل تمامًا التكوين التالي:
notificationEvent  linkUpTrap    linkUp   ifIndex ifAdminStatus ifOperStatus
notificationEvent  linkDownTrap  linkDown ifIndex ifAdminStatus ifOperStatus
monitor  -r 60 -e linkUpTrap   "Generate linkUp" ifOperStatus != 2
monitor  -r 60 -e linkDownTrap "Generate linkDown" ifOperStatus == 2
defaultMonitors yes
سيقوم بتكوين جداول Event MIB لمراقبة جداول UCD-SNMP-MIB المختلفة للمشاكل (كما هو موضح بواسطة كائنات أعمدة xxErrFlag المناسبة).
هذا يعادل تمامًا التكوين التالي:
monitor	-o prNames -o prErrMessage "process table" prErrorFlag != 0
monitor	-o memErrorName -o memSwapErrorMsg "memory" memSwapError != 0
monitor	-o extNames -o extOutput "extTable" extResult != 0
monitor	-o dskPath -o dskErrorMsg "dskTable" dskErrorFlag != 0
monitor	-o laNames -o laErrMessage  "laTable" laErrorFlag != 0
monitor	-o fileName -o fileErrorMsg  "fileTable" fileErrorFlag != 0

في كلتا هاتين الحالتين الأخيرتين، يجب أن يحتوي ملف snmpd.conf أيضًا على توجيه iquerySecName، جنبًا إلى جنب مع إدخال createUser المقابل وتكوين تحكم مناسب في الوصول.

DisMan Schedule MIB

قامت مجموعة عمل DisMan أيضًا بإنشاء آلية لجدولة إجراءات معينة (تعيين SET محدد) في أوقات معينة. يتطلب هذا أن يكون الوكيل قد تم بناؤه بدعم من وحدة disman/schedule (وهي مدرجة كجزء من تكوين البناء الافتراضي لأحدث توزيع).

هناك ثلاث طرق لتحديد الإجراء المجدول:

repeat FREQUENCY OID = VALUE
يقوم بتكوين تعيين SET للقيمة (عدد صحيح) VALUE إلى مثيل MIB OID، ليتم تشغيله كل FREQUENCY ثانية، حيث FREQUENCY بالثواني أو اختياريًا متبوعًا بـ s (للثواني) أو m (للدقائق) أو h (للساعات) أو d (للأيام) أو w (للأسابيع).
cron MINUTE HOUR DAY MONTH WEEKDAY OID = VALUE
يقوم بتكوين تعيين SET للقيمة (عدد صحيح) VALUE إلى مثيل MIB OID، ليتم تشغيله في الأوقات المحددة بواسطة الحقول MINUTE إلى WEEKDAY. تتبع هذه نفس نمط حقول crontab(5) المكافئة.
ملاحظة:
يجب تحديد هذه الحقول كقائمة (مفصولة بفواصل) من القيم الرقمية. لا يتم دعم القيم المسماة لحقول MONTH و WEEKDAY، ولا نطاقات القيم. يمكن تحديد تطابق حرف البدل كـ '*'.
يمكن لحقل DAY أيضًا قبول قيم سالبة، للإشارة إلى الأيام المحسوبة إلى الوراء من نهاية الشهر.
at MINUTE HOUR DAY MONTH WEEKDAY OID = VALUE
يقوم بتكوين تعيين SET لمرة واحدة، ليتم تشغيله في أول وقت مطابق كما هو محدد بواسطة الحقول MINUTE إلى WEEKDAY. تفسير هذه الحقول هو نفس تفسير توجيه cron بالضبط.

Data Delivery via Notfiications

ملاحظة: هذه الوظيفة متاحة فقط إذا تم تجميع وحدة deliver/deliverByNotify mib في الوكيل

في بعض المواقف، قد يكون من المفيد توصيل بيانات SNMP عبر إشعارات SNMP (TRAPs و INFORMs) بدلاً من العملية النموذجية التي يقوم بها المدير بإصدار طلبات للبيانات (عبر GETs و GETNEXTs). أسباب القيام بذلك عديدة، ولكنها في كثير من الأحيان حالات زاوية. السبب الأكثر شيوعًا لرغبة هذا السلوك قد يكون مراقبة الأجهزة التي تقع خلف NATs أو جدران الحماية التي تمنع حركة مرور SNMP الواردة.

تجدر الإشارة إلى أنه على الرغم من أن معظم برامج الإدارة قادرة على تسجيل الإشعارات، فإن القليل جدًا (إن وجد) من برامج الإدارة سيقوم بتحديث "قاعدة بيانات المعرفة" الخاصة بها بناءً على محتويات إشعارات SNMP. أي، لن يقوم (على سبيل المثال) بتحديث تاريخ عداد حركة الواجهة المستخدم لإنتاج الرسوم البيانية. تحتوي معظم حزم إدارة الشبكات الكبيرة على قاعدة بيانات منفصلة لتخزين البيانات المستلمة عبر طلبات SNMP (GETs و GETNEXTs) مقابل تلك المستلمة من الإشعارات. يلزم البحث في إمكانيات برنامج محطة الإدارة الخاصة بك قبل افتراض أن هذه الوظيفة ستحل متطلبات توصيل البيانات الخاصة بك.

سيتم إرسال الإشعارات التي تم إنشاؤها عبر هذه الآلية إلى مجموعة الأهداف القياسية للإشعارات المكونة. راجع قسم "معالجة الإشعارات" في هذه الوثيقة لمزيد من المعلومات.

deliverByNotify [-p] [-m] [-s MAXSIZE] FREQUENCY OID
يخبر هذا التوجيه وكيل SNMP بالقيام بمسح ذاتي لـ OID، وجمع كافة البيانات وإرسالها كل FREQUENCY ثانية، حيث FREQUENCY بالثواني أو اختياريًا متبوعًا بـ s (للثواني) أو m (للدقائق) أو h (للساعات) أو d (للأيام) أو w (للأسابيع). افتراضيًا، يتم تضمين الأعداد الثابتة في الإشعار الذي حدد عدد مرات إرسال الإشعار (ما لم يتم تحديد الخيار -p) ورقم الرسالة من إجمالي الرسائل التي ينتمي إليها إشعار معين (ما لم يتم تحديد -m). لتقسيم الإشعارات إلى أحجام حزم قابلة للإدارة، استخدم العلامة -s لتحديد الحد الأقصى التقريبي لعدد البايتات التي يجب أن يقتصر عليها كل رسالة إشعار. إذا تطلب الأمر أكثر من MAXSIZE بايت، فسيتم إرسال إشعارات متعددة لتوصيل البيانات. لاحظ أن الحسابات لضمان الوصول إلى الحد الأقصى للحجم هي تقديرات، وبالتالي لا يمكن ضمان أنها ستكون أقل من هذا الحجم تمامًا، لذا اترك مساحة احتياطية إذا كان من الضروري تجنب التجزئة. تشير القيمة -1 إلى فرض كل شيء في رسالة واحدة بغض النظر عن حجمها.
مثال على الاستخدام: ما يلي سيقوم بتسليم محتويات ifTable مرة كل ساعة ومحتويات مجموعة system مرة كل ساعتين:
deliverByNotify 3600 ifTable
deliverByNotify 7200 system
deliverByNotifyMaxPacketSize SIZEINBYTES
يحدد الحد الافتراضي لحجم الإشعار (انظر علامة -s أعلاه).
deliverByNotifyOid OID
deliverByNotifyFrequencyOid OID
deliverByNotifyMessageNumberOid OID
deliverByNotifyMaxMessageNumberOid OID
تحدد هذه العناصر OID البيانات التي سيتم إرسال الإشعار تحتها، و OID القياسي، و OID رقم الرسالة، و OID الحد الأقصى لعدد الرسائل. هذه العناصر افتراضية للعناصر في MIB-PERIODIC-NOTIFY-MIB.

توسيع وظائف الوكيل

إحدى الميزات المميزة الأولى لمجموعة UCD الأصلية كانت القدرة على توسيع وظائف الوكيل - ليس فقط عن طريق إعادة التجميع برموز لوحدات MIB جديدة، ولكن أيضًا عن طريق تكوين الوكيل قيد التشغيل للإبلاغ عن معلومات إضافية. هناك عدد من التقنيات لدعم ذلك، بما في ذلك:

  • تشغيل أوامر خارجية (exec, extend, pass)
  • تحميل رموز جديدة ديناميكيًا (perl مضمن، dlmod)
  • التواصل مع وكلاء آخرين (proxy, SMUX, AgentX)

أوامر التوسيع العشوائية

كانت آلية التوسيع الأولى هي القدرة على تشغيل أوامر عشوائية أو نصوص برمجية (scripts). لا تحتاج هذه الأوامر إلى أن تكون مدركة لعمليات SNMP، أو تتبع سلوكًا معينًا - تم تصميم هياكل MIB لاستيعاب أي شكل من أشكال إخراج الأوامر. يتطلب استخدام هذه الآلية أن يكون الوكيل قد تم بناؤه بدعم من وحدات ucd-snmp/extensible و/أو agent/extend (والتي يتم تضمين كليهما كجزء من تكوين البناء الافتراضي).

exec [MIBOID] NAME PROG ARGS
sh [MIBOID] NAME PROG ARGS
استدعاء PROG المسمى مع وسائط ARGS. افتراضيًا، سيتم الإبلاغ عن حالة الخروج والسطر الأول من الإخراج من الأمر عبر extTable، مع تجاهل أي إخراج إضافي.
ملاحظة:
تظهر الإدخالات في هذه الجدول بالترتيب الذي يتم به قراءتها من ملف التكوين. هذا يعني أن إضافة توجيهات exec (أو sh) جديدة وإعادة تشغيل الوكيل قد يؤثر على فهرسة الإدخالات الأخرى.
يجب أن يكون وسيط PROG لتعليمات exec مسارًا كاملاً لملف ثنائي حقيقي، حيث يتم تنفيذه عبر استدعاء النظام exec(). لاستدعاء نص برمجي، استخدم التوجيه sh بدلاً من ذلك.
إذا تم تحديد MIBOID، فسيتم تجذير النتائج في هذه النقطة في شجرة OID، وإرجاع عبارة الخروج كـ MIBOID.100.0 والإخراج الكامل للأمر في جدول زائف مرتكز على MIBNUM.101 - مع "صف" واحد لكل سطر من الإخراج.
ملاحظة:
لا يشكل تخطيط هذا الشكل "القابل لإعادة التوطين" لإخراج exec (أو sh) بنية MIB صالحة بدقة. يتم إهمال هذه الآلية - يرجى الرجوع إلى التوجيه extend (الموضح أدناه) بدلاً من ذلك.
لا يقوم الوكيل بتخزين حالة الخروج أو إخراج البرنامج المنفذ مؤقتًا.
execfix NAME PROG ARGS
يسجل أمرًا يمكن استدعاؤه عند الطلب - عادةً للاستجابة للأخطاء أو إصلاحها مع إدخال exec أو sh المقابل. عند تعيين المثيل extErrFix لإدخال NAMEd معين إلى القيمة العددية 1، سيتم استدعاء هذا الأمر.
ملاحظة:
يمكن استخدام هذا التوجيه فقط بالاقتران مع توجيه exec أو sh مطابق، والذي يجب تعريفه أولاً. محاولة تعريف توجيه execfix منفصل ستفشل.

لا يمكن تكوين امتدادات exec و sh إلا عبر ملف snmpd.conf. لا يمكن تعيينها عبر طلبات SNMP SET.

extend [-cacheTime TIME] [-execType TYPE] [MIBOID] NAME PROG ARGS
يعمل بطريقة مماثلة لتوجيه exec، ولكن مع عدد من التحسينات. جداول MIB (nsExtendConfigTable وما إلى ذلك) مفهرسة بواسطة الرمز NAME، وبالتالي لا تتأثر بترتيب قراءة الإدخالات من ملفات التكوين. هناك جدولان للنتائج - أحدهما (nsExtendOutput1Table) يحتوي على حالة الخروج، والسطر الأول، والإخراج الكامل (كسلسلة واحدة) لكل إدخال extend، والآخر (nsExtendOutput2Table) يحتوي على الإخراج الكامل كسلسلة من الأسطر المنفصلة.
إذا تم تحديد -cacheTime، فسيتم استخدام وسيطه كوقت انتهاء صلاحية ذاكرة التخزين المؤقت (بالثواني الكاملة) لإدخال extend هذا. توفر هذه الآلية طريقة غير متطايرة لتحديد وقت انتهاء صلاحية ذاكرة التخزين المؤقت.
إذا تم تحديد -execType وكانت قيمته sh، فسيتم تشغيل إدخال extend هذا في shell. وإلا فسيتم تشغيله في وضع exec الافتراضي. توفر هذه الآلية طريقة غير متطايرة لتحديد نوع التنفيذ.
إذا تم تحديد MIBOID، فسيتم تجذير جداول التكوين والنتائج في هذه النقطة في شجرة OID، ولكنها منظمة بطريقة مماثلة تمامًا. هذا يعني أن العديد من توجيهات extend المنفصلة يمكن أن تحدد نفس جذر MIBOID، دون تعارض.
يتم تخزين حالة الخروج والإخراج مؤقتًا لكل إدخال على حدة، ويمكن مسحهما (وتكوين سلوك التخزين المؤقت) باستخدام nsCacheTable.
extendfix NAME PROG ARGS
يسجل أمرًا يمكن استدعاؤه عند الطلب، عن طريق تعيين المثيل nsExtendRunType المناسب إلى القيمة run-command(3). على عكس execfix المكافئ، لا يحتاج هذا التوجيه إلى إقرانه بإدخال extend مطابق، ويمكن أن يظهر بمفرده.

يمكن تكوين كل من توجيهات extend و extendfix ديناميكيًا، باستخدام طلبات SNMP SET إلى NET-SNMP-EXTEND-MIB.

أوامر التوسيع الخاصة بـ MIB

تستدعي المجموعة الأولى من توجيهات التوسيع أوامر عشوائية، وتعتمد على مرونة بنية MIB (وتطبيقات الإدارة) لاستيعاب الإخراج وتفسيره. هذه طريقة مريحة لجعل المعلومات متاحة بسرعة وبساطة، ولكنها غير مفيدة عند تنفيذ كائنات MIB محددة، حيث يجب أن يتوافق التوسيع مع بنية MIB (بدلاً من العكس). تتعلق آليات التوسيع المتبقية بجميع هذه المواقف الخاصة بـ MIB - بدءًا بنصوص "التمرير". يتطلب استخدام هذه الآلية أن يكون الوكيل قد تم بناؤه بدعم من وحدات ucd-snmp/pass و ucd-snmp/pass_persist (والتي يتم تضمين كليهما كجزء من تكوين البناء الافتراضي).

pass [-p priority] MIBOID PROG
سيمرر التحكم في الشجرة الفرعية المتجذرة في MIBOID إلى الأمر PROG المحدد. سيؤدي طلب GET و GETNEXT لـ OIDs داخل هذه الشجرة إلى تشغيل هذا الأمر، ويتم استدعاؤه كالتالي:
PROG -g OID
PROG -n OID
على التوالي، حيث OID هو OID المطلوب. يجب أن يعيد الأمر PROG متغير الاستجابة كثلاثة أسطر منفصلة مطبوعة إلى stdout - يجب أن يكون السطر الأول هو OID للقيمة المعادة، والثاني هو نوعها (واحد من السلاسل النصية integer, gauge, counter, timeticks, ipaddress, objectid, octet, أو string)، والثالث هو القيمة نفسها. (ملاحظة: يتم إرسال البايتات كسلاسل ست عشري ASCII مفصولة بمسافات، على سبيل المثال "00 3f dd 00 c6 be").
إذا لم يتمكن الأمر من إعادة متغير ربط مناسب - على سبيل المثال، لم يتوافق OID المحدد مع مثيل صالح لطلب GET، أو لم تكن هناك مثيلات تالية لـ GETNEXT - فيجب عليه الخروج دون إنتاج أي إخراج. سيؤدي ذلك إلى خطأ SNMP noSuchName، أو استثناء noSuchInstance.
ملاحظة:
لا يتم دعم نوع SMIv2 counter64 واستثناء noSuchObject لـ SNMPv2.
سيؤدي طلب SET إلى استدعاء الأمر كالتالي:
PROG -s OID TYPE VALUE
حيث TYPE هو أحد الرموز المدرجة أعلاه، مشيرًا إلى نوع القيمة المقدمة كمعلمة ثالثة.
إذا نجح التعيين، فيجب على الأمر PROG الخروج دون إنتاج أي إخراج. يجب الإشارة إلى الأخطاء عن طريق الكتابة

pass, pass_persist, and pass_suffix

These directives allow you to delegate the handling of parts of the MIB tree to external commands. The command specified is invoked whenever an OID is requested from the corresponding subtree.

pass OID PROG
will pass control of the subtree rooted at OID to the specified PROG command. This command is invoked once for each request (and each varbind within a single request).
Upon initialization, PROG will be passed the string "PING\n" on stdin, and should respond by printing "PONG\n" to stdout.
For GET and GETNEXT requests, PROG will be passed two lines on stdin: the command (get or getnext) and the requested OID. It should respond by printing three lines to stdout: the OID for the result varbind, the TYPE and the VALUE itself. If the command cannot return an appropriate varbind, it should print "NONE\n" to stdout.
For SET requests, PROG will be passed three lines on stdin: the command (set), the requested OID, and the type and value (both on the same line). If the assignment is successful, the command should print "DONE\n" to stdout. Errors should be indicated by writ-
Note:
The other SNMPv2 errors are not supported.
In either case, the command should exit once it has finished processing. Each request (and each varbind within a single request) will trigger a separate invocation of the command.
The default registration priority is 127. This can be changed by supplying the optional -p flag, with lower priority registrations being used in preference to higher priority values.
pass_persist [-p priority] MIBOID PROG
will also pass control of the subtree rooted at MIBOID to the specified PROG command. However this command will continue to run after the initial request has been answered, so subsequent requests can be processed without the startup overheads.
Upon initialization, PROG will be passed the string "PING\n" on stdin, and should respond by printing "PONG\n" to stdout.
For GET and GETNEXT requests, PROG will be passed two lines on stdin, the command (get or getnext) and the requested OID. It should respond by printing three lines to stdout - the OID for the result varbind, the TYPE and the VALUE itself - exactly as for the pass directive above. If the command cannot return an appropriate varbind, it should print print "NONE\n" to stdout (but continue running).
For SET requests, PROG will be passed three lines on stdin, the command (set) and the requested OID, followed by the type and value (both on the same line). If the assignment is successful, the command should print "DONE\n" to stdout. Errors should be indicated by writing one of the strings not-writable, wrong-type, wrong-length, wrong-value or inconsistent-value to stdout, and the agent will generate the appropriate error response. In either case, the command should continue running.
The registration priority can be changed using the optional -p flag, just as for the pass directive.

pass and pass_persist extensions can only be configured via the snmpd.conf file. They cannot be set up via SNMP SET requests.

Embedded Perl Support

Programs using the previous extension mechanisms can be written in any convenient programming language - including perl, which is a common choice for pass-through extensions in particular. However the Net-SNMP agent also includes support for embedded perl technology (similar to mod_perl for the Apache web server). This allows the agent to interpret perl scripts directly, thus avoiding the overhead of spawning processes and initializing the perl system when a request is received.

Use of this mechanism requires that the agent was built with support for the embedded perl mechanism, which is not part of the default build environment. It must be explicitly included by specifying the '--enable-embedded-perl' option to the configure script when the package is first built.

If enabled, the following directives will be recognised:

disablePerl true
will turn off embedded perl support entirely (e.g. if there are problems with the perl installation).
perlInitFile FILE
loads the specified initialisation file (if present) immediately before the first perl directive is parsed. If not explicitly specified, the agent will look for the default initialisation file /usr/share/snmp/snmp_perl.pl.
The default initialisation file creates an instance of a NetSNMP::agent object - a variable $agent which can be used to register perl-based MIB handler routines.
perl EXPRESSION
evaluates the given expression. This would typically register a handler routine to be called when a section of the OID tree was requested:
perl use Data::Dumper;
perl sub myroutine  { print "got called: ",Dumper(@_),"\n"; }
perl $agent->register('mylink', '.1.3.6.1.8765', \&myroutine);
This expression could also source an external file:
perl 'do /path/to/file.pl';
or perform any other perl-based processing that might be required.

Dynamically Loadable Modules

Most of the MIBs supported by the Net-SNMP agent are implemented as C code modules, which were compiled and linked into the agent libraries when the suite was first built. Such implementation modules can also be compiled independently and loaded into the running agent once it has started. Use of this mechanism requires that the agent was built with support for the ucd-snmp/dlmod module (which is included as part of the default build configuration).

dlmod NAME PATH
will load the shared object module from the file PATH (an absolute filename), and call the initialisation routine init_NAME.
Note:
If the specified PATH is not a fully qualified filename, it will be interpreted relative to /usr/lib/snmp/dlmod, and .so will be appended to the filename.

This functionality can also be configured using SNMP SET requests to the UCD-DLMOD-MIB.

Proxy Support

Another mechanism for extending the functionality of the agent is to pass selected requests (or selected varbinds) to another SNMP agent, which can be running on the same host (presumably listening on a different port), or on a remote system. This can be viewed either as the main agent delegating requests to the remote one, or acting as a proxy for it. Use of this mechanism requires that the agent was built with support for the ucd-snmp/proxy module (which is included as part of the default build configuration).

proxy [-Cn CONTEXTNAME] [SNMPCMD_ARGS] HOST OID [REMOTEOID]
will pass any incoming requests under OID to the agent listening on the port specified by the transport address HOST. See the section LISTENING ADDRESSES in the snmpd(8) manual page for more information about the format of listening addresses.
Note:
To proxy the entire MIB tree, use the OID .1.3 (not the top-level .1)

The SNMPCMD_ARGS should provide sufficient version and administrative information to generate a valid SNMP request (see snmpcmd(1)).

Note:
The proxied request will not use the administrative settings from the original request.

If a CONTEXTNAME is specified, this will register the proxy delegation within the named context in the local agent. Defining multiple proxy directives for the same OID but different contexts can be used to query several remote agents through a single proxy, by specifying the appropriate SNMPv3 context in the incoming request (or using suitable configured community strings - see the com2sec directive).

Specifying the REMOID parameter will map the local MIB tree rooted at OID to an equivalent subtree rooted at REMOID on the remote agent.

SMUX Sub-Agents

The Net-SNMP agent supports the SMUX protocol (RFC 1227) to communicate with SMUX-based subagents (such as gated, zebra or quagga). Use of this mechanism requires that the agent was built with support for the smux module, which is not part of the default build environment, and must be explicitly included by specifying the '--with-mib-modules=smux' option to the configure script when the package is first built.

Note:
This extension protocol has been officially deprecated in favour of AgentX (see below).
smuxpeer OID PASS
will register a subtree for SMUX-based processing, to be authenticated using the password PASS. If a subagent (or "peer") connects to the agent and registers this subtree then requests for OIDs within it will be passed to that SMUX subagent for processing.
A suitable entry for an OSPF routing daemon (such as gated, zebra or quagga) might be something like
smuxpeer .1.3.6.1.2.1.14 ospf_pass
smuxsocket <IPv4-address>
defines the IPv4 address for SMUX peers to communicate with the Net-SNMP agent. The default is to listen on all IPv4 interfaces ("0.0.0.0"), unless the package has been configured with "--enable-local-smux" at build time, which causes it to only listen on 127.0.0.1 by default. SMUX uses the well-known TCP port 199.

Note the Net-SNMP agent will only operate as a SMUX master agent. It does not support acting in a SMUX subagent role.

AgentX Sub-Agents

The Net-SNMP agent supports the AgentX protocol (RFC 2741) in both master and subagent roles. Use of this mechanism requires that the agent was built with support for the agentx module (which is included as part of the default build configuration), and also that this support is explicitly enabled (e.g. via the snmpd.conf file).
