SETUID(3P) دليل مبرمجي POSIX SETUID(3P)

المقدمة

هذه الصفحة الدليلية هي جزء من دليل مبرمجي POSIX. قد يختلف تطبيق Linux لهذا الواجهة (استشر صفحة دليل Linux المقابلة لتفاصيل سلوك Linux)، أو قد لا تكون الواجهة مطبقة في Linux.

الاسم

setuid — تعيين معرف المستخدم

الملخص

#include <unistd.h>
int setuid(uid_t uid);

الوصف

إذا كانت العملية تتمتع بالصلاحيات المناسبة، فإن setuid() ستقوم بتعيين معرف المستخدم الحقيقي، ومعرف المستخدم الفعلي، ومعرف المستخدم المحفوظ للعملية المتصلة إلى uid.

إذا كانت العملية لا تتمتع بالصلاحيات المناسبة، ولكن uid يساوي معرف المستخدم الحقيقي أو معرف المستخدم المحفوظ، فإن setuid() ستقوم بتعيين معرف المستخدم الفعلي إلى uid؛ سيظل معرف المستخدم الحقيقي ومعرف المستخدم المحفوظ كما هما.

لن تؤثر الدالة setuid() على قائمة مجموعات إضافية بأي شكل من الأشكال.

قيمة الإرجاع

عند اكتمالها بنجاح، سيتم إرجاع 0. خلاف ذلك، سيتم إرجاع -1 وتعيين errno للإشارة إلى الخطأ.

الأخطاء

ستفشل الدالة setuid()، وتعيد -1، وتعين errno إلى القيمة المقابلة إذا كان أحد ما يلي صحيحًا أو أكثر:

EINVAL
قيمة الوسيط uid غير صالحة ولا تدعمها التنفيذ.
EPERM
العملية لا تتمتع بالصلاحيات المناسبة و uid لا يتطابق مع معرف المستخدم الحقيقي أو معرف المستخدم المحفوظ.

الأقسام التالية إعلامية.

أمثلة

لا شيء.

استخدام التطبيق

لا شيء.

التعليل

تعكس السلوكيات المختلفة للدوال setuid() و setgid() عند استدعائها بواسطة عمليات غير مميزة سلوك تطبيقات تاريخية مختلفة. للتوافقية، يوصى بأن تستخدم التطبيقات الجديدة غير المميزة الدوال seteuid() و setegid() بدلاً من ذلك.

تسمح إمكانية معرف المستخدم المحفوظ للبرنامج باستعادة معرف المستخدم الفعلي الذي تم إنشاؤه عند آخر استدعاء exec. وبالمثل، تسمح إمكانية معرف المجموعة المحفوظ للبرنامج باستعادة معرف المجموعة الفعلي الذي تم إنشاؤه عند آخر استدعاء exec. هذه الإمكانيات مشتقة من System V. بدونها، قد يضطر البرنامج إلى العمل بصلاحيات المستخدم الخارق لأداء نفس الوظائف، لأن المستخدم الخارق يمكنه الكتابة على ملفات المستخدم. هذه مشكلة لأن مثل هذا البرنامج يمكنه الكتابة على ملفات أي مستخدم، ولذلك يجب كتابته بعناية لمحاكاة أذونات العملية المتصلة بشكل صحيح. في System V، تم تنفيذ هذه الإمكانيات تقليديًا فقط من خلال الدوال setuid() و setgid() للعمليات غير المميزة. حقيقة أن سلوك هذه الدوال كان مختلفًا للعمليات المميزة جعلها صعبة الاستخدام. قام معيار POSIX.1-1990 بتعريف الدالة setuid() لتتصرف بشكل مختلف للمستخدمين المميزين وغير المميزين. عندما كان لدى المتصل صلاحيات مناسبة، كانت الدالة تعين معرف المستخدم الحقيقي، ومعرف المستخدم الفعلي، ومعرف المستخدم المحفوظ للعملية المتصلة في التطبيقات التي تدعم ذلك. عندما لم يكن لدى المتصل صلاحيات مناسبة، كانت الدالة تعين فقط معرف المستخدم الفعلي، مع مراعاة فحوصات الأذونات. الاستخدام السابق مطلوب عمومًا لأدوات مثل login و su، وهي ليست تطبيقات متوافقة وبالتالي خارج نطاق POSIX.1-2008. ترغب هذه الأدوات في تغيير معرف المستخدم بشكل لا رجعة فيه إلى قيمة جديدة، وعادةً ما تكون قيمة مستخدم غير مميز. الاستخدام الأخير مطلوب للتطبيقات المتوافقة المثبتة مع بت تعيين المستخدم (set-user-ID) وتحتاج إلى إجراء عمليات باستخدام معرف المستخدم الحقيقي.

يضيف POSIX.1-2008 الوظيفة الأخيرة بميزة إلزامية تسمى _POSIX_SAVED_IDS. تسمح هذه الميزة لتطبيق بت-تعيين-المستخدم (set-user-ID) بالتبديل بين معرف المستخدم الفعلي الخاص به بين قيم معرف المستخدم الحقيقي في وقت exec ومعرف المستخدم الفعلي. لسوء الحظ، لم يسمح معيار POSIX.1-1990 للتطبيق المتوافق الذي يستخدم هذه الميزة بالعمل بشكل صحيح عندما يحدث أن يتم تنفيذه بصلاحيات (معرفة بشكل ضمني) مناسبة. علاوة على ذلك، لم يكن لدى التطبيق وسيلة لمعرفة ما إذا كان يمتلك هذه الصلاحية. نظرًا لأن ميزة معرف المستخدم المحفوظ مرغوبة جدًا للتطبيقات، كما يتضح من حقيقة أن NIST طلبها في FIPS 151-2، فقد تم إلزامها بواسطة POSIX.1-2008. ومع ذلك، هناك مطبقون ترددوا في دعمها نظرًا للقيود المذكورة أعلاه.

يتعامل نظام 4.3BSD مع المشكلة من خلال دعم دوال منفصلة: setuid() (التي تعين دائمًا معرفي المستخدم الحقيقي والفعلي، مثل setuid() في POSIX.1-2008 للمستخدمين المميزين)، و seteuid() (التي تعين دائمًا معرف المستخدم الفعلي فقط، مثل setuid() في POSIX.1-2008 للعمليات غير المميزة). يبدو أن فصل الوظائف هذا إلى دوال متميزة مرغوب فيه. لا يدعم 4.3BSD ميزة معرف المستخدم المحفوظ. إنه يدعم وظائف مماثلة لتبديل معرف المستخدم الفعلي ذهابًا وإيابًا عبر setreuid()، والتي تسمح بتبديل معرفي المستخدم الحقيقي والفعلي. يبدو هذا النموذج أقل تفضيلاً من معرف المستخدم المحفوظ لأن معرف المستخدم الحقيقي يتغير كتأثير جانبي. يتضمن 4.4BSD الحالي معرفات فعلية محفوظة ويستخدمها لـ seteuid() و setegid() كما هو موضح أعلاه. سيتم إهمال أو إزالة الدوال setreuid() و setregid().

الحل هنا هو:

*
المتطلب بأن تدعم جميع التطبيقات وظائف معرف المستخدم المحفوظ، والتي تم تعيينها بواسطة دوال exec واستدعاءات setuid() المميزة.
*
إضافة الدوال seteuid() و setegid() كبدائل محمولة لـ setuid() و setgid() للعمليات غير المميزة والمميزة.

قدمت الأنظمة التاريخية آليتين لعملية بت-تعيين-المستخدم (set-user-ID) لتغيير معرف المستخدم الفعلي الخاص بها ليكون هو نفسه معرف المستخدم الحقيقي الخاص بها بطريقة يمكنها من العودة إلى معرف المستخدم الفعلي الأصلي: استخدام الدالة setuid() في وجود معرف مستخدم محفوظ، أو استخدام دالة BSD setreuid()، التي كانت قادرة على تبديل معرفي المستخدم الحقيقي والفعلي. التغييرات المضمنة في POSIX.1-2008 توفر آلية جديدة باستخدام seteuid() بالاقتران مع معرف مستخدم محفوظ. وبالتالي، فإن جميع التطبيقات التي تحتوي على آلية seteuid() الجديدة سيكون لديها معرف مستخدم محفوظ لكل عملية، وقد تم تغيير معظم السلوك الذي تتحكم فيه _POSIX_SAVED_IDS ليتفق مع الحالة التي تم فيها تعريف الخيار. الدالة kill() هي استثناء. سيُطلب من مطبقي آلية seteuid() الجديدة عمومًا الحفاظ على التوافق مع الآليات القديمة التي كانت مدعومة سابقًا بواسطة أنظمتهم. ومع ذلك، فإن التوافق مع هذا الاستخدام لـ setreuid() ومع سلوك _POSIX_SAVED_IDS لـ kill() معقد بشكل مؤسف. إذا سمحت آلية ذات معرف مستخدم محفوظ لعملية باستخدام setreuid() لتبديل معرفي المستخدم الحقيقي والفعلي، ولكنها تركت معرف المستخدم المحفوظ دون تغيير، فسيكون للعملية بعد ذلك معرف مستخدم فعلي يساوي معرف المستخدم الحقيقي الأصلي، وسيكون كل من معرف المستخدم الحقيقي والمحفوظ يساوي معرف المستخدم الفعلي الأصلي. في تلك الحالة، لن يتمكن المستخدم الحقيقي من إنهاء العملية، على الرغم من أن معرف المستخدم الفعلي للعملية يتطابق مع معرف المستخدم الحقيقي، إذا تم استخدام سلوك kill() الخاص بـ _POSIX_SAVED_IDS. هذا غير مقبول بشكل واضح. الخيار البديل، المستخدم في تطبيق واحد على الأقل، هو تغيير معرف المستخدم المحفوظ إلى معرف المستخدم الفعلي أثناء معظم استدعاءات setreuid(). اعتبر مطورو المعيار أن هذا البديل أقل صحة من الاحتفاظ بالسلوك القديم لـ kill() في مثل هذه الأنظمة. يجب أن تتكيف التطبيقات المتوافقة الحالية مع أي من السلوكين من kill()، ويبدو أنه لا يوجد سبب قوي لـ kill() للتحقق من معرف المستخدم المحفوظ.

NAME

setuid - set user identity

SYNOPSIS

#include <unistd.h>

int setuid(uid_t uid);

DESCRIPTION

The setuid() function sets the effective user ID of the calling process to uid.

This is a powerful operation. It may only be performed by a privileged process (typically, one running as root). A process may not increase its privilege level by calling setuid().

If the effective user ID of the calling process is root, then the real user ID and the saved set-user-ID are also set to uid. A non-privileged process may execute setuid() to drop its normal privileges.

If the calling process is not privileged, the setuid() call will only succeed if uid is equal to the real user ID or the effective user ID of the calling process.

The value of uid is a user ID. POSIX.1 defines that on success, setuid() sets the real user ID, effective user ID, and saved set-user-ID to the value of uid. It also sets the group IDs to match the new user ID. The `setlogin()` system call is also performed to set the login name associated with the process.

A process may change its effective user ID without changing its real user ID or saved set-user-ID only by using the seteuid() system call.

RETURN VALUE

On success, zero is returned.

On error, -1 is returned, and errno is set to indicate the error.

ERRORS

EPERM
The effective user ID of the calling process is not root, and uid is not equal to the real user ID or the effective user ID of the calling process.

EINVAL
The value of uid is invalid.

EXAMPLES

Set the effective user ID to 500:

uid_t new_uid = 500;
int result;

result = setuid(new_uid);
if (result == -1) {
    perror("setuid");
    exit(EXIT_FAILURE);
}

APPLICATION USAGE

Because setuid() also changes the real user ID and saved set-user-ID, it is a much more drastic operation than seteuid(). It is primarily used by daemons or other privileged programs that need to drop all privileges to run as a specific user.

If you need to temporarily drop privileges to perform a specific task and then regain them, you should use seteuid().

RATIONALE

The setuid() function is part of the POSIX standard, and provides a way for a process to change its user ID. It is a fundamental security mechanism in Unix-like operating systems.

The behavior of setuid() on Linux is consistent with the POSIX standard. Specifically, when a privileged process calls setuid(), it sets the real user ID, effective user ID, and saved set-user-ID to the new UID. Non-privileged processes can only set their effective UID to their real UID or saved set-UID.
