الاسم

slapd-mdb - الواجهة الخلفية لقاعدة بيانات MDB في slapd

الملخص

/etc/openldap/slapd.conf

الوصف

تستخدم الواجهة الخلفية mdb لـ slapd(8) مكتبة OpenLDAP Lightning Memory-Mapped DB (LMDB) لتخزين البيانات. تعتمد بشكل كامل على نظام التشغيل الأساسي لإدارة الذاكرة ولا تقوم بالتخزين المؤقت الخاص بها. إنها الواجهة الخلفية الموصى بها لقاعدة البيانات الأساسية.

تدعم الواجهة الخلفية mdb تخطيط قاعدة بيانات هرمي يدعم إعادة تسمية الأفرع.

الإعداد

تنطبق خيارات slapd.conf هذه على الواجهة الخلفية mdb. أي أنها يجب أن تتبع سطر "backend mdb" وتأتي قبل أي أسطر "backend" أو "database" لاحقة.

idlexp <exp>
حدد قوة 2 للحد الأقصى لحجم خانة الفهرس. الافتراضي هو 16، مما ينتج عنه حجم خانة أقصى قدره 2^16 أو 65536. بمجرد تحديده، ينطبق هذا الخيار على كل مثيل لقاعدة بيانات mdb. يجب أن تكون القيمة المحددة في النطاق من 16 إلى 30.

تنطبق خيارات slapd.conf هذه على قاعدة بيانات الواجهة الخلفية mdb. أي أنها يجب أن تتبع سطر "database mdb" وتأتي قبل أي أسطر "backend" أو "database" لاحقة. توجد خيارات قاعدة بيانات أخرى موصوفة في صفحة دليل slapd.conf(5).

checkpoint <kbyte> <min>
حدد تكرار مسح مخازن مؤقت لقاعدة البيانات على القرص. هذا الإعداد مطلوب فقط إذا تم استخدام خيار dbnosync. سيحدث الفحص إذا تم كتابة بيانات <kbyte> أو مرت <min> دقيقة منذ آخر فحص. كلا الوسيطين افتراضيان إلى صفر، وفي هذه الحالة يتم تجاهلهما. عندما يكون الوسيط <min> غير صفري، سيتم تشغيل مهمة داخلية كل <min> دقيقة لإجراء الفحص. ملاحظة: حاليًا، لم يتم تنفيذ الإعداد <kbyte>.
dbnosync
حدد أنه لا يجب مزامنة محتويات قاعدة البيانات على القرص فورًا مع التغييرات في الذاكرة. قد يؤدي تمكين هذا الخيار إلى تحسين الأداء على حساب أمان البيانات. على وجه الخصوص، إذا تعطل نظام التشغيل قبل مسح التغييرات، فقد تفقد بعض المعاملات. بشكل افتراضي، يتم إجراء مسح/مزامنة بيانات كاملة عند تأكيد كل معاملة.
directory <directory>
حدد الدليل الذي توجد فيه ملفات LMDB التي تحتوي على قاعدة البيانات هذه والفهارس المرتبطة بها. يجب تحديد دليل منفصل لكل قاعدة بيانات. الافتراضي هو /var/lib/openldap/openldap-data.
envflags {nosync,nometasync,writemap,mapasync,nordahead}
حدد علامات للتحكم الدقيق في عملية مكتبة LMDB.
nosync
هذا هو نفس توجيه dbnosync تمامًا.
nometasync
مسح البيانات عند التأكيد، ولكن تخطي مزامنة الصفحة الوصفية. هذا الوضع أسرع قليلاً من إجراء مزامنة كاملة، ولكنه قد يؤدي إلى فقدان آخر معاملة مؤكدة إذا تعطل نظام التشغيل. إذا تم تعيين كل من nometasync و nosync، فإن علامة nosync لها الأسبقية.
writemap
استخدم خريطة ذاكرة قابلة للكتابة بدلاً من قراءة فقط. هذا يسرع عمليات الكتابة ولكنه يجعل قاعدة البيانات عرضة للتلف في حالة تسبب أي أخطاء في slapd في كتابات عشوائية في منطقة الذاكرة الخرائط.
mapasync
عند استخدام خريطة ذاكرة قابلة للكتابة وإجراء عمليات مسح عند كل تأكيد، استخدم مسحًا غير متزامن بدلاً من مسح متزامن (الافتراضي). لا يكون لهذا الخيار أي تأثير إذا لم يتم تعيين writemap. كما أنه ليس له أي تأثير إذا تم تعيين nosync.
nordahead
إيقاف قراءة الذاكرة المسبقة للملف. عادةً ما يقوم نظام التشغيل بقراءة الذاكرة المسبقة لكل طلب قراءة. هذا يعزز عادةً أداء القراءة ولكنه قد يكون ضارًا بأداء قراءة الوصول العشوائي إذا كانت ذاكرة النظام ممتلئة وقاعدة البيانات أكبر من ذاكرة الوصول العشوائي. هذا الخيار غير مطبق على Windows.
index {<attrlist>|default} [pres,eq,approx,sub,<special>]
حدد الفهارس المراد صيانتها للسمة (أو قائمة السمات) المحددة. تدعم بعض السمات مجموعة فرعية فقط من الفهارس. إذا تم توفير <attr> فقط، يتم الاحتفاظ بالفهارس المحددة لـ default. لاحظ أن تحديد افتراضي لا يعني أن جميع السمات سيتم فهرستها. أيضًا، للحصول على أفضل أداء، يجب دائمًا تكوين فهرس eq لسمة objectClass.

يمكن تحديد عدد من معلمات الفهرس الخاصة. يمكن تقسيم نوع الفهرس sub إلى فهارس subinitial و subany و subfinal. يمكن تحديد النوع الخاص nolang لمنع استخدام هذا الفهرس بواسطة الأنواع الفرعية اللغوية. يمكن تحديد النوع الخاص nosubtypes لمنع استخدام هذا الفهرس بواسطة الأنواع الفرعية المسماة. ملاحظة: يتطلب تغيير إعدادات index في slapd.conf(5) إعادة بناء الفهارس، راجع slapindex(8)؛ تغيير إعدادات index ديناميكيًا عن طريق تعديل LDAP لـ "cn=config" يتسبب تلقائيًا في إعادة بناء الفهارس عبر الإنترنت في مهمة خلفية.

maxentrysize <bytes>
حدد الحد الأقصى لحجم الإدخال بالبايت. سيتم رفض محاولات تخزين إدخال أكبر من هذا الحجم مع الخطأ LDAP_ADMINLIMIT_EXCEEDED. الافتراضي هو 0، وهو غير محدود.
maxreaders <integer>
حدد الحد الأقصى لعدد الخيوط التي قد يكون لديها وصول قراءة متزامن إلى قاعدة البيانات. الأدوات مثل slapcat تُحسب كخيط واحد، بالإضافة إلى الخيوط في أي عمليات slapd نشطة. الافتراضي هو 126.
maxsize <bytes>
حدد الحد الأقصى لحجم قاعدة البيانات بالبايت. يتم تخصيص خريطة ذاكرة بهذا الحجم عند بدء التشغيل ولن يُسمح لقاعدة البيانات بالنمو بما يتجاوز هذا الحجم. الافتراضي هو 10485760 بايت. يمكن تغيير هذا الإعداد للأعلى إذا احتاج الحد المكون إلى زيادة.

ملاحظة: من المهم تعيين هذا إلى أكبر قيمة ممكنة (بالنسبة للنمو المتوقع للبيانات الفعلية بمرور الوقت) نظرًا لأن زيادة الحجم لاحقًا قد لا تكون عملية عندما يكون النظام تحت ضغط كبير.

mode <integer>
حدد وضع حماية الملف الذي يجب أن تمتلكه ملفات قاعدة البيانات التي تم إنشاؤها حديثًا. الافتراضي هو 0600.
multival {<attrlist>|default} <integer hi>,<integer lo>
حدد عدد القيم التي يتم تخزينها لسمة متعددة القيم في جدول منفصل. عادةً ما يتم تخزين الإدخالات ككتلة واحدة داخل قاعدة البيانات. عندما يصبح الإدخال كبيرًا جدًا أو يحتوي على سمات ذات عدد كبير جدًا من القيم، قد تصبح التعديلات على هذا الإدخال بطيئة جدًا. يمكن أن يؤدي فصل السمات الكبيرة إلى جدول منفصل إلى تحسين أداء عمليات التعديل. يتم تحديد العتبة كزوج من الأعداد الصحيحة. إذا تجاوز عدد القيم العتبة العالية (hi) فسيتم فصل القيم. إذا أدت عملية تعديل إلى حذف قيم كافية لإعادة سمة أقل من العتبة المنخفضة (lo)، فسيتم إزالة القيم من الجدول المنفصل ودمجها مرة أخرى في كتلة الإدخال الرئيسية. يمكن تعيين العتبة لقائمة محددة من السمات، أو t

slapd-mdb(5)

NAME

slapd-mdb – LMDB backend for slapd

SYNOPSIS

Configuration:
database mdb

DESCRIPTION

The LMDB (Lightning Memory-Mapped Database) backend is a highly efficient, memory-mapped key/value store. It is used as the default backend for slapd(8) since version 2.4.40.

The LMDB backend provides transactional semantics, supporting ACID properties. All modifications to the database are performed within transactions. Read operations may occur outside of a write transaction, but read operations within a write transaction are also protected by it.

LMDB uses memory-mapping to access the database file. This means that the database file is directly mapped into the process's address space. This allows for very fast access to the data, as there is no need for explicit read or write operations between the user process and the operating system kernel. The operating system handles the paging of data in and out of memory as needed.

The LMDB backend stores entries in a sorted manner, allowing for efficient searching and retrieval. It supports multiple indices per attribute, which can further optimize search performance.

CONFIGURATION

The LMDB backend can be configured using the following parameters within the slapd.conf(5) file, or via dynamic configuration.

database mdb
Selects the LMDB backend.
suffix <dn>
The DN under which the entries will be stored. This is typically the domain name of the directory, e.g. "dc=example,dc=com".
directory <path>
The directory where the database files will be stored. This directory must exist and be writable by the slapd(8) process. The default is "/var/lib/ldap".
maxsize <bytes>
Sets the maximum size of the database file. The default is 1073741824 bytes (1 GiB). Setting this to 0 means unlimited size. The size can be increased later, but cannot be decreased. Note that the underlying LMDB library may impose its own limits on the maximum file size depending on the operating system and filesystem.
cachesize <bytes>
Sets the size of the memory map cache used by LMDB. The default is 256 MiB. Increasing this value can improve performance for read-heavy workloads, but may also increase memory usage. The value should be a multiple of the system's page size.
writemode IMMEDIATE|FSYNC|BATCH
Controls how LMDB handles writes to the database.
IMMEDIATE
Each write operation is immediately flushed to disk. This provides the highest level of data durability but may impact performance.
FSYNC
Each write operation is flushed to the operating system's page cache, which is then periodically flushed to disk. This offers a good balance between durability and performance. This is the default.
BATCH
Writes are buffered and flushed to disk in batches. This can significantly improve write performance but reduces data durability in the event of a system crash.
indices <list>
Specifies the attributes for which indices should be created. Indices significantly speed up search operations based on the indexed attributes. The default is to index "cn,description,go,uid".
lockmmap on|off
When enabled (default is off), use mlock() to lock the database into memory. This can prevent the OS from swapping out the database, potentially improving performance but increasing memory usage.
mode <permissions>
Sets the file permissions for the database files. The default is 0600.
mapcachemax <pages>
Sets the maximum number of memory map pages that can be held in the cache. The default is 255.
thrlowater <threshold>
Sets the low water mark for the memory pool, used to reclaim memory. The default can be configured for all other attributes. The default value for both hi and lo thresholds is UINT_MAX, which keeps all attributes in the main blob.
rtxnsize <entries>
Specify the maximum number of entries to process in a single read transaction when executing a large search. Long-lived read transactions prevent old database pages from being reused in write transactions, and so can cause significant growth of the database file when there is heavy write traffic. This setting causes the read transaction in large searches to be released and reacquired after the given number of entries has been read, to give writers the opportunity to reclaim old database pages. The default is 10000.
searchstack <depth>
Specify the depth of the stack used for search filter evaluation. Search filters are evaluated on a stack to accommodate nested AND / OR clauses. An individual stack is assigned to each server thread. The depth of the stack determines how complex a filter can be evaluated without requiring any additional memory allocation. Filters that are nested deeper than the search stack depth will cause a separate stack to be allocated for that particular search operation. These allocations can have a major negative impact on server performance, but specifying too much stack will also consume a great deal of memory. Each search stack uses 512K bytes per level. The default stack depth is 16, thus 8MB per thread is used.

ACCESS CONTROL

The mdb backend honors access control semantics as indicated in slapd.access(5).

default slapd configuration file
