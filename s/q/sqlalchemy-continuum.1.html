الاسم

sqlalchemy-continuum - وثائق SQLAlchemy-Continuum

SQLAlchemy-Continuum هو امتداد لتتبع الإصدارات لـ SQLAlchemy.

مقدمة

لماذا؟

كمتحمس لـ Python/SQLAlchemy، أردت إنشاء أداة لتتبع إصدارات قاعدة البيانات لـ Python مع جميع ميزات Envers وبواجهة برمجة تطبيقات بديهية مثل papertrail. كما أردت أن أجعلها _سريعة_ مع إبقاء الأشياء قريبة قدر الإمكان من قاعدة البيانات.

الميزات

  • لا يقوم بتخزين التحديثات التي لا تغير شيئًا
  • يدعم ترحيلات alembic
  • يمكنه التراجع عن بيانات الكائنات وكذلك جميع علاقات الكائنات في معاملة معينة حتى لو تم حذف الكائن
  • يمكن الاستعلام عن المعاملات لاحقًا باستخدام صيغة استعلام SQLAlchemy
  • الاستعلام عن السجلات التي تم تغييرها في معاملة معينة
  • الاستعلام عن إصدارات الكيان التي تم تعديل خاصية معينة
  • الاستعلام عن المعاملات التي تغيرت فيها كيانات فئة معينة
  • توفر نماذج السجل وصولاً إلى علاقات الكائنات الأصلية في أي وقت معين

التثبيت

pip install SQLAlchemy-Continuum

الأساسيات

لجعل نماذجك قابلة لتتبع الإصدارات، تحتاج إلى شيئين:

1.
استدعاء make_versioned() قبل تعريف نماذجك.
2.
إضافة __versioned__ إلى جميع النماذج التي ترغب في إضافة تتبع الإصدارات إليها
import sqlalchemy as sa
from sqlalchemy_continuum import make_versioned
make_versioned(user_cls=None)
class Article(Base):
    __versioned__ = {}
    __tablename__ = 'article'
    id = sa.Column(sa.Integer, primary_key=True, autoincrement=True)
    name = sa.Column(sa.Unicode(255))
    content = sa.Column(sa.UnicodeText)
# بعد تعريف جميع نماذجك، قم باستدعاء configure_mappers():
sa.orm.configure_mappers()

بعد هذا الإعداد، يقوم SQLAlchemy-Continuum بما يلي:

1.
يقوم بإنشاء نموذج ArticleHistory الذي يعمل كسجل تاريخي لنموذج Article
2.
يقوم بإنشاء نماذج TransactionLog و TransactionChanges لتتبع تاريخ المعاملات
3.
يقوم بإضافة بعض المستمعين بحيث يتم تسجيل كل إدراج وتحديث وحذف لكائن Article

عندما يتم تكوين النماذج إما عن طريق استدعاء configure_mappers() أو عن طريق الوصول إلى بعضها للمرة الأولى، تصبح الأشياء التالية متاحة:

from sqlalchemy_continuum import version_class, parent_class
version_class(Article)  # فئة ArticleHistory
parent_class(version_class(Article))  # فئة Article

الإصدارات والمعاملات

في نهاية كل معاملة، يقوم SQLAlchemy-Continuum بتجميع كافة التغييرات معًا ويقوم بإنشاء كائنات إصدار لكل كيان إصدار تم تغييره. يقوم Continuum أيضًا بإنشاء كيان TransactionLog واحد و N من كيانات TransactionChanges لكل معاملة (هنا N هو عدد الفئات المتأثرة لكل معاملة). يتم إنشاء كيانات TransactionLog و TransactionChanges لتتبع المعاملات.

article = Article(name=u'Some article')
session.add(article)
session.commit()
article.versions[0].name == u'Some article'
article.name = u'Some updated article'
session.commit()
article.versions[1].name == u'Some updated article'

كائنات الإصدار

أنواع العمليات

عند تغيير الكيانات وتثبيت النتائج في قاعدة البيانات، يقوم Continuum بحفظ العمليات المستخدمة (INSERT، UPDATE، أو DELETE) في كائنات الإصدار. يتم تخزين أنواع العمليات افتراضيًا في حقل عدد صحيح صغير يسمى 'operation_type'. الفئة المسماة 'Operation' تحتفظ بثوابت مفيدة لهذه القيم كما هو موضح أدناه:

from sqlalchemy_continuum import Operation
article = Article(name=u'Some article')
session.add(article)
session.commit()
article.versions[0].operation_type == Operation.INSERT
article.name = u'Some updated article'
session.commit()
article.versions[1].operation_type == Operation.UPDATE
session.delete(article)
session.commit()
article.versions[2].operation_type == Operation.DELETE

اجتياز الإصدار

first_version = article.versions[0]
first_version.index
# 0
second_version = first_version.next
assert second_version == article.versions[1]
second_version.previous == first_version
# True
second_version.index
# 1

مجموعة التغييرات

يوفر Continuum طريقة سهلة للحصول على مجموعة التغييرات لكائن إصدار معين. يحتوي كل كائن إصدار على خاصية changeset التي تحتفظ بقاموس للحقول التي تم تغييرها في هذا الإصدار.

article = Article(name=u'New article', content=u'Some content')
session.add(article)
session.commit(article)
version = article.versions[0]
version.changeset
# {
#   'id': [None, 1],
#   'name': [None, u'New article'],
#   'content': [None, u'Some content']
# }
article.name = u'Updated article'
session.commit()
version = article.versions[1]
version.changeset
# {
#   'name': [u'New article', u'Updated article'],
# }
session.delete(article)
version = article.versions[2]
version.changeset
# {
#   'id': [1, None]
#   'name': [u'Updated article', None],
#   'content': [u'Some content', None]
# }

يوفر SQLAlchemy-Continuum أيضًا وظيفة مساعدة تسمى changeset. باستخدام هذه الوظيفة، يمكنك بسهولة التحقق من مجموعة التغييرات لكائن معين في المعاملة الحالية.

from sqlalchemy_continuum import changeset
article = Article(name=u'Some article')
changeset(article)
# {'name': [None, u'Some article']}

علاقات الإصدار

يعكس كل كائن إصدار جميع علاقات الكائنات الأصلية. يمكنك التفكير في علاقات كائن الإصدار على أنها "علاقات الكائن الأصل في نقطة زمنية معينة".

لنفترض أن لديك نموذجين: Article و Category. كل Article لديه فئة واحدة. في المثال التالي، نقوم أولاً بإضافة كائنات Article و Category إلى قاعدة البيانات.

يقوم Continuum بحفظ سجلات ArticleVersion و CategoryVersion جديدة في الخلفية. بعد ذلك، نقوم بتحديث كيان المقالة الذي تم إنشاؤه لاستخدام فئة أخرى. يقوم Continuum بإنشاء كائنات إصدار جديدة وفقًا لذلك.

أخيرًا، نتحقق من علاقات الفئة لإصدارات المقالات المختلفة.

category = Category(name=u'Some category')
article = Article(
    name=u'Some article',
    category=category
)
session.add(article)
session.commit()
article.category = Category(name=u'Some other category')
session.commit()
article.versions[0].category.name  # u'Some category'
article.versions[1].category.name  # u'Some other category'

يتم تضمين المنطق حول كيفية بناء SQLAlchemy-Continuum لهذه العلاقات داخل الفئة RelationshipBuilder.

العلاقات مع الفئات غير القابلة لتتبع الإصدارات

لنتخيل المثال السابق للمقالات والفئات. الآن، لنفترض أن نموذج المقالة فقط هو الذي يتم تتبع إصداراته:

>
  • أسرع بكثير من الإصدارات العادية المستندة إلى الكائنات
  • الحد الأدنى من استخدام الذاكرة عند استخدامه مع خيارات التهيئة create_tables=False و create_models=False.
  • ترحيل قواعد البيانات أكثر تعقيدًا، حيث يجب تحديث المشغلات أيضًا.

الاستخدام

لتمكين الإصدار الأصلي، تحتاج إلى تعيين خيار التهيئة native_versioning إلى True.

make_versioned(options={'native_versioning': True})

ترحيلات المخطط

عند إجراء ترحيلات للمخطط (على سبيل المثال، إضافة أعمدة جديدة إلى جداول الإصدارات)، تحتاج إلى تذكر استدعاء sync_trigger للحفاظ على تحديث مشغل الإصدار.

from sqlalchemy_continuum.dialects.postgresql import sync_trigger
sync_trigger(conn, 'article_version')

إذا كنت لا تستخدم PropertyModTrackerPlugin، فيجب عليك تعطيله:

sync_trigger(conn, 'article_version', use_property_mod_tracking=False)

الإضافات

استخدام الإضافات

from sqlalchemy_continuum.plugins import PropertyModTrackerPlugin
versioning_manager.plugins.append(PropertyModTrackerPlugin())
versioning_manager.plugins  # <PluginCollection [...]>
# يمكنك أيضًا إزالة إضافة
del versioning_manager.plugins[0]

النشاط

ActivityPlugin هي الإضافة الأكثر قوة لتتبع التغييرات في الكيانات الفردية. إذا كنت تستخدم ActivityPlugin، فمن المحتمل أنك لن تحتاج إلى استخدام TransactionChanges أو TransactionMeta plugins.

يمكنك تهيئة ActivityPlugin عن طريق إضافتها إلى مدير الإصدارات.

العمود النوع الوصف
id BigInteger المفتاح الأساسي للنشاط
verb Unicode يحدد الفعل إجراء النشاط
data JSON بيانات إضافية للنشاط بتنسيق JSON
transaction_id BigInteger المعاملة التي ارتبط بها هذا النشاط
object_id BigInteger المفتاح الأساسي للكائن. يمكن أن يكون الكائن أي كيان له مفتاح أساسي صحيح.
object_type Unicode نوع الكائن (اسم الفئة كسلسلة نصية)
object_tx_id BigInteger آخر transaction_id مرتبط بالكائن. يستخدم لجلب إصدار الكائن المرتبط بهذا النشاط بكفاءة.
target_id BigInteger المفتاح الأساسي للهدف. يمكن أن يكون الهدف أي كيان له مفتاح أساسي صحيح.
target_type Unicode نوع الهدف (اسم الفئة كسلسلة نصية)
target_tx_id BigInteger آخر transaction_id مرتبط بالهدف.

القيود

حاليًا، يجب تأكيد أو تثبيت جميع التغييرات على النماذج الأصل قبل إنشاء الأنشطة. هذا يرجع إلى حقيقة أنه لا تزال هناك معالجات تبعية للعلاقات العامة. لذا، عند إنشاء الأنشطة وتعيين الكائنات / الأهداف لتلك الأنشطة، يرجى تذكر تأكيد الجلسة قبل إنشاء نشاط:

article = Article(name=u'Some article')
session.add(article)
session.flush()  # <- هام!
first_activity = Activity(verb=u'create', object=article)
session.add(first_activity)
session.commit()

يجب أن تحتوي الأهداف والكائنات لنشاط معين على عمود مفتاح أساسي صحيح id.

إنشاء الأنشطة

بمجرد تكوين نماذجك، يمكنك الحصول على نموذج النشاط من خاصية activity_cls في الفئة ActivityPlugin:

Activity = activity_plugin.activity_cls

الآن، لنفترض أن لدينا نموذجًا يسمى Article و Category. لكل Article فئة واحدة. يجب إنشاء الأنشطة جنبًا إلى جنب مع التغييرات التي تجريها على هذه النماذج.

article = Article(name=u'Some article')
session.add(article)
session.flush()
first_activity = Activity(verb=u'create', object=article)
session.add(first_activity)
session.commit()

يتم تعيين المعاملة الحالية تلقائيًا لكائن النشاط:

first_activity.transaction  # Transaction object

تحديث الأنشطة

يحتوي خاصية object لكائن Activity على الكائن الحالي، وتحتوي خاصية object_version على إصدار الكائن في الوقت الذي تم فيه إنشاء النشاط.

article.name = u'Some article updated!'
session.flush()
second_activity = Activity(verb=u'update', object=article)
session.add(second_activity)
session.commit()
second_activity.object.name  # u'Some article updated!'
first_activity.object.name  # u'Some article updated!'
first_activity.object_version.name  # u'Some article'

حذف الأنشطة

تكون خصائص الإصدار مفيدة بشكل خاص لأنشطة الحذف. بمجرد جلب النشاط من قاعدة البيانات، لن يكون الكائن متاحًا بعد الآن (لأنه محذوف)، وبالتالي فإن الطريقة الوحيدة لعرض بعض المعلومات حول الكائن الذي حذفها المستخدم هي الوصول إلى خاصية object_version.

session.delete(article)
session.flush()
third_activity = Activity(verb=u'delete', object=article)
session.add(third_activity)
session.commit()
third_activity.object_version.name  # u'Some article updated!'

سجلات الإصدارات المحلية باستخدام الأهداف

توفر خاصية target لكائن Activity طريقة لتتبع التغييرات في كائن مرتبط معين. في المثال أدناه، ننشئ نشاطًا جديدًا عند إضافة فئة للمقالة ثم نحدد المقالة كهدف لهذا النشاط.

session.add(Category(name=u'Fist category', article=article))
session.flush()
activity = Activity(
    verb=u'create',
    object=category,
    target=article
)
session.add(activity)
session.commit()

الآن، إذا أردنا العثور على جميع التغييرات التي أثرت على مقالة معينة، فيمكننا القيام بذلك عن طريق البحث في جميع الأنشطة حيث يكون الكائن أو الهدف هو المقالة المعطاة.

import sqlalchemy as sa
activities = session.query(Activity).filter(
    sa.or_(
        Activity.object == article,
        Activity.target == article
    )
)

Flask

يوفر FlaskPlugin طريقة لدمج إطار عمل Flask مع SQLAlchemy-Continuum. تضيف Flask-Plugin عمودين إلى نموذج Transaction، وهما user_id و remote_addr.

يتم ملء هذين العمودين تلقائيًا عند إنشاء كائن المعاملة. يتم ملء العمود remote_addr بقيمة العنوان البعيد الذي قام بالطلب الحالي. يتم ملء العمود user_id بمعرف الكائن current_user.

from sqlalchemy_continuum.plugins import FlaskPlugin
from sqlalchemy_continuum import make_versioned
make_versioned(plugins=[FlaskPlugin()])

PropertyModTracker

توفر PropertyModTrackerPlugin طريقة لتتبع تعديلات الخصائص الفردية بكفاءة. مع PropertyModTrackerPlugin، يمكنك إجراء استعلامات فعالة مثل:

ابحث عن جميع إصدارات النموذج X حيث قام المستخدم بتحديث الخاصية A أو الخاصية B.

ابحث عن جميع إصدارات النموذج X حيث لم يقم المستخدم بتحديث الخاصية أ.

يضيف مكون PropertyModTrackerPlugin عمود تتبع تعديل منفصل لكل عمود محسوب. على سبيل المثال، إذا كان لديك نموذج محسوب يسمى Article مع أعمدة name و content، فإن هذا المكون يضيف عمودين إضافيين منطقيين name_mod و content_mod للنموذج المحسوب. عندما يقوم المستخدم بتأكيد المعاملات، يقوم المكون تلقائيًا بتحديث هذه الأعمدة المنطقية.

TransactionChanges

يوفر TransactionChanges طريقة لتتبع النماذج التعريفية التي تم تغييرها بكفاءة في معاملة معينة. يمكن أن يكون هذا مفيدًا عندما تحتاج المعاملات إلى الاستعلام عنها لاحقًا لمشاكل مثل:

1.
ابحث عن جميع المعاملات التي أثرت على نموذج User.
2.
ابحث عن جميع المعاملات التي لم تؤثر على نماذج Entity و Event.

يعمل المكون بطريقتين. في مرحلة تجهيز الفئة، ينشئ هذا المكون نموذج معاملة خاص يسمى TransactionChanges. يرتبط هذا النموذج بجدول يسمى transaction_changes، والذي يحتوي على حقلين فقط: transaction_id و entity_name. على سبيل المثال، إذا كانت المعاملة تتكون من حفظ 5 كيانات مستخدم جديدة وكيان مقال واحد، فسيتم إدراج صفين جديدين في جدول transaction_changes.

transaction_id entity_name
233678 User
233678 Article

TransactionMeta

يوفر مكون TransactionMetaPlugin طريقة لحفظ بيانات المفتاح والقيمة للمعاملات. يمكنك استخدام المكون بنفس طريقة المكونات الأخرى:

meta_plugin = TransactionMetaPlugin()
versioning_manager.plugins.append(meta_plugin)

ينشئ مكون TransactionMetaPlugin نموذجًا بسيطًا يسمى TransactionMeta. يحتوي هذا الفصل على ثلاثة أعمدة: transaction_id، key، و value. كما ينشئ مكون TransactionMeta Plugin وكيل ارتباط بين فئتي TransactionMeta و Transaction للوصول السهل المستند إلى القاموس إلى أزواج المفاتيح والقيم.

يمكنك بسهولة "وضع علامات" على المعاملات بأزواج مفاتيح وقيم معينة عن طريق إعطاء هذه المفاتيح والقيم للخاصية meta لفئة Transaction.

from sqlalchemy_continuum import versioning_manager
article = Article()
session.add(article)
uow = versioning_manager.unit_of_work(session)
tx = uow.create_transaction(session)
tx.meta = {u'some_key': u'some value'}
session.commit()
TransactionMeta = meta_plugin.model_class
Transaction = versioning_manager.transaction_cls
# البحث عن جميع المعاملات ذات علامات "article"
query = (
    session.query(Transaction)
    .join(Transaction.meta_relation)
    .filter(
        db.and_(
            TransactionMeta.key == 'some_key',
            TransactionMeta.value == 'some value'
        )
    )
)

التكوين

التكوين على مستوى عام وعلى مستوى الفصل

يمكن تعيين جميع معلمات تكوين Continuum على المستوى العام (مستوى المدير) وعلى مستوى الفصل. يؤثر تعيين خيار على مستوى المدير على جميع الفئات ضمن نطاق مستمع تجهيز الفئة للمدير (بشكل افتراضي، جميع نماذج SQLAlchemy التعريفية).

في المثال التالي، نقوم بتعيين خيار التكوين 'transaction_column_name' إلى False على مستوى المدير.

make_versioned(options={'transaction_column_name': 'my_tx_id'})

كما يوحي الاسم، ينطبق التكوين على مستوى الفصل فقط على الفصل المحدد. يمكن تمرير التكوين على مستوى الفصل إلى سمة الفئة __versioned__.

class User(Base):
    __versioned__ = {
        'transaction_column_name': 'tx_id'
    }

استراتيجيات الحساب

على غرار Hibernate Envers، تقدم SQLAlchemy-Continuum استراتيجيتين حسابيتين مميزتين: "validity" و "subquery". الاستراتيجية الافتراضية هي "validity".

الصلاحية

تحفظ استراتيجية "validity" عمودين في كل جدول تاريخ، وهما 'transaction_id' و 'end_transaction_id'. يمكن تكوين أسماء هذه الأعمدة باستخدام خيارات التكوين transaction_column_name و end_transaction_column_name.

كما هو الحال مع استراتيجية 'subquery'، لكل كيان تم إدراجه أو تحديثه أو حذفه، يقوم Continuum بإنشاء نسخة جديدة في جدول التاريخ. ومع ذلك، فإنه يقوم أيضًا بتحديث end_transaction_id للنسخة السابقة للإشارة إلى النسخة الحالية. هذا يخلق القليل من الحمل الزائد أثناء معالجة البيانات.

مع استراتيجية "validity"، يكون اجتياز الإصدارات سريعًا جدًا. عند الوصول إلى نسخة سابقة، يحاول Continuum العثور على سجل النسخة حيث تتطابق المفاتيح الأساسية ويكون end_transaction_id هو نفسه transaction_id لسجل النسخة المحدد. عند الوصول إلى النسخة التالية، يحاول Continuum العثور على سجل النسخة حيث تتطابق المفاتيح الأساسية ويكون transaction_id هو نفسه end_transaction_id لسجل النسخة المحدد.

استعلام فرعي

تستخدم استراتيجية "subquery" عمودًا واحدًا في كل جدول تاريخ، وهو 'transaction_id'. يمكن تكوين اسم هذا العمود باستخدام خيار التكوين transaction_column_name.

بعد كل كيان تم إدراجه أو تحديثه أو حذفه، يقوم Continuum بإنشاء نسخة جديدة في جدول التاريخ وتعيين عمود 'transaction_id' للإشارة إلى المعاملة الحالية.

مع استراتيجية "subquery"، يكون اجتياز الإصدارات بطيئًا. عند الوصول إلى الإصدارات السابقة والتالية لكائن إصدار معين، يلزم وجود استعلامات فرعية مترابطة.

الايجابيات:
•
التحديثات والإدخالات والحذف أسرع قليلاً من استراتيجية "validity"
السلبيات:
•
اجتياز الإصدارات أبطأ بكثير

استبعاد وتضمين الأعمدة

باستخدام خيار التكوين exclude، يمكنك تحديد سمات الكيان التي تريد حسابها. افتراضيًا، يقوم Continuum بحساب جميع سمات الكيان.

class User(Base):
    __versioned__ = {
        'exclude': ['picture']
    }
    id = sa.Column(sa.Integer, primary_key=True)
    name = sa.Column(sa.Unicode(255))
    picture = sa.Column(sa.LargeBinary)

خيارات التكوين الأساسية

هذه قائمة كاملة بخيارات التكوين:

•
base_classes (الافتراضي: None)
مجموعة تحدد الفئات الأساسية للتاريخ.
•
table_name (الافتراضي: '%s_version')
اسم جدول التاريخ.
•
transaction_column_name (الافتراضي: 'transaction_id')
اسم عمود المعاملة (المستخدم في جداول التاريخ).
•
end_transaction_column_name (الافتراضي: 'end_transaction_id')
اسم عمود نهاية المعاملة في جدول التاريخ عند استخدام استراتيجية الحساب validity.
•
operation_type_column_name (الافتراضي: 'operation_type')
اسم عمود نوع العملية (المستخدم في جداول التاريخ).
•
strategy (الافتراضي: 'validity')
استراتيجية الحساب المراد استخدامها. إما 'validity' أو 'subquery'

مثال

class Article(Base):
    __versioned__ = {
        'transaction_column_name': 'tx_id'
    }
    __tablename__ = 'user'
    id = sa.Column(sa.Integer, primary_key=True, autoincrement=True)
    name = sa.Column(sa.Unicode(255))
    content = sa.Column(sa.UnicodeText)
