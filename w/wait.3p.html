The interpretation of the status value\n is described below.\n\n If the waitpid() call returns because a child process was terminated\n by a signal, and the WNOHANG option was not specified, the value placed\n in wstatus is the value returned by the terminated child's call to\n exit(2), or 0 if the child terminated normally. A single wait() issued from a SIGCHLD signal handler can be guaran-\n teed to return immediately with status information for a child pro-\n cess.\n\n 3. If the implemen-\n tation supports queued signals, then eventually the system will run\n out of memory for the queue. The guarantee cannot be made because\n there must be some limit to the depth of queuing.\n\n Guarantees #2 and #3\n These cannot be guaranteed unless the wait() family of functions\n accepts the SIGCHLD signal. Otherwise, a fork()/wait() executed\n while SIGCHLD is blocked (as in the system() function) will result\n in an invocation of the handler when SIGCHLD is unblocked, after\n the process has disappeared.\n\n Guarantee #4\n Although possible to make this guarantee, system() would have to set\n the SIGCHLD handler to SIG_DFL so that the SIGCHLD signal generated\n by its fork() would be discarded (the SIGCHLD default action is to\n be ignored), then restore it to its previous setting. NAME

\n

waitpid ‐ wait for a child process to change state

\n
\n
\n

SYNOPSIS

\n

#include <sys/types.h>
#include <sys/wait.h>

\n

pid_t waitpid(pid_t pid, int *wstatus, int options);

\n
\n
\n

DESCRIPTION

\n

The waitpid() call suspends execution of the calling process until a
child of the calling process terminates, or until a signal is delivered
whose action is to invoke a signal-terminating function, or until an
unhandled signal is delivered. If the calling process has no children,
the call returns immediately.

\n

The waitpid() call provides a mechanism to obtain status from and con-
trol the behavior of a child process. The value of the pid argument
can be used to obtain the status of a specific child, or any child,
or any child in a process group.

\n

The options argument is an integer value which is the bitwise-OR of
zero or more of the following constant values:

\n
\n
WNOHANG
\n
Return immediately if no child has called exit(2)
or terminated and the status of the child has not
been requested. Otherwise, wait up to the time
specified by the third argument of waitid().
\n
WUNTRACED
\n
(The default is to query only child processes that have
terminated.) Also return for child processes that have
stopped, and whose status has not been reported.
The status of such children is returned in wstatus.
(WIFSTOPPED will be true of the return status.)
\n
WCONTINUED
\n
(Since Linux 2.8.0 and Linux 3.8.0) Also return if any
child of the calling process specified by pid has
stopped by delivery of a SIGCONT signal.
\n
\n

If pid is equal to (pid_t) -1, then waitpid() waits for any child
process to change state, and the return value is the process ID of
the child which changed state. A child process is one which is
created, directly or indirectly, by the calling process, and which
has not been waited upon by any process so far.

\n

If pid is a positive integer, then waitpid() waits for the child
whose process ID is equal to pid. The return value is the process
ID of the child which changed state.

\n

If pid is equal to (pid_t) 0, then waitpid() waits for any child
process in the same process group as the calling process to change
state. The return value is the process ID of the child which
changed state. A child process is one which is created, directly
or indirectly, by the calling process, and which has not been waitedby any process so far.

\n

If pid is a negative value other than (pid_t) -1, then waitpid() waits
for any child process in the process group whose process group ID
is equal to the absolute value of pid. The return value is the
process ID of the child which changed state.

\n

If the waitpid() call returns because the status of a child process
was requested, then the status of that child is placed in the integer
variable pointed to by wstatus. The interpretation of the status value
is described below.

\n

If the waitpid() call returns because a child process was terminated
by a signal, and the WNOHANG option was not specified, the value placed
in wstatus is the value returned by the terminated child's call to
exit(2), or 0 if the child terminated normally. If the child was
terminated by a signal, then the value placed in wstatus indicates
this.

\n

If WNOHANG is specified in options and no child has terminated or
stopped, then waitpid() returns 0 immediately.

\n

If waitpid() returns a non-zero value, it is the process ID of the
child which terminated or stopped.

\n

If waitpid() returns -1, an error occurred.

\n

If the calling process has set up a SIGCHLD signal handler, then the
signal handler is invoked before waitpid() returns.

\n

The status value placed in wstatus is interpreted by the following macros:

\n
\n
WIFEXITED(wstatus)
\n
True if the child terminated normally, that is, by calling
exit(2) or returning from main().
\n
WEXITSTATUS(wstatus)
\n
If WIFEXITED is true, this returns the exit status
of the child (the value passed to exit(2) or returned by
main()).
\n
WIFSIGNALED(wstatus)
\n
True if the child was terminated by a signal.
\n
WTERMSIG(wstatus)
\n
If WIFSIGNALED is true, this returns the number of the signal
that caused the child to terminate.
\n
WCOREDUMP(wstatus)
\n
True if the child produced a core dump.
\n
WIFSTOPPED(wstatus)
\n
True if the child has stopped because it received a signal.
\n
WSTOPSIG(wstatus)
\n
If WIFSTOPPED is true, this returns the number of the signal
that caused the child to stop.
\n
WIFCONTINUED(wstatus)
\n
(Since Linux 2.8.0 and Linux 3.8.0) True if the child was
stopped by the delivery of a SIGCONT signal.
\n
\n

The macros WIFEXITED, WEXITSTATUS, WIFSIGNALED, WTERMSIG, WCOREDUMP,
WIFSTOPPED, WSTOPSIG, and WIFCONTINUED are defined in <sys/wait.h>.
The behavior is undefined unless wstatus is an integer value that was
stored by a successful call to waitpid() or wait() in the location pointed to by the
stat_loc argument.

\n
\n
\n

RETURN VALUE

\n

On success, waitpid() returns the process ID of the child which has
changed state. If options includes WNOHANG and no child has yet changed
state, then 0 is returned.

\n

On failure, waitpid() returns -1 and sets errno to indicate the error.

\n
\n
\n

ERRORS

\n
\n
ECHILD
\n
The value specified by pid does not correspond to a child of
the calling process.
\n
EINTR
\n
The call was interrupted by a signal other than the ones
specified by the WUNTRACED or WCONTINUED options.
\n
EINVAL
\n
The value of the options argument is not valid.
\n
\n

EXAMPLES

\n

Wait for any child process to terminate:

\n
\n
pid_t child_pid = fork();\nint status;\n\nif (child_pid == 0) { /* child */\n    // ... child code ...\n    exit(0);\n} else if (child_pid > 0) { /* parent */\n    pid_t terminated_pid = waitpid(child_pid, &status, 0);\n    // ... check status ...\n} else {\n    // fork failed\n}\n
\n
\n

Wait for any child process to terminate, but return immediately if
none have:

\n
\n
pid_t pid = waitpid(-1, &status, WNOHANG);\nif (pid == 0) {\n    printf(\"No child has terminated yet.\\n\");\n} else if (pid > 0) {\n    printf(\"Child %d terminated.\\n\", pid);\n    // ... check status ...\n} else {\n    // waitpid failed\n}\n
\n

APPLICATION USAGE

\n

The waitpid() function is used by a parent process to obtain status
information about a child process that has terminated or stopped. The
default behavior is to block until a child process terminates. This can
be modified with the WNOHANG and WUNTRACED options.

\n

The WUNTRACED flag is used only in conjunction with job control on sys-
tems supporting job control. Its name comes from 4.3 BSD and refers to
the fact that there are two types of stopped processes in that imple-
mentation: processes being traced via the ptrace() debugging facility
and (untraced) processes stopped by job control signals. Since ptrace()
is not part of this volume of POSIX.1‐2017, only the second type is rel-
evant. The name WUNTRACED was retained because its usage is the same,
even though the name is not intuitively meaningful in this context.

\n

The third reason for the waitpid() function is to permit independent sec-
tions of a process to spawn and wait for children without interfering
with each other. For example, the following problem occurs in devel-
oping a portable shell, or command interpreter:

\n
\n
stream = popen("/bin/true");\n(void) system("sleep 100");\n(void) pclose(stream);
\n
\n

On all historical implementations, the final pclose() fails to reap the
wait() status of the popen().

\n

The status values are retrieved by macros, rather than given as specific
bit encodings as they are in most historical implementations (and thus
expected by existing programs). This was necessary to eliminate a limi-
tation on the number of signals an implementation can support that was
inherent in the traditional encodings. This volume of POSIX.1‐2017
does require that a status value of zero corresponds to a process
calling _exit(0), as this is the most common encoding expected by
existing programs. Some of the macro names were adopted from 4.3 BSD.

\n

These macros syntactically operate on an arbitrary integer value. The
behavior is undefined unless that value is one stored by a successful
call to wait() or waitpid() in the location pointed to by the
stat_loc argument. An early proposal attempted to make this clearer by specifying
each argument as *stat_loc rather than stat_val. However, that did not
follow the conventions of other specifications in this volume of
POSIX.1‐2017 or traditional usage. It also could have implied that the
argument to the macro must literally be *stat_loc; in fact, that value
can be stored or passed as an argument to other functions before being
interpreted by these macros.

\n

The extension that affects wait() and waitpid() and is common in his-
torical implementations is the ptrace() function. It is called by a
child process and causes that child to stop and return a status that
appears identical to the status indicated by WIFSTOPPED. The status of
ptrace() children is traditionally returned regardless of the WUNTRACED
flag (or by the wait() function). Most applications do not need to con-
cern themselves with such extensions because they have control over
what extensions they or their children use. However, applications, suchcommand interpreters, that invoke arbitrary processes may see this
behavior when those arbitrary processes misuse such extensions.

\n

Implementations that support core file creation or other implemen-
tation-defined actions on termination of some processes traditionally
provide a bit in the status returned by wait() to indicate that such
actions have occurred.

\n

Allowing the wait() family of functions to discard a
pending SIGCHLD signal that is associated with a successfully waited-for child process
puts them into the sigwait() and sigwaitinfo()
category with respect to SIGCHLD.

\n

This definition allows implementations to treat a pending SIGCHLD sig-
nal as accepted by the process in wait(), with the same meaning of
\"accepted\" as when that word is applied to the sigwait() family of
functions.

\n

Allowing the wait() family of functions to behave this way permits an
implementation to be able to deal precisely with SIGCHLD signals.

\n

In particular, an implementation that does accept (discard) the SIGCHLD
signal can make the following guarantees regardless of the queuing depth
of signals in general (the list of waitable children can hold the SIGCHLD
queue):

\n
\n
1.
\n
If a SIGCHLD signal handler is established via sigaction() without
the SA_RESETHAND flag, SIGCHLD signals can be accurately counted; that
is, exactly one SIGCHLD signal will be delivered to or accepted by the process
for every child process that terminates.
\n
2.
\n
A single wait() issued from a SIGCHLD signal handler can be
guaranteed to return immediately with status information for a child pro-
cess.
\n
3.
\n
When SA_SIGINFO is requested, the SIGCHLD signal handler can be guaranteed
to receive a non-null pointer to a siginfo_t structure that
describes a child process for which a wait via waitpid() or
waitid() will not block or fail.
\n
4.
\n
The system() function will not cause the SIGCHLD handler of a pro-
cess to be called as a result of the fork()/exec() executed
within system() because system() will accept the SIGCHLD signal when it
performs a waitpid() for its child process. This is a desirable
behavior of system() so that it can be used in a library without
causing side-effects to the application linked with the library.
\n
\n

An implementation that does not permit the wait() family of functions to
accept (discard) a pending SIGCHLD signal associated with a
successfully waited-for child, cannot make the guarantees described above for
the following reasons:

\n
\n
Guarantee
#1
\n
\n
Although it might be assumed that reliable queuing of all SIGCHLD signals
generated by the system can make this guarantee, the counter-example is
the case of a process that blocks SIGCHLD and performs an indefinite loop
of fork()/wait() operations. If the implementation supports queued signals, then eventually the system will run out of memory for the queue. The guarantee cannot be made because there must be some limit to the depth of queuing.
\n
Guarantees #2 and
#3
\n
\n
These cannot be guaranteed unless the wait() family of functions
accepts the SIGCHLD signal. Otherwise, a fork()/wait() executed while SIGCHLD is blocked (as in the system() function) will result in an invocation of the handler when SIGCHLD is unblocked, after the process has disappeared.
\n
Guarantee
#4
\n
\n
Although possible to make this guarantee, system() would have to set the SIGCHLD handler to SIG_DFL so that the SIGCHLD signal generated by its
fork() would be discarded (the SIGCHLD default action is to be ignored), then restore it to its previous setting. This would have the undesirable side-effect of discarding all SIGCHLD signals pending to the process.
\n
