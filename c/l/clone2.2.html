عندما تنتهي العملية الفرعية، قد يتم إرسال إشارة إلى العملية الأم. يتم تحديد إشارة الإنهاء في البايت المنخفض من flags (clone()) أو في cl_args.exit_signal (clone3()). إذا تم تحديد هذه الإشارة كأي شيء آخر غير SIGCHLD، فيجب على العملية الأم تحديد الخيارات __WALL أو __WCLONE عند الانتظار للعملية الفرعية باستخدام wait(2). إذا لم يتم تحديد إشارة (أي صفر)، فلن يتم إخطار العملية الأم عند انتهاء العملية الفرعية.

مصفوفة set_tid

بشكل افتراضي، تختار النواة معرف PID التسلسلي التالي للعملية الجديدة في كل من مساحات أسماء PID التي توجد فيها. عند إنشاء عملية باستخدام clone3()، يمكن استخدام مصفوفة set_tid (متاحة منذ Linux 5.5) لتحديد معرفات PID محددة للعملية في بعض أو كل مساحات أسماء PID التي توجد فيها. إذا كان معرف PID للعملية التي تم إنشاؤها حديثًا يجب تعيينه فقط لمساحة اسم PID الحالية أو في مساحة اسم PID التي تم إنشاؤها حديثًا (إذا كانت flags تحتوي على CLONE_NEWPID)، فيجب أن يكون العنصر الأول في مصفوفة set_tid هو معرف PID المطلوب ويجب أن يكون set_tid_size هو 1.

إذا كان معرف PID للعملية التي تم إنشاؤها حديثًا يجب أن يكون له قيمة معينة في مساحات أسماء PID متعددة، فيمكن أن تحتوي مصفوفة set_tid على إدخالات متعددة. يحدد الإدخال الأول معرف PID في مساحة اسم PID الأكثر تداخلًا، ويحتوي كل إدخال لاحق على معرف PID في مساحة اسم PID السلف المقابلة. يتم تحديد عدد مساحات أسماء PID التي يجب تعيين معرف PID فيها بواسطة set_tid_size، والذي لا يمكن أن يكون أكبر من عدد مساحات أسماء PID المتداخلة حاليًا.

لإنشاء عملية بمعرفات PID التالية في تسلسل هرمي لمساحات أسماء PID:

مستوى مساحة اسم PID معرف PID المطلوب ملاحظات
0 31496 أبعد مساحة اسم PID
1 42
2 7 أقرب مساحة اسم PID

اضبط المصفوفة على:


set_tid[0] = 7;
set_tid[1] = 42;
set_tid[2] = 31496;
set_tid_size = 3;

إذا كان المطلوب تحديد معرفات PID في مساحتي أسماء PID الأقرب فقط، فاضبط المصفوفة على:


set_tid[0] = 7;
set_tid[1] = 42;
set_tid_size = 2;

يتم اختيار معرف PID في مساحات أسماء PID خارج مساحتي أسماء PID الأقرب بنفس الطريقة التي يتم بها اختيار أي معرف PID آخر.

تتطلب ميزة set_tid CAP_SYS_ADMIN أو (منذ Linux 5.9) CAP_CHECKPOINT_RESTORE في جميع مساحات أسماء المستخدمين المالكة لمساحات أسماء PID المستهدفة.

يجوز للمستدعين فقط اختيار معرف PID أكبر من 1 في مساحة اسم PID معينة إذا كانت هناك عملية init (أي عملية بمعرف PID 1) موجودة بالفعل في تلك المساحة. بخلاف ذلك، يجب أن يكون إدخال PID لمساحة اسم PID هذه هو 1.

قناع flags

تسمح كل من clone() و clone3() بقناع بتات (bit mask) يقوم بتعديل سلوكهما ويسمح للمستدعي بتحديد ما يتم مشاركته بين العملية المتصلة والعملية الفرعية. يتم الإشارة إلى قناع البتات هذا - الوسيط flags لـ clone() أو حقل cl_args.flags الذي يتم تمريره إلى clone3() - باسم قناع flags في بقية هذه الصفحة.

يتم تحديد قناع flags كعملية OR ثنائية (bitwise OR) لصفر أو أكثر من الثوابت المدرجة أدناه. باستثناء ما هو مذكور أدناه، تتوفر هذه العلامات (ولها نفس التأثير) في كل من clone() و clone3().

CLONE_CHILD_CLEARTID (منذ Linux 2.5.49)
مسح (صفر) معرف العملية الفرعية في الموقع الذي يشير إليه child_tid (clone()) أو cl_args.child_tid (clone3()) في ذاكرة العملية الفرعية عند انتهاء العملية الفرعية، وإجراء استيقاظ على futex في هذا العنوان. يمكن تغيير العنوان المعني بواسطة استدعاء نظام set_tid_address(2). يتم استخدام هذا بواسطة مكتبات الخيوط.
CLONE_CHILD_SETTID (منذ Linux 2.5.49)
تخزين معرف العملية الفرعية في الموقع الذي يشير إليه child_tid (clone()) أو cl_args.child_tid (clone3()) في ذاكرة العملية الفرعية. تكتمل عملية التخزين قبل أن تعود استدعاء clone بالتحكم إلى مساحة المستخدم في العملية الفرعية. (لاحظ أن عملية التخزين قد لا تكتمل قبل عودة استدعاء clone في العملية الأم، وهو أمر مهم إذا تم استخدام العلامة CLONE_VM أيضًا.)
CLONE_CLEAR_SIGHAND (منذ Linux 5.5)
بشكل افتراضي، تكون حالات الإشارة في العملية الفرعية هي نفسها كما في العملية الأم. إذا تم تحديد هذه العلامة، فسيتم إعادة تعيين جميع الإشارات التي يتم التعامل معها في العملية الأم (وليست مضبوطة على SIG_IGN) إلى حالاتها الافتراضية (SIG_DFL) في العملية الفرعية.
تحديد هذه العلامة مع CLONE_SIGHAND أمر غير منطقي ومحظور.
CLONE_DETACHED (تاريخي)
لفترة من الوقت (خلال سلسلة تطوير Linux 2.5) كانت هناك علامة CLONE_DETACHED، والتي تسببت في عدم تلقي العملية الأم لإشارة عند انتهاء العملية الفرعية. في النهاية، تم استيعاب تأثير هذه العلامة ضمن علامة CLONE_THREAD وبحلول وقت إصدار Linux 2.6.0، لم يكن لهذه العلامة أي تأثير. منذ Linux 2.6.2، اختفت الحاجة إلى تقديم هذه العلامة مع CLONE_THREAD.
لا تزال هذه العلامة محددة، ولكن عادة ما يتم تجاهلها عند استدعاء clone(). ومع ذلك، راجع وصف CLONE_PIDFD لبعض الاستثناءات.
CLONE_FILES (منذ Linux 2.0)
إذا تم تعيين CLONE_FILES، فإن العملية المتصلة والعملية الفرعية تشارك نفس جدول واصفات الملفات. أي واصف ملف تم إنشاؤه بواسطة العملية المتصلة أو العملية الفرعية يكون صالحًا أيضًا في العملية الأخرى. وبالمثل، إذا قامت إحدى العمليتين بإغلاق واصف ملف، أو غيرت علاماته المرتبطة (باستخدام عملية fcntl(2) F_SETFD)، فتتأثر العملية الأخرى أيضًا. إذا قامت عملية تشارك جدول واصفات الملفات باستدعاء execve(2)، فسيتم مضاعفة جدول واصفات ملفاتها (فصلها).
إذا لم يتم تعيين CLONE_FILES، فإن العملية الفرعية ترث نسخة من جميع واصفات الملفات المفتوحة في العملية المتصلة وقت استدعاء clone. العمليات اللاحقة التي تفتح أو تغلق واصفات الملفات، أو تغير علامات واصفات الملفات، التي تقوم بها إحدى العمليتين (المتصلة أو الفرعية) لا تؤثر على العملية الأخرى. لاحظ، مع ذلك، أن واصفات الملفات المضاعفة في العملية الفرعية تشير إلى نفس وصف الملفات المفتوحة كما في العملية المتصلة، وبالتالي تشترك في إزاحات الملفات وحالات الملفات (انظر open(2)).
CLONE_FS (منذ Linux 2.0)
إذا تم تعيين CLONE_FS، فإن العملية المتصلة والعملية الفرعية تشارك نفس معلومات نظام الملفات. وهذا يشمل جذر نظام الملفات، ودليل العمل الحالي، و umask. أي استدعاء لـ chroot(2)، chdir(2)، أو umask(2) يتم تنفيذه بواسطة العملية المتصلة أو العملية الفرعية يؤثر أيضًا على العملية الأخرى.
إذا لم يتم تعيين CLONE_FS، فإن العملية الفرعية تعمل على نسخة من معلومات نظام الملفات للعملية المتصلة وقت استدعاء clone. الاستدعاءات لـ chroot(2)، chdir(2)، أو umask(2) التي تتم لاحقًا بواسطة إحدى العمليتين لا تؤثر على العملية الأخرى.
CLONE_INTO_CGROUP (منذ Linux 5.7)
بشكل افتراضي، يتم وضع العملية الفرعية في نفس cgroup الإصدار 2 مثل العملية الأم. تسمح العلامة CLONE_INTO_CGROUP بإنشاء العملية الفرعية في cgroup إصدار 2 مختلف. (لاحظ أن CLONE_INTO_CGROUP لها تأثير فقط على cgroups الإصدار 2.)
لوضع العملية الفرعية في cgroup مختلف، يحدد المستدعي CLONE_INTO_CGROUP في cl_args.flags ويمرر واصف ملف يشير إلى cgroup إصدار 2 في الحقل cl_args.cgroup. (يمكن الحصول على واصف الملف هذا عن طريق فتح دليل cgroup v2 باستخدام علامة O_RDONLY أو علامة O_PATH.) لاحظ أن جميع القيود المعتادة (الموصوفة في cgroups(7)) على وضع عملية في cgroup إصدار 2 تنطبق.
من بين حالات الاستخدام الممكنة لـ CLONE_INTO_CGROUP ما يلي:
•
إنشاء عملية في cgroup مختلف عن cgroup العملية الأم يجعل من الممكن لمدير الخدمة إنشاء خدمات جديدة مباشرة في cgroups مخصصة. هذا يلغي تقلب المحاسبة الذي قد ينجم عن إنشاء العملية الفرعية أولاً في نفس cgroup مثل العملية الأم ثم نقلها إلى cgroup المستهدف. علاوة على ذلك، فإن إنشاء العملية الفرعية مباشرة في cgroup مستهدف أرخص بكثير من نقل العملية الفرعية إلى cgroup المستهدف بعد إنشائها.
•
تسمح العلامة CLONE_INTO_CGROUP أيضًا بإنشاء عمليات مجمدة عن طريق إنشائها في cgroup مجمد. (انظر cgroups(7) لوصف وحدة التحكم المجمدة.)
•
بالنسبة للتطبيقات المتوازية (أو حتى تطبيقات الخيوط التي تستخدم cgroups للحد من الخيوط الفردية)، من الممكن إنشاء تخطيط cgroup ثابت قبل إنشاء كل خيط مباشرة في cgroup المستهدف الخاص به.
CLONE_IO (منذ Linux 2.6.25)
إذا تم تعيين CLONE_IO، فإن العملية الجديدة تشارك سياق I/O مع العملية المتصلة. إذا لم يتم تعيين هذه العلامة، فإن (كما هو الحال مع fork(2)) العملية الجديدة لديها سياق I/O خاص بها.
سياق I/O هو نطاق I/O لمجدول القرص

clone

clone - إنشاء عملية جديدة

الملخص

int clone(int (*fn)(void *), void *stack, int flags, void *arg, ...
          /* pid_t *ptid, void *newtls, pid_t *ctid */ );
int clone3(unsigned long flags, void *stack,
           int stack_size,        /* Size of stack */
           int *parent_tid, int *child_tid,
           unsigned long tls);

الوصف

تُنشئ كل من الاستدعاءات clone() و clone3() عملية جديدة (خيط جديد). إذا نجح الاستدعاء، فسيتم إرجاع 0 إلى العملية الجديدة، وسيتم إرجاع معرف العملية (PID) للعملية الجديدة إلى العملية الأصلية. إذا فشل الاستدعاء، فسيتم إرجاع -1 إلى العملية الأصلية، ولن يتم إنشاء أي عملية جديدة.

يجعل الاستدعاء clone() العملية الجديدة نسخة من العملية الأصلية، باستثناء ما هو محدد بواسطة العلم flags. يتم توفير البيانات الخاصة بالعملية التي يتم إنشاؤها حديثًا (مثل معرف العملية، معرف العملية للمؤقت، معرّفات خيوط النقل، إلخ) بواسطة flags. بالإضافة إلى ذلك، إذا تم توفير stack، فإن العملية الجديدة تبدأ تنفيذها من الدالة fn، مع تمرير arg كوسيطة لهذه الدالة. إذا لم يتم توفير stack، فإن العملية الجديدة تستمر في التنفيذ من النقطة التي تم استدعاء clone() عندها.

يمكن أن تؤدي الأعلام المختلفة إلى سلوكيات مختلفة. على سبيل المثال، يشير CLONE_VM إلى أن العملية الجديدة تشترك في مساحة العنوان الافتراضي مع العملية الأصلية، مما يعني أن كلاهما يعمل في نفس مساحة الذاكرة. يشير CLONE_FILES إلى أن كلاهما يشترك في جدول واصفات الملفات. يشير CLONE_SIGHAND إلى أن كلاهما يشترك في جدول معالجات الإشارات.

يسمح العلم CLONE_NEWUTS للعملية الجديدة بأن يكون لها نطاق UTS (hostname) خاص بها. وهذا يعني أن التغييرات التي تم إجراؤها على اسم المضيف أو اسم النطاق في العملية الجديدة لن تؤثر على العملية الأصلية، والعكس صحيح.

يسمح العلم CLONE_NEWPID للعملية الجديدة بأن يكون لها مجموعة معرفات العمليات (PIDs) الخاصة بها. وهذا يعني أن معرفات العمليات التي تراها العملية الجديدة ستكون مختلفة عن تلك التي تراها العملية الأصلية.

يتم استدعاء fn مع تمرير arg إليه. إذا تم توفير stack، فيجب أن يشير إلى بداية المساحة المخصصة لمكدس العملية الجديدة. تفترض نواة لينكس أن المكدس ينمو لأسفل، لذا يجب أن يشير stack إلى أعلى عنوان في المساحة المخصصة للمكدس.

إذا تم تحديد CLONE_PARENT_SETTID في flags، يتم كتابة معرف العملية (PID) للعملية الجديدة في الموقع الذي يشير إليه ctid من قبل العملية الأصلية. إذا تم تحديد CLONE_CHILD_SETTID في flags، فسيتم كتابة معرف العملية (PID) للعملية الجديدة في الموقع الذي يشير إليه ctid بواسطة العملية الجديدة نفسها.

إذا تم تحديد CLONE_PARENT_SETTID في flags، يتم كتابة معرف العملية (PID) للعملية الجديدة في الموقع الذي يشير إليه ptid من قبل العملية الأصلية. إذا تم تحديد CLONE_CHILD_CLEARTID في flags، فسيتم مسح معرف العملية (PID) في الموقع الذي يشير إليه ctid عندما تنهي العملية الجديدة مسارها.

استخدم clone3() بدلاً من clone() في التطبيقات الجديدة. إنه يوفر طريقة أكثر مرونة لتحديد خيارات العملية الجديدة، ولا يستخدم تمرير وسيطات متغيرة.

Linux 2.4 وما قبلها

في سلسلة Linux 2.4.x، لا تجعل CLONE_THREAD بشكل عام والد العملية الجديدة هو نفس والد العملية المستدعية. ومع ذلك، من Linux 2.4.7 إلى Linux 2.4.18، كان علم CLONE_THREAD يعني ضمنيًا علم CLONE_PARENT (كما هو الحال في Linux 2.6.0 وما بعده).

في Linux 2.4 وما قبلها، لا يأخذ clone() الوسيطات parent_tid و tls و child_tid.

ia64

على ia64، يتم استخدام واجهة مختلفة:


int __clone2(typeof(int (void *)) *fn,
             void *stack_base, size_t stack_size,
             int flags, void *arg, ...
          /* pid_t *parent_tid, struct user_desc *tls,
             pid_t *child_tid */ );

النموذج الأولي الموضح أعلاه هو لدالة التغليف glibc؛ بالنسبة لاستدعاء النظام نفسه، يمكن وصف النموذج الأولي على النحو التالي (وهو مطابق للنموذج الأولي لـ clone() على microblaze):


long clone2(unsigned long flags, void *stack_base,
            int stack_size,         /* Size of stack */
            int *parent_tid, int *child_tid,
            unsigned long tls);

يعمل __clone2() بنفس طريقة عمل clone()، باستثناء أن stack_base يشير إلى أدنى عنوان لمنطقة مكدس الطفل، و stack_size يحدد حجم المكدس الذي يشير إليه stack_base.

ملاحظات

أحد استخدامات استدعاءات النظام هذه هو تنفيذ الخيوط (threads): تدفقات متعددة للتحكم في برنامج تعمل بشكل متزامن في مساحة عنوان مشتركة.

يمكن استخدام استدعاء النظام kcmp(2) لاختبار ما إذا كانت عمليتان تشتركان في موارد مختلفة مثل جدول واصفات الملفات، أو عمليات إلغاء استدعاءات تزامنية للنظام V، أو مساحة عنوان افتراضية.

المعالجات المسجلة باستخدام pthread_atfork(3) لا يتم تنفيذها أثناء استدعاء clone.

أخطاء

احتوت إصدارات مكتبة GNU C من 2.3.4 إلى 2.24 بما في ذلك على دالة تغليف لـ getpid(2) قامت بتخزين معرفات العمليات مؤقتًا. اعتمد هذا التخزين المؤقت على الدعم في تغليف glibc لـ clone()، لكن القيود في التنفيذ عنت أن المخزن المؤقت لم يكن محدثًا في بعض الظروف. على وجه الخصوص، إذا تم تسليم إشارة إلى الطفل فورًا بعد استدعاء clone()، فقد تعيد استدعاء getpid(2) في معالج للإشارة معرف العملية للمستدعي ("الأب")، إذا لم تكن دالة تغليف clone قد حصلت على فرصة لتحديث المخزن المؤقت لمعرف العملية في الطفل. (يتجاهل هذا النقاش الحالة التي تم فيها إنشاء الطفل باستخدام CLONE_THREAD، عندما يجب أن تعيد getpid(2) نفس القيمة في الطفل وفي العملية التي استدعت clone()، نظرًا لأن المستدعي والطفل في نفس مجموعة الخيوط. مشكلة المخزن المؤقت القديم لا تحدث أيضًا إذا كان الوسيط flags يتضمن CLONE_VM.) للحصول على الحقيقة، كان من الضروري أحيانًا استخدام كود مثل ما يلي:


#include <syscall.h>
pid_t mypid;
mypid = syscall(SYS_getpid);

نظرًا لمشكلة المخزن المؤقت القديم، بالإضافة إلى مشاكل أخرى مذكورة في getpid(2)، تمت إزالة ميزة تخزين معرفات العمليات مؤقتًا في glibc 2.25.

أمثلة

يوضح البرنامج التالي استخدام clone() لإنشاء عملية ابن تنفذ في نطاق UTS منفصل. يغير الطفل اسم المضيف في نطاق UTS الخاص به. ثم تعرض كل من الأصل والابن اسم المضيف للنظام، مما يجعل من الممكن رؤية أن اسم المضيف يختلف في نطاقات UTS للأصل والابن. للحصول على مثال لاستخدام هذا البرنامج، راجع setns(2).

داخل البرنامج النموذجي، نقوم بتخصيص الذاكرة التي سيتم استخدامها لمكدس الطفل باستخدام mmap(2) بدلاً من malloc(3) للأسباب التالية:

•
mmap(2) يخصص كتلة من الذاكرة تبدأ على حدود صفحة وهي مضاعف لحجم الصفحة. هذا مفيد إذا أردنا إنشاء صفحة حراسة (صفحة بحماية PROT_NONE) في نهاية المكدس باستخدام mprotect(2).
•
يمكننا تحديد العلم MAP_STACK لطلب تعيين مناسب للمكدس. في الوقت الحالي، هذا العلم لا يفعل شيئًا على لينكس، ولكنه موجود وله تأثير على بعض الأنظمة الأخرى، لذا يجب تضمينه من أجل قابلية النقل.

مصدر البرنامج

#define _GNU_SOURCE
#include <err.h>
#include <sched.h>
#include <signal.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/mman.h>
#include <sys/types.h>
#include <sys/utsname.h>
#include <sys/wait.h>
#include <unistd.h>
static int              /* Start function for cloned child */
childFunc(void *arg)
{
    struct utsname uts;
    /* Change hostname in UTS namespace of child.  */
    if (sethostname(arg, strlen(arg)) == -1)
        err(EXIT_FAILURE, "sethostname");
    /* Retrieve and display hostname.  */
    if (uname(&uts) == -1)
        err(EXIT_FAILURE, "uname");
    printf("uts.nodename in child:  %s\n", uts.nodename);
    /* Keep the namespace open for a while, by sleeping.
       This allows some experimentation--for example, another
       process might join the namespace.  */
    sleep(200);
    return 0;           /* Child terminates now */
}
#define STACK_SIZE (1024 * 1024)    /* Stack size for cloned child */
int
main(int argc, char *argv[])
{
    char            *stack;         /* Start of stack buffer */
    char            *stackTop;      /* End of stack buffer */
    pid_t           pid;
    struct utsname  uts;
    if (argc < 2) {
        fprintf(stderr, "Usage: %s <child-hostname>\n", argv[0]);
        exit(EXIT_SUCCESS);
    }
    /* Allocate memory to be used for the stack of the child.  */
    stack = mmap(NULL, STACK_SIZE, PROT_READ | PROT_WRITE,
                 MAP_PRIVATE | MAP_ANONYMOUS | MAP_STACK, -1, 0);
    if (stack == MAP_FAILED)
        err(EXIT_FAILURE, "mmap");
    stackTop = stack + STACK_SIZE;  /* Assume stack grows downward */
    /* Create child that has its own UTS namespace;
       child commences execution in childFunc().  */
    pid = clone(childFunc, stackTop, CLONE_NEWUTS | SIGCHLD, argv[1]);
    if (pid == -1)
        err(EXIT_FAILURE, "clone");
    if (munmap(stack, STACK_SIZE))
        err(EXIT_FAILURE, "munmap");
    printf("clone() returned %jd\n", (intmax_t) pid);
    /* Parent falls through to here */
    sleep(1);           /* Give child time to change its hostname */
    /* Display hostname in parent's UTS namespace.  This will be
       different from hostname in child's UTS namespace.  */
    if (uname(&uts) == -1)
        err(EXIT_FAILURE, "uname");
    printf("uts.nodename in parent: %s\n", uts.nodename);
    if (waitpid(pid, NULL, 0) == -1)    /* Wait for child */
        err(EXIT_FAILURE, "waitpid");
    printf("child has terminated\n");
    exit(EXIT_SUCCESS);
}
