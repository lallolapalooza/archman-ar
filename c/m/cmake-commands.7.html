block

تمت الإضافة في الإصدار 3.25.

تقييم مجموعة من الأوامر بنطاق متغير و/أو سياسة مخصص.

block([SCOPE_FOR [POLICIES] [VARIABLES]] [PROPAGATE <var-name>...])
  <commands>
endblock()

يتم تسجيل جميع الأوامر بين block() والأمر المطابق endblock() <#command:endblock> دون استدعائها. بمجرد تقييم الأمر endblock() <#command:endblock>، يتم استدعاء قائمة الأوامر المسجلة داخل النطاقات المطلوبة، ثم تتم إزالة النطاقات التي تم إنشاؤها بواسطة الأمر block().

SCOPE_FOR
تحديد النطاقات التي يجب إنشاؤها.
POLICIES
إنشاء نطاق سياسة جديد. هذا يعادل cmake_policy(PUSH) <#push> مع cmake_policy(POP) <#pop> تلقائي عند مغادرة نطاق الكتلة.
VARIABLES
إنشاء نطاق متغير جديد.

إذا لم يتم تحديد SCOPE_FOR، فإن هذا يعادل:

block(SCOPE_FOR VARIABLES POLICIES)
PROPAGATE
عند إنشاء نطاق متغير بواسطة الأمر block()، يقوم هذا الخيار بتعيين أو إلغاء تعيين المتغيرات المحددة في النطاق الأصلي. هذا يعادل أوامر set(PARENT_SCOPE) <#command:set> أو unset(PARENT_SCOPE) <#command:unset>.
set(var1 "INIT1")
set(var2 "INIT2")
set(var3 "INIT3")
block(PROPAGATE var1 var2)
  set(var1 "VALUE1")
  unset(var2)
  set(var3 "VALUE3")
endblock()
# الآن var1 يحمل VALUE1، تم إلغاء تعيين var2، و var3 يحمل القيمة الأولية INIT3

يُسمح بهذا الخيار فقط عند إنشاء نطاق متغير. سيتم رفع خطأ في الحالات الأخرى.

عندما تكون block() داخل أمر foreach() <#command:foreach> أو while() <#command:while>، يمكن استخدام الأمرين break() <#command:break> و continue() <#command:continue> داخل الكتلة.

while(TRUE)
  block()
     ...
     # الأمر break() سيوقف الأمر while()
     break()
  endblock()
endwhile()

انظر أيضًا

  • endblock() <#command:endblock>
  • return() <#command:return>
  • cmake_policy() <#command:cmake_policy>

glob
Expand globbing patterns to a list of files.
glob(<out-var> ["<pat1>" ["pat2" ...]] [LIST_DIRECTORIES true|false]
     [RELATIVE <dir>] [USE_RELATIVE_PATHS] [NO_MATCH_RECURSE])
glob2(<out-var> ["<pat1>" ["pat2" ...]])

The glob command expands the given globbing patterns into a list of files or directories. The list is stored in the variable named by <out-var>.

The patterns are similar to Unix shell globbing patterns. The following wildcard characters are supported:

  • * Matches 0 or more characters.
  • ? Matches exactly 1 character.
  • [...] Matches any one character within the brackets.
  • [!...] Matches any one character not within the brackets.

If the LIST_DIRECTORIES option is provided with value true, the results will include directories which match the patterns. The default behavior is to list files only. If LIST_DIRECTORIES is provided with value false, then directories are excluded from the results.

If the RELATIVE <dir> option is provided, then relative paths are evaluated with respect to <dir>. If the USE_RELATIVE_PATHS option is provided, the paths stored in the output variable will be relative to the current source directory. The RELATIVE option implies USE_RELATIVE_PATHS.

If the NO_MATCH_RECURSE option is given, then the wildcard ** will not be recursive. This is useful on systems that do not support recursive globbing such as Windows.

The glob2 command is similar to glob, but it also supports the recursive wildcard **, which matches files and directories recursively in CMakeLists.txt files. It also supports the GLOB_RECURSE keyword for recursive globbing.

For example:

glob(my_files RELATIVE ${CMAKE_CURRENT_SOURCE_DIR} *.c *.h)

will find all files ending in .c or .h in the current source directory and store their relative paths in the `my_files` variable.

The following is an example of recursive globbing:

glob(my_files ${CMAKE_CURRENT_SOURCE_DIR}/src/*.cpp
             ${CMAKE_CURRENT_SOURCE_DIR}/include/*.h)

The following example uses GLOB_RECURSE to find all C++ source files under the src directory.

file(GLOB_RECURSE CPP_FILES src/*.cpp)

The following example matches all python files in /dir and subdirectories.

glob(PYTHON_FILES /dir/*.py)
/dir/*.py match all python files in /dir and subdirectories

The options are:

file(REMOVE <files>...)
file(REMOVE_RECURSE <files>...)
Remove the given files. The REMOVE_RECURSE mode will remove the given files and directories, including non-empty directories. No error is emitted if a given file does not exist. Relative input paths are evaluated with respect to the current source directory.

Changed in version 3.15: Empty input paths are ignored with a warning. Previous versions of CMake interpreted empty strings as a relative path with respect to the current directory and removed its contents.

file(RENAME <oldname> <newname> [RESULT <result>] [NO_REPLACE])
Move a file or directory within a filesystem from <oldname> to <newname>, replacing the destination atomically.

The options are:

RESULT <result>
Added in version 3.21.

Set <result> variable to 0 on success or an error message otherwise. If RESULT is not specified and the operation fails, an error is emitted.

NO_REPLACE
Added in version 3.21.

If the <newname> path already exists, do not replace it. If RESULT <result> is used, the result variable will be set to NO_REPLACE. Otherwise, an error is emitted.

file(COPY_FILE <oldname> <newname> [RESULT <result>] [ONLY_IF_DIFFERENT] [INPUT_MAY_BE_RECENT])
Added in version 3.21.

Copy a file from <oldname> to <newname>. Directories are not supported. Symlinks are ignored and <oldfile>'s content is read and written to <newname> as a new file.

The options are:

RESULT <result>
Set <result> variable to 0 on success or an error message otherwise. If RESULT is not specified and the operation fails, an error is emitted.
ONLY_IF_DIFFERENT
If the <newname> path already exists, do not replace it if the file's contents are already the same as <oldname> (this avoids updating <newname>'s timestamp).
INPUT_MAY_BE_RECENT
Added in version 3.26.

Tell CMake that the input file may have been recently created. This is meaningful only on Windows, where files may be inaccessible for a short time after they are created. With this option, if permission is denied, CMake will retry reading the input a few times.

This sub-command has some similarities to configure_file() <#command:configure_file> with the COPYONLY option. An important difference is that configure_file() <#command:configure_file> creates a dependency on the source file, so CMake will be re-run if it changes. The file(COPY_FILE) sub-command does not create such a dependency.

See also the file(COPY) sub-command just below which provides further file-copying capabilities.

file(COPY [...])
file(INSTALL [...])
The COPY signature copies files, directories, and symlinks to a destination folder. Relative input paths are evaluated with respect to the current source directory, and a relative destination is evaluated with respect to the current build directory. Copying preserves input file timestamps, and optimizes out a file if it exists at the destination with the same timestamp. Copying preserves input permissions unless explicit permissions or NO_SOURCE_PERMISSIONS are given (default is USE_SOURCE_PERMISSIONS).
file(<COPY|INSTALL> <files>... DESTINATION <dir>
     [NO_SOURCE_PERMISSIONS | USE_SOURCE_PERMISSIONS]
     [FILE_PERMISSIONS <permissions>...]
     [DIRECTORY_PERMISSIONS <permissions>...]
     [FOLLOW_SYMLINK_CHAIN]
     [FILES_MATCHING]
     [[PATTERN <pattern> | REGEX <regex>]
      [EXCLUDE] [PERMISSIONS <permissions>...]] [...])

Note:

For a simple file copying operation, the file(COPY_FILE) sub-command just above may be easier to use.

Added in version 3.15: If FOLLOW_SYMLINK_CHAIN is specified, COPY will recursively resolve the symlinks at the paths given until a real file is found, and install a corresponding symlink in the destination for each symlink encountered. For each symlink that is installed, the resolution is stripped of the directory, leaving only the filename, meaning that the new symlink points to a file in the same directory as the symlink. This feature is useful on some Unix systems, where libraries are installed as a chain of symlinks with version numbers, with less specific versions pointing to more specific versions. FOLLOW_SYMLINK_CHAIN will install all of these symlinks and the library itself into the destination directory. For example, if you have the following directory structure:

  • /opt/foo/lib/libfoo.so.1.2.3
  • /opt/foo/lib/libfoo.so.1.2 -> libfoo.so.1.2.3
  • /opt/foo/lib/libfoo.so.1 -> libfoo.so.1.2
  • /opt/foo/lib/libfoo.so -> libfoo.so.1

and you do:

file(COPY /opt/foo/lib/libfoo.so DESTINATION lib FOLLOW_SYMLINK_CHAIN)

This will install all of the symlinks and libfoo.so.1.2.3 itself into lib.

See the install(DIRECTORY) <#directory> command for documentation of permissions, FILES_MATCHING, PATTERN, REGEX, and EXCLUDE options. Copying directories preserves the structure of their content even if options are used to select a subset of files.

The INSTALL signature differs slightly from COPY: it prints status messages, and NO_SOURCE_PERMISSIONS is default. Installation scripts generated by the install() <#command:install> command use this signature (with some undocumented options for internal use).

Changed in version 3.22: The environment variable CMAKE_INSTALL_MODE <#envvar:CMAKE_INSTALL_MODE> can override the default copying behavior of file(INSTALL).

file(SIZE <filename> <variable>)
Added in version 3.14.

Determine the file size of the <filename> and put the result in <variable> variable. Requires that <filename> is a valid path pointing to a file and is readable.

file(READ_SYMLINK <linkname> <variable>)
Added in version 3.14.

Query the symlink <linkname> and stores the path it points to in the result <variable>. If <linkname> does not exist or is not a symlink, CMake issues a fatal error.

Note that this command returns the raw symlink path and does not resolve a relative path. The following is an example of how to ensure that an absolute path is obtained:

set(linkname "/path/to/foo.sym")
file(READ_SYMLINK "${linkname}" result)
if(NOT IS_ABSOLUTE "${result}")
  get_filename_component(dir "${linkname}" DIRECTORY)
  set(result "${dir}/${result}")
endif()

The following arguments specify filters for including or excluding libraries to be resolved. See below for a full description of how they work.

POST_EXCLUDE_REGEXES <regexes>...
List of post-exclude regexes through which to filter the names of resolved dependencies.

Added in version 3.21.

List of post-include filenames through which to filter the names of resolved dependencies. Symlinks are resolved when attempting to match these filenames.

POST_EXCLUDE_FILES <files>...
Added in version 3.21.

List of post-exclude filenames through which to filter the names of resolved dependencies. Symlinks are resolved when attempting to match these filenames.

These arguments can be used to exclude unwanted system libraries when resolving the dependencies, or to include libraries from a specific directory. The filtering works as follows:

1.
If the not-yet-resolved dependency matches any of the PRE_INCLUDE_REGEXES, steps 2 and 3 are skipped, and the dependency resolution proceeds to step 4.
2.
If the not-yet-resolved dependency matches any of the PRE_EXCLUDE_REGEXES, dependency resolution stops for that dependency.
3.
Otherwise, dependency resolution proceeds.
4.
file(GET_RUNTIME_DEPENDENCIES) searches for the dependency according to the linking rules of the platform (see below).
5.
If the dependency is found, and its full path matches one of the POST_INCLUDE_REGEXES or POST_INCLUDE_FILES, the full path is added to the resolved dependencies, and file(GET_RUNTIME_DEPENDENCIES) recursively resolves that library's own dependencies. Otherwise, resolution proceeds to step 6.
6.
If the dependency is found, but its full path matches one of the POST_EXCLUDE_REGEXES or POST_EXCLUDE_FILES, it is not added to the resolved dependencies, and dependency resolution stops for that dependency.
7.
If the dependency is found, and its full path does not match either POST_INCLUDE_REGEXES, POST_INCLUDE_FILES, POST_EXCLUDE_REGEXES, or POST_EXCLUDE_FILES, the full path is added to the resolved dependencies, and file(GET_RUNTIME_DEPENDENCIES) recursively resolves that library's own dependencies.

Different platforms have different rules for how dependencies are resolved. These specifics are described here.

On Linux platforms, library resolution works as follows:

1.
If the depending file does not have any RUNPATH entries, and the library exists in one of the depending file's RPATH entries, or its parents', in that order, the dependency is resolved to that file.
2.
Otherwise, if the depending file has any RUNPATH entries, and the library exists in one of those entries, the dependency is resolved to that file.
3.
Otherwise, if the library exists in one of the directories listed by ldconfig, the dependency is resolved to that file.
4.
Otherwise, if the library exists in one of the DIRECTORIES entries, the dependency is resolved to that file. In this case, a warning is issued, because finding a file in one of the DIRECTORIES means that the depending file is not complete (it does not list all the directories from which it pulls dependencies).
5.
Otherwise, the dependency is unresolved.

If a library file name is encountered again in the dependency tree, the original resolution is assumed. This behavior more closely matches the dynamic loader's behavior on Linux.

math

قم بتقييم تعبير رياضي.

math(EXPR <variable> "<expression>" [OUTPUT_FORMAT <format>])

يقوم بتقييم <expression> رياضي ويضبط <variable> إلى القيمة الناتجة. يجب أن تكون نتيجة التعبير قابلة للتمثيل كعدد صحيح موقع بـ 64 بت. المدخلات ذات الفاصلة العائمة غير صالحة، على سبيل المثال 1.1 * 10. يتم اقتطاع النتائج غير الصحيحة، على سبيل المثال 3 / 2.

يجب تقديم التعبير الرياضي كسلسلة نصية (أي محاطة بعلامات اقتباس مزدوجة). مثال هو "5 * (10 + 13)". العوامل المدعومة هي +، -، *، /، %، |، &، ^، ~، <<، >>، و (...)؛ لها نفس المعنى كما في كود C.

تمت الإضافة في الإصدار 3.13: يتم التعرف على الأرقام السداسية العشرية عند بادئتها بـ 0x، كما هو الحال في كود C.

تمت الإضافة في الإصدار 3.13: يتم تنسيق النتيجة وفقًا للخيار OUTPUT_FORMAT، حيث <format> هو أحد:

HEXADECIMAL
تدوين سداسي عشري كما في كود C، أي يبدأ بـ "0x".
DECIMAL
تدوين عشري. وهو ما يستخدم أيضًا إذا لم يتم تحديد خيار OUTPUT_FORMAT.

على سبيل المثال

math(EXPR value "100 * 0xA" OUTPUT_FORMAT DECIMAL)      # value is set to "1000"
math(EXPR value "100 * 0xA" OUTPUT_FORMAT HEXADECIMAL)  # value is set to "0x3e8"

تسجيل نص الرسالة المحدد في السجل. إذا تم إعطاء أكثر من سلسلة رسالة واحدة، يتم دمجها في رسالة واحدة بدون فاصل بين السلاسل.

يحدد المفتاح الاختياري <mode> نوع الرسالة، مما يؤثر على كيفية التعامل مع الرسالة:

FATAL_ERROR
خطأ CMake، إيقاف المعالجة والتوليد.

سيعيد البرنامج التنفيذي cmake(1) <#manual:cmake(1)> رمز خروج غير صفري <#cmake-exit-code>.

SEND_ERROR
خطأ CMake، متابعة المعالجة، ولكن تخطي التوليد.
WARNING
تحذير CMake، متابعة المعالجة.
AUTHOR_WARNING
تحذير CMake (المطور)، متابعة المعالجة.
DEPRECATION
خطأ أو تحذير إلغاء استخدام CMake إذا تم تمكين المتغير CMAKE_ERROR_DEPRECATED <#variable:CMAKE_ERROR_DEPRECATED> أو CMAKE_WARN_DEPRECATED <#variable:CMAKE_WARN_DEPRECATED>، على التوالي، وإلا فلا توجد رسالة.
(none) or NOTICE
رسالة مهمة مطبوعة إلى stderr لجذب انتباه المستخدم.
STATUS
الرسائل الرئيسية الشيقة التي قد يهتم بها مستخدمو المشروع. من المثالي أن تكون موجزة، لا تزيد عن سطر واحد، ولكنها لا تزال مفيدة.
VERBOSE
رسائل معلوماتية مفصلة مخصصة لمستخدمي المشروع. يجب أن توفر هذه الرسائل تفاصيل إضافية لن تكون ذات أهمية في معظم الحالات، ولكنها قد تكون مفيدة لأولئك الذين يقومون ببناء المشروع عندما يريدون رؤية أعمق لما يحدث.
DEBUG
رسائل معلوماتية مفصلة مخصصة للمطورين الذين يعملون على المشروع نفسه بدلاً من المستخدمين الذين يريدون فقط بنائه. لن تكون هذه الرسائل عادةً ذات أهمية للمستخدمين الآخرين الذين يقومون ببناء المشروع وغالبًا ما ترتبط ارتباطًا وثيقًا بتفاصيل التنفيذ الداخلية.
TRACE
رسائل دقيقة مع تفاصيل تنفيذ منخفضة المستوى للغاية. الرسائل التي تستخدم هذا المستوى من السجل ستكون عادةً مؤقتة فقط وستتوقع إزالتها قبل إصدار المشروع، أو تجميع الملفات، وما إلى ذلك.

تمت الإضافة في الإصدار 3.15: تمت إضافة المستويات NOTICE، VERBOSE، DEBUG، و TRACE.

تعرض أداة سطر الأوامر CMake رسائل STATUS إلى TRACE على stdout مسبوقة بشرطتين ومسافة. يتم إرسال جميع أنواع الرسائل الأخرى إلى stderr ولا تكون مسبوقة بشرطتين. يعرض CMake GUI <#manual:cmake-gui(1)> جميع الرسائل في منطقة السجل الخاصة به. تعرض واجهة curses <#manual:ccmake(1)> رسائل STATUS إلى TRACE واحدة تلو الأخرى على سطر الحالة ورسائل أخرى في نافذة منبثقة تفاعلية. يمكن استخدام خيار سطر الأوامر --log-level <#cmdoption-cmake-log-level> لكل من هذه الأدوات للتحكم في الرسائل التي سيتم عرضها.

تمت الإضافة في الإصدار 3.17: لجعل مستوى السجل يستمر بين تشغيلات CMake، يمكن تعيين المتغير CMAKE_MESSAGE_LOG_LEVEL <#variable:CMAKE_MESSAGE_LOG_LEVEL> بدلاً من ذلك. لاحظ أن خيار سطر الأوامر له الأسبقية على متغير التخزين المؤقت.

تمت الإضافة في الإصدار 3.16: الرسائل ذات مستويات السجل NOTICE وما دونها ستكون مسبوقة بكل سطر بمحتوى المتغير CMAKE_MESSAGE_INDENT <#variable:CMAKE_MESSAGE_INDENT> (محوّل إلى سلسلة نصية واحدة عن طريق دمج عناصر القائمة الخاصة به). بالنسبة لرسائل STATUS إلى TRACE، سيتم إدراج هذا المحتوى البادئ بعد الشرطتين.

تمت الإضافة في الإصدار 3.17: يمكن أيضًا أن تكون الرسائل ذات مستويات السجل NOTICE وما دونها مسبوقة بكل سطر بسياق بالشكل [some.context.example]. يتم الحصول على المحتوى الموجود بين الأقواس المربعة عن طريق تحويل المتغير القائمة CMAKE_MESSAGE_CONTEXT <#variable:CMAKE_MESSAGE_CONTEXT> إلى سلسلة نصية مفصولة بنقاط. سيظهر سياق الرسالة دائمًا قبل أي محتوى بادئ ولكن بعد أي شرطات بادئة مضافة تلقائيًا. بشكل افتراضي، لا يتم عرض سياق الرسالة، ويجب تمكينه صراحةً عن طريق إعطاء خيار سطر الأوامر cmake --log-context <#cmdoption-cmake-log-context> أو عن طريق تعيين المتغير CMAKE_MESSAGE_CONTEXT_SHOW <#variable:CMAKE_MESSAGE_CONTEXT_SHOW> إلى true. راجع وثائق CMAKE_MESSAGE_CONTEXT <#variable:CMAKE_MESSAGE_CONTEXT> للحصول على أمثلة الاستخدام.

يعرض نص رسائل تحذير وخطأ CMake لغة ترميز بسيطة. يتم تنسيق النص غير المسافات البادئة في فقرات مغلفة بالأسطر محددة بأسطر جديدة. يعتبر النص المسافات البادئة مُنسقًا مسبقًا.

الإبلاغ عن عمليات التحقق

تمت الإضافة في الإصدار 3.17.

نمط شائع في إخراج CMake هو رسالة تشير إلى بداية نوع ما من التحقق، تليها رسالة أخرى تبلغ عن نتيجة هذا التحقق. على سبيل المثال:

message(STATUS "Looking for someheader.h")
#... do the checks, set checkSuccess with the result
if(checkSuccess)
  message(STATUS "Looking for someheader.h - found")
else()
  message(STATUS "Looking for someheader.h - not found")
endif()

يمكن التعبير عن هذا بشكل أكثر قوة وملاءمة باستخدام صيغة المفتاح CHECK_... لأمر message():

message(<checkState> "message" ...)

حيث يجب أن يكون <checkState> أحد ما يلي:

CHECK_START
تسجيل رسالة موجزة حول التحقق الذي سيتم إجراؤه.
CHECK_PASS
تسجيل نتيجة ناجحة للتحقق.
CHECK_FAIL
تسجيل نتيجة غير ناجحة للتحقق.

عند تسجيل نتيجة تحقق، يكرر الأمر الرسالة من آخر تحقق تم البدء فيه ولم يتم الإبلاغ عن نتيجة له بعد، ثم بعض أحرف الفصل ثم نص الرسالة المقدم بعد المفتاح CHECK_PASS أو CHECK_FAIL. يتم دائمًا الإبلاغ عن رسائل التحقق بمستوى السجل STATUS.

يمكن تداخل عمليات التحقق ويجب أن يكون لكل CHECK_START مطابق واحد تمامًا CHECK_PASS أو CHECK_FAIL. يمكن أيضًا استخدام المتغير CMAKE_MESSAGE_INDENT <#variable:CMAKE_MESSAGE_INDENT> لإضافة مسافات بادئة إلى عمليات التحقق المتداخلة إذا رغبت في ذلك. على سبيل المثال:

message(CHECK_START "Finding my things")
list(APPEND CMAKE_MESSAGE_INDENT "  ")
unset(missingComponents)
message(CHECK_START "Finding partA")
# ... do check, assume we find A
message(CHECK_PASS "found")
message(CHECK_START "Finding partB")
# ... do check, assume we don't find B
list(APPEND missingComponents B)
message(CHECK_FAIL "not found")
list(POP_BACK CMAKE_MESSAGE_INDENT)
if(missingComponents)
  message(CHECK_FAIL "missing components: ${missingComponents}")
else()
  message(CHECK_PASS "all components found")
endif()

سينتج عن الإخراج من الأعلى شيء من هذا القبيل:

-- Finding my things
--   Finding partA
--   Finding partA - found
--   Finding partB
--   Finding partB - not found
-- Finding my things - missing components: B

unset

قم بإلغاء تعيين متغير، أو متغير ذاكرة تخزين مؤقت، أو متغير بيئة.

Unset Normal Variable

unset(<variable> [PARENT_SCOPE])
قم بإزالة متغير عادي من النطاق الحالي، مما يجعله غير محدد.

إذا كان PARENT_SCOPE موجودًا، فسيتم إزالة المتغير من النطاق الذي يعلو النطاق الحالي. راجع الخيار نفسه في أمر set() <#command:set> لمزيد من التفاصيل.

    rest are its arguments. The command can be an executable name or a full path
    to an executable. If the command is just an executable name, CTest will search
    for it in the system's PATH. If the command is a relative path, CTest will
    search for it relative to the current build directory. A full path is also
    acceptable. The test will be run from the directory specified by the
    WORKING_DIRECTORY option. If the WORKING_DIRECTORY option is
    not specified, the test will be run from the top-level directory of the
    current CTest build. The command can be a generator expression.


The INCLUDE_REGULAR_EXPRESSION option takes a regular
    expression that is matched against the test's output. If the expression
    matches any part of the output, the test is considered to have passed. This
    is useful for tests that produce a lot of output but indicate success with
    a specific string.


The EXCLUDE_REGULAR_EXPRESSION option takes a regular
    expression that is matched against the test's output. If the expression
    matches any part of the output, the test is considered to have failed. This
    is useful for tests that might produce a specific string indicating failure,
    but still produce other output that might match an
    INCLUDE_REGULAR_EXPRESSION.


The TIMEOUT option specifies the maximum time in seconds
    that the test is allowed to run. If the test exceeds this time limit, it will
    be terminated and CTest will report it as having failed. A value of 0 means
    no timeout.


The PROCESSOR_AFFINITY option binds the test process to
    a specific set of CPUs. The <cpuset> argument is a string
    representing a CPU set, such as "0,1" for CPUs 0 and 1, or
    "0-3" for CPUs 0 through 3. This option is available on Linux and
    Windows.


The USE_LAUNCHER option indicates that the test should be
    run using the CTest launcher program. The launcher program can be configured
    via the CTEST_LAUNCHER_EXE variable. This is useful for tests that require
    special environment setup or debugging capabilities.


The ATTACHED_FILES option specifies a list of files that
    should be attached to the test result. These files will be uploaded to the
    dashboard server along with the test output. This is useful for attaching
    log files, configuration files, or other relevant artifacts.


The ATTACHED_FILES_ON_FAIL option specifies a list of files
    that should be attached to the test result only if the test fails. This is
    useful for attaching debugging information or crash dumps.


The ENVIRONMENT option allows you to specify environment
    variables that will be set for the test process. You can specify multiple
    ENVIRONMENT options to set multiple variables.


The COST option assigns a cost to the test. CTest uses this
    cost to prioritize tests when running them in parallel. Higher cost means
    lower priority.


The PARALLEL_LEVEL option specifies the minimum number of
    parallel jobs required to run this test. CTest will only run this test if it
    can be run with at least this many parallel jobs.


The SKIP_REGULAR_EXPRESSION option takes a regular
    expression. If the test name matches this regular expression, the test will
    be skipped.


The SKIP_RETURN_VALUE option takes an integer return
    value. If the test returns this value, it will be skipped.


The BUILD_OUTPUT option tells CTest to capture the build
    output of the test and include it in the test results. This is useful for
    tests that produce output during the build process itself, rather than just
    during execution.


The LOGNAME option specifies a name for the log file that
    will be generated for this test. If not specified, CTest will generate a
    default log name.


The CONTROL_FILE option specifies a control file that CTest
    will use to manage the test. This is useful for advanced test management
    scenarios.


The FIXTURES_SETUP, FIXTURES_TEARDOWN, and
    FIXTURES_REQUIRED options are used to manage test fixtures. Fixtures
    are setup or teardown routines that are executed before or after a test, or
    that are required by a test. This allows for better organization and
    management of test dependencies.


If the name of the test file is known at configure time, you can
    use the ATTACHED_FILES or ATTACHED_FILES_ON_FAIL test
    properties instead.

exec_program


Changed in version 3.28: This command is available only if policy
    CMP0153 <#policy:CMP0153> is not set to NEW. Port
    projects to the execute_process() <#command:execute_process>
    command.


Deprecated since version 3.0: Use the execute_process()
    <#command:execute_process> command instead.


Runs an executable program during the processing of a CMake file
    or script:






exec_program(
  <executable>
  [<working-dir>]
  [ARGS <arguments-to-executable>...]
  [OUTPUT_VARIABLE <var>]
  [RETURN_VALUE <var>]
)






The <executable> is run in the optionally specified
    directory <working-dir>. The executable can include arguments
    if it is double quoted, but it is better to use the optional ARGS
    argument to specify arguments to the executable program. This is because
    CMake will then be able to escape spaces in the executable path. An optional
    argument OUTPUT_VARIABLE specifies a variable in which to store the
    output. To capture the return value of the execution, provide a
    RETURN_VALUE. If OUTPUT_VARIABLE is specified, then no output
    will go to the stdout/stderr of the console running CMake.






Examples


Example of the legacy exec_program() command used in
    earlier versions of CMake:






exec_program(
  some_command
  ${dir}
  ARGS arg_1 arg_2 args "\"<quoted-arg>\""
  OUTPUT_VARIABLE output
  RETURN_VALUE result
)






A direct equivalent replacement of the previous example using the
    execute_process() <#command:execute_process> command in new
    code:






execute_process(
  COMMAND some_command arg_1 arg_2 args "<quoted-arg>"
  WORKING_DIRECTORY ${dir}
  RESULT_VARIABLE result
  OUTPUT_VARIABLE output
  ERROR_VARIABLE output
  OUTPUT_STRIP_TRAILING_WHITESPACE
)
