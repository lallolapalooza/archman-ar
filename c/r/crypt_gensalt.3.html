DESCRIPTION

These functions generate a salt string suitable for use with the crypt(3) function. The salt determines which hashing algorithm is used and provides the necessary random component for the hashing process.

The primary function for generating salts is crypt_gensalt(). It takes an id string that specifies the desired hashing algorithm and parameters. The format of the id string depends on the underlying hashing module.

The functions ending with _rn (e.g., crypt_gensalt_rn()) fill a user-provided buffer of size n with the generated salt. These functions are generally preferred over the ones that allocate memory themselves, as they avoid potential memory leaks and offer better control over buffer management.

The functions ending with _ra (e.g., crypt_gensalt_ra()) take an additional argument rbytes, which is a pointer to a buffer containing random bytes to be used for salt generation. This allows for reproducible salt generation if the same rbytes are provided. The n argument specifies the number of random bytes available in the rbytes buffer.

The generic password hashing functions crypt_pwhash_gensalt(), crypt_pwhash_gensalt_rn(), and crypt_pwhash_gensalt_ra() provide a unified interface for generating salts for various password hashing algorithms supported by libxcrypt. The alg parameter specifies the algorithm (e.g., _CRYPT_MD5, _CRYPT_SHA512, _CRYPT_BLOWFISH). The salt and salt_len parameters are used for pre-existing salt data or to specify the buffer size. The flags parameter can be used to control generation options (see crypt(3)).

The functions named after specific algorithms (e.g., crypt_blowfish_gensalt()) are convenience functions that directly call the underlying hashing modules for that specific algorithm. They often take a salt string which contains the algorithm identifier and any parameters specific to that algorithm (e.g., "$2a$12$" for Blowfish with 12 rounds).

If salt is NULL for the _rn and _ra variants, these functions may return NULL or set errno. It is the caller's responsibility to provide a buffer large enough to hold the generated salt.

The crypt_gensalt() function allocates memory for the returned salt string. This memory must be freed by the caller using free().

The exact set of supported hashing methods and the format of the id string for crypt_gensalt() can vary depending on the system's configuration and the installed crypto modules.

The crypt_pwhash_gensalt* functions and the algorithm-specific functions use the format expected by the respective hashing modules. For example, Blowfish salts typically start with "$2a$" or "$2b$" followed by the cost factor (e.g., "$2a$12$"). MD5 salts start with "$1$". SHA-256 salts start with "$5$". SHA-512 salts start with "$6$". Traditional DES salts use a two-character salt followed by the hashed password.

The rbytes argument is intended for use with cryptographically secure random number generators. If rbytes is NULL, the functions will typically use a default source of randomness, which may or may not be cryptographically secure.

PORTABILITY NOTES

The behavior of crypt_gensalt() and the specific algorithms supported can vary between systems. The crypt_pwhash_gensalt* functions and the algorithm-specific functions provide a more standardized interface for modern hashing algorithms.

Using the _ra variants with a cryptographically secure source of random bytes is recommended for security-sensitive applications.

The traditional DES-based functions (crypt_des_gensalt* and crypt_unix_gensalt*) are considered insecure and should not be used for new applications.

The exact meaning and usage of the id parameter for crypt_gensalt() depends heavily on the specific hashing implementation. For example, some implementations might use an empty string for the default algorithm, while others might expect specific tags like "sha512-crypt".

The crypt_pwhash_gensalt() function requires the caller to specify the algorithm via the alg parameter and the salt string via the salt and salt_len arguments. The salt argument itself should conform to the salt format expected by the specified algorithm.

The crypt_pwhash_gensalt_rn() and crypt_pwhash_gensalt_ra() functions require the caller to provide a buffer for the salt and its size. If the provided buffer is too small, the behavior is undefined (it may truncate the salt or cause a buffer overflow).

The crypt_pwhash_gensalt_ra() and crypt_blowfish_gensalt_ra(), crypt_md5_gensalt_ra(), crypt_sha256_gensalt_ra(), crypt_sha512_gensalt_ra(), crypt_des_gensalt_ra(), and crypt_unix_gensalt_ra() functions take an additional rbytes argument. This is a pointer to a buffer containing random bytes to be used in salt generation. The size of this buffer is specified by the rbytes_len argument. Providing cryptographically secure random bytes via rbytes is crucial for generating secure salts.

The crypt_gensalt() function allocates memory using malloc(). The caller is responsible for freeing this memory using free().

The specific set of supported hashing methods varies considerably from system to system.
