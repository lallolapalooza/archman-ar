الاسم

unbound.conf - ملف تكوين Unbound 1.24.2.

الخلاصة

unbound.conf

الوصف

يُستخدم unbound.conf لتكوين unbound(8). يحتوي تنسيق الملف على سمات وقيم. بعض السمات لها سمات بداخلها. الصيغة هي: attribute: value.

تبدأ التعليقات بـ # وتستمر حتى نهاية السطر. يتم تجاهل الأسطر الفارغة وكذلك المسافات البيضاء في بداية السطر.

يمكن استخدام الأداة المساعدة unbound-checkconf(8) للتحقق من unbound.conf قبل الاستخدام.

مثال

يوضح أدناه ملف تكوين نموذجي. انسخه إلى /etc/unbound/unbound.conf وابدأ الخادم بـ:

$ unbound -c /etc/unbound/unbound.conf

معظم الإعدادات هي الإعدادات الافتراضية. أوقف الخادم بـ:

$ kill `cat /etc/unbound/unbound.pid`

أدناه ملف تكوين بسيط. يحتوي توزيع المصدر على ملف example.conf واسع النطاق مع جميع الخيارات.

# unbound.conf(5) config file for unbound(8).
server:
    directory: "/etc/unbound"
    username: unbound
    # make sure unbound can access entropy from inside the chroot.
    # e.g. on linux the use these commands (on BSD, devfs(8) is used):
    #      mount --bind -n /dev/urandom /etc/unbound/dev/urandom
    # and  mount --bind -n /dev/log /etc/unbound/dev/log
    chroot: "/etc/unbound"
    # logfile: "/etc/unbound/unbound.log"  # uncomment to use logfile.
    pidfile: "/etc/unbound/unbound.pid"
    # verbosity: 1      # uncomment and increase to get more logging.
    # listen on all interfaces, answer queries from the local subnet.
    interface: 0.0.0.0
    interface: ::0
    access-control: 10.0.0.0/8 allow
    access-control: 2001:DB8::/64 allow

تنسيق الملف

يجب أن يكون هناك مسافة بيضاء بين الكلمات المفتاحية. تنتهي الكلمات المفتاحية للسمات بـ ':'. تتبع السمة قيمة، أو السمات المحتوية عليها والتي تشير إليها باسم بند. يمكن تكرار البنود في جميع أنحاء الملف (أو الملفات المضمنة) لتجميع السمات تحت نفس البند.

يمكن تضمين الملفات باستخدام التوجيه include:. يمكن أن يظهر في أي مكان، وهو يقبل اسم ملف واحد كوسيط. تستمر المعالجة كما لو تم نسخ النص من الملف المضمن إلى ملف التكوين في تلك النقطة. إذا كنت تستخدم أيضًا chroot، فإن استخدام المسارات الكاملة للملفات المضمنة يعمل، والمسارات النسبية للأسماء المضمنة تعمل إذا كان الدليل الذي يبدأ منه الخادم يساوي دليل chroot/العمل الخاص به أو تم تحديده قبل عبارة التضمين باستخدام directory: dir. يمكن استخدام أحرف البدل لتضمين ملفات متعددة، انظر glob(7).

لخيار تضمين هيكلي أكثر، يمكن استخدام التوجيه include-toplevel:. هذا يغلق أي بند نشط حاليًا (إن وجد) ويفرض استخدام البنود في الملفات المضمنة وبعد هذا التوجيه مباشرة.

خيارات الخادم

هذه الخيارات جزء من بند server:.

verbosity: <number>
مستوى التفصيل.
Level 0
لا تفاصيل، أخطاء فقط.
Level 1
يعطي معلومات تشغيلية.
Level 2
يعطي معلومات تشغيلية مفصلة بما في ذلك معلومات قصيرة لكل استعلام.
Level 3
يعطي معلومات مستوى الاستعلام، إخراج لكل استعلام.
Level 4
يعطي معلومات مستوى الخوارزمية.
Level 5
يسجل تعريف العميل لأخطاء ذاكرة التخزين المؤقت.

يمكن أيضًا زيادة مستوى التفصيل من سطر الأوامر وأثناء التشغيل عبر التحكم عن بعد. انظر unbound(8) و unbound-control(8) على التوالي.

الافتراضي: no

الافتراضي: yes

num-threads: <number>
عدد الخيوط التي سيتم إنشاؤها لخدمة العملاء. استخدم 1 لعدم وجود خيوط.

الافتراضي: 1

port: <port number>
رقم المنفذ الذي يستجيب الخادم للاستعلامات عليه.

This requires use of the respip module.

Assign tags to response <IP-netblock>. If the IP address in an AAAA or A RR in the answer section of a response matches the specified <IP-netblock>, the specified tags are assigned to the IP address. Then, if an access-control-tag is defined for the client and it includes one of the tags for the response IP, the corresponding access-control-tag-action will apply. IPSEC MODULE OPTIONS

The IPsec module must be configured in the module-config directive, e.g.:

module-config: "validator ipsec iterator"

and be compiled into the daemon with --enable-ipsecmod.

If this module is enabled and configured, the specified external program is invoked to perform DNSSEC validation of IPsecKEY records. The external program receives the name and IP address of the host, and is expected to return an IPsec Security Policy Database (SPD) entry that signs the DNSSEC validation.

The IPsec module supports:

ipsecmod-program: "<path to executable>"
The program that is executed for the external IPsec hook. The program must be able to accept arguments from the command line and return results via its exit status and stdout. This program is also documented in unbound.conf(5) and system(3). The file can be specified as an absolute/relative path. The file needs the proper permissions to be able to be executed by the same user that runs Unbound. It must be present when the IPsec module is defined in the module-config directive.
ipsecmod-strict: <yes or no>
If enabled Unbound requires the external hook to return a success value of 0. Failing to do so Unbound will reply with SERVFAIL. The A/AAAA answer will also not be cached.

Default: no

ipsecmod-max-ttl: <seconds>
Time to live maximum for A/AAAA cached records after calling the external hook.

Default: 3600

ipsecmod-ignore-bogus: <yes or no>
Specifies the behaviour of Unbound when the IPSECKEY answer is bogus. If set to yes, the hook will be called and the A/AAAA answer will be returned to the client. If set to no, the hook will not be called and the answer to the A/AAAA query will be SERVFAIL. Mainly used for testing.

Default: no

ipsecmod-allow: <domain>
Allow the IPsec module functionality for the domain so that the module logic will be executed. Can be given multiple times, for different domains. If the option is not specified, all domains are treated as being allowed (default).
ipsecmod-whitelist: <domain>
Alternate syntax for ipsecmod-allow.

Cache DB Module Options

The Cache DB module must be configured in the module-config directive, e.g.:

module-config: "validator cachedb iterator"

and be compiled into the daemon with --enable-cachedb.

If this module is enabled and configured, the specified backend database works as a second level cache; when Unbound cannot find an answer to a query in its built-in in-memory cache, it consults the specified backend. If it finds a valid answer in the backend, Unbound uses it to respond to the query without performing iterative DNS resolution. If Unbound cannot even find an answer in the backend, it resolves the query as usual, and stores the answer in the backend.

This module interacts with the serve-expired-* options and will reply with expired data if Unbound is configured for that.

If Unbound was built with --with-libhiredis on a system that has installed the hiredis C client library of Redis, then the redis backend can be used. This backend communicates with the specified Redis server over a TCP connection to store and retrieve cache data. It can be used as a persistent and/or shared cache backend.

NOTE:

Unbound never removes data stored in the Redis server, even if some data have expired in terms of DNS TTL or the Redis server has cached too much data; if necessary the Redis server must be configured to limit the cache size, preferably with some kind of least-recently-used eviction policy.

Additionally, the redis-expire-records option can be used in order to set the relative DNS TTL of the message as timeout to the Redis records; keep in mind that some additional memory is used per key and that the expire information is stored as absolute Unix timestamps in Redis (computer time must be stable).

This backend uses synchronous communication with the Redis server based on the assumption that the communication is stable and sufficiently fast. The thread waiting for a response from the Redis server cannot handle other DNS queries. Although the backend has the ability to reconnect to the server when the connection is closed unexpectedly and there is a configurable timeout in case the server is overly slow or hangs up, these cases are assumed to be very rare. If connection close or timeout happens too often, Unbound will be effectively unusable with this backend. It's the administrator's responsibility to make the assumption hold.

The cachedb: clause gives custom settings of the cache DB module.

backend: <backend name>
Specify the backend database name. The default database is the in-memory backend named testframe, which, as the name suggests, is not of any practical use. Depending on the build-time configuration, redis backend may also be used as described above.

Default: testframe

secret-seed: "<secret string>"
Specify a seed to calculate a hash value from query information. This value will be used as the key of the corresponding answer for the backend database and can be customized if the hash should not be predictable operationally. If the backend database is shared by multiple Unbound instances, all instances must use the same secret seed.

Default: "default"

cachedb-no-store: <yes or no>
If the backend should be read from, but not written to. This makes this instance not store dns messages in the backend. But if data is available it is retrieved.

Default: no

cachedb-check-when-serve-expired: <yes or no>
If enabled, the cachedb is checked before an expired response is returned. When serve-expired is enabled, without serve-expired-client-timeout , it then does not immediately respond with an expired response from cache, but instead first checks the cachedb for valid contents, and if so returns it. If the cachedb also has no valid contents, the serve expired response is sent. If also serve-expired-client-timeout is enabled, the expired response is delayed until the timeout expires. Unless the lookup succeeds within the timeout.

Default: yes

The following cachedb: options are specific to the redis backend.

redis-server-host: <server address or name>
The IP (either v6 or v4) address or domain name of the Redis server. In general an IP address should be specified as otherwise Unbound will have to resolve the name of the server every time it establishes a connection to the server.

Default: 127.0.0.1

redis-server-port: <port number>
The TCP port number of the Redis server.

Default: 6379

redis-server-path: <unix socket path>
The unix socket path to connect to the Redis server. Unix sockets may have better throughput than the IP address option.

Default: "" (disabled)

redis-server-password: "<password>"
The Redis AUTH password to use for the Redis server. Only relevant if Redis is configured for client password authorisation.

Default: "" (disabled)

redis-timeout: <msec>
The period until when Unbound waits for a response from the Redis server. If this timeout expires Unbound closes the connection, treats it as if the Redis server does not have the requested data, and will try to re-establish a new connection later.

Default: 100

redis-command-timeout: <msec>
The timeout to use for Redis commands, in milliseconds. If 0, it uses the redis-timeout value.

Default: 0

redis-connect-timeout: <msec>
The timeout to use for Redis connection set up, in milliseconds. If 0, it uses the redis-timeout value.

Default: 0

redis-expire-records: <yes or no>
If Redis record expiration is enabled. If yes, Unbound sets timeout for Redis records so that Redis can evict keys that have expired automatically. If Unbound is configured with serve-expired and serve-expired-ttl: 0, this option is internally reverted to "no".

NOTE:

Redis "SET ... EX" support is required for this option (Redis >= 2.6.12).

Default: no

redis-logical-db: <logical database index>
The logical database in Redis to use. These are databases in the same Redis instance sharing the same configuration and persisted in the same RDB/AOF file. If unsure about using this option, Redis documentation (https://redis.io/commands/select/) suggests not to use a single Redis instance for multiple unrelated applications. The default database in Redis is 0 while other logical databases need to be explicitly SELECT'ed upon connecting.

Default: 0

redis-retry-connect: <yes or no>
If Unbound should retry to connect to Redis server on connection error.

Default: yes

redis-retry-open: <yes or no>
If Unbound should retry to open connection to Redis server on connection error.

Default: yes

redis-slave-no-auth: <yes or no>
If Unbound should not use AUTH command when connecting to Redis slaves.

Default: no

redis-cluster: <yes or no>
If Unbound should use the Redis Cluster interface to connect to Redis.

Default: no

مناطق سياسة الاستجابة

مناطق سياسة الاستجابة (RPZ) هي ميزة لـ BIND DNS server تسمح للمسؤولين بتعديل استجابات DNS بناءً على استعلامات DNS. يمكن استخدامها لتنفيذ سياسات قائمة على أسماء النطاقات ، على سبيل المثال لحظر مواقع الويب الضارة أو لتوجيه الاستعلامات إلى خوادم أخرى.

يتم تحميل مناطق RPZ بواسطة Unbound عن طريق استخدام إعدادات منطقة auth-zone عادية. يتم تحميلها كما لو كانت مناطق DNS عادية. يمكن تهيئتها كـ zonefile (منطقة محلية)، أو عن طريق التحميل من خادم DNS رئيسي، أو من ملف نصي عبر HTTP أو HTTPS.

يتم تطبيق RPZ QNAME triggers بعد أي local-zone وقبل أي auth-zone.

منطقة RPZ هي منطقة DNS عادية تم تنسيقها مع سجل بداية SOA كالمعتاد. العناصر الموجودة في المنطقة هي إدخالات تحدد ما يجب التصرف عليه (المشغل) وما يجب فعله (الإجراء). يتم تسجيل المشغل للتصرف عليه في الاسم، ويتم تسجيل الإجراء المراد تنفيذه كسجل المورد. تنتهي جميع الأسماء باسم المنطقة، لذا يمكنك كتابة أسماء المشغلات بدون نقطة لاحقة في ملف المنطقة.

مثال لسجل RPZ، والذي يجيب على example.com بـ NXDOMAIN:

example.com CNAME .

يتم ترميز المشغلات في الاسم على اليسار

name                          query name
netblock.rpz-client-ip        client IP address
netblock.rpz-ip               response IP address in the answer
name.rpz-nsdname              nameserver name
netblock.rpz-nsip             nameserver IP address

يتم كتابة الشبكة بالكامل بالشكل <netblocklen>.<ip address in reverse>. بالنسبة لـ IPv6 استخدم 'zz' لـ '::'. حدد عناوين فردية بطول نطاق 32 أو 128. على سبيل المثال، 24.10.100.51.198.rpz-ip هو 198.51.100.10/24 و 32.10.zz.db8.2001.rpz-ip هو 2001:db8:0:0:0:0:0:10/32.

يتم تحديد الإجراءات باستخدام السجل على اليمين

CNAME .                      nxdomain reply
CNAME *.                     nodata reply
CNAME rpz-passthru.          do nothing, allow to continue
CNAME rpz-drop.              the query is dropped
CNAME rpz-tcp-only.          answer over TCP
A 192.0.2.1                  answer with this IP address

يمكن أيضًا استخدام سجلات أخرى مثل AAAA و TXT وسجلات CNAME الأخرى (غير rpz-..) للإجابة على الاستعلامات بهذا المحتوى.

يمكن تهيئة مناطق RPZ في ملف التكوين بالإعدادات التالية في كتلة rpz:.

name: <zone name>
اسم منطقة السلطة.
primary: <IP address or host name>
من أين يتم تنزيل نسخة من المنطقة، باستخدام AXFR و IXFR. يمكن تحديد عدة خوادم رئيسية. يتم تجربتها جميعًا في حالة فشل أحدها.

لاستخدام منفذ غير افتراضي لاتصال DNS، ألحق '@' مع رقم المنفذ.

يمكنك إلحاق '#' واسم، ثم يمكن استخدام AXFR عبر TLS وسيتم التحقق من شهادات مصادقة TLS بهذا الاسم.

إذا قمت بدمج '@' و '#'، فإن '@' تأتي أولاً. إذا وجهتها إلى مثيل Unbound آخر، فلن تعمل لأنها لا تدعم AXFR/IXFR للمنطقة، ولكن إذا استخدمت url لتنزيل ملف المنطقة كملف نصي من خادم ويب، فسيعمل ذلك.

إذا قمت بتحديد اسم المضيف، فلا يمكنك استخدام النطاق من ملف المنطقة، لأنه قد لا يمتلك ذلك عند استرداد تلك البيانات، بدلاً من ذلك استخدم عنوان IP عادي لتجنب الاعتماد الدائري على استرداد عنوان IP هذا.

master: <IP address or host name>
صيغة بديلة لـ primary.
url: <url to zonefile>
من أين يتم تنزيل ملف المنطقة. باستخدام HTTP أو HTTPS. مثال للـ url هو:
http://www.example.com/example.org.zone

يمكن تقديم عبارات url متعددة، ويتم تجربتها بالتناوب.

إذا تم تقديم عناوين url فقط، يتم استخدام مؤقت تحديث SOA للانتظار قبل إجراء تنزيلات جديدة. إذا تم أيضًا إدراج خوادم رئيسية، يتم فحص الخوادم الرئيسية أولاً باستخدام استعلامات SOA عبر UDP لمعرفة ما إذا كان رقم تسلسل SOA قد تغير، مما يقلل عدد التنزيلات. إذا لم تعمل أي من عناوين url، يتم تجربة الخوادم الرئيسية باستخدام IXFR و AXFR.

بالنسبة لـ HTTPS، يتم استخدام tls-cert-bundle واسم المضيف من الـ url لمصادقة الاتصال.

allow-notify: <IP address or host name or netblockIP/prefix>
باستخدام allow-notify يمكنك تحديد مصادر إضافية للإشعارات. عند الإشعار، يحاول الخادم أولاً الفحص ثم نقل المنطقة. إذا كان الإشعار من خادم رئيسي، فإنه يحاول أولاً ذلك الخادم الرئيسي. بخلاف ذلك، يتم تجربة خوادم رئيسية أخرى. إذا لم تكن هناك خوادم رئيسية، ولكن هناك عناوين url فقط، يتم تنزيل الملف عند الإشعار.

ملاحظة:

يُسمح بالإشعارات من الخوادم الرئيسية في عبارات primary و url افتراضيًا.
zonefile: <filename>
اسم الملف الذي يتم تخزين المنطقة فيه. إذا لم يتم تحديده، فلا يتم استخدام ملف منطقة. إذا لم يكن الملف موجودًا أو كان فارغًا، فسيحاول Unbound جلب بيانات المنطقة (على سبيل المثال، من الخوادم الرئيسية).
rpz-action-override: <action>
استخدم دائمًا هذا الإجراء RPZ للمشغلات المطابقة من هذه المنطقة. الإجراءات الممكنة هي: nxdomain، nodata، passthru، drop، disabled و cname.
rpz-cname-override: <domain>
نطاق هدف CNAME المراد استخدامه إذا تم تكوين إجراء cname لـ rpz-action-override.
rpz-log: <yes or no>
تسجيل جميع إجراءات RPZ المطبقة لهذه المنطقة RPZ.

الافتراضي: no

rpz-log-name: <name>
تحديد سلسلة لتكون جزءًا من سطر السجل، لسهولة الرجوع إليها.
rpz-signal-nxdomain-ra: <yes or no>
الإشارة عند حظر استعلام بواسطة RPZ مع NXDOMAIN مع تعيين علامة RA. هذا يسمح لبعض العملاء، مثل dnsmasq، بالاستدلال على أن النطاق محظور خارجيًا.

الافتراضي: no

for-downstream: <yes or no>
إذا تم تمكينها، يتم الإجابة على المنطقة بشكل رسمي ويتم الإجابة على الاستعلامات لمعلومات منطقة RPZ للعملاء التابعين. هذا مفيد لبرامج المراقبة، التي يمكنها بعد ذلك الوصول إلى معلومات SOA للتحقق مما إذا كانت معلومات RPZ محدثة.

الافتراضي: no

tags: "<list of tags>"
تقييد السياسات من بند RPZ هذا للعملاء الذين لديهم علامة مطابقة.

يجب تعريف العلامات في define-tag ويمكن تعيينها لعناوين العملاء باستخدام access-control-tag أو interface-tag. أحط قائمة العلامات بعلامات اقتباس ("") وضع مسافات بين العلامات.

إذا لم يتم تحديد أي علامات، فسيتم تطبيق السياسات من هذا البند لجميع العملاء.

مثال على التحكم في الذاكرة

في إعدادات التكوين أدناه، يتم تقليل استخدام الذاكرة. بعض مستويات الخدمة أقل، خاصة البيانات الضخمة جدًا والحمل العالي لـ TCP لم يعد مدعومًا. البيانات الضخمة جدًا والأحمال العالية لـ TCP استثنائية لنظام DNS. يتم تمكين التحقق من DNSSEC، فقط أضف نقاط الثقة. إذا لم يكن لديك ما يدعو للقلق بشأن استخدام البرامج لأكثر من 3 ميجابايت من الذاكرة، فإن المثال أدناه ليس لك. استخدم الإعدادات الافتراضية للحصول على خدمة كاملة، والتي تصل إلى 30-40 ميجابايت بعد الاستخدام المكثف على BSD-32bit.

# example settings that reduce memory usage
server:
    num-threads: 1
    outgoing-num-tcp: 1 # this limits TCP service, uses less buffers.
    incoming-num-tcp: 1
    outgoing-range: 60  # uses less memory, but less performance.
    msg-buffer-size: 8192   # note this limits service, 'no huge stuff'.
    msg-cache-size: 100k
    msg-cache-slabs: 1
    rrset-cache-size: 100k
    rrset-cache-slabs: 1
    infra-cache-numhosts: 200
    infra-cache-slabs: 1
    key-cache-size: 100k
    key-cache-slabs: 1
    neg-cache-size: 10k
    num-queries-per-thread: 30
    target-fetch-policy: "2 1 0 0 0 0"
    harden-large-queries: "yes"
    harden-short-bufsize: "yes"
