unlinkat(2)

unlink(2) دليل استدعاءات النظام unlink(2)

الاسم

unlink, unlinkat - حذف اسم وربما الملف الذي يشير إليه

المكتبة

مكتبة C القياسية (libc، -lc)

الملخص

#include <unistd.h>
int unlink(const char *path);
#include <fcntl.h>           /* تعريف الثوابت AT_* */
#include <unistd.h>
int unlinkat(int dirfd, const char *path, int flags);
متطلبات خاصية الاختبار (Feature Test Macro) لـ glibc (انظر feature_test_macros(7)):

unlinkat():

    منذ glibc 2.10:
        _POSIX_C_SOURCE >= 200809L
    قبل glibc 2.10:
        _ATFILE_SOURCE

الوصف

يقوم unlink() بحذف اسم من نظام الملفات. إذا كان هذا الاسم هو الرابط الأخير لملف ولم تكن هناك عمليات تفتح الملف، يتم حذف الملف وإتاحة المساحة التي كان يشغلها لإعادة الاستخدام.

إذا كان الاسم هو الرابط الأخير لملف ولكن لا تزال هناك عمليات تحتفظ بالملف مفتوحًا، فسيظل الملف موجودًا حتى يتم إغلاق آخر واصف ملف يشير إليه.

إذا كان الاسم يشير إلى رابط رمزي، يتم إزالة الرابط.

إذا كان الاسم يشير إلى مقبس (socket)، أو FIFO، أو جهاز، يتم إزالة الاسم الخاص به ولكن يمكن للعمليات التي لديها الكائن مفتوحًا الاستمرار في استخدامه.

unlinkat()

تعمل استدعاءات النظام unlinkat() بنفس طريقة عمل unlink() أو rmdir(2) (حسب ما إذا كانت flags تتضمن العلم AT_REMOVEDIR أم لا) باستثناء الاختلافات الموضحة هنا.

إذا كان path نسبيًا، فسيتم تفسيره بالنسبة للدليل الذي تشير إليه واصف الملف dirfd (بدلاً من تفسيره بالنسبة لدليل العمل الحالي للعملية المستدعية، كما يفعل unlink() و rmdir(2) لمسار نسبي).

إذا كان path نسبيًا وكان dirfd هو القيمة الخاصة AT_FDCWD، فسيتم تفسير path بالنسبة لدليل العمل الحالي للعملية المستدعية (مثل unlink() و rmdir(2)).

إذا كان path مطلقًا، فسيتم تجاهل dirfd.

flags هي قناع بت يمكن تحديده كـ 0، أو عن طريق ORing قيم الأعلام التي تتحكم في عملية unlinkat(). حاليًا، هناك علم واحد فقط محدد:

AT_REMOVEDIR
افتراضيًا، يقوم unlinkat() بتنفيذ ما يعادل unlink() على path. إذا تم تحديد العلم AT_REMOVEDIR، فإنه ينفذ ما يعادل rmdir(2) على path.

انظر openat(2) لشرح الحاجة إلى unlinkat().

قيمة الإرجاع

عند النجاح، يتم إرجاع صفر. عند الخطأ، يتم إرجاع -1، ويتم تعيين errno للإشارة إلى الخطأ.

الأخطاء

EACCES
لا يُسمح بالوصول للكتابة إلى الدليل الذي يحتوي على path لمعرف المستخدم الفعال للعملية، أو أن أحد الأدلة في path لم يسمح بإذن البحث. (انظر أيضًا path_resolution(7)).
EBUSY
لا يمكن إلغاء ربط path لأنه قيد الاستخدام من قبل النظام أو عملية أخرى؛ على سبيل المثال، هو نقطة تحميل (mount point) أو أن برنامج عميل NFS قام بإنشائه لتمثيل inode نشط ولكن بدون اسم ("NFS silly renamed").
EFAULT
path يشير إلى خارج مساحة العنوان القابلة للوصول الخاصة بك.
EIO
حدث خطأ إدخال/إخراج.
EISDIR
path يشير إلى دليل. (هذه هي القيمة غير المتوافقة مع POSIX التي يتم إرجاعها منذ Linux 2.1.132).
ELOOP
تم اكتشاف عدد كبير جدًا من الروابط الرمزية أثناء ترجمة path.
ENAMETOOLONG
path كان طويلاً جدًا.
ENOENT
أحد المكونات في path غير موجود أو رابط رمزي معلق، أو أن path فارغ.
ENOMEM
كانت ذاكرة النواة المتاحة غير كافية.
ENOTDIR
أحد المكونات المستخدم كدليل في path ليس في الواقع دليلًا.
EPERM
النظام لا يسمح بإلغاء ربط الأدلة، أو أن إلغاء ربط الأدلة يتطلب صلاحيات لا تمتلكها العملية المستدعية. (هذا هو الخطأ الموصوف في POSIX؛ كما لوحظ أعلاه، يعيد Linux EISDIR لهذه الحالة).
EPERM (Linux فقط)
نظام الملفات لا يسمح بإلغاء ربط الملفات.
EPERM أو EACCES
الدليل الذي يحتوي على path لديه بت اللصق (S_ISVTX) معين ومعرف المستخدم الفعال للعملية ليس هو معرف المستخدم للملف المراد حذفه ولا معرف الدليل الذي يحتوي عليه، والعملية ليست ذات صلاحيات (Linux: لا تمتلك القدرة CAP_FOWNER).
EPERM
الملف المراد إلغاء ربطه معلم على أنه غير قابل للتغيير (immutable) أو قابل للإلحاق فقط (append-only). (انظر FS_IOC_SETFLAGS(2const).)
EROFS
path يشير إلى ملف على نظام ملفات للقراءة فقط.

نفس الأخطاء التي تحدث لـ unlink() و rmdir(2) يمكن أن تحدث أيضًا لـ unlinkat(). يمكن أن تحدث الأخطاء الإضافية التالية لـ unlinkat():

EBADF
path نسبي ولكن dirfd ليس AT_FDCWD ولا واصف ملف صالح.
EINVAL
تم تحديد قيمة علم غير صالحة في flags.
EISDIR
path يشير إلى دليل، ولم يتم تحديد AT_REMOVEDIR في flags.
ENOTDIR
path نسبي و dirfd هو واصف ملف يشير إلى ملف بخلاف الدليل.

المعايير

POSIX.1-2024.

التاريخ

unlink()
SVr4, 4.3BSD, POSIX.1-2001.
unlinkat()
POSIX.1-2008. Linux 2.6.16, glibc 2.4.

glibc

في الأنوية القديمة حيث unlinkat() غير متوفر، تعود وظيفة الغلاف glibc إلى استخدام unlink() أو rmdir(2). عندما يكون path نسبيًا، تقوم glibc ببناء مسار استنادًا إلى الرابط الرمزي في /proc/self/fd الذي يتوافق مع الوسيط dirfd.

الأخطاء

يمكن أن تتسبب العيوب في البروتوكول الأساسي لـ NFS في اختفاء غير متوقع للملفات التي لا تزال قيد الاستخدام.
