UNLINK(3P) دليل مبرمج POSIX UNLINK(3P)

المقدمة

هذه الصفحة اليدوية جزء من دليل مبرمج POSIX. قد يختلف تطبيق Linux لهذا الواجهة (راجع صفحة Linux اليدوية المقابلة لتفاصيل سلوك Linux)، أو قد لا يتم تطبيق الواجهة على Linux.

الاسم

unlink, unlinkat — إزالة إدخال دليل

الملخص

#include <unistd.h>
int unlink(const char *path);
#include <fcntl.h>
int unlinkat(int fd, const char *path, int flag);

الوصف

تقوم الدالة unlink() بإزالة رابط لملف. إذا كان path يشير إلى رابط رمزي، فإن unlink() تزيل الرابط الرمزي المسمى path ولن تؤثر على أي ملف أو دليل مسمى بمحتويات الرابط الرمزي. بخلاف ذلك، تزيل unlink() الرابط المسمى بمسار الملف المشار إليه بواسطة path وتقوم بتقليل عدد روابط الملف المشار إليه بواسطة الرابط.

عندما يصبح عدد روابط الملف صفرًا ولا توجد عملية تملك الملف مفتوحًا، يتم تحرير المساحة التي يشغلها الملف ولا يعود الملف قابلاً للوصول. إذا كانت هناك عملية واحدة أو أكثر تملك الملف مفتوحًا عند إزالة الرابط الأخير، تتم إزالة الرابط قبل أن تعود unlink()، ولكن سيتم تأجيل إزالة محتويات الملف حتى يتم إغلاق جميع المراجع للملف.

لا يجب أن يشير الوسيط path إلى دليل ما لم يكن لدى العملية امتيازات مناسبة ويدعم التنفيذ استخدام unlink() على الأدلة.

عند الانتهاء بنجاح، تقوم unlink() بتمييز آخر تعديل للبيانات وآخر تغيير لحالة الملف في الدليل الأب ليتم تحديثهما. أيضًا، إذا لم يكن عدد روابط الملف صفرًا، فسيتم تمييز آخر تغيير لحالة الملف ليتم تحديثه.

تكون الدالة unlinkat() مكافئة لدالة unlink() أو rmdir() باستثناء الحالة التي يحدد فيها path مسارًا نسبيًا. في هذه الحالة، يتم تحديد إدخال الدليل المراد إزالته بالنسبة للدليل المرتبط بمُعرّف الملف fd بدلاً من الدليل الحالي العامل. إذا كان وضع الوصول لوصف الملف المفتوح المرتبط بمُعرّف الملف ليس O_SEARCH، فستقوم الدالة بالتحقق مما إذا كانت عمليات البحث في الأدلة مسموح بها باستخدام الأذونات الحالية للدليل الأساسي لمُعرّف الملف. إذا كان وضع الوصول هو O_SEARCH، فلن تقوم الدالة بالتحقق.

يتم بناء القيم الخاصة بـ flag عن طريق OR منطقي شامل للعلامات من القائمة التالية، المعرفة في <fcntl.h>:

AT_REMOVEDIR

إزالة إدخال الدليل المحدد بواسطة fd و path كدليل، وليس كملف عادي.

إذا تم تمرير القيمة الخاصة AT_FDCWD إلى unlinkat() في الوسيط fd، فسيتم استخدام الدليل الحالي العامل وسيكون السلوك مطابقًا لاستدعاء unlink() أو rmdir() على التوالي، اعتمادًا على ما إذا كانت بت AT_REMOVEDIR مضبوطة في flag أم لا.

قيمة الإرجاع

عند الانتهاء بنجاح، تعيد هذه الدوال 0. بخلاف ذلك، تعيد هذه الدوال -1 وتعيّن errno للإشارة إلى الخطأ. إذا تم إرجاع -1، فلن يتم تغيير الملف المسمى.

الأخطاء

تفشل هذه الدوال ولا تزيل الملف إذا:

EACCES
تم رفض إذن البحث عن جزء من بادئة المسار، أو تم رفض إذن الكتابة على الدليل الذي يحتوي على إدخال الدليل المراد إزالته.
EBUSY
لا يمكن إزالة الملف المسمى بالوسيط path لأنه قيد الاستخدام من قبل النظام أو عملية أخرى ويعتبر التنفيذ هذا خطأ.
ELOOP
توجد حلقة في الروابط الرمزية التي تم مواجهتها أثناء حل الوسيط path.
ENAMETOOLONG

طول جزء من اسم المسار أطول من {NAME_MAX}.
ENOENT
جزء من path لا يسمي ملفًا موجودًا أو path سلسلة فارغة.
ENOTDIR
جزء من بادئة المسار يسمي ملفًا موجودًا ليس دليلًا ولا رابطًا رمزيًا لدليل، أو يحتوي الوسيط path على حرف واحد على الأقل غير <slash> وينتهي بحرف <slash> واحد أو أكثر، ويسمي جزء اسم المسار الأخير ملفًا موجودًا ليس دليلًا ولا رابطًا رمزيًا لدليل.
EPERM
الملف المسمى بواسطة path هو دليل، ولا يمتلك العملية المستدعية الامتيازات المناسبة، أو يمنع التنفيذ استخدام unlink() على الأدلة.
EPERM أو EACCES

تم تعيين علامة S_ISVTX على الدليل الذي يحتوي على الملف المشار إليه بواسطة الوسيط path ولا تستوفي العملية المعايير المحددة في مجلد التعريفات الأساسية من POSIX.1-2017، القسم 4.3، حماية الدليل.
EROFS
إدخال الدليل المراد إزالته هو جزء من نظام ملفات للقراءة فقط.

تفشل الدالة unlinkat() إذا:

EACCES
وضع الوصول لوصف الملف المفتوح المرتبط بـ fd ليس O_SEARCH ولا تسمح أذونات الدليل الأساسي لـ fd بعمليات البحث في الأدلة.
EBADF
الوسيط path لا يحدد مسارًا مطلقًا و fd ليس AT_FDCWD أو مُعرّف ملف صالح مفتوح للقراءة أو البحث.
ENOTDIR
الوسيط path ليس مسارًا مطلقًا و fd هو مُعرّف ملف مرتبط بملف غير دليل.
EEXIST أو ENOTEMPTY

تم تعيين بت AT_REMOVEDIR على الوسيط flag ويسمي الوسيط path دليلًا ليس دليلًا فارغًا، أو توجد روابط صلبة للدليل بخلاف نقطة أو إدخال واحد في نقطة.
ENOTDIR
تم تعيين بت AT_REMOVEDIR على الوسيط flag و path لا يسمي دليلًا.

قد تفشل هذه الدوال ولا تزيل الملف إذا:

EBUSY
الملف المسمى بواسطة path هو STREAM مسمى.
ELOOP
تمت مواجهة أكثر من {SYMLOOP_MAX} رابط رمزي أثناء حل الوسيط path.
ENAMETOOLONG

يتجاوز طول اسم المسار {PATH_MAX}، أو نتج عن حل اسم المسار لرابط رمزي نتيجة وسيطة يتجاوز طولها {PATH_MAX}.
ETXTBSY
الإدخال المراد إزالته هو آخر إدخال دليل لملف إجراء نقي (نص مشترك) يتم تنفيذه.

قد تفشل الدالة unlinkat() إذا:

EINVAL
قيمة الوسيط flag غير صالحة.

unlink(3p) — man pages

PROLOG

This page is a manual page for the Linux utility unlink. It is a wrapper around the POSIX function unlink() and is intended for use by shell scripts.

NAME

unlink — remove a file or directory entry

SYNOPSIS

#include <unistd.h>

int unlink(const char *pathname);

DESCRIPTION

The unlink() function shall remove a link to a file. If the most [last] link to a file is removed, the file itself shall be destroyed. If the last link to a file was removed and no process has the file open, the space occupied by the file shall be freed.

If pathname refers to a symbolic link, unlink() shall remove the symbolic link name, and not the file or directory to which the link points.

If pathname is a non-empty directory, unlink() shall fail.

If pathname refers to a directory, the behavior is implementation-defined. Historically, it has been allowed for the superuser to unlink a directory. In many historical implementations, unlinking a directory required it to be empty.

The unlinkat() function shall be equivalent to the unlink() function except that if pathname specifies a relative path, the file is interpreted relative to the directory referred to by the file descriptor dirfd (rather than as a normal relative path from the current working directory). If pathname specifies a relative path, the behavior of unlinkat() is the same as unlink() if dirfd is AT_FDCWD.

An unlinkat() call in which dirfd is the file descriptor associated with a directory, and pathname is not specified as an absolute path, shall remove the directory entry (link) named by pathname within that directory. If pathname is specified as an absolute path, the value of dirfd is ignored.

Otherwise, the behavior of unlinkat() is the same as unlink().

The unlinkat() function shall support the same functionality as unlink() when flags is 0.

The unlinkat() function shall support the same functionality as unlink() when flags is AT_REMOVEDIR, and the link named by pathname refers to a directory. In this case, the directory shall be removed. The directory must be empty, and the directory must not be the current working directory of any process. The directory must not be the root directory of any process. The directory must not be the mount point of any file system. The directory must not be in use by any process.

When flags is AT_REMOVEDIR, the value of pathname is interpreted relative to the directory referred to by dirfd. If pathname specifies an absolute path, dirfd is ignored.

The unlinkat() function shall support the same functionality as unlink() when flags has any other value. If flags contains values other than 0 or AT_REMOVEDIR, or values that are not permitted, the behavior is undefined.

The unlinkat() function shall fail if any of the following conditions occur:

[EACCES]
Search permission was not denied for a component of the prefix of pathname that is a directory, or write access was denied for a directory in which a link is to be deleted.
[EBADF]
The pathname argument does not specify an absolute path, and the dirfd argument is not a valid file descriptor, or dirfd is not open for search access to the directory.
[EBUSY]
The directory named by pathname is the root directory of a mounted file system, or the directory named by pathname is currently in use.
[DIRFD_AT_FDCWD]
The pathname argument is not an absolute path, and dirfd is AT_FDCWD, and the file described by pathname is not found.
[EINVAL]
The dirfd argument is not valid.
[EISDIR]
The named file is a directory, and the caller does not have appropriate privileges (that is, the caller is not the superuser).
[ELOOP]
A loop is detected in the path. More than {LINK_MAX} links exist to the file named by pathname.
[ENAMETOOLONG]
The length of the pathname argument exceeds {PATH_MAX}.
[ENOENT]
The named file does not exist, or the pathname argument is an empty string. Or, the dirfd argument is not valid.
[ENOTDIR]
A component of pathname is not a directory, or the dirfd argument refers to a file other than a directory, or pathname is not an absolute path and dirfd is AT_FDCWD and the file referenced by dirfd is not a directory.
[EPERM]
The named file is a directory, and the caller does not have appropriate privileges (that is, the caller is not the superuser).
[EROFS]
The named file resides on a read-only file system.
[ETXTBSY]
The file is a regular file that is currently being executed. This error may or may not be returned.

The unlinkat() function shall fail if any of the following conditions occur:

[EACCES]
Search permission was not denied for a component of the prefix of pathname that is a directory, or write access was denied for a directory in which a link is to be deleted.
[EBADF]
The pathname argument does not specify an absolute path, and the dirfd argument is not a valid file descriptor, or dirfd is not open for search access to the directory.
[EBUSY]
The directory named by pathname is the root directory of a mounted file system, or the directory named by pathname is currently in use.
[DIRFD_AT_FDCWD]
The pathname argument is not an absolute path, and dirfd is AT_FDCWD, and the file described by pathname is not found.
[EINVAL]
The dirfd argument is not valid.
[EISDIR]
The named file is a directory, and the caller does not have appropriate privileges (that is, the caller is not the superuser).
[ELOOP]
A loop is detected in the path. More than {LINK_MAX} links exist to the file named by pathname.
[ENAMETOOLONG]
The length of the pathname argument exceeds {PATH_MAX}.
[ENOENT]
The named file does not exist, or the pathname argument is an empty string. Or, the dirfd argument is not valid.
[ENOTDIR]
A component of pathname is not a directory, or the dirfd argument refers to a file other than a directory, or pathname is not an absolute path and dirfd is AT_FDCWD and the file referenced by dirfd is not a directory.
[EPERM]
The named file is a directory, and the caller does not have appropriate privileges (that is, the caller is not the superuser).
[EROFS]
The named file resides on a read-only file system.
[ETXTBSY]
The file is a regular file that is currently being executed. This error may or may not be returned.

RETURN VALUE

Upon successful completion, 0 shall be returned. Otherwise, -1 shall be returned and errno set to indicate the error.

ERRORS

The unlink() function shall fail if:

[EACCES]
Search permission was not denied for a component of the prefix of pathname that is a directory, or write access was denied for a directory in which a link is to be deleted.
[EBUSY]
The named file is a directory that is currently in use. (This is implementation-defined.)
[EDQUOT]
The file resides on a device with which there is no space left.
[EINTR]
A signal was caught during the execution of this function.
[EPERM]
The named file is a directory, and the caller does not have appropriate privileges (that is, the caller is not the superuser).
[ELOOP]
A loop is detected in the path. More than {LINK_MAX} links exist to the file named by pathname.
[ENAMETOOLONG]
The length of the pathname argument exceeds {PATH_MAX}.
[ENOENT]
The named file does not exist, or the pathname argument is an empty string.
[ENOTDIR]
A component of pathname is not a directory.
[EROFS]
The named file resides on a read-only file system.
[ETXTBSY]
The file is a regular file that is currently being executed. This error may or may not be returned.

EXAMPLES

The following example fragment removes the file named
/modules/pass1.

#include <unistd.h>
char *path = "/modules/pass1";
int   status;
...
status = unlink(path);

Checking for an Error

The following example fragment creates a temporary password lock file named LOCKFILE, which is defined as /etc/ptmp, and gets a file descriptor for it. If the file cannot be opened for writing, unlink() is used to remove the link between the file descriptor and LOCKFILE.

#include <sys/types.h>
#include <stdio.h>
#include <fcntl.h>
#include <errno.h>
#include <unistd.h>
#include <sys/stat.h>
#define LOCKFILE "/etc/ptmp"
int pfd;  /* Integer for file descriptor returned by open call. */
FILE *fpfd;  /* File pointer for use in putpwent(). */
...
/* Open password Lock file. If it exists, this is an error. */
if ((pfd = open(LOCKFILE, O_WRONLY| O_CREAT | O_EXCL, S_IRUSR
    | S_IWUSR | S_IRGRP | S_IROTH)) == -1)  {
    fprintf(stderr, "Cannot open /etc/ptmp. Try again later.\n");
    exit(1);
}
/* Lock file created; proceed with fdopen of lock file so that
   putpwent() can be used.
 */
if ((fpfd = fdopen(pfd, "w")) == NULL) {
    close(pfd);
    unlink(LOCKFILE);
    exit(1);
}

Replacing Files

The following example fragment uses unlink() to discard links to files, so that they can be replaced with new versions of the files. The first call removes the link to LOCKFILE if an error occurs. Successive calls remove the links to SAVEFILE and PASSWDFILE so that new links can be created, then removes the link to LOCKFILE when it is no longer needed.

#include <sys/types.h>
#include <stdio.h>
#include <fcntl.h>
#include <errno.h>
#include <unistd.h>
#include <sys/stat.h>
#define LOCKFILE "/etc/ptmp"
#define PASSWDFILE "/etc/passwd"
#define SAVEFILE "/etc/opasswd"
...
/* If no change was made, assume error and leave passwd unchanged. */
if (!valid_change) {
    fprintf(stderr, "Could not change password for user %s\n", user);
    unlink(LOCKFILE);
    exit(1);
}
/* Change permissions on new password file. */
chmod(LOCKFILE, S_IRUSR | S_IRGRP | S_IROTH);
/* Remove saved password file. */
unlink(SAVEFILE);
/* Save current password file. */
link(PASSWDFILE, SAVEFILE);
/* Remove current password file. */
unlink(PASSWDFILE);
/* Save new password file as current password file. */
link(LOCKFILE,PASSWDFILE);
/* Remove lock file. */
unlink(LOCKFILE);
exit(0);

APPLICATION USAGE

Applications should use rmdir() to remove a directory.

RATIONALE

Unlinking a directory is restricted to the superuser in many historical implementations for reasons given in link() (see also rename()).

The meaning of [EBUSY] in historical implementations is ``mount point busy''. Since this volume of POSIX.1‐2017 does not cover the system administration concepts of mounting and unmounting, the description of the error was changed to ``resource busy''. (This meaning is used by some device drivers when a second process tries to open an exclusive use device.) The wording is also intended to allow implementations to refuse to remove a directory if it is the root or current working directory of any process.

The standard developers reviewed TR 24715‐2006 and noted that LSB-conforming implementations may return [EISDIR] instead of [EPERM] when unlinking a directory. A change to permit this behavior by changing the requirement for [EPERM] to [EPERM] or [EISDIR] was considered, but decided against since it would break existing strictly conforming and conforming applications. Applications written for portability to both POSIX.1‐2008 and the LSB should be prepared to handle either error code.

The purpose of the unlinkat() function is to remove directory entries in directories other than the current working directory without exposure to race conditions. Any part of the path of a file could be changed in parallel to a call to unlink(), resulting in unspecified behavior. By opening a file descriptor for the target directory and using the unlinkat() function it can be guaranteed that the removed directory entry is located relative to the desired directory.
