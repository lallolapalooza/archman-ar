الاسم

user_namespaces - نظرة عامة على مساحات أسماء المستخدم في لينكس

الوصف

للحصول على نظرة عامة على مساحات الأسماء، راجع namespaces(7).

تقوم مساحات أسماء المستخدم بعزل المعرفات والسمات المتعلقة بالأمان، وبشكل خاص، معرفات المستخدم والمجموعة (انظر credentials(7))، المجلد الجذر، المفاتيح (انظر keyrings(7))، والصلاحيات (انظر capabilities(7)). يمكن أن تكون معرفات المستخدم والمجموعة الخاصة بالعملية مختلفة داخل وخارج مساحة اسم المستخدم. على وجه الخصوص، يمكن أن يكون للعملية معرف مستخدم عادي غير مميز خارج مساحة اسم المستخدم بينما يكون في نفس الوقت معرف مستخدم 0 داخل مساحة الاسم؛ بمعنى آخر، تمتلك العملية صلاحيات كاملة للعمليات داخل مساحة اسم المستخدم، ولكنها غير مميزة للعمليات خارج مساحة الاسم.

مساحات الأسماء المتداخلة، عضوية مساحة الاسم

يمكن تداخل مساحات أسماء المستخدم؛ أي أن كل مساحة اسم مستخدم — باستثناء مساحة الاسم الأولية ("الجذر") — لها مساحة اسم مستخدم أب، ويمكن أن يكون لها صفر أو أكثر من مساحات أسماء المستخدم الفرعية. مساحة اسم المستخدم الأب هي مساحة اسم المستخدم الخاصة بالعملية التي تنشئ مساحة اسم المستخدم عبر استدعاء إلى unshare(2) أو clone(2) مع العلامة CLONE_NEWUSER.

يفرض النواة (منذ لينكس 3.11) حدًا أقصى يبلغ 32 مستوى من مساحات أسماء المستخدم المتداخلة. تفشل استدعاءات unshare(2) أو clone(2) التي قد تتجاوز هذا الحد بخطأ EUSERS.

كل عملية هي عضو في مساحة اسم مستخدم واحدة بالضبط. العملية التي تم إنشاؤها عبر fork(2) أو clone(2) بدون العلامة CLONE_NEWUSER هي عضو في نفس مساحة اسم المستخدم مثل أبويتها. يمكن لعملية أحادية الخيط الانضمام إلى مساحة اسم مستخدم أخرى باستخدام setns(2) إذا كانت تمتلك CAP_SYS_ADMIN في تلك المساحة؛ عند القيام بذلك، تكتسب مجموعة كاملة من الصلاحيات في تلك المساحة.

يجعل استدعاء clone(2) أو unshare(2) مع العلامة CLONE_NEWUSER العملية الابنة الجديدة (لـ clone(2)) أو المتصل (لـ unshare(2)) عضوًا في مساحة اسم المستخدم الجديدة التي تم إنشاؤها بواسطة الاستدعاء.

يمكن استخدام عملية ioctl(2) NS_GET_PARENT لاكتشاف العلاقة الأبوية بين مساحات أسماء المستخدم؛ راجع ioctl_nsfs(2).

مهمة تغير إحدى معرفاتها الفعالة ستعيد قابلية تفريغها إلى القيمة الموجودة في /proc/sys/fs/suid_dumpable. قد يؤثر هذا على ملكية ملفات proc للعمليات الفرعية وقد يتسبب بالتالي في افتقار العملية الأم للصلاحيات للكتابة إلى ملفات التعيين للعمليات الفرعية التي تعمل في مساحة اسم مستخدم جديدة. في مثل هذه الحالات، جعل العملية الأم قابلة للتفريغ، باستخدام PR_SET_DUMPABLE في استدعاء لـ prctl(2)، قبل إنشاء عملية فرعية في مساحة اسم مستخدم جديدة قد يصحح هذه المشكلة. راجع prctl(2) و proc(5) للحصول على تفاصيل حول كيفية تأثر الملكية.

الصلاحيات

تبدأ العملية الابنة التي تم إنشاؤها بواسطة clone(2) مع العلامة CLONE_NEWUSER بمجموعة كاملة من الصلاحيات في مساحة اسم المستخدم الجديدة. وبالمثل، فإن العملية التي تنشئ مساحة اسم مستخدم جديدة باستخدام unshare(2) أو تنضم إلى مساحة اسم مستخدم موجودة باستخدام setns(2) تكتسب مجموعة كاملة من الصلاحيات في تلك المساحة. من ناحية أخرى، ليس لتلك العملية أي صلاحيات في مساحة اسم المستخدم الأب (في حالة clone(2)) أو السابق (في حالة unshare(2) و setns(2))، حتى لو تم إنشاء مساحة الاسم الجديدة أو الانضمام إليها بواسطة المستخدم الجذر (أي، عملية بمعرف مستخدم 0 في مساحة الاسم الجذر).

لاحظ أن استدعاء execve(2) سيؤدي إلى إعادة حساب صلاحيات العملية بالطريقة المعتادة (انظر capabilities(7)). ونتيجة لذلك، ما لم يكن لدى العملية معرف مستخدم 0 داخل مساحة الاسم، أو كان الملف التنفيذي لديه قناع صلاحيات قابل للتوريث غير فارغ، ستفقد العملية جميع الصلاحيات. انظر المناقشة حول تعيينات معرفات المستخدم والمجموعة، أدناه.

استدعاء clone(2) أو unshare(2) باستخدام العلامة CLONE_NEWUSER أو استدعاء setns(2) الذي ينقل المتصل إلى مساحة اسم مستخدم أخرى يقوم بتعيين علامات "securebits" (انظر capabilities(7)) إلى قيمها الافتراضية (جميع العلامات معطلة) في الابنة (لـ clone(2)) أو المتصل (لـ unshare(2) أو setns(2)). لاحظ أنه نظرًا لأن المتصل لم يعد لديه صلاحيات في مساحة اسم المستخدم الأصلية بعد استدعاء setns(2)، فإنه ليس من الممكن لعملية إعادة تعيين علامات "securebits" الخاصة بها مع الاحتفاظ بعضوية مساحة اسم المستخدم الخاصة بها عن طريق استخدام زوج من استدعاءات setns(2) للانتقال إلى مساحة اسم مستخدم أخرى ثم العودة إلى مساحة اسم المستخدم الأصلية.

قواعد تحديد ما إذا كانت العملية تمتلك صلاحية في مساحة اسم مستخدم معينة أم لا هي كما يلي:

•
تمتلك العملية صلاحية داخل مساحة اسم مستخدم إذا كانت عضوًا في تلك المساحة وتمتلك الصلاحية في مجموعة صلاحياتها الفعالة. يمكن للعملية اكتساب صلاحيات في مجموعة صلاحياتها الفعالة بطرق مختلفة. على سبيل المثال، قد تقوم بتنفيذ برنامج مضبوط بالمعرف المستخدم أو ملف تنفيذي بصلاحيات ملف مرتبطة. بالإضافة إلى ذلك، قد تكتسب العملية صلاحيات عبر تأثير clone(2) أو unshare(2) أو setns(2)، كما هو موضح بالفعل.
•
إذا كانت العملية تمتلك صلاحية في مساحة اسم مستخدم، فإنها تمتلك تلك الصلاحية في جميع مساحات الأسماء الفرعية (والأحفاد الأبعد) أيضًا.
•
عند إنشاء مساحة اسم مستخدم، يسجل النواة معرف المستخدم الفعال للعملية المنشئة على أنه "مالك" مساحة الاسم. العملية التي تتواجد في الأب لمساحة اسم المستخدم والتي يتطابق معرف المستخدم الفعال الخاص بها مع مالك مساحة الاسم تمتلك جميع الصلاحيات في مساحة الاسم. بحكم القاعدة السابقة، هذا يعني أن العملية تمتلك جميع الصلاحيات في جميع مساحات أسماء المستخدم الفرعية الأبعد أيضًا. يمكن استخدام عملية ioctl(2) NS_GET_OWNER_UID لاكتشاف معرف المستخدم لمالك مساحة الاسم؛ راجع ioctl_nsfs(2).

تأثير الصلاحيات داخل مساحة اسم المستخدم

امتلاك صلاحية داخل مساحة اسم مستخدم يسمح للعملية بتنفيذ عمليات (تتطلب امتيازات) فقط على الموارد التي تحكمها تلك المساحة. بمعنى آخر، يسمح امتلاك صلاحية في مساحة اسم مستخدم للعملية بتنفيذ عمليات مميزة على الموارد التي تحكمها مساحات الأسماء (غير المستخدم) المملوكة (المرتبطة) بمساحة اسم المستخدم (انظر القسم التالي).

من ناحية أخرى، هناك العديد من العمليات المميزة التي تؤثر على الموارد التي لا ترتبط بأي نوع من مساحات الأسماء، على سبيل المثال، تغيير وقت النظام (أي الوقت التقويمي) (تحكمه CAP_SYS_TIME)، تحميل وحدة نواة (تحكمه CAP_SYS_MODULE)، وإنشاء جهاز (تحكمه CAP_MKNOD). فقط عملية ذات امتيازات في مساحة اسم المستخدم *الأولية* يمكنها تنفيذ مثل هذه العمليات.

يمتلك CAP_SYS_ADMIN داخل مساحة اسم المستخدم التي تمتلك مساحة اسم تحميل العملية يسمح لتلك العملية بإنشاء تركيبات ربط وتركيب أنواع أنظمة الملفات التالية:

•
/proc (منذ لينكس 3.8)
•
/sys (منذ لينكس 3.8)
•
devpts (منذ لينكس 3.9)
•
tmpfs(5) (منذ لينكس 3.9)
•
ramfs (منذ لينكس 3.9)
•
mqueue (منذ لينكس 3.9)
•
bpf (منذ لينكس 4.4)
•
overlayfs (منذ لينكس 5.11)

يسمح امتلاك CAP_SYS_ADMIN ضمن نطاق المستخدم الذي يمتلك نطاق cgroup الخاص بالعملية (منذ لينكس 4.6) لهذه العملية بتركيب نظام ملفات cgroup الإصدار 2 والهرميات المسماة cgroup الإصدار 1 (أي، أنظمة ملفات cgroup التي تم تركيبها باستخدام الخيار "none,name=").

يسمح امتلاك CAP_SYS_ADMIN ضمن نطاق المستخدم الذي يمتلك نطاق PID الخاص بالعملية (منذ لينكس 3.8) لهذه العملية بتركيب أنظمة ملفات /proc.

ومع ذلك، لا يمكن تركيب أنظمة الملفات المستندة إلى الكتل إلا بواسطة عملية تمتلك CAP_SYS_ADMIN في نطاق المستخدم الأولي.

تفاعل نطاقات المستخدم وأنواع النطاقات الأخرى

منذ لينكس 3.8، يمكن للعمليات غير المميزة إنشاء نطاقات مستخدم، ويمكن إنشاء أنواع النطاقات الأخرى باستخدام القدرة CAP_SYS_ADMIN فقط في نطاق المستخدم للمتصل.

عند إنشاء نطاق غير مستخدم، فإنه مملوك لنطاق المستخدم الذي كانت العملية المنشئة عضواً فيه وقت إنشاء النطاق. تتطلب العمليات المميزة على الموارد التي يحكمها النطاق غير المستخدم أن تمتلك العملية القدرات اللازمة في نطاق المستخدم الذي يمتلك النطاق غير المستخدم.

إذا تم تحديد CLONE_NEWUSER مع علامات CLONE_NEW* الأخرى في استدعاء clone(2) أو unshare(2) واحد، فمن المضمون إنشاء نطاق المستخدم أولاً، مما يمنح الطفل (clone(2)) أو المتصل (unshare(2)) امتيازات على النطاقات المتبقية التي تم إنشاؤها بواسطة الاستدعاء. وبالتالي، من الممكن لمتصل غير مميز تحديد هذا المزيج من العلامات.

عند إنشاء نطاق جديد (بخلاف نطاق المستخدم) عبر clone(2) أو unshare(2)، يسجل النواة نطاق المستخدم للعملية المنشئة كمالك للنطاق الجديد. (لا يمكن تغيير هذا الارتباط.) عندما تقوم عملية في النطاق الجديد لاحقًا بإجراء عمليات مميزة تعمل على الموارد العالمية المعزولة بواسطة النطاق، يتم إجراء فحوصات الأذونات وفقًا لقدرات العملية في نطاق المستخدم الذي ارتبطت به النواة بالنطاق الجديد. على سبيل المثال، لنفترض أن عملية تحاول تغيير اسم المضيف (sethostname(2))، وهو مورد يحكمه نطاق UTS. في هذه الحالة، ستحدد النواة نطاق المستخدم الذي يمتلك نطاق UTS الخاص بالعملية، وتتحقق مما إذا كانت العملية تمتلك القدرة المطلوبة (CAP_SYS_ADMIN) في نطاق المستخدم هذا.

يمكن استخدام عملية ioctl(2) المسماة NS_GET_USERNS لاكتشاف نطاق المستخدم الذي يمتلك نطاقًا غير مستخدم؛ انظر ioctl_nsfs(2).

تعيينات معرفات المستخدم والمجموعة: uid_map و gid_map

عند إنشاء نطاق مستخدم، فإنه يبدأ بدون تعيين لمعرفات المستخدم (معرفات المجموعة) إلى نطاق المستخدم الأصل. تعرض الملفات /proc/pid/uid_map و /proc/pid/gid_map (المتوفرة منذ لينكس 3.5) تعيينات معرفات المستخدم والمجموعة داخل نطاق المستخدم للعملية pid. يمكن قراءة هذه الملفات لعرض التعيينات في نطاق المستخدم وكتابتها (مرة واحدة) لتحديد التعيينات.

يشرح الوصف في الفقرات التالية التفاصيل الخاصة بـ uid_map؛ gid_map هو نفسه تمامًا، ولكن يتم استبدال كل ظهور لـ "معرف المستخدم" بـ "معرف المجموعة".

يعرض ملف uid_map تعيين معرفات المستخدم من نطاق المستخدم للعملية pid إلى نطاق المستخدم للعملية التي فتحت uid_map (ولكن انظر تأهيلاً لهذه النقطة أدناه). بعبارة أخرى، من المحتمل أن ترى العمليات الموجودة في نطاقات مستخدم مختلفة قيمًا مختلفة عند القراءة من ملف uid_map معين، اعتمادًا على تعيينات معرف المستخدم لنطاقات المستخدم للعمليات القارئة.

تحدد كل سطر في ملف uid_map تعيينًا من 1 إلى 1 لنطاق من معرفات المستخدم المتجاورة بين نطاقي مستخدم. (عند إنشاء نطاق مستخدم لأول مرة، يكون هذا الملف فارغًا.) المواصفات في كل سطر تأخذ شكل ثلاثة أرقام مفصولة بمسافات بيضاء. يحدد الرقمان الأولان معرف المستخدم البدء في كل من نطاقي المستخدم. يحدد الرقم الثالث حجم النطاق المعين. بالتفصيل، يتم تفسير الحقول على النحو التالي:

(1)
بداية نطاق معرفات المستخدم في نطاق المستخدم للعملية pid.
(2)
بداية نطاق معرفات المستخدم التي يتم تعيين معرفات المستخدم المحددة بواسطة الحقل الأول إليها. يعتمد كيفية تفسير الحقل الثاني على ما إذا كانت العملية التي فتحت uid_map والعملية pid في نفس نطاق المستخدم، على النحو التالي:
(a)
إذا كانت العمليتان في نطاقي مستخدم مختلفين: الحقل الثاني هو بداية نطاق معرفات المستخدم في نطاق المستخدم للعملية التي فتحت uid_map.
(b)
إذا كانت العمليتان في نفس نطاق المستخدم: الحقل الثاني هو بداية نطاق معرفات المستخدم في نطاق المستخدم الأصل للعملية pid. تمكن هذه الحالة فاتح uid_map (الحالة الشائعة هنا هي فتح /proc/self/uid_map) من رؤية تعيين معرفات المستخدم إلى نطاق المستخدم للعملية التي أنشأت نطاق المستخدم هذا.
(3)
حجم نطاق معرفات المستخدم الذي يتم تعيينه بين نطاقي المستخدم.

الاستدعاءات النظامية التي تعيد معرفات المستخدم (معرفات المجموعة) - على سبيل المثال، getuid(2)، getgid(2)، وحقول بيانات الاعتماد في الهيكل الذي تعيده stat(2) - تعيد معرف المستخدم (معرف المجموعة) المعين إلى نطاق المستخدم الخاص بالمتصل.

عندما تصل عملية إلى ملف، يتم تعيين معرفات المستخدم والمجموعة الخاصة بها إلى نطاق المستخدم الأولي لغرض التحقق من الأذونات وتعيين المعرفات عند إنشاء ملف. عندما تسترد عملية معرفات ملفات المستخدم والمجموعة عبر stat(2)، يتم تعيين المعرفات في الاتجاه المعاكس، لإنتاج قيم بالنسبة لتعيينات معرف المستخدم والمجموعة الخاصة بالعملية.

ليس لنطاق المستخدم الأولي نطاق أصلي، ولكن، للاتساق، توفر النواة ملفات تعيين معرفات مستخدم ومجموعة وهمية لهذا النطاق. النظر إلى ملف uid_map (gid_map هو نفسه) من shell في النطاق الأولي يظهر:


$ cat /proc/$$/uid_map;
         0          0 4294967295

يخبرنا هذا التعيين أن النطاق الذي يبدأ بمعرف المستخدم 0 في هذا النطاق يتطابق مع نطاق يبدأ بـ 0 في النطاق الأصل (غير الموجود)، وحجم النطاق هو أكبر عدد صحيح غير موقع 32 بت. هذا يترك 4294967295 (القيمة -1 الموقعة 32 بت) غير معينة. هذا متعمد: يتم استخدام (uid_t) -1 في واجهات متعددة (على سبيل المثال، setreuid(2)) كوسيلة لتحديد "لا يوجد معرف مستخدم". ترك (uid_t) -1 غير معين وغير قابل للاستخدام يضمن عدم حدوث ارتباك عند استخدام هذه الواجهات.

تحديد تعيينات معرفات المستخدم والمجموعة: الكتابة إلى uid_map و gid_map

بعد إنشاء نطاق مستخدم جديد، يمكن الكتابة إلى ملف uid_map لـ عملية واحدة في النطاق مرة واحدة لتحديد تعيين معرفات المستخدم في نطاق المستخدم الجديد. محاولة الكتابة أكثر من مرة إلى ملف uid_map في نطاق مستخدم تفشل مع الخطأ EPERM. تنطبق قواعد مماثلة لملفات gid_map.

يجب أن تلتزم الأسطر المكتوبة إلى uid_map (gid_map) بقواعد الصلاحية التالية:

•
يجب أن تكون الحقول الثلاثة أرقامًا صالحة، ويجب أن يكون الحقل الأخير أكبر من 0.
•
تنتهي الأسطر بأحرف سطر جديد.
•

•
يجب كتابة سطر واحد على الأقل إلى الملف.

تفشل الكتابات التي تنتهك القواعد المذكورة أعلاه بالخطأ EINVAL.

تعيينات معرفات المشاريع: projid_map

على غرار تعيينات معرفات المستخدم والمجموعة، من الممكن إنشاء تعيينات معرفات مشاريع لمساحة اسم المستخدم. (تُستخدم معرفات المشاريع للحصص النسبية للأقراص؛ انظر setquota(8) و quotactl(2).)

يجب أن تكون العملية التي تكتب إما في مساحة اسم المستخدم للعملية pid أو في مساحة اسم المستخدم الأصلية للعملية pid.

يجب أن تمتلك معرفات المشاريع المعينة بدورها تعيينًا في مساحة اسم المستخدم الأصلية.

التفاعل مع استدعاءات النظام التي تغير معرفات المستخدمين أو المجموعات للعمليات

في مساحة اسم مستخدم لم تتم الكتابة فيها إلى الملف uid_map، تفشل استدعاءات النظام التي تغير معرفات المستخدم. وبالمثل، إذا لم تتم الكتابة في الملف gid_map، تفشل استدعاءات النظام التي تغير معرفات المجموعات. بعد الكتابة في الملفين uid_map و gid_map، يمكن استخدام القيم المعينة فقط في استدعاءات النظام التي تغير معرفات المستخدم والمجموعة.

بالنسبة لمعرفات المستخدم، تشمل استدعاءات النظام ذات الصلة setuid(2)، setfsuid(2)، setreuid(2)، و setresuid(2). بالنسبة لمعرفات المجموعة، تشمل استدعاءات النظام ذات الصلة setgid(2)، setfsgid(2)، setregid(2)، setresgid(2)، و setgroups(2).

الكتابة "deny" إلى الملف /proc/pid/setgroups قبل الكتابة إلى /proc/pid/gid_map ستعطل بشكل دائم setgroups(2) في مساحة اسم المستخدم وتسمح بالكتابة إلى /proc/pid/gid_map دون امتلاك صلاحية CAP_SETGID في مساحة اسم المستخدم الأصلية.

الملف /proc/pid/setgroups

يعرض الملف /proc/pid/setgroups السلسلة النصية "allow" إذا كانت العمليات في مساحة اسم المستخدم التي تحتوي على العملية pid مسموح لها باستخدام استدعاء النظام setgroups(2)؛ يعرض "deny" إذا لم يكن setgroups(2) مسموحًا به في مساحة اسم المستخدم تلك. لاحظ أنه بغض النظر عن القيمة في الملف /proc/pid/setgroups (وبغض النظر عن صلاحيات العملية)، فإن استدعاءات setgroups(2) غير مسموح بها أيضًا إذا لم يتم تعيين الملف /proc/pid/gid_map بعد.

يمكن لعملية ذات امتيازات (تلك التي تمتلك صلاحية CAP_SYS_ADMIN في مساحة الاسم) كتابة أي من السلسلتين "allow" أو "deny" إلى هذا الملف قبل كتابة تعيين معرف مجموعة لمساحة اسم المستخدم هذه إلى الملف /proc/pid/gid_map. كتابة السلسلة "deny" تمنع أي عملية في مساحة اسم المستخدم من استخدام setgroups(2).

جوهر القيود الموضحة في الفقرة السابقة هو أنه يُسمح بالكتابة إلى /proc/pid/setgroups فقط طالما أن استدعاء setgroups(2) محظور لأن /proc/pid/gid_map لم يتم تعيينه بعد. هذا يضمن أن العملية لا يمكنها الانتقال من حالة يُسمح فيها بـ setgroups(2) إلى حالة يُحظر فيها setgroups(2)؛ يمكن للعملية الانتقال فقط من حظر setgroups(2) إلى السماح بـ setgroups(2).

القيمة الافتراضية لهذا الملف في مساحة اسم المستخدم الأولية هي "allow".

بمجرد الكتابة في /proc/pid/gid_map (مما يؤدي إلى تمكين setgroups(2) في مساحة اسم المستخدم)، لم يعد من الممكن منع setgroups(2) عن طريق الكتابة "deny" إلى /proc/pid/setgroups (تفشل الكتابة مع الخطأ EPERM).

ترث مساحة اسم المستخدم الفرعية إعداد /proc/pid/setgroups من مساحة الاسم الأصلية.

إذا كانت قيمة الملف setgroups هي "deny"، فلا يمكن لاحقًا إعادة تمكين استدعاء النظام setgroups(2) (عن طريق الكتابة "allow" إلى الملف) في مساحة اسم المستخدم هذه. (محاولات القيام بذلك تفشل مع الخطأ EPERM.) ينتشر هذا القيد أيضًا إلى جميع مساحات اسم المستخدم الفرعية لهذه المساحة.

تمت إضافة الملف /proc/pid/setgroups في لينكس 3.19، ولكن تم إعادته إلى العديد من سلاسل نواة المستقرة السابقة، لأنه يعالج مشكلة أمنية. كانت المشكلة تتعلق بالملفات ذات الأذونات مثل "rwx---rwx". تمنح هذه الملفات أذونات أقل لـ "المجموعة" مقارنة بـ "الآخرين". هذا يعني أن إسقاط المجموعات باستخدام setgroups(2) قد يسمح للعملية بالوصول إلى ملف لم تكن تمتلكه سابقًا. قبل وجود مساحات اسم المستخدم، لم يكن هذا مصدر قلق، حيث أن العملية ذات الامتيازات فقط (التي تمتلك صلاحية CAP_SETGID) يمكنها استدعاء setgroups(2). ومع ذلك، مع إدخال مساحات اسم المستخدم، أصبح من الممكن لعملية غير ذات امتيازات إنشاء مساحة اسم جديدة يكون فيها للمستخدم جميع الامتيازات. سمح هذا للمستخدمين الذين لم تكن لديهم امتيازات سابقًا بإسقاط المجموعات وبالتالي اكتساب الوصول إلى الملفات التي لم تكن لديهم سابقًا. تمت إضافة الملف /proc/pid/setgroups لمعالجة هذه المشكلة الأمنية، عن طريق منع أي مسار لعملية غير ذات امتيازات لإسقاط المجموعات باستخدام setgroups(2).

USER NAMESPACES

This page describes the user namespaces available in Linux.

User namespaces allow a process to have a different set of user and group IDs than its parent. More generally, user namespaces form a hierarchy that allows a process to have a different view of user and group ID mappings than its ancestors. A process can create new user namespaces that are children of its current user namespace. The root of a user namespace can map arbitrary ranges of user and group IDs in the parent user namespace to arbitrary ranges of user and group IDs in its own user namespace.

User namespaces are implemented as a hierarchy of /proc/[pid]/uid_map and /proc/[pid]/gid_map files. A process that is the direct ancestor of a new user namespace (i.e., the process that creates the new namespace using the unshare(2) or clone(2) system calls with the CLONE_NEWUSER flag) can write to the uid_map and gid_map files of the child process. These files define the mapping between user and group IDs in the parent user namespace and the user and group IDs in the child user namespace.

The user and group ID maps

Each user namespace has an associated user ID map and group ID map. Each map is a list of mappings from ranges of IDs in the parent user namespace to ranges of IDs in the current user namespace.

The mapping is defined in the file /proc/[pid]/uid_map (for user IDs) and /proc/[pid]/gid_map (for group IDs). A process can write to the map file of a process that is its direct child in the user namespace hierarchy.

Each line in the map file defines a mapping and takes the following form:

ID-inside-ns ID-outside-ns size
Here, ID-inside-ns is the starting ID in the current user namespace, ID-outside-ns is the starting ID in the parent user namespace, and size is the number of IDs in the range.

For example, writing the following to /proc/self/uid_map:

0 100000 1

maps user ID 0 in the current user namespace to user ID 100000 in the parent user namespace. The size is 1, meaning only user ID 0 is mapped.

Writing the following:

0 100000 65536

maps the range of user IDs from 0 to 65535 in the current user namespace to the range of user IDs from 100000 to 165535 in the parent user namespace.

A process can write multiple lines to the map files to define multiple mappings. The ranges specified in the map files must not overlap. The sum of the size values for all mappings in a map file cannot exceed the maximum number of UIDs or GIDs supported by the kernel (typically 2^32).

When a process is created with the CLONE_NEWUSER flag, the initial user namespace is created with a default set of mappings. These mappings typically map the user ID 0 in the new namespace to the user ID of the calling process in the parent namespace, and map a range of subordinate IDs starting from 1 in the new namespace to subordinate IDs starting from the next available ID in the parent namespace. The exact default mappings can vary depending on the system configuration.

If a user or group ID is not covered by any mapping in the corresponding map file, it is considered to be an illegal ID. Access checks are performed using the mapped IDs. If a mapping is not found for a particular ID, the access is denied.

There is a special value for the ID-outside-ns field, 4294967295. This is treated as -1 as an unsigned integer. If this value is used for the ID-outside-ns, and there is no mapping for the

second field, that field is displayed as 4294967295 (-1 as an unsigned integer).

Accessing files

In order to determine permissions when an unprivileged process accesses a file, the process credentials (UID, GID) and the file credentials are in effect mapped back to what they would be in the initial user namespace and then compared to determine the permissions that the process has on the file. The same is also true of other objects that employ the credentials plus permissions mask accessibility model, such as System V IPC objects.

Operation of file-related capabilities

Certain capabilities allow a process to bypass various kernel-enforced restrictions when performing operations on files owned by other users or groups. These capabilities are: CAP_CHOWN, CAP_DAC_OVERRIDE, CAP_DAC_READ_SEARCH, CAP_FOWNER, and CAP_FSETID.

Within a user namespace, these capabilities allow a process to bypass the rules if the process has the relevant capability over the file, meaning that:

•
the process has the relevant effective capability in its user namespace; and
•
the file's user ID and group ID both have valid mappings in the user namespace.

The CAP_FOWNER capability is treated somewhat exceptionally: it allows a process to bypass the corresponding rules so long as at least the file's user ID has a mapping in the user namespace (i.e., the file's group ID does not need to have a valid mapping).

Set-user-ID and set-group-ID programs

When a process inside a user namespace executes a set-user-ID (set-group-ID) program, the process's effective user (group) ID inside the namespace is changed to whatever value is mapped for the user (group) ID of the file. However, if either the user or the group ID of the file has no mapping inside the namespace, the set-user-ID (set-group-ID) bit is silently ignored: the new program is executed, but the process's effective user (group) ID is left unchanged. (This mirrors the semantics of executing a set-user-ID or set-group-ID program that resides on a filesystem that was mounted with the MS_NOSUID flag, as described in mount(2).)

Miscellaneous

When a process's user and group IDs are passed over a UNIX domain socket to a process in a different user namespace (see the description of SCM_CREDENTIALS in unix(7)), they are translated into the corresponding values as per the receiving process's user and group ID mappings.

STANDARDS

Linux.

NOTES

Over the years, there have been a lot of features that have been added to the Linux kernel that have been made available only to privileged users because of their potential to confuse set-user-ID-root applications. In general, it becomes safe to allow the root user in a user namespace to use those features because it is impossible, while in a user namespace, to gain more privilege than the root user of a user namespace has.

Global root

The term "global root" is sometimes used as a shorthand for user ID 0 in the initial user namespace.

Availability

Use of user namespaces requires a kernel that is configured with the CONFIG_USER_NS option. User namespaces require support in a range of subsystems across the kernel. When an unsupported subsystem is configured into the kernel, it is not possible to configure user namespaces support.

As at Linux 3.8, most relevant subsystems supported user namespaces, but a number of filesystems did not have the infrastructure needed to map user and group IDs between user namespaces. Linux 3.9 added the required infrastructure support for many of the remaining unsupported filesystems (Plan 9 (9P), Andrew File System (AFS), Ceph, CIFS, CODA, NFS, and OCFS2). Linux 3.12 added support for the last of the unsupported major filesystems, XFS.

EXAMPLES

The program below is designed to allow experimenting with user namespaces, as well as other types of namespaces. It creates namespaces as specified by command-line options and then executes a command inside those namespaces. The comments and usage() function inside the program provide a full explanation of the program. The following shell session demonstrates its use.

First, we look at the run-time environment:


$ uname -rs;     # Need Linux 3.8 or later
Linux 3.8.0
$ id -u;         # Running as unprivileged user
1000
$ id -g;
1000

Now start a new shell in new user (-U), mount (-m), and PID (-p) namespaces, with user ID (-M) and group ID (-G) 1000 mapped to 0 inside the user namespace:


$ ./userns_child_exec -p -m -U -M '0 1000 1' -G '0 1000 1' bash;

The shell has PID 1, because it is the first process in the new PID namespace:


bash$ echo $$;
1

Mounting a new /proc filesystem and listing all of the processes visible in the new PID namespace shows that the shell can't see any processes outside the PID namespace:


bash$ mount -t proc proc /proc;
bash$ ps ax;
  PID TTY      STAT   TIME COMMAND
    1 pts/3    S      0:00 bash
   22 pts/3    R+     0:00 ps ax

Inside the user namespace, the shell has user and group ID 0, and a full set of permitted and effective capabilities:


bash$ cat /proc/$$/status | egrep '^[UG]id';
Uid:	0	0	0	0
Gid:	0	0	0	0
bash$ cat /proc/$$/status | egrep '^Cap(Prm|Inh|Eff)';
CapInh:	0000000000000000
CapPrm:	0000001fffffffff
CapEff:	0000001fffffffff

/* Update the mapping file 'map_file', with the value provided in
   'mapping', a string that defines a UID or GID mapping.  A UID or
   GID mapping consists of one or more newline-delimited records
   of the form:
       ID_inside-ns    ID-outside-ns   size
   Requiring the user to supply a string that contains newlines is
   of course inconvenient for command-line use.  Thus, we permit the
   use of commas to delimit records in this string, and replace them
   with newlines before writing the string to the file.  */
static void
update_map(char *mapping, char *map_file)
{
    int fd;
    size_t map_len;     /* Length of 'mapping' */
    /* Replace commas in mapping string with newlines.  */
    map_len = strlen(mapping);
    for (size_t j = 0; j < map_len; j++)
        if (mapping[j] == ',')
            mapping[j] = '\n';
    fd = open(map_file, O_RDWR);
    if (fd == -1) {
        fprintf(stderr, "ERROR: open %s: %s\n", map_file,
                strerror(errno));
        exit(EXIT_FAILURE);
    }
    if (write(fd, mapping, map_len) != map_len) {
        fprintf(stderr, "ERROR: write %s: %s\n", map_file,
                strerror(errno));
        exit(EXIT_FAILURE);
    }
    close(fd);
}
