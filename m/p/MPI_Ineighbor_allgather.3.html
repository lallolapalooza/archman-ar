معاملات الإدخال

  • sendbuf: عنوان بدء مخزن الإرسال (اختياري).
  • sendcount: عدد العناصر في مخزن الإرسال (عدد صحيح).
  • sendtype: نوع بيانات عناصر مخزن الإرسال (مقبض).
  • recvbuf: عنوان بدء مخزن الاستقبال (اختياري).
  • recvcount: عدد العناصر المستلمة من أي عملية (عدد صحيح).
  • recvtype: نوع بيانات عناصر مخزن الاستقبال (مقبض).
  • comm: التواصل (مقبض).

معاملات الإخراج

  • recvbuf: عنوان مخزن الاستقبال (اختياري).
  • request: طلب (مقبض، فقط للعمليات غير المتزامنة).
  • ierror: Fortran فقط: حالة الخطأ (عدد صحيح).

الوصف

MPI_Neighbor_allgather مشابهة لـ MPI_Allgather، باستثناء أن الجيران فقط هم من يستقبلون النتيجة، بدلاً من جميع العمليات. يتم تحديد الجيران وتخطيط المخزن بواسطة طوبولوجيا comm.

يجب أن تكون بصمة النوع المرتبطة بـ sendcount و sendtype في عملية ما مساوية لبصمة النوع المرتبطة بـ recvcount و recvtype في أي عملية أخرى.

ترتيب الجيران

بالنسبة لطوبولوجيا الرسم البياني الموزع، التي تم إنشاؤها باستخدام MPI_Dist_graph_create، يتم تعريف تسلسل الجيران في مخازن الإرسال والاستقبال في كل عملية كتسلسل تم إرجاعه بواسطة MPI_Dist_graph_neighbors للوجهات والمصادر، على التوالي. بالنسبة لطوبولوجيا الرسم البياني العامة، التي تم إنشاؤها باستخدام MPI_Graph_create، يتم تعريف ترتيب الجيران في مخازن الإرسال والاستقبال كتسلسل الجيران كما تم إرجاعه بواسطة MPI_Graph_neighbors. لاحظ أنه يجب استبدال طوبولوجيات الرسم البياني العامة بشكل عام بطوبولوجيات الرسم البياني الموزعة.

بالنسبة لطوبولوجيا الديكارتية، التي تم إنشاؤها باستخدام MPI_Cart_create، يتم تعريف تسلسل الجيران في مخازن الإرسال والاستقبال في كل عملية بترتيب الأبعاد، أولاً الجار في الاتجاه السلبي ثم في الاتجاه الإيجابي بإزاحة 1. عدد المصادر والوجهات في روتينات الاتصال هو 2 * ndims حيث يتم تعريف ndims في MPI_Cart_create. إذا لم يكن الجار موجودًا، أي عند حدود طوبولوجيا ديكارتية في حالة بعد شبكة افتراضية غير دورية (أي، periods[…]==false)، فإن هذا الجار يُعرّف بأنه MPI_PROC_NULL.

إذا كان الجار في أي من الدوال هو MPI_PROC_NULL، فإن الاتصال الجماعي للجوار يتصرف مثل الاتصال من نقطة إلى نقطة مع MPI_PROC_NULL في هذا الاتجاه. أي، لا يزال المخزن جزءًا من تسلسل الجيران ولكنه لا يتم الاتصال به أو تحديثه.

ملاحظات

خيار MPI_IN_PLACE لمخزن الإرسال sendbuf ليس له معنى لهذه العملية.

الأخطاء

تقريبًا جميع روتينات MPI ترجع قيمة خطأ؛ روتينات C كنتيجة للإرجاع للدالة، وروتينات Fortran في الوسيط الأخير.

قبل إرجاع قيمة الخطأ، يتم استدعاء معالج خطأ MPI الحالي المرتبط بكيان الاتصال (مثل، المتصل، النافذة، الملف). إذا لم يكن هناك كيان اتصال مرتبط باستدعاء MPI، فسيتم اعتبار الاستدعاء مرتبطًا بـ MPI_COMM_SELF وسيتم استدعاء معالج خطأ MPI المرتبط. عندما لا يكون MPI_COMM_SELF مهيأً (أي، قبل MPI_Init/MPI_Init_thread، بعد MPI_Finalize، أو عند استخدام نموذج الجلسات حصريًا) يثير الخطأ معالج الخطأ الأولي. يمكن تغيير معالج الخطأ الأولي عن طريق استدعاء MPI_Comm_set_errhandler على MPI_COMM_SELF عند استخدام نموذج العالم، أو وسيط CLI mpi_initial_errhandler إلى mpiexec أو مفتاح info إلى MPI_Comm_spawn/MPI_Comm_spawn_multiple. إذا لم يتم تعيين معالج خطأ مناسب آخر، فسيتم استدعاء معالج الخطأ MPI_ERRORS_RETURN لوظائف MPI I/O وسيتم استدعاء معالج الخطأ MPI_ERRORS_ABORT لجميع وظائف MPI الأخرى.

يتضمن Open MPI ثلاثة معالجات أخطاء محددة مسبقًا يمكن استخدامها:

  • MPI_ERRORS_ARE_FATAL يتسبب في إنهاء البرنامج لجميع عمليات MPI المتصلة.
  • MPI_ERRORS_ABORT معالج خطأ يمكن استدعاؤه على متصل، نافذة، ملف، أو جلسة. عند استدعائه على متصل، يتصرف كما لو تم استدعاء MPI_Abort على هذا المتصل. عند استدعائه على نافذة أو ملف، يتصرف كما لو تم استدعاء MPI_Abort على متصل يحتوي على مجموعة العمليات في النافذة أو الملف المقابل. عند استدعائه على جلسة، ينهي العملية المحلية فقط.
  • MPI_ERRORS_RETURN يرجع رمز خطأ إلى التطبيق.

يمكن لتطبيقات MPI أيضًا تنفيذ معالجات أخطاء خاصة بها عن طريق استدعاء:

  • MPI_Comm_create_errhandler ثم MPI_Comm_set_errhandler
  • MPI_File_create_errhandler ثم MPI_File_set_errhandler
  • MPI_Session_create_errhan

SYNTAX

int MPI_Ineighbor_allgather(const void *sendbuf, int sendcount,
                              MPI_Datatype sendtype, void *recvbuf, int recvcount,
                              MPI_Datatype recvtype, MPI_Comm comm,
                              MPI_Request *request);

INPUT PARAMETERS

sendbuf

Starting address of the send buffer (choice).

sendcount

Number of elements in the send buffer (non-negative integer).

sendtype

Datatype of elements in the send buffer (handle).

recvcount

Number of elements to receive from each neighbor (non-negative integer).

recvtype

Datatype of elements in the receive buffer (handle).

comm

Communicator with a topology (handle).

OUTPUT PARAMETERS

request

MPI request handle (handle).

DESCRIPTION

MPI_Ineighbor_allgather performs a non-blocking allgather operation using neighbor communication. The data from the send buffer of each process is sent to all of its neighbors. The receive buffer on each process will contain the concatenated data from all of its neighbors.

This operation is only valid on communicators that have a Cartesian or graph topology associated with them.

NEIGHBOR ORDERING

The order in which data is received in the receive buffer depends on the topology of the communicator. For Cartesian communicators, the neighbors are ordered according to the dimension and direction.

NOTES

The non-blocking nature of this function means that the operation may not be complete when the function returns. The user must call MPI_Wait or MPI_Test to determine when the operation is complete.

The send and receive counts and datatypes do not have to be the same. However, the total size of the data sent by each process must be equal to the total size of the data received by each process.

ERRORS

When the C binding is used, if the communicator in use is not valid or if one of the arguments is invalid, no error is raised. Instead, the behavior is undefined. However, if the communicator is valid, errors that occur during the MPI_Ineighbor_allgather call, such as inability to allocate memory, are errors in the MPI library and may be handled by a user-defined error handler.

The default error handler is MPI_ERRORS_RETURN.

See the MPI man page for a full list of MPI error codes.

See the Error Handling section of the MPI-3.1 standard for more information.
