الوصف

mkosi هي أداة لبناء صور نظام تشغيل مخصصة بسهولة. إنها غلاف متطور حول dnf و apt و pacman و zypper قد ينشئ صور أقراص مع عدد من الميزات الإضافية.

الأوامر

الأوامر التالية معروفة:

ملخص
عرض ملخص سهل القراءة لجميع الخيارات المستخدمة لبناء الصور. سيقوم هذا بتحليل سطر الأوامر وملفات التكوين، ولكنه سيطبع فقط ما هو معد له ولن يقوم ببناء أو تشغيل أي شيء فعليًا.
عرض-الملفات
إخراج أسماء ومحتويات جميع ملفات التكوين المحملة. يقوم mkosi بتحميل مجموعة من الملفات من مواقع مختلفة وهذا الأمر يسهل معرفة ما تم تكوينه وأين.
بناء
بناء الصورة بناءً على الإعدادات الممررة في سطر الأوامر وفي ملفات التكوين. هذا الأمر هو الافتراضي إذا لم يتم تحديد أي أمر. أي وسائط سطر أوامر محددة بعد الأمر سيتم تمريرها مباشرة إلى برنامج البناء النصي، إذا تم تعريفه.
قشرة
يقوم هذا ببناء الصورة إذا لم يتم بناؤها بعد، ثم يستدعي systemd-nspawn لتشغيل قشرة تفاعلية في الصورة. هذا لا يتطلب إقلاع النظام، إنه مثل chroot أفضل. يمكن تحديد سطر أوامر اختياري بعد أمر قشرة، ليتم استدعاؤه بدلاً من القشرة في الحاوية. استخدم -f لإعادة بناء الصورة بشكل غير مشروط قبل الحصول على القشرة، انظر أدناه. يجب تنفيذ هذا الأمر كـ root.
إقلاع
على غرار قشرة، ولكن بدلاً من استدعاء قشرة، يقوم بإقلاع systemd في الصورة باستخدام systemd-nspawn. يمكن تحديد سطر أوامر اختياري بعد أمر إقلاع، والذي يمكن أن يحتوي على خيارات nspawn إضافية بالإضافة إلى الوسائط التي يتم تمريرها كـ سطر أوامر النواة إلى نظام التهيئة في الصورة.
آلة-افتراضية
على غرار إقلاع، ولكنه يستخدم مراقب الآلة الافتراضية المعد (الافتراضي هو qemu) لإقلاع الصورة، أي بدلاً من المحاكاة الافتراضية للحاويات، يتم استخدام المحاكاة الافتراضية للآلات الافتراضية. كيفية تفسير وسائط سطر الأوامر الإضافية يعتمد على مراقب الآلة الافتراضية المعد. انظر VirtualMachineMonitor= لمزيد من المعلومات.
ssh
عند بناء الصورة باستخدام خيار Ssh=yes، يتصل هذا الأمر بآلة افتراضية تم إقلاعها عبر SSH. تأكد من تشغيل mkosi ssh بنفس التكوين الذي تم استخدامه لـ mkosi build حتى تتوفر له المعلومات اللازمة للاتصال بالآلة الافتراضية قيد التشغيل عبر SSH. على وجه التحديد، يتم استخدام مفتاح SSH الخاص من إعداد SshKey= للاتصال بالآلة الافتراضية. استخدم mkosi genkey لإنشاء مفتاح وشهادة تلقائيًا سيتم التقاطهما بواسطة mkosi. أي وسائط ممررة بعد أمر ssh يتم تمريرها كوسائط لاستدعاء ssh. للاتصال بحاوية، استخدم machinectl login أو machinectl shell.

يمكن استخدام خيار Machine= لإعطاء الآلة اسم مضيف مخصص عند إقلاعها والذي يمكن استخدامه لاحقًا لـ ssh إلى الصورة (على سبيل المثال، mkosi --machine=mymachine vm متبوعًا بـ mkosi --machine=mymachine ssh).

journalctl
يستخدم journalctl لفحص سجل النظام داخل الصورة. أي وسائط محددة بعد أمر journalctl يتم إلحاقها باستدعاء journalctl.
coredumpctl
يستخدم coredumpctl للبحث عن عمليات تفريغ النواة داخل الصورة. أي وسائط محددة بعد أمر coredumpctl يتم إلحاقها باستدعاء coredumpctl.
sysupdate
يستدعي systemd-sysupdate مع ضبط خيار --transfer-source= على مجلد الإخراج وخيار --definitions= على المجلد المحدد بواسطة SysupdateDirectory=. أي وسائط محددة بعد أمر sysupdate يتم تمريرها مباشرة إلى استدعاء systemd-sysupdate.
صندوق-رمل
تشغيل أوامر عشوائية داخل نفس صندوق الرمل المستخدم لتنفيذ أوامر أخرى مثل إقلاع، قشرة، آلة-افتراضية وأكثر. هذا يعني أن /usr سيتم استبداله بـ /usr من شجرة الأدوات إذا تم استخدام واحدة بينما سيبقى كل شيء آخر في مكانه. إذا لم يتم توفير أمر، سيتم استدعاء $SHELL أو bash إذا لم يتم تعيين $SHELL.
تنظيف
إزالة مخلفات البناء التي تم إنشاؤها في بناء سابق. إذا تم دمجها مع -f، فإنها تزيل أيضًا صور ذاكرة التخزين المؤقت للبناء التدريجي. إذا تم تحديد -f مرتين، فإنها تزيل أيضًا أي ذاكرة تخزين مؤقت للحزم.
تقديم
يقوم هذا ببناء الصورة إذا لم يتم بناؤها بعد، ثم يقدم مجلد الإخراج (أي عادةً mkosi.output/، انظر أدناه) عبر خادم HTTP مدمج صغير، يستمع على المنفذ 8081. ادمج مع -f لإعادة بناء الصورة بشكل غير مشروط قبل تقديمها. هذا الأمر مفيد لاختبار الاكتساب المستند إلى الشبكة لصور نظام التشغيل، على سبيل المثال عبر machinectl pull-raw ... و machinectl pull-tar ....
حرق <جهاز>
يقوم هذا ببناء الصورة إذا لم يتم بناؤها بعد، ثم يكتبها إلى الجهاز المحدد. يتم كتابة محتويات القسم كما هي، ولكن يتم تصحيح جدول أقسام GPT لمطابقة حجم القطاع والقرص للوسيط المحدد.

mkosi.conf — configuration file for mkosi

DESCRIPTION

The configuration file for mkosi is read from the file mkosi.conf in the current directory. If it does not exist, or if a file is not specified via --config=, the file is searched for in the build directory, and then in /etc/mkosi.conf.

The configuration file is a plain text file, which may contain comments starting with a # character. The file may contain any of the command line options, but they are interpreted differently. Command line options are preferred over settings in the configuration file.

Mkosi recognizes the following configuration options:

Target=, --target=
Takes the name of the build target. This is the most important option. The build target defines the system that is being built. It may be any operating system that is supported by mkosi. This is usually a distribution name like debian, ubuntu, fedora, centos, archlinux, or opensuse. In case of multiple distributions, the specific version might be specified too, e.g. debian11. The default value is debian.
ImageBuild=, --image-build=
Takes a boolean or auto. Enables or disables image building. If enabled, mkosi will build an image. If disabled, mkosi will only install packages and perform configuration steps, but will not produce an image. auto (the default) enables image building if any image output is configured (e.g. --disk-image= or --tar-image=).
PackageFormat=, --package-format=
Takes one of rpm, deb, apk, pacman, or none. Defaults to auto. Specifies the package format to use. If set to auto, the package format is inferred from the Target= option.
SourceImage=, --source-image=
Takes a path to an existing disk image file. This image will be used as the base for the new image. This is useful for creating incremental builds or for creating customized versions of existing images.
BaseImage=, --base-image=
Takes a path to an existing disk image file. This image will be used as the base for the new image. This is useful for creating incremental builds or for creating customized versions of existing images.
RootPassword=, --root-password=
Takes a password string. If set, the root user's password will be set to this value. If not set, the root user will have no password set, which may prevent login.
RootKey=, --root-key=
Takes a path to an SSH public key file. If set, the root user's ~/.ssh/authorized_keys file will be created and populated with the content of the specified file. This allows passwordless SSH login for the root user.
Username=, --username=
Takes a username. If set, a user with this username will be created. If RootPassword= is also set, this user will have the same password. If RootKey= is also set, this user will also have their SSH authorized keys populated. This option can be specified multiple times to create multiple users.
UserPassword=, --user-password=
Takes a password string. If set, this password will be used for all users created with the Username= option.
UserKey=, --user-key=
Takes a path to an SSH public key file. If set, this key will be added to the ~/.ssh/authorized_keys file for all users created with the Username= option.
SshKeys=, --ssh-keys=
Takes a comma-separated list of paths to SSH public key files. These keys will be added to the ~/.ssh/authorized_keys file for the root user.
InstallSSHKeys=, --install-ssh-keys=
Takes a boolean. If enabled (default: true), SSH public keys specified via RootKey=, UserKey= or SshKeys= will be installed into the image.
Packages=, --package=
Takes a comma-separated list of package specifications. Packages will be installed into the image. For distributions that support it, this can also include package versions, e.g. package=vim,bash-4.2.
SkeletonTrees=, --skeleton-tree=
Takes a comma-separated list of colon-separated path pairs. The first path of each pair refers to a directory to copy from the host into the image. The second path of each pair refers to the target directory inside the image. If the second path is not provided, the directory is copied on top of the root directory of the image. The second path is always interpreted as an absolute path. This is used to copy configuration files and other data into the image. Use this to override any default configuration files shipped with the distribution. If the mkosi.skeleton/ directory is found in the local directory it is also used for this purpose with the root directory as target (also see the Files section below).

As with the base tree logic above, instead of a directory, a tar file may be provided too. mkosi.skeleton.tar will be automatically used if found in the local directory.

Note that SkeletonTrees= is processed before package installation. Therefore, any package manager configuration files provided via SkeletonTrees= will be present in the image when mkosi invokes a package manager to install packages. However, if the configuration files are located outside the image, they won’t be picked up by the package manager running inside the image. This is because the package manager runs inside the image, and these files are only available on the host system. This means that any package manager configuration files provided via SkeletonTrees= won’t take effect when mkosi invokes a package manager to install packages.

ExtraTrees=, --extra-tree=
Takes a comma-separated list of colon-separated path pairs. The first path of each pair refers to a directory to copy from the host into the image. The second path of each pair refers to the target directory inside the image. If the second path is not provided, the directory is copied on top of the root directory of the image. The second path is always interpreted as an absolute path. Use this to override any default configuration files shipped with the distribution. If the mkosi.extra/ directory is found in the local directory it is also used for this purpose with the root directory as target (also see the Files section below).

As with the base tree logic above, instead of a directory, a tar file may be provided too. mkosi.extra.tar will be automatically used if found in the local directory.

RemovePackages=, --remove-package=
Takes a comma-separated list of package specifications for removal, in the same format as Packages=. The removal will be performed as one of the last steps. This step is skipped if CleanPackageMetadata=no is used.
RemoveFiles=, --remove-files=
Takes a comma-separated list of globs. Files in the image matching the globs will be purged at the end.
CleanPackageMetadata=, --clean-package-metadata=
Enable/disable removal of package manager databases and repository metadata at the end of installation. Can be specified as true, false, or auto (the default). With auto, package manager databases and repository metadata will be removed if the respective package manager executable is not present at the end of the installation.
SourceDateEpoch=, --source-date-epoch=
Takes a timestamp in seconds since the UNIX epoch as argument. File modification times of all files will be clamped to this value. The variable is also propagated to systemd-repart and scripts executed by mkosi. If not set explicitly, SOURCE_DATE_EPOCH from --environment and from the host environment are tried in that order. This is useful to make builds reproducible. See SOURCE_DATE_EPOCH for more information.
SyncScripts=, --sync-script=
Takes a comma-separated list of paths to executables that are used as the sync scripts for this image. See the Scripts section for more information.
PrepareScripts=, --prepare-script=
Takes a comma-separated list of paths to executables that are used as the prepare scripts for this image. See the Scripts section for more information.
BuildScripts=, --build-script=
Takes a comma-separated list of paths to executables that are used as the build scripts for this image. See the Scripts section for more information.
PostInstallationScripts=, --postinst-script=
Takes a comma-separated list of paths to executables that are used as the post-installation scripts for this image. See the Scripts section for more information.
FinalizeScripts=, --finalize-script=
Takes a comma-separated list of paths to executables that are used as the finalize scripts for this image. See the Scripts section for more information.
PostOutputScripts=, --postoutput-script
Takes a comma-separated list of paths to executables that are used as the post output scripts for this image. See the Scripts section for more information.
Bootable=, --bootable=
Takes a boolean or auto. Enables or disables generation of a bootable image. If enabled, mkosi will install an EFI bootloader, and add an ESP partition when the disk image output is used. If the selected EFI bootloader (see Bootloader=) is not installed or no kernel images can be found, the build will fail. auto behaves as if the option was enabled, but the build won’t fail if either no kernel images or the selected EFI bootloader can’t be found. If disabled, no bootloader will be installed even if found inside the image, no unified kernel images will be generated and no ESP partition will be added to the image if the disk output format is used.
Bootloader=, --bootloader=
Takes one of none, systemd-boot, uki, grub, systemd-boot-signed, uki-signed or grub-signed. Defaults to systemd-boot. If set to none, no EFI bootloader will be installed into the image. If set to systemd-boot, systemd-boot will be installed and for each installed kernel, a UKI will be generated and stored in EFI/Linux in the ESP. If set to uki, a single UKI will be generated for the latest installed kernel (the one with the highest version) which is installed to EFI/BOOT/BOOTX64.EFI in the ESP. If set to grub, for each installed kernel, a UKI will be generated and stored in EFI/Linux in the ESP. For each generated UKI, a menu entry is appended to the grub configuration in grub/grub.cfg in the ESP which chainloads into the UKI. A shim grub.cfg is also written to EFI/<distribution>/grub.cfg in the ESP which loads grub/grub.cfg in the ESP for compatibility with signed versions of grub which load the grub configuration from this location.

The signed variants will only install pre-signed EFI binaries shipped by the distribution.

Kernels need to be placed into the root filesystem (for example using ExtraTrees=) under /usr/lib/modules/$version, named vmlinux or vmlinuz. The $version is as produced by Kbuild’s kernelversion make target.

BiosBootloader=, --bios-bootloader=
Takes one of none or grub. Defaults to none. If set to none, no BIOS bootloader will be installed. If set to grub, grub is installed as the BIOS boot loader if a bootable image is requested with the Bootable= option. If no repart partition definition files are configured, mkosi will add a grub BIOS boot partition and an EFI system partition to the default partition definition files.

Note that this option is not mutually exclusive with Bootloader=. It is possible to have an image that is both bootable on UEFI and BIOS by configuring both Bootloader= and BiosBootloader=.

The grub BIOS boot partition should have UUID 21686148-6449-6e6f-744e-656564454649 and should be at least 1MB.

Even if no EFI bootloader is installed, we still need an ESP for BIOS boot as that’s where we store the kernel, initrd and grub modules.

ShimBootloader=, --shim-bootloader=
Takes one of none, unsigned, or signed. Defaults to none. If set to none, shim and MokManager will not be installed to the ESP. If set to unsigned, mkosi will search for unsigned shim and MokManager EFI binaries and install them. If SecureBoot= is enabled, mkosi will sign the unsigned EFI binaries before installing them. If set to signed, mkosi will search for signed EFI binaries and install those. Even if SecureBoot= is enabled, mkosi won’t sign these binaries again.

Note that this option only takes effect when an image that is bootable on UEFI firmware is requested using other options (Bootable=, Bootloader=).

Note that when this option is enabled, mkosi will only install already signed bootloader binaries, kernel image files and unified kernel images as self-signed binaries would not be accepted by the signed version of shim.

RepartOffline=, --repart-offline=
تحدد ما إذا كان سيتم بناء صور الأقراص باستخدام أجهزة loopback. ممكّن بشكل افتراضي. عند التمكين، لن يستخدم systemd-repart أجهزة loopback لبناء صور الأقراص. عند التعطيل، سيستخدم systemd-repart دائمًا أجهزة loopback لبناء صور الأقراص.

لاحظ أنه عند استخدام RepartOffline=no، لا يمكن تشغيل mkosi بدون امتيازات، ويجب إجراء بناء الصورة كمستخدم root خارج أي حاويات ومع توفر أجهزة loopback على النظام المضيف.

هناك حاليًا سيناريوهان معروفان يجب فيه استخدام RepartOffline=no. الأول هو عند استخدام Subvolumes= في ملف تعريف قسم repart، حيث لا يمكن إنشاء الأقسام الفرعية دون استخدام أجهزة loopback. الثاني هو عند إنشاء نظام مع SELinux وقسم root XFS. نظرًا لأن mkfs.xfs لا يدعم ملء نظام ملفات XFS بالسمات الموسعة، يجب استخدام أجهزة loopback لضمان وجود سمات SELinux الموسعة في نظام ملفات XFS الذي تم إنشاؤه.

History=, --history=
تأخذ قيمة منطقية. إذا تم تمكينها، سيكتب mkosi معلومات حول آخر عملية بناء إلى الدليل الفرعي .mkosi-private في الدليل الذي تم استدعاؤه منه. يتم استخدام هذه المعلومات بعد ذلك لاستعادة إعدادات آخر عملية بناء عند تشغيل أي أمر يتطلب بناءً دون تحديد --force.

لإعطاء مثال على سبب فائدة هذا، إذا قمت بتشغيل mkosi -O my-custom-output-dir -f متبوعًا بـ mkosi vm، سيفشل mkosi قائلاً إن الصورة لم يتم بناؤها بعد. إذا قمت بتشغيل mkosi -O my-custom-output-dir --history=yes -f متبوعًا بـ mkosi vm، فسيتم تشغيل الصورة التي تم بناؤها في الخطوة السابقة كما هو متوقع.

BuildSources=, --build-sources=
تأخذ قائمة مفصولة بفواصل من أزواج مسارات مفصولة بنقطتين. يشير المسار الأول لكل زوج إلى دليل ليتم تحميله من المضيف. يشير المسار الثاني لكل زوج إلى الدليل حيث يجب تحميل دليل المصدر عند تشغيل البرامج النصية. يتم إضافة البادئة /work/src إلى كل مسار هدف، ويتم فرز جميع مصادر البناء أبجديًا حسب هدفها قبل التحميل، بحيث يتم تحميل المسارات ذات المستوى الأعلى أولاً. إذا لم يتم تكوينها بشكل صريح، يتم تحميل دليل العمل الحالي إلى /work/src.
BuildSourcesEphemeral=, --build-sources-ephemeral=
تأخذ قيمة منطقية أو القيمة الخاصة buildcache. معطلة بشكل افتراضي. تحدد ما إذا كانت التغييرات على أدلة المصدر، ودليل العمل، والمكونة باستخدام BuildSources=، يتم الاحتفاظ بها. إذا تم تمكينها، فسيتم إعادة تعيين جميع أدلة المصدر إلى حالتها الأصلية في كل مرة بعد تشغيل جميع البرامج النصية من نوع معين (باستثناء برامج المزامنة).

💥💣💥 إذا تم ضبطها على buildcache، فلا يتم تجاهل الطبقة عند تشغيل برامج بناء البناء، بل يتم حفظها في دليل البناء، والتي تم تكوينها عبر BuildDirectory=، وسيتم إعادة استخدامها في التشغيلات اللاحقة. لا تزال الطبقة يتم تجاهلها لجميع البرامج النصية الأخرى. يمكن استخدام هذا الخيار لتطبيق تخزين مؤقت أكثر تقدمًا للبناء، ولكنه قد يؤدي إلى حالات غير متوقعة لدليل المصدر. عند استخدام هذا الخيار، يجب تكوين دليل بناء. 💥💣💥

يضيف متغيرات إلى البيئة التي يتم تشغيل مديري الحزم وبرامج التحضير/البناء/التثبيت اللاحق/التشطيب النصية بها. يأخذ قائمة مفصولة بمسافات من تعيينات المتغيرات أو أسماء المتغيرات فقط. في الحالة الأخيرة، سيتم تمرير قيم هذه المتغيرات من البيئة التي تم استدعاء mkosi بها. يمكن تحديد هذا الخيار أكثر من مرة، وفي هذه الحالة سيتم تعيين جميع المتغيرات المدرجة. إذا تم تعيين نفس المتغير مرتين، فإن التعيين الأخير يلغي التعيين السابق.
EnvironmentFiles=, --env-file=
تأخذ قائمة مفصولة بفواصل من المسارات إلى الملفات التي تحتوي على تعريفات متغيرات البيئة ليتم إضافتها إلى بيئة البرمجة النصية. يستخدم mkosi.env إذا تم العثور عليه في الدليل المحلي. تقرأ المتغيرات أولاً من mkosi.env إذا كان موجودًا، ثم من القائمة المحددة للملفات، ثم من إعدادات Environment=.
WithTests=, --without-tests, -T

ProxyUrl=, --proxy-url=
تكوين وكيل لاستخدامه لجميع اتصالات الشبكة الصادرة. يتم تكوين أدوات مختلفة يستدعيها mkosi والتي يمكن تكوين الوكيل لها لاستخدام هذا الوكيل. يقوم mkosi أيضًا بتعيين متغيرات بيئة معروفة مختلفة لتحديد الوكيل المراد استخدامه لأي برامج يستدعيها قد تحتاج إلى الوصول إلى الإنترنت.
ProxyExclude=, --proxy-exclude=
تكوين أسماء المضيفين التي لا ينبغي أن تمر الطلبات من خلالها عبر الوكيل. تأخذ قائمة مفصولة بفواصل بأسماء المضيفين.

حاليًا، يتم دعم تعيين مفتاح عميل الوكيل فقط عند استخدام dnf أو dnf5 لبناء الصورة.

NSpawnSettings=, --settings=
يحدد ملف إعدادات .nspawn لاستخدامه بواسطة systemd-nspawn في أوامر boot و shell، وللوضعه بجوار الصورة التي تم إنشاؤها. هذا مفيد لتكوين بيئة systemd-nspawn عند تشغيل الصورة. إذا لم يتم استخدام هذا الإعداد ولكن تم العثور على ملف mkosi.nspawn في الدليل المحلي، فسيتم استخدامه تلقائيًا لهذا الغرض.
VirtualMachineMonitor=, --vmm=
يكوّن جهاز مراقبة الأجهزة الافتراضية المراد استخدامه. يأخذ أحد الخيارات qemu أو vmspawn. الافتراضي هو qemu.

عند ضبطه على qemu، يتم تشغيل الصورة باستخدام qemu. يمكن تشغيل معظم تنسيقات الإخراج في qemu. أي وسيطات محددة بعد الأمر يتم إلحاقها باستدعاء qemu ويتم تفسيرها كوسيطات سطر أوامر إضافية لـ qemu.

عند ضبطه على vmspawn، يتم استخدام systemd-vmspawn لتشغيل الصورة. vmspawn يدعم فقط صور الأقراص وأنواع المجلدات. أي وسيطات محددة بعد الأمر يتم إلحاقها باستدعاء systemd-vmspawn ويتم تفسيرها كخيارات إضافية لـ vmspawn ووسيطات سطر أوامر إضافية للنواة.

Console=, --console=
يكون إعداد وحدة التحكم للجهاز الافتراضي. يأخذ أحد الخيارات interactive, read-only, native, أو gui. الافتراضي هو interactive
Format=

SystemdVersion=

BuildSources=

[Build]

[Match]

[Include]

Include=, --include=, -I
تضمين تكوين إضافي من الملف أو الدليل المحدد. يتم تضمين التكوين الإضافي فور تحليل الإعداد، إلا عند استخدامه في سطر الأوامر، حيث يتم تضمين التكوين الإضافي بعد تحليل جميع وسيطات سطر الأوامر.

لاحظ أن كل مسار يحتوي على تكوين إضافي يتم تحليله مرة واحدة فقط، حتى لو تم تضمينه أكثر من مرة باستخدام Include=.

يمكن تضمين التكوينات المدمجة لـ mkosi الافتراضية initrd، وشجرة الأدوات الافتراضية، وصورة الجهاز الافتراضي عن طريق تضمين القيمة الحرفية mkosi-initrd، mkosi-tools، أو mkosi-vm على التوالي.

ملاحظة: أسماء التضمين التي تبدأ بأي من الأحرف الحرفية mkosi- أو contrib- محجوزة للاستخدام بواسطة mkosi نفسه.

[Config] Section

Profiles=, --profile=
تحديد الملفات الشخصية المحددة. الملف الشخصي هو ملف تكوين أو دليل في الدليل mkosi.profiles/. يتم تضمين ملفات التكوين وأدلة كل ملف شخصي بعد تحليل تكوين الإلحاق mkosi.conf.d/*.conf.
Dependencies=, --dependency=
الصور التي تعتمد عليها هذه الصورة محددة كقائمة مفصولة بفواصل. سيتم بناء جميع الصور المكونة في هذا الخيار قبل هذه الصورة.

عند تحديد هذا الإعداد للصورة "الرئيسية"، فإنه يحدد أي الصور الفرعية يجب بناؤها. انظر قسم بناء صور متعددة لمزيد من المعلومات.

MinimumVersion=, --minimum-version=
الحد الأدنى لإصدار mkosi المطلوب لبناء هذا التكوين. إذا تم تحديده عدة مرات، فسيتم استخدام أعلى إصدار تم تحديده.
ConfigureScripts=, --configure-script=
يأخذ قائمة مفصولة بفواصل لمسارات الملفات التنفيذية التي تستخدم كبرامج نصية للتكوين لهذه الصورة. انظر قسم البرامج النصية لمزيد من المعلومات.
PassEnvironment=, --pass-environment=
يأخذ قائمة بأسماء متغيرات البيئة مفصولة بمسافات. عند بناء صور متعددة، قم بتمرير متغيرات البيئة المدرجة إلى كل صورة فرعية فردية كما لو كانت إعدادات "عالمية". انظر قسم بناء صور متعددة لمزيد من المعلومات.

النصوص (Scripts)

للسماح بتخصيص الصورة الذي لا يمكن تنفيذه باستخدام الميزات المدمجة في mkosi، يدعم mkosi تشغيل نصوص في نقاط مختلفة أثناء عملية بناء الصورة لتخصيص الصورة حسب الحاجة. يتم تنفيذ النصوص على النظام المضيف بصلاحيات الجذر (إما الجذر الحقيقي أو الجذر داخل مساحة اسم المستخدم التي أنشأها mkosi عند التشغيل بدون امتيازات) مع بيئة مخصصة لتبسيط تعديل الصورة. لكل نص، يتم تحميل مصادر البناء المُكوّنة (BuildSources=) في دليل العمل الحالي قبل تشغيل النص في دليل العمل الحالي. يتم تعيين $SRCDIR للإشارة إلى دليل العمل الحالي. يتم دعم النصوص التالية:

•
إذا كان ملف mkosi.configure (ConfigureScripts=) موجودًا، فسيتم تنفيذه قبل بناء الصورة. يمكن استخدام هذا النص لتعديل التكوين ديناميكيًا. يتلقى التكوين مُسلسلاً بصيغة JSON عبر الإدخال القياسي ويجب أن يخرج التكوين المعدل مُسلسلاً بصيغة JSON عبر الإخراج القياسي. لاحظ أن هذا النص يعمل فقط عند بناء الصورة أو تمهيدها (أفعال build و vm و boot و shell). إذا تم تكوين شجرة أدوات افتراضية، فسيتم بناؤها قبل تشغيل نصوص التكوين وسيتم تشغيل نصوص التكوين مع توفر شجرة الأدوات. هذا يعني أيضًا أن التعديلات التي تجريها نصوص التكوين لن تكون مرئية في مخرجات summary.
•
إذا كان ملف mkosi.sync (SyncScripts=) موجودًا، فسيتم تنفيذه قبل بناء الصورة. يمكن استخدام هذا النص لتحديث المصادر المختلفة المستخدمة لبناء الصورة. أحد حالات الاستخدام هو تشغيل git pull على مستودعات المصدر المختلفة قبل بناء الصورة. على وجه التحديد، لا ينطبق الإعداد BuildSourcesEphemeral= على نصوص المزامنة، مما يعني أنه يمكن استخدام نصوص المزامنة لتحديث مصادر البناء حتى لو كان BuildSourcesEphemeral= ممكّنًا.
•
إذا كان ملف mkosi.prepare (PrepareScripts=) موجودًا، فسيتم استدعاؤه أولاً بالوسيط final، مباشرةً
t بعد تثبيت حزم البرامج. يتم استدعاؤه مرة أخرى باستخدام معلمة سطر الأوامر build، مباشرة بعد تثبيت حزم البناء وتركيب طبقة البناء فوق دليل جذر الصورة. يتمتع هذا البرنامج النصي بالوصول إلى الشبكة ويمكن استخدامه لتثبيت حزم من مصادر أخرى غير مدير حزم التوزيع (مثل pip، npm، ...)، بعد تثبيت جميع حزم البرامج ولكن قبل تخزين الصورة مؤقتًا (إذا تم تمكين الوضع التزايدي). على عكس التثبيت للأغراض العامة، من الآمن تثبيت الحزم في النظام ( pip install، npm install -g) بدلاً من $SRCDIR نفسه لأن صورة البناء تستخدم لمشروع واحد فقط ويمكن التخلص منها وإعادة بنائها بسهولة، لذلك لا يوجد خطر من تضارب التبعيات ولا يوجد خطر من تلويث النظام المضيف.
•
إذا كان mkosi.build (BuildScripts=) موجودًا، فسيتم تنفيذه مع تركيب طبقة البناء فوق دليل جذر الصورة. عند تشغيل برنامج نصي للبناء، يشير $DESTDIR إلى دليل يجب على البرنامج النصي وضع أي ملفات تم إنشاؤها يرغب في أن تنتهي في الصورة فيه. لاحظ أن أنظمة البناء المستندة إلى make وautomake وmeson تلتزم بشكل عام بـ $DESTDIR، مما يجعل من الطبيعي جدًا بناء أشجار المصدر من برنامج نصي البناء. بعد تشغيل برنامج نصي البناء، يتم نسخ محتويات $DESTDIR إلى الصورة.
•
إذا كان mkosi.postinst (PostInstallationScripts=) موجودًا، فسيتم تنفيذه بعد تثبيت شجرة البناء (الاختياري) والأشجار الإضافية. يمكن استخدام هذا البرنامج النصي لتعديل الصور دون أي قيود، بعد تثبيت جميع حزم البرامج ومصادر البناء.
•
إذا كان mkosi.finalize (FinalizeScripts=) موجودًا، فسيتم تنفيذه كخطوة أخيرة لإعداد صورة.
•
إذا كان mkosi.postoutput (PostOutputScripts=) موجودًا، فسيتم تنفيذه مباشرة بعد إنشاء جميع ملفات الإخراج، قبل نقلها نهائيًا إلى دليل الإخراج. يمكن استخدام هذا لإنشاء مخرجات إضافية أو بديلة، مثل SHA256FILES أو قوائم بيانات مكونات البرامج (SBOM).
•
إذا كان mkosi.clean (CleanScripts=) موجودًا، فسيتم تنفيذه مباشرة بعد تنظيف مخرجات البناء السابق. يمكن لبرنامج نصي التنظيف تنظيف أي مخرجات لا يعرفها mkosi (مثل القطع الأثرية من SplitArtifacts=partitions أو ملفات RPM التي تم بناؤها في برنامج نصي البناء). لاحظ أن هذا البرنامج النصي لا يستخدم شجرة الأدوات حتى لو تم تكوين واحدة.
•
إذا كان mkosi.version موجودًا وقابلًا للتنفيذ، فسيتم تشغيله أثناء تحليل التكوين ويملأ ImageVersion= بالإخراج القياسي. يمكن استخدام هذا لتتبع الإصدار الخارجي، مثل git describe أو date '+%Y-%m-%d'. لاحظ أن هذا البرنامج النصي يتم تنفيذه على النظام المضيف دون أي عزل.
•
إذا كان mkosi.rootpw موجودًا وقابلًا للتنفيذ، فسيتم تشغيله أثناء تحليل التكوين ويملأ RootPassword= بالإخراج القياسي. يمكن استخدام هذا لتوليد كلمة مرور عشوائيًا ويمكن تذكرها عن طريق إخراجها إلى الخطأ القياسي أو عن طريق قراءة $MKOSI_CONFIG في برنامج نصي آخر (مثل mkosi.postoutput). لاحظ أن هذا البرنامج النصي يتم تنفيذه على النظام المضيف دون أي عزل.

إذا استخدم برنامج نصي امتداد .chroot، فسيقوم mkosi بالتبديل إلى الصورة باستخدام mkosi-chroot (انظر أدناه) قبل تنفيذ البرنامج النصي. على سبيل المثال، إذا كان mkosi.postinst.chroot موجودًا، فسيقوم mkosi بالتبديل إلى الصورة وتنفيذه كبرنامج نصي ما بعد التثبيت.

بدلاً من برنامج نصي ملف واحد، سيقرأ mkosi أيضًا جميع الملفات بترتيب معجمي من الدلائل المسماة بشكل مناسب .d، على سبيل المثال، سيتم استخدام جميع الملفات في mkosi.build.d كبرامج نصية للبناء. هذا مدعوم من قبل

•
mkosi.sync.d،
•
mkosi.prepare.d،
•
mkosi.build.d،
•
mkosi.postinst.d،
•
mkosi.finalize.d،
•
mkosi.postoutput.d، و
•
mkosi.clean.d.

يمكن دمج هذا مع امتداد .chroot، على سبيل المثال، سيتم تشغيل mkosi.build.d/01-foo.sh دون التبديل إلى الصورة وسيتم تشغيل mkosi.build.d/02-bar.sh.chroot بعد التبديل إلى الصورة أولاً.

تتلقى البرامج النصية التي ينفذها mkosi متغيرات البيئة التالية:

•
يحتوي $ARCHITECTURE على البنية من الإعداد Architecture=. إذا لم يتم تعيين Architecture=، فسوف يحتوي على البنية الأصلية لجهاز المضيف. انظر توثيق Architecture= للقيم المحتملة لهذا المتغير.
•
يحتوي $QEMU_ARCHITECTURE على البنية من $ARCHITECTURE بالصيغة التي يستخدمها qemu. مفيد للعثور على ملف qemu الثنائي ( qemu-system-$QEMU_ARCHITECTURE).
•
يحتوي $DISTRIBUTION على التوزيع من الإعداد Distribution=.
•
يحتوي $RELEASE على الإصدار من الإعداد Release=.
•
يحتوي $DISTRIBUTION_ARCHITECTURE على البنية من $ARCHITECTURE بالصيغة التي يستخدمها التوزيع المحدد.
•
يحتوي $PROFILES على التشكيلات من الإعداد Profiles= كسلسلة مفصولة بفواصل.
•
يتم تعيين $CACHED= إلى 1 إذا كانت صورة مخبأة متاحة، و 0 بخلاف ذلك.
•
يحتوي $CHROOT_SCRIPT على المسار إلى البرنامج النصي قيد التشغيل بالنسبة لدليل جذر الصورة. الاستخدام الأساسي لهذا المتغير هو بالاشتراك مع البرنامج النصي mkosi-chroot. انظر وصف mkosi-chroot أدناه لمزيد من المعلومات.
•
يحتوي $SRCDIR على المسار إلى الدليل الذي تم استدعاء mkosi منه، مع تركيب مصادر البناء المحددة فوقه. يحتوي $CHROOT_SRCDIR على القيمة التي سيحصل عليها $SRCDIR بعد استدعاء mkosi-chroot.
•
يتم تعريف $BUILDDIR فقط إذا كان mkosi.builddir موجودًا ويشير إلى دليل البناء المراد استخدامه. هذا مفيد لجميع أنظمة البناء التي تدعم البناء خارج الشجرة لإعادة استخدام القطع الأثرية المبنية بالفعل من عمليات التشغيل السابقة. يحتوي $CHROOT_BUILDDIR على القيمة التي سيحصل عليها $BUILDDIR بعد استدعاء mkosi-chroot.
•
$DESTDIR هو دليل يمكن وضع أي برنامج تم تثبيته تم إنشاؤه بواسطة برنامج نصي بناء فيه. يتم تعيين هذا المتغير فقط عند تنفيذ برنامج نصي بناء. يحتوي $CHROOT_DESTDIR على القيمة التي سيحصل عليها $DESTDIR بعد استدعاء mkosi-chroot.
•
يشير $OUTPUTDIR إلى دليل التجهيز المستخدم لتخزين القطع الأثرية للبناء التي تم إنشاؤها أثناء عملية البناء. يحتوي $CHROOT_OUTPUTDIR على القيمة التي سيحصل عليها $OUTPUTDIR بعد استدعاء mkosi-chroot.
•
يشير $PACKAGEDIR إلى الدليل الذي يحتوي على مستودع الحزم المحلي. يمكن لبرامج نصية البناء إضافة المزيد من الحزم إلى المستودع المحلي عن طريق كتابة الحزم إلى $PACKAGEDIR.
•
يشير $ARTIFACTDIR إلى الدليل المستخدم لتمرير القطع الأثرية للبناء التي تم إنشاؤها أثناء عملية البناء وجعلها متاحة للاستخدام بواسطة mkosi. هذا مشابه لـ PACKAGEDIR، ولكنه مخصص للقطع الأثرية التي قد لا تكون حزمًا يفهمها مدير الحزم، مثل initrds التي تم إنشاؤها بواسطة مولدات initrd أخرى غير mkosi. يمكن لبرامج نصية البناء إضافة المزيد من القطع الأثرية إلى الدليل عن طريق وضعها في $ARTIFACTDIR. يتم توفير الملفات في هذا الدليل فقط للبناء الحالي ولا يتم نسخها للخارج مثل محتويات $OUTPUTDIR.

سيستخدم mkosi أيضًا أدلة فرعية معينة لدليل القطع الأثرية لاستخدام محتوياتها تلقائيًا في خطوات معينة. حاليًا، يتم استخدام الدليلين الفرعيين التاليين في دليل القطع الأثرية بواسطة mkosi:

•
io.mkosi.microcode: يتم استخدام جميع الملفات في هذا الدليل كملفات microcode، أي يتم إلحاقها بـ initrds بترتيب معجمي.
•
io.mkosi.initrd: يتم استخدام جميع الملفات في هذا الدليل كـ initrds ويتم ربطها بترتيب معجمي.

يوصى بأن يضع مستخدمو $ARTIFACTDIR الأشياء لاستخدامهم الخاص في دليل مساحة اسم مماثلة، مثل local.my.namespace.

•
يشير $BUILDROOT إلى الدليل الجذر للصورة التي يتم بناؤها، مع أو بدون تركيب طبقة البناء فوقها اعتمادًا على البرنامج النصي الذي يتم تنفيذه.
•
$WITH_DOCS هو إما 0 أو 1 اعتمادًا على ما إذا كان قد تم طلب بناء بدون تثبيت وثائق أو مع تثبيتها (WithDocs=yes). يجب على برنامج نصي البناء منع تثبيت أي وثائق حزم في $DESTDIR في حالة
$WITH_DOCS is set to 0.
•
$WITH_TESTS is either 0 or 1 depending on whether a build without or with running the test suite was requested (WithTests=no). A build script should avoid running any unit or integration tests in case $WITH_TESTS is 0.
•
$WITH_NETWORK is either 0 or 1 depending on whether a build without or with networking is being executed (WithNetwork=no). A build script should avoid any network communication in case $WITH_NETWORK is 0.
•
$SOURCE_DATE_EPOCH is defined if requested (SourceDateEpoch=TIMESTAMP, Environment=SOURCE_DATE_EPOCH=TIMESTAMP or the host environment variable $SOURCE_DATE_EPOCH). This is useful to make builds reproducible. See SOURCE_DATE_EPOCH for more information.
•
$MKOSI_UID and $MKOSI_GID respectively are the uid, gid of the user that invoked mkosi.
•
$MKOSI_CONFIG is a file containing a json summary of the settings of the current image. This file can be parsed inside scripts to gain access to all settings for the current image.
•
$IMAGE_ID contains the identifier from the ImageId= or --image-id= setting.
•
$IMAGE_VERSION contains the version from the ImageVersion= or --image-version= setting.

بالإضافة إلى ذلك، عند تنفيذ نص برمجي، تتوفر بعض النصوص البرمجية عبر $PATH لتبسيط حالات الاستخدام الشائعة.

•
mkosi-chroot: يقوم هذا النص البرمجي بإنشاء chroot داخل الصورة وتنفيذ الأمر المحدد. بالإضافة إلى إنشاء chroot داخل الصورة، سيقوم أيضًا بتثبيت ملفات ومجلدات مختلفة ($SRCDIR، $DESTDIR، $BUILDDIR، $OUTPUTDIR، $CHROOT_SCRIPT) داخل الصورة وتعديل متغيرات البيئة المقابلة للإشارة إلى المواقع داخل الصورة. سيقوم أيضًا بتثبيت أنظمة ملفات APIVFS (/proc، /dev، ...) للتأكد من أن النصوص البرمجية والأدوات التي يتم تنفيذها داخل chroot تعمل بشكل صحيح. كما أنه يقوم بنشر /etc/resolv.conf من المضيف إلى chroot إذا طُلب ذلك لضمان عمل تحليل DNS داخل chroot. بعد خروج أمر mkosi-chroot، يتم تنظيف نقاط التثبيت المختلفة.

على سبيل المثال، لاستدعاء ls داخل الصورة، استخدم ما يلي:

mkosi-chroot ls ...

لتنفيذ النص البرمجي بالكامل داخل الصورة، أضف لاحقة .chroot إلى الاسم (mkosi.build.chroot بدلاً من mkosi.build، وما إلى ذلك).

•
لجميع مديري الحزم المدعومين (dnf، rpm، apt، dpkg، pacman، zypper)، يتم وضع نصوص برمجية بنفس الاسم في $PATH تضمن أن هذه الأوامر تعمل على دليل الجذر الخاص بالصورة مع التكوين المقدم من المستخدم بدلاً من نظام المضيف. هذا يعني أنه من نص برمجي، يمكنك القيام، على سبيل المثال، dnf install vim لتثبيت vim في الصورة.

بالإضافة إلى ذلك، سيقوم mkosi-install، mkosi-reinstall، mkosi-upgrade و mkosi-remove باستدعاء العملية المقابلة لمدير الحزم المستخدم لبناء الصورة.

•
يتم استدعاء git تلقائيًا مع safe.directory=* لتجنب أخطاء الأذونات عند التشغيل كمستخدم جذر في مساحة اسم المستخدم.
•
يتم استدعاء useradd و groupadd تلقائيًا مع --root=$BUILDROOT عند تنفيذها خارج الصورة.

عند تنفيذ النصوص البرمجية، يتم جعل أي مجلدات لا تزال قابلة للكتابة للقراءة فقط (/home، /var، /root، ...) ويظل الحد الأدنى من المجلدات التي تحتاج إلى أن تكون قابلة للكتابة قابلة للكتابة. هذا لضمان أن النصوص البرمجية لا يمكنها العبث بنظام المضيف عند تشغيل mkosi كجذر.

لاحظ أنه عند تنفيذ النصوص البرمجية، يتم جعل جميع مجلدات المصدر مؤقتة، مما يعني أن جميع التغييرات التي تم إجراؤها على مجلدات المصدر أثناء تشغيل النصوص البرمجية يتم التخلص منها بعد انتهاء النصوص البرمجية من التنفيذ. استخدم مجلدات الإخراج أو البناء أو ذاكرة التخزين المؤقت إذا كنت بحاجة إلى الاحتفاظ بالبيانات بين عمليات البناء.

الملفات

لتسهيل بناء الصور لإصدارات التطوير لمشاريعك، يمكن لـ mkosi قراءة بيانات التكوين من الدليل المحلي، بافتراض أنه يتم استدعاؤه من شجرة مصدر. على وجه التحديد، يتم استخدام الملفات التالية إذا كانت موجودة في الدليل المحلي:

•
قد يتم استخدام الدليل mkosi.skeleton/ أو الأرشيف mkosi.skeleton.tar لإدراج ملفات في الصورة. يتم نسخ الملفات قبل تثبيت حزم التوزيع في الصورة. هذا يسمح بإنشاء ملفات تحتاج إلى توفيرها مبكرًا، على سبيل المثال لتكوين مدير الحزم أو تعيين إعدادات systemd.

عند استخدام الدليل، لا يتم الاحتفاظ بملكية الملف: ستكون جميع الملفات المنسوخة مملوكة للجذر. للحفاظ على الملكية، استخدم أرشيف tar.

•
قد يتم استخدام الدليل mkosi.extra/ أو الأرشيف mkosi.extra.tar لإدراج ملفات إضافية في الصورة، بالإضافة إلى ما يتضمنه التوزيع في حزمه. وهي مشابهة لـ mkosi.skeleton/ و mkosi.skeleton.tar، ولكن يتم نسخ الملفات إلى شجرة دليل الصورة بعد تثبيت نظام التشغيل.

عند استخدام الدليل، لا يتم الاحتفاظ بملكية الملف: ستكون جميع الملفات المنسوخة مملوكة للجذر. للحفاظ على الملكية، استخدم أرشيف tar.

•
قد يتم استخدام الدليل mkosi.sandbox/ أو الأرشيف mkosi.sandbox.tar لتكوين مدير الحزم دون إدراج الملفات في الصورة. إذا كان ينبغي تضمين الملفات في الصورة، فيجب استخدام mkosi.skeleton/ و mkosi.skeleton.tar بدلاً من ذلك.

عند استخدام الدليل، لا يتم الاحتفاظ بملكية الملف: ستكون جميع الملفات المنسوخة مملوكة للجذر. للحفاظ على الملكية، استخدم أرشيف tar.

•
سيتم نسخ ملف إعدادات nspawn mkosi.nspawn إلى نفس المكان الذي يوجد فيه ملف الصورة الناتج، إذا كان موجودًا. هذا مفيد نظرًا لأن nspawn يبحث عن ملفات الإعدادات بجوار ملفات الصور التي يقوم بتشغيلها، لإعدادات تشغيل حاوية إضافية.
•
يتم استخدام الدليل mkosi.cache/ تلقائيًا كذاكرة تخزين مؤقت لتنزيل الحزم، في حالة وجوده، لتسريع عمليات تشغيل الأداة المتكررة.
•
يتم استخدام الدليل mkosi.builddir/ تلقائيًا كدليل بناء خارج الشجرة، في حالة وجوده، إذا كانت أوامر البناء في نصوص mkosi.build تدعم ذلك. على وجه التحديد، سيتم تثبيت هذا الدليل في حاوية البناء، وسيتم تعيين متغير البيئة $BUILDDIR عليه عند استدعاء نصوص البناء. قد يستخدم نص البناء بعد ذلك هذا الدليل كدليل بناء، للبناء خارج الشجرة بأسلوب automake أو ninja. هذا يسرع عمليات البناء بشكل كبير، لا سيما عند استخدام mkosi في الوضع التزايدي (-i): لا يتم فقط إعادة استخدام الصورة وoverlay للبناء، ولكن أيضًا شجرة البناء بين الاستدعاءات المتتالية. لاحظ أنه إذا لم يكن هذا الدليل موجودًا، فلن يتم تعيين متغير البيئة $BUILDDIR، ويعود الأمر إلى نصوص البناء لتحديد ما إذا كان سيتم إجراء بناء داخل الشجرة أو خارجها، وأي دليل بناء سيتم استخدامه.
•
يمكن استخدام الملف mkosi.rootpw لتوفير كلمة مرور لمستخدم الجذر في الصورة. إذا كانت كلمة المرور مسبوقة بـ hashed:، فسيتم اعتبارها كلمة مرور جذر مجزأة بالفعل. قد تتبع كلمة المرور اختياريًا حرف سطر جديد يتم إزالته ضمنيًا. يجب أن يكون للملف وضع وصول 0600 أو أقل. إذا لم يكن هذا الملف موجودًا، فسيتم تعيين كلمة مرور الجذر الافتراضية للتوزيع (والتي تعني عادةً حظر الوصول إلى مستخدم الجذر).
•
يوفر الملف mkosi.passphrase عبارة المرور المراد استخدامها عند تحديد تشفير LUKS. يجب أن يحتوي على عبارة المرور حرفيًا، و
- content: | لا ينتهي بحرف سطر جديد (أي، بنفس تنسيق ملفات كلمة المرور التي يتوقعها cryptsetup و /etc/crypttab). يجب أن يكون وضع الوصول للملف 0600 أو أقل.
•
تحتوي الملفات mkosi.crt و mkosi.key على شهادة X.509 ومفتاح خاص بتنسيق PEM لاستخدامهما عند الحاجة إلى التوقيع (UEFI SecureBoot، verity، ...).
•
يُستخدم الدليل mkosi.output/ لتخزين جميع مخرجات البناء.
•
يُستخدم الدليل mkosi.credentials/ كمصدر للمعلومات الإضافية المشابهة لخي Credentials=. لكل ملف في الدليل، سيتم استخدام اسم الملف كاسم للمعلومات، وسيصبح محتوى الملف هو قيمة المعلومة، أو، إذا كان الملف قابلاً للتنفيذ، سيقوم mkosi بتنفيذ الملف وسيتم استخدام مخرجات الأمر القياسية كقيمة للمعلومة. سيتم تجاهل المخرجات إلى الخطأ القياسي. المعلومات التي تم تكوينها باستخدام Credentials= لها الأولوية على الملفات الموجودة في mkosi.credentials.
•
يُستخدم الدليل mkosi.repart/ كمصدر لملفات تعريف الأقسام الخاصة بـ systemd-repart والتي يتم تمريرها إلى systemd-repart عند بناء صورة القرص. إذا لم يكن موجودًا ولم يتم تكوين الإعداد RepartDirectories=، فسيلجأ mkosi افتراضيًا إلى ملفات تعريف الأقسام التالية:

00-esp.conf (إذا كنا نبني صورة قابلة للتشغيل):

[Partition]
    Type=esp
    Format=vfat
    CopyFiles=/boot:/
    CopyFiles=/efi:/
    SizeMinBytes=512M
    SizeMaxBytes=512M

05-bios.conf (إذا كنا نبني صورة قابلة للتشغيل بنظام BIOS):

[Partition]
    # UUID لقسم تمهيد BIOS الخاص بنظام GRUB والذي يحتاجه GRUB على GPT
    # لتضمين نفسه فيه.
    Type=21686148-6449-6e6f-744e-656564454649
    SizeMinBytes=1M
    SizeMaxBytes=1M

10-root.conf

[Partition]
    Type=root
    Format=<distribution-default-filesystem>
    CopyFiles=/
    Minimize=guess

لاحظ أنه إذا تم العثور على mkosi.repart/ أو تم استخدام RepartDirectories=، فلن نستخدم أيًا من تعريفات الأقسام الافتراضية.

جميع هذه الملفات اختيارية.

لاحظ أن موقع جميع هذه الملفات يمكن أيضًا تهيئته أثناء الاستدعاء عبر خيارات سطر الأوامر، وكإعدادات في mkosi.conf، في حالة عدم قبول الإعدادات الافتراضية لمشروع ما.

يدعم mkosi ثلاثة أنواع مختلفة من ذاكرة التخزين المؤقت لتسريع إعادة بناء الصور بشكل متكرر. على وجه التحديد:

1.
قد يتم تخزين ذاكرة التخزين المؤقت للحزم لمدير حزم التوزيع بين عمليات البناء. يتم تكوين هذا باستخدام الخيار --cache-directory= أو الدليل mkosi.cache/. يعتمد هذا الشكل من التخزين المؤقت على مدير حزم التوزيع، ويخزن مؤقتًا حزم التوزيع (RPM، deb، ...) بعد تنزيلها، ولكن قبل فكها.
2.
إذا تم تمكين وضع البناء التزايدي باستخدام --incremental، يتم إنشاء نسخ مخزنة مؤقتًا من الصورة النهائية وطبقة البناء فورًا قبل نسخ مصادر البناء (لطبقة البناء) أو نسخ المخرجات التي تم إنشاؤها بواسطة mkosi.build (في حالة الصورة النهائية). يسمح هذا الشكل من التخزين المؤقت بتجاوز خطوة فك ضغط الحزم التي تستغرق وقتًا طويلاً لمديري حزم التوزيع، ولكنه فعال فقط إذا ظلت قائمة الحزم المراد استخدامها مستقرة، بينما تتغير مصادر البناء ونصوصها البرمجية بانتظام. لاحظ أن هذا التخزين المؤقت يتطلب مسحًا يدويًا: كلما تم تعديل قائمة الحزم، يجب إزالة الصور المخزنة مؤقتًا بشكل صريح قبل إعادة البناء التالية، باستخدام المفتاح -f.
3.
أخيرًا، بين عمليات البناء المتعددة، يمكن مشاركة دليل مخرجات البناء، باستخدام الدليل mkosi.builddir/. يسمح هذا الدليل لأنظمة البناء مثل Meson بإعادة استخدام المصادر المترجمة بالفعل من بناء سابق، وبالتالي تسريع عملية بناء نص برمجي لبناء mkosi.build.

تكون ذاكرة التخزين المؤقت للحزم ووضع البناء التزايدي مفيدة بشكل غير مشروط. ينطبق التخزين المؤقت النهائي فقط على استخدامات mkosi مع شجرة المصدر ونص البناء. عندما يتم تمكين الثلاثة معًا، تكون أوقات الانعطاف لإكمال بناء الصور الدنيا، حيث يلزم فقط إعادة ترجمة ملفات المصدر المتغيرة.

بناء صور متعددة

إذا كان الدليل mkosi.images/ موجودًا، فسوف يقوم mkosi بتحميل تكوينات الصور الفرعية الفردية منه وسيقوم ببناء كل منها. يمكن أن تكون تكوينات الصور إما أدلة تحتوي على ملفات تكوين mkosi أو ملفات عادية بامتداد .conf.

عندما يتم العثور على تكوينات الصور في mkosi.images/، سيقوم mkosi ببناء الصور المحددة في الإعداد Dependencies= للصورة الرئيسية وجميع تبعياتها (أو كلها إذا لم يتم تكوين أي صور بشكل صريح باستخدام Dependencies= في تكوين الصورة الرئيسية). لإضافة تبعيات بين الصور الفرعية، يمكن أيضًا استخدام الإعداد Dependencies=. يتم بناء الصور الفرعية دائمًا قبل الصورة الرئيسية.

عند تعريف الصور، سيقوم mkosi أولاً بقراءة تكوين الصورة الرئيسية (التكوين خارج دليل mkosi.images/)، متبوعًا بتكوين الصورة المحدد. تنطبق العديد من الإعدادات "العالمية" على الصورة الرئيسية وجميع صورها الفرعية ولا يمكن تكوينها بشكل منفصل في الصور الفرعية. الإعدادات التالية عالمية ولا يمكن تكوينها في الصور الفرعية:

يمكن للصور الرجوع إلى مخرجات الصور التي تعتمد عليها. على وجه التحديد، بالنسبة للخيارات التالية، سيتحقق mkosi فقط مما إذا كانت المدخلات موجودة قبل بناء الصورة:

•

•
ExtraTrees=
•
Initrds=

للإشارة إلى مخرجات تبعيات الصورة، قم ببساطة بتكوين أي من هذه الخيارات بمسار نسبي للمخرجات لاستخدامها في دليل المخرجات للتبعية. أو استخدم محدد %O للإشارة إلى دليل المخرجات.

يمكن العثور على مثال جيد لكيفية بناء صور متعددة في مستودع systemd.
