mkudffs(8)

الحزمة: udftools

التراخيص: GPL

mbr لا معنى له إلا عند تشغيل mkudffs على القرص بأكمله، وليس على قسم واحد فقط. الخيارات الصحيحة هي:
preserve
احتفظ بمنطقة التمهيد UDF الحالية، لا تلمسها (الافتراضي لنوع الوسائط المختلف عن hd)
erase
مسح منطقة التمهيد UDF الحالية، املأها بالأصفار (الافتراضي لنوع الوسائط hd على الأقسام وعلى الأقراص القابلة للإزالة)
mbr
وضع جدول MBR بقسم واحد يبدأ من القطاع 0 (يشمل MBR نفسه) ويمتد عبر جهاز القرص بأكمله، يلزم فقط للأقراص الصلبة غير القابلة للإزالة المستخدمة على أنظمة Microsoft Windows (الافتراضي لنوع الوسائط hd على الأقراص الصلبة غير القابلة للإزالة بدون أقسام)، انظر قسم WHOLE DISK VS PARTITION
mbr:sec-size
نفس mbr ولكن قم بتعيين حجم قطاع MBR صراحةً إلى قيمة sec-size، الافتراضي sec-size هو حجم كتلة الجهاز المنطقية (القطاع) مع الرجوع إلى حجم 512 بايت
(الخيار متاح منذ mkudffs 2.0)
--strategy= strategy
حدد استراتيجية التخصيص المراد استخدامها. الاستراتيجيات الصالحة هي 4 و 4096. إذا تم حذفه، فإن استراتيجية mkudffs تستند إلى --media-type.
--spartable, --spartable= spartable-number
تمكين استخدام جدول الاستبدال (Sparing Table). اختياريًا، حدد أيضًا عدد جداول الاستبدال. الأعداد الصحيحة الصالحة هي 1–4. عندما يتم حذف رقم جدول الاستبدال، يتم كتابة جدولين على القرص. إذا تم حذف الخيار، فإن استخدام جدول الاستبدال يعتمد على نوع الوسائط. (الخيار قبل mkudffs 2.0 كان متاحًا فقط لنوع الوسائط cdrw)
--sparspace= num-of-entires
حدد عدد الإدخالات في جدول الاستبدال. إذا تم حذفه، فإن العدد الافتراضي للإدخالات هو 1024، ولكنه يعتمد على نوع الوسائط. (الخيار متاح منذ mkudffs 2.0)
--packetlen= length
طول الحزمة في عدد الكتل المستخدمة للمحاذاة. سيتم محاذاة جميع هياكل UDF المستمرة إلى حزم. كما يحدد حجم مساحة الاستبدال وطول الحزمة في جدول الاستبدال. يجب أن يتطابق مع طول ECC / الحزمة للجهاز. إذا تم حذفه، فإن القيمة الافتراضية لأقراص DVD هي 16 كتلة، ولأقراص CD/BD هي 32 كتلة، وإلا 1 كتلة. (الخيار قبل mkudffs 2.1 كان متاحًا فقط لأنواع الوسائط cdrw و dvdrw)
--vat
تمكين استخدام جدول التخصيص الافتراضي (VAT). إذا تم حذفه، فإن الاستخدام يعتمد على نوع الوسائط. (الخيار متاح منذ mkudffs 2.0)
--startblock= start-block
حدد موقع الكتلة حيث تبدأ نظام ملفات UDF.

عادةً ما يكون كتلة البداية 0، ولكن عند إنشاء جلسة ثانية أو أعلى لقرص UDF بصري متعدد الجلسات، يكون هذا هو موقع الكتلة حيث تبدأ تلك الجلسة الجديدة.

عند تحديث ملف صورة UDF متعدد الجلسات موجود، يقوم mkudffs بالكتابة فوق كتل البيانات فقط لجلسة جديدة في موضع كتلة البداية في ملف الصورة.

عند إنشاء ملف صورة UDF جديد، يقوم mkudffs بكتابة كتل البيانات فقط لجلسة جديدة في بداية ملف الصورة. لذلك، سيتم كتابة بيانات كتلة البداية في كتلة صفر بدلاً من كتلة البداية. هذه الصورة بدون الكتل الرائدة (حيث توجد الجلسات السابقة) مناسبة لحرق جلسة جديدة على القرص البصري. ولكن لا يمكن قراءتها أو اكتشافها بواسطة أي أداة UDF حتى يتم إضافة الكتل الصفرية الرائدة (أو الجلسات السابقة) إلى ملف الصورة.

لحساب الموضع الذي يجب أن تبدأ فيه جلسة جديدة لقرص بصري معين، يلزم استخدام برنامج سيتم استخدامه لحرق الصورة التي تم إنشاؤها حديثًا. على سبيل المثال، إذا كان برنامج الحرق المستخدم هو wodim(1)، فإن القيمة الثانية في ناتج استدعاء wodim -msinfo هي كتلة البداية. وبالمثل، بالنسبة لاستدعاء cdrecord(1) cdrecord -msinfo أو لاستدعاء cdrdao(1) cdrdao msinfo أو لاستدعاء xorriso(1) xorriso -as cdrecord dev=/dev/cdrw -msinfo.

(الخيار متاح منذ mkudffs 2.3)

--minblocks= min-num-of-blocks
حدد الحد الأدنى لعدد الكتل للكتابة على القرص باستخدام جدول التخصيص الافتراضي.

يؤثر هذا الخيار على موضع الكتلة حيث يتم كتابة جدول التخصيص الافتراضي. وفي حالة استخدام الخيار --closed، فإنه يؤثر أيضًا على موضع الكتلة لمؤشر وصف المجلد الثاني (AVDP).

القيمة الافتراضية لنوع الوسائط cdr هي 300. هذا افتراضي آمن للسماح بحرق صورة قرص CD-R في وضع Track-at-Once. يتطلب هذا الوضع حرق صورة بحجم أدنى يبلغ 300 قطاع. قد تسمح أوضاع حرق أقراص CD-R الأخرى (مثل Disc-at-Once أو Packet-Writing) باستخدام صور أقراص أصغر.

بالنسبة لجميع أنواع الوسائط الأخرى، لا يوجد حد أدنى افتراضي.

(الخيار متاح منذ mkudffs 2.3)

--closed
أغلق القرص باستخدام جدول التخصيص الافتراضي. يتم كتابة AVDP أيضًا في نهاية القرص. بشكل افتراضي، القرص المزود بجدول التخصيص الافتراضي غير مغلق.
--space= space
حدد مجموعة المساحة. تستخدم مجموعة المساحة غير المخصصة للوسائط التي يمكن تخصيص كتلها على الفور. تستخدم مجموعة المساحة المحررة للوسائط التي تحتاج كتلها إلى إعداد/مسح خاص قبل التخصيص. في جدول المساحة يتم تخزين قائمة بالنطاقات غير المخصصة. في خريطة بت المساحة يتم تخزين خريطة بت للكتل غير المخصصة. لا تستخدم لـ VAT.
freedbitmap
خريطة بت محررة
freedtable
جدول محرّر
unallocbitmap
خريطة بت غير مخصصة (افتراضي)
unalloctable
جدول غير مخصص
--ad= ad
حدد واصفات التخصيص للدليل الجذر (/).
inicb
واصفات التخصيص في ICB (افتراضي)
short
واصفات تخصيص قصيرة
long
واصفات تخصيص طويلة
--noefe
لا تستخدم إدخالات الملف الموسعة للدليل الجذر (/). يؤثر فقط على UDF 2.00 أو أعلى. يجب تحديده بعد --udfrev.
--locale
عامل خيارات سلسلة المعرف كسلاسل مشفرة وفقًا لإعدادات اللغة المحلية الحالية (افتراضي). يجب تحديده كوسيط أول. (الخيار متاح منذ mkudffs 2.0)
--u8
عامل خيارات سلسلة المعرف كسلاسل مشفرة بتنسيق OSTA Compressed Unicode ثنائي البايت بدون بايت معرف الضغط البادئ، وهو ما يعادل Latin1 (ISO-8859-1). يجب تحديده كوسيط أول.
--u16
عامل خيارات سلسلة المعرف كسلاسل مشفرة بتنسيق OSTA Compressed Unicode ثنائي البايت بدون بايت معرف الضغط البادئ، وهو ما يعادل UTF-16BE. لاحظ أنه لا يمكن تضمين البايت الصفري في خيارات سطر الأوامر، لذلك لا يمكن توفير أي حرف يحتوي على بايت صفري واحد على الأقل (ينطبق هذا على جميع أحرف Latin1). يجب تحديده كوسيط أول.
--utf8
عامل خيارات سلسلة المعرف كسلاسل مشفرة بتنسيق UTF-8. يجب تحديده كوسيط أول. (قبل mkudffs 2.0 كان هذا هو الخيار الافتراضي)

حجم الكتلة

In most cases, operating systems are unable to mount UDF filesystem if UDF block size differs from logical sector size of the device. Typically hard disks have sector size 512 bytes and optical media 2048 bytes. Therefore UDF block size must match the logical sector size of the device.

Linux kernel prior to version 2.6.30 used hardcoded UDF block size of 2048 bytes independently of logical sector size, therefore it was not able to automatically mount UDF filesystem if block size differed from 2048. Since 2.6.30 and prior to 4.11 Linux kernel used a logical sector size of the device as UDF block size, plus it tried fallback to 2048. Since 4.11 it uses logical sector size and fallbacks to any valid block size between logical sector size and 4096. Therefore since version 2.6.30 Linux kernel can automatically mount UDF filesystems correctly if UDF block size matches device logical sector size and since version 4.11 can automatically also mount devices which sector size does not match UDF block size. In any case and also for Linux kernel prior to version 2.6.30, different UDF block size (which is not autodetected) can be manually specified via bs=blocksize mount parameter.

القرص الكامل مقابل القسم

UDF filesystem is supposed to be formatted on the whole media and not to the partitioned hard disk. Mac OS X systems enforce this rule and reject to automatically mount UDF filesystem unless it is formatted on the whole unpartitioned hard disk. Possible partition table (e.g. MBR or GPT) on disk with valid UDF filesystem is ignored. On the other hand, Microsoft Windows systems are unable to detect non-removable hard disks without MBR or GPT partition table. Removable disks do not have this restriction. A consequence is that non-removable hard disks formatted to UDF by Windows Vista+ are not recognized by Mac OS X systems and vice-versa. Note that manual mount of UDF partition on partitioned hard disk on Mac OS X system is possible and working (e.g. by running commands: mkdir /Volumes/DriveName && mount_udf /dev/disk1s1 /Volumes/DriveName). But there is no known way to mount an unpartitioned non-removable disk on Windows system.

Thanks to reserved and unused UDF boot area (first 32kB of UDF filesystem) it is possible to deal with this problem, by putting MBR on such non-removable hard disk just for compatibility reasons with Windows. Such MBR table would contain one partition which starts at sector 0 (includes MBR itself) and spans whole disk device. So the whole disk device and also the first partition on disk points to same sectors. Therefore UDF filesystem can be mounted either from whole disk device (needed for Mac OS X systems) or from first partition (needed for Microsoft Windows systems).

Linux kernel ignores MBR table if contains partition which starts at sector 0. Normally Linux kernel can detect and mount UDF filesystem either on a partition or on whole disk device. It does not have any restrictions.

mkudffs option --bootarea=mbr put such MBR table for compatibility with Microsoft Windows systems into disk when formatting.

أخطاء تسميات لينكس

In most cases Logical Volume Identifier is used as UDF label. But Linux libblkid prior to version 2.26 used Volume Identifier. Therefore mkudffs --label for compatibility reasons set both Logical Volume Identifier and Volume Identifier.

Linux libblkid prior to version 2.30 incorrectly processed non-ASCII identifier strings encoded in 8-bit OSTA Compressed Unicode format. Therefore mkudffs since version 2.0 for compatibility reasons tries to encode a non-ASCII identifier strings in 16-bit OSTA Compressed Unicode format and then fallbacks to 8-bit format.

For more information about UDF Label and UUID see udflabel(8) section UDF LABEL AND UUID.

حالة الخروج

mkudffs returns 0 if successful, non-zero if there are problems.

القيود

mkudffs cannot create UDF 2.50 Metadata partition, therefore it does not support UDF revisions higher than 2.01 for non Write Once media yet. So there is no support for Blu-ray discs which needs UDF 2.50 (except for Blu-ray Disc Recordable which does not require Metadata partition).

mkudffs prior to version 2.2 was unable to process Unicode strings with code points above U+FFFF. When option --utf8 was specified then input strings were limited to 3-byte UTF-8 sequences and when option --u16 was specified then input strings were limited just to UCS-2BE strings (subset of UTF-16BE).

الأخطاء

mkudffs prior to version 1.1 was unable to process non-ASCII characters from identifier strings in --utf8 mode, --vsid option was completely broken and --blocksize must have been manually specified for hard disks as default value was hardcoded for optical disks. mkudffs prior to version 2.0 generated broken and unreadable cdr disc images.
