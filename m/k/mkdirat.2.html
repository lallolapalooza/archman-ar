mkdir(2) دليل استدعاءات النظام mkdir(2)

الاسم

mkdir, mkdirat - إنشاء دليل

المكتبة

مكتبة C القياسية (libc, -lc)

الملخص

#include <sys/stat.h>
int mkdir(const char *path, mode_t mode);
#include <fcntl.h>           /* تعريف ثوابت AT_* */
#include <sys/stat.h>
int mkdirat(int dirfd, const char *path, mode_t mode);
متطلبات ميزة الاختبار (Feature Test Macro Requirements) لـ glibc (انظر feature_test_macros(7)):

mkdirat():

    منذ glibc 2.10:
        _POSIX_C_SOURCE >= 200809L
    قبل glibc 2.10:
        _ATFILE_SOURCE

الوصف

يحاول mkdir() إنشاء دليل بالاسم path.

تحدد الوسيطة mode وضع الدليل الجديد (انظر inode(7)). يتم تعديلها بواسطة umask الخاصة بالعملية بالطريقة المعتادة: في غياب ACL افتراضي، يكون وضع الدليل الذي تم إنشاؤه هو (mode & ~umask & 0777). يعتمد ما إذا كانت بتات mode الأخرى سيتم احترامها للدليل الذي تم إنشاؤه على نظام التشغيل. بالنسبة لنظام Linux، انظر VERSIONS أدناه.

سيتم امتلاك الدليل الذي تم إنشاؤه حديثًا بواسطة معرف المستخدم الفعال للعملية. إذا كان الدليل الأب الذي يحتوي على الملف يحتوي على بت تعيين-معرف-المجموعة (set-group-ID) مضبوطًا، أو إذا تم تحميل نظام الملفات مع دلالات مجموعة BSD (mount -o bsdgroups أو، بشكل مرادف mount -o grpid)، فسيرث الدليل الجديد ملكية المجموعة من والديه؛ وإلا فسيكون مملوكًا لمعرف المجموعة الفعال للعملية.

إذا كان الدليل الأب يحتوي على بت تعيين-معرف-المجموعة (set-group-ID) مضبوطًا، فسيكون الدليل الذي تم إنشاؤه حديثًا كذلك.

mkdirat()

يعمل استدعاء النظام mkdirat() بنفس الطريقة تمامًا مثل mkdir()، باستثناء الاختلافات الموضحة هنا.

إذا كان path نسبيًا، فسيتم تفسيره بالنسبة للدليل المشار إليه بواسطة واصف الملف dirfd (بدلاً من اعتباره نسبيًا إلى دليل العمل الحالي للعملية المستدعية، كما تفعل mkdir() للمسار النسبي).

إذا كان path نسبيًا وكانت dirfd هي القيمة الخاصة AT_FDCWD، فسيتم تفسير path نسبيًا إلى دليل العمل الحالي للعملية المستدعية (مثل mkdir()).

إذا كان path مطلقًا، فسيتم تجاهل dirfd.

انظر openat(2) لشرح الحاجة إلى mkdirat().

قيمة الإرجاع

يعيد mkdir() و mkdirat() صفرًا عند النجاح. عند حدوث خطأ، يتم إرجاع -1 ويتم تعيين errno للإشارة إلى الخطأ.

الأخطاء

EACCES
لا يسمح الدليل الأب بإذن الكتابة للعملية، أو أن أحد الأدلة في path لم يسمح بإذن البحث. (انظر أيضًا path_resolution(7)).
EBADF
(mkdirat()) path نسبي ولكن dirfd ليس AT_FDCWD ولا واصف ملف صالح.
EDQUOT
تم استنفاد حصة المستخدم من كتل القرص أو العقد (inodes) على نظام الملفات.
EEXIST
path موجود بالفعل (ليس بالضرورة كدليل). يشمل هذا الحالة التي يكون فيها path رابطًا رمزيًا، معلقًا أو غير ذلك.
EFAULT
يشير path إلى خارج مساحة العنوان القابلة للوصول الخاصة بك.
EINVAL
المكون النهائي ("اسم الأساس") للدليل الجديد path غير صالح (على سبيل المثال، يحتوي على أحرف غير مسموح بها من قبل نظام الملفات الأساسي).
ELOOP
تم العثور على عدد كبير جدًا من الروابط الرمزية في حل path.
EMLINK
سيتجاوز عدد الروابط إلى الدليل الأب LINK_MAX.
ENAMETOOLONG
كان path طويلاً جدًا.
ENOENT
مكون دليل في path غير موجود أو رابط رمزي معلق.
ENOMEM
كانت ذاكرة النواة غير كافية متاحة.
ENOSPC
لا توجد مساحة كافية على الجهاز الذي يحتوي على path للدليل الجديد.
ENOSPC
لا يمكن إنشاء الدليل الجديد لأن حصة المستخدم من القرص قد استنفدت.
ENOTDIR
مكون مستخدم كدليل في path ليس دليلًا في الواقع.
ENOTDIR
(mkdirat()) path نسبي و dirfd هو واصف ملف يشير إلى ملف غير دليل.
EPERM
لا يدعم نظام الملفات الذي يحتوي على path إنشاء الأدلة.
EROFS
يشير path إلى ملف على نظام ملفات للقراءة فقط.
EOVERFLOW
لم يتم تكوين تعيينات UID أو GID (انظر user_namespaces(7)).

الإصدارات

في نظام Linux، بالإضافة إلى بتات الأذونات، يتم أيضًا احترام بت mode S_ISVTX.

ملاحظات glibc

على النواة الأقدم حيث mkdirat() غير متاحة، يعود التفاف glibc إلى استخدام mkdir(). عندما يكون path نسبيًا، تقوم glibc ببناء مسار بناءً على الرابط الرمزي في /proc/self/fd الذي يتوافق مع الوسيطة dirfd.
