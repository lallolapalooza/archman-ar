**القسم 1: إعداد إضافة TxRep** - **استخدام TxRep** القيمة الافتراضية هي 0. إذا كانت القيمة 1، فسيتم استخدام نظام سمعة TxRep. يسجل TxRep متوسط درجة طويلة الأجل لكل مرسل ويضبط درجات الرسائل الجديدة نحو هذا المتوسط. يمكن أن يزيد هذا أو يقلل الدرجة بناءً على السلوك طويل الأجل للمرسل المعني. ملاحظة: سيتم تجاهل بعض الاختبارات عند تحديد الدرجة النهائية للرسالة: - القواعد التي تم تعيين `tflags` لها على `noautolearn`. - **txrep_factor** النطاق [0..1] (الافتراضي: 0.5) مقدار عودة الرسالة نحو متوسط المرسل طويل الأجل. يسجل الخوارزمية إجمالي الدرجات وعدد الرسائل للمرسل (العناصر `total` و `count`)، ثم يحسب الدرجة النهائية كالتالي: ``` finalscore = score + factor * (total + score) / (count + 1) ``` إذا كان المعامل 0.5، فسيتحرك نحو منتصف المسافة بين الدرجة المحسوبة والمتوسط الجديد. إذا كان المعامل 0.3، فسيتحرك نحو ثلث المتوسط. إذا كان المعامل 1، فسيتم استخدام المتوسط طويل الأجل بما في ذلك الدرجة غير المعدلة. إذا كان المعامل 0، فسيتم استخدام الدرجة المحسوبة فقط، دون تعديل الدرجة، على الرغم من تسجيلها في قاعدة البيانات. - **txrep_dilution_factor** النطاق [0.7..1.0] (الافتراضي: 0.98) يتم تخفيف (أو "تخفيف") الدرجة التاريخية للمرسل بنسبة مئوية معينة بواسطة هذا المعامل. هذا يعني أن تأثير السجلات القديمة يقل مع كل رسالة جديدة من المرسل. هذا مهم للتعامل مع التغيرات في سمعة المرسلين بمرونة أكبر. بدون انتهاء صلاحية للتخفيف (المعامل = 1)، تتم إضافة الدرجة الجديدة إلى إجمالي الدرجات للمرسل. إذا تم استخدام التخفيف (المعامل < 1)، يتم تقليل تأثير المتوسط التاريخي حسب المعامل قبل حساب المتوسط الجديد. ثم يستخدم هذا المتوسط لتعديل إجمالي الدرجات للمرسل. يتم حساب إجمالي الدرجات الجديدة كالتالي: ``` newtotal = (oldcount + 1) * (newscore + dilution * oldtotal) / (dilution * oldcount + 1) ``` على سبيل المثال، إذا كان المعامل 0.9 (تخفيف بنسبة 10٪)، فسيتم تسجيل الدرجة الجديدة بنسبة 100٪ من الدرجة الأخيرة، و 90٪ من الدرجة قبل الأخيرة، و 81٪ من الدرجة قبل الثالثة (0.9 * 0.9 = 0.81)، وهكذا. - **txrep_learn_penalty** النطاق [0..200] (الافتراضي: 20) عند تدريب SpamAssassin برسالة بريد عشوائي، تتم إضافة هذه الدرجة إلى إجمالي الدرجات للمرسل، بغض النظر عن الدرجة الفعلية للرسالة. يكون تأثير الدرجة أقل كلما زاد عدد الرسائل التي يمتلكها المرسل في قاعدة بيانات TxRep. - **txrep_learn_bonus** النطاق [0..200] (الافتراضي: 20) عند تدريب SpamAssassin برسالة بريد غير عشوائي (ham)، يتم خصم هذه الدرجة من إجمالي الدرجات للمرسل، بغض النظر عن الدرجة الفعلية للرسالة. يكون تأثير الدرجة أقل كلما زاد عدد الرسائل التي يمتلكها المرسل في قاعدة بيانات TxRep. - **txrep_learn_penalty** النطاق [0..5] (الافتراضي: 0) عندما يصنف SpamAssassin رسالة كبريد عشوائي أو بريد غير عشوائي أثناء الفحص، ويتم تنشيط عملية التعلم الآلي، يتم تعديل درجات المرسل بقيمة المعامل `txrep_learn_penalty` (أو `txrep_learn_bonus` بنفس المعنى). القيمة 0 تعطّل تعديل الدرجات بواسطة التعلم الآلي، ويتم فقط تخزين الدرجة المحسوبة قبل هذا التعديل في قاعدة البيانات. - **txrep_track_messages** 0 | 1 (الافتراضي: 1) إذا تم تعيينه على 1، يقوم TxRep بتسجيل الرسائل التي تم فحصها وتعلمها بالفعل. ينشئ هذا سجلًا إضافيًا في قاعدة بيانات السمعة لتجنب التعديلات الخاطئة بسبب الفحص المتكرر، ويسمح بإعادة تعلم الرسائل التي تم تعلمها بشكل خاطئ سابقًا أو التي تحتاج إلى إعادة تعلم بعد تعديل درجة التعلم أو المكافأة. - **txrep_welcomelist_out** النطاق [0..200] (الافتراضي: 10) تم استخدام القيمة السابقة `txrep_whitelist_out` حتى الإصدار 4.1. عندما تكون قيمة هذا الإعداد أكبر من 0، يتم إدراج المستلمين للرسائل المرسلة من الشبكات الداخلية كترحيب عن طريق زيادة إجمالي درجاتهم بالقيمة المحددة هنا. عند إرسال الرسالة، لا يتم معرفة عنوان IP أو معرفات أخرى للمرسل، بل يتم استخدام درجة البريد القياسية فقط. يبقى اسم النطاق كما هو. لا يعمل قائمة الترحيب الصادرة إلا عندما يتم تكوين SpamAssassin لفحص رسائل البريد الصادر، وعندما يستخدم المستخدمون المحليون خادم SMTP لإرسال رسائل البريد، وعندما يتم تحديد الشبكات الداخلية في تكوين SpamAssassin. تتحسن درجة السمعة مع كل رسالة مرسلة من الشبكات الداخلية، لذلك كلما زاد عدد الرسائل المرسلة إلى المستلم، تحسنت سمعة عنوان بريده الإلكتروني. - txrep_ipv6_mask_len
range [0..128]         (default: 48)

La base de datos AWL mantiene solo los bits más significativos de una dirección IPv6 en sus campos, para que diferentes direcciones IP individuales dentro de una subred pertenecientes a la misma propiedad sean gestionadas bajo una sola entrada en la base de datos. Como no disponemos de información sobre los rangos de direcciones asignadas a los envíadores, esta longitud de máscara CIDR es solo una aproximación. El valor por defecto es 48 bits, correspondiendo a un rango de direcciones comúnmente asignado a organizaciones individuales (más pequeñas). Aumenta el número para una mayor resolución, por ejemplo, a 64 o 96 o 128, o disminuye para rangos más amplios, por ejemplo, a 32. Un valor 0 es permitido pero no es especialmente útil, ya que trataría al entero internet como una sola organización. El número no tiene que ser múltiplo de 4, y se permite cualquier división.

txrep_user2global_ratio
range [0..10]          (default: 0)

Cuando el opción txrep_user2global_ratio está establecida con un valor mayor que 0 y el servidor permite hacerlo, se usarán dos almacenamientos: el almacenamiento de usuarios (usado por el usuario) y el almacenamiento global (almacenado en el servidor).

El almacenamiento de usuarios mantiene solo las direcciones de envío de los envíadores que envían mensajes a los destinatarios correspondientes, y también refleja los puntajes corregidos/ aprendidos cuando algunos mensajes son marcados por el usuario como spam o ham, o cuando el envíador está bien listado o bloqueado por la API de SpamAssassin.

El almacenamiento global mantiene los datos de reputación de todos los mensajes procesados por SpamAssassin, con sus puntajes de spam y aprendidos por spam/ham de todos los usuarios en el servidor. Por lo tanto, el módulo devolverá un valor de reputación incluso para envíadores no conocidos por el destinatario actual, siempre que ya hayan enviado correo electrónico a alguien else en el servidor.

El valor del parámetro txrep_user2global_ratio controla el impacto de cada una de las dos reputaciones. Cuando es igual a 1, tanto el puntaje global como el puntaje de usuario tienen el mismo impacto en el resultado. Cuando se establece en 2, el puntaje tomado del almacenamiento de usuarios tendrá el doble de impacto que el puntaje global. El valor final del etiqueta TXREP se calcula así: 

total = (ratio * user + global) / (ratio + 1)

Cuando no se encuentra ninguna reputación en el almacenamiento de usuarios y hay un puntaje global disponible, se usará completamente el almacenamiento global sin aplicar el ratio.

Cuando el ratio se establece en 0, solo se utilizará el almacenamiento por defecto. Y entonces depende si se usa el almacenamiento global o el almacenamiento local (usado por el usuario) por defecto, lo cual se controla por el parámetro user_awl_sql_override_username (en caso de almacenamiento SQL) o el parámetro "/auto_welcomelist_path" (en caso de base de datos Berkeley).

Cuando esta almacenamiento dual está habilitada, y no hay almacenamiento global definido por los parámetros mencionados anteriormente para las bases de datos Berkeley o SQL, TxRep intentará usar un almacenamiento general - el usuario 'GLOBAL' en caso de SQL, y en caso de base de datos Berkeley usará el directorio definido por '__local_state_dir__/tx-reputation', que generalmente se renderiza como /var/db/spamassassin/tx-reputation. Cuando los almacenamientos por defecto no están disponibles o no son escritos, tendrías que definir el almacenamiento global con la ayuda de los parámetros "user_awl_sql_override_username" o "auto_welcomelist_path".

Por favor, notar que algunas instalaciones de SpamAssassin siempre se ejecutan bajo el mismo usuario ID. En tal caso, es inútil habilitar el almacenamiento dual, ya que resultaría en dos almacenamientos globales idénticos en diferentes ubicaciones.

Esta función está desactivada por defecto.

auto_welcomelist_distinguish_signed (default: 1 - enabled)
Antes de auto_welcomelist_distinguish_signed que será compatible hasta 4.1.

Usado por la implementación de la base de datos de listado de direcciones (SQLBasedAddrList).

Si esta opción está establecida, el módulo SQLBasedAddrList mantendrá entradas separadas para direcciones de correo electrónico validadas con DKIM y para las no validadas. Sin esta opción, o para dominios que no usan una firma DKIM, el puntaje de correo legítimo puede mezclarse con el puntaje de falsificaciones. También debe estar habilitado un plugin DKIM para que esta opción funcione. Esta opción es altamente recomendada. Excepto si estás usando una base de esquema anterior a 3.3.0 y no puedes actualizar, no hay razón para desactivar esta opción. Si estás actualizando desde AWL y usas una base de esquema anterior a 3.3.0, la columna txrep.signedby no existirá. Se recomienda agregar esta columna, pero si no es posible, debes establecer esta opción a 0 para evitar errores SQL.

txrep_spf
0 | 1                 (default: 1)

Cuando está activada, TxRep tratará cualquier dirección IP usando un correo electrónico dado como la misma identidad autorizada, y no asociará ninguna dirección IP con ella. (El mismo efecto ocurre con firmas DKIM válidas. No hay opción disponible para DKIM).

Nota: en dominios que definen SPF útil +all (pasar todo), ningún IP sería asociado con el correo electrónico, y todos los direcciones (incluidas las falsas) serían consideradas como provenientes de la fuente autorizada. Sin embargo, estos dominios son probablemente raros y lo solicitan ya sea así.

REPUTACIÓN PESOS

La reputación del remitente comprende varios elementos:

1) La reputación de la dirección de correo electrónico "From" asociada a la dirección IP de origen (ver los parámetros de máscara para más detalles)
2) La reputación de la dirección de correo electrónico "From" (sin importar la dirección IP actualmente utilizada)
3) La reputación del nombre del dominio de la dirección de correo electrónico "From"
4) La reputación de la dirección IP de origen, sin importar la dirección de correo electrónico del remitente
5) La reputación del nombre de la máquina de inicio (si está disponible)

Cada una de estas reputaciones parciales se pesa con el ayuda de estos parámetros, y la reputación total se calcula como la suma de las reputaciones individuales dividida por la suma de sus pesos:

sender_reputation = weight_email    * rep_email    +
                    weight_email_ip * rep_email_ip +
                    weight_domain   * rep_domain   +
                    weight_ip        * rep_ip       +
                    weight_helo      * rep_helo

Puedes desactivar las reputaciones parciales individuales estableciendo su peso en 0. Esto reducirá también el tamaño de la base de datos, ya que cada reputación parcial requiere una entrada separada en la tabla de la base de datos. Desactivar algunas de estas reputaciones puede también ayudar con la performance en servidores ocupados, ya que las consultas y procesos de base de datos se omitirán.

txrep_weight_email
range [0..10]          (default: 3)

Este factor de influencia controla la influencia de la reputación de la dirección de correo electrónica estándar, independientemente de la dirección IP de origen. Cuando se ajusta el peso, tienes que tener en cuenta que una dirección de correo electrónico puede ser fácilmente falsificada, por lo que los espías pueden usar direcciones de correo "from" pertenecientes a remitentes con buena reputación. Desde este punto de vista, la dirección de correo asociada a la dirección IP de origen es un indicador más confiable para la reputación general.

Por otro lado, algunos remitentes reputables pueden enviar mensajes desde múltiples direcciones IP, por lo que no tener en cuenta la dirección IP de origen al buscar la reputación de la dirección de correo estándar tiene algún sentido.

Se recomienda usar un valor relativamente bajo para esta reputación parcial.

txrep_weight_email_ip
range [0..10]          (default: 10)

Este es el peso estándar utilizado en el mismo modo que el original AWL plugin. Cada dirección de correo de un remitente está asociada a la dirección IP de origen, o a su parte según los parámetros txrep_ipv4_mask_len o txrep_ipv6_mask_len.

Para un usuario que envía desde múltiples ubicaciones, diferentes servidores de correo o desde un rango de IP dinámico fuera del bloque delimitado, su dirección de correo tendrá un valor de reputación separado para cada de las diferentes (parciales) direcciones IP.

Cuando el opción auto_welcomelist_distinguish_signed está habilitada, en contraste con el módulo original AWL, TxRep no registra la dirección IP cuando se detecta una firma DKIM. La dirección de correo no está asociada a ninguna dirección IP, sino solo al DKIM, ya que se considera que autentifica el remitente más confiable que la dirección IP (la cual también puede variar).

Este es el puntaje más relevante, y su peso debería ser alto.

txrep_weight_domain
range [0..10]          (default: 2)

القائمة_السوداء_/_قائمة_الترحيب

عندما يطلب SpamAssassin حظر مستخدم أو إضافته إلى قائمة الترحيب، يضيف المكون الإضافي TxRep نقاطًا قدرها 100 (للحظر) أو -100 (للقائمة الترحيبية) إلى عنوان البريد الإلكتروني للمرسل. إذا لم يكن هناك عنوان IP، يتم ضرب القيمة بنسبة مجموع نقاط السمعة الإجمالية إلى نقاط السمعة الفردية للبريد.

total_weight = weight_email + weight_email_ip + weight_domain + weight_ip + weight_helo
blocklisted_reputation = 100 * total_weight / weight_email

إذا تم حظر عنوان بريد إلكتروني فردي أو إضافته إلى القائمة الترحيبية، يتم حذف جميع السجلات من قاعدة البيانات المتعلقة بعنوان بريد إلكتروني مرتبط بعنوان IP، أو توقيع DKIM، أو اجتياز SPF. يتم الاحتفاظ بالسجل الفردي فقط.

بالإضافة إلى حظر عناوين البريد الإلكتروني الفردية أو إضافتها إلى قائمة الترحيب، يمكن استخدام نفس الطريقة لحظر عناوين IP أو المجالات أو أسماء HELO (يُسمح فقط بأسماء HELO بدون نقطة) أو إضافتها إلى قائمة الترحيب.

عند إضافة عناوين البريد الإلكتروني أو المجالات إلى قائمة الترحيب أو القائمة السوداء، يمكنك ربطها بتوقيع DKIM محدد أو سجل SPF، بإضافة اسم المجال الذي تم توقيعه أو العلامة 'spf' بعد المعرف على النحو التالي:

spamassassin --add-addr-to-blocklist=spamming.biz,spf
spamassassin --add-addr-to-welcomelist=friend@good.org,good.org

عندما يحتوي البريد على توقيع DKIM واجتياز SPF، يكون لتوقيع DKIM الأولوية، لذلك لن يتم التحقق من السجل المرتبط بالعلامة 'spf'. يمكن ربط عناوين البريد الإلكتروني والمجالات فقط بـ DKIM أو SPF. لا تحتوي سجلات عناوين IP وأسماء HELO على DKIM/SPF.

في حالة التخزين المزدوج، يتم إجراء الحظر أو القائمة الترحيبية على التخزين الافتراضي فقط.

منطق_السمعة

1. المعرف الأكثر أهمية هو نفس AWL، أي مزيج من عنوان البريد الإلكتروني وعنوان IP المصدر، أو جزء منه المحدد بواسطة قناع IPv4 أو IPv6.

2. لا يتم التحقق من IP لسمعة البريد الفردية.

3. لا يتم التحقق من التوقيع لسمعة IP أو لسمعة اسم HELO.

4. يتم استخدام وزن سمعة IP للبريد، وليس وزن السمعة الفردية للبريد فقط، عندما لا يكون عنوان IP متاحًا (سمعة IP للبريد هي المؤشر الرئيسي، ولها أعلى وزن).

5. لا يتم التحقق من IP في رسائل البريد الموقعة (التوقيع يصادق على عنوان البريد الإلكتروني بدلاً من عنوان IP).

6. لا يتم التحقق من IP في اجتياز SPF (نفترض أن مالك المجال مسؤول عن جميع عناوين IP التي يسمح بإرسالها، لذلك نستخدم توقيع DKIM/SPF).

NAME

Mail::SpamAssassin::Plugin::TxRep - Track and store sender reputation

SYNOPSIS

This plugin tracks and stores sender reputation, ie. how often a sender (or domain, or IP address) has been seen sending spam or legitimate mail in the past. It uses this information to score incoming mail.

The plugin requires a database for storing the reputation data. This can be a Berkeley DB file or an SQL database.

In order to use this plugin, you have to load it in your user_prefs.cf file:

loadplugin Mail::SpamAssassin::Plugin::TxRep

DESCRIPTION

TxRep plugin is designed to keep track of reputation of senders, domains and IP addresses. It stores this information in a database and uses it to score incoming mail. The higher the reputation score, the more likely it is that the sender is a spammer.

The plugin supports several types of reputation tracking:

EMAIL:
Reputation of the full email address (e.g. user@example.com).
EMAIL_IP:
Reputation of the combination of email address and the sending IP address.
DOMAIN:
Reputation of the domain part of the email address (e.g. example.com).
IP:
Reputation of the sending IP address.
HELO:
Reputation of the HELO string used by the sending mail server.

The plugin uses a combination of these identifiers to determine the reputation of a sender. For example, a specific email address might have a good reputation, but if it's sent from a known spamming IP address, the overall reputation might be lowered.

The plugin's behavior and scoring can be configured through various options in SpamAssassin's configuration files.

TEMPLATE TAGS

The following template tags are available for use in message templates:

TXREP_EMAIL_SCORE:
The reputation score for the sender's email address.
TXREP_EMAIL_IP_SCORE:
The reputation score for the sender's email address and IP address combination.
TXREP_DOMAIN_SCORE:
The reputation score for the sender's domain.
TXREP_IP_SCORE:
The reputation score for the sender's IP address.
TXREP_HELO_SCORE:
The reputation score for the sender's HELO string.
TXREP_GLOBAL_SCORE:
The overall reputation score calculated by the TxRep plugin.

USER PREFERENCES

The following options can be set in the user's user_prefs.cf file:

txrep_learn_penalty
The amount to subtract from a sender's reputation when a message is learned as spam. Default is 1.
txrep_learn_bonus
The amount to add to a sender's reputation when a message is learned as ham. Default is 1.
txrep_autolearn_penalty
The amount to subtract from a sender's reputation when a message is automatically learned as spam. Default is 1.
txrep_autolearn_bonus
The amount to add to a sender's reputation when a message is automatically learned as ham. Default is 1.
txrep_welcomelist_out
If set to 1 (default), entries in the welcomelist are used to increase the reputation of senders. If set to 0, welcomelist entries are ignored for reputation purposes.
txrep_welcomelist_distinguish_signed
If set to 1 (default), signed messages are treated differently from unsigned messages when calculating reputation based on welcomelist entries. If set to 0, all messages are treated the same.

ADMINISTRATOR SETTINGS

The following options can be set in the main local.cf or v311.pre file:

use_txrep
Enable or disable the TxRep plugin. Default is 1 (enabled).
txrep_db_path
Path to the Berkeley DB file used for storing reputation data. If this is not set, TxRep will try to use an SQL database.
txrep_sql_dsn
Data Source Name for the SQL database. For example: DB_File=sqlite:/path/to/txrep.db.
txrep_sql_username
Username for connecting to the SQL database.
txrep_sql_password
Password for connecting to the SQL database.
txrep_user2global_ratio
Ratio of user-specific reputation to global reputation. A value of 1 means user and global reputations are treated equally. A value of 0 disables user-specific reputation tracking. Default is 1.
txrep_track_messages
If set to 1 (default), TxRep tracks reputation for individual messages. If set to 0, reputation is tracked based on aggregated data.
txrep_autolearn
If set to 1 (default), TxRep automatically learns messages as spam or ham based on scoring. If set to 0, automatic learning is disabled.
txrep_welcomelist_out
If set to 1 (default), welcomelist entries are used to boost sender reputation. If set to 0, welcomelist entries are ignored.
auto_welcomelist_distinguish_signed
If set to 1 (default), signed messages are treated differently from unsigned messages when calculating reputation from welcomelist entries. This can reduce database size by not storing separate entries for each IP address of signed messages.

BLOCKLISTING / WELCOMELISTING

TxRep plugin integrates with SpamAssassin's blocklisting and welcomelisting features. When a message is determined to be spam, the sender's reputation is lowered. Conversely, when a message is determined to be legitimate, the sender's reputation is increased.

The plugin uses the following identifiers for reputation tracking:

EMAIL:
The full email address (e.g., user@example.com).
EMAIL_IP:
The combination of the email address and the sending IP address.
DOMAIN:
The domain part of the email address (e.g., example.com).
IP:
The sending IP address.
HELO:
The HELO string used by the sending mail server.

The plugin uses the following rules for reputation updates:

1. When a message is learned as spam, the reputation score for all relevant identifiers (EMAIL, EMAIL_IP, DOMAIN, IP, HELO) is decreased by the value of "txrep_learn_penalty".

2. When a message is learned as ham, the reputation score for all relevant identifiers is increased by the value of "txrep_learn_bonus".

3. When a message is automatically learned as spam (autolearn), the reputation score is decreased by "txrep_autolearn_penalty".

4. When a message is automatically learned as ham, the reputation score is increased by "txrep_autolearn_bonus".

5. If "txrep_welcomelist_out" is enabled, entries in the welcomelist (both global and user-specific) will increase the reputation scores of the corresponding identifiers.

6. If "auto_welcomelist_distinguish_signed" is enabled, and the message is signed, the IP address is ignored for reputation updates. This helps to reduce the database size by avoiding multiple entries for the same sender if they send from different IPs.

7. No signature is used for standalone EMAIL reputation, as it would be redundant with EMAIL_IP reputation and would result in duplicate entries.

8. When available, the DKIM signer is used instead of the domain name for DOMAIN reputation.

9. No IP address or signature is used for HELO reputation, even if multiple computers might share the same HELO string.

10. The full (unmasked IP) address is used in the address field (instead of the IP field) for standalone IP reputation.

REPUTATION LOGICS

The plugin calculates reputation scores based on the following logic:

1. **EMAIL reputation:** Based on the full sender email address. This is the most specific identifier.

2. **EMAIL_IP reputation:** Based on the combination of sender email address and the sending IP address. This is more specific than EMAIL or IP reputation alone.

3. **DOMAIN reputation:** Based on the domain part of the sender email address. This is useful for tracking reputation of entire domains.

4. **IP reputation:** Based on the sending IP address. This is a general indicator of sender reputation.

5. **HELO reputation:** Based on the HELO string used by the sending mail server. This can help identify mail servers with suspicious HELO names.

The plugin prioritizes more specific identifiers when available. For example, if both EMAIL_IP and IP reputations are available, the EMAIL_IP reputation might be given more weight.

The plugin also supports dual storage, where reputation is tracked both globally and per user. The "txrep_user2global_ratio" setting controls the balance between user-specific and global reputation.

LEARNING SPAM / HAM

When SpamAssassin is instructed to learn (or relearn) a message as spam or ham, all relevant reputations for the message (email, email_ip, domain, ip, helo) in both global and user storages are updated using the "txrep_learn_penalty" and "rxrep_learn_bonus" values, respectively. The new reputation for a given sender property (email, domain, etc.) will be the result of one of the following formulas:

new_reputation = old_reputation + learn_penalty
new_reputation = old_reputation - learn_bonus

The TxRep plugin currently tracks each message individually. This means it does not detect when a message is learned repeatedly. It will add/subtract the penalty/bonus score each time the message is fed to the spam learner.

OPTIMIZING TXREP

TxRep can be optimized for speed and simplicity, or for precision in assigning reputation scores.

First, TxRep can be quickly disabled and re-enabled using the option "use_txrep". This can be done globally or individually in each respective "user_prefs". Disabling TxRep does not destroy the database, so it can be re-enabled at any time later.

On many systems, SQL-based storage may perform faster than the default Berkeley DB storage, so consider setting it up.

There are also multiple settings that can reduce the number of records stored in the database, thus reducing storage size and processing time:

1. Setting "txrep_user2global_ratio" to zero disables dual storage, effectively halving disk space requirements and plugin processing times.

2. You can disable all but one of the "REPUTATION WEIGHTS". EMAIL_IP is the most specific option, making it the most likely choice in such a scenario, but the reputation system could be based on any of the remaining scores. Each enabled reputation adds a new entry to the database for each new identifier. Therefore, while the number of recorded and scored domains might be large, the number of stored IP addresses will likely be higher, requiring more storage space.

3. Disabling "txrep_track_messages" avoids storing a separate entry for every scanned message, thus reducing disk space requirements and processing time.

4. Disabling the "txrep_autolearn" option saves processing time on messages that trigger the auto-learning process.

5. Disabling "txrep_welcomelist_out" reduces processing time on outbound connections.

6. Keeping the option "auto_welcomelist_distinguish_signed" enabled may slightly help reduce the database size. For signed messages, the originating IP address is ignored, thus eliminating the need for additional database entries for each separate IP address (or a masked block of IP addresses).

Since TxRep reuses the storage architecture of the former AWL plugin, the same instructions apply for initializing the SQL storage for TxRep. Although the old AWL table can be reused for TxRep, TxRep expects the SQL table to be named "txrep" by default.

To install a new SQL table for TxRep, run the appropriate SQL file for your system under the /sql directory.

If you encounter a syntax error on an older MySQL version, use TYPE=MyISAM instead of ENGINE=MyISAM at the end of the command. You can also use other ENGINE types (depending on what is available on your system). For example, the MEMORY engine stores the entire table in server memory, achieving performance similar to Redis. You would need to ensure replication of the RAM table to disk via a cronjob to avoid data loss upon reboot. The InnoDB engine is used by default, offering high scalability (database size and access concurrency). In conjunction with a high value for innodb_buffer_pool or with the memcached plugin (MySQL v5.6+), it can also offer performance comparable to Redis.
