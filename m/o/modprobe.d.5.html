NAME

\n

modprobe.d - Configuration directory for modprobe

\n
\n
\n

SYNOPSIS

\n

/etc/modprobe.d/*.conf

\n

/run/modprobe.d/*.conf

\n

/usr/local/lib/modprobe.d/*.conf

\n

/usr/lib/modprobe.d/*.conf

\n

/lib/modprobe.d/*.conf

\n
\n
\n

DESCRIPTION

\n

Because the modprobe command can add or remove more than\n one module, due to modules having dependencies, we need a method of\n specifying what options are to be used with those modules. One can also use\n them to create convenient aliases: alternate names for a module, or they can\n override the normal modprobe behavior altogether for those with\n special requirements (such as inserting more than one module).

\n

Note that module and alias names (like other module names) can\n have - or _ in them: both are interchangeable throughout all the module\n commands as underscore conversion happens automatically.

\n
\n
\n

CONFIGURATION FORMAT

\n

The configuration files contain one command per line, with blank\n lines and lines starting with '#' ignored (useful for adding comments). A\n '\\' at the end of a line causes it to continue on the next line, which makes\n the files a bit neater.

\n

See the COMMANDS section below for more.

\n
\n
\n

CONFIGURATION DIRECTORIES AND PRECEDENCE

\n

Configuration files are read from directories in listed in\n SYNOPSIS in that order of precedence. Once a file of a given filename is\n loaded, any file of the same name in subsequent directories is ignored.

\n

All configuration files are sorted in lexicographic order,\n regardless of the directory they reside in. Configuration files can either\n be completely replaced (by having a new configuration file with the same\n name in a directory of higher priority) or partially replaced (by having a\n configuration file that is ordered later).

\n

NOTE: The configuration directories may be altered via the\n MODPROBE_OPTIONS environment variable. See the ENVIRONMENT section in\n modprobe(8).

\n
\n
\n

COMMANDS

\n

alias wildcard modulename

\n
This allows you to give alternate names for a module. For\n example: "alias my-mod really_long_modulename" means you can use\n "modprobe my-mod" instead of "modprobe\n really_long_modulename". You can also use shell-style wildcards, so\n "alias my-mod* really_long_modulename" means that "modprobe\n my-mod-something" has the same effect. You can't have aliases to other\n aliases (that way lies madness), but aliases can have options, which will be\n added to any other options.\n

Note that modules can also contain their own aliases, which you\n can see using modinfo. These aliases are used as a last resort (ie.\n if there is no real module, install, remove, or alias\n command in the configuration).

\n
\n

blacklist modulename

\n
Modules can contain their own aliases: usually these are\n aliases describing the devices they support, such as "pci:123...". \n These "internal" aliases can be overridden by normal\n "alias" keywords, but there are cases where two or more modules both\n support the same devices, or a module invalidly claims to support a device\n that it does not: the blacklist keyword indicates that all of that\n particular module's internal aliases are to be ignored.
\n

install modulename command...

\n
This command instructs modprobe to run your\n command instead of inserting the module in the kernel as normal. The command\n can be any shell command: this allows you to do any kind of complex processing\n you might wish. For example, if the module "fred" works better with\n the module "barney" already installed (but it doesn't depend on it, \n so modprobe won't automatically load it), you could say "install\n fred /sbin/modprobe barney; /sbin/modprobe --ignore-install fred", which\n would do what you wanted. Note the --ignore-install, which stops the\n second modprobe from running the same install command again. See\n also remove below.\n

The long term future of this command as a solution to the problem\n of providing additional module dependencies is not assured and it is\n intended to replace this command with a warning about its eventual removal\n or deprecation at some point in a future release. Its use complicates the\n automated determination of module dependencies by distribution utilities,\n such as mkinitrd (because these now need to somehow interpret what the\n install commands might be doing. In a perfect world, modules would\n provide all dependency information without the use of this command and work\n is underway to implement soft dependency support within the Linux\n kernel.

\n

If you use the string "$CMDLINE_OPTS" in the command, it\n will be replaced by any options specified on the modprobe command line. This\n can be useful because users expect "modprobe fred opt=1" to pass\n the "opt=1" arg to the module, even if there's an install command\n in the configuration file. So our above example becomes "install fred\n /sbin/modprobe barney; /sbin/modprobe --ignore-install fred\n $CMDLINE_OPTS"

\n
\n

options modulename option...

\n
This command allows you to add options to the module\n modulename (which might be an alias) every time it is inserted into the\n kernel: whether directly (using modprobe modulename) or because\n the module being inserted depends on this module.\n

All options are added together: they can come from an\n option for the module itself, for an alias, and on the command\n line.

\n
\n

remove modulename command...

\n
This is similar to the install command above,\n except it is invoked when "modprobe -r" is run.
\n

softdep modulename pre: modules... post: \n modules...

\n
The softdep command allows you to specify soft, or\n optional, module dependencies. modulename can be used without these\n optional modules installed, but usually with some features missing. For\n example, a driver for a storage HBA might require another module be loaded in\n order to use management features.\n

pre-deps and post-deps modules are lists of names and/or aliases\n of other modules that modprobe will attempt to install (or remove) in order\n before and after the main module given in the modulename\n argument.

\n

Example: Assume "softdep c pre: a b post: d e" is\n provided in the configuration. Running "modprobe c" is now\n equivalent to "modprobe a b c d e" without the softdep. Flags such\n as --use-blacklist are applied to all the specified modules, while module\n parameters only apply to module c.

\n

Note: if there are install or remove commands with\n the same modulename argument, softdep takes precedence.

\n
\n

weakdep modulename modules...

\n
The weakdep command allows you to specify weak\n module dependencies. Those are similar to pre softdep, with the difference\n that userspace doesn't attempt to load that dependency before the specified\n module. Instead the kernel may request one or multiple of them during module\n probe, depending on the hardware it's binding to. The purpose of weak module\n is to allow a driver to specify that a certain dependency may be needed, so it\n should be present in the filesystem (e.g. in initramfs) when that module is\n probed.\n

Example: Assume "weakdep c a b". A program creating an\n initramfs knows it should add a, b, and c to the filesystem since a and b\n may be required/desired at runtime. When c is loaded and is being probed, it\n may issue calls to request_module() causing a or b to also be loaded.

\n

الوصف

\n

بما أن الأمر modprobe يمكنه إضافة أو إزالة أكثر من وحدة نمطية بسبب تبعيات الوحدات النمطية، نحتاج إلى طريقة لتحديد الخيارات التي يجب استخدامها مع تلك الوحدات النمطية. يمكن للمرء أيضًا استخدامها لإنشاء أسماء مستعارة ملائمة: أسماء بديلة لوحدة نمطية، أو يمكنها تجاوز السلوك الطبيعي للأمر modprobe تمامًا لأولئك الذين لديهم متطلبات خاصة (مثل إدراج أكثر من وحدة نمطية).

\n

لاحظ أن أسماء الوحدات النمطية والأسماء المستعارة (مثل أسماء الوحدات النمطية الأخرى) يمكن أن تحتوي على - أو _: كلاهما قابل للتبديل في جميع أوامر الوحدات النمطية حيث يتم تحويل الشرطة السفلية تلقائيًا.

\n
\n
\n

تنسيق الإعدادات

\n

تحتوي ملفات الإعدادات على أمر واحد في كل سطر، مع تجاهل الأسطر الفارغة والأسطر التي تبدأ بـ '#' (مفيد لإضافة التعليقات). يتسبب وجود '\' في نهاية السطر في استمراره في السطر التالي، مما يجعل الملفات أكثر ترتيبًا.

\n

انظر قسم الأوامر أدناه لمزيد من التفاصيل.

\n
\n
\n

أدلة الإعدادات والأسبقية

\n

يتم قراءة ملفات الإعدادات من الأدلة المدرجة في الموجز بهذا الترتيب من حيث الأسبقية. بمجرد تحميل ملف بنفس اسم الملف في دليل لاحق، يتم تجاهله.

\n

يتم فرز جميع ملفات الإعدادات بترتيب أبجدي، بغض النظر عن الدليل الذي تنتمي إليه. يمكن استبدال ملفات الإعدادات بالكامل (عن طريق وجود ملف إعدادات جديد بنفس الاسم في دليل ذي أولوية أعلى) أو استبدالها جزئيًا (عن طريق وجود ملف إعدادات بترتيب لاحق).

\n

ملاحظة: يمكن تغيير أدلة الإعدادات عبر متغير البيئة MODPROBE_OPTIONS. انظر قسم البيئة في modprobe(8).

\n
\n

الأوامر

\n

alias wildcard modulename

\n
يسمح لك هذا بإعطاء أسماء بديلة لوحدة نمطية. على سبيل المثال: \"alias my-mod really_long_modulename\" يعني أنه يمكنك استخدام \"modprobe my-mod\" بدلاً من \"modprobe really_long_modulename\". يمكنك أيضًا استخدام أحرف بدل بأسلوب shell، لذا فإن \"alias my-mod* really_long_modulename\" يعني أن \"modprobe my-mod-something\" له نفس التأثير. لا يمكنك إنشاء أسماء مستعارة لوحدات نمطية أخرى (هذا يقود إلى الجنون)، ولكن يمكن للأسماء المستعارة أن تحتوي على خيارات، والتي ستضاف إلى أي خيارات أخرى.\n

لاحظ أن الوحدات النمطية يمكن أن تحتوي أيضًا على أسمائها المستعارة الخاصة، والتي يمكنك رؤيتها باستخدام modinfo. تُستخدم هذه الأسماء المستعارة كحل أخير (أي إذا لم يكن هناك أمر حقيقي للوحدة النمطية، أو أمر install، أو remove، أو alias في الإعدادات).

\n
\n

blacklist modulename

\n
يمكن للوحدات النمطية أن تحتوي على أسمائها المستعارة الخاصة: عادةً ما تكون هذه أسماء مستعارة تصف الأجهزة التي تدعمها، مثل \"pci:123...\". يمكن تجاوز هذه الأسماء المستعارة \"الداخلية\" بواسطة كلمات مفتاحية \"alias\" عادية، ولكن هناك حالات يكون فيها وحدتان نمطيتان أو أكثر تدعمان نفس الأجهزة، أو تدعي وحدة نمطية بشكل غير صحيح أنها تدعم جهازًا لا تدعمه: تشير الكلمة المفتاحية blacklist إلى تجاهل جميع الأسماء المستعارة الداخلية لتلك الوحدة النمطية المحددة.
\n

install modulename command...

\n
يُعلم هذا الأمر modprobe بتشغيل الأمر الخاص بك بدلاً من إدراج الوحدة النمطية في النواة كالمعتاد. يمكن أن يكون الأمر أي أمر shell: هذا يسمح لك بإجراء أي نوع من المعالجة المعقدة قد ترغب فيه. على سبيل المثال، إذا كانت الوحدة النمطية \"fred\" تعمل بشكل أفضل مع الوحدة النمطية \"barney\" المثبتة بالفعل (لكنها لا تعتمد عليها، لذا لن يقوم modprobe بتحميلها تلقائيًا)، يمكنك قول \"install fred /sbin/modprobe barney; /sbin/modprobe --ignore-install fred\"، مما سيؤدي إلى ما تريده. لاحظ --ignore-install، الذي يمنع الأمر modprobe الثاني من تشغيل نفس أمر install مرة أخرى. انظر أيضًا remove أدناه.\n

المستقبل طويل الأجل لهذا الأمر كحل لمشكلة توفير تبعيات إضافية للوحدات النمطية غير مضمون ومن المعتزم استبدال هذا الأمر بتحذير بشأن إزالته أو إيقافه في نهاية المطاف في إصدار مستقبلي. استخدامه يعقد التحديد التلقائي لتبعيات الوحدات النمطية بواسطة أدوات التوزيع، مثل mkinitrd (لأن هذه تحتاج الآن إلى تفسير ما قد تقوم به أوامر install بطريقة ما. في عالم مثالي، ستوفر الوحدات النمطية جميع معلومات التبعية دون استخدام هذا الأمر، ويجري العمل على تنفيذ دعم التبعية الناعمة داخل نواة Linux.

\n

إذا استخدمت السلسلة \"$CMDLINE_OPTS\" في الأمر، فسيتم استبدالها بأي خيارات محددة في سطر أوامر modprobe. يمكن أن يكون هذا مفيدًا لأن المستخدمين يتوقعون أن \"modprobe fred opt=1\" يمرر وسيطة \"opt=1\" إلى الوحدة النمطية، حتى لو كان هناك أمر install في ملف الإعدادات. لذلك يصبح مثالنا أعلاه \"install fred /sbin/modprobe barney; /sbin/modprobe --ignore-install fred $CMDLINE_OPTS\"

\n
\n

options modulename option...

\n
يسمح لك هذا الأمر بإضافة خيارات إلى الوحدة النمطية modulename (التي قد تكون اسمًا مستعارًا) في كل مرة يتم فيها إدراجها في النواة: سواء بشكل مباشر (باستخدام modprobe modulename) أو لأن الوحدة النمطية التي يتم إدراجها تعتمد على هذه الوحدة النمطية.\n

تُضاف جميع الخيارات معًا: يمكن أن تأتي من option للوحدة النمطية نفسها، أو من اسم مستعار، أو من سطر الأوامر.

\n
\n

remove modulename command...

\n
هذا مشابه لأمر install أعلاه، باستثناء أنه يتم استدعاؤه عند تشغيل \"modprobe -r\".
\n

softdep modulename pre: modules... post: \n modules...

\n
يسمح الأمر softdep لك بتحديد تبعيات وحدات نمطية ناعمة أو اختيارية. يمكن استخدام modulename بدون تثبيت الوحدات النمطية الاختيارية هذه، ولكن عادةً ما تكون بعض الميزات مفقودة. على سبيل المثال، قد يتطلب مشغل HBA للتخزين تحميل وحدة نمطية أخرى لاستخدام ميزات الإدارة.\n

تُعد قوائم pre-deps و post-deps أسماء و/أو أسماء مستعارة لوحدات نمطية أخرى سيحاول modprobe تثبيتها (أو إزالتها) بالترتيب قبل وبعد الوحدة النمطية الرئيسية المحددة في الوسيط modulename.

\n

مثال: افترض وجود \"softdep c pre: a b post: d e\" في الإعدادات. تشغيل \"modprobe c\" يعادل الآن \"modprobe a b c d e\" بدون softdep. تُطبق الأعلام مثل --use-blacklist على جميع الوحدات النمطية المحددة، بينما تنطبق معلمات الوحدة النمطية فقط على الوحدة النمطية c.

\n

ملاحظة: إذا كانت هناك أوامر install أو remove بنفس الوسيط modulename، فإن softdep له الأسبقية.

\n
\n

weakdep modulename modules...

\n
يسمح لك الأمر weakdep بتحديد تبعيات وحدات نمطية ضعيفة. هذه مشابهة لـ pre softdep، مع الاختلاف أن مساحة المستخدم لا تحاول تحميل هذه التبعية قبل الوحدة النمطية المحددة. بدلاً من ذلك، قد تطلب النواة وحدة واحدة أو أكثر منها أثناء فحص الوحدة النمطية، اعتمادًا على الأجهزة التي ترتبط بها. الغرض من الوحدات النمطية الضعيفة هو السماح للمشغل بتحديد أن تبعية معينة قد تكون مطلوبة، لذا يجب أن تكون موجودة في نظام الملفات (مثل initramfs) عند فحص هذه الوحدة النمطية.\n

مثال: افترض \"weakdep c a b\". برنامج ينشئ initramfs يعرف أنه يجب إضافة a، b، و c إلى نظام الملفات نظرًا لأن a و b قد تكون مطلوبة/مرغوبة في وقت التشغيل. عند تحميل c وفحصه، قد يصدر استدعاءات لـ request_module() مما يتسبب في تحميل a أو b أيضًا.
