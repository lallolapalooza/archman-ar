Module__Build__Authoring(3pm)

الحزمة: perl-module-build

التراخيص: PerlArtistic, GPL

Module::Build::Authoring(3pm) توثيق مقدم من المساهمين في Perl Module::Build::Authoring(3pm)

الاسم

Module::Build::Authoring - تأليف وحدات Module::Build

الوصف

عند إنشاء سكربت "Build.PL" لوحدة، يتم عادةً استخدام كود مشابه لما يلي:

use Module::Build;
my $build = Module::Build->new
  (
   module_name => 'Foo::Bar',
   license  => 'perl',
   requires => {
                'perl'          => '5.6.1',
                'Some::Module'  => '1.23',
                'Other::Module' => '>= 1.2, != 1.5, < 2.0',
               },
  );
$build->create_build_script;

يمكن لوحدة بسيطة أن تكتفي بسكربت "Build.PL" قصير كهذا:

use Module::Build;
Module::Build->new(
  module_name => 'Foo::Bar',
  license     => 'perl',
)->create_build_script;

النموذج الذي تستخدمه "Module::Build" يشبه إلى حد كبير استعارة "MakeMaker"، مع التطابقات التالية:

 في Module::Build                 في ExtUtils::MakeMaker
---------------------------      ------------------------
 Build.PL (السكربت الأولي)        Makefile.PL (السكربت الأولي)
 Build (سكربت perl قصير)         Makefile (Makefile طويل)
 _build/ (معلومات الحالة المحفوظة)       نصوص تكوين مختلفة في Makefile

يمكن إجراء أي تخصيص ببساطة عن طريق إنشاء فئة فرعية من "Module::Build" وإضافة طريقة تسمى (على سبيل المثال) "ACTION_test"، مع تجاوز الإجراء الافتراضي 'test'. يمكنك أيضًا إضافة طريقة تسمى "ACTION_whatever"، وبعد ذلك يمكنك تنفيذ الإجراء "Build whatever".

للحصول على معلومات حول توفير التوافق مع "ExtUtils::MakeMaker"، راجع Module::Build::Compat و http://www.makemaker.org/wiki/index.cgi?ModuleBuildConversionGuide.

الهيكل

تقوم Module::Build بإنشاء تسلسل هرمي للفئات يسهل تخصيصه. هذا هو التسلسل الهرمي للفئات الأصل-الفرع في فن ASCII الراقي:

/--------------------\
|   Your::Parent     |  (إذا قمت بإنشاء فئة فرعية من Module::Build)
\--------------------/
         |
         |
/--------------------\  (لا تحدد أي وظائف
|   Module::Build    |   خاصة بها - فقط تحدد أي
\--------------------/   وحدات أخرى سيتم تحميلها.)
         |
         |
/-----------------------------------\  (قد تحدد بعض قيم $^O
|   Module::Build::Platform::$^O    |   وظائف متخصصة.
\-----------------------------------/   بخلاف ذلك تكون ...::Default،
         |                              فئة مرور.)
         |
/--------------------------\
|   Module::Build::Base    |  (يتم تعريف معظم وظائف
\--------------------------/   Module::Build هنا.)

إنشاء فئة فرعية

في الوقت الحالي، هناك طريقتان لإنشاء فئة فرعية من Module::Build. الطريقة الأولى هي إنشاء وحدة عادية (في ملف ".pm") ترث من Module::Build، واستخدام فئة هذه الوحدة بدلاً من استخدام Module::Build مباشرة:

------ في Build.PL: ----------
#!/usr/bin/perl
use lib q(/nonstandard/library/path);
use My::Builder;  # أو أي اسم آخر تريده
my $build = My::Builder->new
  (
   module_name => 'Foo::Bar',  # جميع الوسائط العادية...
   license     => 'perl',
   dist_author => 'A N Other <me@here.net.au>',
   requires    => { Carp => 0 }
  );
$build->create_build_script;

هذا مباشر نسبيًا، وهو أفضل طريقة للقيام بالأشياء إذا كانت فئتك My::Builder تحتوي على الكثير من التعليمات البرمجية. ستضمن طريقة create_build_script() أن يتم تمرير القيمة الحالية لـ @INC (بما في ذلك "/nonstandard/library/path") إلى سكربت البناء، بحيث يمكن العثور على My::Builder عند تشغيل إجراءات البناء. إذا وجدت أنك بحاجة إلى "chdir" إلى دليل مختلف في طرق أو إجراءات الفئة الفرعية الخاصة بك، فتأكد دائمًا من العودة إلى الدليل الأصلي (المتاح عبر طريقة base_dir()) قبل إعادة التحكم إلى الفئة الأصل. هذا مهم لتجنب مشاكل تسلسل البيانات.

للإضافات الصغيرة جدًا، توفر Module::Build طريقة subclass() تتيح لك إنشاء فئة فرعية من Module::Build بشكل أكثر ملاءمة، دون إنشاء ملف منفصل لوحدتك:

------ في Build.PL: ----------
#!/usr/bin/perl
use Module::Build;
my $class = Module::Build->subclass
  (
   class => 'My::Builder',
   code => q{
     sub ACTION_foo {
       print "I'm fooing to death!\n";
     }
   },
  );
my $build = $class->new
  (
   module_name => 'Foo::Bar',  # جميع الوسائط العادية...
   license     => 'perl',
   dist_author => 'A N Other <me@here.net.au>',
   requires    => { Carp => 0 }
  );
$build->create_build_script;

في الكواليس، يقوم هذا فعليًا بإنشاء ملف ".pm"، نظرًا لأن التعليمات البرمجية التي تقدمها يجب أن تستمر بعد تشغيل Build.PL إذا كانت ستكون مفيدة جدًا.

راجع أيضًا توثيق طريقة "subclass()" في Module::Build::API.

المتطلبات المسبقة

أنواع المتطلبات المسبقة

لتحديد إصدارات الوحدات الأخرى التي تستخدمها هذه التوزيعة، يمكن تعريف عدة أنواع من المتطلبات المسبقة باستخدام المعلمات التالية:

configure_requires
العناصر التي يجب تثبيتها قبل تكوين هذه التوزيعة (أي قبل تشغيل سكربت Build.PL). قد يكون هذا إصدارًا أدنى محددًا من "Module::Build" أو أي وحدة أخرى يحتاجها سكربت Build.PL للقيام بعمله. يُتوقع من العملاء مثل "CPAN.pm" أو "CPANPLUS" استخلاص "configure_requires" من ملف META.yml وتثبيت هذه العناصر قبل تشغيل "Build.PL".

إذا لم يتم تحديد configure_requires، تتم إضافة الإصدار الحالي من Module::Build تلقائيًا إلى configure_requires.

build_requires
العناصر الضرورية لبناء واختبار هذه التوزيعة، ولكنها ليست ضرورية بعد التثبيت. يمكن أن يساعد هذا المستخدمين الذين يرغبون فقط في تثبيت هذه العناصر مؤقتًا. كما أنه يساعد في تقليل حجم الرسم البياني لتفاعلات CPAN إذا لم يتم دمج كل شيء في "requires".
requires
العناصر الضرورية للتشغيل الأساسي.
recommends
العناصر الموصى بها لوظائف محسنة، ولكن هناك طرق لاستخدام هذه التوزيعة بدون تثبيتها. يمكنك أيضًا التفكير في هذا على أنه "يمكن استخدامه" أو "يعرف بـ" أو "يغير السلوك في وجود".
test_requires
العناصر الضرورية للاختبار.
conflicts
العناصر التي يمكن أن تسبب مشاكل لهذه التوزيعة عند تثبيتها. هذا نادر جدًا.

تنسيق المتطلبات المسبقة

يتم تقديم المتطلبات المسبقة في مرجع هاش (hash reference)، حيث تكون المفاتيح هي أسماء الوحدات والقيم هي محددات الإصدار:

requires => {
             Foo::Module => '2.4',
             Bar::Module => 0,
             Ken::Module => '>= 1.2, != 1.5, < 2.0',
             perl => '5.6.0'
            },

لمحددات الإصدار الأربعة المذكورة أعلاه تأثيرات مختلفة. القيمة '2.4' تعني أنه يجب تثبيت إصدار 2.4 على الأقل من "Foo::Module". القيمة 0 تعني أن أي إصدار من "Bar::Module" مقبول، حتى لو كان "Bar::Module" د
