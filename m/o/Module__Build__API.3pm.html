[version 0.37]

سيقوم هذا تلقائيًا بفعل الشيء الصحيح بناءً على "dist_version" و "release_status". عندما لا تحتوي "dist_version" على شرطة ولا تكون "release_status" 'stable'، فإن القيمة الافتراضية لـ "dist_suffix" ستكون 'TRIAL'. بخلاف ذلك، سيتم استخدام القيم الافتراضية، والتي تقوم بتعطيل اللاحقة.

بشكل عام، يجب على المؤلفين تعيين هذا فقط إذا كان **لغرض محدد** يجب عليهم تجاوز السلوك الافتراضي.

dist_version_from
[version 0.11]

يحدد ملفًا للبحث فيه عن إصدار التوزيع. نادرًا ما يحتاج المؤلفون إلى تعيينه مباشرة، يمكنهم استخدام "module_name" لتعيينه إلى قيمة افتراضية معقولة.

يتم استخراج الإصدار من هذا الملف وفقًا لنفس القواعد التي تتبعها ExtUtils::MakeMaker و "CPAN.pm". يتضمن العثور على السطر الأول الذي يطابق النمط المنتظم:

/([\$*])(([\w\:\']*)\bVERSION)\b.*\=/

تقييم() هذا السطر، ثم التحقق من قيمة متغير $VERSION. على الرغم من بشاعته، إلا أن جميع الوحدات في CPAN تعتمد على هذه العملية، لذلك لا توجد فرصة حقيقية للتغيير إلى شيء أفضل.

إذا كان الملف المستهدف لـ "dist_version_from" يحتوي على أكثر من تعريف حزمة واحد، فسيكون الإصدار المُرجع هو الذي يتوافق مع وحدة "module_name" المحددة.

PL_files
[الإصدار 0.06]

معامل اختياري يحدد مجموعة من ".PL" الملفات في توزيعك. سيتم تشغيلها كبرامج Perl قبل معالجة بقية الملفات في توزيعك مع اسم الملف الذي تنشئه كوسيط. تُستخدم عادةً كقوالب لإنشاء ملفات أخرى ديناميكيًا، بحيث قد ينشئ ملف مثل "lib/Foo/Bar.pm.PL" الملف "lib/Foo/Bar.pm".

يتم تحديد الملفات باستخدام ".PL" الملفات كمفاتيح هاش، والملفات التي تنشئها كقيم هاش، مثل:

my $build = Module::Build->new
  (
   module_name => 'Foo::Bar',
   ...
   PL_files => { 'lib/Foo/Bar.pm.PL' => 'lib/Foo/Bar.pm' },
  );

لاحظ أن مواصفات المسار تُعطى دائمًا بتنسيق شبيه بـ Unix، وليس بأسلوب النظام المحلي.

إذا لم تنشئ نصوص ".PL" الخاصة بك أي ملفات، أو إذا أنشأت ملفات بأسماء غير متوقعة، أو حتى إذا أنشأت ملفات متعددة، يمكنك الإشارة إلى ذلك حتى يتمكن Module::Build من التعامل بشكل صحيح مع هذه الملفات التي تم إنشاؤها:

PL_files => {
             'lib/Foo/Bar.pm.PL' => 'lib/Foo/Bar.pm',
             'lib/something.PL'  => ['/lib/something', '/lib/else'],
             'lib/funny.PL'      => [],
            }

إليك مثال لنص PL بسيط.

my $output_file = shift;
open my $fh, ">", $output_file or die "Can't open $output_file: $!";
print $fh <<'END';
#!/usr/bin/perl
print "Hello, world!\n";
END

لا يتم تثبيت ملفات PL افتراضيًا، لذلك من الآمن وضعها في lib/ و bin/.

pm_files
[الإصدار 0.19]

معامل اختياري يحدد مجموعة ".pm" الملفات في هذا التوزيع، محددة كمرجع هاش تكون مفاتيحه مواقع الملفات في التوزيعات، وقيمها مواقعها المنطقية بناءً على اسم الحزمة الخاصة بها، أي المكان الذي يمكن العثور عليها فيه في توزيع بأسلوب Module::Build "طبيعي". هذا المعامل مخصص بشكل أساسي لدعم تخطيطات الملفات البديلة.

على سبيل المثال، إذا كان لديك توزيع بأسلوب قديم "MakeMaker" لوحدة تسمى "Foo::Bar" وملف Bar.pm في المستوى الأعلى من التوزيع، يمكنك تحديد تخطيطك في "Build.PL" الخاص بك على هذا النحو:

my $build = Module::Build->new
  (
   module_name => 'Foo::Bar',
   ...
   pm_files => { 'Bar.pm' => 'lib/Foo/Bar.pm' },
  );

لاحظ أن القيم يجب أن تتضمن "lib/"، لأن هذا هو المكان الذي يمكن العثور عليها فيه في توزيع بأسلوب Module::Build "طبيعي".

لاحظ أيضًا أن مواصفات المسار تُعطى دائمًا بتنسيق شبيه بـ Unix، وليس بأسلوب النظام المحلي.

recommends
[الإصدار 0.08]

هذا تمامًا مثل وسيط "requires"، باستثناء أن الوحدات المدرجة في هذا القسم ليست ضرورية، بل هي مجرد فكرة جيدة. سنطبع فقط تحذيرًا ودودًا إذا لم يتم العثور على إحدى هذه الوحدات، ولكننا سنستمر في التشغيل.

إذا تم التوصية بوحدة ولكنها لم تكن مطلوبة، يجب أن تمر جميع الاختبارات بنجاح حتى لو لم تكن الوحدة مثبتة. قد يعني هذا أنه قد يتم تخطي بعض الاختبارات إذا لم تكن التبعيات الموصى بها موجودة.

يجب أن تخبر الأدوات الآلية مثل CPAN.pm المستخدم عندما لا تكون الوحدات الموصى بها مثبتة، ويجب أن تقدم تثبيتها إذا كانت ترغب في أن تكون مفيدة.

add_property
[version 0.31] 
package 'My::Build';
use base 'Module::Build';
__PACKAGE__->add_property( 'pedantic' );
__PACKAGE__->add_property( answer => 42 );
__PACKAGE__->add_property(
   'epoch',
    default => sub { time },
    check   => sub {
        return 1 if /^\d+$/;
        shift->property_error( "'$_' is not an epoch time" );
        return 0;
    },
);

يضيف خاصية إلى فئة "Module::Build". الخصائص هي سمات كائن "Module::Build" يمكن تمريرها إلى المنشئ ولها ملحقات للحصول عليها وتعيينها. يتم تعريف جميع الخصائص الأساسية، مثل "module_name" و "license"، باستخدام هذه الطريقة.

الوسيط الأول لـ add_property() هو دائمًا اسم الخاصية. يمكن أن يكون الوسيط الثاني قيمة افتراضية للخاصية، أو قائمة بأزواج مفتاح-قيمة. المفاتيح المدعومة هي:

"default"
القيمة الافتراضية. يمكن تحديدها اختياريًا كمرجع إلى رمز، وفي هذه الحالة سيتم استخدام القيمة المرتجعة من تنفيذ الرمز. إذا كنت بحاجة إلى أن تكون القيمة الافتراضية مرجعًا إلى رمز، فما عليك سوى استخدام مرجع إلى رمز لإرجاعه، على سبيل المثال: 
default => sub { sub { ... } },
"check"
رمز يتحقق من أن القيمة المحددة للخاصية صالحة. أثناء تنفيذ الرمز، سيتم تضمين القيمة الجديدة في المتغير $_. إذا كانت القيمة صحيحة، يجب أن يعيد رمز التحقق "check" قيمة صحيحة. إذا كانت القيمة غير صحيحة، فأرسل رسالة خطأ إلى "property_error() وأعد قيمة خاطئة.

عند استدعاء هذه الطريقة، يتم تثبيت خاصية جديدة في فئة "Module::Build"، ويتم إنشاء ملحق للحصول على الخاصية أو تعيينها في كائن البناء.

print $build->pedantic, $/;
$build->pedantic(0);

إذا كانت القيمة الافتراضية مرجعًا إلى hash، فإنها تنشئ طريقة ملحق خاصة، حيث يمكن تعيين أزواج المفاتيح والقيم الفردية أو استعادتها:

print "stuff{foo} is: ", $build->stuff( 'foo' ), $/;
$build->stuff( foo => 'bar' );
print $build->stuff( 'foo' ), $/; # Outputs "bar"

يمكنك أيضًا تعيين مجموعة كاملة من أزواج المفاتيح والقيم مباشرة:

$build->stuff( { foo => 'bar', baz => 'yo' } );

في أي من الحالتين، إذا تم تحديد "check" للخاصية، فسيتم تطبيقه على hash بأكمله. لذلك، يجب أن يبدو رمز التحقق شيئًا كهذا:

check => sub {
      return 1 if defined $_ && exists $_->{foo};
      shift->property_error(qq{Property "stuff" needs "foo"});
      return 0;
},

check_installed_status($module, $version)
[version 0.11]

Este método devuelve un referencia de hash indicando si una dependencia de versión específica del módulo $module está satisfecha. El argumento $module se pasa como una cadena como "Data::Dumper" o "perl", y el argumento $version puede tomar cualquier forma descrita en "requires" anteriormente. Esto permite un control fino de versiones.

El retorno del hash tiene la siguiente estructura:

{
 ok => $whether_the_dependency_is_satisfied,
 have => $version_already_installed,
 need => $version_requested, # mismo que el argumento $version
 message => $informative_error_message,
}

Si no hay una versión de $module instalada, el valor "have" será la cadena "<none>". De lo contrario, el valor "have" será simplemente la versión del módulo instalado. Debe tener en cuenta que si $module está instalado pero no define un número de versión, el valor "have" será "undef" - por eso no usamos "undef" en este caso cuando $module no está instalado.

Este método puede llamarse tanto como método de objeto ("$build->check_installed_status($module, $version)") como método de clase ("Module::Build->check_installed_status($module, $version)").

check_installed_version($module, $version)
[version 0.05]

Como check_installed_status(), pero simplemente devuelve true o false dependiendo si el módulo $module satisface la dependencia $version.

Si el chequeo es exitoso, el valor devuelto es la versión real del módulo $module instalado en el sistema. Esto permite realizar lo siguiente:

my $installed = $build->check_installed_version('DBI', '1.15');
if ($installed) {
  print "Congratulations, version $installed of DBI is installed.\n";
} else {
  die "Sorry, you must install DBI.\n";
}

Si el chequeo falla, devolvemos false y establecemos $@ a un mensaje de error informativo.

Si $version es cualquier valor no verdadero (notablemente cero) y cualquier versión de $module está instalada, devolvemos true. En este caso, si $module no define una versión o su versión es cero, devolvemos el valor especial "0 but true", que numéricamente es cero pero lógicamente verdadero.

En general, prefieres usar "check_installed_status" si necesitas información detallada, o este método si solo necesitas un respuesta de sí/no.

طريقة notes() هي في الأساس وصول إلى تجزئة (hash) مجيدة. بدون وسائط، تعيد notes() التجزئة الكاملة للملاحظات. بوسيط واحد، تعيد notes($key) القيمة المرتبطة بالمفتاح المحدد. بوسيطين، تعين "notes($key, $value)" القيمة المرتبطة بالمفتاح المحدد إلى $value وتعيد القيمة الجديدة.

عمر بيانات "notes" هو "عملية بناء" - أي أن تجزئة "notes" يتم إنشاؤها عند تشغيل "perl Build.PL" (أو عند تشغيل طريقة new()، إذا تم استخدام واجهة برمجة التطبيقات لوحدة Module::Build Perl بدلاً من استدعائها من shell)، وتستمر حتى يتم تشغيل "perl Build.PL" مرة أخرى أو تشغيل إجراء "clean".

get_metadata()
[version 0.36]

تعيد هذه الطريقة مرجع تجزئة (hash reference) للبيانات الوصفية التي يمكن استخدامها لإنشاء تدفق بيانات YAML. يتم توفيرها للمؤلفين لتجاوز حقول META.yml أو تخصيصها. مثال:

package My::Builder;
use base 'Module::Build';
sub get_metadata {
  my $self, @args = @_;
  my $data = $self->SUPER::get_metadata(@args);
  $data->{custom_field} = 'foo';
  return $data;
}

الوسائط الصالحة تشمل:

  • "fatal" -- يشير إلى ما إذا كانت حقول البيانات الوصفية المطلوبة المفقودة يجب أن تكون خطأ فادحًا أم لا. لإنشاء META، يجب أن تكون بشكل عام كذلك، ولكن لإنشاء MYMETA لمستخدمي النهاية، لا ينبغي أن تكون فادحة.
  • "auto" -- يشير إلى ما إذا كان ينبغي إضافة أي configure_requires ضروري تلقائيًا. يتم استخدام هذا في إنشاء META.

هذه الطريقة هي غلاف للطريقة القديمة prepare_metadata الآن بعد أن لم نعد نستخدم YAML::Node للاحتفاظ بالبيانات الوصفية.

prereq_failures()
[version 0.20]

Devuelve un hash de referencias a hashes que describen las dependencias previas que no pudieron ser encontradas o que fallaron una verificación de conflictos. Las claves principales son los tipos de dependencias (requires, build_requires, test_requires, configure_requires, recommends, y conflicts). Los valores son referencias a hashes de nombres de módulos y hashes que describen el fallo.

La estructura de los hashes de fallos es la misma que la retornada por check_installed_status():

{
 have   => '<none>',
 need   => '0.59',
 message => 'Prerequisite Foo isn't installed',
}

Esta hash tiene la misma estructura que la retornada por el método check_installed_status(), excepto que en el caso de dependencias de "conflicts" cambiamos la clave "need" a "conflicts" y construimos un mensaje adecuado.

Ejemplos:

# Check a required dependency on Foo::Bar
if ( $build->prereq_failures->{requires}{Foo::Bar} ) { ...
# Check whether there were any failures
if ( $build->prereq_failures ) { ...
# Show messages for all failures
my $failures = $build->prereq_failures;
while (my ($type, $list) = each %$failures) {
  while (my ($name, $hash) = each %$list) {
    print "Failure for $name: $hash->{message}\n";
  }
}

prompt($message, $default)
[version 0.12]

Pregunta al usuario una pregunta y devuelve la respuesta como una cadena. El primer argumento especifica el mensaje a mostrar al usuario (por ejemplo, "Donde guardas tu dinero?"). El segundo argumento, opcional, especifica una respuesta por defecto (por ejemplo, "wallet"). El usuario se preguntará una vez.

Si prompt() detecta que no está ejecutando de forma interactiva y no hay nada en STDIN o si el entorno de ambiente PERL_MM_USE_DEFAULT está establecido en true, el valor $default se utilizará sin preguntar.

Para evitar que procesos automatizados bloqueen, el usuario debe establecer PERL_MM_USE_DEFAULT o colocar algo en STDIN (esto puede ser un pipe/file con una secuencia de respuestas scriptada o /dev/null).

Si no se proporciona un valor $default se utilizará una cadena vacía. En modo no interactivo, la ausencia de $default es un error (aunque pasar undef() como valor por defecto es válido desde 0.27).

Este método puede llamarse tanto como método de clase como objeto.

rscan_dir($dir, $pattern)
[version 0.28]

Usa "File::Find" para recorrer el directorio $dir, devolviendo una referencia a un array de entradas que coincidan con $pattern. $pattern puede ser una expresión regular (usando qr// o simplemente un string), o una referencia a una subrutina que devuelva true para entradas deseadas. Si $pattern no está dado, se devolverán todos los entradas.

Ejemplos:

# Todos los archivos .pm en lib/
$m->rscan_dir('lib', qr/\.pm$/)
# Todos los archivos en blib que no sean archivos .html
$m->rscan_dir('blib', sub {-f $_ and not /\.html$/});
# Todos los archivos en t/
$m->rscan_dir('t');
runtime_params()
runtime_params($key)
[version 0.28]

El método runtime_params() almacena los valores que se pasaron por la línea de comandos para propiedades válidas (es decir, cualquier opción de la línea de comandos para la cual valid_property() devuelve un valor verdadero). El valor en la línea de comandos puede sobreescalar el valor por defecto de una propiedad, así como cualquier valor especificado en una llamada a new(). Esto permite que se programáticamente indiquen si "perl Build.PL" o cualquier ejecución de "./Build" tuviera opciones de la línea de comandos que sobrescriben propiedades válidas.

El método runtime_params() es básicamente un hash de solo lectura glorificado. Sin argumentos, runtime_params() devuelve el entero hash de propiedades especificadas en la línea de comandos. Con un argumento, runtime_params($key) devuelve el valor asociado con la clave dada.

La vida útil del dato "runtime_params" es para "una build" - es decir, el hash "runtime_params" se crea cuando se ejecute "perl Build.PL" (o cuando se llame al método new() si se esté utilizando la API de Module::Build en lugar de llamarse desde la shell), y se mantiene hasta que se ejecute "perl Build.PL" nuevamente o se ejecute el acción "clean".

script_files()
[version 0.18]

up_to_date($source_file, $derived_file)

[version 0.20]

Este método puede utilizarse para comparar un conjunto de archivos de fuente con un conjunto de archivos derivados. y_n($message, $default)
[version 0.12]

Pregunta al usuario una pregunta usando prompt() y devuelve verdadero o falso según la respuesta. El usuario se preguntará repetidamente hasta que dé una respuesta que parece "yes" o "no".

Este método puede llamarse tanto como método de clase como objeto.

NAME

Module::Build::API - A list of meta-arguments for Module::Build

SYNOPSIS

  use Module::Build;
  my $build = Module::Build->new(
      module_name        => 'My-Module',
      dist_version       => '0.01',
      license            => 'perl',
      requires           => {
          'Module::Dependency' => '0.001',
      },
      build_requires     => {
          'Test::More'       => '0.001',
      },
      # ... and so on
  );
  $build->create_build_script;

DESCRIPTION

This document lists the meta-arguments that can be passed to the "Module::Build->new()" method, and documented by the various "Module::Build::*" modules.

The documentation for these arguments is spread across several files, so this document acts as a handy reference.

Meta-arguments

add_build_element()
Allows you to define new build elements. This is a more advanced feature for those wanting to extend Module::Build.
add_build_rule()
Allows you to define new build rules. This is a more advanced feature for those wanting to extend Module::Build.
all_from_dir()
A convenience method for setting up "pm_files", "pod_files", and "script_files" based on files found in a given directory.
auto_configure_requires()

auto_install_requires()
If true, Module::Build will automatically add itself and any required modules to the "requires" list. Defaults to true.
auto_requires()
A convenience method for setting both "auto_configure_requires" and "auto_install_requires".
build_class()
The name of the class that Module::Build should use to build the module. Defaults to "Module::Build".
build_data()
The data that will be put into the build script. This is mostly used internally.
build_dir()

build_elements()

build_extra_install_path()

build_installs()

build_log_file()
