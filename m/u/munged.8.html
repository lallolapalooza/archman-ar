NAME

munged ― MUNGE Uid 'N' Gid Emporium daemon

SYNOPSIS

munged [ OPTION… ]

DESCRIPTION

The munged daemon provides the MUNGE authentication service. It is responsible for creating and validating MUNGE credentials.

OPTIONS

The munged daemon understands the following options:

‑‑allow-root
Allow munged to be run as root. This is the default behavior.
‑‑chroot
Chroot the munged daemon to the specified directory. This option is used in conjunction with --rundir and --pidfile.
‑‑config-file
Read configuration options from the specified file. The default is /etc/munge/munged.conf.
‑‑console
Log messages to the console instead of syslog. This option is intended for debugging.
‑‑daemon
Run munged as a daemon. This is the default behavior.
‑‑disable-replay-cache
Disable the replay cache. This option should only be used if memory locking is not required or desired.
‑‑gid
Change to the specified GID after initialization. The default is to use the GID of the munge user.
‑‑group
Change to the specified group after initialization. The default is to use the group of the munge user.
‑‑host-identity
Use the specified string as the host identity. This option overrides the default behavior of determining the host identity from the system hostname. This option is useful for testing or in environments where the system hostname may not be unique or stable.
‑‑key-file
Use the specified file as the encryption key. The default is /etc/munge/munge.key.
‑‑log-prefix
Prepend the specified string to all log messages. The default is munged.
‑‑max-ttl
Set the maximum time-to-live (TTL) for credentials in seconds. The default is 3600 seconds (1 hour).
‑‑mlockall
Lock all of munged's memory into physical memory using mlockall(2). This option prevents the operating system from swapping out munged's memory, which can improve performance and security. However, it requires sufficient available memory and may not be supported on all systems.
‑‑pidfile
Write the process ID to the specified file. The default is /run/munge/munged.pid.
‑‑port
Listen on the specified UDP port. The default is 2113.
‑‑recursive-lock
Enable recursive locking for the replay cache. This option is useful on systems with multiple CPUs or cores, as it allows munged to acquire locks more efficiently.
‑‑renew-key
Generate a new encryption key and replace the existing one. This option should be used with caution, as it will invalidate all existing MUNGE credentials.
‑‑runsubdir
Create the PID file and socket in the specified subdirectory of --rundir. The default is munge.
‑‑rundir
Create the PID file and socket in the specified directory. The default is /run/munge.
‑‑syslog
Log messages to syslog. This is the default behavior.
‑‑user
Change to the specified user after initialization. The default is to use the munge user.
‑‑validate-after-fork
Perform credential validation after forking. This option is useful for testing purposes.
‑‑version
Print version information and exit.

MEMORY LOCKING

The munged daemon can lock its memory into physical RAM using the mlockall(2) system call. This prevents the operating system from swapping out the daemon's memory, which can improve performance and security by reducing the likelihood of sensitive data being written to disk. This option is enabled using --mlockall.

Using --mlockall requires sufficient available memory. If not enough memory is available, munged may fail to start or may terminate unexpectedly. The amount of memory required depends on the number of active credentials and the size of the replay cache.

The replay cache stores recently decoded credentials to prevent replay attacks. The size of the replay cache is determined by the --max-ttl option and the rate at which credentials are decoded. When --mlockall is enabled, the replay cache is also locked into memory.

On systems with untrusted local users, it may be possible for an attacker to fill the replay cache with credentials that have a long TTL, potentially causing a denial of service by exhausting available memory. In such environments, it is recommended to either:

  • Set a reasonable upper bound for the memory lock limit using the PAM limits configuration (see PAM limits below).
  • Disable the replay cache using --disable-replay-cache if memory locking is not strictly required.

It is also recommended to monitor the locked memory usage of munged on high-volume systems to ensure that the limit is not approached during normal operation.

Reducing the maximum TTL (--max-ttl) can help limit the growth of the replay cache, but this requires tight clock synchronization between clients and the server.

To reload the configuration and restart the service:

systemctl daemon-reload
systemctl restart munge.service

PAM limits

Add to /etc/security/limits.conf (values in KB):

munge  soft  memlock  262144
munge  hard  memlock  262144

On systemd-based systems, PAM limits are ignored for services. Use the systemd configuration instead.

Shell environment (for testing)

Set the limit before starting munged (value in KB):

ulimit -l 262144
munged --mlockall

Security Considerations

The replay cache is unbounded and grows with credential decode rate. Replay entries are retained until credentials expire based on their time-to-live (TTL). Credentials have a default TTL of 5 minutes; clients can specify up to the maximum TTL configured on the encoding munged (1 hour by default, configurable via --max-ttl). During decoding, the credential's TTL is capped at the decoding munged's maximum TTL. When --mlockall is specified, replay entries are locked in physical memory.

On systems with untrusted local users, an attacker could encode credentials with the maximum TTL (1 hour by default) and decode them repeatedly to fill the replay cache. Once the memory lock limit is reached, munged will likely terminate when attempting to allocate additional memory, causing a denial of service.

Use this option only on trusted systems where local users are controlled, or set the memory lock limit to a reasonable upper bound rather than unlimited. Monitor munged's locked memory usage on high-volume systems to ensure the limit is not approached during normal operation. Reducing --max-ttl can limit replay cache growth but requires tight clock synchronization.

SIGNALS

SIGHUP
Immediately update the supplementary group membership mapping instead of waiting for the next scheduled update; this mapping is used when restricting credentials by GID.
SIGTERM
Terminate the daemon.

NOTES

All clocks within a security realm must be kept in sync within the credential time-to-live setting.

While munged prevents a given credential from being decoded on a particular host more than once, nothing prevents a credential from being decoded on multiple hosts within the security realm before it expires.
