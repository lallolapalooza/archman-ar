It provides a hook into MIME::Parser that allows you to control the naming of the extracted files. The base class MIME::Parser::Filer provides default behavior, which is then overridden by subclasses like MIME::Parser::FileInto and MIME::Parser::FileUnder, or by your own custom subclasses. The basic flow for determining the output path for a part is: 1. Get a recommended filename from the MIME header (e.g. Content-Disposition). 2. If a recommended filename is not available, or if it's deemed "evil" (see `evil_filename()`), generate a filename using `output_filename()`. 3. Determine the output directory using `output_dir()`. 4. Combine the directory and filename, ensuring the filename is unique using `find_unused_path()`. The default methods are designed to be overridden by subclasses or by developers who need fine-grained control over file naming. - section: Sh title: PUBLIC INTERFACE content: - section: Ss title: MIME::Parser::Filer content: - section: dl items: - dt: id="evil_filename" dd: | Instance method. Return true if the filename is considered "evil" and should not be used. The default implementation returns true if the filename contains any character other than alphanumeric characters, periods, hyphens, or underscores.

With argument, sets this value.

- dt: id="find_unused_path" dd: | Instance method. Given a DIRECTORY and a FILENAME, return a full path that does not exist. This is done by appending numeric suffixes (e.g., file.txt, file.1.txt, file.2.txt, etc.) until an unused path is found.

Note: If you are overriding output_path(), you may not need to worry about this method, as the default implementation uses it. However, if you are providing your own naming logic that might generate collisions (e.g. if you are placing multiple parts in the same directory and they happen to have the same recommended filename, and you are placing them all in the same directory, this method might be unavoidable.

- dt: id="ignore_filename" dd: | Instance method. Return true if we should always ignore recommended filenames in messages, choosing instead to always generate our own filenames. With argument, sets this value.

Note: subclasses of MIME::Parser::Filer which override output_path() might not honor this setting; note, however, that the built-in subclasses honor it.

- dt: id="output_path" dd: | Instance method, subclasses only. Given a MIME head for a file to be extracted, come up with a good output pathname for the extracted file. This is the only method you need to worry about if you are building a custom filer.

The default implementation does a lot of work; subclass implementers really should try to just override its components instead of the whole thing. It works basically as follows:

$directory = $self->output_dir($head);
$filename = $head->recommended_filename();
if (!$filename or
     $self->ignore_filename() or
     $self->evil_filename($filename)) {
    $filename = $self->output_filename($head);
}
return $self->find_unused_path($directory, $filename);

Note: There are many, many, many ways you might want to control the naming of files, based on your application. If you don't like the behavior of this function, you can easily define your own subclass of MIME::Parser::Filer and override it there.

Note: Nickolay Saukh pointed out that, given the subjective nature of what is "evil", this function really shouldn't warn about an evil filename, but maybe just issue a debug message. I considered that, but then I thought: if debugging were off, people wouldn't know why (or even if) a given filename had been ignored. In mail robots that depend on externally-provided filenames, this could cause hard-to-diagnose problems. So, the message is still a warning.

Thanks to Laurent Amon for pointing out problems with the original implementation, and for making some good suggestions. Thanks also to Achim Bohnet for pointing out that there should be a hookless, OO way of overriding the output path.

- dt: id="purge" dd: | Instance method, final. Purge all files/directories created by the last parse. This method simply goes through the purgeable list in reverse order (see "purgeable") and removes all existing files/directories in it. You should not need to override this method. - dt: id="purgeable" dd: | Instance method, final. Add FILE to the list of "purgeable" files/directories (those which will be removed if you do a purge()). You should not need to override this method.

If FILE is not given, the "purgeable" list is returned. This may be used for more-sophisticated purging.

As a special case, invoking this method with a FILE that is an arrayref will replace the purgeable list with a copy of the array's contents, so [] may be used to clear the list.

Note that the "purgeable" list is cleared when a parser begins a new parse; therefore, if you want to use purge() to do cleanup, you must do so before starting a new parse!
