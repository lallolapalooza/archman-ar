MISE(1) General Commands Manual MISE(1)

NAME

mise - الواجهة الأمامية لبيئة التطوير الخاصة بك

SYNOPSIS

mise [OPTIONS] [<TASK>] [<TASK_ARGS>] ... [<TASK_ARGS_LAST>] ... [COMMAND]

DESCRIPTION

يدير mise أدوات التطوير، متغيرات البيئة، ويقوم بتشغيل المهام. https://github.com/jdx/mise

OPTIONS

-c, --continue-on-error
متابعة تشغيل المهام حتى لو فشلت إحداها
-C, --cd <DIR>
تغيير الدليل قبل تشغيل الأمر
-E, --env <ENV>
تعيين البيئة لتحميل `mise.<ENV>.toml`
-f, --force
فرض العملية
-i, --interleave
تعيين مستوى تفصيل سجل الإخراج
-j, --jobs <JOBS>
عدد المهام التي سيتم تشغيلها بالتوازي [الافتراضي: 8]
-n, --dry-run
تشغيل تجريبي، لا تفعل شيئًا في الواقع
-p, --prefix
-P, --profile <PROFILE>
تعيين الملف الشخصي (البيئة)
-q, --quiet
كتم الرسائل غير المتعلقة بالأخطاء
-s, --shell <SHELL>
-t, --tool <TOOL@VERSION>
الأدوات التي سيتم تشغيلها بالإضافة إلى ما هو موجود في ملفات mise.toml، على سبيل المثال: node@20 python@3.10
-v, --verbose
إظهار مخرجات إضافية (استخدم -vv لمزيد من التفاصيل)
-V, --version
-y, --yes
الإجابة بنعم على جميع المطالبات التأكيدية
--debug
تعيين مستوى السجل إلى debug
--log-level <LEVEL>
--no-config
عدم تحميل أي ملفات تكوين

يمكن أيضًا استخدام `MISE_NO_CONFIG=1`

--no-timings
إخفاء الوقت المنقضي بعد اكتمال كل مهمة

الافتراضي للإخفاء الدائم باستخدام `MISE_TASK_TIMINGS=0`

--output <OUTPUT>
--raw
القراءة/الكتابة مباشرة إلى stdin/stdout/stderr بدلاً من سطر بسطر
--silent
كتم كل مخرجات المهام ورسائل mise غير المتعلقة بالأخطاء
--timings
عرض الوقت المنقضي بعد اكتمال كل مهمة

الافتراضي للعرض الدائم باستخدام `MISE_TASK_TIMINGS=1`

--trace
تعيين مستوى السجل إلى trace

<TASK>
المهمة التي سيتم تشغيلها.

اختصار لـ `mise task run <TASK>`.

<TASK_ARGS>
وسيطات المهمة

MISE ACTIVATE

Initializes mise in the current shell session

This should go into your shell's rc file or login shell. Otherwise, it will only take effect in the current session. (e.g. ~/.zshrc, ~/.zprofile, ~/.zshenv, ~/.bashrc, ~/.bash_profile, ~/.profile, ~/.config/fish/config.fish, or $PROFILE for powershell)

Typically, this can be added with something like the following:


echo 'eval "$(mise activate zsh)"' >> ~/.zshrc

However, this requires that "mise" is in your PATH. If it is not, you need to specify the full path like this:


echo 'eval "$(/path/to/mise activate zsh)"' >> ~/.zshrc

Customize status output with `status` settings.

Usage: mise activate [OPTIONS] [<SHELL_TYPE>]

Options:

-q, --quiet
Suppress non-error messages
-s, --shell <SHELL>
Shell type to generate the script for
--no-hook-env
Do not automatically call hook-env

This can be helpful for debugging mise. If you run `eval "$(mise activate --no-hook-env)"`, then you can call `mise hook-env` manually which will output the env vars to stdout without actually modifying the environment. That way you can do things like `mise hook-env --trace` to get more information or just see the values that hook-env is outputting.

--shims
Use shims instead of modifying PATH Effectively the same as:


PATH="$HOME/.local/share/mise/shims:$PATH"

`mise activate --shims` does not support all the features of `mise activate`. See https://mise.jdx.dev/dev-tools/shims.html#shims-vs-path for more information

MISE ENV

تصدير متغيرات البيئة لتفعيل mise لمرة واحدة

استخدم هذا إذا كنت لا ترغب في تثبيت mise بشكل دائم. ليس من الضروري استخدام هذا إذا كان لديك `mise activate` في

most likely binary

-u, --url <URL>
عنوان URL لتنزيل الأداة

مثال: https://github.com/owner/repo/releases/download/v2.0.0/tool-linux-x64.tar.gz

--fetch
جلب المجموع الاختباري والأحجام لملف إرشاد أداة موجود

هذا يقرأ ملف إرشاد موجود ويملأ أي حقول مجموع اختباري/حجم مفقودة عن طريق تنزيل الملفات. يجب أن تكون عناوين URL موجودة بالفعل في الإرشاد.

--http <HTTP>

--platform-bin <PLATFORM_BIN>
مسارات الملفات الثنائية الخاصة بالمنصة بالتنسيق platform:path

أمثلة: --platform-bin windows-x64:tool.exe --platform-bin linux-x64:bin/tool

--platform-url <PLATFORM_URL>
عناوين URL الخاصة بالمنصة بالتنسيق platform:url أو url فقط (اكتشاف تلقائي للمنصة)

عندما يكون ملف الإخراج موجودًا بالفعل، ستتم إضافة منصات جديدة إلى جدول المنصات الحالي. سيتم تحديث عناوين URL للمنصات الموجودة إذا تم تحديدها مرة أخرى.

إذا تم توفير عنوان URL فقط (بدون platform:)، فسيتم اكتشاف المنصة تلقائيًا من اسم ملف عنوان URL.

أمثلة: --platform-url linux-x64:https://... --platform-url https://nodejs.org/dist/v22.17.1/node-v22.17.1-darwin-arm64.tar.gz

--skip-download
تخطي التنزيل لاكتشاف المجموع الاختباري ومسار الملف الثنائي (أسرع ولكن أقل إفادة)

MISE WATCH

تشغيل مهمة (مهام) ومراقبة التغييرات لإعادة تشغيلها

يستخدم هذا الأمر الأداة `watchexec` لمراقبة التغييرات في الملفات وإعادة تشغيل المهام المحددة. يجب تثبيتها لكي يعمل هذا الأمر، ولكن يمكنك تثبيتها باستخدام `mise use -g watchexec@latest`.

الاستخدام: mise watch [OPTIONS] [<TASK>] [<ARGS>] ...

الخيارات:

-t, --task-flag <TASK_FLAG>
المهام المراد تشغيلها
-g, --glob <GLOB>
الملفات المراد مراقبتها. الافتراضي هو المصادر من المهام.
-w, --watch <PATH>
مراقبة ملف أو مجلد محدد

افتراضيًا، تراقب Watchexec الدليل الحالي.

عند مراقبة ملف واحد، غالبًا ما يكون من الأفضل مراقبة الدليل المحتوي بدلاً من ذلك، وتصفية اسم الملف. قد تستبدل بعض المحررات الملف بملف جديد عند الحفظ، وقد لا تكتشف بعض المنصات ذلك أو المزيد من التغييرات.

عند البدء، تقوم Watchexec بحل "أصل المشروع" من المسارات التي تتم مراقبتها. راجع المساعدة الخاصة بـ '--project-origin' لمزيد من المعلومات.

يمكن تحديد هذا الخيار عدة مرات لمراقبة ملفات أو مجلدات متعددة.

القيمة الخاصة '/dev/null'، المقدمة كالمسار الوحيد الذي تتم مراقبته، ستتسبب في عدم قيام Watchexec بمراقبة أي مسارات. قد لا تزال مصادر الأحداث الأخرى (مثل الإشارات أو أحداث المفاتيح) قيد الاستخدام.

-W, --watch-non-recursive <PATH>
مراقبة مجلد محدد، بشكل غير تكراري

على عكس '-w'، لا يتم الدخول إلى المجلدات التي تتم مراقبتها بهذا الخيار.

يمكن تحديد هذا الخيار عدة مرات لمراقبة مجلدات متعددة بشكل غير تكراري.

-F, --watch-file <PATH>
مراقبة الملفات والمجلدات من ملف

سيتم تفسير كل سطر في الملف كما لو تم تمريره إلى '-w'.

للاستخدامات الأكثر تعقيدًا (مثل المراقبة غير التكرارية)، استخدم إمكانية ملف الوسيط: قم بإنشاء ملف يحتوي على خيارات سطر الأوامر ومرره إلى watchexec باستخدام `@path/to/argfile`.

القيمة الخاصة '-' ستقرأ من STDIN؛ وهذا غير متوافق مع '--stdin-quit'.

-c, --clear <MODE>
مسح الشاشة قبل تشغيل الأمر

إذا لم يؤدِ هذا إلى مسح الشاشة تمامًا، جرب '--clear=reset'.

-o, --on-busy-update <MODE>
ماذا تفعل عند تلقي أحداث أثناء تشغيل الأمر

الافتراضي هو 'do-nothing'، والذي يتجاهل الأحداث أثناء تشغيل الأمر، بحيث يتم تجاهل التغييرات التي تحدث بسبب الأمر، مثل مخرجات التجميع. يمكنك أيضًا استخدام 'queue' والذي سيقوم بتشغيل الأمر مرة أخرى عند انتهاء التشغيل الحالي إذا حدثت أي أحداث أثناء تشغيله، أو 'restart'، والذي ينهي الأمر قيد التشغيل ويبدأ واحدًا جديدًا. أخيرًا، هناك 'signal'، والذي يرسل إشارة فقط؛ يمكن أن يكون هذا مفيدًا مع البرامج التي يمكنها إعادة تحميل تكوينها دون إعادة تشغيل كاملة.

يمكن تحديد الإشارة باستخدام الخيار '--signal'.

-r, --restart
إعادة تشغيل العملية إذا كانت لا تزال قيد التشغيل

هذا اختصار لـ '--on-busy-update=restart'.

-s, --signal <SIGNAL>
إرسال إشارة إلى العملية عندما تكون لا تزال قيد التشغيل

حدد إشارة لإرسالها إلى العملية عندما تكون لا تزال قيد التشغيل. هذا يعني ضمنيًا '--on-busy-update=signal'؛ بخلاف ذلك، يتم التحكم في الإشارة المستخدمة عند استخدام هذا الوضع 'restart' بواسطة '--stop-signal'.

راجع الوثائق المطولة لـ '--stop-signal' للحصول على الصيغة.

الإشارات غير مدعومة حاليًا على Windows، وسيتم تجاوزها دائمًا إلى 'kill'. راجع '--stop-signal' لمزيد من المعلومات حول "الإشارات" على Windows.

--stop-signal <SIGNAL>
الإشارة المراد إرسالها لإيقاف الأمر

يستخدم هذا بواسطة أوضاع 'restart' و 'signal' الخاصة بـ '--on-busy-update' (ما لم يتم توفير '--signal'). سلوك إعادة التشغيل هو إرسال الإشارة، والانتظار حتى تخرج العملية، وإذا لم تخرج بعد فترة معينة (انظر '--timeout-stop')، فقم بإنهاءها بالقوة.

الافتراضي على unix هو "SIGTERM".

يتم تحليل الإدخال كاسم إشارة كامل (مثل "SIGTERM")، أو اسم إشارة قصير (مثل "TERM")، أو رقم إشارة (مثل "15"). جميع المدخلات غير حساسة لحالة الأحرف.

على Windows، يدعم هذا الخيار تقنيًا ولكنه يدعم فقط حدث "KILL"، حيث لا يمكن لـ Watchexec حاليًا تسليم أحداث أخرى. لا تحتوي Windows على إشارات بالمعنى الحرفي؛ بدلاً من ذلك، لديها إنهاء (يسمى هنا "KILL" أو "STOP") وأحداث "CTRL+C" و "CTRL+BREAK" و "CTRL+CLOSE". للتوافق، يتم تعيين إشارات unix "SIGKILL" و "SIGINT" و "SIGTERM" و "SIGHUP" إلى هذه على التوالي.

--stop-timeout <TIMEOUT>
الوقت للانتظار حتى تخرج العملية بأمان

يستخدم هذا بواسطة وضع 'restart' لـ '--on-busy-update'. بعد إرسال إشارة الإيقاف الآمن، ستنتظر Watchexec حتى تخرج العملية. إذا لم تخرج بعد هذه المدة، فسيتم إنهاؤها بالقوة.

يأخذ قيمة بدون وحدة بالثواني، أو قيمة فترة زمنية مثل "5min 20s". تقديم قيمة بدون وحدة مهمل وسيؤدي إلى تحذير؛ سيكون خطأ في المستقبل.

الافتراضي هو 10 ثوانٍ. اضبطها على 0 لإنهاء العملية فورًا بالقوة.

ليس لهذا تأثير عملي على Windows حيث يتم إنهاء العملية دائمًا بالقوة؛ راجع '--stop-signal' لسبب ذلك.

--map-signal <SIGNAL:SIGNAL>
ترجمة الإشارات من نظام التشغيل إلى إشارات لإرسالها إلى الأمر

يأخذ زوجًا من أسماء الإشارات، مفصولة بنقطتين رأسيتين، مثل "TERM:INT" لترجمة SIGTERM إلى SIGINT. الإشارة الأولى هي التي تتلقاها watchexec، والثانية هي التي يتم إرسالها إلى الأمر. يمكن حذف الثانية لتجاهل الإشارة الأولى، مثل "TERM:" لعدم القيام بأي شيء عند تلقي SIGTERM.

إذا تم تعيين SIGINT أو SIGTERM، فإنهما لم يعودا ينهيان Watchexec. بالإضافة إلى جعل إنهاء Watchexec نفسه صعبًا، يكون هذا مفيدًا لإرسال Ctrl-C إلى الأمر دون إنهاء Watchexec والبرنامج الأساسي معه، على سبيل المثال مع "INT:INT".

يمكن تحديد هذا الخيار عدة مرات لتعيين إشارات متعددة.

صيغة الإشارة غير حساسة لحالة الأحرف للأسماء القصيرة (مثل "TERM" و "USR2") والأسماء الطويلة (مثل "SIGKILL" و "SIGHUP"). تدعم أرقام الإشارات أيضًا (مثل "15" و "31"). على Windows، تدعم الأشكال "STOP" و "CTRL+C" و "CTRL+BREAK" أيضًا للاستلام، ولكن Watchexec لا يمكنها حاليًا تسليم "إشارات" أخرى سوى STOP.

-d, --debounce <TIMEOUT>
الوقت للانتظار قبل اتخاذ إجراء عند تلقي أحداث جديدة

عند تلقي حدث، ستنتظر Watchexec لمدة تصل إلى هذا الوقت قبل معالجته (مثل تشغيل الأمر). هذا ضروري لأن ما قد تدركه كتغيير واحد قد يصدر العديد من الأحداث، وبدون هذا السلوك، ستعمل Watchexec كثيرًا جدًا. بالإضافة إلى ذلك، ليس من غير المألوف أن تكون كتابات الملفات غير ذرية، وقد يصدر كل كتابة حدثًا، لذا هذه طريقة جيدة لتجنب تشغيل أمر أثناء كتابة ملف جزئيًا.

استخدام بديل هو تعيين قيمة عالية (مثل "30min" أو أكثر)، لتوفير الطاقة أو النطاق الترددي في المهام المكثفة، مثل نص برمجي للاحتياطي حسب الحاجة. في حالات الاستخدام هذه، لاحظ أن كل حدث متراكم سيتراكم في الذاكرة.

يأخذ قيمة بدون وحدة بالمللي ثانية، أو قيمة فترة زمنية مثل "5sec 20ms". تقديم قيمة بدون وحدة مهمل وسيؤدي إلى تحذير؛ سيكون خطأ في المستقبل.

الافتراضي هو 50 مللي ثانية. يوصى بشدة بعدم تعيينها على 0.

--stdin-quit
الخروج عند إغلاق stdin

هذا يراقب واصف ملف stdin لـ EOF، ويخرج Watchexec بأمان عند إغلاقه. يستخدم هذا بواسطة بعض مديري العمليات لتجنب ترك عمليات زومبي.

--no-vcs-ignore
لا تقم بتحميل gitignores

من بين ملفات استبعاد VCS الأخرى، مثل Mercurial و Subversion و Bazaar و DARCS و Fossil. لاحظ أن Watchexec ستكتشف أيًا من هذه قيد الاستخدام، إن وجدت، وستقوم فقط بتحميل الملفات ذات الصلة. يتم النظر في كل من الملفات العامة (مثل '~/.gitignore') والملفات المحلية (مثل '.gitignore').

هذا الخيار مفيد إذا كنت ترغب في مراقبة الملفات التي يتجاهلها Git.

--no-project-ignore
لا تقم بتحميل ملفات التجاهل المحلية للمشروع

هذا يعطل تحميل ملفات التجاهل المحلية للمشروع، مثل '.gitignore' أو '.ignore' في المشروع الذي تتم مراقبته. هذا يتناقض مع '--no-vcs-ignore'، والذي يعطل تحميل ملفات التجاهل الخاصة بـ Git و VCS الأخرى، ومع '--no-global-ignore'، والذي يعطل تحميل ملفات التجاهل العامة أو الخاصة بالمستخدم، مثل '~/.gitignore' أو '~/.config/watchexec/ignore'.

ملفات التجاهل المحلية المدعومة

es:


- Git: .gitignore في جذر المشروع والأدلة الفرعية، .git/info/exclude، والملف المشار إليه بواسطة `core.excludesFile` في .git/config.
- Mercurial: .hgignore في جذر المشروع والأدلة الفرعية.
- Bazaar: .bzrignore في جذر المشروع.
- Darcs: _darcs/prefs/boring
- Fossil: .fossil-settings/ignore-glob
- Ripgrep/Watchexec/generic: .ignore في جذر المشروع والأدلة الفرعية.

يتم استخدام ملفات تجاهل VCS (Git، Mercurial، Bazaar، Darcs، Fossil) فقط إذا تم اكتشاف أن VCS المقابل قيد الاستخدام للمشروع/المصدر. على سبيل المثال، سيتم تجاهل ملف .bzrignore في مستودع Git.

--no-global-ignore
لا تقم بتحميل ملفات التجاهل العامة

يقوم هذا الخيار بتعطيل تحميل ملفات التجاهل العامة أو الخاصة بالمستخدم، مثل '~/.gitignore'، '~/.config/watchexec/ignore'، أو '%APPDATA%\Bazzar\2.0\ignore'. قارن مع '--no-vcs-ignore' و '--no-project-ignore'.

ملفات التجاهل العامة المدعومة


- Git (إذا تم تعيين core.excludesFile): الملف الموجود في هذا المسار
- Git (بخلاف ذلك): أول ملف تم العثور عليه من بين $XDG_CONFIG_HOME/git/ignore، %APPDATA%/.gitignore، %USERPROFILE%/.gitignore، $HOME/.config/git/ignore، $HOME/.gitignore.
- Bazaar: أول ملف تم العثور عليه من بين %APPDATA%/Bazzar/2.0/ignore، $HOME/.bazaar/ignore.
- Watchexec: أول ملف تم العثور عليه من بين $XDG_CONFIG_HOME/watchexec/ignore، %APPDATA%/watchexec/ignore، %USERPROFILE%/.watchexec/ignore، $HOME/.watchexec/ignore.

مثل ملفات المشروع، سيتم استخدام ملفات Git و Bazaar العامة فقط لـ VCS المقابلة كما هو مستخدم في المشروع.

--no-default-ignore
لا تستخدم التجاهلات الافتراضية الداخلية

لدى Watchexec مجموعة من أنماط التجاهل الافتراضية، مثل ملفات تبديل المحرر، `*.pyc`، `*.pyo`، `.DS_Store`، `.bzr`، `_darcs`، `.fossil-settings`، `.git`، `.hg`، `.pijul`، `.svn`، وملفات سجل Watchexec.

--no-discover-ignore
لا تكتشف أي ملفات تجاهل على الإطلاق

هذا اختصار لـ '--no-global-ignore'، '--no-vcs-ignore'، '--no-project-ignore'، ولكنه أكثر كفاءة لأنه سيتجاوز جميع آليات اكتشاف التجاهل من البداية.

لاحظ أنه لا يزال يتم تحميل التجاهلات الافتراضية، انظر '--no-default-ignore'.

--ignore-nothing
لا تتجاهل أي شيء على الإطلاق

هذا اختصار لـ '--no-discover-ignore'، '--no-default-ignore'.

لاحظ أنه لا تزال تستخدم التجاهلات التي تم تحميلها صراحةً عبر خيارات سطر الأوامر الأخرى، مثل '--ignore' أو '--ignore-file'.

-p, --postpone
انتظر حتى يحدث التغيير الأول قبل تشغيل الأمر

بشكل افتراضي، سيقوم Watchexec بتشغيل الأمر مرة واحدة على الفور. مع هذا الخيار، سينتظر بدلاً من ذلك حتى يتم اكتشاف حدث قبل تشغيل الأمر كالمعتاد.

--delay-run <DURATION>
النوم قبل تشغيل الأمر

سيؤدي هذا الخيار إلى جعل Watchexec ينام للمدة الزمنية المحددة قبل تشغيل الأمر، بعد اكتشاف حدث. هذا يشبه استخدام "sleep 5 && command" في سطر الأوامر، ولكنه محمول وأكثر كفاءة قليلاً.

يأخذ قيمة بدون وحدة بالثواني، أو قيمة فترة زمنية مثل "2min 5s". تقديم قيمة بدون وحدة هو أمر مهمل وسيصدر تحذيرًا؛ سيكون خطأ في المستقبل.

--poll <INTERVAL>
الاستطلاع بحثًا عن تغييرات نظام الملفات

بشكل افتراضي، وحيثما كان متاحًا، يستخدم Watchexec إمكانيات مراقبة نظام الملفات الأصلية لنظام التشغيل. يعطل هذا الخيار ذلك ويستخدم آلية الاستطلاع بدلاً من ذلك، وهي أقل كفاءة ولكنها يمكن أن تتجاوز المشكلات المتعلقة ببعض أنظمة الملفات (مثل مشاركات الشبكة) أو الحالات الطرفية.

يأخذ اختياريًا قيمة بدون وحدة بالمللي ثانية، أو قيمة فترة زمنية مثل "2s 500ms"، لاستخدامها كفاصل زمني للاستطلاع. إذا لم يتم تحديده، يكون الافتراضي 30 ثانية. تقديم قيمة بدون وحدة هو أمر مهمل وسيصدر تحذيرًا؛ سيكون خطأ في المستقبل.

مُختصر باسم '--force-poll'.

--shell <SHELL>
استخدام سطر أوامر مختلف

بشكل افتراضي، سيستخدم Watchexec '$SHELL' إذا كان معرفًا أو الافتراضي 'sh' على أنظمة Unix المشابهة، وإما 'pwsh' أو 'powershell' أو 'cmd' (CMD.EXE) على Windows، اعتمادًا على ما يكتشفه Watchexec أنه سطر الأوامر قيد التشغيل.

مع هذا الخيار، يمكنك تجاوز ذلك واستخدام سطر أوامر مختلف، على سبيل المثال سطر أوامر لديه ميزات أكثر أو لديه الأسماء المستعارة والوظائف المخصصة الخاصة بك.

إذا كانت القيمة تحتوي على مسافات، يتم تحليلها كسطر أوامر، ويتم استخدام الكلمة الأولى كبرنامج سطر الأوامر، والباقي كوسائط لسطر الأوامر.

يتم تشغيل الأمر مع العلامة '-c' (باستثناء 'cmd' على Windows، حيث تكون '/C').

يمكن استخدام القيمة الخاصة 'none' لتعطيل استخدام سطر الأوامر تمامًا. في هذه الحالة، سيتم تحليل الأمر المقدم إلى Watchexec، حيث تكون الكلمة الأولى هي الملف التنفيذي والباقي هي الوسائط، وسيتم تنفيذه مباشرة. لاحظ أن هذا التحليل بدائي، وقد لا يعمل كما هو متوقع في جميع الحالات.

استخدام 'none' أكثر كفاءة قليلاً ويمكن أن يتيح تفسيرًا أكثر صرامة للمدخلات، ولكنه يعني أيضًا أنه لا يمكنك استخدام ميزات سطر الأوامر مثل التجميع، أو إعادة التوجيه، أو تدفق التحكم، أو المنطق، أو الأنابيب.

أمثلة:

الاستخدام بدون سطر أوامر:

$ watchexec -n -- zsh -x -o shwordsplit scr

الاستخدام مع powershell core:

$ watchexec --shell=pwsh -- Test-Connection localhost

الاستخدام مع CMD.exe:

$ watchexec --shell=cmd -- dir

الاستخدام مع سطر أوامر Unix مختلف:

$ watchexec --shell=bash -- 'echo $BASH_VERSION'

الاستخدام مع سطر أوامر Unix ووسائط:

$ watchexec --shell='zsh -x -o shwordsplit' -- scr

-n
اختصار لـ '--shell=none'
--emit-events-to <MODE>
تكوين بث الأحداث

يمكن لـ Watchexec بث معلومات الحدث عند تشغيل أمر، والتي يمكن استخدامها من قبل العملية الفرعية لاستهداف الملفات المتغيرة المحددة.

أحد الأشياء التي يجب توخي الحذر بشأنها هو افتراض سلوك متأصل حيث يوجد مجرد فرصة. وعلى وجه الخصوص، قد يبدو أن المتغير `RENAMED` يحتوي على كل من المسار الأصلي والجديد الذي تم إعادة تسميته. في الإصدارات السابقة، بدا حتى في بعض المنصات أن الأصل يأتي دائمًا قبل الجديد. ومع ذلك، لم يكن أي من هذا صحيحًا. من المستحيل معرفة المسار المتغير القديم أو الجديد بشكل موثوق ومتوافق، وقد تظهر عمليات إعادة تسمية "نصفية" (فقط الأصل، فقط الجديد)، وقد تظهر عمليات إعادة تسمية "غير معروفة" (كان التغيير إعادة تسمية، ولكن ما إذا كان القديم أو الجديد غير معروف)، وقد تنقسم أحداث إعادة التسمية عبر حدود تخميد مزدوجة، وما إلى ذلك.

يتحكم هذا الخيار في مكان بث هذه المعلومات. يتم تعيينه افتراضيًا على 'none'، والذي لا يبث معلومات الحدث على الإطلاق. الخيارات الأخرى هي 'environment' (مهمل)، 'stdio'، 'file'، 'json-stdio'، و 'json-file'.

وضعا 'stdio' و 'file' هما وضعان نصيان: 'stdio' يكتب المسارات المطلقة إلى المدخل القياسي للأمر، مسار واحد في كل سطر، كل منها مسبوق بـ `create:`، `remove:`، `rename:`، `modify:`، أو `other:`، ثم يغلق المقبض؛ 'file' يكتب نفس الشيء إلى ملف مؤقت، ويتم توفير مساره مع متغير البيئة `$WATCHEXEC_EVENTS_FILE`.

هناك أيضًا وضعان JSON، يعتمدان على كائنات JSON ويمكنهما تمثيل المجموعة الكاملة من الأحداث التي يتعامل معها Watchexec. إليك مثال على مجلد يتم إنشاؤه على Linux:

```json
{
"tags": [
{
"kind": "path",
"absolute": "/home/user/your/new-folder",
"filetype": "dir"
},
{
"kind": "fs",
"simple": "create",
"full": "Create(Folder)"
},
{
"kind": "source",
"source": "filesystem",
}
],
"metadata": {
"notify-backend": "inotify"
}
} ```

الحقول هي كما يلي:


- `tags`، بيانات الحدث المهيكلة.
- `tags[].kind`، والتي يمكن أن تكون:
* 'path'، جنبًا إلى جنب مع:
+ `absolute`، مسار مطلق.
+ `filetype`، نوع الملف إذا كان معروفًا ('dir'، 'file'، 'symlink'، 'other').
* 'fs':
+ `simple`، نوع الحدث "البسيط" ('access'، 'create'، 'modify'، 'remove'، أو 'other').
+ `full`، نوع الحدث "الكامل"، وهو معقد للغاية لوصفه بالكامل هنا، ولكنه يبدو مثل 'General(Precise(Specific))'.
* 'source'، جنبًا إلى جنب مع:
+ `source`، مصدر الحدث ('filesystem'، 'keyboard'، 'mouse'، 'os'، 'time'، 'internal').
* 'keyboard'، جنبًا إلى جنب مع:
+ `keycode`. حاليًا، القيمة 'eof' هي الوحيدة المدعومة.
* 'process'، للأحداث التي تسببها العمليات:
+ `pid`، معرف العملية.
* 'signal'، للإشارات المرسلة إلى Watchexec:
+ `signal`، اسم الإشارة المُطبع ('hangup'، 'interrupt'، 'quit'، 'terminate'، 'user1'، 'user2').
* 'completion'، عند انتهاء الأمر:
+ `disposition`، وضع الإنهاء ('success'، 'error'، 'signal'، 'stop'، 'exception'، 'continued').
+ `code`، رمز الإنهاء أو الإشارة أو التوقف أو الاستثناء.
- `metadata`، معلومات إضافية حول الحدث.

وضع 'json-stdio' سيقوم ببث أحداث JSON إلى المدخل القياسي للأمر، سطر واحد في كل مرة، ثم إغلاق المدخل القياسي. وضع 'json-file' سينشئ ملفًا مؤقتًا، ويكتب الأحداث إليه، ويوفر المسار إلى الملف مع $WATCHEXEC_EVENTS_FILE.
