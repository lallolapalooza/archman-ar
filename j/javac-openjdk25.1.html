للحصول على التفاصيل.

-Xdiags:[compact, verbose]
يحدد وضع التشخيص.
-Xdoclint
يمكّن الفحوصات الموصى بها للمشاكل في تعليقات التوثيق.
-Xdoclint:(all|none|[-]group)[/access]
يمكّن أو يعطّل مجموعات محددة من الفحوصات في تعليقات التوثيق.

يمكن أن تأخذ group إحدى القيم التالية: accessibility, html, missing, reference, syntax.

يحدد المتغير access الحد الأدنى لمستوى الرؤية للفئات والأعضاء التي يتحقق منها الخيار -Xdoclint. يمكن أن يأخذ إحدى القيم التالية (بترتيب من الأكثر إلى الأقل رؤية): public, protected, package, private.

مستوى access الافتراضي هو private.

عندما تسبقها doclint:، يمكن استخدام أسماء group و all مع @SuppressWarnings لقمع التحذيرات المتعلقة بتعليقات التوثيق في أجزاء من الكود الذي يتم تجميعه.

لمزيد من المعلومات حول مجموعات الفحص هذه، راجع قسم DocLint في وثائق الأمر javadoc. يتم تعطيل الخيار -Xdoclint افتراضيًا في الأمر javac.

على سبيل المثال، يتحقق الخيار التالي من الفئات والأعضاء (مع جميع مجموعات الفحص) التي لها مستوى الوصول المحدد protected وما فوق (والذي يتضمن protected و public):

-Xdoclint:all/protected

الخيار التالي يمكّن جميع مجموعات الفحص لجميع مستويات الوصول، باستثناء أنه لن يتحقق من أخطاء HTML للفئات والأعضاء التي لها مستوى الوصول package وما فوق (والذي يتضمن package، protected و public):

-Xdoclint:all,-html/package

-Xdoclint/package:[-]packages(,[-]package)*
يمكّن أو يعطّل الفحوصات في حزم محددة. كل package هو إما الاسم المؤهل لحزمة أو بادئة اسم حزمة متبوعة بـ .*، والتي تتوسع إلى جميع الحزم الفرعية للحزمة المعطاة. يمكن أن تسبق كل package علامة ناقص (-) لتعطيل الفحوصات لحزمة أو حزم محددة.

لمزيد من المعلومات، راجع قسم DocLint في وثائق الأمر javadoc.

-Xlint
يمكّن جميع التحذيرات الموصى بها. في هذا الإصدار، يوصى بتمكين جميع التحذيرات المتاحة.
-Xlint:[-]key(,[-]key)*
يمكّن و/أو يعطّل فئات التحذير باستخدام مفتاح واحد أو أكثر من المفاتيح الموضحة أدناه مفصولة بفواصل. المفاتيح all و none تمكّن أو تعطّل جميع الفئات (على التوالي)؛ المفاتيح الأخرى تمكّن الفئة المقابلة، أو تعطّلها إذا سبقتها علامة ناقص (-).

مسار الفئة ومسار الوحدة

The javac compiler searches for classes and resources in a list of directories and files specified by the -classpath option. If the -classpath option is not specified, javac searches the current directory. The -classpath option is described in -classpath option.

Linux and macOS:

javac -classpath /examples /examples/greetings/Hi.java

Windows:

C:\>javac -classpath \examples \examples\greetings\Hi.java

If you change greetings.Hi to use a banner utility, then that utility also needs to be accessible through the user class path.

Linux and macOS:

javac -classpath /examples:/lib/Banners.jar \
            /examples/greetings/Hi.java

Windows:

C:\>javac -classpath \examples;\lib\Banners.jar ^
            \examples\greetings\Hi.java

To execute a class in the greetings package, the program needs access to the greetings package, and to the classes that the greetings classes use.

Linux and macOS:

java -classpath /examples:/lib/Banners.jar greetings.Hi

Windows:

C:\>java -classpath \examples;\lib\Banners.jar greetings.Hi

تكوين نظام الوحدات

If you want to include additional modules in your compilation, use the --add-modules option. This may be necessary when you are compiling code that is not in a module, or which is in an automatic module, and the code refers to API in the additional modules.

If you want to restrict the set of modules in your compilation, use the --limit-modules option. This may be useful if you want to ensure that the code you are compiling is capable of running on a system with a limited set of modules installed.

If you want to break encapsulation and specify that additional packages should be considered as exported from a module, use the --add-exports option. This may be useful when performing white-box testing; relying on access to internal API in production code is strongly discouraged.

If you want to specify that additional packages should be considered as required by a module, use the --add-reads option. This may be useful when performing white-box testing; relying on access to internal API in production code is strongly discouraged.

You can patch additional content into any module using the --patch-module option. See [Patching a Module] for more details.

البحث عن تعريفات الوحدات والحزم والأنواع

To compile a source file, the compiler often needs information about a module or type, but the declaration is not in the source files specified on the command line.

javac needs type information for every class or interface used, extended, or implemented in the source file. This includes classes and interfaces not explicitly mentioned in the source file, but that provide information through inheritance.

For example, when you create a subclass of java.awt.Window, you are also using the ancestor classes of Window: java.awt.Container, java.awt.Component, and java.lang.Object.

When compiling code for a module, the compiler also needs to have available the declaration of that module.

A successful search may produce a class file, a source file, or both. If both are found, then you can use the -Xprefer option to instruct the compiler which to use.

If a search finds and uses a source file, then by default javac compiles that source file. This behavior can be altered with -implicit.

The compiler might not discover the need for some type information until after annotation processing completes. When the type information is found in a source file and no -implicit option is specified, the compiler gives a warning that the file is being compiled without being subject to annotation processing. To disable the warning, either specify the file on the command line (so that it will be subject to annotation processing) or use the -implicit option to specify whether or not class files should be generated for such source files.

The way that javac locates the declarations of those types depends on whether the reference exists within code for a module or not.

البحث في المسارات الموجهة للحزم

When searching for a source or class file on a path composed of package oriented locations, javac will check each location on the path in turn for the possible presence of the file. The first occurrence of a particular file shadows (hides) any subsequent occurrences of like-named files. This shadowing does not affect any search for any files with a different name. This can be convenient when searching for source files, which may be grouped in different locations, such as shared code, platform-specific code and generated code. It can also be useful when injecting alternate versions of a class file into a package, to debugging or other instrumentation reasons. But, it can also be dangerous, such as when putting incompatible different versions of a library on the class path.

البحث في المسارات الموجهة للوحدات

Prior to scanning any module paths for any package or type declarations, javac will lazily scan the following paths and locations to determine the modules that will be used in the compilation.

•
The module source path (see the --module-source-path option)
•
The path for upgradeable modules (see the --upgrade-module-path option)
•
The system modules (see the --system option)
•
The user module path ( see the --module-path option)

For any module, the first occurrence of the module during the scan completely shadows (hides) any subsequent appearance of a like-named module. While locating the modules, javac is able to determine the packages exported by the module and to associate with each module a package oriented path for the contents of the module. For any previously compiled module, this path will typically be a single entry for either a directory or a file that provides an internal directory-like hierarchy, such as a JAR file. Thus, when searching for a type that is in a package that is known to be exported by a module, javac can locate the declaration directly and efficiently.

البحث عن تعريف الوحدة

If the module has been previously compiled, the module declaration is located in a file named module-info.class in the root of the package hierarchy for the content of the module.

If the module is one of those currently being compiled, the module declaration will be either the file named module-info.class in the root of the package hierarchy for the module in the class output directory, or the file named module-info.java in one of the locations on the source path or one the module source path for the module.

البحث عن تعريف النوع عندما لا يكون المرجع في وحدة

When searching for a type that is referenced in code that is not in a module, javac will look in the following places:

•
The platform classes (or the types in exported packages of the platform modules) (This is for compiled class files only.)
•
Types in exported packages of any modules on the module path, if applicable. (This is for compiled class files only.)
•
Types in packages on the class path and/or source path:
•
If both are specified, javac looks for compiled class files on the class path and for source files on the source path.
•
If the class path is specified, but not source path, javac looks for both compiled class files and source files on the class path.
•
If the class path is not specified, it defaults to the current directory.

When looking for a type on the class path and/or source path, if both a compiled class file and a source file are found, the most recently modified file will be used by default. If the source file is newer, it will be compiled and will may override any previously compiled version of the file. You can use the -Xprefer option to override the default behavior.

بعد مسح الملفات المصدر والفئات الموجودة في سطر الأوامر لتحديد التعليقات التوضيحية الموجودة، يستعلم المترجم من المعالجات لتحديد التعليقات التوضيحية التي تعالجها. عند العثور على تطابق، يتم استدعاء المعالج. يمكن للمعالج المطالبة بالتعليقات التوضيحية التي يعالجها، وفي هذه الحالة لا يتم بذل أي محاولة أخرى للعثور على أي معالجات لهذه التعليقات التوضيحية. بعد المطالبة بجميع التعليقات التوضيحية، لا يبحث المترجم عن معالجات إضافية.

إذا قامت أي معالجات بإنشاء ملفات مصدر جديدة، تحدث جولة أخرى من معالجة التعليقات التوضيحية: يتم مسح أي ملفات مصدر تم إنشاؤها حديثًا، ويتم معالجة التعليقات التوضيحية كما في السابق. يتم أيضًا استدعاء أي معالجات تم استدعاؤها في الجولات السابقة في جميع الجولات اللاحقة. يستمر هذا حتى لا يتم إنشاء ملفات مصدر جديدة.

بعد جولة لا يتم فيها إنشاء ملفات مصدر جديدة، يتم استدعاء معالجات التعليقات التوضيحية مرة أخيرة، لإعطائها فرصة لإكمال أي عمل متبقٍ. أخيرًا، ما لم يتم استخدام الخيار -proc:only، يقوم المترجم بتجميع الملفات المصدر الأصلية وجميع الملفات المصدر التي تم إنشاؤها.

إذا كنت تستخدم معالج تعليقات توضيحية ينشئ ملفات مصدر إضافية ليتم تضمينها في الترجمة، يمكنك تحديد وحدة افتراضية ليتم استخدامها للملفات التي تم إنشاؤها حديثًا، للاستخدام عندما لا يتم إنشاء إعلان وحدة أيضًا. في هذه الحالة، استخدم الخيار --default-module-for-created-files.

بيئة الترجمة وبيئة التشغيل.

يتم تحليل الإعلانات في الملفات المصدر وملفات الفئات المترجمة مسبقًا بواسطة javac في بيئة ترجمة تختلف عن بيئة التشغيل المستخدمة لتشغيل javac نفسه. على الرغم من وجود تشابه متعمد بين العديد من خيارات javac والخيارات ذات الأسماء المماثلة لـ Java launcher، مثل --class-path، --module-path وما إلى ذلك، من المهم فهم أنه بشكل عام تؤثر خيارات javac فقط على البيئة التي يتم فيها ترجمة الملفات المصدر، ولا تؤثر على تشغيل javac نفسه.

التمييز بين بيئة الترجمة وبيئة التشغيل مهم عندما يتعلق الأمر باستخدام معالجات التعليقات التوضيحية. على الرغم من أن معالجات التعليقات التوضيحية تعالج العناصر (الإعلانات) الموجودة في بيئة الترجمة، فإن معالج التعليقات التوضيحية نفسه يتم تنفيذه في بيئة التشغيل. إذا كان لمعالج التعليقات التوضيحية تبعيات على مكتبات ليست في وحدات، يمكن وضع المكتبات، جنبًا إلى جنب مع معالج التعليقات التوضيحية نفسه، على مسار المعالج. (انظر الخيار --processor-path.) إذا كان معالج التعليقات التوضيحية وتبعياته في وحدات، فيجب عليك استخدام مسار وحدة المعالج بدلاً من ذلك. (انظر الخيار --processor-module-path.) عندما تكون هذه غير كافية، قد يكون من الضروري توفير تكوين إضافي لبيئة التشغيل. يمكن القيام بذلك بطريقتين:

1.
إذا تم استدعاء javac من سطر الأوامر، يمكن تمرير الخيارات إلى بيئة التشغيل الأساسية عن طريق إضافة بادئة للخيار بـ -J.
2.
يمكنك بدء نسخة من آلة جافا الافتراضية مباشرة واستخدام خيارات سطر الأوامر وواجهة برمجة التطبيقات (API) لتكوين بيئة يمكن فيها استدعاء javac من خلال أحد واجهات برمجة التطبيقات (APIs).

الترجمة لإصدارات سابقة من المنصة

javac يمكنه ترجمة الكود الذي سيتم استخدامه على إصدارات أخرى من المنصة، باستخدام إما الخيار --release، أو خيارات --source/-source و --target/-target، جنبًا إلى جنب مع خيارات إضافية لتحديد فئات المنصة.

اعتمادًا على إصدار المنصة المطلوب، هناك بعض القيود على بعض الخيارات التي يمكن استخدامها.

•
عند الترجمة لإصدارات JDK 8 والإصدارات السابقة، لا يمكنك استخدام أي خيار مخصص للاستخدام مع نظام الوحدات. يشمل هذا جميع الخيارات التالية:
•
--module-source-path، --upgrade-module-path، --system، --module-path، --add-modules، --add-exports، --add-opens، --add-reads، --limit-modules، --patch-module

إذا كنت تستخدم خيارات --source/-source أو --target/-target، فيجب عليك أيضًا تعيين فئات المنصة المناسبة باستخدام خيارات عائلة مسار فئة التمهيد.

•
عند الترجمة لإصدارات JDK 9 والإصدارات اللاحقة، لا يمكنك استخدام أي خيار مخصص لتكوين مسار فئة التمهيد. يشمل هذا جميع الخيارات التالية:
•
-Xbootclasspath/p:، -Xbootclasspath، -Xbootclasspath/a:، -endorseddirs، -Djava.endorsed.dirs، -extdirs، -Djava.ext.dirs، -profile

إذا كنت تستخدم خيارات --source/-source أو --target/-target، فيجب عليك أيضًا تعيين فئات المنصة المناسبة باستخدام الخيار --system لتحديد موقع إصدار مثبت مناسب من JDK.

عند استخدام الخيار --release، لا يجوز استخدام سوى واجهة برمجة التطبيقات (API) الموثقة المدعومة لهذا الإصدار؛ لا يمكنك استخدام أي خيارات لكسر التغليف للوصول إلى أي فئات داخلية.

واجهات برمجة التطبيقات (APIS)

يمكن استدعاء مترجم javac باستخدام واجهة برمجة تطبيقات (API) بثلاث طرق مختلفة:

واجهة برمجة تطبيقات مترجم جافا (Java Compiler API)
يوفر هذا الطريقة الأكثر مرونة لاستدعاء المترجم، بما في ذلك القدرة على ترجمة الملفات المصدر المقدمة في مخازن الذاكرة المؤقتة أو أنظمة الملفات غير القياسية الأخرى.
واجهة برمجة تطبيقات ToolProvider
يمكن الحصول على ToolProvider لـ javac عن طريق استدعاء ToolProvider.findFirst("javac"). هذا يعيد كائنًا له وظائف مكافئة لأداة سطر الأوامر.

ملاحظة: لا ينبغي الخلط بين واجهة برمجة التطبيقات هذه وواجهة برمجة التطبيقات (API) ذات الاسم المماثل في حزمة javax.tools.

واجهة برمجة التطبيقات القديمة (Legacy API) لـ javac
تم الاحتفاظ بواجهة برمجة التطبيقات هذه للتوافق مع الإصدارات السابقة فقط. يجب أن تستخدم جميع الأكواد الجديدة إما واجهة برمجة تطبيقات مترجم جافا أو واجهة برمجة تطبيقات ToolProvider.

ملاحظة: جميع الفئات والطرق الأخرى الموجودة في حزمة بأسماء تبدأ بـ com.sun.tools.javac (الحزم الفرعية لـ com.sun.tools.javac) هي داخلية بشكل صارم وعرضة للتغيير في أي وقت.
