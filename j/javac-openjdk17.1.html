PROCESSING ANNOTATIONS

The compiler may be invoked with options that enable annotation processing. Annotation processing is separate from compilation. It is performed before the compiler produces class files.

When annotation processing is enabled, the compiler will run annotation processors before it compiles the source files. If the annotation processing step finds no errors, then the compiler will compile the source files.

If the annotation processing step finds errors, then the compiler will not compile the source files, and will report the errors found during annotation processing. However, if the annotation processing step finds no errors, but the compilation step finds errors, the compiler will report the compilation errors.

Annotation processing is enabled by default when the compiler is invoked with the -processor option, or when the -processorpath option is used. If annotation processing is enabled, the compiler looks for annotation processors in the order specified by the -processorpath option, and then in the class path.

If the compiler is invoked with the -proc:none option, annotation processing is disabled.

If the compiler is invoked with the -proc:only option, the compiler will perform only annotation processing, and will not compile the source files.

The options described below are used to configure annotation processing.

Annotation Processing Options

-processor class
Explicitly specifies the annotation processors to use. If this option is not present, but annotation processing is enabled, the compiler will discover annotation processors automatically.
-processorpath classpath
Specifies the path to search for annotation processors. This is similar to the -classpath option, but is used only to find annotation processors. If this option is not present, the compiler will search for annotation processors in the class path.
-proc:none
Disables annotation processing. If this option is present, the compiler will not run any annotation processors.
-proc:only
Runs only annotation processing. Source files will not be compiled.
-XprintProcessorInfo
Prints information about which annotations a processor is asked to process.
-XprintRounds
Prints information about initial and subsequent annotation processing rounds.

Annotations with Source-Retention Policies

The compiler processes annotations with a RetentionPolicy.SOURCE retention policy only during the annotation processing phase. These annotations are discarded before the compilation phase. Thus, if you want an annotation processor to be able to access annotations declared with a RetentionPolicy.SOURCE retention policy, you must enable annotation processing.

The compiler supports annotation processing when invoked with options that enable annotation processing, such as -processor, -processorpath, -proc:only, or -XprintProcessorInfo. If annotation processing is not enabled, annotations with a RetentionPolicy.SOURCE retention policy will not be available to annotation processors.

The compiler processes annotations with RetentionPolicy.CLASS and RetentionPolicy.RUNTIME retention policies during both the annotation processing phase and the compilation phase. Thus, these annotations are always available to annotation processors, regardless of whether annotation processing is enabled.

-Xplugin:name args
Specifies the name and optional arguments for a plug-in to be run. If args are provided, name and args should be quoted or otherwise escape the whitespace characters between the name and all the arguments. For details on the API for a plugin, see the API documentation for jdk.compiler/com.sun.source.util.Plugin.
-Xprefer:[source, newer]
Specifies which file to read when both a source file and class file are found for an implicitly compiled class using one of the following options. See Searching for Module, Package and Type Declarations.
•
-Xprefer:newer: Reads the newer of the source or class files for a type (default).
•
-Xprefer:source : Reads the source file. Use -Xprefer:source when you want to be sure that any annotation processors can access annotations declared with a retention policy of SOURCE.
-Xprint
Prints a textual representation of specified types for debugging purposes. This does not perform annotation processing or compilation. The format of the output could change.
-XprintProcessorInfo
Prints information about which annotations a processor is asked to process.
-XprintRounds
Prints information about initial and subsequent annotation processing rounds.
-Xstdout filename
Sends compiler messages to the named file. By default, compiler messages go to System.err.

ENVIRONMENT VARIABLES

CLASSPATH

If the --class-path option or any of its alternate forms are not specified, the class path will default to the value of the CLASSPATH environment variable if it is set. However, it is recommended that this environment variable should not be set, and that the --class-path option should be used to provide an explicit value for the class path when one is required.

JDK_JAVAC_OPTIONS

The content of the JDK_JAVAC_OPTIONS environment variable, separated by white-spaces ( ) or white-space characters (\n, \t, \r, or \f) is prepended to the command line arguments passed to javac as a list of arguments.

The encoding requirement for the environment variable is the same as the javac command line on the system. JDK_JAVAC_OPTIONS environment variable content is treated in the same manner as that specified in the command line.

Single quotes (') or double quotes (") can be used to enclose arguments that contain whitespace characters. All content between the open quote and the first matching close quote are preserved by simply removing the pair of quotes. In case a matching quote is not found, the launcher will abort with an error message. @files are supported as they are specified in the command line. However, as in @files, use of a wildcard is not supported.

Examples of quoting arguments containing white spaces:

export JDK_JAVAC_OPTIONS='@"C:\white spaces\argfile"'

export JDK_JAVAC_OPTIONS='"@C:\white spaces\argfile"'

export JDK_JAVAC_OPTIONS='@C:\"white spaces"\argfile'

COMMAND-LINE ARGUMENT FILES

An argument file can include command-line options and source file names in any combination. The arguments within a file can be separated by spaces or new line characters. If a file name contains embedded spaces, then put the whole file name in double quotation marks.

File names within an argument file are relative to the current directory, not to the location of the argument file. Wildcards (*) are not allowed in these lists (such as for specifying *.java). Use of the at sign (@) to recursively interpret files is not supported. The -J options are not supported because they're passed to the launcher, which does not support argument files.

When executing the javac command, pass in the path and name of each argument file with the at sign (@) leading character. When the javac command encounters an argument beginning with the at sign (@), it expands the contents of that file into the argument list.

Examples of Using javac @filename

Single Argument File
You could use a single argument file named argfile to hold all javac arguments:

Two Argument Files
You can create two argument files: one for the javac options and the other for the source file names. Note that the following lists have no line-continuation characters.

Create a file named options that contains the following:

Linux and macOS:


-d classes
-g
-sourcepath /java/pubs/ws/1.3/src/share/classes

Windows:


-d classes

ARRANGEMENT OF SOURCE CODE

In the Java language, classes and interfaces can be organized into packages, and packages can be organized into modules. javac expects that the physical arrangement of source files in directories of the file system will mirror the organization of classes into packages, and packages into modules.

It is a widely adopted convention that module names and package names begin with a lower-case letter, and that class names begin with an upper-case letter.

When classes and interfaces are organized into a package, the package is represented as a directory, and any subpackages are represented as subdirectories.

يسمح javac بأي محتوى، سواء في شكل مصدر أو مجمع، بتصحيحه إلى أي وحدة نمطية باستخدام الخيار --patch-module. قد ترغب في القيام بذلك لتجميع تطبيقات بديلة لفئة ليتم تصحيحها في وقت التشغيل إلى JVM، أو لحقن فئات إضافية في الوحدة النمطية، كما هو الحال عند الاختبار.

شكل الخيار هو:

•
--patch-module module-name=file-path (path-separator file-path )*

حرف فاصل المسار هو ; على Windows، و : بخلاف ذلك. يجب أن تحدد المسارات المعطاة للوحدة النمطية جذر التسلسل الهرمي للحزم لمحتويات الوحدة النمطية.

يمكن إعطاء الخيار مرة واحدة على الأكثر لكل وحدة نمطية معينة. أي محتوى على المسار سيخفي أي محتوى يحمل نفس الاسم لاحقًا في المسار وفي الوحدة النمطية المصححة.

عند تصحيح الكود المصدري إلى أكثر من وحدة نمطية، يجب أيضًا استخدام --module-source-path، بحيث يتم تنظيم دليل الإخراج في تسلسل هرمي للوحدات النمطية، وقادر على الاحتفاظ بملفات الفئة المجمعة للوحدات النمطية التي يتم تجميعها.

ANNOTATION PROCESSING

يوفر الأمر javac دعمًا مباشرًا لمعالجة التعليقات التوضيحية.

تم تعريف واجهة برمجة التطبيقات لمعالجات التعليقات التوضيحية في الحزم javax.annotation.processing و javax.lang.model وحزمها الفرعية.

How Annotation Processing Works

ما لم يتم تعطيل معالجة التعليقات التوضيحية باستخدام الخيار -proc:none، يبحث المترجم عن أي معالجات تعليقات توضيحية متاحة. يمكن تحديد مسار البحث باستخدام الخيار -processorpath. إذا لم يتم تحديد مسار، يتم استخدام مسار فئة المستخدم. يتم تحديد المعالجات عن طريق ملفات تكوين موفر الخدمة المسماة META-INF/services/javax.annotation.processing. المعالج على مسار البحث. يجب أن تحتوي هذه الملفات على أسماء أي معالجات تعليقات توضيحية سيتم استخدامها، مدرجة سطرًا بسطر. بدلاً من ذلك، يمكن تحديد المعالجات بشكل صريح، باستخدام الخيار -processor.

بعد مسح الملفات المصدر والفئات في سطر الأوامر لتحديد التعليقات التوضيحية الموجودة، يستعلم المترجم من المعالجات لتحديد التعليقات التوضيحية التي تعالجها. عند العثور على تطابق، يتم استدعاء المعالج. يمكن للمعالج المطالبة بالتعليقات التوضيحية التي يعالجها، وفي هذه الحالة لا يتم بذل أي محاولة إضافية للعثور على أي معالجات لتلك التعليقات التوضيحية. بعد المطالبة بجميع التعليقات التوضيحية، لا يبحث المترجم عن معالجات إضافية.

إذا قامت أي معالجات بإنشاء ملفات مصدر جديدة، تحدث جولة أخرى من معالجة التعليقات التوضيحية: يتم مسح أي ملفات مصدر تم إنشاؤها حديثًا، ويتم معالجة التعليقات التوضيحية كما في السابق. يتم أيضًا استدعاء أي معالجات تم استدعاؤها في الجولات السابقة في جميع الجولات اللاحقة. يستمر هذا حتى لا يتم إنشاء ملفات مصدر جديدة.

بعد حدوث جولة لا يتم فيها إنشاء ملفات مصدر جديدة، يتم استدعاء معالجات التعليقات التوضيحية مرة أخيرة، لمنحها فرصة لإكمال أي عمل متبقٍ. أخيرًا، ما لم يتم استخدام الخيار -proc:only، يقوم المترجم بتجميع الملفات المصدر الأصلية وجميع الملفات المصدر المنشأة.

إذا كنت تستخدم معالج تعليقات توضيحية يقوم بإنشاء ملفات مصدر إضافية لتضمينها في عملية التجميع، يمكنك تحديد وحدة نمطية افتراضية لاستخدامها للملفات التي تم إنشاؤها حديثًا، للاستخدام عندما لا يتم أيضًا إنشاء إعلان وحدة نمطية. في هذه الحالة، استخدم الخيار --default-module-for-created-files.

Compilation Environment and Runtime Environment.

يتم تحليل الإعلانات في الملفات المصدر والفئات المجمعة مسبقًا بواسطة javac في بيئة تجميع تختلف عن بيئة وقت التشغيل المستخدمة لتنفيذ javac نفسه. على الرغم من وجود تشابه متعمد بين العديد من خيارات javac والخيارات ذات الأسماء المماثلة لـ Java launcher، مثل --class-path و --module-path وما إلى ذلك، فمن المهم فهم أنه بشكل عام تؤثر خيارات javac فقط على البيئة التي يتم فيها تجميع الملفات المصدر، ولا تؤثر على تشغيل javac نفسه.

التمييز بين بيئة التجميع وبيئة وقت التشغيل مهم عندما يتعلق الأمر باستخدام معالجات التعليقات التوضيحية. على الرغم من أن معالجات التعليقات التوضيحية تعالج العناصر (الإعلانات) الموجودة في بيئة التجميع، إلا أن معالج التعليقات التوضيحية نفسه يتم تنفيذه في بيئة وقت التشغيل. إذا كان لمعالج التعليقات التوضيحية تبعيات على مكتبات ليست في وحدات نمطية، يمكن وضع المكتبات، جنبًا إلى جنب مع معالج التعليقات التوضيحية نفسه، على مسار المعالج. (انظر الخيار --processor-path.) إذا كان معالج التعليقات التوضيحية وتبعياته في وحدات نمطية، فيجب عليك استخدام مسار وحدة المعالج بدلاً من ذلك. (انظر الخيار --processor-module-path.) عندما تكون هذه غير كافية، قد يكون من الضروري توفير تكوين إضافي لبيئة وقت التشغيل. يمكن القيام بذلك بطريقتين:

1.
إذا تم استدعاء javac من سطر الأوامر، يمكن تمرير الخيارات إلى وقت التشغيل الأساسي عن طريق إضافة بادئة للخيار بـ -J.
2.
يمكنك بدء نسخة من آلة جافا الافتراضية مباشرة واستخدام خيارات سطر الأوامر وواجهات برمجة التطبيقات لتكوين بيئة يمكن فيها استدعاء javac من خلال إحدى واجهات برمجة التطبيقات الخاصة به.

COMPILING FOR EARLIER RELEASES OF THE PLATFORM

يمكن لـ javac تجميع التعليمات البرمجية التي سيتم استخدامها على إصدارات سابقة من النظام الأساسي، باستخدام إما الخيار --release، أو الخيارين --source/-source و --target/-target، جنبًا إلى جنب مع خيارات إضافية لتحديد فئات النظام الأساسي.

اعتمادًا على إصدار النظام الأساسي المطلوب، هناك بعض القيود على بعض الخيارات التي يمكن استخدامها.

•
عند التجميع لإصدارات JDK 8 والإصدارات الأقدم، لا يمكنك استخدام أي خيار مخصص للاستخدام مع نظام الوحدات النمطية. وهذا يشمل جميع الخيارات التالية:
•
--module-source-path، --upgrade-module-path، --system، --module-path، --add-modules، --add-exports، --add-opens، --add-reads، --limit-modules، --patch-module

إذا كنت تستخدم الخيارات --source/-source أو --target/-target، فيجب عليك أيضًا تعيين فئات النظام الأساسي المناسبة باستخدام عائلة خيارات مسار فئة التمهيد.

•
عند التجميع لإصدارات JDK 9 والإصدارات اللاحقة، لا يمكنك استخدام أي خيار مخصص لتكوين مسار فئة التمهيد. وهذا يشمل جميع الخيارات التالية:
•
-Xbootclasspath/p:، -Xbootclasspath، -Xbootclasspath/a:، -endorseddirs، -Djava.endorsed.dirs، -extdirs، -Djava.ext.dirs، -profile

إذا كنت تستخدم الخيارات --source/-source أو --target/-target، فيجب عليك أيضًا تعيين فئات النظام الأساسي المناسبة باستخدام الخيار --system لتحديد موقع إصدار مثبت مناسب من JDK.

عند استخدام الخيار --release، لا يجوز استخدام سوى واجهة برمجة التطبيقات الموثقة المدعومة لهذا الإصدار؛ لا يمكنك استخدام أي خيارات لكسر التغليف للوصول إلى أي فئات داخلية.

يمكن استدعاء مترجم javac باستخدام واجهة برمجة تطبيقات بثلاث طرق مختلفة:

The Java Compiler API
توفر هذه الطريقة الأكثر مرونة لاستدعاء المترجم، بما في ذلك القدرة على تجميع الملفات المصدر المقدمة في مخازن مؤقتة في الذاكرة أو أنظمة ملفات غير قياسية أخرى.

The javac Legacy API
تم الاحتفاظ بواجهة برمجة التطبيقات هذه للتوافق مع الإصدارات السابقة فقط. يجب على جميع التعليمات البرمجية الجديدة استخدام واجهة برمجة تطبيقات مترجم جافا أو واجهة برمجة تطبيقات ToolProvider.

ملاحظة: جميع الفئات والطرق الأخرى الموجودة في حزمة بأسماء تبدأ بـ com.sun.tools.javac (الحزم الفرعية لـ com.sun.tools.javac) هي داخلية بحتة وعرضة للتغيير في أي وقت.
