الاسم

javac - قراءة تعريفات Java وتجميعها إلى ملفات class

الملخص

javac [الخيارات] [ملفات-المصدر-أو-أسماء-الفئات]

الخيارات
خيارات سطر الأوامر.
ملفات-المصدر-أو-أسماء-الفئات
ملفات المصدر المراد تجميعها (على سبيل المثال، Shape.java) أو أسماء الفئات المجمّعة مسبقًا المراد معالجتها للتعليقات التوضيحية (على سبيل المثال، geometry.MyShape).

الوصف

يقرأ الأمر javac ملفات المصدر التي تحتوي على إعلانات الوحدات والحزم والأنواع المكتوبة بلغة برمجة Java، ويقوم بتجميعها إلى ملفات فئات تعمل على الجهاز الافتراضي Java.

يمكن للأمر javac أيضاً معالجة التعليقات التوضيحية في ملفات المصدر والفئات الخاصة بـ Java.

يجب أن يكون امتداد اسم ملفات المصدر .java. أما ملفات الفئات فيكون امتداد اسم الملف الخاص بها .class. عادةً ما تحتوي كل من ملفات المصدر وملفات الفئات على أسماء ملفات تحدد محتوياتها. على سبيل المثال، يتم الإعلان عن فئة تسمى Shape في ملف مصدر يسمى Shape.java، ويتم تجميعها إلى ملف فئة يسمى Shape.class.

هناك طريقتان لتحديد ملفات المصدر إلى javac:

•
لعدد صغير من ملفات المصدر، يمكنك سرد أسماء ملفاتها على سطر الأوامر.
•
لعدد كبير من ملفات المصدر، يمكنك استخدام الخيار @filename على سطر الأوامر لتحديد ملف وسائط يسرد أسماء ملفاتها. راجع الخيارات القياسية للحصول على وصف للخيار وملفات وسائط سطر الأوامر للحصول على وصف لملفات وسائط javac.

ترتيب ملفات المصدر المحددة على سطر الأوامر أو في ملف الوسائط ليس مهماً. سيقوم javac بتجميع الملفات معاً، كمجموعة، وسيقوم تلقائياً بحل أي تبعيات بين الإعلانات في ملفات المصدر المختلفة.

يتوقع javac أن تكون ملفات المصدر مرتبة في تسلسل هرمي واحد أو أكثر من الدلائل على نظام الملفات، كما هو موضح في ترتيب الشيفرة المصدرية.

لتجميع ملف مصدر، يحتاج javac إلى العثور على إعلان كل فئة أو واجهة يتم استخدامها أو توسيعها أو تنفيذها بواسطة الشيفرة في ملف المصدر. يتيح ذلك لـ javac التحقق من أن الشيفرة لديها الحق في الوصول إلى تلك الفئات والواجهات. بدلاً من تحديد ملفات المصدر لتلك الفئات والواجهات بشكل صريح، يمكنك استخدام خيارات سطر الأوامر لإخبار javac بمكان البحث عن ملفات المصدر الخاصة بها. إذا قمت بتجميع ملفات المصدر تلك مسبقاً، يمكنك استخدام الخيارات لإخبار javac بمكان البحث عن ملفات الفئات المقابلة. الخيارات، التي تنتهي جميع أسمائها بـ "path"، موصوفة في الخيارات القياسية، وموصوفة بشكل أكبر في تكوين عملية تجميع والبحث عن إعلانات الوحدات والحزم والأنواع.

بشكل افتراضي، يقوم javac بتجميع كل ملف مصدر إلى ملف فئة في نفس الدليل الذي يوجد فيه ملف المصدر. ومع ذلك، يوصى بتحديد دليل وجهة منفصل باستخدام الخيار -d.

تتحكم خيارات سطر الأوامر ومتغيرات البيئة أيضاً في كيفية قيام javac بتنفيذ مهام متنوعة:

•
تجميع الشيفرة لتشغيلها على إصدارات سابقة من JDK.
•
تجميع الشيفرة لتشغيلها تحت مصحح أخطاء.
•
التحقق من المشكلات الأسلوبية في الشيفرة المصدرية لـ Java.
•
التحقق من المشكلات في تعليقات javadoc (/** ... */).
•
معالجة التعليقات التوضيحية في ملفات المصدر وملفات الفئات.
•
ترقية الوحدات وتصحيحها في بيئة وقت التجميع.

يدعم javac التجميع لإصدارات سابقة من المنصة ويمكن أيضاً استدعاؤه من شيفرة Java باستخدام واحدة من عدد من واجهات برمجة التطبيقات

OPTIONS

javac provides standard options, and extra options that are either non-standard or are for advanced use.

Some options take one or more arguments. If an argument contains spaces or other whitespace characters, the value should be quoted according to the conventions of the environment being used to invoke javac. If the option begins with a single dash (-) the argument should either directly follow the option name, or should be separated with a colon (:) or whitespace, depending on the option. If the option begins with a double dash (--), the argument may be separated either by whitespace or by an equals (=) character with no additional whitespace. For example,


-Aname="J. Duke"
-proc:only
-d myDirectory
--module-version 3
--module-version=3

In the following lists of options, an argument of path represents a search path, composed of a list of file system locations separated by the platform path separator character, (semicolon ; on Windows, or colon : on other systems.) Depending on the option, the file system locations may be directories, JAR files or JMOD files.

Standard Options

@filename
Reads options and file names from a file. To shorten or simplify the javac command, you can specify one or more files that contain arguments to the javac command (except -J options). This lets you to create javac commands of any length on any operating system. See Command-Line Argument Files.
-Akey[=value]
Specifies options to pass to annotation processors. These options are not interpreted by javac directly, but are made available for use by individual processors. The key value should be one or more identifiers separated by a dot (.).
--add-modules module,module
Specifies root modules to resolve in addition to the initial modules, or all modules on the module path if module is ALL-MODULE-PATH.
--boot-class-path path or -bootclasspath path
Overrides the location of the bootstrap class files.

Note: This can only be used when compiling for releases prior to JDK 9. As applicable, see the descriptions in --release, -source, or -target for details. For JDK 9 or later, see --system.

--class-path path, -classpath path, or -cp path
Specifies where to find user class files and annotation processors. This class path overrides the user class path in the CLASSPATH environment variable.
•
If --class-path, -classpath, or -cp are not specified, then the user class path is the value of the CLASSPATH environment variable, if that is set, or else the current directory.
•
If not compiling code for modules, if the --source-path or -sourcepath` option is not specified, then the user class path is also searched for source files.
•
If the -processorpath option is not specified, then the class path is also searched for annotation processors.
-d directory
Sets the destination directory (or class output directory) for class files. If a class is part of a package, then javac puts the class file in a subdirectory that reflects the module name (if appropriate) and package name. The directory, and any necessary subdirectories, will be created if they do not already exist.

If the -d option is not specified, then javac puts each class file in the same directory as the source file from which it was generated.

Except when compiling code for multiple modules, the contents of the class output directory will be organized in a package hierarchy. When compiling code for multiple modules, the contents of the output directory will be organized in a module hierarchy, with the contents of each module in a separate subdirectory, each organized as a package hierarchy.

Note: When compiling code for one or more modules, the class output directory will automatically be checked when searching for previously compiled classes. When not compiling for modules, for backwards compatibility, the directory is not automatically checked for previously compiled classes, and so it is recommended to specify the class output directory as one of the locations on the user class path, using the --class-path option or one of its alternate forms.

-deprecation
Shows a description of each use or override of a deprecated member or class. Without the -deprecation option, javac shows a summary of the source files that use or override deprecated members or classes. The -deprecation option is shorthand for -Xlint:deprecation.
--enable-preview
Enables preview language features. Used in conjunction with either -source or --release.
-encoding encoding
Specifies character encoding used by source files, such as EUC-JP and UTF-8. If the -encoding option is not specified, then the platform default converter is used.
-endorseddirs directories
Overrides the location of the endorsed standards path.

Note: This can only be used when compiling for releases prior to JDK 9. As applicable, see the descriptions in --release, -source, or -target for details.

-extdirs directories
Overrides the location of the installed extensions. directories is a list of directories, separated by the platform path separator (; on Windows, and : otherwise). Each JAR file in the specified directories is searched for class files. All JAR files found become part of the class path.

If you are compiling for a release of the platform that supports the Extension Mechanism, then this option specifies the directories that contain the extension classes. See [Compiling for Other Releases of the Platform].

Note: This can only be used when compiling for releases prior to JDK 9. As applicable, see the descriptions in --release, -source, or -target for details.

-g
Generates all debugging information, including local variables. By default, only line number and source file information is generated.
-g:[lines, vars, source]
Generates only the kinds of debugging information specified by the comma-separated list of keywords. Valid keywords are:
lines
Line number debugging information.
vars
Local variable debugging information.
source
Source file debugging information.
-g:none
Does not generate debugging information.
-h directory
Specifies where to place generated native header files.

When you specify this option, a native header file is generated for each class that contains native methods or that has one or more constants annotated with the java.lang.annotation.Native annotation. If the class is part of a package, then the compiler puts the native header file in a subdirectory that reflects the module name (if appropriate) and package name. The directory, and any necessary subdirectories, will be created if they do not already exist.

--help, -help or -?
Prints a synopsis of the standard options.
--help-extra or -X
Prints a synopsis of the set of extra options.
--help-lint
Prints the supported keys for the -Xlint option.
-implicit:[none, class]
Specifies whether or not to generate class files for implicitly referenced files:
•
-implicit:class --- Automatically generates class files.
•
-implicit:none --- Suppresses class file generation.

If this option is not specified, then the default automatically generates class files. In this case, the compiler issues a warning if any class files are generated when also doing annotation processing. The warning is not issued when the -implicit option is explicitly set. See Searching for Module, Package and Type Declarations.

-Joption
Passes option to the runtime system, where option is one of the Java options described on java command. For example, -J-Xms48m sets the startup memory to 48 MB.

Note: The CLASSPATH environment variable, -classpath option, -bootclasspath option, and -extdirs option do not specify the classes used to run javac. Trying to customize the compiler implementation with these options and variables is risky and often does not accomplish what you want. If you must customize the compiler implementation, then use the -J option to pass options through to the underlying Java launcher.

--limit-modules module,module*
Limits the universe of observable modules.
--module module-name (,module-name)* or -m module-name (,module-name)*
Compiles those source files in the named modules that are newer than the corresponding files in the output directory.
--module-path path or -p path
Specifies where to find application modules.
--module-source-path module-source-path
Specifies where to find source files when compiling code in multiple modules. See [Compilation Modes] and The Module Source Path Option.
--module-version version
Specifies the version of modules that are being compiled.
-nowarn
Disables warning messages. This option operates the same as the -Xlint:none option.
-parameters
Generates metadata for reflection on method parameters. Stores formal parameter names of constructors and methods in the generated class file so that the method java.lang.reflect.Executable.getParameters from the Reflection API can retrieve them.
-proc:[none, only]
Controls whether annotation processing and compilation are done. -proc:none means that compilation takes place without annotation processing. -proc:only means that only annotation processing is done, without any subsequent compilation.
-processor class1[,class2,class3...]
Names of the annotation processors to run. This bypasses the default discovery process.
--processor-module-path path
Specifies the module path used for finding annotation processors.
--processor-path path or -processorpath path
Specifies where to find annotation processors. If this option is not used, then the class path is searched for processors.
-profile profile
Checks that the API used is available in the specified profile.

Note: This can only be used when compiling for releases prior to JDK 9. As applicable, see the descriptions in --release, -source, or -target for details.

--release release
Compiles source code according to the rules of the Java programming language for the specified Java SE release, generating class files which target that release. Source code is compiled against the combined Java SE and JDK API for the specified release.

The supported values of release are the current Java SE release and a limited number of previous releases, detailed in the command-line help.

For the current release, the Java SE API consists of the java.*, javax.*, and org.* packages that are exported by the Java SE modules in the release; the JDK API consists of the com.* and jdk.* packages that are exported by the JDK modules in the release, plus the javax.* packages that are exported by standard, but non-Java SE, modules in the release.

For previous releases, the Java SE API and the JDK API are as defined in that release.

Note: When using --release, you cannot also use the --source/-source or --target/-target options.

Note: When using --release to specify a release that supports the Java Platform Module System, the --add-exports option cannot be used to enlarge the set of packages exported by the Java SE, JDK, and standard modules in the specified release.

-s directory
Specifies the directory used to place the generated source files. If a class is part of a package, then the compiler puts the source file in a subdirectory that reflects the module name (if appropriate) and package name. The directory, and any necessary subdirectories, will be created if they do not already exist.

Except when compiling code for multiple modules, the contents of the source output directory will be organized in a package hierarchy. When compiling code for multiple modules, the contents of the source output directory will be organized in a module hierarchy, with the contents of each module in a separate subdirectory, each organized as a package hierarchy.

--source release or -source release
Compiles source code according to the rules of the Java programming language for the specified Java SE release. The supported values of release are the current Java SE release and a limited number of previous releases, detailed in the command-line help.

If the option is not specified, the default is to compile source code according to the rules of the Java programming language for the current Java SE release.

--source-path path or -sourcepath path
Specifies where to find source files. Except when compiling multiple modules together, this is the source code path used to search for class or interface definitions.

Note: Classes found through the class path might be recompiled when their source files are also found. See Searching for Module, Package and Type Declarations.

--system jdk | none
Overrides the location of system modules.
--target release or -target release
Generates class files suitable for the specified Java SE release. The supported values of release are the current Java SE release and a limited number of previous releases, detailed in the command-line help.

Note: The target release must be equal to or higher than the source release. (See --source.)

--upgrade-module-path path
Overrides the location of upgradeable modules.
-verbose
Outputs messages about what the compiler is doing. Messages include information about each class loaded and each source file compiled.
--version or -version
Prints version information.
-Werror
Terminates compilation when warnings occur.

متغيرات البيئة

CLASSPATH

إذا لم يتم تحديد الخيار --class-path أو أي من صيغه البديلة، فسيتم تعيين مسار الفئة افتراضيًا إلى قيمة متغير البيئة CLASSPATH إذا كان معينًا. ومع ذلك، يُوصى بعدم تعيين متغير البيئة هذا، ويُوصى باستخدام الخيار --class-path لتوفير قيمة صريحة لمسار الفئة عند الحاجة إليها.

JDK_JAVAC_OPTIONS

يتم إضافة محتوى متغير البيئة JDK_JAVAC_OPTIONS، مفصولًا بمسافات بيضاء ( ) أو أحرف مسافة بيضاء (\n، \t، \r، أو \f)، إلى وسائط سطر الأوامر التي تُمرَّر إلى javac كقائمة من الوسائط.

متطلبات الترميز لمتغير البيئة هي نفسها الخاصة بسطر أوامر javac على النظام. يُعامَل محتوى متغير البيئة JDK_JAVAC_OPTIONS بالطريقة نفسها المحددة في سطر الأوامر.

يمكن استخدام علامات الاقتباس المفردة (') أو علامات الاقتباس المزدوجة (") لإحاطة الوسائط التي تحتوي على أحرف مسافة بيضاء. يتم الحفاظ على كل المحتوى بين علامة الاقتباس الافتتاحية وأول علامة اقتباس إغلاق مطابقة بمجرد إزالة زوج علامات الاقتباس. في حال عدم العثور على علامة اقتباس مطابقة، سيتوقف المُشغِّل برسالة خطأ. يتم دعم @files كما هي محددة في سطر الأوامر. ومع ذلك، كما هو الحال في @files، لا يتم دعم استخدام أحرف البدل.

أمثلة على إحاطة الوسائط التي تحتوي على مسافات بيضاء بعلامات اقتباس:

export JDK_JAVAC_OPTIONS='@"C:\white spaces\argfile"'

export JDK_JAVAC_OPTIONS='"@C:\white spaces\argfile"'

export JDK_JAVAC_OPTIONS='@C:\"white spaces"\argfile'

ملفات وسائط سطر الأوامر

يمكن أن يتضمن ملف الوسائط خيارات سطر الأوامر وأسماء ملفات المصدر بأي مزيج. يمكن فصل الوسائط داخل الملف بمسافات أو أحرف سطر جديد. إذا احتوى اسم ملف على مسافات مضمّنة، فضع اسم الملف بالكامل بين علامتي اقتباس مزدوجتين.

أسماء الملفات داخل ملف الوسائط نسبية إلى الدليل الحالي، وليس إلى موقع ملف الوسائط. لا يُسمح بأحرف البدل (*) في هذه القوائم (مثل تحديد *.java). لا يُدعم استخدام علامة @ (@) لتفسير الملفات بشكل متكرر. لا تُدعم خيارات -J لأنها تُمرَّر إلى المشغّل، الذي لا يدعم ملفات الوسائط.

عند تنفيذ الأمر javac، مرّر مسار واسم كل ملف وسائط مع حرف علامة @ (@) في البداية. عندما يصادف الأمر javac وسيطًا يبدأ بعلامة @ (@)، فإنه يوسّع محتويات ذلك الملف إلى قائمة الوسائط.

أمثلة على استخدام javac @filename

ملف وسائط واحد
يمكنك استخدام ملف وسائط واحد باسم argfile لاحتواء جميع وسائط javac:

javac @argfile

يمكن أن يحتوي ملف الوسائط هذا على محتويات كلا الملفين الموضحين في المثال التالي ملفا وسائط.

ملفا وسائط
يمكنك إنشاء ملفي وسائط: أحدهما لخيارات javac والآخر لأسماء ملفات المصدر. لاحظ أن القوائم التالية لا تحتوي على أحرف استمرار الأسطر.

أنشئ ملفًا باسم options يحتوي على ما يلي:

Linux وmacOS:


-d classes
-g
-sourcepath /java/pubs/ws/1.3/src/share/classes

Windows:


-d classes
-g
-sourcepath C:\java\pubs\ws\1.3\src\share\classes

أنشئ ملفًا باسم classes يحتوي على ما يلي:


MyClass1.java
MyClass2.java
MyClass3.java

ثم شغّل الأمر javac كما يلي:

javac @options @classes

ملفات الوسائط مع المسارات
يمكن أن تحتوي ملفات الوسائط على مسارات، لكن أي أسماء ملفات داخل الملفات تكون نسبية إلى دليل العمل الحالي (وليس path1 أو path2):

javac @path1/options @path2/classes

ترتيب الشيفرة المصدرية

في لغة Java، يمكن تنظيم الفئات والواجهات في حزم، ويمكن تنظيم الحزم في وحدات. تتوقع javac أن يعكس الترتيب الفيزيائي لملفات المصدر في أدلة نظام الملفات تنظيم الفئات في حزم، والحزم في وحدات.

من الاصطلاحات المعتمدة على نطاق واسع أن تبدأ أسماء الوحدات وأسماء الحزم بحرف صغير، وأن تبدأ أسماء الفئات بحرف كبير.

ترتيب الشيفرة المصدرية لحزمة

عندما تُنظَّم الفئات والواجهات في حزمة، تُمثَّل الحزمة كدليل، وتُمثَّل أي حزم فرعية كأدلة فرعية.

على سبيل المثال:

•
تُمثَّل الحزمة p كدليل يُسمى p.
•
تُمثَّل الحزمة p.q -- أي الحزمة الفرعية q التابعة للحزمة p -- كالدليل الفرعي q داخل الدليل p. وبالتالي فإن شجرة الأدلة التي تمثل الحزمة p.q هي p\q على Windows، و p/q على الأنظمة الأخرى.
•
تُمثَّل الحزمة p.q.r كشجرة الأدلة p\q\r (على Windows) أو p/q/r (على الأنظمة الأخرى).

داخل دليل أو دليل فرعي، تمثل ملفات .java الفئات والواجهات في الحزمة أو الحزمة الفرعية المقابلة.

على سبيل المثال:

•
تُمثَّل الفئة X المعلنة في الحزمة p بالملف X.java في دليل p.
•
تُمثَّل الفئة Y المعلنة في الحزمة p.q بالملف Y.java في الدليل الفرعي q داخل الدليل p.
•
تُمثَّل الفئة Z المعلنة في الحزمة p.q.r بالملف Z.java في الدليل الفرعي r داخل p\q (على Windows) أو p/q (على الأنظمة الأخرى).

في بعض الحالات، يكون من الملائم تقسيم الشيفرة إلى أدلة منفصلة، كل منها مُنظَّم كما هو موضح أعلاه، وتحديد القائمة الإجمالية للأدلة إلى javac.

ترتيب الشيفرة المصدرية لوحدة

في لغة Java، الوحدة هي مجموعة من الحزم المصممة لإعادة الاستخدام. بالإضافة إلى ملفات .java الخاصة بالفئات والواجهات، تحتوي كل وحدة على ملف مصدر يُسمى module-info.java والذي:

1.
يعلن اسم الوحدة؛
2.
يسرد الحزم التي تصدّرها الوحدة (للسماح بإعادة استخدامها من قبل الوحدات الأخرى)؛
3.
يسرد الوحدات الأخرى التي تتطلبها الوحدة (لإعادة استخدام حزمها المصدَّرة).

عندما تُنظَّم الحزم في وحدة، تُمثَّل الوحدة بدليل واحد أو أكثر يمثل الحزم في الوحدة، يحتوي أحدها على ملف module-info.java. قد يكون من الملائم، لكنه ليس مطلوبًا، استخدام دليل واحد، مُسمَّى باسم الوحدة، لاحتواء ملف module-info.java إلى جانب شجرة الأدلة التي تمثل الحزم في الوحدة (أي التسلسل الهرمي للحزم الموصوف أعلاه). عادةً ما يُملى الترتيب الدقيق للشيفرة المصدرية لوحدة ما بالاصطلاحات المعتمدة من قبل بيئة تطوير (IDE) أو نظام بناء.

على سبيل المثال:

•
قد تُمثَّل الوحدة a.b.c بالدليل a.b.c، على جميع الأنظمة.
•
يُمثَّل إعلان الوحدة بالملف module-info.java في دليل a.b.c.
•
إذا كانت الوحدة تحتوي على الحزمة p.q.r، فإن دليل a.b.c يحتوي على شجرة الأدلة p\q\r (على Windows) أو p/q/r (على الأنظمة الأخرى).

قد تفرض بيئة التطوير بعض التسلسلات الهرمية للأدلة بين الدليل المُسمَّى باسم الوحدة وملفات المصدر التي ستُقرأ بواسطة javac.

على سبيل المثال:

•
قد تُمثَّل الوحدة a.b.c بالدليل a.b.c
•
قد يكون إعلان الوحدة وحزم الوحدة في بعض الأدلة الفرعية لـ a.b.c، مثل src\main\java (على Windows) أو src/main/java (على الأنظمة الأخرى).

تكوين عملية الترجمة

يصف هذا القسم كيفية تكوين javac لتنفيذ عملية ترجمة أساسية.

راجع تكوين نظام الوحدات للحصول على تفاصيل إضافية لاستخدامها عند الترجمة لإصدار من المنصة يدعم الوحدات.

ملفات المصدر

•
حدد ملفات المصدر المراد ترجمتها على سطر الأوامر.

إذا لم تكن هناك أخطاء في الترجمة، فسيتم وضع ملفات الفئة المقابلة في دليل الإخراج.

قد تحد بعض الأنظمة من المقدار الذي يمكنك وضعه على سطر أوامر؛ للتغلب على تلك القيود، يمكنك استخدام ملفات الوسائط.

عند ترجمة الشيفرة الخاصة بالوحدات، يمكنك أيضًا تحديد ملفات المصدر بشكل غير مباشر، باستخدام الخيار --module أو -m.

دليل الإخراج

•
استخدم الخيار -d لتحديد دليل إخراج توضع فيه ملفات الفئة المترجمة.

سيتم تنظيم هذا عادةً في تسلسل هرمي للحزم، ما لم تكن تترجم شيفرة مصدر من وحدات متعددة، وفي هذه الحالة سيتم تنظيمه كـ تسلسل هرمي للوحدات.

عند اكتمال الترجمة، إذا كنت تترجم وحدة واحدة أو أكثر، يمكنك وضع دليل الإخراج على مسار الوحدات الخاص بـ مشغّل Java؛ وإلا، يمكنك وضع دليل الإخراج على مسار الفئات الخاص بمشغّل Java.

الشيفرة المترجمة مسبقًا

قد تشير الشيفرة المراد ترجمتها إلى مكتبات تتجاوز ما توفره المنصة. إذا كان الأمر كذلك، يجب عليك وضع هذه المكتبات على مسار الفئات أو مسار الوحدات. إذا لم تكن شيفرة المكتبة في وحدة، فضعها على مسار الفئات؛ وإذا كانت في وحدة، فضعها على مسار الوحدات.

•
استخدم الخيار --class-path لتحديد المكتبات التي ستوضع على مسار الفئات. يجب تنظيم المواقع على مسار الفئات في تسلسل هرمي للحزم. يمكنك أيضًا استخدام أشكال بديلة من الخيار: -classpath أو -cp.
•
استخدم الخيار --module-path لتحديد المكتبات التي ستوضع على مسار الوحدات. يجب أن تكون المواقع على مسار الوحدات إما وحدات أو أدلة لوحدات. يمكنك أيضًا استخدام شكل بديل من الخيار: -p.

راجع تكوين نظام الوحدات للحصول على تفاصيل حول كيفية تعديل التكوين الافتراضي لوحدات المكتبة.

ملاحظة: خيارات مسار الفئات ومسار الوحدات ليست حصرية بشكل متبادل، على الرغم من أنه ليس شائعًا تحديد مسار الفئات عند ترجمة الشيفرة لوحدة واحدة أو أكثر.

ملفات مصدر إضافية

قد تشير الشيفرة المراد ترجمتها إلى أنواع في ملفات مصدر إضافية غير محددة على سطر الأوامر. إذا كان الأمر كذلك، يجب عليك وضع تلك الملفات المصدرية على مسار المصدر أو مسار الوحدات. يمكنك تحديد واحد فقط من هذه الخيارات: إذا كنت لا تترجم شيفرة لوحدة، أو إذا كنت تترجم شيفرة لوحدة واحدة فقط، فاستخدم مسار المصدر؛ وإذا كنت تترجم شيفرة لوحدات متعددة، فاستخدم مسار مصدر الوحدات.

•
استخدم الخيار --source-path لتحديد مواقع ملفات المصدر الإضافية التي قد يقرأها javac. يجب تنظيم المواقع على مسار المصدر في تسلسل هرمي للحزم. يمكنك أيضًا استخدام شكل بديل من الخيار: -sourcepath.
•
استخدم الخيار --module-source-path مرة واحدة أو أكثر لتحديد موقع ملفات مصدر إضافية في وحدات مختلفة قد يقرأها javac، أو عند ترجمة ملفات مصدر في وحدات متعددة. يمكنك إما تحديد المواقع لكل وحدة بشكل فردي، أو يمكنك تنظيم ملفات المصدر بحيث يمكنك تحديد المواقع معًا. لمزيد من التفاصيل، راجع خيار مسار مصدر الوحدات.

إذا كنت تريد أن تكون قادرًا على الإشارة إلى أنواع في ملفات مصدر إضافية ولكنك لا تريد ترجمتها، فاستخدم الخيار -implicit.

ملاحظة: إذا كنت تترجم شيفرة لوحدات متعددة، فيجب عليك دائمًا تحديد مسار مصدر الوحدات، ويجب أن تكون جميع ملفات المصدر المحددة على سطر الأوامر في أحد الأدلة على مسار مصدر الوحدات، أو في دليل فرعي منه.

مثال على ترجمة ملفات مصدر متعددة

يقوم هذا المثال بترجمة ملفات المصدر Aloha.java، GutenTag.java، Hello.java، و Hi.java في حزمة greetings.

Linux وmacOS:


% javac greetings/*.java
% ls greetings
Aloha.class         GutenTag.class      Hello.class         Hi.class
Aloha.java          GutenTag.java       Hello.java          Hi.java

Windows:


C:\>javac greetings\*.java
C:\>dir greetings
Aloha.class         GutenTag.class      Hello.class         Hi.class
Aloha.java          GutenTag.java       Hello.java          Hi.java

مثال على تحديد مسار فئات المستخدم

بعد تغيير أحد ملفات المصدر في المثال السابق، أعد ترجمته:

Linux وmacOS:


pwd
/examples
javac greetings/Hi.java

Windows:


C:\>cd
\examples
C:\>javac greetings\Hi.java

نظرًا لأن greetings.Hi يشير إلى فئات أخرى في حزمة greetings، يحتاج المترجم إلى العثور على هذه الفئات الأخرى. يعمل المثال السابق لأن مسار فئات المستخدم الافتراضي هو الدليل الذي يحتوي على دليل الحزمة. إذا كنت تريد إعادة ترجمة هذا الملف دون الاهتمام بالدليل الذي أنت فيه، فأضف دليل examples إلى مسار فئات المستخدم عن طريق تعيين CLASSPATH. يستخدم هذا المثال الخيار -classpath.

Linux وmacOS:

javac -classpath /examples /examples/greetings/Hi.java

Windows:

C:\>javac -classpath \examples \examples\greetings\Hi.java

إذا قمت بتغيير greetings.Hi لاستخدام أداة لافتة، فإن تلك الأداة تحتاج أيضًا إلى أن تكون متاحة عبر مسار فئات المستخدم.

Linux وmacOS:


javac -classpath /examples:/lib/Banners.jar \
            /examples/greetings/Hi.java

Windows:


C:\>javac -classpath \examples;\lib\Banners.jar ^
            \examples\greetings\Hi.java

لتنفيذ فئة في حزمة greetings، يحتاج البرنامج إلى الوصول إلى حزمة greetings، وإلى الفئات التي تستخدمها فئات greetings.

Linux وmacOS:

java -classpath /examples:/lib/Banners.jar greetings.Hi

Windows:

C:\>java -classpath \examples;\lib\Banners.jar greetings.Hi

تكوين نظام الوحدات

إذا كنت تريد تضمين وحدات إضافية في عملية الترجمة البرمجية الخاصة بك، فاستخدم الخيار --add-modules. قد يكون هذا ضروريًا عندما تقوم بترجمة تعليمات برمجية ليست في وحدة، أو موجودة في وحدة تلقائية، وتشير التعليمات البرمجية إلى واجهة برمجة تطبيقات في الوحدات الإضافية.

إذا كنت تريد تقييد مجموعة الوحدات في عملية الترجمة البرمجية الخاصة بك، فاستخدم الخيار --limit-modules. قد يكون هذا مفيدًا إذا كنت تريد التأكد من أن التعليمات البرمجية التي تقوم بترجمتها قادرة على العمل على نظام يحتوي على مجموعة محدودة من الوحدات المثبتة.

إذا كنت تريد كسر التغليف وتحديد أن حزمًا إضافية يجب اعتبارها مُصدَّرة من وحدة ما، فاستخدم الخيار --add-exports. قد يكون هذا مفيدًا عند إجراء اختبار الصندوق الأبيض؛ يُنصح بشدة بعدم الاعتماد على الوصول إلى واجهة برمجة تطبيقات داخلية في تعليمات الإنتاج البرمجية.

إذا كنت تريد تحديد أن حزمًا إضافية يجب اعتبارها مطلوبة بواسطة وحدة ما، فاستخدم الخيار --add-reads. قد يكون هذا مفيدًا عند إجراء اختبار الصندوق الأبيض؛ يُنصح بشدة بعدم الاعتماد على الوصول إلى واجهة برمجة تطبيقات داخلية في تعليمات الإنتاج البرمجية.

يمكنك ترقيع محتوى إضافي في أي وحدة باستخدام الخيار --patch-module. راجع [ترقيع وحدة] لمزيد من التفاصيل.

البحث عن إعلانات الوحدات والحزم والأنواع

لتجميع ملف مصدر، غالبًا ما يحتاج المترجم إلى معلومات حول وحدة أو نوع، لكن الإعلان ليس في ملفات المصدر المحددة على سطر الأوامر.

يحتاج javac إلى معلومات النوع لكل فئة أو واجهة تُستخدم أو تُوسَّع أو تُنفَّذ في ملف المصدر. يشمل ذلك الفئات والواجهات غير المذكورة صراحةً في ملف المصدر، ولكنها توفر معلومات من خلال الوراثة.

على سبيل المثال، عند إنشاء فئة فرعية من java.awt.Window، فإنك تستخدم أيضًا الفئات السلف لـ Window: java.awt.Container، وjava.awt.Component، وjava.lang.Object.

عند تجميع شيفرة لوحدة ما، يحتاج المترجم أيضًا إلى أن يكون إعلان تلك الوحدة متاحًا.

قد ينتج عن البحث الناجح ملف فئة، أو ملف مصدر، أو كليهما. إذا تم العثور على كليهما، فيمكنك استخدام الخيار -Xprefer لإرشاد المترجم إلى أيّهما يستخدم.

إذا وجد البحث ملف مصدر واستخدمه، فإن javac يقوم افتراضيًا بتجميع ملف المصدر ذلك. يمكن تغيير هذا السلوك باستخدام -implicit.

قد لا يكتشف المترجم الحاجة إلى بعض معلومات النوع حتى بعد اكتمال معالجة التعليقات التوضيحية. عندما يتم العثور على معلومات النوع في ملف مصدر ولم يتم تحديد خيار -implicit، يعطي المترجم تحذيرًا بأن الملف يتم تجميعه دون أن يخضع لمعالجة التعليقات التوضيحية. لتعطيل التحذير، إما حدد الملف على سطر الأوامر (بحيث يخضع لمعالجة التعليقات التوضيحية) أو استخدم الخيار -implicit لتحديد ما إذا كان يجب إنشاء ملفات فئة لملفات المصدر هذه أم لا.

تعتمد الطريقة التي يحدد بها javac مواقع إعلانات تلك الأنواع على ما إذا كانت الإشارة موجودة داخل شيفرة وحدة أم لا.

البحث في المسارات الموجهة للحزم

عند البحث عن ملف مصدر أو ملف فئة على مسار مكوّن من مواقع موجهة للحزم، سيتحقق javac من كل موقع على المسار بدوره لاحتمال وجود الملف. أول ظهور لملف معين يحجب (يخفي) أي ظهور لاحق لملفات مشابهة الاسم. لا يؤثر هذا الحجب على أي بحث عن أي ملفات ذات اسم مختلف. يمكن أن يكون هذا ملائمًا عند البحث عن ملفات المصدر، التي قد تكون مجمعة في مواقع مختلفة، مثل الشيفرة المشتركة والشيفرة الخاصة بالمنصة والشيفرة المولّدة. يمكن أن يكون مفيدًا أيضًا عند إدخال إصدارات بديلة من ملف فئة إلى حزمة، لأغراض التصحيح أو أغراض أخرى. لكنه يمكن أن يكون خطيرًا أيضًا، كما هو الحال عند وضع إصدارات مختلفة غير متوافقة من مكتبة على مسار الفئات.

البحث في المسارات الموجهة للوحدات

قبل فحص أي مسارات وحدات بحثًا عن أي إعلانات حزم أو أنواع، سيقوم javac بفحص المسارات والمواقع التالية بشكل كسول لتحديد الوحدات التي ستُستخدم في التجميع.

•
مسار مصدر الوحدات (انظر الخيار --module-source-path)
•
مسار الوحدات القابلة للترقية (انظر الخيار --upgrade-module-path)
•
وحدات النظام (انظر الخيار --system)
•
مسار وحدات المستخدم (انظر الخيار --module-path)

بالنسبة لأي وحدة، فإن أول ظهور للوحدة أثناء الفحص يحجب (يخفي) تمامًا أي ظهور لاحق لوحدة مشابهة الاسم. أثناء تحديد مواقع الوحدات، يكون javac قادرًا على تحديد الحزم التي تصدّرها الوحدة وربط كل وحدة بمسار موجه للحزم لمحتويات الوحدة. بالنسبة لأي وحدة مجمّعة مسبقًا، سيكون هذا المسار عادةً مدخلًا واحدًا إما لدليل أو لملف يوفر تسلسلًا هرميًا داخليًا شبيهًا بالدليل، مثل ملف JAR. وبالتالي، عند البحث عن نوع موجود في حزمة معروف أن وحدة ما تصدّرها، يمكن لـ javac تحديد موقع الإعلان مباشرةً وبكفاءة.

البحث عن إعلان وحدة

إذا كانت الوحدة قد جُمّعت مسبقًا، فإن إعلان الوحدة يوجد في ملف باسم module-info.class في جذر التسلسل الهرمي للحزم لمحتوى الوحدة.

إذا كانت الوحدة إحدى الوحدات التي يتم تجميعها حاليًا، فسيكون إعلان الوحدة إما الملف المسمى module-info.class في جذر التسلسل الهرمي للحزم للوحدة في دليل إخراج الفئات، أو الملف المسمى module-info.java في أحد المواقع على مسار المصدر أو مسار مصدر الوحدات للوحدة.

البحث عن إعلان نوع عندما لا تكون الإشارة في

وحدة

عند البحث عن نوع يُشار إليه في شيفرة ليست في وحدة، سيبحث javac في الأماكن التالية:

•
فئات المنصة (أو الأنواع في الحزم المصدّرة من وحدات المنصة) (هذا لملفات الفئات المجمّعة فقط.)
•
الأنواع في الحزم المصدّرة من أي وحدات على مسار الوحدات، إن أمكن. (هذا لملفات الفئات المجمّعة فقط.)
•
الأنواع في الحزم على مسار الفئات و/أو مسار المصدر:
•
إذا تم تحديد كليهما، يبحث javac عن ملفات الفئات المجمّعة على مسار الفئات وعن ملفات المصدر على مسار المصدر.
•
إذا تم تحديد مسار الفئات، ولكن ليس مسار المصدر، يبحث javac عن كل من ملفات الفئات المجمّعة وملفات المصدر على مسار الفئات.
•
إذا لم يتم تحديد مسار الفئات، فإنه يعود افتراضيًا إلى الدليل الحالي.

عند البحث عن نوع على مسار الفئات و/أو مسار المصدر، إذا تم العثور على كل من ملف فئة مجمّع وملف مصدر، فسيتم استخدام الملف الأحدث تعديلًا افتراضيًا. إذا كان ملف المصدر أحدث، فسيتم تجميعه وقد يتجاوز أي نسخة مجمّعة سابقًا من الملف. يمكنك استخدام الخيار -Xprefer لتجاوز السلوك الافتراضي.

البحث عن إعلان نوع عندما تكون الإشارة في

وحدة

عند البحث عن نوع يُشار إليه في شيفرة داخل وحدة، سيفحص javac إعلان الوحدة المحيطة لتحديد ما إذا كان النوع موجودًا في حزمة تصدّرها وحدة أخرى يمكن للوحدة المحيطة قراءتها. إذا كان الأمر كذلك، فسينتقل javac ببساطة ومباشرة إلى تعريف تلك الوحدة للعثور على تعريف النوع المطلوب. ما لم تكن الوحدة وحدة أخرى من الوحدات التي يتم تجميعها، فلن يبحث javac إلا عن ملفات الفئات المجمّعة. بعبارة أخرى، لن يبحث javac عن ملفات المصدر في وحدات المنصة أو الوحدات على مسار الوحدات.

إذا لم يكن النوع المشار إليه موجودًا في وحدة أخرى قابلة للقراءة، فسيفحص javac الوحدة التي يتم تجميعها لمحاولة العثور على إعلان النوع. سيبحث javac عن إعلان النوع كما يلي:

•
ملفات المصدر المحددة على سطر الأوامر أو على مسار المصدر أو مسار مصدر الوحدات.
•
الملفات المجمّعة مسبقًا في دليل الإخراج.

التسلسلات الهرمية للدلائل

يفترض javac عادةً أن ملفات المصدر وملفات الفئات المترجمة سيتم تنظيمها في تسلسل هرمي لدلائل نظام الملفات أو في نوع من الملفات يدعم تسلسلاً هرمياً داخلياً للدلائل، مثل ملف JAR. يتم دعم ثلاثة أنواع مختلفة من التسلسلات الهرمية: تسلسل هرمي للحزم، وتسلسل هرمي للوحدات، وتسلسل هرمي لمصادر الوحدات.

بينما يكون javac متسامحاً إلى حد ما بشأن تنظيم الشيفرة المصدرية، بما يتجاوز التوقع بأن يتم تنظيم المصدر في تسلسل هرمي واحد أو أكثر للحزم، ويمكنه عموماً استيعاب التنظيمات التي تحددها بيئات التطوير وأدوات البناء، فإن أدوات Java بشكل عام، وjavac ومشغّل Java على وجه الخصوص، أكثر صرامة فيما يتعلق بتنظيم ملفات الفئات المترجمة، وسيتم تنظيمها في تسلسلات هرمية للحزم أو تسلسلات هرمية للوحدات، حسب الاقتضاء.

يتم تحديد موقع هذه التسلسلات الهرمية لـ javac باستخدام خيارات سطر الأوامر، التي تنتهي أسماؤها عادةً بـ "path"، مثل --source-path أو --class-path. وكقاعدة عامة أيضاً، تُستخدم خيارات المسار التي يتضمن اسمها كلمة module، مثل --module-path، لتحديد التسلسلات الهرمية للوحدات، على الرغم من أن بعض خيارات المسار المتعلقة بالوحدات تسمح بتحديد تسلسل هرمي للحزم على أساس كل وحدة على حدة. تُستخدم جميع خيارات المسار الأخرى لتحديد التسلسلات الهرمية للحزم.

التسلسل الهرمي للحزم

في التسلسل الهرمي للحزم، تُستخدم الدلائل والدلائل الفرعية لتمثيل الأجزاء المكوّنة لاسم الحزمة، حيث يتم تخزين ملف المصدر أو ملف الفئة المترجمة لنوع ما كملف بامتداد .java أو .class في الدليل الأكثر تداخلاً.

على سبيل المثال، في تسلسل هرمي للحزم، سيتم تخزين ملف المصدر لفئة com.example.MyClass في الملف com/example/MyClass.java

التسلسل الهرمي للوحدات

في التسلسل الهرمي للوحدات، يتم تسمية المستوى الأول من الدلائل بأسماء الوحدات في التسلسل الهرمي؛ وداخل كل من تلك الدلائل يتم تنظيم محتويات الوحدة في تسلسلات هرمية للحزم.

على سبيل المثال، في تسلسل هرمي للوحدات، سيتم تخزين ملف الفئة المترجمة لنوع يُسمى com.example.MyClass في وحدة تُسمى my.library في my.library/com/example/MyClass.class.

ستتم جميع دلائل الإخراج المختلفة التي يستخدمها javac (دليل إخراج الفئات، ودليل إخراج المصدر، ودليل إخراج الترويسات الأصلية) تنظيمها في تسلسل هرمي للوحدات عندما يتم تجميع وحدات متعددة.

التسلسل الهرمي لمصادر الوحدات

على الرغم من أنه ينبغي دائماً تنظيم المصدر لكل وحدة فردية في تسلسل هرمي للحزم، فقد يكون من الملائم تجميع تلك التسلسلات الهرمية في تسلسل هرمي لمصادر الوحدات. وهذا مشابه للتسلسل الهرمي للوحدات، باستثناء أنه قد تكون هناك دلائل وسيطة بين دليل الوحدة والدليل الذي يمثل جذر التسلسل الهرمي للحزم للشيفرة المصدرية للوحدة.

على سبيل المثال، في تسلسل هرمي لمصادر الوحدات، قد يتم تخزين ملف المصدر لنوع يُسمى com.example.MyClass في وحدة تُسمى my.library في ملف مثل my.library/src/main/java/com/example/MyClass.java.

خيار مسار مصدر الوحدة

للخيار --module-source-path صيغتان: صيغة خاصة بالوحدة، يُعطى فيها مسار حزمة لكل وحدة تحتوي على شيفرة يُراد ترجمتها، وصيغة نمط الوحدة، يُحدَّد فيها مسار المصدر لكل وحدة بواسطة نمط. تكون الصيغة الخاصة بالوحدة أبسط عادةً في الاستخدام عندما يكون عدد الوحدات المعنية صغيرًا؛ وقد تكون صيغة نمط الوحدة أكثر ملاءمة عندما يكون عدد الوحدات كبيرًا وتكون الوحدات منظمة بطريقة منتظمة يمكن وصفها بنمط.

يمكن إعطاء عدة نسخ من الخيار --module-source-path، كل واحدة منها تستخدم إما صيغة نمط الوحدة أو الصيغة الخاصة بالوحدة، مع مراعاة القيود التالية:

•
يمكن استخدام صيغة نمط الوحدة مرة واحدة على الأكثر
•
يمكن استخدام الصيغة الخاصة بالوحدة مرة واحدة على الأكثر لأي وحدة معينة

إذا استُخدمت الصيغة الخاصة بالوحدة لأي وحدة، فإن مسار البحث المرتبط بها يتجاوز أي مسار كان يمكن استنتاجه بخلاف ذلك من صيغة نمط الوحدة.

الصيغة الخاصة بالوحدة

تتيح الصيغة الخاصة بالوحدة إعطاء مسار بحث صريح لأي وحدة معينة. وهذه الصيغة هي:

•
--module-source-path module-name=file-path (path-separator file-path)*

محرف فاصل المسار هو ; على Windows، و: فيما عدا ذلك.

ملاحظة: هذا مشابه للصيغة المستخدمة للخيار --patch-module.

صيغة نمط الوحدة

تتيح صيغة نمط الوحدة تحديدًا موجزًا لمسار مصدر الوحدة لأي عدد من الوحدات المنظمة بطريقة منتظمة.

•
--module-source-path pattern

يُعرَّف النمط بالقواعد التالية، التي تُطبَّق بالترتيب:

•
تُعتبر الوسيطة سلسلة من المقاطع مفصولة بمحرف فاصل المسار (; على Windows، و: فيما عدا ذلك).
•
كل مقطع يحتوي على أقواس معقوفة من الشكل

string1{alt1 ( ,alt2 )* } string2

يُعتبر مستبدلًا بسلسلة من المقاطع المتكوّنة من "توسيع" الأقواس المعقوفة:


string1 alt1 string2
string1 alt2 string2
and so on...

يجوز أن تكون الأقواس المعقوفة متداخلة.

تُطبَّق هذه القاعدة على جميع حالات استخدام الأقواس المعقوفة هذه.

•
يجب أن يحتوي كل مقطع على نجمة واحدة (*) على الأكثر. إذا لم يحتوي المقطع على نجمة، فيُعتبر كما لو أُلحق به محرف فاصل الملفات ونجمة.

لأي وحدة M، يتكوّن مسار المصدر لتلك الوحدة من سلسلة المقاطع التي تُحصل عليها باستبدال اسم الوحدة M بالنجمة في كل مقطع.

ملاحظة: في هذا السياق، تُستخدم النجمة فقط كعلامة خاصة، للدلالة على موضع اسم الوحدة في المسار. ولا ينبغي الخلط بينها وبين استخدام * كمحرف بدل لأسماء الملفات، كما هو موجود في معظم أنظمة التشغيل.

ترقيع الوحدات

يسمح javac بأي محتوى، سواء كان في صورة مصدرية أو مترجمة، بأن يُرقَّع في أي وحدة باستخدام الخيار --patch-module. قد ترغب في فعل ذلك لترجمة تطبيقات بديلة لفئة ليتم ترقيعها وقت التشغيل في JVM، أو لحقن فئات إضافية في الوحدة، كما هو الحال عند الاختبار.

صيغة الخيار هي:

•
--patch-module module-name=file-path (path-separator file-path )*

حرف فاصل المسار هو ; على Windows، و: فيما عدا ذلك. يجب أن تحدد المسارات المعطاة للوحدة جذر تسلسل هرمي لحزمة لمحتويات الوحدة

يمكن إعطاء الخيار مرة واحدة على الأكثر لأي وحدة معينة. أي محتوى على المسار سيخفي أي محتوى مماثل الاسم لاحقًا في المسار وفي الوحدة المُرَقَّعة.

عند ترقيع الشيفرة المصدرية في أكثر من وحدة، يجب أيضًا استخدام --module-source-path، بحيث يتم تنظيم دليل الإخراج في تسلسل هرمي للوحدات، ويكون قادرًا على استيعاب ملفات الفئات المترجمة للوحدات التي تتم ترجمتها.

معالجة التعليقات التوضيحية

يوفر الأمر javac دعمًا مباشرًا لمعالجة التعليقات التوضيحية.

تُعرَّف واجهة برمجة التطبيقات لمعالجات التعليقات التوضيحية في حزمتي javax.annotation.processing و javax.lang.model والحزم الفرعية التابعة لهما.

كيفية عمل معالجة التعليقات التوضيحية

ما لم يتم تعطيل معالجة التعليقات التوضيحية باستخدام الخيار -proc:none، يبحث المترجم عن أي معالجات تعليقات توضيحية متاحة. يمكن تحديد مسار البحث باستخدام الخيار -processorpath. إذا لم يتم تحديد مسار، فسيتم استخدام مسار فئة المستخدم. يتم تحديد موقع المعالجات عن طريق ملفات تهيئة مزوّد الخدمة المسماة META-INF/services/javax.annotation.processing. المعالج على مسار البحث. يجب أن تحتوي هذه الملفات على أسماء أي معالجات تعليقات توضيحية سيتم استخدامها، مسرودةً واحدًا في كل سطر. بدلاً من ذلك، يمكن تحديد المعالجات صراحةً باستخدام الخيار -processor.

بعد فحص ملفات المصدر والفئات الموجودة على سطر الأوامر لتحديد التعليقات التوضيحية الموجودة، يستعلم المترجم من المعالجات لتحديد التعليقات التوضيحية التي تعالجها. عند العثور على تطابق، يتم استدعاء المعالج. يمكن للمعالج أن يطالب بالتعليقات التوضيحية التي يعالجها، وفي هذه الحالة لا تتم أي محاولة أخرى للعثور على أي معالجات لتلك التعليقات التوضيحية. بعد المطالبة بجميع التعليقات التوضيحية، لا يبحث المترجم عن معالجات إضافية.

إذا أنشأ أي معالج ملفات مصدر جديدة، فستحدث جولة أخرى من معالجة التعليقات التوضيحية: يتم فحص أي ملفات مصدر تم إنشاؤها حديثًا، وتتم معالجة التعليقات التوضيحية كما كان من قبل. يتم أيضًا استدعاء أي معالجات تم استدعاؤها في الجولات السابقة في جميع الجولات اللاحقة. يستمر هذا حتى لا يتم إنشاء أي ملفات مصدر جديدة.

بعد حدوث جولة لا يتم فيها إنشاء أي ملفات مصدر جديدة، يتم استدعاء معالجات التعليقات التوضيحية مرة أخيرة، لإعطائها فرصة لإكمال أي عمل متبقٍ. أخيرًا، ما لم يتم استخدام الخيار -proc:only، يقوم المترجم بتجميع ملفات المصدر الأصلية وجميع الملفات التي تم إنشاؤها.

إذا كنت تستخدم معالج تعليقات توضيحية ينشئ ملفات مصدر إضافية لتضمينها في التجميع، فيمكنك تحديد وحدة افتراضية لاستخدامها مع الملفات التي تم إنشاؤها حديثًا، لاستخدامها عندما لا يتم إنشاء إعلان وحدة أيضًا. في هذه الحالة، استخدم الخيار --default-module-for-created-files.

بيئة التجميع وبيئة التشغيل.

يتم تحليل الإعلانات في ملفات المصدر وملفات الفئات المترجمة مسبقًا بواسطة javac في بيئة تجميع متميزة عن بيئة التشغيل المستخدمة لتنفيذ javac نفسه. على الرغم من وجود تشابه متعمد بين العديد من خيارات javac والخيارات المسماة بالمثل الخاصة بـ مشغّل Java، مثل --class-path و --module-path وما إلى ذلك، فمن المهم فهم أنه بشكل عام تؤثر خيارات javac فقط على البيئة التي يتم فيها تجميع ملفات المصدر، ولا تؤثر على تشغيل javac نفسه.

التمييز بين بيئة التجميع وبيئة التشغيل مهم عند استخدام معالجات التعليقات التوضيحية. على الرغم من أن معالجات التعليقات التوضيحية تعالج العناصر (الإعلانات) الموجودة في بيئة التجميع، إلا أن معالج التعليقات التوضيحية نفسه يتم تنفيذه في بيئة التشغيل. إذا كان لمعالج التعليقات التوضيحية تبعيات على مكتبات غير موجودة في وحدات، فيمكن وضع المكتبات، جنبًا إلى جنب مع معالج التعليقات التوضيحية نفسه، على مسار المعالج. (انظر الخيار --processor-path.) إذا كان معالج التعليقات التوضيحية وتبعياته في وحدات، فيجب عليك استخدام مسار وحدة المعالج بدلاً من ذلك. (انظر الخيار --processor-module-path.) عندما تكون هذه غير كافية، قد يكون من الضروري توفير مزيد من التهيئة لبيئة التشغيل. يمكن القيام بذلك بطريقتين:

1.
إذا تم استدعاء javac من سطر الأوامر، فيمكن تمرير الخيارات إلى وقت التشغيل الأساسي عن طريق إضافة البادئة -J إلى الخيار.
2.
يمكنك بدء نسخة من Java Virtual Machine مباشرةً واستخدام خيارات سطر الأوامر وواجهة برمجة التطبيقات لتهيئة بيئة يمكن فيها استدعاء javac عبر إحدى واجهات برمجة التطبيقات الخاصة به.

الترجمة إلى إصدارات أقدم من المنصة

javac يمكنه ترجمة الشيفرة التي ستُستخدم على إصدارات أخرى من المنصة، باستخدام إما خيار --release، أو خياري --source/-source و --target/-target، إلى جانب خيارات إضافية لتحديد فئات المنصة.

اعتمادًا على إصدار المنصة المطلوب، توجد بعض القيود على بعض الخيارات التي يمكن استخدامها.

•
عند الترجمة إلى JDK 8 والإصدارات الأقدم، لا يمكنك استخدام أي خيار مخصص للاستخدام مع نظام الوحدات. يشمل ذلك جميع الخيارات التالية:
•
--module-source-path، --upgrade-module-path، --system، --module-path، --add-modules، --add-exports، --add-opens، --add-reads، --limit-modules، --patch-module

إذا استخدمت خياري --source/-source أو --target/-target، فيجب عليك أيضًا تعيين فئات المنصة المناسبة باستخدام عائلة خيارات مسار فئات التمهيد.

•
عند الترجمة إلى JDK 9 والإصدارات الأحدث، لا يمكنك استخدام أي خيار مخصص لتكوين مسار فئات التمهيد. يشمل ذلك جميع الخيارات التالية:
•
-Xbootclasspath/p:، -Xbootclasspath، -Xbootclasspath/a:، -endorseddirs، -Djava.endorsed.dirs، -extdirs، -Djava.ext.dirs، -profile

إذا استخدمت خياري --source/-source أو --target/-target، فيجب عليك أيضًا تعيين فئات المنصة المناسبة باستخدام خيار --system لتحديد موقع إصدار JDK مثبت ومناسب.

عند استخدام خيار --release، لا يجوز استخدام سوى واجهة برمجة التطبيقات الموثقة والمدعومة لذلك الإصدار؛ لا يمكنك استخدام أي خيارات لكسر التغليف للوصول إلى أي فئات داخلية.

واجهات برمجة التطبيقات

يمكن استدعاء مترجم javac باستخدام واجهة برمجة تطبيقات بثلاث طرق مختلفة:

واجهة برمجة تطبيقات مترجم Java
توفر هذه الطريقة الأكثر مرونة لاستدعاء المترجم، بما في ذلك القدرة على ترجمة ملفات المصدر المقدمة في مخازن مؤقتة في الذاكرة أو أنظمة ملفات أخرى غير قياسية.
واجهة برمجة تطبيقات ToolProvider
يمكن الحصول على ToolProvider الخاص بـ javac عن طريق استدعاء ToolProvider.findFirst("javac"). يُرجع هذا كائنًا له الوظائف المكافئة لأداة سطر الأوامر.

ملاحظة: لا ينبغي الخلط بين واجهة برمجة التطبيقات هذه وبين واجهة برمجة التطبيقات المشابهة في الاسم في حزمة javax.tools.

واجهة برمجة تطبيقات javac القديمة
يتم الاحتفاظ بواجهة برمجة التطبيقات هذه للتوافق مع الإصدارات السابقة فقط. يجب أن تستخدم جميع الشيفرات الجديدة إما واجهة برمجة تطبيقات مترجم Java أو واجهة برمجة تطبيقات ToolProvider.

ملاحظة: جميع الفئات والطرق الأخرى الموجودة في حزمة بأسماء تبدأ بـ com.sun.tools.javac (الحزم الفرعية لـ com.sun.tools.javac) هي داخلية بشكل صارم وقابلة للتغيير في أي وقت.

EXAMPLES OF USING -XLINT KEYS

cast
Warns about unnecessary and redundant casts, for example:

String s = (String) "Hello!"

classfile
Warns about issues related to class file contents.
deprecation
Warns about the use of deprecated items. For example:

java.util.Date myDate = new java.util.Date();
int currentDay = myDate.getDay();

The method java.util.Date.getDay has been deprecated since JDK 1.1.

dep-ann
Warns about items that are documented with the @deprecated Javadoc comment, but do not have the @Deprecated annotation, for example:

/**
  * @deprecated As of Java SE 7, replaced by {@link #newMethod()}
  */
public static void deprecatedMethod() { }
public static void newMethod() { }
divzero
Warns about division by the constant integer 0, for example:

int divideByZero = 42 / 0;

empty
Warns about empty statements after ifstatements, for example:

class E {
    void m() {
         if (true) ;
    }
}
fallthrough
Checks the switch blocks for fall-through cases and provides a warning message for any that are found. Fall-through cases are cases in a switch block, other than the last case in the block, whose code does not include a break statement, allowing code execution to fall through from that case to the next case. For example, the code following the case 1 label in this switch block does not end with a break statement:

switch (x) {
case 1:
  System.out.println("1");
  // No break statement here.
case 2:
  System.out.println("2");
}

If the -Xlint:fallthrough option was used when compiling this code, then the compiler emits a warning about possible fall-through into case, with the line number of the case in question.

finally
Warns about finally clauses that cannot be completed normally, for example:

public static int m() {
  try {
     throw new NullPointerException();
  }  catch (NullPointerException(); {
     System.err.println("Caught NullPointerException.");
     return 1;
   } finally {
     return 0;
   }
  }

The compiler generates a warning for the finally block in this example. When the int method is called, it returns a value of 0. A finally block executes when the try block exits. In this example, when control is transferred to the catch block, the int method exits. However, the finally block must execute, so it's executed, even though control was transferred outside the method.

options
Warns about issues that related to the use of command-line options. See Compiling for Earlier Releases of the Platform.
overrides
Warns about issues related to method overrides. For example, consider the following two classes:

public class ClassWithVarargsMethod {
  void varargsMethod(String... s) { }
}
public class ClassWithOverridingMethod extends ClassWithVarargsMethod {
   @Override
   void varargsMethod(String[] s) { }
}

The compiler generates a warning similar to the following:.


warning: [override] varargsMethod(String[]) in ClassWithOverridingMethod
overrides varargsMethod(String...) in ClassWithVarargsMethod; overriding
method is missing '...'

When the compiler encounters a varargs method, it translates the varargs formal parameter into an array. In the method ClassWithVarargsMethod.varargsMethod, the compiler translates the varargs formal parameter String... s to the formal parameter String[] s, an array that matches the formal parameter of the method ClassWithOverridingMethod.varargsMethod. Consequently, this example compiles.

path
Warns about invalid path elements and nonexistent path directories on the command line (with regard to the class path, the source path, and other paths). Such warnings cannot be suppressed with the @SuppressWarnings annotation. For example:
•
Linux and macOS: javac -Xlint:path -classpath /nonexistentpath Example.java
•
Windows: javac -Xlint:path -classpath C:\nonexistentpath Example.java
processing
Warns about issues related to annotation processing. The compiler generates this warning when you have a class that has an annotation, and you use an annotation processor that cannot handle that type of annotation. For example, the following is a simple annotation processor:

Source file AnnoProc.java:


import java.util.*;
import javax.annotation.processing.*;
import javax.lang.model.*;
import javax.lang.model.element.*;
@SupportedAnnotationTypes("NotAnno")
public class AnnoProc extends AbstractProcessor {
  public boolean process(Set<? extends TypeElement> elems, RoundEnvironment renv){
     return true;
  }
  public SourceVersion getSupportedSourceVersion() {
     return SourceVersion.latest();
   }
}

Source file AnnosWithoutProcessors.java:


@interface Anno { }
@Anno
class AnnosWithoutProcessors { }

The following commands compile the annotation processor AnnoProc, then run this annotation processor against the source file AnnosWithoutProcessors.java:


javac AnnoProc.java
javac -cp . -Xlint:processing -processor AnnoProc -proc:only AnnosWithoutProcessors.java

When the compiler runs the annotation processor against the source file AnnosWithoutProcessors.java, it generates the following warning:


warning: [processing] No processor claimed any of these annotations: Anno

To resolve this issue, you can rename the annotation defined and used in the class AnnosWithoutProcessors from Anno to NotAnno.

rawtypes
Warns about unchecked operations on raw types. The following statement generates a rawtypes warning:

void countElements(List l) { ... }

The following example does not generate a rawtypes warning:

void countElements(List<?> l) { ... }

List is a raw type. However, List<?> is an unbounded wildcard parameterized type. Because List is a parameterized interface, always specify its type argument. In this example, the List formal argument is specified with an unbounded wildcard (?) as its formal type parameter, which means that the countElements method can accept any instantiation of the List interface.

serial
Warns about missing serialVersionUID definitions on serializable classes. For example:

public class PersistentTime implements Serializable
{
  private Date time;
   public PersistentTime() {
     time = Calendar.getInstance().getTime();
   }
   public Date getTime() {
     return time;
   }
}

The compiler generates the following warning:


warning: [serial] serializable class PersistentTime has no definition of
serialVersionUID

If a serializable class does not explicitly declare a field named serialVersionUID, then the serialization runtime environment calculates a default serialVersionUID value for that class based on various aspects of the class, as described in the Java Object Serialization Specification. However, it's strongly recommended that all serializable classes explicitly declare serialVersionUID values because the default process of computing serialVersionUID values is highly sensitive to class details that can vary depending on compiler implementations. As a result, this might cause an unexpected InvalidClassExceptions during deserialization. To guarantee a consistent serialVersionUID value across different Java compiler implementations, a serializable class must declare an explicit serialVersionUID value.

static
Warns about issues relating to the use of static variables, for example:

class XLintStatic {
    static void m1() { }
    void m2() { this.m1(); }
}

The compiler generates the following warning:


warning: [static] static method should be qualified by type name,
XLintStatic, instead of by an expression

To resolve this issue, you can call the static method m1 as follows:

XLintStatic.m1();

Alternately, you can remove the static keyword from the declaration of the method m1.

try
Warns about issues relating to the use of try blocks, including try-with-resources statements. For example, a warning is generated for the following statement because the resource ac declared in the try block is not used:

try ( AutoCloseable ac = getResource() ) {    // do nothing}
unchecked
Gives more detail for unchecked conversion warnings that are mandated by the Java Language Specification, for example:

List l = new ArrayList<Number>();
List<String> ls = l;       // unchecked warning

During type erasure, the types ArrayList<Number> and List<String> become ArrayList and List, respectively.

The ls command has the parameterized type List<String>. When the List referenced by l is assigned to ls, the compiler generates an unchecked warning. At compile time, the compiler and JVM cannot determine whether l refers to a List<String> type. In this case, l does not refer to a List<String> type. As a result, heap pollution occurs.

A heap pollution situation occurs when the List object l, whose static type is List<Number>, is assigned to another List object, ls, that has a different static type, List<String>. However, the compiler still allows this assignment. It must allow this assignment to preserve backward compatibility with releases of Java SE that do not support generics. Because of type erasure, List<Number> and List<String> both become List. Consequently, the compiler allows the assignment of the object l, which has a raw type of List, to the object ls.

varargs
Warns about unsafe use of variable arguments (varargs) methods, in particular, those that contain non-reifiable arguments, for example:

public class ArrayBuilder {
  public static <T> void addToList (List<T> listArg, T... elements) {
    for (T x : elements) {
      listArg.add(x);
    }
  }
}

A non-reifiable type is a type whose type information is not fully available at runtime.

The compiler generates the following warning for the definition of the method ArrayBuilder.addToList:


warning: [varargs] Possible heap pollution from parameterized vararg type T

When the compiler encounters a varargs method, it translates the varargs formal parameter into an array. However, the Java programming language does not permit the creation of arrays of parameterized types. In the method ArrayBuilder.addToList, the compiler translates the varargs formal parameter T... elements to the formal parameter T[] elements, an array. However, because of type erasure, the compiler converts the varargs formal parameter to Object[] elements. Consequently, there's a possibility of heap pollution.
