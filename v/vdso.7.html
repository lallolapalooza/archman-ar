vDSO(7) Miscellaneous Information Manual vDSO(7)

الاسم

vdso — نظرة عامة على كائن المشاركة الديناميكي الافتراضي (virtual ELF dynamic shared object)

الملخص

#include <sys/auxv.h>
void *vdso = (uintptr_t) getauxval(AT_SYSINFO_EHDR);

الوصف

كائن المشاركة الديناميكي الافتراضي (vDSO) هو مكتبة مشاركة صغيرة يقوم النواة تلقائيًا بتعيينها (mapping) في مساحة عنوان جميع تطبيقات مساحة المستخدم (user-space). لا تحتاج التطبيقات عادةً إلى الاهتمام بهذه التفاصيل نظرًا لأن vDSO يتم استدعاؤه عادةً بواسطة مكتبة C. بهذه الطريقة، يمكنك البرمجة بالطريقة العادية باستخدام الدوال القياسية، وستتولى مكتبة C استخدام أي وظيفة متاحة عبر vDSO.

لماذا يوجد vDSO على الإطلاق؟ هناك بعض استدعاءات النظام (system calls) التي توفرها النواة والتي ينتهي الأمر بكود مساحة المستخدم لاستخدامها بشكل متكرر، إلى الحد الذي يمكن أن تهيمن فيه هذه الاستدعاءات على الأداء العام. ويرجع ذلك إلى تكرار الاستدعاء بالإضافة إلى الحمل الزائد لتبديل السياق (context-switch overhead) الذي ينتج عن الخروج من مساحة المستخدم والدخول إلى النواة.

بقية هذه الوثائق موجهة إلى الفضوليين و/أو كتاب مكتبات C بدلاً من المطورين العامين. إذا كنت تحاول استدعاء vDSO في تطبيقك الخاص بدلاً من استخدام مكتبة C، فمن المحتمل جدًا أنك تفعل ذلك بشكل خاطئ.

خلفية مثال

يمكن أن تكون استدعاءات النظام بطيئة. في أنظمة x86 32 بت، يمكنك تشغيل مقطع برمجي (interrupt) عبر البرمجيات (int $0x80) لإخبار النواة برغبتك في إجراء استدعاء نظام. ومع ذلك، فإن هذه التعليمات مكلفة: فهي تمر عبر مسارات معالجة المقاطع البرمجية الكاملة في الميكروكود الخاص بالمعالج وكذلك في النواة. تمتلك المعالجات الأحدث تعليمات أسرع (لكنها غير متوافقة مع الإصدارات السابقة) لبدء استدعاءات النظام. بدلاً من مطالبة مكتبة C بمعرفة ما إذا كانت هذه الوظيفة متاحة في وقت التشغيل، يمكن لمكتبة C استخدام الدوال التي توفرها النواة في vDSO.

لاحظ أن المصطلحات يمكن أن تكون مربكة. في أنظمة x86، تُسمى دالة vDSO المستخدمة لتحديد الطريقة المفضلة لإجراء استدعاء نظام بـ "__kernel_vsyscall"، ولكن في x86-64، يشير مصطلح "vsyscall" أيضًا إلى طريقة قديمة للسؤال عن النواة عن الوقت الحالي أو عن وحدة المعالجة المركزية (CPU) التي يوجد عليها المستدعي.

أحد استدعاءات النظام شائعة الاستخدام هو gettimeofday(2). يتم استدعاء استدعاء النظام هذا بشكل مباشر من قبل تطبيقات مساحة المستخدم وكذلك بشكل غير مباشر بواسطة مكتبة C. فكر في الطوابع الزمنية أو حلقات التوقيت أو الاستقصاء (polling) — كل هذه تحتاج بشكل متكرر إلى معرفة الوقت الحالي. هذه المعلومات ليست سرية أيضًا — أي تطبيق بأي وضع امتياز (root أو أي مستخدم غير مميز) سيحصل على نفس الإجابة. وبالتالي، ترتب النواة لوضع المعلومات المطلوبة للإجابة على هذا السؤال في الذاكرة التي يمكن للعملية الوصول إليها. الآن، يتغير استدعاء gettimeofday(2) من استدعاء نظام إلى استدعاء دالة عادي وبعض عمليات الوصول إلى الذاكرة.

العثور على vDSO

يتم تمرير عنوان الأساس لـ vDSO (إذا كان موجودًا) بواسطة النواة إلى كل برنامج في المتجه المساعد الأولي (initial auxiliary vector) (راجع getauxval(3))، عبر العلامة AT_SYSINFO_EHDR.

لا يجب أن تفترض أن vDSO معين في موقع معين في خريطة ذاكرة المستخدم. عادةً ما يتم عشوائيته (randomized) في وقت التشغيل في كل مرة يتم فيها إنشاء صورة عملية جديدة (في وقت execve(2)). يتم ذلك لأسباب أمنية، لمنع هجمات "العودة إلى libc".

بالنسبة لبعض معماريات الأجهزة، توجد أيضًا علامة AT_SYSINFO. تُستخدم هذه العلامة فقط لتحديد نقطة دخول vsyscall وغالبًا ما يتم حذفها أو تعيينها إلى 0 (مما يعني أنها غير متاحة). هذه العلامة هي تذكير بالعمل الأولي لـ vDSO (راجع التاريخ أدناه) ويجب تجنب استخدامها.

تنسيق الملف

نظرًا لأن vDSO هو صورة ELF مكتملة، يمكنك إجراء عمليات بحث عن الرموز (symbol lookups) عليه. هذا يسمح بإضافة رموز جديدة مع إصدارات أحدث للنواة، ويسمح لمكتبة C باكتشاف الوظائف المتاحة في وقت التشغيل عند التشغيل تحت إصدارات مختلفة من النواة. غالبًا ما تقوم مكتبة C بإجراء الكشف عند الاستدعاء الأول ثم تخزين النتيجة مؤقتًا للاستدعاءات اللاحقة.

جميع الرموز لها أيضًا إصدارات (باستخدام تنسيق إصدار GNU). هذا يسمح للنواة بتحديث توقيع الدالة دون كسر التوافق مع الإصدارات السابقة. وهذا يعني تغيير الوسائط التي تقبلها الدالة بالإضافة إلى القيمة المرجعة. وبالتالي، عند البحث عن رمز في vDSO، يجب عليك دائمًا تضمين الإصدار لمطابقة ABI الذي تتوقعه.

عادةً ما يتبع vDSO اصطلاح التسمية المتمثل في بادئة جميع الرموز بـ "__vdso_" أو "__kernel_" لتمييزها عن الرموز القياسية الأخرى. على سبيل المثال، تُسمى دالة "gettimeofday" "__vdso_gettimeofday".

تستخدم اصطلاحات الاستدعاء القياسية لمكتبة C عند استدعاء أي من هذه الدوال. لا داعي للقلق بشأن سلوك غريب للسجلات (registers) أو المكدس (stack).

المصدر

عند تجميع النواة، ستقوم تلقائيًا بتجميع وربط كود vDSO لك. غالبًا ما ستجده تحت الدليل الخاص بمعمارية الجهاز:


find arch/$ARCH/ -name '*vdso*.so*' -o -name '*gate*.so*'

strace(1)، seccomp(2)، و vDSO

عند تتبع استدعاءات النظام باستخدام strace(1)، فإن الرموز (استدعاءات النظام) التي تصدرها vDSO لن تظهر في مخرجات التتبع. وبالمثل، لن تكون استدعاءات النظام هذه مرئية لمرشحات seccomp(2).

ملاحظات خاصة بمعمارية الجهاز

تقدم الأقسام الفرعية أدناه ملاحظات خاصة بمعمارية الجهاز حول vDSO.

لاحظ أن vDSO المستخدم يعتمد على ABI الخاص بكود مساحة المستخدم وليس على ABI للنواة. وبالتالي، على سبيل المثال، عند تشغيل ثنائي i386 32 بت ELF، ستحصل على نفس vDSO بغض النظر عما إذا كنت تقوم بتشغيله تحت نواة i386 32 بت أو تحت نواة x86-64 64 بت. لذلك، يجب استخدام اسم ABI لمساحة المستخدم لتحديد أي من الأقسام أدناه هو ذو صلة.

vdso-functions

The Kernel Virtual Dynamic Shared Object (vDSO) provides a small shared library that the kernel can map into user-space processes. The purpose of the vDSO is to implement certain system calls in user space that can be satisfied without requiring a kernel mode transition.

This is achieved by placing the code for these system calls in a shared object that is mapped into the address space of every process. When a user-space process calls one of these functions, it executes the code in the vDSO rather than performing a traditional system call.

The vDSO is specifically designed for functions that are called frequently and can be implemented safely in user space with minimal kernel involvement. Common examples include functions for retrieving the current time or process ID.

The exact set of functions exported by the vDSO varies depending on the architecture and the kernel version. The following sections detail the functions available for specific architectures.

The vDSO is typically linked using the ELF dynamic linker and symbol resolution mechanisms. It also provides support for different versions of symbols, allowing for backward compatibility and gradual introduction of new features.

For detailed information on the kernel code page, it is recommended to refer to the kernel documentation, which is comprehensive and covers all necessary details: Documentation/arm/kernel_user_helpers.rst.

bfin (Blackfin) functions (port removed in Linux 4.17)

As this CPU lacks a memory management unit (MMU), it doesn't set up a vDSO in the normal sense. Instead, it maps at boot time a few raw functions into a fixed location in memory. User-space applications then call directly into that region. There is no provision for backward compatibility beyond sniffing raw opcodes, but as this is an embedded CPU, it can get away with things—some of the object formats it runs aren't even ELF based (they're bFLT/FLAT).

For information on this code page, it's best to refer to the public documentation:
http://docs.blackfin.uclinux.org/doku.php?id=linux-kernel:fixed-code

parisc (hppa) functions

The parisc port has a code page with utility functions called a gateway page. Rather than use the normal ELF auxiliary vector approach, it passes the address of the page to the process via the SR2 register. The permissions on the page are such that merely executing those addresses automatically executes with kernel privileges and not in user space. This is done to match the way HP-UX works.

Since it's just a raw page of code, there is no ELF information for doing symbol lookups or versioning. Simply call into the appropriate offset via the branch instruction, for example:


ble <offset>(%sr2, %r0)
offset function
00b0 lws_entry (CAS operations)
00e0 set_thread_pointer (used by glibc)
0100 linux_gateway_entry (syscall)
