req

This is the request from the client, which consists of the client‘s request line, the client‘s HTTP headers and the client‘s request body.

Some fields are read-only, some are writeable, and some can be unset. For fields that are writeable, this implies that they are also readable. For fields that are unsettable, this implies that they are also readable.

There is a subtle difference between the client request and the varnish request. The varnish request is stripped of the "per-hop" headers that are mandated by RFC 2616 Section 13.5.1. These headers are: Connection, Keep-Alive, Transfer-Encoding, and TE. They are stripped because varnish itself handles these concerns, and passing them along could confuse backends or intermediary proxies. These headers are also protected against modification in VCL.

For the most part, the above is true, but there are exceptions. The protection of the above headers is configurable on a per-varnishd instance. You can find the current settings in the VSL log, or by using the Varnish CLI command {@code vcl log}.

It is possible to modify the request in a way that is irrelevant to certain clients, and differences in the way the resource is presented don‘t change how the client will interpret it.

Use with caution.

req.http.*

Type: HEADER

Readable from: client

Writable from: client

Unsettable from: client

The headers of request, things like req.http.date.

The RFCs allow multiple headers with the same name, and both set and unset will remove all headers with the name given.

The header name * is a VCL symbol and as such cannot, for example, start with a numeral. To work with valid header that can‘t be represented as VCL symbols it is possible to quote the name, like req.http."grammatically.valid". None of the HTTP headers present in IANA registries need to be quoted, so the quoted syntax is discouraged but available for interoperability.

Some headers that cannot be tampered with for proper HTTP fetch or delivery are read-only.

bereq

This is the request we send to the backend, it is built from the clients req.* fields by filtering out "per-hop" fields which should not be passed along (Connection:, Range: and similar).

Slightly more fields are allowed through for pass` fetches than for `miss` fetches, for instance ``Range.

الاسم

varnishd - Varnish Cache.

الملخص

varnishd [-a [ip:]port] [-b ip:port] [-C] [-d] [-F] [-j chunk_size] [-L level] [-M ip:port] [-n name] [-N nuke] [-p param[=value]] [-P pidfile] [-r dir] [-S ip:port] [-T ip:port] [-V] [-w storage] [-x file] [varnishd_options]

الوصف

The varnishd command starts the Varnish Cache daemon. It is a high-performance HTTP accelerator.

The daemon can be configured by command line options or by installing VCL (Varnish Configuration Language) programs, which define how Varnish will handle HTTP requests and responses.

The varnishd daemon is typically started and stopped by the system's init scripts, which are configured to use a specific VCL program.

The following are the command line options:

-a [ip:]port
Specify the listening interface and port. This option can be specified multiple times to listen on multiple interfaces. If ip is omitted, Varnish will listen on all available network interfaces. If only port is given, Varnish will listen on all interfaces on that port. The default is to listen on port 8080 on all interfaces.
-b ip:port
Specify the backend server. This option can be specified multiple times to define multiple backends. If used, Varnish will ignore any backend definitions in the VCL program. The default is to use the backend defined in the VCL program.
-C
Print the VCL configuration in C code and exit.
-d
Enable debugging mode. This means that varnishd will not detach from the terminal, and will print much more information about what it is doing.
-F
Run in the foreground. This is useful for debugging and for running Varnish under tools like supervisord or systemd.
-j chunk_size
Set the chunk size for the shared memory log. The default is 80MB. This option must be specified before any other options that might require a shared memory log (like -F or -d).
-L level
Set the debug log level. The default is 1.
-M ip:port
Connect to the administration interface listening on the specified ip and port. This is useful for remote administration.
-n name
Specify the instance name. This is used to identify the Varnish instance in logs and statistics. If not specified, the default name is "default".
-N nuke
Attempt to nuke existing Varnish instances with the same name and storage definition.
-p param[=value]
Set a runtime parameter. Parameters can be set to their default values by simply specifying the parameter name. If a value is expected but not provided, the default value is used. For a list of available parameters and their default values, see the -P option.
-P pidfile
Write the process ID to the specified pidfile. This is useful for managing the Varnish process.
-r dir
Specify the directory for runtime data. This includes things like the shared memory log and the VCL compilation directory. If not specified, the default directory is /var/lib/varnish.
-S ip:port
Specify the listening interface and port for the administration CLI. This allows remote administration of Varnish.
-T ip:port
Specify the listening interface and port for the administration CLI. This is equivalent to the -S option.
-V
Print version information and exit.
-w storage
Specify the storage backend for caching. The storage can be a file path (e.g., -w /var/lib/varnish/varnish.cache) or a memory size (e.g., -w 128M). If a file path is specified, Varnish will create a file of the specified size for caching. If a memory size is specified, Varnish will allocate that amount of memory for caching. The default is to use malloc(256MB).
-x file
Load the VCL configuration from the specified file. If not specified, Varnish will look for a file named default.vcl in the VCL directory.
varnishd_options
Additional command line options for varnishd.

حقول الرأس المحمية

Headers content-length and transfer-encoding are read-only. They must be preserved to ensure HTTP/1 framing remains consistent and maintain a proper request and response synchronization with both clients and backends.

VMODs can still update these headers, when there is a reason to change the framing, such as a transformation of a request or response body.

حالة استجابة HTTP

A HTTP status code has 3 digits XYZ where X must be between 1 and 5 included. Since it is not uncommon to see HTTP clients or servers relying on non-standard or even invalid status codes, Varnish can work with any status between 100 and 999.

Within VCL code it is even possible to use status codes in the form VWXYZ as long as the overall value is lower than 65536, but only the XYZ part will be sent to the client, by which time the X must also have become non-zero.

The VWXYZ form of status codes can be communicate extra information in resp.status and beresp.status to return(synth(...)) and return(error(...)), to indicate which synthetic content to produce:

sub vcl_recv {
    if ([...]) {
        return synth(12404);
    }
}
sub vcl_synth {
    if (resp.status == 12404) {
        [...]       // this specific 404
    } else if (resp.status % 1000 == 404) {
        [...]       // all other 404's
    }
}

The obj.status variable will inherit the VWXYZ form, but in a ban expression only the XYZ part will be available. The VWXYZ form is strictly limited to VCL execution.

Assigning an HTTP standardized code to resp.status or beresp.status will also set resp.reason or beresp.reason to the corresponding status message.

معالجة 304

For a 304 response, Varnish core code amends beresp before calling vcl_backend_response:

  • If the gzip status changed, Content-Encoding is unset and any Etag is weakened
  • Any headers not present in the 304 response are copied from the existing cache object. Content-Length is copied if present in the existing cache object and discarded otherwise.
  • The status gets set to 200.

beresp.was_304 marks that this conditional response processing has happened.

Note: Backend conditional requests are independent of client conditional requests, so clients may receive 304 responses no matter if a backend request was conditional.

beresp.ttl / beresp.grace / beresp.keep

Before calling vcl_backend_response, core code sets beresp.ttl based on the response status and the response headers Age, Cache-Control or Expires and Date as follows:

  • If present and valid, the value of the Age header is effectively deduced from all ttl calculations.
  • For status codes 200, 203, 204, 300, 301, 304, 404, 410 and 414:
  • If Cache-Control contains an s-maxage or max-age field (in that order of preference), the ttl is set to the respective non-negative value or 0 if negative.
  • Otherwise, if no Expires header exists, the default ttl is used.
  • Otherwise, if Expires contains a time stamp before Date, the ttl is set to 0.
  • Otherwise, if no Date header is present or the Date header timestamp differs from the local clock by no more than the clock_skew parameter, the ttl is set to
  • 0 if Expires denotes a past timestamp or
  • the difference between the local clock and the Expires header otherwise.
•
Otherwise, the ttl is set to the difference between Expires and Date
  • For status codes 302 and 307, the calculation is identical except that the default ttl is not used and -1 is returned if neither Cache-Control nor Expires exists.
  • For all other status codes, ttl -1 is returned.

beresp.grace defaults to the default_grace parameter.

For a non-negative ttl, if Cache-Control contains a stale-while-revalidate field value, beresp.grace is set to that value if non-negative or 0 otherwise.

beresp.keep defaults to the default_keep parameter.
