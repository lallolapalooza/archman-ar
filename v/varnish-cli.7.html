الاسم

varnish-cli - واجهة سطر أوامر Varnish

الوصف

لدى Varnish واجهة سطر أوامر (CLI) يمكنها التحكم في معظم معلمات التشغيل وتكوين Varnish وتغييرها، دون مقاطعة الخدمة قيد التشغيل.

يمكن استخدام واجهة سطر الأوامر للمهام التالية:

التكوين
يمكنك تحميل وتغيير وحذف ملفات VCL من واجهة سطر الأوامر.
المعلمات
يمكنك فحص وتغيير المعلمات المختلفة التي يوفرها Varnish عبر واجهة سطر الأوامر. يتم توثيق المعلمات الفردية في صفحة الدليل varnishd(1).
الحظر
الحظر هو عوامل تصفية يتم تطبيقها لمنع Varnish من تقديم محتوى قديم. عند إصدار حظر، لن يقدم Varnish أي كائن "محظور" من ذاكرة التخزين المؤقت، بل سيعيد جلبه من خوادم الواجهة الخلفية الخاصة به.
إدارة العمليات
يمكنك إيقاف وبدء عملية ذاكرة التخزين المؤقت (الابن) عبر واجهة سطر الأوامر. يمكنك أيضًا استرداد آخر تتبع للمكدس إذا تعطلت عملية الابن.

إذا قمت بتشغيل varnishd(1) مع -T أو -M أو -d، ستكون واجهة سطر الأوامر متاحة. في وضع التصحيح (-d) ستكون واجهة سطر الأوامر في المقدمة، ومع -T يمكنك الاتصال بها باستخدام varnishadm أو telnet، ومع -M سيتصل varnishd بخدمة استماع *تدفع* واجهة سطر الأوامر إلى تلك الخدمة. يرجى الاطلاع على varnishd(1) للحصول على التفاصيل.

الصياغة

واجهة سطر أوامر Varnish تشبه واجهة سطر أوامر أخرى، وهي Bourne Shell. عادةً ما تنتهي الأوامر بسطر جديد، وقد تأخذ وسيطات. يتم *تقسيم* الأمر ووسيطاته إلى رموز قبل التحليل، وبالتالي يجب أن تكون الوسيطات التي تحتوي على مسافات محاطة بعلامات اقتباس مزدوجة.

هذا يعني أن تحليل الأوامر

help banner

يعادل

"help" banner

لأن علامات الاقتباس المزدوجة تشير فقط إلى حدود الرمز help.

داخل علامات الاقتباس المزدوجة، يمكنك استبعاد الأحرف باستخدام \ (الشرطة المائلة للخلف). يتم ترجمة \n و \r و \t إلى أسطر جديدة وعمليات إرجاع علامات جدولة. يمكن استبعاد علامات الاقتباس المزدوجة والشرطات المائلة للخلف نفسها باستخدام \" و \\ على التوالي.

لإدخال الأحرف بالأرقام الثمانية استخدم الصيغة \nnn. يمكن إدخال الأرقام الستة عشرية باستخدام الصيغة \xnn.

قد لا تنتهي الأوامر بسطر جديد عند استخدام *مستند نصي هنا* (here document أو heredoc) على غرار shell. تنسيق المستند النصي هنا هو:

<< word
     here document
word

word يمكن أن يكون أي سلسلة متصلة مختارة لضمان عدم ظهورها بشكل طبيعي في *المستند النصي هنا* التالي. تقليديًا يتم استخدام EOF أو END.

مزالق علامات الاقتباس

قد يكون دمج واجهة سطر أوامر Varnish مفاجئًا في بعض الأحيان عندما يتعلق الأمر بعلامات الاقتباس. على سبيل المثال، في Bourne Shell، قد يكون الفاصل المستخدم مع مستندات النص هنا مفصولًا بمسافات عن الرمز << أو قد لا يكون:

cat <<EOF
hello
world
EOF
hello
world

مع واجهة سطر أوامر Varnish، يجب أن يكون الرمزان << و EOF مفصولين بمسافة واحدة على الأقل:

vcl.inline boot <<EOF
106 258
Message from VCC-compiler:
VCL version declaration missing
Update your VCL to Version 4 syntax, and add
        vcl 4.0;
on the first line of the VCL files.
('<vcl.inline>' Line 1 Pos 1)
<<EOF
##---
Running VCC-compiler failed, exited with 2
VCL compilation failed

مع غياب المسافة، يمكن إضافة مستند النص هنا ويمكن تحميل VCL الفعلي:

vcl.inline test << EOF
vcl 4.0;
backend be {
        .host = "localhost";
}
EOF
200 14
VCL compiled.

فرق كبير عن مستند النص هنا shell هو معالجة الرمز <<. تمامًا مثل أسماء الأوامر التي يمكن اقتباسها، يحتفظ رمز المستند النصي هنا بمعناه، حتى لو تم اقتباسه:

vcl.inline test "<<" EOF
vcl 4.0;
backend be {
        .host = "localhost";
}
EOF
200 14
VCL compiled.

عند استخدام واجهة أمامية لواجهة سطر أوامر Varnish مثل varnishadm، يجب أخذ التوسع المزدوج الذي يحدث في الاعتبار. أولاً في shell الذي يشغل الأمر varnishadm ثم في واجهة سطر أوامر Varnish نفسها. عندما تتطلب وسيطة الأمر مسافات، تحتاج إلى التأكد من أن واجهة سطر أوامر Varnish ترى علامات الاقتباس المزدوجة:

varnishadm param.set cc_command '"my alternate cc command"'
Change will take effect when VCL script is reloaded

خلاف ذلك، إذا لم تقم باقتباس علامات الاقتباس، فقد تحصل على رسالة خطأ تبدو غير مرتبطة:

varnishadm param.set cc_command "my alternate cc command"
Unknown request.
Type 'help' for more info.
Too many parameters
Command failed with error code 105

إذا كنت تستخدم علامات الاقتباس مع مستند نصي هنا، فيجب عليك لفه داخل وسيطة shell متعددة الأسطر:

varnishadm vcl.inline test '<< EOF
vcl 4.0;
backend be {
        .host = "localhost";
}
EOF'
VCL compiled.

فرق آخر عن مستند نصي هنا shell هو أنه يمكن استخدام مستند نصي هنا واحد فقط في كل سطر أمر. على سبيل المثال، من الممكن القيام بذلك في نص shell:

#!/bin/sh
cat << EOF1 ; cat << EOF2
hello
EOF1
world
EOF2

سيكون الإخراج المتوقع:

hello
world

مع واجهة سطر أوامر Varnish، يمكن فقط للوسيطة الأخيرة استخدام شكل المستند النصي هنا، مما يقيد بشكل كبير عدد الأوامر التي يمكنها استخدامها بفعالية. محاولة استخدام مستندات نصية متعددة هنا يأخذ فقط الأخير في الاعتبار.

على سبيل المثال:

command argument << EOF1 << EOF2
heredoc1
EOF1
heredoc2
EOF2

ينتج هذا بشكل مفاهيمي عن سطر الأوامر التالي:

  • "command"
  • "argument"
  • "<<"
  • "EOF1"
  • "heredoc1\nEOF1\nheredoc2\n"

تشمل الزلات الأخرى التوسع المتغير لـ shell الذي يستدعي varnishadm ولكن هذا ليس متعلقًا مباشرة بواجهة سطر أوامر Varnish. إذا حصلت على علامات الاقتباس بشكل صحيح، فيجب أن تكون بخير حتى مع الأوامر المعقدة.

JSON

تدعم العديد من الأوامر ذات الاستجابات المعلوماتية وسيطة -j للإخراج بتنسيق JSON، كما هو موضح أدناه. الهيكل العلوي لاستجابة JSON هو مصفوفة تحتوي على هذه العناصر الثلاثة الأولى:

  • رقم إصدار تنسيق JSON (عدد صحيح)
  • مصفوفة من السلاسل التي تشكل أمر واجهة سطر الأوامر الذي تم استلامه للتو
  • الوقت الذي تم فيه إنشاء الاستجابة، كوقت حقبة Unix بالثواني مع دقة المللي ثانية (عدد عشري)

تشكل العناصر المتبقية من المصفوفة البيانات الخاصة بأمر واجهة سطر الأوامر، ويعتمد هيكلها ومحتواها على الأمر.

على سبيل المثال، تحتوي استجابة status -j فقط على سلسلة في المصفوفة العلوية تشير إلى حالة عملية الابن ("running"، "stopped" وما إلى ذلك):

[ 2, ["status", "-j"], 1538031732.632, "running"
]

قد تحتوي استجابات JSON لأوامر أخرى على قوائم أطول من العناصر، والتي قد تحتوي على أنواع بيانات بسيطة أو تشكل كائنات منظمة.

يتم إرجاع إخراج JSON فقط إذا نجح تنفيذ الأمر. يكون الإخراج للاستجابة الخطأ دائمًا هو نفسه كما لو كان الأمر بدون معلمة -j.

الأوامر

auth <response>

المصادقة.

backend.list [-j] [-p] [<backend_pattern>]

قائمة الواجهات الخلفية.

-p يعرض أيضًا حالة التحقق.

-j تحدد إخراج JSON.

ما لم يتم تحديد -j لإخراج JSON، فإن تنسيق الإخراج هو خمسة أعمدة بعرض ديناميكي، مفصولة بمسافات بيضاء مع الحقول:

  • اسم الواجهة الخلفية
  • مسؤول: كيف يتم تحديد حالة الصحة:
  • healthy: تم تعيين healthy من خلال backend.set_health.
  • sick: تم تعيين sick من خلال backend.set_health.
  • probe: يتم تحديد حالة الصحة بواسطة فحص أو آلية ديناميكية أخرى.
  • deleted: تم حذف الواجهة الخلفية، ولكن لم يتم تنظيفها بعد.

المسؤول له الأسبقية على الصحة

  • فحص X/Y: تم نجاح X من أصل Y فحوصات

    X و Y خاصان بالواجهة الخلفية وقد يمثلان فحوصات، أو واجهات خلفية أخرى، أو أي مقياس آخر.

    إذا لم يكن هناك فحص أو لم يوفر المخرج تفاصيل حول نتائج فحص، يتم إخراج 0/0.

  • الصحة: حالة صحة الفحص
  • healthy
  • sick

إذا لم يكن هناك فحص، يتم إخراج healthy.

•
آخر تغيير: طابع زمني لتغيير حالة الصحة آخر مرة.

حالة الصحة المبلغ عنها هنا عامة. قد تعتمد صحة الواجهة الخلفية أيضًا على السياق الذي يتم استخدامه فيه (على سبيل المثال، تجزئة الكائن)، لذلك قد تختلف حالة الصحة الفعلية كما هي مرئية من VCL (على سبيل المثال، باستخدام std.healthy()).

بالنسبة لـ -j، يجب أن تكون عناصر الكائن واضحة بذاتها، وتتوافق مع الحقول الموضحة أعلاه. probe_message له التنسيق [X, Y, "state"] كما هو موضح أعلاه للفحص. تفاصيل فحص JSON (وسيطات -j -p) خاصة بالمخرج.

backend.set_health <backend_pattern> [auto|healthy|sick]

تعيين حالة صحة الواجهة الخلفية (الواجهات الخلفية) المطابقة لـ <backend_pattern>.
  • مع auto، يتم تحديد حالة الصحة بواسطة فحص أو آلية ديناميكية أخرى، إن وجدت.
  • healthy تعيين الواجهة الخلفية كقابلة للاستخدام.
  • sick تعيين الواجهة الخلفية كغير قابلة للاستخدام.

ban <field> <operator> <arg> [&& <field> <oper> <arg> ...]

وضع علامة على جميع الكائنات التي تتطابق معها جميع الشروط على أنها مهملة.

انظر std.ban() للحصول على التفاصيل.

ban.list [-j]

قائمة الحظر النشط.

ما لم يتم تحديد -j لإخراج JSON، فإن تنسيق الإخراج هو:

  • الكائنات التي تشير إلى هذا الحظر.
  • C إذا اكتمل الحظر = لا مزيد من الاختبارات ضده.
  • إذا كان تصحيح الأخطاء lurker ممكّنًا:

NAME

varnish-cli - varnish command line interface

SYNOPSIS

varnishadm vcl {inline|load|list|show|state|symtab|use} ...
varnishadm backend {list|purge|set_health} ...
varnishadm ban {list|expire|url|req|obj} ...
varnishadm help [...]

DESCRIPTION

The varnishadm command line interface allows users to query and control a running Varnish cache.

VCL

vcl.inline <configname>

Load VCL configuration from standard input.

Multi-line VCL can be input using the here document ref_syntax.

vcl.label <label> <configname>

Apply label to configuration.

A VCL label is like a UNIX symbolic link, a name without substance, which points to another VCL.

Labels are mandatory whenever one VCL references another.

vcl.list [-j]

List all loaded configuration.

Unless -j is specified for JSON output, the output format is five or seven columns of dynamic width, separated by white space with the fields:

  • status: active, available or discarded
  • state: label, cold, warm, or auto
  • temperature: init, cold, warm, busy or cooling
  • busy: number of references to this vcl (integer)
  • name: the name given to this vcl or label
  • [ <- | -> ] and label info last two fields)
  • -> <vcl> : label "points to" the named <vcl>
  • <- (<n> label[s]): the vcl has <n> label(s)

vcl.load <configname> <filename> [auto|cold|warm]

Compile and load the VCL file under the name provided.

vcl.show [-v] [<configname>]

Display the source code for the specified configuration.

vcl.state <configname> auto|cold|warm

Force the state of the named configuration.

vcl.symtab

Dump the VCL symbol-tables.

vcl.use <configname|label>

Switch to the named configuration immediately.

Backend Pattern

A backend pattern can be a backend name or a combination of a VCL name and backend name in "VCL.backend" format. If the VCL name is omitted, the active VCL is assumed. Partial matching on the backend and VCL names is supported using shell-style wildcards, e.g. asterisk (*).

Examples:

backend.list def*
backend.list b*.def*
backend.set_health default sick
backend.set_health def* healthy
backend.set_health * auto

Ban Expressions

A ban expression consists of one or more conditions. A condition consists of a field, an operator, and an argument. Conditions can be ANDed together with "&&".

A field can be any of the variables from VCL, for instance req.url, req.http.host or obj.http.set-cookie.

Operators are "==" for direct comparison, "~" for a regular expression match, and ">" or "<" for size comparisons. Prepending an operator with "!" negates the expression.

The argument could be a quoted string, a regexp, or an integer. Integers can have "KB", "MB", "GB" or "TB" appended for size related fields.

VCL Temperature

A VCL program goes through several states related to the different commands: it can be loaded, used, and later discarded. You can load several VCL programs and switch at any time from one to another. There is only one active VCL, but the previous active VCL will be maintained active until all its transactions are over.

Over time, if you often refresh your VCL and keep the previous versions around, resource consumption will increase, you can't escape that. However, most of the time you want to pay the price only for the active VCL and keep older VCLs in case you'd need to rollback to a previous version.

The VCL temperature allows you to minimize the footprint of inactive VCLs. Once a VCL becomes cold, Varnish will release all the resources that can be be later reacquired. You can manually set the temperature of a VCL or let varnish automatically handle it.

EXAMPLES

Load a multi-line VCL using shell-style here document:

vcl.inline example << EOF
vcl 4.0;
backend www {
    .host = "127.0.0.1";
    .port = "8080";
}
EOF

Ban all requests where req.url exactly matches the string /news:

ban req.url == "/news"

Ban all documents where the serving host is "example.com" or "www.example.com", and where the Set-Cookie header received from the backend contains "USERID=1663":

ban req.http.host ~ "^(?i)(www\\.)?example\\.com$" && obj.http.set-cookie ~ "USERID=1663"
