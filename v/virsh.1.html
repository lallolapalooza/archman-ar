الوصف

البرنامج virsh هو الواجهة الرئيسية لإدارة نطاقات الضيوف (guest domains) في virsh. يمكن استخدام البرنامج لإنشاء وإيقاف مؤقت وإيقاف تشغيل النطاقات. يمكن استخدامه أيضًا لسرد النطاقات الحالية. Libvirt هي مجموعة أدوات C للتفاعل مع إمكانيات المحاكاة الافتراضية للإصدارات الحديثة من Linux (وأنظمة التشغيل الأخرى). إنها برامج مجانية متاحة بموجب ترخيص GNU Lesser General Public License. تعني المحاكاة الافتراضية لنظام التشغيل Linux القدرة على تشغيل مثيلات متعددة لأنظمة التشغيل بشكل متزامن على نظام أجهزة واحد حيث يتم تشغيل الموارد الأساسية بواسطة مثيل Linux. تهدف المكتبة إلى توفير واجهة برمجة تطبيقات C مستقرة طويلة الأجل. وهي تدعم حاليًا Xen و QEMU و KVM و LXC و OpenVZ و VirtualBox و VMware ESX.

الهيكل الأساسي لمعظم استخدامات virsh هو:

virsh [خيار]... <أمر> <نطاق> [وسيط]...

حيث الأمر هو أحد الأوامر المدرجة أدناه؛ النطاق هو معرف النطاق الرقمي، أو اسم النطاق، أو معرف UUID للنطاق؛ و الوسائط هي خيارات خاصة بالأمر. هناك بعض الاستثناءات لهذه القاعدة في الحالات التي يعمل فيها الأمر المعني على جميع النطاقات، أو الجهاز بأكمله، أو مباشرة على برنامج hypervisor الخاص بـ xen. ستكون هذه الاستثناءات واضحة لكل من هذه الأوامر. ملاحظة: يُسمح بتعيين أسماء رقمية للنطاقات، ومع ذلك، فإن القيام بذلك سيؤدي إلى نطاق يمكن تحديده فقط بواسطة معرف النطاق. بعبارة أخرى، إذا تم توفير قيمة رقمية، فسيتم تفسيرها كمعرف نطاق، وليس كاسم. أي أمر يبدأ بـ # يُعامل كتعليق ويتم تجاهله بصمت، ويتم تشخيص جميع الأوامر الأخرى غير المعروفة.

يفهم البرنامج virsh إما لتشغيل أمر واحد عن طريق إعطاء الأمر ووسائطه في سطر أوامر shell، أو سلسلة_أوامر وهي وسيط shell واحد يتكون من عدة إجراءات أمر ووسائطها مرتبطة بمسافات بيضاء مفصولة بفواصل منقوطة أو أسطر جديدة بين الأوامر، حيث يتم حذف أزواج backslash-newline غير المقتبسة. داخل سلسلة_أوامر، يفهم virsh نفس تسلسلات الهروب الأحادية والمزدوجة وتسلسلات الهروب بالشرطة المائلة العكسية مثل shell، على الرغم من أنه يجب عليك إضافة طبقة أخرى من الهروب من shell عند إنشاء وسيط shell الواحد، وأي كلمة تبدأ بـ # غير مقتبسة تبدأ تعليقًا ينتهي عند السطر الجديد. إذا لم يتم تقديم أي أمر في سطر الأوامر، فسيقوم virsh ببدء مترجم الحد الأدنى الذي ينتظر أوامرك، وسيقوم الأمر quit بعد ذلك بإنهاء البرنامج.

يفهم البرنامج virsh الخيارات التالية.

-c, --connect URI

الاتصال بـ URI المحدد، كما لو كان بواسطة الأمر connect، بدلاً من الاتصال الافتراضي.

-d, --debug LEVEL

تمكين رسائل التصحيح عند المستوى الصحيح LEVEL وما فوق. يمكن أن يتراوح LEVEL من 0 إلى 4 (الافتراضي). انظر وثائق متغير البيئة VIRSH_DEBUG أدناه لوصف كل LEVEL.

•
-e, --escape string

تعيين تسلسل هروب بديل لأمر console. افتراضيًا، يتم استخدام ^] الخاص بـ telnet. الأحرف المسموح بها عند استخدام ترميز القبعة هي: حرف أبجدي، @، [، ]، ، ^، _.

•
-h, --help

تجاهل جميع الوسائط الأخرى، وتصرف كما لو تم تقديم الأمر help بدلاً من ذلك.

•
-k, --keepalive-interval INTERVAL

تعيين INTERVAL (بالثواني) لإرسال رسائل keepalive للتحقق مما إذا كان الاتصال بالخادم لا يزال حيًا. يؤدي تعيين الفاصل الزمني إلى 0 إلى تعطيل آلية keepalive الخاصة بالعميل.

•
-K, --keepalive-count COUNT

تعيين عدد المرات التي يمكن فيها إرسال رسالة keepalive دون تلقي رد من الخادم دون وضع علامة على الاتصال على أنه ميت. لا يوجد تأثير لهذا الإعداد في حالة تعيين INTERVAL على 0.

•
-l, --log FILE

تفاصيل تسجيل الإخراج إلى FILE.

•
-q, --quiet

تجنب رسائل المعلومات الإضافية.

•
-r, --readonly

اجعل الاتصال الأولي للقراءة فقط، كما لو كان بواسطة الخيار --readonly للأمر connect.

•
-t, --timing

عرض معلومات الوقت المنقضي لكل أمر.

•
--no-pkttyagent

لا تقم بتسجيل pkttyagent كوكيل مصادقة مع خدمة نظام polkit، حتى لو تم بدء virsh من طرفية.

•
-v, --version[=short]

تجاهل جميع الوسائط الأخرى، واطبع إصدار مكتبة libvirt التي يأتي منها virsh

•
-V, --version=long

تجاهل جميع الوسائط الأخرى، واطبع إصدار مكتبة libvirt التي يأتي منها virsh والخيارات وبرامج التشغيل التي تم تجميعها.

ملاحظات

تعتمد معظم عمليات virsh على قدرة مكتبة libvirt على الاتصال بخدمة libvirtd قيد التشغيل بالفعل. يمكن القيام بذلك عادةً باستخدام الأمر service libvirtd start.

تتطلب معظم أوامر virsh امتيازات الجذر للتشغيل بسبب قنوات الاتصال المستخدمة للتحدث إلى hypervisor. سيؤدي التشغيل كـ non root إلى إرجاع خطأ.

تعمل معظم أوامر virsh بشكل متزامن، باستثناء ربما shutdown و setvcpus و setmem. في هذه الحالات، حقيقة أن برنامج virsh قد عاد، قد لا يعني أن الإجراء قد اكتمل ويجب عليك الاستقصاء بشكل دوري لاكتشاف أن الضيف أكمل العملية.

يسعى virsh جاهدًا لتحقيق التوافق الخلفي. على الرغم من أن الأمر help يسرد فقط الاستخدام المفضل لأمر ما، إذا دعمت نسخة أقدم من virsh تهجئة بديلة لأمر أو خيار (مثل --tunnelled بدلاً من --tunneled)، فستستمر البرامج النصية التي تستخدم هذه التهجئة الأقدم في العمل.

تأخذ العديد من أوامر virsh عددًا صحيحًا مُقاسًا اختياريًا؛ إذا لم يتم توفير مقياس، فسيتم سرد الافتراضي في الأمر (لأسباب تاريخية، تفترض بعض الأوامر وحدات البايت، بينما تفترض الأوامر الأخرى الكيبيبايت). يمكن استخدام اللاحقات التالية غير الحساسة لحالة الأحرف لتحديد مقياس معين:

free-memory

Syntax:

free-memory [--all | --cellno cellno | --pagepagesize pagesize] [--pagesize pagesize]

Displays the total free memory on the machine. If the option --all is specified, it displays the free memory in each cell and the total free memory on the machine. If the option --cellno is specified along with a cell number, it displays the free memory for the specified cell only. If the option --pagesize is specified along with a page size, it displays the free memory for the specified page size only.

hypervisor-cpu-compare

Syntax:

hypervisor-cpu-compare [--virttype virttype] [--emulator emulator]
   [--arch arch] [--machine machine] [--all] model1 model2 ...

Compare the given CPU models (model1, model2, ...) against each other. The output indicates for each pair of models whether one is a superset of the other, or if they are incompatible.

The virttype option specifies the virtualization type (usable in the 'type' attribute of the <domain> top level element from the domain XML). emulator specifies the path to the emulator, arch specifies the CPU architecture, and machine specifies the machine type.

By default, this command compares the models based on the set of features supported by the host hypervisor. The option --all will compare the models based on the full set of CPU features known by the hypervisor, regardless of host capabilities.

This command is useful for determining the compatibility of CPU models between different hosts, or between a host and a guest. If model A is a superset of model B, it means that any guest configured with model B can also run on a host configured with model A. However, a guest configured with model A may not run on a host configured with model B if model A includes features not present in model B.

Two models are considered incompatible if neither is a superset of the other. This typically occurs when they support different sets of CPU features.

The output format is designed to be easily parseable by scripts. Each line of output represents a comparison between two CPU models. The line will contain the names of the two models being compared, followed by a description of their relationship (e.g., "is superset of", "is subset of", "is incompatible with").

Example: 

virsh hypervisor-cpu-compare --arch x86_64 Haswell SandyBridge
This command would compare the Haswell and SandyBridge CPU models for the x86_64 architecture and report their compatibility.

The results can be used to select the most appropriate CPU model for a virtual machine, balancing compatibility with feature availability. For instance, choosing a CPU model that is a superset of the host's baseline CPU can provide better performance and access to more features, but risks reducing portability to older or less capable hosts. Conversely, sticking to the host's baseline or a model known to be a subset of many others ensures maximum guest portability.

Note that the hypervisor may have specific requirements or recommendations for certain architectures or machine types. It is always a good idea to consult the hypervisor's documentation for the most accurate information regarding CPU model compatibility.

The command output does not directly list the features that make one model a superset or subset of another. For detailed feature comparison, one might need to use other tools or inspect the XML definitions of the CPU models, if available. However, the superset/subset/incompatible relationship provides a sufficient level of abstraction for most use cases related to guest CPU configuration and migration.

Consider the case where you want to migrate a virtual machine from host A to host B. If you configured the VM with CPU model X, you should ensure that host B's hypervisor also supports model X, or a model Y that is a superset of X. If you simply query the baseline CPU of host A and host B, and they are different, it doesn't automatically mean migration will fail. The critical factor is the CPU model *as configured for the VM* and the CPU models supported by the *target hypervisor*. The hypervisor-cpu-compare command helps in navigating these relationships.

The `--all` flag is particularly useful when you want to understand the full range of CPU models the hypervisor knows about, irrespective of what the current host machine can actually run. This can be helpful for planning deployments on potentially diverse hardware, or for testing the behavior of guests with advanced CPU features that might not be available on the local system.

The command assumes that the specified CPU models are valid names recognized by the hypervisor for the given architecture. If an invalid CPU model name is provided, the hypervisor may return an error or the comparison may yield unexpected results.

It's important to remember that CPU compatibility is just one aspect of VM migration and compatibility. Other factors like available memory, devices, and specific hypervisor features also play a role. However, CPU model compatibility is often a primary concern.

In summary, hypervisor-cpu-compare is a powerful tool for understanding and managing CPU model compatibility within a virtualization environment, helping to ensure smooth operation and migration of virtual machines.

The hypervisor acts as the backend, providing the definitions and capabilities of various CPU models. Libvirt, through the `virsh` command, exposes these capabilities in a structured and usable format. The commands like `hypervisor-cpu-baseline` and `hypervisor-cpu-compare` are essentially front-ends to the underlying hypervisor's CPU feature reporting mechanisms.

When using `hypervisor-cpu-compare`, the output indicating that model A "is superset of" model B means that model A has all the features of model B, and possibly more. This implies that a guest configured with model B can run on a hypervisor exposing model A. If model A "is subset of" model B, then model B has all features of A plus potentially more. If they "are incompatible", it means they have overlapping but distinct feature sets, and a guest configured for one might not run correctly on a hypervisor exposing the other.

The concept of CPU models is tied to specific architectures (like x86_64, aarch64, etc.). The `--arch` option is crucial for ensuring that you are comparing relevant CPU models. Comparing an x86_64 model with an aarch64 model would not be meaningful.

The `--machine` option might be relevant in certain hypervisors like KVM/QEMU, where different machine types can expose different sets of devices and sometimes influence the available CPU features or their interpretation. Usually, specifying a common machine type like `pc-Q35-x.y` (where x.y is a version number) is sufficient.

The `--emulator` option is generally less frequently used by end-users as libvirt typically finds the default emulator for the specified architecture. However, it can be useful in environments where multiple emulator versions are installed or when testing specific emulator behaviors.

The relationship of these commands to the FILE section mentioned earlier is that the CPU models described might be defined or referenced in configuration files related to the hypervisor or libvirt, although direct user interaction with these files is often not required.

To summarize, `hypervisor-cpu-compare` allows a user to understand the feature set relationships between different CPU models that a hypervisor knows about. This is critical for ensuring VM compatibility across different hosts or when upgrading guest configurations. It complements `hypervisor-cpu-baseline` by providing a more granular view of compatibility beyond the host's guaranteed baseline.

It is important to note that the CPU models listed by `hypervisor-cpu-models` are those that the hypervisor *claims* to support. `hypervisor-cpu-compare` then allows you to understand the relationships *between* those claimed models. The `--all` option in `hypervisor-cpu-compare` is similar in spirit to the `--all` option in `hypervisor-cpu-models` - it asks for information about all known models, not just those deemed "usable" on the current host.

The practical application involves planning VM deployments. If you intend to run a VM on multiple hosts with potentially different CPU generations, you might configure the VM with a CPU model that is a common superset of the baselines of all target hosts. `hypervisor-cpu-compare` helps identify such models. Alternatively, if maximum portability is required, one might choose the host's baseline CPU model or a model known to be widely compatible (often older models like Nehalem or Westmere for x86_64).

Understanding the output of `hypervisor-cpu-compare` is key:

  • A is superset of B: Model A has all CPU features of model B, plus possibly more. A guest using model B can run on a hypervisor configured with model A.

  • A is subset of B: Model A has fewer CPU features than model B. A guest using model A can run on a hypervisor configured with model B.

  • A is incompatible with B: Models A and B have different sets of features, and neither fully encompasses the other. A guest configured with model A might not run on a hypervisor configured with model B, and vice versa.

This functionality is essential for cloud environments and large deployments where VM mobility and compatibility across diverse hardware are critical requirements.

The comparison is based on the CPU feature flags recognized by the underlying architecture and reported by the hypervisor. For example, on x86_64, this includes features like SSE, AVX, AES, etc. The specific set of features associated with each named CPU model (e.g., Haswell, Broadwell, Skylake) is defined by the CPU vendor and interpreted by the hypervisor.

The relationship is transitive: if A is a superset of B, and B is a superset of C, then A is also a superset of C. This property is implicitly used when determining compatibility for migration.

Consider a scenario where you have Host1 with CPU model X1 and Host2 with CPU model X2. If you want to migrate a VM configured with CPU model VM_CPU from Host1 to Host2:

  • You need to ensure that the hypervisor on Host2 supports VM_CPU, or a model Y that is a superset of VM_CPU. This is checked by running `virsh hypervisor-cpu-compare --arch <arch> VM_CPU <hypervisor_cpu_on_host2>`.

  • If Host1's CPU (X1) is a superset of Host2's CPU (X2), but VM_CPU is set to X1, migration might fail if Host2 doesn't support X1 or a superset. The command helps identify such potential issues.

Essentially, `hypervisor-cpu-compare` helps in finding the "least common denominator" or the most compatible CPU model across a set of target hosts, or verifying if a specific model is suitable for a given hypervisor environment.

This command is particularly useful when dealing with CPU pinning or NUMA configurations, where the specific features and topology of the CPU play a significant role in performance and stability.

Final check: the `FILE` reference in the introductory sentence suggests that the definitions of these CPU models might be found in specific files, likely related to QEMU's CPU definitions or libvirt's internal data. However, for the user of `virsh`, these commands abstract away the need to directly inspect these files, providing a higher-level interface to CPU compatibility information.

The output is concise and focuses on the relationship: superset, subset, or incompatible. This allows scripts to easily process the results and make decisions about VM configuration or migration.

One should be aware that CPU models are constantly evolving. Newer CPU models are introduced with additional features. The `--all` flag in both `hypervisor-cpu-models` and `hypervisor-cpu-compare` is valuable for keeping track of these advancements and understanding the full capabilities exposed by the hypervisor, even if the current host hardware doesn't support them.

cache=none|writeback|writethrough|unsafe specifies the disk cache mode. 'none' means no caching, 'writeback' uses host cache for performance (risky on power loss), 'writethrough' writes directly to disk, and 'unsafe' is similar to writeback but potentially less safe.

aio=threads|io_uring` specifies the asynchronous I/O driver to use. 'threads' uses a thread pool, while 'io_uring' leverages the Linux kernel's io_uring interface.

After creating the disk image, you would typically use attach-disk or edit the domain's XML to attach this newly created disk to the domain.

Example: Create a 20GiB qcow2 image file named 'my_disk.qcow2' in the current directory:

virsh domblkcreate mydomain qcow2:my_disk.qcow2,size=20480

Example: Create a sparse raw image file with a backing file:

virsh domblkcreate mydomain raw:/path/to/new_disk.img,sparse=y,backing_file=/path/to/base.img

The command returns quickly after initiating the disk creation. The actual creation process happens in the background via qemu-img. The status of the created disk can be verified using `domblklist` and by checking the file system.

domblockpeek

Syntax:

Read raw data from a block device of domain. device is the name of the block device (e.g., vda, vdb). offset is the byte offset to start reading from, and len is the number of bytes to read.

This command is useful for low-level inspection of disk contents, such as examining boot sectors or specific file system structures. It requires the domain to be running.

The output is raw binary data. You might want to redirect the output to a file and then use tools like `hexdump` or `xxd` to view it in a human-readable format.

Example: Read 512 bytes from the beginning of the 'vda' device of a domain named 'myvm':

virsh domblockpeek myvm vda 0 512 > bootsector.bin

The offset and length must be specified in bytes. Ensure the device name is correct by using `domblklist domain` first.

This command operates directly on the block device presented to the guest. It bypasses the guest's operating system and file system layer, giving direct access to the underlying storage.

Be cautious when using this command, as reading incorrect offsets or lengths could potentially lead to issues if combined with write operations (though this command is read-only). Ensure the domain is not actively modifying the data you are reading, as this could lead to inconsistent results.

The maximum value for `len` might be limited by the hypervisor or the underlying storage system. If you need to read very large amounts of data, consider using file-based tools or snapshotting the disk first.

This command is primarily intended for debugging and low-level analysis tasks.

virsh for domains

The virsh(1) utility is a command-line interface to manage domains, nodes, storage, networks, etc. It is intended primarily for interactive use, but may also be used for scripting.

This section describes the virsh commands for managing domains.

create

Syntax:

create FILE [--live] [--force]

Create a domain from an XML <file>. If --live is specified, the domain is created with the live configuration otherwise it is created with the persistent configuration. If the domain is already running, the changes will take effect on the next boot. If --force is specified, then any existing persistent domain definition will be replaced with the new one.

The XML file is typically named domain.xml and contains the domain configuration. This command can be used to start a domain that has been defined using the define command or to start a domain using a temporary XML file.

If the XML file describes a domain that is already defined and running, this command can be used to apply runtime changes to it if the domain supports live configuration changes. However, for changes that require a reboot, the domain needs to be shut down and then created again.

This command is generally used for transient domains, or when you want to apply a temporary configuration to an existing domain without modifying its persistent definition.

الصيغة:

    [--preserve-domain-on-shutdown]

بدء مهمة نسخ احتياطي جديدة. إذا تم حذف backupxml، فإن هذا افتراضيًا لنسخ احتياطي كامل باستخدام نموذج دفع إلى أسماء الملفات التي تم إنشاؤها بواسطة libvirt؛ يوفر توفير XML ضبطًا دقيقًا مثل طلب نسخ احتياطي تزايدي بالنسبة لنقطة تفتيش سابقة، والتحكم في الأقراص التي تشارك أو أسماء الملفات المعنية، أو طلب استخدام نموذج سحب للنسخ الاحتياطي. يعرض الأمر backup-dumpxml أي قيم ناتجة تم تعيينها بواسطة libvirt. لمزيد من المعلومات حول XML النسخ الاحتياطي، انظر: https://libvirt.org/formatbackup.html

إذا تم استخدام --reuse-external، فإنه يوجه libvirt لإعادة استخدام الملفات المؤقتة وملفات الإخراج التي قدمها المستخدم في backupxml.

عند استخدام علامة --preserve-domain-on-shutdown، لن تقوم libvirt بإنهاء الجهاز الافتراضي إذا قام نظام تشغيل الضيف بالإغلاق أثناء تشغيل النسخ الاحتياطي. سيتم الاحتفاظ بالجهاز الافتراضي في حالة VIR_DOMAIN_PAUSED حتى تنتهي مهمة النسخ الاحتياطي. يمكن أيضًا استئناف الجهاز الافتراضي لتشغيل مرة أخرى.

إذا تم تحديد checkpointxml، يتم استخدام ملف ثانٍ بعنصر علوي domaincheckpoint لإنشاء نقطة تفتيش متزامنة، للقيام بنسخ احتياطي تزايدي لاحق بالنسبة للوقت الذي تم فيه إنشاء النسخ الاحتياطي. انظر checkpoint-create لمزيد من التفاصيل حول نقاط التفتيش.

يعود هذا الأمر في أقرب وقت ممكن، وتعمل مهمة النسخ الاحتياطي في الخلفية؛ يمكن التحقق من تقدم النسخ الاحتياطي بنموذج الدفع باستخدام domjobinfo أو بالانتظار لحدث باستخدام event (تقدم النسخ الاحتياطي بنموذج السحب يخضع لسيطرة أي طرف ثالث يتصل بتصدير NBD). تنتهي المهمة باستخدام domjobabort.

dump

Syntax:

dump domain corefilepath [--bypass-cache]
   { [--live] | [--crash] | [--reset] }
   [--verbose] [--memory-only] [--format string]

يقوم بتفريغ نواة النطاق إلى ملف للتحليل. إذا تم تحديد --live، يستمر النطاق في التشغيل حتى يكتمل تفريغ النواة، بدلاً من التوقف مسبقًا. إذا تم تحديد --crash، يتم إيقاف النطاق بحالة تعطل، بدلاً من تركه ببساطة في حالة إيقاف مؤقت. إذا تم تحديد --reset، يتم إعادة تعيين النطاق بعد تفريغ ناجح. لاحظ أن هذه المفاتيح الثلاثة متبادلة. إذا تم تحديد --bypass-cache، يتجنب الحفظ ذاكرة التخزين المؤقت لنظام الملفات، على الرغم من أن هذا قد يبطئ العملية. إذا تم تحديد --memory-only، يكون الملف بتنسيق elf، ولن يتضمن سوى ذاكرة النطاق وقيمة سجل وحدة المعالجة المركزية الشائعة. هذا مفيد جدًا إذا كان النطاق يستخدم أجهزة المضيف مباشرة. --format string يستخدم لتحديد تنسيق التفريغ 'memory-only'، و string يمكن أن يكون أحد الخيارات التالية: elf، kdump-zlib (تنسيق مضغوط kdump باستخدام ضغط zlib)، kdump-lzo (تنسيق مضغوط kdump باستخدام ضغط lzo)، kdump-snappy (تنسيق مضغوط kdump باستخدام ضغط snappy)، win-dmp (تنسيق تفريغ تعطل كامل لنظام Windows).

يمكن مراقبة التقدم باستخدام الأمر domjobinfo في virsh وإلغاؤه باستخدام الأمر domjobabort (يتم إرساله بواسطة مثيل virsh آخر). خيار آخر هو إرسال SIGINT (عادةً باستخدام Ctrl-C) إلى عملية virsh التي تقوم بتشغيل الأمر dump. يعرض --verbose تقدم التفريغ.

ملاحظة: قد تتطلب بعض أنظمة المحاكاة الفائقة من المستخدم ضمان الأذونات المناسبة يدويًا على الملف والمسار المحددين بواسطة الوسيط corefilepath.

ملاحظة: يتم إهمال تفريغ التعطل بتنسيق kvmdump قديم ولا يمكن تحميله ومعالجته بواسطة أداة crash منذ الإصدار 6.1.0. يلزم استخدام خيار --memory-only لإنتاج ملف ELF صالح يمكن معالجته لاحقًا بواسطة أداة crash.

MIGRATING DOMAINS

This section describes the virsh commands related to migrating domains between hosts.

migrate

Syntax:

migrate [--live] [--offline] [--direct] [--p2p [--tunnelled]]
   [--persistent] [--undefinesource] [--suspend] [--copy-storage-all]
   [--copy-storage-inc] [--change-protection] [--unsafe] [--verbose]
   [--rdma-pin-all] [--abort-on-error] [--postcopy]
   [--postcopy-after-precopy] [--postcopy-resume] [--zerocopy]
   domain desturi [migrateuri] [graphicsuri] [listen-address] [dname]
   [--timeout seconds [--timeout-suspend | --timeout-postcopy]]
   [--xml file]
   [--migrate-disks disk-list] [--migrate-disks-detect-zeroes disk-list]
   [--disks-port port]
   [--compressed] [--comp-methods method-list]
   [--comp-mt-level] [--comp-mt-threads] [--comp-mt-dthreads]
   [--comp-xbzrle-cache] [--comp-zlib-level] [--comp-zstd-level]
   [--auto-converge] [auto-converge-initial]
   [auto-converge-increment] [--persistent-xml file] [--tls]
   [--postcopy-bandwidth bandwidth]
   [--parallel [--parallel-connections connections]]
   [--bandwidth bandwidth] [--tls-destination hostname]
   [--disks-uri URI] [--copy-storage-synchronous-writes]
   [--available-switchover-bandwidth bandwidth]

Migrate domain to another host. Add --live for live migration; <--p2p> for peer-2-peer migration; --direct for direct migration; or --tunnelled for tunnelled migration. --offline migrates a stopped domain. --persistent makes the domain persistent on the destination. If not specified, the domain will be ephemeral on the destination. --undefinesource undefines the domain on the source host after successful migration. --suspend forces the migration to stop the domain at the end of the transfer (i.e., makes it an offline migration). --copy-storage-all copies all disks associated with the domain. --copy-storage-inc copies only those disks that have changed since the last migration. --change-protection tries to prevent unauthorized changes to the domain during migration. --unsafe disables certain checks, potentially speeding up migration but with risks. --verbose shows migration progress. --rdma-pin-all pins all memory using RDMA. --abort-on-error aborts the migration if an error occurs. --postcopy enables post-copy migration, where the domain starts running on the destination before all its memory has been transferred. --postcopy-after-precopy attempts post-copy migration only if pre-copy migration fails. --postcopy-resume resumes a post-copy migration. --zerocopy enables zero-copy migration where applicable. domain is the domain to migrate. desturi is the destination hypervisor connection URI. migrateuri is an optional URI for the migration process itself. graphicsuri is an optional URI for graphics. listen-address is the IP address to listen on for incoming connections. dname is the new name for the domain on the destination. --timeout sets a timeout for the migration, with options for suspend or post-copy phases. --xml file specifies an XML file to use for the destination domain configuration. --migrate-disks disk-list specifies which disks to migrate. --migrate-disks-detect-zeroes disk-list detects zeroed blocks in specified disks during migration. --disks-port port specifies the port for disk transfer. --compressed enables data compression during migration. --comp-methods specifies compression methods. --comp-mt-level, --comp-mt-threads, --comp-mt-dthreads configure multi-threaded compression. --comp-xbzrle-cache sets the XBZRLE cache size. --comp-zlib-level, --comp-zstd-level set Zlib and Zstd compression levels. --auto-converge enables automatic convergence after migration. --persistent-xml file specifies an XML file to store the persistent domain definition. --tls enables TLS encryption for migration. --postcopy-bandwidth sets the bandwidth limit for post-copy migration. --parallel enables parallel migration streams. --parallel-connections sets the number of parallel connections. --bandwidth sets the overall bandwidth limit for migration. --tls-destination specifies the hostname for TLS verification. --disks-uri URI specifies the URI for disk storage. --copy-storage-synchronous-writes enables synchronous writes for storage copy. --available-switchover-bandwidth specifies the available bandwidth for switchover.

The desturi parameter can be specified in several ways:

  • To migrate to a remote host using TLS (the default): 
    qemu+tls://REMOTE_HOST/system
  • To migrate to a remote host using SSH: 
    qemu+ssh://REMOTE_HOST/system
  • To migrate to a remote host using a specific user: 
    qemu+ssh://USER@REMOTE_HOST/system
  • To migrate to a remote host using a specific port: 
    qemu+ssh://REMOTE_HOST:PORT/system
  • To migrate to a remote host using a specific private key: 
    qemu+ssh://REMOTE_HOST/system?keyfile=/path/to/key
  • To migrate to a remote host, passing specific SSH options: 
    qemu+ssh://REMOTE_HOST/system?ssh_args=--option=value

The migrateuri parameter can be used to specify the migration transport and connection details if they differ from the destination URI. For example:

qemu+tls://REMOTE_HOST/system tcp://0.0.0.0:8000/

Here, the domain is migrated to the remote host using TLS, but the migration data itself is sent over TCP to the specified address and port.

If --migrate-disks is used, the disk list must be specified as a comma-separated list of disk identifiers (e.g., 'sda', 'vda', 'disk1').

If --migrate-disks-detect-zeroes is used, the disk list must be specified in the same way.

If --xml is used, the file specified should contain the XML description of the domain to be created on the destination host. Only host-specific portions of the XML may be changed.

If --persistent-xml is used, the file specified will contain the domain's persistent XML definition after a successful migration. This is useful for saving the configuration of a migrated domain.

If the domain is to be migrated to a host that does not support live migration, use the --offline flag. If the domain is already paused, you can use the --suspend flag to migrate it as an offline domain.

If --copy-storage-all or --copy-storage-inc is used, the desturi must support storage migration. If the storage migration protocol is not implicitly known, it may need to be explicitly specified in the desturi.

The --parallel flag can significantly speed up migration by transferring data over multiple TCP connections.

The --abort-on-error flag can be useful for preventing partial migrations in case of failures.

The --postcopy-bandwidth option allows you to limit the bandwidth used during the post-copy phase, which can be important for managing network resources.

The --available-switchover-bandwidth option informs the migration process about the available network bandwidth during the final switchover phase, allowing for potential optimizations.

The --disks-uri option allows specifying a different URI for migrating the disk images. This can be useful for migrating disks over a dedicated high-speed network or storage solution.

The --copy-storage-synchronous-writes option ensures that all disk writes are confirmed before the migration proceeds, guaranteeing data integrity at the cost of potentially slower performance.

Syntax:

Allows you to display or set the domain memory parameters. Without flags, the current settings are displayed; with a flag, the appropriate limit is adjusted if supported by the hypervisor. LXC and QEMU/KVM support --hard-limit, --soft-limit, and --swap-hard-limit. --min-guarantee is supported only by ESX hypervisor. Each of these limits are scaled integers (see NOTES above), with a default of kibibytes (blocks of 1024 bytes) if no suffix is present. Libvirt rounds up to the nearest kibibyte. Some hypervisors require a larger granularity than KiB, and requests that are not an even multiple will be rounded up. For example, vSphere/ESX rounds the parameter up to mebibytes (1024 kibibytes).

If --current is specified, it is equivalent to either --live or --config, depending on the current state of the guest. Both --live and --config flags may be given, but --current is exclusive. If no flag is specified, behavior is different depending on hypervisor.

For QEMU/KVM, the parameters are applied to the QEMU process as a whole. Thus, when counting them, one needs to add up guest RAM, guest video RAM, and some memory overhead of QEMU itself. The last piece is hard to determine so one needs guess and try.

For LXC, the displayed hard_limit value is the current memory setting from the XML or the results from a virsh setmem command.

  • --hard-limit

    The maximum memory the guest can use.

  • --soft-limit

    The memory limit to enforce during memory contention.

  • --swap-hard-limit

    The maximum memory plus swap the guest can use. This has to be more than hard-limit value provided.

  • --min-guarantee

    The guaranteed minimum memory allocation for the guest.

Specifying -1 as a value for these limits is interpreted as unlimited.

  • يقوم جدار الحماية بتقييد المنافذ المتاحة. عندما يقوم libvirt بإنشاء URI ترحيل، فإنه يختار رقم منفذ باستخدام قواعد خاصة بالبرنامج الافتراضي. تتطلب بعض البرامج الافتراضية منفذًا واحدًا فقط ليتم فتحه في جدران الحماية، بينما تتطلب برامج أخرى نطاقًا كاملاً من أرقام المنافذ. في الحالة الأخيرة، قد يتم تحديد migrateuri لاختيار رقم منفذ محدد خارج النطاق الافتراضي للامتثال لسياسات جدار الحماية المحلية.
  • يستخدم desturi طريقة نقل UNIX. في هذه الحالة المتقدمة، لا ينبغي لـ libvirt تخمين migrateuri ويجب تحديده باستخدام URI لمسار مقبس UNIX:
    • unix:///path/to/socket

    راجع https://libvirt.org/migration.html#uris لمزيد من التفاصيل حول URIs الترحيل.

    يقوم graphicsuri الاختياري بتجاوز معلمات الاتصال المستخدمة لإعادة توصيل العملاء الرسوميين تلقائيًا في نهاية الترحيل. إذا تم حذفه، سيقوم libvirt بحساب المعلمات بناءً على عنوان IP الخاص بالمضيف المستهدف. في حالة عدم وصول العميل مباشرة إلى الشبكة التي تتصل بها مضيفات المحاكاة الافتراضية ويحتاج إلى الاتصال عبر وكيل، يمكن استخدام graphicsuri لتحديد العنوان الذي يجب على العميل الاتصال به. يتكون URI على النحو التالي:

    protocol://hostname[:port]/[?parameters]

    حيث يكون البروتوكول إما "spice" أو "vnc" وتكون المعلمات قائمة بالمعلمات الخاصة بالبروتوكول مفصولة بـ '&'. المعلمات المعترف بها حاليًا هي "tlsPort" و "tlsSubject". على سبيل المثال،

    spice://target.host.com:1234/?tlsPort=4567

    يقوم listen-address الاختياري بتعيين عنوان الاستماع الذي يجب أن يربط به البرنامج الافتراضي على الجانب الوجهة لحركة الترحيل الواردة. يتم قبول عناوين IPv4 و IPv6 بالإضافة إلى أسماء المضيفات (يتم حلها على الوجهة). لا تدعم بعض البرامج الافتراضية تحديد عنوان الاستماع وستعيد خطأ إذا تم استخدام هذا المعلمة. لا يمكن استخدام هذه المعلمة إذا كان desturi يستخدم طريقة نقل UNIX.

    يقوم disks-port الاختياري بتعيين المنفذ الذي يجب أن يربط به البرنامج الافتراضي على الجانب الوجهة لحركة الأقراص الواردة. حاليًا، يتم دعمه فقط بواسطة QEMU.

    يمكن أيضًا تحديد disks-uri الاختياري (متناقض مع disks-port) لتحديد ما يجب أن يربط به البرنامج الافتراضي البعيد / يتصل به عند ترحيل الأقراص. يمكن أن يكون هذا tcp://address:port لتحديد عنوان استماع (يتجاوز --migrate-uri و --listen-address لترحيل الأقراص) ومنفذ أو unix:///path/to/socket في حال احتجت إلى حدوث ترحيل الأقراص عبر مقبس UNIX بالمسار المحدد. في هذه الحالة، تحتاج إلى التأكد من إمكانية الوصول إلى نفس مسار المقبس لكل من مضيفات المصدر والوجهة، والاتصال بالمقبس على المصدر (بعد أن يقوم البرنامج الافتراضي بإنشائه على الوجهة) سيتصل بالفعل بالوجهة. إذا كنت تستخدم SELinux (على الأقل على مضيف المصدر)، تحتاج إلى التأكد من أن المقبس على المصدر متاح لـ libvirtd/QEMU للاتصال. لا يمكن لـ Libvirt تغيير سياق المقبس الموجود لأنه يختلف عن التمثيل الملفي للمقبس ويتم اختيار السياق من قبل المنشئ (عادةً باستخدام وظائف setsockcreatecon{,_raw}()).

    يقوم --available-switchover-bandwidth الاختياري بتجاوز النطاق الترددي المحسوب تلقائيًا (بـ MiB/s) المتاح للمرحلة النهائية من الترحيل (النسخ المسبق) والتي يتم خلالها إيقاف وحدات المعالجة المركزية ونقل جميع الذاكرة المتبقية وحالة الجهاز. معرفة هذا النطاق الترددي مهم لتقدير دقيق لوقت تعطل النطاق وتحديد اللحظة المناسبة للتحويل. عادةً ما يتم تقدير ذلك بناءً على النطاق الترددي المستخدم في الترحيل، ولكن قد يكون هذا أقل من النطاق الترددي المتاح فعليًا. قد يساعد استخدام هذا الخيار في تقارب الترحيل عندما يستمر الترحيل في التكرار مرارًا وتكرارًا معتقدًا أنه لا يوجد نطاق ترددي كافٍ للامتثال لوقت التعطل الأقصى المحدد.

    numatune

    الصيغة:

    numatune domain [--mode mode] [--nodeset nodeset]
   [[--config] [--live] | [--current]]

    تعيين أو الحصول على معلمات numa الخاصة بالنطاق، المقابلة للعنصر <numatune> في XML الخاص بالنطاق. بدون علامات، يتم عرض الإعدادات الحالية.

    يمكن أن يكون mode أحد "strict" أو "interleave" أو "preferred" أو "restrictive" أو أي رقم صالح من تعداد virDomainNumatuneMemMode في حالة دعم الخادم لذلك. بالنسبة للنطاق الذي يعمل، لا يمكن تغيير الوضع، ويمكن تغيير nodeset فقط إذا بدأ النطاق بوضع "restrictive".

    nodeset هي قائمة بعقد numa التي يستخدمها المضيف لتشغيل النطاق. صيغتها هي قائمة مفصولة بفواصل، مع '-' للنطاقات و '^' لاستثناء عقدة.

    إذا تم تحديد --live، فقم بتعيين معلومات المجدول لنطاق تشغيل. إذا تم تحديد --config، فسيؤثر ذلك على البدء التالي لنطاق دائم. إذا تم تحديد --current، فإنه يعادل إما --live أو --config، اعتمادًا على الحالة الحالية للنطاق.

    بالنسبة للنطاقات قيد التشغيل على مضيفات Linux، فإن التغييرات التي تم إجراؤها على معلمات numa للنطاق لا تعني أن ذاكرة النطاق سيتم نقلها إلى nodeset مختلف على الفور. يعتمد ترحيل الذاكرة على نشاط النطاق، وذاكرة النطاق الخامل ستبقى في nodeset السابق لفترة أطول. سيؤدي وجود أجهزة VFIO أيضًا إلى قفل أجزاء من ذاكرة النطاق في نفس nodeset المستخدم لبدء النطاق، بغض النظر عن تغييرات nodeset.

    perf

    الصيغة:

    perf domain [--enable eventSpec] [--disable eventSpec]
   [[--config] [--live] | [--current]]

    الحصول على إعداد حدث perf الحالي أو تمكين/تعطيل أحداث perf محددة لنطاق ضيف.

    Perf هي أداة تحليل أداء في Linux، ويمكنها تشغيل عدادات أداء وحدة المعالجة المركزية، ونقاط التتبع، و kprobes، و uprobes (التتبع الديناميكي). يدعم Perf قائمة بالأحداث القابلة للقياس، ويمكنه قياس الأحداث القادمة من مصادر مختلفة. على سبيل المثال، بعض الأحداث هي عدادات نواة خالصة، في هذه الحالة تسمى أحداث برمجية، بما في ذلك تبديلات السياق، والأخطاء الطفيفة، وما إلى ذلك. الآن يمكن دعم عشرات الأحداث من مصادر مختلفة بواسطة perf.

    حاليًا، يدعم QEMU/KVM فقط هذا الأمر. يمكن استخدام الخيارين --enable و --disable مع eventSpec لتمكين أو تعطيل حدث أداء محدد. eventSpec هو قائمة سلاسل نصية لحدث واحد أو أكثر مفصولة بفواصل. أسماء الأحداث الصالحة هي كما يلي:

    أسماء أحداث perf الصالحة

    • cmt - ميزة PQos (Platform Qos) لمراقبة استخدام ذاكرة التخزين المؤقت بواسطة التطبيقات التي تعمل على المنصة.
    • mbmt - يوفر طريقة لمراقبة إجمالي عرض النطاق الترددي للذاكرة للنظام بين مستوى ذاكرة التخزين المؤقت وآخر.
    • mbml - يوفر طريقة للحد من كمية البيانات (بايت/ثانية) المرسلة عبر وحدة التحكم في الذاكرة على المقبس.
    • cache_misses - يوفر عدد مرات فقدان ذاكرة التخزين المؤقت بواسطة التطبيقات التي تعمل على المنصة.
    • cache_references - يوفر عدد مرات الوصول إلى ذاكرة التخزين المؤقت بواسطة التطبيقات التي تعمل

    schedinfo

    الصيغة:

    schedinfo domain [[--config] [--live] | [--current]] [[--set] parameter=value]...
schedinfo [--weight number] [--cap number] domain

    يسمح لك بعرض (وتعيين) معلمات مجدول النطاق. المعلمات المتاحة لكل جهاز افتراضي هي:

    LXC (مجدول posix): cpu_shares, vcpu_period, vcpu_quota

    QEMU/KVM (مجدول posix): cpu_shares, vcpu_period, vcpu_quota, emulator_period, emulator_quota, global_period, global_quota, iothread_period, iothread_quota

    Xen (مجدول الائتمان): weight, cap

    ESX (مجدول التخصيص): reservation, limit, shares

    إذا تم تحديد --live، فسيتم تعيين معلومات المجدول للضيف قيد التشغيل. إذا تم تحديد --config، فسيؤثر ذلك على البدء التالي لضيف دائم. إذا تم تحديد --current، فإنه يعادل إما --live أو --config، اعتمادًا على الحالة الحالية للضيف.

    ملاحظة: الحد الأدنى لقيمة معلمة cpu_shares هو 2 والحد الأقصى هو 262144 مع cgroups v1، و 1-1000 مع cgroups v2.

    ملاحظة: المعلمات weight و cap معرفة فقط لمجدول XEN_CREDIT.

    ملاحظة: المعلمات vcpu_period، emulator_period، و iothread_period لها نطاق قيمة صالح من 1000-1000000 أو 0، والمعلمات vcpu_quota، emulator_quota، و iothread_quota لها نطاق قيمة صالح من 1000-17592186044415 أو أقل من 0. القيمة 0 لأي من المعلمتين تعادل عدم تحديد تلك المعلمة.

    The following commands manipulate "secrets" (e.g. passwords, passphrases and encryption keys). Libvirt can store secrets independently from their use, and other objects (e.g. volumes or domains) can refer to the secrets for encryption or possibly other uses. Secrets are identified using a UUID. See https://libvirt.org/formatsecret.html for documentation of the XML format used to represent properties of secrets.

    secret-define

    Syntax:

    secret-define file [--validate]

    Create a secret with the properties specified in file, with no associated secret value. If file does not specify a UUID, choose one automatically. If file specifies a UUID of an existing secret, replace its properties by properties defined in file, without affecting the secret value.

    Optionally, the format of the input XML file can be validated against an internal RNG schema with --validate.

The default behaviour is to print each matching node as a standalone document, however, for ease of additional processing, the --wrap argument will cause the matching node to be wrapped in a common root node.

    secret-event

    Syntax:

    secret-event {[secret] event [--loop] [--timeout seconds] [--timestamp] | --list}

    Wait for a class of secret events to occur, and print appropriate details of events as they happen. The events can optionally be filtered by secret. Using --list as the only argument will provide a list of possible event values known by this client, although the connection might not allow registering for all these events.

    By default, this command is one-shot, and returns success once an event occurs; you can send SIGINT (usually via Ctrl-C) to quit immediately. If --timeout is specified, the command gives up waiting for events after seconds have elapsed. With --loop, the command prints all events until a timeout or interrupt key.

    أوامر اللقطات

    The following commands manipulate domain snapshots. Snapshots take the disk, memory, and device state of a domain at a point-of-time, and save it for future use. They have many uses, from saving a "clean" copy of an OS image to saving a domain's state before a potentially destructive operation. Snapshots are identified with a unique name. See https://libvirt.org/formatsnapshot.html for documentation of the XML format used to represent properties of snapshots.

    snapshot-create

    Syntax:

    snapshot-create domain [xmlfile] {[--redefine [--current]] |
   [--no-metadata] [--halt] [--disk-only] [--reuse-external]
   [--quiesce] [--atomic] [--live]} [--validate]

    Create a snapshot for domain domain with the properties specified in xmlfile. Optionally, the --validate option can be passed to validate the format of the input XML file against an internal RNG schema (identical to using the virt-xml-validate(1) tool). Normally, the only properties settable for a domain snapshot are the <name> and <description> elements, as well as <disks> if --disk-only is given; the rest of the fields are ignored, and automatically filled in by libvirt. If xmlfile is completely omitted, then libvirt will choose a value for all fields. The new snapshot will become current, as listed by snapshot-current.

    If --halt is specified, the domain will be left in an inactive state after the snapshot is created.

    If --disk-only is specified, the snapshot will only include disk content rather than the usual full system snapshot with vm state. Disk snapshots are captured faster than full system snapshots, but reverting to a disk snapshot may require fsck or journal replays, since it is like the disk state at the point when the power cord is abruptly pulled; and mixing --halt and --disk-only loses any data that was not flushed to disk at the time.

    If --redefine is specified, then all XML elements produced by snapshot-dumpxml are valid; this can be used to migrate snapshot hierarchy from one machine to another, to recreate hierarchy for the case of a transient domain that goes away and is later recreated with the same name and UUID, or to make slight alterations in the snapshot metadata (such as host-specific aspects of the domain XML embedded in the snapshot). When this flag is supplied, the xmlfile argument is mandatory, and the domain's current snapshot will not be altered unless the --current flag is also given.

    If --no-metadata is specified, then the snapshot data is created, but any metadata is immediately discarded (that is, libvirt does not treat the snapshot as current, and cannot revert to the snapshot unless --redefine is later used to teach libvirt about the metadata again).

    If --reuse-external is specified, and the snapshot XML requests an external snapshot with a destination of an existing file, then the destination must exist and be pre-created with correct format and metadata. The file is then reused; otherwise, a snapshot is refused to avoid losing contents of the existing files.

    If --quiesce is specified, libvirt will try to use guest agent to freeze and unfreeze domain's mounted file systems. However, if domain has no guest agent, snapshot creation will fail. Currently, this requires --disk-only to be passed as well.

    If --atomic is specified, libvirt will guarantee that the snapshot either succeeds, or fails with no changes; not all hypervisors support this. If this flag is not specified, then some hypervisors may fail after partially performing the action, and dumpxml must be used to see whether any partial changes occurred.

    If --live is specified, libvirt takes the snapshot while the guest is running. Both disk snapshot and domain memory snapshot are taken. This increases the size of the memory image of the external snapshot. This is currently supported only for full system external snapshots.

    Existence of snapshot metadata will prevent attempts to undefine a persistent guest. However, for transient domains, snapshot metadata is silently lost when the domain quits running (whether by command such as destroy or by internal guest action).

    For now, it is not possible to create snapshots in a domain that has checkpoints, although this restriction will be lifted in a future release.

    snapshot-create-as

    Syntax:

    snapshot-create-as domain {[--print-xml] [--no-metadata]
   [--halt] [--reuse-external]} [name]
   [description
    ] [--disk-only [--quiesce]] [--atomic] [--validate] [[--live] [--memspec memspec]] [--diskspec] diskspec]...

    إنشاء لقطة للكيان domain بالاسم <name> والوصف <description>؛ إذا تم حذف أي من القيمتين، سيختار libvirt قيمة. إذا تم تحديد --print-xml، فسيتم إخراج XML المناسب لـ snapshot-create، بدلاً من إنشاء لقطة فعليًا. وإلا، إذا تم تحديد --halt، فسيظل الكيان في حالة غير نشطة بعد إنشاء اللقطة، وإذا تم تحديد --disk-only، فلن تتضمن اللقطة حالة الجهاز الظاهري.

    يمكن استخدام الخيار --memspec للتحكم فيما إذا كانت لقطة النظام الكاملة داخلية أو خارجية. يجب أن يكون العلم --memspec إلزاميًا، متبوعًا بـ memspec بالشكل [file=]name[,snapshot=type]، حيث يمكن أن يكون النوع no أو internal أو external. لتضمين فاصلة حرفية في file=name، قم بإلغاء تهريبتها بفاصلة ثانية. لا يمكن استخدام --memspec مع --disk-only.

    يمكن استخدام الخيار --diskspec للتحكم في كيفية إنشاء ملفات خارجية بواسطة --disk-only ولقطات النظام الخارجية الكاملة. يمكن تكرار هذا الخيار، وفقًا لعدد عناصر <disk> في XML الخاص بالكيان. كل <diskspec> يكون بالشكل disk[,snapshot=type][,driver=type][,stype=type][,file=name]. يجب توفير diskspec للأقراص المدعومة بأجهزة الكتل حيث لا يقوم libvirt بإنشاء أسماء ملفات تلقائيًا لتلك الأقراص. يسمح المعامل الاختياري stype بالتحكم في نوع ملف المصدر. القيم المدعومة هي 'file' (الافتراضي) و 'block'. لاستبعاد قرص من لقطة خارجية استخدم --diskspec disk,snapshot=no.

    لتضمين فاصلة حرفية في disk أو في file=name، قم بإلغاء تهريبتها بفاصلة ثانية. يجب أن يسبق --diskspec حرفي كل diskspec ما لم تكن جميع الخيارات الثلاثة domain و name و description موجودة أيضًا. على سبيل المثال، يؤدي diskspec لـ "vda,snapshot=external,file=/path/to,,new" إلى XML التالي:

    <disk name='vda' snapshot='external'>
  <source file='/path/to,new'/>
</disk>

    إذا تم تحديد --reuse-external، وكان XML الخاص بالكيان أو خيار diskspec يطلب لقطة خارجية بوجهة ملف موجود، فيجب أن يكون الوجهة موجودًا وتم إنشاؤه مسبقًا بالتنسيق والبيانات الوصفية الصحيحة. ثم يتم إعادة استخدام الملف؛ وإلا، يتم رفض اللقطة لتجنب فقدان محتويات الملفات الموجودة.

    إذا تم تحديد --quiesce، سيحاول libvirt استخدام وكيل الضيف لتجميد وإلغاء تجميد أنظمة الملفات المثبتة للكيان. ومع ذلك، إذا لم يكن لدى الكيان وكيل ضيف، فسيفشل إنشاء اللقطة. حاليًا، يتطلب هذا تمرير --disk-only أيضًا.

    إذا تم تحديد --no-metadata، فسيتم إنشاء بيانات اللقطة، ولكن سيتم تجاهل أي بيانات وصفية على الفور (أي، لا يعتبر libvirt اللقطة حالية، ولا يمكن الرجوع إليها إلا إذا تم استخدام snapshot-create لاحقًا لتعليم libvirt حول البيانات الوصفية مرة أخرى).

    إذا تم تحديد --atomic، فسيضمن libvirt أن تنجح اللقطة، أو تفشل دون أي تغييرات؛ لا تدعم جميع برامج المحاكاة الافتراضية هذا. إذا لم يتم تحديد هذا العلم، فقد تفشل بعض برامج المحاكاة الافتراضية بعد أداء الإجراء جزئيًا، ويجب استخدام dumpxml لمعرفة ما إذا حدثت أي تغييرات جزئية.

    إذا تم تحديد --live، يقوم libvirt بأخذ لقطة أثناء تشغيل الضيف. يزيد هذا من حجم صورة الذاكرة للقطة الخارجية. هذا مدعوم حاليًا فقط لقطات النظام الخارجية الكاملة.

    حاليًا، لا يمكن إنشاء لقطات في كيان يحتوي على نقاط تحقق، على الرغم من رفع هذا القيد في إصدار مستقبلي.

    اختياريًا، يمكن تمرير الخيار --validate للتحقق من صحة مستند XML الذي تم إنشاؤه داخليًا بواسطة هذا الأمر مقابل مخطط RNG الداخلي.

    snapshot-list

    الصيغة:

    snapshot-list domain [--metadata] [--no-metadata]
   [{--parent | --roots | [{--tree | --name}]}] [--topological]
   [{[--from] snapshot | --current} [--descendants]]
   [--leaves] [--no-leaves] [--inactive] [--active]
   [--disk-only] [--internal] [--external]

    عرض جميع اللقطات المتاحة للكيان المحدد، مع عرض أعمدة لاسم اللقطة ووقت الإنشاء وحالة الكيان بشكل افتراضي.

    عادةً، يتم فرز إخراج الجدول حسب اسم اللقطة؛ باستخدام --topological بدلاً من ذلك، يتم الفرز بحيث لا يتم إدراج أي ابن قبل أسلافه (على الرغم من أنه قد يكون هناك أكثر من ترتيب ممكن واحد بهذه الخاصية).

    إذا تم تحديد --parent، فسيتم إضافة عمود إلى جدول الإخراج يعطي اسم الوالد لكل لقطة. إذا تم تحديد --roots، فستتم تصفية القائمة لتشمل فقط اللقطات التي ليس لها آباء. إذا تم تحديد --tree، فسيتم إخراج الإخراج بتنسيق شجري، مع عرض أسماء اللقطات فقط. هذه الخيارات الثلاثة متبادلة.

    إذا تم تحديد --name، فسيتم طباعة اسم اللقطة فقط متبوعًا اختياريًا باسم مفصول بجدولة للقطة الوالد إذا تم استخدام --parent أيضًا. هذا الخيار متبادل مع --tree.

    إذا تم توفير --from، قم بتصفية القائمة لتشمل اللقطات التي هي أبناء لـ snapshot المحدد؛ أو إذا تم توفير --current، ابدأ من اللقطة الحالية. عند استخدامه بمعزل أو مع --parent، تقتصر القائمة على الأبناء المباشرين ما لم يتم أيضًا توفير --descendants. عند استخدامه مع --tree، يتم تضمين استخدام --descendants ضمنيًا. هذا الخيار غير متوافق مع --roots. لاحظ أنه لا يتم تضمين نقطة البداية لـ --from أو --current في القائمة ما لم يتم أيضًا توفير خيار --tree.

    إذا تم تحديد --leaves، فسيتم تصفية القائمة لتشمل فقط اللقطات التي ليس لها أبناء. وبالمثل، إذا تم تحديد --no-leaves، فسيتم تصفية القائمة لتشمل فقط اللقطات التي لها أبناء. (لاحظ أن حذف كلا الخيارين لا يؤدي إلى أي تصفية، بينما قد يؤدي توفير كلا الخيارين إلى نفس القائمة أو خطأ اعتمادًا على ما إذا كان الخادم يتعرف على الأعلام). خيارات التصفية غير متوافقة مع --tree.

    إذا تم تحديد --metadata، فسيتم تصفية القائمة لتشمل فقط اللقطات التي تتضمن بيانات وصفية لـ libvirt، وبالتالي ستمنع undefine لكيان دائم، أو فقدانها عند destroy لكيان عابر. وبالمثل، إذا تم تحديد --no-metadata، فسيتم تصفية القائمة لتشمل فقط اللقطات الموجودة دون الحاجة إلى بيانات وصفية لـ libvirt.

    إذا تم تحديد --inactive، فسيتم تصفية القائمة لتشمل اللقطات التي تم أخذها عندما كان الكيان مغلقًا. إذا تم تحديد --active، فسيتم تصفية القائمة لتشمل اللقطات التي تم أخذها عندما كان الكيان قيد التشغيل، وحيث تتضمن اللقطة حالة الذاكرة للعودة إلى تلك الحالة قيد التشغيل. إذا تم تحديد --disk-only، فسيتم تصفية القائمة لتشمل اللقطات التي تم أخذها عندما كان الكيان قيد التشغيل، ولكن حيث تتضمن اللقطة حالة القرص فقط.

    إذا تم تحديد --internal، فسيتم تصفية القائمة لتشمل اللقطات التي تستخدم تخزينًا داخليًا لصور الأقراص الموجودة. إذا تم تحديد --external، فسيتم تصفية القائمة لتشمل اللقطات التي تستخدم ملفات خارجية لأقراص الصور أو حالة الذاكرة.

    snapshot-dumpxml

    الصيغة:

    snapshot-dumpxml [--security-info] [--xpath EXPRESSION] [--wrap]
                 domain snapshot

    إخراج XML اللقطة لـ snapshot مسمى للكيان. استخدام --security-info سيشمل أيضًا معلومات حساسة أمنيًا. استخدم snapshot-current للوصول بسهولة إلى XML للقطة الحالية.

    إذا وفر الوسيط --xpath تعبير XPath، فسيتم تقييمه مقابل XML الناتج وسيتم طباعة العقد المطابقة فقط. السلوك الافتراضي هو طباعة كل عقدة مطابقة كمستند مستقل، ومع ذلك، لتسهيل المعالجة الإضافية، فإن
