virtualenv هي أداة لإنشاء بيئات بايثون معزولة.

VIRTUALENV مقابل VENV

منذ بايثون 3.3، تم دمج جزء منها في المكتبة القياسية تحت وحدة venv https://docs.python.org/3/library/venv.html. وحدة venv لا تقدم جميع ميزات هذه المكتبة، على سبيل المثال لا الحصر:

  • أبطأ (لعدم وجود طريقة بذرة app-data)،
  • ليست قابلة للتوسيع بنفس القدر،
  • لا يمكنها إنشاء بيئات افتراضية لإصدارات بايثون مثبتة بشكل تعسفي (واكتشافها تلقائيًا)،
  • غير قابلة للترقية عبر pip https://pip.pypa.io/en/stable/installing/،
  • ليس لديها واجهة برمجة تطبيقات غنية بنفس القدر (تصف البيئات الافتراضية دون إنشائها).

مفهوم والغرض من VIRTUALENV

المشكلة الأساسية التي يتم تناولها هي مشكلة التبعيات والإصدارات، وبشكل غير مباشر الأذونات. تخيل أن لديك تطبيقًا يحتاج إلى الإصدار 1 من LibFoo، ولكن تطبيقًا آخر يتطلب الإصدار 2. كيف يمكنك استخدام كلا المكتبتين؟ إذا قمت بتثبيت كل شيء في بايثون المضيف الخاص بك (على سبيل المثال، python3.8)، فمن السهل الوقوع في موقف تكون فيه حزمتان لهما متطلبات متعارضة.

أو بشكل عام، ماذا لو كنت تريد تثبيت تطبيق وتركه كما هو؟ إذا كان التطبيق يعمل، فإن أي تغيير في مكتباته أو إصدارات تلك المكتبات يمكن أن يكسر التطبيق. أيضًا، ماذا لو لم تتمكن من تثبيت حزم في دليل site-packages العام، بسبب عدم وجود أذونات لتغيير بيئة بايثون المضيف؟

في كل هذه الحالات، يمكن لـ virtualenv المساعدة. يقوم بإنشاء بيئة تحتوي على مجلدات التثبيت الخاصة بها، والتي لا تشترك في مكتبات مع بيئات virtualenv أخرى (وبشكل اختياري لا تصل إلى المكتبات المثبتة عالميًا أيضًا).

Python and OS Compatibility

virtualenv works with the following Python interpreter implementations:

  • CPython https://www.python.org/: 3.13 >= python_version >= 3.7
  • PyPy https://pypy.org/: 3.10 >= python_version >= 3.7

This means virtualenv works on the latest patch version of each of these minor versions. Previous patch versions are supported on a best effort approach.

CPython is shipped in multiple forms, and each OS repackages it, often applying some customization along the way. Therefore we cannot say universally that we support all platforms, but rather specify some we test against. In case of ones not specified here the support is unknown, though likely will work. If you find some cases please open a feature request on our issue tracker.

User Guide

Quick start

Create the environment (creates a folder in your current directory)
virtualenv env_name
In Linux or Mac, activate the new python environment
source env_name/bin/activate
Or in Windows
.\env_name\Scripts\activate
Confirm that the env is successfully selected
which python3

Introduction

Virtualenv has one basic command:

virtualenv venv

Note:

When creating a virtual environment, it's recommended to use a specific Python version, for example, by invoking virtualenv with python3.10 -m virtualenv venv. If you use a generic command like python3 -m virtualenv venv, the created environment will be linked to /usr/bin/python3. This can be problematic because when a new Python version is installed on the system, the /usr/bin/python3 symlink will likely be updated to point to the new version. This will cause the virtual environment to inadvertently use the new Python version, which is often not the desired behavior. Using a specific version ensures that the virtual environment is tied to that exact version, providing stability and predictability.

This will create a python virtual environment of the same version as virtualenv, installed into the subdirectory venv. The command line tool has quite a few of flags that modify the tool's behavior, for a full list make sure to check out CLI flags <#cli-flags>.

The tool works in two phases:

  • Phase 1 discovers a python interpreter to create a virtual environment from (by default this is the same python as the one virtualenv is running from, however we can change this via the p <#p> option).
  • Phase 2 creates a virtual environment at the specified destination (dest <#dest>), this can be broken down into four further sub-steps:
  • create a python that matches the target python interpreter from phase 1,
  • install (bootstrap) seed packages (one or more of pip https://pypi.org/project/pip, setuptools https://pypi.org/project/setuptools, wheel https://pypi.org/project/wheel) in the created virtual environment,
  • install activation scripts into the binary directory of the virtual environment (these will allow end users to activate the virtual environment from various shells).
  • create files that mark the virtual environment as to be ignored by version control systems (currently we support Git only, as Mercurial, Bazaar or SVN do not support ignore files in subdirectories). This step can be skipped with the no-vcs-ignore <#no-vcs-ignore> option.

The python in your new virtualenv is effectively isolated from the python that was used to create it.

Python discovery

The first thing we need to be able to create a virtual environment is a python interpreter. This will describe to the tool what type of virtual environment you would like to create, think of it as: version, architecture, implementation.

virtualenv being a python application has always at least one such available, the one virtualenv itself is using, and as such this is the default discovered element. This means that if you install virtualenv under python 3.8, virtualenv will by default create virtual environments that are also of version 3.8.

Created python virtual environments are usually not self-contained. A complete python packaging is usually made up of thousands of files, so it's not efficient to install the entire python again into a new folder. Instead virtual environments are mere shells, that contain little within themselves, and borrow most from the system python (this is what you installed, when you installed python itself). This does mean that if you upgrade your system python your virtual environments might break, so watch out. The upside of this, referring to the system python, is that creating virtual environments can be fast.

Here we'll describe the built-in mechanism (note this can be extended though by plugins). The CLI flag p <#p> or python <#python> allows you to specify a python specifier for what type of virtual environment you would like, the format is either:

  • a relative/absolute path to a Python interpreter,
  • a specifier identifying the Python implementation, vers

المُفعّلات

هذه هي نصوص تفعيل تقوم بتعديل إعدادات الشل الخاص بك لضمان أن الأوامر من داخل بيئة بايثون الافتراضية لها الأولوية على مسارات النظام الخاص بك. على سبيل المثال، إذا كان استدعاء pip من الشل الخاص بك يعيد pip بايثون النظام قبل التفعيل، فبمجرد إجراء التفعيل، يجب أن يشير هذا إلى pip بيئة بيئة بايثون الافتراضية. لاحظ، مع ذلك، أن كل ما نفعله هو تغيير الأولوية؛ لذلك، إذا لم تكن مجلدات bin/Scripts الخاصة ببيئة بايثون الافتراضية تحتوي على بعض الملفات التنفيذية، فسيظل هذا يحل إلى نفس الملف التنفيذي الذي كان سيتم حله قبل التفعيل.

للحصول على قائمة بالمُفسّرات التي نوفر لها نصوص تفعيل، انظر activators <#activators>. موقع هذه النصوص هو بجوار ملفات بايثون التنفيذية مباشرة: عادةً مجلد Scripts في Windows، ومجلد bin في POSIX. تُسمى activate، بالإضافة إلى امتداد خاص بكل نص تفعيل، وبدون امتداد لـ Bash. يمكنك استدعائها، عادةً عن طريق مصدرتها (source-ing). قد يختلف أمر المصدر (source) حسب الشل - على سبيل المثال، في Bash يكون source (أو .):

source venv/bin/activate

يقوم نص التفعيل بإضافة مجلد الملفات التنفيذية لبيئة بايثون الافتراضية إلى متغير البيئة PATH. هذا مجرد وسيلة للوصول السهل للقيام بذلك، حيث يمكنك القيام بذلك بنفسك.

لاحظ أنه ليس عليك تفعيل بيئة بايثون الافتراضية لاستخدامها. يمكنك بدلاً من ذلك استخدام المسارات الكاملة لملفاتها التنفيذية، بدلاً من الاعتماد على الشل الخاص بك لحلها إلى بيئة بايثون الافتراضية الخاصة بك.

تقوم نصوص التفعيل أيضًا بتعديل موجه الشل الخاص بك للإشارة إلى البيئة النشطة حاليًا، عن طريق إضافة اسم البيئة (أو الاسم المحدد بواسطة --prompt عند إنشاء البيئة في البداية) بين قوسين، مثل (venv). يمكنك تعطيل هذا السلوك عن طريق تعيين متغير البيئة VIRTUAL_ENV_DISABLE_PROMPT إلى أي قيمة. يمكنك أيضًا الحصول على اسم البيئة عبر متغير البيئة VIRTUAL_ENV_PROMPT إذا كنت ترغب في تخصيص الموجه الخاص بك، على سبيل المثال.

توفر النصوص أيضًا أمر deactivate الذي سيسمح لك بالتراجع عن العملية:

deactivate

واجهة برمجة التطبيقات

في الوقت الحالي، يوفر virtualenv واجهة على مستوى CLI فقط. إذا كنت ترغب في تشغيل استدعاء لبيئات Python من داخل Python، فيجب عليك استخدام الدالة virtualenv.cli_run؛ تأخذ هذه الدالة وسيطة args حيث يمكنك تمرير الخيارات بنفس الطريقة التي تفعل بها من سطر الأوامر. ستعيد الدالة كائن جلسة يحتوي على بيانات حول بيئة بايثون الافتراضية التي تم إنشاؤها.

from virtualenv import cli_run
cli_run(["venv"])
virtualenv.cli_run(args, options=None, setup_logging=True, env=None)
إنشاء بيئة بايثون افتراضية بناءً على بعض وسائط واجهة سطر الأوامر.

أعلام سطر الأوامر

virtualenv هو في الأساس تطبيق سطر أوامر.

يقوم بتعديل متغيرات البيئة في الشل لإنشاء بيئة Python معزولة، لذلك ستحتاج إلى شل لتشغيله. يمكنك كتابة virtualenv (اسم التطبيق) متبوعًا بأعلام تتحكم في سلوكه. جميع الخيارات لها قيم افتراضية منطقية، وهناك وسيطة واحدة مطلوبة: اسم/مسار بيئة بايثون الافتراضية المراد إنشاؤها. يمكن تجاوز القيم الافتراضية لخيارات سطر الأوامر عبر ملف التكوين أو متغيرات البيئة. متغيرات البيئة لها الأولوية على قيم ملف التكوين (--help سيظهر إذا كان الافتراضي يأتي من متغير البيئة حيث سينتهي مفتاح المساعدة في هذه الحالة بمتغيرات البيئة أو ملف التكوين).

الخيارات التي يمكن تمريرها إلى virtualenv، جنبًا إلى جنب مع قيمها الافتراضية ووصف مختصر مدرجة أدناه.
