الاسم

vcsh - نظام التحكم بالإصدار لـ $HOME - مستودعات Git متعددة في $HOME

الخلاصة

vcsh [خيارات] أمر

vcsh clone [-b فرع] عنوان_url [مستودع]

vcsh delete مستودع

vcsh enter مستودع

vcsh foreach [-g] أمر_git

vcsh help

vcsh init مستودع

vcsh list

vcsh list-tracked [مستودع]

vcsh list-untracked [-a] [-r] [مستودع]

vcsh pull

vcsh push

vcsh rename مستودع اسم_جديد

vcsh run مستودع أمر_shell

vcsh status [مستودع]

vcsh upgrade مستودع

vcsh version

vcsh which نص_جزئي

vcsh write-gitignore [مستودع]

vcsh مستودع أمر_git

vcsh مستودع

الوصف

يسمح لك vcsh بامتلاك عدة مستودعات git(1)، وكلها تحافظ على أشجار العمل الخاصة بها في $HOME دون أن تتصادم مع بعضها البعض. هذا، بدوره، يعني أنه يمكنك الحصول على مستودع واحد لكل مجموعة إعدادات (zsh، vim، ssh، إلخ)، واختيار مجموعات الإعدادات التي تريد استخدامها في كل آلة.

يستخدم vcsh تقنية تسمى مستودعات Git الوهمية غير المكتملة (fake bare Git repositories)، مع الاحتفاظ بـ $GIT_DIR في دليل مختلف عن $GIT_WORK_TREE والذي يشير إلى $HOME.

لا يلزم استخدام الروابط الرمزية (symlinks) في هذا الإعداد، مما يؤدي إلى إعداد أنظف.

تم تصميم vcsh مع وضع mr(1) في الاعتبار، لذا قد ترغب في تثبيته جنبًا إلى جنب مع vcsh. ومع ذلك، يمكنك بسهولة استخدام vcsh بدون mr إذا كنت تفضل ذلك.

يمكن العثور على عينة تهيئة لـ vcsh و mr في https://github.com/RichiH/vcsh_mr_template واستخدامها مع vcsh clone https://github.com/RichiH/vcsh_mr_template mr.

يرجى ملاحظة أنه يمكنك دائمًا استخدام مسار بدلاً من اسم لـ مستودع. هذا ضروري لدعم mr والبرامج النصية الأخرى بشكل صحيح وهو غير ذي أهمية للمستخدم التفاعلي.

خيارات

-c
قم بتضمين ملف قبل ملفات التكوين الأخرى
-d
تمكين وضع التصحيح (debug)
-v
تمكين الوضع المطول (verbose)

أوامر

clone
استنساخ مستودع موجود.
إذا كنت بحاجة إلى استنساخ مجموعة من المستودعات، فابحث في الخطاف (hook) post-clone-retired.
يمكنك أيضًا استخدام مستودع git واحد مع فروع متعددة. استخدم الخيار -b لتحديد فرع عند الاستنساخ، الافتراضي هو master.
commit
تثبيت في جميع المستودعات
delete
حذف مستودع موجود.
enter
الدخول إلى المستودع؛ تشغيل $SHELL جديد مع تعيين $GIT_DIR.
foreach
تنفيذ أمر git لكل مستودع vcsh.
-g: التنفيذ في السياق العام.
help
عرض المساعدة.
init
تهيئة مستودع فارغ.
list
سرد جميع مستودعات vcsh المحلية.
list-tracked
سرد جميع الملفات التي يتتبعها vcsh.
إذا كنت ترغب في سرد الملفات التي يتتبعها مستودع معين، فما عليك سوى إلحاق اسم المستودع في النهاية.
list-tracked-by
سرد الملفات التي يتتبعها مستودع.
هذا أمر قديم؛ يجب عليك استخدام list-tracked <مستودع> بدلاً منه.
list-untracked
سرد جميع الملفات التي لا يتتبعها vcsh.
-a: عرض جميع الملفات. افتراضيًا، يتم استدعاء git ls-files --exclude-standard.
-r: وضع تكراري. افتراضيًا، تكون قائمة الملفات ضحلة وتتوقف عند مستويات الدليل حيثما أمكن.
$مستودع: سرد الملفات التي لا يتتبعها هذا المستودع المحدد.
pull
السحب من جميع مستودعات vcsh البعيدة.
push
الدفع إلى جميع مستودعات vcsh البعيدة.
rename
إعادة تسمية مستودع.
run
تشغيل أمر مع تعيين $GIT_DIR و $GIT_WORK_TREE. يسمح لك بتشغيل أي أو جميع الأوامر دون أي قيود. استخدم بحذر.
يرجى ملاحظة أن هناك ميزة سحرية إلى حد ما لـ run. بدلاً من مستودع، يقبل مسار أيضًا. سيتم افتراض أن أي شيء يحتوي على شرطة مائلة فيه هو مسار. سيقوم vcsh run بعد ذلك بتشغيل هذا الدليل بدلاً من الدليل الذي يتم إنشاؤه عادةً من اسم المستودع. هذا ضروري لدعم mr والبرامج النصية الأخرى بشكل صحيح وهو غير ذي أهمية للمستخدم التفاعلي.
status
إظهار حالات جميع مستودعات vcsh / مستودع واحد.
upgrade
ترقية المستودع إلى الإعدادات الموصى بها حاليًا.
version
طباعة معلومات الإصدار.
which نص_جزئي
البحث عن نص_جزئي في اسم أي ملف متتبع.
write-gitignore
كتابة .gitignore.d/مستودع عبر git ls-files. إذا لم يكن مستودع محددًا ولكننا داخل مستودع vcsh، استخدمه.
مستودع أمر_git
اختصار لتشغيل أوامر git على مستودع. سيقوم بprepend git إلى أمر_git.
مستودع
اختصار لتشغيل vcsh enter <مستودع>.

البيئة

كما ذكرنا سابقًا، سيقوم vcsh بتعيين $GIT_DIR و $GIT_WORK_TREE إلى القيم المناسبة لمستودعات Git الوهمية غير المكتملة.

التكوين

هناك عدة طرق لتعديل الإعدادات المختلفة في vcsh. بالترتيب التصاعدي للأسبقية، هي:

○
VARIABLE=foo vcsh
○
</etc/vcsh/config>
○
<$XDG_CONFIG_HOME/vcsh/config>
○
vcsh -c <ملف>

يرجى ملاحظة أن هذه الملفات يتم تضمينها (sourced). سيتم تنفيذ أي أو جميع الأوامر في سياق shell الخاص بك.

الإعدادات المثيرة للاهتمام التي يمكنك تغييرها:

$VCSH_GITATTRIBUTES
يمكن أن تكون none، أو أي قيمة أخرى.
none لن تحتفظ بملفات Git attributes في موقع خاص.
إذا تم تعيينها على أي قيمة أخرى، فسيتم الاحتفاظ بملفات gitattributes الخاصة بكل مستودع.
الافتراضي هو none.
$VCSH_GITIGNORE
يمكن أن تكون exact، none، أو recursive.
exact سيقوم بتعبئة ملف التجاهل الخاص بكل مستودع بجميع أسماء الملفات والدلائل التي ترجعها git ls-files.
none لن يكتب أي ملف تجاهل.
recursive سيتعمق عبر جميع الدلائل بشكل تكراري

vcsh(1) — Arch manual pages

NAME

vcsh — shell interface for managing dotfiles in multiple git repositories

SYNOPSIS

vcsh COMMAND [arguments...]

vcsh OPTION...

DESCRIPTION

vcsh is a tool to manage configuration files (dotfiles) in multiple git repositories. The idea is to have repositories for different parts of your configuration, check them out in subdirectories, and symlink the files into their final locations.

This allows for much finer-grained control than a single repository, e.g. you might want to have one repository for your shell configuration and another for your editor configuration.

vcsh aims to be a replacement for tools like git(1)'s worktree feature, or mr(1), but uses git repositories directly, without any wrapper scripts or custom formats.

OPTIONS

vcsh accepts the following options:

-h, --help
Show help message and exit.
-V, --version
Show version and exit.
-v, --verbose
Turn on verbosity.
-q, --quiet
Turn off verbosity.

COMMANDS

The following commands are available:

add repo [file...]
Add files to a repository.
clone url [repo]
Clone a repository into a subdirectory.
commit repo [file...]
Commit changes in a repository.
enter repo
Enter the directory of a repository.
export repo [dir]
Export a repository to a directory.
gc
Run garbage collection on all repositories.
help [command]
Show help message, optionally for a specific command.
init [repo]
Initialize a new repository.
list
List all managed repositories.
move repo newname
Rename a repository.
pull repo [branch]
Pull changes from a remote repository.
push repo [branch]
Push changes to a remote repository.
remove repo [file...]
Remove files from a repository.
rename repo newname
Rename a repository.
show repo [file...]
Show the status of files in a repository.
status repo [file...]
Show the status of files in a repository.
update [repo]
Update all repositories or a specific repository.
upgrade
Upgrade all repositories to the latest configuration.

ENVIRONMENT

$VCSH_HOME
The base directory for vcsh. Defaults to $HOME/.config/vcsh.
$VCSH_ROOT
The directory where repositories are checked out to. Defaults to $VCSH_HOME.
$VCSH_GIT_DIR
The directory where git repositories are stored. Defaults to $VCSH_ROOT.
$VCSH_WORKTREE
The directory where worktrees are created. Defaults to $VCSH_ROOT.
Can be absolute, or relative.
absolute will set an absolute path; defaulting to $HOME.
relative will set a path relative to $GIT_DIR.
Defaults to absolute.

Less interesting knobs you could turn:

$VCSH_DEBUG
Enter debug mode.
$XDG_CONFIG_HOME
As specified in the 'XDG Base Directory Specification', see http://standards.freedesktop.org/basedir-spec/basedir-spec-latest.html
Defaults to <$HOME/.config>.
$VCSH_REPO_D
The directory where repositories are read from and stored.
Defaults to <$XDG_CONFIG_HOME/vcsh/repo.d>.
$VCSH_HOOK_D
The directory where hooks are read from.
Defaults to <$XDG_CONFIG_HOME/vcsh/hooks-enabled>.
$VCSH_BASE
The directory where repositories are checked out to.
Defaults to $HOME.

CONFIG

The configuration files are sourced in the following order:

$VCSH_CONFIG
Can be set in the environment to point to a specific config file.
$XDG_CONFIG_HOME/vcsh/config
User-specific configuration.
/etc/vcsh/config
System-wide configuration.

The configuration files are shell scripts that are sourced by vcsh. They can be used to set environment variables or define functions.

HOOK SYSTEM

vcsh provides a hook system. Hook scripts must be executable and should be placed in <$XDG_CONFIG_HOME/vcsh/hooks-available>. From there, they can be soft-linked into <$XDG_CONFIG_HOME/vcsh/hooks-enabled>; vcsh will only execute hooks that are in this directory.

Hooks follow a simple format. pre-run will be run before anything is run. If you want to have more than one script for a certain hook, just append any kind of string to order them. A system of pre-run, <pre-run.10>, <pre-run.20> etc is suggested; other options would be pre-run-10 or <pre-run.sh>. A dot after the hook name is optional.

If you want to create hooks for a specific vcsh repository, simply prepend the repository's name, followed by a dot, i.e. <zsh.pre-run>. Otherwise, the same rules as above apply. The dot between the repository's name and the hook is mandatory, though.

Available hooks are pre-clone, post-clone, post-clone-retired, pre-command, post-command, pre-enter, post-enter, pre-init, post-init, pre-pull, post-pull, pre-push, post-push, pre-run, post-run, pre-upgrade, and post-upgrade. If you need more, vcsh is trivial to patch, but please let upstream know so we can ship them by default.

OVERLAY SYSTEM

vcsh also provides an overlay system. Similar to hooks, the recommended locations are <$XDG_CONFIG_HOME/vcsh/overlays-available> and <$XDG_CONFIG_HOME/vcsh/overlays-enabled>.

Overlays follow the same rules as hooks and you are free to overwrite any and all functions. Same as hooks, you can use global or repository-specific overlays by using either <$VCSH_OVERLAY_D/$VCSH_COMMAND> or <$VCSH_OVERLAY_D/$VCSH_REPO_NAME.$VCSH_COMMAND>.

Please note that nothing stops you from, e.g. overwriting status() in <$VCSH_OVERLAY_D/commit>. As the overlays will be sourced and you are replacing arbitrary functions, any and all features may stop working, or you may even lose data.

You have been warned.

DETAILED HOWTO AND FURTHER READING

Manpages are often short and sometimes useless to glean best practices from. While the author tried to avoid this in this case, manpages can not cover detailed howtos.

This software also comes with a file called <README.md>. It contains various approaches to setting up and using vcsh. You can view the file it as plain text or render it into various other formats via Markdown.

On Debian-based systems, this file can be found in </usr/share/doc/vcsh>.

SECURITY CONSIDERATIONS

vcsh allows you to execute arbitrary commands via vcsh run. For example, adding a sudo(8) rule for vcsh would be pretty stupid.

Additionally, vcsh will source, i.e. execute, all files listed in CONFIG. You can put any and all commands into these config files and they will be executed.

BUGS

None are known at this time, but reports and/or patches are more than welcome.

INTEROPERABILITY

If you rely on git submodule use git 1.7.12 or later. Earlier versions do not clean internal variables properly before descending into submodules, resulting in unhappy end users.

HISTORY

Like most people, the author initially made do with a single repository for all config files, all of which were soft-linked into $HOME.

Martin F. Krafft aka madduck came up with the concept of fake bare Git repositories.

vcsh was initially written by madduck. This version is a re-implementation from scratch with a lot more features. madduck graciously agreed to let the author take over the name.
