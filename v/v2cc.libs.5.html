الاسم

v2cc.libs - ملف تعيين مكتبة VHDL لمترجم/محاكي FreeHDL.

الوصف

FreeHDL هي مجموعة مترجم/محاكي للغة وصف الأجهزة VHDL. يتم دعم كل من معايير VHDL'93 و VHDL'87.

يقوم FreeHDL بترجمة ملفات مصدر VHDL الأصلية إلى C++. بعد ذلك، يمكن ترجمة مصدر C++ وربطه بالنواة لبناء برنامج المحاكاة. سيؤدي تشغيل الملف التنفيذي الذي تم إنشاؤه إلى محاكاة نموذج VHDL المقابل. العملية الفعلية للبناء لإنشاء المحاكي من مصدر VHDL هي عملية معقدة يتم التعامل معها بواسطة البرنامج النصي gvhdl.

لا يمتلك FreeHDL مفهومًا غامضًا لمكتبات التصميم. لا يتم تحليل ملفات VHDL مسبقًا وتخزينها في قاعدة بيانات مكتبة كما في أنظمة مترجم/محاكي VHDL الأخرى. بدلاً من ذلك، كلما احتاج الأمر إلى إجراء مرجع لوحدة تصميم، يقوم FreeHDL بتحليل كود VHDL لتلك الوحدة من جديد. لذلك، يحتاج إلى أن يكون قادرًا على العثور على ملف المصدر لوحدة تصميم معينة بمعرف VHDL الخاص بتلك الوحدة.

وبالتالي، بقدر ما يتعلق الأمر بـ FreeHDL، فإن مكتبة التصميم هي تعيين من معرفات VHDL إلى أسماء الملفات. يوجد أيضًا تعيين للحصول على أسماء المكتبات من ملفات التعيين.

يتم تحديد مثل هذا التعيين عبر "ملف تعيين". يحتوي على قائمة بقواعد الأنماط التي تحول كل فئة معينة من المعرفات إلى أسماء ملفات.

صيغة ملف التعيين هي:


معجمي:


litchar: 'a'..'z' | 'A'..'Z' | '0'..'9' | '_' | '/' | '-' | '.' escchar


escchar: '\' char


whitespace: ' ' | '\n' | '\v' | '\t' | comment


comment: '#' any_character* '\n'


opchar: ':' | ',' | '(' | ')'


specchar: every printable char except litchar, whitespace and opchar


symchar: litchar | specchar


symbol: symchar+


قواعد:


mapping: version patternrule*


version: "v2cc_mapfile" "0"


patternrule: symbol [ ':' symbol ]

يتم تجاهل التعليقات.

يحدد ملف التعيين تسلسلاً من قواعد الأنماط. عند تحويل معرف، يتم تجربة كل قاعدة بالتناوب ويتم اختيار الأولى التي تتطابق.

تبدو القاعدة كالتالي


pattern: filename

عندما يتم حذف جزء ": filename"، فإنه افتراضياً يكون "patternEXT" حيث يتم تحديد "EXT" بواسطة مستخدم ملف التعيين.

يمكن أن يحتوي "pattern" على الحرف الخاص "<" الذي يقدم "حرف بدل". يجب أن يتبع "<" حرف ">"، مع أحرف عشوائية بينهما. تشكل هذه الأحرف اسم حرف البدل. يطابق حرف البدل أي تسلسل من الأحرف. يمكن أن يكون هناك أي عدد من أحرف البدل في النمط، ولكن يجب أن يكون لكل منها اسم فريد.

يمكن أن يحتوي "filename" أيضًا على الحرف "<"، متبوعًا باسم، متبوعًا بـ ">". هناك، يقدم "استبدال حرف بدل". سيتم استبداله بالأحرف التي طابقت حرف البدل بنفس الاسم في "pattern". عندما لا يكون هناك حرف بدل في "pattern" بالاسم الصحيح، فسيتم استبداله بلا شيء. أثناء إجراء هذا الاستبدال، يتم استبدال الأحرف "#" و "/" بـ "##" و "#-" على التوالي. لا تتم أي ترجمات أحرف أخرى، لذلك إذا كان لديك أحرف غريبة في معرفات VHDL الخاصة بك، فستحصل على أحرف غريبة في أسماء ملفاتك.

قبل إجراء المقارنة مع الأنماط، يتم تحويل معرف VHDL إلى شكل قياسي: عندما لا يكون معرفًا مجردًا، يتم تحويل جميع أحرفه إلى أحرف صغيرة.

عندما يكون اسم الملف الناتج نسبيًا (لا يبدأ بـ "/"), فإنه يتم إضافة مسار ملف التعيين قبله.

يعادل ملف التعيين غير الموجود القاعدة الوحيدة


<>

ملف التعيين الفارغ هو بالضبط ذلك: تعيين فارغ.

لا يلزم أن يكون التعيين قابلاً للعكس. لا بأس عندما ترتبط معرفات متعددة باسم ملف واحد.

لا يوجد حرف خاص بخلاف "<" و ">" صالح في "pattern" أو "filename". إنها محجوزة للتوسعات المستقبلية.

يتم العثور على ملفات التعيين للانتقال من أسماء وحدات التصميم إلى أسماء الملفات عن طريق البحث في الدلائل المحددة بواسطة "مسار مكتبة v2cc". يمكنك استخدام متغير البيئة V2CC_LIBRARY_PATH وخيارات سطر الأوامر لتحديد المسار. عندما لا يتم تعيين متغير البيئة، فإنه افتراضيًا إلى قيمة تجعل المكتبات القياسية الموزعة والمثبتة مع v2cc نفسها متاحة. عندما يتم تعيينه، فإنه يحل محل هذه القيمة الافتراضية بالكامل.

يتكون المتغير V2CC_LIBRARY_PATH من أسماء ملفات مفصولة بـ ":". يتم استبدال اسم الملف "*" بالقيمة الافتراضية المذكورة أعلاه.

بالإضافة إلى متغير البيئة، يمكنك استخدام خيار سطر الأوامر "-L libdir" مع v2cc. تتم إضافة الدلائل المحددة بـ "-L" قبل تلك المحددة بواسطة V2CC_LIBRARY_PATH. في مسار المكتبة النهائي، تظهر بنفس الترتيب الذي ظهرت به في سطر الأوامر.

البحث عن وحدة تصميم تسمى UNIT في مكتبة تسمى LIB يتم كالتالي:


لكل مكون في مسار المكتبة، L
إذا كان L ملفًا عاديًا
عيّن LMAP إلى L
وإلا إذا كان L دليلاً
عيّن LMAP إلى L/v2cc.libs
وإلا
استمر مع المكون التالي
ترجم LIB إلى FLIB باستخدام LMAP مع EXT = ""
إذا كان FLIB.vhdl موجودًا
إنهاء بـ FLIB.vhdl كنتيجة
إذا كان FLIB.v2cc موجودًا
عيّن UMAP إلى FLIB.v2cc
وإلا إذا كان FLIB دليلاً
عيّن UMAP إلى FLIB/v2cc.units
وإلا
استمر مع المكون التالي
ترجم UNIT إلى FUNIT باستخدام UMAP مع EXT = ".vhdl"
إنهاء بـ FUNIT كنتيجة
إنهاء بنجاح

تُستخدم هذه الآلية لجميع وحدات التصميم التي تتم الإشارة إليها من داخل كود VHDL (أو عبر وسائل أخرى). هناك تعقيد مع البنى وأجسام الحزم، على الرغم من ذلك، لأنها لا يتم تحديدها بشكل فريد بواسطة معرف واحد. بالنسبة لهم، يتم إنشاء معرف مصطنع. تحصل البنى على أسماء بالشكل


<entity>(<architecture>)

بينما تصبح أجسام الحزم


<package>(body)

على سبيل المثال، يتم تحويل "architecture struct of model" إلى "model(struct)" ويتم تحويل "package body misc" إلى "misc(body)".

عندما يحتوي ملف تصميم على وحدات تصميم متعددة، يتم تحليلها جميعًا، وفحصها للتأكد من صحتها، وتذكرها، ولكن سيتم استخدام الوحدة المطلوبة فقط لتوليد الكود. وهذا يعني، عندما يحتوي ملف تصميم على كل من رأس الحزمة وجسم الحزمة ويتم الإشارة إلى رأس الحزمة من وحدة تصميم أخرى، فلن يتم إنشاء أي كود لجسم الحزمة. عندما يتم الإشارة إلى إحدى الوحدات المتجاهلة لاحقًا في نفس استدعاء v2cc، فلن يتم قراءة ملف التصميم مرة أخرى لأن جميع وحدات التصميم يتم الاحتفاظ بها في الذاكرة.

أمثلة

أبسط موقف هو عندما لا يكون لديك أي ملفات تعيين على الإطلاق. تكون مكتبة التصميم بعد ذلك دليلاً في مسار مكتبتك. اسم هذا الدليل هو اسم المكتبة في VHDL. يتم استخدام كل ملف في هذا الدليل بامتداد ".vhdl" لوحدة تصميم بنفس اسم الملف بدون امتداده.

لنفترض أن لديك هذا الهيكل الدليلي


somedir/
std/
standard.vhdl
textio.vhdl
ieee/
numeric_bit.vhdl
std_logic_1164.vhdl

عندما تضع "somedir" في مسار مكتبتك، يكون لديك وصول إلى وحدات التصميم


STD.STANDARD
STD.TEXTIO
IEEE.NUMERIC_BIT
IEEE.STD_LOGIC_1164

في هذا الموقف، لديك ملف واحد لكل وحدة تصميم. عندما يكون لديك ملف واحد لكل مكتبة تصميم، سيبدو الأمر كالتالي


somedir/
fmf.vhdl

سيتم توجيه جميع الإشارات إلى وحدات التصميم في مكتبة التصميم FMF إلى "fmf.vhdl".

كمثال آخر، افترض أنه تم تعيين جميع مكتبات VHDL إلى أدلة فرعية تبدأ من الدليل الجذر "/foo". علاوة على ذلك، افترض أن هناك مكتبات VHDL تسمى "lib1" و "lib2". يجب عليها

NAME

v2cc.libs - VHDL library mapping control file

DESCRIPTION

The file v2cc.libs controls the mapping of VHDL libraries to file system directories for the v2cc compiler front-end (part of FreeHDL).

A VHDL library is a named collection of VHDL design units. The v2cc.libs file allows you to specify which directory on the file system corresponds to which VHDL library name.

A typical scenario is to have your VHDL source files organized into different subdirectories, with each subdirectory corresponding to a VHDL library. For example, you might have a library named lib1 whose VHDL source files are located in lib1_dir, and another library named lib2 whose source files are in lib2_dir. These directories would typically reside under a common root directory, say /foo.

The VHDL library root directory is specified by the environment variable VHDL_LIBRARY_PATH. If this variable is not set, the current working directory is assumed to be the library root.

In the example above, the VHDL libraries lib1 and lib2 would be mapped to subdir "/foo/lib1_dir" and "/foo/lib2_dir". Hence, the file/directory structure is as follows:

/foo <- library root directory /foo/v2cc.libs <- mapping control file /foo/lib1_dir <- library dir for VHDL library lib1 /foo/lib1_dir/comp1.vhdl <- file that contains VHDL model comp1 /foo/lib2_dir <- library dir for VHDL library lib2 /foo/lib2_dir/comp2.vhdl <- file that contains VHDL model comp2

Then, file "/foo/v2cc.libs" should contain:

v2cc_mapfile 0 lib1 : lib1_dir lib2 : lib2_dir

In order to compile a design named comp1 (stored in file comp1.vhdl) into VHDL library lib1 goto subdir "/foo/lib1_dir" and execute:


gvhdl -c -L .. -l lib1 comp1.vhdl

Note that option "-l lib1" forces the compiler to associate the model stored in "comp1.vhdl" with VHDL library lib1. Note further, that the compiler switch "-L .." specifies the path to the directory where "v2cc.libs" is stored. You may also specify an absolute path:


gvhdl -c -L /foo -l lib1 comp1.vhdl

Note that comp1 should reside in a file named "comp1.vhdl".

If lib2 contains a design comp2 that makes use of comp1 from lib1 then goto "/foo/lib2_dir" and run the following command to create an executable for model comp2:


gvhdl -L .. -l lib2 comp2.vhdl ../lib1_dir/comp1.o
