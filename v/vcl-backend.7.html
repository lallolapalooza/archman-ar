VCL-backends - تعريف الواجهات الخلفية

تعريف الواجهة الخلفية

يُنشئ تعريف الواجهة الخلفية ويُهيئ كائن واجهة خلفية مُسمى. يبدأ التعريف بكلمة المفتاح backend متبوعة باسم الواجهة الخلفية. التعريف الفعلي موجود بين أقواس معقوفة، بصيغة مفتاح/قيمة:

backend name {
    .attribute1 = value;
    .attribute2 = value;
    [...]
}

إذا كانت هناك واجهة خلفية باسم default، فسيتم استخدامها ما لم يتم تحديد واجهة خلفية أخرى بشكل صريح. إذا لم يكن هناك واجهة خلفية باسم default، فإن أول واجهة خلفية في برنامج VCL تصبح الافتراضية.

إذا كنت تستخدم فقط واجهات خلفية ديناميكية يتم إنشاؤها بواسطة VMODs، فيمكن تحديد واجهة خلفية فارغة تفشل دائمًا (503):

backend default none;

يجب تحديد الواجهة الخلفية إما بـ .host أو بـ .path، وليس كلاهما. لجميع السمات الأخرى قيم افتراضية.

السمة .HOST

لتحديد واجهة خلفية شبكية، يأخذ .host إما عنوان IPv4/IPv6 رقمي أو اسم نطاق يحل إلى عنوان IPv4 واحد و/أو عنوان IPv6 واحد على الأكثر:

.host = "127.0.0.1";
.host = "[::1]:8080";
.host = "example.com:8081";
.host = "example.com:http";

السمة .PORT

يمكن تحديد رقم منفذ TCP أو اسم خدمة كجزء من .host كما هو موضح أعلاه أو بشكل منفصل باستخدام السمة .port:

.port = "8081";
.port = "http";

السمة .PATH

المسار المطلق لمقبس مجال Unix(4) لواجهة خلفية محلية:

.path = "/var/run/http.sock";

أو، حيثما كان متاحًا، @ متبوعًا باسم مقبس مجرد لواجهة خلفية محلية:

.path = "@mybackend";

سيتم إصدار تحذير إذا لم يكن مقبس uds موجودًا عند تحميل VCL. هذا يجعل من الممكن بدء العملية التي تستمع إلى UDS، أو ضبط أذونات ملف المقبس لاحقًا.

إذا لم يكن مقبس uds موجودًا أو منعت الأذونات الوصول، فستفشل محاولات الاتصال.

السمة .HOST_HEADER

رأس مضيف لإضافته إلى الاستطلاعات وطلبات الواجهة الخلفية العادية إذا لم يكن لديها مثل هذا الرأس:

.host_header = "example.com";

سمات المهلة

تتحكم هذه السمات في مدى صبر varnishd أثناء جلب الواجهات الخلفية:

.connect_timeout = 1.4s;
.first_byte_timeout = 20s;
.between_bytes_timeout = 10s;

تأتي القيم الافتراضية من معلمات بنفس الأسماء، راجع varnishd(1).

السمة .MAX_CONNECTIONS

حد أقصى لعدد الاتصالات المتزامنة التي يمكن لـ varnish فتحها إلى الواجهة الخلفية:

.max_connections = 1000;

السمة .WAIT_LIMIT

الحد الأقصى لعدد المعاملات التي يمكن أن تنتظر في قائمة الانتظار للحصول على اتصال واجهة خلفية متاح:

.wait_limit = 1000;

لاحظ أن هذه الميزة يجب استخدامها بحذر، لأنها يمكن أن تتسبب في تراكم الخيوط وزيادة أوقات الاستجابة.

الافتراضي هو معلمة backend_wait_limit الخاصة بـ varnishd(1).

السمة .WAIT_TIMEOUT

عندما ينتظر المعامل في قائمة الانتظار للحصول على اتصال واجهة خلفية ليصبح متاحًا (انظر .wait_limit)، فهذا هو الوقت الذي سينتظره المعامل قبل التخلي:

.wait_timeout = 1s;

ينصح بشدة بعدم تعيين هذا أعلى من بضع ثوان.

الافتراضي هو معلمة backend_wait_timeout الخاصة بـ varnishd(1).

السمة .PROXY_HEADER

إرسال رأس PROXY protocol إلى الواجهة الخلفية مع قيم client.ip و server.ip:

.proxy_header = 2;

القيم القانونية هي واحد واثنان، اعتمادًا على إصدار PROXY protocol الذي تريده.

ملاحظة سيؤدي هذا الإعداد إلى استخدام اتصالات الواجهة الخلفية لطلب واحد فقط (يخضع لتحسينات مستقبلية). وبالتالي، يجب اتخاذ عناية إضافية لتجنب مواجهة اتصالات الواجهة الخلفية الفاشلة مع EADDRNOTAVAIL بسبب عدم توفر منافذ محلية. الخيارات الممكنة هي:

  • استخدام اتصالات واجهة خلفية إضافية لعناوين IP أو منافذ TCP إضافية
  • زيادة عدد المنافذ المتاحة (sysctl Linux net.ipv4.ip_local_port_range)
  • إعادة استخدام منافذ اتصال الواجهة الخلفية مبكرًا (sysctl Linux net.ipv4.tcp_tw_reuse)

السمة .PREAMBLE

إرسال BLOB على جميع الاتصالات المفتوحة حديثًا إلى الواجهة الخلفية:

.preamble = :SGVsbG8gV29ybGRcbgo=:;

السمة .VIA

اسم وكيل آخر (proxy) عبره يتم إجراء الاتصال بالواجهة الخلفية المستهدفة باستخدام بروتوكول PROXY2، على سبيل المثال:

backend proxy {
  .path = "/path/to/proxy2_endpoint";
}
backend destination {
  .host = "1.2.3.4";
  .via = proxy;
}

يمكن للواجهة الخلفية proxy أيضًا استخدام تعريف .host/.port بدلاً من .path.

استخدام السمة .path للواجهة الخلفية المستهدفة غير مدعوم.

السمة .via غير مرتبطة بـ .proxy_header. إذا تم استخدام كليهما، يتم إرسال رأس ثانٍ وفقًا لمواصفات .proxy_header.

ما لم يتم تحديده للوجهة destination، يتم نسخ سمات connect_timeout و first_byte_timeout و between_bytes_timeout من proxy إلى destination.

حتى هذا الإصدار، لا يمكن أن تكون الواجهة الخلفية proxy المستخدمة مع .via موجهة، لا يمكنها استخدام .via بنفسها (خطأ: لا يمكن تكديس الواجهات الخلفية .via) والبروتوكول ثابت على PROXY2.

تفصيل التنفيذ:

إذا تم استخدام .via = <proxy>، فسيتم إنشاء بادئة PROXY2 بمعلومات عنوان الواجهة الخلفية المستهدفة كـ dst_addr/dst_port، وربما سمات TLV أخرى. ثم يتم إجراء الاتصال بنقطة نهاية الواجهة الخلفية proxy (path أو host/port). هذا يعادل تقنيًا تحديد backend destination_via_proxy مع سمة .preamble تحتوي على بادئة PROXY2 المناسبة للواجهة الخلفية المستهدفة.

السمة .AUTHORITY

صلاحية HTTP المستخدمة عند الاتصال بهذه الواجهة الخلفية. إذا لم يتم تعيينها، يتم استخدام .host_header أو .host.

.authority = "" يُعطل إرسال صلاحية.

.authority لا يمكن أن تكون عنوان IP.

نقطتان رأسيتان وأي شيء يليهما (مما يشير إلى منفذ) هو
