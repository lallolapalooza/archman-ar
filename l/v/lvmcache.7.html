dm-writecache حجم الكتلة

يمكن أن يكون حجم كتلة dm-writecache 4096 بايت (الافتراضي)، أو 512 بايت. الافتراضي 4096 يوفر أداءً أفضل ويجب استخدامه إلا عند الضرورة القصوى لـ 512 للتوافق. يتم تحديد حجم كتلة dm-writecache باستخدام --cachesettings block_size=4096|512 عند بدء التخزين المؤقت.

عندما يكون هناك نظام ملفات مثل xfs موجودًا بالفعل على LV الرئيسي قبل التخزين المؤقت، وكان نظام الملفات يستخدم حجم كتلة 512 بايت، فيجب ضبط حجم كتلة writecache على 512. (من المحتمل أن يفشل نظام الملفات في التحميل إذا تم استخدام حجم كتلة writecache 4096 في هذه الحالة).

تحقق من حجم قطاع xfs أثناء تحميل نظام الملفات:

# xfs_info /dev/vg/main
ابحث عن sectsz=512 أو sectsz=4096

يجب اختيار حجم كتلة writecache ليتطابق مع قيمة xfs sectsz.

من الممكن أيضًا تحديد حجم قطاع 4096 لـ mkfs.xfs عند إنشاء نظام الملفات. في هذه الحالة، يمكن استخدام حجم كتلة writecache 4096.

يتم عرض حجم كتلة writecache بواسطة الأمر:

# lvs -o writecacheblocksize VG/LV

dm-writecache استخدام الذاكرة

يمكن أن يكون مقدار ذاكرة النظام الرئيسية المستخدمة بواسطة dm-writecache عاملاً عند اختيار حجم ذاكرة التخزين المؤقت writecache وحجم كتلة writecache.

•
حجم كتلة writecache 4096: كل 100 جيجابايت من ذاكرة التخزين المؤقت writecache تستهلك أكثر بقليل من 2 جيجابايت من ذاكرة النظام.
•
حجم كتلة writecache 512: كل 100 جيجابايت من ذاكرة التخزين المؤقت writecache تستهلك أكثر بقليل من 16 جيجابايت من ذاكرة النظام.

dm-writecache الإعدادات

لتحديد إعدادات dm-writecache القابلة للضبط في سطر الأوامر، استخدم:


--cachesettings 'option=N' أو
--cachesettings 'option1=N option2=N ...'

على سبيل المثال، --cachesettings 'high_watermark=90 writeback_jobs=4'.

لتضمين الإعدادات عند بدء التخزين المؤقت، قم بتشغيل:

# lvconvert --type writecache --cachevol fast \
	--cachesettings 'option=N' vg/main

لتغيير الإعدادات لوحدة LV للتخزين المؤقت writecache موجودة، قم بتشغيل:

# lvchange --cachesettings 'option=N' vg/main

لمسح جميع الإعدادات التي تم تطبيقها، قم بتشغيل:

# lvchange --cachesettings '' vg/main

لعرض الإعدادات المطبقة على وحدة LV للتخزين المؤقت writecache، قم بتشغيل:

# lvs -o cachesettings vg/main

الإعدادات القابلة للضبط هي:

high_watermark = <نسبة>
ابدأ الكتابة الاحتياطية عندما يصل استخدام ذاكرة التخزين المؤقت writecache إلى هذه النسبة (0-100).
low_watermark = <نسبة>
توقف عن الكتابة الاحتياطية عندما يصل استخدام ذاكرة التخزين المؤقت writecache إلى هذه النسبة (0-100).
writeback_jobs = <عدد>
حدد عدد الكتل التي قيد التنفيذ أثناء الكتابة الاحتياطية. يؤدي ضبط هذه القيمة إلى تقليل إنتاجية الكتابة الاحتياطية، ولكنه قد يحسن زمن انتقال طلبات القراءة.
autocommit_blocks = <عدد>
عندما تكتب التطبيقات هذه الكمية من الكتل دون إصدار طلب FLUSH، يتم تثبيت الكتل تلقائيًا.
autocommit_time = <مللي ثانية>
يتم تثبيت البيانات تلقائيًا إذا مرت هذه المدة الزمنية ولم يتم استلام طلب FLUSH.
fua = 0|1
استخدم علامة FUA عند كتابة البيانات من الذاكرة المستمرة مرة أخرى إلى الجهاز الأساسي. ينطبق فقط على الذاكرة المستمرة.
nofua = 0|1
لا تستخدم علامة FUA عند إعادة كتابة البيانات وأرسل طلب FLUSH بعد ذلك. قد تعمل بعض الأجهزة الأساسية بشكل أفضل مع fua، وبعضها مع nofua. يلزم إجراء اختبار لتحديد أي منها. ينطبق فقط على الذاكرة المستمرة.
cleaner = 0|1
يؤدي تعيين cleaner=1 إلى تمكين وضع منظف writecache الذي يتم فيه مسح البيانات تدريجيًا من ذاكرة التخزين المؤقت. إذا تم ذلك قبل فصل writecache، فسيكون لدى أمر splitcache القليل من عمليات المسح لتنفيذها أو لن يكون لديه أي عمليات. إذا لم يتم ذلك مسبقًا، فإن أمر splitcache يتيح وضع المنظف وينتظر حتى تكتمل عملية المسح قبل فصل writecache. سيؤدي إضافة cleaner=0 إلى أمر splitcache إلى تخطي وضع المنظف، ويتم إجراء أي عمليات مسح مطلوبة في وضع تعليق الجهاز.
max_age = <مللي ثانية>
يحدد الحد الأقصى لعمر الكتلة بالمللي ثانية. إذا تم تخزين كتلة في ذاكرة التخزين المؤقت لفترة طويلة جدًا، فسيتم كتابتها إلى الجهاز الأساسي وتنظيفها.
metadata_only = 0|1
فقط البيانات الوصفية هي التي يتم ترقيتها إلى ذاكرة التخزين المؤقت. يحسن هذا الخيار الأداء للأعباء الثقيلة من REQ_META.
pause_writeback = <مللي ثانية>
إيقاف الكتابة الاحتياطية مؤقتًا إذا كان هناك بعض إدخال / إخراج الكتابة المعاد توجيهه إلى وحدة LV الأصلية خلال عدد المللي ثانية الأخير.

dm-writecache استخدام ملفات تعريف البيانات الوصفية

بالإضافة إلى تحديد إعدادات writecache في سطر الأوامر، يمكن أيضًا تعيينها في lvm.conf(5)، أو في ملف تعريف، باستخدام بنية التكوين allocation/cache_settings/writecache الموضحة أدناه.

من الممكن إعداد عدد من ملفات التعريف المختلفة في الدليل /etc/lvm/profile وتحديد اسم ملف التعريف عند بدء writecache.

مثال

# cat <<EOF > /etc/lvm/profile/cache_writecache.profile
allocation {
cache_settings {
writecache {
high_watermark=60
writeback_jobs=1024
}
}
}
EOF
# lvcreate -an -L10G --name fast vg /dev/fast_ssd
# lvcreate --type writecache -L10G --name main  --cachevol fast \
   --metadataprofile cache_writecache vg /dev/slow_hdd

dm-cache مع وحدات LV منفصلة للبيانات والبيانات الوصفية

الطريقة المفضلة لاستخدام dm-cache هي وضع بيانات التعريف للتخزين المؤقت وبيانات التخزين المؤقت على وحدات LV منفصلة. للقيام بذلك، يتم إنشاء "مجمع تخزين مؤقت" (cache pool)، وهو وحدة LV خاصة تشير إلى وحدتي LV فرعيتين، واحدة للبيانات والأخرى للبيانات الوصفية.

لإنشاء مجمع تخزين مؤقت بحجم بيانات معين والسماح لـ lvm2 بحساب حجم البيانات الوصفية المناسب:

# lvcreate --type cache-pool -L DataSize -n fast vg /dev/fast_ssd1

لإنشاء مجمع تخزين مؤقت من وحدة LV منفصلة والسماح لـ lvm2 بحساب حجم البيانات الوصفية للتخزين المؤقت المناسب:

# lvcreate -n fast -L DataSize vg /dev/fast_ssd1
# lvconvert --type cache-pool vg/fast /dev/fast_ssd1

لإنشاء مجمع تخزين مؤقت من وحدتي LV منفصلتين:

# lvcreate -n fast -L DataSize vg /dev/fast_ssd1
# lvcreate -n fastmeta -L MetadataSize vg /dev/fast_ssd2
# lvconvert --type cache-pool --poolmetadata fastmeta vg/fast

ثم استخدم وحدة LV لمجمع التخزين المؤقت لبدء تخزين وحدة LV الرئيسية مؤقتًا:

# lvconvert --type cache --cachepool fast vg/main

يتم إنشاء مجموعة تخزين مؤقت تلقائيًا عند بدء التخزين المؤقت كاختلاف من نفس الإجراء. للقيام بذلك، استخدم وحدة LV قياسية كـ --cachepool (ستحتوي هذه على بيانات ذاكرة التخزين المؤقت)، واستخدم وحدة LV قياسية أخرى كـ --poolmetadata (ستحتوي هذه على بيانات تعريف ذاكرة التخزين المؤقت). سيقوم LVM بإنشاء وحدة LV لمجمع التخزين المؤقت من وحدتي LV المحددتين، واستخدام مجمع التخزين المؤقت لبدء تخزين وحدة LV الرئيسية مؤقتًا.

# lvcreate -n fast -L DataSize vg /dev/fast_ssd1
# lvcreate -n fastmeta -L MetadataSize vg /dev/fast_ssd2
# lvconvert --type cache --cachepool fast \
        --poolmetadata fastmeta vg/main

dm-cache أوضاع التخزين المؤقت

وضع التخزين المؤقت الافتراضي لـ dm-cache هو "writethrough". يضمن writethrough أن أي بيانات تتم كتابتها سيتم تخزينها في ذاكرة التخزين المؤقت وعلى وحدة LV الأصلية. في هذه الحالة، فإن فقدان جهاز مرتبط بذاكرة التخزين المؤقت لن يعني فقدان أي بيانات.

وضع تخزين مؤقت ثانٍ هو "writeback". يؤخر writeback كتابة كتل البيانات من ذاكرة التخزين المؤقت مرة أخرى إلى وحدة LV الأصلية. سيزيد هذا الوضع من الأداء، ولكن فقدان جهاز ذاكرة التخزين المؤقت يمكن أن يؤدي إلى فقدان البيانات.

باستخدام الخيار --cachemode، يمكن تعيين وضع التخزين المؤقت عند بدء التخزين المؤقت، أو تغييره على وحدة LV تم تخزينها مؤقتًا بالفعل. يمكن عرض وضع التخزين المؤقت الحالي باستخدام خيار الإبلاغ cache_mode:

# lvs -o+cache_mode VG/LV

lvm.conf(5) allocation/cache_mode – يحدد وضع التخزين المؤقت الافتراضي.

# lvconvert --type cache --cachemode writethrough \
        --cachepool fast vg/main
# lvconvert --type cache --cachemode writethrough \
        --cachevol fast vg/main

dm-cache حجم القطعة

يمكن تحديد حجم كتل البيانات التي تديرها dm-cache باستخدام الخيار --chunksize عند بدء التخزين المؤقت. الوحدة الافتراضية هي KiB. يجب أن تكون القيمة مضاعفًا لـ 32 KiB بين 32 KiB و 1 GiB. يجب استخدام قطع ذاكرة التخزين المؤقت الأكبر من 512KiB فقط عند الضرورة.

يمكن أن يؤدي استخدام حجم قطعة كبير جدًا إلى استخدام غير فعال لذاكرة التخزين المؤقت، حيث تتسبب عمليات القراءة والكتابة الصغيرة في تخزين أقسام كبيرة من وحدة LV في ذاكرة التخزين المؤقت. يمكن أن يتطلب أيضًا زيادة عتبة الترحيل التي تساوي افتراضيًا 2048 قطاعًا (1 MiB). تضمن Lvm2 أن عتبة الترحيل بحجم 8 قطع على الأقل. قد يؤدي هذا في بعض الحالات إلى حمل كبير جدًا على النطاق الترددي لنقل البيانات بين وحدة LV لذاكرة التخزين المؤقت ووحدة LV الأصلية لذاكرة التخزين المؤقت. ومع ذلك، فإن اختيار حجم قطعة صغير جدًا يمكن أن يؤدي إلى المزيد من الحمل الزائد في محاولة إدارة القطع العديدة التي يتم تعيينها في ذاكرة التخزين المؤقت. يمكن أن يشمل الحمل الزائد كلاً من وقت وحدة المعالجة المركزية المفرط في البحث عن القطع، والذاكرة المفرطة في تتبع القطع.

الأمر لعرض حجم القطعة:

# lvs -o+chunksize VG/LV

NAME

lvmcache.7

dm-cache target support

DESCRIPTION

This man page describes the dm-cache target support in the Linux Device Mapper (dm) subsystem, used by LVM2.

dm-cache is a general-purpose caching device target. It can be used to cache a block device (the "origin" device) with another block device (the "cache" device). Caching improves performance by serving read/write requests from the faster cache device instead of the slower origin device.

dm-cache uses a separate block device for metadata (the "metadata" device). This metadata device stores information about which blocks are cached, dirty blocks, and other metadata required by the cache policy.

The dm-cache target requires three block devices:

  • Origin device: The slower, larger device that is being cached. This can be a logical volume, a physical volume, a partition, or any other block device.
  • Cache device: The faster, smaller device used for caching. This can also be a logical volume, physical volume, partition, or block device.
  • Metadata device: A small device used to store dm-cache metadata. This can also be a logical volume, physical volume, partition, or block device.

The cache device and metadata device are typically combined into a single LVM thin pool when using LVM tools.

USAGE

dm-cache functionality is typically accessed through LVM commands like lvcreate(8), lvconvert(8), and lvchange(8).

When using LVM2, a cache pool is created using a thin pool. The thin pool contains both the data for the cache and the metadata for the cache. You can specify the size of the cache pool and the metadata pool separately.

Basic LVM cache creation:

# lvcreate -L <size> -n main_lv vg_name /dev/slow_device
# lvcreate -L <size> -n cache_pool_lv vg_name /dev/fast_device
# lvconvert --type cache --poolmetadata cache_pool_lv vg_name/main_lv

A more common LVM approach is to create a cache pool which includes both data and metadata LVs:

# lvcreate -L <origin_size> -n origin_lv vg_name /dev/slow_device
# lvcreate -L <cache_data_size> -n cache_data_lv vg_name /dev/fast_device
# lvcreate -L <cache_meta_size> -n cache_meta_lv vg_name /dev/fast_device
# lvconvert --type cache-pool --poolmetadata cache_meta_lv \
	cache_data_lv vg_name/origin_lv

The most convenient way is to use lvcreate(8) with the --cache option:

# lvcreate -L <origin_size> -n origin_lv vg_name /dev/slow_device
# lvcreate --type cache --pool <cache_pool_name> -L <cache_size> \
	vg_name/origin_lv /dev/fast_device

This creates a cache pool logical volume and attaches it to the origin logical volume.

OPTIONS

dm-cache cache mode

The cache mode determines how writes are handled. The available modes are:

  • writeback: Writes are immediately acknowledged to the host after they are written to the cache device. Writes are later flushed to the origin device. This offers the best performance but carries a risk of data loss if the cache device fails before data is flushed.
  • writethrough: Writes are acknowledged to the host only after they are written to both the cache and origin devices. This is slower but safer.
  • writehint: Writes are acknowledged after being written to the cache device. The origin device is updated lazily by background operations. This is a compromise between writeback and writethrough.

The default mode is writeback.

The cache mode can be set using the --cachemode option when creating or converting a cache:

# lvcreate --cachemode writeback ...
# lvconvert --cachemode writethrough ...

It can also be changed on an existing cached LV:

# lvchange --cachemode writehint vg/lv

The current cache mode can be displayed with:

# lvs -o+cache_mode VG/LV

lvm.conf(5) allocation/cache_mode – defines the default cache mode.

dm-cache cache pool chunk size

The cache pool chunk size is the smallest unit of data that dm-cache manages. It must be a power of 2, and can range from 32KiB to 2GiB. Smaller chunk sizes can improve cache hit rates for random I/O, but increase metadata overhead. Larger chunk sizes are better for sequential I/O but can waste space if the cached data is mostly random.

The default chunk size is 64KiB.

The chunk size can be specified with --chunksize option when creating or converting a cache pool:

# lvcreate --chunksize 128K ...
# lvconvert --chunksize 1M ...

The chunk size cannot be changed on an existing cache pool.

Command to display the chunk size:

# lvs -o+chunksize VG/LV

Controls the default chunk size.

The default value is shown by:

# lvmconfig --type default allocation/cache_pool_chunk_size

Checking migration threshold (in sectors) of running cached LV:

# lvs -o+kernel_cache_settings VG/LV

dm-cache cache settings

To set dm-cache cache setting use:

--cachesettings 'option1=N option2=N ...'

To unset/drop cache setting and restore its default kernel value use special keyword 'default' as option parameter:

--cachesettings 'option1=default option2=default ...'

dm-cache migration threshold cache setting

Migrating data between the origin and cache LV uses bandwidth. The user can set a throttle to prevent more than a certain amount of migration occurring at any one time. Currently dm-cache is not taking any account of normal io traffic going to the devices.

User can set migration threshold via cache policy settings as "migration_threshold=<#sectors>" to set the maximum number of sectors being migrated, the default being 2048 sectors (1 MiB) or 8 cache chunks whichever of those two values is larger.

Command to set migration threshold to 2 MiB (4096 sectors):

# lvcreate --cachesettings 'migration_threshold=4096' VG/LV

Command to display the migration threshold:

# lvs -o+kernel_cache_settings,cache_settings VG/LV
# lvs -o+chunksize VG/LV

Command to restore/revert to default value:

# lvchange --cachesettings 'migration_threshold=default' VG/LV

dm-cache cache policy

The dm-cache subsystem has additional per-LV parameters: the cache policy to use, and possibly tunable parameters for the cache policy. Three policies are currently available: "smq" is the default policy, "mq" is an older implementation, and "cleaner" is used to force the cache to write back (flush) all cached writes to the origin LV.

The older "mq" policy has a number of tunable parameters. The defaults are chosen to be suitable for the majority of systems, but in special circumstances, changing the settings can improve performance. Newer kernels however alias this policy with "smq" policy. Cache settings used to configure "mq" policy [random_threshold, sequential_threshold, discard_promote_adjustment, read_promote_adjustment, write_promote_adjustment] are thus silently ignored also performance matches "smq".

With the --cachepolicy and --cachesettings options, the cache policy and settings can be set when caching is started, or changed on an existing cached LV (both options can be used together). The current cache policy and settings can be displayed with the cache_policy and cache_settings reporting options:

# lvs -o+cache_policy,cache_settings VG/LV

Change the cache policy and settings of an existing LV.

# lvchange --cachepolicy mq --cachesettings \
	'migration_threshold=2048 random_threshold=4' vg/main

lvm.conf(5) allocation/cache_policy – defines the default cache policy.

lvm.conf(5) allocation/cache_settings – defines the default cache settings.

dm-cache using metadata profiles

Cache pools allows to set a variety of options. Lots of these settings can be specified in lvm.conf or profile settings. You can prepare a number of different profiles in the /etc/lvm/profile directory and just specify the metadata profile file name when caching LV or creating cache-pool. Check the output of:

# lvmconfig --type default --withcomments

for a detailed description of all individual cache settings.

Example

# cat <<EOF > /etc/lvm/profile/cache_big_chunk.profile
allocation {
cache_pool_metadata_require_separate_pvs=0
cache_pool_chunk_size=512
cache_metadata_format=2
cache_mode="writethrough"
cache_policy="smq"
cache_settings {
smq {
migration_threshold=8192
}
}
}
EOF
# lvcreate --cache -L10G --metadataprofile cache_big_chunk vg/main \
        /dev/fast_ssd
# lvcreate --cache -L10G vg/main --config \
        'allocation/cache_pool_chunk_size=512' /dev/fast_ssd

dm-cache spare metadata LV

See lvmthin(7) for a description of the "pool metadata spare" LV. The same concept is used for cache pools.

dm-cache metadata formats

There are two disk formats for dm-cache metadata. The metadata format can be specified with --cachemetadataformat when caching is started, and cannot be changed. Format 2 has better performance; it is more compact, and stores dirty bits in a separate btree, which improves the speed of shutting down the cache. With auto, lvm selects the best option provided by the current dm-cache kernel module.

RAID1 cache device

RAID1 can be used to create the fast LV holding the cache so that it can tolerate a device failure. (When using dm-cache with separate data and metadata LVs, each of the sub-LVs can use RAID1.)

# lvcreate -n main -L Size vg /dev/slow
# lvcreate --type raid1 -m 1 -n fast -L Size vg /dev/ssd1 /dev/ssd2
# lvconvert --type cache --cachevol fast vg/main

dm-cache command shortcut

A single command can be used to cache main LV with automatic creation of a cache-pool:

# lvcreate --cache --size CacheDataSize VG/LV [FastPVs]

or the longer variant

# lvcreate --type cache --size CacheDataSize \
        --name NameCachePool VG/LV [FastPVs]

In this command, the specified LV already exists, and is the main LV to be cached. The command creates a new cache pool with size and given name or the name is automatically selected from a sequence lvolX_cpool, using the optionally specified fast PV(s) (typically an ssd). Then it attaches the new cache pool to the existing main LV to begin caching.

(Note: ensure that the specified main LV is a standard LV. If a cache pool LV is mistakenly specified, then the command does something different.)

(Note: the type option is interpreted differently by this command than by normal lvcreate commands in which --type specifies the type of the newly created LV. In this case, an LV with type cache-pool is being created, and the existing main LV is being converted to type cache.)
