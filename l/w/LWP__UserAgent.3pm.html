LWP__UserAgent(3pm)

الحزمة: perl-libwww

التراخيص: GPL-1.0-or-later OR Artistic-1.0-Perl

LWP::UserAgent(3) وثائق Perl المساهم بها من قبل المستخدم LWP::UserAgent(3)

الاسم

LWP::UserAgent - فئة وكيل المستخدم للويب

الملخص

use strict;
use warnings;
use LWP::UserAgent ();
my $ua = LWP::UserAgent->new(timeout => 10);
$ua->env_proxy;
my $response = $ua->get('http://example.com');
if ($response->is_success) {
    print $response->decoded_content;
}
else {
    die $response->status_line;
}

طبقات إضافية من الأمان (لاحظ "cookie_jar" و "protocols_allowed"):

use strict;
use warnings;
use HTTP::CookieJar::LWP ();
use LWP::UserAgent       ();
my $jar = HTTP::CookieJar::LWP->new;
my $ua  = LWP::UserAgent->new(
    cookie_jar        => $jar,
    protocols_allowed => ['http', 'https'],
    timeout           => 10,
);
$ua->env_proxy;
my $response = $ua->get('http://example.com');
if ($response->is_success) {
    print $response->decoded_content;
}
else {
    die $response->status_line;
}

الوصف

LWP::UserAgent هي فئة تنفذ وكيل مستخدم ويب. يمكن استخدام كائنات LWP::UserAgent لإرسال طلبات الويب.

في الاستخدام العادي، ينشئ التطبيق كائن LWP::UserAgent، ثم يقوم بتكوينه بقيم للمهلات، الوكلاء، الاسم، إلخ. ثم يقوم بإنشاء نسخة من HTTP::Request للطلب الذي يحتاج إلى تنفيذه. يتم بعد ذلك تمرير هذا الطلب إلى إحدى طرق الطلب في UserAgent، والتي ترسلها باستخدام البروتوكول المناسب، وتعيد كائن HTTP::Response. توجد طرق مساعدة لإرسال أنواع الطلبات الأكثر شيوعًا: "get" في LWP::UserAgent، "head" في LWP::UserAgent، "post" في LWP::UserAgent، "put" في LWP::UserAgent و "delete" في LWP::UserAgent. عند استخدام هذه الطرق، يتم إخفاء إنشاء كائن الطلب كما هو موضح في الملخص أعلاه.

النهج الأساسي للمكتبة هو استخدام الاتصال بأسلوب HTTP لجميع مخططات البروتوكولات. هذا يعني أنك ستقوم بإنشاء كائنات HTTP::Request وتلقي كائنات HTTP::Response حتى للموارد غير HTTP مثل gopher و ftp. لتحقيق تشابه أكبر مع الاتصالات بأسلوب HTTP، يتم تحويل قوائم gopher ودلائل الملفات إلى مستندات HTML.

طرق المنشئ

طرق المنشئ التالية متاحة:

clone

my $ua2 = $ua->clone;

يعيد نسخة من كائن LWP::UserAgent.

تحذير: يرجى العلم أن طريقة النسخ لا تنسخ أو تستنسخ سمة "cookie_jar" الخاصة بك. نظرًا للقيود المحدودة على ما يمكن استخدامه لـ cookie_jar الخاص بك، لا توجد طريقة لنسخ السمة. ستكون سمة "cookie_jar" "undef" في نسخة الكائن الجديد.

new

my $ua = LWP::UserAgent->new( %options )

تقوم هذه الطريقة بإنشاء كائن LWP::UserAgent جديد وتعيده. يمكن توفير وسائط مفتاح/قيمة لضبط الحالة الأولية. الخيارات التالية تتوافق مع طرق السمات الموصوفة أدناه:

KEY                     DEFAULT
-----------             --------------------
agent                   "libwww-perl/#.###"
conn_cache              undef
cookie_jar              undef
cookie_jar_class        HTTP::Cookies
default_headers         HTTP::Headers->new
from                    undef
local_address           undef
max_redirect            7
max_size                undef
no_proxy                []
parse_head              1
protocols_allowed       undef
protocols_forbidden     undef
proxy                   {}
requests_redirectable   ['GET', 'HEAD']
send_te                 1
show_progress           undef
ssl_opts                { verify_hostname => 1 }
timeout                 180

تُقبل الوسائط الإضافية التالية أيضًا: إذا تم تمرير الوسيط "env_proxy" بقيمة صحيحة، يتم قراءة إعدادات الوكيل من متغيرات البيئة (راجع "env_proxy" في LWP::UserAgent). إذا لم يتم توفير "env_proxy"، فإن متغير البيئة "PERL_LWP_ENV_PROXY" يتحكم فيما إذا كان "env_proxy" في LWP::UserAgent يتم استدعاؤه أثناء التهيئة. إذا كانت قيمة الوسيط "keep_alive" محددة وغير صفرية، فإن "LWP::ConnCache" يتم إعداده (راجع "conn_cache" في LWP::UserAgent). يتم تمرير قيمة "keep_alive" كـ "total_capacity" لذاكرة التخزين المؤقت للاتصال.

"proxy" يجب تعيينها كـ arrayref من أزواج المفاتيح/القيم. "no_proxy" تأخذ arrayref من النطاقات.

السمات

تقوم إعدادات سمات التكوين بتعديل سلوك LWP::UserAgent عند إرسال الطلبات. يمكن أيضًا تهيئة معظم هذه السمات بواسطة الوسائط المقدمة لطريقة المنشئ.

السمات التالية موفرة. تظل قيمة السمة دون تغيير إذا لم يتم تقديم وسيط. القيمة المرتجعة من كل طريقة هي قيمة السمة القديمة.

agent

my $agent = $ua->agent;
$ua->agent('Checkbot/0.4 ');    # إضافة الافتراضي إلى النهاية
$ua->agent('Mozilla/5.0');
$ua->agent("");                 # عدم التعريف

الحصول/تعيين رمز المنتج المستخدم لتحديد وكيل المستخدم على الشبكة. يتم إرسال قيمة الوكيل كرأس "User-Agent" في الطلبات.

الافتراضي هو سلسلة من النموذج "libwww-perl/#.###"، حيث يتم استبدال "#.###" برقم إصدار هذه المكتبة.

إذا كانت السلسلة المقدمة تنتهي بمسافة، يتم إلحاق السلسلة الافتراضية "libwww-perl/#.###" بها.

يجب أن يكون سلسلة وكيل المستخدم معرف منتج بسيط أو أكثر مع رقم إصدار اختياري مفصول بـ "/".

conn_cache

my $cache_obj = $ua->conn_cache;
$ua->conn_cache( $cache_obj );

الحصول/تعيين كائن LWP::ConnCache للاستخدام. راجع LWP::ConnCache للتفاصيل.

cookie_jar

my $jar = $ua->cookie_jar;
$ua->cookie_jar( $cookie_jar_obj );

الحصول/تعيين كائن cookie jar للاستخدام. المتطلب الوحيد هو أن كائن cookie jar يجب أن ينفذ طرق extract_cookies($response) و add_cookie_header($request). سيتم استدعاء هذه الطرق بواسطة وكيل المستخدم عند إرسال الطلبات واستقبال الاستجابات. عادةً ما يكون هذا كائن HTTP::Cookies أو بعض الفئات الفرعية. ومع ذلك، يُشجعك على استخدام HTTP::CookieJar::LWP بدلاً من ذلك. راجع "أفضل الممارسات" لمزيد من المعلومات.

use HTTP::CookieJar::LWP ();
my $jar = HTTP::CookieJar::LWP->new;
my $ua = LWP::UserAgent->new( cookie_jar => $jar );
# أو بعد إنشاء الكائن
$ua->cookie_jar( $cookie_jar );

الافتراضي هو عدم وجود cookie jar، أي عدم إضافة رؤوس "Cookie" تلقائيًا إلى الطلبات.

إذا احتوى $jar على مرجع تجزئة غير مصقول، يتم إنشاء كائن cookie jar جديد لك تلقائيًا. الكائن من الفئة المعينة باستخدام وسيط المنشئ "cookie_jar_class"، والذي يفتراضي إلى HTTP::Cookies.

$ua->cookie_jar({ file => "$ENV{HOME}/.cookies.txt" });

هو في الواقع مجرد اختصار لـ:

require HTTP::Cookies;
$ua->cookie_jar(HTTP::Cookies->new(file => "$ENV{HOME}/.cookies.txt"));

كما هو موضح أعلاه وفي "أفضل الممارسات"، يجب عليك تعيين "cookie_jar_class" إلى "HTTP::CookieJar::LWP" للحصول على cookie jar أكثر أمانًا.

my $ua = LWP::UserAgent->new( cookie_jar_class => 'HTTP::CookieJar::LWP' );
$ua->cookie_jar({}); # HTTP::CookieJar::LWP لا يأخذ وسائط

يمكن دمج هذه أيضًا في المنشئ، لذا

هذا الموقع غير مرتبط بـ Arch Linux ولا تابع له بأي شكل من الأشكال. المحتوى هو ترجمة فقط لصفحات دليل Arch المنشورة على man.archlinux.org.

delete( $url, $field_name => $value, ... );

هذه الطريقة ستقوم بإرسال طلب "DELETE" على عنوان URL المعطى. رؤوس إضافية وخيارات المحتوى هي نفسها كما في طريقة "get" في LWP::UserAgent.

ستستخدم هذه الطريقة دالة DELETE() من HTTP::Request::Common لبناء الطلب. انظر HTTP::Request::Common للحصول على تفاصيل حول كيفية تمرير محتوى النماذج والميزات المتقدمة الأخرى.

get

my $res = $ua->get( $url );
my $res = $ua->get( $url , $field_name => $value, ... );

هذه الطريقة ستقوم بإرسال طلب "GET" على عنوان URL المعطى. يمكن تقديم وسيطات إضافية لتهيئة رؤوس الطلب. يتم تقديمها كأزواج اسم/قيمة منفصلة. القيمة المرجعة هي كائن استجابة. انظر HTTP::Response لوصف الواجهة التي يوفرها.

سيظل هناك كائن استجابة يتم إرجاعه عندما لا يمكن لـ LWP الاتصال بالخادم المحدد في عنوان URL أو عند حدوث أعطال أخرى في معالجات البروتوكول. تستخدم هذه الاستجابات الداخلية رموز حالة HTTP القياسية، لذلك لا يمكن تمييز الاستجابات عن طريق اختبار رمز حالة الاستجابة وحده. الاستجابات الخطأ التي ينشئها LWP داخليًا سيكون لديها رأس "Client-Warning" معين إلى القيمة "Internal response". إذا كنت بحاجة إلى التمييز بين هذه الاستجابات الداخلية والاستجابات التي ينشئها خادم بعيد بالفعل، فأنت بحاجة إلى اختبار قيمة هذا الرأس.

أسماء الحقول التي تبدأ بـ ":" مميزة. هذه لن تهيئ رؤوس الطلب ولكنها ستحدد كيفية التعامل مع محتوى الاستجابة. يتم التعرف على أسماء الحقول الخاصة التالية:

':content_file'   => $filename # أو $filehandle
':content_cb'     => \&callback
':read_size_hint' => $bytes

إذا تم توفير $filename أو $filehandle مع الخيار ":content_file"، فسيتم حفظ محتوى الاستجابة هنا بدلاً من كائن الاستجابة. قد يكون $filehandle أيضًا كائنًا له واصف ملف مفتوح، مثل كائن File::Temp. إذا تم توفير رد اتصال مع الخيار ":content_cb"، فسيتم استدعاء هذه الدالة لكل جزء من محتوى الاستجابة عند استلامها من الخادم. إذا لم يتم توفير أي من هذين الخيارين، فسيتراكم محتوى الاستجابة في كائن الاستجابة نفسه. قد لا يكون هذا مناسبًا لأجسام الاستجابة الكبيرة جدًا. يمكن تحديد واحد فقط من ":content_file" أو ":content_cb". يتراكم محتوى الاستجابات غير الناجحة دائمًا في كائن الاستجابة نفسه، بغض النظر عن الخيارات ":content_file" أو ":content_cb" المقدمة. لاحظ أن أخطاء الكتابة إلى ملف المحتوى (على سبيل المثال، بسبب رفض الإذن أو امتلاء نظام الملفات) سيتم الإبلاغ عنها عبر رؤوس الاستجابة "Client-Aborted" أو "X-Died"، وليس طريقة "is_success".

يتم تمرير الخيار ":read_size_hint" إلى وحدة البروتوكول التي ستحاول قراءة البيانات من الخادم في أجزاء بهذا الحجم. سيؤدي حجم أصغر لـ ":read_size_hint" إلى عدد أكبر من استدعاءات رد الاتصال.

يتم استدعاء دالة رد الاتصال بثلاث وسيطات: جزء من البيانات، مرجع إلى كائن الاستجابة، ومرجع إلى كائن البروتوكول. يمكن لرد الاتصال إلغاء الطلب عن طريق استدعاء die(). ستظهر رسالة الاستثناء كرأس "X-Died" في الاستجابة التي يتم إرجاعها بواسطة طريقة "$ua->get()".

head

my $res = $ua->head( $url );
my $res = $ua->head( $url , $field_name => $value, ... );

هذه الطريقة ستقوم بإرسال طلب "HEAD" على عنوان URL المعطى. بخلاف ذلك، تعمل مثل طريقة "get" في LWP::UserAgent الموضحة أعلاه.

is_protocol_supported

my $bool = $ua->is_protocol_supported( $scheme );

يمكنك استخدام هذه الطريقة لاختبار ما إذا كان كائن وكيل المستخدم هذا يدعم "scheme" المحدد. (قد يكون "scheme" سلسلة نصية (مثل "http" أو "ftp") أو قد يكون مرجع كائن URI.)

يتم تحديد ما إذا كان البروتوكول مدعومًا بواسطة قوائم "protocols_allowed" أو "protocols_forbidden" لوكيل المستخدم (إن وجدت)، وقدرات LWP. أي، ستعيد هذه القيمة صحيحة فقط إذا كان LWP يدعم هذا البروتوكول * وكان * مسموحًا به لهذا الكائن المحدد.

is_online

my $bool = $ua->is_online;

يحاول تحديد ما إذا كان لديك وصول إلى الإنترنت. تعيد 1 (صحيح) إذا حددت الاستدلالات المضمنة أن وكيل المستخدم قادر على الوصول إلى الإنترنت (عبر HTTP) أو 0 (خطأ).

انظر أيضًا LWP::Online.

mirror

my $res = $ua->mirror( $url, $filename );

ستحصل هذه الطريقة على المستند المحدد بواسطة عنوان URL وتخزينه في ملف يسمى $filename. إذا كان الملف موجودًا بالفعل، فسيحتوي الطلب على رأس "If-Modified-Since" يطابق وقت تعديل الملف. إذا لم يتغير المستند على الخادم منذ ذلك الوقت، فلن يحدث شيء. إذا تم تحديث المستند، فسيتم تنزيله مرة أخرى. سيتم إجبار وقت تعديل الملف على مطابقة وقت الخادم.

يستخدم "move" في File::Copy لمحاولة استبدال $filename بشكل ذري.

القيمة المرجعة هي كائن HTTP::Response.

تفشل إذا كانت الاستجابة لجلب المستند تحتوي على رأس "X-Died".

patch

# أي إصدار من HTTP::Message يعمل مع هذا الشكل:
my $res = $ua->patch( $url, $field_name => $value, Content => $content );
# استخدام مراجع الهاش أو المصفوفة يتطلب HTTP::Message >= 6.12
use HTTP::Request 6.12;
my $res = $ua->patch( $url, \%form );
my $res = $ua->patch( $url, \@form );
my $res = $ua->patch( $url, \%form, $field_name => $value, ... );
my $res = $ua->patch( $url, $field_name => $value, Content => \%form );
my $res = $ua->patch( $url, $field_name => $value, Content => \@form );

ستقوم هذه الطريقة بإرسال طلب "PATCH" على عنوان URL المعطى، مع توفير %form أو @form أزواج المفتاح/القيمة لمحتوى النموذج. رؤوس إضافية وخيارات المحتوى هي نفسها كما في طريقة "get" في LWP::UserAgent.

تنويه:

يمكن لهذه الطريقة فقط قبول المحتوى الذي يكون في أزواج مفتاح/قيمة عند استخدام HTTP::Request::Common قبل الإصدار 6.12. أي استخدام لمراجع الهاش أو المصفوفة سيؤدي إلى خطأ قبل الإصدار 6.12.

ستستخدم هذه الطريقة دالة "PATCH" من HTTP::Request::Common لبناء الطلب. انظر HTTP::Request::Common للحصول على تفاصيل حول كيفية تمرير محتوى النماذج والميزات المتقدمة الأخرى.
