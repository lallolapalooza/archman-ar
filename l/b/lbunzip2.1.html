lbunzip2(1)

الحزمة: lbzip2

التراخيص: GPL3

LBZIP2(1) أوامر المستخدم LBZIP2(1)

الاسم

lbzip2 - أداة bzip2 متوازية

ملخص

lbzip2|bzip2 [-n WTHRS] [-k|-c|-t] [-d] [-1 .. -9] [-f] [-s] [-u] [-v] [-S] [ FILE ... ]

lbunzip2|bunzip2 [-n WTHRS] [-k|-c|-t] [-z] [-f] [-s] [-u] [-v] [-S] [ FILE ... ]

lbzcat|bzcat [-n WTHRS] [-z] [-f] [-s] [-u] [-v] [-S] [ FILE ... ]

lbzip2|bzip2|lbunzip2|bunzip2|lbzcat|bzcat -h

الوصف

ضغط أو فك ضغط FILE أو المدخل القياسي إلى ملفات عادية أو المخرج القياسي باستخدام خوارزمية ضغط نص Burrows-Wheeler block-sorting. تستخدم الأداة lbzip2 خيوطًا متعددة ومقسم مدخلات محدود حتى عند فك ضغط ملفات .bz2 التي تم إنشاؤها بواسطة bzip2 القياسي.

بشكل عام، يكون الضغط أفضل بكثير مما تحققه الضواغط التقليدية المعتمدة على LZ77/LZ78، وهو تنافسي مع جميع عائلات ضواغط PPM الإحصائية ما عدا الأفضل منها.

يتم دائمًا إجراء الضغط، حتى لو كان الملف المضغوط أكبر قليلاً من الملف الأصلي. أقصى توسع في الحالة السيئة هو للملفات ذات الطول صفر، والتي تتوسع إلى أربعة عشر بايت. يتم ترميز البيانات العشوائية (بما في ذلك مخرجات معظم ضواغط الملفات) بتوسع تقريبي يقارب 0.5٪.

خيارات سطر الأوامر متشابهة عن قصد جدًا مع تلك الخاصة بـ bzip2 و gzip، ولكنها ليست متطابقة.

الاستدعاء

الوضع الافتراضي للتشغيل هو الضغط. إذا تم استدعاء الأداة باسم lbunzip2 أو bunzip2، يتم التبديل إلى وضع فك الضغط. يؤدي استدعاء الأداة باسم lbzcat أو bzcat إلى اختيار فك الضغط، مع كتابة التسلسل الثنائي المفكوك إلى المخرج القياسي.

الخيارات

-n WTHRS
حدد عدد خيوط (فك) الضغط إلى WTHRS. إذا لم يتم تحديد هذا الخيار، تحاول lbzip2 الاستعلام عن النظام لعدد المعالجات المتصلة (إذا كانت بيئة الترجمة وبيئة التنفيذ تدعم ذلك)، أو تخرج بخطأ (إذا لم تتمكن من تحديد عدد المعالجات المتصلة).
-k, --keep
لا تقم بإزالة عوامل FILE بعد (فك) الضغط بنجاح. افتح ملفات الإدخال العادية التي تحتوي على أكثر من رابط واحد.
-c, --stdout
اكتب المخرج إلى المخرج القياسي، حتى عند وجود عوامل FILE. يعني -k ويستبعد -t.
-t, --test
اختبر فك الضغط؛ تجاهل المخرج بدلاً من كتابته إلى الملفات أو المخرج القياسي. يعني -k ويستبعد -c. يعادل تقريبًا تمرير -c وإعادة توجيه المخرج القياسي إلى "سلة المهملات".
-d, --decompress
فرض فك الضغط بدلاً من الوضع المحدد باسم الاستدعاء.
-z, --compress
فرض الضغط بدلاً من الوضع المحدد باسم الاستدعاء.
-1 .. -9
حدد حجم كتلة الضغط إلى 100K .. 900K، بزيادات 100K. يتم تجاهله أثناء فك الضغط. انظر أيضًا قسم حجم الكتلة أدناه.
--fast
اسم مستعار لـ -1.
--best
اسم مستعار لـ -9. هذا هو الافتراضي.
-f, --force
افتح ملفات الإدخال غير العادية. افتح ملفات الإدخال التي تحتوي على أكثر من رابط واحد، وكسر الروابط عندما لا يتم تحديد -k بالإضافة إلى ذلك. حاول إزالة كل ملف مخرج قبل فتحه. افتراضيًا، لن تقوم lbzip2 بالكتابة فوق الملفات الموجودة؛ إذا كنت ترغب في حدوث ذلك، يجب عليك تحديد -f. إذا تم إعطاء -c و -d أيضًا، لا ترفض الملفات التي ليست بتنسيق bzip2، فقط قم بنسخها دون تغيير؛ بدون -f ستتوقف lbzip2 بعد الوصول إلى ملف ليس بتنسيق bzip2.
-s, --small
تقليل استخدام الذاكرة على حساب الأداء.
-u, --sequential
قم بتقسيم كتل الإدخال بشكل متسلسل. قد يؤدي هذا إلى تحسين نسبة الضغط وتقليل استخدام وحدة المعالجة المركزية، ولكنه سيؤدي إلى تدهور قابلية التوسع.
-v, --verbose
كن أكثر تفصيلاً. اطبع معلومات أكثر تفصيلاً حول تقدم (فك) الضغط إلى المخرج القياسي: قبل معالجة كل ملف، اطبع رسالة تفيد بأسماء ملفات الإدخال والمخرج؛ أثناء (فك) الضغط، اطبع نسبة تقريبية للإكمال والوقت المقدر للوصول (فقط إذا كان المخرج القياسي متصلاً بطرفية)؛ بعد معالجة كل ملف اطبع رسالة تظهر نسبة الضغط، وتوفير المساحة، ووقت الضغط الإجمالي (وقت الحائط)، ومتوسط سرعة (فك) الضغط (بايت من البيانات العادية التي تم معالجتها في الثانية).
-S
اطبع إحصائيات متغير الشرط إلى المخرج القياسي لكل عملية (فك) ضغط مكتملة. مفيد في التوصيف.
-q, --quiet, --repetitive-fast, --repetitive-best, --exponential
مقبول للتوافق مع bzip2، يتم تجاهله بخلاف ذلك.
-h, --help
اطبع المساعدة حول استخدام سطر الأوامر على المخرج القياسي واخرج بنجاح.
-L, --license, -V, --version
اطبع معلومات الترخيص والإصدار على المخرج القياسي واخرج بنجاح.

البيئة

LBZIP2, BZIP2, BZIP
قبل تحليل سطر الأوامر، تقوم lbzip2 بإدراج محتويات هذه المتغيرات، بالترتيب المحدد، بين اسم الاستدعاء وبقية سطر الأوامر. يتم فصل الرموز بمسافات وعلامات جدولة، والتي لا يمكن الهروب منها.

عوامل التشغيل

FILE
حدد الملفات لضغطها أو فك ضغطها.

سيتم تخطي الملفات ذات اللاحقة .bz2، .tbz، .tbz2 و .tz2 عند الضغط. عند فك الضغط، سيتم إزالة اللاحقات .bz2 من أسماء ملفات المخرج؛ سيتم استبدال اللاحقات .tbz، .tbz2 و .tz2 بـ .tar؛ سيتم تذييل أسماء الملفات الأخرى بـ .out. إذا تم تسليم إشارة INT أو TERM إلى lbzip2، فإنها تقوم بإزالة ملف المخرج العادي المفتوح حاليًا قبل الخروج.

إذا لم يتم إعطاء أي FILE، فإن lbzip2 تعمل كمرشح، وتعالج المدخل القياسي إلى المخرج القياسي. في هذه الحالة، سترفض lbzip2 الكتابة المضغوطة إلى طرفية (أو قراءة مدخلات مضغوطة من طرفية)، لأن هذا سيكون غير مفهوم تمامًا وبالتالي غير مجدٍ.

حالة الخروج

0
إذا انتهت lbzip2 بنجاح. يفترض هذا أن lbzip2 لا تفشل أبدًا في الكتابة إلى المخرج القياسي متى حاولت.
1
إذا واجهت lbzip2 خطأ فادحًا.
4
إذا أصدرت lbzip2 تحذيرات دون مواجهة خطأ فادح. يفترض هذا أن lbzip2 لا تفشل أبدًا في الكتابة إلى المخرج القياسي متى حاولت.
SIGPIPE, SIGXFSZ
إذا كانت lbzip2 تنوي الخروج بالحالة 1 بسبب أي خطأ فادح، ولكن أي إشارة مماثلة مع إجراء SIG_DFL موروث كانت.

EXIT STATUS

lbzip2 can terminate by way of signals.

SIGABRT
if a runtime assertion fails (i.e. lbzip2 detects a bug in itself). Hopefully whoever compiled your binary wasn't bold enough to #define NDEBUG.
SIGINT, SIGTERM
lbzip2 catches these signals so that it can remove an interrupted output file. In such cases, lbzip2 exits by re-raising (one of) the received signal(s).

If you run lbzip2 as a filter, that is, without specifying an output file, and it terminates by way of one of said signals, then it will clean up any interrupted output file.

Other error conditions result in a non-zero exit status, but not in the termination by way of a signal.

BLOCK SIZE

lbzip2 compresses large files in blocks. It can operate at various block sizes, ranging from 100k to 900k in 100k steps, and it allocates only as much memory as it needs to. The block size affects both the compression ratio achieved, and the amount of memory needed both for compression and decompression. Compression and decompression speed is virtually unaffected by block size, provided that the file being processed is large enough to be split among all worker threads.

The flags -1 through -9 specify the block size to be 100,000 bytes through 900,000 bytes (the default) respectively. At decompression-time, the block size used for compression is read from the compressed file -- the flags -1 to -9 are irrelevant to and so ignored during decompression.

Larger block sizes give rapidly diminishing marginal returns; most of the compression comes from the first two or three hundred k of block size, a fact worth bearing in mind when using lbzip2 on small machines. It is also important to appreciate that the decompression memory requirement is set at compression-time by the choice of block size. In general you should try and use the largest block size memory constraints allow.

Another significant point applies to small files. By design, only one of lbzip2's worker threads can work on a single block. This means that if the number of blocks in the compressed file is less than the number of processors online, then some of worker threads will remain idle for the entire time. Compressing small files with smaller block sizes can therefore significantly increase both compression and decompression speed. The speed difference is more noticeable as the number of CPU cores grows.

ERROR HANDLING

Dealing with error conditions is the least satisfactory aspect of lbzip2. The policy is to try and leave the filesystem in a consistent state, then quit, even if it means not processing some of the files mentioned in the command line.

`A consistent state' means that a file exists either in its compressed or uncompressed form, but not both. This boils down to the rule `delete the output file if an error condition occurs, leaving the input intact'. Input files are only deleted when we can be pretty sure the output file has been written and closed successfully.

RESOURCE ALLOCATION

lbzip2 needs various kinds of system resources to operate. Those include memory, threads, mutexes and condition variables. The policy is to simply give up if a resource allocation failure occurs.

Resource consumption grows linearly with number of worker threads. If lbzip2 fails because of lack of some resources, decreasing number of worker threads may help. It would be possible for lbzip2 to try to reduce number of worker threads (and hence the resource consumption), or to move on to subsequent files in the hope that some might need less resources, but the complications for doing this seem more trouble than they are worth.

DAMAGED FILES

lbzip2 attempts to compress data by performing several non-trivial transformations on it. Every compression of a file implies an assumption that the compressed file can be decompressed to reproduce the original. Great efforts in design, coding and testing have been made to ensure that this program works correctly. However, the complexity of the algorithms, and, in particular, the presence of various special cases in the code which occur with very low but non-zero probability make it very difficult to rule out the possibility of bugs remaining in the program. That is not to say this program is inherently unreliable. Indeed, I very much hope the opposite is true -- lbzip2 has been carefully constructed and extensively tested.

As a self-check for your protection, lbzip2 uses 32-bit CRCs to make sure that the decompressed version of a file is identical to the original. This guards against corruption of the compressed data, and against undiscovered bugs in lbzip2 (hopefully unlikely). The chances of data corruption going undetected is microscopic, about one chance in four billion for each file processed. Be aware, though, that the check occurs upon decompression, so it can only tell you that that something is wrong.

CRCs can only detect corrupted files, they can't help you recover the original, uncompressed data. However, because of the block nature of the compression algorithm, it may be possible to recover some parts of the damaged file, even if some blocks are destroyed.

BUGS

Separate input files don't share worker threads; at most one input file is worked on at any moment.
