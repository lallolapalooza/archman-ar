DESCRIPTION

\n

The sox_add_effect function may have to change the sample\n rate or number of channels to meet the effect's requirements. If it does,\n it modifies the given sox_signal_t structure in to reflect the changes. When this happens, it is the caller's\n responsibility to pass the modified in back into the next\n call to sox_add_effect. This propagation of changes ensures that\n all subsequent effects are aware of the current signal parameters.

\n

The function returns SOX_SUCCESS if the\n effect was successfully added and processed. Otherwise, it indicates an\n error by returning a different status code.

\n
\n
void\n sox_delete_effects_chain(sox_effects_chain_t \n *ecp)
\n
sox_delete_effects_chain() is responsible for cleaning up and\n releasing all resources that were allocated when an effects chain was\n created. This includes deallocating any memory used by the chain and\n closing any associated file handles or streams. Additionally, it deletes\n all the individual effects that were part of the chain.

EXAMPLES

\n

SoX provides skeleton C files, namely skelform.c for\n formats and skeleff.c for effects, to aid developers in creating new\n ones. For new formats, it's often sufficient to handle the file header and\n then utilize the routines provided by raw.c for the actual reading and\n writing of audio data.

\n

The files example0.c and example1.c serve as\n excellent starting points for understanding how to build applications using\n the libsox_ng library. The source code for sox_ng.c itself also\n offers valuable insights and can be used as a reference.

INTERNALS

\n

Internally, SoX processes all audio samples using a signed\n 32-bit integer format. The routines responsible for audio processing operate\n on buffers containing these samples. The buffer sizes provided refer to the\n number of samples, not the number of bytes. When reading from files, format\n handlers are responsible for converting the input samples into this signed\n 32-bit integer format. For instance, data in linear signed byte format is\n left-shifted by 24 bits to achieve this.

\n

Representing audio samples as integers can introduce challenges\n during processing. For example, an effect designed to mix the left and right\n channels into a single monophonic channel might use the straightforward\n calculation:

\n
   *obuf++ = (*ibuf++ + *ibuf++)/2;
\n

This approach can lead to distortion if the intermediate addition\n of the two channel samples exceeds the 32-bit integer limit, causing an\n overflow. An alternative calculation:

\n
   *obuf++ = *ibuf++/2 + *ibuf++/2;
\n

would circumvent the overflow issue but might result in a loss of\n precision due to the loss of the least significant bit.

\n

Stereo audio data is stored sequentially, with the left channel's\n samples followed by the right channel's samples. For quadraphonic audio, the\n order is left front, right front, left rear, and then right rear samples.

\n

FORMATS

\n

A format in SoX is responsible for the conversion between\n audio files and the library's internal audio buffer representation. The\n internal buffer uses signed longs and a fixed sampling rate. Each format\n operates using two primary data structures: a format structure and a private\n structure.

\n

The format structure holds essential audio parameters such as the\n sampling rate, data size (8, 16, or 32 bits), encoding type (e.g., unsigned,\n signed, floating point), and the number of audio channels. It also stores\n state information, including whether the file requires byte-swapping, if\n seeking operations (sox_seek()) are supported, the file's suffix,\n a pointer to the file stream, a pointer to the format structure\n itself, and a pointer to the format's private structure.

\n

The private area is a pre-allocated memory block that the\n format can utilize as needed. It's recommended to define a specific\n data structure for this area and cast the array to that structure. The\n voc.c file provides an example of how to use a private data area.\n For instance, voc.c needs to keep track of the number of samples it\n writes and, upon completion, must reposition the file pointer to the beginning\n to write the header information. While the private area is typically small,\n some effects, like echo, might require larger memory allocations using\n lsx_malloc() for purposes such as delay lines.

\n

A format consists of six key routines:

\n
\n
startread
\n
Initializes the format parameters, reads the audio file's header,\n and performs any other necessary setup operations before reading data.
\n
read
\n
Reads a specified number of samples from the audio file. It transforms\n the read samples into the internal signed long integer format and copies\n them into the provided buffer. The function returns the actual number of\n samples read.
\n
stopread
\n
Performs any cleanup or finalization tasks required after all data has\n been read from the file.
\n
startwrite
\n
Sets up the format parameters for writing audio data. This may include\n writing an initial file header or performing other necessary\n preparations before data can be written.
\n
write
\n
Writes a specified number of samples from a buffer to the audio file.\n It converts the samples from the internal signed long integer format to the\n file's appropriate data format before writing. If it cannot write all\n the requested samples, it returns the number of samples successfully\n written.
\n
stopwrite
\n
Typically used to finalize the audio file, such as writing a complete\n header or performing any other necessary post-writing operations.
\n

EFFECTS

\n

Each effect operates on a single input and a single output stream.\n An effect's implementation is composed of six functions that are invoked in a\n specific sequence, as illustrated by the following flow:

\n
LOOP (invocations with different parameters)\n  getopts\n  LOOP (invocations with the same parameters)\n    LOOP (channels)\n      start\n    LOOP (while there is input audio to process)\n      LOOP (channels)\n        flow\n    LOOP (while there is output audio to generate)\n      LOOP (channels)\n        drain\n    LOOP (channels)\n      stop\n  kill
\n

Functions that an effect does not need to implement can be left\n as NULL. Effects marked as MCHAN do not follow the\n LOOP (channels) structure; instead, they must handle multi-channel\n processing internally within their affected functions. It's also possible for\n multiple instances of the same effect to be processed in parallel.

\n
\n
getopts
\n
This function is called with a list of arguments provided as a character\n string, which are used to configure the effect's behavior.
\n
start
\n
This function is invoked with the signal parameters defining the input\n and output streams. It's responsible for initializing the effect based on\n these parameters.
\n
flow
\n
This function is called with input and output data buffers, along with\n pointers to the input and output data buffer sizes. It processes the data\n from the input buffer and writes the results to the output buffer, updating\n the size variables to reflect the number of samples actually processed.\n The effect is not required to read from the input or write to the output\n in the same call. If this function returns SOX_EOF, it signifies\n that the effect will not read any further input data, allowing the process\n to transition to the drain mode earlier if applicable.
\n
drain
\n
This function is called when there is no more input data available.\n If the effect needs to generate additional output data (e.g., for a delay\n effect fading out), it copies the generated data into the provided buffer\n and returns the number of samples generated. If the buffer is filled,\n this function will be called again. The echo effect, for example,\n uses this mechanism to implement a fading-out behavior.
\n
stop
\n
This function is called when there are no more input samples and no more\n output samples to process. It is typically used to release resources,\n such as memory or temporary files, that were allocated during the\n start phase. The echo.c example demonstrates its usage.
\n
kill
\n
This function is called to allow the release of resources that were\n allocated by the getopts function. The pad.c example shows\n how this function can be implemented.
\n
\n

LINKING

\n

The method for linking against the libsox_ng library depends on how\n SoX was compiled on your system. If it was a static build, you simply link\n against the library file. For a dynamic build, you should use libtool\n to ensure the correct linker flags are used. Consult the libtool\n manual for detailed instructions. A typical usage example is as follows:

\n
   libtool --mode=link gcc -o prog /path/to/libsox_ng.la
