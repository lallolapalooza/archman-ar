libcurl(3)

الحزمة: curl

التراخيص: MIT

libcurl(3) دليل دوال المكتبة libcurl(3)

الاسم

libcurl - عمليات نقل عناوين URL من جانب العميل

الوصف

هذا نظرة عامة موجزة حول كيفية استخدام libcurl في برامج C الخاصة بك. هناك صفحات دليل محددة لكل دالة مذكورة هنا. راجع libcurl-easy(3)، libcurl-multi(3)، libcurl-share(3)، libcurl-url(3)، libcurl-ws(3) و libcurl-tutorial(3) لفهم معمق لكيفية البرمجة باستخدام libcurl.

هناك العديد من الارتباطات المتاحة التي تجلب الوصول إلى libcurl للغتك المفضلة. ابحث في مكان آخر عن وثائق حول هذه.

عمليات النقل

لنقل الملفات، تقوم بإنشاء "مقبض سهل" باستخدام curl_easy_init(3) لنقل فردي واحد (في أي اتجاه). ثم تقوم بتعيين مجموعتك المطلوبة من الخيارات في هذا المقبض باستخدام curl_easy_setopt(3). الخيارات التي تعينها باستخدام curl_easy_setopt(3) تبقى. ثم يتم استخدامها لكل استخدام متكرر لهذا المقبض حتى تقوم إما بتغيير الخيار، أو تقوم بإعادة تعيينها كلها باستخدام curl_easy_reset(3).

لأجل نقل البيانات فعليًا، لديك خيار استخدام واجهة "easy" (سهلة)، أو واجهة "multi" (متعددة).

واجهة "easy" هي واجهة متزامنة تقوم فيها باستدعاء curl_easy_perform(3) وتدعها تقوم بعملية النقل. عندما تكتمل، تعود الدالة ويمكنك المتابعة. مزيد من التفاصيل موجود في صفحة الدليل libcurl-easy(3).

في المقابل، واجهة "multi" هي واجهة غير متزامنة، تقوم باستدعائها وتقوم بتنفيذ جزء صغير فقط من عملية النقل في كل استدعاء. إنها مثالية إذا كنت ترغب في القيام بأشياء أثناء تقدم عملية النقل، أو ما شابه. تسمح واجهة "multi" لك بالاختيار () بناءً على إجراء libcurl، وحتى لتنزيل ملفات متعددة بسهولة في وقت واحد باستخدام خيط واحد. انظر المزيد من التفاصيل في صفحة الدليل libcurl-multi(3).

واجهات الدعم

هناك أيضًا سلسلة من الدوال والمجموعات المفيدة الأخرى للاستخدام، بما في ذلك:

curl_version_info()
يحصل على معلومات مفصلة حول إصدار libcurl (والمكتبات الأخرى المستخدمة). انظر curl_version_info(3)
curl_getdate()
يحول سلسلة تاريخ إلى time_t. انظر curl_getdate(3)
curl_easy_getinfo()
يحصل على معلومات حول عملية نقل تم إجراؤها. انظر curl_easy_getinfo(3)
curl_mime_addpart()
يساعد في بناء نموذج POST لـ HTTP. انظر curl_mime_addpart(3)
curl_slist_append()
يبني قائمة مترابطة. انظر curl_slist_append(3)
مشاركة البيانات بين عمليات النقل
يمكنك أن تجعل عدة مقبضات "easy" تشارك بيانات معينة، حتى لو تم استخدامها في خيوط مختلفة. يتم إعداد هذا السحر باستخدام واجهة المشاركة، كما هو موضح في صفحة الدليل libcurl-share(3).
تحليل عناوين URL
تحليل ومعالجة عناوين URL. انظر libcurl-url(3)
اتصالات WebSocket
انظر libcurl-ws(3)

الربط مع LIBCURL

على الآلات الشبيهة بـ Unix، توجد أداة تسمى curl-config يتم تثبيتها مع بقية محتويات curl عند تنفيذ 'make install'.

تمت إضافة curl-config لتسهيل ربط التطبيقات بـ libcurl وللمطورين للتعرف على libcurl وكيفية استخدامه.

قم بتشغيل 'curl-config --libs' للحصول على خيارات الربط (الإضافية) التي تحتاجها للربط مع الإصدار المحدد من libcurl الذي قمت بتثبيته. انظر صفحة الدليل curl-config(1) لمزيد من التفاصيل.

أنظمة التشغيل الشبيهة بـ Unix التي تقدم libcurl كجزء من توزيعاتها غالبًا لا توفر أداة curl-config، بل تقوم ببساطة بتثبيت المكتبة ورؤوس الملفات في المسار الشائع لهذا الغرض.

تستخدم العديد من أنظمة Linux وما شابهها pkg-config لتوفير خيارات البناء والربط حول المكتبات، و libcurl تدعم ذلك أيضًا.

أسماء رموز LIBCURL

جميع الدوال العامة في واجهة libcurl تبدأ بالبادئة 'curl_' (بحرف c صغير). يمكنك العثور على دوال أخرى في شفرة المصدر للمكتبة، ولكن البادئات الأخرى تشير إلى أن الدوال خاصة وقد تتغير دون إشعار مسبق في الإصدار التالي.

استخدم فقط الدوال والوظائف الموثقة.

قابلية النقل

تعمل libcurl **تمامًا** بنفس الطريقة، على أي من المنصات التي يتم تجميعها وبناؤها عليها.

الخيوط

libcurl آمنة للخيوط ولكن هناك بعض الاستثناءات. راجع libcurl-thread(3) لمزيد من المعلومات.

الاتصالات المستمرة

الاتصالات المستمرة تعني أن libcurl يمكنها إعادة استخدام نفس الاتصال لعدة عمليات نقل، إذا كانت الظروف مناسبة.

تحاول libcurl دائمًا استخدام الاتصالات المستمرة. كلما استخدمت curl_easy_perform(3) أو curl_multi_perform(3) إلخ، تحاول libcurl استخدام اتصال موجود لإجراء عملية النقل، وإذا لم يكن هناك واحد، تفتح اتصالًا جديدًا يخضع لإعادة الاستخدام في مكالمة تالية محتملة لـ curl_easy_perform(3) أو curl_multi_perform(3).

للسماح لـ libcurl بالاستفادة الكاملة من الاتصالات المستمرة، يجب عليك إجراء أكبر عدد ممكن من عمليات نقل الملفات باستخدام نفس المقبض.

إذا كنت تستخدم واجهة "easy"، وقمت باستدعاء curl_easy_cleanup(3)، سيتم إغلاق جميع الاتصالات المفتوحة المحتملة التي تحتفظ بها libcurl وسيتم نسيانها.

عندما تقوم بإنشاء مقبض "multi" وتستخدم واجهة "multi"، يتم الاحتفاظ بمجمع الاتصالات في المقبض "multi" بدلاً من ذلك، لذا فإن إغلاق وإنشاء مقبضات "easy" جديدة لإجراء عمليات النقل لا يؤثر عليها. بدلاً من ذلك، يمكن لجميع المقبضات "easy" المضافة الاستفادة من المجمع المشترك الواحد.

الثوابت العامة

هناك مجموعة متنوعة من الثوابت التي تستخدمها libcurl، بشكل أساسي من خلال استخدامها الداخلي لمكتبات أخرى، وهي معقدة للغاية بالنسبة لمحمّل المكتبات لإعدادها. لذلك، يجب على البرنامج استدعاء دالة مكتبة بعد تحميل البرنامج وتشغيله لإنهاء إعداد شفرة المكتبة. على سبيل المثال، عندما يتم بناء libcurl لدعم SSL عبر مكتبة GNU TLS، هناك شجرة مفصلة داخل هذه المكتبة تصف بروتوكول SSL.

curl_global_init(3) هي الدالة التي يجب عليك استدعاؤها. قد تقوم هذه الدالة بتخصيص موارد (على سبيل المثال، الذاكرة لشجرة GNU TLS المذكورة أعلاه)، لذا فإن الدالة المصاحبة لها curl_global_cleanup(3) تحررها.

إذا تم تجميع libcurl بدعم للعديد من الواجهات الخلفية لـ SSL، يمكن استدعاء الدالة curl_global_sslset(3) قبل curl_global_init(3) لتحديد الواجهة الخلفية النشطة لـ SSL.

الدوال الثابتة العامة آمنة للخيوط منذ libcurl 7.84.0 إذا كانت curl_version_info(3) تحتوي على CURL_VERSION_

THREADSAFE

feature bit set (most platforms). Read libcurl-thread(3) for thread safety guidelines.

If the global constant functions are not thread safe, then you must not call them when any other thread in the program is running. It is not good enough that no other thread is using libcurl at the time, because these functions internally call similar functions of other libraries, and those functions are similarly thread-unsafe. You cannot generally know what these libraries are, or whether other threads are using them.

If the global constant functions are not thread safe, then the basic rule for constructing a program that uses libcurl is this: Call curl_global_init(3), with a CURL_GLOBAL_ALL argument, immediately after the program starts, while it is still only one thread and before it uses libcurl at all. Call curl_global_cleanup(3) immediately before the program exits, when the program is again only one thread and after its last use of libcurl.

It is not actually required that the functions be called at the beginning and end of the program -- that is just usually the easiest way to do it.

You can call both of these multiple times, as long as all calls meet these requirements and the number of calls to each is the same.

The global constant situation merits special consideration when the code you are writing to use libcurl is not the main program, but rather a modular piece of a program, e.g. another library. As a module, your code does not know about other parts of the program -- it does not know whether they use libcurl or not. Its code does not necessarily run at the start and end of the whole program.

A module like this must have global constant functions of its own, just like curl_global_init(3) and curl_global_cleanup(3). The module thus has control at the beginning and end of the program and has a place to call the libcurl functions. If multiple modules in the program use libcurl, they all separately call the libcurl functions, and that is OK because only the first curl_global_init(3) and the last curl_global_cleanup(3) in a program change anything. (libcurl uses a reference count in static memory).

In a C++ module, it is common to deal with the global constant situation by defining a special class that represents the global constant environment of the module. A program always has exactly one object of the class, in static storage. That way, the program automatically calls the constructor of the object as the program starts up and the destructor as it terminates. As the author of this libcurl-using module, you can make the constructor call curl_global_init(3) and the destructor call curl_global_cleanup(3) and satisfy libcurl's requirements without your user having to think about it. (Caveat: If you are initializing libcurl from a Windows DLL you should not initialize it from DllMain or a static initializer because Windows holds the loader lock during that time and it could cause a deadlock.)

curl_global_init(3) has an argument that tells what particular parts of the global constant environment to set up. In order to successfully use any value except CURL_GLOBAL_ALL (which says to set up the whole thing), you must have specific knowledge of internal workings of libcurl and all other parts of the program of which it is part.

A special part of the global constant environment is the identity of the memory allocator. curl_global_init(3) selects the system default memory allocator, but you can use curl_global_init_mem(3) to supply one of your own. However, there is no way to use curl_global_init_mem(3) in a modular program -- all modules in the program that might use libcurl would have to agree on one allocator.

There is a failsafe in libcurl that makes it usable in simple situations without you having to worry about the global constant environment at all: curl_easy_init(3) sets up the environment itself if it has not been done yet. The resources it acquires to do so get released by the operating system automatically when the program exits.

This failsafe feature exists mainly for backward compatibility because there was a time when the global functions did not exist. Because it is sufficient only in the simplest of programs, it is not recommended for any program to rely on it.
