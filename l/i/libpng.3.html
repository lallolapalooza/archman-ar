I. Introduction

This file describes how to use and modify the PNG reference library (known as libpng) for your own use. In addition to this file, example.c is a good starting point for using the library, as it is heavily commented and should include everything most people will need. We assume that libpng is already installed; see the INSTALL file for instructions on how to configure and install libpng.

For examples of libpng usage, see the files "example.c", "pngtest.c", and the files in the "contrib" directory, all of which are included in the libpng distribution.

Libpng was written as a companion to the PNG specification, as a way of reducing the amount of time and effort it takes to support the PNG file format in application programs.

The PNG specification (Third Edition), June 2025, is available as a W3C Recommendation at https://www.w3.org/TR/2025/REC-png-3-20250624/.

The PNG specification (Second Edition), November 2003, is available as a W3C Recommendation and as an ISO Standard (ISO/IEC 15948:2004 (E)) at https://www.w3.org/TR/2003/REC-PNG-20031110/. The W3C and ISO documents have identical technical content.

The PNG-1.2 specification is available at https://www.libpng.org/pub/png/spec/1.2/. It is technically equivalent to the PNG specification (Second Edition) but has some additional material.

The PNG-1.0 specification is available as RFC 2083 at https://www.libpng.org/pub/png/spec/1.0/ and as a W3C Recommendation at https://www.w3.org/TR/REC-png-961001.

Some additional chunks are described in the special-purpose public chunks documents at http://www.libpng.org/pub/png/spec/register/

Other information about PNG, and the latest version of libpng, can be found at the PNG home page, http://www.libpng.org/pub/png/.

Most users will not have to modify the library significantly; advanced users may want to modify it more. All attempts were made to make it as complete as possible, while keeping the code easy to understand. Currently, this library only supports C. Support for other languages is being considered.

Libpng has been designed to handle multiple sessions at one time, to be easily modifiable, to be portable to the vast majority of machines (ANSI, K&R, 16-, 32-, and 64-bit) available, and to be easy to use. The ultimate goal of libpng is to promote the acceptance of the PNG file format in whatever way possible. While there is still work to be done (see the TODO file), libpng should cover the majority of the needs of its users.

Libpng uses zlib for its compression and decompression of PNG files. Further information about zlib, and the latest version of zlib, can be found at the zlib home page, https://zlib.net/. The zlib compression utility is a general purpose utility that is useful for more than PNG files, and can be used without libpng. See the documentation delivered with zlib for more details. You can usually find the source files for the zlib utility wherever you find the libpng source files.

Libpng is thread safe, provided the threads are using different instances of the structures. Each thread should have its own png_struct and png_info instances, and thus its own image. Libpng does not protect itself against two threads using the same instance of a structure.

II. Structures

There are two main structures that are important to libpng, png_struct and png_info. Both are internal structures that are no longer exposed in the libpng interface (as of libpng 1.5.0).

The png_info structure is designed to provide information about the PNG file. At one time, the fields of png_info were intended to be directly accessible to the user. However, this tended to cause problems with applications using dynamically loaded libraries, and as a result a set of interface functions for png_info (the png_get_*() and png_set_*() functions) was developed, and direct access to the png_info fields was deprecated..

The png_struct structure is the object used by the library to decode a single image. As of 1.5.0 this structure is also not exposed.

Almost all libpng APIs require a pointer to a png_struct as the first argument. Many (in particular the png_set and png_get APIs) also require a pointer to png_info as the second argument. Some application visible macros defined in png.h designed for basic data access (reading and writing integers in the PNG format) don't take a png_info pointer, but it's almost always safe to assume that a (png_struct*) has to be passed to call an API function.

You can have more than one png_info structure associated with an image, as illustrated in pngtest.c, one for information valid prior to the IDAT chunks and another (called "end_info" below) for things after them.

The png.h header file is an invaluable reference for programming with libpng. And while I'm on the topic, make sure you include the libpng header file:

#include <png.h>

and also (as of libpng-1.5.0) the zlib header file, if you need it:

#include <zlib.h>

Types

The png.h header file defines a number of integral types used by the APIs. Most of these are fairly obvious; for example types corresponding to integers of particular sizes and types for passing color values.

One exception is how non-integral numbers are handled. For application convenience most APIs that take such numbers have C (double) arguments; however, internally PNG, and libpng, use 32 bit signed integers and encode the value by multiplying by 100,000. As of libpng 1.5.0 a convenience macro PNG_FP_1 is defined in png.h along with a type (png_fixed_point) which is simply (png_int_32).

All APIs that take (double) arguments also have a matching API that takes the corresponding fixed point integer arguments. The fixed point API has the same name as the floating point one with "_fixed" appended. The actual range of values permitted in the APIs is frequently less than the full range of (png_fixed_point) (-21474 to +21474). When APIs require a non-negative argument the type is recorded as png_uint_32 above. Consult the header file and the text below for more information.

Special care must be take with sCAL chunk handling because the chunk itself uses non-integral values encoded as strings containing decimal floating point numbers. See the comments in the header file.

Configuration

The main header file function declarations are frequently protected by C preprocessing directives of the form:


#ifdef PNG_feature_SUPPORTED
declare-function
#endif
...
#ifdef PNG_feature_SUPPORTED
use-function
#endif

The library can be built without support for these APIs, although a standard build will have all implemented APIs. Application programs should check the feature macros before using an API for maximum portability. From libpng 1.5.0 the feature macros set during the build of libpng are recorded in the header file "pnglibconf.h" and this file is always included by png.h.

If you don't need to change the library configuration from the default, skip to the next section ("Reading").

Notice that some of the makefiles in the 'scripts' directory and (in 1.5.0) all of the build project files in the 'projects' directory simply copy scripts/pnglibconf.h.prebuilt to pnglibconf.h. This means that these build systems do not permit easy auto-configuration of the library - they only support the default configuration.

The easiest way to make minor changes to the libpng configuration when auto-configuration is supported is to add definitions to the command line using (typically) CPPFLAGS. For example:

CPPFLAGS=-DPNG_NO_FLOATING_ARITHMETIC

will change the internal libpng math implementation for gamma correction and other arithmetic calculations to fixed point, avoiding the need for fast floating point support. The result can be seen in the generated pnglibconf.h - make sure it contains the changed feature macro setting.

If you need to make more extensive configuration changes - more than one or two feature macro settings - you can either add -DPNG_USER_CONFIG to the build command line and put a list of feature macro settings in pngusr.h or you can set DFA_XTRA (a makefile variable) to a file containing the same information in the form of 'option' settings.

III. القراءة

سنستعرض الآن الدوال الممكنة التي يجب استدعاؤها عند قراءة ملف PNG بشكل متسلسل، مع شرح موجز للصيغة والغرض لكل منها. راجع example.c و png.h لمزيد من التفاصيل. بينما تتم تغطية القراءة التدريجية في القسم التالي، لا يزال يتعين عليك استخدام بعض الدوال التي تمت مناقشتها في هذا القسم لقراءة ملف PNG.

الإعداد

ستحتاج إلى القيام بتهيئة الإدخال / الإخراج (*) قبل الدخول إلى libpng، لذلك إذا لم ينجح الأمر، فلن يكون لديك الكثير للتراجع عنه. بالطبع، سترغب أيضًا في التأكد من أنك تتعامل بالفعل مع ملف PNG. توفر libpng فحصًا بسيطًا لمعرفة ما إذا كان الملف ملف PNG. لاستخدامه، قم بتمرير البايتات من 1 إلى 8 الأولى من الملف إلى الدالة png_sig_cmp()، وسترجع 0 (خطأ) إذا كانت البايتات تطابق البايتات المقابلة لتوقيع PNG، أو قيمة غير صفرية (صحيح) بخلاف ذلك. بالطبع، كلما مررت المزيد من البايتات، زادت دقة التنبؤ.

إذا كنت تنوي إبقاء مؤشر الملف مفتوحًا للاستخدام في libpng، فيجب عليك التأكد من عدم قراءة أكثر من 8 بايتات من بداية الملف، ويجب عليك أيضًا استدعاء png_set_sig_bytes() مع عدد البايتات التي قرأتها من البداية. ستقوم libpng بعد ذلك بفحص البايتات (إن وجدت) التي لم يقرأها برنامجك فقط.

(*): إذا كنت لا تستخدم وظائف الإدخال / الإخراج القياسية، فستحتاج إلى استبدالها بوظائف مخصصة. راجع المناقشة تحت "تخصيص libpng".


FILE *fp = fopen(file_name, "rb");
if (!fp)
{
return ERROR;
}


if (fread(header, 1, number, fp) != number)
{
return ERROR;
}


is_png = (png_sig_cmp(header, 0, number) == 0);
if (!is_png)
{
return NOT_PNG;
}

بعد ذلك، يجب تخصيص وتهيئة png_struct و png_info. لضمان أن حجم هذه الهياكل صحيح حتى مع libpng المرتبطة ديناميكيًا، توجد وظائف لتهيئة وتخصيص الهياكل. نمرر أيضًا إصدار المكتبة، ومؤشرات اختيارية لوظائف معالجة الأخطاء، ومؤشر إلى هيكل بيانات للاستخدام من قبل وظائف الخطأ، إذا لزم الأمر (يمكن أن يكون المؤشر والوظائف NULL إذا كان سيتم استخدام معالجات الأخطاء الافتراضية). راجع القسم الخاص بالتغييرات على Libpng أدناه فيما يتعلق بوظائف التهيئة القديمة. وظائف تخصيص الهيكل ترجع NULL بصمت إذا فشلت في إنشاء الهيكل، لذا يجب أن يتحقق تطبيقك من ذلك.


png_structp png_ptr = png_create_read_struct
(PNG_LIBPNG_VER_STRING, (png_voidp)user_error_ptr,
user_error_fn, user_warning_fn);


if (!png_ptr)
return ERROR;


png_infop info_ptr = png_create_info_struct(png_ptr);


if (!info_ptr)
{
png_destroy_read_struct(&png_ptr, NULL, NULL);
return ERROR;
}

إذا كنت ترغب في استخدام روتينات تخصيص الذاكرة الخاصة بك، فاستخدم libpng تم بناؤها مع تمكين PNG_USER_MEM_SUPPORTED، واستخدم png_create_read_struct_2() بدلاً من png_create_read_struct():


png_structp png_ptr = png_create_read_struct_2
(PNG_LIBPNG_VER_STRING, (png_voidp)user_error_ptr,
user_error_fn, user_warning_fn, (png_voidp)
user_mem_ptr, user_malloc_fn, user_free_fn);

روتينات معالجة الأخطاء الممررة إلى png_create_read_struct() وروتينات تخصيص / تحرير الذاكرة الممررة إلى png_create_struct_2() ضرورية فقط إذا كنت لا تستخدم وظائف معالجة الأخطاء وتخصيص الذاكرة التي توفرها libpng.

عندما تواجه libpng خطأ، تتوقع القفز مرة أخرى (longjmp) إلى الروتين الخاص بك. لذلك، ستحتاج إلى استدعاء setjmp وتمرير png_jmpbuf(png_ptr) الخاص بك. إذا كنت تقرأ الملف من روتينات مختلفة، فستحتاج إلى تحديث مخزن القفز المؤقت (longjmp buffer) في كل مرة تدخل فيها إلى روتين جديد سيستدعي دالة png_*().

راجع وثائق setjmp/longjmp الخاصة بالمترجم الخاص بك لمزيد من المعلومات حول setjmp/longjmp. راجع المناقشة حول معالجة أخطاء libpng في قسم "تخصيص Libpng" أدناه لمزيد من المعلومات حول معالجة أخطاء libpng. إذا حدث خطأ، وقامت libpng بالقفز مرة أخرى إلى setjmp الخاص بك، فستحتاج إلى استدعاء png_destroy_read_struct() لتحرير أي ذاكرة.


if (setjmp(png_jmpbuf(png_ptr)))
{
png_destroy_read_struct(&png_ptr, &info_ptr, &end_info);
fclose(fp);
return ERROR;
}

مرر NULL بدلاً من &end_info إذا لم تقم بإنشاء هيكل end_info.

إذا كنت تفضل تجنب تعقيد قضايا setjmp/longjmp، يمكنك بناء libpng مع PNG_NO_SETJMP، وفي هذه الحالة ستؤدي الأخطاء إلى استدعاء PNG_ABORT() الذي يفشل افتراضيًا (abort()).

يمكنك #define PNG_ABORT() إلى دالة تقوم بشيء أكثر فائدة من الإجهاض (abort())، طالما أن دالتك لا تعود.

الآن تحتاج إلى إعداد رمز الإدخال. الإعداد الافتراضي لـ libpng هو استخدام دالة C fread(). إذا استخدمت هذا، فستحتاج إلى تمرير FILE * صالح في الدالة png_init_io(). تأكد من أن الملف مفتوح في الوضع الثنائي. إذا كنت ترغب في التعامل مع قراءة البيانات بطريقة أخرى، فلست بحاجة إلى استدعاء الدالة png_init_io()، ولكن يجب عليك بعد ذلك تنفيذ طرق إدخال / إخراج libpng التي تمت مناقشتها في قسم "تخصيص Libpng" أدناه.


png_init_io(png_ptr, fp);

إذا كنت قد فتحت الملف سابقًا وقرأت أيًا من التوقيع من البداية لرؤية ما إذا كان هذا ملف PNG، فأنت بحاجة إلى إعلام libpng بأن هناك بعض البايتات المفقودة من بداية الملف.


png_set_sig_bytes(png_ptr, number);

يمكنك تغيير حجم مخزن ضغط zlib للاستخدام أثناء قراءة البيانات المضغوطة باستخدام


png_set_compression_buffer_size(png_ptr, buffer_size);

حيث الحجم الافتراضي هو 8192 بايت. لاحظ أن حجم المخزن مؤقت يتم تغييره فورًا ويتم إعادة تخصيص المخزن مؤقت فورًا، بدلاً من تعيين علامة ليتم التصرف عليها لاحقًا.

إذا كنت ترغب في معالجة أخطاء CRC بطريقة مختلفة عن الافتراضي، فاستخدم


png_set_crc_action(png_ptr, crit_action, ancil_action);

تقول القيم الخاصة بـ png_set_crc_action() كيف يجب على libpng التعامل مع أخطاء CRC في المقطوعات الهامشية والنقدية، وما إذا كان سيتم استخدام البيانات الموجودة فيها. بدءًا من libpng-1.6.26، يحكم هذا أيضًا كيفية التعامل مع خطأ ADLER32 أثناء قراءة المقطوعة IDAT. لاحظ أنه من المستحيل "التخلص" من البيانات في مقطوعة نقدية.

خيارات (int) crit_action هي
PNG_CRC_DEFAULT 0 error/quit
PNG_CRC_ERROR_QUIT 1 error/quit
PNG_CRC_WARN_USE 3 warn/use data
PNG_CRC_QUIET_USE 4 quiet/use data
PNG_CRC_NO_CHANGE 5 use the current value

خيارات (int) ancil_action هي
PNG_CRC_DEFAULT 0 error/quit
PNG_CRC_ERROR_QUIT 1 error/quit
PNG_CRC_WARN_DISCARD 2 warn/discard data
PNG_CRC_WARN_USE 3 warn/use data
PNG_CRC_QUIET_USE 4 quiet/use data
PNG_CRC_NO_CHANGE 5 use the current value

عندما يكون الإعداد الخاص بـ crit_action هو PNG_CRC_QUIET_USE، لا يتم تجاهل فحوصات CRC و ADLER32 فحسب، بل لا يتم تقييمها أيضًا.

إعداد رمز الاستدعاء

سيتم فك تشفير البيانات إلى مخازن الصف المقدمة المكدسة في بايتات ما لم يتم إخبار المكتبة بتحويلها إلى تنسيق آخر. على سبيل المثال، سيتم إرجاع بيانات ذات 4 بت/بكسل ملونة أو رمادية 2 بكسل/بايت مع وضع البكسل الأيسر في البتات عالية الترتيب للبايت، ما لم يتم استدعاء png_set_packing(). سيتم تخزين بيانات RGB ذات 8 بت بتنسيق RGB RGB RGB ما لم يتم استدعاء png_set_filler() أو png_set_add_alpha() لإدراج بايتات حشو، إما قبل أو بعد كل ثلاثي RGB.

سيتم إرجاع بيانات RGB ذات 16 بت RRGGBB RRGGBB، مع وضع البايت الأكثر أهمية لقيمة اللون أولاً، ما لم يتم استدعاء png_set_scale_16() لتحويلها إلى ثلاثيات RGB RGB عادية، أو png_set_filler() أو png_set_add alpha() لإدراج بايتات حشو، إما قبل أو بعد كل ثلاثي RRGGBB. وبالمثل، يمكن تعديل بيانات الرمادية ذات 8 بت أو 16 بت باستخدام png_set_filler()، و png_set_add_alpha()، و png_set_strip_16()، أو png_set_scale_16().

يقوم الكود التالي بتحويل الصور الرمادية التي تقل عن 8 بت إلى 8 بت، ويغير الصور الملونة إلى RGB، ويضيف قناة ألفا كاملة إذا كان هناك شفافية في جزء tRNS. هذا مفيد للغاية في الصور الرمادية ذات عمق البت 2 أو 4 أو إذا كان هناك تطبيق عرض متعدد الصور يرغب في التعامل مع جميع الصور بنفس الطريقة.


if (color_type == PNG_COLOR_TYPE_PALETTE)
png_set_palette_to_rgb(png_ptr);


if (png_get_valid(png_ptr, info_ptr, PNG_INFO_tRNS))
png_set_tRNS_to_alpha(png_ptr);


if (color_type == PNG_COLOR_TYPE_GRAY && bit_depth < 8)
png_set_expand_gray_1_2_4_to_8(png_ptr);

الدالتان الأوليان هما في الواقع اسم مستعار لـ png_set_expand()، تمت إضافتهما في إصدار libpng 1.0.4، مع توسيع أسماء الدوال لتحسين قابلية قراءة الكود. في إصدار مستقبلي قد يقومان بأشياء مختلفة.

اعتبارًا من إصدار libpng 1.2.9، تمت إضافة png_set_expand_gray_1_2_4_to_8(). تقوم بتوسيع عمق العينة دون تغيير tRNS إلى ألفا.

اعتبارًا من إصدار libpng 1.5.2، تمت إضافة png_set_expand_16(). تعمل مثل png_set_expand()؛ ومع ذلك، فإن القنوات الناتجة تحتوي على 16 بت بدلاً من 8. استخدم هذا عندما تكون قنوات الألوان أو الرمادية الناتجة خطية لتجنب فقدان الدقة الشديد.


if (bit_depth < 16)
png_set_expand_16(png_ptr);

يمكن أن تحتوي ملفات PNG على ملفات بعمق 16 بت لكل قناة. إذا كان يمكنك فقط التعامل مع 8 بت لكل قناة، فسيؤدي ذلك إلى تقليص البكسلات إلى 8 بت.


if (bit_depth == 16)
{ #if PNG_LIBPNG_VER >= 10504
png_set_scale_16(png_ptr); #else
png_set_strip_16(png_ptr); #endif
}

(واجهة برمجة التطبيقات الأكثر دقة "png_set_scale_16()" أصبحت متاحة في إصدار libpng 1.5.4).

إذا كنت بحاجة إلى معالجة قناة ألفا في الصورة بشكل منفصل عن بيانات الصورة (على سبيل المثال، إذا قمت بتحويلها إلى قناع نقطي) فمن الممكن جعل libpng تقوم بتجريد القناة تاركة بيانات RGB أو الرمادية فقط:


if (color_type & PNG_COLOR_MASK_ALPHA)
png_set_strip_alpha(png_ptr);

إذا قمت بتجريد قناة ألفا، فستحتاج إلى إيجاد طريقة أخرى للتعامل مع المعلومات. إذا، بدلاً من ذلك، كنت ترغب في تحويل الصورة إلى نسخة غير شفافة بدون قناة ألفا، فاستخدم png_set_background؛ انظر أدناه.

اعتبارًا من إصدار libpng 1.5.2، يتم دعم معظم التوسعات المفيدة، والغفلات الرئيسية هي تحويل الرمادية إلى صور مفهرسة (والتي يمكن القيام بها بسهولة في التطبيق) وتحويل المفهرسة إلى رمادية (والتي يمكن القيام بها عن طريق معالجة بسيطة للوحة الألوان).

عندما يحتوي الإدخال على عدة تحويلات مدرجة، يجب أن تكون جميعها مطلوبة لإحداث التحويل الكلي الصحيح. عندما يتم فصل تحويلين بفاصلة، يقوم أي منهما بالمهمة. عندما تكون التحويلات محاطة بأقواس []، يجب أن يقوم التحويل بالمهمة ولكن هذا غير منفذ حاليًا - ستكون هناك نتيجة مختلفة إذا تم استخدام التحويلات المقترحة.

في ملفات PNG، قناة ألفا في الصورة هي مستوى التعتيم. إذا كنت بحاجة إلى قناة ألفا في الصورة لتكون مستوى الشفافية بدلاً من التعتيم، يمكنك عكس قناة ألفا (أو بيانات جزء tRNS) بعد قراءتها، بحيث يكون 0 معتمًا بالكامل و 255 (في الصور ذات 8 بت أو الملونة) أو 65535 (في الصور ذات 16 بت) شفافًا بالكامل، باستخدام


png_set_invert_alpha(png_ptr);

تقوم ملفات PNG بتعبئة بكسلات عمق البت 1، 2، و 4 في بايتات بأكبر قدر ممكن، مما يؤدي، على سبيل المثال، إلى 8 بكسلات لكل بايت للملفات ذات البت الواحد. يقوم هذا الكود بالتوسع إلى 1 بكسل لكل بايت دون تغيير قيم البكسلات:


if (bit_depth < 8)
png_set_packing(png_ptr);

تحتوي ملفات PNG على أعماق بت محتملة 1، 2، 4، 8، و 16. تم "قياس" أو "تحويل" جميع البكسلات المخزنة في صورة PNG إلى عمق البت الأعلى التالي الممكن (على سبيل المثال، من 5 بت/عينة في النطاق [0، 31] إلى 8 بت/عينة في النطاق [0، 255]). ومع ذلك، من الممكن أيضًا تحويل بيانات بكسل PNG مرة أخرى إلى عمق البت الأصلي للصورة. يقلل هذا الاستدعاء البكسلات مرة أخرى إلى عمق البت الأصلي:


png_color_8p sig_bit;


if (png_get_sBIT(png_ptr, info_ptr, &sig_bit))
png_set_shift(png_ptr, sig_bit);

تقوم ملفات PNG بتخزين بكسلات 3 ألوان بترتيب الأحمر والأخضر والأزرق. هذا الكود يغير تخزين البكسلات إلى الأزرق والأخضر والأحمر:


if (color_type == PNG_COLOR_TYPE_RGB ||
color_type == PNG_COLOR_TYPE_RGB_ALPHA)
png_set_bgr(png_ptr);

تقوم ملفات PNG بتخزين بكسلات RGB المكدسة في 3 أو 6 بايتات. يقوم هذا الكود بتوسيعها إلى 4 أو 8 بايتات لأنظمة النوافذ التي تحتاجها بهذا التنسيق:


if (color_type == PNG_COLOR_TYPE_RGB)
png_set_filler(png_ptr, filler, PNG_FILLER_BEFORE);

حيث "filler" هو الرقم 8 بت أو 16 بت للملء به، والموقع هو إما PNG_FILLER_BEFORE أو PNG_FILLER_AFTER، اعتمادًا على ما إذا كنت تريد الحشو قبل RGB أو بعده. عند ملء بكسل 8 بت، يتم استخدام أقل 8 بتات أهمية للرقم، إذا تم توفير رقم 16 بت. لا يؤثر هذا التحويل على الصور التي تحتوي بالفعل على قنوات ألفا كاملة. لإضافة قناة ألفا غير شفافة، استخدم filler=0xffff و PNG_FILLER_AFTER مما سيؤدي إلى إنشاء بكسلات RGBA.

لاحظ أن png_set_filler() لا يغير نوع اللون. إذا كنت ترغب في القيام بذلك، يمكنك إضافة قناة ألفا حقيقية باستخدام


if (color_type == PNG_COLOR_TYPE_RGB ||
color_type == PNG_COLOR_TYPE_GRAY)
png_set_add_alpha(png_ptr, filler, PNG_FILLER_AFTER);

حيث يحتوي "filler" على قيمة ألفا لتعيينها لكل بكسل. تمت إضافة الدالة png_set_add_alpha() في libpng-1.2.7.

إذا كنت تقرأ صورة تحتوي على قناة ألفا، وتحتاج إلى البيانات بصيغة ARGB بدلاً من تنسيق PNG العادي RGBA:


if (color_type == PNG_COLOR_TYPE_RGB_ALPHA)
png_set_swap_alpha(png_ptr);

لبعض الاستخدامات، قد ترغب في تمثيل صورة رمادية كـ RGB. سيقوم هذا الكود بإجراء هذا التحويل:


if (color_type == PNG_COLOR_TYPE_GRAY ||
color_type == PNG_COLOR_TYPE_GRAY_ALPHA)
png_set_gray_to_rgb(png_ptr);

على العكس، يمكنك تحويل صورة RGB أو RGBA إلى رمادية أو رمادية مع ألفا.


if (color_type == PNG_COLOR_TYPE_RGB ||
color_type == PNG_COLOR_TYPE_RGB_ALPHA)
png_set_rgb_to_gray(png_ptr, error_action,
(double)red_weight, (double)green_weight);


error_action = 1: قم بالتحويل بصمت
error_action = 2: إصدار تحذير إذا كانت الصورة الأصلية تحتوي على أي بكسل حيث
red != green أو red != blue
error_action = 3: إصدار خطأ وإيقاف التحويل إذا كانت الصورة الأصلية تحتوي على أي بكسل حيث
red != green أو red != blue
red_weight: وزن مكون الأحمر
green_weight: وزن مكون الأخضر
إذا كان أي من الوزنين سالبًا، فسيتم استخدام الأوزان الافتراضية.

في واجهة برمجة التطبيقات الثابتة المقابلة، يتم ببساطة قياس قيم red_weight و green_weight بـ 100000:


png_set_rgb_to_gray(png_ptr, error_action,
(png_fixed_point)red_weight,
(png_fixed_point)green_weight);

إذا قمت بتعيين error_action = 1 أو 2، يمكنك لاحقًا التحقق مما إذا كان

التحويلات

تُستخدم التحويلات في libpng لتبسيط عملية قراءة صور PNG. فهي تسمح لك بتحديد كيفية معالجة بيانات الصورة قبل أن تصل إليك، مما يوفر عليك الحاجة إلى كتابة الكثير من التعليمات البرمجية للتعامل مع التفاصيل الدقيقة لصيغ PNG المختلفة.

تُطبق التحويلات بالترتيب الذي تحدده، وعادةً ما يتم استدعاء معظمها قبل قراءة بيانات الصورة الفعلية.

بعض التحويلات الشائعة:

  • png_set_rgb_to_gray(): تحويل صور RGB إلى تدرج رمادي. يتم الاحتفاظ ببيانات قناة ألفا (إذا كانت موجودة). يمكنك التحقق مما إذا كان قد تم إجراء التحويل باستخدام `png_get_rgb_to_gray_status()`. ستُرجع قيمة 0 إذا كانت الصورة تدرج رمادي بالفعل، و 1 إذا تم تحويل أي وحدات بكسل غير رمادية. سيتم تحويل الخلفية وبيانات sBIT بصمت إلى تدرج رمادي، باستخدام بيانات القناة الخضراء لـ sBIT، بغض النظر عن إعداد `error_action`.

  • png_set_background(): دمج الصور ذات الشفافية (قناة ألفا أو شفافية بسيطة) مع لون خلفية محدد. القيم الافتراضية تأتي من كتلة cHRM في ملف PNG إن وجدت؛ وإلا، فإن الافتراضيات تتوافق مع توصية ITU-R 709، وكذلك مساحة الألوان sRGB، كما هو موصى به في Charles Poynton's Colour FAQ، القسم 9:


    Y = 0.2126 * R + 0.7152 * G + 0.0722 * B

    الإصدارات السابقة من هذه الوثيقة، من 1998 إلى 2002، أوصت بصيغة مختلفة قليلاً:


    Y = 0.212671 * R + 0.715160 * G + 0.072169 * B

    تستخدم Libpng تقريبًا للأعداد الصحيحة:


    Y = (6968 * R + 23434 * G + 2366 * B)/32768

    يتم الحساب في مساحة ألوان خطية، إذا كان من الممكن تحديد جاما الصورة. تم وصف الدالة `png_set_background()` بالفعل؛ فهي تخبر libpng بدمج الصور ذات قناة ألفا أو شفافية بسيطة مع لون الخلفية المقدم. للتوافق مع الإصدارات السابقة من libpng قبل libpng-1.5.4، يوصى باستدعاء الدالة بعد قراءة رأس الملف، حتى لو كنت لا ترغب في استخدام اللون الموجود في كتلة bKGD، إن وجدت.

    إذا كان ملف PNG يحتوي على كتلة bKGD (PNG_INFO_bKGD صالح)، يمكنك استخدام هذا اللون، أو توفير لون آخر أكثر ملاءمة للعرض الحالي (على سبيل المثال، لون خلفية صفحة ويب). تحتاج إلى إخبار libpng بكيفية تمثيل اللون، سواء تنسيق قيم المكونات في اللون (عدد البتات) أو ترميز جاما للون. تأخذ الدالة وسيطين، `background_gamma_mode` و `need_expand` لنقل هذه المعلومات؛ ومع ذلك، سيكون هناك مجموعتان فقط مفيدتان:


    png_color_16 my_background;
    png_color_16p image_background;


    if (png_get_bKGD(png_ptr, info_ptr, &image_background))
    png_set_background(png_ptr, image_background,
    PNG_BACKGROUND_GAMMA_FILE, 1/*needs to be expanded*/, 1);
    else
    png_set_background(png_ptr, &my_background,
    PNG_BACKGROUND_GAMMA_SCREEN, 0/*do not expand*/, 1);

    تم وصف الاستدعاء الثاني أعلاه - `my_background` بتنسيق الإخراج النهائي للعرض الذي تنتجه libpng. نظرًا لأنك تعرف الآن تنسيق PNG، فمن الممكن تجنب الحاجة إلى اختيار إخراج 8 بت أو 16 بت والاحتفاظ بصور اللوحة (سيتم تعديل ألوان اللوحة بشكل مناسب وإزالة كتلة tRNS). ومع ذلك، إذا كنت تفعل ذلك، فاحذر من طلب تحويلات دون التحقق أولاً من أنها قابلة للتطبيق!

    في الاستدعاء الأول، لون الخلفية له عمق البت الأصلي ونوع اللون لملف PNG. لذلك، بالنسبة لصور اللوحة، يتم توفير اللون كفهرس للوحة، وبالنسبة لصور التدرج الرمادي ذات البت المنخفض، يكون اللون قيمة مخفضة في `image_background->gray`.

  • png_set_gamma(): ضبط جاما الشاشة وملف PNG. إذا لم تستدع `png_set_gamma()` قبل قراءة رأس الملف، على سبيل المثال إذا كنت بحاجة إلى الحفاظ على توافق التعليمات البرمجية الخاصة بك مع الإصدارات القديمة من libpng قبل libpng-1.5.4، فهذا هو المكان المناسب لاستدعائها. لا تستدعيها إذا استدعيت `png_set_alpha_mode()`؛ سيؤدي ذلك إلى إتلاف الإعدادات التي وضعتها `png_set_alpha_mode()`. (إذا كان `png_set_alpha_mode()` مدعومًا، فيمكنك بالتأكيد إجراء `png_set_gamma()` قبل قراءة رأس PNG.)

    هذه الواجهة تضبط بشكل لا لبس فيه قيم جاما للشاشة والملف، لذلك ستحل محل القيمة الموجودة في ملف PNG ما لم يتم استدعائها قبل بدء قراءة ملف PNG. لهذا السبب، يجب عليك دائمًا استدعائها مع قيمة ملف PNG عند استدعائها في هذا الموضع:


    if (png_get_gAMA(png_ptr, info_ptr, &file_gamma))
    png_set_gamma(png_ptr, screen_gamma, file_gamma);
    else
    png_set_gamma(png_ptr, screen_gamma, 0.45455);

  • png_set_quantize(): لتقليل عدد الألوان في صورة RGB إلى لوحة، أو لتقليل عدد مدخلات اللوحة إذا كانت أكبر من الألوان المتاحة على الشاشة. هذه عملية كمية بسيطة تطابق اللون الأقرب المتاح. تعمل بشكل جيد مع اللوحات المحسّنة، ولكن بشكل سيئ مع مكعبات الألوان الخطية. إذا قمت بتمرير لوحة أكبر من `maximum_colors`، فسيتم تقليل عدد الألوان في اللوحة لتناسب `maximum_colors`. إذا كان هناك مخطط، ستستخدمه libpng لاتخاذ خيارات أكثر ذكاءً عند تقليل اللوحة. إذا لم يكن هناك مخطط، فقد لا يكون الأداء جيدًا.


    if (color_type & PNG_COLOR_MASK_COLOR)
    {
    if (png_get_valid(png_ptr, info_ptr,
    PNG_INFO_PLTE))
    {
    png_uint_16p histogram = NULL;
    png_get_hIST(png_ptr, info_ptr,
    &histogram);
    png_set_quantize(png_ptr, palette, num_palette,
    max_screen_colors, histogram, 1);
    }
    else
    {
    png_color std_color_cube[MAX_SCREEN_COLORS] =
    { ... colors ... };
    png_set_quantize(png_ptr, std_color_cube,
    MAX_SCREEN_COLORS, MAX_SCREEN_COLORS,
    NULL,0);
    }
    }

  • png_set_invert_mono(): عكس الألوان في صور أحادية اللون (أسود/أبيض). تصف ملفات PNG الأحادية اللون بأن الأسود هو صفر والأبيض هو واحد. التعليمات البرمجية التالية ستعكس ذلك (تجعل الأسود واحدًا والأبيض صفرًا):


    if (bit_depth == 1 && color_type == PNG_COLOR_TYPE_GRAY)
    png_set_invert_mono(png_ptr);

    يمكن استخدام هذه الدالة أيضًا لعكس صور التدرج الرمادي وصور التدرج الرمادي مع قناة ألفا:


    if (color_type == PNG_COLOR_TYPE_GRAY ||
    color_type == PNG_COLOR_TYPE_GRAY_ALPHA)
    png_set_invert_mono(png_ptr);

  • png_set_swap(): تبديل ترتيب البايتات لبيانات البكسل ذات 16 بت. تخزن ملفات PNG وحدات البكسل ذات 16 بت بترتيب بايت الشبكة (big-endian، أي البتات الأكثر أهمية أولاً). هذا الكود يغير التخزين إلى الاتجاه الآخر (little-endian، أي البتات الأقل أهمية أولاً، وهي الطريقة التي تخزن بها أجهزة الكمبيوتر الشخصية):


    if (bit_depth == 16)
    png_set_swap(png_ptr);

  • png_set_packswap(): تبديل ترتيب وحدات البكسل المعبأة في البايتات لصور ذات 1، 2، أو 4 بت لكل بكسل. إذا كنت تستخدم صورًا ذات بكسل معبأة (1، 2، أو 4 بت/بكسل)، وكنت بحاجة إلى تغيير ترتيب تعبئة وحدات البكسل في البايتات، يمكنك استخدام:


    if (bit_depth < 8)
    png_set_packswap(png_ptr);

  • png_set_read_user_transform_fn(): تعيين دالة تحويل مخصصة. يمكنك كتابة دالة التحويل الخاصة بك إذا لم تلبي أي من الدوال الموجودة احتياجاتك. يتم ذلك عن طريق تعيين استدعاء رد اتصال مع:


    png_set_read_user_transform_fn(png_ptr,
    read_transform_fn);

    يجب عليك توفير الدالة:


    void read_transform_fn(png_structp png_ptr, png_row_infop
    row_info, png_bytep data)

    راجع pngtest.c للحصول على مثال عملي. سيتم استدعاء دالتك بعد معالجة جميع التحويلات الأخرى. كن حذرًا مع الصور المتشابكة إذا كنت تتعامل مع التشابك بنفسك - عرض الصف هو العرض في 'row_info'، وليس عرض الصورة الإجمالي.

    إذا كانت مدعومة، توفر libpng روتينين للمعلومات يمكنك استخدامهما لمعرفة مكانك في معالجة الصورة:


    png_get_current_pass_number(png_structp png_ptr);
    png_get_current_row_number(png_structp png_ptr);

    لا تحاول استخدام هذه خارج استدعاء رد اتصال التحويل - أولاً، إنها مدعومة فقط إذا كانت تحويلات المستخدم مدعومة، وثانيًا، قد تُرجع نتائج غير متوقعة ما لم تتم معالجة الصف فعليًا في اللحظة التي يتم فيها استدعاؤها.

    مع الصور المتشابكة، تكون القيمة المرجعة هي الصف في الصورة الفرعية المدخلة. استخدم `PNG_ROW_FROM_PASS_ROW(row, pass)` و `PNG_COL_FROM_PASS_COL(col, pass)` للعثور على بكسل الإخراج (x,y) بالنظر إلى بكسل الصورة الفرعية المتشابكة (row,col,pass).

    يحتوي مناقشة معالجة التشابك أعلاه على مزيد من المعلومات حول كيفية استخدام هذه القيم.

    يمكنك أيضًا إعداد مؤشر إلى بنية مستخدم لاستخدامها بواسطة دالة رد الاتصال الخاصة بك، ويمكنك إعلام libpng بأن دالة التحويل الخاصة بك ستغير عدد القنوات أو عمق البت باستخدام الدالة:


    png_set_user_transform_info(png_ptr, user_ptr,
    user_depth, user_channels);

    تطبيق المستخدم، وليس libpng، هو المسؤول عن تخصيص وتحرير أي ذاكرة مطلوبة لبنية المستخدم.

    يمكنك استرداد المؤشر عبر الدالة `png_get_user_transform_ptr()`. على سبيل المثال:


    voidp read_user_transform_ptr =
    png_get_user_transform_ptr(png_ptr);

  • png_set_interlace_handling(): معالجة التشابك. الشيء الأخير الذي يجب معالجته هو التشابك؛ هذا مغطى بالتفصيل أدناه، ولكن يجب عليك استدعاء الدالة هنا إذا كنت تريد أن تتعامل libpng مع توسيع الصورة المتشابكة.


    number_of_passes = png_set_interlace_handling(png_ptr);

تحديث المعلومات

بعد تعيين التحويلات، يمكن لـ libpng تحديث بنية `png_info` الخاصة بك لتعكس أي تحويلات طلبتها بهذا الاستدعاء.


png_read_update_info(png_ptr, info_ptr);

هذا مفيد جدًا لتحديث حقل `rowbytes` لبنية المعلومات بحيث يمكنك استخدامه لتخصيص ذاكرة صورتك. ستقوم هذه الدالة أيضًا بتحديث لوحتك بـ `screen_gamma` و `background` الصحيحين إذا تم توفيرها مع الاستدعاءات أعلاه. يمكنك فقط استدعاء `png_read_update_info()` مرة واحدة مع `info_ptr` معين.

بعد استدعاء `png_read_update_info()`، يمكنك تخصيص أي ذاكرة تحتاجها للاحتفاظ بالصورة. بيانات الصف هي مجرد بيانات بايت خام لجميع أشكال الصور. نظرًا لأن التخصيص الفعلي يختلف بين التطبيقات، فلن يتم تقديم مثال. إذا كنت تقوم بتخصيص قطعة كبيرة واحدة، فستحتاج إلى بناء مصفوفة من المؤشرات لكل صف، حيث سيتم طلبها لبعض الدوال أدناه.

تأكد من أن نظامك الأساسي يمكنه تخصيص المخزن المؤقت الذي ستحتاجه. تتحقق libpng داخليًا من العرض الكبير جدًا، ولكن ستحتاج إلى إجراء فحصك الخاص لـ `number_of_rows*width*pixel_size` إذا كنت تستخدم مخزنًا مؤقتًا متعدد الصفوف:


/* Guard against integer overflow */
if (number_of_rows > PNG_SIZE_MAX/(width*pixel_size))
png_error(png_ptr, "image_data buffer would be too large");

تذكر: قبل استدعاء `png_read_update_info()`، تُرجع دوال `png_get_*()` القيم المقابلة لصورة PNG الأصلية. بعد استدعاء `png_read_update_info()`، تشير القيم إلى الصورة التي ستنتجها libpng. بالتالي، يجب عليك استدعاء جميع دوال `png_set_` قبل استدعاء `png_read_update_info()`. هذا مهم بشكل خاص لـ `png_set_interlace_handling()` - إذا كنت ستستدعي `png_read_update_info()`، فيجب عليك استدعاء `png_set_interlace_handling()` قبلها ما لم ترغب في تلقي إخراج متشابك.

قراءة بيانات الصورة

بعد تخصيص الذاكرة، يمكنك قراءة بيانات الصورة. أبسط طريقة للقيام بذلك هي في استدعاء دالة واحدة. إذا كنت تقوم بتخصيص ذاكرة كافية لاستيعاب الصورة بأكملها، يمكنك فقط استدعاء `png_read_image()` وستقوم libpng بقراءة جميع بيانات الصورة ووضعها في منطقة الذاكرة المقدمة. ستحتاج إلى تمرير مصفوفة من المؤشرات لكل صف.

تتعامل هذه الدالة تلقائيًا مع التشابك، لذلك لا تحتاج إلى استدعاء `png_set_interlace_handling()` (إلا إذا قمت باستدعاء `png_read_update_info()`) أو استدعاء هذه الدالة عدة مرات، أو أي من الأشياء الأخرى اللازمة مع `png_read_rows()`.


png_read_image(png_ptr, row_pointers);

حيث `row_pointers` هي:


png_bytep row_pointers[height];

يمكنك الإشارة إلى `void` أو `char` أو أي شيء تستخدمه للبيكسلات.

إذا كنت لا ترغب في قراءة الصورة بأكملها مرة واحدة، يمكنك استخدام `png_read_rows()` بدلاً من ذلك. إذا لم يكن هناك تشابك (تحقق من `interlace_type == PNG_INTERLACE_NONE`)، فهذا بسيط:


png_read_rows(png_ptr, row_pointers, NULL,
number_of_rows);

حيث `row_pointers` هو نفس استدعاء `png_read_image()`.

إذا كنت تفعل هذا صفًا واحدًا في كل مرة، يمكنك القيام بذلك باستخدام مؤشر صف واحد بدلاً من مصفوفة من مؤشرات الصفوف:


png_bytep row_pointer = row;
png_read_row(png_ptr, row_pointer, NULL);

إذا كانت الملف متشابكًا ( `interlace_type != 0` في كتلة IHDR)، تصبح الأمور أصعب إلى حد ما. النوع الوحيد للتشابك الحالي (إصدار مواصفات PNG 1.2) هو (`interlace_type == PNG_INTERLACE_ADAM7`)، وهو مخطط تشابك ثنائي الأبعاد معقد إلى حد ما، يُعرف باسم Adam7، والذي يقسم الصورة إلى سبع صور أصغر بأحجام متفاوتة، بناءً على شبكة 8x8. يتم تعريف هذا الرقم (من libpng 1.5) باسم `PNG_INTERLACE_ADAM7_PASSES` في `png.h`

يمكن لـ libpng ملء تلك الصور أو تقديمها لك "كما هي". من الأفضل دائمًا ترك libpng تتعامل مع التشابك نيابة عنك. إذا كنت تريد ملء الصور، فهناك طريقتان للقيام بذلك. الطريقة المذكورة في مواصفات PNG هي توسيع كل بكسل لتغطية البكسلات التي لم يتم قراءتها بعد (طريقة "المستطيل"). ينتج عن هذا صورة متقطعة للمرور الأول، والتي تنعم تدريجياً مع قراءة المزيد من البكسلات. الطريقة الأخرى هي طريقة "البريق"، حيث يتم رسم وحدات البكسل فقط في مواقعها النهائية، مع بقاء بقية الصورة بأي ألوان تم تهيئتها بها قبل بدء القراءة. الطريقة الأولى تبدو أفضل عمومًا، ولكنها تميل إلى أن تكون أبطأ، حيث يوجد المزيد من وحدات البكسل لوضعها في الصفوف.

إذا كنت تريد، كما هو مرجح، أن تقوم libpng بتوسيع الصور، فاستدعِ هذا قبل استدعاء `png_start_read_image()` أو `png_read_update_info()`:


if (interlace_type == PNG_INTERLACE_ADAM7)
number_of_passes
= png_set_interlace_handling(png_ptr);

سيؤدي هذا إلى إرجاع عدد التمريرات المطلوبة. حاليًا، هذا سبعة، ولكنه قد يتغير إذا تمت إضافة نوع تشابك آخر. يمكن استدعاء هذه الدالة حتى لو لم تكن الصورة متشابكة، حيث ستعيد تمريرة واحدة. ثم تحتاج إلى قراءة الصورة بأكملها 'number_of_passes' مرات. في كل مرة سيتم توزيع وحدات البكسل من التمريرة الحالية إلى المكان الصحيح في الصورة المخرجة، لذلك تحتاج إلى توفير نفس الصفوف لـ `png_read_rows()` في كل تمريرة.

إذا لم تكن ستعرض الصورة بعد كل تمريرة، ولكنك ستنتظر حتى يتم قراءة الصورة بأكملها، فاستخدم تأثير البريق. هذا التأثير أسرع والنتيجة النهائية لأي طريقة هي نفسها تمامًا. إذا كنت تخطط لعرض الصورة بعد كل تمريرة، فإن تأثير "المستطيل" يعتبر بشكل عام أفضل مظهرًا.

إذا كنت تريد فقط تأثير "البريق"، فما عليك سوى استدعاء `png_read_row()` أو `png_read_rows()` كالمعتاد، مع جعل المعلمة الثالثة NULL. تأكد من المرور على الصورة عدد مرات `number_of_passes`، ولا تقم بتغيير البيانات في الصفوف بين الاستدعاءات. يمكنك تغيير مواقع البيانات، فقط ليس البيانات. كل تمريرة تكتب فقط وحدات البكسل المناسبة لتلك التمريرة، وتفترض أن البيانات من التمريرات السابقة لا تزال صالحة.


png_read_rows(png_ptr, row_pointers, NULL,
number_of_rows);
or
png_read_row(png_ptr, row_pointers, NULL);

إذا كنت تريد فقط التأثير الأول (المستطيلات)، فافعل نفس الشيء كما من قبل باستثناء تمرير مخزن الصف المؤقت في المعلمة الثالثة، واترك المعلمة الثانية NULL.


png_read_rows(png_ptr, NULL, row_pointers,
number_of_rows);
or
png_read_row(png_ptr, NULL, row_pointers);

إذا كنت لا تريد أن تتعامل libpng مع تفاصيل التشابك، فما عليك سوى استدعاء `png_read_rows()` لـ `PNG_INTERLACE_ADAM7_PASSES` مرة لقراءة جميع الصور. كل صورة هي صورة صالحة بحد ذاتها؛ ومع ذلك، ستحتاج تقريبًا بالتأكيد إلى توزيع وحدات البكسل من كل صورة فرعية إلى المكان الصحيح. هذا هو المكان الذي تصبح فيه الأمور معقدة للغاية.

إذا كنت ترغب في استرداد الصور المنفصلة، فيجب عليك تمرير العدد الصحيح من الصفوف لكل استدعاء متعاقب لـ `png_read_rows()`. يصبح الحساب معقدًا جدًا للصور الصغيرة، حيث قد لا تكون بعض الصور الفرعية موجودة لأن عرضها أو ارتفاعها يصبح صفرًا. توفر libpng وحدتين ماكرو للمساعدة في إصداراتها 1.5 وما بعدها:


png_uint_32 width = PNG_PASS_COLS(image_width, pass_number);
png_uint_32 height = PNG_PASS_ROWS(image_height, pass_number);

على التوالي، تخبرنا هذه عن عرض وارتفاع الصورة الفرعية المقابلة للتمريرة المرقمة. 'pass' في النطاق من 0 إلى 6 - قد يكون هذا مربكًا لأن المواصفات تشير إلى نفس التمريرات على أنها 1 إلى 7! كن حذرًا، يجب عليك التحقق من كل من العرض والارتفاع قبل استدعاء `png_read_rows()` وعدم استدعائه لتلك التمريرة إذا كان أي منهما صفرًا.

يمكنك بالطبع قراءة كل صورة فرعية صفًا بصف. إذا كنت ترغب في إنتاج كود مثالي لتحويل صورة متشابكة بكسل بكسل، فهذه هي أفضل طريقة؛ قراءة كل صف من كل تمريرة، وتحويله، وكتابته إلى صورة متشابكة جديدة.

إذا كنت ترغب في إلغاء تشابك الصورة بنفسك، توفر libpng وحدات ماكرو إضافية للمساعدة في إخبارك بمكان وضع وحدات البكسل في الصورة المخرجة. نظرًا لأن مخطط التشابك مستطيل - تكون وحدات البكسل الفرعية دائمًا مرتبة على شبكة مستطيلة - كل ما تحتاج إلى معرفته لكل تمريرة هو عمود البداية وصف البداية في الصورة المخرجة لأول بكسل بالإضافة إلى المسافة بين كل بكسل. اعتبارًا من libpng 1.5، هناك أربع وحدات ماكرو لاسترداد هذه المعلومات:


png_uint_32 x = PNG_PASS_START_COL(pass);
png_uint_32 y = PNG_PASS_START_ROW(pass);
png_uint_32 xStep = 1U << PNG_PASS_COL_SHIFT(pass);
png_uint_32 yStep = 1U << PNG_PASS_ROW_SHIFT(pass);

تسمح لك هذه بكتابة الحلقة الواضحة:


png_uint_32 input_y = 0;
png_uint_32 output_y = PNG_PASS_START_ROW(pass);


while (output_y < output_image_height)
{
png_uint_32 input_x = 0;
png_uint_32 output_x = PNG_PASS_START_COL(pass);


while (output_x < output_image_width)
{
image[output_y][output_x] =
subimage[pass][input_y][input_x++];


output_x += xStep;
}


++input_y;
output_y += yStep;
}

لاحظ أن الخطوات بين صفوف وأعمدة الإخراج المتتالية يتم إرجاعها كإزاحات. هذا ممكن لأن وحدات البكسل في الصور الفرعية دائمًا ما تكون على مسافة قوة 2 - 1، 2، 4 أو 8 بكسلات - في الصورة الأصلية. في الممارسة العملية، قد تحتاج إلى حساب إحداثيات الإخراج مباشرة بالنظر إلى إحداثيات الإدخال. توفر libpng وحدتين ماكرو إضافيتين لهذا الغرض:


png_uint_32 output_x = PNG_COL_FROM_PASS_COL(input_x, pass);
png_uint_32 output_y = PNG_ROW_FROM_PASS_ROW(input_y, pass);

أخيرًا، يتم توفير زوج من وحدات الماكرو لإخبارك ما إذا كان صف أو عمود صورة معين يظهر في تمريرة معينة:


int col_in_pass = PNG_COL_IN_INTERLACE_PASS(output_x, pass);
int row_in_pass = PNG_ROW_IN_INTERLACE_PASS(output_y, pass);

ضع في اعتبارك أنك قد تحتاج أيضًا إلى التحقق من عرض وارتفاع التمريرة بالإضافة إلى ما سبق للتأكد من وجود التمريرة بالفعل!

مع بعض الحظ، تكون مقتنعًا الآن بأنك لا تريد التعامل مع التشابك بنفسك. في الواقع، عادةً ما يكون السبب الوجيه الوحيد للقيام بذلك هو إذا كنت تعالج ملفات PNG على أساس بكسل بكسل ولا تريد تحميل الملف بأكمله في الذاكرة عند تشابكه.

تتضمن libpng برنامج اختبار، `pngvalid`، يوضح قراءة وكتابة الصور المتشابكة. إذا لم تتمكن من جعل التشابك يعمل في الكود الخاص بك ولا تريد تركه لـ libpng (النهج الموصى به)، فانظر كيف يفعل `pngvalid.c` ذلك.

إنهاء القراءة التسلسلية

بعد الانتهاء من قراءة الصورة عبر الواجهة منخفضة المستوى، يمكنك إنهاء قراءة الملف.

إذا كنت ترغب في استخدام إجراء crc مختلف لمعالجة أخطاء CRC في الكتل بعد بيانات الصورة، يمكنك استدعاء `png_set_crc_action()` مرة أخرى في هذه النقطة.

إذا كنت مهتمًا بالتعليقات أو الوقت، والتي قد يتم تخزينها إما قبل أو بعد بيانات الصورة، فيجب عليك تمرير هيكل `png_info` منفصل إذا كنت ترغب في الاحتفاظ بالتعليقات من قبل وبعد الصورة منفصلة.


png_infop end_info = png_create_info_struct(png_ptr);


if (!end_info)
{
png_destroy_read_struct(&png_ptr, &info_ptr, NULL);
return ERROR;
}


png_read_end(png_ptr, end_info);

إذا لم تكن مهتمًا، يجب عليك مع ذلك استدعاء `png_read_end()` ولكن يمكنك تمرير NULL، مما يجنب الحاجة إلى إنشاء هيكل `end_info`. إذا قمت بذلك، فلن تقوم libpng بمعالجة أي كتل بعد IDAT باستثناء تخطيها وربما (اعتمادًا على ما إذا كنت قد استدعيت `png_set_crc_action()`) التحقق من CRC الخاصة بها أثناء البحث عن كتلة IEND.


png_read_end(png_ptr, NULL);

إذا لم تستدعِ `png_read_end()`، فسيظل مؤشر الملف الخاص بك يشير إلى الكتلة الأولى بعد آخر IDAT، وهو على الأرجح ليس ما تريده إذا كنت تتوقع قراءة شيء بعد نهاية دفق بيانات PNG.

عند الانتهاء، يمكنك تحرير كل الذاكرة التي خصصتها libpng على النحو التالي:


png_destroy_read_struct(&png_ptr, &info_ptr, &end_info);

أو، إذا لم تنشئ هيكل `end_info`،


png_destroy_read_struct(&png_ptr, &info_ptr, NULL);

من الممكن أيضًا تحرير بشكل فردي

لا يوجد خيار لتبديل ترتيب المكونات في التنسيق الخطي. المكونات هي أعداد صحيحة بحجم 16 بت بترتيب البايت الأصلي لمنصتك، ولا يوجد خيار لتبديل البايتات إلى حالة إنْديان مختلفة.


PNG_FORMAT_LINEAR_Y
PNG_FORMAT_LINEAR_Y_ALPHA
PNG_FORMAT_LINEAR_RGB
PNG_FORMAT_LINEAR_RGB_ALPHA

مع التنسيقات المعتمدة على خريطة الألوان، تكون بيانات الصورة عبارة عن بايت واحد لكل بكسل. البايت هو فهرس في خريطة الألوان المنسقة كما هو موضح أعلاه. للحصول على تنسيق معتمد على خريطة الألوان، يكفي فقط إضافة PNG_FOMAT_FLAG_COLORMAP إلى أحد التعريفات المذكورة أعلاه، أو يمكنك استخدام أحد التعريفات التالية.


PNG_FORMAT_RGB_COLORMAP
PNG_FORMAT_BGR_COLORMAP
PNG_FORMAT_RGBA_COLORMAP
PNG_FORMAT_ARGB_COLORMAP
PNG_FORMAT_BGRA_COLORMAP
PNG_FORMAT_ABGR_COLORMAP

وحدات الماكرو PNG_IMAGE

هذه وحدات ماكرو مساعدة لاستخلاص المعلومات من بنية png_image. ترجع وحدات الماكرو PNG_IMAGE_SAMPLE_ قيمًا مناسبة لقيم عينات الصورة الفعلية - إما الإدخالات في خريطة الألوان أو وحدات البكسل في الصورة. ترجع وحدات الماكرو PNG_IMAGE_PIXEL_ قيمًا مقابلة لوحدات البكسل وسترجع دائمًا 1 للتنسيقات المعتمدة على خريطة الألوان. ترجع وحدات الماكرو المتبقية معلومات حول الصفوف في الصورة والصورة الكاملة.

ملاحظة: جميع وحدات الماكرو التي تأخذ معلمة png_image::format هي ثوابت وقت التصريف إذا كانت معلمة التنسيق هي نفسها ثابتة. لذلك يمكن استخدام وحدات الماكرو هذه في تعريفات المصفوفات وملصقات case عند الحاجة. وبالمثل، فإن وحدات الماكرو هي أيضًا ثوابت للمعالج المسبق (لا يتم استخدام sizeof) بحيث يمكن استخدامها في اختبارات #if.


PNG_IMAGE_SAMPLE_CHANNELS(fmt)
يرجع العدد الإجمالي للقنوات في تنسيق معين: 1..4


PNG_IMAGE_SAMPLE_COMPONENT_SIZE(fmt)
يرجع حجم كل مكون في بكسل أو إدخال خريطة ألوان (حسب الاقتضاء) بالبايت في الصورة: 1 أو 2.


PNG_IMAGE_SAMPLE_SIZE(fmt)
هذا هو حجم بيانات العينة لعينة واحدة. إذا كانت الصورة معتمدة على خريطة الألوان، فهذا هو حجم إدخال خريطة ألوان واحد (ووحدات بكسل الصورة بحجم بايت واحد)، وإلا فهو حجم بكسل صورة واحد.


PNG_IMAGE_MAXIMUM_COLORMAP_COMPONENTS(fmt)
الحد الأقصى لحجم خريطة الألوان المطلوبة بواسطة التنسيق معبرًا عنه بعدد المكونات. يمكن استخدام هذا لتخصيص خريطة ألوان وقت التصريف:


png_uint_16 colormap[PNG_IMAGE_MAXIMUM_COLORMAP_COMPONENTS(linear_fmt)];


png_byte colormap[PNG_IMAGE_MAXIMUM_COLORMAP_COMPONENTS(sRGB_fmt)];


بدلاً من ذلك، استخدم وحدة الماكرو PNG_IMAGE_COLORMAP_SIZE أدناه لاستخدام المعلومات من إحدى واجهات برمجة تطبيقات png_image_begin_read_ وتخصيص الذاكرة المطلوبة ديناميكيًا.


PNG_IMAGE_COLORMAP_SIZE(fmt)
حجم خريطة الألوان المطلوبة بواسطة التنسيق؛ هذا هو حجم مخزن خريطة الألوان الذي يتم تمريره إلى واجهات برمجة تطبيقات png_image_{read,write}_colormap. إنه رقم ثابت يحدده التنسيق، لذا يمكن تخصيصه بسهولة على المكدس إذا لزم الأمر.

حجم البكسل الكامل بالبايت؛ 1 لصورة معتمدة على خريطة الألوان.

معلومات عن الصف بأكمله، أو الصورة بأكملها


PNG_IMAGE_ROW_STRIDE(image)
يرجع العدد الإجمالي للمكونات في صف واحد من الصورة؛ هذا هو الحد الأدنى "لخطوة الصف"، وهو الحد الأدنى لعدد المكونات بين كل صف. بالنسبة لصورة معتمدة على خريطة الألوان، هذا هو الحد الأدنى لعدد البايتات في الصف.


إذا كنت بحاجة إلى خطوة مقاسة بالبايت، فإن row_stride_bytes هي
PNG_IMAGE_ROW_STRIDE(image) * PNG_IMAGE_PIXEL_COMPONENT_SIZE(fmt)
بالإضافة إلى أي بايتات حشو قد تحتاج إليها تطبيقك، على سبيل المثال
لبدء الصف التالي على حدود 4 بايت.


PNG_IMAGE_BUFFER_SIZE(image, row_stride)
يرجع حجم مخزن الصورة بالبايت، بالنظر إلى png_image وخطوة صف - عدد المكونات التي يجب ترك مساحة لها في كل صف.


PNG_IMAGE_SIZE(image)
يرجع حجم الصورة بالبايت في الذاكرة، بالنظر فقط إلى png_image؛
خطوة الصف هي الحد الأدنى للخطوة المطلوبة للصورة.


PNG_IMAGE_COLORMAP_SIZE(image)
يرجع حجم خريطة الألوان لهذه الصورة بالبايت. إذا لم يكن تنسيق الصورة تنسيق خريطة ألوان، فسترجع حجمًا كافيًا لـ 256 إدخالًا بالتنسيق المحدد؛ تحقق من PNG_FORMAT_FLAG_COLORMAP إذا
كنت لا ترغب في تخصيص خريطة ألوان في هذه الحالة.

PNG_IMAGE_FLAG_*

تحتوي الأعلام التي تحتوي على معلومات إضافية حول الصورة في حقل 'flags' الخاص بـ png_image.


PNG_IMAGE_FLAG_COLORSPACE_NOT_sRGB == 0x01
يشير هذا إلى أن قيم RGB للبيانات النقطية في الذاكرة لا
تتوافق مع نقاط النهاية الحمراء والخضراء والزرقاء المحددة بواسطة sRGB.


PNG_IMAGE_FLAG_FAST == 0x02
عند الكتابة، ركز على السرعة بدلاً من الضغط؛ سيكون ملف PNG الناتج أكبر ولكنه سينتج بشكل أسرع بكثير، خاصة بالنسبة للصور الكبيرة. لا تستخدم هذا الخيار للصور التي سيتم توزيعها، فقط استخدمه عند إنتاج ملفات وسيطة سيتم قراءتها مرة أخرى
بشكل متكرر. بالنسبة لصورة نموذجية بدقة 24 بت، سيضاعف الخيار سرعة القراءة مقابل زيادة حجم الصورة بنسبة 25٪، ومع ذلك، بالنسبة للعديد من الصور الأكثر قابلية للضغط، يمكن أن يكون ملف PNG أكبر بعشر مرات مع زيادة طفيفة في السرعة.


PNG_IMAGE_FLAG_16BIT_sRGB == 0x04
عند القراءة، إذا كانت الصورة عبارة عن صورة بدقة 16 بت لكل مكون ولا يوجد فيها مقطع gAMA أو sRGB، فافترض أن المكونات مشفرة sRGB. لاحظ أن الصور التي تخرجها واجهة برمجة التطبيقات المبسطة تحتوي دائمًا على معلومات جاما؛ تعيين هذا العلم يؤثر فقط على تفسير الصور بدقة 16 بت من
مصدر خارجي. يوصى بأن يكشف التطبيق هذا العلم للمستخدم؛ يمكن للمستخدم عادةً التعرف بسهولة على الفرق بين الترميز الخطي و sRGB. هذا العلم ليس له تأثير على الكتابة - يجب أن تحتوي البيانات التي يتم تمريرها إلى واجهات برمجة التطبيقات للكتابة على الترميز الصحيح (كما هو محدد أعلاه.)


إذا لم يتم تعيين العلم (الافتراضي)، فمن المفترض أن تكون بيانات الإدخال بدقة 16 بت لكل مكون خطية.


ملاحظة: لا يمكن تعيين العلم إلا بعد استدعاء png_image_begin_read_،
لأن هذا الاستدعاء يقوم بتهيئة حقل 'flags'.

السادس - تعديل/تخصيص libpng

هناك مسألتان هنا. الأولى هي تغيير كيفية قيام libpng بالأشياء القياسية مثل تخصيص الذاكرة، والإدخال/الإخراج، ومعالجة الأخطاء. والثانية تتعامل مع أشياء أكثر تعقيدًا مثل إضافة مقاطع جديدة، وإضافة تحويلات جديدة، وتغيير كيفية عمل libpng بشكل عام. كلاهما مسألة وقت الترجمة؛ أي، يتم تحديدها عمومًا في وقت كتابة الكود، ونادرًا ما تكون هناك حاجة لتوفير وسيلة للمستخدم لتغييرها.

تخصيص الذاكرة، والإدخال/الإخراج، ومعالجة الأخطاء

يتم تخصيص جميع الذاكرة، والإدخال/الإخراج، ومعالجة الأخطاء في libpng من خلال استدعاءات ردود فعل يمكن للمستخدم تعيينها. الروتينات الافتراضية موجودة في pngmem.c، pngrio.c، pngwio.c، و pngerror.c، على التوالي. لتغيير هذه الوظائف، قم باستدعاء الوظيفة المناسبة png_set_*_fn().

يتم تخصيص الذاكرة من خلال الوظائف png_malloc() و png_calloc() و png_free(). الوظائف png_malloc() و png_free() حاليًا تستدعي وظائف C القياسية و png_calloc() تستدعي png_malloc() ثم تمسح الذاكرة المخصصة حديثًا إلى الصفر؛ لاحظ أن png_calloc(png_ptr, size) ليست مثل وظيفة calloc(number, size) المقدمة بواسطة stdlib.h. هناك دعم محدود لأنظمة معينة ذات هياكل ذاكرة مقسمة وأنواع المؤشرات المعلنة بواسطة png.h تطابق هذا؛ ستحتاج إلى استخدام مؤشرات مناسبة في تطبيقك. إذا كنت تفضل استخدام طريقة مختلفة لتخصيص البيانات وتحريرها، يمكنك استخدام png_create_read_struct_2() أو png_create_write_struct_2() لتسجيل وظائفك الخاصة كما هو موضح أعلاه. توفر هذه الوظائف أيضًا مؤشر void يمكن استرداده عبر


mem_ptr = png_get_mem_ptr(png_ptr);

يجب أن تحتوي وظائف الذاكرة البديلة الخاصة بك على توقيعات كما يلي:


png_voidp malloc_fn(png_structp png_ptr,
png_alloc_size_t size);


void free_fn(png_structp png_ptr, png_voidp ptr);

يجب أن تعيد وظيفتك malloc_fn() القيمة NULL في حالة الفشل. ستستدعي وظيفة png_malloc() عادةً png_error() إذا تلقت NULL من مخصص الذاكرة للنظام أو من وظيفة malloc_fn() البديلة الخاصة بك.

لن يتم استدعاء وظيفتك free_fn() أبدًا بمؤشر NULL، لأن png_free() في libpng تتحقق من NULL قبل استدعاء free_fn().

يتم الإدخال/الإخراج في libpng من خلال png_read() و png_write()، والتي تستدعي حاليًا fread() و fwrite(). يتم تخزين FILE * في png_struct ويتم تهيئتها عبر png_init_io(). إذا كنت ترغب في تغيير طريقة الإدخال/الإخراج، توفر المكتبة استدعاءات رد فعل يمكنك تعيينها من خلال الوظيفة png_set_read_fn() و png_set_write_fn() في وقت التشغيل، بدلاً من استدعاء الوظيفة png_init_io(). توفر هذه الوظائف أيضًا مؤشر void يمكن استرداده عبر الوظيفة png_get_io_ptr(). على سبيل المثال:


png_set_read_fn(png_structp read_ptr,
voidp read_io_ptr, png_rw_ptr read_data_fn)


png_set_write_fn(png_structp write_ptr,
voidp write_io_ptr, png_rw_ptr write_data_fn,
png_flush_ptr output_flush_fn);


voidp read_io_ptr = png_get_io_ptr(read_ptr);
voidp write_io_ptr = png_get_io_ptr(write_ptr);

يجب أن تحتوي وظائف الإدخال/الإخراج البديلة على توقيعات كما يلي:


void user_read_data(png_structp png_ptr,
png_bytep data, size_t length);


void user_write_data(png_structp png_ptr,
png_bytep data, size_t length);


void user_flush_data(png_structp png_ptr);

وظيفة user_read_data() مسؤولة عن اكتشاف أخطاء نهاية البيانات ومعالجتها.

توفير NULL لوظائف القراءة أو الكتابة أو المسح يعيدها إلى استخدام وظائف تدفق C الافتراضية، والتي تتوقع أن يشير io_ptr إلى بنية *FILE قياسية. من المحتمل أن يكون من الخطأ استخدام NULL لأحد وظيفتي write_data_fn و output_flush_fn ولكن ليس كليهما، ما لم تكن قد بنيت libpng مع تعريف PNG_NO_WRITE_FLUSH. من الخطأ القراءة من تدفق كتابة، والعكس صحيح.

تتم معالجة الأخطاء في libpng من خلال png_error() و png_warning(). الأخطاء التي تتم معالجتها من خلال png_error() قاتلة، مما يعني أن png_error() يجب ألا تعود أبدًا إلى المتصل الخاص بها. حاليًا، يتم التعامل مع هذا عبر setjmp() و longjmp() (ما لم تكن قد قمت بترجمة libpng باستخدام PNG_NO_SETJMP، وفي هذه الحالة يتم التعامل معها عبر PNG_ABORT())، ولكن يمكنك تغيير ذلك للقيام بأشياء مثل exit() إذا رغبت في ذلك، طالما أن وظيفتك لا تعود.

في الأخطاء غير القاتلة، يتم استدعاء png_warning() لطباعة رسالة تحذير، ثم يعود التحكم إلى الكود المتصل. افتراضيًا، تقوم png_error() و png_warning() بطباعة رسالة على stderr عبر fprintf() ما لم يتم تجميع المكتبة مع تعريف PNG_NO_CONSOLE_IO (لأنك لا تريد الرسائل) أو PNG_NO_STDIO (لأن fprintf() غير متاح). إذا كنت ترغب في تغيير سلوك وظائف الخطأ، فستحتاج إلى إعداد وظائف ردود فعل الرسائل الخاصة بك. يتم توفير هذه الوظائف عادةً في الوقت الذي تم فيه إنشاء png_struct. من الممكن أيضًا إعادة توجيه الأخطاء والتحذيرات إلى وظائفك البديلة الخاصة بعد استدعاء png_create_*_struct() عن طريق استدعاء:


png_set_error_fn(png_structp png_ptr,
png_voidp error_ptr, png_error_ptr error_fn,
png_error_ptr warning_fn);

إذا تم توفير NULL لأي من error_fn أو warning_fn، فسيتم استخدام وظيفة libpng الافتراضية، والتي تستدعي fprintf() و/أو longjmp() إذا تمت مواجهة مشكلة. يجب أن تحتوي وظائف الخطأ البديلة على معلمات كما يلي:


void user_error_fn(png_structp png_ptr,
png_const_charp error_msg);


void user_warning_fn(png_structp png_ptr,
png_const_charp warning_msg);

الدافع وراء استخدام setjmp() و longjmp() هو طرق C++ throw و catch لمعالجة الاستثناءات. هذا يجعل الكود أسهل بكثير للكتابة، حيث لا حاجة للتحقق من كل رمز إرجاع لكل استدعاء وظيفة. ومع ذلك، هناك بعض الشكوك حول حالة المتغيرات المحلية بعد longjmp، لذلك قد يرغب المستخدم في توخي الحذر بشأن القيام بأي شيء بعد أن تعود setjmp بقيمة غير صفرية بخلاف إرجاع نفسها. استشر وثائق المترجم الخاص بك لمزيد من التفاصيل. للحصول على نهج بديل، قد ترغب في استخدام مرفق "cexcept" (انظر https://cexcept.sourceforge.io/)، والذي يتم توضيحه في pngvalid.c وفي contrib/visupng.

بدءًا من libpng-1.4.0، أصبحت واجهة برمجة التطبيقات png_set_benign_errors() متاحة. يمكنك استخدام هذا لمعالجة بعض الأخطاء (التي يتم التعامل معها عادةً كأخطاء) كتحذيرات.

مقاطع مخصصة

إذا كنت بحاجة إلى قراءة أو كتابة مقاطع مخصصة، فقد تحتاج إلى التعمق أكثر في كود libpng. تحتوي المكتبة الآن على آليات لتخزين وكتابة مقاطع من نوع غير معروف؛ يمكنك حتى تعريف استدعاءات ردود الفعل لمقاطع مخصصة. ومع ذلك، قد لا يكون هذا جيدًا بما يكفي إذا كان كود المكتبة نفسه يحتاج إلى معرفة التفاعلات بين مقطعك والمقاطع "الأصلية" الموجودة.

إذا كنت بحاجة إلى كتابة مقطع أصلي جديد، فاقرأ أولاً مواصفات PNG. اكتسب مستوى فهم أول لكيفية عمله. انتبه بشكل خاص للأقسام التي تصف أسماء المقاطع، وانظر إلى كيفية تصميم المقاطع الأخرى، حتى تتمكن من فعل الأشياء بطريقة مماثلة. ثانيًا، تحقق من أقسام libpng التي تقرأ وتكتب المقاطع. حاول العثور على مقطع مشابه لمقطعك واستخدمه كقالب. مزيد من التفاصيل يمكن العثور عليها في التعليقات داخل الكود. من الأفضل التعامل مع المقاطع الخاصة أو غير المعروفة بطريقة عامة، عبر وظائف ردود الفعل، بدلاً من تعديل وظائف libpng. يتم توضيح ذلك في pngtest.c، والذي يستخدم وظيفة رد فعل للتعامل مع مقطع خاص "vpAg" والمقطع الجديد "sTER"، وكلاهما غير معروف لـ libpng.

إذا كنت ترغب في كتابة تحويل خاص بك للبيانات، فراجع جزء الكود الذي يقوم بالتحويلات، وتحقق من بعض التحويلات الأبسط للحصول على فكرة عن كيفية عملها. حاول العثور على تحويل مشابه للتحويل الذي تريد إضافته وانسخه منه. مزيد من التفاصيل يمكن العثور عليها في التعليقات داخل الكود نفسه.

X. Changes to Libpng from version 1.0.x/1.2.x to 1.4.x

Private libpng prototypes and macro definitions were moved from png.h and pngconf.h into a new pngpriv.h header file.

Functions png_set_benign_errors(), png_benign_error(), and png_chunk_benign_error() were added.

Support for setting the maximum amount of memory that the application will allocate for reading chunks was added, as a security measure. The functions png_set_chunk_cache_max() and png_get_chunk_cache_max() were added to the library.

We implemented support for I/O states by adding png_ptr member io_state and functions png_get_io_chunk_name() and png_get_io_state() in pngget.c

We added PNG_TRANSFORM_GRAY_TO_RGB to the available high-level input transforms.

Checking for and reporting of errors in the IHDR chunk is more thorough.

Support for global arrays was removed, to improve thread safety.

Some obsolete/deprecated macros and functions have been removed.

Typecasted NULL definitions such as
#define png_voidp_NULL (png_voidp)NULL were eliminated. If you used these in your application, just use NULL instead.

The png_struct and info_struct members "trans" and "trans_values" were changed to "trans_alpha" and "trans_color", respectively.

The obsolete, unused pnggccrd.c and pngvcrd.c files and related makefiles were removed.

The PNG_1_0_X and PNG_1_2_X macros were eliminated.

The PNG_LEGACY_SUPPORTED macro was eliminated.

Many WIN32_WCE #ifdefs were removed.

The functions png_read_init(info_ptr), png_write_init(info_ptr), png_info_init(info_ptr), png_read_destroy(), and png_write_destroy() have been removed. They have been deprecated since libpng-0.95.

The png_permit_empty_plte() was removed. It has been deprecated since libpng-1.0.9. Use png_permit_mng_features() instead.

We removed the obsolete stub functions png_get_mmx_flagmask(), png_set_mmx_thresholds(), png_get_asm_flags(), png_get_mmx_bitdepth_threshold(), png_get_mmx_rowbytes_threshold(), png_set_asm_flags(), and png_mmx_supported()

We removed the obsolete png_check_sig(), png_memcpy_check(), and png_memset_check() functions. Instead use png_sig_cmp() == 0, memcpy(), and memset(), respectively.

The function png_set_gray_1_2_4_to_8() was removed. It has been deprecated since libpng-1.0.18 and 1.2.9, when it was replaced with png_set_expand_gray_1_2_4_to_8() because the former function also expanded any tRNS chunk to an alpha channel.

Macros for png_get_uint_16, png_get_uint_32, and png_get_int_32 were added and are used by default instead of the corresponding functions. Unfortunately, from libpng-1.4.0 until 1.4.4, the png_get_uint_16 macro (but not the function) incorrectly returned a value of type png_uint_32.

We changed the prototype for png_malloc() from
png_malloc(png_structp png_ptr, png_uint_32 size) to
png_malloc(png_structp png_ptr, png_alloc_size_t size)

This also applies to the prototype for the user replacement malloc_fn().

The png_calloc() function was added and is used in place of of "png_malloc(); memset();" except in the case in png_read_png() where the array consists of pointers; in this case a "for" loop is used after the png_malloc() to set the pointers to NULL, to give robust. behavior in case the application runs out of memory part-way through the process.

We changed the prototypes of png_get_compression_buffer_size() and png_set_compression_buffer_size() to work with size_t instead of png_uint_32.

Support for numbered error messages was removed by default, since we never got around to actually numbering the error messages. The function png_set_strip_error_numbers() was removed from the library by default.

The png_zalloc() and png_zfree() functions are no longer exported. The png_zalloc() function no longer zeroes out the memory that it allocates. Applications that called png_zalloc(png_ptr, number, size) can call png_calloc(png_ptr, number*size) instead, and can call png_free() instead of png_zfree().

Support for dithering was disabled by default in libpng-1.4.0, because it has not been well tested and doesn't actually "dither". The code was not removed, however, and could be enabled by building libpng with PNG_READ_DITHER_SUPPORTED defined. In libpng-1.4.2, this support was re-enabled, but the function was renamed png_set_quantize() to reflect more accurately what it actually does. At the same time, the PNG_DITHER_[RED,GREEN_BLUE]_BITS macros were also renamed to PNG_QUANTIZE_[RED,GREEN,BLUE]_BITS, and PNG_READ_DITHER_SUPPORTED was renamed to PNG_READ_QUANTIZE_SUPPORTED.

We removed the trailing '.' from the warning and error messages.

XI. Changes to Libpng from version 1.4.x to 1.5.x

From libpng-1.4.0 until 1.4.4, the png_get_uint_16 macro (but not the function) incorrectly returned a value of type png_uint_32. The incorrect macro was removed from libpng-1.4.5.

Checking for invalid palette index on write was added at libpng 1.5.10. If a pixel contains an invalid (out-of-range) index libpng issues a benign error. This is enabled by default because this condition is an error according to the PNG specification, Clause 11.3.2, but the error can be ignored in each png_ptr with


png_set_check_for_invalid_index(png_ptr, allowed);


allowed - one of
0: disable benign error (accept the
invalid data without warning).
1: enable benign error (treat the
invalid data as an error or a
warning).

If the error is ignored, or if png_benign_error() treats it as a warning, any invalid pixels are decoded as opaque black by the decoder and written as-is by the encoder.

Retrieving the maximum palette index found was added at libpng-1.5.15. This statement must appear after png_read_png() or png_read_image() while reading, and after png_write_png() or png_write_image() while writing.


int max_palette = png_get_palette_max(png_ptr, info_ptr);

This will return the maximum palette index found in the image, or "-1" if the palette was not checked, or "0" if no palette was found. Note that this does not account for any palette index used by ancillary chunks such as the bKGD chunk; you must check those separately to determine the maximum palette index actually used.

There are no substantial API changes between the non-deprecated parts of the 1.4.5 API and the 1.5.0 API; however, the ability to directly access members of the main libpng control structures, png_struct and png_info, deprecated in earlier versions of libpng, has been completely removed from libpng 1.5, and new private "pngstruct.h", "pnginfo.h", and "pngdebug.h" header files were created.

We no longer include zlib.h in png.h. The include statement has been moved to pngstruct.h, where it is not accessible by applications. Applications that need access to information in zlib.h will need to add the '#include "zlib.h"' directive. بدءًا من libpng-1.6.19، يعتبر محاولة تعيين قطعة PLTE تتجاوز الطول المسموح به خطأً. في السابق، لم يتم فرض هذا المتطلب لمواصفات PNG، وتم تحديد عدد الإدخالات في اللوحة دائمًا عند 256. قطعة PLTE التي تتجاوز الطول المسموح به والموجودة في ملف PNG مدخل يتم اقتطاعها بصمت.

بدءًا من libpng-1.6.31، تم دعم قطعة eXIf. لا تحاول libpng فك تشفير ملف Exif التعريفي؛ بل تعيد ببساطة مصفوفة بايتات تحتوي على الملف التعريفي للتطبيق المستدعي الذي يجب أن يقوم بفك التشفير الخاص به.

اسم

libpng - مكتبة تشغيل صور PNG

نظرة عامة

#include <png.h>

وصف

مكتبة libpng هي مكتبة C غير رسمية للتعامل مع ملفات PNG. تم تصميمها لتوفير وظائف لإنشاء وقراءة ومعالجة ملفات PNG. تدعم المكتبة الإصدار 1.0 و 1.2 و 1.4 و 1.5 و 1.6 من مواصفات PNG.

تتكون المكتبة من مجموعة من الملفات المصدر في C، والتي يمكن تجميعها كمكتبة ثابتة أو ديناميكية. يتم توفير ملفات الرأس الضرورية في "png.h".

ميزات

  • قراءة وكتابة ملفات PNG.
  • دعم مختلف ألوان PNG (رمادي، RGB، ملون، مع قناة ألفا).
  • ضغط وفك ضغط بيانات PNG.
  • التحقق من سلامة ملفات PNG.
  • دعم نطاقات ألوان PNG متعددة (8 بت، 16 بت).
  • التعامل مع أخطاء PNG.

أمثلة

يمكن العثور على أمثلة على استخدام libpng في مستودع libpng الرسمي.

أخطاء

تقوم libpng بإرجاع رموز أخطاء للإشارة إلى المشكلات. يمكن معالجة هذه الأخطاء باستخدام وظائف المعالجة المناسبة.

متغيرات البيئة

لا تستخدم libpng أي متغيرات بيئة.

ملاحظات

عند استخدام libpng، من المهم التأكد من أن لديك إصدارًا متوافقًا مع متطلباتك. تأكد من التحقق من وثائق الإصدار المحدد الذي تستخدمه.
