link(2) دليل استدعاءات النظام link(2)

الاسم

link, linkat - إنشاء اسم جديد لملف

المكتبة

مكتبة C القياسية (libc, -lc)

ملخص

#include <unistd.h>
int link(const char *oldpath, const char *newpath);
#include <fcntl.h>           /* تعريف ثوابت AT_* */
#include <unistd.h>
int linkat(int olddirfd, const char *oldpath,
           int newdirfd, const char *newpath, int flags);
متطلبات ميزة الاختبار (Feature Test Macro Requirements) لـ glibc (انظر feature_test_macros(7)):

linkat():

    منذ glibc 2.10:
        _POSIX_C_SOURCE >= 200809L
    قبل glibc 2.10:
        _ATFILE_SOURCE

الوصف

يقوم link() بإنشاء ارتباط جديد (يُعرف أيضًا باسم الارتباط الصلب) لملف موجود.

إذا كان newpath موجودًا، فلن يتم الكتابة فوقه.

يمكن استخدام هذا الاسم الجديد تمامًا مثل الاسم القديم لأي عملية؛ كلا الاسمين يشيران إلى نفس الملف (وبالتالي لهما نفس الأذونات والملكية) ويستحيل معرفة أي اسم كان "الأصلي".

linkat()

تعمل استدعاء النظام linkat() بنفس الطريقة تمامًا مثل link()، باستثناء الاختلافات الموضحة هنا.

إذا كان المسار المحدد في oldpath نسبيًا، فسيتم تفسيره بالنسبة للدليل المشار إليه بواسطة واصف الملف olddirfd (بدلاً من الدليل الحالي لعملية الاستدعاء، كما يفعل link() للمسار النسبي).

إذا كان oldpath نسبيًا وكان olddirfd هو القيمة الخاصة AT_FDCWD، فسيتم تفسير oldpath بالنسبة للدليل الحالي لعملية الاستدعاء (مثل link()).

إذا كان oldpath مطلقًا، فسيتم تجاهل olddirfd.

تفسير newpath كما هو الحال بالنسبة لـ oldpath، باستثناء أن المسار النسبي سيتم تفسيره بالنسبة للدليل المشار إليه بواسطة واصف الملف newdirfd.

يمكن دمج القيم التالية في flags:

AT_EMPTY_PATH (منذ Linux 2.6.39)
إذا كان oldpath سلسلة فارغة، فقم بإنشاء ارتباط للملف الذي يشير إليه olddirfd (والذي ربما تم الحصول عليه باستخدام open(2) مع العلامة O_PATH). في هذه الحالة، يمكن لـ olddirfd الإشارة إلى أي نوع من الملفات باستثناء الدليل. بشكل عام، لن يعمل هذا إذا كان للملف عدد روابط يساوي صفر (الملفات التي تم إنشاؤها باستخدام O_TMPFILE وبدون O_EXCL هي استثناء). يجب أن تمتلك الجهة المستدعية القدرة CAP_DAC_READ_SEARCH لاستخدام هذه العلامة. هذه العلامة خاصة بنظام Linux؛ قم بتعريف _GNU_SOURCE للحصول على تعريفها.
AT_SYMLINK_FOLLOW (منذ Linux 2.6.18)
افتراضيًا، لا يقوم linkat() بتتبع oldpath إذا كان رابطًا رمزيًا (مثل link()). يمكن تحديد العلامة AT_SYMLINK_FOLLOW في flags لتتبع oldpath إذا كان رابطًا رمزيًا. إذا كان procfs مثبتًا، فيمكن استخدام هذا كبديل لـ AT_EMPTY_PATH، كالتالي:

linkat(AT_FDCWD, "/proc/self/fd/<fd>", newdirfd,
       newname, AT_SYMLINK_FOLLOW);

قبل Linux 2.6.18، لم يتم استخدام الوسيط flags، وكان يجب تحديده كـ 0.

انظر openat(2) لشرح الحاجة إلى linkat().

قيمة الإرجاع

عند النجاح، يتم إرجاع صفر. عند حدوث خطأ، يتم إرجاع -1، ويتم تعيين errno للإشارة إلى الخطأ.

الأخطاء

EACCES
تم رفض الوصول للكتابة إلى الدليل الذي يحتوي على newpath، أو تم رفض إذن البحث لأحد الأدلة في بادئة المسار لـ oldpath أو newpath. (انظر أيضًا path_resolution(7)).
EDQUOT
تم استنفاد حصة المستخدم من كتل القرص على نظام الملفات.
EEXIST
newpath موجود بالفعل.
EFAULT
oldpath أو newpath يشير خارج مساحة العنوان التي يمكن الوصول إليها.
EIO
حدث خطأ إدخال/إخراج.
ELOOP
تم العثور على عدد كبير جدًا من الروابط الرمزية أثناء تحليل oldpath أو newpath.
EMLINK
الملف المشار إليه بواسطة oldpath لديه بالفعل الحد الأقصى لعدد الارتباطات به. على سبيل المثال، في نظام ملفات ext4(5) الذي لا يستخدم ميزة dir_index، الحد الأقصى لعدد الارتباطات الصلبة لملف هو 65000؛ على btrfs(5)، الحد هو 65535 ارتباطًا.
ENAMETOOLONG
oldpath أو newpath كان طويلاً جدًا.
ENOENT
مكون دليل في oldpath أو newpath غير موجود أو هو رابط رمزي معلق.
ENOMEM
لم تكن هناك ذاكرة كافية في النواة متاحة.
ENOSPC
لا توجد مساحة في الجهاز الذي يحتوي على الملف لإدخال الدليل الجديد.
ENOTDIR
مكون تم استخدامه كدليل في oldpath أو newpath ليس في الواقع دليلًا.
EPERM
oldpath هو دليل.
EPERM
نظام الملفات الذي يحتوي على oldpath و newpath لا يدعم إنشاء الارتباطات الصلبة.
EPERM (منذ Linux 3.6)
لا تملك الجهة المستدعية الإذن بإنشاء ارتباط صلب لهذا الملف (انظر وصف /proc/sys/fs/protected_hardlinks في proc_sys_fs(5)).
EPERM
oldpath معلم كـ "غير قابل للتعديل" (immutable) أو "قابل للإلحاق فقط" (append-only). (انظر FS_IOC_SETFLAGS(2const).)
EROFS
الملف موجود على نظام ملفات للقراءة فقط.
EXDEV
oldpath و newpath ليسا على نفس نظام الملفات المثبت. (يسمح Linux بنظام ملفات مثبت في نقاط متعددة، ولكن link() لا يعمل عبر وحدات التحميل المختلفة، حتى لو تم تحميل نفس نظام الملفات على كليهما.)

الأخطاء الإضافية التالية يمكن أن تحدث لـ linkat():

EBADF
oldpath (newpath) نسبي ولكن olddirfd (newdirfd) ليس AT_FDCWD وليس واصف ملف صالح.
EINVAL
تم تحديد قيمة علامة غير صالحة في flags.
ENOENT
تم تحديد AT_EMPTY_PATH في flags، ولكن الجهة المستدعية لم تمتلك القدرة CAP_DAC_READ_SEARCH.
ENOENT
تمت محاولة ربط ملف /proc/self/fd/NN المقابل لواصف ملف تم إنشاؤه بواسطة

open(path, O_TMPFILE | O_EXCL, mode);

انظر open(2).

linkat - إنشاء رابط (link)

NAME

linkat - إنشاء رابط (link)

LIBRARY

Linux POSIX API

SYNOPSIS

    #include <fcntl.h>

    int linkat(int dirfd1, const char *pathname1,
               int dirfd2, const char *pathname2, unsigned int flags);

DESCRIPTION

The linkat() system call is similar to link(2), but differs in the way it handles pathnames.

The arguments are as follows:

dirfd1
A file descriptor that specifies the directory in which the new link (pathname2) will be created. If dirfd1 is the special value AT_FDCWD, then pathname2 is interpreted relative to the current working directory.
pathname1
The pathname of the existing file to be linked to. This is the oldpath argument from link(2). If pathname1 is relative, it is interpreted relative to the directory referred to by dirfd1 (unless dirfd1 is AT_FDCWD).
dirfd2
A file descriptor that specifies the directory in which the new link (pathname2) will be created. If dirfd2 is the special value AT_FDCWD, then pathname2 is interpreted relative to the current working directory.
pathname2
The pathname of the new link to be created. This is the newpath argument from link(2). If pathname2 is relative, it is interpreted relative to the directory referred to by dirfd2 (unless dirfd2 is AT_FDCWD).
flags
A bit mask that modifies the behavior of the call. The only recognized flag value is AT_SYMLINK_FOLLOW. If this flag is specified, then the behavior is the same as link(2): if pathname1 refers to a symbolic link, then pathname2 is created as a hard link to the file referred to by the symbolic link. If AT_SYMLINK_FOLLOW is not specified, then if pathname1 refers to a symbolic link, pathname2 is created as a hard link to the symbolic link file itself.

The arguments dirfd1 and dirfd2 are file descriptors obtained from open(2) (or other functions that return file descriptors). These file descriptors should refer to directories.

See path_resolution(7) for a discussion of the differences between relative and absolute pathnames and the roles of AT_FDCWD and directory file descriptors.

RETURN VALUE

On success, linkat() returns 0. On error, it returns -1, and errno is set to indicate the error.

ERRORS

The errors documented for link(2) also apply to linkat(). In addition, the following errors may occur:

EBADF
oldpath is relative, and olddirfd is not a valid file descriptor or refers to a file that is not a directory. Similar for newpath and newdirfd.
ENOENT
An attempt was made to link to a /proc/self/fd/NN file corresponding to a file that has been deleted.
ENOENT
oldpath is a relative pathname and olddirfd refers to a directory that has been deleted, or newpath is a relative pathname and newdirfd refers to a directory that has been deleted.
ENOTDIR
oldpath is relative and olddirfd is a file descriptor referring to a file other than a directory; or similar for newpath and newdirfd
EPERM
AT_EMPTY_PATH was specified in flags, oldpath is an empty string, and olddirfd refers to a directory.

VERSIONS

POSIX.1-2001 says that link() should dereference oldpath if it is a symbolic link. However, since Linux 2.0, Linux does not do so: if oldpath is a symbolic link, then newpath is created as a (hard) link to the same symbolic link file (i.e., newpath becomes a symbolic link to the same file that oldpath refers to). Some other implementations behave in the same manner as Linux. POSIX.1-2008 changes the specification of link(), making it implementation-dependent whether or not oldpath is dereferenced if it is a symbolic link. For precise control over the treatment of symbolic links when creating a link, use linkat().

glibc

On older kernels where linkat() is unavailable, the glibc wrapper function falls back to the use of link(), unless the AT_SYMLINK_FOLLOW is specified. When oldpath and newpath are relative pathnames, glibc constructs pathnames based on the symbolic links in /proc/self/fd that correspond to the olddirfd and newdirfd arguments.

STANDARDS

POSIX.1-2024.

HISTORY

link()
SVr4, 4.3BSD, POSIX.1-2001 (but see VERSIONS).
linkat()
POSIX.1-2008. Linux 2.6.16, glibc 2.4.

NOTES

Hard links, as created by link(), cannot span filesystems. Use symlink(2) if this is required.

BUGS

On NFS filesystems, the return code may be wrong in case the NFS server performs the link creation and dies before it can say so. Use stat(2) to find out if the link got created.
