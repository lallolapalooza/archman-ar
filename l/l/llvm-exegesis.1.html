>على سبيل المثال، تعتمد مقتطفة الشفرة التالية على قيم XMM1 (التي سيتم تعيينها بواسطة الأداة) والمخزن المؤقت للذاكرة الذي تم تمريره في RDI (حالي).

# LLVM-EXEGESIS-LIVEIN RDI
# LLVM-EXEGESIS-DEFREG XMM1 42
vmulps        (%rdi), %xmm1, %xmm2
vhaddps       %xmm2, %xmm2, %xmm3
addq $0x10, %rdi

مثال 3: القياس مع تعليقات الذاكرة

تتطلب بعض المقتطفات إعداد الذاكرة في أماكن محددة للتنفيذ دون تعطل. يمكن تحقيق إعداد الذاكرة باستخدام التعليقات التوضيحية LLVM-EXEGESIS-MEM-DEF و LLVM-EXEGESIS-MEM-MAP. لتنفيذ المقتطفة التالية:

movq $8192, %rax
movq (%rax), %rdi

نحتاج إلى تخصيص ثمانية بايتات على الأقل من الذاكرة بدءًا من 0x2000. يمكننا إنشاء بيئة التنفيذ اللازمة بالتعليقات التوضيحية التالية المضافة إلى المقتطفة:

# LLVM-EXEGESIS-MEM-DEF test1 4096 7fffffff
# LLVM-EXEGESIS-MEM-MAP test1 8192
movq $8192, %rax
movq (%rax), %rdi

مثال 4: التحليل

بافتراض أن لديك مجموعة من التعليمات المقاسة (إما زمن الوصول أو وحدات العمليات) بصيغة YAML في الملف /tmp/benchmarks.yaml، يمكنك تحليل النتائج باستخدام الأمر التالي:

  $ llvm-exegesis --mode=analysis \
--benchmarks-file=/tmp/benchmarks.yaml \
--analysis-clusters-output-file=/tmp/clusters.csv \
--analysis-inconsistencies-output-file=/tmp/inconsistencies.html

سيؤدي هذا إلى تجميع التعليمات في مجموعات ذات خصائص أداء متطابقة. سيتم كتابة المجموعات إلى /tmp/clusters.csv بالتنسيق التالي:

cluster_id,opcode_name,config,sched_class
...
2,ADD32ri8_DB,,WriteALU,1.00
2,ADD32ri_DB,,WriteALU,1.01
2,ADD32rr,,WriteALU,1.01
2,ADD32rr_DB,,WriteALU,1.00
2,ADD32rr_REV,,WriteALU,1.00
2,ADD64i32,,WriteALU,1.01
2,ADD64ri32,,WriteALU,1.01
2,MOVSX64rr32,,BSWAP32r_BSWAP64r_MOVSX64rr32,1.00
2,VPADDQYrr,,VPADDBYrr_VPADDDYrr_VPADDQYrr_VPADDWYrr_VPSUBBYrr_VPSUBDYrr_VPSUBQYrr_VPSUBWYrr,1.02
2,VPSUBQYrr,,VPADDBYrr_VPADDDYrr_VPADDQYrr_VPADDWYrr_VPSUBBYrr_VPSUBDYrr_VPSUBQYrr_VPSUBWYrr,1.01
2,ADD64ri8,,WriteALU,1.00
2,SETBr,,WriteSETCC,1.01
...

سيقوم llvm-exegesis أيضًا بتحليل المجموعات للإشارة إلى التناقضات في معلومات الجدولة. الناتج هو ملف html. على سبيل المثال، سيحتوي /tmp/inconsistencies.html على رسائل مثل ما يلي: [صورة]

لاحظ أنه سيتم حل أسماء فئات الجدولة فقط عند تجميع llvm-exegesis في وضع التصحيح، وإلا سيتم عرض المعرف فقط. هذا لا يبطل أيًا من نتائج التحليل.

الخيارات

--help
طباعة ملخص لخيارات سطر الأوامر.
--opcode-index=<فهرس LLVM للعملية>
تحديد العملية المراد قياسها، عن طريق الفهرس. سيؤدي تحديد -1 إلى قياس كل عملية موجودة. انظر المثال 1 لمزيد من التفاصيل. يجب تعيين opcode-index أو opcode-name أو snippets-file.
--opcode-name=<اسم العملية 1>،<اسم العملية 2>،...
تحديد العملية المراد قياسها، بالاسم. يمكن تحديد عدة عمليات كقائمة مفصولة بفواصل. انظر المثال 1 لمزيد من التفاصيل. يجب تعيين opcode-index أو opcode-name أو snippets-file.
--snippets-file=<اسم الملف>
تحديد مقتطفة الشفرة المخصصة المراد قياسها. انظر المثال 2 لمزيد من التفاصيل. يجب تعيين opcode-index أو opcode-name أو snippets-file.
--mode=[latency|uops|inverse_throughput|analysis]
تحديد وضع التشغيل. لاحظ أن بعض الأوضاع لها متطلبات وخيارات إضافية.

يمكن لوضع latency الاستفادة من RDTSC أو LBR. latency[LBR] متاح فقط على X86 (على الأقل Skylake). للعمل في وضع latency، يجب تحديد قيمة موجبة لـ x86-lbr-sample-period و --repetition-mode=loop.

في وضع analysis، تحتاج أيضًا إلى تحديد واحد على الأقل من -analysis-clusters-output-file= و -analysis-inconsistencies-output-file=.

--benchmark-phase=[prepare-snippet|prepare-and-assemble-snippet|assemble-measured-code|measure]
بشكل افتراضي، عند تحديد -mode=، سيتم تنفيذ المقتطفة التي تم إنشاؤها وقياسها، ويتطلب ذلك أننا نعمل على الأجهزة التي تم إنشاء المقتطفة لها، والتي تدعم قياسات الأداء. ومع ذلك، من الممكن التوقف عند مرحلة ما قبل القياس. الخيارات هي: * prepare-snippet: إنشاء الحد الأدنى من تسلسل التعليمات فقط. * prepare-and-assemble-snippet: نفس prepare-snippet، ولكن يطرح أيضًا جزءًا من التسلسل (مشفر بالنظام الست عشري). * assemble-measured-code: نفس prepare-and-assemble-snippet. ولكن ينشئ أيضًا التسلسل الكامل الذي يمكن طرحه في ملف باستخدام --dump-object-to-disk. * measure: نفس assemble-measured-code. ولكن يقوم أيضًا بتشغيل القياس.
--x86-lbr-sample-period=<عدد الفروع/عينة>
تحديد فترة أخذ عينات LBR - كم عدد الفروع قبل أن نأخذ عينة. عندما يتم تحديد قيمة موجبة لهذا الخيار وعندما يكون الوضع latency، سنستخدم LBRs للقياس. عند اختيار فترة أخذ العينات "الصحيحة"، يفضل قيمة صغيرة، ولكن يمكن أن يحدث اختناق إذا كان أخذ العينات متكررًا جدًا. يجب استخدام رقم أولي لتجنب تخطي كتل معينة باستمرار.
--x86-disable-upper-sse-registers
استخدام سجلات xmm العلوية (xmm8-xmm15) يجبر على تشفير تعليمات أطول قد يضع ضغطًا أكبر على مراحل جلب وفك تشفير الواجهة الأمامية، مما قد يقلل من معدل إرسال التعليمات إلى الواجهة الخلفية، خاصة على الأجهزة القديمة. يمكن أن يساعد مقارنة النتائج الأساسية مع تمكين هذا الوضع في تحديد تأثيرات الواجهة الأمامية ويمكن استخدامه لتحسين تقديرات زمن الوصول والإنتاجية.
--repetition-mode=[duplicate|loop|min|middle-half-duplicate|middle-half-loop]
تحديد وضع التكرار. سيقوم duplicate بإنشاء كتلة أساسية كبيرة ومستقيمة تحتوي على min-instructions تعليمات (تكرار المقتطفة min-instructions/حجم المقتطفة مرات). سيقوم loop، اختياريًا، بتكرار المقتطفة حتى تحتوي على جسم الحلقة على الأقل loop-body-size تعليمات، ثم يغلف النتيجة في حلقة ستنفذ min-instructions تعليمات (وبالتالي، مرة أخرى، تكرار المقتطفة min-instructions/حجم المقتطفة مرات). وضع loop، خاصة مع تكرار الحلقة، يميل إلى إخفاء تأثيرات الواجهة الأمامية لوحدة المعالجة المركزية بشكل أفضل على البنى التي تخزن التعليمات المفككة مؤقتًا، ولكنه يستهلك سجلًا لحساب التكرارات. إذا كنت تقوم بإجراء تحليل على العديد من العمليات، فقد يكون من الأفضل استخدام وضع min، والذي سيقوم بتشغيل كل وضع آخر، وإنتاج الحد الأدنى من النتائج المقاسة. أوضاع تكرار النصف الأوسط ستقوم إما بتكرار المقتطفة أو تشغيلها في حلقة اعتمادًا على الوضع المحدد. أوضاع تكرار النصف الأوسط ستنفذ قياسين، أحدهما ضعف طول الأول، ثم تطرح الفرق بينهما للحصول على قيم بدون عبء إضافي.
--min-instructions=<عدد التعليمات>
تحديد العدد المستهدف للتعليمات المنفذة. لاحظ أن عدد التكرارات الفعلي للمقتطفة سيكون min-instructions/حجم المقتطفة. تؤدي القيم الأعلى إلى قياسات أكثر دقة ولكنها تطيل مدة القياس.
--loop-body-size=<حجم جسم الحلقة المفضل>
فعال فقط لـ -repetition-mode=[loop|min]. بدلاً من التكرار على المقتطفة مباشرة، قم أولاً بتكرارها بحيث يحتوي جسم الحلقة على عدد من التعليمات لا يقل عن هذا العدد. هذا قد يؤدي إلى تخزين جسم الحلقة مؤقتًا في ذاكرة التخزين المؤقت للتعليمات / ذاكرة التخزين المؤقت للحلقات بوحدة المعالجة المركزية، مما يسمح بنفاذية أعلى من وحدات فك التشفير بوحدة المعالجة المركزية.
--max-configs-per-opcode=<القيمة>
تحديد الحد الأقصى للتكوينات التي يمكن إنشاؤها لكل عملية. افتراضيًا، هذا هو 1، مما يعني أننا نفترض أن قياسًا واحدًا يكفي لوصف العملية. قد لا يكون هذا صحيحًا لجميع التعليمات: على سبيل المثال، تعتمد خصائص أداء تعليمة LEA على X86 على قيمة السجلات والمقادير الصحيحة المعينة. يسمح تعيين قيمة أكبر من -max-configs-per-opcode من 1 لـ llvm-exegesis باستكشاف المزيد من التكوينات لاكتشاف ما إذا كانت بعض تعيينات السجلات أو المقادير الصحيحة تؤدي إلى خصائص أداء مختلفة.
--benchmarks-file=</مسار/إلى/الملف>
الملف للقراءة (وضع analysis) أو الكتابة (أوضاع latency/uops/inverse_throughput) نتائج القياس. "-" يستخدم stdin/stdout.
--analysis-clusters-output-file=</مسار/إلى/الملف>
إذا تم توفيره، قم بكتابة مجموعات التحليل كـ CSV إلى هذا الملف. "-" يطبع إلى stdout. افتراضيًا، لا يتم تشغيل هذا التحليل.

llvm-exegesis(1)

الحزمة: llvm

التراخيص: Apache-2.0 WITH LLVM-exception

NAME

llvm-exegesis ‐ Instruction Benchmarking Utility

SYNOPSIS

llvm-exegesis [options] [input files]

DESCRIPTION

llvm-exegesis is a tool for benchmarking small code snippets to measure instruction latency, throughput, and other performance characteristics. It can benchmark individual instructions or entire code snippets, and analyze the results to identify inconsistencies or performance regressions.

SUPPORTED PLATFORMS

Currently, llvm-exegesis is primarily supported on x86-64 and AArch64.

SNIPPET ANNOTATIONS

Code snippets can be annotated with special comments to guide llvm-exegesis's analysis and benchmarking process. These annotations allow specifying details such as memory access patterns, execution constraints, and performance counter configurations.

// Exegesis: latency
Measures the latency of the instruction(s).
// Exegesis: throughput
Measures the throughput of the instruction(s).
// Exegesis: num-instructions <N>
Specifies the number of instructions to benchmark.
// Exegesis: num-cycles <N>
Specifies the expected number of cycles for the instruction(s).
// Exegesis: max-latency <N>
Sets the maximum acceptable latency.
// Exegesis: max-throughput <N>
Sets the maximum acceptable throughput.
// Exegesis: memory[<read|write|sequential|random>]
Annotates memory access patterns.
// Exegesis: register[<use|define>]
Annotates register usage.
// Exegesis: cp-event[<event-name>]
Specifies a performance counter event for validation.

EXAMPLE 1: BENCHMARKING INSTRUCTIONS

To benchmark the latency of the `add` instruction:

cat <<EOF | llvm-exegesis --benchmark-instruction=add
// Exegesis: latency
ADD X0, X1, X2
EOF

EXAMPLE 2: BENCHMARKING A CUSTOM CODE SNIPPET

To benchmark a custom code snippet and measure throughput:

cat <<EOF | llvm-exegesis --benchmark-mode=throughput
// Exegesis: throughput
ADD X0, X1, X2
ADD X3, X4, X5
EOF

EXAMPLE 3: BENCHMARKING WITH MEMORY ANNOTATIONS

Benchmarking a snippet with memory read annotations:

cat <<EOF | llvm-exegesis --benchmark-mode=latency
// Exegesis: latency
// Exegesis: memory=read
LDR X0, [X1]
ADD X2, X0, X3
EOF

EXAMPLE 4: ANALYSIS

Analyzing benchmark results for inconsistencies:

llvm-exegesis --analysis-inconsistencies-output-file=inconsistencies.txt \
              --analysis-filter=all --analysis-clustering=naive \
              --benchmark-input-file=benchmarks.ll

OPTIONS

--analysis-inconsistencies-output-file=</path/to/file>
If non-empty, write inconsistencies found during analysis to this file. - prints to stdout. By default, this analysis is not run.
--analysis-filter=[all|reg-only|mem-only]
By default, all benchmark results are analysed, but sometimes it may be useful to only look at those that to not involve memory, or vice versa. This option allows to either keep all benchmarks, or filter out (ignore) either all the ones that do involve memory (involve instructions that may read or write to memory), or the opposite, to only keep such benchmarks.
--analysis-clustering=[dbscan,naive]
Specify the clustering algorithm to use. By default DBSCAN will be used. Naive clustering algorithm is better for doing further work on the -analysis-inconsistencies-output-file= output, it will create one cluster per opcode, and check that the cluster is stable (all points are neighbours).
--analysis-numpoints=<dbscan numPoints parameter>
Specify the numPoints parameters to be used for DBSCAN clustering (analysis mode, DBSCAN only).
--analysis-clustering-epsilon=<dbscan epsilon parameter>
Specify the epsilon parameter used for clustering of benchmark points (analysis mode).
--analysis-inconsistency-epsilon=<epsilon>
Specify the epsilon parameter used for detection of when the cluster is different from the LLVM schedule profile values (analysis mode).
--analysis-display-unstable-clusters
If there is more than one benchmark for an opcode, said benchmarks may end up not being clustered into the same cluster if the measured performance characteristics are different. by default all such opcodes are filtered out. This flag will instead show only such unstable opcodes.
--ignore-invalid-sched-class=false
If set, ignore instructions that do not have a sched class (class idx = 0).
--mtriple=<triple name>
Target triple. See -version for available targets.
--mcpu=<cpu name>
If set, measure the cpu characteristics using the counters for this CPU. This is useful when creating new sched models (the host CPU is unknown to LLVM). (-mcpu=help for details)
--analysis-override-benchmark-triple-and-cpu
By default, llvm-exegesis will analyze the benchmarks for the triple/CPU they were measured for, but if you want to analyze them for some other combination (specified via -mtriple/-mcpu), you can pass this flag.
--dump-object-to-disk=<filename>
If set, llvm-exegesis will dump the generated code to a temporary file to enable code inspection. Disabled by default.
--use-dummy-perf-counters
If set, llvm-exegesis will not read any real performance counters and return a dummy value instead. This can be used to ensure a snippet doesn't crash when hardware performance counters are unavailable and for debugging llvm-exegesis itself.
--execution-mode=[inprocess,subprocess]
This option specifies what execution mode to use. The inprocess execution mode is the default. The subprocess execution mode allows for additional features such as memory annotations but is currently restricted to X86-64 on Linux.
--benchmark-repeat-count=<repeat-count>
This option enables specifying the number of times to repeat the measurement when performing latency measurements. By default, llvm-exegesis will repeat a latency measurement enough times to balance run-time and noise reduction.
--validation-counter=[instructions-retired,l1d-cache-load-misses,
l1d-cache-store-misses,l1i-cache-load-misses,data-tlb-load-misses,
data-tld-store-misses,instruction-tlb-load-misses]
This option enables the use of validation counters, which measure additional microarchitectural events like cache misses to validate snippet execution conditions. These events are measured using the perf subsystem in a group with the performance counter used to measure the value of interest. This flag can be specified multiple times to measure multiple events. The maximum number of validation counters is platform dependent.
--benchmark-process-cpu=<cpu id>
This option specifies the number of the CPU that should be used to run the benchmarking subprocess. When starting the subprocess, llvm-exegesis will set the affinity of the subprocess to only include the specified CPU. This option only works in the subprocess execution mode.

EXIT STATUS

llvm-exegesis returns 0 on success. Otherwise, an error message is printed to standard error, and the tool returns a non 0 value.
