Clone the specified repository and leave the working directory in the state of the specified revision.

hg clone [-U] [-r REV] [-b BRANCH] [--pull] [--uncompressed] [--stream] [-e CMD] [--remotecmd CMD] [--insecure] SOURCE [DEST]

Clone the specified repository into a new local repository. The default is to create the destination repository in the current directory and check out the tip revision.

It is possible to specify an ssh:// URL as the destination. See hg help urls for more information.

Examples:

  • clone a repository into a subdirectory: 
    hg clone https://www.mercurial-scm.org/repo/hg/ experimental/
  • clone only specific changesets after a particular revision: 
    hg clone -r 04e544 experimental/ good/
  • clone (and track) a particular named branch: 
    hg clone https://www.mercurial-scm.org/repo/hg/#stable

See hg help urls for details on specifying URLs.

Returns 0 on success.

Options:

-u,--updaterev <REV>

-r,--rev <REV[+]>

- heading: Remote repository management - heading: incoming content: |

show new changesets found in source:

hg incoming [-p] [-n] [-M] [-f] [-r REV]... [--bundle FILENAME] [SOURCE]

Show new changesets found in the specified path/URL or the default pull location. These are the changesets that would have been pulled by hg pull at the time you issued this command.

See pull for valid source format details.

With -B/--bookmarks, the result of bookmark comparison between local and remote repositories is displayed. With -v/--verbose, status is also displayed for each bookmark like below:

BM1               01234567890a added
BM2               1234567890ab advanced
BM3               234567890abc diverged
BM4               34567890abcd changed

The action taken locally when pulling depends on the status of each bookmark:

added

pull will create it

advanced

pull will update it

diverged

pull will create a divergent bookmark

changed

result depends on remote changesets

From the point of view of pulling behavior, bookmark existing only in the remote repository are treated as added, even if it is in fact locally deleted.

For remote repository, using --bundle avoids downloading the changesets twice if the incoming is followed by a pull.

Examples:

  • show incoming changes with patches and full description: 
    hg incoming -vp
  • show incoming changes excluding merges, store a bundle: 
    hg in -vpM --bundle incoming.hg
        hg pull incoming.hg
  • briefly list changes inside a bundle: 
    hg in changes.hg -T "<desc|firstline>\n"

Returns 0 if there are incoming changes, 1 otherwise.

archive

إنشاء أرشيف غير مُدار الإصدارات لمراجعة مستودع:

hg archive [OPTION]... DEST

افتراضيًا، تكون المراجعة المستخدمة هي الأصل لدليل العمل؛ استخدم -r/--rev لتحديد مراجعة مختلفة.

يتم اكتشاف نوع الأرشيف تلقائيًا بناءً على امتداد الملف (للتجاوز، استخدم -t/--type).

أمثلة:

  • إنشاء ملف zip يحتوي على الإصدار 1.0: 
    hg archive -r 1.0 project-1.0.zip
  • إنشاء ملف tar يستثني ملفات .hg: 
    hg archive project.tar.gz -X ".hg*"

أرشيف zip، غير مضغوط

يتم إعطاء الاسم الدقيق للأرشيف الوجهة أو الدليل باستخدام سلسلة تنسيق؛ راجع hg help export للحصول على التفاصيل.

تتم إضافة بادئة دليل إلى كل عضو مضاف إلى ملف أرشيف. استخدم -p/--prefix لتحديد سلسلة تنسيق للبادئة. الافتراضي هو الاسم الأساسي للأرشيف، مع إزالة اللاحقات.

bundle

إنشاء ملف حزمة:

hg bundle [-f] [-t BUNDLESPEC] [-a] [-r REV]... [--base REV]... FILE [DEST]...

إنشاء ملف حزمة يحتوي على بيانات ليتم نقلها إلى مستودع آخر.

لإنشاء حزمة تحتوي على جميع التغييرات، استخدم -a/--all (أو --base null). بخلاف ذلك، يفترض hg أن الوجهة ستحتوي على جميع العقد التي تحددها باستخدام معلمات --base. بخلاف ذلك، سيفترض hg أن المستودع يحتوي على جميع العقد في الوجهة، أو افتراضي-push/افتراضي إذا لم يتم تحديد وجهة، حيث الوجهة هي المستودعات التي تقدمها من خلال خيار DEST.

يمكنك تغيير تنسيق الحزمة باستخدام الخيار -t/--type. راجع hg help bundlespec للحصول على توثيق لهذا التنسيق. افتراضيًا، يتم استخدام التنسيق الأنسب، ويتم تعيين ضغط bzip2 افتراضيًا.

يمكن بعد ذلك نقل ملف الحزمة باستخدام الوسائل التقليدية وتطبيقه على مستودع آخر باستخدام أمر unbundle أو pull. هذا مفيد عندما لا تكون الدفع والسحب المباشر متاحين أو عندما يكون تصدير مستودع كامل غير مرغوب فيه.

تطبيق الحزم يحافظ على جميع محتويات التغييرات بما في ذلك الأذونات، معلومات النسخ/إعادة التسمية، وسجل المراجعة.

يعيد 0 عند النجاح، 1 في حالة عدم العثور على تغييرات.

export

تفريغ الرأس والفروقات لتغيير واحد أو أكثر:

hg export [OPTION]... [-o OUTFILESPEC] [-r] [REV]...

طباعة رأس التغيير والفروقات لمراجعة واحدة أو أكثر. إذا لم يتم تقديم مراجعة، فسيتم استخدام الأصل لدليل العمل.

المعلومات المعروضة في رأس التغيير هي: المؤلف، التاريخ، اسم الفرع (إذا لم يكن افتراضيًا)، تجزئة التغيير، الأصل (الأصول)، وتعليق الالتزام.

ملاحظة
hg export قد ينتج عنه مخرجات فروقات غير متوقعة لتغييرات الدمج، لأنه سيقارن تغيير الدمج مع أصله الأول فقط.

قد تكون المخرجات إلى ملف، وفي هذه الحالة يتم إعطاء اسم الملف باستخدام سلسلة قالب. راجع hg help templates. بالإضافة إلى كلمات القالب الشائعة، يتم دعم قواعد التنسيق التالية:

%%

حرف "%" حرفي

%H

تجزئة التغيير (40 رقم ست عشري)

%N

عدد الرقع التي يتم إنشاؤها

%R

رقم مراجعة التغيير

%b

الاسم الأساسي للمستودع المصدر

%h

تجزئة التغيير مختصرة (12 رقم ست عشري)

%m

السطر الأول من رسالة الالتزام (الأحرف الأبجدية الرقمية فقط)

%n

رقم تسلسلي مبطن بالأصفار، يبدأ من 1

%r

رقم مراجعة التغيير مبطن بالأصفار

بدون الخيار -a/--text، سيتجنب التصدير إنشاء فروقات للملفات التي يكتشف أنها ثنائية. مع -a، سينشئ التصدير فروقات على أي حال، مع نتائج غير مرغوب فيها على الأرجح.

مع -B/--bookmark، يتم تحديد التغييرات التي يمكن الوصول إليها بواسطة علامة الكتاب هذه.

استخدم الخيار -g/--git لإنشاء فروقات بتنسيق git extended diff. راجع hg help diffs لمزيد من المعلومات.

مع الخيار --switch-parent، ستكون الفرق مقابل الأصل الثاني. يمكن أن يكون مفيدًا لمراجعة الدمج.

القالب:

يتم دعم الكلمات الرئيسية التالية بالإضافة إلى كلمات القالب والوظائف الشائعة. راجع أيضًا hg help templates.

  • تصدير جميع التغييرات بين مراجعتين إلى ملف مع معلومات إعادة التسمية: 
    hg export --git -r 123:150 > changes.txt

لغة RevSet

Mercurial supports a powerful expression language for selecting revisions, known as "revsets".

مقدمة

Revsets are expressions that evaluate to a set of revisions. They can be used in many Mercurial commands, such as:

hg log -r "revset expression"
hg diff -r "revset expression"
hg update -r "revset expression"

The basic syntax of a revset is a sequence of terms separated by operators. Terms can be revision numbers, tags, branches, keywords, or calls to revset functions.

المعاملات

The following operators are supported:

and, &
Intersection of two sets. The result contains only revisions present in both sets.
or, |
Union of two sets. The result contains revisions present in either set.
not, ~
Set difference. The result contains revisions present in the first set but not in the second.
xor, ^
Exclusive OR. The result contains revisions present in either set, but not both.
(expr)
Parentheses for grouping expressions.
::
Range operator. A::B selects all revisions from A up to and including B. If A is omitted, it defaults to the first revision. If B is omitted, it defaults to the tip. For example, ::tip selects all revisions, and 123:: selects all revisions from 123 up to the tip.
descendants(revset)
Selects all descendants of the revisions in revset.
ancestors(revset)
Selects all ancestors of the revisions in revset.
before(revset)
Selects all revisions committed before any revision in revset.
after(revset)
Selects all revisions committed after any revision in revset.

الدوال

The following functions can be used in revsets:

branch(name)

Revisions on the specified branch. If no branch name is given, all branches are returned.

Pattern matching is supported for name. See hg help revisions.patterns.

closed()

Closed branches.

date(spec)

Revisions matching the given date specification. See hg help dates.

file(pattern)

Changesets that modified files matching the given pattern. See hg help patterns.

filter(revset, predicate)

Filters the given revset, returning only those revisions for which the predicate returns true.

first()

The first revision in the set.

head(revset)

The heads of the specified revision set. If no set is given, all heads are returned.

keyword(string)

Changesets that contain the given keyword string in their commit message.

Pattern matching is supported for string. See hg help revisions.patterns.

limit(revset, n)

Limits the given revset to at most n revisions. The order of revisions is determined by the underlying revset.

merge()

Changesets that are merge commits.

parents(revset)

The parents of the revisions in the specified set. If no set is given, the parents of all heads are returned.

predicate(name)

Returns true if the revision satisfies the given predicate. Possible predicates include: branch, date, file, keyword, merge, subrepo, tag, user.

reverse(revset)

Reverses the order of the revisions in the given set.

sort(revset, key)

Sorts the given revset by the specified key. Possible keys include: author, date, files, user.

tag(name)

The specified tag by name, or all tagged revisions if no name is given.

Pattern matching is supported for name. See hg help revisions.patterns.

subrepo([pattern])

Changesets that add, modify or remove the given subrepo. If no subrepo pattern is named, any subrepo changes are returned.

tag([name])

The specified tag by name, or all tagged revisions if no name is given.

Pattern matching is supported for name. See hg help revisions.patterns.

user(string)

User name contains string. The match is case-insensitive.

Pattern matching is supported for string. See hg help revisions.patterns.

الأسماء المستعارة

New predicates (known as "aliases") can be defined, using any combination of existing predicates or other aliases. An alias definition looks like:

<alias> = <definition>

in the revsetalias section of a Mercurial configuration file. Arguments of the form a1, a2, etc. are substituted from the alias into the definition.

For example,

[revsetalias]
h = heads()
d(s) = sort(s, date)
rs(s, k) = reverse(sort(s, k))

defines three aliases, h, d, and rs. rs(0:tip, author) is exactly equivalent to reverse(sort(0:tip, author)).

المكافئات

Command line equivalents for hg log:

-f    ->  ::.
-d x  ->  date(x)
-k x  ->  keyword(x)
-m    ->  merge()
-u x  ->  user(x)
-b x  ->  branch(x)
-P x  ->  !::x
-l x  ->  limit(expr, x)

أمثلة

Some sample queries:

  • Changesets on the default branch: 
    hg log -r "branch(default)"
  • Changesets on the default branch since tag 1.5 (excluding merges): 
    hg log -r "branch(default) and 1.5:: and not merge()"
  • Open branch heads: 
    hg log -r "head() and not closed()"
  • Changesets between tags 1.3 and 1.5 mentioning "bug" that affect hgext/*: 
    hg log -r "1.3::1.5 and keyword(bug) and file('hgext/*')"
  • Changesets committed in May 2008, sorted by user: 
    hg log -r "sort(date('May 2008'), user)"
  • Changesets mentioning "bug" or "issue" that are not in a tagged release: 
    hg log -r "(keyword(bug) or keyword(issue)) and not ancestors(tag())"
  • Update to the commit that bookmark @ is pointing to, without activating the bookmark (this works because the last revision of the revset is used): 
    hg update :@
  • Show diff between tags 1.3 and 1.5 (this works because the first and the last revisions of the revset are used): 
    hg diff -r 1.3::1.5

Rust في Mercurial

Mercurial can be augmented with Rust extensions for speeding up certain operations.

كلمة تحذير

Using the Rust extension might result in the use of various repository formats that are not supported by non-Rust mercurial. When using a Mercurial without Rust support on the same repositories, you might need to downgrade your repository formats and/or activate cripplingly slow paths for compatibility. For details, see:

  • hg help config.format.use-persistent-nodemap
  • hg help config.format.use-dirstate-v2

In addition, while the tests are run with the Rust code, there might be subtle undetected divergences from the historical non-Rust code. So keep your eyes open and report any oddity. Rust is not considered a first class citizen to the project yet.

التوافق

Though the Rust extensions are only tested by the project under Linux, users of MacOS, FreeBSD and other UNIX-likes have been using the Rust extensions. Your mileage may vary, but by all means do give us feedback or signal your interest for better support.

For compatibility with non-Rust version of Mercurial check the previous "Word of Caution" section.

No Rust extensions are available for Windows at this time.

الميزات

The following operations are sped up when using Rust:

  • discovery of differences between repositories (pull/push)
  • nodemap (see hg help config.format.use-persistent-nodemap)
  • all commands using the dirstate (status, commit, diff, add, update, etc.)
  • dirstate-v2 (see hg help config.format.use-dirstate-v2)
  • iteration over ancestors in a graph

More features are in the works, and improvements on the above listed are still in progress. For more experimental work see the "rhg" section.

التحقق من Rust

You may already have the Rust extensions depending on how you install Mercurial:

$ hg debuginstall | grep -i rust
checking Rust extensions (installed)
checking module policy (rust+c-allow)

If those lines don't even exist, you're using an old version of hg which does not have any Rust extensions yet.

التثبيت

You will need cargo to be in your $PATH. See the "MSRV" section for which version to use.

الاستخدام مع pip

Users of pip can install the Rust extensions with the following commands:

$ pip cache remove mercurial
$ pip install mercurial -v \
      --config-settings --global-option=--rust \
      --no-binary mercurial --force

pip cache remove and --no-binary are there to tell pip to not use the pre-compiled wheels that are missing rust support. This might take a couple of minutes because you're compiling everything.

See the "Checking for Rust" section to see if the install succeeded.

الاستخدام مع pipx

Using pipx is an efficient way to get an isolated installation of mercurial available for a user or globally.

$ pipx install mercurial
--pip-args '--no-cache-dir --config-settings --global-option=--rust --no-binary=mercurial'

You can then add extensions to that install using

$ pipx inject mercurial hg-foo

من التوزيع الخاص بك

Some distributions are shipping Mercurial with Rust extensions enabled and pre-compiled (meaning you won't have to install cargo), or allow you to specify an install flag. Check with your specific distribution for how to do that, or ask their team to add support for hg+Rust!

من المصدر

Please refer to the rust/README.md file in the Mercurial repository for instructions on how to install from source.

MSRV

The minimum supported Rust version is defined in rust/clippy.toml. The project's policy is to keep it at or below the version from Debian testing, to make the distributions' job easier.

rhg

There exists an experimental pure-Rust version of Mercurial called rhg with a fallback mechanism for unsupported invocations. It allows for much faster execution of certain commands while adding no discernable overhead for the rest.

The only way of trying it out is by building it from source. Please refer to rust/README.md in the Mercurial repository.

See hg help config.rhg for configuration options.

المساهمة

If you would like to help the Rust endeavor, please refer to rust/README.md in the Mercurial repository.

استخدام Mercurial من النصوص البرمجية والأتمتة

It is common for machines (as opposed to humans) to consume Mercurial. This help topic describes some of the considerations for interfacing machines with Mercurial.

اختيار الواجهة

Machines have a choice of several methods to interface with Mercurial. These include:

  • Executing the hg process
  • Querying a HTTP server
  • Calling out to a command server

Executing hg processes is very similar to how humans interact with Mercurial in the shell. It should already be familiar to you.

hg serve can be used to start a server. By default, this will start a "hgweb" HTTP server. This HTTP server has support for machine-readable output, such as JSON. For more, see hg help hgweb.

hg serve can also start a "command server." Clients can connect to this server and issue Mercurial commands over a special protocol. For more details on the command server, including links to client
