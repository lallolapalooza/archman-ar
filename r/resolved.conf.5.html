الوصف

تتحكم ملفات الإعدادات هذه في تحليل أسماء DNS و LLMNR المحلية.

دليل الإعدادات والأسبقية

يتم تعيين الإعداد الافتراضي أثناء التجميع، لذا لا يلزم الإعداد إلا عند الضرورة للانحراف عن تلك الافتراضيات. يتم تحميل ملف الإعداد الرئيسي من أحد الدلائل المدرجة حسب الأسبقية، ويتم استخدام الملف الأول الذي تم العثور عليه فقط: /etc/systemd/، /run/systemd/، /usr/local/lib/systemd/ [1]، /usr/lib/systemd/. يحتوي ملف البائع الخاص بالملف على إدخالات معلّقة توضح الافتراضيات كدليل للمسؤول. يمكن أيضًا إنشاء تجاوزات محلية عن طريق إنشاء ملحقات، كما هو موضح أدناه. يمكن أيضًا تعديل ملف الإعداد الرئيسي لهذا الغرض (أو نسخة في /etc/ إذا تم توزيعه تحت /etc/)، ومع ذلك، يوصى باستخدام الملحقات للإعداد المحلي بدلاً من التعديلات على ملف الإعداد الرئيسي.

بالإضافة إلى ملف الإعداد الرئيسي، يتم قراءة مقتطفات إعداد الملحقات من /usr/lib/systemd/*.conf.d/، /usr/local/lib/systemd/*.conf.d/، و /etc/systemd/*.conf.d/. تتمتع هذه الملحقات بأسبقية أعلى وتتجاوز ملف الإعداد الرئيسي. يتم فرز الملفات في الدلائل الفرعية للإعداد *.conf.d/ حسب اسم ملفها بترتيب أبجدي، بغض النظر عن الدلائل الفرعية التي تقيم فيها. عندما تحدد ملفات متعددة نفس الخيار، بالنسبة للخيارات التي تقبل قيمة واحدة فقط، يأخذ الإدخال في الملف الذي تم فرزه أخيرًا الأسبقية، وبالنسبة للخيارات التي تقبل قائمة قيم، يتم جمع الإدخالات كما تحدث في الملفات التي تم فرزها.

عندما تحتاج الحزم إلى تخصيص الإعدادات، يمكنها تثبيت ملحقات تحت /usr/. تم تخصيص الملفات في /etc/ للمسؤول المحلي، والذي قد يستخدم هذا المنطق لتجاوز ملفات الإعداد التي تم تثبيتها بواسطة حزم البائع. يجب استخدام الملحقات لتجاوز ملحقات الحزم، نظرًا لأن ملف الإعداد الرئيسي له أسبقية أقل. يوصى بتسمية جميع أسماء الملفات في هذه الدلائل الفرعية برقم مكون من رقمين وشرطة، لتبسيط الترتيب. هذا يحدد أيضًا مفهوم أولوية الملحق للسماح لموردي نظام التشغيل بتوفير الملحقات ضمن نطاق معين أقل من النطاق الذي يستخدمه المستخدمون. يجب أن يؤدي هذا إلى تقليل خطر تجاوز الملحقات الخاصة بالحزم عن غير قصد للملحقات المحددة من قبل المستخدمين. يوصى باستخدام النطاق 10-40 للملحقات في /usr/ والنطاق 60-90 للملحقات في /etc/ و /run/، للتأكد من أن الملحقات المحلية والمؤقتة لها الأولوية على الملحقات التي يوفرها بائع نظام التشغيل.

لتعطيل ملف إعداد مقدم من البائع، فإن الطريقة الموصى بها هي وضع رابط رمزي إلى /dev/null في دليل الإعدادات في /etc/، بنفس اسم ملف الإعداد الخاص بالبائع.

خيارات

الخيارات التالية متاحة في قسم [Resolve]:

DNS=

قائمة مفصولة بمسافات من عناوين IPv4 و IPv6 لاستخدامها كخوادم DNS للنظام. يمكن لكل عنوان اختياريًا أخذ رقم منفذ مفصول بـ ":"، واسم واجهة شبكة أو فهرس مفصول بـ "%"، واسم مؤشر الخادم (SNI) مفصول بـ "#". عند تحديد عنوان IPv6 برقم منفذ، يجب أن يكون العنوان داخل أقواس مربعة. أي، التنسيقات الكاملة المقبولة هي "111.222.333.444:9953%ifname#example.com" لـ IPv4 و "[1111:2222::3333]:9953%ifname#example.com" لـ IPv6. يتم إرسال استعلامات DNS إلى أحد خوادم DNS المدرجة بالتوازي مع خوادم DNS المناسبة لكل رابط تم الحصول عليها من systemd-networkd.service(8) أو تم تعيينها في وقت التشغيل بواسطة تطبيقات خارجية. لأسباب التوافق، إذا لم يتم تحديد هذا الإعداد، يتم استخدام خوادم DNS المدرجة في /etc/resolv.conf بدلاً من ذلك، إذا كان هذا الملف موجودًا وتم تكوين أي خوادم فيه. هذا الإعداد افتراضيًا للقائمة الفارغة.

تمت الإضافة في الإصدار 213.

FallbackDNS=

قائمة مفصولة بمسافات من عناوين IPv4 و IPv6 لاستخدامها كخوادم DNS احتياطية. يرجى الاطلاع على DNS= لتنسيق العناوين المقبول. أي خوادم DNS لكل رابط تم الحصول عليها من systemd-networkd.service(8) لها الأسبقية على هذا الإعداد، وكذلك أي خوادم تم تعيينها عبر DNS= أعلاه أو /etc/resolv.conf. لذلك، يتم استخدام هذا الإعداد فقط إذا لم تكن هناك معلومات خادم DNS أخرى معروفة. إذا لم يتم تقديم هذا الخيار، فسيتم استخدام قائمة خوادم DNS المجمعة مسبقًا بدلاً من ذلك.

تمت الإضافة في الإصدار 216.

Domains=

قائمة مفصولة بمسافات من المجالات، مسبوقة اختياريًا بـ "~"، تستخدم لغرضين مميزين موصوفين أدناه. افتراضيًا للقائمة الفارغة.

يتم استخدام أي مجالات غير مسبوقة بـ "~" كلاحقات بحث عند تحليل أسماء المضيف ذات التسمية الواحدة (أسماء المجالات التي لا تحتوي على نقطة)، من أجل تأهيلها إلى أسماء مجالات مؤهلة بالكامل (FQDNs). تتم معالجة هذه "المجالات البحث" بشكل صارم بالترتيب الذي يتم تحديده بها، حتى يتم العثور على الاسم مع إضافة اللاحقة. لأسباب التوافق، إذا لم يتم تحديد هذا الإعداد، يتم استخدام مجالات البحث المدرجة في /etc/resolv.conf مع الكلمة المفتاحية search بدلاً من ذلك، إذا كان هذا الملف موجودًا وتم تكوين أي مجالات فيه.

المجالات المسبوقة بـ "~" تسمى "مجالات التوجيه فقط". تحدد جميع المجالات المدرجة هنا (كل من مجالات البحث ومجالات التوجيه فقط بعد إزالة البادئة "~") مسار بحث يوجه استعلامات DNS بشكل مفضل إلى هذه الواجهة. يكون لمسار البحث هذا تأثير فقط عندما تكون خوادم DNS المناسبة لكل رابط معروفة. يمكن تعريف هذه الخوادم من خلال إعداد DNS= (انظر أعلاه) وديناميكيًا في وقت التشغيل، على سبيل المثال من عقود DHCP. إذا لم تكن هناك خوادم DNS لكل رابط معروفة، فإن مجالات التوجيه فقط ليس لها تأثير.

استخدم البناء "~." (الذي يتكون من "~" للإشارة إلى مجال توجيه فقط و "." للإشارة إلى مجال جذر DNS وهو اللاحقة الضمنية لجميع مجالات DNS) لاستخدام خوادم DNS المحددة لهذا الرابط بشكل مفضل لجميع المجالات.

انظر "البروتوكولات والتوجيه" في systemd-resolved.service(8) للحصول على تفاصيل حول كيفية استخدام مجالات البحث والتوجيه فقط.

لاحظ أن تكوين مجال MulticastDNS "local" كمجال بحث أو توجيه له تأثير توجيه الاستعلامات لهذا المجال إلى DNS التقليدي أحادي البث. يمكن استخدام هذا لتوفير التوافق مع التركيبات القديمة التي تستخدم هذا المجال في سياق DNS أحادي البث، ضد تعيين IANA لهذا المجال لأغراض MulticastDNS فقط. مجالات البحث والتوجيه هي مفهوم DNS أحادي البث، ولا يمكن استخدامها لتحليل الاستعلامات ذات التسمية الواحدة عبر MulticastDNS.

تمت الإضافة في الإصدار 229.

LLMNR=

يقبل وسيطة منطقية أو "resolve". يتحكم في دعم تحليل أسماء المضيفين عبر البث المتعدد المحلي (LLMNR) (RFC 4795[2]) على المضيف المحلي. إذا كانت صحيحة، فإنه يتيح دعم مستجيب ومحلل LLMNR كامل. إذا كانت خاطئة، فإنه يعطل كلاهما. إذا تم تعيينه على "resolve"، يتم تمكين دعم التحليل فقط، ولكن يتم تعطيل الاستجابة. لاحظ أن systemd-networkd.service(8) يحتفظ أيضًا بإعدادات LLMNR لكل رابط. سيتم تمكين LLMNR على رابط فقط إذا كان الإعداد لكل رابط والإعداد العام قيد التشغيل.

تمت الإضافة في الإصدار 216.

DNSSEC=

يأخذ وسيطة منطقية أو "allow-downgrade".

إذا تم تعيينه على "true"، فسيتم التحقق من صحة جميع استعلامات DNS محليًا (باستثناء LLMNR و Multicast DNS). إذا تم اكتشاف أن الاستجابة لطلب استعلام غير صالحة، فسيتم إرجاع فشل الاستعلام للتطبيقات. لاحظ أن هذا الوضع يتطلب خادم DNS يدعم DNSSEC. إذا كان خادم DNS لا يدعم DNSSEC بشكل صحيح، فستفشل جميع عمليات التحقق.

إذا تم تعيينه على "allow-downgrade"، يتم محاولة التحقق من DNSSEC، ولكن إذا كان الخادم لا يدعم DNSSEC بشكل صحيح، فسيتم تعطيل وضع DNSSEC تلقائيًا. لاحظ أن هذا الوضع يجعل التحقق من DNSSEC عرضة لهجمات "الخفض"، حيث قد يتمكن المهاجم من فرض خفض إلى وضع عدم DNSSEC عن طريق إنشاء استجابة DNS تشير إلى أن DNSSEC غير مدعوم.

إذا تم تعيينه على "false"، فلن يتم التحقق من صحة استعلامات DNS باستخدام DNSSEC.

لاحظ أن التحقق من DNSSEC يتطلب استرداد بيانات DNS إضافية، وبالتالي يؤدي إلى عقوبة صغيرة في وقت استعلام DNS.

يتطلب DNSSEC معرفة "مرتكزات الثقة" لإثبات سلامة البيانات. مرتكز الثقة لنطاق الجذر على الإنترنت مدمج في المحلل، ويمكن تعريف مرتكزات ثقة إضافية باستخدام dnssec-trust-anchors.d(5). قد تتغير مرتكزات الثقة على فترات منتظمة، وقد يتم إلغاء صلاحية مرتكزات الثقة القديمة. في هذه الحالة، لن يكون التحقق من DNSSEC ممكنًا حتى يتم تكوين مرتكزات ثقة جديدة محليًا أو تحديث حزمة برامج المحلل مع مرتكز الثقة الجديد للجذر. في الواقع، عندما يتم إلغاء صلاحية المرتكز المدمج ويكون DNSSEC= صحيحًا، ستفشل جميع الاستعلامات اللاحقة، حيث لم يعد من الممكن إثبات ما إذا كانت الاستعلامات موقّعة بشكل صحيح، أو غير موقّعة بشكل صحيح. إذا تم تعيين DNSSEC= على "allow-downgrade"، فسيقوم المحلل تلقائيًا بإيقاف تشغيل التحقق من DNSSEC في هذه الحالة.

سيتم إبلاغ برامج العميل التي تستعلم عن بيانات DNS بما إذا كان يمكن التحقق من صحة الاستعلامات باستخدام DNSSEC، أو ما إذا كانت البيانات التي تم إرجاعها لا يمكن التحقق منها (إما لأن البيانات تم العثور عليها بدون توقيع في DNS، أو أن خادم DNS لم يدعم DNSSEC أو لم تكن هناك مرتكزات ثقة مناسبة معروفة). في الحالة الأخيرة، يُفترض أن برامج العميل تستخدم مخططًا ثانويًا للتحقق من صحة بيانات DNS التي تم إرجاعها، إذا كان ذلك مطلوبًا.

يوصى بتعيين DNSSEC= على "true" على الأنظمة التي يُعرف أن خادم DNS الخاص بها يدعم DNSSEC بشكل صحيح، وحيث يتم تحديث البرامج أو مرتكزات الثقة بانتظام. على الأنظمة الأخرى، يوصى بتعيين DNSSEC= على "allow-downgrade".

بالإضافة إلى هذا الإعداد العام لـ DNSSEC، systemd-networkd.service(8) يحافظ أيضًا على إعدادات DNSSEC لكل ارتباط. بالنسبة لخوادم DNS للنظام (انظر أعلاه)، فإن إعداد DNSSEC العام فقط هو الذي يكون ساري المفعول. بالنسبة لخوادم DNS لكل ارتباط، فإن الإعداد لكل ارتباط هو الذي يكون ساري المفعول، ما لم يتم إلغاء تعيينه، وفي هذه الحالة يتم استخدام الإعداد العام بدلاً من ذلك.

تتعارض مناطق DNS الخاصة بالموقع بشكل عام مع تشغيل DNSSEC، ما لم يتم تكوين مرتكز ثقة سلبي (إذا كانت المنطقة الخاصة غير موقّعة) أو إيجابي (إذا كانت المنطقة الخاصة موقّعة) لها. إذا تم تحديد وضع "allow-downgrade"، فسيتم محاولة اكتشاف مناطق DNS الخاصة بالموقع باستخدام نطاقات المستوى الأعلى (TLDs) غير المعروفة لخوادم DNS الجذر. لا تعمل هذه المنطق في جميع إعدادات المنطقة الخاصة.

الافتراضي هو "no".

DNSOverTLS=

يأخذ وسيطة منطقية أو "opportunistic". إذا كان "true" فسيتم تشفير جميع الاتصالات بالخادم. لاحظ أن هذا الوضع يتطلب خادم DNS يدعم DNS-over-TLS ولديه شهادة صالحة. إذا تم تحديد اسم المضيف في DNS= باستخدام التنسيق "address#server_name"، فسيتم استخدامه للتحقق من صحة شهادته وأيضًا لتمكين اسم الخادم المشار إليه (SNI) عند فتح اتصال TLS. بخلاف ذلك، يتم فحص الشهادة مقابل IP الخاص بالخادم. إذا كان خادم DNS لا يدعم DNS-over-TLS، فستفشل جميع طلبات DNS.

عند التعيين على "opportunistic"، يتم محاولة إرسال طلبات DNS مشفرة باستخدام DNS-over-TLS. إذا كان خادم DNS لا يدعم TLS، فسيتم تعطيل DNS-over-TLS. لاحظ أن هذا الوضع يجعل DNS-over-TLS عرضة لهجمات "الخفض"، حيث قد يتمكن المهاجم من فرض خفض إلى وضع غير مشفر عن طريق إنشاء استجابة تشير إلى أن DNS-over-TLS غير مدعوم. إذا تم التعيين على "false"، يتم إرسال استعلامات DNS عبر UDP.

لاحظ أن DNS-over-TLS يتطلب إرسال بيانات إضافية لإعداد اتصال مشفر، وبالتالي يؤدي إلى عقوبة صغيرة في وقت استعلام DNS.

لاحظ أنه في وضع "opportunistic"، لا يستطيع المحلل المصادقة على الخادم، لذلك فهو عرضة لهجمات "الرجل في المنتصف".

بالإضافة إلى هذا الإعداد العام لـ DNSOverTLS=، systemd-networkd.service(8) يحافظ أيضًا على إعدادات DNSOverTLS= لكل ارتباط. بالنسبة لخوادم DNS للنظام (انظر أعلاه)، فإن إعداد DNSOverTLS= العام فقط هو الذي يكون ساري المفعول. بالنسبة لخوادم DNS لكل ارتباط، فإن الإعداد لكل ارتباط هو الذي يكون ساري المفعول، ما لم يتم إلغاء تعيينه، وفي هذه الحالة يتم استخدام الإعداد العام بدلاً من ذلك.

الافتراضي هو "no".

Cache=

يأخذ وسيطة منطقية أو "no-negative". إذا كان "yes" (الافتراضي)، فإن حل اسم نطاق تم الاستعلام عنه بالفعل سابقًا سيعيد النتيجة السابقة طالما أنها لا تزال صالحة، وبالتالي لا ينتج عنها طلب شبكة جديد. كن على علم بأن إيقاف التخزين المؤقت يأتي بتكلفة أداء، وهي مرتفعة بشكل خاص عند استخدام DNSSEC. إذا كان "no-negative"، فسيتم تخزين الإجابات الإيجابية فقط مؤقتًا.

لاحظ أن التخزين المؤقت معطل افتراضيًا لخوادم DNS المحلية للمضيف. راجع CacheFromLocalhost= للحصول على التفاصيل.

تمت الإضافة في الإصدار 231.

CacheFromLocalhost=

يأخذ وسيطة منطقية. إذا كان "no" (الافتراضي)، وعندما تأتي الاستجابة من عنوان IP محلي للمضيف (مثل 127.0.0.1 أو ::1)، فلن يتم تخزين النتيجة مؤقتًا لتجنب التخزين المؤقت المحلي المزدوج المحتمل.

تمت الإضافة في الإصدار 248.

DNSStubListener=

يأخذ وسيطة منطقية أو "udp" أو "tcp". إذا كان "udp"، فسيستمع محلل DNS الفرعي لطلبات UDP على العناوين 127.0.0.53 و 127.0.0.54، المنفذ 53. إذا كان "tcp"، فسيستمع المحلل لطلبات TCP على نفس العناوين والمنفذ. إذا كان "yes" (الافتراضي)، فسيستمع المحلل لطلبات UDP و TCP. إذا كان "no"، فسيتم تعطيل مستمع المحلل.

يوفر محلل DNS الفرعي على 127.0.0.53 مجموعة الميزات الكاملة للمحلل المحلي، والتي تشمل تقديم دقة LLMNR/MulticastDNS. يوفر محلل DNS الفرعي على 127.0.0.54 محللًا محدودًا، يعمل في وضع "الوكيل" فقط، أي أنه سيمرر معظم رسائل DNS دون تعديل نسبيًا إلى خوادم DNS الخارجية الحالية والعودة، ولكنه لن يحاول معالجة الرسائل محليًا، وبالتالي لا يتحقق من صحة DNSSEC، أو يقدم LLMNR/MulticastDNS. (ومع ذلك، سيترجم إلى اتصال DNS-over-TLS إذا لزم الأمر.)

لاحظ أن مستمع DNS الفرعي يتم إيقافه ضمنيًا عندما يكون عنوانه ومنفذه قيد الاستخدام بالفعل.

تمت الإضافة في الإصدار 232.

RefuseRecordTypes=

يأخذ قائمة بأنواع سجلات DNS مفصولة بمسافة. سيتم رفض الأنواع المحددة في كل استعلام. يمكن تحديد هذا الخيار عدة مرات. إذا تم تحديد سلسلة فارغة، فسيتم مسح جميع التعيينات السابقة.

أمثلة:

RefuseRecordTypes=AAAA SRV TXT

لاحظ أنه لرفض سجل AAAA (على عكس SRV، TXT، إلخ) تمامًا، يرجى أيضًا تعطيل مكدس IPv6 في النواة باستخدام "sysctl -w net.ipv6.conf.all.disable_ipv6=1".

تمت الإضافة في الإصدار 258.

DNSStubListenerExtra=

يأخذ عنوان IPv4 أو IPv6 للاستماع عليه. يمكن اختياريًا إضافة بادئة للعنوان باسم بروتوكول ("udp" أو "tcp") مفصولة بـ ":". إذا لم يتم تحديد البروتوكول، فستستمع الخدمة على كل من UDP و TCP. يمكن اختياريًا إضافة لاحقة لرقم منفذ رقمي بفاصل ":". عند تحديد عنوان IPv6 مع رقم منفذ، يجب أن يكون العنوان بين أقواس مربعة. إذا لم يتم تحديد المنفذ، فستستخدم الخدمة المنفذ 53. لاحظ أن هذا مستقل عن المحلل الفرعي DNS الأساسي الذي تم تكوينه باستخدام DNSStubListener=، ويقوم فقط بتكوين مقابس *إضافية* للاستماع عليها. يمكن تحديد هذا الخيار عدة مرات. إذا تم تعيين سلسلة فارغة، فسيتم مسح جميع التعيينات السابقة. الافتراضي هو غير معين.

أمثلة:

DNSStubListenerExtra=192.168.10.10
DNSStubListenerExtra=2001:db8:0:f102::10
DNSStubListenerExtra=192.168.10.11:9953
DNSStubListenerExtra=[2001:db8:0:f102::11]:9953
DNSStubListenerExtra=tcp:192.168.10.12
DNSStubListenerExtra=udp:2001:db8:0:f102::12
DNSStubListenerExtra=tcp:192.168.10.13:9953
DNSStubListenerExtra=udp:[2001:db8:0:f102::13]:9953

تمت الإضافة في الإصدار 247.

ReadEtcHosts=

يأخذ وسيطة منطقية. إذا كان "yes" (الافتراضي)، فسيقوم systemd-resolved بقراءة /etc/hosts، ومحاولة حل المضيفين أو العناوين باستخدام الإدخالات في الملف قبل إرسال استعلام إلى خوادم DNS.

تمت الإضافة في الإصدار 240.

ResolveUnicastSingleLabel=

يأخذ وسيطة منطقية. عند "false" (الافتراضي)، لن يقوم systemd-resolved بحل استعلامات A و AAAA للأسماء ذات الملصق الواحد عبر DNS الكلاسيكي. لاحظ أنه لا يزال من الممكن حل هذه الأسماء إذا تم تحديد نطاقات البحث (انظر Domains= أعلاه)، أو باستخدام آليات أخرى، خاصة عبر LLMNR أو من /etc/hosts. عند "true"، سيتم توجيه الاستعلامات للأسماء ذات الملصق الواحد إلى خوادم DNS العامة حتى لو لم يتم تعريف نطاقات بحث.

تم توفير هذا الخيار للتوافق مع التكوينات التي *لا تستخدم خوادم DNS عامة*. توجيه الأسماء ذات الملصق الواحد إلى خوادم خارجة عن سيطرتك ليس قياسيًا، انظر بيان IAB[4]، وقد يشكل خطرًا على الخصوصية والأمان.

تمت الإضافة في الإصدار 246.

StaleRetentionSec=SECONDS

يأخذ قيمة مدة، تحدد المدة التي يمكن الاحتفاظ بسجلات موارد DNS في ذاكرة التخزين المؤقت بعد مدة صلاحيتها (TTL). هذا يسمح بإعادة هذه السجلات كسجلات قديمة. افتراضيًا، يتم تعيين هذه القيمة على صفر، مما يعني أنه لا يتم تخزين سجلات موارد DNS في ذاكرة التخزين المؤقت بعد انتهاء مدة صلاحيتها.

هذا مفيد عند حدوث فشل في خادم DNS أو يصبح غير قابل للوصول. في مثل هذه الحالات، /usr/lib/. Instead, they should be placed in /etc/ or /run/.

If the configuration file is placed in /etc/systemd/resolved.conf, this setting will be enabled. If you want to disable this feature, remove the configuration file.

OPTIONS

DNSStubListener=
Enables or disables the DNS stub listener. If enabled, systemd-resolved.service(8) will listen on 127.0.0.53 port 53. This is the default. If disabled, systemd-resolved will not listen on any network address and will not provide DNS service. This is useful if you want to use another DNS resolver, like dnsmasq or a local bind.
DNS=
Takes a space-separated list of IP addresses to use as DNS servers. If this option is used, the DNS servers from /etc/resolv.conf will be ignored. This is useful for setting up a static list of DNS servers.
FallbackDNS=
Takes a space-separated list of IP addresses to use as fallback DNS servers. These servers are only used if the primary DNS servers fail to respond. This is useful for setting up redundant DNS servers.
Domains=
Takes a space-separated list of domains to use for DNS searches. If a hostname is not fully qualified, these domains will be appended to it. This is useful for setting up local domains.
DNSSEC=
Controls DNSSEC validation. Possible values are no (disabled), allow-downgrade (allow DNSSEC data to be absent), yes (require DNSSEC data), opportunistic (like allow-downgrade, but only if the DNS server supports it). The default is no.
DNSOverTLS=
Controls DNS-over-TLS mode. Possible values are no (disabled), opportunistic (use DNS-over-TLS if the server supports it), yes (require DNS-over-TLS). The default is no.
MulticastDNS=
Enables or disables multicast DNS (also known as Bonjour or Avahi). If enabled, systemd-resolved.service(8) will respond to and send multicast DNS queries. The default is yes.
LLMNR=
Enables or disables Link-Local Multicast Name Resolution (LLMNR). If enabled, systemd-resolved.service(8) will respond to and send LLMNR queries. The default is yes.
Cache=
Controls the DNS cache. Possible values are yes (enable cache) and no (disable cache). The default is yes.
DNSStubListener=no
If this option is enabled, systemd-resolved.service(8) continues to use the stale records to answer DNS queries, particularly when no valid response can be obtained from the upstream DNS servers. However, this does not apply to NXDOMAIN responses, as those are still perfectly valid responses. This feature enhances resilience against DNS infrastructure failures and outages.

systemd-resolved always attempts to reach the upstream DNS servers first, before providing the client application with any stale data. If this feature is enabled, cache will not be flushed when changing servers.

Added in version 254.
