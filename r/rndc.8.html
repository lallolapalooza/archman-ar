NAME

\n

rndc - name server control utility

\n
\n
\n

SYNOPSIS

\n

rndc [-b source-address] [-c config-file] \n [-k key-file] [-s server] [-p port] [-q] \n [-r] [-V] [-y server_key] [[-4] | [-6]]\n {command}

\n
\n
\n

DESCRIPTION

\n

rndc controls the operation of a name server. If \n rndc is invoked with no command line options or arguments, it prints\n a short summary of the supported commands and the available options and\n their arguments.

\n

rndc communicates with the name server over a TCP\n connection, sending commands authenticated with digital signatures. In the\n current versions of rndc and named <#std-iscman-named>, \n the only supported authentication algorithms are HMAC-MD5 (for\n compatibility), HMAC-SHA1, HMAC-SHA224, HMAC-SHA256 (default), HMAC-SHA384, \n and HMAC-SHA512. They use a shared secret on each end of the connection, \n which provides TSIG-style authentication for the command request and the\n name server's response. All commands sent over the channel must be signed by\n a server_key known to the server.

\n

rndc reads a configuration file to determine how to contact\n the name server and decide what algorithm and key it should use.

\n
\n
\n

COMMANDS

\n

A list of commands supported by rndc can be seen by running\n rndc without arguments.

\n

Currently supported commands are:

\n
\n
\n
addzone zone [class\n [view]] configuration
\n
This command adds a zone while the server is running. This command\n requires the allow-new-zones option to be set to yes. The\n configuration string specified on the command line is the zone\n configuration text that would ordinarily be placed in named.conf\n <#std-iscman-named.conf>.\n

The configuration is saved in a file called\n viewname.nzf (or, if named <#std-iscman-named> is\n compiled with liblmdb, an LMDB database file called\n viewname.nzd). viewname is the name of the view, unless\n the view name contains characters that are incompatible with use as a\n file name, in which case a cryptographic hash of the view name is used\n instead. When named <#std-iscman-named> is restarted, the\n file is loaded into the view configuration so that zones that were added\n can persist after a restart.

\n

This sample addzone command adds the zone\n example.com to the default view:

\n

rndc addzone example.com '{ type primary; file\n "example.com.db"; };'

\n

(Note the brackets around and semi-colon after the zone\n configuration text.)

\n

See also rndc delzone and rndc modzone.

\n

delzone [-clean] zone\n [class [view]]
\n
This command deletes a zone while the server is running.\n

If the -clean argument is specified, the zone's master\n file (and journal file, if any) are deleted along with the zone. Without\n the -clean option, zone files must be deleted manually. (If the\n zone is of type secondary or stub, the files needing to be\n removed are reported in the output of the rndc delzone\n command.)

\n

If the zone was originally added via rndc addzone, then\n it is removed permanently. However, if it was originally configured in\n named.conf <#std-iscman-named.conf>, then that original\n configuration remains in place; when the server is restarted or\n reconfigured, the zone is recreated. To remove it permanently, it must\n also be removed from named.conf\n <#std-iscman-named.conf>.

See also rndc addzone and rndc modzone.

NAME

rndc

a control utility for BIND

SYNOPSIS

rndc [-c configfile] [-s server] [-p port] [-k keyfile] command

DESCRIPTION

The rndc utility is used to control a running BIND 9 nameserver (named). It can be used to view the nameserver's status, reload zone data, change the nameserver's view of zones, and configure certain runtime parameters.

The rndc utility communicates with named using a TSIG key for authentication. The location of the named.conf file, the keys, and the server address are typically specified in rndc.conf. The default configuration file is /etc/rndc.conf. The default key file is /etc/rndc.key.

The rndc utility supports the following commands:

COMMANDS

addzone zone [class [view]]
Adds a zone that is not listed in named.conf. This command can only be used if allow-new-zones is enabled in named.conf.
delzone [zone [class [view]]]
Deletes a zone that is not listed in named.conf. If no zone is specified, then all zones that are not listed in named.conf are deleted.
dumpdb -a
Writes the contents of the server's database (including any dynamically updated data) to the zone files. The -a option writes to all zones.
flush
Deletes all data from the server's cache. This command is not effective when used with the named view option.
freeze [zone [class [view]]]
Causes updates to a frozen dynamic zone to be refused. If no zone is specified, all dynamic zones are frozen. This command is primarily useful for backing up zones. After a zone has been frozen, the server stops accepting updates for it. If the zone has changed since the last save, the server will write the changes to the journal file, but not to the master file. If the journal file is later removed, these changes will be lost.

See also rndc thaw.

loadkeys
Causes named to reload the public keys of a DNSSEC-signed zone.
managed-keys-dump -a
Writes the server's managed keys database to the file specified by the managed-keys-directory option. The -a option writes to all views.
signing zone [class [view]]
Displays the keys and cryptographic parameters for a zone that is being signed using automatic DNSSEC key management. The zone must be configured with the auto-dnssec maintain; or auto-dnssec allow; option in named.conf.
nsec3param
Sets the NSEC3 parameters for a zone. This is the only supported mechanism for using NSEC3 with inline-signing zones. Parameters are specified in the same format as an NSEC3PARAM resource record: hash algorithm, flags, iterations, and salt, in that order.

Currently, the only defined value for hash algorithm is 1, representing SHA-1. The flags may be set to 0 or 1, depending on whether the opt-out bit in the NSEC3 chain should be set. iterations defines the number of additional times to apply the algorithm when generating an NSEC3 hash. The salt is a string of data expressed in hexadecimal, a hyphen (-) if no salt is to be used, or the keyword auto, which causes named <#std-iscman-named> to generate a random 64-bit salt.

The only recommended configuration is rndc signing -nsec3param 1 0 0 - zone, i.e. no salt, no additional iterations, no opt-out.

Warning:

Do not use extra iterations, salt, or opt-out unless all their implications are fully understood. A higher number of iterations causes interoperability problems and opens servers to CPU-exhausting DoS attacks.

rndc signing -nsec3param none removes an existing NSEC3 chain and replaces it with NSEC.

rndc signing -serial value sets the serial number of the zone to value. If the value would cause the serial number to go backwards, it is rejected. The primary use of this parameter is to set the serial number on inline signed zones.

stats
This command writes server statistics to the statistics file. (See the statistics-file option in the BIND 9 Administrator Reference Manual.)
status
This command displays the status of the server. Note that the number of zones includes the internal bind/CH zone and the default ./IN hint zone, if there is no explicit root zone configured.
stop -p
This command stops the server, making sure any recent changes made through dynamic update or IXFR are first saved to the master files of the updated zones. If -p is specified, named <#std-iscman-named>'s process ID is returned. This allows an external process to determine when named <#std-iscman-named> has completed stopping.

See also rndc halt.

sync -clean [zone [class [view]]]
This command syncs changes in the journal file for a dynamic zone to the master file. If the "-clean" option is specified, the journal file is also removed. If no zone is specified, then all zones are synced.
tcp-timeouts [initial idle keepalive advertised]
When called without arguments, this command displays the current values of the tcp-initial-timeout, tcp-idle-timeout, tcp-keepalive-timeout, and tcp-advertised-timeout options. When called with arguments, these values are updated. This allows an administrator to make rapid adjustments when under a denial-of-service (DoS) attack. See the descriptions of these options in the BIND 9 Administrator Reference Manual for details of their use.
thaw [zone [class [view]]]
This command enables updates to a frozen dynamic zone. If no zone is specified, then all frozen zones are enabled. This causes the server to reload the zone from disk, and re-enables dynamic updates after the load has completed. After a zone is thawed, dynamic updates are no longer refused. If the zone has changed and the ixfr-from-differences option is in use, the journal file is updated to reflect changes in the zone. Otherwise, if the zone has changed, any existing journal file is removed. If no zone is specified, the reloading happens asynchronously.

See also rndc freeze.

trace [level]
If no level is specified, this command increments the server's debugging level by one.
level
If specified, this command sets the server's debugging level to the provided value.

See also rndc notrace.

validation (on | off | status) [view ...]
This command enables, disables, or checks the current status of DNSSEC validation. By default, validation is enabled.

The cache is flushed when validation is turned on or off to avoid using data that might differ between states.

zonestatus zone [class [view]]
This command displays the current status of the given zone, including the master file name and any include files from which it was loaded, when it was most recently loaded, the current serial number, the number of nodes, whether the zone supports dynamic updates, whether the zone is DNSSEC signed, whether it uses automatic DNSSEC key management or inline signing, and the scheduled refresh or expiry times for the zone.

See also rndc showzone.

rndc commands that specify zone names, such as reload retransfer, or zonestatus, can be ambiguous when applied to zones of type redirect. Redirect zones are always called ., and can be confused with zones of type hint or with secondary copies of the root zone. To specify a redirect zone, use the special zone name -redirect, without a trailing period. (With a trailing period, this would specify a zone called "-redirect".)

LIMITATIONS

There is currently no way to provide the shared secret for a server_key without using the configuration file.

Several error messages could be clearer.
