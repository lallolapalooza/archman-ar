rc_keymap(5)

الحزمة: v4l-utils

التراخيص: LGPL

RC_KEYMAP(5) صيغ الملفات RC_KEYMAP(5)

الاسم

rc_keymap - ملف toml يصف خريطة مفاتيح جهاز التحكم عن بعد

الوصف

يصف rc_keymap جهاز تحكم عن بعد. يسرد البروتوكولات المستخدمة، والربط من IR مفككة إلى رموز مفاتيح Linux. يستخدم هذا الملف بواسطة ir-keytable(1) للتفكيك IR، و بواسطة ir-ctl(1) لإرسال IR.

صيغة الملف هي toml. بما أن جهاز تحكم عن بعد يمكنه استخدام بروتوكولات متعددة، فإن المستوى الأعلى هو مصفوفة من البروتوكولات. الغالبية العظمى من أجهزة التحكم عن بعد تستخدم بروتوكولاً واحداً فقط.

إدخال بروتوكول خريطة المفاتيح

لكل بروتوكول تستخدمه أجهزة التحكم عن بعد، يجب أن يكون هناك إدخال واحد في مصفوفة protocols العلوية.

حقل الاسم

كل إدخال بروتوكول له حقل name. لا يتم استخدام الاسم بواسطة ir-keytable أو ir-ctl، ولكنه يمكن استخدامه لإعطاء اسم جهاز التحكم عن بعد وصفياً أكثر من اسم الملف، على سبيل المثال رقم الطراز.

حقل البروتوكول

يحدد حقل protocol البروتوكول. يمكن أن يكون هذا إما أحد وحدات فك التشفير لنواة Linux، وفي هذه الحالة يكون nec، rc-5، rc-6، jvc، sony، sanyo، rc-5-sz، sharp، mce-kbd، xmp، imon، rc-mm، other أو unknown. إذا لم يتطابق مع أي من هذه الإدخالات، فإنه يفترض أنه وحدة فك تشفير قائمة على BPF. unknown و other هي بروتوكولات مفككة بواسطة أجهزة RC محددة حيث يكون البروتوكول إما غير معروف أو خاص، على التوالي.

هناك بعض وحدات فك التشفير بروتوكول BPF محددة مسبقًا، والتي تم إدراجها أدناه. انظر https://lwn.net/Articles/759188/ لكيفية كتابة وحدة فك التشفير الخاصة بك.

حقل المتغير

يحدد حقل variant المتغير الذي يستخدمه بروتوكول معين. بروتوكولات sony، rc-5، rc-6 لها متغيرات مختلفة لطول البت، على سبيل المثال. يستخدم هذا الحقل بواسطة ir-ctl عند إرسال IR.

المتغيرات التالية محددة حاليًا:

البروتوكول rc-5 له متغيرات rc-5، rc-5x-20، rc-5-sz.

البروتوكول nec له متغيرات nec، nec-x، nec-32.

البروتوكول sony له متغيرات sony-12، sony-15، sony-20.

البروتوكول rc-6 له متغيرات rc-6-0، rc-6-6a-20، rc-6-6a-24، rc-6-6a-32، rc-6-mce.

البروتوكول rc-mm له متغيرات rc-mm-12، rc-mm-24، و rc-mm-32.

حقل الرموز (Scancodes)

يسرد جدول scancodes الرموز وربطها بترميز مفتاح Linux. يمكن لعدة رموز أن ترتبط بنفس ترميز المفتاح. حقل scancodes غير موجود لبروتوكولات raw.

إذا بدأ الرمز بـ 0x، فسيتم تفسيره كرقم سداسي عشري. إذا بدأ بـ 0، فسيتم تفسيره كرقم ثماني.

الرموز المفتاحية الصالحة مدرجة في ملف الرأس input-event-codes.h. الأمثلة هي KEY_ENTER، KEY_ESC أو BTN_LEFT لزر الفأرة الأيسر. لاحظ أنه إذا تم استخدام خريطة المفاتيح لإرسال IR فقط، فلن يكون للمفتاح ترميز مفتاح Linux صالح. يمكن أن يكون أي سلسلة بدون مسافات.

حقل الخام (Raw)

إذا كان البروتوكول raw، فإن حقل raw هو مصفوفة من ترميز المفتاح إلى ربط خام. لكل إدخال، يوجد حقل keycode وحقل raw. keycode هو ترميز مفتاح إدخال Linux، كما هو موضح في قسم scancodes أعلاه.

حقل raw هو سلسلة، تسرد قيم النبضات والفراغات، مفصولة بمسافات. الأولى هي قيمة نبضة بالميكروثانية، والثانية فراغ، الثالث نبضة، وهكذا. يمكن أن تسبق قيم الفراغ علامة - ويمكن أن تسبق قيمة النبضة علامة +. يجب أن يكون هناك عدد فردي من القيم بحيث يكون الإدخال الأخير نبضة.

الحقول المتبقية (معلمات BPF)

إذا كان البروتوكول هو وحدة فك تشفير قائمة على BPF، فقد يكون لديه أي عدد من المعلمات الرقمية. تستخدم هذه المعلمات لدعم البروتوكولات ذات أطوال الإشارات غير القياسية لبروتوكولات IR القياسية. سيتم استخدام أي حقول أخرى محددة هنا مطلوبة بواسطة وحدة فك التشفير BPF المحددة. سيتم تجاهل جميع الحقول الأخرى.

وحدات فك التشفير البروتوكول غير BPF المستندة إلى النواة ليس لديها أي معلمات.

بروتوكولات BPF

بعض وحدات فك التشفير BPF عامة وستحتاج إلى معلمات للعمل. البعض الآخر مخصص لأجهزة التحكم عن بعد المحددة ويجب أن تعمل بدون أي معلمات. جميع معلمات التوقيت بالميكروثانية (µs).

raw

يجب استخدام وحدة فك التشفير هذه عندما تكون خريطة المفاتيح خام؛ لكل مفتاح، يوجد إدخال في مصفوفة raw مع قيم النبضة والفراغ لهذا المفتاح. لا يتم إجراء أي تفكيك، تتم مطابقة IR الوارد ببساطة مع قيم النبضة والفراغ المختلفة.

imon_rsc

وحدة فك التشفير هذه مخصصة لجهاز التحكم عن بعد iMON RSC، والذي تم تعبئته مع iMON Station (من بين أشياء أخرى). وحدة فك التشفير مخصصة للعصا الاتجاهية في المنتصف؛ ستقوم بتفكيكها إلى حركات الماوس. جميع الأزرار مشفرة باستخدام nec-x، لذا تحتاج خريطة المفاتيح إلى بروتوكولين لتعمل بشكل صحيح.

هذا لا علاقة له ببروتوكول imon.

margin
تحديد مقدار التسامح لطول الرسالة. الافتراضي 200.

grundig

وحدة فك التشفير هذه مخصصة لأجهزة التحكم عن بعد القديمة من Grundig.

header_pulse
طول النبضة الأولى، الافتراضي 900.
header_space
طول الفراغ التالي، الافتراضي 2900.
leader_pulse
طول النبضة الثانية، الافتراضي 1300.

xbox

وحدة فك التشفير هذه مخصصة لجهاز DVD Remote الخاص بـ XBox، وهو لجهاز XBox من الجيل الأول.

margin
تحديد مقدار التسامح لطول الرسالة. الافتراضي 200.

manchester

معظم أجهزة التحكم عن بعد المشفرة بـ manchester هي إما rc-5، rc-6، أو rc-mm. تستخدم بعض أجهزة التحكم عن بعد متغيرًا مختلفًا (على سبيل المثال، قد تحتوي على نبضة رأس) وهذا هو ما تم تصميم وحدة فك التشفير من أجله. يجب تحديد بعض المعلمات، وبشكل افتراضي تم إعدادها لـ rc-5.

margin
تحديد مقدار التسامح لطول الرسالة. الافتراضي 200.
header_pulse
تحديد طول نبضة بادئة. هذه ليست موجودة دائمًا. الافتراضي 0.
header_space
تحديد طول الفراغ بعد نبضة الرأس. يجب تعيينها إذا تم تعيين header_pulse.
zero_pulse, zero_space, one_pulse, one_space
أطوال الإشارة للبتات. انظر https://clearwater.com.au/code/rc5 لتعريف هذه.
bits
عدد البتات. الافتراضي 14.
scancode_mask
البتات التي يجب تجاهلها من الرمز الناتج.
toggle_bit
البت الذي يحدد التبديل. إذا كانت هذه القيمة أكبر من عدد البتات، فلا يوجد تبديل محدد.

rc_keymap(5)

NAME

rc_keymap - remote control keymap file format

DESCRIPTION

The rc_keymap file specifies the scancodes to keycodes mapping for a particular remote control device. This file is used by the rc_core module in the Linux kernel.

The file format is a TOML file. It contains one or more sections marked with square brackets. The first section is required and MUST be named protocols. Additional sections are optional and should be named according to the protocol they define.

KEYMAP PROTOCOL ENTRY

The protocols section contains a list of protocol entries. Each entry describes a specific remote control protocol and its associated scancodes.

name
The name of the protocol. This is used to identify the protocol in the system. Examples: "lircd", "rc-rc6-decoder", "nec".
protocol
The name of the protocol implementation to use. This MUST be one of the supported protocol names. Examples: "nec", "sony", "rc5", etc. Note that the protocol name is case-sensitive.
variant
Optional. Specifies a variant of the protocol. Not all protocols have variants. Example: "necx" for the NEC protocol.
scancodes
A mapping from scancode to keycode. The scancode is represented as a hexadecimal string (e.g., "0x100f"). The keycode is a standard Linux input event keycode name (e.g., "KEY_POWER", "KEY_VOLUMEUP"). See input-event-codes.h for a full list of keycodes.

A protocol entry can also specify parameters for the decoder. These parameters are specific to the protocol implementation.

BPF PROTOCOLS

Some protocols can be implemented using eBPF. These protocols are defined in separate sections with the protocol name prefixed with bpf-. For example, bpf-nec.

The parameters for these BPF protocols are defined within the protocol-specific section.

pulse_distance

This is a generic decoder for protocols that define bits by distance between pulses, and the pulses are always of the same length. The most well known protocol like this is nec. This decoder is cases where nec is not used. The parameters must be set.

margin
Define how much tolerance there is for message length. Default 200.
header_pulse
Length of the first leading pulse. Default 2125.
header_space
Length of the space after the leading pulse. Default 1875.
repeat_pulse
Length of the leading pulse for key repeat. Default 0.
repeat_space
Length of the space after the leading pulse for key repeat. Default 0.
bit_pulse
Length of the pulse for each bit. Default 625.
bit_0_space
Length of the space for a zero bit. Default 375.
bit_1_space
Length of the space for a one bit. Default 1625.
trailer_pulse
Length of the pulse after the last bit. Needed to bookend the last bit. Default 625.
bits
Number of bits. Default 4.
reverse
Should the bits be read in least significant bit first. Set to non-zero to enable. Default 0.
header_optional
Some remotes do not send the header pulse and space for key repeats, so set this to non-zero to make the header optional. Default 0.

An alternative implementation might only allow missing headers for repeat messages, but this would fail to decode key presses if the first message with the header did not decode correctly to due interference.

pulse_length

This is a generic decoder for protocols that define bits by length of pulses, and the spaces are always the same. The sony protocol is the most well-known protocol, but this decoder is for protocols which are not sony.

margin
Define how much tolerance there is for message length. Default 200.
header_pulse
Length of the first leading pulse. Default 2125.
header_space
Length of the space after the leading pulse. Default 1875.
repeat_pulse
Length of the leading pulse for key repeat. Default 0.
repeat_space
Length of the space after the leading pulse for key repeat. Default 0.
bit_space
Length of the space for each bit. Default 625.
bit_0_pulse
Length of the pulse for a zero bit. Default 375.
bit_1_pulse
Length of the pulse for a one bit. Default 1625.
trailer_pulse
Length of the pulse after the last bit. Optional. Default 0.
bits
Number of bits. Default 4.
reverse
Should the bits be read in least significant bit first. Set to non-zero to enable. Default 0.
header_optional
Some remotes do not send the header pulse and space for key repeats, so set this to non-zero to make the header optional. Default 0.

An alternative implementation might only allow missing headers for repeat messages, but this would fail to decode key presses if only the first message did not decode correctly to due interference.
