reprotest(1)

الحزمة: reprotest

التراخيص: GPL3

OPTIONS

--auto-preset-expr PYTHON_EXPRESSION
This may be used to transform the presets returned by the auto-detection feature. The value should be a python expression that transforms the _ variable, which is of type reprotest.presets.ReprotestPreset. See that class's documentation for ways you can write this expression. Default: _
--no-clean-on-error
Don't clean the virtual_server if there was an error. Useful for debugging but will leave cruft on your system depending on the virtual_server used; we hint about some but there may be others.
--dry-run
Don't run the builds, just print what would happen.
--print-sudoers
Print a sudoers file for passwordless operation using the given --variations, useful for user_group.available, domain_host.use_sudo.
--control-build CONTROL_BUILD
Override control build with artifacts located on this path. Allows reusing previous build as baseline.
--append-build-command COMMANDS
Append arguments to the build command

COMMAND-LINE EXAMPLES

The easiest way to run reprotest is via our presets:

# Build the current directory in a null server (/tmp)
$ reprotest .
$ reprotest . -vv -- null -d # for very verbose output
# Build a make-based program
$ reprotest "make clean && make" mybinary
# Build a Debian package
$ apt-get source hello && cd hello-2.10
$ reprotest  auto -- null
# Build a Debian package and disable some variations
$ reprotest --vary=-user_group,-domain_host,-fileordering auto -- null
# Build the given Debian source package in an schroot
# See https://wiki.debian.org/sbuild for instructions on setting that up.
$ reprotest reprotest_0.3.3.dsc -- schroot unstable-amd64-sbuild
# Build the given RPM source package
# Only null server (/tmp) is currently supported.
$ reprotest reprotest-0.7.16.src.rpm
# Build the given RPM source package and automatically install dependencies
$ reprotest --testbed-build-pre 'dnf -y builddep ./*.src.rpm' reprotest-0.7.16.src.rpm

Currently, we only support this for Debian and RPM based packages, but are keen on adding more. If we don't have knowledge on how to build your file or directory, you can send a patch to us on adding this intelligence - see the reprotest.presets python module, and adapt the existing logic.

In the meantime, you can use other parts of the CLI to build arbitrary things. You'll need to give two mandatory arguments, the build command to run and the build artifact file/pattern to test after running the build. For example:

$ reprotest 'python3 setup.py bdist' 'dist/*.tar.gz'

This runs the command on ., the current working directory. To run it on a project located elsewhere:

$ reprotest -s ../path/to/other/project 'python3 setup.py bdist' 'dist/*.tar.gz'
$ reprotest -c 'python3 setup.py bdist' ../path/to/other/project 'dist/*.tar.gz'

These two invocations are equivalent; you can pick the most convenient one for your use-case. When using these from a shell:

  • If the build command has spaces, you will need to quote them, e.g. reprotest "dpkg-buildpackage -b --no-sign" [..].
  • If you want to use several build artifact patterns, or if you want to use shell wildcards as a pattern, you will also need to quote them, e.g. reprotest [..] "*.tar.gz *.tar.xz".
  • If your build artifacts have spaces in their names, you will need to quote these twice, e.g. '"a file with spaces.gz"' for a single artifact or '"dir 1"/* "dir 2"/*' for multiple patterns.

To get more help for the CLI, including documentation on optional arguments and what they do, run:

$ reprotest --help

RUNNING IN A VIRTUAL SERVER

You can also run the build inside what is called a "virtual server". This could be a container, a chroot, etc. You run them like this:

$ reprotest 'python3 setup.py bdist_wheel'   'dist/*.whl' -- qemu    /path/to/qemu.img
$ reprotest 'dpkg-buildpackage -b --no-sign' '../*.deb'   -- schroot unstable-amd64

There are different server types available. See --help for a list of them, which appears near the top, in the "virtual_server_args" part of the "positional arguments" section.

For each virtual server (e.g. "schroot"), you see which extra arguments it supports:

$ reprotest --help schroot

When running builds inside a virtual server, you will probably have to give extra commands, in order to set up your build dependencies inside the virtual server. For example, to take you through what the "Debian directory" preset would look like, if we ran it using the full CLI:

# "Debian directory" preset
$ reprotest . -- schroot unstable-amd64-sbuild
# This is exactly equivalent to this:
$ reprotest -c auto . -- schroot unstable-amd64-sbuild
# In the non-preset full CLI, this is roughly similar to:
$ reprotest \
    --testbed-init 'apt-get -y --no-install-recommends install \
                    disorderfs faketime locales-all sudo util-linux; \
                    test -c /dev/fuse || mknod -m 666 /dev/fuse c 10 229; \
                    test -f /etc/mtab || ln -s ../proc/self/mounts /etc/mtab' \
    --testbed-build-pre 'apt-get -y --no-install-recommends build-dep ./' \
    --build-command 'dpkg-buildpackage --no-sign -b' \
    . \
    '../*.deb' \
    -- \
    schroot unstable-amd64-sbuild

The --testbed-init argument is needed to set up basic tools, which reprotest needs in order to make the variations in the first place. This should be the same regardless of what package is being built, but might differ depending on what virtual_server is being used.

Next, we have --testbed-build-pre, then --build-command (or -c). For our Debian directory, we install build-dependencies using apt-get, then we run the actual build command itself using dpkg-buildpackage(1).

Then, we have the source_root and the artifact_pattern. For reproducibility, we're only interested in the binary packages.

Finally, we specify that this is to take place in the "schroot" virtual_server with arguments "unstable-amd64-sbuild".

Of course, all of this is a burden to remember, if you must run the same thing many times. So that is why adding new presets for new package types would be good.

Here is a more complex example. It tells reprotest to store the build products into ./artifacts to analyse later; and also tweaks the "Debian dsc" preset so that it uses our experimental toolchain https://wiki.debian.org/ReproducibleBuilds/ExperimentalToolchain:

$ reprotest --store-dir=artifacts \
    --auto-preset-expr '_.prepend.testbed_init("apt-get install -y wget; \
        echo deb http://reproducible.alioth.debian.org/debian/ ./ >> /etc/apt/sources.list; \
        wget -q -O- https://reproducible.alioth.debian.org/reproducible.asc | apt-key add -; \
        apt-get update; apt-get upgrade -y; ")' \
    ./bash_4.4-4.0~reproducible1.dsc \
    -- \
    schroot unstable-amd64-sbuild

Alternatively, you can clone your unstable-amd64-sbuild chroot, add our repo to the cloned chroot, then use this chroot in place of "unstable-amd64-sbuild". That would allow you to omit the long --auto-preset-expr flag above.

CONFIG FILE

You can also give options to reprotest via a config file. This is a time-saving measure similar to auto presets; the difference is that these are more suited for local builds that are suited to your personal purposes. (You may use both presets and config files in the same build.)

The config file takes exactly the same options as the command-line interface, but with the additional restriction that the section name must match the ones given in the --help output. Whitespace is allowed if and only if the same command-line option allows whitespace. Finally, it is not possible to give positional arguments via this mechanism.

Reprotest by default does not load any config file. You can tell it to load one with the --config-file or -f command line options. If you give it a directory such as ., it will load .reprotestrc within that directory.

A sample config file is below:

[basics]
verbosity = 1
variations =
  environment
  build_path
  user_group.available+=builduser:builduser
  fileordering
  home
  kernel
  locales
  exec_path
  time
  timezone
  umask
store_dir =
  /home/foo/build/reprotest-artifacts
[diff]
diffoscope_arg =
  --debug

ANALYSING DIFF OUTPUT

Normally when diffoscope compares directories, it also compares the metadata of files in those directories - file permissions, owners, and so on.

However depending on the circumstance, this filesystem-level metadata may or may not be intended to be distributed to other systems. For example: (1) for most distros' package builders, we don't care about the metadata of the output package files; only the file contents will be distributed to other systems. On the other hand, (2) when running something like make install, we do care about the metadata, because this is what will be recreated on another system.

In developing reprotest, our experience has been that case (1) is more common and so we pass --exclude-directory-metadata=yes by default to diffoscope. If you find that you are using reprotest for case (2) then you should pass --diffoscope-args=--exclu

de-directory-metadata=no إلى reprotest، لإخبار diffoscope بعدم تجاهل البيانات الوصفية لأنها سيتم توزيعها ويجب أن تكون قابلة للتكرار. وإلا، قد تحصل على نتيجة إيجابية خاطئة.

الاختلافات

العلامات --vary و --variations في أشكالها البسيطة، هي قائمة مفصولة بفواصل لأسماء الاختلافات التي تشير إلى الاختلافات التي يجب تطبيقها. القائمة الكاملة للأسماء معطاة في نص --help لـ --variations.

بتفصيل كامل، العلامات هي قائمة مفصولة بفواصل من الإجراءات، على النحو التالي:
+$variation (أو $variation بدون عامل تشغيل صريح)
-$variation
تمكين أو تعطيل اختلاف
@$variation
تمكين اختلاف، مع إعادة تعيين معلماته (انظر أدناه) إلى القيم الافتراضية.
$variation.$param=$value
$variation.$param+=$value
$variation.$param-=$value
تعيين/إضافة/إزالة $value كـ/إلى/من القيمة الحالية للمعلمة $param
للـ $variation.
$variation.$param++
$variation.$param--
زيادة/إنقاص قيمة المعلمة $param للـ $variation.

معظم الاختلافات ليس لديها معلمات، وبالنسبة لها فقط عوامل التشغيل + و - هي ذات صلة. الاختلافات التي تقبل معلمات هي:

build_path.path
المسار الذي سيتم استخدامه لبناء التجارب عند تمكين اختلافات مسار البناء. يجب أن يكون هذا في موقع يمكن للمستخدم المستخدم لتشغيل البناء الكتابة فيه. هذا مفيد (بشكل ساخر إلى حد ما) لتطبيع مسار البناء عند استخدامه بالاقتران مع --control-build للمقارنة مع بناء موجود لم يتم إجراؤه باستخدام reprotest.
domain_host.use_sudo
عدد صحيح، سواء تم استخدام sudo(1) مع unshare(1) لتغيير اسم المضيف واسم النطاق للنظام. 0 يعني عدم استخدام sudo؛ أي قيمة غير صفرية تعني استخدام sudo. الافتراضي هو 0، ومع ذلك لا يُنصح بهذا وقد يتسبب في فشل البناء الخاص بك، انظر "تغيير أسماء النطاقات والمضيفين" للتفاصيل.
environment.variables
مجموعة مرتبة مفصولة بفواصل منقوطة، تحدد متغيرات البيئة التي يجب أن يحاول reprotest تغييرها. الافتراضي هو "REPROTEST_CAPTURE_ENVIRONMENT". يدعم صيغة تعتمد على التعبيرات النمطية مثل:
  • PID=\d{1,6}
  • HOME=(/\w{3,12}){1,4}
  • (GO|PYTHON|)PATH=(/\w{3,12}){1,4}(:(/\w{3,12}){1,4}){0,4}

حالات خاصة:

  • $VARNAME= (الجانب الأيمن فارغ) لإخبار reprotest بحذف المتغير
  • $VARNAME=.{0} لإخبار reprotest بتعيين قيمة فارغة بالفعل
  • \x2c و \x3b لمطابقة أو إنشاء , و ; على التوالي.
user_group.available
مجموعة مرتبة مفصولة بفواصل منقوطة، تحدد مجموعات المستخدم+المجموعة المتاحة التي يمكن لـ reprotest استخدام sudo(1) لها. الافتراضي فارغ، وفي هذه الحالة يكون الاختلاف عديم الفائدة، وسترى تحذيرًا بشأن هذا. يجب تقديم كل مستخدم+مجموعة في شكل $user:$group حيث يمكن حذف أي من المكونين، أو إذا لم يكن هناك نقطتان رأسيتان فسيتم تفسيرهما على أنه $user فقط، بدون اختلاف $group.
time.faketimes
مجموعة مرتبة مفصولة بفواصل منقوطة، تحدد واصفات وقت faketime(1) المحتملة للاستخدام. الافتراضي فارغ، وفي هذه الحالة نختار وقتًا: إما الآن (إذا كان آخر وقت لتعديل الملف في source_root أقدم من 398 يومًا) أو بعد أكثر من 398 يومًا في المستقبل.

لاحظ أن الساعة تستمر في العمل أثناء البناء. من الممكن لـ faketime(1) تجميدها، لكننا لم ندعم ذلك بعد؛ هناك احتمال أكبر لفشل البناء الخاص بك أو لسوء سلوكه.

locales.locale
قائمة مفصولة بفواصل منقوطة تضم مكانًا واحدًا أو أكثر لاختبارها عند إجراء اختلافات الأماكن. إذا تم تحديد عدة أماكن، فسيتم اختيار واحد عشوائيًا. الأماكن ذات الخصائص المختلفة عن en_US.UTF-8 هي fr_CH.UTF-8، ru_RU.CP1251، kk_KZ.RK1048 أو zh_CN. الافتراضي هو et_EE.UTF-8 إذا لم يتم تحديده.
num_cpus.cpus
قائمة مفصولة بفواصل منقوطة تتكون من قيمة رقمية واحدة أو أكثر لتحديد عدد وحدات المعالجة المركزية المستخدمة عند إجراء اختلافات num_cpus.

الفرق بين --vary و --variations هو أن الأول يضيف إلى القيم السابقة بينما الآخر يعيد تعيينها. علاوة على ذلك، يتم التعامل مع القيمة الأخيرة المعينة لـ --variations كوسيط --vary صفري. على سبيل المثال:

reprotest --vary=-user_group

يعني تغيير +all (القيمة الافتراضية لـ --variations) و -user_group (القيمة المعطاة لـ --vary)، بينما:

reprotest --variations=-all,locales --variations=home,time --vary=timezone --vary=-time

يعني تغيير home، time (القيمة الأخيرة المعطاة لـ --variations)، timezone، و -time (القيم المتعددة المعطاة لـ --vary)، أي home و timezone.

ملاحظات على الاختلافات

يحاول reprotest جاهداً إجراء الاختلافات دون افتراض أن لديه وصولاً كاملاً كجذر للنظام. كما يفترض أن البرامج الأخرى قد تعمل على نفس النظام، لذلك لا يقوم بإجراء تعديلات على مستوى النظام تؤثر على العمليات الأخرى. بسبب هذه الافتراضات، يتم تنفيذ بعض الاختلافات باستخدام حيل بمستويات مختلفة من القذارة، والتي يتم توثيقها أدناه.

نأمل أن نرفع هذه الافتراضات لسياقات virtual_server معينة، في المستقبل. من المحتمل أن يسمح ذلك بتشغيل أكثر سلاسة في تلك السياقات. ستظل الافتراضات قائمة لـ virtual_server "null" (الافتراضي) ومع ذلك.

عدد وحدات المعالجة المركزية

يستخدم البناء المتحكم وحدة معالجة مركزية واحدة فقط لمحاولة تقليل عدم الحتمية التي قد توجد بسبب تعدد مؤشرات الترابط أو العمليات. إذا كنت متأكدًا من أن البناء الخاص بك غير متأثر بهذا (ويجب ألا تكون عمليات البناء الجيدة كذلك)، يمكنك إعطاء --min-cpus=99999 لاستخدام جميع الأنوية المتاحة لكلا البنائين.

النطاق أو المضيف

قد يؤدي القيام بذلك بدون sudo إلى فشل البناء الخاص بك.

من المحتمل أن يفشل إذا كان البناء الخاص بك يجب أن يقوم بأشياء متعلقة بالنظام - على عكس معالجة البتات والبايتات فقط. هذا لأنه يعمل في مساحة اسم منفصلة حيث يبدو المستخدم غير المميز الخاص بك "root"، ولكنه يمنع نظام الملفات من التعرف على الملفات المملوكة للمستخدم "root" الفعلي، من بين أمور أخرى. هذا قيد على unshare(1) ولا يمكن تجاوزه في reprotest بدون جهد كبير.

لذلك، يوصى بتشغيل هذا الاختلاف مع use_sudo=1. لتجنب مطالبات كلمة المرور، انظر القسم "تجنب مطالبات كلمة مرور sudo(1)" أدناه.

عند العمل داخل خادم افتراضي:

تفشل طريقة عدم استخدام sudo مع "Operation not permitted"، حتى لو قمت بتحرير /proc/sys/kernel/unprivileged_userns_clone. السبب غير معروف حاليًا.

تعمل طريقة sudo فقط إذا اتخذت تدابير لتجنب مطالبات كلمة مرور sudo، حيث لا تحتوي الحاويات على طريقة لإدخالها.

المستخدم أو المجموعة

إذا قمت أيضًا بتغيير ترتيب الملفات في نفس الوقت (وهذا هو الحال افتراضيًا)، فيجب أن يكون كل مستخدم تستخدمه في مجموعة "fuse". افعل ذلك عن طريق تشغيل usermod -aG fuse $OTHERUSER كـ root.

لتجنب مطالبات كلمة مرور sudo(1)، انظر القسم "تجنب مطالبات كلمة مرور sudo(1)" أدناه.

الوقت

يستخدم اختلاف "الوقت" faketime(1) والذي يسبب أحيانًا مشاكل غريبة ويصعب تشخيصها. في الماضي، شملت هذه:

  • عمليات بناء تستغرق وقتًا لا نهائيًا؛ على الرغم من أنه يجب إصلاح هذا في الإصدارات الحديثة من reprotest.
  • عمليات بناء بفروقات غير معقولة ناتجة عن قيام نصوص configure البرمجية بإنتاج نتائج مختلفة مع وبدون faketime. هذا لا يزال يؤثر على bash وربما حزم أخرى معينة تستخدم autotools.
  • فشل عمليات البناء التي تصل إلى الشبكة بسبب أخطاء انتهاء صلاحية الشهادات و/أو أخطاء أمان أخرى متعلقة بالوقت. (لا ينبغي لعمليات البناء الشفافة لـ FOSS الوصول إلى الشبكة في المقام الأول، ولكنه خارج نطاق reprotest التدقيق أو منع ذلك.)

إذا رأيت فرقًا تعتقد حقًا أنه لا ينبغي أن يكون موجودًا، فحاول تمرير --variations=-time إلى reprotest، و/أو تحقق من نتائجنا على https://tests.reproducible-builds.org/ التي تستخدم آلية مختلفة (أكثر موثوقية) لتغيير وقت النظام.

النواة

اختلاف "النواة" لا يعمل حاليًا للحزم المستندة إلى RPM وعمليات البناء الأخرى التي تتطلب ldconfig. أثناء البناء مع تمكين هذا الاختلاف، يشتكي ldconfig من FATAL: kernel too old ويتوقف البناء.

تجنب مطالبات كلمة مرور sudo(1)

لا توجد حاليًا طريقة جيدة للقيام بذلك. ما يلي هو حل تجريبي وهو غير مستقر وغير نظيف. سيتعين عليك أن تقرر بنفسك ما إذا كان الأمر يستحق ذلك لحالة استخدامك:

$ reprotest --print-sudoers \
    --variations=user_group.available+=guest-builder,domain_host.use_sudo=1 \
    | sudo EDITOR=tee visudo -f /etc/sudoers.d/local-reprotest

تأكد من تعيين الاختلافات التي تريد استخدامها بالفعل. من الواضح، لا تختر مستخدمين مميزين لهذا الغرض، مثل root.

(تبسيط الإخراج باستخدام أحرف البدل، سيفتح الوصول بدون كلمة مرور لتغيير ملكية أي شيء على نظامك، لأن أحرف البدل هنا تطابق المسافات البيضاء. لا أعرف ما الذي كان يفكر فيه مؤلفو sudo.)

لا، هذا ليس لطيفًا على الإطلاق - الاقتراحات والتصحيحات مرحب بها.

إذا كنت ترغب في استخدام هذا في خادم افتراضي مثل chroot، فستحتاج إلى نسخ (أو تحميل أو تعيين بطريقة أخرى) النتيجة

هذا الموقع غير مرتبط بـ Arch Linux ولا تابع له بأي شكل من الأشكال. المحتوى هو ترجمة فقط لصفحات دليل Arch المنشورة على man.archlinux.org.
