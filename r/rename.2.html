NAME

rename - change the name or location of a file

LIBRARY

Standard C library (libc, -lc)

SYNOPSIS

    #include <stdio.h>

    int rename(const char *oldpath, const char *newpath);

    #include <fcntl.h> // For AT_* flags

    int renameat(int olddirfd, const char *oldpath, int newdirfd,
                 const char *newpath);

    #define _GNU_SOURCE
    #include <fcntl.h>

    int renameat2(int olddirfd, const char *oldpath, int newdirfd,
                  const char *newpath, unsigned int flags);

DESCRIPTION

The rename() function renames a file or directory, moving it from one place to another if necessary. The old path is given by oldpath, and the new path is given by newpath.

If newpath exists, it must be a single empty directory for the rename to succeed, unless the process has the CAP_SYS_ADMIN capability (or the real or effective UID is 0). If newpath exists and is a file and not a directory, it will be atomically replaced by the link named by oldpath (if oldpath is not a directory). If oldpath is a directory, newpath must not exist, or must be an empty directory.

If oldpath and newpath are in the same directory, rename() should be an atomic operation provided that both arguments are plain files. If oldpath and newpath are on different filesystems, rename() fails with the error EXDEV.

The behavior of rename() when trying to rename a directory is filesystem-dependent. For example, on some filesystems, you can rename a directory, but on others, it is not permitted.

The process must have appropriate privileges to perform the rename. Specifically, write permission is required for the directories in which the files reside.

If oldpath is a symbolic link, then the symbolic link itself is renamed. The target of the link is unaffected.

If newpath is a symbolic link, it will be overwritten. The target of the link is unaffected.

The renameat() function is equivalent to rename() except that the manner in which pathnames are resolved is modified according to the values of olddirfd and newdirfd. If oldpath (or newpath) is an absolute path, then olddirfd (or newdirfd) is ignored. If oldpath (or newpath) is a relative path, then it is resolved relative to the directory indicated by the file descriptor olddirfd (or newdirfd). If either oldpath or newpath, or both, are relative paths then olddirfd and newdirfd may specify different base directories.

If olddirfd is the special value AT_FDCWD, then oldpath is resolved relative to the current working directory. If newdirfd is the special value AT_FDCWD, then newpath is resolved relative to the current working directory.

The behavior of renameat() is undefined if any of the file descriptors olddirfd or newdirfd are neither the special value AT_FDCWD nor a valid file descriptor referring to a directory.

The renameat2() function is a modern extension of renameat(). It adds a flags argument that allows fine-grained control over the rename operation. The following flags are supported:

RENAME_NOREPLACE
Do not replace an existing file. If newpath already exists, renameat2() fails with the error EEXIST. This flag is useful for implementing atomic renames of configuration files where you want to ensure that you don't accidentally overwrite an existing file.
RENAME_EXCHANGE
Atomically exchange the existence of oldpath and newpath. Both paths must exist. If newpath does not exist, renameat2() fails with the error ENOENT. If both paths exist, their existence is exchanged. If oldpath is a directory, it must be empty. If newpath is a directory, it must be empty.
RENAME_WHITEOUT
Create a whiteout (a special type of empty file that indicates the absence of a file) at newpath. This flag is primarily used by overlay filesystems. The caller must have the CAP_MKNOD capability to use this flag.

The flags argument can also be 0 for default behavior.

RETURN VALUE

On success, zero is returned. On failure, -1 is returned, and errno is set to indicate the error.

ERRORS

The following error conditions can occur for rename(), renameat(), and renameat2():

EACCES
A component in the path prefix of either oldpath or newpath denied write access, or search permission was denied for one of the directories in oldpath or newpath. (A file is considered to be in a directory, so we check write permissions on the directory.)
EBUSY
oldpath refers to a file that is busy (e.g., is a mounted file system as a mount point), while the system considers this an error. (Note that there is no requirement to return EBUSY in such cases—there is nothing wrong with doing the rename anyway—but it is allowed to return EBUSY if the system cannot otherwise handle such situations.)
EDQUOT
The user's quota of disk blocks on the filesystem has been exhausted.
EFAULT
oldpath or newpath points outside your accessible address space.
EINVAL
The new pathname contained a path prefix of the old, or, more generally, an attempt was made to make a directory a subdirectory of itself.
EISDIR
newpath is an existing directory, but oldpath is not a directory.
ELOOP
Too many symbolic links were encountered in resolving oldpath or newpath.
EMLINK
oldpath already has the maximum number of links to it, or it was a directory and the directory containing newpath has the maximum number of links.
ENAMETOOLONG
oldpath or newpath was too long.
ENOENT
The link named by oldpath does not exist; or, a directory component in newpath does not exist; or, oldpath or newpath is an empty string.
ENOMEM
Insufficient kernel memory was available.
ENOSPC
The device containing the file has no room for the new directory entry.
ENOTDIR
A component used as a directory in oldpath or newpath is not, in fact, a directory. Or, oldpath is a directory, and newpath exists but is not a directory.
ENOTEMPTY or EEXIST
newpath is a nonempty directory, that is, contains entries other than "." and "..".
EPERM or EACCES
The directory containing oldpath has the sticky bit (S_ISVTX) set and the process's effective user ID is neither the user ID of the file to be deleted nor that of the directory containing it, and the process is not privileged (Linux: does not have the CAP_FOWNER capability); or newpath is an existing file and the directory containing it has the sticky bit set and the process's effective user ID is neither the user ID of the file to be replaced nor that of the directory containing it, and the process is not privileged (Linux: does not have the CAP_FOWNER capability); or the filesystem containing oldpath does not support renaming of the type requested.
EROFS
The file is on a read-only filesystem.
EXDEV
oldpath and newpath are not on the same mounted filesystem. (Linux permits a filesystem to be mounted at multiple points, but rename() does not work across different mount points, even if the same filesystem is mounted on both.)

The following additional errors can occur for renameat() and renameat2():

EBADF
oldpath (newpath) is relative but olddirfd (newdirfd) is not a valid file descriptor.
ENOTDIR
oldpath is relative and olddirfd is a file descriptor referring to a file other than a directory; or similar for newpath and newdirfd

The following additional errors can occur for renameat2():

EEXIST
flags contains RENAME_NOREPLACE and newpath already exists.
EINVAL
An invalid flag was specified in flags.
EINVAL
Both RENAME_NOREPLACE and RENAME_EXCHANGE were specified in flags.
EINVAL
Both RENAME_WHITEOUT and RENAME_EXCHANGE were specified in flags.
EINVAL
The filesystem does not support one of the flags in flags.
ENOENT
flags contains RENAME_EXCHANGE and newpath does not exist.
EPERM
RENAME_WHITEOUT was specified in flags, but the caller does not have the CAP_MKNOD capability.

STANDARDS

C11, POSIX.1-2024.
renameat()
POSIX.1-2024.

HISTORY

Linux 3.15, glibc 2.28.

glibc notes

On older kernels where renameat() is unavailable, the glibc wrapper function falls back to the use of rename(). When oldpath and newpath are relative pathnames, glibc constructs pathnames based on the symbolic links in /proc/self/fd that correspond to the olddirfd and newdirfd arguments.

BUGS

On NFS filesystems, you can not assume that if the operation failed, the file was not renamed. If the server does the rename operation and then crashes, the retransmitted RPC which will be processed when the server is up again causes a failure. The application is expected to deal with this. See link(2) for a similar problem.
