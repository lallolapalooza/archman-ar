تتراوح قيمة هذا الحد من 1 (المقابلة لقيمة "nice" جميلة قدرها 19) إلى 40 (المقابلة لقيمة "nice" جميلة قدرها -20). كان هذا النطاق غير العادي ضروريًا لأن الأرقام السالبة لا يمكن تحديدها كقيم لحدود الموارد، لأنها عادةً ما تحمل معاني خاصة. على سبيل المثال، RLIM_INFINITY عادة ما تكون مساوية لـ -1. لمزيد من التفاصيل حول قيمة "nice"، راجع sched(7).
RLIMIT_NOFILE
يحدد هذا قيمة تزيد بواحد عن أقصى رقم لمُعامل الملفات (file descriptor) يمكن أن يفتحه هذا العملية. المحاولات (open(2)، pipe(2)، dup(2)، وما إلى ذلك) لتجاوز هذا الحد تؤدي إلى الخطأ EMFILE. (تاريخيًا، كان هذا الحد يسمى RLIMIT_OFILE في BSD.)
منذ Linux 4.5، يحدد هذا الحد أيضًا الحد الأقصى لعدد مُعاملات الملفات (file descriptors) التي يمكن لعملية غير مميزة (واحدة بدون القدرة CAP_SYS_RESOURCE) أن تكون "قيد التشغيل" لعمليات أخرى، عن طريق تمريرها عبر مقابس نطاق UNIX. ينطبق هذا الحد على استدعاء النظام sendmsg(2). لمزيد من التفاصيل، راجع unix(7).
RLIMIT_NPROC
هذا هو حد للعمليات النشطة (أو بشكل أكثر دقة في Linux، الخيوط - threads) لمعرف المستخدم الحقيقي (real user ID) للعملية المستدعية. طالما أن العدد الحالي للعمليات التي تنتمي إلى معرف المستخدم الحقيقي لهذه العملية يساوي أو يزيد عن هذا الحد، فإن fork(2) يفشل مع الخطأ EAGAIN.
لا يتم تطبيق حد RLIMIT_NPROC على العمليات التي لديها إما القدرة CAP_SYS_ADMIN أو CAP_SYS_RESOURCE، أو تعمل بمعرف مستخدم حقيقي 0.
RLIMIT_RSS
هذا حد (بالبايت) لمجموعة العمليات المقيمة (resident set) (عدد الصفحات الافتراضية المقيمة في الذاكرة العشوائية - RAM). هذا الحد له تأثير فقط في Linux 2.4.x، x < 30، وهو يؤثر فقط على استدعاءات madvise(2) التي تحدد MADV_WILLNEED.
RLIMIT_RTPRIO (منذ Linux 2.6.12، ولكن انظر BUGS)
يحدد هذا سقفًا للأولوية في الوقت الفعلي (real-time priority) التي يمكن تعيينها لهذه العملية باستخدام sched_setscheduler(2) و sched_setparam(2).
لمزيد من التفاصيل حول سياسات جدولة الوقت الفعلي، راجع sched(7)
RLIMIT_RTTIME (منذ Linux 2.6.25)
هذا حد (بالميكروثانية) لكمية وقت وحدة المعالجة المركزية (CPU time) التي يمكن أن تستهلكها عملية مجدولة بموجب سياسة جدولة في الوقت الفعلي دون إجراء استدعاء نظام يحظر. لغرض هذا الحد، في كل مرة تجري فيها عملية استدعاء نظام يحظر، يتم إعادة تعيين عداد وقت وحدة المعالجة المركزية المستهلكة إلى الصفر. لا يتم إعادة تعيين عداد وقت وحدة المعالجة المركزية إذا استمرت العملية في محاولة استخدام وحدة المعالجة المركزية ولكن تم مقاطعتها، أو انتهت شريحة الوقت الخاصة بها، أو استدعت sched_yield(2).
عند الوصول إلى الحد الناعم (soft limit)، يتم إرسال إشارة SIGXCPU إلى العملية. إذا قامت العملية بالتقاط أو تجاهل هذه الإشارة واستمرت في استهلاك وقت وحدة المعالجة المركزية، فسيتم إنشاء SIGXCPU مرة واحدة كل ثانية حتى يتم الوصول إلى الحد الصعب (hard limit)، وعندها سيتم إرسال إشارة SIGKILL إلى العملية.
الاستخدام المقصود لهذا الحد هو إيقاف عملية في الوقت الفعلي جامحة من تجميد النظام.
لمزيد من التفاصيل حول سياسات جدولة الوقت الفعلي، راجع sched(7)
RLIMIT_SIGPENDING (منذ Linux 2.6.8)
هذا حد لعدد الإشارات التي يمكن وضعها في قائمة انتظار لمعرف المستخدم الحقيقي للعملية المستدعية. يتم احتساب كل من الإشارات القياسية وإشارات الوقت الفعلي لغرض التحقق من هذا الحد. ومع ذلك، لا يتم فرض الحد إلا على sigqueue(3)؛ من الممكن دائمًا استخدام kill(2) لوضع مثيل واحد من أي من الإشارات التي ليست بالفعل في قائمة انتظار للعملية.
RLIMIT_STACK
هذا هو الحد الأقصى لحجم مكدس العملية (process stack)، بالبايت. عند الوصول إلى هذا الحد، يتم إنشاء إشارة SIGSEGV. لمعالجة هذه الإشارة، يجب على العملية استخدام مكدس إشارة بديل (sigaltstack(2)).
منذ Linux 2.6.23، يحدد هذا الحد أيضًا مقدار المساحة المستخدمة لوسائط سطر الأوامر ومتغيرات البيئة الخاصة بالعملية؛ لمزيد من التفاصيل، راجع execve(2).

prlimit()

يجمع استدعاء النظام prlimit() الخاص بنظام Linux ويوسع وظائف setrlimit() و getrlimit(). يمكن استخدامه لتعيين واسترداد حدود موارد عملية عشوائية.

يكون للوسيط resource نفس المعنى كما في setrlimit() و getrlimit().

إذا كانت الوسيط new_limit ليست NULL، فإن البنية rlimit التي تشير إليها تُستخدم لتعيين قيم جديدة للحدود الناعمة والصعبة لـ resource. إذا كانت الوسيط old_limit ليست NULL، فإن استدعاء ناجح لـ prlimit() يضع الحدود الناعمة والصعبة السابقة لـ resource في البنية rlimit التي تشير إليها old_limit.

تحدد الوسيط pid معرف العملية التي سيتم تشغيل الاستدعاء عليها. إذا كان pid يساوي 0، فإن الاستدعاء ينطبق على العملية المستدعية. لتعيين أو استرداد موارد عملية غير نفسها، يجب أن تمتلك الجهة المستدعية القدرة CAP_SYS_RESOURCE في مساحة اسم المستخدم للعملية التي يتم تغيير حدود مواردها، أو يجب أن تتطابق معرفات المستخدم الحقيقية والفعالة والمحفوظة (real, effective, and saved user IDs) للعملية المستهدفة مع معرف المستخدم الحقيقي للجهة المستدعية و يجب أن تتطابق معرفات المجموعة الحقيقية والفعالة والمحفوظة (real, effective, and saved group IDs) للعملية المستهدفة مع معرف المجموعة الحقيقي للجهة المستدعية.

قيمة الإرجاع

عند النجاح، تعيد استدعاءات النظام هذه 0. عند حدوث خطأ، يتم إرجاع -1، ويتم تعيين errno للإشارة إلى الخطأ.

NAME

prlimit — control and report process resource limits

LIBRARY

prlimit(2) (libc)

SYNOPSIS

#include <sys/resource.h>
int prlimit(pid_t pid, int resource,
            const struct rlimit *new_limit,
            struct rlimit *old_limit);

DESCRIPTION

The prlimit() system call allows a process to control and report the resource limits of another process. The pid argument specifies the process ID of the target process. If pid is 0, then the calling process is used.

The resource argument specifies the resource limit to be operated on. The possible values for resource are:

RLIMIT_AS
Maximum size of the process's virtual address space.
RLIMIT_CORE
Maximum size of core files created in blocks.
RLIMIT_CPU
Maximum amount of processor time, in seconds, that a process can consume.
RLIMIT_DATA
Maximum size of the process's data segment (after the break).
RLIMIT_FSIZE
Maximum size of files that this process can create, in bytes.
RLIMIT_LOCKS
Maximum number of fcntl(2) locks held by the process.
RLIMIT_MEMLOCK
Maximum number of bytes of memory that can be locked into RAM with mlock(2) and mlockall(2).
RLIMIT_MSGQUEUE
Maximum number of bytes in POSIX message queues for the process.
RLIMIT_NFILE
Maximum number of files that this process may have open simultaneously. This limit applies to the number of file descriptors returned by open(2) and similar calls.
RLIMIT_NPROC
Maximum number of processes that can be created by the user (real user ID).
RLIMIT_NPAGEFILE
Maximum number of bytes that can be swapped out.
RLIMIT_RTPRIO
Maximum real-time priority that may be assigned to this process.
RLIMIT_RTTIME
Maximum amount of processor time, in microseconds, that a process scheduled with SCHED_RR or SCHED_FIFO may consume.
RLIMIT_SIGPENDING
Maximum number of signals that may be pending for the process.
RLIMIT_STACK
Maximum size of the process stack, in bytes.
RLIMIT_TIMESTAMP
Maximum number of timestamps that can be generated per second.

The new_limit and old_limit arguments are pointers to struct rlimit structures, defined as follows:

struct rlimit {
    rlim_t rlim_cur; /* Current (soft) limit */
    rlim_t rlim_max; /* Maximum (hard) limit */
};

Here, rlim_cur is the current (soft) limit, and rlim_max is the maximum (hard) limit. The type rlim_t is an unsigned integer type.

If new_limit is not NULL, then it points to a struct rlimit structure that specifies the new soft and hard limits for the specified resource. Only processes with the CAP_SYS_RESOURCE capability can increase the hard limit of any resource.

If old_limit is not NULL, then it points to a struct rlimit structure where the previous soft and hard limits for the specified resource are stored.

If both new_limit and old_limit are NULL, then prlimit() performs no operation and returns success, though the kernel may still perform some checks.

Only the privileged process (with the CAP_SYS_RESOURCE capability) can set resource limits for an arbitrary process. Unprivileged processes can set resource limits only for themselves, and they are subject to further restrictions:

An unprivileged process can decrease its soft limit for any resource to any value below its current soft limit, or set it to RLIM_INFINITY.
An unprivileged process can decrease its hard limit for any resource to any value below its current hard limit.
An unprivileged process can increase its soft limit only up to the current hard limit.
An unprivileged process cannot change its hard limits.

The constant RLIM_INFINITY represents an unlimited resource.

Since glibc 2.13, the glibc getrlimit() and setrlimit() wrapper functions no longer invoke the corresponding system calls, but instead employ prlimit(), for the reasons described in BUGS.

The name of the glibc wrapper function is prlimit(); the underlying system call is prlimit64().

RETURN VALUE

On success, prlimit() returns 0. On failure, it returns -1, and errno is set to indicate the error.

ERRORS

EINVAL
An invalid resource was specified.
EPERM
A non-privileged process tried to increase a hard limit, or to increase a soft limit beyond the hard limit.
ESRCH
The process specified by pid does not exist.
EACCES
A non-privileged process tried to set a resource limit for a process other than itself.

Interface Attribute Value
prlimit() Thread safety Not thread-safe

STANDARDS

This system call is Linux-specific.

HISTORY

The prlimit() system call first appeared in Linux kernel 2.6.36.

The glibc wrapper function was added in glibc 2.13. Before glibc 2.13, the getrlimit() and setrlimit() library functions were thin wrappers around the corresponding system calls.

The `rlim_t` type is defined in sys/resource.h. On older systems, it might not be defined correctly. For example, on some older Linux systems, RLIM_INFINITY was defined as 0, and 32-bit systems had a 32-bit `rlim_t`. This could lead to problems when setting large resource limits. For example, the 32-bit version of setrlimit(2) on Linux would silently treat values greater than `ULONG_MAX` as `RLIM_INFINITY`.

On Linux, setrlimit() also accepts the RLIMIT_RTTIME and RLIMIT_TIMESTAMP resources, which are not specified in POSIX.1-2001 or POSIX.1-2008.

The glibc setrlimit() function used to provide a vlimit() interface for compatibility with older systems. This function is now obsolete and should not be used. All new applications should be written using setrlimit().

C library/kernel ABI differences

Since glibc 2.13, the glibc getrlimit() and setrlimit() wrapper functions no longer invoke the corresponding system calls, but instead employ prlimit(), for the reasons described in BUGS.

The name of the glibc wrapper function is prlimit(); the underlying system call is prlimit64().

BUGS

In older Linux kernels, the SIGXCPU and SIGKILL signals delivered when a process encountered the soft and hard RLIMIT_CPU limits were delivered one (CPU) second later than they should have been. This was fixed in Linux 2.6.8.

In Linux 2.6.x kernels before Linux 2.6.17, a RLIMIT_CPU limit of 0 is wrongly treated as "no limit" (like RLIM_INFINITY). Since Linux 2.6.17, setting a limit of 0 does have an effect, but is actually treated as a limit of 1 second.

A kernel bug means that RLIMIT_RTPRIO does not work in Linux 2.6.12; the problem is fixed in Linux 2.6.13.

In Linux 2.6.12, there was an off-by-one mismatch between the priority ranges returned by getpriority(2) and RLIMIT_NICE. This had the effect that the actual ceiling for the nice value was calculated as 19 - rlim_cur. This was fixed in Linux 2.6.13.

Since Linux 2.6.12, if a process reaches its soft RLIMIT_CPU limit and has a handler installed for SIGXCPU, then, in addition to invoking the signal handler, the kernel increases the soft limit by one second. This behavior repeats if the process continues to consume CPU time, until the hard limit is reached, at which point the process is killed. Other implementations do not change the RLIMIT_CPU soft limit in this manner, and the Linux behavior is probably not standards conformant; portable applications should avoid relying on this Linux-specific behavior. The Linux-specific RLIMIT_RTTIME limit exhibits the same behavior when the soft limit is encountered.

Kernels before Linux 2.4.22 did not diagnose the error EINVAL for setrlimit() when rlim->rlim_cur was greater than rlim->rlim_max.

Linux doesn't return an error when an attempt to set RLIMIT_CPU has failed, for compatibility reasons.

Representation of "large" resource limit values on 32-bit platforms

The glibc getrlimit() and setrlimit() wrapper functions use a 64-bit rlim_t data type, even on 32-bit platforms. However, the rlim_t data type used in the getrlimit() and setrlimit() system calls is a (32-bit) unsigned long. Furthermore, in Linux, the kernel represents resource limits on 32-bit platforms as unsigned long. However, a 32-bit data type is not wide enough. The most pertinent limit here is RLIMIT_FSIZE, which specifies the maximum size to which a file can grow: to be useful, this limit must be represented using a type that is as wide as the type used to represent file offsets—that is, as wide as a 64-bit off_t (assuming a program compiled with _FILE_OFFSET_BITS=64).

To work around this kernel limitation, if a program tried to set a resource limit to a value larger than can be represented in a 32-bit unsigned long, then the glibc setrlimit() wrapper function silently converted the limit value to RLIM_INFINITY. In other words, the requested resource limit setting was silently ignored.

Since glibc 2.13, glibc works around the limitations of the getrlimit() and setrlimit() system calls by implementing setrlimit() and getrlimit() as wrapper functions that call prlimit().

EXAMPLES

The program below demonstrates the use of prlimit().

#define _GNU_SOURCE
#define _FILE_OFFSET_BITS 64
#include <err.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/resource.h>
#include <time.h>
int
main(int argc, char *argv[])
{
    pid_t          pid;
    struct rlimit  old, new;
    struct rlimit  *newp;
    if (!(argc == 2 || argc == 4)) {
        fprintf(stderr, "Usage: %s <pid> [<new-soft-limit> "
                "<new-hard-limit>]\n", argv[0]);
        exit(EXIT_FAILURE);
    }
    pid = atoi(argv[1]);        /* PID of target process */
    newp = NULL;
    if (argc == 4) {
        new.rlim_cur = atoi(argv[2]);
        new.rlim_max = atoi(argv[3]);
        newp = &new;
    }
    /* Set CPU time limit of target process; retrieve and display
       previous limit */
    if (prlimit(pid, RLIMIT_CPU, newp, &old) == -1)
        err(EXIT_FAILURE, "prlimit-1");
    printf("Previous limits: soft=%jd; hard=%jd\n",
           (intmax_t) old.rlim_cur, (intmax_t) old.rlim_max);
    /* Retrieve and display new CPU time limit */
    if (prlimit(pid, RLIMIT_CPU, NULL, &old) == -1)
        err(EXIT_FAILURE, "prlimit-2");
    printf("New limits: soft=%jd; hard=%jd\n",
           (intmax_t) old.rlim_cur, (intmax_t) old.rlim_max);
    exit(EXIT_SUCCESS);
}
