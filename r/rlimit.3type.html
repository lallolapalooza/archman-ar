الوصف

استدعاءات النظام getrlimit() و setrlimit() تحصل على حدود الموارد وتعينها. كل مورد له حد ناعم وحد صعب مرتبط به، كما هو محدد في بنية rlimit.

الحد الناعم هو القيمة التي يفرضها النواة للمورد المقابل. الحد الصعب يعمل كسقف للحد الناعم: يمكن لعملية غير مميزة تعيين حدها الناعم فقط إلى قيمة في النطاق من 0 حتى الحد الصعب، وخفض حدها الصعب (بشكل لا رجعة فيه). يمكن لعملية مميزة (في لينكس: عملية تمتلك القدرة CAP_SYS_RESOURCE في مساحة اسم المستخدم الأولية) إجراء تغييرات اعتباطية على أي من قيمتي الحد.

القيمة RLIM_INFINITY تعني عدم وجود حد على مورد (سواء في البنية التي تم إرجاعها بواسطة getrlimit() أو في البنية التي تم تمريرها إلى setrlimit()).

يجب أن يكون الوسيط resource أحد الخيارات التالية:

RLIMIT_AS
هذا هو الحد الأقصى لحجم الذاكرة الافتراضية للعملية (مساحة العنوان). يتم تحديد الحد بالبايت، ويتم تقريبه لأسفل إلى حجم صفحة النظام. يؤثر هذا الحد على استدعاءات brk(2)، mmap(2)، و mremap(2)، والتي تفشل مع الخطأ ENOMEM عند تجاوز هذا الحد. بالإضافة إلى ذلك، يفشل توسيع المكدس التلقائي (ويولد SIGSEGV التي تقتل العملية إذا لم يتم توفير مكدس بديل عبر sigaltstack(2)). نظرًا لأن القيمة هي long، على الأجهزة التي تحتوي على long 32 بت، إما أن هذا الحد هو 2 جيجابايت على الأكثر، أو أن هذا المورد غير محدود.
RLIMIT_CORE
هذا هو الحد الأقصى لحجم ملف core (انظر core(5)) بالبايت الذي يمكن للعملية نسخه. عندما يكون 0، لا يتم إنشاء أي ملفات core dump. عندما يكون غير صفري، يتم تقصير عمليات النسخ الأكبر إلى هذا الحجم.
RLIMIT_CPU
هذا حد، بالثواني، على كمية وقت وحدة المعالجة المركزية التي يمكن للعملية استهلاكها. عندما تصل العملية إلى الحد الناعم، يتم إرسال إشارة SIGXCPU إليها. الإجراء الافتراضي لهذه الإشارة هو إنهاء العملية. ومع ذلك، يمكن التقاط الإشارة، ويمكن للمتعامل معها إعادة التحكم إلى البرنامج الرئيسي. إذا استمرت العملية في استهلاك وقت وحدة المعالجة المركزية، فسيتم إرسال SIGXCPU إليها مرة واحدة في الثانية حتى يتم الوصول إلى الحد الصعب، وعند هذه النقطة يتم إرسال SIGKILL إليها. (هذه النقطة الأخيرة تصف سلوك لينكس. تختلف التطبيقات في كيفية معاملتها للعمليات التي تستمر في استهلاك وقت وحدة المعالجة المركزية بعد الوصول إلى الحد الناعم. يجب على التطبيقات القابلة للنقل التي تحتاج إلى التقاط هذه الإشارة إجراء إنهاء منظم عند الاستلام الأول لـ SIGXCPU.)
RLIMIT_DATA
هذا هو الحد الأقصى لحجم قسم البيانات للعملية (البيانات المهيئة، والبيانات غير المهيئة، والمكدس). يتم تحديد الحد بالبايت، ويتم تقريبه لأسفل إلى حجم صفحة النظام. يؤثر هذا الحد على استدعاءات brk(2)، sbrk(2)، و (منذ لينكس 4.7) mmap(2)، والتي تفشل مع الخطأ ENOMEM عند مواجهة الحد الناعم لهذا المورد.
RLIMIT_FSIZE
هذا هو الحد الأقصى لحجم الملفات بالبايت التي يمكن للعملية إنشاؤها. محاولات توسيع ملف يتجاوز هذا الحد تؤدي إلى تسليم إشارة SIGXFSZ. بشكل افتراضي، تنهي هذه الإشارة عملية، ولكن يمكن للعملية التقاط هذه الإشارة بدلاً من ذلك، وفي هذه الحالة، تفشل استدعاء النظام ذي الصلة (على سبيل المثال، write(2)، truncate(2)) مع الخطأ EFBIG.
RLIMIT_LOCKS (Linux 2.4.0 إلى Linux 2.4.24)
هذا حد على العدد الإجمالي لقفل flock(2) واستئجار fcntl(2) التي يمكن لهذه العملية إنشاؤها.
RLIMIT_MEMLOCK
هذا هو الحد الأقصى لعدد البايتات من الذاكرة التي يمكن قفلها في ذاكرة الوصول العشوائي. يتم تقريب هذا الحد لأسفل إلى أقرب مضاعف لحجم صفحة النظام. يؤثر هذا الحد على mlock(2)، mlockall(2)، و عملية mmap(2) MAP_LOCKED. منذ لينكس 2.6.9، يؤثر أيضًا على عملية shmctl(2) SHM_LOCK، حيث يحدد حدًا أقصى للبايتات الإجمالية في أقسام الذاكرة المشتركة (انظر shmget(2)) التي يمكن قفلها بواسطة معرف المستخدم الحقيقي للعملية المتصلة. يتم حساب أقفال shmctl(2) SHM_LOCK بشكل منفصل عن أقفال الذاكرة لكل عملية التي تم إنشاؤها بواسطة mlock(2)، mlockall(2)، و عملية mmap(2) MAP_LOCKED؛ يمكن للعملية قفل بايتات تصل إلى هذا الحد في كل من هذين الفئتين.
قبل لينكس 2.6.9، كان هذا الحد يتحكم في كمية الذاكرة التي يمكن قفلها بواسطة عملية مميزة. منذ لينكس 2.6.9، لا توجد حدود على كمية الذاكرة التي يمكن لعملية مميزة قفلها، وهذا الحد يحكم بدلاً من ذلك كمية الذاكرة التي يمكن لعملية غير مميزة قفلها.
RLIMIT_MSGQUEUE (منذ لينكس 2.6.8)
هذا حد على عدد البايتات التي يمكن تخصيصها لقوائم انتظار الرسائل POSIX للمعرف المستخدم الحقيقي للعملية المتصلة. يتم فرض هذا الحد على mq_open(3). كل قائمة انتظار رسائل ينشئها المستخدم (حتى تتم إزالتها) تُحتسب مقابل هذا الحد وفقًا للصيغة:
منذ لينكس 3.5:

bytes = attr.mq_maxmsg * sizeof(struct msg_msg) +
        MIN(attr.mq_maxmsg, MQ_PRIO_MAX) *
              sizeof(struct posix_msg_tree_node)+
                        /* للتكاليف الإضافية */
        attr.mq_maxmsg * attr.mq_msgsize;
                        /* لبيانات الرسالة */

لينكس 3.4 والإصدارات الأقدم:

bytes = attr.mq_maxmsg * sizeof(struct msg_msg *) +
                        /* للتكاليف الإضافية */
        attr.mq_maxmsg * attr.mq_msgsize;
                        /* لبيانات الرسالة */

حيث attr هي البنية mq_attr المحددة كمعامل رابع لـ mq_open(3)، و msg_msg و posix_msg_tree_node هي هياكل داخلية للنواة.
تُغطي إضافة "التكاليف الإضافية" في الصيغة البايتات الإضافية المطلوبة بواسطة التنفيذ وتضمن أن المستخدم لا يمكنه إنشاء عدد غير محدود من الرسائل الفارغة (مثل هذه الرسائل لا تزال تستهلك بعض ذاكرة النظام للنفقات الإدارية).
RLIMIT_NICE (منذ لينكس 2.6.12، ولكن انظر BUGS أدناه)

prlimit(2) — prlimit

تعديل حدود الموارد للعملية أو مؤشر ترابط

LIBRARY

libc, -lc

SYNOPSIS

#define _GNU_SOURCE             /* Get prlimit() and PR_SET_MM macro */
#include <sys/resource.h>
int prlimit(pid_t pid, int resource, const struct rlimit *new_rlim, struct rlimit *old_rlim);

DESCRIPTION

The prlimit() system call modifies and/or retrieves resource limits of the calling process (if -1 is specified for pid) or a specified process (if pid is the PID of that process). A process can only modify resource limits for another process if it has appropriate privileges (typically, it must be running as root or have the CAP_SYS_RESOURCE capability). A process can always modify its own resource limits.

The resource argument specifies the resource to be modified or retrieved. It is one of the constants described in getrlimit(2). Currently, the following values are supported:

RLIMIT_AS
Maximum size of the process's virtual address space.
RLIMIT_CORE
Maximum size of a core file.
RLIMIT_CPU
Maximum CPU time (per second) a process can consume.
RLIMIT_DATA
Maximum size of the process's data segment.
RLIMIT_FSIZE
Maximum size of a file that the process can create.
RLIMIT_LOCKS
Maximum number of file locks the process may hold.
RLIMIT_MEMLOCK
Maximum amount of physical memory (RAM) that may be locked into RAM by the process.
RLIMIT_MSGQUEUE
Maximum number of bytes that can be used by POSIX message queues for the real-time messages.
RLIMIT_NICE
Maximum value of the niceness (priority string) that can be set for a process.
RLIMIT_NLIMITS
Maximum number of resource limits that can be created for a process.
RLIMIT_NOFILE
Maximum number of file descriptors that a process may have open.
RLIMIT_NPROC
Maximum number of processes that can be created by the real user ID.
RLIMIT_RSS
Maximum resident set size (physical memory usage).
RLIMIT_RTPRIO
Maximum real-time priority that may be established by a process.
RLIMIT_RTTIME
Maximum amount of CPU time that may be consumed by any threads in the process, which are using real-time scheduling.
RLIMIT_SIGPENDING
Maximum number of signals that can be pending for the process.
RLIMIT_STACK
Maximum size of the process stack.
RLIMIT_TIMESTAMP
This resource limit is not implemented on Linux.

The new_rlim and old_rlim arguments are pointers to struct rlimit structures. Each structure contains two members:

rlim_cur
The soft limit (current limit).
rlim_max
The hard limit (maximum limit).

If new_rlim is not NULL, the soft and hard limits for the specified resource are set to the values given in the structure pointed to by new_rlim. Only the soft limit can be lowered by a non-privileged process. Both soft and hard limits can be raised by a privileged process. A non-privileged process can only increase the soft limit up to the hard limit, and can only increase the hard limit if it is currently RLIM_INFINITY.

If old_rlim is not NULL, the current (soft and hard) limits for the specified resource are stored in the structure pointed to by old_rlim.

The value RLIM_INFINITY represents infinity. For a 32-bit system, the maximum value that can be represented is typically 2^31-1 or 2^32-1. For a 64-bit system, it is 2^63-1.

The pid argument specifies the target process. If pid is -1, then prlimit() operates on the calling process.

Note that getrlimit(2) and setrlimit(2) are often implemented as wrapper functions around the prlimit() system call.

On systems that support cgroups, the effective limits imposed by prlimit() are often overridden by cgroup limits. See cgroups(7).

C library/kernel ABI differences

Since glibc 2.13, the glibc getrlimit() and setrlimit() wrapper functions no longer invoke the corresponding system calls, but instead employ prlimit(), for the reasons described in BUGS.

The name of the glibc wrapper function is prlimit(); the underlying system call is prlimit64().

RETURN VALUE

On success, prlimit() returns 0. On failure, it returns -1, and errno is set to indicate the error.

ERRORS

EACCES
A non-privileged process tried to raise a hard limit above the current hard limit, or to raise a soft limit above the hard limit.
EINVAL
The specified resource is invalid. Or, if new_rlim is not NULL, then either rlim->rlim_cur or rlim->rlim_max is invalid (e.g., negative, or greater than RLIM_INFINITY). Or, the kernel could not represent the requested limit (e.g. a 32-bit kernel trying to set a limit larger than ULONG_MAX).
EPERM
A non-privileged process tried to modify the limits of another process. Or, a process tried to raise a hard limit above the current hard limit. (This is a specific case of EACCES).
ESRCH
The process specified by pid does not exist.

ATTRIBUTES

For an explanation of the terms used in this section, see attributes(7).

Interface Attribute Value
prlimit() feature POSIX.1 N/A
prlimit() feature XSI N/A
prlimit() feature GNU N/A

STANDARDS

The prlimit() system call is specific to Linux. It is available on Linux since kernel 2.6.36. It was added to glibc in version 2.13.

HISTORY

The prlimit() system call was introduced in Linux kernel 2.6.36. It was added to glibc in version 2.13. Prior to glibc 2.13, getrlimit(2) and setrlimit(2) were implemented using the getrlimit and setrlimit system calls, respectively. Since glibc 2.13, these functions are implemented using the prlimit() system call.

The RLIMIT_RTTIME resource limit was added in kernel 2.6.25. The RLIMIT_MSGQUEUE and RLIMIT_RTPRIO resource limits were added in kernel 2.6.26. The RLIMIT_TIMESTAMP resource limit is not implemented on Linux.

The pid argument of prlimit() was added in kernel 3.4.

NOTES

The older setrlimit(2) and getrlimit(2) system calls are older than prlimit(). On Linux, these older system calls are implemented using the prlimit64() system call. The glibc wrappers setrlimit(2) and getrlimit(2) use the prlimit() system call. The use of prlimit() is preferred because it handles 64-bit values correctly on 32-bit systems, avoiding the problem described in the BUGS section below.

The value RLIM_INFINITY is defined as the largest possible value for rlim_t. On Linux, this is typically 2^63-1 on 64-bit systems and 2^32-1 on 32-bit systems.

It is possible to use prlimit() to set resource limits for processes that are not children of the calling process. However, this requires the calling process to have the CAP_SYS_RESOURCE capability, or to be running as root.

The prlimit() system call can also be used to set the PR_SET_MM, PR_GET_MM, PR_SET_PTRACER, PR_GET_PTRACER, PR_SET_SYSCALL_USER_DISPATCH, and PR_GET_SYSCALL_USER_DISPATCH process attributes. See prctl(1) for details.

The prlimit() system call uses the prlimit64() system call internally, which handles resource limits that may exceed the size of a 32-bit type. This ensures correct behavior even on 32-bit systems when dealing with large resource limits, such as file sizes.

A non-privileged process can change its own soft limits up to the hard limit. It can also change its hard limits, but only if the current value is RLIM_INFINITY. A privileged process (root or CAP_SYS_RESOURCE) can change both soft and hard limits without restriction.

The prlimit() call is a superset of the functionality of getrlimit(2) and setrlimit(2). If new_rlim is NULL, then only the current limits are retrieved. If old_rlim is NULL, then only the limits are set. If both are non-NULL, then both are retrieved and set.

The prlimit() system call is a Linux-specific extension. The POSIX standard only defines getrlimit(2) and setrlimit(2).

Note that older Linux kernels might not correctly handle large values for resource limits on 32-bit systems. For example, attempting to set RLIMIT_FSIZE to a value greater than ULONG_MAX might result in the limit being silently set to RLIM_INFINITY. This is why glibc uses prlimit() instead of the older setrlimit() system call.

The prlimit() system call is generally preferred over setrlimit(2) and getrlimit(2) because it can correctly handle resource limits larger than what can be represented by a 32-bit unsigned long, even on 32-bit architectures. This is especially important for RLIMIT_FSIZE.

When the soft RLIMIT_CPU limit is encountered, the kernel may increase the soft limit by one second if the process has a signal handler for SIGXCPU. This behavior is Linux-specific and may not be portable. Portable applications should avoid relying on this behavior.

Also note that older versions of libc may provide a wrapper for setrlimit() that uses the vlimit() system call. All new applications should be written using setrlimit().

C library/kernel ABI differences

Since glibc 2.13, the glibc getrlimit() and setrlimit() wrapper functions no longer invoke the corresponding system calls, but instead employ prlimit(), for the reasons described in BUGS.

The name of the glibc wrapper function is prlimit(); the underlying system call is prlimit64().

BUGS

In older Linux kernels, the SIGXCPU and SIGKILL signals delivered when a process encountered the soft and hard RLIMIT_CPU limits were delivered one (CPU) second later than they should have been. This was fixed in Linux 2.6.8.

In Linux 2.6.x kernels before Linux 2.6.17, a RLIMIT_CPU limit of 0 is wrongly treated as "no limit" (like RLIM_INFINITY). Since Linux 2.6.17, setting a limit of 0 does have an effect, but is actually treated as a limit of 1 second.

A kernel bug means that RLIMIT_RTPRIO does not work in Linux 2.6.12; the problem is fixed in Linux 2.6.13.

In Linux 2.6.12, there was an off-by-one mismatch between the priority ranges returned by getpriority(2) and RLIMIT_NICE. This had the effect that the actual ceiling for the nice value was calculated as 19 - rlim_cur. This was fixed in Linux 2.6.13.

Since Linux 2.6.12, if a process reaches its soft RLIMIT_CPU limit and has a handler installed for SIGXCPU, then, in addition to invoking the signal handler, the kernel increases the soft limit by one second. This behavior repeats if the process continues to consume CPU time, until the hard limit is reached, at which point the process is killed. Other implementations do not change the RLIMIT_CPU soft limit in this manner, and the Linux behavior is probably not standards conformant; portable applications should avoid relying on this Linux-specific behavior. The Linux-specific RLIMIT_RTTIME limit exhibits the same behavior when the soft limit is encountered.

Kernels before Linux 2.4.22 did not diagnose the error EINVAL for setrlimit() when rlim->rlim_cur was greater than rlim->rlim_max.

Linux doesn't return an error when an attempt to set RLIMIT_CPU has failed, for compatibility reasons.

Representation of "large" resource limit values on 32-bit platforms

The glibc getrlimit() and setrlimit() wrapper functions use a 64-bit rlim_t data type, even on 32-bit platforms. However, the rlim_t data type used in the getrlimit() and setrlimit() system calls is a (32-bit) unsigned long. Furthermore, in Linux, the kernel represents resource limits on 32-bit platforms as unsigned long. However, a 32-bit data type is not wide enough. The most pertinent limit here is RLIMIT_FSIZE, which specifies the maximum size to which a file can grow: to be useful, this limit must be represented using a type that is as wide as the type used to represent file offsets—that is, as wide as a 64-bit off_t (assuming a program compiled with _FILE_OFFSET_BITS=64).

To work around this kernel limitation, if a program tried to set a resource limit to a value larger than can be represented in a 32-bit unsigned long, then the glibc setrlimit() wrapper function silently converted the limit value to RLIM_INFINITY. In other words, the requested resource limit setting was silently ignored.

Since glibc 2.13, glibc works around the limitations of the getrlimit() and setrlimit() system calls by implementing setrlimit() and getrlimit() as wrapper functions that call prlimit().

EXAMPLES

The program below demonstrates the use of prlimit().

#define _GNU_SOURCE
#define _FILE_OFFSET_BITS 64
#include <err.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/resource.h>
#include <time.h>
int
main(int argc, char *argv[])
{
    pid_t          pid;
    struct rlimit  old, new;
    struct rlimit  *newp;
    if (!(argc == 2 || argc == 4)) {
        fprintf(stderr, "Usage: %s <pid> [<new-soft-limit> "
                "<new-hard-limit>]\n", argv[0]);
        exit(EXIT_FAILURE);
    }
    pid = atoi(argv[1]);        /* PID of target process */
    newp = NULL;
    if (argc == 4) {
        new.rlim_cur = atoi(argv[2]);
        new.rlim_max = atoi(argv[3]);
        newp = &new;
    }
    /* Set CPU time limit of target process; retrieve and display
       previous limit */
    if (prlimit(pid, RLIMIT_CPU, newp, &old) == -1)
        err(EXIT_FAILURE, "prlimit-1");
    printf("Previous limits: soft=%jd; hard=%jd\n",
           (intmax_t) old.rlim_cur, (intmax_t) old.rlim_max);
    /* Retrieve and display new CPU time limit */
    if (prlimit(pid, RLIMIT_CPU, NULL, &old) == -1)
        err(EXIT_FAILURE, "prlimit-2");
    printf("New limits: soft=%jd; hard=%jd\n",
           (intmax_t) old.rlim_cur, (intmax_t) old.rlim_max);
    exit(EXIT_SUCCESS);
}
