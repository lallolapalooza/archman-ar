NAME

systemd-fstab-generator - generate filesystem mount units for fstab entries

SYNOPSIS

systemd-fstab-generator

DESCRIPTION

On boot, systemd consults fstab(5) to discover local filesystems that should be mounted. systemd does not parse this file directly. Instead, it invokes systemd-fstab-generator, which translates the entries in fstab(5) into native systemd units, specifically mount units for local filesystems and automount units for automounted ones. These units are then loaded by the systemd system and service manager.

This generator is instantiated early during the boot process. It reads fstab(5) (looking in /etc/fstab, /etc/filesystems and other locations) and creates temporary units named local-fs@.service and automount.service. These units are then started to perform the mount operations.

The generator determines the unit names based on the mount point specified in the fstab entry. For example, an entry for /home results in a unit named local-fs-/home.service.

Entries in fstab(5) with the dump field set to non-zero and the pass field set to non-zero are treated as candidates for filesystem check ordering. The generator creates systemd-fsck@.service units for these, which are instantiated and started by local-fs-pre.target.

Entries with the pass field set to zero are not checked by fsck(8) and are mounted after local filesystems have been set up. Entries with the pass field set to non-zero are checked in the order determined by the generator and then mounted.

The generator supports the following fstab(5) fields:

pass: This field is used to determine the order in which filesystem checks are performed. A value of 0 means no check is performed. A value of 1 means the root filesystem is checked first. A value of 2 means other filesystems are checked after the root filesystem. All filesystems with a pass value of 2 are checked in parallel.

freq: This field is used by the dump utility to determine which filesystems to back up. A value of 0 means no backup is performed. Non-zero values indicate the frequency of backups. This field is not directly used by systemd but is passed through to the underlying mount and fsck utilities.

The generator recognizes various options in the sixth field of fstab(5):

  • noauto: If this option is specified, the filesystem will not be mounted automatically at boot time. It must be mounted manually using the mount command.
  • user: Allows any user to mount the filesystem.
  • owner: Allows the owner of the device node to mount the filesystem.
  • group: Allows any member of the group owning the device node to mount the filesystem.
  • rootcontext: Sets the security context for the root directory of the filesystem.
  • exec, noexec: Controls whether files on the filesystem can be executed.
  • nodev, dev: Controls whether device files on the filesystem are allowed.
  • suid, nosuid: Controls whether set-user-ID and set-group-ID bits are honored.
  • remount: Instructs the system to remount an already mounted filesystem with different options.
  • bind: Creates a bind mount, making a file or directory available at another location.
  • late: Mounts the filesystem after all other filesystems have been mounted.
  • comment=: Allows arbitrary comments to be added to the fstab entry.
  • x-systemd.*: These options provide finer-grained control over systemd's behavior. For example, x-systemd.automount can be used to enable automounting of a filesystem. x-systemd.mount-timeout= sets the timeout for mounting. x-systemd.requires=, x-systemd.after=, x-systemd.before= allow specifying dependencies between mount units. x-systemd.device-timeout= allows setting a timeout for device availability. x-systemd.idle-timeout= sets the timeout after which an automounted filesystem is unmounted.

If an fstab entry uses the UUID= or LABEL= syntax, systemd will use the corresponding filesystem attributes to identify the device.

For network filesystems (NFS, CIFS, etc.), systemd will attempt to start the necessary client services before attempting to mount them. Dependencies on network-online.target may be automatically added.

The generator also handles swap entries specified in fstab(5). These are translated into swap.service units and enabled to start at boot.

Added in version 258.

FileSystemSectorSize=

Controls the sector size for any file system, LUKS volume or Verity volume formatted on this partition. Expects a power of 2 as value, and must be equal or larger than 512. Typically it's recommended to set the file system sector size to 4096, even on 512 sector disks (and in particular for images that are only ever intended to be stored as file on disks), in order to optimize performance. However, for compatibility with foreign operating systems or firmware it might be advisable to use the native sector size of the backing disk.

If unspecified and operating on a block device, defaults to the native sector size of the device. If unspecified and operating on a disk image file defaults to 4096.

Regardless of what is configured here, or which default is picked, the file system sector size is always increased to be equal or larger than the disk sector size.

Added in version 258.

أمثلة

Example 1. Grow the root partition to the full disk size at first boot

With the following file the root partition is automatically grown to the full disk if possible during boot.

# /usr/lib/repart.d/50-root.conf
[Partition]
Type=root

Example 2. Create a swap and home partition automatically on boot, if missing

The home partition gets all available disk space while the swap partition gets 1G at most and 64M at least. We set a priority > 0 on the swap partition to ensure the swap partition is not used if not enough space is available. For every three bytes assigned to the home partition the swap partition gets assigned one.

# /usr/lib/repart.d/60-home.conf
[Partition]
Type=home
# /usr/lib/repart.d/70-swap.conf
[Partition]
Type=swap
SizeMinBytes=64M
SizeMaxBytes=1G
Priority=1
Weight=333

Example 3. Create B partitions in an A/B Verity setup, if missing

Let's say the vendor intends to update OS images in an A/B setup, i.e. with two root partitions (and two matching Verity partitions) that shall be used alternatingly during upgrades. To minimize image sizes the original image is shipped only with one root and one Verity partition (the "A" set), and the second root and Verity partitions (the "B" set) shall be created on first boot on the free space on the medium.

# /usr/lib/repart.d/50-root.conf
[Partition]
Type=root
SizeMinBytes=512M
SizeMaxBytes=512M
# /usr/lib/repart.d/60-root-verity.conf
[Partition]
Type=root-verity
SizeMinBytes=64M
SizeMaxBytes=64M

The definitions above cover the "A" set of root partition (of a fixed 512M size) and Verity partition for the root partition (of a fixed 64M size). Let's use symlinks to create the "B" set of partitions, since after all they shall have the same properties and sizes as the "A" set.

# ln -s 50-root.conf /usr/lib/repart.d/70-root-b.conf
# ln -s 60-root-verity.conf /usr/lib/repart.d/80-root-verity-b.conf

Example 4. Create a data partition and corresponding verity partitions from a OS tree

Assuming we have an OS tree at /var/tmp/os-tree that we want to package in a root partition together with matching verity partitions, we can do so as follows:

# 50-root.conf
[Partition]
Type=root
CopyFiles=/var/tmp/os-tree
Verity=data
VerityMatchKey=root
Minimize=guess
# 60-root-verity.conf
[Partition]
Type=root-verity
Verity=hash
VerityMatchKey=root
# Explicitly set the hash and data block size to 4K
VerityDataBlockSizeBytes=4096
VerityHashBlockSizeBytes=4096
Minimize=best
# 70-root-verity-sig.conf
[Partition]
Type=root-verity-sig
Verity=signature
VerityMatchKey=root

NAME

repart.d.5 — تعريف قسم أدوات النظام

SYNOPSIS

. Bin file /etc/systemd/system/repart.d/*.conf

. Bor in file /usr/lib/systemd/system/repart.d/*.conf

DESCRIPTION

ملفات *.conf في /etc/systemd/system/repart.d/ و /usr/lib/systemd/system/repart.d/ قد تصف أقسامًا جديدة لإنشاء القرص. وهي صالحة فقط إذا تم استخدامها مع yptenroll(1).

يتم تحليل هذه الملفات بترتيب أبجدي. إذا كان هناك قسم يحتوي على نفس الاسم، فإن القسم الأخير فقط هو الذي سيتم استخدامه.

عادةً، يجب وضع ملفات التكوين المخصصة في /etc/systemd/system/repart.d/. لا ينبغي تعديل الملفات الموجودة في /usr/lib/systemd/system/repart.d/ مباشرة. بدلاً من ذلك، ينبغي وضعها في /etc/systemd/system/repart.d/ كـ overrides.

يتم تقسيم كل ملف تكوين إلى أقسام.

[PARTITION] SECTION OPTIONS

يحتوي كل قسم على خيارات التكوين التالية:

Name=
السلسلة المطلوب إنشاؤها. قد تحتوي على اسم قسم الأدوات أو اسم قسم الأدوات المحدد.
PartitionScheme=
السلسلة التي تحدد مخطط الأقسام. راجع systemd.exec(5) لـ [PARTITION] SECTION OPTIONS.
Type=
معرف النوع. يمكن أن يكون UUID أو PARTLABEL أو PARTUUID. يتطلب قيمة.
Size=
يحدد حجم القسم. يمكن أن يكون قيمة مطلقة (بالبايت) أو قيمة نسبية. راجع systemd.exec(5) لـ [PARTITION] SECTION OPTIONS.
Offset=
يحدد موقع بدء القسم. راجع systemd.exec(5) لـ [PARTITION] SECTION OPTIONS.
Priority=
يحدد أولوية القسم. راجع systemd.exec(5) لـ [PARTITION] SECTION OPTIONS.

SPECIFIERS

يمكن استخدام المواصفات التالية في بعض الخيارات:

Device=
اسم الجهاز الذي سيتم استخدامه لإنشاء قسم جديد.
Size=
يحدد حجم القسم.
Offset=
يحدد موقع بدء القسم.
Type=
معرف النوع.
PartitionScheme=
يحدد مخطط الأقسام.
Priority=
يحدد أولوية القسم.

ENVIRONMENT

يتم تمرير متغيرات البيئة التالية إلى أدوات الإنشاء:

PARTMAN_DEVICE
اسم الجهاز الذي سيتم استخدامه.

EXAMPLES

إنشاء قسم الأدوات بسم بحجم 512 ميجابايت.

[Partition]
Name=ESP
PartitionScheme=gpt
Type=efi
Size=512M

إنشاء قسم جذر بحجم 20 جيجابايت.

[Partition]
Name=root
Type=ext4
Size=20G
