rename(2) دليل استدعاءات النظام rename(2)

الاسم

rename, renameat, renameat2 - تغيير اسم أو موقع ملف

المكتبة

مكتبة C القياسية (libc, -lc)

الملخص

#include <stdio.h>
int rename(const char *oldpath, const char *newpath);
#include <fcntl.h>           /* تعريف ثوابت AT_* */
#include <stdio.h>
int renameat(int olddirfd, const char *oldpath,
             int newdirfd, const char *newpath);
int renameat2(int olddirfd, const char *oldpath,
             int newdirfd, const char *newpath, unsigned int flags);

الوصف

يقوم rename() بإعادة تسمية ملف، نقله بين الدلائل إذا لزم الأمر. أي روابط صلبة أخرى للملف (كما تم إنشاؤها باستخدام link(2)) لا تتأثر. واصفات الملفات المفتوحة لـ oldpath لا تتأثر أيضًا.

تحدد قيود مختلفة ما إذا كانت عملية إعادة التسمية تنجح أم لا: انظر الأخطاء أدناه.

إذا كان newpath موجودًا بالفعل، فسيتم استبداله بشكل ذري، بحيث لا توجد نقطة سيجد فيها عملية أخرى تحاول الوصول إلى newpath أنها مفقودة. ومع ذلك، قد تكون هناك نافذة تشير فيها كل من oldpath و newpath إلى الملف الذي يتم إعادة تسميته.

إذا كان oldpath و newpath عبارة عن روابط صلبة موجودة تشير إلى نفس الملف، فإن rename() لا تفعل شيئًا، وتعيد حالة نجاح.

إذا كان newpath موجودًا ولكن فشلت العملية لسبب ما، فإن rename() تضمن ترك نسخة من newpath في مكانها.

يمكن لـ oldpath تحديد دليل. في هذه الحالة، يجب أن يكون newpath إما غير موجود، أو يجب أن يحدد دليلًا فارغًا.

إذا أشارت oldpath إلى رابط رمزي، يتم إعادة تسمية الرابط؛ إذا أشارت newpath إلى رابط رمزي، فسيتم استبدال الرابط.

renameat()

يعمل استدعاء النظام renameat() بنفس الطريقة تمامًا مثل rename()، باستثناء الاختلافات الموضحة هنا.

إذا كان المسار المحدد في oldpath نسبيًا، فسيتم تفسيره نسبيًا إلى الدليل المشار إليه بواسطة واصف الملف olddirfd (بدلاً من كونه نسبيًا إلى دليل العمل الحالي للعملية المستدعية، كما يتم فعله بواسطة rename() لمسار نسبي).

إذا كان oldpath نسبيًا وكان olddirfd هو القيمة الخاصة AT_FDCWD، فسيتم تفسير oldpath نسبيًا إلى دليل العمل الحالي للعملية المستدعية (مثل rename()).

إذا كان oldpath مطلقًا، فسيتم تجاهل olddirfd.

تفسير newpath هو كما هو الحال بالنسبة لـ oldpath، باستثناء أن المسار النسبي سيتم تفسيره نسبيًا إلى الدليل المشار إليه بواسطة واصف الملف newdirfd.

انظر openat(2) لشرح الحاجة إلى renameat().

renameat2()

يحتوي renameat2() على وسيطة flags إضافية. يعد استدعاء renameat2() بوسيطة flags صفرية مكافئًا لـ renameat().

الوسيطة flags عبارة عن قناع بت يتكون من صفر أو أكثر من الرايات التالية:

RENAME_EXCHANGE
تبادل oldpath و newpath بشكل ذري. يجب أن يكون كلا المسارين موجودين ولكن قد يكونان من أنواع مختلفة (على سبيل المثال، أحدهما يمكن أن يكون دليلًا غير فارغ والآخر رابطًا رمزيًا).
RENAME_NOREPLACE
لا تستبدل newpath عند إعادة التسمية. أعد خطأ إذا كان newpath موجودًا بالفعل.
لا يمكن استخدام RENAME_NOREPLACE مع RENAME_EXCHANGE.
تتطلب RENAME_NOREPLACE دعمًا من نظام الملفات الأساسي. تمت إضافة الدعم لأنظمة الملفات المختلفة على النحو التالي:
•
ext4 (Linux 3.15)؛
•
btrfs, tmpfs, و cifs (Linux 3.17)؛
•
xfs (Linux 4.0)؛
•
تمت إضافة دعم للعديد من أنظمة الملفات الأخرى في Linux 4.9، بما في ذلك ext2, minix, reiserfs, jfs, vfat, و bpf.
RENAME_WHITEOUT (منذ Linux 3.18)
هذه العملية ذات مغزى فقط لتطبيقات أنظمة الملفات المتراكبة/الاتحاد.
يؤدي تحديد RENAME_WHITEOUT إلى إنشاء كائن "whiteout" في مصدر إعادة التسمية في نفس الوقت الذي يتم فيه إجراء إعادة التسمية. العملية برمتها ذرية، بحيث إذا نجحت إعادة التسمية، فسيتم أيضًا إنشاء whiteout.
يعتبر "whiteout" كائنًا له معنى خاص في هياكل أنظمة الملفات union/overlay. في هذه الهياكل، توجد طبقات متعددة ولا يتم تعديل سوى الطبقة العليا. سيؤدي whiteout في طبقة عليا إلى إخفاء ملف مطابق في الطبقة السفلية فعليًا، مما يجعل الأمر يبدو وكأن الملف غير موجود.
عند إعادة تسمية ملف موجود في الطبقة السفلية، يتم نسخ الملف أولاً (إذا لم يكن موجودًا بالفعل في الطبقة العليا) ثم إعادة تسميته في الطبقة العليا، القابلة للقراءة والكتابة. في نفس الوقت، يجب "whiteout" للملف المصدر (بحيث يصبح الإصدار من الملف المصدر في الطبقة السفلية غير مرئي). يجب إجراء العملية بأكملها بشكل ذري.
عند عدم التضمين في اتحاد/تراكب، يظهر whiteout كجهاز حرفي برقم جهاز {0,0}. (لاحظ أن تطبيقات union/overlay الأخرى قد تستخدم طرقًا مختلفة لتخزين إدخالات whiteout؛ على وجه التحديد، يستخدم union mount الخاص بـ BSD نوع inode منفصل، DT_WHT، والذي، على الرغم من دعمه من قبل بعض أنظمة الملفات المتاحة في Linux، مثل CODA و XFS، يتم تجاهله بواسطة رمز دعم whiteout الخاص بالنواة، اعتبارًا من Linux 4.19، على الأقل.)
تتطلب RENAME_WHITEOUT نفس الامتيازات مثل إنشاء عقدة جهاز (أي القدرة CAP_MKNOD).
لا يمكن استخدام RENAME_WHITEOUT مع RENAME_EXCHANGE.
تتطلب RENAME_WHITEOUT دعمًا من نظام الملفات الأساسي. من بين أنظمة الملفات التي تدعمها tmpfs (منذ Linux 3.18)، ext4 (منذ Linux 3.18)، XFS (منذ Linux 4.1)، f2fs (منذ Linux 4.2)، btrfs (منذ Linux 4.7)، و ubifs (منذ Linux 4.9).

قيمة الإرجاع

عند النجاح، يتم إرجاع الصفر. عند الخطأ، يتم إرجاع -1، ويتم تعيين errno للإشارة إلى الخطأ.

الأخطاء

EACCES
يُرفض إذن الكتابة للدليل الذي يحتوي على oldpath أو newpath، أو يُرفض إذن البحث لأحد الأدلة في بادئة المسار لـ oldpath أو newpath، أو oldpath هو دليل ولا يسمح بإذن الكتابة (مطلوب لتحديث إدخال ..). (انظر أيضًا path_resolution(7)).
EBUSY
تفشل عملية إعادة التسمية لأن oldpath أو newpath هو دليل قيد الاستخدام بواسطة عملية ما (ربما كدليل عمل حالي، أو كدليل جذر، أو لأنه تم فتحه للقراءة) أو قيد الاستخدام بواسطة النظام (على سبيل المثال كنقطة تحميل)، بينما يعتبر النظام هذا خطأ. (لاحظ أنه لا يوجد شرط لإرجاع EBUSY في مثل هذه الحالات — لا يوجد خطأ في إجراء إعادة التسمية على أي حال — ولكن يُسمح بإرجاع EBUSY إذا لم يتمكن النظام من التعامل مع مثل هذه المواقف بطريقة أخرى.)
EDQUOT
حصص الاقتباس للمستخدم من نظام الملفات المحدد قد تم تجاوزها.

ENOENT
\n
The link named by oldpath does not exist; or, a directory component\n in newpath does not exist; or, oldpath or newpath is\n an empty string.
\n
ENOMEM
\n
Insufficient kernel memory was available.
\n
ENOSPC
\n
The device containing the file has no room for the new directory\n entry.
\n
ENOTDIR
\n
A component used as a directory in oldpath or newpath is\n not, in fact, a directory. Or, oldpath is a directory, and\n newpath exists but is not a directory.
\n
ENOTEMPTY or\n EEXIST
\n
newpath is a nonempty directory, that is, contains entries other\n than \".\" and \"..\".
\n
EPERM or\n EACCES
\n
The directory containing oldpath has the sticky bit\n (S_ISVTX) set and the process's effective user ID is neither the\n user ID of the file to be deleted nor that of the directory containing it,\n and the process is not privileged (Linux: does not have the\n CAP_FOWNER capability); or newpath is an existing file and\n the directory containing it has the sticky bit set and the process's\n effective user ID is neither the user ID of the file to be replaced nor\n that of the directory containing it, and the process is not privileged\n (Linux: does not have the CAP_FOWNER capability); or the filesystem\n containing oldpath does not support renaming of the type\n requested.
\n
EROFS
\n
The file is on a read-only filesystem.
\n
EXDEV
\n
oldpath and newpath are not on the same mounted filesystem.\n (Linux permits a filesystem to be mounted at multiple points, but\n rename() does not work across different mount points, even if the\n same filesystem is mounted on both.)
\n

ENOTDIR

glibc notes

\n

On older kernels where renameat() is unavailable, the glibc\n wrapper function falls back to the use of rename(). When\n oldpath and newpath are relative pathnames, glibc constructs\n pathnames based on the symbolic links in /proc/self/fd that\n correspond to the olddirfd and newdirfd arguments.

BUGS

\n

On NFS filesystems, you can not assume that if the operation\n failed, the file was not renamed. If the server does the rename operation\n and then crashes, the retransmitted RPC which will be processed when the\n server is up again causes a failure. The application is expected to deal\n with this. See link(2) for a similar problem.
