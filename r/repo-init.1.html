الحزمة: repo

التراخيص: Apache-2.0

NAME

repo-init - Initialize a local repository directory

SYNOPSIS

repo init [-h | --help] [-m manifest.xml] [-u URL] [-b BRANCH] [--standalone-manifest] [--reference=DIRECTORY] [--dissociate] [--no-clone-bundle] [-g | --groups=GROUPS] [-b | --manifest-branch=BRANCH] [--depth=DEPTH] [--no-repo-verify] [-q | --quiet] [-v | --verbose]

DESCRIPTION

Initializes the local repository. This involves creating the .repo directory and downloading the manifest file that specifies the Git repositories that make up the project. repo init will ask you where you want to start and how you want to start.

The repo init command requires you to specify the URL of the manifest repository. This is usually done with the -u option.

The manifest defines the project structure and the Git repositories that comprise the project. It also defines the branches of Git repositories that should be checked out. Typically, a project will have a default branch which repo init will check out by default.

For projects that use Git, you can specify a particular manifest branch to use with the -b option. If you do not specify a branch, the default branch specified in the manifest repository will be used.

The repository directory will be created as a Git repository itself. It will be populated with the files and directories specified in the manifest. The manifest itself will be downloaded into the .repo/manifests directory.

The manifest file is a special XML file that describes the Git repositories that make up the Android source code. It specifies the location of each repository, the branch to check out, and the local directory where each repository should be placed.

By default, repo init will create a repository directory named manifest in the current directory. This can be changed by specifying a different directory name at the end of the command.

The -g option can be used to specify which groups of projects should be downloaded. This is useful for projects that have many optional components or features that you may not need.

The --depth option can be used to create a shallow clone of the Git repository. This will reduce the size of the repository and speed up the initial clone. However, it will also limit the history that is available in the repository.

The --no-repo-verify option can be used to disable the verification of the repo client signature. This is generally not recommended, but may be necessary in some environments.

The --quiet and --verbose options can be used to control the amount of output that is displayed by repo init.

OPTIONS

-h, --help
Show the help message and exit.
-m manifest.xml
Specify an alternate manifest to be used. If no manifest is specified, the default manifest (default.xml) will be used.
-u URL
Specify the URL of the manifest repository. This is a required option.
-b BRANCH
Specify the branch of the manifest repository to use. If not specified, the default branch will be used.
-g, --groups=GROUPS
Specify the groups of projects to download. This is a comma-separated list of group names.
--standalone-manifest
Download the manifest directly from the specified --manifest-url as a static file. This will not set up a manifest Git checkout. The manifest will be fully static and will not be re-downloaded during subsequent repo init and repo sync calls.
--reference=DIRECTORY
Point to a directory that has the content of a --mirror sync. This will make the working directory use as much data as possible from the local reference directory when fetching from the server. This will make the sync go a lot faster by reducing data traffic on the network.
--dissociate
Borrow the objects from the directory specified with the --reference option only to reduce network transfer, and stop borrowing from them after a first clone is made by making necessary local copies of borrowed objects.
--no-clone-bundle
Disables any attempt to use $URL/clone.bundle to bootstrap a new Git repository from a resumeable bundle file on a content delivery network. This may be necessary if there are problems with the local Python HTTP client or proxy configuration, but the Git binary works.
--depth=DEPTH
Create a shallow clone of the Git repository with the specified depth. This will reduce the size of the repository and speed up the initial clone. However, it will also limit the history that is available in the repository.
--no-repo-verify
Disable the verification of the repo client signature. This is generally not recommended, but may be necessary in some environments.
-q, --quiet
Output less information.
-v, --verbose
Output more information.

DETAILS

The optional -m argument can be used to specify an alternate manifest to be used. If no manifest is specified, the manifest default.xml will be used.

If the --standalone-manifest argument is set, the manifest will be downloaded directly from the specified --manifest-url as a static file (rather than setting up a manifest git checkout). With --standalone-manifest, the manifest will be fully static and will not be re-downloaded during subsesquent `repo init` and `repo sync` calls.

The --reference option can be used to point to a directory that has the content of a --mirror sync. This will make the working directory use as much data as possible from the local reference directory when fetching from the server. This will make the sync go a lot faster by reducing data traffic on the network.

The --dissociate option can be used to borrow the objects from the directory specified with the --reference option only to reduce network transfer, and stop borrowing from them after a first clone is made by making necessary local copies of borrowed objects.

The --no-clone-bundle option disables any attempt to use $URL/clone.bundle to bootstrap a new Git repository from a resumeable bundle file on a content delivery network. This may be necessary if there are problems with the local Python HTTP client or proxy configuration, but the Git binary works.

Switching Manifest Branches

To switch to another manifest branch, `repo init -b otherbranch` may be used in an existing client. However, as this only updates the manifest, a subsequent `repo sync` (or `repo sync -d`) is necessary to update the working directory files.
