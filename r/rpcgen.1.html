rpcgen(1) دليل الأوامر العامة rpcgen(1)

الاسم

rpcgen - مترجم بروتوكول RPC

ملخص

rpcgen ملف_الإدخال
rpcgen [-Dاسم[=قيمة]] [-T] [-K ثواني] ملف_الإدخال
rpcgen -c|-h|-l|-m|-M|-t [-o ملف_الإخراج ] ملف_الإدخال
rpcgen -I -s نوع_الشبكة [-o ملف_الإخراج] ملف_الإدخال
rpcgen -n معرف_الشبكة [-o ملف_الإخراج] ملف_الإدخال

الوصف

rpcgen هي أداة تولد كود C لتنفيذ بروتوكول RPC. المدخلات لـ rpcgen هي لغة تشبه C تُعرف بلغة RPC (لغة استدعاء الإجراءات عن بعد).

rpcgen تستخدم عادة كما في الملخص الأول حيث تأخذ ملف مدخلات وتولد ما يصل إلى أربعة ملفات إخراج. إذا كان ملف الإدخال اسمه proto.x، فإن rpcgen ستولد ملف رأس في proto.h، وروتينات XDR في proto_xdr.c، وأجزاء جانب الخادم في proto_svc.c، وأجزاء جانب العميل في proto_clnt.c. مع الخيار -T، ستولد أيضًا جدول إرسال RPC في proto_tbl.i. مع الخيار -Sc، ستولد أيضًا كود عينة يوضح كيفية استخدام الإجراءات عن بعد على جانب العميل. سيتم إنشاء هذا الكود في proto_client.c. مع الخيار -Ss، ستولد أيضًا كود خادم عينة يوضح كيفية كتابة الإجراءات عن بعد. سيتم إنشاء هذا الكود في proto_server.c.

الخادم الذي تم إنشاؤه يمكن تشغيله بواسطة مراقبي المنافذ (على سبيل المثال، inetd أو listen) أو بنفسه. عندما يتم تشغيله بواسطة مراقب منفذ، فإنه ينشئ خوادم فقط للنقل الذي تم تمرير واصف الملف 0 له. يجب تحديد اسم النقل عن طريق تعيين المتغير البيئي PM_TRANSPORT. عندما يتم تشغيل الخادم الذي تم إنشاؤه بواسطة rpcgen، فإنه ينشئ مقابض خادم لجميع عمليات النقل المحددة في متغير البيئة NETPATH، أو إذا كان غير معين، فإنه ينشئ مقابض خادم لجميع عمليات النقل المرئية من الملف /etc/netconfig. ملاحظة: يتم اختيار عمليات النقل في وقت التشغيل وليس في وقت الترجمة.

عند البناء لمراقب منفذ (rpcgen -I)، وعندما يتم تشغيل الخادم ذاتيًا، فإنه يعمل في الخلفية افتراضيًا. يمكن استخدام رمز تعريف خاص RPC_SVC_FG لتشغيل عملية الخادم في المقدمة.

الملخص الثاني يوفر ميزات خاصة تسمح بإنشاء خوادم RPC أكثر تطوراً. تتضمن هذه الميزات الدعم لـ #defines المقدمة من المستخدم وجداول إرسال RPC. تحتوي الإدخالات في جدول إرسال RPC على:

•
مؤشرات إلى روتين الخدمة المقابل لهذا الإجراء،
•
مؤشر إلى وسائط الإدخال والإخراج
•
حجم هذه الروتينات
يمكن للخادم استخدام جدول الإرسال للتحقق من المصادقة ثم تنفيذ روتين الخدمة؛ يمكن لمكتبة العميل استخدامها للتعامل مع تفاصيل إدارة التخزين وتحويل بيانات XDR.

الملخصات الثلاثة الأخرى الموضحة أعلاه تستخدم عندما لا يرغب المرء في إنشاء جميع ملفات الإخراج، بل ملف واحد فقط. يتم وصف أمثلة على استخدامها في قسم EXAMPLE أدناه. عندما يتم تنفيذ rpcgen بالخيار -s، فإنه ينشئ خوادم لفئة معينة من عمليات النقل. عند التنفيذ بالخيار -n، فإنه ينشئ خادمًا لعملية النقل المحددة بواسطة معرف_الشبكة. إذا لم يتم تحديد ملف_الإدخال، فإن rpcgen يقبل المدخل القياسي.

يتم تشغيل معالج C المسبق، cc -E [انظر cc(1)]، على ملف الإدخال قبل تفسيره فعليًا بواسطة rpcgen. لكل نوع من ملفات الإخراج، تعرف rpcgen رمز معالج مسبق خاص ليستخدمه مبرمج rpcgen:

RPC_HDR
معرف عند الترجمة إلى ملفات رأس
RPC_XDR
معرف عند الترجمة إلى روتينات XDR
RPC_SVC
معرف عند الترجمة إلى أجزاء جانب الخادم
RPC_CLNT
معرف عند الترجمة إلى أجزاء جانب العميل
RPC_TBL
معرف عند الترجمة إلى جداول إرسال RPC

أي سطر يبدأ بـ `%' يتم تمريره مباشرة إلى ملف الإخراج، دون تفسير بواسطة rpcgen.

لكل نوع بيانات مشار إليه في ملف_الإدخال، تفترض rpcgen وجود روتين مع السلسلة xdr_ مسبوقة باسم نوع البيانات. إذا لم يكن هذا الروتين موجودًا في مكتبة RPC/XDR، فيجب توفيره. توفير نوع بيانات غير معرف يسمح بتخصيص روتينات XDR.

الخيارات التالية متاحة:

-a
توليد جميع الملفات بما في ذلك الكود العينة لجانبي العميل والخادم.
-b
هذا يولد كودًا لنظام rpc من نوع SunOS4.1. إنه للتوافق مع الإصدارات السابقة. هذا هو الافتراضي.
-5
هذا يولد كودًا لنظام rpc من نوع SysVr4. يتم استخدامه بواسطة Transport Independent RPC الموجود في أنظمة Svr4. افتراضيًا، يولد rpcgen كودًا لنظام rpc من نوع SunOS4.1.
-c
الترجمة إلى روتينات XDR.
-C
توليد الكود بـ ANSI C. هذا الخيار يولد أيضًا كودًا يمكن ترجمته باستخدام مترجم C++. هذا هو الافتراضي.
-k
توليد الكود بـ K&R C. الافتراضي هو ANSI C.
-Dاسم[=قيمة]
تعريف رمز اسم. يعادل توجيه #define في المصدر. إذا لم يتم إعطاء قيمة، فإن القيمة معرفة كـ 1. يمكن تحديد هذا الخيار أكثر من مرة.
-h
الترجمة إلى تعريفات بيانات C (ملف رأس). يمكن استخدام الخيار -T بالاشتراك لإنتاج ملف رأس يدعم جداول إرسال RPC.
-I
توليد خدمة يمكن تشغيلها من inetd. الافتراضي هو توليد خدمة ثابتة تتعامل مع عمليات النقل المحددة باستخدام -s. استخدام -I يسمح بتشغيل خدمة بأي من الطريقتين.
-K ثواني
افتراضيًا، تنتظر الخدمات التي تم إنشاؤها باستخدام rpcgen 120 ثانية بعد معالجة طلب قبل الخروج. يمكن تغيير تلك الفترة باستخدام العلم -K. لإنشاء خادم يخرج فورًا بعد معالجة طلب، يمكن استخدام -K 0. لإنشاء خادم لا يخرج أبدًا، الوسيط المناسب هو -K -1.
عند المراقبة لخادم، بعض مراقبي المنافذ، مثل listen(1M)، ينشئون عملية جديدة دائمًا استجابة لطلب خدمة. إذا كان معروفًا أن خادمًا سيتم استخدامه مع مراقب كهذا، فيجب أن يخرج الخادم فورًا عند الانتهاء. لمثل هذه الخوادم، يجب استخدام rpcgen مع -K -1.
-l
الترجمة إلى أجزاء جانب العميل.
-m
الترجمة إلى أجزاء جانب الخادم، ولكن لا تولد روتين "main". هذا الخيار مفيد لروتينات الاستدعاء الخلفي وللمستخدمين الذين يحتاجون إلى كتابة روتين "main" الخاص بهم للقيام بالتهيئة.
-M
توليد أجزاء آمنة للخيوط المتعددة لتمرير الوسائط والنتائج بين الكود الذي تم إنشاؤه بواسطة rpcgen والكود المكتوب بواسطة المستخدم. هذا الخيار مفيد للمستخدمين الذين يرغبون في استخدام الخيوط في الكود الخاص بهم.

NAME

rpcgen — an rpc protocol compiler

SYNOPSIS

rpcgen [ -bcdfgklmsStvV ] [ -a | -A ] [ -C | -c ] [ -D name[=value] ] [ -I arg ] [ -O file ] [ -P file ] [ -X file ] [ -N file ] [ -o outfile ] [ -T | -t ] [ -i infile ] [ -n netid | -s nettype ] [ -m | -M ] [ -e ] [ -p file ] [ -w ] [ -W ] [ -x ] [ -y file ] [ -Z file ] [ infile

DESCRIPTION

The rpcgen utility is a compiler that takes an RPC Protocol definition file, described in the rpc(5) manual page, and generates C code suitable for use with the RPC library routines.

The rpcgen utility can generate the following types of files:

-c
Generate C function and structure definitions.
-C
Generate C function and structure definitions compatible with the ANSI C compiler.
-d
Generate default code.
-f
Generate client-side remote procedure call code.
-g
Generate both client and server side code.
-h
Generate C declarations (header file).
-i infile
Include the specified header file.
-k
Generate code for both client and server, allowing you to select which one to compile.
-l
Generate client-side stubs.
-m
Generate server-side stubs allowing you to specify the makefile.
-M
Generate server-side stubs allowing you to specify the makefile and allowing you to specify multiple transports.
-n netid
Compile into server-side stubs for the transport specified by netid. There should be an entry for netid in the netconfig database. This option may be specified more than once, so as to compile a server that serves multiple transports.
-N
Use the newstyle of rpcgen. This allows procedures to have multiple arguments. It also uses the style of parameter passing that closely resembles C. So, when passing an argument to a remote procedure you do not have to pass a pointer to the argument but the argument itself. This behaviour is different from the oldstyle of rpcgen generated code. The newstyle is not the default case because of backward compatibility.
-o outfile
Specify the name of the output file. If none is specified, standard output is used (-c, -h, -l, -m, -n, -s, -Sc, -Sm, -Ss, and -t modes only).
-s nettype
Compile into server-side stubs for all the transports belonging to the class nettype. The supported classes are netpath, visible, circuit_n, circuit_v, datagram_n, datagram_v, tcp, and udp [see rpc(3N) for the meanings associated with these classes]. This option may be specified more than once. Note: the transports are chosen at run time and not at compile time.
-Sc
Generate sample code to show the use of remote procedure and how to bind to the server before calling the client side stubs generated by rpcgen.
-Sm
Generate a sample Makefile which can be used for compiling the application.
-Ss
Generate skeleton code for the remote procedures on the server side. You would need to fill in the actual code for the remote procedures.
-t
Compile into RPC dispatch table.
-T
Generate the code to support RPC dispatch tables.

The options -c, -h, -l, -m, -s and -t are used exclusively to generate a particular type of file, while the options -D and -T are global and can be used with the other options.

NOTES

The RPC Language does not support nesting of structures. As a work-around, structures can be declared at the top-level, and their name used inside other structures in order to achieve the same effect.

Name clashes can occur when using program definitions, since the apparent scoping does not really apply. Most of these can be avoided by giving unique names for programs, versions, procedures and types.

The server code generated with -n option refers to the transport indicated by netid and hence is very site specific.

EXAMPLE

The following example:

$ rpcgen -T prot.x

generates the five files: prot.h, prot_clnt.c, prot_svc.c, prot_xdr.c and prot_tbl.i.

The following example sends the C data-definitions (header file) to the standard output.

$ rpcgen -h prot.x

To send the test version of the -DTEST, server side stubs for all the transport belonging to the class datagram_n to standard output, use:

$ rpcgen -s datagram_n -DTEST prot.x

To create the server side stubs for the transport indicated by netid tcp, use:

$ rpcgen -n tcp -o prot_svc.c prot.x
