التعبيرات العادية

يستخدم re2js الصيغة التالية للتعبيرات العادية:

"foo"
حرفي سلسلة نصية حساس لحالة الأحرف.
'foo'
حرفي سلسلة نصية غير حساس لحالة الأحرف.
[a-xyz], [^a-xyz]
فئة أحرف (ربما معكوسة).
.
أي حرف باستثناء سطر جديد.
R \ S
الفرق بين فئتي الأحرف R و S.
R*
صفر أو أكثر من تكرارات R.
R+
واحد أو أكثر من تكرارات R.
R?
R اختياري.
R{n}
تكرار R بالضبط n مرات.
R{n,}
تكرار R على الأقل n مرات.
R{n,m}
تكرار R من n إلى m مرة.
(R)
فقط R؛ تُستخدم الأقواس لتجاوز الأسبقية. إذا تم تمكين استخراج المطابقة الفرعية، فإن (R) هي مجموعة التقاط أو مجموعة غير التقاط اعتمادًا على الخيار --invert-captures.
(!R)
إذا تم تمكين استخراج المطابقة الفرعية، فإن (!R) هي مجموعة غير التقاط أو مجموعة التقاط اعتمادًا على الخيار --invert-captures.
R S
تسلسل: R متبوعًا بـ S.
R | S
بديل: R أو S.
R / S
تطلع أمامي: R متبوعًا بـ S، ولكن لم يتم استهلاك S.
name
تعبير عادي معرف باسم name (أو حرفي سلسلة نصية "name" في وضع توافق Flex).
{name}
تعبير عادي معرف باسم name في وضع توافق Flex.
@stag
علامة s: تحفظ آخر موضع إدخال تطابقت فيه @stag في متغير يسمى stag.
#mtag
علامة m: تحفظ جميع مواضع الإدخال التي تطابقت فيها #mtag في متغير يسمى mtag.

قد تحتوي فئات الأحرف وحروف السلاسل النصية على تسلسلات الهروب التالية: \a، \b، \f، \n، \r، \t، \v، \\، تسلسلات ثمانية \ooo وتسلسلات ست عشرية \xhh، \uhhhh و \Uhhhhhhhh.

الإجراءات

هذه قائمة بالإجراءات المعرفة مسبقًا التي يدعمها re2js:

!entry code
يربط إجراء الدخول كتلة معرفة من قبل المستخدم من code بحالة البداية لآلة الحالة المحدودة الحالية. إذا تم استخدام شروط البداية، يمكن تعيين إجراء الدخول بشكل فردي لكل شرط. يمكن استخدام هذا الإجراء لإجراء تهيئة، على سبيل المثال لحفظ موقع بداية رمز.
!pre_rule code
يسبق إجراء ما قبل القاعدة كتلة معرفة من قبل المستخدم من code بإجراءات دلالية لجميع القواعد في الكتلة الحالية (أو الشرط، إذا تم استخدام شروط البداية). يمكن استخدام هذا الإجراء لعزل الجزء المشترك من جميع الإجراءات الدلالية (مثل حفظ موقع نهاية رمز).
!post_rule code
يُلحق إجراء ما بعد القاعدة كتلة معرفة من قبل المستخدم من code بإجراءات دلالية لجميع القواعد في الكتلة الحالية (أو الشرط، إذا تم استخدام شروط البداية). يمكن استخدام هذا الإجراء لإصدار عبارات فخ تمنع تدفق التحكم غير المقصود.

التوجيهات

هذه قائمة كاملة بالتوجيهات التي يدعمها re2js:

!use:name ;
توجيه استخدام داخل الكتلة يقوم بدمج كتلة قواعد معرفة مسبقًا بالاسم المحدد name في الكتلة الحالية. تتم إضافة التعريفات المسماة والتكوينات والقواعد الخاصة بالكتلة المشار إليها إلى القواعد الحالية. يتم حل التعارضات بين القواعد والتكوينات المتداخلة بالطريقة المعتادة: الأولوية للقاعدة الأولى، وتجاوز أحدث تكوين التكوينات السابقة. الاستثناء الوحيد هو القواعد الخاصة * و $ و <!> التي لها دائمًا تعريف محلي للكتلة له الأولوية. يمكن وضع توجيه استخدام في أي مكان داخل كتلة، ويُسمح بتوجيهات استخدام متعددة.
!include file ;
هذا التوجيه هو نفس كتلة include: يقوم بإدراج محتويات file حرفيًا في مكان التوجيه.

واجهة البرنامج

يتفاعل الكود المنشأ مع البرنامج الخارجي بمساعدة بدائيات، يشار إليها جماعيًا باسم API. تعتمد البدائيات اللازمة لبرنامج معين على عوامل متعددة، بما في ذلك تعقيد التعبيرات العادية، وتمثيل الإدخال، والتخزين المؤقت، واستخدام الميزات المختلفة. يجب تعريف جميع البدائيات اللازمة من قبل المستخدم في شكل وحدات ماكرو، أو دوال، أو متغيرات، أو أي شكل آخر مناسب يجعل الكود المنشأ صحيحًا نحويًا ودلاليًا. re2js لا يتحقق (ولا يستطيع) من التعريفات، لذا إذا كان هناك شيء مفقود أو تم تعريفه بشكل غير صحيح، فقد يكون للبرنامج المنشأ أخطاء في وقت الترجمة أو وقت التشغيل. يقدم هذا الدليل أمثلة على تعريفات API في الحالات الأكثر شيوعًا.

لدى re2js ثلاثة نكهات API تحدد المجموعة الأساسية من البدائيات التي يستخدمها البرنامج:

واجهة برمجة تطبيقات بسيطة API
هذه هي واجهة برمجة التطبيقات الافتراضية للواجهة الخلفية JavaScript. تتكون من البدائيات التالية: YYINPUT (الذي يجب تعريفه كسلسلة من وحدات الكود، على سبيل المثال سلسلة نصية) و YYCURSOR، YYMARKER، YYCTXMARKER، YYLIMIT (التي يجب تعريفها كفهارس في YYINPUT).
واجهة برمجة تطبيقات سجل API
واجهة برمجة تطبيقات السجل مفيدة في الحالات التي يجب فيها تخزين حالة المحلل في كائن. يتم تمكينها باستخدام الخيار --api record أو تكوين re2c:api = record. تتكون واجهة برمجة التطبيقات هذه من متغير yyrecord (يمكن تجاوز الاسم باستخدام re2c:yyrecord) والذي يجب تعريفه ككائن بخصائص yyinput، yycursor، yymarker، yyctxmarker، yylimit (فقط الحقول التي يستخدمها الكود المنشأ تحتاج إلى تعريف، ويمكن تكوين أسمائها).
واجهة برمجة تطبيقات عامة API
هذه هي واجهة برمجة التطبيقات الأكثر مرونة. يتم تمكينها باستخدام الخيار --api generic أو تكوين re2c:api = generic. تحتوي على بدائيات للعمليات العامة: YYPEEK، YYSKIP، YYBACKUP، YYBACKUPCTX، YYSTAGP، YYSTAGN، YYMTAGP، YYMTAGN، YYRESTORE، YYRESTORECTX، YYRESTORETAG، YYSHIFT، YYSHIFTSTAG، YYSHIFTMTAG، YYLESSTHAN.

هذه قائمة كاملة ببدائيات API التي قد يستخدمها الكود المنشأ للتفاعل مع البرنامج الخارجي.

YYCTYPE
نوع أحرف الإدخال (وحدات الكود). بالنسبة لتشفيرات ASCII و EBCDIC و UTF-8، يجب أن يكون عدد صحيح غير موقع بحجم بايت واحد. بالنسبة لـ UTF-16 أو UCS-2، يجب أن يكون عدد صحيح غير موقع بحجم بايتين. بالنسبة لـ UTF-32، يجب أن يكون عدد صحيح غير موقع بحجم 4 بايت.
YYCURSOR
قيمة يسارية تخزن موضع الإدخال الحالي (مؤشر أو إزاحة عدد صحيح في YYINPUT). مبدئيًا، يجب أن يشير YYCURSOR إلى حرف الإدخال الأول، ويتم تقدمه لاحقًا بواسطة الكود المنشأ. عندما تطابق قاعدة، يكون موضع YYCURSOR هو الموضع بعد آخر حرف مطابق.
YYLIMIT
قيمة يمينية تخزن نهاية موضع الإدخال (مؤشر أو إزاحة عدد صحيح في YYINPUT). مبدئيًا، يجب أن يشير YYLIMIT إلى الموضع بعد آخر حرف إدخال متاح. لا يتم تغييره بواسطة الكود المنشأ. يقارن المحلل YYCURSOR بـ YYLIMIT لتحديد ما إذا كانت هناك أحرف إدخال كافية متبقية.
YYMARKER
قيمة يسارية تخزن موضع آخر قاعدة مطابقة (مؤشر أو إزاحة عدد صحيح في YYINPUT). تُستخدم لاستعادة موضع YYCURSOR إذا فشلت المطابقة الأطول واحتاج المحلل إلى التراجع. لا يلزم تهيئة.
YYCTXMARKER
قيمة يسارية تخزن موضع السياق الخلفي (مؤشر أو إزاحة عدد صحيح في YYINPUT). لا يلزم تهيئة. YYCTXMARKER مطلوب فقط إذا تم استخدام عامل التشغيل التطلعي /.
YYFILL
بدائية API عامة مع متغير واحد len. يجب أن يوفر YYFILL على الأقل len حرف إدخال إضافي أو يفشل. إذا تم استخدام re2c:eof، فإن len هو دائمًا 1 ويجب على YYFILL دائمًا العودة إلى الدالة المستدعية؛ القيمة المرجعة صفر تشير إلى النجاح. إذا لم يتم استخدام re2c:eof، يتم تجاهل القيمة المرجعة لـ YYFILL ويجب ألا تعود عند الفشل. الحد الأقصى لقيمة len هو YYMAXFILL.

--api <simple | record | generic>
تحديد واجهة برمجة التطبيقات (API) التي يستخدمها الكود المولد للتفاعل مع التعليمات البرمجية المعرفة من قبل المستخدم. يجب استخدام الخيار simple في الحالات البسيطة عندما لا تكون هناك حاجة لإعادة تعبئة المخزن المؤقت وتخزين حالة المحلل اللغوي. يجب استخدام الخيار record عندما تحتاج حالة المحلل اللغوي إلى تخزينها في سجل (هيكل، فئة، إلخ). يجب استخدام الخيار generic في الحالات المعقدة عندما لا تكون واجهات برمجة التطبيقات الأخرى مرنة بما يكفي.
--bit-vectors -b
تحسين القفزات الشرطية باستخدام أقنعة البت. هذا الخيار يعني ضمنيًا --nested-ifs.
--captures, --leftmost-captures
تمكين استخراج المجموعات الفرعية مع مجموعات الالتقاط ذات التسليم الأقصى اليسرى. يتم جمع النتيجة في مصفوفة yybmatch بسعة 2 * YYMAXNMATCH، ويتم تعيين yynmatch لعدد المجموعات للقاعدة المطابقة.
--captvars, --leftmost-captvars
تمكين استخراج المجموعات الفرعية مع مجموعات الالتقاط ذات التسليم الأقصى اليسرى. يتم جمع النتيجة في متغيرات yytl<k>, yytr<k> للمجموعة الملتقطة ذات الترتيب k.
--case-insensitive
معاملة السلاسل المقتبسة بعلامة اقتباس فردية أو مزدوجة على أنها غير حساسة لحالة الأحرف.
--case-inverted
عكس معنى السلاسل المقتبسة بعلامة اقتباس فردية أو مزدوجة: معاملة السلاسل المقتبسة بعلامة اقتباس فردية على أنها حساسة لحالة الأحرف والسلاسل المقتبسة بعلامة اقتباس مزدوجة على أنها غير حساسة لحالة الأحرف.
--case-ranges
دمج الحالات المتتالية في عبارات switch في نطاق بالشكل low ... high. هذا التركيب هو امتداد للغة C/C++ مدعوم من قبل المترجمات مثل GCC و Clang و Tcc. الميزة الرئيسية مقارنة باستخدام حالات فردية هي توليد كود أصغر ووقت توليد أسرع، على الرغم من أنه بالنسبة لبعض المترجمات مثل Tcc، فإنه ينتج أيضًا حجم ثنائي أصغر.
--computed-gotos -g
تحسين القفزات الشرطية باستخدام امتداد "computed goto" غير قياسي (والذي يجب أن يكون مدعومًا من قبل المترجم). يقوم re2js بتوليد جداول القفز فقط في الحالات المعقدة التي تحتوي على الكثير من الفروع الشرطية. يمكن تكوين عتبة التعقيد باستخدام إعداد cgoto:threshold. يمكن تمكين الإزاحات النسبية باستخدام إعداد cgoto:relative. هذا الخيار يعني ضمنيًا --bit-vectors.
--computed-gotos-relative
مشابه لـ --computed-gotos ولكن مع توليد إزاحات نسبية لجداول القفز بدلاً من ذلك (والذي يجب أن يكون مدعومًا من قبل المترجم). هذا الخيار يعني ضمنيًا --computed-gotos.
--conditions --start-conditions -c
تمكين دعم "الشروط" الشبيهة بـ Flex: محللات لغوية متعددة مترابطة داخل كتلة واحدة. هذا بديل لتحديد كتل re2js مختلفة يدويًا متصلة باستخدام goto أو استدعاءات الوظائف.
--depfile FILE
كتابة معلومات التبعية إلى FILE في شكل قاعدة Makefile <output-file> : <input-file> [include-file ...]. هذا يسمح بتتبع تبعيات البناء في وجود كتل/توجيهات include، بحيث يؤدي تحديث ملفات التضمين إلى إعادة توليد الملف الناتج. يعتمد هذا الخيار على خيار --output.
--ebcdic --ecb -e
توليد محلل لغوي يقرأ الإدخال بتشفير EBCDIC. يفترض re2js أن نطاق الأحرف هو 0 -- 0xFF وحجم الأحرف هو 1 بايت.
--empty-class <match-empty | match-none | error>
تحديد الطريقة التي يعامل بها re2js فئات الأحرف الفارغة. مع match-empty (الافتراضي) تطابق الفئة الفارغة المدخلات الفارغة (وهو أمر غير منطقي، ولكنه متوافق مع الإصدارات السابقة). مع match-none تفشل الفئة الفارغة دائمًا في المطابقة. مع error تثير الفئة الفارغة خطأ تجميع.
--encoding-policy <fail | substitute | ignore>
تحديد الطريقة التي يعامل بها re2js بدائل Unicode (surrogates). مع fail يتوقف re2js عن العمل بخطأ عند مواجهة بديل. مع substitute يستبدل re2js البدائل بصمت بنقطة رمز الخطأ 0xFFFD. مع ignore (الافتراضي) يعامل re2js البدائل كنقاط رمز عادية. تنص معيار Unicode على أن البدائل المستقلة غير صالحة، ولكن المكتبات والبرامج الواقعية تتصرف بطرق مختلفة.
--flex-syntax -F
دعم جزئي لصيغة Flex: في هذا الوضع، لا تحتاج التعريفات المسماة إلى علامة المساواة والفاصلة المنقوطة النهائية، وعند استخدامها يجب أن تكون محاطة بأقواس متعرجة. تُعامل الأسماء بدون أقواس متعرجة كسلاسل مقتبسة بعلامة اقتباس مزدوجة.
--goto-label
استخدام نموذج التعليمات البرمجية "goto/label": ترميز DFA في شكل كتل تعليمات برمجية مسماة متصلة بانتقالات goto عبر الكتل. هذا مدعوم فقط للغات التي تحتوي على عبارة goto.
--header --type-header -t HEADER
توليد ملف HEADER. يمكن تحديد محتويات الملف باستخدام الكتل الخاصة header:on و header:off. إذا تم استخدام الشروط، فسيحتوي الرأس المولد على تعداد شرطي مضاف إليه تلقائيًا (ما لم يكن هناك كتلة conditions صريحة).
-I PATH
أضف PATH إلى قائمة المواقع المستخدمة عند البحث عن ملفات التضمين. هذا الخيار مفيد بالاشتراك مع كتلة أو توجيه include. يبحث re2js عن FILE في دليل الملف الأصل وفي مواقع التضمين المحددة بالخيار -I.
--input <default | custom>
اسم مستعار مهمل لـ --api. الخيار default يتوافق مع simple (وهو بالفعل الافتراضي لمعظم الواجهات الخلفية، ولكن ليس لكل منها). الخيار custom يتوافق مع generic.
--input-encoding <ascii | utf8>
تحديد الطريقة التي يفسر بها re2js التعبيرات العادية. مع ascii (الافتراضي) يعامل re2js الإدخال كـ ASCII: أي تسلسل وحدات رمز هو تسلسل أحرف مستقلة أحادية البايت. مع utf8 يعامل re2js الإدخال كـ UTF8 ويتعرف على الأحرف متعددة البايت.
--invert-captures
عكس معنى المجموعات الالتقاطية وغير الالتقاطية. افتراضيًا (...) هو التقاط و (! ...) هو غير التقاط. مع هذا الخيار (! ...) هو التقاط و (...) هو غير التقاط.
--lang <none | c | d | go | haskell | java | js | ocaml | python | rust | swift | v | zig>
تحديد لغة الهدف. اللغات المدعومة هي C، D، Go، Haskell، Java، JS، OCaml، Python، Rust، Swift، V، Zig (يمكن إضافة المزيد من اللغات عبر ملفات الصيغة المعرفة من قبل المستخدم، انظر الخيار --syntax). الخيار none يعطل تكوينات الصيغة الافتراضية، بحيث تكون لغة الهدف غير محددة.
--location-format <gnu | msvc>
تحديد تنسيق الموقع في الرسائل. مع gnu تتم طباعة المواقع كـ "filename:line:column: ...". مع msvc تتم طباعة المواقع كـ "filename(line,column) ...". الافتراضي هو gnu.
--loop-switch
استخدام نموذج التعليمات البرمجية "loop/switch": ترميز DFA في شكل حلقة فوق عبارة switch، حيث تكون الحالات الفردية حالات switch. يتم تخزين الحالة في متغير yystate. تؤدي الانتقالات بين الحالات إلى تحديث yystate إلى تسمية حالة الوجهة وتستمر في التنفيذ حتى رأس الحلقة.
--nested-ifs -s
استخدام عبارات if متداخلة بدلاً من عبارات switch في القفزات الشرطية. ينتج عن هذا عادةً كود أكثر كفاءة مع المترجمات غير المحسنة.
--no-debug-info -i
عدم إخراج توجيهات الأسطر. قد يكون هذا مفيدًا عندما يتم تخزين الكود المولد في نظام التحكم في الإصدارات (لتجنب اختلافات كبيرة مولدة تلقائيًا على تغييرات صغيرة).
--no-generation-date

--no-version
منع إخراج الإصدار في الملف المولد.
--no-unsafe

تحذير إذا كان الحد الأدنى للنطاق أكبر من حده الأعلى. السلوك الافتراضي هو تبديل حدود النطاق بصمت.

-Wnondeterministic-tags
تحذير إذا كان للعلامة درجة n من عدم التحديد، حيث n أكبر من 1.
-Wsentinel-in-midrule
تحذير إذا ظهر رمز الحارس في منتصف قاعدة --- قد يتسبب هذا في قراءات تتجاوز نهاية المخزن المؤقت، أو تعطل، أو تلف في الذاكرة في المحلل اللغوي الذي تم إنشاؤه. ينطبق هذا التحذير فقط إذا تم استخدام طريقة الحارس للتحقق من نهاية الإدخال. يتم تعيينه كخطأ إذا تم استخدام تكوين re2c:sentinel.

ملفات الصيغة

يعتمد دعم اللغات المختلفة في re2c على فكرة ملفات الصيغة. ملف الصيغة هو ملف تكوين يحدد صيغة اللغة المستهدفة -- ليست اللغة بأكملها، ولكن جزء صغير منها يستخدمه الرمز الذي تم إنشاؤه. تجعل ملفات الصيغة re2c مرنة للغاية، ولكن لا ينبغي استخدامها كبديل لتكوينات re2c:: الغرض منها هو تحديد صيغة اللغة المستهدفة، وليس تخصيص محلل لغوي واحد معين. جميع اللغات المدعومة لديها ملفات صيغة افتراضية وهي جزء من التوزيع (انظر الدليل الفرعي include/syntax)؛ كما أنها مدمجة في الثنائي re2js. يمكن للمستخدمين تقديم ملف صيغة مخصص يحل محل بعض التكوينات للغة مدعومة، أو يمكنهم اختيار إعادة تعريف جميع التكوينات (في هذه الحالة يجب استخدام الخيار --lang none). تحتوي ملفات الصيغة على تكوينات من أربعة أنواع مختلفة: قوائم الميزات، تكوينات اللغة، تكوينات في المكان، وقوالب الرموز.

قوائم الميزات

تحدد بعض تكوينات القوائم ميزات مختلفة تدعمها الواجهة الخلفية، بحيث يمكن لـ re2js إعطاء خطأ واضح إذا حاول المستخدم تمكين ميزة غير مدعومة:
supported_apis
قائمة بواجهات برمجة التطبيقات المدعومة مع عناصر محتملة simple، record، generic.
supported_api_styles
قائمة بأنماط واجهة برمجة التطبيقات المدعومة مع عناصر محتملة functions، free-form.
supported_code_models
قائمة بنماذج الرموز المدعومة مع عناصر محتملة goto-label، loop-switch، recursive-functions.
supported_targets
قائمة بأهداف توليد الرموز المدعومة مع عناصر محتملة code، dot، skeleton.
supported_features
قائمة بالميزات المدعومة مع عناصر محتملة nested-ifs، bitmaps، computed-gotos، case-ranges، monadic، unsafe، tags، captures، captvars.

قوالب الرموز

تحدد قوالب الرموز صيغة اللغة المستهدفة. وهي مكتوبة بلغة بسيطة خاصة بالمجال مع قواعد نحوية رسمية التالية: 
code-template ::
      name '=' code-exprs ';'
    | CODE_TEMPLATE ';'
    | '<undefined>' ';'
code-exprs ::
      <EMPTY>
    | code-exprs code-expr
code-expr ::
      STRING
    | VARIABLE
    | optional
    | list
optional ::
      '(' CONDITIONAL '?' code-exprs ')'
    | '(' CONDITIONAL '?' code-exprs ':' code-exprs ')'
list ::
      '[' VARIABLE ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER '}' ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER ',' NUMBER '}' ':' code-exprs ']'

قالب الرمز هو تسلسل من الثوابت النصية، والمتغيرات، والعناصر الاختيارية والقوائم، أو إشارة إلى قالب رمز آخر، أو قيمة خاصة <undefined>. المتغيرات هي عناصر نائبة يتم استبدالها أثناء مرحلة توليد الرموز. متغيرات القوائم مميزة: عند توسيع قوالب القوائم، يكرر re2js التعبيرات الموجودة على الجانب الأيمن من العمود عدة مرات، وفي كل مرة يستبدل تكرارات متغير القائمة بقيمة خاصة بهذه التكرار. تحتوي القوائم على حدود اختيارية (يتم حساب القيم السالبة من النهاية، على سبيل المثال -1 تعني العنصر الأخير). تبدأ أسماء الشروط بنقطة. يمكن أن تكون الشروط والمتغيرات محلية (خاصة بقالب الرمز المحدد) أو عامة (مسموح بها في جميع قوالب الرموز). عندما يقرأ re2js ملف الصيغة، يتحقق من أن كل قالب رمز يستخدم فقط المتغيرات والشروط المسموح بها فيه.

على سبيل المثال، يحدد قالب الرمز التالي بنية if-then-else للغة شبيهة بـ C:

code:if_then_else =
    [branch{0}: topindent "if " cond " {" nl
        indent [stmt: stmt] dedent]
    [branch{1:-1}: topindent "} else" (.cond ? " if " cond) " {" nl
        indent [stmt: stmt] dedent]
    topindent "}" nl;

هنا branch هو متغير قائمة: branch{0} يتوسع إلى الفرع الأول (وهو خاص، حيث لا يوجد جزء else)، branch{1:-1} يتوسع إلى جميع الفروع المتبقية (إن وجدت). stmt هو أيضًا متغير قائمة: [stmt: stmt] هي قائمة متداخلة تتوسع إلى قائمة من العبارات في جسم الفرع الحالي. topindent، indent، dedent و nl هي متغيرات عامة، و .cond هو شرط محلي (يتم وصف معناها أدناه). يمكن أن ينتج قالب الرمز هذا الرمز التالي:

if x {
    // do something
} else if y {
    // do something else
} else {
    // don't do anything
}

الحالة القابلة للتخزين

مع الخيار --storable-state، يقوم re2js بإنشاء محلل يمكنه تخزين حالته الحالية، والعودة إلى المستدعي، واستئناف العمليات لاحقًا تمامًا من حيث توقف. الوضع الافتراضي للعمل في re2js هو نموذج "السحب"، حيث "يسحب" المحلل المزيد من الإدخال كلما احتاج إليه. قد يكون هذا غير مقبول في الحالات التي يصبح فيها الإدخال متاحًا قطعة قطعة (على سبيل المثال، إذا تم استدعاء المحلل بواسطة المحلل، أو إذا كان برنامج المحلل يتواصل عبر بروتوكول المقبس مع برنامج آخر يجب أن ينتظر ردًا من المحلل قبل إرسال الرسالة التالية). ميزة الحالة القابلة للتخزين مخصصة تمامًا لهذه الحالات: فهي تسمح بإنشاء محللات تعمل بنموذج "الدفع". عندما يحتاج المحلل إلى المزيد من الإدخال، فإنه يخزن حالته ويعود إلى المستدعي. لاحقًا، عندما يصبح المزيد من الإدخال متاحًا، يقوم المستدعي باستئناف المحلل تمامًا من حيث توقف. هناك بعض التغييرات اللازمة مقارنة بنموذج "السحب":

  • تعريف بدائيات YYSETSTATE() و YYGETSTATE(state).
  • تعريف المتغيرات yych، yyaccept (إذا تم استخدامها)، و state كجزء من حالة المحلل الدائمة. يجب تهيئة المتغير state إلى -1.
  • يجب أن يعود YYFILL إلى البرنامج الخارجي بدلاً من محاولة توفير المزيد من الإدخال. يجب أن يشير رمز الإرجاع إلى أن المحلل يحتاج إلى المزيد من الإدخال.
  • يجب على البرنامج الخارجي التعرف على المواقف التي يحتاج فيها المحلل إلى المزيد من الإدخال والاستجابة بشكل مناسب.
  • اختياريًا، استخدم كتلة getstate لإنشاء مفتاح YYGETSTATE منفصل عن المحلل الرئيسي. هذا يعمل فقط مع اللغات التي لديها goto (ليس في وضع --loop-switch).
  • استخدم re2c:eof وطريقة الحارس مع فحوصات الحدود للتعامل مع نهاية الإدخال. قد لا تعمل طريقة الحشو المستندة إلى الحشو لأنها غير واضحة متى يتم إضافة الحشو: قد لا تكون نهاية الإدخال الحالية هي نهاية الإدخال النهائية، وقد يؤدي إضافة الحشو مبكرًا جدًا إلى قطع جزء من التعبير القياسي الجشع المقروء جزئيًا. علاوة على ذلك، نظرًا لمنطق البرنامج عالي المستوى، فإن الحصول على المزيد من الإدخال قد يعتمد على معالجة التعبير القياسي في نهاية المخزن المؤقت (والذي تم حظره بالفعل بسبب شرط نهاية الإدخال).

INTRODUCTION

re2js programs are very useful for a number of reasons:

  • They can check correctness of various re2js optimizations (the data is generated early in the process, before any DFA transformations have taken place).
  • Generating a set of input data with good coverage may be useful for both testing and benchmarking.
  • Generating self-contained executable programs allows one to get minimized test cases (the original code may be large or have a lot of dependencies).

The difficulty with generating input data is that for all but the most trivial cases the number of possible input strings is too large (even if the string length is limited). re2js solves this difficulty by generating sufficiently many strings to cover almost all DFA transitions. It uses the following algorithm. First, it constructs a skeleton of the DFA. For encodings with 1-byte code unit size (such as ASCII, UTF-8 and EBCDIC) skeleton is just an exact copy of the original DFA. For encodings with multibyte code units skeleton is a copy of DFA with certain transitions omitted: namely, re2js takes at most 256 code units for each disjoint continuous range that corresponds to a DFA transition. The chosen values are evenly distributed and include range bounds. Instead of trying to cover all possible paths in the skeleton (which is infeasible) re2js generates sufficiently many paths to cover all skeleton transitions, and thus trigger the corresponding conditional jumps in the lexer. The algorithm implementation is limited by ~1Gb of transitions and consumes constant amount of memory (re2js writes data to file as soon as it is generated).

Visualization and debug

With the -D, --emit-dot option, re2js does not generate code. Instead, it dumps the generated DFA in DOT format. One can convert this dump to an image of the DFA using Graphviz or another library. Note that this option shows the final DFA after it has gone through a number of optimizations and transformations. Earlier stages can be dumped with various debug options, such as --dump-nfa, --dump-dfa-raw etc. (see the full list of options).
