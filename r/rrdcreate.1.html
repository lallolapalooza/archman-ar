الحزمة: rrdtool

NAME

rrdcreate

create Round Robin Databases

SYNOPSIS

rrdtool create rrdfile [options] DS:name:type:heartbeat:min:max [DS:...] [RRA:...]

DESCRIPTION

rrdtool create is used to create new Round Robin Databases (RRD). It is important to plan your database structure carefully, as it is difficult to change later.

The command line consists of the standard arguments followed by a list of data sources (DS) and Round Robin Archives (RRA).

The standard arguments are:

--step N
This specifies the maximum number of seconds allowed between data updates. If this is not set, it will be determined by the number of data sources. If more than one DS is defined, the step is the greatest common divisor of all heartbeat arguments. If this is not set, it is 300.
--source file
Create the RRD file based on the structure of an existing RRD file. This command will override the DS and RRA definitions.

Data Source (DS) arguments:

DS:name:type:heartbeat:min:max
This defines a data source.
name
The name of the data source. This must be unique for each DS in an RRD. Maximum length is 19 characters.
type
The type of the data source. This can be one of:
COUNTER
A counter that only increases. It can wrap around (e.g. 32-bit counters).
DERIVE
A counter that can also decrease. It is expected to change by small amounts relatively often. It is used to measure things like disk I/O which may occasionally go down.
GAUGE
A value that can increase or decrease (e.g. temperature).
ABSOLUTE
A value that is reset to zero when it is read. It is used for non-monotonic counters, for example, number of requests processed by a web server since boot.
COMPUTE
This data source type is computed on the fly from other data sources using RPN calculations. See the rrdcalc man page for details.
heartbeat
The maximum number of seconds allowed between two updates. If this value is exceeded, the data source is considered *UNKNOWN*. The default is 600 seconds (10 minutes).
min
The minimum accepted value for this data source. Use U for undefined. The default is U.
max
The maximum accepted value for this data source. Use U for undefined. The default is U.

Round Robin Archive (RRA) arguments:

RRA:type:xff:steps_in_period:num_rows
This defines a Round Robin Archive.
type
The consolidation function to use for this archive. This can be AVERAGE, MIN, MAX, LAST, or one of the specialized functions HWPREDICT, SEASONAL, DEVSEASONAL, DEVPREDICT, FAILURES.
xff
The x-files factor. This indicates the minimum percentage of data points that must be defined in a step for the consolidated data point to be considered valid. It must be a value between 0 and 1. The default is 0.5.
steps_in_period
This indicates how many steps (defined by the --step argument) are in one consolidation period. For example, if step is 300 (5 minutes) and you want to store data consolidated per hour, then steps_in_period would be 12 (60 minutes / 5 minutes). The default is 1.
num_rows
This indicates the number of data rows to store in this archive. This determines the lifespan of the data in this archive.

Aberrant Behavior Detection with Holt-Winters Forecasting

The specialized RRAs allow you to detect aberrant behavior in your data. This is done using Holt-Winters forecasting.

HWPREDICT:period:alpha:beta:gamma[:rra-num]
This RRA stores the Holt-Winters forecast and the prediction interval boundaries. The period is the length of the seasonal cycle in number of data points. alpha is the smoothing factor for the level, beta for the trend, and gamma for the seasonality. rra-num is optional and specifies which of the other RRAs contain the data to be used for the forecast.
SEASONAL:period:alpha[:rra-num]
This RRA stores the seasonal cycle data. period is the length of the seasonal cycle in number of data points. alpha is the smoothing factor for the seasonal component. rra-num is optional.
DEVSEASONAL:period:alpha[:rra-num]
This RRA stores the deviation from the seasonal cycle. It's used to detect if the current value deviates significantly from the expected seasonal value. period and alpha are similar to SEASONAL.
DEVPREDICT:period[:rra-num]
This RRA stores the predicted deviation from the seasonal cycle. It's used to predict how much the deviation is likely to increase or decrease. period is the length of the seasonal cycle in number of data points. rra-num is optional.
FAILURES:period:threshold:decay[:rra-num]
This RRA stores the number of failures detected. A failure is declared when the current value exceeds the predicted deviation limits. period is the length of the seasonal cycle. threshold is the minimum number of consecutive failures to trigger an alert. decay is the decay factor for the failure count. rra-num is optional.

STEP, HEARTBEAT, and Rows As Durations

The choice of STEP, HEARTBEAT and the number of Rows in your RRA definitions is crucial for the performance and accuracy of your RRD database.

The STEP defines the interval between data points. Larger steps mean less data storage but also less granularity.

The HEARTBEAT defines the maximum time allowed between data updates before the data is considered stale. A shorter heartbeat means that the system will quickly detect missing data, but it also means that you need to provide data more frequently.

The number of Rows in an RRA defines how long data will be kept in that archive. For example, if you have a step of 300 seconds (5 minutes) and an RRA with 12 rows, it will store data for 60 minutes (1 hour).

The HEARTBEAT and the STEP

It is recommended that the heartbeat value be at least twice the step value. This provides a buffer for temporary network outages or other issues that might cause a missed update. If the heartbeat is less than twice the step, the system might report data as UNKNOWN even if there was just a temporary glitch.

HOW TO MEASURE

At some later stage you want to know the number of messages transported in a day, you can get the average messages per second from RRDtool for the day in question and multiply this number with the number of seconds in a day. Because all math is run with Doubles, the precision should be acceptable.

It's always a Rate
RRDtool stores rates in amount/second for COUNTER, DERIVE, DCOUNTER, DDERIVE and ABSOLUTE data. When you plot the data, you will get on the y axis amount/second which you might be tempted to convert to an absolute amount by multiplying by the delta-time between the points. RRDtool plots continuous data, and as such is not appropriate for plotting absolute amounts as for example "total bytes" sent and received in a router. What you probably want is plot rates that you can scale to bytes/hour, for example, or plot absolute amounts with another tool that draws bar-plots, where the delta-time is clear on the plot for each point (such that when you read the graph you see for example GB on the y axis, days on the x axis and one bar for each day).

EXAMPLE

rrdtool create temperature.rrd --step 300 \
 DS:temp:GAUGE:600:-273:5000 \
 RRA:AVERAGE:0.5:1:1200 \
 RRA:MIN:0.5:12:2400 \
 RRA:MAX:0.5:12:2400 \
 RRA:AVERAGE:0.5:12:2400

This sets up an RRD called temperature.rrd which accepts one temperature value every 300 seconds. If no new data is supplied for more than 600 seconds, the temperature becomes *UNKNOWN*. The minimum acceptable value is -273 and the maximum is 5'000.

A few archive areas are also defined. The first stores the temperatures supplied for 100 hours (1'200 * 300 seconds = 100 hours). The second RRA stores the minimum temperature recorded over every hour (12 * 300 seconds = 1 hour), for 100 days (2'400 hours). The third and the fourth RRA's do the same for the maximum and average temperature, respectively.

EXAMPLE 2

rrdtool create monitor.rrd --step 300        \
  DS:ifOutOctets:COUNTER:1800:0:4294967295   \
  RRA:AVERAGE:0.5:1:2016                     \
  RRA:HWPREDICT:1440:0.1:0.0035:288

This example is a monitor of a router interface. The first RRA tracks the traffic flow in octets; the second RRA generates the specialized functions RRAs for aberrant behavior detection. Note that the rra-num argument of HWPREDICT is missing, so the other RRAs will implicitly be created with default parameter values. In this example, the forecasting algorithm baseline adapts quickly; in fact the most recent one hour of observations (each at 5 minute intervals) accounts for 75% of the baseline prediction. The linear trend forecast adapts much more slowly. Observations made during the last day (at 288 observations per day) account for only 65% of the predicted linear trend. Note: these computations rely on an exponential smoothing formula described in the LISA 2000 paper.

The seasonal cycle is one day (288 data points at 300 second intervals), and the seasonal adaption parameter will be set to 0.1. The RRD file will store 5 days (1'440 data points) of forecasts and deviation predictions before wrap around. The file will store 1 day (a seasonal cycle) of 0-1 indicators in the FAILURES RRA.

The same RRD file and RRAs are created with the following command, which explicitly creates all specialized function RRAs using "STEP, HEARTBEAT, and Rows As Durations".

rrdtool create monitor.rrd --step 5m \
  DS:ifOutOctets:COUNTER:30m:0:4294967295 \
  RRA:AVERAGE:0.5:1:2016 \
  RRA:HWPREDICT:5d:0.1:0.0035:1d:3 \
  RRA:SEASONAL:1d:0.1:2 \
  RRA:DEVSEASONAL:1d:0.1:2 \
  RRA:DEVPREDICT:5d:5 \
  RRA:FAILURES:1d:7:9:5

Of course, explicit creation need not replicate implicit create, a number of arguments could be changed.

EXAMPLE 3

rrdtool create proxy.rrd --step 300 \
  DS:Requests:DERIVE:1800:0:U  \
  DS:Duration:DERIVE:1800:0:U  \
  DS:AvgReqDur:COMPUTE:Duration,Requests,0,EQ,1,Requests,IF,/ \
  RRA:AVERAGE:0.5:1:2016

This example is monitoring the average request duration during each 300 sec interval for requests processed by a web proxy during the interval. In this case, the proxy exposes two counters, the number of requests processed since boot and the total cumulative duration of all processed requests. Clearly these counters both have some rollover point, but using the DERIVE data source also handles the reset that occurs when the web proxy is stopped and restarted.

In the RRD, the first data source stores the requests per second rate during the interval. The second data source stores the total duration of all requests processed during the interval divided by 300. The COMPUTE data source divides each PDP of the AccumDuration by the corresponding PDP of TotalRequests and stores the average request duration. The remainder of the RPN expression handles the divide by zero case.

SECURITY

Note that new rrd files will have the permission 0644 regardless of your umask setting. If a file with the same name previously exists, its permission settings will be copied to the new file.
