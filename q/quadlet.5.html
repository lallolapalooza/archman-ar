AddCapability=

AddDevice=

يضيف عقدة جهاز من المضيف إلى الحاوية. تنسيق هذا هو HOST-DEVICE[:CONTAINER-DEVICE][:PERMISSIONS]، حيث HOST-DEVICE هو مسار عقدة الجهاز على المضيف، CONTAINER-DEVICE هو مسار عقدة الجهاز في الحاوية، و PERMISSIONS هي قائمة من الأذونات التي تجمع بين 'r' للقراءة، 'w' للكتابة، و 'm' لـ mknod(2). البادئة - تخبر Quadlet بإضافة الجهاز فقط إذا كان موجودًا على المضيف.

يمكن إدراج هذا المفتاح عدة مرات.

AutoUpdate=

يشير إلى ما إذا كانت الحاوية سيتم تحديثها تلقائيًا (podman-auto-update(1)). القيم التالية مدعومة:

  • registry: يتطلب مرجع صورة مؤهل بالكامل (على سبيل المثال، quay.io/podman/stable:latest) ليتم استخدامه لإنشاء الحاوية. هذا الإنفاذ ضروري لمعرفة الصورة التي سيتم التحقق منها وسحبها. إذا تم استخدام معرف صورة، فإن Podman لا يعرف الصورة التي سيتم التحقق منها/سحبها بعد الآن.
  • local: يخبر Podman بمقارنة الصورة التي تستخدمها الحاوية بالصورة ذات الاسم الخام في التخزين المحلي. إذا تم تحديث صورة محليًا، فإن Podman يعيد تشغيل وحدة systemd التي تنفذ الحاوية ببساطة.

CgroupsMode=

بشكل افتراضي، وضع cgroups للحاوية التي تم إنشاؤها بواسطة Quadlet هو split، والذي يختلف عن الافتراضي (enabled) المستخدم بواسطة Podman CLI.

إذا انضمت الحاوية إلى pod (أي تم تحديد Pod=)، قد ترغب في تغيير هذا إلى no-conmon أو enabled حتى يمكن تطبيق حدود موارد cgroup على مستوى pod.

Exec=

التنسيق هو نفس تنسيق سطور أوامر systemd، ومع ذلك، على عكس سيناريو الاستخدام لفعل ExecStart= المشابه في systemd الذي يعمل على نظام ملفات الجذر المحيط، من الشائع جدًا أن تحتوي صور الحاويات على بيانات وصفية خاصة بها ENTRYPOINT أو CMD والتي يتفاعل معها هذا.

•

SetWorkingDirectory=

توفير سياق (دليل عمل) لـ podman build. القيم المدعومة هي مسار، عنوان URL، أو المفاتيح الخاصة file أو unit لتعيين دليل السياق إلى الدليل الأصل للملف من المفتاح File= أو إلى ملف وحدة Quadlet .build على التوالي. هذا يسمح لـ Quadlet بحل المسارات النسبية.

عند استخدام أحد المفاتيح الخاصة (file أو unit)، سيتم أيضًا تعيين حقل WorkingDirectory من مجموعة Service لوحدة خدمة Systemd وفقًا لذلك. بدلاً من ذلك، يمكن للمستخدمين تعيين حقل WorkingDirectory الخاص بمجموعة Service بشكل صريح في ملف .build. يرجى ملاحظة أنه إذا تم تعيين حقل WorkingDirectory الخاص بمجموعة Service بواسطة المستخدم، فلن يقوم Quadlet بالكتابة فوقه حتى لو تم تعيين SetWorkingDirectory إلى file أو unit.

من خلال توفير عنوان URL إلى SetWorkingDirectory=، يمكنك توجيه podman build لنسخ مستودع Git أو تنزيل ملف أرشيفي يتم استخراجه إلى موقع مؤقت بواسطة podman build كسياق بناء. لاحظ أنه في هذه الحالة، يترك Quadlet حقل WorkingDirectory لوحدة خدمة Systemd دون تغيير.

لاحظ أن توفير دليل السياق إلزامي لملف .build، ما لم يتم توفير مفتاح File= أيضًا.

quadlet(5)

الحزمة: podman

التراخيص: Apache-2.0

الاسم

quadlet - أدوات لإنشاء وإدارة حاويات podman المستندة إلى Systemd

ملخص

يتم استخدام ملفات Unit (.unit) لإنشاء وإدارة حاويات podman.

الوصف

ملفات الوحدة هي ملفات تكوين تستخدم لإنشاء وإدارة حاويات Podman. يمكن استخدامها لتحديد صورة الحاوية، والوسائط، والمنافذ، والمجلدات، والشبكات، وغيرها من الإعدادات. يتم استدعاء الأداة باسم ملف الوحدة (بدون امتداد)، وتتم معالجة الملف بواسطة Systemd.

توجد أقسام مختلفة لتكوين ملفات الوحدة.

وحدات الحاوية [Container]

يحدد هذا القسم إعدادات الحاوية.

مثال:

[Container]
Image=docker.io/library/ubuntu:latest
Exec=/usr/bin/sleep infinity
Port=8080:80
Mount=type=bind,source=/tmp/data,destination=/data
Network=container:my-container

وحدات Pod [Pod]

يحدد هذا القسم إعدادات Pod. يمكن استخدام Pod لتجميع حاويات متعددة.

مثال:

[Pod]
PodName=my-pod
Labels=app=my-app,env=prod
Infra=true

وحدات Kube [Kube]

يحدد هذا القسم إعدادات Kubernetes. يمكن استخدامه لتشغيل ملفات YAML الخاصة بـ Kubernetes.

مثال:

[Kube]
Yaml=/path/to/your/deployment.yaml

وحدات الشبكة [Network]

يحدد هذا القسم إعدادات الشبكة. يمكن استخدامه لإنشاء وإدارة شبكات Podman.

مثال:

[Network]
Subnet=10.10.0.0/24
Gateway=10.10.0.1
Port=8080:80

وحدات المجلد [Volume]

يحدد هذا القسم إعدادات المجلد. يمكن استخدامه لإنشاء وإدارة مجلدات Podman.

مثال:

[Volume]
VolumeName=my-volume
Mountpoint=/var/lib/my-volume

وحدات البناء [Build]

يحدد هذا القسم إعدادات البناء. يمكن استخدامه لبناء صور الحاويات.

مثال:

[Build]
ImageTag=my-image:latest
Dockerfile=./Dockerfile
Context=.

وحدات الصورة [Image]

يحدد هذا القسم إعدادات الصورة. يمكن استخدامه لسحب الصور من سجل.

مثال:

[Image]
Name=docker.io/library/ubuntu:latest

وحدات الأثر [Artifact]

يحدد هذا القسم إعدادات الأثر. يمكن استخدامه لسحب الآثار من سجل.

مثال:

[Artifact]
Artifact=quay.io/example/my-artifact:latest
AuthFile=/etc/registry/auth.json
TLSVerify=false

قسم Quadlet [Quadlet]

يحدد هذا القسم إعدادات Quadlet العامة.

مثال:

[Quadlet]
AutoUpdate=true
AutoRemove=true

أمثلة

مثال لملف test.network:

[Unit]
Description=My Test Network
[Network]
Subnet=192.168.100.0/24
Gateway=192.168.100.1

مثال لملف test.container:

[Unit]
Description=My Test Container
After=test.network
[Container]
Image=docker.io/library/alpine:latest
Volume=my-volume:/data
Network=test.network
Exec=sleep infinity

مثال لملف test.kube:

[Unit]
Description=A kubernetes yaml based service
Before=local-fs.target
[Kube]
Yaml=/opt/k8s/deployment.yml
[Install]
# Start by default on boot
WantedBy=multi-user.target default.target

مثال لإنشاء صورة محلية لاستخدامها في حاوية مع وسائط بناء محددة:

test.build

[Build]
# Tag the image to be built
ImageTag=localhost/imagename
# Set the working directory to the path of the unit file,
# expecting to find a Containerfile/Dockerfile
# + other files needed to build the image
SetWorkingDirectory=unit
# Set build arguments VERSION and DEBUG
BuildArg=VERSION=1.0
          DEBUG=false

test.container

[Container]
Image=test.build

مثال لملف test.volume:

[Volume]
User=root
Group=root
Label=org.test.Key=value

مثال لملف test.network:

[Network]
Subnet=172.16.0.0/24
Gateway=172.16.0.1
IPRange=172.16.0.0/28
Label=org.test.Key=value

مثال لملف test.artifact لسحب الأثر فقط باستخدام ملف مصادقة واحد:

[Artifact]
Artifact=quay.io/example/my-artifact:latest
AuthFile=/etc/registry/auth.json
TLSVerify=false

مثال للاستخدام حيث تعتمد حاوية على أثر:

my-artifact.artifact:

[Artifact]
Artifact=quay.io/example/my-config:latest

my-app.container:

[Container]
Image=quay.io/example/my-app:latest
Mount=type=artifact,source=my-artifact.artifact,destination=/etc/config

مثال للحاوية في Pod:

test.pod

[Pod]
PodName=test

centos.container

[Container]
Image=quay.io/centos/centos:latest
Exec=sh -c "sleep inf"
Pod=test.pod

مثال لـ Pod مع مهمة بدء تشغيل لمرة واحدة:

test.pod

[Pod]
PodName=test
ExitPolicy=continue

startup-task.container

[Service]
Type=oneshot
RemainAfterExit=yes
[Container]
Pod=test.pod
Image=quay.io/centos/centos:latest
Exec=sh -c "echo 'setup starting'; sleep 2; echo 'setup complete'"

app.container

[Unit]
Requires=startup-task.container
After=startup-task.container
[Container]
Pod=test.pod
Image=quay.io/centos/centos:latest
Exec=sh -c "echo 'app running.'; sleep 30"

مثال لملف s3fs.volume:

لمزيد من التفاصيل، يرجى الاطلاع على مشروع s3fs-fuse. تذكر قراءة الأسئلة الشائعة

ملاحظة: تمكين ذاكرة التخزين المؤقت يسرع بشكل كبير الوصول وأوقات الكتابة على الملفات/الكائنات الثابتة.

ومع ذلك، فإن use_cache غير محدود!

كن حذرًا، سيتم ملؤه بأي ملفات تم الوصول إليها على مخزن S3 من خلال نظام الملفات.

يرجى تذكر تعيين S3_BUCKET و PATH و AWS_REGION. يجب إعداد CACHE_DIRECTORY بواسطة systemd

[Service]
CacheDirectory=s3fs
ExecStartPre=/usr/local/bin/aws s3api put-object --bucket ${S3_BUCKET} --key ${PATH}/
[Volume]
Device=${S3_BUCKET}:/${PATH}
Type=fuse.s3fs
VolumeName=s3fs-volume
Options=iam_role,endpoint=${AWS_REGION},use_xattr,listobjectsv2,del_cache,use_cache=${CACHE_DIRECTORY}
# `iam_role` يفترض داخل EC2، إذا لم يكن كذلك، استخدم `profile=` بدلاً من ذلك
