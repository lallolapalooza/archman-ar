ZSHTCPSYS(1) دليل الأوامر العامة ZSHTCPSYS(1)

الاسم

zshtcpsys - نظام TCP الخاص بـ zsh

الوصف

يتم توفير الوحدة النمطية zsh/net/tcp لتوفير إدخال/إخراج الشبكة عبر TCP/IP من داخل الصدفة؛ انظر وصفها في zshmodules(1). تصف صفحة الدليل هذه مجموعة من الوظائف المستندة إلى الوحدة النمطية. إذا كانت الوحدة النمطية مثبتة، فعادةً ما يتم تثبيت الوظائف في نفس الوقت، وفي هذه الحالة ستكون متاحة للتحميل التلقائي في مسار البحث عن الوظائف الافتراضي. بالإضافة إلى الوحدة النمطية zsh/net/tcp، يتم استخدام الوحدة النمطية zsh/zselect لتنفيذ مهلات على عمليات القراءة. للحصول على نصائح استكشاف الأخطاء وإصلاحها، راجع النصائح المقابلة لوظائف zftp الموصوفة في zshzftpsys(1).

هناك وظائف مقابلة لعمليات الإدخال/الإخراج الأساسية: فتح، إغلاق، قراءة، وإرسال، مسماة tcp_open وما إلى ذلك، بالإضافة إلى وظيفة tcp_expect لمطابقة الأنماط لتحليل البيانات المقروءة كمدخل. يجعل النظام من السهل استقبال البيانات من وإلى جلسات متعددة مسماة في وقت واحد. بالإضافة إلى ذلك، يمكن ربطه بمحرر أسطر الصدفة بحيث يتم عرض بيانات الإدخال تلقائيًا على الطرفية. تشمل التسهيلات الأخرى المتاحة التسجيل والتصفية ومطالبات الإخراج القابلة للتكوين.

لاستخدام النظام حيثما كان متاحًا، يجب أن يكون كافيًا تشغيل `autoload -U tcp_open' وتشغيل tcp_open كما هو موثق أدناه لبدء جلسة. ستقوم وظيفة tcp_open بتحميل الوظائف المتبقية تلقائيًا.

وظائف مستخدم TCP

الإدخال/الإخراج الأساسي

tcp_open [ -qz ] مضيف منفذ [ جلسة ]
tcp_open [ -qz ] [ -s جلسة | -l جلسة[,...] ] ...
tcp_open [ -qz ] [ -a موصِّل | -f موصِّل ] [ جلسة ]
افتح جلسة جديدة. في الشكل الأول والأبسط، افتح اتصال TCP بالمضيف مضيف على المنفذ منفذ؛ يتم فهم الأشكال الرقمية والرمزية لكلاهما.

إذا تم توفير جلسة، فستصبح هذه هي اسم الجلسة التي يمكن استخدامها للإشارة إلى اتصالات TCP متعددة مختلفة. إذا لم يتم توفير جلسة، فستقوم الوظيفة بابتكار قيمة اسم رقمية (لاحظ أن هذا *ليس* نفس الواصف الملفي الذي تم إرفاق الجلسة به). يوصى بأن أسماء الجلسات لا تحتوي على أحرف "غريبة"، حيث لا يتم تعريف الأحرف الغريبة بشكل جيد ولكنها بالتأكيد لا تشمل الأحرف الأبجدية الرقمية أو الشرطات السفلية، وبالتأكيد تشمل المسافات البيضاء.

في الحالة الثانية، يتم تحديد جلسة واحدة أو أكثر ليتم فتحها بالاسم. يتم إعطاء اسم جلسة واحدة بعد -s وقائمة مفصولة بفواصل بعد -l؛ يمكن تكرار كلا الخيارين حسب الضرورة. يتسبب فشل فتح أي جلسة في إنهاء tcp_open. تتم قراءة المضيف والمنفذ من الملف .ztcp_sessions في نفس الدليل الذي يحتوي على ملفات تهيئة zsh للمستخدم، أي عادةً دليل المنزل، ولكن $ZDOTDIR إذا تم تعيينه. يتكون الملف من أسطر كل منها يعطي اسم جلسة والمضيف والمنفذ المقابلين، بالترتيب (لاحظ أن اسم الجلسة يأتي أولاً، وليس أخيراً)، مفصولة بمسافات بيضاء.

يسمح الشكل الثالث بالاتصالات TCP السلبية والمزيفة. إذا تم استخدام الخيار -a، فإن وسيطته هي واصف ملف مفتوح للاستماع للاتصالات. لا توجد واجهة وظيفية مقدمة لفتح واصف ملف، ولكن استدعاء `ztcp -l منفذ' سينشئ واحدًا مع تخزين الواصف الملفي في المعلمة $REPLY. يمكن إغلاق منفذ الاستماع باستخدام `ztcp -c موصِّل'. سيتم حظر استدعاء `tcp_open -a موصِّل' حتى يتم إجراء اتصال TCP بعيد بالمنفذ منفذ على الجهاز المحلي. عند هذه النقطة، يتم إنشاء جلسة بالطريقة المعتادة وهي غير قابلة للتمييز إلى حد كبير عن اتصال نشط تم إنشاؤه بأحد الأشكال الأولى.

إذا تم استخدام الخيار -f، فإن وسيطته هي واصف ملف يتم استخدامه مباشرة كما لو كان جلسة TCP. تعتمد مدى جودة تعامل بقية نظام وظائف TCP مع هذا على ما يكمن فعليًا وراء واصف الملف هذا. من المحتمل أن يكون الملف العادي غير قابل للاستخدام؛ سيكون الأنبوب (FIFO) من نوع ما أفضل، ولكن لاحظ أنه لا ينبغي أن يحاول جلستان مختلفتان القراءة من نفس الأنبوب في وقت واحد.

إذا تم إعطاء الخيار -q مع أي من الأشكال الثلاثة، فلن تقوم tcp_open بطباعة رسائل معلوماتية، على الرغم من أنها ستخرج في أي حال بحالة مناسبة.

إذا كان محرر الأسطر (zle) قيد الاستخدام، وهو ما يحدث عادةً إذا كانت الصدفة تفاعلية، فستقوم tcp_open بتثبيت معالج داخل zle الذي سيتحقق من البيانات الجديدة في نفس الوقت الذي يتحقق فيه من إدخال لوحة المفاتيح. هذا مناسب حيث لا تستهلك الصدفة وقت وحدة المعالجة المركزية أثناء الانتظار؛ يتم إجراء الاختبار بواسطة نظام التشغيل. يمنع إعطاء الخيار -z لأي من أشكال tcp_open تثبيت المعالج، لذلك يجب قراءة البيانات بشكل صريح. لاحظ، ومع ذلك، أن هذا ليس ضروريًا لتنفيذ مجموعات كاملة من أوامر الإرسال والقراءة من وظيفة، حيث أن zle غير نشط في هذه المرحلة. بشكل عام، المعالج نشط فقط عندما تنتظر الصدفة إدخالاً عند موجه الأوامر أو في الأمر المدمج vared. ليس للخيار أي تأثير إذا كان zle غير نشط؛ `[[ -o zle]]' سيختبر ذلك.

تصبح الجلسة الأولى التي تم فتحها هي الجلسة الحالية ولا تقوم استدعاءات tcp_open اللاحقة بتغييرها. يتم تخزين الجلسة الحالية في المعلمة $TCP_SESS؛ انظر أدناه لمزيد من التفاصيل حول المعلمات التي يستخدمها النظام.

يتم استدعاء الوظيفة tcp_on_open، إذا تم تعريفها، عند فتح جلسة. انظر الوصف أدناه.

tcp_close [ -qn ] [ -a | -l جلسة[,...] | جلسة ... ]
أغلق الجلسات المسماة، أو الجلسة الحالية إذا لم يتم تقديم أي منها، أو جميع الجلسات المفتوحة إذا تم تقديم -a. يتم التعامل مع الخيارين -l و -s من أجل الاتساق مع tcp_open، على الرغم من أن الأخير غير ضروري.

إذا كانت الجلسة التي يتم إغلاقها هي الجلسة الحالية، فسيتم إلغاء تعيين $TCP_SESS، مما يترك جلسة غير محددة، حتى لو كانت هناك جلسات أخرى لا تزال مفتوحة.

إذا تم فتح الجلسة باستخدام tcp_open -f، يتم إغلاق واصف الملف طالما أنه في النطاق من 0 إلى 9 يمكن الوصول إليه مباشرة من سطر الأوامر. إذا تم تقديم الخيار -n، فلن يتم إجراء أي محاولة لإغلاق واصفات الملفات في هذه الحالة. لا يستخدم الخيار -n لجلسات ztcp حقيقية؛ يتم دائمًا إغلاق واصفات الملفات مع الجلسة.

إذا تم تقديم الخيار -q، فلن يتم طباعة أي رسائل معلوماتية.

tcp_read [ -bdq ] [ -t المُهلة ] [ -T المُهلة ]
[ -a | -u موصِّل[,...] | -l جلسة[,...] | -s جلسة ... ]
قم بإجراء عملية قراءة على الجلسة الحالية، أو على قائمة من الجلسات إذا تم تقديم أي منها مع -u، -l، أو -s، أو جميع الجلسات المفتوحة إذا تم تقديم الخيار -a. يمكن تكرار أي من الخيارات -u، -l، أو -s أو خلطها معًا. يحدد الخيار -u واصف ملف مباشرة (فقط تلك التي يديرها هذا النظام مفيدة)، والآخرين يحددان الجلسات كما هو موضح لـ tcp_open أعلاه.

تتحقق الوظيفة من البيانات الجديدة المتاحة في جميع الجلسات المحددة. ما لم يتم تقديم الخيار -b، فلن يتم حظرها في انتظار بيانات جديدة. سيتم قراءة أي سطر بيانات واحد من أي من الجلسات المتاحة، وتخزينه في المعلمة $TCP_LINE، وعرضه على المخرج القياسي ما لم تحتوي $TCP_SILENT على سلسلة غير فارغة. عند طباعتها إلى المخرج القياسي، سيتم عرض السلسلة $TCP_PROMPT في بداية السطر؛ يتضمن الشكل الافتراضي لهذا اسم الجلسة التي يتم القراءة منها. انظر أدناه لمزيد من المعلومات حول هذه المعلمات. في هذا الوضع، يمكن استدعاء tcp_read بشكل متكرر حتى تعود بالحالة 2 التي تشير إلى أن جميع المدخلات المعلقة من جميع الجلسات المحددة قد تم التعامل معها.

مع الخيار -b، والذي يعادل مهلة لا نهائية، ستحظر الوظيفة حتى يتوفر سطر للقراءة من إحدى الجلسات المحددة. ومع ذلك، يتم إرجاع سطر واحد فقط.

يشير الخيار -d إلى أنه يجب استنزاف جميع المدخلات المعلقة. في هذه الحالة، قد تعالج tcp_read أسطرًا متعددة بالطريقة الموضحة أعلاه؛ يتم تخزين السطر الأخير فقط في $TCP_LINE، ولكن المجموعة الكاملة

هذا الموقع غير مرتبط بـ Arch Linux ولا تابع له بأي شكل من الأشكال. المحتوى هو ترجمة فقط لصفحات دليل Arch المنشورة على man.archlinux.org.

مخزن في المصفوفة $tcp_lines. يتم مسح هذا في بداية كل استدعاء لـ tcp_read.

الخيارات -t و -T تحدد مهلة بالثواني، والتي قد تكون رقمًا عشريًا لزيادة الدقة. مع -t، يتم تطبيق المهلة قبل قراءة كل سطر. مع -T، تنطبق المهلة على العملية بأكملها، وقد تشمل عمليات قراءة متعددة إذا كان الخيار -d موجودًا؛ بدون هذا الخيار، لا يوجد فرق بين -t و -T.

لا تقوم الدالة بطباعة رسائل معلوماتية، ولكن إذا تم إعطاء الخيار -q، فلن يتم طباعة أي رسالة خطأ لجلستين غير موجودتين.

يشير رمز العودة 2 إلى انتهاء المهلة أو عدم وجود بيانات للقراءة. أي رمز عودة آخر غير صفري يشير إلى وجود حالة خطأ.

راجع tcp_log لمعرفة كيفية التحكم في مكان إرسال البيانات بواسطة tcp_read.

tcp_send [ -cnq ] [ -s sess | -l sess[,...] ] data ...
tcp_send [ -cnq ] -a data ...
يرسل سلاسل البيانات المقدمة إلى جميع الجلسات المحددة بالتتابع. تختلف العملية الأساسية قليلاً عن `print -r' إلى واصف ملف الجلسة، على الرغم من أنها تحاول منع الشل من الموت بسبب SIGPIPE ناتج عن محاولة الكتابة إلى جلسة متوقفة.

يتسبب الخيار -c في سلوك tcp_send مثل cat. يقرأ الأسطر من المدخل القياسي حتى نهاية المدخل ويرسلها بالتتابع إلى الجلسة (الجلسات) المحددة تمامًا كما لو تم تقديمها كوسائط data لأوامر tcp_send فردية.

يمنع الخيار -n tcp_send من وضع سطر جديد في نهاية سلاسل البيانات.

جميع الخيارات المتبقية تتصرف كما هو الحال بالنسبة لـ tcp_read.

لا يتم معالجة وسائط البيانات بشكل إضافي بمجرد تمريرها إلى tcp_send؛ يتم تمريرها ببساطة إلى print -r.

إذا كانت المعلمة $TCP_OUTPUT عبارة عن سلسلة غير فارغة وكان التسجيل ممكّنًا، فسيتم عرض البيانات المرسلة إلى كل جلسة في ملف السجل (السجلات) مع وجود $TCP_OUTPUT في المقدمة حيثما كان ذلك مناسبًا، بطريقة مشابهة لـ $TCP_PROMPT.

إدارة الجلسات

tcp_alias [ -q ] alias=sess ...
tcp_alias [ -q ] [ alias ... ]
tcp_alias -d [ -q ] alias ...
لم يتم اختبار هذه الدالة بشكل كافٍ.

الشكل الأول ينشئ اسمًا مستعارًا لاسم جلسة؛ يمكن بعد ذلك استخدام alias للإشارة إلى الجلسة الموجودة sess. يمكن سرد العديد من الأسماء المستعارة حسب الحاجة.

الشكل الثاني يسرد أي أسماء مستعارة محددة، أو جميع الأسماء المستعارة إذا لم يتم تحديد أي منها.

الشكل الثالث يحذف جميع الأسماء المستعارة المدرجة. لا تتأثر الجلسات الأساسية.

يقوم الخيار -q بقمع مجموعة مختارة بشكل غير متسق من رسائل الخطأ.

tcp_log [ -asc ] [ -n | -N ] [ logfile ]
مع وسيط logfile، سيتم تسجيل جميع المدخلات المستقبلية من tcp_read في الملف المسماة. ما لم يتم استخدام -a (إلحاق)، سيتم قص هذا الملف أولاً أو إنشاؤه فارغًا. بدون وسائط، يتم عرض الحالة الحالية للتسجيل.

مع الخيار -s، يتم تمكين التسجيل لكل جلسة. يتم إخراج المدخلات من tcp_read إلى الملف logfile.sess. نظرًا لأن الجلسة مميزة تلقائيًا بواسطة اسم الملف، فإن المحتويات تكون خامًا (بدون $TCP_PROMPT). ينطبق الخيار -a كما هو مذكور أعلاه. لا يعتبر التسجيل لكل جلسة وتسجيل جميع البيانات في ملف واحد متعارضين.

الخيار -c يغلق جميع عمليات التسجيل، سواء كانت تامة أو لكل جلسة.

الخياران -n و -N على التوالي إيقاف أو استعادة إخراج البيانات التي قرأتها tcp_read إلى المخرج القياسي؛ وبالتالي فإن `tcp_log -cn' يوقف جميع المخرجات بواسطة tcp_read.

الدالة هي مجرد واجهة مريحة لضبط المعلمات $TCP_LOG، $TCP_LOG_SESS، $TCP_SILENT، والتي سيتم وصفها أدناه.

tcp_rename old new
إعادة تسمية الجلسة old إلى الجلسة new. يصبح الاسم القديم غير صالح.
tcp_sess [ sess [ command [ arg ... ] ] ]
بدون وسائط، يتم سرد جميع الجلسات المفتوحة وواصفات الملفات المرتبطة بها. يتم تمييز الجلسة الحالية بنجمة. للاستخدام في الدوال، قد يكون الوصول المباشر إلى المعلمات $tcp_by_name، $tcp_by_fd و $TCP_SESS أكثر ملاءمة؛ انظر أدناه.

مع وسيط sess، يتم تعيين الجلسة الحالية إلى sess. هذا يعادل تغيير $TCP_SESS مباشرة.

مع وسائط إضافية، يتم تعيين الجلسة الحالية مؤقتًا أثناء تنفيذ `command arg ...'. تتم إعادة تقييم command لتوسيع الأسماء المستعارة وما إلى ذلك، ولكن يتم تمرير arg المتبقية كما تظهر لـ tcp_sess. يتم استعادة الجلسة الأصلية عند خروج tcp_sess.

إدخال/إخراج متقدم

tcp_command send-option ... send-argument ...
هذه واجهة أمامية ملائمة لـ tcp_send. يتم تمرير جميع الوسائط إلى tcp_send، ثم تتوقف الدالة انتظارًا للبيانات. أثناء وصول البيانات كل $TCP_TIMEOUT (افتراضي 0.3) ثانية على الأقل، يتم التعامل مع البيانات وطباعتها وفقًا للإعدادات الحالية. دائمًا ما يتم إرجاع الحالة 0.

هذا مفيد بشكل عام للاستخدام التفاعلي فقط، لمنع تجزئة العرض بسبب المخرجات العائدة من الاتصال. داخل برنامج أو دالة، من الأفضل عمومًا التعامل مع قراءة البيانات بطريقة أكثر وضوحًا.

tcp_expect [ -q ] [ -p var | -P var ] [ -t TO | -T TO ]
[ -a | -s sess | -l sess[,...] ] pattern ...
انتظر المدخلات التي تطابق أيًا من patterns المعطاة من أي من الجلسات المحددة. يتم تجاهل المدخلات حتى يطابق سطر مدخل أحد الأنماط المعطاة؛ عند هذه النقطة، يتم إرجاع الحالة صفر، ويتم تخزين السطر المطابق في $TCP_LINE، ويتم تخزين مجموعة كاملة من الأسطر المقروءة أثناء استدعاء tcp_expect في المصفوفة $tcp_expect_lines.

يتم تحديد الجلسات بنفس طريقة tcp_read: الافتراضي هو استخدام الجلسة الحالية، وإلا فإن الجلسات المحددة بواسطة -a، -s، أو -l تستخدم.

كل pattern هو نمط توسيع globing ممتد قياسي لـ zsh؛ لاحظ أنه يحتاج إلى أن يكون محاطًا بعلامات اقتباس لتجنب توسيعه فورًا بواسطة إنشاء اسم الملف. يجب أن يطابق السطر بالكامل، لذا لمطابقة جزء من السلسلة يجب أن يكون هناك `*' في البداية والنهاية. السطر المطابق يتضمن $TCP_PROMPT المضاف بواسطة tcp_read. من الممكن تضمين علامات globing `#b' أو `#m' في الأنماط لجعل المراجع الخلفية متاحة في المعلمات $MATCH، $match، وما إلى ذلك، كما هو موضح في وثائق zsh الأساسية حول مطابقة الأنماط.

على عكس tcp_read، السلوك الافتراضي لـ tcp_expect هو الانتظار إلى أجل غير مسمى حتى يتم العثور على المدخلات المطلوبة. يمكن تعديل ذلك عن طريق تحديد مهلة باستخدام -t أو -T؛ تعمل هذه كما في tcp_read، وتحدد مهلة لكل قراءة أو مهلة إجمالية، على التوالي، بالثواني، كرقم صحيح أو رقم عشري. كما هو الحال في tcp_read، ترجع الدالة الحالة 2 إذا حدث انتهاء المهلة.

تعود الدالة فورًا بمجرد مطابقة أي من الأنماط المعطاة. إذا احتاج المتصل لمعرفة أي من الأنماط تطابقت، يمكن استخدام الخيار -p var؛ عند العودة، يتم تعيين $var إلى رقم النمط باستخدام فهرسة zsh العادية، أي أن الأول هو 1، وهكذا. لاحظ غياب `$' قبل var. لتجنب التعارض، لا يمكن أن تبدأ المعلمة بـ `_expect'. يتم استخدام الفهرس -1 في حالة انتهاء المهلة و 0 في حالة عدم وجود تطابق.

يعمل الخيار -P var بشكل مشابه لـ -p، ولكن بدلاً من الفهارس الرقمية، يجب أن تبدأ الوسائط العادية ببادئة متبوعة بنقطتين: يتم استخدام هذه البادئة بعد ذلك كعلامة يتم تعيين var إليها عند مطابقة الوسيط. يتم استخدام العلامة timeout في حالة انتهاء المهلة والسلسلة الفارغة في حالة عدم وجود تطابق. لاحظ أنه من المقبول أن تبدأ الوسائط المختلفة بنفس البادئة إذا لم تكن هناك حاجة لتمييز التطابقات.

يتم تمرير الخيار -q مباشرة إلى tcp_read.

نظرًا لأن جميع المدخلات تتم عبر tcp_read، تنطبق جميع القواعد المعتادة حول إخراج الأسطر المقروءة. أحد الاستثناءات هو أن المعلمة $tcp_lines ستعكس فقط السطر الذي تم مطابقته بالفعل بواسطة tcp_expect؛ استخدم $tcp_expect_lines لمجموعة كاملة من الأسطر المقروءة أثناء استدعاء الدالة.

tcp_proxy
هذه دالة بسيطة لقبول اتصال TCP وتنفيذ أمر مع إعادة توجيه الإدخال/الإخراج إلى الاتصال. يجب توخي الحذر الشديد حيث لا يوجد أمان على الإطلاق ويمكن أن يترك جهاز الكمبيوتر الخاص بك مفتوحًا للعالم. من الناحية المثالية، يجب استخدامه فقط خلف جدار ناري.

الوسيط الأول هو منفذ TCP الذي ستستمع عليه الدالة.

تحدد الوسائط المتبقية أمرًا ووسائطه لتنفيذه مع إعادة توجيه المدخل القياسي، والمخرج القياسي، والخطأ القياسي إلى واصف الملف الذي تم قبول جلسة TCP عليه. إذا لم يتم إعطاء أمر، يتم بدء zsh جديد. هذا يمنح كل شخص على شبكتك وصولاً مباشرًا إلى حسابك، وهو ما قد يكون سيئًا في العديد من الحالات.

يتم تشغيل الأمر في الخلفية، لذا يمكن لـ tcp_proxy بعد ذلك قبول اتصالات جديدة. يستمر في قبول اتصالات جديدة حتى يتم مقاطعته.

tcp_spam [ -ertv ] [ -a | -s sess | -l sess[,...] ] cmd [ arg ... ]
تنفيذ `cmd [ arg ... ]' لكل جلسة بالتتابع. لاحظ أن هذا ينفذ الأمر والوسائط؛ فهو لا يرسل سطر الأوامر كبيانات ما لم يكن -t (الإرسال
) .

يمكن تحديد الجلسات بشكل صريح باستخدام الخيارات القياسية -a أو -s أو -l ، أو يمكن اختيارها ضمنيًا. إذا لم يتم تقديم أي من الخيارات الثلاثة ، فإن القواعد هي: أولاً ، إذا تم تعيين المصفوفة $tcp_spam_list ، فيتم اعتبارها قائمة الجلسات ، وإلا يتم أخذ جميع الجلسات. ثانيًا ، تتم إزالة أي جلسات معطاة في المصفوفة $tcp_no_spam_list من قائمة الجلسات.

عادةً ، يتم إرسال أي جلسات تمت إضافتها بواسطة العلامة `-a' أو عند اختيار جميع الجلسات ضمنيًا بترتيب أبجدي ؛ يتم إرسال الجلسات المعطاة بواسطة المصفوفة $tcp_spam_list أو في سطر الأوامر بالترتيب المعطى. العلم -r يعكس الترتيب ، بغض النظر عن كيفية الوصول إليه.

يحدد العلم -v أنه سيتم إخراج $TCP_PROMPT قبل كل جلسة. يتم إخراج هذا بعد أي تعديل لـ TCP_SESS بواسطة الدالة المعرفة من قبل المستخدم tcp_on_spam الموضحة أدناه. (من الواضح أن هذه الدالة قادرة على إنشاء مخرجاتها الخاصة.)

إذا كان الخيار -e موجودًا ، يتم تنفيذ السطر المعطى كـ `cmd [ arg ... ]' باستخدام eval ، وإلا يتم تنفيذه بدون أي معالجة إضافية.

tcp_talk
هذا محاولة بسيطة إلى حد ما لإجبار الإدخال إلى محرر الأسطر على الذهاب مباشرة إلى TCP_SESS الافتراضي.

يتم استخدام سلسلة الهروب ، $TCP_TALK_ESCAPE ، الافتراضية `:' ، للسماح بالوصول إلى تشغيل shell العادي. إذا كانت موجودة بمفردها في بداية السطر ، أو متبوعة بمسافات بيضاء فقط ، يعود محرر الأسطر إلى التشغيل العادي. بخلاف ذلك ، يتم تخطي السلسلة وأي مسافات بيضاء تتبعها ويتم تنفيذ بقية السطر كمدخل shell دون أي تغيير في وضع تشغيل محرر الأسطر.

التنفيذ الحالي يعاني من نقص إلى حد ما فيما يتعلق باستخدام سجل الأوامر. لهذا السبب ، يفضل العديد من المستخدمين استخدام شكل من أشكال النهج البديلة لإرسال البيانات بسهولة إلى الجلسة الحالية. أحد النهج البسيطة هو إنشاء اسم مستعار لحرف خاص معين (مثل `%') إلى `tcp_command --'.

tcp_wait
الحجة الوحيدة هي عدد صحيح أو رقم عشري يمثل الثواني للتأخير. لن يقوم shell بأي شيء خلال تلك الفترة باستثناء الانتظار للإدخال على جميع جلسات TCP عن طريق استدعاء tcp_read -a. هذا مشابه للسلوك التفاعلي عند موجه الأوامر عند تثبيت معالجات zle.

نقل ملف `مرة واحدة'

tcp_point port
tcp_shoot host port
توفر هاتان الوظيفتان طريقة بسيطة لنقل ملف بين مضيفين داخل shell. لاحظ ، مع ذلك ، أن نقل البيانات بكميات كبيرة يتم حاليًا باستخدام cat. تقرأ tcp_point أي بيانات تصل إلى port وترسلها إلى الإخراج القياسي ؛ تتصل tcp_shoot بـ port على host وترسل مدخلاتها القياسية. يمكن استخدام أي port غير مستخدم ؛ الآلية القياسية لاختيار منفذ هي التفكير في رقم عشوائي مكون من أربعة أرقام فوق 1024 حتى يعمل أحدها.

لنقل ملف من المضيف woodcock إلى المضيف springes ، على springes:

tcp_point 8091 >output_file

وعلى woodcock:

tcp_shoot springes 8091 <input_file

نظرًا لأن هاتين الوظيفتين لا تتطلبان tcp_open لإعداد اتصال TCP أولاً ، فقد تحتاجان إلى تحميلهما بشكل منفصل.

الوظائف المعرفة من قبل المستخدم TCP

سيتم استدعاء بعض الوظائف ، إذا عرفها المستخدم ، بواسطة نظام الوظائف في سياقات معينة. يعتمد هذا المرفق على الوحدة zsh/parameter ، وهي متاحة عادة في shells التفاعلية لأن نظام الإكمال يعتمد عليها. لا تحتاج أي من الوظائف إلى تعريفها ؛ إنها توفر ببساطة نقاط ربط ملائمة عند الضرورة.

عادةً ، يتم استدعاء هذه بعد اتخاذ الإجراء المطلوب ، بحيث تعكس المعلمات المختلفة الحالة الجديدة.

tcp_on_alias alias fd
عند تعريف اسم مستعار ، سيتم استدعاء هذه الوظيفة بحجتين: اسم الاسم المستعار ، وموجه الملف للجلسة المقابلة.
tcp_on_awol sess fd
إذا كانت الوظيفة tcp_fd_handler تعالج الإدخال من محرر الأسطر وتكتشف أن موجه الملف لم يعد قابلاً لإعادة الاستخدام ، فإنها تقوم افتراضيًا بإزالته من قائمة مواجهات الملفات التي تتعامل معها هذه الطريقة وتطبع رسالة. إذا تم تعريف الوظيفة tcp_on_awol ، فسيتم استدعاؤها قبل هذه النقطة مباشرة. يمكنها إرجاع الحالة 100 ، مما يشير إلى أنه يجب إجراء المعالجة العادية ؛ أي حالة إرجاع أخرى تشير إلى أنه لا يجب اتخاذ أي إجراء إضافي ويجب على tcp_fd_handler العودة فورًا بالحالة المعطاة. عادةً ما يكون إجراء tcp_on_awol هو إغلاق الجلسة.

سيكون المتغير TCP_INVALIDATE_ZLE سلسلة غير فارغة إذا كان من الضروري إلغاء صلاحية عرض محرر الأسطر باستخدام `zle -I' قبل طباعة الإخراج من الوظيفة.

(`AWOL' هو مصطلح عسكري يعني `غائب بدون إجازة' أو أي اختلاف. ليس له معنى تقني سابق موجود معروف للمؤلف.)

tcp_on_close sess fd
يتم استدعاء هذه الوظيفة باسم جلسة يتم إغلاقها وموجه الملف الذي يتوافق مع تلك الجلسة. كلاهما سيكون غير صالح بحلول الوقت الذي يتم فيه استدعاء الوظيفة.
tcp_on_open sess fd
يتم استدعاء هذه الوظيفة بعد تعريف جلسة جديدة باسم الجلسة وموجه الملف كحجتين. إذا أعادت حالة غير صفرية ، فمن المفترض أن يفشل فتح الجلسة ويتم إغلاق الجلسة مرة أخرى ؛ ومع ذلك ، سيستمر tcp_open في محاولة فتح أي جلسات متبقية معطاة في سطر الأوامر.
tcp_on_rename oldsess fd newsess
يتم استدعاء هذه الوظيفة بعد إعادة تسمية جلسة بالحجج الثلاث: اسم الجلسة القديم ، وموجه الملف ، واسم الجلسة الجديد.
tcp_on_spam sess command ...
يتم استدعاء هذه الوظيفة مرة واحدة لكل جلسة يتم إرسالها ، قبل تنفيذ أمر لجلسة بواسطة tcp_spam. الحجج هي اسم الجلسة متبوعًا بقائمة الأوامر التي سيتم تنفيذها. إذا تم استدعاء tcp_spam مع الخيار -t ، فسيكون الأمر الأول هو tcp_send.

يتم استدعاء هذه الوظيفة بعد تعيين $TCP_SESS ليعكس الجلسة المراد إرسالها ، ولكن قبل استخدامها. لذلك من الممكن تعديل قيمة $TCP_SESS داخل هذه الوظيفة. على سبيل المثال ، يمكن أن تتضمن حجج الجلسة لـ tcp_spam معلومات إضافية ليتم تجريدها ومعالجتها في tcp_on_spam.

إذا قامت الوظيفة بتعيين المعلمة $REPLY إلى `done'، فلن يتم تنفيذ سطر الأوامر ؛ بالإضافة إلى ذلك ، لن يتم طباعة موجه للخيار -v لـ tcp_spam.

tcp_on_unalias alias fd
يتم استدعاء هذه الوظيفة باسم اسم مستعار وموجه الملف المقابل للجلسة بعد حذف اسم مستعار.

وظائف الأداة المساعدة TCP

الوظائف التالية تستخدمها نظام وظائف TCP ولكن نادرًا ما تحتاج إلى استدعائها مباشرة.

tcp_fd_handler
هذه هي الوظيفة التي تم تثبيتها بواسطة tcp_open للتعامل مع الإدخال من داخل محرر الأسطر ، إذا كان ذلك مطلوبًا. وهي بالتنسيق الموثق لـ `zle -F' المدمج في zshzle(1) .

أثناء النشاط ، تقوم الوظيفة بتعيين المعلمة TCP_HANDLER_ACTIVE إلى 1. هذا يسمح لشفرة shell المستدعاة داخليًا (على سبيل المثال ، عن طريق تعيين tcp_on_read) بمعرفة ما إذا كانت تُستدعى عندما يكون shell خاملاً بخلاف ذلك عند موجه المحرر.

tcp_output [ -q ] -P prompt -F fd -S sess
تستخدم هذه الوظيفة لتسجيل المخرجات والتعامل معها إلى الإخراج القياسي ، من داخل tcp_read و (إذا تم تعيين $TCP_OUTPUT) tcp_send.

الموجه prompt المراد استخدامه محدد بواسطة -P ؛ الافتراضي هو السلسلة الفارغة. يمكن أن يحتوي على:

%c
يتوسع إلى 1 إذا كانت الجلسة هي الجلسة الحالية ، وإلا 0. يستخدم مع تعبيرات ثلاثية مثل `%(c.-.+)' لإخراج `+' للجلسة الحالية و `-' بخلاف ذلك.
%f
يتم استبداله بموجه ملف الجلسة.
%s
يتم استبداله باسم الجلسة.
%%
يتم استبداله بـ `%' واحد.

الخيار -q يمنع الإخراج إلى الإخراج القياسي ، ولكن ليس إلى أي ملفات سجل تم تكوينها.

تستخدم الخيارين -S و -F لتمرير اسم الجلسة وموجه الملف للاستبدال المحتمل في الموجه.

معلمات المستخدم TCP

تتبع المعلمات الاصطلاح المعتاد بأن الأحرف الكبيرة تستخدم للقيم العددية والأعداد الصحيحة ، بينما تستخدم الأحرف الصغيرة للمصفوفات العادية والمصفوفات الترابطية. من الآمن دائمًا لشفرة المستخدم قراءة هذه المعلمات. يمكن أيضًا تعيين بعض المعلمات ؛ هذه مذكورة بشكل صريح. يتم تضمين المعلمات الأخرى في هذه المجموعة حيث يتم تعيينها بواسطة نظام الوظائف لصالح المستخدم ، أي أن تعيينها عادةً ما يكون غير مفيد ولكنه غير ضار.

من المفيد غالبًا أيضًا جعل المعلمات القابلة للتعيين محلية لوظيفة. على سبيل المثال ، `local TCP_SILENT=1' تحدد أن البيانات المقروءة أثناء استدعاء الوظيفة لن تتم طباعتها إلى الإخراج القياسي ، بغض النظر عن الإعداد خارج الوظيفة. وبالمثل ، `local TCP_SESS=sess' تعين جلسة لـ

duration of a function, and `local TCP_PROMPT=' specifies that no prompt is used for input during the function.

tcp_expect_lines
Array. The set of lines read during the last call to tcp_expect, including the last ($TCP_LINE).
tcp_filter
Array. May be set directly. A set of extended globbing patterns which, if matched in tcp_output, will cause the line not to be printed to standard output. The patterns should be defined as described for the arguments to tcp_expect. Output of line to log files is not affected.
TCP_HANDLER_ACTIVE
Scalar. Set to 1 within tcp_fd_handler to indicate to functions called recursively that they have been called during an editor session. Otherwise unset.
TCP_LINE
The last line read by tcp_read, and hence also tcp_expect.
TCP_LINE_FD
The file descriptor from which $TCP_LINE was read. ${tcp_by_fd[$TCP_LINE_FD]} will give the corresponding session name.
tcp_lines
Array. The set of lines read during the last call to tcp_read, including the last ($TCP_LINE).
TCP_LOG
May be set directly, although it is also controlled by tcp_log. The name of a file to which output from all sessions will be sent. The output is proceeded by the usual $TCP_PROMPT. If it is not an absolute path name, it will follow the user's current directory.
TCP_LOG_SESS
May be set directly, although it is also controlled by tcp_log. The prefix for a set of files to which output from each session separately will be sent; the full filename is ${TCP_LOG_SESS}.sess. Output to each file is raw; no prompt is added. If it is not an absolute path name, it will follow the user's current directory.
tcp_no_spam_list
Array. May be set directly. See tcp_spam for how this is used.
TCP_OUTPUT
May be set directly. If a non-empty string, any data sent to a session by tcp_send will be logged. This parameter gives the prompt to be used in a file specified by $TCP_LOG but not in a file generated from $TCP_LOG_SESS. The prompt string has the same format as TCP_PROMPT and the same rules for its use apply.
TCP_PROMPT
May be set directly. Used as the prefix for data read by tcp_read which is printed to standard output or to the log file given by $TCP_LOG, if any. Any `%s', `%f' or `%%' occurring in the string will be replaced by the name of the session, the session's underlying file descriptor, or a single `%', respectively. The expression `%c' expands to 1 if the session being read is the current session, else 0; this is most useful in ternary expressions such as `%(c.-.+)' which outputs `+' if the session is the current one, else `-'.

If the prompt starts with %P, this is stripped and the complete result of the previous stage is passed through standard prompt %-style formatting before being output.

TCP_READ_DEBUG
May be set directly. If this has non-zero length, tcp_read will give some limited diagnostics about data being read.
TCP_SECONDS_START
This value is created and initialised to zero by tcp_open.

The functions tcp_read and tcp_expect use the shell's SECONDS parameter for their own timing purposes. If that parameter is not of floating point type on entry to one of the functions, it will create a local parameter SECONDS which is floating point and set the parameter TCP_SECONDS_START to the previous value of $SECONDS. If the parameter is already floating point, it is used without a local copy being created and TCP_SECONDS_START is not set. As the global value is zero, the shell elapsed time is guaranteed to be the sum of $SECONDS and $TCP_SECONDS_START.

This can be avoided by setting SECONDS globally to a floating point value using `typeset -F SECONDS'; then the TCP functions will never make a local copy and never set TCP_SECONDS_START to a non-zero value.

TCP_SESS
May be set directly. The current session; must refer to one of the sessions established by tcp_open.
TCP_SILENT
May be set directly, although it is also controlled by tcp_log. If of non-zero length, data read by tcp_read will not be written to standard output, though may still be written to a log file.
tcp_spam_list
Array. May be set directly. See the description of the function tcp_spam for how this is used.
TCP_TALK_ESCAPE
May be set directly. See the description of the function tcp_talk for how this is used.
TCP_TIMEOUT
May be set directly. Currently this is only used by the function tcp_command, see above.

TCP USER-DEFINED PARAMETERS

The following parameters are not set by the function system, but have a special effect if set by the user.

tcp_on_read
This should be an associative array; if it is not, the behaviour is undefined. Each key is the name of a shell function or other command, and the corresponding value is a shell pattern (using EXTENDED_GLOB). Every line read from a TCP session directly or indirectly using tcp_read (which includes lines read by tcp_expect) is compared against the pattern. If the line matches, the command given in the key is called with two arguments: the name of the session from which the line was read, and the line itself.

If any function called to handle a line returns a non-zero status, the line is not output. Thus a tcp_on_read handler containing only the instruction `return 1' can be used to suppress output of particular lines (see, however, tcp_filter above). However, the line is still stored in TCP_LINE and tcp_lines; this occurs after all tcp_on_read processing.

TCP UTILITY PARAMETERS

These parameters are controlled by the function system; they may be read directly, but should not usually be set by user code.

tcp_aliases
Associative array. The keys are the names of sessions established with tcp_open; each value is a space-separated list of aliases which refer to that session.
tcp_by_fd
Associative array. The keys are session file descriptors; each value is the name of that session.
tcp_by_name
Associative array. The keys are the names of sessions; each value is the file descriptor associated with that session.

TCP EXAMPLES

Here is a trivial example using a remote calculator.

To create a calculator server on port 7337 (see the dc manual page for quite how infuriating the underlying command is):

tcp_proxy 7337 dc

To connect to this from the same host with a session also named `dc':

tcp_open localhost 7337 dc

To send a command to the remote session and wait a short while for output (assuming dc is the current session):

tcp_command 2 4 + p

To close the session:

tcp_close

The tcp_proxy needs to be killed to be stopped. Note this will not usually kill any connections which have already been accepted, and also that the port is not immediately available for reuse.

The following chunk of code puts a list of sessions into an xterm header, with the current session followed by a star.

print -n "\033]2;TCP:" ${(k)tcp_by_name:/$TCP_SESS/$TCP_SESS\*} "\a"

TCP BUGS

The function tcp_read uses the shell's normal read builtin. As this reads a complete line at once, data arriving without a terminating newline can cause the function to block indefinitely.

Though the function suite works well for interactive use and for data arriving in small amounts, the performance when large amounts of data are being exchanged is likely to be extremely poor.
