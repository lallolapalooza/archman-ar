EINTR

نظام الملفات لا يدعم العلامة O_DIRECT. انظر ملاحظات لمزيد من المعلومات.
EINVAL
قيمة غير صالحة في flags.
EINVAL
تم تحديد O_TMPFILE في flags، ولكن لم يتم تحديد أي من O_WRONLY أو O_RDWR.
EINVAL
تم تحديد كل من O_CREAT و O_DIRECTORY في flags، وإصدار نواة لينكس هو 6.4 أو أحدث. (النوى الأقدم كانت غير متسقة في هذا المجال، ولا يحدد POSIX السلوك.)

EINVAL
المكون الأخير ("اسم الأساس") للملف path غير صالح (على سبيل المثال، يحتوي على أحرف غير مسموح بها بواسطة نظام الملفات الأساسي).
EISDIR
يشير path إلى دليل وتم تضمين الكتابة في الوصول المطلوب (أي، تم تعيين O_WRONLY أو O_RDWR).
EISDIR
يشير path إلى دليل موجود، وتم تحديد O_TMPFILE وأحد O_WRONLY أو O_RDWR في flags، ولكن إصدار النواة هذا لا يوفر وظيفة O_TMPFILE.

تم العثور على عدد كبير جدًا من الروابط الرمزية أثناء تحليل path.

كان path رابطًا رمزيًا، وحدد flags O_NOFOLLOW ولكن ليس O_PATH.

الإصدارات

يختلف التأثير (غير المحدد) لـ O_RDONLY | O_TRUNC بين التطبيقات. على العديد من الأنظمة، يتم اقتطاع الملف فعليًا.

عمليات الإدخال/الإخراج المتزامنة

يحدد خيار "عمليات الإدخال/الإخراج المتزامنة" في POSIX.1-2008 اختلافات مختلفة لعمليات الإدخال/الإخراج المتزامنة، ويحدد علامات open() O_SYNC، O_DSYNC، و O_RSYNC للتحكم في السلوك. بغض النظر عما إذا كان التطبيق يدعم هذا الخيار، يجب أن يدعم على الأقل استخدام O_SYNC للملفات العادية.

يطبق لينكس O_SYNC و O_DSYNC، ولكن ليس O_RSYNC. بشكل غير صحيح إلى حد ما، يعرف glibc O_RSYNC بأن له نفس قيمة O_SYNC. (تم تعريف O_RSYNC في ملف رأس لينكس <asm/fcntl.h> على HP PA-RISC، ولكنه لا يستخدم.)

توفر O_SYNC اكتمال سلامة الملف المتزامنة لعمليات الإدخال/الإخراج، مما يعني أن عمليات الكتابة ستدفع البيانات وجميع البيانات الوصفية المرتبطة بها إلى الأجهزة الأساسية. توفر O_DSYNC اكتمال سلامة بيانات الإدخال/الإخراج المتزامنة، مما يعني أن عمليات الكتابة ستدفع البيانات إلى الأجهزة الأساسية، ولكنها ستدفع فقط تحديثات البيانات الوصفية اللازمة للسماح لعملية قراءة لاحقة بالنجاح. يمكن أن يقلل اكتمال سلامة البيانات من عدد عمليات القرص المطلوبة للتطبيقات التي لا تحتاج إلى ضمانات اكتمال سلامة الملف.

لفهم الفرق بين نوعي الاكتمال، ضع في اعتبارك قطعتين من البيانات الوصفية للملف: آخر وقت تعديل للملف (st_mtime) وطول الملف. ستحدث جميع عمليات الكتابة تحديثًا لآخر وقت تعديل للملف، ولكن فقط الكتابات التي تضيف بيانات إلى نهاية الملف ستغير طول الملف. لا يلزم تعديل وقت آخر تعديل لضمان نجاح عملية قراءة، ولكن طول الملف ضروري. وبالتالي، تضمن O_DSYNC فقط دفع التحديثات إلى البيانات الوصفية لطول الملف (بينما ستدفع O_SYNC دائمًا تحديثات البيانات الوصفية لوقت آخر تعديل أيضًا).

قبل لينكس 2.6.33، كان لينكس يطبق فقط علامة O_SYNC لـ open(). ومع ذلك، عند تحديد هذه العلامة، قدمت معظم أنظمة الملفات في الواقع ما يعادل اكتمال سلامة بيانات الإدخال/الإخراج المتزامنة (أي، تم تنفيذ O_SYNC فعليًا بما يعادل O_DSYNC).

منذ لينكس 2.6.33، تم توفير دعم O_SYNC المناسب. ومع ذلك، لضمان التوافق الثنائي الرجعي، تم تعريف O_DSYNC بنفس قيمة O_SYNC التاريخية، وتم تعريف O_SYNC كقيمة علامة جديدة (ثنائية البت) تتضمن قيمة علامة O_DSYNC. هذا يضمن أن التطبيقات التي تم تجميعها مقابل رؤوس جديدة تحصل على الأقل على دلالات O_DSYNC قبل لينكس 2.6.33.

الاختلافات بين مكتبة C والنواة

منذ glibc 2.26، تستخدم وظيفة التغليف glibc لـ open() استدعاء النظام openat()، بدلاً من استدعاء النظام open() الخاص بالنواة. بالنسبة لمعماريا معينة، هذا صحيح أيضًا قبل glibc 2.26.

NAME

openat, openat2 - فتح ملف أو جهاز (مع خيارات إضافية)

LIBRARY

التيار القياسي C library (libc، libucrt)

SYNOPSIS

#define _GNU_SOURCE
#include <fcntl.h>

int openat(int dirfd, const char *pathname, int flags);
int openat(int dirfd, const char *pathname, int flags, mode_t mode);
int openat2(int dirfd, const char *pathname,
            const struct open_how *openhow, size_t setsize);

DESCRIPTION

These system calls are used to open a file or device. The openat() system call is similar to open(2), but with the added behavior that the file named by the pathname operand is resolved relative to the directory referred to by the file descriptor dirfd. If pathname is relative, then it is interpreted relative to dirfd (or the current directory if dirfd is AT_FDCWD). If pathname is absolute, then dirfd is ignored.

If pathname is empty, then openat() behaves identically to dup(2), returning a new file descriptor referring to the same open file description as the one referred to by dirfd.

The openat2() system call is a more flexible interface that allows more control over how the file is opened. It takes a pointer to a structure open_how, which contains a list of flags and attributes that specify how to open the file. The openhow structure is defined as follows:

struct open_how {
    unsigned int flags;      /* Flags for openat() */
    unsigned long long mode; /* Mode for file creation */
    int_t promisc;           /* Placeholder for future extensions */
};

The flags field contains flags similar to those used by openat(). The mode field specifies the mode for file creation if the O_CREAT flag is specified. The promisc field is reserved for future extensions.

The following flags can be passed in flags (and in the open_how.flags field):

O_ACCMODE
Mask for the file access modes. This is the bitwise OR of O_RDONLY, O_WRONLY, and O_RDWR.
O_DIRECTORY
If this flag is specified, the system call will only succeed if the specified pathname refers to a directory. If the pathname refers to anything else, the call will fail with the error ENOTDIR. This flag can be combined with O_NOFOLLOW.
O_DSYNC
Write I/O is to occur at a rate that will make data updates visible to other retrievals of that data by those same means that will use that new data at a rate that will cause them to be updated also. Write I/O or data updates to the file are performed only when the system considers it necessary to make the file's content be updated.
O_EXCL
If O_CREAT is specified, and the file exists, then open() will fail. The O_EXCL flag can only be used if the pathname refers to a regular file. This flag is intended to be used to create new files atomically. Otherwise, the system may not be able to guarantee atomicity. If O_EXCL is used with O_CREAT on a symbolic link, the call fails with EEXIST.
O_FILE_CLOEXEC
Obsolete. Use O_CLOEXEC.
O_FIND_ செயல
This flag is not in the C standard. It is used by some programs like find(1) to signify that the file should be deleted after it is closed. This is not a standard flag and should not be used in portable code.
O_NDELAY
Same as O_NONBLOCK.
O_NOATIME
Do not update access timestamps. When this flag is used, the atime for a file is not change when the file is read. This can be useful for performance reasons.
O_NOCTTY
If pathname refers to a terminal device, opening the terminal will not cause the process controlling the terminal to be associated with the terminal. If the process has no controlling terminal, then the newly opened terminal becomes the process's controlling terminal. This flag is not useful on its own, but it is useful for programs that open terminals for specific purposes, such as daemons, that should not be associated with the controlling terminal.
O_NOFOLLOW
Do not follow symbolic links. If the pathname is a symbolic link, then the system call will return an error (ELOOP) instead of the file pointed to by the symbolic link.
O_NONBLOCK
When opening a device driver file, this flag prevents the O_RDONLY, O_WRONLY, or O_RDWR flags from being used to block the calling process until the device is ready or available. If the device is not ready or available, the call will fail immediately with an error. This flag can be useful for non-blocking I/O operations.
O_PATH
Obtain a file descriptor that can be used with file descriptor passing operations (e.g. sendfile(2), splice(2)). The file descriptor obtained is not a regular file descriptor; it cannot be used for read, write, or seek operations. It can be used only to pass to other system calls that support the O_PATH flag.
O_RDONLY
Open for reading only.
O_RDWR
Open for reading and writing.
O_SYNC
Synchronous I/O for file data. This flag requests that the system perform I/O operations in such a way that all data and necessary metadata are written to the underlying storage device before the system call returns. This ensures that the data is persistently stored.
O_TMPFILE
Create a temporary file. This flag can only be used with O_DIRECTORY and O_WRONLY. The file is created in the directory referred to by dirfd and is deleted when the last file descriptor referring to it is closed. If pathname is not NULL, it must refer to a directory. If pathname is NULL, the temporary file is created in the current directory.
O_TRUNC
If the file exists and is opened for writing, truncate its length to 0 in this call. The O_TRUNC flag has no effect if the file is not opened for writing. This flag can be combined with O_RDWR or O_WRONLY.
O_WRONLY
Open for writing only.

The mode argument specifies the file permission bits to be set for the new file if O_CREAT is specified. It is ANDed with the process's umask value. See chmod(2) for more details.

The O_DIRECT flag can be used to perform direct I/O. When this flag is used, data is transferred directly between the user buffer and the underlying storage device, bypassing the page cache. This can improve performance for certain workloads, but it also imposes stricter alignment requirements on the buffer address and I/O segment size.

Alignment restrictions can only be assumed from known characteristics of the filesystem, the individual file, the underlying storage device(s), and the kernel version. In Linux 2.4, most filesystems based on block devices require that the file offset and the length and memory address of all I/O segments be multiples of the filesystem block size (typically 4096 bytes). In Linux 2.6.0, this was relaxed to the logical block size of the block device (typically 512 bytes). A block device's logical block size can be determined using the ioctl(2) BLKSSZGET operation or from the shell using the command:


blockdev --getss

O_DIRECT I/Os should never be run concurrently with the fork(2) system call, if the memory buffer is a private mapping (i.e., any mapping created with the mmap(2) MAP_PRIVATE flag; this includes memory allocated on the heap and statically allocated buffers). Any such I/Os, whether submitted via an asynchronous I/O interface or from another thread in the process, should be completed before fork(2) is called. Failure to do so can result in data corruption and undefined behavior in parent and child processes. This restriction does not apply when the memory buffer for the O_DIRECT I/Os was created using shmat(2) or mmap(2) with the MAP_SHARED flag. Nor does this restriction apply when the memory buffer has been advised as MADV_DONTFORK with madvise(2), ensuring that it will not be available to the child after fork(2).

The O_DIRECT flag was introduced in SGI IRIX, where it has alignment restrictions similar to those of Linux 2.4. IRIX has also a fcntl(2) call to query appropriate alignments, and sizes. FreeBSD 4.x introduced a flag of the same name, but without alignment restrictions.

O_DIRECT support was added in Linux 2.4.10. Older Linux kernels simply ignore this flag. Some filesystems may not implement the flag, in which case open() fails with the error EINVAL if it is used.

Applications should avoid mixing O_DIRECT and normal I/O to the same file, and especially to overlapping byte regions in the same file. Even when the filesystem correctly handles the coherency issues in this situation, overall I/O throughput is likely to be slower than using either mode alone. Likewise, applications should avoid mixing mmap(2) of files with direct I/O to the same files.

The behavior of O_DIRECT with NFS will differ from local filesystems. Older kernels, or kernels configured in certain ways, may not support this combination. The NFS protocol does not support passing the flag to the server, so O_DIRECT I/O will bypass the page cache only on the client; the server may still cache the I/O. The client asks the server to make the I/O synchronous to preserve the synchronous semantics of O_DIRECT. Some servers will perform poorly under these circumstances, especially if the I/O size is small. Some servers may also be configured to lie to clients about the I/O having reached stable storage; this will avoid the performance penalty at some risk to data integrity in the event of server power failure. The Linux NFS client places no alignment restrictions on O_DIRECT I/O.

In summary, O_DIRECT is a potentially powerful tool that should be used with caution. It is recommended that applications treat use of O_DIRECT as a performance option which is disabled by default.

RETURN VALUE

On success, these system calls return the new file descriptor. On error, they return -1, and errno is set to indicate the error.

ERRORS

In addition to the standard file access errors, the following may occur:

EACCES
The requested access to the file is not allowed, or for openat() with O_CREAT, the requested permissions are not allowed.
EADDRINUSE
The O_CREAT and O_EXCL flags are specified, and the file already exists, and the file is a socket.
EBADF
The dirfd argument is not a valid file descriptor, or pathname is relative and dirfd is not a directory. Or, O_TMPFILE is specified, and dirfd refers to a file descriptor of a type other than a directory.
EBUSY
The file pathname refers to a device that is busy.
ECHILD
A signal occurred while opening the file.
EDEADLK
O_CREAT and O_EXCL are specified, and the file already exists. Or, a deadlock was detected.
EEXIST
O_CREAT and O_EXCL are specified, and the file already exists. Or, O_EXCL is used with O_CREAT on a symbolic link.
EINTR
The call was interrupted by a signal.
EINVAL
Invalid value for flags or mode. Or, O_TMPFILE is specified without O_DIRECTORY. Or, the filesystem does not support O_DIRECT or O_TMPFILE.
EISDIR
The name pathname refers to a directory, and the access requested includes writing or is O_WRONLY or O_RDWR.
ELOOP
pathname contains a symbolic link loop, or O_NOFOLLOW was specified and pathname was a symbolic link.
EMFILE
The process has reached its limit for the number of open file descriptors.
EMLINK
The file referred to by pathname has too many links.
ENAMETOOLONG
pathname is too long.
ENFILE
The system-wide limit on the total number of open files has been reached.
ENOENT
pathname does not exist and O_CREAT was not specified. Or, O_TMPFILE was specified, and pathname is NULL, and dirfd does not refer to a directory.
ENOMEM
Insufficient kernel memory was available.
ENOSPC
O_CREAT was specified, but the device containing pathname has no room for the file.
ENOTDIR
pathname is not a directory, and O_DIRECTORY
ENXIO
A non-existent physical name was specified, or the device or attribute referred to by pathname does not exist.
EOVERFLOW
The file is a regular file or symbolic link, and the size of the file or the number of hard links on the file exceeds the maximum value that can be represented in the file's inode.
EROFS
The named file resides on a read-only filesystem, and was opened for writing.
ETXTBSY
The file is a regular file that is being executed. This error is returned only when the file is opened with O_RDWR or O_WRONLY. This flag is used by some programs like vi(1) to indicate that the file is being edited. It is not a standard flag and should not be used in portable code.
EXDEV
A pathname was specified that referred to a file on another filesystem, and the requested operation requires that the file remain on the same filesystem.

VERSIONS

openat() was added in Linux kernel 2.6.16. openat2() was added in Linux kernel 5.12.

STANDARDS

openat() is specified by POSIX.1-2008.

openat2() is a Linux-specific extension.

HISTORY

The O_DIRECT flag was introduced in SGI IRIX. FreeBSD 4.x introduced a flag of the same name, but without alignment restrictions.

Support for O_DIRECT was added in Linux kernel 2.4.10.

The O_TMPFILE flag was introduced in Linux kernel 3.11.

NOTES

The openat() system call and the other file descriptor passing methods are useful for writing programs that handle file paths correctly. They are particularly useful for writing programs that do not follow symbolic links, or that operate in directories that are modified by other processes. They are also useful for writing programs that need to avoid race conditions when opening files.

The O_DIRECT flag bypasses the kernel's page cache. This can improve performance for certain applications, such as database systems, but it can also lead to performance degradation if not used carefully. The alignment requirements for O_DIRECT I/O are typically stricter than for normal I/O. The offset and size of I/O operations, as well as the memory address of the buffer, must be aligned to the logical block size of the underlying storage device.

Applications should avoid mixing O_DIRECT and normal I/O to the same file, and especially to overlapping byte regions in the same file. Even when the filesystem correctly handles the coherency issues in this situation, overall I/O throughput is likely to be slower than using either mode alone. Likewise, applications should avoid mixing mmap(2) of files with direct I/O to the same files.

The behavior of O_DIRECT with NFS will differ from local filesystems. Older kernels, or kernels configured in certain ways, may not support this combination. The NFS protocol does not support passing the flag to the server, so O_DIRECT I/O will bypass the page cache only on the client; the server may still cache the I/O. The client asks the server to make the I/O synchronous to preserve the synchronous semantics of O_DIRECT. Some servers will perform poorly under these circumstances, especially if the I/O size is small. Some servers may also be configured to lie to clients about the I/O having reached stable storage; this will avoid the performance penalty at some risk to data integrity in the event of server power failure. The Linux NFS client places no alignment restrictions on O_DIRECT I/O.

In summary, O_DIRECT is a potentially powerful tool that should be used with caution. It is recommended that applications treat use of O_DIRECT as a performance option which is disabled by default.

BUGS

Currently, it is not possible to enable signal-driven I/O by specifying O_ASYNC when calling open(); use fcntl(2) to enable this flag.

One must check for two different error codes, EISDIR and ENOENT, when trying to determine whether the kernel supports O_TMPFILE functionality.

مكتبة C القياسية (libc، libucrt)

#define _GNU_SOURCE

int openat(int dirfd, const char *pathname, int flags);

الوصف

تُستخدم استدعاءات النظام هذه لفتح ملف أو جهاز. استدعاء النظام openat() مشابه لـ open(2)، ولكنه يحتوي على سلوك إضافي وهو أن المسار المحدد بواسطة المعامل pathname يتم حله بالنسبة للدليل المشار إليه بواسطة واصف الملف dirfd. إذا كان pathname نسبيًا، فسيتم تفسيره بالنسبة لـ dirfd (أو الدليل الحالي إذا كان dirfd هو AT_FDCWD). إذا كان pathname مطلقًا، فسيتم تجاهل dirfd.

إذا كان pathname فارغًا، فإن openat() يعمل بشكل مطابق لـ dup(2)، ويعيد واصف ملف جديد يشير إلى نفس وصف الملف المفتوح الذي يشير إليه dirfd.

استدعاء النظام openat2() هو واجهة أكثر مرونة تسمح بمزيد من التحكم في كيفية فتح الملف. يأخذ مؤشرًا إلى بنية open_how، والتي تحتوي على قائمة بالأعلام والسمات التي تحدد كيفية فتح الملف. تم تعريف بنية open_how على النحو التالي:

struct open_how {
    unsigned int flags;      /* Flags for openat() */
    unsigned long long mode; /* Mode for file creation */
    int_t promisc;           /* Placeholder for future extensions */
};

يحتوي حقل flags على أعلام مشابهة لتلك المستخدمة بواسطة openat(). يحدد حقل mode الوضع لإنشاء الملف إذا تم تحديد العلم O_CREAT. حقل promisc محجوز للتوسعات المستقبلية.

يمكن تمرير الأعلام التالية في flags (وفي حقل open_how.flags):

O_ACCMODE
قناع لوضعيات الوصول إلى الملف. هذا هو OR البتي لـ O_RDONLY و O_WRONLY و O_RDWR.
O_DIRECTORY
إذا تم تحديد هذا العلم، فسينجح استدعاء النظام فقط إذا كان المسار المحدد يشير إلى دليل. إذا كان المسار يشير إلى أي شيء آخر، فسيفشل الاستدعاء بالخطأ ENOTDIR. يمكن دمج هذا العلم مع O_NOFOLLOW.
O_DSYNC
يجب أن تحدث عمليات الإدخال/الإخراج للكتابة بمعدل يجعل تحديثات البيانات مرئية لاسترجاعها بنفس الوسائل التي تستخدم تلك البيانات الجديدة، بنفس المعدل الذي يجعلها تُحدث أيضًا. يتم إجراء عمليات الإدخال/الإخراج للكتابة أو تحديثات البيانات للملف فقط عندما تعتبرها النظام ضرورية لتحديث محتوى الملف.
O_EXCL
إذا تم تحديد O_CREAT، وكان الملف موجودًا، فسيفشل open(). يمكن استخدام العلم O_EXCL فقط إذا كان pathname يشير إلى ملف عادي. هذا العلم مخصص لإنشاء ملفات جديدة بشكل ذري. بخلاف ذلك، قد لا يتمكن النظام من ضمان الذرية. إذا تم استخدام O_EXCL مع O_CREAT على رابط رمزي، فسيفشل الاستدعاء مع EEXIST.
O_FILE_CLOEXEC
مهمل. استخدم O_CLOEXEC.
O_FIND_ செயல
هذا العلم ليس في معيار C. تستخدمه بعض البرامج مثل find(1) للإشارة إلى أنه يجب حذف الملف بعد إغلاقه. هذا ليس علمًا قياسيًا ولا يجب استخدامه في التعليمات البرمجية المحمولة.
O_NDELAY
نفس O_NONBLOCK.
O_NOATIME
لا تقم بتحديث طوابع الوصول. عند استخدام هذا العلم، لا يتم تغيير atime للملف عند قراءة الملف. يمكن أن يكون هذا مفيدًا لأسباب الأداء.
O_NOCTTY
إذا كان pathname يشير إلى جهاز طرفي، فلن يؤدي فتح الجهاز الطرفي إلى ربط العملية التي تتحكم في الجهاز الطرفي به. إذا لم يكن لدى العملية جهاز طرفي متحكم، فس يصبح الجهاز الطرفي الذي تم فتحه حديثًا هو الجهاز الطرفي المتحكم في العملية. هذا العلم ليس مفيدًا بمفرده، ولكنه مفيد للبرامج التي تفتح أجهزة طرفية لأغراض محددة، مثل الشياطين، التي لا ينبغي ربطها بالجهاز الطرفي المتحكم.
O_NOFOLLOW
لا تتبع الروابط الرمزية. إذا كان المسار رابطًا رمزيًا، فسيعيد استدعاء النظام خطأ (ELOOP) بدلاً من الملف الذي يشير إليه الرابط الرمزي.
O_NONBLOCK
عند فتح ملف مشغل جهاز، يمنع هذا العلم استخدام الأعلام O_RDONLY أو O_WRONLY أو O_RDWR من حظر العملية المستدعية حتى يصبح الجهاز جاهزًا أو متاحًا. إذا لم يكن الجهاز جاهزًا أو متاحًا، فسيفشل الاستدعاء فورًا بخطأ. يمكن أن يكون هذا العلم مفيدًا لعمليات الإدخال/الإخراج غير المانعة.
O_PATH
احصل على واصف ملف يمكن استخدامه مع عمليات تمرير واصف الملف (مثل sendfile(2)، splice(2)). واصف الملف الذي تم الحصول عليه ليس واصف ملف عادي؛ لا يمكن استخدامه لعمليات القراءة أو الكتابة أو البحث. يمكن استخدامه فقط لتمريره إلى استدعاءات النظام الأخرى التي تدعم العلم O_PATH.
O_RDONLY
افتح للقراءة فقط.
O_RDWR
افتح للقراءة والكتابة.
O_SYNC
الإدخال/الإخراج المتزامن لبيانات الملف. يطلب هذا العلم من النظام تنفيذ عمليات الإدخال/الإخراج بطريقة تجعل جميع البيانات والبيانات الوصفية الضرورية مكتوبة على جهاز التخزين الأساسي قبل أن يعود استدعاء النظام. يضمن هذا أن البيانات مخزنة بشكل دائم.
O_TMPFILE
إنشاء ملف مؤقت. يمكن استخدام هذا العلم فقط مع O_DIRECTORY و O_WRONLY. يتم إنشاء الملف في الدليل المشار إليه بواسطة dirfd ويتم حذفه عندما يتم إغلاق آخر واصف ملف يشير إليه. إذا كان pathname هو NULL، فسيتم إنشاء الملف المؤقت في الدليل الحالي.
O_TRUNC
إذا كان الملف موجودًا وتم فتحه للكتابة، قم بقص طوله إلى 0 في هذا الاستدعاء. لا يؤثر العلم O_TRUNC إذا لم يكن الملف مفتوحًا للكتابة. يمكن دمج هذا العلم مع O_RDWR أو O_WRONLY.
O_WRONLY
افتح للكتابة فقط.

يحدد الوسيط mode بتات إذن الملف التي سيتم تعيينها للملف الجديد إذا تم تحديد O_CREAT. يتم تطبيق عملية AND عليه مع قيمة umask الخاصة بالعملية. راجع chmod(2) لمزيد من التفاصيل.

يمكن استخدام العلم O_DIRECT لإجراء إدخال/إخراج مباشر. عند استخدام هذا العلم، يتم نقل البيانات مباشرة بين مخزن المستخدم وجهاز التخزين الأساسي، متجاوزًا ذاكرة التخزين المؤقت للصفحات. يمكن أن يحسن ذلك الأداء لبعض أعباء العمل، ولكنه يفرض أيضًا متطلبات محاذاة أكثر صرامة على عنوان المخزن المؤقت وحجم مقطع الإدخال/الإخراج.

لا يمكن افتراض قيود المحاذاة إلا من الخصائص المعروفة لنظام الملفات، والملف الفردي، وأجهزة التخزين الأساسية، وإصدار النواة. في Linux 2.4، تتطلب معظم أنظمة الملفات المستندة إلى أجهزة الكتل أن يكون إزاحة الملف وطول وعنوان الذاكرة لجميع مقاطع الإدخال/الإخراج مضاعفات حجم كتلة نظام الملفات (عادة 4096 بايت). في Linux 2.6.0، تم تخفيف ذلك إلى الحجم المنطقي لكتلة جهاز الكتل (عادة 512 بايت). يمكن تحديد الحجم المنطقي لكتلة جهاز الكتل باستخدام عملية ioctl(2) BLKSSZGET أو من سطر الأوامر باستخدام الأمر:


blockdev --getss

يجب عدم تشغيل عمليات الإدخال/الإخراج O_DIRECT بالتزامن مع استدعاء النظام fork(2)، إذا كان المخزن المؤقت للذاكرة عبارة عن تعيين خاص (أي، أي تعيين تم إنشاؤه باستخدام العلم MAP_PRIVATE لـ mmap(2)؛ وهذا يشمل الذاكرة المخصصة على الكومة والمخازن المؤقتة المخصصة بشكل ثابت). يجب إكمال أي عمليات إدخال/إخراج من هذا القبيل، سواء تم تقديمها عبر واجهة إدخال/إخراج غير متزامنة أو من مؤشر ترابط آخر في العملية، قبل استدعاء fork(2). قد يؤدي الفشل في القيام بذلك إلى تلف البيانات وسلوك غير محدد في العمليات الأصلية والفرعية. لا ينطبق هذا القيد عندما تم إنشاء المخزن المؤقت للذاكرة لعمليات الإدخال/الإخراج O_DIRECT باستخدام shmat(2) أو mmap(2) مع العلم MAP_SHARED. ولا ينطبق هذا القيد عندما تم الإشارة إلى المخزن المؤقت للذاكرة كـ MADV_DONTFORK باستخدام madvise(2)، مما يضمن أنه لن يكون متاحًا للطفل بعد fork(2).

تم تقديم العلم O_DIRECT في SGI IRIX، حيث كان لديه قيود محاذاة مشابهة لتلك الخاصة بـ Linux 2.4. لدى IRIX أيضًا استدعاء fcntl(2) للاستعلام عن المحاذاة والأحجام المناسبة. قدم FreeBSD 4.x علمًا بنفس الاسم، ولكن بدون قيود محاذاة.

تمت إضافة دعم O_DIRECT في Linux 2.4.10. تتجاهل نواة Linux الأقدم هذا العلم ببساطة. قد لا تنفذ بعض أنظمة الملفات العلم، وفي هذه الحالة يفشل open() بالخطأ EINVAL إذا تم استخدامه.

يجب على التطبيقات تجنب خلط O_DIRECT والإدخال/الإخراج العادي لنفس الملف، وخاصة لمناطق البايت المتداخلة في نفس الملف. حتى عندما تتعامل نظام الملفات بشكل صحيح مع قضايا التناسق في هذا الموقف، من المحتمل أن يكون معدل نقل الإدخال/الإخراج الإجمالي أبطأ من استخدام أي وضع بمفرده. وبالمثل، يجب على التطبيقات تجنب خلط mmap(2) للملفات مع الإدخال/الإخراج المباشر لنفس الملفات.

سيختلف سلوك O_DIRECT مع NFS عن أنظمة الملفات المحلية. قد لا تدعم النوى الأقدم، أو النوى التي تم تكوينها بطرق معينة، هذا المزيج. لا يدعم بروتوكول NFS تمرير العلم إلى الخادم، لذلك سيتم تجاوز ذاكرة التخزين المؤقت للصفحات لعمليات الإدخال/الإخراج O_DIRECT على العميل فقط؛ قد يظل الخادم يخزن الإدخال/الإخراج مؤقتًا. يطلب العميل من الخادم جعل الإدخال/الإخراج متزامنًا للحفاظ على دلالات التزامن الخاصة بـ O_DIRECT. قد تعمل بعض الخوادم بشكل سيء في ظل هذه الظروف، خاصة إذا كان حجم الإدخال/الإخراج صغيرًا. قد يتم أيضًا تكوين بعض الخوادم للكذب على العملاء بشأن وصول الإدخال/الإخراج إلى التخزين المستقر؛ سيتجنب ذلك عقوبة الأداء مع بعض المخاطر على سلامة البيانات في حالة فشل طاقة الخادم. لا تفرض عميل Linux NFS أي قيود محاذاة على عمليات الإدخال/الإخراج O_DIRECT.

باختصار، O_DIRECT هي أداة قوية محتملة يجب استخدامها بحذر. يوصى بأن تعامل التطبيقات استخدام O_DIRECT كخيار أداء معطل افتراضيًا.

قيمة الإرجاع

عند النجاح، تعيد استدعاءات النظام هذه واصف الملف الجديد. عند حدوث خطأ، تعيد -1، ويتم تعيين errno للإشارة إلى الخطأ.

الأخطاء

بالإضافة إلى أخطاء الوصول إلى الملف القياسية، قد تحدث الأخطاء التالية:

EACCES
الوصول المطلوب للملف غير مسموح به، أو لـ openat() مع O_CREAT، الأذونات المطلوبة غير مسموح بها.
EADDRINUSE
تم تحديد الأعلام O_CREAT و O_EXCL، وكان الملف موجودًا بالفعل، وكان الملف عبارة عن مقبس.
EBADF
الوسيط dirfd ليس واصف ملف صالحًا، أو أن pathname نسبي و dirfd ليس دليلاً. أو، تم تحديد O_TMPFILE، و dirfd يشير إلى نوع واصف ملف بخلاف الدليل.
EBUSY
يشير الملف pathname إلى جهاز مشغول.
ECHILD
حدثت إشارة أثناء فتح الملف.
EDEADLK
تم تحديد O_CREAT و O_EXCL، وكان الملف موجودًا بالفعل. أو، تم اكتشاف حالة توقف.
EEXIST
تم تحديد O_CREAT و O_EXCL، وكان الملف موجودًا بالفعل. أو، تم استخدام O_EXCL مع O_CREAT على رابط رمزي.
EINTR
تم مقاطعة الاستدعاء بإشارة.
EINVAL
قيمة غير صالحة لـ flags أو mode. أو، تم تحديد O_TMPFILE بدون O_DIRECTORY. أو، نظام الملفات لا يدعم O_DIRECT أو O_TMPFILE.
EISDIR
يشير الاسم pathname إلى دليل، ويشمل الوصول المطلوب الكتابة أو هو O_WRONLY أو O_RDWR.
ELOOP
يحتوي pathname على حلقة رابط رمزي، أو تم تحديد O_NOFOLLOW وكان pathname رابطًا رمزيًا.
EMFILE
وصلت العملية إلى حدها الأقصى لعدد واصفات الملفات المفتوحة.
EMLINK
الملف المشار إليه بواسطة pathname لديه روابط كثيرة جدًا.
ENAMETOOLONG
pathname طويل جدًا.
ENFILE
تم الوصول إلى الحد الأقصى على مستوى النظام لعدد الملفات المفتوحة الإجمالي.
ENOENT
pathname غير موجود ولم يتم تحديد O_CREAT. أو، تم تحديد O_TMPFILE، و pathname هو NULL، و dirfd لا يشير إلى دليل.
ENOMEM
لم تكن ذاكرة النواة كافية متاحة.
ENOSPC
تم تحديد O_CREAT، ولكن الجهاز الذي يحتوي على pathname ليس لديه مساحة للملف.
ENOTDIR
pathname ليس دليلًا، و O_DIRECTORY
ENXIO
تم تحديد اسم مادي غير موجود، أو الجهاز أو السمة المشار إليها بواسطة pathname غير موجودة.
EOVERFLOW
الملف هو ملف عادي أو رابط رمزي، وحجم الملف أو عدد الروابط الثابتة في الملف يتجاوز القيمة القصوى التي يمكن تمثيلها في inode الملف.
EROFS
الملف المسمى موجود على نظام ملفات للقراءة فقط، وتم فتحه للكتابة.
ETXTBSY
الملف هو ملف عادي قيد التنفيذ. يتم إرجاع هذا الخطأ فقط عند فتح الملف باستخدام O_RDWR أو O_WRONLY. يستخدم هذا العلم من قبل بعض البرامج مثل vi(1) للإشارة إلى أن الملف قيد التحرير. هذا ليس علمًا قياسيًا ولا يجب استخدامه في التعليمات البرمجية المحمولة.
EXDEV
تم تحديد pathname يشير إلى ملف في نظام ملفات آخر، وتتطلب العملية المطلوبة أن يظل الملف في نفس نظام الملفات.

ملاحظات

استدعاء النظام openat() والطرق الأخرى لتمرير واصفات الملفات مفيدة لكتابة برامج تتعامل مع مسارات الملفات بشكل صحيح. وهي مفيدة بشكل خاص لكتابة برامج لا تتبع الروابط الرمزية، أو تعمل في أدلة يتم تعديلها بواسطة عمليات أخرى. وهي مفيدة أيضًا لكتابة برامج تحتاج إلى تجنب حالات السباق عند فتح الملفات.

يتجاوز العلم O_DIRECT ذاكرة التخزين المؤقت للصفحات الخاصة بالنواة. يمكن أن يحسن هذا الأداء لتطبيقات معينة، مثل أنظمة قواعد البيانات، ولكنه قد يؤدي أيضًا إلى تدهور الأداء إذا لم يتم استخدامه بعناية. عادة ما تكون متطلبات المحاذاة لعمليات الإدخال/الإخراج O_DIRECT أكثر صرامة من الإدخال/الإخراج العادي. يجب محاذاة إزاحة وحجم عمليات الإدخال/الإخراج، بالإضافة إلى عنوان الذاكرة للمخزن المؤقت، مع الحجم المنطقي للكتلة لجهاز التخزين الأساسي.

يجب على التطبيقات تجنب خلط O_DIRECT والإدخال/الإخراج العادي لنفس الملف، وخاصة لمناطق البايت المتداخلة في نفس الملف. حتى عندما تتعامل نظام الملفات بشكل صحيح مع قضايا التناسق في هذا الموقف، من المحتمل أن يكون معدل نقل الإدخال/الإخراج الإجمالي أبطأ من استخدام أي وضع بمفرده. وبالمثل، يجب على التطبيقات تجنب خلط mmap(2) للملفات مع الإدخال/الإخراج المباشر لنفس الملفات.

سيختلف سلوك O_DIRECT مع NFS عن أنظمة الملفات المحلية. قد لا تدعم النوى الأقدم، أو النوى التي تم تكوينها بطرق معينة، هذا المزيج. لا يدعم بروتوكول NFS تمرير العلم إلى الخادم، لذلك سيتم تجاوز ذاكرة التخزين المؤقت للصفحات لعمليات الإدخال/الإخراج O_DIRECT على العميل فقط؛ قد يظل الخادم يخزن الإدخال/الإخراج مؤقتًا. يطلب العميل من الخادم جعل الإدخال/الإخراج متزامنًا للحفاظ على دلالات التزامن الخاصة بـ O_DIRECT. قد تعمل بعض الخوادم بشكل سيء في ظل هذه الظروف، خاصة إذا كان حجم الإدخال/الإخراج صغيرًا. قد يتم أيضًا تكوين بعض الخوادم للكذب على العملاء بشأن وصول الإدخال/الإخراج إلى التخزين المستقر؛ سيتجنب ذلك عقوبة الأداء مع بعض المخاطر على سلامة البيانات في حالة فشل طاقة الخادم. لا تفرض عميل Linux NFS أي قيود محاذاة على عمليات الإدخال/الإخراج O_DIRECT.

باختصار، O_DIRECT هي أداة قوية محتملة يجب استخدامها بحذر. يوصى بأن تعامل التطبيقات استخدام O_DIRECT كخيار أداء معطل افتراضيًا.

الأخطاء

حاليا، لا يمكن تمكين الإدخال/الإخراج المدفوع بالإشارة عن طريق تحديد O_ASYNC عند استدعاء open()؛ استخدم fcntl(2) لتمكين هذا العلم.

يجب التحقق من رمزي خطأ مختلفين، EISDIR و ENOENT، عند محاولة تحديد ما إذا كانت النواة تدعم وظيفة O_TMPFILE.
