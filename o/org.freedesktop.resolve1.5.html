ORG.FREEDESKTOP.RESOLVE1(5) org.freedesktop.resolve1 ORG.FREEDESKTOP.RESOLVE1(5)

الاسم

org.freedesktop.resolve1 - واجهة D-Bus الخاصة بـ systemd-resolved

مقدمة

systemd-resolved.service(8) هي خدمة نظام توفر حل أسماء المضيف والتخزين المؤقت باستخدام DNS و LLMNR و mDNS. كما تقوم بالتحقق من صحة DNSSEC. تصف هذه الصفحة دلالات الحل وواجهة D-Bus.

تحتوي هذه الصفحة على مرجع API فقط. إذا كنت تبحث عن شرح أطول لكيفية استخدام واجهة برمجة التطبيقات هذه، يرجى استشارة كتابة مديري تكوين الشبكة[1] و كتابة عملاء محلل[2].

الأساليب

ResolveHostname() تأخذ اسم مضيف وتقوم بحله إلى عنوان IP واحد أو أكثر. كمعلمات، تأخذ فهرس واجهة الشبكة في Linux لتنفيذ الاستعلام عليها، أو 0 إذا كان يمكن القيام بذلك على أي واجهة مناسبة. تحدد معلمة name اسم المضيف المطلوب حله. لاحظ أنه إذا لزم الأمر، يتم تطبيق تحويل IDNA على هذا الاسم ما لم يتم حله عبر LLMNR أو MulticastDNS. تحدد معلمة family النتائج لعائلة عناوين معينة. يمكن أن تكون AF_INET أو AF_INET6 أو AF_UNSPEC. إذا تم تحديد AF_UNSPEC (موصى به)، يتم استرداد كلا النوعين، حسب تكوين الشبكة المحلي (أي، إذا لم يتم العثور على عنوان IPv6 محلي قابل للتوجيه، فلن يتم استرداد عنوان IPv6؛ وبالمثل بالنسبة لـ IPv4). يمكن استخدام حقل flags ذي 64 بت لتغيير سلوك عملية الحل (انظر أدناه). تُرجع الطريقة مصفوفة من سجلات العناوين. يتكون كل سجل عنوان من فهرس الواجهة الذي ينتمي إليه العنوان، وعائلة عنوان، بالإضافة إلى مصفوفة بايت مع بيانات IP الفعلية (التي تحتوي إما على 4 أو 16 عنصرًا، اعتمادًا على عائلة العنوان). ستكون عائلة العنوان المرتجعة إما AF_INET أو AF_INET6. بالنسبة لـ IPv6، يجب استخدام فهرس واجهة العنوان المرتجع لتهيئة حقل .sin6_scope_id لكائن struct sockaddr_in6 للسماح بدعم الحل لعناوين IP المحلية للرابط. تتبع مصفوفة العناوين الاسم القانوني للمضيف، والذي قد يكون مطابقًا لاسم المضيف الذي تم حله أو لا. أخيرًا، يتم إرجاع حقل flags ذي 64 بت والذي يتم تعريفه بشكل مشابه لحقل flags الذي تم تمريره، ولكنه يحتوي على معلومات حول البيانات التي تم حلها (انظر أدناه). إذا كان اسم المضيف الذي تم تمريره هو عنوان IPv4 أو IPv6 بتنسيق سلسلة، يتم تحليله، ويتم إرجاع النتيجة. في هذه الحالة، لا يتم إجراء أي اتصال بالشبكة.

ResolveAddress() تنفذ العملية العكسية: تأخذ عنوان IP وتسترد اسم مضيف واحد أو أكثر له. كمعلمات، تأخذ فهرس الواجهة لتنفيذ الاستعلام عليها، أو 0 إذا كانت جميع الواجهات المناسبة لا بأس بها. تشير معلمة family إلى عائلة عنوان IP المطلوب حلها. يمكن أن تكون إما AF_INET أو AF_INET6. تأخذ معلمة address بيانات عنوان IP الخام (إما كمصفوفة بايت 4 أو 16). يمكن استخدام معلمة flags المدخلة لتغيير عملية الحل (انظر أدناه). تُرجع الطريقة مصفوفة من سجلات الأسماء، يتكون كل منها من فهرس الواجهة واسم المضيف. يحتوي حقل flags المخرج على معلومات إضافية حول عملية الحل (انظر أدناه).

ResolveRecord() تأخذ نوع سجل المورد DNS (RR) والفئة والاسم، وتسترد مجموعة سجل المورد (RRset) الكاملة، بما في ذلك RDATA، لها. كمعلمة، تأخذ فهرس واجهة الشبكة في Linux لتنفيذ الاستعلام عليها، أو 0 إذا كان يمكن القيام بذلك على أي واجهة مناسبة. تحدد معلمة name اسم مجال RR المطلوب البحث عنه (لا يتم تطبيق تحويل IDNA)، متبوعًا بحقول الفئة والنوع ذي 16 بت (والتي يمكن أن تكون ANY). أخيرًا، يمكن تمرير حقل flags لتغيير سلوك البحث (انظر أدناه). عند الانتهاء، يتم إرجاع مصفوفة من عناصر RR. يتكون كل إدخال في المصفوفة من فهرس واجهة الشبكة الذي تم اكتشاف RR عليه، وحقول النوع والفئة لـ RR الموجود، ومصفوفة بايت لـ RR الخام المكتشف. تبدأ بيانات RR الخام باسم مجال RR، بالصيغة الأصلية، متبوعًا بنوع RR والفئة و TTL و RDATA، بالتنسيق الثنائي الموثق في RFC 1035[3]. بالنسبة لـ RRs التي تدعم ضغط الأسماء في الحمولة (مثل MX أو PTR)، يتم تطبيق الضغط ex

موسعة في البيانات المرتجعة.

لاحظ أنه حاليًا، يجب تحديد حقل الفئة على أنه IN أو ANY. سيؤدي تحديد فئة مختلفة إلى إرجاع خطأ يشير إلى أن عمليات البحث من هذا النوع غير مدعومة. وبالمثل، لا يتم دعم بعض الأنواع الخاصة أيضًا (AXFR، OPT، ...). بينما يقوم systemd-resolved بتحليل والتحقق من صحة سجلات الموارد من العديد من الأنواع، من الضروري أن يفهم العملاء الذين يستخدمون هذه الواجهة البرمجية أن بيانات RR تنشأ من الشبكة ويجب التحقق من صحتها بدقة قبل الاستخدام.

ResolveService() يمكن استخدامها لحل سجل خدمة DNS SRV، وكذلك أسماء المضيف المشار إليها فيها، وربما سجل TXT مصاحب لـ DNS-SD يحتوي على بيانات وصفية إضافية للخدمة. الفائدة الرئيسية لاستخدام هذه الطريقة بدلاً من ResolveRecord() مع تحديد النوع SRV هي أنها ستقوم بحل سجلات SRV و TXT بالإضافة إلى أسماء المضيف المشار إليها في SRV في عملية واحدة. كمعلمات، تأخذ فهرس واجهة شبكة Linux، واسم خدمة، ونوع خدمة، ونطاق خدمة. يمكن استدعاء هذه الطريقة في ثلاثة أوضاع مختلفة:

1. لحل خدمة DNS-SD، قم بتحديد اسم الخدمة (على سبيل المثال، "ملفات Lennart")، ونوع الخدمة (على سبيل المثال، "_webdav._tcp") والنطاق للبحث فيه (على سبيل المثال، "local") كمعلمات الخدمة الثلاثة. يجب أن يكون اسم الخدمة بتنسيق UTF-8، ولا يتم تطبيق تحويل IDNA عليه في هذا الوضع (كما هو مطلوب بموجب مواصفات DNS-SD). ومع ذلك، إذا لزم الأمر، يتم تطبيق تحويل IDNA على معلمة النطاق.
2. لحل سجل SRV عادي، قم بتعيين معلمة اسم الخدمة إلى سلسلة فارغة وقم بتعيين نوع الخدمة والنطاق بشكل صحيح. (يتم تطبيق تحويل IDNA على النطاق، إذا لزم الأمر.)
3. بدلاً من ذلك، اترك اسم الخدمة والنوع فارغين وحدد اسم النطاق الكامل لسجل SRV (أي، مسبوقًا بنوع الخدمة) في معلمة النطاق. (لا يتم تطبيق تحويل IDNA في هذا الوضع.)

المعلمة family لطريقة ResolveService() تشفر العائلة المطلوبة للعناوين المراد حلها (استخدم AF_INET، AF_INET6، أو AF_UNSPEC). إذا كان هذا ممكّنًا (استخدم علامة NO_ADDRESS لإيقاف حل العناوين، انظر أدناه). تأخذ المعلمة flags عددًا قليلاً من العلامات التي يمكن استخدامها لتعديل عملية المستكشف.

عند الاكتمال، ترجع ResolveService() مصفوفة من هياكل سجل SRV. كل عنصر يتكون من حقول الأولوية والوزن والمنفذ بالإضافة إلى اسم المضيف المراد الاتصال به، كما هو مشفر في سجل SRV. يتبع ذلك مباشرة مصفوفة من عناوين اسم المضيف هذا، حيث يتكون كل عنصر من فهرس الواجهة، وعائلة العنوان، وبيانات العنوان في مصفوفة بايت. تتبع مصفوفة العناوين هذه اسم المضيف المؤهل. بعد مصفوفة هياكل سجل SRV هذه، تتبع مصفوفة من مصفوفات البايت التي تشفر سلاسل سجل TXT، في حالة تمكين عمليات بحث DNS-SD. المعلمات التالية هي اسم الخدمة ونوعها ونطاقها القياسي. قد يكون هذا مطابقًا أو غير مطابق للمعلمات التي تم تمريرها. أخيرًا، يتم إرجاع حقل flags يحتوي على معلومات حول عملية المستكشف التي تم إجراؤها.

تقوم طريقة ResetStatistics() بإعادة تعيين عدادات الإحصائيات المختلفة التي يحتفظ بها systemd-resolved إلى الصفر. (للتفاصيل، انظر خصائص الإحصائيات أدناه.)

تأخذ طريقة GetLink() فهرس واجهة الشبكة وترجع مسار الكائن لكائن org.freedesktop.resolve1.Link المقابل له.

تقوم طريقة SetLinkDNS() بتعيين خوادم DNS لاستخدامها على واجهة معينة. قد تُستخدم هذه الطريقة (والطرق التالية) بواسطة برامج إدارة الشبكة لتكوين إعدادات DNS لكل واجهة. تأخذ فهرس واجهة شبكة بالإضافة إلى مصفوفة من سجلات عناوين IP لخوادم DNS. يتكون كل عنصر مصفوفة من عائلة عنوان (إما AF_INET أو AF_INET6)، يليه مصفوفة 4 بايت أو 16 بايت تحتوي على بيانات العنوان الخام. هذه الطريقة هي اختصار من خطوة واحدة لاسترداد كائن Link لواجهة شبكة باستخدام GetLink() (انظر أعلاه) ثم استدعاء طريقة SetDNS() (انظر أدناه) عليها.

SetLinkDNSEx() مشابهة لـ SetLinkDNS()، ولكنها تسمح بتحديد منفذ IP (بدلاً من المنفذ الافتراضي 53) واسم DNS لكل خادم DNS. يتم استخدام اسم الخادم لـ Server Name Indication (SNI)، وهو مفيد عند استخدام DNS-over-TLS. انظر DNS= في resolved.conf(5).

SetLinkDefaultRoute() تحدد ما إذا كان سيتم استخدام الرابط كمسار افتراضي لاستعلامات الأسماء. انظر وصف توجيه الأسماء في systemd-resolved.service(8) للتفاصيل.

تقوم طريقة SetLinkDomains() بتعيين نطاقات البحث والتوجيه لاستخدامها على واجهة شبكة معينة لعمليات بحث DNS. تأخذ فهرس واجهة شبكة ومصفوفة من النطاقات، كل منها يحتوي على معلمة منطقية تشير إلى ما إذا كان سيتم استخدام النطاق المحدد كنطاق بحث (خطأ)، أو كنطاق توجيه فقط (صحيح). تستخدم نطاقات البحث لتأهيل الأسماء ذات التسمية الواحدة إلى FQDN عند البحث عن أسماء المضيف، وكذلك لاتخاذ قرارات التوجيه بشأن الواجهة التي سيتم إرسال الاستعلامات التي تنتهي بالنطاق إليها. تستخدم نطاقات التوجيه فقط لاتخاذ قرارات التوجيه ولا تستخدم لتأهيل أسماء التسمية الواحدة. قم بتمرير نطاقات البحث بالترتيب الذي يجب استخدامه.

تقوم طريقة SetLinkLLMNR() بتمكين أو تعطيل دعم LLMNR على واجهة شبكة معينة. تأخذ فهرس واجهة شبكة بالإضافة إلى سلسلة قد تكون فارغة أو أحد "yes" أو "no" أو "resolve". إذا كانت فارغة، يتم استخدام الإعداد الافتراضي لـ LLMNR على مستوى النظام. إذا كانت "yes"، يتم استخدام LLMNR لحل أسماء التسمية الواحدة، ويتم تسجيل اسم المضيف المحلي على جميع شبكات LAN المحلية لحل LLMNR بواسطة الأقران. إذا كانت "no"، يتم إيقاف LLMNR بالكامل على هذه الواجهة. إذا كانت "resolve"، يتم تمكين LLMNR فقط لحل الأسماء، ولكن لا يتم تسجيل اسم المضيف المحلي للأقران لاستخدامه.

وبالمثل، تقوم طريقة SetLinkMulticastDNS() بتمكين أو تعطيل دعم MulticastDNS على واجهة معينة. تأخذ نفس المعلمات مثل SetLinkLLMNR() الموضحة أعلاه.

تقوم طريقة SetLinkDNSSEC() بتمكين أو تعطيل التحقق من صحة DNSSEC على واجهة شبكة معينة. تأخذ فهرس واجهة شبكة بالإضافة إلى سلسلة قد تكون فارغة أو أحد "yes" أو "no" أو "allow-downgrade". عندما تكون فارغة، يتم استخدام الإعداد الافتراضي لـ DNSSEC على مستوى النظام. إذا كانت "yes"، يتم إجراء التحقق الكامل من صحة DNSSEC لجميع عمليات البحث. إذا كان خادم DNS المحدد لا يدعم DNSSEC، فستفشل عمليات البحث إذا تم استخدام هذا الوضع. إذا كانت "no"، يتم تعطيل التحقق من صحة DNSSEC بالكامل. إذا كانت "allow-downgrade"، يتم تمكين التحقق من صحة DNSSEC، ولكنه يتم تعطيله تلقائيًا إذا كان الخادم المحدد لا يدعمه (مما يفتح السلوك لهجمات خفض المستوى). لاحظ أن DNSSEC ينطبق فقط على DNS التقليدي، وليس على LLMNR أو MulticastDNS.

يمكن استخدام طريقة SetLinkDNSSECNegativeTrustAnchors() لتكوين Positive Trust Anchors (NTAs) لـ DNSSEC لواجهة شبكة معينة. تأخذ فهرس واجهة شبكة وقائمة بالنطاقات كمعلمات.

تقوم طريقة SetLinkDNSOverTLS() بتمكين أو تعطيل DNS-over-TLS. انظر DNSOverTLS= في systemd-resolved.service(8) للتفاصيل.

يجب على برامج إدارة الشبكات التي تتكامل مع systemd-resolved استدعاء SetLinkDNS() أو SetLinkDNSEx() و SetLinkDefaultRoute() و SetLinkDomains() وغيرها بعد ظهور الواجهة في النواة (وبالتالي بعد تعيين فهرس واجهة شبكة)، ولكن قبل تنشيط واجهة الشبكة (تعيين IFF_UP) بحيث تسري جميع الإعدادات طوال الوقت الذي تكون فيه واجهة الشبكة قيد التشغيل. من الآمن تغيير الإعدادات أثناء تشغيل الواجهة. استخدم RevertLink() (الموصوفة أدناه) لإعادة تعيين جميع الإعدادات لكل واجهة.

يمكن استخدام طريقة RevertLink() لإعادة تعيين جميع الإعدادات لكل رابط الموضحة أعلاه إلى القيم الافتراضية.

تقوم طريقة FlushCaches() بمسح جميع ذاكرات التخزين المؤقت لسجلات الموارد التي يحتفظ بها المستكشف، وتضمن أن أي عمليات بحث لاحقة تعيد طلب استجاباتها من مصادرها.

تقوم طريقة ResetServerFeatures() بمسح أي معلومات ميزات تم تعلمها حول خوادم DNS البعيدة. هذا يضمن أن عمليات البحث اللاحقة سيتم محاولةها مبدئيًا بأعلى مستوى ميزة DNS مرة أخرى، مما قد يتطلب دورة خفض (قد تكون بطيئة) للتعرف على مستوى الميزة المدعوم مرة أخرى.

يمكن استخدام طريقة RegisterService() لتسجيل خدمة DNS-SD على المضيف. ترتبط هذه الوظيفة ارتباطًا وثيقًا بالوظيفة المقدمة بواسطة ملفات systemd.dnssd(5). تأخذ سلسلة معرف خادم كمعلمة أولى (هذا مجرد معرف محلي، ويجب اختياره بحيث لا يتعارض مع الاسم الأساسي لملفات *.dnssd ولا مع الأسماء التي يختارها عملاء IPC الآخرون). كما تأخذ سلسلة قالب اسم لاسم خدمة DNS-SD المرئي على الشبكة. تخضع هذه السلسلة لتوسيع المحددات، كما هو موثق للإعداد Name= في ملفات *.dnssd. كما تأخذ سلسلة نوع خدمة تحتوي على نوع خدمة DNS-SD، بالإضافة إلى منفذ IP، وزوج أولوية/وزن لسجل DNS-SD SRV. أخيرًا، تأخذ مصفوفة من بيانات سجل TXT. ترجع مسار كائن يمكن استخدامه كمعرف للخدمة المسجلة.

تقوم طريقة UnregisterService() بإلغاء تأثير RegisterService() وحذف خدمة DNS-SD تم إنشاؤها مسبقًا عبر IPC مرة أخرى.

ترجع طريقة GetDelegate() مسار كائن D-Bus لمعرف تفويض DNS المحدد.

ترجع طريقة ListDelegates() قائمة بمعرفات ومسارات كائنات D-Bus للتفويضات DNS المكونة حاليًا.

عند الإدخال، تتحكم العلامات الخمس الأولى في البروتوكولات المراد استخدامها للبحث. وتشير إلى DNS أحادي البث الكلاسيكي، و LLMNR عبر IPv4/UDP و IPv6/UDP على التوالي، وكذلك MulticastDNS عبر IPv4/UDP و IPv6/UDP. إذا كانت جميع هذه البتات الخمسة غير نشطة عند الإدخال (وهو ما يوصى به بشدة) فسيتم إجراء البحث عبر جميع البروتوكولات المناسبة للبحث المحدد. لاحظ أن هذه العلامات تعمل كمرشح فقط، ولكن لا يمكنها إجبار البحث على أن يتم عبر بروتوكول. على وجه التحديد، سيقوم systemd-resolved بتوجيه عمليات البحث داخل TLD .local فقط إلى MulticastDNS (بالإضافة إلى بعض نطاقات البحث عن عناوين البحث العكسي)، والأسماء ذات التسمية الواحدة إلى LLMNR (بالإضافة إلى بعض نطاقات البحث عن عناوين البحث العكسي). ولن يقوم بتوجيه أي من هذه إلى خوادم DNS أحادية البث. أيضًا، سيقوم LLMNR و Multicast DNS فقط على الواجهات المناسبة للبث المتعدد.

عند الإخراج، تشير هذه العلامات الخمس إلى البروتوكول الذي تم استخدامه لتنفيذ العملية، وبالتالي من أين تم العثور على البيانات.

حالات الاستخدام الأساسية لهذه العلامات الخمس هي عمليات البحث اللاحقة بناءً على بيانات DNS التي تم استردادها سابقًا. في هذه الحالة، غالبًا ما يكون من الجيد الحد من البحث اللاحق إلى البروتوكول الذي تم استخدامه لاكتشاف نتيجة DNS الأولى.

تتحكم علامة NO_CNAME فيما إذا كان سيتم متابعة سجلات موارد CNAME/DNAME أثناء البحث. هذه العلامة متاحة فقط عند الإدخال، ولن تقوم أي من الوظائف بإرجاعها عند الإخراج. إذا تم اكتشاف CNAME/DNAME RR أثناء حل اسم المضيف، فسيتم إرجاع خطأ بدلاً من ذلك. افتراضيًا، عندما تكون العلامة غير نشطة، يتم متابعة CNAME/DNAME RRs.

تؤثر علامتا NO_TXT و NO_ADDRESS فقط على عملية الطريقة ResolveService(). وهما معرفتان فقط للإدخال، وليس للإخراج. إذا تم تعيين NO_TXT، فلن يتم إجراء البحث عن DNS-SD TXT RR في نفس العملية. إذا تم تعيين NO_ADDRESS، فلن يتم تحويل أسماء المضيفين المكتشفة ضمنيًا إلى عناوينها.

تقوم علامة NO_SEARCH بتعطيل منطق نطاق البحث. وهي معرفة فقط للإدخال في ResolveHostname(). عند تحديدها، لا يتم تأهيل أسماء المضيفين ذات التسمية الواحدة باستخدام نطاقات البحث المحددة، إن وجدت. لاحظ أن ResolveRecord() لن تؤهل أبدًا أسماء النطاقات ذات التسمية الواحدة باستخدام نطاقات البحث. ولاحظ أيضًا أن أسماء المضيفين ذات التسمية المتعددة لا تخضع أبدًا لتوسيع قائمة البحث.

يمكن تعيين NO_VALIDATE لتعطيل التحقق عبر DNSSEC حتى لو كان سيتم استخدامه عادةً.

تسمح العلامات الست التالية بتعطيل مصادر معينة أثناء الحل. NO_SYNTHESIZE يعطل السجلات الاصطناعية، على سبيل المثال، اسم المضيف المحلي، انظر قسم السجلات الاصطناعية في systemd-resolved.service(8) لمزيد من المعلومات. NO_CACHE يعطل استخدام ذاكرة التخزين المؤقت للسجلات المحلة مسبقًا. NO_ZONE يعطل الإجابات باستخدام سجلات الموارد العامة المسجلة محليًا LLMNR/mDNS. NO_TRUST_ANCHOR يعطل الإجابات باستخدام مرساة الثقة المكونة محليًا. يتطلب NO_NETWORK أن يتم توفير جميع الإجابات دون استخدام الشبكة، أي إما من المصادر المحلية أو ذاكرة التخزين المؤقت. يمكن تعيين علامة NO_STALE لتعطيل الإجابة على الطلبات باستخدام السجلات القديمة.

تم تعريف بت AUTHENTICATED فقط في علامات الإخراج للوظائف الأربع. إذا تم تعيينه، فقد تم المصادقة على البيانات المرجعة بالكامل. على وجه التحديد، يتم تعيين هذا البت لجميع البيانات المحمية بواسطة DNSSEC والتي يمكن إنشاء سلسلة ثقة كاملة لها إلى مرساة نطاق موثوق بها. كما يتم تعيينها للبيانات الاصطناعية محليًا، مثل "localhost" أو البيانات من /etc/hosts. علاوة على ذلك، يتم تعيينها لجميع LLMNR أو mDNS RRs التي تنشأ من المضيف المحلي. يجب على التطبيقات التي تتطلب بيانات RR مصادق عليها للتشغيل التحقق من هذه العلامة قبل الوثوق بالبيانات. لاحظ أن systemd-resolved لن يقوم أبدًا بإرجاع بيانات غير صالحة، وبالتالي تسمح هذه العلامة ببساطة بالتمييز بين الحالات التي يُعرف فيها أن البيانات موثوق بها، أو حيث يوجد دليل على أن البيانات "بشكل صحيح" غير مصادق عليها (والتي تشمل الحالات التي لا يدعم فيها البروتوكول الأساسي أو الخادم المصادقة على البيانات).

CONFIDENTIAL تعني أن الاستعلام تم حله عبر قنوات مشفرة أو لم يغادر هذا النظام أبدًا.

تُستخدم البتات الخمس التالية في الإخراج وتوفر معلومات حول أصل الإجابة. FROM_SYNTHETIC تعني أن الاستعلام تم (على الأقل جزئيًا) اصطناعه محليًا. FROM_CACHE تعني أن الاستعلام تم الرد عليه (على الأقل جزئيًا) باستخدام ذاكرة التخزين المؤقت. FROM_ZONE تعني أن الاستعلام تم الرد عليه (على الأقل جزئيًا) بناءً على السجلات العامة المسجلة محليًا. FROM_TRUST_ANCHOR تعني أن الاستعلام تم الرد عليه (على الأقل جزئيًا) باستخدام مرساة الثقة المحلية. FROM_NETWORK تعني أن الاستعلام تم الرد عليه (على الأقل جزئيًا) باستخدام الشبكة.

الخصائص

تقوم خاصيتا LLMNR و MulticastDNS بالإبلاغ عما إذا كان LLMNR و MulticastDNS ممكنين (بشكل عام). يمكن أن يكون كل منهما "yes"، "no"، و "resolve". انظر SetLinkLLMNR() و SetLinkMulticastDNS() أعلاه.

يحتوي LLMNRHostname على اسم المضيف المعروض حاليًا على الشبكة عبر LLMNR. عادةً ما يتبع اسم المضيف للنظام كما يمكن الاستعلام عنه عبر gethostname(3)، ولكنه قد يختلف إذا تم اكتشاف تعارض على الشبكة.

تحتوي DNS و DNSEx على مصفوفات لجميع خوادم DNS المستخدمة حالياً بواسطة systemd-resolved. تحتوي DNS على معلومات مشابهة لبيانات خادم DNS في /run/systemd/resolve/resolv.conf. تتكون كل بنية في المصفوفة من فهرس واجهة الشبكة الرقمية، وعائلة العناوين، ومصفوفة بايت تحتوي على عنوان خادم DNS (إما بطول 4 بايت لـ IPv4 أو أطوال 16 بايت لـ IPv6). DNSEx مشابه، ولكن يحتوي أيضًا على منفذ IP واسم الخادم (المستخدم لـ Server Name Indication، SNI). تحتوي كلتا المصفوفتين على خوادم DNS المكونة على مستوى النظام، بما في ذلك تلك التي ربما تم قراءتها من /etc/resolv.conf خارجي أو إعداد DNS= في /etc/systemd/resolved.conf، بالإضافة إلى معلومات خادم DNS لكل واجهة تم استردادها من systemd-networkd(8)، أو تم تكوينها بواسطة برنامج خارجي عبر SetLinkDNS() أو SetLinkDNSEx() (انظر أعلاه). سيكون فهرس واجهة الشبكة 0 للخدمات المكونة على مستوى النظام وغير الصفر للخوادم لكل واجهة.

تحتوي FallbackDNS و FallbackDNSEx على مصفوفات لجميع خوادم DNS المكونة كخوادم احتياطية، إن وجدت، بنفس التنسيق مثل DNS و DNSEx الموصوفة أعلاه. انظر وصف FallbackDNS= في resolved.conf(5) لوصف وقت استخدام تلك الخوادم.

يحدد CurrentDNSServer و CurrentDNSServerEx الخادم المستخدم حاليًا لحل الاستعلامات، بنفس تنسيق إدخال واحد في مصفوفتي DNS و DNSEx الموصوفتين أعلاه.

بشكل مشابه، تحتوي خاصية Domains على مصفوفة لجميع نطاقات البحث والتوجيه المستخدمة حاليًا بواسطة systemd-resolved. يتكون كل إدخال من فهرس واجهة شبكة (مرة أخرى، 0 يمثل الإدخالات على مستوى النظام)، اسم النطاق الفعلي، وما إذا كان الإدخال يستخدم فقط للتوجيه (صحيح) أو لكل من التوجيه والبحث (خطأ).

تحتوي خاصية TransactionStatistics على معلومات حول عدد المعاملات التي عالجها systemd-resolved. تحتوي على زوج من عدادات 64 بت غير موقعة، الأول يحتوي على عدد المعاملات الجارية حاليًا، والثاني عدد المعاملات الإجمالية التي يقوم systemd-resolved بمعالجتها أو عالجها. قد يتم إعادة تعيين القيمة الأخيرة باستخدام الطريقة ResetStatistics() الموصوفة أعلاه. لاحظ أن عدد المعاملات لا يتطابق مباشرة مع عدد استدعاءات طريقة الناقل للمحلل. بينما تتطلب عمليات البحث البسيطة عادةً معاملة واحدة فقط، قد تؤدي عمليات البحث الأكثر تعقيدًا إلى المزيد، على سبيل المثال عند استخدام CNAMEs أو DNSSEC.

تحتوي خاصية CacheStatistics على معلومات حول عمليات ذاكرة التخزين المؤقت المنفذة حتى الآن. تعرض ثلاثة عدادات 64 بت: الأول هو العدد الإجمالي لمدخلات ذاكرة التخزين المؤقت الحالية (الإيجابية والسلبية)، والثاني هو عدد ضربات ذاكرة التخزين المؤقت، والثالث هو عدد إخفاقات ذاكرة التخزين المؤقت. قد يتم إعادة تعيين العدادات الأخيرة باستخدام ResetStatistics() (انظر أعلاه).

تحدد خاصية DNSSEC الحالة الحالية للتحقق من DNSSEC. وهي واحدة من "yes" (يتم فرض التحقق)، "no" (لا يتم إجراء أي تحقق)، "allow-downgrade" (يتم إجراء التحقق إذا كان خادم DNS الحالي يدعمه). انظر وصف DNSSEC= في resolved.conf(5).

تحتوي خاصية DNSSECStatistics على معلومات حول عمليات التحقق من DNSSEC المنفذة حتى الآن. تحتوي على أربعة عدادات 64 بت: عدد التحققات الآمنة، وغير الآمنة، والخبيثة، وغير المحددة حتى الآن. يتم زيادة العدادات لكل مجموعة RR تم التحقق منها، ولكل دليل على عدم الوجود. يتم زيادة العداد الآمن لكل عملية قامت بنجاح بالتحقق من رد موقّع، ويتم زيادة العداد غير الآمن لكل عملية قامت بنجاح بالتحقق من أن ردًا غير موقّع هو غير موقّع بشكل صحيح. يتم زيادة العداد الخبيث لكل عملية لم يتم فيها التحقق من صحة التحقق والبيانات يحتمل أن تكون قد تم التلاعب بها. أخيرًا، يتم زيادة العداد غير المحدد لكل عملية لم تكتمل بسبب عدم إمكانية الحصول على المفاتيح الضرورية أو عدم معرفة الخوارزميات التشفيرية.

تقوم خاصية DNSSECSupported المنطقية بالإبلاغ عما إذا كان DNSSEC ممكّنًا وما إذا كانت خوادم DNS المحددة تدعمه. تجمع بين معلومات حول إعدادات DNS على مستوى النظام ولكل واجهة (انظر أدناه)، وتُبلغ عن true فقط إذا كان DNSSEC ممكّنًا ومدعومًا على كل واجهة تم تكوين DNS لها وللإعدادات على مستوى النظام إذا كانت موجودة. لاحظ أن systemd-resolved يفترض أن خوادم DNS تدعم DNSSEC حتى تثبت العكس. وبالتالي، قد تكون القيمة المبلّغ عنها صحيحة مبدئيًا، حتى يتم تنفيذ المعاملات الأولى.

تقوم خاصية DNSOverTLS المنطقية بالإبلاغ عما إذا كان DNS-over-TLS ممكّنًا.

DNS CONFIGURATION

The DNS resolution is configured in four places. First, per-interface settings may be configured in systemd.link(5) files. Second, global DNS settings may be configured in resolved.conf(5). Third, DNS settings may be obtained dynamically via DHCP, or other network configuration protocols. Fourth, DNS settings may be pushed from a network location, such as a captive portal.

When systemd-resolved.service(8) is running, it is used as the system's primary DNS resolver. It maintains a global pool of DNS servers, and a per-interface pool. The per-interface pool is used to determine the DNS server(s) to use for resolving host names belonging to specific domains, and the global pool is used as fallback.

The per-interface DNS servers are configured in the following order of priority:

  1. DNS servers obtained via DHCP or other dynamic protocols for the interface. These are configured by the DHCP client or other network configuration daemon.

  2. DNS servers configured in systemd.link(5) files. These are configured by the administrator.

  3. DNS servers configured in resolved.conf(5) files. These are configured by the administrator.

  4. DNS servers obtained via the captive portal detection mechanism.

The global DNS servers are configured in the following order of priority:

  1. DNS servers configured in resolved.conf(5) files. These are configured by the administrator.

  2. DNS servers obtained via DHCP or other dynamic protocols for the interface that is used as the default route. These are configured by the DHCP client or other network configuration daemon.

The DNS servers are then ordered based on the available scopes. When querying a host name, the DNS servers for the interface associated with the resulting route are tried first. If no suitable interface is found, or if the DNS servers for that interface do not answer, the DNS servers for the default route are tried. If they also do not answer, the global DNS servers are tried.

When systemd-resolved.service(8) is not running, the system's DNS resolver configuration is taken from resolv.conf(5). The content of resolv.conf(5) might be automatically generated by systemd-networkd(8) or another network configuration manager, or it might be set manually by the administrator.

The DNSStubListener property reports whether the stub listener on port 53 is enabled. Possible values are "yes" (enabled), "no" (disabled), "udp" (only the UDP listener is enabled), and "tcp" (only the TCP listener is enabled).

The DNSSECNegativeTrustAnchors property contains a list of recognized DNSSEC negative trust anchors and contains a list of domains.

For each Linux network interface a "Link" object is created which exposes per-link DNS configuration and state. Use GetLink() on the Manager interface to retrieve the object path for a link object given the network interface index (see above).

Methods

The various methods exposed by the Link interface are equivalent to their similarly named counterparts on the Manager interface. e.g. SetDNS() on the Link object maps to SetLinkDNS() on the Manager object, the main difference being that the later expects an interface index to be specified. Invoking the methods on the Manager interface has the benefit of reducing roundtrips, as it is not necessary to first request the Link object path via GetLink() before invoking the methods. The same relationship holds for SetDNSEx(), SetDomains(), SetDefaultRoute(), SetLLMNR(), SetMulticastDNS(), SetDNSOverTLS(), SetDNSSEC(), SetDNSSECNegativeTrustAnchors(), and Revert(). For further details on these methods see the Manager documentation above.

Properties

ScopesMask defines which resolver scopes are currently active on this interface. This 64-bit unsigned integer field is a bit mask consisting of a subset of the bits of the flags parameter describe above. Specifically, it may have the DNS, LLMNR and MDNS bits (the latter in IPv4 and IPv6 flavours) set. Each individual bit is set when the protocol applies to a specific interface and is enabled for it. It is unset otherwise. Specifically, a multicast-capable interface in the "UP" state with an IP address is suitable for LLMNR or MulticastDNS, and any interface that is UP and has an IP address is suitable for DNS. Note the relationship of the bits exposed here with the LLMNR and MulticastDNS properties also exposed on the Link interface. The latter expose what is *configured* to be used on the interface, the former expose what is actually used on the interface, taking into account the abilities of the interface.

DNSSECSupported exposes a boolean field that indicates whether DNSSEC is currently configured and in use on the interface. Note that if DNSSEC is enabled on an interface, it is assumed available until it is detected that the configured server does not actually support it. Thus, this property may initially report that DNSSEC is supported on an interface.

DefaultRoute exposes a boolean field that indicates whether the interface will be used as default route for name queries. See SetLinkDefaultRoute() above.

The other properties reflect the state of the various configuration settings for the link which may be set with the various methods calls such as SetDNS() or SetLLMNR().

COMMON ERRORS

Many bus methods systemd-resolved exposes (in particular the resolver methods such as ResolveHostname() on the Manager interface) may return some of the following errors:

org.freedesktop.resolve1.NoNameServers

No suitable DNS servers were found to resolve a request.

Added in version 246.

org.freedesktop.resolve1.InvalidReply

A response from the selected DNS server was not understood.

Added in version 246.

org.freedesktop.resolve1.NoSuchRR

The requested name exists, but there is no resource record of the requested type for it. (This is the DNS NODATA case).

Added in version 246.

org.freedesktop.resolve1.CNameLoop

The look-up failed because a CNAME or DNAME loop was detected.

Added in version 246.

org.freedesktop.resolve1.Aborted

The look-up was aborted because the selected protocol became unavailable while the operation was ongoing.

Added in version 246.

org.freedesktop.resolve1.NoSuchService

A service look-up was successful, but the SRV record reported that the service is not available.

Added in version 246.

org.freedesktop.resolve1.DnssecFailed

The acquired response did not pass DNSSEC validation.

Added in version 246.

org.freedesktop.resolve1.NoTrustAnchor

No chain of trust could be established for the response to a configured DNSSEC trust anchor.

Added in version 246.

org.freedesktop.resolve1.ResourceRecordTypeUnsupported

The requested resource record type is not supported on the selected DNS servers. This error is generated for example when an RRSIG record is requested from a DNS server that does not support DNSSEC.

Added in version 246.

org.freedesktop.resolve1.NoSuchLink

No network interface with the specified network interface index exists.

Added in version 246.

org.freedesktop.resolve1.LinkBusy

The requested configuration change could not be made because systemd-networkd(8), already took possession of the interface and supplied configuration data for it.

Added in version 246.

org.freedesktop.resolve1.NetworkDown

The requested look-up failed because the system is currently not connected to any suitable network.

Added in version 246.

org.freedesktop.resolve1.DnsError.NXDOMAIN, org.freedesktop.resolve1.DnsError.REFUSED, ...

The look-up failed with a DNS return code reporting a failure. The error names used as suffixes here are defined in by IANA in DNS RCODEs[4].

Added in version 246.
