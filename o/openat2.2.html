الوصف

استدعاء النظام openat2() هو امتداد لـ openat(2) ويوفر مجموعة فرعية من وظائفه.

يفتح استدعاء النظام openat2() الملف المحدد بواسطة path. إذا كان الملف المحدد غير موجود، فقد يتم إنشاؤه اختياريًا (إذا تم تحديد O_CREAT في how.flags).

كما هو الحال مع openat(2)، إذا كان path نسبيًا، فسيتم تفسيره بالنسبة للدليل المشار إليه بواسطة واصف الملف dirfd (أو الدليل العامل الحالي للعملية المتصلة، إذا كان dirfd هو القيمة الخاصة AT_FDCWD). إذا كان path مطلقًا، فإن dirfd يتم تجاهله (ما لم يكن how.resolve يحتوي على RESOLVE_IN_ROOT، وفي هذه الحالة يتم حل path بالنسبة إلى dirfd).

بدلاً من أخذ وسيطة flags واحدة، يتم تمرير بنية قابلة للتوسيع (how) للسماح بالامتدادات المستقبلية. يجب تحديد الوسيطة size على أنها sizeof(struct open_how).

بنية open_how

تحدد الوسيطة how كيفية فتح path، وتعمل كمجموعة فوق الوسيطات flags و mode لـ openat(2). هذه الوسيطة هي مؤشر إلى بنية open_how، موصوفة في open_how(2type).

ستتم معالجة أي امتدادات مستقبلية لـ openat2() كحقول جديدة تضاف إلى بنية open_how، مع قيمة صفرية في حقل جديد يؤدي إلى سلوك النواة كما لو أن حقل الامتداد هذا غير موجود. لذلك، يجب على المتصل مسح هذه البنية (املأها بالأصفار) عند تهيئتها. (انظر قسم "قابلية التوسيع" في ملاحظات لمزيد من التفاصيل حول سبب ضرورة ذلك.)

الحقول في بنية how هي كما يلي:

flags
يحدد هذا الحقل إنشاء الملف وعلامات حالة الملف لاستخدامها عند فتح الملف. جميع علامات O_* المعرفة لـ openat(2) هي قيم علامات صالحة لـ openat2().
بينما يتجاهل openat(2) البتات غير المعروفة في وسيطته flags، يعيد openat2() خطأ إذا تم تحديد علامات غير معروفة أو متعارضة في how.flags.
mode
يحدد هذا الحقل الوضع للملف الجديد، مع دلالات متطابقة لوسيطة mode الخاصة بـ openat(2).
بينما يتجاهل openat(2) البتات بخلاف تلك الموجودة في النطاق 07777 في وسيطته mode، يعيد openat2() خطأ إذا احتوت how.mode على بتات بخلاف 07777. وبالمثل، يتم إرجاع خطأ إذا تم استدعاء openat2() بقيمة how.mode غير صفرية و how.flags لا تحتوي على O_CREAT أو O_TMPFILE.
resolve
هذه قناع بت يحدد علامات تعدل الطريقة التي يتم بها حل جميع مكونات path. (انظر path_resolution(7) للحصول على معلومات أساسية.)
حالة الاستخدام الرئيسية لهذه العلامات هي السماح للبرامج الموثوقة بتقييد كيفية حل المسارات غير الموثوق بها (أو المسارات داخل الدلائل غير الموثوق بها). القائمة الكاملة لعلامات resolve هي كما يلي:
RESOLVE_BENEATH
لا تسمح بنجاح حل المسار إذا لم يكن أي مكون من مكونات الحل سليلًا للدليل المشار إليه بواسطة dirfd. هذا يؤدي إلى رفض الروابط الرمزية المطلقة (والقيم المطلقة لـ path).
حاليًا، هذه العلامة تتعطل أيضًا حل الروابط السحرية (انظر أدناه). ومع ذلك، قد يتغير هذا في المستقبل. لذلك، لضمان عدم حل الروابط السحرية، يجب على المتصل تحديد RESOLVE_NO_MAGICLINKS بشكل صريح.
RESOLVE_IN_ROOT
عامل الدليل المشار إليه بواسطة dirfd كدليل الجذر أثناء حل path. يتم تفسير الروابط الرمزية المطلقة بالنسبة إلى dirfd. إذا كان مكون بادئة لـ path يساوي dirfd، فإن مكون .. الذي يتبعه مباشرة يعادل أيضًا dirfd (تمامًا كما أن /.. يعادل تقليديًا /). إذا كان path مطلقًا، فسيتم تفسيره أيضًا بالنسبة إلى dirfd.
تأثير هذه العلامة كما لو أن العملية المتصلة قد استخدمت chroot(2) لتغيير دليل الجذر الخاص بها (بشكل مؤقت) (إلى الدليل المشار إليه بواسطة dirfd). ومع ذلك، على عكس chroot(2) (التي تغير جذر نظام الملفات بشكل دائم للعملية)، تسمح RESOLVE_IN_ROOT للبرنامج بتقييد حل المسارات بكفاءة على أساس فتح كل مرة.
حاليًا، هذه العلامة تتعطل أيضًا حل الروابط السحرية. ومع ذلك، قد يتغير هذا في المستقبل. لذلك، لضمان عدم حل الروابط السحرية، يجب على المتصل تحديد RESOLVE_NO_MAGICLINKS بشكل صريح.
RESOLVE_NO_MAGICLINKS
رفض جميع حلول الروابط السحرية أثناء حل المسار.
الروابط السحرية هي كائنات شبيهة بالروابط الرمزية الموجودة بشكل أساسي في proc(5)؛ تشمل الأمثلة /proc/pid/exe و /proc/pid/fd/*. (انظر symlink(7) لمزيد من التفاصيل.)
قد يكون فتح الروابط السحرية دون علم خطرًا على بعض التطبيقات. تشمل أمثلة مثل هذه المخاطر ما يلي:
•
إذا كانت العملية التي تفتح اسم مسار هي عملية تحكم ليس لديها حاليًا طرفية تحكم (انظر credentials(7))، فإن فتح رابط سحري داخل /proc/pid/fd والذي يشير عن طريق الصدفة إلى طرفية سيؤدي إلى اكتساب العملية طرفية تحكم.
•
في بيئة حاويات، قد يشير رابط سحري داخل /proc إلى كائن خارج الحاوية، وبالتالي قد يوفر وسيلة للهروب من الحاوية.
بسبب هذه المخاطر، قد تفضل التطبيقات تعطيل حل الروابط السحرية باستخدام علامة RESOLVE_NO_MAGICLINKS.
إذا كان المكون الأخير (أي اسم الأساس) لـ path رابطًا سحريًا، وكان how.resolve يحتوي على RESOLVE_NO_MAGICLINKS، و how.flags يحتوي على كل من O_PATH و O_NOFOLLOW، فسيتم إرجاع واصف ملف O_PATH يشير إلى الرابط السحري.
RESOLVE_NO_SYMLINKS
رفض حل الروابط الرمزية أثناء حل المسار. هذا الخيار يتضمن RESOLVE_NO_MAGICLINKS.
إذا كان المكون الأخير (أي اسم الأساس) لـ path رابطًا رمزيًا، وكان how.resolve يحتوي على RESOLVE_NO_SYMLINKS، و how.flags يحتوي على كل من O_PATH و O_NOFOLLOW، فسيتم إرجاع واصف ملف O_PATH يشير إلى الرابط الرمزي.

It takes the following arguments: * ``dirfd``: A file descriptor. If path is relative, it is interpreted relative to the directory referred to by dirfd (unless dirfd is specified as ``AT_FDCWD``, in which case path is interpreted relative to the current working directory). If path is absolute, then dirfd is ignored. * ``path``: The path to the file or directory to be opened. * ``how``: A pointer to a ``struct open_how`` structure, which specifies the open operation. The structure is defined as follows: ```c struct open_how { int flags; /* Flags for open() and openat() */ long long resolve; /* Flags for path resolution */ /* ... future extensions ... */ }; ``` The ``flags`` field contains flags that are passed to openat(2). The ``resolve`` field contains flags that control path resolution. * ``size``: The size of the ``struct open_how`` structure. This is used for extensibility, allowing new fields to be added to the structure in the future without breaking compatibility with older applications. The ``resolve`` field can be set to the bitwise OR of the following flags:
RESOLVE_IN_ROOT
Causes the entire path to be resolved relative to the root directory (``/``). This is a more secure way to resolve paths, as it prevents symlink attacks that could occur if the path were resolved relative to a user-controlled directory. This flag implies RESOLVE_BENEATH, and therefore requires that the path be fully contained within the directory specified by dirfd (or the current working directory if dirfd is ``AT_FDCWD``).
RESOLVE_BENEATH
Causes the entire path to be resolved relative to the directory specified by dirfd (or the current working directory if dirfd is ``AT_FDCWD``). This flag is useful for preventing directory traversal attacks, where an attacker might try to use a path like ``../../../../etc/passwd`` to access sensitive files. With RESOLVE_BENEATH, such a path would be resolved relative to dirfd, and would likely result in an error if it attempted to escape the directory hierarchy of dirfd.
RESOLVE_NO_MAGICLINKS
Disallows traversal of magic links. Magic links are a security feature that allows certain directories to be treated as symbolic links, but only if the path resolution is performed with the appropriate flags. This flag prevents the use of magic links, ensuring that the path is resolved as a regular file system path.
RESOLVE_NO_SYMLINKS
Disallows traversal of symbolic links in any component of path. This flag prevents the resolution of symbolic links, ensuring that the path is resolved to the actual file or directory. Note that the effect of the RESOLVE_NO_SYMLINKS flag, which affects the treatment of symbolic links in all of the components of path, differs from the effect of the O_NOFOLLOW file creation flag (in how.flags), which affects the handling of symbolic links only in the final component of path.
Applications that employ the RESOLVE_NO_SYMLINKS flag are encouraged to make its use configurable (unless it is used for a specific security purpose), as symbolic links are very widely used by end-users. Setting this flag indiscriminately—i.e., for purposes not specifically related to security—for all uses of openat2() may result in spurious errors on previously functional systems. This may occur if, for example, a system pathname that is used by an application is modified (e.g., in a new distribution release) so that a pathname component (now) contains a symbolic link.
RESOLVE_NO_XDEV
Disallow traversal of mount points during path resolution (including all bind mounts). Consequently, path must either be on the same mount as the directory referred to by dirfd, or on the same mount as the current working directory if dirfd is specified as AT_FDCWD.
Applications that employ the RESOLVE_NO_XDEV flag are encouraged to make its use configurable (unless it is used for a specific security purpose), as bind mounts are widely used by end-users. Setting this flag indiscriminately—i.e., for purposes not specifically related to security—for all uses of openat2() may result in spurious errors on previously functional systems. This may occur if, for example, a system pathname that is used by an application is modified (e.g., in a new distribution release) so that a pathname component (now) contains a bind mount.
RESOLVE_CACHED (since Linux 5.12)
Make the open operation fail unless all path components are already present in the kernel's lookup cache. If any kind of revalidation or I/O is needed to satisfy the lookup, openat2() fails with the error EAGAIN. This is useful in providing a fast-path open that can be performed without resorting to thread offload, or other mechanisms that an application might use to offload slower operations.
If any bits other than those listed above are set in how.resolve, an error is returned.

FreeBSD's O_RESOLVE_BENEATH semantics are based on Linux's RESOLVE_BENEATH and the two are now functionally equivalent. - type: section title: NOTES content: | Section: Extensibility In order to allow for future extensibility, openat2() requires the user-space application to specify the size of the open_how structure that it is passing. By providing this information, it is possible for openat2() to provide both forwards- and backwards-compatibility, with size acting as an implicit version number. (Because new extension fields will always be appended, the structure size will always increase.) This extensibility design is very similar to other system calls such as sched_setattr(2), perf_event_open(2), and clone3(2). If we let usize be the size of the structure as specified by the user-space application, and ksize be the size of the structure which the kernel supports, then there are three cases to consider:
  • If ksize equals usize, then there is no version mismatch and how can be used verbatim.
  • If ksize is larger than usize, then there are some extension fields that the kernel supports which the user-space application is unaware of. Because a zero value in any added extension field signifies a no-op, the kernel treats all of the extension fields not provided by the user-space application as having zero values. This provides backwards-compatibility.
  • If ksize is smaller than usize, then there are some extension fields which the user-space application is aware of but which the kernel does not support. Because any extension field must have its zero values signify a no-op, the kernel can safely ignore the unsupported extension fields if they are all-zero. If any unsupported extension fields are nonzero, then -1 is returned and errno is set to E2BIG. This provides forwards-compatibility.
Because the definition of struct open_how may change in the future (with new fields being added when system headers are updated), user-space applications should zero-fill struct open_how to ensure that recompiling the program with new headers will not result in spurious errors at run time. The simplest way is to use a designated initializer:

```c struct open_how how = { .flags = O_RDWR, .resolve = RESOLVE_IN_ROOT }; ``` or explicitly using memset(3) or similar:
