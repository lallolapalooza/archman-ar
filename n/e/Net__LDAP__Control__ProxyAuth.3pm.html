Net__LDAP__Control__ProxyAuth(3pm)

الحزمة: perl-ldap

التراخيص: GPL

Net::LDAP::Control::ProxyAuth(3) وثائق بيرل مساهم بها من المستخدم Net::LDAP::Control::ProxyAuth(3)

الاسم

Net::LDAP::Control::ProxyAuth - كائن تحكم في تفويض وكالة LDAPv3

الملخص

use Net::LDAP;
use Net::LDAP::Control::ProxyAuth;
$ldap = Net::LDAP->new( "ldap.mydomain.eg" );
$auth = Net::LDAP::Control::ProxyAuth->new( authzID => 'dn:cn=me,ou=people,o=myorg.com' );
@args = ( base     => "cn=subnets,cn=sites,cn=configuration,$BASE_DN",
          scope    => "subtree",
          filter   => "(objectClass=subnet)",
          callback => \&process_entry, # استدعاء هذه الدالة الفرعية لكل إدخال
          control  => [ $auth ],
);
while (1) {
  # إجراء البحث
  my $mesg = $ldap->search( @args );
  # الاستمرار فقط عند نجاح LDAP
  $mesg->code and last;
}

الوصف

"Net::LDAP::Control::ProxyAuth" يوفر واجهة لإنشاء ومعالجة الكائنات التي تمثل "تحكم تفويض الوكالة" كما هو موضح في RFC 4370.

يسمح للعميل بالارتباط بخادم LDAP بهويته الخاصة، ولكن لتنفيذ عمليات نيابة عن مستخدم آخر، "authzID".

باستثناء أي امتداد يسبب تغييرًا في المصادقة أو الترخيص أو سرية البيانات، يمكن تضمين "تحكم تفويض الوكالة" واحد في أي عملية بحث أو مقارنة أو تعديل أو إضافة أو حذف أو moddn أو عملية موسعة.

كما هو مطلوب بموجب RFC، يتم تعيين أهمية هذا التحكم تلقائيًا إلى TRUE لحماية العملاء من تقديم طلبات بهويات غير هوياتهم المقصودة.

وسيطات المُنشئ

بالإضافة إلى وسيطات المُنشئ الموضحة في Net::LDAP::Control، يتم توفير ما يلي.

authzID
معرف التفويض المطلوب. هذا هو الهوية التي نطلب استخدام العمليات لها.
proxyDN
في الإصدارات المبكرة من المسودات إلى RFC 4370، draft-weltman-ldapv3-proxy-XX.txt، كانت القيمة في التحكم وبالتالي وسيطة المُنشئ عبارة عن DN وتم تسميتها "proxyDN". وقد خدمت نفس الغرض مثل "authzID" في الإصدارات الحديثة من تحكم "proxyAuthorization".

يرجى ملاحظة: لسوء الحظ، تغير OID وتشفير أو "تحكم تفويض الوكالة" بشكل كبير بين الإصدارات المبكرة من draft-weltman-ldapv3-proxy-XX.txt و RFC النهائي. يحاول Net::LDAP::Control::ProxyAuth التعامل مع هذا الوضع وتغيير OID والتشفير المستخدم اعتمادًا على وسيطة المُنشئ.

مع "proxyDN" كوسيطة مُنشئ، يتم استخدام OID والتشفير القديمين، بينما مع "authzID" كوسيطة مُنشئ، يتم استخدام OID والتشفير الجديدين. باستخدام هذا المنطق، يمكن التعامل مع الخوادم التي تدعم أيًا من OIDs بشكل صحيح.

الطرق

كما هو الحال مع Net::LDAP::Control، كل وسيطة مُنشئ موصوفة أعلاه متاحة أيضًا كطريقة على الكائن والتي ستعيد القيمة الحالية للسمة إذا تم استدعاؤها بدون وسيطة، وتقوم بتعيين قيمة جديدة للسمة إذا تم استدعاؤها مع وسيطة.
