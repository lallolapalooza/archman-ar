يعيد تشغيل جلسة SSH عن طريق إغلاق أي اتصال مفتوح وإنشاء اتصال جديد. سيتم أيضًا إنهاء أي قناة مفتوحة.

لاحظ أن استدعاء هذه الطريقة قد يطلب كلمة المرور أو عبارة المرور من المستخدم مرة أخرى.

في الوضع غير المتزامن، تتطلب هذه الطريقة أن يكون الاتصال قد انتهى قبل استدعائها. بعد ذلك، يجب استدعاء "wait_for_master" بشكل متكرر حتى يتم إنشاء الاتصال الجديد. على سبيل المثال:

my $async = 1;
$ssh->disconnect($async);
while (1) {
  defined $ssh->wait_for_master($async) # يعيد 0 عندما تنتهي
                                        # عملية الإنهاء
    and last;
  do_something_else();
}
$ssh->restart($async);
while (1) {
  defined $ssh->wait_for_master($async)
    and last;
  do_something_else();
}
$pid = $ssh->sshfs_import(\%opts, $remote_fs, $local_mnt_point)
$pid = $ssh->sshfs_export(\%opts, $local_fs, $remote_mnt_point)
تستخدم هذه الطرق sshfs(1) لاستيراد أو تصدير نظام ملفات عبر اتصال SSH.

تعيد معرف العملية $pid لعملية "sshfs" أو لعملية "ssh" التابعة المستخدمة لتمثيلها. إنهاء تلك العملية يفك تحميل نظام الملفات، على الرغم من أنه قد يكون من الأفضل استخدام fusermount(1).

الخيارات المقبولة هي كما يلي:

ssh_opts => \@ssh_opts
الخيارات التي تم تمريرها إلى عملية "ssh" التابعة.
sshfs_opts => \@sshfs_opts
الخيارات التي تم تمريرها إلى أمر "sshfs". على سبيل المثال، لتحميل نظام الملفات في وضع القراءة فقط: 
my $pid = $ssh->sshfs_export({sshfs_opts => [-o => 'ro']},
                             "/", "/mnt/foo");

لاحظ أن هذا الأمر يتطلب إصدارًا حديثًا من "sshfs" ليعمل (في وقت كتابة هذه السطور، يتطلب الإصدار الذي لم يتم إصداره بعد والمتاح من مستودع FUSE git!).

في بعض الحالات (النادرة)، من المرغوب فيه ترك العملية الرئيسية وجميع الاتصالات قيد التشغيل على قيد الحياة. القيام بذلك بهذه الطريقة، تخبر كائن Net::OpenSSH بأن العملية الرئيسية لم تعد ملكه.

اقتباس الواجهة الطرفية (Shell quoting)

بشكل افتراضي، عند استدعاء أوامر بعيدة، تحاول هذه الوحدة محاكاة السلوك المدمج في Perl `system` فيما يتعلق بمعالجة الوسائط. اقتباس `system` في perlfunc:

يختلف معالجة الوسائط اعتمادًا على عدد الوسائط. إذا كان هناك أكثر من وسيط
واحد في LIST، أو إذا كان LIST مصفوفة تحتوي على أكثر من قيمة واحدة، يبدأ البرنامج
المعطى بالعنصر الأول من القائمة مع الوسائط المعطاة ببقية القائمة. إذا كان هناك
وسيط قياسي واحد فقط، يتم فحص الوسيط بحثًا عن الأحرف الوصفية (metacharacters)
للواجهة الطرفية، وإذا وجدت، يتم تمرير الوسيط بأكمله إلى مفسر أوامر الواجهة
الطرفية للتحليل (هذا هو "/bin/sh -c" على أنظمة Unix، ولكنه يختلف على أنظمة
أخرى).

خذ على سبيل المثال طريقة `system` الخاصة بـ Net::OpenSSH:

$ssh->system("ls -l *");
$ssh->system('ls', '-l', '/');

ينفذ الاستدعاء الأول الوسيط دون تغيير إلى ssh ويتم تنفيذه على الجانب البعيد من خلال الواجهة الطرفية التي تفسر الأحرف الوصفية.

ينشئ الاستدعاء الثاني أي أحرف وصفية للواجهة الطرفية بحيث يكون، بشكل فعال، مكافئًا لاستدعاء الأمر مباشرة وليس من خلال الواجهة الطرفية.

تحت الغطاء، نظرًا لأن بروتوكول Secure Shell لا يوفر هذا الوضع من التشغيل ويقوم دائمًا بإنشاء واجهة طرفية جديدة حيث يقوم بتشغيل الأمر المعطى، تقوم Net::OpenSSH باقتباس أي أحرف وصفية للواجهة الطرفية في قائمة الأوامر.

تقبل جميع الطرق التي تستدعي أمرًا بعيدًا (system، open_ex، إلخ) الخيار "quote_args" الذي يسمح بفرض/تعطيل اقتباس الواجهة الطرفية.

على سبيل المثال:

$ssh->system({quote_args => 1}, "/path with spaces/bin/foo");

سيتعامل بشكل صحيح مع المسافات في مسار البرنامج.

تنفيذ آلية اقتباس الواجهة الطرفية بعض الامتدادات (على سبيل المثال، تنفيذ عمليات إعادة التوجيه إلى /dev/null على الجانب البعيد) التي يمكن تعطيلها باستخدام الخيار "quote_args_extended":

$ssh->system({ stderr_discard => 1,
               quote_args => 1, quote_args_extended => 0 },
             @cmd);

يمكن أيضًا استخدام الخيار "quote_args" لتعطيل الاقتباس عندما يتم تمرير أكثر من وسيط واحد. على سبيل المثال، للحصول على بعض الأنماط التي يتم توسيعها بواسطة الواجهة الطرفية البعيدة:

$ssh->system({quote_args => 0}, 'ls', '-l', "/tmp/files_*.dat");

يمكن استخدام الطريقة "shell_quote" لاقتباس بعض الوسائط بشكل انتقائي وترك الأخرى دون تغيير:

$ssh->system({quote_args => 0},
             $ssh->shell_quote('ls', '-l'),
             "/tmp/files_*.dat");

عندما يتم تعيين خيار glob في "scp" و "rsync" fi

التنفيذ المتزامن للتخزين المؤقت للاتصال ، على سبيل المثال:

my $old_factory = $Net::OpenSSH::FACTORY;
my %cache;
sub factory {
  my ($class, %opts) = @_;
  my $signature = join("\0", $class, map { $_ => $opts{$_} }, sort keys %opts);
  my $old = $cache{$signature};
  return $old if ($old and $old->error != OSSH_MASTER_FAILED);
  local $Net::OpenSSH::FACTORY = $old_factory;
  $cache{$signature} = $class->new(%opts);
}
$Net::OpenSSH::FACTORY = \&factory;

... وأنا متأكد من أنه يمكن إساءة استخدامه بعدة طرق أخرى!

استخدم مؤقتًا لاستدعاء الطريقة في الوضع غير المتزامن بشكل متكرر حتى ترجع قيمة صحيحة تشير إلى النجاح.

أيضًا ، يجب التحقق من حالة خطأ الكائن بعد كل استدعاء لاكتشاف الاتصالات الفاشلة. على سبيل المثال:

my $ssh = Net::OpenSSH->new(..., async => 1);

$w = AE::timer 0.1, 0.1, sub {
  if ($ssh->wait_for_master(1)) {
    # تم إنشاء الاتصال!
    # يمكن تشغيل الأوامر البعيدة الآن
    undef $w;
    on_ssh_success(...);
  }
  elsif ($ssh->error) {
    # لا يمكن إنشاء الاتصال
    undef $w;
    on_ssh_failure(...);
  }
}

استدعاء Net::OpenSSH لإنشاء أوامر يمكن تشغيلها باستخدام المرافق العادية للإطار لإطلاق الأوامر الخارجية.

if (defined(my $cmd = $ssh->make_remote_command(echo => 'hello!')) {

else {

}

4. عند الانتهاء ، قم بقطع الاتصال بشكل غير متزامن

$ssh->disconnect(1);
my $w; $w = AE::timer 0.1, 0.1, sub {

استكشاف الأخطاء وإصلاحها

عادةً ما تعمل Net::OpenSSH بشكل طبيعي ، ولكن عندما تفشل ، يجد بعض المستخدمين صعوبة في تحديد سبب المشكلة. يجب أن يساعدك دليل استكشاف الأخطاء وإصلاحها المصغر هذا في العثور عليه وحله.

1 - تحقق من رسالة الخطأ
أضف في نصك البرمجي ، بعد استدعاء مُنشئ Net::OpenSSH ، فحص خطأ: 
$ssh = Net::OpenSSH->new(...);
$ssh->error and die "SSH connection failed: " . $ssh->error;

ستخبرك رسالة الخطأ بما حدث خطأ.

2 - تحقق من معلمات الاتصال
صدق أو لا تصدق ، فإن تمرير معلمات خاطئة إلى Net::OpenSSH يتحول إلى أحد الأسباب الرئيسية للفشل ، لذا تحقق من أنك تستخدم المعلمات الصحيحة.

على وجه التحديد ، إذا كنت تحصل عليها من الخارج ، فتأكد من عدم وجود مسافات إضافية أو أسطر جديدة مرفقة (هل تحتاج إلى ؟).

قد تحتوي كلمات المرور وعناوين URI على أحرف أو . إذا كنت قد قمت بتضمينها في النص البرمجي الخاص بك ، فتأكد من أن هذه الأحرف محاطة بشكل صحيح (وبالمناسبة ، استخدم ).

3 - إصدار OpenSSH
تأكد من أن لديك إصدارًا من حديثًا بما فيه الكفاية: 
$ ssh -V
OpenSSH_5.1p1 Debian-5, OpenSSL 0.9.8g 19 Oct 2007

كان إصدار OpenSSH 4.1 هو الأول الذي يدعم ميزة تعدد الإرسال وهو الحد الأدنى المطلوب لكي تعمل الوحدة. أنصحك باستخدام أحدث إصدار من OpenSSH (حاليًا 7.5).

خيار المُنشئ يتيح لك تحديد ثنائي المراد استخدامه. على سبيل المثال:

$ssh = Net::OpenSSH->new($host,
                         ssh_cmd => "/opt/OpenSSH/5.8/bin/ssh")

يقوم بعض بائعي الأجهزة (على سبيل المثال ، Sun ، آه ... Oracle) بتضمين إصدارات مخصصة من OpenSSH مجمعة مع نظام التشغيل. من حيث المبدأ ، يجب أن تعمل Net::OpenSSH مع هؤلاء العملاء SSH طالما أنها مشتقة من إصدار حديث بما فيه الكفاية من OpenSSH. على أي حال ، نصيحتي هي استخدام برنامج OpenSSH الحقيقي إذا استطعت!

4 - تشغيل ssh من سطر الأوامر
تحقق من أنه يمكنك الاتصال بالمضيف البعيد باستخدام نفس المعلمات التي تمررها إلى Net::OpenSSH. على وجه الخصوص ، تأكد من أنك تقوم بتشغيل ك نفس المستخدم المحلي.

إذا كنت تقوم بتشغيل نصك البرمجي من خادم ويب ، فمن المحتمل أن يكون المستخدم أو أو شيء من هذا القبيل.

المشاكل الشائعة هي:

  • المفتاح العام للمضيف البعيد غير موجود في ملف known_hosts.

    يستخدم بروتوكول SSH مفاتيح عامة لتحديد المضيفين البعيدين حتى لا يتم استبدالهم من قبل بعض الأطراف الثالثة الخبيثة.

    بالنسبة لـ OpenSSH ، عادةً ما يتم تخزين المفتاح العام للخادم في

  • "/etc/ssh/ssh_host_dsa_key.pub" أو "/etc/ssh/ssh_host_rsa_key.pub" والمفتاح الذي يجب نسخه في ملف "~/.ssh/known_hosts" على الجهاز المحلي (قد تستخدم تطبيقات SSH أخرى مواقع ملفات مختلفة).
  • المفتاح العام للمضيف البعيد في ملف الأكواع غير صحيح.

    هذه مشكلة شائعة أخرى تحدث عندما يتم استبدال خادم أو إعادة تشغيله من الصفر ويتغير مفتاحه العام ليختلف عن المفتاح المثبت في ملف الأكواع.

    أسهل طريقة لحل هذه المشكلة هي حذف المفتاح القديم يدويًا من ملف الأكواع باستخدام أي محرر، ثم الاتصال بالخادم، والرد بـ "yes" عند سؤالك عن المفتاح الجديد.

  • أذونات غير صحيحة على الدليل "~/.ssh" أو محتوياته.

    يقوم عميل OpenSSH بإجراء العديد من عمليات التحقق على أذونات الدليل "~/.ssh" ومحتوياته ويرفض استخدامها عندما تكون مهيأة بشكل غير صحيح. راجع قسم FILES في صفحة دليل ssh(1).

  • تهيئة غير صحيحة للمصادقة بكلمة المرور أو المفتاح العام.

    تحقق من أنك تستخدم كلمة المرور الصحيحة أو أن المفتاح العام للمستخدم مثبت بشكل صحيح على الخادم.

5 - فحوصات الأمان على مقبس التعدد
يقوم Net::OpenSSH بإجراء بعض فحوصات الأمان على الدليل الذي سيتم وضع مقبس التعدد فيه للتأكد من عدم إمكانية الوصول إليه من قبل مستخدمين آخرين.

الموقع الافتراضي لمقبس التعدد هو ضمن "~/.libnet-openssh-perl". يمكن تعديله باستخدام وسائط "ctl_dir" و "ctl_path" لفئة المنشئ.

متطلبات هذا الدليل وأدلته الأصلية هي:

  • يجب أن يكونوا جميعًا مملوكين للمستخدم الذي يقوم بتشغيل البرنامج النصي أو للجذر (root).
  • يجب أن يكون لديهم حد أذونات 0755 أو أكثر تقييدًا، بحيث لا يتمكن أي شخص آخر من إجراء عمليات كتابة عليها.

يقوم خيار المنشئ "strict_mode" بتعطيل فحوصات الأمان هذه، ولكن لا يجب استخدامه ما لم تفهم آثاره.

6 - يجب أن يدعم نظام الملفات المقابس
لا تدعم بعض أنظمة الملفات (مثل FAT أو AFS على سبيل المثال) وضع المقابس بداخلها.

تأكد من أن المسار "ctl_dir" ليس ضمن أنظمة الملفات هذه.

تصحيح الأخطاء (DEBUGGING)

يتم التحكم في تصحيح أخطاء Net::OpenSSH الداخلية بواسطة المتغير $Net::OpenSSH::debug. يقوم كل بت من هذا المتغير بتفعيل تصحيح أخطاء بعض الأنظمة الفرعية وفقًا لما يلي:

البت 1 - الأخطاء
يطبع التغييرات في السمة الداخلية للكائن حيث يتم تخزين الأخطاء.
البت 2 - ctl_path
يطبع معلومات حول حساب ctl_path والاختبارات التي تم إجراؤها على هذا الدليل لتحديد ما إذا كان من الآمن وضع مقبس التعدد بداخله.
البت 4 - الاتصال
يطبع معلومات حول إنشاء اتصالات رئيسية جديدة.
البت 8 - الأوامر والوسائط
يطبع الأوامر والوسائط لكل استدعاء نظام / exec.
البت 16 - تنفيذ الأوامر
يطبع معلومات حول تقدم تنفيذ الأوامر.
البت 32 - التدمير
يطبع معلومات حول تدمير كائنات Net::OpenSSH وإنهاء عمليات SSH الرئيسية.
البت 64 - حلقة_IO
يطبع معلومات حول تقدم حلقة_IO في عمليات الالتقاط.
البت 128 - hexadumps
ينشئ hexadumps للمعلومات التي تمر عبر قنوات SSH أثناء الالتقاط.
البت 512 - تتبع العملية الرئيسية على نظام التشغيل
يستخدم الوحدة Net::OpenSSH::OSTracer لتتبع عملية SSH الرئيسية على مستوى نظام التشغيل.

على سبيل المثال، لتفعيل جميع علامات تصحيح الأخطاء، يمكنك استخدام:

$Net::OpenSSH::debug = ~0;

لاحظ أن معنى العلامات والمعلومات التي تم إنشاؤها مخصص فقط لتصحيح أخطاء الوحدة وقد يتغير دون إشعار بين الإصدارات.

إذا كنت تستخدم المصادقة بكلمة المرور، فإن تفعيل تصحيح الأخطاء لـ IO::Tty يمكن أن يعرض أيضًا معلومات مثيرة للاهتمام:

$IO::Tty::DEBUG = 1;

أخيرًا، افتراضيًا، يتم إرسال مخرجات تصحيح الأخطاء إلى "STDERR". يمكنك تغييره عن طريق توجيه $Net::OpenSSH::debug_fh إلى مقبض ملف مختلف. على سبيل المثال:

BEGIN {
  open my $out, '>', '/tmp/debug.txt or warn $!;
  $Net::OpenSSH::debug_fh = $out;
  $Net::OpenSSH::debug = -1;
}

الأمان

هل هذه الوحدة آمنة؟

نعم؟ حسناً، إنها تحاول أن تكون كذلك!

من منظور أمني، هدف هذه الوحدة هو أن تكون آمنة مثل OpenSSH، ونظام التشغيل الخاص بك، والطرفية الخاصة بك، وبيئتك بشكل عام.

لا تتخذ أي إجراءات مجاملة فقط لجعل حياتك أسهل إذا كان ذلك يعني تقليل مستوى الأمان (على سبيل المثال، تعطيل "StrictHostKeyChecking" افتراضيًا).

في ميزات الكود التي ليست مجرد بروكسيات لـ OpenSSH، تحاول الوحدة الحفاظ على نفس معايير الأمان مثل OpenSSH (على سبيل المثال، التحقق من أذونات الدلائل والملفات عند وضع مقبس التعدد).

من ناحية أخرى، باتباع فلسفة OpenSSH، تسمح الوحدة بتعطيل معظم (كل؟) هذه الإجراءات الأمنية. ولكن لمجرد أنها تسمح بذلك، لا يعني أن استخدامها فكرة جيدة!

إذا كنت مبرمجًا جديدًا أو مستخدمًا لـ SSH، وقد وجدت عند البحث عن معلمات لا تفهمها ولكن يبدو أنها تحل مشاكل الاتصال الخاصة بك... ثق بي، من المحتمل أن يكون استخدامها فكرة سيئة! اسأل شخصًا يعرف الموضوع حقًا!

لتوضيح الأمر، إذا كان الكود الخاص بك يحتوي على أي من الكلمات الرئيسية في القائمة التالية (ولا تعرف لماذا)، فمن المحتمل أنك تضر بأمان بروتوكول SSH:

strict_mode
StrictHostKeyChecking
UserKnownHostsFile

جوانب الأمان الأخرى التي قد ترغب في معرفتها هي:

وضع_الوصم (Taint mode)
تدعم الوحدة وضع_الوصم.

إذا كنت في بيئة معرضة للخطر، فيجب عليك تمكين هذا الوضع في برنامجك النصي لالتقاط أي أوامر غير مدققة يتم تشغيلها على الجانب البعيد.

بيئات_الويب
إن إنشاء اتصالات SSH من خادم الويب الخاص بك فكرة سيئة لأنه إذا تم اختراقه، يمكن للمهاجم استخدام بيانات اعتماد البرنامج النصي الخاص بك للاتصال بالمضيف البعيد والقيام بأي شيء يريده.
تنفيذ_الأوامر
يمكن للوحدة أن تمارس الاقتباس (quoting) للأوامر والوسائط بمرونة وقوة.

هذه ميزة يجب عليك استخدامها لأنها تقلل من احتمال أن يتمكن المهاجم من حقن وتشغيل أوامر عشوائية على المضيف البعيد (وحتى بالنسبة للبرامج النصية غير المعرضة للخطر، يُنصح دائمًا بتمكين اقتباس الوسائط).

ومع ذلك، ضع في اعتبارك أن اقتباس الوسائط هو مجرد خدعة لمحاكاة وظيفة الاستدعاء بدون shell لوظائف Perl مثل "system" وما شابه ذلك. قد تكون هناك أخطاء في كود الاقتباس، قد يكون للطرفية الخاصة بك قواعد اقتباس مختلفة عن حالات الحافة لمشكلة أو أي شيء مماثل. إذا كان البرنامج النصي الخاص بك معرضًا خارجيًا، فيجب عليك مراجعة مدخلاتك والحد من ما تقبله كصالح.

[* حتى لو كان هذا جزءًا تم اختباره بكثافة من الوحدة!]

Shellshock
(انظر Shellshock http://en.wikipedia.org/wiki/Shellshock_%28software_bug%29)

عند تنفيذ أوامر محلية، تتجنب الوحدة دائمًا استدعاء الطرفية، لذلك لا تتأثر بـ Shellshock.

ومع ذلك، تستدعي بعض الأوامر ("scp"، "rsync" و "ssh" عند استخدام خيار "ProxyCommand") أوامر أخرى تحت طرفية المستخدم. هذا يفتح الباب لاستغلال Shellshock المحلي.

استدعاء الطرفية على الجانب البعيد لا مفر منه بسبب بنية البروتوكول.

افتراضيًا، لا ترسل SSH متغيرات البيئة، ولكن بعض توزيعات Linux تغير بشكل صريح إعدادات OpenSSH الافتراضية لتمكين إرسال وقبول بعض المتغيرات المحددة (على سبيل المثال، "LANG" و "LC_*" في Debian ومشتقاتها، و Fedora تفعل ذلك أيضًا). هذا يفتح الباب أيضًا لاستغلال Shellshock.

لاحظ أن الطرفية المستخدمة لاستدعاء الأوامر ليست "/bin/sh" ولكنها طرفية المستخدم المكونة في "/etc/passwd"، PAM أو أي نظام مصادقة آخر مستخدم في النظام المحلي أو البعيد. مستخدمو Debian، لا تقلقوا بشأن التأثر لأن "/bin/sh" الخاص بكم يشير إلى "dash"!

أسئلة متكررة

أسئلة متكررة حول الوحدة:

الاتصال بالمفاتيح، والموجهات، إلخ.

س: لا يمكنني جعل طريقة "system"، "capture"، إلخ، تعمل عند الاتصال ببعض الموجهات، المفاتيح، إلخ. ما الذي أفعله بشكل خاطئ؟

ج: بشكل عام، يسمح بروتوكول SSH بنمطين من التشغيل: نمط الأوامر ونمط التفاعل.

نمط الأوامر مصمم لتشغيل أوامر فردية على المضيف البعيد. يقوم بفتح قناة SSH بين كلا المضيفين، ويطلب من الكمبيوتر البعيد تشغيل أمر معين، وعندما ينتهي، يتم إغلاق القناة. هذا ما تحصل عليه، على سبيل المثال، عندما تقوم بتشغيل شيء ما مثل...

$ ssh my.unix.box cat foo.txt

... وهذه هي الطريقة التي تشغل بها Net::OpenSSH الأوامر على المضيف البعيد.

نمط التفاعل يشغل قشرة على المضيف البعيد مع إعادة توجيه تدفقات الإدخال/الإخراج القياسية إلى التدفقات المحلية حتى يتمكن المستخدم من التفاعل معها بشفافية.

بعض الأجهزة (كما هو الحال على الأرجح مع الجهاز الذي تستخدمه) لا تشغل قشرة قياسية للأغراض العامة (مثل "bash"، "csh"، أو "ksh") ولكن برنامجًا مخصصًا ومحدودًا بشكل خاص لمهمة تكوين الجهاز.

عادةً، لا يدعم خادم SSH الذي يعمل على هذه الأجهزة نمط الأوامر. يقوم بربط القشرة المقيدة بشكل غير مشروط بأي اتصال SSH وارد وينتظر من المستخدم إدخال الأوامر من خلال تدفق الإدخال القياسي المعاد توجيهه.

الطريقة الوحيدة للتغلب على هذا القيد هي جعل النص البرمجي الخاص بك يتحدث إلى القشرة المقيدة (1-فتح جلسة SSH جديدة، 2-الانتظار حتى يظهر موجه القشرة، 3-إرسال أمر، 4-قراءة الإخراج حتى تصل إلى موجه القشرة مرة أخرى، كرر من 3). أفضل أداة لهذه المهمة هي على الأرجح Expect، المستخدمة بمفردها أو بالاشتراك مع Net::OpenSSH (انظر "Expect").

هناك بعض الأجهزة التي تدعم نمط الأوامر ولكنها تقبل أمرًا واحدًا فقط لكل اتصال. في هذه الحالات، ربما يكون استخدام Expect هو الخيار الأفضل أيضًا.

في الوقت الحاضر، هناك لاعب جديد، Net::CLI::Interact، قد يكون أكثر ملاءمة من Expect، و Net::Appliance::Session للعمل خصيصًا مع أجهزة الشبكة.

فشل الاتصال

س: أنا غير قادر على جعل الوحدة تتصل بالمضيف البعيد...

ج: هل قرأت قسم استكشاف الأخطاء وإصلاحها؟ (انظر "TROUBLESHOOTING").

تعطيل StrictHostKeyChecking

س: لماذا لا يتم تشغيل "ssh" باستخدام "StrictHostKeyChecking=no"؟

ج: استخدام "StrictHostKeyChecking=no" يخفف من مستوى الأمان الافتراضي لـ SSH وسيصبح من السهل نسبيًا الانتهاء بتكوين SSH خاطئ (على سبيل المثال، عندما تكون "known_hosts" غير قابلة للكتابة) والتي يمكن تزويرها للاتصال بمضيف سيئ لإجراء هجمات الوسيط، إلخ.

أنصحك بعدم استخدام هذا الخيار ما لم تفهم تمامًا آثاره من وجهة نظر أمنية.

إذا كنت ترغب في استخدامه على أي حال، قم بتمريره إلى المنشئ:

$ssh = Net::OpenSSH->new($host,
    master_opts => [-o => "StrictHostKeyChecking=no"],
    ...);
عملية فرعية STDIN/STDOUT/STDERR ليست مقبض نظام حقيقي

س: فشلت استدعاءات "system"، "capture"، إلخ، مع الخطأ السابق، ما الذي يحدث؟

ج: تدفق الإدخال/الإخراج القياسي المبلغ عنه مغلق أو غير متصل بمقبض ملف حقيقي (على سبيل المثال، هو مقبض مقيد). أعد توجيهه إلى "/dev/null" أو إلى ملف حقيقي:

my $out = $ssh->capture({stdin_discard => 1, stderr_to_stdout => 1},
                   $cmd);

انظر أيضًا مدخل mod_perl أعلاه.

Solaris (و AIX وربما غيرها)

س: كنت أجرب Net::OpenSSH على Solaris ويبدو أنني أواجه مشكلة...

ج: عميل SSH المدمج مع Solaris هو نسخة مبكرة من OpenSSH لا توفر وظيفة تعدد الإرسال المطلوبة بواسطة Net::OpenSSH. سيتعين عليك تثبيت عميل OpenSSH.

تتوفر حزم مجمعة مسبقًا من Sun Freeware (http://www.sunfreeware.com). هناك، اختر إصدار نظام التشغيل الخاص بك وهندسة المعالج، قم بتنزيل حزمة OpenSSH وتبعياتها وقم بتثبيتها. لاحظ أنك لا تحتاج إلى تكوين Solaris لاستخدام خادم OpenSSH "sshd".

تأكد من أن عميل OpenSSH موجود في مسارك قبل عميل "ssh" الخاص بالنظام، أو بدلاً من ذلك، يمكنك تضمين المسار الكامل بشكل ثابت في نصوصك البرمجية على النحو التالي:

$ssh = Net::OpenSSH->new($host,
                  ssh_cmd => '/usr/local/bin/ssh');

AIX وربما بعض أنظمة Unix الأخرى، تتضمن أيضًا عملاء SSH يفتقرون إلى وظيفة تعدد الإرسال ويتطلبون تثبيت OpenSSH الحقيقي.

لا يمكن تغيير دليل العمل

س: أريد تشغيل بعض الأوامر داخل دليل بعيد معين ولكنني غير قادر على تغيير دليل العمل. على سبيل المثال:

$ssh->system('cd /home/foo/bin');
$ssh->systen('ls');

لا يسرد محتويات "/home/foo/bin".

ما الذي أفعله بشكل خاطئ؟

ج: Net::OpenSSH (وبالتالي، جميع وحدات SSH المتاحة من CPAN باستثناء Net::SSH::Expect) تقوم بتشغيل كل أمر في جلسة جديدة، لذا فإن معظم الأوامر المدمجة في القشرة التي يتم تشغيلها لتأثيراتها الجانبية تصبح عديمة الفائدة (مثل "cd"، "export"، "ulimit"، "umask"، إلخ، عادةً، يمكنك سردها بتشغيل "help" من القشرة).

يتمثل الحل البديل في الجمع بين عدة أوامر في أمر واحد، على سبيل المثال:

$ssh->system('cd /home/foo/bin && ls');

لاحظ استخدام عامل تشغيل القشرة "&&" بدلاً من ";" من أجل إيقاف الأمر بمجرد فشل أي من الأوامر الفرعية.

أيضًا، يمكن دمج عدة أوامر في أمر واحد مع الاستمرار في استخدام ميزة الاقتباس متعدد الوسائط على النحو التالي:

$ssh->system(@cmd1, \\'&&', @cmd2, \\'&&', @cmd3, ...);
تشغيل عمليات بعيدة منفصلة

س: أحتاج إلى أن أكون قادرًا على تسجيل الدخول عبر SSH إلى عدة آلات من النص البرمجي الخاص بي، وتشغيل عملية للعمل في الخلفية هناك، ثم العودة فورًا بينما تستمر البرامج البعيدة في العمل...

ج: إذا كانت الأنظمة البعيدة تشغل نوعًا من Unix/Linux، فإن النهج الصحيح هو استخدام nohup(1) الذي سيقوم بفصل العملية البعيدة عن تدفقات الإدخال/الإخراج القياسية وطلب من القشرة تشغيل الأمر في الخلفية. على سبيل المثال:

$ssh->system("nohup $long_running_command &");

أيضًا، قد يكون من الممكن تحويل العملية البعيدة إلى خدمة. إذا كانت مكتوبة بلغة Perl، فيمكنك استخدام App::Daemon لهذا الغرض (في الواقع، هناك العديد من وحدات CPAN التي توفر هذا النوع من الوظائف).

في أي حال، لاحظ أنه لا ينبغي عليك استخدام "spawn" لهذا الغرض.

تم الوصول إلى الحد الأقصى للجلسات (MaxSessions) في الخادم

س: قمت بإنشاء كائن $ssh ثم قمت بعمل نسخ متعددة للعمليات الفرعية التي تستخدم هذا الكائن. عندما يكون عدد العمليات الفرعية أكبر من "MaxSessions" كما هو محدد في تكوين sshd (الافتراضي هو 10)، فإن محاولة إنشاء أوامر بعيدة جديدة ستطالب المستخدم بكلمة المرور.

ج: عندما يتلقى عميل SSH التابع استجابة من الخوادم البعيدة تفيد بأنه تم الوصول إلى الحد الأقصى لعدد الجلسات للاتصال الحالي، فإنه يعود لفتح اتصال مباشر جديد دون المرور عبر مقبس تعدد الإرسال.

لإيقاف حدوث ذلك، يمكن استخدام الحل البديل التالي:

$ssh = Net::OpenSSH->new(host,
    default_ssh_opts => ['-oConnectionAttempts=0'],
    ...);
تشغيل أوامر بعيدة باستخدام sudo

س: كيف يمكنني تشغيل أوامر بعيدة باستخدام "sudo" لتصبح جذرًا أولاً؟

ج: الطريقة الأسهل هي إخبار "sudo" بقراءة كلمة المرور من stdin باستخدام العلامة "-S" وعدم استخدام بيانات الاعتماد المخزنة مؤقتًا باستخدام العلامة "-k". قد ترغب أيضًا في استخدام العلامة "-p" لإخبار "sudo" بطباعة مطالبة فارغة. على سبيل المثال:

my @out = $ssh->capture({ stdin_data => "$sudo_passwd\n" },
                   'sudo', '-Sk',
                   '-p', '',
                   '--',
                   @cmd);

إذا كان إصدار sudo المثبت على المضيف البعيد لا يدعم العلامة "-S" (تخبر sudo بقراءة كلمة المرور من تدفق STDIN الخاص بها)، فيمكنك القيام بذلك على النحو التالي:

my @out = $ssh->capture({ tty => 1,
                     stdin_data => "$sudo_passwd\n" },
                   'sudo', '-k',
                   '-p', '',
                   '--',
                   @cmd);

قد يؤدي هذا إلى تحذير غير ضروري وغير ضار من اتصال SSH الرئيسي (لأننا نطلب تخصيص tty على الجانب البعيد ونقوم محليًا بتوصيله بزوج من الأنابيب العادية).

إذا فشلت الطرق المذكورة أعلاه لأي سبب، فيمكنك دائمًا العودة إلى استخدام Expect للتحدث مع "sudo" البعيد. انظر البرنامج النصي "examples/expect.pl" من توزيع هذه الوحدة.

تفاعلي
الجلسات
س: كيف يمكنني بدء جلسة تفاعلية عن بعد؟

ج: فقط قم باستدعاء الدالة "system" مع قائمة وسائط فارغة:

my $ssh = Net::OpenSSH->new(...);
$ssh->system;

س: ماذا عن تشغيل جلسة "sftp" تفاعلية؟

ج: البرامج التي تستخدم اتصال SSH أساسي عادة ما توفر طريقة ما (على سبيل المثال، خيار سطر الأوامر ) لتمرير خيارات إضافية لأمر "ssh" المستخدم لتشغيل هذا الاتصال. نحن فقط نحتاج إلى استخدام هذه الآلية لتمرير مسار مقبس التحكم.

على سبيل المثال، بالنسبة للحالة المحددة لـ "sftp":

$cp = $ssh->get_ctl_path;

انظر أيضاً

وثائق عميل OpenSSH ssh(1)، ssh_config(5)، موقع المشروع على الويب http://www.openssh.org وقسم الأسئلة الشائعة الخاص به http://www.openbsd.org/openssh/faq.html. scp(1) و rsync(1). كتاب OpenSSH المصور http://en.wikibooks.org/wiki/OpenSSH.

Net::OpenSSH::Gateway للحصول على تعليمات مفصلة حول كيفية جعل هذه الوحدة تتصل بالمضيفين عبر الوكلاء وخوادم بوابات SSH الأخرى.

وثائق Perl الأساسية perlipc، "open" في perlfunc، "waitpid" في perlfunc.

IO::Pty لمعرفة كيفية استخدام كائنات pseudo tty التي تم إرجاعها بواسطة عدة طرق في هذه الحزمة.

Net::SFTP::Foreign يوفر تنفيذ SFTP متوافق.

يمكن استخدام Expect للتفاعل مع الأوامر التي تم تشغيلها من خلال هذه الوحدة على الجهاز البعيد (انظر أيضًا نصوص "expect.pl" و <autosudo.pl> في مجلد الأمثلة).

SSH::OpenSSH::Parallel هو مجدول متقدم يسمح بتشغيل الأوامر على المضيفين البعيدين بشكل متوازٍ. وهو يعتمد بشكل واضح على Net::OpenSSH.

SSH::Batch يسمح بتشغيل الأوامر البعيدة بشكل متوازٍ في مجموعة. وهو مبني فوق "Net::OpenSSH" أيضًا.

عملاء SSH آخرون في Perl: Net::SSH::Perl, Net::SSH2, Net::SSH, Net::SSH::Expect, Net::SCP, Net::SSH::Mechanize.

Net::OpenSSH::Compat هي حزمة توفر مجموعة من طبقات التوافق لوحدات SSH الأخرى فوق Net::OpenSSH.

IPC::PerlSSH، GRID::Machine تسمح بتنفيذ كود Perl على الأجهزة البعيدة عبر SSH.

SSH::RPC ينفذ آلية RPC فوق SSH باستخدام Net::OpenSSH لمعالجة الاتصالات.

Net::CLI::Interact يسمح بالتفاعل مع الأوامر الطرفية البعيدة والخدمات الأخرى. وهي مناسبة بشكل خاص للتفاعل مع معدات الشبكة. النهج "كتاب العبارات" الذي تستخدمه ذكي للغاية. قد ترغب أيضًا في الاطلاع على الوحدات الأخرى https://metacpan.org/author/OLIVER من مؤلفها، Oliver Gorwits.

NAME

Net::OpenSSH - A Perl module to use OpenSSH client commands from Perl.

SYNOPSIS

use Net::OpenSSH;

my $ssh = Net::OpenSSH->new(
    host    => 'localhost',
    user    => 'user',
    port    => 22,
    key     => '/path/to/ssh/private/key',
    timeout => 10,
);

# Run a command and get its stdout, stderr, and exit code
my ($stdout, $stderr, $exit_code) = $ssh->run('ls -l');

# Run a command and check for errors
$ssh->run('rm -rf /') && die "Something went wrong!";

# Run a command and capture its output
my $output = $ssh->capture('date');

# Upload a file
$ssh->scp_put('local/path/to/file', 'remote/path/to/file');

# Download a file
$ssh->scp_get('remote/path/to/file', 'local/path/to/file');

# Run a command in a remote shell
my $shell = $ssh->shell;
$shell->send_cmd('cd /tmp');
$shell->send_cmd('echo "hello"');
print $shell->slurp_out; # slurp all stdout
$shell->close;

DESCRIPTION

Net::OpenSSH is a Perl module that allows you to use OpenSSH client commands from within Perl. It provides an object-oriented interface to OpenSSH commands such as ssh, scp, and sftp.

This module is a wrapper around the OpenSSH command-line client. It does not implement the SSH protocol itself. Therefore, you must have the OpenSSH client installed on your system for this module to work.

API

new(%args)
Constructor for Net::OpenSSH. Takes a hash of arguments:
  • host: The hostname or IP address of the remote server.
  • user: The username to log in as.
  • port: The SSH port to connect to (default is 22).
  • key: The path to the private SSH key file.
  • password: The password for SSH authentication (use with caution).
  • timeout: The connection timeout in seconds.
  • strict_host_key_checking: Whether to enable strict host key checking (default is 1).
run($command)
Runs a command on the remote server and returns its stdout, stderr, and exit code.
capture($command)
Runs a command on the remote server and returns its stdout. Dies if the command fails.
scp_put($local_path, $remote_path)
Uploads a file from the local system to the remote server using scp.
scp_get($remote_path, $local_path)
Downloads a file from the remote server to the local system using scp.
shell()
Opens an interactive shell session on the remote server. Returns a Net::OpenSSH::Shell object.

3rd PARTY MODULE INTEGRATION

This module can be used in conjunction with other Perl modules that require SSH access, such as configuration management tools or deployment scripts.

TROUBLESHOOTING

If you encounter problems, ensure that the OpenSSH client is installed and in your system's PATH. Check your SSH configuration and authentication methods.

DEBUGGING

You can enable debugging output by setting the PERL_NET_OPENSSH_DEBUG environment variable to a true value:

export PERL_NET_OPENSSH_DEBUG=1
perl your_script.pl

SECURITY

Using passwords for authentication is generally discouraged. It is recommended to use SSH key-based authentication instead.

FAQ

Q: How do I handle SSH host key verification?
By default, strict host key checking is enabled. You can disable it by passing strict_host_key_checking => 0 to the constructor, but this is not recommended for security reasons. It's better to ensure the remote host's key is in your known_hosts file.
Q: How do I transfer files?
Use the scp_put and scp_get methods.
