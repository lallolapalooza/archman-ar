nix-store-export(1)

الحزمة: nix

التراخيص: LGPL-2.1-only

nix-store --export(1) دليل الأوامر العامة nix-store --export(1)

الاسم

nix-store --export - تصدير مسارات التخزين إلى أرشيف Nix

الملخص

nix-store --export مسارات…

الوصف

العملية --export تكتب تسلسلاً للكائنات المخزنة المحددة إلى المخرج القياسي بتنسيق يمكن استيراده إلى متجر Nix آخر باستخدام nix-store --import.

تحذير

هذا الأمر لا ينتج إغلاقًا لمسارات المتجر المحددة. سيؤدي فشل استيراد كائن متجر يشير إلى مسارات متجر غير متوفرة في متجر Nix الهدف.

استخدم nix-store --query للحصول على إغلاق مسار المتجر.

يختلف هذا الأمر عن nix-store --dump، الذي ينتج أرشيف Nix لا يتضمن مجموعة المرجعيات لمسار المتجر المحدد.

ملاحظة

للنقل الفعال للإغلاقات إلى الأجهزة البعيدة عبر SSH، استخدم nix-copy-closure.

خيارات

يُسمح بالخيارات التالية لجميع عمليات nix-store، ولكنها قد لا يكون لها تأثير دائمًا.

•
--add-root مسار
يتسبب في تسجيل نتيجة التحقيق (--realise و --force-realise) كجذر لجامع القمامة. سيتم إنشاء مسار كرابط رمزي لمسار المتجر الناتج. بالإضافة إلى ذلك، سيتم إنشاء رابط رمزي باسم فريد لـ مسار في /nix/var/nix/gcroots/auto/. على سبيل المثال،
$ nix-store --add-root /home/eelco/bla/result --realise ...
$ ls -l /nix/var/nix/gcroots/auto
lrwxrwxrwx    1 ... 2005-03-13 21:10 dn54lcypm8f8... -> /home/eelco/bla/result
$ ls -l /home/eelco/bla/result
lrwxrwxrwx    1 ... 2005-03-13 21:10 /home/eelco/bla/result -> /nix/store/1r11343n6qd4...-f-spot-0.0.10
وبالتالي، عندما تتم إزالة /home/eelco/bla/result، يصبح جذر جامع القمامة في دليل auto رابطًا رمزيًا معلقًا وسيتم تجاهله بواسطة المجمع.
تحذير
لاحظ أنه لا يمكن نقل أو إعادة تسمية جذور جامع القمامة، حيث سيظل الرابط الرمزي في دليل auto يشير إلى الموقع القديم.
إذا كانت هناك نتائج متعددة، فسيتم إنشاء روابط رمزية متعددة عن طريق ترقيم الروابط الرمزية بالتتابع بعد الأولى (على سبيل المثال، foo، foo-2، foo-3، وهكذا).

--verbose / -v

يمكن تحديد هذا الخيار بشكل متكرر. حاليًا، توجد مستويات التفصيل التالية:

يمكن تحديد هذا الخيار بشكل متكرر. انظر قائمة مستويات التفصيل السابقة.
•
--log-format تنسيق

internal-json
يخرج السجلات بتنسيق منظم.
تحذير
بينما يكون المخطط نفسه مستقرًا نسبيًا، يمكن أن يتغير تنسيق رسائل الخطأ (وتحديدًا حقل msg) بين الإصدارات.
•

يعرض شريط تقدم فقط أثناء عمليات البناء.

•
--no-build-output / -Q
بشكل افتراضي، يتم عكس الإخراج الذي تكتبه أدوات البناء إلى المخرج القياسي والمخرج القياسي إلى المخرج القياسي لأمر Nix. هذا الخيار يمنع هذا السلوك. لاحظ أن المخرج القياسي والخطأ القياسي لأداة البناء يتم دائمًا كتابتهما إلى ملف سجل في prefix/nix/var/log/nix.
•
--max-jobs / -j رقم
يحدد الحد الأقصى لعدد وظائف البناء التي ستقوم بها Nix بالتوازي إلى

هذا الموقع غير مرتبط بـ Arch Linux ولا تابع له بأي شكل من الأشكال. المحتوى هو ترجمة فقط لصفحات دليل Arch المنشورة على man.archlinux.org.

العدد المحدد. حدد auto لاستخدام عدد وحدات المعالجة المركزية في النظام. القيمة الافتراضية محددة بواسطة إعداد التكوين max-jobs، والتي بدورها تعطي القيمة الافتراضية لـ 1. قيمة أعلى مفيدة في أنظمة SMP أو لاستغلال زمن الوصول للإدخال/الإخراج.
تعطيل البناء على الجهاز المحلي بتعيينها على 0، وهو أمر مفيد عندما تريد أن تتم عمليات البناء فقط على أدوات البناء عن بُعد.
•
--cores
يحدد قيمة متغير البيئة NIX_BUILD_CORES في استدعاء أدوات البناء. يمكن لأدوات البناء استخدام هذا المتغير حسب تقديرها للتحكم في الحد الأقصى للتوازي. على سبيل المثال، في Nixpkgs، إذا تم تعيين سمة الاشتقاق enableParallelBuilding إلى true، فإن أداة البناء تمرر العلامة -jN إلى GNU Make. القيمة الافتراضية هي قيمة إعداد التكوين cores، إذا تم تعيينها، أو 1 بخلاف ذلك. القيمة 0 تعني أن أداة البناء يجب أن تستخدم جميع أنوية وحدة المعالجة المركزية المتاحة في النظام.
•
--max-silent-time
يحدد الحد الأقصى لعدد الثواني التي يمكن أن تمر بها أداة البناء دون إنتاج أي بيانات على المخرج القياسي أو الخطأ القياسي. يتم تحديد القيمة الافتراضية بواسطة إعداد التكوين max-silent-time. 0 يعني عدم وجود مهلة.
•
--timeout
يحدد الحد الأقصى لعدد الثواني التي يمكن لأداة البناء تشغيلها. يتم تحديد القيمة الافتراضية بواسطة إعداد التكوين timeout. 0 يعني عدم وجود مهلة.
•
--keep-going / -k
استمر في العمل في حالة فشل عمليات البناء، إلى أقصى حد ممكن. أي، إذا فشل بناء أحد مدخلات اشتقاق ما، فستقوم Nix ببناء المدخلات الأخرى، ولكن ليس الاشتقاق نفسه. بدون هذا الخيار، تتوقف Nix إذا فشل أي بناء (باستثناء عمليات بناء البدائل)، وقد تقتل عمليات البناء قيد التقدم (في حالة عمليات البناء المتوازية أو الموزعة).
•
--keep-failed / -K
يحدد أنه في حالة فشل البناء، يجب عدم حذف الدليل المؤقت (عادةً في /tmp) الذي يتم فيه إجراء البناء. تتم طباعة مسار دليل البناء كرسالة إعلامية.
•
--fallback
عندما تحاول Nix بناء اشتقاق معروف له بدائل لكل مسار مخرج، ولكن فشلت استعادة مسارات المخرجات من خلال البدائل، ارجع إلى بناء الاشتقاق.
السيناريو الأكثر شيوعًا الذي يكون فيه هذا مفيدًا هو عندما نكون قد سجلنا بدائل لإجراء التوزيع الثنائي، على سبيل المثال، من مستودع شبكة. إذا كان المستودع معطلاً، فستفشل عملية استعادة الاشتقاق. عندما يتم تحديد هذا الخيار، ستقوم Nix ببناء الاشتقاق بدلاً من ذلك. وبالتالي، فإن التثبيت من الثنائيات سيعود إلى التثبيت من المصدر. هذا الخيار ليس هو الافتراضي لأنه لا يُفضل بشكل عام أن يؤدي فشل مؤقت في الحصول على البدائل إلى بناء كامل من المصدر (مع استهلاك الموارد المرتبط).
•
--readonly-mode
عند استخدام هذا الخيار، لا يتم بذل أي محاولة لفتح قاعدة بيانات Nix. معظم عمليات Nix تحتاج إلى الوصول إلى قاعدة البيانات، لذلك ستفشل تلك العمليات.
•
--arg name value
يتم قبول هذا الخيار من قبل nix-env، nix-instantiate، nix-shell و nix-build. عند تقييم تعبيرات Nix، سيحاول مقيّم التعبير تلقائيًا استدعاء الدوال التي يواجهها. يمكنه استدعاء الدوال تلقائيًا التي يكون لكل وسيطة فيها قيمة افتراضية (على سبيل المثال، { argName ? defaultValue }: ...).
باستخدام --arg، يمكنك أيضًا استدعاء الدوال التي تحتوي على وسيطات بدون قيمة افتراضية (أو تجاوز قيمة افتراضية). أي، إذا واجه المقيّم دالة ذات وسيطة باسم name، فسيقوم باستدعائها بالقيمة value.
على سبيل المثال، default.nix في المستوى الأعلى في Nixpkgs هو في الواقع دالة:
{ # النظام (على سبيل المثال، `i686-linux') الذي سيتم بناء الحزم له.
system ? builtins.currentSystem
...
}: ...
لذلك، إذا قمت باستدعاء تعبير Nix هذا (على سبيل المثال، عند القيام بـ nix-env --install --attr pkgname)، فسيتم استدعاء الدالة تلقائيًا باستخدام القيمة builtins.currentSystem للوسيطة system. يمكنك تجاوز هذا باستخدام --arg، على سبيل المثال، nix-env --install --attr pkgname --arg system \"i686-freebsd\". (لاحظ أنه نظرًا لأن الوسيطة هي حرف سلسلة Nix، يجب عليك الهروب من علامات الاقتباس.)
•
--argstr name value
هذا الخيار يشبه --arg، فقط القيمة ليست تعبير Nix ولكنها سلسلة نصية. لذا بدلاً من --arg system \"i686-linux\" (علامات الاقتباس الخارجية للحفاظ على عمل الصدفة) يمكنك قول --argstr system i686-linux.
•
--attr / -A attrPath
حدد سمة من تعبير Nix في المستوى الأعلى الذي يتم تقييمه. ( nix-env، nix-instantiate، nix-build و nix-shell فقط.) مسار السمة attrPath هو تسلسل من أسماء السمات مفصولة بنقاط. على سبيل المثال، بالنظر إلى تعبير Nix في المستوى الأعلى e، فإن مسار السمة xorg.xorgserver سيؤدي إلى استخدام التعبير e.xorg.xorgserver. انظر nix-env --install لبعض الأمثلة الملموسة.
بالإضافة إلى أسماء السمات، يمكنك أيضًا تحديد فهارس المصفوفة. على سبيل المثال، يحدد مسار السمة foo.3.bar السمة bar للعنصر الرابع في المصفوفة في السمة foo للتعبير في المستوى الأعلى.
•
--expr / -E
فسر وسائط سطر الأوامر على أنها قائمة بتعبيرات Nix ليتم تحليلها وتقييمها، بدلاً من قائمة بأسماء ملفات تعبيرات Nix. ( nix-instantiate، nix-build و nix-shell فقط.)
بالنسبة لـ nix-shell، يُستخدم هذا الخيار بشكل شائع لمنحك صدفة يمكنك فيها بناء الحزم التي تعيدها التعبير. إذا كنت ترغب في الحصول على صدفة تحتوي على الحزم *المبنية* الجاهزة للاستخدام، فقدم تعبيرك إلى علم الراحة nix-shell --packages بدلاً من ذلك.
•
-I / --include path
أضف إدخالاً إلى قائمة مسارات البحث المستخدمة لحل مسارات البحث. يمكن إعطاء هذا الخيار عدة مرات.
المسارات المضافة من خلال -I لها الأسبقية على إعداد التكوين nix-path و متغير البيئة NIX_PATH.
•
--option name value
قم بتعيين خيار تكوين Nix name إلى value. هذا يتجاوز الإعدادات في ملف تكوين Nix (انظر nix.conf5).
•
--repair
إصلاح مسارات المخزن التالفة أو المفقودة عن طريق إعادة تنزيلها أو إعادة بنائها. لاحظ أن هذا بطيء لأنه يتطلب حساب تجزئة تشفير لمحتويات كل مسار في إغلاق البناء. لاحظ أيضًا التحذير الموجود تحت nix-store --repair-path.

nix-store(1) — nix manual

NAME

nix-store — manage the Nix data store

SYNOPSIS

nix-store [-d—--daemon] [--realise] [--export] [--import] [--query] [--optimise] [--verify] [--repair] [--gc] [--build-log] [--ban] [--unban] [--roots] [--references] [--referrers] [--drvs] [--graph] [--trace] [--requisites] [--blobs] [--cat-nar] [--read-nar] [--hash-nar] [--narinfo] [--serve] [--log-gc] [--log-derivations] [-q—--quiet] [-v—--verbose] [-s—--substituters] [-r—--trusted-public-keys] [-a—--all] [--force-store-path] [--allow-unsafe-path] [-j N—--cores N] [--experimental-features FEATURES] [--log-format FORMAT] [ARGUMENTS

DESCRIPTION

The nix-store command is the primary interface to the Nix data store, the database of all build products managed by Nix.

This page describes the low-level commands for manipulating the Nix store. For a higher-level interface, see nix(1).

Many nix-store operations require interacting with the Nix daemon. If the daemon is not running, nix-store will attempt to start it. If this fails, or if you want to explicitly use the daemon, use the -d or --daemon option.

The Nix store is a collection of paths identified by cryptographic hashes. These paths are immutable: once built, they can never be changed. This ensures reproducibility and allows Nix to share dependencies between projects.

The Nix store is typically located at /nix/store. The location can be overridden using the NIX_STORE_DIR environment variable.

Nix Store Operations

•
--realise—-r
Builds the specified Nix store paths. This command is typically used by Nix builders. Use nix-build(1) for a more user-friendly interface.
•
--export
Exports the specified Nix store paths and their dependencies to standard output as a tarball. This is useful for transferring Nix store contents between machines.
•
--import
Imports Nix store paths and their dependencies from standard input (a tarball). This is the counterpart to --export.
•
--query—-q
Queries information about Nix store paths. Common subcommands include:
  • path: Prints the path of the store item.
  • is-built: Checks if the store item is already built.
  • type: Prints the type of the store item (e.g., regular file, directory, symlink).
  • nar: Prints the NAR hash of the store item.
  • references: Prints the direct dependencies of the store item.
  • all-references: Prints all dependencies (direct and indirect).
  • fixed-output: Checks if the store item is a fixed-output derivation.
  • derivations: Prints the derivation(s) that produced the store item.
  • build-date: Prints the build date of the store item.
  • build-host: Prints the build host of the store item.
  • build-users-count: Prints the number of users that built the store item.
  • count-referrers: Counts the number of store items that refer to this item.
  • hash-script: Prints the hash of the build script used for the derivation.
•
--optimise
Optimises the Nix store by garbage collecting unused paths and potentially moving paths to a shared cache.
•
--verify
Verifies the integrity of the Nix store paths. It checks that all paths exist and that their contents match their expected hashes.
•
--repair
Attempts to repair the Nix store by rebuilding any missing or corrupted paths.
•
--gc
Performs garbage collection on the Nix store, removing paths that are no longer referenced by any derivations. Use nix-collect-garbage(1) for a more user-friendly interface.
•
--build-log
Retrieves the build log for a given Nix store path.
•
--ban
Bans a specific Nix store path, preventing it from being garbage collected.
•
--unban
Unbans a Nix store path, allowing it to be garbage collected.
•
--roots
Lists all paths in the Nix store that are currently referenced (i.e., not garbage collectable).
•
--references
Lists the direct dependencies of a Nix store path.
•
--referrers
Lists all Nix store paths that depend on the given path.
•
--drvs
Lists all derivations in the Nix store.
•
--graph
Generates a GraphViz graph representing the dependency relationships in the Nix store.
•
--trace
Traces the build process of a Nix store path, showing the commands executed.
•
--requisites
Outputs a list of all Nix store paths that are required by the given path(s), sorted topologically.
•
--blobs
Prints information about Nix blobs (unreferenced data) in the store.
•
--cat-nar
Prints the contents of a NAR archive from standard input.
•
--read-nar
Reads a NAR archive from standard input and adds its contents to the Nix store.
•
--hash-nar
Computes the NAR hash of the contents provided via standard input.
•
--narinfo
Generates NAR info files for the specified Nix store paths.
•
--serve
Starts a Nix daemon that serves store paths over the network.
•
--log-gc
Enables detailed logging for garbage collection operations.
•
--log-derivations
Enables detailed logging for derivation builds.

OPTIONS

•
NIX_PATH
A colon-separated list of search path entries used to resolve lookup paths.
This environment variable overrides the value of the nix-path configuration setting.
It can be extended using the -I option.
Example
$ export NIX_PATH=`/home/eelco/Dev:nixos-config=/etc/nixos`
If NIX_PATH is set to an empty string, resolving search paths will always fail.
Example
$ NIX_PATH= nix-instantiate --eval '<nixpkgs>'
error: file 'nixpkgs' was not found in the Nix search path (add it using $NIX_PATH or -I)
•
NIX_IGNORE_SYMLINK_STORE
Normally, the Nix store directory (typically /nix/store) is not allowed to contain any symlink components. This is to prevent “impure” builds. Builders sometimes “canonicalise” paths by resolving all symlink components. Thus, builds on different machines (with /nix/store resolving to different locations) could yield different results. This is generally not a problem, except when builds are deployed to machines where /nix/store resolves differently. If you are sure that you’re not going to do that, you can set NIX_IGNORE_SYMLINK_STORE to 1.
Note that if you’re symlinking the Nix store so that you can put it on another file system than the root file system, on Linux you’re better off using bind mount points, e.g.,
$ mkdir /nix
$ mount -o bind /mnt/otherdisk/nix /nix
Consult the mount 8 manual page for details.
•
NIX_STORE_DIR
Overrides the location of the Nix store (default prefix/store).
•
NIX_DATA_DIR
Overrides the location of the Nix static data directory (default prefix/share).
•
NIX_LOG_DIR
Overrides the location of the Nix log directory (default prefix/var/log/nix).
•
NIX_STATE_DIR
Overrides the location of the Nix state directory (default prefix/var/nix).
•
NIX_CONF_DIR
Overrides the location of the system Nix configuration directory (default prefix/etc/nix).
•
NIX_CONFIG
Applies settings from Nix configuration from the environment. The content is treated as if it was read from a Nix configuration file. Settings are separated by the newline character.
•
NIX_USER_CONF_FILES
Overrides the location of the Nix user configuration files to load from.
The default are the locations according to the XDG Base Directory Specification. See the XDG Base Directories sub-section for details.
The variable is treated as a list separated by the : token.
•
TMPDIR
Use the specified directory to store temporary files. In particular, this includes temporary build directories; these can take up substantial amounts of disk space. The default is /tmp.
•
NIX_REMOTE
This variable should be set to daemon if you want to use the Nix daemon to execute Nix operations. This is necessary in multi-user Nix installations. If the Nix daemon’s Unix socket is at some non-standard path, this variable should be set to unix://path/to/socket. Otherwise, it should be left unset.
•
NIX_SHOW_STATS
If set to 1, Nix will print some evaluation statistics, such as the number of values allocated.
•
NIX_COUNT_CALLS
If set to 1, Nix will print how often functions were called during Nix expression evaluation. This is useful for profiling your Nix expressions.
•
GC_INITIAL_HEAP_SIZE
If Nix has been configured to use the Boehm garbage collector, this variable sets the initial size of the heap in bytes. It defaults to 384 MiB. Setting it to a low value reduces memory consumption, but will increase runtime due to the overhead of garbage collection.

XDG Base Directories

Nix follows the XDG Base Directory Specification.

For backwards compatibility, Nix commands will follow the standard only when use-xdg-base-directories is enabled. New Nix commands (experimental) conform to the standard by default.

The following environment variables are used to determine locations of various state and configuration files:

  • [XDG_CONFIG_HOME]{#env-XDGCONFIGHOME} (default ~/.config)
  • [XDG_STATE_HOME]{#env-XDGSTATEHOME} (default ~/.local/state)
  • [XDG_CACHE_HOME]{#env-XDGCACHEHOME} (default ~/.cache)

EXAMPLES

Example

Deploy GNU Hello to an airgapped machine via USB stick.

Write the closure to the block device on a machine with internet connection:

[alice@itchy]$ storePath=$(nix-build '<nixpkgs>' -I nixpkgs=channel:nixpkgs-unstable -A hello --no-out-link)
[alice@itchy]$ nix-store --export $(nix-store --query --requisites $storePath) | sudo dd of=/dev/usb

Read the closure from the block device on the machine without internet connection:

[bob@scratchy]$ hello=$(sudo dd if=/dev/usb | nix-store --import | tail -1)
[bob@scratchy]$ $hello/bin/hello
Hello, world!
