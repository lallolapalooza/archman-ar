تعيين اسم التصدير

قد تخدم بعض خوادم NBD صور أقراص متعددة ("تصديرات"). يختار العميل اسم التصدير أثناء عملية التفاوض. اسم التصدير الافتراضي هو سلسلة فارغة "".

تتجاهل بعض خوادم NBD هذه القيمة وتخدم نفس المحتوى بغض النظر عن اسم التصدير. هذه الميزة ذات صلة فقط عند الاتصال بالخوادم باستخدام النمط الجديد للبروتوكول، حيث أن النمط القديم لم يدعم أسماء التصدير.

يحد بروتوكول NBD أسماء التصدير إلى 4096 بايت، ولكن قد لا تدعم الخوادم الطول الكامل. ترميز أسماء التصدير دائمًا هو UTF-8.

إذا لم يكن وضع الخيار قيد الاستخدام، فيجب تعيين اسم التصدير قبل بدء الاتصال. ومع ذلك، عندما يقوم nbd_set_opt_mode(3) بتمكين وضع الخيار، فمن الممكن تغيير اسم التصدير قبل استدعاء nbd_opt_go(3). على وجه الخصوص، يمكن استخدام nbd_opt_list(3) أثناء التفاوض لتحديد اسم يوافق الخادم على قبوله، ويمكن استخدام nbd_opt_info(3) لمعرفة التفاصيل حول التصدير قبل الاتصال.

يمكن تخطي هذا الاستدعاء إذا تم استخدام nbd_connect_uri(3) للاتصال بـ URI يتضمن اسم تصدير.

التحكم فيما إذا كان وضع الخيار NBD_OPT_GO يطلب أحجام الكتل

بشكل افتراضي، عند الاتصال بتصدير، يطلب libnbd من الخادم الإبلاغ عن أي قيود على أحجام الكتل. يشير بروتوكول NBD إلى أن الخادم يمكنه توفير أحجام الكتل بغض النظر عما إذا كان العميل يطلبها، وسيقوم libnbd بالإبلاغ عن تلك الأحجام (انظر nbd_get_block_size(3))؛ ومع ذلك، إذا لم يطلب العميل أحجام الكتل، فقد يرفض الخادم الاتصال بدلاً من التعامل مع طلب عميل غير متوافق. تتيح هذه الوظيفة اختبار سلوك الخادم عن طريق محاكاة العملاء القدامى.

ملاحظة: على الرغم من طلب حجم الكتلة، لا يلزم أن يوفر الخادم أي أحجام. بالإضافة إلى ذلك، إذا تم توفير أحجام الكتل (سواء طلبها العميل أم لا)، فسيقوم libnbd بتطبيق المحاذاة على تلك الأحجام، باستثناء الحالات التي يتم فيها استخدام nbd_set_strict_mode(3) لمنع فحوصات الأمان من جانب العميل.

NBD.set_tls t tls

تمكين أو طلب TLS (المصادقة والتشفير)

تمكين أو طلب TLS (اتصالات مصادق عليها ومشفرة) إلى خادم NBD. الإعدادات الممكنة هي:

"LIBNBD_TLS_DISABLE" تعطيل TLS. (الافتراضي، ما لم يتم استخدام nbd_connect_uri(3) مع URI يتطلب TLS).

هذا الإعداد مطلوب أيضًا إذا تم استخدام nbd_set_opt_mode(3) وتريد التفاعل بنص عادي مع خادم ينفذ وضع "SELECTIVETLS" لبروتوكول NBD قبل تمكين TLS باستخدام nbd_opt_starttls(3). تفضل معظم الخوادم التي تدعم TLS وضع "FORCEDTLS" لبروتوكول NBD، لذا فإن هذا النوع من التفاعل اليدوي مفيد بشكل أساسي أثناء اختبار التكامل.

"LIBNBD_TLS_ALLOW" تمكين TLS إذا كان ذلك ممكنًا.

هذا الخيار غير آمن (أو بالأحرى، جهد) في بعض الحالات، حيث يمكن أن يسقط إلى اتصال غير مشفر أو غير مصدق إذا لم يكن من الممكن إنشاء TLS. استخدم "LIBNBD_TLS_REQUIRE" إذا كان يجب تشفير الاتصال.

قد ترفض بعض الخوادم الاتصال إذا فشل TLS، لذلك قد لا يكون التراجع ممكنًا دائمًا.

"LIBNBD_TLS_REQUIRE" يتطلب اتصال TLS مشفر ومصدق عليه. يفشل دائمًا إذا لم يكن الاتصال مشفرًا ومصدقًا عليه.

بالإضافة إلى استدعاء هذا الأمر، قد تحتاج أيضًا إلى توفير دليل الشهادات (nbd_set_tls_certificates(3))، واسم المستخدم (nbd_set_tls_username(3)) و/أو ملفات مفاتيح ما قبل المشاركة (PSK) (nbd_set_tls_psk_file(3)). حاليًا، عند استخدام nbd_connect_uri(3)، لا يتم التعامل مع أي معلمات استعلام متعلقة بـ TLS تلقائيًا. سيفشل تعيين أعلى مستوى أكبر من صفر إذا لم يتم تجميع libnbd مقابل gnutls؛ يمكنك معرفة ما إذا كان الأمر كذلك باستخدام nbd_supports_tls(3).

معرفة ما إذا تم التفاوض على TLS في اتصال

بعد الاتصال، يمكنك استدعاء هذه الوظيفة لمعرفة ما إذا كان الاتصال يستخدم TLS.

هذا مفيد عادةً فقط إذا قمت بتعيين وضع طلب TLS إلى "LIBNBD_TLS_ALLOW" (انظر nbd_set_tls(3))، لأنه في هذا الوضع نحاول استخدام TLS ولكن نسقط إلى اتصال غير مشفر إذا لم يكن متاحًا. ستخبرك هذه الوظيفة ما إذا تم التفاوض على TLS أم لا.

val set_strict_mode : t -> STRICT.t list -> unit

NBD.set_strict_mode t flags

control how strictly to follow NBD protocol

By default, libnbd tries to detect requests that would trigger undefined behavior in the NBD protocol, and rejects them client side without causing any network traffic, rather than risking undefined server behavior. However, for integration testing, it can be handy to relax the strictness of libnbd, to coerce it into sending such requests over the network for testing the robustness of the server in dealing with such traffic.

The "flags" argument is a bitmask, including zero or more of the following strictness flags:

"LIBNBD_STRICT_COMMANDS" = 0x1 If set, this flag rejects client requests that do not comply with the set of advertised server flags (for example, attempting a write on a read-only server, or attempting to use "LIBNBD_CMD_FLAG_FUA" when nbd_can_fua(3) returned false). If clear, this flag relies on the server to reject unexpected commands.

"LIBNBD_STRICT_FLAGS" = 0x2 If set, this flag rejects client requests that attempt to set a command flag not recognized by libnbd (those outside of "LIBNBD_CMD_FLAG_MASK"), or a flag not normally associated with a command (such as using "LIBNBD_CMD_FLAG_FUA" on a read command). If clear, all flags are sent on to the server, even if sending such a flag may cause the server to change its reply in a manner that confuses libnbd, perhaps causing deadlock or ending the connection.

Flags that are known by libnbd as associated with a given command (such as "LIBNBD_CMD_FLAG_DF" for nbd_pread_structured(3) gated by nbd_can_df(3)) are controlled by "LIBNBD_STRICT_COMMANDS" instead; and "LIBNBD_CMD_FLAG_PAYLOAD_LEN" is managed automatically by libnbd unless "LIBNBD_STRICT_AUTO_FLAG" is disabled.

Note that the NBD protocol only supports 16 bits of command flags, even though the libnbd API uses "uint32_t"; bits outside of the range permitted by the protocol are always a client-side error.

"LIBNBD_STRICT_BOUNDS" = 0x4 If set, this flag rejects client requests that would exceed the export bounds without sending any traffic to the server. If clear, this flag relies on the server to detect out-of-bounds requests.

"LIBNBD_STRICT_ZERO_SIZE" = 0x8 If set, this flag rejects client requests with length 0. If clear, this permits zero-length requests to the server, which may produce undefined results.

"LIBNBD_STRICT_ALIGN" = 0x10 If set, and the server provided minimum block sizes (see "LIBNBD_SIZE_MINIMUM" for nbd_get_block_size(3)), this flag rejects client requests that do not have length and offset aligned to the server's minimum requirements. If clear, unaligned requests are sent to the server, where it is up to the server whether to honor or reject the request.

"LIBNBD_STRICT_PAYLOAD" = 0x20 If set, the client refuses to send a command to the server with more than libnbd's outgoing payload maximum (see "LIBNBD_SIZE_PAYLOAD" for nbd_get_block_size(3)), whether or not the server advertised a block size maximum. If clear, oversize requests up to 64MiB may be attempted, although requests larger than 32MiB are liable to cause some servers to disconnect.

"LIBNBD_STRICT_AUTO_FLAG" = 0x40 If set, commands that accept the "LIBNBD_CMD_FLAG_PAYLOAD_LEN" flag (such as nbd_pwrite(3) and nbd_block_status_filter(3)) ignore the presence or absence of that flag from the caller, instead sending the value over the wire that matches the server's expectations based on whether extended headers were negotiated when the connection was made. If clear, the caller takes on the responsibility for whether the payload length flag is set or clear during the affected command, which can be useful during integration testing but is more likely to lead to undefined behavior.

For convenience, the constant "LIBNBD_STRICT_MASK" is available to describe all strictness flags supported by this build of libnbd. Future versions of libnbd may add further flags, which are likely to be enabled by default for additional client-side filtering. As such, when attempting to relax only one specific bit while keeping remaining checks at the client side, it is wiser to first call nbd_get_strict_mode(3) and modify that value, rather than blindly setting a constant value.

val set_opt_mode : t -> bool -> unit

NBD.set_opt_mode t enable

control option mode, for pausing during option negotiation

Set this flag to true in order to request that a connection command "nbd_connect_*" will pause for negotiation options rather than proceeding all the way to the ready state, when communicating with a newstyle server. This setting has no effect when connecting to an oldstyle server.

Note that libnbd defaults to attempting "NBD_OPT_STARTTLS", "NBD_OPT_EXTENDED_HEADERS", and "NBD_OPT_STRUCTURED_REPLY" before letting you control remaining negotiation steps; if you need control over these steps as well, first set nbd_set_tls(3) to "LIBNBD_TLS_DISABLE", and nbd_set_request_extended_headers(3) or nbd_set_request_structured_replies(3) to false, before starting the connection attempt.

When option mode is enabled, you have fine-grained control over which options are negotiated, compared to the default of the server negotiating everything on your behalf using settings made before starting the connection. To leave the mode and proceed on to the ready state, you must use nbd_opt_go(3) successfully; a failed nbd_opt_go(3) returns to the negotiating state to allow a change of export name before trying again. You may also use nbd_opt_abort(3) or nbd_shutdown(3) to end the connection without finishing negotiation.

end negotiation and move on to using an export

Request that the server finish negotiation and move on to serving the export previously specified by the most recent nbd_set_export_name(3) or nbd_connect_uri(3). This can only be used if nbd_set_opt_mode(3) enabled option mode.

By default, libnbd will automatically request all meta contexts registered by nbd_add_meta_context(3) as part of this call; but this can be suppressed with nbd_set_request_meta_context(3), particularly if nbd_opt_set_meta_context(3) was used earlier in the negotiation sequence.

val opt_starttls : t -> bool

NBD.opt_starttls t

request the server to initiate TLS

Request that the server initiate a secure TLS connection, by sending "NBD_OPT_STARTTLS". This can only be used if nbd_set_opt_mode(3) enabled option mode; furthermore, if you use nbd_set_tls(3) to request anything other than the default of "LIBNBD_TLS_DISABLE", then libnbd will have already attempted a TLS connection prior to allowing you control over option negotiation. This command is disabled if nbd_supports_tls(3) reports false.

This function is mainly useful for integration testing of corner cases in server handling; in particular, misuse of this function when coupled with a server that is not careful about resetting stateful commands such as nbd_opt_structured_reply(3) could result in a security hole (see CVE-2021-3716 against nbdkit, for example). Thus, when security is a concern, you should instead prefer to use nbd_set_tls(3) with "LIBNBD_TLS_REQUIRE" and let libnbd negotiate TLS automatically.

This function returns true if the server replies with success, false if the server replies with an error, and fails only if the server does not reply (such as for a loss of connection, which can include when the server rejects credentials supplied during the TLS handshake). Note that the NBD protocol documents that requesting TLS after it is already enabled is a client error; most servers will gracefully fail a second request, but that does not downgrade a TLS session that has already been established, as reported by nbd_get_tls_negotiated(3).

مدعومة في الإصدار الحالي من libnbd:

"nbd:" الاتصال عبر TCP دون استخدام TLS.

"nbds:" الاتصال عبر TCP. مطلوب TLS وسيفشل الاتصال إذا لم يدعم الخادم TLS.

"nbd+unix:" "nbds+unix:" الاتصال عبر مقبس نطاق Unix، بدون TLS أو مع TLS على التوالي. يجب تحديد المعلمة "socket".

"nbd+vsock:" "nbds+vsock:" الاتصال عبر النقل "AF_VSOCK"، بدون TLS أو مع TLS على التوالي. يمكنك استخدام nbd_supports_vsock(3) لمعرفة ما إذا كان هذا الإصدار من libnbd يدعم "AF_VSOCK".

"nbd+ssh:" "nbds+ssh:" *تجريبي*

نفق NBD عبر اتصال Secure Shell. يتطلب هذا تثبيت ssh(1) محليًا، و nc(1) (من مشروع nmap) مثبتًا على الخادم البعيد.

سلطة URI يتم تحليل الجزء الخاص بالسلطة من URI "username@servername:port" اعتمادًا على النقل. بالنسبة لـ TCP، فإنه يحدد الخادم للاتصال به ورقم المنفذ الاختياري. بالنسبة لـ "+unix" لا ينبغي تقديمه. بالنسبة لـ "+vsock" يكون اسم الخادم هو CID الرقمي (مثل 2 للاتصال بالخادم)، وقد يكون رقم المنفذ الاختياري موجودًا. بالنسبة لـ "+ssh"، يكون خادم Secure Shell والمنفذ الاختياري. إذا تم تقديم "username"، يتم استخدامه للمصادقة على TLS.

اسم تصدير URI لجميع عمليات النقل، يمكن تقديم اسم تصدير، يتم تحليله وفقًا لمواصفات URI الخاصة بـ NBD. لاحظ أن حرف "/" الأولي ليس جزءًا من اسم التصدير:

اسم تصدير URI nbd://localhost/ "" (سلسلة فارغة) nbd://localhost/export "export"

من الممكن تجاوز اسم التصدير برمجيًا باستخدام nbd_set_opt_mode(3) لتمكين وضع الخيارات، ثم استخدام nbd_set_export_name(3) و nbd_opt_go(3) كجزء من التفاوض اللاحق.

استعلام URI أخيرًا، يمكن أن يحتوي جزء الاستعلام من URI على:

socket=SOCKET يحدد مقبس نطاق Unix للاتصال عليه. يجب أن يكون موجودًا للنقل "+unix"، اختياري لـ "+ssh"، ويجب ألا يكون موجودًا لعمليات النقل الأخرى.

tls-certificates=DIR تعيين دليل الشهادات. انظر nbd_set_tls_certificates(3). لاحظ أن هذا غير مسموح به افتراضيًا - انظر القسم التالي.

tls-psk-file=PSKFILE تعيين ملف PSK. انظر nbd_set_tls_psk_file(3). لاحظ أن هذا غير مسموح به افتراضيًا - انظر القسم التالي.

tls-hostname="SERVER" تعيين اسم مضيف TLS. انظر nbd_set_tls_hostname(3).

tls-verify-peer=false عدم التحقق من شهادة الخادم. انظر nbd_set_tls_verify_peer(3). الافتراضي هو "true".

تعطيل ميزات URI لأسباب أمنية، قد ترغب في تعطيل ميزات URI معينة. التصفية المسبقة لـ URIs عرضة للأخطاء ويجب عدم محاولتها. بدلاً من ذلك، استخدم واجهات برمجة تطبيقات libnbd أدناه للتحكم فيما يمكن أن يظهر في URIs. لاحظ أنه يجب عليك استدعاء هذه الدوال على نفس المقبض قبل استدعاء nbd_connect_uri(3) أو nbd_aio_connect_uri(3).

عمليات نقل TCP، مقبس نطاق Unix، "AF_VSOCK"، أو SSH الافتراضي: كلها مسموح بها

لاختيار عمليات النقل المسموح بها، استدع nbd_set_uri_allow_transports(3).

يفرض libxml2 (المستخدم لتحليل URI) قيودًا إضافية. libxml2 < 2.9 قيدت أرقام المنافذ بـ 99,999,999. libxml2 ≥ 2.9 يحد أرقام المنافذ بـ ≤ 0x7fff_ffff (31 بت).

إنهاء التفاوض والمضي قدمًا في استخدام تصدير

اطلب من الخادم إنهاء التفاوض والمضي قدمًا في خدمة التصدير الذي تم تحديده مسبقًا بواسطة أحدث استدعاء لـ nbd_set_export_name(3) أو nbd_connect_uri(3). لا يمكن استخدام هذا إلا إذا قام nbd_set_opt_mode(3) بتمكين وضع الخيارات.

لتحديد وقت اكتمال الطلب، انتظر حتى يعيد nbd_aio_is_connecting(3) القيمة false. أو قم بتوفير "دالة رد الاتصال" "completion_callback" الاختيارية التي سيتم استدعاؤها كما هو موضح في "دوال رد الاتصال" في libnbd(3)، باستثناء أنه يتم التراجع عنها تلقائيًا بغض النظر عن القيمة المعادة. لاحظ أن الكشف المباشر عما إذا كان الخادم يعيد خطأ (كما هو الحال مع القيمة المعادة للمقابل المتزامن) ممكن فقط باستخدام دالة رد اتصال؛ ومع ذلك، من الممكن أيضًا اكتشاف خطأ بشكل غير مباشر عندما يعيد nbd_aio_is_negotiating(3) القيمة true.
