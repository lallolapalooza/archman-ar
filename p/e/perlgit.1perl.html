PERLGIT(1perl) دليل مبرمجي بيرل PERLGIT(1perl)

الاسم

perlgit - معلومات مفصلة حول git ومستودع Perl

الوصف

يقدم هذا المستند تفاصيل حول استخدام git لتطوير Perl. إذا كنت مهتمًا فقط بالعمل على تصحيح سريع، فراجع perlhack أولاً. هذا المستند مخصص للأشخاص الذين يساهمون بانتظام في Perl، بما في ذلك أولئك الذين لديهم حق الوصول للكتابة إلى مستودع git.

استنساخ المستودع

يتم الاحتفاظ بجميع الشيفرة المصدرية لـ Perl مركزيًا في مستودع Git على github.com.

يمكنك إنشاء نسخة للقراءة فقط من المستودع عن طريق تشغيل:

% git clone git@github.com:Perl/perl5.git perl

إذا لم تتمكن من استخدام هذا لأسباب تتعلق بجدار الحماية، فيمكنك أيضًا الاستنساخ عبر http:

% git clone https://github.com/Perl/perl5.git perl

العمل مع المستودع

بمجرد دخولك إلى دليل المستودع، يمكنك فحصه. بعد الاستنساخ، سيحتوي المستودع على فرع محلي واحد، وسيكون هو الفرع الحالي أيضًا، كما يتضح من علامة النجمة.

% git branch
* blead

استخدام الخيار -a للأمر "branch" سيظهر أيضًا فروع التتبع عن بعد في المستودع:

% git branch -a
* blead
  origin/HEAD
  origin/blead
...

الفروع التي تبدأ بـ "origin" تتوافق مع "git remote" الذي قمت بالاستنساخ منه (والذي يسمى "origin"). سيتم تتبع كل فرع على الطرف البعيد بواسطة هذه الفروع. لا يجب عليك أبدًا العمل على فروع التتبع عن بعد هذه. أنت تعمل دائمًا في فرع محلي. يمكن تكوين الفروع المحلية لدمج تلقائي (عند السحب) من فرع تتبع عن بعد مخصص. هذا هو الحال مع الفرع الافتراضي "blead" والذي سيتم تكوينه للدمج من فرع التتبع عن بعد "origin/blead".

يمكنك رؤية الالتزامات الأخيرة:

% git log

وسحب التغييرات الجديدة من المستودع، وتحديث المستودع المحلي الخاص بك (يجب أن يكون نظيفًا أولاً)

% git pull

بافتراض أننا على الفرع "blead" مباشرة بعد السحب، سيكون هذا الأمر مكافئًا تقريبًا لـ:

% git fetch
% git merge origin/blead

في الواقع، إذا كنت ترغب في تحديث مستودعك المحلي دون لمس دليل العمل الخاص بك، فقم بتشغيل:

% git fetch

وإذا كنت ترغب في تحديث فروع التتبع عن بعد لجميع الأطراف البعيدة المحددة في وقت واحد، يمكنك تشغيل:

% git remote update

لا يؤدي أي من هذين الأمرين الأخيرين إلى تحديث دليل العمل الخاص بك، ومع ذلك، سيقوم كلاهما بتحديث فروع التتبع عن بعد في المستودع الخاص بك.

لإنشاء فرع محلي من فرع بعيد:

% git checkout -b maint-5.10 origin/maint-5.10

للتبديل مرة أخرى إلى blead:

% git checkout blead

معرفة حالتك

الأمر git الأكثر استخدامًا سيكون على الأرجح

% git status

سينتج هذا الأمر كمخرج وصف للحالة الحالية للمستودع، بما في ذلك الملفات المعدلة والملفات غير المتتبعة التي لم يتم تجاهلها، بالإضافة إلى ذلك سيظهر أشياء مثل الملفات التي تم إعدادها للالتزام التالي، وعادةً بعض المعلومات المفيدة حول كيفية تغيير الأشياء. على سبيل المثال، ما يلي:

% git status
On branch blead
Your branch is ahead of 'origin/blead' by 1 commit.
Changes to be committed:
  (use "git reset HEAD <file>..." to unstage)
      modified:   pod/perlgit.pod
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git checkout -- <file>..." to discard changes in working
                                                             directory)
      modified:   pod/perlgit.pod
Untracked files:
  (use "git add <file>..." to include in what will be committed)
      deliberate.untracked

يظهر هذا أنه كانت هناك تغييرات في هذا المستند تم إعدادها للالتزام، وأنه كانت هناك تغييرات إضافية في دليل العمل لم يتم إعدادها بعد. كما يظهر أنه كان هناك ملف غير متتبع في دليل العمل، وكما ترى يوضح كيفية تغيير كل هذا. كما يظهر أنه يوجد التزام واحد على الفرع العامل "blead" لم يتم دفعه إلى الطرف البعيد "origin" بعد. ملاحظة: هذا الإخراج هو أيضًا ما تراه كقالب إذا لم تقدم رسالة إلى "git commit".

سير عمل التصحيح

أولاً، يرجى قراءة perlhack للحصول على تفاصيل حول تعديل نواة Perl. يغطي هذا المستند العديد من التفاصيل حول كيفية إنشاء تصحيح جيد.

إذا كان لديك بالفعل مستودع Perl، فيجب عليك التأكد من أنك على الفرع blead، وأن المستودع الخاص بك محدث:

% git checkout blead
% git pull

يفضل التصحيح مقابل أحدث إصدار من blead، حيث أن هذا هو المكان الذي يحدث فيه التطوير الجديد لجميع التغييرات بخلاف إصلاحات الأخطاء الحرجة. يجب إجراء تصحيحات الأخطاء الحرجة مقابل فروع maint ذات الصلة، أو يجب تقديمها مع ملاحظة تشير إلى جميع الفروع التي يجب تطبيق الإصلاح عليها.

الآن بعد أن أصبح كل شيء محدثًا، نحتاج إلى إنشاء فرع جديد مؤقت لهذه التغييرات والتبديل إليه:

% git checkout -b orange

وهو اختصار لـ:

% git branch orange
% git checkout orange

إنشاء فرع موضوعي يجعل من السهل على المشرفين إعادة تشكيل أو دمج مرة أخرى إلى blead الرئيسي للحصول على تاريخ أكثر خطية. إذا لم تعمل على فرع موضوعي، فسيتعين على المشرف اختيار تغييراتك يدويًا إلى blead قبل أن يمكن تطبيقها.

سيؤدي ذلك إلى تعرضك للانتقاد على perl5-porters، لذا لا تفعل ذلك. كن رائعًا.

ثم قم بإجراء تغييراتك. على سبيل المثال، إذا قام Leon Brocard بتغيير اسمه إلى Orange Brocard، فيجب علينا تغيير اسمه في ملف AUTHORS:

% perl -pi -e 's{Leon Brocard}{Orange Brocard}' AUTHORS

يمكنك رؤية الملفات التي تم تغييرها:

% git status
On branch orange
Changes to be committed:
  (use "git reset HEAD <file>..." to unstage)
   modified:   AUTHORS

ويمكنك رؤية التغييرات:

% git diff
diff --git a/AUTHORS b/AUTHORS
index 293dd70..722c93e 100644
--- a/AUTHORS
+++ b/AUTHORS
@@ -541,7 +541,7 @@    Lars Hecking              <lhecking@nmrc.ucc.ie>
 Laszlo Molnar                  <laszlo.molnar@eth.ericsson.se>
 Leif Huhn                      <leif@hale.dkstat.com>
 Len Johnson                    <lenjay@ibm.net>
-Leon Brocard                   <acme@astray.com>
+Orange Brocard                 <acme@astray.com>

الآن قم بالالتزام بتغييرك محليًا:

% git commit -a -m 'Rename Leon Brocard to Orange Brocard'
Created commit 6196c1d: Rename Leon Brocard to Orange Brocard
 1 files changed, 1 insertions(+), 1 deletions(-)

يتم استخدام الخيار "-a" لتضمين جميع الملفات التي يتتبعها git والتي قمت بتغييرها. إذا كنت ترغب في هذا الوقت في الالتزام ببعض الملفات التي عملت عليها فقط، فيمكنك حذف "-a" واستخدام الأمر "git add FILE ..." قبل إجراء الالتزام. يتيح لك "git add --interactive" حتى الالتزام بأجزاء من الملفات بدلاً من جميع التغييرات فيها.

يتم استخدام الخيار "-m" لتحديد رسالة الالتزام. إذا حذفتها، فسيفتح git محرر نصوص لك لصياغة الرسالة تفاعليًا. هذا مفيد عندما تكون التغييرات أكثر تعقيدًا من العينة المعطاة هنا، وبناءً على المحرر، لمعرفة أن السطر الأول من رسالة الالتزام لا يتجاوز الحد الأقصى القانوني البالغ 50 حرفًا. انظر "رسالة الالتزام" في perlhack لمزيد من المعلومات حول ما يجعل رسالة الالتزام جيدة.

بمجرد الانتهاء من كتابة رسالة الالتزام والخروج من المحرر، سيقوم git بكتابة تغييرك إلى القرص وإخبارك بشيء كهذا:

Created commit daf8e63: explain git status and stuff about remotes
 1 files changed, 83 insertions(+), 3 deletions(-)

إذا قمت بإعادة تشغيل

هذا الموقع غير مرتبط بـ Arch Linux ولا تابع له بأي شكل من الأشكال. المحتوى هو ترجمة فقط لصفحات دليل Arch المنشورة على man.archlinux.org.

n "حذف-ودفع" % git push origin :$user/$topic % git push origin $user/$topic

ملاحظة: يُحظر على مستوى المستودع حذف أي من الفروع "الأساسية". وهي أي فرع يطابق "m!^(blead|maint|perl)!". أي محاولة للقيام بذلك ستؤدي إلى قيام git بإنتاج خطأ مثل هذا:

% git push origin :blead
*** يُحظر حذف فروع blead/maint في هذا المستودع
خطأ: انتهى تشغيل الخطافات/التحديث برمز الخطأ 1
خطأ: رفض الخطاف تحديث refs/heads/blead
إلى ssh://perl5.git.perl.org/perl
 ! [مرفوض عن بعد] blead (رفض الخطاف)
 خطأ: فشل في دفع بعض المراجع إلى 'ssh://perl5.git.perl.org/perl'

كجزء من السياسة، نحن لا نعدل سجل التغييرات لفروع blead و maint-*. إذا تسلل خطأ إملائي (أو أسوأ) إلى التزام لـ blead أو maint-*, فسنصلحه في التزام آخر. أنواع التحديثات الوحيدة المسموح بها على هذه الفروع هي "التقديم السريع"، حيث يتم الاحتفاظ بجميع السجلات.

لن يتم حذف العلامات المشروحة (annotated tags) في المستودع الرسمي perl.git أو تعديلها مطلقًا. فكر طويلاً وبجدية فيما إذا كنت ترغب في دفع علامة محلية إلى perl.git قبل القيام بذلك. (دفع العلامات البسيطة غير مسموح به).

التطعيمات

يحتوي سجل التغييرات في perl على خطأ واحد لم يتم اكتشافه أثناء التحويل: تم تسجيل دمج في السجل بين blead و maint-5.10 لم يحدث فيه أي دمج فعليًا. نظرًا لطبيعة git، أصبح من المستحيل الآن إصلاح هذا في المستودع العام. يمكنك إزالة هذا الدمج الخاطئ محليًا عن طريق إضافة السطر التالي إلى ملفك ".git/info/grafts":

296f12bbbbaa06de9be9d09d3dcf8f4528898a49 434946e0cb7a32589ed92d18008aaa1d88515930

من المهم بشكل خاص وجود سطر التطعيم هذا إذا تم إجراء أي عملية تقسيم (bisecting) في منطقة "الدمج" المعنية.

الكتابة إلى مستودع Git

بمجرد حصولك على حق الكتابة، ستحتاج إلى تعديل عنوان URL للطرف البعيد "origin" لتمكين الدفع. قم بتحرير .git/config باستخدام الأمر git-config(1):

% git config remote.origin.url git@github.com:Perl/perl5.git

يمكنك أيضًا إعداد اسم المستخدم وعنوان البريد الإلكتروني الخاص بك. يقوم معظم الأشخاص بذلك مرة واحدة بشكل عام في ملف ~/.gitconfig بفعل شيء مثل:

% git config --global user.name "Ævar Arnfjörð Bjarmason"
% git config --global user.email avarab@gmail.com

ومع ذلك، إذا كنت ترغب في تجاوز ذلك خصيصًا لـ perl، فقم بتنفيذ شيء مثل ما يلي في perl:

% git config user.email avar@cpan.org

من الممكن أيضًا الاحتفاظ "origin" كطرف بعيد لـ git، وإضافة طرف جديد للوصول عبر ssh:

% git remote add camel git@github.com:Perl/perl5.git

هذا يسمح لك بتحديث المستودع المحلي الخاص بك عن طريق السحب من "origin"، وهو أسرع ولا يتطلب منك المصادقة، ودفع تغييراتك مرة أخرى باستخدام الطرف البعيد "camel":

% git fetch camel
% git push camel

يقوم أمر "fetch" بتحديث مراجع "camel" فقط، حيث يجب أن تكون الكائنات نفسها قد تم جلبها عند السحب من "origin".

العمل مع طلبات السحب الخاصة بـ GitHub

تنبع طلبات السحب عادةً من خارج مستودع "Perl/perl.git"، لذلك إذا كنت ترغب في اختبارها أو العمل معها محليًا، فإن استدعاء "git fetch" القياسي من مستودع "Perl/perl5.git" لن يجلبها.

ومع ذلك، يوفر GitHub آلية لجلب طلب سحب إلى فرع محلي. وهي متاحة على الأطراف البعيدة الخاصة بـ GitHub تحت "pull/"، لذا يمكنك استخدام "git fetch pull/PRID/head:localname" لإنشاء نسخة محلية. على سبيل المثال، لجلب طلب السحب 9999 إلى الفرع المحلي "local-branch-name"، قم بتشغيل:

git fetch origin pull/9999/head:local-branch-name

ثم:

git checkout local-branch-name

ملاحظة: هذا الفرع ليس معادًا بناؤه على "blead"، لذا بدلاً من عملية السحب المذكورة أعلاه، قد ترغب في:

git rebase origin/blead local-branch-name

مما يعيد بناء "local-branch-name" على "blead"، ويقوم بسحبها.

بدلاً من ذلك، يمكنك تكوين الطرف البعيد لجلب جميع طلبات السحب كمراجع تتبع الأطراف البعيدة. للقيام بذلك، قم بتحرير الطرف البعيد في .git/config، على سبيل المثال إذا كان طرفك البعيد على GitHub هو "origin"، سيكون لديك:

[remote "origin"]
        url = git@github.com:/Perl/perl5.git
        fetch = +refs/heads/*:refs/remotes/origin/*

أضف سطرًا لربط فروع طلبات السحب البعيدة بمراجع تتبع الأطراف البعيدة:

[remote "origin"]
        url = git@github.com:/Perl/perl5.git
        fetch = +refs/heads/*:refs/remotes/origin/*
        fetch = +refs/pull/*/head:refs/remotes/origin/pull/*

ثم قم بعمل fetch كالمعتاد:

git fetch origin

سيؤدي هذا إلى إنشاء فرع تتبع طرف بعيد لكل طلب سحب، بما في ذلك الطلبات المغلقة.

لإزالة فروع تتبع الأطراف البعيدة هذه، قم بإزالة السطر المضاف أعلاه وقم بالتقليم:

git fetch -p origin # أو git remote prune origin

قبول رقعة (patch)

إذا تلقيت ملف رقعة تم إنشاؤه باستخدام القسم أعلاه، فيجب عليك تجربة الرقعة.

أولاً، نحتاج إلى إنشاء فرع جديد مؤقت لهذه التغييرات والانتقال إليه:

% git checkout -b experimental

يتم تطبيق الرقع التي تم تنسيقها بواسطة "git format-patch" باستخدام "git am":

% git am 0001-Rename-Leon-Brocard-to-Orange-Brocard.patch
Applying Rename Leon Brocard to Orange Brocard

لاحظ أن بعض أنظمة البريد الإلكتروني UNIX يمكن أن تتلاعب بالملفات النصية المرفقة التي تحتوي على 'From '. هذا سيصلحها:

% perl -pi -e's/^>From /From /' \
                       0001-Rename-Leon-Brocard-to-Orange-Brocard.patch

إذا تم توفير اختلاف خام (raw diff) فقط، فمن الممكن أيضًا استخدام هذه العملية المكونة من خطوتين:

% git apply bugfix.diff
% git commit -a -m "بعض الإصلاحات" \
                           --author="That Guy <that.guy@internets.com>"

إذا كنت مساهمًا في Perl وتعتقد أن الرقعة جيدة، فيمكنك بعد ذلك دمجها في blead ثم دفعها إلى المستودع الرئيسي:

% git checkout blead
% git merge experimental
% git push origin blead

إذا كنت تريد حذف فرعك المؤقت، يمكنك القيام بذلك باستخدام:

% git checkout blead
% git branch -d experimental
خطأ: الفرع 'experimental' ليس سلفًا لرأسك الحالي (HEAD). إذا كنت متأكدًا من رغبتك في حذفه، قم بتشغيل 'git branch -D experimental'.
% git branch -D experimental
تم حذف الفرع experimental.

الالتزام بـ blead

سيصبح فرع 'blead' الإصدار الإنتاجي التالي من Perl.

قبل دفع أي تغيير محلي إلى blead، من المهم للغاية أن تقوم ببعض الأشياء، حتى لا يأتي المساهمون الآخرون بعدك بمشاعل ورمانات:

  • تأكد من أن لديك رسالة التزام جيدة. انظر "رسالة الالتزام" في perlhack للحصول على التفاصيل.
  • قم بتشغيل مجموعة الاختبارات. قد لا تعتقد أن إصلاح خطأ إملائي واحد سيؤدي إلى فشل ملف اختبار. ستكون مخطئًا. إليك مثال على مكان تسبب عدم تشغيل الاختبارات في مشاكل. تم تقديم رقعة أضافت اختبارين إلى ملف .t موجود. لا يمكن أن تؤثر على أي شيء آخر، لذا لا داعي للاختبار بعد الملف .t المتأثر الوحيد، صحيح؟ ولكن، تغير عنوان البريد الإلكتروني للمقدم منذ آخر تقديم له، وتسبب هذا في فشل اختبارات أخرى. كان تشغيل هدف الاختبار الموضح في البند التالي سيؤدي إلى اكتشاف هذه المشكلة.
  • إذا لم تقم بتشغيل مجموعة الاختبارات الكاملة، فقم بتشغيل "make test_porting" على الأقل. سيؤدي هذا إلى تشغيل فحوصات السلامة الأساسية. لمعرفة فحوصات السلامة، انظر في t/porting.
  • إذا قمت بإجراء أي تغييرات تؤثر على miniperl أو روتينات النواة التي لديها مسارات رمز مختلفة لـ miniperl، فتأكد من تشغيل "make minitest". سيؤدي هذا إلى اكتشاف المشاكل التي حتى مجموعة الاختبارات الكاملة لن تكتشفها لأنها تشغل مجموعة فرعية من الاختبارات تحت miniperl بدلاً من perl.

حول الدمج وإعادة البناء

يجب أن تكون الالتزامات البسيطة، لمرة واحدة، التي يتم دفعها إلى فرع 'blead' التزامات بسيطة تنطبق بشكل نظيف. بمعنى آخر، يجب عليك التأكد من أن عملك ملتزم مقابل الموضع الحالي لـ blead، بحيث يمكنك الدفع مرة أخرى إلى المستودع الرئيسي دون دمج.

في بعض الأحيان، يتحرك blead أثناء بناء أو اختبار تغييراتك. عندما يحدث هذا، سيتم رفض الدفع الخاص بك برسالة مثل هذه:

إلى ssh://perl5.git.perl.org/perl.git
 ! [مرفوض]        blead -> blead (تحديثات غير تقديم سريع)
خطأ: فشل في دفع بعض المراجع إلى 'ssh://perl5.git.perl.org/perl.git'
لمنعك من فقدان السجل، تم رفض التحديثات غير التقديم السريع. قم بدمج التغييرات البعيدة (على سبيل المثال 'git pull') قبل الدفع مرة أخرى. انظر قسم 'ملاحظة حول التقديم السريع' في 'git push --help' للتفاصيل.

عندما يحدث هذا، يمكنك ببساطة إعادة بناء عملك مرة أخرى

st الموضع الجديد لـ blead، على هذا النحو (بافتراض أن المستودع البعيد الخاص بك للمستودع الرئيسي هو "p5p"):

% git fetch p5p
% git rebase p5p/blead

سترى الالتزامات الخاصة بك يتم إعادة تطبيقها، وبعد ذلك ستتمكن من الدفع بأمان. يمكن العثور على مزيد من المعلومات حول إعادة التأسيس في وثائق الأمر git-rebase(1).

لمجموعات أكبر من الالتزامات التي لا معنى لها إلا معًا، أو التي ستستفيد من ملخص لغرض المجموعة، يجب عليك استخدام التزام دمج. يجب عليك أداء عملك على فرع موضوع، والذي يجب عليك إعادة تأسيسه بانتظام مقابل blead للتأكد من أن الكود الخاص بك لا يتم كسره بواسطة blead المتحرك. عند الانتهاء من عملك، يرجى إجراء إعادة تأسيس نهائية واختبار. تاريخ خطي هو شيء يتم فقده مع كل التزام في blead، ولكن إعادة تأسيس نهائية تجعل التاريخ خطيًا مرة أخرى، مما يسهل على القائمين على الصيانة المستقبليين رؤية ما حدث. قم بإعادة التأسيس على النحو التالي (بافتراض أن عملك كان على الفرع "committer/somework"):

% git checkout committer/somework
% git rebase blead

ثم يمكنك دمجه في الرئيسي على هذا النحو:

% git checkout blead
% git merge --no-ff --no-commit committer/somework
% git commit -a

تستحق المفاتيح أعلاه الشرح. "--no-ff" يشير إلى أنه حتى لو كان يمكن تطبيق كل عملك خطيًا مقابل blead، لا يزال يجب إعداد التزام دمج. هذا يضمن أن كل عملك سيتم عرضه كفرع جانبي، مع دمج جميع الالتزامات الخاصة بك في blead الرئيسي بواسطة التزام الدمج.

"--no-commit" يعني أن التزام الدمج سيتم إعداده ولكن ليس الالتزام به. يتم بعد ذلك أداء الالتزام فعليًا عند تشغيل الأمر التالي، والذي سيؤدي إلى فتح المحرر الخاص بك لوصف الالتزام. بدون "--no-commit"، سيتم إجراء الالتزام بدون رسالة مفيدة تقريبًا، مما سيقلل بشكل كبير من قيمة التزام الدمج كعنصر نائب لوصف العمل.

عند وصف التزام الدمج، اشرح الغرض من الفرع، وخذ في الاعتبار أن هذا الوصف سيتم استخدامه على الأرجح من قبل مهندس الإصدار النهائي عند مراجعة مستند perldelta التالي.

إذا فشل الدفع اللاحق، فيجب عليك توخي الحذر في كيفية إعادة التأسيس. إذا استخدمت

% git rebase p5p/blead

أو

% git pull --rebase

فقد يتم فقدان التزام الدمج الذي أنشأته بعناية! لتجنب ذلك، يمكنك استخدام:

% git fetch p5p
% git rebase --rebase-merges p5p/blead

سيؤدي هذا إلى إعادة إنشاء التزام الدمج الخاص بك.

(إذا كنت عالقًا بإصدار أقدم من git (قبل 2.18)، فلن يحتوي "git rebase" على المفتاح "--rebase-merges"، بدلاً من ذلك، يجب عليك استخدام المفتاح "--preserve-merges".)

Commiting to maintenance versions

يجب تعديل إصدارات الصيانة فقط لإضافة إصلاحات حرجة للأخطاء، انظر perlpolicy.

للالتزام بإصدار صيانة من perl، تحتاج إلى إنشاء فرع تتبع محلي:

% git checkout --track -b maint-5.005 origin/maint-5.005

يقوم هذا بإنشاء فرع محلي يسمى "maint-5.005"، والذي يتتبع الفرع البعيد "origin/maint-5.005". ثم يمكنك السحب، الالتزام، الدمج، والدفع كما كان من قبل.

يمكنك أيضًا اختيار التزامات محددة (cherry-pick) من blead وفرع آخر، وذلك باستخدام الأمر "git cherry-pick". يوصى باستخدام الخيار -x لـ "git cherry-pick" لتسجيل SHA1 للالتزام الأصلي في رسالة الالتزام الجديدة.

قبل دفع أي تغيير إلى إصدار صيانة، تأكد من أنك قد استوفيت الخطوات في "Commiting to blead" أعلاه.

Using a smoke-me branch to test changes

في بعض الأحيان يؤثر التغيير على مسارات الكود التي لا يمكنك اختبارها على أنظمة التشغيل المتاحة لك مباشرة، وسيكون من الحكمة أن يقوم المستخدمون على أنظمة تشغيل أخرى باختبار التغيير قبل أن تلتزم به في blead.

لحسن الحظ، هناك طريقة لاختبار التغيير الخاص بك على أنظمة تشغيل مختلفة: قم بدفعه إلى فرع "smoke-me" وانتظر حتى يقوم مختبرو الدخان الآليون بالإبلاغ عن النتائج من أنظمة التشغيل الخاصة بهم. يتم تحديد فرع "smoke-me" بواسطة اسم الفرع: على وجه التحديد، كما هو موضح على github.com، يجب أن يكون فرعًا محليًا يكون مكون اسمه الأول هو بالضبط "smoke-me".

الإجراء الخاص بفعل ذلك هو تقريبًا كما يلي (باستخدام مثال فرع smoke-me الخاص بـ tonyc المسمى win32stat):

أولاً، قم بإنشاء فرع محلي وانتقل إليه:

% git checkout -b win32stat

قم بإجراء بعض التغييرات، وقم ببناء perl واختبر تغييراتك، ثم قم بالالتزام بها في فرعك المحلي. ثم قم بدفع فرعك المحلي إلى فرع smoke-me بعيد:

% git push origin win32stat:smoke-me/tonyc/win32stat

الآن يمكنك العودة إلى blead محليًا:

% git checkout blead

واستمر في العمل على أشياء أخرى أثناء انتظار يوم أو يومين، مع مراقبة النتائج المبلغ عنها لفرع "smoke-me" الخاص بك على https://perl.develop-help.com/?b=smoke-me/tonyc/win32state.

إذا كان كل شيء على ما يرام، فقم بتحديث فرع blead الخاص بك:

% git pull

ثم قم بفحص فرع smoke-me الخاص بك مرة أخرى وأعد تأسيسه على blead:

% git rebase blead win32stat

الآن عد إلى blead وادمج فرع smoke-me الخاص بك فيه:

% git checkout blead
% git merge win32stat

كما هو موضح سابقًا، إذا كان هناك العديد من التغييرات في فرع smoke-me الخاص بك، فيجب عليك إعداد التزام دمج لتقديم نظرة عامة على تلك التغييرات باستخدام الأمر التالي بدلاً من الأمر الأخير أعلاه:

% git merge win32stat --no-ff --no-commit

يجب عليك الآن بناء perl واختبار تغييراتك (التي تم دمجها) مرة أخيرة (من المثالي تشغيل مجموعة الاختبار بأكملها، ولكن إذا لم يكن ذلك ممكنًا، فقم بتشغيل اختبارات t/porting/*.t على الأقل) قبل دفع تغييراتك كالمعتاد:

% git push origin blead

أخيرًا، يجب عليك بعد ذلك حذف فرع smoke-me البعيد:

% git push origin :smoke-me/tonyc/win32stat

(والذي من المحتمل أن ينتج عنه تحذير مثل هذا، والذي يمكن تجاهله:

remote: fatal: ambiguous argument
                                 'refs/heads/smoke-me/tonyc/win32stat':
unknown revision or path not in the working tree.
remote: Use '--' to separate paths from revisions

) ثم حذف الفرع المحلي الخاص بك:

% git branch -d win32stat
