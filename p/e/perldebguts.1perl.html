NAME

perldebguts - Guts of Perl debugging

DESCRIPTION

This is not perldebug, which tells you how to use the debugger. This manpage describes low-level details concerning the debugger's internals, which range from difficult to impossible to understand for anyone who isn't incredibly intimate with Perl's guts. Caveat lector.

Debugger Internals

Perl has special debugging hooks at compile-time and run-time used to create debugging environments. These hooks are not to be confused with the perl -Dxxx command described in perlrun, which is usable only if a special Perl is built per the instructions in the INSTALL file in the Perl source tree.

For example, whenever you call Perl's built-in "caller" function from the package "DB", the arguments that the corresponding stack frame was called with are copied to the @DB::args array. These mechanisms are enabled by calling Perl with the -d switch. Specifically, the following additional features are enabled (cf. "$^P" in perlvar):

  • Perl inserts the contents of $ENV{PERL5DB} (or "BEGIN {require 'perl5db.pl'}" if not present) before the first line of your program.
  • If the "-dt" switch is supplied, "PERL5DB_THREADED=1" is set in the environment. "perl5db.pl" or your custom debugger can use this to enable threading support.
  • Each array "@{"_<$filename"}" holds the lines of $filename for a file compiled by Perl. The same is also true for "eval"ed strings that contain subroutines, or which are currently being executed. The $filename for "eval"ed strings looks like "(eval 34)".

    Values in this array are magical in numeric context: they compare equal to zero only if the line is not breakable.

  • Each hash "%{"_<$filename"}" contains breakpoints and actions keyed by line number. Individual entries (as opposed to the whole hash) are settable. Perl only cares about Boolean true here, although the values used by perl5db.pl have the form "$break_condition\0$action".

    The same holds for evaluated strings that contain subroutines, or which are currently being executed. The $filename for "eval"ed strings looks like "(eval 34)".

  • Each scalar "${"_<$filename"}" contains $filename. This is also the case for evaluated strings that contain subroutines, or which are currently being executed. The $filename for "eval"ed strings looks like "(eval 34)".
  • After each "require"d file is compiled, but before it is executed, DB::postponed(*{"_<$filename"}) is called if the subroutine "DB::postponed" exists. Here, the $filename is the expanded name of the "require"d file, as found in the values of %INC.
  • After each subroutine "subname" is compiled, the existence of $DB::postponed{subname} is checked. If this key exists, DB::postponed(subname) is called if the "DB::postponed" subroutine also exists.
  • A hash %DB::sub is maintained, whose keys are subroutine names and whose values have the form "filename:startline-endline". "filename" has the form "(eval 34)" for subroutines defined inside "eval"s.
  • When the execution of your program reaches a point that can hold a breakpoint, the DB::DB() subroutine is called if any of the variables $DB::trace, $DB::single, or $DB::signal is true. These variables are not "local"izable. This feature is disabled when executing inside DB::DB(), including functions called from it unless "$^D & (1<<30)" is true.
  • When execution of the program reaches a subroutine call, a call to &DB::sub(args) is made instead, with $DB::sub set to identify the called subroutine. (This doesn't happen if the calling subroutine was compiled in the "DB" package.) $DB::sub normally holds the name of the called subroutine, if it has a name by which it can be looked up. Failing that, $DB::sub will hold a reference to the called subroutine. Either way, the &DB::sub subroutine can use $DB::sub as a reference by which to call the called subroutine, which it will normally want to do.

    If the call is to an lvalue subroutine, and &DB::lsub is defined &DB::lsub(args) is called instead, otherwise falling back to &DB::sub(args).

  • When execution of the program uses "goto" to enter a non-XS subroutine and the 0x80 bit is set in $^P, a call to &DB::goto is made, with $DB::sub set to identify the subroutine being entered. The call to &DB::goto does not replace the "goto"; the requested subroutine will still be entered once &DB::goto has returned. $DB::sub normally holds the name of the subroutine being entered, if it has one. Failing that, $DB::sub will hold a reference to the subroutine being entered. Unlike when &DB::sub is called, it is not guaranteed that $DB::sub can be used as a reference to operate on the subroutine being entered.

Note that if &DB::sub needs external data for it to work, no subroutine call is possible without it. As an example, the standard debugger's &DB::sub depends on the $DB::deep variable (it defines how many levels of recursion deep into the debugger you can go before a mandatory break). If $DB::deep is not defined, subroutine calls are not possible, even though &DB::sub exists.

Writing Your Own Debugger

Environment Variables

The "PERL5DB" environment variable can be used to define a debugger. For example, the minimal "working" debugger (it actually doesn't do anything) consists of one line:

sub DB::DB {}

It can easily be defined like this:

$ PERL5DB="sub DB::DB {}" perl -d your-script

Another brief debugger, slightly more useful, can be created with only the line:

sub DB::DB {print ++$i; scalar <STDIN>}

This debugger prints a number which increments for each statement encountered and waits for you to hit a newline before continuing to the next statement.

The following debugger is actually useful:

{
  package DB;
  sub DB  {}
  sub sub {print ++$i, " $sub\n"; &$sub}
}

It prints the sequence number of each subroutine call and the name of the called subroutine. Note that &DB::sub is being compiled into the package "DB" through the use of the "package" directive.

يُظهر السطر الأول الشكل المترجم مسبقًا للتعبير النمطي. يُظهر الثاني حجم الشكل المترجم (بوحدات اعتباطية، عادةً كلمات من 4 بايت) والعدد الإجمالي للبايتات المخصصة لجدول الإزاحة/الطول، عادةً 4+"الحجم"*8. يُظهر السطر التالي تسمية *المعرّف* لأول عقدة تقوم بمطابقة.

السطر

anchored 'de' at 1 floating 'gh' at 3..2147483647 (checking floating)
      stclass 'ANYOF[bc]' minlen 7

(المقسم إلى سطرين أعلاه) يحتوي على معلومات المُحسِّن. في المثال المعروض، وجد المُحسِّن أن المطابقة يجب أن تحتوي على سلسلة فرعية "de" عند الإزاحة 1، بالإضافة إلى سلسلة فرعية "gh" عند إزاحة ما بين 3 و اللانهاية. علاوة على ذلك، عند التحقق من هذه السلاسل الفرعية (للتخلي بسرعة عن المطابقات المستحيلة)، سيفحص Perl السلسلة الفرعية "gh" قبل التحقق من السلسلة الفرعية "de". قد يستخدم المُحسِّن أيضًا المعرفة بأن المطابقة تبدأ (عند *المعرّف* "الأول") بفئة أحرف، ولا يمكن لمطابقة أقل من 7 أحرف أن تتطابق.

الحقول ذات الأهمية التي قد تظهر في هذا السطر هي:

"anchored" STRING "at" POS
"floating" STRING "at" POS1..POS2
انظر أعلاه.
"matching floating/anchored"
السلسلة الفرعية التي سيتم التحقق منها أولاً.
"minlen"
الحد الأدنى لطول المطابقة.
"stclass" TYPE
نوع عقدة المطابقة الأولى.
"noscan"
لا تفحص السلاسل الفرعية الموجودة.
"isall"
يعني أن معلومات المُحسِّن هي كل ما يحتويه التعبير النمطي، وبالتالي لا تحتاج إلى الدخول إلى محرك التعبيرات النمطية على الإطلاق.
"GPOS"
تم ضبطه إذا كان النمط يحتوي على "\G".
"plus"
تم ضبطه إذا كان النمط يبدأ بحرف مكرر (كما في "x+y").
"implicit"
تم ضبطه إذا كان النمط يبدأ بـ ".*".
"with eval"
تم ضبطه إذا كان النمط يحتوي على مجموعات تقييم، مثل "(?{ code })" و "(??{ code })".
anchored(TYPE)
إذا كان النمط قد يتطابق فقط في عدد قليل من الأماكن، مع كون "TYPE" هو "SBOL"، "MBOL"، أو "GPOS". انظر الجدول أدناه.

إذا كان من المعروف أن سلسلة فرعية تتطابق في نهاية السطر فقط، فقد تتبعها "$"، كما في "floating 'k'$".

تُستخدم المعلومات الخاصة بالمُحسِّن لتجنب الدخول إلى محرك تعبيرات نمطية (بطيء) على السلاسل التي لن تتطابق بالتأكيد. إذا تم ضبط العلم "isall"، يمكن تجنب استدعاء محرك التعبيرات النمطية حتى عندما يجد المُحسِّن مكانًا مناسبًا للمطابقة.

NAME

perldebguts - Debug Perl memory usage

DESCRIPTION

This manual page is intended to provide a user-visible summary of the internal memory management of Perl, with a focus on how to debug it. It is not a replacement for the gory details found in perlguts.

Perl's memory usage can be quite high, and debugging it can be tricky. This document tries to shed some light on the topic.

The following section delves into the internals of the Perl debugger itself, for those interested in how it works.

Debugger Internals

The Perl debugger, when invoked with the appropriate flags, can provide detailed information about the program's execution. This includes tracking memory allocations.

Frame Listing Output Examples

When debugging, the debugger might output information about call frames, which can indirectly reveal memory usage patterns.

Debugging Regular Expressions

Perl's regular expression engine also has its own debugging mechanisms, which can be helpful when performance issues related to regex are suspected.

Debugging Perl Memory Usage

Perl's memory management can be complex. Various factors contribute to the overall memory footprint:

  • Data Structure Overhead: Simple data types like integers may require a base amount of memory (e.g., 20 bytes). Floating-point numbers might require more (e.g., 24 bytes), and strings even more (e.g., 32 bytes). These examples assume 32-bit architectures; 64-bit architectures tend to have larger memory footprints.

    If a variable is used in multiple contexts (integer, float, string), its memory footprint can increase further (an additional 20 bytes in the example). A poorly implemented malloc(3) can exacerbate these numbers significantly.

  • Subroutine Declarations: Even a simple subroutine declaration like 

    sub foo;
    can consume up to 500 bytes, depending on the Perl release.

  • Source-to-Compiled Code Bloat: Estimates suggest that the compiled form of well-written (commented, indented) code can be roughly eight times larger in memory than its source code on disk.

The "-DL" command-line switch is obsolete since Perl 5.6.0. It was used for tracking memory allocations and potential leaks, but is now superseded by dedicated malloc debugging tools like Purify or valgrind. For more information, consult "PERL_MEM_LOG" in perlhacktips.

To determine the memory usage of Perl data structures, the Devel::Size module from CPAN can be used. It provides the minimum bytes required to store a data structure. Pay attention to the difference between "size()" and "total_size()".

If Perl was compiled using its own malloc implementation, memory usage can be analyzed by setting the environment variable $ENV{PERL_DEBUG_MSTATS}.

Using $ENV{PERL_DEBUG_MSTATS}

When Perl is configured to use its own malloc() and compiled with the necessary options (which is the default), setting "$ENV{PERL_DEBUG_MSTATS} > 1" will print memory usage statistics after code compilation. Setting "$ENV{PERL_DEBUG_MSTATS} >= 1" will print statistics before program termination. The output format resembles the following example:

The Devel::Peek module's mstat() function can be used to obtain these statistics at arbitrary points during program execution.

Explanation of the output format:

"buckets SMALLEST(APPROX)..GREATEST(APPROX)"
Perl's malloc() employs a bucket allocation strategy. Each memory request is rounded up to the nearest available bucket size.

This line indicates the range of bucket sizes currently in use. Each bucket has a memory footprint and a maximum user data size. For example, if the smallest bucket size is 4, the largest usable size might be 8188 bytes with a footprint of 8192 bytes.

In debug builds of Perl, some buckets might show a negative usable size, meaning they are not used. For larger buckets, the memory footprint might exceed a power of two by one page; in such cases, the power of two is shown in the "APPROX" field.

Free/Used
The one or two rows of numbers following represent the count of buckets for each size between "SMALLEST" and "GREATEST". The first row typically shows buckets whose memory footprints are powers of two (or slightly larger). The second row, if present, details buckets with footprints falling between the sizes in the first row.

For instance, if the memory footprints were:

free:    8     16    32    64    128  256 512 1024 2048 4096 8192
                    4     12    24    48    80

In a non-"DEBUGGING" Perl build, buckets from 128 upwards may have a 4-byte overhead, meaning an 8192-byte bucket could accommodate up to 8188-byte allocations.

"Total sbrk(): SBRKed/SBRKs:CONTINUOUS"
The first two values indicate the total memory obtained via sbrk(2) and the number of sbrk(2) calls made. The third number reflects Perl's assessment of memory chunk continuity. A positive value suggests that sbrk(2) is likely to return contiguous memory blocks.

Memory allocated by external libraries is not included in this count.

"pad: 0"
The amount of memory obtained via sbrk(2) used to ensure bucket alignment.
"heads: 2192"
While larger buckets incorporate their overhead internally, smaller buckets store their overhead separately. This field represents the total size of these separate overhead areas.
"chain: 0"
malloc() may break down larger buckets into smaller ones. If a portion of a freed bucket remains undivided, it's kept as part of a linked list. This field shows the total size of these chain elements.
"tail: 6144"
To minimize the number of sbrk(2) calls, malloc() requests more memory than immediately needed. This field indicates the size of the unused portion of the memory obtained via sbrk(2) that has not yet been utilized.
