ملاحظة:




عند التجربة بإعدادات مختلفة (خاصة تلك المتعلقة بالبيانات الوصفية) قد يتداخل التخزين المؤقت وقد لا تكون التغييرات مرئية. في هذه الحالات، قم بتعطيل التخزين المؤقت باستخدام LOAD_CONTENT_CACHE = False أو استخدم مفتاح سطر الأوامر --ignore-cache.




modified يجب أن يكون آخر مرة قمت فيها بتحديث المقالة، ويتم تعيينه افتراضيًا على date إذا لم يتم تحديده. بالإضافة إلى ذلك، يمكنك عرض modified في القوالب، وسيتم تحديث إدخالات الموجز في قارئات الموجز تلقائيًا عند تعيين modified إلى التاريخ الحالي بعد تعديل مقالتك.

صفحات

إذا قمت بإنشاء مجلد باسم pages داخل مجلد المحتوى، فسيتم استخدام جميع الملفات الموجودة فيه لإنشاء صفحات ثابتة، مثل صفحات About أو Contact. (انظر مثال تخطيط نظام الملفات أدناه.)

يمكنك استخدام إعداد DISPLAY_PAGES_ON_MENU للتحكم فيما إذا كانت جميع هذه الصفحات معروضة في قائمة التنقل الرئيسية. (الافتراضي هو True.)

إذا كنت ترغب في استبعاد أي صفحات من الارتباط بها أو إدراجها في القائمة، فأضف سمة status: hidden إلى بياناتها الوصفية. هذا مفيد لأشياء مثل إنشاء صفحات خطأ تتناسب مع السمة المنشأة لموقعك.

محتوى ثابت

الملفات الثابتة هي ملفات أخرى غير المقالات والصفحات التي يتم نسخها إلى مجلد الإخراج كما هي، دون معالجة. يمكنك التحكم في الملفات الثابتة التي يتم نسخها باستخدام إعداد STATIC_PATHS لملف pelicanconf.py الخاص بالمشروع. تكوين Pelican الافتراضي يتضمن دليل images لهذا الغرض، ولكن يجب إضافة الآخرين يدويًا. بالإضافة إلى ذلك، يتم تضمين الملفات الثابتة التي يتم الارتباط بها بشكل صريح (انظر أدناه).

ملاحظة:

في التكوين الافتراضي، يتم معالجة جميع الملفات ذات لاحقة ملف المحتوى الصالحة (.html، .rst، .md، ...) بواسطة مولدات المقالات والصفحات قبل المولد الثابت. يتم تجنب ذلك عن طريق تعديل إعدادات *_EXCLUDE بشكل مناسب.

محتوى مختلط في نفس الدليل

بدءًا من Pelican 3.5، يمكن للملفات الثابتة مشاركة دليل مصدر بشكل آمن مع ملفات مصدر الصفحات، دون كشف مصادر الصفحات في الموقع المنشأ. يجب إضافة أي دليل من هذا القبيل إلى كل من STATIC_PATHS و PAGE_PATHS (أو STATIC_PATHS و ARTICLE_PATHS). سيحدد Pelican ويعالج ملفات مصدر الصفحات بشكل طبيعي، وينسخ الملفات المتبقية كما لو كانت تعيش في دليل منفصل مخصص للملفات الثابتة.

ملاحظة: وضع الملفات الثابتة وملفات مصدر المحتوى معًا في نفس دليل المصدر لا يضمن أنها ستنتهي في نفس المكان في الموقع المنشأ. أسهل طريقة للقيام بذلك هي باستخدام صيغة الارتباط {attach} (الموصوفة أدناه). بدلاً من ذلك، يمكن تكوين إعدادات STATIC_SAVE_AS و PAGE_SAVE_AS و ARTICLE_SAVE_AS (وإعدادات *_URL المقابلة) لوضع ملفات من أنواع مختلفة معًا، تمامًا كما كان يمكن في الإصدارات السابقة من Pelican.

الربط بالمحتوى الداخلي

بدءًا من Pelican 3.1، أصبح من الممكن الآن تحديد روابط داخل الموقع لملفات في تسلسل هرمي لمحتوى المصدر بدلاً من الملفات في التسلسل الهرمي المنشأ. هذا يجعل من السهل الربط من المنشور الحالي إلى محتوى آخر قد يكون بجانب هذا المنشور (بدلاً من الاضطرار إلى تحديد مكان وضع المحتوى الآخر بعد إنشاء الموقع).

للربط بالمحتوى الداخلي (الملفات في دليل content)، استخدم الصيغة التالية لهدف الارتباط: {filename}path/to/file. ملاحظة: الشرطات المائلة للأمام، /، هي فاصل المسار المطلوب في توجيه {filename} على جميع أنظمة التشغيل، بما في ذلك Windows.

│   └── pages

`a link relative to the current file <{filename}../article2.md>`_
`a link relative to the content root <{filename}/article2.md>`_

When using the code-block directive, you can specify a number of options that control the output of the syntax highlighting.

filename string If set, display the filename above the code block.

For example, the following code block enables line numbers, starting at 153, and prefixes the Pygments CSS classes with pgcss to make the names more unique and avoid possible CSS conflicts:

.. code-block:: identifier
    :classprefix: pgcss
    :linenos: table
    :linenostart: 153
   <indented code block goes here>

It is also possible to specify the PYGMENTS_RST_OPTIONS variable in your Pelican settings file to include options that will be automatically applied to every code block.

For example, if you want to have line numbers displayed for every code block and a CSS prefix, you would set this variable to:

PYGMENTS_RST_OPTIONS = {'classprefix': 'pgcss', 'linenos': 'table'}

If specified, settings for individual code blocks will override the defaults in your settings file.

Publishing drafts

If you want to publish an article or a page as a draft (for friends to review before publishing, for example), you can add a Status: draft attribute to its metadata. That article will then be output to the drafts folder and not listed on the index page nor on any category or tag page.

If your articles should be automatically published as a draft (to not accidentally publish an article before it is finished), include the status in the DEFAULT_METADATA:

DEFAULT_METADATA = {
    'status': 'draft',
}

To publish a post when the default status is draft, update the post's metadata to include Status: published.

Hidden Posts

Like pages, posts can also be marked as hidden with the Status: hidden attribute. Hidden posts will be output to ARTICLE_SAVE_AS as expected, but are not included by default in tag, category, and author indexes, nor in the main article feed. This has the effect of creating an "unlisted" post.

Skip Posts

Posts marked with skip status are ignored entirely. They are not processed nor output to the ARTICLE_SAVE_AS path. Such posts will similarly not be included in indexes or feeds.

Publish your site

Site generation

Once Pelican is installed and you have some content (e.g., in Markdown or reST format), you can convert your content into HTML via the pelican command, specifying the path to your content and (optionally) the path to your settings file:

pelican /path/to/your/content/ [-s path/to/your/settings.py]

The above command will generate your site and save it in the output/ folder, using the default theme to produce a simple site. The default theme consists of very simple HTML without styling and is provided so folks may use it as a basis for creating their own themes.

pelican --autoreload --listen

Pelican has other command-line switches available. Have a look at the help to see all the options you can use:

pelican --help

Viewing the generated files

The files generated by Pelican are static files, so you don't actually need anything special to view them. You can use your browser to open the generated HTML files directly:

firefox output/index.html

Deployment

After you have generated your site, previewed it in your local development environment, and are ready to deploy it to production, you might first re-generate your site with any production-specific settings (e.g., analytics, feeds, etc.) that you may have defined:

The first thing to understand is that there are currently two supported methods for URL formation: relative and absolute. Relative URLs are useful when testing locally, and absolute URLs are reliable and most useful when publishing. One method of supporting both is to have one Pelican configuration file for local development and another for publishing. To see an example of this type of setup, use the pelican-quickstart script as described in the Installation section, which will produce two separate configuration files for local development and publishing, respectively.

You can customize the URLs and locations where files will be saved. The *_URL and *_SAVE_AS variables use Python's format strings. These variables allow you to place your articles in a location such as {slug}/index.html and link to them as {slug} for clean URLs (see example below). These settings give you the flexibility to place your articles and pages anywhere you want.

NOTE:

If a *_SAVE_AS setting contains a parent directory that doesn't match the parent directory inside the corresponding *_URL setting, this may cause Pelican to generate unexpected URLs in a few cases, such as when using the {attach} syntax.

If you don't want that flexibility and instead prefer that your generated output paths mirror your source content's filesystem path hierarchy, try the following settings:

PATH_METADATA = '(?P<path_no_ext>.*)\..*'
ARTICLE_URL = ARTICLE_SAVE_AS = PAGE_URL = PAGE_SAVE_AS = '{path_no_ext}.html'

Otherwise, you can use a variety of file metadata attributes within URL-related settings:

  • slug
  • date
  • lang
  • author
  • category

Example usage:

ARTICLE_URL = 'posts/{date:%Y}/{date:%b}/{date:%d}/{slug}/'
ARTICLE_SAVE_AS = 'posts/{date:%Y}/{date:%b}/{date:%d}/{slug}/index.html'
PAGE_URL = 'pages/{slug}/'
PAGE_SAVE_AS = 'pages/{slug}/index.html'

This would save your articles into something like /posts/2011/Aug/07/sample-post/index.html, save your pages into /pages/about/index.html, and render them available at URLs of /posts/2011/Aug/07/sample-post/ and /pages/about/, respectively.

NOTE:

If you specify a datetime directive, it will be substituted using the input files' date metadata attribute. If the date is not specified for a particular file, Pelican will rely on the file's mtime timestamp. Check the Python datetime documentation for more information.

استخدام أنماط ترقيم الصفحات

افتراضيًا، يتم إنشاء الصفحات اللاحقة لـ .../foo.html كـ .../foo2.html، إلخ. يمكن استخدام الإعداد PAGINATION_PATTERNS لتغيير ذلك. يأخذ تسلسلاً من ثلاثيات، حيث تتكون كل ثلاثية من:

(minimum_page, page_url, page_save_as,)

بالنسبة لـ page_url و page_save_as، يمكنك استخدام عدد من المتغيرات. يقابل {url} و {save_as} قيم *_URL و *_SAVE_AS لنوع الصفحة المقابل (على سبيل المثال، ARTICLE_SAVE_AS). إذا كان {save_as} == foo/bar.html، فإن {name} == foo/bar و {extension} == .html. يساوي {base_name} {name} باستثناء أنه يزيل /index اللاحق إذا كان موجودًا. يساوي {number} رقم الصفحة.

على سبيل المثال، إذا كنت ترغب في ترك الصفحة الأولى دون تغيير، ولكن وضع الصفحات اللاحقة في .../page/2/ إلخ، يمكنك تعيين PAGINATION_PATTERNS على النحو التالي:

PAGINATION_PATTERNS = (
    (1, '{url}', '{save_as}'),
    (2, '{base_name}/page/{number}/', '{base_name}/page/{number}/index.html'),
)

إذا كنت ترغب في تطبيق نمط على الصفحة الأخيرة في القائمة، فاستخدم -1 كقيمة لـ minimum_page:

(-1, '{base_name}/last/', '{base_name}/last/index.html'),

Listing and Linking to Period Archives

The period_archives variable can be used to generate a list of links to the set of period archives that Pelican generates. As a common variable, it is available for use in any template, so you can implement such an index in a custom direct template, or in a sidebar visible across different site pages.

period_archives is a dict that may contain year, month, and/or day keys, depending on which *_ARCHIVE_SAVE_AS settings are enabled. The corresponding value is a list of dicts, where each dict in turn represents a time period (ordered according to the NEWEST_FIRST_ARCHIVES setting) with the following keys and values:

Key Value
period The same tuple as described in period_archives.html, e.g. (2023, 'June', 18).
period_num The same tuple as described in period_archives.html, e.g. (2023, 6, 18).
url The URL to the period archive page, e.g. posts/2023/06/18/. This is controlled by the corresponding *_ARCHIVE_URL setting.
save_as The path to the save location of the period archive page file, e.g. posts/2023/06/18/index.html. This is used internally by Pelican and is usually not relevant to themes.
articles A list of Article objects that fall under the time period.
dates Same list as articles, but ordered according to the NEWEST_FIRST_ARCHIVES setting.

Here is an example of how period_archives can be used in a template:

<ul>
{% for archive in period_archives.month %}
    <li>
        <a href="{{ SITEURL }}/{{ archive.url }}">
            {{ archive.period | reverse | join(' ') }} ({{ archive.articles|count }})
        </a>
    </li>
{% endfor %}
</ul>

You can change period_archives.month in the for statement to period_archives.year or period_archives.day as appropriate, depending on the time period granularity desired.

Inheritance

Since version 3.0, Pelican supports inheritance from the simple theme, so you can reuse the simple theme templates in your own themes.

If one of the mandatory files in the templates/ directory of your theme is missing, it will be replaced by the matching template from the simple theme. So if the HTML structure of a template in the simple theme is suitable for you, you don't have to write a new template from scratch.

You can also extend templates from the simple theme in your own themes by using the {% extends %} directive as in the following example:

{% extends "!simple/index.html" %}   <!-- extends the ``index.html`` template from the ``simple`` theme -->
{% extends "index.html" %}   <!-- "regular" extending -->

Example

With this system, it is possible to create a theme with just two files.

base.html

The first file is the templates/base.html template:

{% extends "!simple/base.html" %}
{% block head %}
{{ super() }}
   <link rel="stylesheet" type="text/css" href="{{ SITEURL }}/theme/css/style.css" />
{% endblock %}
1.
On the first line, we extend the base.html template from the simple theme, so we don't have to rewrite the entire file.
2.
On the third line, we open the head block which has already been defined in the simple theme.
3.
On the fourth line, the function super() keeps the content previously inserted in the head block.
4.
On the fifth line, we append a stylesheet to the page.
5.
On the last line, we close the head block.

This file will be extended by all the other templates, so the stylesheet will be linked from all pages.

style.css

The second file is the static/css/style.css CSS stylesheet:

    font-size : 100% ;

إنشاء روابط رمزية

يمكن لـ pelican-themes أيضًا تثبيت الثيمات عن طريق إنشاء روابط رمزية بدلاً من نسخ الثيمات بأكملها إلى مسار ثيمات Pelican.

لإنشاء رابط رمزي لثيم، يمكنك استخدام -s أو --symlink، والتي تعمل تمامًا مثل الخيار --install:

# pelican-themes --symlink ~/Dev/Python/pelican-themes/two-column

في هذا المثال، تم الآن ربط ثيم two-column رمزيًا بمسار ثيمات Pelican، لذا يمكننا استخدامه، ولكن يمكننا أيضًا تعديله دون الحاجة إلى إعادة تثبيته بعد كل تعديل.

هذا مفيد لتطوير الثيمات:

$ sudo pelican-themes -s ~/Dev/Python/pelican-themes/two-column
$ pelican ~/Blog/content -o /tmp/out -t two-column
$ firefox /tmp/out/index.html
$ vim ~/Dev/Pelican/pelican-themes/two-column/static/css/main.css
$ pelican ~/Blog/content -o /tmp/out -t two-column
$ cp /tmp/bg.png ~/Dev/Pelican/pelican-themes/two-column/static/img/bg.png
$ pelican ~/Blog/content -o /tmp/out -t two-column
$ vim ~/Dev/Pelican/pelican-themes/two-column/templates/index.html
$ pelican ~/Blog/content -o /tmp/out -t two-column

الخيارات --install و --remove و --symlink ليست حصرية، لذا يمكنك دمجها في نفس سطر الأوامر للقيام بأكثر من عملية واحدة في المرة الواحدة، مثل هذا:

# pelican-themes --remove notmyidea-cms two-column \

أسئلة متكررة (FAQ)

هنا بعض الأسئلة المتكررة حول Pelican.

ما هي أفضل طريقة للإبلاغ عن مشكلة أو سؤال أو اقتراح؟

يرجى قراءة إرشادات الملاحظات لدينا.

كيف يمكنني المساعدة؟

يمكنك أيضًا المساهمة عن طريق إنشاء سمات (themes) وتحسين التوثيق.

هل ملف إعدادات Pelican إلزامي؟

ملفات التكوين اختيارية وهي مجرد طريقة سهلة لتكوين Pelican. للعمليات الأساسية، من الممكن تحديد الخيارات عند استدعاء Pelican عبر سطر الأوامر. انظر pelican --help لمزيد من المعلومات.

التغييرات على ملف الإعدادات لا يكون لها تأثير

عند تجربة إعدادات مختلفة (خاصة تلك المتعلقة بالبيانات الوصفية)، قد يتداخل التخزين المؤقت (caching) وقد لا تكون التغييرات مرئية. في مثل هذه الحالات، تأكد من تعطيل التخزين المؤقت عبر LOAD_CONTENT_CACHE = False أو استخدم مفتاح سطر الأوامر --ignore-cache.

أقوم بإنشاء نسق خاص بي. كيف أستخدم Pygments لتظليل الشفرة؟

يمكنك استخدام أوامر المثال التالية لإنشاء ملف CSS ابتدائي من نمط Pygments مدمج (في هذه الحالة، "monokai") ثم نسخ ملف CSS الذي تم إنشاؤه إلى نسقك الجديد:

pygmentize -S monokai -f html -a .highlight > pygment.css
cp pygment.css path/to/theme/static/css/

لا تنسَ استيراد ملف pygment.css الخاص بك من ملف CSS الرئيسي.

كيف أقوم بإنشاء نسقي الخاص؟

يرجى الرجوع إلى السمات (Themes).

هل يمكنني تجاوز قوالب فردية دون عمل نسخة كاملة من النسق؟

نعم، يمكنك تجاوز القوالب الموجودة للنسق الذي تستخدمه، أو إضافة قوالب جديدة، عبر متغير THEME_TEMPLATES_OVERRIDES. على سبيل المثال، لتجاوز قالب الصفحة، يمكنك تحديد موقع القوالب الخاصة بك كالتالي:

THEME_TEMPLATES_OVERRIDES = ["templates"]

يمكنك بعد ذلك تحديد قالب مخصص في templates/page.html. انظر السمات (Themes) لمزيد من التفاصيل.

أريد استخدام Markdown، ولكنني تلقيت خطأ.

إذا حاولت إنشاء محتوى Markdown دون تثبيت مكتبة Markdown أولاً، فقد ترى رسالة تقول لم يتم العثور على ملفات صالحة في المحتوى. Markdown ليس تبعية أساسية لـ Pelican، لذلك إذا كان لديك محتوى بتنسيق Markdown، فستحتاج إلى تثبيت مكتبة Markdown بشكل صريح. يمكنك القيام بذلك عن طريق كتابة الأمر التالي، مع إضافة sudo في البداية إذا كانت الأذونات تتطلب ذلك:

python -m pip install markdown

هل يمكنني استخدام بيانات وصفية عشوائية في قوالبي؟

نعم. على سبيل المثال، لتضمين تاريخ معدل في مشاركة Markdown، يمكن للمرء تضمين ما يلي في أعلى المقال:

Modified: 2012-08-08

بالنسبة لـ reStructuredText، يجب أن تكون هذه البيانات الوصفية مسبوقة بنقطتين رأسيتين (:):

:Modified: 2012-08-08

يمكن الوصول إلى هذه البيانات الوصفية بعد ذلك في قوالب مثل article.html عبر:

{% if article.modified %}
Last modified: {{ article.modified }}
{% endif %}

إذا كنت ترغب في تضمين بيانات وصفية في قوالب خارج سياق المقال (على سبيل المثال، base.html)، فيجب أن تكون عبارة if كالتالي بدلاً من ذلك:

{% if article and article.modified %}

كيف أجعل بنية مجلد الإخراج متطابقة مع تسلسل هرمي للمحتوى؟

جرب هذه الإعدادات:

USE_FOLDER_AS_CATEGORY = False
PATH_METADATA = "(?P<path_no_ext>.*)\..*"
ARTICLE_URL = ARTICLE_SAVE_AS = PAGE_URL = PAGE_SAVE_AS = "{path_no_ext}.html"

كيف أقوم بتعيين قوالب مخصصة لكل صفحة على حدة؟

الأمر بسيط مثل إضافة سطر بيانات وصفية إضافي إلى أي صفحة أو مقال تريد أن يكون له قالب خاص به. على سبيل المثال، هذا هو كيفية التعامل مع المحتوى بتنسيق reST:

:template: template_name

بالنسبة للمحتوى بتنسيق Markdown:

Template: template_name

ثم تأكد فقط من أن نسقك يحتوي على ملف القالب ذي الصلة (مثل template_name.html). إذا كنت ترغب فقط في إضافة قالب مخصص جديد إلى نسق موجود، يمكنك أيضًا توفيره في دليل محدد بواسطة THEME_TEMPLATES_OVERRIDES (انظر السمات (Themes)).

كيف يمكنني تجاوز عنوان URL الذي تم إنشاؤه لصفحة أو مقال معين؟

قم بتضمين البيانات الوصفية url و save_as في أي صفحات أو مقالات تريد تجاوز عنوان URL الذي تم إنشاؤه لها. إليك مثال لصفحة بتنسيق reST:

Override url/save_as page
#########################
:url: override/url/
:save_as: override/url/index.html

باستخدام هذه البيانات الوصفية، سيتم كتابة الصفحة إلى override/url/index.html وسيستخدم Pelican عنوان URL override/url/ للربط بهذه الصفحة.

كيف يمكنني استخدام صفحة ثابتة كصفحة رئيسية لي؟

يمكن استخدام ميزة التجاوز المذكورة أعلاه لتحديد صفحة ثابتة كصفحة رئيسية لك. يمكن تخزين مثال Markdown التالي في content/pages/home.md:

Title: Welcome to My Site
URL:
save_as: index.html
Thank you for visiting. Welcome!

إذا كنت لا تزال تريد فهرس المدونة الأصلي، فيمكن حفظه في موقع مختلف عن طريق تعيين INDEX_SAVE_AS = 'blog_index.html' للقالب المباشر 'index'.

ماذا لو أردت تعطيل إنشاء الموجزات؟

لتعطيل إنشاء الموجزات، يجب تعيين جميع إعدادات الموجزات على None. جميع إعدادات الموجزات باستثناء ثلاثة افتراضيًا على None، لذلك إذا كنت ترغب في تعطيل جميع إنشاءات الموجزات، تحتاج فقط إلى تحديد الإعدادات التالية:

FEED_ALL_ATOM = None
CATEGORY_FEED_ATOM = None
TRANSLATION_FEED_ATOM = None
AUTHOR_FEED_ATOM = None
AUTHOR_FEED_RSS = None

يجب ألا تكون كلمة None محاطة بعلامات اقتباس. يرجى ملاحظة أن None و '' ليسا نفس الشيء.

لإصلاح ذلك، انتقل إلى إعدادات مستودع موقعك وقم بتمكين إعداد فرض HTTPS: انتقل إلى الإعدادات → الصفحات وحدد فرض HTTPS. ثم أعد تشغيل سير العمل لإعادة نشر موقعك. بدلاً من ذلك، يمكنك استخدام إعدادات siteurl و feed_domain في سير العمل.

صفحات 404 المخصصة

تحديث موقعك مع كل commit

لتحديث موقع Pelican الخاص بك تلقائيًا مع كل commit، يمكنك إنشاء خطاف ما بعد commit (post-commit hook). على سبيل المثال، يمكنك إضافة ما يلي إلى .git/hooks/post-commit:

STATIC_PATHS = ['images', 'extra/CNAME']
EXTRA_PATH_METADATA = {'extra/CNAME': {'path': 'CNAME'},}

ملاحظة: استخدم الشرطات المائلة للأمام، /، حتى على نظام Windows.

يمكنك أيضًا استخدام آلية EXTRA_PATH_METADATA لوضع ملف favicon.ico أو robots.txt في جذر أي موقع.

كيفية إضافة مقاطع فيديو YouTube أو Vimeo

أسهل طريقة هي لصق رمز التضمين (embed code) للفيديو من هذه المواقع مباشرة في محتوى المصدر الخاص بك.

بدلاً من ذلك، يمكنك أيضًا استخدام إضافات Pelican مثل liquid_tags أو pelican_youtube أو pelican_vimeo لتضمين مقاطع الفيديو في المحتوى الخاص بك.

التطوير محليًا باستخدام SSL

إليك كيفية إعداد خادم Pelican المحلي الخاص بك لدعم SSL.

أولاً، قم بإنشاء شهادة موقعة ذاتيًا ومفتاح باستخدام openssl (ينشئ هذا cert.pem و key.pem):

$ openssl req -x509 -newkey rsa:4096 -keyout key.pem -out cert.pem -days 365 -nodes

واستخدم هذا الأمر لتشغيل الخادم (يبدأ الخادم داخل الدليل output الخاص بك):

python -m pelican.server 8443 --key=../key.pem --cert=../cert.pem

إذا كنت تستخدم develop-server.sh، أضف هذا في الأعلى:

CERT="$BASEDIR/cert.pem"
KEY="$BASEDIR/key.pem"

لا تتردد في عمل fork لـ Pelican وتقديم مشكلة أو طلب سحب على GitHub. عند القيام بذلك، يرجى مراعاة الإرشادات التالية.

تقديم المشكلات

  • قبل تقديم مشكلة جديدة، حاول طلب المساعدة أولاً.
  • إذا قررت إنشاء مشكلة جديدة، فابحث أولاً في مناقشات Pelican و المشكلات الحالية (المفتوحة والمغلقة) لمعرفة ما إذا كان سؤالك قد تمت الإجابة عليه مسبقًا.

كيفية الحصول على المساعدة

قبل أن تطلب المساعدة، يرجى التأكد من قيامك بما يلي:

1.
اقرأ الوثائق بشكل شامل. إذا كنت في عجلة من أمرك، فاستخدم على الأقل حقل البحث المتوفر في أعلى اليسار في صفحات الوثائق. تأكد من قراءة الوثائق الخاصة بإصدار Pelican الذي تستخدمه.
2.
استخدم محرك بحث (مثل DuckDuckGo، Google) للبحث عن حل لمشكلتك. قد يكون شخص ما قد وجد حلاً بالفعل، ربما في شكل 'إضافات' أو مجموعة محددة من الإعدادات.
3.
حاول إعادة إنتاج المشكلة في بيئة نظيفة، مع التأكد من أنك تستخدم:
  • أحدث إصدار من Pelican (أو نسخة Git محدثة من الفرع الرئيسي main لـ Pelican)
  • أحدث إصدارات المكتبات التي تستخدمها Pelican
  • لا توجد إضافات أو فقط تلك المتعلقة بالمشكلة

ملاحظة: المصادر الأكثر شيوعًا للمشاكل هي حالات شاذة في (1) السمات، (2) الإضافات، (3) ملفات الإعدادات، و (4) مغلفات الأتمتة make/invoke. إذا لم تتمكن من إعادة إنتاج مشكلتك عند استخدام الخطوات التالية لإنشاء موقعك، فإن المشكلة بالتأكيد تتعلق بأحد العناصر المذكورة أعلاه (وليس Pelican نفسه):

cd ~/projects/your-site
