PERLVMS(1perl) Perl Programmers Reference Guide PERLVMS(1perl)

NAME

perlvms - VMS-specific documentation for Perl

DESCRIPTION

Gathered below are notes describing details of Perl 5's behavior on VMS. They are a supplement to the regular Perl 5 documentation, so we have focussed on the ways in which Perl 5 functions differently under VMS than it does under Unix, and on the interactions between Perl and the rest of the operating system. We haven't tried to duplicate complete descriptions of Perl features from the main Perl documentation, which can be found in the [.pod] subdirectory of the Perl distribution.

We hope these notes will save you from confusion and lost sleep when writing Perl scripts on VMS. If you find we've missed something you think should appear here, please don't hesitate to drop a line to vmsperl@perl.org.

Installation

Directions for building and installing Perl 5 can be found in the file README.vms in the main source directory of the Perl distribution.

Organization of Perl Images

Core Images

During the build process, three Perl images are produced. Miniperl.Exe is an executable image which contains all of the basic functionality of Perl, but cannot take advantage of Perl XS extensions and has a hard-wired list of library locations for loading pure-Perl modules. It is used extensively to build and test Perl and various extensions, but is not installed.

Most of the complete Perl resides in the shareable image PerlShr.Exe, which provides a core to which the Perl executable image and all Perl extensions are linked. It is generally located via the logical name PERLSHR. While it's possible to put the image in SYS$SHARE to make it loadable, that's not recommended. And while you may wish to INSTALL the image for performance reasons, you should not install it with privileges; if you do, the result will not be what you expect as image privileges are disabled during Perl start-up.

Finally, Perl.Exe is an executable image containing the main entry point for Perl, as well as some initialization code. It should be placed in a public directory, and made world executable. In order to run Perl with command line arguments, you should define a foreign command to invoke this image.

Perl Extensions

Perl extensions are packages which provide both XS and Perl code to add new functionality to perl. (XS is a meta-language which simplifies writing C code which interacts with Perl, see perlxs for more details.) The Perl code for an extension is treated like any other library module - it's made available in your script through the appropriate "use" or "require" statement, and usually defines a Perl package containing the extension.

The portion of the extension provided by the XS code may be connected to the rest of Perl in either of two ways. In the static configuration, the object code for the extension is linked directly into PerlShr.Exe, and is initialized whenever Perl is invoked. In the dynamic configuration, the extension's machine code is placed into a separate shareable image, which is mapped by Perl's DynaLoader when the extension is "use"d or "require"d in your script. This allows you to maintain the extension as a separate entity, at the cost of keeping track of the additional shareable image. Most extensions can be set up as either static or dynamic.

The source code for an extension usually resides in its own directory. At least three files are generally provided: Extshortname.xs (where Extshortname is the portion of the extension's name following the last "::"), containing the XS code, Extshortname.pm, the Perl library module for the extension, and Makefile.PL, a Perl script which uses the "MakeMaker" library modules supplied with Perl to generate a Descrip.MMS file for the extension.

Installing static extensions

Since static extensions are incorporated directly into PerlShr.Exe, you'll have to rebuild Perl to incorporate a new extension. You should edit the main Descrip.MMS or Makefile you use to build Perl, adding the extension's name to the "ext" macro, and the extension's object file to the "extobj" macro. You'll also need to build the extension's object file, either by adding dependencies to the main Descrip.MMS, or using a separate Descrip.MMS for the extension. Then, rebuild PerlShr.Exe to incorporate the new code.

Finally, you'll need to copy the extension's Perl library module to the [.Extname] subdirectory under one of the directories in @INC, where Extname is the name of the extension, with all "::" replaced by "." (e.g. the library module for extension Foo::Bar would be copied to a [.Foo.Bar] subdirectory).

Installing dynamic extensions

In general, the distributed kit for a Perl extension includes a file named Makefile.PL, which is a Perl program which is used to create a Descrip.MMS file which can be used to build and install the files required by the extension. The kit should be unpacked into a directory tree not under the main Perl source directory, and the procedure for building the extension is simply

$ perl Makefile.PL  ! Create Descrip.MMS
$ mmk               ! Build necessary files
$ mmk test          ! Run test code, if supplied
$ mmk install       ! Install into public Perl tree

VMS support for this process in the current release of Perl is sufficient to handle most extensions. (See the MakeMaker documentation for more details on installation options for extensions.)

  • the [.Lib.Auto.Arch$PVersExtname] subdirectory of one of the directories in @INC (where PVers is the version of Perl you're using, as supplied in $], with '.' converted to '_'), or
  • one of the directories in @INC, or
  • a directory which the extensions Perl library module passes to the DynaLoader when asking it to map the shareable image, or
  • Sys$Share or Sys$Library.

If the shareable image isn't in any of these places, you'll need to define a logical name Extshortname, where Extshortname is the portion of the extension's name after the last "::", which translates to the full file specification of the shareable image.

File specifications

Syntax

We have tried to make Perl aware of both VMS-style and Unix-style file specifications wherever possible. You may use either style, or both, on the command line and in scripts, but you may not combine the two styles within a single file specification. VMS Perl interprets Unix pathnames in much the same way as the CRTL (e.g. the first component of an absolute path is read as the device name for the VMS file specification). There are a set of functions provided in the "VMS::Filespec" package for explicit interconversion between VMS and Unix syntax; its documentation provides more details.

We've tried to minimize the dependence of Perl library modules on Unix syntax, but you may find that some of these, as well as some scripts written for Unix systems, will require that you use Unix syntax, since they will assume that '/' is the directory separator, etc. If you find instances of this in the Perl distribution itself, please let us know, so we can try to work around them.

سطر الأوامر

إعادة توجيه الإدخال/الإخراج والتشغيل في الخلفية

يدعم Perl لنظام VMS إعادة توجيه الإدخال والإخراج على سطر الأوامر، باستخدام مجموعة فرعية من صيغة Bourne shell:

  • "<file" يقرأ stdin من "file"،
  • ">file" يكتب stdout إلى "file"،
  • ">>file" يلحق stdout بـ "file"،
  • "2>file" يكتب stderr إلى "file"،
  • "2>>file" يلحق stderr بـ "file"، و
  • "2>&1" يعيد توجيه stderr إلى stdout.

بالإضافة إلى ذلك، يمكن توجيه الإخراج إلى عملية فرعية، باستخدام الرمز '|'. يتم تمرير كل شيء بعد هذا الرمز على سطر الأوامر إلى عملية فرعية للتنفيذ؛ تأخذ العملية الفرعية مخرجات Perl كمدخلاتها.

أخيرًا، إذا انتهى سطر الأوامر بـ '&'، يتم تشغيل الأمر بأكمله في الخلفية كعملية فرعية غير متزامنة.

مفاتيح سطر الأوامر

تتصرف مفاتيح سطر الأوامر التالية بشكل مختلف تحت VMS مقارنة بما هو موصوف في perlrun. لاحظ أيضًا أنه لتمرير المفاتيح ذات الأحرف الكبيرة إلى Perl، تحتاج إلى وضعها بين علامتي اقتباس مزدوجتين على سطر الأوامر، لأن CRTL يحول جميع السلاسل النصية غير المقتبسة إلى أحرف صغيرة.

في الإصدارات الأحدث ذات 64 بت من OpenVMS، يتحكم إعداد عملية الآن فيما إذا كان الاقتباس مطلوبًا للحفاظ على حالة وسائط سطر الأوامر.

-i
إذا كان المفتاح "-i" موجودًا ولكن لم يتم إعطاء امتداد لنسخة احتياطية، فإن تحرير المكان ينشئ إصدارًا جديدًا من الملف؛ لا يتم حذف النسخة الموجودة. (لاحظ أنه إذا تم تقديم امتداد، فسيتم إعادة تسمية ملف موجود إلى الملف الاحتياطي، كما هو الحال تحت أنظمة التشغيل الأخرى، لذلك لا يبقى كإصدار سابق تحت اسم الملف الأصلي.)
-S
إذا كان المفتاح "-S" أو "-"S"" موجودًا و لم يكن اسم البرنامج النصي يحتوي على دليل، فإن Perl يترجم الاسم المنطقي DCL$PATH كقائمة بحث، باستخدام كل ترجمة كدليل للبحث فيه عن البرنامج النصي. بالإضافة إلى ذلك، إذا لم يتم تحديد نوع ملف، فإن Perl يبحث في كل دليل عن ملف مطابق للاسم المحدد، بنوع فارغ، ونوع .pl، ونوع .com، بهذا الترتيب.
-u
المفتاح "-u" يتسبب في استدعاء مصحح VMS بعد تجميع برنامج Perl، ولكن قبل تشغيله. لا يقوم بإنشاء ملف تفريغ أساسي.

اختبارات الملفات
تعمل الاختبارات "-b"، "-B"، "-c"، "-C"، "-d"، "-e"، "-f"، "-o"، "-M"، "-s"، "-S"، "-t"، "-T"، و "-z" كما هو معلن. قيم الإرجاع لـ "-r"، "-w"، و "-x" تخبرك بما إذا كان يمكنك فعليًا الوصول إلى الملف؛ قد لا يعكس هذا حماية الملفات المستندة إلى UIC. نظرًا لأن UIC الحقيقي والفعال لا يختلفان تحت VMS، فإن "-O"، "-R"، "-W"، و "-X" تعادل "-o"، "-r"، "-w"، و "-x". وبالمثل، العديد من الاختبارات الأخرى، بما في ذلك "-A"، "-g"، "-k"، "-l"، "-p"، و "-u"، ليست ذات مغزى خاص تحت VMS، والقيم التي يتم إرجاعها بواسطة هذه الاختبارات تعكس ما يفعله روتين stat() الخاص بـ CRTL الخاص بك مع البتات المكافئة في حقل st_mode. أخيرًا، ترجع "-d" قيمة صحيحة إذا تم تمرير مواصفات جهاز بدون دليل صريح (على سبيل المثال "DUA1:")، وكذلك إذا تم تمرير دليل.

هناك أسماء منطقية لميزات DECC وسمات حجم ODS-5 تتحكم أيضًا في القيم التي يتم إرجاعها لحقول التاريخ.

ملاحظة: أبلغت بعض المواقع عن مشاكل عند استخدام اختبارات الوصول إلى الملفات ( "-r"، "-w"، و "-x") على الملفات التي تم الوصول إليها عبر DFS الخاص بـ DEC. على وجه التحديد، نظرًا لأن DFS لا يوفر حاليًا وصولاً إلى رأس الملف الموسع للملفات الموجودة على وحدات تخزين بعيدة، فإن محاولات فحص ACL تفشل، وسترجع اختبارات الملفات قيمة خاطئة، مع $! يشير إلى أن الملف غير موجود. يمكنك استخدام "stat" على هذه الملفات، حيث إنها تتحقق فقط من الحماية المستندة إلى UIC، ثم تتحقق يدويًا من البتات المناسبة، كما هو محدد بواسطة stat.h الخاص بمترجم C الخاص بك، في قيمة الوضع التي ترجعها، إذا كنت بحاجة إلى تقريب لحمايات الملف.

علامات الاقتباس المائلة
تنشئ علامات الاقتباس المائلة عملية فرعية، وتمرر السلسلة النصية المغلقة إليها لتنفيذها كأمر DCL. نظرًا لأن العملية الفرعية يتم إنشاؤها مباشرة عبر "lib$spawn()"، يمكن تحديد أي سلسلة أوامر DCL صالحة.
binmode FILEHANDLE
سيحاول المعامل "binmode" التأكد من عدم حدوث أي ترجمة لرقابة التحكم عند الإدخال من أو الإخراج إلى مقبض الملف هذا. نظرًا لأن هذا يتضمن إعادة فتح الملف ثم استعادة مؤشر موضع الملف الخاص به، إذا كانت هذه الوظيفة r
returns FALSE, the underlying filehandle may no longer point to an open file, or may point to a different position in the file than before "binmode" was called.

Note that "binmode" is generally not necessary when using normal filehandles; it is provided so that you can control I/O to existing record-structured files when necessary. You can also use the "vmsfopen" function in the VMS::Stdio extension to gain finer control of I/O to files and devices with different record structures.

crypt PLAINTEXT, USER
يستخدم المعامل "crypt" خدمة النظام "sys$hash_password" لتوليد التمثيل المجزأ لـ PLAINTEXT. إذا كان USER اسم مستخدم صالحًا، فسيتم أخذ الخوارزمية وقيم الملح من سجل UAF الخاص بذلك المستخدم. إذا لم يكن الأمر كذلك، فسيتم استخدام الخوارزمية المفضلة والملح 0. يتم إرجاع القيمة المشفرة رباعية البايت كسلسلة من 8 أحرف.

يمكن مقارنة القيمة التي تم إرجاعها بواسطة "crypt" مع كلمة المرور المشفرة من UAF التي تم إرجاعها بواسطة دوال "getpw*"، وذلك للمصادقة على المستخدمين. إذا كنت ستفعل ذلك، فتذكر أن كلمة المرور المشفرة في UAF تم إنشاؤها باستخدام أسماء المستخدمين وكلمات المرور بالأحرف الكبيرة؛ ستحتاج إلى تحويل وسيطات "crypt" إلى أحرف كبيرة لضمان حصولك على القيمة الصحيحة:

sub validate_passwd {
    my($user,$passwd) = @_;
    my($pwdhash);
    if ( !($pwdhash = (getpwnam($user))[1]) ||
           $pwdhash ne crypt("\U$passwd","\U$name") ) {
        intruder_alert($name);
    }
    return 1;
}
die
سيؤدي "die" إلى فرض حالة خروج VMS الأصلية لتكون رمز SS$_ABORT إذا لم تكن أي من قيم الحالة $! أو $؟ من القيم التي ستتسبب في تفسير الحالة الأصلية على أنها ما تصنفه VMS على أنه خطأ جسيم (SEVERE_ERROR) لمعالجة أخطاء DCL.

عندما يكون "PERL_VMS_POSIX_EXIT" نشطًا (انظر "$?" أدناه)، سيحتوي على قيمة حالة خروج VMS الأصلية إما على إحدى قيم $! أو $؟ أو $^E أو قيمة Unix 255 مشفرة بطريقة يمكن بها فك تشفير القيمة الأصلية الفعالة بواسطة برامج أخرى مكتوبة بلغة C، بما في ذلك Perl وحزمة GNV. كما هو الحال مع السلوك الطبيعي لـ "die" خارج VMS، إذا كانت $! أو $؟ غير صفر، فسيتم تشفير إحدى هذه القيم في قيمة حالة خروج VMS أصلية. إذا كانت قيمتا Unix للحالة كلاهما 0، وكانت قيمة $^E مضبوطة على إحدى درجات خطورة ERROR أو SEVERE_ERROR، فسيتم استخدام قيمة $^E كرمز خروج كما هي. إذا لم ينطبق أي مما سبق، فسيتم تشفير قيمة Unix 255 في قيمة حالة خروج VMS أصلية.

يرجى ملاحظة فرق مهم في سلوك "die" في وضع "PERL_VMS_POSIX_EXIT" وهو أنه لا يفرض حالة خطأ جسيم (SEVERE_ERROR) في VMS عند الخروج. سيتم تشفير قيم خروج Unix من 2 إلى 255 في قيم حالة VMS بدرجات خطورة نجاح (SUCCESS). سيتم تشفير قيمة خروج Unix 1 في قيمة حالة VMS بدرجة خطورة خطأ (ERROR). هذا ليكون متوافقًا مع كيفية قيام مكتبة VMS C بتشفير هذه القيم.

قد يتم تغيير الحد الأدنى لدرجة الخطورة التي يحددها "die" في وضع "PERL_VMS_POSIX_EXIT" إلى ERROR أو أعلى في المستقبل اعتمادًا على نتائج الاختبار والمراجعة الإضافية.

انظر "$?" لوصف تشفير قيمة Unix لإنتاج حالة VMS أصلية تحتوي عليها.

dump
بدلاً من التسبب في تعطل Perl وتفريغ الذاكرة، يقوم المعامل "dump" باستدعاء مصحح أخطاء VMS. إذا واصلت تنفيذ برنامج Perl تحت مصحح الأخطاء، فسيتم نقل التحكم إلى التسمية المحددة كوسيط للمعامل "dump"، أو إذا لم يتم تحديد تسمية، فسيتم العودة إلى بداية البرنامج. لا تتأثر جميع حالات البرنامج الأخرى (مثل قيم المتغيرات، مقابض الملفات المفتوحة) باستدعاء "dump".
exec LIST
سيؤدي استدعاء "exec" إلى إنهاء Perl، واستدعاء الأمر المحدد كوسيط لـ "exec" عبر "lib$do_command". إذا بدأ الوسيط بـ '@' أو '$' (بخلاف كونه جزءًا من مواصفات الملف)، فسيتم تنفيذه كأمر DCL. خلاف ذلك، يتم معاملة الرمز الأول في سطر الأوامر كمواصفات ملف لصورة ليتم تشغيلها، ويتم محاولة استدعائها (باستخدام .Exe والافتراضات العملية لتوسيع مواصفات الملف) وتمرير بقية وسيطات "exec" إليها كمعلمات. إذا لم يكن للرمز نوع ملف، وتطابق مع ملف بنوع فارغ، فسيتم محاولة تحديد ما إذا كان الملف عبارة عن صورة قابلة للتنفيذ يجب استدعاؤها باستخدام "MCR" أو ملف نصي يجب تمريره إلى DCL كإجراء أوامر.
fork
بينما من حيث المبدأ يمكن تنفيذ المعامل "fork" عبر (وبنفس القيود الصارمة) روتين CRTL vfork()، وبينما يوجد دعم داخلي للقيام بذلك، لم يكتمل التنفيذ، مما يجعل "fork" غير متاح حاليًا. من المتوقع أن تظهر وظيفة fork() حقيقية في نواة النظام في إصدار مستقبلي من VMS، وقد تكون الوظيفة الوهمية القائمة على خيوط المفسر متاحة في إصدار مستقبلي من Perl على VMS (انظر perlfork). في غضون ذلك، استخدم "system"، أو علامات الاقتباس المزدوجة، أو مقابض الملفات المقسمة لإنشاء عمليات فرعية.
getpwent
getpwnam
getpwuid
تحصل هذه المعاملات على المعلومات الموضحة في perlfunc، إذا كانت لديك الامتيازات اللازمة لاسترداد معلومات UAF للمستخدم المحدد عبر "sys$getuai". إذا لم يكن الأمر كذلك، فسيتم إرجاع عناصر $name و $uid و $gid فقط. يحتوي العنصر $dir على دليل تسجيل الدخول بصيغة VMS، بينما يحتوي العنصر $comment على دليل تسجيل الدخول بصيغة Unix. يحتوي العنصر $gcos على حقل المالك من سجل UAF. لا يتم استخدام العنصر $quota.

(يتم تعريف هذا الاسم المنطقي تلقائيًا إذا كنت تشغل إصدارًا من VMS يدعم التوقيت العالمي المنسق). إذا لم ينطبق أي من هاتين الحالتين، فستتم طباعة رسالة تحذير، وسيتم إرجاع "undef".
kill
في معظم الحالات، يتم تنفيذ "kill" عبر خدمة النظام غير الموثقة $SIGPRC، والتي لها نفس تسلسل الاستدعاء الخاص بـ $FORCEX، ولكنها تثير استثناءً في العملية المستهدفة بدلاً من إجبارها على استدعاء $EXIT. بشكل عام، يتبع "kill" سلوك دالة CRTL kill()، ولكن على عكس تلك الدالة يمكن استدعاؤها من داخل معالج الإشارة. أيضًا، على عكس "kill" في بعض إصدارات CRTL، تتحقق "kill" في Perl من صحة الإشارة المقدمة وترجع خطأ بدلاً من محاولة إرسال إشارة غير معروفة.

أيضًا، لا تقوم قيم الإشارة السالبة بأي شيء خاص تحت VMS؛ يتم تحويلها ببساطة إلى القيمة الموجبة المقابلة.

Perl builtins

system LIST
The "system" function provides a way to execute a command outside of the current Perl process. The LIST is passed to the appropriate interpreter for execution.
  • If the LIST is a single scalar argument, it is interpreted as a command string.
  • If the LIST is a list of arguments, the first argument is the command, and the rest are its arguments.

On VMS, the command is first interpreted by DCL. If the command does not contain any file-type specifiers (e.g., `.com`, `.exe`, `.vms`), and a file with the same name exists but without a type, Perl attempts to determine if the file is an executable image to be invoked using "MCR" or a text file to be passed to DCL as a command procedure.

If LIST is an empty string, "system" spawns an interactive DCL subprocess, similar to typing SPAWN at the DCL prompt.

Perl waits for the subprocess to complete before continuing execution in the current process. The return value of "system" is a status code. By default, this follows POSIX semantics. However, if the pragma "use vmsish 'status'" is in effect, the return value follows VMS conventions. Refer to the description of $? in this document for more details.

time
The "time" function returns the current time as the number of seconds elapsed since 01-JAN-1970 00:00:00. This convention is adopted from the CRTL's times() routine to facilitate compatibility with POSIX/Unix code.
times
The "times" operator returns an array representing process times, structured according to the CRTL times() routine. On VMS, the distinction between "user time" and "system time" is not made, so the "system time" elements in the returned array will always be 0. The "child time" field may or may not reflect time accumulated by subprocesses, depending on whether the CRTL times() routine tracks subprocesses separately. Note that the VAXCRTL (and potentially other versions) only tracks times for subprocesses spawned using fork() and exec(). It does not accumulate times for subprocesses spawned via pipes, system(), or backticks.
unlink LIST
"unlink" deletes the highest version of a file. To delete all versions of a file, use the following construct: 
1 while unlink LIST;

This behavior might require adjustments to scripts originally written for Unix systems, which typically expect "unlink" to remove all files matching the given names.

Note: This behavior can be altered at compile time. If you use "use Config" and $Config{'d_unlink_all_versions'} is defined (e.g., set to "define"), then "unlink" will delete all versions of a file on the first call.

"unlink" attempts to delete files even if it requires changing file protection, but it will not modify the protection of the parent directory. You can check for explicit delete access using the "VMS::Filespec::candelete" operator. For example, to delete only files to which you have delete access:

sub safe_unlink {
    my($file,$num);
    foreach $file (@_) {
        next unless VMS::Filespec::candelete($file);
        $num += unlink $file;
    }
    $num;
}

Alternatively, if the VMS::Stdio extension is installed, you can use "VMS::Stdio::remove".

If "unlink" needs to change file protection to delete a file and is interrupted, the file might remain unchanged but with modified ACLs granting delete access.

This "unlink" behavior is intended to align with POSIX standards, differing from traditional VMS behavior.

utime LIST
On ODS-2 volumes and ODS-5 volumes without access dates enabled, this operator modifies only the file's modification time (VMS revision date). On ODS-5 volumes with access dates enabled, it modifies the true access time.
waitpid PID,FLAGS
If PID refers to a subprocess initiated by a piped open() (see open), "waitpid" will wait for that subprocess to terminate and return its final status in $?. If PID refers to a subprocess created by other means (e.g., spawned before Perl was invoked), "waitpid" will periodically check (once per second) for the process's completion and return when it has. A warning will be issued if PID specifies a process not belonging to the current process hierarchy and the Perl script is run with the "-w" switch.

The function returns the PID on success and -1 on error. The FLAGS argument is ignored in all cases.

Perl variables

The following VMS-specific information supplements the general descriptions in perlvar for certain "special" Perl variables. This information takes precedence in case of conflict.

%ENV
The behavior of the %ENV array is governed by the translation of the logical name PERL_ENV_TABLES. If defined, it must be a search list, where each element specifies a location for %ENV elements. When Perl reads or sets an element like "$ENV{"name"}", it uses the translations of PERL_ENV_TABLES as follows:
CRTL_ENV
If an element translates to "CRTL_ENV", Perl consults the CRTL's internal "environ" array of key-value pairs, using name as the key. This array usually contains few entries, but if Perl was invoked using the C "exec[lv]e()" function (as might occur in embedded Perl applications or when running under shells like GNV bash), the calling program might have populated the "environ" array.
CLISYM_[LOCAL]
A string starting with "CLISYM_" directs Perl to consult the CLI's symbol tables, using name as the symbol name. When reading an element of %ENV, the local symbol table is checked first, followed by the global symbol table. The characters following "CLISYM_" determine whether setting or deleting an element of %ENV affects the local or global symbol table. If the string is exactly "CLISYM_LOCAL", the change is made in the local symbol table; otherwise, the global symbol table is modified.
Any other string
If an element of PERL_ENV_TABLES translates to any other string, that string is treated as the name of a logical name table. Perl then consults this table using name as the logical name, following the normal search order for access modes.

PERL_ENV_TABLES is translated once when Perl starts. Subsequent changes to it during runtime do not affect %ENV's behavior. If PERL_ENV_TABLES is undefined, Perl defaults to consulting the logical name tables specified by LNM$FILE_DEV first, and then the CRTL "environ" array. This default order is reversed if the logical name GNV$UNIX_SHELL is defined (e.g., when running under GNV bash).

For operations involving logical names or DCL symbols, the key string is treated as uppercase, irrespective of its case in the Perl expression. Conversely, entries in %ENV based on the CRTL's environ array preserve the case of the key string, and lookups are case-sensitive.

When an element of %ENV is read, Perl checks the locations specified by PERL_ENV_TABLES in order and returns the value from the first successful lookup. If the name contains a semicolon, that semicolon and any subsequent characters are disregarded when consulting the CRTL "environ" array or a CLI symbol table. However, when looking up in a logical name table, the suffix after the semicolon is used as the translation index. This allows for looking up successive values in search list logical names. For example:

$  Define STORY  once,upon,a,time,there,was
$  perl -e "for ($i = 0; $i <= 6; $i++) " -
_$ -e "{ print $ENV{'story;'.$i},' '}"

This script will output "ONCE UPON A TIME THERE WAS", assuming PERL_ENV_TABLES is configured such that the logical name "story" is found, rather than a CLI symbol or CRTL "environ" element with the same name.

When an element of %ENV is assigned a defined string value, the definition is made in the location pointed to by the first translation of PERL_ENV_TABLES. If this creates a logical name, it is defined in supervisor mode. Existing logical names defined in executive or kernel mode are reset to the new value; user or supervisor mode logical names are updated. Assigning an empty string results in the logical name's translation being set to a single "NUL" (ASCII "\0") character, as logical names cannot translate to zero-length strings. This restriction does not apply to CLI symbols or CRTL "environ" values, which are set to the empty string.

تأثير مماثل، ولكن بعد حذف العنصر، تتم محاولة أخرى للبحث عن العنصر، لذلك سيحل اسم منطقي في وضع داخلي أو اسم في موقع آخر محل الاسم المنطقي الذي تم حذفه للتو. في كلتا الحالتين، فقط القيمة الأولى التي تم العثور عليها يتم تغيير البحث عن PERL_ENV_TABLES. لا يمكن حاليًا تحديد اسم منطقي لقائمة بحث عبر %ENV.

العنصر $ENV{DEFAULT} مميز: عند قراءته، يعود بالجهاز والدليل الافتراضي الحالي لـ Perl، وعندما يتم تعيينه، يعيد ضبطهما، بغض النظر عن تعريف PERL_ENV_TABLES. لا يمكن مسحه أو حذفه؛ يتم تجاهل المحاولات للقيام بذلك بصمت.

لاحظ أنه إذا كنت ترغب في تمرير أي عناصر من مصفوفة البيئة المحلية C إلى عملية فرعية لا تبدأ بواسطة fork/exec، أو لا تقوم بتشغيل برنامج C، يمكنك "ترقيتها" إلى أسماء منطقية في العملية الحالية، والتي سيتم بعد ذلك وراثتها من قبل جميع العمليات الفرعية، بالقول

foreach my $key (qw[C-local keys you want promoted]) {
    my $temp = $ENV{$key}; # read from C-local array
    $ENV{$key} = $temp;    # and define as logical name
}

(لا يمكنك فقط قول "$ENV{$key} = $ENV{$key}"، لأن محسن Perl ذكي بما يكفي لتخطي التعبير.)

لا تحاول مسح %ENV بقول "%ENV = ();"، سيؤدي ذلك إلى خطأ فادح. هذا يعادل القيام بما يلي من DCL:

DELETE/LOGICAL *

يمكنك تخيل مدى سوء الأمور إذا، على سبيل المثال، تم حذف الأسماء المنطقية SYS$MANAGER أو SYS$SYSTEM.

في الوقت الحالي، في المرة الأولى التي تتكرر فيها فوق %ENV باستخدام "keys"، أو "values"، ستتحمل عقوبة زمنية حيث تتم قراءة جميع الأسماء المنطقية، من أجل ملء %ENV بالكامل. التكرارات اللاحقة لن تعيد قراءة الأسماء المنطقية، لذلك لن تكون بطيئة بنفس القدر، ولكنها أيضًا لن تعكس أي تغييرات في جداول الأسماء المنطقية التي تسببها البرامج الأخرى.

تحتاج إلى توخي الحذر مع الأسماء المنطقية التي تمثل ملفات دائمة للعملية، مثل "SYS$INPUT" و "SYS$OUTPUT". تمت إضافة الترجمات لهذه الأسماء المنطقية مسبقًا بقيمة ثنائية من بايتين (0x1B 0x00) تحتاج إلى إزالتها إذا كنت ترغب في استخدامها. (في الإصدارات السابقة من Perl لم يكن من الممكن الحصول على قيم هذه الأسماء المنطقية، حيث كان البايت الصفري يعمل كعلامة نهاية السلسلة)

$!
القيمة النصية لـ $! هي تلك التي تم إرجاعها بواسطة دالة strerror() الخاصة بـ CRTL، لذلك ستشمل رسالة VMS للأخطاء الخاصة بـ VMS. القيمة الرقمية لـ $! هي قيمة "errno"، باستثناء إذا كان errno هو EVMSERR، في هذه الحالة يحتوي $! على قيمة vaxc$errno. تعيين $! يقوم دائمًا بتعيين errno إلى القيمة المحددة. إذا كانت هذه القيمة EVMSERR، فإنها تقوم أيضًا بتعيين vaxc$errno إلى 4 (NONAME-F-NOMSG)، بحيث لا تعكس القيمة النصية لـ $! رسالة خطأ VMS قبل تعيين $!.
$^E
يوفر هذا المتغير وصولاً مباشرًا إلى قيم حالة VMS في vaxc$errno، والتي غالبًا ما تكون أكثر تحديدًا من رسائل الخطأ العامة ذات النمط Unix في $!. قيمته الرقمية هي قيمة vaxc$errno، وقيمته النصية هي سلسلة رسالة VMS المقابلة، كما تم استردادها بواسطة sys$getmsg(). تعيين $^E يقوم بتعيين vaxc$errno إلى القيمة المحددة.

بينما يحاول Perl الحفاظ على قيمة vaxc$errno لتكون حديثة، إذا لم يكن errno هو EVMSERR، فقد لا يكون من العملية الحالية.

$?
قيمة "الحالة" التي تم إرجاعها في $? هي مصطنعة من حالة الخروج الفعلية للعملية الفرعية بطريقة تقارب دلالات POSIX wait(5)، من أجل السماح لبرامج Perl باختبار اكتمال العمليات الفرعية بنجاح بشكل محمول. الـ 8 بتات الأدنى من $? هي دائمًا 0 تحت VMS، نظرًا لأن حالة إنهاء العملية قد تكون أو لا تكون ناتجة عن استثناء.

الـ 8 بتات التالية تحتوي على حالة إنهاء البرنامج.

إذا اتبعت العملية الفرعية اصطلاح برامج C المترجمة مع تعيين الماكرو _POSIX_EXIT، فإن قيمة الحالة ستحتوي على القيمة الفعلية من 0 إلى 255 التي أعادتها تلك البرنامج عند الخروج الطبيعي.

مع تعيين الماكرو _POSIX_EXIT، يتم تمثيل قيمة Unix للخروج صفر كحالة VMS أصلية 1، ويتم ترميز قيم Unix من 2 إلى 255 بواسطة المعادلة:

VMS_status = 0x35a000 + (unix_value * 8) + 1.

وفي الحالة الخاصة لقيمة Unix 1 الترميز هو:

VMS_status = 0x35a000 + 8 + 2 + 0x10000000.

بالنسبة لحالات الإنهاء الأخرى، يتم استخدام جزء الخطورة من حالة خروج العملية الفرعية: إذا كانت الخطورة نجاحًا أو معلومات، فإن هذه البتات هي كلها 0؛ إذا كانت الخطورة تحذيرًا، فإنها تحتوي على قيمة 1؛ إذا كانت الخطورة خطأ أو خطأ فادحًا، فإنها تحتوي على بتات الخطورة الفعلية، والتي تتحول إلى قيمة 2 للخطأ و 4 للخطأ الشديد. الخطورة الفادحة هو مصطلح آخر لحالة الخطورة الشديدة.

ونتيجة لذلك، سيكون $? صفرًا دائمًا إذا شارت حالة خروج العملية الفرعية إلى اكتمال ناجح، وغير صفري إذا حدث تحذير أو خطأ أو تم تشغيل برنامج متوافق مع ترميز قيم _POSIX_EXIT وعين حالة.

كيف يمكنك التمييز بين حالة غير صفرية هي نتيجة لحالة خطأ VMS أصلية أو حالة Unix مرمزة؟ لا يمكنك إلا إذا نظرت إلى قيمة ${^CHILD_ERROR_NATIVE}. قيمة ${^CHILD_ERROR_NATIVE} تعيد قيمة VMS الحالة الفعلية وتفحص بتات الخطورة. إذا كانت بتات الخطورة تساوي 1، فعندئذ إذا كانت القيمة الرقمية لـ $? بين 2 و 255 أو 0، فعندئذ يعكس $? بدقة قيمة تم تمريرها من تطبيق Unix. إذا كان $? يساوي 1، وتشير بتات الخطورة إلى خطأ VMS (2)، فعندئذ $? من قيمة خروج تطبيق Unix.

في الممارسة العملية، تتوقع برامج Perl التي تستدعي برامج تعيد قيم حالة _POSIX_EXIT تلك القيم، والبرامج التي تستدعي برامج VMS التقليدية إما تتوقع السلوك السابق أو مجرد التحقق من حالة غير صفرية.

والنجاح هو دائمًا القيمة 0 في جميع السلوكيات.

عندما تكون حالة إنهاء VMS الفعلية للطفل خطأ، داخليًا سيتم تعيين قيمة $! إلى أقرب قيمة errno في Unix لتلك الخطأ حتى ترى برامج Perl التي تختبر رسائل الخطأ رسالة الخطأ المتوقعة بنمط Unix بدلاً من رسالة VMS.

على العكس من ذلك، عند تعيين $? في كتلة END، تتم محاولة تحويل قيمة POSIX إلى حالة أصلية مفهومة لنظام التشغيل عند الخروج من Perl. ما يعنيه هذا هو أن تعيين $? إلى صفر يؤدي إلى قيمة النجاح العامة SS$_NORMAL، وتعيين $? إلى قيمة غير صفرية يؤدي إلى حالة الفشل العامة SS$_ABORT. انظر أيضًا "exit" في perlport.

مع تعريف الاسم المنطقي "PERL_VMS_POSIX_EXIT" كـ "ENABLE"، سيؤدي تعيين $? إلى ترميز القيمة الجديدة في $^E بحيث يمكن استرداد قيم حالة الخروج الأصلية الأصلية أو الفرعية
0 إلى 255 تلقائيًا بواسطة برامج C التي تتوقع سلوك _POSIX_EXIT. إذا كان كل من حالة خروج الوالدين والطفل غير صفريين، فسيتم افتراض أن هذا في الواقع قيمة حالة VMS أصلية سيتم تمريرها. القيمة الخاصة 0xFFFF هي شبه NOOP لأنها ستتسبب في أن تصبح حالة VMS الأصلية الحالية في مكتبة C هي حالة VMS Perl الأصلية الحالية، ويتم معالجتها بهذه الطريقة لأنها معروفة بأنها ليست قيمة حالة VMS أصلية صالحة. يوصى باستخدام فقط القيم في نطاق أرقام حالة الوالدين أو الطفل العادية في Unix، من 0 إلى 255.

يجعل السابقة "use vmsish 'status'" $? تعكس حالة الخروج الفعلية لـ VMS بدلاً من محاكاة الحالة الافتراضية لـ POSIX الموضحة أعلاه. هذه السابقة تعطل أيضًا تحويل القيم غير الصفرية إلى SS$_ABORT عند تعيين $? في كتلة END (ولكن لا يزال صفر سيتم تحويله إلى SS$_NORMAL).

لا تستخدم السابقة "use vmsish 'status'" مع "PERL_VMS_POSIX_EXIT" ممكّن، لأنها في بعض الأحيان تطلب إجراءات متعارضة ونتيجة تجاهل هذه النصيحة ستكون غير محددة للسماح بتحسينات مستقبلية في معالجة الخروج لـ POSIX.

بشكل عام، مع تمكين "PERL_VMS_POSIX_EXIT"، ستكون المعلومات الأكثر تفصيلاً متاحة في حالة الخروج لبرامج DCL النصية أو أدوات VMS الأصلية الأخرى، وستعطي المعلومات المتوقعة لبرامج Posix. لم يتم جعلها افتراضية للحفاظ على التوافق الخلفي.

ملاحظة: تعيين "DECC$FILENAME_UNIX_REPORT" يمكّن ضمنيًا "PERL_VMS_POSIX_EXIT".

$|
يتسبب تعيين $| لتدفق إدخال/إخراج في دفع البيانات بالكامل إلى القرص عند كل عملية كتابة (أي، ليس فقط إلى مخازن RMS الأساسية لملف). بمعنى آخر، إنه يعادل استدعاء fflush() و fsync() من C.

وحدات قياسية مع اختلافات خاصة بـ VMS

SDBM_File

تعمل SDBM_File بشكل صحيح على VMS. ومع ذلك، لديها اختلاف طفيف واحد. ملف دليل قاعدة البيانات الذي تم إنشاؤه له امتداد .sdbm_dir بدلاً من امتداد .dir. ملفات .dir هي ملفات دليل نظام ملفات VMS، واستخدامها لأغراض أخرى قد يسبب مشاكل غير مقبولة.
