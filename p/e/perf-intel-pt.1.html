NAME

perf-intel-pt - Support for Intel Processor Trace within perf tools

SYNOPSIS

perf record -e intel_pt//

DESCRIPTION

Intel Processor Trace (Intel PT) is an extension of Intel Architecture that collects information about software execution such as control flow, execution modes and timings and formats it into highly compressed binary packets. Technical details are documented in the Intel 64 and IA-32 Architectures Software Developer Manuals, Chapter 36 Intel Processor Trace.

Intel PT is first supported in Intel Core M and 5th generation Intel Core processors that are based on the Intel micro-architecture code name Broadwell.

Trace data is collected by perf record and stored within the perf.data file. See below for options to perf record.

Trace data must be decoded which involves walking the object code and matching the trace data packets. For example a TNT packet only tells whether a conditional branch was taken or not taken, so to make use of that packet the decoder must know precisely which instruction was being executed.

Decoding is done on-the-fly. The decoder outputs samples in the same format as samples output by perf hardware events, for example as though the "instructions" or "branches" events had been recorded. Presently 3 tools support this: perf script, perf report and perf inject. See below for more information on using those tools.

The main distinguishing feature of Intel PT is that the decoder can determine the exact flow of software execution. Intel PT can be used to understand why and how did software get to a certain point, or behave a certain way. The software does not have to be recompiled, so Intel PT works with debug or release builds, however the executed images are needed - which makes use in JIT-compiled environments, or with self-modified code, a challenge. Also symbols need to be provided to make sense of addresses.

A limitation of Intel PT is that it produces huge amounts of trace data (hundreds of megabytes per second per core) which takes a long time to decode, for example two or three orders of magnitude longer than it took to collect. Another limitation is the performance impact of tracing, something that will vary depending on the use-case and architecture.

QUICKSTART

It is important to start small. That is because it is easy to capture vastly more data than can possibly be processed.

The simplest thing to do with Intel PT is userspace profiling of small programs. Data is captured with perf record e.g. to trace ls userspace-only:

perf record -e intel_pt//u ls

And profiled with perf report e.g.

perf report

To also trace kernel space presents a problem, namely kernel self-modifying code. A fairly good kernel image is available in /proc/kcore but to get an accurate image a copy of /proc/kcore needs to be made under the same conditions as the data capture. perf record can make a copy of /proc/kcore if the option --kcore is used, but access to /proc/kcore is restricted e.g.

sudo perf record -o pt_ls --kcore -e intel_pt// -- ls

which will create a directory named pt_ls and put the perf.data file (named simply data) and copies of /proc/kcore, /proc/kallsyms and /proc/modules into it. The other tools understand the directory format, so to use perf report becomes:

sudo perf report -i pt_ls

Because samples are synthesized after-the-fact, the sampling period can be selected for reporting. e.g. sample every microsecond

sudo perf report pt_ls --itrace=i1usge

See the sections below for more information about the --itrace option.

Beware the smaller the period, the more samples that are produced, and the longer it takes to process them.

Also note that the coarseness of Intel PT timing information will start to distort the statistical value of the sampling as the sampling period becomes smaller.

To represent software control flow, "branches" samples are produced. By default a branch sample is synthesized for every single branch. To get an idea what data is available you can use the perf script tool with all itrace sampling options, which will list all the samples.

perf record -e intel_pt//u ls
perf script --itrace=iybxwpe

An interesting field that is not printed by default is flags which can be displayed as follows:

perf script --itrace=iybxwpe -F+flags

The flags are "bcrosyiABExghDt" which stand for branch, call, return, conditional, system, asynchronous, interrupt, transaction abort, trace begin, trace end, in transaction, VM-entry, VM-exit, interrupt disabled, and interrupt disable toggle respectively.

perf script also supports higher level ways to dump instruction traces:

perf script --insn-trace=disasm

or to use the xed disassembler, which requires installing the xed tool (see XED below):

perf script --insn-trace --xed

Dumping all instructions in a long trace can be fairly slow. It is usually better to start with higher level decoding, like

perf script --call-trace

or

perf script --call-ret-trace

and then select a time range of interest. The time range can then be examined in detail with

perf script --time starttime,stoptime --insn-trace=disasm

While examining the trace it’s also useful to filter on specific CPUs using the -C option

perf script --time starttime,stoptime --insn-trace=disasm -C 1

Dump all instructions in time range on CPU 1.

Another interesting field that is not printed by default is ipc which can be displayed as follows:

perf script --itrace=be -F+ipc

There are two ways that instructions-per-cycle (IPC) can be calculated depending on the recording.

If the cyc config term (see config terms section below) was used, then IPC and cycle events are calculated using the cycle count from CYC packets, otherwise MTC packets are used - refer to the mtc config term. When MTC is used, however, the values are less accurate because the timing is less accurate.

Because Intel PT does not update the cycle count on every branch or instruction, the values will often be zero. When there are values, they will be the number of instructions and number of cycles since the last update, and thus represent the average IPC cycle count since the last IPC for that event type. Note IPC for "branches" events is calculated separately from IPC for "instructions" events.

Even with the cyc config term, it is possible to produce IPC information for every change of timestamp, but at the expense of accuracy. That is selected by specifying the itrace A option. Due to the granularity of timestamps, the actual number of cycles increases even though the cycles reported does not. The number of instructions is known, but if IPC is reported, cycles can be too low and so IPC is too high. Note that inaccuracy decreases as the period of sampling increases i.e. if the number of cycles is too low by a small amount, that becomes less significant if the number of cycles is large. It may also be useful to use the A option in conjunction with dlfilter-show-cycles.so to provide higher granularity cycle information.

Also note that the IPC instruction count may or may not include the current instruction. If the cycle count is associated with an asynchronous branch (e.g. page fault or interrupt), then the instruction count does not include the current instruction, otherwise it does. That is consistent with whether or not that instruction has retired when the cycle count is updated.

Another note, in the case of "branches" events, non-taken branches are not presently sampled, so IPC values for them do not appear e.g. a CYC packet with a TNT packet that starts with a non-taken branch. To see every possible IPC value, "instructions" events can be used e.g. --itrace=i0ns

حدث جديد

يقوم برنامج تشغيل Intel PT في النواة بإنشاء PMU جديد لـ Intel PT. يتم تحديد أحداث PMU عن طريق توفير اسم PMU متبوعًا بـ "config" مفصولًا بشرطات مائلة. تم إجراء تحسين للسماح بـ "config" افتراضي، على سبيل المثال الخيار

-e intel_pt//

سيستخدم قيمة config افتراضية. حاليًا، هذا هو نفس

-e intel_pt/tsc,noretcomp=0/

وهو نفس

-e intel_pt/tsc=1,noretcomp=0/

لاحظ أن هناك مصطلحات config أخرى - انظر قسم مصطلحات config أدناه.

يتم سرد مصطلحات config في /sys/devices/intel_pt/format. وهي حقول بت داخل عضو config في `struct perf_event_attr` الذي يتم تمريره إلى النواة بواسطة استدعاء النظام `perf_event_open`. تتوافق مع حقول البت في MSR IA32_RTIT_CTL. إليك قائمة بها وتعريفاتها:

-e intel_pt/noretcomp=0/

-e intel_pt/tsc=0/

-e intel_pt/config=0x400/

مصطلحات config

مصطلحات config هي معلمات محددة مع خيار الحد `-e intel_pt//`، على سبيل المثال:

-e intel_pt/cyc/

والذي يحدد وضع الدقة الزمنية. يمكن أن يحتوي كل مصطلح config على قيمة افتراضية هي 1، لذا فإن ما سبق هو نفس:

-e intel_pt/cyc=1/

يتم تعيين بعض المصطلحات افتراضيًا، لذا يجب تعيينها إلى 0 لإيقاف تشغيلها. على سبيل المثال، لتعطيل تتبع الفروع:

-e intel_pt/branch=0/

يتم فصل مصطلحات config المتعددة بفواصل، على سبيل المثال:

-e intel_pt/cyc,mtc_period=9/

هناك أيضًا مصطلحات config شائعة، انظر وثائق perf-record(1).

يتم وصف مصطلحات Intel PT config أدناه.

tsc

مدعوم دائمًا. ينتج حزم طوابع زمنية TSC لتوفير معلومات التوقيت. في بعض الحالات، يكون من الممكن فك التشفير بدون معلومات التوقيت، على سبيل المثال سياق لكل خيط لا يتداخل مع خرائط الذاكرة القابلة للتنفيذ.

يحدد config الافتراضي tsc (أي tsc=1).

noretcomp

مدعوم دائمًا. يعطل "ضغط العودة" بحيث يتم إنتاج حزمة TIP عند عودة دالة. يسبب إنتاج المزيد من الحزم ولكنه قد يجعل فك التشفير أكثر موثوقية.

لا يحدد config الافتراضي noretcomp (أي noretcomp=0).

psb_period

يسمح بتحديد تردد حزم PSB.

حزمة PSB هي حزمة مزامنة توفر نقطة بداية لفك التشفير أو الاسترداد من الأخطاء.

يتم الإشارة إلى دعم psb_period بواسطة:

/sys/bus/event_source/devices/intel_pt/caps/psb_cyc

والذي يحتوي على "1" إذا كانت الميزة مدعومة و "0" بخلاف ذلك.

القيم الصالحة معطاة بواسطة:

/sys/bus/event_source/devices/intel_pt/caps/psb_periods

والذي يحتوي على قيمة سداسية عشرية، تمثل بتاتها القيم الصالحة، على سبيل المثال، تعيين البت 2 يعني أن القيمة 2 صالحة.

يتم تحويل قيمة psb_period إلى العدد التقريبي للبايتات المتتبعة بين حزم PSB كالتالي:

2 ^ (value + 11)

على سبيل المثال، القيمة 3 تعني 16 كيلوبايت بين PSBs

إذا تم إدخال قيمة غير صالحة، فستعطي رسالة الخطأ قائمة بالقيم الصالحة، على سبيل المثال

$ perf record -e intel_pt/psb_period=15/u uname
Invalid psb_period for intel_pt. Valid values are: 0-5

إذا تم تحديد حزم MTC، فإن config الافتراضي يحدد قيمة 3 (أي psb_period=3) أو أقرب قيمة أقل مدعومة (0 مدعوم دائمًا). بخلاف ذلك، القيمة الافتراضية هي 0.

إذا كان من المتوقع أن يكون فك التشفير موثوقًا به وكان المخزن المؤقت كبيرًا، فيمكن استخدام فترة PSB كبيرة.

نظرًا لأنه يتم إنتاج حزمة TSC مع PSB، يمكن لفترة PSB أيضًا التأثير على دقة معلومات التوقيت في غياب MTC أو CYC.

mtc

ينتج حزم توقيت MTC.

توفر حزم MTC معلومات توقيت أدق من حزم TSC. تسجل حزم MTC الوقت باستخدام ساعة الكريستال العتادية (CTC) التي ترتبط بحزم TSC باستخدام حزمة TMA.

يتم الإشارة إلى دعم هذه الميزة بواسطة:

/sys/bus/event_source/devices/intel_pt/caps/mtc

والذي يحتوي على "1" إذا كانت الميزة مدعومة و "0" بخلاف ذلك.

يمكن أيضًا تحديد تردد حزم MTC - انظر mtc_period أدناه.

mtc_period

يحدد مدى تكرار إنتاج حزم MTC - انظر mtc أعلاه لمعرفة كيفية تحديد ما إذا كانت حزم MTC مدعومة.

القيم الصالحة معطاة بواسطة:

/sys/bus/event_source/devices/intel_pt/caps/mtc_periods

والذي يحتوي على قيمة سداسية عشرية، تمثل بتاتها القيم الصالحة، على سبيل المثال، تعيين البت 2 يعني أن القيمة 2 صالحة.

يتم تحويل قيمة mtc_period إلى تردد MTC كالتالي:

CTC-frequency / (2 ^ value)

على سبيل المثال، القيمة 3 تعني ثُمن تردد CTC

حيث CTC هي ساعة الكريستال العتادية، والتي يمكن ربط ترددها بـ TSC عبر القيم المقدمة في cpuid leaf 0x15.

إذا تم إدخال قيمة غير صالحة، فستعطي رسالة الخطأ قائمة بالقيم الصالحة، على سبيل المثال

$ perf record -e intel_pt/mtc_period=15/u uname
Invalid mtc_period for intel_pt. Valid values are: 0,3,6,9

القيمة الافتراضية هي 3 أو أقرب قيمة أقل مدعومة (0 مدعوم دائمًا).

cyc

ينتج حزم توقيت CYC.

توفر حزم CYC معلومات توقيت أدق من حزم MTC و TSC. تحتوي حزمة CYC على عدد دورات وحدة المعالجة المركزية منذ آخر حزمة CYC. على عكس حزم MTC و TSC، يتم إرسال حزم CYC فقط عند إرسال حزمة أخرى.

يتم الإشارة إلى دعم هذه الميزة بواسطة:

/sys/bus/event_source/devices/intel_pt/caps/psb_cyc

والذي يحتوي على "1" إذا كانت الميزة مدعومة و "0" بخلاف ذلك.

يمكن تقليل عدد حزم CYC المنتجة عن طريق تحديد عتبة - انظر cyc_thresh أدناه.

cyc_thresh

يحدد مدى تكرار إنتاج حزم CYC - انظر cyc أعلاه لمعرفة كيفية تحديد
إذا تم دعم حزم CYC.

القيم الصالحة لـ cyc_thresh مُعطاة بواسطة:

/sys/bus/event_source/devices/intel_pt/caps/cycle_thresholds

التي تحتوي على قيمة سداسية عشرية، تمثل بتاتها القيم الصالحة، على سبيل المثال، بت 2 مضبوط يعني أن القيمة 2 صالحة.

تمثل قيمة cyc_thresh الحد الأدنى لعدد دورات وحدة المعالجة المركزية التي يجب أن تمر قبل إرسال حزمة CYC. عدد دورات وحدة المعالجة المركزية هو:

2 ^ (value - 1)

على سبيل المثال، القيمة 4 تعني أنه يجب أن تمر 8 دورات لوحدة المعالجة المركزية قبل إرسال حزمة CYC. ملاحظة: لا تزال حزمة CYC تُرسل فقط عند إرسال حزمة أخرى، وليس في كل 8 دورات لوحدة المعالجة المركزية، على سبيل المثال.

إذا تم إدخال قيمة غير صالحة، فإن رسالة الخطأ ستعرض قائمة بالقيم الصالحة، على سبيل المثال:

$ perf record -e intel_pt/cyc,cyc_thresh=15/u uname
Invalid cyc_thresh for intel_pt. Valid values are: 0-12

لا يتم طلب حزم CYC افتراضيًا.

pt

يحدد تمرير (pass-through) الذي يمكّن مصطلح التكوين *branch*.

يحدد التكوين الافتراضي *pt* إذا كان متاحًا، لذلك لن يحتاج المستخدم أبدًا إلى تحديد هذا المصطلح.

branch

يمكّن تتبع الفروع. يتم تمكين تتبع الفروع افتراضيًا، لذا لتعطيل تتبع الفروع استخدم *branch=0*.

يحدد التكوين الافتراضي *branch* إذا كان متاحًا.

ptw

يمكّن حزم PTWRITE التي يتم إنتاجها عند تنفيذ تعليمة ptwrite.

يتم الإشارة إلى دعم هذه الميزة بواسطة:

/sys/bus/event_source/devices/intel_pt/caps/ptwrite

الذي يحتوي على "1" إذا كانت الميزة مدعومة و "0" بخلاف ذلك.

كبديل، راجع "PTWRITE المحاكى" أدناه.

fup_on_ptw

يمكّن حزمة FUP لتتبع حزمة PTWRITE. توفر حزمة FUP عنوان تعليمة ptwrite. في غياب fup_on_ptw، سيستخدم المُفكك عنوان الفرع السابق إذا كان تتبع الفروع ممكّنًا، وإلا فسيكون العنوان صفرًا. لاحظ أن fup_on_ptw سيعمل حتى عند تعطيل تتبع الفروع.

pwr_evt

يمكّن أحداث الطاقة. توفر أحداث الطاقة معلومات حول التغييرات في حالة C لوحدة المعالجة المركزية.

/sys/bus/event_source/devices/intel_pt/caps/power_event_trace

مصطلحات التكوين على الأحداث الأخرى

تعمل بعض ميزات Intel PT مع أحداث أخرى، مثل أخذ عينات منطقة AUX و PEBS-via-PT. في هذه الحالات، يمكن أن تحتوي الأحداث الأخرى على مصطلحات تكوين أدناه:

aux-sample-size

يُستخدم لضبط حجم عينة منطقة AUX، راجع قسم خيار أخذ عينات منطقة AUX

aux-output

يُستخدم لتحديد PEBS-via-PT، راجع قسم PEBS عبر Intel PT

aux-action

يُستخدم لإيقاف مؤقت أو استئناف التتبع، راجع قسم إيقاف مؤقت أو استئناف التتبع

خيار أخذ عينات منطقة AUX

لتحديد "أخذ العينات" في Intel PT، يمكن استخدام خيار أخذ عينات منطقة AUX:

--aux-sample

اختياريًا، يمكن أن يتبعه حجم العينة بالبايت، على سبيل المثال:

--aux-sample=8192

بالإضافة إلى ذلك، يجب تحديد حدث Intel PT لأخذ العينات، على سبيل المثال:

-e intel_pt//u

سيتم إنشاء عينات على أحداث أخرى تحتوي على بيانات Intel PT، على سبيل المثال، سيؤدي ما يلي إلى إنشاء عينات Intel PT على حدث فقدان الفروع، لاحظ أنه يجب تجميع الأحداث باستخدام {}:

perf record --aux-sample -e '{intel_pt//u,branch-misses:u}'

بديل لـ *--aux-sample* هو إضافة مصطلح التكوين *aux-sample-size* إلى الأحداث. في هذه الحالة، يكون التجميع ضمنيًا، على سبيل المثال:

perf record -e intel_pt//u -e branch-misses/aux-sample-size=8192/u

هو نفس:

perf record -e '{intel_pt//u,branch-misses/aux-sample-size=8192/u}'

ولكن يسمح أيضًا باستخدام مرشح عنوان، على سبيل المثال:

perf record -e intel_pt//u --filter 'filter * @/bin/ls' -e branch-misses/aux-sample-size=8192/u -- ls

من المهم اختيار حجم عينة كبير بما يكفي لاحتواء حزمة PSB واحدة على الأقل. إذا لم يكن الأمر كذلك، فسيتم عرض تحذير:

Intel PT sample size (%zu) may be too small for PSB period (%zu)

الحساب المستخدم لذلك هو: إذا كانت sample_size ≤ psb_period + 256، فسيتم عرض التحذير. عند استخدام أخذ العينات، يكون psb_period افتراضيًا 0 (2KiB).

حجم العينة الافتراضي هو 4KiB.

يتم تمرير حجم العينة في aux_sample_size في الهيكل perf_event_attr. يتم تحديد حجم العينة بواسطة الحد الأقصى لحجم الحدث وهو 64KiB. من الصعب معرفة مدى حجم الحدث بدون إرفاق عينة التتبع، ولكن الأداة تتحقق من أن حجم العينة ليس أكبر من 60KiB.

خيار اللقطة الجديد

يكمن الاختلاف بين التتبع الكامل واللقطة من منظور النواة في أننا في التتبع الكامل لا نعيد كتابة بيانات التتبع التي لم يجمعها المستخدم بعد (وأشار إلى ذلك عن طريق تقدم aux_tail)، بينما في وضع اللقطة نسمح للتتبع بالتشغيل وإعادة كتابة البيانات القديمة في المخزن المؤقت بحيث متى حدث شيء مثير للاهتمام، يمكننا إيقافه والتقاط لقطة لما كان يحدث حول تلك اللحظة المثيرة للاهتمام.

لتحديد وضع اللقطة، تمت إضافة خيار جديد:

-S

اختياريًا، يمكن أن يتبعه حجم اللقطة، على سبيل المثال:

-S0x100000

حجم اللقطة الافتراضي هو حجم mmap لمنطقة AUX. إذا لم يتم تحديد حجم mmap لمنطقة AUX أو حجم اللقطة، فسيتم افتراضيًا 4MiB للمستخدمين المتميزين (أو إذا كان /proc/sys/kernel/perf_event_paranoid < 0)، 128KiB للمستخدمين غير المتميزين. إذا لم يحدد المستخدم غير المتميز صفحات mmap، فسيتم تقليل صفحات mmap كما هو موضح في قسم خيار حجم mmap لمنطقة AUX الجديد أدناه.

يتم عرض حجم اللقطة إذا تم استخدام الخيار -vv، على سبيل المثال:

Intel PT snapshot size: %zu

خيار حجم mmap لمنطقة AUX الجديد

يتم تحديد حجم مخزن Intel PT المؤقت بإضافة إلى الخيار -m، على سبيل المثال:

-m,16

يحدد حجم المخزن المؤقت 16 صفحة أي 64KiB.

لاحظ أن الوظائف الحالية لـ -m لم تتغير. يتم تحديد حجم mmap لمنطقة AUX بواسطة الإضافة الاختيارية لفاصلة والقيمة.

يبلغ حجم mmap الافتراضي لمنطقة AUX لـ Intel PT 4MiB/حجم الصفحة للمستخدمين المتميزين (أو إذا كان /proc/sys/kernel/perf_event_paranoid < 0)، 128KiB للمستخدمين غير المتميزين. إذا لم يحدد المستخدم غير المتميز صفحات mmap، فسيتم تقليل صفحات mmap من الافتراضي 512KiB/حجم الصفحة إلى 256KiB/حجم الصفحة، وإلا فمن المحتمل أن يحصل المستخدم على خطأ لأنه يتجاوز حد mlock الخاص به (أقصى ذاكرة مقفلة كما هو موضح في /proc/self/limits). لاحظ أن perf لا يحسب أول 512KiB (فعليًا /proc/sys/kernel/perf_event_mlock_kb ناقص صفحة واحدة) لكل وحدة معالجة مركزية ضد حد mlock، لذا يُسمح للمستخدم غير المتميز بـ 512KiB لكل وحدة معالجة مركزية بالإضافة إلى حد mlock الخاص به (الذي يبلغ افتراضيًا 64KiB ولكنه لا يُضرب في عدد وحدات المعالجة المركزية).

في وضع التتبع الكامل، يُسمح بقوى الرقم 2 لحجم المخزن المؤقت، مع حد أدنى للحجم صفحتان. في وضع اللقطة أو وضع أخذ العينات، يكون الأمر نفسه ولكن الحد الأدنى للحجم صفحة واحدة.

يتم عرض حجم mmap وحجم mmap لمنطقة AUX إذا تم استخدام الخيار -vv، على سبيل المثال:

mmap length 528384
auxtrace mmap length 4198400

أوضاع تشغيل Intel PT

يمكن استخدام Intel PT في 3 أوضاع: وضع التتبع الكامل، وضع أخذ العينات، وضع اللقطة.

وضع التتبع الكامل يتتبع بشكل مستمر، على سبيل المثال:

perf record -e intel_pt//u uname

وضع أخذ العينات يرفق عينة Intel PT بأحداث أخرى، على سبيل المثال:

perf record --aux-sample -e intel_pt//u -e branch-misses:u

وضع اللقطة يلتقط البيانات المتاحة عند إرسال إشارة أو إصدار أمر تحكم "لقطة". على سبيل المثال، باستخدام إشارة:

perf record -v -e intel_pt//u -S ./loopy 1000000000 &
[1] 11435
kill -USR2 11435
Recording AUX area tracing snapshot

لاحظ أن الإشارة المرسلة هي SIGUSR2. لاحظ أن "Recording AUX area tracing snapshot" يتم عرضه بسبب استخدام الخيار -v.

ميزة استخدام أمر التحكم "snapshot" هي أن الوصول يتم التحكم فيه عن طريق الوصول إلى FIFO، على سبيل المثال:

$ mkfifo perf.control
$ mkfifo perf.ack
$ cat perf.ack &
[1] 15235
$ sudo ~/bin/perf record --control fifo:perf.control,perf.ack -S -e intel_pt//u -- sleep 60 &
[2] 15243
$ ps -e | grep perf
15244 pts/1    00:00:00
er dlfilter-show-cycles.so

لرؤية قائمة بـ dlfilters:

perf script -v --list-dlfilters

انظر أيضًا perf-dlfilters(1)

خيار dump

يحتوي perf script على خيار (-D) لـ "إفراغ" الأحداث، أي عرض البيانات الثنائية.

عند استخدام -D، يتم عرض حزم Intel PT. لا يهتم محلل الحزم بحزم PSB، بل يقوم فقط بفك ترميز البايتات - لذا قد لا تكون الحزم التي يراها محلل الحزم الفعلي متطابقة في الأماكن التي تكون فيها البيانات تالفة. أحد الأمثلة على ذلك هو عندما يكون مقاطع التبديل المخزن مؤقتًا بطيئًا جدًا، وتم ملء المخزن المؤقت بالكامل. في هذه الحالة، قد تكون الحزمة الأخيرة في المخزن المؤقت مقطوعة ويتبعها فورًا PSB مع استمرار التتبع في المخزن المؤقت التالي.

لتعطيل عرض حزم Intel PT، ادمج الخيار -D مع --no-itrace.

PERF REPORT

بشكل افتراضي، سيقوم perf report بفك ترميز بيانات التتبع الموجودة في ملف perf.data. يمكن التحكم في ذلك بشكل أكبر من خلال الخيار الجديد --itrace بالضبط كما في perf script، مع استثناء أن الافتراضي هو --itrace=igxe.

PERF INJECT

يقبل perf inject أيضًا خيار --itrace، وفي هذه الحالة تتم إزالة بيانات التتبع واستبدالها بالأحداث المصنعة. مثال:

perf inject --itrace -i perf.data -o perf.data.new

PEBS VIA INTEL PT

بعض الأجهزة تحتوي على ميزة إعادة توجيه سجلات PEBS إلى تتبع Intel PT. يتم تحديد التسجيل باستخدام مصطلح تكوين المخرج المساعد، مثال:

perf record -c 10000 -e '{intel_pt/branch=0/,cycles/aux-output/ppp}' uname

في الأصل، كان البرنامج يدعم فقط إعادة توجيه حدث PEBS واحد على الأكثر لأنه لم يكن قادرًا على التمييز بين حدث وآخر. للتغلب على ذلك، تضيف النواة الحديثة وأدوات perf دعمًا لحدث النطاق الجانبي PERF_RECORD_AUX_OUTPUT_HW_ID. للتحقق من وجود هذا الحدث في تتبع PEBS-via-PT:

perf script -D --no-itrace | grep PERF_RECORD_AUX_OUTPUT_HW_ID

لعرض أحداث PEBS من تتبع Intel PT، استخدم خيار itrace o، مثال:

perf script --itrace=oe

تتبع الآلات الافتراضية (النواة فقط)

حاليًا، يتم دعم تتبع النواة باستخدام فك الترميز "الخالد" (أي لا توجد طوابع زمنية TSC) أو ارتباط وقت VM. ارتباط وقت VM هو خطوة إضافية باستخدام perf inject ويتطلب إزاحة VMX TSC ثابتة وعدم وجود قياس VMX لـ TSC.

قيود وملاحظات أخرى

قد تقمع ضوابط VMX الحزم اللازمة لفك الترميز مما يؤدي إلى أخطاء في فك الترميز
قد تمنع ضوابط VMX مقاطعة NMI الخاصة بـ perf للمضيف مما قد يؤدي إلى فقدان بيانات التتبع
الكود الذاتي التعديل للنواة الضيف (مثل تسميات القفز أو eBPF المترجم JIT) سيؤدي إلى أخطاء في فك الترميز
معلومات خيط الضيف غير معروفة
وحدة معالجة الرسومات الافتراضية (VCPU) غير معروفة ولكن قد يكون من الممكن استنتاجها من خيط المضيف
لا تدعم سلاسل الاستدعاء

TRACING KVM GUESTS

There are 3 main ways of tracing KVM guests:

1.
Trace only the VM.
2.
Trace the VM and its host, i.e. the KVM process.
3.
Trace the VM and its host, and inject guest events into the host trace.

In order to trace a VM, the VM must be started with the qemu trace enabled.

With the example below, the VM has 4 virtual CPUs.

  CPU 0/KVM 17006  0   17007  4  80   0 - 1818189 -    ?        00:00:05 CPU 1/KVM
  CPU 1/KVM 16998  1   17007  3  80   0 - 1818189 -    ?        00:00:04 CPU 2/KVM
  CPU 2/KVM 16998  1   17008  4  80   0 - 1818189 -    ?        00:00:05 CPU 3/KVM

Start an open-ended perf record, tracing the VM process, do something on the VM, and then ctrl-C to stop. IPC can be determined, hence cyc=1 can be added. Only kernel decoding is supported, so k must be specified. Intel PT traces both the host and the guest so --guest and --host need to be specified.

$ sudo perf kvm --guest --host --guestkallsyms record --kcore -e intel_pt/cyc=1/k -p 16998
^C[ perf record: Woken up 1 times to write data ]
[ perf record: Captured and wrote 9.041 MB perf.data.kvm ]

Now perf inject can be used to determine the VMX TCS Offset. Note, Intel PT TSC packets are only 7-bytes, so the TSC Offset might differ from the actual value in the 8th byte. That will have no effect i.e. the resulting timestamps will be correct anyway.

$ perf inject -i perf.data.kvm --vm-time-correlation=dry-run
ERROR: Unknown TSC Offset for VMCS 0x1bff6a
VMCS: 0x1bff6a  TSC Offset 0xffffe42722c64c41
ERROR: Unknown TSC Offset for VMCS 0x1cbc08
VMCS: 0x1cbc08  TSC Offset 0xffffe42722c64c41
ERROR: Unknown TSC Offset for VMCS 0x1c3ce8
VMCS: 0x1c3ce8  TSC Offset 0xffffe42722c64c41
ERROR: Unknown TSC Offset for VMCS 0x1cbce9
VMCS: 0x1cbce9  TSC Offset 0xffffe42722c64c41

Each virtual CPU has a different Virtual Machine Control Structure (VMCS) shown above with the calculated TSC Offset. For an unchanging TSC Offset they should all be the same for the same virtual machine.

Now that the TSC Offset is known, it can be provided to perf inject

$ perf inject -i perf.data.kvm --vm-time-correlation="dry-run 0xffffe42722c64c41"

Note the options for perf inject --vm-time-correlation are:

[ dry-run ] [ <TSC Offset> [ : <VMCS> [ , <VMCS> ]... ]  ]...

So it is possible to specify different TSC Offsets for different VMCS. The option "dry-run" will cause the file to be processed but without updating it. Note it is also possible to get a intel_pt.log file by adding option --itrace=d

There were no errors so, do it for real

$ perf inject -i perf.data.kvm --vm-time-correlation=0xffffe42722c64c41 --force

perf script can be used to see if there are any decoder errors

$ perf script -i perf.data.kvm --guestkallsyms $KALLSYMS --itrace=e-o

TRACING VIRTUAL MACHINES (INCLUDING USER SPACE)

It is possible to use perf record to record sideband events within a virtual machine, so that an Intel PT trace on the host can be decoded. Sideband events from the guest perf.data file can be injected into the host perf.data file using perf inject.

Here is an example of the steps needed:

On the guest machine:

Check that no-kvmclock kernel command line option was used to boot:

Note, this is essential to enable time correlation between host and guest machines.

$ cat /proc/cmdline
BOOT_IMAGE=/boot/vmlinuz-5.10.0-16-amd64 root=UUID=cb49c910-e573-47e0-bce7-79e293df8e1d ro no-kvmclock

There is no BPF support at present so, if possible, disable JIT compiling:

$ echo 0 | sudo tee /proc/sys/net/core/bpf_jit_enable
0

Start perf record to collect sideband events:

$ sudo perf record -o guest-sideband-testing-guest-perf.data --sample-identifier --buildid-all --switch-events --kcore -a -e dummy

On the host machine:

Start perf record to collect Intel PT trace:

Note, the host trace will get very big, very fast, so the steps from starting to stopping the host trace really need to be done so that they happen in the shortest time possible.

$ sudo perf record -o guest-sideband-testing-host-perf.data -m,64M --kcore -a -e intel_pt/cyc/

On the guest machine:

Run a small test case, just uname in this example:

$ uname
Linux

On the host machine:

Stop the Intel PT trace:

^C
[ perf record: Woken up 1 times to write data ]
[ perf record: Captured and wrote 76.122 MB guest-sideband-testing-host-perf.data ]

On the guest machine:

Stop the Intel PT trace:

^C
[ perf record: Woken up 1 times to write data ]
[ perf record: Captured and wrote 1.247 MB guest-sideband-testing-guest-perf.data ]

And then copy guest-sideband-testing-guest-perf.data to the host (not shown here).

With the 2 perf.data recordings, and with their ownership changed to the user.

PERF_EMULATE_PTWRITE

This is a helper function to emulate the PTW instruction, which is used by Intel PT to write data into the trace buffer.

The function uses the PTWRITE_MAGIC string to check whether the function is called via the native PTWRITE instruction (e.g., using the <kaddr>:ptwrite event) or if it's called via the emulation code.

PTWRITE_MAGIC is defined as:

#define PERF_EMULATE_PTWRITE_8_BITS        "1: shl %rax\n"     \
                "   jc 1f\n"
/* Undefined instruction */
#define PERF_EMULATE_PTWRITE_UD2        ".byte 0x0f, 0x0b\n"
#define PERF_EMULATE_PTWRITE_MAGIC        PERF_EMULATE_PTWRITE_UD2 ".ascii \"perf,ptwrite  \"\n"
void perf_emulate_ptwrite(uint64_t x __attribute__ ((__unused__)))
{
         /* Assumes SysV ABI : x passed in rdi */
        __asm__ volatile (
                "jmp 1f\n"
                PERF_EMULATE_PTWRITE_MAGIC
                "1: mov %rdi, %rax\n"
                PERF_EMULATE_PTWRITE_8_BITS
                PERF_EMULATE_PTWRITE_8_BITS
                PERF_EMULATE_PTWRITE_8_BITS
                PERF_EMULATE_PTWRITE_8_BITS
                PERF_EMULATE_PTWRITE_8_BITS
                PERF_EMULATE_PTWRITE_8_BITS
                PERF_EMULATE_PTWRITE_8_BITS
                PERF_EMULATE_PTWRITE_8_BITS
                "1: ret\n"
        );
}

For example, a test program with the function above:

#include <stdio.h>
#include <stdint.h>
#include <stdlib.h>
#include "perf_emulate_ptwrite.h"
int main(int argc, char *argv[])
{
        uint64_t x = 0;
        if (argc > 1)
                x = strtoull(argv[1], NULL, 0);
        perf_emulate_ptwrite(x);
        return 0;
}

PIPE MODE

Pipe mode is a problem for Intel PT and possibly other auxtrace users. It’s not recommended to use a pipe as data output with Intel PT because of the following reason.

Essentially the auxtrace buffers do not behave like the regular perf event buffers. That is because the head and tail are updated by software, but in the auxtrace case the data is written by hardware. So the head and tail do not get updated as data is written.

In the Intel PT case, the head and tail are updated only when the trace is disabled by software, for example: - full-trace, system wide : when buffer passes watermark - full-trace, not system-wide : when buffer passes watermark or context switches - snapshot mode : as above but also when a snapshot is made - sample mode : as above but also when a sample is made

That means finished-round ordering doesn’t work. An auxtrace buffer can turn up that has data that extends back in time, possibly to the very beginning of tracing.

For a perf.data file, that problem is solved by going through the trace and queuing up the auxtrace buffers in advance.

For pipe mode, the order of events and timestamps can presumably be messed up.

PAUSE OR RESUME TRACING

With newer Kernels, it is possible to use other selected events to pause or resume Intel PT tracing. This is configured by using the "aux-action" config term:

"aux-action=pause" is used with events that are to pause Intel PT tracing.

"aux-action=resume" is used with events that are to resume Intel PT tracing.

"aux-action=start-paused" is used with the Intel PT event to start in a paused state.
