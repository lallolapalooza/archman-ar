كلاهما يفعل نفس الشيء ولكن باستخدام أساليب تحليل مختلفة. سنغطي كلاهما بالتفصيل. آمل أن تجد أن Pegex يتعامل مع تحليل أسبقية المعاملات بأناقة.

المشكلة

محللات الأسبقية مثيرة للاهتمام لأنك تحتاج إلى التعامل مع معاملات لها نفس الأسبقية، وأسبقيات مختلفة، وكل من الارتباط الأيسر والأيمن.

خذ بعين الاعتبار المعادلة:

1 - 2 ^ 3 ^ 4 + 5 * 6 / 7

قواعد الأسبقية والارتباط العادية تجعل هذا هو نفسه:

(1 - (2 ^ (3 ^ 4)) + ((5 * 6) / 7))

يجب أن ينتج محسّبنا نفس النتيجة لكلاهما. لاحظ أن هذا يعني أننا سنقوم بتحليل الأرقام، 5 معاملات، أقواس، وفصل المسافات.

الحلول

تتضمن معظم الحلول التي ستقرأ عنها على الويب خطوة مسح / ترميز قبل التحليل. يقوم Pegex دائمًا بتحليل تيار إدخال مباشرة، مستخرجًا "رموز" يحتاجها باستخدام التقاطات regex. لذلك يحدث التحليل كعملية واحدة، والتي لها العديد من المزايا.

ولكن كيف نحصل على قواعد أسبقية المعاملات في هذا؟ حسنًا، لدينا طريقتان مختلفتان:

calculator1.pl - تسلق أسبقية المعاملات

ملاحظة: تم نسخ الكود في هذا المثال ولصقه من "calculator/" في ملفات الأمثلة. الكود الموجود في تلك الملفات التشغيلية مختلف قليلاً ولكنه أعيد كتابته ليبدو أكثر منطقية في هذه الوثيقة.

تستخدم حاسبتنا المثال الأول ما يعرف بطريقة تسلق أسبقية المعاملات. انظر: http://en.wikipedia.org/wiki/Operator-precedence_parser#Precedence_climbing_method.

هذه في الأساس تقنية ذكية لتحديد قواعد النحو الخاصة بنا بطريقة تشير إلى الأسبقية. إليك قواعد pegex من الكود:

expr: add-sub
add-sub: mul-div+ % /- ( [ '+-' ])/
mul-div: power+ % /- ([ '*/' ])/
power: token+ % /- '^' /
token: /- '(' -/ expr /- ')'/ | number
number: /- ( '-'? DIGIT+ )/

إنها غريبة بعض الشيء ولكنها تعمل. تقول إن أي تعبير هو جمع/طرح وأن الجمع/الطرح هو حقًا ضرب/قسمة إلخ. أخيرًا بعد المعامل الأخير يأتي رمز الرقم والأقواس.

يبدو الأمر معكوسًا قليلاً. أحد أكبر عيوب PCM هو أنه يصبح أقل كفاءة مع زيادة عدد المعاملات. يحتاج إلى المرور عبر الشجرة بأكملها، فقط للعثور على كل رقم.

لكنها تعمل والكود بسيط. تحصل فئة المستلم على الأرقام بالترتيب الصحيح، وتقوم بتقييم الإجابة على الفور وتعيد الإجابة لكل مستوى. مهما كانت قيمة الإرجاع للعملية النهائية، تصبح نتيجة التحليل. إليك فئة المستلم:

{
    package Calculator;
    use base 'Pegex::Tree';
    sub gotrule {
        my ($self, $list) = @_;
        return $list unless ref $list;
        # Right associative:
        if ($self->rule eq 'power') {
            while (@$list > 1) {
                my ($a, $b) = splice(@$list, -2, 2);
                push @$list, $a ** $b;
            }
        }
        # Left associative:
        else {
            while (@$list > 1) {
                my ($a, $op, $b) = splice(@$list, 0, 3);
                unshift @$list,
                    ($op eq '+') ? ($a + $b) :
                    ($op eq '-') ? ($a - $b) :
                    ($op eq '*') ? ($a * $b) :
                    ($op eq '/') ? ($a / $b) :
                    die;
            }
        }
        return @$list;
    }
}

كما ترى، لديها طريقة عمل لكل مستوى أو أسبقية. تقوم بالتكرار فوق التعبير، وتقييمه. ما إذا كانت تتكرر من اليسار إلى اليمين أو من اليمين إلى اليسار يعتمد على الارتباط الذي نريد استخدامه.

كود التشغيل الخاص بنا يبدو كالتالي:

while (1) {
    print "\nEnter an equation: ";
    my $expr = <> || '';
    chomp $expr;
    last unless length $expr;
    calc($expr);
}
sub calc {
    my ($expr) = @_;
    my $result = pegex($grammar, 'Calculator')->parse($expr);
    if ($@) {
        warn $@;
        return;
    }
    print "$expr = $result\n";
}

وهذا هو كل شيء. لدينا حاسبة عاملة كما هو محدد!

ومع ذلك، فإن النقطة الحقيقية هنا هي استكشاف تقنيات التحليل الجيدة، و PCM يجعلنا نرغب في تجربة نهج أكثر كفاءة. دعنا نجرب طريقة أخرى...

calculator2.pl - خوارزمية ساحة التفريغ (Shunting Yard Algorithm)

طريقة قديمة لتحليل التعابير هي الحصول بطريقة ما على الأرقام والمعاملات في مكدس RPN (Reverse Polish Notation)، والذي يكون كل معامل يتبعه عامله. بمجرد أن تكون في هذا الشكل، يتم حساب الأسبقية والارتباط.

على سبيل المثال:

1 / 2 - ( -3 * 4 )

يصبح:

1, 2, /, -3, 4, *, -

لتقييم RPN، قم بإخراج معامل ثم حاول إخراج معامل. إذا كان المعامل معاملًا آخر، فاستدعِ نفسك. عندما يكون لديك معاملان، قم بالعملية وقم بإعادة النتيجة إلى المكدس. عندما يكون هناك عنصر واحد فقط في المكدس، تكون قد انتهيت. هذه هي نتيجتك.

دعنا نلقي نظرة على قواعدنا الجديدة في "calculator2.pl":

expr: operand (operator operand)*
operator: /- (['+-*/^'])/
operand: num | /- '('/ expr /- ')'/
num: /- ('-'? DIGIT+)/

هذا أسهل بكثير للفهم. نحن فقط نحلل الرموز. بمعنى حقيقي (وحقيقي جدًا)، نستخدم Pegex كماسح.

الآن دعنا نلقي نظرة على فئة المستلم:

{
    package Calculator;
    use base 'Pegex::Tree', 'Precedence';
    my $operator_precedence_table = {
        '+' => {p => 1, a => 'l'},
        '-' => {p => 1, a => 'l'},
        '*' => {p => 2, a => 'l'},
        '/' => {p => 2, a => 'l'},
        '^' => {p => 3, a => 'r'},
    };
    sub got_expr {
        my ($self, $expr) = @_;
        $self->precedence_rpn($expr, $operator_precedence_table);
    }
}

هذا أيضًا أبسط بكثير. هناك طريقة واحدة فقط. ما الذي يحدث؟ حسنًا ، السر هو أنني وضعت الكود لتحويل الرموز إلى RPN في فئة أساسية منفصلة تسمى "lib/Precedence.pm" في المثال.

هذا تطبيق لخوارزمية Shunting-yard الشهيرة لإدجسر دايكسترا من عام 1961! إنها مجرد 20 سطرًا من Perl. لن أدرجها هنا، ولكن ألقِ نظرة عليها بنفسك. https://github.com/ingydotnet/pegex-pm/blob/master/eg/calculator/lib/Precedence.pm

تقوم خوارزمية Shunting-yard ببساطة بأخذ قائمة رموز التعبير وتحولها إلى مكدس RPN. تستخدم معلومات من جدول الأسبقية / الارتباط مثل المذكور أعلاه.

على عكس calculator1.pl حيث قمنا بالتقييم أثناء التحليل، فإن calculator2.pl ينشئ RPN الذي يشبه AST. بعبارة أخرى، إنه أشبه بشيء سيقوم به لغة فعلية

The Problem

The pegex parser will produce a Pegex AST. We still need to evaluate this expression. A simple grammar producing an AST might look something like this:

    use Pegex;
    my $grammar = q{
        # Grammar
        TOP     = expr
        expr    = term ((\+|-) term)*
        term    = factor ((\*|\/) factor)*
        factor  = NUMBER | '(' expr ')'
        NUMBER  = @{ qr/[0-9]+/ }
    };
    my $calculator = pegex($grammar, 'TOP');
    my $ast = $calculator->parse('1 + 2 * 3');
    # AST would be:
    # TOP
    #   expr
    #     term
    #       factor
    #         NUMBER: 1
    #     +: +
    #     term
    #       factor
    #         NUMBER: 2
    #       *: *
    #       factor
    #         NUMBER: 3

This AST is nice, but not executable. If we were writing a compiler, we would now write code to traverse the AST and generate machine code or bytecode. But we are writing a calculator and we still need to evaluate this puppy. I changed the runner code to look like this:

sub calc {
    my $expr = shift;
    my $calculator = pegex($grammar, 'Calculator');
    my $rpn = eval { $calculator->parse($expr) };
    my $result = RPN::evaluate($rpn);
    print $@ || "$expr = $result\n";
}

So overall, this second solution was a bit more code, but also feels more solid on several levels.

Conclusion

Pegex strives to be the nicest and most reusable way to write new parsers. Operator precedence parsers are a necessary part of parsing mathematical expressions and computer languages. This tutorial showed you 2 ways to do it. As the demands for Pegex grow, we may see even more ways to do it.
