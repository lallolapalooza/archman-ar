\n

PgBouncer internally examines all the queries that are sent as a prepared statement by clients and gives each unique query string an internal name with the format PGBOUNCER_{unique_id}. If the same query string is prepared multiple times (possibly by different clients), then these queries share the same internal name. PgBouncer keeps track of the name that the client gave to each prepared statement. 200 x 5kB + 1000 x 4 x 4kB = ~17MB of memory.

so_reuseport

يحدد ما إذا كان سيتم تعيين خيار المقبس SO_REUSEPORT على مقابس الاستماع TCP. على بعض أنظمة التشغيل، يسمح هذا بتشغيل عدة مثيلات PgBouncer على نفس المضيف والاستماع على نفس المنفذ وجعل النواة توزع الاتصالات تلقائيًا. هذا الخيار هو وسيلة لجعل PgBouncer يستخدم المزيد من أنوية وحدة المعالجة المركزية. (PgBouncer أحادي الخيط ويستخدم نواة CPU واحدة لكل مثيل.)

يعتمد السلوك بالتفصيل على نواة نظام التشغيل. حتى وقت كتابة هذه السطور، كان لهذا الإعداد التأثير المطلوب على (إصدارات حديثة بما فيه الكفاية من) Linux و DragonFlyBSD و FreeBSD. (على FreeBSD، يتم تطبيق خيار المقبس SO_REUSEPORT_LB بدلاً من ذلك.) تدعم بعض أنظمة التشغيل الأخرى خيار المقبس ولكنه لن يكون له التأثير المطلوب: سيسمح لعدة عمليات بالارتباط بنفس المنفذ ولكن سيحصل واحد فقط منها على الاتصالات. راجع وثائق setsockopt() الخاصة بنظام التشغيل الخاص بك للحصول على التفاصيل.

على الأنظمة التي لا تدعم خيار المقبس على الإطلاق، سيؤدي تشغيل هذا الإعداد إلى حدوث خطأ.

يحتاج كل مثيل PgBouncer على نفس المضيف إلى إعدادات مختلفة على الأقل لـ unix_socket_dir و pidfile، وكذلك logfile إذا تم استخدامه. لاحظ أيضًا أنه إذا استفدت من هذا الخيار، فلن تتمكن بعد الآن من الاتصال بمثيل PgBouncer معين عبر TCP / IP، مما قد يكون له آثار على المراقبة وجمع المقاييس.

للتأكد من أن عمليات إلغاء الاستعلامات تظل تعمل، يجب عليك إعداد تطابق PgBouncer بين عمليات PgBouncer المختلفة. للحصول على التفاصيل، ابحث عن الوثائق الخاصة بخيار تكوين peer_id وقسم تكوين peers. هناك أيضًا مثال يستخدم المطابقة و so_reuseport في قسم الأمثلة في هذه الوثائق.

الافتراضي: 0

القسم [DATABASES]

يحدد القسم [databases] أسماء قواعد البيانات التي يمكن للعملاء من PgBouncer الاتصال بها ويحدد أين سيتم توجيه تلك الاتصالات. يحتوي القسم على أسطر مفتاح=قيمة مثل

dbname = سلسلة الاتصال

حيث يتم أخذ المفتاح كاسم قاعدة بيانات والقيمة كسلسلة اتصال، تتكون من أزواج مفتاح=قيمة من معلمات الاتصال، كما هو موضح أدناه (على غرار libpq، ولكن libpq الفعلي لا يتم استخدامه ومجموعة الميزات المتاحة مختلفة). مثال:

foodb = host=host1.example.com port=5432
bardb = host=localhost dbname=bazdb

يمكن أن يحتوي اسم قاعدة البيانات على الأحرف _0-9A-Za-z بدون اقتباس. الأسماء التي تحتوي على أحرف أخرى تحتاج إلى اقتباس باستخدام اقتباس معرف SQL القياسي: علامتي اقتباس مزدوجتين، مع "" لنسخة واحدة من علامة اقتباس مزدوجة.

اسم قاعدة البيانات "pgbouncer" محجوز لواجهة التحكم الإدارية ولا يمكن استخدامه كمفتاح هنا.

يعمل "*" كقاعدة بيانات احتياطية: إذا لم يكن الاسم الدقيق موجودًا، فإن قيمته تؤخذ كسلسلة اتصال لقاعدة البيانات المطلوبة. على سبيل المثال، إذا كان هناك إدخال (ولم تكن هناك إدخالات أخرى متجاوزة)

* = host=foo

ثم سيتم التعامل مع اتصال بـ PgBouncer يحدد قاعدة بيانات "bar" فعليًا كما لو كان هناك إدخال

bar = host=foo dbname=bar

موجود (مستفيدًا من القيمة الافتراضية لـ dbname كونها اسم قاعدة البيانات من جانب العميل؛ انظر أدناه).

سيتم تنظيف إدخالات قاعدة البيانات التي تم إنشاؤها تلقائيًا بهذه الطريقة إذا بقيت خاملة لفترة أطول من الوقت المحدد بواسطة المعلمة autodb_idle_timeout.

dbname

قاعدة البيانات الوجهة.

الافتراضي: نفس اسم قاعدة البيانات من جانب العميل

host

اسم المضيف أو عنوان IP للاتصال به. يتم حل أسماء المضيفين في وقت الاتصال، ويتم تخزين النتيجة مؤقتًا لكل معلمة dns_max_ttl. عند تغيير حل اسم المضيف، يتم إغلاق اتصالات الخادم الموجودة تلقائيًا عند تحريرها (وفقًا لوضع التجميع)، وتستخدم اتصالات الخادم الجديدة على الفور الحل الجديد. إذا أعادت DNS عدة نتائج، فسيتم استخدامها بطريقة التناوب. (إذا كانت قائمة المضيفين تحتوي على أسماء مضيفين تحل بدورها عبر DNS إلى عناوين متعددة، فإن أنظمة التناوب تعمل بشكل مستقل. هذا تبعية تطبيق تخضع للتغيير.)

إذا بدأ القيمة بـ /، فسيتم استخدام مقبس Unix في مساحة اسم نظام الملفات. إذا بدأت القيمة بـ @، فسيتم استخدام مقبس Unix في مساحة الاسم المجردة.

يمكن تحديد قائمة مفصولة بفواصل بأسماء مضيفين أو عناوين. في هذه الحالة، تتم الاتصالات بطريقة التناوب. لاحظ أنه في القائمة، يجب أن تكون جميع المضيفات متاحة

NAME

pgbouncer.ini, users.txt, pg_hba.conf - configuration file formats

DESCRIPTION

This manual page describes the file formats used by PgBouncer.

The main configuration file is pgbouncer.ini. Additional configuration files can be used for user authentication and client connection control.

MAIN CONFIG FILE

The main configuration file is typically located at /etc/pgbouncer/pgbouncer.ini, but its location can be specified by the config_file parameter at runtime.

The file is divided into sections, each denoted by a name in square brackets, e.g. [databases]. Section names are case-insensitive.

Within each section, configuration parameters are specified as key = value pairs. Parameters are case-insensitive. Comments start with a semicolon (;) and continue to the end of the line.

GENERIC SETTINGS

logfile
Path to log file. Defaults to stderr.
pidfile
Path to PID file. Defaults to /var/run/pgbouncer.pid.
admin_users
List of users that have administrative privileges. Defaults to pgbouncer.
stats_users
List of users that can view statistics. Defaults to pgbouncer.

AUTHENTICATION SETTINGS

auth_type
Authentication method. Supported values are:
md5: User password is MD5-hashed. Requires auth_file or auth_query.
plain: User password is in plain text. Requires auth_file or auth_query.
scram-sha-256: User password is stored in SCRAM-SHA-256 format. Requires auth_file or auth_query.
hba: Use PostgreSQL's pg_hba.conf-style authentication. Requires auth_hba_file.
peer: User name is taken from the operating system.
cert: Use SSL client certificates for authentication.
any: Allow any user to connect without a password.
auth_file
Path to the authentication file. Used when auth_type is md5, plain, or scram-sha-256.
auth_query
SQL query to perform user lookup. Used when auth_type is md5, plain, or scram-sha-256. The query should return a single row with two columns: user name and password hash. The user name column should match the username passed to the query.
auth_hba_file
Path to the HBA file. Used when auth_type is hba.

LOG SETTINGS

log_connections
Whether to log new connections. Defaults to 0 (no).
log_disconnections
Whether to log disconnections. Defaults to 0 (no).
log_pooler_errors
Whether to log pooler errors. Defaults to 1 (yes).
log_timestamp
Format for log timestamps. Supported values: 0 (off), 1 (start of line), 2 (start of line, with timezone), 3 (unix epoch milliseconds).

CONSOLE ACCESS CONTROL

admin_users
List of users allowed to access the console. Defaults to pgbouncer.
stats_users
List of users allowed to view statistics via the console. Defaults to pgbouncer.

CONNECTION SANITY CHECKS, TIMEOUTS

server_reset_query
Query to run when a server connection is reset. Defaults to DISCARD ALL.
server_check_query
Query to check if a server connection is still alive. Defaults to SELECT 1.
server_idle_timeout
Maximum time a server connection can be idle. Defaults to 60 seconds.
server_lifetime
Maximum time a server connection can live. Defaults to 3600 seconds.
connection_pool_timeout
Maximum time a client connection can wait for a server connection. Defaults to 60 seconds.

TLS SETTINGS

tls_cert_file
Path to the server certificate file.
tls_key_file
Path to the server private key file.
tls_ca_file
Path to the CA certificate file.
tls_protocols
Allowed TLS protocols. Defaults to 2 (TLSv1.2).
tls_ciphers
Allowed TLS ciphers.

DANGEROUS TIMEOUTS

These parameters can be used to tune performance, but can also cause data loss or other problems if set incorrectly.

client_idle_timeout
Maximum time a client connection can be idle. Defaults to 300 seconds.
client_login_timeout
Maximum time a client can take to log in. Defaults to 10 seconds.
client_max_lifetime
Maximum time a client connection can live. Defaults to 3600 seconds.
backend_connection_timeout
Timeout for connecting to backend server. Defaults to 10 seconds.

LOW-LEVEL NETWORK SETTINGS

listen_addr
Address to listen on. Defaults to * (all interfaces).
listen_port
Port to listen on. Defaults to 5432.
unix_socket_dir
Directory for Unix domain sockets. Defaults to /tmp.
so_reuseport
Enable SO_REUSEPORT socket option. Defaults to 0 (no).

SECTION [DATABASES]

This section defines the databases that PgBouncer will connect to.

Each entry in this section defines a database that clients can connect to. The key is the database name that clients will use, and the value is a connection string describing how to connect to the actual PostgreSQL server.

Connection string parameters are separated by spaces. Supported parameters include:

host
Host name of the PostgreSQL server.
port
Port number of the PostgreSQL server. Defaults to 5432.
dbname
Name of the database on the PostgreSQL server.
user
Username to use when connecting to the PostgreSQL server.
password
Password to use when connecting to the PostgreSQL server.
auth_user
Username to use for authentication. If not specified, user is used.
client_encoding
Client encoding.
datestyle
Date style.

Example:

[databases]
template1 = host=localhost dbname=template1
myappdb = host=db.example.com port=5433 dbname=myapp user=appuser password=secret

SECTION [USERS]

This section defines the users that can connect to PgBouncer.

Each entry in this section defines a user. The key is the username, and the value is the password. The password format depends on the auth_type setting.

Example:

[users]
testuser = trust
anotheruser = md5a1b2c3d4e5f67890

SECTION [PEERS]

This section defines other PgBouncer instances that this instance will connect to.

Each entry in this section defines a peer. The key is a unique identifier for the peer, and the value is a connection string.

Example:

[peers]
peer1 = host=/var/run/pgbouncer/pgbouncer-peer1.sock
peer2 = host=192.168.1.100 port=6433

INCLUDE DIRECTIVE

The include directive can be used to include other configuration files. This is useful for organizing large configuration files.

Example:

include = /etc/pgbouncer/users.d/*.ini

AUTHENTICATION FILE FORMAT

The authentication file is a plain text file with one user per line.

Each line has the following format:

<user>:<password>[:<database>]

The database field is optional. If specified, the user can only log in to that specific database.

The password can be in plain text or MD5-hashed.

Example for plain text password:

user1:password
user2:anotherpassword:mydb

Example for MD5-hashed password:

If you have MD5-hashed password, like:

you'll have MD5-hashed password

md545f2603610af569b6155c45067268c6b.

PostgreSQL SCRAM secret format:

SCRAM-SHA-256$<iterations>:<salt>$<storedkey>:<serverkey>

See the PostgreSQL documentation and RFC 5803 for details on this.

The passwords or secrets stored in the authentication file serve two purposes. First, they are used to verify the passwords of incoming client connections, if a password-based authentication method is configured. Second, they are used as the passwords for outgoing connections to the backend server, if the backend server requires password-based authentication (unless the password is specified directly in the database’s connection string). The latter works if the password is stored in plain text or MD5-hashed. SCRAM secrets can only be used for logging into a server if the client authentication also uses SCRAM, the PgBouncer database definition does not specify a user name, and the SCRAM secrets are identical in PgBouncer and the PostgreSQL server (same salt and iterations, not merely the same password). This is due to an inherent security property of SCRAM: The stored SCRAM secret cannot by itself be used for deriving login credentials.

The authentication file can be written by hand, but it’s also useful to generate it from some other list of users and passwords. See ./etc/mkauth.py for a sample script to generate the authentication file from the pg_shadow system table. Alternatively, use auth_query instead of auth_file to avoid having to maintain a separate authentication file.

HBA FILE FORMAT

The location of the HBA file is specified by the setting auth_hba_file. It is only used if auth_type is set to hba.

The file follows the format of the PostgreSQL pg_hba.conf file (see https://www.postgresql.org/docs/current/auth-pg-hba-conf.html).

•
Supported record types: local, host, hostssl, hostnossl.
•
Database field: Supports all, sameuser, @file, multiple names. Not supported: replication, samerole, samegroup.
•
User name field: Supports all, @file, multiple names. Not supported: +groupname.
•
Address field: Supports IPv4, IPv6. Not supported: DNS names, domain prefixes.
•
Auth-method field: Only methods supported by PgBouncer’s auth_type are supported, plus peer and reject, but except any and pam, which only work globally. User name map (map=) parameter is not supported.

EXAMPLES

Small example configuration:

[databases]
template1 = host=localhost dbname=template1 auth_user=someuser
[pgbouncer]
pool_mode = session
listen_port = 6432
listen_addr = localhost
auth_type = md5
auth_file = users.txt
logfile = pgbouncer.log
pidfile = pgbouncer.pid
admin_users = someuser
stats_users = stat_collector

Database examples:

[databases]
; foodb over Unix socket
foodb =
; redirect bardb to bazdb on localhost
bardb = host=localhost dbname=bazdb
; access to destination database will go with single user
forcedb = host=localhost port=300 user=baz password=foo client_encoding=UNICODE datestyle=ISO

Example of a secure function for auth_query:

CREATE OR REPLACE FUNCTION pgbouncer.user_lookup(in i_username text, out uname text, out phash text)
RETURNS record AS $$
BEGIN
    SELECT usename, passwd FROM pg_catalog.pg_shadow
    WHERE usename = i_username INTO uname, phash;
    RETURN;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;
REVOKE ALL ON FUNCTION pgbouncer.user_lookup(text) FROM public, pgbouncer;
GRANT EXECUTE ON FUNCTION pgbouncer.user_lookup(text) TO pgbouncer;

Example configs for 2 peered PgBouncer processes to create a multi-core PgBouncer setup using so_reuseport. The config for the first process:

[databases]
postgres = host=localhost dbname=postgres
[peers]
1 = host=/tmp/pgbouncer1
2 = host=/tmp/pgbouncer2
[pgbouncer]
listen_addr=127.0.0.1
auth_file=auth_file.conf
so_reuseport=1
unix_socket_dir=/tmp/pgbouncer1
peer_id=1

The config for the second process:

[databases]
postgres = host=localhost dbname=postgres
[peers]
1 = host=/tmp/pgbouncer1
2 = host=/tmp/pgbouncer2
[pgbouncer]
listen_addr=127.0.0.1
auth_file=auth_file.conf
so_reuseport=1
; only unix_socket_dir and peer_id are different
unix_socket_dir=/tmp/pgbouncer2
peer_id=2
