pgbench(1)

الحزمة: postgresql

التراخيص: PostgreSQL

SYNOPSIS

pgbench [connection-option...] [option...] [-M querymode] [-P progress] [-r] [-R rate] [-s scale_factor] [-t transactions | -T seconds] [--aggregate-interval=seconds] [--log-prefix=prefix] [--max-tries=number_of_tries] [--partitions=NUM] [--progress=sec] [--rate=rate] [--scale=scale_factor] [--transactions=transactions] [--time=seconds]

DESCRIPTION

pgbench is a benchmarking tool for PostgreSQL. It is supplied with a standard set of TPCB-like transactions, but it can also be driven by custom SQL scripts.

The primary purpose of pgbench is to provide a realistic workload that can be run against a PostgreSQL database, allowing you to determine how well it will perform under load. It can also be used to test the efficiency of the PostgreSQL query planner and optimizer.

pgbench operates by connecting to a PostgreSQL database and executing a series of SQL transactions. The number of clients, the number of transactions, and the type of transactions can all be configured.

Connection Options

The following command-line arguments control the PostgreSQL connection parameters:

-d dbname
--dbname=dbname

Specifies the database to connect to. Default is to use the database name specified in the PGDATABASE environment variable, or the user name if that is not set.

-h hostname
--host=hostname

Specifies the host name of the machine on which the server is running. If not specified, it uses the PGDATABASE environment variable or defaults to a local socket in most cases.

-p port
--port=port

Specifies the TCP port or local Unix domain socket file extension on which the server is listening for connections. Defaults to the PGPORT environment variable or the default compile-time port (usually 5432).

-U username
--username=username

User name to connect as.

-w
--password

Force a password prompt.

-W
--password-file=filename

Read password from the specified file.

--connect-timeout=seconds

Maximum time to wait for a connection attempt to succeed. Must be a non-negative number. If unspecified, the default is to wait indefinitely.

--ssl-mode=mode

Specifies the SSL connection mode. The default is prefer. Possible modes are disable, allow, prefer, require, verify-ca, verify-full.

Setup Options

The following command-line arguments control the setup of the database for benchmarking:

-i
--initialize

Initialize the database with the standard set of tables and data. This option must be used when running pgbench for the first time or when resetting the database to its initial state.

-F fillfactor
--fillfactor=fillfactor

Set the fillfactor for the tables. This is a percentage value between 10 and 100. Default is 90.

-p port
--port=port

Specifies the TCP port or local Unix domain socket file extension on which the server is listening for connections. Defaults to the PGPORT environment variable or the default compile-time port (usually 5432).

-s scale_factor
--scale=scale_factor

Sets the scale factor for the database size. The scale factor determines the number of rows in the tables. A scale factor of 1 creates approximately 1.2 million rows in the pgbench_accounts table. Default is 1.

-S
--script=script

Initialize the database with the specified script. This option overrides the default initialization.

-t transactions
--transactions=transactions

Number of transactions to execute for each client. Default is 10.

-T seconds
--time=seconds

Run the benchmark for the specified number of seconds. This option overrides the -t option.

-v
--vacuum

Perform a vacuum operation on the database before running the benchmark. This is recommended to ensure consistent performance results.

--init-sql=filename

Execute the SQL commands in the specified file after creating the standard tables.

--partitions=NUM

Create a partitioned pgbench_accounts table with NUM partitions of nearly equal size for the scaled number of accounts. Default is 0, meaning no partitioning.

--tablespace=tablespace

Create tables in the specified tablespace, rather than the default tablespace.

--unlogged-tables

Create all tables as unlogged tables, rather than permanent tables.

Benchmarking Options

pgbench accepts the following command-line benchmarking arguments:

-b scriptname[@weight]
--builtin=scriptname[@weight]

Add the specified built-in script to the list of scripts to be executed. Available built-in scripts are: tpcb-like, simple-update and select-only. Unambiguous prefixes of built-in names are accepted. With the special name list, show the list of built-in scripts and exit immediately.

Optionally, write an integer weight after @ to adjust the probability of selecting this script versus other ones. The default weight is 1. See below for details.

-c clients
--client=clients

Number of clients simulated, that is, number of concurrent database sessions. Default is 1.

-C
--connect

Establish a new connection for each transaction, rather than doing it just once per client session. This is useful to measure the connection overhead.

-D varname=value
--define=varname=value

Define a variable for use by a custom script (see below). Multiple -D options are allowed.

-f filename[@weight]
--file=filename[@weight]

Add a transaction script read from filename to the list of scripts to be executed.

Optionally, write an integer weight after @ to adjust the probability of selecting this script versus other ones. The default weight is 1. (To use a script file name that includes an @ character, append a weight so that there is no ambiguity, for example filen@me@1.) See below for details.

-j threads
--jobs=threads

Number of worker threads within pgbench. Using more than one thread can be helpful on multi-CPU machines. Clients are distributed as evenly as possible among available threads. Default is 1.

-l
--log

Write information about each transaction to a log file. See below for details.

-L limit
--latency-limit=limit

Transactions that last more than limit milliseconds are counted and reported separately, as late.

When throttling is used (--rate=...), transactions that lag behind schedule by more than limit ms, and thus have no hope of meeting the latency limit, are not sent to the server at all. They are counted and reported separately as skipped.

When the --max-tries option is used, a transaction which fails due to a serialization anomaly or from a deadlock will not be retried if the total time of all its tries is greater than limit ms. To limit only the time of tries and not their number, use --max-tries=0. By default, the option --max-tries is set to 1 and transactions with serialization/deadlock errors are not retried. See Failures and Serialization/Deadlock Retries for more information about retrying such transactions.

-M querymode
--protocol=querymode

Protocol to use for submitting queries to the server:
•simple: use simple query protocol.
•extended: use extended query protocol.
•prepared: use extended query protocol with prepared statements.

In the prepared mode, pgbench reuses the parse analysis result starting from the second query iteration, so pgbench runs faster than in other modes.

The default is simple query protocol. (See Chapter 54 for more information.)

-n
--no-vacuum

Perform no vacuuming before running the test. This option is necessary if you are running a custom test scenario that does not include the standard tables pgbench_accounts, pgbench_branches, pgbench_history, and pgbench_tellers.

-N
--skip-some-updates

Run built-in simple-update script. Shorthand for -b simple-update.

-P sec
--progress=sec

Show progress report every sec seconds. The report includes the time since the beginning of the run, the TPS since the last report, and the transaction latency average, standard deviation, and the number of failed transactions since the last report. Under throttling (-R), the latency is computed with respect to the transaction scheduled start time, not the actual transaction beginning time, thus it also includes the average schedule lag time. When --max-tries is used to enable transaction retries after serialization/deadlock errors, the report includes the number of retried transactions and the sum of all retries.

-r
--report-per-command

Report the following statistics for each command after the benchmark finishes: the average per-statement latency (execution time from the perspective of the client), the number of failures, and the number of retries after serialization or deadlock errors in this command. The report displays retry statistics only if the --max-tries option is not equal to 1.

-R rate
--rate=rate

Execute transactions targeting the specified rate instead of running as fast as possible (the default). The rate is given in transactions per second. If the targeted rate is above the maximum possible rate, the rate limit won't impact the results.

The rate is targeted by starting transactions along a Poisson-distributed schedule time line. The expected start time schedule moves forward based on when the client first started, not when the previous transaction ended. That approach means that when transactions go past their original scheduled end time, it is possible for later ones to catch up again.

When throttling is active, the transaction latency reported at the end of the run is calculated from the scheduled start times, so it includes the time each transaction had to wait for the previous transaction to finish. The wait time is called the schedule lag time, and its average and maximum are also reported separately. The transaction latency with respect to the actual transaction start time, i.e., the time spent executing the transaction in the database, can be computed by subtracting the schedule lag time from the reported latency.

If --latency-limit is used together with --rate, a transaction can lag behind so much that it is already over the latency limit when the previous transaction ends, because the latency is calculated from the scheduled start time. Such transactions are not sent to the server, but are skipped altogether and counted separately.

A high schedule lag time is an indication that the system cannot process transactions at the specified rate, with the chosen number of clients and threads. When the average transaction execution time is longer than the scheduled interval between each transaction, each successive transaction will fall further behind, and the schedule lag time will keep increasing the longer the test run is. When that happens, you will have to reduce the specified transaction rate.

-s scale_factor
--scale=scale_factor

Report the specified scale factor in pgbench's output. With the built-in tests, this is not necessary; the correct scale factor will be detected by counting the number of rows in the pgbench_branches table. However, when testing only custom benchmarks (-f option), the scale factor will be reported as 1 unless this option is used.

-S
--select-only

Run built-in select-only script. Shorthand for -b select-only.

-t transactions
--transactions=transactions

Number of transactions each client runs. Default is 10.

-T seconds
--time=seconds

Run the test for this many seconds, rather than a fixed number of transactions per client. -t and -T are mutually exclusive.

-v
--vacuum-all

Vacuum all four standard tables before running the test. With neither -n nor -v, pgbench will vacuum the pgbench_tellers and pgbench_branches tables, and will truncate pgbench_history.

--aggregate-interval=seconds

Length of aggregation interval (in seconds). May be used only with -l option. With this option, the log contains per-interval summary data, as described below.

--exit-on-abort

Exit immediately when any client is aborted due to some error. Without this option, even when a client is aborted, other clients could continue their run as specified by -t or -T option, and pgbench will print an incomplete results in this case.

Note that serialization failures or deadlock failures do not abort the client, so they are not affected by this option. See Failures and Serialization/Deadlock Retries for more information.

--failures-detailed

Report failures in per-transaction and aggregation logs, as well as in the main and per-script reports, grouped by the following types:
•serialization failures;
•deadlock failures;

See Failures and Serialization/Deadlock Retries for more information.

--log-prefix=prefix

Set the filename prefix for the log files created by --log. The default is pgbench_log.

--max-tries=number_of_tries

Enable retries for transactions with serialization/deadlock errors and set the maximum number of these tries. تسجيل مجمع

مع الخيار --aggregate-interval، يتم استخدام تنسيق مختلف لملفات السجل. يصف كل سطر سجل فترة تجميع واحدة. يحتوي على الحقول التالية المفصولة بمسافات:

interval_start

وقت بدء الفترة، كطابع زمني لنظام Unix

num_transactions

عدد المعاملات خلال الفترة

sum_latency

مجموع زمن استجابة المعاملات

sum_latency_2

مجموع مربعات زمن استجابة المعاملات

min_latency

أقل زمن استجابة للمعاملات

max_latency

أقصى زمن استجابة للمعاملات

sum_lag

مجموع تأخيرات بدء المعاملات (صفر ما لم يتم تحديد --rate)

sum_lag_2

مجموع مربعات تأخيرات بدء المعاملات (صفر ما لم يتم تحديد --rate)

min_lag

max_lag

تقرير لكل بيان

باستخدام الخيار -r، تجمع pgbench الإحصائيات التالية لكل بيان:

•زمن الاستجابة — الوقت المنقضي للمعاملة لكل بيان. تُبلغ pgbench عن متوسط قيمة لجميع عمليات التشغيل الناجحة للبيان.
•عدد حالات الفشل في هذا البيان. انظر حالات الفشل ومحاولات المعاودة للتسلسل/الجمود لمزيد من المعلومات.
•عدد محاولات المعاودة بعد خطأ تسلسل أو جمود في هذا البيان. انظر حالات الفشل ومحاولات المعاودة للتسلسل/الجمود لمزيد من المعلومات.

يعرض التقرير إحصائيات المعاودة فقط إذا كان الخيار --max-tries لا يساوي 1.

حالات الفشل ومحاولات المعاودة للتسلسل/الجمود

عند تنفيذ pgbench، هناك ثلاثة أنواع رئيسية من الأخطاء:

•أخطاء البرنامج الرئيسي. وهي الأكثر خطورة وتؤدي دائمًا إلى خروج فوري من pgbench مع رسالة الخطأ المقابلة. وتشمل:
•أخطاء في بداية pgbench (على سبيل المثال، قيمة خيار غير صالحة)؛
•أخطاء في وضع التهيئة (على سبيل المثال، يفشل الاستعلام لإنشاء جداول للبرامج النصية المضمنة)؛
•أخطاء قبل بدء سلاسل العمل (على سبيل المثال، تعذر الاتصال بخادم قاعدة البيانات، خطأ في بناء الجملة في الأمر الوصف، فشل إنشاء السلسلة)؛
•أخطاء pgbench الداخلية (والتي يُفترض ألا تحدث أبدًا...).
•أخطاء عندما تدير السلسلة عملائها (على سبيل المثال، لم يتمكن العميل من بدء اتصال بخادم قاعدة البيانات / أصبح المقبس لربط العميل بخادم قاعدة البيانات غير صالح). في مثل هذه الحالات، تتوقف جميع عملاء هذه السلسلة بينما تستمر السلاسل الأخرى في العمل. ومع ذلك، إذا تم تحديد --exit-on-abort، فإن جميع السلاسل تتوقف على الفور في هذه الحالة.
•أخطاء العميل المباشرة. تؤدي إلى خروج فوري من pgbench مع رسالة الخطأ المقابلة في حالة وجود خطأ داخلي في pgbench (والذي يُفترض ألا يحدث أبدًا...) أو عند تحديد --exit-on-abort. بخلاف ذلك، في أسوأ الحالات، تؤدي فقط إلى إنهاء العميل الفاشل بينما تستمر العملاء الآخرون في التشغيل (ولكن يتم التعامل مع بعض أخطاء العميل دون إنهاء العميل والإبلاغ عنها بشكل منفصل، انظر أدناه). في وقت لاحق في هذا القسم، يُفترض أن الأخطاء التي تمت مناقشتها هي فقط أخطاء العميل المباشرة وهي ليست أخطاء pgbench داخلية.

يتم إنهاء تشغيل العميل في حالة وجود خطأ جسيم؛ على سبيل المثال، فقد الاتصال بخادم قاعدة البيانات أو تم الوصول إلى نهاية البرنامج النصي دون إكمال المعاملة الأخيرة. بالإضافة إلى ذلك، إذا فشل تنفيذ أمر SQL أو أمر وصفي لأسباب غير أخطاء التسلسل أو الجمود، يتم إنهاء العميل. بخلاف ذلك، إذا فشل أمر SQL مع أخطاء التسلسل أو الجمود، لا يتم إنهاء العميل. في مثل هذه الحالات، يتم التراجع عن المعاملة الحالية، والتي تتضمن أيضًا تعيين متغيرات العميل كما كانت قبل تشغيل هذه المعاملة (يُفترض أن نص المعاملة يحتوي على معاملة واحدة فقط؛ انظر ما هي "المعاملة" التي يتم تنفيذها فعليًا في pgbench؟ لمزيد من المعلومات). تتم معاودة المعاملات التي بها أخطاء تسلسل أو جمود بعد التراجعات حتى تكتمل بنجاح أو تصل إلى الحد الأقصى لعدد المحاولات (المحدد بواسطة الخيار --max-tries) /

الحد الأقصى لوقت إعادة المحاولة (محدد بواسطة الخيار --latency-limit) / نهاية القياس (محددة بالخيار --time). إذا فشلت آخر محاولة تشغيل، فسيتم الإبلاغ عن هذه المعاملة على أنها فاشلة ولكن العميل لا يتم إنهاؤه ويستمر في العمل.


ملاحظة

بدون تحديد الخيار --max-tries، لن تتم إعادة محاولة المعاملة أبدًا بعد خطأ تسلسل أو تعارض لأنه القيمة الافتراضية هي 1. استخدم عددًا غير محدود من المحاولات (--max-tries=0) والخيار --latency-limit لتحديد الحد الأقصى لوقت المحاولات فقط. يمكنك أيضًا استخدام الخيار --time لتحديد مدة القياس تحت عدد غير محدود من المحاولات.

كن حذرًا عند تكرار البرامج النصية التي تحتوي على معاملات متعددة: يتم دائمًا إعادة محاولة البرنامج النصي بالكامل، لذلك يمكن تنفيذ المعاملات الناجحة عدة مرات.

كن حذرًا عند تكرار المعاملات باستخدام أوامر shell. على عكس نتائج أوامر SQL، لا يتم التراجع عن نتائج أوامر shell، باستثناء القيمة المتغيرة لأمر \setshell.

يشمل زمن الوصول للمعاملة الناجحة كامل وقت تنفيذ المعاملة مع التراجعات وإعادة المحاولات. يتم قياس زمن الوصول فقط للمعاملات والأوامر الناجحة ولكن ليس للمعاملات أو الأوامر الفاشلة.

يحتوي التقرير الرئيسي على عدد المعاملات الفاشلة. إذا لم يكن الخيار --max-tries يساوي 1، فإن التقرير الرئيسي يحتوي أيضًا على إحصائيات متعلقة بإعادة المحاولات: العدد الإجمالي للمعاملات التي تمت إعادة محاولةها والعدد الإجمالي لإعادة المحاولات. يكتسب تقرير البرنامج النصي لكل جزء جميع هذه الحقول من التقرير الرئيسي. يعرض تقرير كل عبارة إحصائيات إعادة المحاولة فقط إذا كان الخيار --max-tries لا يساوي 1.

إذا كنت ترغب في تجميع حالات الفشل حسب الأنواع الأساسية في سجلات المعاملات والتجميع، وكذلك في التقارير الرئيسية وتقارير البرامج النصية، فاستخدم الخيار --failures-detailed. إذا كنت ترغب أيضًا في تمييز جميع الأخطاء وحالات الفشل (الأخطاء دون إعادة المحاولة) حسب النوع بما في ذلك أي حد لإعادة المحاولات تم تجاوزه وكم تم تجاوزه بالنسبة لأخطاء التسلسل/التعارض، فاستخدم الخيار --verbose-errors.

أساليب الوصول إلى الجداول

يمكنك تحديد طريقة الوصول إلى الجدول للجداول التي أنشأها pgbench. تحدد متغير البيئة PGOPTIONS خيارات تكوين قاعدة البيانات التي يتم تمريرها إلى PostgreSQL عبر سطر الأوامر (انظر القسم 19.1.4). على سبيل المثال، يمكن تحديد طريقة وصول افتراضية افتراضية للجداول التي ينشئها pgbench تسمى wuzza باستخدام:

PGOPTIONS='-c default_table_access_method=wuzza'

ممارسات جيدة

من السهل جدًا استخدام pgbench لإنتاج أرقام لا معنى لها تمامًا. فيما يلي بعض الإرشادات للمساعدة في الحصول على نتائج مفيدة.

أولاً وقبل كل شيء، * لا تصدق * أبدًا أي اختبار يستمر لبضع ثوانٍ فقط. استخدم الخيار -t أو -T لجعل التشغيل يستمر لبضع دقائق على الأقل، وذلك للتوسط في الضوضاء. في بعض الحالات، قد تحتاج إلى ساعات للحصول على أرقام قابلة للتكرار. من الجيد تجربة تشغيل الاختبار عدة مرات، لمعرفة ما إذا كانت أرقامك قابلة للتكرار أم لا.

بالنسبة لسيناريو الاختبار الافتراضي الشبيه بـ TPC-B، يجب أن يكون عامل القياس الأولي (-s) على الأقل بنفس حجم أكبر عدد من العملاء الذين تنوي اختبارهم (-c)؛ وإلا فإنك ستقيس في الغالب تضارب التحديث. هناك فقط -s صفوف في جدول pgbench_branches، وكل معاملة تريد تحديث أحدها، لذلك فإن قيم -c التي تتجاوز -s ستؤدي بلا شك إلى العديد من المعاملات المحظورة في انتظار معاملات أخرى.

سيناريو الاختبار الافتراضي حساس أيضًا لمدى الوقت الذي مر منذ تهيئة الجداول: تراكم الصفوف الفارغة والمساحة الفارغة في الجداول يغير النتائج. لفهم النتائج، يجب عليك تتبع العدد الإجمالي للتحديثات ومتى يحدث التنظيف. إذا تم تمكين autovacuum، فقد يؤدي ذلك إلى تغييرات غير متوقعة في الأداء المقاس.

أحد قيود pgbench هو أنه يمكن أن يصبح هو نفسه عنق الزجاجة عند محاولة اختبار عدد كبير من جلسات العملاء. يمكن تخفيف ذلك عن طريق تشغيل pgbench على جهاز مختلف عن خادم قاعدة البيانات، على الرغم من أن زمن الوصول المنخفض للشبكة سيكون ضروريًا. قد يكون من المفيد حتى تشغيل عدة مثيلات pgbench بشكل متزامن، على عدة أجهزة عملاء، ضد نفس خادم قاعدة البيانات.

الأمان

إذا كان لدى المستخدمين غير الموثوق بهم إمكانية الوصول إلى قاعدة بيانات لم تتبنى نمط استخدام مخطط آمن، فلا تقم بتشغيل pgbench في تلك القاعدة البيانات. يستخدم pgbench أسماء غير مؤهلة ولا يتلاعب بمسار البحث.
