pt-online-schema-change(1p)

الحزمة: percona-toolkit

التراخيص: GPL

PT-ONLINE-SCHEMA-CHANGE(1) توثيق Perl مساهم به من المستخدم PT-ONLINE-SCHEMA-CHANGE(1)

الاسم

pt-online-schema-change - تعديل جداول MySQL دون قفلها.

الملخص

الاستخدام: pt-online-schema-change [خيارات] DSN

يقوم pt-online-schema-change بتغيير بنية الجدول دون حظر القراءات أو الكتابات. حدد قاعدة البيانات والجدول في DSN. لا تستخدم هذه الأداة قبل قراءة توثيقها والتحقق من نسخك الاحتياطية بعناية.

إضافة عمود إلى sakila.actor:

pt-online-schema-change --alter "ADD COLUMN c1 INT" D=sakila,t=actor

تغيير sakila.actor إلى InnoDB، وتنفيذ OPTIMIZE TABLE بشكل غير حاجب للقراءة لأنه بالفعل جدول InnoDB:

pt-online-schema-change --alter "ENGINE=InnoDB" D=sakila,t=actor

المخاطر

Percona Toolkit ناضجة، مثبتة في العالم الواقعي، وتم اختبارها جيدًا، ولكن جميع أدوات قواعد البيانات يمكن أن تشكل خطرًا على النظام وخادم قاعدة البيانات. قبل استخدام هذه الأداة، يرجى:

  • قراءة توثيق الأداة
  • مراجعة "الأخطاء" المعروفة للأداة
  • اختبار الأداة على خادم غير إنتاجي
  • نسخ خادم الإنتاج احتياطيًا والتحقق من النسخ الاحتياطية

الوصف

يحاكي pt-online-schema-change الطريقة التي تقوم بها MySQL بتغيير الجداول داخليًا، ولكنه يعمل على نسخة من الجدول الذي ترغب في تغييره. هذا يعني أن الجدول الأصلي لا يتم قفله، وقد يستمر العملاء في قراءة البيانات وتغييرها فيه.

يعمل pt-online-schema-change عن طريق إنشاء نسخة فارغة من الجدول المراد تغييره، وتعديلها حسب الرغبة، ثم نسخ الصفوف من الجدول الأصلي إلى الجدول الجديد. عند اكتمال النسخ، يتم إزاحة الجدول الأصلي واستبداله بالجدول الجديد. بشكل افتراضي، يقوم أيضًا بإسقاط الجدول الأصلي.

تتم عملية نسخ البيانات على دفعات صغيرة من البيانات، والتي يتم تغيير حجمها لمحاولة تنفيذها في فترة زمنية محددة (انظر "--chunk-time"). هذه العملية تشبه إلى حد كبير كيفية عمل الأدوات الأخرى، مثل pt-table-checksum. أي تعديلات على البيانات في الجداول الأصلية أثناء النسخ ستنعكس في الجدول الجديد، لأن الأداة تنشئ مشغلات (triggers) على الجدول الأصلي لتحديث الصفوف المقابلة في الجدول الجديد. استخدام المشغلات يعني أن الأداة لن تعمل إذا كانت هناك أي مشغلات معرفة بالفعل على الجدول.

عندما تنتهي الأداة من نسخ البيانات إلى الجدول الجديد، فإنها تستخدم عملية "RENAME TABLE" ذرية لإعادة تسمية الجدول الأصلي والجديد في وقت واحد. بعد اكتمال ذلك، تقوم الأداة بإسقاط الجدول الأصلي.

تزيد المفاتيح الخارجية (Foreign keys) من تعقيد عملية الأداة وتضيف مخاطر إضافية. تقنية إعادة تسمية الجدول الأصلي والجديد بشكل ذري لا تعمل عندما تشير المفاتيح الخارجية إلى الجدول. يجب على الأداة تحديث المفاتيح الخارجية للإشارة إلى الجدول الجديد بعد اكتمال تغيير المخطط. تدعم الأداة طريقتين لتحقيق ذلك. يمكنك قراءة المزيد حول ذلك في توثيق "--alter-foreign-keys-method".

تسبب المفاتيح الخارجية أيضًا بعض الآثار الجانبية. سيكون للجدول النهائي نفس المفاتيح الخارجية والفهارس مثل الجدول الأصلي (ما لم تحدد خلاف ذلك في بيان ALTER الخاص بك)، ولكن قد يتم تغيير أسماء الكائنات قليلاً لتجنب تضارب أسماء الكائنات في MySQL و InnoDB.

للأمان، لا تقوم الأداة بتعديل الجدول ما لم تحدد خيار "--execute"، والذي لا يتم تمكينه افتراضيًا. تدعم الأداة مجموعة متنوعة من الإجراءات الأخرى لمنع الحمل غير المرغوب فيه أو المشاكل الأخرى، بما في ذلك اكتشاف النسخ المتماثلة تلقائيًا، والاتصال بها، واستخدام فحوصات الأمان التالية:

  • في معظم الحالات، ترفض الأداة العمل ما لم يكن هناك مفتاح أساسي (PRIMARY KEY) أو فهرس فريد (UNIQUE INDEX) موجود في الجدول. انظر "--alter" للتفاصيل.
  • ترفض الأداة العمل إذا اكتشفت عوامل تصفية النسخ المتماثل. انظر "--[no]check-replication-filters" للتفاصيل.
  • توقف الأداة عملية نسخ البيانات إذا لاحظت أي نسخ متماثلة متأخرة في النسخ المتماثل. انظر "--max-lag" للتفاصيل.
  • توقف الأداة أو تبطل عمليتها إذا اكتشفت حملًا زائدًا على الخادم. انظر "--max-load" و "--critical-load" للتفاصيل.
  • تقوم الأداة بتعيين "innodb_lock_wait_timeout=1" و (لـ MySQL 5.5 والإصدارات الأحدث) "lock_wait_timeout=60" بحيث من المرجح أن تكون ضحية أي نزاع على القفل، وأقل عرضة لتعطيل المعاملات الأخرى. يمكن تغيير هذه القيم عن طريق تحديد "--set-vars".
  • ترفض الأداة تعديل الجدول إذا كانت قيود المفاتيح الخارجية تشير إليه، ما لم تحدد "--alter-foreign-keys-method".
  • لا يمكن للأداة تعديل جداول MyISAM على عقد "Percona XtraDB Cluster".

Percona XtraDB Cluster

يعمل pt-online-schema-change مع Percona XtraDB Cluster (PXC) 5.5.28-23.7 والإصدارات الأحدث، ولكن هناك قيدان: يمكن تعديل جداول InnoDB فقط، ويجب تعيين "wsrep_OSU_method" إلى "TOI" (total order isolation). تخرج الأداة برسالة خطأ إذا كان المضيف عقدة مجموعة و كان الجدول MyISAM أو يتم تحويله إلى MyISAM ("ENGINE=MyISAM")، أو إذا لم يكن "wsrep_OSU_method" هو "TOI". لا توجد طريقة لتعطيل هذه الفحوصات.

MySQL 5.7 + الأعمدة المنشأة

تتجاهل الأداة أعمدة "GENERATED" في MySQL 5.7+ نظرًا لأن قيمة هذه الأعمدة يتم إنشاؤها وفقًا للتعبير المستخدم لحساب قيم الأعمدة.

الناتج

تطبع الأداة معلومات حول أنشطتها إلى STDOUT حتى تتمكن من رؤية ما تفعله. أثناء مرحلة نسخ البيانات، تطبع تقارير "--progress" إلى STDERR. يمكنك الحصول على معلومات إضافية عن طريق تحديد "--print".

إذا تم تحديد "--statistics"، تتم طباعة تقرير عن عدد الأحداث الداخلية المختلفة في النهاية، مثل:

# Event  Count
# ====== =====
# INSERT     1

الخيارات

"--dry-run" و "--execute" متعارضان.

تقبل هذه الأداة وسائط سطر أوامر إضافية. ارجع إلى "SYNOPSIS" ومعلومات الاستخدام للحصول على التفاصيل.

--alter
النوع: string

التعديل على المخطط، بدون الكلمات المفتاحية ALTER TABLE. يمكنك إجراء تعديلات متعددة على الجدول عن طريق تحديدها بفواصل. يرجى الرجوع إلى دليل MySQL لبناء جملة ALTER TABLE.

تنطبق القيود التالية، والتي إذا تم محاولة تنفيذها، ستتسبب في فشل الأداة بطرق غير متوقعة:

  • في جميع الحالات تقريبًا، يلزم وجود مفتاح أساسي (PRIMARY KEY) أو فهرس فريد (UNIQUE INDEX) في الجدول. هذا ضروري لأن الأداة تنشئ مشغل حذف (DELETE trigger) للحفاظ على تحديث الجدول الجديد أثناء تشغيل العملية.

    استثناء ملحوظ هو عندما يتم إنشاء مفتاح أساسي أو فهرس فريد من الأعمدة الموجودة كجزء من عبارة ALTER؛ في هذه الحالة، سيتم استخدام هذه العمود/الأعمدة لمشغل الحذف.

  • لا يمكن استخدام عبارة "RENAME" لإعادة تسمية الجدول.
  • لا يمكن إعادة تسمية الأعمدة عن طريق إسقاطها وإعادة إضافتها بالاسم الجديد. لن تقوم الأداة بنسخ بيانات العمود الأصلي إلى العمود الجديد.
  • إذا قمت بإضافة عمود بدون قيمة افتراضية وجعلته NOT NULL، ستفشل الأداة، لأنها لن تحاول تخمين قيمة افتراضية لك؛ يجب عليك تحديد القيمة الافتراضية.
  • "DROP FOREIGN KEY constraint_name" يتطلب تحديد "_constraint_name" بدلاً من "constraint_name" الحقيقي. بسبب قيد في MySQL، يضيف pt-online-schema-change شرطة سفلية بادئة لأسماء قيود المفاتيح الخارجية عند إنشاء الجدول الجديد. على سبيل المثال، لإسقاط هذا القيد: 
    CONSTRAINT `fk_foo` FOREIGN KEY (`foo_id`) REFERENCES `bar` (`foo_id`)

    يجب عليك تحديد "LOCK IN SHARE MODE" مع MySQL 5.0 لأنها يمكن أن تسبب خطأ في النسخة المتماثلة مما يؤدي إلى تعطل النسخ المتماثل: 

    استعلام تسبب في أخطاء مختلفة على الماستر والتابع. خطأ في الماستر:
'تم العثور على حالة جمود عند محاولة الحصول على قفل؛ حاول إعادة تشغيل المعاملة' (1213)،
خطأ في التابع: 'لا يوجد خطأ' (0). قاعدة البيانات الافتراضية: 'pt_osc'.
الاستعلام: 'INSERT INTO pt_osc.t (id, c) VALUES ('730', 'صف جديد')'

    يحدث الخطأ عند تحويل جدول MyISAM إلى InnoDB لأن MyISAM غير معاملاتي بينما InnoDB معاملاتي. MySQL 5.1 والأحدث تتعامل مع هذه الحالة بشكل صحيح، ولكن الاختبار يعيد إنتاج الخطأ بنسبة 5٪ من الوقت مع MySQL 5.0.

    هذا خطأ في MySQL، مشابه لـ http://bugs.mysql.com/bug.php?id=45694، ولكن لا يوجد إصلاح أو حل بديل في MySQL 5.0. بدون "LOCK IN SHARE MODE"، تمر الاختبارات بنسبة 100٪ من الوقت، لذلك يجب أن يكون خطر فقدان البيانات أو تعطل النسخ المتماثل ضئيلاً.

    تأكد من التحقق من صحة الجدول الجديد عند استخدام MySQL 5.0 و التحويل من MyISAM إلى InnoDB!

--alter-foreign-keys-method
النوع: سلسلة نصية

كيفية تعديل المفاتيح الخارجية بحيث تشير إلى الجدول الجديد. يجب معاملة المفاتيح الخارجية التي تشير إلى الجدول المراد تعديله بشكل خاص لضمان استمرارها في الإشارة إلى الجدول الصحيح. عندما تقوم الأداة بإعادة تسمية الجدول الأصلي للسماح للجديد بالحل محله، فإن المفاتيح الخارجية "تتبع" الجدول المعاد تسميته، ويجب تغييرها للإشارة إلى الجدول الجديد بدلاً من ذلك.

تدعم الأداة تقنيتين لتحقيق ذلك. إنها تحدد تلقائيًا "الجداول الفرعية" التي تشير إلى الجدول المراد تعديله.

تلقائي
تحديد الطريقة الأفضل تلقائيًا. تستخدم الأداة "rebuild_constraints" إن أمكن (انظر وصف تلك الطريقة للحصول على التفاصيل)، وإلا فإنها تستخدم "drop_swap".
rebuild_constraints
تستخدم هذه الطريقة "ALTER TABLE" لحذف وإعادة إضافة قيود المفاتيح الخارجية التي تشير إلى الجدول الجديد. هذه هي التقنية المفضلة، ما لم يكن أحد "الجداول الفرعية" أو أكثر كبيراً لدرجة أن "ALTER" سيستغرق وقتاً طويلاً. تحدد الأداة ذلك من خلال مقارنة عدد الصفوف في الجدول الفرعي بمعدل نسخ الأداة للصفوف من الجدول القديم إلى الجدول الجديد. إذا قدرت الأداة أن الجدول الفرعي يمكن تعديله في وقت أقل من "--chunk-time"، فستستخدم هذه التقنية. لأغراض تقدير الوقت المطلوب لتعديل الجدول الفرعي، تضرب الأداة معدل نسخ الصفوف في "--chunk-size-limit"، لأن "ALTER TABLE" في MySQL أسرع عادةً من عملية نسخ الصفوف الخارجية.

بسبب قيد في MySQL، لن تحمل المفاتيح الخارجية نفس الأسماء بعد ALTER كما كانت قبلها. تضطر الأداة إلى إعادة تسمية المفتاح الخارجي عند إعادة تعريفه، مما يضيف شرطة سفلية بادئة إلى الاسم. في بعض الحالات، تعيد MySQL تسمية الفهارس المطلوبة للمفتاح الخارجي تلقائيًا.

drop_swap
تعطيل فحوصات المفاتيح الخارجية (FOREIGN_KEY_CHECKS=0)، ثم حذف الجدول الأصلي قبل إعادة تسمية الجدول الجديد ليحل محله. يختلف هذا عن الطريقة العادية لتبديل الجدول القديم والجديد، والتي تستخدم "RENAME" ذرية غير قابلة للكشف للتطبيقات العميل.

هذه الطريقة أسرع ولا تمنع، ولكنها أكثر خطورة لسببين. أولاً، لفترة وجيزة بين حذف الجدول الأصلي وإعادة تسمية الجدول المؤقت، فإن الجدول المراد تعديله ببساطة غير موجود، والاستعلامات ضده ستؤدي إلى خطأ. ثانياً، إذا حدث خطأ ولم يتمكن الجدول الجديد من أن يحل محل القديم، فسيكون الوقت متأخراً للإجهاض، لأن الجدول القديم قد اختفى بشكل دائم.

هذه الطريقة تفرض "--no-swap-tables" و "--no-drop-old-table".

لا شيء
هذه الطريقة تشبه "drop_swap" بدون "التبديل". أي مفاتيح خارجية كانت تشير إلى الجدول الأصلي، ستشير الآن إلى جدول غير موجود. سيؤدي هذا عادةً إلى انتهاكات المفاتيح الخارجية التي تكون مرئية في "SHOW ENGINE INNODB STATUS"، مشابهة لـ: 
محاولة الإضافة إلى الفهرس `idx_fk_staff_id` tuple:
DATA TUPLE: حقلان؛
0: طول 1؛ سداسي 05؛ كما;;
1: طول 4؛ سداسي 80000001؛ كما;;
لكن الجدول الأب `sakila`.`staff_old`
أو ملف .ibd الخاص به غير موجود حاليًا!

وذلك لأن الجدول الأصلي (في هذه الحالة، sakila.staff) تم إعادة تسميته إلى sakila.staff_old ثم حذفه. يتم توفير هذه الطريقة للتعامل مع قيود المفاتيح الخارجية حتى يتمكن مسؤول قاعدة البيانات من تعطيل وظيفة الأداة المدمجة إذا رغب في ذلك.

--[no]analyze-before-swap
الافتراضي: نعم

تنفيذ ANALYZE TABLE على الجدول الجديد قبل تبديله بالجدول القديم. افتراضيًا، يحدث هذا فقط عند تشغيل MySQL 5.6 والإصدارات الأحدث، ويكون "innodb_stats_persistent" ممكّنًا. حدد الخيار صراحةً لتمكينه أو تعطيله بغض النظر عن إصدار MySQL و "innodb_stats_persistent".

يتجاوز هذا مشكلة خطيرة محتملة تتعلق بإحصائيات محسن InnoDB. إذا كان الجدول الذي يتم تعديله قيد الاستخدام وانتهت الأداة بسرعة، فلن يكون للجدول الجديد إحصائيات محسّن بعد تبديله. يمكن أن يتسبب هذا في قيام استعلامات سريعة تستخدم الفهرس بإجراء عمليات مسح كاملة للجدول حتى يتم تحديث إحصائيات المحسن (عادةً بعد 10 ثوانٍ). إذا كان الجدول كبيراً والخادم مشغولاً للغاية، فقد يتسبب هذا في انقطاع الخدمة.

--ask-pass
المطالبة بكلمة مرور عند الاتصال بـ MySQL.
--binary-index
يعدل هذا الخيار سلوك "--history" بحيث يتم إنشاء أعمدة الحدود العليا والسفلى لجدول السجل باستخدام نوع بيانات BLOB. هذا مفيد عند تغيير الجداول الكبيرة ذات المفاتيح التي تشمل نوع بيانات ثنائي أو التي تحتوي على مجموعات أحرف غير قياسية. انظر "--history" و "--resume".
--channel
النوع: سلسلة نصية

اسم القناة المستخدم عند الاتصال بخادم باستخدام قنوات النسخ المتماثل. افترض أن لديك مصدرين للنسخ المتماثل، source_a على المنفذ 12345، و source_b على المنفذ 1236، ونسخة متماثلة متصلة بكليهما باستخدام القناتين chan_source_a و chan_source_b. يمكنك استخدام --channel=chan_source_a لتحديد اسم القناة المراد استخدامه في أمر SHOW REPLICA STATUS الذي تستخدمه pt-online-schema-change لحساب تأخير النسخ المتماثل.

--charset
الشكل المختصر: -A؛ النوع: سلسلة نصية

مجموعة الأحرف الافتراضية. إذا كانت القيمة utf8، تقوم بتعيين binmode في Perl على STDOUT إلى utf8، وتمرير خيار mysql_enable_utf8 إلى DBD::mysql، وتشغيل SET NAMES UTF8 بعد الاتصال بـ MySQL. أي قيمة أخرى تقوم بتعيين binmode على STDOUT بدون طبقة utf8، وتشغيل SET NAMES بعد الاتصال بـ MySQL.

--[no]check-alter
الافتراضي: نعم

يقوم بتحليل "--alter" المحدد ويحاول التحذير من السلوك غير المقصود المحتمل. حاليًا، يتحقق من:

إعادة تسمية الأعمدة

تستخدم الأداة عدة استدلالات لتحديد ما إذا كانت خطة التنفيذ سيئة. الأول هو ما إذا كان EXPLAIN يبلغ عن أن MySQL تنوي استخدام الفهرس المطلوب للوصول إلى الصفوف. إذا اختارت MySQL فهرسًا مختلفًا، تعتبر الأداة الاستعلام غير آمن.

تتحقق الأداة أيضًا من مقدار الفهرس الذي تبلغ عنه MySQL أنها ستستخدمه للاستعلام. يعرض إخراج EXPLAIN هذا في عمود key_len. تتذكر الأداة أكبر key_len شوهد، وتنهي إذا أبلغت MySQL أنها ستستخدم بادئة أصغر للفهرس.

pt-online-schema-change(1p) — Percona Toolkit — Arch Linux

NAME

pt-online-schema-change

perform online schema changes on MySQL tables

SYNOPSIS

pt-online-schema-change [OPTIONS] [DSN]
pt-online-schema-change --alter "alter_clause" [OPTIONS] [DSN]
pt-online-schema-change --execute [OPTIONS] [DSN]
pt-online-schema-change --print [OPTIONS] [DSN]

RISKS

This tool performs a schema change on your table without locking it. This is a good thing. However, it is still a schema change, and schema changes can be risky. It is crucial that you understand these risks before you use this tool. Please read the following carefully.

  • The table is NOT locked, but it IS busy. This tool copies your table, changes the copy, and then swaps the original table for the modified copy. During this time, the table is busy with these operations. If your application cannot tolerate some latency on the table during this operation, then this tool is not for you. For some operations, e.g. ALTER TABLE ... ADD COLUMN, the latency will be very low. For others, e.g. ALTER TABLE ... CHANGE COLUMN ... TYPE, it might be higher. The tool automatically retries some operations in case of temporary issues, but you should still expect some latency.

  • The tool creates temporary tables and triggers. In order to perform the schema change, the tool creates a new table, copies data from the old table to the new table, and then swaps the tables. It does this using triggers to ensure that data changes made to the old table during the copy are also applied to the new table. This can be very resource intensive, and may cause noticeable load on your server.

  • This tool is not a magic bullet. There are many reasons why a schema change might fail, even with this tool. For example, if you try to change a column type to one that is incompatible with the existing data, or if you run out of disk space, the operation may fail. It is your responsibility to ensure the schema change you are attempting is valid and that your environment has sufficient resources.

  • The tool requires certain MySQL privileges. See the "SYSTEM REQUIREMENTS" section for details.

  • This tool creates a reverse-engineered ALTER TABLE statement. In most cases this is perfect. However, in some edge cases it may be incorrect. This is particularly true if your table uses features that the tool does not support (e.g. generated columns, spatial indexes, etc.). If the tool generates an incorrect statement, the schema change will fail.

  • Percona Toolkit is not responsible for any data loss or corruption that may occur as a result of using this tool. Use this tool at your own risk.

DESCRIPTION

Percona Toolkit's pt-online-schema-change tool is a Perl script that performs online schema changes on MySQL tables without downtime. It works by creating a copy of the original table and then copying the data from the original table to the new table. During the copy, it uses triggers to synchronize data changes between the original and the new table. Finally, it swaps the original table for the new table, effectively performing the schema change online.

The tool supports a wide range of schema changes, including adding, dropping, or modifying columns, changing table engines, and altering keys. It attempts to reverse-engineer the correct ALTER TABLE statement from your schema, but you can also specify the ALTER clause directly.

It is designed to be safe and robust, with features such as automatic retries, dry runs, and detailed logging. However, users should still exercise caution and understand the risks involved in online schema changes.

Percona XtraDB Cluster

This tool works with Percona XtraDB Cluster (PXC). However, you must use --no-check-binlog-format and --no-check-replication-filters when running against PXC. This is because PXC does not support the binary log format or replication filters that this tool checks for. For more information, see the documentation for Percona XtraDB Cluster.

MySQL 5.7 + Generated columns

This tool does not support generated columns. If your table has generated columns, you must drop them before using this tool. After the schema change is complete, you can re-add them.

OUTPUT

When the tool is running, it prints progress information to standard output. This includes the number of rows copied, the estimated time remaining, and any errors encountered. The verbosity of the output can be controlled with the --verbose option.

The tool can also generate SQL statements for review using the --print option. This is useful for verifying that the generated ALTER TABLE statement is correct before executing it.

OPTIONS

The tool has a wide range of options to control its behavior. Some of the most important options include:

--alter alter_clause
Specifies the ALTER TABLE clause to execute. For example, "ADD COLUMN c INT" or "ENGINE=InnoDB".
--execute
Executes the ALTER TABLE statement. This option is mutually exclusive with --print.
--print
Prints the ALTER TABLE statement without executing it. This option is mutually exclusive with --execute.
--host host, -h host
The hostname of the MySQL server.
--port port, -P port
The port number of the MySQL server.
--user user, -u user
The username for connecting to the MySQL server.
--password password, -p password
The password for connecting to the MySQL server.
--database database, -d database
The name of the database containing the table.
--table table, -t table
The name of the table to alter.
--dry-run
Specifies that the tool should not make any changes to the database. It will print the ALTER TABLE statement and exit.
--pause seconds
Pauses for the specified number of seconds before starting the schema change. This gives you time to cancel the operation if needed.
--bail-on-error
Exits immediately if any error occurs. By default, the tool will attempt to retry some operations.
--no-check-binlog-format
Disables the check for binary log format. Required when using Percona XtraDB Cluster.
--no-check-replication-filters
Disables the check for replication filters. Required when using Percona XtraDB Cluster.

PLUGIN

This tool can be used as a plugin with pt-archiver. See the pt-archiver documentation for details.

DSN OPTIONS

In addition to the command-line options, you can also specify connection parameters using a DSN (Data Source Name) string. The DSN string should be in the format:

DSN: DBI:mysql:database=database;host=host;port=port

For example:

pt-online-schema-change --alter "ADD COLUMN c INT" \
  DBI:mysql:database=test;host=localhost;port=3306

You can also specify the DSN on the command line without any options:

pt-online-schema-change --alter "ADD COLUMN c INT" \
  D=test,h=localhost,P=3306

This is equivalent to the previous example.

You need Perl, DBI, DBD::mysql, and some core packages that ought to be installed in any reasonably new version of Perl.
