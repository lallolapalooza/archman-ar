pthread_cond_init, pthread_cond_signal, pthread_cond_broadcast, pthread_cond_wait, pthread_cond_timedwait, pthread_cond_destroy - عمليات على الشروط

الملخص

#include <pthread.h>
pthread_cond_t cond = PTHREAD_COND_INITIALIZER;
int pthread_cond_init(pthread_cond_t *cond,
                      pthread_condattr_t *cond_attr);
int pthread_cond_signal(pthread_cond_t *cond);
int pthread_cond_broadcast(pthread_cond_t *cond);
int pthread_cond_wait(pthread_cond_t *cond, pthread_mutex_t *mutex);
int pthread_cond_timedwait(pthread_cond_t *cond, pthread_mutex_t *mutex,
                      const struct timespec *abstime);
int pthread_cond_destroy(pthread_cond_t *cond);

الوصف

الشرط (اختصار لـ "متغير الشرط") هو جهاز تزامن يسمح للخيوط بتعليق التنفيذ والتخلي عن المعالجات حتى يتم تلبية شرط معين على بيانات مشتركة. العمليات الأساسية على الشروط هي: إشارة الشرط (عندما يصبح الشرط صحيحًا)، وانتظار الشرط، وتعليق تنفيذ الخيط حتى يقوم خيط آخر بالإشارة إلى الشرط.

يجب دائمًا ربط متغير الشرط بقفل، لتجنب حالة السباق حيث يستعد خيط للانتظار على متغير شرط، ويقوم خيط آخر بالإشارة إلى الشرط قبل أن ينتظر الخيط الأول فعليًا.

تقوم pthread_cond_init() بتهيئة متغير الشرط cond، باستخدام سمات الشرط المحددة في cond_attr، أو السمات الافتراضية إذا كان cond_attr فارغًا. تنفيذ LinuxThreads لا يدعم أي سمات للشروط، لذلك يتم تجاهل المعامل cond_attr فعليًا.

يمكن أيضًا تهيئة المتغيرات من النوع pthread_cond_t بشكل ثابت، باستخدام الثابت PTHREAD_COND_INITIALIZER.

تقوم pthread_cond_signal() بإعادة تشغيل أحد الخيوط التي تنتظر على متغير الشرط cond. إذا لم تكن هناك خيوط تنتظر على cond، فلن يحدث شيء. إذا كانت عدة خيوط تنتظر على cond، فسيتم إعادة تشغيل واحد منها بالضبط، ولكن لم يتم تحديد أي منها.

تقوم pthread_cond_broadcast() بإعادة تشغيل جميع الخيوط التي تنتظر على متغير الشرط cond. لا يحدث شيء إذا لم تكن هناك خيوط تنتظر على cond.

تقوم pthread_cond_wait() بإلغاء قفل mutex بشكل ذري (وفقًا لـ pthread_unlock_mutex()) وتنتظر حتى يتم الإشارة إلى متغير الشرط cond. يتم تعليق تنفيذ الخيط ولا يستهلك أي وقت وحدة معالجة مركزية حتى يتم الإشارة إلى متغير الشرط. يجب أن يكون mutex مقفلاً بواسطة الخيط المتصل عند الدخول إلى pthread_cond_wait(). قبل العودة إلى الخيط المتصل، تعيد pthread_cond_wait() قفل mutex (وفقًا لـ pthread_mutex_lock()).

يتم إلغاء قفل الـ mutex والانتظار على متغير الشرط بشكل ذري. وبالتالي، إذا كان كل خيط يحصل دائمًا على الـ mutex قبل الإشارة إلى الشرط، فهذا يضمن أن الشرط لا يمكن الإشارة إليه (وبالتالي تجاهله) بين الوقت الذي يقوم فيه الخيط بقفل الـ mutex والوقت الذي ينتظر فيه متغير الشرط. انظر التحذيرات أدناه.

تقوم pthread_cond_timedwait() بإلغاء قفل mutex بشكل ذري والانتظار على cond، كما تفعل pthread_cond_wait()، ولكنها تحدد أيضًا مدة الانتظار. إذا لم يتم الإشارة إلى cond خلال الوقت المحدد بواسطة abstime، يتم إعادة قفل mutex وتُرجع pthread_cond_timedwait() الخطأ ETIMEDOUT. يحدد المعامل abstime وقتًا مطلقًا، بنفس الأصل مثل time(2) و gettimeofday(2): abstime بقيمة 0 يقابل 00:00:00 بتوقيت جرينتش، 1 يناير 1970.

تقوم pthread_cond_destroy() بتدمير متغير شرط، وتحرير الموارد التي قد يمتلكها. يجب ألا تكون هناك خيوط تنتظر على متغير الشرط عند الدخول إلى pthread_cond_destroy(). في تنفيذ LinuxThreads، لا توجد موارد مرتبطة بمتغيرات الشروط، وبالتالي فإن pthread_cond_destroy() لا تفعل شيئًا فعليًا باستثناء التحقق من أن الشرط لا يحتوي على خيوط تنتظر.

الإلغاء

pthread_cond_wait() و pthread_cond_timedwait() هي نقاط إلغاء. إذا تم إلغاء خيط أثناء تعليقه في إحدى هذه الوظائف، فإن الخيط يستأنف التنفيذ فورًا، ثم يعيد قفل mutex كوسيط لـ pthread_cond_wait() و pthread_cond_timedwait()، وينفذ الإلغاء في النهاية. نتيجة لذلك، يتم ضمان أن معالجات التنظيف تقوم بقفل mutex عندما يتم استدعاؤها.

سلامة الإشارة غير المتزامنة

وظائف الشرط ليست آمنة للإشارة غير المتزامنة، ولا ينبغي استدعاؤها من معالج الإشارة. على وجه الخصوص، قد يؤدي استدعاء pthread_cond_signal() أو pthread_cond_broadcast() من معالج إشارة إلى توقف الخيط المتصل عن العمل.

قيمة الإرجاع

جميع وظائف متغير الشرط تُرجع 0 عند النجاح ورمز خطأ غير صفري عند حدوث خطأ.

الأخطاء

pthread_cond_init() و pthread_cond_signal() و pthread_cond_broadcast() و pthread_cond_wait() لا تُرجع أبدًا رمز خطأ.

تُرجع وظيفة pthread_cond_timedwait() رموز الخطأ التالية عند حدوث خطأ:

ETIMEDOUT
لم يتم الإشارة إلى متغير الشرط حتى انقضاء المهلة المحددة بواسطة abstime.

تُرجع وظيفة pthread_cond_destroy() رمز الخطأ التالي عند حدوث خطأ:

EBUSY
بعض الخيوط تنتظر حاليًا على cond.

انظر أيضًا

pthread_condattr_init(3)، pthread_mutex_lock(3)، pthread_mutex_unlock(3)، gettimeofday(2)، nanosleep(2).

تحذيرات

كان تنفيذ الوظائف المقدمة حتى glibc 2.25 يستخدم قفلاً داخليًا للبيانات. لم يكن هذا القفل يدعم توريث الأولوية وكان عرضة لانعكاس الأولوية غير المحدد، وهو أمر مرئي في نظام الوقت الحقيقي.

بعد إعادة كتابة التنفيذ في glibc 2.25، تغير استخدام القفل الداخلي. يتم الحصول على القفل الداخلي دائمًا بواسطة وظائف الإشارة pthread_cond_signal() و pthread_cond_broadcast(). تحصل وظيفة الانتظار على القفل إذا تم مقاطعة عملية الانتظار. يمكن أن يكون سبب المقاطعة، على سبيل المثال، مهلة محددة، ويشار إليها بقيمة الخطأ ETIMEDOUTA، أو إشارة تم استلامها، والتي يشار إليها بقيمة الخطأ EINTR.

مثال

ضع في اعتبارك متغيرين مشتركين x و y، محميين بواسطة القفل mut، ومتغير شرط cond الذي تتم الإشارة إليه عندما يصبح x أكبر من y.

int x,y;
pthread_mutex_t mut = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t cond = PTHREAD_COND_INITIALIZER;

يتم أداء الانتظار حتى يصبح x أكبر من y على النحو التالي:

pthread_mutex_lock(&mut);
while (x <= y) {
        pthread_cond_wait(&cond, &mut);
}
/* تشغيل على x و y */
pthread_mutex_unlock(&mut);

pthread_mutex_lock(&mut);
/* تعديل x و y */
if (x > y) pthread_cond_broadcast(&cond);
pthread_mutex_unlock(&mut);

NAME

pthread_cond_wait, pthread_cond_timedwait - wait on a condition variable

SYNOPSIS

#include <pthread.h>
int pthread_cond_wait(pthread_cond_t *restrict cond,
                              pthread_mutex_t *restrict mutex);
int pthread_cond_timedwait(pthread_cond_t *restrict cond,
                                   pthread_mutex_t *restrict mutex,
                                   const struct timespec *restrict abstime);

DESCRIPTION

Condition variables provide a way for threads to wait until some condition becomes true. Condition variables are always associated with a mutex. To wait on a condition variable, a thread must first lock the mutex.

A thread calls pthread_cond_wait() to wait for the condition variable cond to be signaled. When calling pthread_cond_wait(), the thread must have mutex locked. The pthread_cond_wait() function atomically unlocks the mutex and puts the calling thread to sleep until it is awakened by a call to pthread_cond_signal() or pthread_cond_broadcast() for the same condition variable. Once the thread is awakened, pthread_cond_wait() locks the mutex again before returning.

pthread_cond_timedwait() is like pthread_cond_wait(), but with a timeout. The abstime argument points to a structure specifying the absolute time (in seconds and nanoseconds since the Epoch) when the wait should time out. If the time specified by abstime has already passed, pthread_cond_timedwait() returns immediately.

If the condition is signaled while a thread is waiting, the thread will be woken up. However, condition variables are subject to spurious wakeups, so a thread that is woken up should re-check the condition it is waiting for. This is why pthread_cond_wait() and pthread_cond_timedwait() are almost always used inside a while loop that checks the condition.

CANCELLATION

Threads can be cancelled while they are blocked in a call to pthread_cond_wait() or pthread_cond_timedwait(). Cancellation is handled asynchronously as per the thread's cancellation type (see pthread_setcancelstate(3)). If the thread is canceled while blocked in one of these functions, the function returns the error value ECANCELED. In this case, the mutex is locked before the function returns. If the thread is canceled while waiting, it does not perform the implicit mutex lock that would normally occur on a normal return. This means that the mutex remains locked by the thread that is performing the cancellation.

If the thread has pthread_cancel() deferred, and it is canceled, then the mutex will be unlocked, and the function will return ECANCELED.

pthread_cond_wait() and pthread_cond_timedwait() are cancellation points.

ASYNC SIGNAL SAFETY

pthread_cond_wait() and pthread_cond_timedwait() are not async-signal-safe.

RETURN VALUE

On success, these functions return 0.

On failure, they return an error number.

If the timeout expires for pthread_cond_timedwait(), it returns ETIMEDOUT.

If the thread is canceled, it returns ECANCELED.

ERRORS

EINVAL
The value specified by cond or mutex is not a valid condition variable or mutex.
EDEADLK
The mutex was already locked by the current thread.

SEE ALSO

pthread_cond_broadcast(3), pthread_cond_destroy(3), pthread_cond_init(3), pthread_cond_signal(3), pthread_create(3), pthread_mutex_lock(3), pthread_mutex_unlock(3), pthread_setcancelstate(3), pthread_testcancel(3), pthread(7)

CAVEATS

If you are implementing a condition using a shared variable, and you want to signal threads waiting on that condition, use pthread_cond_signal() to wake up just one thread, or pthread_cond_broadcast() to wake up all threads. If you do not know how many threads might be waiting on the condition, use pthread_cond_broadcast(). Otherwise, if only one thread can actually perform the work, using pthread_cond_signal() can be more efficient.

If you are using pthread_cond_timedwait() and you need to re-calculate the timeout value because of spurious wakeups or other delays, be careful. If you simply add a fixed interval to the current time, you may find that the timeout expires much sooner than you intended due to the time taken by the pthread_cond_timedwait() call itself. A better approach is to calculate the absolute timeout value once, before the loop, and reuse that value.

EXAMPLE

The following example shows how to wait for a variable x to become greater than another variable y.

struct timespec ts;
struct timeval tv;

/* Some condition that determines when to signal. */
int x, y;
pthread_mutex_t mut = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t cond = PTHREAD_COND_INITIALIZER;

/* ... elsewhere ... */

/* Wait for x to be greater than y */
pthread_mutex_lock(&mut);
while (x <= y) {
        /* Calculate absolute timeout: now + 5 seconds */
        gettimeofday(&tv);
        ts.tv_sec = tv.tv_sec + 5;
        ts.tv_nsec = tv.tv_usec * 1000;

        pthread_cond_timedwait(&cond, &mut, &ts);
}
/* x is now guaranteed to be greater than y */
/* operate on x and y */
pthread_mutex_unlock(&mut);

If you do not want a timeout, simply use pthread_cond_wait():

/* Wait indefinitely for x to be greater than y */
pthread_mutex_lock(&mut);
while (x <= y) {
        pthread_cond_wait(&cond, &mut);
}
/* x is now guaranteed to be greater than y */
/* operate on x and y */
pthread_mutex_unlock(&mut);

Using pthread_cond_signal() (wakes up one thread) is more efficient than pthread_cond_broadcast() (wakes up all threads) if only one thread can proceed. If unsure, use pthread_cond_broadcast().

To wait for x to become greater than y with a timeout of 5 seconds, do:

struct timeval now;
struct timespec timeout;
int retcode;
pthread_mutex_lock(&mut);
gettimeofday(&now);
timeout.tv_sec = now.tv_sec + 5;
timeout.tv_nsec = now.tv_usec * 1000;
retcode = 0;
while (x <= y && retcode != ETIMEDOUT) {
        retcode = pthread_cond_timedwait(&cond, &mut, &timeout);
}
if (retcode == ETIMEDOUT) {
        /* timeout occurred */
} else {
        /* operate on x and y */
}
pthread_mutex_unlock(&mut);
