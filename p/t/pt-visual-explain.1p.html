pt-visual-explain(1p)

الحزمة: percona-toolkit

التراخيص: GPL

PT-VISUAL-EXPLAIN(1) وثائق Perl مقدمة من المستخدم PT-VISUAL-EXPLAIN(1)

الاسم

pt-visual-explain - تنسيق ناتج EXPLAIN كشجرة.

الموجز

الاستخدام: pt-visual-explain [خيارات] [ملفات]

يقوم pt-visual-explain بتحويل ناتج EXPLAIN إلى تمثيل شجري لخطة الاستعلام. إذا تم تقديم ملف، تتم قراءة الإدخال من الملف (الملفات). بدون ملف، أو عندما يكون الملف هو -، تتم قراءة الإدخال القياسي.

أمثلة:

pt-visual-explain <ملف يحتوي على ناتج explain>
pt-visual-explain -c <ملف يحتوي على استعلام>
mysql -e "explain select * from mysql.user" | pt-visual-explain

مخاطر

Percona Toolkit ناضج، مثبت في العالم الحقيقي، وتم اختباره جيدًا، ولكن جميع أدوات قواعد البيانات يمكن أن تشكل خطرًا على النظام وخادم قاعدة البيانات. قبل استخدام هذه الأداة، يرجى:

  • قراءة وثائق الأداة
  • مراجعة "الأخطاء" المعروفة للأداة
  • اختبار الأداة على خادم غير إنتاجي
  • عمل نسخة احتياطية من خادم الإنتاج والتحقق من النسخ الاحتياطية

الوصف

يقوم pt-visual-explain بهندسة عكسية لناتج EXPLAIN الخاص بـ MySQL إلى خطة تنفيذ استعلام، والتي يقوم بعد ذلك بتنسيقها كشجرة عميقة على اليسار - بنفس الطريقة التي يتم بها تمثيل الخطة داخل MySQL. من الممكن القيام بذلك يدويًا، أو قراءة ناتج EXPLAIN مباشرة، ولكن هذا يتطلب صبرًا وخبرة. يجد العديد من الأشخاص أن التمثيل الشجري أكثر قابلية للفهم.

يمكنك توجيه الإدخال إلى pt-visual-explain أو تحديد اسم ملف على سطر الأوامر، بما في ذلك اسم الملف السحري '-'، والذي سيقرأ من الإدخال القياسي. يمكنه القيام بأمرين بالإدخال: تحليله بحثًا عن شيء يبدو كنتاج EXPLAIN، أو الاتصال بمثيل MySQL وتشغيل EXPLAIN على الإدخال.

عند تحليل إدخاله، يفهم pt-visual-explain ثلاثة تنسيقات: جدولية مثل تلك المعروضة في عميل سطر أوامر mysql، عمودية مثل تلك التي تم إنشاؤها باستخدام محدد نهاية السطر \G في عميل سطر أوامر mysql، ومفصولة بمسافات. يتجاهل أي أسطر لا يعرف كيفية تحليلها.

عند تنفيذ الإدخال، يقوم pt-visual-explain باستبدال كل شيء في الإدخال حتى أول كلمة SELECT بـ 'EXPLAIN SELECT،' ثم يقوم بتنفيذ النتيجة. يجب عليك تحديد "--connect" لتنفيذ الإدخال كاستعلام.

في كلتا الحالتين، يقوم ببناء شجرة من مجموعة النتائج وطباعتها إلى الإخراج القياسي. للاستعلام التالي،

select * from sakila.film_actor join sakila.film using(film_id);

1.

لمزيد من المعلومات حول كيفية قراءة ناتج EXPLAIN، يرجى الرجوع إلى http://dev.mysql.com/doc/en/explain.html.

الوحدات

هذا البرنامج هو في الواقع وحدة قابلة للتشغيل، وليس مجرد نص Perl عادي. في الواقع، هناك وحدتان مضمنتان فيه. هذا يجعل الاختبار الوحدوي سهلاً، ولكنه يسهل عليك أيضًا استخدام وظائف التحليل وبناء الشجرة إذا أردت.

تقبل حزمة ExplainParser سلسلة وتقوم بتحليل أي شيء تعتقد أنه يبدو كنتاج EXPLAIN منها. الموجز هو كما يلي:

require "pt-visual-explain";
my $p    = ExplainParser->new();
my $rows = $p->parse("some text");
# $rows هو مرجع مصفوفة من hashrefs.

تقبل حزمة ExplainTree مجموعة من الصفوف وتحولها إلى شجرة. للراحة، يمكنك أيضًا جعلها تفوض إلى ExplainParser وتحليل النص لك. إليك الموجز:

require "pt-visual-explain";
my $e      = ExplainTree->new();
my $tree   = $e->parse("some text", \%options);
my $output = $e->pretty_print($tree);
print $tree;

الخوارزمية

يشرح هذا القسم الخوارزمية التي تحول EXPLAIN إلى شجرة. قد تكون مهتمًا بقراءة هذا إذا كنت ترغب في فهم EXPLAIN بشكل أعمق، أو محاولة فهم كيفية عمل هذا، ولكن بخلاف ذلك، قد لا يثري هذا القسم حياتك.

يمكن بناء الشجرة عن طريق فحص الأعمدة id و select_type و table لكل صف.

عمود id هو الرقم التسلسلي للاختيار. هذا لا يشير إلى التداخل؛ إنه يأتي فقط من عد SELECT من يسار جملة SQL. إنه مثل التقاط الأقواس في تعبير عادي.

إذا كان لصفين متجاورين نفس قيمة id، فسيتم ربطهما بطريقة الربط المتعدد القياسية أحادية المسح.

يخبر عمود select_type: أ) أن نطاقًا فرعيًا جديدًا قد تم فتحه ب) نوع العلاقة التي يملكها الصف مع الصف السابق ج) نوع العملية التي يمثلها الصف.

  • SIMPLE يعني عدم وجود استعلامات فرعية أو اتحادات في الاستعلام بأكمله.
  • PRIMARY يعني وجودها، ولكن هذا هو SELECT الخارجي.
  • [DEPENDENT] UNION يعني أن هذه النتيجة يتم اتحادها مع النتيجة السابقة (وليس صفًا؛ قد تشمل النتيجة أكثر من صف واحد).
  • UNION RESULT ينهي مجموعة من النتائج الموحدة.
  • [DEPENDENT|UNCACHEABLE] SUBQUERY يعني أن نطاقًا فرعيًا جديدًا يتم فتحه. هذا هو نوع الاستعلام الفرعي الذي يحدث في عبارة WHERE، قائمة SELECT أو ما شابه ذلك؛ لا يُرجع ما يسمى "جدول مشتق".
  • DERIVED هو استعلام فرعي في عبارة FROM.

الجداول التي يتم ربطها جميعًا لها نفس select_type. على سبيل المثال، إذا قمت بربط ثلاثة جداول داخل استعلام فرعي تابع، فسوف يقولون جميعًا نفس الشيء: DEPENDENT SUBQUERY.

عمود table يحدد عادةً اسم الجدول أو الاسم المستعار، ولكنه قد يقول أيضًا <derivedN> أو <unionN,N...N>. إذا قال <derivedN>، يمثل الصف وصولًا إلى الجدول المؤقت الذي يحتوي على نتيجة الاستعلام الفرعي الذي رقمه N. إذا قال <unionN,..N> فهو نفس الشيء، ولكنه يشير إلى النتائج التي يوحدها معًا.

أخيرًا، الترتيب مهم. إذا كان id الصف أقل من الصف الذي قبله، فهذا يعني أنه تابع لشيء آخر غير الصف الذي قبله. على سبيل المثال،

explain select
   (select 1 from sakila.film),
   (select 2 from sakila.film_actor),
   (select 3 from sakila.actor);
| id | select_type | table      |
+----+-------------+------------+
|  1 | PRIMARY     | NULL       |
|  4 | SUBQUERY    | actor      |
|  3 | SUBQUERY    | film_actor |
|  2 | SUBQUERY    | film       |

إذا كانت النتائج بالترتيب 2-3-4، فهذا يعني أن 3 هو استعلام فرعي لـ 2، وأن 4 هو استعلام فرعي لـ 3. كما هو الحال، هذا يعني أن 4 هو استعلام فرعي لأقرب صف حديث سابق له id أصغر، وهو 1. وكذلك الحال بالنسبة لـ 3 و 2.

هذا الهيكل صعب البناء بشكل برمجي في شجرة لنفس سبب صعوبة فهمه بالفحص: هناك إشارات أمامية وخلفية. <derivedN> هي إشارة أمامية إلى selectN، بينما <unionM,N> هي إشارة خلفية إلى selectM و selectN. هذا يجعل التكرار وخوارزميات بناء الشجرة الأخرى صعبة الفهم (ملاحظة: بعد التنفيذ، أرى الآن كيف يمكن التعامل مع الإشارات الأمامية والخلفية، لكن ليس لدي دافع لتغيير شيء يعمل). ضع في اعتبارك ما يلي:

select * from (
   select 1 from sakila.actor as actor_1
   union
   select 1 from sakila.actor as actor_2
) as der_1
union
select * from (
   select 1 from sakila.actor as actor_3
   union all
   select 1 from sakila.actor as actor_4
) as der_2;
| id   | select_type  | table      |
+------+--------------+------------+
|  1   | PRIMARY      | <derived2> |
|  2   | DERIVED      | actor_1    |
|  3   | UNION        | actor_2    |
| NULL | UNION RESULT | <union2,3> |
|  4   | UNION        | <derived5> |
|  5   | DERIVED      | actor_3    |
|  6   | UNION        | actor_4    |
| NULL | UNION RESULT | <union5,6> |
| NULL | UNION RESULT | <union1,4> |

Consider how MySQL numbers the SELECTs sequentially according to their position in the SQL, left-to-right. It always seems to do this, and there might be other methods of finding the scope boundaries including looking for the lower boundary of the next largest sibling, but this is a good enough heuristic. We are forced to rely on it for non-DERIVED subqueries, so we rely on it here too. Therefore, we decide that everything greater than or equal to 3 belongs to the DERIVED scope. This is because a UNION cannot be a sibling of another UNION or a table, DERIVED or not. (Try writing such a statement if you don't see it intuitively). There are only three kinds of enclosing scopes: UNION, DERIVED, and SUBQUERY. Armed with this knowledge, it's possible to use recursion to turn the parent-child relationship between all the rows into a tree representing the execution plan. MySQL prints the rows in execution order, even the forward and backward references. At any given scope, the rows are processed as a left-deep tree. MySQL does not do "bushy" execution plans. It begins with a table, finds a matching row in the next table, and continues till the last table, when it emits a row. When it runs out, it backtracks till it can find the next row and repeats. There are subtleties of course, but this is the basic plan. This is why MySQL transforms all RIGHT OUTER JOINs into LEFT OUTER JOINs and cannot do FULL OUTER JOIN. ENVIRONMENT

The environment variable "PTDEBUG" enables verbose debugging output to STDERR. To enable debugging and capture all output to a file, run the tool like:

PTDEBUG=1 pt-visual-explain ... > FILE 2>&1

Be careful: debugging output is voluminous and can generate several megabytes of output.

ATTENTION

Using <PTDEBUG> might expose passwords. When debug is enabled, all command line parameters are shown in the output.

SYSTEM REQUIREMENTS

You need Perl, DBI, DBD::mysql, and some core packages that ought to be installed in any reasonably new version of Perl.
