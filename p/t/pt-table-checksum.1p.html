الحزمة: percona-toolkit

BACKWARDS COMPATIBILITY

Version 2.0 of pt-table-checksum is not backwards compatible with pt-table-sync version 1.0. In some cases this is not a serious problem. Adding a "boundaries" column to the table, and then updating it with a manually generated WHERE clause, may suffice to let pt-table-sync version 1.0 interoperate with pt-table-checksum version 2.0. Assuming an integer primary key named 'id', You can try something like the following:

ALTER TABLE checksums ADD boundaries VARCHAR(500);
UPDATE checksums
 SET boundaries = COALESCE(CONCAT('id BETWEEN ', lower_boundary,
    ' AND ', upper_boundary), '1=1');

Take into consideration that by default, pt-table-checksum use "CRC32" checksums. "CRC32" is not a cryptographic algorithm and for that reason it is prone to have collisions. On the other hand, "CRC32" algorithm is faster and less CPU-intensive than "MD5" and "SHA1".

Related reading material: Percona Toolkit UDFs: https://docs.percona.com/percona-server/8.0/udf-percona-toolkit.html How to avoid hash collisions when using MySQL’s CRC32 function: https://www.percona.com/blog/2014/10/13/how-to-avoid-hash-collisions-when-using-mysqls-crc32-function/

LIMITATIONS

Replicas using row-based replication
pt-table-checksum requires statement-based replication, and it sets "binlog_format=STATEMENT" on the source, but due to a MySQL limitation replicas do not honor this change. Therefore, checksums will not replicate past any replicas using row-based replication that are sources for further replicas.

The tool automatically checks the "binlog_format" on all servers. See "--[no]check-binlog-format" .

(Bug 899415 https://bugs.launchpad.net/percona-toolkit/+bug/899415)

Schema and table differences
The tool presumes that schemas and tables are identical on the source and all replicas. Replication will break if, for example, a replica does not have a schema that exists on the source (and that schema is checksummed), or if the structure of a table on a replica is different than on the source.

Percona XtraDB Cluster

pt-table-checksum works with Percona XtraDB Cluster (PXC) 5.5.28-23.7 and newer. The number of possible Percona XtraDB Cluster setups is large given that it can be used with regular replication as well. Therefore, only the setups listed below are supported and known to work. Other setups, like cluster to cluster, are not supported and probably don't work.

Except where noted, all of the following supported setups require that you use the "dsn" method for "--recursion-method" to specify cluster nodes. Also, the lag check (see "REPLICA CHECKS") is not performed for cluster nodes.

Single cluster
The simplest PXC setup is a single cluster: all servers are cluster nodes, and there are no regular replicas. If all nodes are specified in the DSN table (see "--recursion-method"), then you can run the tool on any node and any diffs on any other nodes will be detected.

All nodes must be in the same cluster (have the same "wsrep_cluster_name" value), else the tool exits with an error. Although it's possible to have different clusters with the same name, this should not be done and is not supported. This applies to all supported setups.

Single cluster with replicas
Cluster nodes can also be regular replication sources and replicate to regular replicas. However, the tool can only detect diffs on a replica if ran on the replica's "source node". For example, if the cluster setup is, 
node1 <-> node2 <-> node3
            |         |
            |         +-> replica3
            +-> replica2

you can detect diffs on replica3 by running the tool on node3, but to detect diffs on replica2 you must run the tool again on node2. If you run the tool on node1, it will not detect diffs on either replica.

Currently, the tool does not detect this setup or warn about replicas that cannot be checked (e.g. replica2 when running on node3).

Replicas in this setup are still subject to "--[no]check-binlog-format".

Replication source to single cluster
It is possible for a regular source to replicate to a cluster, as if the cluster were one logical replica, like: 
source -> node1 <-> node2 <-> node3

The tool supports this setup but only if ran on the source and if all nodes in the cluster are consistent with the "direct replica" (node1 in this example) of the source. For example, if all nodes have value "foo" for row 1 but the source has value "bar" for the same row, this diff will be detected. Or if only node1 has this diff, it will also be detected. But if only node2 or node3 has this diff, it will not be detected. Therefore, this setup is used to check that the source and the cluster as a whole are consistent.

In this setup, the tool can automatically detect the "direct replica" (node1) when ran on the source, so you do not have to use the "dsn" method for "--recursion-method" because node1 will represent the entire cluster, which is why all other nodes must be consistent with it.

The tool warns when it detects this setup to remind you that it only works when used as described above. These warnings do not affect the exit status of the tool; they're only reminders to help avoid false-positive results.

RocksDB support
Due to the limitations in the RocksDB engine like not supporting binlog_format=STATEMENT or they way RocksDB handles Gap locks, pt-table-checksum will skip tables using RocksDB engine. More Information: (https://www.percona.com/doc/percona-server/LATEST/myrocks/limitations.html)

This option can override the default behavior, which is to adjust chunk size dynamically to try to make chunks run in exactly "--chunk-time" seconds. When this option isn't set explicitly, its default value is used as a starting point, but after that, the tool ignores this option's value. If you set this option explicitly, however, then it disables the dynamic adjustment behavior and tries to make all chunks exactly the specified number of rows.

There is a subtlety: if the chunk index is not unique, then it's possible that chunks will be larger than desired. For example, if a table is chunked by an index that contains 10,000 of a given value, there is no way to write a WHERE clause that matches only 1,000 of the values, and that chunk will be at least 10,000 rows large. Such a chunk will probably be skipped because of "--chunk-size-limit".

Selecting a small chunk size will cause the tool to become much slower, in part because of the setup work required for "--[no]check-plan".

--chunk-size-limit
type: float; default: 2.0; group: Safety

Do not checksum chunks this much larger than the desired chunk size.

When a table has no unique indexes, chunk sizes can be inaccurate. This option specifies a maximum tolerable limit to the inaccuracy. The tool uses <EXPLAIN> to estimate how many rows are in the chunk. If that estimate exceeds the desired chunk size times the limit (twice as large, by default), then the tool skips the chunk.

The minimum value for this option is 1, which means that no chunk can be larger than "--chunk-size". You probably don't want to specify 1, because rows reported by EXPLAIN are estimates, which can be different from the real number of rows in the chunk. If the tool skips too many chunks because they are oversized, you might want to specify a value larger than the default of 2.

You can disable oversized chunk checking by specifying a value of 0.

--chunk-time
type: float; default: 0.5

Adjust the chunk size dynamically so each checksum query takes this long to execute.

The tool tracks the checksum rate (rows per second) for all tables and each table individually. It uses these rates to adjust the chunk size after each checksum query, so that the next checksum query takes this amount of time (in seconds) to execute.

The algorithm is as follows: at the beginning of each table, the chunk size is initialized from the overall average rows per second since the tool began working, or the value of "--chunk-size" if the tool hasn't started working yet. For each subsequent chunk of a table, the tool adjusts the chunk size to try to make queries run in the desired amount of time. It keeps an exponentially decaying moving average of queries per second, so that if the server's performance changes due to changes in server load, the tool adapts quickly. This allows the tool to achieve predictably timed queries for each table, and for the server overall.

If this option is set to zero, the chunk size doesn't auto-adjust, so query checksum times will vary, but query checksum sizes will not. Another way to do the same thing is to specify a value for "--chunk-size" explicitly, instead of leaving it at the default.

--float-precision
type: int

Precision for FLOAT and DOUBLE number-to-string conversion. Causes FLOAT and DOUBLE values to be rounded to the specified number of digits after the decimal point, with the ROUND() function in MySQL. This can help avoid checksum mismatches due to different floating-point representations of the same values on different MySQL versions and hardware. The default is no rounding; the values are converted to strings by the CONCAT() function, and MySQL chooses the string representation. If you specify a value of 2, for example, then the values 1.008 and 1.009 will be rounded to 1.01, and will checksum as equal.

--function
type: string

Hash function for checksums (FNV1A_64, MURMUR_HASH, SHA1, MD5, CRC32, etc).

The default is to use CRC32(), but MD5() and SHA1() also work, and you can use your own function, such as a compiled UDF, if you wish. The function you specify is run in SQL, not in Perl, so it must be available to MySQL.

MySQL doesn't have good built-in hash functions that are fast. CRC32() is too prone to hash collisions, and MD5() and SHA1() are very CPU-intensive. The FNV1A_64() UDF that is distributed with Percona Server is a faster alternative. It is very simple to compile and install; look at the header in the source code for instructions. If it is installed, it is preferred over MD5(). You can also use the MURMUR_HASH() function if you compile and install that as a UDF; the source is also distributed with Percona Server, and it might be better than FNV1A_64().

أضف TRIM() إلى أعمدة VARCHAR (يساعد عند مقارنة 4.1 بالإصدار 5.0 وما فوق). هذا مفيد عندما لا تهتم باختلافات المسافات اللاحقة بين إصدارات MySQL التي تختلف في كيفية التعامل مع المسافات اللاحقة. الإصدارات MySQL 5.0 والإصدارات الأحدث تحتفظ بجميع المسافات اللاحقة في VARCHAR، بينما كانت الإصدارات السابقة تزيلها. هذه الاختلافات ستؤدي إلى اختلافات تدقيق خاطئة.
--truncate-replicate-table
اقتطع الجدول المنسوخ قبل بدء التدقيق. يختلف هذا المعامل عن "--[no]empty-replicate-table" الذي يحذف فقط الصفوف الخاصة بالجدول الذي يتم تدقيقه عند بدء التدقيق لهذا الجدول، بينما يقوم "--truncate-replicate-table" باقتطاع الجدول المنسوخ في بداية العملية وبالتالي، سيتم فقدان جميع معلومات التدقيق السابقة، حتى لو توقفت العملية بسبب خطأ.
--user
الشكل المختصر: -u؛ النوع: string؛ المجموعة: Connection

المستخدم لتسجيل الدخول إذا لم يكن المستخدم الحالي.

--version
المجموعة: Help

اعرض الإصدار واخرج.

--[no]version-check
الافتراضي: yes

تحقق من أحدث إصدار من Percona Toolkit و MySQL والبرامج الأخرى.

هذه ميزة قياسية "للتحقق من التحديثات تلقائيًا"، مع ميزتين إضافيتين. أولاً، تتحقق الأداة من إصدارها الخاص وأيضًا من إصدارات البرامج التالية: نظام التشغيل، Percona Monitoring and Management (PMM)، MySQL، مشغل MySQL لـ Perl (DBD::mysql)، و Percona Toolkit. ثانيًا، تتحقق من الإصدارات ذات المشاكل المعروفة وتحذر منها. على سبيل المثال، كان لدى MySQL 5.5.25 خطأ حرج وتم إعادة إصداره كـ 5.5.25a.

يتم إجراء اتصال آمن بخادم قاعدة بيانات التحقق من الإصدارات الخاص بـ Percona لإجراء هذه الفحوصات. يتم تسجيل كل طلب بواسطة الخادم، بما في ذلك أرقام إصدارات البرامج ومعرف فريد للنظام الذي تم فحصه. يتم إنشاء المعرف بواسطة برنامج تثبيت Percona Toolkit أو عند إجراء استدعاء قاعدة بيانات التحقق من الإصدارات لأول مرة.

يتم طباعة أي تحديثات أو مشاكل معروفة إلى STDOUT قبل الإخراج العادي للأداة. يجب ألا تتداخل هذه الميزة أبدًا مع التشغيل العادي للأداة.

لمزيد من المعلومات، تفضل بزيارة https://www.percona.com/doc/percona-toolkit/LATEST/version-check.html.

--where
النوع: string

قم فقط بمعالجة الصفوف التي تطابق عبارة WHERE هذه. يمكنك استخدام هذا الخيار لتحديد نطاق التدقيق لجزء فقط من الجدول. هذا مفيد بشكل خاص إذا كان لديك جداول للإلحاق فقط ولا تريد إعادة فحص جميع الصفوف باستمرار؛ يمكنك تشغيل وظيفة يومية لفحص صفوف الأمس فقط، على سبيل المثال.

هذا الخيار يشبه إلى حد كبير الخيار -w في mysqldump. لا تحدد الكلمة المفتاحية WHERE. قد تحتاج إلى وضع القيمة بين علامتي اقتباس. إليك مثال:

pt-table-checksum --where "ts > CURRENT_DATE - INTERVAL 1 DAY"

فحوصات النسخ المتماثلة

افتراضيًا، يحاول pt-table-checksum العثور على جميع النسخ المتماثلة المتصلة بمضيف المصدر والاتصال بها. تسمى هذه العملية الآلية "تكرار النسخ المتماثل" ويتم التحكم فيها بواسطة الخيارين "--recursion-method" و "--recurse".

فحوصات التدقيق

يقوم الأداة بإجراء هذه الفحوصات على جميع النسخ المتماثلة:

1. "--[no]check-replication-filters"
يفحص pt-table-checksum عوامل تصفية النسخ المتماثل على جميع النسخ المتماثلة لأنها يمكن أن تعقد أو تكسر عملية التدقيق. بشكل افتراضي، ستخرج الأداة إذا تم العثور على أي عوامل تصفية للنسخ المتماثل، ولكن يمكن تعطيل هذا الفحص عن طريق تحديد "--no-check-replication-filters".
2. "--replicate" table
يفحص pt-table-checksum وجود الجدول "--replicate" على جميع النسخ المتماثلة، وإلا فإن التدقيق يمكن أن يكسر النسخ المتماثل عندما تتكرر التحديثات على الجدول في المصدر إلى نسخة متماثلة لا تحتوي على الجدول. لا يمكن تعطيل هذا الفحص، وتنتظر الأداة إلى الأبد حتى يوجد الجدول على جميع النسخ المتماثلة، مع طباعة رسائل "--progress" أثناء انتظارها.
3. حجم الشريحة الواحدة
إذا كان يمكن تدقيق جدول في شريحة واحدة على المصدر، فسيتحقق pt-table-checksum من أن حجم الجدول على جميع النسخ المتماثلة أقل من "--chunk-size" * "--chunk-size-limit". هذا يمنع مشكلة نادرة حيث يكون الجدول في المصدر فارغًا أو صغيرًا، ولكنه على نسخة متماثلة يكون أكبر بكثير. في هذه الحالة، سيؤدي تدقيق الشريحة الواحدة على المصدر إلى إرهاق النسخة المتماثلة.

تحدث مشكلة نادرة أخرى عندما يكون حجم الجدول على نسخة متماثلة قريبًا من "--chunk-size" * "--chunk-size-limit". في مثل هذه الحالات، من المرجح أن يتم تخطي الجدول على الرغم من أنه آمن للتدقيق في شريحة واحدة. يحدث هذا لأن تقديرات حجم الجدول وهذه القيمة "--chunk-size" * "--chunk-size-limit" قريبتان جدًا من بعضهما البعض، ويصبح هذا الفحص أكثر حساسية لهامش خطأ التقديرات بدلاً من الاختلافات الهامة الفعلية في أحجام الجداول. يساهم تحديد قيمة أكبر لـ "--chunk-size-limit" في تجنب هذه المشكلة.

لا يمكن تعطيل هذا الفحص.

4. التأخير
بعد كل شريحة، يتحقق pt-table-checksum من التأخير على جميع النسخ المتماثلة، أو فقط النسخة المتماثلة المحددة بواسطة "--check-replica-lag". يساعد هذا الأداة على عدم إرهاق النسخ المتماثلة ببيانات التدقيق. لا توجد طريقة لتعطيل هذا الفحص، ولكن يمكنك تحديد نسخة متماثلة واحدة للتحقق منها باستخدام "--check-replica-lag"، وإذا كانت تلك النسخة المتماثلة هي الأسرع، فسيساعد ذلك على منع الأداة من الانتظار طويلاً حتى يتلاشى تأخير النسخة المتماثلة.
5. شرائح التدقيق
عندما ينتهي pt-table-checksum من تدقيق جدول، فإنه ينتظر حتى يتم نسخ شريحة التدقيق الأخيرة إلى جميع النسخ المتماثلة حتى يتمكن من إجراء "--[no]replicate-check". يؤدي تعطيل هذا الخيار عن طريق تحديد --no-replicate-check إلى تعطيل هذا الفحص، ولكنه يعطل أيضًا الإبلاغ الفوري عن اختلافات التدقيق، مما يتطلب تشغيلًا ثانيًا للأداة باستخدام "--replicate-check-only" للعثور على اختلافات التدقيق وطباعتها.

المكون الإضافي

يجب أن يحدد الملف المحدد بواسطة "--plugin" فئة (أي حزمة) تسمى "pt_table_checksum_plugin" مع روتين فرعي new(). ستقوم الأداة بإنشاء نسخة من هذه الفئة واستدعاء أي خطافات تعرفها. لا يلزم وجود خطافات، ولكن المكون الإضافي ليس مفيدًا جدًا بدونها.

يتم استدعاء خطافات (hooks) هذه، بهذا الترتيب، إذا تم تعريفها:

init
before_replicate_check
after_replicate_check
get_replica_lag
before_checksum_table
after_checksum_table

يتم تمرير وسائط مختلفة إلى كل خطاف. لمعرفة الوسائط التي يتم تمريرها إلى خطاف، ابحث عن اسم الخطاف في الكود المصدري للأداة، مثل:

# --plugin hook
if ( $plugin && $plugin->can('init') ) {
   $plugin->init(
      replicas         => $replicas,
      replica_lag_cxns => $replica_lag_cxns,
      repl_table       => $repl_table,
   );
}

يسبق التعليق "# --plugin hook" كل استدعاء للخطاف.

يرجى الاتصال بـ Percona إذا كانت لديك أسئلة أو تحتاج إلى مساعدة.

خيارات DSN

تُستخدم خيارات DSN هذه لإنشاء DSN. يتم إعطاء كل خيار مثل "option=value". الخيارات حساسة لحالة الأحرف، لذلك P و p ليسا نفس الخيار. لا يمكن أن يكون هناك مسافة بيضاء قبل أو بعد "=" وإذا كانت القيمة تحتوي على مسافات بيضاء فيجب أن تكون مقتبسة. يتم فصل خيارات DSN بفواصل. انظر صفحة دليل percona-toolkit للحصول على التفاصيل الكاملة.

  • A

    dsn: charset; copy: yes

    مجموعة الأحرف الافتراضية.

  • D

    copy: no

    قاعدة بيانات جدول DSN.

  • F

    dsn: mysql_read_default_file; copy: yes

    ملف القيم الافتراضية للاتصال.

  • h

    dsn: host; copy: yes

    الاتصال بالمضيف.

  • p

    dsn: password; copy: yes

    كلمة المرور المستخدمة عند الاتصال. إذا كانت كلمة المرور تحتوي على فواصل، فيجب إلغاء تهريبها بشرطة مائلة عكسية: "exam\,ple"

  • P

    dsn: port; copy: yes

    رقم المنفذ المستخدم للاتصال.

  • S

    dsn: mysql_socket; copy: no

    ملف المقبس المستخدم للاتصال.

  • t

    copy: no

    جدول DSN.

  • u

    dsn: user; copy: yes

    المستخدم لتسجيل الدخول إذا لم يكن المستخدم الحالي.

  • s

    dsn: mysql_ssl; copy: yes

    إنشاء اتصال SSL

بيئة التشغيل

يقوم متغير البيئة "PTDEBUG" بتمكين إخراج تصحيح الأخطاء المطول إلى STDERR. لتمكين تصحيح الأخطاء والتقاط جميع المخرجات في ملف، قم بتشغيل الأداة مثل:

PTDEBUG=1 pt-table-checksum ... > FILE 2>&1

كن حذرًا: إخراج تصحيح الأخطاء غزير جدًا ويمكن أن يولد عدة ميغابايت من المخرجات.

انتباه

قد يؤدي استخدام <PTDEBUG> إلى كشف كلمات المرور. عند تمكين تصحيح الأخطاء، يتم عرض جميع معلمات سطر الأوامر في المخرجات.

متطلبات النظام

تحتاج إلى Perl و DBI و DBD::mysql وبعض الحزم الأساسية التي يجب تثبيتها في أي إصدار حديث إلى حد ما من Perl.
