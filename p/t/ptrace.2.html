الاسم

ptrace - تتبع العمليات

المكتبة

مكتبة C القياسية (libc, -lc)

المُلَخَّص

#include <sys/ptrace.h>

الوصف

يوفر استدعاء النظام ptrace() وسيلة يمكن لعملية (الـ "tracer") من خلالها مراقبة والتحكم في تنفيذ عملية أخرى (الـ "tracee")، وفحص وتغيير ذاكرة وسجلات الـ tracee. يستخدم بشكل أساسي لتنفيذ تصحيح نقاط التوقف وتتبع استدعاءات النظام.

تحتاج عملية tracee أولاً إلى الاتصال بالـ tracer. الاتصال والأوامر اللاحقة تكون لكل خيط (thread): في عملية متعددة الخيوط، يمكن ربط كل خيط بشكل فردي بـ tracer (قد يكون مختلفًا)، أو تركه غير مرتبط وبالتالي لا يتم تصحيحه. لذلك، "tracee" يعني دائمًا "(خيط واحد)"، وليس "عملية (متعددة الخيوط محتملة)". يتم إرسال أوامر Ptrace دائمًا إلى خيط tracee محدد باستخدام استدعاء بالشكل


ptrace(PTRACE_foo, pid, ...)

حيث pid هو معرف الخيط (thread ID) الخاص بالخيط المحدد في Linux.

(لاحظ أن هذه الصفحة، "عملية متعددة الخيوط" تعني مجموعة من الخيوط التي تم إنشاؤها باستخدام راية clone(2) CLONE_THREAD.)

يمكن لعملية ما بدء تتبع عملية أخرى عن طريق استدعاء fork(2) وجعل العملية الوليدة تقوم بـ PTRACE_TRACEME، يتبعها (عادةً) استدعاء execve(2). بدلاً من ذلك، قد تبدأ عملية ما في تتبع عملية أخرى باستخدام PTRACE_ATTACH أو PTRACE_SEIZE.

أثناء تتبعها، تتوقف الـ tracee في كل مرة يتم فيها تسليم إشارة، حتى لو تم تجاهل الإشارة. (الاستثناء هو SIGKILL، التي لها تأثيرها المعتاد.) سيتم إخطار الـ tracer عند استدعائه التالي لـ waitpid(2) (أو أحد استدعاءات "wait" ذات الصلة)؛ سيعيد هذا الاستدعاء قيمة status تحتوي على معلومات تشير إلى سبب التوقف في الـ tracee. أثناء توقف الـ tracee، يمكن لـ tracer استخدام عمليات ptrace مختلفة لفحص وتعديل الـ tracee. ثم يتسبب الـ tracer في استمرار الـ tracee في التنفيذ، مع تجاهل اختياري للإشارة المسلمة (أو حتى تسليم إشارة مختلفة بدلاً منها).

إذا لم تكن الخيار PTRACE_O_TRACEEXEC مفعلة، فإن جميع استدعاءات execve(2) الناجحة التي تجريها العملية المتتبعة ستتسبب في إرسال إشارة SIGTRAP إليها، مما يمنح العملية الأصلية فرصة للتحكم قبل بدء تشغيل البرنامج الجديد.

عندما ينتهي الـ tracer من التتبع، يمكنه جعل الـ tracee يستمر في التنفيذ في وضع طبيعي وغير متتبع عبر PTRACE_DETACH.

PTRACE_TRACEME
تشير إلى أن هذه العملية سيتم تتبعها بواسطة العملية الأصلية. من الأفضل عدم قيام العملية بهذا الإجراء إذا لم تكن العملية الأصلية تتوقع تتبعها. (pid، addr، و data يتم تجاهلها.)
عملية PTRACE_TRACEME يستخدمها الـ tracee فقط؛ العمليات المتبقية يستخدمها الـ tracer فقط. في العمليات التالية، تحدد pid معرف الخيط (thread ID) للـ tracee المراد العمل عليه. بالنسبة للعمليات بخلاف PTRACE_ATTACH، PTRACE_SEIZE، PTRACE_INTERRUPT، و PTRACE_KILL، يجب أن يكون الـ tracee متوقفًا.
PTRACE_PEEKTEXT
PTRACE_PEEKDATA

PTRACE_PEEKUSER

PTRACE_POKETEXT

PTRACE_POKEUSER
نسخ الكلمة data إلى الإزاحة addr في منطقة المستخدم (USER area) الخاصة بالـ tracee. كما هو الحال بالنسبة لـ PTRACE_PEEKUSER، عادةً ما يجب أن تكون الإزاحة متوافقة مع حجم الكلمة. للحفاظ على سلامة النواة، يتم منع بعض التعديلات على منطقة المستخدم.

PTRACE_PEEKSIGINFO (since Linux 3.10)
Retrieve siginfo_t structures without removing signals from a queue. addr points to a ptrace_peeksiginfo_args structure that specifies the ordinal position from which copying of signals should start, and the number of signals to copy. siginfo_t structures are copied into the buffer pointed to by data. The return value contains the number of copied signals (zero indicates that there is no signal corresponding to the specified ordinal position). Within the returned siginfo structures, the si_code field includes information (__SI_CHLD, __SI_FAULT, etc.) that are not otherwise exposed to user space.


struct ptrace_peeksiginfo_args {
    u64 off;    /* Ordinal position in queue at which
                   to start copying signals */
    u32 flags;  /* PTRACE_PEEKSIGINFO_SHARED or 0 */
    s32 nr;     /* Number of signals to copy */
};
Currently, there is only one flag, PTRACE_PEEKSIGINFO_SHARED, for dumping signals from the process-wide signal queue. If this flag is not set, signals are read from the per-thread queue of the specified thread.
PTRACE_GETSIGMASK (since Linux 3.11)
Place a copy of the mask of blocked signals (see sigprocmask(2)) in the buffer pointed to by data, which should be a pointer to a buffer of type sigset_t. The addr argument contains the size of the buffer pointed to by data (i.e., sizeof(sigset_t)).
PTRACE_SETSIGMASK (since Linux 3.11)
Change the mask of blocked signals (see sigprocmask(2)) to the value specified in the buffer pointed to by data, which should be a pointer to a buffer of type sigset_t. The addr argument contains the size of the buffer pointed to by data (i.e., sizeof(sigset_t)).
PTRACE_SETOPTIONS (since Linux 2.4.6; see BUGS for caveats)
Set ptrace options from data. (addr is ignored.) data is interpreted as a bit mask of options, which are specified by the following flags:
PTRACE_O_EXITKILL (since Linux 3.8)
Send a SIGKILL signal to the tracee if the tracer exits. This option is useful for ptrace jailers that want to ensure that tracees can never escape the tracer's control.
PTRACE_O_TRACECLONE (since Linux 2.5.46)
Stop the tracee at the next clone(2) and automatically start tracing the newly cloned process, which will start with a SIGSTOP, or PTRACE_EVENT_STOP if PTRACE_SEIZE was used. A waitpid(2) by the tracer will return a status value such that
  status>>8 == (SIGTRAP | (PTRACE_EVENT_CLONE<<8))
The PID of the new process can be retrieved with PTRACE_GETEVENTMSG.
This option may not catch clone(2) calls in all cases. If the tracee calls clone(2) with the CLONE_VFORK flag, PTRACE_EVENT_VFORK will be delivered instead if PTRACE_O_TRACEVFORK is set; otherwise if the tracee calls clone(2) with the exit signal set to SIGCHLD, PTRACE_EVENT_FORK will be delivered if PTRACE_O_TRACEFORK is set.
PTRACE_O_TRACEEXEC (since Linux 2.5.46)
Stop the tracee at the next execve(2). A waitpid(2) by the tracer will return a status value such that
  status>>8 == (SIGTRAP | (PTRACE_EVENT_EXEC<<8))
If the execing thread is not a thread group leader, the thread ID is reset to thread group leader's ID before this stop. Since Linux 3.0, the former thread ID can be retrieved with PTRACE_GETEVENTMSG.
PTRACE_O_TRACEEXIT (since Linux 2.5.60)
Stop the tracee at exit. A waitpid(2) by the tracer will return a status value such that
  status>>8 == (SIGTRAP | (PTRACE_EVENT_EXIT<<8))
The tracee's exit status can be retrieved with PTRACE_GETEVENTMSG.
The tracee is stopped early during process exit, when registers are still available, allowing the tracer to see where the exit occurred, whereas the normal exit notification is done after the process is finished exiting. Even though context is available, the tracer cannot prevent the exit from happening at this point.
PTRACE_O_TRACEFORK (since Linux 2.5.46)
Stop the tracee at the next fork(2) and automatically start tracing the newly forked process, which will start with a SIGSTOP, or PTRACE_EVENT_STOP if PTRACE_SEIZE was used. A waitpid(2) by the tracer will return a status value such that
  status>>8 == (SIGTRAP | (PTRACE_EVENT_FORK<<8))
The PID of the new process can be retrieved with PTRACE_GETEVENTMSG.
PTRACE_O_TRACESYSGOOD (since Linux 2.4.6)
When delivering system call traps, set bit 7 in the signal number (i.e., deliver SIGTRAP|0x80). This makes it easy for the tracer to distinguish normal traps from those caused by a system call.
PTRACE_O_TRACEVFORK (since Linux 2.5.46)
Stop the tracee at the next vfork(2) and automatically start tracing the newly vforked process, which will start with a SIGSTOP, or PTRACE_EVENT_STOP if PTRACE_SEIZE was used. A waitpid(2) by the tracer will return a status value such that
  status>>8 == (SIGTRAP | (PTRACE_EVENT_VFORK<<8))
The PID of the new process can be retrieved with PTRACE_GETEVENTMSG.
PTRACE_O_TRACEVFORKDONE (since Linux 2.5.60)
Stop the tracee at the completion of the next vfork(2). A waitpid(2) by the tracer will return a status value such that
  status>>8 == (SIGTRAP | (PTRACE_EVENT_VFORK_DONE<<8))
The PID of the new process can (since Linux 2.6.18) be retrieved with PTRACE_GETEVENTMSG.
PTRACE_O_TRACESECCOMP (since Linux 3.5)
Stop the tracee when a seccomp(2) SECCOMP_RET_TRACE rule is triggered. A waitpid(2) by the tracer will return a status value such that
  status>>8 == (SIGTRAP | (PTRACE_EVENT_SECCOMP<<8))
While this triggers a PTRACE_EVENT stop, it is similar to a syscall-enter-stop. For details, see the note on PTRACE_EVENT_SECCOMP below. The seccomp event message data (from the SECCOMP_RET_DATA portion of the seccomp filter rule) can be retrieved with PTRACE_GETEVENTMSG.
PTRACE_O_SUSPEND_SECCOMP (since Linux 4.3)
Suspend the tracee's seccomp protections. This applies regardless of mode, and can be used when the tracee has not yet installed seccomp filters. That is, a valid use case is to suspend a tracee's seccomp protections before they are installed by the tracee, let the tracee install the filters, and then clear this flag when the filters should be resumed. Setting this option requires that the tracer have the CAP_SYS_ADMIN capability, not have any seccomp protections installed, and not have PTRACE_O_SUSPEND_SECCOMP set on itself.
PTRACE_GETEVENTMSG (since Linux 2.5.46)
Retrieve a message (as an unsigned long) about the ptrace event that just happened, placing it at the address data in the tracer. For PTRACE_EVENT_EXIT, this is the tracee's exit status. For PTRACE_EVENT_FORK, PTRACE_EVENT_VFORK, PTRACE_EVENT_VFORK_DONE, and PTRACE_EVENT_CLONE, this is the PID of the new process. For PTRACE_EVENT_SECCOMP, this is the seccomp(2) filter's SECCOMP_RET_DATA associated with the triggered rule. (addr is ignored.)
PTRACE_CONT
Restart the stopped tracee process. If data is nonzero, it is interpreted as the number of a signal to be delivered to the tracee; otherwise, no signal is delivered. Thus, for example, the tracer can control whether a signal sent to the tracee is delivered or not. (addr is ignored.)

PTRACE_SINGLESTEP

PTRACE_PEEKSIGINFO (منذ Linux 3.10)
استرداد هياكل siginfo_t دون إزالة الإشارات من قائمة انتظار. addr يشير إلى هيكل ptrace_peeksiginfo_args يحدد الموضع الترتيبي الذي يجب أن يبدأ منه نسخ الإشارات، وعدد الإشارات التي يجب نسخها. يتم نسخ هياكل siginfo_t إلى المخزن المؤقت الذي يشير إليه data. تحتوي القيمة المرتجعة على عدد الإشارات التي تم نسخها (يشير الصفر إلى عدم وجود إشارة مقابلة للموضع الترتيبي المحدد). داخل هياكل siginfo المرتجعة، يتضمن الحقل si_code معلومات (__SI_CHLD، __SI_FAULT، إلخ) غير متاحة للمساحة المستخدمة بخلاف ذلك.

                   to start copying signals */

PTRACE_GETSIGMASK (منذ Linux 3.11)
ضع نسخة من قناع الإشارات المحظورة (انظر sigprocmask(2)) في المخزن المؤقت الذي يشير إليه data، والذي يجب أن يكون مؤشرًا إلى مخزن مؤقت من النوع sigset_t. يحتوي الوسيط addr على حجم المخزن المؤقت الذي يشير إليه data (أي sizeof(sigset_t)).
PTRACE_SETSIGMASK (منذ Linux 3.11)
غيّر قناع الإشارات المحظورة (انظر sigprocmask(2)) إلى القيمة المحددة في المخزن المؤقت الذي يشير إليه data، والذي يجب أن يكون مؤشرًا إلى مخزن مؤقت من النوع sigset_t. يحتوي الوسيط addr على حجم المخزن المؤقت الذي يشير إليه data (أي sizeof(sigset_t)).
PTRACE_SETOPTIONS (منذ Linux 2.4.6؛ انظر BUGS للحصول على محاذير)
اضبط خيارات ptrace من data. (addr يتم تجاهله.) يتم تفسير data كقناع بت من الخيارات، والتي يتم تحديدها بالأعلام التالية:
PTRACE_O_EXITKILL (منذ Linux 3.8)
أرسل إشارة SIGKILL إلى المسلوب إذا خرج المقتفي. هذا الخيار مفيد لمقيّدي ptrace الذين يرغبون في التأكد من أن المسلوبين لا يستطيعون أبدًا الهروب من سيطرة المقتفي.
PTRACE_O_TRACECLONE (منذ Linux 2.5.46)
أوقف المسلوب عند الاستدعاء التالي لـ clone(2) وابدأ تلقائيًا تتبع العملية المستنسخة حديثًا، والتي ستبدأ بـ SIGSTOP، أو PTRACE_EVENT_STOP إذا تم استخدام PTRACE_SEIZE. waitpid(2) بواسطة المقتفي ستعيد قيمة status بحيث
  status>>8 == (SIGTRAP | (PTRACE_EVENT_CLONE<<8))
يمكن استرداد PID العملية الجديدة باستخدام PTRACE_GETEVENTMSG.
قد لا يلتقط هذا الخيار استدعاءات clone(2) في جميع الحالات. إذا استدعى المسلوب clone(2) مع العلم CLONE_VFORK، سيتم تسليم PTRACE_EVENT_VFORK بدلاً من ذلك إذا تم تعيين PTRACE_O_TRACEVFORK؛ وإلا، إذا استدعى المسلوب clone(2) مع تعيين إشارة الخروج إلى SIGCHLD، سيتم تسليم PTRACE_EVENT_FORK إذا تم تعيين PTRACE_O_TRACEFORK.
PTRACE_O_TRACEEXEC (منذ Linux 2.5.46)
أوقف المسلوب عند الاستدعاء التالي لـ execve(2). waitpid(2) بواسطة المقتفي ستعيد قيمة status بحيث
  status>>8 == (SIGTRAP | (PTRACE_EVENT_EXEC<<8))
إذا لم يكن الخيط الذي ينفذ قائد مجموعة الخيوط، فسيتم إعادة تعيين معرف الخيط إلى معرف قائد مجموعة الخيوط قبل هذا التوقف. منذ Linux 3.0، يمكن استرداد معرف الخيط السابق باستخدام PTRACE_GETEVENTMSG.
PTRACE_O_TRACEEXIT (منذ Linux 2.5.60)
أوقف المسلوب عند الخروج. waitpid(2) بواسطة المقتفي ستعيد قيمة status بحيث
  status>>8 == (SIGTRAP | (PTRACE_EVENT_EXIT<<8))
يمكن استرداد حالة خروج المسلوب باستخدام PTRACE_GETEVENTMSG.
يتم إيقاف المسلوب مبكرًا أثناء خروج العملية، عندما تكون السجلات متاحة لا تزال، مما يسمح للمقتفي برؤية مكان حدوث الخروج، بينما يتم إرسال إشعار الخروج العادي بعد انتهاء العملية من الخروج. على الرغم من أن السياق متاح، لا يمكن للمقتفي منع الخروج من الحدوث في هذه النقطة.

الموت تحت ptrace

عندما تتلقى عملية (ربما متعددة الخيوط) إشارة قتل (إشارة يكون تصرفها معينًا على SIG_DFL ويكون إجراءها الافتراضي هو قتل العملية)، تخرج جميع الخيوط. تبلغ العمليات المتتبعة بموتها إلى المتتبعين لها. يتم تسليم إشعار بهذا الحدث عبر waitpid(2).

لاحظ أن إشارة القتل ستتسبب أولاً في توقف تسليم الإشارة (على متعقب واحد فقط)، وفقط بعد حقنها بواسطة المتتبع (أو بعد إرسالها إلى خيط غير متعقب)، سيحدث الموت من الإشارة على جميع المتعقبين في عملية متعددة الخيوط. (مصطلح "توقف تسليم الإشارة" مشروح أدناه).

SIGKILL لا تولد توقف تسليم الإشارة وبالتالي لا يمكن للمتتبع قمعها. SIGKILL تقتل حتى أثناء استدعاءات النظام (لا يتم إنشاء توقف خروج استدعاء النظام قبل الموت بواسطة SIGKILL). التأثير الصافي هو أن SIGKILL تقتل العملية دائمًا (جميع خيوطها)، حتى لو كان بعض خيوط العملية متعقبة.

عندما يقوم المتعقب باستدعاء _exit(2)، فإنه يبلغ بموته إلى المتتبع الخاص به. لا تتأثر الخيوط الأخرى.

عندما يقوم أي خيط بتنفيذ exit_group(2)، يقوم كل متعقب في مجموعته الخيطية بالإبلاغ عن موته إلى المتتبع الخاص به.

إذا كان الخيار PTRACE_O_TRACEEXIT مفعلًا، فسيحدث PTRACE_EVENT_EXIT قبل الموت الفعلي. ينطبق هذا على الخروج عبر exit(2)، exit_group(2)، وموت الإشارات (باستثناء SIGKILL، اعتمادًا على إصدار النواة؛ انظر BUGS أدناه)، وعندما يتم تفكيك الخيوط في execve(2) في عملية متعددة الخيوط.

لا يمكن للمتتبع افتراض أن المتعقب المتوقف لا يزال موجودًا. هناك العديد من السيناريوهات التي قد يموت فيها المتعقب أثناء التوقف (مثل SIGKILL). لذلك، يجب أن يكون المتتبع مستعدًا للتعامل مع خطأ ESRCH في أي عملية ptrace. للأسف، يتم إرجاع نفس الخطأ إذا كان المتعقب موجودًا ولكنه غير متوقف بواسطة ptrace (للأوامر التي تتطلب متعقبًا متوقفًا)، أو إذا لم يتم تعقبه بواسطة العملية التي أصدرت استدعاء ptrace. يحتاج المتتبع إلى تتبع حالة التوقف/التشغيل للمتعقب، وتفسير ESRCH على أنها "مات المتعقب بشكل غير متوقع" فقط إذا كان يعلم أن المتعقب قد لوحظ وهو يدخل توقف ptrace. لاحظ أنه لا يوجد ضمان بأن waitpid(WNOHANG) سيبلغ بشكل موثوق عن حالة موت المتعقب إذا أعادت عملية ptrace ESRCH. قد تعيد waitpid(WNOHANG) القيمة 0 بدلاً من ذلك. بعبارة أخرى، قد يكون المتعقب "لم يمت تمامًا بعد"، ولكنه يرفض عمليات ptrace بالفعل.

لا يمكن للمتتبع افتراض أن المتعقب دائمًا ينهي حياته بالإبلاغ عن WIFEXITED(status) أو WIFSIGNALED(status)؛ هناك حالات لا يحدث فيها ذلك. على سبيل المثال، إذا قام خيط آخر غير قائد المجموعة الخيطية بتنفيذ execve(2)، فإنه يختفي؛ لن يتم رؤية معرف العملية الخاص به مرة أخرى، وسيتم الإبلاغ عن أي توقفات ptrace لاحقة تحت معرف العملية لقائد المجموعة الخيطية.

حالات التوقف

يمكن أن يكون المتعقب في حالتين: تشغيل أو توقف. لأغراض ptrace، تعتبر العملية المتوقفة في استدعاء نظام (مثل read(2)، pause(2)، إلخ) قيد التشغيل، حتى لو كانت العملية متوقفة لفترة طويلة. حالة المتعقب بعد PTRACE_LISTEN هي منطقة رمادية إلى حد ما: فهي ليست في أي توقف ptrace (لن تعمل أوامر ptrace عليها، وستقوم بتسليم إشعارات waitpid(2))، ولكن يمكن اعتبارها أيضًا "متوقفة" لأنها لا تنفذ تعليمات (غير مجدولة)، وإذا كانت في توقف جماعي قبل PTRACE_LISTEN، فلن تستجيب للإشارات حتى تتلقى SIGCONT.

هناك العديد من أنواع الحالات عندما يكون المتعقب متوقفًا، وفي مناقشات ptrace غالبًا ما يتم الخلط بينها. لذلك، من المهم استخدام مصطلحات دقيقة.

في صفحة الدليل هذه، تسمى أي حالة توقف يكون فيها المتعقب جاهزًا لقبول أوامر ptrace من المتتبع توقف ptrace. يمكن تقسيم توقفات ptrace إلى توقف تسليم الإشارة، توقف جماعي، توقف استدعاء النظام، توقفات PTRACE_EVENT، وما إلى ذلك. يتم وصف هذه الحالات المتوقفة بالتفصيل أدناه.

عندما يدخل المتعقب قيد التشغيل في توقف ptrace، فإنه يبلغ المتتبع الخاص به باستخدام waitpid(2) (أو إحدى استدعاءات النظام "wait" الأخرى). تفترض معظم صفحة الدليل هذه أن المتتبع ينتظر باستخدام:


pid = waitpid(pid_or_minus_1, &status, __WALL);

لا تتضمن علامة __WALL علامتي WSTOPPED و WEXITED، ولكنها تتضمن وظائفهما.

لا يُنصح بتعيين علامة WCONTINUED عند استدعاء waitpid(2): حالة "المتابعة" خاصة بالعملية واستهلاكها يمكن أن يربك الوالد الحقيقي للمتعقب.

قد يتسبب استخدام علامة WNOHANG في أن تعيد waitpid(2) القيمة 0 ("لا توجد نتائج انتظار متاحة بعد") حتى لو كان المتتبع يعرف أنه يجب أن يكون هناك إشعار. مثال:


errno = 0;
ptrace(PTRACE_CONT, pid, 0L, 0L);
if (errno == ESRCH) {
    /* tracee is dead */
    r = waitpid(tracee, &status, __WALL | WNOHANG);
    /* r can still be 0 here! */
}

توجد الأنواع التالية من توقفات ptrace: توقفات تسليم الإشارة، التوقفات الجماعية، توقفات PTRACE_EVENT، توقفات استدعاء النظام. يتم الإبلاغ عنها جميعًا بواسطة waitpid(2) مع WIFSTOPPED(status) صحيح. يمكن التمييز بينها بفحص القيمة status>>8، وإذا كان هناك غموض في تلك القيمة، عن طريق الاستعلام عن PTRACE_GETSIGINFO. (ملاحظة: لا يمكن استخدام الماكرو WSTOPSIG(status) لإجراء هذا الفحص، لأنه يعيد القيمة (status>>8) & 0xff.)

توقف تسليم الإشارة

عندما تتلقى عملية (ربما متعددة الخيوط) أي إشارة باستثناء SIGKILL، تختار النواة خيطًا عشوائيًا يعالج الإشارة. (إذا تم إنشاء الإشارة باستخدام tgkill(2)، يمكن اختيار الخيط المستهدف بشكل صريح بواسطة المتصل.) إذا كان الخيط المتعقب متعقبًا، فإنه يدخل توقف تسليم الإشارة. في هذه المرحلة، لم يتم تسليم الإشارة إلى العملية بعد، ويمكن قمعها بواسطة المتتبع. إذا لم يقم المتتبع بقمع الإشارة، فإنه يمرر الإشارة إلى المتعقب في عملية إعادة تشغيل ptrace التالية. تسمى هذه الخطوة الثانية من تسليم الإشارة حقن الإشارة في صفحة الدليل هذه. لاحظ أنه إذا كانت الإشارة محظورة، فلن يحدث توقف تسليم الإشارة حتى يتم إلغاء حظر الإشارة، مع الاستثناء المعتاد وهو أن SIGSTOP لا يمكن حظرها.

يتم ملاحظة توقف تسليم الإشارة بواسطة المتتبع على أنه waitpid(2) يعيد WIFSTOPPED(status) صحيحًا، مع الإشارة التي تعيدها WSTOPSIG(status). إذا كانت الإشارة هي SIGTRAP، فقد يكون هذا نوعًا مختلفًا من توقف ptrace؛ انظر قسمي "توقفات استدعاء النظام" و "execve" أدناه للحصول على التفاصيل. إذا أعادت WSTOPSIG(status) إشارة توقف، فقد يكون هذا توقفًا جماعيًا؛ انظر أدناه.

حقن وقمع الإشارة

بعد ملاحظة توقف تسليم الإشارة بواسطة المتتبع، يجب على المتتبع إعادة تشغيل المتعقب باستخدام الاستدعاء


ptrace(PTRACE_restart, pid, 0, sig)

حيث PTRACE_restart هو أحد عمليات ptrace لإعادة التشغيل. إذا كان sig يساوي 0، فلن يتم تسليم أي إشارة. بخلاف ذلك، يتم تسليم الإشارة sig. تسمى هذه العملية حقن الإشارة في صفحة الدليل هذه، للتمييز بينها وبين توقف تسليم الإشارة.

قد تكون قيمة sig مختلفة عن قيمة WSTOPSIG(status): يمكن للمتتبع التسبب في حقن إشارة مختلفة.

لاحظ أن الإشارة المقمعة لا تزال تتسبب في عودة استدعاءات النظام بشكل سابق لأوانه. في هذه الحالة، سيتم إعادة تشغيل استدعاءات النظام: سيلاحظ المتتبع أن المتعقب يعيد تنفيذ استدعاء النظام المقاطع (أو استدعاء النظام restart_syscall(2) لبضعة استدعاءات نظام تستخدم آلية مختلفة لإعادة التشغيل) إذا استخدم المتتبع PTRACE_SYSCALL. حتى استدعاءات النظام (مثل poll(2)) التي لا يمكن إعادة تشغيلها بعد الإشارة يتم إعادة تشغيلها بعد قمع الإشارة؛ ومع ذلك، توجد أخطاء في النواة تسبب فشل بعض استدعاءات النظام مع EINTR على الرغم من عدم حقن أي إشارة قابلة للملاحظة في المتعقب.

لا يُضمن أن عمليات ptrace لإعادة التشغيل الصادرة في توقفات ptrace بخلاف توقفات تسليم الإشارة ستقوم بحقن إشارة، حتى لو كان sig غير صفري. لا يتم الإبلاغ عن أي خطأ؛ قد يتم تجاهل sig غير الصفري ببساطة. يجب ألا يحاول مستخدمو Ptrace "إنشاء إشارة جديدة" بهذه الطريقة: استخدم tgkill(2) بدلاً من ذلك.

حقيقة أن عمليات حقن الإشارة قد يتم تجاهلها عند إعادة تشغيل المتعقب بعد توقفات ptrace التي ليست توقفات تسليم الإشارة هي سبب للارتباك بين مستخدمي ptrace. واحد نمطي

al scenario is that the tracer observes group-stop, mistakes it for signal-delivery-stop, restarts the tracee with


ptrace(PTRACE_restart, pid, 0, stopsig)

with the intention of injecting stopsig, but stopsig gets ignored and the tracee continues to run.

The SIGCONT signal has a side effect of waking up (all threads of) a group-stopped process. This side effect happens before signal-delivery-stop. The tracer can't suppress this side effect (it can only suppress signal injection, which only causes the SIGCONT handler to not be executed in the tracee, if such a handler is installed). In fact, waking up from group-stop may be followed by signal-delivery-stop for signal(s) other than SIGCONT, if they were pending when SIGCONT was delivered. In other words, SIGCONT may be not the first signal observed by the tracee after it was sent.

Stopping signals cause (all threads of) a process to enter group-stop. This side effect happens after signal injection, and therefore can be suppressed by the tracer.

In Linux 2.4 and earlier, the SIGSTOP signal can't be injected.

PTRACE_GETSIGINFO can be used to retrieve a siginfo_t structure which corresponds to the delivered signal. PTRACE_SETSIGINFO may be used to modify it. If PTRACE_SETSIGINFO has been used to alter siginfo_t, the si_signo field and the sig parameter in the restarting command must match, otherwise the result is undefined.

توقف جماعي

When a (possibly multithreaded) process receives a stopping signal, all threads stop. If some threads are traced, they enter a group-stop. Note that the stopping signal will first cause signal-delivery-stop (on one tracee only), and only after it is injected by the tracer (or after it was dispatched to a thread which isn't traced), will group-stop be initiated on all tracees within the multithreaded process. As usual, every tracee reports its group-stop separately to the corresponding tracer.

Group-stop is observed by the tracer as waitpid(2) returning with WIFSTOPPED(status) true, with the stopping signal available via WSTOPSIG(status). The same result is returned by some other classes of ptrace-stops, therefore the recommended practice is to perform the call


ptrace(PTRACE_GETSIGINFO, pid, 0, &siginfo)

The call can be avoided if the signal is not SIGSTOP, SIGTSTP, SIGTTIN, or SIGTTOU; only these four signals are stopping signals. If the tracer sees something else, it can't be a group-stop. Otherwise, the tracer needs to call PTRACE_GETSIGINFO. If PTRACE_GETSIGINFO fails with EINVAL, then it is definitely a group-stop. (Other failure codes are possible, such as ESRCH ("no such process") if a SIGKILL killed the tracee.)

If tracee was attached using PTRACE_SEIZE, group-stop is indicated by PTRACE_EVENT_STOP: status>>16 == PTRACE_EVENT_STOP. This allows detection of group-stops without requiring an extra PTRACE_GETSIGINFO call.

As of Linux 2.6.38, after the tracer sees the tracee ptrace-stop and until it restarts or kills it, the tracee will not run, and will not send notifications (except SIGKILL death) to the tracer, even if the tracer enters into another waitpid(2) call.

The kernel behavior described in the previous paragraph causes a problem with transparent handling of stopping signals. If the tracer restarts the tracee after group-stop, the stopping signal is effectively ignored—the tracee doesn't remain stopped, it runs. If the tracer doesn't restart the tracee before entering into the next waitpid(2), future SIGCONT signals will not be reported to the tracer; this would cause the SIGCONT signals to have no effect on the tracee.

Since Linux 3.4, there is a method to overcome this problem: instead of PTRACE_CONT, a PTRACE_LISTEN command can be used to restart a tracee in a way where it does not execute, but waits for a new event which it can report via waitpid(2) (such as when it is restarted by a SIGCONT).

توقفات PTRACE_EVENT

If the tracer sets PTRACE_O_TRACE_* options, the tracee will enter ptrace-stops called PTRACE_EVENT stops.

PTRACE_EVENT stops are observed by the tracer as waitpid(2) returning with WIFSTOPPED(status), and WSTOPSIG(status) returns SIGTRAP (or for PTRACE_EVENT_STOP, returns the stopping signal if tracee is in a group-stop). An additional bit is set in the higher byte of the status word: the value status>>8 will be


((PTRACE_EVENT_foo<<8) | SIGTRAP).

The following events exist:

PTRACE_EVENT_VFORK
Stop before return from vfork(2) or clone(2) with the CLONE_VFORK flag. When the tracee is continued after this stop, it will wait for child to exit/exec before continuing its execution (in other words, the usual behavior on vfork(2)).
PTRACE_EVENT_FORK
Stop before return from fork(2) or clone(2) with the exit signal set to SIGCHLD.
PTRACE_EVENT_CLONE
Stop before return from clone(2).
PTRACE_EVENT_VFORK_DONE
Stop before return from vfork(2) or clone(2) with the CLONE_VFORK flag, but after the child unblocked this tracee by exiting or execing.

For all four stops described above, the stop occurs in the parent (i.e., the tracee), not in the newly created thread. PTRACE_GETEVENTMSG can be used to retrieve the new thread's ID.

PTRACE_EVENT_EXEC
Stop before return from execve(2). Since Linux 3.0, PTRACE_GETEVENTMSG returns the former thread ID.
PTRACE_EVENT_EXIT
Stop before exit (including death from exit_group(2)), signal death, or exit caused by execve(2) in a multithreaded process. PTRACE_GETEVENTMSG returns the exit status. Registers can be examined (unlike when "real" exit happens). The tracee is still alive; it needs to be PTRACE_CONTed or PTRACE_DETACHed to finish exiting.
PTRACE_EVENT_STOP
Stop induced by PTRACE_INTERRUPT command, or group-stop, or initial ptrace-stop when a new child is attached (only if attached using PTRACE_SEIZE).
PTRACE_EVENT_SECCOMP
Stop triggered by a seccomp(2) rule on tracee syscall entry when PTRACE_O_TRACESECCOMP has been set by the tracer. The seccomp event message data (from the SECCOMP_RET_DATA portion of the seccomp filter rule) can be retrieved with PTRACE_GETEVENTMSG. The semantics of this stop are described in detail in a separate section below.

PTRACE_GETSIGINFO on PTRACE_EVENT stops returns SIGTRAP in si_signo, with si_code set to (event<<8) | SIGTRAP.

توقفات استدعاء النظام

If the tracee was restarted by PTRACE_SYSCALL or PTRACE_SYSEMU, the tracee enters syscall-enter-stop just prior to entering any system call (which will not be executed if the restart was using PTRACE_SYSEMU, regardless of any change made to registers at this point or how the tracee is restarted after this stop). No matter which method caused the syscall-entry-stop, if the tracer restarts the tracee with PTRACE_SYSCALL, the tracee enters syscall-exit-stop when the system call is finished, or if it is interrupted by a signal. (That is, signal-delivery-stop never happens between syscall-enter-stop and syscall-exit-stop; it happens after syscall-exit-stop.). If the tracee is continued using any other method (including PTRACE_SYSEMU), no syscall-exit-stop occurs. Note that all mentions PTRACE_SYSEMU apply equally to PTRACE_SYSEMU_SINGLESTEP.

However, even if the tracee was continued using PTRACE_SYSCALL, it is not guaranteed that the next stop will be a syscall-exit-stop. Other possibilities are that the tracee may stop in a PTRACE_EVENT stop (including seccomp stops), exit (if it entered _exit(2) or exit_group(2)), be killed by SIGKILL, or die silently (if it is a thread group leader, the execve(2) happened in another thread, and that thread is not traced by the same tracer; this situation is discussed later).

Syscall-enter-stop and syscall-exit-stop are observed by the tracer as waitpid(2) returning with WIFSTOPPED(status) true, and WSTOPSIG(status) giving SIGTRAP. If the PTRACE_O_TRACESYSGOOD option was set by the tracer, then WSTOPSIG(status) will give the value (SIGTRAP | 0x80).

ومع ذلك، تحدث توقفات استدعاء النظام بشكل متكرر جدًا (مرتين لكل استدعاء نظام)، وقد يكون إجراء PTRACE_GETSIGINFO لكل توقف استدعاء نظام مكلفًا إلى حد ما.

تسمح بعض معماريات التمييز بين الحالات عن طريق فحص السجلات. على سبيل المثال، على x86، rax == -ENOSYS في توقف دخول استدعاء النظام. نظرًا لأن SIGTRAP (مثل أي إشارة أخرى) تحدث دائمًا بعد توقف خروج استدعاء النظام، وفي هذه النقطة نادرًا ما يحتوي rax على -ENOSYS، تبدو SIGTRAP كـ "توقف استدعاء نظام ليس توقف دخول استدعاء نظام"؛ بعبارة أخرى، تبدو كـ "توقف خروج استدعاء نظام عشوائي" ويمكن اكتشافها بهذه الطريقة. ولكن هذا الاكتشاف هش ومن الأفضل تجنبه.

يعد استخدام الخيار PTRACE_O_TRACESYSGOOD الطريقة الموصى بها للتمييز بين توقفات استدعاء النظام وأنواع أخرى من توقفات ptrace، لأنه موثوق ولا يسبب عقوبة أداء.

توقفات دخول استدعاء النظام وتوقفات خروج استدعاء النظام غير قابلة للتمييز بينهما بواسطة المتعقب. يحتاج المتعقب إلى تتبع تسلسل توقفات ptrace حتى لا يفسر خطأً توقف دخول استدعاء النظام كتوقف خروج استدعاء النظام أو العكس. بشكل عام، يتبع توقف دخول استدعاء النظام دائمًا توقف خروج استدعاء النظام، أو توقف PTRACE_EVENT، أو موت المتتبع؛ لا يمكن أن تحدث أنواع أخرى من توقفات ptrace بينهما. ومع ذلك، لاحظ أن توقفات seccomp (انظر أدناه) يمكن أن تسبب توقفات خروج استدعاء النظام، دون توقفات دخول استدعاء النظام مسبقة. إذا كان seccomp قيد الاستخدام، فيجب توخي الحذر لعدم تفسير هذه التوقفات بشكل خاطئ كتوقفات دخول استدعاء النظام.

إذا، بعد توقف دخول استدعاء النظام، استخدم المتعقب أمر إعادة تشغيل غير PTRACE_SYSCALL، فلن يتم إنشاء توقف خروج استدعاء النظام.

PTRACE_GETSIGINFO على توقفات استدعاء النظام يعيد SIGTRAP في si_signo، مع تعيين si_code إلى SIGTRAP أو (SIGTRAP|0x80).

توقفات PTRACE_EVENT_SECCOMP (Linux 3.5 إلى Linux 4.7)

تغير سلوك توقفات PTRACE_EVENT_SECCOMP وتفاعلها مع أنواع أخرى من توقفات ptrace بين إصدارات النواة. توثق هذه الوثيقة السلوك من وقت تقديمها حتى Linux 4.7 (شامل). يوثق السلوك في إصدارات النواة اللاحقة في القسم التالي.

يحدث توقف PTRACE_EVENT_SECCOMP كلما تم تشغيل قاعدة SECCOMP_RET_TRACE. هذا مستقل عن أي طرق تم استخدامها لإعادة تشغيل استدعاء النظام. والجدير بالذكر أن seccomp لا يزال يعمل حتى لو تم إعادة تشغيل المتتبع باستخدام PTRACE_SYSEMU وتم تخطي استدعاء النظام هذا بشكل غير مشروط.

ستتصرف عمليات إعادة التشغيل من هذا التوقف كما لو أن التوقف قد حدث مباشرة قبل استدعاء النظام المعني. على وجه الخصوص، سيؤدي كل من PTRACE_SYSCALL و PTRACE_SYSEMU عادةً إلى توقف دخول استدعاء نظام لاحق. ومع ذلك، إذا كان رقم استدعاء النظام سالبًا بعد PTRACE_EVENT_SECCOMP، فسيتم تخطي كل من توقف دخول استدعاء النظام واستدعاء النظام نفسه. هذا يعني أنه إذا كان رقم استدعاء النظام سالبًا بعد PTRACE_EVENT_SECCOMP وتمت إعادة تشغيل المتتبع باستخدام PTRACE_SYSCALL، فإن التوقف التالي المرصود سيكون توقف خروج استدعاء نظام، بدلاً من توقف دخول استدعاء نظام الذي قد يكون متوقعًا.

توقفات PTRACE_EVENT_SECCOMP (منذ Linux 4.8)

بدءًا من Linux 4.8، تمت إعادة ترتيب توقف PTRACE_EVENT_SECCOMP ليحدث بين توقف دخول استدعاء النظام وتوقف خروج استدعاء النظام. لاحظ أن seccomp لم يعد يعمل (ولن يتم الإبلاغ عن PTRACE_EVENT_SECCOMP) إذا تم تخطي استدعاء النظام بسبب PTRACE_SYSEMU.

من الناحية الوظيفية، يتصرف توقف PTRACE_EVENT_SECCOMP بشكل مشابه لتوقف دخول استدعاء النظام (أي، ستؤدي الاستمرارات باستخدام PTRACE_SYSCALL إلى توقفات خروج استدعاء النظام، ويمكن تغيير رقم استدعاء النظام، كما يمكن رؤية أي سجلات أخرى معدلة بواسطة استدعاء النظام الذي سيتم تنفيذه.) لاحظ أنه قد يكون هناك، ولكن ليس بالضرورة، توقف دخول استدعاء نظام مسبق.

بعد توقف PTRACE_EVENT_SECCOMP، سيتم إعادة تشغيل seccomp، مع قاعدة SECCOMP_RET_TRACE تعمل الآن بنفس طريقة عمل SECCOMP_RET_ALLOW. على وجه التحديد، هذا يعني أنه إذا لم يتم تعديل السجلات أثناء توقف PTRACE_EVENT_SECCOMP، فسيتم السماح باستدعاء النظام بعد ذلك.

أوامر ptrace الاستعلامية وإعادة التشغيل

تتطلب معظم أوامر ptrace (كلها باستثناء PTRACE_ATTACH، PTRACE_SEIZE، PTRACE_TRACEME، PTRACE_INTERRUPT، و PTRACE_KILL) أن يكون المتتبع في حالة توقف ptrace، وإلا فإنها تفشل مع ESRCH.

عندما يكون المتتبع في حالة توقف ptrace، يمكن للمتعقب قراءة وكتابة البيانات إلى المتتبع باستخدام الأوامر الاستعلامية. تترك هذه الأوامر المتتبع في حالة توقف ptrace:


ptrace(PTRACE_PEEKTEXT/PEEKDATA/PEEKUSER, pid, addr, 0);
ptrace(PTRACE_POKETEXT/POKEDATA/POKEUSER, pid, addr, long_val);
ptrace(PTRACE_GETREGS/GETFPREGS, pid, 0, &struct);
ptrace(PTRACE_SETREGS/SETFPREGS, pid, 0, &struct);
ptrace(PTRACE_GETREGSET, pid, NT_foo, &iov);
ptrace(PTRACE_SETREGSET, pid, NT_foo, &iov);
ptrace(PTRACE_GETSIGINFO, pid, 0, &siginfo);
ptrace(PTRACE_SETSIGINFO, pid, 0, &siginfo);
ptrace(PTRACE_GETEVENTMSG, pid, 0, &long_var);
ptrace(PTRACE_SETOPTIONS, pid, 0, PTRACE_O_flags);

لاحظ أن بعض الأخطاء لا يتم الإبلاغ عنها. على سبيل المثال، قد لا يكون لتعيين معلومات الإشارة (siginfo) أي تأثير في بعض توقفات ptrace، ومع ذلك قد ينجح الاستدعاء (يعود 0 ولا يعين errno)؛ قد ينجح الاستعلام عن PTRACE_GETEVENTMSG ويعيد قيمة عشوائية إذا لم يتم توثيق توقف ptrace الحالي على أنه يعيد رسالة حدث ذات معنى.

يؤثر الاستدعاء


ptrace(PTRACE_SETOPTIONS, pid, 0, PTRACE_O_flags);

على متتبع واحد. يتم استبدال الأعلام الحالية للمتتبع. يتم توريث الأعلام للمتتبعين الجدد الذين تم إنشاؤهم و"إرفاقهم تلقائيًا" عبر خيارات PTRACE_O_TRACEFORK، PTRACE_O_TRACEVFORK، أو PTRACE_O_TRACECLONE النشطة.

مجموعة أخرى من الأوامر تجعل المتتبع المتوقف عن ptrace يعمل. لها الشكل:


ptrace(cmd, pid, 0, sig);

حيث cmd هو PTRACE_CONT، PTRACE_LISTEN، PTRACE_DETACH، PTRACE_SYSCALL، PTRACE_SINGLESTEP، PTRACE_SYSEMU، أو PTRACE_SYSEMU_SINGLESTEP. إذا كان المتتبع في حالة توقف تسليم الإشارة، فإن sig هي الإشارة المراد حقنها (إذا كانت غير صفرية). بخلاف ذلك، قد يتم تجاهل sig. (عند إعادة تشغيل متتبع من توقف ptrace غير توقف تسليم الإشارة، فإن الممارسة الموصى بها هي دائمًا تمرير 0 في sig.)

الإرفاق وفصل

يمكن إرفاق سلسلة (thread) بالمتعقب باستخدام الاستدعاء


ptrace(PTRACE_ATTACH, pid, 0, 0);

أو


ptrace(PTRACE_SEIZE, pid, 0, PTRACE_O_flags);

يرسل PTRACE_ATTACH SIGSTOP إلى هذه السلسلة. إذا أراد المتعقب أن يكون لـ SIGSTOP هذا تأثير، فإنه يحتاج إلى قمعه. لاحظ أنه إذا تم إرسال إشارات أخرى في نفس الوقت إلى هذه السلسلة أثناء الإرفاق، فقد يرى المتعقب المتتبع يدخل حالة توقف تسليم الإشارة مع إشارة (إشارات) أخرى أولاً! الممارسة المعتادة هي إعادة حقن هذه الإشارات حتى يتم رؤية SIGSTOP، ثم قمع حقن SIGSTOP. الخطأ التصميمي هنا هو أن مرفق ptrace وإشارة SIGSTOP مرسلة في نفس الوقت قد تتنافس وقد تفقد إشارة SIGSTOP المتزامنة.

نظرًا لأن الإرفاق يرسل SIGSTOP وعادة ما يقمعها المتعقب، فقد يتسبب ذلك في عودة خاطئة EINTR من استدعاء النظام الذي يتم تنفيذه حاليًا في المتتبع، كما هو موضح في قسم "حقن وقمع الإشارة".

منذ Linux 3.4، يمكن استخدام PTRACE_SEIZE بدلاً من PTRACE_ATTACH. لا يوقف PTRACE_SEIZE العملية المرفقة. إذا كنت بحاجة إلى إيقافها بعد الإرفاق (أو في أي وقت آخر) دون إرسال أي إشارات إليها، فاستخدم الأمر PTRACE_INTERRUPT.

ptrace(PTRACE_TRACEME, 0, 0, 0);

raise(SIGSTOP);

والسماح للعملية الأم (التي هي الآن المتعقب الخاص بنا) بملاحظة توقف تسليم الإشارة الخاص بنا.

إذا كانت خيارات PTRACE_O_TRACEFORK، PTRACE_O_TRACEVFORK، أو PTRACE_O_TRACECLONE سارية المفعول، فإن الأطفال الذين تم إنشاؤهم بواسطة، على التوالي، vfork(2) أو clone(2) مع علامة CLONE_VFORK، fork(2) أو clone(2) مع تعيين إشارة الخروج إلى SIGCHLD، وأنواع أخرى من clone(2)، يتم إرفاقها تلقائيًا بنفس المتعقب الذي تعقب الوالد الخاص بهم. يتم تسليم SIGSTOP للأطفال، مما يتسبب في دخولهم حالة توقف تسليم الإشارة بعد خروجهم من استدعاء النظام الذي أنشأهم.

يتم فصل المتتبع عن طريق:


ptrace(PTRACE_DETACH, pid, 0, sig);

PTRACE_DETACH هي عملية إعادة تشغيل؛ لذلك تتطلب أن يكون المتتبع في حالة توقف ptrace. إذا كان المتتبع في حالة توقف تسليم الإشارة، فيمكن حقن إشارة. بخلاف ذلك، قد يتم تجاهل المعلمة sig بصمت.

إذا كان المتتبع يعمل عندما يريد المتعقب فصله، فإن الحل المعتاد هو إرسال SIGSTOP (باستخدام tgkill(2)، للتأكد من وصولها إلى السلسلة الصحيحة)، والانتظار حتى يتوقف المتتبع في حالة توقف تسليم الإشارة لـ SIGSTOP ثم فصله (مع قمع حقن SIGSTOP). خطأ تصميمي هو أن هذا يمكن أن يتنافس مع إشارات SIGSTOP المتزامنة. تعقيد آخر هو أن المتتبع قد يدخل توقفات ptrace أخرى ويحتاج إلى إعادة تشغيله والانتظار مرة أخرى، حتى يتم رؤية SIGSTOP. تعقيد آخر هو التأكد من أن المتتبع ليس متوقفًا بالفعل بواسطة ptrace، لأنه لا يحدث تسليم إشارة أثناء كونه كذلك - حتى SIGSTOP.

SYNOPSIS

#include <sys/types.h>
#include <sys/ptrace.h>

long ptrace(enum __ptrace_request request, pid_t pid, void *addr, void *data);

DESCRIPTION

The name ptrace stands for "process trace". It provides a mechanism whereby one process (the "tracer") can observe and control the execution of another process (the "tracee"), and examine and modify the tracee's memory and registers. It is a powerful but complex interface, used primarily for implementing debuggers, strace(1), and similar tools.

The interpretation of the arguments depends on the value of the request argument.

Requests

The following values can be passed in the request argument:

PTRACE_TRACEME
Used by a process that wishes to be traced by its parent. When a process calls ptrace() with PTRACE_TRACEME, its parent process is notified (via waitpid(2)) that the child has stopped. The child process continues execution, but it is stopped in the kernel just before executing the first instruction of the user-level program. The parent can then use the other ptrace() requests to observe and control the child. A child process with this request being active can only be traced by its parent. Any attempt by a non-parent process to trace this child will fail with EPERM.
PTRACE_TODO
Attach to the process specified by pid, making it a tracee of the calling process (the tracer). The tracer must have appropriate privileges (see EPERM). The process specified by pid must be a direct child of the tracer. (This is true only for some architectures. For many architectures, any process that the tracer has permission to signal can be traced.) The tracee is stopped, and the tracer is notified (via waitpid(2)). If the tracee was trying to perform an operation that stops it (like read(2) or write(2)), that operation is not completed; the tracee is stopped before it starts. When the tracer receives the stop notification, it can examine and modify the tracee's memory and registers.
PTRACE_SYSCALL
Tell the tracee process to restart the syscall it was stopped in. If the tracee was stopped in system call entry, the system call is executed, and the tracee is stopped again at system call exit. If the tracee was stopped at system call exit, the tracee is restarted, and will run until the next system call entry or signal.

On some architectures (like x86), the tracee can be restarted to resume execution at the system call specified by the value in data. If data is non-zero, it is interpreted as a signal number, and that signal is delivered to the tracee instead of the normal stop-at-syscall-exit behavior. If data is zero, the syscall is executed and the tracee stops at syscall exit.

If the tracee is in a group-stop (e.g., due to kill(2) -SIGSTOP), the tracee is restarted (and the group-stop is canceled) and run until the next syscall-enter-stop, syscall-exit-stop, or signal-stop. The group-stop is not ended until the tracee is restarted.

If the tracee is in signal-delivery-stop, the signal is injected. The tracee is restarted and will run until the next syscall- or signal-stop. The pending signal is delivered.

If the tracee is in syscall-exit-stop, the tracee is restarted and run until the next syscall-enter-stop, syscall-exit-stop, or signal-stop.

Restarting from signal-delivery-stop is currently buggy, but the "as planned" behavior is to leave tracee stopped and waiting for SIGCONT. If the tracee is restarted from signal-delivery-stop, the pending signal is injected.

Handling of restart from group-stop is currently buggy, but the "as planned" behavior is to leave tracee stopped and waiting for SIGCONT. If the tracee is restarted from signal-delivery-stop, the pending signal is injected.

PTRACE_SINGLESTEP
Restarts the tracee process and advances it by a single instruction. The tracer is subsequently notified when the tracee stops after executing that instruction. This stop happens because the kernel inserts a special trap instruction (e.g., INT3 on x86) in place of the next instruction to be executed. This is typically used for single-stepping through code.
PTRACE_CONT
Restarts the tracee process. If data is non-zero, it is interpreted as a signal number, and that signal is delivered to the tracee. Otherwise (if data is zero), the tracee continues without a signal. The tracee will run until it is stopped by a signal or exits. If the tracee was stopped in system call entry or exit, it is restarted. The tracer is notified when the tracee stops again.
PTRACE_DETACH
Restarts the tracee process and removes the tracee's status from the tracer. The tracee continues execution, and the tracer will no longer receive stop notifications for it. If data is non-zero, it is interpreted as a signal number, and that signal is delivered to the tracee. Otherwise, the tracee continues without a signal. The tracee resumes execution from its current stopped state.
PTRACE_PEEKTEXT, PTRACE_PEEKDATA
Read a word (a `long') from the tracee's memory space at the location specified by addr. The value read is returned as the result of the ptrace call. The address addr must be aligned to a word boundary. Note: EIO is returned if the address is invalid.
PTRACE_PEEKUSER
Read a word from the tracee's user area structure at the specified offset addr. The value read is returned as the result of the ptrace call. The offset addr must be word-aligned. (The user area is a per-process structure holding information like the registers.) The offset is relative to the start of the user area structure. The exact layout of the user area is architecture-dependent. Note: EIO is returned if the address is invalid.
PTRACE_POKETEXT, PTRACE_POKEINSTRUCTION
Write a word (a `long') from data to the tracee's memory space at the location specified by addr. The address addr must be word-aligned. Note: EIO is returned if the address is invalid.
PTRACE_POKEDATA
Same as PTRACE_POKETEXT.
PTRACE_POKEUSER
Write a word from data to the tracee's user area structure at the specified offset addr. The offset addr must be word-aligned. Note: EIO is returned if the address is invalid.
PTRACE_SECCOMP_GET_FILTER
(Since Linux 3.5) Retrieve the seccomp BPF filter that is attached to the tracee. The filter is written to the buffer specified by data. The size of the buffer is specified by addr. The number of bytes written to the buffer is returned. If the tracee has no seccomp filter attached, 0 is returned and errno is not set. EINVAL is returned if the tracee is not using seccomp.
PTRACE_GET_SYSCALL_INFO
(Since Linux 4.3) Retrieve information about the current system call. The information is written to the buffer specified by data. The size of the buffer is specified by addr. The number of bytes available to be written by the kernel is returned. The structure written is struct ptrace_syscall_info.
PTRACE_GETEVENTMSG
(Since Linux 2.4.24 and 2.6.7) Retrieve a message about a process event. The message is written to the buffer specified by data. The size of the buffer is specified by addr. The number of bytes written is returned. The message is a 64-bit value. This request is only valid after the tracer has received a stop notification for one of the PTRACE_EVENT_* stops.

(Since Linux 2.4.6) Set options for the tracee. The options are specified by data. The options are OR-ed together. Valid options are:
PTRACE_O_TRACESYSGOOD
Make signal deliveries appear to the tracer as system call traps. If this option is set, a signal being delivered to the tracee will cause the tracee to stop at system call exit, and the tracer will be notified of a trap (strace -c will count this as a syscall). If the signal is being delivered to a non-traced process, the signal is delivered normally. This flag is intended to make tracing system calls more robust.
PTRACE_O_TRACEFORK
Stop the tracee when it forks a new process. The tracer will be notified of the new process ID via PTRACE_GETEVENTMSG. The new process is not stopped by default; the tracer must explicitly `continue' it with PTRACE_CONT or PTRACE_SYSCALL.
PTRACE_O_TRACEVFORK
Stop the tracee when it vforks a new process. The tracer will be notified of the new process ID via PTRACE_GETEVENTMSG. The new process is not stopped by default; the tracer must explicitly `continue' it with PTRACE_CONT or PTRACE_SYSCALL.
PTRACE_O_TRACECLONE
Stop the tracee when it clones a new process. The tracer will be notified of the new process ID via PTRACE_GETEVENTMSG. The new process is not stopped by default; the tracer must explicitly `continue' it with PTRACE_CONT or PTRACE_SYSCALL.
PTRACE_O_TRACEEXEC
Stop the tracee when it executes a new program via execve(2). The tracer will be notified of the execve event via PTRACE_EVENT_EXEC. The new program is not stopped by default; the tracer must explicitly `continue' it with PTRACE_CONT or PTRACE_SYSCALL.
PTRACE_O_TRACEVFORKDONE
(Since Linux 2.6.18) Stop the tracee when the child created by vfork(2) calls execve(2) or _exit(2).
PTRACE_O_TRACEEXIT
(Since Linux 2.6.14) Stop the tracee when it is exiting. The tracer will be notified of the exit event via PTRACE_EVENT_EXIT. The exit code is available via PTRACE_GETEVENTMSG.
PTRACE_O_SUSPEND_SECCOMP
(Since Linux 3.5) If the tracee has a seccomp filter attached, suspend it. The tracer can later resume it using PTRACE_SECCOMP_RESUME.

(Since Linux 3.14) This request is used to reset the credentials of the tracee to the same credentials as the tracer. This is primarily useful for debugging processes that have dropped privileges and subsequently regained them. The addr and data arguments are unused.

(Since Linux 3.5) Resume the tracee's seccomp filter after it has been suspended by PTRACE_O_SUSPEND_SECCOMP. The behavior of the tracee upon resumption depends on the value of data. If data is 0, the tracee continues execution normally. If data is non-zero, it is interpreted as a signal number, and that signal is delivered to the tracee.

Get the tracee's FPU registers. The registers are written to the buffer specified by data. The size of the buffer must be sufficient to hold the FPU register set structure. The exact structure is architecture-dependent.

Set the tracee's FPU registers from the buffer specified by data. The size of the buffer must be sufficient to hold the FPU register set structure. The exact structure is architecture-dependent.
PTRACE_GETREGSET
(Since Linux 2.6.2) Get a set of registers (e.g., general-purpose registers, FPU registers, etc.) from the tracee. The set of registers to be retrieved is specified by the addr argument. The retrieved registers are written to the buffer specified by data. The size of the buffer is specified by addr. The value returned is the number of bytes written to the buffer. Supported register sets are defined in <sys/reg.h>. For example, NT_PRSTATUS for general-purpose registers and NT_FPREGSET for FPU registers.
PTRACE_SETREGSET
(Since Linux 2.6.2) Set a set of registers in the tracee. The set of registers to be modified is specified by the addr argument. The new register values are read from the buffer specified by data. The size of the buffer is specified by addr. The value returned is the number of bytes read from the buffer. Supported register sets are defined in <sys/reg.h>.

(Since Linux 3.3) Attach to the process specified by pid, making it a tracee of the calling process (the tracer). This is similar to PTRACE_TODO, but it also implies enabling options like PTRACE_O_TRACEEXIT, PTRACE_O_TRACEFORK, PTRACE_O_TRACEVFORK, PTRACE_O_TRACECLONE, and PTRACE_O_TRACEEXEC, and also disables the automatic SIGTRAP delivery on execve. This makes it easier to handle complex multithreaded scenarios and execve events. The tracee is stopped and the tracer is notified (via waitpid(2)). If the tracee was trying to perform an operation that stops it, that operation is not completed; the tracee is stopped before it starts. When the tracer receives the stop notification, it can examine and modify the tracee's memory and registers. Unlike PTRACE_TODO, PTRACE_SEIZE can attach to any process that the tracer has permission to signal, not just direct children.

(Since Linux 3.2) Put the tracee process into a listening state. This is used in conjunction with PTRACE_SEIZE to trace a whole process group. When a process group is in a listening state, new threads created by traced threads will be automatically attached to the tracer.

Restarting after stops

When a tracee is stopped, the tracer can restart it using PTRACE_CONT, PTRACE_SYSCALL, PTRACE_SINGLESTEP, or PTRACE_DETACH. The behavior depends on the type of stop:

syscall-enter stop
The tracee stops just before executing a system call. It can be restarted using PTRACE_CONT (to continue until the next signal or exit), PTRACE_SYSCALL (to execute the system call and stop at exit), or PTRACE_SINGLESTEP (to execute a single instruction).
syscall-exit stop
The tracee stops just after returning from a system call. It can be restarted using PTRACE_CONT (to continue until the next signal or exit), or PTRACE_SYSCALL (to continue until the next system call entry).
signal-delivery stop
The tracee stops just before delivering a signal. It can be restarted using PTRACE_CONT (to deliver the signal and continue until the next signal or exit), PTRACE_SYSCALL (to deliver the signal and stop at the next system call entry/exit), or PTRACE_SINGLESTEP (to deliver the signal and stop after the next instruction).
group-stop
The tracee is stopped as part of a group-stop (e.g., due to kill(2) -SIGSTOP). It can be restarted using PTRACE_CONT or PTRACE_SYSCALL, which will cancel the group-stop and allow the tracee to continue execution. The tracee will stop again at the next signal or system call.

Restarting from group-stop is currently buggy, but the "as planned" behavior is to leave tracee stopped and waiting for SIGCONT. If the tracee is restarted from signal-delivery-stop, the pending signal is injected.

execve(2) under ptrace

When one thread in a multithreaded process calls execve(2), the kernel destroys all other threads in the process, and resets the thread ID of the execing thread to the thread group ID (process ID). (Or, to put things another way, when a multithreaded process does an execve(2), at completion of the call, it appears as though the execve(2) occurred in the thread group leader, regardless of which thread did the execve(2).) This resetting of the thread ID looks very confusing to tracers:

•
All other threads stop in PTRACE_EVENT_EXIT stop, if the PTRACE_O_TRACEEXIT option was turned on. Then all other threads except the thread group leader report death as if they exited via _exit(2) with exit code 0.
•
The execing tracee changes its thread ID while it is in the execve(2). (Remember, under ptrace, the "pid" returned from waitpid(2), or fed into ptrace calls, is the tracee's thread ID.) That is, the tracee's thread ID is reset to be the same as its process ID, which is the same as the thread group leader's thread ID.
•
Then a PTRACE_EVENT_EXEC stop happens, if the PTRACE_O_TRACEEXEC option was turned on.
•
If the thread group leader has reported its PTRACE_EVENT_EXIT stop by this time, it appears to the tracer that the dead thread leader "reappears from nowhere". (Note: the thread group leader does not report death via WIFEXITED(status) until there is at least one other live thread. This eliminates the possibility that the tracer will see it dying and then reappearing.) If the thread group leader was still alive, for the tracer this may look as if thread group leader returns from a different system call than it entered, or even "returned from a system call even though it was not in any system call". If the thread group leader was not traced (or was traced by a different tracer), then during execve(2) it will appear as if it has become a tracee of the tracer of the execing tracee.

All of the above effects are the artifacts of the thread ID change in the tracee.

The PTRACE_O_TRACEEXEC option is the recommended tool for dealing with this situation. First, it enables PTRACE_EVENT_EXEC stop, which occurs before execve(2) returns. In this stop, the tracer can use PTRACE_GETEVENTMSG to retrieve the tracee's former thread ID. (This feature was introduced in Linux 3.0.) Second, the PTRACE_O_TRACEEXEC option disables legacy SIGTRAP generation on execve(2).

When the tracer receives PTRACE_EVENT_EXEC stop notification, it is guaranteed that except this tracee and the thread group leader, no other threads from the process are alive.

On receiving the PTRACE_EVENT_EXEC stop notification, the tracer should clean up all its internal data structures describing the threads of this process, and retain only one data structure—one which describes the single still running tracee, with


thread ID == thread group ID == process ID.

Example: two threads call execve(2) at the same time:

*** we get syscall-enter-stop in thread 1: **
PID1 execve("/bin/foo", "foo" <unfinished ...>
*** we issue PTRACE_SYSCALL for thread 1 **
*** we get syscall-enter-stop in thread 2: **
PID2 execve("/bin/bar", "bar" <unfinished ...>
*** we issue PTRACE_SYSCALL for thread 2 **
*** we get PTRACE_EVENT_EXEC for PID0, we issue PTRACE_SYSCALL **
*** we get syscall-exit-stop for PID0: **
PID0 <... execve resumed> )             = 0

If the PTRACE_O_TRACEEXEC option is not in effect for the execing tracee, and if the tracee was PTRACE_ATTACHed rather that PTRACE_SEIZEd, the kernel delivers an extra SIGTRAP to the tracee after execve(2) returns. This is an ordinary signal (similar to one which can be generated by kill -TRAP), not a special kind of ptrace-stop. Employing PTRACE_GETSIGINFO for this signal returns si_code set to 0 (SI_USER). This signal may be blocked by signal mask, and thus may be delivered (much) later.

Usually, the tracer (for example, strace(1)) would not want to show this extra post-execve SIGTRAP signal to the user, and would suppress its delivery to the tracee (if SIGTRAP is set to SIG_DFL, it is a killing signal). However, determining which SIGTRAP to suppress is not easy. Setting the PTRACE_O_TRACEEXEC option or using PTRACE_SEIZE and thus suppressing this extra SIGTRAP is the recommended approach.

Real parent

The ptrace API (ab)uses the standard UNIX parent/child signaling over waitpid(2). This used to cause the real parent of the process to stop receiving several kinds of waitpid(2) notifications when the child process is traced by some other process.

Many of these bugs have been fixed, but as of Linux 2.6.38 several still exist; see BUGS below.

As of Linux 2.6.38, the following is believed to work correctly:

•
exit/death by signal is reported first to the tracer, then, when the tracer consumes the waitpid(2) result, to the real parent (to the real parent only when the whole multithreaded process exits). If the tracer and the real parent are the same process, the report is sent only once.

RETURN VALUE

On success, the PTRACE_PEEK* operations return the requested data (but see NOTES), the PTRACE_SECCOMP_GET_FILTER operation returns the number of instructions in the BPF program, the PTRACE_GET_SYSCALL_INFO operation returns the number of bytes available to be written by the kernel, and other operations return zero.

On error, all operations return -1, and errno is set to indicate the error. Since the value returned by a successful PTRACE_PEEK* operation may be -1, the caller must clear errno before the call, and then check it afterward to determine whether or not an error occurred.

ERRORS

EBUSY
(i386 only) There was an error with allocating or freeing a debug register.
EFAULT
There was an attempt to read from or write to an invalid area in the tracer's or the tracee's memory, probably because the area wasn't mapped or accessible. Unfortunately, under Linux, different variations of this fault will return EIO or EFAULT more or less arbitrarily.
EINVAL
An attempt was made to set an invalid option.
EIO
op is invalid, or an attempt was made to read from or write to an invalid area in the tracer's or the tracee's memory, or there was a word-alignment violation, or an invalid signal was specified during a restart operation.
EPERM
The specified process cannot be traced. This could be because the tracer has insufficient privileges (the required capability is CAP_SYS_PTRACE); unprivileged processes cannot trace processes that they cannot send signals to or those running set-user-ID/set-group-ID programs, for obvious reasons. Alternatively, the process may already be being traced, or (before Linux 2.6.26) be init(1) (PID 1).
ESRCH
The specified process does not exist, or is not currently being traced by the caller, or is not stopped (for operations that require a stopped tracee).

STANDARDS

None.

HISTORY

SVr4, 4.3BSD.

Before Linux 2.6.26, init(1), the process with PID 1, may not be traced.

NOTES

Although arguments to ptrace() are interpreted according to the prototype given, glibc currently declares ptrace() as a variadic function with only the op argument fixed. It is recommended to always supply four arguments, even if the requested operation does not use them, setting unused/ignored arguments to 0L or (void *) 0.

A tracees parent continues to be the tracer even if that tracer calls execve(2).

The layout of the contents of memory and the USER area are quite operating-system- and architecture-specific. The offset supplied, and the data returned, might not entirely match with the definition of struct user.

The size of a "word" is determined by the operating-system variant (e.g., for 32-bit Linux it is 32 bits).

This page documents the way the ptrace() call works currently in Linux. Its behavior differs significantly on other flavors of UNIX. In any case, use of ptrace() is highly specific to the operating system and architecture.

يمكن لعملية تمتلك القدرة CAP_SYS_PTRACE تحديث الملف /proc/sys/kernel/yama/ptrace_scope بإحدى القيم التالية:

0 ("أذونات ptrace الكلاسيكية")
لا توجد قيود إضافية على العمليات التي تجري فحوصات PTRACE_MODE_ATTACH (تجاوز تلك المفروضة بواسطة LSM cap المشترك ووحدات LSM الأخرى).
استخدام PTRACE_TRACEME لم يتغير.
1 ("ptrace مقيد") [القيمة الافتراضية]
عند إجراء عملية تتطلب فحص PTRACE_MODE_ATTACH، يجب على العملية المتصلة إما أن تمتلك القدرة CAP_SYS_PTRACE في مساحة المستخدم الخاصة بالهدف أو يجب أن يكون لديها علاقة محددة مسبقًا مع العملية المستهدفة. افتراضيًا، العلاقة المحددة مسبقًا هي أن العملية المستهدفة يجب أن تكون سليلًا للمتصل.
يمكن للعملية المستهدفة استخدام عملية prctl(2) PR_SET_PTRACER لتحديد معرف PID إضافي مسموح له بإجراء عمليات PTRACE_MODE_ATTACH على الهدف. انظر ملف مصدر النواة Documentation/admin-guide/LSM/Yama.rst (أو Documentation/security/Yama.txt قبل Linux 4.13) لمزيد من التفاصيل.
استخدام PTRACE_TRACEME لم يتغير.
2 ("مرفق المسؤول فقط")
فقط العمليات التي تمتلك القدرة CAP_SYS_PTRACE في مساحة المستخدم الخاصة بالهدف قد تجري عمليات PTRACE_MODE_ATTACH أو تتتبع الأطفال الذين يستخدمون PTRACE_TRACEME.
3 ("لا مرفق")
لا يمكن لأي عملية إجراء عمليات PTRACE_MODE_ATTACH أو تتبع الأطفال الذين يستخدمون PTRACE_TRACEME.
بمجرد كتابة هذه القيمة في الملف، لا يمكن تغييرها.

فيما يتعلق بالقيم 1 و 2، لاحظ أن إنشاء مساحة مستخدم جديدة يلغي فعليًا الحماية التي توفرها Yama. هذا لأنه لدى عملية في مساحة المستخدم الأصلية يتطابق معرف المستخدم الفعال الخاص بها مع معرف المستخدم لمنشئ مساحة فرعية جميع القدرات (بما في ذلك CAP_SYS_PTRACE) عند إجراء
