NAME

pt-find - find MySQL tables and other objects that match criteria

This manual page is for Percona Toolkit version 3.5.0.

SYNOPSIS

pt-find --host=HOST --port=PORT --user=USER --password=PASS
        [option]... [test]...

DESCRIPTION

pt-find is a powerful Perl-based tool for finding MySQL tables and other database objects that match a wide variety of criteria. It's particularly useful for identifying tables that might need attention, such as those that are old, large, or have specific properties. It can also be used to find stored procedures, functions, and triggers that match specific patterns.

The tool works by querying the database's information schema and running various `SHOW` statements. It then applies a set of tests (defined by command-line options) to filter the results. Actions can then be performed on the matched objects, such as printing their names, executing commands, or dropping them (with extreme caution).

Key features include:

  • Flexible testing criteria for tables, databases, columns, and other objects.
  • Support for various data types and formats in tests (strings, numbers, sizes, dates, regular expressions, SQL LIKE patterns).
  • Ability to perform actions on matched objects (e.g., print, execute, drop).
  • User-friendly output and options for controlling verbosity.
  • Integration with Percona Toolkit's common options for host, user, password, etc.

TESTS

Most tests check some criterion against a column of SHOW TABLE STATUS output. Numeric arguments can be specified as +n for greater than n, -n for less than n, and n for exactly n. All numeric options can take an optional suffix multiplier of k, M or G (1_024, 1_048_576, and 1_073_741_824 respectively). All patterns are Perl regular expressions (see 'man perlre') unless specified as SQL LIKE patterns.

Dates and times are all measured relative to the same instant, when pt-find first asks the database server what time it is. All date and time manipulation is done in SQL, so if you say to find tables modified 5 days ago, that translates to SELECT DATE_SUB(CURRENT_TIMESTAMP, INTERVAL 5 DAY). If you specify "--day-start", if course it's relative to CURRENT_DATE instead.

However, table sizes and other metrics are not consistent at an instant in time. It can take some time for MySQL to process all the SHOW queries, and pt-find can't do anything about that. These measurements are as of the time they're taken.

If you need some test that's not in this list, file a feature request at https://jira.percona.com/projects/PT.

--autoinc
type: string; group: Tests

Table's next AUTO_INCREMENT is n. This tests the Auto_increment column.

--avgrowlen
type: size; group: Tests

Table avg row len is n bytes. This tests the Avg_row_length column. The specified size can be "NULL" to test where Avg_row_length IS NULL.

--checksum
type: string; group: Tests

Table checksum is n. This tests the Checksum column.

--cmin
type: size; group: Tests

Table was created n minutes ago. This tests the Create_time column.

--collation
type: string; group: Tests

Table collation matches pattern. This tests the Collation column.

--column-name
type: string; group: Tests

A column name in the table matches pattern.

--column-type
type: string; group: Tests

A column in the table matches this type (case-insensitive).

Examples of types are: varchar, char, int, smallint, bigint, decimal, year, timestamp, text, enum.

--comment
type: string; group: Tests

Table comment matches pattern. This tests the Comment column.

--connection-id
type: string; group: Tests

Table name has nonexistent MySQL connection ID. This tests the table name for a pattern. The argument to this test must be a Perl regular expression that captures digits like this: (\d+). If the table name matches the pattern, these captured digits are taken to be the MySQL connection ID of some process. If the connection doesn't exist according to SHOW FULL PROCESSLIST, the test returns true. If the connection ID is greater than pt-find's own connection ID, the test returns false for safety.

Why would you want to do this? If you use MySQL statement-based replication, you probably know the trouble temporary tables can cause. You might choose to work around this by creating real tables with unique names, instead of temporary tables. One way to do this is to append your connection ID to the end of the table, thusly: scratch_table_12345. This assures the table name is unique and lets you have a way to find which connection it was associated with. And perhaps most importantly, if the connection no longer exists, you can assume the connection died without cleaning up its tables, and this table is a candidate for removal.

The argument to use for "--connection-id" is "\D_(\d+)$". That finds tables with a series of numbers at the end, preceded by an underscore and some non-number character (the latter criterion prevents from examining tables with a date at the end, which people tend to do: baron_scratch_2007_05_07 for example). It's better to keep the scratch tables separate.

If you do this, make sure the user pt-find runs as has the PROCESS privilege! Otherwise it will only see connections from the same user, and might think some tables are ready to remove when they're still in use. For safety, pt-find checks this for you.

See also "--server-id".

--server-id
type: string; group: Tests

Table name contains the server ID. If you create temporary tables with the naming convention explained in "--connection-id", but also add the server ID of the server on which the tables are created, then you can use this pattern match to ensure tables are dropped only on the server they're created on. This prevents a table from being accidentally dropped on a replica while it's in use (provided that your server IDs are all unique, which they should be for replication to work).

For example, on the replication source (server ID 22) you create a table called scratch_table_22_12345. If you see this table on the replica (server ID 23), you might think it can be dropped safely if there's no such connection 12345. But if you also force the name to match the server ID with "--server-id '\D_(\d+)_\d+$'", the table won't be dropped on the replica.

--tablesize
type: size; group: Tests

pt-archiver(1p)

Archive MySQL data

Author: Percona Toolkit Team <info@percona.com>

Version: 3.6.1

Description: pt-archiver archives data from a MySQL table. It can be used to archive data to another table, or to a file. It can also be used to delete old data from a table.

SYNOPSIS

pt-archiver [OPTIONS] DSN

DESCRIPTION

pt-archiver archives data from a MySQL table. It can be used to archive data to another table, or to a file. It can also be used to delete old data from a table.

OPTIONS

--source DSN
The DSN for the source database. This is a DSN, not a database name. You can specify a host, port, and socket, as well as a username and password.
--dest DSN
The DSN for the destination database. This is a DSN, not a database name. You can specify a host, port, and socket, as well as a username and password.
--file FILE
The file to archive the data to. If this option is specified, the data will be archived to a file instead of another table.
--table TABLE
The table to archive the data from. If this option is not specified, pt-archiver will try to guess the table name from the DSN.
--where WHERE
A WHERE clause to specify which rows to archive. If this option is not specified, all rows will be archived.
--limit LIMIT
The number of rows to archive at a time. If this option is not specified, pt-archiver will archive all rows at once.
--txn-size TXN_SIZE
The number of rows to include in each transaction. If this option is not specified, pt-archiver will use a default value.
--sleep SLEEP
The number of seconds to sleep between transactions. If this option is not specified, pt-archiver will not sleep.
--dry-run
Print the SQL statements that would be executed, but do not execute them.
--help
Show help message and exit.

EXAMPLES

Archive data from the table `logs` to the table `logs_archive`:

pt-archiver --source mysql://user:password@host:port/database --dest mysql://user:password@host:port/database --table logs --where 'ts < NOW() - INTERVAL 7 DAY' --limit 1000
