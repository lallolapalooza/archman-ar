الاسم

pthread_mutex_lock, pthread_mutex_trylock, pthread_mutex_unlock — قفل وإلغاء قفل mutex

الصيغة

#include <pthread.h>
int pthread_mutex_lock(pthread_mutex_t *mutex);
int pthread_mutex_trylock(pthread_mutex_t *mutex);
int pthread_mutex_unlock(pthread_mutex_t *mutex);

الوصف

سيتم قفل كائن mutex الذي يشير إليه mutex بواسطة استدعاء لـ pthread_mutex_lock() الذي يعيد صفرًا أو [EOWNERDEAD]. إذا كان mutex مقفلاً بالفعل بواسطة خيط آخر، يجب أن يتوقف الخيط المستدعي حتى يصبح mutex متاحًا. يجب أن تعود هذه العملية مع كائن mutex الذي يشير إليه mutex في حالة مقفلة والخيط المستدعي هو مالكه. إذا حاول خيط إعادة قفل mutex قام بقفله بالفعل، فسيتصرف pthread_mutex_lock() كما هو موصوف في عمود إعادة القفل في الجدول التالي. إذا حاول خيط إلغاء قفل mutex لم يقفله أو mutex غير مقفل، فسيتصرف pthread_mutex_unlock() كما هو موصوف في عمود إلغاء القفل عند عدم كونك المالك في الجدول التالي.

إذا كان نوع mutex هو PTHREAD_MUTEX_DEFAULT، فقد يتوافق سلوك pthread_mutex_lock() مع أحد أنواع mutex القياسية الثلاثة الأخرى كما هو موصوف في الجدول أعلاه. إذا لم يتوافق مع أحد هذه الأنواع الثلاثة، فإن السلوك غير محدد في الحالات التي تحمل علامة †.

حيث تشير الجدول إلى سلوك متكرر، يجب أن يحتفظ mutex بمفهوم عد القفل. عندما يكتسب خيط mutex بنجاح لأول مرة، يجب تعيين عد القفل إلى واحد. في كل مرة يقوم فيها خيط بإعادة قفل هذا mutex، يجب زيادة عد القفل بمقدار واحد. في كل مرة يقوم فيها الخيط بإلغاء قفل mutex، يجب تخفيض عد القفل بمقدار واحد. عندما يصل عد القفل إلى الصفر، يجب أن يصبح mutex متاحًا للخيوط الأخرى لاكتسابه.

تكون وظيفة pthread_mutex_trylock() مكافئة لـ pthread_mutex_lock()، باستثناء أنه إذا كان كائن mutex الذي يشير إليه mutex مقفلاً حاليًا (بواسطة أي خيط، بما في ذلك الخيط الحالي)، فسوف تعود المكالمة فورًا. إذا كان نوع mutex هو PTHREAD_MUTEX_RECURSIVE وكان mutex مملوكًا حالياً للخيط المستدعي، يجب زيادة عد قفل mutex بمقدار واحد ويجب أن تعود وظيفة pthread_mutex_trylock() بنجاح فورًا.

تقوم وظيفة pthread_mutex_unlock() بتحرير كائن mutex الذي يشير إليه mutex. تعتمد طريقة تحرير mutex على سمة نوع mutex. إذا كانت هناك خيوط عالقة على كائن mutex الذي يشير إليه mutex عند استدعاء pthread_mutex_unlock()، مما يؤدي إلى إتاحة mutex، فإن سياسة الجدولة ستحدد أي خيط سيحصل على mutex.

(في حالة mutexes PTHREAD_MUTEX_RECURSIVE، يصبح mutex متاحًا عندما يصل العد إلى الصفر ولم يعد للخيط المستدعي أي أقفال على هذا mutex.)

إذا تم تسليم إشارة إلى خيط ينتظر mutex، عند العودة من معالج الإشارة، يجب أن يستأنف الخيط انتظار mutex كما لو لم يتم مقاطعته.

إذا كان mutex mutex متينًا وانتهت العملية التي تحتوي على الخيط المالك أثناء الاحتفاظ بقفل mutex، فإن استدعاء pthread_mutex_lock() سيعيد قيمة الخطأ [EOWNERDEAD]. إذا كان mutex mutex متينًا وانتهى الخيط المالك أثناء الاحتفاظ بقفل mutex، قد يعيد استدعاء pthread_mutex_lock() قيمة الخطأ [EOWNERDEAD] حتى لو لم تنته العملية التي يوجد بها الخيط المالك. في هذه الحالات، يتم قفل mutex بواسطة الخيط ولكن الحالة التي يحميها يتم تمييزها على أنها غير متسقة. يجب على التطبيق التأكد من أن الحالة تم جعلها متسقة لإعادة الاستخدام وعند اكتمال ذلك، يجب استدعاء pthread_mutex_consistent(). إذا لم يتمكن التطبيق من استعادة الحالة، فيجب عليه إلغاء قفل mutex دون استدعاء مسبق لـ pthread_mutex_consistent()، وبعد ذلك يتم تمييز mutex على أنه غير قابل للاستخدام بشكل دائم.

إذا كان mutex لا يشير إلى كائن mutex تم تهيئته، فإن سلوك pthread_mutex_lock() و pthread_mutex_trylock() و pthread_mutex_unlock() غير محدد.

قيمة الإرجاع

في حالة النجاح، تعيد وظائف pthread_mutex_lock() و pthread_mutex_trylock() و pthread_mutex_unlock() القيمة صفر؛ بخلاف ذلك، سيتم إرجاع رقم خطأ للإشارة إلى الخطأ.

الأخطاء

ستفشل وظائف pthread_mutex_lock() و pthread_mutex_trylock() إذا:

EAGAIN
لم يكن من الممكن الحصول على mutex لأنه تم تجاوز الحد الأقصى لعدد الأقفال المتكررة لـ mutex.
EINVAL
تم إنشاء mutex بسمة البروتوكول التي تحمل القيمة PTHREAD_PRIO_PROTECT وكانت أولوية الخيط المستدعي أعلى من سقف الأولوية الحالي لـ mutex.
ENOTRECOVERABLE

الحالة التي يحميها mutex غير قابلة للاسترداد.
EOWNERDEAD

الـ mutex هو mutex متين وانتهت العملية التي تحتوي على الخيط السابق المالك أثناء الاحتفاظ بقفل mutex. سيتم الحصول على قفل mutex بواسطة الخيط المستدعي والأمر متروك للمالك الجديد لجعل الحالة متسقة.

ستفشل وظيفة pthread_mutex_lock() إذا:

EDEADLK
نوع mutex هو PTHREAD_MUTEX_ERRORCHECK والخيط الحالي يمتلك بالفعل mutex.

NAME

pthread_mutex_lock, pthread_mutex_trylock, pthread_mutex_unlock - POSIX mutex operations

SYNOPSIS

Include Header

#include <pthread.h>

Compile and link with -pthread.

Link with Threads Library

-lpthread

pthread_mutex_lock

int pthread_mutex_lock(pthread_mutex_t *mutex);

pthread_mutex_trylock

int pthread_mutex_trylock(pthread_mutex_t *mutex);

pthread_mutex_unlock

int pthread_mutex_unlock(pthread_mutex_t *mutex);

DESCRIPTION

The pthread_mutex_lock() function shall lock the mutex object pointed to by mutex. If the mutex is already locked by another thread, the calling thread shall block until the mutex becomes available. The calling thread attempts to lock the mutex.

The pthread_mutex_trylock() function shall attempt to lock the mutex object pointed to by mutex. If the mutex is already locked by another thread, the call shall return immediately. Otherwise, the mutex is locked and returned to the calling thread.

The pthread_mutex_unlock() function shall unlock the mutex object pointed to by mutex. The calling thread must own the mutex. If the mutex is successfully unlocked, then no thread waiting to lock the mutex shall remain blocked. If any threads are waiting to lock the mutex, one of them shall be unblocked. The exact thread to be unblocked is the one that made the earliest (and undetected by any other pair of callers) call to lock the mutex.

If the calling thread tries to unlock a mutex it does not own, or a mutex that is not locked, an implementation may return an error or leave the mutex in an undefined state.

If a thread attempts to lock a mutex that it has already locked, and the mutex is not initialized with the PTHREAD_MUTEX_RECURSIVE type attribute, it shall deadlock.

If a thread attempts to lock a mutex that is initialized with the PTHREAD_MUTEX_RECURSIVE type attribute and that the calling thread already owns, the mutex shall be successfully locked by the calling thread. The recursive locking count for the mutex shall be incremented. The mutex shall be successfully unlocked only when the calling thread has performed a corresponding number of unlock operations that matches the number of lock operations.

Robust mutexes provide a mechanism for handling the termination of a thread while it owns a mutex lock. When a thread terminates while holding a robust mutex lock, the mutex enters a "robust" state. If a subsequent call to pthread_mutex_lock() or pthread_mutex_trylock() attempts to acquire a mutex in a "robust" state, and the mutex is successfully acquired, the function shall return [EOWNERDEAD] to indicate that the previous owner died while holding the lock. The calling thread can then recover the mutex's state using pthread_mutex_consistent() and then use the mutex normally. For non-robust mutexes, the state of the mutex becomes undefined when the owner terminates.

RETURN VALUE

On success, these functions shall return 0 and set the mutex state appropriately. On failure, they shall return a non-zero error number.

ERRORS

The pthread_mutex_lock() and pthread_mutex_trylock() functions shall fail if:

EAGAIN
The mutex could not be acquired because it was already locked, and the mutex type is PTHREAD_MUTEX_ERRORCHECK and the current thread already owns the mutex.
EDEADLK
A deadlock condition was detected.
EINVAL
The value specified by the mutex argument does not refer to an initialized mutex object.
EOWNERDEAD

The mutex is a robust mutex and the previous owning thread terminated while holding the mutex lock. The mutex lock shall be acquired by the calling thread and it is up to the new owner to make the state consistent.

The pthread_mutex_trylock() function shall fail if:

EBUSY
The mutex could not be acquired because it was already locked.

The pthread_mutex_unlock() function shall fail if:

EPERM
The mutex type is PTHREAD_MUTEX_ERRORCHECK or PTHREAD_MUTEX_RECURSIVE, or the mutex is a robust mutex, and the current thread does not own the mutex.

The pthread_mutex_lock() and pthread_mutex_trylock() functions may fail if:

EOWNERDEAD

The mutex is a robust mutex and the previous owning thread terminated while holding the mutex lock. The mutex lock shall be acquired by the calling thread and it is up to the new owner to make the state consistent.

The pthread_mutex_lock() function may fail if:

EDEADLK
A deadlock condition was detected.

These functions shall not return an error code of [EINTR].

The following sections are informative.

EXAMPLES

None.

APPLICATION USAGE

Applications that have assumed that non-zero return values are errors will need updating for use with robust mutexes, since a valid return for a thread acquiring a mutex which is protecting a currently inconsistent state is [EOWNERDEAD]. Applications that do not check the error returns, due to ruling out the possibility of such errors arising, should not use robust mutexes. If an application is supposed to work with normal and robust mutexes it should check all return values for error conditions and if necessary take appropriate action.

RATIONALE

Mutex objects are intended to serve as a low-level primitive from which other thread synchronization functions can be built. As such, the implementation of mutexes should be as efficient as possible, and this has ramifications on the features available at the interface.

The mutex functions and the particular default settings of the mutex attributes have been motivated by the desire to not preclude fast, inlined implementations of mutex locking and unlocking.

Since most attributes only need to be checked when a thread is going to be blocked, the use of attributes does not slow the (common) mutex-locking case.

Likewise, while being able to extract the thread ID of the owner of a mutex might be desirable, it would require storing the current thread ID when each mutex is locked, and this could incur unacceptable levels of overhead. Similar arguments apply to a mutex_tryunlock operation.

For further rationale on the extended mutex types, see the Rationale (Informative) volume of POSIX.1‐2017, Threads Extensions.

If an implementation detects that the value specified by the mutex argument does not refer to an initialized mutex object, it is recommended that the function should fail and report an [EINVAL] error.
