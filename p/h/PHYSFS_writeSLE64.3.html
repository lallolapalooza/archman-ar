Error Codes

The following are possible error codes returned by PhysicsFS functions.

PHYSFS_ERR_WRITE_DIRECORY
لم يتم تحديد دليل للكتابة.
PHYSFS_ERR_OPEN_FOR_READING
تمت الكتابة إلى ملف مفتوح للقراءة.
PHYSFS_ERR_OPEN_FOR_WRITING
تمت القراءة من ملف مفتوح للكتابة.
PHYSFS_ERR_NOT_A_FILE
كان مطلوبًا ملف، ولكن تم الحصول على دليل (وما إلى ذلك).
PHYSFS_ERR_READ_ONLY
تمت الكتابة إلى نظام ملفات للقراءة فقط.
PHYSFS_ERR_CORRUPT
تم العثور على بيانات تالفة.
PHYSFS_ERR_SYMLINK_LOOP
حلقة ارتباط رمزي لا نهائية.
PHYSFS_ERR_IO
خطأ في الإدخال/الإخراج (فشل الأجهزة، إلخ).
PHYSFS_ERR_PERMISSION
تم رفض الإذن.
PHYSFS_ERR_NO_SPACE
لا توجد مساحة (القرص ممتلئ، تجاوز الحصة، إلخ)
PHYSFS_ERR_BAD_FILENAME
اسم الملف غير صالح/غير آمن.
PHYSFS_ERR_BUSY
تمت محاولة تعديل ملف يحتاجه نظام التشغيل.
PHYSFS_ERR_DIR_NOT_EMPTY
تمت محاولة حذف دليل به ملفات.
PHYSFS_ERR_OS_ERROR
خطأ غير محدد على مستوى نظام التشغيل.
PHYSFS_ERR_DUPLICATE
إدخال مكرر.
PHYSFS_ERR_BAD_PASSWORD
كلمة مرور خاطئة.
PHYSFS_ERR_APP_CALLBACK
أبلغت استدعاءات التطبيق عن خطأ.

مهمل

اعتبارًا من PhysicsFS 2.0، استخدم PHYSFS_mount() بدلاً من ذلك. هذه الوظيفة تقوم فقط بتغليفها على أي حال.

هذه الوظيفة تعادل:

PHYSFS_mount(newDir, NULL, appendToPath);

يجب عليك استخدام هذه الوظيفة وليس PHYSFS_mount إذا كانت التوافقية الثنائية مع PhysicsFS 1.0 مهمة (وهو ما قد لا يكون مهمًا للكثير من الأشخاص).

const char * PHYSFS_getPrefDir (const char * org, const char * app)

Get the user-and-app-specific path where files can be written. Helper function.

Get the "pref dir". This is meant to be where users can write personal files (preferences and save games, etc) that are specific to your application. This directory is unique per user, per application.

This function will decide the appropriate location in the native filesystem, create the directory if necessary, and return a string in platform-dependent notation, suitable for passing to PHYSFS_setWriteDir().

On Windows, this might look like: "C:\\Users\\bob\\AppData\\Roaming\\My Company\\My Program Name"

On Linux, this might look like: "/home/bob/.local/share/My Program Name"

On Mac OS X, this might look like: "/Users/bob/Library/Application Support/My Program Name"

(etc.)

You should probably use the pref dir for your write dir, and also put it near the beginning of your search path. Older versions of PhysicsFS offered only PHYSFS_getUserDir() and left you to figure out where the files should go under that tree. This finds the correct location for whatever platform, which not only changes between operating systems, but also versions of the same operating system.

You specify the name of your organization (if it's not a real organization, your name or an Internet domain you own might do) and the name of your application. These should be proper names.

Both the (org) and (app) strings may become part of a directory name, so please follow these rules:

  • Try to use the same org string (including case-sensitivity) for all your applications that use this function.
  • Always use a unique app string for each one, and make sure it never changes for an app once you've decided on it.
  • Unicode characters are legal, as long as it's UTF-8 encoded, but...
  • ...only use letters, numbers, and spaces. Avoid punctuation like "Game Name 2: Bad Guy's Revenge!" ... "Game Name 2" is sufficient.

The pointer returned by this function remains valid until you call this function again, or call PHYSFS_deinit(). This is not necessarily a fast call, though, so you should call this once at startup and copy the string if you need it.

You should assume the path returned by this function is the only safe place to write files (and that PHYSFS_getUserDir() and PHYSFS_getBaseDir(), while they might be writable, or even parents of the returned path, aren't where you should be writing things).

const char * PHYSFS_getRealDir (const char * filename)

Figure out where in the search path a file resides. The file is specified in platform-independent notation. The returned filename will be the element of the search path where the file was found, which may be a directory, or an archive. Even if there are multiple matches in different parts of the search path, only the first one found is used, just like when opening a file.

So, if you look for "maps/level1.map", and C:\mygame is in your search path and C:\mygame\maps\level1.map exists, then "C:\mygame" is returned.

If a any part of a match is a symbolic link, and you've not explicitly permitted symlinks, then it will be ignored, and the search for a match will continue.

If you specify a fake directory that only exists as a mount point, it'll be associated with the first archive mounted there, even though that directory isn't necessarily contained in a real archive.

Parameters

filename file to look for.

Returns

READ ONLY string of element of search path containing the the file in question. NULL if not found.

Warning

Unless you have some special, low-level need, you should be using PHYSFS_mount() instead of this.

Archives-in-archives may be very slow! While a PHYSFS_File can seek even when the data is compressed, it may do so by rewinding to the start and decompressing everything before the seek point. Normal archive usage may do a lot of seeking behind the scenes. As such, you might find normal archive usage extremely painful if mounted this way. Plan accordingly: if you, say, have a self-extracting .zip file, and want to mount something in it, compress the contents of the inner archive and make sure the outer .zip file doesn't compress the inner archive too.

This function operates just like PHYSFS_mount(), but takes a PHYSFS_File handle instead of a pathname. This handle contains all the data of the archive, and is used instead of a real file in the physical filesystem. The PHYSFS_File may be backed by a real file in the physical filesystem, but isn't necessarily. The most popular use for this is likely to mount archives stored inside other archives.

(newDir) must be a unique string to identify this archive. It is used to optimize archiver selection (if you name it XXXXX.zip, we might try the ZIP archiver first, for example, or directly choose an archiver that can only trust the data is valid by filename extension). It doesn't need to refer to a real file at all. If the filename extension isn't helpful, the system will try every archiver until one works or none of them do. This filename must be unique, as the system won't allow you to have two archives with the same name.

(file) must remain until the archive is unmounted. When the archive is unmounted, the system will call PHYSFS_close(file). If you need this handle to survive, you will have to wrap this in a PHYSFS_Io and use PHYSFS_mountIo() instead.

int PHYSFS_registerArchiver (const PHYSFS_Archiver * archiver)

إضافة مسير أرشيف جديد إلى النظام.

تحذير

هذه أشياء متقدمة وصعبة. لا تحتاج إليها ما لم تكن تعرف حقًا ما تفعله. معظم التطبيقات لن تحتاج إليها.

إذا كنت ترغب في توفير مسير أرشيف خاص بك (على سبيل المثال، تنسيق ملف أرشيف مخصص، أو شيء افتراضي تريد أن يبدو كأنظمة ملفات يمكن الوصول إليها من خلال واجهات برمجة تطبيقات PhysicsFS المعتادة)، فهذا هو المكان الذي تبدأ منه. بمجرد تسجيل مسير أرشيف بنجاح، يمكنك بعد ذلك استخدام PHYSFS_mount() لإضافة الأرشيفات التي يدعمها مسير الأرشيف الخاص بك إلى مسار البحث، أو ربما استخدامه كدليل للكتابة. داخليًا، تستخدم PhysicsFS هذه الدالة لتسجيل مسيرات الأرشيف المضمنة الخاصة بها، مثل دعم .zip، إلخ.

لا يمكنك أن يكون لديك مسيري أرشيف يتعاملان مع نفس الامتداد. إذا كنت ستحصل على تعارض، يمكنك إلغاء تسجيل مسير الأرشيف الآخر (بما في ذلك المدمجة) باستخدام PHYSFS_deregisterArchiver().

يتم نسخ البيانات الموجودة في (archiver)؛ يمكنك تحرير هذا المؤشر عندما تعود هذه الدالة.

بمجرد عودة هذه الدالة بنجاح، ستتمكن PhysicsFS من دعم أرشيفات من هذا النوع حتى تقوم بإلغاء تسجيل مسير الأرشيف مرة أخرى.

void PHYSFS_utf8ToUtf16 (const char * src, PHYSFS_uint16 *dst, PHYSFS_uint64 len)

Convertir una cadena UTF-8 a una cadena UTF-16.

Advertencia

Esta función no informará de un error si hay secuencias UTF-8 inválidas en la cadena de entrada. Las sustituirá con un carácter '?' y continuará.

Las cadenas UTF-16 tienen 16 bits por carácter (excepto algunos caracteres que son de 32 bits): TCHAR en Windows, cuando se compila con soporte Unicode. Las versiones modernas de Windows utilizan UTF-16. Las versiones antiguas de Windows anteriores a 2000 usaban TCHAR, pero solo manejaban UCS-2. UTF-16 es UCS-2, excepto para los caracteres que son de 4 bytes, que no se pueden representar completamente en UCS-2. Si no estás seguro, deberías estar usando UTF-16 en Windows ahora.

Para asegurar que el búfer de destino sea lo suficientemente grande para la conversión, por favor, asigna un búfer que sea el doble del tamaño del búfer de origen. UTF-8 utiliza de uno a cuatro bytes por carácter, pero UTF-16 siempre utiliza de dos a cuatro, por lo que una cadena completamente ASCII duplicará su tamaño. Los caracteres UTF-16 que ocuparían cuatro bytes también ocuparían cuatro bytes en UTF-8, por lo que no necesitas asignar 4 veces el espacio, solo duplicar.

Las cadenas que no caben en el búfer de destino serán truncadas, pero siempre se terminarán con NULL y no tendrán un par de sustitutos incompletos al final. Si la longitud del búfer es 0, esta función no hará nada.

Parámetros

src Cadena de entrada terminada en NULL en formato UTF-8.
dst Búfer para almacenar la cadena UTF-16 convertida.
len Tamaño en bytes del búfer de destino.

PHYSFS_sint64 PHYSFS_writeBytes (PHYSFS_File * handle, const void * buffer, PHYSFS_uint64 len)

Escribir datos en un archivo de PhysicsFS. El archivo debe estar abierto para escritura.

Nota: aunque (len) es un entero sin signo de 64 bits, estás limitado a 63 bits (9223372036854775807 bytes), por lo que puedes devolver un valor negativo en caso de error. Si la longitud es mayor que 0x7FFFFFFFFFFFFFFF, esta función fallará inmediatamente. Para sistemas sin tipos de 64 bits, estás limitado a 31 bits (0x7FFFFFFF, o 2147483647 bytes). Aunque confiamos en que casi nada necesita realizar múltiples gigabytes de E/S en una sola llamada, ¿por qué limitar las cosas?

Parámetros

handle Valor devuelto por PHYSFS_openWrite() o PHYSFS_openAppend().
buffer Búfer de (len) bytes a escribir (handle).
len Número de bytes a escribir (handle).

Devuelve

Número de bytes escritos. Esto puede ser menor que (len); en caso de error, el sistema puede intentar escribir tantos bytes como sea posible, por lo que podría haber una escritura incompleta. PHYSFS_getLastErrorCode() puede proporcionar información sobre por qué este número podría ser menor que (len). -1 si hay un fallo completo.
