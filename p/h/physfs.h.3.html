تحدد هذه القيم ما إذا كان يجب أن تستمر الدالة الاستدعائية للسرد في العمل، أو تتوقف (ولماذا تتوقف).

PHYSFS_enumerate

هذا هو نفس الشيء مثل PHYSFS_EnumFilesCallback من PhysicsFS 2.0، باستثناء أنه يمكنه إرجاع نتيجة من الدالة الاستدعائية: وبالتحديد: إذا كنت تبحث عن شيء معين، بمجرد العثور عليه، يمكنك إخبار PhysicsFS بالتوقف عن سرد المزيد. يتم استخدام هذا مع PHYSFS_enumerate()، والتي نأمل أن نكون قد حصلنا عليها بشكل صحيح هذه المرة. :)

المعلمات

data مؤشر بيانات معرف من قبل المستخدم، تم تمريره من الواجهة البرمجية (API) التي استدعت الدالة الاستدعائية في النهاية.
origdir سلسلة نصية تحتوي على المسار الكامل، بتدوين مستقل عن النظام الأساسي، للدليل الذي يحتوي على هذا الملف. في معظم الحالات، هذا هو الدليل الذي طلبت السرد منه، وتم تمريره في الدالة الاستدعائية لراحتك.
fname اسم الملف الذي يتم سرده. قد لا يكون بترتيب أبجدي مقارنة بالدالات الاستدعائية الأخرى التي تم تشغيلها، ولن يحتوي على المسار الكامل. يمكنك إعادة بناء المسار الكامل باستخدام $origdir/$fname ... يمكن أن يكون الملف دليلاً فرعيًا، أو ملفًا، أو رابطًا رمزيًا، وما إلى ذلك.

القيم المعادة

قيمة من PHYSFS_EnumerateCallbackResult. جميع القيم الأخرى غير محددة (حاليًا)؛ لا تستخدمها.

القيم التي تمثل أسبابًا محددة للفشل. في معظم الأوقات، يجب أن تقلق فقط بشأن ما إذا كانت عملية معينة قد فشلت أم لا، ولكن قد تكون هناك مناسبات تخطط فيها لمعالجة حالة فشل معينة بلطف، لذلك نقدم رموز خطأ محددة.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Get a file listing of a search path's directory, using an application-defined callback, with errors reported. Internally, PHYSFS_enumerateFiles() just calls this function and then builds a list before returning to the application, so functionality is identical except for how the information is represented to the application.

Unlike PHYSFS_enumerateFiles(), this function does not return an array. Rather, it calls a function specified by the application once per element of the search path:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Items sent to the callback are not guaranteed to be in any order whatsoever. There is no sorting done at this level, and if you need that, you should probably use PHYSFS_enumerateFiles() instead, which guarantees alphabetical sorting. This form reports whatever is discovered in each archive before moving on to the next. Even within one archive, we can't guarantee what order it will discover data. Any sorting you find in these callbacks is just pure luck. Do not rely on it. As this walks the entire list of archives, you may receive duplicate filenames.

This API and the callbacks themselves are capable of reporting errors. Prior to this API, callbacks had to accept every enumerated item, even if they were only looking for a specific thing and wanted to stop after that, or had a serious error and couldn't alert anyone. Furthermore, if PhysicsFS itself had a problem (disk error or whatnot), it couldn't report it to the calling app, it would just have to skip items or stop enumerating outright, and the caller wouldn't know it had lost some data along the way.

Now the caller can be sure it got a complete data set, and its callback has control if it wants enumeration to stop early. See the documentation for PHYSFS_EnumerateCallback for details on how your callback should behave.

Parameters

dir Directory, in platform-independent notation, to enumerate.
c Callback function to notify about search path elements.
d Application-defined data passed to callback. Can be NULL.

Returns

non-zero on success, zero on failure. Use PHYSFS_getLastErrorCode() to obtain the specific error. If the callback returns PHYSFS_ENUM_STOP to stop early, this will be considered success. Callbacks returning PHYSFS_ENUM_ERROR will make this function return zero and set the error code to PHYSFS_ERR_APP_CALLBACK.

See also

char ** PHYSFS_enumerateFiles (const char * dir)

Get a file listing of a search path's directory.

Warning

In PhysicsFS versions prior to 2.1, this function would return as many items as it could in the face of a failure condition (out of memory, disk i/o error, etc). Since this meant apps couldn't distinguish between complete success and partial failure, and since the function could always return NULL to report catastrophic failures anyway, in PhysicsFS 2.1 this function's policy changed: it will either return a list of complete results or it will return NULL for any failure of any kind, so we can guarantee that the enumeration ran to completion and has no gaps in its results.

Matching directories are interpolated. That is, if "C:\mydir" is in the search path and contains a directory "savegames" that contains "x.sav", "y.sav", and "z.sav", and there is also a "C:\userdir" in the search path that has a "savegames" subdirectory with "w.sav", then the following code:

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);
PHYSFS_freeList(rc);
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..fi
Feel free to sort the list however you like. However, the returned data will always contain no duplicates, and will be always sorted in alphabetic (rather: case-sensitive Unicode) order for you.
Don't forget to call PHYSFS_freeList() with the return value from this function when you are done with it.

قد تصبح كل من السلسلتين (org) و (app) جزءًا من اسم مجلد، لذا يرجى اتباع هذه القواعد:

  • حاول استخدام نفس السلسلة org (بما في ذلك حساسية حالة الأحرف) لجميع تطبيقاتك التي تستخدم هذه الدالة.
  • استخدم دائمًا سلسلة app فريدة لكل منها، وتأكد من أنها لا تتغير أبدًا لتطبيق بمجرد أن تقرر بشأنها.
  • الأحرف Unicode قانونية، طالما أنها مشفرة بـ UTF-8، ولكن...
  • ...استخدم فقط الأحرف والأرقام والمسافات. تجنب علامات الترقيم مثل "Game Name 2: Bad Guy's Revenge!" ... "Game Name 2" كافٍ.

يظل المؤشر الذي ترجعه هذه الدالة صالحًا حتى تستدعي هذه الدالة مرة أخرى، أو تستدعي PHYSFS_deinit(). هذه ليست بالضرورة مكالمة سريعة، لذلك يجب عليك استدعاء هذه الدالة مرة واحدة عند بدء التشغيل ونسخ السلسلة إذا كنت بحاجة إليها.

يجب أن تفترض أن المسار الذي ترجعه هذه الدالة هو المكان الآمن الوحيد للكتابة الملفات (وأن PHYSFS_getUserDir() و PHYSFS_getBaseDir()، على الرغم من أنها قد تكون قابلة للكتابة، أو حتى آباء للمسار المرتجع، ليست الأماكن التي يجب أن تكتب فيها الأشياء).

int PHYSFS_init (const char * argv0)

Initialize the PhysicsFS library. This must be called before any other PhysicsFS function.

This should be called prior to any attempts to change your process's current working directory.

Warning

On Android, argv0 should be a non-NULL pointer to a PHYSFS_AndroidInit struct. This struct must hold a valid JNIEnv * and a JNI jobject of a Context (either the application context or the current Activity is fine). Both are cast to a void * so we don't need jni.h included wherever physfs.h is. PhysicsFS uses these objects to query some system details. int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

Parameters

newDir directory or archive to add to the path, in platform-dependent notation.
mountPoint Location in the interpolated tree that this archive will be "mounted", in platform-independent notation. NULL or "" is equivalent to "/".
appendToPath nonzero to append to search path, zero to prepend.

Returns

nonzero if added to path, zero on failure (bogus archive, dir missing, etc). Use PHYSFS_getLastErrorCode() to obtain the specific error.

(file) يجب أن يبقى حتى يتم إلغاء تحميل الأرشيف. عند إلغاء تحميل الأرشيف، ستقوم الدالة باستدعاء PHYSFS_close(file). إذا كنت بحاجة إلى بقاء هذا المقبض، فسيتعين عليك تغليفه في PHYSFS_Io واستخدام PHYSFS_mountIo() بدلاً من ذلك.

تمكين أو تعطيل تتبع الروابط الرمزية. تحتوي بعض أنظمة الملفات الأرشيفية والمادية على ملفات هي مجرد مؤشرات لملفات أخرى. على نظام الملفات المادي، سيؤدي فتح مثل هذا الرابط إلى (بشفافية) فتح الملف الذي يشير إليه.

بشكل افتراضي، سيتحقق PhysicsFS مما إذا كان الملف رابطًا رمزيًا فعليًا أثناء استدعاءات الفتح ويفشل إذا كان كذلك. بخلاف ذلك، يمكن أن يأخذ الرابط خارج مسارات الكتابة والبحث، ويضر بالأمان.

إذا كنت ترغب في تحمل هذا الخطر، استدع هذه الوظيفة بمعامل غير صفري. لاحظ أن هذا ينطبق أكثر على وضع الحماية للغة البرمجة النصية للبرنامج، في حالة محاولة البرامج النصية غير الموثوق بها اختراق النظام. بشكل عام، قد يكون لدى المستخدم سبب شرعي لإنشاء رابط رمزي، لذلك ما لم تشعر بوجود خطر معين في السماح بها، يجب عليك السماح بها.

يتم التحقق من الروابط الرمزية بشكل صريح فقط عند التعامل مع أسماء الملفات بتنسيق مستقل عن المنصة. وهذا يعني، عند إعداد مسارات البحث والكتابة، وما إلى ذلك، لا يتم التحقق من الروابط الرمزية مطلقًا.

يرجى ملاحظة أن PHYSFS_stat() سيتحقق دائمًا من المسار المحدد؛ إذا كان هذا المسار رابطًا رمزيًا، فلن يتم اتباعه في أي حال. إذا لم تكن الروابط الرمزية مسموحًا بها من خلال هذه الوظيفة، فإن PHYSFS_stat() يتجاهلها، وسيعامل الاستعلام كما لو كان المسار غير موجود على الإطلاق.

يمكن تمكين أو تعطيل إذن الروابط الرمزية في أي وقت بعد استدعاء PHYSFS_init()، ويتم تعطيله افتراضيًا.

هذه أشياء متقدمة وصعبة. لا تحتاج إليها إلا إذا كنت تعرف حقًا ما تفعله. معظم التطبيقات لن تحتاج إليها.

إذا كنت ترغب في توفير أداة الأرشفة الخاصة بك (على سبيل المثال، تنسيق ملف أرشيف مخصص، أو شيء افتراضي تريد أن يبدو كنظام ملفات يمكنك الوصول إليه عبر واجهات برمجة تطبيقات PhysicsFS العادية)، فهذا هو المكان الذي تبدأ فيه. بمجرد تسجيل أداة الأرشفة بنجاح، يمكنك بعد ذلك استخدام PHYSFS_mount() لإضافة الأرشيفات التي تدعمها أداة الأرشفة الخاصة بك إلى مسار البحث، أو ربما استخدامها كدليل للكتابة. داخليًا، يستخدم PhysicsFS هذه الوظيفة لتسجيل أدوات الأرشفة المضمنة الخاصة به، مثل دعم .zip، وما إلى ذلك.

لا يمكنك أن يكون لديك أدوات أرشفة تتعامل مع نفس الامتداد. إذا كنت ستواجه تعارضًا، يمكنك إلغاء تسجيل أداة الأرشفة الأخرى (بما في ذلك الأرشيفات المضمنة) باستخدام PHYSFS_deregisterArchiver().

يتم نسخ البيانات في (archiver)؛ قد تحرر هذا المؤشر عند عودة هذه الوظيفة.

بمجرد عودة هذه الوظيفة بنجاح، سيكون PhysicsFS قادرًا على دعم الأرشيفات من هذا النوع حتى تقوم بإلغاء تسجيل أداة الأرشفة مرة أخرى.

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convert a Latin1 string to a UTF-8 string. Latin1 strings are 8-bits per character: a popular "high ASCII" encoding.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 expands latin1 codepoints over 127 from 1 to 2 bytes, so the string may grow in some cases.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-8 sequence at the end. If the buffer length is 0, this function does nothing.

Please note that we do not supply a UTF-8 to Latin1 converter, since Latin1 can't express most Unicode codepoints. It's a legacy encoding; you should be converting away from it at all times.

Parameters

src Null-terminated source string in Latin1 format.
dst Buffer to store converted UTF-8 string.
len Size, in bytes, of destination buffer.

int PHYSFS_utf8stricmp (const char * str1, const char * str2)

Case-insensitive compare of two UTF-8 strings. This is a strcasecmp/stricmp replacement that expects both strings to be in UTF-8 encoding. It will do "case folding" to decide if the Unicode codepoints in the strings match.

If both strings are exclusively low-ASCII characters, this will do the right thing, as that is also valid UTF-8. If there are any high-ASCII chars, this will not do what you expect!

It will report which string is "greater than" the other, but be aware that this doesn't necessarily mean anything: 'a' may be "less than" 'b', but a Japanese kuten has no meaningful alphabetically relationship to a Greek lambda, but being able to assign a reliable "value" makes sorting algorithms possible, if not entirely sane. Most cases should treat the return value as "equal" or "not equal".

Like stricmp, this expects both strings to be NULL-terminated.

Parameters

str1 First string to compare.
str2 Second string to compare.

Returns

-1 if str1 is "less than" str2, 1 if "greater than", 0 if equal.

Description

These functions write an unsigned integer of a specified byte order and size to a PHYSFS_File handle.

If the platform's native byte order is already the same as the requested byte order, the value is written directly. Otherwise, the value is swapped to match the requested byte order before writing.

These are convenience functions. The most portable way to write integers to files is to always convert them to a known byte order (like little-endian or big-endian) and then write the raw bytes using PHYSFS_write.
