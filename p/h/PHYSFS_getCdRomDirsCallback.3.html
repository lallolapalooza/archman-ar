typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Function signature for callbacks that enumerate files.

Warning

As of PhysicsFS 2.1, Use PHYSFS_EnumerateCallback with PHYSFS_enumerate() instead; it gives you more control over the process.

These are used to report a list of directory entries to an original caller, one file/dir/symlink per callback. All strings are UTF-8 encoded. Functions should not try to modify or free any string's memory.

These callbacks are used, starting in PhysicsFS 1.1, as an alternative to functions that would return lists that need to be cleaned up with PHYSFS_freeList(). The callback means that the library doesn't need to allocate an entire list and all the strings up front.

Be aware that promised data ordering in the list versions are not necessarily so in the callback versions. Check the documentation on specific APIs, but strings may not be sorted as you expect and you might get duplicate strings.

Parameters

data User-defined data pointer, passed through from the API that eventually called the callback.
origdir A string containing the full path, in platform-independent notation, of the directory containing this file. In most cases, this is the directory on which you requested enumeration, passed in the callback for your convenience.
fname The filename that is being enumerated. It may not be in alphabetical order compared to other callbacks that have fired, and it will not contain the full path. You can recreate the fullpath with $origdir/$fname ... The file can be a subdirectory, a file, a symlink, etc.

enum PHYSFS_ErrorCode

Values that represent specific causes of failure. Most of the time, you should only concern yourself with whether a given operation failed or not, but there may be occasions where you plan to handle a specific failure case gracefully, so we provide specific error codes.

Most of these errors are a little vague, and most aren't things you can fix...if there's a permission error, for example, all you can really do is pass that information on to the user and let them figure out how to handle it. In most these cases, your program should only care that it failed to accomplish its goals, and not care specifically why.

تحذير

أي شخص يدرس يونيكود يعرف مشكلة "الحرف التركي I". هذه الواجهة لا تتعامل معها. افترض أن هذا الحرف الواحد في كل يونيكود سيتم طيه بشكل غير صحيح. إذا كنت لا تعرف ما يدور حوله هذا الأمر، فيمكنك على الأرجح تجاهل هذه المشكلة لمعظم الكوكب، ولكن الكمال مستحيل.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Get a file listing of a search path's directory, using an application-defined callback, with errors reported. Internally, PHYSFS_enumerateFiles() just calls this function and then builds a list before returning to the application, so functionality is identical except for how the information is represented to the application.

Unlike PHYSFS_enumerateFiles(), this function does not return an array. Rather, it calls a function specified by the application once per element of the search path:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Items sent to the callback are not guaranteed to be in any order whatsoever. There is no sorting done at this level, and if you need that, you should probably use PHYSFS_enumerateFiles() instead, which guarantees alphabetical sorting. This form reports whatever is discovered in each archive before moving on to the next. Even within one archive, we can't guarantee what order it will discover data. Any sorting you find in these callbacks is just pure luck. Do not rely on it. As this walks the entire list of archives, you may receive duplicate filenames.

This API and the callbacks themselves are capable of reporting errors. Prior to this API, callbacks had to accept every enumerated item, even if they were only looking for a specific thing and wanted to stop after that, or had a serious error and couldn't alert anyone. Furthermore, if PhysicsFS itself had a problem (disk error or whatnot), it couldn't report it to the calling app, it would just have to skip items or stop enumerating outright, and the caller wouldn't know it had lost some data along the way.

Now the caller can be sure it got a complete data set, and its callback has control if it wants enumeration to stop early. See the documentation for PHYSFS_EnumerateCallback for details on how your callback should behave.

Parameters

dir Directory, in platform-independent notation, to enumerate.
c Callback function to notify about search path elements.
d Application-defined data passed to callback. Can be NULL.

Returns

non-zero on success, zero on failure. Use PHYSFS_getLastErrorCode() to obtain the specific error. If the callback returns PHYSFS_ENUM_STOP to stop early, this will be considered success. Callbacks returning PHYSFS_ENUM_ERROR will make this function return zero and set the error code to PHYSFS_ERR_APP_CALLBACK.

See also

char ** PHYSFS_enumerateFiles (const char * dir)

Get a file listing of a search path's directory.

Warning

In PhysicsFS versions prior to 2.1, this function would return as many items as it could in the face of a failure condition (out of memory, disk i/o error, etc). Since this meant apps couldn't distinguish between complete success and partial failure, and since the function could always return NULL to report catastrophic failures anyway, in PhysicsFS 2.1 this function's policy changed: it will either return a list of complete results or it will return NULL for any failure of any kind, so we can guarantee that the enumeration ran to completion and has no gaps in its results.

Matching directories are interpolated. That is, if "C:\mydir" is in the search path and contains a directory "savegames" that contains "x.sav", "y.sav", and "z.sav", and there is also a "C:\userdir" in the search path that has a "savegames" subdirectory with "w.sav", then the following code:

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);
PHYSFS_freeList(rc);
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..fi
Feel free to sort the list however you like. However, the returned data will always contain no duplicates, and will be always sorted in alphabetic (rather: case-sensitive Unicode) order for you.
Don't forget to call PHYSFS_freeList() with the return value from this function when you are done with it.

DESCRIPTION

These functions deal with reading and writing files. They abstract away the complexities of the underlying operating system's file I/O, and also allow for reading from archives.

PHYSFS_openRead opens a file for reading. If the file is not found, or cannot be opened for any other reason, it returns NULL and PHYSFS_getLastErrorCode() can be used to determine the error.

PHYSFS_openAppend opens a file for appending. If the file does not exist, it will be created. If it cannot be opened for any other reason, it returns NULL and PHYSFS_getLastErrorCode() can be used to determine the error.

PHYSFS_read reads data from an open file handle. It reads `objCount` objects, each of `objSize` bytes, into the provided `buffer`. It returns the number of objects successfully read. This may be less than `objCount` if the end of the file is reached or an error occurs. If a complete failure occurs, it returns -1.

PHYSFS_readBytes reads a specified number of bytes from an open file handle into the provided buffer. It returns the number of bytes successfully read. This may be less than `len` if the end of the file is reached or an error occurs. If a complete failure occurs, it returns -1.

PHYSFS_readSBE16, PHYSFS_readSBE32, PHYSFS_readSBE64, PHYSFS_readSLE16, PHYSFS_readSLE32, PHYSFS_readSLE64, PHYSFS_readUBE16, PHYSFS_readUBE32, PHYSFS_readUBE64, PHYSFS_readULE16, PHYSFS_readULE32, and PHYSFS_readULE64 are convenience functions for reading and converting integer values in specific endian formats (Big Endian or Little Endian) and sizes (16, 32, or 64 bits), signed or unsigned. They read the data from the specified file handle and convert it to the platform's native byte order. They return non-zero on success and zero on failure. If successful, the converted value is stored in the memory location pointed to by `val`.

PHYSFS_write writes data to an open file handle. It writes `objCount` objects, each of `objSize` bytes, from the provided `buffer`. It returns the number of objects successfully written. This may be less than `objCount` if an error occurs. If a complete failure occurs, it returns -1.

PHYSFS_writeBytes writes a specified number of bytes from the provided buffer to an open file handle. It returns the number of bytes successfully written. This may be less than `len` if an error occurs. If a complete failure occurs, it returns -1.

PHYSFS_writeSBE16, PHYSFS_writeSBE32, PHYSFS_writeSBE64, PHYSFS_writeSLE16, PHYSFS_writeSLE32, PHYSFS_writeSLE64, PHYSFS_writeUBE16, PHYSFS_writeUBE32, PHYSFS_writeUBE64, PHYSFS_writeULE16, PHYSFS_writeULE32, and PHYSFS_writeULE64 are convenience functions for writing integer values in specific endian formats (Big Endian or Little Endian) and sizes (16, 32, or 64 bits), signed or unsigned. They convert the provided integer value `val` to the specified endian format and write it to the file handle. They return non-zero on success and zero on failure.

PHYSFS_close closes an open file handle, flushing any buffered data. It returns zero on success and -1 on failure.

PHYSFS_permitSymbolicLinks controls whether symbolic links should be followed when opening files. By default, symbolic links are denied to prevent potential security risks or unexpected behavior. If `allow` is non-zero, symbolic links will be followed. If `allow` is zero, they will be ignored. This function can be called at any time after PHYSFS_init().

Note: PHYSFS_stat() will always examine the path specified and will not follow symbolic links. If symbolic links are not permitted via PHYSFS_permitSymbolicLinks(), PHYSFS_stat() will treat a symbolic link as if it did not exist.

Warning: On platforms without native 64-bit integer support, PHYSFS_sint64 and PHYSFS_uint64 may only be 32 bits. This can affect the behavior of the 64-bit read/write functions.

RETURN VALUES

Functions that return file handles (e.g., PHYSFS_openRead, PHYSFS_openAppend) return a pointer to a PHYSFS_File structure on success, and NULL on failure. Use PHYSFS_getLastErrorCode() to get more information about errors.

Functions that perform read or write operations (e.g., PHYSFS_read, PHYSFS_writeBytes) return the number of items (objects or bytes) successfully processed. A return value less than the requested amount does not necessarily indicate an error, but could mean the end of the file was reached. A return value of -1 indicates a complete failure, and PHYSFS_getLastErrorCode() should be consulted.

Integer read/write convenience functions (e.g., PHYSFS_readSBE16, PHYSFS_writeUBE32) return non-zero on success and zero on failure. On success, the appropriate value is stored in the output parameter.

PHYSFS_close returns 0 on success and -1 on failure.

PHYSFS_permitSymbolicLinks does not return a value.

يجعل مجلدًا فرعيًا في أرشيف ما هو المجلد الجذر. هذا يسمح لك بتقييد الملفات التي يمكن الوصول إليها في أرشيف معين. على سبيل المثال، إذا كان لديك x.zip مع ملف في y/z.txt تم تحميله على /a، فإذا قمت باستدعاء PHYSFS_setRoot("x.zip", "/y")، فإن استدعاء PHYSFS_openRead("/a/z.txt") سينجح.

يمكنك تغيير المجلد الجذر لأرشيف في أي وقت، وبالتالي تغيير شجرة الملفات المتداخلة (اعتمادًا على مكان نقل المسارات، قد يوفر ملف مختلف ملفات متنوعة). إذا قمت بتعيين المجلد الجذر إلى NULL أو إلى "/"، فسيتم التعامل مع الأرشيف كما لو لم يتم تعيين أي مجلد خاص (كما لو تم تحميل الأرشيف بشكل طبيعي).

تغيير المجلد الجذر يؤثر فقط على العمليات المستقبلية على مسارات الملفات؛ لن يتأثر الملف الذي تم فتحه من مسار تم تغييره بسبب setRoot.

تعيين مجلد جذر جديد لا يقتصر على الملفات الموجودة في مسار البحث؛ يمكنك تعيينه إلى مجلد الكتابة أيضًا، وهو ما قد يكون مفيدًا إذا كان لديك ملفات مفتوحة للكتابة ولا يمكنك تغيير مجلد الكتابة في الوقت الحالي.

voidPHYSFS_utf8FromUtf16 (const PHYSFS_uint16 * src, char * dst, PHYSFS_uint64 len)

تحويل سلسلة UTF-16 إلى سلسلة UTF-8.

تحذير

لن تقوم هذه الدالة بالإبلاغ عن خطأ إذا كانت هناك تسلسلات UTF-16 غير صالحة في سلسلة المصدر. ستقوم باستبدالها بحرف '؟' وتستمر.

سلاسل UTF-16 هي 16 بت لكل حرف (باستثناء بعض الأحرف، والتي هي 32 بت): TCHAR على Windows، عند البناء بدعم Unicode. تستخدم إصدارات Windows الحديثة UTF-16. استخدمت إصدارات Windows قبل عام 2000 TCHAR، ولكنها تعاملت فقط مع UCS-2. UTF-16 هو UCS-2، باستثناء الأحرف التي تبلغ 4 بايت، والتي لا يمكن تمثيلها في UCS-2 على الإطلاق. إذا لم تكن متأكدًا، فيجب عليك استخدام UTF-16 في هذه المرحلة على Windows.

لضمان أن يكون المخزن المؤقت الوجهة كبيرًا بما يكفي للتحويل، يرجى تخصيص مخزن مؤقت بحجم مضاعف لحجم المخزن المؤقت المصدر. نادراً ما تستخدم UTF-8 أكثر من 32 بت لكل حرف، لذلك بينما قد تقلص سلسلة UTF-16، قد توسعها أيضًا.

void PHYSFS_utf8ToUtf16 (const char * src, PHYSFS_uint16 * dst, PHYSFS_uint64 len)

تحويل سلسلة UTF-8 إلى سلسلة UTF-16.

تنويه

لن تبلغ هذه الوظيفة عن خطأ إذا كانت هناك تسلسلات UTF-8 غير صالحة في سلسلة الإدخال. سيتم استبدالها بحرف "?" والاستمرار.

تحتوي سلاسل UTF-16 على 16 بت لكل حرف (باستثناء بعض الأحرف، التي تكون 32 بت): TCHAR في Windows، عند تجميعها مع دعم Unicode. تستخدم إصدارات Windows الحديثة UTF-16. استخدمت إصدارات Windows القديمة قبل عام 2000 TCHAR، لكنها تعاملت فقط مع UCS-2. UTF-16 هو UCS-2، باستثناء الأحرف التي تكون 4 بايت، والتي لا يمكن تمثيلها بالكامل في UCS-2. إذا لم تكن متأكدًا، يجب أن تستخدم UTF-16 في هذه المرحلة في Windows.

للتأكد من أن المخزن المؤقت الوجهة كبير بما يكفي للتحويل، يرجى تخصيص مخزن مؤقت بحجم ضعف حجم المخزن المؤقت للإدخال. يستخدم UTF-8 من 1 إلى 4 بايت لكل حرف، ولكن UTF-16 يستخدم دائمًا من 2 إلى 4 بايت، لذلك ستتضاعف سلسلة ASCII بالكامل في الحجم! الأحرف UTF-16 التي تتطلب 4 بايت ستتطلب أيضًا 4 بايت في UTF-8، لذلك لا تحتاج إلى حجز 4 أضعاف المساحة، فقط الضعف.

سيتم اقتطاع السلاسل التي لا تتناسب مع حجم المخزن المؤقت الوجهة، ولكنها ستنتهي دائمًا بنقطة ولن تحتوي أبدًا على زوج بديل غير مكتمل في النهاية. إذا كان حجم المخزن المؤقت 0، فلن تفعل هذه الوظيفة شيئًا.
