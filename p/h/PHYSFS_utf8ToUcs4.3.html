int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

"طي" نقطة رمزية Unicode إلى ما يعادلها بحروف صغيرة. (هذا للاستخدام المحدود والصعب. إذا لم ترَ حاجة فورية له، يمكنك تجاهله إلى الأبد).

سيؤدي هذا إلى تحويل نقطة رمزية Unicode إلى ما يعادلها بحروف صغيرة. سيتم إرجاع النقاط الرمزية غير الصالحة والنقاط التي لا تحتوي على ما يعادلها بحروف صغيرة دون تحويل.

لاحظ أنك قد تحصل على نقاط رمزية متعددة في المقابل! على سبيل المثال، الرمز الألماني Eszett سيتم طيه إلى نقطتين رمزيتين بحرف "s" صغير. النظرية هي أنه إذا قمت بوضع سلسلتين، إحداهما تحتوي على Eszett والأخرى تحتوي على "SS"، فسيتم مطابقتهما.

تحذير

أي شخص يدرس Unicode يعرف مشكلة "الحرف التركي I". هذه الواجهة لا تتعامل معها. افترض أن هذا الحرف الواحد في جميع أنحاء Unicode سيتم طيه بشكل غير صحيح. إذا لم تكن تعرف ما يدور حوله هذا الأمر، فيمكنك تجاهل هذه المشكلة لمعظم أنحاء العالم، لكن الكمال مستحيل.

المعلمات

from نقطة الرمز المراد طيها.
to المخزن المؤقت لتخزين قيم النقاط الرمزية المطوية فيه. يجب أن يشير هذا إلى مساحة لـ 3 PHYSFS_uint32 slots على الأقل.

القيم المعادة

إلغاء تهيئة مكتبة PhysicsFS. يقوم هذا بإغلاق أي ملفات مفتوحة عبر PhysicsFS، ويقوم بمسح مسارات البحث/الكتابة، ويحرر الذاكرة، ويبطل جميع مقبضات الملفات الخاصة بك.

لاحظ أن هذه المكالمة يمكن أن تفشل إذا كان هناك ملف مفتوح للكتابة يرفض الإغلاق (على سبيل المثال، كان نظام التشغيل الأساسي يقوم بتخزين الكتابات مؤقتًا على نظام ملفات الشبكة، وتعطل خادم الملفات، أو فشل القرص الصلب، وما إلى ذلك). عادة ما يكون من الأفضل إغلاق جميع مقبضات الكتابة بنفسك قبل استدعاء هذه الوظيفة، حتى تتمكن من التعامل بلطف مع فشل معين.

بمجرد إلغاء التهيئة بنجاح، يمكن استدعاء PHYSFS_init() مرة أخرى لإعادة تشغيل النظام الفرعي. تتم استعادة جميع حالات واجهة برمجة التطبيقات الافتراضية في هذه المرحلة، باستثناء أي مخصص للمخصصات قد تكون حددتها، والتي تظل بين التهيئة.

int PHYSFS_delete (const char * filename)

حذف ملف أو دليل. (اسم الملف) محدد بتدوين مستقل عن المنصة فيما يتعلق بدليل الكتابة.

يجب أن يكون الدليل فارغًا قبل أن تتمكن هذه المكالمة من حذفه.

سيؤدي حذف ربط رمزي إلى إزالة الرابط، وليس ما يشير إليه، بغض النظر عما إذا كنت قد "سمحت بالروابط الرمزية" أم لا.

لذلك إذا كان لديك دليل الكتابة مضبوطًا على "C:\mygame\writedir" واستدعيت PHYSFS_delete("downloads/maps/level1.map") ، فسيتم إزالة الملف "C:\mygame\writedir\downloads\maps\level1.map" من نظام الملفات المادي، إذا كان موجودًا وسمح نظام التشغيل بال حذف.

لاحظ أنه في أنظمة Unix، قد ينجح حذف الملف، ولكن لن تتم إزالة الملف الفعلي حتى تقوم جميع العمليات التي لديها مقبض ملف مفتوح له (بما في ذلك برنامجك) بإغلاق مقبضاتها.

من المحتمل أن تكون الأجزاء التي يتكون منها الملف لا تزال موجودة، وهي متاحة فقط ليتم الكتابة فوقها في وقت لاحق. لا تعتبر هذه طريقة أمان أو أي شيء من هذا القبيل. :)

int PHYSFS_deregisterArchiver (const char * ext)

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Get a file listing of a search path's directory, using an application-defined callback, with errors reported. Internally, PHYSFS_enumerateFiles() just calls this function and then builds a list before returning to the application, so functionality is identical except for how the information is represented to the application.

Unlike PHYSFS_enumerateFiles(), this function does not return an array. Rather, it calls a function specified by the application once per element of the search path:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Items sent to the callback are not guaranteed to be in any order whatsoever. There is no sorting done at this level, and if you need that, you should probably use PHYSFS_enumerateFiles() instead, which guarantees alphabetical sorting. This form reports whatever is discovered in each archive before moving on to the next. Even within one archive, we can't guarantee what order it will discover data. Any sorting you find in these callbacks is just pure luck. Do not rely on it. As this walks the entire list of archives, you may receive duplicate filenames.

This API and the callbacks themselves are capable of reporting errors. Prior to this API, callbacks had to accept every enumerated item, even if they were only looking for a specific thing and wanted to stop after that, or had a serious error and couldn't alert anyone. Furthermore, if PhysicsFS itself had a problem (disk error or whatnot), it couldn't report it to the calling app, it would just have to skip items or stop enumerating outright, and the caller wouldn't know it had lost some data along the way.

Now the caller can be sure it got a complete data set, and its callback has control if it wants enumeration to stop early. See the documentation for PHYSFS_EnumerateCallback for details on how your callback should behave.

Parameters

dir Directory, in platform-independent notation, to enumerate.
c Callback function to notify about search path elements.
d Application-defined data passed to callback. Can be NULL.

Returns

non-zero on success, zero on failure. Use PHYSFS_getLastErrorCode() to obtain the specific error. If the callback returns PHYSFS_ENUM_STOP to stop early, this will be considered success. Callbacks returning PHYSFS_ENUM_ERROR will make this function return zero and set the error code to PHYSFS_ERR_APP_CALLBACK.

See also

char ** PHYSFS_enumerateFiles (const char * dir)

Get a file listing of a search path's directory.

Warning

In PhysicsFS versions prior to 2.1, this function would return as many items as it could in the face of a failure condition (out of memory, disk i/o error, etc). Since this meant apps couldn't distinguish between complete success and partial failure, and since the function could always return NULL to report catastrophic failures anyway, in PhysicsFS 2.1 this function's policy changed: it will either return a list of complete results or it will return NULL for any failure of any kind, so we can guarantee that the enumeration ran to completion and has no gaps in its results.

Matching directories are interpolated. That is, if "C:\mydir" is in the search path and contains a directory "savegames" that contains "x.sav", "y.sav", and "z.sav", and there is also a "C:\userdir" in the search path that has a "savegames" subdirectory with "w.sav", then the following code:

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);
PHYSFS_freeList(rc);
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..fi
Feel free to sort the list however you like. However, the returned data will always contain no duplicates, and will be always sorted in alphabetic (rather: case-sensitive Unicode) order for you.
Don't forget to call PHYSFS_freeList() with the return value from this function when you are done with it.

dir directory in platform-independent notation to enumerate. 
Returns
Null-terminated array of null-terminated strings, or NULL for failure cases.

مقارنة غير حساسة لحالة الأحرف لسلسلتين UTF-8. هذا بديل لـ strcasecmp/stricmp الذي يتوقع أن تكون كلتا السلسلتين بتشفير UTF-8. سيقوم بإجراء "طي حالة" لتحديد ما إذا كانت رموز Unicode في السلاسل متساوية.

إذا كانت كلتا السلسلتين مجرد أحرف ASCII منخفضة، فستقوم بذلك بشكل صحيح، لأنها أيضًا UTF-8 صالحة. إذا كان هناك أي حرف ASCII عالي، فلن تقوم بذلك كما تتوقع!

ستكون أي منهما "أكبر من" الأخرى، ولكن ضع في اعتبارك أن هذا لا يعني بالضرورة شيئًا: يمكن أن يكون 'a' "أقل من" 'b'، ولكن الكانجي الياباني ليس له علاقة أبجدية كبيرة مع lambda اليوناني، ولكن القدرة على تعيين قيمة "موثوقة" تجعل خوارزميات الترتيب ممكنة، حتى لو لم تكن عقلانية تمامًا. معظم الحالات يجب أن تتعامل مع القيمة المرجعة كـ "متساوية" أو "غير متساوية".

مثل stricmp، تتوقع هذه الدالة أن تنتهي كلتا السلسلتين بـ null.

المعلمات

str1 السلسلة للمقارنة.
str2 السلسلة للمقارنة.

الإرجاع

-1 إذا كانت str1 "أقل من" str2، 1 إذا كانت "أكبر من"، 0 إذا كانتا متساويتين.

void PHYSFS_utf8ToUcs2 (const char * src, PHYSFS_uint16 * dst, PHYSFS_uint64 len)

تحويل سلسلة UTF-8 إلى سلسلة UCS-2.

تحذير

من شبه المؤكد أنك يجب أن تستخدم PHYSFS_utf8ToUtf16()، الذي أصبح متاحًا في PhysicsFS 2.1، إلا إذا كنت تعرف ما تفعله.

لن تبلغ هذه الدالة عن خطأ إذا كانت هناك تسلسلات UTF-8 غير صالحة في سلسلة المصدر. ستقوم باستبدالها بحرف '؟' وتستمر.

سلاسل UCS-2 هي 16 بت لكل حرف: TCHAR في Windows عند تجميعها مع دعم Unicode. يجب أن تلاحظ أن الإصدارات الحديثة من Windows تستخدم UTF-16، وهي شكل موسع من UCS-2، ولكنها ليست متطابقة. شبه المؤكد أنك تريد PHYSFS_utf8ToUtf16()، ولكن يجب أن تفهم كيف يتغير هذا.

للتأكد من أن المخزن المؤقت للوجهة كبير بما يكفي للتحويل، يرجى تخصيص مخزن مؤقت يكون ضعف حجم المخزن المؤقت المصدر. UTF-8 يستخدم من 1 إلى 4 بايت لكل حرف، ولكن UCS-2 يستخدم دائمًا 2، لذلك ستتضاعف سلسلة ASCII منخفضة تمامًا في الحجم!

سيتم اقتطاع السلاسل التي لا تتناسب مع المخزن المؤقت للوجهة، ولكنها ستنتهي دائمًا بـ null ولن تحتوي أبدًا على تسلسل UCS-2 غير مكتمل في النهاية. إذا كان طول المخزن المؤقت 0، فلن تقوم هذه الدالة بأي شيء.

المعلمات

src سلسلة UTF-8 بتنسيق سلسلة منتهية بـ null.
dst المخزن المؤقت لتخزين سلسلة UCS-2 المحولة.
len حجم المخزن المؤقت للوجهة بالبايت.

void PHYSFS_utf8ToUcs4 (const char * src, PHYSFS_uint32 * dst, PHYSFS_uint64 len)

تحويل سلسلة UTF-8 إلى سلسلة UCS-4.

تحذير
