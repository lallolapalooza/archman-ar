typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Function signature for callbacks that enumerate files.

Warning

As of PhysicsFS 2.1, Use PHYSFS_EnumerateCallback with PHYSFS_enumerate() instead; it gives you more control over the process.

These are used to report a list of directory entries to an original caller, one file/dir/symlink per callback. All strings are UTF-8 encoded. Functions should not try to modify or free any string's memory.

These callbacks are used, starting in PhysicsFS 1.1, as an alternative to functions that would return lists that need to be cleaned up with PHYSFS_freeList(). The callback means that the library doesn't need to allocate an entire list and all the strings up front.

Be aware that promised data ordering in the list versions are not necessarily so in the callback versions. Check the documentation on specific APIs, but strings may not be sorted as you expect and you might get duplicate strings.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Get a list of files from a directory in a search path, using a user-defined callback, with errors reported. Internally, PHYSFS_enumerateFiles() calls only this function and then builds a list before returning to the application, so the functionality is identical, apart from how the information is presented to the application.

Unlike PHYSFS_enumerateFiles(), this function does not return an array. Instead, it calls a user-specified function once for each item in the search path:

static physfs_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // Give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Items supplied to the callback are not guaranteed in any specific order. No sorting is done at this level, and if you need it, you should use PHYSFS_enumerateFiles(), which guarantees alphabetical order. This form reports what it finds in each archive before moving on to the next. Even within one archive, we can't guarantee the order in which data is discovered. *Any sorting you find in these callbacks is just pure luck. Do not rely on it.* As this walks through the entire list of files, you might receive duplicate filenames.

This API and the callbacks themselves can now report errors. Before this API, callbacks had to accept every enumerated item, even if they were just looking for a specific object and wanted to stop there, or if they had a fatal error and couldn't notify anyone. Also, if PhysicsFS itself had a problem (disk error or something), it couldn't report it to the application; it would just skip items or stop enumeration entirely, and the caller wouldn't know that it had lost some data along the way.

Now the caller can be assured that it has obtained a complete set of data, and if it wants to stop enumeration early, its callback will have control. See the documentation for PHYSFS_EnumerateCallback for details on how your callback should behave.

Parameters

dir Directory, in platform-independent notation, to enumerate.
c Callback function to notify about items in the search path.
d Application-defined data to be passed to the callback. May be NULL.

Returns

Non-zero on success, zero on failure. Use PHYSFS_getLastErrorCode() to get the specific error. If the callback returns PHYSFS_ENUM_STOP, this will be considered success. Callbacks that return PHYSFS_ENUM_ERROR will cause this function to return zero and set the error code to PHYSFS_ERR_APP_CALLBACK.

See also

char ** PHYSFS_enumerateFiles (const char * dir)

Get a list of files from a directory in a search path.

Warning

In PhysicsFS versions prior to 2.1, this function would return as many items as possible under failure conditions (memory error, disk I/O error, etc.). Since this prevented applications from distinguishing between complete success and partial failure, and since the function could return NULL to report catastrophic failures anyway, in PhysicsFS 2.1 the policy for this function was changed: it will return a complete list of results or NULL in case of any failure, so we can guarantee that the enumeration completed and there are no gaps in your results.

Directories that match are interpolated. That is, if "C:\mydir" is in the search path and it contains a directory "savegames" which contains "x.sav", "y.sav", "z.sav", and there is also a "C:\userdir" in the search path which has a subdirectory "savegames" with "w.sav", then the following code:

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);
PHYSFS_freeList(rc);
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..fi
Feel free to sort the list however you like. However, the returned data will always contain no duplicates, and will be always sorted in alphabetic (rather: case-sensitive Unicode) order for you.
Don't forget to call PHYSFS_freeList() with the return value from this function when you are done with it.
Parameters
dir directory in platform-independent notation to enumerate. 
Returns
Null-terminated array of strings, or NULL on failure.

تحدد اسم مؤسستك (إذا لم تكن مؤسسة حقيقية، فقد يكون اسمك أو نطاق إنترنت تملكه كافيًا) واسم تطبيقك. يجب أن تكون هذه أسماء صحيحة.

قد تصبح كل من سلسلتي (org) و (app) جزءًا من اسم دليل، لذا يرجى اتباع هذه القواعد:

  • حاول استخدام نفس سلسلة org (بما في ذلك حساسية الحالة) لجميع تطبيقاتك التي تستخدم هذه الدالة.
  • استخدم دائمًا سلسلة app فريدة لكل منها، وتأكد من أنها لا تتغير أبدًا لتطبيق بمجرد أن تقرر بشأنها.
  • الأحرف Unicode قانونية، طالما أنها مشفرة بتنسيق UTF-8، ولكن...
  • ...استخدم فقط الأحرف والأرقام والمسافات. تجنب علامات الترقيم مثل "Game Name 2: Bad Guy's Revenge!" ... "Game Name 2" كافٍ.

المؤشر الذي تعيده هذه الدالة يظل صالحًا حتى تقوم باستدعاء هذه الدالة مرة أخرى، أو تستدعي `PHYSFS_deinit()`. ومع ذلك، قد لا يكون هذا استدعاءً سريعًا، لذا يجب عليك استدعاء هذا مرة واحدة عند بدء التشغيل ونسخ السلسلة إذا كنت بحاجة إليها.

(ptr) يجب أن يبقى حتى يتم إلغاء تحميل الأرشيف. عند إلغاء تحميل الأرشيف، سيقوم النظام باستدعاء (del)(ptr)، والذي سيبلغك بأن النظام قد انتهى من المخزن المؤقت، وسيعطيك فرصة لتحرير مواردك. يمكن أن يكون (del) NULL، وفي هذه الحالة لن يقوم النظام بمحاولة تحرير المخزن المؤقت.

إذا فشلت هذه الوظيفة، فلن يتم استدعاء (del).

المعلمات

buf عنوان المخزن المؤقت للذاكرة الذي يحتوي على بيانات الأرشيف.
len حجم المخزن المؤقت للذاكرة، بالبايت.
del رد اتصال يتم تشغيله عند إلغاء التحميل. يمكن أن يكون NULL.
newDir اسم ملف يمكن أن يمثل هذا التدفق.
mountPoint الموقع في الشجرة المفسرة التي سيتم "تحميل" هذا الأرشيف فيها، بتدوين مستقل عن المنصة. NULL أو "" يعادل "/".
appendToPath غير صفري للإضافة إلى مسار البحث، صفري للاحتلال المسبق.

يعود

غير صفري إذا تمت إضافته إلى المسار، صفري عند الفشل (أرشيف خاطئ، إلخ). استخدم PHYSFS_getLastErrorCode() للحصول على الخطأ المحدد.

افتراضيًا، سيتحقق PhysicsFS مما إذا كان الملف رابطًا رمزيًا بالفعل أثناء استدعاءات الفتح وسيفشل إذا كان الأمر كذلك. وإلا، يمكن أن يؤدي الرابط إلى خارج مسارات القراءة والكتابة، مما يضر بالأمان.

إذا كنت ترغب في تحمل هذا الخطر، فاستدع هذه الوظيفة بقيمة غير صفرية. لاحظ أن هذا يتعلق أكثر بـ sandboxing لغة البرمجة النصية لبرنامج، في حالة محاولة البرامج النصية غير الموثوق بها اختراق النظام. بشكل عام، قد يكون لدى المستخدم سبب شرعي لإنشاء رابط رمزي، لذلك لا يجب عليك تعطيله، إلا إذا كنت تشعر أن هناك خطرًا محددًا في السماح بها.

سيتم رؤية الروابط الرمزية فقط عند التعامل مع أسماء الملفات بترميز مستقل عن النظام. أي، عند تعيين مسارات البحث والكتابة وما إلى ذلك، لن يتم رؤية الروابط الرمزية أبدًا.

int PHYSFS_ucs4stricmp (const PHYSFS_uint32 * str1, const PHYSFS_uint32 * str2)

مقارنة غير حساسة لحالة الأحرف لسلسلتي UCS-4. هذا هو بديل strcasecmp/stricmp الذي يتوقع أن تكون كلتا السلسلتين بتشفير UCS-4 (المعروف أيضًا باسم UTF-32). سيقوم بـ "طي الحالة" لتحديد ما إذا كانت نقاط ترميز Unicode في السلاسل متطابقة.

سيقوم بالإبلاغ عن أي سلسلة "أكبر من" الأخرى، ولكن كن على علم بأن هذا لا يعني بالضرورة شيئًا: قد تكون 'a' "أصغر من" 'b'، ولكن لا توجد علاقة أبجدية ذات معنى بين حرف ياباني (kuten) وحرف يوناني (lambda)، ولكن القدرة على تعيين "قيمة" موثوقة تجعل خوارزميات الفرز ممكنة، وإن لم تكن دائمًا منطقية. في معظم الحالات، يجب معاملة القيمة المرجعة على أنها "متساوية" أو "غير متساوية".

مثل stricmp، يتوقع أن تكون كلتا السلسلتين منتهيتين بـ NULL.

المعاملات

str1 السلسلة الأولى للمقارنة.
str2 السلسلة الثانية للمقارنة.

الإرجاع

-1 إذا كانت str1 "أصغر من" str2، 1 إذا كانت "أكبر من"، 0 إذا كانت متساوية.

int PHYSFS_unmount (const char * oldDir)

إزالة دليل أو أرشيف من مسار البحث. هذا مكافئ وظيفيًا لـ PHYSFS_removeFromSearchPath()، ولكن تم إهمال تلك الدالة للحفاظ على المفردات متوافقة مع PHYSFS_mount().

يجب أن يكون هذا تطابقًا (حساسًا لحالة الأحرف) لدليل أو أرشيف موجود بالفعل في مسار البحث، محددًا بالترميز الخاص بالمنصة.

سيفشل هذا الاستدعاء (وسيفشل في الإزالة من المسار) إذا كانت هناك ملفات مفتوحة فيه.

تحذير

تطلب هذه الدالة المسار إلى الأرشيف أو الدليل الذي تم تحميله (نفس السلسلة المستخدمة كوسيط "newDir" للدالة PHYSFS_addToSearchPath أو أي من دوال التحميل)، وليس المسار الذي يتم تحميله فيه في الشجرة (الوسيط "mountPoint" لأي من دوال التحميل).

المعاملات

oldDir الدليل / الأرشيف المراد إزالته.

الإرجاع

قيمة غير صفرية عند النجاح، وصفر عند الفشل. استخدم PHYSFS_getLastErrorCode() للحصول على الخطأ المحدد.
