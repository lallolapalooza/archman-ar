typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Function signature for callbacks that enumerate files.

Warning

As of PhysicsFS 2.1, Use PHYSFS_EnumerateCallback with PHYSFS_enumerate() instead; it gives you more control over the process.

These are used to report a list of directory entries to an original caller, one file/dir/symlink per callback. All strings are UTF-8 encoded. Functions should not try to modify or free any string's memory.

These callbacks are used, starting in PhysicsFS 1.1, as an alternative to functions that would return lists that need to be cleaned up with PHYSFS_freeList(). The callback means that the library doesn't need to allocate an entire list and all the strings up front.

Be aware that promised data ordering in the list versions are not necessarily so in the callback versions. Check the documentation on specific APIs, but strings may not be sorted as you expect and you might get duplicate strings.

Parameters

data User-defined data pointer, passed through from the API that eventually called the callback.
origdir A string containing the full path, in platform-independent notation, of the directory containing this file. In most cases, this is the directory on which you requested enumeration, passed in the callback for your convenience.
fname The filename that is being enumerated. It may not be in alphabetical order compared to other callbacks that have fired, and it will not contain the full path. You can recreate the fullpath with $origdir/$fname ... The file can be a subdirectory, a file, a symlink, etc.

Values that represent specific causes of failure. Most of the time, you should only concern yourself with whether a given operation failed or not, but there may be occasions where you plan to handle a specific failure case gracefully, so we provide specific error codes.

int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

"Fold" a Unicode codepoint to a lowercase equivalent. (This is for limited, hardcore use. If you don't immediately see a need for it, you can probably ignore this forever.)

This will convert a Unicode codepoint into its lowercase equivalent. Bogus codepoints and codepoints without a lowercase equivalent will be returned unconverted.

Note that you might get multiple codepoints in return! The German Eszett, for example, will fold down to two lowercase latin 's' codepoints. The theory is that if you fold two strings, one with an Eszett and one with "SS" down, they will match.

Warning

Anyone that is a student of Unicode knows about the "Turkish I" problem. This API does not handle it. Assume this one letter in all of Unicode will definitely fold sort of incorrectly. If you don't know what this is about, you can probably ignore this problem for most of the planet, but perfection is impossible.

Parameters

from The codepoint to fold.
to Buffer to store the folded codepoint values into. This should point to space for at least 3 PHYSFS_uint32 slots.

Returns

The number of codepoints the folding produced. Between 1 and 3.

int PHYSFS_deinit (void )

Deinitialize the PhysicsFS library. This closes any files opened via PhysicsFS, blanks the search/write paths, frees memory, and invalidates all of your file handles.

Note that this call can FAIL if there's a file open for writing that refuses to close (for example, the underlying operating system was buffering writes to network filesystem, and the fileserver has crashed, or a hard drive has failed, etc). It is usually best to close all write handles yourself before calling this function, so that you can gracefully handle a specific failure.

Once successfully deinitialized, PHYSFS_init() can be called again to restart the subsystem. All default API states are restored at this point, with the exception of any custom allocator you might have specified, which survives between initializations.

Returns

nonzero on success, zero on error. Specifics of the error can be gleaned from PHYSFS_getLastError(). If failure, state of PhysFS is undefined, and probably badly screwed up.

int PHYSFS_delete (const char * filename)

Delete a file or directory. (filename) is specified in platform-independent notation in relation to the write dir.

A directory must be empty before this call can delete it.

Deleting a symlink will remove the link, not what it points to, regardless of whether you "permitSymLinks" or not.

So if you've got the write dir set to "C:\mygame\writedir" and call PHYSFS_delete("downloads/maps/level1.map") then the file "C:\mygame\writedir\downloads\maps\level1.map" is removed from the physical filesystem, if it exists and the operating system permits the deletion.

Note that on Unix systems, deleting a file may be successful, but the actual file won't be removed until all processes that have an open filehandle to it (including your program) close their handles.

Chances are, the bits that make up the file still exist, they are just made available to be written over at a later point. Don't consider this a security method or anything. :)

Parameters

filename Filename to delete.

Returns

nonzero on success, zero on error. Use PHYSFS_getLastErrorCode() to obtain the specific error.

يمكن لواجهة برمجة التطبيقات هذه وردود الاتصال نفسها الإبلاغ عن الأخطاء. قبل واجهة برمجة التطبيقات هذه، كان على ردود الاتصال قبول كل عنصر تم تعداده، حتى لو كانوا يبحثون فقط عن كائن معين ويريدون التوقف عند هذا الحد، أو لديهم خطأ فادح ولم يتمكنوا من تنبيه أي شخص. بالإضافة إلى ذلك، إذا كانت PhysicsFS نفسها لديها مشكلة (خطأ في القرص أو ما شابه)، فلن تتمكن من الإبلاغ عنها للتطبيق، بل ستتجاوز العناصر أو توقف التعداد، ولن يعرف المتصل أنه قد فقد بيانات على طول الطريق.

الآن يمكن للمتصل أن يكون متأكدًا من أنه حصل على مجموعة كاملة من البيانات، وإذا رغب في ذلك، فإن رد الاتصال الخاص به لديه السيطرة على ما إذا كان سيتم إيقاف التعداد مبكرًا. راجع الوثائق الخاصة بـ PHYSFS_EnumerateCallback للحصول على تفاصيل حول كيفية سلوك رد الاتصال الخاص بك.

تحذير

اعتبارًا من PhysicsFS 2.1، تم إضعاف هذه الوظيفة. قبل PhysicsFS 2.1، كانت هذه الوظيفة هي الطريقة الوحيدة للحصول على تفاصيل الخطأ تتجاوز القيمة الأساسية التي ترجعها وظيفة معينة. كان من المفترض أن تكون سلسلة قابلة للقراءة البشرية بواحدة من عدة لغات، ولم تكن مفيدة لتحليل التطبيق. كانت هذه مشكلة، لأن المطور وليس المستخدم هو الذي يختار اللغة عند الترجمة، وكان على صانعي PhysicsFS (بشكل سيء) الحفاظ على كمية كبيرة من أعمال الترجمة. لم يتمكن التطبيق من تحليل السلاسل، حتى لو اعتمد على لغة معينة، حيث أن بعضها تم إنشاؤه ديناميكيًا. في الإصدار 2.1 وما بعده، تعيد هذه الوظيفة دائمًا سلسلة ثابتة باللغة الإنجليزية؛ يمكنك استخدامها كمفتاح للسلاسل الخاصة بك إذا أردت، حيث سنعد بعدم تغيير سلاسل الأخطاء الموجودة. أيضًا، إذا كان تطبيقك يرغب في التحقق من الأخطاء المحددة، فإننا نقدم الآن خيارًا أفضل: استخدم PHYSFS_getLastErrorCode() بدلاً من ذلك.

الحصول على رسالة الخطأ الأخيرة لـ PhysicsFS كسلسلة نصية قابلة للقراءة البشرية ومنتهية بـ NULL. سيعيد NULL إذا لم يكن هناك خطأ منذ آخر استدعاء لهذه الوظيفة. يشير المؤشر الذي تعيده هذه المكالمة إلى مخزن مؤقت داخلي. لكل مؤشر ترابط حالة خطأ فريدة مرتبطة به، ولكن في كل مرة يتم فيها تعيين رسالة خطأ جديدة، سيتم الكتابة فوق الرسالة السابقة المرتبطة بهذا المؤشر. من الآمن استدعاء هذه الوظيفة في أي وقت، حتى قبل PHYSFS_init().

PHYSFS_getLastError() و PHYSFS_getLastErrorCode() يقومان بإعادة تعيين نفس حالة الخطأ الخاصة بالمؤشر. استدعاء أحدهما سيمحو بيانات الآخر. إذا كنت بحاجة إلى كليهما، قم باستدعاء PHYSFS_getLastErrorCode()، ثم مرر هذه القيمة إلى PHYSFS_getErrorByCode().

اعتبارًا من PhysicsFS 2.1، تقدم هذه الوظيفة النصوص باللغة الإنجليزية فقط، ولكن السلاسل ثابتة، لذا يمكنك استخدامها كمفاتيح في قاموس الترجمة الخاص بك. هذه السلاسل مخصصة للتمرير مباشرة إلى المستخدم.

بشكل عام، يجب أن تهتم التطبيقات فقط بما إذا كانت وظيفة معينة قد فشلت؛ ومع ذلك، إذا كان الكود الخاص بك يتطلب مزيدًا من التفاصيل، فيجب عليك استخدام PHYSFS_getLastErrorCode() بدلاً من هذه الوظيفة.

يعيد

سلسلة للقراءة فقط لرسالة الخطأ الأخيرة.

### Sección 5:
PHYSFS_getPrefDir
Obtiene la ruta de directorio específica para escritura de archivos, función de ayuda.
Obtiene el "pref dir". Esto es para donde los usuarios puedan escribir archivos personales (preferencias y guardar juegos, etc) específicos de su aplicación. Este directorio es único por usuario y por aplicación.
Esta función decide la ubicación adecuada en el sistema de archivos nativo, crea el directorio si necesario y devuelve una cadena en notación dependiente de plataforma apta para pasar a PHYSFS_setWriteDir().
En Windows, podría parecer: "C:\\Users\\bob\\AppData\\Roaming\\My Company\\My Program Name" En Linux, podría parecer: "/home/bob/.local/share/My Program Name" En Mac OS X, podría parecer: "/Users/bob/Library/Application Support/My Program Name" (etc.)
Debes usar el pref dir para tu ruta de escritura, y también colocarlo cerca del principio de tu ruta de búsqueda. Versiones antiguas de PhysicsFS ofrecían solo PHYSFS_getUserDir() y dejaban a los usuarios figuran donde los archivos deberían estar bajo ese árbol. Esta encuentra la ubicación correcta para cualquier plataforma, que no solo cambia entre sistemas operativos, sino también entre versiones del mismo sistema operativo.
Especifica el nombre de tu organización (si no es un organismo real, tu nombre o un dominio que posees podría hacerlo) y el nombre de tu aplicación. Estos deben ser nombres correctos.
Ambos los (org) y (app) strings pueden ser parte del nombre de un directorio, así que por favor siga estas reglas:
  • Usa el mismo string de organización (incluyendo la sensibilidad de mayúsculas) para todas tus aplicaciones que usen esta función.
  • Usa un string único para cada aplicación y asegúrate de que no cambie después de haber decidido su ubicación.
  • Caracteres Unicode son válidos, siempre que estén codificados en UTF-8, pero...
  • ...sólo use letras, números y espacios. Evita caracteres como "Game Name 2: Bad Guy's Revenge!" ... "Game Name 2" es suficiente.
El puntero devuelto por esta función queda válido hasta que lo uses de nuevo o llames PHYSFS_deinit(). No es necesariamente una llamada rápida, así que deberías llamarla una vez al inicio y copiar la cadena si la necesitas.
Debes asumir que la ruta devuelta es la única ubicación segura para escribir archivos (y que PHYSFS_getUserDir() y PHYSFS_getBaseDir(), aunque puedan ser escritos, o incluso padres de la ruta devuelta, no son donde debes escribir).

org: nombre de tu organización. app: nombre de tu aplicación.
Devuelve
string de directorio de usuario en notación dependiente de plataforma. NULL si hay un problema (creación del directorio falló, etc).

### Sección 6:
PHYSFS_getRealDir
Determina dónde en la ruta de búsqueda se encuentra un archivo. El archivo se especifica en notación independiente de plataforma. El nombre devuelto será el elemento de la ruta de búsqueda donde fue encontrado, que podría ser un directorio o un archivo archivado. Aunque haya múltiples coincidencias en diferentes partes de la ruta de búsqueda, solo se usa la primera encontrada, como cuando se abre un archivo.
Así, si buscas "maps/level1.map" y C:\mygame está en tu ruta de búsqueda y C:\mygame\maps\level1.map existe, se devuelve "C:\mygame".
Si cualquier parte de una coincidencia es un enlace simbólico y no has permitido enlaces simbólicos explícitamente, se ignorará y la búsqueda continuará.
Si especificas un directorio falsificado que solo existe como un punto de montaje, se asociará con el primer archivo archivado allí, incluso aunque ese directorio no esté contenido en un archivo real.
Advertencia
Este devolverá NULL si no hay un directorio real asociado (filename). Específicamente, PHYSFS_mountIo(), PHYSFS_mountMemory() y PHYSFS_mountHandle() devolverán NULL incluso si el archivo se encuentra en la ruta de búsqueda. Planifica adecuadamente.
Parámetros
filename: archivo a buscar.
Devuelve
string de elemento de la ruta de búsqueda que contiene el archivo en cuestión. NULL si no se encuentra.

int PHYSFS_init (const char * argv0)

Initialize the PhysicsFS library. This must be called before any other PhysicsFS function.

This should be called prior to any attempts to change your process's current working directory.

Warning

On Android, argv0 should be a non-NULL pointer to a PHYSFS_AndroidInit struct. This struct must hold a valid JNIEnv * and a JNI jobject of a Context (either the application context or the current Activity is fine). Both are cast to a void * so we don't need jni.h included wherever physfs.h is. PhysicsFS uses these objects to query some system details. PhysicsFS does not hold a reference to the JNIEnv or Context past the call to PHYSFS_init(). If you pass a NULL here, PHYSFS_init can still succeed, but PHYSFS_getBaseDir() and PHYSFS_getPrefDir() will be incorrect.

argv0 the argv[0] string passed to your program's mainline. This may be NULL on most platforms (such as ones without a standard main() function), but you should always try to pass something in here. Many Unix-like systems need to pass argv[0] from main() in here. See warning about Android, too!

nonzero on success, zero on error. Specifics of the error can be gleaned from PHYSFS_getLastError().

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

Parameters

newDir directory or archive to add to the path, in platform-dependent notation.
mountPoint Location in the interpolated tree that this archive will be "mounted", in platform-independent notation. NULL or "" is equivalent to "/".
appendToPath nonzero to append to search path, zero to prepend.

Returns

nonzero if added to path, zero on failure (bogus archive, dir missing, etc). Use PHYSFS_getLastErrorCode() to obtain the specific error.

تحذير

ما لم يكن لديك حاجة خاصة ومنخفضة المستوى، يجب عليك استخدام PHYSFS_mount() بدلاً من ذلك.

قد تكون الأرشيفات داخل الأرشيفات بطيئة جدًا! بينما يمكن لـ PHYSFS_File البحث حتى عندما تكون البيانات مضغوطة، فقد تفعل ذلك عن طريق الرجوع إلى البداية وفك ضغط كل شيء قبل نقطة البحث. قد يؤدي الاستخدام العادي للأرشيف إلى الكثير من البحث خلف الكواليس. على هذا النحو، قد تجد أن الاستخدام العادي للأرشيف مؤلم للغاية إذا تم تحميله بهذه الطريقة. خطط وفقًا لذلك: إذا كان لديك، على سبيل المثال، ملف .zip ذاتي الاستخراج، وتريد تحميل شيء بداخله، فقم بضغط محتويات الأرشيف الداخلي وتأكد من أن ملف .zip الخارجي لا يضغط الأرشيف الداخلي أيضًا.

تعمل هذه الوظيفة تمامًا مثل PHYSFS_mount()، ولكنها تأخذ مقبض PHYSFS_File بدلاً من اسم المسار. يحتوي هذا المقبض على جميع بيانات الأرشيف، ويتم استخدامه بدلاً من ملف حقيقي في نظام الملفات الفعلي. قد يكون PHYSFS_File مدعومًا بملف حقيقي في نظام الملفات الفعلي، ولكنه ليس بالضرورة. الاستخدام الأكثر شيوعًا لهذا هو على الأرجح تحميل الأرشيفات المخزنة داخل أرشيفات أخرى.

(newDir) يجب أن يكون سلسلة فريدة لتحديد هذا الأرشيف. يستخدم لتحسين اختيار الأرشيف (إذا سميته XXXXX.zip، فقد نحاول أولاً أرشيف ZIP، على سبيل المثال، أو نختار مباشرة أرشيفًا لا يمكنه الوثوق بصحة البيانات إلا من خلال امتداد اسم الملف). لا يحتاج إلى الإشارة إلى ملف حقيقي على الإطلاق. إذا لم يكن امتداد اسم الملف مفيدًا، فسيحاول النظام كل أرشيف حتى يعمل أحدهم أو لا يعمل أي منهم. يجب أن يكون اسم الملف هذا فريدًا، حيث لن يسمح لك النظام بأن يكون لديك أرشيفان بنفس الاسم.

(file) يجب أن يظل موجودًا حتى يتم إلغاء تحميل الأرشيف. عند إلغاء تحميل الأرشيف، ستستدعي النظام PHYSFS_close(file). إذا كنت بحاجة إلى بقاء هذا المقبض، فسيتعين عليك تغليفه في PHYSFS_Io واستخدام PHYSFS_mountIo() بدلاً من ذلك.

إذا فشلت هذه الوظيفة، فلن يتم استدعاء PHYSFS_close(file).

المعلمات

file مقبض PHYSFS_File الذي يحتوي على بيانات الأرشيف.
newDir اسم ملف يمكن أن يمثل هذا التدفق.
mountPoint الموقع في الشجرة المستقرضة التي سيتم "تحميل" هذا الأرشيف فيها، بتدوين مستقل عن النظام الأساسي. NULL أو "" يعادل "/".
appendToPath قيمة غير صفرية للإلحاق بمسار البحث، صفر للاستباق.

العودة

قيمة غير صفرية إذا تمت إضافتها إلى المسار، صفر في حالة الفشل (أرشيف زائف، إلخ). استخدم PHYSFS_getLastErrorCode() للحصول على الخطأ المحدد.

هذا أمر متقدم وشديد التعقيد. لست بحاجة إليه إلا إذا كنت تعرف حقًا ما تفعله. معظم التطبيقات لن تحتاج إليه.

int PHYSFS_setRoot (const char * archive, const char * subdir)

اجعل دليلًا فرعيًا للأرشيف دليلًا جذريًا له. يتيح لك هذا تضييق الملفات التي يمكن الوصول إليها في أرشيف معين. على سبيل المثال، إذا كان لديك x.zip مع ملف في y/z.txt، وتم تحميله على /a، وإذا قمت باستدعاء PHYSFS_setRoot("x.zip", "/y")، فإن استدعاء PHYSFS_openRead("/a/z.txt") سينجح.

يمكنك تغيير جذر الأرشيف في أي وقت، مما يؤدي إلى تغيير شجرة الملفات المدمجة (اعتمادًا على مكان تحول المسارات، قد يوفر أرشيف مختلف ملفات مختلفة). إذا قمت بتعيين الجذر إلى NULL أو "/"، فسيتم معاملة الأرشيف كما لو لم يتم تعيين جذر خاص (كما لو تم تحميل الأرشيف بشكل طبيعي).

يؤثر تغيير الجذر فقط على العمليات المستقبلية على أسماء المسارات؛ لن يتأثر الملف الذي تم فتحه من مسار تغير بسبب setRoot.

لا يقتصر تعيين جذر جديد على الأرشيفات الموجودة في مسار البحث؛ يمكنك تعيين واحد على دليل الكتابة أيضًا، والذي قد يكون مفيدًا إذا كان لديك ملفات مفتوحة للكتابة وبالتالي لا يمكنك تغيير دليل الكتابة في الوقت الحالي.

لا يعتبر خطأ تعيين دليل فرعي غير موجود ليصبح جذر الأرشيف؛ ومع ذلك، لن تكون هناك ملفات مرئية في هذه الحالة. إذا تم إنشاء الدلائل المفقودة في النهاية (mkdir لنظام الملفات الفعلي، إلخ) فسيتم عكس ذلك في شجرة الملفات المدمجة.

المعلمات

archive دليل/أرشيف لتغيير الجذر فيه.
subdir دليل فرعي جديد لجعله جذر هذا الأرشيف.

int PHYSFS_setSaneConfig (const char * organization, const char * appName, const char * archiveExt, int includeCdRoms, int archivesFirst)

إعداد مسارات افتراضية منطقية. وظيفة مساعدة.

سيتم تعيين دليل الكتابة إلى دليل التفضيلات الذي تم إرجاعه بواسطة

PHYSFS_getPrefDir(organization, appName)

، والذي يتم إنشاؤه إذا لم يكن موجودًا.

ما سبق كافٍ لضمان فصل دليل تكوين برنامجك عن الفوضى الأخرى، وهو مستقل عن المنصة.

سيكون مسار البحث:

  • دليل الكتابة (يتم إنشاؤه إذا لم يكن موجودًا)
  • الدليل الأساسي (PHYSFS_getBaseDir())
  • جميع أدلة أقراص CD-ROM التي تم العثور عليها (اختياريًا)

ثم يتم البحث في هذه الأدلة عن ملفات تنتهي بالامتداد (archiveExt)، والتي، إذا كانت أرشيفات صالحة ومدعومة، فسيتم إضافتها أيضًا إلى مسار البحث. إذا حددت "PKG" لـ (archiveExt)، وكان هناك ملف يسمى data.PKG في الدليل الأساسي، فسيتم التحقق منه. يمكن إلحاق الأرشيفات أو إلحاقها بمسار البحث بترتيب أبجدي، بغض النظر عن الأدلة التي تم العثور عليها فيها. يتم تحميل جميع الأرشيفات في جذر نظام الملفات الافتراضي ("/").

يمكن تحقيق كل هذا من التطبيق، ولكن هذا يقوم بكل شيء من أجلك. لا تتردد في إضافة المزيد إلى مسار البحث يدويًا أيضًا.

المعلمات

organization اسم شركتك/مجموعتك/إلخ ليتم استخدامه كدليل، لذا اجعله صغيرًا وبسيطًا.
appName اسم برنامجك الخاص بالبرنامج، لفصله عن البرامج الأخرى التي تستخدم PhysicsFS.
archiveExt امتداد الملف الذي يستخدمه برنامجك لتحديد أرشيف. على سبيل المثال، يستخدم Quake 3 "pk3"، على الرغم من أنها مجرد ملفات مضغوطة. حدد NULL لعدم استخراج الأرشيفات تلقائيًا. لا تحدد الحرف '.'؛ إذا كنت تريد البحث عن ملفات ZIP، فحدد "ZIP" وليس ".ZIP" ... البحث عن الأرشيف غير حساس لحالة الأحرف.
includeCdRoms قيمة غير صفرية لتضمين أقراص CD-ROM في مسار البحث، و (إذا كان (archiveExt) != NULL) البحث فيها عن أرشيفات. قد يتسبب هذا في قدر كبير من التعليق أثناء الوصول إلى الأقراص، وإذا لم تكن هناك أقراص في المحرك (أو حتى غير محملة على أنظمة Unix)، فقد لا يتم توفيرها على أي حال. قد ترغب في تحديد صفر والتعامل مع إعداد القرص بنفسك.
archivesFirst قيمة غير صفرية لإلحاق الأرشيفات بمسار البحث. صفر لإلحاقها. يتم تجاهلها إذا كان !(archiveExt).

const PHYSFS_ArchiveInfo ** PHYSFS_supportedArchiveTypes (void )

الحصول على قائمة بأنواع الأرشيف المدعومة. الحصول على قائمة بأنواع الأرشيف التي تدعمها هذه التنفيذ لـ PhysicFS. هذه هي تنسيقات الملفات القابلة للاستخدام لإدخالات مسار البحث. هذا لأغراض إعلامية فقط. لاحظ أن الامتداد المدرج هو مجرد اصطلاح: إذا أدرجنا "ZIP"، يمكنك فتح أرشيف متوافق مع PkZip بامتداد "XYZ"، إذا أردت.

القيمة المرتجعة هي مصفوفة من المؤشرات إلى هياكل PHYSFS_ArchiveInfo، مع إدخال NULL للدلالة على نهاية القائمة:

PHYSFS_ArchiveInfo **i;
for (i = PHYSFS_supportedArchiveTypes(); *i != NULL; i++)
{
    printf("Supported archive: [%s], which is [%s].\n",
             (*i)->extension, (*i)->description);
}

القيم المرتجعة هي مؤشرات إلى الذاكرة الداخلية، ويجب اعتبارها للقراءة فقط، ولا يجب تحريرها أبدًا. القيم المرتجعة صالحة حتى الاستدعاء التالي لـ PHYSFS_deinit() أو PHYSFS_registerArchiver() أو PHYSFS_deregisterArchiver().
