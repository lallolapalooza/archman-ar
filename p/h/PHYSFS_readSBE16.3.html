حذف ملف أو دليل. (اسم الملف) محدد بتنسيق مستقل عن النظام الأساسي بالنسبة إلى دليل الكتابة.

يجب أن يكون الدليل فارغًا قبل أن تتمكن هذه المكالمة من حذفه.

سيؤدي حذف رابط رمزي إلى إزالة الرابط، وليس ما يشير إليه، بغض النظر عما إذا كنت قد قمت بتعيين "السماح بالروابط الرمزية" أم لا.

لذلك إذا كان لديك دليل الكتابة معينًا إلى "C:\mygame\writedir" واستدعيت PHYSFS_delete("downloads/maps/level1.map") فسيتم إزالة الملف "C:\mygame\writedir\downloads\maps\level1.map" من نظام الملفات الفعلي، إذا كان موجودًا ويسمح نظام التشغيل بالحذف.

لاحظ أنه على أنظمة Unix، قد يكون حذف ملف ناجحًا، ولكن لن تتم إزالة الملف الفعلي حتى تقوم جميع العمليات التي لديها مقبض ملف مفتوح له (بما في ذلك برنامجك) بإغلاق مقابضها.

على الأرجح، لا تزال أجزاء الملف موجودة، بل تم جعلها متاحة للكتابة فوقها في وقت لاحق. لا تعتبر هذا طريقة أمنية أو أي شيء من هذا القبيل. :)

int PHYSFS_deregisterArchiver (const char * ext)

إزالة برنامج أرشفة من النظام. إذا، لسبب ما، كنت تحتاج فقط إلى برنامج الأرشفة المسجل سابقًا الخاص بك ليعيش لجزء من عمر التطبيق الخاص بك، يمكنك إزالته من النظام بمجرد الانتهاء منه عبر هذه الوظيفة.

يفشل هذا إذا كانت هناك أي أرشيفات لا تزال مفتوحة تستخدم برنامج الأرشفة هذا.

يمكن لهذه الوظيفة أيضًا إزالة برامج الأرشفة المقدمة داخليًا، مثل دعم .zip أو ما شابه. يمكن أن يكون هذا مفيدًا في بعض المواقف، مثل تعطيل دعمها تمامًا أو تجاوزها بتنفيذك الخاص. بمجرد تعطيل برنامج أرشفة داخلي بهذه الطريقة، لا يوفر PhysicsFS آلية لاستعادته، بخلاف استدعاء PHYSFS_deinit() و PHYSFS_init() مرة أخرى.

Unlike PHYSFS_enumerateFiles(), this function does not return an array. Rather, it calls a function specified by the application once per element of the search path:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Items sent to the callback are not guaranteed to be in any order whatsoever. There is no sorting done at this level, and if you need that, you should probably use PHYSFS_enumerateFiles() instead, which guarantees alphabetical sorting. This form reports whatever is discovered in each archive before moving on to the next. Even within one archive, we can't guarantee what order it will discover data. Any sorting you find in these callbacks is just pure luck. Do not rely on it. As this walks the entire list of archives, you may receive duplicate filenames.

This API and the callbacks themselves are capable of reporting errors. Prior to this API, callbacks had to accept every enumerated item, even if they were only looking for a specific thing and wanted to stop after that, or had a serious error and couldn't alert anyone. Furthermore, if PhysicsFS itself had a problem (disk error or whatnot), it couldn't report it to the calling app, it would just have to skip items or stop enumerating outright, and the caller wouldn't know it had lost some data along the way.

Now the caller can be sure it got a complete data set, and its callback has control if it wants enumeration to stop early. See the documentation for PHYSFS_EnumerateCallback for details on how your callback should behave.

dir Directory, in platform-independent notation, to enumerate.
c Callback function to notify about search path elements.
d Application-defined data passed to callback. Can be NULL.

non-zero on success, zero on failure. Use PHYSFS_getLastErrorCode() to obtain the specific error. If the callback returns PHYSFS_ENUM_STOP to stop early, this will be considered success. Callbacks returning PHYSFS_ENUM_ERROR will make this function return zero and set the error code to PHYSFS_ERR_APP_CALLBACK.

char ** PHYSFS_enumerateFiles (const char * dir)

Get a file listing of a search path's directory.

Warning

In PhysicsFS versions prior to 2.1, this function would return as many items as it could in the face of a failure condition (out of memory, disk i/o error, etc). Since this meant apps couldn't distinguish between complete success and partial failure, and since the function could always return NULL to report catastrophic failures anyway, in PhysicsFS 2.1 this function's policy changed: it will either return a list of complete results or it will return NULL for any failure of any kind, so we can guarantee that the enumeration ran to completion and has no gaps in its results.

Matching directories are interpolated. That is, if "C:\mydir" is in the search path and contains a directory "savegames" that contains "x.sav", "y.sav", and "z.sav", and there is also a "C:\userdir" in the search path that has a "savegames" subdirectory with "w.sav", then the following code:

char **rc = PHYSFS_enumerateFiles("savegames");

* We've got [y.sav].
* We've got [z.sav].

int PHYSFS_mountFile (PHYSFS_File * file, const char * newDir, const char * mountPoint, int appendToPath)

Add an archive, contained in a PHYSFS_File handle, to the search path.

Warning

Unless you have some special, low-level need, you should be using PHYSFS_mount() instead of this.

Archives-in-archives may be very slow! While a PHYSFS_File can seek even when the data is compressed, it may do so by rewinding to the start and decompressing everything before the seek point. Normal archive usage may do a lot of seeking behind the scenes. As such, you might find normal archive usage extremely painful if mounted this way. Plan accordingly: if you, say, have a self-extracting .zip file, and want to mount something in it, compress the contents of the inner archive and make sure the outer .zip file doesn't compress the inner archive too.

This function operates just like PHYSFS_mount(), but takes a PHYSFS_File handle instead of a pathname. This handle contains all the data of the archive, and is used instead of a real file in the physical filesystem. The PHYSFS_File may be backed by a real file in the physical filesystem, but isn't necessarily. The most popular use for this is likely to mount archives stored inside other archives.

(newDir) must be a unique string to identify this archive. It is used to optimize archiver selection (if you name it XXXXX.zip, we might try the ZIP archiver first, for example, or directly choose an archiver that can only trust the data is valid by filename extension). It doesn't need to refer to a real file at all. If the filename extension isn't helpful, the system will try every archiver until one works or none of them do. This filename must be unique, as the system won't allow you to have two archives with the same name.

(file) must remain until the archive is unmounted. When the archive is unmounted, the system will call PHYSFS_close(file). If you need this handle to survive, you will have to wrap this in a PHYSFS_Io and use PHYSFS_mountIo() instead.

If this function fails, PHYSFS_close(file) is not called.

تمكين أو تعطيل متابعة الروابط الرمزية. تحتوي بعض أنظمة الملفات المادية والأرشيفات على ملفات ليست سوى مؤشرات إلى ملفات أخرى. على نظام الملفات المادي، سيؤدي فتح مثل هذا الرابط إلى (بشفافية) فتح الملف الذي يشير إليه.

افتراضيًا، سيتحقق PhysicsFS مما إذا كان الملف رابطًا رمزيًا بالفعل أثناء استدعاءات الفتح وسيفشل إذا كان كذلك. وإلا، يمكن للرابط أن يأخذك خارج مسارات الكتابة والبحث، ويعرض الأمان للخطر.

إذا كنت ترغب في تحمل هذا الخطر، اتصل بهذه الدالة بمعامل غير صفري. لاحظ أن هذا يتعلق أكثر بصندوق رمل لغة البرمجة النصية للبرنامج، في حالة محاولة البرامج النصية غير الموثوق بها تعريض النظام للخطر. بشكل عام، يمكن للمستخدم أن يكون لديه سبب مشروع لإنشاء رابط رمزي، لذا ما لم تشعر أن هناك خطرًا محددًا في السماح لهم، يجب عليك السماح لهم.

يتم فحص الروابط الرمزية بشكل صريح فقط عند التعامل مع أسماء الملفات بتدوين مستقل عن النظام الأساسي. أي، عند إعداد مسارات البحث والكتابة وما إلى ذلك، لا يتم فحص الروابط الرمزية مطلقًا.

يرجى ملاحظة أن PHYSFS_stat() سيتحقق دائمًا من المسار المحدد؛ إذا كان هذا المسار رابطًا رمزيًا، فلن يتم اتباعه في أي حالة. إذا لم تكن الروابط الرمزية مسموحًا بها من خلال هذه الدالة، فإن PHYSFS_stat() يتجاهلها، وسيعامل الاستعلام كما لو كان المسار غير موجود على الإطلاق.

يمكن تمكين أو تعطيل إذن الرابط الرمزي في أي وقت بعد استدعاء PHYSFS_init()، وهو معطل افتراضيًا.

المعلمات

allow قيمة غير صفرية للسماح بالروابط الرمزية، صفر لرفض الربط.

قراءة البيانات من مقبض ملف PhysicsFS. يجب فتح الملف للقراءة.

مهمل

اعتبارًا من PhysicsFS 2.1، استخدم PHYSFS_readBytes() بدلاً من ذلك. هذه الدالة ما هي إلا تغليف لها. لم توضح هذه الدالة أبدًا ما سيحدث إذا تمكنت من قراءة كائن جزئي، لذا فإن العمل على مستوى البايت يجعل هذا الأمر أوضح للجميع، خاصة الآن بعد أنه يمكن توفير واجهات PHYSFS_Io بواسطة التطبيق.

المعلمات

handle المقبض الذي تم إرجاعه من PHYSFS_openRead().
buffer المخزن المؤقت لتخزين البيانات المقروءة فيه.
objSize حجم الكائنات المراد قراءتها بالبايت من (المقبض).
objCount عدد الكائنات (objSize) المراد قراءتها من (المقبض).

يعيد

عدد الكائنات المقروءة. يمكن لـ PHYSFS_getLastErrorCode() تسليط الضوء على سبب كون هذا أقل من (objCount)، وكذلك PHYSFS_eof(). -1 في حالة الفشل الكامل.

تمكين أو تعطيل متابعة الروابط الرمزية. تحتوي بعض أنظمة الملفات المادية والأرشيفات على ملفات ليست سوى مؤشرات إلى ملفات أخرى. على نظام الملفات المادي، سيؤدي فتح مثل هذا الرابط إلى (بشفافية) فتح الملف الذي يشير إليه.

افتراضيًا، سيتحقق PhysicsFS مما إذا كان الملف رابطًا رمزيًا بالفعل أثناء استدعاءات الفتح وسيفشل إذا كان كذلك. وإلا، يمكن للرابط أن يأخذك خارج مسارات الكتابة والبحث، ويعرض الأمان للخطر.

إذا كنت ترغب في تحمل هذا الخطر، اتصل بهذه الدالة بمعامل غير صفري. لاحظ أن هذا يتعلق أكثر بصندوق رمل لغة البرمجة النصية للبرنامج، في حالة محاولة البرامج النصية غير الموثوق بها تعريض النظام للخطر. بشكل عام، يمكن للمستخدم أن يكون لديه سبب مشروع لإنشاء رابط رمزي، لذا ما لم تشعر أن هناك خطرًا محددًا في السماح لهم، يجب عليك السماح لهم.

يتم فحص الروابط الرمزية بشكل صريح فقط عند التعامل مع أسماء الملفات بتدوين مستقل عن النظام الأساسي. أي، عند إعداد مسارات البحث والكتابة وما إلى ذلك، لا يتم فحص الروابط الرمزية مطلقًا.

يرجى ملاحظة أن PHYSFS_stat() سيتحقق دائمًا من المسار المحدد؛ إذا كان هذا المسار رابطًا رمزيًا، فلن يتم اتباعه في أي حالة. إذا لم تكن الروابط الرمزية مسموحًا بها من خلال هذه الدالة، فإن PHYSFS_stat() يتجاهلها، وسيعامل الاستعلام كما لو كان المسار غير موجود على الإطلاق.

يمكن تمكين أو تعطيل إذن الرابط الرمزي في أي وقت بعد استدعاء PHYSFS_init()، وهو معطل افتراضيًا.

المعلمات

allow قيمة غير صفرية للسماح بالروابط الرمزية، صفر لرفض الربط.

يجعل دليل فرعي من أرشيف ما هو دليل الجذر الخاص به. هذا يسمح لك بتقييد الملفات التي يمكن الوصول إليها في أرشيف معين. على سبيل المثال، إذا كان لديك x.zip يحتوي على ملف في y/z.txt تم تحميله على /a، وإذا قمت باستدعاء PHYSFS_setRoot("x.zip", "/y")، فإن استدعاء PHYSFS_openRead("/a/z.txt") سينجح.

يمكنك تغيير جذر أرشيف في أي وقت، مما يؤثر على شجرة الملفات المستقرة (اعتمادًا على مكان تحرك المسارات، قد يوفر أرشيف مختلف ملفات متعددة). إذا قمت بتعيين الجذر إلى NULL أو "/", فسيتم التعامل مع الأرشيف كما لو لم يتم تحديد جذر خاص (كما لو تم تحميل الأرشيف بشكل طبيعي).

يؤثر تغيير الجذر فقط على العمليات المستقبلية على مسارات الملفات؛ لن يتأثر الملف الذي تم فتحه من مسار تغير بسبب setRoot.

لا يقتصر تعيين جذر جديد على الأرشيفات في دليل البحث؛ يمكنك تعيين جذر في دليل الكتابة أيضًا، والذي قد يكون مفيدًا إذا كان لديك ملفات مفتوحة للكتابة ولا يمكنك تغيير دليل الكتابة الآن.

لا يعد خطأ تعيين دليل فرعي غير موجود كجذر لأرشيف، على الرغم من أنه لن يتم عرض أي ملفات في هذه الحالة. إذا تم إنشاء الأدلة المفقودة (mkdir في نظام الملفات الفعلي، وما إلى ذلك)، فسيتم عكس ذلك في الشجرة المستقرة.

تحويل سلسلة نصية بتشفير UTF-8 إلى سلسلة نصية بتشفير UCS-4.

تحذير

لن تقوم هذه الدالة بالإبلاغ عن خطأ إذا كانت هناك تسلسلات UTF-8 غير صالحة في السلسلة المصدر. ستقوم باستبدالها بحرف '؟' وتستمر.

سلاسل UCS-4 (المعروفة أيضًا باسم UTF-32) هي 32 بت لكل حرف: wchar_t على Unix.

للتأكد من أن المخزن المؤقت الوجهة كبير بما يكفي للتحويل، يرجى تخصيص مخزن مؤقت بحجم أربعة أضعاف حجم المخزن المؤقت المصدر. يستخدم UTF-8 من بايت واحد إلى أربعة بايتات لكل حرف، ولكن UCS-4 يستخدم دائمًا أربعة، لذلك ستتضاعف حجم سلسلة ASCII منخفضة بالكامل!

سيتم اقتطاع النصوص التي لا تتناسب مع المخزن المؤقت الوجهة، ولكنها ستنتهي دائمًا بـ NULL ولن تحتوي أبدًا على تسلسل UTF-8 غير مكتمل في النهاية. إذا كان طول المخزن المؤقت 0، فإن هذه الدالة لا تفعل شيئًا.

void PHYSFS_utf8ToUtf16 (const char * src, PHYSFS_uint16 *dst, PHYSFS_uint64 len)

قم بتحويل سلسلة نصية بصيغة UTF-8 إلى سلسلة نصية بصيغة UTF-16.

تحذير

لن تقوم هذه الدالة بالإبلاغ عن خطأ إذا كانت هناك تسلسلات UTF-8 غير صالحة في سلسلة الإدخال. سيتم استبدال هذه بحرف '؟' وستستمر الدالة.

سلاسل UTF-16 تحتوي على 16 بت لكل حرف (ما لم تكن بعض الأحرف 32 بت): TCHAR في Windows، عند بنائها مع دعم Unicode. تستخدم إصدارات Windows الحديثة UTF-16. كانت إصدارات Windows القديمة قبل عام 2000 تستخدم TCHAR، ولكنها تدعم فقط UCS-2. UTF-16 هو UCS-2، ما لم تكن الأحرف ذات الـ 4 بايت غير قابلة للتمثيل في UCS-2 على الإطلاق. إذا لم تكن متأكدًا، يجب أن تستخدم UTF-16 في Windows الآن.

لضمان أن يكون المخزن المؤقت الوجهة كبيرًا بما يكفي للتحويل، يرجى تخصيص مخزن مؤقت بحجم ضعف حجم مخزن الإدخال. يستخدم UTF-8 من بايت واحد إلى أربعة بايتات لكل حرف، ولكن UTF-16 يستخدم دائمًا من اثنين إلى أربعة، لذا ستتضاعف سلسلة ASCII بالكامل في الحجم! الأحرف UTF-16 التي ستتطلب أربعة بايتات ستتطلب أيضًا أربعة بايتات في UTF-8، لذلك لا تحتاج إلى تخصيص 4 أضعاف المساحة في حالة الخطأ: ضعف المساحة سيكون كافيًا.

سيتم اقتطاع السلاسل التي لا تتناسب مع المخزن المؤقت الوجهة، ولكن سيتم دائمًا إنهاؤها بحرف فارغ ولن تحتوي أبدًا على زوج غير مكتمل من البدل في النهاية. إذا كان حجم المخزن المؤقت 0، فلن تقوم هذه الدالة بأي شيء.
