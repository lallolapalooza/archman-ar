PHYSFS_Allocator * PHYSFS_getAllocator (void )

Get the currently used allocator. This can be useful for apps that want to access PhysicsFS's internal, default allocation routines, as well as for external code that wants to share the same allocator, even if the application specified their own.

This call is only valid between PHYSFS_init() and PHYSFS_deinit() calls; it will return NULL if the library isn't initialized. As we can't guarantee the state of the internal allocators unless the library is initialized, you shouldn't use any allocator returned here after a call to PHYSFS_deinit().

Do not call the returned allocator's Init() or Deinit() methods under any circumstances.

If you aren't immediately sure what to do with this function, you can safely ignore it altogether.

Returns

Current allocator, as set by PHYSFS_setAllocator(), or PhysicsFS's internal, default allocator if no application defined allocator is currently set. Will return NULL if the library is not initialized.

const char * PHYSFS_getBaseDir (void )

Get the path where the application resides. Helper function.

Get the "base dir". This is the directory where the application was run from, which is probably the installation directory, and may or may not be the process's current working directory.

You should probably use the base dir in your search path.

Warning

On most platforms, this is a directory; on Android, this gives you the path to the app's package (APK) file. As APK files are just .zip files, you can mount them in PhysicsFS like regular directories. You'll probably want to call PHYSFS_setRoot(basedir, "/assets") after mounting to make your app's actual data available directly without all the Android metadata and directory offset. Note that if you passed a NULL to PHYSFS_init(), you will not get the APK file here.

Returns

READ ONLY string of base dir in platform-dependent notation.

char ** PHYSFS_getCdRomDirs (void )

Get an array of paths to available CD-ROM drives. The dirs returned are platform-dependent ("D:\" on Win32, "/cdrom" or whatnot on Unix). Dirs are only returned if there is a disc ready and accessible in the drive. So if you've got two drives (D: and E:), and only E: has a disc in it, then that's all you get. If the user inserts a disc in D: and you call this function again, you get both drives. If, on a Unix box, the user unmounts a disc and remounts it elsewhere, the next call to this function will reflect that change.This function refers to "CD-ROM" media, but it really means "inserted disc media," such as DVD-ROM, HD-DVD, CDRW, and Blu-Ray discs. const char * PHYSFS_getDirSeparator (void )

Get platform-dependent dir separator string. This returns "\" on win32, "/" on Unix, and ":" on MacOS. It may be more than one character, depending on the platform, and your code should take that into account. Note that this is only useful for setting up the search/write paths, since access into those dirs always use '/' (platform-independent notation) to separate directories. const char * PHYSFS_getErrorByCode (PHYSFS_ErrorCode code)

Get human-readable description string for a given error code. Get a static string, in UTF-8 format, that represents an English description of a given error code.

This string is guaranteed to never change (although we may add new strings for new error codes in later versions of PhysicsFS), so you can use it for keying a localization dictionary.

It is safe to call this function at anytime, even before PHYSFS_init().

These strings are meant to be passed on directly to the user. Generally, applications should only concern themselves with whether a given function failed, but not care about the specifics much.

Do not attempt to free the returned strings; they are read-only and you don't own their memory pages.

Parameters

code Error code to convert to a string.

Returns

READ ONLY string of requested error message, NULL if this is not a valid PhysicsFS error code. Always check for NULL if you might be looking up an error code that didn't exist in an earlier version of PhysicsFS.

const char * PHYSFS_getLastError (void )

Get human-readable error information.

Deprecated

Use PHYSFS_getLastErrorCode() and PHYSFS_getErrorByCode() instead.

Warning

As of PhysicsFS 2.1, this function has been nerfed. Before PhysicsFS 2.1, this function was the only way to get error details beyond a given function's basic return value. This was meant to be a human-readable string in one of several languages, and was not useful for application parsing. This was a problem, because the developer and not the user chose the language at compile time, and the PhysicsFS maintainers had to (poorly) maintain a significant amount of localization work. The app couldn't parse the strings, even if they counted on a specific language, since some were dynamically generated. In 2.1 and later, this always returns a static string in English; you may use it as a key string for your own localizations if you like, as we'll promise not to change existing error strings. Also, if your application wants to look at specific errors, we now offer a better option: use PHYSFS_getLastErrorCode() instead.

Get the last PhysicsFS error message as a human-readable, null-terminated string. This will return NULL if there's been no error since the last call to this function. The pointer returned by this call points to an internal buffer. Each thread has a unique error state associated with it, but each time a new error message is set, it will overwrite the previous one associated with that thread. It is safe to call this function at anytime, even before PHYSFS_init().

PHYSFS_getLastError() and PHYSFS_getLastErrorCode() both reset the same thread-specific error state. Calling one will wipe out the other's data. If you need both, call PHYSFS_getLastErrorCode(), then pass that value to PHYSFS_getErrorByCode().

As of PhysicsFS 2.1, this function only presents text in the English language, but the strings are static, so you can use them as keys into your own localization dictionary. These strings are meant to be passed on directly to the user.

Generally, applications should only concern themselves with whether a given function failed; however, if your code require more specifics, you should use PHYSFS_getLastErrorCode() instead of this function.

Returns

READ ONLY string of last error message.

Añade un archivo, contenido en un PHYSFS_File handle, a la ruta de búsqueda.

Aviso

No debe usarse PHYSFS_mount() si no tiene algún necesidad especial, baja nivel.

Los archivos-in-archivos pueden ser muy lentos! Aunque un PHYSFS_File puede seek incluso cuando los datos están comprimidos, puede hacerlo restando al principio y descompressionando todo antes del punto de seek. El uso normal de archivos puede hacer un gran número de seeks en el fondo. Como tal, podrías encontrar el uso normal de archivos extremadamente incómodo si se monta así. Planifica adecuadamente: si tienes, por ejemplo, un archivo .zip self-extracting y quieres montar algo dentro, comprime los contenidos del archivo interior y asegúrate de que el archivo exterior no comprima el interior demasiado.

Esta función opera exactamente como PHYSFS_mount(), pero toma un PHYSFS_File handle en lugar de un camino. Este handle contiene toda la data del archivo, y se usa en lugar de un archivo real en el sistema de archivos físico. El PHYSFS_File puede ser backed por un archivo real en el sistema de archivos físico, pero no necesariamente es así. La más popular usos de esta es montar archivos que están dentro de otros archivos.

(newDir) debe ser un string único para identificar este archivo. Se usa para optimizar el seleccionar archiver (si lo nombras XXXXX.zip, podríamos intentar el archiver ZIP, por ejemplo, o elegir directamente un archiver que solo confie en la extensión de nombre). No necesita referirse a un archivo real en absoluto. Si la extensión del nombre no es útil, el sistema intentará cada archiver hasta que uno funcione o ninguno lo haga. Este nombre debe ser único, ya que el sistema no permitirá tener dos archivos con el mismo nombre.

(file) debe permanecer hasta que el archivo sea desmontado. Cuando el archivo es desmontado, el sistema llamará a PHYSFS_close(file). Si quieres que este handle survive, tendrás que envolverlo en un PHYSFS_Io y usar PHYSFS_mountIo() en lugar.

Si esta función falla, PHYSFS_close(file) no es llamado.

Parámetros

file El handle PHYSFS_File que contiene los datos del archivo.
newDir El nombre de archivo que puede representar este flujo.
mountPoint La ubicación en la árbol interpolado donde este archivo se "montará", en notación independiente de plataforma. NULL o "" es equivalente a "/".
appendToPath No cero para append a la ruta de búsqueda, cero para prepender.

Retorno

No cero si se añadió a la ruta, cero en caso de error (archivo inalcanzable, etc). Usa PHYSFS_getLastErrorCode() para obtener el error específico.

تمكين أو تعطيل تتبع الروابط الرمزية. تحتوي بعض أنظمة الملفات المادية والأرشيفات على ملفات هي مجرد مؤشرات لملفات أخرى. على نظام الملفات المادي، سيؤدي فتح مثل هذا الرابط إلى (بشكل شفاف) فتح الملف الذي يشير إليه.

بشكل افتراضي، ستتحقق PhysicsFS مما إذا كان الملف رابطًا رمزيًا بالفعل أثناء استدعاءات الفتح وتفشل إذا كان كذلك. بخلاف ذلك، يمكن أن يأخذك الرابط خارج مسارات الكتابة والبحث، ويعرض الأمان للخطر.

إذا كنت ترغب في تحمل هذه المخاطرة، استدع هذه الدالة بمعامل غير صفري. لاحظ أن هذا يتعلق أكثر بعزل بيئة لغة برمجة نصية في برنامج، في حالة محاولة البرامج النصية غير الموثوق بها اختراق النظام. بشكل عام، قد يكون لدى المستخدم سبب مشروع لإعداد رابط رمزي، لذلك ما لم تشعر بوجود خطر محدد في السماح بها، يجب عليك السماح بها.

يتم التحقق صراحة من الروابط الرمزية فقط عند التعامل مع أسماء الملفات بالتنسيق المستقل عن النظام الأساسي. أي، عند إعداد مسارات البحث والكتابة الخاصة بك، وما إلى ذلك، لا يتم فحص الروابط الرمزية أبدًا.

يرجى ملاحظة أن PHYSFS_stat() ستتحقق دائمًا من المسار المحدد؛ إذا كان هذا المسار رابطًا رمزيًا، فلن يتم تتبعه في أي حالة. إذا لم تسمح بالروابط الرمزية من خلال هذه الدالة، فسوف تتجاهلها PHYSFS_stat()، وستعامل الاستعلام كما لو كان المسار غير موجود على الإطلاق.

يمكن تمكين أو تعطيل إذن الروابط الرمزية في أي وقت بعد استدعاء PHYSFS_init()، وهي معطلة بشكل افتراضي.

تحذير

هذا أمر متقدم وصعب. لست بحاجة إليه إلا إذا كنت تعرف حقًا ما تفعله. معظم التطبيقات لن تحتاج إليه.

إذا كنت ترغب في تقديم أرشيف خاص بك (على سبيل المثال، تنسيق ملف أرشيف مخصص، أو شيء افتراضي تريد أن يبدو كنظام ملفات يمكنك الوصول إليه من خلال واجهات برمجة تطبيقات PhysicsFS المعتادة)، فهذه هي نقطة البداية. بمجرد تسجيل أرشيف بنجاح، يمكنك بعد ذلك استخدام PHYSFS_mount() لإضافة الأرشيفات التي يدعمها الأرشيف الخاص بك إلى مسار البحث، أو ربما استخدامه كدليل للكتابة. داخليًا، تستخدم PhysicsFS هذه الوظيفة لتسجيل أرشيفاتها المدمجة، مثل دعم .zip، إلخ.

بمجرد إرجاع هذه الوظيفة بنجاح، ستتمكن PhysicsFS من دعم الأرشيفات من هذا النوع حتى تقوم بإلغاء تسجيل الأرشيف مرة أخرى.

ملاحظة تحذيرية

هذه الدالة لن تبلغ عن خطأ إذا كانت هناك تسلسلات غير صالحة في مصدر UTF-8. ستقوم باستبدالها بسلسلة '؟' وتستمر.

السلاسل النصية بتنسيق UCS-4 (المعروفة أيضًا باسم UTF-32) هي 32 بت لكل حرف: wchar_t في Unix.

للتأكد من أن المخزن المؤقت الوجهة كبير بما يكفي للتحويل، يرجى تخصيص مخزن مؤقت بحجم أربعة أضعاف حجم المخزن المؤقت المصدر. يستخدم UTF-8 من 1 إلى 4 بايت لكل حرف، ولكن السلاسل النصية بتنسيق UCS-4 تستخدم دائمًا 4 بايت، لذلك ستتضاعف سلسلة ASCII المنخفضة أربع مرات!

سيتم اقتطاع السلاسل النصية التي لا تتناسب مع المخزن المؤقت الوجهة، ولكنها ستكون دائمًا منتهية بـ null ولن تحتوي أبدًا على تسلسل UCS-4 غير مكتمل في النهاية. إذا كان طول المخزن المؤقت 0، فإن هذه الدالة لا تفعل شيئًا.

مقطوع، ولكن سيتم دائمًا إنهاؤه بـ null ولن تحتوي أبدًا على تسلسل UCS-4 غير مكتمل في النهاية. إذا كان طول المخزن المؤقت 0، فلن تقوم هذه الدالة بأي شيء.

تحويل سلسلة UTF-8 إلى سلسلة UTF-16.

تحذير

لن تقوم هذه الدالة بالإبلاغ عن خطأ إذا كانت هناك تسلسلات UTF-8 غير صالحة في السلسلة المصدر. ستقوم باستبدالها بحرف '؟' وتستمر.

سلاسل UTF-16 هي 16 بت لكل حرف (باستثناء بعض الأحرف التي هي 32 بت): TCHAR على Windows، عند البناء بدعم Unicode. إصدارات Windows الحديثة تستخدم UTF-16. إصدارات Windows قبل عام 2000 استخدمت TCHAR، ولكنها تعاملت فقط مع UCS-2. UTF-16 *هو* UCS-2، باستثناء الأحرف التي هي 4 بايت، والتي لا يمكن تمثيلها في UCS-2 على الإطلاق. إذا لم تكن متأكدًا، يجب عليك استخدام UTF-16 في هذه المرحلة على Windows.

للتأكد من أن المخزن المؤقت الوجهة كبير بما يكفي للتحويل، يرجى تخصيص مخزن مؤقت بحجم ضعف حجم المخزن المؤقت المصدر. يستخدم UTF-8 من بايت واحد إلى أربعة بايتات لكل حرف، ولكن UTF-16 يستخدم دائمًا من اثنين إلى أربعة، لذا فإن سلسلة ASCII منخفضة بالكامل ستتضاعف في الحجم! الأحرف UTF-16 التي تتطلب أربعة بايتات تأخذ أيضًا أربعة بايتات في UTF-8، لذا لا تحتاج إلى تخصيص 4 أضعاف المساحة الاحتياطية: الضعف سيكون كافياً.

سيتم اقتطاع السلاسل التي لا تناسب المخزن المؤقت الوجهة، ولكن سيتم دائمًا إنهاؤها بـ null ولن تحتوي أبدًا على زوج بديل UTF-16 غير مكتمل في النهاية. إذا كان طول المخزن المؤقت 0، فلن تقوم هذه الدالة بأي شيء.
