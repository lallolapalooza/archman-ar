#define PHYSFS_file PHYSFS_File

تعريف توافق API 1.0. PHYSFS_file مطابق لـ PHYSFS_File. هذا التعريف موجود للتوافق مع الإصدارات السابقة مع اصطلاح العاصمة غير المتسق في واجهة برمجة التطبيقات 1.0 في هذه الحالة. يجب أن يستخدم التعليمات البرمجية الجديدة PHYSFS_File، حيث قد يتم إزالة هذا التعريف في يوم من الأيام.

PHYSFS_Error_Codes

Error codes for PhysicsFS.

PHYSFS_ERR_OK

No error.
PHYSFS_ERR_WRITE_DIR
No write dir has been specified.
PHYSFS_ERR_OPEN_FOR_READING
Wrote to a file opened for reading.
PHYSFS_ERR_OPEN_FOR_WRITING
Read from a file opened for writing.
PHYSFS_ERR_NOT_A_FILE

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Get a file listing of a search path's directory, using an application-defined callback, with errors reported. Internally, PHYSFS_enumerateFiles() just calls this function and then builds a list before returning to the application, so functionality is identical except for how the information is represented to the application.

Unlike PHYSFS_enumerateFiles(), this function does not return an array. Rather, it calls a function specified by the application once per element of the search path:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Items sent to the callback are not guaranteed to be in any order whatsoever. There is no sorting done at this level, and if you need that, you should probably use PHYSFS_enumerateFiles() instead, which guarantees alphabetical sorting. This form reports whatever is discovered in each archive before moving on to the next. Even within one archive, we can't guarantee what order it will discover data. Any sorting you find in these callbacks is just pure luck. Do not rely on it. As this walks the entire list of archives, you may receive duplicate filenames.

This API and the callbacks themselves are capable of reporting errors. Prior to this API, callbacks had to accept every enumerated item, even if they were only looking for a specific thing and wanted to stop after that, or had a serious error and couldn't alert anyone. Furthermore, if PhysicsFS itself had a problem (disk error or whatnot), it couldn't report it to the calling app, it would just have to skip items or stop enumerating outright, and the caller wouldn't know it had lost some data along the way.

Now the caller can be sure it got a complete data set, and its callback has control if it wants enumeration to stop early. See the documentation for PHYSFS_EnumerateCallback for details on how your callback should behave.

Parameters

dir Directory, in platform-independent notation, to enumerate.
c Callback function to notify about search path elements.
d Application-defined data passed to callback. Can be NULL.

Returns

non-zero on success, zero on failure. Use PHYSFS_getLastErrorCode() to obtain the specific error. If the callback returns PHYSFS_ENUM_STOP to stop early, this will be considered success. Callbacks returning PHYSFS_ENUM_ERROR will make this function return zero and set the error code to PHYSFS_ERR_APP_CALLBACK.

char ** PHYSFS_enumerateFiles (const char * dir)

Get a file listing of a search path's directory.

Warning

In PhysicsFS versions prior to 2.1, this function would return as many items as it could in the face of a failure condition (out of memory, disk i/o error, etc). Since this meant apps couldn't distinguish between complete success and partial failure, and since the function could always return NULL to report catastrophic failures anyway, in PhysicsFS 2.1 this function's policy changed: it will either return a list of complete results or it will return NULL for any failure of any kind, so we can guarantee that the enumeration ran to completion and has no gaps in its results.

Matching directories are interpolated. That is, if "C:\mydir" is in the search path and contains a directory "savegames" that contains "x.sav", "y.sav", and "z.sav", and there is also a "C:\userdir" in the search path that has a "savegames" subdirectory with "w.sav", then the following code:

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)

PHYSFS_freeList(rc);
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..fi

تحذير

ما لم يكن لديك حاجة خاصة منخفضة المستوى، يجب عليك استخدام PHYSFS_mount() بدلاً من هذه الدالة.

قد تكون الأرشيفات داخل الأرشيفات بطيئة جدًا! بينما يمكن لـ PHYSFS_File البحث حتى عندما تكون البيانات مضغوطة، قد تفعل ذلك عن طريق العودة إلى البداية وفك ضغط كل شيء قبل نقطة البحث. قد يؤدي الاستخدام العادي للأرشيف إلى الكثير من عمليات البحث خلف الكواليس. على هذا النحو، قد تجد أن الاستخدام العادي للأرشيف مؤلم للغاية إذا تم تحميله بهذه الطريقة. خطط وفقًا لذلك: إذا كان لديك، على سبيل المثال، ملف .zip ذاتي الاستخراج، وتريد تحميل شيء بداخله، فقم بضغط محتويات الأرشيف الداخلي وتأكد من أن ملف .zip الخارجي لا يضغط الأرشيف الداخلي أيضًا.

تعمل هذه الدالة تمامًا مثل PHYSFS_mount()، ولكنها تأخذ معرّف PHYSFS_File بدلاً من اسم مسار. يحتوي هذا المعرّف على جميع بيانات الأرشيف، ويتم استخدامه بدلاً من ملف حقيقي في نظام الملفات الفعلي. قد يستند PHYSFS_File إلى ملف حقيقي في نظام الملفات الفعلي، ولكنه ليس بالضرورة كذلك. الاستخدام الأكثر شيوعًا لهذا هو على الأرجح تحميل الأرشيفات المخزنة داخل أرشيفات أخرى.

يجب أن يكون (newDir) سلسلة فريدة لتحديد هذا الأرشيف. يتم استخدامه لتحسين اختيار الأرشفة (إذا سميته XXXXX.zip، فقد نجرب أداة ZIP أولاً، على سبيل المثال، أو نختار مباشرة أداة لا يمكنها الوثوق بصحة البيانات إلا من خلال امتداد اسم الملف). لا يلزم أن يشير إلى ملف حقيقي على الإطلاق. إذا لم يكن امتداد اسم الملف مفيدًا، فسيحاول النظام تجربة كل أداة أرشفة حتى تعمل واحدة أو لا يعمل أي منها. يجب أن يكون اسم الملف هذا فريدًا، حيث لن يسمح لك النظام بوجود أرشيفين بنفس الاسم.

يجب أن يظل (file) ساري المفعول حتى يتم إلغاء تحميل الأرشيف. عند إلغاء تحميل الأرشيف، سيستدعي النظام PHYSFS_close(file). إذا كنت بحاجة إلى بقاء هذا المعرّف، فسيتعين عليك تغليفه في PHYSFS_Io واستخدام PHYSFS_mountIo() بدلاً من ذلك.

إذا فشلت هذه الدالة، فلن يتم استدعاء PHYSFS_close(file).

هذه الدالة لن تبلغ عن خطأ إذا كانت هناك تسلسلات UTF-8 غير صالحة في السلسلة المصدر. سيتم استبدالها بحرف '؟' والمتابعة.

سلاسل UTF-16 هي 16 بت لكل حرف (باستثناء بعض الأحرف، التي تكون 32 بت): TCHAR على Windows، عند البناء مع دعم Unicode. إصدارات Windows الحديثة تستخدم UTF-16. إصدارات Windows قبل عام 2000 استخدمت TCHAR، لكنها تعاملت فقط مع UCS-2. UTF-16 هو UCS-2، باستثناء الأحرف التي تبلغ 4 بايت، والتي لا يمكن تمثيلها في UCS-2 على الإطلاق. إذا لم تكن متأكدًا، يجب أن تستخدم UTF-16 في هذه المرحلة على Windows.

للتأكد من أن المخزن المؤقت الوجهة كبير بما يكفي للتحويل، يرجى تخصيص مخزن مؤقت بحجم ضعف حجم المخزن المؤقت المصدر. يستخدم UTF-8 من بايت واحد إلى أربعة بايتات لكل حرف، ولكن UTF-16 يستخدم دائمًا من اثنين إلى أربعة، لذا فإن سلسلة ASCII منخفضة بالكامل ستتضاعف في الحجم! أحرف UTF-16 التي تتطلب أربعة بايتات تتطلب أيضًا أربعة بايتات في UTF-8، لذلك لا تحتاج إلى تخصيص مساحة 4x فقط في حالة، الضعف يكفي.

سيتم اقتطاع السلاسل التي لا تتناسب مع المخزن المؤقت الوجهة، ولكنها ستكون دائمًا منتهية بصفرية ولن يكون لديها زوج بديل UTF-16 غير مكتمل في النهاية. إذا كان طول المخزن المؤقت 0، فلن تقوم هذه الدالة بأي شيء.

مهمل

اعتبارًا من PhysicsFS 2.1، استخدم PHYSFS_writeBytes() بدلاً من ذلك. هذه الدالة تقوم فقط بتغليفها على أي حال. هذه الدالة لم توضح أبدًا ما سيحدث إذا تمكنت من كتابة كائن جزئي، لذا فإن العمل على مستوى البايت يجعل هذا الأمر أوضح للجميع، خاصة الآن بعد أن يمكن توفير واجهات PHYSFS_Io بواسطة التطبيق.

objCount عدد الكائنات (objSize) للكتابة إليها (المقبض).

كتابة بيانات إلى مقبض ملف PhysicsFS. يجب فتح الملف للكتابة.

يرجى ملاحظة أنه بينما (len) هو عدد صحيح غير موقع 64 بت، فأنت مقيد بـ 63 بت (9223372036854775807 بايت)، لذلك يمكننا إرجاع قيمة سالبة عند الخطأ. إذا كان الطول أكبر من 0x7FFFFFFFFFFFFFFF، فستفشل هذه الدالة على الفور. بالنسبة للأنظمة التي لا تحتوي على نوع بيانات 64 بت، فأنت مقيد بـ 31 بت (0x7FFFFFFF، أو 2147483647 بايت). نحن نثق بأن معظم الأشياء لن تحتاج إلى إجراء عمليات إدخال/إخراج متعددة الجيجابايت في استدعاء واحد على أي حال، ولكن لماذا نقيد الأشياء؟

المعلمات

handle القيمة المرتجعة من PHYSFS_openWrite() أو PHYSFS_openAppend().
buffer المخزن المؤقت لـ (len) بايت للكتابة إليه (المقبض).
len عدد البايتات التي يتم كتابتها إلى (المقبض).

القيم المرتجعة

عدد البايتات المكتوبة. قد يكون هذا أقل من (len)؛ في حالة حدوث خطأ، قد يحاول النظام كتابة أكبر عدد ممكن من البايتات، لذلك قد يحدث كتابة غير مكتملة. PHYSFS_getLastErrorCode() يمكن أن تلقي الضوء على سبب كون هذا الرقم أقل من (len). -1 في حالة فشل كامل.
