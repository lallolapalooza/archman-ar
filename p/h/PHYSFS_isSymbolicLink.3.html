توقيع دالة للوظائف التي تقوم بتعداد الملفات.

تحذير

منذ PhysicsFS 2.1، استخدم PHYSFS_EnumerateCallback مع PHYSFS_enumerate() للحصول على مزيد من التحكم في العملية.

تُستخدم هذه الإدخالات للإبلاغ عن قائمة بإدخالات الدليل إلى مستدعي أصلي، إدخال واحد لكل دالة استدعاء. جميع السلاسل النصية مرمزة بـ UTF-8. لا ينبغي للدوال محاولة تعديل أو تحرير ذاكرة السلاسل النصية.

تُستخدم دوال الاستدعاء هذه، منذ PhysicsFS 1.1، كبديل للدوال التي تُرجع قوائم تحتاج إلى تنظيف باستخدام PHYSFS_freeList(). تعني دالة الاستدعاء أن المكتبة لا تحتاج إلى تخصيص قائمة كاملة وجميع السلاسل النصية مسبقًا.

لاحظ أن الترتيب المضمون في إصدارات القائمة لا يتم بالضرورة الوفاء به في إصدارات دوال الاستدعاء. تحقق من الوثائق الخاصة بواجهات برمجة التطبيقات، ولكن قد لا يتم ترتيب السلاسل النصية بالترتيب المتوقع وقد تحصل على سلاسل نصية مكررة.

المعلمات

data مؤشر بيانات مخصص، تم تمريره بواسطة واجهة برمجة التطبيقات التي استدعت دالة الاستدعاء في النهاية.
origdir سلسلة نصية تحتوي على المسار الكامل، بتدوين مستقل عن النظام الأساسي، للدليل الذي يحتوي على هذا الملف. في معظم الحالات، هو الدليل الذي طلبت التعداد منه، وتم تمريره في دالة الاستدعاء للراحة.
fname اسم الملف الذي يتم تعداده. قد لا يتم ترتيبه أبجديًا مقارنة بدوال الاستدعاء الأخرى التي تم تشغيلها ولن يحتوي على المسار الكامل. يمكن إعادة إنشائه باستخدام $origdir/$fname ... قد يكون الملف دليلًا فرعيًا، أو ملفًا، أو رابطًا رمزيًا، إلخ.

العودة

قيمة من PHYSFS_EnumerateCallbackResult. جميع القيم الأخرى غير محددة (حاليًا)؛ لا تستخدمها.

قيم تمثل أسبابًا محددة للفشل. في معظم الأحيان، يجب أن تهتم فقط بما إذا كانت العملية قد فشلت أم لا، ولكن قد تكون هناك أوقات تخطط فيها للتعامل مع حالة خطأ محددة بلطف، ولهذا السبب نقدم رموز خطأ محددة.

معظم هذه الأخطاء غامضة بعض الشيء وليست أشياء يمكنك إصلاحها... إذا كان هناك خطأ في الأذونات، على سبيل المثال، فما يمكنك فعله هو تمرير تلك المعلومات إلى المستخدمين والسماح لهم بمعرفة كيفية التعامل معها. في معظم هذه الحالات، يجب أن يهتم برنامجك فقط بفشله في تحقيق أهدافه، وليس بالضرورة سبب فشله.

int PHYSFS_deinit (void )

Deinitialize the PhysicsFS library. This closes any files opened via PhysicsFS, blanks the search/write paths, frees memory, and invalidates all of your file handles.

Note that this call can FAIL if there's a file open for writing that refuses to close (for example, the underlying operating system was buffering writes to network filesystem, and the fileserver has crashed, or a hard drive has failed, etc). It is usually best to close all write handles yourself before calling this function, so that you can gracefully handle a specific failure.

Once successfully deinitialized, PHYSFS_init() can be called again to restart the subsystem. All default API states are restored at this point, with the exception of any custom allocator you might have specified, which survives between initializations.

int PHYSFS_delete (const char * filename)

Delete a file or directory. (filename) is specified in platform-independent notation in relation to the write dir.

A directory must be empty before this call can delete it.

Deleting a symlink will remove the link, not what it points to, regardless of whether you "permitSymLinks" or not.

So if you've got the write dir set to "C:\mygame\writedir" and call PHYSFS_delete("downloads/maps/level1.map") then the file "C:\mygame\writedir\downloads\maps\level1.map" is removed from the physical filesystem, if it exists and the operating system permits the deletion.

Note that on Unix systems, deleting a file may be successful, but the actual file won't be removed until all processes that have an open filehandle to it (including your program) close their handles.

Chances are, the bits that make up the file still exist, they are just made available to be written over at a later point. Don't consider this a security method or anything. :)
