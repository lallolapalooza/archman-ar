PHYSFS_enumerate

هذا هو نفس الشيء مثل PHYSFS_EnumFilesCallback من PhysicsFS 2.0، باستثناء أنه يمكنه إرجاع نتيجة من المكالمة: على وجه التحديد: إذا كنت تبحث عن شيء معين، بمجرد العثور عليه، يمكنك إخبار PhysicsFS بالتوقف عن تعداد المزيد. يتم استخدام هذا مع PHYSFS_enumerate()، والذي نأمل أن نكون قد أحسننا استخدامه هذه المرة. :)

المعلمات

data مؤشر بيانات معرف من قبل المستخدم، يتم تمريره من واجهة برمجة التطبيقات التي استدعت المكالمة في النهاية.
origdir سلسلة نصية تحتوي على المسار الكامل، بتنسيق مستقل عن النظام الأساسي، للدليل الذي يحتوي على هذا الملف. في معظم الحالات، هذا هو الدليل الذي طلبت تعداد محتوياته، ويتم تمريره في المكالمة لراحتك.
fname اسم الملف الذي يتم تعداد محتوياته. قد لا يكون مرتبًا أبجديًا مقارنة بالمكالمات الأخرى التي تم تشغيلها، ولن يحتوي على المسار الكامل. يمكنك إعادة بناء المسار الكامل باستخدام $origdir/$fname ... يمكن أن يكون الملف دليلًا فرعيًا، أو ملفًا، أو رابطًا رمزيًا، وما إلى ذلك.

القيمة المعادة

قيمة من PHYSFS_EnumerateCallbackResult. جميع القيم الأخرى غير محددة (حاليًا)؛ لا تستخدمها.

تحذير

اعتبارًا من PhysicsFS 2.1، استخدم PHYSFS_EnumerateCallback مع PHYSFS_enumerate() بدلاً من ذلك؛ حيث يمنحك مزيدًا من التحكم في العملية.

تُستخدم هذه لتقديم قائمة بمدخلات الدليل إلى المتصل الأصلي، ملف/دليل/رابط رمزي واحد لكل مكالمة. جميع السلاسل النصية مشفرة بـ UTF-8. يجب ألا تحاول الدوال تعديل أو تحرير ذاكرة أي سلسلة نصية.

تُستخدم هذه المكالمات، بدءًا من PhysicsFS 1.1، كبديل للدوال التي كانت ترجع قوائم تحتاج إلى تنظيف باستخدام PHYSFS_freeList(). تعني المكالمة أن المكتبة لا تحتاج إلى تخصيص قائمة كاملة وجميع السلاسل النصية مسبقًا.

كن على علم بأن ترتيب البيانات الموعود به في إصدارات القائمة ليس ضروريًا في إصدارات المكالمات. تحقق من التوثيق الخاص بواجهات برمجة التطبيقات المحددة، فقد لا تكون السلاسل النصية مرتبة كما تتوقع وقد تحصل على سلاسل نصية مكررة.

تحذير

اعتبارًا من PhysicsFS 2.1، تم إضعاف هذه الوظيفة. قبل PhysicsFS 2.1، كانت هذه الوظيفة هي الطريقة الوحيدة للحصول على تفاصيل الخطأ تتجاوز القيمة الأساسية التي تعود بها وظيفة معينة. كان من المفترض أن تكون هذه سلسلة نصية قابلة للقراءة للبشر بواحدة من عدة لغات، ولم تكن مفيدة لتحليل التطبيقات. كان هذا مشكلة، لأن المطور وليس المستخدم هو من اختار اللغة وقت الترجمة، وكان على صائني PhysicsFS (بشكل سيء) الحفاظ على كمية كبيرة من أعمال الترجمة. لم يتمكن التطبيق من تحليل السلاسل، حتى لو اعتمد على لغة معينة، لأن بعضها تم إنشاؤه ديناميكيًا. في الإصدار 2.1 وما بعده، تعود هذه الوظيفة دائمًا بسلسلة ثابتة باللغة الإنجليزية؛ يمكنك استخدامها كمفتاح لسلاسل الترجمة الخاصة بك إذا أردت، حيث أننا سنعد بعدم تغيير سلاسل الأخطاء الحالية. أيضًا، إذا كان تطبيقك يرغب في النظر إلى أخطاء معينة، فإننا نقدم الآن خيارًا أفضل: استخدم PHYSFS_getLastErrorCode() بدلاً من ذلك.

int PHYSFS_getLastErrorCode (void)

Get the last error code that was reported. This is useful for debugging and for handling errors in a more granular fashion.

This function returns an enumeration value that corresponds to the last error that occurred within the PhysicsFS library. It's important to note that different functions within PhysicsFS might reset the same thread-specific error state. Calling one will wipe out the other's data. If you need both, call PHYSFS_getLastErrorCode(), then pass that value to PHYSFS_getErrorByCode().

Generally, applications should only concern themselves with whether a given function failed; however, if you require more specifics, you can try this function to glean information, if there's some specific problem you're expecting and plan to handle. But with most things that involve file systems, the best course of action is usually to give up, report the problem to the user, and let them figure out what should be done about it. For that, you might prefer PHYSFS_getErrorByCode() instead.

Returns

Enumeration value that represents last reported error.

const char * PHYSFS_getPrefDir (const char * org, const char * app)

Get the user-and-app-specific path where files can be written. Helper function.

Get the "pref dir". This is meant to be where users can write personal files (preferences and save games, etc) that are specific to your application. This directory is unique per user, per application.

This function will decide the appropriate location in the native filesystem, create the directory if necessary, and return a string in platform-dependent notation, suitable for passing to PHYSFS_setWriteDir().

On Windows, this might look like: "C:\\Users\\bob\\AppData\\Roaming\\My Company\\My Program Name"

On Linux, this might look like: "/home/bob/.local/share/My Program Name"

On Mac OS X, this might look like: "/Users/bob/Library/Application Support/My Program Name"

(etc.)

You should probably use the pref dir for your write dir, and also put it near the beginning of your search path. Older versions of PhysicsFS offered only PHYSFS_getUserDir() and left you to figure out where the files should go under that tree. This finds the correct location for whatever platform, which not only changes between operating systems, but also versions of the same operating system.

You specify the name of your organization (if it's not a real organization, your name or an Internet domain you own might do) and the name of your application. These should be proper names.

Both the (org) and (app) strings may become part of a directory name, so please follow these rules:

  • Try to use the same org string (including case-sensitivity) for all your applications that use this function.
  • Always use a unique app string for each one, and make sure it never changes for an app once you've decided on it.
  • Unicode characters are legal, as long as it's UTF-8 encoded, but...
  • ...only use letters, numbers, and spaces. Avoid punctuation like "Game Name 2: Bad Guy's Revenge!" ... "Game Name 2" is sufficient.

The pointer returned by this function remains valid until you call this function again, or call PHYSFS_deinit(). This is not necessarily a fast call, though, so you should call this once at startup and copy the string if you need it.

You should assume the path returned by this function is the only safe place to write files (and that PHYSFS_getUserDir() and PHYSFS_getBaseDir(), while they might be writable, or even parents of the returned path, aren't where you should be writing things).
