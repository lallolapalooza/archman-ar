MACRO DEFINITION DOCUMENTATION

#define PHYSFS_file PHYSFS_File

1.0 API compatibility define. PHYSFS_file is identical to PHYSFS_File. This #define is here for backwards compatibility with the 1.0 API, which had an inconsistent capitalization convention in this case. New code should use PHYSFS_File, as this #define may go away someday.

#define PHYSFS_VERSION( x)

Value:

{ \
    (x)->major = PHYSFS_VER_MAJOR; \
    (x)->minor = PHYSFS_VER_MINOR; \
    (x)->patch = PHYSFS_VER_PATCH; \
}

Macro to determine PhysicsFS version program was compiled against. This macro fills in a PHYSFS_Version struct

مع الإصدار الذي قمت بتجميعه مقابله. يتم تحديد ذلك من خلال أي رأس يستخدمه المترجم. لاحظ أنه إذا قمت بربط المكتبة ديناميكيًا، فقد يكون لديك إصدار أحدث قليلاً أو أقدم في وقت التشغيل. يمكن تحديد هذا الإصدار باستخدام PHYSFS_getLinkedVersion()، والذي، على عكس PHYSFS_VERSION، ليس ماكرو.

تحدد هذه القيم ما إذا كان يجب أن تستمر الدالة الاستدعائية للإدراج في العمل، أو تتوقف (ولماذا تتوقف).

انظر أيضًا

PHYSFS_EnumerateCallback

PHYSFS_enumerate

هذا هو نفس الشيء مثل PHYSFS_EnumFilesCallback من PhysicsFS 2.0، باستثناء أنه يمكنه إرجاع نتيجة من الدالة الاستدعائية: على وجه التحديد: إذا كنت تبحث عن شيء معين، بمجرد العثور عليه، يمكنك إخبار PhysicsFS بالتوقف عن الإدراج بشكل أكبر. يتم استخدام هذا مع PHYSFS_enumerate()، والتي نأمل أن نكون قد قمنا بها بشكل صحيح هذه المرة. :)

المعلمات

data مؤشر بيانات محدد من قبل المستخدم، تم تمريره من واجهة برمجة التطبيقات التي استدعت الدالة الاستدعائية في النهاية.
origdir سلسلة تحتوي على المسار الكامل، بتدوين مستقل عن النظام الأساسي، للدليل الذي يحتوي على هذا الملف. في معظم الحالات، هذا هو الدليل الذي طلبت منه الإدراج، تم تمريره في الدالة الاستدعائية لراحتك.
fname اسم الملف الذي يتم إدراجه. قد لا يكون بترتيب أبجدي مقارنة بالدوال الاستدعائية الأخرى التي تم تشغيلها، ولن يحتوي على المسار الكامل. يمكنك إعادة إنشاء المسار الكامل باستخدام $origdir/$fname ... يمكن أن يكون الملف دليلاً فرعيًا، أو ملفًا، أو رابطًا رمزيًا، وما إلى ذلك.

القيمة المعادة

قيمة من PHYSFS_EnumerateCallbackResult. جميع القيم الأخرى (حاليًا) غير محددة؛ لا تستخدمها.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Get a file listing of a search path's directory, using an application-defined callback, with errors reported. Internally, PHYSFS_enumerateFiles() just calls this function and then builds a list before returning to the application, so functionality is identical except for how the information is represented to the application.

Unlike PHYSFS_enumerateFiles(), this function does not return an array. Rather, it calls a function specified by the application once per element of the search path: 

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Items sent to the callback are not guaranteed to be in any order whatsoever. There is no sorting done at this level, and if you need that, you should probably use PHYSFS_enumerateFiles() instead, which guarantees alphabetical sorting. This form reports whatever is discovered in each archive before moving on to the next. Even within one archive, we can't guarantee what order it will discover data. Any sorting you find in these callbacks is just pure luck. Do not rely on it. As this walks the entire list of archives, you may receive duplicate filenames.

This API and the callbacks themselves are capable of reporting errors. Prior to this API, callbacks had to accept every enumerated item, even if they were only looking for a specific thing and wanted to stop after that, or had a serious error and couldn't alert anyone. Furthermore, if PhysicsFS itself had a problem (disk error or whatnot), it couldn't report it to the calling app, it would just have to skip items or stop enumerating outright, and the caller wouldn't know it had lost some data along the way.

Now the caller can be sure it got a complete data set, and its callback has control if it wants enumeration to stop early. See the documentation for PHYSFS_EnumerateCallback for details on how your callback should behave.

Parameters

dir Directory, in platform-independent notation, to enumerate.
c Callback function to notify about search path elements.
d Application-defined data passed to callback. Can be NULL.

Returns

non-zero on success, zero on failure. Use PHYSFS_getLastErrorCode() to obtain the specific error. If the callback returns PHYSFS_ENUM_STOP to stop early, this will be considered success. Callbacks returning PHYSFS_ENUM_ERROR will make this function return zero and set the error code to PHYSFS_ERR_APP_CALLBACK.

const char * PHYSFS_getPrefDir (const char * org, const char * app)

Get the user-and-app-specific path where files can be written. Helper function.

Get the "pref dir". This is meant to be where users can write personal files (preferences and save games, etc) that are specific to your application. This directory is unique per user, per application.

This function will decide the appropriate location in the native filesystem, create the directory if necessary, and return a string in platform-dependent notation, suitable for passing to PHYSFS_setWriteDir().

On Windows, this might look like: "C:\\Users\\bob\\AppData\\Roaming\\My Company\\My Program Name"

On Linux, this might look like: "/home/bob/.local/share/My Program Name"

On Mac OS X, this might look like: "/Users/bob/Library/Application Support/My Program Name"

(etc.)

You should probably use the pref dir for your write dir, and also put it near the beginning of your search path. Older versions of PhysicsFS offered only PHYSFS_getUserDir() and left you to figure out where the files should go under that tree. This finds the correct location for whatever platform, which not only changes between operating systems, but also versions of the same operating system.

You specify the name of your organization (if it's not a real organization, your name or an Internet domain you own might do) and the name of your application. These should be proper names.

Both the (org) and (app) strings may become part of a directory name, so please follow these rules:

  • Try to use the same org string (including case-sensitivity) for all your applications that use this function.
  • Always use a unique app string for each one, and make sure it never changes for an app once you've decided on it.
  • Unicode characters are legal, as long as it's UTF-8 encoded, but...
  • ...only use letters, numbers, and spaces. Avoid punctuation like "Game Name 2: Bad Guy's Revenge!" ... "Game Name 2" is sufficient.

The pointer returned by this function remains valid until you call this function again, or call PHYSFS_deinit(). This is not necessarily a fast call, though, so you should call this once at startup and copy the string if you need it.

You should assume the path returned by this function is the only safe place to write files (and that PHYSFS_getUserDir() and PHYSFS_getBaseDir(), while they might be writable, or even parents of the returned path, aren't where you should be writing things).

const char * PHYSFS_getRealDir (const char * filename)

Figure out where in the search path a file resides. The file is specified in platform-independent notation. The returned filename will be the element of the search path where the file was found, which may be a directory, or an archive. Even if there are multiple matches in different parts of the search path, only the first one found is used, just like when opening a file.

So, if you look for "maps/level1.map", and C:\mygame is in your search path and C:\mygame\maps\level1.map exists, then "C:\mygame" is returned.

If a any part of a match is a symbolic link, and you've not explicitly permitted symlinks, then it will be ignored, and the search for a match will continue.

int PHYSFS_registerArchiver (const PHYSFS_Archiver * archiver)

إضافة برنامج أرشيف جديد إلى النظام.

تحذير

هذا للوظائف المتقدمة والأساسية. لا تحتاج إليها ما لم تكن تعرف حقًا ما تفعله. معظم التطبيقات لن تحتاج إليها.

إذا كنت ترغب في توفير برنامج أرشيف خاص بك (على سبيل المثال، تنسيق ملف أرشيف مخصص، أو شيء افتراضي تريد أن يبدو كنظام ملفات يمكنك الوصول إليه من خلال واجهات برمجة تطبيقات PhysicsFS العادية)، فهذا هو المكان الذي تبدأ منه. بمجرد تسجيل برنامج الأرشيف بنجاح، يمكنك بعد ذلك استخدام PHYSFS_mount() لإضافة الأرشيفات التي يدعمها برنامج الأرشيف الخاص بك إلى مسار البحث، أو ربما استخدامه كدليل للكتابة. داخليًا، تستخدم PhysicsFS هذه الوظيفة لتسجيل برامج الأرشيف المدمجة الخاصة بها، مثل دعم .zip، إلخ.

لا يمكنك أن يكون لديك برنامجي أرشيف يتعاملان مع نفس الامتداد. إذا كان لديك تعارض، يمكنك إلغاء تسجيل برنامج الأرشيف الآخر (بما في ذلك المدمج) باستخدام PHYSFS_deregisterArchiver().

سيتم نسخ البيانات الموجودة في (archiver)؛ يمكنك تحرير هذا المؤشر عند عودة هذه الوظيفة.

بمجرد أن تعود هذه الوظيفة بنجاح، ستتمكن PhysicsFS من دعم الأرشيفات من هذا النوع حتى تقوم بإلغاء تسجيل برنامج الأرشيف مرة أخرى.

void PHYSFS_utf8ToUtf16 (const char * src, PHYSFS_uint16 *dst, PHYSFS_uint64 len)

تحويل سلسلة نصية UTF-8 إلى سلسلة نصية UTF-16.

تحذير

لن تقوم هذه الوظيفة بالإبلاغ عن خطأ إذا كانت هناك تسلسلات UTF-8 غير صالحة في السلسلة المصدر. ستقوم باستبدالها بحرف '؟' وتستمر.

السلاسل النصية UTF-16 هي 16 بت لكل حرف (باستثناء بعض الأحرف التي تكون 32 بت): TCHAR على Windows، عند البناء بدعم Unicode. إصدارات Windows الحديثة تستخدم UTF-16. إصدارات Windows قبل عام 2000 استخدمت TCHAR، ولكنها تعاملت فقط مع UCS-2. UTF-16 هو UCS-2، باستثناء الأحرف التي تتكون من 4 بايت، والتي لا يمكن تمثيلها في UCS-2 على الإطلاق. إذا لم تكن متأكدًا، فيجب عليك استخدام UTF-16 في هذه المرحلة على Windows.

لضمان أن يكون المخزن المؤقت الوجهة كبيرًا بما يكفي للتحويل، يرجى تخصيص مخزن مؤقت بحجم ضعف حجم المخزن المؤقت المصدر. يستخدم UTF-8 من بايت واحد إلى أربعة بايتات لكل حرف، ولكن UTF-16 يستخدم دائمًا من اثنين إلى أربعة، لذا فإن سلسلة ASCII منخفضة بالكامل ستتضاعف في الحجم! الأحرف UTF-16 التي تتطلب أربعة بايتات تأخذ أيضًا أربعة بايتات في UTF-8، لذلك لا تحتاج إلى تخصيص مساحة 4x في حال حدوث ذلك: ضعف الحجم يكفي.

سيتم اقتطاع السلاسل النصية التي لا تتناسب مع المخزن المؤقت الوجهة، ولكنها ستكون دائمًا منتهية بـ null ولن تحتوي أبدًا على زوج بديل UTF-16 غير مكتمل في النهاية. إذا كان طول المخزن المؤقت 0، فلن تفعل هذه الوظيفة شيئًا.

المعلمات

src سلسلة مصدر منتهية بـ null بتنسيق UTF-8.
dst المخزن المؤقت لتخزين سلسلة UTF-16 المحولة.
len الحجم، بالبايت، للمخزن المؤقت الوجهة.
