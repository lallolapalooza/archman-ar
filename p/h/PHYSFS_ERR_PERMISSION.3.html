The version of the library you compiled against. This is determined by what header the compiler uses. Note that if you dynamically linked the library, you might have a slightly newer or older version at runtime. typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Function signature for callbacks that enumerate files.

Warning

As of PhysicsFS 2.1, Use PHYSFS_EnumerateCallback with PHYSFS_enumerate() instead; it gives you more control over the process.

These are used to report a list of directory entries to an original caller, one file/dir/symlink per callback. All strings are UTF-8 encoded. Functions should not try to modify or free any string's memory.

These callbacks are used, starting in PhysicsFS 1.1, as an alternative to functions that would return lists that need to be cleaned up with PHYSFS_freeList(). The callback means that the library doesn't need to allocate an entire list and all the strings up front.

Be aware that promised data ordering in the list versions are not necessarily so in the callback versions. Check the documentation on specific APIs, but strings may not be sorted as you expect and you might get duplicate strings.

data User-defined data pointer, passed through from the API that eventually called the callback.
origdir A string containing the full path, in platform-independent notation, of the directory containing this file. In most cases, this is the directory on which you requested enumeration, passed in the callback for your convenience.
fname The filename that is being enumerated. It may not be in alphabetical order compared to other callbacks that have fired, and it will not contain the full path. You can recreate the fullpath with $origdir/$fname ... The file can be a subdirectory, a file, a symlink, etc.

enum PHYSFS_ErrorCode

Values that represent specific causes of failure. Most of the time, you should only concern yourself with whether a given operation failed or not, but there may be occasions where you plan to handle a specific failure case gracefully, so we provide specific error codes.

Most of these errors are a little vague, and most aren't things you can fix...if there's a permission error, for example, all you can really do is pass that information on to the user and let them figure out how to handle it. In most these cases, your program should only care that it failed to accomplish its goals, and not care specifically why.

إلغاء تهيئة مكتبة PhysicsFS. يقوم هذا بإغلاق أي ملفات تم فتحها عبر PhysicsFS، ويقوم بمسح مسارات البحث/الكتابة، ويحرر الذاكرة، ويبطل جميع مقابض الملفات الخاصة بك.

لاحظ أن هذه المكالمة يمكن أن تفشل إذا كان هناك ملف مفتوح للكتابة يرفض الإغلاق (على سبيل المثال، كان نظام التشغيل الأساسي يقوم بتخزين مؤقت للكتابات إلى نظام ملفات شبكة، وتعطل خادم الملفات، أو فشل القرص الصلب، إلخ). عادةً ما يكون من الأفضل إغلاق جميع مقابض الكتابة بنفسك قبل استدعاء هذه الوظيفة، حتى تتمكن من التعامل مع فشل معين بلطف.

بمجرد إلغاء تهيئته بنجاح، يمكن استدعاء PHYSFS_init() مرة أخرى لإعادة تشغيل النظام الفرعي. يتم استعادة جميع حالات الواجهة الافتراضية في هذه النقطة، باستثناء أي مخصص تخصيص قد تكون حددته، والذي يبقى بين التهيئة.

Add an archive, contained in a PHYSFS_File handle, to the search path.

Warning

Unless you have some special, low-level need, you should be using PHYSFS_mount() instead of this.

Archives-in-archives may be very slow! While a PHYSFS_File can seek even when the data is compressed, it may do so by rewinding to the start and decompressing everything before the seek point. Normal archive usage may do a lot of seeking behind the scenes. As such, you might find normal archive usage extremely painful if mounted this way. Plan accordingly: if you, say, have a self-extracting .zip file, and want to mount something in it, compress the contents of the inner archive and make sure the outer .zip file doesn't compress the inner archive too.

This function operates just like PHYSFS_mount(), but takes a PHYSFS_File handle instead of a pathname. This handle contains all the data of the archive, and is used instead of a real file in the physical filesystem. The PHYSFS_File may be backed by a real file in the physical filesystem, but isn't necessarily. The most popular use for this is likely to mount archives stored inside other archives.

افتراضيًا، ستتحقق PhysicsFS مما إذا كان الملف رابطًا رمزيًا بالفعل أثناء استدعاءات الفتح وتفشل إذا كان كذلك. بخلاف ذلك، يمكن أن يأخذك الرابط خارج مسارات الكتابة والبحث، ويعرض الأمان للخطر.

إذا كنت ترغب في تحمل هذا الخطر، فاتصل بهذه الوظيفة بمعامل غير صفري. لاحظ أن هذا يتعلق أكثر بصندوق رمل لغة برمجة النص لبرنامج، في حالة محاولة البرامج النصية غير الموثوق بها تعريض النظام للخطر. بشكل عام، قد يكون لدى المستخدم سبب مشروع لإعداد رابط رمزي، لذلك ما لم تشعر بوجود خطر معين في السماح لهم، يجب عليك السماح لهم.

يتم التحقق من الروابط الرمزية بشكل صريح فقط عند التعامل مع أسماء الملفات بالترميز المستقل عن النظام الأساسي. وهذا يعني، عند إعداد مسارات البحث والكتابة الخاصة بك، وما إلى ذلك، لا يتم التحقق من الروابط الرمزية أبدًا.

يرجى ملاحظة أن PHYSFS_stat() سيتحقق دائمًا من المسار المحدد؛ إذا كان هذا المسار رابطًا رمزيًا، فلن يتم اتباعه في أي حال. إذا لم تكن الروابط الرمزية مسموحًا بها من خلال هذه الوظيفة، فإن PHYSFS_stat() يتجاهلها، وسيعامل الاستعلام كما لو كان المسار غير موجود على الإطلاق.

يمكن تمكين أو تعطيل إذن الرابط الرمزي في أي وقت بعد استدعاء PHYSFS_init()، وهو معطل افتراضيًا.

تحذير

هذا أمر متقدم وصعب. أنت لا تحتاجه إلا إذا كنت تعرف حقًا ما تفعله. معظم التطبيقات لن تحتاج إليه.

اجعل دليلًا فرعيًا لأرشيف ما هو دليله الجذر. هذا يسمح لك بتضييق الملفات القابلة للوصول في أرشيف معين. على سبيل المثال، إذا كان لديك x.zip مع ملف في y/z.txt، تم تحميله إلى /a، إذا قمت باستدعاء PHYSFS_setRoot("x.zip", "/y")، فسيؤدي استدعاء PHYSFS_openRead("/a/z.txt") إلى النجاح.

يمكنك تغيير جذر الأرشيف في أي وقت، وتغيير شجرة الملفات المستنبطة (اعتمادًا على مكان تحول المسارات، قد يوفر أرشيف مختلف ملفات مختلفة). إذا قمت بتعيين الجذر إلى NULL أو "/"، فسيتم التعامل مع الأرشيف كما لو لم يتم تعيين جذر خاص (كما لو تم تحميل الأرشيف بشكل طبيعي).
