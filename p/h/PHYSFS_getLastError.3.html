توثيق تعريفات الماكرو

#define PHYSFS_file PHYSFS_File

تعريف توافق واجهة برمجة التطبيقات 1.0. PHYSFS_file مطابق لـ PHYSFS_File. هذا #define موجود هنا للتوافق مع الإصدارات السابقة مع واجهة برمجة التطبيقات 1.0، التي كانت لديها اصطلاح كتابة بحروف كبيرة غير متسق في هذه الحالة. يجب أن تستخدم الشيفرة الجديدة PHYSFS_File، لأن هذا #define قد يزول يومًا ما.

احصل على قائمة ملفات دليل في مسار البحث، باستخدام دالة رد نداء يحددها التطبيق، مع الإبلاغ عن الأخطاء. داخليًا، PHYSFS_enumerateFiles() تستدعي هذه الدالة فقط ثم تبني قائمة قبل العودة إلى التطبيق، لذا فإن الوظائف متطابقة باستثناء كيفية تمثيل المعلومات للتطبيق.

على عكس PHYSFS_enumerateFiles()، لا تُرجع هذه الدالة مصفوفة. بدلاً من ذلك، تستدعي دالة يحددها التطبيق مرة واحدة لكل عنصر من مسار البحث:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

العناصر المرسلة إلى رد النداء غير مضمونة أن تكون بأي ترتيب على الإطلاق. لا يوجد فرز يتم على هذا المستوى، وإذا كنت بحاجة إلى ذلك، فمن المحتمل أن تستخدم PHYSFS_enumerateFiles() بدلاً من ذلك، والتي تضمن الفرز الأبجدي. هذا الشكل يبلّغ عن كل ما يتم اكتشافه في كل أرشيف قبل الانتقال إلى التالي. حتى داخل أرشيف واحد، لا يمكننا ضمان الترتيب الذي سيكتشف به البيانات. أي فرز تجده في ردود النداء هذه هو مجرد حظ محض. لا تعتمد عليه. نظرًا لأن هذا يتنقل عبر القائمة الكاملة للأرشيفات، فقد تتلقى أسماء ملفات مكررة.

واجهة البرمجة هذه وردود النداء نفسها قادرة على الإبلاغ عن الأخطاء. قبل واجهة البرمجة هذه، كان على ردود النداء قبول كل عنصر مُعدَّد، حتى لو كانت تبحث فقط عن شيء محدد وأرادت التوقف بعد ذلك، أو واجهت خطأً جسيمًا ولم تستطع تنبيه أي شخص. علاوة على ذلك، إذا واجهت PhysicsFS نفسها مشكلة (خطأ في القرص أو ما شابه)، لم تستطع الإبلاغ عنها للتطبيق المستدعي، كان عليها فقط تخطي العناصر أو إيقاف التعداد تمامًا، ولن يعرف المستدعي أنها فقدت بعض البيانات على طول الطريق.

الآن يمكن للمستدعي التأكد من حصوله على مجموعة بيانات كاملة، و رد النداء الخاص به لديه التحكم إذا أراد أن يتوقف التعداد مبكرًا. راجع الوثائق الخاصة بـ PHYSFS_EnumerateCallback للحصول على تفاصيل حول كيفية تصرف رد النداء الخاص بك.

تحذير

في إصدارات PhysicsFS قبل 2.1، كانت هذه الدالة تُرجع أكبر عدد ممكن من العناصر في مواجهة حالة فشل (نفاد الذاكرة، خطأ إدخال/إخراج القرص، إلخ). نظرًا لأن هذا يعني أن التطبيقات لا تستطيع التمييز بين النجاح الكامل والفشل الجزئي، ونظرًا لأن الدالة يمكنها دائمًا إرجاع NULL للإبلاغ عن حالات فشل كارثية على أي حال، في PhysicsFS 2.1 تغيرت سياسة هذه الدالة: ستُرجع إما قائمة نتائج كاملة أو ستُرجع NULL لأي فشل من أي نوع، حتى نتمكن من ضمان أن التعداد اكتمل وليس به فجوات في نتائجه.

يتم دمج الأدلة المتطابقة. أي، إذا كان "C:\mydir" في مسار البحث ويحتوي على دليل "savegames" يحتوي على "x.sav"، "y.sav"، و "z.sav"، وهناك أيضًا "C:\userdir" في مسار البحث يحتوي على دليل فرعي "savegames" به "w.sav"، فإن الكود التالي:

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);
PHYSFS_freeList(rc);
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..fi
لا تتردد في فرز القائمة كما تشاء. ومع ذلك، فإن البيانات المُرجعة ستحتوي دائمًا على عدم وجود تكرارات، وستُفرز دائمًا بترتيب أبجدي (بل: يونيكود حساس لحالة الأحرف) نيابة عنك.
لا تنسَ استدعاء PHYSFS_freeList() مع القيمة المُرجعة من هذه الدالة عندما تنتهي منها.

int PHYSFS_mountFile(PHYSFS_File *file, const char *newDir, const char *mountPoint, int appendToPath)

Add an archive, contained in a PHYSFS_File handle, to the search path.

Warning

Unless you have some special, low-level need, you should be using PHYSFS_mount() instead of this.

Archives-in-archives may be very slow! While a PHYSFS_File can seek even when the data is compressed, it may do so by rewinding to the start and decompressing everything before the seek point. Normal archive usage may do a lot of seeking behind the scenes. As such, you might find normal archive usage extremely painful if mounted this way. Plan accordingly: if you, say, have a self-extracting .zip file, and want to mount something in it, compress the contents of the inner archive and make sure the outer .zip file doesn't compress the inner archive too.

This function operates just like PHYSFS_mount(), but takes a PHYSFS_File handle instead of a pathname. This handle contains all the data of the archive, and is used instead of a real file in the physical filesystem. The PHYSFS_File may be backed by a real file in the physical filesystem, but isn't necessarily. The most popular use for this is likely to mount archives stored inside other archives.

(newDir) must be a unique string to identify this archive. It is used to optimize archiver selection (if you name it XXXXX.zip, we might try the ZIP archiver first, for example, or directly choose an archiver that can only trust the data is valid by filename extension). It doesn't need to refer to a real file at all. If the filename extension isn't helpful, the system will try every archiver until one works or none of them do. This filename must be unique, as the system won't allow you to have two archives with the same name.

(file) must remain until the archive is unmounted. When the archive is unmounted, the system will call PHYSFS_close(file). If you need this handle to survive, you will have to wrap this in a PHYSFS_Io and use PHYSFS_mountIo() instead.

If this function fails, PHYSFS_close(file) is not called.

newDir Filename that can represent this stream.
mountPoint Location in the interpolated tree that this archive will be "mounted", in platform-independent notation. NULL or "" is equivalent to "/".
appendToPath nonzero to append to search path, zero to prepend.

بشكل افتراضي، ستتحقق PhysicsFS مما إذا كان الملف رابطًا رمزيًا حقًا أثناء استدعاءات الفتح وتفشل إذا كان كذلك. وإلا، فقد يأخذك الرابط خارج مسارات الكتابة والبحث، ويقوّض الأمان.

إذا كنت تريد تحمل هذا الخطر، فاستدعِ هذه الدالة بمعامل غير صفري. لاحظ أن هذا أكثر لتقييد برنامج لغة برمجة نصية، في حال حاولت نصوص برمجية غير موثوقة تقويض النظام. بشكل عام، قد يكون لدى المستخدم سبب مشروع تمامًا لإعداد رابط رمزي، لذا ما لم تشعر بوجود خطر محدد في السماح بها، يجب أن تسمح بها.

يتم التحقق من الروابط الرمزية صراحةً فقط عند التعامل مع أسماء الملفات بترميز مستقل عن المنصة. أي عند إعداد مسارات البحث والكتابة، إلخ، لا يتم التحقق من الروابط الرمزية أبدًا.

void PHYSFS_flush (PHYSFS_File * handle)

Vacía cualquier dato en el buffer al disco. También libera la memoria asignada al buffer.

Esto causará que cualquier dato que esté esperando en el buffer se escriba al disco. Esto es importante si quieres asegurarte de que los datos estén seguros en el disco, o si necesitas liberar la memoria del buffer por alguna razón.

Si estableces el tamaño del buffer a cero, esto eliminará cualquier buffer existente en el archivo dado.

Esto está implícitamente garantizado para ocurrir cuando un archivo es cerrado, pero si quieres asegurarte de que los datos se escriban antes de que el archivo sea cerrado, deberías llamar a esta función explícitamente.

No hacer un flush puede resultar en la pérdida de datos si el programa falla inesperadamente. También, liberar la memoria del buffer puede ser importante para aplicaciones con memoria limitada.

Esta función puede implicar una llamada a `PHYSFS_setBuffer` con un tamaño de cero.

Los handles de archivos de PhysicsFS son sin buffering por defecto.

int PHYSFS_setRoot (const char * archive, const char * subdir)

Hace un subdirectorio de un archivo su directorio raíz. Esto te permite restringir los archivos accesibles en un archivo específico. Por ejemplo, si tienes un archivo x.zip con un archivo en y/z.txt montado en /a, si llamas a PHYSFS_setRoot("x.zip", "/y"), entonces la llamada PHYSFS_openRead("/a/z.txt") será exitosa.

Puedes cambiar el directorio raíz de un archivo en cualquier momento, lo que altera el árbol de archivos interpolado (dependiendo de donde los caminos se ajusten, un archivo diferente podría proporcionar diferentes archivos). Si estableces el directorio raíz a NULL o a "/", el archivo será tratado como si no hubiera sido establecido especifiquemente (como si el archivo hubiera sido montado normally).

Cambiar el directorio raíz solo afecta las operaciones futuras en rutas de archivos; un archivo que fue abierto desde una ruta que cambió debido a un setRoot no se afectará.

Establecer un nuevo directorio raíz no está limitado a archivos en la lista de búsqueda; también puedes establecerlo en el directorio de escritura, lo cual puede ser útil si tienes archivos abiertos para escribir y no puedes cambiar el directorio de escritura en este momento.

No es un error establecer un subdirectorio que no exista como directorio raíz de un archivo; sin embargo, en ese caso no se verán archivos. Si los directorios que faltan terminan siendo creados (una mkdir en el sistema de archivos físico, etc), esto se reflejará en el árbol interpolado.

Parámetros

archive directorio/archivo en el cual se cambia el directorio raíz.
subdir nuevo subdirectorio para ser el directorio raíz de este archivo.

Retorno

no cero en éxito, cero en error. Usa PHYSFS_getLastErrorCode() para obtener el error específico.

لضمان أن يكون المخزن المؤقت الهدف كبيرًا بما يكفي للتحويل، يرجى تخصيص مخزن مؤقت بحجم ضعف حجم المخزن المؤقت المصدر. لا يستخدم UTF-8 أبدًا أكثر من 32 بت لكل حرف، لذا على الرغم من أنه قد يقلّص سلسلة UTF-16، فقد يوسّعها أيضًا.

السلاسل التي لا تتسع في المخزن المؤقت الهدف سيتم اقتطاعها، لكنها ستكون دائمًا منتهية بـ null ولن تحتوي أبدًا على تسلسل UTF-8 غير مكتمل في النهاية. إذا كان طول المخزن المؤقت 0، فإن هذه الدالة لا تفعل شيئًا.
