Error Codes

PhysicsFS defines a number of error codes that can be returned by its functions. These codes are returned via the return value of the functions themselves. If a function returns zero (or some other indicator of failure) then you may call PHYSFS_getLastErrorCode() to retrieve the specific reason for the failure.

The error codes are:

PHYSFS_ERR_OK
No error.
PHYSFS_ERR_OS_ERROR
Unspecified OS-level error. Use PHYSFS_getLastError() to get the OS-specific error message.
PHYSFS_ERR_NOT_INITIALIZED
PhysicsFS has not been initialized.
PHYSFS_ERR_ALREADY_INITIALIZED
PhysicsFS has already been initialized.
PHYSFS_ERR_MOUNT_FAILED
A specified archive or directory could not be mounted.
PHYSFS_ERR_UNMOUNT_FAILED
A specified archive or directory could not be unmounted.
PHYSFS_ERR_ARCHIVE_IN_USE
An attempt was made to unmount an archive that still contains open files.
PHYSFS_ERR_INVALID_ARGUMENT
An invalid argument was passed to a function.
PHYSFS_ERR_NO_WRITE_DIR
No write dir has been specified.
PHYSFS_ERR_OPEN_FOR_READING
Wrote to a file opened for reading.
PHYSFS_ERR_OPEN_FOR_WRITING
Read from a file opened for writing.
PHYSFS_ERR_NOT_A_FILE
Needed a file, got a directory (etc).
PHYSFS_ERR_READ_ONLY
Wrote to a read-only filesystem.
PHYSFS_ERR_CORRUPT
Corrupted data encountered.
PHYSFS_ERR_SYMLINK_LOOP
Infinite symbolic link loop.
PHYSFS_ERR_IO
i/o error (hardware failure, etc).
PHYSFS_ERR_PERMISSION
Permission denied.
PHYSFS_ERR_NO_SPACE
No space (disk full, over quota, etc)
PHYSFS_ERR_BAD_FILENAME
Filename is bogus/insecure.
PHYSFS_ERR_BUSY
Tried to modify a file the OS needs.
PHYSFS_ERR_DIR_NOT_EMPTY
Tried to delete dir with files in it.
PHYSFS_ERR_OS_ERROR
Unspecified OS-level error.
PHYSFS_ERR_DUPLICATE
Duplicate entry.
PHYSFS_ERR_BAD_PASSWORD
Bad password.
PHYSFS_ERR_APP_CALLBACK
Application callback reported error.

Deinitialize the PhysicsFS library. This closes any files opened via PhysicsFS, blanks the search/write paths, frees memory, and invalidates all of your file handles.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Get a file listing of a search path's directory, using an application-defined callback, with errors reported. Internally, PHYSFS_enumerateFiles() just calls this function and then builds a list before returning to the application, so functionality is identical except for how the information is represented to the application.

Unlike PHYSFS_enumerateFiles(), this function does not return an array. Rather, it calls a function specified by the application once per element of the search path:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Items sent to the callback are not guaranteed to be in any order whatsoever. There is no sorting done at this level, and if you need that, you should probably use PHYSFS_enumerateFiles() instead, which guarantees alphabetical sorting. This form reports whatever is discovered in each archive before moving on to the next. Even within one archive, we can't guarantee what order it will discover data. Any sorting you find in these callbacks is just pure luck. Do not rely on it. As this walks the entire list of archives, you may receive duplicate filenames.

This API and the callbacks themselves are capable of reporting errors. Prior to this API, callbacks had to accept every enumerated item, even if they were only looking for a specific thing and wanted to stop after that, or had a serious error and couldn't alert anyone. Furthermore, if PhysicsFS itself had a problem (disk error or whatnot), it couldn't report it to the calling app, it would just have to skip items or stop enumerating outright, and the caller wouldn't know it had lost some data along the way.

Now the caller can be sure it got a complete data set, and its callback has control if it wants enumeration to stop early. See the documentation for PHYSFS_EnumerateCallback for details on how your callback should behave.

Parameters

dir Directory, in platform-independent notation, to enumerate.
c Callback function to notify about search path elements.
d Application-defined data passed to callback. Can be NULL.

Returns

non-zero on success, zero on failure. Use PHYSFS_getLastErrorCode() to obtain the specific error. If the callback returns PHYSFS_ENUM_STOP to stop early, this will be considered success. Callbacks returning PHYSFS_ENUM_ERROR will make this function return zero and set the error code to PHYSFS_ERR_APP_CALLBACK.

int PHYSFS_registerArchiver (const PHYSFS_Archiver * archiver)

أضف أداة أرشفة جديدة إلى النظام.

تحذير

هذا شيء متقدم وصعب. لست بحاجة إليه إلا إذا كنت تعرف حقًا ما تفعله. معظم التطبيقات لن تحتاج إليه.

إذا كنت تريد توفير أداة أرشفة خاصة بك (على سبيل المثال، تنسيق ملف أرشيف مخصص، أو شيء افتراضي تريد جعله يبدو كـ نظام ملفات يمكنك الوصول إليه من خلال واجهات برمجة تطبيقات PhysicsFS العادية)، فهذا هو المكان الذي تبدأ منه. بمجرد تسجيل أداة أرشفة بنجاح، يمكنك استخدام PHYSFS_mount() لإضافة الأرشيفات التي تدعمها أداة الأرشفة الخاصة بك إلى مسار البحث، أو ربما استخدامها كدليل للكتابة. داخليًا، يستخدم PhysicsFS هذه الوظيفة لتسجيل أدوات الأرشفة المدمجة الخاصة به، مثل دعم .zip، وما إلى ذلك.

لا يمكنك امتلاك أداتي أرشفة تتعاملان مع نفس الامتداد. إذا كان هناك تعارض، يمكنك إلغاء تسجيل أداة الأرشفة الأخرى (بما في ذلك المدمجة) باستخدام PHYSFS_deregisterArchiver().

يتم نسخ البيانات الموجودة في (archiver)؛ يمكنك تحرير هذا المؤشر عند إرجاع هذه الوظيفة.

بمجرد أن تعود هذه الوظيفة بنجاح، سيكون PhysicsFS قادرًا على دعم الأرشيفات من هذا النوع حتى تقوم بإلغاء تسجيل أداة الأرشفة مرة أخرى.

اجعل دليلًا فرعيًا للأرشيف دليله الجذر. يتيح لك هذا تضييق نطاق الملفات القابلة للوصول في أرشيف معين. على سبيل المثال، إذا كان لديك x.zip مع ملف في y/z.txt، تم تحميله على /a، إذا قمت باستدعاء PHYSFS_setRoot("x.zip", "/y")، فإن الاستدعاء PHYSFS_openRead("/a/z.txt") سينجح.

يمكنك تغيير جذر الأرشيف في أي وقت، مما يؤدي إلى تغيير شجرة الملفات المدمجة (اعتمادًا على مكان تحول المسارات، قد يوفر أرشيف مختلف ملفات مختلفة). إذا قمت بتعيين الجذر إلى NULL أو "/"، فسيتم التعامل مع الأرشيف كما لو لم يتم تعيين جذر خاص (كما لو تم تحميل الأرشيف بشكل طبيعي).

يؤثر تغيير الجذر فقط على العمليات المستقبلية على أسماء المسارات؛ لن يتأثر ملف تم فتحه من مسار تغير بسبب setRoot.

لا يقتصر تعيين جذر جديد على الأرشيفات في مسار البحث؛ يمكنك تعيين واحد على دليل الكتابة أيضًا، وهو ما قد يكون مفيدًا إذا كان لديك ملفات مفتوحة للكتابة وبالتالي لا يمكنك تغيير دليل الكتابة في الوقت الحالي.

ليس خطأ تعيين دليل فرعي غير موجود ليكون جذر أرشيف؛ ومع ذلك، لن يتم عرض أي ملفات في هذه الحالة. إذا تم إنشاء الدلائل المفقودة في النهاية (mkdir إلى نظام الملفات الفعلي، وما إلى ذلك) فسيتم عكس ذلك في الشجرة المدمجة.

PHYSFS_getLastError(3)

NAME

PHYSFS_getLastError - Get the last error code from the PhysicsFS library.

LIBRARY

PhysicsFS -- physfs(3)

SYNOPSIS

#include <physfs.h>

PHYSFS_ErrorCode PHYSFS_getLastErrorCode (
    void
);

const char *PHYSFS_getLastError (
    void
);

DESCRIPTION

These functions return the last error code or a human-readable string representing the last error that occurred in the PhysicsFS library.

PHYSFS_getLastErrorCode() returns an enum value of type PHYSFS_ErrorCode representing the error. You can compare this value against the defined constants such as PHYSFS_ERR_OK, PHYSFS_ERR_NOT_FOUND, etc.

PHYSFS_getLastError() returns a pointer to a null-terminated string that describes the error. This string is owned by PhysicsFS and may be overwritten by subsequent calls to any PhysicsFS function.

The error state is cleared whenever a function returns successfully.

RETURN VALUE

On success, PHYSFS_getLastError() returns a pointer to a valid error string. On failure (i.e., no error has occurred), it returns NULL.

PHYSFS_getLastErrorCode() returns PHYSFS_ERR_OK on success.
