typedef PHYSFS_EnumerateCallbackResult(* physFS_EnumerateCallback) (void *data, const char *origdir, const char *fname)

Possible return values from PHYSFS_EnumerateCallback. Function signature for callbacks that enumerate and return results.

These values dictate if an enumeration callback should continue to fire, or stop (and why it is stopping).

See also

PHYSFS_EnumerateCallback

PHYSFS_enumerate

This is the same thing as PHYSFS_EnumFilesCallback from PhysicsFS 2.0, except it can return a result from the callback: namely: if you're looking for something specific, once you find it, you can tell PhysicsFS to stop enumerating further. This is used with PHYSFS_enumerate(), which we hopefully got right this time. :)

Parameters

data User-defined data pointer, passed through from the API that eventually called the callback.
origdir A string containing the full path, in platform-independent notation, of the directory containing this file. In most cases, this is the directory on which you requested enumeration, passed in the callback for your convenience.
fname The filename that is being enumerated. It may not be in alphabetical order compared to other callbacks that have fired, and it will not contain the full path. You can recreate the fullpath with $origdir/$fname ... The file can be a subdirectory, a file, a symlink, etc.

Returns

A value from PHYSFS_EnumerateCallbackResult. All other values are (currently) undefined; don't use them.

typedef void(* physFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Function signature for callbacks that enumerate files.

Warning

As of PhysicsFS 2.1, Use PHYSFS_EnumerateCallback with PHYSFS_enumerate() instead; it gives you more control over the process.

These are used to report a list of directory entries to an original caller, one file/dir/symlink per callback. All strings are UTF-8 encoded. Functions should not try to modify or free any string's memory.

These callbacks are used, starting in PhysicsFS 1.1, as an alternative to functions that would return lists that need to be cleaned up with PHYSFS_freeList(). The callback means that the library doesn't need to allocate an entire list and all the strings up front.

Be aware that promised data ordering in the list versions are not necessarily so in the callback versions. Check the documentation on specific APIs, but strings may not be sorted as you expect and you might get duplicate strings.

Parameters

data User-defined data pointer, passed through from the API that eventually called the callback.
origdir A string containing the full path, in platform-independent notation, of the directory containing this file. In most cases, this is the directory on which you requested enumeration, passed in the callback for your convenience.
fname The filename that is being enumerated. It may not be in alphabetical order compared to other callbacks that have fired, and it will not contain the full path. You can recreate the fullpath with $origdir/$fname ... The file can be a subdirectory, a file, a symlink, etc.

enum PHYSFS_ErrorCode

Values that represent specific causes of failure. Most of the time, you should only concern yourself with whether a given operation failed or not, but there may be occasions where you plan to handle a specific failure case gracefully, so we provide specific error codes.

Most of these errors are a little vague, and most aren't things you can fix...if there's a permission error, for example, all you can really do is pass that information on to the user and let them figure out how to handle it. In most these cases, your program should only care that it failed to accomplish its goals, and not care specifically why.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

احصل على قائمة ملفات لكتالوج مسار بحث، باستخدام دالة استدعاء معرفة من التطبيق، مع الإبلاغ عن الأخطاء. داخليًا، تقوم PHYSFS_enumerateFiles() فقط باستدعاء هذه الدالة ثم بناء قائمة قبل العودة إلى التطبيق، لذا فإن الوظائف متطابقة باستثناء كيفية تمثيل المعلومات للتطبيق.

على عكس PHYSFS_enumerateFiles()، هذه الدالة لا ترجع مصفوفة. بدلاً من ذلك، تستدعي دالة محددة من قبل التطبيق مرة واحدة لكل عنصر في مسار البحث:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

لا يُضمن أن تكون العناصر المرسلة إلى دالة الاستدعاء بأي ترتيب على الإطلاق. لا يتم إجراء أي فرز على هذا المستوى، وإذا كنت بحاجة إلى ذلك، فربما يجب عليك استخدام PHYSFS_enumerateFiles() بدلاً من ذلك، والتي تضمن الفرز الأبجدي. هذا الشكل يبلغ عن أي شيء يتم اكتشافه في كل أرشيف قبل الانتقال إلى التالي. حتى داخل أرشيف واحد، لا يمكننا ضمان الترتيب الذي سيتم به اكتشاف البيانات. أي فرز تجده في دوال الاستدعاء هذه هو مجرد حظ. لا تعتمد عليه. نظرًا لأن هذا يجتاز قائمة الأرشيفات بأكملها، فقد تتلقى أسماء ملفات مكررة.

هذه الواجهة البرمجية (API) ودوال الاستدعاء نفسها قادرة على الإبلاغ عن الأخطاء. قبل هذه الواجهة البرمجية، كان على دوال الاستدعاء قبول كل عنصر تمت معالجته، حتى لو كانوا يبحثون عن شيء معين ويريدون التوقف بعد ذلك، أو كان لديهم خطأ جسيم ولم يتمكنوا من تنبيه أي شخص. علاوة على ذلك، إذا كانت PhysicsFS نفسها لديها مشكلة (خطأ في القرص أو ما شابه)، فلا يمكنها إبلاغ التطبيق المستدعي، بل كان عليها ببساطة تخطي العناصر أو التوقف عن المعالجة تمامًا، ولن يعرف المتصل أنه فقد بعض البيانات على طول الطريق.

الآن يمكن للمتصل التأكد من حصوله على مجموعة بيانات كاملة، ودالة الاستدعاء الخاصة به لديها السيطرة إذا أراد إيقاف المعالجة مبكرًا. انظر وثائق PHYSFS_EnumerateCallback للحصول على تفاصيل حول كيفية سلوك دالة الاستدعاء الخاصة بك.

الإرجاع

قيمة غير صفرية عند النجاح، صفر عند الفشل. استخدم PHYSFS_getLastErrorCode() للحصول على الخطأ المحدد. إذا أعادت دالة الاستدعاء PHYSFS_ENUM_STOP للإيقاف المبكر، فسيتم اعتبار ذلك نجاحًا. ستؤدي دوال الاستدعاء التي تعيد PHYSFS_ENUM_ERROR إلى جعل هذه الدالة ترجع صفرًا وتعيين رمز الخطأ إلى PHYSFS_ERR_APP_CALLBACK.

تحذير

في إصدارات PhysicsFS قبل 2.1، كانت هذه الدالة ترجع أكبر عدد ممكن من العناصر في مواجهة حالة فشل (نفاد الذاكرة، خطأ في إدخال/إخراج القرص، إلخ). نظرًا لأن هذا يعني أنه لا يمكن للتطبيقات التمييز بين النجاح الكامل والفشل الجزئي، وبما أن الدالة يمكن أن تعيد دائمًا NULL للإبلاغ عن حالات الفشل الكارثية على أي حال، فقد تغيرت سياسة هذه الدالة في PhysicsFS 2.1: إما أن ترجع قائمة بنتائج كاملة أو ترجع NULL لأي فشل من أي نوع، حتى نتمكن من ضمان أن المعالجة اكتملت وليس لديها فجوات في نتائجها.

char **rc = PHYSFS_enumerateFiles("savegames");

for (i = rc; *i != NULL; i++)

PHYSFS_freeList(rc);

* We've got [y.sav].
* We've got [z.sav].

This should be called prior to any attempts to change your process's current working directory.

On Android, argv0 should be a non-NULL pointer to a PHYSFS_AndroidInit struct. This struct must hold a valid JNIEnv * and a JNI jobject of a Context (either the application context or the current Activity is fine). int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

Parameters

newDir directory or archive to add to the path, in platform-dependent notation.
mountPoint Location in the interpolated tree that this archive will be "mounted", in platform-independent notation. NULL or "" is equivalent to "/".
appendToPath nonzero to append to search path, zero to prepend.

Returns

nonzero if added to path, zero on failure (bogus archive, dir missing, etc). Use PHYSFS_getLastErrorCode() to obtain the specific error.

تحذير

ما لم يكن لديك حاجة خاصة ومنخفضة المستوى، يجب عليك استخدام PHYSFS_mount() بدلاً من هذا.

قد تكون الأرشيفات داخل الأرشيفات بطيئة جدًا! في حين أن PHYSFS_File يمكنه البحث حتى عندما تكون البيانات مضغوطة، فقد يقوم بذلك عن طريق العودة إلى البداية وفك ضغط كل شيء قبل نقطة البحث. قد يقوم استخدام الأرشيف العادي بالكثير من البحث في الخلفية. على هذا النحو، قد تجد أن استخدام الأرشيف العادي مؤلم للغاية إذا تم تحميله بهذه الطريقة. خطط وفقًا لذلك: إذا كان لديك، على سبيل المثال، ملف .zip يستخرج نفسه، وتريد تحميل شيء بداخله، فقم بضغط محتويات الأرشيف الداخلي وتأكد من أن ملف .zip الخارجي لا يضغط الأرشيف الداخلي أيضًا.

تعمل هذه الدالة تمامًا مثل PHYSFS_mount()، ولكنها تأخذ مقبض PHYSFS_File بدلاً من مسار. يحتوي هذا المقبض على جميع بيانات الأرشيف، ويتم استخدامه بدلاً من ملف حقيقي في نظام الملفات الفعلي. قد يكون PHYSFS_File مدعومًا بملف حقيقي في نظام الملفات الفعلي، ولكنه ليس بالضرورة. الاستخدام الأكثر شعبية لهذا هو على الأرجح تحميل الأرشيفات المخزنة داخل أرشيفات أخرى.

يجب أن يكون (newDir) سلسلة فريدة لتحديد هذا الأرشيف. يتم استخدامه لتحسين اختيار الأرشيف (إذا قمت بتسميته XXXXX.zip، فقد نجرب أرشيف ZIP أولاً، على سبيل المثال، أو نختار مباشرةً أرشيفًا لا يمكنه إلا الوثوق بأن البيانات صالحة بواسطة امتداد اسم الملف). لا يحتاج إلى الإشارة إلى ملف حقيقي على الإطلاق. إذا لم يكن امتداد اسم الملف مفيدًا، فسيقوم النظام بتجربة كل أرشيف حتى يعمل أحدهم أو لا يعمل أي منهم. يجب أن يكون هذا الاسم فريدًا، حيث لن يسمح لك النظام بوجود أرشيفين بنفس الاسم.

يجب أن يظل (file) موجودًا حتى يتم إلغاء تحميل الأرشيف. عند إلغاء تحميل الأرشيف، سيقوم النظام باستدعاء PHYSFS_close(file). إذا كنت بحاجة إلى بقاء هذا المقبض، فسيتعين عليك تغليفه في PHYSFS_Io واستخدام PHYSFS_mountIo() بدلاً من ذلك.

إذا فشلت هذه الدالة، فلن يتم استدعاء PHYSFS_close(file).

يجب أن يكون (newDir) سلسلة فريدة لتحديد هذا الأرشيف. يتم استخدامه لتحسين اختيار الأرشيف (إذا قمت بتسميته XXXXX.zip، فقد نجرب أرشيف ZIP أولاً، على سبيل المثال، أو نختار مباشرةً أرشيفًا لا يمكنه إلا الوثوق بأن البيانات صالحة بواسطة امتداد اسم الملف). لا يحتاج إلى الإشارة إلى ملف حقيقي على الإطلاق. إذا لم يكن امتداد اسم الملف مفيدًا، فسيقوم النظام بتجربة كل أرشيف حتى يعمل أحدهم أو لا يعمل أي منهم. يجب أن يكون هذا الاسم فريدًا، حيث لن يسمح لك النظام بوجود أرشيفين بنفس الاسم.

يجب أن يظل (ptr) موجودًا حتى يتم إلغاء تحميل الأرشيف. عند إلغاء تحميل الأرشيف، سيقوم النظام باستدعاء (del)(ptr)، مما سيخطر بأن النظام قد انتهى من استخدام المخزن المؤقت، وسيمنحك فرصة لتحرير مواردك. يمكن أن يكون (del) NULL، وفي هذه الحالة لن يبذل النظام أي محاولة لتحرير المخزن المؤقت.

إذا فشلت هذه الدالة، فلن يتم استدعاء (del).

المعلمات

buf عنوان مخزن الذاكرة المؤقت الذي يحتوي على بيانات الأرشيف.
len حجم المخزن المؤقت للذاكرة، بالبايت.
del رد اتصال يتم تشغيله عند إلغاء التحميل. يمكن أن يكون NULL.
newDir اسم ملف يمكن أن يمثل هذا البث.
mountPoint الموقع في الشجرة المتداخلة التي سيتم "تحميل" هذا الأرشيف فيها، بتدوين مستقل عن المنصة. NULL أو "" يعادل "/".
appendToPath قيمة غير صفرية لإضافتها إلى مسار البحث، وصفر للتقديم.

يعود

قيمة غير صفرية إذا تم الإضافة إلى المسار، وصفر في حالة الفشل (أرشيف غير صالح، إلخ). استخدم PHYSFS_getLastErrorCode() للحصول على الخطأ المحدد.
