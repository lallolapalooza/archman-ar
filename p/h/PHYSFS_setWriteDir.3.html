ملاحظة

منذ PhysicsFS 2.1، تم إهمال هذه الدالة. قبل 2.1، كانت الطريقة الوحيدة للحصول على تفاصيل الخطأ بخلاف التقييم الأساسي لدالة ما. تم تصميمها لتكون سلسلة قابلة للقراءة بلغات متعددة وغير مفيدة لتحليل التطبيق. كانت مشكلة لأن المطور، وليس المستخدم، هو من يختار اللغة عند الترجمة، وكان على مشغلي PhysicsFS (بشكل سيء) الاحتفاظ بكمية كبيرة من عمل الترجمة. لم يتمكن التطبيق من تحليل السلاسل، حتى لو كانت بلغة معينة، حيث تم إنشاء بعضها ديناميكيًا. في الإصدار 2.1 وما بعده، ترجع دائمًا سلسلة ثابتة باللغة الإنجليزية؛ يمكنك استخدامها كمفاتيح ترجمة في ملفاتك الخاصة، حيث وعدنا بعدم تغيير السلاسل الموجودة. أيضًا، إذا كان تطبيقك يريد رؤية أخطاء محددة، فإننا نقدم الآن خيارًا أفضل: استخدم PHYSFS_getLastErrorCode().

الحصول على آخر رسالة خطأ PhysicsFS كسلسلة قابلة للقراءة ومنتهية بـ NULL. ترجع NULL إذا لم يكن هناك خطأ منذ آخر استدعاء لهذه الدالة. يشير المؤشر المرجع إلى مخزن مؤقت داخلي. كل خيط له حالة خطأ فريدة مرتبطة به، ولكن في كل مرة يتم فيها تعيين رسالة خطأ جديدة، فإنها تستبدل السابقة المرتبطة بهذا الخيط. من الآمن استدعاء هذه الدالة في أي وقت، حتى قبل PHYSFS_init().

PHYSFS_getLastError() و PHYSFS_getLastErrorCode() كلاهما يعيدان تعيين حالة الخطأ المرتبطة بخيط معين. استدعاء أحدهما سيمحو الآخر. إذا كنت بحاجة إلى كليهما، استدعاء PHYSFS_getLastErrorCode()، ثم قم بتمرير القيمة إلى PHYSFS_getErrorByCode().

منذ PhysicsFS 2.1، تعرض هذه الدالة نصًا باللغة الإنجليزية فقط، ولكن السلاسل ثابتة، لذا يمكنك استخدامها كمفاتيح في قاموس الترجمة الخاص بك. هذه السلاسل مخصصة ليتم تمريرها مباشرة إلى المستخدم.

بشكل عام، تهتم التطبيقات فقط بما إذا كانت الدالة قد فشلت؛ ومع ذلك، إذا كان الكود الخاص بك يتطلب المزيد من التفاصيل، يجب عليك استخدام PHYSFS_getLastErrorCode() بدلاً من هذه الدالة.

int PHYSFS_setRoot (const char * archive, const char * subdir)

يجعل مجلدًا فرعيًا من أرشيف ما هو الدليل الجذر له. هذا يسمح لتطبيقك بتقييد الملفات التي يمكن الوصول إليها في أرشيف معين. على سبيل المثال، إذا كان لديك x.zip بملف في y/z.txt، تم تحميله على /a، إذا استدعيت PHYSFS_setRoot("x.zip"، "/y")، فسيتم نجاح استدعاء PHYSFS_openRead("/a/z.txt").

يمكنك تغيير جذر أرشيف في أي وقت، وبالتالي تغيير شجرة الملفات المستقاة (اعتمادًا على مكان انتقال المسارات، قد يوفر أرشيف مختلف ملفات مختلفة). إذا قمت بتعيين الجذر إلى NULL أو إلى ""، فسيتم التعامل مع الأرشيف كما لو لم يتم تعيين جذر خاص (كما لو تم تحميل الأرشيف بشكل طبيعي).

يؤثر تغيير الجذر فقط على العمليات المستقبلية على مسارات الدليل؛ لن يتأثر الملف الذي تم فتحه من مسار تغير بسبب استدعاء PHYSFS_setRoot.

لا يقتصر تعيين جذر جديد على الأرشيفات في مسار البحث عن الدليل؛ يمكنك أيضًا تعيينه إلى دليل الكتابة، والذي قد يكون مفيدًا إذا كان لديك ملفات مفتوحة للكتابة ولا يمكنك تغيير دليل الكتابة في هذا الوقت.

ليس خطأ تعيين دليل فرعي غير موجود كجذر لأرشيف، على الرغم من أنه في هذه الحالة لن يتم عرض أي ملفات. إذا تم إنشاء الأدلة المفقودة في النهاية (mkdir في نظام الملفات الفعلي، وما إلى ذلك)، فسيتم عكس ذلك في الشجرة المستقاة.

مقارنة غير حساسة لحالة الأحرف لسلسلتين UCS-4. هذه بديلة لـ strcasecmp/stricmp التي تتوقع أن تكون كلتا السلسلتين بتنسيق UCS-4 (المعروفة أيضًا باسم UTF-32). إنها تقوم بـ "طي حالة الأحرف" لتحديد ما إذا كانت رموز Unicode في السلاسل متطابقة.

تُرجع أي سلسلة "أكبر" من الأخرى، ولكن ضع في اعتبارك أن هذا لا يعني بالضرورة شيئًا: قد يكون 'a' "أصغر" من 'b'، ولكن لا توجد علاقة أبجدية ذات معنى بين حرف ياباني وحرف يوناني لامدا، ولكن القدرة على تعيين قيمة موثوقة تسمح بخوارزميات الترتيب، حتى لو لم تكن معقولة تمامًا. في معظم الحالات، يجب عليك التعامل مع القيمة المرتجعة على أنها "متساوية" أو "غير متساوية".

مثل stricmp، تتوقع أن تكون كلتا السلسلتين منتهيتين بـ NULL.

المعلمات

str1 السلسلة الأولى للمقارنة.
str2 السلسلة الثانية للمقارنة.

يعيد

-1 إذا كانت str1 "أصغر" من str2، و 1 إذا كانت "أكبر"، و 0 إذا كانت متساوية.

يزيل دليلًا أو أرشيفًا من مسار البحث. هذه الوظيفة مكافئة وظيفيًا لـ PHYSFS_removeFromSearchPath()، ولكن تم إسقاط هذه الوظيفة للحفاظ على المفردات بالتوازي مع PHYSFS_mount().

يجب أن يكون لديك تطابق (حساس لحالة الأحرف) مع دليل أو أرشيف موجود بالفعل في مسار البحث، محدد بتنسيق يعتمد على المنصة.

سيفشل هذا الاستدعاء (ولن يزيل من المسار) إذا كانت هناك ملفات مفتوحة لا تزال موجودة.

تحذير

تريد هذه الوظيفة المسار إلى الدليل أو الأرشيف الذي تم تحميله (نفس السلسلة المستخدمة للوسيط "newDir" لـ PHYSFS_addToSearchPath أو أي من وظائف التحميل)، وليس المسار حيث تم تحميله في الشجرة (الوسيط "mountPoint" لأي من وظائف التحميل).

المعلمات

يعيد

غير صفري عند النجاح، وصفر عند الفشل. استخدم PHYSFS_getLastErrorCode() للحصول على الخطأ المحدد.

void PHYSFS_utf8ToUcs4 (const char * src, PHYSFS_uint32 unicode_char, PHYSFS_uint64 len)

Convert a UTF-8 string to a UCS-4 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UCS-4 strings are 32-bits per character. UTF-8 uses from one to four bytes per character. If you aren't sure how large a buffer you need, you can roughly estimate by assuming every character will take 4 bytes, or even better, just assume it might be as large as 4 times the source buffer size. The worst case for UTF-8 is 4 bytes per character, so if the source string is N bytes, the destination buffer should be at least 4*N bytes.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UCS-4 sequence at the end. If the buffer length is 0, this function does nothing.

Parameters

src Null-terminated source string in UTF-8 format.
dst Buffer to store converted UCS-4 string.
len Size, in bytes, of destination buffer.

void PHYSFS_utf8ToUtf16 (const char * src, PHYSFS_uint16 * dst, PHYSFS_uint64 len)

Convert a UTF-8 string to a UTF-16 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UTF-16 strings are 16-bits per character (except some chars, which are 32-bits): TCHAR on Windows, when building with Unicode support. Modern Windows releases use UTF-16. Windows releases before 2000 used TCHAR, but only handled UCS-2. UTF-16 is UCS-2, except for the characters that are 4 bytes, which aren't representable in UCS-2 at all anyhow. If you aren't sure, you should be using UTF-16 at this point on Windows.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 uses from one to four bytes per character, but UTF-16 always uses two to four, so an entirely low-ASCII string will double in size! The UTF-16 characters that would take four bytes also take four bytes in UTF-8, so you don't need to allocate 4x the space just in case: double will do.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-16 surrogate pair at the end. If the buffer length is 0, this function does nothing.

Parameters

src Null-terminated source string in UTF-8 format.
dst Buffer to store converted UTF-16 string.
len Size, in bytes, of destination buffer.

PHYSFS_sint64 PHYSFS_writeBytes (PHYSFS_File * handle, const void * buffer, PHYSFS_uint64 len)

Write data to a PhysicsFS filehandle. The file must be opened for writing.

Please note that while (len) is an unsigned 64-bit integer, you are limited to 63 bits (9223372036854775807 bytes), so we can return a negative value on error. If length is greater than 0x7FFFFFFFFFFFFFFF, this function will immediately fail. For systems without a 64-bit datatype, you are limited to 31 bits (0x7FFFFFFF, or 2147483647 bytes). We trust most things won't need to do multiple gigabytes of i/o in one call anyhow, but why limit things?

Parameters

handle retval from PHYSFS_openWrite() or PHYSFS_openAppend().
buffer buffer of (len) bytes to write to (handle).
len number of bytes being written to (handle).

Returns

number of bytes written. This may be less than (len); in the case of an error, the system may try to write as many bytes as possible, so an incomplete write might occur. PHYSFS_getLastErrorCode() can shed light on the reason this might be < (len). -1 if complete failure.
