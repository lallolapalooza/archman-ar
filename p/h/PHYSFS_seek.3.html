PHYSFS_VERSION

A macro that contains the version of PhysicsFS you have compiled against.

This is determined by what header the compiler uses. Note that if you dynamically linked the library, you might have a slightly newer or older version at runtime. That version can be determined with PHYSFS_getLinkedVersion(), which, unlike PHYSFS_VERSION, is not a macro.

typedef PHYSFS_EnumerateCallbackResult(* PHYSFS_EnumerateCallback) (void *data, const char *origdir, const char *fname)

Possible return values from PHYSFS_EnumerateCallback. Function signature for callbacks that enumerate and return results.

These values dictate if an enumeration callback should continue to fire, or stop (and why it is stopping).

See also

PHYSFS_EnumerateCallback

PHYSFS_enumerate

This is the same thing as PHYSFS_EnumFilesCallback from PhysicsFS 2.0, except it can return a result from the callback: namely: if you're looking for something specific, once you find it, you can tell PhysicsFS to stop enumerating further. This is used with PHYSFS_enumerate(), which we hopefully got right this time. :)

Parameters

data User-defined data pointer, passed through from the API that eventually called the callback.
origdir A string containing the full path, in platform-independent notation, of the directory containing this file. In most cases, this is the directory on which you requested enumeration, passed in the callback for your convenience.
fname The filename that is being enumerated. It may not be in alphabetical order compared to other callbacks that have fired, and it will not contain the full path. You can recreate the fullpath with $origdir/$fname ... The file can be a subdirectory, a file, a symlink, etc.

Returns

A value from PHYSFS_EnumerateCallbackResult. All other values are (currently) undefined; don't use them.

typedef void(* PHYSFS_EnumFilesCallback) (void *data, const char *origdir, const char *fname)

Function signature for callbacks that enumerate files.

Warning

As of PhysicsFS 2.1, Use PHYSFS_EnumerateCallback with PHYSFS_enumerate() instead; it gives you more control over the process.

These are used to report a list of directory entries to an original caller, one file/dir/symlink per callback. All strings are UTF-8 encoded. Functions should not try to modify or free any string's memory.

These callbacks are used, starting in PhysicsFS 1.1, as an alternative to functions that would return lists that need to be cleaned up with PHYSFS_freeList(). The callback means that the library doesn't need to allocate an entire list and all the strings up front.

Be aware that promised data ordering in the list versions are not necessarily so in the callback versions. Check the documentation on specific APIs, but strings may not be sorted as you expect and you might get duplicate strings.

Parameters

data User-defined data pointer, passed through from the API that eventually called the callback.
origdir A string containing the full path, in platform-independent notation, of the directory containing this file. In most cases, this is the directory on which you requested enumeration, passed in the callback for your convenience.
fname The filename that is being enumerated. It may not be in alphabetical order compared to other callbacks that have fired, and it will not contain the full path. You can recreate the fullpath with $origdir/$fname ... The file can be a subdirectory, a file, a symlink, etc.

enum PHYSFS_ErrorCode

Values that represent specific causes of failure. Most of the time, you should only concern yourself with whether a given operation failed or not, but there may be occasions where you plan to handle a specific failure case gracefully, so we provide specific error codes.

Most of these errors are a little vague, and most aren't things you can fix...if there's a permission error, for example, all you can really do is pass that information on to the user and let them figure out how to handle it. In most these cases, your program should only care that it failed to accomplish its goals, and not care specifically why.

قد تكون الأرشيفات داخل الأرشيفات بطيئة جدًا! بينما يمكن لـ PHYSFS_File التخطي حتى عندما تكون البيانات مضغوطة، فقد يتم ذلك عن طريق العودة إلى البداية وفك ضغط كل شيء قبل نقطة التخطي. قد يقوم الاستخدام العادي للأرشيف بالكثير من عمليات التخطي خلف الكواليس. على هذا النحو، قد تجد أن الاستخدام العادي للأرشيف مؤلم للغاية إذا تم تحميله بهذه الطريقة. خطط وفقًا لذلك: إذا كان لديك، على سبيل المثال، ملف .zip ذاتي الاستخراج، وتريد تحميل شيء ما بداخله، فقم بضغط محتويات الأرشيف الداخلي وتأكد من أن ملف .zip الخارجي لا يضغط الأرشيف الداخلي أيضًا.

تعمل هذه الوظيفة تمامًا مثل PHYSFS_mount()، ولكنها تأخذ مقبض PHYSFS_File بدلاً من مسار. يحتوي هذا المقبض على جميع بيانات الأرشيف، ويتم استخدامه بدلاً من ملف حقيقي في نظام الملفات المادي. قد يستند PHYSFS_File إلى ملف حقيقي في نظام الملفات المادي، ولكنه ليس بالضرورة كذلك. الاستخدام الأكثر شيوعًا لهذا هو على الأرجح تحميل الأرشيفات المخزنة داخل الأرشيفات الأخرى.

(newDir) يجب أن يكون سلسلة فريدة لتحديد هذا الأرشيف. يتم استخدامه لتحسين اختيار أداة الأرشفة (إذا سميته XXXXX.zip، فقد نجرب أداة ZIP أولاً، على سبيل المثال، أو نختار مباشرة أداة لا يمكنها التأكد من صحة البيانات إلا من خلال امتداد اسم الملف). لا يلزم أن يشير إلى ملف حقيقي على الإطلاق. إذا لم يكن امتداد اسم الملف مفيدًا، فسيحاول النظام تجربة كل أداة أرشفة حتى تعمل واحدة أو لا تعمل أي منها. يجب أن يكون اسم الملف هذا فريدًا، حيث لن يسمح لك النظام بوجود أرشيفين بنفس الاسم.

(file) يجب أن يظل موجودًا حتى يتم إلغاء تحميل الأرشيف. عند إلغاء تحميل الأرشيف، سيستدعي النظام PHYSFS_close(file). إذا كنت بحاجة إلى بقاء هذا المقبض، فستحتاج إلى تغليفه في PHYSFS_Io واستخدام PHYSFS_mountIo() بدلاً من ذلك.

إذا فشلت هذه الوظيفة، فلن يتم استدعاء PHYSFS_close(file).

هذه أداة متقدمة، على مستوى عالٍ. لا تحتاجها، إلا إذا كنت تعرف بالضبط ما تفعله. معظم التطبيقات لن تحتاج إليها.

Set the buffer size for a given file handle. Buffers are generally a good thing. They reduce the number of system calls that must be made to read or write files. PhysicsFS attempts to use buffering by default.

You may explicitly turn off buffering by calling this function with a bufsize of zero. This is usually a bad idea, as it will make all reads and writes into expensive system calls.

Setting a buffer size greater than zero will enable buffering. If a buffer already exists for this file handle, it will be flushed to disk and its size will be changed to the new value.

PhysicsFS file handles are unbuffered by default.

Please check the return value of this function! Failures can include not being able to seek backwards in a read-only file when removing the buffer, not being able to allocate the buffer, and not being able to flush the buffer to disk, among other unexpected problems.

The write dir will be set to the pref dir returned by

PHYSFS_getPrefDir(organization, appName)

, which is created if it doesn't exist.

The above is sufficient to make sure your program's configuration directory is separated from other clutter, and platform-independent.

The search path will be:

  • The Write Dir (created if it doesn't exist)
  • The Base Dir (PHYSFS_getBaseDir())
  • All found CD-ROM dirs (optionally)

If you specified "PKG" for (archiveExt), and there's a file named data.PKG in the base dir, it'll be checked. Archives can either be appended or prepended to the search path in alphabetical order, regardless of which directories they were found in. All of this can be accomplished from the application, but this just does it all for you. Feel free to add more to the search path manually, too.

Detailed Description

These functions offer a way to write unsigned integers to a PHYSFS_File in a platform-independent way. You specify the byte order you want (big-endian or little-endian) and the type of integer (16, 32, or 64 bits) and these functions will convert the value from the platform's native byte order and write it to the file.

These are convenience functions. They do the same thing as calling PHYSFS_write directly after converting the value yourself.

Returns zero on failure, non-zero on success. On failure, you can find out what went wrong from PHYSFS_getLastErrorCode().
