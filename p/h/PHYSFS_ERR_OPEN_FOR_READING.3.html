int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Get a file listing of a search path's directory, using an application-defined callback, with errors reported. Internally, PHYSFS_enumerateFiles() just calls this function and then builds a list before returning to the application, so functionality is identical except for how the information is represented to the application.

Unlike PHYSFS_enumerateFiles(), this function does not return an array. Rather, it calls a function specified by the application once per element of the search path:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Items sent to the callback are not guaranteed to be in any order whatsoever. There is no sorting done at this level, and if you need that, you should probably use PHYSFS_enumerateFiles() instead, which guarantees alphabetical sorting. This form reports whatever is discovered in each archive before moving on to the next. Even within one archive, we can't guarantee what order it will discover data. Any sorting you find in these callbacks is just pure luck. Do not rely on it. As this walks the entire list of archives, you may receive duplicate filenames.

This API and the callbacks themselves are capable of reporting errors. Prior to this API, callbacks had to accept every enumerated item, even if they were only looking for a specific thing and wanted to stop after that, or had a serious error and couldn't alert anyone. Furthermore, if PhysicsFS itself had a problem (disk error or whatnot), it couldn't report it to the calling app, it would just have to skip items or stop enumerating outright, and the caller wouldn't know it had lost some data along the way.

Now the caller can be sure it got a complete data set, and its callback has control if it wants enumeration to stop early. See the documentation for PHYSFS_EnumerateCallback for details on how your callback should behave.

Parameters

dir Directory, in platform-independent notation, to enumerate.
c Callback function to notify about search path elements.
d Application-defined data passed to callback. Can be NULL.

Returns

non-zero on success, zero on failure. Use PHYSFS_getLastErrorCode() to obtain the specific error. If the callback returns PHYSFS_ENUM_STOP to stop early, this will be considered success. Callbacks returning PHYSFS_ENUM_ERROR will make this function return zero and set the error code to PHYSFS_ERR_APP_CALLBACK.

char ** PHYSFS_enumerateFiles (const char * dir)

Get a file listing of a search path's directory.

Warning

In PhysicsFS versions prior to 2.1, this function would return as many items as it could in the face of a failure condition (out of memory, disk i/o error, etc). Since this meant apps couldn't distinguish between complete success and partial failure, and since the function could always return NULL to report catastrophic failures anyway, in PhysicsFS 2.1 this function's policy changed: it will either return a list of complete results or it will return NULL for any failure of any kind, so we can guarantee that the enumeration ran to completion and has no gaps in its results.

Matching directories are interpolated. That is, if "C:\mydir" is in the search path and contains a directory "savegames" that contains "x.sav", "y.sav", and "z.sav", and there is also a "C:\userdir" in the search path that has a "savegames" subdirectory with "w.sav", then the following code:

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);
PHYSFS_freeList(rc);
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..fi
Feel free to sort the list however you like. However, the returned data will always contain no duplicates, and will be always sorted in alphabetic (rather: case-sensitive Unicode) order for you.
Don't forget to call PHYSFS_freeList() with the return value from this function when you are done with it.
Parameters
dir directory in platform-independent notation to enumerate. 
Returns
Null-terminated array of null-terminated strings, or NULL for failure cases.

Get a file listing of a search path's directory, using an application-defined callback.

Deprecated

As of PhysicsFS 2.1, use PHYSFS_enumerate() instead. This function has no way to report errors (or to have the callback signal an error or request a stop), so if data will be lost, your callback has no way to direct the process, and your calling app has no way to know.

As of PhysicsFS 2.1, this function just wraps PHYSFS_enumerate() and ignores errors. Consider using PHYSFS_enumerate() or PHYSFS_enumerateFiles() instead.

تمكين أو تعطيل متابعة الروابط الرمزية. تحتوي بعض أنظمة الملفات المادية والأرشيفات على ملفات هي مجرد مؤشرات لملفات أخرى. على نظام الملفات المادي، سيؤدي فتح مثل هذا الرابط إلى (بشكل شفاف) فتح الملف الذي يشير إليه.

افتراضيًا، سيقوم PhysicsFS بالتحقق مما إذا كان الملف هو رابط رمزي بالفعل أثناء استدعاءات الفتح وسيفشل إذا كان كذلك. خلاف ذلك، يمكن للرابط أن يأخذك خارج مسارات الكتابة والبحث، ويشكل خطرًا على الأمان.

إذا كنت ترغب في تحمل هذا الخطر، قم باستدعاء هذه الوظيفة بمعامل غير صفري. لاحظ أن هذا هو المزيد من أجل وضع برنامجك في وضع الحماية، في حالة محاولة البرامج النصية غير الموثوق بها اختراق النظام. بشكل عام، يمكن للمستخدم أن يكون لديه سبب مشروع لإعداد رابط رمزي، لذا ما لم تشعر بوجود خطر معين في السماح بها، يجب عليك السماح بها.

يتم التحقق من الروابط الرمزية بشكل صريح فقط عند التعامل مع أسماء الملفات بالترميز المستقل عن المنصة. أي، عند إعداد مسارات البحث والكتابة الخاصة بك، وما إلى ذلك، لا يتم التحقق من الروابط الرمزية أبدًا.

يرجى ملاحظة أن PHYSFS_stat() سيتحقق دائمًا من المسار المحدد؛ إذا كان هذا المسار رابطًا رمزيًا، فلن يتم اتباعه في أي حال. إذا لم تسمح الروابط الرمزية من خلال هذه الوظيفة، فإن PHYSFS_stat() يتجاهلها، وسيعامل الاستعلام كما لو كان المسار غير موجود على الإطلاق.

يمكن تمكين أو تعطيل إذن الروابط الرمزية في أي وقت بعد استدعاء PHYSFS_init()، ويتم تعطيله افتراضيًا.

int PHYSFS_registerArchiver (const PHYSFS_Archiver * archiver)

إضافة أداة أرشفة جديدة إلى النظام.

تحذير

هذه أمور متقدمة وصعبة. لست بحاجة إليها إلا إذا كنت تعرف حقًا ما تفعله. معظم التطبيقات لن تحتاج إليها.

إذا كنت ترغب في توفير أداة أرشفة خاصة بك (على سبيل المثال، تنسيق ملف أرشيف مخصص، أو شيء افتراضي تريد أن يبدو كملف نظام يمكنك الوصول إليه من خلال واجهات برمجة تطبيقات PhysicsFS العادية)، فهذا هو المكان الذي تبدأ منه. بمجرد تسجيل أداة أرشفة بنجاح، يمكنك بعد ذلك استخدام PHYSFS_mount() لإضافة الأرشيفات التي تدعمها أداة الأرشفة الخاصة بك إلى مسار البحث، أو ربما استخدامها كدليل للكتابة. داخليًا، تستخدم PhysicsFS هذه الوظيفة لتسجيل أدوات الأرشفة المضمنة الخاصة بها، مثل دعم .zip، إلخ.

لا يمكنك أن يكون لديك أدوات أرشفة اثنتان تعالجان نفس الامتداد. إذا كان لديك تعارض، يمكنك إلغاء تسجيل أداة الأرشفة الأخرى (بما في ذلك المدمجة) باستخدام PHYSFS_deregisterArchiver().

يتم نسخ البيانات في (archiver)؛ يمكنك تحرير هذا المؤشر عندما تعود هذه الوظيفة.

بمجرد عودة هذه الوظيفة بنجاح، ستتمكن PhysicsFS من دعم الأرشيفات من هذا النوع حتى تقوم بإلغاء تسجيل أداة الأرشفة مرة أخرى.

NAME

PHYSFS_writeUBE16, PHYSFS_writeUBE32, PHYSFS_writeUBE64, PHYSFS_writeULE16, PHYSFS_writeULE32, PHYSFS_writeULE64 — convert and write unsigned integer types.

SYNOPSIS

#include <physfs.h>

int PHYSFS_writeUBE16(PHYSFS_File *file, PHYSFS_uint16 val);
int PHYSFS_writeUBE32(PHYSFS_File *file, PHYSFS_uint32 val);

int PHYSFS_writeULE32(PHYSFS_File *file, PHYSFS_uint32 val);
int PHYSFS_writeULE64(PHYSFS_File *file, PHYSFS_uint64 val);

Detailed Description

These functions convert an unsigned integer from the platform's native byte order to the specified endianness (big-endian or little-endian) and then write it to a PhysicsFS file handle.

These are convenience functions for writing binary data in a cross-platform compatible way.
