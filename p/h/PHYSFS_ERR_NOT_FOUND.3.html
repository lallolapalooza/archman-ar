int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

الحصول على قائمة ملفات من دليل في مسار البحث، باستخدام دالة رد اتصال معرفة من قبل المستخدم، مع الإبلاغ عن الأخطاء. داخليًا، PHYSFS_enumerateFiles() تستدعي هذه الدالة فقط ثم تبني قائمة قبل إعادتها إلى التطبيق، لذا فإن الوظيفة متطابقة، على الرغم من أن المحتوى يتم تقديمه بطريقة مختلفة.

على عكس PHYSFS_enumerateFiles()، لا تعيد هذه الدالة مصفوفة. بدلاً من ذلك، تستدعي دالة محددة من قبل التطبيق مرة واحدة لكل عنصر في مسار البحث:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // أرغب في الحصول على المزيد من البيانات، من فضلك.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

لا يُضمن أن تكون العناصر المرسلة إلى دالة رد الاتصال بترتيب معين. لا يتم إجراء فرز على هذا المستوى، وإذا كنت بحاجة إليه، فيجب عليك استخدام PHYSFS_enumerateFiles()، والتي تضمن الترتيب الأبجدي. هذا الشكل يبلغ عما يتم العثور عليه في كل ملف أرشيف قبل الانتقال إلى الملف التالي. حتى داخل ملف واحد، لا يمكننا ضمان الترتيب الذي يتم به اكتشاف البيانات. أي ترتيب تجده في دوال رد الاتصال هذه هو مجرد حظ. لا تعتمد عليه أبدًا. نظرًا لأن هذه الدالة تمر عبر قائمة الملفات بأكملها، فقد تتلقى أسماء ملفات مكررة.

يمكن لواجهة برمجة التطبيقات هذه ودوال رد الاتصال نفسها الإبلاغ عن الأخطاء. قبل واجهة برمجة التطبيقات هذه، كان على دوال رد الاتصال قبول كل عنصر تم تعداده، حتى لو كانت تبحث فقط عن عنصر معين وتريد التوقف بعد ذلك، أو إذا كان لديها خطأ جسيم ولم تتمكن من إبلاغ أي شخص. علاوة على ذلك، إذا كانت PhysicsFS نفسها لديها مشكلة (خطأ في القرص أو ما شابه)، فلا يمكنها إبلاغ التطبيق المستدعي، كان عليها فقط تخطي العناصر أو إيقاف التعداد، ولن يعرف المستدعي أنه فقد بعض البيانات أثناء العملية.

الآن يمكن للمستدعي التأكد من أنه حصل على مجموعة كاملة من البيانات، وستكون لديه دالة رد الاتصال الخاصة به تحكم في ما إذا كان سيوقف التعداد مبكرًا. راجع وثائق PHYSFS_EnumerateCallback للحصول على تفاصيل حول كيفية سلوك دالة رد الاتصال الخاصة بك.

المعلمات

dir الدليل، بتدوين مستقل عن نظام التشغيل، ليتم تعداده.
c دالة رد الاتصال للإبلاغ عن عناصر مسار البحث.
d بيانات معرفة من قبل التطبيق يتم تمريرها إلى دالة رد الاتصال. يمكن أن تكون NULL.

القيمة المعادة

غير صفري عند النجاح، صفر عند حدوث خطأ. استخدم PHYSFS_getLastErrorCode() للحصول على الخطأ المحدد. إذا أعادت دالة رد الاتصال PHYSFS_ENUM_STOP للإيقاف مبكرًا، فسيتم اعتبار ذلك نجاحًا. دوال رد الاتصال التي تعيد PHYSFS_ENUM_ERROR ستجعل هذه الدالة تعيد صفرًا وتعيين رمز الخطأ إلى PHYSFS_ERR_APP_CALLBACK.

PHYSFS_getLastErrorCode

Get the last error code.

This function returns the last error code that was reported by PhysicsFS. Note that this error code is per-thread, so it doesn't interfere with other threads' error states.

Note: PHYSFS_getLastErrorCode() and PHYSFS_getErrorByCode() share the same thread-specific error state. Calling one will wipe out the other's data. If you need both, call PHYSFS_getLastErrorCode(), then pass that value to PHYSFS_getErrorByCode().

const char * PHYSFS_getPrefDir (const char * org, const char * app)

Get the user-and-app-specific path where files can be written. Helper function.

Get the "pref dir". This is meant to be where users can write personal files (preferences and save games, etc) that are specific to your application. This directory is unique per user, per application.

This function will decide the appropriate location in the native filesystem, create the directory if necessary, and return a string in platform-dependent notation, suitable for passing to PHYSFS_setWriteDir().

On Windows, this might look like: "C:\\Users\\bob\\AppData\\Roaming\\My Company\\My Program Name"

On Linux, this might look like: "/home/bob/.local/share/My Program Name"

On Mac OS X, this might look like: "/Users/bob/Library/Application Support/My Program Name"

(etc.)

You should probably use the pref dir for your write dir, and also put it near the beginning of your search path. Older versions of PhysicsFS offered only PHYSFS_getUserDir() and left you to figure out where the files should go under that tree. This finds the correct location for whatever platform, which not only changes between operating systems, but also versions of the same operating system.

You specify the name of your organization (if it's not a real organization, your name or an Internet domain you own might do) and the name of your application. These should be proper names.

Both the (org) and (app) strings may become part of a directory name, so please follow these rules:

  • Try to use the same org string (including case-sensitivity) for all your applications that use this function.
  • Always use a unique app string for each one, and make sure it never changes for an app once you've decided on it.
  • Unicode characters are legal, as long as it's UTF-8 encoded, but...
  • ...only use letters, numbers, and spaces. Avoid punctuation like "Game Name 2: Bad Guy's Revenge!" ... "Game Name 2" is sufficient.

The pointer returned by this function remains valid until you call this function again, or call PHYSFS_deinit(). This is not necessarily a fast call, though, so you should call this once at startup and copy the string if you need it.

You should assume the path returned by this function is the only safe place to write files (and that PHYSFS_getUserDir() and PHYSFS_getBaseDir(), while they might be writable, or even parents of the returned path, aren't where you should be writing things).

Parameters

org The name of your organization.
app The name of your application.

Returns

READ ONLY string of user dir in platform-dependent notation. NULL if there's a problem (creating directory failed, etc).

const char * PHYSFS_getRealDir (const char * filename)

Figure out where in the search path a file resides. The file is specified in platform-independent notation. The returned filename will be the element of the search path where the file was found, which may be a directory, or an archive. Even if there are multiple matches in different parts of the search path, only the first one found is used, just like when opening a file.

So, if you look for "maps/level1.map", and C:\mygame is in your search path and C:\mygame\maps\level1.map exists, then "C:\mygame" is returned.

If a any part of a match is a symbolic link, and you've not explicitly permitted symlinks, then it will be ignored, and the search for a match will continue.

If you specify a fake directory that only exists as a mount point, it'll be associated with the first archive mounted there, even though that directory isn't necessarily contained in a real archive.

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

تحويل سلسلة نصية بصيغة UTF-8 إلى سلسلة نصية بصيغة Latin1. سلاسل Latin1 هي 8 بت لكل حرف: ترميز شائع لـ "ASCII عالي".

لضمان أن يكون المخزن المؤقت الوجهة كبيرًا بما يكفي للتحويل، يرجى تخصيص مخزن مؤقت بحجم ضعف حجم المخزن المؤقت المصدر. توسع UTF-8 نقاط ترميز Latin1 فوق 127 من 1 إلى 2 بايت، لذا قد تنمو السلسلة النصية في بعض الحالات.

سيتم اقتطاع السلاسل النصية التي لا تتناسب مع المخزن المؤقت الوجهة، ولكنها ستنتهي دائمًا بحرف NULL ولن تحتوي أبدًا على تسلسل UTF-8 غير مكتمل في النهاية. إذا كان طول المخزن المؤقت 0، فلن تقوم هذه الدالة بأي شيء.

يرجى ملاحظة أننا لا نقدم محولًا من UTF-8 إلى Latin1، نظرًا لأن Latin1 لا يمكنه التعبير عن معظم نقاط ترميز Unicode. إنه ترميز قديم؛ يجب عليك الابتعاد عنه في جميع الأوقات.

المعلمات

src سلسلة نصية مصدرية منتهية بـ NULL بصيغة Latin1.
dst مخزن مؤقت لتخزين السلسلة النصية المحولة بصيغة UTF-8.
len حجم، بالبايت، المخزن المؤقت الوجهة.

void PHYSFS_utf8FromUcs2 (const PHYSFS_uint16 * src, char * dst, PHYSFS_uint64 len)

تحويل سلسلة نصية بصيغة UCS-2 إلى سلسلة نصية بصيغة UTF-8.

تحذير

من شبه المؤكد أنك يجب أن تستخدم PHYSFS_utf8FromUtf16()، التي أصبحت متاحة في PhysicsFS 2.1، ما لم تكن تعرف ما تفعله.
