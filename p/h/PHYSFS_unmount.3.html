انظر أيضًا

PHYSFS_EnumerateCallback

PHYSFS_enumerate

هذا هو نفس PHYSFS_EnumFilesCallback من PhysicsFS 2.0، إلا أنه يعيد نتيجة من رد النداء: إذا كنت تبحث عن شيء محدد، بمجرد العثور عليه، يمكنك إخبار PhysicsFS بإيقاف السرد. يتم استخدام هذا مع PHYSFS_enumerate()، والذي نتوقع أنك حصلت عليه بشكل صحيح. :)

المعلمات

data مؤشر إلى بنية PHYSFS_Version للتهيئة.
origdir سلسلة تحتوي على المسار الكامل، بترقيم مستقل عن نظام التشغيل، للدليل الذي يحتوي على هذا الملف. في معظم الحالات، يكون هذا هو الدليل الذي طلبت منه السرد، وتم تمريره في رد النداء لراحتك.
fname اسم الملف الذي يتم سرده. قد لا يكون بالترتيب الأبجدي مقارنة بردود النداء الأخرى التي تم تنفيذها، ولن يحتوي على المسار الكامل. يمكنك إعادة بناء المسار الكامل باستخدام $origdir/$fname ... قد يكون الملف دليلًا فرعيًا، أو ملفًا، أو رابطًا رمزيًا، وما إلى ذلك.

الإرجاع

قيمة من PHYSFS_EnumerateCallbackResult. جميع القيم الأخرى (حاليًا) غير محددة؛ لا تستخدمها.

int PHYSFS_caseFold (const PHYSFS_uint32 from, PHYSFS_uint32 * to)

"Fold" a Unicode codepoint to a lowercase equivalent. (This is for limited, hardcore use. If you don't immediately see a need for it, you can probably ignore this forever.)

This will convert a Unicode codepoint into its lowercase equivalent. Bogus codepoints and codepoints without a lowercase equivalent will be returned unconverted.

Note that you might get multiple codepoints in return! The German Eszett, for example, will fold down to two lowercase latin 's' codepoints. The theory is that if you fold two strings, one with an Eszett and one with "SS" down, they will match.

Warning

Anyone that is a student of Unicode knows about the "Turkish I" problem. This API does not handle it. Assume this one letter in all of Unicode will definitely fold sort of incorrectly. If you don't know what this is about, you can probably ignore this problem for most of the planet, but perfection is impossible.

The number of codepoints the folding produced. Between 1 and 3.

int PHYSFS_deinit (void )

Deinitialize the PhysicsFS library. This closes any files opened via PhysicsFS, blanks the search/write paths, frees memory, and invalidates all of your file handles.

Note that this call can FAIL if there's a file open for writing that refuses to close (for example, the underlying operating system was buffering writes to network filesystem, and the fileserver has crashed, or a hard drive has failed, etc). int PHYSFS_delete (const char * filename)

Delete a file or directory. (filename) is specified in platform-independent notation in relation to the write dir.

A directory must be empty before this call can delete it.

Deleting a symlink will remove the link, not what it points to, regardless of whether you "permitSymLinks" or not.

So if you've got the write dir set to "C:\mygame\writedir" and call PHYSFS_delete("downloads/maps/level1.map") then the file "C:\mygame\writedir\downloads\maps\level1.map" is removed from the physical filesystem, if it exists and the operating system permits the deletion.

Note that on Unix systems, deleting a file may be successful, but the actual file won't be removed until all processes that have an open filehandle to it (including your program) close their handles.

Chances are, the bits that make up the file still exist, they are just made available to be written over at a later point. Don't consider this a security method or anything. :)

const char * PHYSFS_getPrefDir (const char * org, const char * app)

Get the user-and-app-specific path where files can be written. Helper function.

Get the "pref dir". This is meant to be where users can write personal files (preferences and save games, etc) that are specific to your application. This directory is unique per user, per application.

This function will decide the appropriate location in the native filesystem, create the directory if necessary, and return a string in platform-dependent notation, suitable for passing to PHYSFS_setWriteDir().

On Windows, this might look like: "C:\\Users\\bob\\AppData\\Roaming\\My Company\\My Program Name"

On Linux, this might look like: "/home/bob/.local/share/My Program Name"

On Mac OS X, this might look like: "/Users/bob/Library/Application Support/My Program Name"

(etc.)

You should probably use the pref dir for your write dir, and also put it near the beginning of your search path. Older versions of PhysicsFS offered only PHYSFS_getUserDir() and left you to figure out where the files should go under that tree. This finds the correct location for whatever platform, which not only changes between operating systems, but also versions of the same operating system.

You specify the name of your organization (if it's not a real organization, your name or an Internet domain you own might do) and the name of your application. These should be proper names.

Both the (org) and (app) strings may become part of a directory name, so please follow these rules:

  • Try to use the same org string (including case-sensitivity) for all your applications that use this function.
  • Always use a unique app string for each one, and make sure it never changes for an app once you've decided on it.
  • Unicode characters are legal, as long as it's UTF-8 encoded, but...
  • ...only use letters, numbers, and spaces. Avoid punctuation like "Game Name 2: Bad Guy's Revenge!" ... "Game Name 2" is sufficient.

The pointer returned by this function remains valid until you call this function again, or call PHYSFS_deinit(). This is not necessarily a fast call, though, so you should call this once at startup and copy the string if you need it.

You should assume the path returned by this function is the only safe place to write files (and that PHYSFS_getUserDir() and PHYSFS_getBaseDir(), while they might be writable, or even parents of the returned path, aren't where you should be writing things).

Parameters

org The name of your organization.
app The name of your application.

Returns

READ ONLY string of user dir in platform-dependent notation. NULL if there's a problem (creating directory failed, etc).

See also

const char * PHYSFS_getRealDir (const char * filename)

Figure out where in the search path a file resides. The file is specified in platform-independent notation. The returned filename will be the element of the search path where the file was found, which may be a directory, or an archive. Even if there are multiple matches in different parts of the search path, only the first one found is used, just like when opening a file.

So, if you look for "maps/level1.map", and C:\mygame is in your search path and C:\mygame\maps\level1.map exists, then "C:\mygame" is returned.

READ ONLY string of element of search path containing the the file in question. NULL if not found.

تحذير

ما لم يكن لديك حاجة خاصة ومنخفضة المستوى، يجب عليك استخدام PHYSFS_mount() بدلاً من هذه الوظيفة.

قد تكون الأرشيفات داخل الأرشيفات بطيئة جدًا! بينما يمكن لـ PHYSFS_File القفز حتى عند ضغط البيانات، قد يفعل ذلك عن طريق التراجع إلى البداية وفك ضغط كل شيء قبل نقطة القفز. قد يؤدي الاستخدام العادي للأرشيف إلى الكثير من عمليات القفز خلف الكواليس. على هذا النحو، قد تجد أن الاستخدام العادي للأرشيف مؤلم للغاية إذا تم تحميله بهذه الطريقة. خطط حسب الاقتضاء: إذا كان لديك، على سبيل المثال، ملف .zip يقوم بفك ضغط نفسه، وتريد تحميل شيء ما بداخله، فقم بضغط محتويات الأرشيف الداخلي وتأكد من أن ملف .zip الخارجي لا يضغط الأرشيف الداخلي أيضًا.

تعمل هذه الوظيفة تمامًا مثل PHYSFS_mount()، ولكنها تأخذ مقبض PHYSFS_File بدلاً من مسار اسم ملف. يحتوي هذا المقبض على جميع بيانات الأرشيف، ويتم استخدامه بدلاً من ملف حقيقي في نظام الملفات المادي. قد يعتمد PHYSFS_File على ملف حقيقي في نظام الملفات المادي، ولكنه ليس ضروريًا بالضرورة. الاستخدام الأكثر شيوعًا لهذا هو على الأرجح تحميل الأرشيفات المخزنة داخل أرشيفات أخرى.

يجب أن يكون (newDir) سلسلة فريدة لتحديد هذا الأرشيف. يتم استخدامه لتحسين اختيار الأرشيف (إذا قمت بتسميته XXXXX.zip، فقد نجرب أرشيف ZIP أولاً، على سبيل المثال، أو نختار مباشرةً أرشيفًا يمكنه فقط الوثوق بصحة البيانات عن طريق امتداد اسم الملف). لا يلزم أن يشير إلى ملف حقيقي على الإطلاق. إذا لم يكن امتداد اسم الملف مفيدًا، فسيقوم النظام بتجربة كل أرشيف حتى ينجح أحدهم أو لا يعمل أي منها. يجب أن يكون اسم الملف هذا فريدًا، حيث لن يسمح لك النظام بوجود أرشيفين بنفس الاسم.

يجب أن يظل (file) موجودًا حتى يتم إلغاء تحميل الأرشيف. عند إلغاء تحميل الأرشيف، سيقوم النظام باستدعاء PHYSFS_close(file). إذا كنت بحاجة إلى بقاء هذا المقبض، فسيتعين عليك تغليفه في PHYSFS_Io واستخدام PHYSFS_mountIo() بدلاً من ذلك.

إذا فشلت هذه الوظيفة، فلن يتم استدعاء PHYSFS_close(file).

تمكين أو تعطيل تتبع الروابط الرمزية. تحتوي بعض أنظمة الملفات المادية والأرشيفات على ملفات هي مجرد مؤشرات إلى ملفات أخرى. على نظام الملفات المادي، سيؤدي فتح مثل هذا الرابط إلى (بشكل شفاف) فتح الملف المشار إليه.

بشكل افتراضي، سيتحقق PhysicsFS مما إذا كان الملف رابطًا رمزيًا بالفعل أثناء استدعاءات الفتح وسيفشل إذا كان كذلك. وإلا، يمكن أن يأخذك الرابط خارج مسارات الكتابة والبحث، ويضر بالأمان.

إذا كنت ترغب في تحمل هذا الخطر، قم باستدعاء هذه الوظيفة بمعامل غير صفري. لاحظ أن هذا يتعلق أكثر بوضع برنامج في بيئة معزولة (sandboxing) للغة البرمجة النصية، في حالة محاولة البرامج النصية غير الموثوق بها اختراق النظام. بشكل عام، يمكن للمستخدم أن يكون لديه سبب مشروع لإنشاء رابط رمزي، لذلك ما لم تشعر بوجود خطر محدد في السماح بها، يجب عليك السماح بها.

يتم التحقق من الروابط الرمزية بشكل صريح فقط عند التعامل مع أسماء الملفات بتنسيق مستقل عن النظام الأساسي. أي، عند إعداد مسارات البحث والكتابة وما إلى ذلك، لا يتم التحقق من الروابط الرمزية مطلقًا.

int PHYSFS_utf8icmp (const char * str1, const char * str2)

Compare two UTF-8 strings case-insensitively. This is a strcasecmp/stricmp replacement that expects both strings to be in UTF-8 encoding. It will do "case folding" to decide if the Unicode codepoints in the strings match.

If both strings are exclusively low-ASCII characters, this will do the right thing, as that is also valid UTF-8. If there are any high-ASCII chars, this will not do what you expect!

It will report which string is "greater than" the other, but be aware that this doesn't necessarily mean anything: 'a' may be "less than" 'b', but a Japanese 'kuten' has no meaningful alphabetical relationship to a Greek 'lambda', but being able to assign a reliable "value" makes sorting algorithms possible, if not entirely sane. Most cases should treat the return value as "equal" or "not equal".

Like stricmp, this expects both strings to be NULL-terminated.

Parameters

str1 First string to compare.
str2 Second string to compare.

Returns

-1 if str1 is "less than" str2, 1 if "greater than", 0 if equal.

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

Convert a Latin1 string to a UTF-8 string. Latin1 strings are 8-bits per character: a popular "high ASCII" encoding.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 expands latin1 codepoints over 127 from 1 to 2 bytes, so the string may grow in some cases.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-8 sequence at the end. If the buffer length is 0, this function does nothing.

Please note that we do not supply a UTF-8 to Latin1 converter, since Latin1 can't express most Unicode codepoints. It's a legacy encoding; you should be converting away from it at all times.

Parameters

src Null-terminated source string in Latin1 format.
dst Buffer to store converted UTF-8 string.
len Size, in bytes, of destination buffer.

Detailed Description

These functions are convenience functions for writing various integer types in different endiannesses to a PHYSFS_File.

They convert the value from the platform's native byte order to the specified endianness and write it to the file handle.

The function names are structured as follows: PHYSFS_writeU(B|L)E(16|32|64)

U
Unsigned integer.
B
Big-endian byte order.
L
Little-endian byte order.
E
Specifies that the following number is the number of bits in the integer type.
16
16-bit integer.
32
32-bit integer.
64
64-bit integer.
