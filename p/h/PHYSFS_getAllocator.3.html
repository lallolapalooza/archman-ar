توقيع دالة للوظائف الإستدعائية التي تقوم بتعداد الملفات.

تحذير

منذ PhysicsFS 2.1، استخدم PHYSFS_EnumerateCallback مع PHYSFS_enumerate() بدلاً من PHYSFS_EnumFilesCallback، مما يمنحك المزيد من التحكم في العملية.

تُستخدم هذه التقارير لإبلاغ قائمة بإدخالات الدليل إلى المتصل الأصلي، إدخال واحد لكل استدعاء. جميع السلاسل مرمزة بـ UTF-8. يجب ألا تحاول الوظائف تعديل أو تحرير ذاكرة أي من السلاسل.

تُستخدم هذه الاستدعاءات، منذ PhysicsFS 1.1، كبديل للدوال التي تعيد قوائم يجب تنظيفها باستخدام PHYSFS_freeList(). يعني الاستدعاء أن المكتبة لا تحتاج إلى تخصيص قائمة كاملة وجميع السلاسل في المقدمة.

لاحظ أن ترتيب البيانات الموعود به في إصدارات القائمة ليس بالضرورة هو الحال في إصدارات الاستدعاء. تحقق من الوثائق الخاصة بواجهات برمجة التطبيقات، ولكن السلاسل لن تكون بالضرورة مرتبة كما توقعت وقد تحصل على سلاسل مكررة.

المعلمات

data مؤشر إلى بيانات مخصصة، تم تمريرها عبر واجهة برمجة التطبيقات التي استدعت في النهاية الاستدعاء.
origdir سلسلة نصية تحتوي على المسار الكامل، بتدوين مستقل عن نظام التشغيل، للدليل الذي يحتوي على هذا الملف. في معظم الحالات، هذا هو الدليل الذي طلبت التعداد فيه، وتم تمريره في الاستدعاء لراحتك.
fname اسم الملف الذي يتم إحصاؤه. قد لا يكون بترتيب أبجدي مقارنة بالاستدعاءات الأخرى التي تم تشغيلها، ولن يحتوي على المسار الكامل. يمكنك إعادة إنشاء المسار الكامل باستخدام $origdir/$fname ... قد يكون الملف دليلاً فرعياً، أو ملفاً، أو رابطاً رمزياً، إلخ.

يعيد

قيمة من PHYSFS_EnumerateCallbackResult. جميع القيم الأخرى (حالياً) غير محددة؛ لا تستخدمها.

const char * PHYSFS_getPrefDir (const char * org, const char * app)

Get the user-and-app-specific path where files can be written. Helper function.

Get the "pref dir". This is meant to be where users can write personal files (preferences and save games, etc) that are specific to your application. This directory is unique per user, per application.

This function will decide the appropriate location in the native filesystem, create the directory if necessary, and return a string in platform-dependent notation, suitable for passing to PHYSFS_setWriteDir().

(etc.)

Older versions of PhysicsFS offered only PHYSFS_getUserDir() and left you to figure out where the files should go under that tree. This finds the correct location for whatever platform, which not only changes between operating systems, but also versions of the same operating system.

You specify the name of your organization (if it's not a real organization, your name or an Internet domain you own might do) and the name of your application. These should be proper names.

  • Try to use the same org string (including case-sensitivity) for all your applications that use this function.
  • Always use a unique app string for each one, and make sure it never changes for an app once you've decided on it.
  • Unicode characters are legal, as long as it's UTF-8 encoded, but...
  • ...only use letters, numbers, and spaces. Avoid punctuation like "Game Name 2: Bad Guy's Revenge!" ... "Game Name 2" is sufficient.

You should assume the path returned by this function is the only safe place to write files (and that PHYSFS_getUserDir() and PHYSFS_getBaseDir(), while they might be writable, or even parents of the returned path, aren't where you should be writing things).

int PHYSFS_mount (const char * newDir, const char * mountPoint, int appendToPath)

Add an archive or directory to the search path. If this is a duplicate, the entry is not added again, even though the function succeeds. You may not add the same archive to two different mountpoints: duplicate checking is done against the archive and not the mountpoint.

When you mount an archive, it is added to a virtual file system...all files in all of the archives are interpolated into a single hierachical file tree. Two archives mounted at the same place (or an archive with files overlapping another mountpoint) may have overlapping files: in such a case, the file earliest in the search path is selected, and the other files are inaccessible to the application. This allows archives to be used to override previous revisions; you can use the mounting mechanism to place archives at a specific point in the file tree and prevent overlap; this is useful for downloadable mods that might trample over application data or each other, for example.

The mountpoint does not need to exist prior to mounting, which is different than those familiar with the Unix concept of "mounting" may expect. As well, more than one archive can be mounted to the same mountpoint, or mountpoints and archive contents can overlap...the interpolation mechanism still functions as usual.

Specifying a symbolic link to an archive or directory is allowed here, regardless of the state of PHYSFS_permitSymbolicLinks(). That function only deals with symlinks inside the mounted directory or archive.

تحويل سلسلة UTF-8 إلى سلسلة Latin1. سلاسل Latin1 هي 8 بت لكل حرف: ترميز "ASCII عالي" شائع.

للتأكد من أن المخزن المؤقت للوجهة كبير بما يكفي للتحويل، يرجى تخصيص مخزن مؤقت بحجم مضاعف لحجم المصدر. UTF-8 توسع رموز Latin1 الأعلى من 127 من بايت واحد إلى بايتين، لذلك يمكن أن تنمو السلسلة في بعض الحالات.

تحذير

يجب عليك تقريبًا بالتأكيد استخدام PHYSFS_utf8ToUtf16()، والتي أصبحت متاحة في PhysicsFS 2.1، ما لم تكن تعرف ما تفعله.

لن تقوم هذه الدالة بالإبلاغ عن خطأ إذا كانت هناك تسلسلات UTF-8 غير صالحة في المصدر. ستقوم باستبدالها بحرف '؟' وتستمر.

سلاسل UCS-2 هي 16 بت لكل حرف: TCHAR في Windows، عند تجميعها مع دعم Unicode. يرجى ملاحظة أن إصدارات Windows الحديثة تستخدم UTF-16، وهو شكل موسع من UCS-2، وليس UCS-2 بحد ذاته. على الأرجح تريد PHYSFS_utf8ToUtf16() في هذه الحالة، ولكنك تحتاج إلى فهم كيف يتغير هذا.

للتأكد من أن المخزن المؤقت للوجهة كبير بما يكفي للتحويل، يرجى تخصيص مخزن مؤقت بحجم مضاعف لحجم المصدر. يستخدم UTF-8 من 1 إلى 4 بايت لكل حرف، ولكن UCS-2 يستخدم دائمًا 2، لذلك سيتضاعف حجم سلسلة ASCII المنخفضة!

سيتم اقتطاع السلاسل التي لا تتناسب مع المخزن المؤقت للوجهة، ولكنها ستنتهي دائمًا بحرف null ولن تحتوي أبدًا على تسلسل UCS-2 غير مكتمل في النهاية. إذا كان حجم المخزن المؤقت 0، فلن تقوم هذه الدالة بأي شيء.

void PHYSFS_utf8ToUtf16(const char *src, PHYSFS_uint16 *dst, PHYSFS_uint64 len)

تحويل سلسلة UTF-8 إلى سلسلة UTF-16.

تحذير

لن تبلغ هذه الدالة عن خطأ إذا كانت هناك تسلسلات UTF-8 غير صالحة في السلسلة المدخلة. ستقوم باستبدالها بالحرف '؟' وستستمر.

تحتوي سلاسل UTF-16 على 16 بت لكل حرف (باستثناء بعض الأحرف، وهي 32 بت): TCHAR في Windows، عند ترجمتها مع دعم Unicode. تستخدم إصدارات Windows الحديثة UTF-16. استخدمت إصدارات Windows القديمة قبل عام 2000 TCHAR، ولكنها تعاملت فقط مع UCS-2. UTF-16 هو UCS-2، باستثناء الأحرف التي تتطلب 4 بايت، والتي لا يمكن تمثيلها بشكل صحيح في UCS-2 على الإطلاق. إذا لم تكن متأكدًا، يجب عليك استخدام UTF-16 في هذه المرحلة في Windows.

للتأكد من أن المخزن المؤقت الوجهة كبير بما يكفي للتحويل، يرجى حجز مخزن مؤقت بحجم مضاعف لحجم المخزن المؤقت المدخل. يستخدم UTF-8 من بايت واحد إلى أربعة بايتات لكل حرف، ولكن UTF-16 يستخدم دائمًا من اثنين إلى أربعة بايتات، لذلك سيتضاعف حجم السلسلة ASCII بالكامل. الأحرف UTF-16 التي ستستغرق أربعة بايتات ستستغرق أيضًا أربعة بايتات في UTF-8، لذلك لا تحتاج إلى حجز مساحة مضاعفة في حالة الخطأ.

سيتم اقتطاع السلاسل التي لا تتناسب مع المخزن المؤقت الوجهة، ولكن سيتم دائمًا إنهاؤها بحرف فارغ ولن تحتوي أبدًا على زوج مستورد غير مكتمل في النهاية. إذا كان حجم المخزن المؤقت صفرًا، فلن تقوم هذه الدالة بأي شيء.
