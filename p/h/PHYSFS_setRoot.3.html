على عكس PHYSFS_enumerateFiles()، لا تعيد هذه الدالة مصفوفة. بدلاً من ذلك، تستدعي دالة يحددها التطبيق مرة واحدة لكل عنصر في مسار البحث:

العناصر التي يتم تمريرها إلى دالة رد النداء ليست مضمونة أن تكون بترتيب معين. لا يتم إجراء أي فرز على هذا المستوى، وإذا كنت بحاجة إلى ذلك، يجب عليك استخدام PHYSFS_enumerateFiles()، والتي تضمن الترتيب الأبجدي. هذا الشكل يبلغ عن ما تم العثور عليه في كل أرشيف قبل الانتقال إلى التالي. حتى داخل أرشيف واحد، لا يمكننا ضمان الترتيب الذي سيتم به اكتشاف البيانات. أي ترتيب يتم العثور عليه في دوال رد النداء هذه هو محض صدفة. لا تعتمد عليه. نظرًا لأن هذه الدالة تتجول في قائمة الملفات بأكملها، قد تتلقى أسماء ملفات مكررة.

يمكن لواجهة برمجة التطبيقات هذه ودوال رد النداء نفسها الإبلاغ عن الأخطاء. قبل واجهة برمجة التطبيقات هذه، كان على دوال رد النداء قبول كل عنصر تم عده، حتى لو كانت تبحث فقط عن عنصر معين وتريد التوقف بعده، أو كان بها خطأ جسيم ولم تتمكن من إبلاغ أي شخص. علاوة على ذلك، إذا كان لدى PhysicsFS نفسه مشكلة (خطأ في القرص أو ما شابه)، فلن يتمكن من إبلاغ التطبيق، بل يمكنه ببساطة الانتقال إلى العنصر التالي أو إيقاف التعداد، ولن يعرف المستدعي أنه فقد بعض البيانات أثناء المسار.

الآن يمكن للمستدعي التأكد من أنه قد حصل على مجموعة كاملة من البيانات، وإذا أراد، فإن دالة رد النداء الخاصة به تتحكم في ما إذا كان سيتم إيقاف التعداد مبكرًا. راجع توثيق PHYSFS_EnumerateCallback للحصول على تفاصيل حول كيفية سلوك دالة رد النداء الخاصة بك.

اعتبارًا من PhysicsFS 2.1، تم إضعاف هذه الوظيفة. قبل PhysicsFS 2.1، كانت هذه الوظيفة هي الطريقة الوحيدة للحصول على تفاصيل الخطأ بخلاف القيمة الأساسية التي تعيدها الوظيفة. كان من المفترض أن تكون هذه سلسلة نصية سهلة القراءة بإحدى لغات متعددة، ولم تكن مفيدة لتحليل التطبيق. كان هذا مشكلة، لأن المطور وليس المستخدم هو من يختار اللغة وقت الترجمة، وكان على مشرفي PhysicsFS (بشكل سيء) الحفاظ على قدر كبير من عمل التوطين. لم يتمكن التطبيق من تحليل السلاسل النصية، حتى لو اعتمد على لغة معينة، حيث تم إنشاء بعضها ديناميكيًا. في الإصدار 2.1 وما بعده، تعيد هذه الوظيفة دائمًا سلسلة نصية ثابتة باللغة الإنجليزية؛ يمكنك استخدامها كسلسلة مفتاح لتوطينك الخاص إذا أردت، حيث سنعد بعدم تغيير سلاسل الأخطاء الحالية. أيضًا، إذا أراد تطبيقك الاطلاع على أخطاء محددة، فإننا نقدم الآن خيارًا أفضل: استخدم PHYSFS_getLastErrorCode() بدلاً من ذلك.

الحصول على آخر رسالة خطأ PhysicsFS كسلسلة نصية سهلة القراءة ومنتهية بـ NULL. سيعيد هذا NULL إذا لم يكن هناك خطأ منذ آخر استدعاء لهذه الوظيفة. يشير المؤشر الذي أعادته هذه المكالمة إلى مخزن مؤقت داخلي. لكل خيط حالة خطأ فريدة مرتبطة به، ولكن في كل مرة يتم فيها تعيين رسالة خطأ جديدة، فإنها ستحل محل الرسالة السابقة المرتبطة بهذا الخيط. من الآمن استدعاء هذه الوظيفة في أي وقت، حتى قبل PHYSFS_init().

تقوم كل من PHYSFS_getLastError() و PHYSFS_getLastErrorCode() بإعادة تعيين نفس حالة الخطأ الخاصة بالخيط. استدعاء إحداهما سيمحو بيانات الأخرى. إذا كنت بحاجة إلى كليهما، استدعِ PHYSFS_getLastErrorCode()، ثم مرر تلك القيمة إلى PHYSFS_getErrorByCode().

اعتبارًا من PhysicsFS 2.1، تقدم هذه الوظيفة النص باللغة الإنجليزية فقط، ولكن السلاسل النصية ثابتة، لذلك يمكنك استخدامها كمفاتيح في قاموس التوطين الخاص بك. تهدف هذه السلاسل النصية إلى تمريرها مباشرة إلى المستخدم.

بشكل عام، يجب على التطبيقات الاهتمام فقط بما إذا كانت وظيفة معينة قد فشلت؛ ومع ذلك، إذا كان كودك يتطلب تفاصيل أكثر تحديدًا، فيجب عليك استخدام PHYSFS_getLastErrorCode() بدلاً من هذه الوظيفة.

const char * PHYSFS_getPrefDir (const char * org, const char * app)

Get the user-and-app-specific path where files can be written. Helper function.

Get the "pref dir". This is meant to be where users can write personal files (preferences and save games, etc) that are specific to your application. This directory is unique per user, per application.

This function will decide the appropriate location in the native filesystem, create the directory if necessary, and return a string in platform-dependent notation, suitable for passing to PHYSFS_setWriteDir().

On Windows, this might look like: "C:\\Users\\bob\\AppData\\Roaming\\My Company\\My Program Name"

On Linux, this might look like: "/home/bob/.local/share/My Program Name"

On Mac OS X, this might look like: "/Users/bob/Library/Application Support/My Program Name"

(etc.)

You should probably use the pref dir for your write dir, and also put it near the beginning of your search path. Older versions of PhysicsFS offered only PHYSFS_getUserDir() and left you to figure out where the files should go under that tree. This finds the correct location for whatever platform, which not only changes between operating systems, but also versions of the same operating system.

You specify the name of your organization (if it's not a real organization, your name or an Internet domain you own might do) and the name of your application. These should be proper names.

Both the (org) and (app) strings may become part of a directory name, so please follow these rules:

  • Try to use the same org string (including case-sensitivity) for all your applications that use this function.
  • Always use a unique app string for each one, and make sure it never changes for an app once you've decided on it.
  • Unicode characters are legal, as long as it's UTF-8 encoded, but...
  • ...only use letters, numbers, and spaces. Avoid punctuation like "Game Name 2: Bad Guy's Revenge!" ... "Game Name 2" is sufficient.

The pointer returned by this function remains valid until you call this function again, or call PHYSFS_deinit(). This is not necessarily a fast call, though, so you should call this once at startup and copy the string if you need it.

You should assume the path returned by this function is the only safe place to write files (and that PHYSFS_getUserDir() and PHYSFS_getBaseDir(), while they might be writable, or even parents of the returned path, aren't where you should be writing things).

Parameters

org The name of your organization.
app The name of your application.

Returns

const char * PHYSFS_getRealDir (const char * filename)

Figure out where in the search path a file resides. The file is specified in platform-independent notation. The returned filename will be the element of the search path where the file was found, which may be a directory, or an archive. Even if there are multiple matches in different parts of the search path, only the first one found is used, just like when opening a file.

So, if you look for "maps/level1.map", and C:\mygame is in your search path and C:\mygame\maps\level1.map exists, then "C:\mygame" is returned.

If a any part of a match is a symbolic link, and you've not explicitly permitted symlinks, then it will be ignored, and the search for a match will continue.

If you specify a fake directory that only exists as a mount point, it'll be associated with the first archive mounted there, even though that directory isn't necessarily contained in a real archive.

filename file to look for.

READ ONLY string of element of search path containing the the file in question. NULL if not found.

يتم فحص الروابط الرمزية بشكل صريح فقط عند التعامل مع أسماء الملفات بتنسيق غير مستقل عن المنصة. وهذا يعني، عند إعداد مسارات البحث والكتابة الخاصة بك، وما إلى ذلك، لا يتم فحص الروابط الرمزية مطلقًا.

يمكن تمكين أو تعطيل إذن الروابط الرمزية في أي وقت بعد استدعاء PHYSFS_init()، ويتم تعطيله افتراضيًا.

void PHYSFS_setBuffer(PHYSFS_File *handle, size_t bufsize)

Set the buffer size for an open file handle. This affects read and write operations performed through this handle. If you set the buffer size to zero, the buffer is freed and all writes are flushed.

The default buffer size is 32768 bytes (32KiB).

When changing the buffer size, if the new size is smaller than the old size, the buffer will be flushed first. This implicitly causes a flush...check your return values!

Seeking, etc transparently accounts for buffering.

You can resize an existing buffer by calling this function more than once on the same file. Setting the buffer size to zero will free an existing buffer.

PhysicsFS file handles are unbuffered by default.

Please check the return value of this function! Failures can include not being able to seek backwards in a read-only file when removing the buffer, not being able to allocate the buffer, and not being able to flush the buffer to disk, among other unexpected problems.

int PHYSFS_setRoot(const char *archive, const char *subdir)

Make a subdirectory of an archive its root directory. This lets you narrow down the accessible files in a specific archive. For example, if you have x.zip with a file in y/z.txt, mounted to /a, if you call PHYSFS_setRoot("x.zip", "/y"), then the call PHYSFS_openRead("/a/z.txt") will succeed.

You can change an archive's root at any time, altering the interpolated file tree (depending on where paths shift, a different archive may be providing various files). If you set the root to NULL or "/" , the archive will be treated as if no special root was set (as if the archive was just mounted normally).

Changing the root only affects future operations on pathnames; a file that was opened from a path that changed due to a setRoot will not be affected.

Setting a new root is not limited to archives in the search path; you may set one on the write dir, too, which might be useful if you have files open for write and thus can't change the write dir at the moment.

It is not an error to set a subdirectory that does not exist to be the root of an archive; however, no files will be visible in this case. If the missing directories end up getting created (a mkdir to the physical filesystem, etc) then this will be reflected in the interpolated tree.

Advertencia

Esta función no reportará un error si hay secuencias de UTF-8 inválidas en la cadena de origen. Reemplazará estas con un carácter '?' y continuará.

Las cadenas de UTF-32 tienen 32 bits por carácter. Advertencia

Esta función no reportará un error si hay secuencias de UTF-8 inválidas en la cadena de origen. Reemplazará estas con un carácter '?' y continuará.

Las cadenas que no se ajustan al buffer de destino se truncarán, pero siempre serán nulas-terminadas y nunca tendrán una paréntesis de surroupe incompleto al final. Si el largo del buffer es 0, esta función no hace nada.

Detailed Description

These functions convert an integer value from the platform's native byte order to a specified endianness and write it to the given PhysicsFS file handle.

All functions return zero on failure, non-zero on success. If a function fails, you can query the error code using PHYSFS_getLastErrorCode.

The BE functions write in big-endian format. The LE functions write in little-endian format.

The U prefix indicates unsigned integers (e.g., PHYSFS_writeUBE16 writes an unsigned 16-bit big-endian integer).

The 64 suffix indicates 64-bit integers. Note that on platforms without native 64-bit support, PHYSFS_uint64 might only be 32 bits wide, potentially leading to data truncation.

These are convenience functions. For more direct control over writing, you might use PHYSFS_write.

file PhysicsFS file handle to which to write.
val Value to convert and write.

Returns

zero on failure, non-zero on success. On failure, you can find out what went wrong from PHYSFS_getLastErrorCode().

Warning

Remember, PHYSFS_uint64 is only 32 bits on platforms without any sort of 64-bit support.
