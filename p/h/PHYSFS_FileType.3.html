توثيق تعريفات الماكرو

#define PHYSFS_file PHYSFS_File

تعريف توافق API 1.0. PHYSFS_file مطابق لـ PHYSFS_File. هذا #define موجود للتوافق مع الإصدارات السابقة مع واجهة برمجة التطبيقات 1.0، التي كانت لها اتفاقية كتابة غير متناسقة في هذه الحالة. يجب أن تستخدم التعليمات البرمجية الجديدة PHYSFS_File، حيث قد يختفي هذا #define في يوم من الأيام.

Deinitialize the PhysicsFS library. This closes any files opened via PhysicsFS, blanks the search/write paths, frees memory, and invalidates all of your file handles.

int PHYSFS_delete(const char *filename)

Delete a file or directory. (filename) is specified in platform-independent notation in relation to the write dir.

A directory must be empty before this call can delete it.

Deleting a symlink will remove the link, not what it points to, regardless of whether you "permitSymLinks" or not.

So if you've got the write dir set to "C:\mygame\writedir" and call PHYSFS_delete("downloads/maps/level1.map") then the file "C:\mygame\writedir\downloads\maps\level1.map" is removed from the physical filesystem, if it exists and the operating system permits the deletion.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

Get a file listing of a search path's directory, using an application-defined callback, with errors reported. Internally, PHYSFS_enumerateFiles() just calls this function and then builds a list before returning to the application, so functionality is identical except for how the information is represented to the application.

Unlike PHYSFS_enumerateFiles(), this function does not return an array. Rather, it calls a function specified by the application once per element of the search path:

static PHYSFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // give me more data, please.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

Items sent to the callback are not guaranteed to be in any order whatsoever. There is no sorting done at this level, and if you need that, you should probably use PHYSFS_enumerateFiles() instead, which guarantees alphabetical sorting. This form reports whatever is discovered in each archive before moving on to the next. Even within one archive, we can't guarantee what order it will discover data. Any sorting you find in these callbacks is just pure luck. Do not rely on it. As this walks the entire list of archives, you may receive duplicate filenames.

This API and the callbacks themselves are capable of reporting errors. Prior to this API, callbacks had to accept every enumerated item, even if they were only looking for a specific thing and wanted to stop after that, or had a serious error and couldn't alert anyone. Furthermore, if PhysicsFS itself had a problem (disk error or whatnot), it couldn't report it to the calling app, it would just have to skip items or stop enumerating outright, and the caller wouldn't know it had lost some data along the way.

Now the caller can be sure it got a complete data set, and its callback has control if it wants enumeration to stop early. See the documentation for PHYSFS_EnumerateCallback for details on how your callback should behave.

Parameters

dir Directory, in platform-independent notation, to enumerate.
c Callback function to notify about search path elements.
d Application-defined data passed to callback. Can be NULL.

Returns

non-zero on success, zero on failure. Use PHYSFS_getLastErrorCode() to obtain the specific error. If the callback returns PHYSFS_ENUM_STOP to stop early, this will be considered success. Callbacks returning PHYSFS_ENUM_ERROR will make this function return zero and set the error code to PHYSFS_ERR_APP_CALLBACK.

تحذير

const char *physFS_getPrefDir (const char * org, const char * app)

Obtener la ruta de directorio específica para donde los archivos se pueden escribir. Función de ayuda.

Obtener el "pref dir". Este es para donde los usuarios pueden escribir archivos personales (preferencias y juegos salvados, etc) específicos de su aplicación. Este directorio es único por usuario y por aplicación.

Esta función decide la ubicación adecuada en el sistema de archivos nativo, crea el directorio si necesario y devuelve una cadena en notación del sistema operativo, adecuada para pasar a PHYSFS_setWriteDir().

En Windows, esto podría ser: "C:\\Users\\bob\\AppData\\Roaming\\My Company\\My Program Name"

En Linux, esto podría ser: "/home/bob/.local/share/My Program Name"

En Mac OS X, esto podría ser: "/Users/bob/Library/Application Support/My Program Name"

(etc.)

Deberías usar el pref dir para tu ruta de escritura, y también colocarlo cerca del principio de tu ruta de búsqueda. Versión antiguas de PhysicsFS ofrecían solo PHYSFS_getUserDir() y dejaban a ti determinar dónde los archivos deberían estar bajo ese árbol. Esta encuentra la ubicación correcta para cualquier plataforma, que no solo cambia entre sistemas operativos, sino también entre versiones del mismo sistema operativo.

Especifícalo el nombre de tu organización (si no es una organización real, tu nombre o un dominio Internet que tienes podrían hacerlo) y el nombre de tu aplicación. Estos deberían ser nombres correctos.

Ambos los (org) y (app) pueden convertirse en parte de un nombre de directorio, así que por favor sigue estas reglas:

  • Intenta usar el mismo string de organización (incluyendo el caso sensible) para todas tus aplicaciones que usen esta función.
  • Usa siempre un string único para cada aplicación, y asegúrate de que no cambie para una aplicación una vez que lo hayas decidido.
  • Caracteres Unicode son válidos, siempre que estén codificados como UTF-8, pero...
  • ...solo usen letras, números y espacios. Evite caracteres como "Game Name 2: Bad Guy's Revenge!" ... "Game Name 2" es suficiente.

El puntero devuelto por esta función permanece válido hasta que lo llames otra vez o llames PHYSFS_deinit(). Aunque no es rápido, debes llamarlo una vez al iniciar y copia la cadena si la necesitas.

Debes asumir que la ruta devuelta por esta función es la única ubicación segura para escribir archivos (y que PHYSFS_getUserDir() y PHYSFS_getBaseDir(), aunque puedan ser escritos, o incluso padres de la ruta devuelta, no son donde debes escribir).

org nombre de tu organización.
app nombre de tu aplicación.

cadena SOLO de directorio de usuario en notación del sistema operativo. NULL si hay un problema (creación del directorio falló, etc).

const char *physFS_getRealDir (const char * filename)

Determinar dónde se encuentra un archivo en la ruta de búsqueda. El archivo se especifica en notación independiente del sistema operativo. filename archivo a buscar.

cadena SOLO de elemento de la ruta de búsqueda que contiene el archivo en cuestión. NULL si no se encuentra.

(newDir) يجب أن يكون سلسلة فريدة لتحديد هذا الأرشيف. يتم استخدامه لتحسين اختيار الأرشيف (إذا قمت بتسميته XXXXX.zip، فقد نحاول أولاً أرشيف ZIP، على سبيل المثال، أو نختار مباشرة أرشيفًا يمكنه الوثوق فقط بأن البيانات صالحة عن طريق امتداد اسم الملف). لا يحتاج إلى الإشارة إلى ملف حقيقي على الإطلاق. إذا لم يكن امتداد اسم الملف مفيدًا، فسيقوم النظام بتجربة كل أرشيف حتى يعمل أحدهم أو لا يعمل أي منهم. يجب أن يكون اسم الملف هذا فريدًا، حيث لن يسمح لك النظام بوجود أرشيفين بنفس الاسم.

(file) يجب أن تبقى حتى يتم إلغاء تحميل الأرشيف. عند إلغاء تحميل الأرشيف، ستقوم الدالة باستدعاء PHYSFS_close(file). إذا كنت بحاجة إلى بقاء هذه الواجهة، فسيتعين عليك تغليفها في PHYSFS_Io واستخدام PHYSFS_mountIo() بدلاً من ذلك.

إذا فشلت هذه الدالة، فلن يتم استدعاء PHYSFS_close(file).

Warning

This is advanced, hardcore stuff. You don't need this unless you really know what you're doing. Most apps will not need this.

Hook your own allocation routines into PhysicsFS. (This is for limited, hardcore use. If you don't immediately see a need for it, you can probably ignore this forever.)

By default, PhysicsFS will use whatever is reasonable for a platform to manage dynamic memory (usually ANSI C malloc/realloc/free, but some platforms might use something else), but in some uncommon cases, the app might want more control over the library's memory management. Set up buffering for a PhysicsFS file handle. Define an i/o buffer for a file handle. A memory block of (bufsize) bytes will be allocated and associated with (handle).

For files opened for reading, up to (bufsize) bytes are read from (handle) and stored in the internal buffer. Note that compressed files, like ZIP archives, will decompress while buffering, so this can be handy for offsetting CPU-intensive operations. The buffer isn't filled until you do your next read.

int PHYSFS_ucs4stricmp (const PHYSFS_uint32 * str1, const PHYSFS_uint32 * str2)

مقارنة سلسلتين من 4 بايتات بتنسيق UCS-4 بدون حساسية لحالة الأحرف. هذا بديل لـ strcasecmp/stricmp والذي يتوقع أن تكون السلاسل النصية بتنسيق UCS-4 (المعروف أيضًا باسم UTF-32). يقوم بإجراء "طي للحالة" لتحديد ما إذا كانت رموز Unicode في السلاسل متساوية.

يعيد أي سلسلة نصية "أكبر" من الأخرى، ولكن تذكر أن هذا لا يعني بالضرورة شيئًا: قد يكون 'a' "أصغر" من 'b'، ولكن لا توجد علاقة ذات مغزى بين حرف ياباني وحرف يوناني فيما يتعلق بالترتيب الأبجدي. ومع ذلك، فإن تعيين قيمة موثوقة يسمح لخوارزميات الفرز بالعمل، حتى لو لم تكن منطقية تمامًا. في معظم الحالات، يجب معاملة القيمة المرتجعة على أنها "متساوية" أو "غير متساوية".

مثل stricmp، يتوقع أن تكون كلا السلسلتين منتهيتين بـ NULL.

المعلمات

str1 السلسلة الأولى للمقارنة.
str2 السلسلة الثانية للمقارنة.

المرتجعات

-1 إذا كانت str1 "أصغر" من str2، 1 إذا كانت str1 "أكبر" من str2، 0 إذا كانت متساوية.

void PHYSFS_utf8FromLatin1 (const char * src, char * dst, PHYSFS_uint64 len)

تحويل سلسلة UTF-8 إلى سلسلة Latin1. سلاسل Latin1 تحتوي كل حرف فيها على 8 بت: ترميز "مرتفع ASCII" شائع.

لضمان أن يكون المخزن المؤقت الوجهة كبيرًا بما يكفي للتحويل، يرجى تخصيص مخزن مؤقت بحجم ضعف حجم المخزن المؤقت المصدر. UTF-8 يوسع رموز Latin1 التي تتجاوز 127 من 1 إلى 2 بايت، لذلك يمكن أن تنمو السلسلة في بعض الحالات.

السلاسل التي لا تتناسب مع المخزن المؤقت الوجهة سيتم قصها، ولكنها ستنتهي دائمًا بحرف صفري ولن تحتوي أبدًا على تسلسل UTF-8 غير مكتمل في النهاية. إذا كان طول المخزن المؤقت 0، فلن تقوم هذه الدالة بأي شيء.

ملاحظة: لا نقدم محولًا من UTF-8 إلى Latin1، لأن Latin1 لا يمكنه التعبير عن العديد من رموز Unicode. إنه ترميز قديم؛ يجب عليك التحويل منه في جميع الأوقات.

المعلمات

src سلسلة المصدر بكل تنسيق Latin1، منتهية بحرف صفري.
dst المخزن المؤقت لتخزين السلسلة المحولة UTF-8.
len حجم المخزن المؤقت الوجهة بالبايت.

void PHYSFS_utf8ToUtf16 (const char * src, PHYSFS_uint16 * dst, PHYSFS_uint64 len)

Convert a UTF-8 string to a UTF-16 string.

Warning

This function will not report an error if there are invalid UTF-8 sequences in the source string. It will replace them with a '?' character and continue on.

UTF-16 strings are 16-bits per character (except some chars, which are 32-bits): TCHAR on Windows, when building with Unicode support. Modern Windows releases use UTF-16. Windows releases before 2000 used TCHAR, but only handled UCS-2. UTF-16 is UCS-2, except for the characters that are 4 bytes, which aren't representable in UCS-2 at all anyhow. If you aren't sure, you should be using UTF-16 at this point on Windows.

To ensure that the destination buffer is large enough for the conversion, please allocate a buffer that is double the size of the source buffer. UTF-8 uses from one to four bytes per character, but UTF-16 always uses two to four, so an entirely low-ASCII string will double in size! The UTF-16 characters that would take four bytes also take four bytes in UTF-8, so you don't need to allocate 4x the space just in case: double will do.

Strings that don't fit in the destination buffer will be truncated, but will always be null-terminated and never have an incomplete UTF-16 surrogate pair at the end. If the buffer length is 0, this function does nothing.

Parameters

src Null-terminated source string in UTF-8 format.
dst Buffer to store converted UTF-16 string.
len Size, in bytes, of destination buffer.

PHYSFS_sint64 PHYSFS_writeBytes (PHYSFS_File * handle, const void * buffer, PHYSFS_uint64 len)

Write data to a PhysicsFS filehandle. The file must be opened for writing.

Please note that while (len) is an unsigned 64-bit integer, you are limited to 63 bits (9223372036854775807 bytes), so we can return a negative value on error. If length is greater than 0x7FFFFFFFFFFFFFFF, this function will immediately fail. For systems without a 64-bit datatype, you are limited to 31 bits (0x7FFFFFFF, or 2147483647 bytes). We trust most things won't need to do multiple gigabytes of i/o in one call anyhow, but why limit things?

Parameters

handle retval from PHYSFS_openWrite() or PHYSFS_openAppend().
buffer buffer of (len) bytes to write to (handle).
len number of bytes being written to (handle).

Returns

number of bytes written. This may be less than (len); in the case of an error, the system may try to write as many bytes as possible, so an incomplete write might occur. PHYSFS_getLastErrorCode() can shed light on the reason this might be < (len). -1 if complete failure.
