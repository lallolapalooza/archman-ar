Function signature for callbacks that enumerate files.

Warning

As of PhysicsFS 2.1, Use PHYSFS_EnumerateCallback with PHYSFS_enumerate() instead; it gives you more control over the process.

These are used to report a list of directory entries to an original caller, one file/dir/symlink per callback. All strings are UTF-8 encoded. Functions should not try to modify or free any string's memory.

These callbacks are used, starting in PhysicsFS 1.1, as an alternative to functions that would return lists that need to be cleaned up with PHYSFS_freeList(). The callback means that the library doesn't need to allocate an entire list and all the strings up front.

Be aware that promised data ordering in the list versions are not necessarily so in the callback versions. Check the documentation on specific APIs, but strings may not be sorted as you expect and you might get duplicate strings.

int PHYSFS_enumerate (const char * dir, PHYSFS_EnumerateCallback c, void * d)

الحصول على قائمة بملفات دليل من مسار بحث، باستخدام دالة استدعاء محددة من قبل المستخدم، مع تقارير الأخطاء. داخليًا، PHYSFS_enumerateFiles() تستدعي هذه الدالة ببساطة ثم تبني قائمة قبل إعادتها للتطبيق، لذا فإن الوظيفة متطابقة، لكن تمثيل المعلومات للتطبيق مختلف.

على عكس PHYSFS_enumerateFiles()، هذه الدالة لا تعيد مصفوفة. بدلًا من ذلك، تستدعي دالة محددة من قبل المستخدم مرة واحدة لكل عنصر في مسار البحث:

static physFS_EnumerateCallbackResult printDir(void *data, const char *origdir, const char *fname)
{
    printf(" * We've got [%s] in [%s].\n", fname, origdir);
    return PHYSFS_ENUM_OK;  // أعطني المزيد من البيانات، من فضلك.
}
// ...
PHYSFS_enumerate("/some/path", printDir, NULL);

العناصر التي يتم إرسالها إلى دالة الاستدعاء ليست مضمونة لتكون بأي ترتيب محدد. لا يتم إجراء أي فرز على هذا المستوى، وإذا كنت بحاجة إليه، يجب عليك استخدام PHYSFS_enumerateFiles()، التي تضمن الترتيب الأبجدي. هذا الشكل يبلغ عن ما يتم اكتشافه في كل ملف مؤرشف قبل الانتقال إلى الملف التالي. حتى داخل أرشيف واحد، لا يمكننا ضمان ترتيب اكتشاف البيانات. أي فرز تجده في دوال الاستدعاء هذه هو مجرد حظ. لا تعتمد عليه. نظرًا لأن هذه الدالة تمر عبر قائمة الملفات بأكملها، فقد تتلقى أسماء ملفات مكررة.

هذه الواجهة البرمجية ودوال الاستدعاء نفسها قادرة على الإبلاغ عن الأخطاء. قبل هذه الواجهة البرمجية، كان على دوال الاستدعاء قبول كل عنصر تم تعداده، حتى لو كانوا يبحثون فقط عن عنصر معين ويريدون التوقف بعد ذلك، أو كان لديهم خطأ جسيم ولم يتمكنوا من إبلاغ أي شخص. علاوة على ذلك، إذا كانت PhysicsFS نفسها لديها مشكلة (خطأ في القرص أو ما شابه)، لم يكن بإمكانها إبلاغ التطبيق المتصل، بل كان عليها فقط تخطي العناصر أو إيقاف التعداد بالكامل، ولن يعرف المتصل أنه فقد بيانات في الطريق.

الآن يمكن للمتصل التأكد من أنه حصل على مجموعة كاملة من البيانات، وإذا أراد إيقاف التعداد مبكرًا، فإن دالة الاستدعاء الخاصة به تتحكم في ذلك. انظر إلى وثائق PHYSFS_EnumerateCallback للحصول على تفاصيل حول كيفية سلوك دالة الاستدعاء الخاصة بك.

المعلمات

dir الدليل، بتدوين مستقل عن النظام الأساسي، لتعداد محتوياته.
c دالة الاستدعاء للإبلاغ عن عناصر مسار البحث.
d بيانات محددة من قبل التطبيق يتم تمريرها إلى دالة الاستدعاء. يمكن أن تكون NULL.

القيمة المعادة

غير صفر عند النجاح، صفر عند الفشل. استخدم PHYSFS_getLastErrorCode() للحصول على الخطأ المحدد. إذا أعادت دالة الاستدعاء PHYSFS_ENUM_STOP، فسيتم اعتبار ذلك نجاحًا. دوال الاستدعاء التي تعيد PHYSFS_ENUM_ERROR ستجعل هذه الدالة تعيد صفرًا وتعيين رمز الخطأ إلى PHYSFS_ERR_APP_CALLBACK.

تحذير

في إصدارات PhysicsFS قبل 2.1، كانت هذه الدالة تعيد أكبر عدد ممكن من العناصر في حالة حدوث فشل (خطأ في الذاكرة، خطأ في قراءة القرص، إلخ). نظرًا لأن هذا يعني أن التطبيقات لم تتمكن من التمييز بين النجاح الكامل والفشل الجزئي، وبما أن الدالة يمكن أن تعيد NULL للإبلاغ عن فشل كارثي، فقد تغيرت هذه السياسة في PhysicsFS 2.1: ستعيد قائمة كاملة بالنتائج أو ستعيد NULL في حالة حدوث أي فشل، حتى نتمكن من ضمان اكتمال التعداد وأنه لا توجد فجوات في نتائجك.

يتم استيفاء الدلائل المتطابقة. أي، إذا كان "C:\mydir" في مسار البحث ويحتوي على دليل "savegames" يحتوي على "x.sav" و "y.sav" و "z.sav"، وهناك أيضًا "C:\userdir" في مسار البحث الذي يحتوي على دليل "savegames" مع "w.sav"، فإن الكود التالي:

char **rc = PHYSFS_enumerateFiles("savegames");
char **i;
for (i = rc; *i != NULL; i++)
    printf(" * We've got [%s].\n", *i);
PHYSFS_freeList(rc);
* We've got [x.sav].
* We've got [y.sav].
* We've got [z.sav].
* We've got [w.sav]..fi
لا تتردد في فرز القائمة كيفما تشاء. ومع ذلك، فإن البيانات المعادة لن تحتوي أبدًا على مكررات، وسيتم دائمًا فرزها أبجديًا (أو بالأحرى، بترتيب Unicode حساس لحالة الأحرف) لك.
لا تنس استدعاء PHYSFS_freeList() مع القيمة المعادة من هذه الدالة عندما تنتهي منها.

const char * PHYSFS_getPrefDir(const char *org, const char *app)

Get the user-and-app-specific path where files can be written. Helper function.

Get the "pref dir". This is meant to be where users can write personal files (preferences and save games, etc) that are specific to your application. This directory is unique per user, per application.

This function will decide the appropriate location in the native filesystem, create the directory if necessary, and return a string in platform-dependent notation, suitable for passing to PHYSFS_setWriteDir().

On Windows, this might look like: "C:\\Users\\bob\\AppData\\Roaming\\My Company\\My Program Name"

On Linux, this might look like: "/home/bob/.local/share/My Program Name"

On Mac OS X, this might look like: "/Users/bob/Library/Application Support/My Program Name"

(etc.)

You should probably use the pref dir for your write dir, and also put it near the beginning of your search path. Older versions of PhysicsFS offered only PHYSFS_getUserDir() and left you to figure out where the files should go under that tree. This finds the correct location for whatever platform, which not only changes between operating systems, but also versions of the same operating system.

You specify the name of your organization (if it's not a real organization, your name or an Internet domain you own might do) and the name of your application. These should be proper names.

Both the (org) and (app) strings may become part of a directory name, so please follow these rules:

  • Try to use the same org string (including case-sensitivity) for all your applications that use this function.
  • Always use a unique app string for each one, and make sure it never changes for an app once you've decided on it.
  • Unicode characters are legal, as long as it's UTF-8 encoded, but...
  • ...only use letters, numbers, and spaces. Avoid punctuation like "Game Name 2: Bad Guy's Revenge!" ... "Game Name 2" is sufficient.

The pointer returned by this function remains valid until you call this function again, or call PHYSFS_deinit(). This is not necessarily a fast call, though, so you should call this once at startup and copy the string if you need it.

You should assume the path returned by this function is the only safe place to write files (and that PHYSFS_getUserDir() and PHYSFS_getBaseDir(), while they might be writable, or even parents of the returned path, aren't where you should be writing things).

const char * PHYSFS_getRealDir(const char *filename)

Figure out where in the search path a file resides. The file is specified in platform-independent notation. The returned filename will be the element of the search path where the file was found, which may be a directory, or an archive. Even if there are multiple matches in different parts of the search path, only the first one found is used, just like when opening a file.

So, if you look for "maps/level1.map", and C:\mygame is in your search path and C:\mygame\maps\level1.map exists, then "C:\mygame" is returned.

If a any part of a match is a symbolic link, and you've not explicitly permitted symlinks, then it will be ignored, and the search for a match will continue.

If you specify a fake directory that only exists as a mount point, it'll be associated with the first archive mounted there, even though that directory isn't necessarily contained in a real archive.

Warning

This will return NULL if there is no real directory associated with (filename). Specifically, PHYSFS_mountIo(), PHYSFS_mountMemory(), and PHYSFS_mountHandle() will return NULL even if the filename is found in the search path. Plan accordingly.

filename file to look for.

Returns

READ ONLY string of element of search path containing the the file in question. NULL if not found.

void PHYSFS_utf8ToUtf16 (const char * src, PHYSFS_uint16 * dst, PHYSFS_uint64 len)

تحويل سلسلة UTF-8 إلى سلسلة UTF-16.

تحذير

لن تقوم هذه الدالة بالإبلاغ عن خطأ إذا كانت هناك تسلسلات UTF-8 غير صالحة في سلسلة الإدخال. ستقوم باستبدال هذه التسلسلات بالحرف '؟' وتستمر.

تحتوي سلاسل UTF-16 على 16 بت لكل حرف (باستثناء بعض الأحرف، التي تبلغ 32 بت): TCHAR في Windows، عند استخدام دعم Unicode. تستخدم إصدارات Windows الحديثة UTF-16. استخدمت إصدارات Windows القديمة قبل عام 2000 TCHAR، ولكنها تعاملت فقط مع UCS-2. UTF-16 هو UCS-2، باستثناء الأحرف التي تبلغ 4 بايت، والتي لا يمكن تمثيلها بالكامل في UCS-2. إذا لم تكن متأكدًا، فيجب عليك استخدام UTF-16 في Windows الآن.

للتأكد من أن المخزن المؤقت للوجهة كبير بما يكفي للتحويل، يرجى تخصيص مخزن مؤقت يكون ضعف حجم المخزن المؤقت للإدخال. يستخدم UTF-8 من 1 إلى 4 بايت لكل حرف، ولكن UTF-16 يستخدم دائمًا من 2 إلى 4 بايت، لذلك سيتم مضاعفة حجم سلسلة ASCII المنخفضة تمامًا. تتطلب أحرف UTF-16 التي تحتاج إلى 4 بايت أيضًا 4 بايت في UTF-8، لذلك لا تحتاج إلى تخصيص 4 أضعاف المساحة، فقط مضاعفتها.

سيتم اقتطاع السلاسل التي لا تتناسب مع المخزن المؤقت للوجهة، ولكن سيتم دائمًا إنهاؤها بحرف فارغ ولن تحتوي أبدًا على زوج بديل غير مكتمل في النهاية. إذا كان طول المخزن المؤقت 0، فلن تقوم هذه الدالة بأي شيء.
