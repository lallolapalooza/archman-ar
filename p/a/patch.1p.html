المخرج القياسي

غير مستخدم.

المخرج القياسي للأخطاء

سيتم استخدام المخرج القياسي للأخطاء لرسائل التشخيص والمعلومات.

ملفات الإخراج

سيكون إخراج الأداة patch، وملفات الحفظ (لاحقات .orig)، وملفات الرفض (لاحقات .rej) ملفات نصية.

الوصف الموسع

قد يحتوي ملف التصحيح على تعليمات تصحيح لأكثر من ملف واحد؛ سيتم تحديد أسماء الملفات كما هو محدد في تحديد اسم الملف. عند تحديد الخيار -b، لكل ملف تم تصحيحه، سيتم حفظ الملف الأصلي في ملف بنفس الاسم مع إضافة اللاحقة .orig إليه.

لكل ملف تم تصحيحه، قد يتم أيضًا إنشاء ملف رفض كما هو مذكور في تطبيق التصحيح. في غياب الخيار -r، سيتم تكوين اسم هذا الملف عن طريق إضافة اللاحقة .rej إلى اسم الملف الأصلي.

تنسيق ملف التصحيح

سيحتوي ملف التصحيح على صفر أو أكثر من أسطر معلومات الرأس متبوعة بتصحيحات واحدة أو أكثر. سيحتوي كل تصحيح على صفر أو أكثر من أسطر تحديد اسم الملف بالتنسيق الذي تنتجه الخيارات -c أو -C أو -u أو -U للأداة diff، ومجموعات واحدة أو أكثر من مخرجات diff، والتي تسمى عادةً hunks.

ستتعرف الأداة patch على التعبير التالي في معلومات الرأس:

Index: pathname

اسم الملف المراد تصحيحه هو pathname.

إذا كانت جميع الأسطر (بما في ذلك الرؤوس) داخل التصحيح تبدأ بنفس تسلسل الأحرف البادئة <blank>، فإن الأداة patch ستزيل هذا التسلسل قبل المتابعة. داخل كل تصحيح، إذا كان نوع الاختلاف هو سياق مشترك، فستتعرف الأداة patch على التعبيرات التالية:

*** filename timestamp

نشأت التصحيحات من filename.
--- filename timestamp

يجب تطبيق التصحيحات على filename.

إذا كان نوع الاختلاف هو سياق موحد، فستتعرف الأداة patch على التعبيرات التالية:

--- filename timestamp

نشأت التصحيحات من filename.
+++ filename timestamp

يجب تطبيق التصحيحات على filename.

كل hunk داخل التصحيح سيكون مخرجات diff لتغيير نطاق سطر في الملف الأصلي. ستحدث أرقام الأسطر للتصحيحات المتتالية داخل التصحيح بترتيب تصاعدي.

تحديد اسم الملف

إذا لم يتم تحديد عامل تشغيل file، ستقوم patch بتنفيذ الخطوات التالية لتحديد اسم الملف المراد استخدامه:

1.
إذا كان نوع diff هو سياق، فإن الأداة patch ستحذف مكونات مسار (كما هو محدد بواسطة الخيار -p) من اسم الملف الموجود على السطر الذي يبدأ بـ "***" (إذا كان سياقًا منسوخًا) أو "---" (إذا كان سياقًا موحدًا)، ثم تختبر وجود هذا الملف نسبةً إلى الدليل الحالي (أو الدليل المحدد بالخيار -d). إذا كان الملف موجودًا، فستستخدم الأداة patch اسم الملف هذا.
2.
إذا كان نوع diff هو سياق، فإن الأداة patch ستحذف مكونات مسار (كما هو محدد بواسطة الخيار -p) من اسم الملف الموجود على السطر الذي يبدأ بـ "---" (إذا كان سياقًا منسوخًا) أو "+++" (إذا كان سياقًا موحدًا)، ثم تختبر وجود هذا الملف نسبةً إلى الدليل الحالي (أو الدليل المحدد بالخيار -d). إذا كان الملف موجودًا، فستستخدم الأداة patch اسم الملف هذا.
3.
إذا كانت معلومات الرأس تحتوي على سطر يبدأ بالسلسلة Index:، فستقوم الأداة patch بحذف مكونات مسار (كما هو محدد بواسطة الخيار -p) من هذا السطر، ثم تختبر وجود هذا الملف نسبةً إلى الدليل الحالي (أو الدليل المحدد بالخيار -d). إذا كان الملف موجودًا، فستستخدم الأداة patch اسم الملف هذا.
4.
إذا كان دليل SCCS موجودًا في الدليل الحالي، ستحاول patch تنفيذ أمر get -e SCCS/s.filename لاسترداد نسخة قابلة للتحرير من الملف. إذا كان الملف موجودًا، فستستخدم الأداة patch اسم الملف هذا.
5.
ستكتب الأداة patch مطالبة إلى المخرج القياسي وتطلب اسم ملف بشكل تفاعلي من الطرفية المتحكمة (على سبيل المثال، /dev/tty).

تطبيق التصحيح

إذا كان الخيار -c أو -e أو -n أو -u موجودًا، فستفسر الأداة patch المعلومات داخل كل hunk على أنها اختلاف سياق منسوخ، أو اختلاف ed، أو اختلاف عادي، أو اختلاف سياق موحد، على التوالي. في غياب أي من هذه الخيارات، ستقوم الأداة patch بتحديد نوع الاختلاف بناءً على تنسيق المعلومات داخل الـ hunk.

لكل hunk، ستبدأ الأداة patch في البحث عن مكان لتطبيق التصحيح عند رقم السطر في بداية الـ hunk، مع إضافة أو طرح أي إزاحة مستخدمة في تطبيق الـ hunk السابق. إذا لم يتم العثور على أسطر تطابق سياق الـ hunk، فستقوم patch بالمسح للأمام وللخلف لمسافة 1000 بايت على الأقل بحثًا عن مجموعة من الأسطر التي تطابق سياق الـ hunk.

إذا لم يتم العثور على مكان وكان اختلاف سياق، فسيتم إجراء مسح آخر، مع تجاهل السطر الأول والأخير من السياق. إذا فشل ذلك، سيتم تجاهل السطرين الأولين والسطرين الأخيرين من السياق وسيتم إجراء مسح آخر. قد تبحث التطبيقات بشكل أوسع عن مواقع التثبيت.

إذا لم يتم العثور على مكان، فستقوم الأداة patch بإلحاق الـ hunk بملف الرفض. سيتم كتابة الـ hunk المرفوض الذي هو اختلاف سياق منسوخ، أو اختلاف ed، أو اختلاف عادي بتنسيق اختلاف السياق المنسوخ بغض النظر عن تنسيق ملف التصحيح. يعتمد تحديد ما إذا كان الـ hunk المرفوض الذي هو اختلاف سياق موحد سيتم كتابته بتنسيق اختلاف السياق المنسوخ أو بتنسيق اختلاف السياق الموحد على التنفيذ. إذا كان الإدخال اختلافًا عاديًا أو بأسلوب ed، فقد يحتوي ملف الرفض على اختلافات مع صفر أسطر سياق. قد تختلف أرقام الأسطر في الـ hunks الموجودة في ملف الرفض عن أرقام الأسطر في ملف التصحيح حيث أنها ستعكس المواقع التقريبية للـ hunks الفاشلة في الملف الجديد بدلاً من الملف القديم.

إذا كان نوع التصحيح اختلاف ed، فقد يقوم التنفيذ بإنجاز عملية التصحيح عن طريق استدعاء الأداة ed.

استخدام التطبيق

الخيار -R لا يعمل مع نصوص ed لأنه لا توجد معلومات كافية لإعادة بناء العملية العكسية.

الخيار -p يجعل من الممكن تخصيص ملف التصحيح لهياكل أدلة المستخدم المحلية دون تحرير ملف التصحيح يدويًا. على سبيل المثال، إذا كان اسم الملف في ملف التصحيح هو:

/curds/whey/src/blurfl/blurfl.c

يعطي تحديد -p 0 المسار الكامل دون تعديل؛ -p 1 يعطي:

curds/whey/src/blurfl/blurfl.c

بدون الشرطة المائلة الأمامية، -p 4 يعطي:

blurfl/blurfl.c

وعدم تحديد -p على الإطلاق يعطي:

blurfl.c .

الأساس المنطقي

لم يتم تحديد بعض الوظائف في تطبيقات patch التاريخية. توثق الفقرات التالية الميزات الموجودة في التطبيقات التاريخية التي لم يتم تحديدها.

تم حذف وظيفة كانت خيارًا زائفًا "+" يسمح بتحديد مجموعة إضافية من الخيارات وعامل تشغيل ملف تصحيح. لم يُنظر إلى هذا على أنه مفيد بما يكفي لتوحيده.

في التطبيقات التاريخية، إذا ظهرت السلسلة "Prereq:" في الرأس، فستبحث الأداة patch عن معلومات الإصدار المقابلة (السلسلة المحددة في الرأس، مفصولة بأحرف <blank> أو بداية أو نهاية سطر أو الملف) و

RATIONALE

The -pnum option was not included in the original System V definition because it was not considered to be necessary. It was added to POSIX.1‐2001 because it is useful for automating the application of patches from files that are created in different directory structures. For example, if a user has created a patch file from the top of a source tree, and the patch file contains filenames that are relative to the top of that source tree, the -pnum option can be used to strip the correct number of leading directories from the filenames in the patch file so that they can be applied to a different directory structure.

The -c, -e, and -n options were dropped from historical implementations of patch as too simplistic and insufficiently trustworthy a mechanism to standardize. For example, if:

Prereq: 1.2

were in the header, the presence of a delimited 1.2 anywhere in the file would satisfy the prerequisite.

The following options were dropped from historical implementations of patch as insufficiently useful to standardize:

-b
The -b option historically provided a method for changing the name extension of the backup file from the default .orig. This option has been modified and retained in this volume of POSIX.1‐2017.
-F
The -F option specified the number of lines of a context diff to ignore when searching for a place to install a patch.
-f
The -f option historically caused patch not to request additional information from the user.
-r
The -r option historically provided a method of overriding the extension of the reject file from the default .rej.
-s
The -s option historically caused patch to work silently unless an error occurred.
-x
The -x option historically set internal debugging flags.

In some file system implementations, the saving of a .orig file may produce unwanted results. In the case of 12, 13, or 14-character filenames (on file systems supporting 14-character maximum filenames), the .orig file overwrites the new file. The reject file may also exceed this filename limit. It was suggested, due to some historical practice, that a <tilde> ('~') suffix be used instead of .orig and some other character instead of the .rej suffix. This was rejected because it is not obvious to the user which file is which. The suffixes .orig and .rej are clearer and more understandable.

The -b option has the opposite sense in some historical implementations—do not save the .orig file. The default case here is not to save the files, making patch behave more consistently with the other standard utilities.

The -w option in early proposals was changed to -l to match historical practice.

The -N option was included because without it, a non-interactive application cannot reject previously applied patches. For example, if a user is piping the output of diff into the patch utility, and the user only wants to patch a file to a newer version non-interactively, the -N option is required.

Changes to the -l option description were proposed to allow matching across <newline> characters in addition to just <blank> characters. Since this is not historical practice, and since some ambiguities could result, it is suggested that future developments in this area utilize another option letter, such as -L.

The -u option of GNU patch has been added, along with support for unified context formats.
