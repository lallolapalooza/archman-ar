قد يكون بعض ما يلي مخيفًا أو مربكًا للمبتدئين، لذا لا تخف من تخطيه حتى تكون مستعدًا له...

تستخدم Perl (و PDF::Builder) داخليًا سلاسل نصية إما أحادية البايت (ISO-8859-1/Latin-1) أو مشفرة بتشفير UTF-8 متعدد البايت (هناك علامة داخلية تحدد ما إذا كانت السلسلة النصية مشفرة بتشفير UTF-8 أم لا). إذا كنت تعمل *بصرامة* في ASCII أو Latin-1 أو CP-1252 (كل منها مجموعة فائقة للمجموعة السابقة)، فيجب أن تكون بخير دون القيام بأي شيء خاص بشأن ترميز السلاسل النصية الخاصة بك. يمكنك ببساطة استخدام السلاسل النصية أحادية البايت الافتراضية في Perl (المميزة داخليًا على أنها *ليست* UTF-8) وترميز الإخراج الافتراضي (WinAnsiEncoding).

إذا كنت تنوي استخدام مدخلات من مصادر متنوعة، فيجب عليك التفكير في فك تشفير (تحويل) نصك إلى UTF-8، والذي سيوفر تمثيلًا داخليًا متسقًا (ويجب حفظ كود Perl الخاص بك بتشفير UTF-8، في حالة رغبتك في استخدام أي أحرف غير ASCII مكتوبة بشكل ثابت). في أي سلسلة نصية، سيتم تحويل الأحرف غير ASCII (0x80 أو أعلى) إلى التمثيل الداخلي لـ UTF-8 في Perl، عبر "$string = Encode::decode(MY_ENCODING, $input);". سيكون "MY_ENCODING" سلسلة نصية مثل 'latin1'، 'cp-1252'، 'utf8'، إلخ. تتوفر إمكانيات مماثلة للإعلان عن ملف بتشفير معين.

كن على علم بأنه إذا كنت تستخدم ترميز UTF-8 لنصك، فإن خطوط TrueType فقط ("ttfont") يمكنها التعامل معه مباشرة. سيتطلب خطوط Corefont و Type1 أن يتم تحويل النص مرة أخرى إلى ترميز أحادي البايت (باستخدام "Encode::encode")، والذي قد يحتاج إلى تعريفه باستخدام "encode" (لـ "corefont" أو "psfont"). إذا كان لديك أي أحرف *غير* موجودة في الترميز أحادي البايت المحدد (ولكنها *موجودة* في الخط نفسه)، فستحتاج إلى استخدام "automap" لتقسيم رموز الخط إلى 256 مستوى من الأحرف، وتعيين مثل هذه الأحرف إلى 0x00 .. 0xFF في المستوى المناسب، والتبديل بين مستويات الخط حسب الحاجة.

تستخدم خطوط Core و Type1 (الإخراج) قيم البايت في السلسلة النصية (ترميز أحادي البايت فقط!) وتوفر سجل تعيين بايت إلى رمز لكل مستوى. تنتج خطوط TrueType مجموعة من أربعة أرقام ستة عشرية تمثل "CId" (معرف الحرف) لكل حرف. لا يتوافق CId مع أي من التمثيل الداخلي أحادي البايت أو UTF-8 للأحرف.

الخلاصة هي أنك بحاجة إلى معرفة التمثيل الداخلي لنصك، حتى تتمكن إجراءات الإخراج من إخبار قارئ PDF بذلك (عبر ملف PDF). لن تتم ترجمة النص عند الإخراج، ولكن يحتاج قارئ PDF إلى معرفة الترميز المستخدم، حتى يعرف الرمز الذي يجب ربطه بكل بايت (أو تسلسل بايت).

لاحظ أن بعض أنظمة التشغيل ونكهات Perl تشتهر بصرامتها بشأن أسماء الترميز. على سبيل المثال، قد يتم رفض latin1 (اسم مستعار) على أنه غير صالح، بينما يعمل iso-8859-1 (قيمة قياسية).

بالمناسبة، يوصى باستخدام Perl 5.10 *على الأقل* إذا كنت ستستخدم أي أحرف غير ASCII. قد يكون Perl 5.8 غير قابل للتنبؤ به قليلاً في التعامل مع هذا النوع من النصوص.

ترتيب العرض

للأفضل أو للأسوأ، ولأغراض التوافق، تستمر PDF::Builder في نفس نموذج العرض الذي استخدمته PDF::API2 (وربما سابقاتها). أي أن جميع الرسومات *لكائن رسومات واحد* يتم وضعها في سجل واحد، وكل إخراج نصي *لكائن نصي واحد* يذهب إلى سجل آخر. أيهما يتم إخراجه أولاً هو أيهما تم تعريفه أولاً. يمكن أن يؤدي هذا إلى نتائج غير متوقعة، حيث يتم عرض العناصر بترتيب (يبدو) خاطئ. أي أن عناصر النص والرسومات لا يتم بالضرورة إخراجها (عرضها) بنفس الترتيب الذي تم إنشاؤها به في الكود. سيتم عرض عنصرين في نفس الكائن (على سبيل المثال، $text) بنفس الترتيب الذي تم ترميزهما به، ولكن قد لا يتم عرض العناصر من كائنات مختلفة بالترتيب المتوقع. نأمل أن يوضح المثال التالي (كود المصدر واقتباسات PDF المشروحة) المشكلة:

use strict;
use warnings;
use PDF::Builder;
# demonstrate text and graphics object order
# 
my $fname = "objorder";
my $paper_size = "Letter";
# see the text and graphics stream contents
my $pdf = PDF::Builder->new(compress => 'none');
$pdf->mediabox($paper_size);
my $page = $pdf->page();
# adjust path for your operating system
my $fontTR = $pdf->ttfont('C:\\Windows\\Fonts\\timesbd.ttf');

After saving a file...

Note that a PDF object such as $pdf cannot continue to be used after saving an output PDF file or string with $pdf->save(), saveas(), or stringify(). There is some cleanup and other operations done internally which make the object unusable for further operations. You will likely receive an error message about can't call method new_obj on an undefined value if you try to keep using a PDF object.

IntegrityCheck

The PDF::Builder methods that open an existing PDF file, pass it by the integrity checker method, "$self->IntegrityCheck(level, content)". This method servers two purposes: 1) to find any "/Version" settings that override the PDF version found in the PDF heading, and 2) perform some basic validations on the contents of the PDF.

The "level" parameter accepts the following values:

0
Do not output any diagnostic messages; just return any version override.
1
Output error-level (serious) diagnostic messages, as well as returning any version override.

Errors include, in no place was the /Root object specified, or if it was, the indicated object was not found. An object claims another object as its child (/Kids list), but another object has already claimed that child. An object claims a child, but that child does not list a Parent, or the child lists a different Parent.

2
Output error- (serious) and warning- (less serious) level diagnostic messages, as well as returning any version override. This is the default.
3
Output error- (serious), warning- (less serious), and note- (informational) level diagnostic messages, as well as returning any version override.

أساليب "الصندوق"

ملاحظة عامة: استخدم الحذر إذا كنت تحدد مربع وسائط (أو أي "صندوق" آخر) مختلفًا لصفحة ما، عن "الصندوق" العام المحدد، لتحديد "سلسلة" الصناديق في الصفحة، لتجنب المفاجآت. على سبيل المثال، لتحديد مربع وسائط عام (حجم الورق) ومربع اقتصاص عام، ثم تحديد مربع وسائط جديد على مستوى الصفحة دون تحديد مربع اقتصاص جديد على مستوى الصفحة، قد يؤدي إلى نتائج غريبة في الاقتصاص الناتج. هذه التركيبات ليست محددة جيدًا.

جميع الأبعاد في الصناديق افتراضية إلى وحدة المستخدم الافتراضية، وهي نقاط (1/72 بوصة). لاحظ أن مواصفات PDF تحدد الأحجام والإحداثيات بـ 14400 وحدة مستخدم (200 بوصة، لوحدة المستخدم الافتراضية نقطة واحدة)، وتتبع منتجات Adobe (حتى الآن) هذا الحد لأكروبات و Distiller. يجدر ملاحظة أن كتاب PDF وقارئات أخرى قد تختار تجاهل حد 14400 وحدة، مع أو بدون استخدام وحدة مستخدم محددة. لذلك، لا يفرض PDF::Builder أي حدود على الإحداثيات - إنها مسؤوليتك النظر في القارئات والأدوات الأخرى لملف PDF التي قد تستخدم مع ملف PDF تنتجه! لاحظ أيضًا أن قارئات Acrobat الأقدم كان لديها حدود إحداثيات صغيرة تصل إلى 3240 وحدة مستخدم (45 بوصة)، و الحد الأدنى لحجم الوسائط 72 أو 3 وحدات مستخدم.

وحدات المستخدم (userunit)

$pdf->userunit($number)
وحدة المستخدم الافتراضية في نظام إحداثيات PDF هي نقطة واحدة (1/72 بوصة). يمكنك التفكير فيها كعامل قياس لتمكين مستندات أكبر (أو حتى أصغر). يمكن استخدام هذه الطريقة (لـ PDF 1.6 وما فوق) لضبط وحدة المستخدم إلى عدد معين من النقاط. على سبيل المثال، سيضبط userunit(72) مضاعف القياس إلى 72.0 نقطة لكل وحدة مستخدم، أو 1 بوصة إلى وحدة المستخدم. أي رقم أكبر من صفر مقبول، على الرغم من أن بعض القارئات والأدوات قد لا تتعامل جيدًا مع وحدات المستخدم الأقل من 1.0.

لا تحترم جميع القارئات وحدة المستخدم، إذا قدمت واحدة، أو تتعامل معها بنفس الطريقة تمامًا. Adobe Distiller، على سبيل المثال، لا تستخدمها. كيفية معالجة وحدات المستخدم قد تختلف من قارئ لآخر. Adobe Acrobat، في وقت كتابة هذه السطور، تحترم وحدة المستخدم في الإصدار 7.0 وما فوق، ولكنها تحددها بـ 75000 (مما يوفر حجم مستند أقصى يبلغ 15 مليون بوصة أو 236.7 ميل أو 381 كم). قد تسمح القارئات وأدوات PDF الأخرى بحد أقصى أكبر (أو أصغر).

قد تختلف تجربتك: تتجاهل بعض القارئات إعداد وحدة مستخدم عام ولا تجعل الصفحات ترثها (يقوم PDF::Builder بتكرارها في كل صفحة لمحاكاة الوراثة). قد تصدر بعض القارئات تحذيرات زائفة بشأن المحتوى المقتطع عند تغيير مربع وسائط أثناء استخدام وحدات المستخدم. تقوم بعض القارئات بأشياء غريبة مع صناديق الاقتصاص عند وجود وحدة مستخدم قيد التأثير.

اعتمادًا على القارئ المستخدم، قد يعني تأثير وحدة المستخدم الأكبر (أكبر من 1) دقة أقل (مظهر خشن أو متقطع) في المستند المعروض. إذا كنت تطبع شيئًا بحجم لوحة إعلانات طريق سريع، فقد لا يهمك هذا، ولكن يجب أن تكون على دراية بالاحتمال (حتى مع الإحداثيات الكسرية). على العكس من ذلك، فإن وحدة المستخدم الأقل من 1.0 (إذا سمح بها) تقلل الحجم المسموح به لمستندك، ولكنها *قد* تؤدي إلى دقة أكبر.

يتم وراثة إعداد وحدة المستخدم العام (مستوى PDF) من قبل كل صفحة (إجراء بواسطة PDF::Builder، لا يتم بالضرورة تلقائيًا بواسطة القارئ)، أو يمكن إلغاؤه عن طريق استدعاء userunit في الصفحة. لا تقدم أكثر من إعداد userunit عام واحد، حيث سيتم استخدام الأخير فقط. يُسمح بضبط وحدة المستخدم للصفحة (إذا "$page->" بدلاً من ذلك) (لإلغاء الإعداد العام لهذه الصفحة). ومع ذلك، توصي العديد من المصادر بعدم القيام بذلك، حيث قد لا تكون النتائج كما هو متوقع (مرة أخرى، اعتمادًا على غرائب القارئ).

تذكر استدعاء "userunit" قبل استدعاء أي شيء يتعلق بأحجام الصفحات أو الصناديق، أو الإحداثيات. خاصة عند تعيين أحجام الصناديق 'المسماة'، تحتاج الأساليب إلى معرفة وحدة المستخدم الحالية حتى يمكن تقليص أحجام الصفحات المسماة (بالنقاط) إلى وحدة المستخدم الحالية.

مربع الوسائط (mediabox)

$pdf->mediabox($name)
$pdf->mediabox($name, orient => 'orientation' )
$pdf->mediabox($w,$h)
$pdf->mediabox($llx,$lly, $urx,$ury)
($llx,$lly, $urx,$ury) = $pdf->mediabox()
يحدد مربع الوسائط العام (أو مربع الوسائط للصفحة، إذا كان "$page->" بدلاً من ذلك). يحدد هذا عرض وارتفاع (أو بالإحداثيات الزاوية، أو بالاسم القياسي) للصفحة نفسها، مثل حجم الورق الفعلي. هذا هو عادةً أكبر "الصناديق". إذا تجاوز أي صندوق فرعي (داخله) مربع الوسائط، فسيتم تجاهل الجزء الخاص بالمواد أو الصناديق خارج مربع الوسائط. أي أن مربع الوسائط هو الصندوق الوحيد الذي يحكمهم جميعًا، وهو الحد الإجمالي للصناديق الأخرى (تشير بعض الوثائق إلى مربع الوسائط على أنه "قص" للصناديق الأخرى). بالإضافة إلى ذلك، يحدد مربع الوسائط نظام الإحداثيات العام لعمليات النص والرسومات.

إذا لم يتم تقديم أي وسائط، فسيتم إرجاع إحداثيات مربع الوسائط الحالي (العام أو الخاص بالصفحة) بدلاً من ذلك. تم إهمال وظيفة "get_mediabox" السابقة (الصفحة فقط) وتم إزالتها. بالإضافة إلى ذلك، عند تعيين مربع الوسائط، يتم إرجاع الإحداثيات الناتجة. هذا يسمح لك بتحديد حجم الصفحة باسم (اسم مستعار) والحصول على الأبعاد مرة أخرى، كل ذلك في استدعاء واحد.

لاحظ أن العديد من الطابعات لا يمكنها الطباعة حتى الحافة المادية للورق، لذلك يجب عليك التخطيط لترك هامش فارغ، حتى خارج علامات القص (crop marks) والتنزفات (bleeds). للطابعات والقارئات على الشاشة الحرية في التخلص من أي محتوى موجود خارج مربع الوسائط، وقد تقوم الطابعات بالتخلص من بعض المواد الموجودة مباشرة داخل مربع الوسائط.

مربع وسائط عام مطلوب بموجب مواصفات PDF؛ إذا لم يتم تقديمه صراحةً، فسيقوم PDF::Builder بتعيين مربع الوسائط العام إلى حجم US Letter (8.5 بوصة × 11 بوصة). هذا هو حجم الوسائط الذي سيتم استخدامه لجميع الصفحات إذا لم تحدد استدعاء "mediabox" على صفحة. أي أن إعداد مربع وسائط عام (مستوى PDF) يتم وراثته من قبل كل صفحة، أو يمكن إلغاؤه عن طريق تعيين mediabox في الصفحة. لا تقدم أكثر من إعداد mediabox عام واحد، حيث سيتم استخدام الأخير فقط.

إذا قدمت اسم سلسلة واحدة (مثل 'A4')، يمكنك اختياريًا إضافة اتجاه لتحويل الصفحة 90 درجة إلى وضع أفقي: "orient => 'L'" أو "orient => 'l'". "orient" هو الخيار الوحيد المعترف به، وسلسلة تبدأ بـ 'L' أو 'l' (للأفقي) هي القيمة الوحيدة ذات الأهمية (يتم معاملة أي شيء آخر على أنه وضع عمودي). لا يزال المحور y يعمل من 0 في أسفل الصفحة إلى ما كان يُعتبر عرض الصفحة (الآن، ارتفاعها) في الأعلى، وبالمثل للمحور x: 0 في اليسار إلى (السابق) الارتفاع في اليمين. أي أن نظام الإحداثيات هو نفسه من قبل، باستثناء أن الارتفاع والعرض مختلفان.

الزاوية السفلية اليسرى لا يجب أن تكون 0,0. يمكن أن تكون أي قيم تريدها، بما في ذلك القيم السالبة (طالما أن جوانب الوسائط الناتجة لا تقل عن نقطة واحدة). "mediabox" يحدد نظام الإحداثيات (بما في ذلك الأصل) للرسومات والنصوص التي سيتم رسمها، وكذلك لـ "الصناديق" اللاحقة. من الممكن حتى تقديم أي زاويتين متقابلتين (مثل الزاوية العلوية اليسرى والسفلية اليمنى). سيتم إعادة ترتيب نظام الإحداثيات (بواسطة القارئ) ليظل الحد الأدنى التقليدي لـ "x" و "y" في الأسفل الأيسر (أي، لا يمكنك جعل "y" يزيد من أعلى إلى أسفل!).

$pdf->saveas('our/new.pdf');
$pdf = PDF::Builder->new();
$pdf->mediabox(595, 842); # حجم A4، مع زاوية سفلية يسرى ضمنية 0,0
...
$pdf->saveas('our/new.pdf');
$pdf = PDF::Builder->new;
$pdf->mediabox(0, 0, 595, 842); # حجم A4، مع زاوية سفلية يسرى صريحة 0,0
...
$pdf->saveas('our/new.pdf');

  • كن على علم بصفحة التعليمات البرمجية التي يستخدمها نظام تشغيل معين ومحرره عند إنشاء ملف بنصك ليتم تحويله إلى PDF! إذا قمت بكتابة "اليورو" ولكنه، على سبيل المثال، سلسلة بايت UTF-8 في الملف، فمن المحتمل أن لا تحصل على "اليورو" في ملف PDF الخاص بك.

  • كن على علم أيضًا بأن قارئ PDF حر في استبدال خط آخر مشابه (ولكن ليس بالضرورة مطابقًا) للخط الأساسي المطلوب. على سبيل المثال، غالبًا ما تستبدل أجهزة الكمبيوتر التي تعمل بنظام Windows خط Arial بخط Helvetica المطلوب. المقاييس (العروض) متساوية، ولكن الأحرف الرسومية مختلفة قليلاً.
  • من المفترض أن تكون الخطوط الأساسية متاحة على جميع قراء PDF، لذلك لا يمكن تضمينها في PDF (كما هو الحال مع خطوط TTF). لا يُعتقد أن هذا مشكلة بالنسبة للمستندات الأرشيفية (PDF/A)، ولكنه قد يصبح مشكلة في وقت ما، لذلك يجب أن تكون على دراية.

    • راجع "font automap" في PDF::Builder::Resource::Font method للحصول على معلومات حول الوصول إلى أكثر من 256 حرفًا رسوميًا في خط، باستخدام planes، على الرغم من عدم وجود ضمان بأن التغييرات المستقبلية في ملفات الخطوط ستسمح بنتائج متسقة.

    هل يجب أن تستخدم TTF بدلاً من ذلك؟

    إذا كنت بحاجة إلى الوصول بشكل موثوق إلى أحرف معينة غير موجودة في الترميزات الشائعة، يرجى التفكير في استخدام خطوط TrueType (TTF) أو OpenType (OTF) عبر طريقة ttfont(). لاحظ أنك ستكون مسؤولاً عن تحديد المسار الدقيق والاسم الكامل لملف TTF، والتأكد من أن ملف الخط متاح على PDF Writer، وربما على Reader (إذا لم يكن مضمنًا).

    سيسمح لك هذا باستخدام نص UTF-8، مع قابلية استخدام رسومية ممتدة، بالإضافة إلى السماح بتضمين الخط نفسه في PDF، مما يضمن حصولك على الأحرف الرسومية التي تريدها بالضبط، دون أي استبدالات. قد يكون دعم Kerning والربط (عبر HarfBuzz::Shaper) متاحًا بشكل أكبر لخطوط TTF. هناك أدوات، مثل FontForge، التي يمكنها القيام بعمل جيد إلى حد ما (على الرغم من أنه ليس مثاليًا) لتحويل مكتبة خطوط Type1 (إذا كانت هذه هي خطوطك الأساسية، داخليًا) إلى OTF.

    راجع أيضًا PDF::Builder::Resource::Font::CoreFont.

    خطوط PS

    تُعرف خطوط PostScript أيضًا باسم خطوط "Type 1". هذه ليست خطوطًا "مضمنة"، وسيحتاج كل من PDF Writer وقارئ PDF إلى توفير ملفات الخطوط المطلوبة. كانت خطوط PostScript شائعة جدًا في السابق، لكنها تراجعت.

    خطوط PS (Type 1) ليست مدرجة مع PDF::Builder، ولكن من المتوقع العثور عليها على الجهاز الذي يعمل عليه قارئ PDF. معظم قراء PDF لا يقومون بتثبيت خطوط PS، وتقع على عاتق مستخدم قارئ PDF مسؤولية تثبيت الخطوط المطلوبة. على عكس خطوط TrueType، لا يتم تضمين خطوط PS (T1) في PDF، ويجب توفيرها في نهاية القارئ.

    تقتصر خطوط PS على ترميزات بايت واحد. الترميز الافتراضي لخطوط PS هو WinAnsiEncoding (تقريبًا مجموعة Superset CP-1252/Windows-1252 من ISO-8859-1/Latin-1). راجع خيار "encode" أدناه لتغيير هذا الترميز.

    إحدى خصائص استخدام خطوط PS هي أنه يتم استخدام ملفين لكل خط: ملف حرف رسومي (.pfa بتنسيق ASCII، .pfb بتنسيق ثنائي، أو .t1 بتنسيق ممتد)، وملف مقاييس (.afm بتنسيق ASCII، أو .pfm بتنسيق ثنائي). يمكن استخدام ملف حرف رسومي ثنائي مع ملف مقاييس ASCII، والعكس صحيح، إذا رغبت في ذلك أو احتجت إليه. الملفات النصية والثنائية لها نفس المحتوى، ولكن بتنسيقات مختلفة.

    تحذير: يجب أن يكون اسم الملف المحدد لملف الحرف الرسومي (الوسيط الأول لـ "psfont") له امتداد ملف .pfa أو .pfb أو .t1؛ حيث سيتم فحص الامتداد لمعرفة كيفية تحليل الملف.

    تحذير: نهاية دعم Adobe

    أعلنت Adobe عن نهاية الدعم لخطوط Type 1 (Postscript/T1) في منتجاتها. صيغ الإعلان غامضة إلى حد ما، وتشير أحيانًا إلى "جميع المنتجات" وأحيانًا أخرى فقط إلى "برامج التأليف". من المفترض أن تستمر قراءات PDF الخاصة بـ Adobe (بالإضافة إلى القراءات التي توفرها أطراف أخرى) في عرض ملفات PDF بخطوط Type 1 لفترة طويلة، على الرغم من أن هذا ليس مؤكدًا على الإطلاق. لاحظ أن هذا لا يعني أن PDF::Builder أو أدوات التأليف الأخرى من أطراف ثالثة قد لا تستمر في دعم خطوط Type 1. هذا الإنهاء من قبل Adobe لدعم تنسيق خط قديم وبالٍ لا يؤثر على استخدام PDF::Builder لتأليف ملفات PDF، ولا يلزم الأدوات الأخرى غير التابعة لـ Adobe والقراءات. ومع ذلك، قد لا يكون من الممكن استخدام منتجات Adobe لتحرير ملفات PDF بخطوط Type 1، وربما لعرضها. على أي حال، قد يرغب المستخدمون في التفكير في البدء في الابتعاد عن استخدام خطوط Type 1 والتبديل إلى TTF/OTF أو حتى الخطوط الأساسية، على الرغم من أنه من غير المعروف إلى متى سيستمر دعم القارئ لـ Type 1.

    أمثلة

    $font1 = $pdf->psfont('Times-Book.pfa', afmfile => 'Times-Book.afm');
$font2 = $pdf->psfont('/fonts/Synest-FB.pfb', pfmfile => '/fonts/Synest-FB.pfm');

    يمكن أيضًا طلب خطوط PS عبر طريقة font()

    $font3 = $pdf->font('/fonts/Times-Book.t1', afmfile => '/fonts/Times-Book.afm');

    بالإضافة إلى القدرة على التحميل في FontManager

    $font4 = $pdf->get_font('face'=>'Times-Book', 'italic'=>0, 'bold'=>0);

    ملاحظات وقيود

    • لا يمكنك استخدام UTF-8 أو ترميزات متعددة البايتات أخرى مع خطوط PS، فقط ترميزات بايت واحد (256 حرفًا كحد أقصى). لا يعرف قارئ PDF (أو الكاتب!) ما يجب فعله بحرف متعدد البايتات، ومن المحتمل أن يقوم بعرضه كسلسلة من الأحرف الفردية (مما ينتج عنه هراء). على الرغم من أن معظم ترميزات بايت واحد، على الأقل للغات الأوروبية، مدعومة، فمن الممكن أن تواجه ترميزًا يتضمن حرفًا غير موجود في ملف خط معين، أو العكس (يحتوي الخط على أحرف لا تمنحك الترميز الوصول إليها).
    • لا تخلط بين نقاط ترميز Unicode (كما هو معطى مع كيان HTML) وقيم البايت الواحد أو الأحرف متعددة البايتات. الطريقة الوحيدة للوصول إلى حرف معرف لترميز معين هي باستخدام قيمة بايت واحدة في النطاق من 0 إلى 255. على سبيل المثال، إذا لم تتمكن من كتابة رمز "اليورو" مباشرة، فهو "\x80" في العديد من الترميزات -- ستستخدم ذلك بدلاً من نقطة ترميز Unicode "\x{20AC}" أو سلسلة بايت UTF-8 "x\{E282AC}". إنها مسألة إعطاء قيمة بايت واحدة يمكن لقارئ PDF البحث عنها في تعريف الخط الخاص به للحصول على الحرف الرسومي المطلوب. إذا لم يتم العثور على رمز "اليورو" في الترميز الذي تستخدمه، حسنًا، فقد فات الأوان.
    • كن على علم بصفحة التعليمات البرمجية التي يستخدمها نظام تشغيل معين ومحرره عند إنشاء ملف بنصك ليتم تحويله إلى PDF! إذا قمت بكتابة "اليورو" ولكنه، على سبيل المثال، سلسلة بايت UTF-8 في الملف، فمن المحتمل أن لا تحصل على "اليورو" في ملف PDF الخاص بك.

    خطوط TrueType

    خطوط TrueType (TTF) وأقاربها المقربين، خطوط OpenType (OTF)، تستخدم على نطاق واسع. غالبًا ما يتم تضمين هذه مع العديد من أنظمة التشغيل، على الرغم من أنها ليست "مضمنة" في PDF، وسيحتاج كل من PDF Writer وأي قارئ PDF (إذا لم يتم تضمين الخط) إلى توفير ملفات الخطوط المطلوبة.

    خطوط TTF و OTF ليست مدرجة مع PDF::Builder، ولكن من المتوقع العثور عليها على الجهاز الذي يعمل عليه PDF Writer (وإذا لزم الأمر، القارئ). معظم قراء PDF لا يقومون بتثبيت خطوط TTF/OTF، ويقع على عاتق مستخدم قارئ PDF مسؤولية تثبيت الخطوط المطلوبة (إذا لم تكن مضمنة). لاحظ أن السلوك الافتراضي هو تضمين مجموعة فرعية من الخط (الأحرف الرسومية المستخدمة بالفعل) في ملف PDF، لذلك لا يوجد احتمال لعدم توفر الخط الصحيح على القارئ.

    خطوط TTF و OTF ليست مقيدة بترميزات بايت واحد، ولكن يمكنها استخدام ترميزات متعددة البايتات مثل UTF-8. الترميز الافتراضي لهذه الخطوط هو WinAnsiEncoding (تقريبًا مجموعة Superset CP-1252/Windows-1252 من ISO-8859-1/Latin-1). راجع خيار "encode" أدناه لتغيير هذا الترميز.

    أمثلة

    $font1 = $pdf->ttfont('Times.ttf');
$font2 = $pdf->ttfont('Georgia.otf');

    يمكن أيضًا طلب خطوط TTF/OTF عبر طريقة font()

    $font3 = $pdf->font('/fonts/Sanskrit.ttf');

    Caution: a given character's glyph ID is not necessarily going to be the same between any two fonts! For example, an ASCII space (U+0020) might be "<0001>" in one font, and "<0003>" in another font (even one closely related!). A U+00A0 required blank (non-breaking space) may be output as a regular ASCII space U+0020. Take care if you need to find a particular glyph in the array, especially if the number of elements don't match. You may have to count spaces, say, to see where you could break a glyph array to fit a line.

    The advancewidthHS() method uses the same inputs as does textHS(). Like advancewidth(), it returns the chunk length in points. Unlike advancewidth(), you cannot override the glyph array's font, font size, etc.

    Once you have your (possibly modified) array of glyphs, you feed it to the textHS() method to render it to the page. Remember that this method handles only a single line of text; it does not do line splitting or fitting -- that you currently need to do manually. For Western scripts (e.g., Latin), that might not be too difficult, but for other scripts that involve extensive modification of the raw characters, it may be quite difficult to split words, but you still may be able to split at inter-word spaces.

    A useful, but not exhaustive, set of functions are allowed by textHS() use. Support includes direction setting (top-to-bottom and bottom-to-top directions, e.g., for Far Eastern languages in traditional orientation), and explicit script names and language (depending on what support HarfBuzz itself gives). Not yet supported are features such as discretionary ligatures and manual selection of glyphs (e.g., swashes and alternate forms).

    Currently, textHS() can only handle a single text string. We are looking at how fitting to a line length (splitting up an array) could be done, as well as how words might be split on hard and soft hyphens. At some point, full paragraph and page shaping could be possible.

    MARKUP

    This section documents the markup capabilities of the column() method. It is expected to be updated over time as more functionality is added.

    A certain flavor of Markdown is supported, as translated by the Text::Markdown package into HTML. That HTML (and more, as direct input), along with a subset of CSS, is supported by column(). This is not the full Markdown or HTML languages, by any stretch of the imagination, so check before using! Also, a small none markup which only does paragraphs (separated by empty lines) is provided.

    In all markup cases, certain CSS settings can be given as parameters or options to the column() call, including a CSS <style> section which applies to both 'none' and Markdown source input.

    Other input formats

    PDF::Builder currently only supports the markup languages described above. If you want to use something else (e.g., Perl's POD, or man format, or even MS Word or some other WYSIWYG format), you will need to find a converter utility to convert it to a supported flavor of Markdown or HTML. Many such converters already exist, so take a look (although you may well have to do some cleanup before column() accepts it).

    Perhaps in the future, PDF::Builder will directly support additional formats, but no promises. You will probably never see TeX/LaTeX input, as these already have excellent PDF output (and would be a massive undertaking to process).

    Current HTML/Markdown supported

    • <i> and <em> tags (Markdown _, *) as italic font style
    • <b> and <strong> tags (Markdown **) as bold font weight
    • <p> tag (Markdown empty line) as a paragraph
    • <font face="font-family" color="color" size="font-size"> as selecting face, color and size
    • <span> needs style= attribute with CSS to do anything useful
    • <ul> tag (Markdown -) unordered (bulleted) list. type to override marker supported
    • <ol> tag (Markdown 1.) ordered (numbered) list. start and type supported.
    • <_marker> tag (not standard HTML) provide a place to specify, on a per list item basis, overrides to default marker settings (see "_marker-*" CSS extensions below). If omitted, the same HTML list markers and CSS properties are used for each list item (per usual practice)
    • <li> tag list item. value to override ordered list counter, and type to override marker type supported
    • <a href="URL"> tag (Markdown []()) anchor/link, web page URL or this document target "#p[-x-y[-z]]"
    • <h1> through <h6> tags (Markdown # through ######) headings
    • <hr width="length" size="length"> tag (Markdown ---) horizontal rule. currently no align property (left alignment only). Default is "width" = full column, and "size" = 0.5pt.
    • <s>, <strike>, <del> tags (Markdown ~~) text line-through
    • <u>, <ins> tags text underline
    • <blockquote> tag (Markdown >) indented both sides block of smaller text
    • <_marker> tag (non-standard) to explicitly set list marker properties (_marker-*) for one specific (immediately following) <li> list item
    • <_move> tag (non-standard) to explicitly move current write point left or right. "x="value"" is an absolute move (in points), while "dx="value"" is a relative move

    Numbered (decimal and hexadecimal) entities are supported, as well as named entities (e.g., "&mdash;"). Both lists get a "gutter" (for the marker) of marker_width points wide, so list alignments are consistent over the call.

    Current CSS supported

    Note that the default CSS also applies to Markdown, unless you give a "style =>" entry to the column() call to revise the CSS.

    In HTML, you can define <style> tags, but caution: these are pulled out into a global style block (cumulative and global, as though they had all been given in the <head>), applied after the CSS property defaults are defined and then any column() global "style => 'CSS list'" has been applied.

    CSS Selectors are very primitive:: a simple tag name (including body), such as ol; a class name such as .error; or an ID such as #myID. There are no hierarchies or combinations supported (e.g., nothing like p.abstract or li > p). The (decreasing) order of precedence follows a browser's: in a style = attribute, as a tag attribute (which may have a different name from the CSS's), an ID, a class, or a tag name. Comments /* and */ are NOT currently supported in CSS.

    Global Settings

    There are a number of global settings either required or available for tuning the behavior of column(). In the parameter list you can set

    font_size
    default initial font size (points) to be used, but can be overridden by CSS or "<font size>". Initially 12.
    leading
    default leading (text-height) ratio. Initially 1.125.
    marker_width
    points, set width of gutter where a list's marker goes. Initially "2 * <font size>" (2 em).
    marker_gap
    points, set width of additional space between the marker and the start of the list item text. Initially "<font size>" (1 em).
    para
    list of indentation (text-indent) and inter-paragraph spacing (margin-top), both in points. These are the defaults for all formatting modes, unless overridden by a style => entry. Initially "[ <font size>, 0 ]".
    color
    initial text and graphics color setting, in standard PDF::Builder formats. Initially 'black'.
    style
    CSS declarations to be applied after CSS properties initialization and before any global <style> tags, Initially ''.

    The Font Manager system is used to supply the requested fonts, so it is up to the application to pre-load the desired font information before column() is called. Any request to change the encoding within column() will be ignored, as the fonts have already been specified for a specific encoding. Needless to say, the encoding used in creating the input text needs to match the specified font encoding.

    Absent any markup changing the font face or styling, whatever is defined by Font Manager as the current font will be what is used. This way, you may inherit the font from the previous column(), or call "$text-"font($pdf->get_font(), size)> to set both the font and size, or just call "$pdf-"get_font()> to set only the font, relying on the "font_size" option or CSS markup to set the size.

    Line fitting (paragraph shaping) is currently quite primitive. Words will not be split (hyphenated). It is planned to eventually add Knuth-Plass paragraph shaping, along with proper language-dependent hyphenation.

    Each change of font automatically supplies its maximum ascender and minimum descender, the extents above and below the text line's baseline. Each block of text with a given face and variant, or change of font size, will be given the same vertical extents -- the extents are font-wide, and not determined on a per-glyph basis. So, unfortunately, a block of text "acemnorsuvwz" will have the same vertical extents as a block of text "bdfghijklpqty". For a given line of text, the highest ascender and the lowest descender (plus leading) will be used to position the line at the appropriate distance below the previous line (or the top of the column). No attempt is made to "fit" projections into recesses (jigsaw-puzzle like). If there is an inset into the side of a column, or it is otherwise not a straight vertical line, so long as the baseline fits within the column outline, no check is made whether descenders or ascenders will fall outside the defined column (i.e., project into the inset). We suggest that you try to keep font sizes fairly consistent, to keep reasonably consistent text vertical extents.
