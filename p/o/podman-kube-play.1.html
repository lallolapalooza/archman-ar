r envFrom: - configMapRef: name: foo optional: false

ونتيجة لذلك، يتم تعيين متغير البيئة FOO إلى bar للحاوية container-1.

Kubernetes Secret

يمثل Kubernetes Secret سر Podman المسمى. يتم حفظ Kubernetes Secret بأكمله وقد يُشار إليه كمصدر لمتغيرات البيئة أو وحدات التخزين في Pods أو Deployments.

على سبيل المثال، يحدد مستند YAML التالي سرًا ثم يستخدمه في Pod:

kind: Secret
apiVersion: v1
metadata:
  name: foo
data:
  foo: YmFy # base64 for bar
---
apiVersion: v1
kind: Pod
metadata:
  name: foobar
spec:
  containers:
  - name: container-1
    image: foobar
    env:
    - name: FOO
      valueFrom:
        secretKeyRef:
          name: foo
          key: foo

ونتيجة لذلك، يتم تعيين متغير البيئة FOO إلى bar للحاوية container-1.

Automounting Volumes (deprecated)

ملاحظة: تم إيقاف التعليق التوضيحي automounting. تمتلك Kubernetes دعمًا أصليًا لوحدات تخزين الصور ويجب استخدامها بدلاً من هذا التعليق التوضيحي الخاص بـ Podman.

يمكن تحميل صورة تلقائيًا في حاوية إذا تم توفير التعليق التوضيحي io.podman.annotations.kube.image.automount/$ctrname. تنطبق القواعد التالية:

  • يجب أن تكون الصورة موجودة بالفعل محليًا.
  • يجب أن تحتوي الصورة على توجيه وحدة تخزين واحد على الأقل.
  • سيتم تحميل المسار المحدد بواسطة توجيه وحدة التخزين من الصورة إلى الحاوية. على سبيل المثال، صورة تحتوي على وحدة تخزين في /test/test_dir سيتم تحميل /test/test_dir في الصورة إلى /test/test_dir في الحاوية.
  • يمكن تحديد صور متعددة. إذا كانت صور متعددة تحتوي على وحدة تخزين في مسار معين، فإن الصورة الأخيرة المحددة تتفوق.
  • يتم تحميل الصور دائمًا للقراءة فقط.
  • يتم تعريف الصور المراد تحميلها في التعليق التوضيحي "io.podman.annotations.kube.image.automount/$ctrname" كقائمة مفصولة بعلامات ترقيم. يتم تحميلها في حاوية واحدة في Pod، وليس في Pod بأكمله. يمكن تحديد التعليق التوضيحي لحاويات إضافية إذا كانت هناك حاجة إلى تحميلات إضافية.

OPTIONS

--annotation=key=value

أضف تعليقًا توضيحيًا إلى الحاوية أو Pod. يمكن تعيين هذا الخيار عدة مرات.

ملاحظة: بالنسبة لـ podman kube play، يضيف العلم --annotation تعليقات توضيحية خاصة بـ Podman إلى الحاويات و Pods التي ينشئها Podman، وليس إلى ملف YAML الخاص بـ Kubernetes نفسه. يمكن استخدام هذه التعليقات التوضيحية لتكوين ميزات خاصة بـ Podman مثل مساحات أسماء المستخدمين (io.podman.annotations.userns) و volumes-from (io.podman.annotations.volumes-from) وسلوكيات الحاويات الأخرى.

--authfile=path

مسار ملف المصادقة. الافتراضي هو ${XDG_RUNTIME_DIR}/containers/auth.json على Linux، و $HOME/.config/containers/auth.json على Windows/macOS. يتم إنشاء الملف بواسطة podman login. إذا لم يتم العثور على حالة المصادقة هناك، يتم التحقق من $HOME/.docker/config.json، والذي تم تعيينه باستخدام docker login.

ملاحظة: هناك أيضًا خيار لتجاوز المسار الافتراضي لملف المصادقة عن طريق تعيين متغير البيئة REGISTRY_AUTH_FILE. يمكن القيام بذلك باستخدام export REGISTRY_AUTH_FILE=path.

--build

قم ببناء الصور حتى لو تم العثور عليها في التخزين المحلي. استخدم --build=false لتعطيل عمليات البناء تمامًا. (هذا الخيار غير متاح مع عميل Podman البعيد)

ملاحظة: يمكنك أيضًا تجاوز نوع العزل الافتراضي عن طريق تعيين متغير البيئة BUILDAH_ISOLATION. export BUILDAH_ISOLATION=oci. انظر podman-build.1.md لمزيد من المعلومات.

--cert-dir=path

استخدم الشهادات الموجودة في path (*.crt, *.cert, *.key) للاتصال بالسجل. (الافتراضي: /etc/containers/certs.d) للتفاصيل، انظر containers-certs.d(5). (هذا الخيار غير متاح مع عميل Podman البعيد، بما في ذلك أجهزة Mac و Windows (باستثناء WSL2))

--configmap=path

استخدم ملف YAML الخاص بـ Kubernetes configmap في المسار لتوفير مصدر لقيم متغيرات البيئة داخل حاويات Pod. (هذا الخيار غير متاح مع عميل Podman البعيد)

ملاحظة: يمكن استخدام الخيار --configmap عدة مرات أو يمكن استخدام قائمة مسارات مفصولة بفواصل لتمرير ملفات YAML متعددة لـ Kubernetes configmap. قد يكون ملف YAML بتنسيق YAML متعدد المستندات. ولكن، يجب أن يحتوي فقط على configmaps

--context-dir=path

استخدم path كدليل سياق البناء لكل صورة. يتطلب أن يكون خيار --build صحيحًا. (هذا الخيار غير متاح مع عميل Podman البعيد)

--creds=[username[:password]]

[اسم المستخدم[:كلمة المرور]] المستخدم للمصادقة مع السجل، إذا كان مطلوبًا. إذا لم يتم توفير قيمة واحدة أو كلتا القيمتين، يظهر موجه سطر الأوامر ويمكن إدخال القيمة. يتم إدخال كلمة المرور بدون عرض.

لاحظ أن بيانات الاعتماد المحددة تستخدم فقط للمصادقة مع السجلات المستهدفة. لا يتم استخدامها للمرايا أو عند إعادة كتابة السجل (انظر containers-registries.conf(5))؛ للمصادقة مع هذه، ضع في اعتبارك استخدام ملف containers-auth.json(5).

--force

طباعة بيان الاستخدام

--ip=IP address

تعيين عنوان IP ثابت للـ Pod. يمكن تحديد هذا الخيار عدة مرات عندما يقوم kube play بإنشاء أكثر من Pod واحد. ملاحظة: عند الانضمام إلى شبكات متعددة، استخدم الصيغة --network name:ip=<ip>.

--log-driver=driver

تعيين برنامج تشغيل التسجيل لجميع الحاويات التي تم إنشاؤها.

--log-opt=name=value

خيارات خاصة ببرنامج تشغيل التسجيل.

قم بتعيين تكوين تسجيل مخصص. الأسماء *المعتمدة* التالية:

path: تحديد مسار لملف السجل
(مثال: --log-opt path=/var/log/container/mycontainer.json)؛

max-size: تحديد الحد الأقصى لحجم ملف السجل
(مثال: --log-opt max-size=10mb)؛

tag: تحديد علامة تسجيل مخصصة للحاوية
(مثال: --log-opt tag="{{.ImageName}}". يدعم نفس المفاتيح الموجودة في podman inspect --format. هذا الخيار مدعوم حاليًا فقط بواسطة برنامج تشغيل السجل journald.

--mac-address=MAC address

تعيين عنوان MAC ثابت للـ Pod. يمكن تحديد هذا الخيار عدة مرات عندما يقوم kube play بإنشاء أكثر من Pod واحد. ملاحظة: عند الانضمام إلى شبكات متعددة، استخدم الصيغة --network name:mac=<mac>.

--network=mode, --net

تعيين وضع الشبكة للـ Pod.

القيم الصالحة لـ mode هي:

•
bridge[:OPTIONS,...]: إنشاء مكدس شبكة على الجسر الافتراضي. هذا هو الافتراضي للحاويات المسموح لها بالجذر. من الممكن تحديد الخيارات الإضافية التالية:
  • alias=name: إضافة اسم مستعار خاص بالشبكة للحاوية.
  • ip=IPv4: تحديد عنوان IPv4 ثابت لهذه الحاوية.
  • ip6=IPv6: تحديد عنوان IPv6 ثابت لهذه الحاوية.
  • mac=MAC: تحديد عنوان MAC ثابت لهذه الحاوية.
  • interface_name=name: تحديد اسم لواجهة الشبكة التي تم إنشاؤها داخل الحاوية.
  • host_interface_name=name: تحديد اسم لواجهة الشبكة التي تم إنشاؤها خارج الحاوية.
سيتم تمرير أي خيارات أخرى إلى netavark دون التحقق. يمكن أن يكون هذا مفيدًا لتمرير الوسائط إلى مكونات netavark الإضافية.

على سبيل المثال، لتعيين عنوان IPv4 ثابت وعنوان MAC ثابت، استخدم --network bridge:ip=10.88.0.10,mac=44:33:22:11:00:99.

  • <network name or ID>[:OPTIONS,...]: الاتصال بشبكة معرفة من قبل المستخدم؛ هذا هو اسم الشبكة أو معرفها من شبكة تم إنشاؤها بواسطة podman network create. من الممكن تحديد نفس الخيارات الموضحة تحت وضع bridge أعلاه. استخدم الخيار --network عدة مرات لتحديد شبكات إضافية.
    للتوافق مع الإصدارات السابقة، من الممكن أيضًا تحديد شبكات مفصولة بفواصل في الوسيطة الأولى --network، ولكن هذا يمنعك من استخدام الخيارات الموضحة تحت قسم bridge أعلاه.
  • none: إنشاء مساحة اسم شبكة للحاوية ولكن لا تقم بتكوين واجهات شبكة لها، وبالتالي لا تتمتع الحاوية بأي اتصال شبكة.
  • container:id: إعادة استخدام مكدس شبكة حاوية أخرى.
  • host: استخدام مساحة اسم شبكة المضيف للحاوية بدلاً من إنشاء مساحة اسم معزولة. تحذير: هذا يمنح الحاوية وصولاً كاملاً إلى مقابس Unix المجردة ومقابس TCP/UDP المرتبطة بـ localhost. نظرًا لأن هذه الآليات غالبًا ما تستخدم لمنع الوصول إلى خدمات النظام الحساسة، وعزلها عن الوصول إليها من قبل كيانات خارجية، فقد يعتبر استخدام هذا الخيار ثغرة أمنية.
  • ns:path: مسار إلى مساحة اسم شبكة للانضمام إليها.
  • private: إنشاء مساحة اسم جديدة للحاوية. يستخدم هذا وضع bridge للحاويات المسموح لها بالجذر و slirp4netns للحاويات غير المسموح لها بالجذر.
  • slirp4netns[:OPTIONS,...]: استخدام slirp4netns(1) لإنشاء مكدس شبكة للمستخدم. من الممكن تحديد هذه الخيارات الإضافية، ويمكن أيضًا تعيينها باستخدام network_cmd_options في containers.conf:
  • allow_host_loopback=true|false: السماح لـ slirp4netns بالوصول إلى عنوان IP الخاص بحلقة المضيف (الافتراضي هو 10.0.2.2 أو عنوان IP الثاني من شبكة CIDR الخاصة بـ slirp4netns عند تغييره، انظر خيار CIDR أدناه). الافتراضي هو false.
  • mtu=MTU: تحديد MTU لاستخدامه في هذه الشبكة. (الافتراضي هو 65520).
  • cidr=CIDR: تحديد نطاق IP لاستخدامه في ت
شبكته. (الافتراضي هو 10.0.2.0/24).
  • enable_ipv6=true|false: تمكين IPv6. الافتراضي هو true. (مطلوب لـ outbound_addr6).
  • outbound_addr=INTERFACE: حدد واجهة الإخراج التي يربط بها slirp (حركة مرور ipv4 فقط).
  • outbound_addr=IPv4: حدد عنوان ipv4 للإخراج الذي يربط به slirp.
  • outbound_addr6=INTERFACE: حدد واجهة الإخراج التي يربط بها slirp (حركة مرور ipv6 فقط).
  • outbound_addr6=IPv6: حدد عنوان ipv6 للإخراج الذي يربط به slirp.
  • port_handler=rootlesskit: استخدم rootlesskit لإعادة توجيه المنافذ. الافتراضي.
    ملاحظة: يغير rootlesskit عنوان IP المصدر للحزم الواردة إلى عنوان IP داخل مساحة اسم شبكة الحاوية، وعادةً ما يكون 10.0.2.100. إذا كان التطبيق يتطلب عنوان IP المصدر الحقيقي، على سبيل المثال، سجلات خادم الويب، استخدم معالج منفذ slirp4netns. يتم أيضًا استخدام معالج منفذ rootlesskit للحاويات عديمة الجذر عند الاتصال بالشبكات المعرفة من قبل المستخدم.
  • port_handler=slirp4netns: استخدم إعادة توجيه منفذ slirp4netns، فهو أبطأ من rootlesskit ولكنه يحافظ على عنوان IP المصدر الصحيح. لا يمكن استخدام معالج المنفذ هذا للشبكات المعرفة من قبل المستخدم.
    • •
    pasta[:OPTIONS,...]: استخدم pasta(1) لإنشاء مكدس شبكات في وضع المستخدم.
    هذا هو الافتراضي للحاويات عديمة الجذر ومدعوم فقط في وضع عديم الجذر.
    بشكل افتراضي، يتم نسخ عناوين IPv4 و IPv6 والمسارات، بالإضافة إلى اسم واجهة الحاوية، من المضيف. تحافظ إعادة توجيه المنافذ على عنوان IP المصدر الأصلي. يمكن تحديد الخيارات الموضحة في pasta(1) كحجج مفصولة بفواصل.
    فيما يتعلق بخيارات pasta(1)، يتم افتراض --config-net افتراضيًا، من أجل تكوين الشبكات عند بدء تشغيل الحاوية، ويتم افتراض --no-map-gw أيضًا افتراضيًا، لتجنب الوصول المباشر من الحاوية إلى المضيف باستخدام عنوان البوابة. يمكن تجاوز الأخير عن طريق تمرير --map-gw في خيارات pasta المحددة (على الرغم من أنها ليست خيارًا فعليًا لـ pasta(1)).
    لتحسين التكامل مع معالجة DNS، يتم تمرير --dns-forward 169.254.1.1، ويتم إضافة هذا العنوان إلى resolv.conf(5) كمحلل أول. من الممكن تمرير --dns-forward بشكل صريح في حال كان يجب استخدام عنوان IP مختلف. لجعل الإدخال host.containers.internal في /etc/hosts يعمل ويسمح بالاتصالات بالمضيف، يتم تمرير --map-guest-addr 169.254.1.2. مرة أخرى، يمكن تعيينه بشكل صريح لاختيار عنوان IP مختلف.
    أيضًا، يتم تمرير -t none و -u none إذا لم يتم تكوين أي إعادة توجيه منافذ TCP أو UDP من المضيف إلى الحاوية (عبر --publish الخاص بـ Podman أو عن طريق تمرير خيارات pasta -t/-u مباشرة)، لتعطيل إعادة توجيه المنافذ تلقائيًا بناءً على المنافذ المرتبطة. بشكل مشابه، يتم استخدام -T none و -U none لتعطيل نفس الوظيفة من الحاوية إلى المضيف.
    يمكن أيضًا تعيين جميع الخيارات في containers.conf(5)؛ راجع المفتاح pasta_options ضمن قسم الشبكة في هذا الملف.
    بعض الأمثلة:
    • pasta:--map-gw: السماح للحاوية بالوصول مباشرة إلى المضيف باستخدام عنوان البوابة.
    • pasta:--mtu,1500: تحديد MTU بحجم 1500 بايت لواجهة tap في الحاوية.
    • pasta:--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,-m,1500,--no-ndp,--no-dhcpv6,--no-dhcp, يعادل خيارات slirp4netns(1) الافتراضية: تعطيل IPv6، وتعيين 10.0.2.0/24 لواجهة tap0 في الحاوية، مع بوابة 10.0.2.3، وتمكين موجه DNS الذي يمكن الوصول إليه عند 10.0.2.3، وتعيين MTU إلى 1500 بايت، وتعطيل دعم NDP و DHCPv6 و DHCP.
    • pasta:-I,tap0,--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,--no-ndp,--no-dhcpv6,--no-dhcp, يعادل خيارات slirp4netns(1) الافتراضية مع تجاوزات Podman: نفس الخيارات المذكورة أعلاه، ولكن مع ترك MTU بحجم 65520 بايت.
    • pasta:-t,auto,-u,auto,-T,auto,-U,auto: تمكين إعادة توجيه المنافذ التلقائي بناءً على المنافذ المرتبطة التي تم ملاحظتها من جانبي المضيف والحاوية.
    • pasta:-T,5201: تمكين إعادة توجيه منفذ TCP 5201 من الحاوية إلى المضيف، باستخدام واجهة loopback بدلاً من واجهة tap لتحسين الأداء.

    عند عدم تحديد خيار شبكة وعدم تكوين وضع شبكة host في ملف YAML، يتم إنشاء مكدس شبكات جديد وتوصيل الحاويات به، مما يجعل الاتصال بين الحاويات ممكنًا.

    --no-hostname

    لا تقم بإنشاء ملف /etc/hostname في الحاويات.

    بشكل افتراضي، يدير Podman ملف /etc/hostname، مضيفًا اسم مضيف الحاوية الخاص بها. عند تعيين الخيار --no-hostname، سيتم الاحتفاظ بملف /etc/hostname الخاص بالصورة دون تعديل إذا كان موجودًا.

    --no-hosts

    لا تقم بتعديل ملف /etc/hosts في الحاوية.

    يفترض Podman التحكم في ملف /etc/hosts الخاص بالحاوية بشكل افتراضي ويضيف إدخالات لاسم الحاوية (انظر الخيار --name) واسم المضيف (انظر الخيار --hostname)، المضيفين الداخليين host.containers.internal و host.docker.internal، بالإضافة إلى أي اسم مضيف تمت إضافته باستخدام الخيار --add-host. راجع الخيار --add-host للحصول على التفاصيل. يؤدي تمرير --no-hosts إلى تعطيل ذلك، بحيث يتم الاحتفاظ بملف /etc/hosts الخاص بالصورة دون تعديل. يمكن تحقيق نفس الشيء عالميًا عن طريق تعيين no_hosts=true في containers.conf.

    يتعارض هذا الخيار مع المضيف المضاف في YAML الخاص بـ Kubernetes.

    --no-pod-prefix

    لا تسبق اسم الحاوية باسم الحاوية.

    --publish=[[ip:][hostPort]:]containerPort[/protocol]

    تعريف أو تجاوز تعريف منفذ في ملف YAML.

    يتم دمج قوائم المنافذ في ملف YAML وفي سطر الأوامر. تتم المطابقة باستخدام حقل containerPort. إذا كان containerPort موجودًا في كل من ملف YAML والخيارة، فإن الخيارة لها الأسبقية.

    --publish-all

    سيؤدي تعيين هذا الخيار إلى true إلى كشف جميع المنافذ للمضيف، حتى لو تم تحديدها فقط عبر containerPort في K8 YAML. من حيث المنفذ الذي سيتم كشفه، فإن --publish له أولوية أعلى من hostPort، وله أولوية أعلى من containerPort.

    إذا تم تعيينه إلى false (وهو الافتراضي)، فسيتم نشر المنافذ المحددة عبر hostPort أو --publish فقط على المضيف.

    --quiet, -q

    كتم إخراج المعلومات عند سحب الصور.

    --replace

    يقوم بإيقاف تشغيل الحاويات التي تم إنشاؤها بواسطة تشغيل سابق لـ kube play وإعادة إنشاء الحاويات. يستخدم هذا الخيار للحفاظ على الحاويات الحالية محدثة بناءً على Kubernetes YAML.

    --seccomp-profile-root=path

    مسار الدليل لملفات تعريف seccomp (الافتراضي: "/var/lib/kubelet/seccomp"). (هذا الخيار غير متاح مع عميل Podman البعيد، بما في ذلك أجهزة Mac و Windows (باستثناء WSL2)).

    --start

    ابدأ الحاوية بعد إنشائها، اضبطه على false لإنشائها فقط.

    --tls-verify

    طلب HTTPS والتحقق من الشهادات عند الاتصال بالسجلات (الافتراضي: true). إذا تم تعيينه صراحةً إلى true، يتم استخدام التحقق من TLS. إذا تم تعيينه إلى false، فلا يتم استخدام التحقق من TLS. إذا لم يتم تحديده، يتم استخدام التحقق من TLS ما لم يتم إدراج السجل المستهدف كسجل غير آمن في containers-registries.conf(5).

    --userns=mode

    تعيين وضع مساحة اسم المستخدم للحاوية.

    إذا لم يتم تعيين --userns، يتم تحديد القيمة الافتراضية على النحو التالي: - إذا تم تعيين --pod، يتم تجاهل --userns ويتم استخدام مساحة اسم المستخدم للحاوية. - إذا تم تعيين متغير البيئة PODMAN_USERNS، يتم استخدام قيمته. - إذا تم تحديد userns في containers.conf، يتم استخدام هذه القيمة. - بخلاف ذلك، يفترض --userns=host.

    --userns="" (أي، سلسلة فارغة) هو اسم مستعار لـ --userns=host.

    هذا الخيار غير متوافق مع --gidmap و --uidmap و --subuidname و --subgidname.

    تعيينات المفاتيح لمستخدم عديم الجذر --userns:

    المفتاح مستخدم المضيف مستخدم الحاوية
    auto $UID nil (لا يتم تعيين UID المستخدم المضيف إلى الحاوية.)
    host $UID 0 (يتم تعيين حساب المستخدم الافتراضي إلى المستخدم الجذر في الحاوية.)
    keep-id $UID $UID (تعيين حساب المستخدم إلى نفس UID داخل الحاوية.)
    keep-id:uid=200,gid=210 $UID 200:210 (تعيين حساب المستخدم إلى قيم UID و GID المحددة داخل الحاوية.)
    nomap $UID nil (لا يتم تعيين UID المستخدم المضيف إلى الحاوية.)

    القيم mode الصالحة هي:

    auto[:OPTIONS,...]: إنشاء مساحة اسم مستخدم فريدة تلقائيًا.

    • وضع rootful: يتطلب العلم --userns=auto أن يتم تحديد اسم المستخدم containers في ملفات /etc/subuid و /etc/subgid، مع نطاق غير مستخدم من معرفات المستخدمين الفرعية التي يُسمح لحاويات Podman بتخصيصها. مثال: containers:2147483647:2147483648.
    • وضع عديم الجذر: سيتم استخدام نطاقات المستخدمين من ملفات /etc/subuid و /etc/subgid. لاحظ أن تشغيل حاوية واحدة بدون استخدام --userns=auto سيستخدم النطاق الكامل لمعرفات المستخدمين ولن يسمح بمزيد من التقسيم. انظر subuid(5).

    يقوم Podman بتخصيص نطاقات فريدة من معرفات المستخدمين (UIDs) ومعرفات المجموعات (GIDs) من معرفات المستخدمين الفرعية containers. يعتمد حجم النطاقات على عدد معرفات المستخدمين المطلوبة في الصورة. يمكن تجاوز عدد معرفات المستخدمين والمجموعات باستخدام الخيار size.

    الخيار --userns=keep-id يستخدم جميع معرفات المستخدمين والمجموعات الفرعية الخاصة بالمستخدم. الخيار --userns=nomap يستخدم جميع معرفات المستخدمين والمجموعات الفرعية الخاصة بالمستخدم باستثناء معرف المستخدم الخاص به. استخدام --userns=auto عند بدء حاويات جديدة لا يعمل طالما توجد أي حاويات تم تشغيلها باستخدام --userns=nomap أو --userns=keep-id بدون تحديد حجم مساحة اسم المستخدم.

    podman-kube-play(1)

    الحزمة: podman

    التراخيص: Apache-2.0

    NAME

    podman-kube-play - Play a Kubernetes YAML file against the local container engine

    SYNOPSIS

    podman kube play [-i FILE] [-a] [-c] [--creds CREDS] [--identity IDENTITY] [--network NETWORK] [-q] [--replace] [--start-paused] [--tls-verify BOOL] POD ...

    podman kube play --help

    DESCRIPTION

    The podman kube play command takes a Kubernetes YAML file (or multiple files) describing Pods, Deployments, DaemonSets, StatefulSets, or Jobs, and runs them as containers on the user's machine.

    This command is intended for development and testing purposes. It translates Kubernetes objects into runnable containers and associated Podman resources like networks and volumes.

    OPTIONS

    -a, --all:: All YAML files will be played. If this is not set, then you must specify at least one POD.

    -c, --creds CREDS:: The username and password of the registry to use for pulling the image.

    -i, --infile FILE:: Input file from which to read the Kubernetes YAML. Can be specified multiple times.

    --identity IDENTITY:: The identity file to use for authentication with the registry.

    --network NETWORK:: Specify a network to use for the containers. This network must already exist in Podman.

    -q, --quiet:: Suppress verbose output.

    --replace:: Replace existing Pods that are already running and managed by Podman.

    --start-paused:: Start containers in a paused state.

    --tls-verify BOOL:: Whether to verify the TLS certificate of the registry. Default is true.

    --help:: Print usage information.

    EXAMPLES

    Run a pod defined in mypod.yaml:

    $ podman kube play mypod.yaml

    Run multiple pods defined in pod1.yaml and pod2.yaml:

    $ podman kube play pod1.yaml pod2.yaml

    Run all pods in the current directory:

    $ podman kube play -a

    Run a pod and replace any existing pod with the same name:

    $ podman kube play --replace mypod.yaml
