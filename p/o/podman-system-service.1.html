الحزمة: podman

التراخيص: Apache-2.0

podman-system-service(1) دليل الأوامر العامة podman-system-service(1)

الاسم

podman-system-service - تشغيل خدمة API

الملخص

podman system service [خيارات]

الوصف

يقوم الأمر podman system service بإنشاء خدمة استماع تستجيب لطلبات API الخاصة بـ Podman. الأمر متاح على أنظمة Linux ويتم تنفيذه عادةً في خدمات systemd. الأمر غير متاح عند تنفيذ أمر Podman مباشرة على مضيف Windows أو macOS أو في مواقف أخرى يصل فيها أمر Podman إلى خدمة Podman API عن بُعد.

تنقسم واجهة برمجة التطبيقات REST التي توفرها podman system service إلى جزأين: طبقة توافق توفر دعمًا لواجهة برمجة التطبيقات Docker v1.40، وطبقة Libpod الأصلية الخاصة بـ Podman. تتوفر وثائق للأخيرة على https://docs.podman.io/en/latest/_static/api.html. يتم ترقيم كلا واجهتي برمجة التطبيقات، ولكن الخادم لا يرفض الطلبات ذات الإصدار غير المدعوم.

تشغيل الأمر في خدمة systemd

يدعم الأمر podman system service تنشيط مقبس systemd. عند تشغيل الأمر في خدمة systemd، يمكن توفير خدمة API عند الطلب. إذا لم تكن خدمة systemd قيد التشغيل بالفعل، فسيتم تنشيطها بمجرد اتصال عميل بمقبس الاستماع. ثم يقوم systemd بتنفيذ أمر podman system service. بعد مرور بعض الوقت من عدم النشاط، كما هو محدد في الخيار --time، ينتهي الأمر. يقوم systemd بتعيين حالة podman.service على غير نشط. في هذه النقطة، لا توجد عملية podman system service قيد التشغيل. لا يتم إهدار موارد الحوسبة غير الضرورية. بمجرد اتصال عميل آخر، يقوم systemd بتنشيط خدمة systemd مرة أخرى.

ملفات وحدة systemd التي تعلن عن خدمة Podman API للمستخدمين هي:

  • /usr/lib/systemd/user/podman.service
  • /usr/lib/systemd/user/podman.socket

في الملف podman.socket، يتم تعريف مسار مقبس Unix للاستماع بواسطة

ListenStream=%t/podman/podman.sock

يحتوي المسار على محدد systemd %t والذي يقوم systemd بتوسيعه إلى قيمة المتغير البيئي XDG_RUNTIME_DIR (راجع محددات systemd في صفحة دليل systemd.unit(5)).

بالإضافة إلى خدمات مستخدم systemd، توجد أيضًا خدمة نظام systemd podman.service. تقوم بتشغيل Podman rootful ويتم الوصول إليها من مقبس Unix /run/podman/podman.sock. راجع ملفات وحدة systemd:

  • /usr/lib/systemd/system/podman.service
  • /usr/lib/systemd/system/podman.socket

لا يدعم الأمر podman system service أكثر من مقبس استماع واحد لخدمة API.

ملاحظة: تقوم ملفات وحدة systemd الافتراضية (النظام والمستخدم) بتغيير خيار مستوى السجل إلى info من error. يوفر هذا التغيير معلومات إضافية حول كل طلب API.

تشغيل الأمر مباشرة

لدعم تشغيل خدمة API دون استخدام خدمة systemd، يأخذ الأمر أيضًا وسيط نهاية نقطة اختياري لواجهة برمجة التطبيقات في شكل URI. على سبيل المثال، unix:///tmp/foobar.sock أو tcp://localhost:8080. إذا لم يتم توفير نهاية نقطة، فسيتم استخدام الافتراضيات. نهاية نقطة الخدمة rootful الافتراضية هي unix:///run/podman/podman.sock و rootless هي unix://$XDG_RUNTIME_DIR/podman/podman.sock (على سبيل المثال unix:///run/user/1000/podman/podman.sock)

الوصول إلى مقبس Unix من داخل حاوية

للوصول إلى خدمة API داخل حاوية: - قم بتحميل المقبس كوحدة تخزين - قم بتشغيل الحاوية باستخدام --security-opt label=disable

الأمان

يرجى ملاحظة أن واجهة برمجة التطبيقات تمنح وصولاً كاملاً إلى جميع وظائف Podman، وبالتالي تسمح بتنفيذ تعليمات برمجية عشوائية كالمستخدم الذي يقوم بتشغيل واجهة برمجة التطبيقات، دون القدرة على الحد من هذا الوصول أو تدقيقه. يعتمد نموذج الأمان لواجهة برمجة التطبيقات على الوصول عبر مقبس Unix مع تقييد الوصول عبر أذونات الملفات القياسية، مما يضمن أن المستخدم الذي يقوم بتشغيل الخدمة فقط هو من سيكون قادرًا على الوصول إليها. يمكن استخدام TLS لتأمين هذا المقبس عن طريق مطالبة العملاء بتقديم شهادة موقعة من سلطة شهادات موثوقة ("CA")، وكذلك للسماح للعميل بالتحقق من هوية واجهة برمجة التطبيقات. نوصي بشدة بعدم جعل مقبس واجهة برمجة التطبيقات متاحًا عبر الشبكة (أي، ربط الخدمة بعنوان tcp) دون تمكين TLS المتبادل للمصادقة على العميل. حتى الوصول عبر Localhost يحمل مخاطر - أي شخص لديه وصول إلى النظام سيكون قادرًا على الوصول إلى واجهة برمجة التطبيقات. إذا كان الوصول عن بعد مطلوبًا، فنحن نوصي بدلاً من ذلك بإعادة توجيه مقبس واجهة برمجة التطبيقات عبر SSH، وتقييد الوصول على الجهاز البعيد إلى أقصى حد ممكن. إذا كان يجب استخدام عنوان tcp بدون TLS، فيوصى باستخدام الخيار --cors لتحسين الأمان.

الخيارات

--cors

رؤوس CORS لحقنها في استجابة HTTP. القيمة الافتراضية هي سلسلة فارغة مما يعطل رؤوس CORS.

--help, -h

طباعة بيان الاستخدام.

--time, -t

الوقت حتى انتهاء صلاحية الجلسة بالثواني. الافتراضي هو 5 ثوانٍ. القيمة 0 تعني عدم وجود انتهاء صلاحية، وبالتالي لا تنتهي صلاحية الجلسة.

--tls-cert=path

مسار إلى ملف PEM يحتوي على شهادة TLS لتقديمها للعملاء. يجب أيضًا توفير --tls-key.

--tls-client-ca=path

مسار إلى ملف PEM يحتوي على حزمة شهادات TLS للتحقق من اتصالات العملاء. سيتم رفض الاتصالات التي لا تقدم شهادة أو شهادة غير موقعة من قبل إحدى هذه الشهادات.

--tls-key=path

مسار إلى ملف PEM يحتوي على المفتاح الخاص المطابق لـ --tls-cert. يجب أيضًا توفير --tls-cert.

يمكن تغيير انتهاء الصلاحية الافتراضي عبر الحقل service_timeout=VALUE في containers.conf. انظر containers.conf(5) لمزيد من المعلومات.

أمثلة

بدء مقبس systemd للمستخدم لخدمة rootless.

systemctl --user start podman.socket

تكوين متغير البيئة DOCKER_HOST للإشارة إلى مقبس Podman حتى يمكن استخدامه عبر أدوات Docker API مثل docker-compose.

$ export DOCKER_HOST=unix://$XDG_RUNTIME_DIR/podman/podman.sock
$ docker-compose up

تكوين مقبس systemd ليتم تشغيله تلقائيًا بعد إعادة التشغيل، وتشغيله كمستخدم محدد.

systemctl --user enable podman.socket
loginctl enable-linger <USER>

بدء مقبس systemd للخدمة rootful.

sudo systemctl start podman.socket

تكوين المقبس ليتم تشغيله تلقائيًا بعد إعادة التشغيل.

sudo systemctl enable podman.socket

من الممكن تشغيل واجهة برمجة التطبيقات دون استخدام تنشيط مقبس systemd. في هذه الحالة، لن تكون واجهة برمجة التطبيقات متاحة عند الطلب لأن الأمر سيبقى متوقفًا بعد انتهاء مهلة عدم النشاط. تشغيل API مع مهلة عدم نشاط مدتها 5 ثوانٍ دون استخدام تنشيط المقبس.

podman system service --time 5

تم استخدام المقبس الافتراضي حيث لم يتم تقديم وسيط URI.

تشغيل خدمة API مع مسار مقبس مخصص وعدم وجود مهلة:

podman system service --time 0 unix:///var/run/mypodman.sock

يبدأ هذا خدمة API بالاستماع على المقبس المخصص /var/run/mypodman.sock بدون مهلة عدم نشاط (يعمل إلى أجل غير مسمى).
