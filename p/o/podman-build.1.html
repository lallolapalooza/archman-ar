podman-build(1)

الحزمة: podman

التراخيص: Apache-2.0

podman-build(1) دليل الأوامر العامة podman-build(1)

الاسم

podman-build - بناء صورة حاوية باستخدام ملف حاوية (Containerfile)

الملخص

podman build [خيارات] [سياق]

podman image build [خيارات] [سياق]

الوصف

podman build يبني صورة باستخدام تعليمات من ملف حاوية واحد أو أكثر (Containerfiles) أو ملفات Docker (Dockerfiles) ودليل سياق بناء محدد. ملف الحاوية (Containerfile) يستخدم نفس صيغة ملف Docker (Dockerfile) داخليًا. في هذا المستند، يمكن أن يكون الملف المشار إليه بـ Containerfile ملفًا باسم 'Containerfile' أو 'Dockerfile' حصريًا. أي ملف لديه امتداد إضافي لن يتم التعرف عليه بواسطة podman build . إلا إذا تم استخدام العلم -f لتحديد الملف.

يمكن تحديد دليل سياق البناء كعنوان URL (http أو https) لأرشيف، مستودع git، أو ملف حاوية (Containerfile).

عند استدعائه مع -f ومسار إلى ملف حاوية (Containerfile)، وبدون دليل سياق (CONTEXT) صريح، يستخدم Podman الدليل الأصل لملف الحاوية كسياق بناء له.

ملفات الحاوية (Containerfiles) التي تنتهي باللاحقة ".in" يتم معالجتها مسبقًا عبر CPP(1). يمكن أن يكون هذا مفيدًا لتقسيم ملفات الحاوية (Containerfiles) إلى عدة أجزاء قابلة لإعادة الاستخدام والتي يمكن استخدامها عبر توجيه #include الخاص بـ CPP. ملفات الحاوية (Containerfiles) التي تنتهي بـ .in مقيدة بعدم وجود أسطر تعليق إلا إذا كانت أوامر CPP. ملاحظة، يمكن استخدام ملف Containerfile.in بواسطة أدوات أخرى عند معالجتها مسبقًا يدويًا عبر cpp -E.

عندما يكون عنوان URL أرشيفًا، يتم تنزيل محتويات عنوان URL إلى موقع مؤقت واستخراجها قبل التنفيذ.

عندما يكون عنوان URL ملف حاوية (Containerfile)، يتم تنزيل ملف الحاوية إلى موقع مؤقت.

عندما يتم تعيين مستودع Git كعنوان URL، يتم استنساخ المستودع محليًا ثم تعيينه كسياق. يعامل عنوان URL كمستودع Git إذا كان لديه بادئة git:// أو لاحقة .git.

ملاحظة: podman build يستخدم رمزًا مصدره مشروع Buildah لبناء صور الحاويات. يقوم كود Buildah هذا بإنشاء حاويات Buildah لخيارات RUN في تخزين الحاويات. في مواقف معينة، عندما يتعطل podman build أو يقوم المستخدمون بإيقاف عملية podman build، يمكن ترك هذه الحاويات الخارجية في تخزين الحاويات. استخدم الأمر podman ps --all --external لرؤية هذه الحاويات.

الأمر podman buildx build هو اسم مستعار للأمر podman build. ليست كل ميزات buildx build متاحة في Podman. تم توفير الخيار buildx build للتوافق البرمجي.

الخيارات

--add-host=hostname[;hostname[;...]]:ip

أضف تعيين مضيف مخصص إلى ملف /etc/hosts الخاص بالحاوية.

يأخذ الخيار اسم مضيف واحد أو أكثر مفصولًا بفاصلة منقوطة لتعيينه إلى عنوان IPv4 أو IPv6 واحد، مفصولًا بنقطتين. يمكن استخدامه أيضًا للكتابة فوق عناوين IP الخاصة بأسماء المضيفين التي يضيفها Podman إلى /etc/hosts افتراضيًا (انظر أيضًا خيارات --name و --hostname). يمكن تحديد هذا الخيار عدة مرات لإضافة تعيينات إضافية إلى /etc/hosts. يتعارض مع الخيار --no-hosts ويتعارض مع no_hosts=true في containers.conf.

بدلاً من عنوان IP، يمكن إعطاء العلامة الخاصة host-gateway. يتم حل هذا إلى عنوان IP يمكن للحاوية استخدامه للاتصال بالمضيف. يعتمد عنوان IP المختار على إعداد الشبكة الخاص بك، لذلك لا يوجد ضمان بأن Podman يمكنه تحديد عنوان host-gateway تلقائيًا، مما سيؤدي إلى فشل Podman برسالة خطأ. يمكنك الكتابة فوق عنوان IP هذا باستخدام خيار host_containers_internal_ip في containers.conf.

يستخدم عنوان host-gateway أيضًا بواسطة Podman لإضافة أسماء المضيفين host.containers.internal و host.docker.internal تلقائيًا إلى /etc/hosts. يمكنك منع ذلك إما عن طريق إعطاء الخيار --no-hosts، أو عن طريق تعيين host_containers_internal_ip="none" في containers.conf. إذا لم يتم تكوين عنوان host-gateway يدويًا وفشل Podman في تحديد عنوان IP تلقائيًا، فسيتخطى Podman بصمت إضافة أسماء المضيفين الداخلية هذه إلى /etc/hosts. إذا كان Podman يعمل في آلة افتراضية باستخدام podman machine (وهذا يشمل مضيفي Mac و Windows)، فسيتخطى Podman بصمت إضافة أسماء المضيفين الداخلية إلى /etc/hosts، إلا إذا تم تكوين عنوان IP يدويًا؛ يتم حل أسماء المضيفين الداخلية بواسطة محلل DNS لـ gvproxy بدلاً من ذلك.

سيستخدم Podman الملف /etc/hosts الخاص بالمضيف كأساس افتراضيًا، أي أن أي اسم مضيف موجود في هذا الملف سيكون موجودًا أيضًا في ملف /etc/hosts الخاص بالحاوية. يمكن تكوين ملف أساسي مختلف باستخدام الإعداد base_hosts_file في containers.conf.

--all-platforms

بدلاً من البناء لمجموعة من المنصات المحددة باستخدام خيار --platform، قم بفحص صور الأساس للبناء، وقم بالبناء لجميع المنصات التي تتوفر لها جميعًا. المراحل التي تستخدم scratch كنقطة انطلاق لا يمكن فحصها، لذلك يجب أن تكون هناك مرحلة واحدة غير scratch على الأقل لكي يعمل الاكتشاف بشكل مفيد.

--annotation=annotation=value

أضف علامة annotation للصورة (على سبيل المثال، annotation=value) إلى بيانات التعريف للصورة. يمكن استخدامها عدة مرات.

ملاحظة: هذه المعلومات غير موجودة في تنسيقات صور Docker، لذلك يتم تجاهلها عند كتابة الصور بتنسيقات Docker.

--arch=arch

قم بتعيين بنية الصورة المراد بناؤها، وبنية صورة الأساس المراد سحبها، إذا كان البناء يستخدم واحدة، إلى القيمة المقدمة بدلاً من استخدام بنية المضيف للبناء. ما لم يتم تجاوز ذلك، تتطابق عمليات البحث اللاحقة عن نفس الصورة في التخزين المحلي مع هذه البنية، بغض النظر عن المضيف. (أمثلة: arm، arm64، 386، amd64، ppc64le، s390x)

--authfile=path

مسار ملف المصادقة. الافتراضي هو ${XDG_RUNTIME_DIR}/containers/auth.json على Linux، و $HOME/.config/containers/auth.json على Windows/macOS. يتم إنشاء الملف بواسطة podman login. إذا لم يتم العثور على حالة المصادقة هناك، يتم التحقق من $HOME/.docker/config.json، والذي يتم تعيينه باستخدام docker login.

ملاحظة: هناك أيضًا خيار لتجاوز المسار الافتراضي لملف المصادقة عن طريق تعيين متغير البيئة REGISTRY_AUTH_FILE. يمكن القيام بذلك عن طريق export REGISTRY_AUTH_FILE=path.

--build-arg=arg=value

يحدد وسيط بناء وقيمته، والذي يتم استيفاؤه في التعليمات المقروءة من ملفات الحاوية (Containerfiles) بنفس الطريقة التي يتم بها استيفاء متغيرات البيئة، ولكن هذه الوسائط لا تتم إضافتها إلى قائمة متغيرات البيئة في تكوين الصورة الناتجة.

--build-arg-file=path

يحدد ملفًا يحتوي على أسطر من وسائط البناء بالصيغة arg=value. اسم الملف المقترح هو argfile.conf.

يتم تجاهل أسطر التعليقات التي تبدأ بـ #، إلى جانب الأسطر الفارغة. يجب أن تكون جميع الأسطر الأخرى بتنسيق arg=value المقدمة إلى --build-arg.

إذا تم توفير العديد من الوسائط عبر الخيارين --build-arg-file و --build-arg، يتم دمج وسائط البناء عبر جميع الملفات والوسائط المقدمة من سطر الأوامر.

يتم قراءة أي ملف مقدم في خيار --build-arg-file قبل الوسائط المقدمة عبر خيار --build-arg.

عندما يتم تحديد اسم وسيط معين عدة مرات، فإن الحالة الأخيرة هي التي يتم تمريرها إلى عمليات البناء الناتجة. هذا يعني أن قيم --build-arg تتجاوز دائمًا تلك الموجودة في --build-arg-file.

--build-context=name=value

حدد سياق بناء إضافي باستخدام اسمه المختصر وموقعه. يمكن الإشارة إلى سياقات البناء الإضافية بنفس الطريقة التي نصل بها إلى مراحل مختلفة في تعليمات COPY.

القيم الصالحة هي:

  • دليل محلي – على سبيل المثال --build-context project2=../path/to/project2/src
  • عنوان URL لملف مضغوط (tarball) – على سبيل المثال --build-context src=https://example.org/releases/src.tar
  • صورة حاوية – يتم تحديدها باستخدام البادئة container-image://، على سبيل المثال --build-context alpine=container-image://al

Arch manual pages are provided by the Arch Linux community.

هذا الموقع غير مرتبط بـ Arch Linux ولا تابع له بأي شكل من الأشكال. المحتوى هو ترجمة فقط لصفحات دليل Arch المنشورة على man.archlinux.org.

pine:3.15، (يقبل أيضاً docker://، docker-image://)

على جانب Containerfile، قم بالإشارة إلى سياق البناء في جميع الأوامر التي تقبل المعامل "from". إليك كيف قد يبدو ذلك:

FROM [name]
COPY --from=[name] ...
RUN --mount=from=[name] …

تتم مطابقة قيمة [name] مع ترتيب الأولوية التالي:

  • سياق بناء مسمى تم تعريفه باستخدام --build-context [name]=..
  • مرحلة تم تعريفها باستخدام AS [name] داخل Containerfile
  • صورة [name]، سواء كانت محلية أو في سجل بعيد

--cache-from=image

المستودع المراد استخدامه كمصدر محتمل للتخزين المؤقت. عند تحديده، يحاول Buildah البحث عن صور مخبأة مؤقتًا في المستودع المحدد ويحاول سحب الصور المخبأة مؤقتًا بدلاً من تنفيذ خطوات البناء فعليًا محليًا. يحاول Buildah فقط سحب الصور المخزنة مؤقتًا سابقًا إذا تم اعتبارها متطابقة مع ذاكرة التخزين المؤقت.

استخدم الخيار --cache-to لتعبئة مستودع بعيد بمحتوى ذاكرة التخزين المؤقت.

مثال

# تعبئة ذاكرة التخزين المؤقت والتشاور معها أيضًا
buildah build -t test --layers --cache-to registry/myrepo/cache --cache-from registry/myrepo/cache .

ملاحظة: يتم تجاهل الخيار --cache-from ما لم يتم تحديد --layers.

--cache-to=image

قم بتعيين هذا العلامة لتحديد مستودع بعيد يستخدم لتخزين صور ذاكرة التخزين المؤقت. يحاول Buildah دفع صورة ذاكرة التخزين المؤقت المبنية حديثًا إلى المستودع البعيد.

ملاحظة: استخدم الخيار --cache-from لاستخدام محتوى ذاكرة التخزين المؤقت في مستودع بعيد.

مثال

# تعبئة ذاكرة التخزين المؤقت والتشاور معها أيضًا
buildah build -t test --layers --cache-to registry/myrepo/cache --cache-from registry/myrepo/cache .

ملاحظة: يتم تجاهل الخيار --cache-to ما لم يتم تحديد --layers.

--cache-ttl

قم بتقييد استخدام الصور المخبأة مؤقتًا للنظر فقط في الصور التي أقل من duration عمرًا. على سبيل المثال، إذا تم تحديد --cache-ttl=1h، فإن Buildah يأخذ في الاعتبار صور ذاكرة التخزين المؤقت الوسيطة التي تم إنشاؤها خلال فترة ساعة واحدة، ويتم تجاهل صور ذاكرة التخزين المؤقت الوسيطة خارج هذه المدة.

ملاحظة: تعيين --cache-ttl=0 يدويًا يعادل استخدام --no-cache في التنفيذ حيث أن هذا يعني أن المستخدم لا يرغب في استخدام ذاكرة التخزين المؤقت على الإطلاق.

--cap-add=CAP_xxx

عند تنفيذ تعليمات RUN، قم بتشغيل الأمر المحدد في التعليمات مع إضافة القدرة المحددة إلى مجموعة القدرات الخاصة بها. يتم منح بعض القدرات افتراضيًا؛ يمكن استخدام هذا الخيار لإضافة المزيد.

--cap-drop=CAP_xxx

عند تنفيذ تعليمات RUN، قم بتشغيل الأمر المحدد في التعليمات مع إزالة القدرة المحددة من مجموعة القدرات الخاصة بها. يتم منح القدرات CAP_CHOWN، CAP_DAC_OVERRIDE، CAP_FOWNER، CAP_FSETID، CAP_KILL، CAP_NET_BIND_SERVICE، CAP_SETFCAP، CAP_SETGID، CAP_SETPCAP، و CAP_SETUID افتراضيًا؛ يمكن استخدام هذا الخيار لإزالتها.

إذا تم تحديد قدرة لكل من الخيارين --cap-add و --cap-drop، فإنها يتم إسقاطها، بغض النظر عن ترتيب تقديم الخيارات.

--cert-dir=path

استخدم الشهادات في path (*.crt, *.cert, *.key) للاتصال بالسجل. (الافتراضي: /etc/containers/certs.d) للحصول على التفاصيل، راجع containers-certs.d(5). (هذا الخيار غير متاح مع عميل Podman البعيد، بما في ذلك أجهزة Mac و Windows (باستثناء WSL2))

--cgroup-parent=path

المسار إلى cgroups التي يتم إنشاء cgroup للحاوية ضمنها. إذا لم يكن المسار مطلقًا، فسيتم اعتبار المسار نسبيًا لمسار cgroups لعملية التهيئة. يتم إنشاء cgroups إذا لم تكن موجودة بالفعل.

--cgroupns=how

يضبط تكوين مساحات أسماء cgroup عند معالجة تعليمات RUN. يمكن أن تكون القيمة المكونة "" (السلسلة الفارغة) أو "private" للإشارة إلى أنه يتم إنشاء مساحة أسماء cgroup جديدة، أو يمكن أن تكون "host" للإشارة إلى أنه يتم إعادة استخدام مساحة أسماء cgroup التي يتم تشغيل buildah فيها.

--compat-volumes

تعامل مع الدلائل المشار إليها باستخدام تعليمات VOLUME (في هذا البناء، وتلك الموروثة من الصور الأساسية) بحيث لا يمكن تعديل محتوياتها إلا بواسطة تعليمات ADD و COPY. سيتم التراجع عن أي تغييرات تم إجراؤها في تلك المواقع بواسطة تعليمات RUN. قبل تقديم هذا الخيار، كان هذا السلوك هو الافتراضي، ولكنه الآن معطل افتراضيًا.

--compress

تمت إضافة هذا الخيار ليتوافق مع واجهات سطر الأوامر الأخرى للحاويات. لا يتواصل Podman مع خادم أو خادم بعيد. وبالتالي، فإن ضغط البيانات قبل إرسالها غير ذي صلة بـ Podman. (هذا الخيار غير متاح مع عميل Podman البعيد، بما في ذلك أجهزة Mac و Windows (باستثناء WSL2))

--cpp-flag=flags

قم بتعيين علامات إضافية لتمريرها إلى معالج C المسبق cpp(1). تنتهي ملفات Containerfile بلاحقة ".in" ويتم معالجتها مسبقًا عبر cpp(1). يمكن استخدام هذا الخيار لتمرير علامات إضافية إلى cpp. ملاحظة: يمكنك أيضًا تعيين CPPFLAGS افتراضيًا عن طريق تعيين متغير البيئة BUILDAH_CPPFLAGS (على سبيل المثال، export BUILDAH_CPPFLAGS=" -DDEBUG").

--cpu-period=limit

قم بتعيين فترة CPU لمجدول المهام العادل (CFS)، وهي مدة بالميكروثانية. بمجرد استهلاك حصة CPU الخاصة بالحاوية، لن يتم جدولتها للتشغيل حتى تنتهي الفترة الحالية. الافتراضي هو 100000 ميكروثانية.

على بعض الأنظمة، قد لا يُسمح بتغيير حدود الموارد للمستخدمين غير الجذر. لمزيد من التفاصيل، انظر https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

هذا الخيار غير مدعوم في أنظمة cgroups V1 غير الجذر.

--cpu-quota=limit

قم بتقييد حصة مجدول المهام العادل (CFS) لوحدة المعالجة المركزية.

قم بتقييد استخدام وحدة المعالجة المركزية للحاوية. افتراضيًا، تعمل الحاويات بكامل موارد وحدة المعالجة المركزية. الحد هو رقم بالميكروثانية. إذا تم توفير رقم، يُسمح للحاوية باستخدام هذا القدر من وقت وحدة المعالجة المركزية حتى تنتهي فترة وحدة المعالجة المركزية (يمكن التحكم فيها عبر --cpu-period).

على بعض الأنظمة، قد لا يُسمح بتغيير حدود الموارد للمستخدمين غير الجذر. لمزيد من التفاصيل، انظر https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

هذا الخيار غير مدعوم في أنظمة cgroups V1 غير الجذر.

--cpu-shares, -c=shares

حصة وحدة المعالجة المركزية (الوزن النسبي).

افتراضيًا، تحصل جميع الحاويات على نفس نسبة دورات وحدة المعالجة المركزية. يمكن تعديل هذه النسبة عن طريق تغيير وزن حصة وحدة المعالجة المركزية للحاوية مقارنة بالوزن المجمع لجميع الحاويات قيد التشغيل. الوزن الافتراضي هو 1024.

تنطبق النسبة فقط عندما تكون العمليات المستهلكة لوحدة المعالجة المركزية قيد التشغيل. عندما تكون المهام في حاوية واحدة خاملة، يمكن للحاويات الأخرى استخدام وقت وحدة المعالجة المركزية المتبقي. يختلف المقدار الفعلي لوقت وحدة المعالجة المركزية اعتمادًا على عدد الحاويات قيد التشغيل على النظام.

على سبيل المثال، لنفترض ثلاث حاويات، واحدة لها حصة وحدة معالجة مركزية تبلغ 1024 واثنتان أخريان لهما إعداد حصة وحدة معالجة مركزية تبلغ 512. عندما تحاول العمليات في جميع الحاويات الثلاث استخدام 100٪ من وحدة المعالجة المركزية، تحصل الحاوية الأولى على 50٪ من إجمالي وقت وحدة المعالجة المركزية. إذا تمت إضافة حاوية رابعة بحصة وحدة معالجة مركزية تبلغ 1024، فإن الحاوية الأولى تحصل فقط على 33٪ من وحدة المعالجة المركزية. تحصل الحاويات المتبقية على 16.5٪، 16.5٪، و 33٪ من وحدة المعالجة المركزية.

على نظام متعدد النوى، يتم توزيع حصص وقت وحدة المعالجة المركزية على جميع نوى وحدة المعالجة المركزية. حتى لو تم تقييد حاوية بأقل من 100٪ من وقت وحدة المعالجة المركزية، يمكنها استخدام 100٪ من كل نواة وحدة معالجة مركزية فردية.

على سبيل المثال، لنفترض نظامًا به أكثر من ثلاثة نوى. إذا تم تشغيل الحاوية C0 باستخدام --cpu-shares=512 وتشغيل عملية واحدة، وحاوية أخرى C1 باستخدام --cpu-shares=1024 وتشغيل عمليتين، فقد ينتج عن ذلك تقسيم حصص وحدة المعالجة المركزية التالي:

PID container CPU CPU share
100 C0 0 100% of CPU0
101 C1 1 100% of CPU1
102 C1 2 100% of CPU2

على بعض الأنظمة، قد لا يُسمح بتغيير حدود الموارد للمستخدمين غير الجذر. لمزيد من التفاصيل، انظر https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

هذا الخيار غير مدعوم في أنظمة cgroups V1 غير الجذر.

--cpuset-cpus=number

وحدات المعالجة المركزية التي يُسمح بالتنفيذ فيها. يمكن تحديدها كقائمة مفصولة بفواصل (على سبيل المثال، 0,1)، كمدى (على سبيل المثال، 0-3)، أو أي مزيج منها (على سبيل المثال، 0-3,7,11-15).

على بعض الأنظمة، قد لا يُسمح بتغيير حدود الموارد للمستخدمين غير الجذر. لمزيد من التفاصيل، انظر https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

هذا الخيار غير مدعوم في أنظمة cgroups V1 غير الجذر.

--cpuset-mems=nodes

عقد الذاكرة (MEMs) التي يُسمح بالتنفيذ فيها (0-3، 0،1). فعال فقط على أنظمة NUMA.

إذا كانت هناك أربع عقد ذاكرة في النظام (0-3)، استخدم --cpuset-mems=0,1 ثم تستخدم العمليات في الحاوية الذاكرة فقط من عقد الذاكرة الأولى.

على بعض الأنظمة، قد لا يُسمح بتغيير حدود الموارد للمستخدمين غير يُسمح به للمستخدمين غير الجذر. لمزيد من التفاصيل، راجع https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

هذا الخيار غير مدعوم على أنظمة cgroups V1 بدون جذر.

--created-annotation

أضف "تعليق" للصور (انظر أيضًا --annotation) إلى بيانات الصورة الوصفية التي تضبط "org.opencontainers.image.created" على الوقت الحالي، أو على الطابع الزمني المحدد للعلامة --source-date-epoch أو --timestamp، إذا تم استخدام أي منهما. إذا كانت القيمة false، فلن يكون هناك مثل هذا التعليق في الصورة المكتوبة.

ملاحظة: هذه المعلومات غير موجودة في تنسيقات صور Docker، لذلك يتم تجاهلها عند كتابة الصور بتنسيقات Docker.

--creds=[username[:password]]

اسم المستخدم [:كلمة المرور] المستخدم للمصادقة مع السجل، إذا لزم الأمر. إذا لم يتم توفير قيمة واحدة أو كلتيهما، يظهر موجه سطر الأوامر ويمكن إدخال القيمة. يتم إدخال كلمة المرور بدون عرض.

لاحظ أن بيانات الاعتماد المحددة تُستخدم فقط للمصادقة ضد سجلات الوجهة. لا يتم استخدامها للمرايا أو عند إعادة كتابة السجل (انظر containers-registries.conf(5)) ؛ للمصادقة ضد هذه، ضع في اعتبارك استخدام ملف containers-auth.json(5).

--cw=options

إنتاج صورة مناسبة للاستخدام كعبء عمل سري يعمل في بيئة تنفيذ موثوقة (TEE) باستخدام krun (أي، crun مبني بميزة libkrun ممكّنة ويتم استدعاؤه كـ krun). بدلاً من المحتويات التقليدية، سيحتوي نظام الملفات الجذر للصورة على صورة قرص مشفرة ومعلومات تكوين لـ krun.

القيمة الخاصة بـ options هي قائمة مفصولة بفواصل من أزواج key=value، توفر معلومات التكوين اللازمة لإنتاج البيانات الإضافية التي سيتم تضمينها في صورة الحاوية.

المفاتيح المعترف بها هي:

attestation_url: موقع خادم مفتاح / شهادة. إذا تم تحديد قيمة، فسيتم تسجيل معرف عبء العمل الخاص بالصورة الجديدة، بالإضافة إلى العبارة السرية المستخدمة لتشفير صورة القرص، مع الخادم، وسيتم تخزين موقع الخادم في صورة الحاوية. في وقت التشغيل، يتوقع من krun الاتصال بالخادم لاسترداد العبارة السرية باستخدام معرف عبء العمل، والذي يتم تخزينه أيضًا في صورة الحاوية. إذا لم يتم تحديد قيمة، فيجب تحديد قيمة passphrase.

cpus: عدد وحدات المعالجة المركزية الافتراضية التي تتوقع الصورة أن تعمل بها في وقت التشغيل. إذا لم يتم تحديده، فسيتم توفير قيمة افتراضية.

firmware_library: موقع مكتبة libkrunfw-sev المشتركة. إذا لم يتم تحديده، فإن buildah يتحقق من وجودها في عدد من المواقع الثابتة.

memory: مقدار الذاكرة الذي تتوقع الصورة أن تعمل به في وقت التشغيل، كرقم بالميجابايت. إذا لم يتم تحديده، فسيتم توفير قيمة افتراضية.

passphrase: العبارة السرية المستخدمة لتشفير صورة القرص التي سيتم تضمينها في صورة الحاوية. إذا لم يتم تحديد قيمة، ولكن تم تحديد قيمة attestation_url، فسيتم استخدام عبارة سرية تم إنشاؤها عشوائيًا. يوصي المؤلفون بتعيين attestation_url ولكن ليس passphrase.

slop: مساحة إضافية مخصصة لصورة القرص مقارنة بحجم محتويات صورة الحاوية، معبر عنها إما كنسبة مئوية (..٪) أو كقيمة حجم (بايت، أو وحدات أكبر إذا كانت البادئات مثل KB أو MB موجودة)، أو مجموع مواصفاتين أو أكثر. إذا لم يتم تحديده، تخمن buildah أن 25٪ مساحة إضافية من المحتويات ستكون كافية، ولكن هذا الخيار متوفر في حال كان تخمينها خاطئًا.

type: نوع بيئة التنفيذ الموثوقة (TEE) التي يجب أن يتم تمييز الصورة لاستخدامها معها. القيم المقبولة هي "SEV" (AMD Secure Encrypted Virtualization - Encrypted State) و "SNP" (AMD Secure Encrypted Virtualization - Secure Nested Paging). إذا لم يتم تحديده، يكون الافتراضي هو "SNP".

workload_id: معرف عبء عمل سيتم تسجيله في صورة الحاوية، لاستخدامه في وقت التشغيل لاسترداد العبارة السرية التي تم استخدامها لتشفير صورة القرص. إذا لم يتم تحديده، فسيتم اشتقاق قيمة شبه عشوائية من معرف الصورة الأساسية للصورة.

هذا الخيار غير مدعوم على العميل البعيد، بما في ذلك أجهزة Mac و Windows (باستثناء WSL2).

--decryption-key=key[:passphrase]

المفتاح [:العبارة السرية] المستخدم لفك تشفير الصور. يمكن أن يشير المفتاح إلى المفاتيح و/أو الشهادات. تتم محاولة فك التشفير بجميع المفاتيح. إذا كان المفتاح محميًا بعبارة سرية، فيجب تمريره في الوسيطة وحذفه بخلاف ذلك.

--device=host-device[:container-device][:permissions]

أضف جهاز مضيف إلى الحاوية. يمكن استخدام المعلمة الاختيارية permissions لتحديد أذونات الجهاز عن طريق الجمع بين r للقراءة، w للكتابة، و m لـ mknod(2).

مثال: --device=/dev/sdc:/dev/xvdc:rwm.

ملاحظة: إذا كان host-device رابطًا رمزيًا، فسيتم حله أولاً. تقوم الحاوية بتخزين أرقام الجهاز الرئيسية والثانوية لجهاز المضيف فقط.

قد يقوم Podman بتحميل وحدات النواة المطلوبة لاستخدام الجهاز المحدد. الأجهزة التي تقوم Podman بتحميل وحدات لها عند الضرورة هي: /dev/fuse.

في الوضع بدون جذر، يتم ربط الجهاز الجديد في الحاوية من المضيف بدلاً من قيام Podman بإنشائه داخل مساحة الحاوية. نظرًا لأن الربط يحتفظ بتسمية SELinux الخاصة به على أنظمة SELinux، فقد تحصل الحاوية على رفض الإذن عند الوصول إلى الجهاز المرتبط. قم بتعديل إعدادات SELinux للسماح للحاويات باستخدام جميع تسميات الأجهزة عبر الأمر التالي:

$ sudo setsebool -P container_use_devices=true

ملاحظة: إذا كان لدى المستخدم حقوق الوصول فقط عبر مجموعة، فإن الوصول إلى الجهاز من داخل حاوية بدون جذر يفشل. يوفر وقت تشغيل crun(1) حلاً لهذه المشكلة عن طريق إضافة الخيار --annotation run.oci.keep_original_groups=1.

--disable-compression, -D

لا تقم بضغط طبقات نظام الملفات عند بناء الصورة ما لم يكن ذلك مطلوبًا من قبل الموقع الذي يتم كتابة الصورة إليه. هذا هو الإعداد الافتراضي، لأن طبقات الصور يتم ضغطها تلقائيًا عند دفعها إلى السجلات، والصور التي يتم كتابتها إلى التخزين المحلي تحتاج فقط إلى فك ضغطها مرة أخرى لتخزينها. يمكن فرض الضغط في جميع الحالات عن طريق تحديد --disable-compression=false.

--disable-content-trust

هذا خيار خاص بـ Docker لتعطيل التحقق من الصور إلى سجل حاويات ولا يدعمه Podman. هذا الخيار هو NOOP (لا يفعل شيئًا) ويتم توفيره فقط للتوافق النصي.

--dns=ipaddr

تعيين خوادم DNS مخصصة.

يمكن استخدام هذا الخيار لتجاوز تكوين DNS الذي تم تمريره إلى الحاوية. عادة ما يكون هذا ضروريًا عندما يكون تكوين DNS الخاص بالمضيف غير صالح للحاوية (على سبيل المثال، 127.0.0.1). في هذه الحالة، يكون العلم --dns ضروريًا لكل عملية تشغيل.

يمكن تحديد القيمة الخاصة none لتعطيل إنشاء /etc/resolv.conf في الحاوية بواسطة Podman. سيتم استخدام ملف /etc/resolv.conf في الصورة دون تغييرات.

لاحظ أنه يمكن إضافة ipaddr مباشرة إلى /etc/resolv.conf الخاص بالحاوية. هذا غير مضمون. على سبيل المثال، تمرير شبكة مخصصة تم ضبط dns_enabled الخاص بها على true إلى --network سيؤدي إلى أن يشير /etc/resolv.conf فقط إلى خادم aardvark-dns. ثم يقوم aardvark-dns بتوجيه إلى ipaddr المحدد لجميع استعلامات الأسماء غير الخاصة بالحاوية.

لا يمكن دمج هذا الخيار مع --network الذي تم تعيينه إلى none.

ملاحظة: هذا الخيار ساري المفعول فقط أثناء تعليمات RUN في البناء. لا يؤثر على /etc/resolv.conf في الصورة النهائية.

--dns-option=option

تعيين خيارات DNS مخصصة ليتم استخدامها أثناء البناء.

--dns-search=domain

تعيين نطاقات بحث DNS مخصصة ليتم استخدامها أثناء البناء.

--env=env[=value]

أضف قيمة (مثل env=value) إلى الصورة المبنية. يمكن استخدامه عدة مرات. إذا لم يتم تحديد = أو value، ولكن تم تعيين env في البيئة الحالية، تتم إضافة القيمة من البيئة الحالية إلى الصورة. لإزالة متغير بيئة من الصورة المبنية، استخدم الخيار --unsetenv.

--file, -f=Containerfile

يحدد Containerfile الذي يحتوي على تعليمات لبناء الصورة، سواء كان ملفًا محليًا أو عنوان URL http أو https. إذا تم تحديد أكثر من Containerfile واحد، فسيتم قبول تعليمات FROM فقط من الملف الأخير المحدد.

إذا لم يتم تحديد سياق بناء، وكان Containerfile واحدًا على الأقل ملفًا محليًا، فسيتم استخدام الدليل الذي يقع فيه كسياق بناء.

يؤدي تحديد الخيار -f - إلى قراءة محتويات Containerfile من stdin.

--force-rm

قم دائمًا بإزالة الحاويات الوسيطة بعد البناء، حتى لو فشل البناء (القيمة الافتراضية true).

--format

تحكم في تنسيق بيانات بيان وتكوين الصورة المبنية. تشمل التنسيقات المعترف بها oci (مواصفات الصورة OCI v1.0، الافتراضي) و docker (الإصدار 2، باستخدام تنسيق المخطط 2 للبيان).

ملاحظة: يمكنك أيضًا تجاوز التنسيق الافتراضي عن طريق تعيين متغير البيئة BUILDAH_FORMAT. export BUILDAH_FORMAT=docker

--from

يستبدل أول تعليمات FROM داخل Containerfile. إذا كانت هناك تعليمات FROM متعددة في Containerfile، فسيتم تغيير الأولى فقط.

مع عميل podman البعيد، لا تعمل جميع نُقل الحاويات كما هو متوقع. على سبيل المثال، تشير oci-archive:/x.tar إلى /x.tar على الجهاز البعيد بدلاً من العميل. عند استخدام عملاء podman عن بُعد، من الأفضل تقييد الاستخدام بـ containers-storage و docker:// النُقل.

Pass stdin into the RUN containers. Sometime commands being RUN within a Containerfile want to request information from the user. For example apt asking for a confirmation for install. Use --stdin to be able to interact from the terminal during the build.

--tag, -t=imageName

Specifies the name which is assigned to the resulting image if the build process completes successfully. If imageName does not include a registry name, the registry name localhost is prepended to the image name.

--target=stageName

Set the target build stage to build. When building a Containerfile with multiple build stages, --target can be used to specify an intermediate build stage by name as the final stage for the resulting image. Commands after the target stage is skipped.

--timestamp=seconds

Set the create timestamp to seconds since epoch to allow for deterministic builds (defaults to current time). By default, the created timestamp is changed and written into the image manifest with every commit, causing the image's sha256 hash to be different even if the sources are exactly the same otherwise. When --timestamp is set, the created timestamp is always set to the time specified and therefore not changed, allowing the image's sha256 hash to remain the same. All files committed to the layers of the image is created with the timestamp.

If the only instruction in a Containerfile is FROM, this flag has no effect.

--userns=how

Sets the configuration for user namespaces when handling RUN instructions. The configured value can be "" (the empty string) or "container" to indicate that a new user namespace is created, it can be "host" to indicate that the user namespace in which podman itself is being run is reused, or it can be the path to a user namespace which is already in use by another process.

--userns-gid-map=mapping

Directly specifies a GID mapping to be used to set ownership, at the filesystem level, on the working container's contents. Commands run when handling RUN instructions defaults to being run in their own user namespaces, configured using the UID and GID maps.

Entries in this map take the form of one or more triples of a starting in-container GID, a corresponding starting host-level GID, and the number of consecutive IDs which the map entry represents.

This option overrides the remap-gids setting in the options section of /etc/containers/storage.conf.

If this option is not specified, but a global --userns-gid-map setting is supplied, settings from the global option is used.

If none of --userns-uid-map-user, --userns-gid-map-group, or --userns-gid-map are specified, but --userns-uid-map is specified, the GID map is set to use the same numeric values as the UID map.

--userns-gid-map-group=group

Specifies that a GID mapping to be used to set ownership, at the filesystem level, on the working container's contents, can be found in entries in the /etc/subgid file which correspond to the specified group. Commands run when handling RUN instructions defaults to being run in their own user namespaces, configured using the UID and GID maps. If --userns-uid-map-user is specified, but --userns-gid-map-group is not specified, podman assumes that the specified user name is also a suitable group name to use as the default setting for this option.

NOTE: When this option is specified by a rootless user, the specified mappings are relative to the rootless user namespace in the container, rather than being relative to the host as it is when run rootful.

--userns-uid-map=mapping

Directly specifies a UID mapping to be used to set ownership, at the filesystem level, on the working container's contents. Commands run when handling RUN instructions default to being run in their own user namespaces, configured using the UID and GID maps.

Entries in this map take the form of one or more triples of a starting in-container UID, a corresponding starting host-level UID, and the number of consecutive IDs which the map entry represents.

This option overrides the remap-uids setting in the options section of /etc/containers/storage.conf.

If this option is not specified, but a global --userns-uid-map setting is supplied, settings from the global option is used.

If none of --userns-uid-map-user, --userns-gid-map-group, or --userns-uid-map are specified, but --userns-gid-map is specified, the UID map is set to use the same numeric values as the GID map.

--userns-uid-map-user=user

Specifies that a UID mapping to be used to set ownership, at the filesystem level, on the working container's contents, can be found in entries in the /etc/subuid file which correspond to the specified user. Commands run when handling RUN instructions defaults to being run in their own user namespaces, configured using the UID and GID maps. If --userns-gid-map-group is specified, but --userns-uid-map-user is not specified, podman assumes that the specified group name is also a suitable user name to use as the default setting for this option.

NOTE: When this option is specified by a rootless user, the specified mappings are relative to the rootless user namespace in the container, rather than being relative to the host as it is when run rootful.

--volume, -v=[HOST-DIR:CONTAINER-DIR[:OPTIONS]]

Mount a host directory into containers when executing RUN instructions during the build.

The OPTIONS are a comma-separated list and can be one or more of:

  • [rw|ro]
  • [z|Z|O]
  • [U]
  • [[r]shared|[r]slave|[r]private][1] ⟨#Footnote1⟩

The CONTAINER-DIR must be an absolute path such as /src/docs. The HOST-DIR must be an absolute path as well. Podman bind-mounts the HOST-DIR to the specified path when processing RUN instructions.

You can specify multiple -v options to mount one or more mounts.

You can add the :ro or :rw suffix to a volume to mount it read-only or read-write mode, respectively. By default, the volumes are mounted read-write. See examples.
