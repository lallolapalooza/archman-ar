podman-run(1) دليل الأوامر العامة podman-run(1)

الاسم

podman-run - تشغيل أمر في حاوية جديدة

الملخص

podman run [خيارات] صورة [أمر [وسيط ...]]

podman container run [خيارات] صورة [أمر [وسيط ...]]

الوصف

تشغيل عملية في حاوية جديدة. يقوم podman run ببدء عملية بمساحة ملفاتها الخاصة، وشبكتها الخاصة، وشجرة عملياتها المعزولة. قد تحدد الصورة التي تبدأ العملية افتراضيات متعلقة بالعملية التي سيتم تشغيلها في الحاوية، والشبكات المراد كشفها، والمزيد، ولكن podman run يمنح التحكم النهائي للمشغل أو المسؤول الذي يبدأ الحاوية من الصورة. لهذا السبب، يحتوي podman run على خيارات أكثر من أي أمر Podman آخر.

إذا لم تكن الصورة محملة بالفعل، فسوف يقوم podman run بسحب الصورة، وجميع تبعيات الصورة، من المستودع بنفس الطريقة التي يعمل بها podman pull صورة، قبل أن يبدأ الحاوية من تلك الصورة.

سيتم إنشاء عدة ملفات تلقائيًا داخل الحاوية. تشمل هذه الملفات /etc/hosts، /etc/hostname، و /etc/resolv.conf لإدارة الشبكات. ستستند هذه الملفات إلى إصدارات مضيف الملفات، على الرغم من أنه يمكن تخصيصها باستخدام الخيارات (على سبيل المثال، قد يتجاوز --dns خوادم DNS الخاصة بالمضيف في resolv.conf الذي تم إنشاؤه). بالإضافة إلى ذلك، يتم إنشاء ملف بيئة حاوية في كل حاوية للإشارة إلى البرامج بأنها تعمل في حاوية. يوجد هذا الملف في /run/.containerenv (أو /var/run/.containerenv للحاويات FreeBSD). عند استخدام العلم --privileged، يحتوي .containerenv على أزواج الاسم/القيمة التي تشير إلى إصدار محرك الحاوية، سواء كان المحرك يعمل في وضع غير جذري، واسم الحاوية ومعرفها، وكذلك اسم الصورة ومعرفها الذي تستند إليه الحاوية. ملاحظة: لن يتم إنشاء /run/.containerenv عند تحميل وحدة تخزين على /run.

عند التشغيل من مساحة أسماء شبكة محددة بواسطة المستخدم، سيتم استخدام /etc/netns/NSNAME/resolv.conf إذا كان موجودًا، وإلا فسيتم استخدام /etc/resolv.conf.

يتم تعريف الإعدادات الافتراضية في containers.conf. معظم الإعدادات للاتصالات عن بعد تستخدم خوادم containers.conf، إلا عند توثيقها في صفحات الدليل.

صورة

يتم تحديد الصورة باستخدام تنسيق transport:path. إذا لم يتم تحديد النقل، يتم استخدام نقل docker (سجل الحاويات) افتراضيًا. بالنسبة لـ Podman عن بعد، بما في ذلك أجهزة Mac و Windows (باستثناء WSL2)، فإن docker هو النقل المسموح به الوحيد.

dir:path
دليل محلي موجود path يخزن البيان، وأرشيفات الطبقات، والتوقيعات كملفات فردية. هذا تنسيق غير قياسي، مفيد بشكل أساسي للتصحيح أو لفحص الحاوية غير التدخلي.

$ podman save --format docker-dir fedora -o /tmp/fedora
$ podman run dir:/tmp/fedora echo hello

docker://docker-reference (افتراضي)
مرجع صورة مخزن في سجل صور الحاويات البعيد. مثال: "quay.io/podman/stable:latest". يمكن أن يتضمن المرجع مسارًا إلى سجل معين؛ إذا لم يفعل ذلك، يتم الاستعلام عن السجلات المدرجة في registries.conf للعثور على صورة مطابقة. افتراضيًا، يتم استخدام بيانات الاعتماد من podman login (المخزنة في $XDG_RUNTIME_DIR/containers/auth.json افتراضيًا) للمصادقة؛ بخلاف ذلك، يتم الرجوع إلى بيانات الاعتماد في $HOME/.docker/config.json.

$ podman run registry.fedoraproject.org/fedora:latest echo hello

docker-archive:path[:docker-reference] صورة مخزنة في ملف بتنسيق docker save. docker-reference يستخدم فقط عند إنشاء مثل هذا الملف، ويجب ألا يحتوي على ملخص.

$ podman save --format docker-archive fedora -o /tmp/fedora
$ podman run docker-archive:/tmp/fedora echo hello

ملاحظة: على العملاء البعيدين، بما في ذلك أجهزة Mac و Windows (باستثناء WSL2)، لا يدعم هذا النقل.

docker-daemon:docker-reference
صورة بتنسيق docker-reference مخزنة في التخزين الداخلي لـ docker daemon. يمكن أن يكون docker-reference أيضًا معرف صورة (docker-daemon:algo:digest).

$ sudo docker pull fedora
$ sudo podman run docker-daemon:docker.io/library/fedora echo hello

ملاحظة: على العملاء البعيدين، بما في ذلك أجهزة Mac و Windows (باستثناء WSL2)، لا يدعم هذا النقل.

oci-archive:path:tag
صورة في دليل متوافق مع "مواصفات تخطيط صور الحاويات المفتوحة" في المسار المحدد path ومحددة بـ tag.

$ podman save --format oci-archive fedora -o /tmp/fedora
$ podman run oci-archive:/tmp/fedora echo hello

ملاحظة: على العملاء البعيدين، بما في ذلك أجهزة Mac و Windows (باستثناء WSL2)، لا يدعم هذا النقل.

خيارات

--add-host=hostname[;hostname[;...]]:ip

أضف تعيين مضيف إلى IP مخصص إلى ملف /etc/hosts الخاص بالحاوية.

يأخذ الخيار أسماء مضيفين مفصولة بفاصلة منقوطة (واحد أو أكثر) ليتم تعيينها إلى عنوان IPv4 أو IPv6 واحد، مفصول بـ: . يمكن استخدامه أيضًا لتجاوز عناوين IP الخاصة بأسماء المضيفين التي يضيفها Podman إلى /etc/hosts افتراضيًا (انظر أيضًا خيارات --name و --hostname). يمكن تحديد هذا الخيار عدة مرات لإضافة تعيينات إضافية إلى /etc/hosts. يتعارض مع الخيار --no-hosts و no_hosts=true في containers.conf.

بدلاً من عنوان IP، يمكن إعطاء العلامة الخاصة host-gateway. هذا يحل إلى عنوان IP يمكن للحاوية استخدامه للاتصال بالمضيف. يعتمد عنوان IP المختار على إعدادات الشبكة الخاصة بك، لذلك لا يوجد ضمان بأن Podman يمكنه تحديد عنوان host-gateway تلقائيًا، مما سيؤدي بعد ذلك إلى فشل Podman مع رسالة خطأ. يمكنك تجاوز عنوان IP هذا باستخدام خيار host_containers_internal_ip في containers.conf.

يستخدم عنوان host-gateway أيضًا بواسطة Podman لإضافة أسماء المضيفين host.containers.internal و host.docker.internal تلقائيًا إلى /etc/hosts. يمكنك منع ذلك إما عن طريق إعطاء الخيار --no-hosts، أو عن طريق تعيين host_containers_internal_ip="none" في containers.conf. إذا لم يتم تكوين عنوان host-gateway يدويًا وفشل Podman في تحديد عنوان IP تلقائيًا، فسيتخطى Podman بصمت إضافة أسماء المضيفين الداخلية هذه إلى /etc/hosts. إذا كان Podman يعمل في جهاز افتراضي باستخدام podman machine (وهذا يشمل مضيفي Mac و Windows)، فسيتخطى Podman بصمت إضافة أسماء المضيفين الداخلية إلى /etc/hosts، ما لم يتم تكوين عنوان IP يدويًا؛ يتم حل أسماء المضيفين الداخلية بواسطة محلل DNS الخاص بـ gvproxy بدلاً من ذلك.

سيستخدم Podman ملف /etc/hosts الخاص بالمضيف كأساس افتراضيًا، أي أن أي اسم مضيف موجود في هذا الملف سيكون موجودًا أيضًا في ملف /etc/hosts الخاص بالحاوية. يمكن تكوين ملف أساسي مختلف باستخدام تكوين base_hosts_file في containers.conf.

--cpuset-cpus=cpus

CPUs in which to allow execution (0-2, 0,6,4-7). An effective way to limit the number of CPUs the container can use is to use the --cpuset-cpus option.

The format is a list of CPUs separated by commas and/or ranges for example: 0-4,7. The CPUs must be available on the host system. If the list contains CPUs that are not available on the host system, an error is returned.

On some systems, changing the resource limits may not be allowed for non-root users. For more details, see https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

This option is not supported on cgroups V1 rootless systems.

--cpuset-mems=nodes

Memory nodes (MEMs) in which to allow execution (0-3, 0,1). Only effective on NUMA systems.

If there are four memory nodes on the system (0-3), use --cpuset-mems=0,1 then processes in the container only uses memory from the first two memory nodes.

On some systems, changing the resource limits may not be allowed for non-root users. For more details, see https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

This option is not supported on cgroups V1 rootless systems.

--creds=[username[:password]]

The [username[:password]] to use to authenticate with the registry, if required. If one or both values are not supplied, a command line prompt appears and the value can be entered. The password is entered without echo.

Note that the specified credentials are only used to authenticate against target registries. They are not used for mirrors or when the registry gets rewritten (see containers-registries.conf(5)); to authenticate against those consider using a containers-auth.json(5) file.

--decryption-key=key[:passphrase]

The [key[:passphrase]] to be used for decryption of images. Key can point to keys and/or certificates. Decryption is tried with all keys. If the key is protected by a passphrase, it is required to be passed in the argument and omitted otherwise.

--detach, -d

Detached mode: run the container in the background and print the new container ID. The default is false.

At any time run podman ps in the other shell to view a list of the running containers. Reattach to a detached container with podman attach command.

When attached via tty mode, detach from the container (and leave it running) using a configurable key sequence. The default sequence is ctrl-p,ctrl-q. Specify the key sequence using the --detach-keys option, or configure it in the containers.conf file: see containers.conf(5) for more information.

--detach-keys=sequence

Specify the key sequence for detaching a container. Format is a single character [a-Z] or one or more ctrl-<value> characters where <value> is one of: a-z, @, ^, [, , or _. Specifying "" disables this feature. The default is ctrl-p,ctrl-q.

This option can also be set in containers.conf(5) file.

--device=host-device[:container-device][:permissions]

Add a host device to the container. Optional permissions parameter can be used to specify device permissions by combining r for read, w for write, and m for mknod(2).

Example: --device=/dev/sdc:/dev/xvdc:rwm.

Note: if host-device is a symbolic link then it is resolved first. The container only stores the major and minor numbers of the host device.

Podman may load kernel modules required for using the specified device. The devices that Podman loads modules for when necessary are: /dev/fuse.

In rootless mode, the new device is bind mounted in the container from the host rather than Podman creating it within the container space. Because the bind mount retains its SELinux label on SELinux systems, the container can get permission denied when accessing the mounted device. Modify SELinux settings to allow containers to use all device labels via the following command:

$ sudo setsebool -P container_use_devices=true

Note: if the user only has access rights via a group, accessing the device from inside a rootless container fails. Use the --group-add keep-groups flag to pass the user's supplementary group access into the container.

--device-cgroup-rule="type major:minor mode"

Add a rule to the cgroup allowed devices list. The rule is expected to be in the format specified in the Linux kernel documentation admin-guide/cgroup-v1/devices: - type: a (all), c (char), or b (block); - major and minor: either a number, or * for all; - mode: a composition of r (read), w (write), and m (mknod(2)).

On some systems, changing the resource limits may not be allowed for non-root users. For more details, see https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

This option is not supported on cgroups V1 rootless systems.

--device-write-iops=path:rate

Limit write rate (in IO operations per second) to a device (e.g. --device-write-iops=/dev/sda:1000).

On some systems, changing the resource limits may not be allowed for non-root users. For more details, see https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

This option is not supported on cgroups V1 rootless systems.

--disable-content-trust

This is a Docker-specific option to disable image verification to a container registry and is not supported by Podman. This option is a NOOP and provided solely for scripting compatibility.

--dns=ipaddr

Set custom DNS servers.

This option can be used to override the DNS configuration passed to the container. Typically this is necessary when the host DNS configuration is invalid for the container (e.g., 127.0.0.1). When this is the case the --dns flag is necessary for every run.

The special value none can be specified to disable creation of /etc/resolv.conf in the container by Podman. The /etc/resolv.conf file in the image is then used without changes.

Note that ipaddr may be added directly to the container's /etc/resolv.conf. This is not guaranteed though. For example, passing a custom network whose dns_enabled is set to true to --network will result in /etc/resolv.conf only referring to the aardvark-dns server. aardvark-dns then forwards to the supplied ipaddr for all non-container name queries.

This option cannot be combined with --network that is set to none or container:id.

--dns-option=option

Set custom DNS options. Invalid if using --dns-option with --network that is set to none or container:id.

--dns-search=domain

Set custom DNS search domains. Invalid if using --dns-search with --network that is set to none or container:id. Use --dns-search=. to remove the search domain.

--entrypoint="command" | '["command", arg1 , ...]'

Override the default ENTRYPOINT from the image.

The ENTRYPOINT of an image is similar to a COMMAND because it specifies what executable to run when the container starts, but it is (purposely) more difficult to override. The ENTRYPOINT gives a container its default nature or behavior. When the ENTRYPOINT is set, the container runs as if it were that binary, complete with default options. More options can be passed in via the COMMAND. But, if a user wants to run something else inside the container, the --entrypoint option allows a new ENTRYPOINT to be specified.

Specify multi option commands in the form of a JSON string.

--env, -e=env

Set environment variables.

This option allows arbitrary environment variables that are available for the process to be launched inside the container. You can provide multiple environment variables by using the option multiple times. Example: -e MY_VAR=my_value.

If the value part is omitted, the environment variable is taken from the host environment.

Example: -e PATH.

If the specified environment variable is set to an empty value on the host, it is cleared in the container.

Example: -e VAR=.

For Podman, all environment variables are set by default. If you only want to use a subset of the default environment variables, you need to specify them all using the -e option. For example, to only include PATH and TERM, you would use:

podman run -e TERM -e PATH alpine echo $PATH

Note: The container must be run in the foreground (-d is not used) for the -e option to work.

--env-file=file

Specify a file containing environment variables.

The file format is one variable per line in the format NAME=VALUE. Blank lines and lines starting with # are ignored.

Example: 

#This is a comment
    VAR1=VAL1
    VAR2=VAL2

--expose=[][/udp|/tcp]

Expose a port or range of ports, or a Unix socket, from the container. The IP address and port number are optional. You can also specify the protocol (tcp or udp).

The default protocol is tcp.

Example: --expose=8080, --expose=8080/udp, --expose=1000-2000.

This option can be used multiple times to expose multiple ports.

Note that this option only documents the ports and does not publish them. To publish ports, use the -p option.

--group-add=group

Add additional groups for the container user. The group can be specified by name or ID. This option can be used multiple times.

Special group keep-groups keeps supplementary groups from the parent process. If the user is root, this is all groups. If the user is non-root, this is the supplementary groups.

--health-cmd=command

The command to run to check the container's health. This command can be an executable in the container, or a command to run using `sh`. The default command is none, which means health checks are disabled.

The command should exit with status 0 for a healthy container, 123 for an unhealthy container, and a status other than 0 or 123 for an unknown (degraded) state.

--health-interval=duration

The time interval between running the health check command. The default interval is 30s.

The duration format is a sequence of decimal numbers each with an optional suffix multiplier, where the multipliers are: ns (nanoseconds), us (microseconds), ms (milliseconds), s (seconds), m (minutes), h (hours).

--health-retries=number

The number of consecutive failures of the health check command before the container is marked unhealthy. The default is 3.

--health-start-period=duration

The time to wait for the container to start before running health checks. During this period, the container is not considered unhealthy, even if the health check fails. The default is 0s.

The duration format is a sequence of decimal numbers each with an optional suffix multiplier, where the multipliers are: ns (nanoseconds), us (microseconds), ms (milliseconds), s (seconds), m (minutes), h (hours).

--health-timeout=duration

The maximum time allowed to wait for the health check command to return. If the command does not return within this time, it is considered to have failed. The default is 0s (no timeout).

The duration format is a sequence of decimal numbers each with an optional suffix multiplier, where the multipliers are: ns (nanoseconds), us (microseconds), ms (milliseconds), s (seconds), m (minutes), h (hours).

--hidden

If specified, then the container will be run as a hidden container. Hidden containers are not displayed by default by commands like `podman ps`. You must use the -a or --all flag to see them.

--host-add=hostname:ip

Add a custom host-alias entry to the container's /etc/hosts file.

--http-proxy

This option is ignored by Podman. HTTP proxies are configured via environment variables like http_proxy, https_proxy, and no_proxy.

--idmap-gidmap=container_gid:host_gid:size

Configure the GID map for the container. This option allows users to specify how container UIDs map to host UIDs. For rootless containers, this is often necessary to ensure proper file permissions.

Example: --idmap-gidmap 0:1000:1 maps the container's GID 0 to the host's GID 1000, with a size of 1.

This option is primarily for use with rootless Podman. The default behavior attempts to map the container's UIDs/GIDs to unused UIDs/GIDs on the host.

--idmap-uidmap=container_uid:host_uid:size

Configure the UID map for the container. This option allows users to specify how container UIDs map to host UIDs. For rootless containers, this is often necessary to ensure proper file permissions.

Example: --idmap-uidmap 0:1000:1 maps the container's UID 0 to the host's UID 1000, with a size of 1.

This option is primarily for use with rootless Podman. The default behavior attempts to map the container's UIDs/GIDs to unused UIDs/GIDs on the host.

--image-conf=path

Use the specified container image configuration file. The default is /etc/containers/containers.conf.

--ip=ip

Specify a static IP address for the container's network interface. This option is only valid when using user-defined networks.

--ip6=ip6

Specify a static IPv6 address for the container's network interface. This option is only valid when using user-defined networks.

--ipc=

Set the IPC mode for the container. The default is private.

Supported modes:

private: Each container has its own IPC namespace. This is the default.

share: The container shares its IPC namespace with the host. This is equivalent to --ipc=host.

container:name|id: The container shares its IPC namespace with another container. The other container must be started first.

Note: Using --ipc=host is not recommended as it can lead to security vulnerabilities.

--kernel-memory=bytes

Memory limit (working set). Default is unlimited.

You can specify the value in bytes, or use a suffix like b (bytes), k (kilobytes), m (megabytes), or g (gigabytes).

Example: --kernel-memory=512m.

On some systems, changing the resource limits may not be allowed for non-root users. For more details, see https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

This option is not supported on cgroups V1 rootless systems.

--label, -l=label

Add metadata to the container in the form of a key=value pair. Labels can be used to identify and organize containers.

Example: --label=environment=production.

This option can be used multiple times to add multiple labels.

--label-file=file

Add metadata to the container in the form of key-value pairs read from a file. The file format is one label per line in the format KEY=VALUE. Lines starting with # are ignored.

--log-driver=driver

The logging driver for the container. Supported drivers are: journald, json-file, syslog, and none.

The default driver is json-file.

If using journald, the container logs will be sent to the systemd journal.

If using syslog, the container logs will be sent to the system logger.

If using none, container logs will not be collected.

--log-opt=key=value

Set default log driver options. This option can be used multiple times.

--mount=type=TYPE[,OPTIONS]

Add a mount to the container. The mount type can be bind, volume, or tmpfs.

For bind mounts, the options are:

source=SOURCE: Path to the file or directory on the host machine.

target=TARGET: Path in the container where the volume is mounted.

readonly: Mount the volume as read-only.

bind-propagation=MODE: Controls the behavior of bind mount propagation. Possible values are: rprivate, private, rshared, shared, rslave, slave.

For volumes, the options are:

target=TARGET: Path in the container where the volume is mounted.

volume-driver=DRIVER: Name of the volume driver to use.

volume-label=LABEL: Add metadata to the volume in the form of a key=value pair.

volume-opt=KEY=VALUE: Specify volume driver options.

readonly: Mount the volume as read-only.

For tmpfs mounts, the options are:

target=TARGET: Path in the container where the tmpfs is mounted.

tmpfs-size=SIZE: Specify the maximum size of the tmpfs mount. Defaults to system maximum.

tmpfs-mode=MODE: Specify the mode of the tmpfs mount (e.g., 0755).

Example:

--mount type=volume,target=/data

--mount type=tmpfs,target=/ramdisk,tmpfs-size=512m

  • src, source: مواصفات مصدر التحميل لـ bind و glob و volume. إلزامي لـ artifact و bind و glob و image و volume.
  • dst, dest, destination, target: مواصفات وجهة التحميل.

عند تحديد مسارات المصدر العامة (globs) بدون دليل الوجهة، يتم تحميل الملفات والأدلة بالمسار الكامل لها داخل الحاوية. عند تحديد الوجهة، يتم تحميل الملفات والأدلة المطابقة للمسار العام على اسم الملف الأساسي في دليل الوجهة. يوجه الخيار type=glob,src=/foo*,destination=/tmp/bar محركات الحاويات لتحميل ملفات المضيف التي تطابق /foo* إلى الدليل /tmp/bar/ في الحاوية.

الخيارات الخاصة بالنوع=artifact:

  • digest: إذا كان مصدر القطعة الأثرية يحتوي على عدة قطع (blobs)، يمكن تحديد هضم (digest) لتحميل قطعة واحدة محددة فقط ذات الهضم.
  • title: إذا كان مصدر القطعة الأثرية يحتوي على عدة قطع، يمكن تعيين عنوان (title) تتم مقارنته مع التعليق التوضيحي org.opencontainers.image.title.
  • name: يمكن استخدام هذا للكتابة فوق اسم الملف الذي نستخدمه داخل الحاوية للتحميل. في قطعة أثرية ذات قطعة واحدة (single blob)، يتم استخدام الاسم كما هو إذا كان dst دليلاً، وإلا يتم تجاهله. مع قطعة أثرية متعددة القطع (multi blob)، سيتم استخدام الاسم مع لاحقة فهرس <name>-x حيث x هو فهرس الطبقة في القطعة الأثرية بدءًا من 0.

يحتوي الوسيط src على اسم القطعة الأثرية، والذي يجب أن يكون موجودًا محليًا بالفعل. يحتوي الوسيط dst على المسار الهدف، إذا كان المسار في الحاوية دليلاً، فسيتم استخدام عنوان القطعة الأثرية (التعليق التوضيحي org.opencontainers.image.title) كاسم ملف ويتم دمجه مع المسار. إذا لم يكن التعليق التوضيحي موجودًا، فسيتم استخدام الهضم كاسم ملف بدلاً من ذلك. ينتج عن هذا تحميل جميع قطع القطعة الأثرية في الحاوية في المسار المحدد.

ومع ذلك، إذا كان مسار dst ملفًا موجودًا في الحاوية، فسيتم تحميل القطعة الأثرية مباشرة فوقه. يعمل هذا فقط عندما تحتوي القطعة الأثرية على قطعة واحدة أو عندما يتم تحديد digest أو title.

إذا كان مسار dst غير موجود بالفعل في الحاوية، فإذا كانت القطعة الأثرية تحتوي على قطعة واحدة، فإنها تتصرف مثل حالة الملف الموجود وتحمل مباشرة إلى هذا المسار. إذا كان للقطعة الأثرية أكثر من قطعة واحدة، فإنها تعمل مثل حالة الدليل الموجود وتقوم بتحميل كل قطعة كملف ضمن المسار dst.

الخيارات الخاصة بالنوع=volume:

  • ro, readonly: true أو false (القيمة الافتراضية إذا لم يتم تحديدها: false).
  • U, chown: true أو false (القيمة الافتراضية إذا لم يتم تحديدها: false). تغيير المالك والمجموعة بشكل متكرر لوحدة التخزين المصدر بناءً على UID و GID للحاوية.
  • subpath: تحميل مسار فرعي محدد فقط داخل وحدة التخزين، بدلاً من وحدة التخزين بأكملها.
  • idmap: إذا تم تحديده، قم بإنشاء تحميل mapped ID إلى مساحة اسم المستخدم المستهدفة في الحاوية. لا يدعم خيار idmap إلا Podman في وضع rootful. لا تسمح نواة Linux باستخدام أنظمة ملفات mapped ID للمستخدمين غير المميزين. يدعم خيار idmap تعيينًا مخصصًا يمكن أن يختلف عن مساحة اسم المستخدم المستخدمة بواسطة الحاوية. يمكن تحديد التعيين بعد خيار idmap مثل: idmap=uids=0-1-10#10-11-10;gids=0-100-10. لكل ثلاثي، القيمة الأولى هي بداية معرفات نظام الملفات الأساسي التي يتم تعيينها إلى القيمة الثانية على المضيف. طول هذا التعيين معطى في القيمة الثالثة. يتم فصل النطاقات المتعددة بـ #. إذا تم تمهيد التعيين المحدد بـ "@"، فيعتبر التعيين نسبيًا لمساحة اسم المستخدم في الحاوية. يتم تغيير معرف المضيف للتعيين للحساب الموضع النسبي لمستخدم الحاوية في مساحة اسم المستخدم في الحاوية.

الخيارات الخاصة بالنوع=image:

  • rw, readwrite: true أو false (القيمة الافتراضية إذا لم يتم تحديدها: false).
  • subpath: تحميل مسار محدد فقط داخل الصورة، بدلاً من الصورة بأكملها.

الخيارات الخاصة بـ bind و glob:

  • ro, readonly: true أو false (القيمة الافتراضية إذا لم يتم تحديدها: false).
  • bind-propagation: shared, slave, private, unbindable, rshared, rslave, runbindable, أو rprivate (الافتراضي).[1] ⟨#Footnote1⟩ انظر أيضًا mount(2).
  • bind-nonrecursive: لا تقم بإعداد تحميل bind متكرر. افتراضيًا، يكون متكررًا.
  • relabel: shared, private.
  • idmap: true أو false (القيمة الافتراضية إذا لم يتم تحديدها: false). إذا كان صحيحًا، قم بإنشاء تحميل mapped ID إلى مساحة اسم المستخدم المستهدفة في الحاوية. لا يدعم خيار idmap إلا Podman في وضع rootful.
  • U, chown: true أو false (القيمة الافتراضية إذا لم يتم تحديدها: false). تغيير المالك والمجموعة بشكل متكرر لوحدة التخزين المصدر بناءً على UID و GID للحاوية.
  • no-dereference: لا تقم بإلغاء إشارة الروابط الرمزية ولكن انسخ مصدر الرابط إلى وجهة التحميل.

الخيارات الخاصة بالنوع=tmpfs و ramfs:

  • ro, readonly: true أو false (القيمة الافتراضية إذا لم يتم تحديدها: false).
  • tmpfs-size: حجم تحميل tmpfs/ramfs، بالبايت. غير محدود افتراضيًا في Linux.
  • tmpfs-mode: وضع ملف ثماني لـ tmpfs/ramfs (مثل 700 أو 0700.).
  • tmpcopyup: تمكين النسخ لأعلى من دليل الصورة في نفس الموقع إلى tmpfs/ramfs. مستخدم افتراضيًا.
  • noatime: تعطيل تحديث أوقات الوصول إلى الملف عند قراءة الملف.
  • notmpcopyup: تعطيل نسخ الملفات من الصورة إلى tmpfs/ramfs.
  • U, chown: true أو false (القيمة الافتراضية إذا لم يتم تحديدها: false). تغيير المالك والمجموعة بشكل متكرر لوحدة التخزين المصدر بناءً على UID و GID للحاوية.

الخيارات الخاصة بالنوع=devpts:

  • uid: UID رقمي لمالك الملف (الافتراضي: 0).
  • gid: GID رقمي لمالك الملف (الافتراضي: 0).
  • mode: قناع أذونات ثماني للملف (الافتراضي: 600).
  • max: الحد الأقصى لعدد PTYs (الافتراضي: 1048576).

أمثلة:

  • type=bind,source=/path/on/host,destination=/path/in/container
  • type=bind,src=/path/on/host,dst=/path/in/container,relabel=shared
  • type=bind,src=/path/on/host,dst=/path/in/container,relabel=shared,U=true
  • type=devpts,destination=/dev/pts
  • type=glob,src=/usr/lib/libfoo*,destination=/usr/lib,ro=true
  • type=image,source=fedora,destination=/fedora-image,rw=true
  • type=ramfs,tmpfs-size=512M,destination=/path/in/container
  • type=tmpfs,tmpfs-size=512M,destination=/path/in/container
  • type=tmpfs,destination=/path/in/container,noswap
  • type=artifact,src=quay.io/libpod/testartifact:20250206-single,dst=/data
  • type=artifact,src=quay.io/libpod/testartifact:20250206-multi,dst=/data,title=test1
  • type=volume,src=test_vol,dst=/data,subpath=/code/docs

--name=name

تعيين اسم للحاوية.

يمكن للمشغل تحديد حاوية بثلاث طرق:

  • معرف UUID طويل (“f78375b1c487e03c9438c729345e54db9d20cfa2ac1fc3494b6eb60872e74778”);
  • معرف UUID قصير (“f78375b1c487”);
  • الاسم (“jonah”).

يقوم Podman بإنشاء UUID لكل حاوية، وإذا لم يتم تعيين اسم للحاوية باستخدام --name، يقوم Podman بإنشاء اسم سلسلة عشوائية. يمكن أن يكون الاسم مفيدًا كطريقة أكثر سهولة للبشر لتحديد الحاويات. يعمل هذا مع كل من الحاويات الخلفية والأمامية. يتم أيضًا إضافة اسم الحاوية إلى ملف /etc/hosts باستخدام عنوان IP الأساسي للحاوية (انظر أيضًا الخيار --add-host).

--network=mode, --net

تعيين وضع الشبكة للحاوية.

القيم الصالحة لـ mode هي:

•
bridge[:OPTIONS,...]: إنشاء مكدس شبكة على الجسر الافتراضي. هذا هو الافتراضي للحاويات الكاملة (rootful). من الممكن تحديد خيارات إضافية:
  • alias=name: إضافة اسم مستعار خاص بالشبكة للحاوية.
  • ip=IPv4: تحديد عنوان IPv4 ثابت لهذه الحاوية.
  • ip6=IPv6: تحديد عنوان IPv6 ثابت لهذه الحاوية.
  • mac=MAC: تحديد عنوان MAC ثابت لهذه الحاوية.
  • interface_name=name: تحديد اسم لواجهة الشبكة المنشأة داخل الحاوية.
  • host_interface_name=name: تحديد اسم لواجهة الشبكة المنشأة خارج الحاوية.
سيتم تمرير أي خيارات أخرى إلى netavark دون التحقق. قد يكون هذا مفيدًا لتمرير وسيطات إلى مكونات netavark الإضافية.

على سبيل المثال، لتعيين عنوان IPv4 ثابت وعنوان MAC ثابت، استخدم --network bridge:ip=10.88.0.10,mac=44:33:22:11:00:99.

  • <network name or ID>[:OPTIONS,...]: الاتصال بشبكة معرفة من قبل المستخدم؛ هذا هو اسم الشبكة أو معرفها من شبكة تم إنشاؤها بواسطة podman network create. من الممكن تحديد نفس الخيارات الموصوفة تحت وضع bridge أعلاه. استخدم الخيار --network عدة مرات لتحديد شبكات إضافية.
    للتوافق مع الإصدارات السابقة، من الممكن أيضًا تحديد شبكات مفصولة بفواصل في الوسيط الأول --network، ولكن هذا يمنعك من استخدام الخيارات الموصوفة تحت قسم bridge أعلاه.
  • none: إنشاء مساحة اسم شبكة للحاوية ولكن لا تقم بتكوين واجهات شبكة لها، وبالتالي ليس للحاوية اتصال بالشبكة.
  • container:id: إعادة استخدام مكدس شبكة لحاوية أخرى.
  • host: استخدام مساحة اسم شبكة المضيف للحاوية بدلاً من إنشاء مساحة اسم معزولة. تحذير: هذا يمنح الحاوية وصولاً كاملاً إلى مقابس Unix المجردة ومقابس TCP/UDP المرتبطة بـ localhost. نظرًا لأن هذه الآليات غالبًا ما تستخدم لمنع الوصول إلى خدمات النظام الحساسة، وعزلها عن الوصول من قبل الكيانات الخارجية، فقد يعتبر استخدام هذا الخيار ثغرة أمنية.
  • ns:path: المسار إلى مساحة اسم شبكة للانضمام إليها.
هي المنصة، بغض النظر عن المضيف.

--pod=name

تشغيل حاوية في بود موجود. يقوم Podman بإنشاء البود تلقائيًا إذا كان اسم البود مسبوقًا بـ new:. لإنشاء بود بخيارات أكثر دقة، استخدم الأمر podman pod create قبل إنشاء حاوية. عند تشغيل حاوية مع بود يحتوي على حاوية بنية تحتية، يتم بدء تشغيل حاوية البنية التحتية أولاً.

--pod-id-file=file

تشغيل حاوية في بود موجود وقراءة معرف البود من الملف المحدد file. عند تشغيل حاوية ضمن بود يحتوي على حاوية بنية تحتية، يتم بدء تشغيل حاوية البنية التحتية أولاً.

--preserve-fd=FD1[,FD2,...]

تمرير واصفات الملفات الإضافية المحددة في القائمة المفصولة بفواصل إلى العملية. يمكن تحديده عدة مرات. هذا الخيار مدعوم فقط مع وقت تشغيل crun OCI. قد يكون استخدام هذا الخيار مع أوقات تشغيل OCI الأخرى خطرًا أمنيًا.

(هذا الخيار غير متاح مع عميل Podman عن بعد، بما في ذلك أجهزة Mac و Windows (باستثناء WSL2))

--preserve-fds=N

تمرير N واصفات ملفات إضافية (بالإضافة إلى 0، 1، 2) إلى العملية. إجمالي واصفات الملفات هو 3+N. (هذا الخيار غير متاح مع عميل Podman عن بعد، بما في ذلك أجهزة Mac و Windows (باستثناء WSL2))

--privileged

منح امتيازات موسعة لهذه الحاوية. القيمة الافتراضية هي false.

بشكل افتراضي، تكون حاويات Podman غير مميزة (=false) ولا يمكنها، على سبيل المثال، تعديل أجزاء من نظام التشغيل. هذا لأنه افتراضيًا يُسمح للحاوية بالوصول المحدود إلى الأجهزة. تُمنح الحاوية "المميزة" نفس الوصول إلى الأجهزة مثل المستخدم الذي يشغل الحاوية، باستثناء وحدات التحكم الافتراضية (/dev/tty\d+) عند التشغيل في وضع systemd (--systemd=always).

تقوم الحاوية المميزة بإيقاف تشغيل ميزات الأمان التي تعزل الحاوية عن المضيف. يتم تعطيل القدرات التي تم إسقاطها، والأجهزة المحدودة، ونقاط التحميل للقراءة فقط، وفصل Apparmor/SELinux، ومرشحات Seccomp. بسبب ميزات الأمان المعطلة، يجب عدم تعيين الحقل المميز --privileged إلا نادرًا جدًا حيث يمكن للحاويات بسهولة تجاوز القيود.

لا يمكن للحاويات التي تعمل في مساحة اسم مستخدم (مثل الحاويات غير الجذرية) أن تمتلك امتيازات أكثر من المستخدم الذي بدأها.

--publish, -p=[[ip:][hostPort]:]containerPort[/protocol]

نشر منفذ حاوية، أو نطاق من المنافذ، إلى المضيف.

يمكن تحديد كل من hostPort و containerPort كنطاق من المنافذ. عند تحديد نطاقات لكليهما، يجب أن يتطابق عدد منافذ الحاوية في النطاق مع عدد منافذ المضيف في النطاق.

إذا تم تعيين IP المضيف إلى 0.0.0.0 أو لم يتم تعيينه على الإطلاق، فسيتم ربط المنفذ بجميع عناوين IP على المضيف.

افتراضيًا، يقوم Podman بنشر منافذ TCP. لنشر منفذ UDP بدلاً من ذلك، قم بإعطاء udp كبروتوكول. لنشر كل من منافذ TCP و UDP، قم بتعيين --publish مرتين، مع tcp و udp كبروتوكولات على التوالي. يمكن للحاويات الجذرية أيضًا نشر المنافذ باستخدام بروتوكول sctp.

لا يلزم تحديد منفذ المضيف (على سبيل المثال، podman run -p 127.0.0.1::80). إذا لم يكن كذلك، فسيتم تعيين منفذ الحاوية عشوائيًا إلى منفذ على المضيف.

استخدم podman port لرؤية التعيين الفعلي: podman port $CONTAINER $CONTAINERPORT.

يتم دعم نشر المنافذ فقط للحاويات التي تستخدم مساحة اسم الشبكة الخاصة بها من خلال شبكات bridge، أو أوضاع الشبكة pasta و slirp4netns.

ملاحظة: إذا كانت الحاوية تعمل ضمن بود، فليس من الضروري نشر المنفذ للحاويات في البود. يجب نشر المنفذ بواسطة البود نفسه فقط. تعمل مكدسات شبكة البود مثل مكدس الشبكة على المضيف - مما يعني أن مجموعة متنوعة من الحاويات في البود والبرامج في الحاوية تشترك جميعًا في واجهة واحدة وعنوان IP والمنافذ المرتبطة بها. إذا ربطت حاوية منفذًا، فلا يمكن لأي حاوية أخرى استخدام هذا المنفذ داخل البود أثناء استخدامه. يمكن للحاويات في البود أيضًا التواصل عبر localhost عن طريق ربط حاوية واحدة بـ localhost في البود، وحاوية أخرى تتصل بهذا المنفذ.

--publish-all, -P

نشر جميع المنافذ المكشوفة إلى منافذ عشوائية على واجهات المضيف. القيمة الافتراضية هي false.

عند التعيين إلى true، قم بنشر جميع المنافذ المكشوفة إلى واجهات المضيف. إذا استخدم المشغل -P (أو -p) فإن Podman يجعل المنفذ المكشوف متاحًا على المضيف وتكون المنافذ متاحة لأي عميل يمكنه الوصول إلى المضيف.

عند استخدام هذا الخيار، يقوم Podman بربط أي منفذ مكشوف بمنفذ عشوائي على المضيف ضمن نطاق منافذ مؤقت محدد بواسطة /proc/sys/net/ipv4/ip_local_port_range. للعثور على التعيين بين منافذ المضيف والمنافذ المكشوفة، استخدم podman port.

--pull=policy

سياسة سحب الصورة. الافتراضي هو missing.

  • always: اسحب الصورة دائمًا وأصدر خطأ إذا فشل السحب.
  • missing: اسحب الصورة فقط عندما تكون الصورة غير موجودة في تخزين الحاويات المحلي. أصدر خطأ إذا لم يتم العثور على صورة وفشل السحب.
  • never: لا تسحب الصورة أبدًا ولكن استخدم الصورة من تخزين الحاويات المحلي. أصدر خطأ إذا لم يتم العثور على صورة.
  • newer: اسحب إذا كانت الصورة الموجودة في السجل أحدث من تلك الموجودة في تخزين الحاويات المحلي. تعتبر الصورة أحدث عندما تكون الملخصات مختلفة. مقارنة الطوابع الزمنية عرضة للأخطاء. يتم قمع أخطاء السحب إذا تم العثور على صورة محلية.

--read-only

قم بتركيب نظام ملفات الجذر للحاوية للقراءة فقط.

بشكل افتراضي، تكون أنظمة ملفات الجذر للحاويات قابلة للكتابة، مما يسمح للعمليات بكتابة الملفات في أي مكان. عن طريق تحديد علامة --read-only، يتم تركيب نظام ملفات الجذر للحاويات للقراءة فقط، مما يمنع أي عمليات كتابة.

--read-only-tmpfs

عند تشغيل حاويات --read-only، قم بتركيب tmpfs للقراءة والكتابة على /dev و /dev/shm و /run و /tmp و /var/tmp. القيمة الافتراضية هي true.

--read-only --read-only-tmpfs / /run, /tmp, /var/tmp
true true r/o r/w
true false r/o r/o
false false r/w r/w
false true r/w r/w

عندما تكون --read-only=true و --read-only-tmpfs=true، يتم تركيب tmpfs إضافية على الدلائل /tmp و /run و /var/tmp.

عندما تكون --read-only=true و --read-only-tmpfs=false، يتم تمييز /dev و /dev/shm للقراءة فقط (Read/Only) ولا يتم تركيب tmpfs على /tmp و /run و /var/tmp. يتم كشف الدلائل من الصورة الأساسية، مما يعني أنها للقراءة فقط بشكل افتراضي. هذا يجعل الحاوية للقراءة فقط تمامًا. لا توجد دلائل قابلة للكتابة داخل الحاوية. في هذا الوضع، تحتاج الدلائل القابلة للكتابة إلى إضافتها عبر وحدات تخزين أو تركيبات خارجية.

بشكل افتراضي، عندما تكون --read-only=false، تكون /dev و /dev/shm قابلة للقراءة والكتابة (read/write)، وتكون /tmp و /run و /var/tmp دلائل قابلة للقراءة والكتابة من صورة الحاوية.

القيم الصالحة لـ policy هي:

  • no: لا تقم بإعادة تشغيل الحاويات عند الخروج
  • never: مرادف لـ no؛ لا تقم بإعادة تشغيل الحاويات عند الخروج
  • on-failure[:max_retries]: أعد تشغيل الحاويات عند خروجها برمز خروج غير صفري، مع المحاولة إلى أجل غير مسمى أو حتى الوصول إلى عدد max_retries الاختياري
  • always: أعد تشغيل الحاويات عند خروجها، بغض النظر عن الحالة، مع المحاولة إلى أجل غير مسمى
  • unless-stopped: مطابق لـ always

--uidmap=[flags]container_uid:from_uid[:amount]

قم بتشغيل الحاوية في مساحة اسم مستخدم جديدة باستخدام خريطة UID المقدمة. يتعارض هذا الخيار مع الخيارين --userns و --subuidname. يوفر هذا الخيار طريقة لتعيين معرفات المضيف (host UIDs) إلى معرفات الحاوية (container UIDs). يمكن تمريره عدة مرات لتعيين نطاقات مختلفة.

تتم مناقشة القيم الممكنة لـ flags الاختيارية بشكل أعمق في هذه الصفحة. قيمة amount اختيارية وتُفترض أنها 1 إذا لم يتم تقديمها.

قيمة from_uid تستند إلى المستخدم الذي يقوم بتشغيل الأمر، سواء كان مستخدمًا بصلاحيات الجذر (rootful) أو بدون صلاحيات الجذر (rootless).

  • مستخدم بصلاحيات الجذر (rootful): [flags]container_uid:host_uid[:amount]
  • مستخدم بدون صلاحيات الجذر (rootless): [flags]container_uid:intermediate_uid[:amount]

تعيينات المستخدم بصلاحيات الجذر (Rootful mappings)

عندما يتم استدعاء podman run بواسطة مستخدم لديه صلاحيات، يعمل الخيار --uidmap كتعيين مباشر بين معرفات المضيف (host UIDs) ومعرفات الحاويات (container UIDs).

معرف المضيف (host UID) -> معرف الحاوية (container UID)

تحدد amount عدد معرفات UID المتتالية التي يتم تعيينها. إذا كانت amount على سبيل المثال 4، فإن التعيين يبدو كالتالي:

معرف المضيف (host UID) معرف الحاوية (container UID)
from_uid container_uid
from_uid + 1 container_uid + 1
from_uid + 2 container_uid + 2
from_uid + 3 container_uid + 3

تعيينات المستخدم بدون صلاحيات الجذر (Rootless mappings)

عندما يتم استدعاء podman run بواسطة مستخدم غير مميز (أي، يعمل بدون صلاحيات الجذر rootless)، يتم تفسير قيمة from_uid على أنها "معرف وسيط" (intermediate UID). في حالة عدم وجود صلاحيات الجذر (rootless)، لا يتم تعيين معرفات المضيف (host UIDs) مباشرة إلى معرفات الحاويات (container UIDs). بدلاً من ذلك، يتم التعيين عبر خطوتين للتعيين:

معرف المضيف (host UID) -> معرف وسيط (intermediate UID) -> معرف الحاوية (container UID)

يؤثر خيار --uidmap فقط على خطوة التعيين الثانية.

يتم استنتاج خطوة التعيين الأولى بواسطة Podman من محتويات الملف /etc/subuid ومعرف UID للمستخدم الذي يستدعي Podman.

خطوة التعيين الأولى:

معرف المضيف (host UID) معرف وسيط (intermediate UID)
UID للمستخدم Podman 0
معرف UID فرعي أول (1st subordinate UID) 1
معرف UID فرعي ثاني (2nd subordinate UID) 2
معرف UID فرعي ثالث (3rd subordinate UID) 3
معرف UID فرعي n (nth subordinate UID) n

لكي يتمكن المستخدم من استخدام معرفات UID وسيطة أكبر من الصفر، يحتاج المستخدم إلى تكوين معرفات UID فرعية في /etc/subuid. انظر subuid(5).

يتم تكوين خطوة التعيين الثانية باستخدام --uidmap.

إذا كانت amount على سبيل المثال 5، فإن خطوة التعيين الثانية تبدو كالتالي:

كمستخدم بدون صلاحيات الجذر (rootless)، يتم تعيين معرف المضيف (host ID) المحدد في --uidmap أو --gidmap من مساحة الاسم الوسيطة (intermediate namespace) التي تم إنشاؤها بواسطة Podman. في بعض الأحيان يكون من المرغوب الإشارة مباشرة إلى مساحة اسم المضيف (host namespace). يمكن القيام بذلك يدويًا، عن طريق تشغيل podman unshare cat /proc/self/gid_map، والعثور على معرف المضيف المطلوب في العمود الثاني من الإخراج، والحصول على المعرف الوسيط المقابل من العمود الأول.

    • The volume is not managed by an external volume driver
    • The volume driver is not "image"

    For volumes with idmapped mounts (using the idmap option), the ownership change takes into account the container's user namespace mappings, but the idmapped volume retains proper UID/GID mapping. For volumes without idmapping, the mount point is chowned to match the container's process user and group, mapped to the host user namespace if user namespace remapping is enabled.

    If a container is created in a new user namespace, the UID and GID in the container may correspond to another UID and GID on the host.

    The :U suffix tells Podman to use the correct host UID and GID based on the UID and GID within the container, to change recursively the owner and group of the source volume. Chowning walks the file system under the volume and changes the UID/GID on each file. If the volume has thousands of inodes, this process takes a long time, delaying the start of the container.

    Warning use with caution since this modifies the host filesystem.

    Labeling Volume Mounts

    Labeling systems like SELinux require that proper labels are placed on volume content mounted into a container. Without a label, the security system might prevent the processes running inside the container from using the content. By default, Podman does not change the labels set by the OS.

    To change a label in the container context, add either of two suffixes :z or :Z to the volume mount. These suffixes tell Podman to relabel file objects on the shared volumes. The z option tells Podman that two or more containers share the volume content. As a result, Podman labels the content with a shared content label. Shared volume labels allow all containers to read/write content. The Z option tells Podman to label the content with a private unshared label. Only the current container can use a private volume.

    Note: all containers within a pod share the same SELinux label. This means all containers within said pod can read/write volumes shared into the container created with the :Z on any one of the containers. Relabeling walks the file system under the volume and changes the label on each file; if the volume has thousands of inodes, this process takes a long time, delaying the start of the container. If the volume was previously relabeled with the z option, Podman is optimized to not relabel a second time. If files are moved into the volume, then the labels can be manually changed with the chcon -Rt container_file_t PATH command.

    Note: Do not relabel system files and directories. Relabeling system content might cause other confined services on the machine to fail. For these types of containers we recommend disabling SELinux separation. The option --security-opt label=disable disables SELinux separation for the container. For example if a user wanted to volume mount their entire home directory into a container, they need to disable SELinux separation.

    $ podman run --security-opt label=disable -v $HOME:/home/user fedora touch /home/user/file

    Overlay Volume Mounts

    The :O flag tells Podman to mount the directory from the host as a temporary storage using the overlay file system. The container processes can modify content within the mountpoint which is stored in the container storage in a separate directory. In overlay terms, the source directory is the lower, and the container storage directory is the upper. Modifications to the mount point are destroyed when the container finishes executing, similar to a tmpfs mount point being unmounted.

    For advanced users, the overlay option also supports custom non-volatile upperdir and workdir for the overlay mount. Custom upperdir and workdir can be fully managed by the users themselves, and Podman does not remove it on lifecycle completion. Example :O,upperdir=/some/upper,workdir=/some/work

    Subsequent executions of the container sees the original source directory content, any changes from previous container executions no longer exist.

    One use case of the overlay mount is sharing the package cache from the host into the container to allow speeding up builds.

    Note: The O flag conflicts with other options listed above.

    Content mounted into the container is labeled with the private label. On SELinux systems, labels in the source directory must be readable by the container label. Usually containers can read/execute container_share_t and can read/write container_file_t. If unable to change the labels on a source volume, SELinux container separation must be disabled for the container to work.

    Do not modify the source directory mounted into the container with an overlay mount, it can cause unexpected failures. Only modify the directory after the container finishes running.

    Mounts propagation

    By default, bind-mounted volumes are private. That means any mounts done inside the container are not visible on the host and vice versa. One can change this behavior by specifying a volume mount propagation property. When a volume is shared, mounts done under that volume inside the container are visible on host and vice versa.

    تعيين المنافذ للاستخدام الخارجي

    يمكن تعيين المنفذ المكشوف لتطبيق ما إلى منفذ المضيف باستخدام العلامة -p. على سبيل المثال، يمكن تعيين منفذ httpd 80 إلى منفذ المضيف 8080 باستخدام الأمر التالي:

    $ podman run -p 8080:80 -d -i -t fedora/httpd

    تحميل وحدات تخزين خارجية

    لتحميل دليل مضيف كوحدة تخزين للحاوية، حدد المسار المطلق للدليل والمسار المطلق لدليل الحاوية مفصولين بنقطتين رأسيتين. إذا كان المصدر وحدة تخزين مسماة تحت إدارة Podman، فيُوصى باستخدام اسمها بدلاً من مسار وحدة التخزين. وإلا، تعتبر وحدة التخزين يتيمة وسيتم مسحها بواسطة أمر podman volume prune:

    $ podman run -v /var/db:/data1 -i -t fedora bash
$ podman run -v data:/data2 -i -t fedora bash
$ podman run -v /var/cache/dnf:/var/cache/dnf:O -ti fedora dnf -y update

    إذا كانت الحاوية بحاجة إلى وحدة تخزين قابلة للكتابة بواسطة مستخدم غير جذر داخل الحاوية، استخدم الخيار U. يخبر هذا الخيار Podman بتغيير ملكية وحدة التخزين المصدر لتطابق معرف المستخدم (UID) ومعرف المجموعة (GID) الافتراضيين المستخدمين داخل الحاوية.

    $ podman run -d -e MARIADB_ROOT_PASSWORD=root --user mysql --userns=keep-id -v ~/data:/var/lib/mysql:Z,U mariadb

    بدلاً من ذلك، إذا كانت الحاوية بحاجة إلى وحدة تخزين قابلة للكتابة بواسطة مستخدم غير جذر داخل الحاوية، فإن الخيار --userns=keep-id يسمح للمستخدمين بتحديد معرف المستخدم (UID) ومعرف المجموعة (GID) للمستخدم الذي ينفذ Podman إلى معرفات مستخدم ومجموعة محددة داخل الحاوية. نظرًا لأن العمليات التي تعمل داخل الحاوية تعمل بمعرف المستخدم، يمكنها قراءة/كتابة الملفات المملوكة للمستخدم.

    $ podman run -d -e MARIADB_ROOT_PASSWORD=root --user mysql --userns=keep-id:uid=999,gid=999 -v ~/data:/var/lib/mysql:Z mariadb

    باستخدام علامات --mount لتحميل دليل مضيف كمجلد حاوية، حدد المسار المطلق للدليل أو اسم وحدة التخزين، والمسار المطلق داخل دليل الحاوية:

    $ podman run --mount type=bind,src=/var/db,target=/data1 busybox sh
$ podman run --mount type=bind,src=volume-name,target=/data1 busybox sh

    عند استخدام SELinux، كن على علم بأن المضيف ليس لديه معرفة بسياسة SELinux للحاوية. لذلك، في المثال أعلاه، إذا تم فرض سياسة SELinux، فإن الدليل /var/db غير قابل للكتابة بواسطة الحاوية. سيحدث خطأ "Permission Denied" (رفض الإذن)، وسيتم إضافة رسالة avc: إلى سجل نظام المضيف.

    للتغلب على ذلك، في وقت كتابة صفحة الدليل هذه، يلزم تشغيل الأمر التالي حتى يتم إرفاق نوع سياسة SELinux المناسب بالدليل المضيف:

    $ chcon -Rt svirt_sandbox_file_t /var/db

    الآن، يُسمح بالكتابة إلى وحدة التخزين /data1 في الحاوية، وتنطبق التغييرات على المضيف في /var/db.

    استخدام تسميات أمان بديلة

    تجاوز مخطط التسمية الافتراضي لكل حاوية عن طريق تحديد العلامة --security-opt. على سبيل المثال، تحديد مستوى MCS/MLS، وهو متطلب لأنظمة MLS. يتيح تحديد المستوى في الأمر التالي مشاركة نفس المحتوى بين الحاويات.

    podman run --security-opt label=level:s0:c100,c200 -i -t fedora bash

    مثال على MLS قد يكون:

    $ podman run --security-opt label=level:TopSecret -i -t rhel7 bash

    لتعطيل تسميات الأمان لهذه الحاوية بدلاً من التشغيل بالعلامة

    --permissive، استخدم الأمر التالي:

    $ podman run --security-opt label=disable -i -t fedora bash

    قم بتشديد سياسة الأمان على العمليات داخل الحاوية عن طريق تحديد نوع بديل للحاوية. على سبيل المثال، قم بتشغيل حاوية يُسمح لها فقط بالاستماع على منافذ Apache عن طريق تنفيذ الأمر التالي:

    $ podman run --security-opt label=type:svirt_apache_t -i -t centos bash

    لاحظ أنه يجب كتابة سياسة SELinux تحدد نوع svirt_apache_t.

    لإخفاء مسارات محددة إضافية في الحاوية، حدد المسارات مفصولة بنقطتين رأسيتين باستخدام الخيار mask مع العلامة --security-opt.

    $ podman run --security-opt mask=/foo/bar:/second/path fedora bash

    لإلغاء إخفاء جميع المسارات التي تم إخفاؤها افتراضيًا، قم بتعيين الخيار unmask إلى ALL. أو لإلغاء إخفاء مسارات محددة فقط، حدد المسارات كما هو موضح أعلاه مع الخيار mask.

    $ podman run --security-opt unmask=ALL fedora bash

    لإلغاء إخفاء جميع المسارات التي تبدأ بـ /proc، قم بتعيين الخيار unmask إلى /proc/*.

    $ podman run --security-opt unmask=/proc/* fedora bash
    $ podman run --security-opt unmask=/foo/bar:/sys/firmware fedora bash

    تعيين وزن الجهاز عبر العلامة --blkio-weight-device.

    $ podman run -it --blkio-weight-device "/dev/sda:200" ubuntu

    $ echo "asdf" | podman run --rm -i --entrypoint /bin/cat someimage
asdf

    تعيين معلمات نواة مسماة (Sysctls)

    يقوم --sysctl بتعيين معلمات نواة مسماة (sysctls) في الحاوية. على سبيل المثال، لتشغيل إعادة توجيه IP في مساحة اسم شبكة الحاوية، قم بتشغيل هذا الأمر:

    $ podman run --sysctl net.ipv4.ip_forward=1 someimage

    لاحظ أنه ليست كل sysctls مسماة. لا يدعم Podman تغيير sysctls داخل حاوية تعدل أيضًا نظام المضيف. مع تطور النواة، نتوقع رؤية المزيد من sysctls تصبح مسماة.

    راجع تعريف الخيار --sysctl أعلاه للحصول على القائمة الحالية لـ sysctls المدعومة.

    تعيين تعيين UID/GID في مساحة اسم مستخدم جديدة

    يتطلب تشغيل حاوية في مساحة اسم مستخدم جديدة تعيين معرفات المستخدم (UIDs) ومعرفات المجموعة (GIDs) من المضيف.

    $ podman run --uidmap 0:30000:7000 --gidmap 0:30000:7000 fedora echo hello

    يسمح Podman بتكوين التخزين عن طريق تغيير القيم في /etc/container/storage.conf أو باستخدام خيارات عامة. يوضح هذا كيفية استخدام مخزن صور إضافي لتشغيل لمرة واحدة لـ busybox باستخدام خيارات عامة.
