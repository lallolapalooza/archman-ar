/podman-init. تحميل فوق /run يكسر تنفيذ الحاوية.

--init-ctr=type

(للحاويات فقط). عند استخدام الحاويات، قم بإنشاء حاوية من نوع init، والتي يتم تشغيلها بعد بدء تشغيل حاوية البنية التحتية ولكن قبل بدء تشغيل حاويات الحاوية العادية. تعتبر حاويات init مفيدة لتشغيل عمليات الإعداد لتطبيقات الحاوية.

القيم الصالحة لنوع init-ctr هي always أو once. القيمة always تعني أن الحاوية تعمل مع كل تشغيل للحاوية، بينما القيمة once تعني أن الحاوية تعمل مرة واحدة فقط عند بدء تشغيل الحاوية ثم يتم إزالة الحاوية.

لا تعمل حاويات init إلا عند بدء الحاوية. إعادة تشغيل حاوية لا ينفذ أي حاويات init. علاوة على ذلك، لا يمكن إنشاء حاويات init إلا في حاوية عندما لا تكون تلك الحاوية قيد التشغيل.

--init-path=path

المسار إلى ثنائي حاوية-init.

--interactive, -i

عند تعيينه على true، اجعل stdin متاحًا للعملية المحتواة. إذا كان false، فإن stdin للعملية المحتواة فارغ ويتم إغلاقه على الفور.

إذا تم التوصيل، يتم تمرير stdin إلى العملية المحتواة. إذا تم الفصل، فإن قراءة stdin ستمنع حتى يتم توصيلها لاحقًا.

تنبيه: سيستهلك Podman الإدخال من stdin بمجرد توفره، حتى لو لم تطلبه العملية المحتواة.

--ip=ipv4

حدد عنوان IPv4 ثابت للحاوية، على سبيل المثال 10.88.64.128. لا يمكن استخدام هذا الخيار إلا إذا كانت الحاوية مرتبطة بشبكة واحدة فقط - أي، يتم استخدام --network=network-name مرة واحدة على الأكثر - وإذا لم تكن الحاوية تنضم إلى مساحة اسم شبكة حاوية أخرى عبر --network=container:id. يجب أن يكون العنوان ضمن تجمع عناوين IP للشبكة (الافتراضي 10.88.0.0/16).

لتحديد عناوين IP ثابتة متعددة لكل حاوية، قم بتعيين شبكات متعددة باستخدام الخيار --network مع عنوان IP ثابت محدد لكل منها باستخدام وضع ip لهذا الخيار.

--ip6=ipv6

حدد عنوان IPv6 ثابت للحاوية، على سبيل المثال fd46:db93:aa76:ac37::10. لا يمكن استخدام هذا الخيار إلا إذا كانت الحاوية مرتبطة بشبكة واحدة فقط - أي، يتم استخدام --network=network-name مرة واحدة على الأكثر - وإذا لم تكن الحاوية تنضم إلى مساحة اسم شبكة حاوية أخرى عبر --network=container:id. يجب أن يكون العنوان ضمن تجمع عناوين IPv6 للشبكة.

لتحديد عناوين IPv6 ثابتة متعددة لكل حاوية، قم بتعيين شبكات متعددة باستخدام الخيار --network مع عنوان IPv6 ثابت محدد لكل منها باستخدام وضع ip6 لهذا الخيار.

--ipc=ipc

قم بتعيين وضع مساحة اسم IPC للحاوية. الافتراضي هو إنشاء مساحة اسم IPC خاصة.

  • "": استخدم افتراضي Podman، المحدد في containers.conf.
  • container:id: يعيد استخدام الذاكرة المشتركة، ودلالات، وقوائم الرسائل لحاوية أخرى.
  • host: استخدم ذاكرة المضيف المشتركة، ودلالات، وقوائم الرسائل داخل الحاوية. ملاحظة: وضع المضيف يمنح الحاوية وصولاً كاملاً إلى الذاكرة المحلية المشتركة ولذلك يعتبر غير آمن.
  • none: مساحة اسم IPC خاصة، مع عدم تحميل /dev/shm.
  • ns:path: المسار إلى مساحة اسم IPC للانضمام إليها.
  • private: مساحة اسم IPC خاصة.
  • shareable: مساحة اسم IPC خاصة مع إمكانية مشاركتها مع حاويات أخرى.

--label, -l=key=value

إضافة بيانات وصفية إلى حاوية.

--label-file=file

قراءة ملف من تسميات مفصولة بسطور.

--link-local-ip=ip

غير منفذ.

--log-driver=driver

مشغل التسجيل للحاوية. الخيارات المتاحة حاليًا هي k8s-file، journald، none، passthrough، و passthrough-tty، مع json-file تم تسميتها بـ k8s-file للتوافق مع البرمجة النصية. (الافتراضي journald).

يعرض أمر podman info أدناه مشغل التسجيل الافتراضي للنظام.

$ podman info --format '{{ .Host.LogDriver }}'
journald

مشغل passthrough يمرر التدفقات القياسية (stdin، stdout، stderr) إلى الحاوية. لا يُسمح به مع عميل Podman البعيد، بما في ذلك أجهزة Mac و Windows (باستثناء WSL2)، وعلى TTY، لأنه عرضة للهجمات عبر TIOCSTI.

مشغل passthrough-tty هو نفسه مشغل passthrough باستثناء أنه يسمح باستخدامه أيضًا على TTY إذا أراد المستخدم ذلك حقًا.

--log-opt=name=value

خيارات محددة لمشغل التسجيل.

تعيين تكوين تسجيل مخصص. أسماء *name* المدعومة هي:

path: تحديد مسار لملف السجل
(مثال: --log-opt path=/var/log/container/mycontainer.json)؛

max-size: تحديد أقصى حجم لملف السجل
(مثال: --log-opt max-size=10mb)؛

tag: تحديد علامة سجل مخصصة للحاوية
(مثال: --log-opt tag="{{.ImageName}}". يدعم نفس المفاتيح مثل podman inspect --format. هذا الخيار مدعوم حاليًا فقط بواسطة مشغل التسجيل journald.

--mac-address=address

عنوان MAC لواجهة شبكة الحاوية (مثال 92:d0:c6:0a:29:33) لا يمكن استخدام هذا الخيار إلا إذا كانت الحاوية مرتبطة بشبكة واحدة فقط - أي، يتم استخدام --network=network-name مرة واحدة على الأكثر - وإذا لم تكن الحاوية تنضم إلى مساحة اسم شبكة حاوية أخرى عبر --network=container:id.

تذكر أن عنوان MAC في شبكة Ethernet يجب أن يكون فريدًا. يعتمد عنوان IPv6 المحلي للربط على عنوان MAC للجهاز وفقًا لـ RFC4862.

لتحديد عناوين MAC ثابتة متعددة لكل حاوية، قم بتعيين شبكات متعددة باستخدام الخيار --network مع عنوان MAC ثابت محدد لكل منها باستخدام وضع mac لهذا الخيار.

--memory, -m=number[unit]

حد الذاكرة. يمكن أن تكون الوحدة unit هي b (بايت)، k (كيلوبايت)، m (ميجابايت)، أو g (جيجابايت).

يسمح بتقييد الذاكرة المتاحة للحاوية. إذا كان المضيف يدعم ذاكرة المبادلة، فيمكن أن يكون إعداد الذاكرة -m أكبر من ذاكرة الوصول العشوائي الفعلية. إذا تم تحديد حد 0 (دون استخدام -m)، فلن يتم تحديد ذاكرة الحاوية. قد يتم تقريب الحد الفعلي لأعلى إلى مضاعف حجم صفحة نظام التشغيل (القيمة كبيرة جدًا، وهي ملايين التريليونات).

هذا الخيار غير مدعوم على أنظمة cgroups V1 بدون جذر.

--memory-reservation=number[unit]

حد الذاكرة الناعم. يمكن أن تكون الوحدة unit هي b (بايت)، k (كيلوبايت)، m (ميجابايت)، أو g (جيجابايت).

بعد تعيين حجز الذاكرة، عندما يكتشف النظام تضاربًا في الذاكرة أو نقصًا في الذاكرة، يتم إجبار الحاويات على تقييد استهلاكها إلى حجزها. لذا قم دائمًا بتعيين القيمة أقل من --memory، وإلا فإن الحد الأقصى يأخذ الأسبقية. بشكل افتراضي، يكون حجز الذاكرة هو نفسه حد الذاكرة.

هذا الخيار غير مدعوم على أنظمة cgroups V1 بدون جذر.

--memory-swap=number[unit]

قيمة حد تساوي الذاكرة بالإضافة إلى المبادلة. يمكن أن تكون الوحدة unit هي b (بايت)، k (كيلوبايت)، m (ميجابايت)، أو g (جيجابايت).

يجب استخدامه مع علامة
-m (--memory). يجب أن تكون قيمة الوسيط أكبر من قيمة
-m (--memory). بشكل افتراضي، يتم تعيينها على ضعف قيمة --memory.

قم بتعيين number إلى -1 لتمكين المبادلة غير المحدودة.

هذا الخيار غير مدعوم على أنظمة cgroups V1 بدون جذر.

--memory-swappiness=number

ضبط سلوك مبادلة ذاكرة الحاوية. يقبل عددًا صحيحًا بين 0 و 100.

هذا العلم مدعوم فقط على أنظمة cgroups V1 ذات الجذر.

--mount=type=TYPE,TYPE-SPECIFIC-OPTION[,...]

إرفاق تحميل نظام ملفات بالحاوية.

أنواع التحميل المدعومة حاليًا هي artifact، bind، devpts، glob، image، ramfs، tmpfs، و volume.

خيارات مشتركة لجميع أنواع التحميل:

  • src، source: مصدر التحميل لـ bind، glob، و volume. مطلوب لـ artifact، bind، glob، image، و volume.
  • dst، dest، destination، target: وجهة التحميل.

عند تحديد مصادر glob بدون دليل الوجهة، يتم تحميل الملفات والدلائل مع مسارها الكامل داخل الحاوية. عند تحديد الوجهة، يتم تحميل الملفات والدلائل التي تطابق glob على اسم الملف الأساسي في دليل الوجهة. يخبر الخيار type=glob,src=/foo*,destination=/tmp/bar محركات الحاويات بتحميل ملفات المضيف التي تطابق /foo* إلى الدليل /tmp/bar/ في الحاوية.

خيارات خاصة بنوع=artifact:

  • digest: إذا كان مصدر القطعة الأثرية يحتوي على أجزاء متعددة، فيمكن تحديد هضم لتركيب جزء واحد فقط محدد بالهضم.
  • title: إذا كان مصدر القطعة الأثرية يحتوي على أجزاء متعددة، فيمكن تعيين عنوان يتم مقارنته مع التعليق التوضيحي org.opencontainers.image.title.
  • name: يمكن استخدام هذا لتجاوز اسم الملف الذي نستخدمه داخل الحاوية للتحميل. في قطعة أثرية ذات جزء واحد، يتم استخدام الاسم كما هو إذا كان dst دليلًا وإلا يتم تجاهله. مع قطعة أثرية متعددة الأجزاء، سيتم استخدام الاسم مع لاحقة فهرس <name>-x حيث x هو فهرس الطبقة في القطعة الأثرية بدءًا من 0.

يحتوي الوسيط src على اسم القطعة الأثرية، والتي يجب أن تكون موجودة محليًا بالفعل. يحتوي الوسيط dst على المسار المستهدف، إذا كان المسار في الحاوية دليلًا، فسيتم استخدام عنوان الجزء (التعليق التوضيحي org.opencontainers.image.title) كاسم ملف ويتم دمجه مع المسار.

If the annotation does not exist the digest will be used as filename instead. This results in all blobs of the artifact mounted into the container at the given path.

However, if the dst path is an existing file in the container, then the blob will be mounted directly on it. This only works when the artifact contains a single blob or when either digest or title are specified.

If the dst path does not already exist in the container then if the artifact contains a single blob it behaves like existing file case and mounts directly to that path. If the artifact has more than one blob it works like the existing directory case and mounts each blob as file within the dst path.

Options specific to type=volume:

  • ro, readonly: true or false (default if unspecified: false).
  • U, chown: true or false (default if unspecified: false). Recursively change the owner and group of the source volume based on the UID and GID of the container.
  • subpath: Mount only a specific subpath within the volume, instead of the whole volume.
  • idmap: If specified, create an idmapped mount to the target user namespace in the container. The idmap option is only supported by Podman in rootful mode. The Linux kernel does not allow the use of idmapped file systems for unprivileged users. The idmap option supports a custom mapping that can be different than the user namespace used by the container. The mapping can be specified after the idmap option like: idmap=uids=0-1-10#10-11-10;gids=0-100-10. For each triplet, the first value is the start of the backing file system IDs that are mapped to the second value on the host. The length of this mapping is given in the third value. Multiple ranges are separated with #. If the specified mapping is prepended with a '@', then the mapping is considered relative to the container user namespace. The host ID for the mapping is changed to account for the relative position of the container user in the container user namespace.

Options specific to type=image:

  • rw, readwrite: true or false (default if unspecified: false).
  • subpath: Mount only a specific path within the image, instead of the whole image.

Options specific to bind and glob:

  • ro, readonly: true or false (default if unspecified: false).
  • bind-propagation: shared, slave, private, unbindable, rshared, rslave, runbindable, or rprivate (default).[1] ⟨#Footnote1⟩ See also mount(2).
  • bind-nonrecursive: do not set up a recursive bind mount. By default it is recursive.
  • relabel: shared, private.
  • idmap: true or false (default if unspecified: false). If true, create an idmapped mount to the target user namespace in the container. The idmap option is only supported by Podman in rootful mode.
  • U, chown: true or false (default if unspecified: false). Recursively change the owner and group of the source volume based on the UID and GID of the container.
  • no-dereference: do not dereference symlinks but copy the link source into the mount destination.

Options specific to type=tmpfs and ramfs:

  • ro, readonly: true or false (default if unspecified: false).
  • tmpfs-size: Size of the tmpfs/ramfs mount, in bytes. Unlimited by default in Linux.
  • tmpfs-mode: Octal file mode of the tmpfs/ramfs (e.g. 700 or 0700.).
  • tmpcopyup: Enable copyup from the image directory at the same location to the tmpfs/ramfs. Used by default.
  • noatime: Disable updating file access times when the file is read.
  • notmpcopyup: Disable copying files from the image to the tmpfs/ramfs.
  • U, chown: true or false (default if unspecified: false). Recursively change the owner and group of the source volume based on the UID and GID of the container.

Options specific to type=devpts:

  • uid: numeric UID of the file owner (default: 0).
  • gid: numeric GID of the file owner (default: 0).
  • mode: octal permission mask for the file (default: 600).
  • max: maximum number of PTYs (default: 1048576).

Examples:

  • type=bind,source=/path/on/host,destination=/path/in/container
  • type=bind,src=/path/on/host,dst=/path/in/container,relabel=shared
  • type=bind,src=/path/on/host,dst=/path/in/container,relabel=shared,U=true
  • type=devpts,destination=/dev/pts
  • type=glob,src=/usr/lib/libfoo*,destination=/usr/lib,ro=true
  • type=image,source=fedora,destination=/fedora-image,rw=true
  • type=ramfs,tmpfs-size=512M,destination=/path/in/container
  • type=tmpfs,tmpfs-size=512M,destination=/path/in/container
  • type=tmpfs,destination=/path/in/container,noswap
  • type=artifact,src=quay.io/libpod/testartifact:20250206-single,dst=/data
  • type=artifact,src=quay.io/libpod/testartifact:20250206-multi,dst=/data,title=test1
  • type=volume,src=test_vol,dst=/data,subpath=/code/docs

--name=name

Assign a name to the container.

The operator can identify a container in three ways:

  • UUID long identifier (“f78375b1c487e03c9438c729345e54db9d20cfa2ac1fc3494b6eb60872e74778”);
  • UUID short identifier (“f78375b1c487”);
  • Name (“jonah”).

Podman generates a UUID for each container, and if no name is assigned to the container using --name, Podman generates a random string name. The name can be useful as a more human-friendly way to identify containers. This works for both background and foreground containers. The container's name is also added to the /etc/hosts file using the container's primary IP address (also see the --add-host option).

--network=mode, --net

Set the network mode for the container.

Valid mode values are:

•
bridge[:OPTIONS,...]: Create a network stack on the default bridge. This is the default for rootful containers. It is possible to specify these additional options:
  • alias=name: Add network-scoped alias for the container.
  • ip=IPv4: Specify a static IPv4 address for this container.
  • ip6=IPv6: Specify a static IPv6 address for this container.
  • mac=MAC: Specify a static MAC address for this container.
  • interface_name=name: Specify a name for the created network interface inside the container.
  • host_interface_name=name: Specify a name for the created network interface outside the container.
Any other options will be passed through to netavark without validation. This can be useful to pass arguments to netavark plugins.

For example, to set a static ipv4 address and a static mac address, use --network bridge:ip=10.88.0.10,mac=44:33:22:11:00:99.

  • <network name or ID>[:OPTIONS,...]: Connect to a user-defined network; this is the network name or ID from a network created by podman network create. It is possible to specify the same options described under the bridge mode above. Use the --network option multiple times to specify additional networks.
    For backwards compatibility it is also possible to specify comma-separated networks on the first --network argument, however this prevents you from using the options described under the bridge section above.
  • none: Create a network namespace for the container but do not configure network interfaces for it, thus the container has no network connectivity.
  • container:id: Reuse another container's network stack.
  • host: Use the host's network namespace for the container instead of creating an isolated namespace. Warning: This gives the container full access to abstract Unix domain sockets and to TCP/UDP sockets bound to localhost. Since these mechanisms are often used to prevent access to sensitive system services, isolating them from access by external entities, use of this option may be considered a security vulnerability.
  • ns:path: Path to a network namespace to join.
  • private: Create a new namespace for the container. This uses the bridge mode for rootful containers and slirp4netns for rootless ones.
  • slirp4netns[:OPTIONS,...]: use slirp4netns(1) to create a user network stack. It is possible to specify these additional options, they can also be set with network_cmd_options in containers.conf:
  • allow_host_loopback=true|false: Allow slirp4netns to reach the host loopback IP (default is 10.0.2.2 or the second IP from slirp4netns cidr subnet when changed, see the cidr option below). The default is false.
  • mtu=MTU: Specify the MTU to use for this network. (Default is 65520).
  • cidr=CIDR: Specify ip range to use for this network. (Default is 10.0.2.0/24).
  • enable_ipv6=true|false: Enable IPv6. Default is true. (Required for outbound_addr6).
  • outbound_addr=INTERFACE: Specify the outbound interface slirp binds to (ipv4 traffic only).
  • outbound_addr=IPv4: Specify the outbound ipv4 address slirp binds to.
  • outbound_addr6=INTERFACE: Specify the outbound interface slirp binds to (ipv6 traffic only).
  • outbound_addr6=IPv6: Specify the outbound ipv6 address slirp binds to.
  • port_handler=rootlesskit: Use rootlesskit for port forwarding. Default.
    Note: Rootlesskit changes the source IP address of incoming packets to an IP address in the container network namespace, usually 10.0.2.100. If the application requires the real source IP address, e.g. web server logs, use the slirp4netns port handler.     ملاحظة: إذا كانت الحاوية تعمل داخل pod، فليس من الضروري نشر المنفذ للحاويات الموجودة في pod. يجب فقط نشر المنفذ بواسطة pod نفسه. تعمل مكدسات شبكة pod مثل مكدس الشبكة على المضيف - عندما تكون هناك مجموعة متنوعة من الحاويات في pod، وبرامج في الحاوية، تشترك جميعها في واجهة عنوان IP واحد، والمنافذ المرتبطة. إذا تم ربط حاوية بمنفذ، فلا يمكن لأي حاوية أخرى استخدام هذا المنفذ داخل pod أثناء استخدامه. يمكن للحاويات في pod أيضًا التواصل عبر localhost عن طريق ربط حاوية بـ localhost في pod، وتوصيل أخرى بهذا المنفذ.

--publish-all, -P

انشر جميع المنافذ المكشوفة إلى منافذ عشوائية على واجهات المضيف. الافتراضي هو false.

عند تعيينه على true، انشر جميع المنافذ المكشوفة إلى واجهات المضيف. إذا استخدم المشغل -P (أو -p) فستجعل Podman المنفذ المكشوف متاحًا على المضيف وتكون المنافذ متاحة لأي عميل يمكنه الوصول إلى المضيف.

عند استخدام هذا الخيار، ترتبط Podman بأي منفذ مكشوف بمنفذ عشوائي على المضيف ضمن نطاق منافذ مؤقتة محدد بواسطة /proc/sys/net/ipv4/ip_local_port_range. للعثور على التعيين بين منافذ المضيف والمنافذ المكشوفة، استخدم podman port.

--pull=policy

سياسة سحب الصورة. الافتراضي هو missing.

  • always: اسحب الصورة دائمًا وأصدر خطأ إذا فشل السحب.
  • missing: اسحب الصورة فقط عندما لا تكون الصورة موجودة في تخزين الحاويات المحلي. أصدر خطأ إذا لم يتم العثور على صورة وفشل السحب.
  • never: لا تسحب الصورة أبدًا ولكن استخدم الصورة من تخزين الحاويات المحلي. أصدر خطأ إذا لم يتم العثور على صورة.
  • newer: اسحب إذا كانت الصورة الموجودة في السجل أحدث من الصورة في تخزين الحاويات المحلي. تعتبر الصورة أحدث عندما تكون التجزئات مختلفة. مقارنة الطوابع الزمنية عرضة للأخطاء. يتم قمع أخطاء السحب إذا تم العثور على صورة محلية.

--quiet, -q

قم بكتم إخراج المعلومات عند سحب الصور

--rdt-class=intel-rdt-class-of-service

يقوم Rdt-class بتعيين فئة الخدمة (CLOS أو COS) لتشغيل الحاوية فيها. بناءً على ميزة تقنية تخصيص ذاكرة التخزين المؤقت (CAT) التي تعد جزءًا من مجموعة ميزات تقنية مدير موارد Intel (RDT)، ستعمل جميع عمليات الحاوية ضمن COS المعدة مسبقًا، والتي تمثل جزءًا من ذاكرة التخزين المؤقت. يجب إنشاء COS وتكوينه باستخدام نظام ملفات وهمي (عادةً ما يتم تحميله في /sys/fs/resctrl) الذي توفره برامج تشغيل نواة resctrl. تعيين الحاوية إلى COS يتطلب امتيازات الجذر وبالتالي لا يعمل في بيئة بدون جذر. حاليًا، الميزة مدعومة فقط باستخدام runc كوقت تشغيل. راجع ⟨https://docs.kernel.org/arch/x86/resctrl.html⟩ لمزيد من التفاصيل حول إنشاء COS قبل أن يتم تعيين الحاوية إليها.

--read-only

قم بتحميل نظام ملفات الجذر للحاوية للقراءة فقط.

افتراضيًا، تكون أنظمة ملفات الجذر للحاوية قابلة للكتابة، مما يسمح للعمليات بكتابة الملفات في أي مكان. بتحديد العلم --read-only، يتم تحميل نظام ملفات الجذر للحاويات للقراءة فقط مما يمنع أي عمليات كتابة.

--read-only-tmpfs

عند تشغيل حاويات --read-only، قم بتحميل tmpfs للقراءة والكتابة في /dev و /dev/shm و /run و /tmp و /var/tmp. الافتراضي هو true.

--read-only --read-only-tmpfs / /run, /tmp, /var/tmp
true true r/o r/w
true false r/o r/o
false false r/w r/w
false true r/w r/w

عندما يكون --read-only=true و --read-only-tmpfs=true يتم تحميل tmpfs إضافية في الأدلة /tmp و /run و /var/tmp.

عندما يكون --read-only=true و --read-only-tmpfs=false يتم تمييز /dev و /dev/shm كـ Read/Only ولا يتم تحميل tmpfs في /tmp و /run و /var/tmp. يتم عرض الأدلة من الصورة الأساسية، مما يعني أنها للقراءة فقط بشكل افتراضي. هذا يجعل الحاوية للقراءة فقط تماما. لا توجد أدلة قابلة للكتابة داخل الحاوية. في هذا الوضع، يجب إضافة الأدلة القابلة للكتابة عبر وحدات تخزين أو تحميلات خارجية.

افتراضيًا، عندما يكون --read-only=false، فإن /dev و /dev/shm هما للقراءة/الكتابة، و /tmp و /run و /var/tmp هي أدلة قابلة للكتابة من صورة الحاوية.

--replace

إذا كانت هناك حاوية أخرى بنفس الاسم موجودة بالفعل، فاستبدلها وأزلها. الافتراضي هو false.

--requires=container

حدد متطلبًا واحدًا أو أكثر. المتطلب هو حاوية تابعة يتم بدؤها قبل هذه الحاوية. يمكن تحديد الحاويات بالاسم أو المعرف، مع فصل الحاويات المتعددة بفواصل.

--restart=policy

سياسة إعادة التشغيل التي يجب اتباعها عند خروج الحاويات. لا تسري سياسة إعادة التشغيل إذا تم إيقاف حاوية عبر أوامر podman kill أو podman stop.

القيم الصالحة لـ policy هي:

  • no: لا تعيد تشغيل الحاويات عند الخروج
  • never: مرادف لـ no؛ لا تعيد تشغيل الحاويات عند الخروج
  • on-failure[:max_retries]: أعد تشغيل الحاويات عند خروجها برمز خروج غير صفري، مع المحاولة إلى أجل غير مسمى أو حتى الوصول إلى عدد max_retries الاختياري
  • always: أعد تشغيل الحاويات عند خروجها، بغض النظر عن الحالة، مع المحاولة إلى أجل غير مسمى
  • unless-stopped: مطابق لـ always

توفر Podman ملف وحدة systemd، podman-restart.service، الذي يعيد تشغيل الحاويات بعد إعادة تشغيل النظام.

عند تشغيل الحاويات في خدمات systemd، استخدم وظيفة إعادة التشغيل التي يوفرها systemd. بمعنى آخر، لا تستخدم هذا الخيار في وحدة حاوية، بدلاً من ذلك قم بتعيين توجيه Restart= في قسم [Service]. راجع podman-systemd.unit(5) و systemd.service(5).

--retry=attempts

عدد المرات لمحاولة سحب أو دفع الصور بين السجل والتخزين المحلي في حالة الفشل. الافتراضي هو 3.

--retry-delay=duration

مدة التأخير بين محاولات إعادة المحاولة عند سحب أو دفع الصور بين السجل والتخزين المحلي في حالة الفشل. يبدأ الافتراضي بثانيتين ثم يتراجع أسيًا. يتم استخدام التأخير عند تعيين هذه القيمة، ولا يحدث تراجع أسي.

--rm

قم بإزالة الحاوية وأي وحدة تخزين مجهولة غير مسماة مرتبطة بالحاوية تلقائيًا عند خروجها. الافتراضي هو false.

--rootfs

إذا تم تحديده، فإن الوسيط الأول يشير إلى حاوية مفككة في نظام الملفات.

هذا مفيد لتشغيل حاوية دون الحاجة إلى أي إدارة للصور، ويفترض أن نظام ملفات الجذر للحاوية تتم إدارته خارجيًا.

تحميلات Overlay Rootfs

العلامة :O تخبر Podman بتحميل الدليل من مسار rootfs كتخزين باستخدام نظام الملفات overlay. يمكن لعمليات الحاوية تعديل المحتوى داخل نقطة التحميل التي يتم تخزينها في تخزين الحاوية في دليل منفصل. بمصطلحات overlay، الدليل المصدر هو السفلي، ودليل تخزين الحاوية هو العلوي. يتم تدمير التعديلات على نقطة التحميل عند انتهاء تنفيذ الحاوية، على غرار إلغاء تحميل نقطة تحميل tmpfs.

ملاحظة: على أنظمة SELinux، يحتاج rootfs إلى التسمية الصحيحة، والتي هي افتراضيًا unconfined_u:object_r:container_file_t:s0.

idmap

إذا تم تحديد idmap، فقم بإنشاء تحميل idmapped إلى مساحة اسم المستخدم المستهدفة في الحاوية. يدعم خيار idmap تعيينًا مخصصًا يمكن أن يختلف عن مساحة اسم المستخدم المستخدمة بواسطة الحاوية. يمكن تحديد التعيين بعد خيار idmap مثل: idmap=uids=0-1-10#10-11-10;gids=0-100-10. لكل ثلاثي، القيمة الأولى هي بداية معرفات نظام الملفات الأساسية التي يتم تعيينها إلى القيمة الثانية على المضيف. طول هذا التعيين معطى في القيمة الثالثة. يتم فصل النطاقات المتعددة بواسطة #.

--sdnotify=container | conmon | healthy | ignore

الافتراضي هو container، مما يعني السماح لوقت تشغيل OCI بتمرير المقبس إلى الحاوية لتلقي إشعار الاستعداد. Podman يقوم بتعيين MAINPID إلى conmon's pid. الخيار conmon يعين MAINPID إلى conmon's pid، ويقوم بإرسال READY عندما تبدأ الحاوية. لا يتم تمرير المقبس أبدًا إلى وقت التشغيل أو الحاوية. الخيار healthy يعين MAINPID إلى conmon's pid، ويقوم بإرسال READY عندما تصبح الحاوية صحية؛ يتطلب تعيين فحص صحة. لا يتم تمرير المقبس أبدًا إلى وقت التشغيل أو الحاوية. الخيار ignore يزيل NOTIFY_SOCKET من البيئة لنفسه وللعمليات التابعة، في حالة أن عملية أخرى فوق Podman تستخدم NOTIF

Y_SOCKET ولا يستخدم Podman هذا.

--secret=secret[,opt=opt ...]

منح الحاوية حق الوصول إلى سر. يمكن تحديده عدة مرات.

السر هو كتلة من البيانات الحساسة التي تحتاجها الحاوية في وقت التشغيل ولكنها غير مخزنة في الصورة أو في نظام التحكم في الإصدار، مثل أسماء المستخدمين وكلمات المرور، وشهادات ومفاتيح TLS، ومفاتيح SSH أو سلاسل أخرى مهمة عامة أو محتوى ثنائي (حتى 512 كيلو بايت).

عندما يتم تحديد الأسرار من النوع mount، يتم نسخ الأسرار وتثبيتها في الحاوية عند إنشاء حاوية. عندما يتم تحديد الأسرار من النوع env، يتم تعيين السر كمتغير بيئة داخل الحاوية. يتم كتابة الأسرار في الحاوية في وقت إنشاء الحاوية، ويؤثر تعديل السر باستخدام أوامر podman secret بعد إنشاء الحاوية على السر داخل الحاوية.

يتم إدارة الأسرار وتخزينها باستخدام أمر podman secret.

خيارات السر

  • type=mount|env : كيف يتم كشف السر للحاوية.
    mount يقوم بتثبيت السر في الحاوية كملف.
    env يكشف السر كمتغير بيئة.
    الافتراضي هو mount.
  • target=target : هدف السر.
    بالنسبة للأسرار المثبتة، هذا هو المسار إلى السر داخل الحاوية.
    إذا تم توفير مسار كامل، فسيتم تثبيت السر في هذا الموقع.
    بخلاف ذلك، يتم تثبيت السر في
    /run/secrets/target للحاويات Linux أو
    /var/run/secrets/target لحاويات FreeBSD.
    إذا لم يتم تعيين الهدف، فسيتم تثبيت السر افتراضيًا في /run/secrets/secretname.
    بالنسبة لأسرار البيئة، هذا هو مفتاح متغير البيئة. الافتراضي هو secretname.
  • uid=0 : UID للسر. الافتراضي هو 0. نوع سر التركيب فقط.
  • gid=0 : GID للسر. الافتراضي هو 0. نوع سر التركيب فقط.
  • mode=0 : وضع السر. الافتراضي هو 0444. نوع سر التركيب فقط.

أمثلة

التثبيت في /my/location/mysecret مع UID 1:

--secret mysecret,target=/my/location/mysecret,uid=1

التثبيت في /run/secrets/customtarget مع وضع 0777:

--secret mysecret,target=customtarget,mode=0777

إنشاء متغير بيئة سر يسمى ENVSEC:

--secret mysecret,type=env,target=ENVSEC

خيارات الأمان

  • apparmor=unconfined : إيقاف تقييد AppArmor للحاوية
  • apparmor=alternate-profile : تعيين ملف تعريف تقييد AppArmor للحاوية
  • label=user:USER: تعيين مستخدم التسمية لعمليات الحاوية
  • label=role:ROLE: تعيين دور التسمية لعمليات الحاوية
  • label=type:TYPE: تعيين نوع عملية التسمية لعمليات الحاوية
  • label=level:LEVEL: تعيين مستوى التسمية لعمليات الحاوية
  • label=filetype:TYPE: تعيين نوع ملف التسمية لملفات الحاوية
  • label=disable: إيقاف فصل التسمية للحاوية

ملاحظة: يمكن تعطيل التسميات لجميع الحاويات عن طريق تعيين label=false في ملف containers.conf (/etc/containers/containers.conf أو $HOME/.config/containers/containers.conf).

  • label=nested: يسمح بتعديلات SELinux داخل الحاوية. يُسمح للحاويات بتعديل تسميات SELinux على الملفات والعمليات، طالما أن سياسة SELinux تسمح بذلك. بدون nested، ترى الحاويات أن SELinux معطل، حتى عند تمكينه على المضيف. يُمنع الحاويات من تعيين أي تسميات.
  • mask=/path/1:/path/2: المسارات المراد إخفاؤها مفصولة بنقطتين. لا يمكن الوصول إلى المسار المخفي داخل الحاوية.
  • no-new-privileges: تعطيل اكتساب عمليات الحاوية صلاحيات إضافية عبر استدعاء النظام execve(2) (مثل عبر بتات setuid أو setgid، أو عبر صلاحيات الملف). البرامج التي تعتمد على بتات setuid/setgid المعينة على ملفاتها التنفيذية لتغيير معرف المستخدم أو معرف المجموعة لم تعد قادرة على القيام بذلك، وأي صلاحيات ملف مضافة إلى الملف التنفيذي (مثل عبر setcap) لا تتم إضافتها إلى مجموعة الصلاحيات المسموح بها. لمزيد من التفاصيل، انظر: https://docs.kernel.org/userspace-api/no_new_privs.html.
  • seccomp=unconfined: إيقاف تقييد seccomp للحاوية.
  • seccomp=profile.json: ملف JSON لاستخدامه كمرشح seccomp. لاحظ أن التعليق التوضيحي io.podman.annotations.seccomp يتم تعيينه بالقيمة المحددة كما هو موضح في podman inspect.
  • proc-opts=OPTIONS : قائمة خيارات مفصولة بفواصل لاستخدامها مع تركيب /proc. مزيد من التفاصيل حول خيارات التركيب الممكنة موضحة في صفحة الدليل proc(5).
  • unmask=ALL أو /path/1:/path/2، أو المسارات الموسعة بواسطة shell (/proc/*): المسارات المراد إلغاء إخفائها مفصولة بنقطتين. إذا تم تعيينها إلى ALL، فإنها تلغي إخفاء جميع المسارات المخفية أو التي تم جعلها للقراءة فقط افتراضيًا. المسارات المخفية افتراضيًا هي /proc/acpi, /proc/kcore, /proc/keys, /proc/latency_stats, /proc/sched_debug, /proc/scsi, /proc/timer_list, /proc/timer_stats, /sys/firmware, and /sys/fs/selinux, /sys/devices/virtual/powercap. المسارات التي يتم جعلها للقراءة فقط افتراضيًا هي /proc/asound, /proc/bus, /proc/fs, /proc/irq, /proc/sys, /proc/sysrq-trigger, /sys/fs/cgroup.

ملاحظة: يمكن تعطيل التسميات لجميع الحاويات عن طريق تعيين label=false في ملف containers.conf(5).

--shm-size=number[unit]

حجم /dev/shm. يمكن أن تكون الوحدة b (بايت)، k (كيلوبايت)، m (ميجابايت)، أو g (جيجابايت). إذا تم حذف الوحدة، فإن النظام يستخدم البايت. إذا تم حذف الحجم، فإن الافتراضي هو 64m. عندما يكون size هو 0، لا يوجد حد لكمية الذاكرة المستخدمة للاتصال بين العمليات (IPC) بواسطة الحاوية. هذا الخيار يتعارض مع --ipc=host.

--shm-size-systemd=number[unit]

حجم تركيبات tmpfs الخاصة بـ systemd مثل /run، /run/lock، /var/log/journal و /tmp. يمكن أن تكون الوحدة b (بايت)، k (كيلوبايت)، m (ميجابايت)، أو g (جيجابايت). إذا تم حذف الوحدة، فإن النظام يستخدم البايت. إذا تم حذف الحجم، فإن الافتراضي هو 64m. عندما يكون size هو 0، يقتصر الاستخدام على 50٪ من ذاكرة المضيف المتاحة.

--stop-signal=signal

إشارة لإيقاف حاوية. الافتراضي هو SIGTERM.

--stop-timeout=seconds

مهلة لإيقاف حاوية. الافتراضي هو 10. تستخدم الاتصالات عن بعد ملف containers.conf المحلي للقيم الافتراضية.

--subgidname=name

تشغيل الحاوية في وضع systemd يسبب التغييرات التالية:

•

  • /run
  • /run/lock
  • /tmp
  • /sys/fs/cgroup/systemd (على نظام cgroup v1)
  • /var/lib/journal
  • يقوم Podman بتعيين إشارة الإيقاف الافتراضية إلى SIGRTMIN+3.

هذا يسمح لـ systemd بالعمل في حاوية مقيدة دون أي تعديلات.

--uidmap=[flags]container_uid:from_uid[:amount]

تشغيل الحاوية في مساحة مستخدم جديدة باستخدام تعيين UID المقدم. يتعارض هذا الخيار مع خياري --userns و --subuidname. يوفر هذا الخيار طريقة لتعيين معرفات المستخدمين المضيفين (UIDs) إلى معرفات المستخدمين في الحاوية (UIDs). يمكن تمريره عدة مرات لتعيين نطاقات مختلفة.

تتم مناقشة القيم الممكنة للـ flags الاختيارية بشكل أعمق في هذه الصفحة. القيمة amount اختيارية وتفترض أنها 1 إذا لم يتم تقديمها.

تعتمد القيمة from_uid على المستخدم الذي يقوم بتشغيل الأمر، سواء كان مستخدمًا له صلاحيات الجذر (rootful) أو مستخدمًا بدون صلاحيات الجذر (rootless).

  • مستخدم له صلاحيات الجذر (rootful): [flags]container_uid:host_uid[:amount]
  • مستخدم بدون صلاحيات الجذر (rootless): [flags]container_uid:intermediate_uid[:amount]

تعيينات المستخدمين ذوي الصلاحيات (Rootful mappings)

عند استدعاء podman create بواسطة مستخدم مميز، يعمل الخيار --uidmap كتعيين مباشر بين معرفات المستخدمين المضيفين ومعرفات المستخدمين في الحاوية.

معرف المستخدم المضيف -> معرف المستخدم في الحاوية

تحدد amount عدد معرفات المستخدمين المتتالية التي يتم تعيينها. إذا كانت amount على سبيل المثال 4، يكون التعيين كما يلي:

معرف المستخدم المضيف معرف المستخدم في الحاوية
from_uid container_uid
from_uid + 1 container_uid + 1
from_uid + 2 container_uid + 2
from_uid + 3 container_uid + 3

تعيينات المستخدمين بدون صلاحيات (Rootless mappings)

عند استدعاء podman create بواسطة مستخدم غير مميز (أي، تشغيل بدون صلاحيات الجذر)، يتم تفسير القيمة from_uid على أنها "معرف مستخدم وسيط" (intermediate UID). في حالة المستخدم بدون صلاحيات، لا يتم تعيين معرفات المستخدمين المضيفين مباشرة إلى معرفات المستخدمين في الحاوية. بدلاً من ذلك، يحدث التعيين عبر خطوتين:

معرف المستخدم المضيف -> معرف المستخدم الوسيط -> معرف المستخدم في الحاوية

يؤثر خيار --uidmap فقط على خطوة التعيين الثانية.

يتم اشتقاق خطوة التعيين الأولى من محتويات الملف /etc/subuid ومعرف المستخدم للمستخدم الذي يستدعي Podman.

خطوة التعيين الأولى:

معرف المستخدم المضيف معرف المستخدم الوسيط
معرف المستخدم لـ Podman 0
معرف المستخدم الفرعي الأول 1
معرف المستخدم الفرعي الثاني 2
معرف المستخدم الفرعي الثالث 3
معرف المستخدم الفرعي n n

لكي تتمكن من استخدام معرفات المستخدمين الوسيطة الأكبر من الصفر، يحتاج المستخدم إلى تكوين معرفات مستخدمين فرعية في /etc/subuid. انظر subuid(5).

خطوة التعيين الثانية يتم تكوينها باستخدام --uidmap.

إذا كانت amount على سبيل المثال 5، فإن خطوة التعيين الثانية تبدو كالتالي:

معرف المستخدم الوسيط معرف المستخدم في الحاوية
from_uid container_uid
from_uid + 1 container_uid + 1
from_uid + 2 container_uid + 2
from_uid + 3 container_uid + 3
from_uid + 4 container_uid + 4

عند التشغيل بدون صلاحيات الجذر، يستخدم Podman جميع النطاقات المكونة في ملف /etc/subuid.

يتم تعيين معرف المستخدم الحالي إلى UID=0 في مساحة المستخدمين بدون صلاحيات الجذر. يتم إضافة كل نطاق إضافي بالتتابع:

المضيف مساحة المستخدمين بدون صلاحيات الجذر الطول
$UID 0 1
1 $FIRST_RANGE_ID $FIRST_RANGE_LENGTH
1+$FIRST_RANGE_LENGTH $SECOND_RANGE_ID $SECOND_RANGE_LENGTH

الإشارة إلى معرف مضيف من مساحة الأصل

كمستخدم بدون صلاحيات الجذر، يتم تعيين معرف المضيف المحدد في --uidmap أو --gidmap من مساحة الوسيط التي ينشئها Podman. في بعض الأحيان يكون من المرغوب فيه الإشارة مباشرة إلى مساحة المضيف. يمكن القيام بذلك يدويًا عن طريق تشغيل podman unshare cat /proc/self/gid_map، والعثور على معرف المضيف المطلوب في العمود الثاني من الإخراج، والحصول على المعرف الوسيط المقابل من العمود الأول.

يمكن لـ Podman القيام بكل ذلك عن طريق إضافة الرمز @ قبل معرف المضيف في التعيين. على سبيل المثال، بتحديد --gidmap 100000:@2000:1، سيقوم Podman بالبحث عن المعرف الوسيط المقابل لمعرف المضيف 2000 وسيتم تعيين المعرف الوسيط الذي تم العثور عليه إلى معرف الحاوية 100000. يجب أن يكون معرف المضيف المحدد قد تم تخصيصه (وإلا فلن يتم تعيينه إلى مساحة الوسيط في المقام الأول).

إذا كان الطول أكبر من واحد، على سبيل المثال مع --gidmap 100000:@2000:2، سيقوم Podman بتعيين معرفات المضيف 2000 و 2001 إلى 100000 و 100001، على التوالي، بغض النظر عن كيفية تعريف تعيين الوسيط.

توسيع التعيينات السابقة

قد تكون بعض تعديلات التعيين معقدة. على سبيل المثال، يبدأ المستخدم بتعيين مثل --gidmap="0:0:65000"، والذي يحتاج إلى التغيير بحيث يتم تعيين معرف الأصل 1 إلى معرف الحاوية 100000 بدلاً من ذلك، مع ترك معرف الحاوية 1 غير معين. يصبح --gidmap المقابل --gidmap="0:0:1" --gidmap="2:2:65534" --gidmap="100000:1:1".

يمكن تبسيط هذا الترميز باستخدام العلم +، الذي يتولى مهمة تقسيم التعيينات السابقة وإزالة أي تعيينات متعارضة مع التعيين المحدد. يتم إعطاء العلم قبل معرف الحاوية كما يلي: --gidmap="0:0:65000" --gidmap="+100000:1:1"

العلم مثال الوصف
+ +100000:1:1 توسيع التعيين السابق

يؤدي هذا الترميز إلى فجوات في التعيين، لذا قد يكون من الملائم ملء هذه الفجوات لاحقًا: --gidmap="0:0:65000" --gidmap="+100000:1:1" --gidmap="1:65001:1"

حالة استخدام محددة لهذا العلم هي في سياق المستخدمين بدون صلاحيات الجذر. قد يحدد المستخدم بدون صلاحيات الجذر تعيينات باستخدام العلم + كما في --gidmap="+100000:1:1". سيقوم Podman بعد ذلك بـ "ملء الفجوات" بدءًا من الصفر بجميع معرفات المستخدمين الفرعية المتبقية. هذا مناسب عندما يريد المستخدم تعيين معرف وسيط محدد إلى معرف حاوية، مما يترك بقية معرفات المستخدمين الفرعية ليتم تعيينها بواسطة Podman حسب الرغبة.

تمرير واحد فقط من --uidmap أو --gidmap

عادةً، يتم تعيين معرفات المستخدم والمجموعة الفرعية بشكل متزامن، ولكل مستخدم، تتطابق معرفات المستخدم الفرعية مع معرفات المجموعة الفرعية. للتسهيل، إذا تم تقديم واحد فقط من --uidmap أو --gidmap، يفترض Podman أن التعيين يشير إلى كل من معرفات المستخدمين (UIDs) ومعرفات المجموعات (GIDs) ويطبق التعيين المحدد على كليهما. إذا كان هناك حاجة لتغيير قيمة واحدة فقط من الاثنين، فيجب أن تتضمن التعيينات الأعلام u أو g لتحديد أنها تنطبق فقط على معرفات المستخدمين (UIDs) أو معرفات المجموعات (GIDs) ولا ينبغي نسخها.

العلم مثال الوصف
u u20000:2000:1 التعيين ينطبق فقط على معرفات المستخدمين
g g10000:1000:1 التعيين ينطبق فقط على معرفات المجموعات

على سبيل المثال، بالنظر إلى الأمر

podman create --gidmap "0:0:1000" --gidmap "g2000:2000:1"

نظرًا لعدم تقديم --uidmap، يتم نسخ --gidmap إلى --uidmap، مما ينتج عنه أمر مكافئ لـ

podman create --gidmap "0:0:1000" --gidmap "2000:2000:1" --uidmap "0:0:1000"

استخدم --gidmap "g2000:2000:1" العلم g وبالتالي لم يتم نسخه إلى --uidmap.

تعيين معرفات مجموعات المضيف الإضافية بدون صلاحيات الجذر

قد يرغب مستخدم بدون صلاحيات الجذر في تعيين مجموعة مضيف محددة تم

subordinated within /etc/subgid without specifying the rest of the mapping.

This can be done with --gidmap "+gcontainer_gid:@host_gid"

Where:

  • The host GID is given through the @ symbol
  • The mapping of this GID is not copied over to --usermap thanks to the g flag.
  • The rest of the container IDs will be mapped starting from 0 to n, with all the remaining subordinated GIDs, thanks to the + flag.

For instance, if a user belongs to the group 2000 and that group is subordinated to that user (with usermod --add-subgids 2000-2000 $USER), the user can map the group into the container with: --gidmap=+g100000:@2000.

If this mapping is combined with the option, --group-add=keep-groups, the process in the container will belong to group 100000, and files belonging to group 2000 in the host will appear as being owned by group 100000 inside the container.

podman run --group-add=keep-groups --gidmap="+g100000:@2000" ...

No subordinate UIDs

Even if a user does not have any subordinate UIDs in /etc/subuid, --uidmap can be used to map the normal UID of the user to a container UID by running podman create --uidmap $container_uid:0:1 --user $container_uid ....

Pods

The --uidmap option cannot be called in conjunction with the --pod option as a uidmap cannot be set on the container level when in a pod.

--ulimit=option

Ulimit options. Sets the ulimits values inside of the container.

--ulimit with a soft and hard limit in the format =[:]. For example:

$ podman run --ulimit nofile=1024:1024 --rm ubi9 ulimit -n 1024

Set -1 for the soft or hard limit to set the limit to the maximum limit of the current process. In rootful mode this is often unlimited.

If nofile and nproc are unset, a default value of 1048576 will be used, unless overridden in containers.conf(5). However, if the default value exceeds the hard limit for the current rootless user, the current hard limit will be applied instead.

Use host to copy the current configuration from the host.

Don't use nproc with the ulimit flag as Linux uses nproc to set the maximum number of processes available to a user, not to a container.

Use the --pids-limit option to modify the cgroup control to limit the number of processes within a container.

--umask=umask

Set the umask inside the container. Defaults to 0022. Remote connections use the local containers.conf for defaults.

--unsetenv=env

Unset default environment variables for the container. Default environment variables include variables provided natively by Podman, environment variables configured by the image, and environment variables from containers.conf.

--unsetenv-all

Unset all default environment variables for the container. Default environment variables include variables provided natively by Podman, environment variables configured by the image, and environment variables from containers.conf.

--user, -u=user[:group]

Sets the username or UID used and, optionally, the groupname or GID for the specified command. Both user and group may be symbolic or numeric.

Without this argument, the command runs as the user specified in the container image. Unless overridden by a USER command in the Containerfile or by a value passed to this option, this user generally defaults to root.

When a user namespace is not in use, the UID and GID used within the container and on the host match. When user namespaces are in use, however, the UID and GID in the container may correspond to another UID and GID on the host. In rootless containers, for example, a user namespace is always used, and root in the container by default corresponds to the UID and GID of the user invoking Podman.

--userns=mode

Set the user namespace mode for the container.

If --userns is not set, the default value is determined as follows. - If --pod is set, --userns is ignored and the user namespace of the pod is used. - If the environment variable PODMAN_USERNS is set its value is used. - If userns is specified in containers.conf this value is used. - Otherwise, --userns=host is assumed.

--userns="" (i.e., an empty string) is an alias for --userns=host.

This option is incompatible with --gidmap, --uidmap, --subuidname and --subgidname.

Rootless user --userns=Key mappings:

Key Host User Container User
auto $UID nil (Host User UID is not mapped into container.)
host $UID 0 (Default User account mapped to root user in container.)
keep-id $UID $UID (Map user account to same UID within container.)
keep-id:uid=200,gid=210 $UID 200:210 (Map user account to specified UID, GID value within container.)
nomap $UID nil (Host User UID is not mapped into container.)

Valid mode values are:

auto[:OPTIONS,...]: automatically create a unique user namespace.

  • rootful mode: The --userns=auto flag requires that the user name containers be specified in the /etc/subuid and /etc/subgid files, with an unused range of subordinate user IDs that Podman containers are allowed to allocate. Example: containers:2147483647:2147483648.
  • rootless mode: The users range from the /etc/subuid and /etc/subgid files will be used. Note running a single container without using --userns=auto will use the entire range of UIDs and not allow further subdividing. See subuid(5).

Podman allocates unique ranges of UIDs and GIDs from the containers subordinate user IDs. The size of the ranges is based on the number of UIDs required in the image. The number of UIDs and GIDs can be overridden with the size option.

The option --userns=keep-id uses all the subuids and subgids of the user. The option --userns=nomap uses all the subuids and subgids of the user except the user's own ID. Using --userns=auto when starting new containers does not work as long as any containers exist that were started with --userns=nomap or --userns=keep-id without limiting the user namespace size.

Valid auto options:

  • gidmapping=CONTAINER_GID:HOST_GID:SIZE: to force a GID mapping to be present in the user namespace.
  • size=SIZE: to specify an explicit size for the automatic user namespace. e.g. --userns=auto:size=8192. If size is not specified, auto estimates a size for the user namespace.
  • uidmapping=CONTAINER_UID:HOST_UID:SIZE: to force a UID mapping to be present in the user namespace.

The host UID and GID in gidmapping and uidmapping can optionally be prefixed with the @ symbol. In this case, podman will look up the intermediate ID corresponding to host ID and it will map the found intermediate ID to the container id. For details see --uidmap.

container:id: join the user namespace of the specified container.

host or "" (empty string): run in the user namespace of the caller. The processes running in the container have the same privileges on the host as any other process launched by the calling user.

keep-id: creates a user namespace where the current user's UID:GID are mapped to the same values in the container. For containers created by root, the current mapping is created into a new user namespace.

In addition, the init process within the container will run under the current user's UID. This behavior overrides the image's USER instruction unless you explicitly set --user.

Valid keep-id options:

  • uid=UID: override the UID inside the container that is used to map the current user to.
  • gid=GID: override the GID inside the container that is used to map the current user to.
  • size=SIZE: override the size of the configured user namespace. It is useful to not saturate all the available IDs. Not supported when running as root.

nomap: creates a user namespace where the current rootless user's UID:GID are not mapped into the container. This option is not allowed for containers created by the root user.

ns:namespace: run the container in the given existing user namespace.

--uts=mode

Set the UTS namespace mode for the container. The following values are supported:

  • host: use the host's UTS namespace inside the container.
  • private: create a new namespace for the container (default).
  • ns:[path]: run the container in the given existing UTS namespace.

--userns="" (i.e., an empty string) is an alias for --userns=host.

Valid mode values are:

auto[:OPTIONS,...]: automatically create a unique user namespace.

  • rootful mode: The --userns=auto flag requires that the user name containers be specified in the /etc/subuid and /etc/subgid files, with an unused range of subordinate user IDs that Podman containers are allowed to allocate. Example: containers:2147483647:2147483648.
  • rootless mode: The users range from the /etc/subuid and /etc/subgid files will be used. Note running a single container without using --userns=auto will use the entire range of UIDs and not allow further subdividing. See subuid(5).

Podman allocates unique ranges of UIDs and GIDs from the containers subordinate user IDs. The size of the ranges is based on the number of UIDs required in the image. The number of UIDs and GIDs can be overridden with the size option.

The option --userns=keep-id uses all the subuids and subgids of the user. The option --userns=nomap uses all the subuids and subgids of the user except the user's own ID. Using --userns=auto when starting new containers does not work as long as any containers exist that were started with --userns=nomap or --userns=keep-id without limiting the user namespace size.

Valid auto options:

  • gidmapping=CONTAINER_GID:HOST_GID:SIZE: to force a GID mapping to be present in the user namespace.
  • size=SIZE: to specify an explicit size for the automatic user namespace. e.g. --userns=auto:size=8192. If size is not specified, auto estimates a size for the user namespace.
  • uidmapping=CONTAINER_UID:HOST_UID:SIZE: to force a UID mapping to be present in the user namespace.

The host UID and GID in gidmapping and uidmapping can optionally be prefixed with the @ symbol. In this case, podman will look up the intermediate ID corresponding to host ID and it will map the found intermediate ID to the container id. For details see --uidmap.

host or "" (empty string): run in the user namespace of the caller. The processes running in the container have the same privileges on the host as any other process launched by the calling user.

keep-id: creates a user namespace where the current user's UID:GID are mapped to the same values in the container. For containers created by root, the current mapping is created into a new user namespace.

In addition, the init process within the container will run under the current user's UID. This behavior overrides the image's USER instruction unless you explicitly set --user.

Valid keep-id options:

  • uid=UID: override the UID inside the container that is used to map the current user to.
  • gid=GID: override the GID inside the container that is used to map the current user to.
  • size=SIZE: override the size of the configured user namespace. It is useful to not saturate all the available IDs. Not supported when running as root.

nomap: creates a user namespace where the current rootless user's UID:GID are not mapped into the container. This option is not allowed for containers created by the root user.

ns:namespace: run the container in the given existing user namespace.

NAME

podman-create - Create a new container

SYNOPSIS

podman create [OPTIONS] IMAGE [COMMAND] [ARG...]

podman container create [OPTIONS] IMAGE [COMMAND] [ARG...]

DESCRIPTION

Creates a new container from the given image, but does not start it. The container is created with the supplied arguments, but without any command-line, it runs in the foreground and prints its output. You can start, stop, and delete the container using the related commands.

You can create a container from a local image or from an image in a registry. If the image is not present locally, Podman pulls it from the configured registry.

Use podman ps -a to view all containers, including stopped ones. Use podman rm to remove a container.

Podman can run containers in rootless mode. To run rootless containers you must ensure that the shadow-utils package is installed on your system. The shadow-utils package must include the newuidmap and newgidmap executables.

In order for users to run rootless, there must be an entry for their username in /etc/subuid and /etc/subgid which lists the UIDs for their user namespace.

Rootless Podman works better if the fuse-overlayfs and slirp4netns packages are installed. The fuse-overlayfs package provides a userspace overlay storage driver, otherwise users need to use the vfs storage driver, which can be disk space expensive and less performant than other drivers.

To enable VPN on the container, slirp4netns or pasta needs to be specified; without either, containers need to be run with the --network=host flag.

Mounts

Podman supports several types of mounts. The most common are bind mounts and volumes. Bind mounts are created using the -v or --mount option and mount a file or directory on the host machine into a container. Volumes are created using the -v or --mount option and are managed by Podman. They are stored in a dedicated part of the host filesystem, managed by Podman.

The --mount option is the preferred syntax. It is more verbose but clearer. It supports the following options:

type
Specifies the type of mount. Possible values are bind, volume, tmpfs, npipe, and image.
src or source
The source of the mount. For bind mounts, it's the path on the host. For volumes, it's the name of the volume.
dst or destination
The path in the container where the mount is placed.
opts
A comma-separated list of options. Possible values include:
ro
Mount the volume read-only.
rw
Mount the volume read-write (default).
bind-propagation
Controls the propagation behavior of a bind mount. Possible values are rprivate, private, rshared, shared, rslave, slave.
bind-nonrecursive
Do not recursively mount the source directory.
copy-data
Copy data from the source to the destination directory if the destination directory is empty.
tmpfs-size
Maximum size of the tmpfs mount.
tmpfs-mode
Permissions of the tmpfs mount.

The -v option is a shorthand for the -v and --mount options. It supports the following syntax:

-v <host_path>:<container_path>[:<options>] (bind mount)

-v <volume_name>:<container_path>[:<options>] (volume)

The available options are ro and rw.

Idmap Mounts

If idmap is specified, create an idmapped mount to the target user namespace in the container. The idmap option supports a custom mapping that can be different than the user namespace used by the container. The mapping can be specified after the idmap option like: idmap=uids=0-1-10#10-11-10;gids=0-100-10. For each triplet, the first value is the start of the backing file system IDs that are mapped to the second value on the host. The length of this mapping is given in the third value. Multiple ranges are separated with #.

Use the --group-add keep-groups option to pass the user's supplementary group access into the container.

--volumes-from=CONTAINER[:OPTIONS]

Mount volumes from the specified container(s). Used to share volumes between containers. The options is a comma-separated list with the following available elements:

  • rw|ro
  • z

Mounts already mounted volumes from a source container onto another container. CONTAINER may be a name or ID. To share a volume, use the --volumes-from option when running the target container. Volumes can be shared even if the source container is not running.

By default, Podman mounts the volumes in the same mode (read-write or read-only) as it is mounted in the source container. This can be changed by adding a ro or rw option.

Labeling systems like SELinux require that proper labels are placed on volume content mounted into a container. Without a label, the security system might prevent the processes running inside the container from using the content. By default, Podman does not change the labels set by the OS.

To change a label in the container context, add z to the volume mount. This suffix tells Podman to relabel file objects on the shared volumes. The z option tells Podman that two entities share the volume content. As a result, Podman labels the content with a shared content label. Shared volume labels allow all containers to read/write content.

If the location of the volume from the source container overlaps with data residing on a target container, then the volume hides that data on the target.

--workdir, -w=dir

Working directory inside the container.

The default working directory for running binaries within a container is the root directory (/). The image developer can set a different default with the WORKDIR instruction. The operator can override the working directory by using the -w option.

Create a container using a local image:

$ podman create alpine ls

Create a container using a local image and annotate it:

$ podman create --annotation HELLO=WORLD alpine ls

Create a container using a local image, allocating a pseudo-TTY, keeping stdin open and name it myctr:

  podman create -t -i --name myctr alpine ls

Running a container in a new user namespace requires a mapping of the UIDs and GIDs from the host:

$ podman create --uidmap 0:30000:7000 --gidmap 0:30000:7000 fedora echo hello

Setting automatic user-namespace separated containers:

# podman create --userns=auto:size=65536 ubi8-init

Configure the timezone in a container:

$ podman create --tz=local alpine date
$ podman create --tz=Asia/Shanghai alpine date
$ podman create --tz=US/Eastern alpine date

Ensure the first container (container1) is running before the second container (container2) is started:

$ podman create --name container1 -t -i fedora bash
$ podman create --name container2 --requires container1 -t -i fedora bash
$ podman start --attach container2

Create a container which requires multiple containers:

$ podman create --name container1 -t -i fedora bash
$ podman create --name container2 -t -i fedora bash
$ podman create --name container3 --requires container1,container2 -t -i fedora bash
$ podman start --attach container3

Expose shared libraries inside of container as read-only using a glob:

$ podman create --mount type=glob,src=/usr/lib64/libnvidia\*,ro -i -t fedora /bin/bash

Create a container allowing supplemental groups to have access to the volume:

$ podman create -v /var/lib/design:/var/lib/design --group-add keep-groups ubi8

Configure execution domain for containers using the personality option:

$ podman create --name container1 --personality=LINUX32 fedora bash

Create a container with external rootfs mounted as an overlay:

$ podman create --name container1 --rootfs /path/to/rootfs:O bash

Create a container connected to two networks (called net1 and net2) with a static ip:

$ podman create --network net1:ip=10.89.1.5 --network net2:ip=10.89.10.10 alpine ip addr

ENVIRONMENT

Environment variables within containers can be set using multiple different options: This section describes the precedence.

Precedence order (later entries override earlier entries):

  • --env-host : Host environment of the process executing Podman is added.
  • --http-proxy: By default, several environment variables are passed in from the host, such as http_proxy and no_proxy. See --http-proxy for details.
  • Container image : Any environment variables specified in the container image.
  • --env-file : Any environment variables specified via env-files. If multiple files specified, then they override each other in order of entry.
  • --env : Any environment variables specified overrides previous settings.

Create containers and set the environment ending with a *. The trailing * glob functionality is only active when no value is specified:

$ export ENV1=a
$ podman create --name ctr1 --env 'ENV*' alpine env
$ podman start --attach ctr1 | grep ENV
ENV1=a
$ podman create --name ctr2 --env 'ENV*=b' alpine env
$ podman start --attach ctr2 | grep ENV
ENV*=b

CONMON

When Podman starts a container it actually executes the conmon program, which then executes the OCI Runtime. Conmon is the container monitor. It is a small program whose job is to watch the primary process of the container, and if the container dies, save the exit code. It also holds open the tty of the container, so that it can be attached to later. This is what allows Podman to run in detached mode (backgrounded), so Podman can exit but conmon continues to run. Each container has their own instance of conmon. Conmon waits for the container to exit, gathers and saves the exit code, and then launches a Podman process to complete the container cleanup, by shutting down the network and storage. For more information about conmon, see the conmon(8) man page.
