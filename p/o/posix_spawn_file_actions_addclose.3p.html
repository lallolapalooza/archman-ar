POSIX_SPAWN_FILE_ACTIONS_ADDCLOSE(3P) دليل مبرمج POSIX POSIX_SPAWN_FILE_ACTIONS_ADDCLOSE(3P)

PROLOG

هذه الصفحة الدليلية جزء من دليل مبرمج POSIX. قد يختلف تطبيق Linux لهذه الواجهة (راجع صفحة دليل Linux المقابلة لتفاصيل سلوك Linux)، أو قد لا تكون الواجهة مطبقة على Linux.

NAME

posix_spawn_file_actions_addclose، posix_spawn_file_actions_addopen - إضافة إجراء إغلاق أو فتح إلى كائن إجراءات ملفات الإنشاء (ADVANCED REALTIME)

SYNOPSIS

#include <spawn.h>
int posix_spawn_file_actions_addclose(posix_spawn_file_actions_t
    *file_actions, int fildes);
int posix_spawn_file_actions_addopen(posix_spawn_file_actions_t
    *restrict file_actions, int fildes,
    const char *restrict path, int oflag, mode_t mode);

DESCRIPTION

تضيف هذه الوظائف أو تحذف إجراء إغلاق أو فتح إلى كائن إجراءات ملفات الإنشاء.

كائن إجراءات ملفات الإنشاء هو من النوع posix_spawn_file_actions_t (معرف في <spawn.h>) ويستخدم لتحديد سلسلة من الإجراءات التي سيتم تنفيذها بواسطة عملية posix_spawn() أو posix_spawnp() للوصول إلى مجموعة واصفات الملفات المفتوحة للعملية الفرعية نظرًا لمجموعة واصفات الملفات المفتوحة للعملية الأصل. لا يحدد POSIX.1-2008 عوامل مقارنة أو تعيين للنوع posix_spawn_file_actions_t.

كائن إجراءات ملفات الإنشاء، عند تمريره إلى posix_spawn() أو posix_spawnp()، سيحدد كيفية تحويل مجموعة واصفات الملفات المفتوحة في العملية الحالية إلى مجموعة من واصفات الملفات المفتوحة المحتملة للعملية المنشأة. سيتم هذا التحويل كما لو تم تنفيذ سلسلة الإجراءات المحددة مرة واحدة بالضبط، في سياق العملية المنشأة (قبل تنفيذ صورة العملية الجديدة)، بالترتيب الذي تمت به إضافة الإجراءات إلى الكائن؛ بالإضافة إلى ذلك، عند تنفيذ صورة العملية الجديدة، سيتم إغلاق أي واصف ملف (من هذه المجموعة الجديدة) لديه علامة FD_CLOEXEC مضبوطة (انظر posix_spawn()).

تضيف وظيفة posix_spawn_file_actions_addclose() إجراء إغلاق إلى الكائن المشار إليه بواسطة file_actions والذي سيؤدي إلى إغلاق واصف الملف fildes (كما لو تم استدعاء close(fildes)) عند إنشاء عملية جديدة باستخدام كائن إجراءات الملف هذا.

تضيف وظيفة posix_spawn_file_actions_addopen() إجراء فتح إلى الكائن المشار إليه بواسطة file_actions والذي سيؤدي إلى فتح الملف المسمى بواسطة path (كما لو تم استدعاء open(path, oflag, mode)، وتم تغيير واصف الملف المُعاد، إذا لم يكن fildes، إلى fildes) عند إنشاء عملية جديدة باستخدام كائن إجراءات الملف هذا. إذا كان fildes بالفعل واصف ملف مفتوح، فسيتم إغلاقه قبل فتح الملف الجديد.

ستقوم وظيفة posix_spawn_file_actions_addopen() بنسخ السلسلة الموصوفة بواسطة path.

RETURN VALUE

عند اكتمال هذه الوظائف بنجاح، ستعيد صفرًا؛ وإلا، سيتم إرجاع رقم خطأ للإشارة إلى الخطأ.

ERRORS

ستفشل وظيفة posix_spawn_file_actions_addopen() إذا:

EBADF
القيمة المحددة بواسطة fildes سالبة أو أكبر من أو تساوي {OPEN_MAX}.

ستفشل وظيفة posix_spawn_file_actions_addclose() إذا:

EBADF
القيمة المحددة بواسطة fildes سالبة.

قد تفشل هذه الوظائف إذا:

EINVAL
القيمة المحددة بواسطة file_actions غير صالحة.
ENOMEM
لا توجد ذاكرة كافية للإضافة إلى كائن إجراءات ملفات الإنشاء.

لا يعتبر خطأ أن وسيط fildes الذي تم تمريره إلى هذه الوظائف يحدد واصف ملف لا يمكن تنفيذ العملية المحددة له في وقت الاستدعاء. سيتم اكتشاف أي خطأ من هذا القبيل عند استخدام كائن إجراءات الملف المرتبط لاحقًا أثناء عملية posix_spawn() أو posix_spawnp().

الأقسام التالية إعلامية.

EXAMPLES

لا شيء.

APPLICATION USAGE

هذه الوظائف جزء من خيار الإنشاء وقد لا تكون متوفرة في جميع التطبيقات.

قد تستخدم التطبيقات واصفات ملفات يجب أن تُورث إلى العمليات الفرعية لتبقى العملية الفرعية متوافقة، مثل أغراض كتالوج الرسائل أو التتبع. لذلك، فإن التطبيق الذي يستدعي posix_spawn_file_actions_addclose() باستخدام عدد صحيح عشوائي يخاطر بسلوك غير متوافق، ولا يمكن استخدام هذه الوظيفة بشكل محمول إلا لإغلاق قيم واصفات الملفات التي حصل عليها التطبيق من خلال إجراءات صريحة، أو للواصفات الثلاثة للملفات القياسية. لتجنب حالة سباق تسريب واصف ملف غير مقصود إلى عملية فرعية، يجب على التطبيق النظر في فتح جميع واصفات الملفات مع تعيين علامة FD_CLOEXEC ما لم يكن واصف الملف مقصودًا توريثه عبر exec.

RATIONALE

قد يتم تهيئة كائن إجراءات ملفات الإنشاء ليحتوي على تسلسل مرتب من عمليات close() و dup2() و open() لاستخدامها بواسطة posix_spawn() أو posix_spawnp() للوصول إلى مجموعة واصفات الملفات المفتوحة التي ترثها العملية المنشأة من مجموعة واصفات الملفات المفتوحة في العملية الأصل في وقت استدعاء posix_spawn() أو posix_spawnp(). لقد اقتُرح أن عمليتي close() و dup2() وحدهما كافيتان لإعادة ترتيب واصفات الملفات، وأن الملفات التي تحتاج إلى فتح لاستخدامها من قبل العملية المنشأة يمكن معالجتها إما عن طريق فتحها بواسطة العملية المستدعية قبل استدعاء posix_spawn() أو posix_spawnp() (وإغلاقها بعد ذلك)، أو عن طريق تمرير أسماء المسارات إلى العملية المنشأة (في argv) حتى تتمكن من فتحها بنفسها. يوصي مطورو المعيار بأن تستخدم التطبيقات إحدى هاتين الطريقتين عندما يكون ذلك عمليًا، نظرًا لأن حالة الخطأ التفصيلية لعملية فتح فاشلة متاحة دائمًا للتطبيق بهذه الطريقة. ومع ذلك، يشعر مطورو المعيار أن السماح لكائن إجراءات ملفات الإنشاء بتحديد عمليات الفتح لا يزال مناسبًا للأسباب التالية:

1.
إنه متوافق مع وظائف POSIX.5 (Ada) المكافئة.
2.
إنه يدعم نموذج إعادة توجيه الإدخال/الإخراج الذي تستخدمه عادةً برامج POSIX المصممة ليتم استدعاؤها من shell. عندما تكون هذه البرامج هي العملية الفرعية، فقد لا تكون مصممة لفتح الملفات بنفسها.
3.
إنه يسمح بفتح ملفات قد تفشل أو تنتهك حقوق ملكية/وصول الملف إذا تم تنفيذها بواسطة العملية الأصل.

فيما يتعلق بالنقطة 2 أعلاه، لاحظ أن إجراء فتح الإنشاء يوفر لـ posix_spawn() و posix_spawnp() نفس القدرة التي توفرها عوامل إعادة توجيه shell لـ system()، فقط بدون التنفيذ الفاصل لـ shell؛ على سبيل المثال:

system ("myprog <file1 3<file2");

فيما يتعلق بالنقطة 3 أعلاه، لاحظ أنه إذا كانت العملية المستدعية بحاجة إلى فتح ملف واحد أو أكثر للوصول بواسطة العملية المنشأة، ولكن ليس لديها واصفات ملفات كافية، فإن إجراء الفتح ضروري للسماح لـ open() بالحدوث في سياق العملية الفرعية بعد إغلاق واصفات الملفات الأخرى (التي يجب أن تظل مفتوحة في العملية الأصل).

بالإضافة إلى ذلك، إذا تم تنفيذ عملية أصل من ملف له بت وضع "set-user-id" مضاء وتم تعيين علامة POSIX_SPAWN_RESETIDS في سمات الإنشاء، فإن ملفًا تم إنشاؤه داخل العملية الأصل سيحصل (ربما بشكل غير صحيح) على معرف المستخدم الفعال للعملية الأصل كمالك له، في حين أن ملفًا تم إنشاؤه عبر إجراء open() أثناء posix_spawn() أو posix_spawnp() سيحصل على

posix_spawn_file_actions_addclose(3p) — Arch Linux

NAME

posix_spawn_file_actions_addclose - add a close operation to a file actions structure

SYNOPSIS

#include <spawn.h>

 int posix_spawn_file_actions_addclose(
     posix_spawn_file_actions_t *file_actions, int fildes
 );

DESCRIPTION

The posix_spawn_file_actions_addclose() function shall add a close operation to the object referred to by file_actions. This operation, when performed, shall close the file descriptor specified by fildes.

The file_actions argument is the object created by a prior call to posix_spawn_file_actions_init().

The fildes argument is a valid file descriptor.

The effect of calling this function multiple times with the same file_actions and different fildes arguments is cumulative.

If posix_spawn() or posix_spawnp() is called with a file_actions object that has had a close operation added for file descriptor fildes, then after the posix_spawn() or posix_spawnp() call returns, the file descriptor fildes shall be closed in the new process.

RETURN VALUE

Upon successful completion, these functions shall return 0. Otherwise, they shall return an error number.

ERRORS

The posix_spawn_file_actions_addclose() function shall fail if:

[EINVAL]
The value specified by file_actions is not a valid object created by posix_spawn_file_actions_init().
The fildes argument is negative or is greater than or equal to the maximum number of open file descriptors supported by the system.

[ENOMEM]
Insufficient memory is available to add the close operation to the file_actions object.

On implementations where {OPEN_MAX} does not change, it is recommended that posix_spawn_file_actions_addclose() should return [EBADF] if fildes is greater than or equal to {OPEN_MAX}.

EXAMPLES

None.

APPLICATION USAGE

This function is intended to be used by applications that call posix_spawn() or posix_spawnp(). It allows the application to explicitly close file descriptors that would otherwise be inherited by the new process.

A common use case is to close file descriptors associated with unused or sensitive resources before spawning a new process, to prevent the child process from accessing them. For example, closing standard input, output, or error file descriptors if they are not needed, or closing file descriptors to temporary files or network sockets.

RATIONALE

The posix_spawn() and posix_spawnp() functions provide an alternative to the fork-exec sequence for creating new processes. They allow for more fine-grained control over the child process's environment, including its file descriptor table.

When a new process is created using posix_spawn(), by default, it inherits a copy of the parent's file descriptor table. This can be problematic if the parent process has many file descriptors open that are not relevant or should not be accessible to the child. For example, the parent might have sensitive data in an open file, or might have opened too many files, exceeding the child's limits.

The file actions interface, defined by posix_spawn_file_actions_init(), posix_spawn_file_actions_addopen(), posix_spawn_file_actions_addclose(), posix_spawn_file_actions_adddup2(), and posix_spawn_file_actions_destroy(), provides a mechanism to control the state of the child's file descriptor table before the new process image is executed.

Specifically, posix_spawn_file_actions_addclose() allows the application to specify which file descriptors should be closed in the child process. This is crucial for security and resource management. For instance, if a parent process has opened a log file or a network connection that the child should not use, it can add a close action for the corresponding file descriptor.

The original POSIX.1-2001 standard and its predecessors did not specify the exact behavior regarding the user and group IDs of the spawned process. The standard specified that the child process would run with the real user ID and real group ID of the calling process unless explicitly changed. However, this could lead to security issues if the calling process had elevated privileges (e.g., root) but the spawned process should run with less privilege. The POSIX.1-2008 standard introduced the posix_spawnattr_set*id functions to allow explicit control over the effective, real, and saved set-user-ID and set-group-ID. This provides a more secure and flexible way to manage process execution. Without these, the parent process's real ID could be used as its effective ID, potentially giving the child process unintended privileges. This could mean that a file opened by the parent process may successfully open a file to which the real user should not have access, or fail to open a file to which the real user should have access, depending on the privileges of the real user.

The standard developers had originally proposed using an array which specified the mapping of child file descriptors back to those of the parent. It was pointed out by the ballot group that it is not possible to reshuffle file descriptors arbitrarily in a library implementation of posix_spawn() or posix_spawnp() without provision for one or more spare file descriptor entries (which simply may not be available). Such an array requires that an implementation develop a complex strategy to achieve the desired mapping without inadvertently closing the wrong file descriptor at the wrong time.

It was noted by a member of the Ada Language Bindings working group that the approved Ada Language Start_Process family of POSIX process primitives use a caller-specified set of file actions to alter the normal fork()/ exec semantics for inheritance of file descriptors in a very flexible way, yet no such problems exist because the burden of determining how to achieve the final file descriptor mapping is completely on the application. Furthermore, although the file actions interface appears frightening at first glance, it is actually quite simple to implement in either a library or the kernel.

The posix_spawn_file_actions_addclose() function is not required to check whether the file descriptor is less than {OPEN_MAX} because on some implementations {OPEN_MAX} reflects the RLIMIT_NOFILE soft limit and therefore calling setrlimit() to reduce this limit can result in an {OPEN_MAX} value less than or equal to an already open file descriptor. Applications need to be able to close such file descriptors on spawn. On implementations where {OPEN_MAX} does not change, it is recommended that posix_spawn_file_actions_addclose() should return [EBADF] if fildes is greater than or equal to {OPEN_MAX}.
