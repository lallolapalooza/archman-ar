NAME

\n

podman-machine-init - Initialize a new virtual machine

\n
\n
\n

SYNOPSIS

\n

podman machine init [options] [name]

\n
\n
\n

DESCRIPTION

\n

Initialize a new virtual machine for Podman.

\n

The default machine name is podman-machine-default. If a\n machine name is not specified as an argument, then the new machine will be\n named podman-machine-default.

\n

Rootless only.

\n

Podman on MacOS and Windows requires a virtual machine. This is\n because containers are Linux - containers do not run on any other OS because\n containers' core functionality are tied to the Linux kernel. Podman machine\n must be used to manage MacOS and Windows machines, but can be optionally\n used on Linux.

\n

podman machine init initializes a new Linux virtual machine\n where containers are run. SSH keys are automatically generated to access the\n VM, and system connections to the root account and a user account inside the\n VM are added.

\n

By default, the VM distribution is a custom Fedora CoreOS based\n image pushed to quay.io/podman/machine-os (build in\n https://github.com/containers/podman-machine-os). WSL is an exception and is\n based on a custom Fedora image.

\n

To check if there is an upgrade available for your machine os, you\n can run the following command:

\n
$ podman machine ssh 'sudo rpm-ostree upgrade --check'
\n

If an update is available, you can rerun the above command and\n remove the --check and your operating system will be updated. After\n updating, you must stop and start your machine with podman machine stop\n && podman machine start for it to take effect.

\n

The above mechanism is only used to update patch (Z) versions of\n podman. For updates to new major and minor version (X.Y) use the podman\n machine os apply command, see the docs there for more information.

\n

Note: Updating as described above can result in version mismatches\n between Podman on the host and Podman in the machine. Executing podman\n info should reveal versions of both. A configuration where the Podman\n host and machine mismatch are unsupported.

\n

To update the WSL image you must run dnf update inside, use the\n following command:

\n
$ podman machine ssh dnf update
\n

Default Podman machine settings can be set via the [machine]\n section in the containers.conf(5) file.

\n
\n
\n

OPTIONS

\n
\n

--cpus=number

\n

Number of CPUs.

\n
\n
\n

--disk-size=number

\n

Size of the disk for the guest VM in GiB.

\n
\n
\n

--help

\n

Print usage statement.

\n
\n
\n

--ignition-path

\n

Fully qualified path of the ignition file.

\n

If an ignition file is provided, the file is copied into the\n user's CONF_DIR and renamed. Additionally, no SSH keys are generated, nor\n are any system connections made. It is assumed that the user does these\n things manually or handled otherwise.

\n
\n
\n

--image

\n

Fully qualified registry, path, or URL to a VM image. Registry\n target must be in the form of\n docker://registry/repo/image:version.

\n

Note: Only images provided by podman will be supported.

\n
\n
\n

--memory, -m=number

\n

Memory (in MiB). Note: 1024MiB = 1GiB.

\n
\n
\n

--now

\n

Start the virtual machine immediately after it has been\n initialized.

\n
\n
\n

--playbook

\n

Add the provided Ansible playbook to the machine and execute it\n after the first boot.

\n

Note: The playbook will be executed with the same privileges given\n to the user in the virtual machine. The playbook provided cannot include\n other files from the host system, as they will not be copied. Use of the\n --playbook flag will require the image to include Ansible. The\n default image provided will have Ansible included.

\n
\n
\n

--rootful

\n

Whether this machine prefers rootful (true) or rootless\n (false) container execution. This option determines the remote\n connection default if there is no existing remote connection\n configurations.

\n

API forwarding, if available, follows this setting.

\n
\n
\n

--swap, -s=number

\n

Swap (in MiB). Note: 1024MiB = 1GiB.

\n

Renders a zram-generator.conf file with zram-size set to\n the value passed to --swap

\n
\n
\n

--timezone

\n

Set the timezone for the machine and containers. Valid values are\n local or a timezone such as America/Chicago. A value of\n local, which is the default, means to use the timezone of the machine\n host.

\n

The timezone setting is not used with WSL. WSL automatically sets\n the timezone to the same as the host Windows operating system.

\n
\n
\n

--tls-verify

\n

Require HTTPS and verify certificates when contacting registries\n (default: true). If explicitly set to true, TLS verification\n is used. If set to false, TLS verification is not used. If not\n specified, TLS verification is used unless the target registry is listed as\n an insecure registry in containers-registries.conf(5)

\n
\n
\n

--usb=bus=number,devnum=number or\n vendor=hexadecimal,product=hexadecimal

\n

Assign a USB device from the host to the VM via USB passthrough.\n Only supported for QEMU Machines.

\n

The device needs to have proper permissions in order to be passed\n to the machine. This means the device needs to be under your user group.

\n

Note that using bus and device number are simpler but the values\n can change every boot or when the device is unplugged.

\n

When specifying a USB using vendor and product ID's, if more than\n one device has the same vendor and product ID, the first available device is\n assigned.

\n
\n
\n

--user-mode-networking

\n

This option can only be used for the WSL provider on Windows. On\n all other platforms this option is ignored and user mode networking will\n always be true there because these providers always depend on gvproxy\n (our user mode networking tool for the VMs)

\n

In contrast, The Windows/WSL backend defaults to false, and\n follows the standard WSL network setup. Changing this setting to true\n on Windows/WSL informs Podman to replace the WSL networking setup on start\n of this machine instance with a user-mode networking distribution. Since WSL\n shares the same kernel across distributions, all other running distributions\n reuses this network. Likewise, when the last machine instance with a\n true setting stops, the original networking setup is restored.

\n

In some VPN configurations the VPN may drop traffic from alternate\n network interfaces, including VM network devices. By enabling user-mode\n networking VPNs observe all podman machine traffic as coming from the host,\n bypassing the problem.

\n
\n
\n

--username

\n

Username to use for executing commands in remote VM. Default value\n is core for FCOS and user for Fedora (default on Windows\n hosts). Should match the one used inside the resulting VM image.

\n
\n
\n

--volume, -v=source:target[:options]

\n

Mounts a volume from source to target.

\n

Create a mount. If /host-dir:/machine-dir is specified as the\n *source:target*, Podman mounts host-dir in the host to\n machine-dir in the Podman machine.

\n

Additional options may be specified as a comma-separated string. \n Recognized options are: * ro: mount volume read-only * rw: \n mount volume read/write (default) * security_model=[model]: specify \n 9p security model (see below)

\n

Note: The following destinations are forbidden for volumes:\n /bin, /boot, /dev, /etc, /home,\n /proc, /root, /run, /sbin, /sys,\n /tmp, /usr, and /var. Subdirectories of these\n destinations are allowed but users should be ca
