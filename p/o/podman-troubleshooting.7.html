1) مجموعة متنوعة من المشكلات - التحقق من الإصدار

يُكتشف أن عددًا كبيرًا من المشكلات التي يتم الإبلاغ عنها مقابل Podman قد تم إصلاحها بالفعل في الإصدارات الأحدث للمشروع. قبل الإبلاغ عن مشكلة، يرجى التحقق من الإصدار الذي تستخدمه باستخدام podman version ومقارنته بأحدث إصدار موثق في أعلى ملف ⟨README.md⟩ الخاص بـ Podman.

إذا كان هناك اختلاف، يرجى تحديث إصدار PODMAN الخاص بك إلى أحدث إصدار ممكن وإعادة محاولة الأمر قبل الإبلاغ عن المشكلة.

2) لا يمكن استخدام تحميل وحدة التخزين، يتم الحصول على رفض الإذن

$ podman run -v ~/mycontent:/content fedora touch /content/file
touch: cannot touch '/content/file': Permission denied

الحل

هذا ينتج أحيانًا عن SELinux، وأحيانًا عن مساحات أسماء المستخدمين.

تتطلب أنظمة التسمية مثل SELinux وضع تسميات مناسبة على محتوى وحدات التخزين المحملة في حاوية. بدون تسمية، قد يمنع نظام الأمان العمليات التي تعمل داخل الحاوية من استخدام المحتوى. افتراضيًا، لا يغير Podman التسميات التي تم تعيينها بواسطة نظام التشغيل.

لتغيير تسمية في سياق الحاوية، يمكنك إضافة إحدى اللاحقتين :z أو :Z إلى تحميل وحدة التخزين. تخبر هذه اللاحقات Podman بإعادة تسمية كائنات الملفات على وحدات التخزين المشتركة. يخبر الخيار z Podman أن حاويتين تشتركان في محتوى وحدة التخزين. نتيجة لذلك، يقوم Podman بتسمية المحتوى بتسمية محتوى مشترك. تسمح تسميات وحدات التخزين المشتركة لجميع الحاويات بالقراءة/الكتابة للمحتوى. يخبر الخيار Z Podman بتسمية المحتوى بتسمية خاصة غير مشتركة. يمكن للحاوية الحالية فقط استخدام وحدة تخزين خاصة.

$ podman run -v ~/mycontent:/content:Z fedora touch /content/file

تأكد من أن المحتوى خاص بالحاوية. لا تقم بإعادة تسمية أدلة النظام والمحتوى. قد يؤدي إعادة تسمية محتوى النظام إلى فشل خدمات أخرى مقيدة على جهازك. بالنسبة لهذه الأنواع من الحاويات، نوصي بتعطيل فصل SELinux. الخيار --security-opt label=disable سيعطل فصل SELinux للحاوية.

$ podman run --security-opt label=disable -v ~:/home/user fedora touch /home/user/file

في الحالات التي تعمل فيها صورة الحاوية كمستخدم معين غير جذري، يكون الحل هو إصلاح مساحة أسماء المستخدم. قد يشمل ذلك صور الحاويات مثل صورة Jupyter Notebook (التي تعمل باسم "jovyan") وصورة Postgres (التي تعمل باسم "postgres"). في كلتا الحالتين، استخدم المفتاح --userns لتعيين مساحات أسماء المستخدم، في معظم الأوقات باستخدام الخيار keep-id.

$ podman run -v "$PWD":/home/jovyan/work --userns=keep-id jupyter/scipy-notebook

3) لا توجد صورة أو مفاتيح فارغة لا يمكن أن تحتوي على ':'

عند تنفيذ أمر podman pull أو podman build وعدم القدرة على سحب صورة "مشتركة"، فمن المحتمل أن يكون ملف /etc/containers/registries.conf غير مثبت أو قد يكون تكوينه خاطئًا.

العرض

$ sudo podman build -f Dockerfile
STEP 1: FROM alpine
error building: error creating build container: no such image "alpine" in registry: image not known

أو

$ sudo podman pull fedora
error pulling image "fedora": unable to pull fedora: error getting default registries to try: Near line 9 (last key parsed ''): Bare keys cannot contain ':'.

الحل

  • تحقق من وجود ملف /etc/containers/registries.conf. إذا لم يكن موجودًا، فتحقق من تثبيت حزمة containers-common.
  • تحقق من أن الإدخالات في قائمة unqualified-search-registries في ملف /etc/containers/registries.conf صالحة ويمكن الوصول إليها.
•
أي، unqualified-search-registries = ["registry.fedoraproject.org", "quay.io", "registry.access.redhat.com"]

4) http: قدم الخادم استجابة HTTP إلى عميل HTTPS

عند تنفيذ أمر Podman مثل build أو commit أو pull أو push إلى سجل، يكون التحقق من TLS قيد التشغيل افتراضيًا. إذا لم يتم استخدام التشفير مع هذه الأوامر، فقد يحدث هذا الخطأ.

العرض

$ sudo podman push alpine docker://localhost:5000/myalpine:latest
Getting image source signatures
Get https://localhost:5000/v2/: http: server gave HTTP response to HTTPS client

الحل

افتراضيًا، يكون التحقق من TLS قيد التشغيل عند الاتصال بالسجلات من Podman. إذا كان السجل لا يتطلب التشفير، فستفشل أوامر Podman مثل build أو commit أو pull أو push ما لم يتم إيقاف التحقق من TLS باستخدام الخيار --tls-verify. ملاحظة: لا يُنصح على الإطلاق بالاتصال بسجل وعدم استخدام التحقق من TLS.

  • قم بإيقاف التحقق من TLS عن طريق تمرير false إلى خيار tls-verify.
  • أي، podman push --tls-verify=false alpine docker://localhost:5000/myalpine:latest

لحل بديل عام، يمكن للمستخدمين [1] إنشاء الملف /etc/containers/registries.conf.d/registry-NAME.conf (استبدال NAME باسم هذا السجل) بالمحتوى التالي (استبدال FULLY.QUALIFIED.NAME.OF.REGISTRY بعنوان هذا السجل):

[[registry]]
location = "FULLY.QUALIFIED.NAME.OF.REGISTRY"
insecure = true

[1] إذا كنت تستخدم Mac / Windows، يجب عليك تنفيذ podman machine ssh لتسجيل الدخول إلى جهاز podman قبل إضافة الإدخال غير الآمن إلى ملف registry—conf.

هذه طريقة غير آمنة ويجب استخدامها بحذر.

5) الحاويات غير الجذرية لا يمكنها ping المضيفين

عند استخدام أمر ping من حاوية غير جذرية، قد يفشل الأمر بسبب نقص الأذونات.

العرض

$ podman run --rm fedora ping -W10 -c1 redhat.com
PING redhat.com (209.132.183.105): 56 data bytes
--- redhat.com ping statistics ---
1 packets transmitted, 0 packets received, 100% packet loss

الحل

من المحتمل جدًا أنه من الضروري تمكين ping غير المسموح به على المضيف. تأكد من أن UID المستخدم جزء من النطاق في ملف /proc/sys/net/ipv4/ping_group_range.

لتغيير قيمته، يمكنك استخدام شيء مثل:

# sysctl -w "net.ipv4.ping_group_range=0 2000000"

لجعل التغيير دائمًا، ستحتاج إلى إضافة ملف في /etc/sysctl.d يحتوي على net.ipv4.ping_group_range=0 $MAX_UID.

6) USER environment variable not set in container

The USER environment variable is not set by default when running containers with Podman. This can cause issues if the application running inside the container relies on the USER variable to be set.

Symptom

You may encounter errors when running an application inside a container that expects the USER environment variable to be set. The application may fail to start or behave unexpectedly.

$ podman run -ti fedora bash
bash-4.2# echo $USER
root

As you can see, the USER environment variable is set to root by default.

Solution

To set the USER environment variable when running a container, you can use the -e or --env flag with the podman run command. For example, to set the USER variable to newuser, you would run:

$ podman run -e USER=newuser -ti fedora bash
bash-4.2# echo $USER
newuser

Alternatively, you can set the USER variable in your Dockerfile using the USER instruction:

FROM fedora
USER newuser

This will ensure that the USER environment variable is set to newuser when the container is run.

5) Permission denied when running containers as non-root user

When running containers as a non-root user, you may encounter permission denied errors if the useradd command within the container's Dockerfile attempts to create the lastlog file.

Symptom

You will receive a permission denied error when the container is running, similar to the following:

$ podman run -ti --rm ubi8 bash

bash: /var/log/lastlog: Permission denied
bash: /var/log/faillog: Permission denied
bash: newuser is not in the sudoers file.  This incident will be reported.

This occurs because the default behavior of useradd is to create and update the /var/log/lastlog and /var/log/faillog files. When running as a non-root user, these files are not typically writable, leading to the permission denied error.

Change the line in your Dockerfile from:

2) No route to host error when connecting to container networking

When you attempt to connect to a container using its IP address, you may receive a "No route to host" error. This can happen due to several reasons, including incorrect network configuration or firewall rules.

Symptom

You are unable to connect to a container using its IP address, and you receive the following error message:

$ curl http://10.88.0.2:80
curl: (7) couldn't connect to host

Or, if you try to ping the container:

$ ping 10.88.0.2
PING 10.88.0.2 (10.88.0.2) 56(84) bytes of data.
From 10.88.0.1 icmp_seq=1 Destination Host Unreachable

Solution

To resolve the "No route to host" error, you should check the following:

  • Container Network Configuration: Ensure that the container is running and that its network interface is properly configured. You can use the podman network inspect command to view the network settings of your container.

  • Firewall Rules: Check your host's firewall rules to ensure that traffic to and from the container's IP address is allowed. You may need to add rules to allow traffic on the specific port that the container is using.

  • Podman Network: If you are using a custom Podman network, ensure that the network is properly configured and that the container is attached to it. You can create and manage Podman networks using the podman network create and podman network connect commands.

  • IP Address Conflicts: Make sure that the container's IP address does not conflict with any other IP addresses on your network. If there is a conflict, you may need to reconfigure the container's network or the other device's IP address.

By carefully checking these potential issues, you should be able to resolve the "No route to host" error and successfully connect to your container.

4) Podman crashing when updating containers

When updating containers, you may encounter a situation where Podman crashes. This can be due to various reasons, including issues with storage drivers, corrupted container images, or conflicts with other software.

Symptom

Podman terminates unexpectedly when you attempt to update a container. This might happen during commands like `podman pull` or when rebuilding an existing image.

Solution

To address Podman crashing when updating containers, consider the following steps:

  • Check Storage Driver: Ensure that your storage driver is properly configured and compatible with your system. Issues with the storage driver, such as `overlayfs` or `btrfs`, can lead to instability. You can check the configured storage driver in Podman's configuration file (e.g., `/etc/containers/storage.conf`).

  • Clean Up Unused Images/Containers: Remove any unused or dangling images and containers that might be consuming excessive disk space or causing conflicts. Use commands like `podman image prune` and `podman container prune`.

  • Verify Image Integrity: If the crash occurs when pulling or updating a specific image, try removing the local copy of that image and pulling it again. Corrupted image layers can cause issues.

  • Update Podman and Dependencies: Ensure that you are using the latest stable version of Podman and its related dependencies. Updates often include bug fixes that address stability issues.

  • System Resources: Check if your system has sufficient resources (CPU, memory, disk space) available. Running out of resources can lead to crashes.

  • Check System Logs: Examine system logs (e.g., `/var/log/messages` or `journalctl`) for any related error messages around the time of the crash. These logs might provide clues about the underlying cause.

If the problem persists after trying these solutions, it may be beneficial to file a bug report with the Podman project, providing detailed information about your system, Podman version, and the specific steps that lead to the crash.

3) Cannot run containers with user namespace remap enabled after upgrading to RHEL 8.5

After upgrading to Red Hat Enterprise Linux (RHEL) 8.5, you might encounter issues running containers with user namespace remapping enabled. This could be due to changes in the user namespace handling or related security configurations introduced in this version.

Symptom

When attempting to run a container with user namespace remapping enabled (e.g., using `podman --userns=auto` or similar configurations), you might observe errors related to user ID mapping, permissions, or the failure of the container to start correctly. The specific error messages can vary but often indicate problems with sub-UID/sub-GID allocations or mounting user namespaces.

$ podman run --rm -u 1000:1000 alpine id
Error: failed to create user namespace: failed to map user ID for user namespace: fork/exec /usr/bin/newuidmap: no such file or directory

This example shows a specific error related to `newuidmap`, but other errors concerning permissions or namespace creation might also occur.

Solution

To resolve issues with user namespace remapping after upgrading to RHEL 8.5, ensure the following:

  • Install `shadow-utils` and `uidmap` packages: Make sure that the `shadow-utils` package (which provides `newuidmap` and `newgidmap`) and the `uidmap` package are installed on your system. These packages are essential for user namespace remapping functionality.

    # dnf install -y shadow-utils uidmap

  • Configure `/etc/subuid` and `/etc/subgid`: Verify that your user has sufficient ranges of sub-user IDs and sub-group IDs defined in `/etc/subuid` and `/etc/subgid`. If these ranges are missing or too small, Podman might fail to create the necessary mappings.

    You can add or extend these ranges using the `usermod` command. For example, to add a range for a user named `myuser`:

    # usermod --add-subuids 100000-165535 --add-subgids 100000-165535 myuser

    Ensure the range is large enough to accommodate the users and groups that will be remapped within the containers.

  • Check Kernel Configuration: Ensure that user namespaces are enabled in your kernel configuration. Most default RHEL installations have this enabled, but it's worth verifying if you suspect kernel-level issues. You can check related sysctl parameters like `kernel.unprivileged_userns_clone`.

  • Podman Configuration: Review your Podman configuration (e.g., `containers.conf` or `podman system migrate`) to ensure it aligns with the expected settings for user namespace remapping. Sometimes, manual migration or configuration adjustments might be necessary after a system upgrade.

If you continue to experience problems, consult the RHEL documentation for specific guidance on user namespace remapping in version 8.5 and later, as there may be known issues or specific configuration requirements.

11) SELinux denials when using container storage in custom locations

When you redirect container storage (graphroot) to a custom location outside of the default `/var/lib/containers/storage`, you might encounter SELinux denials that prevent Podman from accessing or modifying files in the new location.

Symptom

You configure Podman to use a different directory for its storage, for example, by modifying `/etc/containers/storage.conf` to set `graphroot` to `/srv/containers/storage`. When you then try to run commands like `podman pull` or `podman run`, you receive errors indicating permission denied, often accompanied by SELinux AVC denial messages in the system audit log (`/var/log/audit/audit.log`).

$ podman pull fedora
...
Error: open /srv/containers/storage/overlay-images/a3c23946009b1e0e00a7c501f45a3729e71a655d73a619446a550c156340a050/images/layer.tar: permission denied

And in `/var/log/audit/audit.log`:

type=AVC msg=audit(1678886400.123:123): avc:  denied  { write } for  pid=1234 comm="setools" name="overlay-images" dev="dm-0" ino=5678 scontext=system_u:system_r:container_t:s0:c123,c456 tcontext=system_u:object_r:user_home_dir_t:s0 tclass="dir" permissive=0

The key here is the `tcontext=system_u:object_r:user_home_dir_t:s0` which indicates SELinux is applying incorrect security labels to the custom storage directory.

Solution

To resolve SELinux denials when using custom container storage locations, you need to apply the correct SELinux security context to the directory. This tells SELinux how to treat files and directories within that path.

The recommended approach is to use `semanage fcontext` to define a file context that mirrors the default container storage context and then use `restorecon` to apply it.

  1. Define the SELinux file context equivalence. This command tells SELinux that the directory `/srv/containers` should be treated as if it were `/var/lib/containers`. The `-e` option creates an equivalence record.

    # semanage fcontext -a -e /var/lib/containers /srv/containers

    This command establishes a rule that any content within `/srv/containers` should inherit the security labels appropriate for container storage, specifically those defined under `/var/lib/containers`.

  2. Apply the defined file context to the actual directory and its contents. The `restorecon` command resets the security contexts of files and directories to the default policy. The `-R` flag makes it recursive, and `-v` provides verbose output showing which files are relabeled.

    # restorecon -R -v /srv/containers

    This command will traverse the `/srv/containers` directory and apply the correct SELinux labels based on the equivalence rule you set up in the previous step. You should see output indicating that the files and directories are being relabeled.

After applying these changes, Podman should be able to access and manage its storage in the `/srv/containers` directory without SELinux denials.

**Important Considerations:**

  • Ensure that the directory you are using for custom storage (e.g., `/srv/containers`) is mounted with the correct filesystem type and permissions to allow read/write access for the user running Podman.

  • If you are using NFS or other network file systems for your container storage, SELinux context management might behave differently or require additional configuration. Network file systems often have limited or no SELinux support by default.

  • Always check the audit log (`/var/log/audit/audit.log`) for specific AVC denial messages. This helps in precisely identifying the type of access being denied and can guide troubleshooting efforts if the initial `semanage` and `restorecon` commands do not fully resolve the issue.

10) Newuidmap and newgidmap missing in rootless Podman commands

Rootless Podman relies on the `newuidmap` and `newgidmap` executables to set up user namespace mappings. If these programs are missing from your system, rootless Podman commands will fail.

Symptom

When attempting to run a container in rootless mode, you receive an error message indicating that `newuidmap` or `newgidmap` cannot be found:

This error clearly states that the necessary executables for managing user ID mappings in rootless containers are missing.

To resolve this issue, you need to install the package that provides the `newuidmap` and `newgidmap` executables. On most RHEL-based systems (like Fedora, CentOS, RHEL), this package is `shadow-utils`.

Install the package using your system's package manager:

# On Fedora/CentOS/RHEL:
sudo dnf install -y shadow-utils

If you are using a different Linux distribution, the package name might vary (e.g., `shadow` on Debian/Ubuntu systems). Consult your distribution's package management documentation.

**Important Note for RHEL/CentOS 7:**

Once the `shadow-utils` package (or equivalent) is installed, `newuidmap` and `newgidmap` should be available in your system's PATH, and rootless Podman commands should function correctly.

9) Rootless Podman setup user: invalid argument error

When running Podman in rootless mode, the system needs to allocate a range of user IDs (UIDs) and group IDs (GIDs) to the user running Podman. These allocations are defined in `/etc/subuid` and `/etc/subgid`. If these files do not contain valid or sufficient entries for the user, Podman will fail with an "invalid argument" error during user namespace setup.

Symptom

You attempt to run a Podman command as a non-root user, potentially specifying a user within the container using the `--user` flag, and receive an error like:

$ podman run --rm -ti --user 1000000 alpine echo hi
Error: container create failed: container_linux.go:344: starting container process caused "setup user: invalid argument"

This error indicates that Podman could not properly set up the user mapping required for the rootless container, likely due to missing or incorrect entries in `/etc/subuid` or `/etc/subgid`.

Solution

To fix this, you need to ensure that the user running Podman has appropriate sub-UID and sub-GID ranges defined in the respective configuration files. These files specify which UIDs and GIDs from the host system can be remapped to UIDs and GIDs inside the container's user namespace.

1. Check `/etc/subuid` and `/etc/subgid`:

Examine the contents of these files. Each line typically follows the format `username:start_uid:count`.

$ cat /etc/subuid
johndoe:100000:65536
testuser:165536:65536

$ cat /etc/subgid
johndoe:100000:65536
testuser:165536:65536

In this example:

  • `johndoe` has access to UIDs from 100000 up to (but not including) 165536 (a range of 65536 IDs).
  • `testuser` has access to UIDs from 165536 up to 231072 (also a range of 65536 IDs).

2. Add or Extend Ranges if Necessary:

If your user does not have an entry, or if the allocated range is too small for the UIDs required by your containers, you need to add or extend the ranges. The `usermod` command is the recommended way to do this.

**Using `usermod` (Recommended):**

This command adds a new range of sub-UIDs and sub-GIDs to an existing user. Replace `myuser` with the username of the user running Podman, and adjust the range as needed.

# Add a range of 65536 UIDs starting from 200000
sudo usermod --add-subuids 200000:65536 myuser
# Add a corresponding range of 65536 GIDs starting from 200000
sudo usermod --add-subgids 200000:65536 myuser

After running these commands, verify the changes:

$ grep myuser /etc/subuid
myuser:200000:65536
$ grep myuser /etc/subgid
myuser:200000:65536

**Manually Editing Files (Use with Caution):**

You can also manually edit `/etc/subuid` and `/etc/subgid`, but ensure you follow the correct format and avoid overlapping ranges.

# Example manual addition to /etc/subuid
echo "myuser:200000:65536" | sudo tee -a /etc/subuid
# Example manual addition to /etc/subgid
echo "myuser:200000:65536" | sudo tee -a /etc/subgid

Key Considerations:

  • Sufficient Range Size: Ensure the `count` (the third number in the line) is large enough to cover the highest UID/GID your container might need to use. If your container runs a user with UID 1000000, you need at least 1000000 sub-UIDs available starting from your user's allocation.

  • Unique Ranges: Each user should have a unique, non-overlapping range of sub-UIDs/GIDs to prevent security issues where one user's remapped IDs could accidentally overlap with another's.

  • Restart Services/Containers: After modifying `/etc/subuid` or `/etc/subgid`, it's often necessary to stop any running rootless containers and potentially restart related user services or log out/in for the changes to be fully recognized by Podman.

    The command `podman system migrate` can help clean up stale user namespaces and pause processes, which might be needed after configuration changes.

12) Anonymous image pull fails with 'invalid username/password'

When attempting to pull an image anonymously (without providing explicit credentials), you might encounter an "invalid username/password" error. This usually happens when Podman (or Docker) has cached outdated or invalid credentials for the registry, even though authentication shouldn't be required for anonymous pulls.

Symptom

You try to pull an image that should be publicly accessible, but the operation fails with an error message similar to this:

$ podman pull docker.io/library/alpine:latest
Trying to pull docker.io/library/alpine:latest...ERRO[0000] Error pulling image configuration from docker.io/library/alpine:latest: unable to retrieve auth token: invalid username/password
Error: unable to pull docker.io/library/alpine:latest: unable to pull image: Error determining manifest MIME type for docker.io/library/alpine:latest: unable to retrieve auth token: invalid username/password

This error suggests that Podman is attempting to use authentication credentials, and those credentials are now invalid, even though the pull should have been anonymous.

Solution

The most common cause is stale credentials stored in Podman's configuration file (usually `~/.config/containers/auth.json`). Even for anonymous pulls, if Podman finds an entry for the registry with invalid credentials, it might attempt to use them and fail.

To resolve this, you need to remove the cached credentials for the affected registry.

1. Identify and Remove Credentials:

The credentials are typically stored in `~/.config/containers/auth.json`. You can either edit this file directly to remove the relevant entry for the registry (e.g., `docker.io`) or use the `podman logout` command.

**Using `podman logout`:**

This is the simplest method. Run `podman logout` followed by the registry name. If you're unsure of the exact registry name, you can list logged-in registries first.

# List logged-in registries (optional, to see what's there)
podman login --get-login docker.io

# Log out from the registry
podman logout docker.io

If you previously used Docker commands to log in, you might also need to check `~/.docker/config.json` and potentially run `docker logout docker.io`.

**Manually Editing `auth.json`:**

Open `~/.config/containers/auth.json` in a text editor. Look for an entry related to the registry (e.g., `"docker.io"`) within the `auths` section. Remove the entire key-value pair for that registry.

# Before (example):
{
  "auths": {
    "docker.io": {
      "auth": "dXNlcjpwYXNzd29yZA=="
    }
  }
}

# After removing the entry for docker.io:
{
  "auths": {
    // Other registries might be listed here
  }
}

**2. Retry the Image Pull:**

After removing the cached credentials, try pulling the image again:

$ podman pull docker.io/library/alpine:latest

This time, Podman should perform an anonymous pull without attempting to use invalid credentials.

13) Running Podman inside a container causes container crashes and inconsistent states

Attempting to run Podman (or other container runtimes like Docker) inside an already running container (often referred to as "Podman-in-Podman" or "Docker-in-Docker") can lead to instability, crashes, and unpredictable behavior. This is because nested containerization introduces complexities related to resource management, isolation, networking, and storage drivers.

Symptom

When you attempt to run Podman commands within a container that has Podman itself or its necessary dependencies mounted, you experience issues such as:

  • Podman processes crashing unexpectedly.
  • Nested containers failing to start or running with errors.
  • Filesystem corruption or inconsistent states within the outer or inner containers.
  • Networking problems, where containers launched by the inner Podman cannot communicate.
  • General system instability reported by the outer container's operating system.

For instance, you might mount `/var/lib/containers` and `/run/podman` (or similar paths) from the host into the container and then try to run `podman run` inside that container. The operation might hang, error out, or cause the outer container to crash.

Solution

Running a container runtime like Podman inside another container is generally **not recommended** due to the inherent complexities and potential for instability. It often requires privileged access and specific configurations that can weaken the isolation intended by containerization.

If you absolutely must run container operations from within a container, consider these approaches:

  • Use `podman --remote` or SSH: Instead of running Podman directly inside the container, configure the container to connect to a Podman service running on the host machine. This can be done via Podman's remote API or by using SSH to execute commands on the host.

    On the host machine, ensure the Podman service is running and accessible (e.g., `podman system service --time=0` or via SSH daemon).

    Inside the container, set the `CONTAINER_HOST` environment variable or use `podman --remote` flags to connect to the host's Podman service.

    # Inside the container:
export CONTAINER_HOST=ssh://user@host_ip
podman ps

  • Use `podman machine` (if applicable): For macOS and Windows users, Podman Machine provides a Linux VM where Podman runs. You could potentially run Podman commands inside a container within that VM, though this adds another layer of nesting.

  • Systemd socket activation or Privileged Container: In very specific, controlled environments (like CI/CD pipelines), you might run the outer container in privileged mode (`--privileged`) and ensure necessary kernel modules and device access are available. This approach significantly reduces security isolation and should be used with extreme caution.

    For example, mounting necessary host paths like `/var/run/docker.sock` (if mimicking Docker) or `/run/podman` and `/var/lib/containers` might be attempted, but requires careful handling of storage drivers (e.g., loopback devices, overlayfs). Often, this involves running the outer container with `--cgroup-manager=systemd` or similar systemd integration flags if the host uses systemd.

  • **Re-evaluate the Use Case:** Ask why Podman needs to run inside a container. Often, there's a better architectural solution. For building images, use multi-stage builds or external CI/CD runners. For managing containers, use orchestration tools (Kubernetes, Nomad) or run Podman directly on the host or a dedicated VM.

**Why it's problematic:**

  • **Resource Duplication:** Resources like namespaces, cgroups, and network stacks are duplicated, leading to inefficient resource usage.
  • **Isolation Conflicts:** The inner container runtime might conflict with the outer container's isolation mechanisms or the host's kernel features.
  • **Storage Driver Issues:** Nested storage drivers (e.g., overlayfs inside overlayfs) can be complex to set up correctly and prone to corruption.
  • **Security Risks:** Running nested containers often requires elevated privileges, compromising the security benefits of containerization.

In summary, avoid running Podman inside a container unless absolutely necessary and you fully understand the implications. Prefer connecting to a remote Podman instance or redesigning the workflow.

34) Container creates a file that is not owned by the user's regular UID

After running a container with rootless Podman, the non-root user sees a numerical UID and GID instead of a username and groupname.

Symptom

When listing file permissions with ls -l on the host in a directory that was passed as --volume /some/dir to podman run, the UID and GID are displayed rather than the corresponding username and groupname. The UID and GID numbers displayed are from the user's subordinate UID and GID ranges on the host system.

An example

$ mkdir dir1
$ chmod 777 dir1
$ podman run --rm -v ./dir1:/dir1:Z   
             --user 2003:2003   
             docker.io/library/ubuntu bash -c "touch /dir1/a; chmod 600 /dir1/a"
$ ls -l dir1/a
-rw-------. 1 102002 102002 0 Jan 19 19:35 dir1/a
$ less dir1/a
less: dir1/a: Permission denied

Solution

If you want to read, chown, or remove such a file, enter a user namespace. Instead of running commands such as less dir1/a or rm dir1/a, you need to prepend the command-line with podman unshare, i.e., podman unshare less dir1/a or podman unshare rm dir1/a. To change the ownership of the file dir1/a to your regular user's UID and GID, run podman unshare chown 0:0 dir1/a. A file having the ownership 0:0 in the user namespace is owned by the regular user on the host. To use Bash features, such as variable expansion and globbing, you need to wrap the command with bash -c, e.g. podman unshare bash -c 'ls $HOME/dir1/a*'.

Would it have been possible to run Podman in another way so that your regular user would have become the owner of the file? Yes, you can use the option --userns keep-id:uid=$uid,gid=$gid to change how UIDs and GIDs are mapped between the container and the host. Let's try it out.

In the example above ls -l shows the UID 102002 and GID 102002. Set shell variables

$ uid_from_ls=102002
$ gid_from_ls=102002

Set shell variables to the lowest subordinate UID and GID

$ lowest_subuid=$(podman info --format "{{ (index .Host.IDMappings.UIDMap 1).HostID }}")
$ lowest_subgid=$(podman info --format "{{ (index .Host.IDMappings.GIDMap 1).HostID }}")

Compute the UID and GID inside the container that map to the owner of the created file on the host.

$ uid=$(( $uid_from_ls - $lowest_subuid + 1))
$ gid=$(( $gid_from_ls - $lowest_subgid + 1))

(In the computation it was assumed that there is only one subuid range and one subgid range)

$ echo $uid
2003
$ echo $gid
2003

The computation shows that the UID is 2003 and the GID is 2003 inside the container. This comes as no surprise as this is what was specified before with --user=2003:2003, but the same computation could be used whenever a username is specified or the --user option is not used.

Run the container again but now with UIDs and GIDs mapped

$ mkdir dir1
$ chmod 777 dir1
$ podman run --rm
  -v ./dir1:/dir1:Z   
  --user $uid:$gid   
  --userns keep-id:uid=$uid,gid=$gid   
     docker.io/library/ubuntu bash -c "touch /dir1/a; chmod 600 /dir1/a"
$ id -u
tester
$ id -g
tester
$ ls -l dir1/a
-rw-------. 1 tester tester 0 Jan 19 20:31 dir1/a
$

In this example the --user option specified a rootless user in the container. As the rootless user could also have been specified in the container image, e.g.

$ podman image inspect --format "user: {{.User}}" IMAGE
user: hpc

the same problem could also occur even without specifying --user.

Another variant of the same problem could occur when using --user=root:root (the default), but where the root user creates non-root owned files in some way (e.g by creating them themselves, or switching the effective UID to a rootless user and then creates files).

40) Podman fails to find expected image with error locating pulled image , image not known

When trying to do a Podman command that pulls an image from local storage or a remote repository, an error is raised saying "image not known" or "error locating pulled image". Even though the image had been verified before the Podman command was invoked.

Symptom

After verifying that an image is in place either locally or on a remote repository, a Podman command referencing that image will fail in a manner like:

# ls Containerfile
FROM registry.access.redhat.com/ubi8-minimal:latest
MAINTAINER Podman Community
USER root
# podman build .
STEP 1/2: FROM registry.access.redhat.com/ubi8-minimal
Trying to pull registry.access.redhat.com/ubi8-minimal:latest...
Getting image source signatures
Checking if image destination supports signatures
Copying blob a6577091999b done
Copying config abb1ba1bce done
Writing manifest to image destination
Storing signatures
Error: error creating build container: error locating pulled image "registry.access.redhat.com/ubi8-minimal:latest" name in containers storage: registry.access.redhat.com/ubi8-minimal:latest: image not known

Solution

The general cause for this is a timing issue. To make Podman commands as efficient as possible, read and write locks are only established for critical sections within the code. When pulling an image from a repository, a copy of that image is first written to local storage using a write lock. This lock is released before the image is then acquired/read. If another process does a harmful command such as podman system prune --all or podman system reset or podman rmi --all, between the time the image is written and before the first process can acquire it, this type of image not known error can arise.

The maintainers of Podman have considered heavier-duty locks to close this timing window. However, the slowdown that all Podman commands would encounter was not considered worth the cost of completely closing this small timing window.

باستخدام مشغل التخزين الافتراضي overlay، يكون سطر COPY أو ADD أو سطر RUN المكثف لإدخال/إخراج الملفات في Containerfile الذي يتم تشغيله داخل حاوية أخرى بطيئًا جدًا أو يتعطل تمامًا عند تشغيل podman build داخل الحاوية الأصلية قيد التشغيل.

Solution

قد يكون سبب ذلك استخدام الحاوية الفرعية لـ fuse-overlayfs للكتابة إلى /var/lib/containers/storage. قد تكون عمليات الكتابة بطيئة مع fuse-overlayfs. الحل هو استخدام نظام ملفات overlay الأصلي عن طريق استخدام دليل محلي على نظام المضيف كوحدة تخزين لـ /var/lib/containers/storage كالتالي: podman run --privileged --rm -it -v ./nested_storage:/var/lib/containers/storage parent:latest. تأكد من أن الصورة الأساسية لـ parent:latest في هذا المثال لا تحتوي على أي محتويات في /var/lib/containers/storage في الصورة نفسها لكي يعمل هذا. بمجرد استخدام وحدة التخزين الأصلية، لا يجب أن تعود الحاوية المتداخلة إلى fuse-overlayfs لكتابة الملفات وسيتم الانتهاء من البناء المتداخل بشكل أسرع بكثير.

إذا لم يكن لديك حق الوصول إلى عملية تشغيل الحاوية الأصلية، كما هو الحال في بيئة CI، فإن الخيار الثاني هو تغيير مشغل التخزين إلى vfs في الصورة الأصلية عن طريق تغيير هذا السطر في ملف storage.conf الخاص بك: driver = "vfs". قد تحتاج إلى تشغيل podman system reset ليصبح هذا التغيير ساري المفعول. تعرف أنه تم التغيير عندما يقوم podman info |grep graphDriverName بإخراج graphDriverName: vfs. هذه الطريقة أبطأ أداءً من استخدام طريقة وحدة التخزين المذكورة أعلاه، ولكنها أسرع بكثير من fuse-overlayfs.

43) فشل podman run --userns=auto مع الخطأ: إنشاء تخزين الحاوية: لا توجد معرفات غير مستخدمة كافية في مساحة اسم المستخدم

استخدام --userns=auto عند إنشاء حاويات جديدة لا يعمل طالما أن هناك أي حاويات موجودة تم إنشاؤها باستخدام --userns=keep-id أو --userns=nomap.

Symptom

1.
تشغيل مع --userns=auto $ podman run --rm -d --userns=auto alpine sleep 3600 ينجح الأمر.
2.
تشغيل مع --userns=auto $ podman run --rm -d --userns=auto alpine sleep 3600 ينجح الأمر.
3.
تشغيل مع --userns=keep-id $ podman run --rm -d --userns=keep-id alpine sleep 3600 ينجح الأمر.
4.
تشغيل مع --userns=auto $ podman run --rm -d --userns=auto alpine sleep 3600 يفشل الأمر مع رسالة الخطأ Error: creating container storage: not enough unused IDs in user namespace

Solution

يجب أولاً حذف أي حاويات موجودة تم إنشاؤها باستخدام --userns=keep-id أو --userns=nomap قبل أن يتمكن أي حاوية جديدة من الإنشاء باستخدام --userns=auto.

44) يفشل sudo podman run --userns=auto مع تعذر العثور على تعيينات للمستخدم containers

عند استدعاء podman rootful باستخدام --userns=auto، يحتاج podman إلى اختيار نطاقات فرعية من subuids و subgids لمساحة اسم المستخدم الخاصة بالحاوية. يضمن podman rootful أن نطاقات subuid و subgid لهذه الحاويات لا تتداخل، ولكن كيف يمكن لـ podman rootful منع الأدوات الأخرى من استخدام هذه المعرفات عن طريق الخطأ؟

لا يمكن منع الأدوات الأخرى التي تعمل كـ root من استخدام هذه المعرفات، ولكن مثل هذه الأدوات عادةً لا تستخدم subuids و subgids التي تم تعيينها بالفعل لمستخدم في /etc/subuid و /etc/subgid.

اسم المستخدم containers على المضيف له وظيفة خاصة لـ Podman rootful. يستخدم podman rootful معرفات subuids و subgids للمستخدم containers عند تشغيل حاويات --userns=auto. لا يحتاج المستخدم containers إلى معرفات subuids و subgids هذه لأنه لا ينبغي بدء أي عمليات كالمستخدم containers. بعبارة أخرى، المستخدم containers هو مستخدم خاص موجود فقط على النظام لحجز subuids و subgids لـ podman rootful.

containers هو اسم المستخدم الافتراضي ولكن يمكن تغييره عن طريق تعيين الخيار root-auto-userns-user في الملف /etc/containers/storage.conf.

Symptom

تشغيل podman rootful باستخدام --userns=auto

sudo podman run --rm --userns=auto alpine echo hello

يفشل الأمر مع رسالة الخطأ:

ERRO[0000] Cannot find mappings for user "containers": no subuid ranges found for user "containers" in /etc/subuid
Error: creating container storage: not enough unused IDs in user namespace

الملفات /etc/subuid و /etc/subgid لا تحتوي على أي أسطر تبدأ بـ containers:.

Solution

أضف نطاقات subuid و subgid للمستخدم containers في /etc/subuid و /etc/subgid أو قم بتوفير مثل هذه النطاقات باستخدام /etc/nsswitch.conf. للحصول على التفاصيل، انظر subid(5).

الخطوات التالية تنشئ المستخدم containers وتعين نطاقات subuid و subgid كبيرة له:

1.
إنشاء المستخدم containers sudo useradd --comment "Helper user to reserve subuids and subgids for Podman"
--no-create-home
--shell /usr/sbin/nologin
containers
2.
تحقق من نطاقات subuid و subgid للمستخدم containers $ grep ^containers: /etc/subuid containers:720896:65536 $ grep ^containers: /etc/subgid containers:720896:65536 افتراضيًا، يقوم useradd بتعيين 65536 subuids و 65536 subgids لمستخدم جديد. عادةً ما ترغب في أن يكون المجمع المحجوز أكبر من ذلك. كلما كان الحجم أكبر، زادت الحاويات التي يمكن تشغيلها باستخدام sudo podman run --userns=auto ....
3.
قم بتحرير السطر الخاص بالمستخدم containers في الملفات /etc/subuid و /etc/subgid لجعل النطاقات أكبر. تأكد من أن نطاق subuid للمستخدم containers لا يتداخل مع أي نطاقات subuid أخرى في الملفات /etc/subuid. تأكد من أن نطاق subgid للمستخدم containers لا يتداخل مع أي نطاقات subgid أخرى في الملفات /etc/subgid.

اختبر أمر echo مرة أخرى

sudo podman run --rm --userns=auto alpine echo hello

ينجح الأمر ويطبع hello.

45) يفشل Podman مع lsetxattr(label=system_u:object_r:container_file_t:s0) /dir: العملية غير مسموح بها

تمنع أذونات الملفات الصارمة Podman من تعديل تسميات سياق SELinux للملفات في دليل مثبت عن طريق الربط. قد يحدث الخطأ أيضًا عند استخدام أدلة مثبتة عن طريق الربط تقع على أنظمة ملفات لا تدعم XATTR (مثل الإصدارات القديمة من NFS).

Symptom

1.
إنشاء دليل
owned by root sudo mkdir /var/test
2.
منح الجميع إذن القراءة للدليل sudo chmod 755 /var/test
3.
تشغيل ls مباشرة على المضيف ls /var/test تنجح الأوامر.
4.
تشغيل rootless podman مع ربط الدليل. تعيين z كخيار حجم. podman run --rm -v /var/test:/dir:z fedora ls /dir تفشل الأوامر مع رسالة الخطأ التالية: Error: lsetxattr(label=system_u:object_r:container_file_t:s0) /var/test: operation not permitted الخطأ متوقع لأن المستخدم غير المميز لا يملك الصلاحيات لتعديل سياق SELinux للدليل /var/test
5.
تكرار الأمر السابق ولكن مع إزالة خيار الحجم podman run --rm -v /var/test:/dir fedora ls /dir يتم حظر الأوامر بواسطة SELinux وتفشل مع رسالة الخطأ التالية: ls: cannot open directory '/dir': Permission denied

لاحظ أن الوصول إلى الدليل المرتبط يعتمد على قواعد SELinux. على سبيل المثال، ربط الدليل /usr/share ينجح حتى لو لم يكن لدى المستخدم إذن الكتابة للدليل. ينجح الأمر التالي:

podman run --rm -v /usr/share:/dir fedora ls /dir

الحل

البديل 1

استخدام العلم O لربط الدليل من المضيف كتخزين مؤقت باستخدام نظام ملفات overlay.

podman run --rm -v /var/test:/dir:O fedora ls /dir

يتم تدمير التعديلات على نقطة الربط عند انتهاء تنفيذ الحاوية، مشابهة لإلغاء ربط نقطة الربط tmpfs.

ينجح الأمر التالي:

podman run --rm -v /var/test:/dir:O fedora touch /dir/file

ينشئ الأمر touch الملف ولكن يتم تجاهل الملف عند انتهاء الحاوية.

البديل 2

إذا كان الدليل /var/test موجودًا على نظام ملفات يدعم XATTR، قم بتعيين سياق SELinux للدليل الذي يتوافق مع علم حجم podman :z

sudo chcon -R system_u:object_r:container_file_t:s0 /var/test

ينجح الأمر التالي الآن

podman run --rm -v /var/test:/dir ls /dir

البديل 3

تعديل تكوين سياق SELinux الافتراضي للدليل /var/test باستخدام الأمر

sudo semanage fcontext -a -s system_u -t container_file_t "/var/test(/.*)?"

تغيير سياقات SElinux بشكل متكرر للملفات والأدلة تحت /var/test لمطابقة التكوين الجديد

sudo restorecon -R -F -v /var/test

البديل 4

إضافة الخيار --security-opt label=disable لتعطيل SELinux لأمر Podman.

podman run --rm --security-opt label=disable -v /var/test:/dir fedora ls /dir
