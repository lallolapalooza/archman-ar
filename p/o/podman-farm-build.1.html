--cap-add=CAP_xxx

When executing RUN instructions, run the command specified in the instruction with the specified capability added to its capability set. Certain capabilities are granted by default; this option can be used to add more.

--cap-drop=CAP_xxx

When executing RUN instructions, run the command specified in the instruction with the specified capability removed from its capability set. The CAP_CHOWN, CAP_DAC_OVERRIDE, CAP_FOWNER, CAP_FSETID, CAP_KILL, CAP_NET_BIND_SERVICE, CAP_SETFCAP, CAP_SETGID, CAP_SETPCAP, and CAP_SETUID capabilities are granted by default; this option can be used to remove them.

If a capability is specified to both the --cap-add and --cap-drop options, it is dropped, regardless of the order in which the options were given.

--cert-dir=path

Use certificates at path (*.crt, *.cert, *.key) to connect to the registry. (Default: /etc/containers/certs.d) For details, see containers-certs.d(5). (This option is not available with the remote Podman client, including Mac and Windows (excluding WSL2) machines)

--cgroup-parent=path

Path to cgroups under which the cgroup for the container is created. If the path is not absolute, the path is considered to be relative to the cgroups path of the init process. Cgroups are created if they do not already exist.

--cgroupns=how

Sets the configuration for cgroup namespaces when handling RUN instructions. The configured value can be "" (the empty string) or "private" to indicate that a new cgroup namespace is created, or it can be "host" to indicate that the cgroup namespace in which buildah itself is being run is reused.

--cleanup

Remove built images from farm nodes on success (Default: false).

--compat-volumes

Handle directories marked using the VOLUME instruction (both in this build, and those inherited from base images) such that their contents can only be modified by ADD and COPY instructions. Any changes made in those locations by RUN instructions will be reverted. Before the introduction of this option, this behavior was the default, but it is now disabled by default.

--cpp-flag=flags

Set additional flags to pass to the C Preprocessor cpp(1). Containerfiles ending with a ".in" suffix is preprocessed via cpp(1). This option can be used to pass additional flags to cpp.Note: You can also set default CPPFLAGS by setting the BUILDAH_CPPFLAGS environment variable (e.g., export BUILDAH_CPPFLAGS="-DDEBUG").

--cpu-period=limit

Set the CPU period for the Completely Fair Scheduler (CFS), which is a duration in microseconds. Once the container's CPU quota is used up, it will not be scheduled to run until the current period ends. Defaults to 100000 microseconds.

On some systems, changing the resource limits may not be allowed for non-root users. For more details, see https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

This option is not supported on cgroups V1 rootless systems.

--cpu-quota=limit

Limit the CPU Completely Fair Scheduler (CFS) quota.

Limit the container's CPU usage. By default, containers run with the full CPU resource. The limit is a number in microseconds. If a number is provided, the container is allowed to use that much CPU time until the CPU period ends (controllable via --cpu-period).

On some systems, changing the resource limits may not be allowed for non-root users. For more details, see https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

This option is not supported on cgroups V1 rootless systems.

--cpu-shares, -c=shares

CPU shares (relative weight).

By default, all containers get the same proportion of CPU cycles. This proportion can be modified by changing the container's CPU share weighting relative to the combined weight of all the running containers. Default weight is 1024.

The proportion only applies when CPU-intensive processes are running. When tasks in one container are idle, other containers can use the left-over CPU time. The actual amount of CPU time varies depending on the number of containers running on the system.

For example, consider three containers, one has a cpu-share of 1024 and two others have a cpu-share setting of 512. When processes in all three containers attempt to use 100% of CPU, the first container receives 50% of the total CPU time. If a fourth container is added with a cpu-share of 1024, the first container only gets 33% of the CPU. The remaining containers receive 16.5%, 16.5% and 33% of the CPU.

On a multi-core system, the shares of CPU time are distributed over all CPU cores. Even if a container is limited to less than 100% of CPU time, it can use 100% of each individual CPU core.

For example, consider a system with more than three cores. If the container C0 is started with --cpu-shares=512 running one process, and another container C1 with --cpu-shares=1024 running two processes, this can result in the following division of CPU shares:

PID container CPU CPU share
100 C0 0 100% of CPU0
101 C1 1 100% of CPU1
102 C1 2 100% of CPU2

On some systems, changing the resource limits may not be allowed for non-root users. For more details, see https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

This option is not supported on cgroups V1 rootless systems.

--cpuset-cpus=number

CPUs in which to allow execution. Can be specified as a comma-separated list (e.g. 0,1), as a range (e.g. 0-3), or any combination thereof (e.g. 0-3,7,11-15).

On some systems, changing the resource limits may not be allowed for non-root users. For more details, see https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

This option is not supported on cgroups V1 rootless systems.

--cpuset-mems=nodes

Memory nodes (MEMs) in which to allow execution (0-3, 0,1). Only effective on NUMA systems.

If there are four memory nodes on the system (0-3), use --cpuset-mems=0,1 then processes in the container only uses memory from the first two memory nodes.

On some systems, changing the resource limits may not be allowed for non-root users. For more details, see https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

This option is not supported on cgroups V1 rootless systems.

--created-annotation

Add an image annotation (see also --annotation) to the image metadata setting "org.opencontainers.image.created" to the current time, or to the datestamp specified to the --source-date-epoch or --timestamp flag, if either was used. If false, no such annotation will be present in the written image.

Note: this information is not present in Docker image formats, so it is discarded when writing images in Docker formats.

--creds=[username[:password]]

The [username[:password]] to use to authenticate with the registry, if required. If one or both values are not supplied, a command line prompt appears and the value can be entered. The password is entered without echo.

Note that the specified credentials are only used to authenticate against target registries. They are not used for mirrors or when the registry gets rewritten (see containers-registries.conf(5)); to authenticate against those consider using a containers-auth.json(5) file.

--decryption-key=key[:passphrase]

The [key[:passphrase]] to be used for decryption of images. Key can point to keys and/or certificates. Decryption is tried with all keys. If the key is protected by a passphrase, it is required to be passed in the argument and omitted otherwise.

--device=host-device[:container-device][:permissions]

Add a host device to the container. Optional permissions parameter can be used to specify device permissions by combining r for read, w for write, and m for mknod(2).

--pull=policy

سياسة سحب الصورة. القيمة الافتراضية هي missing.

  • always: اسحب الصورة دائمًا وقم بإطلاق خطأ إذا فشل السحب.
  • missing: اسحب الصورة فقط عندما لا تكون موجودة في مساحة تخزين الحاويات المحلية. قم بإطلاق خطأ إذا لم يتم العثور على صورة وفشل السحب.
  • never: لا تسحب الصورة أبدًا ولكن استخدم الصورة الموجودة في مساحة تخزين الحاويات المحلية. قم بإطلاق خطأ عند عدم العثور على صورة.
  • newer: اسحب إذا كانت الصورة الموجودة في السجل أحدث من الصورة الموجودة في مساحة تخزين الحاويات المحلية. تعتبر الصورة أحدث عندما تكون التجزئات مختلفة. مقارنة الطوابع الزمنية عرضة للأخطاء. يتم قمع أخطاء السحب إذا تم العثور على صورة محلية.

--quiet, -q

قم بكتم رسائل الإخراج التي تشير إلى التعليمة التي تتم معالجتها، والتقدم عند سحب الصور من السجل، وعند كتابة صورة الإخراج.

--retry=attempts

عدد المرات التي يجب فيها إعادة محاولة سحب أو دفع الصور بين السجل ومساحة التخزين المحلية في حالة الفشل. القيمة الافتراضية هي 3.

--retry-delay=duration

مدة التأخير بين محاولات إعادة المحاولة عند سحب أو دفع الصور بين السجل ومساحة التخزين المحلية في حالة الفشل. الافتراضي هو البدء بثانيتين ثم التراجع بشكل أسي. يتم استخدام التأخير عند تعيين هذه القيمة، ولا يحدث أي تراجع أسي.

--rewrite-timestamp

عند إنشاء طبقات جديدة للصورة، تأكد من أن أي محتوى مضاف حديثًا لا يحمل طابعًا زمنيًا أحدث من القيمة المستخدمة بواسطة العلم --source-date-epoch، إذا تم توفير أحدها، عن طريق استبدال أي طوابع زمنية أحدث من تلك القيمة، بتلك القيمة.

--rm

قم بإزالة الحاويات الوسيطة بعد بناء ناجح (افتراضي صحيح).

--runtime=path

المسار path إلى وقت تشغيل بديل متوافق مع OCI، والذي يستخدم لتنفيذ الأوامر المحددة بواسطة التعليمة RUN.

ملاحظة: يمكنك أيضًا تجاوز وقت التشغيل الافتراضي عن طريق تعيين متغير البيئة BUILDAH_RUNTIME. export BUILDAH_RUNTIME=/usr/local/bin/runc

--runtime-flag=flag

يضيف أعلامًا عامة لوقت تشغيل الحاوية. لسرد الأعلام المدعومة، يرجى الرجوع إلى صفحات man لوقت تشغيل الحاوية المحدد.

ملاحظة: لا تقم بتمرير الـ -- البادئة إلى العلم. لتمرير علم runc --log-format json إلى buildah build، الخيار المعطى هو --runtime-flag log-format=json.

--sbom=preset

--sbom-image-output=path

عند إنشاء قوائم SBOMs، قم بتخزين SBOM الناتج في المسار المحدد في الصورة الناتجة. لا يوجد قيمة افتراضية.

--sbom-image-purl-output=path

عند إنشاء قوائم SBOMs، قم بمسحها بحثًا عن معلومات PURL (عنوان URL للحزمة https://github.com/package-url/purl-spec/blob/master/PURL-SPECIFICATION.rst)، وقم بحفظ قائمة بعناوين PURLs التي تم العثور عليها في المسار المحدد في الصورة الناتجة. لا يوجد قيمة افتراضية.

--sbom-merge-strategy=method

إذا تم استخدام أكثر من قيمة واحدة لـ --sbom-scanner-command، استخدم الطريقة المحددة لدمج الإخراج من الأوامر اللاحقة مع الإخراج من الأوامر السابقة. تشمل القيم المعترف بها:

  • cat
    قم بدمج الملفات.
  • merge-cyclonedx-by-component-name-and-version
    قم بدمج حقول "component" في مستندات JSON، مع تجاهل القيم من
    المستندات عندما يكون التركيب من قيم "name" و "version" الخاصة بها
    موجودًا بالفعل. تتم معالجة المستندات بالترتيب الذي تم إنشاؤها به،
    وهو الترتيب الذي تم به تحديد الأوامر التي تنشئها.
  • merge-spdx-by-package-name-and-versioninfo
    قم بدمج حقول "package" في مستندات JSON، مع تجاهل القيم من
    المستندات عندما يكون التركيب من قيم "name" و "versionInfo" الخاصة بها
    موجودًا بالفعل. تتم معالجة المستندات بالترتيب الذي تم إنشاؤها به،
    وهو الترتيب الذي تم به تحديد الأوامر التي تنشئها.

--sbom-output=file

عند إنشاء قوائم SBOMs، قم بتخزين SBOM الناتج في الملف المسمى على نظام الملفات المحلي. لا يوجد قيمة افتراضية.

--sbom-purl-output=file

عند إنشاء قوائم SBOMs، قم بمسحها بحثًا عن معلومات PURL (عنوان URL للحزمة https://github.com/package-url/purl-spec/blob/master/PURL-SPECIFICATION.rst)، وقم بحفظ قائمة بعناوين PURLs التي تم العثور عليها في الملف المسمى على نظام الملفات المحلي. لا يوجد قيمة افتراضية.

--sbom-scanner-command=image

قم بإنشاء قوائم SBOMs عن طريق تشغيل الأمر المحدد من صورة الماسح الضوئي. إذا تم تحديد أوامر متعددة، يتم تشغيلها بالترتيب الذي تم تحديده بها. يتم إجراء استبدالات النص التالية:
- {ROOTFS}
الجذر الخاص بنظام ملفات الصورة المبنية، يتم تركيبه.
- {CONTEXT}
سياق البناء وسياقات البناء الإضافية، يتم تركيبها.
- {OUTPUT}
اسم ملف مؤقت للإخراج، ليتم قراءته ودمجه مع الآخرين أو نسخه إلى مكان آخر.

--sbom-scanner-image=image

قم بإنشاء قوائم SBOMs باستخدام صورة الماسح الضوئي المحددة.

--secret=id=id[,src=envOrFile][,env=ENV][,type=file | env]

قم بتمرير معلومات سرية لاستخدامها في Containerfile لبناء الصور بطريقة آمنة لن تنتهي بتخزينها في الصورة النهائية، أو رؤيتها في مراحل أخرى. سيتم قراءة قيمة السر من متغير بيئة أو ملف مسمى بالخيار "id"، أو مسمى بالخيار "src" إذا تم تحديده، أو من متغير بيئة محدد بالخيار "env". انظر الأمثلة #examples. سيتم تركيب السر في الحاوية على /run/secrets/id افتراضيًا.

لاستخدام السر لاحقًا، استخدم العلم --mount في تعليمة RUN ضمن Containerfile:

RUN --mount=type=secret,id=mysecret cat /run/secrets/mysecret

يمكن تجاوز موقع السر في الحاوية باستخدام خيار "target"، "dst"، أو "destination" لعلم RUN --mount.

RUN --mount=type=secret,id=mysecret,target=/run/secrets/myothersecret cat /run/secrets/myothersecret

ملاحظة: تغيير محتويات ملفات الأسرار لن يؤدي إلى إعادة بناء الطبقات التي تستخدم هذه الأسرار.

--shm-size=number[unit]

حجم /dev/shm. يمكن أن تكون الوحدة unit b (بايت)، k (كيلوبايت)، m (ميجابايت)، أو g (جيجابايت). إذا تم حذف الوحدة، يستخدم النظام البايت. إذا تم حذف الحجم، الافتراضي هو

64m. عندما يكون الحجم 0، فلا يوجد حد لمقدار الذاكرة المستخدمة للاتصال بين العمليات (IPC) بواسطة الحاوية. يتعارض هذا الخيار مع --ipc=host.

--skip-unused-stages

تجاوز المراحل في عمليات البناء متعددة المراحل التي لا تؤثر على المرحلة المستهدفة. (الافتراضي: true).

--source-date-epoch=ثواني

تعيين الطابع الزمني "للإنشاء" للصورة المبنية على هذا العدد من الثواني منذ الحقبة (الوقت العالمي المنسق 0، أي 00:00:00 بالتوقيت العالمي المنسق في 1 يناير 1970) (الافتراضي هو استخدام القيمة المحددة في متغير البيئة SOURCE_DATE_EPOCH، أو الوقت الحالي إذا لم يتم تعيينها).

يتم كتابة الطابع الزمني "للإنشاء" في تكوين الصورة وبيانها عند الالتزام بالصورة، لذا فإن تشغيل نفس عملية البناء مرتين مختلفين سينتج عادةً صورًا ذات تجزئات sha256 مختلفة، حتى لو لم يتم إجراء أي تغييرات أخرى على Containerfile وسياق البناء.

عند تعيين هذا العلم، سيقدم وسيط البناء SOURCE_DATE_EPOCH قيمته لمرحلة يتم الإعلان عنها فيها.

عند تعيين هذا العلم، يتم دائمًا تعيين الطابع الزمني "للإنشاء" لتكوين الصورة إلى الوقت المحدد، مما يجب أن يسمح ببناء صور متطابقة في أوقات مختلفة باستخدام نفس مجموعة المدخلات.

عند تعيين هذا العلم، ستتضمن المخرجات المكتوبة كما هو محدد في العلم --output الطابع الزمني المحدد بدقة.

يتعارض مع العلم المماثل --timestamp، الذي يقوم أيضًا بتعيين وقته المحدد على محتويات الطبقات الجديدة.

--squash

دمج جميع طبقات الصورة الجديدة في طبقة جديدة واحدة؛ لا يتم دمج الطبقات الموجودة مسبقًا.

--squash-all

دمج جميع طبقات الصورة الجديدة (بما في ذلك تلك الموروثة من صورة أساسية) في طبقة جديدة واحدة.

--ssh=default | id=socket>

مقبس وكيل SSH أو مفاتيح ليتم عرضها على عملية البناء. يمكن ترك مسار المقبس فارغًا لاستخدام قيمة default=$SSH_AUTH_SOCK

لاستخدام وكيل SSH لاحقًا، استخدم خيار --mount في تعليم RUN ضمن Containerfile:

RUN --mount=type=ssh,id=id mycmd

--tag, -t=imageName

يحدد الاسم الذي يتم تعيينه للصورة الناتجة إذا اكتملت عملية البناء بنجاح. إذا لم يتضمن imageName اسم سجل، فسيتم إضافة اسم السجل localhost قبل اسم الصورة.

--target=stageName

تعيين مرحلة البناء المستهدفة للبناء. عند بناء Containerfile بمراحل بناء متعددة، يمكن استخدام --target لتحديد مرحلة بناء وسيطة بالاسم كمرحلة نهائية للصورة الناتجة. يتم تخطي الأوامر بعد المرحلة المستهدفة.

--timestamp=ثواني

تعيين الطابع الزمني للإنشاء إلى الثواني منذ الحقبة للسماح بعمليات بناء حتمية (الافتراضي هو الوقت الحالي). بشكل افتراضي، يتم تغيير الطابع الزمني للإنشاء وكتابته في بيان الصورة مع كل التزام، مما يتسبب في اختلاف تجزئة sha256 للصورة حتى لو كانت المصادر متطابقة تمامًا بخلاف ذلك. عند تعيين --timestamp، يتم دائمًا تعيين الطابع الزمني للإنشاء إلى الوقت المحدد وبالتالي لا يتغير، مما يسمح لتجزئة sha256 للصورة بالبقاء كما هي. يتم إنشاء جميع الملفات الملتزم بها في طبقات الصورة بالطابع الزمني.

إذا كان التعليم الوحيد في Containerfile هو FROM، فلن يكون لهذا العلم أي تأثير.

--tls-verify

طلب HTTPS والتحقق من الشهادات عند الاتصال بالسجلات (الافتراضي: true). إذا تم تعيينه صراحةً على true، يتم استخدام التحقق من TLS. إذا تم تعيينه على false، لا يتم استخدام التحقق من TLS. إذا لم يتم تحديده، يتم استخدام التحقق من TLS ما لم يتم إدراج السجل المستهدف كسجل غير آمن في containers-registries.conf(5)

--ulimit=type=soft-limit[:hard-limit]

يحدد حدود الموارد التي سيتم تطبيقها على العمليات التي يتم تشغيلها عند معالجة تعليمات RUN. يمكن تحديد هذا الخيار عدة مرات. تشمل أنواع الموارد المعترف بها:
"core": الحد الأقصى لحجم تفريغ النواة (ulimit -c)
"cpu": الحد الأقصى لوقت وحدة المعالجة المركزية (ulimit -t)
"data": الحد الأقصى لحجم قسم بيانات العملية (ulimit -d)
"fsize": الحد الأقصى لحجم الملفات الجديدة (ulimit -f)
"locks": الحد الأقصى لعدد أقفال الملفات (ulimit -x)
"memlock": الحد الأقصى لمقدار الذاكرة المقفلة (ulimit -l)
"msgqueue": الحد الأقصى لكمية البيانات في قوائم انتظار الرسائل (ulimit -q)
"nice": تعديل اللطف (nice -n، ulimit -e)
"nofile": الحد الأقصى لعدد الملفات المفتوحة (ulimit -n)
"nproc": الحد الأقصى لعدد العمليات (ulimit -u)
"rss": الحد الأقصى لحجم الذاكرة المقيمة للعملية (ulimit -m)
"rtprio": الحد الأقصى لأولوية جدولة الوقت الفعلي (ulimit -r)
"rttime": الحد الأقصى لوقت تنفيذ الوقت الفعلي بين استدعاءات النظام المحظورة
"sigpending": الحد الأقصى لعدد الإشارات المعلقة (ulimit -i)
"stack": الحد الأقصى لحجم المكدس (ulimit -s)

--unsetannotation=annotation

إلغاء تعيين تعليق توضيحي للصورة، مما يؤدي إلى عدم وراثة التعليق التوضيحي من الصورة الأساسية.

--unsetenv=env

إلغاء تعيين متغيرات البيئة من الصورة النهائية.

--unsetlabel=label

إلغاء تعيين تسمية الصورة، مما يؤدي إلى عدم وراثة التسمية من الصورة الأساسية.

--userns=how

يضبط التكوين لمساحات أسماء المستخدم عند معالجة تعليمات RUN. يمكن أن تكون القيمة المكونة "" (سلسلة فارغة) أو "container" للإشارة إلى أنه تم إنشاء مساحة أسماء مستخدم جديدة، أو يمكن أن تكون "host" للإشارة إلى أنه يتم إعادة استخدام مساحة أسماء المستخدم التي يتم تشغيل podman نفسه فيها حاليًا، أو يمكن أن تكون المسار إلى مساحة أسماء مستخدم قيد الاستخدام بالفعل بواسطة عملية أخرى.

--userns-gid-map=mapping

يحدد بشكل مباشر خريطة GID لاستخدامها لتعيين الملكية، على مستوى نظام الملفات، على محتويات الحاوية العاملة. يتم تشغيل الأوامر عند معالجة تعليمات RUN افتراضيًا في مساحات أسماء المستخدم الخاصة بها، ويتم تكوينها باستخدام خرائط UID و GID.

تأخذ الإدخالات في هذه الخريطة شكل ثلاثية واحدة أو أكثر من GID البدء داخل الحاوية، و GID المقابل على مستوى المضيف، وعدد المعرفات المتتالية التي يمثلها إدخال الخريطة.

يتجاوز هذا الخيار إعداد remap-gids في قسم options من /etc/containers/storage.conf.

إذا لم يتم تحديد هذا الخيار، ولكن تم توفير إعداد عام --userns-gid-map، فسيتم استخدام الإعدادات من الخيار العام.

إذا لم يتم تحديد أي من --userns-uid-map-user، أو --userns-gid-map-group، أو --userns-gid-map، ولكن تم تحديد --userns-uid-map، فسيتم تعيين خريطة GID لاستخدام نفس القيم الرقمية مثل خريطة UID.

--userns-gid-map-group=group

يحدد أن خريطة GID التي سيتم استخدامها لتعيين الملكية، على مستوى نظام الملفات، على محتويات الحاوية العاملة، يمكن العثور عليها في الإدخالات في ملف /etc/subgid التي تتوافق مع المجموعة المحددة. يتم تشغيل الأوامر عند معالجة تعليمات RUN افتراضيًا في مساحات أسماء المستخدم الخاصة بها، ويتم تكوينها باستخدام خرائط UID و GID. إذا تم تحديد --userns-uid-map-user، ولكن لم يتم تحديد --userns-gid-map-group، فيفترض podman أن اسم المستخدم المحدد هو أيضًا اسم مجموعة مناسب لاستخدامه كإعداد افتراضي لهذا الخيار.

ملاحظة: عند تحديد هذا الخيار بواسطة مستخدم غير جذر، تكون الخرائط المحددة نسبية لمساحة أسماء المستخدم غير الجذر في الحاوية، بدلاً من أن تكون نسبية إلى المضيف كما هو الحال عند تشغيلها بصلاحيات الجذر.

--userns-uid-map=mapping

يحدد بشكل مباشر خريطة UID لاستخدامها لتعيين الملكية، على مستوى نظام الملفات، على محتويات الحاوية العاملة. يتم تشغيل الأوامر عند معالجة تعليمات RUN افتراضيًا في مساحات أسماء المستخدم الخاصة بها، ويتم تكوينها باستخدام خرائط UID و GID.

تأخذ الإدخالات في هذه الخريطة شكل ثلاثية واحدة أو أكثر من UID البدء داخل الحاوية، و UID المقابل على مستوى المضيف، وعدد المعرفات المتتالية التي يمثلها إدخال الخريطة.

يتجاوز هذا الخيار إعداد remap-uids في قسم options من /etc/containers/storage.conf.

إذا لم يتم تحديد هذا الخيار، ولكن تم توفير إعداد عام --userns-uid-map، فسيتم استخدام الإعدادات من الخيار العام.

إذا لم يتم تحديد أي من --userns-uid-map-user، أو --userns-gid-map-group، أو --userns-uid-map، ولكن تم تحديد --userns-gid-map، فسيتم تعيين خريطة UID لاستخدام نفس القيم الرقمية مثل خريطة GID.

--userns-uid-map-user=user

يحدد أن خريطة UID التي سيتم استخدامها لتعيين الملكية، على مستوى نظام الملفات، على محتويات الحاوية العاملة، يمكن العثور عليها في الإدخالات في ملف /etc/subuid التي تتوافق مع المستخدم المحدد. يتم تشغيل الأوامر عند معالجة تعليمات RUN افتراضيًا في مساحات أسماء المستخدم الخاصة بها، ويتم تكوينها باستخدام خرائط UID و GID. إذا تم تحديد --userns-gid-map-group، ولكن لم يتم تحديد --userns-uid-map-user، فيفترض podman أن اسم المجموعة المحدد هو أيضًا اسم مستخدم مناسب لاستخدامه كإعداد افتراضي لهذا الخيار.

--uts=how

يضبط التكوين لمساحات أسماء UTS عند معالجة تعليمات RUN. يمكن أن تكون القيمة المكونة "" (سلسلة فارغة) أو "container" للإشارة إلى أنه سيتم إنشاء مساحة أسماء UTS جديدة، أو يمكن أن تكون "host" للإشارة إلى أنه سيتم إعادة استخدام مساحة أسماء UTS التي يتم تشغيل podman نفسه فيها حاليًا، أو يمكن أن تكون المسار إلى مساحة أسماء UTS قيد الاستخدام بالفعل بواسطة عملية أخرى.

--volume, -v=[HOST-DIR:CONTAINER-DIR[:OPTIONS]]

تركيب دليل مضيف في الحاويات عند تنفيذ تعليمات RUN أثناء البناء.

OPTIONS هي مجموعة مشتركة

  • [rw|ro]
  • [z|Z|O]
  • [U]
  • [[r]shared|[r]slave|[r]private][1] ⟨#Footnote1⟩

يجب أن يكون CONTAINER-DIR مسارًا مطلقًا مثل /src/docs. يجب أن يكون HOST-DIR مسارًا مطلقًا أيضًا. يقوم Podman بربط HOST-DIR بالمسار المحدد عند معالجة تعليمات RUN.

يمكنك تحديد خيارات -v متعددة لربط تحميل واحد أو أكثر.

يمكنك إضافة اللاحقة :ro أو :rw إلى مجلد لربطه في وضع القراءة فقط أو القراءة والكتابة، على التوالي. افتراضيًا، يتم ربط المجلدات في وضع القراءة والكتابة. انظر الأمثلة.

تغيير ملكية مجلدات الربط

افتراضيًا، لا يغير Podman مالك ومجموعة مجلدات المصدر التي يتم ربطها. عند التشغيل باستخدام مساحات الأسماء للمستخدم، قد يتوافق UID و GID داخل مساحة الأسماء مع UID و GID آخر على المضيف.

تخبر اللاحقة :U Podman باستخدام UID و GID المضيف الصحيحين بناءً على UID و GID داخل مساحة الأسماء، لتغيير مالك ومجموعة مجلد المصدر بشكل متكرر.

تحذير استخدم هذا بحذر لأنه يعدل نظام ملفات المضيف.

وضع علامات على مجلدات الربط

تتطلب أنظمة وضع العلامات مثل SELinux وضع علامات مناسبة على محتوى المجلد الذي يتم ربطه داخل حاوية. بدون علامة، قد يمنع نظام الأمان العمليات التي تعمل داخل الحاوية من استخدام المحتوى. افتراضيًا، لا يغير Podman العلامات التي يضعها نظام التشغيل.

لتغيير علامة في سياق الحاوية، أضف إحدى هاتين اللاحقتين :z أو :Z إلى ربط المجلد. تخبر هذه اللاحقات Podman بإعادة وضع علامات على كائنات الملفات في المجلدات المشتركة. يخبر الخيار z Podman أن حاويتين تشتركان في محتوى المجلد. نتيجة لذلك، يضع Podman علامة على المحتوى بعلامة محتوى مشتركة. تسمح علامات المجلدات المشتركة لجميع الحاويات بقراءة / كتابة المحتوى. يخبر الخيار Z Podman بوضع علامة على المحتوى بعلامة خاصة غير مشتركة. فقط الحاوية الحالية يمكنها استخدام مجلد خاص.

ملاحظة: لا تقم بإعادة وضع علامات على ملفات ومجلدات النظام. قد يتسبب إعادة وضع علامات على محتوى النظام في فشل خدمات أخرى مقيدة على الجهاز المضيف. بالنسبة لهذه الأنواع من الحاويات، يوصى بتعطيل فصل SELinux. الخيار --security-opt label=disable يعطل فصل SELinux للحاوية. على سبيل المثال، إذا أراد مستخدم ربط مجلد المنزل بأكمله الخاص به داخل حاويات البناء، فإنه يحتاج إلى تعطيل فصل SELinux.

$ podman build --security-opt label=disable -v $HOME:/home/user .

مجلدات الربط المتراكبة

يخبر العلم :O Podman بربط المجلد من المضيف كوحدة تخزين مؤقتة باستخدام نظام ملفات Overlay. يُسمح لحاويات أمر RUN بتعديل المحتويات داخل نقطة الربط ويتم تخزينها في تخزين الحاوية في مجلد منفصل. بمصطلحات Overlay FS، يكون مجلد المصدر هو السفلي، ومجلد تخزين الحاوية هو العلوي. يتم تدمير التعديلات على نقطة الربط عند انتهاء تنفيذ أمر RUN، على غرار نقطة ربط tmpfs.

أي تنفيذ لاحق لأوامر RUN يرى محتوى مجلد المصدر الأصلي، ولا توجد أي تغييرات من أوامر RUN السابقة.

إحدى حالات استخدام ربط overlay هي مشاركة ذاكرة التخزين المؤقت للحزم من المضيف داخل الحاوية للسماح بتسريع عمليات البناء.

ملاحظة:

  • روابط Overlay غير مدعومة حاليًا في وضع rootless.
  • العلم O غير مسموح بتحديده مع الأعلام Z أو z. يتم وضع علامة على المحتوى المرتبط داخل الحاوية بالعلامة الخاصة. في أنظمة SELinux، يجب أن تكون العلامات في مجلد المصدر قابلة للقراءة بواسطة علامة الحاوية. إذا لم يكن الأمر كذلك، فيجب تعطيل فصل حاوية SELinux لكي تعمل الحاوية.
  • تعديل مجلد المجلد المرتبط داخل الحاوية برابط overlay يمكن أن يسبب فشلًا غير متوقع. لا تقم بتعديل المجلد حتى تنتهي الحاوية من التشغيل.

افتراضيًا، تكون مجلدات الربط المربوطة خاصة. هذا يعني أن أي ربط يتم داخل الحاويات لن يكون مرئيًا على المضيف والعكس صحيح. يمكن تغيير هذا السلوك عن طريق تحديد خاصية انتشار ربط المجلد.

عندما يتم ضبط سياسة انتشار الربط على shared، فإن أي ربطات يتم إجراؤها داخل الحاوية على هذا المجلد تكون مرئية لكل من المضيف والحاوية. عندما يتم ضبط سياسة انتشار الربط على slave، يتم تمكين انتشار ربط باتجاه واحد وأي ربطات يتم إجراؤها على المضيف لهذا المجلد تكون مرئية فقط داخل الحاوية. للتحكم في خاصية انتشار ربط المجلد استخدم العلم :[r]shared أو :[r]slave أو :[r]private. لكي تعمل انتشار الربط على نقطة ربط المصدر (نقطة الربط حيث يتم ربط مجلد المصدر) يجب أن تمتلك خصائص الربط الصحيحة. بالنسبة للمجلدات المشتركة، يجب أن تكون نقطة ربط المصدر مشتركة. وبالنسبة لمجلدات slave، يجب أن تكون نقطة ربط المصدر إما مشتركة أو slave. [1] ⟨#Footnote1⟩

استخدم df <source-dir> لتحديد ربط المصدر ثم استخدم findmnt -o TARGET,PROPAGATION <source-mount-dir> لتحديد خصائص انتشار ربط المصدر، إذا لم يكن الأداة المساعدة findmnt متاحة، يمكن تحديد نقطة ربط المصدر بالنظر إلى إدخال الربط في /proc/self/mountinfo. انظر إلى الحقول الاختيارية وتحقق مما إذا كانت هناك أي خصائص انتشار محددة. shared:X يعني أن الربط مشترك، master:X يعني أن الربط slave وإذا لم يكن هناك شيء فهذا يعني أن الربط خاص. [1] ⟨#Footnote1⟩

لتغيير خصائص انتشار نقطة الربط استخدم أمر mount. على سبيل المثال، لربط مجلد المصدر /foo استخدم mount --bind /foo /foo و mount --make-private --make-shared /foo. هذا يحول /foo إلى نقطة ربط مشتركة. يمكن تغيير خصائص انتشار الربط للمصدر مباشرة. على سبيل المثال إذا كان / هو ربط المصدر لـ /foo، فاستخدم mount --make-shared / لتحويل / إلى ربط مشترك.

أمثلة

بناء صورة مسماة وقائمةmanifest باستخدام Containerfile محددة بالمزرعة الافتراضية:

$ podman farm build --local -t name -f /path/to/containerfile .

بناء صورة مسماة وقائمة manifest باستخدام المزرعة المحددة:

$ podman farm build --farm myfarm -t name .

بناء صورة مسماة وقائمة manifest باستخدام المزرعة المحددة، وحذف جميع الصور من عقد المزرعة بعد دفعها إلى السجل:

$ podman farm build --farm myfarm --cleanup -t name .

بناء صور مسماة وقائمة manifest لمنصات محددة باستخدام المزرعة الافتراضية:

$ podman farm build --platforms arm64,amd64 -t name .
