الحزمة: podman

التراخيص: Apache-2.0

podman-run(1) دليل الأوامر العامة podman-run(1)

الاسم

podman-run - تشغيل أمر في حاوية جديدة

الملخص

podman run [خيارات] صورة [أمر [وسيط ...]]

podman container run [خيارات] صورة [أمر [وسيط ...]]

الوصف

تشغيل عملية في حاوية جديدة. يقوم podman run ببدء عملية بمجموعة ملفاتها الخاصة، وشبكتها الخاصة، وشجرة عملياتها المعزولة. قد تحدد الصورة التي تبدأ العملية الافتراضيات المتعلقة بالعملية التي سيتم تشغيلها في الحاوية، والشبكة التي سيتم كشفها، والمزيد، ولكن podman run يعطي السيطرة النهائية للمشغل أو المسؤول الذي يبدأ الحاوية من الصورة. لهذا السبب، يحتوي podman run على خيارات أكثر من أي أمر آخر في Podman.

إذا لم يتم تحميل الصورة بالفعل، فسيقوم podman run بسحب الصورة، وجميع تبعيات الصورة، من المستودع بنفس طريقة تشغيل podman pull صورة، قبل أن يبدأ الحاوية من تلك الصورة.

سيتم إنشاء العديد من الملفات تلقائيًا داخل الحاوية. وتشمل هذه /etc/hosts، و /etc/hostname، و /etc/resolv.conf لإدارة الشبكات. ستستند هذه الملفات إلى نسخة الملفات الموجودة على المضيف، على الرغم من أنه يمكن تخصيصها باستخدام الخيارات (على سبيل المثال، قد يتجاوز --dns خوادم DNS الخاصة بالمضيف في resolv.conf الذي تم إنشاؤه). بالإضافة إلى ذلك، يتم إنشاء ملف بيئة حاوية في كل حاوية للإشارة إلى البرامج بأنها تعمل في حاوية. يوجد هذا الملف في /run/.containerenv (أو /var/run/.containerenv لحاويات FreeBSD). عند استخدام العلم --privileged، يحتوي .containerenv على أزواج اسم/قيمة تشير إلى إصدار محرك الحاوية، وما إذا كان المحرك يعمل في وضع بدون صلاحيات الجذر (rootless)، واسم الحاوية ومعرفها، وكذلك اسم الصورة ومعرفها الذي تستند إليه الحاوية. ملاحظة: لن يتم إنشاء /run/.containerenv عند تحميل وحدة تخزين على /run.

عند التشغيل من مساحة اسم شبكة معرفة من قبل المستخدم، سيتم استخدام /etc/netns/NSNAME/resolv.conf إذا كان موجودًا، وإلا فسيتم استخدام /etc/resolv.conf.

يتم تعريف الإعدادات الافتراضية في containers.conf. معظم الإعدادات للاتصالات عن بعد تستخدم خوادم containers.conf، إلا عند توثيقها في صفحات الدليل.

الصورة

يتم تحديد الصورة باستخدام تنسيق النقل:المسار. إذا لم يتم تحديد نقل، فسيتم استخدام نقل docker (سجل الحاويات) افتراضيًا. بالنسبة لـ Podman البعيد، بما في ذلك أجهزة Mac و Windows (باستثناء WSL2)، فإن docker هو النقل الوحيد المسموح به.

dir:مسار
دليل محلي موجود مسار يخزن البيان، و tarballs الطبقة، والتوقيعات كملفات فردية. هذا تنسيق غير قياسي، مفيد بشكل أساسي لتصحيح الأخطاء أو الفحص غير التداخلي للحاوية.

$ podman save --format docker-dir fedora -o /tmp/fedora
$ podman run dir:/tmp/fedora echo hello

docker://مرجع-docker (افتراضي)
مرجع صورة مخزن في سجل صور حاويات بعيد. مثال: "quay.io/podman/stable:latest". يمكن أن يتضمن المرجع مسارًا إلى سجل محدد؛ إذا لم يفعل ذلك، يتم الاستعلام عن السجلات المدرجة في registries.conf للعثور على صورة مطابقة. افتراضيًا، يتم استخدام بيانات الاعتماد من podman login (المخزنة في $XDG_RUNTIME_DIR/containers/auth.json افتراضيًا) للمصادقة؛ وإلا فإنها تتراجع إلى استخدام بيانات الاعتماد في $HOME/.docker/config.json.

$ podman run registry.fedoraproject.org/fedora:latest echo hello

docker-archive:مسار[:مرجع-docker] صورة مخزنة في ملف بتنسيق docker save. مرجع-docker يستخدم فقط عند إنشاء ملف كهذا، ويجب ألا يحتوي على هضم.

$ podman save --format docker-archive fedora -o /tmp/fedora
$ podman run docker-archive:/tmp/fedora echo hello

ملاحظة: في العملاء البعيدين، بما في ذلك أجهزة Mac و Windows (باستثناء WSL2)، لا يتم دعم هذا النقل.

docker-daemon:مرجع-docker
صورة بتنسيق مرجع-docker مخزنة في التخزين الداخلي لـ docker daemon. يمكن أن يكون مرجع-docker أيضًا معرف صورة (docker-daemon:algo:digest).

$ sudo docker pull fedora
$ sudo podman run docker-daemon:docker.io/library/fedora echo hello

ملاحظة: في العملاء البعيدين، بما في ذلك أجهزة Mac و Windows (باستثناء WSL2)، لا يتم دعم هذا النقل.

oci-archive:مسار:علامة
صورة في دليل متوافق مع "مواصفات تخطيط صور الحاويات المفتوحة" في المسار المحدد ومعرّفة بـ علامة.

$ podman save --format oci-archive fedora -o /tmp/fedora
$ podman run oci-archive:/tmp/fedora echo hello

ملاحظة: في العملاء البعيدين، بما في ذلك أجهزة Mac و Windows (باستثناء WSL2)، لا يتم دعم هذا النقل.

خيارات

--add-host=اسم-المضيف[;اسم-المضيف[;...]]:عنوان-IP

إضافة تعيين مخصص من اسم مضيف إلى عنوان IP إلى ملف /etc/hosts الخاص بالحاوية.

يأخذ الخيار اسم مضيف واحد أو أكثر مفصول بنقطتين فوق بعضها البعض ليتم تعيينه إلى عنوان IPv4 أو IPv6 واحد، مفصول بنقطتين. يمكن استخدامه أيضًا لتجاوز عناوين IP لأسماء المضيفين التي يضيفها Podman إلى /etc/hosts افتراضيًا (انظر أيضًا الخيارات --name و --hostname). يمكن تحديد هذا الخيار عدة مرات لإضافة تعيينات إضافية إلى /etc/hosts. يتعارض مع الخيار --no-hosts ومع no_hosts=true في containers.conf.

بدلاً من عنوان IP، يمكن إعطاء العلامة الخاصة host-gateway. يتم حل هذا إلى عنوان IP يمكن للحاوية استخدامه للاتصال بالمضيف. يعتمد عنوان IP المختار على إعداد الشبكة الخاص بك، لذلك لا يوجد ضمان بأن Podman يمكنه تحديد عنوان host-gateway تلقائيًا، مما سيؤدي بعد ذلك إلى فشل Podman مع رسالة خطأ. يمكنك تجاوز عنوان IP هذا باستخدام الخيار host_containers_internal_ip في containers.conf.

يستخدم عنوان host-gateway أيضًا بواسطة Podman لإضافة أسماء المضيفين host.containers.internal و host.docker.internal تلقائيًا إلى /etc/hosts. يمكنك منع ذلك إما عن طريق إعطاء الخيار --no-hosts، أو عن طريق تعيين host_containers_internal_ip="none" في containers.conf. إذا لم يتم تكوين عنوان host-gateway يدويًا وفشل Podman في تحديد عنوان IP تلقائيًا، فسيتخطى Podman بصمت إضافة أسماء المضيفين الداخلية هذه إلى /etc/hosts. إذا كان Podman يعمل في جهاز افتراضي باستخدام podman machine (وهذا يشمل أجهزة Mac و Windows المضيفة)، فسيتخطى Podman بصمت إضافة أسماء المضيفين الداخلية إلى /etc/hosts، ما لم يتم تكوين عنوان IP يدويًا؛ يتم حل أسماء المضيفين الداخلية بواسطة محلل DNS الخاص بـ gvproxy بدلاً من ذلك.

سيستخدم Podman ملف /etc/hosts الخاص بالمضيف كأساس افتراضيًا، أي أن أي اسم مضيف موجود في هذا الملف سيكون موجودًا أيضًا في ملف /etc/hosts الخاص بالحاوية. يمكن تكوين ملف أساسي مختلف باستخدام التكوين base_hosts_file في containers.conf.

--preserve-fd=FD1[,FD2,...]

--privileged

منح امتيازات موسعة لهذه الحاوية. الافتراضي هو false.

افتراضيًا، تكون حاويات Podman غير مميزة (=false) ولا يمكنها، على سبيل المثال، تعديل أجزاء من نظام التشغيل. وذلك لأنه افتراضيًا، يُسمح للحاوية بالوصول المحدود إلى الأجهزة فقط. يتم منح حاوية "مميزة" نفس الوصول إلى الأجهزة مثل المستخدم الذي يقوم بتشغيل الحاوية، باستثناء وحدات التحكم الافتراضية (/dev/tty\d+) عند التشغيل في وضع systemd (--systemd=always).

تقوم الحاوية المميزة بإيقاف تشغيل ميزات الأمان التي تعزل الحاوية عن المضيف. يتم تعطيل القدرات التي تم إسقاطها، والأجهزة المحدودة، ونقاط التحميل للقراءة فقط، وفصل Apparmor/SELinux، ومرشحات Seccomp. نظرًا لميزات الأمان المعطلة، يجب ألا يتم تعيين الحقل المميز --privileged إلا في حالات نادرة جدًا لأن الحاويات يمكن أن تخرج بسهولة من نطاق تقييدها.

لا يمكن للحاويات التي تعمل في مساحة اسم مستخدم (مثل الحاويات غير الجذرية) أن تمتلك امتيازات أكثر من المستخدم الذي قام بتشغيلها.

--publish, -p=[[ip:][hostPort]:]containerPort[/protocol]

نشر منفذ حاوية، أو نطاق من المنافذ، إلى المضيف.

يمكن تحديد كل من hostPort و containerPort كنطاق من المنافذ. عند تحديد نطاقات لكليهما، يجب أن يتطابق عدد منافذ الحاوية في النطاق مع عدد منافذ المضيف في النطاق.

إذا تم تعيين IP المضيف إلى 0.0.0.0 أو لم يتم تعيينه على الإطلاق، فسيتم ربط المنفذ بجميع عناوين IP على المضيف.

افتراضيًا، ينشر Podman منافذ TCP. لنشر منفذ UDP بدلاً من ذلك، قم بتحديد udp كبروتوكول. لنشر منافذ TCP و UDP، قم بتعيين --publish مرتين، مع تحديد tcp و udp كبروتوكولات على التوالي. يمكن للحاويات الجذرية أيضًا نشر المنافذ باستخدام بروتوكول sctp.

لا يلزم تحديد منفذ المضيف (على سبيل المثال، podman run -p 127.0.0.1::80). إذا لم يتم تحديده، فسيتم تعيين منفذ الحاوية عشوائيًا لمنفذ على المضيف.

استخدم podman port لرؤية التعيين الفعلي: podman port $CONTAINER $CONTAINERPORT.

نشر المنافذ مدعوم فقط للحاويات التي تستخدم مساحات الأسماء الشبكية الخاصة بها من خلال شبكات bridge، أو أوضاع الشبكة pasta و slirp4netns.

ملاحظة: إذا كانت الحاوية تعمل داخل بود، فليس من الضروري نشر المنفذ للحاويات الموجودة في البود. يجب نشر المنفذ بواسطة البود نفسه فقط. تتصرف مكدسات شبكة البود مثل مكدس الشبكة على المضيف - مما يعني أن مجموعة متنوعة من الحاويات في البود والبرامج في الحاوية تشترك جميعها في واجهة واحدة وعنوان IP والمنافذ المرتبطة بها. إذا ربطت حاوية بمنفذ، فلا يمكن لأي حاوية أخرى استخدام هذا المنفذ داخل البود أثناء استخدامه. يمكن للحاويات في البود أيضًا الاتصال عبر localhost عن طريق جعل إحدى الحاويات ترتبط بـ localhost في البود، وقيام حاوية أخرى بالاتصال بهذا المنفذ.

--publish-all, -P

نشر جميع المنافذ المكشوفة إلى منافذ عشوائية على واجهات المضيف. الافتراضي هو false.

عند التعيين إلى true، قم بنشر جميع المنافذ المكشوفة إلى واجهات المضيف. إذا استخدم المشغل -P (أو -p) يقوم Podman بجعل المنفذ المكشوف متاحًا على المضيف وتكون المنافذ متاحة لأي عميل يمكنه الوصول إلى المضيف.

عند استخدام هذا الخيار، يقوم Podman بربط أي منفذ مكشوف بمنفذ عشوائي على المضيف ضمن نطاق منافذ مؤقت محدد بواسطة /proc/sys/net/ipv4/ip_local_port_range. لمعرفة التعيين بين منافذ المضيف والمنافذ المكشوفة، استخدم podman port.

--pull=policy

سياسة سحب الصورة. الافتراضي هو missing.

  • always: سحب الصورة دائمًا وتوليد خطأ إذا فشل السحب.
  • missing: سحب الصورة فقط عندما لا تكون الصورة موجودة في تخزين الحاويات المحلي. توليد خطأ إذا لم يتم العثور على صورة وفشل السحب.
  • never: عدم سحب الصورة أبدًا ولكن استخدام الصورة من تخزين الحاويات المحلي. توليد خطأ إذا لم يتم العثور على صورة.
  • newer: السحب إذا كانت الصورة في المستودع أحدث من الصورة الموجودة في تخزين الحاويات المحلي. تعتبر الصورة أحدث عندما تكون التجزئات مختلفة. مقارنة الطوابع الزمنية عرضة للأخطاء. يتم كتم الأخطاء في السحب إذا تم العثور على صورة محلية.

--quiet, -q

كتم معلومات الإخراج عند سحب الصور

--rdt-class=intel-rdt-class-of-service

يحدد Rdt-class فئة الخدمة (CLOS أو COS) التي ستعمل فيها الحاوية. بناءً على ميزة تخصيص ذاكرة التخزين المؤقت (CAT) التي تعد جزءًا من مجموعة ميزات تقنية إدارة موارد Intel (RDT)، ستعمل جميع عمليات الحاوية ضمن COS المعد مسبقًا، والتي تمثل جزءًا من ذاكرة التخزين المؤقت. يجب إنشاء COS وتكوينه باستخدام نظام ملفات وهمي (يتم تحميله عادةً عند /sys/fs/resctrl) الذي توفره برامج تشغيل نواة resctrl. يتطلب تعيين الحاوية إلى COS امتيازات الجذر وبالتالي لا يعمل في بيئة غير جذرية. حاليًا، الميزة مدعومة فقط باستخدام runc كوقت تشغيل. انظر ⟨https://docs.kernel.org/arch/x86/resctrl.html⟩ لمزيد من التفاصيل حول إنشاء COS قبل أن يمكن تعيين الحاوية إليها.

--read-only

تحميل نظام ملفات جذر الحاوية للقراءة فقط.

افتراضيًا، تكون أنظمة ملفات جذر الحاويات قابلة للكتابة، مما يسمح للعمليات بكتابة الملفات في أي مكان. عن طريق تحديد العلامة --read-only، يتم تحميل نظام ملفات جذر الحاويات للقراءة فقط مما يمنع أي كتابات.

--read-only-tmpfs

عند تشغيل حاويات --read-only، قم بتحميل tmpfs للقراءة/الكتابة على /dev و /dev/shm و /run و /tmp و /var/tmp. الافتراضي هو true.

--read-only --read-only-tmpfs / /run, /tmp, /var/tmp
true true r/o r/w
true false r/o r/o
false false r/w r/w
false true r/w r/w

عندما يكون --read-only=true و --read-only-tmpfs=true يتم تحميل tmpfs إضافية على الدلائل /tmp و /run و /var/tmp.

افتراضيًا، عندما يكون --read-only=false، فإن /dev و /dev/shm قابلة للقراءة/الكتابة، و /tmp و /run و /var/tmp هي دلائل قابلة للقراءة/الكتابة من صورة الحاوية.

منح الحاوية الوصول إلى سر. يمكن تحديده عدة مرات.

السر عبارة عن كتلة من البيانات الحساسة التي تحتاجها الحاوية في وقت التشغيل ولكنها غير مخزنة في الصورة أو في التحكم في المصدر ، مثل أسماء المستخدمين وكلمات المرور ، وشهادات ومفاتيح TLS ، ومفاتيح SSH أو سلاسل عامة أخرى مهمة أو محتوى ثنائي (يصل إلى 512 كيلوبايت).

عندما يتم تحديد الأسرار كنوع mount ، يتم نسخ الأسرار وتحميلها في الحاوية عند إنشاء حاوية. عندما يتم تحديد الأسرار كنوع env ، يتم تعيين السر كمتغير بيئة داخل الحاوية. تتم كتابة الأسرار في الحاوية في وقت إنشاء الحاوية ، ويؤثر تعديل السر باستخدام أوامر podman secret بعد إنشاء الحاوية على السر داخل الحاوية.

تتم إدارة الأسرار وتخزينها باستخدام أمر podman secret.

خيارات الأسرار

  • type=mount|env : كيف يتم كشف السر للحاوية.
    mount يقوم بتحميل السر في الحاوية كملف.
    env يكشف السر كمتغير بيئة.
    الافتراضي هو mount.
  • target=target : هدف السر.
    للأسرار المحملة ، هذا هو المسار إلى السر داخل الحاوية.
    إذا تم توفير مسار مؤهل بالكامل ، فسيتم تحميل السر في هذا الموقع.
    بخلاف ذلك ، يتم تحميل السر إلى
    /run/secrets/target للحاويات Linux أو
    /var/run/secrets/target للحاويات FreeBSD.
    إذا لم يتم تعيين الهدف ، يتم تحميل السر إلى /run/secrets/secretname افتراضيًا.
    للأسرار البيئية ، هذا هو مفتاح متغير البيئة. الافتراضي هو secretname.
  • uid=0 : معرف المستخدم السري. الافتراضي هو 0. نوع تحميل السر فقط.
  • gid=0 : معرف المجموعة السري. الافتراضي هو 0. نوع تحميل السر فقط.
  • mode=0 : وضع السر. الافتراضي هو 0444. نوع تحميل السر فقط.

    Add :ro or :rw option to mount a volume in read-only or read-write mode, respectively. By default, the volumes are mounted read-write. See examples.

    Chowning Volume Mounts

    When a named volume is first mounted to a container, Podman automatically adjusts the ownership of the volume's mount point during container initialization. This chown operation occurs under the following conditions:

    • The volume was not used yet (has NeedsChown set to true)
    • The volume is empty or has not been copied up yet
    • The volume is not managed by an external volume driver
    • The volume driver is not "image"

    For volumes with idmapped mounts (using the idmap option), the ownership change takes into account the container's user namespace mappings, but the idmapped volume retains proper UID/GID mapping. For volumes without idmapping, the mount point is chowned to match the container's process user and group, mapped to the host user namespace if user namespace remapping is enabled.

    If a container is created in a new user namespace, the UID and GID in the container may correspond to another UID and GID on the host.

    The :U suffix tells Podman to use the correct host UID and GID based on the UID and GID within the container, to change recursively the owner and group of the source volume. Chowning walks the file system under the volume and changes the UID/GID on each file. If the volume has thousands of inodes, this process takes a long time, delaying the start of the container.

    Warning use with caution since this modifies the host filesystem.

    Labeling Volume Mounts

    Labeling systems like SELinux require that proper labels are placed on volume content mounted into a container. Without a label, the security system might prevent the processes running inside the container from using the content. By default, Podman does not change the labels set by the OS.

    To change a label in the container context, add either of two suffixes :z or :Z to the volume mount. These suffixes tell Podman to relabel file objects on the shared volumes. The z option tells Podman that two or more containers share the volume content. As a result, Podman labels the content with a shared content label. Shared volume labels allow all containers to read/write content. The Z option tells Podman to label the content with a private unshared label. Only the current container can use a private volume.

    Note: all containers within a pod share the same SELinux label. This means all containers within said pod can read/write volumes shared into the container created with the :Z on any one of the containers. Relabeling walks the file system under the volume and changes the label on each file; if the volume has thousands of inodes, this process takes a long time, delaying the start of the container. If the volume was previously relabeled with the z option, Podman is optimized to not relabel a second time. If files are moved into the volume, then the labels can be manually changed with the chcon -Rt container_file_t PATH command.

    Note: Do not relabel system files and directories. Relabeling system content might cause other confined services on the machine to fail. For these types of containers we recommend disabling SELinux separation. The option --security-opt label=disable disables SELinux separation for the container. For example if a user wanted to volume mount their entire home directory into a container, they need to disable SELinux separation.

    $ podman run --security-opt label=disable -v $HOME:/home/user fedora touch /home/user/file

    Overlay Volume Mounts

    The :O flag tells Podman to mount the directory from the host as a temporary storage using the overlay file system. The container processes can modify content within the mountpoint which is stored in the container storage in a separate directory. In overlay terms, the source directory is the lower, and the container storage directory is the upper. Modifications to the mount point are destroyed when the container finishes executing, similar to a tmpfs mount point being unmounted.

    For advanced users, the overlay option also supports custom non-volatile upperdir and workdir for the overlay mount. Custom upperdir and workdir can be fully managed by the users themselves, and Podman does not remove it on lifecycle completion. Example :O,upperdir=/some/upper,workdir=/some/work

    Subsequent executions of the container sees the original source directory content, any changes from previous container executions no longer exist.

    One use case of the overlay mount is sharing the package cache from the host into the container to allow speeding up builds.

    Note: The O flag conflicts with other options listed above.

    Content mounted into the container is labeled with the private label. On SELinux systems, labels in the source directory must be readable by the container label. Usually containers can read/execute container_share_t and can read/write container_file_t. If unable to change the labels on a source volume, SELinux container separation must be disabled for the container to work.

    Do not modify the source directory mounted into the container with an overlay mount, it can cause unexpected failures. Only modify the directory after the container finishes running.

    NAME

    podman-container-run - run a container

    SYNOPSIS

    podman container run [options] image [[command] [args...]]

    DESCRIPTION

    Runs a new container from the specified image and executes the specified command inside the container.

    Podman always creates a new container for the run command. If you want to start an existing container, use podman start.

    When you run an image, Podman creates a container from the image. The container is an object that has a filesystem, a network stack, and one or more processes running inside it. The container is created from the image that you specify. The container is the running instance of the image.

    To run a container, you need an image. You can either pull an image from a registry or create your own image using a Dockerfile. Once you have an image, you can use the podman run command to create and start a container from that image.

    The podman run command has many options that allow you to customize the container's behavior. For example, you can specify the container's name, its networking settings, its storage driver, and more.

    For more information about the podman run command and its options, see the podman run man page.

    IMAGE

    The image to use for the container. This can be an image name, an image ID, or a reference to an image in a registry.

    If the image is not found locally, Podman will attempt to pull it from the default registry. You can specify a different registry using the --registry option.

    Rootless Containers

    Podman runs as a non-root user on most systems. This feature requires that a new enough version of shadow-utils be installed. The shadow-utils package must include the newuidmap(1) and newgidmap(1) executables.

    In order for users to run rootless, there must be an entry for their username in /etc/subuid and /etc/subgid which lists the UIDs for their user namespace.

    Rootless Podman works better if the fuse-overlayfs and slirp4netns packages are installed. The fuse-overlayfs package provides a userspace overlay storage driver, otherwise users need to use the vfs storage driver, which can be disk space expensive and less performant than other drivers.

    To enable VPN on the container, slirp4netns or pasta needs to be specified; without either, containers need to be run with the --network=host flag.

    ENVIRONMENT

    Environment variables within containers can be set using multiple different options, in the following order of precedence (later entries override earlier entries):

    • Container image: Any environment variables specified in the container image.
    • --http-proxy: By default, several environment variables are passed in from the host, such as http_proxy and no_proxy. See --http-proxy for details.
    • --env-host: Host environment of the process executing Podman is added.
    • --env-file: Any environment variables specified via env-files. If multiple files are specified, then they override each other in order of entry.
    • --env: Any environment variables specified overrides previous settings.

    Run containers and set the environment ending with a *. The trailing * glob functionality is only active when no value is specified:

    $ export ENV1=a
$ podman run --env 'ENV*' alpine env | grep ENV
ENV1=a
$ podman run --env 'ENV*=b' alpine env | grep ENV
ENV*=b

    CONMON

    When Podman starts a container it actually executes the conmon program, which then executes the OCI Runtime. Conmon is the container monitor. It is a small program whose job is to watch the primary process of the container, and if the container dies, save the exit code. It also holds open the tty of the container, so that it can be attached to later. This is what allows Podman to run in detached mode (backgrounded), so Podman can exit but conmon continues to run. Each container has their own instance of conmon. Conmon waits for the container to exit, gathers and saves the exit code, and then launches a Podman process to complete the container cleanup, by shutting down the network and storage. For more information about conmon, see the conmon(8) man page.
