الحزمة: podman

podman(1) دليل الأوامر العامة podman(1)

الاسم

podman - أداة إدارة بسيطة للحاويات والمجموعات والصور

الملخص

podman [خيارات] أمر

الوصف

Podman (مدير المجموعات) هو محرك حاويات كامل الميزات وهو أداة بسيطة بدون خادم. يوفر Podman سطر أوامر مشابه لـ Docker-CLI يسهل الانتقال من محركات الحاويات الأخرى ويسمح بإدارة المجموعات والحاويات والصور. ببساطة: alias docker=podman. يمكن تشغيل معظم أوامر Podman كمستخدم عادي، دون الحاجة إلى صلاحيات إضافية.

يستخدم Podman أداة Buildah(1) داخليًا لإنشاء صور الحاويات. تشترك كلتا الأداتين في تخزين الصور (وليس الحاويات)، وبالتالي يمكن لكل منهما استخدام أو معالجة الصور (ولكن ليس الحاويات) التي أنشأتها الأخرى.

يتم تعريف الإعدادات الافتراضية للرايات في containers.conf. تستخدم معظم إعدادات الاتصالات عن بعد ملف containers.conf الخاص بالخادم، باستثناء الحالات الموثقة في صفحات الدليل.

podman [خيارات عامة]

خيارات عامة

--cdi-spec-dir=مسار

مسار دليل مواصفات CDI (يمكن تحديده عدة مرات). المسار الافتراضي هو /etc/cdi.

--cgroup-manager=مدير

مدير cgroup لاستخدامه لحاويات cgroups. القيم المدعومة هي cgroupfs أو systemd. الافتراضي هو systemd ما لم يتم تجاوزه في ملف containers.conf.

ملاحظة: قد يتسبب تعيين هذه الراية في فشل بعض الأوامر عند استدعائها على حاويات تم إنشاؤها مسبقًا بواسطة نوع مدير cgroup الآخر. ملاحظة: مدير cgroup غير مدعوم في وضع rootless عند استخدام Cgroups الإصدار V1.

--config

موقع ملف التكوين. بشكل أساسي للتوافق مع docker، يتم دعم أجزاء المصادقة فقط من التكوين.

--conmon

مسار ثنائي conmon (المسار الافتراضي مهيأ في containers.conf)

--connection, -c

الاتصال المراد استخدامه لـ podman عن بعد، بما في ذلك أجهزة Mac و Windows (باستثناء WSL2)، (الاتصال الافتراضي مهيأ في containers.conf) يؤدي تعيين هذا الخيار إلى تبديل الخيار --remote إلى true. تستخدم الاتصالات عن بعد ملف containers.conf المحلي كافتراضي.

--events-backend=نوع

الواجهة الخلفية المستخدمة لتخزين الأحداث. القيم المسموح بها هي file، journald، و none. عند تحديد file، يتم تخزين الأحداث تحت <tmpdir>/events/events.log (انظر --tmpdir أدناه).

--help, -h

طباعة بيان الاستخدام

--hooks-dir=مسار

كل ملف *.json في المسار يقوم بتكوين خطاف (hook) لحاويات Podman. لمزيد من التفاصيل حول بناء جملة ملفات JSON ودلالات حقن الخطاف، راجع oci-hooks(5). يدعم Podman و libpod حاليًا كلا من مخططات الخطاف 1.0.0 و 0.1.0، على الرغم من أن مخطط 0.1.0 مهمل.

يمكن تعيين هذا الخيار عدة مرات؛ المسارات من الخيارات اللاحقة لها أولوية أعلى (يناقش oci-hooks(5) أولوية الدليل).

بالنسبة لشروط التعليقات التوضيحية، يستخدم libpod أي تعليقات توضيحية تم تعيينها في تكوين OCI الذي تم إنشاؤه.

بالنسبة لشروط الربط (bind-mount)، لا يتم اعتبار سوى عمليات الربط التي يطلبها المتصل صراحةً عبر --volume. لا يتم اعتبار عمليات الربط التي يدرجها libpod افتراضيًا (مثل /dev/shm).

إذا تم إلغاء تعيين --hooks-dir للمتصلين الذين لديهم صلاحيات الجذر، فإن Podman و libpod يشيران حاليًا إلى /usr/share/containers/oci/hooks.d و /etc/containers/oci/hooks.d بترتيب أولوية متزايدة. استخدام هذه الافتراضيات يعتبر مهملًا. قم بالترحيل إلى تعيين --hooks-dir بشكل صريح.

يدعم Podman و libpod حاليًا حالة precreate إضافية يتم استدعاؤها قبل عملية create الخاصة بالوقت التشغيلي. بخلاف المراحل الأخرى، التي تتلقى حالة الحاوية على مدخلاتها القياسية، تتلقى خطافات precreate تكوين وقت التشغيل المقترح على مدخلاتها القياسية. يمكنها تعديل هذا التكوين حسب ما تراه مناسبًا، وكتابة الشكل المعدل إلى مخرجاتها القياسية.

تحذير: يسمح خطاف precreate بإجراء تغييرات قوية، مثل إضافة عمليات ربط إضافية إلى تكوين وقت التشغيل. هذه القوة تجعل من السهل أيضًا كسر الأشياء. قبل الإبلاغ عن أخطاء libpod، حاول تشغيل حاوية مع تعطيل خطافات precreate لمعرفة ما إذا كانت المشكلة بسبب أحد الخطافات.

--identity=مسار

مسار ملف مفتاح SSH. إذا كان ملف المفتاح مشفرًا، سيطلب Podman من المستخدم كلمة المرور. إذا لم يتم توفير ملف مفتاح ولم يتم تحديد مستخدم، فسيستخدم Podman افتراضيًا المستخدم الذي يقوم بتشغيل أمر Podman. سيطلب Podman كلمة مرور تسجيل الدخول على الخادم البعيد.

أولوية حل قيمة المفتاح:
- القيمة الموجودة في سطر الأوامر
- متغير البيئة CONTAINER_SSHKEY، إذا تم العثور على CONTAINER_HOST
- containers.conf تستخدم الاتصالات عن بعد ملف containers.conf المحلي كافتراضي.

--imagestore=مسار

مسار تخزين الصور حيث يتم تخزين الصور. افتراضيًا، تخزن مكتبة التخزين جميع الصور في graphroot ولكن إذا تم توفير مخزن صور، فستقوم مكتبة التخزين بتخزين الصور المسحوبة حديثًا في مخزن الصور المقدم مع الاستمرار في استخدام graphroot لكل شيء آخر. إذا كان المستخدم يستخدم برنامج تشغيل overlay، فستظل الصور التي كانت جزءًا بالفعل من graphroot متاحة.

سيؤدي هذا إلى تجاوز خيار imagestore في containers-storage.conf(5)، راجع containers-storage.conf(5) لمزيد من التفاصيل.

--log-level=مستوى

تسجيل الرسائل عند المستويات المحددة وما فوقها: debug، info، warn، error، fatal أو panic (الافتراضي: warn)

--module=مسار

تحميل وحدة containers.conf(5) المحددة. يمكن أن يكون مسارًا مطلقًا أو نسبيًا. يرجى الرجوع إلى containers.conf(5) للحصول على التفاصيل.

هذه الراية غير مدعومة على العميل البعيد، بما في ذلك أجهزة Mac و Windows (باستثناء WSL2). مزيد من ملاحظة أن الراية هي راية على مستوى الجذر ويجب تحديدها قبل أي أمر فرعي لـ Podman.

--network-cmd-path=مسار

مسار ثنائي أمر slirp4netns(1) لاستخدامه لإعداد شبكة slirp4netns. إذا تم استخدام ""، فسيتم البحث عن الثنائي أولاً باستخدام خيار helper_binaries_dir في containers.conf، ثم باستخدام متغير البيئة $PATH. ملاحظة: هذا الخيار مهمل وسيتم إزالته مع Podman 6.0. استخدم خيار helper_binaries_dir في containers.conf بدلاً من ذلك.

--network-config-dir=دليل

مسار الدليل الذي توجد به ملفات تكوين الشبكة. بالنسبة للواجهة الخلفية لـ netavark، يتم استخدام "/etc/containers/networks" كجذر و "$graphroot/networks" كـ rootless. بالنسبة لواجهة CNI الخلفية، الافتراضي هو "/etc/cni/net.d" كجذر و "$HOME/.config/cni/net.d" كـ rootless. CNI مهمل وسيتم إزالته في الإصدار الرئيسي التالي من Podman 5.0 لصالح Netavark.

--out=مسار

إعادة توجيه مخرجات podman إلى المسار المحدد دون التأثير على مخرجات الحاوية أو سجلاتها. يمكن استخدام هذه المعلمة لالتقاط المخرجات من أي من أوامر podman مباشرة في ملف وتمكين كتم مخرجات podman عن طريق تحديد /dev/null كمسار. لإلغاء تسجيل الحاويات بشكل صريح، يجب استخدام خيار --log-driver.

--remote, -r

عندما يكون صحيحًا، يكون الوصول إلى خدمة Podman عن بعد. الافتراضي هو false. يمكن تعديل الإعدادات في ملف containers.conf. إذا تم تعيين متغير البيئة CONTAINER_HOST، فإن خيار --remote يأخذ القيمة true افتراضيًا.

--root=value

دليل جذر التخزين الذي يتم فيه تخزين البيانات، بما في ذلك الصور (الافتراضي: "/var/lib/containers/storage" لمعرف المستخدم 0، "$HOME/.local/share/containers/storage" للمستخدمين الآخرين). دليل الجذر الافتراضي المحدد في containers-storage.conf(5).

يتسبب تجاوز هذا الخيار في تجاهل إعدادات storage-opt في containers-storage.conf(5). يجب على المستخدم تحديد خيارات إضافية عبر العلامة --storage-opt.

--runroot=value

دليل حالة التخزين حيث يتم تخزين جميع معلومات الحالة (الافتراضي: "/run/containers/storage" لمعرف المستخدم 0، "/run/user/$UID/run" للمستخدمين الآخرين). دليل الحالة الافتراضي المحدد في containers-storage.conf(5).

--runtime=value

اسم مشغل OCI المحدد في containers.conf أو المسار المطلق للبرنامج الثنائي المتوافق مع OCI المستخدم لتشغيل الحاويات.

--runtime-flag=flag

يضيف علامات عامة لمشغل الحاوية. لسرد العلامات المدعومة، يرجى الرجوع إلى صفحات الدليل الخاصة بمشغل الحاوية المحدد (runc هو المشغل الافتراضي، صفحة الدليل التي يجب الرجوع إليها هي runc(8). عندما يتم تكوين الجهاز لـ cgroup V2، يكون المشغل الافتراضي هو crun، وصفحة الدليل التي يجب الرجوع إليها هي crun(8).).

يمكن إضافة علامات المشغل الافتراضية في containers.conf.

ملاحظة: لا تمرر البادئة -- إلى العلامة. لتمرير علامة runc --log-format json إلى podman build، يمكن أن يكون الخيار المعطى هو --runtime-flag log-format=json.

--ssh=value

يسمح هذا الخيار للمستخدم بتغيير وضع ssh، مما يعني أنه بدلاً من استخدام الوضع الافتراضي golang، يمكن بدلاً من ذلك استخدام --ssh=native لاستخدام برنامج ssh المثبت وملف التكوين المعلن في containers.conf.

--storage-driver=value

مشغل التخزين. يتم تكوين مشغل التخزين الافتراضي لمعرف المستخدم 0 في containers-storage.conf(5) في وضع غير جذري)، وهو vfs للمستخدمين غير الجذر عندما لا يكون fuse-overlayfs متاحًا. تتجاوز متغير البيئة STORAGE_DRIVER القيمة الافتراضية. يتجاوز المشغل المحدد --storage-driver كل شيء.

يتسبب تجاوز هذا الخيار في تجاهل إعدادات storage-opt في containers-storage.conf(5). يجب على المستخدم تحديد خيارات إضافية عبر العلامة --storage-opt.

--storage-opt=value

تحديد خيار لمشغل التخزين. يتم تكوين خيارات مشغل التخزين الافتراضية في containers-storage.conf(5). تتجاوز متغير البيئة STORAGE_OPTS القيمة الافتراضية. تتجاوز الخيارات المحددة --storage-opt كل شيء. حدد --storage-opt="" حتى لا يتم استخدام خيارات التخزين.

--syslog

إخراج معلومات التسجيل إلى syslog بالإضافة إلى وحدة التحكم (الافتراضي false).

على العملاء البعيدين، بما في ذلك أجهزة Mac و Windows (باستثناء WSL2)، يتم توجيه التسجيل إلى الملف $HOME/.config/containers/podman.log.

--tls-ca=path

المسار إلى ملف PEM يحتوي على حزمة سلطة الشهادات للتحقق من شهادة الخادم مقابلها.

--tls-cert=path

المسار إلى ملف PEM يحتوي على شهادة عميل TLS لتقديمها إلى الخادم. يجب أيضًا توفير --tls-key.

--tls-key=path

المسار إلى ملف PEM يحتوي على المفتاح الخاص المطابق لـ --tls-cert. يجب أيضًا توفير --tls-cert.

--tmpdir=path

المسار إلى دليل tmp، لمحتوى وقت تشغيل libpod. الافتراضي هو $XDG_RUNTIME_DIR/libpod/tmp في وضع غير جذري و /run/libpod/tmp في وضع جذري.

ملاحظة: لا يتم استخدام --tmpdir للتخزين المؤقت للصور التي تم تنزيلها. استخدم متغير البيئة TMPDIR لتغيير موقع التخزين المؤقت لصور الحاويات التي تم تنزيلها. افتراضيًا، يستخدم Podman /var/tmp.

--transient-store

يمكّن وضع تخزين مؤقت عام حيث يتم تخزين جميع بيانات تعريف الحاوية على وسائط غير دائمة (أي في الموقع المحدد بواسطة --runroot). يسمح هذا الوضع ببدء الحاويات بشكل أسرع، بالإضافة إلى ضمان حالة جديدة عند الإقلاع في حالة الإغلاق غير النظيف أو المشاكل الأخرى. ومع ذلك، فهو غير متوافق مع النموذج التقليدي حيث تستمر الحاويات عبر عمليات إعادة التشغيل.

القيمة الافتراضية لهذا محددة في containers-storage.conf(5).

--url=value

عنوان URL للوصول إلى خدمة Podman (الافتراضي من containers.conf، في وضع غير جذري unix:///run/user/$UID/podman/podman.sock أو كجذر unix:///run/podman/podman.sock). يؤدي تعيين هذا الخيار إلى تبديل الخيار --remote إلى true.

•
CONTAINER_HOST له الصيغة <schema>://[<user[:<password>]@]<host>[:<port>][<path>]

التفاصيل:
- schema هو أحد الخيارات التالية:
* ssh (الافتراضي): مقبس unix(7) محلي على host المحدد و port، يمكن الوصول إليه عبر SSH
* tcp: اتصال TCP غير مشفر وغير مصادق عليه بالمضيف والمنفذ المحددين
* unix: مقبس unix(7) محلي في المسار المحدد، أو الافتراضي للمستخدم
- user افتراضياً إما root أو المستخدم الحالي (ssh فقط)
- password ليس له قيمة افتراضية (ssh فقط)
- يجب توفير host وهو إما عنوان IP أو اسم الجهاز الذي يستضيف خدمة Podman (ssh و tcp)
- الافتراضي للمنفذ هو 22 (ssh و tcp)
- الافتراضي للمسار هو إما /run/podman/podman.sock، أو /run/user/$UID/podman/podman.sock إذا كان يعمل كغير جذري (unix)، أو يجب تحديده صراحةً (ssh)

أسبقية حل قيمة URL:
- قيمة سطر الأوامر
- متغير البيئة CONTAINER_HOST
- جدول engine.service_destinations في containers.conf، باستثناء الدليل /usr/share/containers
- unix:///run/podman/podman.sock

تستخدم الاتصالات البعيدة containers.conf المحلية بشكل افتراضي.

بعض أمثلة قيم URL بالتنسيقات الصالحة:
- unix:///run/podman/podman.sock
- unix:///run/user/$UID/podman/podman.sock
- ssh://notroot@localhost:22/run/user/$UID/podman/podman.sock
- ssh://root@localhost:22/run/podman/podman.sock
- tcp://localhost:34451
- tcp://127.0.0.1:34451

--version, -v

طباعة الإصدار

--volumepath=value

دليل وحدات التخزين حيث يتم تخزين معلومات وحدات التخزين المدمجة (الافتراضي: "/var/lib/containers/storage/volumes" لمعرف المستخدم 0، "$HOME/.local/share/containers/storage/volumes" للمستخدمين الآخرين). يمكن تجاوز مسار وحدات التخزين الافتراضي في containers.conf.

متغيرات البيئة

يمكن لـ Podman إعداد متغيرات البيئة من جدول env في [engine] في containers.conf. يمكن تجاوز هذه المتغيرات عن طريق تمرير متغيرات البيئة قبل أوامر podman.

CONTAINERS_CONF

تعيين المواقع الافتراضية لملف containers.conf

CONTAINERS_REGISTRIES_CONF

تعيين الموقع الافتراضي لملف registries.conf.

CONTAINERS_STORAGE_CONF

تعيين الموقع الافتراضي لملف storage.conf.

CONTAINER_CONNECTION

تجاوز القيمة الافتراضية لـ --connection للوصول إلى خدمة Podman. يمكّن تلقائياً الخيار --remote.

CONTAINER_HOST

تعيين القيمة الافتراضية لـ --url للوصول إلى خدمة Podman. يمكّن تلقائياً الخيار --remote.

CONTAINER_SSHKEY

تعيين المسار الافتراضي لـ --identity لملف مفتاح ssh المستخدم للوصول إلى خدمة Podman.

PODMAN_CONNECTIONS_CONF

المسار إلى الملف الذي يتم فيه تخزين الاتصالات الخاصة بالنظام والمزارع التي تم إنشاؤها باستخدام podman system connection add و podman farm add، افتراضيًا يستخدم ~/.config/containers/podman-connections.json.

STORAGE_DRIVER

تعيين القيمة الافتراضية لـ --storage-driver.

STORAGE_OPTS

تعيين القيمة الافتراضية لـ --storage-opt.

TMPDIR

تعيين موقع التخزين المؤقت لصور الحاويات التي تم تنزيلها. افتراضيًا، يستخدم Podman /var/tmp.

XDG_CONFIG_HOME

في وضع غير جذري، يتم قراءة ملفات التكوين من XDG_CONFIG_HOME عند تحديده، وإلا فإنه في دليل المستخدم تحت $HOME/.config/containers.

XDG_DATA_HOME

في وضع غير جذري، يتم سحب الصور تحت XDG_DATA_HOME عند تحديده، وإلا فإنه في دليل المستخدم تحت $HOME/.local/share/containers/storage.

XDG_RUNTIME_DIR

في وضع غير جذري، يتم تخزين بيانات التكوين المؤقتة في ${XDG_RUNTIME_DIR}/containers.

الوصول عن بعد

يمكن استخدام أمر Podman مع الخدمات عن بعد باستخدام العلامة --remote. يمكن إجراء الاتصالات باستخدام مقابس مجال Unix المحلية، أو ssh، أو مباشرة إلى مقابس tcp. عند تحديد علامة podman --remote، يتم استخدام الخيارات العامة --url، --identity، --log-level، --connection فقط.

podman(1) — Arch manual pages

NAME

podman - manage Podman containers, pods, images, and storage

SYNOPSIS

podman [global options] command [options] [args]

DESCRIPTION

Podman provides a command line interface (CLI) for managing containers and container images. It is compatible with the Docker CLI, and can be used as a drop-in replacement for Docker. Podman is daemonless, meaning that it does not require a running daemon process to manage containers. Containers are managed directly by the user running the podman command.

Podman can also run containers in rootless mode, which allows users to run containers without root privileges. This provides an additional layer of security by limiting the potential damage that a compromised container can cause.

Environment Variables

Podman respects the following environment variables:

CONTAINERS_CONF
Path to containers.conf(5).
STORAGE_CONF
Path to storage.conf(5).
XDG_CONFIG_HOME
If set, Podman looks for configuration files in $XDG_CONFIG_HOME/containers/.
XDG_DATA_HOME
If set, Podman stores container images and volumes in $XDG_DATA_HOME/containers/storage.

Remote Access

Podman can be configured to communicate with a Podman service running on a remote machine. This allows you to manage containers on a remote host from your local machine. To enable remote access, set the --remote option to true.

For more information, see the podman-remote(1) man page.

Rootless mode

Podman can be run in rootless mode, which allows users to run containers without root privileges. This is achieved by using user namespaces and subuid/subgid ranges.

When running in rootless mode, Podman requires that each user have a range of UIDs and GIDs defined in the /etc/subuid and /etc/subgid files, respectively. These ranges are used to map the UIDs and GIDs inside the container to the UIDs and GIDs of the user running the container. Containers created by a non-root user are not visible to other users and are not seen or managed by Podman running as root.

It is required to have multiple UIDS/GIDS set for a user. Be sure the user is present in the files /etc/subuid and /etc/subgid.

Execute the following commands to add the ranges to the files

$ sudo usermod --add-subuids 10000-75535 USERNAME
$ sudo usermod --add-subgids 10000-75535 USERNAME

Or just add the content manually.

$ echo USERNAME:10000:65536 >> /etc/subuid
$ echo USERNAME:10000:65536 >> /etc/subgid

See the subuid(5) and subgid(5) man pages for more information.

Note: whitespace in any row of /etc/subuid or /etc/subgid, including trailing blanks, may result in no entry failures.

Images are pulled under XDG_DATA_HOME when specified, otherwise in the home directory of the user under .local/share/containers/storage.

Currently slirp4netns or pasta is required to be installed to create a network device, otherwise rootless containers need to run in the network namespace of the host.

In certain environments like HPC (High Performance Computing), users cannot take advantage of the additional UIDs and GIDs from the /etc/subuid and /etc/subgid systems. However, in this environment, rootless Podman can operate with a single UID. To make this work, set the ignore_chown_errors option in the containers-storage.conf(5) file. This option tells Podman when pulling an image to ignore chown errors when attempting to change a file in a container image to match the non-root UID in the image. This means all files get saved as the user's UID. Note this can cause issues when running the container.

NOTE: Unsupported file systems in rootless mode

The Overlay file system (OverlayFS) is not supported with kernels prior to 5.12.9 in rootless mode. The fuse-overlayfs package is a tool that provides the functionality of OverlayFS in user namespace that allows mounting file systems in rootless environments. It is recommended to install the fuse-overlayfs package. In rootless mode, Podman automatically uses the fuse-overlayfs program as the mount_program if installed, as long as the $HOME/.config/containers/storage.conf file was not previously created. If storage.conf exists in the homedir, add mount_program = "/usr/bin/fuse-overlayfs" under [storage.options.overlay] to enable this feature.

The Network File System (NFS) and other distributed file systems (for example: Lustre, Spectrum Scale, the General Parallel File System (GPFS)) are not supported when running in rootless mode as these file systems do not understand user namespace. However, rootless Podman can make use of an NFS Homedir by modifying the $HOME/.config/containers/storage.conf to have the graphroot option point to a directory stored on local (Non NFS) storage.
