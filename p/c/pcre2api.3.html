PCRE2 - تعبيرات نمطية متوافقة مع Perl (واجهة برمجة تطبيقات محدثة)

#include <pcre2.h>

مكتبات PCRE2 8-بت، 16-بت، و 32-بت

هناك ثلاث مكتبات PCRE2، تدعم وحدات التعليمات البرمجية 8-بت، 16-بت، و 32-بت، على التوالي. ومع ذلك، هناك ملف رأس واحد فقط، pcre2.h. يحتوي هذا الملف على نماذج الدوال والتعريفات الأخرى لجميع المكتبات الثلاث. يمكن تثبيت مكتبة واحدة، أو اثنتين، أو جميع المكتبات الثلاث في وقت واحد. في أنظمة شبيهة بيونكس، تسمى المكتبات libpcre2-8 و libpcre2-16 و libpcre2-32، ويمكنها أيضًا التعايش مع مكتبات PCRE الأصلية. تأتي كل دالة من دوال PCRE2 في ثلاثة أشكال مختلفة، واحد لكل مكتبة، على سبيل المثال:


pcre2_compile_8()
pcre2_compile_16()
pcre2_compile_32()

هناك أيضًا ثلاث مجموعات مختلفة من أنواع البيانات:


PCRE2_UCHAR8، PCRE2_UCHAR16، PCRE2_UCHAR32
PCRE2_SPTR8، PCRE2_SPTR16، PCRE2_SPTR32

تحدد أنواع UCHAR وحدات التعليمات البرمجية غير الموقعة بالعرض المناسب. على سبيل المثال، عادةً ما يتم تعريف PCRE2_UCHAR16 كـ `uint16_t'. أنواع SPTR هي مؤشرات إلى ثوابت من أنواع UCHAR المكافئة، أي أنها مؤشرات إلى متجهات من وحدات التعليمات البرمجية غير الموقعة.

يتم تمرير سلاسل الأحرف إلى مكتبة PCRE2 كسلاسل من الأعداد الصحيحة غير الموقعة في وحدات التعليمات البرمجية بالعرض المناسب. قد يتم إعطاء طول السلسلة كعدد من وحدات التعليمات البرمجية، أو قد يتم تحديد السلسلة كمنتهية بصفر.

تستخدم العديد من التطبيقات عرض وحدة تعليمات برمجية واحد فقط. لراحتهم، يتم تعريف وحدات ماكرو ذات أسماء مثل pcre2_compile() و PCRE2_SPTR. تستخدم وحدات الماكرو هذه قيمة الماكرو PCRE2_CODE_UNIT_WIDTH لتوليد أسماء الدوال ووحدات الماكرو المناسبة للعرض المحدد. لا يتم تعريف PCRE2_CODE_UNIT_WIDTH افتراضيًا. يجب على التطبيق تعريفه ليكون 8 أو 16 أو 32 قبل تضمين pcre2.h للاستفادة من الأسماء العامة.

يمكن ربط التطبيقات التي تستخدم أكثر من عرض وحدة تعليمات برمجية واحد بأكثر من مكتبة PCRE2 واحدة، ولكن يجب عليها تعريف PCRE2_CODE_UNIT_WIDTH لتكون 0 قبل تضمين pcre2.h، ثم استخدام أسماء الدوال الحقيقية. أي كود سيتم تضمينه في بيئة لا يُعرف فيها قيمة PCRE2_CODE_UNIT_WIDTH يجب أن يستخدم أيضًا أسماء الدوال الحقيقية. (للأسف، لا يمكن في كود C حفظ واستعادة قيمة الماكرو.)

إذا لم يتم تعريف PCRE2_CODE_UNIT_WIDTH قبل تضمين pcre2.h، يحدث خطأ في المترجم.

عند استخدام مكتبات متعددة في تطبيق، يجب عليك توخي الحذر عند معالجة أي نمط معين لاستخدام الدوال من مكتبة واحدة فقط. على سبيل المثال، إذا كنت تريد تشغيل مطابقة باستخدام نمط تم تجميعه بواسطة pcre2_compile_16()، فيجب عليك القيام بذلك باستخدام pcre2_match_16()، وليس pcre2_match_8() أو pcre2_match_32().

في ملخصات الدوال أعلاه، وفي بقية هذا المستند والمستندات الأخرى لـ PCRE2، يتم وصف الدوال وأنواع البيانات باستخدام أسمائها العامة، بدون لاحقة _8 أو _16 أو _32.

نظرة عامة على PCRE2 API

تمتلك PCRE2 واجهة برمجة تطبيقات (API) أصلية خاصة بها، والتي تم وصفها في هذا المستند. هناك أيضًا بعض دوال الغلاف للمكتبة ذات 8 بت التي تتوافق مع واجهة برمجة تطبيقات التعبيرات المنتظمة POSIX، لكنها لا توفر الوصول إلى كل وظائف PCRE2 وهي ليست آمنة للخيوط. تم وصفها في وثائق pcre2posix. كلتا الواجهتين تعرفان مجموعة من استدعاءات دوال C.

يتم تعريف أنواع بيانات C الخاصة بواجهة برمجة التطبيقات الأصلية، ونماذج الدوال، وقيم الخيارات، ورموز الأخطاء في ملف الرأس pcre2.h، الذي يحتوي أيضًا على تعريفات لـ PCRE2_MAJOR و PCRE2_MINOR، وهما رقما الإصدار الرئيسي والثانوي للمكتبة. يمكن للتطبيقات استخدام هذه لدعم إصدارات مختلفة من PCRE2.

في بيئة Windows، إذا كنت ترغب في ربط برنامج تطبيقي بشكل ثابت بمكتبة PCRE2 غير DLL، فيجب عليك تعريف PCRE2_STATIC قبل تضمين pcre2.h.

تُستخدم الدوال pcre2_compile() و pcre2_match() لتجميع ومطابقة التعبيرات المنتظمة بطريقة متوافقة مع Perl. يتم توفير برنامج نموذجي يوضح أبسط طريقة لاستخدامها في ملف يسمى pcre2demo.c في توزيع مصدر PCRE2. يتم تقديم قائمة بهذا البرنامج في وثائق pcre2demo، وتصف وثائق pcre2sample كيفية تجميعه وتشغيله.

تتعرف دوال التجميع والمطابقة على خيارات مختلفة يتم تمريرها كبتات في وسيطة الخيارات. هناك أيضًا بعض المعلمات الأكثر تعقيدًا مثل دوال إدارة الذاكرة المخصصة وحدود الموارد التي يتم تمريرها في "سياقات" (وهي مجرد كتل ذاكرة، موصوفة أدناه). التطبيقات البسيطة لا تحتاج إلى استخدام السياقات.

دعم مترجم Just-in-time (JIT) هو ميزة اختيارية لـ PCRE2 يمكن بناؤها في بيئات الأجهزة المناسبة. إنه يسرع بشكل كبير من أداء المطابقة للعديد من الأنماط. يمكن للبرامج أن تطلب استخدامه إذا كان متاحًا عن طريق استدعاء pcre2_jit_compile() بعد تجميع نمط بنجاح بواسطة pcre2_compile(). هذا لا يفعل شيئًا إذا كان دعم JIT غير متاح.

قد تحتاج البرامج الأكثر تعقيدًا إلى استخدام الدوال المتخصصة pcre2_jit_stack_create() و pcre2_jit_stack_free() و pcre2_jit_stack_assign() للتحكم في استخدام ذاكرة كود JIT.

يتم استخدام مطابقة JIT تلقائيًا بواسطة pcre2_match() إذا كانت متاحة، ما لم يتم تعيين خيار PCRE2_NO_JIT. هناك أيضًا واجهة مباشرة لمطابقة JIT، والتي توفر أداءً محسّنًا على حساب تقليل التحقق من الصحة. تتم مناقشة الدوال الخاصة بـ JIT في وثائق pcre2jit.

يتم توفير دالة مطابقة ثانية، pcre2_dfa_match()، والتي لا تتوافق مع Perl. تستخدم هذه خوارزمية مختلفة للمطابقة. تجد الخوارزمية البديلة جميع المطابقات الممكنة (في نقطة معينة في الموضوع)، وتقوم بمسح الموضوع مرة واحدة فقط (ما لم تكن هناك تأكيدات للمظهر). ومع ذلك، فإن هذه الخوارزمية لا تعيد السلاسل الفرعية الملتقطة. يتم تقديم وصف لخوارزميتي المطابقة ومزاياها وعيوبها في وثائق pcre2matching. لا يوجد دعم JIT لـ pcre2_dfa_match().

بالإضافة إلى دوال التجميع والمطابقة الرئيسية، هناك دوال مساعدة لاستخراج السلاسل الفرعية الملتقطة من سلسلة موضوع تم مطابقته بواسطة pcre2_match(). وهي:

pcre2_substring_free() و pcre2_substring_list_free() متوفرتان أيضًا، لتحرير الذاكرة المستخدمة للسلاسل النصية المستخرجة. إذا تم استدعاء أي من هاتين الدالتين بوسيط NULL، فإن الدالة تعود فورًا دون القيام بأي شيء.

يمكن استدعاء الدالة pcre2_substitute() لمطابقة نمط وإرجاع نسخة من السلسلة النصية الموضوعة مع استبدالات للأجزاء التي تمت مطابقتها.

الدوال التي تبدأ أسماؤها بـ pcre2_serialize_ تستخدم لحفظ الأنماط المترجمة على القرص أو في أماكن أخرى، وإعادة تحميلها لاحقًا.

أخيرًا، هناك دوال لمعرفة المعلومات حول نمط مترجم (pcre2_pattern_info()) حول التكوين الذي تم بناء PCRE2 به (pcre2_config()) والذي يستخدمه.

الدوال التي تنتهي أسماؤها بـ _free() تستخدم لتحرير كتل الذاكرة من أنواع مختلفة. في جميع الحالات، إذا تم استدعاء إحدى هذه الدوال بوسيط NULL، فإنها لا تفعل شيئًا.

أطوال ومواقع السلاسل النصية

يستخدم واجهة برمجة تطبيقات PCRE2 أطوال السلاسل النصية ومواقعها في السلاسل النصية لوحدات التعليمات البرمجية في عدة أماكن. هذه القيم هي دائمًا من نوع PCRE2_SIZE، وهو نوع عدد صحيح غير موقع، محدد حاليًا دائمًا باسم size_t. أكبر قيمة يمكن تخزينها في مثل هذا النوع (وهي ~(PCRE2_SIZE)0) محجوزة كمؤشر خاص للسلاسل النصية المنتهية بـ NULL والمواقع غير المعينة. لذلك، أطول سلسلة نصية يمكن التعامل معها هي أقل بواحد من هذا الحد الأقصى. لاحظ أن أطوال السلاسل النصية تعطى دائمًا بوحدات التعليمات البرمجية. في مكتبة 8 بت فقط يكون هذا الطول هو نفسه عدد البايتات في السلسلة النصية.

أسطر جديدة

يدعم PCRE2 خمس اتفاقيات مختلفة للإشارة إلى فواصل الأسطر في السلاسل النصية: حرف CR (مسافة إرجاع) واحد، حرف LF (تغذية سطر) واحد، التسلسل المكون من حرفين CRLF، أي من الثلاثة السابقة، أو أي تسلسل سطر جديد في Unicode. تسلسلات الأسطر الجديدة في Unicode هي الثلاثة المذكورة أعلاه، بالإضافة إلى الأحرف المنفردة VT (علامة تبويب عمودية، U+000B)، FF (تغذية نموذج، U+000C)، NEL (سطر جديد، U+0085)، LS (فاصل سطر، U+2028)، PS (فاصل فقرة، U+2029).

كل من الاتفاقيات الثلاثة الأولى تستخدمها نظام تشغيل واحد على الأقل ك تسلسل سطر جديد قياسي له. عند بناء PCRE2، يمكن تحديد قيمة افتراضية. إذا لم يتم ذلك، فسيتم تعيين القيمة الافتراضية إلى LF، وهو المعيار الخاص بـ Unix. ومع ذلك، يمكن تغيير اتفاقية السطر الجديد بواسطة تطبيق عند استدعاء pcre2_compile()، أو يمكن تحديدها عن طريق نص خاص في بداية النمط نفسه؛ هذا يتجاوز أي إعدادات أخرى. انظر صفحة pcre2pattern للحصول على تفاصيل حول تسلسلات الأحرف الخاصة.

في وثائق PCRE2، تُستخدم كلمة "سطر جديد" لتعني "الحرف أو زوج الأحرف الذي يشير إلى فاصل سطر". يؤثر اختيار اتفاقية السطر الجديد على معالجة الرموز الوصفية النقطة (.), Circumflex (^), وعلامة الدولار ($)، ومعالجة تعليقات #-comments في وضع /x، وعندما يكون CRLF تسلسلاً معترفًا به لإنهاء السطر، فإن زيادة موضع المطابقة لنمط غير مثبت. هناك مزيد من التفاصيل حول هذا في القسم الخاص بخيارات pcre2_match() أدناه.

لا يؤثر اختيار اتفاقية السطر الجديد على تفسير تسلسلات الهروب \n أو \r، ولا يؤثر على ما يطابقه \R؛ هذا له اتفاقية منفصلة خاصة به.

تعدد الخيوط

في تطبيق متعدد الخيوط، من المهم فصل البيانات الخاصة بكل خيط عن البيانات التي يمكن مشاركتها بين الخيوط. كود مكتبة PCRE2 نفسه آمن للخيوط: فهو لا يحتوي على متغيرات ثابتة أو عامة. تم تصميم واجهة برمجة التطبيقات لتكون بسيطة إلى حد ما للتطبيقات غير المعتمدة على الخيوط مع ضمان قدرة التطبيقات متعددة الخيوط على استخدامها.

هناك عدة كتل مختلفة من البيانات تستخدم لتمرير المعلومات بين التطبيق ومكتبات PCRE2.

يتم إرجاع مؤشر إلى الشكل المترجم للنمط للمستخدم عند نجاح pcre2_compile(). البيانات في النمط المترجم ثابتة، ولا تتغير عند مطابقة النمط. لذلك، فهي آمنة للخيوط، أي يمكن استخدام نفس النمط المترجم بواسطة أكثر من خيط واحد في نفس الوقت. على سبيل المثال، يمكن للتطبيق ترجمة جميع أنماطه في البداية، قبل تقسيمها إلى خيوط متعددة تستخدمها. ومع ذلك، إذا كانت ميزة التحسين (JIT) قيد الاستخدام، فإنها تحتاج إلى مناطق مكدس ذاكرة منفصلة لكل خيط. انظر وثائق pcre2jit لمزيد من التفاصيل.

كتل السياق

يقدم القسم الرئيسي التالي فكرة "السياقات" التي يتم فيها استدعاء وظائف PCRE2. السياق ليس سوى مجموعة من المعلمات التي تتحكم في طريقة عمل PCRE2. تجميع عدد من المعلمات معًا في سياق هو طريقة ملائمة لتمريرها إلى دالة PCRE2 دون استخدام الكثير من الوسائط. المعلمات المخزنة في السياقات هي بمعنى ما "ميزات متقدمة" لواجهة برمجة التطبيقات. العديد من التطبيقات المباشرة لن تحتاج إلى استخدام السياقات.

في تطبيق متعدد الخيوط، إذا كانت المعلمات في السياق هي قيم لا يتم تغييرها أبدًا، فيمكن استخدام نفس السياق من قبل جميع الخيوط. ومع ذلك، إذا احتاج أي خيط إلى تغيير أي قيمة في السياق، فيجب عليه إنشاء نسخة خاصة به خاصة بالخيط.

كتل المطابقة

تحتاج دوال المطابقة إلى كتلة ذاكرة لتخزين نتائج المطابقة. يشمل ذلك تفاصيل حول ما تم مطابقته، بالإضافة إلى معلومات إضافية مثل اسم إعداد (*MARK). يجب على كل خيط توفير نسخته الخاصة من هذه الذاكرة.

سياقات PCRE2

تحتوي بعض دوال PCRE2 على الكثير من المعلمات، العديد منها يستخدم فقط للتطبيقات المتخصصة، على سبيل المثال، تلك التي تستخدم إدارة ذاكرة مخصصة أو جداول أحرف غير قياسية. للحفاظ على قوائم وسائط الدالة بحجم معقول، وفي نفس الوقت للحفاظ على واجهة برمجة التطبيقات قابلة للتوسيع، يتم تمرير المعلمات "غير الشائعة" إلى بعض الدوال في سياق بدلاً من تمريرها مباشرة. السياق هو مجرد كتلة ذاكرة تحتفظ بقيم المعلمات. التطبيقات التي لا تحتاج إلى تعديل أي من معلمات السياق يمكنها تمرير NULL عندما يكون مؤشر السياق مطلوبًا.

هناك ثلاثة أنواع مختلفة من السياقات: سياق عام ذو صلة بالعديد من عمليات PCRE2، وسياق وقت الترجمة، وسياق وقت المطابقة.

السياق العام

في الوقت الحالي، يحتوي هذا السياق فقط على مؤشرات إلى (و بيانات لـ) وظائف إدارة الذاكرة الخارجية التي يتم استدعاؤها من عدة أماكن في مكتبة PCRE2. تمت تسمية السياق 'general' بدلاً من 'memory' تحديدًا لأنه في المستقبل قد تضاف حقول أخرى. إذا كنت لا ترغب في تقديم وظائف إدارة الذاكرة المخصصة الخاصة بك، فلا داعي للقلق بشأن السياق العام. يتم إنشاء سياق عام عن طريق:

pcre2_general_context *pcre2_general_context_create(
  void *(*private_malloc)(PCRE2_SIZE, void *),
  void (*private_free)(void *, void *), void *memory_data);

يشير مؤشران للدالة إلى وظائف إدارة الذاكرة المخصصة، والتي تكون نماذجها الأولية:


void *private_malloc(PCRE2_SIZE, void *);
void private_free(void *, void *);

This section describes the facilities for controlling the matching process via a match context.

Optimizations

In the interests of speed, PCRE2 performs certain optimizations when it is starting a match. For example, when matching an unanchored pattern, it may skip over sections of the subject string if it can deduce that a match cannot start there. The effect of these optimizations can depend on the way the pattern is written, and sometimes it is useful to know how they work. Consider the pattern


(*COMMIT)A

If the subject string is "ABCD", PCRE2 finds the "A" at the start of the subject. Because the pattern is not anchored, PCRE2 runs the first match attempt starting from the beginning of the subject. The first character of the subject is "A". The pattern requires an "A" followed by (*COMMIT). The (*COMMIT) item ensures that if this match attempt succeeds, no further attempts are made. In this case, it matches "A", so the overall result is a match starting at offset 0. The subject string is "ABCD" and the pattern is "A". The match succeeds.

Now, consider the subject string "BCDA". PCRE2 scans the subject string looking for an "A". It finds one at offset 3. It then tries to match the pattern starting from offset 3. The pattern requires an "A", which is found. Then it encounters (*COMMIT). This means that the starting position must be the beginning of the match. The match started at offset 3, so this condition is met. The match succeeds, and the result is a match starting at offset 3. The subject string is "BCDA" and the pattern is "A". The match succeeds.

Now, consider the subject string "ZABC". PCRE2 scans the subject string, looking for the first character of the pattern, which is "A". It finds it at offset 1. It tries to match starting at offset 1. The pattern requires an "A", which is found. Then it encounters (*COMMIT). This means that the match must start at the current position. Since the match started at offset 1, this condition is met. The match succeeds, and the result is a match starting at offset 1.

The behavior described above is for the default matching function, pcre2_match(). When using the DFA matching function, pcre2_dfa_match(), PCRE2 does not scan along the subject string. Instead, it tries to match starting at every possible position. When the pattern is (*COMMIT)A, and the subject is "ZABC", the first attempt is made at offset 0. The character is "Z", which does not match "A". The next attempt is made at offset 1. The character is "A", which matches "A". The (*COMMIT) item is encountered. This requires that the match attempt starts at the current position. Since the match attempt started at offset 1, this condition is met. The match succeeds, starting at offset 1. The subject string is "ZABC" and the pattern is (*COMMIT)A. The match succeeds.

The difference in behaviour between pcre2_match() and pcre2_dfa_match() is related to the presence or absence of start-up optimizations. Let's consider a slightly different pattern, (*COMMIT)A, matched against the subject "XAXA". The pattern is anchored.

With pcre2_match(), the pattern is anchored, so the match must start at the beginning of the subject string. The first character is "X", which does not match "A". The match fails.

With pcre2_dfa_match(), the pattern is anchored, so the match must start at the beginning of the subject string. The first character is "X", which does not match "A". The match fails.

Now, let's remove the anchor, so the pattern is just (*COMMIT)A. Subject is "XAXA".

With pcre2_match(), the starting optimization finds the first "A" at offset 1. It runs the first match attempt from there. The (*COMMIT) item means that the pattern must match the current starting position, which in this case, it does. However, if the same match is run without start-up optimizations, the initial scan along the subject string does not happen. The first match attempt is run starting from "X" (offset 0) and when this fails, (*COMMIT) prevents any further matches being tried, so the overall result is "no match".

Another start-up optimization makes use of a minimum length for a matching subject, which is recorded when possible. Consider the pattern


(*MARK:1)B(*MARK:2)(X|Y)

The minimum length for a match is two characters. If the subject is "XXBB", the "starting character" optimization skips "XX", then tries to match "BB", which is long enough. In the process, (*MARK:2) is encountered and remembered. When the match attempt fails, the next "B" is found, but there is only one character left, so there are no more attempts, and "no match" is returned with the "last mark seen" set to "2". Without start-up optimizations, however, matches are tried at every possible starting position, including at the end of the subject, where (*MARK:1) is encountered, but there is no "B", so the "last mark seen" that is returned is "1". In this case, the optimizations do not affect the overall match result, which is still "no match", but they do affect the auxiliary information that is returned.

The match context

A match context is required if you want to:


Set up a callout function
Set an offset limit for matching an unanchored pattern
Change the limit on the amount of heap used when matching
Change the backtracking match limit
Change the backtracking depth limit
Set custom memory management specifically for the match

If none of these apply, just pass NULL as the context argument of pcre2_match(), pcre2_dfa_match(), or pcre2_jit_match().

A match context is created, copied, and freed by the following functions:

pcre2_match_context *pcre2_match_context_create(
  pcre2_general_context *gcontext);

pcre2_match_context *pcre2_match_context_copy(
  pcre2_match_context *mcontext);

void pcre2_match_context_free(pcre2_match_context *mcontext);

A match context is created with default values for its parameters. These can be changed by calling the following functions, which return 0 on success, or PCRE2_ERROR_BADDATA if invalid data is detected.

int pcre2_set_callout(pcre2_match_context *mcontext,
  int (*callout_function)(pcre2_callout_block *, void *),
  void *callout_data);

This sets up a callout function for PCRE2 to call at specified points during a matching operation. Details are given in the pcre2callout documentation.

int pcre2_set_substitute_callout(pcre2_match_context *mcontext,
  int (*callout_function)(pcre2_substitute_callout_block *, void *),
  void *callout_data);

This sets up a callout function for PCRE2 to call after each substitution made by pcre2_substitute(). Details are given in the section entitled "Creating a new string with substitutions" below.

int pcre2_set_substitute_case_callout(pcre2_match_context *mcontext,
  PCRE2_SIZE (*callout_function)(PCRE2_SPTR, PCRE2_SIZE,
                                 PCRE2_UCHAR *, PCRE2_SIZE,
                                 int, void *),
  void *callout_data);

This sets up a callout function for PCRE2 to call when performing case transformations inside pcre2_substitute(). Details are given in the section entitled "Creating a new string with substitutions" below.

int pcre2_set_offset_limit(pcre2_match_context *mcontext,
  PCRE2_SIZE value);

The offset_limit parameter limits how far an unanchored search can advance in the subject string. The default value is PCRE2_UNSET. The pcre2_match() and pcre2_dfa_match() functions return PCRE2_ERROR_NOMATCH if a match with a starting point before or at the given offset is not found. The pcre2_substitute() function makes no more substitutions.

For example, if the pattern /abc/ is matched against "123abc" with an offset limit less than 3, the result is PCRE2_ERROR_NOMATCH. A match can never be found if the startoffset argument of pcre2_match(), pcre2_dfa_match(), or pcre2_substitute() is greater than the offset limit set in the match context.

When using this facility, you must set the PCRE2_USE_OFFSET_LIMIT option when calling pcre2_compile() so that when JIT is in use, different code can be compiled. If a match is started with a non-default match limit when PCRE2_USE_OFFSET_LIMIT is not set, an error is generated.

The offset limit facility can be used to track progress when searching large subject strings or to limit the extent of global substitutions. See also the PCRE2_FIRSTLINE option, which requires a match to start before or at the first newline that follows the start of matching in the subject. If this is set with an offset limit, a match must occur in the first line and also within the offset limit. In other words, whichever limit comes first is used.

int pcre2_set_heap_limit(pcre2_match_context *mcontext,
  uint32_t value);

The heap_limit parameter specifies, in units of kibibytes (1024 bytes), the maximum amount of heap memory that pcre2_match() may use to hold backtracking information when running an interpretive match. This limit also applies to pcre2_dfa_match(), which may use the heap when processing patterns with a lot of nested pattern recursion or lookarounds or atomic groups. This limit does not apply to matching with the JIT optimization, which has its own memory control arrangements (see the pcre2jit documentation for more details). If the limit is reached, the negative error code PCRE2_ERROR_HEAPLIMIT is returned. The default limit can be set when PCRE2 is built; if it is not, the default is set very large and is essentially unlimited.

A value for the heap limit may also be supplied by an item at the start of a pattern of the form


(*LIMIT_HEAP=ddd)

where ddd is a decimal number. However, such a setting is ignored unless ddd is less than the limit set by the caller of pcre2_match() or, if no such limit is set, less than the default.

The pcre2_match() function always needs some heap memory, so setting a value of zero guarantees a "heap limit exceeded" error. Details of how pcre2_match() uses the heap are given in the pcre2perform documentation.

For pcre2_dfa_match(), a vector on the system stack is used when processing pattern recursions, lookarounds, or atomic groups, and only if this is not big enough is heap memory used. In this case, setting a value of zero disables the use of the heap.

int pcre2_set_match_limit(pcre2_match_context *mcontext,
  uint32_t value);

The match_limit parameter provides a means of preventing PCRE2 from using up too many computing resources when processing patterns that are not going to match, but which have a very large number of possibilities in their search trees. The classic example is a pattern that uses nested unlimited repeats.

There is an internal counter in pcre2_match() that is incremented each time round its main matching loop. If this value reaches the match limit, pcre2_match() returns the negative value PCRE2_ERROR_MATCHLIMIT. This has the effect of limiting the amount of backtracking that can take place. For patterns that are not anchored, the count restarts from zero for each position in the subject string. This limit also applies to pcre2_dfa_match(), though the counting is done in a different way.

When pcre2_match() is called with a pattern that was successfully processed by pcre2_jit_compile(), the way in which matching is executed is entirely different. However, there is still the possibility of runaway matching that goes on for a very long time, and so the match_limit value is also used in this case (but in a different way) to limit how long the matching can continue.

The default value for the limit can be set when PCRE2 is built; the default is 10 million, which handles all but the most extreme cases. A value for the match limit may also be supplied by an item at the start of a pattern of the form


(*LIMIT_MATCH=ddd)

where ddd is a decimal number. However, such a setting is ignored unless ddd is less than the limit set by the caller of pcre2_match() or pcre2_dfa_match() or, if no such limit is set, less than the default.

int pcre2_set_depth_limit(pcre2_match_context *mcontext,
  uint32_t value);

This parameter limits the depth of nested backtracking in pcre2_match(). Each time a nested backtracking point is passed, a new memory frame is used to remember the state of matching at that point. Thus, this parameter indirectly limits the amount of memory that is used in a match. However, because the size of each memory frame depends on the number of capturing parentheses, the actual memory limit varies from pattern to pattern. This limit was more useful in versions before 10.30, where function recursion was used for backtracking.

The depth limit is not relevant, and is ignored, when matching is done using JIT compiled code. However, it is supported by pcre2_dfa_match(), which uses it to limit the depth of nested internal recursive function calls that implement atomic groups, lookaround assertions, and pattern recursions. This limits, indirectly, the amount of system stack that is used. It was more useful in versions before 10.32, when stack memory was used for local workspace vectors for recursive function calls. From version 10.32, only local variables are allocated on the stack and as each call uses only a few hundred bytes, even a small stack can support quite a lot of recursion.

If the depth of internal recursive function calls is great enough, local workspace vectors are allocated on the heap from version 10.32 onwards, so the depth limit also indirectly limits the amount of heap memory that is used. A recursive pattern such as /(.(?2))((?1)|)/, when matched to a very long string using pcre2_dfa_match(), can use a great deal of memory. However, it is probably better to limit heap usage directly by calling pcre2_set_heap_limit().

Compile-time options

The option bits that can be set in a compile context by calling the pcre2_set_compile_options() function are as follows:


PCRE2_AUTO_CALLOUT

This option causes callouts to be called more often than they might be if it is not set. PCRE2 has a number of optimizations that can cause callouts to be skipped, for example, if a pattern starts with a callout followed by an optional item, the callout might be skipped if the optional item is not present. Auto-callouts are only ever generated by internal code that cannot be reached in optimized code. In particular, PCRE2's optimizations may mean that callouts inside groups that contain nothing a+ that can never be successful. However, if callouts are in use, auto-possessification means that some callouts are never taken. You can set this option if you want the matching functions to do a full unoptimized search and run all the callouts, but it is mainly provided for testing purposes.

If a compile context is available, it is recommended to use pcre2_set_optimize() with the directive PCRE2_AUTO_POSSESS_OFF rather than the compile option PCRE2_NO_AUTO_POSSESS. Note that PCRE2_NO_AUTO_POSSESS takes precedence over the pcre2_set_optimize() optimization directives PCRE2_AUTO_POSSESS and PCRE2_AUTO_POSSESS_OFF.


PCRE2_NO_DOTSTAR_ANCHOR

If this (deprecated) option is set, it disables an optimization that is applied when .* is the first significant item in a top-level branch of a pattern, and all the other branches also start with .* or with \A or \G or ^. The optimization is automatically disabled for .* if it is inside an atomic group or a capture group that is the subject of a backreference, or if the pattern contains (*PRUNE) or (*SKIP). When the optimization is not disabled, such a pattern is automatically anchored if PCRE2_DOTALL is set for all the .* items and PCRE2_MULTILINE is not set for any ^ items. Otherwise, the fact that any match must start either at the start of the subject or following a newline is remembered. Like other optimizations, this can cause callouts to be skipped. (If a compile context is available, it is recommended to use pcre2_set_optimize() with the directive PCRE2_DOTSTAR_ANCHOR_OFF instead.)


PCRE2_NO_START_OPTIMIZE

This is an option whose main effect is at matching time. It does not change what pcre2_compile() generates, but it does affect the output of the JIT compiler. Setting this option is equivalent to calling pcre2_set_optimize() with the directive parameter set to PCRE2_START_OPTIMIZE_OFF.

There are a number of optimizations that may occur at the start of a match, in order to speed up the process. For example, if it is known that an unanchored match must start with a specific code unit value, the matching code searches the subject for that value, and fails immediately if it cannot find it, without actually running the main matching function. The start-up optimizations are in effect a pre-scan of the subject that takes place before the pattern is run.

Disabling the start-up optimizations may cause performance to suffer. However, this may be desirable for patterns which contain callouts or items such as (*COMMIT) and (*MARK). See the above description of PCRE2_START_OPTIMIZE_OFF for further details.


PCRE2_NO_UTF_CHECK

When PCRE2_UTF is set, the validity of the pattern as a UTF string is automatically checked. There are discussions about the validity of UTF-8 strings, UTF-16 strings, and UTF-32 strings in the pcre2unicode document. If an invalid UTF sequence is found, pcre2_compile() returns a negative error code.

If you know that your pattern is a valid UTF string, and you want to skip this check for performance reasons, you can set the PCRE2_NO_UTF_CHECK option. When it is set, the effect of passing an invalid UTF string as a pattern is undefined. It may cause your program to crash or loop.

Note that this option can also be passed to pcre2_match() and pcre2_dfa_match(), to suppress UTF validity checking of the subject string.

Note also that setting PCRE2_NO_UTF_CHECK at compile time does not disable the error that is given if an escape sequence for an invalid Unicode code point is encountered in the pattern. In particular, the so-called "surrogate" code points (0xd800 to 0xdfff) are invalid. If you want to allow escape sequences such as \x{d800} you can set the PCRE2_EXTRA_ALLOW_SURROGATE_ESCAPES extra option, as described in the section entitled "Extra compile options" below. However, this is possible only in UTF-8 and UTF-32 modes, because these values are not representable in UTF-16.


PCRE2_UCP

This option has two effects. Firstly, it change the way PCRE2 processes \B, \b, \D, \d, \S, \s, \W, \w, and some of the POSIX character classes. By default, only ASCII characters are recognized, but if PCRE2_UCP is set, Unicode properties are used to classify characters. There are some PCRE2_EXTRA options (see below) that add finer control to this behaviour. More details are given in the section on generic character types in the pcre2pattern page.

The second effect of PCRE2_UCP is to force the use of Unicode properties for upper/lower casing operations, even when PCRE2_UTF is not set. This makes it possible to process strings in the 16-bit UCS-2 code. This option is available only if PCRE2 has been compiled with Unicode support (which is the default).

The PCRE2_EXTRA_CASELESS_RESTRICT option (see above) restricts caseless matching such that ASCII characters match only ASCII characters and non-ASCII characters match only non-ASCII characters. The PCRE2_EXTRA_TURKISH_CASING option (see above) alters the matching of the 'i' characters to follow their behaviour in Turkish and Azeri languages. For further details on PCRE2_EXTRA_CASELESS_RESTRICT and PCRE2_EXTRA_TURKISH_CASING, see the pcre2unicode page.


PCRE2_UNGREEDY

This option inverts the "greediness" of the quantifiers so that they are not greedy by default, but become greedy if followed by "?". It is not compatible with Perl. It can also be set by a (?U) option setting within the pattern.


PCRE2_USE_OFFSET_LIMIT

This option must be set for pcre2_compile() if pcre2_set_offset_limit() is going to be used to set a non-default offset limit in a match context for matches that use this pattern. An error is generated if an offset limit is set without this option. For more details, see the description of pcre2_set_offset_limit() in the section that describes match contexts. See also the PCRE2_FIRSTLINE option above.


PCRE2_UTF

This option causes PCRE2 to regard both the pattern and the subject strings that are subsequently processed as strings of UTF characters instead of single-code-unit strings. It is available when PCRE2 is built to include Unicode support (which is the default). If Unicode support is not available, the use of this option provokes an error. Details of how PCRE2_UTF changes the behaviour of PCRE2 are given in the pcre2unicode page. In particular, note that it changes the way PCRE2_CASELESS works.

Extra compile options

The option bits that can be set in a compile context by calling the pcre2_set_compile_extra_options() function are as follows:


PCRE2_EXTRA_ALLOW_LOOKAROUND_BSK

Since release 10.38 PCRE2 has forbidden the use of \K within lookaround assertions, following Perl's lead. This option is provided to re-enable the previous behaviour (act in positive lookarounds, ignore in negative ones) in case anybody is relying on it.


PCRE2_EXTRA_ALLOW_SURROGATE_ESCAPES

This option applies when compiling a pattern in UTF-8 or UTF-32 mode. It is forbidden in UTF-16 mode, and ignored in non-UTF modes. Unicode "surrogate" code points in the range 0xd800 to 0xdfff are used in pairs in UTF-16 to encode code points with values in the range 0x10000 to 0x10ffff. The surrogates cannot therefore be represented in UTF-16. They can be represented in UTF-8 and UTF-32, but are defined as invalid code points, and cause errors if encountered in a UTF-8 or UTF-32 string that is being checked for validity by PCRE2.

These values also cause errors if encountered in escape sequences such as \x{d912} within a pattern. However, it seems that some applications, when using PCRE2 to check for unwanted characters in UTF-8 strings, explicitly test for the surrogates using escape sequences. The PCRE2_NO_UTF_CHECK option does not disable the error that occurs, because it applies only to the testing of input strings for UTF validity.

If the extra option PCRE2_EXTRA_ALLOW_SURROGATE_ESCAPES is set, surrogate code point values in UTF-8 and UTF-32 patterns no longer provoke errors and are incorporated in the compiled pattern. However, they can only match subject characters if the matching function is called with PCRE2_NO_UTF_CHECK set.


PCRE2_EXTRA_ALT_BSUX

The original option PCRE2_ALT_BSUX causes PCRE2 to process \U, \u, and \x in the way that ECMAscript (aka JavaScript) does. Additional functionality was defined by ECMAscript 6; setting PCRE2_EXTRA_ALT_BSUX has the effect of PCRE2_ALT_BSUX, but in addition it recognizes \u{hhh..} as a hexadecimal character code, where hhh.. is any number of hexadecimal digits.


PCRE2_EXTRA_ASCII_BSD

This option forces \d to match only ASCII digits, even when PCRE2_UCP is set. It can be changed within a pattern by means of the (?aD) option setting.


PCRE2_EXTRA_ASCII_BSS

This option forces \s to match only ASCII space characters, even when PCRE2_UCP is set. It can be changed within a pattern by means of the (?aS) option setting.


PCRE2_EXTRA_ASCII_BSW

This option forces \w to match only ASCII word characters, even when PCRE2_UCP is set. It can be changed within a pattern by means of the (?aW) option setting.


PCRE2_EXTRA_ASCII_DIGIT

This option forces the POSIX character classes [:digit:] and [:xdigit:] to match only ASCII digits, even when PCRE2_UCP is set. It can be changed within a pattern by means of the (?aT) option setting.


PCRE2_EXTRA_ASCII_POSIX

This option forces all the POSIX character classes, including [:digit:] and [:xdigit:], to match only ASCII characters, even when PCRE2_UCP is set. It can be changed within a pattern by means of the (?aP) option setting, but note that this also sets PCRE2_EXTRA_ASCII_DIGIT in order to ensure that (?-aP) unsets all ASCII restrictions for POSIX classes.


PCRE2_EXTRA_BAD_ESCAPE_IS_LITERAL

This is a dangerous option. Use with care. By default, an unrecognized escape such as \j or a malformed one such as \x{2z} causes a compile-time error when detected by pcre2_compile(). Perl is somewhat inconsistent in handling such items: for example, \j is treated as a literal "j", and non-hexadecimal digits in \x{} are just ignored, though warnings are given in both cases if Perl's warning switch is enabled. However, a malformed octal number after \o{ always causes an error in Perl.

If the PCRE2_EXTRA_BAD_ESCAPE_IS_LITERAL extra option is passed to pcre2_compile(), all unrecognized or malformed escape sequences are treated as single characters.

PCRE2 EXTENDED OPTIONS

There are a number of additional options that can be passed to pcre2_compile() via the compile context. These are used to control various aspects of PCRE2's behaviour.


PCRE2_EXTRA_ALLOW_LOOKAROUND

This option is implicitly set if the PCRE2_EXTENDED option is set. It permits the use of lookahead and lookbehind assertions, which are otherwise disabled when PCRE2_EXTENDED is set.


PCRE2_EXTRA_ALT_VERBNAME

When the PCRE2_EXTENDED option is set, the verbosity information produced by the (*VERB...) pseudo-escape is given an alternative, more compact, format. This option can be changed within a pattern by the (*ALT_VERBNAME) or (?V) option settings.


PCRE2_EXTRA_ASM_LABEL_WORDS

When PCRE2_JIT is enabled, and PCRE2_EXTENDED is set, this option causes the generated assembly code to include labels for various internal operations, aiding debugging. It can be changed within a pattern by the (*ASM_LABEL_WORDS) or (?W) option settings.


PCRE2_EXTRA_COMPILE_ONLY

This option is provided for use by tools that build PCRE2 extensions. It causes the pattern to be compiled, but without the final analysis phase that is normally performed. This is faster, but the compiled pattern may not be optimized as well as usual.


PCRE2_EXTRA_DEBUG

This option is provided for debugging the PCRE2 library itself. When set, extra diagnostic information is printed during the compilation and matching phases. The information depends on the specific debugging hooks enabled at compile time.


PCRE2_EXTRA_DOTSTAR_ newNode

This option is provided for debugging the PCRE2 library itself. When set, extra diagnostic information is printed during the compilation and matching phases. The information depends on the specific debugging hooks enabled at compile time.


PCRE2_EXTRA_ESCAPED_CR_IS_LF

There are some legacy applications where the escape sequence \r in a pattern is expected to match a newline. If this option is set, \r in a pattern is converted to \n so that it matches a LF (linefeed) instead of a CR (carriage return) character. The option does not affect a literal CR in the pattern, nor does it affect CR specified as an explicit code point such as \x{0D}.


PCRE2_EXTRA_ESCAPED_EXTENSION_IS_UNICODE

When PCRE2_UTF is set, this option allows the sequence \uXXXX and \UXXXXXXXX to be used for matching Unicode characters. These are normally treated as literals.


PCRE2_EXTRA_ESCAPED_METACHBAR_IS_UNICODE

This option changes the interpretation of the metacharacter | when it is escaped. Normally, \| is treated as a literal vertical bar. If this option is set, and PCRE2_UTF is also set, then \| is treated as a Unicode character U+007C, which is equivalent to a literal vertical bar.


PCRE2_EXTRA_LITERAL_COMMENTS

Normally, when PCRE2_EXTENDED is set, characters following # are treated as comments and ignored. If this option is set, the # character is treated as a literal character, and comments are disabled. This option can be changed within a pattern by the (*LITERAL_COMMENTS) or (?#) option settings.


PCRE2_EXTRA_MATCH_END

This option is provided for use by the -l option of pcre2grep. It causes the pattern only to match at the end of the subject string. This is achieved by automatically inserting the code for "(?:)" at the end of the compiled pattern. This option can be used with PCRE2_LITERAL.


PCRE2_EXTRA_MATCH_LINE

This option is provided for use by the -x option of pcre2grep. It causes the pattern only to match complete lines. This is achieved by automatically inserting the code for "^(?:" at the start of the compiled pattern and ")$" at the end. Thus, when PCRE2_MULTILINE is set, the matched line may be in the middle of the subject string. This option can be used with PCRE2_LITERAL.


PCRE2_EXTRA_MATCH_WORD

This option is provided for use by the -w option of pcre2grep. It causes the pattern only to match strings that have a word boundary at the start and the end. This is achieved by automatically inserting the code for "\b(?:" at the start of the compiled pattern and ")\b" at the end. The option may be used with PCRE2_LITERAL. However, it is ignored if PCRE2_EXTRA_MATCH_LINE is also set.


PCRE2_EXTRA_METACHOOSE

This option is provided for debugging. When set, the pattern compiler recognizes the pseudo-escape sequence (*METACHOOSE:n) where n is a decimal number. This is used to test the recursive descent analyser. It has no effect other than to set an internal flag.


PCRE2_EXTRA_NEWLINE_CR

If this option is set, only CR characters are recognized as newlines. This overrides the default newline setting.


PCRE2_EXTRA_NEWLINE_LF

If this option is set, only LF characters are recognized as newlines. This overrides the default newline setting.


PCRE2_EXTRA_NO_AUTO_POSSESSIVE

Normally, PCRE2 automatically converts possessive quantifiers (e.g. *+, ++, ?+) into auto-possessive form when PCRE2_EXTENDED is set. This option disables that behaviour. It can be changed within a pattern by the (*NO_AUTO_POSSESSIVE) or (?na) option settings.


PCRE2_EXTRA_NO_UTF8_CHECK

This option disables the validity check for UTF-8 strings when PCRE2_UTF is set. This can speed up matching slightly, but it means that invalid UTF-8 sequences might be matched. It is not recommended for general use.


PCRE2_EXTRA_NUMERIC_CALLOUTS

When the PCRE2_EXTENDED option is set, the callout pseudo-escape sequence (*CALLOUT:n) causes a callout to be made with the integer value n. This option changes the interpretation to use only numeric arguments.


PCRE2_EXTRA_PCRE1_COMPAT_ NEWLINE

This option makes the newline interpretation of PCRE1 the default. In PCRE1, newlines were always recognised as CR or LF. This option is therefore equivalent to setting both PCRE2_EXTRA_NEWLINE_CR and PCRE2_EXTRA_NEWLINE_LF.


PCRE2_EXTRA_PCRE1_MATCH_LINE

This option mimics the behaviour of PCRE1 when the --match-line option is used. It causes the pattern only to match complete lines. This is achieved by automatically inserting the code for "^(?:" at the start of the compiled pattern and ")$" at the end. This option can be used with PCRE2_LITERAL.


PCRE2_EXTRA_PCRE1_MATCH_WORD

This option mimics the behaviour of PCRE1 when the --match-word option is used. It causes the pattern only to match strings that have a word boundary at the start and the end. This is achieved by automatically inserting the code for "\b(?:" at the start of the compiled pattern and ")\b" at the end. The option may be used with PCRE2_LITERAL. However, it is ignored if PCRE2_EXTRA_MATCH_LINE is also set.


PCRE2_EXTRA_PERL_CLASSES

When PCRE2_UTF is set, this option causes Perl-compatible character classes (such as \w, \d, \s) to be interpreted using Unicode properties instead of the default PCRE2 Unicode properties. This is a subtle difference that affects some characters. This option can be changed within a pattern by the (*PERL_CLASSES) or (?P) option settings.


PCRE2_EXTRA_REPLACE_BACKSLASH_ESCAPES

When PCRE2_LITERAL is set, escape sequences in the pattern are treated as literals. This option modifies that behaviour, causing backslash escapes such as \n and \t to be converted into their corresponding ASCII characters (LF and TAB, respectively). Other backslash escapes are treated as literals. This option can be changed within a pattern by the (*REPLACE_BACKSLASH_ESCAPES) or (?r) option settings.


PCRE2_EXTRA_STRICT_GROUP_NUMBERS

When PCRE2_EXTENDED is set, this option ensures that group numbers are strictly sequential. If a group is empty or skipped, it will cause a compilation error. This option can be changed within a pattern by the (*STRICT_GROUP_NUMBERS) or (?&n) option settings.


PCRE2_EXTRA_UNICODE_ESCAPES

When PCRE2_UTF is set, this option allows the use of Unicode escape sequences such as \uXXXX and \UXXXXXXXX. These are normally treated as literals.


PCRE2_EXTRA_USE_VARSUBGROUP

This option enables the use of the (*VARSUBGROUP) construct within a pattern. This construct allows for variable substitution within subpatterns. It is intended for use with external matching functions that can provide values for the variables.


PCRE2_EXTRA_UTF8_ PROPERTIES

When PCRE2_UTF is set, this option causes the pattern compiler to use the Unicode character properties for \w, \d, and \s, instead of the default ASCII-based properties. This option can be changed within a pattern by the (*UTF8_PROPERTIES) or (?U) option settings.


PCRE2_EXTRA_WHOLE_LINE

This option is provided for use by the -w option of pcre2grep. It causes the pattern only to match complete lines. This is achieved by automatically inserting the code for "^(?:" at the start of the compiled pattern and ")$" at the end. Thus, when PCRE2_MULTILINE is set, the matched line may be in the middle of the subject string. This option can be used with PCRE2_LITERAL.


PCRE2_EXTRA_WORD_BOUNDARY

This option is provided for use by the -w option of pcre2grep. It causes the pattern only to match strings that have a word boundary at the start and the end. This is achieved by automatically inserting the code for "\b(?:" at the start of the compiled pattern and ")\b" at the end. The option may be used with PCRE2_LITERAL. However, it is ignored if PCRE2_EXTRA_MATCH_LINE is also set.

PCRE2_LITERAL

When this option is set, the pattern is treated as a sequence of literal characters. This means that metacharacters such as ., *, +, ?, ^, $, [, ], (, ), {, }, |, \, and so on, are treated as literal characters and not as special metacharacters. Any backslash escapes are also treated as literals, e.g. \n is treated as a literal backslash followed by the letter n. The only exception is the sequence \X where X is one of the characters that would normally be treated as a metacharacter. In this case, \X is treated as the literal character X. For example, \. is treated as a literal dot. This option is useful for matching strings that contain a lot of metacharacters.

Setting this option means that typos in patterns may go undetected and have unexpected results. Also note that a sequence such as [\N{] is interpreted as a malformed attempt at [\N{...}] and so is treated as [N{] whereas [\N] gives an error because an unqualified \N is a valid escape sequence but is not supported in a character class. To reiterate: this is a dangerous option. Use with great care.


PCRE2_EXTRA_CASELESS_RESTRICT

When either PCRE2_UCP or PCRE2_UTF is set, caseless matching follows Unicode rules, which allow for more than two cases per character. There are two case-equivalent character sets that contain both ASCII and non-ASCII characters. The ASCII letter S is case-equivalent to U+017f (long S) and the ASCII letter K is case-equivalent to U+212a (Kelvin sign). This option disables recognition of case-equivalences that cross the ASCII/non-ASCII boundary. In a caseless match, both characters must either be ASCII or non-ASCII. The option can be changed within a pattern by the (*CASELESS_RESTRICT) or (?r) option settings.


PCRE2_EXTRA_ESCAPED_CR_IS_LF

There are some legacy applications where the escape sequence \r in a pattern is expected to match a newline. If this option is set, \r in a pattern is converted to \n so that it matches a LF (linefeed) instead of a CR (carriage return) character. The option does not affect a literal CR in the pattern, nor does it affect CR specified as an explicit code point such as \x{0D}.


PCRE2_EXTRA_MATCH_LINE

This option is provided for use by the -x option of pcre2grep. It causes the pattern only to match complete lines. This is achieved by automatically inserting the code for "^(?:" at the start of the compiled pattern and ")$" at the end. Thus, when PCRE2_MULTILINE is set, the matched line may be in the middle of the subject string. This option can be used with PCRE2_LITERAL.


PCRE2_EXTRA_MATCH_WORD

This option is provided for use by the -w option of pcre2grep. It causes the pattern only to match strings that have a word boundary at the start and the end. This is achieved by automatically inserting the code for "\b(?:" at the start of the compiled pattern and ")\b" at the end. The option may be used with PCRE2_LITERAL. However, it is ignored if PCRE2_EXTRA_MATCH_LINE is also set.


PCRE2_EXTRA_NO_BS0

If this option is set (note that its final character is the digit 0) it locks out the use of the sequence \0 unless at least one more octal digit follows.


PCRE2_EXTRA_PYTHON_OCTAL

If this option is set, PCRE2 follows Python's rules for interpreting octal escape sequences. The rules for handling sequences such as \14, which could be an octal number or a back reference are different. Details are given in the pcre2pattern documentation.


PCRE2_EXTRA_NEVER_CALLOUT

If this option is set, PCRE2 treats callouts in the pattern as a syntax error, returning PCRE2_ERROR_CALLOUT_CALLER_DISABLED. This is useful if the application knows that a callout will not be provided to pcre2_match(), so that callouts in the pattern are not silently ignored.


PCRE2_EXTRA_TURKISH_CASING

This option alters case-equivalence of the 'i' letters to follow the alphabet used by Turkish and Azeri languages. The option can be changed within a pattern by the (*TURKISH_CASING) start-of-pattern setting. Either the UTF or UCP options must be set. In the 8-bit library, UTF must be set. This option cannot be combined with PCRE2_EXTRA_CASELESS_RESTRICT.

These functions provide support for JIT compilation, which, if the just-in-time compiler is available, further processes a compiled pattern into machine code that executes much faster than the pcre2_match() interpretive matching function. Full details are given in the pcre2jit documentation.

JIT compilation is a heavyweight optimization. It can take some time for patterns to be analyzed, and for one-off matches and simple patterns the benefit of faster execution might be offset by a much slower compilation time. Most (but not all) patterns can be optimized by the JIT compiler.

LOCALE SUPPORT

const uint8_t *pcre2_maketables(pcre2_general_context *gcontext);

void pcre2_maketables_free(pcre2_general_context *gcontext,
  const uint8_t *tables);

PCRE2 handles caseless matching, and determines whether characters are letters, digits, or whatever, by reference to a set of tables, indexed by character code point. However, this applies only to characters whose code points are less than 256. By default, higher-valued code points never match escapes such as \w or \d.

When PCRE2 is built with Unicode support (the default), certain Unicode character properties can be tested with \p and \P, or, alternatively, the PCRE2_UCP option can be set when a pattern is compiled; this causes \w and friends to use Unicode property support instead of the built-in tables. PCRE2_UCP also causes upper/lower casing operations on characters with code points greater than 127 to use Unicode properties. These effects apply even when PCRE2_UTF is not set. There are, however, some PCRE2_EXTRA options (see above) that can be used to modify or suppress them.

The use of locales with Unicode is discouraged. If you are handling characters with code points greater than 127, you should either use Unicode support, or use locales, but not try to mix the two.

PCRE2 contains a built-in set of character tables that are used by default. These are sufficient for many applications. Normally, the internal tables recognize only ASCII characters. However, when PCRE2 is built, it is possible to cause the internal tables to be rebuilt in the default "C" locale of the local system, which may cause them to be different.

The built-in tables can be overridden by tables supplied by the application that calls PCRE2. These may be created in a different locale from the default. As more and more applications change to using Unicode, the need for this locale support is expected to die away.

External tables are built by calling the pcre2_maketables() function, in the relevant locale. The only argument to this function is a general context, which can be used to pass a custom memory allocator. If the argument is NULL, the system malloc() is used. The result can be passed to pcre2_compile() as often as necessary, by creating a compile context and calling pcre2_set_character_tables() to set the tables pointer therein.

For example, to build and use tables that are appropriate for the French locale (where accented characters with values greater than 127 are treated as letters), the following code could be used:


setlocale(LC_CTYPE, "fr_FR");
tables = pcre2_maketables(NULL);
ccontext = pcre2_compile_context_create(NULL);
pcre2_set_character_tables(ccontext, tables);
re = pcre2_compile(..., ccontext);

The locale name "fr_FR" is used on Linux and other Unix-like systems; if you are using Windows, the name for the French locale is "french".

The pointer that is passed (via the compile context) to pcre2_compile() is saved with the compiled pattern, and the same tables are used by the matching functions. Thus, for any single pattern, compilation and matching both happen in the same locale, but different patterns can be processed in different locales.

It is the caller's responsibility to ensure that the memory containing the tables remains available while they are still in use. When they are no longer needed, you can discard them using pcre2_maketables_free(), which should pass as its first parameter the same global context that was used to create the tables.

Saving locale tables

The tables described above are just a sequence of binary bytes, which makes them independent of hardware characteristics such as endianness or whether the processor is 32-bit or 64-bit. A copy of the result of pcre2_maketables() can therefore be saved in a file or elsewhere and re-used later, even in a different program or on another computer. The size of the tables (number of bytes) must be obtained by calling pcre2_config() with the PCRE2_CONFIG_TABLES_LENGTH option because pcre2_maketables() does not return this value. Note that the pcre2_dftables program, which is part of the PCRE2 build system, can be used stand-alone to create a file that contains a set of binary tables. See the pcre2build documentation for details.

PCRE2_INFO_BACKREFMAX

PCRE2_INFO_BSR

المخرج هو عدد صحيح من نوع uint32_t يحدد تسلسلات الأحرف التي تطابقها تسلسل الهروب \R. القيمة PCRE2_BSR_UNICODE تعني أن \R تطابق أي تسلسل نهاية سطر يونيكود؛ القيمة PCRE2_BSR_ANYCRLF تعني أن \R تطابق فقط CR أو LF أو CRLF.


PCRE2_INFO_CAPTURECOUNT

PCRE2_INFO_DEPTHLIMIT

إذا قام النمط بتعيين حد عمق التراجع عن طريق تضمين عنصر بالشكل (*LIMIT_DEPTH=nnnn) في البداية، يتم استرجاع القيمة. يجب أن تشير الحجة الثالثة إلى عدد صحيح من نوع uint32_t. إذا لم يتم تعيين قيمة كهذه، فإن استدعاء pcre2_pattern_info() يعيد الخطأ PCRE2_ERROR_UNSET. لاحظ أن هذا الحد سيتم استخدامه فقط أثناء المطابقة إذا كان أقل من الحد الذي تم تعيينه أو الافتراضي من قبل مستدعي دالة المطابقة.


PCRE2_INFO_FIRSTBITMAP

في غياب وحدة رمز أولى مفردة لنمط غير مثبت، قد يقوم pcre2_compile() بإنشاء جدول بـ 256 بت يحدد مجموعة ثابتة من القيم لوحدة الرمز الأولى في أي تطابق. على سبيل المثال، النمط الذي يبدأ بـ [abc] ينتج عنه جدول به ثلاثة بتات مضبوطة. عندما تكون قيم وحدات الرمز الأكبر من 255 مدعومة، فإن بت العلامة لـ 255 يعني "أي وحدة رمز بقيمة 255 أو أعلى". إذا تم إنشاء مثل هذا الجدول، يتم إرجاع مؤشر إليه. بخلاف ذلك، يتم إرجاع NULL. يجب أن تشير الحجة الثالثة إلى متغير من نوع const uint8_t *.


PCRE2_INFO_FIRSTCODETYPE

استرجاع معلومات حول وحدة الرمز الأولى لأي سلسلة مطابقة، لنمط غير مثبت. يجب أن تشير الحجة الثالثة إلى متغير من نوع uint32_t. إذا كانت هناك قيمة أولى ثابتة، على سبيل المثال، الحرف "c" من نمط مثل (cat|cow|coyote)، يتم إرجاع 1، ويمكن استرداد القيمة باستخدام PCRE2_INFO_FIRSTCODEUNIT. إذا لم تكن هناك قيمة أولى ثابتة، ولكن من المعروف أن التطابق يمكن أن يحدث فقط في بداية الموضوع أو بعد سطر جديد في الموضوع، يتم إرجاع 2. بخلاف ذلك، وللأنماط المثبتة، يتم إرجاع 0.


PCRE2_INFO_FIRSTCODEUNIT

استرجاع قيمة وحدة الرمز الأولى لأي سلسلة مطابقة لنمط ترجع فيه PCRE2_INFO_FIRSTCODETYPE القيمة 1؛ وإلا، استرجع 0. يجب أن تشير الحجة الثالثة إلى متغير من نوع uint32_t. في مكتبة 8 بت، تكون القيمة دائمًا أقل من 256. في مكتبة 16 بت، يمكن أن تصل القيمة إلى 0xffff. في مكتبة 32 بت في وضع UTF-32، يمكن أن تصل القيمة إلى 0x10ffff، وإلى 0xffffffff عند عدم استخدام وضع UTF-32.


PCRE2_INFO_FRAMESIZE

استرجاع حجم (بالبايت) إطارات البيانات التي تُستخدم لتذكر مواضع التراجع عند معالجة النمط بواسطة pcre2_match() دون استخدام JIT. يجب أن تشير الحجة الثالثة إلى متغير من نوع size_t. يعتمد حجم الإطار على عدد الأقواس الملتقطة في النمط. كل مجموعة التقاط إضافية تضيف متغيرين من نوع PCRE2_SIZE.


PCRE2_INFO_HASBACKSLASHC

استرجاع 1 إذا كان النمط يحتوي على أي تكرارات لـ \C، وإلا 0. يجب أن تشير الحجة الثالثة إلى متغير من نوع uint32_t.


PCRE2_INFO_HASCRORLF

استرجاع 1 إذا كان النمط يحتوي على أي تطابقات صريحة لحرفي CR أو LF، وإلا 0. يجب أن تشير الحجة الثالثة إلى متغير من نوع uint32_t. التطابق الصريح هو إما حرف CR أو LF حرفي، أو \r أو \n أو أحد تسلسلات الهروب المكافئة السداسية عشرية أو الثمانية.


PCRE2_INFO_HEAPLIMIT

إذا قام النمط بتعيين حد لذاكرة الكومة عن طريق تضمين عنصر بالشكل (*LIMIT_HEAP=nnnn) في البداية، يتم استرجاع القيمة. يجب أن تشير الحجة الثالثة إلى عدد صحيح من نوع uint32_t. إذا لم يتم تعيين قيمة كهذه، فإن استدعاء pcre2_pattern_info() يعيد الخطأ PCRE2_ERROR_UNSET. لاحظ أن هذا الحد سيتم استخدامه فقط أثناء المطابقة إذا كان أقل من الحد الذي تم تعيينه أو الافتراضي من قبل مستدعي دالة المطابقة.


PCRE2_INFO_JCHANGED

استرجاع 1 إذا تم استخدام إعداد الخيار (?J) أو (?-J) في النمط، وإلا 0. يجب أن تشير الحجة الثالثة إلى متغير من نوع uint32_t. (?J) و (?-J) يقومان بتعيين وإلغاء تعيين الخيار المحلي PCRE2_DUPNAMES على التوالي.


PCRE2_INFO_JITSIZE

إذا تمت معالجة النمط المجمّع بنجاح بواسطة pcre2_jit_compile()، فسيتم إرجاع حجم كود JIT المجمّع، وإلا فسيتم إرجاع صفر. يجب أن تشير الحجة الثالثة إلى متغير من نوع size_t.


PCRE2_INFO_LASTCODETYPE

ترجع 1 إذا كان هناك وحدة رمز حرفية يمينية يجب أن تكون موجودة في أي سلسلة مطابقة، بخلاف بدايتها. يجب أن تشير الحجة الثالثة إلى متغير من نوع uint32_t. إذا لم تكن هناك قيمة كهذه، يتم إرجاع 0. عندما يتم إرجاع 1، يمكن استرداد قيمة وحدة الرمز نفسها باستخدام PCRE2_INFO_LASTCODEUNIT. بالنسبة للأنماط المثبتة، يتم تسجيل قيمة حرفية أخيرة فقط إذا تبعت شيئًا ذا طول متغير. على سبيل المثال، بالنسبة للنمط /^a\d+z\d+/، القيمة المعادة هي 1 (مع "z" المعادة من PCRE2_INFO_LASTCODEUNIT)، ولكن بالنسبة للنمط /^a\dz\d/، القيمة المعادة هي 0.


PCRE2_INFO_LASTCODEUNIT

استرجاع قيمة وحدة الرمز الحرفية اليمنى التي يجب أن تكون موجودة في أي سلسلة مطابقة، بخلاف بدايتها، لنمط ترجع فيه PCRE2_INFO_LASTCODETYPE القيمة 1. وإلا، استرجع 0. يجب أن تشير الحجة الثالثة إلى متغير من نوع uint32_t.


PCRE2_INFO_MATCHEMPTY

استرجاع 1 إذا كان النمط قد يطابق سلسلة فارغة، وإلا 0. يجب أن تشير الحجة الثالثة إلى متغير من نوع uint32_t. عندما يحتوي النمط على استدعاءات فرعية متكررة، لا يكون من الممكن دائمًا تحديد ما إذا كان يمكنه مطابقة سلسلة فارغة أم لا. يأخذ PCRE2 نهجًا حذرًا ويرجع 1 في مثل هذه الحالات.


PCRE2_INFO_MATCHLIMIT

إذا قام النمط بتعيين حد للمطابقة عن طريق تضمين عنصر بالشكل (*LIMIT_MATCH=nnnn) في البداية، يتم استرجاع القيمة. يجب أن تشير الحجة الثالثة إلى عدد صحيح من نوع uint32_t. إذا لم يتم تعيين قيمة كهذه، فإن استدعاء pcre2_pattern_info() يعيد الخطأ PCRE2_ERROR_UNSET. لاحظ أن هذا الحد سيتم استخدامه فقط أثناء المطابقة إذا كان أقل من الحد الذي تم تعيينه أو الافتراضي من قبل مستدعي دالة المطابقة.


PCRE2_INFO_MAXLOOKBEHIND

تنتقل عبارة البحث الخلفي (lookbehind assertion) إلى الوراء عددًا معينًا من الأحرف (وليس وحدات الرمز) عند بدء معالجة كل فرع من فروعها. يرجع هذا الطلب أكبر هذه التحركات للخلف. يجب أن تشير الحجة الثالثة إلى عدد صحيح من نوع uint32_t. تتطلب العبارات البسيطة \b و \B بحثًا خلفيًا بمقدار حرف واحد وتتسبب في أن ترجع PCRE2_INFO_MAXLOOKBEHIND القيمة 1 في غياب أي شيء أطول. \A تسجل أيضًا بحثًا خلفيًا بمقدار حرف واحد، على الرغم من أنها لا تفحص الحرف السابق فعليًا.

لاحظ أن هذه المعلومات مفيدة للمطابقة متعددة الأجزاء فقط إذا كان النمط لا يحتوي على عبارات بحث خلفي متداخلة. على سبيل المثال، النمط (?<=a(?<=ba)c) يرجع بحثًا خلفيًا أقصى قدره 2، ولكن عند معالجته، يتحرك البحث الخلفي الأول للخلف بمقدار حرفين، ويتطابق مع حرف واحد، ثم يتحرك البحث الخلفي المتداخل أيضًا للخلف بمقدار حرفين. هذا يضع نقطة المطابقة ثلاثة أحرف قبل النقطة التي كانت عليها في البداية. PCRE2_INFO_MAXLOOKBEHIND مفيدة حقًا كأداة تصحيح أخطاء فقط. انظر توثيق pcre2partial لمناقشة المطابقة متعددة الأجزاء.


PCRE2_INFO_MINLENGTH

إذا تم حساب طول أدنى للسلاسل الموضوعية المطابقة، يتم إرجاع قيمته. بخلاف ذلك، تكون القيمة المعادة 0. لم يتم حساب هذه القيمة

في حالة تعيين PCRE2_NO_START_OPTIMIZE. القيمة هي عدد من الأحرف، والتي قد تكون في وضع UTF مختلفة عن عدد وحدات التعليمات البرمجية. يجب أن يشير الوسيط الثالث إلى متغير uint32_t. القيمة هي حد أدنى لطول أي سلسلة مطابقة. قد لا تكون هناك سلاسل بهذا الطول تطابق بالفعل، ولكن كل سلسلة تطابق تكون على الأقل بهذا الطول.


PCRE2_INFO_NAMECOUNT
PCRE2_INFO_NAMEENTRYSIZE
PCRE2_INFO_NAMETABLE

يدعم PCRE2 استخدام أقواس الالتقاط المسماة بالإضافة إلى المرقمة. الأسماء هي مجرد طريقة إضافية لتحديد الأقواس، والتي لا تزال تحصل على أرقام. يتم توفير العديد من الوظائف المساعدة مثل pcre2_substring_get_byname() لاستخراج السلاسل الفرعية الملتقطة بالاسم. من الممكن أيضًا استخراج البيانات مباشرة، عن طريق تحويل الاسم إلى رقم أولاً للوصول إلى المؤشرات الصحيحة في متجه الإخراج (الموصوف مع pcre2_match() أدناه). للقيام بالتحويل، تحتاج إلى استخدام خريطة الأسماء إلى الأرقام، والتي توصف بهذه القيم الثلاث.

تتكون الخريطة من عدد من الإدخالات ذات الحجم الثابت. PCRE2_INFO_NAMECOUNT تعطي عدد الإدخالات، و PCRE2_INFO_NAMEENTRYSIZE تعطي حجم كل إدخال بوحدات التعليمات البرمجية؛ كلاهما يعيد قيمة uint32_t. يعتمد حجم الإدخال على طول أطول اسم.

PCRE2_INFO_NAMETABLE يعيد مؤشرًا إلى الإدخال الأول للجدول. هذا مؤشر PCRE2_SPTR إلى كتلة من وحدات التعليمات البرمجية. في مكتبة 8 بت، أول بايتين من كل إدخال هما رقم قوس الالتقاط، البايت الأكثر أهمية أولاً. في مكتبة 16 بت، يشير المؤشر إلى وحدات التعليمات البرمجية 16 بت، والتي تحتوي الأولى منها على رقم القوس. في مكتبة 32 بت، يشير المؤشر إلى وحدات التعليمات البرمجية 32 بت، والتي تحتوي الأولى منها على رقم القوس. بقية الإدخال هو الاسم المقابل، المنتهي بصفر.

الأسماء مرتبة أبجديًا. إذا تم استخدام (?| لإنشاء مجموعات التقاط متعددة بنفس الرقم، كما هو موضح في القسم الخاص بأرقام المجموعات المكررة في صفحة pcre2pattern، يمكن منح المجموعات نفس الاسم، ولكن هناك إدخال واحد فقط في الجدول. لا يُسمح بأسماء مختلفة لمجموعات بنفس الرقم.

يُسمح بالأسماء المكررة لمجموعات الالتقاط بأرقام مختلفة، ولكن فقط إذا تم تعيين PCRE2_DUPNAMES. تظهر في الجدول بترتيب العثور عليها في النمط. في حالة عدم وجود (?|، هذا هو ترتيب الأرقام المتزايدة؛ عند استخدام (?|، هذا ليس بالضرورة هو الحال لأن مجموعات الالتقاط اللاحقة قد يكون لها أرقام أقل.

كمثال بسيط لجدول الاسم/الرقم، انظر النمط التالي بعد تجميعه بواسطة مكتبة 8 بت (افترض تعيين PCRE2_EXTENDED، لذا يتم تجاهل المسافة البيضاء - بما في ذلك أسطر جديدة -):


(?<date> (?<year>(\d\d)?\d\d) -
(?<month>\d\d) - (?<day>\d\d) )

هناك أربع مجموعات التقاط مسماة، لذلك يحتوي الجدول على أربعة إدخالات، وكل إدخال في الجدول بطول ثمانية بايت. الجدول كالتالي، مع إظهار البايتات غير القابلة للطباعة باللون السداسي عشري، والبايتات غير المعرفة بالرمز ؟؟:


00 01 d a t e 00 ??
00 05 d a y 00 ?? ??
00 04 m o n t h 00
00 02 y e a r 00 ??

عند كتابة رمز لاستخراج البيانات من مجموعات الالتقاط المسماة باستخدام خريطة الأسماء إلى الأرقام، تذكر أن طول الإدخالات من المحتمل أن يكون مختلفًا لكل نمط مجمّع.


PCRE2_INFO_NEWLINE

الإخراج هو أحد قيم uint32_t التالية:


PCRE2_NEWLINE_CR حرف العودة إلى بداية السطر (CR)
PCRE2_NEWLINE_LF حرف تغذية السطر (LF)
PCRE2_NEWLINE_CRLF حرف العودة إلى بداية السطر، حرف تغذية السطر (CRLF)
PCRE2_NEWLINE_ANY أي نهاية سطر يونيكود
PCRE2_NEWLINE_ANYCRLF أي من CR، LF، أو CRLF
PCRE2_NEWLINE_NUL حرف NUL (صفر ثنائي)

يحدد هذا التسلسل الحرفي الذي سيتم التعرف عليه على أنه يعني "سطر جديد" أثناء المطابقة.


PCRE2_INFO_SIZE

إرجاع حجم النمط المجمّع بالبايت (للمكتبات الثلاثة). يجب أن يشير الوسيط الثالث إلى متغير size_t. تتضمن هذه القيمة حجم كتلة البيانات العامة التي تسبق وحدات التعليمات البرمجية للنمط المجمّع نفسه. قد تكون القيمة المستخدمة عندما تحصل pcre2_compile() على ذاكرة لوضع النمط المجمّع أكبر قليلاً من القيمة التي تم إرجاعها بواسطة هذا الخيار، نظرًا لوجود حالات يحتاج فيها الكود الذي يحسب الحجم إلى تقدير زائد. معالجة نمط باستخدام مترجم JIT لا تغير القيمة التي تم إرجاعها بواسطة هذا الخيار.

قد يرغب لغة نصية تدعم استخدام وسائط السلسلة في استدعاءات الاستدعاء في مسح جميع استدعاءات الاستدعاء في نمط قبل تشغيل المطابقة. يمكن القيام بذلك عن طريق استدعاء pcre2_callout_enumerate(). الوسيط الأول هو مؤشر إلى نمط مجمّع، والثاني يشير إلى دالة رد اتصال، والثالث هو بيانات مستخدم عشوائية. يتم استدعاء دالة رد الاتصال لكل استدعاء استدعاء في النمط بالترتيب الذي تظهر به. وسيطها الأول هو مؤشر إلى كتلة تعداد استدعاءات الاستدعاء، ووسيطها الثاني هو قيمة user_data التي تم تمريرها إلى pcre2_callout_enumerate(). يتم وصف محتويات كتلة تعداد استدعاءات الاستدعاء في وثائق pcre2callout، والتي تعطي أيضًا تفاصيل إضافية حول استدعاءات الاستدعاء.

التسلسل والتجميع المسبق

من الممكن حفظ الأنماط المجمّعة على القرص أو في مكان آخر، وإعادة تحميلها لاحقًا، مع مراعاة عدد من القيود. يجب أن يكون المضيف الذي تتم فيه إعادة تحميل الأنماط قيد التشغيل بنفس إصدار PCRE2، بنفس عرض وحدة التعليمات البرمجية، ويجب أن يكون له نفس ترتيب البايتات، وعرض المؤشر، ونوع PCRE2_SIZE. قبل أن يتم حفظ الأنماط المجمّعة، يجب تحويلها إلى شكل "مسلسل"، وهو في حالة PCRE2 مجرد تفريغ للتعليمات البرمجية. تُستخدم الوظائف التي تبدأ أسماؤها بـ pcre2_serialize_ للتحويل من وإلى الشكل المسلسل. يتم وصفها في وثائق pcre2serialize. لاحظ أن تسلسل PCRE2 لا يحول الأنماط المجمّعة إلى تنسيق مجرد مثل تسلسل Java أو .NET.

كتلة بيانات المطابقة

pcre2_match_data *pcre2_match_data_create(uint32_t ovecsize,
  pcre2_general_context *gcontext);

pcre2_match_data *pcre2_match_data_create_from_pattern(
  const pcre2_code *code, pcre2_general_context *gcontext);

void pcre2_match_data_free(pcre2_match_data *match_data);

يتم وضع المعلومات حول مطابقة ناجحة أو فاشلة في كتلة بيانات المطابقة، وهي بنية غامضة يتم الوصول إليها عن طريق استدعاءات الوظائف. على وجه الخصوص، تحتوي كتلة بيانات المطابقة على متجه لإزاحات في سلسلة الموضوع التي تحدد الأجزاء المطابقة للموضوع. يُعرف هذا باسم ovector.

قبل استدعاء pcre2_match() أو pcre2_dfa_match() أو pcre2_jit_match()، يجب عليك إنشاء كتلة بيانات مطابقة عن طريق استدعاء إحدى وظائف الإنشاء أعلاه. بالنسبة لـ pcre2_match_data_create()، الوسيط الأول هو عدد أزواج الإزاحات في ovector.

عند استخدام pcre2_match()، يلزم زوج واحد من الإزاحات لتحديد السلسلة التي طابقت النمط بالكامل، مع زوج إضافي لكل سلسلة فرعية ملتقطة. على سبيل المثال، القيمة 4 تنشئ مساحة كافية لتسجيل الجزء المطابق من الموضوع بالإضافة إلى ثلاث سلاسل فرعية ملتقطة.

عند استخدام pcre2_dfa_match()، قد تكون هناك سلاسل فرعية متعددة بأطوال مختلفة في نفس النقطة في الموضوع. يجب أن يكون ovector كبيرًا بما يكفي لاستيعاب أكبر عدد متوقع.

يتم فرض حد أدنى من زوج واحد بواسطة pcre2_match_data_create()، لذلك من الممكن دائمًا إرجاع السلسلة المطابقة الإجمالية في حالة pcre2_match() أو أطول تطابق في حالة pcre2_dfa_match(). الحد الأقصى لعدد الأزواج هو 65535؛ إذا كان الوسيط الأول لـ pcre2_match_data_create() أكبر من هذا، يتم استخدام 65535.

الوسيط الثاني لـ pcre2_match_data_create() هو مؤشر إلى سياق عام، والذي يمكنه تحديد إدارة ذاكرة مخصصة للحصول على الذاكرة لكتلة بيانات المطابقة. إذا كنت لا تستخدم إدارة ذاكرة مخصصة، فمرر NULL، مما يتسبب في استخدام malloc().

بالنسبة لـ pcre2_match_data_create_from_pattern()، الوسيط الأول هو مؤشر إلى نمط مجمّع. يتم إنشاء ovector بحجم مناسب تمامًا لاستيعاب جميع السلاسل الفرعية التي قد يلتقطها النمط عند مطابقته باستخدام pcre2_match(). لا يجب عليك استخدام هذا الاستدعاء عند المطابقة باستخدام pcre2_dfa_match(). الوسيط الثاني هو مرة أخرى مؤشر إلى سياق عام، ولكن في هذه الحالة إذا تم تمرير NULL، يتم الحصول على الذاكرة باستخدام نفس المخصص الذي تم استخدامه للنمط المجمّع (مخصص أو افتراضي).

يمكن استخدام كتلة بيانات مطابقة عدة مرات، مع أنماط مجمّعة مماثلة أو مختلفة. يمكنك استخراج المعلومات من كتلة بيانات مطابقة بعد انتهاء عملية مطابقة، باستخدام وظائف موصوفة في الأقسام المتعلقة بالسلاسل المطابقة وبيانات المطابقة الأخرى أدناه.

عند فشل استدعاء pcre2_match()، تكون البيانات الصالحة متاحة في كتلة المطابقة فقط عندما يكون الخطأ هو PCRE2_ERROR_NOMATCH أو PCRE2_ERROR_PARTIAL أو أحد رموز الخطأ لسلسلة UTF غير صالحة. يعتمد ما هو متاح بالضبط على الخطأ، ويتم تفصيله أدناه.

عند استدعاء إحدى وظائف المطابقة، يتم تعيين مؤشرات إلى النمط المجمّع وسلسلة الموضوع في كتلة بيانات المطابقة حتى يمكن الرجوع إليها بواسطة وظائف الاستخراج بعد مطابقة ناجحة. بعد تشغيل مطابقة، يجب ألا تحرر نمطًا مجمّعًا أو سلسلة موضوع حتى بعد اكتمال جميع العمليات على كتلة بيانات المطابقة (لهذه المطابقة)، ما لم، في حالة سلسلة الموضوع، تكون قد استخدمت خيار PCRE2_COPY_MATCHED_SUBJECT، الذي يوصف في القسم بعنوان "بتات الخيار لـ pcre2_match()" أدناه.

عندما لا تعود كتلة بيانات المطابقة مطلوبة، يجب تحريرها عن طريق استدعاء pcre2_match_data_free(). إذا تم استدعاء هذه الوظيفة مع وسيط NULL، فإنها تعود فورًا، دون القيام بأي شيء.

مطابقة نمط: الدالة التقليدية

int pcre2_match(const pcre2_code *code, PCRE2_SPTR subject,
  PCRE2_SIZE length, PCRE2_SIZE startoffset,
  uint32_t options, pcre2_match_data *match_data,
  pcre2_match_context *mcontext);

يتم استدعاء الدالة pcre2_match() لمطابقة سلسلة موضوع (subject) مع نمط مجمّع، والذي يتم تمريره في الوسيط code. يمكنك استدعاء pcre2_match() بنفس الوسيط code عدة مرات كما تشاء، للعثور على مطابقات متعددة في سلسلة الموضوع أو لمطابقة سلاسل موضوع مختلفة بنفس النمط.

هذه الدالة هي المرفق الرئيسي للمطابقة في المكتبة، وتعمل بطريقة شبيهة بـ Perl. للاستخدام المتخصص، توجد أيضًا دالة مطابقة بديلة، والتي يتم وصفها أدناه في القسم الخاص بالدالة pcre2_dfa_match().

إليك مثال على استدعاء بسيط للدالة pcre2_match():


pcre2_match_data *md = pcre2_match_data_create(4, NULL);
int rc = pcre2_match(
re, /* نتيجة pcre2_compile() */
"some string", /* سلسلة الموضوع */
11, /* طول سلسلة الموضوع */
0, /* ابدأ من الإزاحة 0 في الموضوع */
0, /* خيارات افتراضية */
md, /* كتلة بيانات المطابقة */
NULL); /* سياق المطابقة؛ NULL يعني استخدام الافتراضيات */

إذا كانت سلسلة الموضوع منتهية بصفر (zero-terminated)، فيمكن إعطاء الطول كـ PCRE2_ZERO_TERMINATED. يجب توفير سياق مطابقة إذا كان سيتم تغيير بعض معلمات المطابقة الأقل شيوعًا. للتفاصيل، انظر القسم الخاص بسياق المطابقة أعلاه.

السلسلة المراد مطابقتها بواسطة pcre2_match()

يتم تمرير سلسلة الموضوع إلى pcre2_match() كمؤشر في subject، وطول في length، وإزاحة بداية في startoffset. الطول والإزاحة بالوحدات الرمزية (code units)، وليس الأحرف. أي أنها بالبايت للمكتبة 8 بت، ووحدات رمزية 16 بت للمكتبة 16 بت، ووحدات رمزية 32 بت للمكتبة 32 بت، بغض النظر عما إذا كانت معالجة UTF ممكّنة أم لا. كحالة خاصة، إذا كان subject هو NULL وكان length صفرًا، فيُفترض أن الموضوع هو سلسلة فارغة. إذا كان length غير صفري، يحدث خطأ إذا كان subject هو NULL.

إذا كانت startoffset أكبر من طول الموضوع، فإن pcre2_match() تُرجع PCRE2_ERROR_BADOFFSET. عندما تكون إزاحة البداية صفرًا، يبدأ البحث عن المطابقة من بداية الموضوع، وهذا هو الحال الأكثر شيوعًا بفارق كبير. في وضع UTF-8 أو UTF-16، يجب أن تشير إزاحة البداية إلى بداية حرف، أو إلى نهاية الموضوع (في وضع UTF-32، وحدة رمزية واحدة تساوي حرفًا واحدًا، لذا فإن جميع الإزاحات صالحة). مثل سلسلة النمط، قد تحتوي سلسلة الموضوع على أصفار ثنائية.

تكون إزاحة البداية غير الصفرية مفيدة عند البحث عن مطابقة أخرى في نفس الموضوع عن طريق استدعاء pcre2_match() مرة أخرى بعد نجاح سابق. تختلف تعيين startoffset عن تجاوز جزء من السلسلة المختصرة وتعيين PCRE2_NOTBOL في حالة نمط يبدأ بأي نوع من البحث الخلفي (lookbehind). على سبيل المثال، ضع في اعتبارك النمط


\Biss\B

الذي يجد تكرارات "iss" في منتصف الكلمات. (\B يطابق فقط إذا كان الموضع الحالي في الموضوع ليس حد كلمة.) عند تطبيقه على السلسلة "Mississippi"، تجد المكالمة الأولى لـ pcre2_match() أول تكرار. إذا تم استدعاء pcre2_match() مرة أخرى مع ما تبقى من الموضوع فقط، وهو "issippi"، فلن تتطابق، لأن \B يكون دائمًا خاطئًا في بداية الموضوع، والذي يعتبر حد كلمة. ومع ذلك، إذا تم تمرير نفس السلسلة بالكامل مرة أخرى إلى pcre2_match()، ولكن مع تعيين startoffset إلى 4، فإنها تجد التكرار الثاني لـ "iss" لأنها قادرة على النظر خلف نقطة البداية لاكتشاف أنها مسبوقة بحرف.

يعد العثور على جميع المطابقات في موضوع أمرًا صعبًا عندما يمكن للنمط أن يطابق سلسلة فارغة. تتضمن PCRE2 واجهة برمجة تطبيقات مساعدة للمساعدة في ذلك؛ انظر القسم بعنوان "التكرار فوق جميع المطابقات" أدناه للحصول على التفاصيل.

إذا تم تمرير إزاحة بداية غير صفرية عندما يكون النمط مثبتًا (anchored)، يتم إجراء محاولة واحدة للمطابقة عند الإزاحة المعطاة. قد ينجح هذا فقط إذا لم يتطلب النمط أن تكون المطابقة في بداية الموضوع. بمعنى آخر، يجب أن يكون التثبيت نتيجة تعيين الخيار PCRE2_ANCHORED أو استخدام .* مع PCRE2_DOTALL، وليس عن طريق بدء النمط بـ ^ أو \A.

بتات الخيار لـ pcre2_match()

يجب أن تكون البتات غير المستخدمة للوسيط options للدالة pcre2_match() صفرًا. البتات الوحيدة التي يمكن تعيينها هي PCRE2_ANCHORED، PCRE2_COPY_MATCHED_SUBJECT، PCRE2_DISABLE_RECURSELOOP_CHECK، PCRE2_ENDANCHORED، PCRE2_NOTBOL، PCRE2_NOTEOL، PCRE2_NOTEMPTY، PCRE2_NOTEMPTY_ATSTART، PCRE2_NO_JIT، PCRE2_NO_UTF_CHECK، PCRE2_PARTIAL_HARD، و PCRE2_PARTIAL_SOFT. يتم وصف إجراءاتها أدناه.

تعيين PCRE2_ANCHORED أو PCRE2_ENDANCHORED عند المطابقة غير مدعوم من قبل المجمّع في الوقت المناسب (JIT). إذا تم تعيينه، يتم تعطيل مطابقة JIT وتشغيل الكود التفسيري في pcre2_match(). يتم تجاهل PCRE2_DISABLE_RECURSELOOP_CHECK بواسطة JIT، ولكن بخلاف PCRE2_NO_JIT (بالطبع)، فإن الخيارات المتبقية مدعومة لمطابقة JIT.


PCRE2_ANCHORED

يقيد الخيار PCRE2_ANCHORED الدالة pcre2_match() بالمطابقة في أول موضع مطابق. إذا تم تجميع نمط مع PCRE2_ANCHORED، أو تبين أنه مثبت بحكم محتوياته، فلا يمكن جعله غير مثبت في وقت المطابقة. لاحظ أن تعيين الخيار في وقت المطابقة يعطل مطابقة JIT.


PCRE2_COPY_MATCHED_SUBJECT

بشكل افتراضي، يتم تذكر مؤشر إلى الموضوع في كتلة بيانات المطابقة بحيث، بعد مطابقة ناجحة، يمكن الإشارة إليه بواسطة دوال استخراج السلسلة الفرعية. هذا يعني أنه لا يجب تحرير ذاكرة الموضوع حتى تكتمل جميع عمليات الاستخراج. بالنسبة لبعض التطبيقات التي لا يكون فيها عمر سلسلة الموضوع مضمونًا، قد يكون من الضروري عمل نسخة من سلسلة الموضوع، ولكن هذا يكون هدراً ما لم تكن المطابقة ناجحة. بعد مطابقة ناجحة، إذا تم تعيين PCRE2_COPY_MATCHED_SUBJECT، يتم نسخ الموضوع ويتم تذكر المؤشر الجديد في كتلة بيانات المطابقة بدلاً من مؤشر الموضوع الأصلي. يتم استخدام مخصص الذاكرة الذي تم استخدامه لكتلة المطابقة نفسها. يتم تحرير النسخة تلقائيًا عند استدعاء pcre2_match_data_free() لتحرير كتلة بيانات المطابقة. كما يتم تحريرها تلقائيًا إذا تم إعادة استخدام كتلة بيانات المطابقة لعملية مطابقة أخرى.


PCRE2_DISABLE_RECURSELOOP_CHECK

هذا الخيار ذو صلة فقط بـ pcre2_match() للمطابقة التفسيرية. يتم تجاهله عند استخدام JIT، ويُمنع استخدامه لـ pcre2_dfa_match().

يمكن أن يؤدي استخدام التكرار في الأنماط إلى حلقات لا نهائية. في المضاهاة التفسيرية، سيتم اكتشاف ذلك في النهاية بواسطة حدود المطابقة أو الكومة، ولكن قد يستغرق ذلك وقتًا طويلاً و/أو يستخدم الكثير من الذاكرة إذا كانت الحدود كبيرة. لذلك، هناك فحص في بداية كل تكرار. إذا كانت نفس المجموعة لا تزال نشطة من مكالمة سابقة، وكان مؤشر الموضوع الحالي هو نفسه كما كان في بداية تلك المجموعة، ولم يتغير الحرف الأبعد الذي تم فحصه في الموضوع، يتم إنشاء خطأ.

هناك حالات نادرة من المطابقات التي ستكتمل، ولكنها مع ذلك تؤدي إلى هذا الخطأ. هذا الخيار يعطل الفحص. يتم توفيره بشكل أساسي للاختبار عند مقارنة سلوك JIT والتفسيري.


PCRE2_ENDANCHORED

إذا تم تعيين الخيار PCRE2_ENDANCHORED، فيجب أن تكون أي سلسلة تطابقها الدالة pcre2_match() في نهاية سلسلة الموضوع بالضبط. لاحظ أن تعيين الخيار في وقت المطابقة يعطل مطابقة JIT.


PCRE2_NOTBOL

يحدد هذا الخيار أن الحرف الأول من سلسلة الموضوع ليس بداية سطر، لذلك يجب ألا يتطابق الحرف المجازي (circumflex) قبله. تعيين هذا بدون تعيين PCRE2_MULTILINE عند التجميع يتسبب في عدم تطابق الحرف المجازي أبدًا. يؤثر هذا الخيار فقط على سلوك الحرف المجازي. لا يؤثر على \A.


PCRE2_NOTEOL

يحدد هذا الخيار أن نهاية سلسلة الموضوع ليست نهاية سطر، لذلك يجب ألا يتطابق الحرف المجازي الدولار (dollar) معها ولا (باستثناء وضع تعدد الأسطر) سطر جديد قبلها مباشرة. تعيين هذا بدون تعيين PCRE2_MULTILINE عند التجميع يتسبب في عدم تطابق الدولار أبدًا. يؤثر هذا الخيار فقط على سلوك الحرف المجازي الدولار. لا يؤثر على \Z أو \z.


PCRE2_NOTEMPTY

لا تعتبر السلسلة الفارغة مطابقة صالحة إذا تم تعيين هذا الخيار. إذا كانت هناك بدائل في النمط، يتم تجربتها. إذا طابقت جميع البدائل السلسلة الفارغة، تفشل المطابقة بأكملها. على سبيل المثال، إذا كان النمط


a?b?

تم تطبيقه على سلسلة لا تبدأ بـ

لم يتم تغيير محتويات ovector.

معلومات أخرى حول المطابقة

PCRE2_SPTR pcre2_get_mark(pcre2_match_data *match_data);

PCRE2_SIZE pcre2_get_startchar(pcre2_match_data *match_data);

بالإضافة إلى الإزاحات الموجودة في ovector، يتم الاحتفاظ بمعلومات أخرى حول المطابقة في كتلة بيانات المطابقة ويمكن استرجاعها بواسطة الدوال المذكورة أعلاه في ظروف مناسبة. إذا تم استدعاؤها في أوقات أخرى، فإن النتيجة غير محددة.

بعد مطابقة ناجحة (PCRE2_ERROR_PARTIAL)، أو مطابقة جزئية (PCRE2_ERROR_PARTIAL)، أو فشل في المطابقة (PCRE2_ERROR_NOMATCH)، قد يكون اسم العلامة متاحًا. يمكن استدعاء الدالة pcre2_get_mark() للوصول إلى هذا الاسم، والذي يمكن تحديده في النمط بواسطة أي من عبارات التحكم في التراجع، وليس فقط (*MARK). تنطبق نفس الدالة على جميع العبارات. تُرجع مؤشرًا إلى الاسم المنتهي بصفر، والذي يوجد داخل النمط المترجم. إذا لم يكن هناك اسم متاح، يتم إرجاع NULL. يتم تخزين طول الاسم (باستثناء الصفر النهائي) في وحدة التعليمات البرمجية التي تسبق الاسم. يجب عليك استخدام هذا الطول بدلاً من الاعتماد على الصفر النهائي إذا كان الاسم قد يحتوي على صفر ثنائي.

بعد المطابقة الناجحة، يكون الاسم الذي يتم إرجاعه هو آخر اسم علامة تمت مواجهته في مسار المطابقة عبر النمط. لا تُحتسب حالات عبارات التراجع بدون أسماء. وبالتالي، على سبيل المثال، إذا كان مسار المطابقة يحتوي على (*MARK:A)(*PRUNE)، يتم إرجاع الاسم "A". بعد "عدم المطابقة" أو المطابقة الجزئية، يتم إرجاع آخر اسم تمت مواجهته. على سبيل المثال، ضع في اعتبارك هذا النمط:


^(*MARK:A)((*MARK:B)a|b)c

عند مطابقته مع "bc"، يكون الاسم الذي تم إرجاعه هو A. تتم "رؤية" علامة B في الفرع الأول من المجموعة، ولكنها ليست في مسار المطابقة. من ناحية أخرى، عندما يفشل هذا النمط في مطابقته مع "bx"، يكون الاسم الذي تم إرجاعه هو B.

تحذير: افتراضيًا، يتم استخدام بعض تحسينات بداية المطابقة لتوفير نتيجة "عدم مطابقة" سريعة في بعض المواقف. على سبيل المثال، إذا تمت إزالة التثبيت من النمط أعلاه، يكون هناك فحص أولي لوجود "c" في الموضوع قبل تشغيل محرك المطابقة. يفشل هذا الفحص مع "bx"، مما يؤدي إلى فشل المطابقة دون رؤية أي علامات. يمكنك تعطيل تحسينات بداية المطابقة عن طريق تعيين خيار PCRE2_NO_START_OPTIMIZE لـ pcre2_compile() أو عن طريق بدء النمط بـ (*NO_START_OPT).

بعد المطابقة الناجحة، أو المطابقة الجزئية، أو أحد أخطاء UTF غير الصالحة (على سبيل المثال، PCRE2_ERROR_UTF8_ERR5)، يمكن استدعاء pcre2_get_startchar(). بعد المطابقة الناجحة أو الجزئية، تُرجع إزاحة وحدة التعليمات البرمجية للحرف الذي بدأت فيه المطابقة. بالنسبة للمطابقة غير الجزئية، يمكن أن يكون هذا مختلفًا عن قيمة ovector[0] إذا كان النمط يحتوي على تسلسل الهروب \K. ومع ذلك، بعد المطابقة الجزئية، تكون هذه القيمة دائمًا نفس قيمة ovector[0] لأن \K لا يؤثر على نتيجة المطابقة الجزئية.

بعد فشل فحص UTF، يمكن استخدام pcre2_get_startchar() للحصول على إزاحة وحدة التعليمات البرمجية للحرف غير الصالح UTF. التفاصيل معطاة في صفحة pcre2unicode.

عائدات الخطأ من pcre2_match()

إذا فشلت pcre2_match()، فإنها تُرجع رقمًا سالبًا. يمكن تحويل هذا إلى سلسلة نصية عن طريق استدعاء الدالة pcre2_get_error_message() (انظر "الحصول على رسالة خطأ نصية" أدناه). يتم أيضًا إرجاع رموز الخطأ السالبة بواسطة دوال أخرى، وهي موثقة معها. يتم إعطاء الرموز أسماء في ملف الترويسة. إذا كان فحص UTF ساري المفعول وتم اكتشاف سلسلة موضوع UTF غير صالحة، يتم إرجاع أحد رموز الخطأ السالبة الخاصة بـ UTF. التفاصيل معطاة في صفحة pcre2unicode. فيما يلي الأخطاء الأخرى التي قد تُرجعها pcre2_match():


PCRE2_ERROR_NOMATCH

لم تتطابق سلسلة الموضوع مع النمط.


PCRE2_ERROR_PARTIAL

لم تتطابق سلسلة الموضوع، ولكنها تطابقت جزئيًا. انظر وثائق pcre2partial لتفاصيل المطابقة الجزئية.


PCRE2_ERROR_BADMAGIC

تقوم PCRE2 بتخزين "رقم سحري" مكون من 4 بايت في بداية التعليمات البرمجية المترجمة، للتعامل مع الحالة التي يتم فيها تمرير مؤشر عشوائي. هذا هو الخطأ الذي يتم إرجاعه عندما لا يكون الرقم السحري موجودًا.


PCRE2_ERROR_BADMODE

يتم إعطاء هذا الخطأ عند تمرير نمط مترجم إلى دالة في مكتبة ذات عرض تعليمات برمجية مختلف، على سبيل المثال، نمط تم تجميعه بواسطة مكتبة 8 بت يتم تمريره إلى دالة مكتبة 16 بت أو 32 بت.


PCRE2_ERROR_BADOFFSET

كانت قيمة startoffset أكبر من طول الموضوع.


PCRE2_ERROR_BADOPTION

تم تعيين بت غير معروف في وسيطة options.


PCRE2_ERROR_BADUTFOFFSET

تم فحص تسلسل وحدة التعليمات البرمجية UTF الذي تم تمريره كموضوع وتبين أنه صالح (لم يتم تعيين خيار PCRE2_NO_UTF_CHECK)، ولكن قيمة startoffset لم تشير إلى بداية حرف UTF أو نهاية الموضوع.


PCRE2_ERROR_CALLOUT

لا يتم إنشاء هذا الخطأ أبدًا بواسطة pcre2_match() نفسها. يتم توفيره للاستخدام بواسطة دوال الاستدعاء التي تريد أن تُرجع pcre2_match() أو pcre2_callout_enumerate() رمز خطأ مميز. انظر وثائق pcre2callout للتفاصيل.


PCRE2_ERROR_DEPTHLIMIT

تم الوصول إلى حد عمق التراجع المتداخل.


PCRE2_ERROR_HEAPLIMIT

تم الوصول إلى حد الذاكرة المكدسة.


PCRE2_ERROR_INTERNAL

حدث خطأ داخلي غير متوقع. يمكن أن يكون هذا الخطأ ناتجًا عن خطأ في PCRE2 أو عن الكتابة فوق النمط المترجم.


PCRE2_ERROR_JIT_STACKLIMIT

يتم إرجاع هذا الخطأ عند مطابقة نمط تم دراسته بنجاح باستخدام JIT، ولكن الذاكرة المتاحة لمكدس المعالجة في الوقت المناسب غير كافية. انظر وثائق pcre2jit لمزيد من التفاصيل.


PCRE2_ERROR_MATCHLIMIT

تم الوصول إلى حد مطابقة التراجع.


PCRE2_ERROR_NOMEMORY

تُستخدم ذاكرة المكدس لتذكر نقاط التراجع. يتم إعطاء هذا الخطأ عند فشل دالة تخصيص الذاكرة (الافتراضية أو المخصصة). لاحظ أن خطأ مختلفًا، PCRE2_ERROR_HEAPLIMIT، يتم إعطاؤه إذا تجاوزت كمية الذاكرة المطلوبة حد المكدس. يتم أيضًا إرجاع PCRE2_ERROR_NOMEMORY إذا تم تعيين PCRE2_COPY_MATCHED_SUBJECT وفشل تخصيص الذاكرة.


PCRE2_ERROR_NULL

تم تمرير أحد الوسائط code أو subject أو match_data كـ NULL.


PCRE2_ERROR_RECURSELOOP

يتم إرجاع هذا الخطأ عندما تكتشف pcre2_match() حلقة تراجع داخل النمط. على وجه التحديد، يعني ذلك أنه تم استدعاء النمط بأكمله أو مجموعة التقاط بشكل متكرر للمرة الثانية في نفس الموضع في سلسلة الموضوع. يتم اكتشاف بعض الأنماط البسيطة التي قد تفعل ذلك وتعطلها وقت الترجمة، ولكن الحالات الأكثر تعقيدًا، وخاصة التراجعات المتبادلة بين مجموعتين مختلفتين، لا يمكن اكتشافها حتى تتم محاولة المطابقة.

الحصول على رسالة خطأ نصية

int pcre2_get_error_message(int errorcode, PCRE2_UCHAR *buffer,
  PCRE2_SIZE bufflen);

يمكن الحصول على رسالة نصية لرمز خطأ من أي دالة PCRE2 (ترجمة، مطابقة، أو مساعدة) عن طريق استدعاء pcre2_get_error_message(). يتم تمرير الرمز كوسيط أول، مع تحديد الوسيطين المتبقيين لمخزن مؤقت لوحدات التعليمات البرمجية وطولها بوحدات التعليمات البرمجية، حيث يتم وضع الرسالة النصية. يتم إرجاع الرسالة بوحدات تعليمات برمجية ذات عرض مناسب للمكتبة التي يتم استخدامها.

يتم إنهاء الرسالة المرجعة بصفر لاحق، وتُرجع الدالة عدد وحدات التعليمات البرمجية المستخدمة، باستثناء الصفر اللاحق. إذا كان رقم الخطأ غير معروف، يتم إرجاع رمز الخطأ السالب PCRE2_ERROR_BADDATA. إذا كان المخزن المؤقت صغيرًا جدًا، يتم اقتطاع الرسالة (ولكن مع صفر لاحق)، ويتم إرجاع رمز الخطأ السالب PCRE2_ERROR_NOMEMORY. لا توجد رسائل طويلة جدًا؛ حجم المخزن المؤقت البالغ 120 وحدة تعليمات برمجية كافٍ.

التكرار فوق جميع المطابقات

int pcre2_next_match(pcre2_match_data *match_data,
  PCRE2_SIZE *pstart_offset, uint32_t *poptions);

تتمثل إحدى المهام الشائعة للتطبيقات في تنفيذ سلوك مطابقة "شامل"، على سبيل المثال، استبدال جميع المطابقات في الموضوع؛ تقسيم الموضوع بناءً على جميع المطابقات؛ أو ببساطة عد عدد المطابقات. تساعد الدالة pcre2_next_match() في هذه المهمة من خلال توفير المعلمات المناسبة لمحاولة المطابقة التالية (متاحة منذ PCRE2 10.46).

أولاً، يجب إجراء محاولة مطابقة باستخدام إحدى دوال المطابقة (pcre2_match() أو pcre2_dfa_match() أو pcre2_jit_match()). بعد ذلك، يمكن استدعاء pcre2_next_match()، وتوفير نفس وسيطة match_data.

تُرجع 0 ("خطأ") إذا لم تكن هناك حاجة لمحاولة مطابقة إضافية، أو 1 ("صحيح") إذا كان يجب محاولة مطابقة أخرى. لا يعني إرجاع 1 وجود مطابقة أخرى، بل يعني فقط أنه يجب محاولة مطابقة أخرى (والتي قد تُرجع PCRE2_ERROR_NOMATCH).

يتم تعيين *pstart_offset و *poptions إذا أعادت الدالة 1. يجب تمرير *pstart_offset إلى محاولة المطابقة التالية مباشرة، ويجب تمرير *poptions إلى محاولة المطابقة التالية عن طريق دمجها مع خيارات المطابقة للتطبيق باستخدام OR.

هناك بعض التعليمات البرمجية التي توضح كيفية القيام بذلك في برنامج العينة pcre2demo. النمط العام هو:

  uint32_t app_options = ...;
  uint32_t global_options = 0;
  PCRE2_SIZE start_offset = 0;
  while (1)
    {
    int rc = pcre2_match(re, subject, subject_len, start_offset,
                         app_options | global_options, match_data,
                         match_context);
    if (rc == PCRE2_ERROR_NOMATCH) break; /* no match, and no more attempts */
    if (rc < 0) { ... exit }
    ...handle the match
    if (!pcre2_next_match(match_data, &start_offset, &global_options))
      break; /* no more attempts */
    }

DESCRIPTION

The pcre2_dfa_match() function is called to perform a match using the DFA algorithm. This is an alternative matching algorithm that is available in PCRE2. It has different performance characteristics and some different features from the standard backtracking algorithm implemented by pcre2_match().

The arguments are:

j
Pointer to the JIT environment, or NULL.
code
Pointer to the compiled regular expression.
subject
Pointer to the subject string.
length
The length of the subject string.
startoffset
The offset into the subject at which to start matching.
options
A bitmask of options. For pcre2_dfa_match(), the valid bits are PCRE2_ANCHORED, PCRE2_NOTBOL, PCRE2_NOTEOL, PCRE2_NOTEMPTY, PCRE2_NOTEMPTY_ATSTART, PCRE2_PARTIAL_HARD, PCRE2_PARTIAL_SOFT, PCRE2_DFA_SHORTEST, and PCRE2_DFA_RESTART.
match_data
Pointer to a match data block, which is used to receive information about the match. It must have been previously created by pcre2_match_data_create() or pcre2_match_data_create_with_options().
workspace
Pointer to a vector that is used for intermediate data during the match. It must have been previously created by pcre2_workspace_create().
wscount
The number of elements in the workspace vector.

The return value is the number of matches found, or a negative error code. On success, the return value is greater than zero, indicating the number of complete matches found. If no complete matches are found, the return value is zero.

The pcre2_dfa_match() function may find multiple matches within the subject string. The results are stored in the match data block, which should have been created with sufficient capacity using pcre2_match_data_create() or pcre2_match_data_create_with_options(). The number of elements needed is determined by the number of capture groups in the pattern plus one. The size of the ovector should be at least 2 * (number of capture groups + 1) elements.

The DFA matching algorithm does not support capture groups. All substrings found are stored in the ovector as a list of potential matches, ordered by length from longest to shortest. The first element of the ovector always contains the offset and length of the entire match. Subsequent elements contain the offsets and lengths of any initial substrings that also constitute a match.

The pcre2_match_data_create() and pcre2_match_data_create_with_options() functions take an argument for the number of groups. For use with pcre2_dfa_match(), this should be set to 0, as capture groups are not supported.

The pcre2_workspace_create() function creates a vector that is used for internal data during the match process. The size required depends on the complexity of the pattern and the length of the subject string. It is recommended to use pcre2_workspace_copy_with_options(), which dynamically allocates sufficient space.

Partial matching

Partial matching with pcre2_dfa_match() works similarly to that for pcre2_match(), but the details are slightly different. When PCRE2_PARTIAL_HARD is set for pcre2_dfa_match(), it returns PCRE2_ERROR_PARTIAL if the end of the subject is reached and there is still at least one matching possibility that requires additional characters. This happens even if some complete matches have already been found. When PCRE2_PARTIAL_SOFT is set, the return code PCRE2_ERROR_NOMATCH is converted into PCRE2_ERROR_PARTIAL if the end of the subject is reached, there have been no complete matches, but there is still at least one matching possibility. The portion of the string that was inspected when the longest partial match was found is set as the first matching string in both cases. There is a more detailed discussion of partial and multi-segment matching, with examples, in the pcre2partial documentation.


PCRE2_DFA_SHORTEST

Setting the PCRE2_DFA_SHORTEST option causes the matching algorithm to stop as soon as it has found one match. Because of the way the alternative algorithm works, this is necessarily the shortest possible match at the first possible matching point in the subject string.


PCRE2_DFA_RESTART

When pcre2_dfa_match() returns a partial match, it is possible to call it again, with additional subject characters, and have it continue with the same match. The PCRE2_DFA_RESTART option requests this action; when it is set, the workspace and wscount options must reference the same vector as before because data about the match so far is left in them after a partial match. There is more discussion of this facility in the pcre2partial documentation.

Successful returns from pcre2_dfa_match()

When pcre2_dfa_match() succeeds, it may have matched more than one substring in the subject. Note, however, that all the matches from one run of the function start at the same point in the subject. The shorter matches are all initial substrings of the longer matches. For example, if the pattern


<.*>

is matched against the string


This is <something> <something else> <something further> no more

the three matched strings are


<something> <something else> <something further>
<something> <something else>
<something>

On success, the yield of the function is a number greater than zero, which is the number of matched substrings. The offsets of the substrings are returned in the ovector, and can be extracted by number in the same way as for pcre2_match(), but the numbers bear no relation to any capture groups that may exist in the pattern, because DFA matching does not support capturing.

Calls to the convenience functions that extract substrings by name return the error PCRE2_ERROR_DFA_UFUNC (unsupported function) if used after a DFA match. The convenience functions that extract substrings by number never return PCRE2_ERROR_NOSUBSTRING.

The matched strings are stored in the ovector in reverse order of length; that is, the longest matching string is first. If there were too many matches to fit into the ovector, the yield of the function is zero, and the vector is filled with the longest matches.

NOTE: PCRE2's "auto-possessification" optimization usually applies to character repeats at the end of a pattern (as well as internally). For example, the pattern "a\d+" is compiled as if it were "a\d++". For DFA matching, this means that only one possible match is found. If you really do want multiple matches in such cases, either use an ungreedy repeat such as "a\d+?" or set the PCRE2_NO_AUTO_POSSESS option when compiling.

Error returns from pcre2_dfa_match()

The pcre2_dfa_match() function returns a negative number when it fails. Many of the errors are the same as for pcre2_match(), as described above. There are in addition the following errors that are specific to pcre2_dfa_match():


PCRE2_ERROR_DFA_UITEM

This return is given if pcre2_dfa_match() encounters an item in the pattern that it does not support, for instance, the use of \C in a UTF mode or a backreference.


PCRE2_ERROR_DFA_UCOND

This return is given if pcre2_dfa_match() encounters a condition item that uses a backreference for the condition, or a test for recursion in a specific capture group. These are not supported.


PCRE2_ERROR_DFA_UINVALID_UTF

This return is given if pcre2_dfa_match() is called for a pattern that was compiled with PCRE2_MATCH_INVALID_UTF. This is not supported for DFA matching.


PCRE2_ERROR_DFA_WSSIZE

This return is given if pcre2_dfa_match() runs out of space in the workspace vector.


PCRE2_ERROR_DFA_RECURSE

When a recursion or subroutine call is processed, the matching function calls itself recursively, using private memory for the ovector and workspace. This error is given if the internal ovector is not large enough. This should be extremely rare, as a vector of size 1000 is used.


PCRE2_ERROR_DFA_BADRESTART

When pcre2_dfa_match() is called with the PCRE2_DFA_RESTART option, some plausibility checks are made on the contents of the workspace, which should contain data about the previous partial match. If any of these checks fail, this error is given.
