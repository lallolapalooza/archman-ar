الحزمة: python-pyperformance

التراخيص: MIT

PYTHONPERFORMANCEBENCHMARKSUITE(1) مجموعة اختبار أداء بايثون PYTHONPERFORMANCEBENCHMARKSUITE(1)

الاسم

pythonperformancebenchmarksuite - توثيق مجموعة اختبار أداء بايثون

يهدف مشروع pyperformance إلى أن يكون مصدرًا موثوقًا لاختبارات الأداء لجميع تطبيقات بايثون. التركيز هو على اختبارات الأداء الواقعية، بدلاً من الاختبارات الاصطناعية، باستخدام تطبيقات كاملة إن أمكن.

  • توثيق pyperformance http://pyperformance.readthedocs.io/
  • مشروع pyperformance على GitHub https://github.com/python/pyperformance (الكود المصدري، المشكلات)
  • تنزيل pyperformance على PyPI https://pypi.python.org/pypi/pyperformance

يتم توزيع pyperformance بموجب ترخيص MIT.

التوثيق:

الاستخدام

التثبيت

الأمر لتثبيت pyperformance:

python3 -m pip install pyperformance

يقوم الأمر بتثبيت برنامج جديد باسم pyperformance.

إذا لزم الأمر، يتم تثبيت تبعيات pyperf و six تلقائيًا.

يعمل pyperformance على بايثون 3.6 والإصدارات الأحدث، ولكنه قد يعمل أيضًا على بايثون 3.4 و 3.5.

في وقت التشغيل، قد تكون ملفات تطوير بايثون (ملفات الرأس) مطلوبة لتثبيت بعض التبعيات مثل dulwich_log أو psutil، لبناء امتدادات C الخاصة بها. الأوامر على Fedora لتثبيت التبعيات:

  • بايثون 3: sudo dnf install python3-devel
  • PyPy: sudo dnf install pypy-devel

ملاحظات ويندوز

على ويندوز، للسماح لـ pyperformance ببناء التبعيات من المصدر مثل greenlet أو dulwich أو psutil، إذا كنت ترغب في استخدام python.exe تم بناؤه من المصدر، يجب ألا تستخدم python.exe مباشرة. بدلاً من ذلك، يجب عليك تشغيل الأمر الأقل شهرة PC\layout لإنشاء تخطيط نظام ملفات يشبه تثبيت بايثون:

.\python.bat -m PC.layout --preset-default --copy installed -v

(استخدم علامة --help لمزيد من المعلومات حول PC\layout.)

الآن يمكنك استخدام ملف بايثون التنفيذي "المثبت":

installed\python.exe -m pip install pyperformance
installed\python.exe -m pyperformance run ...

استخدام ملف بايثون التنفيذي المثبت *فعليًا* (على سبيل المثال، عبر py) يعمل بشكل جيد أيضًا.

تشغيل اختبارات الأداء

الأوامر لمقارنة أداء بايثون 3.6 وبايثون 3.7:

pyperformance run --python=python3.6 -o py36.json
pyperformance run --python=python3.7 -o py37.json
pyperformance compare py36.json py37.json

ملاحظة: صيغة python3 -m pyperformance ... تعمل أيضًا (مثال: python3 -m pyperformance run -o py37.json)، ولكنها تتطلب تثبيت pyperformance على كل إصدار بايثون تم اختباره.

يتم إنتاج ملفات JSON بواسطة وحدة pyperf، وبالتالي يمكن تحليلها باستخدام أوامر pyperf:

python3 -m pyperf show py36.json
python3 -m pyperf check py36.json
python3 -m pyperf metadata py36.json
python3 -m pyperf stats py36.json
python3 -m pyperf hist py36.json
python3 -m pyperf dump py36.json
(...)

من الممكن أيضًا استخدام pyperf لمقارنة نتائج ملفي JSON:

python3 -m pyperf compare_to py36.json py37.json --table

خيارات شائعة

الخيارات المتاحة لجميع الأوامر:

-h, --help            إظهار رسالة المساعدة هذه والخروج

run

تشغيل اختبارات الأداء على بايثون الحالي.

الاستخدام:

pyperformance run [-h] [-r] [-f] [--debug-single-value] [-v] [-m]
                     [--affinity CPU_LIST] [-o FILENAME]
                     [--append FILENAME] [--manifest MANIFEST]
                     [--timeout TIMEOUT] [-b BM_LIST]
                     [--inherit-environ VAR_LIST] [-p PYTHON]
                     [--hook HOOK]

خيارات:

-h, --help            إظهار رسالة المساعدة هذه والخروج
-r, --rigorous        قضاء وقت أطول في تشغيل الاختبارات للحصول على
                      نتائج أكثر دقة
-f, --fast            الحصول على إجابات تقريبية بسرعة
--debug-single-value  تصحيح الأخطاء: أسرع وضع، حساب قيمة واحدة فقط
-v, --verbose         طباعة المزيد من المخرجات
-m, --track-memory    تتبع استخدام الذاكرة. يعمل هذا فقط على لينكس.
--affinity CPU_LIST   تحديد ارتباط وحدة المعالجة المركزية لتشغيلات اختبارات الأداء.
                      بهذه الطريقة، يمكن إجبار اختبارات الأداء على التشغيل
                      على وحدة معالجة مركزية معينة لتقليل التباين من تشغيل لآخر.
-o FILENAME, --output FILENAME
                      تشغيل اختبارات الأداء على مفسر واحد فقط وكتابة
                      اختبارات الأداء إلى FILENAME. قدم فقط
                      baseline_python، وليس changed_python.
--append FILENAME     إضافة تشغيلات إلى ملف موجود، أو إنشاؤه إذا
                      لم يكن موجودًا
--timeout TIMEOUT     تحديد مهلة بالثواني لتشغيل اختبار أداء واحد
                      (الافتراضي: معطل)
--manifest MANIFEST   ملف بيان اختبارات الأداء المراد استخدامه
-b BM_LIST, --benchmarks BM_LIST
                      قائمة مفصولة بفواصل من اختبارات الأداء المراد تشغيلها.
                      يمكن أن تحتوي على وسيطات موجبة وسالبة:
                      --benchmarks=run_this,also_this,-not_this. إذا
                      لم تكن هناك وسيطات موجبة، فسنقوم بتشغيل جميع
                      اختبارات الأداء باستثناء الوسيطات السالبة.
                      بخلاف ذلك، سنقوم بتشغيل الوسيطات الموجبة فقط.
--inherit-environ VAR_LIST
                      قائمة مفصولة بفواصل بأسماء متغيرات البيئة
                      التي يتم وراثتها من البيئة الأصلية عند تشغيل
                      عمليات اختبارات الأداء الفرعية.
-p PYTHON, --python PYTHON
                      ملف بايثون التنفيذي (الافتراضي: استخدام بايثون
                      الحالي)
--same-loops SAME_LOOPS
                      استخدام نفس عدد الحلقات مثل التشغيل السابق
                      (أي، لا تعيد المعايرة). يجب أن يكون مسارًا
                      إلى ملف .json من تشغيل سابق.
--hook HOOK
                      تطبيق خطاف pyperf المحدد عند تشغيل اختبارات الأداء.

compare

مقارنة ملفي اختبار أداء.

الاستخدام:

pyperformance compare [-h] [-v] [-O STYLE] [--csv CSV_FILE]
                      [--inherit-environ VAR_LIST] [-p PYTHON]
                      baseline_file.json changed_file.json

وسيطات موضعية:

baseline_file.json
changed_file.json

خيارات:

-v, --verbose         طباعة المزيد من المخرجات
-O STYLE, --output_style STYLE
                      ما هو نمط إخراج اختبار الأداء.
                      الخيارات الصالحة هي 'normal' و 'table'.
                      الافتراضي هو normal.
--csv CSV_FILE        اسم ملف ستتم كتابة النتائج إليه،

هذا الموقع غير مرتبط بـ Arch Linux ولا تابع له بأي شكل من الأشكال. المحتوى هو ترجمة فقط لصفحات دليل Arch المنشورة على man.archlinux.org.

كملف CSV بثلاثة أعمدة يحتوي على الحد الأدنى من أوقات التشغيل لكل معيار أداء. --inherit-environ VAR_LIST قائمة مفصولة بفواصل لأسماء متغيرات البيئة التي يتم توريثها من البيئة الأم عند تشغيل العمليات الفرعية لقياس الأداء. -p PYTHON, --python PYTHON ملف Python التنفيذي (الافتراضي: استخدام Python قيد التشغيل)

Compile Python to run benchmarks

إجراءات pyperformance:

compile             تجميع وتثبيت CPython وتشغيل معايير الأداء على
                    Python المثبت
compile_all         تجميع وتثبيت CPython وتشغيل معايير الأداء على
                    Python المثبت على جميع الفروع والمراجعات لـ
                    CONFIG_FILE
upload              تحميل نتائج JSON إلى موقع Codespeed

تتطلب جميع هذه الأوامر ملف تكوين.

تكوين بسيط قابل للاستخدام لـ compile (ولكن ليس لـ compile_all أو upload)، doc/benchmark.conf:

[config]
json_dir = ~/prog/python/bench_json
[scm]
repo_dir = ~/prog/python/master
update = True
[compile]
bench_dir = ~/prog/python/bench_tmpdir
[run_benchmark]
system_tune = True
affinity = 2,3

عينة ملف التكوين مع تعليقات، doc/benchmark.conf.sample:

[config]
# دليل حيث يتم كتابة ملفات JSON.
# - يتم نقل الملفات التي تم تحميلها إلى json_dir/uploaded/
# - يتم كتابة نتائج Python المعدلة في json_dir/patch/
json_dir = ~/json
# إذا كانت True، فسيتم تجميع CPython في وضع التصحيح (تعطيل LTO و PGO)،
# وتشغيل معايير الأداء باستخدام --debug-single-sample، وتعطيل التحميل.
#
# استخدم هذا الخيار لاختبار التكوين بسرعة.
debug = False
[scm]
# دليل كود مصدر CPython (مستودع Git)
repo_dir = ~/cpython
# تحديث مستودع Git (git fetch)؟
update = True
# اسم مستودع Git البعيد، يستخدم لإنشاء مراجعة لـ
# فرع Git. على سبيل المثال، استخدم المراجعة 'remotes/origin/3.6'
# للفرع '3.6'.
git_remote = remotes/origin
[compile]
# إنشاء ملفات في bench_dir:
# - bench_dir/bench-xxx.log
# - bench_dir/prefix/: حيث يتم تثبيت Python
# - bench_dir/venv/: البيئة الافتراضية التي يستخدمها pyperformance
bench_dir = ~/bench_tmpdir
# تحسين وقت الربط (LTO)؟
lto = True
# تحسين موجه بالملف الشخصي (PGO)؟
pgo = True
# بناء مترجم "just-in-time" (JIT) التجريبي؟
# القيم الممكنة هي:
# - no: (الافتراضي) لا تقم ببناء JIT أو مترجم micro-op.
#   المتغير البيئي الجديد PYTHON_JIT ليس له تأثير.
# - yes: بناء JIT وتمكينه افتراضيًا. يمكن استخدام PYTHON_JIT=0 لـ
#   تعطيله في وقت التشغيل.
# - yes-off: بناء JIT، ولكن لا تقم بتمكينه افتراضيًا. يمكن استخدام PYTHON_JIT=1 لـ
#   تمكينه في وقت التشغيل.
# - interpreter: لا تقم ببناء JIT، ولكن قم ببناء وتمكين مترجم micro-op.
#   هذا مفيد لمن يجدون أنفسهم يطورون
#   أو يصححون أخطاء micro-ops (ولكن لا يرغبون في التعامل مع JIT).
#   يمكن استخدام PYTHON_JIT=0 لتعطيل مترجم micro-op في وقت التشغيل.
jit = no
# قائمة المكتبات المنفصلة، مفصولة بمسافات، وهي خاصة بالحزم،
# أي مثبتة محليًا ولكن ليس في مسارات الرأس والمكتبة.
# لكل مكتبة من هذا القبيل، حدد مسار التثبيت وأضف
# مسارًا فرعيًا مناسبًا إلى تعريفات CFLAGS و LDFLAGS التي تم تمريرها
# إلى configure. كاستثناء، يتم تمرير البادئة لـ openssl، إذا كانت تلك
# المكتبة موجودة هنا، عبر الخيار --with-openssl. حاليًا، هذا يعمل فقط مع Homebrew على macOS.
# إذا كنت تعمل على macOS مع Homebrew، فمن المحتمل أن ترغب في استخدام:
#     pkg_only = openssl readline sqlite3 xz zlib
# الإصدار من zlib الذي يأتي مع macOS يعمل على الأرجح أيضًا،
# طالما تم تثبيت رؤوس SDK الخاصة بـ Apple.

# تثبيت Python؟ إذا كان خطأ، فقم بتشغيل Python من دليل الإنشاء
#
# تحذير: تشغيل Python من دليل الإنشاء يقدم تغييرات دقيقة
# مقارنة بتشغيل Python مثبت. علاوة على ذلك، إنشاء بيئة افتراضية
# باستخدام Python يتم تشغيله من دليل الإنشاء يفشل في العديد من الحالات،
# خاصة على Python الأقدم من 3.4. قم بتعطيل التثبيت فقط إذا كنت
# تفهم حقًا ما تفعله!

# تحديد المعلمة '-j' في أمر 'make'

[run_benchmark]
# تشغيل "sudo python3 -m pyperf system tune" قبل تشغيل معايير الأداء؟

# خيار --manifest لـ 'pyperformance run'

# خيار --affinity لـ 'pyperf system tune' و 'pyperformance run'

#
# يتم تعطيل التحميل على Python المعدل، في وضع التصحيح أو إذا كان التثبيت
# معطلاً.
upload = False
# تكوين لتحميل النتائج إلى موقع Codespeed
[upload]

# قائمة فروع Git لـ CPython

    Telco Benchmark for measuring the performance of decimal calculations:

    • http://speleotrove.com/decimal/telco.html
    • http://speleotrove.com/decimal/telcoSpec.html
    • A call type indicator, c, is set from the bottom (least significant) bit of the duration (hence c is 0 or 1).
    • A rate, r, is determined from the call type. Those calls with c=0 have a low r: 0.0013; the remainder (‘distance calls’) have a ‘premium’ r: 0.00894. (The rates are, very roughly, in Euros or dollarates per second.)
    • A price, p, for the call is then calculated (p=r*n). This is rounded to exactly 2 fractional digits using round-half-even (Banker’s round to nearest).
    • A basic tax, b, is calculated: b=p*0.0675 (6.75%). This is truncated to exactly 2 fractional digits (round-down), and the total basic tax variable is then incremented (sumB=sumB+b).
    • For distance calls: a distance tax, d, is calculated: d=p*0.0341 (3.41%). This is truncated to exactly 2 fractional digits (round-down), and then the total distance tax variable is incremented (sumD=sumD+d).
    • The total price, t, is calculated (t=p+b, and, if a distance call, t=t+d).
    • The total prices variable is incremented (sumT=sumT+t).
    • The total price, t, is converted to a string, s.

CUSTOM BENCHMARKS

pyperformance includes its own set of benchmarks (see Benchmarks <>). However, it also supports using custom benchmarks.

Using Custom Benchmarks

To use custom benchmarks, you will need to use the --manifest CLI option and provide the path to the manifest file describing those benchmarks.

The pyperformance File Formats

pyperformance uses two file formats to identify benchmarks:

  • manifest - a set of benchmarks
  • metadata - a single benchmark

For each benchmark, there are two required files and several optional ones. Those files are expected to be in a specific directory structure (unless customized in the metadata).

The structure (see below) is such that it's easy to maintain a benchmark (or set of benchmarks) on GitHub and distribute it on PyPI. It also simplifies publishing a Python project's benchmarks. The alternative is pointing people at a repo.

Benchmarks can inherit metadata from other metadata files. This is useful for keeping common metadata for a set of benchmarks (e.g. "version") in one file. Likewise, benchmarks for a Python project can inherit metadata from the project's pyproject.toml.

Sometimes a benchmark will have one or more variants that run using the same script. Variants like this are supported by pyperformance without requiring much extra effort.

Benchmark Directory Structure

Normally a benchmark is structured like this:

bm_NAME/
   data/  # if needed
   requirements.txt  # lock file, if any
   pyproject.toml
   run_benchmark.py

(Note the "bm_" prefix on the directory name.)

"pyproject.toml" holds the metadata. "run_benchmark.py" holds the actual benchmark code. Both are necessary.

pyperformance treats the metadata file as the fundamental source of information about a benchmark. A manifest for a set of benchmarks is effectively a mapping of names to metadata files. So a metadata file is essential. It can be located anywhere on disk. However, if it isn't located in the structure described above then the metadata must identify where to find the other files.

Other than that, only a benchmark script (e.g. "run_benchmark.py" above) is required. All other files are optional.

When a benchmark has variants, each has its own metadata file next to the normal "pyproject.toml", named "bm_NAME.toml". (Note the "bm_" prefix.) The format of variant metadata files is exactly the same. pyperformance treats them the same, except that the sibling "pyproject.toml" is inherited by default.

Manifest Files

A manifest file identifies a set of benchmarks, as well as (optionally) how they should be grouped. pyperformance uses the manifest to determine which benchmarks are available to run (and thus which to run by default).

A manifest normally looks like this:

[benchmarks]
name        metafile
bench1      somedir/bm_bench1/pyproject.toml
bench2      somedir/pyproject.toml
bench3      ../anotherdir

The "benchmarks" section is a table with rows of tab-separated-values. The "name" value is how pyperformance will identify the benchmark. The "metafile" value is where pyperformance will look for the benchmark's metadata. If a metafile is a directory then it looks for "pyproject.toml" in that directory.

تنسيق ملف البيان

يحدد ملف البيان MANIFEST كيف يتم البحث عن مواصفات المعيار. يتم تنظيمها في أقسام.

فيما يلي مثال على قسم "المعايير":

[benchmarks]
name        metafile
bench1      somedir/bm_bench1
bench2      somedir/bm_bench2
bench3      anotherdir/mybench.toml

يجب أن تحتوي كل صفوف قسم "المعايير" على عمودين على الأقل: "name" وهو اسم المعيار، و "metafile" وهو المسار إلى ملف بيانات التعريف الخاص بالمعيار (عادةً ملف pyproject.toml).

يمكن أن تكون ملفات البيانات التعريفية في أي مكان، ولكن يجب أن تكون عادةً في دليل شقيق (sibling directory) لدليل ملف البيان.

مجموعات المعايير

تتيح لك أقسام "groups" و "group <name>" في ملف البيان تجميع المعايير.

فيما يلي مثال توضيحي لقسم البيان المتعلق بالتجميع:

[benchmarks]
name        metafile
bench1      somedir/bm_bench1
bench2      somedir/bm_bench2
bench3      anotherdir/mybench.toml
[groups]
tag1
tag2
[group default]
bench2
bench3
[group tricky]
bench2

يحدد قسم "groups" المجموعات المتاحة التي يمكن تحديدها بواسطة علامات المعايير (راجع العلامات حول قسم البيانات التعريفية أدناه). أي أقسام مجموعات أخرى في البيان تضاف تلقائيًا إلى قائمة المجموعات المتاحة.

إذا لم يتم تحديد مجموعة "افتراضية"، فسيتم إضافة واحدة تلقائيًا تحتوي على جميع المعايير من قسم "benchmarks". إذا لم يكن هناك قسم "groups" ولا توجد أقسام مجموعات فردية (بخلاف "default") فسيتم التعامل مع مجموعة جميع العلامات الخاصة بالمعايير المعروفة على أنها "groups". سيتم أيضًا إضافة مجموعة تسمى "all" تحتوي على جميع المعايير المعروفة.

يمكن استبعاد المعايير من مجموعة باستخدام بادئة - (ناقص). أي معيار موجود بالفعل في القائمة (في تلك النقطة) يطابق سيتم إسقاطه من القائمة. إذا كان الإدخال الأول في القسم هو استبعاد، فسيتم إضافة جميع المعايير المعروفة إلى القائمة قبل تطبيق الاستبعاد.

على سبيل المثال:

[benchmarks]
name        metafile
bench1      somedir/bm_bench1
bench2      somedir/bm_bench2
bench3      anotherdir/mybench.toml
[group default]
-bench1

هذا يعني بشكل افتراضي سيتم تشغيل "bench2" و "bench3" فقط.

دمج البيانات التعريفية

لدمج البيانات التعريفية، استخدم قسم [includes] في البيان:

[includes]
project1/benchmarks/MANIFEST
project2/benchmarks/MANIFEST
<default>

لاحظ أن <default> يعادل تضمين ملف البيان لمعايير pyperformance الافتراضية.

مجموعة معايير محلية

غالبًا ما يكون لدى المشروع أكثر من معيار واحد سيعتبره كمجموعة. يتعامل pyperformance مع هذا دون أي عمل إضافي.

في الدليل الذي يحمل ملف البيان، ضع جميع المعايير. ثم ضع <local> في عمود "metafile"، كما يلي:

[benchmarks]
name        metafile
bench1      <local>
bench2      <local>
bench3      <local>
bench4      <local>
bench5      <local>

سيبحث عن DIR/bm_NAME/pyproject.toml.

إذا كانت هناك أيضًا متغيرات، حدد المعيار الرئيسي في قيمة "metafile"، كما يلي:

[benchmarks]
name        metafile
bench1      <local>
bench2      <local>
bench3      <local>
variant1    <local:bench3>
variant2    <local:bench3>

سيبحث pyperformance عن DIR/bm_BASE/bm_NAME.toml، حيث "BASE" هو الجزء الذي يلي "local:".

مجموعة معايير المشروع

يمكن لمشروع Python تحديد مجموعة المعايير الخاصة به عن طريق وضع المسار إلى ملف البيان في ملف pyproject.toml الخاص بالمشروع على المستوى الأعلى. يمكن تحديد بيانات تعريفية إضافية أيضًا:

[tool.pyperformance]
manifest = "..."
manifests = ["...", "..."]

(تذكير: هذا هو ملف pyproject.toml، وليس ملف البيان.)

ملفات بيانات تعريف المعايير

يتبع ملف بيانات تعريف المعيار (عادةً ملف pyproject.toml) التنسيق المحدد في PEP 621 https://www.python.org/dev/peps/pep-0621 و PEP 518 https://www.python.org/dev/peps/pep-0518. لذلك هناك قسمان مدعومان في الملف: "project" و "tool.pyperformance".

ملف بيانات تعريف نموذجي سيبدو كالتالي:

[project]
version = "0.9.1"
dependencies = ["pyperf"]
dynamic = ["name"]
[tool.pyperformance]
name = "my_benchmark"

ملف مفصل للغاية قد يبدو كالتالي:

[project]
name = "pyperformance_bm_json_dumps"
version = "0.9.1"
description = "A benchmark for json.dumps()"
requires-python = ">=3.8"
dependencies = ["pyperf"]
urls = {repository = "https://github.com/python/pyperformance"}
dynamic = ["version"]
[tool.pyperformance]
name = "json_dumps"
tags = "serialize"
runscript = "bench.py"
datadir = ".data-files/extras"
extra_opts = ["--special"]

الوراثة

لكي يرث معيار من معيار آخر (أو من بيانات تعريف مشتركة)، يتوفر حقل "inherits":

[project]
dependencies = ["pyperf"]
dynamic = ["name", "version"]
[tool.pyperformance]
name = "my_benchmark"
inherits = "../common.toml"

تعامل جميع القيم في أي من قسمي البيانات التعريفية الموروثة على أنها قيم افتراضية، وفوقها تطبق البيانات التعريفية الحالية. في المثال أعلاه، على سبيل المثال، سيتم استخدام قيمة "version" في common.toml هنا.

إذا كانت قيمة "inherits" دليلًا (حتى بالنسبة لـ "..") فسيتم وراثة "base.toml" في ذلك الدليل.

بالنسبة للمتغيرات، فإن ملف pyproject.toml الأساسي هو القيمة الافتراضية لـ "inherits".

القيم المستنتجة

في بعض الحالات، سيتم استنتاج القيم المفقودة من بيانات أخرى متاحة (حتى بالنسبة للحقول المطلوبة).

  • project.name <= tool.pyperformance.name
  • project.* <= البيانات التعريفية الموروثة (باستثناء "name" و "dynamic")
  • tool.pyperformance.name <= اسم ملف البيانات التعريفية
  • tool.pyperformance.* <= البيانات التعريفية الموروثة (باستثناء "name" و "inherits")

عند استنتاج الاسم من اسم الملف لمعيار منظم بشكل منتظم، تتم إزالة البادئة "bm_" من دليل المعيار. إذا كان متغيرًا، تتم إزالة تلك البادئة من اسم ملف البيانات التعريفية، بالإضافة إلى لاحقة .toml.

قسم [project]

حقل نوع R T B D
project.name str X X
project.version ver X X X
project.dependencies [str] X
project.dynamic [str]

"R": مطلوب "T": مستنتج من قسم الأداة "B": مستنتج من البيانات التعريفية الموروثة "D": للمعايير الافتراضية، مستنتج من pyperformance

"dynamic" مطلوب بواسطة PEP 621 عندما سيتم ملء حقل ديناميكيًا بواسطة الأداة. هذا مهم بشكل خاص للحقول المطلوبة.

جميع حقول PEP 621 الأخرى اختيارية (مثل requires-python = ">=3.8"، {repository = "https://github.com/..."}).

قسم [tool.pyperformance]

حقل نوع R B F
tool.name str X X
tool.tags [str] X
tool.extra_opts [str] X
tool.inherits file
tool.runscript file

نتائج CPython، 2017

تم تحديث نتائج CPython لعام 2017.

تم نقل المشروع إلى https://github.com/python/performance في أغسطس 2016. تم إعادة تنظيم الملفات، وتم تعديل اختبارات الأداء لاستخدام وحدة perf لتشغيل اختبارات الأداء في عمليات متعددة.
