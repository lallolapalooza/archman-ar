Server WebSocket

We're going to use WebSockets to exchange messages between the web page and the server. This is a bit more complex than sending HTTP requests because it requires running two processes:

  • The web server (e.g. Python's http.server) serves the web page, CSS and JavaScript.
  • The WebSocket server (e.g. websockets) handles communication with the web page.

The web page will be able to find the WebSocket server by running a small HTTP server in the same directory. It will then connect to ws://localhost:8001.

Here's how you can set up the two servers:

    # Check horizontal

        if all(board[row][c+i] == player_token for i in range(4)):
            return True

    # Check vertical
    for r in range(6 - 3):
        if all(board[r+i][col] == player_token for i in range(4)):
            return True

    # Check diagonal (top-left to bottom-right)
    for r in range(6 - 3):
        for c in range(7 - 3):
            if all(board[r+i][c+i] == player_token for i in range(4)):
                return True

    # Check diagonal (bottom-left to top-right)
    for r in range(3, 6):
        for c in range(7 - 3):
            if all(board[r-i][c+i] == player_token for i in range(4)):
                return True

    return False

    """Generate a random string of fixed length."""
    letters = string.ascii_lowercase + string.digits
    return "".join(random.choice(letters) for i in range(length))

async def error(websocket, message):
    event = {
        "type": "error",
        "message": message,
    }
    await websocket.send(json.dumps(event))

async def play(websocket, game, player, connected):
    """Receive and process moves from the given player."""
    async for message in websocket:
        try:
            event = json.loads(message)
            if event["type"] == "play":
                column = event["column"]
                # Check if the move is valid.
                row = game.play(player, column)
                if row is None:
                    await error(websocket, "Invalid move.")
                    continue
                # Send the move to all connected clients.
                event = {
                    "type": "play",
                    "player": player,
                    "column": column,
                    "row": row,
                }
                await asyncio.wait([ws.send(json.dumps(event)) for ws in connected])
                # Check if the game is won.
                if game.won():
                    await asyncio.wait([ws.send(json.dumps({"type": "win", "player": player})) for ws in connected])
            else:
                raise InvalidMessageError("Unsupported event type.")
        except (json.JSONDecodeError, KeyError, InvalidMessageError, TypeError):
            await error(websocket, "Malformed message received.")
async def replay(websocket, game):
    """Send moves from the given game to the newly connected client."""
    for player, column, row in game.history:
        event = {
            "type": "play",
            "player": player,
            "column": column,
            "row": row,
        }
        await websocket.send(json.dumps(event))

    # Generate a unique game ID and keys for joining and watching.
    game_id = random_string()
    join_key = random_string()
    watch_key = random_string()
    # Create a new Connect Four game.
    game = Game()
    # Store the game and the set of connected clients.
    connected = {websocket}
    JOIN[join_key] = (game, connected)
    WATCH[watch_key] = (game, connected)
    # Send the unique keys to the browser of the first player,
    # where they'll be used for building "join" and "watch" links.
    event = {
        "type": "init",
        "join": join_key,
        "watch": watch_key,
    }
    await websocket.send(json.dumps(event))
    # Receive and process moves from the first player.
    await play(websocket, game, PLAYER1, connected)
finally:
    del JOIN[join_key]
    del WATCH[watch_key]
async def join(websocket, join_key):
    """
    Handle a connection from the second player: join an existing game.
    """
    # Find the Connect Four game.
    try:
        game, connected = JOIN[join_key]
    except KeyError:
        await error(websocket, "Game not found.")
        return
    # Register to receive moves from this game.
    connected.add(websocket)
    try:
        # Send the first move, in case the first player already played it.
        await replay(websocket, game)
        # Receive and process moves from the second player.
        await play(websocket, game, PLAYER2, connected)
    finally:
        connected.remove(websocket)
async def watch(websocket, watch_key):
    """
    Handle a connection from a spectator: watch an existing game.
    """
    # Find the Connect Four game.
    try:
        game, connected = WATCH[watch_key]
    except KeyError:
        await error(websocket, "Game not found.")
        return
    # Register to receive moves from this game.
    connected.add(websocket)
    try:
        # Send previous moves, in case the game already started.
        await replay(websocket, game)
        # Keep the connection open, but don't receive any messages.
        await websocket.wait_closed()
    finally:
        connected.remove(websocket)
async def handler(websocket):
    """
    Handle a connection and dispatch it according to who is connecting.
    """
    # Receive and parse the "init" event from the UI.
    message = await websocket.recv()
    event = json.loads(message)
    assert event["type"] == "init"
    if "join" in event:
        # Second player joins an existing game.
        await join(websocket, event["join"])
    elif "watch" in event:
        # Spectator watches an existing game.
        await watch(websocket, event["watch"])
    else:
        # First player starts a new game.
        await start(websocket)

    # Set the stop condition when receiving SIGTERM.
    loop = asyncio.get_running_loop()
    stop = loop.create_future()
    loop.add_signal_handler(signal.SIGTERM, stop.set_result, None)
    port = int(os.environ.get("PORT", "8001"))
    async with websockets.serve(handler, "", port):
        await stop
if __name__ == "__main__":
    asyncio.run(main())

خادم

•

التحقق من الرموز المميزة

دعنا ننتقل إلى خادم الـ websockets.

أضف الـ websockets إلى تبعيات مشروع Django الخاص بك و قم بتثبيتها. في الواقع، سنعيد استخدام بيئة مشروع Django، حتى نتمكن من استدعاء واجهات برمجة التطبيقات الخاصة به في خادم الـ websockets.

الآن إليك كيفية تطبيق المصادقة.

#!/usr/bin/env python
import asyncio
import django
import websockets
django.setup()
from sesame.utils import get_user
from websockets.frames import CloseCode
async def handler(websocket):
    sesame = await websocket.recv()
    user = await asyncio.to_thread(get_user, sesame)
    if user is None:
        await websocket.close(CloseCode.INTERNAL_ERROR, "authentication failed")
        return
    await websocket.send(f"Hello {user}!")
async def main():
    async with websockets.serve(handler, "localhost", 8888):
        await asyncio.Future()  # run forever
if __name__ == "__main__":
    asyncio.run(main())

دعنا نفصل هذا الكود.

نحن نستدعي django.setup() قبل القيام بأي شيء متعلق بـ Django لأننا نستخدم Django في برنامج نصي مستقل. هذا يفترض أن متغير البيئة DJANGO_SETTINGS_MODULE تم تعيينه إلى المسار البرمجي لوحدة الإعدادات الخاصة بك.

يقرأ معالج الاتصال الرسالة الأولى المستلمة من العميل، والتي يُتوقع أن تحتوي على رمز django-sesame. ثم يقوم بمصادقة المستخدم باستخدام get_user()، وهي واجهة برمجة التطبيقات المصادقة خارج العرض. إذا فشلت المصادقة، فإنه يغلق الاتصال ويخرج.

عندما نستدعي واجهة برمجة تطبيقات تقوم باستعلام قاعدة بيانات مثل get_user()، فإننا نغلف الاستدعاء في to_thread(). في الواقع، لا يدعم Django ORM الإدخال/الإخراج غير المتزامن. سيؤدي ذلك إلى حظر حلقة الأحداث إذا لم يتم تشغيله في خيط منفصل. to_thread() متاح منذ Python 3.9. في الإصدارات الأقدم، استخدم run_in_executor() بدلاً من ذلك.

أخيرًا، نبدأ خادمًا باستخدام serve().

نشر الأحداث

import json
from django.contrib.admin.models import LogEntry
from django.db.models.signals import post_save
from django.dispatch import receiver
from django_redis import get_redis_connection
@receiver(post_save, sender=LogEntry)
def publish_event(instance, **kwargs):
    event = {
        "model": instance.content_type.name,
        "object": instance.object_repr,
        "message": instance.get_change_message(),
        "timestamp": instance.action_time.isoformat(),
        "user": str(instance.user),
        "content_type_id": instance.content_type_id,
        "object_id": instance.object_id,
    }
    connection = get_redis_connection("default")
    payload = json.dumps(event)
    connection.publish("events", payload)

بث الأحداث

الآن دعنا ننتقل إلى قراءة الأحداث وبثها إلى العملاء المتصلين. نحن بحاجة إلى إضافة عدة ميزات:

  • تتبع العملاء المتصلين حتى نتمكن من بث الرسائل.
  • تحديد أنواع المحتوى التي يمتلك المستخدم إذنًا لعرضها أو تغييرها.
  • الاتصال بناقل الرسائل وقراءة الأحداث.
  • بث هذه الأحداث إلى المستخدمين الذين لديهم أذونات مقابلة.

إليك تنفيذ كامل.

#!/usr/bin/env python
import asyncio
import json
import aioredis
import django
import websockets
django.setup()
from django.contrib.contenttypes.models import ContentType
from sesame.utils import get_user
from websockets.frames import CloseCode
CONNECTIONS = {}
def get_content_types(user):
    """Return the set of IDs of content types visible by user."""
    # This does only three database queries because Django caches
    # all permissions on the first call to user.has_perm(...).
    return {
        ct.id
        for ct in ContentType.objects.all()
        if user.has_perm(f"{ct.app_label}.view_{ct.model}")
        or user.has_perm(f"{ct.app_label}.change_{ct.model}")
    }
async def handler(websocket):
    """Authenticate user and register connection in CONNECTIONS."""
    sesame = await websocket.recv()
    user = await asyncio.to_thread(get_user, sesame)
    if user is None:
        await websocket.close(CloseCode.INTERNAL_ERROR, "authentication failed")
        return
    ct_ids = await asyncio.to_thread(get_content_types, user)
    CONNECTIONS[websocket] = {"content_type_ids": ct_ids}
    try:
        await websocket.wait_closed()
    finally:
        del CONNECTIONS[websocket]
async def process_events():
    """Listen to events in Redis and process them."""
    redis = aioredis.from_url("redis://127.0.0.1:6379/1")
    pubsub = redis.pubsub()
    await pubsub.subscribe("events")
    async for message in pubsub.listen():
        if message["type"] != "message":
            continue
        payload = message["data"].decode()
        # Broadcast event to all users who have permissions to see it.
        event = json.loads(payload)
        recipients = (
            websocket
            for websocket, connection in CONNECTIONS.items()
            if event["content_type_id"] in connection["content_type_ids"]
        )
        websockets.broadcast(recipients, payload)
async def main():
    async with websockets.serve(handler, "localhost", 8888):
        await process_events()  # runs forever
if __name__ == "__main__":
    asyncio.run(main())

نظرًا لأن دالة get_content_types() تقوم باستعلام قاعدة بيانات، يتم تغليفها داخل asyncio.to_thread(). يتم تشغيلها مرة واحدة عند فتح كل اتصال WebSocket؛ ثم يتم تخزين نتيجتها مؤقتًا طوال عمر الاتصال. في الواقع، تشغيلها لكل رسالة سيؤدي إلى استعلامات قاعدة بيانات لجميع المستخدمين المتصلين في نفس الوقت، مما يضر بقاعدة البيانات.

يقوم معالج الاتصال ببساطة بتسجيل الاتصال في متغير عام، مقترنًا بقائمة أنواع المحتوى التي يجب إرسال الأحداث إليها لهذا الاتصال، وينتظر حتى ينفصل العميل.

s_events()

تقوم الدالة s_events() بقراءة الأحداث من Redis وبثها إلى جميع الاتصالات التي يجب أن تستقبلها. نحن لا نهتم كثيرًا إذا فشلت عملية إرسال إشعار - يحدث هذا عندما ينقطع اتصال بين لحظة تكرارنا للاتصالات ولحظة إرسال الرسالة المقابلة - لذلك نبدأ مهمة لكل رسالة ونتجاهلها. هذا يعني أيضًا أننا مستعدون فورًا لمعالجة الحدث التالي، حتى لو استغرق إرسال رسالة إلى عميل بطيء بعض الوقت.

كيف أصل إلى مسار الطلب؟

إنه متاح في السمة path.

يمكنك توجيه اتصال بمعالجات مختلفة اعتمادًا على مسار الطلب:

async def handler(websocket):
    if websocket.path == "/blue":
        await blue_handler(websocket)
    elif websocket.path == "/green":
        await green_handler(websocket)
    else:
        # No handler for this path; close the connection.
        return

يمكنك أيضًا توجيه الاتصال بناءً على الرسالة الأولى المستلمة من العميل، كما هو موضح في البرنامج التعليمي. عندما تريد المصادقة على الاتصال قبل توجيهه، يكون هذا عادةً أكثر ملاءمة.

بشكل عام، هناك تركيز أقل بكثير على مسار الطلب في خوادم WebSocket مقارنة بخوادم HTTP. عندما يوفر خادم WebSocket نقطة نهاية واحدة، قد يتجاهل مسار الطلب تمامًا.

كيف أصل إلى رؤوس HTTP؟

للوصول إلى رؤوس HTTP أثناء المصافحة WebSocket، يمكنك تجاوز process_request:

async def process_request(self, path, request_headers):
    authorization = request_headers["Authorization"]

بمجرد إنشاء الاتصال، تكون رؤوس HTTP متاحة في request_headers و response_headers:

async def handler(websocket):
    authorization = websocket.request_headers["Authorization"]

كيف أحدد رؤوس HTTP؟

لتحديد رؤوس Sec-WebSocket-Extensions أو Sec-WebSocket-Protocol في استجابة مصافحة WebSocket، استخدم الوسيطات extensions أو subprotocols الخاصة بـ serve().

لتجاوز رأس Server، استخدم الوسيط server_header. قم بتعيينه إلى None لإزالة الرأس.

لتحديد رؤوس HTTP أخرى، استخدم الوسيط extra_headers.

كيف أوقف خادمًا؟

اخرج من مدير سياق serve().

إليك مثال ينهي بشكل نظيف عند تلقي SIGTERM على Unix:

#!/usr/bin/env python
import asyncio
import signal
import websockets
async def echo(websocket):
    async for message in websocket:
        await websocket.send(message)
async def server():
    # Set the stop condition when receiving SIGTERM.
    loop = asyncio.get_running_loop()
    stop = loop.create_future()
    loop.add_signal_handler(signal.SIGTERM, stop.set_result, None)
    async with websockets.serve(echo, "localhost", 8765):
        await stop
asyncio.run(server())

async def server():

كيف أنفذ فحصًا للصحة؟

اعترض طلبات مصافحة WebSocket باستخدام خطاف process_request().

عند إرسال طلب إلى نقطة نهاية فحص الصحة، عامله كطلب HTTP وأرجع tuple (status, headers, body)، كما في هذا المثال:

#!/usr/bin/env python
import asyncio
import http
import websockets
async def health_check(path, request_headers):
    if path == "/healthz":
        return http.HTTPStatus.OK, [], b"OK\n"
async def echo(websocket):
    async for message in websocket:
        await websocket.send(message)
async def main():
    async with websockets.serve(
        echo, "localhost", 8765,
        process_request=health_check,
    ):
        await asyncio.Future()  # run forever
asyncio.run(main())

استخدام asyncio

كيف أشغل كوروتين اثنين بالتوازي؟

يجب عليك بدء مهمتين، والتي سيقوم حلقة الأحداث بتشغيلها بشكل متزامن. يمكنك تحقيق ذلك باستخدام asyncio.gather() أو asyncio.create_task().

احتفظ بسجل للمهام وتأكد من أنها تنتهي أو قم بإلغائها عند انتهاء الاتصال.

لماذا لا يستقبل برنامجي أي رسائل أبدًا؟

برنامجك يشغل كوروتين لا يمنح التحكم لحلقة الأحداث أبدًا. الكوروتين الذي يستقبل الرسائل لا يحصل أبدًا على فرصة للتشغيل.

وضع عبارة await في حلقة for أو while ليس كافيًا لمنح التحكم. انتظار كوروتين قد يمنح التحكم، ولكن لا يوجد ضمان بأنه سيفعل ذلك.

على سبيل المثال، send() يمنح التحكم فقط عندما تكون مخازن الإرسال ممتلئة، وهو ما لا يحدث أبدًا في معظم الحالات العملية.

إذا كنت تشغل حلقة تحتوي فقط على عمليات متزامنة واستدعاء send()، فيجب عليك منح التحكم بشكل صريح باستخدام asyncio.sleep():

async def producer(websocket):
    message = generate_next_message()
    await websocket.send(message)
    await asyncio.sleep(0)  # yield control to the event loop

asyncio.sleep() يعلق دائمًا المهمة الحالية، مما يسمح للمهام الأخرى بالتشغيل. تم توثيق هذا السلوك بالضبط لأنه غير متوقع من كل كوروتين.

لماذا أواجه مشاكل مع الخيوط؟

إذا اخترت التنفيذ الافتراضي لـ websockets المستند إلى asyncio، فلا يجب عليك استخدام الخيوط. في الواقع، يعد اختيار asyncio لمعالجة التزامن متعارضًا مع threading.

إذا كنت تعتقد أنك بحاجة إلى تشغيل websockets في خيط ومنطق معين في خيط آخر، فيجب عليك تشغيل هذا المنطق في Task بدلاً من ذلك. إذا كان يعيق حلقة الأحداث، فإن run_in_executor() سيساعد.

هذا السؤال يتعلق حقًا بـ asyncio. يرجى مراجعة النصيحة حول التزامن وتعدد الخيوط في توثيق Python.

لا توجد طريقة للتحكم في ضغط الإطارات الصادرة على أساس كل إطار على حدة (#538). إذا تم تمكين الضغط، يتم ضغط جميع الإطارات.

لا يتحقق الخادم من رأس Host ويستجيب بـ 400 Bad Request إذا كان مفقودًا أو غير صالح (#1246).

لا يحاول واجهة برمجة التطبيقات للعميل ضمان عدم وجود أكثر من اتصال واحد بعنوان IP معين في حالة CONNECTING. هذا السلوك مفروض بموجب RFC 6455. ومع ذلك، connect() ليس المستوى المناسب لفرض هذا القيد. إنها مسؤولية المتصل.

asyncio

هذا هو التنفيذ الافتراضي. إنه مثالي للخوادم التي تتعامل مع العديد من العملاء بشكل متزامن.

خادم (asyncio)

بدء الخادم

ابدأ خادم WebSocket يستمع على host و port.

عندما يتصل عميل، ينشئ الخادم WebSocketServerProtocol، ويجري مصافحة الفتح، ويفوض إلى معالج الاتصال، ws_handler.

يتلقى المعالج WebSocketServerProtocol ويستخدمه لإرسال واستقبال الرسائل.

بمجرد اكتمال المعالج، سواء بشكل طبيعي أو استثناء، يجري الخادم مصافحة الإغلاق ويغلق الاتصال.

انتظار serve() ينتج WebSocketServer. يوفر هذا الكائن طريقة close() لإيقاف الخادم:

stop = asyncio.Future()  # تعيين هذا المستقبل للخروج من الخادم
server = await serve(...)
await stop
await server.close()

يمكن استخدام serve() كمدير سياق غير متزامن. بعد ذلك، يتم إيقاف الخادم تلقائيًا عند الخروج من السياق:

stop = asyncio.Future()  # تعيين هذا المستقبل للخروج من الخادم
async with serve(...):
    await stop

  • origins (Optional[Sequence[Optional[Origin]]]) -- القيم المقبولة لرأس Origin، للدفاع ضد هجمات اختطاف WebSocket عبر المواقع. قم بتضمين None في القائمة إذا كان نقص الأصل مقبولًا.
  • extensions (Optional[Sequence[ServerExtensionFactory]]) -- قائمة الامتدادات المدعومة، بالترتيب الذي يجب أن يتم التفاوض عليها وتشغيلها به.
  • subprotocols (Optional[Sequence[Subprotocol]]) -- قائمة البروتوكولات الفرعية المدعومة، بترتيب الأفضلية المتناقصة.
  • extra_headers (Union[HeadersLike, Callable[[str, Headers], HeadersLike]]) -- رؤوس HTTP عشوائية لإضافتها إلى الاستجابة. يمكن أن يكون هذا HeadersLike أو قابلاً للاستدعاء يأخذ مسار الطلب والرؤوس كوسائط ويعيد HeadersLike.
  • server_header (Optional[str]) -- قيمة رأس استجابة Server. بشكل افتراضي هو "Python/x.y.z websockets/X.Y". تعيينه إلى None يزيل الرأس.
  • process_request (Optional[Callable[[str, Headers], Awaitable[Optional[Tuple[StatusLike, HeadersLike, bytes]]]]]) -- اعتراض طلب HTTP قبل مصافحة الفتح. انظر process_request() لمزيد من التفاصيل.
  • select_subprotocol (Optional[Callable[[Sequence[Subprotocol], Sequence[Subprotocol]], Subprotocol]]) -- اختيار بروتوكول فرعي يدعمه العميل. انظر select_subprotocol() لمزيد من التفاصيل.
  • open_timeout (Optional[float]) -- مهلة لفتح الاتصالات بالثواني. None يعطل المهلة.

استقبال الرسالة التالية.

عند إغلاق الاتصال، يثير recv() ConnectionClosed. على وجه التحديد، يثير ConnectionClosedOK بعد إغلاق طبيعي و ConnectionClosedError بعد خطأ في البروتوكول أو فشل في الشبكة. هذه هي الطريقة التي تكتشف بها نهاية تدفق الرسائل.

send(message)
إرسال رسالة.

يتم إرسال سلسلة نصية (str) كإطار Text. يتم إرسال سلسلة بايت أو كائن شبيه بالبايت (bytes، bytearray، أو memoryview) كإطار Binary.

send() تقبل أيضًا مكررًا من السلاسل النصية أو سلاسل البايت أو الكائنات الشبيهة بالبايت لتمكين التجزئة. يتم التعامل مع كل عنصر كجزء من الرسالة وإرساله في إطاره الخاص. يجب أن تكون جميع العناصر من نفس النوع، وإلا فسيثير send() خطأ TypeError وسيتم إغلاق الاتصال.

send() يرفض الكائنات الشبيهة بالقاموس لأن هذا غالبًا ما يكون خطأ. (إذا كنت تريد حقًا إرسال مفاتيح كائن شبيه بالقاموس كأجزاء، فاستدعِ طريقة keys() الخاصة به ومرر النتيجة إلى send().)

توجيه الاتصالات

ماذا يشمل التوجيه؟

نظرًا لأن طبقة التوجيه مكشوفة مباشرة للإنترنت ، فيجب أن توفر حماية مناسبة ضد التهديدات التي تتراوح من ضوضاء خلفية الإنترنت إلى الهجمات المستهدفة.

يجب عليك دائمًا تأمين اتصالات WebSocket باستخدام TLS. نظرًا لأن طبقة التوجيه تحمل اسم النطاق العام ، فيجب عليها إنهاء اتصالات TLS.

أخيرًا ، يجب عليها توجيه الاتصالات إلى عمليات الخادم ، وموازنة الاتصالات الجديدة عبرها.

كيف أقوم بتوجيه الاتصالات؟

فيما يلي الحلول النموذجية لموازنة التحميل ، المطابقة لطرق تشغيل العمليات:

1.
إذا كنت تعمل على منصة ، فهي تأتي مع طبقة توجيه:
  • Kubernetes Ingress و Service
  • شبكة خدمات: Istio ، Consul ، Linkerd ، إلخ.
  • شبكة توجيه كخدمة (Platform as a Service)
2.
إذا كنت تشغل N خادمًا ، يمكنك موازنة التحميل باستخدام:
  • موازن تحميل سحابي: AWS Elastic Load Balancing ، GCP Cloud Load Balancing ، إلخ.
  • موازن تحميل برمجي: HAProxy ، NGINX ، إلخ.
3.
إذا كنت تشغل N عمليات على خادم ، يمكنك موازنة التحميل باستخدام:
  • موازن تحميل برمجي: HAProxy ، NGINX ، إلخ.
  • نظام التشغيل - تستمع جميع العمليات على نفس المنفذ

يمكنك الوثوق بموازن التحميل للتعامل مع التشفير وتوفير الأمان. يمكنك إضافة طبقة أخرى أمام موازن التحميل لهذه الأغراض.

هناك العديد من الاحتمالات. لا تضف طبقات لا تحتاجها.

كيف أقوم بتنفيذ فحص الصحة؟

تحتاج موازنات التحميل إلى طريقة للتحقق مما إذا كانت عمليات الخادم تعمل وأنها قيد التشغيل لتجنب توجيه الاتصالات إلى خلفية غير وظيفية.

يوفر websockets الحد الأدنى من الدعم للاستجابة لطلبات HTTP باستخدام الخطاف process_request().

هذا مثال:

#!/usr/bin/env python
import asyncio
import http
import websockets
async def health_check(path, request_headers):
    if path == "/healthz":
        return http.HTTPStatus.OK, [], b"OK\n"
async def echo(websocket):
    async for message in websocket:
        await websocket.send(message)
async def main():
    async with websockets.serve(
        echo, "localhost", 8765,
        process_request=health_check,
    ):
        await asyncio.Future()  # run forever
asyncio.run(main())

التسجيل

محتويات السجلات

عند تشغيل عميل WebSocket ، تستدعي التعليمات البرمجية الخاصة بك coroutine التي توفرها websockets.

إذا حدث خطأ ، تخبرك websockets عن طريق إثارة استثناء. على سبيل المثال ، تثير استثناء ConnectionClosed إذا أغلق الطرف الآخر الاتصال.

عند تشغيل خادم WebSocket ، تقبل websockets الاتصالات ، وتجري المصافحة الافتتاحية ، وتشغل coroutine معالج الاتصال الذي قدمته ، وتجري المصافحة الختامية.

نظرًا لـ انعكاس التحكم هذا ، إذا حدث خطأ في المصافحة الافتتاحية أو تعطل معالج الاتصال ، فلا توجد طريقة لإثارة استثناء يمكنك التعامل معه.

السجلات تخبرك عن هذه الأخطاء.

بالإضافة إلى الأخطاء ، قد ترغب في تسجيل نشاط الخادم.

في بروتوكول طلب/استجابة مثل HTTP ، هناك طريقة واضحة لتسجيل النشاط: تسجيل حدث واحد لكل طلب/استجابة. لسوء الحظ ، لا يعمل هذا الحل بشكل جيد مع بروتوكول ثنائي الاتجاه مثل WebSocket.

بدلاً من ذلك ، عند التشغيل كخادم ، تسجل websockets حدثًا واحدًا عند إنشاء اتصال وحدثًا آخر عند إغلاق اتصال.

افتراضيًا ، لا تسجل websockets حدثًا لكل رسالة. سيكون ذلك مفرطًا للعديد من التطبيقات التي تتبادل رسائل صغيرة بمعدل سريع. إذا كنت بحاجة إلى هذا المستوى من التفاصيل ، يمكنك إضافة تسجيل في التعليمات البرمجية الخاصة بك.

أخيرًا ، يمكنك تمكين سجلات التصحيح للحصول على تفاصيل حول كل ما تفعله websockets. يمكن أن يكون هذا مفيدًا عند تطوير العملاء والخوادم.

انظر مستويات السجل أدناه للحصول على قائمة بالأحداث التي تسجلها سجلات websockets في كل مستوى سجل.

تكوين التسجيل

تعتمد websockets على وحدة logging من المكتبة القياسية لتحقيق أقصى قدر من التوافق والتكامل بشكل جيد مع المكتبات الأخرى:

import logging

تسجل websockets في المسجلات "websockets.client" و "websockets.server".

لا توفر websockets تكوين تسجيل افتراضي لأن المتطلبات تختلف كثيرًا اعتمادًا على البيئة.

هذا تكوين أساسي لخادم في بيئة إنتاجية:

logging.basicConfig(
    format="%(asctime)s %(message)s",
    level=logging.INFO,
)

هذه كيفية تمكين سجلات التصحيح للتطوير:

logging.basicConfig(
    format="%(message)s",
    level=logging.DEBUG,
)

علاوة على ذلك ، تضيف websockets سمة websocket إلى سجلات السجلات ، بحيث يمكنك تضمين معلومات إضافية حول الاتصال الحالي في السجلات.

يمكنك محاولة إضافة معلومات باستخدام تنسيق:

# this doesn't work!
logging.basicConfig(
    format="{asctime} {websocket.id} {websocket.remote_address[0]} {message}",
    level=logging.INFO,
    style="{",
)

ومع ذلك ، تواجه هذه التقنية مشكلتين:

  • ينطبق التنسيق على جميع السجلات. سيتعطل إذا تلقى سجلاً بدون سمة websocket. على سبيل المثال ، يحدث هذا عند تسجيل بدء الخادم لأنه لا يوجد اتصال حالي.
  • حتى مع نمط str.format() ، فإنك تقتصر على سمات وفهارس البحث ، وهو ما لا يكفي لتنفيذ بعض المتطلبات البسيطة نسبيًا.

هناك طريقة أفضل. تقبل connect() و serve() وسيطة logger لتجاوز Logger الافتراضي. يمكنك تعيين logger إلى LoggerAdapter الذي يثري السجلات.

على سبيل المثال ، إذا كان الخادم خلف وكيل عكسي ، فإن remote_address يعطي عنوان IP للوكيل ، وهو غير مفيد. يتم توفير عناوين IP للعملاء في رأس HTTP تم تعيينه بواسطة الوكيل.

هذه هي كيفية تضمينها في السجلات ، بافتراض أنها في رأس X-Forwarded-For:

التسجيل بتنسيق JSON

على الرغم من أن logging يسبق التسجيل المنظم ، إلا أنه لا يزال ممكنًا إخراج السجلات بتنسيق JSON ببعض الجهد.

أولاً ، نحتاج إلى Formatter يعرض JSON:

import json
import logging
import datetime
class JSONFormatter(logging.Formatter):
    """
    Render logs as JSON.
    To add details to a log record, store them in a ``event_data``
    custom attribute. This dict is merged into the event.
    """
    def __init__(self):
        pass  # override logging.Formatter constructor
    def format(self, record):
        event = {
            "timestamp": self.getTimestamp(record.created),
            "message": record.getMessage(),
            "level": record.levelname,
            "logger": record.name,
        }
        event_data = getattr(record, "event_data", None)
        if event_data:
            event.update(event_data)
        if record.exc_info:
            event["exc_info"] = self.formatException(record.exc_info)
        if record.stack_info:
            event["stack_info"] = self.formatStack(record.stack_info)
        return json.dumps(event)
    def getTimestamp(self, created):
        return datetime.datetime.utcfromtimestamp(created).isoformat()

بعد ذلك ، نقوم بتكوين التسجيل لتطبيق هذا التنسيق:

handler = logging.StreamHandler()
handler.setFormatter(formatter)
logger = logging.getLogger()
logger.addHandler(handler)
logger.setLevel(logging.INFO)

أخيرًا ، نقوم بملء سمة event_data المخصصة في سجلات السجلات باستخدام LoggerAdapter:

class LoggerAdapter(logging.LoggerAdapter):
    """Add connection ID and client IP address to websockets logs."""
    def process(self, msg, kwargs):
        try:
            websocket = kwargs["extra"]["websocket"]
        except KeyError:
            return msg, kwargs
        kwargs["extra"]["event_data"] = {
            "connection_id": str(websocket.id),
            "remote_addr": websocket.request_headers.get("X-Forwarded-For"),

افتراضيًا، لا تقوم المكتبة بتكوين وحدات logging. إذا لم يكن لدى تطبيقك معالج تسجيل، فإن Python تطبع رسائل ذات أهمية WARNING وأعلى إلى stderr. سترى رسالة وتتبع المكدس إذا تعطلت كوروتين معالج الاتصال أو إذا واجهت خطأ في المكتبة.

تعطيل التسجيل

إذا لم يقم تطبيقك بتكوين logging، فإن Python تطبع رسائل ذات أهمية WARNING وأعلى إلى stderr. نتيجة لذلك، سترى رسالة وتتبع المكدس إذا تعطلت كوروتين معالج الاتصال أو إذا واجهت خطأ في websockets.

إذا كنت ترغب في تعطيل هذا السلوك لـ websockets، يمكنك إضافة NullHandler:

logging.getLogger("websockets").addHandler(logging.NullHandler())

بالإضافة إلى ذلك، إذا قام تطبيقك بتكوين logging، فيجب عليك تعطيل الانتشار إلى المسجل الجذر، وإلا فقد تقوم معالجاته بطباعة السجلات:

logging.getLogger("websockets").propagate = False

بدلاً من ذلك، يمكنك تعيين مستوى السجل إلى CRITICAL لمسجل "websockets"، حيث أن أعلى مستوى مستخدم حاليًا هو ERROR:

logging.getLogger("websockets").setLevel(logging.CRITICAL)

أو يمكنك تكوين مرشح لإسقاط جميع الرسائل:

logging.getLogger("websockets").addFilter(lambda record: None)

المصادقة

تم تصميم بروتوكول WebSocket لإنشاء تطبيقات الويب التي تحتاج إلى اتصال ثنائي الاتجاه بين العملاء الذين يعملون في المتصفحات والخوادم.

في معظم حالات الاستخدام العملية، تحتاج خوادم WebSocket إلى مصادقة العملاء لتوجيه الاتصالات بشكل مناسب وآمن.

RFC 6455 تظل غامضة عندما يتعلق الأمر بالمصادقة:

هذا البروتوكول لا يحدد أي طريقة معينة يمكن للخوادم من خلالها مصادقة العملاء أثناء مصافحة WebSocket. يمكن لخادم WebSocket استخدام أي آلية مصادقة عميل متاحة لخادم HTTP عام، مثل ملفات تعريف الارتباط، أو مصادقة HTTP، أو مصادقة TLS.

لا تعمل أي من هذه الآليات الثلاث بشكل جيد في الممارسة العملية. استخدام ملفات تعريف الارتباط أمر مزعج، ولا تدعم مصادقة HTTP من قبل جميع المتصفحات الرئيسية، ومصادقة TLS في متصفح هي تجربة مستخدم غريبة.

لحسن الحظ، هناك بدائل أفضل! دعنا نناقشها.

تصميم النظام

ضع في اعتبارك إعدادًا حيث يكون خادم WebSocket منفصلاً عن خادم HTTP.

تعتمد معظم الخوادم المبنية باستخدام websockets لتكملة تطبيق ويب هذا التصميم لأنه لا يهدف إلى دعم HTTP.

يوضح الرسم البياني التالي تدفق المصادقة. [صورة]

بافتراض أن المستخدم الحالي مصادق عليه مع خادم HTTP (1)، تحتاج التطبيق إلى الحصول على بيانات الاعتماد من خادم HTTP (2) لإرسالها إلى خادم WebSocket (3)، الذي يمكنه التحقق منها مقابل قاعدة بيانات حسابات المستخدمين (4).

أسماء المستخدمين وكلمات المرور ليست خيارًا جيدًا لبيانات الاعتماد هنا، إن لم يكن ذلك بسبب أن كلمات المرور غير متوفرة كنص عادي في قاعدة البيانات.

الرموز المرتبطة بحسابات المستخدمين هي خيار أفضل. يجب أن تكون هذه الرموز غير قابلة للتزوير من قبل مهاجم. لمزيد من الأمان، يمكن أن تكون قصيرة الأجل أو حتى للاستخدام مرة واحدة.

إرسال بيانات الاعتماد

افترض أن تطبيق الويب حصل على بيانات اعتماد المصادقة، على الأرجح رمز، من خادم HTTP. هناك أربعة خيارات لتمريرها إلى خادم WebSocket.

1.
إرسال بيانات الاعتماد كرسالة أولى في اتصال WebSocket.

هذه آلية موثوقة بالكامل وأكثرها أمانًا في هذه المناقشة. لها جانبان سلبيان طفيفان:

  • تتم المصادقة على مستوى التطبيق. من الناحية المثالية، يجب إدارتها على مستوى البروتوكول.
  • تتم المصادقة بعد مصافحة WebSocket، مما يجعل من المستحيل مراقبة فشل المصادقة باستخدام رموز استجابة HTTP.
2.
إضافة بيانات الاعتماد إلى URI WebSocket كمعامل استعلام.

هذه أيضًا موثوقة بالكامل ولكنها أقل أمانًا. في الواقع، لها جانب سلبي كبير:

•
تنتهي عناوين URI في السجلات، مما يؤدي إلى تسريب بيانات الاعتماد. حتى لو تم تخفيض هذا الخطر باستخدام رموز تستخدم لمرة واحدة، فإنه يعتبر عادةً غير مقبول.

لا تزال المصادقة تتم على مستوى التطبيق ولكن يمكن أن تحدث قبل مصافحة WebSocket، مما يحسن فصل الاهتمامات ويتيح الاستجابة لفشل المصادقة باستخدام 401 HTTP.

3.
تعيين ملف تعريف ارتباط على نطاق URI WebSocket.

ملفات تعريف الارتباط هي بلا شك الآلية الأكثر شيوعًا وتقوية لإرسال بيانات الاعتماد من تطبيق ويب إلى خادم. في تطبيق HTTP، ستكون بيانات الاعتماد معرف جلسة أو جلسة موقعة، موقعه.

لسوء الحظ، عندما يعمل خادم WebSocket على نطاق مختلف عن تطبيق الويب، فإن هذه الفكرة تصطدم بـ سياسة الأصل نفسه. لأسباب أمنية، من المستحيل تعيين ملف تعريف ارتباط على أصل مختلف.

الحل البديل المناسب يتكون من:

  • إنشاء iframe مخفي يتم تقديمه من نطاق خادم WebSocket
  • إرسال الرمز إلى iframe باستخدام postMessage
  • تعيين ملف تعريف الارتباط في iframe

قبل فتح اتصال WebSocket.

مشاركة نطاق أب (مثل example.com) بين خادم HTTP (مثل www.example.com) وخادم WebSocket (مثل ws.example.com) وتعيين ملف تعريف الارتباط على هذا النطاق الأب سيعمل أيضًا.

ومع ذلك، سيتم مشاركة ملف تعريف الارتباط مع جميع النطاقات الفرعية للنطاق الأب. لملف تعريف ارتباط يحتوي على بيانات اعتماد، هذا غير مقبول.

4.
إضافة بيانات الاعتماد إلى URI WebSocket في معلومات المستخدم.

السماح للمتصفح بإجراء مصادقة HTTP الأساسية فكرة جيدة من الناحية النظرية.

في الواقع، لا تعمل بسبب ضعف الدعم في المتصفحات.

اعتبارًا من مايو 2021:

  • Chrome 90 يتصرف كما هو متوقع.
  • Firefox 88 يخزن بيانات الاعتماد مؤقتًا بشكل مفرط.

    عند الاتصال مرة أخرى بنفس الخادم ببيانات اعتماد جديدة، فإنه يعيد استخدام بيانات الاعتماد القديمة، والتي قد تكون منتهية الصلاحية، مما يؤدي إلى 401 HTTP. ثم ينجح الاتصال التالي. ربما تقوم الأخطاء بمسح الذاكرة المؤقتة.

    عندما تكون الرموز قصيرة الأجل أو تستخدم لمرة واحدة، ينتج هذا الخطأ تأثيرًا مثيرًا للاهتمام: يفشل كل اتصال WebSocket آخر.

  • Safari 14 يتجاهل بيانات الاعتماد تمامًا.

خياران آخران خارج الجدول:

1.
تعيين رأس HTTP مخصص

ستكون هذه هي الآلية الأكثر أناقة، وتحل جميع المشكلات المتعلقة بالخيارات التي تمت مناقشتها أعلاه.

للأسف، لا تعمل لأن WebSocket API لا تدعم تعيين رؤوس مخصصة.

2.
المصادقة باستخدام شهادة TLS

بينما يقترح هذا من قبل RFC، فإن تثبيت شهادة TLS بعيد جدًا عن تجربة مستخدمي المتصفح الرئيسية. قد يكون هذا منطقيًا في سياقات الأمان العالية. آمل ألا يأخذ المطورون الذين يعملون على مثل هذه المشاريع نصائح الأمان من وثائق مشاريع المصادر المفتوحة العشوائية.

الحفاظ على الاتصال في WebSockets

لتجنب هذه المشاكل، تستخدم WebSockets آلية للحفاظ على الاتصال والنبض تعتمد على إطارات Ping و Pong الخاصة بـ WebSocket، والتي تم تصميمها لهذا الغرض.

تتكرر الخطوات التالية:

1.
انتظر 20 ثانية.
2.
أرسل إطار Ping.
3.
استقبل إطار Pong مطابق خلال 20 ثانية.

إذا لم يتم استلام إطار Pong، تعتبر WebSockets الاتصال مكسورًا وتغلقه.

تخدم هذه الآلية غرضين:

1.
تنشئ تدفقًا حركة مرور بحيث لا يكون اتصال TCP خاملاً وتحافظ البنية التحتية للشبكة على طول المسار على فتحه ("الحفاظ على الاتصال").
2.
تكتشف ما إذا كان الاتصال ينقطع أو يصبح بطيئًا جدًا بحيث لا يمكن استخدامه عمليًا ("النبض"). في هذه الحالة، تقوم بإنهاء الاتصال ويحصل تطبيقك على استثناء ConnectionClosed.

الأوقات قابلة للتكوين باستخدام الوسيطات ping_interval و ping_timeout للدالتين connect() و serve(). القيم الأقصر ستكتشف انقطاعات الاتصال بشكل أسرع ولكنها ستزيد من حركة مرور الشبكة وستكون أكثر حساسية للتأخير.

تعيين ping_interval إلى None يعطل آلية الحفاظ على الاتصال والنبض بأكملها.

تعيين ping_timeout إلى None يعطل مهلات الوقت فقط. هذا يمكّن الحفاظ على الاتصال، لإبقاء الاتصالات الخاملة مفتوحة، ويعطل النبض، لدعم زيادة التأخير الكبيرة.

لماذا لا تعتمد WebSockets على TCP keepalive؟

يتم تعطيل TCP keepalive افتراضيًا على معظم أنظمة التشغيل. عند تمكينه، يكون الفاصل الزمني الافتراضي ساعتين أو أكثر، وهو وقت طويل جدًا.

الحفاظ على الاتصال في المتصفحات

لا تقوم المتصفحات بتمكين آلية للحفاظ على الاتصال مثل WebSockets افتراضيًا. نتيجة لذلك، قد تفشل في ملاحظة أن اتصال WebSocket مكسور لفترة طويلة من الوقت، حتى تنتهي صلاحية اتصال TCP.

في هذا السيناريو، لا يقوم الكائن WebSocket في المتصفح بإطلاق حدث close. إذا كان لديك آلية إعادة اتصال، فإنها لا تعمل لأنها تعتقد أن الاتصال لا يزال يعمل.

إذا فشل تطبيقك المستند إلى المتصفح بشكل غامض وعشوائي في تلقي الأحداث، فهذا هو السبب المحتمل. تحتاج إلى آلية للحفاظ على الاتصال في المتصفح لتجنب هذا السيناريو.

لسوء الحظ، لا يكشف واجهة برمجة تطبيقات WebSocket في المتصفحات عن وظائف Ping و Pong الأصلية في بروتوكول WebSocket. عليك أن تبتكر الحل الخاص بك في طبقة التطبيق.

مشاكل التأخير

قد يزيد التأخير بين العميل والخادم لسببين:

  • الاتصال بالشبكة ضعيف. عندما تُفقد حزم الشبكة، يحاول TCP إعادة إرسالها، مما يظهر كتأخير. فقدان الحزم المفرط يجعل الاتصال غير قابل للاستخدام عمليًا. عند نقطة معينة، يكون تحديد مهلة معقولًا.

  • حركة المرور عالية. على سبيل المثال، إذا أرسل العميل رسائل عبر الاتصال أسرع مما يمكن للخادم معالجتها، فهذا يظهر كتأخير أيضًا، لأن البيانات تنتظر في حالة الطيران، معظمها في مخازن نظام التشغيل.

    إذا كان الخادم متأخرًا بأكثر من 20 ثانية، فلن يرى Pong قبل انتهاء مهلة الافتراضي. نتيجة لذلك، يقوم بإغلاق الاتصال. هذا خيار معقول لمنع الحمل الزائد.

    إذا تسببت طفرات حركة المرور في مهلات غير مرغوب فيها وكنت واثقًا من أن الخادم سيلحق بالركب في النهاية، يمكنك زيادة ping_timeout أو تعيينها على None لتعطيل النبض تمامًا.

    ينطبق نفس المنطق على المواقف التي يرسل فيها الخادم حركة مرور أكثر مما يمكن للعميل قبوله.

التأخير الذي تم قياسه خلال آخر تبادل لإطارات Ping و Pong متاح في السمة latency. بدلاً من ذلك، يمكنك قياس التأخير في أي وقت باستخدام الدالة ping.

دورة الحياة

الحالة

تمر اتصالات WebSocket عبر آلة حالة بسيطة:

  • CONNECTING: الحالة الأولية،
  • OPEN: عند اكتمال المصافحة الافتتاحية،
  • CLOSING: عند بدء المصافحة الختامية،
  • CLOSED: عند إغلاق اتصال TCP.

تحدث الانتقالات في الأماكن التالية:

  • CONNECTING -> OPEN: في connection_open() والتي تعمل عند اكتمال المصافحة الافتتاحية وإنشاء اتصال WebSocket - لا ينبغي الخلط بينها وبين connection_made() التي تعمل عند إنشاء اتصال TCP؛
  • OPEN -> CLOSING: في write_frame() مباشرة قبل إرسال إطار إغلاق؛ نظرًا لأن تلقي إطار إغلاق يؤدي إلى إرسال إطار إغلاق، فإن هذا يقوم بالشيء الصحيح بغض النظر عن الجانب الذي بدأ المصافحة الختامية؛ أيضًا في fail_connection() التي تكرر بضعة أسطر من التعليمات البرمجية من write_close_frame() و write_frame()؛
  • * -> CLOSED: في connection_lost() التي يتم استدعاؤها دائمًا مرة واحدة بالضبط عند إغلاق اتصال TCP.

Coroutines الموضحة باللون الرمادي تدير الاتصال. عندما تنجح المصافحة الافتتاحية، تبدأ connection_open() مهمتين:

  • دون تسريب اتصالات TCP مفتوحة،

Cancellation and Exceptions

Tasks that await futures must ensure that these futures are not cancelled accidentally if a coroutine that awaits them is canceled. In other words, they must be shielded from cancellation.

recv() waits for the next message in the queue or for transfer_data_task to terminate, whichever comes first. It relies on wait() for waiting on two futures in parallel. As a consequence, even though it's waiting on a Future signaling the next message and on transfer_data_task, it doesn't propagate cancellation to them.

ensure_open() is called by send(), ping(), and pong(). When the connection state is CLOSING, it waits for transfer_data_task but shields it to prevent cancellation.

close() waits for the data transfer task to terminate with timeout(). If it's canceled or if the timeout elapses, transfer_data_task is canceled, which is correct at this point. close() then waits for close_connection_task but shields it to prevent cancellation.

close() and fail_connection() are the only places where transfer_data_task may be canceled.

close_connection_task starts by waiting for transfer_data_task. It catches CancelledError to prevent a cancellation of transfer_data_task from propagating to close_connection_task.

Backpressure

NOTE:

This section discusses backpressure from the perspective of a server but the concept applies to clients symmetrically.

With a naive implementation, if a server receives inputs faster than it can process them, or if it generates outputs faster than it can send them, data accumulates in buffers, eventually causing the server to run out of memory and crash.

The solution to this problem is backpressure. Any part of the server that receives inputs faster than it can process them and send the outputs must propagate that information back to the previous part in the chain.

websockets is designed to make it easy to get backpressure right.

For incoming data, websockets builds upon StreamReader which propagates backpressure to its own buffer and to the TCP stream. Frames are parsed from the input stream and added to a bounded queue. If the queue fills up, parsing halts until the application reads a frame.

For outgoing data, websockets builds upon StreamWriter which implements flow control. If the output buffers grow too large, it waits until they're drained. That's why all APIs that write frames are asynchronous.

Of course, it's still possible for an application to create its own unbounded buffers and break the backpressure. Be careful with queues.

Buffers

NOTE:

This section discusses buffers from the perspective of a server but it applies to clients as well.

An asynchronous systems works best when its buffers are almost always empty.

For example, if a client sends data too fast for a server, the queue of incoming messages will be constantly full. The server will always be 32 messages (by default) behind the client. This consumes memory and increases latency for no good reason. The problem is called bufferbloat.

If buffers are almost always full and that problem cannot be solved by adding capacity — typically because the system is bottlenecked by the output and constantly regulated by backpressure — reducing the size of buffers minimizes negative consequences.

By default websockets has rather high limits. You can decrease them according to your application's characteristics.

Bufferbloat can happen at every level in the stack where there is a buffer. For each connection, the receiving side contains these buffers:

  • OS buffers: tuning them is an advanced optimization.
  • StreamReader bytes buffer: the default limit is 64 KiB. You can set another limit by passing a read_limit keyword argument to connect() or serve().
  • Incoming messages deque: its size depends both on the size and the number of messages it contains. By default the maximum UTF-8 encoded size is 1 MiB and the maximum number is 32. In the worst case, after UTF-8 decoding, a single message could take up to 4 MiB of memory and the overall memory consumption could reach 128 MiB. You should adjust these limits by setting the max_size and max_queue keyword arguments of connect() or serve() according to your application's requirements.

For each connection, the sending side contains these buffers:

  • StreamWriter bytes buffer: the default size is 64 KiB. You can set another limit by passing a write_limit keyword argument to connect() or serve().
  • OS buffers: tuning them is an advanced optimization.

Concurrency

Awaiting any combination of recv(), send(), close() ping(), or pong() concurrently is safe, including multiple calls to the same method, with one exception and one limitation.

  • Only one coroutine can receive messages at a time. This constraint avoids non-deterministic behavior (and simplifies the implementation). If a coroutine is awaiting recv(), awaiting it again in another coroutine raises RuntimeError.
  • Sending a fragmented message forces serialization. Indeed, the WebSocket protocol doesn't support multiplexing messages. If a coroutine is awaiting send() to send a fragmented message, awaiting it again in another coroutine waits until the first call completes. This will be transparent in many cases. It may be a concern if the fragmented message is generated slowly by an asynchronous iterator.

Receiving frames is independent from sending frames. This isolates recv(), which receives frames, from the other methods, which send frames.

While the connection is open, each frame is sent with a single write. Combined with the concurrency model of asyncio, this enforces serialization. The only other requirement is to prevent interleaving other data frames in the middle of a fragmented message.

After the connection is closed, sending a frame raises ConnectionClosed, which is safe.

Memory usage

In most cases, memory usage of a WebSocket server is proportional to the number of open connections. When a server handles thousands of connections, memory usage can become a bottleneck.

Memory usage of a single connection is the sum of:

1.
the baseline amount of memory websockets requires for each connection,
2.
the amount of data held in buffers before the application processes it,
3.
any additional memory allocated by the application itself.

Baseline

Compression settings are the main factor affecting the baseline amount of memory used by each connection.

With websockets' defaults, on the server side, a single connections uses 70 KiB of memory.

Refer to the topic guide on compression to learn more about tuning compression settings.

Buffers

Under normal circumstances, buffers are almost always empty.

Under high load, if a server receives more messages than it can process, bufferbloat can result in excessive memory usage.

By default websockets has generous limits. It is strongly recommended to adapt them to your application. When you call serve():

  • Set max_size (default: 1 MiB, UTF-8 encoded) to the maximum size of messages your application generates.
  • Set max_queue (default: 32) to the maximum number of messages your application expects to receive faster than it can process them. The queue provides burst tolerance without slowing down the TCP connection.

Furthermore, you can lower read_limit and write_limit (default: 64 KiB) to reduce the size of buffers for incoming and outgoing data.

The design document provides more details about buffers.

Security

Encryption

For production use, a server should require encrypted connections.

See this example of encrypting connections with TLS.

Memory usage

WARNING:

An attacker who can open an arbitrary number of connections will be able to perform a denial of service by memory exhaustion. If you're concerned by denial of service attacks, you must reject suspicious connections before they reach websockets, typically in a reverse proxy.

With the default settings, opening a connection uses 70 KiB of memory.

Sending some highly compressed messages could use up to 128 MiB of memory with an amplification factor of 1000 between network traffic and memory usage.

Configuring a server to optimize memory usage will improve security in addition to improving performance.

Other limits

websockets implements additional limits on the amount of data it accepts in order to minimize exposure to security vulnerabilities.

In the opening handshake, websockets limits the number of HTTP headers to 256 and the size of an individual header to 4096 bytes. These limits are 10 to 20 times larger than what's expected in standard use cases. They're hard-coded.

If you need to change these limits, you can monkey-patch the constants in websockets.http11.

recv() used to return None when the connection was closed. This required checking the return value of every call:

message = await websocket.recv()
if message is None:
    return

Now it raises a ConnectionClosed exception instead. This is more Pythonic. The previous code can be simplified to:

message = await websocket.recv()

When implementing a server, there's no strong reason to handle such exceptions. Let them bubble up, terminate the handler coroutine, and the server will simply ignore them.
