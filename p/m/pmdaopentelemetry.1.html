PMDAOPENTELEMETRY(1) دليل الأوامر العامة PMDAOPENTELEMETRY(1)

الاسم

pmdaopentelemetry - وكيل مجال القياس OpenTelemetry

الملخص

$PCP_PMDAS_DIR/opentelemetry/pmdaopentelemetry [-D] [-n] [-c config] [-d domain] [-l logfile] [-r root] [-t timeout] [-u user]

الوصف

pmdaopentelemetry هو وكيل مجال القياس (PMDA) يقوم بإنشاء مقاييس PCP ديناميكيًا من نقاط نهاية OpenTelemetry المكونة التي توفر وصولاً يستند إلى HTTP إلى مقاييس التطبيق.

المجلد الافتراضي config هو $PCP_PMDAS_DIR/opentelemetry/config.d/، راجع ``مصادر التكوين'' أدناه. مهلة استرداد عنوان URL الافتراضية timeout هي **2** ثانية. المستخدم الافتراضي user، إذا لم يتم تحديده باستخدام الخيار -u، هو المستخدم "pcp". إذا تم استخدام الخيار -n، فلن يتم فرز قائمة ملفات التكوين قبل معالجتها. يتم فرز هذه القائمة افتراضيًا ولكن قد يكون ذلك مكلفًا إذا كان هناك عدد كبير من ملفات التكوين (عناوين URL و / أو البرامج النصية).

إذا تم استخدام الخيار -D، فسيتم كتابة رسائل تشخيصية إضافية إلى ملف سجل وكيل مجال القياس، وهو **$PCP_LOG_DIR/pmcd/opentelemetry.log** افتراضيًا (راجع أيضًا -l أدناه). بالإضافة إلى ذلك، يتحكم المقياس opentelemetry.control.debug في نفس علامة التصحيح ويمكن تعيينه باستخدام الأمر التالي:

pmstore opentelemetry.control.debug value

حيث value إما **1** (لتمكين رسائل السجل المطولة) أو **0** (لتعطيل رسائل السجل المطولة). هذا مفيد بشكل خاص لفحص رؤوس http التي يتم تمريرها إلى كل طلب استرداد، وإعدادات التصفية، وتفاصيل المعالجة الأخرى التي يتم تسجيلها عند تمكين علامة التصحيح.

قد يتم استخدام الخيار -d لتجاوز رقم مجال مقاييس الأداء الافتراضي domain، والذي افتراضيًا هو **164**. يوصى بشدة بعدم تغيير هذا. يجب أن يكون رقم domain مختلفًا لكل وكيل مجال قياس على نفس المضيف، ويجب استخدام نفس رقم domain لوكيل مجال القياس pmdaopentelemetry على جميع المضيفين. راجع أيضًا الخيار -r، الذي يسمح بتغيير جذر مساحة الأسماء الديناميكية من الافتراضي opentelemetry.

قد يتم استخدام الخيار -l لتحديد logfile كوجهة لرسائل وكيل مجال القياس بدلاً من الافتراضي، **$PCP_LOG_DIR/pmcd/opentelemetry.log**. كحالة خاصة، قد يكون logfile **"-"** لإرسال الرسائل إلى تيار stderr بدلاً من ذلك، على سبيل المثال **-l-**. عادةً ما يكون هذا هو تيار stderr للعملية الأصل، pmcd(1)، والتي قد يكون لديها بالفعل stderr معاد توجيهه. عادةً ما يكون هذا التوجيه مفيدًا جدًا في بيئة تحتوي على حاويات، أو عند استخدام dbpmda(1).

يسمح الخيار -r بتغيير جذر مساحة الأسماء الديناميكية إلى root من الافتراضي، opentelemetry. بالاقتران مع خيارات سطر الأوامر الأخرى، يسمح هذا لـ pmdaopentelemetry بنشره كوكيل مجال قياس مختلف مع مساحة أسماء مقاييس فريدة ومجال مقاييس على نفس النظام المضيف. لاحظ أن جميع وكلاء مجال القياس يتطلبون رقم مجال فريدًا لذا يجب أيضًا تحديد الخيار -d. قد يؤدي استخدام الخيار -r** أيضًا إلى تغيير الإعدادات الافتراضية لبعض خيارات سطر الأوامر الأخرى، على سبيل المثال اسم ملف السجل الافتراضي ودليل التكوين الافتراضي.

مصادر التكوين

أثناء التشغيل، يقوم pmdaopentelemetry بمسح دوري وشامل للمجلد **$PCP_PMDAS_DIR/opentelemetry/config.d** (أو المجلد المحدد بالخيار -c)، بحثًا عن ملفات عناوين URL المصدر (*.url) وبرامج نصية قابلة للتنفيذ أو ثنائيات. يتم تجاهل أي ملفات لا تحتوي على لاحقة .url أو ليست قابلة للتنفيذ - وهذا يسمح بوجود ملفات وثائق مثل "README" وتعريفات دالات نصية غير قابلة للتنفيذ دون اعتبارها ملفات تكوين.

لا يلزم أن يكون الخادم البعيد قيد التشغيل أو يبقى قيد التشغيل - يتحمل وكيل مجال القياس عناوين URL البعيدة التي قد تأتي وتذهب بمرور الوقت. سيقوم وكيل مجال القياس بترحيل البيانات والبيانات الوصفية عندما / إذا كانت متاحة، وسيعيد الأخطاء عندما / إذا كانت معطلة. يتم الاحتفاظ بمعرفات مقاييس PCP، ومعرفات نطاق المثيل الداخلية والخارجية، وسيتم استعادتها عند توفر مصادر المقاييس الفردية و / أو عند إعادة تشغيل وكيل مجال القياس. بالإضافة إلى ذلك، يتحقق وكيل مجال القياس من أوقات تعديل الدليل وسيقوم بإعادة المسح للملفات التكوينية الجديدة أو المتغيرة ديناميكيًا. لا يلزم إعادة تشغيل وكيل مجال القياس عند إضافة ملفات التكوين أو إزالتها أو تغييرها.

مصادر عناوين URL

يحتوي كل ملف باللاحقة .url موجود في دليل التكوين أو الدليل الفرعي على عنوان URL واحد كامل لـ HTTP أو HTTPS حيث يمكن لـ pmdaopentelemetry الوصول إلى نقطة نهاية OpenTelemetry. يتم أيضًا دعم الوصول إلى الملفات المحلية باستخدام عنوان URL تقليدي file:///somepath/somefile، وفي هذه الحالة يجب أن يحتوي somepath/somefile على بيانات المقاييس بتنسيق OpenTelemetry.

يجب أن يكون السطر الأول من ملف تكوين .url هو عنوان URL، كما هو موضح أعلاه. الأسطر اللاحقة، إن وجدت، مسبوقة بكلمة مفتاحية يمكن استخدامها لتعديل طلب http GET. يجب أن تنتهي الكلمة المفتاحية بـ **:** (نقطتين) ويمتد النص إلى نهاية السطر. يتم تجاهل أسطر التعليقات التي تبدأ بـ **#** والأسطر الفارغة. الكلمات المفتاحية الوحيدة المدعومة حاليًا هي **HEADER:** و **FILTER:**.

HEADER: headername: value ... إلى نهاية السطر
يضيف headername وقيمته إلى الرؤوس التي يتم تمريرها في طلب http GET لعنوان URL المكون. مثال على ملف تكوين يوفر 3 رؤوس شائعة الاستخدام ورمز مصادقة قد يكون:


http://somehost/path/endpoint.html
# هذا تعليق
HEADER: Accept: text/html
HEADER: Keep-Alive: 300
HEADER: Connection: keep-alive
HEADER: Authorization: token ABCDEF1234567890

كما ذكرنا أعلاه، تمتد قيم الرؤوس إلى نهاية السطر. قد تحتوي على أي أحرف صالحة، بما في ذلك النقاط الرأسية. سيتم ضغط المسافات المتعددة إلى مسافة واحدة، وسيتم اقتطاع المسافات البادئة واللاحقة. الاستخدام الشائع للرؤوس هو تكوين وكيل بروكسي والمعلمات المتنوعة التي قد يتطلبها.

تصفية المقاييس

تصفية المقاييس هي ميزة في ملف التكوين تسمح بتضمين أو استبعاد المقاييس المستوعبة، أي تصفيتها. هذا مفيد لأن معظم نقاط النهاية تعيد مقاييس متعددة، وعادةً ما تكون بعضها فقط ذات أهمية لأغراض المراقبة. الصيغة هي:
FILTER: INCLUDE METRIC regex
أو
FILTER: EXCLUDE METRIC regex
سيتم تضمين مقاييس أسماء المقاييس التي تم إنشاؤها ديناميكيًا والتي تطابق regex أو استبعادها في مساحة الأسماء، كما هو محدد. لاحظ أن مكون ورقة PMNS فقط لاسم المقياس (كما هو مستوعب من مصدر URL) تتم مقارنته بنمط regex. القاعدة البسيطة هي أن أول تطابق لقاعدة تصفية لاسم ورقة مقياس معين هو القاعدة التي تسود. إذا لم تتطابق أي قاعدة تصفية (أو لا توجد عوامل تصفية)، فسيتم تضمين المقياس افتراضيًا، أي أن عامل التصفية الافتراضي إذا لم يتم تحديد أي منها هو FILTER: INCLUDE METRIC .*. هذا متوافق مع الإصدارات الأقدم من ملف التكوين الذي لم يدعم عوامل التصفية. عادةً ما يتم استخدام أسطر FILTER: متعددة، على سبيل المثال لتضمين بعض المقاييس ولكن استبعاد جميع المقاييس الأخرى، استخدم FILTER: EXCLUDE METRIC .* كآخر عامل تصفية من عدة عوامل تصفية تتضمن المقاييس المطلوبة. على العكس من ذلك، لاستبعاد بعض المقاييس ولكن تضمين جميع المقاييس الأخرى، استخدم FILTER: EXCLUDE METRIC regex. في هذه الحالة، لا يلزم (على الرغم من أنه لا يضر) تحديد FILTER: INCLUDE METRIC .*** النهائي لأنه، كما ذكر أعلاه، سيتم تضمين أي مقياس لا يتطابق مع أي قاعدة تصفية افتراضيًا.

opentelemetry.control.status

The OpenTelemetry PMDA has a single control metric, opentelemetry.control.status. This metric indicates the status of the configured OpenTelemetry sources. A value of 0 indicates that all configured sources are currently available and healthy. Any other value signifies an error or an unavailable source. This metric can be used for service availability monitoring, but care must be taken as specific non-zero values may represent transient issues or specific error conditions that do not necessarily indicate a complete service outage. For more detailed information on specific error codes, refer to the PMDA's log file.

opentelemetry.control.calls

The total number of times each configured metric source has been fetched (if it is a URL) or executed (if it's a script), since the PMDA started. This metric has counter semantics and would normally be converted to a rate/second by client tools.

opentelemetry.control.fetch_time

Total time in milliseconds that each configured metric source has taken to return a document, excluding the time to parse the document. This metric has counter semantics and would normally be rate converted by client tools but is also useful in raw form as the accumulated parse time since the PMDA was started.

opentelemetry.control.parse_time

Total time in milliseconds that each configured metric source has taken to parse each document, excluding the time to fetch the document. This metric has counter semantics and would normally be rate converted by client tools but is also useful in raw form as the accumulated parse time since the PMDA was started.

When converted to a rate, the calls metric represents the average fetch rate of each source over the sampling interval (time delta between samples). The fetch_time and parse_time counters, when converted to a rate, represent the average fetch and parsing latency (respectfully), during the sampling interval.

The opentelemetry.control.debug metric has a singular value, defaulting to 0. If a non-zero value is stored into this metric using pmstore(1), additional debug messages will be written to the PMDA log file.

LIMITATIONS

pmdaopentelemetry and libpcp internals impose some numerical constraints about the number of sources (4095), metrics (1024) within each source, and instances for each metric (4194304).

INSTALLATION

Install the OpenTelemetry PMDA by using the Install script as root:

# cd $PCP_PMDAS_DIR/opentelemetry
# ./Install

To uninstall, the following must be done as root:

# cd $PCP_PMDAS_DIR/opentelemetry
# ./Remove

pmdaopentelemetry is launched by pmcd(1) and should never be executed directly. The Install and Remove scripts notify pmcd when the agent is installed or removed.

When scripts and .url files are added, removed or changed in the configuration directory, it is usually not necessary to restart the PMDA - the changes will be detected and managed on subsequent requests to the PMDA.

files containing internal tables for metric and instance ID number persistence (domain 164).

PCP ENVIRONMENT

Environment variables with the prefix PCP_ are used to parameterize the file and directory names used by PCP. On each installation, the file /etc/pcp.conf contains the local values for these variables. The $PCP_CONF variable may be used to specify an alternative configuration file, as described in pcp.conf(5).
