PMDAOPENMETRICS(1) General Commands Manual PMDAOPENMETRICS(1)

NAME

pmdaopenmetrics - OpenMetrics PMDA

SYNOPSIS

$PCP_PMDAS_DIR/openmetrics/pmdaopenmetrics [-D] [-n] [-c config] [-d domain] [-l logfile] [-R refresh_timeout] [-r root] [-t timeout] [-u user]

DESCRIPTION

pmdaopenmetrics is a Performance Metrics Domain Agent (PMDA) which dynamically creates PCP metrics from configured OpenMetrics endpoints, which provide HTTP based access to application metrics. The PMDA essentially implements a bridge between Prometheus and PCP, allowing PCP to easily ingest performance data from more than 650 registered end-points and many other application specific end-points.

The default config directory is $PCP_PMDAS_DIR/openmetrics/config.d/, see ``CONFIGURATION SOURCES'' below. The default URL fetch timeout is 2 seconds. The default user, if not specified with the -u option, is the current user. If the -n option is given, the list of configuration files will not be sorted prior to processing. This list is sorted by default but that can be expensive if there are a large number of configuration files (URLs and/or scripts).

If the -D option is given, additional diagnostic messages will be written to the PMDA log file, which is $PCP_LOG_DIR/pmcd/openmetrics.log by default (see also -lbelow). In addition, the metric openmetrics.control.debug controls the same debug flag and can be set with the following command:

pmstore openmetrics.control.debug value

where value is either 1 (to enable verbose log messages) or 0 (to disable verbose log messages). This is particularly useful for examining the http headers passed to each fetch request, filter settings and other processing details that are logged when the debugging flag is enabled.

The -d option may be used to override the default performance metrics domain number, which defaults to 144. It is strongly recommended not to change this. The domain number should be different for every PMDA on the one host, and the same domain number should be used for pmdaopenmetrics PMDA on all hosts. See also the -r option, which allows the root of the dynamic namespace to be changed from the default openmetrics.

The -l option may be used to specify logfile as the destination for PMDA messages instead of the default, $PCP_LOG_DIR/pmcd/openmetrics.log. As a special case, logfile may be "-" to send messages to the stderr stream instead, e.g. -l-. This would normally be the stderr stream for the parent process, pmcd(1), which may itself have redirected stderr. This redirection is normally most useful in a containerized environment, or when using dbpmda(1).

The -r option allows the root of the dynamic namespace to be changed to root from the default, openmetrics. In conjunction with other command line options, this allows pmdaopenmetrics to be deployed as a different PMDA with distinct metrics namespace and metrics domain on the same host system. Note that all PMDAs require a unique domain number so the -d option must also be specified. Use of the -r option may also change the defaults for some other command line options, e.g. the default log file name and the default configuration directory.

The -R option allows the user to configure the timeout, in seconds, between cluster refreshes. The default value is 10 seconds.

CONFIGURATION SOURCES

As it runs, pmdaopenmetrics periodically recursively scans the $PCP_PMDAS_DIR/openmetrics/config.d directory (or the directory specified with the -c option), looking for source URL files (*.url) and executable scripts or binaries. Any files that do not have the .url suffix or are not executable, are ignored - this allows documentation files such as "README" and non-executable "common" script function definitions to be present without being considered as config files.

A remote server does not have to be up or stay running - the PMDA tolerates remote URLs that may come and go over time. The PMDA will relay data and metadata when/if they are available, and will return errors when/if they are down. PCP metric IDs, internal and external instance domain identifiers are persisted and will be restored when individual metric sources become available and/or when the PMDA is restarted. In addition, the PMDA checks directory modification times and will rescan for new or changed configuration files dynamically. It is not necessary to restart the PMDA when adding, removing or changing configuration files.

URL SOURCES

Each file with the .url suffix found in the config directory or sub-directory contains one complete HTTP or HTTPS URL at which pmdaopenmetrics can reach a OpenMetrics endpoint. Local file access is also supported with a conventional file:///somepath/somefile URL, in which case somepath/somefile should contain openmetrics formatted metric data.

The first line of a .url config file should be the URL, as described above. Subsequent lines, if any, are prefixed with a keyword that can be used to alter the http GET request. A keyword must end with ':' (colon) and the text extends to the end of the line. Comment lines that start with # and blank lines are ignored. The only currently supported keywords are HEADER: and FILTER:.

HEADER: headername: value ... to end of line
Adds headername and its value to the headers passed in the http GET request for the configured URL. An example configuration file that provides 3 commonly used headers and an authentication token might be :


http://somehost/path/endpoint.html
# this is a comment
HEADER: Accept: text/html
HEADER: Keep-Alive: 300
HEADER: Connection: keep-alive
HEADER: Authorization: token ABCDEF1234567890

As mentioned above, header values extend to the end of the line. They may contain any valid characters, including colons. Multiple spaces will be collapsed to a single space, and leading and trailing spaces are trimmed. A common use for headers is to configure a proxy agent and the assorted parameters it may require.

METRIC FILTERING

Metric filtering is a configuration file feature that allows ingested metrics to be included or excluded, i.e. filtered. This is useful because most end-points return multiple metrics, and usually only some are interesting for monitoring purposes. The syntax is:
FILTER: INCLUDE METRIC regex
or
FILTER: EXCLUDE METRIC regex
Dynamically created metric names that match regex will be either included or excluded in the name space, as specified. Note that only the PMNS leaf component of the metric name (as ingested from the URL source) is compared with the regex pattern. The simple rule is that the first matching filter regex for a particular metric leaf name is the rule that prevails. If no filter regex matches (or there are no filters), then the metric is included by default, i.e. the default filter if none are specified is FILTER: INCLUDE METRIC .* This is backward compatible with older versions of the configuration file that did not support filters. Multiple FILTER: lines would normally be used, e.g. to include some metrics but exclude all others, use FILTER: EXCLUDE METRIC .* as the last of several filters that include the desired metrics. Conversely, to exclude some metrics but include all others, use FILTER: EXCLUDE METRIC regex. In this case it's not necessary (though doesn't hurt) to specify the final FILTER: INCLUDE METRIC .* because, as stated above, any metric that does not match any filter regex will be included by default.

LABEL FILTERING

Label filtering uses similar FILTER: syntax and semantics as metric filtering. FILTER: EXCLUDE LABEL regex will delete all labels with label na

FILTER: OPTIONAL LABEL regex تحدد أن أسماء التسميات المتطابقة يجب إدراجها في مجموعات تسميات المقاييس التي تم إرجاعها (أي مضمنة)، ولكن لا يجب استخدامها كجزء من أسماء المثيلات الخارجية. سيتم تجميع جميع التسميات المضمنة التي ليست اختيارية (أي التسميات الجوهرية) واستخدامها لتسمية المثيلات الخارجية. بالإضافة إلى ذلك، سيتم تعيين علامة PM_LABEL_OPTIONAL للتسميات غير الجوهرية (أي التسميات المصنفة كـ OPTIONAL) في مجموعات التسميات التي تم إرجاعها بواسطة استدعاءات notes. تؤثر هذه العلامة على كيفية استخدام التسميات في بعض العملاء. لمزيد من التفاصيل، راجع pmLookupLabels(3) وصفحات man ذات الصلة لمزيد من التفاصيل. لاحظ أن أسماء المثيلات الخارجية تبدأ بمعرف المثيل الداخلي الرقمي الفريد متبوعًا بمسافة، لذلك تكون أسماء المثيلات الخارجية فريدة دائمًا.

يلزم توخي الحذر مع تصفية التسميات لأنه افتراضيًا، يتم استخدام جميع التسميات لإنشاء اسم مثيل PCP. عن طريق استبعاد بعض التسميات (أو تغييرها إلى اختيارية)، ستتغير أسماء المثيلات. بالإضافة إلى ذلك، يؤدي استبعاد جميع التسميات لمقياس معين إلى تحويل هذا المقياس إلى مقياس فردي، أي ليس له مجال مثيل. عن طريق استبعاد بعض التسميات، قد تصبح المثيلات المختلفة التي يتم إرجاعها بواسطة عنوان URL أو إدخال التكوين المكتوب للأمر نفسه للمقياس نفسه مكررة. عندما تحدث هذه التكرارات، فإن آخر مثيل مكرر تم إرجاعه بواسطة نقطة النهاية لعنوان URL أو البرنامج النصي يسود على أي مثيلات سابقة. لهذه الأسباب، يوصى بتكوين قواعد تصفية التسميات عند تعريف ملف التكوين لأول مرة، وعدم تغييرها بعد ذلك. إذا كان تغيير تصفية التسمية مطلوبًا، فيجب إعادة تسمية ملف التكوين، مما يحدد فعليًا مقياسًا جديدًا (أو مجموعة من المقاييس النظيرة كما تم إرجاعها بواسطة عنوان URL أو البرنامج النصي)، مع تسمية المثيل الجديدة (أو المتغيرة).

يتم الإبلاغ عن الكلمات الرئيسية غير المعروفة في ملفات التكوين في ملف سجل PMDA ولكن يتم تجاهلها بخلاف ذلك.

مصادر مكتوبة

سيتم تنفيذ البرامج النصية القابلة للتنفيذ الموجودة في الدليل $PCP_PMDAS_DIR/openmetrics/config.d أو الدلائل الفرعية وسيتم تحليل تدفق stdout الذي يحتوي على بيانات مقياس بتنسيق openmetrics كما لو كان قادمًا من عنوان URL أو ملف. سيتم إرسال تدفق stderr من البرنامج النصي إلى ملف سجل PMDA، والذي يوجد افتراضيًا في $(PCP_LOG_DIR)/pmcd/openmetrics.log.

لاحظ أن المصادر المكتوبة لا تدعم تصفية التسميات أو المقاييس (كما هو موضح أعلاه لمصادر عنوان URL) - يمكنها ببساطة إجراء تصفيتها الخاصة في البرنامج النصي نفسه باستخدام sed(1)، awk(1)، أو أي أداة مرغوبة.

مثال بسيط لإدخال تكوين مكتوب يتبع: 

#! /bin/sh
awk '{
    print("# HELP loadavg local load average")
    print("# TYPE loadavg gauge")
    printf("loadavg {interval=\"1-minute\"} %.2f\n", $1)
    printf("loadavg {interval=\"5-minute\"} %.2f\n", $2)
    printf("loadavg {interval=\"15-minute\"} %.2f\n", $3)
}' /proc/loadavg

ينتج هذا البرنامج النصي بيانات مقياس بتنسيق OpenMetrics التالية عند تشغيله: 

# HELP loadavg local load average
# TYPE loadavg gauge
loadavg {interval="1-minute"} 0.12
loadavg {interval="5-minute"} 0.27
loadavg {interval="15-minute"} 0.54

إذا تم حفظ البرنامج النصي أعلاه وجعله قابلاً للتنفيذ في ملف يسمى $PCP_PMDAS_DIR/openmetrics/config.d/local/system.sh، فسينتج عن ذلك مقياس PCP جديد يسمى openmetrics.local.system.loadavg والذي سيكون له ثلاثة مثيلات لقيم متوسط ​​الحمل الحالية: 1-minute، 5-minute، و 15-minute.

يمكن لإدخالات التكوين المكتوبة أن تنتج أكثر من اسم مقياس ورقة PCP واحد. على سبيل المثال، يمكن للبرنامج النصي "system.sh" أعلاه تصدير مقاييس أخرى مثل إحصائيات وحدة المعالجة المركزية، عن طريق قراءة /proc/stat على النظام المحلي. ستظهر هذه المقاييس الإضافية كمقاييس نظيرة في نفس شجرة مقاييس PCP. في حالة عدادات وحدة المعالجة المركزية، يجب أن يكون تعريف نوع المقياس counter، وليس gauge. للحصول على تفاصيل كاملة لتنسيقات عرض openmetrics، راجع https://github.com/OpenObservability/OpenMetrics/blob/master/specification/OpenMetrics.md.

اعتبارات SELinux

يتم تنفيذ ملفات التكوين المكتوبة بواسطة PMDA pmdaopenmetrics بنفس سياق وسياسة SELinux مثل pmcd(1) المحلي. بالنسبة للبرامج النصية البسيطة، مثل مثال متوسط ​​الحمل الموضح أعلاه، يكون هذا مقبولاً عادةً. ومع ذلك، قد تنتج أخطاء AVC للبرامج النصية التي تقوم باستدعاءات مكتبية أو نظامية مقيدة بالسياق والسياسات السائدة لـ SELinux. في هذه الحالات، لا يمكن منح pmcd أو PMDAs الخاصة به سياسة تنفيذ غير مقيدة بشكل أحادي. في هذه الحالات الخاصة بالموقع، سيكون من الضروري إنشاء وحدة سياسة SELinux محلية. يمكن القيام بذلك عن طريق التقاط سجل (سجلات) AVC من سجل التدقيق المحلي، وإنشاء وحدة سياسة محلية باستخدام audit2allow، ثم تحميل الوحدة الجديدة باستخدام semodule، على سبيل المثال كما يلي: 

    $ sudo grep '^type=AVC.*pcp' /var/log/audit/audit.log \
    | audit2allow -M mypolicy
    $ sudo semodule -i mypolicy.pp

إذا كانت هذه السياسات المحلية بحاجة إلى أن تكون دائمة عبر عمليات إعادة التشغيل، فيمكن إضافة جزء نصي مشابه للمثال أعلاه إلى ملف rc المحلي لـ pmcd (عادةً /etc/pcp/pmcd/rc.local). لمزيد من التفاصيل، راجع audit2allow(1) و semodule(1).

تسمية المقاييس

سيتم تصدير جميع المقاييس من ملف يسمى JOB.* كمقاييس PCP مع البادئة openmetrics.JOB لاسم المقياس. لذلك، يجب أن يكون اسم الوظيفة اسمًا غير ورقة صالحًا لأسماء مقاييس PCP PMNS. إذا كان اسم JOB يحتوي على مكونات متعددة مفصولة بنقطة، فستتضمن أسماء PMNS الناتجة تلك المكونات ويجب توخي الحذر لضمان عدم وجود تعريفات متداخلة، على سبيل المثال، قد تتداخل المقاييس التي تم إرجاعها بواسطة JOB.response أو تتعارض مع المقاييس التي تم إرجاعها بواسطة JOB.response.time.

ستؤدي إدخالات ملف التكوين (عناوين URL أو البرامج النصية) الموجودة في الدلائل الفرعية لدليل التكوين أيضًا إلى أسماء مقاييس هرمية. على سبيل المثال، ملف تكوين يسمى $PCP_PMDAS_DIR/openmetrics/config.d/mysource/latency/get.url سينتج عن إنشاء مقاييس (عن طريق جلب عنوان URL المصدر هذا) أسفل openmetrics.mysource.latency.get في مساحة اسم PCP. تنتج البرامج النصية الموجودة في الدلائل الفرعية لدليل التكوين أسماء مقاييس PCP هرمية بشكل مشابه.

أسماء المقاييس الديناميكية

كما هو موضح أعلاه، يمكن إجراء التغييرات والإضافات الجديدة على الملفات في دليل التكوين دون الحاجة إلى إعادة تشغيل PMDA. يتم اكتشاف هذه التغييرات تلقائيًا وسيتم تحديث أسماء مقاييس PCP أسفل openmetrics في PMNS وفقًا لذلك، أي سيتم إضافة مقاييس جديدة وإزالتها بشكل ديناميكي. بالإضافة إلى ذلك، pmdaopenmetrics يحترم بروتوكول PMCD_NAMES_CHANGE pmFetch(3) الذي تم تقديمه في الإصدار 4.0 من PCP. على وجه الخصوص، إذا كانت مقاييس openmetrics يتم تسجيلها بواسطة pmlogger(1) بإصدار 4.0 أو أحدث من PCP، فستبدأ المقاييس الجديدة التي تظهر نتيجة للتغييرات في دليل تكوين PMDA في التسجيل تلقائيًا، بشرط أن يكون جذر مساحة اسم openmetrics PMDA مكوّنًا للتسجيل في ملف تكوين pmlogger. راجع pmlogger(1) للحصول على التفاصيل. مثال على ملف تكوين pmlogger كهذا: 

log mandatory on 2 second {
	# log all metrics below the root of the openmetrics namespace
	openmetrics
}

البيانات الوصفية

قد تحتوي بيانات المقياس التي تم إرجاعها بواسطة عناوين URL أو ملفات التكوين المكتوبة على بيانات وصفية يمكن استخدامها بواسطة PMDA openmetrics لتحديد الدلالات، ونوع البيانات، والتحجيم، ووحدات المقاييس التي تم إنشاؤها ديناميكيًا. هذه البيانات الوصفية مسبوقة بـ # PCP5 أو # PCP في بيانات المقياس المستوردة. للحصول على معلومات إضافية حول البيانات الوصفية لـ PCP، راجع pmLookupDesc(3) و pmParseUnitsStr(3) والأمثلة في ملفات التكوين المشحونة.

يجب توفير البيانات الوصفية "PCP5" المضمنة بواسطة نقطة نهاية مصدر المقياس (عنوان URL أو البرنامج النصي). البديل هو تحديد ذلك مباشرة في ملف تكوين عنوان URL، والذي يتمتع بميزة عدم الاضطرار إلى تعديل المصدر/نقطة النهاية إذا كانت البيانات الوصفية غير صحيحة أو مفقودة. البيانات الوصفية المحددة في ملف تكوين عنوان URL تتجاوز أي بيانات وصفية مضمنة.

صيغة ملف التكوين لتحديد البيانات الوصفية هي:
METADATA: regex type indom semantics units ... إلى نهاية السطر
حيث:
METADATA: هو حرفي
regex هو تعبير عادي موسع لمطابقة اسم مقياس واحد أو أكثر تم إرجاعه بواسطة عنوان URL،
type هو أحد أنواع PCP الرقمية (32، u32، 64، u64، float أو double)،
indom هو اسم مجال مثيل عشوائي، أو PM_INDOM_NULL،
semantics هو إما counter، instant أو discrete و
units هو إما none أو سلسلة تمتد إلى نهاية السطر والتي يمكن تحليلها بواسطة pmParseUnitsStr(3)، أي الوحدات، الأبعاد، والتحجيم المستخدم للمقاييس المتطابقة.

مثال لملف تكوين يستورد المقاييس من نقطة النهاية Grafana /metrics على localhost، ويستبعد جميع المقاييس التي تم إرجاعها بواسطة عنوان URL هذا باستثناء grafana_api_response_status_total ثم يحدد أن نوع المقياس هو عدد صحيح غير موقع من 32 بت مع مجال مثيل غير فردي يسمى response ودلالات counter مع وحدات count.

http://localhost:3000/metrics
FILTER: INCLUDE METRIC grafana_api_response_status_total
FILTER: EXCLUDE METRIC .*
METADATA: grafana_api_response_status_total u32 response counter count

لاحظ أن الاسم في حقل indom يتم تجاهله حاليًا ما لم يكن PM_INDOM_NULL، وفي هذه الحالة، المقي

c ليس له مثيل

نطاق (أي، مفرد)، حتى لو كان لديه تسميات تستخدم عادةً لتسمية المثيل.

مقاييس التحكم

يحتفظ PMDA بمقاييس تحكم خاصة، كما هو موضح أدناه. بصرف النظر عن openmetrics.control.debug، لكل من هذه المقاييس مثيل واحد لكل مصدر مقياس تم تكوينه. تمتلك جميع هذه المقاييس قيمًا صحيحة ذات دلالات عداد، باستثناء openmetrics.control.status، الذي له قيمة سلسلة. من المهم ملاحظة أن جلب أي من مقاييس openmetrics.control سيقوم فقط بتحديث العدادات وحالات القيم إذا تم جلب عنوان URL المقابل فعليًا. إذا لم يتم جلب عنوان URL للمصدر، فإن قيم مقياس التحكم لا تؤدي إلى تحديث، والقيم المتحكم بها المبلغ عنها تمثل أحدث جلب لكل مصدر مقابل.

يتم تعديل نطاق المثيل لمقاييس openmetrics.control ديناميكيًا عند اكتشاف مصادر جديدة. إذا لم يتم تكوين مصادر، فلا تزال أسماء المقاييس محددة ولكن نطاق المثيل سيكون فارغًا وسيعيد جلب أي قيم.

openmetrics.control.status
سلسلة تمثل حالة آخر جلب للمصدر المقابل. سيكون هذا عادةً success لرمز استجابة HTTP 200. يمكن استخدام هذا المقياس لمراقبة توفر الخدمة - بشرط، كما هو مذكور أعلاه، أن يتم جلب عنوان URL للمصدر المقابل أيضًا.
openmetrics.control.status_code
هذا المقياس مشابه لـ openmetrics.control.status باستثناء أنه رمز الاستجابة الصحيح لآخر جلب. عادةً ما يعني الرقم 200 النجاح وأي قيمة أخرى الفشل. يمكن أيضًا استخدام هذا المقياس لمراقبة توفر الخدمة، مع نفس التحذيرات الخاصة بـ openmetrics.control.status.
openmetrics.control.calls
العدد الإجمالي للمرات التي تم فيها جلب كل مصدر مقياس تم تكوينه (إذا كان عنوان URL) أو تنفيذه (إذا كان نصًا برمجيًا)، منذ بدء PMDA. هذا المقياس له دلالات عداد ويتم تحويله عادةً إلى معدل/ثانية بواسطة أدوات العميل.
openmetrics.control.fetch_time
الوقت الإجمالي بالمللي ثانية الذي استغرقه كل مصدر مقياس تم تكوينه لإعادة مستند، باستثناء وقت تحليل المستند. هذا المقياس له دلالات عداد ويتم تحويله عادةً إلى معدل بواسطة أدوات العميل ولكنه مفيد أيضًا في شكله الخام كوقت تحليل مجمع منذ بدء PMDA.
openmetrics.control.parse_time
الوقت الإجمالي بالمللي ثانية الذي استغرقه كل مصدر مقياس تم تكوينه لتحليل كل مستند، باستثناء وقت جلب المستند. هذا المقياس له دلالات عداد ويتم تحويله عادةً إلى معدل بواسطة أدوات العميل ولكنه مفيد أيضًا في شكله الخام كوقت تحليل مجمع منذ بدء PMDA.

عند التحويل إلى معدل، يمثل مقياس calls متوسط معدل الجلب لكل مصدر خلال فترة العينة (الفارق الزمني بين العينات). العدادات fetch_time و parse_time، عند التحويل إلى معدل، تمثل متوسط زمن الاستجابة للجلب والتحليل (على التوالي)، خلال فترة العينة.

مقياس openmetrics.control.debug له قيمة مفردة، بقيمة افتراضية 0. إذا تم تخزين قيمة غير صفرية في هذا المقياس باستخدام pmstore(1)، فسيتم كتابة رسائل تصحيح إضافية في ملف سجل PMDA.

قيود

pmdaopenmetrics و Internals libpcp تفرض بعض القيود الرقمية على عدد المصادر (4095)، والمقاييس (1024) داخل كل مصدر، والمثيلات لكل مقياس (4194304).

تثبيت

قم بتثبيت OpenMetrics PMDA باستخدام برنامج التثبيت كـ root:

# cd $PCP_PMDAS_DIR/openmetrics
# ./Install

لإلغاء التثبيت، يجب القيام بما يلي كـ root:

# cd $PCP_PMDAS_DIR/openmetrics
# ./Remove

pmdaopenmetrics يتم تشغيله بواسطة pmcd(1) ويجب ألا يتم تنفيذه مباشرة أبدًا. تقوم برامج التثبيت والإزالة بإعلام pmcd عند تثبيت أو إزالة الوكيل.

عند إضافة البرامج النصية وملفات .url أو إزالتها أو تغييرها في دليل التكوين، لا يلزم عادةً إعادة تشغيل PMDA - سيتم اكتشاف التغييرات وإدارتها عند الطلبات اللاحقة إلى PMDA.

ملفات

$PCP_PMDAS_DIR/openmetrics/Install
برنامج تثبيت لوكيل pmdaopenmetrics
$PCP_PMDAS_DIR/openmetrics/Remove
برنامج إلغاء تثبيت وكيل pmdaopenmetrics
$PCP_PMDAS_DIR/openmetrics/config.d/
يحتوي على عناوين URL والنصوص البرمجية التي يستخدمها وكيل pmdaopenmetrics كمصادر لبيانات مقياس openmetrics.
$PCP_LOG_DIR/pmcd/openmetrics.log
ملف السجل الافتراضي لرسائل الخطأ من pmdaopenmetrics
$PCP_VAR_DIR/config/144.*
ملفات تحتوي على جداول داخلية للمقاييس ومُعرّفات المثيل للحفاظ على الأرقام (المجال 144).

بيئة PCP

يتم استخدام متغيرات البيئة ذات البادئة PCP_ لمعلمة أسماء الملفات والدلائل التي يستخدمها PCP. عند كل تثبيت، يحتوي الملف /etc/pcp.conf على القيم المحلية لهذه المتغيرات. يمكن استخدام متغير $PCP_CONF لتحديد ملف تكوين بديل، كما هو موضح في pcp.conf(5).
