PMAPI(3) Library Functions Manual PMAPI(3)

NAME

PMAPI - مقدمة لواجهة برمجة تطبيقات مقاييس الأداء

C SYNOPSIS

#include <pcp/pmapi.h>

... assorted routines ...

cc ... -lpcp

DESCRIPTION

ضمن إطار عمل نظام مراقبة الأداء (PCP)، يتم تطوير تطبيقات العملاء باستخدام واجهة برمجة تطبيقات مقاييس الأداء (PMAPI) التي تحدد واجهة إجرائية مع خدمات مناسبة لتطوير التطبيقات ذات الاهتمام الخاص بمقاييس الأداء.

يقدم هذا الوصف نظرة عامة على PMAPI والسياق الذي يتم فيه تشغيل تطبيقات PMAPI. توصف PMAPI بشكل أكثر اكتمالًا في دليل مبرمج نظام مراقبة الأداء، والصفحات اليدوية لروتينات PMAPI الفردية.

PERFORMANCE METRICS - NAMES AND IDENTIFIERS

لوصف مساحة أسماء مقاييس الأداء (PMNS) والمصطلحات والمفاهيم المرتبطة بها، راجع PCPIntro(1).

لا يلزم تمثيل جميع معرفات المقاييس (PMIDs) في PMNS لكل تطبيق. على سبيل المثال، من المرجح أن يستخدم تطبيق يراقب حركة مرور القرص مساحة أسماء تشير فقط إلى معرفات المقاييس (PMIDs) لإحصائيات الإدخال / الإخراج.

قد تمتلك التطبيقات التي تستخدم PMAPI إصدارات مستقلة من PMNS، يتم إنشاؤها من ملف تهيئة عند بدء تشغيل التطبيق؛ راجع pmLoadASCIINameSpace(3)، pmLoadNameSpace(3)، و PMNS(5).

داخليًا (أسفل PMAPI) يستخدم تنفيذ نظام جمع مقاييس الأداء (PMCS) معرفات المقاييس (PMIDs) فقط، ويوفر PMNS تعيينًا خارجيًا من تسلسل هرمي للأسماء إلى معرفات المقاييس (PMIDs) وهو مناسب في سياق نظام معين أو استخدام معين لـ PMAPI. بالنسبة لمبرمج التطبيق، تقوم الروتينات pmLookupName(3) و pmNameID(3) بالتحويل بين الأسماء في PMNS ومعرفات المقاييس (PMIDs)، والعكس صحيح. يمكن اجتياز PMNS باستخدام pmGetChildren(3) و pmTraversePMNS. تجمع وظائف pmFetchGroup(3) بين عمليات البحث عن اسم المقياس وجلبه وتحويله.

PMAPI CONTEXT

قد يقوم تطبيق يستخدم PMAPI بمعالجة عدة سياقات متزامنة، كل منها مرتبط بمصدر لمقاييس الأداء، على سبيل المثال pmcd(1) على بعض المضيفين، أو مجموعة من الأرشيفات لمقاييس الأداء كما تم إنشاؤها بواسطة pmlogger(1).

يتم التعرف على السياقات بواسطة "معالج"، وهو قيمة عددية صحيحة صغيرة يتم إرجاعها عند إنشاء السياق؛ راجع pmNewContext(3) و pmDupContext(3). تتطلب بعض وظائف PMAPI "معالج" صريحًا لتحديد السياق الصحيح، ولكن بشكل أكثر شيوعًا يتم تنفيذ وظيفة PMAPI في السياق "الحالي". يمكن اكتشاف السياق الحالي باستخدام pmWhichContext(3) وتغييره باستخدام pmUseContext(3).

إذا لم يتم إنشاء سياق PMAPI بشكل صريح (أو تم إغلاق السياق الحالي السابق باستخدام pmDestroyContext(3))، فإن السياق الحالي لـ PMAPI يكون غير محدد.

بالإضافة إلى مصدر مقاييس الأداء، يتضمن السياق أيضًا ملف تعريف المثيل ووقت المجموعة (كلاهما موصوف أدناه) الذي يتحكم في مقدار المعلومات التي تم إرجاعها، ومتى تم جمع المعلومات.

INSTANCE DOMAINS

عندما يتم إرجاع قيم مقاييس الأداء عبر PMAPI إلى تطبيق طالب، قد يكون هناك أكثر من قيمة واحدة لمقياس معين. القيم المتعددة، أو المثيلات، لمقياس واحد هي عادة نتيجة للتنفيذ الذي تم تنفيذه لكل مثيل لمجموعة من المكونات أو الخدمات المماثلة في النظام، على سبيل المثال، عدادات مستقلة لكل وحدة معالجة مركزية، أو كل عملية، أو كل قرص، أو كل نوع استدعاء نظام، إلخ. لا يتم تعداد هذه التعددية في مساحة الأسماء، بل، عند تسليم مقاييس الأداء عبر PMAPI بواسطة pmFetch(3)، فإن تنسيق النتيجة يستوعب قيمًا لمثيل واحد أو أكثر، مع ترميز زوج مثيل-قيمة لقيمة المقياس لمثيل معين.

يتم تحديد المثيلات بواسطة معرف داخلي تم تعيينه بواسطة الوكيل المسؤول عن تجسيد القيم للمقياس المقابل. لكل معرف مثيل اسم معرف مثيل خارجي مطابق (سلسلة ASCII). الروتينات pmGetInDom(3)، pmLookupInDom(3) و pmNameInDom(3) يمكن استخدامها لسرد جميع معرفات المثيلات، والتحويل بين معرفات المثيلات الداخلية والخارجية.

جميع معرفات المثيلات لمقياس أداء معين تُعرف جماعيًا باسم نطاق المثيل. قد تشترك مقاييس الأداء المتعددة في نفس نطاق المثيل.

إذا كان هناك مثيل واحد فقط متاح لمقياس أداء معين، فإن معرف المثيل في النتيجة من pmFetch(3) يأخذ القيمة الخاصة PM_IN_NULL ويمكن تجاهله بواسطة التطبيق، ويظهر زوج مثيل-قيمة واحد فقط في النتيجة لهذا المقياس. في ظل هذه الظروف، يتم تعيين نطاق المثيل المقابل (كما تم إرجاعه عبر pmLookupDesc(3)) إلى PM_INDOM_NULL للإشارة إلى أن قيم هذا المقياس فريدة.

مسألة مقاييس الأداء العابرة الصعبة (مثل المعلومات لكل نظام ملفات، وحدات الأجهزة القابلة للاستبدال بالتبديل الساخن، إلخ) تعني أن الطلبات المتكررة لنفس PMID قد ترجع عددًا مختلفًا من القيم، و / أو بعض التغييرات في معرفات المثيلات المحددة التي تم إرجاعها. هذا يعني أن التطبيقات بحاجة إلى أن تكون على دراية بأن تجسيد المقياس مضمون أن يكون صالحًا في وقت المجموعة فقط. تنطبق قواعد مماثلة على الدلالات العابرة للقيم المقابلة للمقياس. بشكل عام، ومع ذلك، من المتوقع أن يكون لدى غالبية مقاييس الأداء دلالات تجسيد ثابتة على مدى عمر تنفيذ أي عميل PMAPI.

THE TYPE OF METRIC VALUES

تدعم PMAPI مجموعة واسعة من ترميزات التنسيق والنوع لقيم مقاييس الأداء، وهي الأعداد الصحيحة ذات العلامة وبدون علامة، والأرقام العشرية، ترميزات 32-بت و 64-بت لكل ما سبق، وسلاسل ASCII (نمط C، تنتهي ببايت NULL)، وتجميعات عشوائية للبيانات الثنائية.

يشير حقل type في البنية pmDesc التي يتم إرجاعها بواسطة pmLookupDesc(3) إلى تنسيق ونوع القيم لمقياس أداء معين ضمن سياق PMAPI معين.

لاحظ أن ترميز القيم لمقياس أداء معين قد يختلف لسياقات PMAPI مختلفة، بسبب الاختلافات في التنفيذ الأساسي للسياقات المختلفة. ومع ذلك، من المتوقع أن يكون لدى الغالبية العظمى من مقاييس الأداء ترميز قيم متناسق عبر جميع إصدارات جميع التطبيقات، وبالتالي عبر جميع سياقات PMAPI.

تدعم PMAPI الروتينات لأتمتة معالجة تنسيقات وأنواع القيم المختلفة، خاصة في الحالة الشائعة حيث يكون التحويل إلى تنسيق معياري مرغوبًا فيه، راجع pmExtractValue(3) و pmPrintValue(3).

THE DIMENSIONALITY AND SCALE OF METRIC VALUES

The PMAPI(3) routines allow the client application to request performance metric values in a variety of physical units. For example, a counter such as the number of bytes transferred may be requested in units of bytes, kilobytes, megabytes, gigabytes, etc. This is achieved by associating a dimensionality and scale with each performance metric. The dimensionality determines the physical quantity that is being measured, for example, bytes, seconds, or counts. The scale determines the units in which the measurement is to be expressed, for example, kilo-, mega-, or giga-. For metrics that may have values that exceed the precision of a 32-bit integer, the scale component can be used to map these values into a range that can be represented within the available dimension there are a number of common scale values that may be used to better encode ranges that might otherwise exhaust the precision of a 32-bit value. This information is encoded in the pmUnits structure which is embedded in the pmDesc structure returned from pmLookupDesc(3).

The routine pmConvScale(3) is provided to convert values in conjunction with the pmUnits structures that defines the dimensionality and scale of the values for a particular performance metric as returned from pmFetch(3), and the desired dimensionality and scale of the value the PMAPI client wishes to manipulate. Alternatively, the pmFetchGroup(3) functions can perform data format and unit conversion operations, specified by textual descriptions of desired unit / scales.

ملف تعريف المثيل

The set of instances for performance metrics returned from a pmFetch(3) call may be filtered or restricted using an instance profile. There is one instance profile for each PMAPI context the application creates, and each instance profile may include instances from one or more instance domains.

The routines pmAddProfile(3) and pmDelProfile(3) may be used to dynamically adjust the instance profile.

وقت التجميع

For each set of values for performance metrics returned via pmFetch(3) there is an associated ``timestamp'' that serves to identify when the performance metric values were collected; for metrics being delivered from a real-time source (i.e. pmcd(1) on some host) this would typically be not long before they were exported across the PMAPI, and for metrics being delivered from a set of archives, this would be the time when the metrics were written into the archive.

There is an issue here of exactly when individual metrics may have been collected, especially given their origin in potentially different Performance Metric Domains, and variability in the metric updating frequency at the lowest level of the Performance Metric Domain. The PMCS opts for the pragmatic approach, in which the PMAPI implementation undertakes to return all of the metrics with values accurate as of the timestamp, to the best of our ability. The belief is that the inaccuracy this introduces is small, and the additional burden of accurate individual timestamping for each returned metric value is neither warranted nor practical (from an implementation viewpoint).

Of course, in the case of collection of metrics from multiple hosts the PMAPI client must assume the sanity of the timestamps is constrained by the extent to which clock synchronization protocols are implemented across the network.

A PMAPI application may call pmSetMode(3) to vary the requested collection time, e.g. to rescan performance metrics values from the recent past, or to ``fast-forward'' through a set of archives.

قضايا عامة لأسلوب برمجة PMAPI

Across the PMAPI, all arguments and results involving a ``list of something'' are declared to be arrays with an associated argument or function value to identify the number of elements in the list. This has been done to avoid both the varargs(3) approach and sentinel-terminated lists.

Where the size of a result is known at the time of a call, it is the caller's responsibility to allocate (and possibly free) the storage, and the called function will assume the result argument is of an appropriate size. Where a result is of variable size and that size cannot be known in advance (e.g. for pmGetChildren(3), pmGetInDom(3), pmNameInDom(3), pmNameID(3), pmLookupLabels(3), pmLookupText(3) and pmFetch(3)) the PMAPI implementation uses a range of dynamic allocation schemes in the called routine, with the caller responsible for subsequently releasing the storage when no longer required. In some cases this simply involves calls to free(3), but in others (most notably for the result from pmFetch(3)), special routines (e.g. pmFreeResult(3) and pmFreeLabelSets(3)) should be used to release the storage.

As a general rule, if the called routine returns an error status then no allocation will have been done, and any pointer to a variable sized result is undefined.

التشخيص

Where error conditions may arise, the functions that comprise the PMAPI conform to a single, simple error notification scheme, as follows;

+
the function returns an integer
+
values >= 0 indicate no error, and perhaps some positive status, e.g. the number of things really processed
+
values < 0 indicate an error, with a global table of error conditions and error messages

The PMAPI routine pmErrStr(3) translates error conditions into error messages. By convention, the small negative values are assumed to be negated versions of the Unix error codes as defined in <errno.h> and the strings returned are as per strerror(3). The larger, negative error codes are PMAPI error conditions.

One error, common to all PMAPI routines that interact with pmcd(1) on some host is PM_ERR_IPC, which indicates the communication link to pmcd(1) has been lost.

التطبيقات متعددة المواضيع

The original design for PCP was based around single-threaded applications, or more strictly applications in which only one thread was ever expected to call the PCP libraries. This restriction has been relaxed for libpcp to allow the most common PMAPI routines to be safely called from any thread in a multi-threaded application.

However the following groups of functions and services in libpcp are still restricted to being called from a single-thread, and this is enforced by returning PM_ERR_THREAD when an attempt to call the routines in each group from more than one thread is detected.

1.
Any use of a PM_CONTEXT_LOCAL context, as the DSO PMDAs that are called directly from libpcp may not be thread-safe.

بيئة PCP

Most environment variables are described in PCPIntro(1). In addition, environment variables with the prefix PCP_ are used to parameterize the file and directory names used by PCP. On each installation, the file /etc/pcp.conf contains the local values for these variables. The $PCP_CONF variable may be used to specify an alternative configuration file, as described in pcp.conf(5). Values for these variables may be obtained programmatically using the pmGetConfig(3) function.
