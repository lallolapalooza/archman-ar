الوصف

dlopen()

تقوم الدالة dlopen() بتحميل ملف الكائن المشترك الديناميكي (المكتبة المشتركة) المسمى بواسطة السلسلة المنتهية بصفر path وتعيد مقبضًا "غامضًا" للكائن المحمل. يُستخدم هذا المقبض مع دوال أخرى في واجهة برمجة تطبيقات dlopen، مثل dlsym(3)، dladdr(3)، dlinfo(3)، و dlclose().

إذا كان path هو NULL، فإن المقبض المعادل يكون للبرنامج الرئيسي. إذا كان path يحتوي على شرطة مائلة ("/")، فيتم تفسيره كمسار (نسبي أو مطلق). بخلاف ذلك، يبحث الرابط الديناميكي عن الكائن كما يلي (راجع ld.so(8) لمزيد من التفاصيل):

•
(ELF فقط) إذا كان الكائن المستدعي (أي، المكتبة المشتركة أو الملف التنفيذي الذي يتم استدعاء dlopen() منه) يحتوي على علامة DT_RPATH، ولا يحتوي على علامة DT_RUNPATH، فسيتم البحث في الدلائل المدرجة في علامة DT_RPATH.
•
إذا كانت متغير البيئة LD_LIBRARY_PATH محددًا يحتوي على قائمة فواصل نقطية للدلائل، فعند بدء تشغيل البرنامج، يتم البحث فيها. (كإجراء أمني، يتم تجاهل هذا المتغير للبرامج set-user-ID و set-group-ID).
•
(ELF فقط) إذا كان الكائن المستدعي يحتوي على علامة DT_RUNPATH، فسيتم البحث في الدلائل المدرجة في تلك العلامة.
•
يتم التحقق من ملف ذاكرة التخزين المؤقت /etc/ld.so.cache (المُدار بواسطة ldconfig(8)) لمعرفة ما إذا كان يحتوي على إدخال لـ path.
•
يتم البحث في الدلائل /lib و /usr/lib (بهذا الترتيب).

إذا كان الكائن المحدد بواسطة path له تبعيات على كائنات مشتركة أخرى، فسيتم تحميلها تلقائيًا بواسطة الرابط الديناميكي باستخدام نفس القواعد. (قد تحدث هذه العملية بشكل متكرر، إذا كانت تلك الكائنات بدورها لها تبعيات، وهكذا.)

يجب تضمين أحد القيمتين التاليتين في flags:

RTLD_LAZY
تنفيذ الربط الكسول. حل الرموز فقط عند تنفيذ الكود الذي يشير إليها. إذا لم تتم الإشارة إلى الرمز مطلقًا، فلن يتم حله أبدًا. (يتم إجراء الربط الكسول فقط لمراجع الدوال؛ يتم دائمًا ربط مراجع المتغيرات فورًا عند تحميل المكتبة المشتركة.) منذ glibc 2.1.1، يتم تجاوز هذه العلامة بتأثير متغير البيئة LD_BIND_NOW.
RTLD_NOW
إذا تم تحديد هذه القيمة، أو تم تعيين متغير البيئة LD_BIND_NOW إلى سلسلة غير فارغة، فسيتم حل جميع الرموز غير المعرفة في المكتبة المشتركة قبل أن تعود dlopen(). إذا لم يكن ذلك ممكنًا، فسيتم إرجاع خطأ.

يمكن أيضًا دمج صفر أو أكثر من القيم التالية في flags:

RTLD_GLOBAL
سيتم جعل الرموز المعرفة بواسطة هذه المكتبة المشتركة متاحة لحل الرموز في المكتبات المشتركة التي يتم تحميلها لاحقًا.
RTLD_LOCAL
هذا هو عكس RTLD_GLOBAL، وهو الافتراضي إذا لم يتم تحديد أي من العلامتين. لا يتم جعل الرموز المعرفة في هذه المكتبة المشتركة متاحة لحل المراجع في المكتبات المشتركة التي يتم تحميلها لاحقًا.
RTLD_NODELETE (منذ glibc 2.2)
لا تقم بإلغاء تحميل المكتبة المشتركة أثناء dlclose(). وبالتالي، لا تتم إعادة تهيئة المتغيرات الثابتة والعامة للكائن إذا تمت إعادة تحميل الكائن باستخدام dlopen() في وقت لاحق.
RTLD_NOLOAD (منذ glibc 2.2)
لا تقم بتحميل المكتبة المشتركة. يمكن استخدام هذا لاختبار ما إذا كان الكائن موجودًا بالفعل (تعيد dlopen() NULL إذا لم يكن كذلك، أو مقبض الكائن إذا كان موجودًا). يمكن أيضًا استخدام هذه العلامة لترقية العلامات على مكتبة مشتركة تم تحميلها بالفعل. على سبيل المثال، يمكن إعادة فتح مكتبة مشتركة تم تحميلها سابقًا باستخدام RTLD_LOCAL باستخدام RTLD_NOLOAD | RTLD_GLOBAL.
RTLD_DEEPBIND (منذ glibc 2.3.4)
ضع نطاق البحث للرموز في هذه المكتبة المشتركة قبل النطاق العام. هذا يعني أن الكائن المستقل ذاتيًا سيستخدم رموزه الخاصة بشكل تفضيلي على الرموز العامة بنفس الاسم الموجودة في الكائنات التي تم تحميلها بالفعل.

إذا كان path هو NULL، فإن المقبض المعادل يكون للبرنامج الرئيسي. عند إعطائه لـ dlsym(3)، يتسبب هذا المقبض في البحث عن رمز في البرنامج الرئيسي، متبوعًا بجميع المكتبات المشتركة التي تم تحميلها عند بدء تشغيل البرنامج، ثم جميع المكتبات المشتركة التي تم تحميلها بواسطة dlopen() باستخدام العلامة RTLD_GLOBAL.

تتم معالجة مراجع الرموز في المكتبة المشتركة باستخدام (بالترتيب): الرموز في خريطة الربط للكائنات التي تم تحميلها للبرنامج الرئيسي وتبعيته؛ الرموز في المكتبات المشتركة (وتبعياتها) التي تم فتحها سابقًا باستخدام dlopen() باستخدام العلامة RTLD_GLOBAL؛ والتعريفات في المكتبة المشتركة نفسها (وأي تبعيات تم تحميلها لتلك المكتبة).

يمكن أيضًا استخدام أي رموز عامة في الملف التنفيذي التي تم وضعها في جدول الرموز الديناميكي الخاص بها بواسطة ld(1) لمعالجة المراجع في مكتبة مشتركة يتم تحميلها ديناميكيًا. قد يتم وضع الرموز في جدول الرموز الديناميكي إما لأن الملف التنفيذي تم ربطه بالعلامة "-rdynamic" (أو، بشكل مرادف، "--export-dynamic")، مما يتسبب في وضع جميع الرموز العامة للملف التنفيذي في جدول الرموز الديناميكي، أو لأن ld(1) لاحظ تبعية على رمز في كائن آخر أثناء الربط الثابت.

إذا تم فتح نفس المكتبة المشتركة مرة أخرى باستخدام dlopen()، فسيتم إرجاع نفس مقبض الكائن. يحتفظ الرابط الديناميكي بعدادات المراجع لمقابض الكائنات، لذلك لا يتم إلغاء تخصيص المكتبة المشتركة المحملة ديناميكيًا حتى يتم استدعاء dlclose() عليها بالعدد نفسه من المرات التي نجحت فيها dlopen() عليها. يتم استدعاء المنشئات (انظر أدناه) فقط عند تحميل الكائن فعليًا في الذاكرة (أي عندما تزداد عداد المراجع إلى 1).

قد يجبر استدعاء dlopen() لاحقًا الذي يقوم بتحميل نفس المكتبة المشتركة باستخدام RTLD_NOW على حل الرموز لمكتبة مشتركة تم تحميلها سابقًا باستخدام RTLD_LAZY. وبالمثل، يمكن ترقية كائن تم فتحه سابقًا باستخدام RTLD_LOCAL إلى RTLD_GLOBAL في استدعاء dlopen() لاحق.

إذا فشلت dlopen() لأي سبب، فإنها تعيد NULL.

dlmopen()

تقوم هذه الدالة بنفس مهمة dlopen() - الوسائط path و flags، وكذلك القيمة المعادلة، هي نفسها، باستثناء الاختلافات المذكورة أدناه.

تختلف الدالة dlmopen() عن dlopen() بشكل أساسي في أنها تقبل وسيطًا إضافيًا، lmid، الذي يحدد قائمة الخرائط الرابطة (تسمى أيضًا مساحة الاسم) التي يجب تحميل المكتبة المشتركة فيها. (بالمقارنة، تضيف dlopen() المكتبة المشتركة المحملة ديناميكيًا إلى نفس مساحة الاسم مثل المكتبة المشتركة التي تم استدعاء dlopen() منها.) نوع Lmid_t هو مقبض غامض يشير إلى مساحة اسم.

الوسيط lmid هو إما معرف لمساحة اسم موجودة (والتي يمكن الحصول عليها باستخدام طلب RTLD_DI_LMID من dlinfo(3)) أو أحد القيم الخاصة التالية:

LM_ID_BASE
قم بتحميل المكتبة المشتركة في مساحة الاسم الابتدائية (أي، مساحة اسم التطبيق).

NAME

dlclose — unload a shared object

LIBRARY

Realtime Library (libc, -lrt)

SYNOPSIS

#include <dlfcn.h>

int dlclose(void *handle);

DESCRIPTION

The dlclose() function decreases the reference count on the shared object referred to by handle. When the reference count reaches zero, the shared object is unloaded from the address space of the calling process.

The handle argument is a non-NULL value obtained from a prior call to dlopen(3).

The effect of dlclose() on the state of the shared object is undefined if the handle was obtained in some other way.

If dlopen() was called multiple times with the same shared object name, the shared object will not be unloaded until dlclose() has been called an equal number of times.

RETURN VALUE

On success, dlclose() returns 0. On failure, it returns a non-zero value.

ATTRIBUTES

For an explanation of the terms used in this section, see attributes(7).

Interface Attribute Value
dlclose() Thread safety MT-Safe

STANDARDS

POSIX.1-2008, POSIX.1-2013, POSIX.1-2017

HISTORY

POSIX.1-2001, POSIX.1-2008.

NOTES

The behavior of dlclose() is dependent on the underlying dynamic linker. In particular, the exact point at which the shared object is unloaded is not specified. For example, if the shared object has a constructor or destructor, these may be called when dlclose() is invoked, or they may be delayed until the shared object is actually removed from memory.

The consequences of calling dlclose() on a shared object that is currently in use by another thread are undefined. It is the responsibility of the programmer to ensure that the shared object is no longer in use before calling dlclose().

BUGS

The documentation for the specific implementation of the dynamic linker should be consulted for details on its behavior.

EXAMPLES

The following example shows how to use dlclose(): 

#include <stdio.h>
#include <stdlib.h>
#include <dlfcn.h>

int main() {
    void *handle;
    const char *error;

    // Load a shared object
    handle = dlopen("libexample.so", RTLD_LAZY);
    if (!handle) {
        fprintf(stderr, "%s\n", dlerror());
        exit(EXIT_FAILURE);
    }

    // Clear any existing error
    dlerror();

    // ... use functions from libexample.so ...

    // Unload the shared object
    if (dlclose(handle) != 0) {
        fprintf(stderr, "%s\n", dlerror());
        exit(EXIT_FAILURE);
    }

    return 0;
}
