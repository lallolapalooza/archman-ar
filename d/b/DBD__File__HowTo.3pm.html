الوصف

يقدم هذا المستند دليلًا خطوة بخطوة حول كيفية إنشاء مشغل جديد يعتمد على "DBD::File". يتوقع منك أن تكون قد قرأت بعناية وثائق DBI وأن تكون على دراية بـ DBI::DBD وأن تكون قد قرأت وفهمت DBD::ExampleP.

يعالج هذا المستند المطورين ذوي الخبرة الذين هم متأكدون حقًا من أنهم بحاجة إلى استثمار الوقت عند كتابة مشغل DBI جديد. كتابة مشغل DBI ليست مشروع عطلة نهاية الأسبوع أو مهمة سهلة لهواة الترميز بعد العمل. توقع شهرًا أو شهرين من العمل للشروع في العمل.

يجب على أولئك الذين لا يزالون يقرأون أن يكونوا قادرين على إنشاد قواعد "إنشاء مشغل جديد" في DBI::DBD.

بالطبع، DBD::File هو DBI::DBD::SqlEngine ويجب أن تكون قد قرأت DBI::DBD::SqlEngine::HowTo قبل المتابعة هنا.

إنشاء فئات المشغل

هل لديك إدخال في سجل مشغلات DBI؟ لهذا الدليل، يُفترض وجود بادئة "foo_".

هيكل عظمي نموذجي

package DBD::Foo;
use strict;
use warnings;
use base qw(DBD::File);
use DBI ();
our $VERSION = "0.001";
package DBD::Foo::dr;
our @ISA = qw(DBD::File::dr);
our $imp_data_size = 0;
package DBD::Foo::db;
our @ISA = qw(DBD::File::db);
our $imp_data_size = 0;
package DBD::Foo::st;
our @ISA = qw(DBD::File::st);
our $imp_data_size = 0;
package DBD::Foo::Statement;
our @ISA = qw(DBD::File::Statement);
package DBD::Foo::Table;
our @ISA = qw(DBD::File::Table);
1;

صغير، أليس كذلك؟ وكل ما لديك الآن هو مشغل يسمى foo والذي سيكون قادرًا على التعامل مع الجداول المؤقتة، طالما أنك تستخدم SQL::Statement. في بيئات DBI::SQL::Nano، لا يمكن لهذا المشغل فعل أي شيء.

البدء من جديد

بناءً على DBI::DBD::SqlEngine::HowTo، لدينا الآن مشغل يمكنه القيام بالأشياء الأساسية. بالطبع، يجب أن يشتق الآن من DBD::File بدلاً من DBI::DBD::SqlEngine، أليس كذلك؟

يمتد DBD::File على DBI::DBD::SqlEngine للتعامل مع أي نوع من الملفات. من حيث المبدأ، فإن الامتدادات الوحيدة المطلوبة هي لفئة الجدول:

package DBD::Foo::Table;
sub bootstrap_table_meta
{
    my ( $self, $dbh, $meta, $table ) = @_;
    # تهيئة جميع سمات $meta التي قد تكون ذات صلة بـ
    # file2table
    return $self->SUPER::bootstrap_table_meta($dbh, $meta, $table);
}
sub init_table_meta
{
    my ( $self, $dbh, $meta, $table ) = @_;
    # يتم استدعاؤه بعد أن يحتوي $meta على نتائج من file2table
    # تهيئة جميع سمات $meta المفقودة
    $self->SUPER::init_table_meta( $dbh, $meta, $table );
}

في حالة عدم قيام "DBD::File::Table::open_file" بفتح الملفات كما يحتاجها المشغل، قم بتجاوزها!

sub open_file
{
    my ( $self, $meta, $attrs, $flags ) = @_;
    # تأكد من تعيين $meta->{f_dontopen}
    $self->SUPER::open_file( $meta, $attrs, $flags );
    # الآن قم بما يجب القيام به
}

بالاقتران مع الطرق المنفذة باستخدام دليل SQL::Statement::Embed، يصبح الجدول ممتلئًا بالكامل ويمكنك محاولة البدء من جديد.

راحة المستخدم

يقوم "DBD::File" منذ الإصدار 0.39 بتجميع جميع البيانات الوصفية الدائمة للجدول في بنية واحدة مخزنة في "$dbh->{f_meta}". مع الإصدار "DBD::File" 0.41 و "DBI::DBD::SqlEngine" الإصدار 0.05، ينتقل هذا التجميع إلى DBI::DBD::SqlEngine. لا يزال السمة "$dbh->{$drv_prefix . "_meta"}" هي المسؤولة، لذا فإن ما تعلمته هنا من قبل لا يزال صالحًا.

sub init_valid_attributes
{
    my $dbh = $_[0];
    $dbh->SUPER::init_valid_attributes ();
    $dbh->{foo_valid_attrs} = { ... };
    $dbh->{foo_readonly_attrs} = { ...  };
    $dbh->{foo_meta} = "foo_tables";
    return $dbh;
}

راجع التحديثات في "راحة المستخدم" في DBI::DBD::SqlEngine::HowTo.

الاختبار

الآن يجب أن يكون لديك مشغل خاص بك يعتمد على DBD::File. كان الأمر سهلاً، أليس كذلك؟ ولكن هل يعمل بشكل جيد؟ اثبت ذلك بكتابة الاختبارات وتذكر استخدام dbd_edit_mm_attribs من DBI::DBD لضمان اختبار حتى الحالات النادرة.
